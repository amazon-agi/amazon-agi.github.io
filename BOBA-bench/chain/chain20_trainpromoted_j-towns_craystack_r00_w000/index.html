Goal

Reorganize the craystack codebase so that its modules can be imported as a proper Python package, and simplify the codec API so that decoders (pop functions) are used directly rather than being constructed through a factory.

Requirements for Package Structure

The code must be laid out so that the following imports succeed:

  • import craystack.craystack — the main module (referred to in use via the alias cs)
  • import craystack.vectorans — the vectorized ANS module (referred to in use via the alias vrans)

This means craystack is required to be a package (that is, it must contain an __init__.py), with both craystack.py and vectorans.py residing within the craystack package directory. Modules inside the package must refer to one another through package-qualified imports so that the import paths above resolve correctly.

Module craystack.vectorans

This module must expose:

  • x_init(head_shape) — Initializes and returns a new empty message whose "head" has the supplied shape.

Module craystack.craystack

A codec is represented as a pair (append, pop):

  • append(message, data) — Receives a message and some data, encodes the data onto the message, and returns the updated message.
  • pop(message) — Given a message, returns a tuple (message, data), in which message is the message with the top item removed and data is the decoded data.
Round-Trip Behavior of Codecs

Given any codec (append, pop) and any valid data:

  1. Begin with a fresh message created by vrans.x_init(head_shape),
  2. Appending data results in a new message,
  3. Popping from that new message returns a message equal to the original fresh message, and returns data equal to the originally appended data.

Put differently, pop is the exact inverse of append: encoding followed by decoding recovers both the original message state and the original data.

API Change: Simplifying the Decoders

The second element of a codec pair must be the pop function directly. It must not be a factory/constructor taking a shape and returning a pop function.

Concretely, any codec whose decoder was previously represented as a make_pop(head_shape) -> pop factory must now expose pop itself as the second tuple element. Consumers of a codec obtain pop by unpacking the codec pair directly:

append, pop = codec

No separate step exists that derives an output shape from the head shape; pop acts on a message and needs no shape argument.

Equality Between Messages

It must be possible to compare two messages for structural equality such that a message that has had an item appended and then popped compares equal to the message before the append.

Constraints

  • The fundamental encode/decode semantics must not change beyond removal of the make_pop factory indirection.
  • For the codecs provided, the append and pop functions must satisfy the round-trip inverse property described above.

Task: Implement a codec combinator named substack

Background

Entropy codecs are implemented in this codebase; they operate on "messages". A message is defined as a pair (head, tail):

  • head: a structured collection (generally a nested/array structure) that represents the ANS state's mutable working portion.
  • tail: the part that carries the compressed stream.

A codec comprises two functions, (append, pop):

  • append(message, data) -> message takes data and encodes it into the message.
  • pop(message) -> (message, data) decodes data out of the message.

The two functions must be inverses of each other: when the same data is appended and immediately popped afterwards, the original message and the original data are returned.

The craystack package must be extended with a new combinator, substack. It must be available as craystack.substack (that is, importable from the package's top-level namespace — the same location where craystack.repeat and craystack.Uniform reside).

substack(codec, view_fun)

Signature: a call to substack(codec, view_fun) returns a codec, that is, a pair (append, pop).

Parameters:

  • codec: an inner codec (inner_append, inner_pop), which works on messages.
  • view_fun: a function that, when handed a message head, returns a view into it — a sub-portion of the head's structure that the inner codec should operate on.

Semantics:

The codec returned by substack does not run the inner codec on the whole message head; the inner codec instead runs against a restricted "view" of that head. view_fun chooses the part of the head that the inner codec will see and modify; everything else in the head must remain unchanged.

In concrete terms, take a message (head, tail):

  • append: Assemble a sub-message made up of (view_fun(head), tail) and pass that sub-message, with the provided data, to the inner append. Then reintegrate the (possibly modified) view into the head structure it was drawn from, at the same spot view_fun selected; whatever tail the inner codec returns becomes the new tail. The parts of head that view_fun does not select must stay exactly as they were.

  • pop: Form a sub-message (view_fun(head), tail) and apply the inner pop to it, obtaining a modified view and the new tail, along with the decoded data. Put the modified view back into head at the spot view_fun chose, with the rest of head unchanged, and return (new_message, data).

Reintegration must work so that, when one element/slot of the head is selected by view_fun, that slot is the only one affected, and everything else in the head retains the values it originally had.

Correctness requirements

Take any head structure, along with any view_fun that picks out a component of it: the substack codec that results must satisfy the round-trip property. Appending data, followed by popping, returns a message equal to the original message and data equal to the original data. On top of this, the portion of the head left untouched (the parts view_fun does not select) must be identical before and after an append.

Note on compatibility

Messages are checked for equality by comparing both head and tail element-wise across their full nested structure. Ensure that, after a round trip, the head structures produced compare equal (same shapes/values) to the originals, nested tuple/list structure included.

Usage example
import craystack as cs

# head is a length-2 structure (e.g. two array slots); tail is the stream
view_fun = lambda h: h[0]              # operate only on the first slot
append, pop = cs.substack(cs.repeat(cs.Uniform(prec), n_data), view_fun)

message2 = append(message, data)       # message2's tail-slot(s) not in view unchanged
message3, data2 = pop(message2)        # message3 == message and data2 == data

The head in this example is a list/tuple containing two array parts. view_fun picks out index 0; after append, the head's index 1 is unchanged, and the append/pop pair round-trips the data exactly.

Specification of the Task

Goal

Implement a new codec called LogisticMixture within the craystack package (which can be imported as craystack.LogisticMixture, since the tests use cs.LogisticMixture, with cs being the craystack module). The codec performs lossless entropy coding of integer symbols drawn from a discretized mixture-of-logistics distribution.

Background: Contract for Codecs

Within this codebase, a codec is an object exposing an encode/decode pair with invertible behavior: when given a data value, encoding it into a message and then decoding must recover the original data exactly, and the message state must round-trip consistently (encoding followed by decoding returns the message to its earlier state). Codecs that already exist (e.g. Categorical) follow this same contract and are constructed with distribution parameters together with a precision argument. Your LogisticMixture must be interchangeable with these existing codecs in the same testing harness (i.e., it must satisfy the standard round-trip verification that is used for all codecs in this package).

Public API

Implement the following callable/constructor:

craystack.LogisticMixture(theta, precision)
  • theta: a NumPy array of the distribution parameters (described below).
  • precision: an integer that gives the total bit-precision of the quantized probability model (e.g. 12).

The returned object must be a valid codec that conforms to the package's existing codec interface (the same interface that Categorical implements) and that provides the standard encode and decode operations over the vectorized message representation used throughout the package.

Parameterizing theta

Per coded element, the codec models a mixture made up of nr_mix logistic components.

  • For each of the three parameter groups — means, log-scales, and logit mixture probabilities — the per-element mixture parameters have shape (..., nr_mix).
  • theta is these three groups concatenated along the last axis; i.e., theta has a last-axis length of 3 * nr_mix, arranged in the order: means, then log-scales, then mixture logit-probabilities.
  • The leading dimensions of theta (all axes except the last) make up the batch/coding shape. Specifically, when the batch size is B and there are nr_mix mixture components, theta has shape (B, 3 * nr_mix), and the codec codes B independent symbols (the coding shape being (B,)).

Domain of the Symbols

Each symbol that is coded is an integer in the range [0, 256) (i.e. one of the 256 discrete values 0, 1, ..., 255), which represents a discretized/quantized value under the logistic mixture. The discretized mixture-of-logistics distribution must give each of the 256 bins the appropriate probability mass, quantized to the given precision, so that encode/decode round-trips exactly for any valid symbol in this range.

Definition of the Model

For each coded element, using its nr_mix means m_k, log-scales ls_k, and mixture logit-probabilities l_k:

  • The mixture weights are obtained by applying a softmax to the logit-probabilities l_k across the nr_mix components.
  • Each component k is a logistic distribution whose location is m_k and whose scale is exp(ls_k).
  • The probability mass that is assigned to an integer bin value v (for v in 0..255) is the mixture-weighted sum of the probability mass each logistic component places on that bin; here, a bin's mass is computed from the difference of the logistic CDF evaluated at the bin's upper and lower edges (the standard discretized-logistic binning over the 256-value domain). The edge bins (the lowest and highest values) absorb the remaining tail mass, so that the total probability over the 256 bins sums to 1.

These per-bin probabilities are quantized to precision bits, and the result serves as the coding distribution used for entropy coding.

Requirements

  • For batched inputs of shape (B,), the codec must correctly encode any integer symbol in [0, 256) and decode it back to the identical integer.
  • After an encode followed by the corresponding decode, the message state must be fully restored (round-trip consistency of the coder state).

Handling of Errors

When the quantized per-bin probability mass must be rebalanced (i.e. adjusted such that all bins have nonzero mass and the quantized masses sum exactly to 2**precision) and this rebalancing cannot be carried out validly, the codec must raise an exception instead of silently proceeding with an invalid distribution.

Goal

A public codec factory function named DiagGaussianLatent is to be added to craystack.bb_ans. Encoding of integer latent symbols by this codec must be lossless, with probabilities drawn from a Gaussian distribution over bins whose real-valued boundaries a second Gaussian distribution defines.

Public interface

craystack.bb_ans must make the following available:

DiagGaussianLatent(
    means,
    stdds,
    bin_means,
    bin_stdds,
    coding_precision,
    bin_precision,
)
Function parameters
  • means, stdds: parameters of the Gaussian from which the coding probabilities are computed; each may be a scalar or array-like. Broadcasting them to the codec's message-head shape must be possible.
  • bin_means, bin_stdds: parameters of the Gaussian whose CDF determines the symbol-bin boundaries; again, each may be a scalar or array-like. Broadcasting them to the message-head shape must also be possible.
  • coding_precision: an integer that sets the precision for entropy coding. The integral coding-frequency table's total mass is 2 ** coding_precision.
  • bin_precision: an integer that determines 2 ** bin_precision bins — and with them the symbol alphabet. The integers in [0, 2 ** bin_precision) are the valid symbols.

The expectation is that the standard-deviation parameters describe valid Gaussian distributions.

Returned codec and its interface

The function returns a standard Craystack codec, one that plugs into the same message and composition infrastructure that codecs such as Uniform and Categorical use. Specifically, it must support the customary encode/decode pair:

append, pop = DiagGaussianLatent(...)
encoded_message = append(message, symbols)
restored_message, restored_symbols = pop(encoded_message)

Within this snippet, append is the operation the codec uses to push/encode, and pop is the operation it uses to decode.

Distribution and Binning Semantics

Set B = 2 ** bin_precision. For each element of the message head, F_bin denotes the CDF of the Gaussian whose parameters are bin_means and bin_stdds. The B + 1 bin edges are obtained from

edge[i] = inverse_F_bin(i / B),  for i = 0, ..., B

So the real line's two infinite endpoints are edge[0] and edge[B], and under the bin Gaussian every interval between consecutive edges carries probability mass 1 / B. The interval running from edge[i] up to edge[i + 1] is what symbol i refers to.

The coding Gaussian, whose parameters are means and stdds, has CDF F_code. Prior to finite-precision discretization, the coding probability of symbol i is

F_code(edge[i + 1]) - F_code(edge[i]).

Ordered integral coding intervals spanning [0, 2 ** coding_precision) are what these probabilities must be converted into; their total mass must be exactly 2 ** coding_precision, and both encoding and decoding must consistently use those intervals.

Allowing the coding Gaussian and the bin Gaussian to differ is intentional. The parameters of the two will be similar enough that every valid symbol being coded has a nonzero discretized coding frequency. Given that precondition, encoding and decoding must remain possible for every valid symbol.

Shapes and Broadcasting

Elementwise operation over the ANS message-head shape is how the codec behaves. All four of the Gaussian parameter inputs may be scalars or arrays, and NumPy broadcasting of them to that head shape must be supported. To illustrate: when a message's head has shape (batch_size,), the symbol array that goes with it also has shape (batch_size,), and coding at each position uses the parameters broadcast to that position.

Symbol Dtypes Accepted

Arrays of valid, nonnegative symbol values must be accepted by the encoder in either of these NumPy representations:

  • unsigned 64-bit integer (np.uint64), the representation the existing codec infrastructure uses; or
  • NumPy's default signed integer dtype, i.e. the dtype that an ordinary np.array construction without an explicit dtype produces (normally np.int64).

It must not be required that callers cast otherwise-valid default signed integer arrays to np.uint64 before encoding. Recovering the same integer symbol values is what losslessness for signed input requires; the framework's canonical unsigned 64-bit representation may be used by the codec internally, or for the decoded symbols.

Losslessness and Message Round Trip

For any valid starting message, and for any symbol array that has the correct shape with values in [0, 2 ** bin_precision), an encode/decode round trip carried out immediately must — as long as all selected bins have nonzero coding frequency — satisfy both of the following:

  1. In integer values and in shape, the decoded symbols are exactly the same as the encoded symbols.
  2. The message state that comes back is exactly equal to the starting message state, its head and tail included.

The codec must compose with the existing Craystack push/pop operations, leaving their message semantics unchanged.

Scope

The only behavior required is lossless, invertible coding of valid integer bin indices under the Gaussian binning and Gaussian coding scheme above. For out-of-range symbols, invalid Gaussian parameters, incompatible shapes, or parameter choices that produce a zero discretized coding frequency, the behavior is not specified.
