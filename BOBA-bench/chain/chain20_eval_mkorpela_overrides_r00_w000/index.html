Specification for the overrides Module

Goal

The task is to build a Python module named overrides whose two public decorators are overrides and final. Importing both directly from the module must be possible:

from overrides import overrides, final

The overrides Decorator

overrides is a decorator for methods, used on a method that a subclass declares. As the class is being defined, it checks that the method carrying the decorator genuinely overrides a like-named method supplied by one of the class's base classes.

Behavior

  1. Checking that an override exists. When a class defines a method carrying @overrides, the decorator must make sure that at least one of the base classes declares a method whose name is the same — the search spans the entire inheritance hierarchy and takes in base classes declared in other modules together with built-in types.

    • When no ancestor class supplies a method of that name, an AssertionError must be raised. The error is raised during class definition — that is, while the class statement is being executed — so merely defining such a class is enough to trigger the failure.
    • When an ancestor does hold the matching method, the class definition goes ahead as usual.

  2. Handing down the docstring. With no docstring of its own on the overriding method, the decorated method must expose the docstring belonging to the overridden ancestor method (reachable via __doc__ on the bound method). When the overriding method has a docstring of its own, that docstring must be kept and used; the ancestor's docstring must not be put in its place.

  3. Unchanged behavior. The decorated method must stay fully callable, and it must return exactly what the body of the original method returns. The method's runtime behavior and its return value must not be changed by the decorator.

  4. Overriding special and built-in methods. Overriding a method inherited from a built-in type must be handled correctly by the decorator (an example is subclassing int and overriding __str__). An override of this kind must pass validation, and it is the overriding implementation that must be invoked.

Hierarchy-wide search

The ancestor search must take all base classes and their ancestors into account, in any order, including:

  • A parent reached through direct single inheritance.
  • Multiple base classes at once, where the overridden method may sit in any of them (this includes a base class imported from a different module).
  • Ancestors that lie deeper and are reached transitively by way of the base classes.

The final Decorator

final is a decorator that attaches to methods: it marks the method as final, and subclasses are then forbidden to override it.

Behavior

  1. Applying the mark. @final attached to a method designates that method as final. The finalized method stays fully callable and returns exactly the value its body returns; final must not modify the method's runtime behavior or its return value.

  2. Prevention of overriding. If a subclass defines — at any depth within the hierarchy — a method carrying @overrides whose name matches a method marked @final anywhere within its ancestor hierarchy, an AssertionError must be raised while the class is being defined.

    • This enforcement takes effect no matter where the finalized method sits:
      • in a direct parent,
      • in a more remote ancestor (deep in the chain),
      • in an intermediate class located mid-chain,
      • or in a base class that a different module defines.
    • Methods inherited without the final mark may be overridden freely (the ordinary overrides validation described above still applies to them).

  3. How final and overrides interact. A finalized method may be inherited by a subclass and called in the normal way (it is present on instances and returns the original value). Overriding a finalized method is the only thing that is prohibited.

Requirements in Combination

  • A single subclass may override some methods that are not final (valid) while, at the same time, inheriting finalized methods from multiple ancestors (also valid). Defining such a class must succeed; the methods it overrides must return their new values and inherit docstrings correctly; and the finalized methods it inherits must stay callable and return their original values.
  • Any attempt at overriding a finalized method — wherever in the inheritance graph that finalized method is located — must make the class definition fail with AssertionError.

Both decorators work on functions/methods and keep their call semantics and return values intact.

Goal

Write a function that checks whether one function signature (a "subtype") is a compatible substitute for another function signature (a "supertype"), in line with Liskov substitution principles for callables. An error must be raised when the subtype is not a valid substitute.

Both arguments are callables (e.g. Python functions). The function examines their signatures and type annotations. It returns None when sub_callable is a valid, compatible substitute for super_callable; in every other case it raises TypeError.

Rules for Compatibility

Treat the first argument as the super signature and the second as the sub signature. ensure_compatible(super_callable, sub_callable) must raise TypeError unless all of the following are satisfied.

Return type compatibility

The sub-callable's return annotation must be a subtype of (or equal to) the super-callable's return annotation. If the two are incompatible (e.g. super returns int, sub returns str), TypeError must be raised. Widening the return (e.g. super returns str, sub returns object) is compatible.

Positional matching of parameters

Parameters are paired up positionally between the two signatures, in declaration order. Each super parameter must correspond to a sub parameter in a way that satisfies the constraints below.

Parameter naming

Corresponding positional parameters must share the same name. If a parameter that must be matched carries a different name in the sub signature than in the super signature (e.g. super x, y vs sub y, x), TypeError must be raised.

Types of parameters (contravariance)

For each matched parameter, the sub parameter's annotated type must be a supertype of (or equal to) the super parameter's annotated type. In other words, the sub may widen (accept more) but not narrow. When the super parameter is annotated object and the corresponding sub parameter is annotated str, that is a narrowing and must raise TypeError. Widening (super str, sub object) is allowed. Parameters left unannotated are treated as compatible.

Kinds of parameters

The Python parameter kinds are: POSITIONAL_ONLY, POSITIONAL_OR_KEYWORD, KEYWORD_ONLY, VAR_POSITIONAL (*args), VAR_KEYWORD (**kwargs).

The sub signature must accept every way of calling that the super signature accepts. In particular:

  • A super POSITIONAL_ONLY parameter may be matched by a sub parameter that is either POSITIONAL_ONLY or POSITIONAL_OR_KEYWORD (this broadens the ways the argument may be passed — allowed).
  • A super KEYWORD_ONLY parameter may be matched by a sub parameter that is either KEYWORD_ONLY or POSITIONAL_OR_KEYWORD (allowed).
  • A super POSITIONAL_OR_KEYWORD parameter must be matched by a sub parameter that is POSITIONAL_OR_KEYWORD.
  • Restricting the calling convention is not allowed. For instance, when the super parameter is POSITIONAL_OR_KEYWORD but the corresponding sub parameter is KEYWORD_ONLY (the argument can no longer be passed positionally), TypeError must be raised.
Extra parameters declared in the sub signature

The sub signature may declare additional parameters beyond those in the super signature only if doing so does not break callability, i.e. any extra parameters must have default values (or be absorbed by variadic parameters). If the sub signature requires more parameters than the super signature supplies — e.g. super (x) vs sub (x, y) where y has no default — TypeError must be raised.

Parameters missing from the sub signature

The sub signature is permitted to leave out parameters that the super signature declares when:

  • the omitted parameter has a default value in the super signature, or
  • the argument can be absorbed by the sub signature via *args (for positional arguments) or **kwargs (for keyword arguments).

Otherwise, the omission of a required parameter is incompatible and must raise TypeError.

Variadic parameter handling

If the sub signature contains *args and/or **kwargs, it can accept positional and keyword arguments respectively that are not explicitly enumerated, thereby satisfying the corresponding super parameters as described above.

Compatible Signature Examples

The pair below is compatible (no exception raised):

  • super: def sup(a, /, b: str, c: int, *, d, e, **kwargs) -> object
  • sub: def sub(a, b: object, c, d, f: str = "foo", *args, g: str = "bar", e, **kwargs) -> str

Here: a changes from positional-only to positional-or-keyword (allowed); the type of b widens from str to object (allowed) and its kind broadens; c is unannotated in the sub (compatible); d moves from keyword-only to positional-or-keyword (allowed); the sub adds f and g with defaults (allowed); e remains keyword-only; both have **kwargs; and the return narrows from object to str (allowed).

Cases that Must Raise TypeError

  • Incompatible return types: super returns int, sub returns str.
  • Positional parameters reordered/renamed: super (x, y), sub (y, x).
  • Parameter type narrowed: super (x: object), sub (y: str).
  • Calling convention restricted: super (x, /, y), sub (x, *, y).
  • Extra parameter that is required: super (x), sub (x, y).

Value Returned

On success, the function finishes normally (returns None). Incompatibility is communicated solely by raising TypeError.

Task: Disregard the First Parameter When Validating Overridden Method Signatures

Background

A Python package going by the name overrides makes a decorator available that is likewise called overrides; it can be imported as follows:

from overrides import overrides

Applying the decorator to a method written in a subclass marks that method as overriding the identically named method declared in the superclass. In the course of this, it validates signature compatibility, comparing the overriding method with the method it overrides.

The decorator accepts a keyword argument, check_at_runtime, of boolean type. Setting check_at_runtime=True means the compatibility validation involving the subclass method and the corresponding superclass method gets carried out, and (if incompatible) it raises at call/definition time, in the same way it currently behaves for the other checks.

The Change to Make

During the comparison of an overriding method's signature against the overridden method's, the first parameter must be ignored in the case of non-static methods. The rule covers both of the following:

  • Regular instance methods: by convention their first parameter is self.
  • Class methods (methods decorated with @classmethod): by convention their first parameter is cls.

The motivation: for an instance method or a class method, the subclass may legitimately give the first parameter a different type annotation than the one found in the superclass. Take instance methods as an example: the superclass's version may annotate self with the superclass type, and the overriding subclass version instead gives self the subclass type as its annotation. Class methods behave in parallel: cls may be annotated Type[SuperClass] in the superclass, while the subclass gives it Type[SubClass]. Differences of this sort in the first parameter must not make the signature-compatibility validation fail.

In concrete terms, every case below must be considered a valid override and must not raise; this also holds when check_at_runtime=True has been set and the methods get called:

  • A subclass instance method that overrides a superclass instance method, where the subclass method's one and only parameter (which is also its first), self, carries an annotation of the subclass type, while the superclass method's self is annotated with the superclass type. When this method is called on an instance of the subclass, it must succeed and return normally.
  • A subclass class method that overrides a superclass class method, where the subclass method's one and only parameter (which is also its first), cls, carries the annotation Type[Subclass], while the superclass method's cls is annotated with Type[Superclass]. When this class method is called on an instance of the subclass, it must succeed and return normally.

Behavioral Requirements, Summarized

  • With check_at_runtime=True in effect, the overrides decorator must accept an overriding instance method or class method whose first parameter carries a type annotation different from the overridden method's, without raising, as long as the remaining parameters are compatible.
  • Methods decorated like this must still be callable and behave normally (an instance method annotated so that it returns the subclass instance does return the instance; a class method annotated so that it returns None does return None).

Public API

  • overrides.overrides — the decorator itself, which supports the check_at_runtime keyword argument.

There is no need for any new public API; what must be adjusted is the existing decorator's signature-comparison behavior, so that compatibility checking no longer takes the first parameter of non-static methods into account.
