Task Specification: overrides Module

Objective

Implement a Python module named overrides that provides two public decorators: overrides and final. Both must be importable directly from the module:

from overrides import overrides, final

Decorator: overrides

overrides is a method decorator applied to a method defined inside a subclass. It validates, at class-definition time, that the decorated method actually overrides a method of the same name inherited from one of the class's base classes.

Behavior

  1. Validation of override existence. When a method decorated with @overrides is defined in a class, the decorator must verify that at least one of the base classes (searched across the full inheritance hierarchy, including base classes defined in other modules and built-in types) declares a method with the same name.

    • If no ancestor class provides a method of that name, an AssertionError must be raised. This error is raised during class definition (i.e., while the class statement is being processed), so simply defining such a class triggers the failure.
    • If a matching ancestor method exists, class definition proceeds normally.

  2. Docstring inheritance. If the overriding method has no docstring of its own, the decorated method must expose the docstring of the overridden ancestor method (accessible via __doc__ on the bound method). If the overriding method has its own docstring, that docstring must be preserved and used (the ancestor's docstring must not replace it).

  3. Behavior preservation. The decorated method must remain fully callable and return exactly what the original method body returns. The decorator must not alter the method's runtime behavior or return value.

  4. Overriding built-in / special methods. The decorator must correctly handle overriding methods inherited from built-in types (for example, subclassing int and overriding __str__). Such an override must validate successfully and the overriding implementation must be the one invoked.

Search across the hierarchy

The ancestor lookup must consider all base classes and their ancestors, in any order, including:

  • Direct single-inheritance parents.
  • Multiple base classes, where the overridden method may live in any of them (including a base class imported from a different module).
  • Deeper ancestors reachable transitively through the base classes.

Decorator: final

final is a method decorator that marks a method as final, meaning subclasses are forbidden from overriding it.

Behavior

  1. Marking. Applying @final to a method marks it as final. A finalized method remains fully callable and returns exactly what its body returns; final must not change the method's runtime behavior or return value.

  2. Enforcement against overriding. When a subclass (at any depth in the hierarchy) defines a method decorated with @overrides whose name matches a method that was marked @final anywhere in its ancestor hierarchy, an AssertionError must be raised during class definition.

    • This enforcement applies whether the finalized method is:
      • in a direct parent,
      • in a more distant ancestor (deep in the chain),
      • in an intermediate class in the middle of the chain,
      • or in a base class defined in a different module.
    • Non-final inherited methods may be overridden freely (subject to the normal overrides validation described above).

  3. Interaction with overrides. A subclass may inherit a finalized method and call it normally (it is available on instances and returns its original value). Only overriding a finalized method is prohibited.

Combined Requirements

  • A single subclass may simultaneously override some non-final methods (valid) while inheriting finalized methods from multiple ancestors (also valid). Such a class must define successfully, its overridden methods must return their new values with correct docstring inheritance, and its inherited finalized methods must remain callable and return their original values.
  • Any attempt to override a finalized method — regardless of where the finalized method sits in the inheritance graph — must cause the class definition to fail with AssertionError.

Implement a signature-compatibility checker used by an override-enforcement system. It verifies that a subclass callable (the overrider) has a signature compatible with a superclass callable (the overridden method), following Liskov-style substitution for callables.

The governing rule is: every call form that is valid for the superclass callable must also be valid for the overriding callable.

Public API

Provide the following importable function:

  • overrides.enforce.ensure_compatible(super_callable, sub_callable)

The following names must also remain importable from the overrides package:

  • overrides.overrides
  • overrides.final
  • overrides.EnforceOverrides

Their behavior beyond importability is outside the scope of this task.

Function: ensure_compatible(method, override)

ensure_compatible(method, override)

The function takes two callable arguments:

  • method: the superclass callable being overridden.
  • override: the subclass callable intended to override it.

If override is a valid substitute for method, the function returns normally; no meaningful return value is required. If any required signature relationship is incompatible, it raises TypeError. No particular exception message is required.

Type compatibility

Return annotations

When both callables declare return annotations, the return annotation of override must be the same as or a subtype of the return annotation of method (covariance).

For example, an overriding return type of str is compatible with a superclass return type of object, but the reverse is not.

If either return annotation is absent, do not reject the pair on the basis of the return annotation.

Parameter annotations

For each corresponding parameter that is annotated in both callables, the annotation in override must be the same as, a supertype of, or otherwise less restrictive than the annotation in method (contravariance).

For example, widening a parameter annotation from str in method to object in override is allowed; narrowing it from object to str is not. Similarly, widening int to Union[int, str] is allowed, while the reverse direction is not.

If either corresponding parameter is unannotated, do not reject the pair on the basis of that parameter's annotation. Missing annotations do not relax any parameter-name, order, kind, or arity requirements.

Parameter correspondence, names, order, and kinds

Parameter compatibility is determined by the call forms each parameter supports, not just by the total parameter count.

Positional-or-keyword parameters

A fixed positional-or-keyword parameter in method can be supplied either positionally or by its keyword name. An explicitly corresponding fixed parameter in override must therefore:

  • retain the same name;
  • retain the same position in the positional parameter sequence; and
  • continue to accept both positional and keyword use.

Renaming or reordering corresponding positional-or-keyword parameters is incompatible and must raise TypeError, even when the parameters are unannotated or their annotations would otherwise be compatible. For example:

def method(x, y): ...
def override(y, x): ...

ensure_compatible(method, override)  # raises TypeError

The reordered signature does not preserve all mixed positional/keyword calls, such as method(1, y=2). Likewise, replacing a fixed x parameter with a fixed parameter named y loses calls made with x=....

A positional-or-keyword parameter may instead be covered generically only when override provides both the required positional and keyword acceptance, such as through the combination of *args and **kwargs. *args alone does not preserve keyword calls, and **kwargs alone does not preserve positional calls.

Other parameter kinds
  • A positional-only parameter in method must remain acceptable in its positional slot. It may be represented by a positional-only parameter, widened to a positional-or-keyword parameter, or accepted through *args, provided all valid positional calls and annotation constraints remain supported.
  • A keyword-only parameter in method must remain acceptable under the same keyword name, or be accepted through **kwargs. It may be widened to a positional-or-keyword parameter. Keyword-only parameters may be reordered because their declaration order does not change keyword call validity.
  • A positional-or-keyword parameter in method cannot be narrowed to only positional-only or only keyword-only acceptance unless the otherwise lost call form is also accepted by an appropriate catch-all.

Any kind conversion is allowed only when it does not remove a calling form accepted by method.

Arity and signature-shape compatibility

Positional arguments
  • override must accept every positional call accepted by method, including calls with no positional arguments when those are valid.
  • If method accepts an arbitrary number of positional arguments through *args, override must also accept an arbitrary number of positional arguments through a *args-style catch-all. A bounded number of positional parameters is not sufficient.
  • override may accept more positional arguments than method, using extra optional positional parameters or *args, as long as it still accepts every positional call valid for method.
  • An override that removes a positional argument accepted by method is incompatible.
Keyword arguments
  • override must accept every keyword name and combination accepted by method.
  • If method accepts arbitrary keyword names through **kwargs, override must also have a **kwargs-style catch-all. A fixed set of keyword names is not sufficient.
  • override may accept more keyword arguments than method, using extra optional keyword-capable parameters or **kwargs, as long as every keyword call valid for method remains valid.
Extra parameters in the override

override may introduce parameters that do not correspond to parameters in method only when they do not make any formerly valid call fail:

  • Extra positional, positional-or-keyword, and keyword-only parameters must have defaults.
  • Extra *args and **kwargs parameters are allowed because they do not require additional arguments.
  • Any other extra required parameter makes the signatures incompatible and must raise TypeError.

Worked examples

The notation method(...) => override(...) below means that a call valid for the first callable must remain valid for the second.

Arbitrary positional arguments
def sub1(x=2, y=3, z=4, /): ...
def subbest(x=1, /, *burgs): ...
def supah(*args): ...

The following are compatible:

ensure_compatible(supah, subbest)
ensure_compatible(sub1, subbest)

subbest accepts supah(), supah(2), supah(2, 3), and arbitrarily longer positional calls. It also accepts both sub1() and sub1(1, 2, 3).

The following are incompatible and must raise TypeError:

ensure_compatible(supah, sub1)
ensure_compatible(subbest, sub1)

In both cases the first callable can accept four or more positional arguments, while sub1 accepts at most three.

Arbitrary keyword arguments
def sub1(*, x=3, y=3, z=4): ...
def sus(*, x=3, **kwargs): ...
def superb(**kwargs): ...

The following are compatible:

ensure_compatible(superb, sus)
ensure_compatible(sub1, sus)

sus accepts empty keyword calls, named calls such as x=4, arbitrary names such as foo=1, and combinations of known and arbitrary names.

The following are incompatible and must raise TypeError:

ensure_compatible(superb, sub1)
ensure_compatible(sus, sub1)

sub1 cannot accept arbitrary keyword names.

Optional parameters added by the override

A no-argument superclass callable is compatible with overriding callables that add only optional parameters:

def superb(): ...
def optional_arg(arg=1): ...
def optional_positional_arg(arg2=2, /): ...
def optional_kw_only_arg(*, arg3=3): ...

ensure_compatible(superb, optional_arg)
ensure_compatible(superb, optional_positional_arg)
ensure_compatible(superb, optional_kw_only_arg)

All three overrides still accept the valid zero-argument call.

Generic override

An override using both catch-alls can accept a fixed superclass signature:

def method(x: int, y: Optional[str], z: float = 3.0): ...
def generic_override(*args, **kwargs): ...

ensure_compatible(method, generic_override)

The reverse direction is incompatible because the fixed signature cannot accept every arbitrary positional and keyword call supported by generic_override.

Mixed compatible signature

The following pair is compatible:

def method(a, /, b: str, c: int, *, d, e, **kwargs) -> object: ...
def override(
    a,
    b: object,
    c,
    d,
    f: str = "foo",
    *args,
    g: str = "bar",
    e,
    **kwargs,
) -> str: ...

Here:

  • b is widened from str to object;
  • the return type is narrowed from object to str, which is valid covariance;
  • required keyword-only parameters d and e remain accepted by name;
  • positional-only a is widened to positional-or-keyword acceptance;
  • extra parameters f and g are optional; and
  • the catch-alls preserve additional positional and keyword calls.

Compatibility

The checker must work on Python 3.8 and later, including signatures that use / for positional-only parameters and * for keyword-only parameters.

Raise/return contract

Return normally when override is a valid substitute for method. Raise TypeError when it is not, including for:

  • an incompatible return annotation;
  • an incompatibly narrowed parameter annotation;
  • renamed or reordered corresponding positional-or-keyword parameters;
  • incompatible parameter kinds;
  • a missing accepted positional or keyword call form;
  • failure to preserve *args or **kwargs capacity; or
  • an additional required parameter in override.

Behavior of ensure_signature_is_compatible

The function takes two callables: a "super" callable (representing a method defined in a base class) and a "sub" callable (representing an overriding method in a subclass). It verifies that the sub callable's signature is a compatible override of the super callable's signature.

  • If the signatures are compatible, the function returns normally (no return value is required).
  • If the signatures are incompatible, the function raises TypeError.

Compatibility means that any call that is valid against the super callable's signature must also be valid — with type-consistent arguments — against the sub callable's signature. The following rules define compatibility:

Return types
  • The sub callable's return type annotation must be compatible with (i.e., a subtype of, or equal to) the super callable's return type annotation. Incompatible return types are an error.
Parameter types
  • For each parameter that corresponds between the two signatures, the sub callable's parameter type annotation must accept at least everything the super callable's parameter type annotation accepts. In other words, the sub parameter's declared type must be equal to or wider than the super parameter's type.
    • A parameter annotated object is wider than one annotated with a concrete type.
    • A parameter annotated typing.Union[A, B] is wider than one annotated with just A. Narrowing a parameter's accepted types (e.g., super accepts Union[int, str] but sub accepts only int) is an error.
  • A missing type annotation (untyped parameter, as with *args/**kwargs in a fully generic signature) is treated as the widest possible type; a generic signature such as (*args, **kwargs) is a compatible override of any more specifically-typed signature, but a specifically-typed signature is NOT a compatible override of a generic one.
Parameter positions and names
  • Positional parameters that correspond between the signatures must appear in the same positions. Reordering positional parameters (e.g., super (x, y) vs. sub (y, x) with incompatible types resulting) is an error.
  • Keyword-accessible parameters are matched by name across the two signatures.
Parameter kinds
  • The kind of each corresponding parameter must remain compatible. Changing a parameter's kind incompatibly (for example, turning a normal parameter into a keyword-only parameter such that a caller's valid call would break) is an error.
Parameter list shape (arity)
  • Every call permitted by the super signature must be permitted by the sub signature.
  • The sub callable must accept at least the arguments the super callable requires:
    • If the super callable requires an argument the sub callable does not accept, that is an error (missing argument).
    • If the sub callable requires an argument (has a mandatory parameter) that the super callable does not provide, that is an error (additional required argument).
  • The sub callable may declare additional optional parameters (parameters with default values), whether normal, positional-only, or keyword-only, since these do not break any call valid against the super signature. This is allowed.
  • If the super signature accepts variadic positional arguments (*args), the sub signature must also be able to accept arbitrarily many positional arguments; a sub signature with only a bounded number of positional parameters is an incompatible override when the super accepts more positional arguments than the sub can (an error).
  • If the super signature accepts arbitrary keyword arguments (**kwargs), the sub signature must also accept arbitrary keyword arguments; otherwise it is an error.
Examples of compatible pairs (must NOT raise)
  • Super (a, b, c, d, *args, e, **kwargs) -> object (roughly) and a sub that adds extra optional and keyword parameters while preserving the required ones, keeps positions, keeps *args/**kwargs, and returns a subtype.
  • Super (x: int) and sub (x: Union[int, str]).
  • A well-typed method (x: int, y: Optional[str], z: float = 3.0) overridden by a generic (*args, **kwargs).
  • Super with only optional positional-only params (x=2, y=3, z=4, /) overridden by a sub that also accepts *args (accepts everything the super does and more).
  • Super with *args overridden by a sub that also has *args (plus optional leading positional-only params).
  • Super with keyword-only params plus **kwargs overridden by a sub with matching keyword-only params plus **kwargs.
  • Super with no parameters overridden by a sub that adds a single optional parameter — as a normal parameter with a default, a positional-only parameter with a default, or a keyword-only parameter with a default.
Examples of incompatible pairs (must raise TypeError)
  • Super returns int, sub returns str.
  • Super (x, y) vs. sub (y, x) (positions/types incompatible).
  • Super (x: object) vs. sub (x: int) (parameter type narrowed).
  • Super (x) (normal) vs. sub where the corresponding parameter becomes keyword-only.
  • Super (x) vs. sub (x, y) where y is required (additional required argument).
  • Super (x) (requires x) vs. sub () (missing argument).
  • Reversing any of the compatible-direction examples above: a narrower sub cannot override a wider super, and a generic super (*args, **kwargs) cannot be overridden by a more specific sub.
  • A super with bounded positional params where a call with more positional args (permitted because super also has *args) would exceed what the sub can accept.
  • A super with **kwargs overridden by a sub lacking **kwargs.

The decorator is used to mark methods in a subclass as overriding a method with the same name in a superclass. It performs signature-compatibility validation between the overriding method and the method it overrides.

  • A class method in the subclass whose sole (first) parameter cls is annotated with Type[Subclass], overriding a superclass class method whose cls is annotated with Type[Superclass]. Calling this class method on an instance of the subclass must succeed and return normally.
