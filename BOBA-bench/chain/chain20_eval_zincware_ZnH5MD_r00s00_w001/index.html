01 H5MD Compliance and API Simplification for znh5md 542 words · source specification, reworded by GLM-5.3-Flash

Task Specification: H5MD Compliance and API Simplification for znh5md

Overview

The znh5md package — a library that writes ASE (Atomic Simulation Environment) trajectory data to HDF5 files and reads such data back from them, in accordance with the H5MD standard — is the focus of this task. Three changes are required: dropping an explicit initialization step, ensuring H5MD compliance so that external tools can read the files, and raising the version.

Requirements

1. Version bump

znh5md.__version__ must be exposed by the package, equal to the string "0.2.0".

2. Drop the initialize_database_groups step

The DataWriter class (importable as znh5md.io.DataWriter) must no longer require any explicit group-initialization step before the data is written.

  • The public method initialize_database_groups() must be dropped from DataWriter (it must no longer form part of the public API).
  • As part of the normal writing workflow, any HDF5 groups needed to store data must be created automatically, and only when required.

The typical workflow must look as follows:

db = znh5md.io.DataWriter(filename="db.h5")
reader = znh5md.io.AtomsReader(atoms_list)
db.add(reader)

When db.add(...) is called immediately on a freshly constructed DataWriter (with no prior initialization call), the data must be written to the file successfully. After a write carried out this way, all of the existing reading/slicing/property behavior via znh5md.ASEH5MD("db.h5") must continue to work.

A filename must be accepted by DataWriter(filename=...) when given either as a string or as a pathlib.Path.

3. H5MD compliance (files readable by MDAnalysis)

Files written by DataWriter must conform to the H5MD standard closely enough that the standard MDAnalysis H5MD reader (MDAnalysis.coordinates.H5MD.H5MDReader) can read the trajectory positions back correctly.

Concretely, when a list of ase.Atoms objects has been written to an H5 file via:

db = znh5md.io.DataWriter(filename=filename)   # filename is a pathlib.Path
reader = znh5md.io.AtomsReader(trajectory)
db.add(reader)

the MDAnalysis H5MD reader, on opening the resulting file, must yield a trajectory for which the following hold:

  • its length equals the number of written frames, and
  • for every frame, the positions match (elementwise, within floating-point tolerance) the positions of the corresponding input ase.Atoms objects.

To reach this compliance:

  • Units must be stored as HDF5 attrs (attribute metadata) attached to the appropriate datasets/groups — not as separate datasets — because the H5MD specification requires this.
  • Per the H5MD standard, time information must be written correctly.
  • Periodic boundary conditions (PBC) and box/edges information must be written in a way that makes the file represent standard 3-dimensional data. (The trajectories covered here are 3D atomic systems; e.g. a water molecule made up of 3 atoms whose positions translate linearly from frame to frame.)

For trajectories in which the atoms have positions but no attached calculator/energy data, reading must work (i.e., position-only trajectories must be fully valid).

Public API

The items listed below must stay importable and callable:

  • znh5md.__version__ → "0.2.0"
  • znh5md.io.DataWriter(filename=<str | pathlib.Path>) with method .add(reader) — it has no initialize_database_groups method.
  • znh5md.io.AtomsReader(atoms_list, frames_per_chunk=<int>) — accepts a list of ase.Atoms.
  • znh5md.ASEH5MD(<filename>) — for reading written files back.

Out of Scope and Constraints

  • initialize_database_groups must not be reintroduced or preserved as a required or optional step.
  • Nothing beyond correct H5MD-compliant writing (units in attrs, correct time, 3D/PBC/box data) and the version bump is required.
02 Reading and Writing ASE Atoms in H5MD-Compliant Form 633 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Reading and Writing ASE Atoms in H5MD-Compliant Form

Summary

Implement a Python package znh5md that reads molecular structure trajectories (sequences of ASE Atoms objects) from and writes them to HDF5 files following the H5MD file layout. The output files must be interoperable with the reference pyh5md library — that is, files written by znh5md must be readable by pyh5md, and files written by pyh5md must be readable by znh5md.

Public API

Everything listed in this section must be importable and callable exactly as described:

znh5md.ASEH5MD

A class whose constructor takes one positional argument: a filesystem path (str or pathlib.Path) pointing to an existing H5MD file.

reader = znh5md.ASEH5MD(path)

It must expose the method:

reader.get_atoms_list() -> list[ase.Atoms]

which returns the list of ase.Atoms objects reconstructed from the file — one object per stored frame/step, in the order in which they are stored.

znh5md.io.DataWriter

A class whose constructor accepts one positional argument: a filesystem path (str or pathlib.Path) at which an H5MD file is to be written/created.

db = znh5md.io.DataWriter(path)

It must expose the method:

db.add(reader)

where reader is an AtomsReader instance (see below). Calling add writes the data supplied by the reader into the H5MD file at the writer's path.

znh5md.io.AtomsReader

A class whose constructor takes one positional argument: a list of ase.Atoms objects.

reader = znh5md.io.AtomsReader(list_of_atoms)

It adapts an in-memory list of Atoms into the form that DataWriter.add consumes.

Requirements for the H5MD File Layout

Files that DataWriter writes must conform to the H5MD group/dataset structure so that the pyh5md reference implementation can open them and access the elements below. For a particle group named "atoms" (accessed via pyh5md's particles_group("atoms")), the time-dependent elements below must be present, each with a per-frame value array indexed by frame:

  • position — float, with shape (n_atoms, 3) per frame; equals the atomic positions of each frame.
  • species — integer, with shape (n_atoms,) per frame; equals the atomic numbers of each frame.
  • momentum — float, with shape (n_atoms, 3) per frame; equals the atomic momenta of each frame.
  • forces — float, with shape (n_atoms, 3) per frame; equals the atomic forces of each frame.

In addition, an observable element at path observables/atoms/energy (accessed via pyh5md's element(file, "observables/atoms/energy")) must be present, storing the per-frame potential energy.

For each frame index idx, these elements, when read back, must yield, respectively: the positions, atomic numbers, momenta, forces, and potential energy of the corresponding input Atoms object.

Requirements for Reading

ASEH5MD(path).get_atoms_list() must reconstruct Atoms objects from an H5MD file that follows the layout above (including files produced by pyh5md). Reading files containing the standard H5MD h5md metadata group (with version, author, and creator subgroups/attributes) must work without error. For each frame, the reconstructed Atoms must reproduce:

  • the positions (taken from position)
  • the atomic numbers (taken from species)
  • the momenta (taken from momentum)
  • the forces (taken from forces)
  • the potential energy (taken from observables/atoms/energy)

so that these values compare equal to the source data from which the file was written.

Constraints for Round-Trip and Interoperability

  • Data that znh5md.io.DataWriter writes (fed by znh5md.io.AtomsReader) must be readable by pyh5md and yield exactly the original positions, atomic numbers, momenta, forces, and per-frame energies.
  • Data that pyh5md writes in the layout described above must be readable by znh5md.ASEH5MD and yield Atoms whose positions, momenta, forces, potential energy, and atomic numbers match the originals exactly.
  • The values for distinct frames are in general different; per-frame indexing must be preserved (frame idx maps to input structure idx).

Notes

  • The energy that gets stored is the potential energy obtained from each Atoms' attached calculator.
  • For interoperability, all numeric comparisons are exact (not merely approximate).

Redesign of the ZnH5MD trajectory I/O

Implement an ASE-compatible H5MD trajectory API that provides the public surface and behavior laid out below.

Public API surface

The package root znh5md must expose:

class IO:
    def __init__(
        self,
        filename: str | os.PathLike | None = None,
        *,
        file_handle: h5py.File | None = None,
        particle_group: str = "atoms",
        store: str = "linear",
        timestep: float = 1.0,
        author: str = ...,
        author_email: str = ...,
        creator: str = ...,
        creator_version: str = ...,
        save_units: bool = True,
        pbc_group: bool = True,
    ): ...

    def append(self, atoms: ase.Atoms) -> None: ...
    def extend(self, images: Iterable[ase.Atoms]) -> None: ...
    def __len__(self) -> int: ...
    def __getitem__(self, index: int | slice) -> ase.Atoms | list[ase.Atoms]: ...

In addition, expose:

def write(
    filename: str | os.PathLike,
    images: ase.Atoms | Iterable[ase.Atoms],
    *,
    append: bool = False,
    compression: str | None = ...,
    **io_options,
) -> None: ...

def read(
    filename: str | os.PathLike,
    index: int | slice | list[int] = -1,
    **io_options,
) -> ase.Atoms | list[ase.Atoms]: ...

def iread(
    filename: str | os.PathLike,
    **io_options,
) -> Iterator[ase.Atoms]: ...

The utility functions described further down must be importable from znh5md.utils, and the CLI application must be importable as znh5md.cli.app.

Sequence behavior of IO

  • IO must work with either of the following:
    • a filesystem path given as filename, or
    • an already-open h5py.File given as file_handle with no filename.
  • append() adds a single frame.
  • When extend() is called, all supplied frames are added, in order.
  • When another frame or sequence is appended through the same IO, the frames already present must remain.
  • Calling extend() repeatedly continues the trajectory rather than replacing it.
  • len(io) returns the number of frames that the selected particle group contains.
  • Indexing with an integer returns a single ase.Atoms.
  • Indexing with a slice returns a list of ase.Atoms.
  • Ordinary positive-step slicing must be supported, including:
    • full slices,
    • omitted bounds,
    • positive steps,
    • negative bounds,
    • and empty slices.
  • Reads do not change the trajectory length.
  • The last frame must be accessible through negative indexing, which the default read() behavior requires.

Particle groups that differ within the same file must be independent. For instance, two instances configured with particle_group="a" and particle_group="b" must be able to write and read their own trajectories without overwriting one another. This must work both for path-based access and when both instances share a single externally owned h5py.File.

When a file handle is supplied externally, it must remain usable by the caller and by other IO instances for the duration of its surrounding context.

Round-tripping ASE data

Writing and reading an ase.Atoms trajectory must preserve, frame by frame:

  • the positions,
  • the atomic numbers,
  • complete cell matrices,
  • PBC flags per axis,
  • the velocities and the ASE arrays corresponding to them,
  • all keys and values already present in Atoms.arrays,
  • all keys and values already present in Atoms.info,
  • the keys and values of calculator results.

The number of atoms may differ between frames of a trajectory. Positions, species, velocities, per-particle arrays, and per-particle calculator results that vary in size must be reconstructed with their original shapes.

Reading a frame adds exactly the following two metadata keys to Atoms.info, in addition to the original keys:

  • h5md_step
  • h5md_time

Other than these, no extra info keys may be added. No extra calculator-result or atom-array keys may be introduced either.

The SinglePointCalculator.results values listed next must survive a round trip with their original key names, shapes, and values:

  • energy
  • energies
  • free_energy
  • forces
  • stress
  • stresses
  • dipole
  • magmom
  • magmoms
  • dielectric_tensor
  • born_effective_charges
  • polarization

A nonstandard calculator result named mlip_energy must be preserved as well, rather than being rejected or discarded.

If an energy result exists:

  • calling get_potential_energy() on the loaded frame must return the original value;
  • a scalar energy must be returned as a Python float.

The following custom data must round-trip too:

  • scalar and array-valued Atoms.info, including mlip_energy, mlip_energy_2, and a six-element mlip_stress;
  • the per-particle arrays named mlip_forces and mlip_forces_2.

HDF5/H5MD file layout

With the default particle_group="atoms", generated files must contain the following datasets when the corresponding data exists:

  • particles/atoms/position/value
  • particles/atoms/species/value
  • particles/atoms/velocity/value
  • particles/atoms/force/value
  • observables/atoms/energy/value
  • particles/atoms/box/edges/value

For generated files, use the singular names velocity and force.

Data placement must satisfy these rules:

  • Calculator forces are stored under particles/<group>/force and not under observables.
  • Velocities are stored under particles/<group>/velocity and not under observables.
  • Calculator energy is stored under observables/<group>/energy and not under particles.
  • The arrays mlip_forces and mlip_forces_2 are stored under particles/<group>/....
  • mlip_energy, mlip_energy_2, and mlip_stress taken from Atoms.info are stored under observables/<group>/....

Since unit storage is enabled by default:

  • particles/<group>/velocity/value carries a unit attribute equal to "Angstrom/fs".
  • particles/<group>/force/value carries a unit attribute equal to "eV/Angstrom".
Cell and PBC storage

particles/<group>/box must exist, and its boundary attribute must describe the PBC state of the first frame using:

  • "periodic" marks a periodic axis,
  • "none" marks a nonperiodic axis.

If the structure is fully nonperiodic, the attribute is ["none", "none", "none"].

Each frame’s cell must be contained in particles/<group>/box/edges/value. The full 3×3 cells must be preserved.

By default, a trajectory whose PBC changes must also contain:

particles/<group>/box/pbc/value

holding each frame’s three Boolean PBC flags.

If pbc_group=False, the pbc child must be left out of particles/<group>/box. A nonperiodic molecule written in this way must still read back with the correct all-false PBC flags.

Storage of time and step

store="time" and store="linear" must both be supported.

With store="time":

  • dynamic elements such as position and energy have time and step datasets that are one-dimensional, with one entry per frame;
  • frame i carries step i and time i * timestep;
  • appending further frames continues this sequence.

With store="linear":

  • the time dataset of the element is scalar and equals timestep;
  • the step dataset of the element is scalar and equals 1;
  • frames that are loaded must still expose h5md_step == i and h5md_time == i * timestep.

When the same trajectory is extended multiple times, this sequencing must remain continuous.

When a file is reopened without passing the original store argument, files using either storage mode must be detected and read correctly.

Metadata

The constructor parameters:

  • author
  • author_email
  • creator
  • creator_version

must be persisted in the H5MD file. Reopening the file through IO must expose them as string attributes carrying the same names and values:

io.author
io.author_email
io.creator
io.creator_version

Convenience functions for reading and writing

znh5md.write() must accept either a single ase.Atoms or an iterable of frames, and must create a readable H5MD file.

  • Both compression=None and compression="gzip" must be accepted.
  • Writing a large sequence, including one of 10,000 small frames, must succeed.
  • If the destination already exists and append=False is explicitly supplied, the call must raise FileExistsError rather than replacing it.

Behavior of znh5md.read():

  • Without an index, return the last frame.
  • Given a slice, return the selected frames as a list.
  • Given a list of integer indices, return those frames as a list in the order that was requested.

Every frame must be yielded by znh5md.iread(), in trajectory order.

Compatibility with external H5MD

Reading files written by pyh5md

IO must be able to read H5MD files produced with pyh5md, in both the "time" and "linear" storage modes.

Input element names and locations that must be supported include:

  • particles/atoms/position
  • particles/atoms/species
  • particles/atoms/velocity
  • particles/atoms/forces — plural on input
  • observables/atoms/energy
  • particles/atoms/box/edges

The loaded ASE structures must preserve positions, velocities, forces, potential energies, atomic numbers, and cells. Where box edges are represented as three diagonal lengths, they must produce the corresponding ASE cell.

Reading generated files through pyh5md

Files that IO generated must be readable through pyh5md.File and pyh5md.element. Specifically, pyh5md must be able to retrieve:

  • position,
  • species,
  • velocity,
  • the singular force,
  • energy,
  • box edges,
  • the time and step metadata of position.

The values retrieved must equal the original ASE data.

Compatibility with MDAnalysis

Files written using store="time" must be accepted by MDAnalysis.coordinates.H5MD.H5MDReader.

For a trajectory that contains positions, velocities, and forces:

  • with save_units=False and convert_units=False, MDAnalysis must expose the original positions, the ASE velocities, and the forces;
  • the frame numbers must start at zero and increase in order.

Using the default unit storage together with convert_units=True, the positions must still equal the original ASE positions.

CLI

A Typer application must be exposed as:

from znh5md.cli import app

It must provide support for:

znh5md export INPUT.h5md OUTPUT.xyz

This command must exit successfully, create the output file, and export a structure readable by ASE with the same chemical symbols.

Support must also be available for:

This command must exit successfully and create an H5MD file that contains at least one frame which znh5md.IO can read.

The global option:

znh5md --version

must exit successfully and print output that contains the substring "znh5md".

05 znh5md HDF5 Trajectory I/O Improvements 776 words · source specification, reworded by GLM-5.3-Flash

Task Specification: znh5md HDF5 Trajectory I/O Improvements

Overview

You will be working on znh5md, a Python package that reads and writes ASE (Atomic Simulation Environment) atomic trajectory data to and from HDF5 files following the H5MD conventions. The task requires three related changes: a version bump, support for high-dimensional per-atom and per-frame data, and support for explicitly controlling the H5MD time and step values through ASE Atoms metadata.

Public API

The package must expose:

  • znh5md.__version__ — a string that equals "0.3.2".
  • znh5md.IO — a class for reading and writing trajectory data, constructed as:
    znh5md.IO(filename, store="time")
    where filename is a path pointing to the HDF5 file (it accepts str or pathlib.Path), and store is a keyword argument (a string) that selects the storage mode. The supported values include "time" and "linear".

The IO instance must support:

  • io.append(atoms) — appends a single ASE Atoms object as one frame.
  • io.extend(images) — appends an iterable of ASE Atoms objects.
  • Indexing and slicing: io[0] returns a single Atoms object, while io[:] returns a list of Atoms objects (slicing must be supported).

Requirement 1: Round-trip of high-dimensional data

The package must be able to store numpy arrays of arbitrarily high dimension that are held under custom keys in an Atoms object's arrays and info dictionaries, and to retrieve them faithfully.

Behavior:

  • If an Atoms object has atoms.arrays["<key>"] set to a numpy array whose first dimension equals the number of atoms and which has additional trailing dimensions (e.g. shape (n_atoms, 10, 5, 4, 3)), then after appending and reading back, the retrieved Atoms object must contain arrays["<key>"] that is element-wise equal to the original array, with its full shape and values preserved.
  • If an Atoms object has atoms.info["<key>"] set to a numpy array of arbitrary shape (e.g. (5, 10, 4, 4, 3)), then after appending and reading back, the retrieved Atoms object must contain info["<key>"] that is element-wise equal to the original array, with its full shape and values preserved.

This must work no matter how many trailing dimensions the array has.

Requirement 2: Controlling H5MD time and step via ASE metadata

In store="time" mode, the caller may specify the H5MD step and time values for each frame through the Atoms object's info dictionary, using the reserved keys:

  • atoms.info["h5md_step"] — an integer value for the step.
  • atoms.info["h5md_time"] — a floating-point value for the time.
Write behavior (store="time")

Whenever frames that carry these keys are appended, the written HDF5 file must record the given values in the standard H5MD locations:

  • particles/atoms/position/step — the sequence of supplied h5md_step values (in frame order).
  • particles/atoms/position/time — the sequence of supplied h5md_time values (in frame order).
  • For each stored observable (e.g. an energy value produced by an attached calculator), the corresponding observables/atoms/<name>/step and observables/atoms/<name>/time datasets must hold the same per-frame step and time sequences respectively, and observables/atoms/<name>/value must hold the observable values in frame order.

Concretely: if frames carrying h5md_step values s_0, s_1, ... and h5md_time values t_0, t_1, ... are appended, then the step datasets hold [s_0, s_1, ...] and the time datasets hold [t_0, t_1, ...].

Read behavior (store="time")

When frames are read back, each returned Atoms object must expose the stored per-frame step and time through:

  • atoms.info["h5md_step"] — the integer step of that frame.
  • atoms.info["h5md_time"] — the float time of that frame.

Any observable stored for the frame (e.g. potential energy) must be accessible through the normal ASE mechanism (e.g. atoms.get_potential_energy()), which returns the stored value.

Consistency checks (store="time")

When multiple frames are appended/extended in "time" mode, the presence of the h5md_step / h5md_time keys must be consistent across all frames in the batch:

  • If some frames in a batch provide h5md_time while the remaining frames do not, a ValueError must be raised.
  • If some frames in a batch provide h5md_step while the remaining frames do not, a ValueError must be raised.
store="linear" mode

The h5md_step and h5md_time info keys are not honored in "linear" storage mode. If an Atoms object carrying either (or both) of these keys is appended in "linear" mode, a UserWarning must be emitted, and the message of that warning must contain the text:

time and step are ignored in 'linear' storage mode

The append operation itself must still succeed (aside from the warning, the keys are simply ignored).

General remarks

  • All numeric round-trips must be exact for integer/float values that are written and read back.
  • Read/write behavior that already exists for standard ASE quantities (positions, cell, calculator results such as energy, custom arrays/info entries) must continue to work.

Required modification

Modify the public znh5md API so that it has the following behavior:

17 Support for Appending Frames with Differing Property Keys 927 words · rewritten by GPT-5.6-sol, reworded by GLM-5.3-Flash

Task Specification: Support for Appending Frames with Differing Property Keys

Overview

You are working on znh5md, a Python library that stores sequences of ASE Atoms objects in an HDF5 file. The class znh5md.IO is the public entry point; it is constructed with a single path argument (a str or path-like object) that points to an HDF5 file:

io = znh5md.IO(path)

An IO object behaves like a sequence of frames (ASE Atoms objects). You must ensure that the behaviors described below hold.

Public API Surface

The following must be importable and callable as shown:

  • znh5md.IO(path) — constructor that takes a file path.
  • io.append(atoms) — appends a single ASE Atoms object.
  • io.extend(list_of_atoms) — appends multiple ASE Atoms objects.
  • len(io) — the total number of stored frames.
  • iter(io) / list(io) — iteration that yields the stored frames in order.
  • io[i] — indexing with an integer (negative indices are supported).
  • io[a:b] — indexing with a slice, which returns the corresponding frames.

Behavior Requirements

1. Heterogeneous keys across frames that are appended

Frames that are appended or extended into the same file need not share the same set of property keys. Frames written with different info keys, different arrays keys, or different calculator results must all coexist correctly. When a frame is read back, it must expose exactly the optional keys supplied by the user that were present when that frame was written; the only exception is the reserved H5MD metadata exception described below.

In particular:

  • If a given user info key is carried by some frames and not by others, then reading each frame back must yield that key only on the frames that originally had it; on frames that did not have it, that key must be absent.
  • The same holds, independently, for arrays keys.
  • The same holds, independently, for attached ASE calculators and their results: a frame written without a calculator must read back with calc is None; a frame written with a calculator must read back with a calculator whose results are equal to the originally stored results.

This must hold regardless of the order in which mixed frames are written, including cases where batches of frames that have a key are interleaved with batches that do not (for example, write-with, write-without, write-with, and so on). Values that were written earlier must not be overwritten or leaked into later frames, and vice versa.

2. Reserved H5MD metadata during read-back

Every stored frame, when reconstructed as an ASE Atoms object, must have the reserved entries h5md_step and h5md_time in its info mapping. These entries report the H5MD step and time that are associated with that frame; they are added on read-back even when they were not ordinary user-supplied info properties. This applies whether frames are read by integer index, by slice, or by iteration.

As a consequence, for a frame that has been round-tripped, the expected set of info keys is:

set(read_frame.info) == set(original_frame.info) | {"h5md_step", "h5md_time"}

The requirement that optional keys be preserved exactly per frame applies to all keys supplied by the user; the only exception to the no-extra-keys rule is the two reserved metadata entries. The automatic presence of these entries must not cause a user property that is missing from a frame to appear on that frame.

3. Preserving values
  • User info values that have been round-tripped must equal the original values. This includes:
    • Values that are numeric (float).
    • String values that contain non-ASCII characters (for example, "γC"), preserved exactly.
  • arrays values that have been round-tripped (for example, an array of shape (n_atoms, 3)) must be element-for-element equal to the original.
4. Consistency of length and iteration
  • len(io) must equal the total number of frames that were written across all append and extend calls.
  • len(list(io)) must equal that same total; iteration yields every stored frame exactly once, in insertion order.
  • When frames of differing lengths or property sets are combined via repeated extend calls on batches of differing sizes or types, the total count is the sum of the individual batch sizes.
5. Indexing and error conditions
  • Accessing any index on an IO whose backing file does not yet exist must raise FileNotFoundError, whether that index is an integer or a slice.
  • After at least one frame has been written:
    • io[0] returns the first frame, which is not None.
    • io[-1] returns the last frame, which is not None.
    • Slices such as io[0:1] and io[0:2] return results that are valid and not None.
    • An integer index that is at or beyond the number of stored frames must raise IndexError (for example, io[1] when only one frame exists).
    • A negative integer index that resolves to a position before the first frame must raise IndexError (for example, io[-2] when only one frame exists).
6. Extending on an empty file after construction

extend may be called on a freshly constructed IO whose file does not yet exist. The file, together with the frames, must be created, and len(io) must reflect the number of frames that were added.

Notes

  • All comparisons performed on read-back are against the original ASE Atoms objects. Calculator results are compared by way of the calculator's results dictionary.
  • append must accept, without raising an error, frames that introduce keys not present in previously written frames.
  • The automatic h5md_step and h5md_time entries are reserved read-back metadata; they are not optional properties leaked from another frame.
