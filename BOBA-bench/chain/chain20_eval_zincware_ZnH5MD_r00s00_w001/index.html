01 znh5md H5MD Compliance and API Simplification 492 words · source specification

Task Specification: znh5md H5MD Compliance and API Simplification

Overview

You are working on the znh5md package, a library for writing/reading ASE (Atomic Simulation Environment) trajectory data to/from HDF5 files following the H5MD standard. This task requires three changes: removing an explicit initialization step, ensuring H5MD compliance so that files can be read by external tools, and bumping the version.

Requirements

1. Version bump

The package must expose znh5md.__version__ equal to the string "0.2.0".

2. Remove the initialize_database_groups step

The DataWriter class (importable as znh5md.io.DataWriter) must no longer require any explicit group-initialization step before writing data.

  • The public method initialize_database_groups() must be removed from DataWriter (it must no longer be part of the public API).
  • Any HDF5 groups needed to store data must be created automatically and only when required, as part of the normal writing workflow.

The typical workflow must be:

db = znh5md.io.DataWriter(filename="db.h5")
reader = znh5md.io.AtomsReader(atoms_list)
db.add(reader)

Immediately calling db.add(...) on a freshly constructed DataWriter (with no prior initialization call) must successfully write the data to the file. All existing reading/slicing/property behavior via znh5md.ASEH5MD("db.h5") must continue to work after writing this way.

DataWriter(filename=...) must accept a filename given either as a string or as a pathlib.Path.

3. H5MD compliance (readable by MDAnalysis)

Files written by DataWriter must comply with the H5MD standard closely enough that the trajectory positions can be read back correctly by the standard MDAnalysis H5MD reader (MDAnalysis.coordinates.H5MD.H5MDReader).

Concretely, given a list of ase.Atoms objects written to an H5 file via:

db = znh5md.io.DataWriter(filename=filename)   # filename is a pathlib.Path
reader = znh5md.io.AtomsReader(trajectory)
db.add(reader)

opening the resulting file with the MDAnalysis H5MD reader must yield a trajectory whose:

  • length equals the number of written frames, and
  • per-frame positions match (elementwise, within floating-point tolerance) the positions of the corresponding input ase.Atoms objects.

To achieve this compliance:

  • Units must be stored as HDF5 attrs (attribute metadata) on the appropriate datasets/groups, rather than as separate datasets, as required by the H5MD specification.
  • Time information must be written correctly per the H5MD standard.
  • Periodic boundary conditions (PBC) and box/edges information must be written such that the file represents standard 3-dimensional data. (The trajectories in scope are 3D atomic systems; e.g. a water molecule of 3 atoms whose positions translate linearly frame to frame.)

The reading must work for trajectories where atoms have positions but no attached calculator/energy data (i.e., position-only trajectories must be fully valid).

Public API Surface

The following must remain importable and callable:

  • znh5md.__version__ → "0.2.0"
  • znh5md.io.DataWriter(filename=<str | pathlib.Path>) with method .add(reader) — no initialize_database_groups method.
  • znh5md.io.AtomsReader(atoms_list, frames_per_chunk=<int>) — accepts a list of ase.Atoms.
  • znh5md.ASEH5MD(<filename>) — for reading back written files.

Out of Scope / Constraints

  • Do not reintroduce or preserve initialize_database_groups as a required or optional step.
  • No behavior beyond correct H5MD-compliant writing (units in attrs, correct time, 3D/PBC/box data) and the version bump is required.
02 H5MD-Compliant Reading and Writing for ASE Atoms 587 words · source specification

Task Specification: H5MD-Compliant Reading and Writing for ASE Atoms

Overview

Implement a Python package znh5md that reads and writes molecular structure trajectories (sequences of ASE Atoms objects) to/from HDF5 files following the H5MD file layout. The output files must be interoperable with the reference pyh5md library — i.e., files written by znh5md must be readable by pyh5md, and files written by pyh5md must be readable by znh5md.

Public API Surface

The following must be importable and callable exactly as described:

znh5md.ASEH5MD

A class constructed with a single positional argument: a filesystem path (str or pathlib.Path) to an existing H5MD file.

reader = znh5md.ASEH5MD(path)

It must provide the method:

reader.get_atoms_list() -> list[ase.Atoms]

which returns the list of ase.Atoms objects reconstructed from the file, one per stored frame/step, in stored order.

znh5md.io.DataWriter

A class constructed with a single positional argument: a filesystem path (str or pathlib.Path) where an H5MD file is to be written/created.

db = znh5md.io.DataWriter(path)

It must provide the method:

db.add(reader)

where reader is an AtomsReader instance (see below). Calling add writes the data provided by the reader into the H5MD file at the writer's path.

znh5md.io.AtomsReader

A class constructed with a single positional argument: a list of ase.Atoms objects.

reader = znh5md.io.AtomsReader(list_of_atoms)

It adapts an in-memory list of Atoms into the form consumed by DataWriter.add.

H5MD File Layout Requirements

Files written by DataWriter must conform to the H5MD group/dataset structure such that the pyh5md reference implementation can open them and access the following elements. For a particle group named "atoms" (accessed via pyh5md's particles_group("atoms")), the following time-dependent elements must be present, each with a per-frame value array indexed by frame:

  • position — shape (n_atoms, 3) per frame, float; equals each frame's atomic positions.
  • species — shape (n_atoms,) per frame, integer; equals each frame's atomic numbers.
  • momentum — shape (n_atoms, 3) per frame, float; equals each frame's atomic momenta.
  • forces — shape (n_atoms, 3) per frame, float; equals each frame's atomic forces.

Additionally, an observable element at path observables/atoms/energy (accessed via pyh5md's element(file, "observables/atoms/energy")) must be present, storing the per-frame potential energy.

For each frame index idx, reading these elements back must yield, respectively: the positions, atomic numbers, momenta, forces, and potential energy of the corresponding input Atoms object.

Reading Requirements

ASEH5MD(path).get_atoms_list() must reconstruct Atoms objects from an H5MD file that follows the above layout (including files produced by pyh5md). Reading files that contain the standard H5MD h5md metadata group (with version, author, and creator subgroups/attributes) must work without error. For each frame, the reconstructed Atoms must reproduce:

  • positions (from position)
  • atomic numbers (from species)
  • momenta (from momentum)
  • forces (from forces)
  • potential energy (from observables/atoms/energy)

so that these values compare equal to the source data used to write the file.

Round-Trip and Interoperability Constraints

  • Data written by znh5md.io.DataWriter (fed by znh5md.io.AtomsReader) must be readable by pyh5md and yield exactly the original positions, atomic numbers, momenta, forces, and per-frame energies.
  • Data written by pyh5md in the layout described above must be readable by znh5md.ASEH5MD and yield Atoms whose positions, momenta, forces, potential energy, and atomic numbers match the originals exactly.
  • The values across distinct frames are generally different; per-frame indexing must be preserved (frame idx maps to input structure idx).

Notes

  • The energy stored is the potential energy obtained from each Atoms' attached calculator.
  • All numeric comparisons for interoperability are exact (not merely approximate).

IO sequence behavior

  • IO must work with either:

    • an already-open h5py.File supplied as file_handle without a filename.
  • append() adds one frame.
  • extend() adds all supplied frames in order.

This must work both for path-based access and when both instances share one externally owned h5py.File.

An externally supplied file handle must remain usable by the caller and by other IO instances for the duration of its surrounding context.

ASE data round-trip

Writing and reading an ase.Atoms trajectory must preserve, frame by frame:

  • positions,
  • atomic numbers,
  • full cell matrices,
  • per-axis PBC flags,
  • velocities and the corresponding ASE arrays,
  • all existing keys and values in Atoms.arrays,
  • all existing keys and values in Atoms.info,
  • calculator result keys and values.

Trajectories may contain different numbers of atoms in different frames. Variable-sized positions, species, velocities, per-particle arrays, and per-particle calculator results must be reconstructed with their original shapes.

Reading a frame adds exactly these two metadata keys to Atoms.info in addition to the original keys:

  • h5md_step
  • h5md_time

  • born_effective_charges

  • A scalar energy must be returned as a Python float.

The following custom data must also round-trip:

  • scalar and array-valued Atoms.info, including mlip_energy, mlip_energy_2, and a six-element mlip_stress;
  • per-particle arrays named mlip_forces and mlip_forces_2.

HDF5/H5MD layout

For the default particle_group="atoms", generated files must contain these datasets when the corresponding data exists:

  • particles/atoms/position/value
  • particles/atoms/species/value
  • particles/atoms/velocity/value
  • particles/atoms/force/value
  • observables/atoms/energy/value
  • particles/atoms/box/edges/value

Use the singular names velocity and force for generated files.

Data placement must satisfy the following:

  • Calculator forces are stored under particles/<group>/force, not under observables.
  • Velocities are stored under particles/<group>/velocity, not under observables.
  • Calculator energy is stored under observables/<group>/energy, not under particles.
  • mlip_forces and mlip_forces_2 are stored under particles/<group>/....
  • mlip_energy, mlip_energy_2, and mlip_stress from Atoms.info are stored under observables/<group>/....

With unit storage enabled by default:

  • particles/<group>/velocity/value has a unit attribute equal to "Angstrom/fs".
  • particles/<group>/force/value has a unit attribute equal to "eV/Angstrom".
Cell and PBC data

particles/<group>/box must exist and its boundary attribute must describe the first frame’s PBC state using:

  • "periodic" for a periodic axis,
  • "none" for a nonperiodic axis.

For a fully nonperiodic structure, this attribute is ["none", "none", "none"].

particles/<group>/box/edges/value must contain each frame’s cell. Full 3×3 cells must be preserved.

By default, a changing-PBC trajectory must also contain:

particles/<group>/box/pbc/value

with each frame’s three Boolean PBC flags.

When pbc_group=False, the pbc child must be omitted from particles/<group>/box. A nonperiodic molecule written this way must still read back with the correct all-false PBC flags.

Time and step storage

Support store="time" and store="linear".

For store="time":

  • dynamic elements such as position and energy have one-dimensional time and step datasets with one entry per frame;
  • frame i has step i and time i * timestep;
  • appending more frames continues this sequence.

For store="linear":

  • the element’s time dataset is scalar and equals timestep;
  • the element’s step dataset is scalar and equals 1;
  • loaded frames must still expose h5md_step == i and h5md_time == i * timestep.

This sequencing must remain continuous when the same trajectory is extended multiple times.

Files using either storage mode must be detected and read correctly when reopened without passing the original store argument.

Metadata

The constructor parameters:

  • author
  • author_email
  • creator
  • creator_version

Convenience read/write functions

  • Writing a large sequence, including 10,000 small frames, must succeed.
  • If the destination already exists and append=False is explicitly supplied, raise FileExistsError rather than replacing it.

  • With a slice, return the selected frames as a list.

  • particles/atoms/species

  • observables/atoms/energy
  • particles/atoms/box/edges

Task Specification: znh5md HDF5 Trajectory I/O Enhancements

Overview

You are working on znh5md, a Python package that reads and writes ASE (Atomic Simulation Environment) atomic trajectory data to/from HDF5 files following the H5MD conventions. This task requires three related changes: version bump, support for high-dimensional per-atom and per-frame data, and support for explicitly controlling H5MD time and step values via ASE Atoms metadata.

Public API

The package must expose:

  • znh5md.__version__ — a string equal to "0.3.2".
  • znh5md.IO — a class for reading/writing trajectory data, constructed as:
    znh5md.IO(filename, store="time")
    where filename is a path (accepts str or pathlib.Path) pointing to the HDF5 file, and store is a keyword argument (a string) selecting the storage mode. Supported values include "time" and "linear".

The IO instance must support:

  • io.append(atoms) — append a single ASE Atoms object as one frame.
  • io.extend(images) — append an iterable of ASE Atoms objects.
  • Indexing/slicing: io[0] returns a single Atoms object; io[:] returns a list of Atoms objects (slicing must be supported).

The package must be able to store and faithfully retrieve arbitrarily high-dimensional numpy arrays held in an Atoms object's arrays and info dictionaries under custom keys.

Behavior:

  • Given an Atoms object with atoms.arrays["<key>"] set to a numpy array whose first dimension equals the number of atoms and which has additional trailing dimensions (e.g. shape (n_atoms, 10, 5, 4, 3)), after appending and reading back, the retrieved Atoms object must contain arrays["<key>"] that is element-wise equal to the original array, preserving its full shape and values.
  • Given an Atoms object with atoms.info["<key>"] set to a numpy array of arbitrary shape (e.g. (5, 10, 4, 4, 3)), after appending and reading back, the retrieved Atoms object must contain info["<key>"] that is element-wise equal to the original array, preserving its full shape and values.

This must work regardless of the number of trailing dimensions.

Requirement 2: Setting H5MD time and step from ASE metadata

When operating in store="time" mode, the caller may specify the H5MD step and time values for each frame via the Atoms object's info dictionary using the reserved keys:

  • atoms.info["h5md_step"] — an integer step value.
  • atoms.info["h5md_time"] — a floating-point time value.
Writing behavior (store="time")

When frames carrying these keys are appended, the written HDF5 file must record the given values in the standard H5MD locations:

  • particles/atoms/position/step — the sequence of provided h5md_step values (in frame order).
  • particles/atoms/position/time — the sequence of provided h5md_time values (in frame order).
  • For each stored observable (e.g. an energy value produced by an attached calculator), the corresponding observables/atoms/<name>/step and observables/atoms/<name>/time datasets must contain the same per-frame step and time sequences respectively, and observables/atoms/<name>/value must contain the observable values in frame order.

Concretely, if frames are appended with h5md_step values s_0, s_1, ... and h5md_time values t_0, t_1, ..., then the step datasets contain [s_0, s_1, ...] and the time datasets contain [t_0, t_1, ...].

Reading behavior (store="time")

When reading frames back, each returned Atoms object must expose the stored per-frame step and time via:

  • atoms.info["h5md_step"] — the integer step for that frame.
  • atoms.info["h5md_time"] — the float time for that frame.

Any observable stored for the frame (e.g. potential energy) must be accessible through the normal ASE mechanism (e.g. atoms.get_potential_energy()), returning the stored value.

Consistency validation (store="time")

When appending/extending multiple frames in "time" mode, the presence of the h5md_step / h5md_time keys must be consistent across all frames in the batch:

  • If some frames in a batch provide h5md_time while others do not, a ValueError must be raised.
  • If some frames in a batch provide h5md_step while others do not, a ValueError must be raised.
store="linear" mode

In "linear" storage mode, the h5md_step and h5md_time info keys are not honored. When an Atoms object carrying either (or both) of these keys is appended in "linear" mode, a UserWarning must be emitted whose message contains the text:

time and step are ignored in 'linear' storage mode

The append operation itself must still succeed (the keys are simply ignored aside from the warning).

General Notes

  • All numeric round-trips must be exact for integer/float values written and read back.
  • Existing read/write behavior for standard ASE quantities (positions, cell, calculator results such as energy, custom arrays/info entries) must continue to function.

2. Reserved H5MD metadata on read-back

Every stored frame reconstructed as an ASE Atoms object must have the reserved entries h5md_step and h5md_time in its info mapping. These entries report the H5MD step and time associated with that frame and are added on read-back even when they were not ordinary user-supplied info properties. This applies whether frames are read by integer index, slice, or iteration.

Consequently, for a round-tripped frame, the expected info key set is:

set(read_frame.info) == set(original_frame.info) | {"h5md_step", "h5md_time"}

The requirement that optional keys be preserved exactly per frame applies to all user-supplied keys; the two reserved metadata entries are the only exception to the no-extra-keys rule. Their automatic presence must not cause a user property missing from a frame to appear on that frame.

3. Preservation of values
  • Round-tripped user info values must equal the original values. This includes:
    • Numeric (float) values.
    • String values containing non-ASCII characters (for example, "γC"), preserved exactly.
  • Round-tripped arrays values (for example, an array of shape (n_atoms, 3)) must be element-for-element equal to the original.
4. Length and iteration consistency
  • len(io) must equal the total number of frames written across all append and extend calls.
  • len(list(io)) must equal the same total; iteration yields every stored frame exactly once, in insertion order.
  • When frames of differing lengths or property sets are combined through repeated extend calls on differently sized or typed batches, the total count is the sum of the individual batch sizes.
5. Indexing and error conditions
  • Accessing any index, whether an integer or a slice, on an IO whose backing file does not yet exist must raise FileNotFoundError.
  • After at least one frame has been written:
    • io[0] returns the first frame and is not None.
    • io[-1] returns the last frame and is not None.
    • Slices such as io[0:1] and io[0:2] return valid, non-None results.
    • An integer index at or beyond the number of stored frames must raise IndexError (for example, io[1] when only one frame exists).
    • A negative integer index that resolves before the first frame must raise IndexError (for example, io[-2] when only one frame exists).
6. Extending after construction on an empty file

extend may be called on a freshly constructed IO whose file does not yet exist. The file and frames must be created, and len(io) must reflect the number of frames added.

Notes

  • All read-back comparisons are against the original ASE Atoms objects. Calculator results are compared through the calculator's results dictionary.
  • append must accept frames that introduce keys not present in previously written frames without raising an error.
  • The automatic h5md_step and h5md_time entries are reserved read-back metadata, not leaked optional properties from another frame.
18 Support variable-length dictionary and sequence values stored in an ASE Atoms.info mapping across frames in a znh5md.IO file. 377 words · source specification

Required change

Support variable-length dictionary and sequence values stored in an ASE Atoms.info mapping across frames in a znh5md.IO file.

Public API

The package must expose:

  • znh5md.IO(path)
    • path may be a pathlib.Path or equivalent filesystem path.
  • IO.append(atoms)
    • Accepts an ase.Atoms object.
  • IO.__getitem__(index: int)
    • Returns the stored frame as an ase.Atoms object whose info data can be accessed through .info.

Required behavior

Dictionary-valued info

IO.append() must accept Atoms.info entries whose values are dictionaries with string keys and integer values, including values produced after an ASE extxyz write/read round trip.

For a given info key, successive frames may contain dictionaries with different sets or numbers of entries. Reading each frame must return the dictionary associated with that frame, rather than coercing it to a string, truncating it, or applying another frame’s shape/content.

Examples of values that must round-trip independently include:

  • {"a": 1, "b": 2}
  • {"a": 1, "b": 2, "c": 3}
  • {"a": 1}

New dictionary-valued info keys may also be introduced in later frames, such as a later frame containing:

  • "b": {"a": 1, "b": 2, "c": 3, "d": 4}

Different Atoms objects, including molecules with different atom counts, may use the same info key with differently sized dictionaries.

Sequence-valued info

IO.append() must accept numeric sequence values in Atoms.info, including:

  • Python lists.
  • Array-like values produced by reading an ASE extxyz file.

The same info key may have different sequence lengths in successive frames, such as [1, 2] followed by [1, 2, 3]. A new sequence-valued key may be introduced in a later frame, such as "b": [1, 2, 3, 4].

When read through integer indexing, each returned value must be array-equivalent to the sequence stored for that frame, with the same element order and length. No specific concrete return container type or numeric dtype is required.

Per-frame snapshot semantics

Appending an Atoms object must preserve that frame’s current info values. Later mutation of the original object’s dictionaries, lists, or info keys must not alter previously appended frames.

Thus, if an object is appended with a two-entry value, modified to a three-entry value, and appended again, indexing the first frame must still yield the original two-entry value while the second yields the updated value.
