Task Specification: Cursor-Based Querying and Offset for Mock Firestore Collections

Overview

You are working on mockfirestore, an in-memory mock of Google Cloud Firestore. The public entry point is:

from mockfirestore import MockFirestore

A MockFirestore instance exposes its document store through _data, using a nested mapping whose top-level keys are collection names and whose collection keys are document IDs:

{
    '<collection_name>': {
        '<document_id>': {<field>: <value>, ...},
        ...
    },
    ...
}

Add cursor-based query methods and an offset method to the collection query surface, and expose document IDs on document snapshots. Preserve the existing collection, document, snapshot, filtering, ordering, limiting, nested-collection, and streaming behavior except for the default-order clarification stated below.

Existing public behavior and compatibility

  • MockFirestore().collection(name) returns a collection reference. An absent collection can be streamed and produces no documents.
  • Collection references support .where(field, op, value), .order_by(field, direction=...), .limit(n), and .stream().
  • Existing comparison operators remain supported by where: ==, <, <=, >, and >=.
  • order_by(field) orders by the field in ascending order. Passing direction='DESCENDING' orders by that field in descending order.
  • limit(n) restricts the number of streamed documents while preserving the applicable result order.
  • Nested collections obtained through collection(...).document(...).collection(...) retain the same collection and query behavior.
  • .stream() returns an iterable of DocumentSnapshot objects. Each snapshot continues to support .to_dict(), .exists, and .reference as before.
  • Existing document-reference operations, including retrieval, creation, setting, merging, updating, deletion, parent references, and nested collections, must not regress.

All new query methods described below must be available both directly on a collection reference and after another query operation. They must be chainable with one another and with where, order_by, and limit; every intermediate result must retain the full query method surface. Calling .stream() evaluates and terminates the chain.

Required behavior

1. Document ID on snapshots

Every document snapshot returned through the collection or document API must expose a read-only-style id attribute containing the document's key within its collection. This identity is separate from any field named id in the document data.

For example:

snapshot = db.collection('foo').document('first').get()

snapshot.id                 # 'first'
snapshot.to_dict()          # the stored field dictionary
snapshot.reference.id       # 'first'

The snapshots produced by a query or collection stream must likewise carry the ID of the document whose data they contain; ordering or slicing a query must not detach a snapshot's data from its document reference. .to_dict() must continue to return the document's field dictionary.

2. Default ordering by document ID

When no explicit order_by is applied, documents must stream in ascending document-ID order. This rule applies both to CollectionReference.stream() called directly and to any chained query that has no explicit field ordering. It is independent of the insertion order or concrete mapping type used in _data.

For example, if beta is inserted before alpha:

db._data = {
    'foo': {
        'beta': {'value': 1},
        'alpha': {'value': 2},
    }
}

then db.collection('foo').stream() must yield the alpha snapshot first and the beta snapshot second.

An explicit order_by(field) replaces this default result ordering with ordering by the requested field: ascending by default, or descending when requested.

3. offset(num_to_skip)

Add this method to the collection/query surface:

offset(num_to_skip)

It skips the first num_to_skip documents of the applicable ordered result sequence and streams the remainder without changing their relative order.

  • Without order_by, the sequence being offset is in ascending document-ID order.
  • With order_by, the sequence being offset is in the requested field order.
  • It must compose with the other query methods and return an object supporting the full query surface.

For documents keyed first, second, and third, with field data {'id': 1}, {'id': 2}, and {'id': 3}, respectively:

db.collection('foo').offset(1).stream()

must yield {'id': 2} and then {'id': 3}. The same field-data result is required for:

db.collection('foo').order_by('id').offset(1).stream()
4. Cursor methods

Add these methods to the collection/query surface:

start_at(document_fields)
start_after(document_fields)
end_before(document_fields)
end_at(document_fields)

Each accepts one dictionary of field/value pairs describing a cursor position. A document matches the cursor only when, for every entry in document_fields, that document contains the field and its value equals the cursor value. Extra fields on the document do not affect the match. A document missing any cursor field is simply not a match and must not cause an exception.

The cursor locates the first matching document in the current ordered result sequence. The methods retain the following portions of that sequence:

  • start_at(fields): the first matching document and every document after it (inclusive start).
  • start_after(fields): every document after the first matching document (exclusive start).
  • end_before(fields): every document before the first matching document (exclusive end).
  • end_at(fields): every document through the first matching document (inclusive end).

Cursor matching must consider all supplied fields together. For example, {'id': 3, 'value': 2} matches only a document having both values, not a document matching just one of them.

The methods must behave consistently both without an explicit field order—where the sequence is ordered by ascending document ID—and after order_by.

For documents keyed first, second, and third, whose data is {'id': 1}, {'id': 2}, and {'id': 3}, the cursor {'id': 2} produces:

Method Streamed document data, in order
start_at({'id': 2}) {'id': 2}, {'id': 3}
start_after({'id': 2}) {'id': 3}
end_before({'id': 2}) {'id': 1}
end_at({'id': 2}) {'id': 1}, {'id': 2}

The same results must be produced when the chain includes order_by('id').

5. Missing fields in filters

Filtering must be tolerant of heterogeneous document shapes. For any supported where(field, op, value) comparison, a document that lacks field is treated as non-matching rather than raising an error.

For example, given:

{
    'first': {'valid': True},
    'second': {'gumby': False},
}

this query:

db.collection('foo').where('valid', '==', True).stream()

must return only the first document.

Ordering and result semantics

The result sequence used by streaming, offsets, and cursors is determined as follows:

  1. Existing query filters determine which documents are eligible.
  2. If order_by is present, eligible documents are ordered by its requested field and direction.
  3. Otherwise, eligible documents are ordered by ascending document ID, regardless of backing-map insertion order.
  4. Cursor bounds and offsets select from that ordered sequence while preserving its order. Existing limits continue to restrict the streamed result when composed into the chain.

Every streamed item must be a DocumentSnapshot whose .to_dict() data, .id, and .reference all correspond to the same underlying document.

Version

Update the library version to 0.3.0.

Task: Support Missing and Dot-Separated Field Paths in Collection where() Queries

Overview

You are working on a mock implementation of Firestore. This mock exposes a MockFirestore class and a collection-based query API. You must adjust the behavior of the where() filtering method so that it correctly handles two cases: fields that do not exist on a document, and nested field paths expressed with dot-separated notation.

Public API Surface

The relevant API (which already exists and must continue to work) is used as follows:

  • MockFirestore — importable and constructible with no arguments (e.g. from mockfirestore import MockFirestore; construct via MockFirestore()).
  • The MockFirestore instance holds its backing store in an attribute named _data, which is a dict mapping collection names to dicts of document-id → document-data. Document data are plain dicts (which may themselves contain nested dicts).
  • instance.collection(name) — returns a collection reference for the named collection.
  • collection_ref.where(field, op, value) — returns a query/collection reference that applies a filter. field is a string, op is a comparison operator string (e.g. '=='), and value is the value to compare against. This must be chainable with .stream().

  • Each document snapshot has a .to_dict() method returning the document's data as a dict.

Required Behavior

Modify the where() filtering so that the field argument is interpreted as a field path, where a dot (.) separates levels of nesting into the document's data.

1. Dot-separated nested field paths

When field contains one or more dots, each segment names a successively deeper key in the document's nested dict structure. The value used for comparison is the value found by traversing those keys in order.

For example, given a document {'nested': {'a': 1}}, a filter with field path 'nested.a' and operator '==' compares against the value 1. A document whose traversed value equals the query value is included in the results; one whose traversed value does not equal it is excluded.

A single (dot-free) field name continues to reference a top-level key as before.

2. Missing fields

If a document does not contain the referenced field path (i.e., the top-level key is absent, or any segment along a nested path is absent), that document must simply not match the filter and must be excluded from the results. This must not raise an error.

Edge Cases

  • Filtering on a top-level field name that no document possesses yields zero results.
  • Filtering on a nested field path (e.g. 'nested.a') with an equality operator returns exactly those documents whose nested value at that path equals the query value; documents where the value differs are excluded.
  • Results are returned as document snapshots whose .to_dict() returns the full original document data (including nested structure).
