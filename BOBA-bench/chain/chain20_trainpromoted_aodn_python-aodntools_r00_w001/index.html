Context

You are modifying a NetCDF writer library. The relevant public API is the DatasetTemplate class, importable as:

from ncwriter import DatasetTemplate

(The class is defined in the template module of the ncwriter package.)

Required Behavior

DatasetTemplate is constructed with a variables keyword argument, which is a dictionary mapping variable names to their definitions. Each variable definition is itself a dictionary that may contain keys such as type, data, and dimensions.

The instance provides a to_netcdf(path) method that writes the template contents to a NetCDF file at the given path.

Change to implement

writing must succeed, and when the resulting file is opened, the variable X must exist and its .dimensions attribute must equal () (the empty tuple).

Notes

  • A variable whose data value is None must still be created successfully.

Overview

Migrate ncwriter templates to a flatter schema. Reserved template fields are underscore-prefixed, while ordinary metadata is stored directly beside those fields rather than under a required metadata container. Preserve support for the legacy nested variable attributes mapping, with the serialization behavior defined below.

Public API

The following names must remain importable and callable exactly as shown.

ncwriter.schema

  • validate_variables(obj)
  • validate_global_attributes(obj) (replaces the former validate_attributes public name)
  • ValidationError

All three validation functions return normally for valid input and raise ValidationError for invalid input.

Package top level (ncwriter)

  • ValidationError

Flat template format

A template is a mapping such as a JSON object, dict, or OrderedDict.

  • "_dimensions" is the mapping of dimension names to sizes.
  • "_variables" is the mapping of variable names to variable definitions.
  • Every top-level entry whose name does not start with _ is a dataset global attribute.
  • Other underscore-prefixed top-level entries are reserved and are not global attributes. For example, "_format" must not appear among the dataset's global attributes.

A variable definition is a mapping containing any combination of:

  • "_dimensions": a list of dimension names. It may be empty and may be omitted; omission means that the variable is dimensionless.
  • "_datatype": a NetCDF datatype name such as "float32", "float64", or "double".
  • "_data": array-like variable values, a NumPy masked array, or None.
  • Recognized underscore-prefixed control fields, including "_FillValue", "_zlib", and "_complevel". Other supported NetCDF control names follow the same reserved underscore convention (for example, _shuffle, _fletcher32, _contiguous, _chunksizes, _endian, and _least_significant_digit). An arbitrary underscore-prefixed field is not allowed.
  • Ordinary, non-underscore keys such as standard_name, units, and valid_min. These are flat variable template metadata.
  • For compatibility, the special non-underscore key attributes, whose value is a nested mapping of NetCDF variable attributes.

Validation and writability are separate: an incomplete definition such as {} or one containing only _datatype is valid template metadata, even though additional fields may be needed before it can be written.

metadata_attributes(mapping)

metadata_attributes returns a new mapping containing exactly the input entries whose keys do not start with _. It must:

  • exclude every underscore-prefixed entry;
  • retain every non-underscore entry and its value; and
  • preserve input insertion order without mutating the input.

For example, applying it to a top-level template removes _dimensions, _variables, and _format while retaining title, abstract, and number. The same filtering rule identifies flat metadata in a variable definition. This filtering rule does not, by itself, mean that flat variable metadata is serialized as NetCDF variable attributes; variable-attribute serialization has the compatibility rule described under to_netcdf.

Validation

Names for dimensions, variables, and ordinary attributes must begin with an ASCII letter and then contain only ASCII letters, digits, or underscores (^[A-Za-z][A-Za-z0-9_]*$). Thus names such as X, TEMP_2, and Conventions are valid, while 123, 0, _TEMP, and __X are invalid in those ordinary-name positions.

validate_dimensions(obj)

The input must be a mapping of valid dimension names to non-negative integer sizes or None (null in JSON). Zero and None are valid unresolved/unlimited sizes.

It must accept, for example:

{}
{'X': 1, 'Y': 2}
{'TIME': 0, 'DEPTH': None}

It must raise ValidationError for non-mappings such as None, 'X', ['X'], or 10, and for invalid entries such as:

{'123': 123}   # invalid name
{'X': 'one'}   # invalid size type
{'X': -1}      # negative size
{'X': 1.5}     # non-integral size

Boolean values are not integer dimension sizes.

validate_variables(obj)

The input must be a mapping from valid variable names to variable-definition mappings. It must accept empty and partial definitions, including all of the following:

{'X': {'_datatype': 'float32'}}
{'X': {'_dimensions': []}}
{'X': {'name': 'X'}}
{'X': {'_data': None}}

}

The reserved fields must have suitable values:

  • _dimensions is a list of valid dimension-name strings;
  • _datatype is a string;
  • _data is array-like or None, not a bare scalar; and
  • recognized creation/control fields have values suitable for their corresponding NetCDF options.

Ordinary flat metadata names follow the name rule above and their values use NetCDF-attribute-compatible scalar or array forms. The compatibility attributes entry is an explicit exception to the ordinary scalar/array value rule: it must be a mapping of individual NetCDF attribute names to values. It may include creation-time attributes such as _FillValue.

validate_variables must raise ValidationError for, among other cases:

  • None, a string such as 'VAR', or any other non-mapping outer value;
  • a non-mapping variable definition;
  • an invalid variable name such as __X or _TEMP;
  • an unknown reserved field, as in {'X': {'_datatype': 'float32', '_unknown': 'else'}};
  • an invalid flat metadata name, as in {'X': {'_datatype': 'float32', '0': 'none'}};
  • an incorrectly typed reserved value; and
  • scalar data such as {'X': {'_data': 100}}.

The input must be a mapping with valid, non-underscore attribute names. Attribute values may be strings, non-boolean numbers, or arrays/lists suitable for NetCDF attributes.

It must accept:

{}
{'name': 'test'}
{'name': 1.5}
{'name': [1, 2, 3]}

It must raise ValidationError for:

None
'X'
[]

{'null': None}
{'bool': True}
{'object': {}}

In particular, None, booleans, and mappings are not valid global-attribute values.

DatasetTemplate

Construction and state

The supported constructor keywords are dimensions, variables, and global_attributes.

DatasetTemplate()

DatasetTemplate(variables={...})

                global_attributes=global_attributes)

With no arguments, dimensions, variables, and global_attributes are empty mutable mappings. Supplied mappings populate the corresponding public attributes and are validated with the functions above; invalid constructor values raise ValidationError. Examples include a string dimensions value, a negative dimension, a string variables value, a variable named _TEMP, a string global-attributes value, or a global attribute whose value is None.

The public instance state is:

  • template.dimensions: the mutable dimension mapping;
  • template.variables: the mutable mapping of flat variable definitions;
  • template.global_attributes: the mutable global-attribute mapping; and
  • template.ncobj: initially None, then the underlying NetCDF Dataset object used by to_netcdf.

These mappings remain directly mutable. Callers can add or replace dimensions and variables, set template.variables[name]['_dimensions'], set template.variables[name]['_data'], and update a variable definition with flat metadata. Updating a definition in place, for example with units and then comment, must retain existing metadata such as standard_name and preserve mapping insertion order. Global attributes can likewise be added with template.global_attributes.update(...).

DatasetTemplate.from_json(path)

This class method loads a JSON template while preserving object key order. It constructs the instance as follows:

  • dimensions comes from _dimensions, or is empty when that section is absent;
  • variables comes from _variables, or is empty when that section is absent; and
  • global_attributes is metadata_attributes applied to the loaded top-level mapping.

Consequently, a partial template may define _variables and top-level global attributes without defining _dimensions.

Dimension resolution and consistency

Before writing array data, unresolved dimension sizes (0 or None) are resolved from the corresponding axes of _data where possible. For example, data with shapes (10,), (1,), and (10, 1) for TIME, DEPTH, and TEMP produces dimension sizes TIME = 10 and DEPTH = 1.

A value array's rank must match the number of names in its _dimensions, and every fixed nonzero dimension size must agree with the corresponding data axis. Inconsistent shapes or undefined referenced dimensions must cause ValueError rather than producing an inconsistent file.

to_netcdf(path)

to_netcdf creates a NetCDF file at the supplied output path and returns None. An empty template must produce a valid empty file. Writing must provide the following observable behavior:

Dimensions and variables
  • Declared dimensions are created in template order, using resolved sizes where data supplied those sizes.
  • Each variable uses _datatype as its datatype.
  • Each variable uses the names in _dimensions in order. If _dimensions is absent, the variable is dimensionless and has () as its NetCDF dimensions.
  • _data containing array-like values is written to the variable. The stored dtype and dimensions correspond to _datatype and _dimensions.
  • _data: None is an explicit request to create the variable without assigning values. For a dimensioned variable, reading the result with automatic masking yields fill/missing values throughout. It is also valid for a dimensionless variable.
  • A variable that requires data because it has dimensions must explicitly provide _data; omitting that entry raises ValueError. In particular, a dimensioned definition containing only _dimensions and _datatype is not writable until _data is added, although it remains valid under validate_variables.
Global attributes

Every entry of template.global_attributes is written as an individual NetCDF dataset attribute. Underscore-prefixed top-level reserved fields are not emitted as global attributes.

Variable attributes: authoritative compatibility rule

Variable-attribute output has one unambiguous source: the optional nested attributes mapping in the variable definition.

  • Each ordinary entry in that nested mapping is written as an individual NetCDF variable attribute.
  • The container name itself is not written; there must never be a literal NetCDF attribute named attributes merely because this compatibility mapping was supplied.
  • Direct non-underscore entries in the flat definition, including standard_name, units, valid_min, and valid_max, remain mutable template metadata but are not emitted as NetCDF variable attributes.
  • If attributes is absent, direct flat metadata does not cause entries to appear in the variable's ncattrs().
  • A direct reserved _FillValue in the flat definition is not the output fill-value declaration. Fill creation and masking behavior are controlled by _FillValue inside the nested attributes mapping. If both forms are present, the nested compatibility mapping is authoritative for output.

Creation-time attributes must be applied when the variable is created. In particular, with:

{
    '_dimensions': ['X'],
    '_datatype': 'float32',
    'attributes': {'_FillValue': -999.0},
    '_data': values
}

_FillValue is -999.0 in the file, input values equal to -999.0 read back as missing under automatic masking, and masked positions in a NumPy masked-array input are stored using that fill value. Other nested creation-time options must likewise be treated as creation options rather than creating a literal attribute for the attributes container.

Dataset lifetime and errors

to_netcdf must close the underlying dataset on every path after it has been opened:

  • after a successful call, template.ncobj refers to a closed dataset and template.ncobj.isopen() is False; and
  • if any later operation raises, including the missing-_data ValueError, the dataset is closed before the original exception propagates, and template.ncobj.isopen() is False.

No partially handled write error may leave the NetCDF handle open.

Bundled template data

Update the bundled main and partial JSON templates to the flat format.

The main template must contain:

  • _dimensions entries for TIME and DEPTH (sizes may use 0/null for later resolution);
  • _variables.TIME with _dimensions: ["TIME"] and _datatype: "float64";
  • _variables.DEPTH with _dimensions: ["DEPTH"] and _datatype: "float32";
  • _variables.TEMP with _dimensions: ["TIME", "DEPTH"], _datatype: "float32", flat metadata including standard_name: "sea_water_temperature", and related metadata such as units, valid_min, and valid_max;
  • representative reserved variable fields such as _zlib, _complevel, and _FillValue; and
  • non-underscore top-level global attributes such as title, abstract, Conventions, and number rather than a nested global-attributes object.

The partial template must have a _variables section with at least a TEMP definition containing flat standard_name: "sea_water_temperature", plus non-underscore top-level global attributes. It must omit _dimensions, so loading it yields an empty template.dimensions mapping.

Naming and compatibility summary

  • Structural and control fields are underscore-prefixed; examples include _dimensions, _variables, _datatype, _data, _format, _FillValue, _zlib, and _complevel.
  • Non-underscore top-level entries are global attributes.
  • Non-underscore variable entries are flat template metadata, except that attributes has its legacy nested-container meaning.
  • metadata_attributes performs the shared underscore filter and preserves order.
  • The nested attributes form remains accepted by validation and is the sole source of serialized NetCDF variable attributes. Flat variable metadata is intentionally not serialized.

Concept: Special vs. Metadata Attributes

Template dictionaries (for the dataset as a whole, and for individual variables) contain a flat mapping of keys to values. Keys are divided into two categories:

  • Special (structural) attributes: keys that begin with a leading underscore (_). These describe structural information (e.g. _dimensions, _datatype, _fill_value, _data, _FillValue — note that _FillValue also begins with an underscore and is therefore special).
  • Metadata attributes: all other keys (those that do NOT begin with a leading underscore). These represent NetCDF attributes to be written onto the dataset or variable.

  • The values of retained entries are unchanged.
  • The returned mapping preserves the type of the input mapping: if the input is an OrderedDict, the result must be an OrderedDict; a plain dict input yields a plain dict.
  • An empty input yields an empty mapping.

Template Structure Change: Variable Attributes

Variable definitions in a template are flat mappings that mix special keys and metadata keys directly at the same level. Structural information uses underscore-prefixed keys (e.g. _dimensions, _datatype, _data, _FillValue), and NetCDF attributes are given as plain (non-underscore) keys directly in the variable mapping.

A variable is defined like this:

template.variables['X'] = {
    '_dimensions': ['X'],
    '_datatype': 'float32',
    '_FillValue': -999.,
    '_data': <array>,
}

There is no longer a nested 'attributes' sub-dictionary on variables. The NetCDF attributes to be written onto a created variable are exactly the metadata attributes of the variable's mapping (i.e. the result of applying metadata_attributes to the variable definition) — all non-underscore keys, with their values.

When DatasetTemplate produces a NetCDF Dataset:

  • Each variable is created with its declared dimensions (_dimensions) and datatype (_datatype).
  • The set of NetCDF attributes written onto each created variable equals metadata_attributes applied to that variable's definition mapping (i.e. only the non-underscore keys). Specifically, given a fill value of -999. and data where the first five positions are fill/masked, the stored variable's values at those positions must equal -999. and the remaining positions must equal the supplied data values.
  • Variable data (_data) is written as the variable's values.

Constraints

  • Implement only the behavior described above. Do not introduce a nested attributes mapping for variables.
  • metadata_attributes and special_attributes must be usable both internally and as exported package functions.

Task Specification: Template Validation for NetCDF Writing

Overview

Implement complete validation and reconciliation of NetCDF dataset templates before they are written. A template contains dimension definitions and variable definitions and must be checked for schema conformance, completeness, and shape consistency before creation of the NetCDF object begins.

Public API Surface

The work is centered on DatasetTemplate, importable from ncwriter. ValidationError must be importable from the same public location:

from ncwriter import DatasetTemplate, ValidationError
DatasetTemplate construction and state

DatasetTemplate(dimensions=..., variables=...) accepts optional dimension and variable mappings. Omitting either mapping produces an empty mapping.

  • template.dimensions is an insertion-ordered mapping from dimension name to size. A size may be a non-negative integer or None.
  • template.variables is a mapping from variable name to a variable-definition dictionary.
  • Both attributes remain directly assignable and mutable after construction.
  • template.ncobj is None until a NetCDF object is created. If pre-write validation fails, no NetCDF object may be created and template.ncobj must remain None.
Variable-definition dictionaries

A variable definition may contain these structural entries:

  • _dimensions: a list of dimension names. An empty list represents a scalar/dimensionless variable.
  • _datatype: a NumPy dtype, or a string/name convertible to a NumPy dtype, such as 'float32' or 'double'.
  • _data: the variable data. Supported values include a plain Python list, a NumPy array, a NumPy masked array, a zero-dimensional NumPy array, or None. None explicitly means that the variable is present but all of its values are fill values.

The variable schema must accept NumPy arrays, including masked and zero-dimensional arrays, as _data; it must accept supported NumPy dtype values for _datatype; and it must accept _FillValue as a variable attribute. Ordinary variable metadata remains distinct from the underscore-prefixed structural entries.

Required Methods

ensure_completeness(self)

This method validates and completes every definition in template.variables, modifying the definitions in place.

  1. Default dimensions

    • If _dimensions is absent, add _dimensions: [].
    • Leave an existing _dimensions list unchanged.

  2. Require an explicit data entry

    • If the _data key is absent, raise ValidationError with a message of the form: No data specified for variable '<name>'
    • This check takes precedence when both _data and _datatype are absent. Such a definition must report missing data, not missing datatype information.
    • An existing _data key whose value is None is not missing data.

  3. Normalize data

    • Convert a plain Python list in _data to a NumPy array in place without changing the represented values.
    • Leave existing NumPy arrays, including masked arrays and zero-dimensional arrays, usable as arrays.
    • Accept None without attempting to convert it.

  4. Normalize or infer datatype

    • If _datatype is present, normalize it to a numpy.dtype object.
    • If _datatype is absent and non-None _data supplies dtype information, infer the datatype from that data. A list such as [12.3] infers numpy.dtype('float64'); a NumPy array uses that array's own dtype.
    • If _data is present but no datatype was supplied and no datatype can be inferred, raise ValidationError with a message of the form: No data type information for variable '<name>'
    • Consequently, _data: None is valid only when _datatype is otherwise supplied.
ensure_consistency(self)

This method reconciles variable shapes with template.dimensions in place. It must preserve the identity of every variable-definition dictionary already stored in template.variables.

  1. Undefined dimensions

    • Every name referenced by a variable's _dimensions list must exist in template.dimensions, including for variables whose _data is None.
    • If any reference is undefined, raise ValidationError whose message contains undefined dimensions.

  2. Infer unresolved dimensions

    • Both None and 0 declare an unresolved/extendible dimension size. They are not fixed sizes.
    • When non-None variable data uses such a dimension, replace its unresolved size with the corresponding axis length from the data. For example, data of shape (12,) using a dimension declared as either None or 0 updates that dimension to 12.
    • In particular, a zero-sized placeholder must permit data with a positive extent and must grow to that extent rather than causing an inconsistency error.

  3. Check fixed and inferred sizes

    • A positive declared integer is a fixed dimension size and must be preserved.
    • Once a size is known, whether declared or inferred from an earlier variable, every variable using that dimension must have the same extent on the corresponding axis.
    • A mismatch raises ValueError whose message contains inconsistent with dimension sizes defined in template.

  4. Check rank

    • For non-None data, the number of names in _dimensions must equal the rank of the data array.
    • A mismatch raises ValueError with exactly this form: Variable '<name>' has <N> dimensions, but value array has <M> dimensions.
    • For example, _dimensions: ['X'] with data of shape (10, 2) must produce Variable 'W' has 1 dimensions, but value array has 2 dimensions.

  5. Handle variables without materialized data

    • A variable with _data: None does not participate in rank checking or dimension-size inference and does not create a size mismatch. Its definition remains unchanged.

  6. Handle scalar variables

    • Empty _dimensions together with zero-dimensional array data is consistent and does not alter template.dimensions.

After successful reconciliation, positive fixed sizes remain unchanged, and every None- or 0-sized dimension for which data supplied an extent contains the inferred integer size. Unused unresolved dimensions may remain unresolved. ensure_consistency works with the _dimensions and _data entries as present and is normally called after ensure_completeness.

to_netcdf(self, path)

Write the template to a NetCDF file at path. Before opening or creating the NetCDF object, perform full schema validation, completeness validation, and consistency reconciliation as specified above.

Required observable behavior includes:

  • A variable without an _data key raises the missing-data ValidationError; data is mandatory even if dimensions and datatype were supplied.
  • A variable with _data: None is accepted and is written as an all-fill-value variable.
  • A dimension initially declared as 0 or None is inferred from supplied data before writing. Thus a dimension declared as 0 and used by length-N data is written with size N, not rejected as inconsistent.
  • If validation fails, template.ncobj remains None and NetCDF object creation has not begun.
  • A variable with _datatype: 'double' and scalar data such as numpy.array(1) is written as a dimensionless variable whose NetCDF dimensions tuple is ().
  • _FillValue is honored when creating a variable. Data equal to that fill value is represented as fill data under normal NetCDF masking behavior.
  • Masked-array data is written correctly: masked positions become fill values and unmasked positions retain their values.
  • A valid empty template may be written as an empty NetCDF dataset.

Error Types

  • Raise ValidationError for schema violations, an absent _data key, unavailable datatype information, and references to undefined dimensions.
  • Raise ValueError for array-rank mismatches and dimension-size inconsistencies.

Compatibility and Constraints

  • Dimension and variable mappings remain mutable and replaceable through their public attributes.
  • Dimension insertion order is preserved.

Global attributes and complete templates

Global attributes form a dictionary of valid metadata names to string, numeric, list, or NumPy-array values. None, Boolean, and dictionary values are invalid attribute values. A non-dictionary global-attribute value is invalid.

A complete template is a dictionary that may contain _dimensions, _variables, and ordinary global metadata attributes. Any section may be omitted, but a section that is present must satisfy its own schema.

Loading and combining templates

JSON loading

DatasetTemplate.from_json(path) reads JSON while preserving object member order. It obtains dimensions from _dimensions, variables from _variables, and global attributes from all top-level letter-prefixed entries. Missing dimensions or variables become empty dictionaries.

Invalid JSON raises ValueError; its message must identify the input as an invalid JSON file and include the supplied path. File-opening errors continue to propagate normally. Schema-invalid parsed content raises ValidationError during object construction.

Because this is a class method, calling ImosTemplate.from_json(path) returns an ImosTemplate and retains the IMOS default-global behavior described below.

Combining templates

left + right returns a new object of the left operand's template class and does not mutate left. All three sections are merged:

  • dimensions are merged, with values from right replacing values from left for duplicate names;
  • global attributes are merged, with values from right replacing values from left for duplicate names;
  • variables unique to either operand are retained in the result. When the same variable name appears on both sides, the two definitions are merged entry by entry: entries present only in left (including structural entries such as _dimensions and _datatype) are retained, while entries from right override duplicate keys. The right-hand definition does not replace the left-hand definition wholesale.

For example, adding a template whose variable Y is {'_dimensions': ['ONE'], '_datatype': 'float32'} to one whose Y is {'_dimensions': ['TWO'], 'comment': 'updated'} yields {'_dimensions': ['TWO'], '_datatype': 'float32', 'comment': 'updated'}.

Completing and checking a template

Two public methods normalize and check a template before writing. Both mutate the template in place and return None. They may also be called directly.

Completeness

ensure_completeness() normalizes every variable definition in place:

  • When the _dimensions entry is absent, it inserts _dimensions as an empty list.
  • When the _data entry is absent, it raises ValidationError with the message No data specified for variable '{name}'. An entry explicitly set to None is not absent: _data=None is a valid request for a variable created without assigned values.
  • When _data is neither None nor already a NumPy array (for example a plain number or list), it is converted in place with numpy.array, so the stored _data value becomes a NumPy array afterwards.
  • When the _datatype entry is absent, the method infers it from the data array's dtype, stores that dtype object as _datatype, and emits a UserWarning with the message Guessed data type '{datatype}' for variable '{name}'. For example, a Python list [12.3] yields a guessed datatype of float64, and a supplied float32 array yields that array's own dtype object.
  • If no dtype can be inferred (for example when _data is None), it raises ValidationError with the message No data type information for variable '{name}'.
Dimensional consistency

ensure_consistency() checks each variable's declared dimensions and data shape against the template's dimensions, operating on the existing variable-definition objects: the checks and updates must not replace supplied variable-definition objects with copies. It expects completeness normalization to have run first (each variable has a _dimensions list). For each variable, in order:

  1. Every declared variable dimension must exist in the template's dimensions; otherwise it raises ValidationError with the message Variable '{name}' has undefined dimensions {inconsistent_dims}.
  2. A variable whose _data is None is exempt from the remaining rank and shape checks.
  3. Otherwise, the data array's rank must equal the number of declared dimensions; a mismatch raises ValueError with the message Variable '{name}' has {ndim} dimensions, but value array has {nshape} dimensions. (for example, Variable 'W' has 1 dimensions, but value array has 2 dimensions.).
  4. Each referenced dimension whose template size is currently None is then set to the size of the corresponding data axis, and that inferred size persists in the template's dimensions.
  5. Any remaining mismatch between the data shape and the template's dimension sizes raises ValueError with the message Variable '{name}' has dimensions {var_dims} and shape {var_shape}, inconsistent with dimension sizes defined in template {template_shape}.

A scalar variable with _dimensions=[] is consistent and requires no template dimensions. A template already consistent with its data is left unchanged.

Writing NetCDF files

to_netcdf(outfile, var_args=None, **kwargs) records outfile on the template and then, before opening the output dataset, runs the following preflight sequence in order:

  1. current-schema validation of dimensions, variables, and global attributes (as in validate_template_schema());
  2. ensure_completeness();
  3. ensure_consistency().

Consequently, an incomplete variable (for example one with no _data entry at all) fails with ValidationError before any NetCDF handle is opened, whereas an explicit _data=None remains a valid request to create an unassigned variable. After a successful preflight, the method:

  1. opens outfile in write mode, with kwargs forwarded to netCDF4.Dataset;
  2. creates dimensions in dictionary order;
  3. creates variables with the declared datatype and dimensions;
  4. writes non-None _data values;
  5. writes letter-prefixed variable metadata;
  6. writes all global attributes;
  7. synchronizes and closes the write handle.

A successful call returns None after completing this write and reopen sequence.

Existing output is clobbered by the default NetCDF write behavior. An empty template creates a valid empty NetCDF file. A dimensionless variable is created as a scalar NetCDF variable. A variable with _data=None is created without explicit assignment, yielding fill-valued data where applicable.

For dimensioned variables, recognized underscore-prefixed creation settings are passed as NetCDF variable-creation options after removal of their leading underscore. var_args, when supplied, provides creation options applied to every dimensioned variable and takes precedence over per-variable options. The remaining kwargs belong to dataset creation, not variable creation. Legacy scalar creation behavior is retained: scalar variables are created from name and datatype without forwarding these per-variable creation options.

Both _FillValue and _fill_value are aliases for the NetCDF fill_value creation option. If both are supplied with the same value, writing emits a warning and proceeds. If both are supplied with different values, writing raises ValueError. Fill values and masks must round-trip with normal netCDF4 masked-array behavior.

The public create_dimensions(), create_variables(**kwargs), and create_global_attributes() operations retain their behavior of acting on the current ncobj. Any output handle opened during a failed write must be closed. A validation failure before file creation leaves ncobj as None on a fresh template. On successful to_netcdf, the completed file is reopened in append mode and exposed through template.ncobj; the caller may close that handle when finished.

Data ranges

DatasetTemplate.get_data_range(varname) returns (minimum, maximum) for the variable's attached _data, preserving NumPy scalar result types where applicable. Existing masks and NaN values are excluded. A truthy _FillValue takes precedence as the fill value to exclude; otherwise the method falls back to _fill_value. If neither selected value is truthy, only NaNs and existing masks are excluded.

It supports scalar and array data. It raises ValueError if the named variable does not exist or if the resulting data is entirely invalid or empty. For example, data [NaN, 1, 2, 8] has range (1, 8), while a nonzero declared fill value is excluded from both extrema.

IMOS templates

ImosTemplate retains all DatasetTemplate behavior and begins with the bundled IMOS standard global attributes. User-supplied global_attributes are applied after those defaults and therefore override duplicate default names. The standard attributes and values are:

  • title, abstract, author, author_email, principal_investigator, principal_investigator_email, standard_name_vocabulary, and history: empty strings;
  • data_centre: Australian Ocean Data Network (AODN);
  • data_centre_email: info@aodn.org.au;
  • Conventions: CF-1.6,IMOS-1.4;
  • project: Integrated Marine Observing System (IMOS);
  • naming_authority: IMOS;
  • citation: The citation in a list of references is: "IMOS [year-of-data-download], [Title], [data-access-URL], accessed [date-of-access].".;
  • acknowledgement: Any users of IMOS data are required to clearly acknowledge the source of the material derived from IMOS in the format: "Data was sourced from the Integrated Marine Observing System (IMOS) - IMOS is a national collaborative research infrastructure, supported by the Australian Government.";
  • disclaimer: Data, products and services from IMOS are provided "as is" without any warranty as to fitness for a particular purpose.;
  • license: http://creativecommons.org/licenses/by/4.0/;
  • date_created, time_coverage_start, time_coverage_end, geospatial_vertical_min, geospatial_vertical_max, geospatial_lat_min, geospatial_lat_max, geospatial_lon_min, and geospatial_lon_max: empty strings.
Creation time

date_created is a read-only, lazily initialized datetime property. Its value is captured once per instance and reused. It must represent the current UTC time, not local time. Preserve the legacy timezone-naive datetime form while making its fields UTC-valued.

add_date_created_attribute() sets global attribute date_created from that cached value in the exact second-resolution format YYYY-MM-DDTHH:MM:SSZ (%Y-%m-%dT%H:%M:%SZ). The trailing Z therefore truthfully denotes UTC. Construction alone leaves the bundled empty default until this method is called.

Spatial and temporal extents

add_extent_attributes(time_var='TIME', vert_var='DEPTH', lat_var='LATITUDE', lon_var='LONGITUDE') computes selected extents from variable data using get_data_range and returns None:

  • the time range is converted with the time variable's units and its calendar, defaulting the calendar to gregorian, and is stored as time_coverage_start and time_coverage_end in YYYY-MM-DDTHH:MM:SSZ form;
  • vertical extrema become geospatial_vertical_min and geospatial_vertical_max;
  • latitude extrema become geospatial_lat_min and geospatial_lat_max;
  • longitude extrema become geospatial_lon_min and geospatial_lon_max.

Passing None or another false value for a coordinate argument skips that coordinate and leaves its attributes unchanged. Thus, skipping all four coordinates preserves the initial empty extent values. A selected time variable without units raises ValueError. Missing variables and selected variables with no valid values propagate the corresponding range error. The method is explicit; writing a file does not automatically calculate extents or creation time.

Relocated resources and companion packages

The template schema and IMOS global-attribute JSON resources must move with aodntools.ncwriter, be included in distributable artifacts, and remain discoverable when the relocated package is imported from an installed environment. Their contents and runtime meaning must not change.

Apply the same namespace transformation to the repository's existing companion package whose former flat name ends in _ncwriter: replace that final writer component with the two-level _aodntools.ncwriter hierarchy. The relocated parent and its ncwriter child must each be regular packages with package markers, so modules in that tree can import shared code through the transformed dotted name.

The relocated companion ncwriter directory must carry template1.json, template_partial.json, and bad.json. Each resource must be byte-for-byte identical to its same-named pre-relocation counterpart. In particular, the intentionally malformed JSON resource must remain malformed so consumers can exercise invalid-JSON behavior.

Package discovery, version metadata paths, package-data declarations, and related namespace references must cover the new hierarchy rather than only the former top-level package.

Compatibility and non-goals

  • The old top-level ncwriter import path is replaced by aodntools.ncwriter; a backward-compatibility alias for the old path is not required.
  • Do not change template syntax, accepted datatypes, precedence rules, mutation behavior, warning/error behavior, or generated NetCDF content except for the explicitly required UTC correction.
  • Do not add unrelated NetCDF templating features. The task is the complete relocation of existing functionality and its required resources under the aodntools namespace.
