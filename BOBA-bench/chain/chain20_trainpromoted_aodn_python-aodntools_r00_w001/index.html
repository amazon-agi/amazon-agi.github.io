Task: Dimensionless Variable Support in DatasetTemplate

Background

This task involves modifying a NetCDF writer library. The public API of interest is the DatasetTemplate class, importable as:

from ncwriter import DatasetTemplate

(The class in question is defined in the template module of the ncwriter package.)

Behavior That Is Required

A DatasetTemplate instance is constructed by passing a variables keyword argument, a dictionary that maps variable names to their definitions. Each variable definition is itself a dictionary; it may contain keys such as type, data, and dimensions.

The instance exposes a to_netcdf(path) method, which writes the template contents to a NetCDF file at the given path.

Modification to Implement

A variable definition is permitted to omit the dimensions key altogether. When a variable definition contains no dimensions key, that variable must be treated as dimensionless — that is, it is written to the NetCDF file with an empty tuple of dimensions.

In concrete terms, given a template such as:

template = DatasetTemplate(variables={'X': {'type': 'double', 'data': None}})
template.to_netcdf(some_path)

the writing step must succeed, and when the resulting file is opened, the variable X must exist and its .dimensions attribute must equal () (the empty tuple).

Additional Notes

  • The absence of a dimensions key must not raise an error; omitting it is equivalent to specifying no dimensions.
  • A variable with a data value of None must still be created successfully.

Task Specification: Flattened Template Schema for ncwriter

Overview of the migration

ncwriter templates are being moved to a flatter schema. The fields reserved by a template carry an underscore prefix, and ordinary metadata is stored directly next to those fields instead of under a metadata container that was previously required. Support for the legacy nested variable attributes mapping is kept, with the serialization behavior spelled out below.

Public API surface

Each of the following names must stay importable and callable exactly as shown.

ncwriter.schema
  • validate_dimensions(obj)
  • validate_variables(obj)
  • validate_global_attributes(obj) (taking over from the former public name validate_attributes)
  • ValidationError

All three validation functions return normally when the input is valid and raise ValidationError when it is invalid.

Top-level namespace of the package (ncwriter)
  • DatasetTemplate
  • ValidationError
  • metadata_attributes(mapping)

Format of the flat template

A template is a mapping — for example a JSON object, a dict, or an OrderedDict.

  • "_dimensions" is where the mapping of dimension names to sizes lives.
  • "_variables" is where the mapping of variable names to variable definitions lives.
  • Every top-level entry whose name does not begin with _ is a dataset global attribute.
  • Top-level entries with an underscore prefix in any other case are reserved and are not global attributes. For instance, "_format" must not appear among the dataset's global attributes.

A variable definition is a mapping whose entries are drawn from any combination of the following:

  • "_dimensions": a list of dimension names, which may be empty and may be omitted; when it is omitted, the variable is dimensionless.
  • "_datatype": a NetCDF datatype name, such as "float32", "float64", or "double".
  • "_data": the variable's values as array-like data, a NumPy masked array, or None.
  • Recognized control fields with an underscore prefix, including "_FillValue", "_zlib", and "_complevel". Other supported NetCDF control names use the same reserved underscore convention (for example, _shuffle, _fletcher32, _contiguous, _chunksizes, _endian, and _least_significant_digit). An arbitrary underscore-prefixed field is not permitted.
  • Ordinary keys without an underscore prefix, such as standard_name, units, and valid_min. These make up the flat variable template metadata.
  • For compatibility, the special key attributes, which is not underscore-prefixed and whose value is a nested mapping of NetCDF variable attributes.

Validation and writability are separate matters: an incomplete definition such as {}, or one that contains only _datatype, is valid template metadata, even though additional fields may be needed before it can be written.

metadata_attributes(mapping)

Given an input mapping, metadata_attributes returns a new mapping that contains exactly those input entries whose keys do not start with _. The function must:

  • leave out every underscore-prefixed entry;
  • keep every non-underscore entry together with its value; and
  • preserve the input's insertion order while not mutating the input.

For example, applying it to a top-level template removes _dimensions, _variables, and _format while title, abstract, and number are retained. The same filtering rule is what identifies flat metadata inside a variable definition. By itself, this filtering rule does not mean that flat variable metadata is serialized as NetCDF variable attributes; the serialization of variable attributes follows the compatibility rule described under to_netcdf.

Validation behavior

Dimension, variable, and ordinary attribute names must start with an ASCII letter and afterwards contain only ASCII letters, digits, or underscores (^[A-Za-z][A-Za-z0-9_]*$). Names such as X, TEMP_2, and Conventions are therefore valid, whereas 123, 0, _TEMP, and __X are invalid in those ordinary-name positions.

validate_dimensions(obj)

The input must be a mapping from valid dimension names to non-negative integer sizes or None (null in JSON). Zero and None are valid as unresolved/unlimited sizes.

For example, it must accept:

{}
{'X': 1, 'Y': 2}
{'TIME': 0, 'DEPTH': None}

It must raise ValidationError for non-mappings like None, 'X', ['X'], or 10, and for invalid entries like:

{'123': 123}   # invalid name
{'X': 'one'}   # invalid size type
{'X': -1}      # negative size
{'X': 1.5}     # non-integral size

Boolean values do not qualify as integer dimension sizes.

validate_variables(obj)

The input must be a mapping that goes from valid variable names to variable-definition mappings. It must accept empty and partial definitions, including all of these:

{}
{'X': {}}
{'X': {'_datatype': 'float32'}}
{'X': {'_dimensions': []}}
{'X': {'name': 'X'}}
{'X': {'_data': None}}
{'X': {'_dimensions': ['X'], '_datatype': 'float32'}}
{
    'X': {
        '_dimensions': ['X'],
        '_datatype': 'float32',
        '_data': [42],
        'name': 'X',
        'count': 1
    },
    'Y': {'_datatype': 'float64'}
}

The values of the reserved fields must be suitable:

  • _dimensions is a list whose entries are valid dimension-name strings;
  • _datatype is a string;
  • _data is array-like or None, and not a bare scalar; and
  • recognized creation/control fields have values that are suitable for their corresponding NetCDF options.

Ordinary flat metadata names obey the name rule above, and their values take scalar or array forms compatible with NetCDF attributes. The compatibility attributes entry is an explicit exception to that ordinary scalar/array value rule: it must be a mapping from individual NetCDF attribute names to values. Creation-time attributes such as _FillValue may be included in it.

Among other cases, validate_variables must raise ValidationError for:

  • None, a string like 'VAR', or any other outer value that is not a mapping;
  • a variable definition that is not a mapping;
  • a variable name that is invalid, such as __X or _TEMP;
  • a reserved field that is unknown, as in {'X': {'_datatype': 'float32', '_unknown': 'else'}};
  • a flat metadata name that is invalid, as in {'X': {'_datatype': 'float32', '0': 'none'}};
  • a reserved value with an incorrect type; and
  • scalar data such as {'X': {'_data': 100}}.
validate_global_attributes(obj)

The input must be a mapping whose attribute names are valid and non-underscore. Attribute values may be strings, numbers that are not booleans, or arrays/lists suited to NetCDF attributes.

It must accept these:

{}
{'name': 'test'}
{'name': 1.5}
{'name': [1, 2, 3]}

It must raise ValidationError for these:

None
'X'
[]
{'_badname': 1}
{'null': None}
{'bool': True}
{'object': {}}

In particular, None, booleans, and mappings are not valid as global-attribute values.

DatasetTemplate

Construction and instance state

The constructor keywords that are supported are dimensions, variables, and global_attributes.

DatasetTemplate()
DatasetTemplate(dimensions={'X': 10})
DatasetTemplate(variables={...})
DatasetTemplate(dimensions=dims, variables=variables,
                global_attributes=global_attributes)

Called with no arguments, it gives dimensions, variables, and global_attributes as empty mutable mappings. Mappings that are supplied populate the matching public attributes and are validated with the functions above; invalid constructor values raise ValidationError. Examples include a dimensions value that is a string, a negative dimension, a variables value that is a string, a variable named _TEMP, a global-attributes value that is a string, or a global attribute whose value is None.

The public state of an instance is:

  • template.dimensions: the dimension mapping, which is mutable;
  • template.variables: the mutable mapping holding the flat variable definitions;
  • template.global_attributes: the mutable mapping of global attributes; and
  • template.ncobj: None at first, then the underlying NetCDF Dataset object that to_netcdf uses.

These mappings stay directly mutable. Callers can add dimensions and variables or replace them, set template.variables[name]['_dimensions'], set template.variables[name]['_data'], and update a variable definition with flat metadata. An in-place update of a definition — for example first with units and then with comment — must retain existing metadata such as standard_name and preserve mapping insertion order. Global attributes can likewise be added via template.global_attributes.update(...).

DatasetTemplate.from_json(path)

This class method loads a JSON template and keeps object key order while doing so. It builds the instance as follows:

  • dimensions is taken from _dimensions, or is empty when that section is absent;
  • variables is taken from _variables, or is empty when that section is absent; and
  • global_attributes is metadata_attributes applied to the top-level mapping that was loaded.

As a consequence, a partial template may define _variables and top-level global attributes while _dimensions is left undefined.

Dimension resolution and consistency checks

Before any array data is written, dimension sizes that are still unresolved (0 or None) are resolved from the corresponding axes of _data, where possible. For example, when data with shapes (10,), (1,), and (10, 1) is given for TIME, DEPTH, and TEMP, the dimension sizes produced are TIME = 10 and DEPTH = 1.

The rank of a value array must match how many names its _dimensions contains, and every fixed nonzero dimension size must agree with the corresponding data axis. Shapes that are inconsistent, or referenced dimensions that are undefined, must cause ValueError rather than produce an inconsistent file.

to_netcdf(path)

to_netcdf creates a NetCDF file at the output path that is supplied and returns None. An empty template must result in a valid empty file. Writing must provide the following observable behavior:

Creation of dimensions and variables
  • The declared dimensions are created in the template's order, with resolved sizes used where data supplied those sizes.
  • Each variable takes _datatype as its datatype.
  • For each variable, the names in _dimensions are used in order. If _dimensions is absent, the variable is dimensionless and its NetCDF dimensions are ().
  • When _data holds array-like values, it is written to the variable. The dtype and dimensions that get stored correspond to _datatype and _dimensions.
  • _data: None is an explicit request to create the variable with no values assigned. For a dimensioned variable, reading the result with automatic masking yields fill/missing values throughout. This is also valid for a dimensionless variable.
  • A variable that has dimensions and therefore requires data must explicitly provide _data; leaving that entry out raises ValueError. In particular, a dimensioned definition that contains only _dimensions and _datatype is not writable until _data is added, even though it remains valid under validate_variables.
Global attribute writing

Every entry of template.global_attributes is written out as an individual NetCDF dataset attribute. Top-level reserved fields with an underscore prefix are not emitted as global attributes.

Variable attributes: the authoritative compatibility rule

There is one unambiguous source for variable-attribute output: the optional nested attributes mapping inside the variable definition.

  • Every ordinary entry in that nested mapping is written as an individual NetCDF variable attribute.
  • The name of the container is not written itself; there must never be a literal NetCDF attribute named attributes merely because this compatibility mapping was supplied.
  • Non-underscore entries placed directly in the flat definition — including standard_name, units, valid_min, and valid_max — remain mutable template metadata but are not emitted as NetCDF variable attributes.
  • If attributes is absent, flat metadata placed directly does not make entries appear in the variable's ncattrs().
  • A reserved _FillValue placed directly in the flat definition is not the output fill-value declaration. _FillValue inside the nested attributes mapping controls fill creation and masking behavior. If both forms are present, the nested compatibility mapping is the authoritative one for output.

Creation-time attributes must be applied at the time the variable is created. In particular, with:

{
    '_dimensions': ['X'],
    '_datatype': 'float32',
    'attributes': {'_FillValue': -999.0},
    '_data': values
}

_FillValue is -999.0 in the file, input values equal to -999.0 read back as missing under automatic masking, and masked positions in a NumPy masked-array input are stored with that fill value. Other nested creation-time options must likewise be treated as creation options rather than producing a literal attribute for the attributes container.

Dataset lifetime and error handling

Once the underlying dataset has been opened, to_netcdf must close it on every path:

  • after a call that succeeds, template.ncobj refers to a closed dataset and template.ncobj.isopen() is False; and
  • if any later operation raises — including the missing-_data ValueError — the dataset is closed before the original exception propagates, and template.ncobj.isopen() is False.

No write error that is only partially handled may leave the NetCDF handle open.

Bundled template data files

Bring the bundled main and partial JSON templates over to the flat format.

The main template must contain:

  • _dimensions entries for TIME and DEPTH (the sizes may be 0/null, for resolution at a later point);
  • _variables.TIME carrying _dimensions: ["TIME"] and _datatype: "float64";
  • _variables.DEPTH carrying _dimensions: ["DEPTH"] and _datatype: "float32";
  • _variables.TEMP with _dimensions: ["TIME", "DEPTH"], _datatype: "float32", flat metadata that includes standard_name: "sea_water_temperature", and related metadata such as units, valid_min, and valid_max;
  • reserved variable fields that are representative, such as _zlib, _complevel, and _FillValue; and
  • top-level global attributes without an underscore prefix, such as title, abstract, Conventions, and number, rather than a nested global-attributes object.

The partial template must contain a _variables section with at least a TEMP definition that has flat standard_name: "sea_water_temperature", plus top-level global attributes without an underscore prefix. It must leave _dimensions out, so that loading it yields an empty template.dimensions mapping.

Summary of naming and compatibility

  • Fields that are structural or control fields carry an underscore prefix; examples include _dimensions, _variables, _datatype, _data, _format, _FillValue, _zlib, and _complevel.
  • Top-level entries without an underscore prefix are global attributes.
  • Variable entries without an underscore prefix are flat template metadata, with the exception that attributes keeps its legacy nested-container meaning.
  • The shared underscore filter is what metadata_attributes performs, and it preserves order.
  • Validation continues to accept the nested attributes form, and it is the sole source of serialized NetCDF variable attributes. Flat variable metadata is deliberately not serialized.

You are working on the ncwriter package, a set of tools for building NetCDF datasets from template dictionaries. You must implement two public utility functions and change how variable/attribute metadata is represented in templates.

Public API to Implement

The following names must be exported by the ncwriter package (importable directly from ncwriter):

  • DatasetTemplate
  • ValidationError
  • metadata_attributes
  • special_attributes

This task centers on the two utility functions metadata_attributes and special_attributes.

Concept: Special versus Metadata Attributes

Template dictionaries — covering both the dataset as a whole and individual variables — hold a flat mapping of keys to values. The keys fall into two categories:

  • Special (structural) attributes: keys that start with a leading underscore (_). These carry structural information (e.g. _dimensions, _datatype, _fill_value, _data, _FillValue — note that _FillValue also begins with an underscore and is therefore special).
  • Metadata attributes: all remaining keys (the ones that do NOT begin with a leading underscore). These stand for the NetCDF attributes to be written onto the dataset or variable.

Function: metadata_attributes(d)

Signature: metadata_attributes(d) — the function takes a single mapping argument and returns a new mapping.

Behavior:

  • Returns a new mapping that contains only those entries of d whose keys do NOT start with a leading underscore.
  • Entries whose keys begin with _ are left out.
  • The values of the retained entries stay unchanged.
  • The type of the input mapping is preserved in the returned mapping: if the input is an OrderedDict, the result must be an OrderedDict; a plain dict input yields a plain dict.
  • Empty input yields an empty mapping.

Examples of the required results:

  • {} → {}
  • {'_dimensions': {}, '_fill_value': -999} → {}
  • {'title': 'Title'} → {'title': 'Title'}
  • {'title': 'Title', '_fill_value': -999} → {'title': 'Title'}
  • When the input is an OrderedDict, the result is an OrderedDict.

Function: special_attributes(d)

Signature: special_attributes(d) — the function takes a single mapping argument and returns a new mapping.

Behavior:

  • Returns a new mapping that contains only those entries of d whose keys begin with a leading underscore.
  • In the result, each retained key has its single leading underscore stripped.
  • Retained entries keep their values unchanged.
  • Entries whose keys do NOT begin with _ are omitted.
  • Empty input yields an empty mapping.

Examples of the required results:

  • {} → {}
  • {'title': 'Title'} → {}
  • {'_dimensions': {}, '_fill_value': -999} → {'dimensions': {}, 'fill_value': -999}
  • {'title': 'Title', '_fill_value': -999} → {'fill_value': -999}

Change to Template Structure: Variable Attributes

Within a template, a variable definition is a flat mapping in which special keys and metadata keys are mixed directly at the same level. Structural information uses underscore-prefixed keys (e.g. _dimensions, _datatype, _data, _FillValue), and NetCDF attributes are supplied as plain (non-underscore) keys directly in the variable mapping.

A variable is defined as follows:

template.variables['X'] = {
    '_dimensions': ['X'],
    '_datatype': 'float32',
    '_FillValue': -999.,
    '_data': <array>,
}

Variables no longer have a nested 'attributes' sub-dictionary. The NetCDF attributes to be written onto a created variable are exactly the metadata attributes of the variable's mapping (i.e. the outcome of applying metadata_attributes to the variable definition) — all non-underscore keys, together with their values.

Behavior When a NetCDF Dataset Is Created

When a NetCDF Dataset is produced by DatasetTemplate:

  • Each variable is created using its declared dimensions (_dimensions) and datatype (_datatype).
  • For each created variable, the set of NetCDF attributes written onto it equals metadata_attributes applied to that variable's definition mapping (i.e. only the non-underscore keys). Underscore-prefixed keys (such as _dimensions, _datatype, _data, _FillValue) must NOT be present as ordinary NetCDF attributes derived from the metadata set.
  • _FillValue is a structural/special key. If a variable is declared with a _FillValue special key, its fill value must be applied so that masked/fill positions in the data are represented by that fill value in the resulting NetCDF variable. Concretely, with a fill value of -999. and data whose first five positions are fill/masked, the stored variable's values at those positions must equal -999. and the remaining positions must equal the supplied data values.
  • The data of a variable (_data) is written as that variable's values.

Constraints

  • Implement only the behavior set out above. Do not add a nested attributes mapping for variables.
  • It must be possible to use metadata_attributes and special_attributes both internally and as exported package functions.

Task Specification: Validation of Templates for NetCDF Writing

Summary

Full validation and reconciliation of NetCDF dataset templates is to be implemented, taking place before they are written. A template holds definitions of dimensions together with definitions of variables, and it must be checked for schema conformance, for completeness, and for shape consistency before the creation of the NetCDF object begins.

Public API

The work revolves around DatasetTemplate, which is importable from ncwriter. ValidationError must be importable from that same public location:

from ncwriter import DatasetTemplate, ValidationError
Constructing DatasetTemplate and its state

The call DatasetTemplate(dimensions=..., variables=...) accepts mappings of dimensions and of variables, both optional. When either mapping is omitted, the result is an empty mapping.

  • template.dimensions is a mapping from dimension name to size whose order follows insertion. A size may be either a non-negative integer or None.
  • template.variables is a mapping from variable name to a dictionary defining that variable.
  • Both attributes can still be assigned to directly after construction and remain mutable.
  • template.ncobj holds None up until a NetCDF object is created. Should pre-write validation fail, no NetCDF object may be created, and template.ncobj must remain None.
Dictionaries that define variables

A variable definition may contain the following structural entries:

  • _dimensions: a list of dimension names; an empty list stands for a scalar/dimensionless variable.
  • _datatype: a NumPy dtype, or else a string/name that is convertible to a NumPy dtype, such as 'float32' or 'double'.
  • _data: the data of the variable. Values that are supported include a plain Python list, a NumPy array, a NumPy masked array, a zero-dimensional NumPy array, or None. None explicitly signifies that the variable is there but that all of its values are fill values.

The variable schema must accept NumPy arrays — masked arrays and zero-dimensional arrays included — as _data; it must accept, for _datatype, NumPy dtype values that are supported; and it must accept _FillValue as an attribute of the variable. Ordinary variable metadata stays distinct from the structural entries carrying an underscore prefix.

Methods That Are Required

ensure_completeness(self)

This method validates every definition in template.variables and completes it, changing the definitions in place.

  1. Dimension defaults

    • When _dimensions is absent, add _dimensions: [].
    • A _dimensions list that already exists is left as it is.

  2. An explicit data entry is required

    • When the _data key is absent, raise ValidationError with a message matching this form: No data specified for variable '<name>'
    • When both _data and _datatype are absent, it is this check that takes precedence. A definition of that kind must report missing data, not missing datatype information.
    • A _data key that is present with a value of None is not counted as missing data.

  3. Data normalization

    • A plain Python list found in _data is converted in place to a NumPy array, with the represented values kept intact.
    • NumPy arrays that already exist — masked arrays and zero-dimensional arrays included — are left usable as arrays.
    • None is accepted, and no conversion of it is attempted.

  4. Normalizing or inferring the datatype

    • Where _datatype is present, it is normalized into a numpy.dtype object.
    • Where _datatype is absent while non-None _data supplies dtype information, the datatype is inferred from that data. A list such as [12.3] gives numpy.dtype('float64'); for a NumPy array, that array's own dtype is what gets used.
    • Where _data is present but no datatype was supplied and none can be inferred, raise ValidationError with a message matching this form: No data type information for variable '<name>'
    • As a consequence, _data: None is valid only where _datatype is supplied some other way.
ensure_consistency(self)

This method brings variable shapes into line with template.dimensions in place. The identity of every variable-definition dictionary already held in template.variables must be preserved.

  1. Dimensions that are undefined

    • Every name referenced by a variable's _dimensions list must exist in template.dimensions, including when the variable's _data is None.
    • If any reference turns out to be undefined, raise ValidationError with a message containing undefined dimensions.

  2. Inferring unresolved dimensions

    • Both None and 0 are declarations of an unresolved/extendible dimension size; neither of them is a fixed size.
    • Whenever variable data that is non-None uses a dimension of this kind, that dimension's unresolved size is replaced with the length of the corresponding axis as taken from the data. To give an example, data of shape (12,) that uses a dimension declared as either None or 0 results in that dimension being updated to 12.
    • In particular, a placeholder whose size is zero must permit data having a positive extent, and it must grow to that extent instead of triggering an inconsistency error.

  3. Checking fixed and inferred sizes

    • A declared integer that is positive is a fixed dimension size and must be preserved.
    • As soon as a size is known — whether declared or inferred from a variable that came earlier — every variable that uses that dimension must have the same extent along the corresponding axis.
    • A mismatch raises ValueError, and its message contains inconsistent with dimension sizes defined in template.

  4. Checking the rank

    • For data that is non-None, the count of names in _dimensions must equal the rank of the data array.
    • A mismatch raises ValueError, and the message takes exactly this form: Variable '<name>' has <N> dimensions, but value array has <M> dimensions.

  • geospatial_lat_max
  • geospatial_lon_min

In other words, if None is passed for a given variable, the corresponding extent attribute(s) receive an empty string value. The mapping of each variable to its attributes is:

  • vert_var → geospatial_vertical_min, geospatial_vertical_max
  • lat_var → geospatial_lat_min, geospatial_lat_max
  • lon_var → geospatial_lon_min, geospatial_lon_max

After a call to add_extent_attributes(time_var=None, vert_var=None, lat_var=None, lon_var=None), each of the eight attributes above must be accessible in global_attributes with the value ''.

Objective

Restructure the existing ncwriter package so it sits inside a new regular top-level Python package, aodntools, with the writer accessible as aodntools.ncwriter.

What is called for is a namespace relocation, not a redesign. Aside from using UTC for IMOS creation timestamps and from relocating the companion packages and resources described below, the existing APIs, validation rules, object mutations, warnings, errors, NetCDF output, and IMOS behavior are to be preserved.

Required package and import surface

Both aodntools and aodntools.ncwriter must be regular importable Python packages. Use from an installed environment and from the source tree must support all of the following forms:

  • import aodntools.ncwriter
  • from aodntools.ncwriter import DatasetTemplate, ImosTemplate, ValidationError, metadata_attributes, special_attributes
  • from aodntools.ncwriter.schema import validate_template, validate_dimensions, validate_variables, validate_global_attributes, ValidationError
  • from aodntools.ncwriter.template import DatasetTemplate
  • from aodntools.ncwriter.imos_template import ImosTemplate

The five names listed for aodntools.ncwriter are public exports of the package. The package also keeps the existing __version__ behavior.

The objects obtained from the different import locations must be consistent:

  • aodntools.ncwriter.DatasetTemplate and aodntools.ncwriter.template.DatasetTemplate are the same class.
  • aodntools.ncwriter.ImosTemplate and aodntools.ncwriter.imos_template.ImosTemplate are the same class.
  • aodntools.ncwriter.ValidationError is the same exception that aodntools.ncwriter.schema exposes.
  • ImosTemplate is a subclass of DatasetTemplate.

Their other existing public module-level functionality is retained by the relocated submodules, including the template base/helper APIs and the IMOS timestamp constant. Every import inside them must resolve through the new package and must not depend on a separately installed top-level ncwriter module.

Template representation

A DatasetTemplate models a NetCDF dataset by means of three mutable dictionaries:

  • dimensions: dimension name to size. A size is either a non-negative integer or None, the latter meaning it is to be inferred or left unlimited.
  • variables: variable name to a dictionary that holds structural entries, data, and NetCDF metadata attributes.
  • global_attributes: NetCDF metadata attributes at the dataset level.

DatasetTemplate(dimensions=None, variables=None, global_attributes=None) builds empty ordered dictionaries for any sections that are omitted. Passing dictionaries initializes the matching properties and validates them. When a complete replacement is assigned to any of these properties, the same validation is performed. Mutating an already assigned dictionary directly remains supported; such mutations are checked by an explicit schema validation or before the output is written. outfile and ncobj initially hold None.

A variable's structural entries begin with _. The entries that are supported are:

  • _dimensions
  • _datatype
  • _data
  • _FillValue and _fill_value
  • _zlib, _complevel, _shuffle, _fletcher32, _contiguous, _chunksizes, _endian, and _least_significant_digit

A key that begins with a letter is a metadata attribute and is written to the NetCDF variable. Structural entries do not get written as ordinary metadata.

Attribute helper functions

metadata_attributes(mapping) returns a new mapping — of the same concrete mapping type — holding only the entries whose keys begin with a letter. Values and iteration order are retained.

special_attributes(mapping) returns a new mapping — of the same concrete mapping type — holding only the entries whose keys begin with _, and from every returned key it removes exactly the first underscore. Values and iteration order are retained.

As an example, _dimensions turns into dimensions and _fill_value into fill_value, whereas special_attributes leaves out title.

Schema validation

For valid input, the callables below return normally; for invalid input, they raise ValidationError:

  • validate_template(template) performs validation of a complete template dictionary.
  • validate_dimensions(dimensions) performs validation of a dimensions dictionary.
  • validate_variables(variables) performs validation of a variables dictionary.
  • validate_global_attributes(attributes) performs validation of a global-attribute dictionary and explicitly rejects every key beginning with _.

DatasetTemplate.validate_template_schema() applies the dimensions, variables, and global-attribute validation to the template's contents as they currently are. Invalid values are not coerced by the validation.

Names

Names of dimensions, of variables, of variable metadata, and of global metadata must match [A-Za-z][A-Za-z0-9_]*. A name beginning with a digit or an underscore is invalid. At the complete-template level, _dimensions and _variables are the only structural keys that are recognized; any other key with an underscore prefix is invalid.

Dimensions

The dimensions value must be a dictionary. Each size must be an integer greater than or equal to zero, or None. Strings, floating-point sizes, negative sizes, lists, and other values that are not dictionaries are invalid. An empty dictionary is valid. Although a single dimension may have the value None, a _dimensions entry that is present at the complete-template level may not itself be None.

Variables

The variables value must be a dictionary mapping valid names to variable-definition dictionaries. Variable definitions that are empty are schema-valid, although more information is required before such a variable can be written.

  • _dimensions, when present, is a list of valid dimension-name strings.
  • _datatype, when present, accepts the existing NetCDF datatype spellings: int, int8, int16, int32, int64, float, float16, float32, float64, double, S1, c, i1, b, B, u1, i2, h, s, u2, i4, i, l, u4, i8, u8, f4, f, f8, and d. NumPy numeric scalar classes and numpy.dtype objects likewise count as valid datatype specifications. An unknown string or an arbitrary value is invalid.
  • _FillValue and _fill_value accept a value that is numeric or a string.
  • _zlib, _shuffle, _fletcher32, and _contiguous are Boolean.
  • _complevel is an integer ranging from 1 through 9.
  • _endian is little, big, or native.
  • _least_significant_digit is an integer.
  • _chunksizes keeps its permissive legacy schema.
  • _data may be None, a number, a list, or a NumPy array, a masked array included.
  • A variable metadata attribute has a metadata name that is valid and a value that is a string, number, list, or NumPy array.

Underscore-prefixed variable entries that are unknown are rejected, as are invalid metadata names.

Global attributes and complete templates

Global attributes make up a dictionary of valid metadata names to string, numeric, list, or NumPy-array values. Attribute values that are None, Boolean, or dictionaries are invalid. A global-attribute value that is not a dictionary is invalid.

A complete template is a dictionary that may hold _dimensions, _variables, and ordinary global metadata attributes. Any section may be left out, but a section that is present must satisfy its own schema.

Loading and combining templates

JSON loading

DatasetTemplate.from_json(path) reads JSON with object member order preserved. Dimensions are obtained from _dimensions, variables from _variables, and global attributes from all top-level entries beginning with a letter. Dimensions or variables that are missing become empty dictionaries.

JSON that is invalid raises ValueError; its message must identify the input as an invalid JSON file and include the path that was supplied. Errors from opening the file continue to propagate as normal. Parsed content that is schema-invalid raises ValidationError during object construction.

Because this is a class method, a call to ImosTemplate.from_json(path) returns an ImosTemplate and retains the IMOS default-global behavior described below.

Combining templates

left + right returns a new object whose template class is the left operand's, and it does not mutate left. The merge covers all three sections:

  • dimensions are merged, and where names are duplicated, values from right replace values from left;
  • global attributes are merged, and where names are duplicated, values from right replace values from left;
  • variables unique to either operand are retained in the result. When the same variable name appears on both sides, the two definitions are merged entry by entry: entries present only in left (structural entries such as _dimensions and _datatype included) are retained, while entries from right override duplicate keys. The left-hand definition is not replaced wholesale by the right-hand definition.

For example, adding a template in which variable Y is {'_dimensions': ['ONE'], '_datatype': 'float32'} to one in which Y is {'_dimensions': ['TWO'], 'comment': 'updated'} yields {'_dimensions': ['TWO'], '_datatype': 'float32', 'comment': 'updated'}.

Completing and checking a template

Before writing, a template is normalized and checked by two public methods. Both mutate the template in place and return None. They may also be called directly.

Completeness

ensure_completeness() normalizes every variable definition in place:

  • When the _dimensions entry is absent, _dimensions is inserted as an empty list.
  • When the _data entry is absent, ValidationError is raised with the message No data specified for variable '{name}'. An entry that has been explicitly set to None is not absent: _data=None is a valid request for a variable created without assigned values.
  • When _data is neither None nor an already existing NumPy array (a plain number or list, for instance), it is converted in place with numpy.array, so the stored _data value is a NumPy array afterwards.
  • When the _datatype entry is absent, the method infers it from the data array's dtype, stores that dtype object as _datatype, and emits a UserWarning with the message Guessed data type '{datatype}' for variable '{name}'. As an example, a Python list [12.3] yields a guessed datatype of float64, while a supplied float32 array yields that array's own dtype object.
  • If no dtype can be inferred (for example when _data is None), ValidationError is raised with the message No data type information for variable '{name}'.
Dimensional consistency

ensure_consistency() checks the declared dimensions and data shape of each variable against the template's dimensions, working on the variable-definition objects that already exist: the checks and updates must not replace the supplied variable-definition objects with copies. It expects completeness normalization to have run first (each variable has a _dimensions list). For each variable, the following checks are carried out in order:

  1. Every dimension declared on the variable must exist in the template's dimensions; if it does not, ValidationError is raised with the message Variable '{name}' has undefined dimensions {inconsistent_dims}.
  2. A variable whose _data is None is exempt from the rank and shape checks that remain.
  3. In every other case, the rank of the data array must equal the number of declared dimensions; a mismatch raises ValueError with the message Variable '{name}' has {ndim} dimensions, but value array has {nshape} dimensions. (for example, Variable 'W' has 1 dimensions, but value array has 2 dimensions.).
  4. Each referenced dimension whose size in the template is currently None is then set to the size of the corresponding data axis, and that inferred size persists in the template's dimensions.
  5. If a mismatch still remains between the data shape and the template's dimension sizes, ValueError is raised with the message Variable '{name}' has dimensions {var_dims} and shape {var_shape}, inconsistent with dimension sizes defined in template {template_shape}.

A scalar variable with _dimensions=[] is consistent and requires no template dimensions. A template that is already consistent with its data is left unchanged.

Writing NetCDF files

to_netcdf(outfile, var_args=None, **kwargs) records outfile on the template and then, before opening the output dataset, carries out the following preflight sequence in order:

  1. validation of the current schema of dimensions, variables, and global attributes (as in validate_template_schema());
  2. ensure_completeness();
  3. ensure_consistency().

As a consequence, an incomplete variable (for example one with no _data entry at all) fails with ValidationError before any NetCDF handle is opened, whereas an explicit _data=None still counts as a valid request to create an unassigned variable. Once the preflight has succeeded, the method:

  1. opens outfile in write mode, forwarding kwargs to netCDF4.Dataset;
  2. creates the dimensions in dictionary order;
  3. creates the variables with their declared datatype and dimensions;
  4. writes the _data values that are non-None;
  5. writes variable metadata prefixed with letters;
  6. writes all of the global attributes;
  7. synchronizes and then closes the write handle.

A call that succeeds returns None once this write and reopen sequence has been completed.

The default NetCDF write behavior clobbers existing output. An empty template results in a valid empty NetCDF file. A variable with no dimensions is created as a scalar NetCDF variable. A variable with _data=None is created without explicit assignment, so fill-valued data results where applicable.

For variables that have dimensions, recognized underscore-prefixed creation settings are passed as NetCDF variable-creation options once their leading underscore has been removed. When var_args is supplied, it provides creation options applied to every dimensioned variable and takes precedence over the per-variable options. The kwargs that remain belong to dataset creation, not variable creation. The legacy scalar creation behavior is retained: scalar variables are created from name and datatype, and these per-variable creation options are not forwarded for them.

_FillValue and _fill_value are both aliases for the NetCDF fill_value creation option. If both are supplied with the same value, the write emits a warning and proceeds. If both are supplied with different values, the write raises ValueError. Fill values and masks must round-trip under normal netCDF4 masked-array behavior.

The public operations create_dimensions(), create_variables(**kwargs), and create_global_attributes() keep their behavior of acting on the current ncobj. If a write fails, any output handle that was opened must be closed. When validation fails before file creation, a fresh template is left with ncobj as None. When to_netcdf succeeds, the completed file is reopened in append mode and exposed through template.ncobj; when finished, the caller may close that handle.

Data ranges

DatasetTemplate.get_data_range(varname) returns (minimum, maximum) for the _data attached to the variable, with NumPy scalar result types preserved where applicable. Existing masks and NaN values are left out. As the fill value to exclude, a truthy _FillValue takes precedence; otherwise the method falls back to _fill_value. If neither selected value is truthy, the only exclusions are NaNs and existing masks.

Both scalar and array data are supported. ValueError is raised if the named variable does not exist, or if the data that results is entirely invalid or empty. As an example, data [NaN, 1, 2, 8] has range (1, 8), and a declared fill value that is nonzero is excluded from both extrema.

Creation time

date_created is a datetime property that is read-only and lazily initialized. The value is captured once per instance and is then reused. It must represent the current time in UTC, not local time. The legacy timezone-naive datetime form must be preserved while its fields are given UTC values.

add_date_created_attribute() sets the global attribute date_created from that cached value, in exactly the second-resolution format YYYY-MM-DDTHH:MM:SSZ (%Y-%m-%dT%H:%M:%SZ). The trailing Z thus truthfully denotes UTC. Until this method is called, construction on its own leaves the bundled empty default in place.

Spatial and temporal extents

add_extent_attributes(time_var='TIME', vert_var='DEPTH', lat_var='LATITUDE', lon_var='LONGITUDE') uses get_data_range to compute the selected extents from variable data and returns None:

  • the time range is converted with the time variable's units and its calendar, with the calendar defaulting to gregorian, and is stored as time_coverage_start and time_coverage_end in YYYY-MM-DDTHH:MM:SSZ form;
  • the vertical extrema become geospatial_vertical_min and geospatial_vertical_max;
  • the latitude extrema become geospatial_lat_min and geospatial_lat_max;
  • the longitude extrema become geospatial_lon_min and geospatial_lon_max.

When None or another value that is false is passed for a coordinate argument, that coordinate is skipped and its attributes are left unchanged. Skipping all four coordinates therefore preserves the initial empty extent values. A time variable that is selected but has no units raises ValueError. Variables that are missing, and selected variables with no valid values, propagate the corresponding range error. The method is explicit; extents and creation time are not calculated automatically when a file is written.

Relocated resources and companion packages

The JSON resources for the template schema and the IMOS global attributes must move together with aodntools.ncwriter, be included in distributable artifacts, and stay discoverable when the relocated package is imported from an installed environment. Their contents, and their runtime meaning, must not change.

The same namespace transformation must be applied to the repository's existing companion package whose former flat name ends in _ncwriter: the final writer component is replaced by the two-level _aodntools.ncwriter hierarchy. The relocated parent and its ncwriter child must each be regular packages with package markers, so that modules in that tree can import shared code through the transformed dotted name.

template1.json, template_partial.json, and bad.json must be carried by the relocated companion ncwriter directory. Each resource must be byte-for-byte identical to the counterpart with the same name from before the relocation. In particular, the JSON resource that is intentionally malformed must remain malformed, so that consumers can exercise invalid-JSON behavior.

Package discovery, version metadata paths, package-data declarations, and related namespace references must cover the new hierarchy, and not only the former top-level package.

Compatibility and non-goals

  • aodntools.ncwriter takes the place of the old top-level ncwriter import path; a backward-compatibility alias for the old path is not required.
  • Except for the explicitly required UTC correction, template syntax, accepted datatypes, precedence rules, mutation behavior, warning/error behavior, and generated NetCDF content must not be changed.
  • Features of NetCDF templating that are unrelated must not be added. The task consists of the complete relocation of the existing functionality, and its required resources, under the aodntools namespace.
