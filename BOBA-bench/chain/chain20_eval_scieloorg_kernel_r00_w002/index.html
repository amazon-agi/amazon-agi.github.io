01 Implement DocumentsBundleStore 696 words · rewritten by GPT-5.6-sol

Task Specification: Implement DocumentsBundleStore

Overview

Implement a storage adapter class DocumentsBundleStore that persists and retrieves DocumentsBundle domain objects using a MongoDB-style collection. The adapter wraps a collection supplied at construction and translates collection operations into store-level behavior, including the required domain exceptions.

Modules and Public API

The following importable module paths and public names must exist:

  • documentstore.adapters must expose DocumentsBundleStore.
  • documentstore.domain must expose DocumentsBundle.
  • documentstore.exceptions must expose AlreadyExists and DoesNotExist.

documentstore.domain.DocumentsBundle

DocumentsBundle represents a bundle of documents and provides the domain object consumed and returned by the store.

Construction

The following forms must be supported:

  • DocumentsBundle(id="<some-id>") constructs a bundle from an identifier string.
  • DocumentsBundle(manifest={...}) constructs a bundle from an existing manifest dictionary. The manifest contents are accepted without schema validation and are preserved as supplied.
Attributes and methods
  • .manifest is the dictionary representation of the bundle.
    • For a bundle constructed with id="X", the manifest contains an "id" key whose value is "X"; it may also contain additional keys.
    • For a bundle constructed with an explicit manifest, all supplied keys and values are preserved, including both "_id" and "id" when both are present and even when their values differ.
  • .id() returns the logical bundle identifier from the manifest's "id" field. For example, a bundle constructed with manifest={"_id": "1", "id": "0034-8910-rsp-48-2"} returns "0034-8910-rsp-48-2" from .id(). The storage identifier "_id" does not override this logical identifier.

documentstore.exceptions

  • AlreadyExists is raised when an attempt is made to add a bundle whose storage identifier is already in use.
  • DoesNotExist is raised when a requested bundle cannot be found or an update matches no stored bundle.

documentstore.adapters.DocumentsBundleStore

Construction

DocumentsBundleStore(collection) accepts one MongoDB-style collection object. The store uses that object's insert_one, find_one, and replace_one methods.

Storage identifier preparation

For both add and update, prepare the document from bundle.manifest according to this rule:

  1. If the manifest has a truthy "_id" value, preserve that value unchanged. This remains true when "_id" differs from the logical "id" returned by bundle.id().
  2. If "_id" is absent or its value is falsy, set it to bundle.id().

Thus, manifest={"_id": "1", "id": "0034-8910-rsp-48-2"} is persisted with "_id": "1", while a bundle constructed only with id="0034-8910-rsp-48-2" is persisted with "_id": "0034-8910-rsp-48-2". Other manifest keys and values must remain unchanged.

Method: add(bundle)

Persist a new bundle.

  • Prepare the document using the storage identifier rule above.
  • Call collection.insert_one(document) exactly once with that prepared document.
  • If insert_one raises pymongo.errors.DuplicateKeyError, translate it to documentstore.exceptions.AlreadyExists.

Examples of the document passed to insert_one:

  • A bundle constructed with id="0034-8910-rsp-48-2" has "_id": "0034-8910-rsp-48-2" added to its manifest representation.
  • A bundle constructed with manifest={"_id": "1", "id": "0034-8910-rsp-48-2"} is inserted with "_id": "1"; the existing storage identifier must not be replaced by bundle.id().
Method: fetch(id)

Retrieve a bundle by its storage identifier.

  • Call collection.find_one({"_id": id}) exactly once with the supplied identifier.
  • If find_one returns None, raise documentstore.exceptions.DoesNotExist.
  • Otherwise, return a DocumentsBundle constructed from the returned manifest dictionary. All returned manifest keys and values, including "_id" and "id", must be preserved. The returned bundle's .id() follows the domain rule and therefore reflects the manifest's logical "id" value.

For example, if the collection returns {"_id": "1", "id": "0034-8910-rsp-48-2"}, the resulting bundle has an equal manifest and .id() returns "0034-8910-rsp-48-2".

Method: update(bundle)

Replace an existing stored bundle.

  • Prepare the replacement document using the same storage identifier rule as add.
  • Call collection.replace_one({"_id": document["_id"]}, document) exactly once. The filter and replacement document must use the same prepared storage identifier.
  • If the object returned by replace_one has matched_count == 0, raise documentstore.exceptions.DoesNotExist.

In particular:

  • For a bundle constructed with id="0034-8910-rsp-48-2" and no existing "_id", both the filter and replacement document use "0034-8910-rsp-48-2" as "_id".
  • For manifest={"_id": "1", "id": "0034-8910-rsp-48-2"}, call replace_one with the filter {"_id": "1"} and preserve "_id": "1" in the replacement document.

Collection Contract

The supplied collection provides:

  • insert_one(document), which may raise pymongo.errors.DuplicateKeyError;
  • find_one(filter), which returns a manifest dictionary or None; and
  • replace_one(filter, document), which returns an object with a matched_count attribute.

pymongo is available, and pymongo.errors.DuplicateKeyError must be handled as described above.

02 Refactor the persistence-layer interfaces and MongoDB adapters around one shared storage abstraction, DataStore. 786 words · rewritten by GPT-5.6-sol

Overview

Refactor the persistence-layer interfaces and MongoDB adapters around one shared storage abstraction, DataStore. Document stores and documents-bundle stores must expose the same operations and persistence behavior; the domain class materialized by fetch is their only behavioral difference.

Public Interface (documentstore.interfaces)

Provide an importable abstract base class named DataStore with the following public methods:

class DataStore(abc.ABC):
    @abc.abstractmethod
    def add(self, data): ...

    @abc.abstractmethod
    def update(self, data): ...

    @abc.abstractmethod
    def fetch(self, id): ...

The methods are generic over the stored domain object rather than being specific to documents or bundles. DataStore must be subclassable by concrete in-memory or database-backed stores. A concrete implementation must be able to choose the domain class it materializes from a fetched manifest, for example through a class-level DomainClass attribute.

The formerly separate DocumentStore and DocumentsBundleStore abstract interfaces are consolidated into this one interface; there must not be separate per-domain abstract contracts. Existing session access points for documents and documents bundles continue to represent stores implementing the DataStore contract.

Concrete Adapters (documentstore.adapters)

Provide these two concrete collection-backed classes:

  • documentstore.adapters.DocumentStore
  • documentstore.adapters.DocumentsBundleStore

Each constructor accepts one positional argument, a MongoDB collection-like object:

store = adapters.DocumentStore(collection)
store = adapters.DocumentsBundleStore(collection)

Both adapters must implement the common documentstore.interfaces.DataStore contract and share the same persistence behavior. They differ only in the domain type returned by fetch:

  • DocumentStore materializes documentstore.domain.Document.
  • DocumentsBundleStore materializes documentstore.domain.DocumentsBundle.

The supplied collection is expected to provide insert_one, replace_one, and find_one.

Common Adapter Behavior

The following requirements apply identically to DocumentStore and DocumentsBundleStore.

Storage identifier normalization

For add and update, obtain the dictionary exposed by data.manifest and determine the persisted storage identifier as follows:

  • If manifest.get("_id") is truthy, preserve that value unchanged, even when it differs from data.id().
  • If "_id" is absent or its value is falsy, set manifest["_id"] to data.id().

Thus the MongoDB storage identifier (_id) and the domain object's logical identifier (id, as returned by data.id()) are allowed to differ. Other manifest content must be preserved.

For example, an object created from:

{"_id": "1", "id": "0034-8910-rsp-48-2"}

must continue to use "1" as its storage identifier. By contrast, an object whose manifest has no usable _id must be persisted with _id equal to data.id().

add(data)
  1. Normalize the manifest's storage identifier according to the rule above.
  2. Call collection.insert_one(manifest) with that manifest as the sole positional argument.
  3. If insert_one raises pymongo.errors.DuplicateKeyError, translate it to and raise documentstore.exceptions.AlreadyExists.

In particular, a pre-existing truthy _id must reach insert_one unchanged; it must not be overwritten merely because it differs from data.id().

update(data)

  1. Normalize the manifest's storage identifier according to the rule above.

  2. Call collection.replace_one with exactly these two positional arguments:

    {"_id": manifest["_id"]}, manifest

    The filter and replacement must therefore use the same storage identifier.

  3. Inspect the result returned by replace_one. If result.matched_count == 0, raise documentstore.exceptions.DoesNotExist.

Examples:

  • For a manifest {"_id": "1", "id": "0034-8910-rsp-48-2"}, preserve the divergent _id and call:

    collection.replace_one(
    {"_id": "1"},
    {"_id": "1", "id": "0034-8910-rsp-48-2"},
)

  • For an object created with only id="0034-8910-rsp-48-2", add that value as _id and call replace_one with {"_id": "0034-8910-rsp-48-2"} as the filter and the normalized manifest as the replacement.

fetch(id)

  1. Call collection.find_one({"_id": id}).

  2. If find_one returns a falsy value, including None, raise documentstore.exceptions.DoesNotExist.

  3. Otherwise return an instance of the adapter's domain class, constructed as:

    DomainClass(manifest=found_manifest)

DocumentStore.fetch must return a Document; DocumentsBundleStore.fetch must return a DocumentsBundle. The returned object's manifest must have the same content as the found dictionary, and its existing domain API, including .id(), must continue to operate from that manifest.

Exceptions

Use the existing exception classes from documentstore.exceptions:

  • AlreadyExists for an add rejected because MongoDB reports a duplicate key.
  • DoesNotExist when fetch finds no truthy manifest or when update matches no existing record.

These exception semantics must be uniform across both concrete adapters.

Existing Domain Objects and Compatibility

The adapters must continue to interoperate with the existing documentstore.domain.Document and documentstore.domain.DocumentsBundle classes. Both are constructible with either id="..." or manifest={...} and expose .id() and .manifest. Their manifest and versioning behavior is outside this refactor and must remain unchanged.

All existing non-store APIs remain unaffected. The refactor is limited to consolidating the store interface and making the two collection-backed stores use the uniform behavior specified above.

Constraints

  • There is one shared abstract datastore interface, not separate document and bundle interfaces.
  • Both concrete adapters expose identical add, update, and fetch semantics.
  • The concrete adapters share their storage behavior and vary only by the domain class materialized during fetch.
  • A truthy storage _id already present in a manifest always takes precedence over data.id() for both add and update.
03 Versioned Metadata for BundleManifest 814 words · source specification

Task Specification: Versioned Metadata for BundleManifest

Overview

Modify the metadata storage of bundle manifests in the documentstore.domain module so that metadata values are versioned. Instead of storing a single value per metadata key, store a chronological list of (timestamp, value) pairs, where each entry records a value that was set along with the moment it was set.

Module and Time Source

Work within the module documentstore.domain. The module must reference timestamps through a module-level datetime (the standard library datetime module), obtaining the current UTC time via datetime.utcnow(). Timestamps must be formatted as ISO-8601 strings that include microseconds and a trailing Z, e.g. "2018-08-05T22:33:49.795151Z" (this corresponds to datetime.datetime(2018, 8, 5, 22, 33, 49, 795151)).

BundleManifest.set_metadata

Signature:

BundleManifest.set_metadata(bundle_manifest, name, value, now=<callable>)
  • bundle_manifest is a manifest dict (as produced by the existing bundle-creation logic; it contains at least "metadata", "created", and "updated" keys).
  • name is the metadata key (a string).
  • value is the value to store (a string).
  • now is an optional keyword-only callable that returns the current timestamp string. When not provided, it must default to producing the current UTC time formatted as described above (i.e. based on datetime.utcnow()).

Behavior:

  • It appends the pair (now(), value) to the list stored under bundle_manifest["metadata"][name]. If no entry for name exists yet, the list is created with this pair as its first element.
  • Previously stored pairs for the same name are preserved; setting a new value for an existing key does not overwrite or remove earlier pairs — it appends. The resulting list is in insertion order, oldest first.
  • Setting metadata for a different key adds a new key to the metadata mapping without affecting other keys. The number of keys in metadata reflects the number of distinct names set.
  • Each call updates the manifest's "updated" field to a value strictly greater than its previous value (a later timestamp), reflecting the modification.
  • The function returns the resulting manifest (the tests use the return value; treat this like the other manifest-mutating operations in this codebase, returning the manifest).

Example of the stored structure after two sets of the same key:

{
    "publication_year": [
        ("2018-08-05T22:33:49.795151Z", "2018"),
        ("2018-08-05T22:34:07.795151Z", "2019"),
    ]
}

BundleManifest.get_metadata

Signature:

BundleManifest.get_metadata(bundle_manifest, name, default="")

Behavior:

  • Returns the value (not the pair) of the most recently set entry for name — i.e. the value from the last (timestamp, value) pair in that key's list.
  • If name is not present in the manifest's metadata, returns default.
  • default is an optional keyword argument whose default is the empty string "". When the key is missing and a default is supplied, that supplied value is returned instead.

DocumentsBundle metadata properties

The DocumentsBundle class exposes metadata as attributes: publication_year, volume, number, and supplement. These must continue to work:

  • Assigning to one of these attributes stores the value in the manifest via the versioned set_metadata mechanism, so that documents_bundle.manifest["metadata"][<name>] becomes a list of (timestamp, value) pairs. When the current UTC time is datetime.datetime(2018, 8, 5, 22, 33, 49, 795151), assigning documents_bundle.volume = "25" yields:

    documents_bundle.manifest["metadata"]["volume"] == [("2018-08-05T22:33:49.795151Z", "25")]

  • Reading one of these attributes returns the latest stored value (via get_metadata), as a string. Existing value-normalization behavior (e.g. converting assigned values to strings) must be preserved.

Impact on services (fetch/update documents bundle)

The service-layer commands that fetch and update bundle metadata must reflect the new storage format, since they operate on manifests:

  • Creating a bundle with a metadata mapping and then fetching it yields a "metadata" dict where each recognized key maps to a list of (timestamp, value) pairs. With the current UTC time mocked to datetime.datetime(2018, 8, 5, 22, 33, 49, 795151):

    {
    "publication_year": [("2018-08-05T22:33:49.795151Z", "2018")],
    "volume": [("2018-08-05T22:33:49.795151Z", "2")],
}

  • Unknown/unrecognized metadata keys supplied at creation are ignored and never appear in the stored metadata.

  • Updating a bundle's metadata with a new value for an existing recognized key appends a new (timestamp, value) pair to that key's list rather than replacing the prior history. For example, creating with publication_year="2018", volume="2" and then updating with publication_year="2019" yields:

    {
    "publication_year": [
        ("2018-08-05T22:33:49.795151Z", "2018"),
        ("2018-08-05T22:33:49.795151Z", "2019"),
    ],
    "volume": [("2018-08-05T22:33:49.795151Z", "2")],
}

  • Updating with an unrecognized key leaves the stored metadata unchanged.

  • Setting a recognized key to an empty string is a valid update: it appends a (timestamp, "") pair. For example, after creating with publication_year="2018", volume="2" and updating with volume="":

    {
    "publication_year": [("2018-08-05T22:33:49.795151Z", "2018")],
    "volume": [
        ("2018-08-05T22:33:49.795151Z", "2"),
        ("2018-08-05T22:33:49.795151Z", ""),
    ],
}

Notes

  • All existing manifest behaviors not mentioned here (manifest generation on init, created/updated fields being equal at creation, item-management operations, string conversion of assigned metadata values) must remain intact.
  • Timestamps are produced through the module-level datetime reference so that the current UTC time can be controlled externally; ensure the current-time source flows through datetime.utcnow().

Required public API

Expose the following classes from documentstore.domain:

  • domain.Journal(id: str)
  • domain.DocumentsBundle(id: str)

They must also be usable through this import style:

from documentstore import domain

Each class must expose a dictionary-valued manifest. For an instance newly created from an identifier, manifest must contain a dictionary at manifest["metadata"].

Timestamped metadata convention

Except for Journal.mission, every property introduced below uses the bundle metadata-history convention:

  • If the property's metadata has not been set, reading the property returns the empty string "".
  • Assigning a value stores it under the property's exact name in manifest["metadata"] without transforming the value.
  • A metadata history is a list of (timestamp, value) tuples in assignment order. The first assignment therefore creates a one-element list, and later assignments append rather than replacing earlier values.
  • Reading a property with a nonempty history returns its latest assigned value.
  • The timestamp is the current UTC time in ISO 8601 form with a trailing Z. For example, a current UTC time of 2018-08-05 22:33:49.795151 is represented as "2018-08-05T22:33:49.795151Z".

Thus, after a first assignment, an entry has this shape:

instance.manifest["metadata"][property_name] == [
    ("2018-08-05T22:33:49.795151Z", assigned_value)
]

#      {"status": "CEASED"},
#    ]

The timestamps [item[0] for item in journal.status_history] are in sorted (ascending) order.

4. Removal of the previous_journal property

The Journal class must no longer provide a previous_journal property. Any prior getter/setter for previous_journal should be removed.

Notes on existing behavior that must be preserved
  • Journal.subject_categories remains a settable property. When assigned an iterable of values, it stores the resulting list of values (as strings) as a single timestamped metadata entry under "subject_categories", accessible at journal.manifest["metadata"]["subject_categories"] as [(timestamp, [...values...])].
  • The other unchanged domain properties (e.g. institution_responsible_for, online_submission_url, created/updated timestamps, etc.) retain their current behavior.
