Task Description

Summary

Alter the HTTP request layer in pynetbox.core.query so that routine GET, POST, PUT, and DELETE requests are dispatched through an instance of requests.sessions.Session instead of the matching module-level convenience functions.

This change affects transport dispatch only. The existing public APIs, request construction, response handling, and return values must remain compatible. The single explicit exception is API-version discovery: the request issued for Api.version must continue to use module-level requests.get.

Behavior Requirements

1. Dispatch ordinary requests via requests.sessions.Session

For each request that is in scope, use a requests.sessions.Session instance and invoke the bound method that corresponds to the HTTP verb:

  • Session.get for ordinary endpoint reads
  • Session.post for ordinary creates and for session-key acquisition
  • Session.put for operations that use PUT
  • Session.delete for delete operations

Throughout pynetbox.core.query, this routing applies no matter which public operation caused the request. Where applicable, it includes:

  • Fetching a single object with .get()
  • Fetching endpoint collections with .all()
  • Filtering endpoints, including filter values that are repeated and encoded
  • Traversing paginated responses
  • Loading the full details of related or nested records
  • Fetching application choices
  • Reading detail endpoints (such as NAPALM data, rack units, available IPs, and available prefixes)
  • Creating a single object or bulk objects
  • Creating objects by way of writable detail endpoints
  • Modification operations based on PUT
  • Removing records
  • Obtaining a secrets session key during API initialization

Aside from the API-version discovery described below, these flows must not route their GET, POST, PUT, or DELETE calls through requests.get, requests.post, requests.put, or requests.delete. Simply depending on a module-level convenience function that creates its own session internally does not satisfy this requirement; the method on a Session instance must be invoked by the query layer.

2. Retain the module-level API-version request

Api.version, handled through Request.get_version(), is a compatibility exception to session routing. Its HTTP request must still be issued through the top-level requests.get entry point, and requests.sessions.Session.get must not be used for it. Instrumenting or replacing module-level requests.get must therefore continue to intercept version discovery.

The remainder of the version lookup behavior is unchanged:

  • It sends a GET to the normalized API base URL, with its trailing slash included.
  • It sends the existing Content-Type: application/json; header together with the configured ssl_verify value.
  • When the response is successful, it returns the API-Version response header.
  • When that header is absent, it returns the empty string.
  • A response that is unsuccessful continues to raise RequestError.

This exception applies to API-version discovery only. It does not allow normal endpoint GET requests to use the module-level function.

3. Retain exact request construction

Switching the dispatch entry point must not alter any argument supplied to the HTTP operation. In particular, preserve:

  • The URL given as the request's positional URL argument
  • The trailing-slash normalization already in place
  • Endpoint-name conversion, object IDs, detail-route suffixes, filter encoding, repeated list filters, and pagination URLs
  • The request headers already in use, including content type, accept header, token authorization, and conditional handling of X-Session-Key
  • The form encoding already used for session-key acquisition
  • The JSON serialization already used for POST and PUT bodies
  • The configured ssl_verify value, whether that value is True, False, or a path to a certificate bundle
  • The existing usage of positional versus keyword arguments

To give an example, a normal endpoint read must still pass the same URL, headers, and verify arguments as before; the only change is that the callable receiving those arguments becomes a session instance's get method instead of module-level requests.get. POST, PUT, and DELETE follow the same rule.

4. Retain response and error semantics

The move to a session must not change how responses are processed. Preserve all existing behavior for:

  • Decoding JSON and converting it into records or raw detail-endpoint data
  • Return types for single objects and for lists
  • The results of bulk creates
  • Automatic pagination and the aggregation of results
  • Serialization, comparison, idempotence, save/update behavior, and the results of deletions
  • The conditions and contents of RequestError, ContentError, and AllocationError
  • Authentication and session-key behavior

This task introduces no new public methods, parameters, return types, or state-management requirements. For HTTP verbs outside the four named in this task, the existing dispatch behavior must be retained.

5. Keep the dispatch points reachable from outside

The session class used must be the standard requests.sessions.Session class, reached via the requests module that pynetbox.core.query imports. Instrumenting or replacing pynetbox.core.query.requests.sessions.Session.get, .post, .put, or .delete must intercept the corresponding ordinary query-layer operation and observe the original call arguments without an extra explicitly supplied session argument.

Conversely, instrumenting or replacing top-level requests.get must continue to intercept the GET performed by API-version discovery.

Non-goals

  • Do not redesign the public interfaces of Api, App, Endpoint, Record, or Request.
  • Do not modify URLs, headers, bodies, SSL verification, pagination, filtering, serialization, or error handling.
  • Do not move API-version discovery onto a session.
  • Do not alter dispatch behavior for HTTP verbs outside GET, POST, PUT, and DELETE.

03 Request Construction via the HTTP Client's params and json 946 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Request Construction via the HTTP Client's params and json

Background

At the moment, the HTTP request layer in this library puts together URL query strings itself (it appends ?key=value to the URL), and it serializes request bodies itself before they are handed to the underlying HTTP session. A change is required here: query parameters and JSON bodies must be delegated to the underlying HTTP client (a requests-style session), using that client's params and json keyword arguments.

Behavior Requirements

Every HTTP call that travels through the request layer (GET, POST, etc., invoked as methods on the session object, e.g. http_session.get(...), http_session.post(...)) must follow the keyword-argument contract set out below:

URL query parameters
  • The HTTP session methods must not be given URLs that contain any query string. The URL must be the bare endpoint path, and it must end in / (no ?... suffix).
  • Instead, a params= keyword argument must receive a dictionary containing all query parameters.
  • When the request has no query parameters, the value given for params must be the empty dictionary {} (it must not be left out, and it must not be None).
  • Parameter values are not altered on the way through and keep their native Python types. Concretely:
    • Values that are strings are still strings afterwards, e.g. params={"name": "test"}.
    • Values that are integers are still integers afterwards, e.g. params={"limit": 221, "offset": 50}.
    • When a filter is given multiple values, those values must be represented as a list, e.g. params={'role': ['test', 'test1'], 'site': 'TEST#1'}. This layer performs no URL-encoding (e.g. # is not escaped here — escaping is left to the HTTP client).
JSON request body
  • A json= keyword argument must accompany every call made to a session HTTP method.
  • If the request carries no body (e.g. GET / list / count operations), the argument passed must be json=None.
  • If the request submits a payload (e.g. create operations), then rather than being pre-serialized and passed under a data= argument, the payload dictionary must go directly into the json= argument (i.e. json=<payload_dict>). What must be passed is the original Python object supplied by the caller, with no changes.
Remaining keyword arguments
  • For headers and verify, the behavior that exists today is preserved, and they are passed the way they always were.
    • On read/list-type requests, what headers carries is the accept header (together with the authorization header when a token is configured).
    • On create/post-type requests, what headers carries is the content-type header (together with the authorization header when a token is configured).
    • verify keeps getting passed too (e.g. verify=True).

The count operation

As far as its result goes, the count operation keeps working as it did before: a request is sent with a limit of 1 merged together with any filters that were supplied, and the integer count value from the response is what it returns. Under the new contract:

  • What serves as the URL is the bare endpoint path, without any query string.
  • params is what carries the limit=1 value and any filters, in their native types, e.g. params={"q": "abcd", "limit": 1} if a filter is present, or params={"limit": 1} if no filters are present.

Token authentication

Once the API client has been constructed with a token, the authorization header that outgoing requests carry must reflect that token, written as Token <token>. To illustrate: if the client is constructed with token="abc123", the requests that result carry authorization: Token abc123 in their headers (together with the appropriate accept or content-type header).

Public API Surface (importability and callability must be preserved)

Each import path and name below must continue to exist and must behave in the way described:

  • pynetbox.api(url, token=None) — the factory that produces the top-level API client. It accepts a base URL together with an optional token keyword argument. Application attributes such as .dcim, .ipam, .tenancy, .virtualization, .circuits are exposed on it.

  • Endpoint attributes are exposed on application objects (e.g. nb.devices, nb.interfaces, nb.racks, nb.prefixes, etc.), and these support:

    • .list() and .list(**filters) — a list of record objects is returned.
    • .get(id) — a single record object is returned.
    • .filter(**filters) — a list of record objects is returned. ValueError must be raised if filter is called with no arguments.
    • .create(payload) — a create request is submitted, with the payload passed through to serve as the JSON body.

  • Related sub-endpoints are exposed on record objects (e.g. record.units, record.available_ips, record.available_prefixes, record.napalm); these support .list(...) and, where applicable, .create(...).

  • pynetbox.core.query.Request — the class in which requests are built.

    • An http_session attribute exists on instances; the HTTP methods of that attribute are invoked with the params / json / headers / verify keyword contract laid out above.
    • The get_count() method performs a count request (with limit=1 merged into params) and returns the integer count from the response.

  • pynetbox.core.query.Request._make_call — the internal method that carries out a call (it acts as a patch point).

  • pynetbox.core.endpoint.Endpoint — the endpoint class.

    • The signature of its constructor is Endpoint(api, app, name).
    • When .filter(**filters) is called with no filters, ValueError is raised.

What the change does

Take query-string and body construction out of the URL/data string handling, and put it into the HTTP client's native params= and json= keyword arguments. These three things must be passed by every session HTTP call: a bare (query-less) URL; a params dict (empty when no parameters exist, with values kept as native Python types — lists included for multi-valued filters); and a json argument (None for requests without a body, or the raw payload object for create requests).

Task Specification: Correct URL Resolution for Write Operations on Nested Records

Background

This task deals with a Record class that models a data record returned from a REST API. Record objects are built from dictionaries, and any dictionary values nested inside are themselves turned into nested Record instances. Each Record comes with write operations (for instance save()) that issue HTTP requests to the API.

The Problem to Solve

When a nested Record (that is, a Record created from a dictionary value inside a parent record's data) carries out a write operation, the operation must target the record's own API endpoint URL — derived from its own data — rather than the URL of its parent record.

Required Behavior

Constructing a Record

The Record class is constructed via this call:

Record(data, app, endpoint)

  • app: an object that exposes:
    • app.token: a token used for authentication.
    • app.http_session: an HTTP session object; write requests are performed through its methods (e.g. patch).
  • endpoint: an object that has a name attribute.

The field values in data can be reached as attributes on the Record (e.g. record.name, record.id), and they can be assigned to (e.g. record.name = 'new value').

URL resolution when a nested record calls save()

When a Record has been built from a nested dictionary that contains a url field, calling save() on that nested record must send the write request to a URL taken from that nested record's own url value — not from the parent record's endpoint or URL.

Concretely, when save() is invoked on a nested record and the modified field(s) result in an update request:

  • The HTTP write must be sent through the update method of app.http_session (patch).
  • The value passed to that method as its first positional argument must be the nested record's own url value with a single trailing slash appended.

For example, take a parent record containing a child dictionary with url equal to "http://localhost:8080/test"; modifying a field on the child and calling save() on the child must issue the request to:

http://localhost:8080/test/

(A trailing slash is appended to the record's url value; the value had no trailing slash to begin with.)

Public API

  • The module must expose a Record class that is importable and callable as Record(data, app, endpoint).
  • Record instances must support attribute-style access for reading and writing their fields.
  • Fields holding nested dictionaries must be accessible as nested Record instances.
  • Record must provide a save() method that carries out an HTTP update via app.http_session.patch, with the endpoint address derived from the record's own url as described above.

Background

Your work takes place with a Record class located at pynetbox/core/response.py (it can be imported as from pynetbox.core.response import Record). A Record models an object returned by an API, and it is initialized from a dictionary of values.

The constructor of Record has the following signature:

Record(values, api, endpoint)

where values is a dict of field data, and api and endpoint may be None.

A Record has the following capabilities:

  • Attribute access and assignment are available for the fields it was initialized with (e.g. record.some_field = new_value).
  • A _diff() method that returns the set of field names for which the current values differ from the values the record was originally initialized with. If nothing has changed, _diff() returns an empty (falsy) set.
Required Modification

Some of the fields the API returns are "choice" fields, represented as nested dictionaries instead of scalar values. These choice dictionaries differ in structure from one API version to another, but they have one trait in common: each contains a value key.

The following three shapes must be supported:

  1. A dict that has value and label keys, e.g.:

    {"value": 1, "label": "test"}

  2. A dict that has value, label, and id keys, e.g.:

    {"value": "test", "label": "test", "id": 1}

  3. A dict that has value and label keys with a string value, e.g.:

    {"value": "test", "label": "test"}

If the initial value of a field is a dictionary that contains both a value key and could be interpreted as a choice field, the record must treat the effective scalar value of that field as the contents of the value key.

Specifically, the behavior that is required is diff idempotence for choice fields:

  • a record is initialized with a field whose value is a choice dict (any of the three shapes above),
  • that same field is assigned the scalar contained in the dict's value key,
  • and this must result in _diff() reporting no difference for that field (i.e. the record is considered unchanged).

In concrete terms:

  • With an initial field value of {"value": 1, "label": "test"}, assigning the scalar 1 must produce no diff.
  • With an initial field value of {"value": "test", "label": "test", "id": 1}, assigning the scalar "test" must produce no diff.
  • With an initial field value of {"value": "test", "label": "test"}, assigning the scalar "test" must produce no diff.

Put another way: a choice dict whose value key holds scalar X must be considered equivalent to the plain scalar X for the purposes of diff comparison. The presence of a value key is the distinguishing factor for recognizing a choice field (in the shapes shown, alongside a label key, optionally with an id key).

Take particular note of the second shape: although it contains an id key (which might indicate a nested related object in other contexts), the presence of the value key means it must serialize to its value ("test") rather than be treated as a nested record.

Behavior to Preserve

The behavior that already exists must remain intact:

  • When a Record initialized from a dict of plain scalar values is converted with dict(record), it yields back an equivalent dict.
  • Records support hashing and equality that are based on their id and endpoint.

This task imposes no requirement to support saving or writing nested child records.

While a record is being converted to a dictionary, probing the special keys attribute must not set off network hydration.

Hashing and Equality

Records are hashable, and comparison between them rests on API identity:

  • A record's identity key consists of its endpoint name together with its id in cases where an ID is present; with no ID, the endpoint name by itself is the key.
  • An integer is what hash(record) returns.
  • Two Record instances sharing the same endpoint name and ID compare equal, with equal hashes as well — even if they are distinct Python objects or came from different responses.
  • Different IDs mean records compare unequal and produce different hashes; different endpoint names make records distinct in the same way.

This equality behavior must let ordinary membership operations work across representations that were loaded separately. By way of example: when their endpoint names and IDs match, a VLAN loaded from the VLAN endpoint must compare equal to the corresponding VLAN object sitting in an interface's tagged_vlans list.

  • Scalar fields are emitted as-is; this deduplication is what imposes Aftertee.
