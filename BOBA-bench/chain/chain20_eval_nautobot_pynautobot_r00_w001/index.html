Overview

Modify the HTTP request layer in pynetbox.core.query so that ordinary GET, POST, PUT, and DELETE requests are dispatched through an instance of requests.sessions.Session instead of the corresponding module-level convenience functions.

This is a transport-dispatch change only. Existing public APIs, request construction, response handling, and return values must remain compatible. API-version discovery is the one explicit exception: the request made for Api.version must continue to use module-level requests.get.

Required behavior

1. Route ordinary requests through requests.sessions.Session

For each in-scope request, use a requests.sessions.Session instance and invoke its bound method matching the HTTP verb:

  • Session.get for normal endpoint reads
  • Session.post for normal creates and session-key acquisition
  • Session.put for PUT operations
  • Session.delete for deletes

This routing applies throughout pynetbox.core.query, regardless of the public operation that caused the request. It includes, where applicable:

  • Retrieving one object with .get()
  • Retrieving endpoint collections with .all()
  • Filtering endpoints, including repeated and encoded filter values
  • Following paginated responses
  • Loading full details for related or nested records
  • Reading application choices
  • Reading detail endpoints such as NAPALM data, rack units, available IPs, and available prefixes
  • Creating one object or bulk objects
  • Creating objects through writable detail endpoints
  • PUT-based modification operations
  • Deleting records
  • Acquiring a secrets session key during API initialization

Except for API-version discovery described below, these flows must not dispatch their GET, POST, PUT, or DELETE calls through requests.get, requests.post, requests.put, or requests.delete. Merely relying on a module-level convenience function that internally creates its own session does not satisfy this requirement; the query layer must invoke the method on a Session instance.

2. Preserve the module-level API-version request

Api.version, through Request.get_version(), is a compatibility exception to session routing. Its HTTP request must continue to be issued through the top-level requests.get entry point and must not use requests.sessions.Session.get. Replacing or instrumenting module-level requests.get must therefore continue to intercept version discovery.

The rest of the version lookup behavior is unchanged:

  • It sends a GET to the normalized API base URL, including its trailing slash.
  • It sends the existing Content-Type: application/json; header and configured ssl_verify value.
  • On a successful response, it returns the API-Version response header.
  • If that header is absent, it returns the empty string.
  • An unsuccessful response continues to raise RequestError.

This exception applies only to API-version discovery. It does not permit normal endpoint GET requests to use the module-level function.

3. Preserve exact request construction

Changing the dispatch entry point must not alter any argument supplied to the HTTP operation. In particular, preserve:

  • The URL passed as the request's positional URL argument
  • Existing trailing-slash normalization
  • Endpoint-name conversion, object IDs, detail-route suffixes, filter encoding, repeated list filters, and pagination URLs
  • Existing request headers, including content type, accept header, token authorization, and conditional X-Session-Key handling
  • Existing form encoding for session-key acquisition
  • Existing JSON serialization for POST and PUT bodies
  • The configured ssl_verify value, whether it is True, False, or a certificate-bundle path
  • Existing positional-versus-keyword argument usage

For example, a normal endpoint read must still pass the same URL, headers, and verify arguments as before; only the callable receiving those arguments changes from module-level requests.get to a session instance's get method. The same rule applies to POST, PUT, and DELETE.

4. Preserve response and error semantics

The session migration must not change how responses are processed. Preserve all existing behavior for:

  • JSON decoding and conversion into records or raw detail-endpoint data
  • Single-object and list return types
  • Bulk-create results
  • Automatic pagination and aggregation of results
  • Serialization, comparison, idempotence, save/update behavior, and deletion results
  • RequestError, ContentError, and AllocationError conditions and contents
  • Authentication/session-key behavior

No new public methods, parameters, return types, or state-management requirements are introduced. HTTP verbs outside the four named in this task must retain their existing dispatch behavior.

5. Keep the dispatch points externally reachable

The session class must be the standard requests.sessions.Session class, reached through the requests module imported by pynetbox.core.query. Replacing or instrumenting pynetbox.core.query.requests.sessions.Session.get, .post, .put, or .delete must intercept the corresponding ordinary query-layer operation and observe the original call arguments without an extra explicitly supplied session argument.

Conversely, replacing or instrumenting top-level requests.get must continue to intercept the GET performed by API-version discovery.

Non-goals

  • Do not redesign the Api, App, Endpoint, Record, or Request public interfaces.
  • Do not change URLs, headers, bodies, SSL verification, pagination, filtering, serialization, or error handling.
  • Do not migrate API-version discovery to a session.
  • Do not change dispatch behavior for HTTP verbs outside GET, POST, PUT, and DELETE.

Task Specification: Use HTTP Client params and json for Request Construction

Overview

The HTTP request layer of this library currently builds URL query strings manually (appending ?key=value to the URL) and serializes request bodies manually before passing them to the underlying HTTP session. This must be changed so that query parameters and JSON bodies are delegated to the underlying HTTP client (a requests-style session) via its params and json keyword arguments.

Required Behavior

All HTTP calls made through the request layer (GET, POST, etc., invoked as methods on the session object, e.g. http_session.get(...), http_session.post(...)) must be invoked with the following keyword-argument contract:

Query parameters
  • URLs passed to the HTTP session methods must not contain any query string. The URL must be the bare endpoint path ending in / (no ?... suffix).
  • All query parameters must instead be passed as a dictionary via a params= keyword argument.
  • When there are no query parameters, params must be passed as an empty dictionary {} (not omitted, not None).
  • Parameter values are passed through unchanged in their native Python types. Specifically:
    • String values remain strings, e.g. params={"name": "test"}.
    • Integer values remain integers, e.g. params={"limit": 221, "offset": 50}.
    • A filter supplied with multiple values must be represented as a list of those values, e.g. params={'role': ['test', 'test1'], 'site': 'TEST#1'}. No URL-encoding is applied by this layer (e.g. # is not escaped here — it is left to the HTTP client).
JSON body
  • Every call to a session HTTP method must include a json= keyword argument.
  • For requests without a body (e.g. GET / list / count operations), json=None must be passed.
  • For requests that submit a payload (e.g. create operations), the payload dictionary must be passed directly as the json= argument (i.e. json=<payload_dict>), rather than being pre-serialized and passed under a data= argument. The value passed must be the original Python object supplied by the caller, unchanged.
Other keyword arguments
  • Existing behavior for headers and verify is preserved and passed as before.
    • For read/list-type requests, headers carries the accept header (and authorization header when a token is configured).
    • For create/post-type requests, headers carries the content-type header (and authorization header when a token is configured).
    • verify continues to be passed (e.g. verify=True).

Count operation

The count operation continues to work as before in terms of its result: it issues a request with a limit of 1 merged with any supplied filters, and returns the integer count value from the response. With the new contract:

  • The URL is the bare endpoint path with no query string.
  • The limit=1 value and any filters are passed via params as native types, e.g. params={"q": "abcd", "limit": 1} when a filter is present, or params={"limit": 1} when no filters are present.

Authentication token

When the API client is constructed with a token, that token must be reflected in the authorization header of outgoing requests as Token <token>. For example, constructing the client with token="abc123" results in requests carrying authorization: Token abc123 in their headers (alongside the appropriate accept or content-type header).

Public API Surface (must remain importable and callable)

The following import paths and names must continue to exist and behave as described:

  • pynetbox.api(url, token=None) — top-level API client factory. Accepts a base URL and an optional token keyword argument. Exposes application attributes such as .dcim, .ipam, .tenancy, .virtualization, .circuits.

  • Application objects expose endpoint attributes (e.g. nb.devices, nb.interfaces, nb.racks, nb.prefixes, etc.) supporting:

    • .list() and .list(**filters) — returns a list of record objects.
    • .get(id) — returns a single record object.
    • .filter(**filters) — returns a list of record objects. Calling filter with no arguments must raise ValueError.
    • .create(payload) — submits a create request whose payload is passed through as the JSON body.

  • Record objects expose related sub-endpoints (e.g. record.units, record.available_ips, record.available_prefixes, record.napalm) supporting .list(...) and, where applicable, .create(...).

  • pynetbox.core.query.Request — the request-building class.

    • Instances have an http_session attribute whose HTTP methods are invoked with the params / json / headers / verify keyword contract described above.
    • get_count() method — issues a count request (with limit=1 merged into params) and returns the integer count from the response.

  • pynetbox.core.query.Request._make_call — internal call method (used as a patch point).

  • pynetbox.core.endpoint.Endpoint — endpoint class.

    • Constructor signature: Endpoint(api, app, name).
    • .filter(**filters) raises ValueError when called with no filters.

Summary of the change

Move query-string and body construction out of the URL/data string handling and into the HTTP client's native params= and json= keyword arguments. Every session HTTP call must pass a bare (query-less) URL, a params dict (empty when there are no parameters, with values kept as native Python types including lists for multi-valued filters), and a json argument (None for bodyless requests, or the raw payload object for create requests).

Background

This is incorrect. A nested record that carries its own url value must use that url when performing write operations.

Required Behavior

Given a Record constructed as:

Record(data, api, endpoint)

  • Accessing the nested field returns a Record representing the nested object.
