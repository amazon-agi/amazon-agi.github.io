Module Under Change

The module cloudregister.registerutils (imported in code as utils) must expose the functions described below. Two functions are exercised: has_rmt_in_hosts and clean_hosts_file.

Function 1: has_rmt_in_hosts(server)

Signature
def has_rmt_in_hosts(server):
Behavior

Determines whether the system hosts file (/etc/hosts) already contains an entry for the given server's IP address (IPv4 or IPv6).

The server argument is an object exposing two methods:

  • server.get_ipv4() → returns the server's IPv4 address as a string (e.g. '1.1.1.1').
  • server.get_ipv6() → returns the server's IPv6 address as a string (e.g. '11:22:33:44::00').

The function reads the hosts file content and returns:

  • True if the file contains a line beginning with (or containing as its address field) the server's IPv4 address.
  • True if the file contains a line containing the server's IPv6 address.
  • True if either address is present when both are checked.
  • False if neither the IPv4 nor the IPv6 address of the server appears in the file.

Address matching must be exact against the address token present in the hosts file. For example, if the server's IPv6 is 11:22:33:44::00, a file line whose address is 22:22:33:44::00 does not count as a match (returns False), whereas a line whose address is 11:22:33:44::00 counts as a match (returns True).

The hosts file lines are structured as an address followed by whitespace and one or more hostnames, e.g.:

1.1.1.1   smt-foo.susecloud.net  smt-foo
11:22:33:44::00   smt-foo.susecloud.net  smt-foo

Function 2: clean_hosts_file(hostname)

Signature
def clean_hosts_file(hostname):
Behavior

Removes the entry (and its associated marker comment) that was previously added to the hosts file for the given hostname, then rewrites the file. The hostname argument is a bytes value (e.g. b'smt-entry').

The hosts file is read as bytes and rewritten as bytes (the file is opened in binary mode; each written line is a bytes object).

What must be removed

The hosts file may contain a block that was inserted by this tooling, consisting of:

  1. A marker comment line:
    # Added by SMT, please, do NOT remove this line
  2. The following entry line, which is the line whose hostname field matches the provided hostname (e.g. a line such as 2.3.4.5 smt-entry.susecloud.net smt-entry matches b'smt-entry').

Both the marker comment line and the matching entry line must be removed from the file. All other lines are preserved in their original order and content.

Trailing-line normalization (the core fix)

After removing the marker comment and the matching entry, the rewritten file must have exactly one trailing empty line, regardless of how many empty lines existed at the bottom of the original file (zero, one, or several). Specifically:

  • If the original file ended with no trailing newline / no empty bottom lines, the output must still end with a single trailing newline.
  • If the original file ended with one or multiple empty bottom lines, the output must be collapsed to a single trailing empty line.

The function must never wipe out or truncate the file's meaningful content when the bottom of the file has zero or one empty lines. The result is always the preserved content followed by exactly one trailing newline.

Output format (how the file is written)

The file is rewritten line-by-line. The exact sequence of writes must be:

  1. For every resulting content line except the last, write that line's text with a trailing newline (b'\n') appended.
  2. If the last resulting line is non-empty, write it (without an appended newline in this step).
  3. Finally, write a single b'\n'.

Concretely, given the cleaned content (with the marker comment and matching entry removed), split it into lines on newline boundaries. Emit each line except the final split element as line + b'\n'; if the final split element is non-empty, emit it as-is; then always emit a final b'\n'. This guarantees exactly one trailing newline at the end of the file.

Worked example

Original content:


# simulates hosts file containing the ipv6 we are looking for in the test

1.2.3.4   smt-foo.susecloud.net  smt-foo

# Added by SMT, please, do NOT remove this line
2.3.4.5   smt-entry.susecloud.net smt-entry

4.3.2.1   another_entry.whatever.com another_entry

Call: clean_hosts_file(b'smt-entry')

Resulting file content:


# simulates hosts file containing the ipv6 we are looking for in the test

1.2.3.4   smt-foo.susecloud.net  smt-foo


4.3.2.1   another_entry.whatever.com another_entry

Note that the marker comment line and the smt-entry line are removed (leaving the blank line that had preceded the marker in place), and the multiple blank lines at the very bottom are collapsed to a single trailing newline.

The same trailing normalization applies when the marker comment + matching entry are the last meaningful block in the file (whether followed by zero, one, or several empty lines): after their removal, the preceding content is preserved and the file ends with exactly one trailing newline.

Constraints

  • clean_hosts_file reads and writes the hosts file in binary mode; all line data written are bytes.
  • Do not add trailing content beyond the single final newline described above.
  • Preserve all non-removed lines exactly, including comment lines and blank lines that appear between other content lines.

Overview

Modify the SMT class to precompute and expose a mapping of health-check URLs to their corresponding fallback base URLs, supporting both IPv4 and IPv6 addresses.

API Surface

The SMT class is constructed from an XML element (as produced by lxml.etree.fromstring). The relevant attributes on the XML element include the server's IPv4 address (SMTserverIP) and IPv6 address (SMTserverIPv6); either or both may be present.

Required Behavior

The SMT instance must expose a public attribute:

smt._check_urls

This attribute is a dictionary (dict-like object supporting .get(key)). It maps a fully-qualified HTTPS health-status URL to a corresponding plain HTTP base URL, for each IP address the server advertises.

Key / value format

For each advertised IP address, the dictionary contains one entry:

  • Key: https://<host>/api/health/status
  • Value: http://<host>/

where <host> is:

  • The bare IPv4 address for an IPv4 entry (e.g. 192.168.1.1).
  • The IPv6 address enclosed in square brackets for an IPv6 entry (e.g. [fc00::1]).
Coverage per configuration
  • When only an IPv4 address is present, the dictionary contains exactly the IPv4 entry:
    • https://192.168.1.1/api/health/status → http://192.168.1.1/
  • When only an IPv6 address is present, the dictionary contains exactly the IPv6 entry:
    • https://[fc00::1]/api/health/status → http://[fc00::1]/
  • When both an IPv4 and IPv6 address are present, the dictionary contains both entries:
    • https://192.168.1.1/api/health/status → http://192.168.1.1/
    • https://[fc00::1]/api/health/status → http://[fc00::1]/

The _check_urls attribute must be available immediately after the SMT object is constructed.

Existing Behavior To Preserve

The clean_hosts_file(smt_entry) function in the utilities module (utils) must retain its current behavior. Given the byte content of a hosts file and a byte string identifying an SMT entry, it rewrites the hosts file with the matching entry removed while collapsing trailing empty lines, such that the resulting output ends with exactly one trailing newline. Each line of the cleaned content is written back (as bytes, with its terminating newline) followed by a final newline write. No behavioral change to this function is required beyond ensuring it continues to work as described.
