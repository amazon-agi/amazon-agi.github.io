01 The codebase you will be modifying is the picterra Python package, a client library for the Picterra REST API. 658 words · source specification, reworded by GLM-5.3-Flash

Task Description

Background

The codebase you will be modifying is the picterra Python package, a client library for the Picterra REST API. The assignment comes down to two actions: adding a new method to the API client, and removing an existing method plus the command-line interface that belongs to it.

Public API Surface

To get the client class, APIClient, you import it directly from the package:

from picterra import APIClient

Configuration happens through environment variables. Specifically, the environment variable PICTERRA_BASE_URL supplies the base API URL, while authentication of requests happens through an X-Api-Key HTTP header. Every API endpoint is the result of joining paths onto the base URL.

Required Change 1: Add run_advanced_tool

You must add the following new public method to APIClient:

def run_advanced_tool(self, tool_id, inputs, outputs):
    ...
What the method has to do

When invoked, run_advanced_tool has to do the following:

  1. Make an HTTP POST request against the API endpoint whose relative path is:

    advanced_tools/{tool_id}/run/

    with {tool_id} standing for the method's first argument. Attaching the standard X-Api-Key authentication header to this request is required.

  2. Exactly the following JSON has to form the body of this POST request:

    {
  "inputs": <inputs>,
  "outputs": <outputs>
}

    Here <inputs> stands for the inputs argument and <outputs> for the outputs argument, included verbatim. In terms of content, the two arguments are arbitrary JSON-serializable structures (dicts containing nested dicts, lists, strings, integers, and null/None values), and they must be forwarded without modification.

    What the endpoint sends back is HTTP 201 together with a JSON object of this form:

    {
  "operation_id": <int>,
  "poll_interval": <float>
}

  3. Once the operation has been started, the method must poll the operation until it completes. Polling here means sending GET requests to:

    operations/{operation_id}/

    with the operation_id taken from the run response. Every response to a poll is a JSON object that has at least a status field and a type field. The polling keeps going — with the returned poll_interval respected as the interval between checks — until the operation arrives at a successful terminal state (status equal to "success").

  4. After a successful completion, the final operation object — that is, the parsed JSON body of the final polling response — must be returned by the method. That returned value is a dictionary which includes the operation's type field, and callers rely on that field being readable from the return value.

Remarks about the operation object

The final operation response, from which success is determined, contains a status of "success" alongside additional metadata fields. What must be returned to the caller is the full JSON body of that operation response.

Required Change 2: Delete upload_remote_raster

Take the upload_remote_raster method out of APIClient completely. Its former job was uploading a raster from a remote source such as an xyz or wms tile service; it is not part of the client any longer and should not exist.

Required Change 3: Delete the command-line interface

A command-line interface, built on top of the client, used to ship with the package; that entire layer has to be removed. Concretely:

  • The picterra.__main__ module must be deleted, its parse_args entry point included.
  • The picterra.command_parsers package/module must be deleted, together with its submodules (e.g. detect, create).
  • If the only reason picterra.helpers exists is to re-export the client for the CLI, that module must be deleted too.

Once these removals are in place, the client itself (from picterra import APIClient) must still import and work correctly. No CLI-related modules should be left importable.

Constraints

  • Wherever else the APIClient public API surface is used (raster upload from local file, listing rasters/detectors, creating/editing/deleting detectors and rasters, training detectors, running detectors, managing annotations and detection areas, downloading results and rasters, etc.), its behavior must remain unchanged.
  • Beyond run_advanced_tool, you must not add any other new public methods or endpoints.

  • name (optional, defaults to None): a human-readable name for the vector layer.
Value returned

The method must carry out a three-phase upload workflow against the API, relying on the same HTTP client/session and base URL configuration that the other client methods already use.

  • upload_id: an identifier used for committing the upload.
Phase 2 — Uploading the file contents

vector_layers/{raster_id}/upload/{upload_id}/commit/

  • poll_interval: how long to wait between polls.

operations/{operation_id}/
