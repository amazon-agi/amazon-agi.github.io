01 This task targets tensortrax, a Python package (imported as tr) that delivers forward-mode/higher-order automatic differentiation for array-like objects. 729 words · source specification, reworded by GLM-5.3-Flash

Task Description

Task overview

This task targets tensortrax, a Python package (imported as tr) that delivers forward-mode/higher-order automatic differentiation for array-like objects. Two changes, independent of each other, make up the work: the einsum function inside the math subpackage is to be extended, and the handling of the wrt argument in the hessian function is to be improved.

Background: The Dual-Number Types

Inside the package, two special array-wrapper types carry differentiation information (below, these are called "tensor types"):

  • A first-order type, one that carries value and gradient information; it will be called T.
  • A first-order variant, one that carries second-order (dual) information; it will be called F.

The tests work with F and T, which are instances of these two tensor types. Ordinary NumPy arrays are valid inputs for the functions below, too. As their array arguments, the functions must accept any mixture of these tensor types and plain NumPy arrays.

Part 1: tensortrax.math.einsum

The name tm.einsum (i.e., tensortrax.math.einsum, with tensortrax.math imported as tm) refers to a function with this signature:

einsum(subscripts, *operands)

Within it, subscripts is a standard NumPy-style einsum subscript string, with *operands holding the array arguments (each one either a plain NumPy array or one of the tensor types described above).

Required behavior

Subscript expressions working on a variable number of operands must be supported by einsum, specifically:

  • Two operands — an example is a subscript of the form "ij...,kl...->ijkl...".
  • Three operands — an example is a subscript of the form "ij...,kl...,mn...->ijklmn...".

In the case of 2 operands and in the case of 3 operands alike, einsum must correctly handle every combination of operand kinds — each operand may, independently, be a plain NumPy array, the first-order tensor type (T), or the second-order tensor type (F). What must come out is a correctly-differentiated tensor object whose type is appropriate and consistent with the inputs (i.e., einsum applied to the underlying values and propagated through all carried derivative components); the trailing broadcast (...) axes must be preserved.

The ... found in the subscripts stands for trailing axes that all operands and the output have in common; the operation must preserve them.

Error condition

A call to einsum involving four or more operands (for example, subscripts of the form "ij...,kl...,mn...,pq...->ijklmnpq...", which amounts to four operands) must raise NotImplementedError.

Part 2: tensortrax.hessian — handling of the wrt argument

tr.hessian (i.e., tensortrax.hessian) is a function that computes, with respect to one of a scalar-valued function's arguments, that function's second derivative, first derivative, and value. The usage that matters for this task is:

tr.hessian(fun, wrt=..., ntrax=...)(x, y)

fun is a callable that takes multiple array arguments as its input. hessian returns a callable, and calling that callable with the function's arguments in turn returns a tuple (h, g, f) of (hessian, gradient, function value).

Required behavior of wrt

Which of fun's arguments is the differentiation target is controlled through the wrt keyword argument. Two forms must be accepted by it:

  • An integer — the positional index of the target argument (for example, wrt=0 chooses the first positional argument, wrt=1 the second).
  • A string — the name of the parameter for the target argument (for example, wrt="y" chooses the argument named y in fun's signature).

The callable that hessian returns must also accept its arguments by keyword — for example, it can be called as (x=x, y=y) — and this must interoperate correctly with a string wrt.

The ntrax keyword argument, which behaves as before, gives the number of trailing (batch) axes.

Error condition

Should wrt be neither an integer nor a string (a list such as [1, 2], say), calling the wrapped callable must raise TypeError.

Correctness

As returned values, the gradient g and the hessian h must be the mathematically correct first and second derivatives of fun with respect to whichever argument was selected — evaluated at the given inputs, with the specified number of trailing axes treated as batch dimensions.

For validation, this example function is used:

def fun(x, y):
    return x**2 / y + x * log(y)   # elementwise, using the package's math functions

With wrt selecting x, the gradient is 2*x/y + log(y) and the hessian is 2/y. With wrt selecting y, the gradient is -(x**2)/y**2 + x/y and the hessian is 2*x**2/y**3 - x/y**2.

Task Description

Summary

The gradient and hessian decorator functions (accessible through the top-level package imported as tr, i.e. exposed at module level) are to be modified so that they support a new full_output keyword argument, which determines the shape of their return values.

Public Interface

The package (imported by convention as import ... as tr) must expose these callables at the top level:

  • tr.function(fun, ntrax=..., parallel=...)
  • tr.gradient(fun, ntrax=..., parallel=..., full_output=...)
  • tr.hessian(fun, ntrax=..., parallel=..., full_output=...)

Every one of them is a higher-order function: calling it with a scalar-valued function fun together with the keyword options returns a callable. That returned callable is subsequently invoked with a single array argument (a deformation-gradient-like array F) and produces the result.

Keyword arguments that are accepted:

  • ntrax (int): the number of trailing "trax" axes on the input array. It defaults to a sensible value; calls are made both with and without it.
  • parallel (bool): activates/deactivates a parallel evaluation path. It must be accepted for both True and False, and both paths must produce identically-shaped results.
  • full_output (bool): new argument, present on gradient and hessian only. It controls how many outputs are returned (see below). Its default value must be False.

full_output Behavior

tr.gradient(...)

When the returned callable is applied to F, it computes the gradient of fun with respect to F (call it dWdF) together with the function value itself (call it W).

  • With full_output=True: it returns a tuple (dWdF, W) in that order.
  • With full_output=False (the default): it returns only dWdF (a single array, not a tuple).
tr.hessian(...)

Applying the returned callable to F computes the Hessian of fun (call it d2WdF2), the gradient (dWdF), and the function value (W).

  • With full_output=True: it returns a tuple (d2WdF2, dWdF, W) in that order.
  • With full_output=False (the default): it returns only d2WdF2 (a single array, not a tuple).
tr.function(...)

Unchanged behavior: applying the returned callable to F returns the scalar function value evaluated over the input (call it W). It does not have a full_output argument.

Shapes of the Outputs

For an input F whose shape is (3, 3, *trax), with *trax denoting a set of ntrax trailing axes:

  • W is of shape (*trax).
  • dWdF is of shape (3, 3, *trax).
  • d2WdF2 is of shape (3, 3, 3, 3, *trax).

As a concrete case, for F with shape (3, 3, 1, 1) and ntrax=2:

  • W.shape == (1, 1)
  • dWdF.shape == (3, 3, 1, 1)
  • d2WdF2.shape == (3, 3, 3, 3, 1, 1)

Requirements for Correctness

The numerical results must be independent of the parallel flag: evaluating with parallel=False and with parallel=True must yield the same values.

The gradient and function value returned as part of hessian's full output must match the corresponding values that gradient and function compute for the same fun and F, including for inputs F that produce repeated eigenvalues (e.g. the identity matrix, or diagonal matrices with some equal and some differing diagonal entries), across the supported functions.

The implementations must stay correct for at least the following categories of scalar functions of F: standard strain-energy-type functions expressed through invariants (neo-Hookean form), functions expressed through principal stretches / eigenvalues (Ogden form), and functions that involve trigonometric operations on F.

Restriction

Behavior other than the introduction of the full_output argument (defaulting to False) and the corresponding return-value selection described above must not be changed.

06 Extend the tensor/autodifferentiation library in two ways 1100 words · rewritten by GPT-5.6-sol, reworded by GLM-5.3-Flash

Task Description

Extend the tensor/autodifferentiation library in two ways: Tensor objects gain reshape support, and hessian gains support for optional full output. Outside these additions, all existing public behavior and compatibility must be preserved.

1. Reshape support for Tensor objects

Reshape must be exposed through both the Tensor class and the public tensortrax.math module (typically imported as tm).

Core and trailing axes of a Tensor

The dimensions of a Tensor split into:

  • a core shape, exposed via Tensor.shape; and
  • Tensor.ntrax trailing axes, whose shape is exposed via Tensor.trax.

Tensor.size is the product of only the core dimensions. A reshape target applies to this core shape only. Trailing axes are batch-like dimensions, and when checking whether a target shape contains the correct number of elements, they must not be included.

Therefore, the product of every valid target shape must equal the original Tensor.size — it does not need to equal the total number of entries in the tensor's backing array.

The Tensor.reshape method

Add a method with the reshape-style interface:

Tensor.reshape(*shape)

The target core shape must be accepted either as a single shape argument or as multiple positional integer dimensions, in line with ordinary reshape calling conventions. Specifically, for a tensor with core size 9, all of the following forms must be supported where applicable:

t.reshape(9)       # target core shape (9,)
t.reshape(3, 3)    # target core shape (3, 3)
t.reshape((3, 3))  # a shape supplied as one argument

The method returns a Tensor that represents the reshaped result. It does not operate in place. No specific copy-versus-view behavior is required.

The module-level reshape function

The following public function must be exported from tensortrax.math:

reshape(a, newshape)

Here, a is a Tensor and newshape is a tuple giving the target core shape. For a tensor with core size 9, the following calls must succeed and return Tensor objects:

tm.reshape(t, (9,))
tm.reshape(t, (3, 3))
Semantics required for reshaping

The same rules must be obeyed by both APIs:

  1. Only the leading core dimensions are reshaped.
  2. ntrax must be preserved unchanged.
  3. All trailing axes keep their number, order, and extents unchanged.
  4. All data carried by the tensor must be reshaped consistently: the value data (x) and the first- and second-order variation data (δx, Δx, and Δδx) must stay associated with the same elements. The trailing-axis suffix of each component, including any broadcastable singleton trailing dimensions, must remain unchanged.
  5. Metadata consistent with the result must be returned: shape is the requested core shape, size remains the same core element count, and trax remains the original trailing shape.
  6. A valid reshape that preserves the core element count must not raise.

As an example, a tensor whose backing value has shape (3, 3, 100) and whose ntrax is 1 has core shape (3, 3), trailing shape (100,), and core size 9. Its required result shapes are:

Requested core shape Resulting backing value shape Result ntrax
(9,) (9, 100) 1
(3, 3) (3, 3, 100) 1

The requested core shape must not flatten in or absorb the trailing dimension of length 100. When the carried variation arrays also have backing shape (3, 3, 100), their resulting backing shapes must likewise be (9, 100) or (3, 3, 100). For ntrax=0, this becomes an ordinary element-count-preserving reshape covering all tensor dimensions.

2. The full_output option of hessian

The differentiation entry point exported from tensortrax (typically imported as tr) must support the following factory signature, which stays compatible with existing usage:

tr.hessian(
    fun,
    wrt=0,
    ntrax=0,
    parallel=False,
    full_output=False,
)

full_output is a Boolean option whose default is False. The existing parallel option is still accepted, and its behavior is unchanged.

The factory returns a callable that evaluates derivatives of the scalar-valued fun with respect to one selected argument.

Choosing the argument to differentiate

wrt supports the following forms:

  • an integer positional index, such as wrt=0; with this form, the selected value is supplied positionally to the returned callable; or
  • a string argument name, such as wrt="y"; with this form, the selected value is supplied to the returned callable under that keyword name.

Further arguments may be supplied in any manner that fun accepts, provided the selected argument is supplied consistently with the chosen wrt form. When used for evaluation, unsupported wrt values — a list included — must raise TypeError.

ntrax continues to determine how many final axes of the selected input count as trailing axes, and its existing differentiation behavior must be retained. parallel must not change the numerical values or the structure of what is returned.

Return value modes

When full_output=False — including when it is omitted — the returned callable returns only the Hessian:

h = tr.hessian(fun, wrt=..., ntrax=...)(...)

When full_output=True, it returns exactly a three-item tuple in this order:

h, g, f = tr.hessian(
    fun, wrt=..., ntrax=..., full_output=True
)(...)

where:

  • h is the Hessian (second derivative) taken with respect to the selected argument;
  • g is the gradient (first derivative) taken with respect to that same argument; and
  • f is the value of fun at the arguments that were supplied.

These results are ordinary numeric/NumPy values, not hyper-dual Tensor results. In full-output mode, the Hessian that is returned must be the same Hessian as the one that would be returned on its own with full_output=False.

For a selected input with core shape C and trailing shape B, the outputs of a scalar-valued function follow the established trailing-axis layout:

  • g.shape == C + B;
  • h.shape == C + C + B; and
  • f has trailing shape B (or is scalar if there are no trailing axes).

As an example, a selected input with shape (3, 3, 1, 1) and ntrax=2 yields a gradient of shape (3, 3, 1, 1), a Hessian of shape (3, 3, 3, 3, 1, 1), and a function value of shape (1, 1).

Correctness of the numerical results

For a scalar-valued function of multiple variables, differentiation must be with respect to only the argument chosen via wrt. At the inputs that are supplied:

  • g must equal the analytical first derivative of fun with respect to that argument; and
  • h must equal the analytical second derivative of fun with respect to that argument.

This correctness requirement holds equally for integer positional selection and for string keyword selection, and for both serial evaluation and the existing parallel evaluation mode.

A tr.Tensor stores its value in .x, along with its first- and mixed-second-order hyper-dual data in .δx, .Δx, and .Δδx. The ntrax trailing axes are batch-like axes; they are not tensor or matrix axes. For a value whose shape is

(*S, *B)

When values are matrices, the first two logical axes count as matrix axes and all trailing axes are batch axes.
