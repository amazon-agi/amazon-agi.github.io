Overview

Public API

class Article

  • If manifest is not provided, the constructor must generate a new manifest and expose it via the manifest attribute as a dict. When constructed from a doc_id, the generated manifest must record that identifier such that doc_id() returns it (see below).
Attribute: manifest

A dict holding the article's manifest data. It must always be present and be a dict.

The manifest has the following relevant structure:

  • "versions": a list of version entries, ordered from oldest (index 0) to newest (last). Each version entry is a dict of the form:
    {

    }
}
    Note that some version entries may omit "assets" entirely.

Method: version(index=-1)
def version(self, index=-1) -> dict

Returns a single version of the article as a dict.

  • The index selects which version from the manifest's "versions" list to return, using standard list indexing semantics. The default (-1) returns the latest (most recent) version; 0 returns the oldest version.

  • The returned dict must contain:

    • "data": the data path string of the selected version, taken directly from that version entry.

In other words, for each asset name, the returned "assets" maps the asset name directly to the most recent path recorded for it in the selected version.

    If the selected version entry has no "assets" key, the returned dict must not include an "assets" key.

Task Specification: Add Timestamps to Document Versions

Overview

You must implement a set of functions in the module multiverse.manifest that build and manipulate a document manifest data structure. This structure tracks versions of a document, each version referencing a data file and a set of assets. As part of this task, both document versions and individual asset entries must carry timestamps.

Module & Public API

Implement the following in multiverse/manifest.py:

new(doc_id)

Creates and returns a new, empty manifest for a document.

  • Input: doc_id — the document identifier (a string).
  • Returns: a dictionary of the form:
    {"id": doc_id, "versions": []}
add_version(manifest, data_url, assets, *, now=...)

Appends a new version entry to the manifest's "versions" list.

  • Inputs:
    • manifest — an existing manifest dictionary.
    • data_url — a string URL pointing to the version's data file.
    • assets — an iterable of asset names (strings) associated with this version.
    • now — a keyword-only argument that is a zero-argument callable returning a timestamp string. It must be callable via functools.partial binding (i.e., now is a proper keyword parameter). It supplies the current UTC timestamp. When not provided, it should default to a callable producing the actual current UTC timestamp.
  • Behavior: Returns a new manifest (the original need not be mutated in place; the returned value is what matters) whose "versions" list has one additional entry appended. The appended version entry is a dictionary with:
    • "data": the given data_url.
    • "assets": a dictionary mapping each asset name from assets to an empty list []. (Asset entries start with no versions attached; the asset name itself becomes a key with an empty list value.)
    • "timestamp": the string returned by calling now().
  • Note: Any additional keys already present on the manifest (beyond "id" and "versions") must be preserved in the returned manifest.
add_asset_version(manifest, asset_name, asset_url, *, now=...)

Records a new version of a single asset within the manifest's most recent version.

  • Inputs:
    • manifest — an existing manifest dictionary.
    • asset_name — the name of the asset (a string) to add a version to. This name must already exist as a key in the "assets" dictionary of the latest version.
    • asset_url — a string URL pointing to the asset file.
    • now — a keyword-only argument that is a zero-argument callable returning a timestamp string, with the same semantics and default as in add_version.
  • Behavior: Operates on the latest (last) version in the manifest's "versions" list. Appends a tuple (timestamp, asset_url) to the list stored under asset_name in that version's "assets" dictionary, where timestamp is the string returned by calling now().
  • Error condition: If asset_name does not exist as a key in the latest version's "assets" dictionary, a KeyError must be raised.
  • Note: Additional keys already present on the manifest must be preserved.

Data Structure Details

An asset in a version's "assets" dictionary is stored as a list of entries. Each entry is a 2-tuple:

(timestamp_string, asset_url_string)

where timestamp_string is when that asset version was recorded and asset_url_string is the file location.

A version entry looks like:

{
    "data": "<data_url>",
    "assets": {
        "<asset_name>": [
            ("<timestamp>", "<asset_url>"),
            ...
        ],
        ...
    },
    "timestamp": "<version_timestamp>",
}

Additional Required Behavior (Domain Layer)

Elsewhere in the codebase there exists an Article domain abstraction that consumes manifests of the shape described above. It must remain compatible with the timestamped structure:

Resolving an asset URL at a point in time

Given a version entry whose assets are lists of (timestamp, url) tuples, the article layer produces a "flattened" or resolved view of a version in which each asset name maps directly to a single asset URL string (not a list of tuples). When multiple (timestamp, url) entries exist for an asset, select the last entry in the asset history list—the newest entry—and expose its second element, the URL string. This selection is based on list order; timestamp strings do not need to be parsed or compared.

Oldest / resolved version output

When producing the resolved representation of a version, the output dictionary must include:

  • "data": the version's data URL string.
  • "assets": a dictionary mapping each asset name to a single URL string (the resolved asset URL, extracted from the (timestamp, url) tuples).
  • "timestamp": the version's "timestamp" string, carried through unchanged from the version entry.

For example, given a version whose assets contain multiple (timestamp, url) tuples for an asset, the resolved output for that asset is the URL from the last tuple, and the version's own "timestamp" value is preserved in the output.

Carrying a known asset reference into a new article version

When the article layer adds a new document version that refers to an asset already known from the most recent existing version, the new version must reference that asset's latest known URL. For a timestamped asset history, use the same resolution rule: select the last (timestamp, url) tuple and carry its second element, the URL. The tuple itself must not become the resolved asset reference.

Timestamp Format

Timestamps are plain strings in the format "YYYY-MM-DD HH:MM:SS.ffffff" (e.g., "2018-08-05 22:33:49.795151"). They are treated as opaque strings supplied by the now callable; no parsing or formatting logic beyond passing them through is required for add_version and add_asset_version.

08 Implement Document.version_at 699 words · source specification

Task Specification: Implement Document.version_at

Context

You are working with a Document domain class that tracks the versioned history of a document's data and its associated digital assets. Each document is constructed from a manifest that records, over time, the different states ("versions") of the document's data payload and of each of its assets. Every recorded state carries a UTC timestamp indicating when it was produced.

You must add a new method, version_at, to the Document class that reconstructs the state of the document as it existed at a given point in time.

The Manifest Model

A document is built from a manifest that contains:

  • A sequence of data versions, each associating a data URL with the UTC timestamp at which that data was registered.
  • For each asset (identified by an asset name/filename), a sequence of asset versions, each associating an asset URL with the UTC timestamp at which that asset version was registered.

Timestamps in the manifest are recorded as strings with microsecond precision, e.g. "2018-08-05 23:30:29.392990".

Method to Implement

Document.version_at(timestamp: str) -> dict
Input
  • timestamp: a string representing the moment in time (UTC) at which the document's state should be reconstructed. This value may be provided at varying precisions, for example a full timestamp like "2018-08-05 23:04:00" or a date-only value like "2018-12-31". Both forms must be accepted and interpreted as the corresponding UTC instant (a date-only value denotes the start of that day).
Output

The method returns a dictionary describing the document's state as of the requested instant, with exactly the following keys:

  • "data": the URL string of the most recent data version whose registration timestamp is less than or equal to the requested instant.
  • "assets": a dictionary mapping each asset name to a URL string. For each asset, the value is the URL of the most recent asset version whose registration timestamp is less than or equal to the requested instant. If an asset exists but has no version registered at or before the requested instant, its value must be the empty string "".
  • "timestamp": the registration timestamp string of the selected data version (i.e., the timestamp of the data state chosen for "data"), reproduced exactly as recorded in the manifest.
Selection Semantics
  • For the data payload, choose the latest data version whose timestamp is at or before the requested instant. If the requested instant equals a registration timestamp, that version is eligible.
  • For each asset, independently choose the latest asset version whose timestamp is at or before the requested instant.
  • It is possible for the requested instant to fall between the registration of the data and the registration of one of its assets. In that case, the data resolves to its selected version while the asset that has no version registered yet resolves to an empty-string URL.
  • A requested instant far in the future resolves to the most recent data version and the most recent version of each asset.
Error Condition
  • If the requested instant is earlier than the timestamp of the very first (oldest) data version — i.e., no data version exists at or before the requested instant — the method must raise ValueError.

Example Behavior

Task: Implement a create_documents_bundle Service Handler

Overview

You must implement a services layer that exposes command handlers operating over a session/store abstraction. The first (and only) required handler creates a "documents bundle" and persists it into a session-backed store.

Required Public API

Module: documentstore/services.py

Create a new module documentstore.services exposing:

get_handlers(get_session) -> Mapping[str, Callable]
  • Accepts a single argument get_session, a zero-argument callable that returns a session object when invoked.
  • Returns a mapping (e.g. a dict) whose keys are handler names (strings) and whose values are the corresponding callable command handlers.
  • The returned mapping must contain the key "create_documents_bundle", mapped to a callable command handler (described below).
  • The mapping must support .get(name) lookup returning the handler callable for a registered name.
The "create_documents_bundle" handler

A callable retrieved via handlers.get("create_documents_bundle") with the following behavior:

Signature (keyword arguments):

  • id (required): a string identifier for the bundle.
  • docs (optional): a list of document reference strings (e.g. ["/document/1", "/document/2"]).
  • metadata (optional): a mapping of metadata fields (e.g. {"publication_year": "2018", "volume": "2"}).

Behavior:

  • When invoked, it must obtain a session (via the get_session callable passed to get_handlers), build a documents bundle with the given id (and optionally the provided docs and metadata), and add it to the session's documents-bundles store.
  • On successful creation the handler must return None.
  • Calling the handler with an id that has already been added to the store must raise documentstore.exceptions.AlreadyExists.
  • The handler must be callable with only id; with id and docs; with id and metadata — each of these succeeds (returns None) provided the id does not already exist.

Supporting Domain / Interface / Session Requirements

The session object obtained from get_session exposes a documents_bundles property returning a documents-bundles store. That store provides:

  • add(bundle): obtains the bundle's id via bundle.id(); if that id is already present, raises documentstore.exceptions.AlreadyExists; otherwise stores the bundle's manifest data.
  • update(bundle): stores/overwrites the manifest for the bundle's id.
  • fetch(id): returns a bundle constructed from the stored manifest, or raises documentstore.exceptions.DoesNotExist if no such id exists.

To support this you must ensure the following exist:

documentstore/interfaces.py
  • An interface/base class Session exposing a documents_bundles property (in addition to any existing documents property).
  • An interface/base class DocumentsBundleStore declaring the add, update, and fetch methods described above.
documentstore/exceptions.py
  • Exception classes AlreadyExists and DoesNotExist (these may already exist; ensure both are present).
documentstore/domain.py
  • A class DocumentsBundle constructible via DocumentsBundle(manifest=<manifest>), exposing:
    • manifest: an attribute/property holding the bundle's manifest data.
    • id(): a method returning the bundle's identifier.

The DocumentsBundle produced by the create_documents_bundle handler must carry the provided id (retrievable via id()) and must round-trip through the store: a bundle stored via its manifest and reconstructed via DocumentsBundle(manifest=...) must yield the same id().

Constraints

  • The handler must integrate with the session abstraction strictly through get_session() and the session's documents_bundles store; duplicate-id detection is enforced by the store's add operation raising AlreadyExists, which must propagate out of the handler.

Task Specification: Add fetch_documents_bundle Service

Context

There is an existing service registry accessible via a factory function make_services(). This function returns a mapping-like object (supporting both .get("name") and ["name"] access) whose values are callable service commands. One existing service is create_documents_bundle. An exceptions module (referenced as exceptions) already exists and defines AlreadyExists and DoesNotExist exception classes.

You must add a new service, registered under the name "fetch_documents_bundle", to this registry.

Existing Service Behavior (relevant background)

The create_documents_bundle service creates a documents bundle. It is called with keyword arguments:

  • id (required): a string identifier for the bundle.
  • docs (optional): a list of document reference strings (e.g. ["/document/1", "/document/2"]).
  • metadata (optional): a dict of metadata key/value pairs.

The metadata recognized by a bundle is a fixed set of known keys, including at least publication_year and volume. Any keys supplied that are not among the recognized set are ignored/discarded and do not become part of the bundle's stored metadata.

Required New Behavior: fetch_documents_bundle

Register a callable command under the key "fetch_documents_bundle" in the object returned by make_services(). This command must:

Signature

Called with a keyword argument:

  • id (string): the identifier of the bundle to fetch.
Behavior

  1. Non-existent bundle: If no bundle exists with the given id, the command must raise exceptions.DoesNotExist.

  2. Successful fetch: If a bundle with the given id exists, the command must return a dict-like result representing the bundle, containing at least the following keys:

    • "id": the bundle's identifier string (equal to the id it was created with).

    • "items": a list of the document reference strings the bundle was created with (in the same order they were supplied via docs). If the bundle was created without any documents, this reflects that (an empty list).

    • "metadata": a dict containing exactly the recognized metadata key/value pairs stored on the bundle. This dict must include the metadata that was supplied at creation time, restricted to recognized keys only — any unrecognized keys supplied at creation are excluded from this dict.

Examples of expected result content
  • A bundle created with id="xpto" returns a result where result["id"] == "xpto".
  • A bundle created with id="xpto", docs=["/document/1", "/document/2"] returns a result where result["items"] == ["/document/1", "/document/2"].
  • A bundle created with id="xpto", metadata={"publication_year": "2018", "volume": "2"} returns a result where result["metadata"] == {"publication_year": "2018", "volume": "2"}.
  • A bundle created with id="xpto", metadata={"publication_year": "2018", "volume": "2", "unknown": "0"} returns a result where result["metadata"] == {"publication_year": "2018", "volume": "2"} (the unrecognized "unknown" key is not present).

Constraints

  • The command must be a callable and must be retrievable both via make_services().get("fetch_documents_bundle") and via make_services()["fetch_documents_bundle"].
  • Bundles created within the same services instance via create_documents_bundle must be retrievable by fetch_documents_bundle using the same id.
