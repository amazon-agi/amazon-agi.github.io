Overview

In the module multiverse.manifest, you must implement a collection of functions that construct and manipulate a document manifest data structure. This structure keeps track of a document's versions, with each version referencing a data file and a set of assets. As part of this task, timestamps must be carried by both the document versions and the individual asset entries.

Module and Public API

Inside multiverse/manifest.py, implement the following:

new(doc_id)

Constructs and returns a new, empty manifest for a document.

  • Input: doc_id — the identifier of the document (a string).
  • Returns: a dictionary of the form:
    {"id": doc_id, "versions": []}
add_version(manifest, data_url, assets, *, now=...)

Appends a further version entry onto the manifest's "versions" list.

  • Inputs:
    • manifest — a pre-existing manifest dictionary.
    • data_url — a string URL that points to the data file of the version.
    • assets — an iterable of asset names (strings) that belong to this version.
    • now — a keyword-only argument that is a zero-argument callable which returns a timestamp string. It must be possible to call it via functools.partial binding (that is, now is a proper keyword parameter). It provides the current UTC timestamp. When it is not provided, it should default to a callable that produces the actual current UTC timestamp.
  • Behavior: Returns a new manifest (the original need not be mutated in place; the returned value is what matters) whose "versions" list has one more entry appended to it. The version entry that gets appended is a dictionary containing:
    • "data": the data_url that was passed in.
    • "assets": a dictionary that maps each asset name from assets to an empty list []. (Asset entries begin with no versions attached; the asset name itself becomes a key whose value is an empty list.)
    • "timestamp": the string returned when now() is called.
  • Note: Any extra keys already present on the manifest (beyond "id" and "versions") must be preserved in the returned manifest.
add_asset_version(manifest, asset_name, asset_url, *, now=...)

Records a new version for a single asset inside the manifest's most recent version.

  • Inputs:
    • manifest — a pre-existing manifest dictionary.
    • asset_name — the name (a string) of the asset to which a version is being added. The name must already exist as a key inside the latest version's "assets" dictionary.
    • asset_url — a string URL that points to the asset file.
    • now — a keyword-only argument that is a zero-argument callable which returns a timestamp string; it carries the same semantics and default as in add_version.
  • Behavior: Acts on the latest (last) version in the manifest's "versions" list. A tuple (timestamp, asset_url) is appended to the list stored under asset_name in that version's "assets" dictionary; timestamp here is the string returned by calling now().
  • Error condition: A KeyError must be raised if asset_name does not exist as a key in the latest version's "assets" dictionary.
  • Note: Additional keys that are already present on the manifest must be preserved.

Details of the Data Structure

Within a version's "assets" dictionary, an asset is stored as a list of entries. Each entry is a 2-tuple:

(timestamp_string, asset_url_string)

where timestamp_string is the time at which that asset version was recorded and asset_url_string is the location of the file.

A version entry takes this form:

{
    "data": "<data_url>",
    "assets": {
        "<asset_name>": [
            ("<timestamp>", "<asset_url>"),
            ...
        ],
        ...
    },
    "timestamp": "<version_timestamp>",
}

Further Required Behavior (Domain Layer)

Elsewhere in the codebase, an Article domain abstraction exists that consumes manifests of the shape described above. It must remain compatible with the timestamped structure:

Resolving an asset URL at a point in time

Given a version entry whose assets are lists of (timestamp, url) tuples, the article layer produces a view of the version that is "flattened" or resolved: in it, each asset name maps directly to a single asset URL string (not a list of tuples). If an asset has multiple (timestamp, url) entries, select the last entry in the asset history list—the newest entry—and expose its second element, the URL string. The selection relies on list order; the timestamp strings do not have to be parsed or compared.

Oldest / resolved version output

When the resolved representation of a version is produced, the output dictionary must include:

  • "data": the data URL string of the version.
  • "assets": a dictionary that maps each asset name to a single URL string (the resolved asset URL, taken out of the (timestamp, url) tuples).
  • "timestamp": the version's "timestamp" string, passed along unchanged from the version entry.

As an example, for a version whose assets contain multiple (timestamp, url) tuples for an asset, the resolved output for that asset is the URL taken from the last tuple, and the version's own "timestamp" value is preserved in the output.

Carrying a known asset reference into a new article version

If the article layer adds a new document version that refers to an asset already known from the most recent existing version, that new version must reference the asset's latest known URL. With a timestamped asset history, apply the same resolution rule: select the last (timestamp, url) tuple and carry its second element, the URL. The tuple itself must not become the resolved asset reference.

Format of Timestamps

Timestamps are plain strings following the format "YYYY-MM-DD HH:MM:SS.ffffff" (e.g., "2018-08-05 22:33:49.795151"). They are handled as opaque strings provided by the now callable; for add_version and add_asset_version, no parsing or formatting logic beyond passing them through is required.

Task Specification: Implement the Document.version_at Method

Background

In this task you deal with a Document domain class whose job is to keep track of the versioned history of a document's data and of the digital assets that belong to it. The manifest that a document is constructed from logs, as time goes by, the various states ("versions") taken on by the document's data payload and by each of its assets. Every state that gets logged comes with a UTC timestamp showing when it was produced.

You must write a new method, version_at, for the Document class — one that rebuilds the document's state as it stood at a given point in time.

Manifest Structure

A document gets assembled from a manifest, and this manifest contains:

  • a sequence of data versions, each of which pairs a data URL with the UTC timestamp of that data's registration.
  • for each asset (its identifier being an asset name/filename), a sequence of asset versions, each of which pairs an asset URL with the UTC timestamp of that asset version's registration.

Inside the manifest, timestamps are stored as strings carrying microsecond precision — for example, "2018-08-05 23:30:29.392990".

Method to Write

Document.version_at(timestamp: str) -> dict
Input
  • timestamp: the moment in time (UTC) at which the document's state should be reconstructed, given as a string. This value may arrive with varying precisions — e.g. as a full timestamp such as "2018-08-05 23:04:00", or as a date-only value such as "2018-12-31". Both forms must be accepted, and each is to be read as the corresponding UTC instant (a date-only value stands for the start of that day).
Output

The return value is a dictionary capturing the state of the document at the requested instant, and it carries exactly the following keys:

  • "data": the URL string of the most recent data version having a registration timestamp that is less than or equal to the requested instant.
  • "assets": a dictionary in which every asset name is mapped to a URL string. Per asset, the value is the URL of the most recent asset version with a registration timestamp that is less than or equal to the requested instant.
