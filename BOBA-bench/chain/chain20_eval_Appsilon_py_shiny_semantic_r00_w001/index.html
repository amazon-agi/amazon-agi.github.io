Task Specification: Implementation of an Icon Component

Goal

Build an icon function that generates a Fomantic/Semantic UI icon HTML element: an empty <i> element carrying the appropriate icon CSS classes. The resulting value must compose with Shiny/htmltools UI objects and with page_semantic(...).

Public Interface

It must be publicly importable as:

from shiny_semantic.elements import icon
Function Signature
def icon(name, modifiers=""):
    ...
  • name (str, required): Name of the icon, such as "users", "home", or "asterisk".
  • modifiers (str, optional): Extra CSS modifier classes separated by spaces, such as "loading", "large", or "bordered teal". Its default value is the empty string.

Requirements for Rendering the Icon

The icon(...) function must return an HTML tag object compatible with Shiny/htmltools that represents an <i> element.

The value of the element's class attribute must be exactly the modifiers value, one literal space, the name value, one literal space, and the literal word icon, in that order:

f"{modifiers} {name} icon"

As a consequence, the opening tags rendered for the required examples are:

Invocation Opening tag as rendered
icon("users") <i class=" users icon">
icon("asterisk", "loading") <i class="loading asterisk icon">
icon("home", "large") <i class="large home icon">
icon("home", "bordered teal") <i class="bordered teal home icon">

Class ordering and class spacing belong to the public output contract. In particular:

  • When modifiers is omitted, the separator space still follows its empty value, meaning the class value starts with a leading space (for example, " users icon").
  • A modifier string holding multiple classes stays positioned before the icon name and keeps its internal spaces.
  • The <i> element has neither children nor text content.

Integration with page_semantic

The page helper continues to be publicly importable as:

from shiny_semantic import page_semantic

An object that icon(...) returns must be accepted as a child of page_semantic(...), and the serialization of the resulting Shiny page must contain the corresponding <i> markup.

Every page that page_semantic(...) produces, including a page created with no child content, must include references to all of the following front-end dependencies in its rendered HTML:

  • The Fomantic UI stylesheet with the filename fomantic.min.css.
  • The Fomantic UI script with the filename fomantic.min.js.
  • The Shiny Semantic bindings script with the filename shiny-semantic-bindings.js.

Consequently, each of those exact filename literals must be present in the rendered page HTML. Callers must not need to add these dependencies separately in order to use an icon inside a semantic page.

Requirements for Compatibility

  • The value returned by icon(...) must take part in normal Shiny/htmltools tag composition rather than being merely a raw, non-composable value.
  • Use of page_semantic(...) as the semantic page wrapper in existing code must continue to work while supplying the required stylesheet and scripts.

button

Define the callable:

button(input_id, label, class_="", icon=None)

Arguments:

  • input_id (str): the DOM id of the button.

Task Specification: Header and Subheader Elements

Overview

Two functions, header and subheader, are to be implemented in the module shiny_semantic.elements. These functions produce HTML tag objects that are compatible with the htmltools/Shiny tag system and that support .get_html_string() and inclusion in a TagList.

Public API

Both functions must be importable in the following way:

from shiny_semantic.elements import header, subheader
header(*args, class_=None, **kwargs)

This function creates a <div> element that represents a Semantic UI header.

Behavior:

  • The element that gets rendered is a <div>.
  • The class attribute of the element is built from the fixed base classes ui and header, with any classes supplied by the caller inserted between them.
  • The class_ keyword parameter accepts an optional string containing additional class names.
    • When class_ is not given (or None), the resulting class attribute is exactly ui header (base classes only, with a single space as the separator — no extra/doubled spaces).
    • When class_ is supplied, its value appears between ui and header, separated by single spaces. As an example, class_="huge" yields class="ui huge header", and class_="huge icon" yields class="ui huge icon header".
  • Positional arguments (*args) form the element's children/content and are rendered inside the <div>. They may be plain strings and/or other tag objects (such as the result of subheader).
subheader(*args, class_=None, **kwargs)

This function creates a <div> element that represents a Semantic UI sub-header.

Behavior:

  • The element that gets rendered is a <div>.
  • The class attribute of the element is made up of the fixed base classes sub and header, with any classes supplied by the caller inserted between them, following the same composition rules as header.
  • When no class_ is supplied, a call such as subheader("subheader") renders exactly as <div class="sub header">subheader</div>.
  • Positional arguments (*args) constitute the element's children/content and are rendered inside the <div>.

Notes

  • The keyword for passing extra CSS classes is class_ (trailing underscore).
  • Class strings must be joined using single spaces; the produced class attribute must contain no leading, trailing, or doubled spaces when no extra classes are supplied.

  • placeholder (str, keyword-only): text displayed as the dropdown's default/placeholder text.
  • settings (dict, keyword-only): configuration options for the dropdown.

All of the parameters after choices are keyword-only.

Requirements for the Rendered Output

The HTML produced must contain:

  1. A wrapper <div> for the form:

    <div class="ui form">

  2. A wrapper <div> for the field:

    <div class="field">

  3. The settings dictionary serialized as JSON into the data-settings attribute belonging to the underlying dropdown container. For example, settings={"clearable": True} must render (HTML-escaped) as:

    data-settings="{&quot;clearable&quot;: true}

    (i.e. the JSON {"clearable": true}, with the double quotes HTML-escaped as &quot;).

  4. The placeholder value serving as the dropdown's default text. For example, placeholder="Select" must produce:

    <div class="default text">Select</div>

Apart from that, the component must embed a dropdown built from choices and id that follows the same structure defined for the dropdown function.

Task Specification: Building the Checkbox UI Module

Goal

The task is to create a checkbox function inside the shiny_semantic.modules package that produces checkbox HTML components styled with Semantic UI.

Public API Surface

It must be possible to import the following:

from shiny_semantic.modules import checkbox, checkbox_group

Both names, checkbox and checkbox_group, must exist and be importable from shiny_semantic.modules. Detailed behavior is specified below for checkbox only; checkbox_group must simply exist as an importable name (a callable is enough).

checkbox Function

Function Signature
checkbox(id, label, value=False, type=None)
  • id (str): the identifier assigned to the component.
  • label (str): the text shown as the checkbox label.
  • value (bool, default False): whether the checkbox starts out pre-checked.
  • type (str or None, default None): a modifier that alters the input type and the CSS classes.
Return Value

The function must return a tag object compatible with htmltools (one that can be placed inside htmltools.TagList and rendered via get_html_string()).

HTML Structure Produced

When rendered, the component is an outer <div> that contains an <input> and a <label>:

<div id="{id}" class="{classes}">
  <input id="{id}" type="{input_type}" name="{id}"{checked_attr}/>
  <label for="{id}">{label}</label>
</div>

Specifics:

  • The outer <div>'s id is equal to the id argument, and it also carries a class attribute (see the class rules below).
  • The <input> receives id equal to id, a type attribute (see the type rules below), and name equal to id.
  • The <label>'s for is equal to id, and its content is the label text.
Outer <div> Class Rules

The class string always starts with ui and always ends with checkbox. Extra class tokens go between them, depending on value and type:

  • Base case (no value, no type): ui checkbox
  • When value is True: the token checked is inserted immediately after ui.
  • When type is provided: the type value is added as a token before checkbox.

When multiple tokens apply, the order is: ui, then checked (if checked), then {type} (if provided), then checkbox.

Examples:

  • value=True, type="radio" → ui checked radio checkbox
  • type="slider" → ui slider checkbox
  • type="toggle" → ui toggle checkbox
<input> Type Rules
  • When type is None, the input's type attribute is checkbox.
  • When type is "radio", the input's type attribute is radio.
  • When type is "slider" or "toggle", the input's type attribute stays checkbox (the type value only affects the outer <div> class, not the input's type attribute).
Rules for the <input>'s checked Attribute
  • When value is True, the <input> has a checked attribute rendered as checked="".
  • When value is False, no checked attribute appears on the <input>.

Worked Examples

checkbox("test1", "Test1") produces:

<div id="test1" class="ui checkbox">
  <input id="test1" type="checkbox" name="test1"/>
  <label for="test1">Test1</label>
</div>

checkbox("test2", "Test2", value=True, type="radio") produces:

<div id="test2" class="ui checked radio checkbox">
  <input id="test2" type="radio" name="test2" checked=""/>
  <label for="test2">Test2</label>
</div>

checkbox("test3", "Test3", type="slider") produces:

<div id="test3" class="ui slider checkbox">
  <input id="test3" type="checkbox" name="test3"/>
  <label for="test3">Test3</label>
</div>

checkbox("test4", "Test4", type="toggle") produces:

<div id="test4" class="ui toggle checkbox">
  <input id="test4" type="checkbox" name="test4"/>
  <label for="test4">Test4</label>
</div>

Additional Notes

  • The shiny_semantic.tests package must be importable (in other words, the package structure must support test discovery under shiny_semantic/tests/).

Task Specification: Implementing checkbox_group

Goal

Build a function called checkbox_group that produces an HTML element representing a grouped set of checkbox or radio inputs. Each choice that is supplied must be rendered as an individual input in the group.

The new function must coexist with the existing checkbox function; the public availability of that function, together with its existing behavior, must not be removed or changed.

Public API and import paths

The function's signature is:

def checkbox_group(id, label, choices, selected=None, type="checkbox"):
    ...

It must be publicly importable from the shiny_semantic.modules namespace, alongside checkbox:

from shiny_semantic.modules import checkbox, checkbox_group

The import path of the checkbox module must also expose it:

from shiny_semantic.checkbox import checkbox_group

Function parameters

  • id (str): Identifier of the overall group.
  • label (str): Label of the group.
  • choices (list[str]): Choice values to be rendered as individual inputs.
  • selected (str | list[str] | None, optional): A single selected choice, multiple selected choices, or no initial selection. The default is None.
  • type (str, optional): The input type, either "checkbox" or "radio". The default is "checkbox".

Returned value

Return an HTML element object that provides a get_html_string() method. When that method is called, it must produce the group's rendered markup as a string.

HTML structure requirements

As an example:

element = checkbox_group(
    id="group",
    label="group",
    choices=["one", "two"],
    selected="one",
)
html = element.get_html_string()

All of the following exact fragments must be present in the rendered string.

Container for the group
<div id="group" class="grouped fields ss-checkbox-group">

The id of the container is the group id that was supplied, and its class attribute is exactly grouped fields ss-checkbox-group.

Wrapper for each choice

Each choice must have a wrapper of its own. For the selected choice "one", the fragment is:

<div id="group__one" class="ui checked checkbox" data-shiny-value="one">

For every choice:

  • Build its option id as <group id>__<choice>, with exactly two underscores serving as the separator.
  • Apply that id to the choice wrapper.
  • Assign the choice value to data-shiny-value.
  • For a selected option, the wrapper has the checked class token, which in this case yields class="ui checked checkbox". An option that is unselected must use the corresponding unchecked form and must not have the checked class token.
Input for each choice

The selected choice shown above must contain this input fragment:

<input id="group__one" type="checkbox" name="group" checked=""/>

For every choice input:

  • Give it the same <group id>__<choice> id as its wrapper.
  • Set the input's type to the value of the function's type argument; that argument is checkbox by default and radio when requested.
  • Set name to the id of the overall group, so that all inputs belong to the same group.
  • Include checked="" only when the choice in question is selected. For an unselected choice, do not emit the checked attribute.

Behavior of the selection

  • If a single string is passed as selected, the matching choice is initially checked.
  • If a list of strings is passed as selected, every matching choice in that list is initially checked for a checkbox group.
  • Both representations of checked state must be present on every selected choice: the wrapper's checked class token and the input's checked="" attribute.
  • Choices that are not selected must have neither representation of checked state.

Validation for radio groups

A radio group may have at most one initially selected value. If type="radio" and selected is a list that contains more than one value, raise an exception. The message of that exception must contain:

Radio buttons may have a maximum of 1 active value

Requirements for exact output

Use of the double-underscore id separator is required. Given the corresponding arguments and states, every quoted HTML fragment in this specification must occur verbatim in the string that get_html_string() returns.
