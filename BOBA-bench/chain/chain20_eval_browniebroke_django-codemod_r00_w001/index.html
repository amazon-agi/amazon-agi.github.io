01 Implement/fix a code transformer named InlineHasAddPermissionsTransformer located in the module django_codemod.visitors.django_30. 418 words · source specification

Objective

Implement/fix a code transformer named InlineHasAddPermissionsTransformer located in the module django_codemod.visitors.django_30. It must be importable as:

from django_codemod.visitors.django_30 import InlineHasAddPermissionsTransformer

Background

Django admin inline classes (TabularInline, StackedInline) define a has_add_permission method. In newer Django versions this method signature gained a required-by-convention obj parameter. The transformer must update the signature of has_add_permission methods defined inside classes that subclass one of the recognized inline base classes.

Required Behavior

The transformer processes Python source. It targets methods named has_add_permission whose signature is exactly:

def has_add_permission(self, request):

When such a method is defined inside a class whose base-class list includes at least one recognized inline base class, rewrite the method signature to:

def has_add_permission(self, request, obj = None):

The method body and everything else must remain unchanged. When the class does not qualify, the source must be left completely unmodified.

Recognized base classes

A class qualifies if any of its listed base classes is one of the following (matched by the name as written in the source):

  • TabularInline
  • admin.TabularInline
  • StackedInline
  • admin.StackedInline

Both the bare name form (e.g. StackedInline) and the attribute-access form (e.g. admin.StackedInline) must be recognized as valid.

Base-class list handling

Qualification must be based on whether any base class in the class definition matches a recognized inline base class. This includes classes with multiple base classes:

  • A recognized inline base class appearing as the only base class must trigger the transformation.
  • A recognized inline base class appearing last in a multi-base-class list (e.g. class Foo(SomeMixin, admin.StackedInline):) must trigger the transformation.
  • A recognized inline base class appearing first in a multi-base-class list (e.g. class Foo(TabularInline, OtherBase):) must trigger the transformation.

Other, non-recognized base classes present alongside a recognized one do not prevent the transformation.

Non-qualifying cases (no modification)

The source must be left unchanged when:

  • The enclosing class's base classes contain none of the recognized inline base classes (e.g. class MyAdmin(admin.ModelAdmin):).
  • The enclosing class has no base classes at all (e.g. class MyCustomStuff:).

In these cases, any has_add_permission(self, request) method must be preserved verbatim.

Output formatting

The rewritten signature must render exactly as:

def has_add_permission(self, request, obj = None):

(Note the spaces around = in the added obj = None default parameter.)

The transformer is a codemod visitor consistent with the other transformers already present in django_codemod.visitors.django_30; it should be a class usable in the same manner as its siblings in that module.

Overview

You must implement a reusable base class for LibCST-based codemod transformers that rename a function imported from one module to another (possibly different) module. This base class encapsulates the logic for updating both the from ... import ... statement and the call sites of the renamed function.

Public API

The class is intended to be subclassed. Each concrete subclass declares two class-level string attributes:

  • rename_from: the fully-qualified dotted path of the function being renamed (e.g. "django.dummy.module.func"). The last dotted segment is the old function name; the preceding segments form the old module path.
  • rename_to: the fully-qualified dotted path of the replacement function (e.g. "django.dummy.module.better_func" or "django.better.dummy.better_func"). The last dotted segment is the new function name; the preceding segments form the new module path.

The class must be a valid LibCST transformer (a context-aware visitor/transformer) that can be applied to a module's source via the standard codemod machinery, so that instances can transform Python source code.

The old and new module paths may be the same or different. The old and new function names may be the same or different.

Required Behavior

Given source code being transformed, the transformer operates only on the function identified by rename_from. Behavior is determined by matching the imported name against the old module path and old function name.

1. Simple rename (same module)

When the function is imported directly from its module and called by name, both the import and every call site are rewritten to use the new name.

Input:

from django.dummy.module import func

result = func()

Output:

from django.dummy.module import better_func

result = better_func()
2. Rename with change of module

When rename_to names a different module than rename_from, the import statement must be moved to the new module path (with the new function name) and call sites rewritten.

Input:

from django.dummy.module import func

result = func()

Output (with rename_to = "django.better.dummy.better_func"):

from django.better.dummy import better_func

result = better_func()
3. Target name already imported (same module)

When the destination function name is already present in the same import statement alongside the old name, the old name must be removed from the import list, leaving only the destination name, and call sites rewritten.

Input:

from django.dummy.module import func, better_func

result = func(content)

Output:

from django.dummy.module import better_func

result = better_func(content)

This must work regardless of the ordering of names in the import list. In particular, when the old name is the last entry in the import list, no stray/trailing comma may remain:

Input:

from django.dummy.module import better_func, func

result = func(content)

Output:

from django.dummy.module import better_func

result = better_func(content)
4. Target name already imported (different module)

When rename_to names a different module and that destination module already imports the destination function, the old import statement is removed entirely, the existing destination import remains, and call sites are rewritten.

Input (with rename_to = "django.better.dummy.better_func"):

from django.dummy.module import func
from django.better.dummy import better_func

result = func(content)

Output:

from django.better.dummy import better_func

result = better_func(content)
5. Import with alias

When the function is imported with an alias (import func as aliased_func), only the imported original name is changed to the new function name; the alias binding is preserved, and call sites (which use the alias) are left unchanged. This applies for both same-module and different-module renames.

Input (same module):

from django.dummy.module import func as aliased_func

result = aliased_func()

Output:

from django.dummy.module import better_func as aliased_func

result = aliased_func()

Input (different module, rename_to = "django.better.dummy.better_func"):

from django.dummy.module import func as aliased_func

result = aliased_func()

Output:

from django.better.dummy import better_func as aliased_func

result = aliased_func()
6. Same name from a different module (no change)

When a function bearing the same name as the old function is imported from a module that is not the old module path, nothing must change — neither the import nor its call sites.

Input:

from utils.helpers import func

result = func()

Output (unchanged):

from utils.helpers import func

result = func()
7. Calls without a simple name reference (no crash, no change)

The transformer must safely handle call expressions whose callee is not a plain name, without raising errors and without modifying the code.

Input:

factory()()

Output (unchanged):

factory()()

Input:

(lambda x: x)(something)

Output (unchanged):

(lambda x: x)(something)

Notes

  • Only the function specified by rename_from is affected. Any other imports or code must be left intact.
  • The class must be importable and usable purely by declaring the two class attributes on a subclass; no other configuration is required.
