Task Description

Goal

Implement or fix a code transformer named InlineHasAddPermissionsTransformer that lives in the module django_codemod.visitors.django_30. It must be possible to import it as:

from django_codemod.visitors.django_30 import InlineHasAddPermissionsTransformer

Background

Django admin inline classes (TabularInline, StackedInline) define a has_add_permission method. In newer Django versions this method signature gained an obj parameter that is required by convention. The transformer must update the signature of has_add_permission methods that are defined inside classes subclassing one of the recognized inline base classes.

Required Behavior

The transformer works on Python source. It targets methods that are named has_add_permission and whose signature is exactly:

def has_add_permission(self, request):

When a method like this is defined within a class whose base-class list contains at least one recognized inline base class, rewrite the signature of that method to:

def has_add_permission(self, request, obj = None):

The method body, as well as everything else, must remain unchanged. If the class does not qualify, the source must be left completely unmodified.

Recognized base classes

A class qualifies when any of the base classes it lists is one of the following (matched by the name as written in the source):

  • TabularInline
  • admin.TabularInline
  • StackedInline
  • admin.StackedInline

The bare name form (e.g. StackedInline) and the attribute-access form (e.g. admin.StackedInline) must both be recognized as valid.

How the base-class list is handled

Qualification must be decided by whether any base class in the class definition matches a recognized inline base class. This includes classes that have multiple base classes:

  • When a recognized inline base class appears as the only base class, it must trigger the transformation.
  • A recognized inline base class appearing in the last position of a multi-base-class list (e.g. class Foo(SomeMixin, admin.StackedInline):) must trigger the transformation.
  • A recognized inline base class appearing in the first position of a multi-base-class list (e.g. class Foo(TabularInline, OtherBase):) must trigger the transformation.

Base classes that are not recognized, when present alongside a recognized one, do not prevent the transformation.

Cases that do not qualify (no modification)

The source must be left unchanged in these situations:

  • The base classes of the enclosing class contain none of the recognized inline base classes (e.g. class MyAdmin(admin.ModelAdmin):).
  • There are no base classes at all on the enclosing class (e.g. class MyCustomStuff:).

In such cases, any has_add_permission(self, request) method must be preserved verbatim.

Output Format

The rewritten signature must render exactly as follows:

def has_add_permission(self, request, obj = None):

(Take note of the spaces around = in the obj = None default parameter that is added.)

The transformer is a codemod visitor that is consistent with the other transformers already present in django_codemod.visitors.django_30; it should be a class that is usable in the same manner as its siblings in that module.

Summary

You must implement a reusable base class for codemod transformers built on LibCST that rename a function imported from one module to another (possibly different) module. The base class bundles together the logic for updating both the from ... import ... statement and the call sites of the renamed function.

Public Interface

Add a class BaseSimpleFuncRenameTransformer to the module django_codemod.visitors.base.

The class is meant to be subclassed. Each concrete subclass declares two string attributes at class level:

  • rename_from: the fully-qualified dotted path of the function that is being renamed (e.g. "django.dummy.module.func"). Its last dotted segment is the old function name; the segments preceding it make up the old module path.
  • rename_to: the fully-qualified dotted path of the replacement function (e.g. "django.dummy.module.better_func" or "django.better.dummy.better_func"). Its last dotted segment is the new function name; the segments preceding it make up the new module path.

The class must be a valid LibCST transformer (a context-aware visitor/transformer) that can be applied to the source of a module through the standard codemod machinery, so that its instances can transform Python source code.

The old module path and the new module path may be the same, or they may differ. Likewise, the old function name and the new function name may be the same or different.

Behavior Requirements

For the source code undergoing transformation, the transformer acts only on the function identified by rename_from. Which behavior applies is decided by matching the imported name against the old module path and old function name.

1. Simple rename within the same module

When the function is imported directly from its module and called by name, both the import statement and every call site are rewritten so that the new name is used.

Input:

from django.dummy.module import func

result = func()

Output:

from django.dummy.module import better_func

result = better_func()
2. Rename that also changes the module

When the module named by rename_to differs from the one named by rename_from, the import statement must be moved to the new module path (together with the new function name), and the call sites rewritten.

Input:

from django.dummy.module import func

result = func()

Output (with rename_to = "django.better.dummy.better_func"):

from django.better.dummy import better_func

result = better_func()
3. Destination name already imported (same module)

When the destination function name is already present in the same import statement together with the old name, the old name must be removed from the import list so that only the destination name is left, and the call sites rewritten.

Input:

from django.dummy.module import func, better_func

result = func(content)

Output:

from django.dummy.module import better_func

result = better_func(content)

This must work no matter in which order the names appear in the import list. In particular, when the old name is the last entry in the import list, no stray/trailing comma may remain:

Input:

from django.dummy.module import better_func, func

result = func(content)

Output:

from django.dummy.module import better_func

result = better_func(content)
4. Destination name already imported (different module)

When the module named by rename_to is a different module and that destination module already imports the destination function, the old import statement is removed in its entirety, the destination import that already exists remains, and the call sites are rewritten.

Input (with rename_to = "django.better.dummy.better_func"):

from django.dummy.module import func
from django.better.dummy import better_func

result = func(content)

Output:

from django.better.dummy import better_func

result = better_func(content)
5. Aliased import

When the function is imported with an alias (import func as aliased_func), only the original name as imported is changed to the new function name; the binding of the alias is preserved, and the call sites (which use the alias) are left unchanged. This holds for both same-module and different-module renames.

Input (same module):

from django.dummy.module import func as aliased_func

result = aliased_func()

Output:

from django.dummy.module import better_func as aliased_func

result = aliased_func()

Input (different module, rename_to = "django.better.dummy.better_func"):

from django.dummy.module import func as aliased_func

result = aliased_func()

Output:

from django.better.dummy import better_func as aliased_func

result = aliased_func()
6. The same name imported from a different module (no change)

When a function carrying the same name as the old function is imported from a module that is not the old module path, nothing must change — neither the import nor its call sites.

Input:

from utils.helpers import func

result = func()

Output (unchanged):

from utils.helpers import func

result = func()
7. Calls lacking a simple name reference (no crash, no change)

The transformer must safely handle call expressions in which the callee is not a plain name, without raising errors and without modifying the code.

Input:

factory()()

Output (unchanged):

factory()()

Input:

(lambda x: x)(something)

Output (unchanged):

(lambda x: x)(something)

Notes

  • Only the function that rename_from specifies is affected. Any other imports or code must be left intact.
  • The class must be importable and usable purely by declaring the two class attributes on a subclass; no configuration besides that is required.
