01 Implement the update_documents_bundle_metadata Service 465 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Implement the update_documents_bundle_metadata Service

Context

The codebase exposes a set of services that are accessible through a services registry. To obtain the registry, call the make_services() factory (already available in the codebase). Individual services can be looked up in the registry both via a .get(name) method and via item access services[name]; each of these lookups returns a callable service command.

The services listed below already exist in the registry and can be relied upon:

  • create_documents_bundle — creates a documents bundle. It can be called as create_documents_bundle(id=<str>, metadata=<dict>).
  • fetch_documents_bundle — retrieves a documents bundle. It can be called as fetch_documents_bundle(id=<str>) and returns a mapping that includes a "metadata" key whose value is a dict of the bundle's current metadata.

An exceptions module (importable as exceptions) is available; it defines exceptions.DoesNotExist.

What to Implement

Register a new service under the name update_documents_bundle_metadata in the services registry that make_services() produces.

Service Interface

The service must be a callable that can be retrieved from the registry via services.get("update_documents_bundle_metadata") (and services["update_documents_bundle_metadata"]). Each of these lookups must return a non-None, callable object.

The callable accepts two keyword arguments:

update_documents_bundle_metadata(id=<str>, metadata=<dict>)
Behavior

  1. Bundle absent: If there is no documents bundle for the given id, the call must raise exceptions.DoesNotExist.

  2. Metadata update (merge semantics): When the bundle exists, the values supplied in the metadata argument are merged into the bundle's existing metadata:

    • A key present in the argument overwrites the corresponding existing value.
    • A key that is already present in the bundle but absent from the argument stays unchanged.

    Example: a bundle with metadata {"publication_year": "2018", "volume": "2"} that is updated with {"publication_year": "2019"} ends up with {"publication_year": "2019", "volume": "2"}.

  3. Unexpected/unknown metadata keys are ignored: The service accepts only a known set of metadata fields. Any key in the metadata argument that is not among the recognized fields must be silently ignored — it must not be added to the bundle's metadata and must not alter it in any other way.

    Recognized fields exercised here include at least publication_year and volume.

    Example: a bundle with metadata {"publication_year": "2018", "volume": "2"} that is updated with {"unknown": "0"} keeps its metadata as {"publication_year": "2018", "volume": "2"}.

  4. Clearing a metadata value: A recognized field can be cleared by assigning an empty string to it. Doing so overwrites the existing value with ""; the key stays present in the metadata, holding the empty-string value.

    Example: a bundle with metadata {"publication_year": "2018", "volume": "2"} that is updated with {"volume": ""} ends up with {"publication_year": "2018", "volume": ""}.

The results of the update must be observable through a subsequent fetch_documents_bundle(id=<id>) call; the "metadata" returned by that call reflects the merged state described above.

The service need not return any particular value.

02 Introduce a new service command called add_document_to_documents_bundle into the services registry. 390 words · source specification, reworded by GLM-5.3-Flash

Specification of the Task

Summary

Introduce a new service command called add_document_to_documents_bundle into the services registry. Its purpose is to append a document reference to an existing documents bundle.

Background

A factory for the services registry, make_services(), already exists and returns a dict-like mapping of named service commands. The following commands are already present in this registry, and you may rely on them:

  • create_documents_bundle(id, docs=None) — creates a new documents bundle whose identifier is id. An optional docs keyword argument is accepted: a list of document references that pre-populates the bundle's items.
  • fetch_documents_bundle(id) — returns a bundle object that supports item access by key — the "items" key in particular, which yields the ordered list of the document references currently in the bundle.

An exceptions module is available as well, containing the exception classes exceptions.DoesNotExist and exceptions.AlreadyExists.

Behavior Requirements

The mapping returned by make_services() must contain a new command registered under the key "add_document_to_documents_bundle". The command must be a callable, retrievable via the registry's .get(...) method as well as via item access.

Two keyword arguments must be accepted by the command:

  • id — the identifier of the documents bundle being targeted.
  • doc — the document reference that is to be added to the bundle.

Signature (of the callable): add_document_to_documents_bundle(id, doc)

Behavior:

  1. Successful addition. If a bundle with the given id exists and doc is not already present in that bundle's items, doc is appended to the end of the bundle's item list. Once the call has been made, fetching the bundle and reading its "items" key must return the list of document references in insertion order. When multiple documents are added in sequence, their order of insertion must be preserved.

  2. Bundle does not exist. When no bundle exists for the given id, calling the command must raise exceptions.DoesNotExist.

  3. Duplicate document. When the given doc is already present in the target bundle's items, calling the command must raise exceptions.AlreadyExists. The items of the bundle must remain unchanged.

Remarks
  • The "items" value that fetch_documents_bundle returns must be an ordered list of the document references that have been added (whether through the docs argument of create_documents_bundle or through this new command).
  • Nothing meaningful is returned by the command; the effect of calling it is on the stored bundle state.
03 Adding the insert_document_to_documents_bundle Service Command 456 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Adding the insert_document_to_documents_bundle Service Command

Overview

This task introduces a new service command, insert_document_to_documents_bundle, into the services registry. The command's job is to insert a document reference into a documents bundle at a specified position within the bundle's ordered list of items.

Service Registration

Under the key insert_document_to_documents_bundle, the services registry (the object returned by the existing make_services() factory) must expose a new callable command. Retrieval must work both via services.get("insert_document_to_documents_bundle") and via services["insert_document_to_documents_bundle"], and the value that is retrieved must not be None and must be callable.

Command Signature

Calls to the command use keyword arguments exclusively:

insert_document_to_documents_bundle(id=<bundle_id>, index=<int>, doc=<document_reference>)
  • id: the identifier of a documents bundle that already exists.
  • index: an integer position at which the document is to be inserted into the bundle's ordered list of item references.
  • doc: the document reference string that is inserted.

Behavior

Successful insertion

If a documents bundle with the supplied id exists:

  • The doc value is inserted at position index in the bundle's ordered list of items.
  • Standard list positional insertion semantics apply:
    • When the target list is empty, the document is placed as its single element regardless of the numeric index value (e.g. an index larger than the current length appends the document at the end).
    • Inserting at index 0 puts the document at the front and shifts existing items toward the end.
    • When the index is greater than or equal to the current number of items, the document is appended at the end.
  • The change persists, so that fetching the same bundle again reflects the updated ordering.

The bundle's items can be read back using the existing fetch_documents_bundle service command, invoked as fetch_documents_bundle(id=<bundle_id>), which returns a mapping whose "items" key holds the ordered list of document references.

Bundle does not exist

When there is no documents bundle for the given id, the command must raise exceptions.DoesNotExist (this exception comes from the existing exceptions module that the other bundle commands use). This check applies regardless of the supplied index and doc values.

Document already present

If the given doc is already among the bundle's items, the command must raise exceptions.AlreadyExists, and the bundle must not be modified. This holds for any index value provided.

Supporting Context (existing behavior relied upon)

  • Calling create_documents_bundle(id=<bundle_id>) creates a new, empty documents bundle.
  • Calling create_documents_bundle(id=<bundle_id>, docs=[...]) creates a documents bundle that comes pre-populated with the given ordered list of document references.
  • fetch_documents_bundle(id=<bundle_id>) returns the bundle as a mapping that contains an "items" key holding the ordered list of document references.

The new command must integrate with the same bundle storage/retrieval mechanism that these existing commands use.

04 DocumentsBundleStore Implementation 768 words · rewritten by GPT-5.6-sol, reworded by GLM-5.3-Flash

Task Specification: DocumentsBundleStore Implementation

Summary

Build a storage adapter class DocumentsBundleStore that persists and fetches DocumentsBundle domain objects by way of a MongoDB-style collection. The adapter wraps a collection provided at construction time and maps collection operations onto store-level behavior, including the domain exceptions that are required.

Importable Modules and Public API

These importable module paths and public names must exist:

  • documentstore.adapters must expose DocumentsBundleStore.
  • documentstore.domain must expose DocumentsBundle.
  • documentstore.exceptions must expose AlreadyExists and DoesNotExist.

Domain Object: documentstore.domain.DocumentsBundle

DocumentsBundle models a bundle of documents and supplies the domain object that the store consumes and returns.

Constructing a Bundle

These forms must be supported:

  • DocumentsBundle(id="<some-id>") builds a bundle from an identifier string.
  • DocumentsBundle(manifest={...}) builds a bundle from a manifest dictionary that already exists. The manifest's contents are accepted with no schema validation and are preserved as supplied.
Attributes and Methods
  • .manifest is the bundle's dictionary representation.
    • When a bundle is built with id="X", its manifest contains an "id" key whose value is "X", and it may also contain additional keys.
    • When a bundle is built with an explicit manifest, all supplied keys and values are retained, including both "_id" and "id" whenever both are present, and even when their values differ.
  • .id() returns the bundle's logical identifier, which comes from the manifest's "id" field. To illustrate, a bundle built with manifest={"_id": "1", "id": "0034-8910-rsp-48-2"} returns "0034-8910-rsp-48-2" from .id(). The storage identifier "_id" does not take precedence over this logical identifier.

Exceptions: documentstore.exceptions

  • AlreadyExists is raised when an attempt is made to add a bundle whose storage identifier is already being used.
  • DoesNotExist is raised when a bundle that was requested cannot be found, or when an update matches no stored bundle.

The documentstore.adapters.DocumentsBundleStore Adapter

Constructing the Store

DocumentsBundleStore(collection) accepts a single MongoDB-style collection object, and the store makes use of that object's insert_one, find_one, and replace_one methods.

Preparing the Storage Identifier

For both add and update, the document is prepared from bundle.manifest following this rule:

  1. If the manifest's "_id" value is truthy, that value is preserved unchanged. This also holds when "_id" differs from the logical "id" that bundle.id() returns.
  2. If "_id" is absent, or its value is falsy, it is set to bundle.id().

As a result, manifest={"_id": "1", "id": "0034-8910-rsp-48-2"} is persisted with "_id": "1", whereas a bundle built with only id="0034-8910-rsp-48-2" is persisted with "_id": "0034-8910-rsp-48-2". Other manifest keys and values must stay unchanged.

The add(bundle) Method

Save a new bundle.

  • Prepare the document with the storage identifier rule given above.
  • Call collection.insert_one(document) exactly once, passing it the prepared document.
  • Should insert_one raise pymongo.errors.DuplicateKeyError, convert it into documentstore.exceptions.AlreadyExists.

Examples of the document handed to insert_one:

  • For a bundle built with id="0034-8910-rsp-48-2", "_id": "0034-8910-rsp-48-2" is added to its manifest representation.
  • A bundle built with manifest={"_id": "1", "id": "0034-8910-rsp-48-2"} is inserted with "_id": "1"; the existing storage identifier must not be overwritten by bundle.id().
The fetch(id) Method

Fetch a bundle via its storage identifier.

  • Call collection.find_one({"_id": id}) exactly once, passing the supplied identifier.
  • Whenever find_one returns None, raise documentstore.exceptions.DoesNotExist.
  • Otherwise, return a DocumentsBundle built from the manifest dictionary that was returned. All keys and values in the returned manifest, "_id" and "id" included, must be preserved. The .id() of the returned bundle follows the domain rule, and consequently mirrors the logical "id" value in the manifest.

As an example, when the collection returns {"_id": "1", "id": "0034-8910-rsp-48-2"}, the bundle that results has a manifest equal to the returned dictionary, and .id() returns "0034-8910-rsp-48-2".

The update(bundle) Method

Replace a bundle that already exists in storage.

  • Prepare the replacement document with the same storage identifier rule that add follows.
  • Call collection.replace_one({"_id": document["_id"]}, document) exactly once. The same prepared storage identifier must be used in the filter and in the replacement document.
  • When the object that replace_one returns has matched_count == 0, raise documentstore.exceptions.DoesNotExist.

Specifically:

  • For a bundle built with id="0034-8910-rsp-48-2" and no existing "_id", "0034-8910-rsp-48-2" is used as "_id" in both the filter and the replacement document.
  • For manifest={"_id": "1", "id": "0034-8910-rsp-48-2"}, call replace_one using the filter {"_id": "1"}, and retain "_id": "1" in the replacement document.

Contract of the Supplied Collection

The collection given to the store provides:

  • insert_one(document), which may raise pymongo.errors.DuplicateKeyError;
  • find_one(filter), which returns either a manifest dictionary or None; and
  • replace_one(filter, document), which returns an object that carries a matched_count attribute.

pymongo is available, and pymongo.errors.DuplicateKeyError must be handled in the way described above.

05 Rework the persistence-layer interfaces and the MongoDB adapters so that they are organized around one shared storage abstraction, DataStore. 859 words · rewritten by GPT-5.6-sol, reworded by GLM-5.3-Flash

Specification of the Task

Overview

Rework the persistence-layer interfaces and the MongoDB adapters so that they are organized around one shared storage abstraction, DataStore. Document stores and documents-bundle stores must expose the same operations and the same persistence behavior; the only behavioral difference between them is the domain class materialized by fetch.

Public Interface Provided by documentstore.interfaces

Supply an importable abstract base class called DataStore that offers the following public methods:

class DataStore(abc.ABC):
    @abc.abstractmethod
    def add(self, data): ...

    @abc.abstractmethod
    def update(self, data): ...

    @abc.abstractmethod
    def fetch(self, id): ...

The methods are generic over the domain object being stored rather than being specific to documents or bundles. Concrete in-memory or database-backed stores must be able to subclass DataStore. A concrete implementation must be able to choose the domain class it materializes from a fetched manifest, for instance through a class-level DomainClass attribute.

The abstract interfaces DocumentStore and DocumentsBundleStore, which were formerly separate, are consolidated into this one interface; there must not be separate per-domain abstract contracts. The existing session access points for documents and documents bundles keep representing stores that implement the DataStore contract.

Concrete Adapters (documentstore.adapters)

Make the following two concrete collection-backed classes available:

  • documentstore.adapters.DocumentStore
  • documentstore.adapters.DocumentsBundleStore

The constructor of each class accepts one positional argument, a MongoDB collection-like object:

store = adapters.DocumentStore(collection)
store = adapters.DocumentsBundleStore(collection)

Both adapters must implement the common documentstore.interfaces.DataStore contract and share the same persistence behavior. The only difference between them is the domain type returned by fetch:

  • DocumentStore materializes documentstore.domain.Document.
  • DocumentsBundleStore materializes documentstore.domain.DocumentsBundle.

The collection that is supplied is expected to provide insert_one, replace_one, and find_one.

Common Adapter Behavior

The requirements in this section apply identically to DocumentStore and DocumentsBundleStore.

Normalization of the storage identifier

Within add and update, take the dictionary exposed by data.manifest and determine the storage identifier to be persisted as follows:

  • If manifest.get("_id") is truthy, keep that value unchanged, even when it differs from data.id().
  • If "_id" is not present or its value is falsy, assign data.id() to manifest["_id"].

That means the MongoDB storage identifier (_id) and the domain object's logical identifier (id, as returned by data.id()) are allowed to differ. The remaining manifest content must be preserved.

For instance, an object created from:

{"_id": "1", "id": "0034-8910-rsp-48-2"}

must keep using "1" as its storage identifier. By contrast, when an object's manifest has no usable _id, the object must be persisted with _id equal to data.id().

add(data)
  1. Normalize the manifest's storage identifier as prescribed by the rule above.
  2. Call collection.insert_one(manifest), passing that manifest as the sole positional argument.
  3. If insert_one raises pymongo.errors.DuplicateKeyError, translate it and raise documentstore.exceptions.AlreadyExists in its place.

In particular, a truthy _id that is already present must reach insert_one unchanged; it must not be overwritten merely because it differs from data.id().

update(data)

  1. Normalize the manifest's storage identifier as prescribed by the rule above.

  2. Call collection.replace_one, passing exactly these two positional arguments:

    {"_id": manifest["_id"]}, manifest

    The filter and the replacement must therefore be based on the same storage identifier.

  3. Examine the result returned by replace_one. If result.matched_count == 0, raise documentstore.exceptions.DoesNotExist.

Examples:

  • Given a manifest {"_id": "1", "id": "0034-8910-rsp-48-2"}, keep the divergent _id and call:

    collection.replace_one(
    {"_id": "1"},
    {"_id": "1", "id": "0034-8910-rsp-48-2"},
)

  • When an object is created with only id="0034-8910-rsp-48-2", that value becomes the _id, and replace_one is called with {"_id": "0034-8910-rsp-48-2"} as the filter and the normalized manifest as the replacement.

fetch(id)

  1. Call collection.find_one({"_id": id}).

  2. If find_one returns a falsy value, None included, raise documentstore.exceptions.DoesNotExist.

  3. Otherwise return an instance of the adapter's domain class, constructed in the following way:

    DomainClass(manifest=found_manifest)

DocumentStore.fetch must return a Document, and DocumentsBundleStore.fetch must return a DocumentsBundle. The manifest of the returned object must have the same content as the dictionary that was found, and the object's existing domain API, including .id(), must continue to function from that manifest.

Exceptions

The exception classes to use are the existing ones from documentstore.exceptions:

  • AlreadyExists when an add is rejected because MongoDB reports a duplicate key.
  • DoesNotExist for a fetch that finds no truthy manifest, or for an update that matches no existing record.

These exception semantics must hold uniformly across both concrete adapters.

Compatibility with Existing Domain Objects

The adapters must remain interoperable with the existing documentstore.domain.Document and documentstore.domain.DocumentsBundle classes. Both classes are constructible with either id="..." or manifest={...} and expose .id() and .manifest. Their manifest and versioning behavior lies outside this refactor and must remain unchanged.

All existing non-store APIs stay unaffected. The refactor is limited to consolidating the store interface and to making the two collection-backed stores follow the uniform behavior specified above.

Constraints

  • There exists one shared abstract datastore interface — not separate document and bundle interfaces.
  • The add, update, and fetch semantics of both concrete adapters are identical.
  • The concrete adapters have shared storage behavior and vary only in the domain class materialized during fetch.
  • For both add and update, a truthy storage _id already present in a manifest always takes precedence over data.id().
06 Versioned BundleManifest Metadata 896 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Versioned BundleManifest Metadata

Summary

Inside the documentstore.domain module, change how bundle manifests store their metadata, so that the metadata values they hold are versioned. A single value per metadata key gives way to a chronological list of (timestamp, value) pairs, in which every entry records a value that was set plus the instant it was set.

Module and Source of Time

The work happens in the module documentstore.domain. Timestamps must be referenced by this module through a module-level datetime (the standard library datetime module), with the current UTC time obtained via datetime.utcnow(). In terms of format, a timestamp must be an ISO-8601 string that contains microseconds and a trailing Z, e.g. "2018-08-05T22:33:49.795151Z" (matching datetime.datetime(2018, 8, 5, 22, 33, 49, 795151)).

BundleManifest.set_metadata

Signature:

BundleManifest.set_metadata(bundle_manifest, name, value, now=<callable>)
  • bundle_manifest is a manifest dict (of the kind produced by the existing bundle-creation logic; it holds at least the keys "metadata", "created", and "updated").
  • name is the metadata key, a string.
  • value is the value to be stored, a string.
  • now is an optional keyword-only callable; calling it returns the current timestamp string. If it is not given, its default must be to produce the current UTC time as specified above (i.e. based on datetime.utcnow()).

Behavior:

  • A (now(), value) pair is appended to the list held under bundle_manifest["metadata"][name]. When name has no entry yet, a list is created whose first element is this pair.
  • Pairs stored earlier for the same name remain in place; setting a new value for an existing key does not overwrite or remove those earlier pairs — the new pair is appended. In the resulting list, entries appear in insertion order, oldest first.
  • When metadata is set for a different key, a new key is added to the metadata mapping and the other keys are unaffected. How many keys metadata contains reflects how many distinct names have been set.
  • With every call, the manifest's "updated" field is set to a value strictly greater than its previous value (a later timestamp), to reflect the modification.
  • The resulting manifest is what the function returns (the tests use the return value; handle this the way the other manifest-mutating operations in this codebase are handled, i.e. by returning the manifest).

How the stored structure looks once the same key has been set twice:

{
    "publication_year": [
        ("2018-08-05T22:33:49.795151Z", "2018"),
        ("2018-08-05T22:34:07.795151Z", "2019"),
    ]
}

BundleManifest.get_metadata

Signature:

BundleManifest.get_metadata(bundle_manifest, name, default="")

Behavior:

  • The value — not the pair — that belongs to the entry most recently set for name is what gets returned; in other words, the value carried by the last (timestamp, value) pair in that key's list.
  • Should name be absent from the manifest's metadata, default is returned.
  • The keyword argument default is optional, and its default is the empty string "". If the key is missing and a default has been supplied, the supplied value is what gets returned instead.

Metadata properties of DocumentsBundle

Metadata is exposed by the DocumentsBundle class as the attributes publication_year, volume, number, and supplement; these must keep working:

  • A value assigned to any of these attributes is stored in the manifest through the versioned set_metadata mechanism, so that documents_bundle.manifest["metadata"][<name>] ends up as a list of (timestamp, value) pairs. Given a current UTC time of datetime.datetime(2018, 8, 5, 22, 33, 49, 795151), the assignment documents_bundle.volume = "25" yields:

    documents_bundle.manifest["metadata"]["volume"] == [("2018-08-05T22:33:49.795151Z", "25")]

  • Reading any of these attributes returns the value stored most recently (via get_metadata), as a string. The value-normalization behavior that already exists (e.g. converting assigned values to strings) must be preserved.

Effect on services (fetch/update documents bundle)

Because they operate on manifests, the service-layer commands that fetch and update bundle metadata must reflect the new storage format:

  • A bundle that is created with a metadata mapping and then fetched yields a "metadata" dict in which the entry for each recognized key is a list of (timestamp, value) pairs. If the current UTC time is mocked to datetime.datetime(2018, 8, 5, 22, 33, 49, 795151):

    {
    "publication_year": [("2018-08-05T22:33:49.795151Z", "2018")],
    "volume": [("2018-08-05T22:33:49.795151Z", "2")],
}

  • Metadata keys that are unknown/unrecognized and supplied at creation are ignored; the stored metadata never contains them.

  • When a bundle's metadata is updated with a new value for an existing recognized key, a new (timestamp, value) pair is appended to that key's list — the prior history is not replaced. As an example, creating with publication_year="2018", volume="2" and then updating with publication_year="2019" yields:

    {
    "publication_year": [
        ("2018-08-05T22:33:49.795151Z", "2018"),
        ("2018-08-05T22:33:49.795151Z", "2019"),
    ],
    "volume": [("2018-08-05T22:33:49.795151Z", "2")],
}

  • An update performed with an unrecognized key leaves the stored metadata unchanged.

  • Assigning an empty string to a recognized key is a valid update: a (timestamp, "") pair gets appended. For instance, after creating with publication_year="2018", volume="2" and updating with volume="":

    {
    "publication_year": [("2018-08-05T22:33:49.795151Z", "2018")],
    "volume": [
        ("2018-08-05T22:33:49.795151Z", "2"),
        ("2018-08-05T22:33:49.795151Z", ""),
    ],
}

Notes

  • Whatever manifest behavior already exists and is not mentioned here (manifest generation on init, created/updated fields holding equal values at creation, item-management operations, and the string conversion applied to assigned metadata values) must stay intact.
  • Since the module-level datetime reference is what produces the timestamps, the current UTC time can be controlled externally; ensure the current-time source flows through datetime.utcnow().
07 The work consists of two related changes to the domain module (domain) of an existing codebase 547 words · source specification, reworded by GLM-5.3-Flash

Overview

The work consists of two related changes to the domain module (domain) of an existing codebase:

  1. Change the wording of several error messages raised by bundle item operations.
  2. Introduce a new Journal class.

Part 1: Changes to the bundle item error messages

Inside the domain module, a BundleManifest class and a DocumentsBundle class manage a collection of "items" (documents). Certain operations raise exceptions carrying descriptive messages when they fail. The message format must be updated as set out below.

In all cases below, {uri} stands for the item identifier string that was passed to the operation.

Adding an item that is already present

Whenever there is an attempt to add an item that is already present in the bundle, an exceptions.AlreadyExists error must be raised with the message:

cannot add item "{uri}" in bundle: the item already exists

This applies to both of the following:

  • domain.BundleManifest.add_item(bundle, uri)
  • DocumentsBundle.add_document(uri)
Inserting an item that is already present

Whenever there is an attempt to insert an item (at a given index) that is already present in the bundle, an exceptions.AlreadyExists error must be raised with the message:

cannot insert item "{uri}" in bundle: the item already exists

This applies to both of the following:

  • domain.BundleManifest.insert_item(bundle, index, uri)
  • DocumentsBundle.insert_document(index, uri)
Removing an item that is not present

Whenever there is an attempt to remove an item that is not present in the bundle, an exceptions.DoesNotExist error must be raised with the message:

cannot remove item "{uri}" from bundle: the item does not exist

This applies to both of the following:

  • domain.BundleManifest.remove_item(bundle, uri)

20 Introduce support for an "online submission URL" field on the Journal class, which resides in the domain module. 256 words · source specification, reworded by GLM-5.3-Flash

Task Description

Goal

Introduce support for an "online submission URL" field on the Journal class, which resides in the domain module.

Public API

A new property named online_submission_url must be exposed by the domain.Journal class:

  • Getter (journal.online_submission_url): returns the online submission URL's current value as a string.
  • Setter (journal.online_submission_url = value): assigns a new online submission URL string to the journal.

Behavior Requirements

Value by default

If a Journal has been created and no online submission URL has been set, accessing online_submission_url must return an empty string ("").

Assigning a value

Once a URL string has been assigned through the setter:

  • Afterwards, reading online_submission_url must return exactly the string that was assigned.
  • The assignment must be recorded in the journal's manifest structure, under manifest["metadata"]["online_submission_url"], as a list of entries. Every entry is a 2-tuple of (timestamp, value), where:
    • timestamp is an ISO-8601 formatted UTC timestamp string (e.g. "2018-08-05T22:33:49.795151Z") that marks when the assignment took place.
    • value is the URL string that was assigned.
  • After a single assignment, this list must contain exactly one entry that corresponds to that assignment.

This field follows the same versioned-metadata pattern that other Journal metadata fields already use (a list of timestamped values in the manifest, with the getter returning the most current value).

Notes

  • The Journal class receives an id keyword argument at construction time (e.g. domain.Journal(id="0034-8910-rsp-48-2")).
  • This new field must not interfere with the existing behavior of Journal or with other metadata fields.
