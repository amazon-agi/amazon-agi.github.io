Specification of the Task

Add two graph-control utilities to the znflow package, keep them compatible with all supported Node attribute styles, and update the package version.

Background

znflow.DiGraph serves as a context manager for building computational graphs. Within a with znflow.DiGraph() as graph: block, Node instances become associated with the active graph via _graph_. Once a node's construction has finished, reading one of its non-protected public attributes in that context normally returns a znflow.Connection standing for that node and attribute instead of returning the concrete value that ordinary Python attribute lookup would produce. When no graph context is active, _graph_ is None and such reads return their ordinary values.

The new APIs must make it possible to suspend that graph-aware behavior, either temporarily or for one attribute lookup, without changing normal graph behavior elsewhere.

Requirements

1. Package version

Change the package version such that:

znflow.__version__ == "0.1.2"
2. The disable_graph context manager

Supply a context manager at znflow.base.disable_graph that can be called with no arguments:

with znflow.base.disable_graph():
    ...

It must behave as follows:

  • For as long as the block is running, ZnFlow must behave as though there is no active graph. Specifically, every node's _graph_ attribute must evaluate to None, even when the block is entered from inside an active DiGraph context.
  • It must also be valid to use when no graph is active; within the block, _graph_ remains None.
  • When the block is left, the exact graph state that was active immediately before entry must be restored. So a block entered inside a DiGraph restores that graph, whereas a block entered without one restores None.
  • Restoration must take place for normal and exceptional exits and must compose correctly with nested uses of disable_graph.
  • After restoration, the surrounding DiGraph context must continue to operate normally. Once that graph context itself exits, nodes report _graph_ as None again.

As an example, a node created in an active graph normally reports that graph through _graph_; inside disable_graph() the same node reports None, it reports the graph again after the inner block, and it reports None after the outer graph block ends.

3. get_attribute

Make the same callable available through both of these public locations:

  • znflow.base.get_attribute
  • znflow.get_attribute

The supported form of the call is:

get_attribute(instance, name, default=<sentinel>)

where the sentinel that stands for an omitted default is distinct from every user-supplied value, including None.

get_attribute must adhere to these rules:

  • Carry out normal Python attribute lookup for name while graph tracking is temporarily disabled. Properties, descriptor getters, instance attributes, dataclass-style fields, and inherited or plain class attributes must keep their normal lookup semantics.
  • If graph-aware access would otherwise synthesize a znflow.Connection, return the underlying ordinary attribute value instead. This bypass covers only the synthetic wrapping caused by the active graph; the function is not required to resolve a Connection that is itself the value genuinely stored in the attribute.
  • Outside a graph context it works the same way, returning the ordinary value.
  • Only this lookup is affected. The attribute must not be modified, and a later direct read in an active graph must still return a znflow.Connection as usual.
  • After the lookup, restore the previously active graph state, including when attribute lookup raises an exception.
  • If the attribute is missing and default was omitted, raise AttributeError.
  • If the attribute is missing and default was supplied, return that exact default. Supplying None as the default is valid, and it must not be confused with omission.

It follows that the top-level form must support both znflow.get_attribute(obj, name) and znflow.get_attribute(obj, name, default) directly.

4. Resolving connections during graph execution

While it prepares a node for execution, DiGraph.run() must continue to resolve Connection objects found in the node's public attribute values so that run() receives concrete dependency results. The recursive handling of supported container values that already exists must remain intact.

Writing a prepared value back to the node is conditional:

  • Assign the value back only if preparing that particular attribute actually found and resolved at least one Connection, so that the attribute's value was genuinely updated by connection resolution.
  • When no Connection was resolved for an attribute, do not assign the value back merely because the attribute was inspected or because traversal produced an equivalent value.
  • This holds for plain values as well as for values exposed by properties or descriptors. In particular, executing a graph must not invoke a property setter or descriptor __set__ again with the value its getter produced when that value needed no connection resolution.
  • Before the node's run() method is invoked, attributes that do contain connections must still be updated with their resolved values.

For setters and descriptors that transform values or have side effects, this conditional write-back matters externally: graph execution must not transform an already prepared value a second time merely by reading and reassigning it.

Requirements for compatibility

Node subclasses must continue to work when their attributes come from any of the following:

  • ordinary instance attributes;
  • dataclass-style fields;
  • properties with getters and setters;
  • custom descriptors; or
  • inherited or plain class attributes.

Specifically:

  • A property setter that runs while a graph is active may call znflow.get_attribute(self, field_name) to obtain the concrete value of another attribute on the same node. Arithmetic that uses the returned value must work rather than receiving a graph-generated Connection.
  • After the graph is built and graph.run() is called, the results must reflect the arithmetic that such a setter performed. The connection-resolution step at execution time must not re-run a transforming setter when its property value contained no connection.
  • In the same way, a descriptor's __set__ method may call znflow.get_attribute(instance, field_name) and receive the concrete value, including when that field is supplied as a plain class attribute.
  • Inside a graph, direct attribute access stays graph-aware. When a setter or descriptor reads another public node attribute directly, it may receive a Connection; arithmetic between that connection and an ordinary value may raise TypeError. The new helper is the opt-in means of bypassing that behavior, and such direct-access errors do not need to be suppressed.

  • znflow.nodify — a decorator that turns a plain function into a callable graph node factory.

The nodify decorator

Applying znflow.nodify to a function returns a callable that behaves as follows:

  1. Invoked outside any graph context: it invokes the wrapped function directly and returns its normal return value. As an example, a function decorated with nodify that adds two numbers returns the numeric sum.

    • Invoking it with a single positional argument raises TypeError.
    • Invoking it with only one of the parameters supplied by keyword (leaving the other unfilled) raises TypeError.
    • Invoking it with more positional/keyword arguments than the signature accepts (or duplicating a parameter both positionally and by keyword) raises TypeError.

  • Make the instance retrievable through graph.nodes[node.uuid]["value"] (returning the instance itself).

Task Specification: __getitem__ for Node Attributes and FunctionFutures

Goal of the Task

Support for indexing/slicing through __getitem__ is to be added to znflow, the graph-computation library. Users must have the ability to apply subscript operations (for example [::2], [:5], [5:]) to results coming from nodified functions as well as to attributes of Node instances, both inside an active graph context and outside one.

Pre-existing Functionality (assumed to be in place)

The following is already part of the znflow package:

  • znflow.nodify — a decorator that wraps a plain function. A call made outside any active graph context simply executes as usual and returns the real result. A call made inside a znflow.DiGraph context, by contrast, returns a znflow.FunctionFuture placeholder, which gets added to the graph and is evaluated at the time the graph runs.
  • znflow.Node — a base class from which nodes derive; its subclasses are typically dataclasses equipped with a run() method. Instantiating one inside a graph context causes the instance to be tracked as a node of that graph.
  • znflow.DiGraph — a container that doubles as a context manager. len(graph) (the count of nodes it holds) is supported, and so is its run() method, which evaluates all nodes the graph contains.
  • znflow.FunctionFuture — the placeholder object that a nodified function returns while working within a graph. After graph.run() has taken place, its computed value can be read from a .result attribute.
  • znflow.Connection — an object that points at another object (the object being referenced is exposed through an .instance attribute) and also carries the logic for resolving it in the graph. Once graph.run() has happened, its resolved value can be read from a .result attribute.

Required Functionality

1. Applying a Subscript to a FunctionFuture

The subscript operator future[item] must be supported by a FunctionFuture, with item denoting any valid index/slice object.

  • With no graph context active: the nodified function get_list() runs immediately, returning a real object; putting a subscript on what comes back then behaves like ordinary Python subscripting on that object. (This happens automatically, since outside a graph the nodified call returns the real result.)

  • With a graph context active: a subscript applied to a FunctionFuture must return a znflow.Connection. The Connection that comes back must have the original FunctionFuture as the object referenced by its .instance (i.e. connection.instance is the_function_future). The subscript must not add a new node to the graph — only the actual nodes (the function future and any nodes that consume it) are reflected in the graph's node count, whereas subscript connections are not.

    After graph.run():

    • The full computed value is what the FunctionFuture's .result equals.
    • The Connection produced by the subscript exposes, through its .result, the value you get by applying the given index/slice to the future's full result.
2. Applying a Subscript to a Node attribute

When a graph context is active, reading an attribute of a Node instance yields a Connection that points at the attribute. It must be possible to subscript that attribute as well.

  • With no graph context active: the real attribute value is what attribute access returns; a subscript then behaves like ordinary Python subscripting on it.

  • With a graph context active: take a Node instance x — evaluating x.data[item] must return a znflow.Connection. As its .instance, this Connection must reference the Connection standing for the attribute access x.data; that inner connection, for its part, references the node instance x (i.e. outer.instance.instance is x). The subscript must not add a new node to the graph.

    After graph.run():

    • The attribute on the node contains its full computed value.
    • The Connection produced by the subscript exposes, through its .result, the value arrived at by applying the given index/slice to the full attribute value.
3. Supplying subscripted results to other nodes

Within the graph, a subscripted result (a Connection) may serve as an argument to another nodified function.

  • It must work to pass a nodified function subscripted FunctionFuture results as well as subscripted Node attributes as arguments. Each subscript argument is resolved to the sliced value before the consuming function executes — this happens when the graph runs — and the resolved values are what the consuming function receives.

  • Outside a graph, the ordinary Python result comes out of the equivalent direct calls (subscripting real values and passing them to the plain function).

4. Chaining (stacking) subscripts

A Connection that itself came out of subscripting must in turn support being subscripted, and the composition must behave correctly.

  • Inside a graph context: if x = node_a[::2] yields a Connection, then y = x[::2] must yield a Connection too. Once the graph runs, y.result is equal to the second slice applied to x.result, where x.result is itself the first slice over node_a's full result.

  • A node is added to the graph by neither the first nor the second subscript; the only things counting toward len(graph) are the genuine nodes (the source function future and any consuming node).

Public API

Beyond what already exists, no new import names are required. Subscript (__getitem__) capability must be added by the engineer such that:

  • future[item] must be supported by instances of znflow.FunctionFuture, with a znflow.Connection being returned when inside a graph context.
  • connection[item] must be supported by the Connection object obtained through attribute access on a Node, with another znflow.Connection being returned.
  • On znflow.Connection, .instance is exposed (the referenced object); after graph.run(), .result (the resolved, sliced value) is exposed as well.
  • After graph.run(), .result is exposed on znflow.FunctionFuture.

Edge Cases and Constraints

  • Subscript operations carried out within a graph context are lazy: Connection objects are what get created, and evaluation happens only during graph.run().
  • The node count of the graph must never be increased by subscript operations.
  • The index/slice supplied to [...] may be any slice object (e.g. [::2], [:5], [5:]); during graph execution, the stored index/slice is applied verbatim to the resolved full value.
  • It must be allowed to chain subscripts, and the slices must be composed in application order.

Outside the Scope

Putting __getitem__ directly onto a Node subclass (for instance subscripting a Node instance itself, as Compute()[::2]) is not part of this task, and it need not be supported.

  • not try to assign a resolved or converted value to the property; and
  • not add any dependency edge because of the property.

This goes beyond catching or suppressing an assignment error once the property has been processed. The property must be omitted before the automatic resolution process reads its value.

This exclusion holds regardless of the order in which attributes are traversed and of whether the writable backing attribute is visited before or after the read-only property. Explicit access by user code remains governed by the normal attribute and get_attribute semantics; what is required is that the graph's own automatic passes do not evaluate the property.

  • the edge's upstream attribute metadata must keep the normal connection semantics, such as None for a direct node reference or "result" for a nodify result.

When the writable attribute contains multiple upstream values in a list or another supported nested container, the same requirements apply. Read-only aliases must create no extra edges.

Ordinary Methods

A node may also define ordinary methods, among them methods that raise NotImplementedError when called. Merely having these methods must not affect graph construction, finalization, resolution, or execution. They are invoked only when user code explicitly calls them.

  • Normal connection discovery and concrete-value resolution for writable attributes must be preserved.

  • The key of each entry is the uuid of the corresponding input node.
  • If attribute is not given, each value is the corresponding input node itself.
  • Passing attribute="outs" together with return_dict_attr="uuid" must be accepted, and a dictionary that contains one entry per input node must be returned.

The inputs may be supplied either as separate positional arguments or as a single list.

Error behavior
  • If duplicate dictionary keys would result from the combined inputs, raise ValueError rather than silently overwriting entries. This includes the case of a single list that contains the same graph nodes more than once.
  • Outside a znflow.DiGraph context, the function must raise TypeError when return_dict_attr="uuid" is requested for ordinary values produced by direct function execution.
