02 You must extend the combinator utilities so that a field typed as typing.Any is treated as a valid, first-class field type. 469 words · source specification

You must extend the combinator utilities so that a field typed as typing.Any is treated as a valid, first-class field type. This affects type validation and description/number generation for combinators.

Context

The codebase defines dataclasses that represent TL (Type Language) combinators. Each such dataclass has an inner Meta class providing at least a name (string) and order (tuple of field names in serialization order). Fields are annotated with types, some of which are TL-specific type aliases (e.g. long, int128, string, container types like Vector/List, forward references to other registered constructors, etc.).

The utility functions live in a module importable as it currently is (the same module that exposes the functions named below). You must modify the existing behavior of these functions; do not rename or relocate them.

Required Behavior Changes

1. is_good_for_combinator(type_) -> bool

This predicate determines whether a given type annotation is acceptable as a combinator field type.

  • When called with typing.Any, it must return True.
  • All previously-accepted types must continue to be accepted; this change only adds Any to the set of acceptable types.
2. is_valid_combinator(combinator, constructors=...)

Validation of a combinator must succeed (not raise) when one of its fields is annotated with typing.Any.

  • Concretely, given a dataclass whose fields include one annotated as Any (alongside other fields using normal TL types), and given the list of known constructors, this function must complete without raising.
  • The existing InvalidCombinator failure behavior for genuinely invalid combinators is unchanged.
3. is_valid_constructor(constructor, constructors=...)

A constructor whose associated combinator contains an Any-typed field must be accepted (not raise).

  • The existing InvalidConstructor failure behavior for invalid inputs is unchanged.
4. build_combinator_description(combinator, constructor, for_type_number=...) -> str

When rendering a combinator's textual description, a field annotated with typing.Any must be rendered with the type name Object.

  • The description format is: the combinator name, followed by each field rendered as field_name:FieldType separated by single spaces, followed by = and the constructor/type name.
  • For an Any-typed field, the FieldType portion is the literal string Object.

Example: a combinator named rpc_result with fields req_msg_id (type long) and result (type Any), whose constructor type name is RpcResult, must produce:

rpc_result req_msg_id:long result:Object = RpcResult
5. get_combinator_number(combinator, constructor) -> int

The combinator number (a CRC32-style 32-bit integer computed from the combinator's textual description) must be computed using the description produced by build_combinator_description, meaning an Any-typed field contributes as Object.

  • For a combinator named rpc_result with fields req_msg_id:long and result:Object and type name RpcResult, the resulting number must be 0xf35c6d01.

Constraints

  • All existing functionality for non-Any types must remain intact and unchanged.
  • The only new capability is treating typing.Any as a valid field type that renders as Object in descriptions and participates normally in number computation.
