02 You must extend the combinator utilities 597 words · source specification, reworded by GLM-5.3-Flash

Task Description

You must extend the combinator utilities; the effect of the extension is that a field typed as typing.Any counts as a valid, first-class field type. Type validation is one area touched by this, and so is the generation of descriptions and numbers for combinators.

Background

TL (Type Language) combinators are represented in the codebase by dataclasses. Every one of these dataclasses carries an inner Meta class that provides at least a name (string) and an order (a tuple of field names in serialization order). Types annotate the fields; some of these annotations are type aliases specific to TL (e.g. long, int128, string), with container types along the lines of Vector/List and forward references to other registered constructors also appearing, among other cases.

A module that can be imported in its present form houses the utility functions (and that module is also the one which exposes the functions named below). What you must modify is the behavior these functions already exhibit; renaming or relocating them is not permitted.

Behavior Changes That Are Required

1. is_good_for_combinator(type_) -> bool

This predicate exists to answer whether a type annotation handed to it is acceptable as the type of a combinator field.

  • A call whose argument is typing.Any must return True.
  • Every type accepted before this change must still be accepted afterward; the only addition made is Any joining the set of acceptable types.
2. is_valid_combinator(combinator, constructors=...)

Validation of a combinator must succeed (not raise) in the case where one of its fields carries a typing.Any annotation.

  • To make this concrete: hand the function a dataclass whose fields include one annotated as Any (beside other fields that use normal TL types) together with the list of known constructors, and it must complete without raising.
  • For combinators that are genuinely invalid, the failure behavior involving InvalidCombinator stays as it is now.
3. is_valid_constructor(constructor, constructors=...)

A constructor must be accepted (not raise) if the combinator associated with it contains a field whose type is Any.

  • For invalid inputs, nothing changes about the existing failure behavior built around InvalidConstructor.
4. build_combinator_description(combinator, constructor, for_type_number=...) -> str

While a combinator's textual description is being rendered, a field whose annotation is typing.Any must be rendered with Object serving as the type name.

  • Structure of the description: first comes the combinator name; next, every field, each rendered as field_name:FieldType, with single spaces as the separators; after the fields, = appears, and then the constructor/type name.
  • Where a field's type is Any, its FieldType piece is the literal string Object.

Example: take a combinator named rpc_result whose fields are req_msg_id (of type long) and result (of type Any) and whose constructor has the type name RpcResult; the required output is:

rpc_result req_msg_id:long result:Object = RpcResult
5. get_combinator_number(combinator, constructor) -> int

The combinator number — a CRC32-style 32-bit integer that is computed from the combinator's textual description — must be obtained by using, as its basis, the description that build_combinator_description produces; put another way, a field typed Any contributes as Object.

  • For the combinator rpc_result, which has the fields req_msg_id:long and result:Object and the type name RpcResult, the number that comes out must be 0xf35c6d01.

Constraints

  • All functionality that already exists for types other than Any must stay intact, with no changes to it.
  • The sole new capability is the treatment of typing.Any as a valid field type — one that renders as Object in descriptions and takes part in number computation as it normally would.
