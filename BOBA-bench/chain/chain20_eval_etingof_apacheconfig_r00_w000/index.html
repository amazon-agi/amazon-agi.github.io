Task Specification: Apache Config Lexer and Parser

Implement a lexer and parser for Apache-style configuration files using PLY (Python Lex-Yacc). The public API must live in two modules: apacheconfig.lexer and apacheconfig.parser.

Module: apacheconfig.lexer

Provide a class ApacheConfigLexer.

  • The constructor takes no required arguments: ApacheConfigLexer().
  • It must expose a method tokenize(text) that accepts a string of configuration text and returns a list of token values (the meaningful string content of each token), in the order they appear in the input.
Tokenization rules

The following describes what token values tokenize must yield:

  • Whitespace only. Input consisting solely of spaces, tabs, \r, and \n produces no tokens (an empty list).

  • Options and values. An option/value pair on a line may be written with the name and value separated by whitespace or by an = (with optional surrounding whitespace). The lexer emits the option name as a token, optionally an = token, and the value as a token.

    • a b → 'a', 'b'
    • a = b → 'a', '=', 'b'
    • a= b, a =b, a=b, a b → the same tokenization as above (with = emitted only when = is present in the source)
    • Double-quoted values have their surrounding quotes stripped: a "b" → 'a', 'b'.

    For example, the following block:

    a b
a = b
a    b
a= b
a =b
a   b
a "b"
a = "b"

    yields the token values: ['a', 'b', 'a', '=', 'b', 'a', 'b', 'a', '=', 'b', 'a', '=', 'b', 'a', 'b', 'a', 'b', 'a', '=', 'b']

  • Open/close tags. A tag block delimiter is written with angle brackets. The token value is the tag content with the enclosing <, </, and > characters removed and leading/trailing whitespace within trimmed to the tag's textual content.

    • <a> followed by </a> → 'a', 'a'
    • A tag containing an expression preserves its inner text: <if a == 1> followed by </if> → 'if a == 1', 'if'

  • Comments. A line beginning with # produces a single comment token whose value is everything on the line following the # (with no stripping of leading spaces in that remainder).

    • # → ''
    • # a → ' a'
    • #a → 'a'
    • # a b → ' a b'
Combined examples

Block with options and comments interspersed:

<a>
#
# a
# a b
</a>

→ ['a', '', ' a', ' a b', 'a']

A block containing multiple option forms:

<a>
a b
a=b
a =  b
a = "b"
a "b"
</a>

→ ['a', 'a', 'b', 'a', '=', 'b', 'a', '=', 'b', 'a', '=', 'b', 'a', 'b', 'a']

Blank lines inside a block are ignored:

<a>


</a>

→ ['a', 'a']

A mixed configuration:

# h
a = b
<a>
  a b
</a>

→ [' h', 'a', '=', 'b', 'a', 'a', 'b', 'a']

Module: apacheconfig.parser

Provide a class ApacheConfigParser.

  • The constructor takes a lexer instance as its first positional argument and an optional keyword argument start naming the grammar start symbol: ApacheConfigParser(lexer, start='...').
  • When start is omitted, the default start symbol must be the full configuration (equivalent to start='config').
  • It must expose a method parse(text) that parses the given configuration text and returns an abstract syntax tree (AST) built from the token stream produced by the supplied lexer.

The start argument selects which grammar rule serves as the entry point. The supported start symbols and their AST outputs are described below.

AST node shapes
  • Option/value: ('option', <name>, <value>), where <name> and <value> are strings. Quoted values are unquoted (quotes removed), and a value containing spaces is preserved as a single string.
  • Comment: ('comment', <text>), where <text> is the content after the # (matching the lexer's comment token value, including any leading space).
  • Block: ('block', <open_tag>, <body>, <close_tag>), where <open_tag> and <close_tag> are the tag content strings and <body> is a list of the block's contained statement nodes (options and/or comments) in order.
Start symbol: statement

Parses a single option/value statement and returns one ('option', name, value) tuple.

  • a b\n → ('option', 'a', 'b')
  • a=b\n → ('option', 'a', 'b')
  • a "b c"\n → ('option', 'a', 'b c')
Start symbol: statements

Parses a sequence of statements (options and comments) and returns a list of the corresponding nodes in order.

For:

a b
a = b
a    b
a= b
a =b
a   b
a "b"
a = "b"

→ [('option', 'a', 'b')] * 8

For:

#
# a
#a
a = "b b"
# a b
a = "b b"

→

[('comment', ''), ('comment', ' a'),
 ('comment', 'a'), ('option', 'a', 'b b'),
 ('comment', ' a b'), ('option', 'a', 'b b')]
Start symbol: block

Parses a single tagged block and returns a ('block', open_tag, body, close_tag) tuple, where body is the list of statements inside.

For:

<a>
  #a
  a = "b b"
  # a b
  a = "b b"
</a>

→

('block', 'a', [('comment', 'a'),
                ('option', 'a', 'b b'),
                ('comment', ' a b'),
                ('option', 'a', 'b b')], 'a')

Tag content may include spaces; the open and close tag strings are preserved verbatim from the lexer (e.g. an open tag <a a> / close tag </a a> yields open and close values 'a a').

Start symbol: config

Parses a whole configuration document and returns a list whose elements are, in source order:

  • Blocks, represented as ('block', open, body, close) tuples.
  • Runs of consecutive non-block statements (options and comments), each such run represented as a list of statement nodes. Consecutive comments/options that are not separated by a block are grouped together into one list; a block terminates the current run.

For:

# a
a = b

<a>
  a = b
</a>
a b
<a a>
a b
</a a>
# a

→

[[('comment', ' a'), ('option', 'a', 'b')],
 ('block', 'a', [('option', 'a', 'b')], 'a'),
 [('option', 'a', 'b')],
 ('block', 'a a', [('option', 'a', 'b')], 'a a'),
 [('comment', ' a')]]

Note that:

  • The leading comment and the option before the first block are grouped into a single list.
  • Each block appears as its own top-level tuple.
  • The single option between the two blocks forms its own one-element list.
  • The trailing comment after the last block forms its own one-element list.
  • Blank lines do not produce nodes and do not split statement runs.
Full-document default behavior

When constructed without an explicit start, parsing a full document behaves as the config start symbol. For example, parsing:

# Nested block test
<cops>
  name stein
  age 25
  color \#000000
</cops>

→

[[('comment', ' Nested block test')],
 ('block', 'cops',
     [('option', 'name', 'stein'),
      ('option', 'age', '25'),
      ('option', 'color', '\\#000000')],
  'cops')]

Here an unquoted value beginning with a backslash-escaped # is preserved verbatim as the value string ('\\#000000' is the two-character-prefixed literal \#000000).

Constraints

  • Both ApacheConfigLexer and ApacheConfigParser must be importable exactly as from apacheconfig.lexer import ApacheConfigLexer and from apacheconfig.parser import ApacheConfigParser.
  • The parser must consume tokens from the lexer instance it is given at construction time.

Task Specification: Config Loader and AST Format Update

Overview

Update the apacheconfig package in two related ways:

  1. Change the parser's Abstract Syntax Tree (AST) to the list-based format defined below.
  2. Add an ApacheConfigLoader that converts parsed configuration text into a plain Python dictionary.

Existing public components and compatibility

The package already provides:

  • apacheconfig.lexer.ApacheConfigLexer, which remains instantiable with no arguments.
  • apacheconfig.parser.ApacheConfigParser, constructed as ApacheConfigParser(lexer, start=<rule>). Its parse(text) method returns an AST. Supported entry rules used by this API include 'statement', 'statements', 'block', and 'config'; when start is omitted, it defaults to 'config'.

The accepted configuration syntax remains unchanged. Blank lines, indentation, and separator whitespace do not produce AST nodes.

Part 1 — Parser AST format

Every AST node returned by ApacheConfigParser.parse must be a Python list, never a tuple. The first item of every node is a string tag identifying its type. Source order must be preserved.

Statement node

A single option/value pair is represented as:

['statement', <name>, <value>]
  • <name> and <value> are strings.
  • The name and value may be separated by whitespace, as in a b, or by an equals sign with optional surrounding whitespace, as in a=b or a = b.
  • Double quotes around a value are removed, while the content inside them, including spaces, is preserved. For example, a "b c" produces ['statement', 'a', 'b c'].
  • The node tag is 'statement'; the former tuple-based representation and 'option' tag are not part of the new AST.
Comment node

A comment line is represented as:

['comment', <text>]

<text> is the comment content after removing the leading #. All characters following the marker are preserved, including an immediately following space. Thus # a produces ['comment', ' a'], #a produces ['comment', 'a'], and # produces ['comment', ''].

Statements node

An ordered sequence of statement and/or comment nodes is represented as:

['statements', <node>, <node>, ...]

Children remain in source order. A statements container with no children is represented as ['statements'], including when it is used as an empty block body.

Block node

A block delimited by an opening tag and a closing tag is represented as:

['block', <open_tag>, <body>, <close_tag>]
  • <open_tag> is the complete text between < and > in the actual opening delimiter.
  • <body> is a 'statements' node containing the statement and comment nodes actually present inside that block, in source order.
  • <close_tag> is the complete text between </ and > in the actual closing delimiter.
  • Multiword tag text must be preserved in full. For example, <a block> yields the opening-tag value 'a block', not 'a'; <a a block> yields 'a a block', not 'a a'.
  • Opening and closing tag text are recorded independently from the source. Neither value is inferred from, shortened to, or replaced by the other. Consequently, a source block opened with <a block> and closed with </a> records 'a block' as <open_tag> and 'a' as <close_tag>.
Config node

Parsing a whole configuration produces:

['config', <child>, <child>, ...]

Each child is either a 'statements' node or a 'block' node, in source order. Consecutive top-level statements and comments are grouped into one 'statements' node. Every top-level block is a separate child and separates the statement groups before and after it. Each block must retain its own complete source tag texts and its own actual body nodes.

Complete config example

Given:

# a
a = b
<a block>
  a = b
</a>
a b
<a a block>
c "d d"
</a>
# a

parsing with the 'config' entry rule returns:

['config',
 ['statements', ['comment', ' a'], ['statement', 'a', 'b']],
 ['block', 'a block',
  ['statements', ['statement', 'a', 'b']],
  'a'],
 ['statements', ['statement', 'a', 'b']],
 ['block', 'a a block',
  ['statements', ['statement', 'c', 'd d']],
  'a'],
 ['statements', ['comment', ' a']]]

In particular, the block names are the full opening-tag interiors, the closing-tag fields reflect the literal closing delimiters, and the second block's body comes from c "d d".

Part 2 — Config loader

Create a new module, apacheconfig.loader, containing ApacheConfigLoader.

Constructor
ApacheConfigLoader(parser)

The constructor accepts an ApacheConfigParser instance. The loader uses that parser to parse configuration text into the AST defined above.

Method
loads(text) -> dict

loads parses text and returns a plain Python dict.

AST-to-dictionary behavior

Build the dictionary according to these rules:

  • A ['statement', name, value] node contributes name: value, with both key and value as strings.
  • A ['comment', text] node contributes nothing and is ignored.
  • A ['block', open_tag, body, close_tag] node contributes an entry whose key is the complete open_tag string and whose value is a nested dictionary obtained by applying these loading rules to body. The closing-tag field is not used as the dictionary key.
  • 'statements' and 'config' nodes are containers. Their child contributions are flattened and merged into the dictionary for the enclosing scope.
Escape handling in values

Escape removal occurs in loader output only. A backslash used to escape a character in a statement value is removed when producing the dictionary value. For example, the parser-level value \#000000 becomes #000000 in the loaded dictionary. The list-based AST itself continues to carry the parsed value prior to this loader conversion.

Loader examples

Loading the complete configuration shown above returns:

{
    'a': 'b',
    'a block': {'a': 'b'},
    'a a block': {'c': 'd d'}
}

The keys for both blocks use their complete opening-tag text even though the corresponding closing delimiters contain only a.

Given a configuration containing a comment and a cops block with name stein, age 25, and color \#000000:

<cops>
    name stein
    age 25
    color \#000000
</cops>

loads returns:

{
    'cops': {
        'name': 'stein',
        'age': '25',
        'color': '#000000'
    }
}

Task Specification: Apache Config Parser Grammar Refactor

Overview

The apacheconfig package parses Apache-style and Perl Config::General-style configuration files. Refactor its grammar so that block bodies and the top-level document body are represented by a contents AST node, while preserving statement and comment node formats. The parser must also support empty paired blocks and self-closing blocks, and the loader must understand the resulting AST.

Public API Surface

The following public classes must remain importable and usable:

  • apacheconfig.lexer.ApacheConfigLexer — constructible with no arguments as ApacheConfigLexer().
  • apacheconfig.parser.ApacheConfigParser — constructible as ApacheConfigParser(lexer, start=<rule_name>), where lexer is an ApacheConfigLexer instance and start is an optional string naming the grammar start rule. If omitted, start defaults to the whole-document config rule.
  • ApacheConfigParser.parse(text) — parses configuration text and returns an AST made from nested Python lists.
  • apacheconfig.loader.ApacheConfigLoader — constructible as ApacheConfigLoader(parser).
  • ApacheConfigLoader.loads(text) — parses configuration text and returns a Python dict.
  • apacheconfig.error.ApacheConfigError — the exception type used for parsing or loading failures.

The parser must support the statement, statements, block, contents, and config start rules.

Lexer compatibility

Existing lexical behavior must remain available through ApacheConfigLexer.tokenize(text), which returns token values in source order. In particular:

  • spaces, tabs, indentation, blank lines, and line endings are insignificant and are not returned as token values;
  • = remains a token value;
  • surrounding double quotes are removed from quoted strings;
  • opening and closing tag delimiters are removed from tag token values;
  • the # marker is removed from comment token values, while text following it is preserved; and
  • an escaped hash (\#) in an unquoted scalar is decoded to #.

For example, tokenizing a = "b c" yields the values ['a', '=', 'b c'], and tokenizing # note yields [' note'].

Accepted Configuration Forms

A statement may separate its key and value with whitespace, =, or both. Thus all of the following represent the same assignment:

a b
a=b
a = b
a= b
a =b

Spaces and tabs are accepted as separators. Quoted values may contain spaces and lose their surrounding quotes in the AST. Leading indentation is not significant. Blank lines are ignored.

A comment begins with an unescaped #. The comment AST retains everything following that marker, including a leading space. A literal hash in an unquoted scalar can be escaped as \#.

Blocks use <name> ... </name> syntax. Tag names may contain multiple components or an expression, such as <a a> or <if a == 1>. Empty self-closing blocks use <name/>.

AST Contract

Every AST node is a Python list whose first item is a string naming the node type. The empty list used as an empty block body is not itself an AST node.

statement

A single key/value assignment has this form:

['statement', <key>, <value>]

Examples:

  • a b produces ['statement', 'a', 'b'].
  • a=b produces ['statement', 'a', 'b'].
  • a = "b b" produces ['statement', 'a', 'b b'].

The surrounding quotes of a quoted value are not included in the value.

comment

A comment has this form:

['comment', <text>]

<text> is the content after the #; only the marker itself is removed. Therefore:

  • # a produces ['comment', ' a'];
  • #a produces ['comment', 'a']; and
  • a bare # produces ['comment', ''].
statements

One or more consecutive statement lines are grouped as:

['statements', <statement>, <statement>, ...]

A statements node may contain only statement children. Comments and blocks are never children of this node. A comment or block ends the current statement run; later statements begin a new statements node. Blank lines are insignificant and do not, by themselves, end a run.

For example:

a b
a = b

produces:

['statements',
 ['statement', 'a', 'b'],
 ['statement', 'a', 'b']]
contents

A contents node represents the ordered body of a block or of the whole document:

['contents', <child>, <child>, ...]

Its children may be any source-ordered mix of:

  • statements nodes, each representing one uninterrupted run of statement lines;
  • comment nodes; and
  • block nodes.

Consecutive statements collapse into one statements child. A comment or block between statements appears as its own child and causes following statements to be placed in a new statements child.

block

A named block has this form:

['block', <open_name>, <body>, <close_name>]
  • <open_name> is the opening tag name. Multiple tag components are represented as one whitespace-joined string; for example, <a a> has the name 'a a'.
  • A non-empty <body> is a contents node.
  • An empty body is represented by []. This applies to a paired block with no meaningful body, including one containing only insignificant whitespace.
  • <close_name> is the closing tag name represented in the same format as <open_name>.

For example, using the block start rule:

<a>
  <b>
     <c>
     </c>
  </b>
</a>

produces:

['block', 'a',
 ['contents',
  ['block', 'b',
   ['contents',
    ['block', 'c', [], 'c']], 'b']], 'a']

The innermost paired block is empty, so its body is [].

Self-closing blocks

<name/> represents an empty block. Its body is [], and its closing-name field is the same normalized name as its opening-name field. For example, using the contents start rule:

<a/>
<b/>

produces:

['contents',
 ['block', 'a', [], 'a'],
 ['block', 'b', [], 'b']]
config

The whole-document rule has exactly one body child, which is a contents node:

['config', ['contents', ...]]

Complete Parsing Examples

Block containing comments and statements

Using the block start rule, this input:

<a>
#a
a = "b b"
# a b
a = "b b"
</a>

produces:

['block', 'a',
 ['contents',
  ['comment', 'a'],
  ['statements',
   ['statement', 'a', 'b b']],
  ['comment', ' a b'],
  ['statements',
   ['statement', 'a', 'b b']]], 'a']

The comments remain in source order but split the assignments into distinct statements nodes.

Whole document

Using the config start rule, this input:

# a
a = b
<a>
  a = b
</a>
a b
 <a a>
  a b
 </a a>
# a

produces:

['config',
 ['contents',
  ['comment', ' a'],
  ['statements',
   ['statement', 'a', 'b']],
  ['block', 'a',
   ['contents',
    ['statements',
     ['statement', 'a', 'b']]], 'a'],
  ['statements',
   ['statement', 'a', 'b']],
  ['block', 'a a',
   ['contents',
    ['statements',
     ['statement', 'a', 'b']]], 'a a'],
  ['comment', ' a']]]

Loader Contract

ApacheConfigLoader.loads(text) must work with a parser using its default config start rule and return a Python dictionary. It must consume the contents-based AST described above.

Statements and nested blocks

Each statement becomes a dictionary entry. Scalar values remain strings. Each block name becomes a key whose value is a dictionary generated from that block's body. Empty blocks therefore map to empty dictionaries. Comments do not appear in the returned dictionary.

For example:

<cops>
  color \#000000
  age 25
  name stein
</cops>

loads as:

{'cops': {'color': '#000000', 'age': '25', 'name': 'stein'}}
Repeated keys within one statement run

When the same key occurs more than once within a single statements node, all values for that key are collected into a list in source order. The repeated assignments do not have to be immediately adjacent; they only need to belong to the same uninterrupted run of statement lines.

For example:

# Array content example
domain b0fh.org
domain l0pht.com
domain infonexus.com

loads as:

{'domain': ['b0fh.org', 'l0pht.com', 'infonexus.com']}

This merge is scoped to one statements node, not merely to a dictionary nesting level. Assignments to the same key in separate statement runs do not combine into a list. Since comments and blocks split statement runs, an assignment after such a separator replaces the value produced by an earlier run at that same level.

For example:

a first
<section>
  b value
</section>
a second

loads as:

{'a': 'second', 'section': {'b': 'value'}}

The same replacement rule applies when a comment separates the runs. Blank lines alone do not split a statement run and therefore do not change repeated-key list formation. If a later run itself repeats the key, the later run's newly formed list replaces the earlier run's scalar or list. This behavior applies independently within each block body and at the top level.

Errors

If the input cannot be parsed or loaded, loads raises apacheconfig.error.ApacheConfigError. Parser failures exposed through parse must likewise use ApacheConfigError.

Compatibility and Constraints

  • Do not change the list formats of statement or comment nodes.
  • A statements node must contain only statement children.
  • Every non-empty block body and the whole-document body must use the contents layer.
  • Empty block bodies must be represented by [], including bodies of self-closing blocks.
  • Preserve source ordering within every contents node and within repeated-key value lists.
  • Continue accepting both whitespace-separated and equals-separated assignments, quoted values, tabs, indentation, comments, blank lines, nested blocks, multi-component block names, and escaped hashes.

Overview

The parser instance exposes a method that parses text into a nested-list parse tree (the AST form used elsewhere in the codebase for blocks — see the tree format below).

Block Tag Syntax

A block is written with an opening tag <...> and a closing tag </...>. Blocks may be self-closing (<name/>). The content between the opening and closing tags is the block body.

Simple block tag

When the text inside the opening tag <...> contains no whitespace, it is a single token — the block name. Behavior for these blocks is unchanged.

Named block tag (new)

When the text inside the opening tag contains whitespace, split it on the first whitespace only, producing:

  • a head token (everything before the first whitespace), and
  • a name token (everything after the first whitespace).

The block must then be treated as nested: an outer block keyed by the head token, containing an inner block keyed by the name token, whose body is the block's contents.

Parse Tree (AST) Representation

A block appears in the parse tree as a list of the form:

['block', <open-tag-string>, <contents-list>, <close-tag-string>]
  • <open-tag-string> is the token(s) from the opening tag.
  • <close-tag-string> is the token from the closing tag.
  • <contents-list> is the list of statements/blocks in the body.

For an empty self-closing simple block, the open and close tag strings are the same single token and the contents list is empty. For example, input containing:

<a/>
<b/>

produces a top-level statements list whose entries include:

['block', 'a', [], 'a']
['block', 'b', [], 'b']

(preceded by the top-level 'statements' marker consistent with the existing tree format).

Block opening tags may be written at the very start of a line (no leading indentation required) and must parse correctly.

Loaded Configuration Representation (loads)

Named blocks → nested dicts

A named block whose opening tag splits into head h and name n, with body producing dict B, loads as:

{ h: { n: B } }

For example:

<a b>
c = 1
</a b>

loads to:

{'a': {'b': {'c': '1'}}}
Multiple named blocks sharing the same head token

When several named blocks share the same head token but have different name tokens, the head key maps to a list of single-key dicts, one per named block, each keyed by that block's name token and mapping to its body dict.

For example, two named blocks with head officer and names randall and gordon load such that the officer key holds a list of dicts:

'officer': [
    {'randall': {'age': '25', 'name': 'stein'}},
    {'gordon':  {'age': '31', 'name': 'bird'}},
]

For example, given input equivalent to:

<a>
block
...
</a>
a b
<a a block>
c "d d"
...
</a a block>

where:

  • a b is a scalar assignment giving key a the value b,
  • <a> ... </a> is a simple block named a whose body defines block with body {'a': 'b'},
  • <a a block> ... </a a block> is a named block with head a and name a block whose body defines c with value d d,

the result under key a is a list, in document order:

'a': ['b',
      {'block': {'a': 'b'}},
      'b',
      {'a block': {'c': 'd d'}}]

Note that:

  • A simple block named a contributes its body as a dict keyed by the block's inner content head (here {'block': {'a': 'b'}}).
  • A named block with head a and name a block contributes {'a block': {'c': 'd d'}} — i.e., under the shared head key a, the named block is represented as a single-key dict keyed by its name token.

Notes on Scope

  • Values are always strings; no type coercion is performed.
  • Quoted values retain their inner content (masked/escaped quotes and single quotes preserved as-is within the string).
  • Line-continuation and multi-line value handling elsewhere in the parser is unaffected; do not change it. Preserve existing whitespace within values exactly.
