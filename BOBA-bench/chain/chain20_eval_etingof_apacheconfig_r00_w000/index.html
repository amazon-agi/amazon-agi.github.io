Task Specification: Lexer and Parser for Apache Config Files

Using PLY (Python Lex-Yacc), implement a lexer and parser for Apache-style configuration files. The public API must reside in two modules: apacheconfig.lexer and apacheconfig.parser.

The apacheconfig.lexer module

Supply a class ApacheConfigLexer.

  • Its constructor takes no required arguments: ApacheConfigLexer().
  • The class must expose a method tokenize(text) that accepts configuration text as a string and returns a list of token values (each token's meaningful string content), in the order in which they appear in the input.
Rules for tokenization

What follows describes the token values that tokenize must yield:

  • Whitespace only. Input that contains only spaces, tabs, \r, and \n produces no tokens (an empty list).

  • Options and values. On a line, an option/value pair may be written with the name and value separated by whitespace or by an = (whitespace around the = being optional). The lexer emits a token for the option name, then optionally an = token, then a token for the value.

    • a b → 'a', 'b'
    • a = b → 'a', '=', 'b'
    • a= b, a =b, a=b, a b → the same tokenization as above (with = emitted only when the source contains =)
    • A value written in double quotes has its surrounding quotes stripped: a "b" → 'a', 'b'.

    For instance, this block:

    a b
a = b
a    b
a= b
a =b
a   b
a "b"
a = "b"

    yields these token values: ['a', 'b', 'a', '=', 'b', 'a', 'b', 'a', '=', 'b', 'a', '=', 'b', 'a', 'b', 'a', 'b', 'a', '=', 'b']

  • Open/close tags. The delimiters of a tag block are written with angle brackets. The token value is the tag content with the enclosing <, </, and > characters removed and with leading/trailing whitespace inside trimmed down to the tag's textual content.

    • <a> followed by </a> → 'a', 'a'
    • When a tag contains an expression, its inner text is preserved: <if a == 1> followed by </if> → 'if a == 1', 'if'

  • Comments. A line that begins with # produces a single comment token whose value is everything on the line following the # (the leading spaces in that remainder are not stripped).

    • # → ''
    • # a → ' a'
    • #a → 'a'
    • # a b → ' a b'
Examples combining constructs

A block with comments and options interspersed:

<a>
#
# a
# a b
</a>

→ ['a', '', ' a', ' a b', 'a']

A block that contains several option forms:

<a>
a b
a=b
a =  b
a = "b"
a "b"
</a>

→ ['a', 'a', 'b', 'a', '=', 'b', 'a', '=', 'b', 'a', '=', 'b', 'a', 'b', 'a']

Blank lines within a block are ignored:

<a>


</a>

→ ['a', 'a']

A configuration mixing constructs:

# h
a = b
<a>
  a b
</a>

→ [' h', 'a', '=', 'b', 'a', 'a', 'b', 'a']

The apacheconfig.parser module

Supply a class ApacheConfigParser.

  • The constructor takes a lexer instance as its first positional argument, plus an optional keyword argument start naming the grammar's start symbol: ApacheConfigParser(lexer, start='...').
  • If start is omitted, the default start symbol must be the full configuration (equivalent to start='config').
  • The class must expose a method parse(text) that parses the configuration text it is given and returns an abstract syntax tree (AST) built from the token stream produced by the lexer supplied to it.

Which grammar rule serves as the entry point is selected by the start argument. Below, the supported start symbols are described together with the AST outputs they produce.

Shapes of AST nodes
  • Option/value: ('option', <name>, <value>), where <name> and <value> are strings. A quoted value is unquoted (quotes removed), and a value that contains spaces is preserved as a single string.
  • Comment: ('comment', <text>), where <text> is the content after the # (this matches the lexer's comment token value, including any leading space).
  • Block: ('block', <open_tag>, <body>, <close_tag>), where <open_tag> and <close_tag> are the tag content strings and <body> is a list of the statement nodes contained in the block (options and/or comments), in order.
Start symbol: statement

Parses one option/value statement and returns a single ('option', name, value) tuple.

  • a b\n → ('option', 'a', 'b')
  • a=b\n → ('option', 'a', 'b')
  • a "b c"\n → ('option', 'a', 'b c')
Start symbol: statements

Parses a sequence of statements (options and comments) and returns a list of the corresponding nodes, in order.

For this input:

a b
a = b
a    b
a= b
a =b
a   b
a "b"
a = "b"

→ [('option', 'a', 'b')] * 8

For this input:

#
# a
#a
a = "b b"
# a b
a = "b b"

→

[('comment', ''), ('comment', ' a'),
 ('comment', 'a'), ('option', 'a', 'b b'),
 ('comment', ' a b'), ('option', 'a', 'b b')]
Start symbol: block

Parses a single tagged block and returns a ('block', open_tag, body, close_tag) tuple, with body being the list of the statements inside.

For this input:

<a>
  #a
  a = "b b"
  # a b
  a = "b b"
</a>

→

('block', 'a', [('comment', 'a'),
                ('option', 'a', 'b b'),
                ('comment', ' a b'),
                ('option', 'a', 'b b')], 'a')

Tag content may contain spaces; the open and close tag strings are preserved verbatim from the lexer (e.g. an open tag <a a> / close tag </a a> yields the open and close values 'a a').

Start symbol: config

Parses an entire configuration document and returns a list whose elements are, in source order:

  • Blocks, each represented as a ('block', open, body, close) tuple.
  • Runs of consecutive non-block statements (options and comments), where each such run is represented as a list of statement nodes. Consecutive comments/options that are not separated by a block are combined into a single list; a block terminates the current run.

For this document:

# a
a = b

<a>
  a = b
</a>
a b
<a a>
a b
</a a>
# a

→

[[('comment', ' a'), ('option', 'a', 'b')],
 ('block', 'a', [('option', 'a', 'b')], 'a'),
 [('option', 'a', 'b')],
 ('block', 'a a', [('option', 'a', 'b')], 'a a'),
 [('comment', ' a')]]

Note the following:

  • The comment at the start and the option preceding the first block are grouped into a single list.
  • Each block shows up as its own top-level tuple.
  • The lone option between the two blocks forms a one-element list of its own.
  • The trailing comment after the final block likewise forms a one-element list of its own.
  • Blank lines produce no nodes and do not split statement runs.
Default behavior for a full document

When the parser is constructed without an explicit start, parsing a full document behaves like the config start symbol. As an example, parsing:

# Nested block test
<cops>
  name stein
  age 25
  color \#000000
</cops>

→

[[('comment', ' Nested block test')],
 ('block', 'cops',
     [('option', 'name', 'stein'),
      ('option', 'age', '25'),
      ('option', 'color', '\\#000000')],
  'cops')]

Here, an unquoted value that begins with a backslash-escaped # is preserved verbatim as the value string ('\\#000000' is the two-character-prefixed literal \#000000).

Constraints

  • Both ApacheConfigLexer and ApacheConfigParser must be importable in exactly this way: from apacheconfig.lexer import ApacheConfigLexer and from apacheconfig.parser import ApacheConfigParser.
  • The parser must consume its tokens from the lexer instance handed to it at construction time.

Task Specification: List-Based AST and Configuration Loader

Summary

The apacheconfig package needs two related updates:

  1. Switch the parser's Abstract Syntax Tree (AST) to the list-based format specified below.
  2. Introduce an ApacheConfigLoader that turns parsed configuration text into a plain Python dictionary.

Public components and compatibility

The package currently exposes:

  • apacheconfig.lexer.ApacheConfigLexer, which can still be instantiated with no arguments.
  • apacheconfig.parser.ApacheConfigParser, which is constructed as ApacheConfigParser(lexer, start=<rule>); its parse(text) method returns an AST. The entry rules this API supports include 'statement', 'statements', 'block', and 'config'; if start is omitted, it defaults to 'config'.

The configuration syntax accepted by the package stays the same. Blank lines, indentation, and whitespace used as separators do not produce AST nodes.

Part 1 — AST format of the parser

Each AST node that ApacheConfigParser.parse returns must be a Python list, and a tuple is never acceptable. The first item of every node is a string tag that identifies its type. Source order must be preserved.

Statement node

A single option/value pair takes the form:

['statement', <name>, <value>]
  • <name> and <value> are both strings.
  • Whitespace may separate the name and the value, as in a b; alternatively, they may be separated by an equals sign with optional surrounding whitespace, as in a=b or a = b.
  • Double quotes surrounding a value are removed, but the content inside them, spaces included, is preserved. For example, a "b c" produces ['statement', 'a', 'b c'].
  • The tag of this node is 'statement'; the old tuple-based representation and the 'option' tag are not part of the new AST.
Comment node

A comment line takes the form:

['comment', <text>]

<text> holds the comment content once the leading # has been removed. Every character that follows the marker is preserved, including a space that comes immediately after it. Thus # a produces ['comment', ' a'], #a produces ['comment', 'a'], and # produces ['comment', ''].

Statements node

An ordered sequence of statement and/or comment nodes takes the form:

['statements', <node>, <node>, ...]

Children stay in source order. When a statements container has no children, it is represented as ['statements']; this also holds when it serves as an empty block body.

Block node

A block delimited by an opening tag and a closing tag takes the form:

['block', <open_tag>, <body>, <close_tag>]
  • <open_tag> is the full text found between < and > in the actual opening delimiter.
  • <body> is a 'statements' node holding the statement and comment nodes that are actually present inside that block, in source order.
  • <close_tag> is the full text found between </ and > in the actual closing delimiter.
  • Multiword tag text must be kept in its entirety. For instance, <a block> yields the opening-tag value 'a block', not 'a'; <a a block> yields 'a a block', not 'a a'.
  • The opening and closing tag text are each recorded from the source independently. Neither value is inferred from, shortened to, or replaced by the other. As a result, a source block opened with <a block> and closed with </a> records 'a block' as <open_tag> and 'a' as <close_tag>.
Config node

Parsing an entire configuration produces:

['config', <child>, <child>, ...]

Each child is either a 'statements' node or a 'block' node, in source order. Consecutive top-level statements and comments are combined into a single 'statements' node. Every top-level block forms its own child and separates the statement groups that come before and after it. Each block must keep its own complete source tag texts and its own actual body nodes.

Full config example

Given the following input:

# a
a = b
<a block>
  a = b
</a>
a b
<a a block>
c "d d"
</a>
# a

parsing it with the 'config' entry rule returns:

['config',
 ['statements', ['comment', ' a'], ['statement', 'a', 'b']],
 ['block', 'a block',
  ['statements', ['statement', 'a', 'b']],
  'a'],
 ['statements', ['statement', 'a', 'b']],
 ['block', 'a a block',
  ['statements', ['statement', 'c', 'd d']],
  'a'],
 ['statements', ['comment', ' a']]]

In particular, the block names are the full opening-tag interiors, the closing-tag fields mirror the literal closing delimiters, and the body of the second block comes from c "d d".

Part 2 — Configuration loader

Add a new module, apacheconfig.loader, that contains ApacheConfigLoader.

Constructor
ApacheConfigLoader(parser)

The constructor accepts an instance of ApacheConfigParser. That parser is what the loader uses to parse configuration text into the AST defined above.

Method
loads(text) -> dict

When called, loads parses text and returns a plain Python dict.

Converting the AST into a dictionary

The dictionary is built according to these rules:

  • A ['statement', name, value] node contributes name: value to the dictionary, where both the key and the value are strings.
  • A ['comment', text] node adds nothing and is ignored.
  • A ['block', open_tag, body, close_tag] node contributes an entry whose key is the full open_tag string and whose value is a nested dictionary produced by applying these loading rules to body. The closing-tag field is not used as the dictionary key.
  • 'statements' and 'config' nodes act as containers. The contributions of their children are flattened and merged into the dictionary of the enclosing scope.
Handling of escapes in values

Escapes are removed in the loader output only. A backslash that is used to escape a character in a statement value is removed when the dictionary value is produced. For example, the parser-level value \#000000 becomes #000000 in the loaded dictionary. The list-based AST itself continues to carry the parsed value before this loader conversion takes place.

Loader examples

Loading the complete configuration from the earlier example returns:

{
    'a': 'b',
    'a block': {'a': 'b'},
    'a a block': {'c': 'd d'}
}

The keys for both blocks come from their complete opening-tag text, even though the corresponding closing delimiters contain only a.

For a configuration that contains a comment and a cops block with the entries name stein, age 25, and color \#000000:

# Nested block test

<cops>
    name stein
    age 25
    color \#000000
</cops>

loads then returns:

{
    'cops': {
        'name': 'stein',
        'age': '25',
        'color': '#000000'
    }
}

Task Specification: Grammar Refactor for the Apache Config Parser

Summary

The apacheconfig package parses configuration files written in Apache style and in the style of Perl's Config::General. Refactor the grammar such that a contents AST node represents block bodies as well as the top-level document body, while the formats of statement and comment nodes are preserved. Beyond that, the parser must support empty paired blocks and self-closing blocks, and the loader must understand the AST that results.

Public API

The public classes listed below must remain importable and usable:

  • apacheconfig.lexer.ApacheConfigLexer — can be constructed with no arguments as ApacheConfigLexer().
  • apacheconfig.parser.ApacheConfigParser — constructed as ApacheConfigParser(lexer, start=<rule_name>), where lexer is an ApacheConfigLexer instance and start is an optional string that names the grammar start rule. When omitted, start defaults to the whole-document config rule.
  • ApacheConfigParser.parse(text) — parses configuration text and returns an AST composed of nested Python lists.
  • apacheconfig.loader.ApacheConfigLoader — constructed as ApacheConfigLoader(parser).
  • ApacheConfigLoader.loads(text) — takes configuration text, parses it, and returns a Python dict.
  • apacheconfig.error.ApacheConfigError — the exception type used for failures in parsing or loading.

The start rules statement, statements, block, contents, and config must all be supported by the parser.

Compatibility of the lexer

The lexical behavior that already exists must remain reachable through ApacheConfigLexer.tokenize(text), which returns token values in source order. Specifically:

  • spaces, tabs, indentation, blank lines, and line endings carry no significance and are never returned as token values;
  • = continues to be a token value;
  • quoted strings have their surrounding double quotes removed;
  • tag token values have their opening and closing tag delimiters removed;
  • comment token values have the # marker removed, while the text following it is preserved; and
  • within an unquoted scalar, an escaped hash (\#) is decoded to #.

For instance, tokenizing a = "b c" yields the values ['a', '=', 'b c'], and tokenizing # note yields [' note'].

Accepted Forms of Configuration

A statement may separate key and value with whitespace, with =, or with both. Hence all of the following stand for the same assignment:

a b
a=b
a = b
a= b
a =b

Both spaces and tabs are accepted as separators. A quoted value may contain spaces, and its surrounding quotes are lost in the AST. Indentation at the start of a line is not significant. Blank lines are disregarded.

A comment starts with an unescaped #. Everything following that marker is retained by the comment AST, including a leading space. In an unquoted scalar, a literal hash can be escaped as \#.

Blocks are written with <name> ... </name> syntax. A tag name may contain multiple components or an expression, such as <a a> or <if a == 1>. Empty self-closing blocks are written as <name/>.

Contract of the AST

Each AST node is a Python list whose first item is a string that names the node type. An empty list serving as an empty block body is not an AST node itself.

statement

A single key/value assignment looks like this:

['statement', <key>, <value>]

Examples:

  • a b gives ['statement', 'a', 'b'].
  • a=b gives ['statement', 'a', 'b'].
  • a = "b b" gives ['statement', 'a', 'b b'].

The surrounding quotes of a quoted value are not part of the value.

comment

A comment is shaped like this:

['comment', <text>]

<text> is the content that comes after the #; only the marker itself is removed. Therefore:

  • # a gives ['comment', ' a'];
  • #a gives ['comment', 'a']; and
  • a bare # gives ['comment', ''].
statements

One or more statement lines in a row are grouped together as:

['statements', <statement>, <statement>, ...]

A statements node may contain only statement children. Comments and blocks are never children of this node. A comment or block brings the current statement run to an end; statements that come later begin a new statements node. Blank lines are insignificant and do not, on their own, end a run.

As an example:

a b
a = b

yields:

['statements',
 ['statement', 'a', 'b'],
 ['statement', 'a', 'b']]
contents

A contents node stands for the ordered body of either a block or the document as a whole:

['contents', <child>, <child>, ...]

Its children may be any mix, in source order, of:

  • statements nodes, where each represents a single uninterrupted run of statement lines;
  • comment nodes; and
  • block nodes.

Statements that are consecutive collapse into a single statements child. A comment or block sitting between statements appears as its own child and makes the following statements be placed in a new statements child.

block

A block with a name looks like this:

['block', <open_name>, <body>, <close_name>]
  • <open_name> is the name in the opening tag. Several tag components are represented as a single whitespace-joined string; for instance, <a a> has the name 'a a'.
  • When <body> is non-empty, it is a contents node.
  • An empty body is represented as []. This covers a paired block that has no meaningful body, including one that contains only insignificant whitespace.
  • <close_name> is the name in the closing tag, represented in the same format as <open_name>.

For example, with the block start rule:

<a>
  <b>
     <c>
     </c>
  </b>
</a>

the result is:

['block', 'a',
 ['contents',
  ['block', 'b',
   ['contents',
    ['block', 'c', [], 'c']], 'b']], 'a']

Since the innermost paired block is empty, its body is [].

Self-closing blocks

<name/> stands for an empty block. Its body is [], and the closing-name field carries the same normalized name as the opening-name field. For example, with the contents start rule:

<a/>
<b/>

the output is:

['contents',
 ['block', 'a', [], 'a'],
 ['block', 'b', [], 'b']]
config

The rule for the whole document has exactly one body child, and that child is a contents node:

['config', ['contents', ...]]

Contract of the Loader

ApacheConfigLoader.loads(text) must work when given a parser that uses its default config start rule, and must return a Python dictionary. The contents-based AST described above is what it must consume.

Statement entries and nested blocks

Every statement turns into a dictionary entry. Scalar values stay strings. Every block name turns into a key whose value is a dictionary generated from that block's body. Empty blocks therefore map to empty dictionaries. Comments never appear in the returned dictionary.

As an example:

<cops>
  color \#000000
  age 25
  name stein
</cops>

is loaded as:

{'cops': {'color': '#000000', 'age': '25', 'name': 'stein'}}
Repeated keys inside one statement run

If the same key shows up more than once inside a single statements node, all of that key's values are gathered into a list, in source order. The repeated assignments do not need to be immediately adjacent; the only requirement is that they belong to the same uninterrupted run of statement lines.

As an example:

# Array content example
domain b0fh.org
domain l0pht.com
domain infonexus.com

loads to:

{'domain': ['b0fh.org', 'l0pht.com', 'infonexus.com']}

This merging has a scope of one statements node, and not simply a dictionary nesting level. Assignments to the same key that sit in separate statement runs are not combined into a list. Because comments and blocks split statement runs, an assignment that comes after such a separator replaces the value an earlier run produced at that same level.

As an example:

a first
<section>
  b value
</section>
a second

comes out as:

{'a': 'second', 'section': {'b': 'value'}}

When a comment is what separates the runs, the same replacement rule applies. Blank lines on their own do not split a statement run, and therefore do not change how repeated-key lists form. If a later run repeats the key itself, the list that the later run newly forms replaces the earlier run's scalar or list.   • Option and value may be separated by whitespace or by = (with optional surrounding whitespace); both forms yield the same statement node. Multiple statements parsed under start='statements' produce a ['statements', ...] node holding one ['statement', name, value] per line.
Comments

    • # b → ['comment', ' b']

  • Self-closing block tags written as <name/> are supported and appear within contents/config output.

Overview

Public API Surface

    • loads(text: str) -> dict — takes configuration text, parses it, and returns the loaded configuration in the form of nested Python dicts/lists/strings.

The parser instance exposes a method that parses text into a nested-list parse tree (the AST form the codebase uses elsewhere for blocks — the tree format is shown below).

Syntax of Block Tags

A block is written using an opening tag <...> together with a closing tag </...>. A block may be self-closing (<name/>). Whatever appears between the opening and closing tags forms the block body.

Simple block tag

If the text inside the opening tag <...> contains no whitespace, it makes up a single token — the block name. The behavior of these blocks remains unchanged.

Named block tag (new)

If the text inside the opening tag contains whitespace, split it on the first whitespace only. The split produces:

  • a head token (everything before the first whitespace), and
  • a name token (everything after the first whitespace).

The block must then be handled as nested: an outer block keyed by the head token, which contains an inner block keyed by the name token, whose body is the block's contents.

Representation in the Parse Tree (AST)

In the parse tree, a block takes the form of a list:

['block', <open-tag-string>, <contents-list>, <close-tag-string>]
  • <open-tag-string> — the token(s) from the opening tag.
  • <close-tag-string> — the token from the closing tag.
  • <contents-list> — the list of statements/blocks in the body.

When a simple block is empty and self-closing, its open and close tag strings are the same single token, and its contents list is empty. As an example, given the input:

<a/>
<b/>

the result is a top-level statements list whose entries include:

['block', 'a', [], 'a']
['block', 'b', [], 'b']

(which are preceded by the top-level 'statements' marker, matching the existing tree format).

A block opening tag may appear at the very start of a line (no leading indentation required) and must parse correctly.

Representation in the Loaded Configuration (loads)

Named blocks → nested dicts

A named block whose opening tag splits into head h and name n, and whose body produces the dict B, loads as:

{ h: { n: B } }

For instance:

<a b>
c = 1
</a b>

loads to

{'a': {'b': {'c': '1'}}}
Multiple named blocks sharing the same head token

When several named blocks have the same head token but different name tokens, the head key maps to a list of single-key dicts, one per named block, with each dict keyed by that block's name token and mapping to that block's body dict.

As an example, two named blocks whose head is officer and whose names are randall and gordon load so that the officer key holds a list of dicts:

'officer': [
    {'randall': {'age': '25', 'name': 'stein'}},
    {'gordon':  {'age': '31', 'name': 'bird'}},
]
Interleaving between a repeated scalar key and blocks

If a top-level key name serves both for repeated scalar assignments and for block definitions (simple and named), all such values collapse into a single list under that key, with document order preserved. Scalar values show up as plain strings, while blocks show up as single-key dicts.

For example, given input equivalent to:

a b
<a>
block
...
</a>
a b
<a a block>
c "d d"
...
</a a block>

in which:

  • a b is a scalar assignment that gives key a the value b,
  • <a> ... </a> is a simple block named a whose body defines block with the body {'a': 'b'},
  • <a a block> ... </a a block> is a named block with head a and name a block, whose body defines c with the value d d,

what ends up under key a is a list, in document order:

'a': ['b',
      {'block': {'a': 'b'}},
      'b',
      {'a block': {'c': 'd d'}}]

Note that:

  • A simple block named a contributes its body in the form of a dict keyed by the block's inner content head (here {'block': {'a': 'b'}}).
  • A named block with head a and name a block contributes {'a block': {'c': 'd d'}} — that is, under the shared head key a, the named block is represented as a single-key dict keyed by its name token.

Scope Notes

  • Values are always strings; no type coercion takes place.
  • Quoted values keep their inner content (masked/escaped quotes and single quotes preserved as-is within the string).
  • Line-continuation and multi-line value handling elsewhere in the parser is unaffected; do not change it. Preserve existing whitespace within values exactly.
  • Block name comparisons are comparisons of literal tokens; do not alter the existing case-handling behavior for simple block names.

Implement only the named-block splitting, the nesting, and the list-collapsing behavior described above.
