01 A class named HyP3 must be publicly exported by the hyp3_sdk package. 198 words · source specification, reworded by GLM-5.3-Flash

API requirements

  • A class named HyP3 must be publicly exported by the hyp3_sdk package.
  • HyP3 must be constructible when given no arguments:
    api = HyP3()
  • Instances must expose a url attribute that contains the API base URL.
  • The following must be provided by instances:
    api.find_jobs()

Required behavior of find_jobs

A call to HyP3.find_jobs() must retrieve every page of jobs:

  1. Issue the initial request to the /jobs endpoint without a next query parameter.
  2. Read the job records from the "jobs" list in the response.
  3. If a "next" URL is present in the response, request that URL. The subsequent request must include the query parameters of that URL, including next.
  4. Carry on until reaching a response that does not contain "next".
  5. Return one batch containing the jobs from all retrieved pages.

For instance, if the first response contains two jobs plus a "next" URL that ends in /jobs?next=foobar, and the following response has one job with no "next" value, then the returned batch must have a length of 3. The first request must not contain a next parameter, but the second request must contain it.

  • The method is HyP3.find_jobs().

  • The method must continue to be callable without arguments.
  • The return value is still a hyp3_sdk.Batch that contains hyp3_sdk.Job objects. The existing filtering and job-conversion behavior must stay unchanged.

Pagination behavior

When find_jobs() is called with no filters:

  1. Issue the initial GET request to <api.url>/jobs with no query string. In particular, this initial request must not contain a next parameter.

  2. Take all jobs from the response's jobs array and add them to the result.

  3. If the response contains next, treat its value as the complete URL of the next page, its existing query string included. Follow that URL directly, or issue a semantically equivalent request that preserves exactly the query parameters of that URL.

  4. The complete continuation URL must not be passed as the value of a newly added next parameter. For example, if the response contains:

    {
  "next": "<api.url>/jobs?next=foobar"
}

    the subsequent request must be made to <api.url>/jobs?next=foobar, not to a URL equivalent to <api.url>/jobs?next=<URL-encoded complete URL>.

  5. Accumulate the jobs from every fetched page, in page order, into one returned Batch.

  6. Keep following the next URL of each response and stop when a response does not provide next.

For example, if the first page holds two jobs and points to <api.url>/jobs?next=foobar, and that second page holds one job with no further continuation URL, then find_jobs() must return a Batch of length 3.

If no jobs are found across the pages that were retrieved, keep the existing behavior of returning an empty Batch and issuing a UserWarning.

Beyond the behavior described above, no additional error handling or pagination behavior is required.

11 Refactoring the Job Class 1081 words · rewritten by GPT-5.6-sol, reworded by GLM-5.3-Flash

Task Specification: Refactoring the Job Class

Summary

Rework the existing Job class so that it features a consistent, fixed attribute model, can be built from a job dictionary, and can serialize either a complete job dictionary or a resubmission payload. Job must still be importable as Job from hyp3_sdk.jobs and through the existing package-level export.

The surrounding Job API must be preserved by this work. Timestamp conversion in particular must stay compatible with expiration checks and product downloads.

Public API Requirements

Job.from_dict(data: dict) -> Job

Supply a class-level constructor that returns a new Job on each call. For each key in a valid input dictionary:

  • the object that comes back must expose an attribute of that same name through ordinary Python attribute access, including getattr(job, key) and job.__getattribute__(key);
  • the attribute must represent the value that was supplied; and
  • apart from the timestamp conversion described below, the value must be kept unchanged.

Within this contract, valid job dictionaries carry truthy values for the keys they supply. Those values, nested dictionaries and lists included, must retain their content.

Rather than creating only the attributes present in a single response, the class carries a fixed set of known job attributes. As a consequence:

  • vars(job).keys() must form a superset of data.keys();
  • every known instance attribute missing from data must still be present in vars(job), holding exactly the value None rather than some other falsy sentinel such as 0, False, or an empty string; and
  • which attributes a job has available must not depend on whether that job is running, failed, or succeeded. No valid input field may be thrown away merely because it is tied to a particular job state.

Distinct calls must produce instances that are independent of one another. Populating one job, or changing it later, must not alter the attributes or serialization of another job.

ISO-8601 Expiration Timestamps

An ISO-8601 expiration_time that is nonempty and supplied in data is a timestamp, not an opaque string. from_dict must treat it as a datetime-compatible value carrying the timezone semantics that comparison with the current time requires. This in-memory conversion is the exception to the rule that the literal supplied value is kept as the instance attribute.

Once converted, the value must preserve the existing expiration behavior:

  • job.expired() can compare it against the current time and reports future and past expiration times correctly;
  • a successful, unexpired job built from a service dictionary can proceed through job.download_files();
  • an expired job keeps being rejected by that operation; and
  • neither operation may fail merely due to expiration_time originally arriving as an ISO-8601 string.

When expiration_time is absent or has no value, the corresponding known attribute stays None, and the existing behavior for a job that has no expiration timestamp is left unchanged.

Job.to_dict(for_resubmit: bool = False) -> dict

The job is serialized into an ordinary dictionary, and the instance is not mutated.

Default mode: for_resubmit=False

For a job that was created with Job.from_dict(data), the default result must equal data exactly:

  • every supplied key appears in it;
  • all values that are not timestamps are returned unchanged;
  • known attributes that stayed None because data lacked them are left out; and
  • no bookkeeping fields and no extra defaulted fields are added.

More broadly, default serialization covers every populated known job attribute and leaves out known attributes whose value is None.

Timestamp attributes whose values are datetimes must be converted to their ISO-8601 dictionary representation. A parsed expiration_time in particular must serialize back to the matching ISO-8601 value, so canonical service dictionaries round-trip through from_dict and to_dict with no change to their public representation. Compatibility with existing datetime serialization conventions, including second precision where applicable, must be maintained.

Resubmission mode: for_resubmit=True

Resubmission follows whitelist semantics. The result must contain only those populated attributes whose names are members of Job._attributes_for_resubmit; that set does not name attributes to remove.

With any valid input dictionary data, the resubmission result's keys must be exactly:

set(data) & Job._attributes_for_resubmit

Consequently:

  • a supplied key belonging to _attributes_for_resubmit is retained with its original public dictionary value;
  • every supplied key outside the set is absent, even when its instance value is truthy;
  • an allowed known attribute that was not supplied, and therefore remains None, is not added; and
  • no other keys may appear in the result.

Invoking this mode must not clear the excluded attributes or modify them. Immediately afterward, every key originally supplied to from_dict must still be readable on the instance and keep its value, with the documented in-memory timestamp representation as the only exception.

Job._attributes_for_resubmit

Expose _attributes_for_resubmit as a class-level set whose entries are plain attribute-name strings. Normal set behavior must be supported, including membership checks and set difference with a set of dictionary key strings.

The set must be a proper subset of the attributes a job may carry, so that populated job-definition fields can be retained while job state and result metadata are excluded. Normal valid job dictionaries must contain eligible job-definition fields so that resubmission retains those fields. The set's membership and the class's fixed attribute schema must be internally consistent with the exact-intersection rule above.

The individual field names, and the exact membership, are determined by the Job schema. Callers must not have to rely on separate class-level registries partitioned by job outcome; _attributes_for_resubmit is the sole class-level field registry this refactor requires.

Invariants for Attributes and Serialization

The requirements below all apply at the same time:

  1. Standard attribute access makes every valid input key available.
  2. In vars(job), every class-defined instance attribute omitted from the input is exactly None.
  3. Default serialization leaves those None defaults out and recreates the complete input dictionary.
  4. Resubmission serialization emits exactly the populated input keys that _attributes_for_resubmit allows.
  5. The instance is mutated by neither serialization mode.
  6. Timestamp parsing stays inside the object model; the dictionary output remains ISO-8601, and expiration-dependent operations receive a comparable timestamp.
  7. No per-instance bookkeeping with a value other than None may leak into vars(job) as an additional attribute that was absent from the construction dictionary.

Scope

This refactor changes the behavior of Job; it does not redesign batches, submission clients, status helpers, expiration checks, or downloading. Existing consumers of Job.from_dict, Job.to_dict, expired(), and download_files() must keep working with the representations described above. No particular internal organization is required, as long as all public behavior and the invariants are satisfied.
