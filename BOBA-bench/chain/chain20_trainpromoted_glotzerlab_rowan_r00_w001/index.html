Task: Add NumPy Broadcasting to Quaternion Multiplication

Overview

You must modify the quaternion multiplication function so that full NumPy-style broadcasting is supported between its two array operands. In addition, certain input-validation error checks must be removed from several related functions.

Public API

All of the functionality is contained in a module that can be imported as quaternion. The function of interest is:

quaternion.multiply(a, b)

Quaternions are stored in NumPy arrays in which the final axis has length 4 (holding the four quaternion components). A single quaternion is an array of shape (4,); collections of quaternions are arrays whose trailing dimension is 4 and whose leading dimensions index the individual quaternions.

Required Behavior of quaternion.multiply(a, b)

The function multiplies two quaternion arrays element-wise (applying the quaternion product to each aligned pair) and must support NumPy broadcasting over the leading dimensions (that is, every dimension other than the final length-4 component axis).

Specifically:

  1. Broadcasting across leading dimensions. When two inputs are given whose shapes both end with a trailing axis of length 4, their leading dimensions must be broadcast together following standard NumPy broadcasting rules. The leading dimensions of the result are the broadcast of the two operands' leading dimensions, and the result has a trailing dimension of 4.

    • Example: multiplying an operand of shape (45, 3, 13, 4) by an operand of shape (4,) gives a result of shape (45, 3, 13, 4).
    • Example: multiplying an operand of shape (1, 1, 3, 8, 1, 4) by an operand of shape (3, 5, 1, 1, 9, 4) gives a result of shape (3, 5, 3, 8, 9, 4).

  2. Non-conforming shapes. If the leading dimensions of the two operands cannot be broadcast together under standard NumPy rules, a ValueError must be raised.

    • Example: multiplying an operand of shape (45, 3, 13, 4) by an operand of shape (2, 4) must raise ValueError.

  3. Correctness of the products. For any aligned pair of quaternions picked from the broadcast result, the value at that position must equal the quaternion product of the two corresponding single quaternions (that is, the result obtained by calling multiply on those two individual shape-(4,) quaternions). Broadcasting must not alter the computed product values compared with computing each pair individually.

The current behavior for multiplying single quaternions (shape (4,) inputs) and equally-shaped batched inputs must continue to work.

Removals: Remove Input-Validation Error Checks

The functions listed below must no longer raise errors for the inputs described. These validation checks must be removed so that the calls in question no longer raise:

  • quaternion.from_euler(...) must not raise ValueError when given an unrecognized axis-convention string or an unrecognized intrinsic/extrinsic mode argument.
  • quaternion.to_euler(...) must not raise ValueError when given an unrecognized axis-convention string or an unrecognized intrinsic/extrinsic mode argument, and must not raise ValueError for quaternion inputs with a non-unit norm.
  • quaternion.from_matrix(...) must not raise ValueError when given a non-rotation (non-orthonormal) input matrix.
  • quaternion.to_matrix(...) must not raise ValueError when given a non-unit-norm quaternion input.

Note: quaternion.to_euler(...) and quaternion.to_matrix(...) must still raise ZeroDivisionError in cases where a zero quaternion causes division by zero — that behavior stays unchanged. Only the ValueError norm/validation checks are removed.

Constraints

  • The numerical correctness of any existing valid operations must not be changed.
  • The existing signatures and importable names of all mentioned functions must be preserved.

  • For the identity quaternion (1, 0, 0, 0), the 3×3 identity matrix is returned.

  • to_euler and to_matrix do enforce that input quaternions are unit quaternions and must raise ValueError for non-unit inputs (and ZeroDivisionError for zero-magnitude inputs, which take precedence).
  • vector_vector_rotation must not require unit-length input vectors; the vectors are normalized internally.
