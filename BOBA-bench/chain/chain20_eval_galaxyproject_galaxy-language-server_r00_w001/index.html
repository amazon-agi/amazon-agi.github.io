Task Specification: XML Context Parsing with a Position-Aware SAX Parser

Overview

Your task is to implement or refactor the XML context detection subsystem that lives in the module server/services/context.py. The module inspects an XML document at a supplied cursor position and reports which "token" the cursor is on (a tag name, an attribute key, an attribute value, or nothing), together with the stack of open element names at that position.

The public API is imported in the following way:

from server.services.context import (
    XmlContextService,
    XmlContext,
    XmlContextParser,
    ContextTokenType,
)

(Within the codebase, imports use relative paths, e.g. from ...services.context import ....)

Documents are instances of pygls.workspace.Document; positions are instances of pygls.workspace.Position. A Position carries line and character attributes (both zero-based).

  • ContextTokenType.TAG

  • ContextTokenType.ATTRIBUTE_VALUE

Token detection semantics (token_name)

For a given cursor position, token_name is the text of the XML token the cursor sits on, or None when the cursor is not sitting on any recognizable token. Character indices are zero-based: a cursor at character index c sits between character c-1 and character c of the line.

A token's boundaries are inclusive of the token's own characters and exclusive of the surrounding structural/whitespace characters. To be precise:

Tag names

For an opening tag such as <tool ...>:

  • token_name is None when the cursor is positioned immediately before the <, up to and including the boundary at the < itself (i.e. at the character index of < and at any position left of the name).
  • token_name reports the tag name ("tool") when the cursor lands anywhere from immediately after the < through the end of the tag name (i.e. positions that cover the name characters, including the boundary just after the last name character).
  • Positions past the tag name that are not yet inside an attribute (e.g. the whitespace separating the name from an attribute) report None.

Worked example — the content <tool id="test"> on one line (< at character 0):

char range token_name
0 None
1 – 5 "tool"
6 – 8 "id"
9 None
10 – 14 "test"
15 None

Here the attribute is id="test": the key id spans characters 6–7 and its detection region is 6–8; the value test lies inside the quotes and its detection region is 10–14, while the delimiter/quote boundaries (char 9, char 15) report None.

Attribute keys

token_name reports the attribute key name (e.g. "id", "value") when the cursor is positioned over the key characters, including the boundary immediately after the last key character. Positions before the key (on the separating whitespace), or on the = / opening delimiter, report None.

Attribute values

token_name reports the attribute value text (e.g. "test", "value", "0", "1") when the cursor is positioned strictly inside the value, between the quotes surrounding it, including the boundary immediately after the last value character but not the closing quote position itself. The opening-quote position, and the closing-quote position and everything beyond it, report None.

Worked example — the line <test value="0"/> (< at character 4, on line 3 in a multi-line doc):

char token_name
4 None
5 – 9 "test"
10 – 15 "value"
16 None
17 – 18 "0"
19 None

Worked example — a standalone line <description ...> (< at character 4 on line 2):

char token_name
5 – 16 "description"
17 None

Worked example — the incomplete content <other id="1" (no line offset, < at 0):

char token_name
0 None
1 – 6 "other"
7 – 9 "id"
11 – 12 "1"
13 None

The parser must apply these boundaries consistently across multi-line documents (a position is resolved on the correct line/character within the whole document).

Empty-content detection (is_empty)

parse(...) must set is_empty == True whenever the document has no meaningful XML content at/around the cursor. This covers every document whose full content is one of the following:

  • the empty string ""
  • a lone <
  • whitespace only (" ", " ")
  • newlines only ("\n\n")

In all of these cases is_empty == True must result regardless of the cursor position (including positions beyond the actual content, e.g. character 10 in an empty document, or line 1 of a two-newline document).

Non-empty XML (e.g. <a, <test, or any real element) results in is_empty == False.

The open-element stack (node_stack)

node_stack must be a list holding the names of the elements that are currently open at the cursor position, as strings, ordered from the outermost element to the innermost.

The stack includes the element whose start tag the cursor is currently inside, and it excludes elements that were already closed (including self-closed elements) before the cursor position.

Worked examples (a single line, <first> starts at character 0):

  • With the content <first><second><third>:
    • a cursor at character 1 (inside <first) → ["first"]
    • a cursor at character 8 (inside <second) → ["first", "second"]
    • a cursor at character 16 (inside <third) → ["first", "second", "third"]
  • With the content <first><second/><third> (the second element is self-closing):
    • a cursor at character 17 (inside <third) → ["first", "third"]

Deliverables summary

Inside server/services/context.py, provide:

  1. The ContextTokenType enum, containing UNKNOWN, TAG, ATTRIBUTE_KEY, ATTRIBUTE_VALUE.
  2. The XmlContext class with the keyword-constructible signature, the mutable public attributes (token_name, token_type, node, document_line, target_position, is_empty, node_stack), and the three predicate methods is_tag(), is_attribute_key(), is_attribute_value().
  3. A XmlContextService(xsd_tree) that exposes xsd_tree and get_xml_context(document, position).
  4. A XmlContextParser() that exposes parse(document, position), implementing the token detection, empty-content, and open-element-stack semantics above.

Task Specification: Extending the XML Context with is_node_content

Summary

The XML context parser creates a context object that captures the parse state for a particular cursor position inside an XML document. You must give this context object an additional boolean attribute, is_node_content, whose value tells whether the cursor position sits within the text content of an XML element (that is, after an element's opening tag and before its closing tag, in an area where character data would appear).

Public API

The classes involved already exist and are used in this way:

  • XmlContextParser — a class providing this method:

    def parse(self, document: Document, position: Position) -> XmlContext

    where Position carries the integer fields line and character (both zero-based).

  • The object that XmlContextParser.parse(...) returns must expose a boolean attribute:

    is_node_content: bool

Required Behavior

When a document and a cursor Position are supplied to parse, it must set is_node_content to True if the position falls inside a region that constitutes an element's textual content — in other words, strictly after an element's opening tag (>) ends and up to and including the position just before / at the start of the following markup (<) — and to False otherwise.

To put this more precisely, depending on where the cursor sits relative to the markup around it:

  • A position that sits inside an opening tag (whether on the tag name, on the whitespace/attributes, or anywhere from the leading < up to and including the > character that closes the tag) is not node content → False.
  • A position immediately after the closing > of an opening tag (i.e., the point where the content text starts) is node content → True.
  • A position that falls in the text between an opening tag and its matching closing tag is node content → True.
  • The position at the boundary immediately at the < that starts the closing tag (the point at which the content ends and the closing markup starts) is still treated as node content → True.
  • A position that lies within the closing tag itself (after its leading <, on its name, up to and including its >) is not node content → False.
  • A position immediately after the > of a closing tag is not node content → False.
Worked examples

Take this document (lines 0 and 1 are shown; indices for lines and for characters are zero-based):

Line 0: <first id="1">
Line 1:     <second attr="value">test</second>
Line 2: <third

Here are the is_node_content values to expect:

Line Character Location is_node_content
0 1 within the <first opening tag False
0 8 within the attributes of the <first opening tag False
0 14 just after the closing > of <first id="1"> True
1 0 in the content of <first> (start of the next line, leading whitespace) True
1 4 at the < that starts <second ...> True
1 5 within the <second> opening tag (on the tag name) False
1 6 within the <second> opening tag False
1 24 at/inside the > that closes <second attr="value"> False
1 25 just after <second attr="value">, where the test content starts True
1 29 at the < that starts </second> True
1 30 within the </second> closing tag False

(Note: on line 1, characters 0–3 hold the four leading spaces, <second attr="value"> covers characters 4–24 with < at 4 and > at 24, test occupies 25–28, and </second> starts at character 29.)

Constraints

  • All of the context object's other existing behavior and attributes (such as the node stack) must remain unchanged.
  • Only the addition of the is_node_content boolean attribute and its correct population is required.

Goal

Give the XsdTree class a method that locates a node in the tree by following a path (stack) of node names downward from the root.

Background

The codebase contains an XSD parser that constructs a tree structure of nodes out of an XSD schema. Each node in the tree carries a name attribute and is aware of its child nodes. The parser exposes a get_tree() method, and that method returns the root tree object (an XsdTree instance).

API to Add

The following method is to be added to the XsdTree class (it resides in the XSD parser module used by the parser fixture, i.e. the same module whose tree objects are returned by an XsdParser's get_tree() method):

def find_node_by_stack(self, stack: list[str]) -> <Node>:
    ...

Behavior to Implement

The method accepts a stack: an ordered list of node names that represents a path through the tree, one that starts at the top-level element and descends through successive children.

  • The first name in the stack designates a top-level node of the tree.
  • Each subsequent name in the stack designates a descendant node that is reached by continuing downward from the previously matched node (i.e. the next name is matched among the nodes that are reachable below the current node).
  • The method returns the node whose name equals the last name in the stack; this node is found by resolving the full path in order.

Path resolution must handle cases in which intermediate nodes contain grouped child elements: a name that appears later in the stack may be found among elements contributed by a group belonging to an ancestor in the path. Two distinct paths that arrive at the same descendant name (one in which the grouped element is nested under a directly named intermediate element, and one in which the grouped element is reached through an element that references a group) must both resolve correctly to the node carrying that final name.

Examples of the expected resolution

Given a schema tree, the stacks that follow must return a node whose name matches the final element of the stack:

  • ["testElement"] → a node whose name is "testElement"
  • ["testElement", "firstElement"] → a node whose name is "firstElement"
  • ["testElement", "secondElement"] → a node whose name is "secondElement"
  • ["testElement", "secondElement", "group_elem1"] → a node whose name is "group_elem1"
  • ["testElement", "element_with_group", "group_elem1"] → a node whose name is "group_elem1"

In every case, the object that is returned exposes a name attribute equal to the last entry of the provided stack.

Behavior Requirements

Resolving the node (XmlContextService.get_xml_context)

Once the service has been given a document and a cursor position, it must work out the sequence (stack) made up of the XML tag names that are currently open/relevant at that position; it must then descend the XsdTree, starting at its root, to resolve the corresponding XsdNode, with each tag name from the stack being matched, by name, to a child node. Of the matched nodes in the tree, the deepest one — the node that corresponds to the tag stack — is the node the resolution produces.

It may happen that the XML is broken or incomplete. What follows spells out how resolution must behave.

Picture a tree whose structure is:

  • root
    • child
      • subchild
    • sibling

Required is the following mapping from position to resolved node (the line/character positions are zero-based; a character position is a cursor offset, i.e., the cursor is placed before the character at that index):

With the document <root><child (one line):

  • character 0 through 6 → the resolved node is root
  • character 7 through 12 → the resolved node is child

With the document <root><child (a trailing space comes after child):

  • character 13 → the resolved node is child

With the document <root attr="4"><child (one line):

  • character 14 → the resolved node is root
  • character 16 → the resolved node is child

A document spanning two lines:

<root attr="4">
<child/><other
  • line 1, character 7 → the resolved node is child
  • line 1, character 8 → the resolved node is root
  • line 1, character 9 → the resolved node is root

Because <child/> closes itself, as soon as the cursor is at its closing or has moved beyond it, the parent (root) once again becomes the current node context. The unfinished <other tag trailing at the end — its name does not correspond to any child of root — does not carry the resolution any deeper, and the context stays root.

Another document spanning two lines:

<root attr="4">
<child/><sibling
  • line 1, character 9 → the resolved node is sibling

This time the unfinished tag at the end, <sibling, refers to a valid child of root, and the resolution therefore lands on sibling.

And a document spanning three lines, one that contains a broken/incomplete tag:

<root attr="4">
    <
<child
  • line 1, character 5 → the resolved node is root

Line 1 contains just a lone < — an incomplete/broken tag that fails to name any child; the resolved context therefore stays root.

Computing the tag stack (XmlContextParser)

From a supplied cursor position, XmlContextParser is required to produce a stack (an ordered list) of tag names that describes the hierarchy of XML elements open at that point. When XmlContextService descends the XSD tree, it works from exactly this stack.

For the document

<first><second attr="value"/><third

(a single line), the required tag stacks are:

  • character 29 → the tag stack comes out as ["first"]
  • character 30 → the tag stack comes out as ["first", "third"]

At character 29 the cursor is placed immediately after the self-closed <second .../> element; hence first is the only entry on the stack. At character 30 the cursor has gotten into the unfinished <third tag; that tag gets pushed onto the stack, and the result is ["first", "third"].

Summary of Edge Cases and Rules

  • After a self-closing tag (<tag/>) closes, it must not stay on the tag stack any longer; the stack reverts to the context of its parent.
  • When the cursor has gotten past the start of an unfinished opening tag (for instance, <third or <child that has no closing >), that tag must be included on the tag stack.
  • The character index of the cursor denotes an offset that lies before the character at that index; the exact position boundaries given above govern whether the opening < of a tag (and the start of its name) counts as "entered" by the cursor, and hence whether the tag is included on the stack.
  • A bare/incomplete < carrying no valid tag name must not cause any node to be added to the stack (node resolution ignores it; it contributes no matched child).
  • While the XSD tree is being descended, a tag name with no corresponding child node does not take the resolved node any deeper; the stopping point for resolution is the last node that was matched successfully.
  • If the tag stack is empty, or if nothing beyond the root can be resolved from it, the resolved node is the root.

Once both hold, the parser must place that opening tag's name into token_name and classify the token as ContextTokenType.TAG. What completeness refers to in this rule is the opening start tag under the cursor; the rest of the document may still be unfinished.

For instance, when line index 1 starts with a complete opening tag such as <tool ...>, Position(line=1, character=0) must resolve token_name == "tool". Within the tag name, positions must keep resolving to "tool"; over the attributes that come after, they must keep resolving to whichever attribute names are appropriate.

At the boundaries laid out next, the existing unresolved behavior is what must be kept:

  • When a complete opening tag gets its start after indentation — or otherwise begins partway into its line — the position sitting on its < does not resolve the tag. On the line <test value="0"/>, Position(..., character=4) must give token_name is None as well as token_type == ContextTokenType.UNKNOWN. A position inside test — a name that starts at character 5 — keeps resolving the tag as usual.
  • When the start tag itself is unterminated, its < gets no special resolution — not even at character 0. The existing tolerant incomplete-XML behavior still applies to positions inside the tag name and its attributes.

The types listed below come into play, and they must be importable/constructible as described (they already exist in the codebase, except where noted):

  • XsdTree — its purpose is to wrap a root node; you construct it as XsdTree(root_node), and a .root attribute is exposed by it.
  • XsdNode(name, element=..., parent=None) — it carries a .name attribute and an .attributes mapping (name → attribute), and parent/child relationships are supported by it.
  • XsdAttribute(name, element=...) — it carries a .name attribute.
  • XmlContext — an object that holds context (its required attributes are described below).
  • XmlContextParser — parse(document, position) -> XmlContext is what it exposes.
  • XmlCompletionService(xsd_tree) — get_completion_at_context(context, completion_context) and get_node_completion(context) are both exposed by it.
  • ContextTokenType — an enum that contains at least the member UNKNOWN.
  • CompletionContext, CompletionTriggerKind, CompletionItemKind — these come from the language server protocol types.
  • Range — a type that represents a range in a document.

Part 1: XML Context Parser — List of Attributes

attr_list is the name of an attribute that the XmlContext object must carry; it is a list of strings containing the names of the attributes that the XML element (node) at the parse position has, in document order.

For a node, populating attr_list correctly is something the parser (XmlContextParser.parse) must do, including in these situations:

  • An element that is well-formed and self-closing: <first id="1" test="2"/> → attr_list == ["id", "test"].
  • An element whose start tag is left unclosed (there is no > yet): <first id="1" test="2" → attr_list == ["id", "test"]; no matter whether the cursor sits at the tag name, midway through the attributes, or at the unterminated tag's end.
  • An element that is well-formed, whose start tag spans, and where the cursor then sits within/after the tag: <first id="1" test="2">\n</first> → attr_list == ["id", "test"].

Every one of these cases works the same way: the attribute names are taken from the element's start tag, and the listing follows their order of appearance.

Part 2: XML Context Parser — Removing the Invalid Context

The concept of an "invalid" context is one that must be removed. To be more concrete:

  • An is_invalid flag must no longer be set by the parser, nor relied on by it, to signal unparseable/malformed input.
  • XML that is broken or incomplete, and that would previously have been flagged invalid, must instead be parsed as best as possible, with a normal context as the outcome. As an example, take <first>\n<second attr="value"\n</second> with the cursor sitting within the unterminated <second ... tag: a node_stack of ["first", "second"] (that is, the ancestor tag names, ending with the current element) is what the parser must produce, and the context must not be marked invalid.

Aside from that, the other context fields continue to be populated by the parser as before; these include:

  • node_stack: a list of the ancestor element names, going down to the current node.
  • token_range: a Range that delimits the current token's span.
  • the fields for is_node_content, the token name, and the token type, as supported previously.

Part 3: Completion Service — Attribute Completion Excludes Attributes Already Present

Completion suggestions for the attributes of the current node are what XmlCompletionService.get_completion_at_context(context, completion_context) must return, but any attributes already present on the node must be excluded.

The behavior that is required:

  • Take an XmlContext such that:

    • is_empty holds the value False,
    • the attribute names the element already has are what attr_list lists,
    • token_type holds the value ContextTokenType.UNKNOWN,
    • the current XSD node is node (a set of attributes is declared by it in its .attributes mapping),

    and a CompletionContext whose triggering comes from a trigger character (a space, i.e. CompletionTriggerKind.TriggerCharacter with trigger_character=" "),

    then the completion result the service must return is one whose items are exactly the attributes declared on the node that are not already listed in attr_list, with the order in which the node declares those attributes preserved.

  • On each completion item that gets returned, label must be set to the attribute name, and kind must be set to CompletionItemKind.Variable.

Example: take a node that declares the attributes one, two, three (in that order) and for which attr_list == ["one"]; exactly two items must be yielded — two then three — and both of them have kind Variable.

Part 4: Completion Service — The Empty Context

An empty completion result (no items) is what get_completion_at_context — and attribute completion generally — must return when the context is empty (is_empty is True).

Notes

  • Returning an empty node completion for "invalid" contexts specifically was the previous behavior; that behavior is no longer part of the API, and the invalid-context pathway is gone in its entirety.

Task Specification: XML Context Parser — Detecting Closing Tags

Overview

You must extend the XML context parsing functionality so that it detects closing tags, and you must fix how the token type is classified when a cursor is positioned inside a closing tag.

Public API Surface

It must be possible to import the following and to call it in the way described.

XmlContextParser

A class that provides a parse(document, position) method:

parser = XmlContextParser()
context = parser.parse(document, position)
  • document is a document object that represents the text being parsed (it is the same document type already used elsewhere in this codebase; test helpers build these from raw XML strings).
  • position is a position object that carries line and character integer attributes (0-based) identifying a cursor location within the document.
  • The method returns a context object (detailed below).
The context object

The object that parse(...) returns must expose:

  • is_closing_tag: bool — a new attribute that indicates whether the cursor position lies within a closing tag context (see the rules below).
  • token_type — an existing attribute whose value is one of the members of the ContextTokenType enumeration. The members that are relevant here are ContextTokenType.TAG and ContextTokenType.UNKNOWN.

Required Behavior

is_closing_tag attribute

For a cursor position within the document, is_closing_tag must be True when the position is located inside a closing tag or a self-closing tag, and False in every other case.

Concretely, these cases must hold (character indices are 0-based; the cursor is placed before the character at that index):

  • With <first> </first> and the cursor at character 7 (inside the whitespace text content between the open and close tags): is_closing_tag is False.
  • With <first></first> and the cursor at character 8 (immediately after the < of the closing tag, i.e. within </first>): is_closing_tag is True.
  • With <first></first> and the cursor at character 14 (at the > of the closing tag): is_closing_tag is True.
  • With <first></first > and the cursor at character 14 (within the closing tag, before the trailing whitespace): is_closing_tag is True.
  • With <first></first (an unterminated closing tag) and the cursor at character 10 (within the closing tag name): is_closing_tag is True.
  • With <first/> and the cursor at character 7 (at the > of a self-closing tag): is_closing_tag is True.
  • With <first/ > and the cursor at character 7 (within a self-closing tag that has whitespace before >): is_closing_tag is True.
token_type classification

When <first id="value"><second/></first is parsed with the cursor at character 29, the resulting token_type must be ContextTokenType.TAG.

At character 29 the cursor sits inside the trailing unterminated closing tag </first (the text is <first id="value"><second/></first, where character 28 is the f of </first). This position must be classified as a tag context (ContextTokenType.TAG) rather than as ContextTokenType.UNKNOWN.

Notes

  • All other existing parsing behavior must stay unchanged.
  • is_closing_tag is a required boolean attribute that is always present on the returned context object.

Task Specification: Closing Tag Detection in an XML Context Parser

Overview

You must implement (or fix) a parser that determines XML context: it inspects an XML document at a supplied cursor position and reports contextual details for that position. This task is aimed specifically at the is_closing_tag property of the parsed context.

Public API Surface

It must be possible to import the parser and use it as follows:

  • A parser class XmlContextParser that exposes the method:

    def parse(self, document, position) -> <context object>
    • document: an object representing an XML document; the text content of this object is the source under analysis.
    • position: an object describing a position, with the integer attributes line and character; together they indicate a zero-based cursor location (the line first, then the character offset within that line).

  • The object that parse(...) returns must expose a boolean attribute:

    context.is_closing_tag

The position argument is built using a Position type; its line and character fields can be passed as keywords or positionally (e.g. Position(line=0, character=15)).

Behavior Required of is_closing_tag

For a supplied document and cursor position, context.is_closing_tag must be a boolean indicating whether the cursor is positioned within the closing portion of a tag. The cases below define the behavior that is required:

Cases in which is_closing_tag must be True
  • Input text <first></first, cursor at character 10 → True (the cursor is inside an end tag </first...)
  • Input text <first/>, cursor at character 7 → True (the cursor is at the self-closing terminator of a tag that has no attributes)
  • Input text <first/ >, cursor at character 7 → True (the cursor is at the self-closing terminator, which here has whitespace between / and >; the tag has no attributes)
Cases in which is_closing_tag must be False
  • Input text <first attr="1"/>, cursor at character 15 → False
  • Input text <first attr="1" />, cursor at character 15 → False
  • Input text <first attr="1"/, cursor at character 15 → False

In every one of these three False cases, the tag begins with the element name (first), followed by at least one attribute (attr="1"), and the cursor at character 15 lands at the / self-closing marker or immediately around it. Even though a self-closing marker is present, one or more attributes precede the cursor, so the context is NOT regarded as a closing tag.

The Distinction in Summary

  • A self-closing marker (/, optionally followed by whitespace, then optionally by >) on a tag lacking any attributes yields is_closing_tag == True at the marker position.
  • A tag that carries one or more attributes before the cursor position yields is_closing_tag == False, even when the cursor sits at a self-closing marker.
  • A cursor located inside an explicit end tag (</name) yields is_closing_tag == True.

Constraints

  • The only behavior in scope is the is_closing_tag boolean behavior described above. This task exercises no context properties beyond it.
  • The parser must not raise on any of the inputs above; this includes malformed/unterminated tags (e.g. <first/, <first></first).

Task Specification: Parsing Occurrence Constraints on XSD Nodes

Overview

The XSD parser must be extended so that it exposes the occurrence constraints (minOccurs and maxOccurs) declared on XSD element definitions. These constraints must be parsed and presented as attributes on every node the parser produces.

Public API

The following are relevant to this task and must stay importable/usable:

  • Module: server/services/xsd/parser.py

    • Class: GalaxyToolXsdParser
      • Method: get_tree() — returns a tree object in which the root attribute is the top-level node, and each node exposes a children list of child nodes.

  • The node objects created inside the tree (named XsdNode in this document) must expose two integer attributes:

    • min_occurs
    • max_occurs

Behavior Requirements

Each XSD element definition may carry minOccurs and maxOccurs attributes. While building the tree of nodes, the parser must read these attributes from the corresponding XSD element declarations and store their parsed values on the resulting node.

min_occurs
  • If the XSD element declares a minOccurs attribute, min_occurs must equal that value parsed as an integer.
    • Example: minOccurs="1" yields min_occurs == 1.
    • Example: minOccurs="0" yields min_occurs == 0.
max_occurs
  • If the XSD element declares a numeric maxOccurs attribute, max_occurs must equal that value parsed as an integer.
    • Example: maxOccurs="1" yields max_occurs == 1.
  • If the XSD element declares maxOccurs="unbounded", max_occurs must equal -1.

Example

Take an XSD with the following shape:

<xs:schema xmlns:xs="http://www.w3.org/2001/XMLSchema">
  <xs:element name="testElement" type="CustomComplexType" minOccurs="1" maxOccurs="1">
    ...
  </xs:element>
  <xs:complexType name="CustomComplexType">
    <xs:sequence>
      <xs:element name="firstElement" type="CustomIntSimpleType" minOccurs="0" maxOccurs="unbounded">
        ...
      </xs:element>
    </xs:sequence>
  </xs:complexType>
</xs:schema>

After parsing completes:

  • The root node must end up with min_occurs == 1 and max_occurs == 1.
  • The root node's first child (the firstElement node) must have min_occurs == 0 and max_occurs == -1.

Constraints

  • Parsing behavior that already exists (documentation extraction, attributes, enumerations, tree structure, etc.) must remain unchanged.
  • The occurrence values must be exposed as integers (not strings), with unbounded normalized to -1 in the case of max_occurs.

  • As its arguments, the constructor accepts a server name string together with a lxml.etree.XMLSchema instance that has been built in advance.
  • validate_document accepts a pygls.workspace.Document (at minimum it exposes a path/URI like "file://name.xml" and a source string with the document's XML text) and returns a list of diagnostics.
How validate_document Behaves

The method must behave as follows once a document is supplied:

  1. Work out the document kind from the content. As soon as the root element is <macros>, the document is regarded as a macro definition file; every other document is regarded as a tool document. The decision must rest on the document's actual XML content (its root element) rather than on the file name.

  2. A valid tool document → no diagnostics. If the document parses as XML and, taken as a tool document, conforms to the schema, return an empty list.

No validation against the tool schema happens for macro files (they hold fragments like <token> and <macro> definitions, which are not standalone tools); hence a macros document that is well-formed must produce no diagnostics.

Whether the document is a tool or a macro file (by name or by intent) makes no difference — the same handling applies. Malformed content includes a bare word with no tags (tool) as well as an element that is never closed (<macros>unclosed).
