Token detection semantics (token_name)

Given a cursor position, token_name is the text of the XML token the cursor sits on, or None when the cursor is not on any recognizable token. The character index is zero-based; a cursor at character index c sits between character c-1 and character c of the line.

The token boundaries are inclusive on the token's own characters and exclusive of surrounding structural/whitespace characters. Precisely:

Tag names

For an opening tag such as <tool ...>:

  • The cursor is None when positioned immediately before the < up to and including the boundary at the < itself (i.e. at the character index of < and any position left of the name).
  • The cursor reports the tag name ("tool") when it lands anywhere from immediately after the < through the end of the tag name (i.e. positions covering the name characters, including the boundary just after the last name character).
  • Positions past the tag name but not yet inside an attribute (e.g. the whitespace separating the name from an attribute) report None.

Worked example — content <tool id="test"> on a line (< at character 0):

char range token_name
0 None
1 – 5 "tool"
6 – 8 "id"
9 None
10 – 14 "test"
15 None

Here the attribute is id="test": the key id occupies characters 6–7, its detection region is 6–8; the value test is inside the quotes, its detection region is 10–14, with the delimiter/quote boundaries (char 9, char 15) reporting None.

Attribute keys

The cursor reports the attribute key name (e.g. "id", "value") when positioned over the key characters, including the boundary immediately after the last key character. Positions before the key (on the separating whitespace) or on the = / opening delimiter report None.

Attribute values

The cursor reports the attribute value text (e.g. "test", "value", "0", "1") when positioned strictly inside the value between its surrounding quotes, including the boundary immediately after the last value character but not the closing quote position itself. The opening-quote position and the closing-quote (and beyond) positions report None.

Worked example — line <test value="0"/> (< at character 4, on line 3 in a multi-line doc):

char token_name
4 None
5 – 9 "test"
10 – 15 "value"
16 None
17 – 18 "0"
19 None

Worked example — standalone line <description ...> (< at character 4 on line 2):

char token_name
5 – 16 "description"
17 None

Worked example — incomplete content <other id="1" (no line offset, < at 0):

char token_name
0 None
1 – 6 "other"
7 – 9 "id"
11 – 12 "1"
13 None

The parser must handle these boundaries consistently across multi-line documents (positions are resolved on the correct line/character within the whole document).

Empty-content detection (is_empty)

parse(...) must set is_empty == True when the document has no meaningful XML content at/around the cursor. This applies to documents whose full content is any of:

  • empty string ""
  • a lone <
  • only whitespace (" ", " ")
  • only newlines ("\n\n")

These must yield is_empty == True regardless of the cursor position (including positions beyond the actual content, e.g. character 10 in an empty document, or line 1 of a two-newline document).

Non-empty XML (e.g. <a, <test, or any real element) yields is_empty == False.

Open-element stack (node_stack)

node_stack must be a list of the names of the currently open elements at the cursor position, ordered from the outermost element to the innermost, as strings.

The stack includes the element whose start tag the cursor is currently within, and excludes elements that have already been closed (including self-closed elements) before the cursor position.

Worked examples (single line, <first> starts at character 0):

  • Content <first><second><third>:
    • cursor at character 1 (inside <first) → ["first"]
    • cursor at character 8 (inside <second) → ["first", "second"]
    • cursor at character 16 (inside <third) → ["first", "second", "third"]
  • Content <first><second/><third> (the second element is self-closing):
    • cursor at character 17 (inside <third) → ["first", "third"]

Summary of deliverables

In server/services/context.py, provide:

  1. ContextTokenType enum with UNKNOWN, TAG, ATTRIBUTE_KEY, ATTRIBUTE_VALUE.
  2. XmlContext with the keyword-constructible signature, mutable public attributes (token_name, token_type, node, document_line, target_position, is_empty, node_stack), and the three predicate methods is_tag(), is_attribute_key(), is_attribute_value().
  3. XmlContextService(xsd_tree) exposing xsd_tree and get_xml_context(document, position).
  4. XmlContextParser() exposing parse(document, position) implementing the token detection, empty-content, and open-element-stack semantics above.

    def parse(self, document: Document, position: Position) -> XmlContext

    where Position has integer line and character fields (both zero-based).

    is_node_content: bool

Required Behavior

Given a document and a cursor Position, parse must set is_node_content to True when the position lies in a region that is the textual content of an element — that is, strictly after the end of an element's opening tag (>) and up to and including the position just before / at the start of the following markup (<) — and False otherwise.

More precisely, based on cursor placement relative to the surrounding markup:

  • A position inside an opening tag (on the tag name, on the whitespace/attributes, or anywhere from the leading < up to and including the closing > character of that tag) is not node content → False.

  • A position within the text between an opening tag and its matching closing tag is node content → True.
  • The position at the boundary immediately at the < that begins the closing tag (the point where content ends and closing markup begins) is still considered node content → True.
  • A position inside the closing tag itself (after its leading <, on its name, up to and including its >) is not node content → False.
  • A position immediately after a closing tag's > is not node content → False.

Node resolution (XmlContextService.get_xml_context)

Given a document and a cursor position, the service must determine the sequence (stack) of currently open/relevant XML tag names at that position, then resolve the corresponding XsdNode by descending the XsdTree from the root, matching each tag name in the stack to a child node by name. The resolved node is the deepest matched node in the tree corresponding to the tag stack.

The XML may be broken or incomplete. Resolution must behave as follows.

Consider a tree with this structure:

  • root
    • child
      • subchild
    • sibling

The following position-to-resolved-node behavior is required (positions are zero-based line/character; character positions are cursor offsets, i.e., the cursor sits before the character at that index):

Document <root><child (single line):

  • character 0 through 6 → resolves to root
  • character 7 through 12 → resolves to child

Document <root><child (trailing space after child):

  • character 13 → resolves to child

Document <root attr="4"><child (single line):

  • character 14 → resolves to root
  • character 16 → resolves to child

<root attr="4">
<child/><other

  • line 1, character 8 → resolves to root
  • line 1, character 9 → resolves to root

Document with two lines:

<root attr="4">
<child/><sibling
  • line 1, character 9 → resolves to sibling

Here the trailing unfinished tag <sibling names a valid child of root, so it resolves to sibling.

Document with three lines containing a broken/incomplete tag:

<root attr="4">
    <
<child
  • line 1, character 5 → resolves to root

Tag stack computation (XmlContextParser)

Required tag-stack behavior for the document:

<first><second attr="value"/><third

(single line)

  • character 29 → tag stack is ["first"]
  • character 30 → tag stack is ["first", "third"]

  • A self-closing tag (<tag/>) must not remain on the tag stack after its close; the stack reverts to its parent context.
  • An unfinished opening tag (e.g., <third or <child with no closing >) whose start has been passed by the cursor must be included on the tag stack.
  • The cursor character index is an offset before the character at that index; whether a tag's opening < (and its name start) has been "entered" by the cursor determines inclusion on the stack, per the exact position boundaries listed above.
  • A bare/incomplete < with no valid tag name must not add any node to the stack (it is ignored for node resolution, contributing no matched child).
  • When descending the XSD tree, a tag name that does not correspond to any child node does not deepen the resolved node; resolution stops at the last successfully matched node.
  • When the tag stack is empty or fully unresolvable beyond the root, the resolved node is the root.

Task Specification: XML Context Parser — Closing Tag Detection

Overview

You must implement (or correct) an XML context parser that analyzes an XML document at a given cursor position and reports contextual information about that position. This task focuses specifically on the is_closing_tag property of the parsed context.

Public API Surface

The parser must be importable and usable as follows:

  • A parser class XmlContextParser exposing a method:

    def parse(self, document, position) -> <context object>
    • document: an XML document object whose text content is the source being analyzed.
    • position: a position object with line and character integer attributes indicating a zero-based cursor location (line, then character offset within that line).

  • The object returned by parse(...) must expose a boolean attribute:

    context.is_closing_tag

The position argument is constructed from a Position type with line and character keyword/positional fields (e.g. Position(line=0, character=15)).

Required Behavior: is_closing_tag

Given a document and a cursor position, context.is_closing_tag must be a boolean that reflects whether the cursor is positioned within the closing portion of a tag. The following cases define the required behavior:

Cases where is_closing_tag must be True
  • Text <first></first, cursor at character 10 → True (cursor is inside an end tag </first...)
  • Text <first/>, cursor at character 7 → True (cursor is at the self-closing terminator of a tag with no attributes)
  • Text <first/ >, cursor at character 7 → True (cursor is at the self-closing terminator, with whitespace between / and >, tag has no attributes)
Cases where is_closing_tag must be False
  • Text <first attr="1"/>, cursor at character 15 → False
  • Text <first attr="1" />, cursor at character 15 → False
  • Text <first attr="1"/, cursor at character 15 → False

In each of these three False cases, the tag begins with an element name (first) followed by at least one attribute (attr="1"), and the cursor at character 15 lands at or immediately around the / self-closing marker. Despite the presence of a self-closing marker, the presence of one or more attributes preceding the cursor means the context is NOT considered a closing tag.

Summary of the Distinction

  • A self-closing marker (/, optionally followed by whitespace, optionally followed by >) on a tag without any attributes yields is_closing_tag == True at the marker position.
  • A tag that contains one or more attributes before the cursor position yields is_closing_tag == False, even when the cursor is at a self-closing marker.
  • A cursor inside an explicit end tag (</name) yields is_closing_tag == True.

Constraints

  • Only the is_closing_tag boolean behavior described above is in scope. No other context properties are exercised by this task.
  • The parser must not raise on any of the inputs above, including malformed/unterminated tags (e.g. <first/, <first></first).

Task Specification: Parse Occurrence Constraints for XSD Nodes

Overview

The XSD parser must be extended to expose the occurrence constraints (minOccurs and maxOccurs) declared on XSD element definitions. These constraints must be parsed and made available as attributes on each node produced by the parser.

Public API Surface

The following are relevant to this task and must remain importable/usable:

  • Module: server/services/xsd/parser.py

    • Class: GalaxyToolXsdParser
      • Method: get_tree() — returns a tree object whose root attribute is the top-level node, and where each node exposes a children list of child nodes.

  • The node objects (referred to here as XsdNode) produced within the tree must expose two integer attributes:

    • min_occurs
    • max_occurs

Required Behavior

Each XSD element definition may include minOccurs and maxOccurs attributes. When the parser builds the tree of nodes, it must read these attributes from the corresponding XSD element declarations and store their parsed values on the resulting node.

min_occurs
  • When the XSD element declares a minOccurs attribute, min_occurs must equal that value parsed as an integer.
    • Example: minOccurs="1" yields min_occurs == 1.
    • Example: minOccurs="0" yields min_occurs == 0.
max_occurs
  • When the XSD element declares a numeric maxOccurs attribute, max_occurs must equal that value parsed as an integer.
    • Example: maxOccurs="1" yields max_occurs == 1.
  • When the XSD element declares maxOccurs="unbounded", max_occurs must equal -1.

Illustrative Example

Given an XSD of the following shape:

<xs:schema xmlns:xs="http://www.w3.org/2001/XMLSchema">
  <xs:element name="testElement" type="CustomComplexType" minOccurs="1" maxOccurs="1">
    ...
  </xs:element>
  <xs:complexType name="CustomComplexType">
    <xs:sequence>
      <xs:element name="firstElement" type="CustomIntSimpleType" minOccurs="0" maxOccurs="unbounded">
        ...
      </xs:element>
    </xs:sequence>
  </xs:complexType>
</xs:schema>

After parsing:

  • The root node must have min_occurs == 1 and max_occurs == 1.
  • The root node's first child (the firstElement node) must have min_occurs == 0 and max_occurs == -1.

Constraints

  • Existing parsing behavior (documentation extraction, attributes, enumerations, tree structure, etc.) must remain unchanged.
  • The occurrence values must be exposed as integers (not strings), with unbounded normalized to -1 for max_occurs.

Behavior of validate_document

Given a document, the method must:

  1. Determine document kind by content. A document is treated as a macro definition file when its root element is <macros>; otherwise it is treated as a tool document. This determination must be based on the document's actual XML content (the root element), not on the file name.

  2. Valid tool document → no diagnostics. If the document parses as XML and conforms to the schema as a tool document, return an empty list.

  3. Valid macro file → no diagnostics. If the document's root element is <macros> and it is well-formed XML, return an empty list. Macro files are not validated against the tool schema (they contain fragments such as <token> and <macro> definitions that are not standalone tools), so a well-formed macros document must produce no diagnostics.

  4. Schema-invalid tool document → one or more diagnostics. If the document is well-formed XML but does not conform to the tool schema, return a non-empty list of diagnostics (one diagnostic per schema violation).

  5. Malformed XML (syntax error) → exactly one diagnostic. If the document text cannot be parsed as XML at all, return a list containing exactly one diagnostic describing the syntax error. This applies regardless of whether the document is (by name or intent) a tool or a macro file. Examples of malformed content include a bare word with no tags (tool) and an unclosed element (<macros>unclosed).

Each diagnostic in the returned list should be a diagnostic object of the kind used by the language-server framework (pygls / lsprotocol), carrying at least a message and a source range describing the location of the problem.
