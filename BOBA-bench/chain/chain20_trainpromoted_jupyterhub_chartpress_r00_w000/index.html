Task Specification: chartpress Module

Overview

Implement a Python module named chartpress (importable as import chartpress) that builds container images for a Helm chart and updates the chart's manifest files with version/tag identifiers derived from git history. The module must expose a set of helper functions and a main entry point that reads configuration from a chartpress.yaml file in the current working directory.

Public API Surface

The following names must be importable directly from the chartpress module:

  • GITHUB_TOKEN_KEY — a module-level string constant holding the name of the environment variable used to look up a GitHub token.
  • git_remote(repo) — function.
  • latest_tag_or_mod_commit(path) — function.
  • _strip_identifiers_build_suffix(identifier) — function.
  • _get_identifier(tag, n_commits, commit, long) — function.
  • main(argv) — function accepting a list of command-line argument strings.

Helper Function Behavior

_strip_identifiers_build_suffix(identifier)

Given a version-like identifier string, return the identifier with its trailing build-suffix removed. The build suffix is a segment of the form .NNN.<hash> appended to the base version (where NNN is a zero-padded commit count and <hash> is a short commit hash).

  • _strip_identifiers_build_suffix("0.1.2-005.asdf1234") → "0.1.2"
  • _strip_identifiers_build_suffix("0.1.2-alpha.1.005.asdf1234") → "0.1.2-alpha.1"

Note that when the base version contains a prerelease part (e.g. -alpha.1), that prerelease part is retained; only the final .NNN.<hash> build suffix is stripped.

_get_identifier(tag, n_commits, commit, long)

Construct a full identifier string from a base tag, a number of commits since that tag (n_commits, passed as a string), a short commit hash (commit), and a boolean long flag.

Rules:

  • n_commits is interpreted as an integer and zero-padded to at least 3 digits when included in the output.
  • When long is False and n_commits equals 0, return the tag unchanged (no build suffix).
  • Otherwise (when long is True, or when n_commits is nonzero), append a build suffix to the tag.
    • The suffix is joined to the tag differently depending on whether the tag already contains a prerelease component:
      • If the tag has no prerelease part (no - present, e.g. 0.1.2), the suffix is joined with a hyphen: <tag>-<padded_n_commits>.<commit>.
      • If the tag already has a prerelease part (contains -, e.g. 0.1.2-alpha.1), the suffix is joined with a dot: <tag>.<padded_n_commits>.<commit>.

Examples:

  • _get_identifier("0.1.2", "0", "asdf123", True) → "0.1.2-000.asdf123"
  • _get_identifier("0.1.2", "0", "asdf123", False) → "0.1.2"
  • _get_identifier("0.1.2", "5", "asdf123", False) → "0.1.2-005.asdf123"
  • _get_identifier("0.1.2-alpha.1", "0", "asdf1234", True) → "0.1.2-alpha.1.000.asdf1234"
  • _get_identifier("0.1.2-alpha.1", "0", "asdf1234", False) → "0.1.2-alpha.1"
  • _get_identifier("0.1.2-alpha.1", "5", "asdf1234", False) → "0.1.2-alpha.1.005.asdf1234"
git_remote(repo)

Given a GitHub owner/repo slug string, return the git remote URL to use:

  • If the environment variable named by GITHUB_TOKEN_KEY is set, return an HTTPS URL that embeds the token: https://<token>@github.com/<repo>.
  • If that environment variable is not set, return the SSH form: git@github.com:<repo>.

Examples (with GITHUB_TOKEN_KEY env var set to test-github-token):

  • git_remote("jupyterhub/helm-chart") → "https://test-github-token@github.com/jupyterhub/helm-chart"

With the env var unset:

  • git_remote("jupyterhub/helm-chart") → "git@github.com:jupyterhub/helm-chart"
latest_tag_or_mod_commit(path)

Return the short (7-character) commit hash of the most relevant commit for a given file path in the current git repository. The relevant commit is the more recent of:

  • the latest git tag reachable in history, and
  • the latest commit that modified the given path.

Behavior:

  • For a path last modified at or before the latest tag, return the short hash of the tagged commit.
  • For a path modified in a commit made after the latest tag, return the short hash of that later commit.

The returned value is the first 7 characters of the commit's full SHA.

chartpress.yaml Configuration

main reads a chartpress.yaml file from the current working directory. Its structure (as consumed by this task) is:

charts:
  - name: <chart name>
    imagePrefix: <prefix for image names>
    resetTag: <tag value used with --reset>
    resetVersion: <chart version value used with --reset>
    repo:
      git: <owner/repo slug>
      published: <published repo URL>
    paths:
      - <extra chart paths...>
    images:
      <image name>:
        buildArgs:
          <ARG_NAME>: <value, may contain {TAG} and {LAST_COMMIT} placeholders>
        contextPath: <docker build context>
        dockerfilePath: <path to Dockerfile>
        valuesPath:
          - <dotted paths into values.yaml to update>
        paths:
          - <extra image paths...>

The chart directory (named by name) contains a Chart.yaml (with a version: field) and a values.yaml file whose entries reference image tags.

main(argv) Behavior

main accepts a list of argument strings and performs, per chart and per image, the following. All human-readable progress messages described below must be printed to standard output.

Version/tag computation

For each chart, compute a version identifier and, for each image, an image tag, derived from git history using the helper logic above:

  • The base tag comes from the latest git tag if present.
  • When no git tag exists, use 0.0.1 as the fallback base version.
  • The number of commits since the base tag and the short commit hash are incorporated per the _get_identifier rules (default, non---long form).

For example, on a repository whose only tag context yields base 0.0.1 with one commit and short hash <sha>, the computed identifier is 0.0.1-001.<sha>.

Building images

For each image, invoke a docker build. The build command must:

  • Tag the built image as <imagePrefix><imageName>:<computed image tag>.
  • Pass each entry of buildArgs as a --build-arg <NAME>=<value> argument, in the order given.
    • Build-arg values may contain the placeholders {TAG} and {LAST_COMMIT}, which must be substituted with the computed image tag and the relevant short commit hash respectively, before being passed.
      • A static value like test is passed unchanged: --build-arg TEST_STATIC_BUILD_ARG=test.
      • A value like {TAG}-{LAST_COMMIT} becomes --build-arg TEST_DYNAMIC_BUILD_ARG=<tag>-<sha>.

Skip rebuilding when the image for the computed tag already exists / is unchanged; in that case print a message containing Skipping build.

Updating chart manifests

After determining the version and image tags, update the chart's files and print a line for each field updated:

  • Update Chart.yaml's version field. Print: Updating <chart>/Chart.yaml: version: <version>
  • Update each values.yaml entry named by an image's valuesPath. Each valuesPath entry is a dotted path into values.yaml supporting both mapping keys and list indices (e.g. image, list.0, list.1.image). Set each to <imagePrefix><imageName>:<image tag>. Print, for each: Updating <chart>/values.yaml: <valuesPath>: <imagePrefix><imageName>:<image tag>

When a file field already holds the target value, no update line for that field should be printed (i.e., only actual changes are reported).

Command-line options

main must support the following options within argv:

  • (no options): build images and update manifests using the git-derived identifier.

  • --reset: instead of using git-derived values, set the chart version to the chart's configured resetVersion and image tags to the chart's configured resetTag. This produces update lines such as:

    • Updating testchart/Chart.yaml: version: <resetVersion>
    • Updating testchart/values.yaml: image: <imagePrefix><imageName>:<resetTag>
    • Updating testchart/values.yaml: list.0: <imagePrefix><imageName>:<resetTag>
    • Updating testchart/values.yaml: list.1.image: <imagePrefix><imageName>:<resetTag>

  • --skip-build: do not perform any docker build (no image is built or tagged). Manifest updates still occur.

  • --tag <value>: use the given explicit <value> as the base tag/version for the chart version and image tags instead of deriving it from git. For example --tag 1.2.3-test.tag yields:

    • Updating testchart/Chart.yaml: version: 1.2.3-test.tag
    • Updating testchart/values.yaml: image: <imagePrefix><imageName>:1.2.3-test.tag
    • and correspondingly for each valuesPath.

  • --long: force the full build-suffix form of the identifier even when the commit count is zero. When the current commit is exactly at a git tag 1.2.3-test.tag with short hash <sha>, --long produces version/tags of the form 1.2.3-test.tag.000.<sha>, e.g.:

    • Updating testchart/Chart.yaml: version: 1.2.3-test.tag.000.<sha>
    • Updating testchart/values.yaml: image: <imagePrefix><imageName>:1.2.3-test.tag.000.<sha>

Options may be combined (e.g. --skip-build --tag <value>, --skip-build --long).

Git tag detection

When a git tag exists that matches the current commit, main (without --tag and without --long) uses that tag as the base version, producing the non-suffixed form. If the manifests already contain the resulting values, no Updating lines are printed.

Environment / Dependencies

  • The module operates against the git repository rooted at the current working directory.
  • Image builds are performed via docker (the docker CLI output — e.g. lines beginning with Successfully tagged <image>:<tag> — is surfaced to standard output when a build occurs, and absent when builds are skipped).

Notes

  • All "Updating ..." and build progress output must go to standard output so it can be observed by callers.
  • The dotted valuesPath syntax must resolve list indices as integer positions within YAML sequences and string keys as mapping keys, at arbitrary nesting depth.

Task Specification: chartpress — Chart & Image Version Bumping and Build/Publish Tooling

Overview

Provide a top-level Python module named chartpress (importable with import chartpress, from chartpress.py) that automates Helm chart and Docker image release work. It must:

  1. Build Docker images declared in chartpress.yaml.
  2. Compute image tags and Helm chart versions from Git history.
  3. Update each chart's Chart.yaml and values.yaml in place.
  4. Optionally package and publish a chart to a gh-pages branch.

The module must expose main(argv_list) and the importable constants and helper functions documented below.

Configuration: chartpress.yaml

chartpress.yaml is located in a directory that is the parent of one or more Helm chart directories. Each chart directory is named after the chart and contains files such as Chart.yaml, values.yaml, and a templates/ directory.

The supported structure is:

charts:
  - name: <chart-name>              # matches the chart directory name
    resetTag: <string>              # image tag written by --reset
    resetVersion: <string>          # chart version written by --reset
    repo:
      git: <string>                 # publication repository/remote; may be "."
      published: <url>              # public base URL for packaged charts
    paths:                          # OPTIONAL additional chart paths
      - <path>
    images:
      <image-name>:
        buildArgs:                  # OPTIONAL Docker build arguments
          <KEY>: <value>            # may contain {TAG} and {LAST_COMMIT}
        contextPath: <path>         # build context, relative to chartpress.yaml
        dockerfilePath: <path>      # Dockerfile, relative to chartpress.yaml
        valuesPath:                 # values.yaml locations to update
          - <dotted-or-indexed path>
        paths:                      # OPTIONAL additional image paths
          - <path>

All configured paths, contextPath, and dockerfilePath values are interpreted relative to the directory containing chartpress.yaml. contextPath and dockerfilePath are independent: the Dockerfile may be outside the build context.

A valuesPath is split into dot-separated segments. A numeric segment is a list index; for example, list.0 selects the first item of list, while list.1.image selects the image field in its second item.

Git-Based Version and Tag Semantics

Base version

The base is the latest Git tag reachable from the relevant commit. A clean state represented by that tagged commit uses the tag itself. If no tag is reachable, use 0.0.1 as the base.

An explicit --tag bypasses this automatic base and history selection.

Selecting the relevant commit

Path relevance selects the commit whose seven-character short hash is included in an automatically generated chart version or image tag:

  • Consider both the latest tag reachable from HEAD and the latest commit that modified any relevant path.
  • Select whichever commit is newer in the current history.
  • Thus, a tag newer than the last relevant path change advances the result to the tag; a relevant modification after the tag advances it to that modification; and a modification at the tag resolves to that same commit.
  • When no tag is reachable, select the latest relevant-path modification.

For multiple relevant paths, use the newest modification commit among all of them.

Developmental identifiers and commit counting

When the relevant commit is after its base tag, or when no tag exists, append a developmental suffix containing a commit count and the relevant commit's short hash:

<base>-<NNN>.<sha>

For a base that already contains a SemVer prerelease component (and therefore contains -), append the suffix with . instead:

<prerelease-base>.<NNN>.<sha>

NNN is zero-padded to three digits. It is the total number of commits in the repository history after the base tag through and including the relevant commit; the tagged commit itself corresponds to zero. With the 0.0.1 fallback, it is the total number of commits from the beginning of history through and including the relevant commit.

The count includes every commit in that range, even commits that modified no path relevant to the chart or image. Path relevance controls which commit supplies <sha> and whether a chart or image advances; it does not filter the commits counted for NNN. For example, if an initial untagged commit is followed by one unrelated commit and then a chart-relevant commit, the chart-relevant identifier is 0.0.1-003.<sha>, not 0.0.1-002.<sha>.

Long form

Without --long, a relevant commit at a tag has no suffix. With --long, a zero-count suffix is included even for that clean tagged state:

  • Release base: 1.2.3-000.<sha>
  • Prerelease base: 1.2.3-alpha.1.000.<sha>

A developmental state with a positive count has the same suffixed representation whether or not --long is supplied.

Relevant paths

For a chart version in Chart.yaml:

  • Changes anywhere under the chart's own named directory are relevant.
  • Every path in the chart-level paths list is relevant.
  • Any change that updates one of the chart's images is also relevant and must advance the chart version.
  • A change only to an unrelated file elsewhere under the parent directory must not advance the chart.

For an image tag in values.yaml:

  • The image's contextPath is relevant.
  • Its dockerfilePath is relevant even when the Dockerfile is outside the context.
  • Every path in the image-level paths list is relevant.

Consequently:

  • An unrelated file changes neither the chart version nor image tags.
  • A chart-only additional path advances Chart.yaml but not image tags.
  • An image-only additional path advances that image tag and also advances Chart.yaml because the chart references an updated image.
  • Unrelated commits between relevant commits still contribute to the later identifier's numeric commit count.
