Module Specification: chartpress

Overview

A Python module going by the name chartpress has to be implemented (so that import chartpress works); its job is to build container images for a Helm chart and to write version/tag identifiers — obtained from git history — into the chart's manifest files. A set of helper functions must be exposed by the module, together with a main entry point that takes its configuration from a chartpress.yaml file located in the current working directory.

Public API

The names listed here must all be importable directly from the chartpress module:

  • GITHUB_TOKEN_KEY — a string constant at module level whose value is the name of the environment variable in which a GitHub token is looked up.
  • git_remote(repo) — a function.
  • latest_tag_or_mod_commit(path) — a function.
  • _strip_identifiers_build_suffix(identifier) — a function.
  • _get_identifier(tag, n_commits, commit, long) — a function.
  • main(argv) — a function that accepts the command-line arguments in the form of a list of strings.

How the Helper Functions Behave

_strip_identifiers_build_suffix(identifier)

The input is a version-like identifier string, and the output is that same identifier minus its trailing build suffix. A build suffix is a segment shaped like .NNN.<hash> that has been appended to the base version — NNN here denotes a zero-padded commit count, and <hash> a short commit hash.

  • _strip_identifiers_build_suffix("0.1.2-005.asdf1234") → "0.1.2"
  • _strip_identifiers_build_suffix("0.1.2-alpha.1.005.asdf1234") → "0.1.2-alpha.1"

Should the base version contain a prerelease part (e.g. -alpha.1), that part is kept; what gets stripped is only the final .NNN.<hash> build suffix.

_get_identifier(tag, n_commits, commit, long)

Out of a base tag, a count of commits made since that tag (n_commits, given as a string), a short commit hash (commit), and a boolean long flag, a complete identifier string is assembled.

Rules:

  • n_commits is to be read as an integer; wherever it occurs in the output, it is zero-padded so as to occupy at least 3 digits.
  • If long is False and n_commits equals 0, the tag is returned unchanged (with no build suffix).
  • In every other case (long is True, or n_commits is nonzero), a build suffix is appended to the tag.
    • How that suffix is attached to the tag depends on whether a prerelease component is already part of the tag:
      • A tag carrying no prerelease part (no - present, e.g. 0.1.2) gets the suffix joined on with a hyphen: <tag>-<padded_n_commits>.<commit>.
      • A tag that already has a prerelease part (contains -, e.g. 0.1.2-alpha.1) gets the suffix joined on with a dot: <tag>.<padded_n_commits>.<commit>.

Examples:

  • _get_identifier("0.1.2", "0", "asdf123", True) → "0.1.2-000.asdf123"
  • _get_identifier("0.1.2", "0", "asdf123", False) → "0.1.2"
  • _get_identifier("0.1.2", "5", "asdf123", False) → "0.1.2-005.asdf123"
  • _get_identifier("0.1.2-alpha.1", "0", "asdf1234", True) → "0.1.2-alpha.1.000.asdf1234"
  • _get_identifier("0.1.2-alpha.1", "0", "asdf1234", False) → "0.1.2-alpha.1"
  • _get_identifier("0.1.2-alpha.1", "5", "asdf1234", False) → "0.1.2-alpha.1.005.asdf1234"
git_remote(repo)

The function receives a GitHub owner/repo slug string and returns the git remote URL that is to be used:

  • When the environment variable that GITHUB_TOKEN_KEY names is set, what comes back is an HTTPS URL with the token embedded: https://<token>@github.com/<repo>.
  • When that environment variable is not set, the SSH form is what comes back instead: git@github.com:<repo>.

Examples (here the GITHUB_TOKEN_KEY env var holds the value test-github-token):

  • git_remote("jupyterhub/helm-chart") → "https://test-github-token@github.com/jupyterhub/helm-chart"

If the env var is unset:

  • git_remote("jupyterhub/helm-chart") → "git@github.com:jupyterhub/helm-chart"
latest_tag_or_mod_commit(path)

For a file at path in the current git repository, the function returns the short (7-character) commit hash of the most relevant commit. Two candidates are in play, and the relevant one is whichever of them is more recent:

  • the most recent git tag reachable in history, and
  • the most recent commit that modified the given path.

Behavior:

  • When the path's last modification lies at or before the latest tag, the short hash of the tagged commit is what gets returned.
  • When the path was modified in a commit made after the latest tag, the short hash of that later commit is what gets returned.

The value handed back is the commit's full SHA with everything after its first 7 characters removed.

Configuration via chartpress.yaml

The file that main reads is a chartpress.yaml located in the current working directory. In the form this task consumes it, the structure is:

charts:
  - name: <chart name>
    imagePrefix: <prefix for image names>
    resetTag: <tag value used with --reset>
    resetVersion: <chart version value used with --reset>
    repo:
      git: <owner/repo slug>
      published: <published repo URL>
    paths:
      - <extra chart paths...>
    images:
      <image name>:
        buildArgs:
          <ARG_NAME>: <value, may contain {TAG} and {LAST_COMMIT} placeholders>
        contextPath: <docker build context>
        dockerfilePath: <path to Dockerfile>
        valuesPath:
          - <dotted paths into values.yaml to update>
        paths:
          - <extra image paths...>

Inside the chart directory (which takes its name from name) there is a Chart.yaml (one that carries a version: field) and a values.yaml file whose entries refer to image tags.

Behavior of main(argv)

main accepts a list of argument strings as input and then performs the actions below, chart by chart and image by image. All human-readable progress messages described below must be printed out on standard output.

Version and tag computation

A version identifier gets computed for each chart and an image tag for each image, with git history as the source and the helper logic above applied:

  • When the latest git tag is present, it supplies the base tag.
  • When there is no git tag, 0.0.1 steps in as the fallback base version.
  • The commit count since the base tag, along with the short commit hash, is folded in per the _get_identifier rules (default, non---long form).

As an example, take a repository whose only tag context amounts to base 0.0.1, one commit, and short hash <sha>; the identifier computed there is 0.0.1-001.<sha>.

Building the images

For each image, a docker build is invoked. The command that performs the build must:

  • put the tag <imagePrefix><imageName>:<computed image tag> on the image being built.
  • include a --build-arg <NAME>=<value> argument for each buildArgs entry, in the order the entries are given.
    • The placeholders {TAG} and {LAST_COMMIT} may occur inside build-arg values; before an argument is passed, they must have been substituted — {TAG} with the computed image tag, {LAST_COMMIT} with the relevant short commit hash.
      • A static value such as test goes through unchanged: --build-arg TEST_STATIC_BUILD_ARG=test.
      • A value such as {TAG}-{LAST_COMMIT} comes out as --build-arg TEST_DYNAMIC_BUILD_ARG=<tag>-<sha>.

If the image for the computed tag already exists / is unchanged, the rebuild is skipped; in that situation, a message that contains Skipping build is printed.

Updating the chart manifests

Once the version and the image tags have been determined, the chart's files are updated, and for each updated field a line is printed:

  • The version field of Chart.yaml is updated. Print: Updating <chart>/Chart.yaml: version: <version>
  • Each values.yaml entry named by an image's valuesPath is updated as well; every such entry is a dotted path into values.yaml, one that supports both mapping keys and list indices (e.g. image, list.0, list.1.image). The value written into each is <imagePrefix><imageName>:<image tag>. For each one, print: Updating <chart>/values.yaml: <valuesPath>: <imagePrefix><imageName>:<image tag>

If a file field already holds the target value, the update line for that field should be left out — put differently, only actual changes are reported.

Options on the command line

The options below must be supported by main within argv:

  • (no options): images are built and manifests updated, with the git-derived identifier in use.

  • --reset: git-derived values are set aside; the chart version is set to the chart's configured resetVersion and the image tags to the chart's configured resetTag. Update lines such as the following result:

    • Updating testchart/Chart.yaml: version: <resetVersion>
    • Updating testchart/values.yaml: image: <imagePrefix><imageName>:<resetTag>
    • Updating testchart/values.yaml: list.0: <imagePrefix><imageName>:<resetTag>
    • Updating testchart/values.yaml: list.1.image: <imagePrefix><imageName>:<resetTag>

  • --skip-build: no docker build of any kind is performed (no image gets built or tagged). Manifest updates still happen.

  • --tag <value>: the base tag/version for the chart version and the image tags is not derived from git; the explicitly given <value> is used in its place. For example, --tag 1.2.3-test.tag yields:

    • Updating testchart/Chart.yaml: version: 1.2.3-test.tag
    • Updating testchart/values.yaml: image: <imagePrefix><imageName>:1.2.3-test.tag
    • and likewise for each valuesPath.

  • --long: even when the commit count is zero, the identifier is forced into its full build-suffix form. If the current commit sits exactly at git tag 1.2.3-test.tag and has short hash <sha>, then --long produces version/tags shaped like 1.2.3-test.tag.000.<sha>, e.g.:

    • Updating testchart/Chart.yaml: version: 1.2.3-test.tag.000.<sha>
    • Updating testchart/values.yaml: image: <imagePrefix><imageName>:1.2.3-test.tag.000.<sha>

The options may be combined with one another (e.g. --skip-build --tag <value>, --skip-build --long).

Detecting git tags

If a git tag matching the current commit exists, main — run without --tag and without --long — adopts that tag as the base version, which results in the non-suffixed form. Should the manifests already contain the resulting values, no Updating lines are printed.

Environment and Dependencies

  • What the module operates against is the git repository rooted at the current working directory.
  • Docker performs the image builds (when a build occurs, the docker CLI output — e.g. lines beginning with Successfully tagged <image>:<tag> — shows up on standard output, and when builds are skipped it is absent).

Notes

  • All output of the "Updating ..." kind, together with build progress output, must be sent to standard output, where callers can observe it.
  • Under the dotted valuesPath syntax, list indices must be resolved as integer positions within YAML sequences and string keys as mapping keys, however deeply the nesting goes.

Task Specification: chartpress — Version Bumping and Build/Publish Tooling for Charts and Images

Overview of the Module

A top-level Python module named chartpress is to be provided (from chartpress.py, importable with import chartpress) that takes care of Helm chart and Docker image release work automatically. It must:

  1. Build the Docker images that chartpress.yaml declares.
  2. Compute image tags and Helm chart versions on the basis of Git history.
  3. Update, in place, the Chart.yaml and values.yaml of each chart.
  4. Optionally package a chart and publish it to a gh-pages branch.

The module must expose main(argv_list) as well as the constants and helper functions that can be imported, as described below.

The chartpress.yaml Configuration File

The directory in which chartpress.yaml resides is the parent of one or more Helm chart directories. A chart directory bears the chart's name and holds files such as Chart.yaml, values.yaml, and a templates/ directory.

The structure that is supported is the following:

charts:
  - name: <chart-name>              # matches the chart directory name
    resetTag: <string>              # image tag written by --reset
    resetVersion: <string>          # chart version written by --reset
    repo:
      git: <string>                 # publication repository/remote; may be "."
      published: <url>              # public base URL for packaged charts
    paths:                          # OPTIONAL additional chart paths
      - <path>
    images:
      <image-name>:
        buildArgs:                  # OPTIONAL Docker build arguments
          <KEY>: <value>            # may contain {TAG} and {LAST_COMMIT}
        contextPath: <path>         # build context, relative to chartpress.yaml
        dockerfilePath: <path>      # Dockerfile, relative to chartpress.yaml
        valuesPath:                 # values.yaml locations to update
          - <dotted-or-indexed path>
        paths:                      # OPTIONAL additional image paths
          - <path>

Interpret every configured paths, contextPath, and dockerfilePath value as relative to the directory in which chartpress.yaml sits. contextPath and dockerfilePath do not depend on each other: the Dockerfile may lie outside the build context.

To evaluate a valuesPath, break it into segments at the dots. A segment that is numeric addresses a list index; thus list.0 picks out the first item of list, and list.1.image picks out the image field inside its second item.

How Git History Drives Versions and Tags

The base

As the base, use the latest Git tag that is reachable from the relevant commit. When the state is clean and sits at that tagged commit, the tag itself is what gets used. Should there be no reachable tag, 0.0.1 serves as the base.

Supplying --tag explicitly causes this automatic selection of base and history to be bypassed.

How the relevant commit is chosen

Which commit ends up supplying the seven-character short hash inside an automatically generated chart version or image tag is decided by path relevance:

  • Take into account both the latest tag reachable from HEAD and the latest commit that modified any relevant path.
  • Of those two commits, select the one that is newer in the current history.
  • Accordingly: the result advances to the tag when the tag is newer than the last relevant path change; it advances to a relevant modification when that modification came after the tag; and a modification at the tag resolves to that same commit.
  • If no tag is reachable, the latest relevant-path modification is what gets selected.

Where multiple relevant paths exist, use the newest modification commit among all of them.

Developmental identifiers and the counting of commits

A developmental suffix — one that contains a commit count and the relevant commit's short hash — is appended when the relevant commit is after its base tag, or when no tag exists:

<base>-<NNN>.<sha>

If the base already contains a SemVer prerelease component (and therefore contains -), the suffix is instead appended with .:

<prerelease-base>.<NNN>.<sha>

Zero-pad NNN to three digits. Its value is the total number of commits in the repository history after the base tag, counted through and including the relevant commit; the tagged commit itself corresponds to a count of zero. Under the 0.0.1 fallback, the value is the total number of commits from the beginning of history through and including the relevant commit.

Every commit in that range is included in the count, even commits that modified no path relevant to the chart or image. Path relevance governs which commit supplies <sha> and whether a chart or image advances; the commits counted for NNN are not filtered by it. Example: an initial untagged commit is followed by one unrelated commit and then a chart-relevant commit; the chart-relevant identifier is then 0.0.1-003.<sha>, and not 0.0.1-002.<sha>.

The long form

When --long is not supplied, a relevant commit located at a tag carries no suffix. Supplying --long includes a zero-count suffix even for that clean tagged state:

  • With a release base: 1.2.3-000.<sha>
  • With a prerelease base: 1.2.3-alpha.1.000.<sha>

For a developmental state whose count is positive, the representation with its suffix is the same regardless of whether --long was supplied.

Which paths are relevant

Where a chart version in Chart.yaml is concerned:

  • A change anywhere beneath the chart's own named directory counts as relevant.
  • All of the paths in the chart-level paths list are relevant.
  • Relevance also covers any change that updates one of the chart's images, and the chart version must be advanced by it.
  • A change to only an unrelated file somewhere else under the parent directory must not advance the chart.

Where an image tag in values.yaml is concerned:

  • The image's contextPath counts as relevant.
  • Even when the Dockerfile is outside the context, the image's dockerfilePath is relevant.
  • All of the paths in the image-level paths list are relevant.

From this it follows that:

  • Neither the chart version nor the image tags are changed by an unrelated file.
  • When an additional path is chart-only, Chart.yaml advances while image tags do not.
  • An additional path that is image-only advances that image tag, and Chart.yaml advances as well, since the chart references an image that has been updated.
  • The numeric commit count of the later identifier still receives contributions from unrelated commits sitting between relevant commits.

Entry Point via the Command Line: chartpress.main(args)

A list of argument strings is what main accepts — chartpress.main(["--skip-build"]) is one example — and chartpress.yaml is read from the current working directory.

Running with no flags: main([])

Each configured chart and each configured image is handled as follows:

  • The chart version and every image tag are computed according to the rules above.
  • Each required image is built as <prefix><image-name>:<computed-tag>. By default the prefix is the chart's name with / after it (for instance testchart/, which yields testchart/testimage:<tag>).
  • Every configured build argument is passed as --build-arg KEY=VALUE, with dynamic placeholders resolved first as documented under render_build_args.
  • The computed chart version is written to Chart.yaml: version.
  • For each image, its full image reference is written to all of the valuesPath locations configured for that image, in values.yaml.

Update lines are emitted only for actual value changes. They take these forms:

Updating testchart/Chart.yaml: version: <version>
Updating testchart/values.yaml: <valuesPath>: <image-ref>

Indexed paths like list.0 and list.1.image are covered by this. Docker's Successfully tagged <image>:<tag> output is what a successful Docker build exposes. When the exact image is already present locally or in the registry and need not be rebuilt, a line containing Skipping build is printed, and Successfully tagged is not emitted for that image.

--reset

Image building is skipped. Each chart's configured resetVersion is written to Chart.yaml, and each configured image is written using resetTag at every valuesPath. Where values change, the corresponding Updating ... lines are emitted.

--skip-build

The version/tag computation and the YAML updates are carried out, with no images being built. Successfully tagged must not appear.

--tag <TAG>

Automatic version and tag computation is overridden: Chart.yaml: version is set to <TAG>, and every image tag is set to <TAG>.

--long

For chart versions and image tags, the long identifier form applies; at a tagged state, that includes a zero-count suffix.

--image-prefix <PREFIX>

The normal image prefix is overridden, so image references become <PREFIX><image-name>:<tag> (for instance test-prefix/testimage:<tag>). The chart version stays unaffected.

--publish-chart

The chart is packaged and published to the gh-pages branch of the repository that repo.git configures. When repo.git has the value ., the current repository is what that denotes.

Output observable on success includes:

Branch 'gh-pages' set up to track remote branch 'gh-pages' from 'origin'.
Successfully packaged chart and saved it to:

The path of the package must end in /<chart-name>-<version>.tgz.

The new package metadata must be merged by the publication into the gh-pages index.yaml that is already there, rather than that file being replaced. Chart/version entries that exist already remain, and the new version is added. Distinct versions — for example <tag>.001.<sha> — are produced by successive development commits, and publishing one of them must not overwrite the versions published before.

--extra-message <MSG>

When publishing, the commit message created on gh-pages includes <MSG>.

End-to-End Examples of Behavior

The setup: chart directory testchart; one image named testimage; scalar image references at image, list.0, and list.1.image; resetTag: test-reset-tag; and resetVersion: 0.0.1-test.reset.version. Then:

  • For the first untagged commit <sha>, a normal run computes 0.0.1-001.<sha>, builds testchart/testimage:0.0.1-001.<sha>, resolves the static and dynamic build arguments, and puts the version/reference into all of the configured YAML locations.
  • Following a second commit that is unrelated, the relevant chart and image commits do not advance. Given a chart-relevant third commit whose hash is <chart-sha>, the chart becomes 0.0.1-003.<chart-sha>, since the unrelated commit still adds to the total history depth; for a change that is chart-only, image tags do not advance.
  • Suppose the fourth commit changes an image-relevant path and its hash is <image-sha>; both the image and the chart then advance, with 004 as the count.
  • The reset version and tag that are configured get written by main(["--reset"]).
  • A normal run afterwards, with no relevant changes and the image already available, prints Skipping build.
  • With main(["--skip-build", "--tag", "1.2.3-test.tag"]), 1.2.3-test.tag is written everywhere, and nothing is built.
  • Let 1.2.3-test.tag tag that commit; a later main(["--skip-build"]) then makes no Updating writes, given that the files already hold those values.
  • main(["--skip-build", "--long"]) writes 1.2.3-test.tag.000.<sha> into the chart and image references.
  • Running main(["--skip-build", "--image-prefix", "test-prefix/"]) keeps chart version 1.2.3-test.tag in place, while image locations receive test-prefix/testimage:1.2.3-test.tag.
  • Publication of that chart results in testchart-1.2.3-test.tag.tgz being created, older index entries being preserved, the new entry being added, and the publication commit including any extra message that was supplied.

    https://<actor>:<token>@github.com/<repo>

    For instance, using actor test-github-actor, token test-github-token, and repo jupyterhub/helm-chart:

    https://test-github-actor:test-github-token@github.com/jupyterhub/helm-chart

  • When the token environment variable is set while the actor environment variable is not set (unset/absent): The URL that is returned must include only the token as credential:

    https://<token>@github.com/<repo>

    For instance, given token test-github-token and no actor, with repo jupyterhub/helm-chart:

    https://test-github-token@github.com/jupyterhub/helm-chart

Branch Naming in the Repository

In the module's logic that interacts with a Git repository, the primary development branch carries the name main (not master). Every place in the code that publishes, checks out, references, or otherwise relies on the primary source branch must operate against a branch named main.

In particular, the chartpress operations that read commit/tag history and compute version identifiers from the primary branch must function correctly when that branch is called main.

Notes

  • No credential-formatting cases other than those described above are required.
  • Apart from what is specified above, do not change the existing GITHUB_TOKEN_KEY-only behavior.
