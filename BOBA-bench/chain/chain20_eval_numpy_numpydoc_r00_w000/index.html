NumPy docstring parsing

Additional sections

Recognize these section names exactly:

  • Other Parameters
  • Yields
  • Raises
  • Warns

Other Parameters must remain separate from Parameters.

For example:

Other Parameters
----------------
spam : parrot
    A parrot off its mortal coil.

must produce:

doc['Other Parameters'] == [
    ('spam', 'parrot', ['A parrot off its mortal coil.'])
]
Returns and Yields entries

Named entries use the three-part representation:

a : int
    The number of apples.

becomes:

('a', 'int', ['The number of apples.'])

An entry without a colon is anonymous: its heading becomes the first tuple item and its type is the empty string. For example:

list of str
    This is not a real return value.

becomes:

('list of str', '', ['This is not a real return value.'])

This applies to both Returns and Yields.

A Yields section containing:

a : int
    The number of apples.
b : int
    The number of bananas.
int
    The number of unknowns.

must therefore produce:

[
    ('a', 'int', ['The number of apples.']),
    ('b', 'int', ['The number of bananas.']),
    ('int', '', ['The number of unknowns.']),
]

A document containing both a Returns section and a Yields section must cause NumpyDocString(...) to raise ValueError.

Raises and Warns

Entries in Raises and Warns are represented as three-item tuples containing the exception or warning name, a middle field, and the description list.

For example:

Raises
------
LinAlgException
    If array is singular.

Warns
-----
SomeWarning
    If needed

must expose one entry in each section, with:

doc['Raises'][0][0] == 'LinAlgException'
doc['Raises'][0][2] == ['If array is singular.']

doc['Warns'][0][0] == 'SomeWarning'
doc['Warns'][0][2] == ['If needed']

Warns is distinct from the prose-oriented Warnings section.

Duplicate sections

Encountering a second Notes section in the same document must raise ValueError.

Duplicate signature-like lines

For this document:

z(x1, x2)

z(a, theta)

the resulting signature must be:

doc['Signature'].strip() == 'z(a, theta)'

Parsed Unicode text must remain a Python str. For example, a summary containing:

must produce that exact string from doc['Summary'][0], not encoded bytes.

When a template is provided in the config, converting the doc object to a string (via str(...)) must render that template. The template is rendered with a context that makes the individual documentation sections available as named variables. Each section variable must contain the already-formatted string content of that section (the same formatted text the object would normally produce for that section).

  • parameters — the rendered "Parameters" section, including its :Parameters: heading and the formatted parameter entries.

Task Specification: Support Qualified ~ Object References in "See Also"

Context

The numpydoc package parses NumPy-style docstrings in numpydoc.docscrape. A docstring's optional See Also section lists related functions, methods, classes, or objects. Entries may be plain names or Sphinx role references and may have descriptions.

Sphinx object references can use a leading tilde in a qualified target, for example :obj:~baz.obj_r``. The parser must recognize this specific object-reference form without broadly changing which other item-name forms are valid.

Objective

Extend See Also parsing to accept a qualified, tilde-prefixed target when it is written with the obj role. Preserve the tilde in the parsed target, preserve the role, and leave all existing parsing and validation behavior unchanged.

Public API

The behavior is exposed through the existing API in numpydoc.docscrape:

  • NumpyDocString(docstring) parses a docstring string.
  • The parsed section is available as doc['See Also'].
  • ParseError remains the exception used for invalid See Also item names.

doc['See Also'] is a list of three-element entries:

(name, description, role)

where:

  • name is the referenced object name with surrounding role syntax and backticks removed.
  • description is the existing parsed description value; it is empty/falsy when no description is supplied and retains supplied description text otherwise.
  • role is the Sphinx role, such as obj, meth, or class, when explicit role markup was used; it is absent/falsy for a plain reference.

No public API or result shape is to be added or changed.

Required Behavior

Accepted tilde form

A tilde-prefixed See Also target is valid under this extension only when both of the following are true:

  1. It uses explicit :obj: role markup.
  2. The tilde is immediately followed by a qualified, dotted name—that is, a name containing at least one dot separating name components and otherwise following the parser's existing name rules.

For example:

See Also
--------
:obj:`~baz.obj_r`

must contribute one entry with:

  • name equal to ~baz.obj_r;
  • an empty/falsy description; and
  • role equal to obj.

The leading tilde is part of the returned name. It must not be discarded or interpreted as a request for the parser to shorten the name. The :obj: prefix and surrounding backticks are not part of the returned name.

This behaves like the existing non-tilde object reference within the supported form:

  • :obj:baz.obj_q`` produces the name baz.obj_q, role obj, and no description.
  • :obj:~baz.obj_r`` produces the name ~baz.obj_r, role obj, and no description.

Each valid tilde-prefixed reference is a normal, separate See Also entry and therefore increases the list length by one. For example, adding it to a section that previously yielded 12 entries must make that section yield 13 entries.

Descriptions and grouping

The newly accepted form must participate in the existing See Also parsing rules:

  • If no description follows, its description is empty/falsy.
  • If a trailing description follows the reference, that description is retained.
  • Existing continuation-line handling for multi-line descriptions remains unchanged.
  • Existing comma-separated grouping behavior remains unchanged, including grouping role-marked and plain names.
  • The explicit obj role is captured regardless of whether the valid qualified object name has the tilde prefix.

For example, a valid entry with a description such as:

:obj:`~baz.obj_r`: related object

must retain related object through the same description representation used for existing entries.

Invalid Tilde Forms and Error Compatibility

This feature is intentionally narrow. It must not make tilde-prefixed names valid for every Sphinx role or for every name shape. In particular:

  • :func:~foo`` remains invalid.
  • A tilde-prefixed unqualified target, such as :obj:~foo``, remains invalid because it has no dotted qualification.
  • A qualified tilde target under another role, such as :func:~foo.bar``, remains invalid; tilde support in this task is limited to the obj role.
  • A bare tilde-prefixed name without :obj: role markup is not newly accepted.

Invalid item names must continue to raise numpydoc.docscrape.ParseError. Its existing diagnostic format must be preserved:

<entry> is not a item name in <repr(docstring)>

Thus, for a docstring containing :func:~foo`` as its See Also entry, the message begins with the literal text:

:func:`~foo` is not a item name in

and is followed by the representation of the original input docstring, including its original whitespace and newlines. The existing wording, including a item, is compatibility behavior.

Compatibility Requirements

  • Plain references and all previously valid role-marked references without a tilde must parse exactly as before.
  • Existing dotted names, descriptions, multi-line descriptions, comma-separated lists, and role capture must remain unchanged.
  • Existing rendering or other consumers of parsed (name, description, role) entries must continue to receive the same data shape.
  • Other docstring sections and all unrelated parser behavior must remain unchanged.
  • The change must not globally add ~ to every accepted item name; only the qualified :obj: form described above is newly valid.
