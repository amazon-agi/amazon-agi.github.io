Change required

The public NumPy-docstring parsing and rendering APIs are to be extended with the following observable behavior.

Public API

These imports and call forms must be available:

from numpydoc.docscrape import NumpyDocString, FunctionDoc, ClassDoc
from numpydoc.docscrape_sphinx import SphinxDocString, SphinxClassDoc
import numpydoc.linkcode

Construction and operations to be supported:

NumpyDocString(docstring)
SphinxDocString(docstring, config=None)

FunctionDoc(func=callable)

ClassDoc(cls, doc=None, config=None)
SphinxClassDoc(cls, doc=None, config=None)

parsed_doc[section_name]
str(parsed_doc)

For numpydoc.linkcode, importing successfully is the only requirement; no other behavior is required.

Parsing NumPy docstrings

Extra sections

These section names must be recognized exactly:

  • Other Parameters
  • Yields
  • Raises
  • Warns

Other Parameters must be kept separate from Parameters.

As an example:

Other Parameters
----------------
spam : parrot
    A parrot off its mortal coil.

must result in:

doc['Other Parameters'] == [
    ('spam', 'parrot', ['A parrot off its mortal coil.'])
]
Entries under Returns and Yields

An entry that has a name is expressed in three parts:

a : int
    The number of apples.

is turned into:

('a', 'int', ['The number of apples.'])

An entry that has no colon is anonymous: the first tuple item is its heading, and its type is the empty string. For example:

list of str
    This is not a real return value.

is represented as:

('list of str', '', ['This is not a real return value.'])

This holds for both Returns and Yields.

When a Yields section contains:

a : int
    The number of apples.
b : int
    The number of bananas.
int
    The number of unknowns.

the result must therefore be:

[
    ('a', 'int', ['The number of apples.']),
    ('b', 'int', ['The number of bananas.']),
    ('int', '', ['The number of unknowns.']),
]

If a document contains both a Returns section and a Yields section, NumpyDocString(...) must raise ValueError.

The Raises and Warns sections

Each Raises and Warns entry is a three-item tuple made up of the exception or warning name, a middle field, and the description list.

Example:

Raises
------
LinAlgException
    If array is singular.

Warns
-----
SomeWarning
    If needed

each section must expose one entry, such that:

doc['Raises'][0][0] == 'LinAlgException'
doc['Raises'][0][2] == ['If array is singular.']

doc['Warns'][0][0] == 'SomeWarning'
doc['Warns'][0][2] == ['If needed']

Warns and the prose-oriented Warnings section are distinct.

Repeated sections

If the same document contains a second Notes section, ValueError must be raised.

Repeated signature-like lines

Given the document:

z(x1, x2)

z(a, theta)

the signature that results must be:

doc['Signature'].strip() == 'z(a, theta)'
Unicode

Unicode text that has been parsed must remain a Python str. For instance, when a summary contains:

öäöäöäöäöåååå

doc['Summary'][0] must be that exact string, not encoded bytes.

Index directive data

With an index directive equivalent to:

.. index:: random
   :refguide: random;distributions, random;gauss

doc['index'] must have two keys, and:

doc['index']['default'] == 'random'
len(doc['index']['refguide']) == 2

For the generator example above, the nonblank lines must be:

    The number of unknowns.

Sections must be rendered in canonical order rather than in source order. Specifically, See Also must appear before Notes even when Notes is first in the input. Around the new sections, the observed ordering is:

  1. Returns
  2. Other Parameters
  3. Raises
  4. Warns
  5. Warnings
  6. See Also
  7. Notes
  8. References
  9. Examples
  10. index directive

Asterisks in signatures must be escaped for reStructuredText. For example:

my_signature(*params, **kwds)

the rendered form must be:

my_signature(\*params, \*\*kwds)

Similarly, given:

def my_func(a, b, **kwargs):
    pass

the following must hold:

FunctionDoc(func=my_func)['Signature'] == \

Configuring member visibility

Both ClassDoc and SphinxClassDoc must support:

  • show_class_members
  • show_inherited_class_members

Given a class that has methods spam and ham and a property spammity:

  • When show_class_members=False is used, the rendered text must not contain:

    • Methods
    • spam
    • ham
    • spammity
    • the property documentation text Spammity index

  • When show_class_members=True is used, the rendered text must contain:

    • Methods
    • spam
    • ham
    • spammity

In addition:

  • SphinxClassDoc must have an .. autosummary:: directive.
  • The property documentation text Spammity index must be included by plain ClassDoc.

config = {
    'show_class_members': True,
    'show_inherited_class_members': False,
}

ham and bar must be rendered, but spam must not be rendered and spammity must not be rendered.

When show_inherited_class_members=True, all four names must be rendered: spam, ham, bar, and spammity. Plain ClassDoc must then include Spammity index; SphinxClassDoc must include .. autosummary::.

    Bbb.

    Current time.

    Current variable values.

    Some parameter

:Parameters:

        Aaa.
    **jac** : callable ``jac(t, y, *jac_args)``
        Bbb.

For usage examples, see `ode`.

.. autosummary::

   x

.. rubric:: Methods
=====  ==========
**a**
**b**
**c**
=====  ==========

Summary

Change the rendering behavior of SphinxClassDoc in the numpydoc.docscrape_sphinx module so that the string output of a Sphinx documentation object can be generated from a Jinja2 template supplied by the caller.

Behavior Requirements

Template-based rendering

The SphinxClassDoc class (in numpydoc.docscrape_sphinx) must accept a configuration option called template through its config dictionary argument. When this option is present, it holds a Jinja2 template object (an instance of jinja2.Template).

If a template is provided in the config, conversion of the doc object to a string (via str(...)) must render that template. The template is rendered against a context that makes the individual documentation sections available as named variables. Each section variable must contain the already-formatted string content for that section (in other words, the same formatted text the object would normally produce for that section).

The names of the section variables correspond to the documentation sections. Drawing on the sections that must be usable:

  • examples — the rendered "Examples" section, with its .. rubric:: Examples heading and body text included.
  • parameters — the rendered "Parameters" section, with its :Parameters: heading and the formatted parameter entries included.

Every other standard numpydoc section must likewise be exposed as a context variable so a template may reference them; only the sections referenced by the template appear in the final output.

A template made up solely of {{examples}}{{parameters}} must therefore produce output containing the fully rendered Examples section followed by the fully rendered Parameters section, and nothing else.

Object construction

It must be possible to construct SphinxClassDoc as:

SphinxClassDoc(cls, doc, config={...})

in which:

  • cls is the class object being documented (may be None).
  • doc is the raw docstring text to parse.
  • config is a dictionary that may contain the key 'template', whose value is a jinja2.Template instance.
Formatting details needed for the exposed sections
  • The Examples section is rendered using a reStructuredText rubric heading (.. rubric:: Examples) followed by the example body text.
  • The Parameters section is rendered with a :Parameters: heading. Each parameter is rendered in the form **name** : type (the parameter name in bold, followed by : and the type description), and the parameter's description text is indented on the subsequent lines beneath it.

Public API

  • Module: numpydoc.docscrape_sphinx
    • Class: SphinxClassDoc
      • The constructor is compatible with the call form SphinxClassDoc(cls, doc, config=<dict>).
      • Provides support for config['template'] as a jinja2.Template.
      • str(instance) returns the rendered output as described earlier.

Behavior Requirements

If a docstring being parsed contains a section header (a line of text with a line of underline characters immediately following it) whose name is not among the recognized/known sections, the parser must:

  1. Not fail — the parse must succeed, and the content of the unrecognized section must be silently ignored (it must neither be stored as a section nor raise an error).

  2. Emit exactly one warning for that unknown section, using Python's standard warnings mechanism (that is, warnings.warn). The warning must be emitted while the doc object is being constructed (NumpyDocString, and hence also the Sphinx-based subclasses, which parse a docstring).

    Unknown section <SectionName>

    with <SectionName> standing for the header text of the unknown section, exactly as it appeared in the docstring (e.g., a section headed Mope results in the message Unknown section Mope).

Goal

Public API

The existing API in numpydoc.docscrape is what exposes this behavior:

  • A docstring string is parsed by NumpyDocString(docstring).
  • doc['See Also'] holds the parsed section.
  • For See Also item names that are invalid, ParseError remains the exception in use.

  • name is the name of the referenced object, once the surrounding role syntax and backticks have been removed.

Tilde form that is accepted

  • Whether or not the valid qualified object name carries the tilde prefix, the explicit obj role is captured.
