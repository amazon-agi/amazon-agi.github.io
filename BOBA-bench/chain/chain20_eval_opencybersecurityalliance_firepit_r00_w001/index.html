Task Description

Overview

The task is to extend the storage abstraction library that ingests observation data formatted as STIX (SCOs—STIX Cyber Observables) into a per-session database and exposes query and aggregation methods over that data. The work required covers data normalization, exact column projection, and observation-level timestamp and aggregation APIs.

Requirement for a Test Helper

An importable helper must exist, usable as:

from .helpers import tmp_storage

This callable must be exposed by a module tests/helpers.py:

def tmp_storage(tmpdir, clear=True):
    ...

Its behavior is as follows:

  • The database name is read from the FIREPITDB environment variable, with str(tmpdir.join('test.db')) as the default.
  • The session ID is read from the FIREPITID environment variable, with 'test-session' as the default.
  • Storage objects are obtained through the existing get_storage(dbname, session) entry point, which tests/helpers.py must be able to import.
  • If clear is true, a storage object is obtained first and its .delete() method is called to remove prior data for the session; then a fresh storage object is obtained and returned for the same database name and session.
  • If clear is false, the session data is not deleted.
  • The resulting storage object is returned.

Storage APIs That Already Exist

The storage object returned by get_storage already supports the APIs listed below, and they must keep working:

  • store.cache(query_id, bundle_file) takes a STIX bundle from a file and loads it into a named cache/table.
  • store.extract(view_name, sco_type, query_id, pattern) creates a named view of the requested type's objects that match a STIX pattern.
  • store.load(view_name, records, sco_type=...) loads dictionary records as SCOs of the given type.
  • Rows are returned by store.lookup(view_name, ...).
  • store.delete() removes the data of the current session.
  • store.assign(...) and store.values(...) keep their existing behavior.
  • store.timestamped(...) stays available, with the modified behavior described below.

Changes That Are Required

1. Exact selection of columns in lookup

The signature is unchanged:

store.lookup(view_name, limit=None, offset=None, cols=None)

Whenever cols explicitly selects a single column, every returned row must contain exactly that column and must not contain any automatically added or additional columns. As an example, cols="value" must produce row dictionaries having exactly one key, value.

2. Normalization in load for evolving and missing attributes
store.load(view_name, records, sco_type='<type>')

This method loads records that represent SCOs of the given type and returns the SCO type string, such as 'ipv4-addr'.

Records that describe the same underlying object must be merged into a single stored row. Identity means the SCO identity derived from the properties that contribute to identity; equal value fields, for example, identify the same ipv4-addr. It is not required that the records have identical schemas. During the merge:

  • If an attribute is present on any record for that identity, it must be retained in the merged row.
  • A later record may introduce a new attribute, and that attribute must be added to the stored schema and to the row.
  • The absence of an attribute from a later record must not overwrite or erase an earlier non-missing value.
  • These requirements hold regardless of whether the record that contains the extra attribute appears before or after a record that omits it.

For example:

records = [
    {"value": "10.0.0.1", "x_extra": 99},
    {"value": "10.0.0.1"},
]
result = store.load('test_ips', records, sco_type='ipv4-addr')

The result must be 'ipv4-addr', and a lookup of test_ips must yield exactly one object row containing at least:

{
    "type": "ipv4-addr",
    "value": "10.0.0.1",
    "x_extra": 99,
}

Every SCO row that lookup exposes must include a type column equal to the row's SCO type.

3. timestamped: timestamps and projections at the observation level
store.timestamped(view_name, column=None, value=None)

This method returns rows at the observation level. The key for the observation timestamp must be named first_observed, not timestamp.

  • timestamped(view_name) returns all rows in the view, each one augmented with first_observed. Each result contains the row's own columns, such as id and the SCO type's attributes, together with first_observed.
  • timestamped(view_name, column) returns rows that contain exactly two keys: first_observed and the selected column.
  • timestamped(view_name, column, value) returns the same two-key shape, restricted to observations whose resolved column equals value.

The result has one entry per observation instance or occurrence, and not one entry per distinct SCO or per distinct column value. Observing the same SCO or value repeatedly therefore produces repeated rows.

4. value_counts
store.value_counts(view_name, column)

One dictionary is returned for each distinct resolved value of column. Every dictionary has:

  • A grouped-value entry whose key is the resolved attribute's own name. That key is the final attribute component, obtained after removing any type qualifier and following any reference path.
  • A count entry that contains the number of observation instances having that value.

The grouped-value key is not always the literal string value. The key is value only in cases where the resolved attribute itself is named value. Some examples include:

column argument Grouped-value key
account_login account_login
ipv4-addr:value value
src_ref.value value
network-traffic:dst_ref.value value

So a call for account_login returns rows shaped like {'account_login': <login>, 'count': <integer>}, whereas a call for an IPv4 address's value returns rows shaped like {'value': <address>, 'count': <integer>}.

The number of dictionaries that are returned is equal to the number of distinct values. Counts are based on observation instances: repeatedly observing the same value increases that value's count.

5. number_observed
store.number_observed(view_name, column, value=None)

The method returns an integer that represents the number of observation instances:

  • number_observed(view_name, column) returns the total across every value of the resolved column.
  • number_observed(view_name, column, value) returns the count restricted to observations for which the resolved column is equal to value.

This is a count of occurrences, not a count of distinct values, so it may exceed the number of distinct values or the number of distinct SCO rows.

6. summary
store.summary(view_name, column, value=None)

One dictionary is returned, with exactly these summary fields:

  • first_observed: the earliest of the observation timestamps.
  • last_observed: the latest of the observation timestamps.
  • number_observed: the total count of observation instances, consistent with number_observed.

Behavior of the method:

  • summary(view_name, column) aggregates all of the observation instances represented by the resolved column.
  • summary(view_name, column, value) aggregates only the observations for which the resolved column is equal to value.

The timestamp values are the raw ISO-8601 strings, preserved from the ingested observation data. A trailing Z, along with the stored fractional-second precision, must be preserved exactly; for example, both '2020-06-30T19:25:09.447726Z' and '2020-06-30T19:29:59.96346Z' keep the precision they originally had.

How Columns Are Resolved for the Observation APIs

The column argument accepted by timestamped, value_counts, number_observed, and summary takes all of the following forms:

  1. A bare attribute that is relative to the view's SCO type, such as value or account_login.
  2. A dotted path that goes through an object reference, such as src_ref.value or dst_ref.value.
  3. A fully qualified form, either type:attribute or type:path, such as ipv4-addr:value or network-traffic:dst_ref.value.

A bare name is resolved against the SCO type of the view. A dotted path follows the reference to the attribute of the referenced SCO. For reference paths of this kind, grouping and occurrence counts are based on observations of the referencing object in the selected view. A type-qualified path supplies the SCO type and the attribute path explicitly.

Whenever forms denote the same underlying attribute, they must produce equivalent filtered rows, counts, and summaries. In the case of value_counts, equivalent forms also use the resolved terminal attribute name as the key for the grouped-value output.

Consistency Across Methods

For any valid (view_name, column) combined with an optional value filter:

  • len(value_counts(view_name, column)) is equal to the number of distinct resolved values.
  • The sum of all count fields returned by value_counts(view_name, column) is equal to number_observed(view_name, column).
  • len(timestamped(view_name, column)) is equal to number_observed(view_name, column).
  • len(timestamped(view_name, column, value)) is equal to number_observed(view_name, column, value).
  • summary(view_name, column)['number_observed'] is equal to number_observed(view_name, column).
  • summary(view_name, column, value)['number_observed'] is equal to number_observed(view_name, column, value).

Specification of the Task

Summary

The way firepit ingests STIX observation bundles must be modified so that, when a single Observation SDO holds multiple SCOs of the same type, the "primary" (most significant) instance is marked by means of a rank attribute stored on the containment relationship instead of on the SCO itself.

Context

When firepit caches a STIX bundle, it breaks each Observation SDO down into its constituent SCOs (Software, IP addresses, network-traffic, etc.) and tracks which SCOs belong to which observation. A single observation can hold multiple SCOs of the same type. As an example, a network-traffic object typically references two ipv4-addr objects (source and destination). In such situations, firepit chooses one of them as the "primary" SCO for that type within that observation.

Behavior Change Required

How primary SCOs are ranked

Whenever multiple SCOs of the same type occur within a single observation, firepit must mark exactly one of them as the primary instance.

  • The mark must be stored under the attribute name x_firepit_rank.
  • On the primary instance, the x_firepit_rank value must be set to 1.
  • A NULL (unset) x_firepit_rank value must be present on non-primary instances.
  • This attribute must reside on the containment table that links observations to their contained SCOs — to be precise, it must be a column named x_firepit_rank on the __contains relationship table.

The attribute name used previously, x_root (stored on the SCO tables), must no longer be used for this purpose; the ranking information now belongs solely on the __contains table.

Structure of the data model

The __contains table captures containment relationships; the columns relevant to this task that it must include (at minimum) are:

  • target_ref — the id of the SCO that is contained.
  • x_firepit_rank — the rank marker explained above (integer or NULL).

The table belonging to the contained SCO itself (e.g. ipv4-addr) is joined to __contains via <sco_table>.id = __contains.target_ref.

Worked Example

Take a single observation that holds one network-traffic object and two ipv4-addr objects:

  • Both of the ipv4-addr rows exist in the ipv4-addr table.
  • For each ipv4-addr, the __contains table has a row that links it to the observation.
  • Exactly one of those __contains rows carries x_firepit_rank = 1; on the other, x_firepit_rank is NULL.

When a query selects ipv4-addr values by joining the ipv4-addr table to __contains on id = target_ref and filters on rows where __contains.x_firepit_rank IS NOT NULL, it must return exactly one row — the primary IP address.

Scope of the Change

Public API surface, method names, and signatures must not be changed. The only observable change that is required is:

  • The rank marker is called x_firepit_rank (value 1 for the primary), and
  • It is stored as a column on the __contains table instead of on the individual SCO tables.

  • The object's id is what the id column holds.

  • A spec_version property on objects must be tolerated by the store; rather than being stored as a column, it is dropped, and type is dropped too.
  • Ingestion must not fail in situations where objects reference one another through object_refs, resolves_to_refs, or created_by_ref; bundles of this kind must load cleanly and produce the per-type rows and counts that are expected.
  • Duplicate objects should not lead to duplicate rows (exactly one stored row is yielded by each distinct object).

  • pattern (str): The STIX 2.0 observation pattern as a string (the complete bracketed pattern expression, e.g. "[ipv4-addr:value = '9.9.9.9']").
  • sco_type (str): Name of the SCO type the generated SQL clause is intended to filter (e.g. 'ipv4-addr', 'url', 'network-traffic').
  • Returns (str): The body of a SQL WHERE clause (the leading WHERE keyword is not part of it). The string may contain arbitrary internal whitespace; only its content once whitespace is normalized (each run of whitespace collapsed to a single space, leading/trailing whitespace stripped) is significant.

Required Behavior

The function parses the STIX pattern and produces a SQL condition that is expressed in terms of column names only (object-path prefixes such as ipv4-addr: are stripped away, leaving only the property name). In the output, column/property names must be double-quoted.

Filtering by property type

The only comparison expressions that contribute to the output are those whose object path references the given sco_type. Comparisons that target a different SCO type must be omitted.

  • If the pattern's comparison(s) reference an SCO type that does not match sco_type, the returned result is the empty string (an empty WHERE body).
Comparison operators and the SQL forms they produce

For a property prop that matches and a literal value:

  • Equality (=): the SQL form is "prop" = 'value'.
  • LIKE (LIKE): the SQL form is "prop" LIKE 'value'.
  • ISSUBSET (ISSUBSET): the SQL is a subnet-membership predicate call wrapped in parentheses: (in_subnet("prop", 'value')). The value is the CIDR/subnet string taken from the pattern.
  • Reference-list / list membership: a pattern property that carries a list index wildcard of the form prop[*] and is compared with = to a value results in a substring LIKE match: "prop" LIKE '%value%'. (Example: network-traffic:protocols[*] = 'tcp' → "protocols" LIKE '%tcp%'.)
Boolean combination and grouping of comparisons
  • When multiple comparisons are combined with AND, their individual SQL forms are joined by AND in pattern order.
  • When multiple comparisons are combined with OR, their individual SQL forms are joined by OR in pattern order.
  • Parentheses in the input pattern that group sub-expressions carry over into the output as parentheses around the corresponding grouped SQL. That holds both for redundant parentheses enclosing a single comparison (e.g. [(ipv4-addr:value = '9.9.9.9')] → ("value" = '9.9.9.9')) and for meaningful grouping of combined expressions (e.g. a parenthesized OR group AND-ed with another comparison has the parentheses around the OR group kept).
Full input → normalized output examples
  • [ipv4-addr:value = '9.9.9.9'] (for type ipv4-addr) → "value" = '9.9.9.9'
  • [(ipv4-addr:value = '9.9.9.9')] (for type ipv4-addr) → ("value" = '9.9.9.9')
  • [ipv4-addr:value = '9.9.9.9'] (for type process) → `` (empty string)
  • [ipv4-addr:value ISSUBSET '192.168.0.0/16'] (for type ipv4-addr) → (in_subnet("value", '192.168.0.0/16'))
  • [domain-name:value LIKE 'example.%'] (for type domain-name) → "value" LIKE 'example.%'
  • [url:value LIKE 'http://example.%' AND url:value LIKE '%.php'] (for type url) → "value" LIKE 'http://example.%' AND "value" LIKE '%.php'
  • [url:value LIKE 'http://example.%' AND url:value LIKE '%.php' AND url:value LIKE '%foo%'] (for type url) → "value" LIKE 'http://example.%' AND "value" LIKE '%.php' AND "value" LIKE '%foo%'
  • [(url:value LIKE 'http://example.%' OR url:value LIKE 'https://example.%') AND url:value LIKE '%foo%'] (for type url) → ("value" LIKE 'http://example.%' OR "value" LIKE 'https://example.%') AND "value" LIKE '%foo%'
  • [network-traffic:protocols[*] = 'tcp'] (for type network-traffic) → "protocols" LIKE '%tcp%'

Notes

  • For subnet membership, a SQL function named in_subnet is used, invoked as in_subnet("column", 'subnet'). It is the shared predicate that the ISSUBSET operator must emit.
  • The output must not contain table-qualified column names, the leading WHERE keyword, or trailing semicolons.
  • Whitespace inside the returned string carries no significance (it will be normalized before comparison), whereas the token content, the quoting, the parentheses, and the operator/keyword casing shown in the examples above are significant.

Task Specification: Normalized SCO Storage in firepit

Overview

The job here is to build a "normalized" storage model for STIX Cyber Observable (SCO) data inside the firepit package. The key behavioral change: SCO tables must be deduplicated, meaning every distinct SCO (recognizable through its deterministic STIX ID) ends up in storage exactly once, however often it shows up across observations. Which observations contain which SCOs, and which SCOs relate to which other SCOs, is recorded in a separate relation table; this relationship information is not denormalized into the SCO tables.

Counts, column layouts, and ID formats are all affected, and new/changed query behavior plus several new API methods are called for.

Imports and package layout

The import paths listed next must exist and be usable:

  • firepit.get_storage(dbname, session) — a factory whose return value is the storage object that the rest of this document calls store.
  • firepit.stix21.makeid(obj) — details under "Deterministic STIX 2.1 IDs".
  • These classes must be exposed by firepit.query: Query, Table, Filter, Predicate, Aggregation, Group, Order, Limit, Projection, Column, Join.
  • These exceptions must be exposed by firepit.exceptions: IncompatibleType, UnknownViewname, UnexpectedError.

Normalized data model

Per-type SCO tables

One table per SCO type exists, and the table takes its name from the type (e.g. "ipv4-addr", "domain-name", "network-traffic", "user-account", "url", "identity").

  • SCO tables must NOT contain a type column or a spec_version column. (store.columns(...) output, as well as the table schema returned by the schema API, must not include type or spec_version.)
  • The columns of an SCO table come from the SCO's own properties (e.g. id, value, dst_port, account_login, user_id, etc.).
  • A reference property (e.g. src_ref, dst_ref, process_ref, resolves_to_refs) stays as the reference column itself (e.g. process_ref holds a target id) and is not exploded into dotted sub-columns. Concretely: an object that has a process_ref produces a column named process_ref (rather than process_ref.id).
  • One row per distinct SCO. When the same SCO (identical deterministic id) is loaded or cached repeatedly, duplicate rows must not appear.
The relation table __contains

Which observations contain which SCOs is recorded by a table named __contains. Among its columns are at least source_ref and target_ref (target_ref holds an SCO id). It also carries a per-observation ranking column x_firepit_rank, whose job is to flag the "primary"/most significant SCO of a given type within a single observation (see "Primary SCO ranking").

Timestamps at the observation level

The link between SCOs and observation-level timestamp data (first_observed, last_observed, number_observed) runs through the containment relation and observed-data; the SCO tables themselves do not carry these as columns.

Deterministic STIX 2.1 IDs — firepit.stix21.makeid

The input to makeid(obj) is a dict describing a STIX 2.1 SCO: it contains type, spec_version, and the SCO's contributing properties; an id key may also be present, but ID computation must ignore it. The function hands back the deterministic STIX 2.1 id string for that object.

  • The id returned must match, exactly, what the official stix2 library's deterministic ID generation produces for the same object once its id has been removed. SCO types in scope include autonomous-system, directory, domain-name, email-addr, email-message, file, and ipv4-addr; in scope too are objects with nested structures (hashes, additional_header_fields, body_multipart, received_lines), reference properties, and non-ASCII values.
  • When a process SCO carries an x_unique_id, deterministic ID generation must use it.

Loading and caching data

store.cache(query_id, bundles)

One or more STIX bundles get ingested here. bundles may be a single filename or else a list of filenames. Both STIX 2.0 and STIX 2.1 bundles are supported. Ingest proceeds as follows:

  • As described above, the objects are normalized into the SCO tables and the __contains relation.
  • When SCOs are duplicated (identical deterministic id), they get merged into one row.
  • Observed-data objects that are duplicates get dropped.
  • identity objects are handled too (rows do not get duplicated by duplicate identities).
store.load(viewname, objects, sco_type=...)

A list of plain SCO dicts (ids not included), all of the given sco_type, is loaded into a table/view named viewname. What is returned is the sco_type string.

Evolving objects get merged: if several input dicts resolve to one and the same SCO (their identifying properties coincide, e.g. an ipv4-addr with the same value), they must be merged into a single row. Any extra/optional properties found in any of the duplicates must be carried over to the merged row. Example: two ipv4-addr dicts that share a value, one of them carrying an x_extra property (the order can go either way), load into exactly one row — its type is 'ipv4-addr', its value matches, and its x_extra holds the provided value.

Note: for a loaded view, the rows that store.lookup gives back include a type key mirroring the sco_type.

store.delete()

The data/tables belonging to the current session are removed, so that a fresh session can then be created.

Extraction and views

store.extract(viewname, sco_type, query_id, pattern)

A view named viewname is created; it contains the SCOs of sco_type that match the given STIX pattern string (e.g. "[network-traffic:dst_port < 1024]", "[ipv4-addr:value ISSUBSET '10.0.0.0/8']", "[url:value LIKE '%page/1%']"). Extraction into the same viewname, however many times it is repeated, is idempotent with respect to results.

Deduplicated SCO tables imply the following: an extract that draws on the same underlying SCO from many observations returns each distinct SCO once. The identical extract, run again, produces the same result set.

Values, columns, and counts

  • store.values(path, viewname) — for the rows of viewname, returns a list of the values taken by the property path; path may be a bare property such as 'value', a dotted path such as 'src_ref.value', or a fully qualified 'type:path' such as 'user-account:account_login'. Under deduplication, each distinct SCO is represented once.
  • store.columns(viewname) — returns the column names of a table/view; type and spec_version never appear among them.
  • store.types() — returns the set/list of SCO type names the store contains.
  • store.count(viewname) — returns how many rows the view holds.
  • store.schema(viewname) — returns a list of column descriptors, each one a dict carrying at least a 'name' key. type must not be among them.

Lookup

store.lookup(viewname, cols=None, limit=None, offset=None)

The result is a list of row dicts.

  • cols may be left out (all columns then), passed as a comma-separated string (e.g. "value"), or passed as a list of column names/paths (e.g. ['dst_port'], ['src_ref.value', 'dst_ref.value']). If cols is supplied, every returned row dict carries exactly the requested keys.
  • Dotted reference paths inside cols (e.g. 'src_ref.value', 'dst_ref.value') must be resolved by means of a join to the referenced SCO, with the referenced property value coming back under the dotted key.
  • The rows that come back are restricted by limit and offset.
  • Validation: limit and offset must be integer-valued. When a non-integer value (e.g. a string like "1; select * from urls; --") gets passed, ValueError must be raised.

What deduplication means for the fake test bundle (the standard fake_bundle_file):

  • network-traffic with dst_port < 1024: the distinct connections total 78, and the dst_port values occurring among them are exactly {22, 80, 514}.
  • A lookup of those connections' ['src_ref.value', 'dst_ref.value'] comes back with 78 rows; the pair 192.168.90.122 / 10.0.0.214 is present twice, while 192.168.132.245 / 10.0.0.214 is present once.
  • ipv4-addr with value LIKE '10.%': the distinct IPs number exactly 10 (with 10.0.0.141 included).
  • user-account (extracted via [ipv4-addr:value LIKE '10.%']): the distinct account logins number exactly 14, and every distinct login (e.g. henry, isabel) occurs once in values(...).

Grouping

store.group(dest_view, source_view, by=..., aggs=None) (NEW)

The rows of source_view are grouped, and the results are written to dest_view.

  • A single property name/path (a string) may be passed as by, or a list of these. Dotted reference paths (e.g. 'src_ref.value', 'dst_ref.value') as well as plain columns (e.g. 'dst_port') qualify as paths.
  • In the output, the grouped-by columns show up under the names they were given (e.g. output rows contain 'dst_port', or 'src_ref.value' / 'dst_ref.value').
  • If aggs is left out, sensible default aggregations are produced; notably, grouping the connections view by 'src_ref.value' produces an output column named unique_dst_port.
  • aggs has the form of a list of (func, target, alias) tuples, e.g. ('COUNT', '*', 'count'); the alias supplies the output column's name.

On the standard connections view (network-traffic, dst_port < 1024, 78 distinct rows):

  • Grouping by ['src_ref.value', 'dst_ref.value'] gives 74 groups.
  • With aggs=[('COUNT', '*', 'count')], the count of each group reflects how many distinct connections that src/dst pair contains. The pairs that have count 2 are specifically: (192.168.216.111,10.0.0.197), (192.168.27.170,10.0.0.214), (192.168.70.186,10.0.0.139), (192.168.90.122,10.0.0.214); count 1 belongs to all other pairs.
store.assign(dest_view, source_view, op=..., by=..., limit=None)

The pre-existing assign operation. Support for the following must continue:

  • op='sort', together with by=<prop> and an optional limit. A supplied limit must be integer-valued; a non-integer (e.g. '1; SELECT 1; --') must raise ValueError.
  • op='group', with by=<prop or list> (deprecated, though still functional; its behavior matches group). Grouping by 'src_ref.value' produces a unique_dst_port column; grouping by 'dst_port' produces output containing a dst_port column.

assign_query and query objects

store.assign_query(viewname, query)

A Query is executed and its results are stored into viewname.

The constructor forms below (as exercised) must be supported by the firepit.query classes:

  • Table(name)
  • Filter([Predicate(prop, op, value)]) — for instance Predicate('value', '=', '1; select * from url; --'), and similar.
  • Column(name, table=None, alias=None) — points at a column; a table/alias qualifier is optional, and output aliasing is optional too.
  • Join(table, left_col, op, right_col, alias=None, lhs=None) — joins table on left_col <op> right_col. Later Column(table=...) references use alias as the joined table's name; if the left-hand table is not the immediately preceding one, lhs supplies its name. Several joins against the same SCO table under different aliases (e.g. src and dst both joining ipv4-addr) must be supported.
  • Projection([...]) — enumerates output columns; an entry may be a plain column-name string or else a Column(...) object. In the output, an aliased column shows up under its alias (e.g. Column('value', table='src', alias='src_ref.value')).
  • Group([...]) — enumerates group keys; an entry may be a string or a Column(...) object (an aliased Column causes grouping on that column, with output under the alias).
  • Aggregation([(func, target, alias), ...]) — the target may be a string column name or a Column(...); an output column whose name comes from alias is produced.
  • Order([(col, direction), ...]), together with the constants Order.DESC and Order.ASC.
  • Limit(n).

A Query may be given a list of stages at construction (Query([...])), or else built up incrementally via query.append(stage).

Value handling / SQL injection

Predicate values are treated as literal string values (parameterized), never as raw SQL:

  • A predicate value of "1; select * from url; --" counts as valid (it matches nothing); assign_query must not raise, and a lookup afterwards on the result returns 0 rows.
  • If a predicate value has an embedded single quote with injection following it, e.g. "1'; select * from url; --", assign_query ends up raising UnexpectedError.

Summary / statistics APIs (new)

All of the APIs that follow accept an optional final value argument, used to restrict results to rows whose property equals that value. For the property argument, a bare property ('value', 'account_login', 'src_ref.value', 'dst_ref.value') or a fully-qualified 'type:path' (e.g. 'ipv4-addr:value', 'network-traffic:dst_ref.value') may be used. SCO type names (e.g. 'url', 'ipv4-addr', 'network-traffic', 'user-account') as well as extracted view names are what these operate on.

store.number_observed(viewname_or_type, prop, value=None)

Returns an int: the total number of observations (with observation counts summed) in which the SCOs show up — or, where a value is given, in which the SCO with that value shows up. Observation-level counts are added up for this, so the figure is generally larger than the number of distinct SCOs.

A dict comes back carrying the keys first_observed, last_observed, and number_observed:

Examples on the standard fake bundle:

Returns a list of row dicts — one dict per observation occurrence, so the length matches the observation count rather than the distinct-SCO count — and each dict includes a first_observed timestamp.

  • No prop given: each row carries first_observed together with the SCO's columns (e.g. for user-account: account_login, user_id, id, ...).

store.value_counts(viewname_or_type, prop)

Returns a list of dicts; each one pairs the property key with a count key that gives the number of observations (observation counts summed) for that value.

On the standard fake bundle:

  • value_counts('url', 'value') → 31 entries.
  • value_counts('ipv4-addr', 'value') → 70 entries (one per distinct ip value); 192.168.203.101 carries count 3.
  • value_counts('tens', 'ipv4-addr:value') (10.0.0.0/8 subset) → 10 entries; 10.0.0.73 carries count 14.

Ranking of primary SCOs

Should one observation hold several SCOs of the same type (e.g. two ipv4-addr for a network-traffic's source and destination), one of them gets the "primary" label by having x_firepit_rank = 1 set on the matching __contains row (the ranking belongs to the relation, not to the SCO table). Per observation and per type, exactly one SCO receives the rank. When a query joins an SCO table to __contains and filters on c."x_firepit_rank" IS NOT NULL, only the primary SCO(s) are returned.

Deterministic IDs and row ordering (network-traffic example)

SCOs are identified by the deterministic STIX 2.1 ids (e.g. a network-traffic id such as network-traffic--637791d8-c981-5a1e-9714-f0c4cfcb736b), and not by ids carrying an observation suffix. With fake_bundle_file_2, an ascending sort of the network-traffic connections on src_port places the row with src_port == 0 first; this row's id == 'network-traffic--637791d8-c981-5a1e-9714-f0c4cfcb736b' and its start == '2020-06-30T19:25:09.447726Z'.

Handling of x-oca-event

x-oca-event and the event SCOs connected with it are supported. In an extracted x-oca-event view, reference properties turn up as plain reference columns — e.g. the extracted events view contains a column named process_ref (rather than process_ref.id).

Helper for low-level queries

A raw SQL string is run by store._query(sql), which returns a cursor; that cursor supports .fetchall(), whose row objects can be indexed by column name (dict-like). It serves to query joins against __contains (e.g. selecting SCO values where x_firepit_rank IS NOT NULL).

Test helper (support code; not part of the library API)

Tests rely on a helper named tmp_storage(tmpdir, clear=True). It reads the FIREPITDB/FIREPITID env vars (the defaults being a temp file DB and the session test-session), may call store.delete() to clear an earlier session, and returns a fresh store obtained via get_storage(dbname, session). Ensure this pattern is supported by get_storage and delete (repeatable clean sessions against the same DB/session id).

Extra Requirements

  • In the case of store.value_counts() specifically, the count reflects the number of distinct observed-data containment occurrences for a property value; it is not the observations' number_observed fields added up. Consequently, when a single observed-data object references a value and carries number_observed == 50, the count for that value comes out as 1, not 50. This rule stands independently of the summed-count semantics that number_observed() and summary() follow.

Task Specification: Normalized STIX Storage in firepit

Overview

Your job, inside the firepit library, is to build a normalized relational storage layer for STIX 2.0 and 2.1 observation data. Here is the heart of the change: every STIX SCO (STIX Cyber Observable) type gets a table of its own, and that table holds only the properties belonging to the object itself. References — that is, relationships between objects — are recorded separately, and following a reference happens by way of SQL joins at query time. When an identical observable shows up in several observations, it is deduplicated (merged) rather than written once per observation.

The exact behavior required is laid out by this spec. Where the old behavior was "one row per observation," the new behavior is "one row per unique observable."

Public API Surface

Getting a Storage Object

A factory defined at module level is how you obtain a storage object:

from firepit import get_storage
store = get_storage(dbname, session_id)

Calling get_storage(connstring, session) hands back a SqlStorage (concrete subclass) instance. .delete() must be supported by the store as the means of dropping all session data.

Ingestion
  • store.cache(query_id, bundles) — One or more STIX bundle files get loaded. bundles may be a list of file paths, or a single file path supplied as a string. STIX 2.0 and STIX 2.1 bundles must both be handled.
  • store.load(viewname, objects, sco_type=None) — A list of raw SCO dicts — these come without type/id — of a given sco_type is loaded into a table/view going by the name viewname. The sco_type string is what comes back.
  • store.extract(viewname, sco_type, query_id, pattern) — Sets up a view viewname that selects every object of sco_type matching the STIX pattern string pattern.
  • store.reassign(viewname, objects) — A list of object dicts (possibly modified/enriched) is reloaded into the store, which updates the underlying tables. Referenced sub-objects that arrive embedded via dotted paths (see below) must be split out and applied to their own tables.
Querying / Retrieval
  • store.lookup(viewname, cols=None, limit=None, offset=None) — Row dicts come back as a list. cols may be passed as a comma-separated string or as a list. Where offset and limit are provided as non-integer/unsafe values, ValueError must be raised.
  • store.values(path, viewname) — For a single column/path, a list of the values is what comes back. path may be given either as a bare property name or in sco-type:property form.
  • store.columns(viewname) — Returns a list made up of a view/table's column names.
  • store.schema(viewname) — Returns a list of column descriptors of the shape {'name': ..., ...}.
  • store.types() — Returns a list of the SCO type names that are present.
  • store.count(viewname) — Returns the number of rows.
  • store.assign(newname, viewname, op=..., by=..., limit=..., ...) — Carries out an operation ('sort', 'group') whose output is newname. A limit that is non-integer/unsafe must raise ValueError.
  • store.assign_query(viewname, query) — Puts a Query object to use (see Query DSL); viewname is reassigned to the result of that query.
  • store.group(newname, viewname, by=..., aggs=None) — This is the new grouping API (see Grouping).
  • store._query(sql) — Raw SQL gets executed, and what comes back is a cursor whose .fetchall() yields row dicts.
Helpers for Aggregates / Summaries
  • store.number_observed(viewname, path, value=None) — Returns an int: the total number of observations for the given property path; optionally, only the rows where the property equals value are counted.
  • store.summary(viewname, path, value=None) — Returns a dict whose keys are first_observed, last_observed, and number_observed, covering the property path (with an optional restriction to value).
  • store.timestamped(viewname, path=None, value=None) — The result is a list of row dicts, one per observation, and every one of them includes a first_observed timestamp. Given a path, exactly first_observed and the property named by path are what each dict contains. With path left out, the object's own columns plus first_observed make up each dict. A restriction to value is optional.
  • store.value_counts(viewname, path) — Returns a list of dicts {<path>: value, 'count': n}, where for each value the count is the number of distinct observables that have it.

Data Model Requirements

One Table per Type, Own Properties Only

For each SCO type there is a table whose name is the type itself (e.g. "ipv4-addr", "network-traffic", "user-account", "process", "url", "x-oca-event"). The rules below apply to these tables:

  • Do NOT give them a type column.
  • Do NOT give them a spec_version column.
  • Do NOT give them a number_observed column.
  • They do have an id column, together with the object's own scalar properties.
  • A reference property (e.g. src_ref, dst_ref, process_ref, binary_ref, parent_directory_ref, host_ref, network_ref, parent_ref) is stored as a plain column that holds the referenced object's id — the column bears exactly the reference property's name (e.g. column src_ref, process_ref), not a dotted/expanded form like process_ref.id.

Although the tables have no type column, the row dicts handed back by lookup for a loaded view still include a 'type' key that gives the SCO type (see Deduplication behavior below — for a loaded ipv4-addr row, row['type'] == 'ipv4-addr').

Merging / Deduplication of Observables

One and the same observable occurring in several observations occupies a single row. Take two loaded objects that share an identity (same id) yet carry different property sets:

  • What gets retained is the union of all properties (any property present in either input turns up in the stored row).
  • Should both inputs specify the same property with different values, the first-seen value is the winner. To make this concrete: loading [{"value":"10.0.0.1"}, {"value":"10.0.0.1","x_extra":1}] produces one row where x_extra == 1; loading [{"value":"10.0.0.1","x_extra":99}, {"value":"10.0.0.1"}] produces one row where x_extra == 99.
  • When later objects bring in properties not yet present, the stored table has to evolve as needed by gaining new columns (e.g. x_extra).

Owing to deduplication, the number of distinct observables is not the same as the number of observations. In the primary test bundle: ipv4-addr has 10 unique values (200 observations exist in total, though), user-account has 14 unique logins (100 observations exist in total, though), and there are 70 distinct ipv4-addr observable rows and 31 distinct url observable rows.

The __contains Relationship Table

Which observations contain which observable ids is recorded by a table named __contains; among its columns are source_ref (the observation) and target_ref (the contained observable). Indexing this table is required.

Observation Ranking (x_firepit_rank)

If, within one observation, the same SCO type occurs more than once (e.g. several ipv4-addr objects for a network-traffic's src/dst), firepit designates the most significant instance. The designation is stored as an integer column x_firepit_rank on the __contains table (NOT on the SCO table, and NOT named x_root). A non-NULL x_firepit_rank is carried by the primary/most-significant instance.

It must be possible to query this, for instance as follows:

SELECT value FROM "ipv4-addr" i
  JOIN __contains c ON i.id = c.target_ref
  WHERE c."x_firepit_rank" IS NOT NULL

For an observation that contains three ipv4-addrs, with one of them being the "primary" host asset, exactly one row has a non-NULL rank.

Following References with Joins (Dotted Paths)

Dotted reference paths such as src_ref.value, dst_ref.value, and parent_ref.pid must be supported in extracted views and lookups. Whenever a caller asks for such a path — in lookup cols, values, summary, number_observed, timestamped, value_counts, group, or in STIX patterns like [network-traffic:dst_ref.value ISSUBSET '10.0.0.0/8'] — the storage layer must resolve it, doing so by joining the referencing table to the referenced object's table on the reference-id column and then selecting the target property.

The dotted path itself serves as the result column/key (e.g. a row of lookup('conns', cols=['src_ref.value','dst_ref.value']) carries the keys 'src_ref.value' and 'dst_ref.value').

When the pattern given to store.extract references a dotted path (e.g. [network-traffic:dst_ref.value ISSUBSET '10.0.0.0/8']), the objects it selects are those whose referenced object satisfies the condition.

As for process objects: parent_ref.pid must be resolvable (when the request goes through a plain lookup that expands own references, a looked-up process row includes 'parent_ref.pid' — in the ccoe bundle, a lookup('procs') row has the key 'parent_ref.pid').

reassign with enriched references

Rows that carry enriched dotted reference properties must be handled by reassign. Suppose a network-traffic row is modified to include dst_ref.x_enrich = 1 and then reassigned: the enrichment must be applied to the referenced ipv4-addr object's own table, so that a separately-extracted ipv4-addr view shows x_enrich on the matching addresses. Every ipv4-addr in the referenced set acquires the x_enrich column (NULL wherever it is not set); the ones that were dst refs of the enriched connections end up with x_enrich == 1.

Query DSL (firepit.query)

The following classes must be provided so that they can be imported from firepit.query:

  • Query(clauses=None) — .append(clause) is available on it.
  • Table(name)
  • Filter(predicates) and Predicate(prop, op, value)
  • Projection(columns) — columns may be supplied as strings or as Column objects.
  • Column(name, table=None, alias=None) — refers to a column, with qualification by table and/or an alias both being optional.
  • Join(table, left_col, op, right_col, alias=None, lhs=None) — stands for an explicit join; the joined table instance is named by alias, while lhs gives the left side table's name for cases where it is not the immediately-preceding one.
  • Group(columns) — performs group-by; columns may be supplied as strings or as Column objects.
  • Aggregation(specs) — a (func, arg, alias) tuple is what each spec is, e.g. ('COUNT', '*', 'count'), ('COUNT', 'src_port', 'total'). A string or a Column may serve as arg.
  • Order(specs) — a (col, direction) pair makes up each spec; Order.ASC and Order.DESC must be provided.
  • Limit(n)

Where joins have aliases, the projection must be able to reference joined columns by the table alias (e.g. Column('value', table='src', alias='src_ref.value')).

query.Unique must function in cases where the stage preceding it is not a Projection.

The name of this column is the ref property itself, exactly (e.g. process_ref); it is not a dotted/flattened name like process_ref.id. Hence, on an x-oca-event view, columns('events') contains 'process_ref' while 'process_ref.id' is absent.
Dotted paths get resolved through joins
  • If a caller refers to a dotted path — e.g. src_ref.value, dst_ref.value, or parent_ref.pid — the storage must resolve it: a join to the referenced object's table is performed, the target column is selected, and the result column is aliased back to the original dotted path name.
  • On a network-traffic view, lookup with the default columns returns rows that carry the keys src_ref.value and dst_ref.value (these hold the joined address values). Resolution must be correct for both IPv4 and IPv6 addresses (a network-traffic may reference ipv4-addr or ipv6-addr objects).
  • On a process view, the rows that lookup returns include parent_ref.pid.
  • The distinct joined address values are what values('src_ref.value', view) returns.

  • Which SCOs are contained by which observed-data is recorded by a __contains table, and that table also carries a per-observation "primary/rank" marker column under the name x_firepit_rank (integer type). Inside a single observation, where multiple SCOs of one type exist, exactly one of them is marked primary (its rank is set); the rest are not. Example: a single observation holds three ipv4-addr objects (two act as the src/dst of a network-traffic; the third is an event host/nat address) — the primary is exactly one ipv4-addr row. A join along these lines:
    SELECT value FROM "ipv4-addr" i JOIN __contains c ON i.id = c.target_ref WHERE c."x_firepit_rank" IS NOT NULL
    returns exactly one row.
  • List-valued references (reflists) are recorded in a __reflist table whose columns include source_ref and target_ref; paths through *-style list refs (e.g. email-message:to_refs[*].value) are resolved with its help.
Deterministic IDs and de-duplication
  • Observed-data objects that are duplicated (e.g. one and the same object across several bundles) must be de-duplicated, so that storage happens exactly once.
  • IDs come with STIX 2.1 objects already. For STIX 2.0 SCOs, IDs are generated deterministically (see stix21.makeid).

Behavior of load

load(viewname, objects, sco_type='ipv4-addr') takes in a list of SCO dicts that have one ID in common (an identical identifying value) even though their property sets may differ or evolve. All of those records, nevertheless, collapse into a single stored row. Suppose the same logical object shows up several times, with different columns present:

  • A merge produces one row.
  • For each property, the first non-null value that gets encountered is the winner (i.e. a value already set is never overwritten by a later record, and a value contributed by one record is not erased just because another record lacks that property).

To make it concrete: load applied to [{"value":"10.0.0.1"}, {"value":"10.0.0.1","x_extra":1}] produces a single row where x_extra == 1; applied to [{"value":"10.0.0.1","x_extra":99}, {"value":"10.0.0.1"}], it produces a single row where x_extra == 99. In either scenario lookup returns one row with type == 'ipv4-addr' and value == '10.0.0.1', along with the x_extra value. The string 'ipv4-addr' is what load returns.

Behavior of reassign

What reassign(viewname, objects) does is take object dicts obtained earlier (e.g. by way of lookup) and write them back into the normalized tables underneath. Where an enrichment lands on a dotted reference path, it must propagate to the referenced object's table.

Concretely: look up network-traffic rows and enrich every one of them with a new attribute placed on a referenced object (e.g. conn['dst_ref.x_enrich'] = 1). Once reassign has run, the referenced ipv4-addr objects end up with the x_enrich column, set to the assigned value. Extract a separate view (dests) for those same referenced addresses, and on lookup it must show the x_enrich attribute present, the enriched value being attached to the addresses that were referenced (e.g. x_enrich == 1 on every 10.* dest). Treating dotted-path columns as literal columns of the source table is exactly what reassign must avoid: it has to correctly split out referenced objects and update them.

Reassigning a grouped view leaves the row count intact.

firepit.query — the query builder

Composable classes for SQL construction are what the query module exposes. Rendering a query returns (sql_text, values), where values is an ordered list of the bound parameter values; the placeholder goes into render(placeholder) (e.g. '%s').

The public classes that are required, and the behaviors that matter for each (identifiers come out double-quoted in the output):

  • Query(arg=None) — a query. It may be built empty, from a table name string, or from a list of stages. .append(stage) is part of its interface. .render(placeholder) → (sql, values).
  • Table(name) — produces the FROM part over a table.
  • Filter(predicates) — assembles a WHERE clause out of a list of Predicate objects.
  • Predicate(lhs, op, rhs) — expresses a comparison. For rhs, a scalar bound value is one option; the other, when op is 'IN', is a subquery Query (rendered as (<subquery sql>), and for that subquery no bound value is emitted when it has none).
  • Projection(cols) — SELECT restricted to specific columns. Strings as well as Column objects are accepted.
  • Column(name, table=None, alias=None) — refers to a column; a table qualification and/or an alias (AS) can optionally be attached.
  • Join(table, left_col, op, right_col, alias=None, lhs=None) — an INNER JOIN with an ON condition; the joined table may be aliased, and the left-hand table may be specified.
  • Group(cols) — GROUP BY. Strings and Column objects are both accepted.
  • Aggregation(specs) — SELECT expressions that aggregate; a spec (func, col, alias) turns into FUNC("col") AS "alias".
  • Order(specs) — ORDER BY; each spec is a (col, direction) pair; the constants Order.DESC / Order.ASC are available.
  • Limit(n) — LIMIT.
  • Unique() — SELECT DISTINCT; whether or not the stage preceding it is a projection, it must work.
  • CoalescedColumn(...) — a column expression for use after a join, coalescing alternatives.
Subquery rendering examples (the output must be exact)

Inside another Query, a Query may appear as a stage (a FROM-subquery); it is assigned an alias — s1, s2, … — in order:

subquery = Query(); subquery.append(Table('my_table'))
subquery.append(Filter([Predicate('foo', '>', 0)]))
query = Query(); query.append(subquery)
query.append(Group(['baz']))
query.append(Aggregation([('SUM', 'foo', 'TotalFoo')]))
query.render('%s')

must yield the sql:

SELECT "baz", SUM("foo") AS "TotalFoo" FROM (SELECT * FROM "my_table" WHERE ("foo" > %s)) AS s1 GROUP BY "baz"

values: [0].

Where a subquery sits inside an IN predicate:

subquery = Query('some_view'); subquery.append(Projection(['some_ref']))
query = Query('some-type')
query.append(Filter([Predicate('id', 'IN', subquery)]))
query.render('%s')

must yield the sql:

SELECT * FROM "some-type" WHERE ("id" IN (SELECT "some_ref" FROM "some_view"))

values: [].

Translation of STIX patterns into SQL

STIX comparison expressions are converted by the pattern translator into SQL WHERE fragments (joins as well, wherever they are needed), with the normalized schema reflected:

  • A comparison on a ref path — e.g. [network-traffic:src_ref.value = '127.0.0.1'] — comes out as a subquery over the referenced type's table:
    "src_ref" IN (SELECT "id" FROM "ipv4-addr" WHERE "value" = '127.0.0.1')
  • A comparison on a reflist path — e.g. [email-message:to_refs[*].value = 'name@example.com'] — comes out as a join routed through __reflist:
    JOIN "__reflist" AS "r" ON "email-message"."id" = "r"."source_ref" WHERE "r"."target_ref" IN (SELECT "id" FROM "email-addr" WHERE "value" = 'name@example.com')
  • A dictionary/quoted sub-property — e.g. [file:hashes.'SHA-256' = 'whatever'] — comes out as a column comparison on the composite column name:
    "hashes.'SHA-256'" = 'whatever'
  • A property carrying a list index, e.g. windows-registry-key:values[*].name, keeps translating into a LIKE over the serialized column, e.g. "values" LIKE '%"name":"foo"%'.

Validating input / guarding against SQL injection

  • Hand lookup a non-integer offset (e.g. the string "1; select * from urls; --") and it must raise ValueError.
  • Hand assign(..., op='sort', ..., limit=...) a non-integer limit (e.g. '1; SELECT 1; --') and it must raise ValueError.
  • When the bound value of a Filter/Predicate is a benign-looking injection string (e.g. value = '1; select * from url; --'), the treatment it must receive is that of a parameterized literal: assign_query succeeds and returns zero matching rows (lookup → empty list). The injected SQL must not be executed.
  • A predicate value with a closing single quote plus SQL embedded (e.g. value = "1'; select * from url; --") may fail during execution; in that situation assign_query raises the underlying DB driver error (an UnexpectedError-type exception out of the SQL layer). SQL injection must not be performed.

Exceptions

The exception types required to be importable from firepit.exceptions are IncompatibleType and UnknownViewname. Where queries are malformed, the SQL layer surfaces the backend driver errors (referred to in this document as UnexpectedError).

Note: invalid inputs connected with parameter binding (a bad offset/limit) raise ValueError (not TypeError).
