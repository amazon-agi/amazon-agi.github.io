Task Specification: Extracting BETWEEN Columns During SQL Filter Parsing

Goal

Extend the SQL parser utilities such that columns appearing in a BETWEEN ... AND ... clause inside a WHERE condition are extracted correctly into the filter column list, with "between" used as the operator.

Public API

What follows must be importable and callable exactly as described:

  • Module: ParserUtils (imported via from ... import ParserUtils, in line with the existing project layout).
  • Class method: ParserUtils.format_statement(parsed_statement) — accepts a parsed SQL statement object (the result of the project's existing parser.parse(sql) call) and returns a visitor object.
  • The visitor object that is returned must expose an attribute table_list.

These are already present in the codebase; the change that is required is to their behavior for BETWEEN clauses.

Required Behavior

visitor.table_list

table_list is a list of dictionaries containing one dictionary per table referenced in the parsed SQL. Every dictionary carries the following keys:

  • table_name (str): the table's name, stripped of any surrounding backtick quoting.
  • alias (str): the table's alias, or an empty string '' when none is present.
  • filter_column_list (list): a list of dictionaries describing each column that takes part in a filter condition in the WHERE clause.

Each entry inside filter_column_list is a dictionary that holds:

  • column_name (str): the name of the filtered column, without any surrounding backtick quoting.
  • opt (str): the comparison operator that is applied to that column.
Handling of BETWEEN (the change to implement)

When a WHERE condition takes the form:

<column> BETWEEN <value1> AND <value2>

filter_column_list must include the tested column as a single entry:

{'column_name': '<column>', 'opt': 'between'}

The value of the operator must be the lowercase string 'between'. The two boundary values of the BETWEEN expression must not generate any additional filter column entries, and the AND connecting the two boundary values must not be handled as a separate condition.

Other filter conditions within the same WHERE clause (for example, a standard comparison such as <) must continue to be extracted in the normal way, each producing an entry containing its column name and the corresponding operator string (e.g. '<'). The entries in filter_column_list follow the order in which their conditions appear in the SQL.

Concrete result

For input that is equivalent to:

select max(`successRate`) AS `successRate`
from `table_850d`
where `period` between '2022-07-11 00:00:00' and '2022-07-11 23:59:59'
  and `successRate` < 0.35;

the value of visitor.table_list must equal:

[{'table_name': 'table_850d', 'alias': '',
  'filter_column_list': [{'column_name': 'period', 'opt': 'between'},
                         {'column_name': 'successRate', 'opt': '<'}]}]

Notes

  • Backtick quoting around identifiers (table names and column names) must be removed from the values that result.
  • An AND keyword that forms part of a BETWEEN ... AND ... construct must be distinguished from an AND that joins two independent conditions, so that the two BETWEEN boundaries end up as one filter entry instead of being parsed as extra conditions.

2. Calls to the CONCAT function

CONCAT(...) calls must be parsed, including:

  • On its own as a selected expression: SELECT CONCAT('a','-','b')
  • Inside a WHERE predicate: SELECT * FROM t WHERE a=CONCAT('a','-','b')
  • Nested calls: SELECT * FROM t WHERE a=CONCAT('a',CONCAT('b','-','c'))
3. Calls to the CAST function

Expressions of the form CAST(... AS <type>) must be parsed, including:

  • A cast nested inside another cast: SELECT CAST(CAST(1+2 AS TIME) AS JSON)
  • A cast of a parenthesized arithmetic expression: SELECT CAST((8+1) AS SIGNED)
  • A cast of a BETWEEN predicate: SELECT CAST(1 BETWEEN 1 AND 2 AS SIGNED)
  • Casts to types including TIME, JSON, and SIGNED.
4. Fully featured SELECT query

A SELECT statement combining joins, aggregate functions, filtering, grouping, having, ordering, and limit/offset must be parsed, e.g.:

select name,age,count(*),avg(age) from blog join a on a.id = blog.id
where a.b = 1 and blog.c = 2 group by name,age
having count(*)>2 and avg(age)<20 order by a asc,b desc limit 1 OFFSET 3

The query body of the resulting statement must expose a from_ attribute that is an instance of the Join tree node (the src.parser.tree join type, as used elsewhere in the codebase).

Parsing Behavior Required from Both Parsers (formatting/rules context)

The parsers must continue to support:

  • SELECT a.* FROM d1 as a (table alias via as), including when the statement is parsed with debug=True.
  • FOR UPDATE, FOR UPDATE NOWAIT, and FOR UPDATE WAIT 1 clauses on a SELECT, including when the statement is parsed with debug=True.

Reserved Words as Identifiers (MySQL parser)

The MySQL parser must be able to use the words listed below as ordinary column identifiers in a select list of the form SELECT <word> FROM t:

cast, end, escape, group, if, in, id, into, is, or, use, with.

Note: the words from, for, and on are not required to be usable as identifiers in this position, and they are outside the scope of this task.

Constraints

  • All of the listed statements must parse without raising and must return Statement instances.
  • Any parse call must support debug=True being passed, and doing so must not change the parse outcome.
