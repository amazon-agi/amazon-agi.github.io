01 There is a List class in the sqlitecollections package 759 words · source specification, reworded by GLM-5.3-Flash

Task: Implement Mutable Sequence Operations on List

Background

There is a List class in the sqlitecollections package; it stores its elements in a SQLite table, persisting each element as a pickled blob. The class is imported like this:

from sqlitecollections import List

To construct a List, pass the keyword argument connection (a sqlite3.Connection) together with the keyword argument table_name (a str), e.g. List[str](connection=conn, table_name="items"). Each element lives in its own row of the backing table, which carries a pickled serialized_value column and an integer item_index column reflecting the element's 0-based position (contiguous, starting at 0, in order).

You must implement/extend the behaviors described below. Whenever elements are written, they are serialized with pickle, and the resulting stored order/indices must always remain contiguous starting at 0.

1. __getitem__ with a slice: step of zero

If __getitem__ is called with a slice whose step is 0, raise ValueError with the message slice step cannot be zero.

For slices whose step is not zero — including negative steps and out-of-range start/stop values — the behavior must continue to match standard Python list slicing: a new List-like object is returned, and its backing table contains the sliced elements re-indexed contiguously from 0.

2. __setitem__

Assignment by integer index: sut[i] = value
  • For a valid index (negative indexing supported), the element at that position is replaced with the pickled value; all other elements and their indices are unchanged.
  • If the index is outside the valid range (in either direction), IndexError is raised with the message list assignment index out of range, leaving the stored data unchanged.
Assignment by slice: sut[s] = iterable

Assigning an iterable to a slice must reproduce exactly the semantics of Python's built-in list.__setitem__ for slices, covering all combinations of start, stop, step (including None, negative, zero, and out-of-range values) and iterables of varying lengths:

  • For an extended slice (step is not None and not 1), when the count of assigned values differs from the count of selected positions, raise ValueError with Python's message, e.g. attempt to assign sequence of size N to extended slice of size M.
  • For an extended slice where step == 0, raise ValueError with the message slice step cannot be zero.
  • Otherwise, the selected positions are removed and the iterable's values are put in their place (for a simple contiguous slice), or are replaced element-by-element (for a valid extended slice), matching built-in list behavior.
  • The value being assigned is an arbitrary iterable (it may be a one-shot iterator) and must be consumed correctly.

When the operation finishes, the stored (pickled) elements and their item_index values must match exactly what a native Python list would contain after the same slice assignment, re-indexed contiguously from 0.

3. __delitem__

Deletion by integer index: del sut[i]
  • For a valid index (negative indexing supported), the element at that position is removed; the remaining elements are re-indexed contiguously from 0.
Deletion by slice: del sut[s]

Deleting a slice must reproduce exactly the semantics of Python's built-in list.__delitem__ for slices, across all combinations of start, stop, step (including None, negative, zero, and out-of-range values):

  • When a slice has step == 0, raise ValueError with the message slice step cannot be zero.
  • Otherwise, remove exactly those elements that a native Python list would remove for the same slice.

Once the deletion is done, the stored (pickled) elements and their item_index values must match exactly what a native Python list would contain after the same deletion, re-indexed contiguously from 0.

4. insert

Provide the following method:

def insert(self, index: int, value) -> None

Its behavior must be exactly the same as Python's built-in list.insert:

  • Insert the pickled value so that it ends up at position index, with subsequent elements shifted one position later.
  • Negative indices are counted from the end.
  • Indices beyond the end (e.g. very large positive values) clamp to an append at the end.
  • Negative indices beyond the beginning (e.g. very large negative values) clamp to an insertion at the front (position 0).

After the insertion, all elements' item_index values must remain contiguous starting at 0, in the correct order.

Overall Requirements

  • All values written to the backing store are serialized using pickle.
  • After every mutating operation, the backing table must hold exactly the resulting elements, with item_index values 0, 1, 2, … in order and with no gaps.
  • Once operations complete, no auxiliary/temporary tables may remain.

Task Description

Summary

In this task you work with a List class that offers an interface like that of a Python list, backed by a SQLite database table. Elements are stored as pickled Python objects tied to an integer index. This task requires you to implement an append method and to ensure that slice assignment behaves correctly, especially for the error case where a non-iterable is assigned to a slice.

Storage Scheme

Each list element is stored in the backing table as a row made up of:

  • A BLOB column that holds the element serialized via pickle.dumps(value).
  • An INTEGER column that holds the element's zero-based position in the list.

This integer index defines the list order; it is contiguous, starting from 0.

Public Interface

The List class is generic and can be constructed as:

List[T](connection=<sqlite3.Connection>, table_name=<str>)
  • connection: an open sqlite3.Connection to the database that contains the backing table.
  • table_name: the name of the table that backs this list.

The class must support being parameterized with any type argument (e.g., List[str], List[Any]); the type parameter has no effect on runtime behavior.

The append Method
def append(self, value: T) -> None

Adds value to the end of the list. The value is serialized with pickle.dumps and stored under an index equal to the list's current length (i.e., the next available contiguous index, with indices starting from 0; for an empty list this is 0).

Behavior:

  • When the list is empty, an append stores the value at index 0.
  • Each append that follows stores the value at the next consecutive index.

Example: beginning with an empty list, append("a") then append("z") produces the rows ("a" pickled, 0) and ("z" pickled, 1).

Slice Assignment: __setitem__ with a slice key

An assignment of the form sut[start:stop:step] = value must match the semantics of Python's built-in list.__setitem__ when the key is a slice, including the normalization of indices (negative indices, out-of-range indices, None bounds) and the handling of steps.

Concretely, after a slice assignment the stored rows that result (element order and re-indexing from 0) must be identical to what an equivalent in-memory Python list would produce when it performs list_copy[slice(start, stop, step)] = value for the same original elements and the same assigned iterable.

This includes proper handling of:

  • Extended slices (a step other than None/1): the number of assigned items must match the number of selected positions, and a mismatch must raise the same error Python's list would raise.
  • Simple slices (a step of None or 1): the assigned iterable may differ in length from the selected region, in which case the list grows or shrinks accordingly and the remaining elements are re-indexed contiguously from 0.

Error case:

  • If the right-hand side of an extended-slice assignment (an assignment to a slice with an explicit step, e.g. sut[::] = value where the assigned value is not iterable) is not an iterable, a TypeError must be raised with a message that contains the text must assign iterable to extended slice.

Additional Notes

  • For the value column, all persisted values are serialized with pickle.
  • After any mutating operation, the stored index column must remain a contiguous sequence starting at 0 that matches the list's element order.

Task Specification: Implementing add, iadd, and extend on the List class

Task Overview

You must implement three operations, all related, on an existing List class backed by SQLite: the in-place extension operation (extend), the in-place addition operator (+=), and the non-mutating addition operator (+). Each of these operations appends serialized items to a SQLite table.

Background

A List class is already present (a generic type, usable as List[str]); instead of holding its elements in memory, it stores them in a SQLite database table. Its constructor has the form:

List(connection=<sqlite3.Connection>, table_name=<str>)

Every element is stored as a row of the backing table. The table columns that matter here are:

  • serialized_value — the element itself, serialized with pickle.dumps(value) (stored as a BLOB).
  • item_index — the element's integer position within the list, zero-based, contiguous and increasing (0, 1, 2, ...).

The class already exposes a table_name attribute that references its backing table.

Behavior That Must Be Implemented

1. extend(self, values: Iterable) -> None

Every item from values is appended, in iteration order, to the end of the list.

  • Every new item is serialized with pickle.dumps and inserted as a row into the instance's backing table.
  • The item_index assigned to each appended item carries on the existing sequence: when the list currently holds n items (indices 0..n-1), the appended items are given indices n, n+1, n+2, ..., in iteration order.
  • The list is mutated in place; the method returns nothing.
  • Repeated calls to extend keep appending, and contiguous, increasing item_index values are preserved across the entire table.
2. __iadd__(self, values: Iterable) -> List

This implements the += operator. On the backing table, its effect is exactly the same as that of extend: the given items are appended to the instance's own backing table with continuing item_index values. The left-hand operand remains the same underlying list (its own table is the one that gets mutated). The method must return a List.

3. __add__(self, values: Iterable) -> List

This implements the + operator. It produces and returns a new List instance whose backing is a new, separate table (one with a distinct table_name, reachable via the returned object's table_name attribute). This operation must not modify the backing table of the original list.

The table of the new list must contain:

  • all items the original list currently holds, in their original order, followed by
  • all items from values, in iteration order.

All items are stored serialized with pickle.dumps, with item_index values that are contiguous and start at 0 across the combined sequence.

Once the returned List object is garbage-collected / deleted, its separate backing table must be removed, with only the original items table left in the database.

Note on Serialization

Serialization is done with Python's pickle module, in such a way that the stored value equals pickle.dumps(value) byte-for-byte.

Summary of the Public API

Available on the List class (importable just as it currently is, e.g. List[str](connection=..., table_name=...)):

  • extend(self, values) -> None
  • __iadd__(self, values) -> "List"
  • __add__(self, values) -> "List" — returns a new List on a new table, exposes .table_name, and has its table dropped on deletion.

Task: Adding * and In-Place *= Multiplication to the List Class

Background

Provided is a List class — a generic sequence type backed by SQLite. Behind each instance sits a database table; its rows hold pickled Python values next to a zero-based item_index column, and it is this column that determines the ordering of elements. Element type is what parameterizes the class (e.g. List[str]), and construction takes this form:

List(connection=<sqlite3.Connection>, table_name=<str>)

A table_name attribute is exposed on each instance, naming the table where its data is kept.

Beneath the instance lies the underlying table — referred to further down as the "items table" — and it contains at least these columns:

  • serialized_value — a BLOB in which the pickled element value is kept.
  • item_index — an integer that gives an element its position; positions begin at 0 and are contiguous.

Two new operators, __mul__ and __imul__, must be implemented on this class.

Behavior Requirements

In-place multiplication with list *= n

The method __imul__(self, n) must make an in-place multiplication of a List by an integer n repeat the list's current contents n times, with the same backing table undergoing the mutation.

  • For n <= 0 (zero or any negative integer), the list is emptied: all rows in its backing table are removed.
  • For n == 1, the contents are left as they are.
  • For n > 1, the sequence of elements currently present is repeated n times over. The rows this produces must be stored with contiguous item_index values, beginning at 0, in this order: the full original sequence, then another full copy, and so on. As an illustration, if the elements start out as [a, b, c], then once *= 2 has run, the table contains, read in item_index order, values a, b, c, a, b, c at indices 0..5.

What this operation mutates is the receiver's own backing table, in place; it may not leave additional tables behind. For each element, serialized_value must store that element's value, serialized with pickle.

Multiplication with list * n

The method __mul__(self, n) must make multiplication of a List by an integer n return a new List instance whose backing table is a different one, while the original list's table stays unchanged. The table_name of the returned instance names its own new table.

  • For n <= 0, an empty new list is what results.
  • For n == 1, a copy of the original elements (indices 0..len-1) makes up the new list's contents.
  • For n > 1, the new list's contents are the original sequence repeated n times, with item_index running contiguously from 0, in the same repetition order set out above.

Once the resulting list has been discarded and its table has undergone cleanup, the database should contain only the original items table.

Errors (both operators)

When the multiplier is not an integer — a float being the specific case — TypeError must be raised, carrying this message:

can't multiply sequence by non-int of type 'float'

Both * and *= fall under this rule.

Additional notes

  • Python's pickle module is what serializes the element values.
  • Result tables must keep item_index ordering contiguous and zero-based, matching the sequence of elements that gets produced.

Required behavior of List.index

Add a method whose signature semantics are as follows:

def index(self, value, start=..., stop=...) -> int

Overview

Add four new methods to an existing SQLite-backed List collection class; these methods mirror the semantics of Python's built-in list: count, pop, remove, and sort. There is additionally a reverse method, whose behavior is described below.

A generic class List[T] already exists; it stores its elements in a SQLite table and backs an interface similar to a Python list. It is constructed as follows:

List[T](connection=<sqlite3.Connection>, table_name=<str>)

  • serialized_value — the element's value, pickled via pickle.dumps(value) (a BLOB).
  • item_index — the element's zero-based position in the list (an integer).

Rows are ordered by item_index, which always forms a contiguous sequence 0, 1, 2, ... with no gaps. Element values are deserialized via pickle.loads. Any operation that changes the list must keep the item_index values contiguous and starting at 0, while preserving the relative order of the remaining/reordered elements.

The following methods must be implemented on this class. All value comparisons and equality checks operate on the deserialized Python values (== for equality, standard </ordering for sorting).

Methods to Implement

count(self, value: T) -> int

Return the number of list elements that are equal to value.

  • Returns 0 when the list is empty or when no element equals value.
  • Otherwise, returns the exact count of matching elements.
pop(self, index: int = -1) -> T

Remove and return the element at the specified index; index defaults to -1 (the last element).

Behavior:

  • Negative indices are counted from the end (-1 refers to the last element, -2 to the second-to-last, etc.).
  • The value of the removed element is returned.
  • Once the element has been removed, the remaining elements keep their relative order, and their item_index values are re-normalized to a contiguous 0..n-1 sequence.
  • If the list is empty, raise IndexError with the message pop from empty list. This holds for any index argument (including 0, positive, and negative values) whenever the list is empty.
  • If the list is non-empty but index is out of range (once negative indices have been resolved), raise IndexError with the message pop index out of range.
remove(self, value: T) -> None

Remove the first element (the one with the lowest item_index) whose value equals value.

  • Only the first matching element is removed, while other equal elements remain.
  • Once the removal is done, the remaining elements keep their relative order, and their item_index values are re-normalized to a contiguous 0..n-1 sequence.
  • If no element equals value, raise ValueError with the message '<value>' is not in list, where <value> is the repr-style rendering of the value (for example, removing a missing string z produces 'z' is not in list).
reverse(self) -> None

Reverse the order of the list's elements in place.

  • The element that was previously at the end becomes the first, and so on.
  • The item_index values remain a contiguous 0..n-1 sequence that reflects the new order.
sort(self, *, key: Optional[Callable[[T], Any]] = None, reverse: bool = False) -> None

Sort the list's elements in place.

  • key (keyword-only) is an optional callable that is applied to each element to produce the value used for comparisons. When key is None, elements are compared directly.
  • reverse (keyword-only, default False) — when True, sort in descending order.
  • The sort must be stable: elements that compare equal (under the effective key) retain their original relative order. This stability applies to both ascending and descending (reverse=True) sorting — reversing does not invert the relative order of equal elements.
  • Once the sort finishes, the item_index values form a contiguous 0..n-1 sequence reflecting the sorted order.

Notes

  • Values may be of any picklable type, tuples included (e.g. Tuple[int, int]). When no key is given, sorting tuples follows normal Python tuple ordering.
  • All methods mutate the underlying database directly, so the stored rows immediately reflect the new state.
09 The List, Set, and Dict collection classes shipped by the sqlitecollections package contain a bug that you must fix. 611 words · source specification, reworded by GLM-5.3-Flash

Summary

The List, Set, and Dict collection classes shipped by the sqlitecollections package contain a bug that you must fix. If an instance of one of these classes is built against a table that already exists (identified by table_name) and initial data is supplied, any records the table already holds must be discarded before the new initial data gets inserted. Right now the initial data is instead appended on top of whatever the table stored previously, and that behavior is wrong.

Public Interface

All three classes can be imported from the sqlitecollections package:

from sqlitecollections import List, Set, Dict

Each class allows its type parameters to be given via subscripting (e.g. List[Any], Set[Hashable], Dict[Hashable, Any]), and construction happens via keyword arguments:

  • connection: a sqlite3.Connection instance.
  • table_name: a str that names the backing table.
  • data: an optional iterable holding the initial contents.

Required Behavior

Suppose a collection is constructed with a table_name for which records have already been stored — for instance, records written by a previous instance built against the same connection and table name — and data is provided. The backing table that results must contain only the initial data that was newly supplied. Any records originating from a prior construction against the same table must not remain.

This requirement covers all three classes, including the case in which a second instance is built immediately after the first one while the same connection and table_name are reused.

List
  • The data argument takes the form of an iterable of items (e.g. a list).
  • For each element, its pickled value is stored by the backing table alongside a zero-based sequential index that reflects insertion order.
  • After construction with initial data against a table that is already populated, the table is left holding exactly the new elements, with indices starting from 0.

Example: a List[Any] is constructed with data=[0]; then a second List[Any] is constructed with data=[1] on the same connection and table name. The table must be left containing only the single element 1, at index 0.

Set
  • The data argument is an iterable whose items are hashable.
  • For each element, its pickled value is stored in the backing table.
  • Once initial data is passed in during construction against a pre-populated table, the table contains exactly the new elements (deduplicated as a set), and none of the elements that were stored previously remain.

Task Specification: Package-Level Exports and a Mutable table_name

Summary

The package you will be working on, sqlitecollections, is a Python package whose collection types (Dict, List, Set) are persistent and backed by SQLite. This task calls for two changes: certain names are to be exposed at the top level of the package, and the table_name attribute of the base collection class is to become settable, so that when a collection's backing table is renamed, the database reflects it.

  • sc.List

  • sc.Dict, sc.List, and sc.Set must still be subscriptable generic collection classes (e.g. sc.Dict[Hashable, Any](...), sc.List[str](...), sc.Set[Hashable](...)), and they must go on accepting the same constructor keyword arguments they take today (such as connection, table_name, data, serializer/deserializer, key/value serializers, persist, and rebuild_strategy).

None of the behavior of these classes is altered by this requirement; what changes is only how accessible they are as attributes of the top-level package.

Requirement 2: Making the Base Collection Class's table_name Settable

All collections trace back to a single base class, which resides in the base module (base.SqliteCollectionBase is how code refers to it). Each collection instance is tied to a table in the SQLite database, with the instance's table_name identifying that table; moreover, the package keeps a metadata table in which a row of the form (table_name, schema_version, container_type) describes each active collection.

In its current form, table_name is an attribute that can be read. A read/write property is what it must become. When read, it must keep returning the table name that is currently in effect. When a new value is assigned to it (instance.table_name = "new_name"), a rename must be carried out, and its semantics are these:

A rename that succeeds

If the name being assigned is one that is new and unused:

  1. The database table underneath is renamed, with the old name giving way to the new one. Under the new table name, all existing rows are retained, their contents included.
  2. Once the rename has gone through, the database no longer contains a table under the old name. Any attempt made to query the old table name ends in an sqlite3.OperationalError (SQLite raises it because the table is gone).
  3. The matching row inside the metadata table is updated, with its table_name field coming to hold the new name (schema_version and container_type stay as they were).
  4. The change goes through a commit, which makes it visible through the shared database connection.
  5. From then on, reading instance.table_name returns the new name.
A rename that is rejected (name collision)

If the name being assigned is already taken by another collection that is registered in the metadata table:

  1. The assignment must raise a ValueError.
  2. Nothing is changed: the database table does not get renamed, and the metadata table stays exactly as it was (all existing rows remain unchanged — the row belonging to the instance being modified as well as the row for the name that collides).
Behavioral notes
  • The case in which the name assigned is the one the instance itself already holds is not exercised; beyond the rules above, it need not be handled in any special way.
  • For the collision check, the names consulted are those present in the metadata table, taken across all collections that share the connection.

Context for Verifying the Implementation

Set out below is how the base class is shaped when it is exercised, so that your implementation integrates with it correctly. The base class:

  • Has a constructor that takes keyword arguments, with connection (a sqlite3.Connection) and table_name (a str) among them.
  • Provides a connection attribute, which returns the SQLite connection.
  • At construction time, brings its backing table into existence (if needed) and records itself in the metadata table by way of a row (table_name, schema_version, container_type), where container_type holds the name of the concrete class.
  • Hands table-specific SQL operations over to a driver class, which is referenced via a _driver_class class attribute.

Operations that insert rows into the backing table or read rows from it may be added by subclasses, with self.table_name serving to identify the table; once a rename has succeeded, such operations must naturally target the table's new name (that is, reads/writes pass through the value that the table_name property currently has).

It is on the base class itself (as the table_name property setter) that the rename logic should be implemented, independent of the concrete collection subclass that is used, so that it works uniformly for all collection types and for any subclass of the base.

Summary

Update the base class for SQLite-backed collections so that table names are sanitized and a warning log message is emitted whenever sanitization actually changes the name that was provided.

Within the module sqlitecollections.base, expose a module-level logger object (a standard Python logging logger belonging to this module) that is reachable as sqlitecollections.base.logger. This logger must have a warning(message) method, which is used as described below.

Sanitization of Table Names

A table name is supplied when a collection instance is constructed (via the table_name keyword argument) and may also be reassigned later through the instance's table_name attribute (its setter).

Whenever a table name is set — both during construction and on subsequent assignment — the name must be sanitized, with all illegal characters removed. The required behavior is as follows:

  • Only characters that are valid for a table name are kept. Removing illegal characters must strip out characters such as spaces, semicolons (;), asterisks (*), and any similar punctuation/whitespace, while alphanumeric characters (and other characters that constitute a legal identifier) are retained.

Specification of the Task

Overview

You are working on sqlitecollections, a Python library that provides collections behaving like dict, list, and set, backed by SQLite. Values (and dictionary keys) are serialized to bytes before they are stored in the database, and they are deserialized when read back.

You must introduce an explicit, centralized default serializer and deserializer on the base collection class and make it the default (de)serialization mechanism for all collections. These defaults must produce a serialized byte representation that is a specific, deterministic format (see below).

Public API to Be Implemented

The base class SqliteCollectionBase in the module sqlitecollections.base must expose two static methods (callable both on the class and via the class object without instantiating):

class SqliteCollectionBase(...):
    @staticmethod
    def _default_serializer(value) -> bytes: ...

    @staticmethod
    def _default_deserializer(data: bytes) -> Any: ...

They must be reachable as:

  • sqlitecollections.base.SqliteCollectionBase._default_serializer
  • sqlitecollections.base.SqliteCollectionBase._default_deserializer

The module sqlitecollections.base must keep exposing the names dumps and loads (the pickle serialization functions), so that sqlitecollections.base.dumps and sqlitecollections.base.loads are symbols in that module namespace that are patchable/importable.

Behavior Requirements

_default_serializer(value)

Takes an arbitrary Python object and serializes it to bytes using pickle, explicitly specifying pickle protocol version 3.

  • It must delegate to the module-level dumps symbol (sqlitecollections.base.dumps), invoking it with the object as the single positional argument and passing the protocol as the keyword argument protocol=3. Its return value must be exactly what dumps returns.
  • As a concrete case, _default_serializer("123") must return the bytes: b'\x80\x03X\x03\x00\x00\x00123q\x00.'
  • Calling behavior for _default_serializer("x"): dumps is invoked exactly once as dumps("x", protocol=3).
_default_deserializer(data)

Takes the bytes produced by _default_serializer and deserializes them back into the original Python object (pickle load).

  • The call _default_deserializer(b'\x80\x03X\x03\x00\x00\x00123q\x00.') must return "123".
Default (de)serialization applied by all collections

When a collection (Dict, List, Set, or a subclass of SqliteCollectionBase) is constructed without a serializer/deserializer that was supplied explicitly:

  • The serializer attribute must be SqliteCollectionBase._default_serializer.
  • The deserializer attribute must be SqliteCollectionBase._default_deserializer.

Specifically, for an instance that has just been constructed with no serializer/deserializer arguments:

  • instance.serializer is SqliteCollectionBase._default_serializer
  • instance.deserializer is SqliteCollectionBase._default_deserializer

(The rest of the initialization behavior — creating/connecting to the database, persist, table_name, etc. — is unchanged.)

Consequence: serialized format on disk

Since the default serializer now uses pickle protocol 3, every value that any collection using the defaults stores must match the bytes that SqliteCollectionBase._default_serializer produces for that value. In particular:

  • List stores the serialized bytes of each element in the serialized_value column (together with its item_index); for an element x, the stored bytes must equal _default_serializer(x).
  • Dict stores the serialized key and the serialized value in the serialized_key / serialized_value columns (along with item_order); the stored bytes must equal _default_serializer(key) and _default_serializer(value) respectively.
  • Set stores the serialized bytes of each element in the serialized_value column; the stored bytes must equal _default_serializer(element).

For reference, byte sequences produced by protocol‑3 pickle look like:

  • "a" → 800358010000006171002e
  • "z" → 80035801000000 7a 71002e
  • 0 (int) → 80034b002e
  • None → 80034e2e

These are the values that are written to and read from the database for all collection operations (initialization with initial data, item assignment, insertion, appending, extending, popping, sorting, set operations, etc.). All of these operations must round-trip correctly through the new default (de)serializer.

Notes and Constraints

  • This change is purely about the default serialization mechanism and its byte format. Apart from what is needed to route (de)serialization through the new defaults, do not alter the public method signatures or the semantics of the collection operations themselves.
  • Serializer/deserializer arguments that are supplied explicitly must still be honored (only the default changes).
  • list.append must persist the change so that the appended element is reflected immediately in the database.
