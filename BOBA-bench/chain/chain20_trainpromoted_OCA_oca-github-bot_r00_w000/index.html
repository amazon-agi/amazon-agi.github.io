  • ref: a string naming a git reference (e.g. "origin/master") to compare the current working tree state against.
Return value

A set of strings, where each string is the name of an addon that has been modified relative to ref. Addon names are the top-level directory names under which the changed files reside (see rules below). If no addons are modified, an empty set is returned (i.e. a falsy set).

Behavior

The function must determine the set of files that differ between the given ref and the current committed state of the repository at addons_dir, then map those changed files to addon names according to the following rules.

Identifying an addon

A top-level directory within the repository is considered an addon if it is a valid Odoo addons directory containing a recognized manifest file (the existing manifest-detection logic in this module already defines what constitutes a valid addon and its manifest, e.g. a directory containing __manifest__.py).

Mapping changed files to addon names

  1. Direct addon changes. If a changed file lives inside a top-level directory that is a valid addon, that top-level directory name is included in the result set.

  2. setup directory changes. Changes to files located under a top-level setup/ directory must be mapped to the corresponding addon name.   • Changes that have been made in local commits (i.e., present locally but not yet reachable from ref) count as modifications and appear in the result.
  • Once local commits are pushed such that ref includes them, those changes no longer count as modifications (the result set no longer contains those addons based on those commits).

  • A committed setup/addon/setup.py (where addon is a valid addon) not yet in ref → result includes "addon".
  • A commit that simultaneously adds a new addon addon2/ (with manifest), modifies a file inside the existing addon/, and adds a top-level README file → result includes "addon" and "addon2" but nothing derived from the README.

Inputs

version

version is a string containing exactly five dot-separated numeric components:

component_0.component_1.major.minor.patch

The component indices and significance, from left to right, are:

  1. component 0, the most significant
  2. component 1
  3. major at index 2
  4. minor at index 3
  5. patch at index 4, the least significant

For example, "12.0.1.0.0" is valid.

level

level selects the component to increment. The supported values are exactly:

  • "major"
  • "minor"
  • "patch"

Behavior

  • For level == "minor", increment index 3 and reset index 4.
  • For level == "patch", increment index 4; there are no lower-significance components to reset.

The first two components are preserved for every supported level; this API does not provide a level that increments either of them.

Task Specification: Bot Command Parser

Overview

Implement a command parser for a GitHub bot that scans text (e.g., issue/PR comment bodies) for bot commands and yields structured command objects.

Public API

  • InvalidCommandError — an exception class.
  • InvalidOptionsError — an exception class.

Command Syntax

Commands appear on lines within the input text and use the following format:

/ocabot <command_name> [options...]
  • The trigger prefix is /ocabot.
  • The command name follows the prefix.
  • Zero or more whitespace-separated options may follow the command name.
  • Arbitrary amounts of whitespace may separate the prefix, command name, and options (e.g., /ocabot merge patch must parse the same as /ocabot merge patch).
  • Lines that do not contain a bot command (arbitrary text) are ignored.
  • Multiple bot commands may appear in a single input string (typically one per line). All valid commands must be yielded, in order of appearance. For example, an input containing three /ocabot merge ... lines must yield exactly three command objects.

Command Objects

Each yielded command object must expose a name attribute holding the command name string.

The merge command
  • Recognized command name: "merge".
  • Yielded object's name attribute equals "merge".
  • Accepts an optional single argument, the "bump version" level, exposed on the object via a bumpversion attribute.
    • Valid values: "major", "minor", "patch". When one of these is provided, bumpversion equals that string.
    • When no argument is provided (/ocabot merge), bumpversion is None.
    • When an argument is provided that is not one of the valid values (e.g., /ocabot merge brol), parsing must raise InvalidOptionsError.

Error Conditions

  • When the parsed command name is not a recognized command (e.g., /ocabot not_a_command), parsing must raise InvalidCommandError.
  • When a recognized command receives invalid options (see merge above), parsing must raise InvalidOptionsError.

Because parse_commands may return a generator, these errors are permitted to be raised while the result is being iterated/consumed.

Objective

Implement or adjust addon-change detection so that the bot reports the Odoo addons affected by the Git difference between a supplied reference and the repository's current Git-visible state. The detection must distinguish real addons at the repository root from ordinary Python packaging content under setup/, while recognizing the canonical addon symlink used by Odoo packaging layouts.

def git_modified_addons(addons_dir, ref):
    ...

  • ref is the Git reference against which the current state is compared, such as "origin/master".
  • The return value is a set of addon directory names as strings. Names must be unique.
  • If no qualifying addon is affected, return an empty set.

Addon and Change Definitions

A real addon is a directory located directly below addons_dir and containing an Odoo manifest. Supported manifest conventions remain __manifest__.py, __openerp__.py, and __terp__.py.

The relevant changes are those visible in the Git comparison from ref to the current state. This includes revisions recorded after ref and tracked index or working-tree differences represented by that comparison.

Required Detection Behavior

Changes in real root-level addons

For each changed file or entry below a real addon directory at the repository root, include that directory's name in the result. This applies at any depth within the addon and includes newly added root-level addons once they contain a recognized manifest.

Multiple changed entries for one addon must still produce only one set member. Changes in several addons must produce the union of their names.

Once ref represents the same state as the current tree, those previously observed changes must no longer produce a result.

Ordinary setup/ content is excluded

The repository-root setup/ directory is a Python packaging area, not an addon named setup. Its ordinary files and directories must not be interpreted as addon changes merely because their paths contain an addon-like package name.

In particular, a difference confined to a path such as:

setup/<packaging-name>/setup.py

must return an empty set, including when <packaging-name> is also the name of a real root-level addon. Other ordinary packaging files or non-addon subdirectories under setup/ are excluded in the same way.

Canonical packaging symlink exception

There is one explicit exception to the ordinary setup/ exclusion. A changed symlink in this canonical layout:

setup/<packaging-name>/odoo/addons/<addon>

must add <addon> to the result when the symlink points to the real addon directory at <addons_dir>/<addon>. This is an addon-bearing packaging link, and it must be recognized even when no file inside the real root-level addon differs from ref.

For example, with a real root addon named addon, adding and recording this link:

setup/addon/odoo/addons/addon -> ../../../../addon

must make the function return {"addon"} relative to a reference that does not contain the link.

This exception is triggered by the changed addon-link entry itself. The mere presence of an unchanged canonical symlink must not cause an ordinary sibling file such as setup.py to count as an addon change. The returned name is the linked root addon name, not setup and not an unrelated packaging-directory name.

Unrelated changes

Do not report names for repository-root files, directories that are not recognized root-level addons, or ordinary packaging scaffolding. For example, changing only a root README and ordinary setup/ files yields an empty set.

No qualifying difference set()

A new root addon addon2 with a recognized manifest is added {"addon2"}

Overview

Implement functionality to build Python wheels for Odoo addons found in a git repository and publish them into a simple package index directory structure. Additionally, extend an existing module with a helper that returns the directory paths of git-modified addons.

Part 1: New module oca_github_bot/build_wheels.py

Create a new module exposing the following public function:

def build_and_publish_wheels(addons_dir, simple_index_root):
    ...
Parameters
  • addons_dir: a path to a git repository directory that contains Odoo addons. It may be given as a str or as a path-like object (e.g. pathlib.Path). Both forms must work.
  • simple_index_root: a path to the root directory of a simple package index. It may be given as a str or as a path-like object. Both forms must work.
Behavior

For each addon in addons_dir that is packaged (i.e. each addon has an installable Python package definition under a setup/<addon_name>/ layout as produced by the standard Odoo setuptools packaging convention), build a wheel and publish it into the simple index.

Publishing into the simple index means: for each built wheel, place it inside a per-package subdirectory of simple_index_root. The subdirectory is named after the wheel's normalized distribution name using PEP 503 normalization (lowercased, runs of ., _, or - collapsed to a single -). For example, a wheel for the distribution odoo12-addon-addon1 is placed in simple_index_root/odoo12-addon-addon1/, and the wheel file itself keeps its original wheel filename (e.g. one beginning with odoo12_addon_addon1 and ending with .whl).

Concretely, after a run:

  • simple_index_root contains exactly one subdirectory per published addon package.
  • Each such subdirectory contains exactly the wheel file(s) for that package.
Distribution naming and Python tags

The distribution name and the wheel's Python compatibility tag are determined by the addon's Odoo series (the major series taken from its manifest version):

  • Series 10.0: distribution name prefix odoo10-addon-, wheel filename contains the Python tag -py2-.
  • Series 11.0: distribution name prefix odoo11-addon-, wheel filename contains the Python tag -py2.py3-.
  • Series 12.0: distribution name prefix odoo12-addon-, wheel filename contains the Python tag -py3-.

For an addon named addonX of series N.0, the published package directory is odooN-addon-addonX and the wheel filename begins with odooN_addon_addonX and ends with .whl.

(The above naming/tagging follows from the standard Odoo setuptools packaging conventions; the function must produce wheels consistent with them.)

Edge case: no addons

If addons_dir contains no packaged addons, the function must complete successfully and leave simple_index_root empty (no subdirectories or files created).

Incremental / repeated invocation

The function may be called multiple times against the same addons_dir and simple_index_root as addons are added over time. Each call must ensure that every packaged addon currently present in addons_dir is published into simple_index_root. Previously published packages from earlier calls must remain present. After all addons have been added and the function invoked, simple_index_root contains one subdirectory per addon.

Part 2: New function in oca_github_bot/manifest.py

Add a new public function to the existing oca_github_bot.manifest module:

def git_modified_addon_dirs(repo_dir, ref):
    ...
Parameters
  • repo_dir: a path to a git repository (path-like or str).
  • ref: a git ref/tag/branch name to compare the current working tree against (e.g. "origin/master").
Behavior

This is the directory-path counterpart to the existing git_modified_addons(repo_dir, ref) function, which returns a set of the names of addons modified since ref.

git_modified_addon_dirs must return a list of absolute directory path strings, one per modified addon, where each path is the addon's directory joined onto repo_dir (i.e. str(repo_dir / addon_name) form). For example, if the only modified addon is addon in repository repo_dir, the return value is [str(repo_dir / "addon")].

Relationship to existing git_modified_addons

The set of modified addons considered is the same as that produced by git_modified_addons. In particular:

  • An addon counts as modified if changes to its files exist between ref and the current state.
  • If an addon directory has been removed relative to ref, that addon must not appear in the result. In the scenario where the only difference since ref is the removal of an addon (and no other addon changes remain relative to ref), the result of git_modified_addons is empty (and correspondingly git_modified_addon_dirs yields no entries).

git_modified_addons retains its existing behavior of returning a set of addon name strings.
