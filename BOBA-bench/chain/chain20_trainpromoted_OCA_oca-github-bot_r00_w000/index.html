Task Description

Implement several utility functions plus one helper class in the oca_github_bot package. Each of the items below lays out the exact required behavior. The public API names, module paths, and signatures must match precisely so that they can be imported and called as specified.

1. Helper for pushing with git — oca_github_bot.github.git_push_if_needed

Define a function with the signature:

git_push_if_needed(remote, branch, cwd=None)

Behavior:

  • It compares the state of the local branch against the supplied remote for the named branch (operating within the working directory cwd if it is provided).
  • If there is nothing new to push (the remote already contains the local commits), it must carry out no push and return a falsy value.
  • If there are new local commits to push, it must push them to the specified remote/branch and return a truthy value. Once a push has succeeded, a call made immediately after it with no new local commits must again return a falsy value.
  • If the push would be rejected because it is not a fast-forward (for example, the local branch is behind the remote or has diverged from it such that the remote would need to be overwritten), the function must retry the task by raising celery.exceptions.Retry. (Put differently, the function is a Celery task body / makes use of Celery's retry mechanism, and a push rejection caused by a non-fast-forward triggers a retry.)

2. Wrapper around GitHub calls — oca_github_bot.github.gh_call

Define a function:

gh_call(func, *args, **kwargs)

Behavior:

  • It calls func(*args, **kwargs) and returns the result of that call.
  • If the call raises a github3.exceptions.ForbiddenError that represents a rate-limit condition — recognizable from the HTTP response carrying the headers X-RateLimit-Remaining and X-RateLimit-Reset — the function must retry the task by raising celery.exceptions.Retry rather than letting the original error propagate. (This amounts to a Celery task retry.)
  • If the call raises a github3.exceptions.ForbiddenError that is not a rate-limit condition (the rate-limit headers are absent), the original ForbiddenError must propagate unchanged to the caller.

The two cases are told apart solely by whether the rate-limit headers are present on the exception's response object.

3. Detecting addons directories — oca_github_bot.manifest.is_addons_dir

Define a function:

is_addons_dir(addons_dir)

addons_dir is a filesystem path (a string). Behavior:

  • Return truthy if at least one immediate subdirectory of the directory is an Odoo addon — i.e. a subdirectory containing a __manifest__.py file.
  • Return falsy if it has no such addon subdirectory (for example, a directory whose only subdirectory has no manifest file).

4. Classifying branch names — oca_github_bot.version_branch

Create the module oca_github_bot.version_branch offering two functions:

is_main_branch_bot_branch(branch)
is_protected_branch(branch)
is_main_branch_bot_branch(branch)

For a branch name supplied as a string, return truthy only when the branch is an Odoo version branch of the form <major>.0 with the major version being 8 or greater. Specifically:

  • "8.0", "12.0" → truthy
  • "6.1", "7.0" → falsy (version below 8, and/or the minor part is not 0)
  • "10.0-something" → falsy (anything going beyond a bare <major>.0 name)
is_protected_branch(branch)

For a branch name supplied as a string, return truthy when the branch qualifies as a protected branch. Specifically:

  • "master" → truthy
  • Any bare Odoo version branch of the form <major>.<minor> (e.g. "6.0", "12.0") → truthy
  • "10.0-something" (anything going beyond a bare version name) → falsy

03 A function is to be added to the oca_github_bot.manifest module 724 words · source specification, reworded by GLM-5.3-Flash

Specification of the Task

Goal

A function is to be added to the oca_github_bot.manifest module; its job is to determine which Odoo addons in a local git repository count as modified relative to a given git reference.

Public API

Inside the module oca_github_bot.manifest, add the function shown below:

def git_modified_addons(addons_dir, ref):
    ...
Parameters
  • addons_dir: a path (path-like object) that points at the root of a git working tree. This one directory fills both roles: it is the working directory of the git repository, and it contains the addons.
  • ref: a string that names a git reference (e.g. "origin/master"); the state of the current working tree is what gets compared against it.
Value returned

The value returned is a set of strings, each of which names an addon modified relative to ref. An addon's name is taken from the top-level directory under which the changed files sit (see the rules below). When no addons have been modified, an empty set is what gets returned (i.e. a falsy set).

Behavior of the Function

First of all, the function must find the set of files on which the supplied ref and the committed state that the repository at addons_dir currently has disagree; those changed files must then be mapped to addon names by applying the rules below.

Recognizing an addon

Treat a top-level directory of the repository as an addon when it is a valid Odoo addons directory whose contents include a recognized manifest file (this module's existing manifest-detection logic already defines what makes an addon and its manifest valid, e.g. a directory that contains __manifest__.py).

How changed files map to addon names

  1. Changes directly inside an addon. Whenever a changed file is located within a top-level directory that qualifies as a valid addon, the result set comes to include the name of that top-level directory.

  2. Changes under a setup directory. Where files under a top-level setup/ directory are concerned, changes must be mapped onto the name of the corresponding addon. Spelled out concretely: whenever a path has the shape setup/<addon_name>/..., <addon_name> belongs in the result set. (In the OCA layout, packaging for the addon called <addon_name> is mirrored by setup/<addon_name>/.)

  3. Non-addon changes are ignored. Changed files that fall neither within a valid addon directory nor under the setup/ directory — a top-level README file, for instance — add no entry to the result set.

Semantics of the comparison
  • On one side of the comparison sits the committed state of the working tree; on the other side sits the supplied ref.
  • Changes that local commits have brought in (i.e., present locally but not reachable from ref yet) are counted as modifications and show up in the result.
  • After local commits have been pushed such that ref includes them, those changes stop counting as modifications (based on those commits, the result set no longer contains those addons).

Expected outcome examples

  • An addon directory addon/ (it contains a manifest) that has just been committed and is not yet part of ref → "addon" shows up in the result.
  • After a push has caused ref to contain that commit → the result stops including "addon" (an empty set if nothing else has changed).
  • setup/addon/setup.py has been committed (with addon being a valid addon) but is not yet present in ref → the result includes "addon".
  • One commit simultaneously introduces a new addon addon2/ (manifest included), alters a file inside the existing addon/, and adds a top-level README file → "addon" and "addon2" end up in the result, while nothing is derived from the README.

Notes

  • What the function works from is the local repository state together with the referenced git ref; it carries out no network fetch of its own.
  • For deciding whether a top-level directory qualifies as an addon, reuse the module's existing addon/manifest detection.

Note on the Test Fixture (unrelated to core behavior)

Ensure that the git-based test environment can create commits in environments where commit signing might otherwise be required; for this purpose, commit GPG signing must be disabled in the repository configuration used for testing (git config commit.gpgsign false). This is a matter for the test fixture only, and the module's public API is not affected by it.

Goal

The task is to implement bump_version, which increments a single release component of an Odoo-style five-part version and resets every less-significant component to zero.

Public API

The function that is required is the package function oca_github_bot.manifest.bump_version. It must be importable as:

from oca_github_bot.manifest import bump_version
Function Signature
def bump_version(version: str, level: str) -> str:

Input Parameters

version

version is a string consisting of exactly five numeric components separated by dots:

component_0.component_1.major.minor.patch

From left to right, the component indices and their significance are:

  1. component 0, which is the most significant
  2. component 1
  3. major at index 2
  4. minor at index 3
  5. patch at index 4, which is the least significant

An example of a valid value is "12.0.1.0.0".

level

level chooses the component to increment. The supported values are exactly:

  • "major"
  • "minor"
  • "patch"

Behavior

The function returns a new version string built from five components. It must increment the component chosen by level by 1, reset every component to its right to 0, and leave every component to its left unchanged.

  • For level == "major", the component at index 2 is incremented and the components at indices 3 and 4 are reset.
  • For level == "minor", the component at index 3 is incremented and the component at index 4 is reset.
  • For level == "patch", the component at index 4 is incremented; there are no components of lower significance to reset.

For every supported level, the first two components are preserved; the API does not provide a level that increments either of them.

version level result
"12.0.1.0.0" "major" "12.0.2.0.0"
"12.0.1.1.1" "major" "12.0.2.0.0"
"12.0.1.0.0" "minor" "12.0.1.1.0"
"12.0.1.0.1" "minor" "12.0.1.1.0"
"12.0.1.0.0" "patch" "12.0.1.0.1"

Error Conditions

The function must raise RuntimeError in either of the following cases:

  • version does not consist of exactly five numeric components separated by dots, such as "1.0" or "1.0.1".
  • level is not one of "major", "minor", or "patch", such as "none".

Format of the Output

Specification: Parser for Bot Commands

Summary

Write a command parser for a GitHub bot that scans text (for example, the bodies of issue/PR comments) looking for bot commands and yields structured command objects.

Public Interface

Create a module located at oca_github_bot/commands that exposes these names:

  • parse_commands(text) — a function that accepts one string as its argument and returns an iterable (e.g., a generator) of command objects.
  • InvalidCommandError — an exception class.
  • InvalidOptionsError — an exception class.

Syntax of Commands

Commands are placed on lines inside the input text and take this format:

/ocabot <command_name> [options...]
  • The prefix that triggers a command is /ocabot.
  • After the prefix comes the command name.
  • Following the command name, zero or more options separated by whitespace may appear.
  • The prefix, the command name, and the options may be separated by arbitrary amounts of whitespace (e.g., /ocabot merge patch must parse the same as /ocabot merge patch).
  • Lines that hold no bot command (arbitrary text) are ignored.
  • A single input string may contain multiple bot commands (typically one per line). All valid commands must be yielded, in the order in which they appear. For example, input that contains three /ocabot merge ... lines must yield exactly three command objects.

Objects Representing Commands

Every command object that is yielded must expose a name attribute that holds the command name string.

The command called merge
  • The recognized name for this command is "merge".
  • The name attribute of the yielded object equals "merge".
  • Accepts one optional argument, the "bump version" level, which is exposed on the object through a bumpversion attribute.
    • The valid values are "major", "minor", "patch". When one of these is given, bumpversion equals that string.
    • When no argument is given (/ocabot merge), bumpversion is None.
    • When the argument that is provided is not one of the valid values (e.g., /ocabot merge brol), parsing must raise InvalidOptionsError.

Error Cases

  • When the command name produced by parsing is not a recognized command (e.g., /ocabot not_a_command), parsing must raise InvalidCommandError.
  • When invalid options are given to a recognized command (see merge above), parsing must raise InvalidOptionsError.

Since parse_commands may return a generator, it is permitted for these errors to be raised while the result is being iterated/consumed.

09 Detecting Odoo Addons Changed by a Git Diff 966 words · rewritten by GPT-5.6-sol, reworded by GLM-5.3-Flash

Task Specification: Detecting Odoo Addons Changed by a Git Diff

Goal

Addon-change detection is to be implemented or adjusted so that the bot reports which Odoo addons are affected by the Git difference between a reference supplied to it and the repository's current state as visible to Git. The detection must tell real addons at the repository root apart from ordinary Python packaging content under setup/, and the canonical addon symlink used by Odoo packaging layouts must be recognized as well.

Public Interface

It must remain possible to import the existing symbol from the manifest helper module:

from oca_github_bot.manifest import git_modified_addons

def git_modified_addons(addons_dir, ref):
    ...
  • addons_dir — a string or a path-like value — identifies the root of a Git repository or working tree.
  • ref is the Git reference the current state gets compared against; "origin/master" serves as one example.
  • What the function returns is a set holding addon directory names as strings. The names must be unique.
  • An empty set must be returned if no qualifying addon is affected.

What Counts as an Addon and as a Change

A directory counts as a real addon when it sits directly below addons_dir and contains an Odoo manifest. The manifest conventions that are supported stay __manifest__.py, __openerp__.py, and __terp__.py.

A change is relevant when it is visible in the Git comparison from ref to the current state. Revisions recorded after ref fall under this, as do tracked index or working-tree differences that the comparison represents.

What the Detection Is Required to Do

Changes inside real root-level addons

Each changed file or entry that is located below a real addon directory at the repository root must contribute that directory's name to the result. This holds at any depth inside the addon, and newly added root-level addons are covered too, as soon as a recognized manifest is present in them.

If one and the same addon has multiple changed entries, the result must still end up containing only one member for it. When several addons see changes, the result must be the union of those names.

As soon as ref and the current tree represent the same state, the changes observed earlier must no longer produce a result.

Ordinary content under setup/ does not count

At the repository root sits a setup/ directory; it is a Python packaging area, not an addon that is named setup. Its ordinary files and directories must not be interpreted as addon changes merely because an addon-like package name appears somewhere in their paths.

To be concrete: when a difference covers nothing except a path of this form:

setup/<packaging-name>/setup.py

the function must return an empty set, and this holds even when <packaging-name> is also the name of a real root-level addon. The same kind of exclusion covers other ordinary packaging files as well as subdirectories under setup/ that are not addons.

Exception for the canonical packaging symlink

The exclusion of ordinary setup/ content has one explicit exception. When a symlink has changed and sits in this canonical layout:

setup/<packaging-name>/odoo/addons/<addon>

<addon> must be added to the result if the symlink points to the real addon directory at <addons_dir>/<addon>. Being an addon-bearing packaging link, it must be recognized even when there is no file inside the real root-level addon that differs from ref.

As an illustration: take a real root addon named addon. Adding this link and recording it:

setup/addon/odoo/addons/addon -> ../../../../addon

must lead the function to return {"addon"} when measured against a reference that does not contain the link.

The changed addon-link entry itself is what sets off this exception. An unchanged canonical symlink must not, merely by being present, cause an ordinary sibling file such as setup.py to count as an addon change. The name that gets returned is the linked root addon's name — it is not setup, and it is not the name of an unrelated packaging directory either.

Changes that are unrelated

Names must not be reported for repository-root files, for directories that do not count as recognized root-level addons, or for ordinary packaging scaffolding. By way of example: if the only changes are a root README and ordinary setup/ files, an empty set is the result.

Results to Expect

Difference as measured against ref Result
There is no difference that qualifies set()
A file below the root addon addon is changed {"addon"}
A new root addon addon2 that has a recognized manifest is added {"addon2"}
The only thing added is setup/addon/setup.py set()
The canonical link setup/addon/odoo/addons/addon -> ../../../../addon is added and points to the root addon, which is unchanged {"addon"}
The root addons addon and addon2 both have qualifying changes, along with changes to unrelated root files {"addon", "addon2"}

The same rules also govern a cumulative packaging sequence: after the root addon and ref have been synchronized, recording only setup/addon/setup.py yields set(); recording the canonical symlink above afterwards yields {"addon"} against that same unchanged reference, even though the ordinary setup.py path likewise remains part of the overall difference.

Scope and Compatibility

  • The function's name, import location, parameters, and set return type have to be preserved.

Specification of the Task

Summary

Functionality must be implemented to build Python wheels for the Odoo addons found in a git repository and to publish those wheels into a simple package index laid out as a directory structure. In addition, an existing module is to be extended with a helper that returns the directory paths of git-modified addons.

Part 1: The new module oca_github_bot/build_wheels.py

A new module is to be created that exposes the following public function:

def build_and_publish_wheels(addons_dir, simple_index_root):
    ...
Parameters
  • addons_dir: a path to a git repository directory that contains Odoo addons. It may be supplied either as a str or as a path-like object (e.g. pathlib.Path); both forms must work.
  • simple_index_root: a path to the root directory of a simple package index. It may be supplied as a str or as a path-like object, and both forms must work.
Behavior

For every addon in addons_dir that is packaged (that is, every addon has an installable Python package definition under a setup/<addon_name>/ layout as produced by the standard Odoo setuptools packaging convention), build a wheel and publish it into the simple index.

Publishing into the simple index works as follows: each built wheel is placed inside a per-package subdirectory of simple_index_root. The name of the subdirectory comes from the wheel's normalized distribution name, using PEP 503 normalization (lowercased, runs of ., _, or - collapsed to a single -). As an example, a wheel for the distribution odoo12-addon-addon1 is placed in simple_index_root/odoo12-addon-addon1/, and the wheel file itself keeps its original wheel filename (e.g. one beginning with odoo12_addon_addon1 and ending with .whl).

To make this concrete, after a run:

  • simple_index_root ends up containing exactly one subdirectory per published addon package.
  • Every such subdirectory contains exactly the wheel file(s) for that package.
Distribution names and Python tags

The addon's Odoo series (the major series taken from its manifest version) determines the distribution name and the wheel's Python compatibility tag:

  • Series 10.0: the distribution name has the prefix odoo10-addon-, and the wheel filename contains the Python tag -py2-.
  • Series 11.0: the distribution name has the prefix odoo11-addon-, and the wheel filename contains the Python tag -py2.py3-.
  • Series 12.0: the distribution name has the prefix odoo12-addon-, and the wheel filename contains the Python tag -py3-.

When an addon is named addonX and is of series N.0, its published package directory is odooN-addon-addonX, and its wheel filename starts with odooN_addon_addonX and ends with .whl.

(The naming/tagging above follows from the standard Odoo setuptools packaging conventions; the function must produce wheels consistent with them.)

Edge case: no addons

If there are no packaged addons inside addons_dir, the function must complete successfully and leave simple_index_root empty (no subdirectories or files created).

Incremental / repeated invocation

As addons get added over time, the function may be invoked several times against the same addons_dir and simple_index_root. Every call must ensure that each packaged addon present in addons_dir at the time of the call is published into simple_index_root. Packages published by earlier calls must remain present. Once all addons have been added and the function has been invoked, simple_index_root contains one subdirectory per addon.

The existing git_modified_addons(repo_dir, ref) function returns a set of the names of addons modified since ref; the new function is its directory-path counterpart.

git_modified_addon_dirs must return a list of absolute directory path strings, one per modified addon, where each path is the addon's directory joined onto repo_dir (i.e. of the str(repo_dir / addon_name) form).
