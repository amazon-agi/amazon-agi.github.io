Task Specification: Dependency Injection Context

Implement a lightweight dependency-injection container across junkie.core_context and junkie.context. It registers values under string names, inspects callable signatures, resolves dependencies recursively by parameter name, and manages resource lifetimes through build context managers.

Common resolution and lifecycle rules

  • A registration maps a string name to either an already-constructed instance or a factory callable.
  • A registered instance is returned directly. The same registered object must be supplied everywhere that name is requested, so shared mutable instances retain object identity across dependent factories.
  • A factory may be a plain function, lambda, class, or generator function acting as a context manager.
  • To invoke a factory or construct a target class, inspect its parameters and resolve a dependency with the same registered name for every parameter. Supply the resolved dependencies to the callable as keyword arguments.
  • Resolution is recursive and transitive. A factory dependency may itself be produced by another factory, regardless of registration order.
  • Resolve parameters in declaration order. Each parameter must be fully resolved before the next parameter, and the callable is invoked only after all of its dependencies have been resolved. This order also determines observable factory and resource-entry side effects.
  • Dependency matching is purely name-based. Type annotations do not alter lookup behavior.

Every public build method described below returns a context manager and must be usable in a with statement.

Module: junkie.core_context

Class: CoreContext

Construct with no arguments:

context = CoreContext()

The context maintains the instance and factory registrations used by subsequent builds.

add_instances(self, mapping: dict)

Register already-constructed values. mapping maps string names to concrete values such as strings, lists, or arbitrary objects. A value registered this way is supplied directly rather than invoked. Calls accumulate registrations; registering another instance under an existing instance name updates that value for later builds.

add_factories(self, mapping: dict)

Register factory callables under string names. Supported callables include functions, lambdas, classes, and generator-style context-manager factories. Calls accumulate registrations; registering another factory under an existing factory name updates that factory for later builds.

When a factory is resolved, resolve its parameters recursively by name and invoke it with those dependencies. A zero-parameter factory is invoked with no dependencies.

build_dict(self, names) — context manager

names may be either a set of names or a list of names. Entering the returned context manager yields a dictionary from each requested name to its resolved value.

  • Only explicitly requested names appear as keys. Transitive dependencies are not added unless they were also requested.
  • For a list, requested names must be fully resolved in list iteration order. Factory calls and other construction side effects therefore occur in that order, and the yielded dictionary preserves that insertion order.
  • A set is also accepted, but does not establish a deterministic request order.

Examples:

context = CoreContext()
context.add_instances({"text": "abc"})
with context.build_dict({"text"}) as values:
    assert values == {"text": "abc"}

context = CoreContext()
context.add_instances({"prefix": "abc", "suffix": "def"})
context.add_factories({"text": lambda prefix, suffix: prefix + suffix})
with context.build_dict({"text", "prefix"}) as values:
    assert values == {"text": "abcdef", "prefix": "abc"}
build_object_by_type(self, target: type) — context manager

Entering the returned context manager constructs and yields an instance of target. Resolve the target class constructor's parameters by registered name in constructor declaration order and pass them as keyword arguments.

class Message:
    def __init__(self, prefix, suffix):
        self.text = prefix + suffix

context = CoreContext()
context.add_instances({"prefix": "abc", "suffix": "def"})
with context.build_object_by_type(Message) as message:
    assert message.text == "abcdef"
build_object_by_name(self, name: str) — context manager

Entering the returned context manager yields the single value resolved under name. The name may refer to a pre-built instance or to any supported factory, including a class.

class Message:
    def __init__(self, prefix, suffix):
        self.text = prefix + suffix

context = CoreContext()
context.add_instances({"prefix": "abc", "suffix": "def"})
context.add_factories({"text": Message})
with context.build_object_by_name("text") as message:
    assert message.text == "abcdef"
Factory-produced context managers

When a factory function or class produces an object implementing the context-manager protocol (__enter__ and __exit__), manage that result as part of the surrounding build:

  1. Resolve the factory's dependencies and invoke the factory.
  2. Enter the produced context manager immediately.
  3. Use the value returned by __enter__ as the resolved value supplied to dependents or yielded to the caller.
  4. Exit it when the surrounding build context exits.

The same behavior applies when a class constructed directly by build_object_by_type produces a context manager. Generator-function context-manager factories follow this contract as well: their yielded value is the resolved value, and their code after yield runs during teardown. Registered pre-built instances remain direct values and are not automatically entered.

Resources are entered in construction order and exited in reverse construction order. Because dependencies are resolved in parameter declaration order, the first declared context-managed dependency is entered before the next one and exited after it. Teardown occurs when leaving the surrounding build context.

For example, if a target declares (message_service, database_context) and both dependencies are context-managed factories, the observable lifecycle is:

  1. enter message_service;
  2. enter database_context;
  3. execute the caller's with block;
  4. exit database_context;
  5. exit message_service.
Debug logging

Emit build and lifecycle activity at DEBUG level through the logger named junkie, i.e. logging.getLogger("junkie"). The following message text and ordering are part of the public behavior.

Build entry

Entering a build context emits:

build(<target>)

Render the target as follows:

  • A type uses its __name__, for example build(Message).
  • A single string name is shown in single quotes, for example build('message').
  • A set or list uses its normal collection representation, for example build(['a', 'b']).
Callable invocation

Every factory or target-class invocation emits a message after its dependencies have been resolved and immediately before the callable is invoked:

<resolved-name> = <callable-name>(<parameter-name-list>)
  • <resolved-name> is the registered factory name, or the target type's __name__ for a direct type build.
  • <callable-name> is the callable's __name__; a lambda is therefore rendered as <lambda>.
  • <parameter-name-list> is the Python list representation of all parameter names in declaration order, including [] when there are no parameters.

Examples:

connection_string = <lambda>([])
database_context = create_database(['connection_string'])
Message = Message(['database_context', 'message_service', 'text'])

Recursive dependencies emit their invocation messages before the callable that depends on them.

Context-manager entry and exit

Immediately before entering a context-managed result, emit:

<resolved-name>.__enter__()

During its teardown, emit:

<resolved-name>.__exit__()

Entry messages follow construction order. Exit messages occur after the caller's build block and in reverse resource-construction order. Thus dependency invocation and entry messages follow parameter declaration order, while their corresponding exit messages follow the reverse order.

Class: Context

Context is the higher-level convenience interface over the same registry, resolution, and lifecycle behavior.

Construction

Construct it with zero or more mapping arguments:

Context()
Context(mapping)
Context(mapping1, mapping2, ...)

Each argument is a dictionary from string names to values. Constructor mappings are equivalent to constructing an empty Context and immediately calling add with those mappings in the same order. Subsequent add calls continue to accumulate registrations.

add(self, *mappings: dict)

Accept one or more dictionary arguments in one call. Process and combine all mappings in argument order. Multiple calls accumulate registrations.

Classify each mapped value automatically:

  • A non-callable value is registered as a pre-built instance.
  • A callable value, including a function, lambda, or class, is registered as a factory.
  • The reserved key "class" designates the context's primary class factory. Registering {"class": SomeClass} allows that class to be resolved under the string name "class".

Later mappings for an already registered instance or factory name update that registration for subsequent builds. For example, mappings can override configuration while retaining other names:

context = Context({
    "prefix": "abc",
    "suffix": "def",

})
context.add({"class": Message}, {"suffix": "xyz"})

Here subsequent builds use suffix == "xyz".

build(self, target) — context manager

target accepts all of the following forms:

  • Set of string names: resolve the requested values and yield a dictionary containing only those names.
  • List of string names: yield the same kind of dictionary, but resolve names in list order and preserve that order in the result.
  • String name: resolve one registered instance or factory and yield its single value. In particular, build("class") constructs the class factory registered under "class".
  • Class/type: construct that class directly, resolving its constructor parameters by name, and yield its instance. The target class need not be looked up through the "class" registration.

All forms use the same transitive resolution, parameter and list ordering, context-manager lifecycle, reverse teardown, and logging rules as CoreContext.

Using the preceding registrations:

with context.build({"text", "prefix"}) as values:
    assert values == {"text": "abcxyz", "prefix": "abc"}

with context.build(["text", "prefix"]) as values:
    assert values == {"text": "abcxyz", "prefix": "abc"}

with context.build("class") as message:
    assert message.text == "abcxyz"

with context.build(Message) as message:
    assert message.text == "abcxyz"

Direct class builds must work for both ordinary classes and classes decorated with @dataclass; generated dataclass constructor fields are resolved by field/parameter name in the same way.

Compatibility and scope notes

  • Registration order does not constrain dependency resolution: dependencies may be registered before or after factories that consume them.
  • Request order is meaningful when a list is supplied. Parameter declaration order is always meaningful for dependency construction and lifecycle side effects.
  • Shared registered instances must not be copied during injection.
  • No annotation-based matching is required; registration and parameter names are the dependency keys.
  • Context is available from junkie.context and is also exposed by the junkie package for from junkie import Context.

  1. If that name is present in the mapping, resolve the mapped value recursively. This mapped value overrides any declared default, even when the mapped value is None.
  2. Otherwise, if the parameter declares a default, use that default value.
  3. Otherwise, raise the missing-name error for the parameter name.

After all parameters have been resolved, invoke the factory with each ordinary value supplied for its declared parameter name, together with any variadic expansions described below. Parameter annotations do not change this name-based lookup rule. Classes with generated constructors, such as dataclasses, must therefore work in the same way as other classes.

For example, given:

def make_message(prefix, suffix="!"):
    return prefix + suffix

{"prefix": "Hello"} uses the declared "!" suffix, while {"prefix": "Hello", "suffix": "?"} uses the mapped override.

Variadic parameters

Variadic parameters are also associated with mapping entries by their declared parameter names:

  • For a *args parameter, resolve the mapping entry with the same name and unpack the resulting iterable as positional arguments. Tuple and list values are supported, as are iterable values produced by a factory. If the name is absent, use an empty tuple, so the factory receives no additional positional arguments.
  • For a **kwargs parameter, resolve the mapping entry with the same name and unpack the resulting dictionary as keyword arguments. The dictionary may be stored directly or produced by a factory. If the name is absent, use an empty dictionary, so the factory receives no additional keyword arguments.

For example:

class Collector:
    def __init__(self, *items):
        self.items = items

with Junkie({"items": [1, 2, 3]}).inject(Collector) as collector:
    assert collector.items == (1, 2, 3)

A callable mapped under "items" that returns (1, 2, 3) has the same result.

Managed Factory Results

Generator factories

A generator factory is managed as a context:

  • Advance it to its first yield when resolving it.
  • Use the yielded value as the resolved dependency.
  • On exit from the surrounding inject context, resume or close it so that its teardown logic can run.
Objects implementing the context-manager protocol

If any factory, including a class constructor, returns an object implementing __enter__ and __exit__, manage that object for the lifetime of the surrounding inject context:

  • call __enter__ immediately after constructing the object;
  • inject the value returned by __enter__, which need not be the context-manager object itself; and
  • call __exit__ when the inject context exits.

This applies to ordinary context-manager objects as well as context managers produced from generator-based factories. Plain, non-callable objects stored directly in the mapping remain plain values under the normal name-resolution rules.

All managed results created while resolving one injection context must be torn down in reverse order of construction: the most recently constructed managed result exits first. Cleanup must occur when leaving the injection context, including when control leaves it because of an exception. Standard context-manager exception details are passed through to __exit__.

For example, if resolving an application first enters a connection and then enters a session, leaving the injection context exits the session before the connection.

Debug Logging

Use the logger named junkie and emit the following messages at DEBUG level.

Injection request

Each injection operation emits:

inject(<target-representation>)

The representation is Python's repr of the single target when exactly one target is supplied, and repr of the target tuple otherwise. For example, a single name emits:

inject('service')

Two names emit a message shaped like:

Factory invocation

Immediately before invoking a factory, after its dependencies have been resolved, emit:

<resolution-name> = <factory-name>(<parameter-name-list>)
  • For a callable reached through a mapping entry, <resolution-name> is that mapping key.
  • For a callable supplied directly as a target, <resolution-name> is the callable's name.
  • <factory-name> is the factory's name, including names such as a class name or <lambda>.
  • <parameter-name-list> is the Python list representation of the ordinary parameter names in declaration order. The names appear as quoted strings; an empty list is []. Variadic *args and **kwargs names are not included in this list.

The entry message is emitted as the result is entered. Exit messages follow the required reverse teardown order, so the last managed result entered produces the first exit message.

Error Conditions

Missing name

If a requested string target or a required non-variadic factory parameter is not present in the mapping and has no applicable default, raise RuntimeError with exactly:

Unable to find "<name>"

<name> is the exact requested string or parameter name. For example, an absent dependency named instance_name produces:

Unable to find "instance_name"

Missing variadic parameters do not raise this error; they use the empty tuple or dictionary described above.

Unknown target type

If a target supplied to inject is neither a string nor a type/callable, raise RuntimeError with exactly:

Unknown type "<value>" (str, type or Callable expected)

<value> is the string representation of the offending target. For example, passing integer 1 produces:

Unknown type "1" (str, type or Callable expected)
