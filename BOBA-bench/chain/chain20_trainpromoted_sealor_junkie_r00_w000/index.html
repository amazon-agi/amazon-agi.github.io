Task Specification: Dependency Injection Context

Implement a lightweight dependency-injection container spanning junkie.core_context and junkie.context. The container registers values under string names, inspects callable signatures, resolves dependencies recursively by parameter name, and manages resource lifetimes via build context managers.

Rules shared across resolution and lifecycle

  • A registration associates a string name with either an instance that has already been constructed or a factory callable.
  • A registered instance is returned directly. The very same registered object must be supplied everywhere that name is requested, so shared mutable instances keep their object identity across dependent factories.
  • A factory may be a plain function, a lambda, a class, or a generator function acting as a context manager.
  • Invoking a factory or constructing a target class works by inspecting its parameters and, for every parameter, resolving a dependency under the same registered name. The resolved dependencies are then supplied to the callable as keyword arguments.
  • Resolution is recursive and transitive. A factory's dependency may itself come from another factory, no matter the registration order.
  • Parameters are resolved in declaration order. Each parameter must be fully resolved before the next one, and the callable is invoked only after all of its dependencies have been resolved. This ordering also determines observable factory and resource-entry side effects.
  • Dependency matching is based purely on names. Type annotations have no effect on lookup behavior.

Each public build method described below returns a context manager and must be usable in a with statement.

Module: junkie.core_context

Class: CoreContext

Construct it without arguments:

context = CoreContext()

The context holds the instance and factory registrations that later builds use.

add_instances(self, mapping: dict)

Register values that have already been constructed. mapping is a dictionary from string names to concrete values such as strings, lists, or arbitrary objects. A value registered in this manner is supplied directly instead of being invoked. Calls accumulate registrations; registering one more instance under a name that already holds an instance updates that value for later builds.

add_factories(self, mapping: dict)

Register factory callables under string names. Supported callables include functions, lambdas, classes, and generator-style context-manager factories. Calls accumulate registrations; registering one more factory under a name that already holds a factory updates that factory for later builds.

When a factory is resolved, its parameters are resolved recursively by name and the factory is invoked with those dependencies. A factory taking zero parameters is invoked with no dependencies.

build_dict(self, names) — context manager

names may be either a set of names or a list of names. Entering the returned context manager yields a dictionary mapping each requested name to its resolved value.

  • Only the explicitly requested names appear as keys. Transitive dependencies are not added unless they were requested as well.
  • With a list, the requested names must be fully resolved in list iteration order. Factory calls and other construction side effects therefore happen in that order, and the yielded dictionary keeps that insertion order.
  • A set is accepted too, but it does not establish a deterministic request order.

Examples:

context = CoreContext()
context.add_instances({"text": "abc"})
with context.build_dict({"text"}) as values:
    assert values == {"text": "abc"}

context = CoreContext()
context.add_instances({"prefix": "abc", "suffix": "def"})
context.add_factories({"text": lambda prefix, suffix: prefix + suffix})
with context.build_dict({"text", "prefix"}) as values:
    assert values == {"text": "abcdef", "prefix": "abc"}
build_object_by_type(self, target: type) — context manager

Entering the returned context manager constructs an instance of target and yields it. The target class constructor's parameters are resolved by registered name in constructor declaration order and passed as keyword arguments.

class Message:
    def __init__(self, prefix, suffix):
        self.text = prefix + suffix

context = CoreContext()
context.add_instances({"prefix": "abc", "suffix": "def"})
with context.build_object_by_type(Message) as message:
    assert message.text == "abcdef"
build_object_by_name(self, name: str) — context manager

Entering the returned context manager yields the single value resolved under name. That name may refer either to a pre-built instance or to any supported factory, including a class.

class Message:
    def __init__(self, prefix, suffix):
        self.text = prefix + suffix

context = CoreContext()
context.add_instances({"prefix": "abc", "suffix": "def"})
context.add_factories({"text": Message})
with context.build_object_by_name("text") as message:
    assert message.text == "abcdef"
Context managers produced by factories

When a factory function or class produces an object implementing the context-manager protocol (__enter__ and __exit__), that result is managed as part of the surrounding build:

  1. Resolve the factory's dependencies, then invoke the factory.
  2. Enter the produced context manager immediately.
  3. The value returned by __enter__ is used as the resolved value supplied to dependents or yielded to the caller.
  4. Exit it when the surrounding build context exits.

The same behavior applies when a class that build_object_by_type constructs directly produces a context manager. Generator-function context-manager factories also follow this contract: the value they yield is the resolved value, and the code after the yield runs during teardown. Registered pre-built instances remain direct values and are not entered automatically.

Resources are entered in construction order and exited in the reverse construction order. Since dependencies are resolved in parameter declaration order, the first declared context-managed dependency is entered before the next one and exited after it. Teardown takes place when the surrounding build context is left.

For example, if a target declares (message_service, database_context) and both dependencies are context-managed factories, the observable lifecycle is:

  1. message_service is entered;
  2. database_context is entered;
  3. the caller's with block executes;
  4. database_context is exited;
  5. message_service is exited.
Debug logging

Build and lifecycle activity is emitted at DEBUG level through the logger named junkie, i.e. logging.getLogger("junkie"). The message text and ordering shown below are part of the public behavior.

Entering a build

When a build context is entered, it emits:

build(<target>)

The target is rendered as follows:

  • A type is shown via its __name__, for example build(Message).
  • A single string name appears in single quotes, for example build('message').
  • A set or list is rendered with its normal collection representation, for example build(['a', 'b']).
Invoking callables

Each invocation of a factory or of a target class emits a message after its dependencies have been resolved and immediately before the callable is invoked:

<resolved-name> = <callable-name>(<parameter-name-list>)
  • <resolved-name> is the registered factory name, or the target type's __name__ when the build targets a type directly.
  • <callable-name> is the callable's __name__; a lambda is consequently rendered as <lambda>.
  • <parameter-name-list> is the Python list representation of all parameter names in declaration order, with [] included when no parameters are present.

Examples:

connection_string = <lambda>([])
database_context = create_database(['connection_string'])
Message = Message(['database_context', 'message_service', 'text'])

When dependencies are recursive, their invocation messages are emitted before the callable that depends on them.

Entering and exiting context managers

Emit the following immediately before a context-managed result is entered:

<resolved-name>.__enter__()

Emit the following during its teardown:

<resolved-name>.__exit__()

Entry messages come in construction order. Exit messages happen after the caller's build block and in reverse resource-construction order. Hence dependency invocation and entry messages follow parameter declaration order, whereas the corresponding exit messages follow the reverse order.

Module: junkie.context

Class: Context

Context offers the higher-level convenience interface on top of the same registry, resolution, and lifecycle behavior.

Construction

Construct it using zero or more mapping arguments:

Context()
Context(mapping)
Context(mapping1, mapping2, ...)

Every argument is a dictionary from string names to values. Mappings given to the constructor are equivalent to constructing an empty Context and immediately calling add with those mappings in the same order. Subsequent calls to add keep accumulating registrations.

add(self, *mappings: dict)

This method accepts one or more dictionary arguments in a single call. All mappings are processed and combined in argument order. Multiple calls accumulate registrations.

Every mapped value is classified automatically:

  • A value that is not callable is registered as a pre-built instance.
  • A value that is callable — a function, lambda, or class included — is registered as a factory.
  • The key "class" is reserved and designates the context's primary class factory. Registering {"class": SomeClass} makes it possible to resolve that class under the string name "class".

When a later mapping targets a name that already has a registered instance or factory, that registration is updated for subsequent builds. For example, mappings can override configuration while retaining other names:

context = Context({
    "prefix": "abc",
    "suffix": "def",
    "text": lambda prefix, suffix: prefix + suffix,
})
context.add({"class": Message}, {"suffix": "xyz"})

Builds that come afterwards use suffix == "xyz".

build(self, target) — context manager

All of the following forms are accepted for target:

  • Set of string names: the requested values are resolved and a dictionary containing only those names is yielded.
  • List of string names: the same kind of dictionary is yielded, but names are resolved in list order and that order is preserved in the result.
  • String name: one registered instance or factory is resolved and its single value is yielded. In particular, build("class") constructs the class factory registered under "class".
  • Class/type: that class is constructed directly, its constructor parameters are resolved by name, and its instance is yielded. The target class need not be looked up through the "class" registration.

Every form applies the same transitive resolution, parameter and list ordering, context-manager lifecycle, reverse teardown, and logging rules as CoreContext.

Using the registrations from above:

with context.build({"text", "prefix"}) as values:
    assert values == {"text": "abcxyz", "prefix": "abc"}

with context.build(["text", "prefix"]) as values:
    assert values == {"text": "abcxyz", "prefix": "abc"}

with context.build("class") as message:
    assert message.text == "abcxyz"

with context.build(Message) as message:
    assert message.text == "abcxyz"

Class builds performed directly must work for ordinary classes as well as for classes decorated with @dataclass; the constructor fields a dataclass generates are resolved by field/parameter name in the same way.

Notes on compatibility and scope

  • Dependency resolution is not constrained by registration order: dependencies may be registered before or after the factories that consume them.
  • When a list is supplied, the request order is meaningful. Parameter declaration order is always meaningful for dependency construction and for lifecycle side effects.
  • During injection, shared registered instances must not be copied.
  • Annotation-based matching is not required; the dependency keys are the registration and parameter names.
  • Context is available from junkie.context and is additionally exposed by the junkie package for from junkie import Context.

Overview

In this task you implement a lightweight dependency injection library called junkie. To resolve and construct instances, the library inspects the parameters (constructor arguments or function arguments) of the requested types/callables, looks each parameter up by name in a registry of named instances, and injects them.

The primary change this task calls for is: when parameters with default values exist on a callable being constructed, and those parameters are not present in the registry, the default values must be used instead of raising an error.

Resolution Rules

While an instance of a type/callable is being constructed, its parameters are inspected (for a class, the __init__ parameters excluding self). For each parameter, a value is resolved as follows:

  1. Registry lookup by name. When a registered instance exists under the parameter's name, use it.
    • When the registered value is a callable/factory, invoke it (recursively resolving its parameters by name from the registry) to produce the value.
  2. Default values. If a parameter is not present in the registry and declares a default value, use that default value.
  3. Parameters found in the registry always take precedence over their declared default value.

Behavior examples:

  • When a class with __init__(self, argument: str, default_argument: int = 10, default_argument2: str = None) is constructed against a registry containing only {"argument": "value"}, it must produce an instance where argument == "value", default_argument == 10, and default_argument2 == None.

String Concatenation Injection Example (pre-existing behavior to preserve)

  • After registering {"prefix": "abc", "suffix": "def"}, building a class whose __init__(self, prefix, suffix) sets self.text = prefix + suffix must yield an instance with text == "abcdef".
  • Repeated builds of the same class yield distinct instances.
  • This resolution must also work for classes constructed through the @dataclass decorator (Python 3.7+), with the injected values populating the dataclass fields and __post_init__ running normally. For example, a dataclass having fields prefix: str and suffix: str plus a __post_init__ that sets self.text = self.prefix + self.suffix, built from {"prefix": "abc", "suffix": "def"}, yields text == "abcdef".

Factory Resolution & Context-Managed Dependencies (pre-existing behavior to preserve)

Factory callables keyed by name may be held in the registry. Whenever a needed value is produced by such a factory, that factory's own parameters are resolved by name from the registry (recursively).

For constructed/produced dependencies that are context managers, __enter__ must be called when they are brought into scope and __exit__ must be called when the enclosing build's context manager exits. The exit ordering is the reverse of the enter ordering.

  • When a constructed type gets instantiated: <TypeName> = <TypeName>(<sorted list of resolved parameter names>)

In the = factory(...) and = Type(...) messages, the parameter-name lists shown are the names of the parameters that were resolved, rendered as a list (sorted alphabetically).

Compatibility

Inside a context, instances and factories are stored under names; the parameters of a factory are resolved by name; and any resources that a build creates stay alive for as long as the returned context manager lasts.

The existing Context convenience API, together with the other CoreContext build APIs, must keep behaving as set out below.

Imports and version compatibility

from junkie.core_context import CoreContext

from junkie import Context

The package's compatibility with Python 3.5 and newer is to be preserved. On Python versions that provide dataclasses, dataclass constructors must behave the way other class constructors do.

CoreContext

Creating an instance
context = CoreContext()

A context that has just been created holds no registered instances and no registered factories.

Registering entries
add_instances(mapping)

The method accepts a dictionary that maps string names to values that have already been constructed, and it registers every entry the dictionary contains. A call made later either updates existing entries or adds new ones.

add_factories(mapping)

This method accepts a dictionary that maps string names to callables, and again every entry it contains gets registered. The callable may take the form of a function, a class, a zero-argument callable, or a callable with named parameters. As above, later calls either update or add entries.

When a name is present in both the instance registrations and the factory registrations, resolving that name gives the registered instance precedence.

Resolving dependencies

The parameter name is what drives resolution:

  1. When a name is registered as an instance, the value that was stored is used exactly as it is.
  2. Failing that, when the name is registered as a factory, that factory gets invoked and its result is what gets used.
  3. Every parameter declared on a factory or constructor has a dependency resolved under the same name, which is then supplied as a keyword argument.
  4. Parameters are handled in the order in which they were declared. Before a callable is invoked, its factory dependencies have been resolved recursively. As a consequence, the order in which factories are invoked must be a valid dependency/topological order, even when the requested names arrived in some other order.
  5. When a parameter carries a default and no dependency is registered under that name, the keyword is omitted, so the callable applies its own default. When a dependency is registered for an optional parameter, it is injected, and the default gets overridden. A required dependency that is missing fails the same way any other missing name does.

When a requested name or a required dependency is missing, Exception must be raised, carrying the message:

Not found: <name>

No conversion of factory results into registered instances happens. Separate resolutions can therefore construct separate values; notably, resolving the same factory-backed name two times via the tuple API produces two distinct factory results.

  2. Should the name be absent, raise an Exception that carries exactly the message Not found: <name> (e.g. Not found: instance_name).
  3. Should the mapped object be not callable, that object itself is the resolved instance (used directly).
  4. Should the mapped object be callable, treat it as a factory and call it (see "Calling a factory"); whatever the call produces is the resolved instance.

Overview

The task is to provide a lightweight dependency injection container inside a Python package named junkie. The container is handed a mapping from names to values and resolves classes and other factories by lining their parameters up with the mapping's keys. Resolution is name-based and recursive.

Public Interface

It must be possible to import the Junkie class directly from the package:

from junkie import Junkie
Constructor
Junkie(mapping=None)
  • mapping is an optional dictionary; its string keys serve as the dependency names.
  • A value held in the mapping may be:
    • a plain value, including a string, collection, arbitrary object, or None; or
    • a callable, including a function, lambda, class, or generator factory.
  • A mapped value that is callable is always interpreted as a factory. A mapped value that is not callable is returned directly.
  • When mapping is omitted, the container is created with an empty mapping.
  • It is the presence of a key, not its truthiness, that decides whether a dependency exists. Notably, a mapped value of None is valid and must be injected as None.
inject
Junkie.inject(*targets)

The value inject returns is a context manager. Resolution happens at the moment that context is entered, and resources acquired while the requested object graph is being resolved stay active for as long as the context lasts.

Each target may be:

  • a string that names a dependency;
  • a type/class, which then serves as a factory; or
  • another callable, which then serves as a factory.

What the context manager yields is:

  • the single resolved value, when exactly one target is supplied;
  • a tuple of the resolved values, in the order of the targets, when two or more targets are supplied; or
  • an empty tuple, when no targets are supplied.

When multiple targets are passed, they must be resolved from left to right. So both the order in which they are constructed and their positions in the returned tuple match the order that was passed to inject.

Resolution Rules

Resolving a String Name

When the requested name is a string:

  1. Search the mapping for that exact name.
  2. If the key exists and its value is callable, that callable is resolved and invoked as a factory.
  3. If the key exists and its value is not callable, the mapped value is used directly.
  4. If the key does not exist, the missing-name error defined below is raised.

The same rules apply recursively whenever the dependencies of a factory or constructor are resolved.

Resolving Factories and Classes

A class passed directly to inject, any other callable target, and any callable obtained from the mapping are factories.

Walk through the factory's declared parameters in signature order. Each ordinary parameter is tied to a dependency by way of the parameter's name:

  1. If the mapping contains that name, the mapped value is resolved recursively. That mapped value overrides any declared default, even when it is None.
  2. Otherwise, if the parameter declares a default, that default value is used.
  3. Otherwise, the missing-name error is raised for the parameter name.

Once all parameters have been resolved, invoke the factory, passing each ordinary value for its declared parameter name together with any variadic expansions described below. Parameter annotations have no effect on this name-based lookup rule. Classes whose constructors are generated, such as dataclasses, must therefore work in the same way as other classes.

For example, given:

def make_message(prefix, suffix="!"):
    return prefix + suffix

{"prefix": "Hello"} uses the declared "!" suffix, while {"prefix": "Hello", "suffix": "?"} uses the override supplied by the mapping.

Variadic Parameters

Variadic parameters are likewise tied to mapping entries by their declared parameter names:

  • With a *args parameter, resolve the mapping entry of the same name and unpack the iterable it produces as positional arguments. Tuple and list values are supported, as are iterable values that a factory produces. When the name is absent, an empty tuple is used, so the factory receives no additional positional arguments.
  • With a **kwargs parameter, resolve the mapping entry of the same name and unpack the dictionary it produces as keyword arguments. The dictionary may be stored directly, or it may be produced by a factory. When the name is absent, an empty dictionary is used, so the factory receives no additional keyword arguments.

For example:

class Collector:
    def __init__(self, *items):
        self.items = items

with Junkie({"items": [1, 2, 3]}).inject(Collector) as collector:
    assert collector.items == (1, 2, 3)

A callable mapped under "items" that returns (1, 2, 3) gives the same result.

Managed Results from Factories

Generator Factories

A generator factory is managed in the manner of a context:

  • When it is resolved, advance it to its first yield.
  • The yielded value serves as the resolved dependency.
  • When the surrounding inject context exits, the generator is resumed or closed so that its teardown logic can run.
Objects that Implement the Context-Manager Protocol

If a factory of any kind — a class constructor included — returns an object that implements __enter__ and __exit__, that object is managed for the lifetime of the surrounding inject context:

  • __enter__ is called immediately after the object has been constructed;
  • what gets injected is the value __enter__ returns, which is not required to be the context-manager object itself; and
  • __exit__ is called when the inject context exits.

This holds for ordinary context-manager objects and equally for context managers that generator-based factories produce. Plain objects that are not callable and are stored directly in the mapping remain plain values under the normal name-resolution rules.

All managed results created while one injection context is being resolved must be torn down in the reverse of their construction order: the managed result that was constructed most recently exits first. Cleanup must happen when the injection context is left, including when an exception is the reason control leaves it. The standard context-manager exception details are passed through to __exit__.

To illustrate: if resolving an application enters a connection first and then a session, leaving the injection context exits the session before the connection.
