Task: Module for Loading Configuration

Goal

Build a configuration module at n26/config.py that obtains N26 API credentials from either environment variables or a YAML configuration file, and exposes them via a structured configuration object.

Public Interface

The Config class

A container object for configuration data with three fields: username, password, and card_id.

The following requirements apply:

  • It must be possible to construct it with keyword arguments: Config(username=..., password=..., card_id=...).
  • When two Config instances are constructed with the same username, password, and card_id values, they must compare as equal (==).
The get_config() function

Signature: get_config() (takes no arguments).

It returns a Config instance populated with credentials according to the following resolution logic:

  1. Environment variables (highest priority): The credentials are read from these environment variables:

    • N26_USER → username
    • N26_PASSWORD → password
    • N26_CARD_ID → card_id

    If these environment variables are present and non-empty, their values are used to build and return the Config.

  2. Fallback to a YAML file: If the environment variables are absent or empty, the credentials are loaded from a YAML configuration file located at a path obtained by calling os.path.expanduser(...). (The path given to expanduser must be such that its return value determines the file that is opened; the resolved path is the file that gets read.)

    The YAML file has the following structure:

    n26:
    username: john.doe@example.com
    password: $upersecret
    card_id: "123456789"

    Pull username, password, and card_id out from beneath the top-level n26 key, and construct the returned Config from them.

Detailed Behavior

  • If all three environment variables (N26_USER, N26_PASSWORD, N26_CARD_ID) are set to non-empty values, get_config() returns a Config holding those values, and the YAML file is not consulted.
  • If those environment variables are empty strings, get_config() falls back to the YAML file (reading it via the os.path.expanduser-resolved path) and returns a Config built from the file's n26 section.
  • card_id values are handled as strings (e.g. "123456789").

Additional Notes

  • It must be possible to import the module as from n26 import config.
  • Ensure that the package's dependencies include support for YAML parsing.

The package must provide a class Config that stands for user credentials. It must be possible to construct it with the keyword arguments:

Config(username=..., password=...)

  • Two Config instances built from username and password values that are equal must compare equal (==). Instances whose values differ must not compare equal.
  • A mandatory card_id must NOT be required or accepted by the Config object; equality is based on username and password only.
The get_config() function

A function get_config() must exist that returns a Config instance assembled from one of two sources, in the following priority order:

  1. Environment variables. If both of the environment variables N26_USER and N26_PASSWORD are set to non-empty values, return a Config whose username is taken from N26_USER and whose password is taken from N26_PASSWORD.

  2. Configuration file. If those environment variables are absent or empty, read the credentials from a YAML file. The file's path is derived from the user's home directory; the resolution goes through os.path.expanduser. The YAML file uses this structure:

    n26:
  username: john.doe@example.com

get_config() must not rely on any card_id value from either source.

The n26.api module

This module must have requests (used for the HTTP calls via requests.post and requests.get) and config (the n26.config module) as accessible module-level names, so that n26.api.requests and n26.api.config resolve.

The Api class

The module must contain a class Api with this constructor:

Api(config=None)
  • If the call includes an explicit Config argument, the instance must store it and expose it as the config attribute (that is, api_instance.config equals the config passed in).

N26 API Client and CLI: Task Specification

In this task, a Python package called n26 is to be implemented; it provides a programmatic client plus a command-line interface (CLI) for talking to the N26 bank REST API. Its code is organized into three modules: n26.api, n26.config, and n26.cli. Everything described below as public must exist under exactly that name, so it can be imported and called.

The n26.config module

Constants defined at module level
  • ENV_PARAM_USER — a string constant that names the environment variable holding the username.
  • ENV_PARAM_PASSWORD — a string constant that names the environment variable holding the password.
  • CONFIG_FILE_PATH — a module-level attribute (a filesystem path string) that gives the location of the credentials file. The value it holds must be reassignable at runtime, and whatever it currently contains is what get_config() must read.
The Config class

Its constructor takes the keyword arguments username and password:

config.Config(username='...', password='...')
  • It exposes .username and .password for reading, and they return the values passed in.
  • Value-based equality must be implemented: two instances of Config must compare equal (==) when and only when their username and password are equal.
The function get_config() -> Config

This function resolves the credentials and returns a Config:

  1. If the environment variables named by ENV_PARAM_USER and ENV_PARAM_PASSWORD are both present and non-empty, the function must return a Config built from those environment values.
  2. Otherwise, the YAML file at the current value of config.CONFIG_FILE_PATH is read and its contents are used to build a Config. The username and password credentials are found in that file.

An environment variable whose value is the empty string must be treated as "not set"; resolution then falls through to the file.

The n26.api module

Constants defined at module level
  • BASE_URL — a string whose value is "https://api.tech26.de".
  • GET — a string whose value is "get".
  • POST — a string whose value is "post".

The strings themselves are significant: GET/POST are used both for selecting the behavior and for constructing the attribute name of the underlying HTTP function (i.e. requests.get / requests.post are referenced via requests.{GET} / requests.{POST}). Within this module, HTTP calls must be made through n26.api.requests.get(...) and n26.api.requests.post(...); that is, the module must import requests and reference it as requests.get / requests.post. The first positional argument passed to those calls must be the URL.

The Api class

The signature of the constructor is:

Api(config=None)
  • If an explicit Config is passed to the constructor, the instance stores it and exposes it as its .config attribute; that attribute is equal to the object that was passed.
  • If the constructor is called with no argument (Api()), the instance obtains its configuration by calling n26.config.get_config() and exposes the result as .config — and this must not be None.
The method _create_request_url(base_url, params) -> str

A URL is built by this method through appending the given query parameters to base_url. For the input:

_create_request_url(BASE_URL, {"foo": "bar", "bar": "baz"})

the method must return exactly:

https://api.tech26.de?foo=bar&bar=baz

Parameters are appended in insertion order; each one is rendered as key=value, the pairs are separated with &, and everything is joined to the base URL behind a single ?.

Handling of authentication tokens
  • _request_token(...) — issues the raw HTTP request through which an authentication token is obtained from the API, and it returns the parsed JSON response (a dict). Token acquisition happens through this single low-level method; token logic at a higher level must route through it.
  • get_token() — returns the current access token as a string. The token data must ultimately be obtained via _request_token(...), and what it returns is the value of the access_token field from that response.
  • _refresh_token(refresh_token) — its job is refreshing the access token. It sends a POST request to a URL ending in /token and returns the parsed JSON response dict, from which callers read access_token. The refresh token value is what it accepts as its argument.

Suppose the token response contains "access_token": "12345678-1234-1234-1234-123456789012"; then get_token() returns that string. Suppose the refresh response contains "access_token": "12345678-1234-abcd-abcd-1234567890ab"; then _refresh_token(...)["access_token"] is equal to that string.

Dispatching requests and error behaviour

An HTTP method value (GET or POST) decides how a request is dispatched. When a request is attempted with any method other than the supported ones, an error must be raised (rather than None being silently returned).

Methods for retrieving data

An authenticated GET request is performed by each method listed below, which then returns the parsed JSON response (a dict or list matching the JSON payload). None of them has required arguments (each one must work when called with none):

  • get_account_info() → a dict holding the account info. If the payload contains "email": "john.doe@example.com", then result["email"] equals "john.doe@example.com".
  • get_account_statuses() → the account status dict.
  • get_account_limits() → a list of limit entries; each entry carries a limit name (e.g. "POS_DAILY_ACCOUNT", "ATM_DAILY_ACCOUNT") together with an amount.
  • get_addresses() → the addresses response (a dict containing paging and data).
  • get_contacts() → a list of contact entries (each having name, subtitle, account).
  • get_statements() → a list of statement entries (each having id, url, visibleTS, month, year).
  • get_balance() → the balance dict (it has fields such as availableBalance, currency, etc.).
  • get_spaces() → the spaces dict (it contains totalBalance, a spaces list, etc.).
  • get_statistics() → the statistics dict.
  • get_cards() → a list of card entries (each having id, maskedPan, status, etc.).
  • get_transactions() → a list of transaction entries; calling it with no arguments must work.

When the API responds with the corresponding JSON, a non-None value is what all of these must return.

Blocking and unblocking cards

Blocking and unblocking a card by its card id, via POST requests, must be supported by the client. These operations are what the CLI card commands described below rest on (blocking/unblocking a single specified card, and enumerating all cards via get_cards() to operate on each).

The n26.cli module

The click framework is used for this module. Each item below is a click command object (it can be invoked via click.testing.CliRunner().invoke(command, args=...)). The commands write their output to stdout. Each command builds an Api client, taking that client's configuration from n26.config.get_config().

  • info — prints the account information. The output is non-empty.
  • limits — prints the account limits. Each limit name (POS_DAILY_ACCOUNT, ATM_DAILY_ACCOUNT) must be contained in the output, as must the amount value (2500).
  • contacts — prints the contact list. Each contact's identifying name text (e.g. ADAC, Cyberport, DB, ELV, Mindfactory, Seegel) must appear in the output.
  • statements — prints the statement list. The statement period identifiers (e.g. 2016-11, 2017-01, 2018-01, 2019-01), the statement URL (e.g. /api/statements/statement-2019-04), and the raw visibleTS value (e.g. 1554076800000) must all be contained in the output.
  • balance — prints the balance. The regular expression \d*\.\d* \w*.* must be matched by the output; that is, a decimal number followed by a space and a word, such as an amount followed by a currency.
  • spaces — prints the spaces. The output must match \d*\.\d* \w*.*, i.e. a decimal amount followed by a space and a word.
  • statistics — prints the statistics. The output is non-empty.
  • transactions — prints the transactions. Invoking it with no arguments must be possible, and its output must be non-empty. Entries of the transaction response are heterogeneous: descriptive fields such as merchantName and referenceText are optional, and card/ATM entries may have neither of them. Entries that lack one or both of these fields must be rendered by the command without an error being raised. Whichever supported descriptive value is available must be used; when neither is present, a fallback detail label (for example, no details available) must be rendered so that the entry is handled and the command's execution completes normally. No exact wording is prescribed for the fallback label.
  • card_block — blocks one or more cards. An optional --card <card_id> option is accepted.
    • Given --card <id>: that single card is blocked, and the output is exactly Blocked card: <id>\n.
    • Given no --card: all cards are retrieved (via get_cards()) and each is blocked in the order in which they are returned; one line Blocked card: <id>\n is printed per card. For two cards with ids A then B, the complete output is Blocked card: A\nBlocked card: B\n.
  • card_unblock — unblocks one or more cards; the option and behavior match card_block, except that the word is Unblocked:
    • Given --card <id>: the output is exactly Unblocked card: <id>\n.
    • Given no --card: one line per card is printed, each reading Unblocked card: <id>\n, in enumeration order.

For the single-card case, a concrete id example is 12345678-1234-abcd-abcd-1234567890ab; in the two-card enumeration example, the ordering is 12345678-1234-abcd-abcd-1234567890ab followed by 22345678-1234-abcd-abcd-1234567890ab.

Package-wide requirements

  • These imports must be possible with the package layout: from n26 import api, config, from n26.api import BASE_URL, GET, POST, from n26.config import ENV_PARAM_USER, ENV_PARAM_PASSWORD, and from n26.cli import <command>.
  • All authenticated data methods obtain their token through Api._request_token(...) — directly or indirectly — which keeps token acquisition centralized in that single method.
  • Via n26.api.requests.get / n26.api.requests.post is how HTTP GET and POST must be performed; the target URL is passed as the first positional argument, and the JSON body of the response must be obtained through the response object's .json() method.

Notes about the response data shapes

  • Balance — the JSON here is one object that has numeric balance fields and a currency string ("EUR"). In the output of the balance CLI command, a decimal amount is paired with the currency word.
  • Spaces — the JSON contains totalBalance (a number), a spaces array (each entry has a name and a nested balance object that holds availableBalance and currency), and userFeatures. A decimal amount followed by a currency/word appears in the spaces CLI output.
  • Account limits — the JSON is an array whose objects each have a limit (string) and an amount (number).
  • Contacts — the JSON is an array whose objects each carry name, subtitle, and a nested account object.
  • Statements — the JSON is an array whose objects each have id, url, visibleTS (an integer), month, year.
  • Cards — the JSON is an array of card objects, each of which has an id.
  • Account info — the JSON is one object that includes an email field.
  • Transactions — the JSON is an array of objects that carry an amount plus other transaction metadata. The descriptive keys differ between transaction types: merchantName and referenceText may each be absent, and some card/ATM transactions leave out both. Consumers — in particular the transactions CLI formatter — must not treat either descriptive key as mandatory.

In the limits output, the amount 2500.00 must appear, such that the substring 2500 is present.

What gets returned must be the deserialized JSON structures (Python dict/list), not raw strings.

Task overview

The subject of this task is an N26 banking API client. Publicly exposed constants and class

  • GET, holding exactly the lowercase string "get" as its value.
  • POST, holding exactly the lowercase string "post" as its value.
  • Api, the class for the API client.

GET and POST are lowercase dispatch identifiers: they designate the supported requests.get and requests.post call points. They must not be turned into uppercase HTTP-method spellings.

Api._create_request_url(self, url, params=None)

This method assembles a request URL from a base URL plus optional query parameters.

  • url is a string containing a URL, such as BASE_URL.
  • params is an optional dictionary that maps parameter names to values.
  • Query parameters that are included must be ordered alphabetically by key, regardless of the dictionary's insertion order.
  • Parameters are serialized as key=value; entries are joined by &, and the query string is introduced by ?.
  • The established handling of optional parameters must be preserved: entries with falsy values are omitted. If params is absent, empty, or has no included entries, url must be returned unchanged and ? must not be appended.

As an example:

Api._create_request_url(
    "https://api.tech26.de",
    {"foo": "bar", "bar": "baz"},
)

the method must return exactly:

https://api.tech26.de?bar=baz&foo=bar
Api._do_request(self, method, endpoint, params=None)

This method carries out an authenticated HTTP request and returns the JSON response after decoding.

  • method is one of the exported method identifiers, usually GET or POST.
  • endpoint identifies the target path; requests to endpoint paths are made against BASE_URL.
  • Optional params are appended by way of _create_request_url.
  • Retrieval of the authentication token is part of the normal request flow.
  • GET requests are dispatched through requests.get, and POST requests through requests.post.
  • The HTTP response must be checked for unsuccessful status codes; a successful response, in turn, must be returned as parsed JSON rather than as the raw response object.
  • Method identifiers that are unsupported must be rejected rather than silently dispatched.

As an example, _do_request(GET, "/something") must perform the request and return a non-None result derived from its response.

Api.__init__(self, config=None)

  • With Api(conf), the exact object supplied by the caller must be exposed as api_client.config; the constructor must not replace it with a separately loaded configuration.
  • Each new client begins with no cached authentication-token data.
Authentication token behavior

For authenticated requests, Api.get_token() must provide an access token. The token that is returned is a UUID-form string, for example "12345678-1234-1234-1234-123456789012". These behaviors must be retained by the authentication flow:

  • A cached access token that is valid is reused.
  • If no token has been obtained yet, credentials from self.config are used to request one.
  • If cached token data has expired and holds a refresh token, that refresh token is used to obtain replacement token data.
  • Token and refresh responses are decoded mappings, and token retrieval returns the access_token value from them.
  • If valid token data still cannot be obtained, authentication fails rather than an invalid token being returned.

  • get_config(), which returns a validated Config.

Configuration loading and its precedence

For automatic configuration, environment variables and YAML files are supported:

  1. Take the username and password from N26_USER and N26_PASSWORD.

  2. If either value is missing, read the file picked by CONFIG_FILE_PATH and fill in only the value or values that are missing. Environment values therefore take precedence, while partial environment configuration may be merged with configuration from the file.

  3. The YAML file has an n26 mapping with username and password fields, for example:

    n26:
  username: john.doe@example.com
  password: $upersecret

  4. Return a Config built from the resolved values. Both username and password are required. Missing credentials, an empty configuration file, or a file lacking the required n26 section must produce a clear configuration error rather than an unusable client configuration.

As a consequence, constructing Api() without an explicit configuration must produce a non-None Config out of these configured sources; when environment credentials are not supplied, the file at the current CONFIG_FILE_PATH is the source that supplies the values.

Data methods of the public API

The instance methods listed next must be provided by the Api class. Each one performs its corresponding authenticated API request and returns the parsed response data, which is non-None:

  • get_account_info(self) — account information; the mapping that is returned includes an "email" key, for example "john.doe@example.com".

Behavior of the command line

The corresponding API data must be presented by the command-line interface as non-empty, human-readable output. Specifically:

  • Account information is rendered with account fields that are recognizable.
  • Amounts and currencies are included in balances and spaces.
  • Limits, contacts, and statements are rendered as readable listings that contain the names, identifiers, dates, amounts, and other text present in the API response.
  • Statistics and transactions are rendered as readable summaries or tables that are derived from their response data.
  • The card block and unblock commands accept an optional card identifier. When an identifier is supplied, the operation applies to that card; when none is, it applies to every card returned by the account. Within the n26 package, you must add a new optional configuration option and expose a token-refresh method on the API client.

Required Changes

1. Config class — new login_data_store_path option

Module: n26.config Class: Config

In addition to the arguments it already takes, the constructor of the Config class must accept the keyword argument login_data_store_path. Given how it is currently used, the constructor must support at least the following signature:

Config(username=..., password=..., login_data_store_path=...)

Requirements:

  • The argument login_data_store_path must be accepted as a keyword argument.
  • It must accept None as a value.
  • If two Config instances are constructed with the same values for username, password, and login_data_store_path, they must compare equal to each other (==).

The existing username and password arguments must continue to be accepted, and must behave as they did before.

2. Config loading — login_data_store_path set to None when not specified

Module: n26.config Function: get_config()

If login_data_store_path is not provided by the source when the configuration is loaded (from a configuration file or from environment variables), the Config object that results must have login_data_store_path set to None. To put it another way, loading a source that omits this option must produce a Config that equals a Config constructed explicitly with login_data_store_path=None (and the same username/password).

3. Api client — accepting Config, including the new option

Module: n26.api Class: Api

The constructor of Api must accept a Config instance as its argument — including an instance built with login_data_store_path=None. The client that gets created must expose the supplied config via a config attribute that:

  • is equal (==) to the Config instance that was passed in.

Detailed behavior: when the method is given a refresh token value, it performs the token request and returns a dict in which result['access_token'] holds the returned access token string.

Task Specification: Human-Readable Datetimes as Input for CLI Date Parameters

Summary

Within the n26 package, modify the transactions CLI command so that its --from and --to parameters accept human-readable datetime strings instead of numeric (Unix) timestamps.

Public API

The CLI command resides at:

  • Module: n26.cli
  • Command object: transactions

It is a callable CLI command (a Click-style command), and it must be importable as:

from n26.cli import transactions

Behavior Requirements

Options on the command line

The transactions command must accept the following optional command-line options; each of them may be supplied independently of the other (either, both, or neither may be present):

  • --from — a string containing a datetime.
  • --to — a string containing a datetime.
Parsing of the datetime strings

The values passed to --from and --to must be parsed out of human-readable datetime strings. The parsing must support (at minimum) the following formats, attempting each one until one of them succeeds:

  • %m/%d/%Y %H:%M:%S
  • %m/%d/%Y
  • %Y-%m-%d
  • %Y-%m-%dT%H:%M:%S
  • %Y-%m-%d %H:%M:%S
  • %d.%m.%Y
  • %d.%m.%Y %H:%M:%S

As a concrete case, invoking the command with --from set to 01/30/2019 (which matches the %m/%d/%Y format) and --to set to 30.01.2020 (which matches the %d.%m.%Y format) must succeed and produce output.

Output

The command must produce non-empty output when it runs successfully. Invoked with the --from and --to options as described above, the command must complete without error.

Notes and Constraints

  • When both --from and --to are supplied as human-readable datetime strings in any of the supported formats, the command must run end-to-end (retrieving and rendering transaction data) and produce output.
  • Beyond parsing these two datetime options and producing non-empty output, no behavior is required to be verified by this task.

Logging

Logging in the package must be organized under a logger named n26 (i.e., logging.getLogger("n26")), so that log output produced by the package is emitted through that logger hierarchy.
