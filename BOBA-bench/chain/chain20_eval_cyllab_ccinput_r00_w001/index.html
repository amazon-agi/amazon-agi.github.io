Objective

Adjust the command-line argument parsing in the ccinput package so that, when a user supplies an input structure file but does not explicitly specify a calculation name, the name defaults to the base name of the input file (its file name stripped of the directory path and of the extension).

Required Behavior

The parser for CLI arguments exposes an option used to name the calculation (the name argument). As things stand, omitting this option from the command line leaves name unset (or None).

The new behavior: once the command-line arguments have been parsed, if the user gave no explicit name, the name value must be derived automatically from the structure file path that was provided (the file argument). Concretely:

  • Start from the structure file path.
  • Strip away the directory components, leaving only the file name.
  • Remove the file extension.
  • Take the resulting stem as the name.

By way of example, if the structure file path ends in ethanol.xyz (no matter which directory it resides in), the resulting name must be "ethanol".

This default holds uniformly no matter the calculation type (e.g. single-point, constrained optimization) or the target software package (e.g. Gaussian, ORCA), and it applies independently of any other options such as basis set, processor count, memory, or geometry constraints.

When a name is explicitly supplied by the user on the command line, that explicitly given value must be preserved and must not be overridden by the default derived from the file.

API Surface

The object of parsed arguments (the one produced by the existing CLI parsing entry point in the ccinput command-line module) must contain a name attribute/field. When a command line that includes a structure file through the file option (-f/--file) but leaves out the name option has been parsed, the name field must equal the file's stem as described above.

The existing structure of the parsed arguments — including fields such as software, type, method, basis_set, file, nproc, mem, and constraints — must stay unchanged. The only change is the automatic population of the name field in cases where it is not otherwise given.

Task Description

Summary

ccinput is the library this task centers on: a Python library that builds input files for computational chemistry packages (examples are Gaussian and ORCA) out of one unified set of parameters. Two behavioral changes are required here: (1) support for the new calculation type "TDA" in Gaussian, and (2) a fix for the spurious warnings emitted for certain functional names while methods are being parsed.

Change 1: Gaussian Calculations of Type TDA (Tamm–Dancoff Approximation)

The string "TDA" (matched case-insensitively) must name a calculation type that is recognized, and that calculation type must produce input that is valid for Gaussian.

Whenever a Gaussian calculation is requested with type TDA, the keyword tda must take the place of the calculation-type keyword on the route/keyword line of the generated input, with the method and basis set following it.

Behavior when no extra specifications are given

Suppose the parameters are equivalent to the following:

  • processor count: 8
  • memory: 10000MB
  • type: TDA
  • method: M06-2X
  • basis set: Def2-SVP
  • charge: -1
  • a structure consisting of a single atom (Cl at origin)

The Gaussian input that the library produces must be equivalent to the following:

%chk=calc.chk
%nproc=8
%mem=10000MB
#p tda M062X/Def2SVP

File created by ccinput

-1 1
Cl 0.0 0.0 0.0
Behavior when extra specifications are supplied

Whenever a specifications string carrying TDA options is supplied (tda(nstates=2,root=1) serves as an example), those options must be merged into the route line's tda keyword. The options, in normalized form, must be shown on the keyword line with a space after every comma, e.g.:

#p tda(nstates=2, root=1) M062X/Def2SVP

Everything else in the input file is identical to the no-specifications case. Expressed differently: once the user supplies tda(...) specifications, tda(<options>) is what the route line carries instead of a bare tda, the separator between options being , (comma followed by a single space).

Change 2: TPSS-family Functionals Parsed without Spurious Warnings

The emission of a warning should not accompany the parsing of certain functional names of the "custom" exchange+correlation (X+C) kind. To be specific, parsing any one of the method names listed just below must complete without any warning being generated:

  • utpsstpss
  • rtpsstpss
  • tpsstpss

These names are functional names that are both valid and recognized (they combine the tpss exchange functional with the tpss correlation functional, and they carry an optional prefix: the spin-treatment indicator u or r). Parsing them must succeed silently, and so must generating input for them. The warning mechanism in question here is warn, a callable in the ccinput.utilities module; when these inputs are involved, it must not be invoked.

A representative example of a valid command line that must parse without warnings: a single-point Gaussian calculation using one of these methods, with basis set cc-pvdz, on a single Cl atom at charge -1.

Public API

Every import path and callable in the list below must remain available, exhibiting the behavior described:

  • ccinput.calculation.Calculation
  • ccinput.calculation.Parameters
  • ccinput.wrapper.gen_input(**kwargs) — from the keyword parameters passed in (including software, type, method, basis_set, charge, nproc, mem, specifications, and structure/file inputs), this function generates an input-file string and returns it.
  • ccinput.wrapper.get_input_from_args(args) — what it returns is a tuple (objs, outputs), in which objs is a list of calculation objects (an input_file attribute holding the generated input string is exposed by each) and outputs is a list of output path strings.
  • ccinput.wrapper.get_parser() — the value returned is an argument parser, and it accepts the command-line syntax used above (e.g. gaussian sp <method> -bs <basis> --xyz "<atom coords>" -c <charge>, and orca sp HF -bs Def2SVP -f <files...> [-o <output>] [-n <nproc>] [--mem <mem>] [--name <name>]).
  • ccinput.utilities.warn — this callable exists to emit warnings; while the TPSS-family functional names above are being parsed, it must not be called.

The calculation parameters take type values in a case-insensitive manner; TDA is a valid type and must be accepted.

Additional Notes

Where multiple/single file handling, output naming, and equivalence of generated inputs are concerned, the existing CLI behavior must stay unchanged; the TDA type and the parsing of TPSS-family functionals are changes of an additive/corrective nature, and they must not cause existing functionality to regress.

Goal

The task is to ensure that basis set names users provide are normalized so that common synonym variations map to the same canonical basis set. In particular, when a basis set name is interpreted, dash symbols (-) and parentheses (( and )) must be stripped/ignored, so that a name supplied by a user and written without these characters resolves to the correct known basis set.

Background

The codebase offers a command-line interface for producing computational chemistry input files. The CLI is exposed via the following functions (these are already present in the codebase — you must ensure they keep working as described):

  • get_parser() — returns an argparse-style parser that accepts the CLI's arguments.
  • get_input_from_args(args) — accepts the object holding the parsed arguments and returns a tuple (objs, outputs).

Required Behavior

When a basis set is supplied through the -bs / basis set argument, the value must be recognized even when it is written in a form that leaves out dashes and parentheses that appear in the canonical/registered name.

In concrete terms, the following invocation must succeed end-to-end (the arguments are parsed and the corresponding input is generated without raising an error):

Gaussian sp tpsstpss -bs ccpvdz --xyz "Cl 0 0 0" -c -1

In this command:

  • The program / software type is Gaussian.
  • sp (single point) is the calculation type.
  • tpsstpss is the method.
  • The basis set is supplied as ccpvdz, and it must resolve to the canonical basis set normally written as cc-pVDZ (i.e. when matching the user input, the dashes and any parentheses in the canonical name are ignored).
  • The geometry is given inline through --xyz as "Cl 0 0 0".
  • The molecular charge is -1 (supplied with -c).

When given these parsed arguments, get_input_from_args(...) must process them and return its (objs, outputs) result without error, treating the ccpvdz input as the valid cc-pVDZ basis set.

Scope

The normalization applies when a basis set name provided by the user is matched against the set of known/registered basis sets: any dash (-) and parenthesis ((, )) characters are disregarded during that match. No other characters are affected, and no other behavior changes are required.

<presets.data_dir>/my_preset.preset

{

  "type": "sp",
  "method": "tpsstpss",
  "basis_set": "ccpvdz",
  "version": "..."

Gaussian sp -bs ccpvdz --save my_preset

then the JSON object must not contain a method key. It contains exactly the three calculation fields that were supplied, plus the version metadata.

orca opt m062x -bs def2tzvp --specifications "tightscf" \

  • software: "orca"
  • type: "opt"
  • method: "m062x"
  • basis_set: "def2tzvp"
  • specifications: "tightscf"
  • solvation_model: "smd"
  • solvation_radii: "smd18"
  • solvent: "methanol"

Including the version metadata, the object has nine keys.

If method is left out of that command, it must be absent — not serialized as a default or a null value — which leaves eight total keys including the metadata.

--xyz "Cl 0 0 0" -c -1

  • Values that were explicitly supplied replace the corresponding stored values.
  • Values that are left out retain their previously stored values.
  • Values that appear only because of parser defaults must not overwrite stored values.

  -sm pcm -sr bondi -s acetonitrile \

--preset my_preset resolves to:

<presets.data_dir>/my_preset.preset

default_params = vars(get_parser().parse_args([]))

    default_params=default_params,

Take a preset containing:

type=opt
method=m062x
basis_set=def2tzvp

the required behavior is as follows:

  • --preset my_preset provides all four values.
  • With gaussian --preset my_preset, only software is changed, becoming gaussian.
  • orca sp m06 --preset my_preset changes the type to sp and the method to m06.
  • --preset my_preset -bs def2svp alters only the basis set.
  • --preset my_preset --d3 keeps all preset values and adds d3=True on top.

--preset my_preset --xyz 'Cl 0 0 0' -n 1 --mem 1G -c -1

    type="opt",
    method="m062x",
    basis_set="def2tzvp",
    xyz="Cl 0 0 0\n",
    nproc=1,
    mem="1G",
    charge=-1,

Presets that are incomplete or unknown

Loading a preset that does not exist through cmd must raise SystemExit.

Once the preset and the explicit CLI values have been merged, the calculation that results must still satisfy the normal validation of required parameters:

  • A preset that contains software, type, and basis set but no method stays incomplete if the CLI does not supply a method; cmd must raise SystemExit.
  • Supplying the missing method explicitly makes it valid.
  • A preset that contains software, type, and method but no basis set becomes valid when the CLI supplies -bs.

No specific exit message or status value is required.

Argument conversion when no preset is used

If --preset is not present, passing:

default_params=vars(get_parser().parse_args([]))

into get_input_from_args must not change the existing CLI behavior. The way structures, processor and memory options, charge, names, custom basis sets, solvation, dispersion flags, freeze constraints, and scan constraints are currently handled must remain equivalent to the corresponding gen_input(**parameters) call.

This holds for both:

  • software="Gaussian", including a call made with mem="10000MB".
  • software="ORCA", including a call that has no explicit memory value.

Task Specification: CLI Behavior for Preset Saving and Loading

Overview

A command-line tool that generates input files for computational chemistry is the subject of this task. Within that tool, you must implement or adjust the part of its behavior that deals with how command-line invocations get saved into, and loaded back out of, "preset" files.

Public API

Each item listed below must be importable and callable:

  • ccinput.presets — a module that has a module-level attribute, data_dir (a string path), determining which directory preset files are read from and written into. Callers must be able to reassign this attribute, and the value in effect at the moment of a call is the one that must be honored.

  • cmd(cmd_line=...) — a callable (importable in a way that makes cmd(cmd_line=<string>) work). This callable accepts a keyword argument, cmd_line, whose value is a complete command-line invocation packed into a single string; the string then gets parsed and executed.

Behavior of the Command-Line Interface

Command lines of the following form — with tokens separated by spaces — are what the cmd callable must accept:

  • A positional token holding the software/program name (e.g. Gaussian).
  • A token stating the calculation type (e.g. sp).
  • A token naming the method (e.g. tpsstpss).
  • -bs <basis_set> — the basis set (e.g. ccpvdz).
  • -f <filename> — the file holding the input structure (e.g. mystruct.xyz).
  • -o <filename> — the name of the output file (e.g. calc.com).
  • --save <name> — save the options of the invocation as a preset under the given name.
  • --preset <name> — load a preset that was saved previously under the given name.
Preset saving (--save <name>)

Whenever --save <name> is supplied, the tool must write a preset file whose name is <name>.preset, placing it in the directory that ccinput.presets.data_dir gives. The file must contain valid JSON that can be parsed into an object (dictionary).

Configuration options from the invocation are what the saved preset captures, except for the items below, which must never be persisted into the preset file:

  • The file holding the input structure (the value that -f supplies). A "file" key must not appear in the saved JSON object.
  • The output file (the value that -o supplies). An "output" key must not appear in the saved JSON object.

Background

From a set of calculation parameters, the codebase generates quantum chemistry input files (for Gaussian and ORCA). One of the parameters, custom_basis_sets, allows a user to assign a particular basis set to particular chemical elements, overriding the calculation's default basis set. Its value is a string that has the form:

"Element1=basisname1;Element2=basisname2;..."

for instance "O=Def2TZVPD;" or "I=def2-tzvpd;H=def2TZVPD;C=def2 TZVPD;".

Each named basis set is looked up (fetched from a basis set exchange source), and its definition in Gaussian/ORCA format is embedded into the generated input file.

Problem

Basis set names must be resolved even when the user writes them in a form that is non-canonical but recognizable. At present, the lookup succeeds only for one exact spelling of a basis set name, so common variations fail with an "Unknown basis set" error.

Required Behavior

When a basis set name supplied in custom_basis_sets is being resolved, the name must be normalized before the lookup is performed, so that spelling variations differing only by the following are treated as equivalent to the canonical name:

  • Case — the comparison must be case-insensitive (e.g. Def2TZVPD, def2tzvpd, DEF2TZVPD all resolve).
  • Hyphens — a hyphen (-) may be present or absent (e.g. def2-tzvpd resolves the same as def2tzvpd).
  • Spaces — whitespace may be present or absent (e.g. def2 TZVPD and Def2 tzvpd resolve the same as def2tzvpd).

Put another way, two basis set names are equivalent if they become identical once hyphens and whitespace have been removed and the result has been lowercased. Any such recognized variant of a known basis set name must resolve to that basis set and produce the same embedded basis set definition in the output as the canonical spelling would.

Names that do not correspond to any known basis set (even after this normalization) must still be rejected as unknown.

Specific cases that must work

All of these custom_basis_sets values must successfully resolve and embed the corresponding basis set definitions:

  • "O=Def2TZVPD;" — Def2TZVPD is resolved for oxygen.
  • "I=def2-tzvpd;H=def2TZVPD;C=def2 TZVPD;" — the def2-tzvpd/def2TZVPD/def2 TZVPD variants (all the Def2-TZVPD basis set) are resolved, for iodine, hydrogen, and carbon respectively. Iodine additionally pulls in its associated effective core potential (ECP).
  • "N=def2Svp;" — the Def2-SVP basis set is resolved for nitrogen.
  • "I=Def2 tzvpd;" — the Def2-TZVPD basis set (with iodine's ECP) is resolved for iodine.

  • ORCA: The default basis set remains on the ! route line. A %basis block is emitted, containing a newgto Element ... end entry for each custom-basis element and, if an element's basis set carries an ECP, a corresponding NewECP Element ... end block; the entire %basis block is closed with end.

Calculations are produced through the existing entry point, which accepts the parameters shown above (including nproc, mem, type, file, software, charge, method, basis_set, and custom_basis_sets) and returns an object that exposes the generated text through an input_file attribute.
