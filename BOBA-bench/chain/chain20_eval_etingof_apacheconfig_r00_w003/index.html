Overview

You are modifying an Apache-config parsing library. The change concerns how the parser's abstract syntax tree (AST) represents a sequence of configuration statements, and where duplicate-option merging is applied during loading.

The two public factory functions involved are make_lexer and make_parser, both importable from the package's public API (the same location they are currently importable from). The engineer must preserve their existing import paths and calling conventions.

Parser Behavior

AST structure change

The parser produces a nested-list AST. Currently, runs of consecutive statement nodes are wrapped inside an intermediate 'statements' grouping node. This intermediate grouping must be removed entirely: individual ['statement', name, value] nodes must appear directly as elements of their enclosing container ('contents', 'config', or 'block' contents), interleaved in source order with comment and block nodes.

Concretely:

  • A container that previously held ['statements', ['statement', 'a', 'b']] must now hold ['statement', 'a', 'b'] directly.
  • A container that previously held ['statements', ['statement', 'a', 'b'], ['statement', 'c', 'd']] (multiple statements grouped together) must now hold each statement as a separate sibling element: ['statement', 'a', 'b'], ['statement', 'c', 'd'].
  • The 'statements' node name must no longer appear anywhere in any AST produced by the parser.

Statements must remain in their original source order relative to surrounding comment and block nodes.

Example (a mixed document):

['contents',
    ['comment', ' a'],
    ['statement', 'a', 'b'],
    ['block', 'a',
     ['contents', ['statement', 'a', 'b']],
     'a'],
    ['statement', 'a', 'b'],
    ['block', 'a a',
     ['contents',
      ['statement', 'a', 'b'],
      ['statement', 'c', 'd'],
      ['comment', ' c']],
     'a a'],
    ['comment', ' a']]
Parser start symbol

The parser produced by make_parser accepts a start keyword argument selecting the grammar entry symbol. Because the 'statements' rule is removed, start='statements' is no longer a valid entry point. The valid entry symbol that yields a top-level ['contents', ...] node (a flat sequence of statement/comment/block siblings) is start='contents'.

The constructor signature remains: ApacheConfigParser(lexer, start=...), where lexer is a lexer instance obtained from make_lexer(). Its .parse(text) method returns the AST.

Behaviors that must be preserved

The following existing parsing behaviors are unaffected by this change and must continue to work exactly as before, now with statements as direct siblings (no 'statements' wrapper):

  • Comments (both #-style and /* */ C-style) parse to ['comment', text] nodes.
  • Blocks parse to ['block', name, contents, name] nodes; empty blocks to ['block', name, [], name].
  • Nested blocks are supported.
  • Statement values are stripped/not-stripped, and here-documents are captured, according to existing options.
  • A statement is ['statement', name, value].

Loader Behavior

Where merging is applied

Duplicate-option merging must be performed at the level of a container's contents (the flat sequence of sibling statements/blocks/comments), not at the level of a 'statements' grouping node (which no longer exists). The loader must correctly consume the new flat AST structure described above and produce the same loaded configuration mapping it produced before, for the option sets exercised.

Duplicate options — detection across intervening elements

When the option mergeduplicateoptions is not enabled and duplicate options are denied, a duplicate option must be detected and rejected even when the two identically-named options are separated by an intervening element (such as a block) between them. For example, given contents equivalent to:

a = 1
<b/>
a = 2

with duplicate-option-denial in effect (i.e. mergeduplicateoptions disabled), loading must raise an error due to the duplicate a option. Detection must not depend on the duplicates being adjacent.

Merging still works when enabled

When configured with explicit default option values and mergeduplicateoptions set appropriately, the loader must resolve option values consistently with the flat contents structure. In particular, given a set of provided default options and a document that overrides some of them, the resulting merged mapping reflects the document's values layered over the defaults. This behavior must hold regardless of whether the merging is driven by defaults or by in-document duplicates, using the flat-contents representation.

Constraints

  • Do not introduce or emit any 'statements' AST node.
  • Keep the public factory functions make_lexer(**options) and make_parser(**options) and the parser class interface ((lexer, start=...) constructor, .parse(text) method) importable and callable exactly as they are today.
  • All previously supported parsing and loading behaviors (comments, blocks, here-docs, value stripping, force-array, default merging, duplicate handling) must continue to function under the new flat structure.

Overview

The lexer and parser in this codebase process a configuration/markup language that supports hash-style comments (lines beginning with #). Currently, when a hash comment is tokenized and parsed, the leading # character is stripped from the comment's content. This behavior must change so that the # character is retained as part of the comment content.

Required Behavior Change

Lexer

The lexer exposes a tokenize(text) method that accepts a string and returns a list of tokens. For each line, tokens may be strings (for comments and plain content) or tuples (for key/value statements), interleaved with '\n' newline tokens.

For hash comment lines, the token produced for the comment must now include the leading # character verbatim, preserving everything on the line exactly as it appears (including any whitespace immediately following the #).

Examples of the required tokenization of comment lines (the comment token is the string shown):

  • A line containing only # → token '#'
  • A line # a → token '# a'
  • A line #a → token '#a'
  • A line # a b → token '# a b'
  • A line # h → token '# h'

In other words, the previous behavior stripped the # (and produced e.g. '', ' a', 'a', ' a b', ' h'); the new behavior keeps the # prefix intact and does not strip it, while otherwise leaving the remainder of the line unchanged.

This change applies to hash comments wherever they appear — at the top level, inside blocks, and interleaved with statements and blank lines. Non-comment tokens (plain content strings, key/value statement tuples, newlines, indentation) are unaffected.

Parser

The parser exposes a parse(text) method that returns a nested-list AST. Hash comments are represented as two-element lists of the form ['comment', <content>].

The <content> for a hash comment must now include the leading # character, matching the lexer token. For example:

  • #a → ['comment', '#a']
  • # b → ['comment', '# b']
  • # c → ['comment', '# c']
  • # a → ['comment', '# a']
  • # a b → ['comment', '# a b']

This applies to hash comments at the top level, inside blocks, and inside nested blocks.

Out of Scope / Unchanged

  • The structure of the AST (node names such as 'config', 'contents', 'block', 'statement', 'comment') and the representation of statements and blocks remain unchanged.
  • Statement value handling, including escaped hashes within statement values (e.g. a value like # # c produced from an escaped \#), is unchanged.
  • C-style comments are unaffected by this task.
  • Only the treatment of the leading # in hash comments changes: it is now preserved rather than stripped.

Task Specification: Line Continuation Handling in Config Parser

Overview

This task modifies how line continuations (a backslash \ immediately followed by a newline) are handled in a config file lexer and loader. The change affects two layers: the low-level tokenizer, which must preserve escaped newlines in its output, and the higher-level loader/parser, which must collapse line continuations into a single space.

Background: Line Continuation

A line continuation occurs when a line ends with a backslash (\) followed by a newline character. Historically the tokenizer stripped or partially retained these; the new behavior redefines exactly what is emitted and how the parser normalizes it.

Required Behavior

1. Lexer: preserve escaped newlines in tokens

The tokenizer must retain the literal \ + newline sequence as part of the token text where it occurs, rather than dropping it.

Concretely, for an assignment where a value spans multiple physical lines via line continuation, the value portion of the emitted token must include the trailing \ and the newline character(s) exactly as they appeared in the source (after normal whitespace handling around the boundaries).

For example, given input equivalent to:

a \
c b  \

(i.e. key a, then a value that continues across lines with backslash-newline continuations, followed by trailing content)

The tokenizer must produce:

[('a', ' \\\n', 'c b'), '  \\\n  ']

That is:

  • An assignment 3-tuple (key, separator, value) where the separator text between key a and value c b is ' \\\n' — a space, a backslash, and a newline — with the escaped newline preserved rather than removed.
  • A trailing standalone token ' \\\n ' — the leading spaces, backslash, newline, and trailing spaces preserved verbatim.

The lexer must expose a tokenize(text) method that accepts a string and returns a list of tokens, where each token is either:

  • a string (raw text token), or
  • a 3-tuple (key, separator, value) representing an assignment.
2. Loader/Parser: collapse line continuations to a single space

When the loader parses a value that contains one or more line continuations (backslash immediately followed by a newline), each such continuation — together with the whitespace that surrounds the break — must be collapsed into a single space in the final parsed value.

Specifically, a run consisting of any trailing whitespace, the backslash, the newline, and any leading whitespace on the continued line is normalized to exactly one space character in the resulting value string.

Examples of the resulting parsed values:

  • A value written as abc \ (newline) followed by pqr on the next line yields the string 'abc pqr' (single space joining the two fragments — no run of spaces preserved from indentation or trailing whitespace at the break).

  • A multiline shell command written with trailing backslash-newline continuations, such as:

    ssh -f -g orpheus.0x49.org           \
-l azrael -L:34777samir.okir.da.ru:22           \
-L:31773:shane.sol1.rocket.de:22           \
'exec sleep 99999990'

    yields:

    ssh -f -g orpheus.0x49.org -l azrael -L:34777samir.okir.da.ru:22 -L:31773:shane.sol1.rocket.de:22 'exec sleep 99999990'

    Each continuation collapses to a single space, discarding the surrounding whitespace (including the many spaces before each backslash).

This collapsing applies both to values at the top level and to values inside nested blocks.

3. Behavior NOT affected by this change
  • Here-documents: Newlines and content inside here-document values are preserved literally (e.g. embedded \n characters remain). Line-continuation collapsing does not apply to here-doc content.
  • Quoted values: Trailing whitespace inside quoted strings and quoted content (including masked/escaped quotes and single quotes within double quotes) is preserved as-is.
  • Comments inside here-docs: Text that looks like a comment inside a here-doc is retained as literal content, not treated as a comment.

Public API Surface

The loader must expose a loads(text) function/method that accepts a config-file string and returns a dictionary representing the parsed configuration. Nested blocks are represented as nested dictionaries; repeated keys that form lists are represented as lists of values (or lists of dicts for repeated blocks).

The lexer must expose a class with a tokenize(self, text) method as described in section 1.

Both the existing module paths and names for the lexer class and the loader entry point (loads) must remain importable and callable exactly as they currently are — this task only changes the line-continuation behavior, not the API structure.

Task: Add a preserve_whitespace option to the parser and lexer

Overview

The apacheconfig package provides a lexer and parser for Apache-style configuration syntax. Currently the parser discards whitespace information during parsing. You must add an opt-in option, preserve_whitespace, which — when enabled — causes the produced abstract syntax tree (AST) to retain whitespace (including surrounding/leading whitespace and newlines) as explicit elements in the output.

Public API

The package apacheconfig must expose (importable via from apacheconfig import *) at least the following factory functions:

  • make_lexer(**options) → returns a lexer class (ApacheConfigLexer).
  • make_parser(**options) → returns a parser class (ApacheConfigParser).

Both factories accept keyword options. The relevant option for this task is:

  • preserve_whitespace (bool, default falsey/absent): when set to True, whitespace is preserved in the parse output as described below.

The lexer class is constructed with no arguments: ApacheConfigLexer().

The parser class is constructed as ApacheConfigParser(lexer, start=<symbol>) where:

  • the first positional argument is a lexer instance,
  • start is a string naming the grammar start symbol to parse against.

The parser instance must expose a method parse(text) that returns the AST for the given input string, parsed as the configured start symbol.

Both make_lexer and make_parser must be given the same options (so both receive preserve_whitespace=True when whitespace preservation is desired).

Grammar start symbols

The start argument selects which production the input is parsed against. The following start symbols must be supported: statement, include, includeoptional, comment, contents, block, and config.

AST format (with preserve_whitespace=True)

Every AST node is a Python list whose first element is a string tag identifying the node type. The behavior required for each node type follows. All whitespace runs described below are captured verbatim as string elements.

statement

A statement is an option/value pair.

  • The tag is 'statement'.
  • If the statement has leading whitespace (whitespace before the option), that whitespace string is inserted immediately after the tag.
  • The option name and the value follow.
  • Any whitespace/separator between the option and the value (including surrounding spaces and = signs) is captured verbatim as a single string element placed between the option and the value.
  • Quoted values have their surrounding quotes removed but their inner content (including internal spaces) preserved.

Examples:

  • a b → ['statement', 'a', ' ', 'b']
  • a = b → ['statement', 'a', ' = ', 'b']
  • a "b c" → ['statement', 'a', ' ', 'b c']
  • Leading whitespace: \n a b (parsed as a statement) → ['statement', '\n ', 'a', ' ', 'b']
include
  • The tag is 'include'.
  • For the plain form: ['include', 'include', <whitespace>, <path>], where <whitespace> is the verbatim whitespace between the keyword include and the path.
    • include file.conf → ['include', 'include', ' ', 'file.conf']
  • For the angle-bracket form <<include ... >>: the opening << and closing >> delimiters appear as elements surrounding the include content.
    • <<include file.conf>> → ['include', '<<', 'include', ' ', 'file.conf', '>>']
includeoptional
  • The tag is 'includeoptional'.
  • Form: ['includeoptional', 'includeoptional', <whitespace>, <path>].
    • includeoptional file.conf → ['includeoptional', 'includeoptional', ' ', 'file.conf']
comment
  • The tag is 'comment'.
  • The comment text (starting at #, including everything after it on the line) is preserved verbatim.
    • # hello there !!! yep → ['comment', '# hello there !!! yep']
  • When a comment has leading whitespace preceding the #, that whitespace is captured as a string element inserted between the tag and the comment text.
    • Leading whitespace: \n # a b (parsed as contents, see below) yields a comment node ['comment', '\n ', '# a b'].
contents
  • The tag is 'contents'.
  • contents is a sequence of child nodes (statement, comment, or nested structures) interleaved with preserved whitespace strings.

Required behavior

Heredoc values

For a statement of the form:

NAME <<MARKER
...value...
MARKER

the parsed value must:

  • Preserve leading indentation on every value line.
  • Preserve ordinary line breaks.
  • Preserve blank lines.
  • Preserve a backslash immediately followed by a newline as the literal backslash and newline; it must not be treated as a continuation or replaced with a space.
  • Exclude the newline immediately after the opening <<MARKER.
  • Exclude the newline immediately before the terminating marker, so the returned value has no trailing newline in the exercised cases.

For example:

PYTHON <<MYPYTHON
    def a():
        x = \
        y
        return
MYPYTHON

parsed with a parser whose start rule is contents must produce:

    'contents',
    [
        'statement',
        'PYTHON',
        '    def a():\n'

        '        return'
    ]
]

        print "hi"
        return 1 + \

    return 3

must produce:

        'long'

('long', ' \\\n ', 'bloc name ')

[
    ('long', ' \\\n ', 'bloc name '),
    '\n',
    'long'
]

Thus, whitespace normalization applies to ordinary continued block-header values, but not to heredoc contents.

Overview

Implement writable Apache-configuration AST nodes in apacheconfig.wloader. The public node classes are:

  • LeafASTNode, for statements, comments, and supported include directives
  • BlockNode, for <tag ...>...</tag> blocks
  • ListNode, for ordered configuration contents

All three classes must be importable from apacheconfig.wloader. LeafASTNode and BlockNode must also be importable directly from the top-level apacheconfig package.

The nodes consume AST data produced by the existing make_lexer/make_parser infrastructure. They must preserve source formatting and expose targeted writable operations; this task does not replace the existing lexer or parser. A whitespace-preserving parser, such as one configured with flavors.NATIVE_APACHE, supplies the formatting information needed for exact source round trips.

General node behavior

Every successfully constructed node must provide dump(), returning its current Apache configuration text. Before any mutation, dump() must reproduce the successfully parsed input exactly, including leading and trailing whitespace, line breaks, separators, comments, continuation formatting, and quotation marks.

The parser AST forms relevant to these nodes are:

  • A contents node starts with "contents" and is followed by item ASTs and, when present, a final trailing-whitespace string.
  • A leaf starts with its parser typestring, such as "statement", "comment", "include", or "includeoptional". Its payload can include preceding whitespace, logical tokens, separators, and values.
  • A block starts with "block". It contains an opening-tag tuple, body data, and closing-tag text, with an optional preceding-whitespace token when the block occurs in contents.

Formatting tokens are not separate list items. Leading whitespace belongs to the leaf or block it precedes, while whitespace after the final item belongs to the containing ListNode.

LeafASTNode

LeafASTNode represents one non-block item. Supported leaf kinds include ordinary option/value statements, hash comments, Apache include directives, and optional-include directives when produced by the supplied parser.

Construction

Provide both of these entry points:

  • LeafASTNode.parse(raw, parser), which parses a source fragment and returns its leaf node.
  • LeafASTNode(ast), which constructs a leaf from a parser-style AST list.

The direct constructor must validate its input:

  • The leading typestring must be a supported leaf type: "statement", "comment", "include", or "includeoptional".
  • Non-leaf leading typestrings such as "contents" and "block", as well as unsupported typestrings, must raise apacheconfig.error.ApacheConfigError.
  • The AST must contain enough payload to describe that kind of leaf. For example, ["statement"] is malformed and must raise ApacheConfigError; ["statement", "option"] is a valid key-only statement.
Public metadata

A leaf must expose:

  • typestring: the corresponding parser type, including "statement", "comment", "include", or "includeoptional".
  • name: the first logical, non-whitespace name token. It is read-only. For a comment, this is the complete comment token; for a hash comment it includes the leading #. For an include, it is the directive name, such as include.
  • value: the logical parsed value, or None if there is no value. Statement separators and surrounding value quotes are not part of the logical name/value. Thus option "dblquoted value" has name option and value dblquoted value, while an unchanged dump still contains the double quotes. Single-quoted values behave analogously.
  • has_value: true exactly when the leaf currently has a value. Key-only statements and comments initially have no value.
  • whitespace: writable leading whitespace for the leaf. It is excluded from name and value but included by dump().

Examples of logical metadata are:

  • option → name option, value None, whitespace ""
  • include relative/path/* → name include, value relative/path/*, whitespace ""
  • \n option = value → name option, value value, whitespace "\n "
  • # here is a comment → name # here is a comment, value None, whitespace ""
  • \n # here is a comment → the same comment name and value, with whitespace "\n "

Leading whitespace, the exact name/value separator, and original quotation marks must remain unchanged in an unmodified dump.

Value mutation

value must be writable. Assigning a replacement value changes the value text while preserving the leaf's leading whitespace and its existing separator formatting. The assigned string is emitted as the replacement text, so callers can include quotation marks when they want the new value quoted. For example:

  • Changing option value to value2 produces option value2.
  • Changing \noption =\\n value to value2 produces \noption =\\n value2.
  • Assigning long value produces that spacing within the value unchanged.
  • Assigning "long value" emits the supplied double quotes.
  • Changing include old/path/to/file to new/path/to/file produces include new/path/to/file.

If a key-only leaf has no value, assigning one must append the new text after the key with exactly one separating space. For example, assigning option2 to the value of option produces option option2.

BlockNode

BlockNode represents a block such as <tag arguments>...</tag>.

Construction

Provide both of these entry points:

  • BlockNode.parse(raw, parser), which parses a raw block fragment.
  • BlockNode(ast, parser), which constructs a block from parser-style AST data and uses the supplied parser for its nested contents.

The direct constructor must validate the complete block shape:

  • The leading typestring must be "block"; "contents", any leaf typestring, or another type must raise ApacheConfigError.
  • The AST must contain all required opening-tag, body, and closing-tag fields. A form such as ["block", ("b",), []] is too short and must raise ApacheConfigError.
  • An empty list ([]) is a valid body representation and denotes a block with no body text. For example, ["block", ("b",), [], "b"] is valid.
  • A nonempty body representation must be a well-formed contents node whose leading typestring is "contents" and whose remaining entries describe actual whitespace and/or valid children. In the direct block constructor, the bare marker ["contents"] is malformed and must raise ApacheConfigError; it is not the valid representation of an empty block body. Malformed or nested-contents children must likewise raise ApacheConfigError.
Public data and dumping

A block must expose:

  • tag: the opening tag name, without angle brackets. For <b>...</b>, this is b.
  • arguments: a writable argument string, or None if the opening tag has no arguments. Whitespace separating the tag and arguments is excluded from this value. Thus <b name>...</b> has arguments name.
  • typestring: "block".
  • whitespace: writable whitespace preceding the opening <; it is included by dump().

An unmodified dump() must retain the exact opening tag, body, and closing tag. This includes blocks with no arguments, leading whitespace, nested contents, and closing tags that repeat arguments. Examples that must round-trip exactly include:

  • <b>\nhello there\nit me\n</b>
  • <b name/>\n</b>, whose opening arguments are name/ under native Apache parsing with empty-element tags disabled
  • <b>\n</b>
  • <b name>\n</b name>, whose arguments are name
  • \n<b>\n</b>
Argument mutation

Assigning arguments replaces only the opening tag's argument portion. The body and complete closing tag remain unchanged.

  • If arguments already exist, replace them while retaining the surrounding opening-tag formatting. <block name>\n</block> assigned name2 becomes <block name2>\n</block>.
  • If no arguments exist, insert exactly one space between the tag and new arguments. <block>\n</block> assigned name2 becomes <block name2>\n</block>.

ListNode

ListNode represents ordered contents containing any mixture of supported leaves and blocks. Comments and include directives are first-class children: they count toward the length and participate in iteration, insertion, removal, and dumping in their source order just like statement leaves.

Construction

Provide both of these entry points:

  • ListNode.parse(raw, parser), which parses configuration contents.
  • ListNode(ast, parser), which constructs contents from parser-style AST data.

The direct constructor must validate its input:

  • The leading typestring must be "contents"; a block or leaf AST at the root must raise ApacheConfigError.
  • Each item entry must be either a valid supported leaf AST or a complete valid block AST. A nested contents node, an incomplete block, or any other malformed child must raise ApacheConfigError.
  • A final whitespace string is contents formatting, not a child item.

typestring must identify the node as "contents". Its writable whitespace represents trailing whitespace after the last child (or all preserved whitespace when there are no children), and is included by dump().

Iteration, length, and dumping
  • Iteration yields child node objects in source order.
  • len(node) returns the number of child items, including independently represented comments but excluding whitespace.
  • Each yielded child's dump() includes that child's own leading whitespace and exact source formatting.
  • Whitespace-only contents such as " \n" have length zero.
  • Whitespace after the final item is not an item, but it must remain in the containing node's dump.
  • The entire ListNode.dump() must reproduce the original contents when no mutation has occurred.

For example:

  • a b\nc d has two children whose dumps are a b and \nc d.
  • a b \n has one child, while \n is entirely item-less.
  • a b # comment has two children, dumped as a b and # comment.
  • a b\n<b>\n</b> \n has a leaf and a block; the final two spaces and newline are trailing contents whitespace.

add(index, raw) parses raw and inserts it as one child at position index.

  • Valid indices are the inclusive range 0 through len(node). Index 0 inserts before the first item and len(node) inserts after the final item.
  • Negative or too-large indices must raise the built-in IndexError, including an index greater than zero for an item-less list.
  • raw must parse to exactly one valid child. A fragment containing no item, only whitespace/empty text, multiple items, or malformed data must raise ApacheConfigError.
  • The one child may be any supported leaf kind, including a comment, or a block.
  • The fragment's whitespace and comment text must be preserved and spliced with neighboring formatting as illustrated below.

Required insertion results:

  • Inserting \n1 2 at index 1 into a b\nc d yields a b\n1 2\nc d.
  • Inserting \n1 2 at index 2 into a b\nc d yields a b\nc d\n1 2.
  • Inserting ### at index 1 into a b\n yields a b ###\n.
  • Inserting \n1 2 at index 1 into a b # comment\n yields a b\n1 2 # comment\n.
  • Inserting \n1 2 at index 0 into a yields \n1 2\na.
  • Inserting ### at index 0 into a\n yields ###\na\n.
  • Inserting \n1 2 at index 0 into a b yields \n1 2\n a b.
  • Inserting \n1 2 at index 0 into \n yields \n1 2\n.
  • Inserting \n1 2 at index 0 into # comment\n yields \n1 2\n# comment\n.
remove(index)

  • Valid indices are 0 through len(node) - 1.
  • Negative indices, indices at or beyond the current length, and every index on an item-less list must raise the built-in IndexError.
  • Removal must delete the selected child's source while retaining the remaining children and appropriate surrounding/trailing formatting.

Required removal results:

  • Removing index 1 from a b\nc d yields a b.
  • Removing index 0 from a b\nc d yields \nc d.
  • Removing index 0 from \na\n yields \n.
  • Removing index 1 from a # comment yields a.
  • Removing index 0 from a # comment yields # comment.

Without mutation, dumping any successfully parsed node must reproduce its original text byte-for-byte.
