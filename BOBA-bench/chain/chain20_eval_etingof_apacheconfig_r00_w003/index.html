Specification of the Task

Goal

Repair the handling of line continuations in the Apache-style configuration parser so that a backslash occurring on a line that is otherwise empty does not corrupt the parsing that follows.

Public API

The factory functions and classes listed below must be importable and usable exactly as described:

  • make_lexer() — returns a lexer class (referred to below as ApacheConfigLexer). This class is instantiated with no arguments: ApacheConfigLexer().
  • make_parser() — returns a parser class (referred to below as ApacheConfigParser). This class is instantiated with a lexer instance: ApacheConfigParser(ApacheConfigLexer()).
  • ApacheConfigLoader — a loader class that is instantiated with a parser instance: ApacheConfigLoader(ApacheConfigParser(ApacheConfigLexer())).
    • It offers a loads(text) method which parses a configuration string and returns a Python dict representing the configuration that was parsed.

These names must be importable from the same module locations where they are currently exposed (the existing loader module already supplies ApacheConfigLoader; make_lexer and make_parser are the factory functions that already exist).

Behavior That Is Required

When a line ends in a single backslash (\), that signifies a line continuation: the backslash joins the current line with the line that follows.

The parser must handle correctly the situation in which a backslash appears on a line that is empty (that is, the line is composed of only the backslash). Such an empty continuation line — including when comment lines and/or additional empty continuation lines follow it — must be effectively ignored and must not disrupt parsing of the configuration content that comes after.

Specific case

When the input text is equivalent to:

\
# comment
\
<a>
    key value
</a>

(meaning: a line holding only a backslash, then a comment line, then a second line holding only a backslash, then a block named a that contains the single directive key value)

loads(...) must return:

{'a': {'key': 'value'}}

Constraints

  • Behaviors of the lexer, parser, and loader that already exist and are already correct must be preserved. The change is limited to handling empty continuation lines correctly (and comment lines interleaved with them) so that they do not break parsing.
  • Block sections such as <a> ... </a> result in a nested dict keyed by the block name, with the key value directives contained in them becoming key/value entries inside that nested dict.

03 You are making a change to a library that parses Apache configuration. 759 words · source specification, reworded by GLM-5.3-Flash

Overview

You are making a change to a library that parses Apache configuration. The change concerns the way the parser's abstract syntax tree (AST) represents a sequence of configuration statements, together with the point during loading at which duplicate-option merging is applied.

Two public factory functions are involved: make_lexer and make_parser. Both are importable from the package's public API — the same location from which they are importable today. The engineer must preserve both functions' existing import paths and calling conventions.

Parser Behavior

Change to the AST structure

The parser produces an AST in the form of nested lists. At present, runs of consecutive statement nodes are wrapped inside an intermediate 'statements' grouping node. This intermediate grouping must be removed entirely: individual ['statement', name, value] nodes must appear directly as elements of the container enclosing them ('contents', 'config', or 'block' contents), interleaved with comment and block nodes in source order.

In concrete terms:

  • A container that used to hold ['statements', ['statement', 'a', 'b']] must now hold ['statement', 'a', 'b'] directly.
  • A container that used to hold ['statements', ['statement', 'a', 'b'], ['statement', 'c', 'd']] (multiple statements grouped together) must now hold each statement as a separate sibling element: ['statement', 'a', 'b'], ['statement', 'c', 'd'].
  • The node name 'statements' must no longer appear anywhere in any AST the parser produces.

Relative to the comment and block nodes around them, statements must remain in their original source order.

Example (a mixed document):

['contents',
    ['comment', ' a'],
    ['statement', 'a', 'b'],
    ['block', 'a',
     ['contents', ['statement', 'a', 'b']],
     'a'],
    ['statement', 'a', 'b'],
    ['block', 'a a',
     ['contents',
      ['statement', 'a', 'b'],
      ['statement', 'c', 'd'],
      ['comment', ' c']],
     'a a'],
    ['comment', ' a']]
Start symbol of the parser

The parser that make_parser produces accepts a start keyword argument that selects the grammar's entry symbol. Since the 'statements' rule is removed, start='statements' is no longer a valid entry point. The valid entry symbol that yields a top-level ['contents', ...] node — a flat sequence of statement/comment/block siblings — is start='contents'.

The constructor signature remains: ApacheConfigParser(lexer, start=...), with lexer being a lexer instance obtained from make_lexer(). Its .parse(text) method returns the AST.

Behaviors that must be preserved

The parsing behaviors listed below already exist, are unaffected by this change, and must continue to work exactly as before — now with statements as direct siblings (no 'statements' wrapper):

  • Comments (both #-style and /* */ C-style) parse to ['comment', text] nodes.
  • Blocks parse to ['block', name, contents, name] nodes, and empty blocks to ['block', name, [], name].
  • Nested blocks remain supported.
  • Statement values are stripped/not-stripped, and here-documents are captured, in line with the existing options.
  • A statement has the form ['statement', name, value].

Loader Behavior

Where the merging is applied

Duplicate-option merging must be performed on a container's contents (the flat sequence of sibling statements/blocks/comments) rather than at the level of a 'statements' grouping node (which no longer exists). The loader must correctly consume the new flat AST structure described above and, for the option sets exercised, produce the same loaded configuration mapping it produced before.

Duplicate options — detection across intervening elements

When the option mergeduplicateoptions is not enabled and duplicate options are denied, a duplicate option must be detected and rejected even when an intervening element (such as a block) sits between the two identically-named options. For example, with contents equivalent to:

a = 1
<b/>
a = 2

and duplicate-option-denial in effect (i.e. mergeduplicateoptions disabled), loading must raise an error because of the duplicate a option. Detection must not depend on whether the duplicates are adjacent.

Merging still works when it is enabled

When the loader is configured with explicit default option values and mergeduplicateoptions set appropriately, it must resolve option values consistently with the flat contents structure. Specifically, given a set of provided default options and a document that overrides some of them, the resulting merged mapping reflects the document's values layered over the defaults. Using the flat-contents representation, this behavior must hold regardless of whether the merging is driven by defaults or by in-document duplicates.

Constraints

  • You must not introduce or emit any 'statements' AST node.
  • The public factory functions make_lexer(**options) and make_parser(**options), along with the parser class interface ((lexer, start=...) constructor, .parse(text) method), must remain importable and callable exactly as they are today.
  • All previously supported parsing and loading behaviors (comments, blocks, here-docs, value stripping, force-array, default merging, duplicate handling) must keep functioning under the new flat structure.

Task: Keep the leading hash character in hash-style comments

Overview

In this codebase, the lexer and parser process a configuration/markup language that supports hash-style comments (lines that begin with #). At present, when a hash comment is tokenized and parsed, the leading # character is stripped from the comment's content. That behavior must change so that the # character is kept as part of the comment content.

Behavior Change Required

Lexer

The lexer exposes a tokenize(text) method that accepts a string and returns a list of tokens. On each line, tokens may be strings (for comments and plain content) or tuples (for key/value statements), interleaved with '\n' newline tokens.

For hash comment lines, the token generated for the comment must now include the leading # character verbatim, so that everything on the line is preserved exactly as it appears (including any whitespace immediately following the #).

Examples showing the required tokenization of comment lines (the comment token is the string shown):

  • A line that contains only # → token '#'
  • A line # a → token '# a'
  • A line #a → token '#a'
  • A line # a b → token '# a b'
  • A line # h → token '# h'

To restate: previously the # was stripped (producing e.g. '', ' a', 'a', ' a b', ' h'); under the new behavior the # prefix stays intact and does not get stripped, while the rest of the line is otherwise left unchanged.

This change covers hash comments wherever they appear — at the top level, inside blocks, and interleaved with statements and blank lines. Non-comment tokens (plain content strings, key/value statement tuples, newlines, indentation) remain unaffected.

Parser

The parser exposes a parse(text) method that returns a nested-list AST. A hash comment is represented as a two-element list of the form ['comment', <content>].

The <content> of a hash comment must now include the leading # character, matching the lexer token. For example:

  • #a → ['comment', '#a']
  • # b → ['comment', '# b']
  • # c → ['comment', '# c']
  • # a → ['comment', '# a']
  • # a b → ['comment', '# a b']

This holds for hash comments at the top level, inside blocks, and inside nested blocks.

Out of Scope / What Stays Unchanged

  • The AST's structure (node names such as 'config', 'contents', 'block', 'statement', 'comment') along with the representation of statements and blocks stays the same.
  • Statement value handling stays the same, including escaped hashes within statement values (e.g. a value like # # c produced from an escaped \#).
  • C-style comments are not affected by this task.
  • The only aspect that changes is the treatment of the leading # in hash comments: it is now preserved rather than stripped.

Overview

The lexer's handling of include directives during tokenization must be changed so that the token it emits preserves not only the included filename but also the syntax and whitespace data surrounding the directive.

Lexer API

The entry point to the lexer is an object that exposes a tokenize(text) method:

lexer.tokenize(text) -> list
  • Input: text — the configuration source, supplied as a string.
  • Output: a list of tokens. The majority of tokens are ordinary strings (for example identifiers such as 'a', and newline tokens '\n'). Include directives are the exception: the lexer must now emit them as tuples that hold their complete syntax (see below).

Include Syntax Variants

Two include syntaxes must be supported by the implementation.

1. Include syntax wrapped in angle brackets

The source looks like this:

<<include first.conf>>

Any casing may be used when writing the directive keyword (for instance include or Include). Tokenizing input of this kind must result in a 5-element tuple:

('<<', <keyword>, <whitespace>, <filename>, '>>')

The elements have these meanings:

  • element 0: the string '<<', i.e. the literal opening delimiter,
  • element 1: the include keyword, kept exactly as it was written in the source (its case is preserved, e.g. 'include' or 'Include'),
  • element 2: the whitespace string that came between the keyword and the filename (e.g. ' '),
  • element 3: the filename being included, kept exactly as it was written (e.g. 'first.conf'),
  • element 4: the string '>>', i.e. the literal closing delimiter.

As an illustration: <<Include second.conf>> → ('<<', 'Include', ' ', 'second.conf', '>>')

2. Bare include syntax, Apache style

The source looks like this:

Include first.conf

Tokenizing input of this kind must result in a 3-element tuple:

(<keyword>, <whitespace>, <filename>)

The elements have these meanings:

  • element 0: the include keyword, kept exactly as it was written in the source (its case is preserved, e.g. 'include' or 'Include'),
  • element 1: the whitespace string that came between the keyword and the filename (e.g. ' '),
  • element 2: the filename being included, kept exactly as it was written (e.g. 'first.conf').

For instance, for the input Include second.conf, the output ('Include', 'second.conf') is not correct; the tokenization must instead be ('Include', ' ', 'second.conf').

Tokens Around Include Directives

  • Whenever a newline comes after an include directive, the lexer must emit that newline as its own '\n' token, exactly as it did previously.
  • Content of any other kind — identifiers, block markers, and so on — still tokenizes the same way it always did; include directives are the only thing that changes, going from a bare filename string to the tuple forms described above.

To illustrate, take input made up of two include directives in a row, each one followed by a newline and then the identifier a alone on its line; the token stream for that input is:

[<include-tuple-1>, '\n', 'a', '\n', <include-tuple-2>, '\n', 'a', '\n']

Scope of the Change

  • Only the tokens that the lexer emits for include directives are affected. Whitespace and delimiter information is now preserved inside the token tuples.
  • As far as this task is concerned, downstream parser behavior stays the same; you are not required to adapt the parser so that it consumes the new tuple fields differently.

Task Specification: How the Config Parser Handles Line Continuations

Overview

Here we alter the treatment of line continuations — a backslash \ immediately followed by a newline — within a config file's lexer and loader. The change concerns two layers: in the output of the low-level tokenizer, escaped newlines must be preserved; the higher-level loader/parser, by contrast, must collapse line continuations into a single space.

Background: What a Line Continuation Is

A backslash (\) at a line's end, followed by a newline character, constitutes a line continuation. In the past, the tokenizer either stripped these sequences out or kept only part of them; exactly what gets emitted, and the manner in which the parser normalizes it, are both redefined by the new behavior.

What Must Happen

1. Lexer: escaped newlines stay in the tokens

Wherever the literal \ + newline sequence occurs, the tokenizer must retain it within the token text instead of dropping it.

Concretely, consider an assignment whose value spans multiple physical lines through line continuation. In the token that gets emitted for it, the value portion must contain the trailing \ plus the newline character(s), exactly as they were written in the source (after the usual whitespace handling around the boundaries).

For example, take input that is equivalent to:

a \
c b  \

(i.e. the key is a, what follows is a value continued across lines by backslash-newline continuations, and trailing content comes at the end)

The tokenizer must generate:

[('a', ' \\\n', 'c b'), '  \\\n  ']

To unpack this:

  • An assignment 3-tuple (key, separator, value): its separator — the text that sits between key a and value c b — is ' \\\n', that being a space, a backslash, and a newline; the escaped newline is retained here, not removed.
  • A standalone token at the very end, ' \\\n ': its leading spaces, its backslash, its newline, and its trailing spaces are kept verbatim.

A tokenize(text) method must be exposed by the lexer. The method accepts a string, and a list of tokens is returned; each token in that list is either:

  • a string, which is a raw text token, or
  • a 3-tuple (key, separator, value) standing for an assignment.
2. Loader/Parser: collapsing line continuations into a single space

Suppose a value the loader is parsing has one or more line continuations in it — spots where a backslash is immediately followed by a newline. Each of those continuations, along with the whitespace around the break, must then be collapsed into a single space in the value as finally parsed.

Put more precisely, the run at issue — any trailing whitespace, then the backslash, then the newline, then any leading whitespace on the continued line — is normalized to exactly one space character in the value string that results.

The following examples show what the parsed values come out as:

  • If a value is written as abc \ plus a newline, with pqr on the next line, the string that comes out is 'abc pqr' (the two fragments are joined by a single space — no run of spaces from the indentation or from trailing whitespace at the break survives).

  • Take a multiline shell command that uses trailing backslash-newline continuations, such as:

    ssh -f -g orpheus.0x49.org           \
-l azrael -L:34777samir.okir.da.ru:22           \
-L:31773:shane.sol1.rocket.de:22           \
'exec sleep 99999990'

    the parsed result is:

    ssh -f -g orpheus.0x49.org -l azrael -L:34777samir.okir.da.ru:22 -L:31773:shane.sol1.rocket.de:22 'exec sleep 99999990'

    Each continuation turns into a single space, and the whitespace surrounding it is discarded (this includes the many spaces that sit before each backslash).

Values at the top level and values inside nested blocks are both covered by this collapsing.

3. Behavior NOT Touched by This Change
  • Here-documents: Within here-document values, newlines and content are kept literally (embedded \n characters, for instance, remain). Here-doc content is not subject to line-continuation collapsing.
  • Quoted values: Quoted strings and quoted content keep their trailing whitespace as-is (this includes masked/escaped quotes and single quotes within double quotes).
  • Comments inside here-docs: Anything within a here-doc that resembles a comment stays as literal content; it is not handled as a comment.

The Public API

A loads(text) function/method must be exposed by the loader. It accepts a config-file string, and a dictionary that captures the parsed configuration is returned. Nested blocks appear as nested dictionaries; repeated keys that form lists appear as lists of values (or, for repeated blocks, as lists of dicts).

As for the lexer: it must expose a class that has the tokenize(self, text) method described in section 1.

Both for the lexer class and for the loader entry point (loads), the existing module paths and names must stay importable and callable exactly as at present; what this task changes is the line-continuation behavior only, not the API structure.

Task: Give the parser and lexer a preserve_whitespace option

Background

For Apache-style configuration syntax, the apacheconfig package ships both a lexer and a parser. As things work today, whitespace information gets thrown out by the parser during parsing. You must add an opt-in option, preserve_whitespace — once it is enabled, the abstract syntax tree (AST) that gets produced keeps whitespace (surrounding/leading whitespace and newlines included) as explicit elements of the output.

Public interface

At least the following factory functions must be exposed by the package apacheconfig, each importable via from apacheconfig import *:

  • make_lexer(**options) → returns the lexer class, ApacheConfigLexer.
  • make_parser(**options) → returns the parser class, ApacheConfigParser.

Keyword options are accepted by both factories. The option this task revolves around is:

  • preserve_whitespace (bool, default falsey/absent): if it is set to True, whitespace is preserved in the parse output, as detailed below.

No arguments are involved in constructing the lexer class: ApacheConfigLexer().

To build the parser class, the form ApacheConfigParser(lexer, start=<symbol>) is used, where:

  • a lexer instance is the first positional argument,
  • start, given as a string, names the grammar start symbol to parse against.

A parse(text) method must be exposed on the parser instance; calling it returns the AST for the given input string, parsed as the configured start symbol.

The same options must be given to both make_lexer and make_parser (this way, both receive preserve_whitespace=True when whitespace preservation is desired).

Start symbols of the grammar

Which production the input gets parsed against is chosen by the start argument. These are the start symbols that must be supported: statement, include, includeoptional, comment, contents, block, and config.

Shape of the AST (with preserve_whitespace=True)

Each AST node is a Python list; the node type is identified by a string tag that fills the first element. For each node type, the required behavior is set out below. All of the whitespace runs described below get captured verbatim, as string elements.

statement

A statement consists of an option/value pair.

  • The tag reads 'statement'.

Heredoc whitespace preservation in the Apache configuration

Change the Apache configuration lexer/parser behavior so that heredoc values keep their original whitespace, while regular backslash-continued block headers stay normalized.

The public API surface

The APIs listed below must stay available:

  • apacheconfig.make_lexer(**options) / apacheconfig.lexer.make_lexer(**options)

    • The return value is a lexer class.
    • Instantiating the class takes no arguments.
    • Instances of the lexer provide tokenize(text).

  • apacheconfig.make_parser(**options) / apacheconfig.parser.make_parser(**options)

    • The return value is a parser class.
    • The class accepts a lexer instance and an optional start argument, start='contents' included.
    • Instances of the parser provide parse(text).

  • apacheconfig.loader.ApacheConfigLoader(parser, **options)

    • Instances of the loader provide loads(text).

Behavior requirements

Values of heredocs

For a statement written as:

NAME <<MARKER
...value...
MARKER

the value that is parsed must:

  • Keep leading indentation on every value line.
  • Keep regular line breaks.
  • Keep blank lines.
  • Keep a backslash immediately followed by a newline as the literal backslash and newline; it must not be handled as a continuation or replaced by a space.
  • Leave out the newline that appears immediately after the opening <<MARKER.
  • Leave out the newline that appears immediately before the terminating marker, so the value that is returned has no trailing newline in the exercised cases.

As an example:

PYTHON <<MYPYTHON
    def a():
        x = \
        y
        return
MYPYTHON

when parsed with a parser whose start rule is contents, must produce:

[
    'contents',
    [
        'statement',
        'PYTHON',
        '    def a():\n'
        '        x = \\\n'
        '        y\n'
        '        return'
    ]
]

When this configuration is loaded:

PYTHON <<END
def fn():
        print "hi"
        return 1 + \
    fn2()

def fn2():
    return 3
END

the result must be:

{
    'PYTHON':
        'def fn():\n'
        '        print "hi"\n'
        '        return 1 + \\\n'
        '    fn2()\n'
        '\n'
        'def fn2():\n'
        '    return 3'
}
Multiline block headers that are not heredocs

In a regular multiline block header, backslash-newline continuations must still be whitespace-normalized before the parser receives the block-header value.

Parsing:

"<long \\\n bloc \\\n name\\\n>\n</long>"

using the contents start rule must produce:

[
    'contents',
    [
        'block',
        ('long', ' \\\n ', 'bloc name '),
        [],
        'long'
    ]
]

The matching opening block token is:

('long', ' \\\n ', 'bloc name ')

The first separator field stays exactly a space, backslash, newline, and space. The remaining continued block-header words are normalized to "bloc name ", with its trailing space included. When the explicit closing tag follows, the applicable lexer token stream is:

[
    ('long', ' \\\n ', 'bloc name '),
    '\n',
    'long'
]

Therefore, whitespace normalization applies to regular continued block-header values, but not to heredoc contents.

Specification of the Task

Summary

Writable AST nodes for Apache configuration are to be implemented inside apacheconfig.wloader. The node classes that form the public surface are:

  • LeafASTNode, which handles statements, comments, and supported include directives
  • BlockNode, which is used for <tag ...>...</tag> blocks
  • ListNode, which models ordered configuration contents

Importing all three of these classes from apacheconfig.wloader must work. LeafASTNode and BlockNode must additionally be importable directly from the top-level apacheconfig package.

AST data that comes out of the existing make_lexer/make_parser infrastructure is what these nodes consume. Source formatting must be preserved by them, and targeted writable operations must be exposed; the existing lexer and parser are not replaced by this task. For exact source round trips, the formatting information that is needed can come from a whitespace-preserving parser, such as one configured with flavors.NATIVE_APACHE.

Behavior shared by all node types

Every node that gets constructed successfully must provide dump(), and calling that method returns the node's current Apache configuration text. Before any mutation happens, the successfully parsed input must be reproduced exactly by dump() — leading and trailing whitespace, line breaks, separators, comments, continuation formatting, and quotation marks all included.

The AST forms produced by the parser that matter for these nodes are the following:

  • A contents node has "contents" at its start; what follows is item ASTs and, when one is present, a final trailing-whitespace string.
  • A leaf has its parser typestring at the start — "statement", "comment", "include", and "includeoptional" are examples. Preceding whitespace, logical tokens, separators, and values are among the things its payload can include.
  • A block has "block" at its start. Inside it sit an opening-tag tuple, body data, and closing-tag text; an optional preceding-whitespace token appears when the block occurs in contents.

Formatting tokens are not list items in their own right. The leaf or block that leading whitespace precedes is where that whitespace belongs; whitespace coming after the final item belongs to the ListNode that contains the items.

LeafASTNode

A single non-block item is what LeafASTNode stands for. The leaf kinds it supports include ordinary option/value statements, hash comments, Apache include directives, and optional-include directives where the supplied parser produces them.

Constructing instances

Both of the entry points below must be provided:

  • LeafASTNode.parse(raw, parser), which takes a source fragment, parses it, and returns the leaf node for it.
  • LeafASTNode(ast), which takes a parser-style AST list and builds a leaf from it.

The direct constructor must validate whatever input it receives:

  • Whatever appears as the leading typestring must be a supported leaf type, the options being "statement", "comment", "include", or "includeoptional".
  • Leading typestrings that are not leaf types (such as "contents" and "block") must raise apacheconfig.error.ApacheConfigError; unsupported typestrings must raise it as well.
  • Enough payload to describe that kind of leaf must be present in the AST. To give an example: ["statement"] is malformed, and ApacheConfigError must be raised; ["statement", "option"] counts as a valid key-only statement.
Metadata exposed publicly

A leaf must expose the following:

  • typestring: the parser type that corresponds to the leaf, with "statement", "comment", "include", and "includeoptional" among the possibilities.
  • name: the token that comes first among the logical, non-whitespace name tokens. This attribute is read-only. For a comment, the name is the complete comment token; a hash comment's name includes the leading #. For an include, the name is the directive name, include being an example.
  • value: the value as logically parsed, or None if no value is there. The logical name/value does not take in statement separators or the quotes around the value. So option "dblquoted value" gives name option and value dblquoted value, even though a dump left unchanged still contains the double quotes. Values in single quotes work the same way.
  • has_value: true exactly when the leaf currently holds a value. Initially, key-only statements and comments have no value.
  • whitespace: the leaf's leading whitespace, which is writable. name and value leave it out, but dump() includes it.

A few illustrations of logical metadata:

  • option → name option, value None, whitespace ""
  • include relative/path/* → name include, value relative/path/*, whitespace ""
  • \n option = value → name option, value value, whitespace "\n "
  • # here is a comment → name # here is a comment, value None, whitespace ""
  • \n # here is a comment → name and value as in the previous comment, with whitespace "\n "

In a dump that has not been modified, the leading whitespace, the exact name/value separator, and the original quotation marks must all remain unchanged.

Mutating the value

value must be writable. When a replacement value is assigned, the text of the value changes; the leaf's leading whitespace and its existing separator formatting are preserved. The assigned string is what gets emitted as the replacement text, so callers can include quotation marks if they want the new value to come out quoted. Examples:

  • Setting the value of option value to value2 results in option value2.
  • Setting the value of \noption =\\n value to value2 results in \noption =\\n value2.
  • When long value is assigned, that spacing inside the value comes out unchanged.
  • When "long value" is assigned, the supplied double quotes are emitted.
  • Setting the value of include old/path/to/file to new/path/to/file results in include new/path/to/file.

When a key-only leaf has no value, an assignment must append the new text after the key, separated by exactly one space. To illustrate: assigning option2 as the value of option produces option option2.

BlockNode

A block — <tag arguments>...</tag> is one such case — is represented by BlockNode.

Constructing instances

Both of the following entry points must be available:

  • BlockNode.parse(raw, parser), which takes a raw block fragment and parses it.
  • BlockNode(ast, parser), which builds a block out of parser-style AST data, with the supplied parser serving the nested contents.

The full shape of the block must be validated by the direct constructor:

  • "block" is what the leading typestring must be; ApacheConfigError must be raised for "contents", for any leaf typestring, or for some other type.
  • All of the required opening-tag, body, and closing-tag fields must be present in the AST. Something shaped like ["block", ("b",), []] is too short, and ApacheConfigError must be raised.
  • An empty list ([]) is a valid way to represent the body, and it stands for a block that has no body text. To give an example, ["block", ("b",), [], "b"] is valid.
  • A body representation that is nonempty must be a well-formed contents node: "contents" must be its leading typestring, and actual whitespace and/or valid children must be what its remaining entries describe. Within the direct block constructor, the bare marker ["contents"] does not count as a valid representation of an empty block body — it is malformed, and ApacheConfigError must be raised. ApacheConfigError must likewise be raised for children that are malformed or nested contents.
Data exposed publicly, and dumping

A block must expose the following:

  • tag: the name of the opening tag, with the angle brackets stripped. For <b>...</b>, the tag is b.
  • arguments: the argument string, which is writable, or None if the opening tag carries no arguments. Whitespace that sits between the tag and the arguments is excluded from this value. So <b name>...</b> has arguments name.
  • typestring: "block".
  • whitespace: writable whitespace that precedes the opening <; dump() includes it.

The exact opening tag, the body, and the closing tag must all be retained by an unmodified dump(). That includes blocks that have no arguments, leading whitespace, nested contents, and closing tags repeating the arguments. Examples that must round-trip exactly include:

  • <b>\nhello there\nit me\n</b>
  • <b name/>\n</b>, where native Apache parsing with empty-element tags disabled gives name/ as the opening arguments
  • <b>\n</b>
  • <b name>\n</b name>, where the arguments are name
  • \n<b>\n</b>
Mutating the arguments

The only part replaced by an assignment to arguments is the opening tag's argument portion; the body and the whole closing tag stay as they are.

  • With arguments already in place, the assignment swaps them out while the opening tag's surrounding formatting is kept. Assigning name2 to <block name>\n</block> turns it into <block name2>\n</block>.
  • With no arguments present, the assignment puts exactly one space between the tag and the new arguments. Assigning name2 to <block>\n</block> turns it into <block name2>\n</block>.

ListNode

Ordered contents that hold any mixture of supported leaves and blocks are what ListNode represents. First-class status is given to comments and include directives as children: in their source order they figure into the length and take part in iteration, insertion, removal, and dumping, just like statement leaves.

Constructing instances

Two entry points are needed, and both must be present:

  • ListNode.parse(raw, parser), which takes configuration contents and parses them.
  • ListNode(ast, parser), which takes parser-style AST data and constructs contents from it.

The direct constructor must validate the input it receives:

  • "contents" is what the leading typestring must be; when the root is a block or leaf AST, ApacheConfigError must be raised.
  • Whatever an item entry is, it must be either a valid supported leaf AST or a complete valid block AST. ApacheConfigError must be raised by a nested contents node, an incomplete block, or any other malformed child.
  • The final whitespace string is not a child item — it counts as contents formatting.

The node must be identified as "contents" by its typestring. Its whitespace is writable and represents the trailing whitespace after the last child (or, when there are no children, all of the preserved whitespace); dump() includes it.

Iterating, length, and dumping
  • Child node objects are yielded by iteration in source order.
  • The count of child items is what len(node) returns; independently represented comments are counted, while whitespace is not.
  • Each child that gets yielded has a dump() that includes its own leading whitespace and its exact source formatting.
  • Contents made up of nothing but whitespace — " \n" is one such case — have length zero.
  • The whitespace after the final item does not form an item; all the same, it must remain in the containing node's dump.
  • When no mutation has occurred, the original contents must be reproduced by ListNode.dump() in its entirety.

Take these examples:

  • Two children make up a b\nc d; their dumps are a b and \nc d.
  • One child makes up a b \n, whereas \n has no items at all.
  • a b # comment consists of two children; dumped, they come out as a b and # comment.
  • A leaf and a block make up a b\n<b>\n</b> \n; the two spaces and newline at the very end are trailing contents whitespace.
add(index, raw)

add(index, raw) takes raw, parses it, and inserts the result as a single child at position index.

  • The inclusive range 0 through len(node) covers the valid indices. An insert at index 0 goes before the first item; an insert at len(node) goes after the final item.
  • The built-in IndexError must be raised for negative or too-large indices, an index greater than zero for an item-less list included.
  • Exactly one valid child must be what raw parses to. ApacheConfigError must be raised by a fragment that holds no item (only whitespace/empty text), several items, or malformed data.
  • The one child may be a block, or it may be any supported leaf kind, a comment included.
  • The fragment's whitespace and comment text must be preserved and spliced together with the neighboring formatting; the cases below illustrate this.

These are the insertion results that are required:

  • \n1 2 inserted at index 1 into a b\nc d gives a b\n1 2\nc d.
  • \n1 2 inserted at index 2 into a b\nc d gives a b\nc d\n1 2.
  • ### inserted at index 1 into a b\n gives a b ###\n.
  • \n1 2 inserted at index 1 into a b # comment\n gives a b\n1 2 # comment\n.
  • \n1 2 inserted at index 0 into a gives \n1 2\na.
  • ### inserted at index 0 into a\n gives ###\na\n.
  • \n1 2 inserted at index 0 into a b gives \n1 2\n a b.
  • \n1 2 inserted at index 0 into \n gives \n1 2\n.
  • \n1 2 inserted at index 0 into # comment\n gives \n1 2\n# comment\n.
remove(index)

remove(index) removes whichever child sits at index.

  • Indices 0 through len(node) - 1 are the valid ones.
  • The built-in IndexError must be raised by negative indices, by indices at or beyond the current length, and by every index used against an item-less list.
  • What removal must do is delete the source of the selected child; the remaining children and the appropriate surrounding/trailing formatting are retained as well.

These are the removal results that are required:

  • After index 1 is removed from a b\nc d, the result is a b.
  • After index 0 is removed from a b\nc d, the result is \nc d.
  • After index 0 is removed from \na\n, the result is \n.
  • After index 1 is removed from a # comment, the result is a.
  • After index 0 is removed from a # comment, the result is # comment.

Complete round-trip requirement

So long as no mutation occurs, the original text must be reproduced byte-for-byte when any successfully parsed node is dumped. Individual leaves, comments, Apache includes, quoted values, blocks carrying arguments or not, blocks whose closing tag repeats the arguments, nested blocks, whitespace-only contents, and complete multiline configurations that mix comments, assignments, key-only statements, includes, and nested blocks all fall under this. Only the portions and list positions described above are what targeted mutations may change.

Error behavior

All of the validation failures described above — malformed ASTs, invalid children, invalid fragments, and cardinality problems — must raise apacheconfig.error.ApacheConfigError. Range violations of ListNode.add() and ListNode.remove() are the only exception; there, the built-in IndexError must be raised.
