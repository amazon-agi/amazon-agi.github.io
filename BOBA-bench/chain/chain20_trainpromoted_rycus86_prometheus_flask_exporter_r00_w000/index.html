Task Specification: Prometheus Flask Exporter — Metric Decorators and Endpoint Registration

Overview

Implement PrometheusMetrics in the prometheus_flask_exporter module. It instruments a Flask application with automatic HTTP metrics, provides decorators for per-view Prometheus metrics, and exposes a selected Prometheus collector registry through a Flask route. Metrics must be created with prometheus_client and rendered in the standard Prometheus text exposition format.

Public API

Class: PrometheusMetrics

The class must be importable as:

from prometheus_flask_exporter import PrometheusMetrics

Constructor

PrometheusMetrics(app, path='/metrics', export_defaults=True, buckets=(0.1, 0.3, 1.2, 5), registry=prometheus_client.REGISTRY)

  • app is the Flask application to instrument.
  • path controls automatic registration of the exposition route. A string registers that route during construction. The default is /metrics. If path is None, no exposition route is registered automatically; a GET of /metrics must then return 404 unless the application separately defines that route.
  • export_defaults is a boolean and defaults to True. When true, both automatic HTTP metric families described below are registered and collected. When false, neither flask_http_request_total nor flask_http_request_duration_seconds is created or exposed. Disabling these defaults must not disable the exposition route or explicitly decorated metrics.
  • buckets supplies the finite bucket boundaries for the automatic request-duration histogram. It defaults to (0.1, 0.3, 1.2, 5). A supplied sequence replaces those finite defaults for that histogram.
  • registry is the Prometheus collector registry used by this instance and defaults to prometheus_client.REGISTRY. Every automatic metric and every decorator-created metric must be registered in this selected registry. Exposition routes created by the instance must render this same registry rather than always rendering the global default registry.

Constructor-level buckets affect only the automatic duration histogram. A custom histogram decorator uses its own buckets option.

register_endpoint

register_endpoint(path)

Register a Flask route at path that exposes the current contents of the selected registry.

  • A GET request to the registered route returns HTTP 200, the standard Prometheus text body, and the standard Prometheus exposition content type.
  • This method must work after construction with path=None; for example, register_endpoint('/manual/metrics') must make that route available without requiring reconstruction of the metrics object.
  • Registering an exposition route does not reset already collected metrics.
  • Requests to an exposition route registered by this class, whether registered by the constructor or manually, are excluded from both automatic HTTP metrics. Scraping metrics therefore does not change the automatic request count or create duration series for the exposition path.
export_defaults

export_defaults(buckets=(0.1, 0.3, 1.2, 5))

Register the automatic request counter and request-duration histogram described below on the application, using the selected registry and the supplied finite duration buckets. The constructor performs this operation automatically when export_defaults=True; constructing with export_defaults=False omits it.

Automatic HTTP Metrics

When default exporting is enabled, the application must collect the following two metric families for eligible requests. Metrics are recorded after a response is available, using the request method, actual request path, and numeric response status as applicable. Exposition-route requests and views marked with do_not_track() are not eligible.

Request counter

The counter is named flask_http_request_total and counts completed eligible HTTP requests.

  • It has exactly two labels: method and status.
  • It must not gain labels such as path, endpoint, or host.
  • method is the HTTP method, such as GET.
  • status is the numeric HTTP response status, rendered as a label string such as 200.
  • Counts accumulate by method/status combination across paths. For example, two eligible successful GET requests expose:

flask_http_request_total{method="GET",status="200"} 2.0

Fetching the exposition route to read that value must not increment it.

Request-duration histogram

The histogram is named flask_http_request_duration_seconds and observes elapsed request time in seconds.

  • It has exactly three ordinary labels: method, path, and status.
  • path is the actual Flask request path, such as /items/3, rather than an added label on the request counter.
  • It exposes the standard histogram series:
    • flask_http_request_duration_seconds_bucket, with the additional le label;
    • flask_http_request_duration_seconds_count;
    • flask_http_request_duration_seconds_sum.
  • The _count and _sum series carry the same method, path, and status labels. Each eligible request increases the matching _count by one and contributes its non-negative elapsed time to _sum and the cumulative buckets.
  • The default finite bucket labels are 0.1, 0.3, 1.2, and 5.0, followed by the standard +Inf bucket.
  • Supplying custom automatic buckets replaces all finite defaults; for example, (0.2, 2, 4) produces finite le values 0.2, 2.0, and 4.0, plus +Inf, and does not retain the default finite boundaries.

No automatic duration series may be produced for a registered exposition route merely because that route is scraped.

do_not_track

do_not_track()

Return a decorator for Flask view functions. The decorator factory takes no arguments.

A request handled by a view decorated with @metrics.do_not_track() must contribute to neither flask_http_request_total nor flask_http_request_duration_seconds. This opt-out applies only to the automatic metrics. Explicit histogram, summary, gauge, or counter decorators on the same view must continue to collect their own data.

Explicit Metric Decorators

PrometheusMetrics provides four decorator factories:

  • histogram(name, description, labels=None, **kwargs)
  • summary(name, description, labels=None, **kwargs)
  • gauge(name, description, labels=None, **kwargs)
  • counter(name, description, labels=None, **kwargs)

Each factory creates the corresponding prometheus_client metric in the registry selected by the constructor and returns a decorator for a Flask view. name is the metric name and description is its help text. Applicable extra keyword arguments must be forwarded to the corresponding Prometheus metric type; in particular, buckets customizes a decorator-created histogram.

Labels

All four factories use the same label contract:

  • labels may be None or a dictionary mapping label-name strings to callables.
  • Any non-dictionary value other than None, including a tuple or other sequence, must raise TypeError when the decorator factory is invoked.
  • Each label callable is evaluated for each handled request.
  • A callable with no arguments is called with no arguments. It may inspect Flask request context, for example lambda: request.path or lambda: request.view_args['item_id'].
  • A callable with one argument is passed the Flask response object, for example lambda response: response.status_code.
  • Label callable arity determines which invocation form is used.
  • Returned values become Prometheus label values. Numeric values must be converted to their string representation, so an integer view argument 3 appears as "3" and status 200 appears as "200".
  • User labels must be present on the metric's emitted child series. Histogram buckets additionally carry le.

With no labels, the metric is emitted without a label block.

histogram

The histogram decorator measures execution time of the wrapped view and makes one observation per served invocation.

  • It exposes standard histogram children including <name>_count, <name>_sum, and <name>_bucket.
  • <name>_count increases by 1.0 for each invocation.
  • Without a custom buckets option, the normal prometheus_client histogram boundaries are used; standard boundaries such as le="1.0" and le="2.5" must be present.
  • A supplied buckets sequence replaces those defaults. For example, buckets=(0.7, 2.9) must expose le="0.7" and le="2.9", along with +Inf.
  • Bucket values are cumulative. A single fast request has value 1.0 in every bucket whose boundary contains its observed duration.
  • User-generated labels appear on _count, _sum, and _bucket series.
summary

The summary decorator measures execution time of the wrapped view and makes one observation per served invocation.

  • It exposes the standard summary children, including <name>_count and <name>_sum.
  • <name>_count increases by 1.0 per invocation.
  • User-generated labels appear on the summary child series.
gauge

The gauge decorator tracks invocations currently executing.

  • The applicable <name> gauge child is incremented before the wrapped view runs and decremented after it completes.
  • For one in-progress invocation its value is 1.0; after completion it returns to 0.0.
  • Concurrent invocations for the same label combination are reflected by the in-progress count.
  • User-generated labels identify the applicable gauge child and are visible both while the view is running and after it returns to zero.
counter

The counter decorator increments the applicable <name> counter child by one for each served invocation.

  • Values accumulate across requests: successive invocations expose 1.0, 2.0, 3.0, and so on for the same label combination.
  • User-generated labels appear on the counter series.

Exposition Format

All registered exposition routes must use the standard Prometheus text exposition format generated from the selected registry. In particular:

  • An unlabeled sample is rendered as metric_name value.
  • A labeled sample is rendered as metric_name{label1="value1",label2="value2"} value.
  • Numeric metric values are rendered in Prometheus floating-point form, such as 0.0, 1.0, or 2.0.
  • Histogram, summary, gauge, and counter help/type metadata and child series must remain compatible with prometheus_client conventions.

Compatibility

The implementation must remain compatible with both Python 2 and Python 3 and with the Flask and prometheus_client APIs used by this package.

A tracking decorator must not replace Flask's exception handling with a response constructed directly by the decorator. Doing so bypasses registered error handlers and causes response-based labels to observe the wrong status, headers, or other response properties. At the same time, an unhandled Werkzeug HTTP exception must retain its normal HTTP response semantics rather than being treated like an unhandled ordinary Python exception.

Required Behavior

1. Delegate raised exceptions to Flask

If a decorated Flask view raises an exception, the decorator must pass it through the current application's normal user-exception handling mechanism, with the behavior of Flask.handle_user_exception.

This requirement applies to both:

  • ordinary Python exceptions, such as NotImplementedError; and
  • werkzeug.exceptions.HTTPException subclasses, including exceptions raised by flask.abort(...).

Flask, rather than the decorator, must select and invoke any applicable error handler.

2. Respect registered error handlers and their complete responses

When Flask finds a matching error handler, the handler's return value determines the request response. Before evaluating response-based labels, that return value must be finalized as a Flask response in the same way as a normal view return value. Consequently, label callables must be able to observe all final response properties, including:

  • the status code chosen by the handler;
  • headers added by the handler; and
  • any other properties of the finalized response object.

This applies whether the handler returns a response object directly or another Flask-supported response value, such as a body/status tuple or a body/status/headers tuple.

For example, if a handler for NotImplementedError returns a response with status 400, a label defined as lambda response: response.status_code must produce 400. The finalized handler-produced response must continue through the request as the decorated view's result; the exception must not propagate when Flask successfully handles it.

If Flask's user-exception handling raises because an ordinary, non-HTTP exception has no applicable handler, the decorator must not swallow or replace that exception. Before propagating it, the decorator must perform its metric update exactly once. Response-based labels for that update must be evaluated against a response representing HTTP status 500. Thus, for an unhandled ordinary exception:

  • a status label based on response.status_code is recorded as 500;
  • a summary's count and sum are updated once; and
  • the synthetic 500 response is used only for metric evaluation and must not be returned in place of the exception.

The same principle applies if Flask's user-exception processing itself raises an unhandled non-HTTP exception: metric evaluation uses a 500 response, then normal exception propagation is preserved.

4. Preserve unhandled HTTP-exception semantics

An HTTP exception for which no custom error handler exists is not subject to the ordinary-exception re-raise-with-500 rule. It must follow Flask's normal HTTP-exception behavior and become a response carrying the HTTP exception's own status code.

For example, an unhandled abort(503) must:

  • complete as the normal 503 HTTP response;
  • be recorded with status=503 by response-based metric labels; and
  • not be converted into a synthetic 500 metric response or re-raised by the decorator as an unhandled ordinary exception.

A matching HTTP-exception handler still takes precedence as described above; in that case, labels use the handler's finalized response instead of the exception's original status.

5. Record each decorated metric exactly once

For every invocation of a decorated view, the decorator's normal metric update must occur exactly once, regardless of whether the view:

  • returns successfully;
  • raises an exception handled by a registered error handler;
  • raises an unhandled ordinary exception; or
  • raises an HTTP exception with or without a matching custom handler.

Each metric uses the response corresponding to its outcome when evaluating response-based labels. In particular, summaries and histograms must make one observation per invocation, and counters must make their normal single increment. Existing behavior of the different metric types remains otherwise unchanged. If multiple metric decorators are stacked, each decorator updates its own metric once.

6. Finalize and return successful view responses

That same finalized response object must be returned by the wrapper, rather than returning the original unfinalized value and requiring Flask to construct the response a second time.

It must not change the existing return-value behavior of metric-decorated helper functions that are not themselves the active Flask view.

  • Handled HTTP exception: A view raises 409 Conflict; its registered handler returns status 400 and a header containing the original code. The metric is recorded once using status 400 and can read the header value 409.
  • Unhandled ordinary exception: A view raises an ordinary exception without a matching handler. The metric is recorded once with status=500, then the exception propagates from the wrapper.
  • Unhandled HTTP exception: A view calls abort(503) without a matching custom handler. The request retains the normal 503 response, and the metric is recorded once with status=503.

Overview

You are working on a Flask extension that provides Prometheus-style metrics tracking for HTTP endpoints. The extension exposes a metrics object (created via a factory) that offers decorators to attach custom metrics (counters, gauges, etc.) to Flask view functions, and also automatically tracks a set of default HTTP metrics for every request.

You must adjust the behavior of one existing decorator and add one new decorator, as described below.

Background: Default Metrics

For every tracked request, the extension records default HTTP metrics, including at least:

  • flask_http_request_total — labeled with method and status.
  • flask_http_request_duration_seconds_count — labeled with method, path, and status.

Custom metrics attached to a view via decorators such as counter(...) and gauge(...) are recorded independently of these default metrics.

Required Decorators

Both decorators are methods on the metrics object and are used as @metrics.<decorator>() (they take no required arguments and return a decorator that wraps a Flask view function). They can be stacked together with other metric decorators (counter, gauge, etc.) in any order on the same view.

1. do_not_track()

Change the behavior of the existing do_not_track() method so that it only suppresses the recording of the default HTTP metrics for the decorated endpoint. It must not suppress custom metrics.

Specifically, when a view is decorated with do_not_track():

  • The default metrics (e.g. flask_http_request_total, flask_http_request_duration_seconds_count) must not be recorded for requests to that endpoint.
  • Any custom metric decorators applied to the same view (both those applied "outside"/before and "inside"/after the do_not_track() decorator in the decorator stack) must still be recorded normally. For example, if the view is hit twice and has custom counters, those counters must reflect a value of 2.0.
2. exclude_all_metrics()

Add a new method exclude_all_metrics() to the metrics object. When a view is decorated with exclude_all_metrics():

  • The default HTTP metrics must not be recorded for that endpoint.
  • All custom metrics attached to that view (via counter, gauge, or other metric decorators, whether stacked before or after exclude_all_metrics()) must not be recorded either.

In other words, exclude_all_metrics() completely disables all metric recording — both default and custom — for the decorated endpoint.

API Surface

The metrics object (the instance returned by the extension's factory) must expose:

  • do_not_track(self) — returns a view decorator; suppresses only default metrics.
  • exclude_all_metrics(self) — returns a view decorator; suppresses default and all custom metrics.

Existing decorators counter(name, description, ...) and gauge(name, description, ...) must continue to work as before and remain stackable with the two decorators above.
