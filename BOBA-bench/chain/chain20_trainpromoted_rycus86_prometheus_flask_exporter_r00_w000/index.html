Task Specification: Prometheus Flask Exporter — Decorators for Metrics and Endpoint Registration

Overview

Implement PrometheusMetrics in the prometheus_flask_exporter module. It instruments a Flask application with automatic HTTP metrics, offers decorators for per-view Prometheus metrics, and exposes a selected Prometheus collector registry via a Flask route. Metrics must be created using prometheus_client and rendered in the standard Prometheus text exposition format.

Public API

Class: PrometheusMetrics

It must be possible to import the class as:

from prometheus_flask_exporter import PrometheusMetrics

Constructor

PrometheusMetrics(app, path='/metrics', export_defaults=True, buckets=(0.1, 0.3, 1.2, 5), registry=prometheus_client.REGISTRY)

  • app is the Flask application that gets instrumented.
  • path governs whether the exposition route is registered automatically. Passing a string registers that route during construction, and the default value is /metrics. When path is None, no exposition route is registered automatically; a GET of /metrics must then return 404 unless the application defines that route separately.
  • export_defaults is a boolean whose default value is True. When it is true, both of the automatic HTTP metric families described below are registered and collected. When it is false, neither flask_http_request_total nor flask_http_request_duration_seconds is created or exposed. Turning these defaults off must not disable the exposition route or explicitly decorated metrics.
  • buckets supplies the finite bucket boundaries for the automatic request-duration histogram and defaults to (0.1, 0.3, 1.2, 5). A sequence supplied here replaces those finite defaults for that histogram.
  • registry is the Prometheus collector registry used by this instance; its default is prometheus_client.REGISTRY. Every automatic metric and every decorator-created metric must be registered in this selected registry. Exposition routes created by the instance must render this same registry instead of always rendering the global default registry.

buckets given at the constructor level affect only the automatic duration histogram; a custom histogram decorator uses its own buckets option.

register_endpoint

register_endpoint(path)

Registers a Flask route at path that exposes the current contents of the selected registry.

  • A GET request sent to the registered route returns HTTP 200, the standard Prometheus text body, and the standard Prometheus exposition content type.
  • This method must work when called after construction with path=None; for example, register_endpoint('/manual/metrics') must make that route available without requiring the metrics object to be reconstructed.
  • Registering an exposition route does not reset metrics that have already been collected.
  • Requests to an exposition route registered by this class — whether it was registered by the constructor or manually — are excluded from both automatic HTTP metrics. Scraping the metrics therefore does not change the automatic request count or create duration series for the exposition path.
export_defaults

export_defaults(buckets=(0.1, 0.3, 1.2, 5))

Registers the automatic request counter and request-duration histogram described below on the application, using the selected registry and the finite duration buckets that are supplied. The constructor carries out this operation automatically when export_defaults=True; constructing the object with export_defaults=False omits it.

Automatic HTTP Metrics

Once default exporting is enabled, the application must collect the following two metric families for eligible requests. Recording happens after a response is available, using the request method, the actual request path, and the numeric response status where applicable. Requests to exposition routes and views marked with do_not_track() are not eligible.

Request counter

The counter, named flask_http_request_total, counts completed eligible HTTP requests.

  • It carries exactly two labels: method and status.
  • Labels such as path, endpoint, or host must not be added to it.
  • method is the HTTP method, such as GET.
  • status is the numeric HTTP response status, rendered as a label string such as 200.
  • Counts accumulate per method/status combination across paths. For example, two eligible successful GET requests expose:

flask_http_request_total{method="GET",status="200"} 2.0

Fetching the exposition route in order to read that value must not increment it.

Request-duration histogram

The histogram, named flask_http_request_duration_seconds, observes elapsed request time in seconds.

  • It carries exactly three ordinary labels: method, path, and status.
  • path is the actual Flask request path, for instance /items/3, rather than an added label on the request counter.
  • It exposes the standard histogram series:
    • flask_http_request_duration_seconds_bucket, which has the additional le label;
    • flask_http_request_duration_seconds_count;
    • flask_http_request_duration_seconds_sum.
  • The _count and _sum series carry the same method, path, and status labels. Each eligible request increases the matching _count by one, and its non-negative elapsed time is contributed to _sum and the cumulative buckets.
  • By default, the finite bucket labels are 0.1, 0.3, 1.2, and 5.0, followed by the standard +Inf bucket.
  • Supplying custom buckets for the automatic histogram replaces all finite defaults; for example, (0.2, 2, 4) produces finite le values 0.2, 2.0, and 4.0, plus +Inf, and does not retain the default finite boundaries.

For a registered exposition route, no automatic duration series may be produced just because that route is scraped.

do_not_track

do_not_track()

Returns a decorator for Flask view functions. The decorator factory takes no arguments.

A request that is handled by a view decorated with @metrics.do_not_track() must contribute to neither flask_http_request_total nor flask_http_request_duration_seconds. The opt-out applies to the automatic metrics only. Explicit histogram, summary, gauge, or counter decorators on the same view must continue to collect their own data.

Explicit Metric Decorators

PrometheusMetrics offers four decorator factories:

  • histogram(name, description, labels=None, **kwargs)
  • summary(name, description, labels=None, **kwargs)
  • gauge(name, description, labels=None, **kwargs)
  • counter(name, description, labels=None, **kwargs)

Each factory creates the corresponding prometheus_client metric in the registry that the constructor selected and returns a decorator for a Flask view. name is the metric name, while description is its help text. Extra keyword arguments that are applicable must be forwarded to the corresponding Prometheus metric type; in particular, buckets customizes a histogram created by a decorator.

Labels

All four factories follow the same label contract:

  • labels may be None or a dictionary that maps label-name strings to callables.
  • When the decorator factory is invoked, any non-dictionary value other than None — including a tuple or other sequence — must raise TypeError.
  • Every label callable is evaluated on each handled request.
  • A callable that takes no arguments is called with no arguments. It may inspect the Flask request context, for example lambda: request.path or lambda: request.view_args['item_id'].
  • A callable that takes one argument is passed the Flask response object, for example lambda response: response.status_code.
  • The arity of the label callable determines which invocation form is used.
  • The values returned become Prometheus label values. Numeric values must be converted to their string representation, so an integer view argument 3 appears as "3" and the status 200 appears as "200".
  • The user labels must be present on the child series that the metric emits. Histogram buckets additionally carry le.

When no labels are supplied, the metric is emitted without a label block.

histogram

The histogram decorator measures the execution time of the wrapped view and makes one observation per served invocation.

  • It exposes the standard histogram children, including <name>_count, <name>_sum, and <name>_bucket.
  • Each invocation increases <name>_count by 1.0.
  • When there is no custom buckets option, the normal prometheus_client histogram boundaries are used; standard boundaries such as le="1.0" and le="2.5" must be present.
  • A buckets sequence that is supplied replaces those defaults. For example, buckets=(0.7, 2.9) must expose le="0.7" and le="2.9", along with +Inf.
  • Bucket values are cumulative. For a single fast request, every bucket whose boundary contains its observed duration has the value 1.0.
  • User-generated labels appear on the _count, _sum, and _bucket series.
summary

The summary decorator measures the execution time of the wrapped view and makes one observation per served invocation.

  • The standard summary children are exposed, including <name>_count and <name>_sum.
  • <name>_count increases by 1.0 with each invocation.
  • User-generated labels appear on the child series of the summary.
gauge

The gauge decorator tracks the invocations that are currently executing.

  • The applicable <name> gauge child is incremented before the wrapped view runs and is decremented after it completes.
  • While one invocation is in progress its value is 1.0; after completion it returns to 0.0.
  • The in-progress count reflects concurrent invocations for the same label combination.
  • User-generated labels identify the applicable gauge child and are visible both while the view runs and after it returns to zero.
counter

For each served invocation, the counter decorator increments the applicable <name> counter child by one.

  • Values accumulate across requests: for the same label combination, successive invocations expose 1.0, 2.0, 3.0, and so on.
  • User-generated labels appear on the series of the counter.

Exposition Format

All registered exposition routes must use the standard Prometheus text exposition format, generated from the selected registry. Specifically:

  • A sample without labels is rendered as metric_name value.
  • A sample with labels is rendered as metric_name{label1="value1",label2="value2"} value.
  • Numeric metric values are rendered in Prometheus floating-point form, for example 0.0, 1.0, or 2.0.
  • The help/type metadata and child series of histogram, summary, gauge, and counter metrics must remain compatible with prometheus_client conventions.

Compatibility

The implementation must remain compatible with both Python 2 and Python 3, as well as with the Flask and prometheus_client APIs that this package uses.

The following rules apply:

  • When no labels are supplied through either mechanism, the metric is created with no labels and reports value 1.0.
  • When label values are provided (via either mechanism), the metric is created with the corresponding labels applied and with value 1.0.

  • a callable that takes no arguments (invoked to produce the label value), or
  • a callable that takes the response object as its single argument (invoked with the response to produce the label value), or
  • a plain static value (e.g. an integer, string), used directly as the label value.

For example, a labels mapping like {'uri': lambda: request.path, 'code': lambda r: r.status_code, 'variant': 2} must produce the label variant="2" alongside the dynamically computed labels.

4. Response-derived values returned by custom metric callables

Standard HTTP request metrics (flask_http_request_total, flask_http_request_duration_seconds_count) must still be recorded as usual for such requests.

Label values are rendered as strings in the exported metrics (integers such as 1, 2, 200 show up as 1, 2, 200; numeric metric values are shown with one decimal place, e.g. 1.0, 2.0, 5.0).

Background

Through the public PrometheusMetrics class, prometheus_flask_exporter delivers Prometheus instrumentation for Flask applications. Its metric-tracking decorators, for instance summary(...), can wrap Flask view functions and evaluate metric labels based on the response a request produces.

For instance:

    'metric_name',
    'description',
    labels={'status': lambda response: response.status_code}
)
def view_function():
    ...

A label callable that accepts a response must be given the final Flask response belonging to the decorated view. That covers a response produced by a registered Flask error handler. Static labels and label callables that take no arguments keep their existing behavior.

Problem Statement

A tracking decorator must not replace Flask's exception handling with a response that the decorator constructs directly. If it did, registered error handlers would be bypassed and response-based labels would observe the wrong status, headers, or other response properties. At the same time, an unhandled Werkzeug HTTP exception must keep its normal HTTP response semantics instead of being handled as an unhandled ordinary Python exception.

Required Behavior

1. Pass raised exceptions through to Flask

When a decorated Flask view raises an exception, the decorator must route it through the current application's normal user-exception handling mechanism, matching the behavior of Flask.handle_user_exception.

This requirement covers both of the following:

  • ordinary Python exceptions, such as NotImplementedError; and
  • werkzeug.exceptions.HTTPException subclasses, including exceptions raised by flask.abort(...).

It is Flask, not the decorator, that must select and invoke any applicable error handler.

2. Honor registered error handlers and their complete responses

If Flask locates a matching error handler, the handler's return value determines the request response. Before response-based labels are evaluated, that return value must be finalized as a Flask response in the same way as a normal view return value. As a consequence, label callables must be able to observe all final response properties, including:

  • the status code the handler chose;
  • headers the handler added; and
  • any other properties of the finalized response object.

This holds whether the handler returns a response object directly or another Flask-supported response value, such as a body/status tuple or a body/status/headers tuple.

As an example, if a handler for NotImplementedError returns a response with status 400, a label defined as lambda response: response.status_code must be 400. If a handler for an HTTP 409 Conflict returns status 400 and exposes the original code in an X-Original header, response-based labels must observe status 400 as well as the value 409 for that header. A matching handler's chosen status must not be overridden by the HTTP exception's original status.

The finalized response produced by the handler must continue through the request as the decorated view's result; when Flask handles the exception successfully, the exception must not propagate.

3. Let unhandled ordinary exceptions propagate, but still record the metric

When Flask's user-exception handling raises because an ordinary, non-HTTP exception has no applicable handler, the decorator must not swallow or replace that exception. It must propagate from the decorated view with its normal type and value, so the surrounding Flask configuration or caller can handle it in the usual way.

Before propagating the exception, the decorator must perform its metric update exactly once. For that update, response-based labels must be evaluated against a response representing HTTP status 500. Consequently, for an unhandled ordinary exception:

  • a status label based on response.status_code is recorded as 500;
  • the count and sum of a summary are updated once; and
  • the synthetic 500 response serves only for metric evaluation and must not be returned in place of the exception.

The same principle holds if Flask's user-exception processing itself raises an unhandled non-HTTP exception: metric evaluation is done against a 500 response, and normal exception propagation is then preserved.

4. Keep unhandled HTTP-exception semantics intact

When an HTTP exception has no custom error handler, it does not fall under the ordinary-exception re-raise-with-500 rule. It must follow Flask's normal HTTP-exception behavior and become a response that carries the HTTP exception's own status code.

As an example, an unhandled abort(503) must:

  • finish as the normal 503 HTTP response;
  • be recorded with status=503 by response-based metric labels; and
  • not be turned into a synthetic 500 metric response or re-raised by the decorator as an unhandled ordinary exception.

A matching HTTP-exception handler still takes precedence as described above; labels then use the handler's finalized response instead of the exception's original status.

5. Record each decorated metric exactly once

On every invocation of a decorated view, the decorator's normal metric update must occur exactly once, regardless of whether the view:

  • returns successfully;
  • raises an exception that a registered error handler handles;
  • raises an unhandled ordinary exception; or
  • raises an HTTP exception with or without a matching custom handler.

When response-based labels are evaluated, each metric uses the response that corresponds to its outcome. Specifically, summaries and histograms must make one observation per invocation, and counters must make their normal single increment. Apart from that, the existing behavior of the different metric types stays unchanged. When multiple metric decorators are stacked, each decorator updates its own metric once.

6. Finalize successful view responses and return them

When a decorated Flask view is successful, its Flask-supported return value must be finalized into the response that label evaluation uses. That same finalized response object is what the wrapper must return, rather than returning the original unfinalized value and requiring Flask to construct the response a second time.

This response behavior must keep working for ordinarily named routes, for routes whose endpoint name is explicitly assigned, and for decorated views registered through blueprints. The existing return-value behavior of metric-decorated helper functions that are not themselves the active Flask view must not be changed.

Expected Results

  • Handled ordinary exception: A view raises NotImplementedError; its registered handler returns status 400. The request finishes with the handler's response, and the metric is recorded once with status=400.
  • Handled HTTP exception: A view raises 409 Conflict; its registered handler returns status 400 plus a header containing the original code. The metric is recorded once with status 400 and can read the header value 409.
  • Unhandled ordinary exception: A view raises an ordinary exception with no matching handler. The metric is recorded once with status=500, and the exception then propagates from the wrapper.
  • Unhandled HTTP exception: A view calls abort(503) with no matching custom handler. The request keeps the normal 503 response, and the metric is recorded once with status=503.
  • Successful view: The metric is recorded once against the finalized successful response, and the wrapper returns that response.

Public API and Compatibility

No new public API is added. It must remain possible to import PrometheusMetrics from prometheus_flask_exporter, and the existing metric decorators—including summary(name, description, labels=...), histogram(...), counter(...), and gauge(...)—must keep their existing signatures and their ordinary metric semantics. The existing response-label, no-argument-label, static-label, registry, endpoint, blueprint, application-factory, default-metric, and metrics-export behavior must stay compatible. The only behavior that changes is the response finalization and exception-handling behavior described above.

Task Description

Background

This task centers on a Flask metrics library — an instrumentation extension in the Prometheus style. What the library exposes is a metrics object; the test suite instantiates a factory that creates it. Decorators for instrumenting Flask view functions come from this object, and HTTP request metrics are also tracked automatically by the library.

What needs fixing is how the do_not_track() decorator interacts with the metric-collecting decorators (counter(), gauge(), etc.); the desired outcome is that endpoints marked as "do not track" end up fully excluded from all metric collection.

Public API: Decorator Methods

Listed below are the decorator methods the metrics object provides (Flask view functions use them all in combination):

  • metrics.do_not_track() — returns a decorator which flags a view function, leaving it out of automatic HTTP request metric tracking.
  • metrics.counter(name, description, ...) — returns a decorator; a counter metric is registered and incremented for the decorated view.
  • metrics.gauge(name, description, ...) — returns a decorator; a gauge metric is registered and tracked for the decorated view.

These decorators can be stacked: a single view function can carry multiple of them, in any order relative to do_not_track().

Behavior Requirements

Once do_not_track() has been applied to a view function, metric collection must exclude that endpoint completely. In particular:

  1. HTTP request metrics stay unrecorded. For requests that a do_not_track() endpoint serves, the default metric used for tracking HTTP requests (flask_http_request_total) must not produce any sample. Even if such an endpoint is requested multiple times, flask_http_request_total must end up with no sample matching that method/status combination.

  2. On do_not_track() endpoints, custom metric decorators do not increment. If a view function carries do_not_track() alongside counter() and/or gauge() decorators, the metrics in question must stay at their initial value of 0.0, even after the endpoint has been requested. No matter whether the custom-metric decorators are applied above (outer) or below (inner) the do_not_track() decorator within the decorator stack, this requirement must hold.

    Take the concrete case of a view whose decorator stack contains counter()/gauge() decorators and has do_not_track() in the middle: every one of those counter/gauge metrics must still be registered and exposed (the metrics output must contain them), yet, after the endpoint has been invoked, all of their values must be 0.0.

    • A counter metric whose name is foo is exposed as foo_total, and 0.0 is the value it must report.
    • A gauge metric whose name is bar is exposed as bar, with 0.0 as what it must report.

The correctness requirement that matters most: with do_not_track() showing up anywhere in a view's decorator chain, all metric value collection for that view gets suppressed — while still ensuring every declared custom metric ends up registered and present in the exported metrics, carrying a value of 0.0.

Additional Notes

  • Even on a do_not_track() endpoint, custom metrics declared there are still registered (the metrics export shows them); incrementing/updating them simply never happens.
  • The automatic per-request HTTP metrics fall under this suppression, and so do the explicitly declared counter/gauge metrics on the same view.

Overview

The codebase you are working on is a Flask extension that provides Prometheus-style metrics tracking for HTTP endpoints. A metrics object — created via a factory — is exposed by this extension; the object offers decorators for attaching custom metrics (counters, gauges, etc.) to Flask view functions, and it also tracks a set of default HTTP metrics automatically for every request.

You must adjust the behavior of one existing decorator, and you must add one new decorator, as laid out below.

Background: The Default Metrics

For every tracked request, the extension records default HTTP metrics; these include at least:

  • flask_http_request_total — carrying the labels method and status.
  • flask_http_request_duration_seconds_count — carrying the labels method, path, and status.

When custom metrics are attached to a view via decorators such as counter(...) and gauge(...), they are recorded independently of these default metrics.

Decorators Required

Both decorators are methods on the metrics object and are used in the form @metrics.<decorator>() (they take no required arguments and return a decorator that wraps a Flask view function). A stack combining them with other metric decorators (counter, gauge, etc.) can be arranged in any order on the same view.

1. do_not_track()

The existing do_not_track() method must be changed so that only the recording of the default HTTP metrics is suppressed for the decorated endpoint. Custom metrics must not be suppressed by it.

Concretely, when do_not_track() decorates a view:

  • For requests to that endpoint, the default metrics (e.g. flask_http_request_total, flask_http_request_duration_seconds_count) must not be recorded.
  • Any custom metric decorators applied to the same view (both the ones applied "outside"/before and the ones applied "inside"/after the do_not_track() decorator in the decorator stack) must still be recorded normally. For example, if the view is hit twice and has custom counters, those counters must show a value of 2.0.
2. exclude_all_metrics()

Extend the metrics object with a new method, exclude_all_metrics(). When exclude_all_metrics() is applied to a view:

  • For that endpoint, the default HTTP metrics must not be recorded.
  • All custom metrics attached to that view (via counter, gauge, or other metric decorators, whether they are stacked before or after exclude_all_metrics()) must not be recorded either.

In other words, for the decorated endpoint, exclude_all_metrics() disables all metric recording completely — both the default and the custom.
