Task Specification: Choice Field Behavior

Overview

Implement and preserve the public behavior of the Choice form-field validator in the typesystem package. A Choice field accepts only configured choice values, while applying the null and empty-string rules defined below.

Public API

typesystem.Choice

The validator must remain importable from the package top level as:

import typesystem
validator = typesystem.Choice(...)

Its constructor accepts, at minimum, these keyword arguments:

  • choices: a list of two-tuples in the form (value, label). The first item is the value accepted and returned by validation; the second item is its human-readable display label.
  • allow_null: an optional boolean, defaulting to False, that controls whether null input and an otherwise-unmatched empty string may be accepted.

For example:

validator = typesystem.Choice(
    choices=[("R", "red"), ("B", "blue"), ("G", "green")]
)

The validator exposes:

value, error = validator.validate_or_error(data)

The result has these semantics:

  • Success returns (validated_value, None).
  • Failure returns (None, error), where error is a ValidationError.

Choice Matching

Validation matches input against the first item of each (value, label) tuple. Labels are descriptive and are not substituted for stored values.

For a configured choice value, validation succeeds and returns that value unchanged:

validator = typesystem.Choice(
    choices=[("R", "red"), ("B", "blue"), ("G", "green")]
)
value, error = validator.validate_or_error("R")
# value == "R"
# error is None

Except for the special null and empty-string cases below, a value that does not match any configured choice value must fail with:

ValidationError(text="Not a valid choice.", code="choice")

Thus, for the choices above, validating "Z" returns (None, error) with exactly that error.

Null and Empty-String Behavior

The following rules apply to the default validate_or_error(data) call.

Required choices (allow_null=False)

A Choice is non-nullable when allow_null is omitted or is False.

  • Validating None must fail with:

    ValidationError(text="May not be null.", code="null")

  • Validating the empty string "" when it is not one of the configured choice values must fail with:

    ValidationError(text="This field is required.", code="required")

    In particular:

    validator = typesystem.Choice(
    choices=[("R", "red"), ("B", "blue"), ("G", "green")]
)
value, error = validator.validate_or_error("")
# value is None
# error == ValidationError(text="This field is required.", code="required")

  • Any other unmatched value fails with the "choice" error described above.

The required empty-string error is distinct from both the null-input error and the general invalid-choice error.

Nullable choices (allow_null=True)

For a nullable Choice:

  • Validating None succeeds as (None, None).
  • If "" is not a configured choice value, validating "" treats it as null and succeeds as (None, None).
  • If "" is a configured choice value, validating "" succeeds with the actual configured value and returns ("", None), rather than converting it to None.
  • None remains null even when "" is configured as a valid choice. In that case, validating None still returns (None, None).
  • Any unmatched non-empty value still fails with ValidationError(text="Not a valid choice.", code="choice").

For example:

nullable = typesystem.Choice(
    choices=[("R", "red"), ("B", "blue")],
    allow_null=True,
)
assert tuple(nullable.validate_or_error(None)) == (None, None)
assert tuple(nullable.validate_or_error("")) == (None, None)

with_empty_choice = typesystem.Choice(
    choices=[("", "empty"), ("R", "red")],
    allow_null=True,
)
assert tuple(with_empty_choice.validate_or_error("")) == ("", None)
assert tuple(with_empty_choice.validate_or_error(None)) == (None, None)

Validation Error Contract

ValidationError must be constructible with the keyword arguments text and code:

ValidationError(text="This field is required.", code="required")

Two ValidationError instances with the same text and code must compare equal. All message text, capitalization, punctuation, and error codes in this specification are exact.

Compatibility and Scope

  • Choice options continue to use (value, label) tuples; validation is based on value, not label.
  • Successful validation must preserve the selected configured value, including the empty string when it is explicitly configured.
  • Null acceptance must not conflate None with an explicitly configured empty-string value.
  • Existing behavior of other fields, schemas, forms, validation results, and error interfaces must remain unchanged.

Implement a positional tokenization subsystem that parses JSON and YAML text into a token tree recording the source position (character index, line, and column) of every value and key, together with validation entry points that produce positionally annotated diagnostics.

1. Position and message value types (typesystem.base)

Position

Position is a value object constructed as Position(line_no, column_no, char_index); all three arguments must also be keyword-capable. It exposes line_no, column_no, and char_index attributes.

  • line_no is a 1-based line number.

  • column_no is a 1-based column number.

  • char_index is a 0-based offset into the source string.

  • Two Position instances are equal when all three attributes are equal.

  • repr(Position(line_no=1, column_no=1, char_index=0)) must be exactly:

    "Position(line_no=1, column_no=1, char_index=0)"
Message

Message remains the value object for a single diagnostic. Its common keyword arguments are text (a string), code (a string), and optional index (a list). It must additionally support both positional-information shapes below:

  • Single-position form: Message(text=..., code=..., position=<Position>)
  • Range form: Message(text=..., code=..., index=[...], start_position=<Position>, end_position=<Position>)

The existing positionless form, Message(text=..., code=..., index=...), must remain supported. In particular, omitting index preserves the existing empty-index behavior and a positionless message's representation remains Message(text='...', code='...'); a non-empty index is represented as index=[...].

Equality compares text, code, index, and the supplied positional information. repr must reflect the applicable fields in this order: text, code, index when supplied, followed by either position or start_position and end_position.

Required examples are:

Message(text='No content.', code='no_content', position=Position(line_no=1, column_no=1, char_index=0))

and:

Message(text='Must be a number.', code='type', index=['b'], start_position=Position(line_no=3, column_no=10, char_index=27), end_position=Position(line_no=3, column_no=14, char_index=31))

Existing positionless Message behavior, and the existing behavior and representations of ValidationError and ValidationResult, must remain compatible.

2. Token tree (typesystem.tokenize.tokens)

Three token classes represent parsed values. Every token stores its parsed Python value and two 0-based character offsets into the original source: start_index, the index of the first character in the token's textual span, and end_index, the index of the last character in that span, inclusive.

Constructors:

  • ScalarToken(value, start_index, end_index) — a leaf token for a string, number, boolean, or None.
  • DictToken(value, start_index, end_index) — value is a dictionary mapping ScalarToken keys to child tokens.
  • ListToken(value, start_index, end_index) — value is a list of child tokens.

These constructor forms must remain directly usable. Tokens returned by a tokenizer must additionally retain knowledge of the original content so that source substrings and positions can be computed. How that association is represented is not prescribed.

Common token behavior
  • token.value returns the fully materialized plain Python value by recursively unwrapping the token tree. A DictToken produces a plain dictionary whose keys are the scalar key values and whose values are recursively unwrapped child values. A ListToken produces a plain list. A ScalarToken produces its scalar value.
  • token.string is the exact source substring content[start_index:end_index + 1].
  • token.start is the Position corresponding to start_index.
  • token.end is the Position corresponding to end_index.
  • Each returned position's char_index equals the corresponding token index. Line 1, column 1 corresponds to character index 0. A newline increments the line number, and the first character on each new line is column 1.
  • Two tokens are equal when they have the same class, equal token structure, and equal start_index and end_index. Nested tokens are compared recursively, including their own spans.
Container lookups
  • token.lookup(path) accepts a list of keys and/or indices. It descends through a DictToken by matching each requested key against the scalar value of a key token, and through a ListToken by integer index. It returns the child value token at the addressed path.
  • token.lookup_key(path) descends in the same way, but the final path component must address a dictionary entry. It returns that entry's ScalarToken key rather than its value token. For a JSON string key, this token's string includes the surrounding quotes while its value is the decoded, unquoted key. For example, the key token for "a" has string == '"a"' and value == "a".
DictToken representation

repr(dict_token) must be DictToken('<exact source string for the whole token>'). For example:

DictToken('{"a": [1, 2, 3], "b": "test"}')

3. JSON tokenization (typesystem.tokenize.tokenize_json)

tokenize_json(content)

Parse a JSON document string and return its root DictToken, ListToken, or ScalarToken. Every end_index is inclusive.

The following inputs define the required span behavior:

  • For '{"a": [1, 2, 3], "b": "test"}', the root is a DictToken spanning indices 0..28. Key "a" is ScalarToken("a", 1, 3) and its value is a list spanning 6..14, with elements ScalarToken(1, 7, 7), ScalarToken(2, 10, 10), and ScalarToken(3, 13, 13). Key "b" is ScalarToken("b", 17, 19) and its value is ScalarToken("test", 22, 27).
  • For '[true, false, null]', the root is a ListToken spanning 0..18, containing ScalarToken(True, 1, 4), ScalarToken(False, 7, 11), and ScalarToken(None, 14, 17).
  • For '[100.0, 1.0E+2, 1E+2]', the root is a ListToken spanning 0..20, containing ScalarToken(100.0, 1, 5), ScalarToken(100.0, 8, 13), and ScalarToken(100.0, 16, 19).
  • Whitespace does not become part of a scalar token's span. For '{ }', the result is DictToken({}, 0, 2) and its string is "{ }". For '{ "a" : 1 }', the root spans 0..11, the key is ScalarToken("a", 2, 4), and its value is ScalarToken(1, 9, 9).

Thus a scalar's end_index is always the index of its final source character: a one-character number at index 7 ends at 7, the quoted string "test" at indices 22..27 ends at 27, and 100.0 at indices 1..5 ends at 5.

JSON parse errors

Malformed JSON must cause tokenize_json to raise json.decoder.JSONDecodeError. The exception's msg and 0-based pos must match standard-library JSON decoder behavior. Required examples are:

  • "{" → msg == "Expecting property name enclosed in double quotes", pos == 1
  • '{"a"' → msg == "Expecting ':' delimiter", pos == 4
  • '{"a":' → msg == "Expecting value", pos == 5
  • '{"a":1' → msg == "Expecting ',' delimiter", pos == 6
  • '{"a":1,1' → msg == "Expecting property name enclosed in double quotes", pos == 7
  • '{"a":1 "b"' → msg == "Expecting ',' delimiter", pos == 7
validate_json(content, validator=None)

content may be str or bytes. The function parses the document, optionally validates it, and returns a two-tuple (value, messages).

  • On successful parsing and validation, value is the resulting plain/coerced Python value and messages == [].
  • On parse or validation failure, value is None and messages is a non-empty list of Message objects.
  • Empty content returns None and exactly one Message(text="No content.", code="no_content", position=Position(line_no=1, column_no=1, char_index=0)).
  • With no validator, '{"a": 123}' and b'{"a": 123}' both return ({"a": 123}, []).
  • A JSON parse error produces one single-position message. Its code is "parse_error", its text is the decoder's message followed by a period, and its position is the decoder error offset translated to a Position. For '{"a" 123}', the message text is "Expecting ':' delimiter." and its position is Position(line_no=1, column_no=6, char_index=5).

When validator is supplied, its normal coercion behavior applies. Validation diagnostics become range messages containing the validation error's index, start_position, and end_position:

  • A value-level diagnostic uses the source span of the offending value token.

  • A structural diagnostic for which no value token exists, such as a missing required field, uses the whole root token's span.

  • With Object(properties=Integer()), the text:

    {
    "a": "123",
    "b": "abc"
}

    returns value is None and one message with text "Must be a number.", code "type", index ["b"], start Position(line_no=3, column_no=10, char_index=27), and end Position(line_no=3, column_no=14, char_index=31). The range includes both quotes around "abc".

  • With the same validator and "456" in place of "abc", validation succeeds with value == {"a": 123, "b": 456} and no messages.

  • A Schema subclass declaring integer fields a and b reports the same positioned type diagnostic for the "abc" case.

  • For that schema, '{"a": "123"}' is missing required field b. It returns one message with text "The field 'b' is required.", code "required", index ["b"], start Position(line_no=1, column_no=1, char_index=0), and end Position(line_no=1, column_no=12, char_index=11).

5. Validators and compatibility

The top-level typesystem package must continue to expose Integer, Object, and Schema.

  • Integer() validates and coerces integers. In non-strict validation it accepts numeric-looking strings such as "123" and returns 123. It rejects a non-numeric string such as "abc" with code "type" and text "Must be a number.".
  • Object(properties=<validator>) validates a mapping by applying the supplied validator to every property value.
  • Schema remains a base class whose subclasses declare fields as class attributes, for example a = Integer(). Existing required-field and default semantics must not change; an Integer() field without a default is required.

There are two intentionally distinct required-field message contracts:

  1. When a missing-field diagnostic is surfaced by validate_json or validate_yaml, it must be made field-specific: text "The field '<name>' is required.", code "required", and index ["<name>"]. Because the field has no value token, its range is the root document span.
  2. Direct schema validation must retain its established behavior. In particular, Schema.validate_or_error for a missing required field reports text "This field is required.", code "required", and the field index. For a missing field b, the underlying positionless message remains Message(text='This field is required.', code='required', index=['b']). The field-specific wording is not a global change to Schema, Object, or their direct validation APIs.

Other existing field, schema, validation-error, serialization, and form behavior is outside this feature and must remain compatible.

Task Specification: Password Field Rendering in Forms

Overview

You need to modify the form rendering behavior in the typesystem package so that string fields declared with a password format render as password input elements, and so that password field values are never emitted into the rendered HTML.

Public API Surface

The following API is used and must be supported:

  • typesystem.Schema — base class for defining schemas.
  • typesystem.String(max_length=..., format="password") — the String field must accept a format keyword argument. When format="password" is specified, the field represents a password input.
  • typesystem.Text() — text field.
  • typesystem.Choice(choices=[...]) — choice field.
  • typesystem.Jinja2Forms(package="typesystem") — a forms renderer constructed with a package keyword argument. Instances must provide a way to produce an HTML form for a given schema (the same mechanism already used for rendering forms of other field types).

Required Behavior

When a schema containing a String field with format="password" is rendered as an HTML form:

  1. The password field must be rendered using an <input> element whose type attribute is "password" (i.e. the output contains <input type="password").

  2. The rendered password input must be marked as required and must have an empty value. Specifically, the output must contain the substring required value=""> for the password input. The password field's value must not be populated into the rendered HTML — it renders with an empty value regardless of any underlying data.

  3. Rendering of other field types must be unchanged:

    • A boolean field renders as exactly one <input type="checkbox" element.
    • A plain String field (no password format) renders as exactly one <input type="text" element.
    • A Text field renders as exactly one <textarea element.
    • A Choice field renders as exactly one <select element.

Notes

  • Only fields declared with format="password" should be affected by the password rendering behavior. Ordinary string fields must continue to render as text inputs.

Overview

You must implement a new Union field type in the type system's field module, and ensure that password-formatted string fields do not leak their values into rendered HTML forms.

Part 1: The Union Field

Location and Import

Add a new class named Union to the module typesystem.fields. It must be importable as:

from typesystem.fields import Union

It should behave like the other field validators in that module (e.g. Integer, String), exposing a validate_or_error(value) method that returns a two-tuple (value, error), where exactly one of the two is meaningful: on success error is None; on failure value is None and error is a ValidationError.

Constructor
Union(any_of, allow_null=False, ...)
  • any_of: a list of field validator instances (e.g. [Integer(), String()]). These are the candidate types the union will attempt to validate against.
  • allow_null: a boolean keyword argument (default False) following the same convention as the other fields.
Validation Behavior

Given an input value, validate_or_error must attempt to validate the value against each validator in any_of, in the order given:

  1. Successful match: If the value validates successfully against any of the candidate validators, return (validated_value, None) using the result from the first candidate that succeeds.

    • Example: with Union(any_of=[Integer(), String()]), the string "abc" validates as a string and returns ("abc", None); the integer 123 validates as an integer and returns (123, None).

  2. Null handling:

    • If the input is None and none of the candidate validators nor the Union itself permit null, the result must be an error: ValidationError(text="May not be null.", code="null").
    • If None is passed and at least one candidate validator permits null (e.g. Integer(allow_null=True)), then None is accepted: return (None, None).
    • If None is passed and the Union itself was constructed with allow_null=True, then None is accepted: return (None, None).

  3. No match: If the value is not None, does not match any candidate validator, the result must be: ValidationError(text="Did not match any valid type.", code="union")

    • Example: with Union(any_of=[Integer(), String()]), the boolean True matches neither an integer nor a string, producing this "union" error.

  4. Single-candidate constraint errors: When exactly one candidate validator is the appropriate type match but the value fails a specific constraint of that validator, the error returned must be that validator's own specific constraint error rather than the generic union error.

    • Example: with Union(any_of=[Integer(maximum=1000), String()]), the integer 9999 is an integer (so it matches the Integer candidate's type) but exceeds the maximum. The returned error must be ValidationError(text="Must be less than or equal to 1000.", code="maximum").
Error Type

ValidationError is the existing error type used throughout the type system. Errors are compared by their text and code values.

Part 2: Password Field Rendering

Password-formatted string fields must not expose their submitted values in rendered form HTML.

For a schema field defined as typesystem.String(format="password"), when a form is rendered with a value supplied for that field, the rendered HTML must not contain the field's plaintext value.

Example: rendering a form for a schema with a password = typesystem.String(format="password") field, given the value "secret" for that field, must produce HTML in which the substring "secret" does not appear.

Text-formatted and other input types are unaffected; only the value of password-format fields must be suppressed from the rendered output.

Task: Implement JSON Schema Conversion for Numeric Range Keywords

Objective

Add a function that converts a JSON Schema document into a typesystem validator object, supporting the numeric range validation keywords minimum, maximum, exclusiveMinimum, and exclusiveMaximum.

Public API

Create a module at typesystem/json_schema.py exposing a callable:

def from_json_schema(schema):
    ...
  • Input: schema — a JSON Schema value. For this task the schema will always be a JSON object (a dict) that may contain the keys minimum, maximum, exclusiveMinimum, and/or exclusiveMaximum, each mapped to a numeric value.
  • Output: a validator object.

Validator Object Requirements

The returned validator must provide a method:

def validate_or_error(self, value, strict=False):
    ...

This method returns a two-tuple (value, error):

  • When value satisfies the schema, error must be None.
  • When value does not satisfy the schema, error must be a non-None object.

The method must accept a keyword argument strict (which will be passed as True). Its presence in the signature is required.

Validation Semantics

The schema keywords apply only to numeric input values (integers and floats). For any input value that is not a number, all of these keywords are ignored and the value is considered valid (error is None).

For numeric input values, each present keyword constrains the value as follows:

  • minimum: N — the value is valid only if value >= N. A value equal to N is valid; a value below N is invalid.
  • maximum: N — the value is valid only if value <= N. A value equal to N is valid; a value above N is invalid.
  • exclusiveMinimum: N — the value is valid only if value > N. A value equal to N is invalid; a value below N is invalid.
  • exclusiveMaximum: N — the value is valid only if value < N. A value equal to N is invalid; a value above N is invalid.

The keyword values may be floating-point numbers (e.g. 3.0, 1.1), and comparisons must work correctly against both integer and float input values.

Examples of Expected Behavior

  • Schema {"maximum": 3.0}: input 2.6 → valid; input 3.0 → valid; input 3.5 → invalid; input "x" → valid (non-number ignored).
  • Schema {"minimum": 1.1}: input 2.6 → valid; input 1.1 → valid; input 0.6 → invalid; input "x" → valid.
  • Schema {"exclusiveMaximum": 3.0}: input 2.2 → valid; input 3.0 → invalid; input 3.5 → invalid; input "x" → valid.
  • Schema {"exclusiveMinimum": 1.1}: input 1.2 → valid; input 1.1 → invalid; input 0.6 → invalid; input "x" → valid.

Objective

Implement a function that converts a JSON Schema definition into a typesystem validator, such that validating data against the resulting validator produces correct pass/fail results consistent with the JSON Schema specification for a defined subset of keywords.

Public API

Module: typesystem.json_schema

Provide a public function:

def from_json_schema(schema) -> Field

    • A Python bool (True or False), representing a boolean schema, or
    • A Python dict containing JSON Schema keywords (see below).

Module: typesystem.fields

The following must be importable from typesystem.fields:

Boolean, Date, DateTime, Decimal, Float, Integer, Number,
Object, String, Time, Union

Required Validation Behavior

  • text equal to "Must match the pattern /{pattern}/.", where {pattern} is the human-readable pattern string (the regex source text), not the repr() of a compiled regular expression object.

Public API to provide

typesystem.SchemaDefinitions

A container that holds a namespace of named schema classes and behaves as a mutable mapping from schema name (str) to schema class.

  • Constructed with no arguments: typesystem.SchemaDefinitions().
  • Supports item access by name: definitions["Album"] returns the registered schema class.
  • Supports del definitions["Artist"].
  • Supports len(definitions) returning the number of registered schemas.
  • Supports iteration such that dict(definitions) yields {name: schema_class, ...}.
  • Two independent SchemaDefinitions instances are fully separate namespaces; registering schemas with the same class names into different instances must not clash or interfere.

Schemas are registered into a SchemaDefinitions instance at class-definition time (see below).

typesystem.Schema — definitions keyword

typesystem.Schema subclasses may be declared with a keyword argument definitions:

class Album(typesystem.Schema, definitions=definitions):
    ...

When a schema subclass is declared this way, it is registered into that SchemaDefinitions instance under its class name (e.g. "Album"). The definitions keyword is optional; schemas declared without it behave as before.

typesystem.Reference

A field type representing a reference to another schema.

Constructor signatures that must be supported:

  • typesystem.Reference(SchemaClass) — direct reference to a concrete Schema subclass.
  • typesystem.Reference("SchemaName") — string forward-reference, resolved against the enclosing schema's SchemaDefinitions namespace.
  • Accepts the standard field keyword allow_null=True.

Validation behavior:

  • Validating a value against a Reference validates that value against the referenced schema, producing an instance of the referenced schema class.
  • With allow_null=True, a None value validates to None.

String references (Reference("Name")) are only resolvable when the field is used inside a schema that was declared with a shared definitions namespace containing (eventually) a schema registered under that name. The referenced schema may be declared after the referring schema, as long as it is registered in the same namespace before validation occurs.

Reference must be usable both as a top-level field on a schema and as a nested field inside container field types. In particular, string references must resolve correctly when nested inside:

  • typesystem.Array(items=typesystem.Reference("Name"))
  • typesystem.Array(items=[typesystem.Reference("Name")]) (list form of items)
  • typesystem.Object(properties={"key": typesystem.Reference("Name")})

In each nested case, validation of the surrounding structure must produce the referenced schema instances in the appropriate positions (single instance for object properties, list of instances for array items).

Note: typesystem.Reference replaces the previous nested-schema field usage. Existing nested-schema validation behavior (validating a mapping into a child schema instance, and allow_null producing None) must continue to work through Reference, including when passing a concrete schema class directly.

typesystem.to_json_schema(...) must handle references and definitions.

  • The top level has "type": "object", "properties", and "required".

JSON Schema input — loading $ref and definitions

The library's JSON-Schema-driven validation must correctly interpret standard draft-7 $ref and definitions constructs when loading a schema and validating data against it. The following behaviors must hold:

  1. Nested $ref chains. A schema with a definitions block whose entries reference one another, and a top-level $ref pointing into that chain, must resolve transitively. Example:

    {
    "definitions": {
        "a": {"type": "integer"},
        "b": {"$ref": "#/definitions/a"},
        "c": {"$ref": "#/definitions/b"}
    },
    "$ref": "#/definitions/c"
}

    Here integer values are valid and non-integer values (e.g. a string) are invalid.

  2. $ref overrides sibling keywords. When a subschema contains $ref alongside other keywords, only the referenced schema applies; sibling keywords are ignored. Example: a property whose schema is {"$ref": "#/definitions/reffed", "maxItems": 2} where reffed is {"type": "array"} must accept arrays of any length and reject non-arrays; the maxItems constraint is ignored.

  3. $ref to a boolean schema.

    • A $ref pointing to a definition of true makes every value valid.
    • A $ref pointing to a definition of false makes every value invalid.

References are resolved against the local document using #/definitions/<name> JSON-pointer fragments.

Additional correctness requirement

Anywhere the code signals "not implemented" by raising, it must raise the built-in NotImplementedError (a valid exception type), never the NotImplemented singleton (which cannot be raised).

  • typesystem.SchemaDefinitions
  • typesystem.Schema (supporting the definitions= class keyword)
  • typesystem.Reference (accepting a schema class or a string name, plus allow_null)
  • typesystem.String, typesystem.Integer, typesystem.Date, typesystem.Array, typesystem.Object (existing field types, used together with the above)
  • typesystem.to_json_schema (handling both a schema class and a SchemaDefinitions instance)
