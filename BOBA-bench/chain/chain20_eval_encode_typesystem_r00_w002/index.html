Task Specification: Behavior of the Choice Field

Summary

The task is to implement and preserve the public behavior of the Choice form-field validator in the typesystem package. A Choice field accepts only choice values that have been configured, while applying the null and empty-string rules given below.

Public API

typesystem.Choice

The validator must remain importable at the top level of the package, as follows:

import typesystem
validator = typesystem.Choice(...)

At minimum, the constructor accepts these keyword arguments:

  • choices: a list of two-tuples taking the form (value, label). The first item is the value that validation accepts and returns; the second item is its human-readable display label.
  • allow_null: an optional boolean that defaults to False and controls whether null input and an empty string that would otherwise be unmatched may be accepted.

As an example:

validator = typesystem.Choice(
    choices=[("R", "red"), ("B", "blue"), ("G", "green")]
)

The validator exposes the following:

value, error = validator.validate_or_error(data)

These are the semantics of the result:

  • On success, it returns (validated_value, None).
  • On failure, it returns (None, error), with error being a ValidationError.

Matching Against Choices

The first item of each (value, label) tuple is what validation matches the input against. Labels serve a descriptive purpose and are not substituted for stored values.

When the input is a configured choice value, validation succeeds and returns that value unchanged:

validator = typesystem.Choice(
    choices=[("R", "red"), ("B", "blue"), ("G", "green")]
)
value, error = validator.validate_or_error("R")
# value == "R"
# error is None

Apart from the special null and empty-string cases below, if a value does not match any configured choice value, it must fail with:

ValidationError(text="Not a valid choice.", code="choice")

So, for the choices given above, validating "Z" returns (None, error) carrying exactly that error.

Behavior for Null and Empty Strings

The rules in this section apply to the default validate_or_error(data) call.

Required-choice behavior (allow_null=False)

When allow_null is omitted or is False, a Choice is non-nullable.

  • Validation of None must fail with:

    ValidationError(text="May not be null.", code="null")

  • When the empty string "" is not one of the configured choice values, validating it must fail with:

    ValidationError(text="This field is required.", code="required")

    Specifically:

    validator = typesystem.Choice(
    choices=[("R", "red"), ("B", "blue"), ("G", "green")]
)
value, error = validator.validate_or_error("")
# value is None
# error == ValidationError(text="This field is required.", code="required")

  • Any other value that goes unmatched fails with the "choice" error described above.

Both the null-input error and the general invalid-choice error are distinct from the required empty-string error.

Nullable-choice behavior (allow_null=True)

With a nullable Choice:

  • Validation of None succeeds with (None, None).
  • When "" is not a configured choice value, validating "" treats it as null and succeeds with (None, None).
  • When "" is a configured choice value, validating "" succeeds with the actual configured value and returns ("", None) instead of converting it to None.
  • Even when "" is configured as a valid choice, None remains null. Validating None in that case still returns (None, None).
  • Any non-empty unmatched value still fails with ValidationError(text="Not a valid choice.", code="choice").

As an example:

nullable = typesystem.Choice(
    choices=[("R", "red"), ("B", "blue")],
    allow_null=True,
)
assert tuple(nullable.validate_or_error(None)) == (None, None)
assert tuple(nullable.validate_or_error("")) == (None, None)

with_empty_choice = typesystem.Choice(
    choices=[("", "empty"), ("R", "red")],
    allow_null=True,
)
assert tuple(with_empty_choice.validate_or_error("")) == ("", None)
assert tuple(with_empty_choice.validate_or_error(None)) == (None, None)

Contract for Validation Errors

It must be possible to construct ValidationError with the keyword arguments text and code:

ValidationError(text="This field is required.", code="required")

Two ValidationError instances that share the same text and code must compare equal. Throughout this specification, all message text, capitalization, punctuation, and error codes are exact.

Scope and Compatibility

  • Choice options keep using (value, label) tuples; validation is based on value, not on label.
  • Successful validation must preserve the configured value that was selected, including the empty string when it is explicitly configured.
  • Accepting null must not treat None as the same thing as an explicitly configured empty-string value.
  • The behavior that already exists for other fields, schemas, forms, validation results, and error interfaces must remain unchanged.

Task Description

Build a positional tokenization subsystem that parses JSON and YAML text into a token tree recording the source position (character index, line, and column) of every value and key, together with validation entry points that produce diagnostics annotated with positional information.

1. Value types for positions and messages (typesystem.base)

Position

Position is a value object constructed via Position(line_no, column_no, char_index); all three arguments must also work as keyword arguments. It exposes the attributes line_no, column_no, and char_index.

  • line_no is a line number counted from 1.

  • column_no is a column number counted from 1.

  • char_index is an offset into the source string counted from 0.

  • Two Position instances are equal when all three of their attributes are equal.

  • repr(Position(line_no=1, column_no=1, char_index=0)) must be exactly:

    "Position(line_no=1, column_no=1, char_index=0)"
Message

Message stays the value object for a single diagnostic. Its usual keyword arguments are text (a string), code (a string), and the optional index (a list). It must also support both of the positional-information shapes below:

  • Single-position variant: Message(text=..., code=..., position=<Position>)
  • Range variant: Message(text=..., code=..., index=[...], start_position=<Position>, end_position=<Position>)

The pre-existing positionless form, Message(text=..., code=..., index=...), must continue to be supported. In particular, leaving out index preserves the existing empty-index behavior, the representation of a positionless message remains Message(text='...', code='...'), and a non-empty index is represented as index=[...].

Equality takes text, code, index, and the supplied positional information into account. repr must show the applicable fields in this order: text, code, index when supplied, followed by either position or start_position and end_position.

The following examples are required:

Message(text='No content.', code='no_content', position=Position(line_no=1, column_no=1, char_index=0))

as well as:

Message(text='Must be a number.', code='type', index=['b'], start_position=Position(line_no=3, column_no=10, char_index=27), end_position=Position(line_no=3, column_no=14, char_index=31))

The existing behavior of the positionless Message, together with the existing behavior and representations of ValidationError and ValidationResult, must stay compatible.

2. The token tree (typesystem.tokenize.tokens)

Parsed values are represented by three token classes. Every token stores its parsed Python value along with two 0-based character offsets into the original source: start_index, the index of the first character in the token's textual span, and end_index, the index of the last character in that span, inclusive.

The constructors:

  • ScalarToken(value, start_index, end_index) — a leaf token standing for a string, number, boolean, or None.
  • DictToken(value, start_index, end_index) — here value is a dictionary that maps ScalarToken keys to child tokens.
  • ListToken(value, start_index, end_index) — here value is a list whose entries are child tokens.

These constructor forms must stay directly usable. Tokens returned by a tokenizer must also retain knowledge of the original content, so that source substrings and positions can be computed. The manner in which that association is represented is not prescribed.

Shared token behavior
  • token.value returns the plain Python value in fully materialized form, obtained by recursively unwrapping the token tree. For a DictToken this is a plain dictionary whose keys are the scalar key values and whose values are the recursively unwrapped child values. For a ListToken it is a plain list. For a ScalarToken it is the scalar value.
  • token.string is exactly the source substring content[start_index:end_index + 1].
  • token.start is the Position that corresponds to start_index.
  • token.end is the Position that corresponds to end_index.
  • For each returned position, char_index is equal to the corresponding token index. Line 1, column 1 corresponds to character index 0. A newline increments the line number, and the first character on each new line is column 1.
  • Two tokens are equal when they belong to the same class, have equal token structure, and have equal start_index and end_index. Nested tokens are compared recursively, their own spans included.
Lookups within containers
  • token.lookup(path) accepts a list of keys and/or indices. It walks down through a DictToken by matching each requested key against a key token's scalar value, and through a ListToken by integer index. It returns the child value token located at the addressed path.
  • token.lookup_key(path) walks down in the same manner, but the final path component must address a dictionary entry. It returns the entry's ScalarToken key rather than its value token. For a JSON string key, the token's string includes the surrounding quotes, while its value is the decoded, unquoted key. As an example, the key token for "a" has string == '"a"' and value == "a".
How a DictToken is represented

repr(dict_token) must take the form DictToken('<exact source string for the whole token>'). For example:

DictToken('{"a": [1, 2, 3], "b": "test"}')

tokenize_json(content)

Given a JSON document string, parse it and return its root DictToken, ListToken, or ScalarToken. Every end_index is inclusive.

The required span behavior is defined by the following inputs:

  • For '{"a": [1, 2, 3], "b": "test"}', the root is a DictToken covering indices 0..28. Key "a" is ScalarToken("a", 1, 3), and its value is a list covering 6..14 with elements ScalarToken(1, 7, 7), ScalarToken(2, 10, 10), and ScalarToken(3, 13, 13). Key "b" is ScalarToken("b", 17, 19), and its value is ScalarToken("test", 22, 27).
  • For '[true, false, null]', the root is a ListToken covering 0..18 and holding ScalarToken(True, 1, 4), ScalarToken(False, 7, 11), and ScalarToken(None, 14, 17).

The top-level typesystem package must still expose Integer, Object, and Schema.

  • Object(properties=<validator>) validates a mapping, applying the supplied validator to every property value.

Task Specification: Rendering Password Fields in Forms

Summary

Your task is to modify the form rendering behavior in the typesystem package so that string fields declared with a password format are rendered as password input elements, and so that the values of password fields are never emitted into the rendered HTML.

Public API

The API below is used and must be supported:

  • typesystem.Schema — base class used to define schemas.
  • typesystem.String(max_length=..., format="password") — the String field must accept a format keyword argument. If format="password" is specified, the field represents a password input.
  • typesystem.Text() — a text field.
  • typesystem.Choice(choices=[...]) — a choice field.
  • typesystem.Jinja2Forms(package="typesystem") — a forms renderer that is constructed with a package keyword argument. Instances must provide a way to produce an HTML form for a given schema (that is, the same mechanism already used for rendering forms of other field types).

Behavior Requirements

When a schema that contains a String field with format="password" is rendered as an HTML form:

  1. An <input> element whose type attribute is "password" must be used to render the password field (that is, the output contains <input type="password").

  2. The password input that is rendered must be marked as required and must have an empty value. In concrete terms, the output must contain the substring required value=""> for the password input. The password field's value must not be populated into the rendered HTML — the field renders with an empty value regardless of any underlying data.

  3. The rendering of other field types must remain unchanged:

    • A boolean field is rendered as exactly one <input type="checkbox" element.
    • A plain String field (no password format) is rendered as exactly one <input type="text" element.
    • A Text field is rendered as exactly one <textarea element.
    • A Choice field is rendered as exactly one <select element.

Notes

  • The password rendering behavior should affect only fields declared with format="password". Ordinary string fields must continue to be rendered as text inputs.

Overview

There are two requirements here: you must implement a new Union field type in the type system's field module, and you must ensure that password-formatted string fields do not leak their values into rendered HTML forms.

Part 1: The Union Field

Module Placement and Import

Create a new class called Union inside the module typesystem.fields. It must be possible to import it as:

from typesystem.fields import Union

It should behave like the other field validators in that module (e.g. Integer, String), exposing a validate_or_error(value) method that returns a two-tuple (value, error) in which exactly one of the two elements is meaningful: on success error is None; on failure value is None and error is a ValidationError.

The Constructor
Union(any_of, allow_null=False, ...)
  • any_of: a list of field validator instances (e.g. [Integer(), String()]). These are the candidate types against which the union will attempt to validate.
  • allow_null: a boolean keyword argument (default False) that follows the same convention as the other fields.
Behavior of Validation

Given an input value, validate_or_error must attempt to validate it against each validator in any_of, in the order given:

  1. Successful match: If validation succeeds against any of the candidate validators, return (validated_value, None), taking the result from the first candidate that succeeds.

    • Example: with Union(any_of=[Integer(), String()]), the string "abc" validates as a string, returning ("abc", None); the integer 123 validates as an integer, returning (123, None).

  2. Handling of null:

    • If the input is None and null is permitted by neither the candidate validators nor the Union itself, the result must be an error: ValidationError(text="May not be null.", code="null").
    • If None is passed and at least one candidate validator permits null (e.g. Integer(allow_null=True)), None is accepted, so return (None, None).
    • If None is passed and the Union itself was constructed with allow_null=True, then None is accepted: return (None, None).

  3. No match: If the value is not None and fails to match any candidate validator, the result must be: ValidationError(text="Did not match any valid type.", code="union")

    • Example: with Union(any_of=[Integer(), String()]), the boolean True matches neither an integer nor a string, and this "union" error is produced.

  4. Single-candidate constraint errors: When exactly one candidate validator is the appropriate type match, yet the value fails to satisfy a specific constraint of that validator, the error returned must be that validator's own specific constraint error rather than the generic union error.

    • Example: with Union(any_of=[Integer(maximum=1000), String()]), the integer 9999 is an integer (so it matches the type of the Integer candidate) but exceeds the maximum. The error that must be returned is ValidationError(text="Must be less than or equal to 1000.", code="maximum").
The Error Type

ValidationError is the error type that already exists and is used throughout the type system. Errors are compared by their text and code values.

Part 2: Rendering of Password Fields

The values submitted to password-formatted string fields must not be exposed in rendered form HTML.

If a form is rendered with a value supplied for a schema field defined as typesystem.String(format="password"), the rendered HTML must not contain that field's plaintext value.

Example: a form rendered for a schema that has a password = typesystem.String(format="password") field, with the value "secret" given for that field, must produce HTML in which the substring "secret" does not appear.

Text-formatted and other input types are unaffected; the value of password-format fields is the only one that must be suppressed from the rendered output.

Task: Implementing JSON Schema Conversion for Numeric Range Keywords

Goal

The aim is to add a function that takes a JSON Schema document and converts it into a typesystem validator object, with support for the numeric range validation keywords minimum, maximum, exclusiveMinimum, and exclusiveMaximum.

Public API

Create a module located at typesystem/json_schema.py that exposes the following callable:

def from_json_schema(schema):
    ...
  • Input: schema — a JSON Schema value. In this task, the schema will always be a JSON object (a dict) that may contain the keys minimum, maximum, exclusiveMinimum, and/or exclusiveMaximum, with each of them mapped to a numeric value.
  • Output: a validator object.

Requirements for the Validator Object

The validator returned by the function must provide a method:

def validate_or_error(self, value, strict=False):
    ...

A call to this method returns a two-tuple (value, error):

  • If value satisfies the schema, error must be None.
  • If value does not satisfy the schema, error must be a non-None object.

A keyword argument strict (which will be passed as True) must be accepted by the method. It is required to be present in the signature.

Semantics of Validation

Only numeric input values (integers and floats) are subject to the schema keywords. For any input value that is not a number, these keywords are all ignored and the value is regarded as valid (error is None).

When the input value is numeric, each keyword that is present constrains the value in the following way:

  • minimum: N — the value is valid only when value >= N. Values equal to N are valid; values below N are invalid.
  • maximum: N — the value is valid only when value <= N. Values equal to N are valid; values above N are invalid.
  • exclusiveMinimum: N — the value is valid only when value > N. Values equal to N are invalid, and values below N are invalid as well.
  • exclusiveMaximum: N — the value is valid only when value < N. Values equal to N are invalid, and values above N are invalid as well.

The keyword values may be floating-point numbers (e.g. 3.0, 1.1); in addition, the comparisons must work correctly against both integer and float input values.

Examples of the Expected Behavior

  • For the schema {"maximum": 3.0}: input 2.6 → valid; input 3.0 → valid; input 3.5 → invalid; input "x" → valid (the non-number is ignored).
  • For the schema {"minimum": 1.1}: input 2.6 → valid; input 1.1 → valid; input 0.6 → invalid; input "x" → valid.
