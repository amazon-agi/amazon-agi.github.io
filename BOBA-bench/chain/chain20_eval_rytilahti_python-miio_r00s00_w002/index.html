Task Specification: Air Humidifier Firmware and Strong Mode Support

Overview

You will modify the AirHumidifier device support in the miio package. The changes involve extending the AirHumidifierStatus class to accept and expose device firmware information, and adding a new status property.

Required Changes

1. AirHumidifierStatus Constructor Signature

The AirHumidifierStatus class (in miio/airhumidifier.py) must accept a second constructor argument carrying device information:

AirHumidifierStatus(data, device_info)
  • data — the existing dictionary of raw device state values (unchanged from current behavior).
  • device_info — an instance of DeviceInfo (from miio.device), providing firmware details.

The device_info argument must be stored so it can be used by the new firmware-related properties described below.

2. New Properties on AirHumidifierStatus

Add the following read-only properties:

  • firmware_version → returns the full firmware version string from the provided DeviceInfo (i.e., device_info.firmware_version).

  • firmware_version_major → returns the portion of the firmware version string before the last underscore. Concretely: split firmware_version on the last _ and return the left part. For example, '1.2.9_5033' yields '1.2.9'.

  • firmware_version_minor → returns the portion of the firmware version string after the last underscore, converted to an integer. For example, '1.2.9_5033' yields 5033.

  • strong_mode_enabled → returns a boolean. Given the raw device state used in these tests (which contains no strong-mode key), this property must evaluate to False.

3. Wiring the Status Object

The AirHumidifier.status() method must construct AirHumidifierStatus with two arguments: the raw device state dictionary and a DeviceInfo object obtained via the device's info retrieval mechanism (the miIO.info command).

DeviceInfo Reference

The DeviceInfo class lives in miio.device and is constructed from a dictionary of device information. It exposes a firmware_version property returning the fw_ver value from that dictionary. A representative info dictionary looks like:

{
    'fw_ver': '1.2.9_5033',
    'token': '68ffffffffffffffffffffffffffffff',
    'otu_stat': [101, 74, 5343, 0, 5327, 407],
    'mmfree': 228248,
    'netif': {'gw': '192.168.0.1', 'localIp': '192.168.0.25', 'mask': '255.255.255.0'},
    'ott_stat': [0, 0, 0, 0],
    'model': 'zhimi.humidifier.v1',
    'cfg_time': 0,
    'life': 575661,
    'ap': {'rssi': -35, 'ssid': 'ap', 'bssid': 'FF:FF:FF:FF:FF:FF'},
    'wifi_fw_ver': 'SD878x-14.76.36.p84-702.1.0-WM',
    'hw_ver': 'MW300',
    'ot': 'otu',
    'mac': '78:11:FF:FF:FF:FF'
}

Constraints

  • All existing AirHumidifierStatus properties (power state, temperature, humidity, mode, LED brightness, child lock, target humidity, hardware version, button pressed, etc.) must continue to behave as before.
  • The public symbols AirHumidifier, OperationMode, LedBrightness, AirHumidifierStatus, and AirHumidifierException must remain importable from miio.airhumidifier, and AirHumidifier from miio.
  • DeviceInfo must remain importable from miio.device.
  • The repr() of an AirHumidifierStatus object must remain consistent (equal reprs for objects built from equivalent data and device info).

Task Specification: AirHumidifier Model-Aware Status

Module and scope

Extend miio/airhumidifier.py so that Xiaomi air-humidifier status retrieval is aware of the selected device model. The V1 and CA1 models have different status-property sets, and unsupported properties may be omitted from a device response rather than returned as placeholders. Status values must therefore remain correctly associated with their property names for both models.

Required public API

The miio.airhumidifier module must export these importable names:

  • AirHumidifier — the device class; it must remain re-exported by the top-level miio package.
  • AirHumidifierStatus — the status container.
  • AirHumidifierException — the device-specific exception.
  • OperationMode — the operating-mode enum.
  • LedBrightness — the LED-brightness enum.
  • MODEL_HUMIDIFIER_V1 — the string "zhimi.humidifier.v1".
  • MODEL_HUMIDIFIER_CA1 — the string "zhimi.humidifier.ca1".

The two model constants must be distinct.

Enums

OperationMode must support the device mode strings through normal enum construction. It includes at least the following members and values:

  • OperationMode.Silent.value == "silent"
  • OperationMode.Medium.value == "medium"
  • OperationMode.High.value == "high"

Existing Auto ("auto") and Strong ("strong") modes must remain supported. In particular, OperationMode(raw_mode) must succeed for supported mode strings returned by the device.

LedBrightness has these members and integer values:

  • LedBrightness.Bright.value == 0
  • LedBrightness.Dim.value == 1
  • LedBrightness.Off.value == 2

LedBrightness(raw_value) must therefore accept the corresponding integer values reported by a device.

Model selection and status-profile resolution

An AirHumidifier instance has a model attribute whose supported values are MODEL_HUMIDIFIER_V1 and MODEL_HUMIDIFIER_CA1. The device's status() operation must use this attribute to choose the properties requested from the physical device.

AirHumidifierStatus must remain directly constructible with exactly the raw state mapping and device information as its two positional arguments:

AirHumidifierStatus(data, device_info)

Here, device_info is a miio.device.DeviceInfo object. It supplies firmware information, but its model field is not authoritative for status-property applicability. A device can report a stale or different model identifier in its information response. Consequently:

  • Model-specific status availability must be resolved from the shape of the raw state itself.
  • Presence of trans_level and button_pressed identifies available V1-specific values.
  • Presence of speed, depth, and dry identifies available CA1-specific values.
  • A missing model-specific key is unavailable and its public property returns None; accessing it must not raise a missing-key error.
  • DeviceInfo.model must neither suppress model-specific values that are present in the raw state nor manufacture values for keys that are absent.

Thus, a CA1-shaped state must expose CA1 values even when device_info.model says zhimi.humidifier.v1. A status constructed directly from a normal V1- or CA1-shaped raw state must expose the same property values and representation as the status produced from that state by AirHumidifier.status().

AirHumidifier.status()

status() queries the device with get_prop, obtains or reuses the associated DeviceInfo, and returns an AirHumidifierStatus.

Because unsupported requested properties can be omitted entirely from a response, rather than represented by None at their original positions, status() must issue a model-specific request. It must not issue one union request containing the properties of both models. The requested property sequence is:

For MODEL_HUMIDIFIER_V1:

power, mode, temp_dec, humidity, buzzer, led_b, child_lock, limit_hum,
trans_level, use_time, button_pressed, hw_version

For MODEL_HUMIDIFIER_CA1:

power, mode, temp_dec, humidity, buzzer, led_b, child_lock, limit_hum,
speed, depth, dry, use_time, hw_version

In particular, a V1 request must not include speed, depth, or dry, and a CA1 request must not include trans_level or button_pressed. Returned positional values must remain paired with the property names that were actually requested, so omission of an unsupported field cannot shift use_time, hw_version, or any other later value onto the wrong name.

Device commands

The following methods remain available. Each sends the named miIO command with a one-element parameter list as described, and a later status() must reflect the changed state.

  • on() sends set_power with ["on"]; afterward status().is_on is True.
  • off() sends set_power with ["off"]; afterward status().is_on is False.
  • set_mode(mode) accepts an OperationMode member and sends set_mode with [mode.value]; afterward status().mode is that member.
  • set_led_brightness(brightness) accepts a LedBrightness member and sends set_led_b with [brightness.value]; afterward status().led_brightness is that member.
  • set_buzzer(enabled) sends set_buzzer with ["on"] for True and ["off"] for False; afterward status().buzzer is the corresponding boolean.
  • set_child_lock(enabled) sends set_child_lock with ["on"] for True and ["off"] for False; afterward status().child_lock is the corresponding boolean.
  • set_target_humidity(humidity) sends set_limit_hum with [humidity] for a valid target; afterward status().target_humidity is that integer.
  • set_dry(enabled) sends set_dry with ["on"] for True and ["off"] for False. This control is used by CA1, and afterward its status().dry is the corresponding boolean.

The status query itself uses get_prop with the model-specific property list above.

Target-humidity validation

The only valid target humidity values are the integers 30, 40, 50, 60, 70, and 80. Every other value—including values below 30, above 80, or between the accepted ten-point steps—must raise AirHumidifierException rather than send an invalid setting. Examples of invalid values include -1, 20, 35, 90, and 110.

AirHumidifierStatus properties

All properties below are read-only.

Common state properties
  • power returns the raw state["power"] string.
  • is_on is True exactly when power == "on"; otherwise it is False.
  • temperature returns state["temp_dec"] / 10.0. If temp_dec is None, it returns None.
  • humidity returns state["humidity"].
  • mode returns OperationMode(state["mode"]).
  • led_brightness returns LedBrightness(state["led_b"]). If led_b is None, it returns None.
  • buzzer is True exactly when state["buzzer"] == "on"; otherwise it is False.
  • child_lock is True exactly when state["child_lock"] == "on"; otherwise it is False.
  • target_humidity returns state["limit_hum"].
  • use_time returns state["use_time"].
  • hardware_version returns state["hw_version"]; this is the status-state value and is distinct from the hardware information in DeviceInfo.
Model-specific state properties

For a normal V1-shaped state:

  • trans_level returns state["trans_level"].
  • button_pressed returns state["button_pressed"].
  • speed, depth, and dry return None because their keys are unavailable.

For a normal CA1-shaped state:

  • speed returns state["speed"].
  • depth returns state["depth"].
  • If the dry key is available, dry is True exactly when its value is "on" and is False for other available values such as "off". If the key is absent, dry returns None.
  • trans_level and button_pressed return None because their keys are unavailable.

These results are based on raw-state availability, not on DeviceInfo.model. Values for an available key must remain visible even when that information object's model string names the other humidifier model.

Firmware-derived properties

These properties use the supplied DeviceInfo:

  • firmware_version returns device_info.firmware_version.
  • firmware_version_major returns everything before the final underscore in the firmware version. For example, "1.2.9_5033" produces "1.2.9".
  • firmware_version_minor parses the portion after the final underscore as an integer. For example, "1.2.9_5033" produces 5033.
  • strong_mode_enabled reports whether strong operation is indicated by firmware and state. It is True on firmware minor version 25 when trans_level == 90; on firmware minor versions greater than 25 it is True when the operation mode is OperationMode.Strong. It is False otherwise. In particular, an ordinary medium state with firmware 1.2.9_5033 reports False.

Representation consistency

AirHumidifierStatus must implement __repr__ and include its resolved status values consistently. Equal raw states paired with equivalent DeviceInfo values must produce identical representations. More specifically, for either supported state shape, the representation returned by AirHumidifier.status() must equal the representation of AirHumidifierStatus(raw_state, device_info) built directly from the same state and information—even when the model string inside DeviceInfo does not match the state shape.

07 Philips Moonlight RGB API Parameter Fix 537 words · source specification

Task Specification: Philips Moonlight RGB API Parameter Fix

Overview

You must modify the Philips Moonlight device driver and a shared utility module so that RGB values are correctly encoded when sent to the device, and add a supporting utility function.

Utility Function

In the module miio/utils.py, there is an existing function int_to_rgb. You must add a complementary function:

def rgb_to_int(rgb: Tuple[int, int, int]) -> int

Behavior: Given a 3-tuple (red, green, blue) of integer channel values, encode it into a single integer by packing the channels: red in the highest 8 bits, green in the middle 8 bits, blue in the lowest 8 bits. Concretely, the result is (red << 16) | (green << 8) | blue.

This function must be importable as from miio.utils import rgb_to_int and is the exact inverse of the existing int_to_rgb.

Philips Moonlight Device Changes

The affected code is in miio/philips_moonlight.py, exposing the class PhilipsMoonlight (also importable as PhilipsMoonlight from the top-level miio package), plus the supporting classes PhilipsMoonlightStatus and PhilipsMoonlightException (importable from miio.philips_moonlight).

Two methods that send RGB data must be changed to encode RGB as a single packed integer via rgb_to_int:

1. set_rgb

When setting the RGB color, the driver must call the device's set_rgb command with a payload consisting of a single-element list containing the integer-encoded RGB value.

  • Input: an RGB color as a 3-tuple (red, green, blue).
  • The value passed to the device command must be [rgb_to_int((red, green, blue))] — i.e., the three channels packed into one integer, wrapped in a list.
2. set_brightness_and_rgb

Signature:

def set_brightness_and_rgb(self, brightness: int, rgb: Tuple[int, int, int])

This method sets both the RGB color and the brightness in a single device command. The relevant device command is set_brirgb. The payload sent to that command must be an ordered list of exactly four elements:

  1. The integer-encoded RGB value (rgb_to_int(rgb)),
  2. followed by the brightness value.

That is, the payload is [rgb_to_int((r, g, b)), brightness], where the RGB integer comes first and the brightness comes last.

Validation / Error Conditions

set_brightness_and_rgb must validate the RGB channel values. If any of the red, green, or blue channel values is outside the valid range of 0–255 inclusive (for example a channel value of 256), the method must raise PhilipsMoonlightException and must not send any command.

Summary of Payload Encoding

  • set_rgb((r, g, b)) → device command set_rgb with argument [rgb_to_int((r, g, b))].
  • set_brightness_and_rgb(brightness, (r, g, b)) → device command set_brirgb with argument [rgb_to_int((r, g, b)), brightness].

Where rgb_to_int((r, g, b)) == (r << 16) | (g << 8) | b.
