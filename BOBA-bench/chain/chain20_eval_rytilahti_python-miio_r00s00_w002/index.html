01 Firmware and Strong Mode Support for the Air Humidifier 446 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Firmware and Strong Mode Support for the Air Humidifier

Summary

Your task is to modify the AirHumidifier device support in the miio package. The changes consist of extending the AirHumidifierStatus class so it accepts and exposes device firmware information, and of adding a new status property.

Required Modifications

1. Constructor Signature of AirHumidifierStatus

The AirHumidifierStatus class (located in miio/airhumidifier.py) must accept a second constructor argument that carries device information:

AirHumidifierStatus(data, device_info)
  • data — the existing dictionary of raw device state values (it stays unchanged from current behavior).
  • device_info — an instance of DeviceInfo (from miio.device) that provides the firmware details.

The device_info argument must be stored so that the new firmware-related properties described below can use it.

2. New Properties of AirHumidifierStatus

Add these read-only properties:

  • firmware_version → returns the full firmware version string from the supplied DeviceInfo (that is, device_info.firmware_version).

  • firmware_version_major → returns the part of the firmware version string before the last underscore. To be concrete: split firmware_version on the last _ and return the left part. As an example, '1.2.9_5033' yields '1.2.9'.

  • firmware_version_minor → returns the part of the firmware version string after the last underscore, converted to an integer. As an example, '1.2.9_5033' yields 5033.

  • strong_mode_enabled → returns a boolean. With the raw device state used in these tests (which has no strong-mode key), this property must evaluate to False.

3. Constructing the Status Object

The AirHumidifier.status() method must construct AirHumidifierStatus passing two arguments: the raw device state dictionary together with a DeviceInfo object that is obtained via the device's info retrieval mechanism (the miIO.info command).

DeviceInfo Background

The DeviceInfo class resides in miio.device and is constructed from a dictionary of device information. It exposes a firmware_version property that returns the fw_ver value from that dictionary. A typical info dictionary looks like this:

{
    'fw_ver': '1.2.9_5033',
    'token': '68ffffffffffffffffffffffffffffff',
    'otu_stat': [101, 74, 5343, 0, 5327, 407],
    'mmfree': 228248,
    'netif': {'gw': '192.168.0.1', 'localIp': '192.168.0.25', 'mask': '255.255.255.0'},
    'ott_stat': [0, 0, 0, 0],
    'model': 'zhimi.humidifier.v1',
    'cfg_time': 0,
    'life': 575661,
    'ap': {'rssi': -35, 'ssid': 'ap', 'bssid': 'FF:FF:FF:FF:FF:FF'},
    'wifi_fw_ver': 'SD878x-14.76.36.p84-702.1.0-WM',
    'hw_ver': 'MW300',
    'ot': 'otu',
    'mac': '78:11:FF:FF:FF:FF'
}

Constraints

  • All existing AirHumidifierStatus properties (power state, temperature, humidity, mode, LED brightness, child lock, target humidity, hardware version, button pressed, etc.) must keep behaving as before.
  • The public symbols AirHumidifier, OperationMode, LedBrightness, AirHumidifierStatus, and AirHumidifierException must still be importable from miio.airhumidifier, and AirHumidifier must still be importable from miio.
  • DeviceInfo must still be importable from miio.device.
  • The repr() of an AirHumidifierStatus object must remain consistent (objects built from equivalent data and device info must produce equal reprs).
02 Model-Aware Status for AirHumidifier 1348 words · rewritten by GPT-5.6-sol, reworded by GLM-5.3-Flash

Task Specification: Model-Aware Status for AirHumidifier

Module and scope of the change

Modify miio/airhumidifier.py so that retrieving status from Xiaomi air humidifiers takes the selected device model into account. The V1 and CA1 models expose different sets of status properties, and a device response may leave unsupported properties out entirely instead of returning placeholder values. For both models, status values must therefore stay correctly associated with the property names they belong to.

Public API requirements

These importable names must be exported by the miio.airhumidifier module:

  • AirHumidifier — the class representing the device; the top-level miio package must continue to re-export it.
  • AirHumidifierStatus — the container holding status.
  • AirHumidifierException — the exception specific to this device.
  • OperationMode — the enum of operating modes.
  • LedBrightness — the enum for LED brightness.
  • MODEL_HUMIDIFIER_V1 — the string "zhimi.humidifier.v1".
  • MODEL_HUMIDIFIER_CA1 — the string "zhimi.humidifier.ca1".

The two model constants must differ from each other.

Enumerations

OperationMode must support construction in the normal way from the device mode strings. It has at least the following members and values:

  • OperationMode.Silent.value == "silent"
  • OperationMode.Medium.value == "medium"
  • OperationMode.High.value == "high"

The existing modes Auto ("auto") and Strong ("strong") must continue to be supported. Specifically, OperationMode(raw_mode) must succeed for supported mode strings returned by the device.

LedBrightness has these members and integer values:

  • LedBrightness.Bright.value == 0
  • LedBrightness.Dim.value == 1
  • LedBrightness.Off.value == 2

Consequently, LedBrightness(raw_value) must accept the corresponding integer values that a device reports.

Choosing the model and resolving the status profile

An AirHumidifier instance carries a model attribute; the values supported for it are MODEL_HUMIDIFIER_V1 and MODEL_HUMIDIFIER_CA1. The status() operation of the device must use this attribute to choose which properties get requested from the physical device.

It must still be possible to construct AirHumidifierStatus directly with exactly two positional arguments, the raw state mapping and the device information:

AirHumidifierStatus(data, device_info)

In that call, device_info is a miio.device.DeviceInfo object. It provides firmware information, but its model field is not the authority on which status properties apply. Within its information response, a device can report a model identifier that is stale or differs. As a result:

  • Which model-specific status values are available must be resolved from the shape of the raw state itself.
  • The presence of trans_level and button_pressed signals that V1-specific values are available.
  • The presence of speed, depth, and dry signals that CA1-specific values are available.
  • When a model-specific key is missing, it is unavailable, and its public property returns None; accessing it must not raise a missing-key error.
  • DeviceInfo.model must not suppress model-specific values that are present in the raw state, and it must not manufacture values for keys that are absent.

Therefore, a state shaped like CA1 must expose the CA1 values even when device_info.model says zhimi.humidifier.v1. A status built directly from a normal raw state shaped like V1 or CA1 must expose the same property values and the same representation as the status that AirHumidifier.status() produces from that state.

AirHumidifier.status()

The status() method queries the device using get_prop, obtains or reuses the associated DeviceInfo, and returns an AirHumidifierStatus.

Since a response can omit unsupported requested properties entirely rather than represent them with None at their original positions, status() must issue a model-specific request. It must not issue one union request that contains the properties of both models. The sequence of requested properties is:

For MODEL_HUMIDIFIER_V1:

power, mode, temp_dec, humidity, buzzer, led_b, child_lock, limit_hum,
trans_level, use_time, button_pressed, hw_version

For MODEL_HUMIDIFIER_CA1:

power, mode, temp_dec, humidity, buzzer, led_b, child_lock, limit_hum,
speed, depth, dry, use_time, hw_version

Specifically, speed, depth, or dry must not be included in a V1 request, and trans_level or button_pressed must not be included in a CA1 request. The positional values that come back must remain paired with the property names that were actually requested, so that an omitted unsupported field cannot shift use_time, hw_version, or any later value onto the wrong name.

Commands sent to the device

The methods that follow remain available. Each sends the named miIO command with the one-element parameter list described, and a later status() must reflect the changed state.

  • on() sends set_power with ["on"]; afterwards, status().is_on is True.
  • off() sends set_power with ["off"]; afterwards, status().is_on is False.
  • set_mode(mode) accepts an OperationMode member and sends set_mode with [mode.value]; afterwards, status().mode is that member.
  • set_led_brightness(brightness) accepts a LedBrightness member and sends set_led_b with [brightness.value]; afterwards, status().led_brightness is that member.
  • set_buzzer(enabled) sends set_buzzer with ["on"] for True and ["off"] for False; afterwards, status().buzzer is the corresponding boolean.
  • set_child_lock(enabled) sends set_child_lock with ["on"] for True and ["off"] for False; afterwards, status().child_lock is the corresponding boolean.
  • set_target_humidity(humidity) sends set_limit_hum with [humidity] for a valid target; afterwards, status().target_humidity is that integer.
  • set_dry(enabled) sends set_dry with ["on"] for True and ["off"] for False. CA1 uses this control, and afterwards its status().dry is the corresponding boolean.

The status query itself uses get_prop with the model-specific property list shown above.

Validation of the target humidity

The integers 30, 40, 50, 60, 70, and 80 are the only valid target humidity values. Any other value—including values below 30, above 80, or between the accepted ten-point steps—must raise AirHumidifierException instead of sending an invalid setting. Invalid values include, for example, -1, 20, 35, 90, and 110.

Properties of AirHumidifierStatus

Every property below is read-only.

Properties of the common state
  • power returns the raw string state["power"].
  • is_on is True exactly when power == "on"; in every other case it is False.
  • temperature returns state["temp_dec"] / 10.0. It returns None if temp_dec is None.
  • humidity returns state["humidity"].
  • mode returns OperationMode(state["mode"]).
  • led_brightness returns LedBrightness(state["led_b"]). It returns None if led_b is None.
  • buzzer is True exactly when state["buzzer"] == "on"; in every other case it is False.
  • child_lock is True exactly when state["child_lock"] == "on"; in every other case it is False.
  • target_humidity returns state["limit_hum"].
  • use_time returns state["use_time"].
  • hardware_version returns state["hw_version"]; this is the value from the status state and is distinct from the hardware information in DeviceInfo.
Properties of model-specific state

With a normal state shaped like V1:

  • trans_level returns state["trans_level"].
  • button_pressed returns state["button_pressed"].
  • The properties speed, depth, and dry return None because the keys they need are unavailable.

With a normal state shaped like CA1:

  • speed returns state["speed"].
  • depth returns state["depth"].
  • When the dry key is available, dry is True exactly when its value is "on" and is False for other available values such as "off". When the key is absent, dry returns None.
  • The properties trans_level and button_pressed return None because the keys they need are unavailable.

These outcomes depend on what the raw state contains, not on DeviceInfo.model. When a key is available, its values must remain visible even if the model string in that information object names the other humidifier model.

Properties derived from the firmware

These properties use the DeviceInfo that is supplied:

  • firmware_version returns device_info.firmware_version.
  • firmware_version_major returns everything that comes before the final underscore in the firmware version. As an example, "1.2.9_5033" produces "1.2.9".
  • firmware_version_minor parses what follows the final underscore as an integer. As an example, "1.2.9_5033" produces 5033.
  • strong_mode_enabled reports whether strong operation is indicated by the firmware and state. On firmware minor version 25 it is True when trans_level == 90; on firmware minor versions greater than 25 it is True when the operation mode is OperationMode.Strong. In all other cases it is False. Notably, an ordinary medium state with firmware 1.2.9_5033 reports False.

Consistent representation

AirHumidifierStatus must implement __repr__, and its resolved status values must be included in a consistent way. When equal raw states are paired with equivalent DeviceInfo values, the representations produced must be identical. More precisely, for either supported state shape, the representation returned by AirHumidifier.status() must equal the representation of AirHumidifierStatus(raw_state, device_info) built directly from that same state and information—even when the model string inside DeviceInfo does not match the state shape.

Task Specification: Adding Socket Support to the Air Conditioning Companion V3

Overview

This task adds support for a new "V3" variant of the Xiaomi Air Conditioning Companion (AC Partner) device, a variant that includes a controllable power socket (outlet). The work extends the existing miio.airconditioningcompanion module.

Module Constants

Add a new module-level constant to miio/airconditioningcompanion.py:

  • MODEL_ACPARTNER_V3 — a string that identifies the V3 device model.

It must be possible to import this constant from miio.airconditioningcompanion.

Changes to the Status Class

The class AirConditioningCompanionStatus, which already exists in miio.airconditioningcompanion, must change how it is constructed and must also gain a new property.

Constructor

AirConditioningCompanionStatus.__init__(self, data: dict)

The constructor now takes a single dict argument that has the following keys:

  • model_and_state — required. A list of strings that represents the raw device model-and-state data (the same list that was previously passed directly to the constructor).
  • power_socket — optional. A string that gives the socket's plug state (e.g. 'on' or 'off'), or is absent/None when the device has no power socket.

All existing properties (is_on, load_power, air_condition_model, model_format, device_type, air_condition_brand, air_condition_remote, state_format, air_condition_configuration, target_temperature, swing_mode, fan_speed, mode, led, etc.) must continue to be derived by the status class from the model_and_state list, exactly as before.

New Property

power_socket — when a power_socket value was provided at construction, this returns the socket's plug state string; when it was not provided, it returns None.

  • load_power is the integer value of the list's third element (decimal).
  • air_condition_model is the raw bytes of the list's first element (from hex).
  • air_condition_configuration is the list's second element (given as a string of hex characters).
  • The model/state/temperature/mode/fan/swing/led fields are parsed from the hex strings in the same way as in the existing implementation.

A concrete example: for model_and_state = ['010507950000257301', '011001160100002573', '807'] with power_socket = 'on':

  • is_on is True
  • power_socket is 'on'
  • load_power is 807
  • air_condition_model is bytes.fromhex('010507950000257301')
  • model_format is 1
  • device_type is 5
  • air_condition_brand is 795
  • air_condition_remote is 2573
  • state_format is 1
  • air_condition_configuration is '10011601'
  • target_temperature is 22
  • swing_mode is SwingMode.Off
  • fan_speed is FanSpeed.Low
  • mode is OperationMode.Heat
  • led is True

In terms of behavior, the existing (non-V3) status must stay backwards-compatible: constructing it with only model_and_state yields power_socket is None, and all existing derived values remain unchanged (e.g. for the previous default state, is_on is False and load_power is 2).

The New Device Class

Create a new class AirConditioningCompanionV3 in miio/airconditioningcompanion.py, and make it importable from the top-level miio package (from miio import AirConditioningCompanionV3).

The class should behave as an Air Conditioning Companion device (subclassing/extending the existing companion device implementation) whose fixed model is MODEL_ACPARTNER_V3, while additionally supporting socket control and status.

Methods

status(self) -> AirConditioningCompanionStatus

This returns an AirConditioningCompanionStatus. The device builds it as follows:

  1. It queries the device model-and-state via the command get_model_and_state, which produces the model_and_state list.
  2. It queries the socket plug state via the command get_device_prop, passing parameters ['lumi.0', 'plug_state'], which produces the power_socket string.

Both the model_and_state and the power_socket value must be included in the returned status.

socket_on(self)

Switches the power socket on. This is done by sending the command toggle_plug with parameters ending in 'on' (the last element of the parameters list is 'on'). After this call, the status power_socket must read 'on'.

socket_off(self)

Switches the power socket off. This is done by sending the command toggle_plug with parameters ending in 'off' (the last element of the parameters list is 'off'). After this call, the status power_socket must read 'off'.

Notes on the Command Contract

Communication with the device goes through a send(command, parameters) mechanism (inherited). The specific commands used, and their parameter shapes, are:

  • get_model_and_state → returns the model-and-state list.
  • get_device_prop with parameters ['lumi.0', 'plug_state'] → returns the plug state string.
  • toggle_plug with parameters whose last element is 'on' or 'off' → sets the plug state accordingly.

A socket state toggled via socket_on/socket_off must be observable through the power_socket property of a subsequent status() call.

07 Philips Moonlight RGB API Parameter Fix 568 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Philips Moonlight RGB API Parameter Fix

Overview

You must modify the Philips Moonlight device driver and a shared utility module so that RGB values are encoded correctly when they are sent to the device, and you must add a supporting utility function.

Utility Function

The module miio/utils.py already contains a function int_to_rgb. You must add a function that complements it:

def rgb_to_int(rgb: Tuple[int, int, int]) -> int

Behavior: When it receives a 3-tuple (red, green, blue) of integer channel values, the function encodes it into a single integer by packing the channels: red in the highest 8 bits, green in the middle 8 bits, and blue in the lowest 8 bits. In concrete terms, the result is (red << 16) | (green << 8) | blue.

Importing it must work as from miio.utils import rgb_to_int, and it is the exact inverse of the existing int_to_rgb.

Changes to the Philips Moonlight Device

The code to be changed lives in miio/philips_moonlight.py, which exposes the class PhilipsMoonlight (also importable as PhilipsMoonlight from the top-level miio package), together with the supporting classes PhilipsMoonlightStatus and PhilipsMoonlightException (importable from miio.philips_moonlight).

The two methods that send RGB data must be changed so that RGB is encoded as a single packed integer via rgb_to_int:

1. set_rgb

When the RGB color is being set, the driver must call the device's set_rgb command with a payload made up of a single-element list holding the integer-encoded RGB value.

  • Input: an RGB color in the form of a 3-tuple (red, green, blue).
  • What gets passed to the device command must be [rgb_to_int((red, green, blue))] — i.e., the three channels packed into one integer, wrapped in a list.
2. set_brightness_and_rgb

Signature:

A complete raw snapshot may additionally contain an is_on Boolean or other keys that are unrelated. These extra keys must be accepted, but they must not alter the logical status or the way it is represented. In particular, a raw is_on value does not have the final say; the working state is derived from work_state.

Read-only properties

The class must expose the following read-only properties:

  • work_state -> int: returns the value of the raw work_state field.
  • is_on -> bool: returns False exactly when work_state == 1, which is the idle state, and returns True for work-state codes that are not idle. In particular, work state 97, which applies while nozzle cleaning is active, must report True even if the raw is_on field supplied with the data is False.
  • ambient_light -> str: returns the color name from the raw ambient_light field.
  • filter_use_percentage -> str: formats filter_use_flux with one percent sign at the end. For example, the raw value "100" produces "100%".
  • filter_remaining_time: returns the raw filter_use_time value with no change.
Status representation

repr(status) must be deterministic and must portray the exposed logical status values instead of serializing the raw dictionary as a whole. As a consequence:

  • Two instances built from raw dictionaries that are equal must have representations that are equal.
  • Two instances that expose the same status values must also have equal representations even if one raw dictionary contains extra keys and the other does not.
  • In particular, a status assembled from the properties read by Toiletlid.status() must have the same representation as a status constructed directly on the basis of a complete snapshot containing those same properties plus a stored is_on field.

The precise punctuation of the representation is not prescribed, but incidental keys that exist only in the raw data must not affect it.

Toiletlid

Toiletlid must inherit from the common miio device base class and must remain compatible with that class's standard connection and send behavior. It must have a settable model attribute; MODEL_TOILETLID_V1 serves as its default.

status() -> ToiletlidStatus

The current state is fetched by means of the get_prop command. Request the following properties, in this order:

  1. work_state
  2. ambient_light
  3. filter_use_flux
  4. filter_use_time

Take the values that come back, map them to those property names, and return a ToiletlidStatus. A separate is_on property must neither be requested nor depended upon: ToiletlidStatus.is_on must be computed from the work_state that is returned.

For an idle state such as the following:

  • work_state = 1
  • ambient_light = "Yellow"
  • filter_use_flux = "100"
  • filter_use_time = "180"

the result must report is_on is False together with ambient_light == "Yellow", filter_use_percentage == "100%", and filter_remaining_time == "180".

nozzle_clean()

The nozzle_clean command is sent to the device with its normal empty command payload. A nozzle-clean operation that succeeds leaves the device in an active work state. If the reported work_state becomes 97, a later status().is_on must therefore be True; no separate transition of a raw is_on value is required.

set_ambient_light(color: AmbientLightColor)

The set_aled_v_of_uid command is used to set the ambient-light color. The payload sent with the command must be a two-element list, in this order:

[user_id, color.value]

color is a member of AmbientLightColor, and the protocol value that is sent to the device must be that member's .value. After a set that succeeds, a later status().ambient_light must equal color.name. This must hold for every member that AmbientLightColor declares.

The device protocol also supports get_aled_v_of_uid: when it is given a user ID, it returns the current protocol color value. Ambient-light writes and reads must be mutually consistent, so that reading after a member has been set yields that same member's value.

Protocol and Behavior Summary

  • Status retrieval relies on get_prop, and the on/working indicator is derived solely from work_state.
  • Work state 1 counts as idle/off; work states that are not idle, including nozzle-clean state 97, count as working/on.
  • Nozzle cleaning is performed with nozzle_clean.
  • Ambient-light writes go through set_aled_v_of_uid with [user_id, color_value]; protocol readback goes through get_aled_v_of_uid with a user ID.
  • Every valid enum color must round-trip among the enum value, the device protocol value, and the color name that status exposes.
  • Filter percentage display appends % and does not otherwise transform the raw value.
  • The status representation is built only from the exposed logical fields and is unaffected by extra raw snapshot data.

Introduce status support for the Air Quality Monitor S1 and bring the status and command behavior of the Air Dehumidifier V1 into alignment, while existing V1 compatibility is preserved.

MODEL_AIRQUALITYMONITOR_S1 must identify a model that is recognized as supported by AirQualityMonitor.status().

Behavior of the Air Dehumidifier V1

Given a dehumidifier status payload:

  • status().power indicates whether the on_off field equals "on".
  • The temp field is returned by status().temperature.
  • The humidity field is returned by status().humidity.
  • What status().mode returns is an OperationMode constructed from the mode field.
  • status().led is a Boolean whose value is equal to whether the led field equals "on".
  • status().buzzer is a Boolean whose value is equal to whether the buzzer field equals "on".
  • status().child_lock is a Boolean whose value is equal to whether the child_lock field equals "on".
  • The auto field is returned by status().target_humidity.
  • status().tank_full is a Boolean: it is True exactly when the tank_full field equals "on", and False otherwise. The raw "on" or "off" string must not be exposed by it.

Power changes performed via on() and off() must use the device command set_power, and as a consequence the on_off status field is affected.

set_target_humidity(humidity) must use the device command set_auto, passing the requested humidity, so that the auto status field reflects the new target.

For a missing or None LED field, no behavior is required here.

Behavior of the Air Quality Monitor S1

If an AirQualityMonitor has the model MODEL_AIRQUALITYMONITOR_S1, status() must return an AirQualityMonitorStatus populated from the device's get_prop response.

For an S1 payload, the following properties must return their corresponding values unchanged:

Payload field Status property
battery battery
co2 co2
humidity humidity
pm25 pm25
temperature temperature
tvoc tvoc

As an example, integer and floating-point values such as battery 100, humidity 62.1, PM2.5 19.4, and temperature 27.4 must not be rounded or otherwise transformed.

V1-specific fields may be omitted from S1 payloads. When a field is omitted:

  • status().aqi returns None.
  • status().usb_power returns None.
  • status().display_clock returns None.
  • status().night_mode returns None.

These missing values must not make status construction, property access, or representation fail. They must not be converted to False or derived from other measurements.

AirQualityMonitorStatus(data) must accept an S1 mapping directly, including a mapping that contains only the S1 fields shown above. Its representation must be deterministic and value-based: a status returned by status() and an AirQualityMonitorStatus constructed separately with the same payload must have identical repr() output.

Compatibility of the Air Quality Monitor V1

The existing V1 interpretation remains supported. Specifically:

  • usb_state == "on" maps to usb_power is True; any other present state maps to False.
  • time_state == "on" maps to display_clock is True; any other present state maps to False.
  • night_state == "on" maps to night_mode is True; any other present state maps to False.

A plain V1-style mapping may omit all of the S1-specific measurement fields: co2, humidity, pm25, temperature, and tvoc. Such a mapping must be accepted directly by AirQualityMonitorStatus(data). Accessing any omitted measurement property must return None, and computing repr() must not raise an exception. For the same V1 payload, a directly constructed status must have a representation identical to that of the status returned by AirQualityMonitor.status().

Task: Add support for the cgllc.airmonitor.b1 air quality monitor

Overview

Extend the air quality monitor support that already exists in the miio.airqualitymonitor module so that the cgllc.airmonitor.b1 device model is supported as well. Compared with the currently supported V1 and S1 models, this device reports a different set of properties, and it uses a distinct query command to fetch its state.

Required Public API

New constant at module level

Inside miio.airqualitymonitor, add a constant for the model identifier:

  • MODEL_AIRQUALITYMONITOR_B1 = "cgllc.airmonitor.b1"

It must be importable together with the existing constants:

from miio.airqualitymonitor import (
    AirQualityMonitorStatus,
    MODEL_AIRQUALITYMONITOR_V1,
    MODEL_AIRQUALITYMONITOR_S1,
    MODEL_AIRQUALITYMONITOR_B1,
)
The status class

Construction of AirQualityMonitorStatus must continue to take a single mapping argument:

AirQualityMonitorStatus(data)

with data being a dict of device properties. The class must expose the following read-only properties (all of which are already required by the existing V1/S1 behavior, plus one new one):

  • power — the value of power, or None if absent.
  • usb_power — True/False based on the usb_state value being "on", or None if absent.
  • battery — the value of battery, or None if absent.
  • aqi — the value of aqi, or None if absent.
  • temperature — the value of temperature, or None if absent.
  • humidity — the value of humidity, or None if absent.
  • co2 — the value of co2, or None if absent.
  • co2e — new: the value of co2e, or None if absent.
  • pm25 — the value of pm25, or None if absent.
  • tvoc — the value of tvoc, or None if absent.
  • display_clock — True/False based on the time_state value being "on", or None if absent.
  • night_mode — True/False based on the night_state value being "on", or None if absent.

For the B1 device, the data mapping that comes in contains keys such as:

{
    "co2e": 1466,
    "humidity": 59.79999923706055,
    "pm25": 2,
    "temperature": 19.799999237060547,
    "temperature_unit": "c",
    "tvoc": 1.3948699235916138,
    "tvoc_unit": "mg_m3",
}

With data of this kind, the status object must report:

  • power is None
  • usb_power is None
  • battery is None
  • aqi is None
  • temperature equals the temperature value
  • humidity equals the humidity value
  • co2 is None
  • co2e equals the co2e value
  • pm25 equals the pm25 value
  • tvoc equals the tvoc value
  • display_clock is None
  • night_mode is None

The repr() of a status object built directly from a data mapping must equal the repr() of a status object built from a copy of that same mapping (i.e. repr must be deterministic and depend only on the data).

  • For the B1 model (cgllc.airmonitor.b1), the device must obtain its state by issuing the command get_air_data (with no query properties). The whole mapping returned by that command is used directly to build the AirQualityMonitorStatus.
  • For the models that were supported previously, state retrieval keeps using the existing mechanism based on get_prop.

The device's status() method returns an AirQualityMonitorStatus that is built from the retrieved data.

Notes

  • The only things required are the properties and the constant named above.
