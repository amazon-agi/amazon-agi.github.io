  • Raises
  • Warns
  • Attributes

Entry rendering rules

For an entry with a name and a type, the rendered entry line is:

**name** : type

(A single space, a colon, and a single space separate the bolded name from the type.)

For an entry that has only a name and no type — this occurs when an entry represents an anonymous/type-only value (e.g. a bare return type such as list of str, int, or an exception/warning name such as RuntimeError, RuntimeWarning) — the entire name text is still wrapped in double asterisks:

Entries whose name is already an explicit reST cross-reference (for example a name of the form :obj:label <target>``) are emitted as-is and are not wrapped in double asterisks. Task Specification: Multi-Function "See Also" Block Parsing

Overview

Update numpydoc's docstring parsing and rendering so that multiple references written on one reference line in a See Also section can share one description. The parsed public value must retain those references as a group rather than flattening every reference into a separate item.

This is a deliberate change to the in-memory representation of See Also. Parsing and rendering of all other docstring sections must remain unchanged.

Parsed See Also Representation

numpydoc.docscrape.NumpyDocString parses a docstring and exposes its sections through subscript access. For example:

doc = NumpyDocString(docstring)
see_also = doc["See Also"]

doc["See Also"] must be a list of entries in input order. An empty or absent section yields an empty list. Each entry represents exactly one physical reference line and has this shape:

(funcs, desc)
  • funcs is a non-empty list of (func_name, role) 2-tuples, in the order in which the references occurred on that line.
    • func_name is the referenced name as a string.
    • role is the reStructuredText cross-reference role string, such as "meth", "obj", "class", or "func". It is None when the input reference did not specify a role.
  • desc is the single description shared by every reference in funcs. It is a list of description-line strings in source order, and is an empty, falsy list when the line has no description.

The former flat (func_name, description, role) representation must not be returned. In particular, descriptions are stored once at group level, not copied into separate per-reference entries.

See Also Parsing

Reference syntax

A non-indented reference line may contain one or more comma-separated references. Each reference can be either:

  • a bare name, such as func_name or foo.func_e; or
  • a role-decorated reStructuredText cross-reference of the form :role:`name```, such as :meth:func_h```, ``:obj:baz.obj_q or ``:class:`class_j.

A decorated reference stores the text between the backticks as func_name and the role name as role. A bare reference stores role = None.

A trailing comma is permitted. It does not create an empty reference and does not continue the group onto the next physical line.

Descriptions

A reference line can have an inline description following the references. The separator may use the spaced : form or a colon immediately following the final reference. For example:

func_f2, func_g2, :meth:`func_h2`, func_j2 : description of multiple

must produce one group containing all four references and the shared description:

(
    [("func_f2", None), ("func_g2", None),
     ("func_h2", "meth"), ("func_j2", None)],
    ["description of multiple"],
)

The separator after the final reference is distinct from the colons that form role syntax.

A description may instead, or additionally, continue on subsequent indented lines. Leading indentation used to mark continuation is removed from the stored text. For example:

func_d
    some equivalent func

produces desc == ["some equivalent func"], while:

foo.func_e
    some other func over
    multiple lines

produces desc == ["some other func over", "multiple lines"].

Inline and continuation text are combined in order. Thus:

:class:`class_j`: fubar
    foobar

produces desc == ["fubar", "foobar"].

All comma-separated references on the reference line share that entire description.

Group boundaries

Group boundaries are determined by physical reference lines:

  • Every non-indented, non-empty reference line produces exactly one parsed entry.
  • Multiple comma-separated references on that line form the funcs list of that one entry.
  • An indented description continuation belongs to the preceding reference line and does not create an entry.
  • References on different physical reference lines are never merged into one entry, even when both lines have no descriptions.
  • A line ending in a trailing comma is still complete; the next reference line starts a new entry.
  • Blank lines do not themselves create entries.

Consequently, consecutive undescribed lines remain distinct groups. A description can be shared by references on its own reference line, but never implicitly by references from another reference line.

Qualified names beginning with ~

The Sphinx shortened-display form with a leading ~ is supported for role-decorated qualified names, and the leading ~ remains part of the stored func_name. It is valid only when the ~-prefixed component is followed by a dot and another name component. For example, ``:obj:~baz.obj_r``` is valid and produces ("~baz.obj_r", "obj")`.

A role-decorated name with ~ but no dotted component, such as ``:func:~foo``` is not a valid item name. Constructing NumpyDocStringfrom a docstring containing that item must raisenumpydoc.docscrape.ParseError; it must not accept or silently truncate the item. The observable error text follows this exact form, including the existing wording a item`:

<item-text> is not a item name in <original-docstring-repr>

Equivalently, str(error) consists of <item-text> is not a item name, followed by in and the representation of the original, pre-dedentation docstring. For the invalid example, <item-text> is ``:func:`~foo```.
