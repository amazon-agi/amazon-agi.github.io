is_named_tuple(value) -> bool

Determines whether the given value is a named tuple type (a class produced via typing.NamedTuple or collections.namedtuple).

Behavior:

  • Returns True when value is a named tuple class.
  • Returns False when value is the plain built-in tuple type.
  • Returns False for arbitrary types that are not named tuples (e.g. int).

The argument is a type/class object, not an instance.

is_valid_combinator(combinator) -> None

Validates that a class used as a "combinator" satisfies structural requirements. This function does not return a meaningful value; it either completes without error (valid) or raises mtpylon.exceptions.InvalidCombinator (invalid).

A combinator is a named-tuple class that may declare a nested class named Meta. Validation rules exercised:

  1. Missing Meta — If the combinator has no nested Meta class, raise InvalidCombinator.

  2. Missing name on Meta — If Meta exists but does not define a name attribute, raise InvalidCombinator.

  3. Invalid name value — If Meta.name is present but is not a non-empty string, raise InvalidCombinator. Specifically:

    • An empty string ('') is invalid.
    • A non-string value (e.g. an integer) is invalid.

  4. Valid combinator — If the combinator is a named-tuple class with no additional fields defined, and it has a nested Meta class whose name attribute is a non-empty string, validation passes silently (no exception, no return value required).

        name = 'boolTrue'

    pass

class NoName(NamedTuple):

        pass

02 Extend the module mtpylon/utils.py with combinator validation capabilities. 685 words · source specification

Overview

Extend the module mtpylon/utils.py with combinator validation capabilities. You must add one new public function and extend the behavior of an existing one. You will also rely on the existing exception InvalidCombinator located in mtpylon/exceptions.py.

Background Concepts

A combinator is a NamedTuple subclass that carries a nested Meta class describing metadata. A Meta class may contain:

  • name: a string identifying the combinator.
  • order: a tuple of strings naming the combinator's attributes in a defined sequence.

A combinator type (referred to here as a "constructor") is a value produced by typing.NewType, whose supertype is a Union of combinator NamedTuple classes. For example:

Bool = NewType('Bool', Union[BoolTrue, BoolFalse])
Tree = NewType('Tree', Union[TreeNode, LeafNode])

These constructors may be passed around as a list of allowed types when validating.

Required Public API

1. is_good_for_combinator
def is_good_for_combinator(value, combinators: Optional[list] = None) -> bool

Determines whether value is an acceptable type for use as a combinator attribute.

  • value — a type, a typing.ForwardRef, or a type annotation object.
  • combinators — an optional list of allowed constructor types (the NewType-produced values described above). Defaults to no allowed constructors (treat as empty).

Return True when the value is acceptable, False otherwise. Acceptance rules:

  • Basic Python types are always acceptable. For example, str and int are acceptable regardless of the combinators list.
  • A constructor (a NewType value such as Bool or Tree) is acceptable only if it is present in the provided combinators list.
  • A ForwardRef (e.g. ForwardRef('Tree')) is acceptable only if its referenced name matches the name of one of the constructors in the combinators list (e.g. ForwardRef('Tree') is acceptable when the Tree constructor appears in combinators). If no constructor in the list has that name, it is not acceptable.
  • An annotation that refers to a constructor by forward reference — as occurs when a NamedTuple attribute is annotated with a string literal like 'Tree' — must be treated the same as the equivalent ForwardRef and is acceptable only when the referenced constructor is in combinators.
  • An arbitrary user-defined class that is neither a basic type nor a listed constructor (nor a matching forward reference) is not acceptable.
2. is_valid_combinator (extended behavior)
def is_valid_combinator(combinator, combinators: Optional[list] = None) -> None

Validates that combinator is a well-formed combinator. On success it returns normally (no meaningful return value is required). On any validation failure it must raise InvalidCombinator.

The existing validation behavior must be preserved:

  • The combinator must be a NamedTuple subclass with a nested Meta class.
  • The Meta class must define a name attribute that is a string.

A combinator with a Meta that has a valid string name but no attributes and no order is valid.

The following additional validation rules apply and must be enforced:

  • combinators is an optional list of allowed constructor types (as described above), used to validate attribute types. Defaults to no allowed constructors.

  • Every attribute declared in the combinator's annotations must be listed in Meta.order. If the combinator has an annotated attribute that does not appear in order, validation fails.

  • Every name listed in Meta.order must correspond to a declared (annotated) attribute of the combinator. If order references a name that is not an annotated attribute, validation fails.

  • Every attribute's type must be acceptable according to is_good_for_combinator (using the same combinators list). If any attribute's annotated type is not acceptable (for example, an arbitrary user-defined class that is not a listed constructor), validation fails.

  • Recursive / self-referential combinators are supported. An attribute may be annotated with a forward reference to a constructor (e.g. an attribute typed as 'Tree'), and this is valid provided that constructor is present in the combinators list.

A combinator whose attributes all appear in order, whose order entries all correspond to declared attributes, and whose attribute types are all acceptable, is valid.

Notes

  • Basic-typed attributes require no entry in combinators.
  • The combinators list is what makes constructor-typed and forward-referenced attributes valid; without the relevant constructor present, such attributes are invalid.

Valid Constructor Representations

is_valid_constructor must recognize all of the following representations.

1. A named constructor wrapping one combinator

A value created with typing.NewType(name, combinator) is valid when its wrapped supertype is a valid combinator. For example:

from typing import NamedTuple, NewType

class UserCombinator(NamedTuple):
    id: int
    name: str

    class Meta:
        name = 'user'
        order = ('id', 'name')

User = NewType('User', UserCombinator)
is_valid_constructor(User)

The NewType value is the constructor; a plain combinator class is not, by itself, the documented single-combinator constructor form.

2. A direct union of combinators

A typing.Union containing multiple combinator types is valid when every union member is a valid combinator. Each member must be validated separately.

from typing import NamedTuple, Union

class BoolTrue(NamedTuple):
    class Meta:
        name = 'boolTrue'

class BoolFalse(NamedTuple):
    class Meta:
        name = 'boolFalse'

BoolMembers = Union[BoolTrue, BoolFalse]
is_valid_constructor(BoolMembers)
3. A named constructor wrapping a union of combinators

A union constructor may itself be named with NewType. A value created as NewType(name, Union[C1, C2, ...]) must be accepted when every member of the wrapped union is a valid combinator. Constructor validation must inspect the NewType value's wrapped supertype rather than attempting to validate the NewType value as a combinator.

Bool = NewType('Bool', Union[BoolTrue, BoolFalse])
is_valid_constructor(Bool)

This named-union representation is required in addition to the direct typing.Union representation.

Constituent Validation and Context Propagation

For every constituent combinator extracted from any accepted constructor representation, validation must have the same externally observable result as calling:

is_valid_combinator(constituent, combinators)

The same caller-supplied combinators list must be provided when validating every member of a union, including a union wrapped by NewType. It must also be used for the combinator wrapped by a single-member NewType constructor. If combinators is omitted, constituent validation uses the existing no-context behavior of is_valid_combinator.

This propagation is significant for combinators whose annotations refer to related constructors, including recursive annotations and ForwardRef values. For example, if a combinator has a field annotated as 'Tree', a supplied related-constructor list containing the Tree constructor must be available while that combinator is validated.

Success and Failure Semantics

  • Validation succeeds only if value has one of the supported constructor representations and every constituent is a valid combinator in the supplied context.
  • Success is indicated by returning normally without raising an exception. Callers are not required to inspect a Boolean result.
  • Any value that is not one of the supported representations must be rejected with InvalidConstructor. In particular, a plain built-in type such as int must be rejected.
  • A NewType that wraps an invalid combinator or an unsupported supertype must be rejected with InvalidConstructor.
  • A direct or wrapped union must be rejected with InvalidConstructor if any member fails combinator validation.
  • Constituent combinator failures are constructor-validation failures at this API boundary: is_valid_constructor must raise InvalidConstructor, rather than expose InvalidCombinator as the rejection result.

Example rejection:

try:
    is_valid_constructor(int)
except InvalidConstructor:
    pass

Compatibility Scope

The existing combinator rules and utility APIs remain unchanged. This task adds constructor-level recognition, unwrapping, context propagation, and error reporting; it does not make arbitrary classes, built-in types, or otherwise invalid combinators into valid constructors.

<field_name>:<type_name>

<combinator_name> = <constructor_name>

Task Specification: Support Optional Fields in Combinators

Overview

You are extending an existing utility module that validates and describes "combinators" defined as Python NamedTuple subclasses. This task adds support for optional fields — fields whose presence is controlled by a flags bitmask, following the TL (Type Language) convention.

The functions being modified already exist and handle non-optional fields. This spec describes only the additional/modified behavior for optional fields; existing behavior for required fields must be preserved.

Combinator Definition Format

A combinator is a NamedTuple subclass with typed fields and a nested Meta class. The Meta class may contain:

  • name (str): the combinator's name.
  • order (tuple of str): the field names in declaration order.
  • flags (dict, optional): maps optional field names to a bit position (a non-negative integer). Only fields listed here are optional.

A field is considered optional when:

  1. Its type annotation is typing.Optional[...] (i.e. Union[X, None]), AND
  2. Its name appears as a key in Meta.flags with an associated bit position.

Optional fields may be typed with a base type (e.g. Optional[int], Optional[str]) or with a combinator/constructor type produced via NewType (e.g. Optional[SomeConstructor]), including self-referential/forward references.

Public API

The following are importable from the module utils (the same module the existing functions live in). All names below are already partially present; extend them.

is_valid_combinator(combinator, constructors=None)

Validates a combinator definition. Raises InvalidCombinator (an existing exception in the module) when invalid.

Additional rules for optional-field support:

  • Valid: A field annotated as Optional[...] and listed in Meta.flags is accepted. This applies both to base types (e.g. Optional[int]) and to constructor types passed in constructors.
  • Invalid: A field annotated as Optional[...] but not present in Meta.flags (or where Meta.flags is absent entirely) must raise InvalidCombinator.
  • Invalid: A field listed in Meta.flags whose optional type refers to a type that is neither a recognized base type nor a valid constructor (i.e. an unknown/non-constructor type) must raise InvalidCombinator.

The optional constructors argument is a list of NewType constructor types that are considered valid types for that combinator's fields.

is_valid_constructor(constructor, combinators=None)

Validates a constructor (a NewType) and, optionally, the list of combinators that belong to it. Existing behavior is preserved. It must continue to accept constructors whose combinators contain optional (flags-based) fields, including self-referential constructors.

Behavior

combinator_to_dict(combinator) -> dict

Given a single combinator object, return a dictionary with exactly these keys:

  • "id": an integer identifier for the combinator.
  • "predicate": the combinator's name (a string, taken from its Meta.name).
  • "type": the name of the type this combinator belongs to (a string).
  • "params": a list of parameter dictionaries, one per field of the combinator, in the order given by Meta.order. Each parameter dictionary has exactly:
    • "name": the field name (string).
    • "type": the string name of the field's type.

A combinator with no fields produces an empty params list.

function_to_dict(function) -> dict

Given a single function object, return a dictionary with exactly these keys:

  • "id": an integer identifier for the function.
  • "method": the function's name (string).
  • "type": the string name of the function's return type.
  • "params": a list of parameter dictionaries, one per function parameter, in order. Each parameter dictionary has exactly:
    • "name": the parameter name (string).
    • "type": the string name of the parameter's type.

A function with no parameters produces an empty params list.

to_dict(schema) -> dict

Given a Schema, return a dictionary with exactly two keys:

  • "constructors": a list produced by applying combinator_to_dict to every combinator of the schema, in the schema's constructor order.
  • "methods": a list produced by applying function_to_dict to every function of the schema, in the schema's function order.
to_json(schema) -> str

Return the JSON string representation of to_dict(schema), equivalent to json.dumps(to_dict(schema)) (default settings, no extra formatting or key sorting).

Type Name Mapping

Field and parameter type names in the output are string representations of the Python/schema types:

  • int → "int"
  • str → "string"
  • A combinator/type alias → its type name string (e.g. "Bool", "User", "Task", "TaskList").
  • A List[X] field → "Vector<X>", where X is the mapped type name (e.g. List[Task] → "Vector<Task>").

Task Specification: TL Program Serialization

Overview

Extend the mtpylon.serializers module to support serializing schema objects into TL (Type Language) program textual notation. This is in addition to the existing dict/JSON serialization already present in the module.

Public API Surface

The following names must be importable from mtpylon.serializers:

from mtpylon.serializers import (
    combinator_to_tl,
    function_to_tl,
    to_tl_program,
    FUNCTIONS_SEPARATOR,
)
FUNCTIONS_SEPARATOR

A module-level string constant used to visually separate the constructor (combinator) section from the function (method) section in a full TL program. Its exact value is:

---functions---
combinator_to_tl(combinator) -> str

Given a single combinator object (of the kind found in a schema structure's constructors collection), return its one-line TL notation string.

function_to_tl(method) -> str

Given a single function/method object (of the kind found in a schema structure's methods collection), return its one-line TL notation string.

to_tl_program(schema) -> str

Given a schema object, return the complete TL program as a single string.

Schema Access

A schema object exposes schema.get_schema_structure(), which returns an object with:

  • .constructors — an iterable of combinator objects
  • .methods — an iterable of function/method objects

TL Line Format

Each combinator or function is serialized to a single line with the following structure:

<name>#<id> [<arg>:<type> ...] = <result_type>;

Details:

  • <name> — the predicate/method name.
  • #<id> — a # followed by the combinator's/function's identifier rendered as a lowercase 8-digit zero-padded hexadecimal number (e.g. 997275b5, 006287c2, 79cfe94e).
  • After the id, zero or more space-separated argument descriptors, each of the form <arg_name>:<arg_type>. If there are no arguments, this section (and its surrounding space) is omitted.
  • = followed by the result type.
  • A trailing semicolon ;.

Argument type rendering:

  • Simple/bare types are rendered by their type name (e.g. int, string, Bool, Task).
  • Parameterized (vector) types are rendered using angle-bracket notation: Vector<Task>.

The result type is rendered as the bare type name (e.g. Bool, User, Task, TaskList).

Representative examples

Combinators:

boolTrue#997275b5 = Bool;
boolFalse#bc799737 = Bool;
authorizedUser#599b7638 id:int username:string password:string = User;
anonymousUser#5d328bc3 = User;
task#006287c2 id:int content:string completed:Bool = Task;
taskList#66980046 tasks:Vector<Task> = TaskList;

Functions:

register#79cfe94e username:string password:string = User;
login#1c5d7e43 username:string password:string = User;
set_task#0d77615b content:string = Task;
get_task_list#ca222953 = TaskList;

Full Program Format (to_tl_program)

The full program is built by:

  1. Serializing every combinator in .constructors (in the order provided) into its TL line.
  2. Appending a single separator line equal to FUNCTIONS_SEPARATOR.
  3. Serializing every function in .methods (in the order provided) into its TL line.

All of these lines are joined with a single newline character (\n) into one string. There is no trailing newline.

That is, the output equals:

<combinator_line_1>
...
<combinator_line_n>
---functions---
<function_line_1>
...
<function_line_m>

Notes

  • combinator_to_tl and function_to_tl each operate on a single object and produce exactly one line (no trailing newline).
  • The existing serializer functions (combinator_to_dict, function_to_dict, to_dict, to_json) must remain available and unchanged in behavior.

Task Specification: Integer Serialization Module

Overview

Implement a module that serializes and deserializes 32-bit integers using a fixed 4-byte little-endian binary encoding.

Module Location

Create the module at:

mtpylon/serialization/int.py

The package directories must be importable (i.e., mtpylon/serialization/ must be a proper package).

Public API

The module must expose two callables:

dump(value)
  • Input: an integer.
  • Output: a bytes object of length 4 containing the little-endian encoding of the integer.
  • Behavior: encodes the integer into exactly 4 bytes, least-significant byte first.

Example:

  • dump(275) returns b'\x13\x01\x00\x00'.
load(data)
  • Input: a bytes object.
  • Output: an object with two attributes:
    • value: the integer decoded from the first 4 bytes of the input, interpreted as a little-endian integer.
    • offset: an integer equal to 4, representing the number of bytes consumed.
  • Behavior: reads the first 4 bytes of the input and decodes them as a little-endian integer.

Example:

  • load(b'\x13\x01\x00\x00') returns an object where .value == 275 and .offset == 4.

Error Conditions

  • load must raise ValueError if the input bytes object contains fewer than 4 bytes.

Example:

  • load(b'\x13\x00\x00') (3 bytes) raises ValueError.

Notes

  • The return type of load may be any object (e.g., a named tuple or simple data class) that supports attribute access via .value and .offset.
