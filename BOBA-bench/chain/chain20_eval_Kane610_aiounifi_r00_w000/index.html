Specification of the Task

Goal

A new asynchronous method, set_outlet_cycle_enabled(), is to be added to the device class that represents a UniFi smart plug/PDU device. The method sets the "cycle_enabled" property for a specific outlet on the device by sending an update request to the controller.

API Method to Add

The following method is added to the smart plug device class (the same class that already exposes outlets, together with outlet objects that have relay_state and cycle_enabled properties):

async def set_outlet_cycle_enabled(self, outlet_index: int, enabled: bool) -> ...
  • outlet_index: the integer index that identifies which outlet to modify.
  • enabled: the boolean value desired for that outlet's cycle_enabled setting.

Behavior Requirements

Whenever set_outlet_cycle_enabled(index, enabled) is invoked, the method must send an HTTP PUT request to the REST endpoint of the device:

https://<host>:<port>/api/s/<site>/rest/device/<device_id>

(This is the same device REST endpoint that is already used for updating the relay state of outlets.)

The JSON body of the request must contain a single key, "outlet_overrides"; the value of this key is a list of outlet override objects. For the outlet being targeted, the override must include:

  • "index": the index of the outlet (matching outlet_index).
  • "name": the name the outlet already has.
  • "relay_state": the outlet's current relay state (left unchanged).
  • "cycle_enabled": the new value passed via the enabled argument.
Concrete Example

await plug.set_outlet_cycle_enabled(1, True)

must result in a PUT request to the device REST endpoint carrying the following JSON body:

{
    "outlet_overrides": [
        {
            "index": 1,
            "name": "Outlet 1",
            "relay_state": False,
            "cycle_enabled": True
        }
    ]
}

Remarks

  • In the override, the cycle_enabled value must reflect the newly requested enabled argument, not the outlet's prior value.
  • In the override, the relay_state and name fields must reflect the outlet's existing state when the call is made.
  • The method follows the same mechanism that already exists for setting an outlet's relay state (through outlet_overrides), the only difference being that it targets the cycle_enabled field.
02 aiounifi — an async Python client library for talking to UniFi network controllers (both classic controllers and UniFi OS controllers) — is what you will be… 852 words · source specification, reworded by GLM-5.3-Flash

Task Brief

Context

aiounifi — an async Python client library for talking to UniFi network controllers (both classic controllers and UniFi OS controllers) — is what you will be working on. The subject of this task is how the x-csrf-token HTTP header is handled whenever the library issues a request to a controller.

The Problem Today

Communication with a UniFi OS controller currently leads the library to assume that an x-csrf-token value is always available, and this header is attached to its requests. Yet some remote endpoints do not return a CSRF token; one such case is connecting to an invalid site such as port 443 on a UniFi controller instead of 8443. The token value is then effectively None, and a request that carries it ends in failure (TypeError: Cannot serialize non-str key None).

The x-csrf-token header must be attached by the library only if the remote site has actually provided a token.

Behavior to Implement

How the CSRF token is detected
  • An async method, check_unifi_os(), is defined on the controller; it sends a GET request to the controller base URL (e.g. https://host:8443), passing allow_redirects=False. Whether the target is a UniFi OS controller is determined by this method, which then sets the boolean attribute is_unifi_os to match.
  • Should the response from the base URL include an x-csrf-token header, that token is recorded by the controller so that subsequent requests can use it.
  • If the response from the base URL does not include an x-csrf-token header, the controller must have no token on record (there must be no stored token to attach later).
Header rules for requests

These rules cover every request the controller makes (the login as well as all subsequent data requests):

  • Where a CSRF token has been recorded (that is, the remote site provided one), an x-csrf-token header carrying that token value must be included in the request.
  • Where no CSRF token has been recorded, on the other hand, an x-csrf-token header must not be included at all. Specifically, no header entry with a None value may be emitted, and the header key must not be present. In this situation, requests must succeed without raising.

The rules above hold uniformly for:

  • The login request — on a UniFi OS controller, this takes the form of a POST to https://host:8443/api/auth/login.
  • Every data-retrieval request sent to UniFi OS proxy endpoints, for example:
    • GET https://host:8443/proxy/network/api/s/default/stat/sta
    • GET https://host:8443/proxy/network/api/s/default/stat/device
    • GET https://host:8443/proxy/network/api/s/default/rest/user
    • GET https://host:8443/proxy/network/api/s/default/rest/wlanconf
    • GET https://host:8443/proxy/network/api/s/default/self

If a token (e.g. "123") was provided by the base-URL response, every one of the requests above must carry headers={"x-csrf-token": "123"}. If no token was provided, none of these requests may carry an x-csrf-token header.

What the login body must contain

Sent as the login request body, the JSON payload must contain the username, the password, and a remember flag:

{"username": <username>, "password": <password>, "remember": True}

What the password field must carry is the exact password value supplied at the moment the controller is constructed (it must be passed through unchanged — neither substituted nor transformed).

The two scenarios under verification

  1. UniFi OS controller that supplies a CSRF token.

    • is_unifi_os is set to True by check_unifi_os().
    • The base-URL response contains x-csrf-token: 123.
    • On the login POST to /api/auth/login, the headers are headers={"x-csrf-token": "123"}, and the body is the JSON body described above.
    • Every subsequent proxy data request carries headers={"x-csrf-token": "123"}.

  2. UniFi OS controller that does NOT supply a CSRF token.

    • The base-URL response comes with content type text/html, and no x-csrf-token header is included.
    • Running check_unifi_os() sets is_unifi_os to True.
    • login() sends a POST to /api/auth/login that carries the JSON body described above and no x-csrf-token header, finishing without an error.

The controller's public API

Constructed by the library's existing controller class / fixture, the controller object must expose the following:

  • is_unifi_os — a boolean attribute that tells whether the target is a UniFi OS controller; check_unifi_os() sets it as a side effect.
  • async check_unifi_os() — sends the base-URL GET (with allow_redirects=False), sets is_unifi_os, and records the CSRF token only if one was provided by the response.
  • async login() — performs the login request, supplying the correct payload and, conditionally, the x-csrf-token header.
  • async site_description() — makes a GET request to the /proxy/network/api/s/default/self endpoint (for UniFi OS), with the x-csrf-token header carried conditionally.
  • For the data-retrieval operations that send GET requests to the proxy stat/sta, stat/device, rest/user, and rest/wlanconf endpoints, the x-csrf-token header must be carried conditionally by all of them, following the rules above.

A host, a username, and a password go into the controller's construction; the password supplied there must be forwarded verbatim inside the login payload.

Notes and Constraints

  • If a request legitimately has no x-csrf-token, the header must be left out entirely rather than sent with an empty/None value.
  • Beyond what the behavior described requires, requests should have no unexpected headers attached; specifically, a request that should have no CSRF header must not carry one.

Overview

This task is carried out on an asynchronous UniFi controller client and centers on how the controller's login retry logic interacts with its internal HTTP request method. In particular, the internal request method must stop performing an implicit HTTP GET against the controller's base host as part of its request flow.

Behavior That Is Required

The internal request method (_request)

The private request method of the controller, _request, must expect and operate on a fully-qualified URL that is passed to it directly. As part of servicing a request, it must NOT construct or issue any additional HTTP request to the controller's base host (e.g. https://host:8443). Login behavior and retry logic

The login retry behavior of the controller must be retained; it is driven by a "can retry login" flag whose lifecycle is managed inside the login flow:

  • When a login is (re)performed successfully, the retry-permission flag is reset so that a future authentication failure may again trigger a single re-login attempt.

  4. If the re-login does not restore access, the controller raises an authentication failure rather than retrying repeatedly.

  • During the request/relogin cycle, an implicit GET to the controller's root/base URL must not be introduced or relied on.
  • The retry-permission flag must be reset as part of a successful login (rather than being left permanently disabled after a single retry), so that each distinct authentication-failure event gets its own single re-login opportunity.

The existing public/importable surface of the controller module and class must be preserved. The controller exposes:

  • A private request method named _request that accepts a complete URL.
  • A login (and corresponding re-login) flow that manages the "can retry login" flag internally.

Task Specification: Subscription System for the API Handler

Summary

In the module aiounifi.interfaces.api_handlers, implement an APIHandler base class together with a supporting ItemEvent enumeration. The APIHandler maintains a cache of items keyed by an object identifier, processes raw item payloads, and notifies subscribers about item lifecycle events.

Public API

The module aiounifi.interfaces.api_handlers must expose the following:

ItemEvent

An enumeration that has exactly these three members:

  • ItemEvent.ADDED
  • ItemEvent.CHANGED
  • ItemEvent.DELETED

These members are used both as event identifiers that are passed to subscriber callbacks and, collectively, as the valid values for event filtering.

APIHandler

A class whose constructor takes a single positional argument:

APIHandler(controller)

The controller argument is stored/used internally, and this task does not constrain it any further (it may be any object).

After construction, callers may set the instance attributes listed below directly, before using the handler:

  • obj_id_key — a string that names the dictionary key identifying an item within a raw payload dict.
  • item_cls — a callable used for constructing item objects from raw payload dicts.

An internal attribute must also be maintained by the class:

  • _subscribers — a mutable container that holds registered subscriptions. It must support a .clear() method that removes all subscriptions (after clearing, unsubscribe callables returned previously must be safe to invoke and must do nothing).

The class must expose the methods below:

subscribe(callback, event_filter=None, id_filter=None) -> Callable[[], None]

Registers a subscriber callback and returns an unsubscribe callable (a callable taking no arguments and returning nothing).

  • callback — a callable that gets invoked as callback(event, obj_id), where event is an ItemEvent member and obj_id is the item's identifier string.
  • event_filter — optional. It may be:
    • None (default): all event types reach the subscriber.
    • A single ItemEvent member: only events of that type reach the subscriber.
    • A collection (e.g. a set) of ItemEvent members: only events whose type is contained in the collection reach the subscriber.
  • id_filter — optional. It may be:
    • None (default): events for all item identifiers reach the subscriber.
    • A single identifier string: only events whose obj_id equals this value reach the subscriber.

The unsubscribe callable that gets returned removes the subscription. It must be safe to call:

  • More than once (later calls do nothing).
  • After _subscribers has been cleared (the call does nothing).
process_item(raw) -> str

When given a single raw payload dict raw:

  • If raw does not contain the key named by obj_id_key, nothing happens and the empty string "" is returned.
  • Otherwise, extract the identifier value found at raw[obj_id_key]:
    • If this identifier is not already present in the handler's item cache, the item is stored/constructed, an ItemEvent.ADDED event is emitted for this identifier to matching subscribers, and the identifier string is returned.
    • If this identifier is already present in the handler's item cache, the item is updated, an ItemEvent.CHANGED event is emitted for this identifier to matching subscribers, and the empty string "" is returned.
process_raw(raw_list) -> set[str]

Accepts a list of raw payload dicts, processes each one via the same logic as process_item, and returns the set of identifier strings that were newly added (i.e. the non-empty values that process_item would return). Payload dicts that lack the obj_id_key key contribute nothing. Each item that is processed still emits the appropriate ItemEvent.ADDED or ItemEvent.CHANGED event to matching subscribers.

Return value examples:

  • If [{}] is processed, set() is returned.
  • If [{"key": "2"}] is processed while "2" is not cached, {"2"} is returned.
  • If [{"key": "2"}] is processed again (now cached), set() is returned.
remove_item(raw) -> str

When given a single raw payload dict raw:

  • Extract the identifier found at raw[obj_id_key].
  • If that identifier is present in the handler's item cache, it is removed from the cache, an ItemEvent.DELETED event is emitted for this identifier to matching subscribers, and the identifier string is returned.
  • If that identifier is not present in the cache, nothing happens and the empty string "" is returned.

Rules for Event Delivery

Whenever an event is emitted for a given (event, obj_id) pair, every registered subscriber must be considered and invoked as callback(event, obj_id) only if both of the following hold:

  1. The subscriber's event_filter admits event (with no filter, admit all; with a single member, admit if equal; with a collection, admit if contained).
  2. The subscriber's id_filter admits obj_id (with no filter, admit all; with a single string, admit if equal).

For that emission, subscribers whose filters exclude the event or identifier must not be invoked.

Behavioral Notes and Edge Cases

  • The item cache is keyed by the identifier value. Whether something is "Present in cache" is decided solely by whether an item with that identifier has been added (via process_item/process_raw) and not subsequently removed (via remove_item).
  • After an item is removed, processing the same identifier again counts as an ItemEvent.ADDED (it is no longer in the cache).
  • The identifier values in payloads and the returned strings are the raw values found at raw[obj_id_key] (strings in all exercised cases).
  • The sentinel "no new/removed item" return value from process_item and remove_item is the empty string "".

Example Walkthrough

handler = APIHandler(controller)
handler.obj_id_key = "key"
handler.item_cls = SomeItem

unsub = handler.subscribe(cb)                      # all events, all ids

handler.process_item({})                # -> ""      ; cb not called
handler.process_item({"key": "1"})      # -> "1"     ; cb(ItemEvent.ADDED, "1")
handler.process_item({"key": "1"})      # -> ""      ; cb(ItemEvent.CHANGED, "1")
handler.remove_item({"key": "1"})       # -> "1"     ; cb(ItemEvent.DELETED, "1")
handler.remove_item({"key": "2"})       # -> ""      ; cb not called

handler.process_raw([{}])               # -> set()
handler.process_raw([{"key": "2"}])     # -> {"2"}   ; cb(ItemEvent.ADDED, "2")
handler.process_raw([{"key": "2"}])     # -> set()   ; cb(ItemEvent.CHANGED, "2")
handler.remove_item({"key": "2"})       # -> "2"     ; cb(ItemEvent.DELETED, "2")

unsub()                                  # unsubscribe
unsub()                                  # safe no-op
handler._subscribers.clear()
unsub()                                  # safe no-op after clear

When event_filter=ItemEvent.ADDED is in effect, only ADDED emissions invoke the callback; CHANGED and DELETED emissions do not, but the return values of process_item/process_raw/remove_item remain unchanged.

When id_filter="1" is in effect, only events for identifier "1" invoke the callback; events for other identifiers do not, but return values remain unchanged.

3. Subscription mechanism (infrastructure shared across handlers)

A subscribe method, with the following signature, must be supported by the ports handler as well as by the shared handler base:

subscribe(callback, *, id_filter=None, event_filter=None) -> unsubscribe_callable
  • Whenever a matching item event occurs, callback is invoked as callback(event: ItemEvent, obj_id: str).
  • id_filter: if a value is supplied (a single item id, e.g. "fc:ec:da:11:22:33_18"), the callback is invoked only for events whose object id equals it.
  • event_filter: if a value is supplied (an ItemEvent value), the callback is invoked only for events of that type.
  • The callback is never invoked when a filter that was set never matches any event.
  • What subscribe returns is a callable that removes the subscription when it gets called. Calling the returned unsubscribe callable more than once must be safe (no error). Unsubscribing while the subscription is no longer present (e.g. after the internal subscriber store has been cleared) must also be safe (no error).
  • The internal subscriber store must be exposed by the handler as an attribute named _subscribers, one that supports a .clear() operation.
4. The Ports handler, aiounifi.ports

A ports attribute (accessible as controller.ports) must be exposed on the controller; this attribute is an API handler whose provided view — mapping-like and subscribable — spans all ports across all known devices.

It must be possible to import the handler such that aiounifi.ports is a valid coverage target (i.e. a module reachable via that path is where the ports handler lives).

Access behavior as a mapping:

Each port item's key is a string id having the form "{device_mac}_{port_idx}" — the device MAC and the port index, joined by an underscore.

  • items() → returns a view of (id, Port) pairs; with no ports known, the view is empty.
  • values() → returns a view of Port objects; likewise, no known ports means an empty view.
  • get(id, default=None) → returns the Port for id; when the id is absent, default is returned instead (its own default being None).
  • id in handler → a membership test over the port ids.
  • handler[id] → indexing; the Port for the id is what this returns.
  • Iteration (iter(handler)) yields the port ids. That iteration's order must follow the order in which the ports were derived from the device data — port index 1 comes first, etc.; hence, on a 16-port PoE switch with 18 entries, "{mac}_1" is the first id.
  • For an id that is missing, get returns the provided default (a value that is not a Port instance).
How the ports get derived from devices

On the controller there is already a devices handler, complete with a process_raw(list_of_raw_device_dicts) method and a remove_item(raw_device_dict) method. The ports handler must remain in sync with that devices handler:

  • During device processing (devices.process_raw([...])): each device's "port_table" (a list of raw port dicts) is read. Out of the device "mac" and the port's "port_idx", a port id is built for every port entry, and a Port gets registered/updated.

    • No ports are contributed by a device without "port_table".
    • Any port entry lacking "port_idx" (e.g. an empty dict) must be skipped, contributing no port item.
    • 18 port items are yielded by the example 16-port PoE switch fixture.

  • Events emitted while processing:

    • An ItemEvent.ADDED event is emitted for a given port id the first time that id is seen.
    • An ItemEvent.CHANGED event for an already-known port id is emitted when that id shows up again in a subsequent process_raw.
    • All matching subscribers are called by each emitted event as callback(event, port_id).
    • One processing pass over the 18-port device results in 18 ADDED events (one per port); when the same device is processed again, the result is 18 CHANGED events, and the total count stays at 18 ports.

  • Removal (devices.remove_item(raw_device_dict)): all of that device's ports are removed, and an ItemEvent.DELETED event is emitted for each removed port id. After the 18-port device has been removed, no ports remain and 18 DELETED events have been emitted.

Notes on event ordering / consistency (as exercised)
  • Every event for every port is received by a subscriber that has no filters. Across the sequence add 18 → update 18 → remove 18, such a subscriber is called 18 + 18 + 18 = 54 times in total; in each phase, the last event is the one for the highest port id ("{mac}_18") — first ADDED, then CHANGED, then DELETED.
  • Filtered to a single port id ("{mac}_18"), a subscriber is invoked exactly once per phase — one call on add, one on update, one on remove (3 total).
  • Filtered to ItemEvent.ADDED, a subscriber is called 18 times (only during add); on update or remove, it is never called again.
  • Filtered to ItemEvent.CHANGED, a subscriber has a call count of 18 (only during update).
  • Filtered to ItemEvent.DELETED, a subscriber has a call count of 18 (only during remove).
  • With a filter set to a non-existent id ("bad"), a subscriber is never called.
