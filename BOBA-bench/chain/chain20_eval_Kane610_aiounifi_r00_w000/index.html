await plug.set_outlet_cycle_enabled(1, True)

02 You are working on aiounifi, an async Python client library for communicating with UniFi network controllers (both classic controllers and UniFi OS… 765 words · source specification

Overview

You are working on aiounifi, an async Python client library for communicating with UniFi network controllers (both classic controllers and UniFi OS controllers). This task concerns the handling of the x-csrf-token HTTP header when the library issues requests to a controller.

Current Problem

When the library communicates with a UniFi OS controller, it currently assumes an x-csrf-token value is always available and attaches this header to requests. However, some remote endpoints do not return a CSRF token (for example, when connecting to an invalid site such as port 443 on a UniFi controller instead of 8443). In that situation the token value is effectively None, and attaching it to a request causes a failure (TypeError: Cannot serialize non-str key None).

The library must only attach the x-csrf-token header when the remote site has actually provided a token.

Required Behavior

CSRF token detection
  • The controller has a method check_unifi_os() (async) that issues a GET request to the controller base URL (e.g. https://host:8443) with allow_redirects=False. This method determines whether the target is a UniFi OS controller and sets a boolean attribute is_unifi_os accordingly.
  • When the response from the base URL includes an x-csrf-token header, the controller records that token for use in subsequent requests.
  • When the response from the base URL does not include an x-csrf-token header, the controller must record no token (there must be no stored token to attach later).
Request header behavior

For every request the controller makes (login and all subsequent data requests):

  • If a CSRF token has been recorded (i.e., the remote site provided one), the request must include an x-csrf-token header carrying that token value.
  • If no CSRF token has been recorded, the request must not include an x-csrf-token header at all. In particular, the header key must not be present, and no header entry with a None value may be emitted. Requests must succeed in this case without raising.

This applies uniformly to:

  • The login request. For a UniFi OS controller this is a POST to https://host:8443/api/auth/login.
  • All data-retrieval requests to UniFi OS proxy endpoints, for example:
    • GET https://host:8443/proxy/network/api/s/default/stat/sta
    • GET https://host:8443/proxy/network/api/s/default/stat/device
    • GET https://host:8443/proxy/network/api/s/default/rest/user
    • GET https://host:8443/proxy/network/api/s/default/rest/wlanconf
    • GET https://host:8443/proxy/network/api/s/default/self

When a token (e.g. "123") has been provided by the base-URL response, each of the above requests must carry headers={"x-csrf-token": "123"}. When no token was provided, none of these requests may carry an x-csrf-token header.

Login request payload

The login request body (JSON payload) must contain the username, password, and a remember flag:

{"username": <username>, "password": <password>, "remember": True}

The password field must carry the exact password value that was supplied when constructing the controller (it must be passed through unchanged; do not substitute or transform it).

Two verified scenarios

  1. UniFi OS controller that provides a CSRF token.

    • check_unifi_os() sets is_unifi_os to True.
    • The base-URL response includes x-csrf-token: 123.
    • The login POST to /api/auth/login carries headers={"x-csrf-token": "123"} and the JSON body described above.
    • All subsequent proxy data requests carry headers={"x-csrf-token": "123"}.

  2. UniFi OS controller that does NOT provide a CSRF token.

    • The base-URL response has content type text/html and includes no x-csrf-token header.
    • check_unifi_os() sets is_unifi_os to True.
    • login() issues a POST to /api/auth/login with the JSON body described above and no x-csrf-token header, and completes without error.

Public API Surface

The controller object (as constructed by the library's existing controller class / fixture) must expose:

  • is_unifi_os — a boolean attribute indicating whether the target is a UniFi OS controller, set as a side effect of check_unifi_os().
  • async check_unifi_os() — issues the base-URL GET (with allow_redirects=False), sets is_unifi_os, and records the CSRF token only if the response provided one.
  • async login() — issues the login request with the correct payload and, conditionally, the x-csrf-token header.
  • async site_description() — issues a GET to the /proxy/network/api/s/default/self endpoint (for UniFi OS), conditionally carrying the x-csrf-token header.
  • The data-retrieval operations that issue GET requests to the proxy stat/sta, stat/device, rest/user, and rest/wlanconf endpoints must all conditionally carry the x-csrf-token header per the rules above.

The controller is constructed with a host, username, and password; the supplied password must be forwarded verbatim in the login payload.

Constraints / Notes

  • Requests that legitimately have no x-csrf-token must omit the header entirely rather than sending it with an empty/None value.
  • No unexpected headers should be attached to requests beyond what the described behavior requires; specifically, a request that should have no CSRF header must not carry one.

Overview

You are modifying an asynchronous UniFi controller client. This task concerns the interaction between the controller's login retry logic and its internal HTTP request method. Internal request method (_request)

The controller's private request method (_request) must expect and operate on a fully-qualified URL that is provided to it directly. It must NOT construct or issue any additional HTTP request to the controller's base host (e.g. https://host:8443) as part of servicing a request. The controller must retain login retry behavior driven by a "can retry login" flag whose lifecycle is managed within the login flow:

Constraints

Event Delivery Rules

When an event is emitted for a given (event, obj_id) pair, every registered subscriber must be considered and invoked as callback(event, obj_id) only if both of the following hold:

  1. The subscriber's event_filter admits event (no filter → admit all; single member → admit if equal; collection → admit if contained).
  2. The subscriber's id_filter admits obj_id (no filter → admit all; single string → admit if equal).

Subscribers whose filters exclude the event or identifier must not be invoked for that emission.

Behavioral Notes / Edge Cases

  • The item cache is keyed by the identifier value. "Present in cache" is determined solely by whether an item with that identifier has been added (via process_item/process_raw) and not subsequently removed (via remove_item).
  • After an item is removed, processing the same identifier again is treated as an ItemEvent.ADDED (it is no longer in the cache).
  • Identifier values in payloads and returned strings are the raw values found at raw[obj_id_key] (strings in all exercised cases).
  • The empty string "" is used as the sentinel "no new/removed item" return value from process_item and remove_item.

Example Flow

handler = APIHandler(controller)
handler.obj_id_key = "key"
handler.item_cls = SomeItem

unsub = handler.subscribe(cb)                      # all events, all ids

handler.process_item({})                # -> ""      ; cb not called
handler.process_item({"key": "1"})      # -> "1"     ; cb(ItemEvent.ADDED, "1")
handler.process_item({"key": "1"})      # -> ""      ; cb(ItemEvent.CHANGED, "1")
handler.remove_item({"key": "1"})       # -> "1"     ; cb(ItemEvent.DELETED, "1")
handler.remove_item({"key": "2"})       # -> ""      ; cb not called

handler.process_raw([{}])               # -> set()
handler.process_raw([{"key": "2"}])     # -> {"2"}   ; cb(ItemEvent.ADDED, "2")
handler.process_raw([{"key": "2"}])     # -> set()   ; cb(ItemEvent.CHANGED, "2")
handler.remove_item({"key": "2"})       # -> "2"     ; cb(ItemEvent.DELETED, "2")

unsub()                                  # unsubscribe
unsub()                                  # safe no-op
handler._subscribers.clear()
unsub()                                  # safe no-op after clear

With event_filter=ItemEvent.ADDED, only ADDED emissions invoke the callback; CHANGED and DELETED emissions do not, but the return values of process_item/process_raw/remove_item are unchanged.

With id_filter="1", only events for identifier "1" invoke the callback; events for other identifiers do not, but return values are unchanged.

Mapping / access behavior:

Port items are keyed by a string id of the form "{device_mac}_{port_idx}" (device MAC and port index joined by an underscore).

  • items() → returns a view of (id, Port) pairs. Empty when no ports are known.
  • values() → returns a view of Port objects. Empty when no ports are known.
  • get(id, default=None) → returns the Port for id, or default (defaulting to None) if absent.

Deriving ports from devices

The controller already has a devices handler with a process_raw(list_of_raw_device_dicts) method and a remove_item(raw_device_dict) method. The ports handler must stay in sync with the devices handler:

  • When devices are processed (devices.process_raw([...])): for each device, read its "port_table" (a list of raw port dicts). For each port entry, build a port id from the device "mac" and the port's "port_idx", and register/update a Port.

    • A device with no "port_table" contributes no ports.
    • A port entry that has no "port_idx" (e.g. an empty dict) must be skipped and contribute no port item.
    • The example 16-port PoE switch fixture yields 18 port items.

  • Event emission on process:

    • The first time a given port id is seen, emit an ItemEvent.ADDED event for that id.
    • When a port id already known is seen again during a subsequent process_raw, emit an ItemEvent.CHANGED event for that id.
    • Each emitted event calls all matching subscribers as callback(event, port_id).
    • Processing the 18-port device once produces 18 ADDED events (one per port). Processing the same device again produces 18 CHANGED events and leaves the total count at 18 ports.

  • Removal (devices.remove_item(raw_device_dict)): all ports belonging to that device are removed, and an ItemEvent.DELETED event is emitted for each removed port id. After removing the 18-port device, no ports remain and 18 DELETED events have been emitted.

Event ordering / consistency notes (as exercised)
  • A subscriber with no filters receives every event for every port. Over the sequence add 18 → update 18 → remove 18, such a subscriber is called 18 + 18 + 18 = 54 times total, with the last event for each phase being for the highest port id ("{mac}_18"): first ADDED, then CHANGED, then DELETED.
  • A subscriber filtered to a single port id ("{mac}_18") is invoked exactly once per phase: once on add, once on update, once on remove (3 total).
  • A subscriber filtered to ItemEvent.ADDED is called 18 times (only during add) and never again on update or remove.
  • A subscriber filtered to ItemEvent.CHANGED is called 18 times (only during update).
  • A subscriber filtered to ItemEvent.DELETED is called 18 times (only during remove).
  • A subscriber filtered to a non-existent id ("bad") is never called.
