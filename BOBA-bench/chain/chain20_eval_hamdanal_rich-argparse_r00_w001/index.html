01 Add a class-level configuration option to RichHelpFormatter that controls whether user-defined usage strings are rendered with Rich console markup. 386 words · source specification

Overview

Add a class-level configuration option to RichHelpFormatter that controls whether user-defined usage strings are rendered with Rich console markup.

Public API

The formatter class RichHelpFormatter is available for import from the rich_argparse package (i.e. from rich_argparse import RichHelpFormatter).

Add a new class attribute:

class RichHelpFormatter(...):
    usage_markup: bool = False
  • usage_markup defaults to False.
  • It is a class attribute, meaning it can be overridden per-class or temporarily patched at runtime.

Required Behavior

User-defined usage strings

When an argparse.ArgumentParser is constructed with an explicit usage= string and formatter_class=RichHelpFormatter, the behavior of rendering that usage string depends on the value of RichHelpFormatter.usage_markup:

  • When usage_markup is False (the default): the user-defined usage string is rendered literally. Any square-bracket sequences that look like Rich markup tags (e.g. [bold], [/]) are treated as plain text and appear unchanged in the output — they are NOT interpreted as styling.

  • When usage_markup is True: the user-defined usage string is parsed as Rich console markup. Markup tags such as [bold]...[/] are interpreted and converted into the corresponding ANSI styling escape sequences in the output; the tags themselves are removed.

In all cases, the standard %(prog)s substitution in the usage string is performed (replaced with the program name).

Usage prefix and formatting

The rendered usage line is prefixed with USAGE: styled in the formatter's existing usage-prefix style (rendered as the ANSI sequence \x1b[38;5;208m for the label and \x1b[0m reset). The full formatted usage output takes the form:

<styled USAGE:> <rendered usage text>\n
Examples of user usage rendering

Given a parser with prog="PROG" and usage="%(prog)s [bold] CMD[/]", when color output is active:

  • With usage_markup unset/False: the rendered usage text portion is PROG [bold] CMD[/] (brackets literal).
  • With usage_markup = True: the rendered usage text portion is PROG \x1b[1m CMD\x1b[0m ([bold] and [/] interpreted as styling).

Constraints / Non-Goals

  • The usage_markup option affects only user-supplied usage strings. Automatically generated usage (when no explicit usage= is provided) must continue to be rendered exactly as before, with per-argument colorization of option strings and metavars unaffected by this option.
  • No changes to any other formatter behavior.

Programmatically obtaining the usage output is done via the standard argparse methods (parser.format_usage() and parser.format_help()), which must reflect the behavior described above.

Task: Lazy Rich Import and Console Attribute in RichHelpFormatter

Context

rich_argparse provides a RichHelpFormatter class (importable as from rich_argparse import RichHelpFormatter) that can be used as an argparse formatter_class to render colorized help output using the rich library.

The goal of this task is to ensure that importing/using the formatter does not eagerly import the rich library, and to provide a lazily-populated console attribute plus a rich-aware help-expansion method.

Requirements

1. Do not import rich until help is actually formatted

RichHelpFormatter must not cause the rich package (or any rich.* submodule) to be imported merely by:

  • Constructing an argparse.ArgumentParser(formatter_class=RichHelpFormatter).
  • Adding arguments to that parser.
  • Parsing arguments with that parser.

In other words, after building a parser that uses RichHelpFormatter, adding arguments, and calling parse_args(...) (which must return the parsed namespace with the expected values), neither "rich" nor any module name beginning with "rich." may be present in the set of imported modules.

Only when help formatting is performed — specifically when the parser's format_help() is invoked — may rich be imported. After format_help() is called, "rich" is expected to be present among the imported modules.

This implies any module-level or eager imports of rich inside the module defining the formatter must be deferred so they only occur at the point help output is actually rendered.

2. Lazily-populated console attribute

RichHelpFormatter must expose:

  • A private attribute _console. Immediately after constructing a RichHelpFormatter (e.g. RichHelpFormatter("PROG")), _console must be None. It must not be populated during construction.
  • A public console attribute that can be assigned a rich console object (e.g. the object returned by rich.get_console()). After assigning to console, the _console attribute must be non-None.

The construction signature must at minimum accept the program name as the first positional argument, consistent with argparse.HelpFormatter (e.g. RichHelpFormatter(prog=...) and RichHelpFormatter("PROG") must both work).

3. _rich_expand_help(action) method

RichHelpFormatter must provide a method:

def _rich_expand_help(self, action) -> Text

where Text is rich.text.Text.

This method is the rich-rendering counterpart of the standard argparse.HelpFormatter._expand_help(action) method. For a given argparse.Action whose help string contains %-style format specifiers (e.g. %(prog)s, %(prog)d, etc.), the behavior must match the standard _expand_help as follows:

  • Success case: When _expand_help(action) produces a string successfully, _rich_expand_help(action) must return a rich.text.Text object whose plain text (.plain) equals the string produced by _expand_help(action). That is, the same format-specifier substitution and expansion is performed, but the result is wrapped as a Text object.

  • Error case: When _expand_help(action) raises a ValueError (for example, when a format specifier is incompatible with the value being substituted — such as applying a numeric conversion specifier to a non-numeric prog), _rich_expand_help(action) must raise a ValueError with the identical args tuple.

The set of format specifier characters that, when applied to a numeric prog value, are valid includes the numeric/conversion specifiers (c, d, e, E, f, F, g, G, i, o, u, x, X, *); for all other printable format characters a string prog value is appropriate. The correctness requirement is simply that _rich_expand_help mirrors _expand_help's success value (as Text) and error args across the full range of printable format specifier characters.

Public API Summary

  • Module: rich_argparse
  • Class: RichHelpFormatter (usable as an argparse formatter_class)
    • Constructor accepting prog as first positional/keyword argument.
    • Attribute _console: None immediately after construction.
    • Attribute console: assignable; assigning a console object makes _console non-None.
    • Method _rich_expand_help(self, action) -> rich.text.Text.

Notes

  • The formatter must continue to function as a valid argparse formatter class and produce help output via format_help().
  • No rich import may occur before help is rendered.

Overview

rich_argparse provides RichHelpFormatter, a Rich-rendered formatter for Python's argparse module. The formatter currently mishandles escaped percent signs in some interpolated text. In standard argparse formatting, %% represents one literal %; RichHelpFormatter must preserve that behavior without changing its established Rich presentation.

The required change applies to percent substitution and escaping in custom usage strings, argument help strings, and version output. It must not remove or alter existing heading transformations, styles, highlighting, markup support, wrapping behavior, or argparse compatibility unrelated to percent processing.

Public API

RichHelpFormatter must remain importable from rich_argparse and usable as a drop-in formatter_class for argparse.ArgumentParser:

import argparse
from rich_argparse import RichHelpFormatter

parser = argparse.ArgumentParser(
    prog="my-program",
    formatter_class=RichHelpFormatter,
)

Its existing formatter constructor options and class-level presentation controls must remain compatible. In particular:

  • group_name_formatter is a callable used to transform the usage heading and argument-group headings. Its default is str.title.
  • styles remains the configurable mapping of Rich semantic style names.
  • highlights remains the configurable list of regular-expression highlights.
  • usage_markup remains a boolean controlling Rich markup in user-supplied usage strings and defaults to False.

No new public function or class is required.

Required Behavior

Argparse-compatible percent interpolation

Where argparse applies %-style mapping interpolation, RichHelpFormatter must produce the same visible characters as the standard formatter. This includes:

  • %(prog)s and other supported conversions in a custom usage string;
  • action parameters such as %(prog)s, %(default)s, %(type)s, %(type)r, %(metavar)s, and %(choices)s in argument help;
  • flags, widths, precision, and conversion types accepted by argparse/Python formatting, such as %(default).5f; and
  • %(prog)s interpolation performed while rendering a version action.

Interpolation must retain argparse's parameter preparation and error behavior. For example, callable/type values represented by their __name__, joined choice values, numeric conversions, and invalid format specifiers must behave as they do with argparse.HelpFormatter. Values must not be prematurely converted to strings in a way that breaks conversions such as .5f or r.

Percent processing is a single formatting pass. It must not substitute text newly exposed by an escaped percent sequence. In every affected interpolated string:

  • %% becomes one literal %;
  • %%%% becomes %%;
  • an escaped mapping expression such as %%(prog)s becomes the literal text %(prog)s, not the program name; and
  • %%%(prog)s becomes % followed by the substituted program name.
Required examples

For a program named <prog>, this custom usage source:

%(prog)s [%%options] %% [args]

must have the visible result:

<prog> [%options] % [args]

For a program named [underline], this two-line usage source:

%(prog)s [%%options] %% [args]
%%%(prog)s %%(prog)s [%%%%options] %%%% [args]

must have the visible result:

[underline] [%options] % [args]
%[underline] %(prog)s [%%options] %% [args]

The argument help source:

%%(prog)s %%%(prog)s %% %%%% %%%%prog

must render as:

%(prog)s %<prog> % %% %%prog

The version source:

%(prog)s %%1.0.0

must print as:

<prog> %1.0.0

followed by argparse's normal terminating newline.

Literal replacement values and Rich markup

Values inserted by percent substitution must be escaped from Rich markup before they are rendered. Program names, defaults, type names, metavars, and other replacement values may contain arbitrary characters, including strings resembling Rich tags such as [underline], [italic], [bold], [link], or [default]. Those values must remain visible literal text and must not be removed or interpreted as markup. Directly rendered program names, metavars, type names, and defaults must likewise retain their textual characters.

This escaping applies to replacement values, not to markup deliberately authored in fields where RichHelpFormatter already supports Rich markup. Correct percent handling must continue to allow that surrounding markup and the formatter's normal highlighting to work.

For example, a type whose __name__ is [link], a default of [default], and a metavar of [bold] must display those exact bracketed strings. A float default of 1.5 formatted with %(default).5f must display 1.50000, and %(type)r for str must display 'str'.

Parser descriptions, epilogs, and group descriptions must retain their existing %(prog)s substitution behavior, including literal rendering of a program name that resembles markup.

Preserve Rich-specific presentation

Correcting % handling must not turn RichHelpFormatter into an unstyled copy of argparse.HelpFormatter. The following established behavior must remain intact:

  • Heading transformation: group_name_formatter continues to transform the usage prefix and group headings. With the default str.title, headings are title-cased, such as Usage:, Positional Arguments:, and Options: (subject to the heading names supplied by the running Python version). A caller-provided formatter such as str must continue to be honored.
  • Semantic styles: when the Rich console emits color, the configured styles continue to produce ANSI styling. The default semantic mapping remains argparse.args = cyan, argparse.groups = dark_orange, argparse.help = default, argparse.metavar = dark_cyan, argparse.syntax = bold, argparse.text = default, and argparse.prog = grey50.
  • Generated usage styling: auto-generated usage continues to style the usage heading, program name, options, positional arguments, and metavars according to their semantic roles. Actual program-name substitutions in user usage continue to receive argparse.prog styling. Percent escaping must not shift, lose, or misapply these styles.
  • Inline highlights: descriptions, epilogs, group descriptions, and argument help continue to use highlights. By default, option-like words are highlighted with argparse.args, and text enclosed in backticks is highlighted with argparse.syntax. User-added highlight patterns and repeated uses of the same style remain supported.
  • Custom usage markup: with usage_markup = False (the default), a user-supplied usage string is treated as plain text, so markup-looking brackets remain visible. With usage_markup = True, explicit Rich markup in that usage string is interpreted. Percent interpolation and %% collapsing occur correctly in either mode, before the normal rendering behavior is applied.

ANSI escape sequences and Rich markup interpretation are intentional presentation differences. Therefore, compatibility with the standard formatter means equality of the percent-substituted visible text after accounting for configured heading transformation, styling, highlighting, and explicitly enabled markup; it does not require the complete output byte stream to equal the unstyled standard formatter in every configuration.

General formatting compatibility

Subject to the intentional Rich-specific behavior above, help output must continue to follow argparse's structure and established formatter behavior, including:

  • generated and user-supplied usage lines and continuation lines;
  • descriptions, epilogs, and argument-group descriptions;
  • section and group placement;
  • argument invocations, option strings, positional arguments, metavars, and subparsers;
  • help text parameter expansion;
  • indentation, configured width and help position, padding, and line wrapping;
  • suppressed usage, groups, and actions; and
  • version action output.

The percent fix must remain compatible with the existing Rich formatter variants and with formatter subclasses or mixins that rely on argparse.HelpFormatter behavior.

Non-goals

  • Do not remove title-cased headings, semantic colors, highlighting, or program-name styling to force universal byte-for-byte identity with the standard formatter.
  • Do not change the default value or meaning of usage_markup.
  • Do not interpret markup-looking substitution values as a side effect of fixing percent expansion.
  • Do not add a new public API solely for percent escaping.

  • Only the wrapping behavior of group titles/headings changes. All other rendering — usage lines, option/argument help text, group descriptions, and general wrapping of body text to the configured width — remains unchanged.
