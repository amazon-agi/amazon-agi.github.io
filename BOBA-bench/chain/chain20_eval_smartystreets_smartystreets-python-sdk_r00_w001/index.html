12 Update the smartystreets_python_sdk response and retry APIs so responses can carry headers and errors independently, existing two-argument response… 884 words · rewritten by GPT-5.6-sol

Overview

Update the smartystreets_python_sdk response and retry APIs so responses can carry headers and errors independently, existing two-argument response construction remains compatible, and HTTP 429 rate limiting uses the retry sender's maximum backoff step. Existing SDK behavior outside these response and retry contracts must remain unchanged.

1. Response public data model

Response must remain importable with:

from smartystreets_python_sdk import Response

Its constructor must support this signature:

Response(payload, status_code, headers=None, error=None)

The values have the following meanings and must be exposed without transformation on attributes of the same names:

  • payload -> response.payload
  • status_code -> response.status_code
  • headers -> response.headers
  • error -> response.error

The first two arguments remain required. Both trailing arguments are optional, preserving existing calls such as Response(payload, status_code). In that two-argument form, both response.headers and response.error must be None. Three-argument construction assigns the third value to headers, not to error.

All four positions may contain None. In particular, an error-only response can be represented as:

response = Response(None, None, None, some_error)
assert response.error is some_error

The fourth value may be an exception or any other error value; Response must retain that value as supplied.

2. HTTP sender integration

Responses produced from a completed raw HTTP response must preserve all three transport values:

  • the raw response text as payload;
  • the raw status code as status_code; and
  • the raw response headers as headers.

The headers value must be preserved even when it is None. A raw response whose headers attribute is None is valid and must not cause response conversion to fail. No copying, parsing, or normalization of the headers is required.

When the HTTP sender catches a transport exception, the resulting SDK response must place the exception in the fourth constructor position so it is available through .error; its payload, status code, and headers are None. This preserves the existing behavior of API clients that raise a non-null response error.

3. Module-level backoff function

The smartystreets_python_sdk.retry_sender module must expose:

backoff(attempt, ignore_max=False)
  • attempt supplies the wait-duration step.
  • ignore_max is optional, defaults to False, and must be accepted either positionally or by keyword.
  • With the normal capped behavior, the effective wait must not exceed RetrySender.MAX_BACKOFF_DURATION, whose value is 10. If ignore_max=True, the caller is explicitly requesting that the maximum-duration cap not be applied.

The function remains responsible for performing the wait associated with the effective duration.

4. RetrySender behavior

The public retry component remains the class importable as:

from smartystreets_python_sdk import RetrySender

It is constructed and used as follows:

sender = RetrySender(max_retries, inner_sender)
response = sender.send(request)

inner_sender must provide send(request) and return a Response. Retry behavior belongs to RetrySender.send(request) itself. A separate module-level send_with_retry(max_retries, sender) API is not required.

General retry contract
  1. send(request) first calls inner_sender.send(request) once.
  2. A response with status_code == 200 is returned immediately without backoff or another send. Success is determined by the status code; the retry sender must not clear or replace response fields, including .error.
  3. A response whose status code is not 200 is retried while retries remain. Before each retry, the retry sender invokes the module-level backoff callable.
  4. Every retry must pass the same request object originally supplied to RetrySender.send.
  5. max_retries counts sends after the initial send. Thus, at most max_retries + 1 sends occur. With zero retries, the first response is returned directly.
  6. If a later response has status 200, that exact final response is returned. If the retry allowance is exhausted without a 200, the exact last response is returned.

For ordinary non-200, non-429 responses, the backoff attempt values retain their zero-based progression: 0 before the first retry, then 1, 2, and so on. The effective ordinary wait remains capped at 10. For example, four allowed retries after repeated ordinary failures produce four backoff steps corresponding to 0, 1, 2, and 3, followed by return of the fifth response if it is still unsuccessful.

HTTP 429 rate limiting

HTTP status 429 is retryable under the same retry allowance, but it has special backoff behavior. Before resending after a 429, RetrySender.send must invoke the module-level backoff callable with a first argument of exactly 10, the maximum backoff step. It must not use the old fixed value 5 or the ordinary zero-based retry index for this argument.

Consequently, with one retry allowed and an inner sender that returns 429 followed by 200:

  • the inner sender is called twice with the same request;
  • backoff is called once with first argument 10; and
  • the second, successful response is returned.

The retry sender must return the final response without discarding its error value. For example, if the sender's 429 and subsequent 200 responses are constructed with "Big bad" as their fourth value, the returned successful response must have response.error == "Big bad".

Compatibility and scope

  • Existing two-argument Response calls must continue to work unchanged.
  • Code that supplies headers uses the third constructor value; code that supplies an error uses the fourth value or the error keyword.
  • Existing API clients must continue to raise errors obtained from response.error and otherwise continue their established serialization, request-building, and result-assignment behavior.
  • Do not introduce unrelated changes to other SDK APIs or behavior.
