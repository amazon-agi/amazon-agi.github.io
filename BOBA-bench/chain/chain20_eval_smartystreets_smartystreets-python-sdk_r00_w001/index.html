Components Required

A class that represents a reverse-geo lookup by coordinates.

Signature of the constructor:

  • Accepts a latitude and a longitude, which are numeric values.
  • Stores these values so that the Client can access/use them when it builds a request.
The Client class

A class whose job is to send a Lookup to the backend.

  • sender: an object that has a send(request) method. When send is invoked, it is given a request object; that request object exposes a parameters dictionary (a mapping of parameter name to value), and the client populates it.

Remarks

12 The smartystreets_python_sdk response and retry APIs are to be updated so that responses can carry headers and errors independently, the existing… 987 words · rewritten by GPT-5.6-sol, reworded by GLM-5.3-Flash

Task Description

Summary

The smartystreets_python_sdk response and retry APIs are to be updated so that responses can carry headers and errors independently, the existing two-argument form of response construction remains compatible, and the retry sender's maximum backoff step is what HTTP 429 rate limiting uses. Existing SDK behavior that lies outside these response and retry contracts must remain unchanged.

1. The public data model of Response

Response must stay importable via:

from smartystreets_python_sdk import Response

The constructor must support the following signature:

Response(payload, status_code, headers=None, error=None)

The values have these meanings and must be exposed without transformation on attributes of the same names:

  • payload -> response.payload
  • status_code -> response.status_code
  • headers -> response.headers
  • error -> response.error

The first two arguments are still required. Both trailing arguments are optional, which preserves existing calls such as Response(payload, status_code). In that two-argument form, response.headers and response.error must both be None. When the constructor is given three arguments, it assigns the third value to headers, not to error.

Every one of the four positions may contain None. In particular, a response that carries only an error can be represented like this:

response = Response(None, None, None, some_error)
assert response.error is some_error

The fourth value may be an exception or any other error value; Response must retain that value as it was supplied.

2. Integration with the HTTP sender

When a raw HTTP response has completed, the responses built from it must preserve all three transport values:

  • the raw response text as payload;
  • the raw status code as status_code; and
  • the raw response headers as headers.

Even when it is None, the headers value must be preserved. A raw response whose headers attribute is None is valid, and it must not cause response conversion to fail. The headers require no copying, parsing, or normalization.

If the HTTP sender catches a transport exception, the SDK response that results must put the exception into the fourth constructor position so that it is available through .error; its payload, status code, and headers are None. This is what keeps the existing behavior of API clients that raise a non-null response error in place.

3. The module-level backoff function

The smartystreets_python_sdk.retry_sender module must expose the function below:

backoff(attempt, ignore_max=False)
  • The wait-duration step is what attempt supplies.
  • ignore_max is optional, has a default of False, and must be accepted either positionally or by keyword.
  • Under the normal capped behavior, the effective wait must not exceed RetrySender.MAX_BACKOFF_DURATION, whose value is 10. If ignore_max=True, the caller is explicitly requesting that the cap on maximum duration not be applied.

The function is still responsible for performing the wait tied to the effective duration.

4. The behavior of RetrySender

The public retry component is still the class importable via:

from smartystreets_python_sdk import RetrySender

It is constructed and used this way:

sender = RetrySender(max_retries, inner_sender)
response = sender.send(request)

The inner_sender must provide send(request) and return a Response. Retry behavior lives in RetrySender.send(request) itself. No separate module-level send_with_retry(max_retries, sender) API is required.

The general retry contract
  1. send(request) first calls inner_sender.send(request) a single time.
  2. When a response has status_code == 200, it is returned immediately without backoff or another send. The status code is what determines success; the retry sender must not clear or replace response fields, including .error.
  3. A response whose status code is not 200 is retried as long as retries remain. The retry sender invokes the module-level backoff callable before each retry.
  4. Each retry must pass the same request object that was originally supplied to RetrySender.send.
  5. max_retries counts the sends that happen after the initial send. Therefore at most max_retries + 1 sends take place. If there are zero retries, the first response is returned directly.
  6. If a later response has status 200, that exact final response is the one returned. If the retry allowance is used up without a 200, the exact last response is the one returned.

With ordinary non-200, non-429 responses, the backoff attempt values keep their zero-based progression: 0 before the first retry, then 1, 2, and so on. The effective ordinary wait is still capped at 10. For example, four allowed retries after repeated ordinary failures produce four backoff steps corresponding to 0, 1, 2, and 3, after which the fifth response is returned if it is still unsuccessful.
