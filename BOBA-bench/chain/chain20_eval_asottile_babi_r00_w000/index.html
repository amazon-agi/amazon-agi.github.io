01 Text Editor babi 1562 words · source specification

Task Specification: Text Editor babi

Overview

Implement (or extend) a terminal-based text editor named babi, exposed as an importable Python module babi and runnable via python -m babi. The editor loads a text file, displays it, and supports arrow-key navigation. Several small public APIs must be importable from the babi module for direct unit testing.

Module-Level Public API

The following must be importable from the top-level babi module.

babi.VERSION_STR

A string constant. It is displayed somewhere on screen when the editor starts (in the header/status area). Tests only rely on its presence on the initial screen and its disappearance when the header area is hidden or overwritten.

babi.Position

A class constructible with no arguments: Position(). Its repr() must be exactly:

Position(file_line=0, cursor_line=0, x=0, cursor_x_hint=0)

So it has (at least) four fields — file_line, cursor_line, x, cursor_x_hint — all defaulting to 0, rendered in that order in the repr.

babi._get_lines(f)

Takes a text file-like object (supporting iteration/reading, e.g. io.StringIO) and returns a 3-tuple (lines, newline, mixed):

  • lines: a list[str] of the file's lines with line endings stripped, plus a trailing empty string always appended (representing the special end-of-file line). Examples:
    • '' → ['']
    • '1\n2\n' → ['1', '2', '']
    • '1\n2' (no trailing newline) → ['1', '2', '']
  • newline: the detected newline string.
    • Pure LF input → '\n'
    • Pure CRLF input → '\r\n'
    • Mixed line endings → '\n'
    • Empty input → '\n'
  • mixed: a bool, True only if the file contained more than one distinct kind of line ending (e.g. one \r\n and one \n), otherwise False.

Command-Line Interface

python -m babi [OPTIONS] [FILENAME]

Startup

On startup the editor draws a screen that includes VERSION_STR. When a filename is given, the file contents are loaded and displayed starting at the top.

--color-test

When invoked with --color-test, the editor renders a color test screen. Somewhere in the rendered output the sequence * 1* 2 appears (numbered color swatches). It must work whether or not the terminal advertises 256-color support (i.e. with TERM=screen-256color and with TERM=screen). This screen is a normal editor state that can be exited with C-x.

Running without a file / without color

The editor must start successfully with no filename argument, and must start successfully in a non-color terminal (TERM=screen).

Exiting

Pressing C-x exits the editor cleanly (process terminates).

Screen Layout

The terminal has a width and a height (in character cells). The editor occupies the whole pane. The layout by height:

  • Normal height (≥ 3 rows): A header/status region (containing VERSION_STR and the file's name/modified indicator) occupies the top; the file body is displayed below it.
  • Height == 2: The header is hidden. Behaviour is otherwise normal. With a single-line file hello world, the full screenshot is exactly hello world\n\n (the file line, then blank lines filling the pane). Pressing an unhandled key still shows a status message.
  • Height == 1: Only the file body is shown. With file hello world, the full screenshot is exactly hello world\n. A status message (see below) can temporarily replace the single body row and takes precedence over the body; it is cleared after a single subsequent key action, restoring the body.

File Name / Modified Indicator

When a file is loaded, the header shows the file's base name. A modified (dirty) file is indicated by appending * to the name (e.g. f *).

Mixed newlines

If the loaded file has mixed newline styles, the buffer is treated as modified from the start (shows the * indicator) and a status message is displayed:

mixed newlines will be converted to '\n'

(The literal text contains a backslash-n inside single quotes, exactly as written above.)

Status Messages

Pressing a key that has no bound action displays the status message:

unknown key

This message is cleared (disappears) after a subsequent recognized key action. Specifically: after showing unknown key, a large number of no-op movement presses (e.g. pressing Left repeatedly at the start of the buffer) does not clear it, but one more recognized action press clears it. In practice the message persists across roughly 24 further presses and then clears; implement it as: the status message is displayed for one "draw cycle" plus is retained until the next accepted keypress that actually performs/attempts an action, at which point it clears. (Behaviorally: press an unknown key → message shown; keep pressing keys → after enough presses the message clears.)

On a 1-row terminal, showing unknown key replaces the body row; after one more key action the message clears and the body reappears.

Cursor / Navigation Behaviour

Cursor position is reported in terminal cell coordinates (x, y) where y counts from the top of the pane. In normal-height layout with a header, the first body line is at y == 1. The cursor starts at the beginning of the first line.

The buffer always has a trailing special empty end-of-file line (from _get_lines), and the cursor may rest on it.

Arrow keys: Left, Right, Up, Down.

Horizontal movement (Left / Right)
  • Right advances the cursor one column within the current line.
  • Left moves the cursor one column left within the current line.
  • At the start of the buffer (line 0, column 0), Left is a no-op.
  • At the beginning of a line (column 0, not the first line), Left wraps to the end of the previous line.
  • At the end of a line, Right wraps to the beginning of the next line.
  • On the special end-of-file line (empty, last line), Right is a no-op (cannot move past end of buffer).
Vertical movement (Up / Down)
  • Up on the first line is a no-op.
  • Down past the last (end-of-file) line is a no-op.
  • Moving to another line places the cursor at a column derived from a remembered horizontal target ("hint"):
    • The hint is set by explicit horizontal movement.
    • When moving vertically, the cursor's column becomes min(hint, length of the destination line) — it never goes past the end of the destination line.
    • The hint is preserved across vertical moves so that moving through a short line and onto a longer line restores the higher column.

Worked example. Given a file with lines:

short              (length 5)
                   (empty, length 0)
long long long long(length 19)
                   (end-of-file empty line)

Starting cursor (0, 1) (col 0 of short):

  • Left → (0,1); Up → (0,1) (no-ops at buffer start).
  • Right, Right → (2,1).
  • Left → (1,1).
  • Up → (1,1) (no-op, first line).
  • Down → (0,2) (empty line, col clamped to 0; hint from col 1 exceeds line length 0).
  • Down → (1,3) (long line, col restored to hint 1).
  • Down → (0,4) (end-of-file line).
  • Down → (0,4) (no-op, end of buffer).
  • Right → (0,4) (no-op on end-of-file line).
  • Left → (19,3) (wrap to end of previous line long long long long).
  • Right → (0,4) (wrap to next line).
  • Left, then Up, Up → (5,1): the hint is now large (end of the 19-char line), but on short the column clamps to its length 5.
  • Down, Down → (19,3): hint retained, restores to end of the long line.

Scrolling

When the file has more lines than fit in the body area, the cursor moving beyond the visible region scrolls the view.

Example (height 10, file with 10 lines line_0..line_9)
  • Initially the top lines are visible (line_7 visible).
  • Pressing Down 7 times moves the cursor down without scrolling; line_0 still visible; cursor at (0, 8).
  • One more Down scrolls the view: line_8 becomes visible, cursor moves to (0, 4), and line_8 appears on screenshot row index 4 (0-based line 4).
  • From there, 3 Up presses do not scroll (line_9 still visible); a 4th Up scrolls back so line_0 is visible.

The scrolling keeps the cursor within the visible body, scrolling by a page-ish amount when the cursor would leave the visible region, so that after a downward scroll the current line sits near the top of the body.

Resize Behaviour

The editor must react to terminal resize events, redrawing the layout for the new width/height. After a resize the top line of the display generally changes (header re-rendered for the new width).

Resize scroll adjustment

When the terminal is resized smaller such that the cursor's current line would fall outside the (now shorter) visible body, the view scrolls up so the cursor remains visible; a resize that still fits the cursor does not scroll.

Example

File with 10 lines line_0..line_9, default height. Move cursor down 7 times (cursor at (0, 8)).

  • Resize to height 10: does not scroll; line_8 was previously not visible and becomes visible / cursor stays at (0, 8); line_8 is now on screen.
  • Resize to height 9 (smaller): scrolls up so line_0 is no longer visible, cursor ends at (0, 3), and the cursor's line line_7 is on screenshot row index 3.

Notes

  • Terminal color support depends on TERM; the editor must degrade gracefully when 256-color support is unavailable.
  • All the keypress bindings referenced: C-x (exit), C-j (unhandled → unknown key), Left, Right, Up, Down.
02 Text Editor Cursor Movement, Editing, and Horizontal Scrolling 1478 words · source specification

Task Specification: Text Editor Cursor Movement, Editing, and Horizontal Scrolling

You are working on a terminal-based text editor implemented in a module named babi. This task covers the editor's Position state representation, cursor navigation keys, basic text editing operations, and horizontal scrolling behavior. The editor is driven inside a tmux pane; keys are sent to it and its screen and cursor state are observed.

1. Position representation

The babi module exposes a Position class. When constructed with no arguments, its repr() must be exactly:

Position(file_line=0, cursor_line=0, x=0, x_hint=0)

That is, the position tracks four integer fields, all defaulting to 0, named (in this order): file_line, cursor_line, x, x_hint. The field previously representing the horizontal hint must be named x_hint.

2. Screen / cursor conventions

The editor occupies a terminal pane. The top row (row 0) is a status/header area; file content is rendered starting at row 1. Cursor position is reported as an (x, y) pair, where x is the 0-based column and y is the 0-based row on screen.

A file opened for editing shows its lines starting at screen row 1. There is a virtual "end-of-file" line one past the last real line of text: pressing Down through the last line lands the cursor at column 0 on this empty trailing line.

When the file is modified (has unsaved changes), the status area shows the filename followed by * (e.g. f *). When the file is unmodified, no * appears anywhere on screen.

If a key press is not handled, the status area shows text containing unknown key.

3. Vertical cursor movement (arrow keys)

Given the four arrow keys Up, Down, Left, Right:

  • Left / Right move the cursor one column within the current line.
  • At the very beginning of the file, Left and Up are no-ops (cursor stays at (0, 1)).
  • Up on the first line of the file is a no-op.
  • Moving Left from column 0 of a line wraps to the end of the previous line.
  • Moving Right from the end of a line wraps to column 0 of the next line.
  • Pressing Down past the last text line lands on the virtual end-of-file line at column 0; pressing Down or Right there again is a no-op.
  • The cursor cannot move past the end of the file.

Horizontal hint (x_hint) behavior: When moving vertically, the editor remembers the desired x column. If the target line is shorter than the remembered column, the cursor is clamped to the end of that shorter line, but the remembered hint is preserved so that moving onto a longer line restores the original column. Example with lines of differing length: from a long line, moving up onto a short line clamps x to that line's length (e.g. x=5); moving back down onto a longer line restores the higher column (e.g. x=19).

4. Vertical scrolling

The pane has a fixed number of content rows. When the cursor would move below the visible content area, the view scrolls so the cursor stays on screen. For a pane content height where 7 Down presses keep the cursor at (0, 8), the 8th Down press scrolls: the cursor moves to (0, 4) and the line that was below the fold becomes visible at row 4.

Scrolling up when the cursor is above the visible area scrolls the view back up to reveal earlier lines.

5. Home / End keys

Two navigation keys move within the current line. Each is bound to two key names:

  • End — key names End and C-e: moves the cursor to the end of the current line (column equal to the line length). This sets the horizontal hint such that moving Down afterward keeps the cursor at end-of-line-column positions.
  • Home — key names Home and C-a: moves the cursor to column 0 of the current line. Moving Down afterward retains column 0.

6. Basic text insertion

Typing printable text inserts it at the cursor. Typed characters appear in the file content. After typing on one line, pressing Down and typing again inserts on the next line.

7. Enter key

Pressing Enter splits the current line at the cursor:

  • At the beginning of a line, it inserts a blank line before the current text and the cursor moves to (0, next_row).
  • Mid-line, the text after the cursor moves to a new line below; the cursor moves to column 0 of that new line.
  • After an Enter split, pressing Up returns the cursor to (0, previous_row).
  • The Enter edit marks the file modified.

8. Bspace (Backspace) key

  • At the very beginning of the file, Bspace is a no-op: no unknown key message appears, the file remains unmodified (no *), and no content is added.
  • When at column 0 of a non-first line, Bspace joins the current line onto the end of the previous line. The cursor moves to the join column on the previous line, the file is marked modified. The join column becomes the new horizontal hint (moving Down afterward keeps that column).
  • Mid-line/after some characters, Bspace deletes the character immediately before the cursor, moves the cursor left one column, and marks the file modified.
  • Backspacing that empties trailing content must still leave a navigable end-of-file line: after such an edit, pressing Down lands the cursor at (0, 2); the file must not be marked modified when the operation resulted in no net change (no *).

9. DC (Delete) key

  • At the end of the file, DC is a no-op: no unknown key message, and the file is not marked modified (no *).
  • Mid-line, DC removes the character immediately after the cursor and marks the file modified.
  • At the end of a line, DC joins the following line onto the current line and marks the file modified.

10. Horizontal scrolling

When a line is wider than the pane, the editor scrolls horizontally and shows continuation markers:

  • If content extends past the right edge, the rightmost visible column shows a » (right guillemet) marker.
  • If content is scrolled such that there is hidden content to the left, the leftmost visible column shows a « (left guillemet) marker.

Behavior for a pane of width 80:

  • On a long line, before scrolling, the right edge shows the » marker.
  • Moving Right past the visible right edge scrolls the view horizontally: both a « marker on the left and a » marker on the right appear as appropriate, and the cursor's reported x reflects its position within the newly scrolled view.
  • For a line exactly 80 characters wide: moving the cursor to column 78 shows no » marker (the content fits), with the cursor at (78, 1). One more Right scrolls, showing « at the left, with the cursor at (7, 1).

For narrow panes:

  • Width 5: on a long line the visible region shows content followed by ». As the cursor advances right, at the scroll point the left « appears and the cursor's x is reported relative to the scrolled window (e.g. x=3). Further right movement scrolls further, updating the visible content window.
  • Width 1: the pane shows a single » marker while on a long line. After moving right several times and then restoring a wider pane, the full line is visible again and the cursor reports its absolute column (e.g. x=3 after 3 right presses).
  • Very narrow pane (width 5) with an unhandled key: pressing an unhandled key still renders a (truncated) unknown key message; the visible truncated form begins with unkno.

Public API / Test Harness Support

The following must exist so tests can exercise the above.

babi.Position

As described in section 1: a class whose no-arg repr() is Position(file_line=0, cursor_line=0, x=0, x_hint=0).

Test-runner helper methods

The test harness drives the editor through a runner object (an instance of a Runner subclass) with these observation methods. Implement/support the following signatures on the runner used by tests:

  • await_text(self, text, timeout=None) — polls the screen until text appears somewhere in the current screenshot (substring match, without altering newlines); raises AssertionError on timeout.
  • await_text_missing(self, s) — polls until s no longer appears on screen.
  • _get_cursor_position(self) — returns the current (x, y) cursor position as a tuple of ints, obtained from the pane.
  • await_cursor_position(self, *, x, y) — keyword-only x and y; polls until the cursor position equals (x, y); raises AssertionError on timeout, including the last observed position in the message.

The editor is launched either with no file (an empty new buffer) or with a filesystem path to an existing file. Runner support includes launching with a specified pane height and temporarily resizing the pane to a given width and height.

03 babi Editor Enhancements 1613 words · source specification

Task Specification: babi Editor Enhancements

You are working on babi, a terminal-based text editor implemented as a Python package importable as import babi. This task modifies the internal file-state model and adds several editor navigation, multi-file, and process-control behaviors. The package is run as a module (python -m babi <files...>).

The following are exercised through a real tmux-driven integration harness plus one direct repr check. Implement exactly what is described below.

1. Combine file state into a single File class

Replace the previously separate position/file state with a single public class babi.File.

  • Constructor signature: babi.File(filename), where filename is a string.
  • The class must have a repr that renders as a multi-line block in exactly this format:
File(
    filename='f.txt',
    modified=False,
    lines=[],
    nl='\n',
    file_line=0,
    cursor_line=0,
    x=0,
    x_hint=0,
)

Concretely, for a freshly constructed babi.File('f.txt'), repr() must equal:

File(\n    filename='f.txt',\n    modified=False,\n    lines=[],\n    nl='\n',\n    file_line=0,\n    cursor_line=0,\n    x=0,\n    x_hint=0,\n)

That is: the header File(, then each attribute on its own line indented by 4 spaces, in the order filename, modified, lines, nl, file_line, cursor_line, x, x_hint, each followed by a trailing comma, then a closing ) on its own line. Each attribute value is rendered via its standard Python repr. For a new file the defaults are: modified=False, lines=[], nl='\n', and all four positional counters (file_line, cursor_line, x, x_hint) equal to 0.

(The prior babi.Position class no longer exists as a public entry point; this File repr replaces it.)

2. Version string constant

Expose a module-level string constant babi.VERSION_STR. When the editor starts, this exact string must appear somewhere on the screen (e.g. in the status/title area).

3. Opening files: new-file and non-file handling

When babi is launched with a path argument:

  • New file (path does not exist): The editor opens with an empty buffer. The provided filename is displayed on screen, and the text (new file) is displayed somewhere on screen.
  • Path is a directory (not a regular file): The editor opens with an empty buffer. The status text <<new file>> is displayed, and an informational message containing <name>' is not a file is displayed (where <name> is the trailing component of the path, e.g. for a directory named d the message contains d' is not a file).

4. Escape key

Pressing Escape currently has no bound command. It must produce the status message unknown key (same behavior as any other unrecognized key).

5. Page navigation

The editor shows a fixed number of text rows determined by the terminal height. Assume the top row is a header/status line and the bottom row is a status line, so the number of visible text rows is height - 2. Cursor row y in the following is the on-screen row (row 0 is the top header line; text begins at y=1).

Page Down / Page Up

Two key bindings each must trigger "page down": PageDown and ^V. Two key bindings each must trigger "page up": PageUp and ^Y.

Behavior for a file whose lines are line_0 ... line_9:

  • Page down advances the viewport by one page so that a new page of lines becomes visible, and places the cursor at the top text row (x=0, y=1) on the line that is now at the top of the visible region.

    • With a height=10 window (8 visible text rows), starting at the top, after one page down the line at the top text row is line_6, and line_8 is visible.
    • With a height=4 window (2 visible text rows), starting at the top, after one page down line_2 is visible and the cursor sits on line_1 at y=1.

  • Page up moves the viewport back by one page, again placing the cursor at the top text row (x=0, y=1).

    • From the state reached after a page down in the height=10 case, a page up returns to the top so line_0 is at the top text row, line_8 is no longer visible, and cursor is at x=0, y=1.
    • In the height=4 case, after a page down then a single Down, a page up scrolls back so line_0 is at the top text row (cursor x=0, y=1) and line_2 is no longer visible.

  • Page navigation must not scroll such that the top row is above the start of the file (the scroll offset must never go negative).

  • Paging past the end of the file is bounded by the last line. In the height=10 case, after paging down twice, the cursor lands at x=0, y=5 on an empty trailing line (the position just past line_9); pressing Up from there moves the cursor to y=4 onto line_9.

  • When paging, pressing arrow keys afterward behaves consistently with the current cursor line (moving Up from the empty trailing position lands on the last real line).

Cursor line resolution during paging

Vertical position semantics: after paging, the cursor is placed on a real text line where possible; where the cursor lands past the final line it rests on the empty line following the last line.

6. Ctrl-Home and Ctrl-End

  • ^Home moves to the very beginning of the file. After scrolling down (e.g. several page downs so line_0 is off-screen), pressing ^Home scrolls the viewport back so line_0 is visible at the top text row and the cursor is at x=0, y=1.

  • ^End moves to the end of the file (the position after the last line). The viewport scrolls so the last line is visible.

    • With height=6 (4 visible text rows) starting at the top, ^End places the cursor at x=0, y=3 and the on-screen row at index 2 shows line_9 (i.e., the last line is the second-to-bottom visible text row, with the cursor on the empty trailing line below it).
    • With height=8 (6 visible text rows): if already scrolled to the last page (e.g. after one page down leaving line_9 visible and cursor at x=0, y=1), then ^End places the cursor at x=0, y=7 with on-screen row index 6 showing line_9.

7. Resize must not scroll past the top

On resize, the viewport may need to scroll up to keep the cursor visible, but the scroll offset must never become negative. For a file line_0 ... line_9 opened in the default window:

  • After pressing Down five times (cursor at x=0, y=6), resizing the window to 80x7 hides line_9; then the original size restores and line_9 is visible again. After two Up presses, the on-screen row at index 1 shows line_0 (i.e. the buffer remains scrolled to the top, not into negative offset territory).

8. Multiple open files

The editor accepts multiple file path arguments and opens them as an ordered list, showing one at a time.

Given three files file_a (content a text), file_b (b text), file_c (c text) opened in that order:

  • Initially the first file is shown: its name file_a appears, an indicator [1/3] appears, and its content a text appears.
  • M-Right switches to the next file (wrapping is not required in this direction for the tested cases, but see below). Switching to file_b shows file_b, indicator [2/3], content b text, and resets the cursor to x=0, y=1.
  • M-Left switches to the previous file, wrapping around. From file_b, M-Left returns to file_a (indicator [1/3]). From file_a, a further M-Left wraps to the last file file_c (indicator [3/3], content c text).
  • Per-file cursor position is retained: after moving the cursor Right in file_a (to x=1, y=1), switching away and back to file_a restores the cursor at x=1, y=1.
  • The indicator format is [<current>/<total>] using 1-based numbering.
Closing files
  • C-x closes the current file. When more than one file remains open, closing moves to the next file in the list (the following file becomes current and its name is displayed). When the last remaining file is closed, the editor exits.
    • With file_a, file_b, file_c all open and file_a current: C-x closes it and shows file_a... (the next file); pressing C-x again shows the following file; a final C-x exits.

9. Suspend / resume

Pressing C-z suspends the editor process (as with a standard terminal SIGTSTP-style suspend), returning control to the invoking shell so the editor's rendered content is no longer displayed. Bringing the job back to the foreground (shell fg) resumes the editor and re-renders its content. After resuming, normal editing continues (e.g. C-x to close/exit still works).

Screen layout assumptions (for consistency with the above)

  • Row 0 (top) is a header/status line; row height-1 (bottom) is a status line.
  • Text lines render starting at on-screen row y=1.
  • Number of visible text rows = height - 2.
  • The cursor column reported is x; the cursor row reported is the on-screen y.

Public API surface required

  • babi.File(filename: str) — combined file/position state class with the repr format specified in §1.
  • babi.VERSION_STR — module-level string constant displayed at startup.
  • Command-line entry via python -m babi <path> [<path> ...] supporting new files, non-file paths, and multiple files as described.

04 Implement File Saving 693 words · source specification

Task Specification: Implement File Saving

Overview

You are working on a terminal-based text editor implemented in the babi module (invoked via python -m babi <file>). You must implement file saving, triggered by the C-s key combination, and extend the internal line-reading helper to compute a checksum of file contents.

Part 1: Extend babi._get_lines

The module-level function babi._get_lines(io_obj) reads text lines from a file-like object (e.g. io.StringIO).

Currently it returns a 3-tuple (lines, nl, mixed). Change it to return a 4-tuple:

(lines, nl, mixed, sha256)

where the first three elements retain their existing meaning and values, and the new fourth element sha256 is a string: the hex-encoded (lowercase) SHA-256 digest of the file's contents as read from the object.

For example, reading an empty input yields ([''], '\n', False, 'e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855') — i.e. the SHA-256 of the empty byte/string content.

  • spy.undo(lst) applies the inverse of every mutation recorded by the spy to the supplied list. The following must remain importable and callable from the module that exposes the highlighting engine.

_compiler_state(grammar_dict)

Accepts one grammar dictionary and returns a two-tuple (compiler, state):

  • compiler is accepted as the first argument to highlight_line.
  • state is the initial highlighting state accepted as the second argument to highlight_line.

The grammar dictionary uses these keys:

  • scopeName (str): the top-level scope name applied to all regions.
  • patterns (list): a list of rule dictionaries.

A rule dictionary may contain:

  • begin (str): a pattern marking the start of the rule's context.
  • end (str): a pattern marking the end of that context; this key may be absent.
  • name (str): the scope name contributed while the rule is active.
  • patterns (list): nested rule dictionaries applied within the context opened by begin.

Tokenizes one line. Its parameters are:

  • compiler: a compiler returned by _compiler_state.
  • state: either the initial state from _compiler_state or the updated state returned by a preceding call.
  • line (str): the line of text to tokenize.
  • first_line (bool): whether this is the document's first line.

  • end (int): exclusive character offset.

Required Behavior

Rule with both begin and end

When a rule has both patterns, matching begin opens its context. The rule's name scope becomes active at the start of the matched begin text and remains active through the matched end text. Matching end then closes the context and removes its contributed scope before subsequent text is highlighted.

Nested patterns are evaluated within an open context. An enclosing context's end pattern can close that context when processing has returned to it.

Rule with begin but no end

When a rule has a begin pattern but no end pattern or other continuation condition, matching begin opens an unbounded context:

  1. The rule's name scope becomes active at the start of the begin match, and the entire matched begin text carries that scope.
  2. The context remains active after the begin match. All following characters carry its scope together with any enclosing scopes, and its nested patterns remain available.
  3. The missing end must not be treated as an implicit close immediately after the begin match or at the end of the current line. The returned state retains the context, so later calls made with that state continue with the begin-only rule active.
  4. If the begin-only context is nested inside a rule that does have an end, text matching the enclosing rule's delimiter does not close the enclosing context while the begin-only context is active. That text retains both the enclosing and begin-only scopes.

The engine must therefore process such a rule without an exception and without dropping its scope after the opening match.

Normative Example

    'patterns': [
        {
            'begin': '!',
            'end': '!',
            'name': 'bang',

                {'begin': '--', 'name': 'invalid'},

        },

}

    Region(1, 2, ('test', 'bang')),
    Region(2, 3, ('test', 'bang')),
    Region(3, 4, ('test',)),
    Region(4, 5, ('test', 'bang')),
    Region(5, 7, ('test', 'bang', 'invalid')),
    Region(7, 8, ('test', 'bang', 'invalid')),
)

This establishes the relevant boundaries:

  • The first bang context runs from its opening ! through its closing ! at offsets 0–3.
  • The space at offsets 3–4 carries only the top-level test scope.
  • A second bang context opens at offsets 4–5.
  • The begin-only invalid context opens on -- at offsets 5–7.
  • invalid remains active after --. Consequently, the final ! at offsets 7–8 has ('test', 'bang', 'invalid'); it is not processed as the enclosing bang context's closing delimiter.
  • The returned state still contains the open invalid context because the rule supplies no end pattern.

  • Preserve the established behavior of rules that provide an end or continuation pattern.
  • Do not synthesize an end pattern for a begin-only rule.
