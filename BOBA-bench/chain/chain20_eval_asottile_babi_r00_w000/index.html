Task Specification: the Text Editor babi

Overview

Build (or extend) a terminal-based text editor called babi, provided as an importable Python module babi and launchable via python -m babi. The editor loads a text file, shows it, and supports navigation with the arrow keys. A number of small public APIs must be importable from the babi module so that they can be unit-tested directly.

Public API at Module Level

Everything listed below must be importable from the top-level babi module.

babi.VERSION_STR

A string constant. When the editor starts, it is displayed somewhere on screen (in the header/status area). Tests rely only on it being present on the initial screen and on its disappearance when the header area is hidden or overwritten.

babi.Position

A class that can be constructed with no arguments: Position(). Its repr() must be exactly:

Position(file_line=0, cursor_line=0, x=0, cursor_x_hint=0)

That means it has (at least) four fields — file_line, cursor_line, x, cursor_x_hint — each of them defaulting to 0, rendered in that order in the repr.

babi._get_lines(f)

Accepts a text file-like object (one that supports iteration/reading, e.g. io.StringIO) and returns a 3-tuple (lines, newline, mixed):

  • lines: a list[str] of the file's lines with their line endings stripped, plus a trailing empty string always appended (representing the special end-of-file line). Examples:
    • '' → ['']
    • '1\n2\n' → ['1', '2', '']
    • '1\n2' (no trailing newline) → ['1', '2', '']
  • newline: the newline string detected in the input.
    • Input that is pure LF → '\n'
    • Input that is pure CRLF → '\r\n'
    • Mixed line endings → '\n'
    • Empty input → '\n'
  • mixed: a bool that is True only if the file contained more than one distinct kind of line ending (e.g. one \r\n and one \n), and False otherwise.

Command-Line Interface

python -m babi [OPTIONS] [FILENAME]

Startup

When it starts, the editor draws a screen that includes VERSION_STR. If a filename is given, the file's contents are loaded and displayed beginning at the top.

--color-test

When the editor is invoked with --color-test, it renders a color test screen. The sequence * 1* 2 (numbered color swatches) shows up somewhere in the rendered output. It must work whether or not the terminal advertises 256-color support (i.e. with TERM=screen-256color and with TERM=screen). This screen is a normal editor state, and it can be exited with C-x.

Starting without a file / without color

The editor must start successfully when no filename argument is given, and it must start successfully in a non-color terminal (TERM=screen).

Exiting

Pressing C-x exits the editor cleanly (the process terminates).

Layout of the Screen

The terminal has a width and a height (in character cells). The editor fills the whole pane. The layout depends on the height:

  • Normal height (≥ 3 rows): a header/status region (containing VERSION_STR and the file's name/modified indicator) sits at the top; the file body is displayed underneath it.
  • Height == 2: the header is not shown. Everything else behaves normally. With the single-line file hello world, the full screenshot is exactly hello world\n\n (the file line, then blank lines filling the pane). Pressing an unhandled key still produces a status message.
  • Height == 1: only the file body is shown. With the file hello world, the full screenshot is exactly hello world\n. A status message (see below) can temporarily take over the single body row and takes precedence over the body; it is cleared by a single subsequent key action, which restores the body.

File Name / Modified Indicator

Once a file has been loaded, the header shows the file's base name. A modified (dirty) file is signalled by appending * to the name (e.g. f *).

Mixed newlines

If the loaded file has mixed newline styles, the buffer counts as modified from the start (the * indicator is shown) and the following status message is displayed:

mixed newlines will be converted to '\n'

(The literal text has a backslash-n inside single quotes, exactly as written above.)

Status Messages

Pressing a key with no bound action displays the status message:

unknown key

The message is cleared (it disappears) after a subsequent recognized key action. To be specific: once unknown key has been shown, a large number of no-op movement presses (e.g. pressing Left repeatedly at the start of the buffer) does not clear it, but one further recognized action press does clear it. In practice the message survives roughly 24 further presses and then clears; implement it as: the status message is displayed for one "draw cycle" plus is retained until the next accepted keypress that actually performs/attempts an action, at which point it clears. (In behavioural terms: press an unknown key → message shown; keep pressing keys → after enough presses the message clears.)

On a 1-row terminal, unknown key takes the place of the body row while it is shown; after one more key action the message clears and the body comes back.

Cursor and Navigation Behaviour

The cursor position is reported in terminal cell coordinates (x, y), where y is counted from the top of the pane. In the normal-height layout with a header, the first body line sits at y == 1. The cursor begins at the start of the first line.

The buffer always has a trailing special empty end-of-file line (from _get_lines), and the cursor may rest on it.

Arrow keys: Left, Right, Up, Down.

Horizontal movement (Left / Right)
  • Right advances the cursor by one column within the current line.
  • Left moves the cursor one column to the left within the current line.
  • At the start of the buffer (line 0, column 0), Left is a no-op.
  • At the beginning of a line (column 0, not the first line), Left wraps to the end of the previous line.
  • At the end of a line, Right wraps to the beginning of the next line.
  • On the special end-of-file line (empty, last line), Right is a no-op (the cursor cannot move past the end of the buffer).
Vertical movement (Up / Down)
  • Up on the first line is a no-op.
  • Down past the last (end-of-file) line is a no-op.
  • When the cursor moves to a different line, its column is derived from a remembered horizontal target (the "hint"):
    • Explicit horizontal movement sets the hint.
    • On a vertical move, the cursor's column becomes min(hint, length of the destination line) — it never goes past the end of the destination line.
    • The hint is kept across vertical moves, so that moving through a short line and onto a longer line restores the higher column.

Worked example. Take a file with the lines:

short              (length 5)
                   (empty, length 0)
long long long long(length 19)
                   (end-of-file empty line)

The cursor starts at (0, 1) (column 0 of short):

  • Left → (0,1); Up → (0,1) (no-ops at the buffer start).
  • Right, Right → (2,1).
  • Left → (1,1).
  • Up → (1,1) (no-op, first line).
  • Down → (0,2) (empty line, column clamped to 0; the hint from column 1 exceeds the line length 0).
  • Down → (1,3) (long line, column restored to hint 1).
  • Down → (0,4) (end-of-file line).
  • Down → (0,4) (no-op, end of buffer).
  • Right → (0,4) (no-op on the end-of-file line).
  • Left → (19,3) (wrap to the end of the previous line long long long long).
  • Right → (0,4) (wrap to the next line).
  • Left, then Up, Up → (5,1): the hint is now large (the end of the 19-char line), but on short the column clamps to that line's length 5.
  • Down, Down → (19,3): the hint is retained and restores the cursor to the end of the long line.

Scrolling

When the file has more lines than the body area can hold, moving the cursor beyond the visible region scrolls the view.

Example (height 10, a file with the 10 lines line_0..line_9)
  • At first the top lines are visible (line_7 visible).
  • Pressing Down 7 times moves the cursor down without any scrolling; line_0 remains visible; the cursor is at (0, 8).
  • One further Down scrolls the view: line_8 becomes visible, the cursor moves to (0, 4), and line_8 appears on screenshot row index 4 (0-based line 4).
  • From there, 3 Up presses do not scroll (line_9 remains visible); a 4th Up scrolls back so that line_0 is visible.

The scrolling keeps the cursor inside the visible body; when the cursor would leave the visible region the view scrolls by a page-ish amount, so that after a downward scroll the current line sits near the top of the body.

Behaviour on Resize

The editor must respond to terminal resize events, redrawing the layout for the new width/height. After a resize, the top line of the display generally changes (the header is re-rendered for the new width).

Scroll adjustment when resizing

If the terminal is resized smaller in a way that would leave the cursor's current line outside the (now shorter) visible body, the view scrolls up so the cursor remains visible; a resize where the cursor still fits does not scroll.

Example

Use the file with 10 lines line_0..line_9 at the default height. Move the cursor down 7 times (cursor at (0, 8)).

  • Resize to height 10: does not scroll; line_8 was not visible before and becomes visible / the cursor stays at (0, 8); line_8 is now on screen.
  • Resize to height 9 (smaller): the view scrolls up so line_0 is no longer visible, the cursor ends at (0, 3), and the cursor's line line_7 is on screenshot row index 3.

Notes

  • Terminal color support depends on TERM; when 256-color support is unavailable, the editor must degrade gracefully.
  • All of the keypress bindings referenced: C-x (exit), C-j (unhandled → unknown key), Left, Right, Up, Down.
02 Cursor Movement, Editing, and Horizontal Scrolling in a Terminal Text Editor 1621 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Cursor Movement, Editing, and Horizontal Scrolling in a Terminal Text Editor

You are working on a text editor that runs in a terminal, implemented in a module called babi. The topics of this task are the editor's Position state representation, the cursor navigation keys, basic text editing operations, and horizontal scrolling behavior. The editor is exercised inside a tmux pane: keys are sent to it, with its screen and cursor state being observed.

1. The Position class

A Position class is exposed by the babi module. Its repr(), when the class is constructed with no arguments, must be exactly:

Position(file_line=0, cursor_line=0, x=0, x_hint=0)

In other words, the position stores four integer fields, all of which default to 0, named (in this order): file_line, cursor_line, x, x_hint. The field that previously represented the horizontal hint must be named x_hint.

2. Conventions for the screen and cursor

The editor takes up a terminal pane. Row 0, the top row, serves as a status/header area; rendering of file content begins at row 1. The cursor position is reported as an (x, y) pair, in which x is the 0-based column and y is the 0-based row on screen.

A file that is opened for editing displays its lines beginning at screen row 1. One past the last real line of text there sits a virtual "end-of-file" line: pressing Down through the last line leaves the cursor at column 0 on this empty trailing line.

If the file has been modified (i.e. it has unsaved changes), the status area displays the filename followed by * (e.g. f *). If the file is unmodified, no * is present anywhere on screen.

When a key press goes unhandled, the status area displays text that contains unknown key.

3. Moving the cursor vertically (arrow keys)

With the four arrow keys Up, Down, Left, Right:

  • Left / Right shift the cursor by one column within the current line.
  • At the very start of the file, Left and Up are no-ops (the cursor remains at (0, 1)).
  • Up on the file's first line is a no-op.
  • When Left is pressed at column 0 of a line, the cursor wraps to the end of the previous line.
  • When Right is pressed at the end of a line, the cursor wraps to column 0 of the next line.
  • Pressing Down beyond the last text line places the cursor on the virtual end-of-file line at column 0; pressing Down or Right again there is a no-op.
  • The cursor cannot go past the end of the file.

Horizontal hint (x_hint) behavior: During vertical movement, the editor keeps track of the desired x column. If the destination line is shorter than the remembered column, the cursor is clamped to the end of that shorter line, yet the remembered hint is retained, so that a later move onto a longer line restores the original column. Example involving lines of differing lengths: starting on a long line and moving up onto a short one clamps x to that line's length (e.g. x=5); moving back down onto a longer line brings back the higher column (e.g. x=19).

4. Scrolling vertically

The pane provides a fixed number of content rows. Whenever the cursor is about to move below the visible content area, the view scrolls so that the cursor remains on screen. With a pane content height such that 7 Down presses keep the cursor at (0, 8), the 8th Down press causes a scroll: the cursor ends up at (0, 4), and the line that had been below the fold becomes visible at row 4.

If the cursor is above the visible area, scrolling up moves the view back up so that earlier lines are revealed.

5. The Home / End keys

Two navigation keys move the cursor within the current line. Each one is bound to two key names:

  • End — key names End and C-e: places the cursor at the end of the current line (at the column equal to the line's length). This sets the horizontal hint so that a subsequent Down keeps the cursor at end-of-line-column positions.
  • Home — key names Home and C-a: places the cursor at column 0 of the current line. Moving Down afterwards keeps the cursor at column 0.

6. Inserting basic text

Printable text that is typed gets inserted at the cursor. The characters typed show up in the file's content. After typing on one line, pressing Down and then typing again inserts text on the next line.

7. The Enter key

Pressing Enter splits the line the cursor is on, at the cursor's position:

  • At a line's beginning, Enter inserts a blank line before the current text, and the cursor moves to (0, next_row).
  • Mid-line, the text after the cursor is moved to a new line below; the cursor ends up at column 0 of that new line.
  • Once an Enter split has happened, pressing Up brings the cursor back to (0, previous_row).
  • The edit performed by Enter marks the file modified.

8. The Bspace (Backspace) key

  • At the very start of the file, Bspace is a no-op: no unknown key message shows up, the file stays unmodified (no *), and no content gets added.
  • When at column 0 of a line that is not the first line, Bspace joins the current line onto the end of the previous line. The cursor moves to the join column on the previous line, and the file is marked modified. The join column becomes the new horizontal hint (a subsequent Down keeps that column).
  • Mid-line/after some characters, Bspace deletes the character immediately before the cursor, shifts the cursor left by one column, and marks the file modified.
  • Backspacing that empties out trailing content must still leave an end-of-file line that can be navigated: following such an edit, pressing Down places the cursor at (0, 2); when the operation resulted in no net change, the file must not be marked modified (no *).

9. The DC (Delete) key

  • At the end of the file, DC is a no-op: there is no unknown key message, and the file is not marked modified (no *).
  • Mid-line, DC deletes the character immediately after the cursor and marks the file modified.
  • At a line's end, DC joins the following line onto the current line and marks the file modified.

10. Scrolling horizontally

If a line is wider than the pane, the editor scrolls horizontally and displays continuation markers:

  • If the content extends beyond the right edge, a » (right guillemet) marker appears in the rightmost visible column.
  • If the content is scrolled so that hidden content exists to the left, a « (left guillemet) marker appears in the leftmost visible column.

What happens with a pane of width 80:

  • On a long line, prior to any scrolling, the » marker shows at the right edge.
  • Moving Right beyond the visible right edge causes a horizontal scroll of the view: a « marker on the left and a » marker on the right both appear as appropriate, and the cursor's reported x reflects where it sits within the newly scrolled view.
  • For a line that is exactly 80 characters wide: taking the cursor to column 78 shows no » marker (the content fits), with the cursor at (78, 1). One more Right scrolls, with « shown at the left and the cursor at (7, 1).

With narrow panes:

  • Width 5: on a long line, the visible region displays content followed by ». As the cursor moves right, at the scroll point the « appears on the left and the cursor's x is reported relative to the scrolled window (e.g. x=3). Continued rightward movement scrolls further, refreshing the visible content window.
  • Width 1: while on a long line, the pane displays a single » marker. After moving right several times and then restoring a wider pane, the whole line is visible again and the cursor reports its absolute column (e.g. x=3 after 3 right presses).
  • Very narrow pane (width 5) with an unhandled key: pressing an unhandled key still renders a (truncated) unknown key message; the truncated text that is visible begins with unkno.

Public API / Support for the Test Harness

The following must exist so that tests can exercise the above.

babi.Position

Exactly as covered in section 1: a class whose repr() when constructed with no arguments is Position(file_line=0, cursor_line=0, x=0, x_hint=0).

Helper methods of the test runner

The test harness drives the editor by way of a runner object (an instance of a Runner subclass) that has these observation methods. On the runner used by tests, implement/support these signatures:

  • await_text(self, text, timeout=None) — polls the screen until text shows up somewhere in the current screenshot (a substring match, performed without altering newlines); raises AssertionError on timeout.
  • await_text_missing(self, s) — polls until s no longer shows up on screen.
  • _get_cursor_position(self) — returns the cursor's current (x, y) position as a tuple of ints, as obtained from the pane.
  • await_cursor_position(self, *, x, y) — x and y are keyword-only; polls until the cursor position is equal to (x, y); raises AssertionError on timeout, with the last observed position included in the message.

The editor gets launched either with no file (an empty new buffer) or with a filesystem path pointing to an existing file. Runner support includes launching with a specified pane height as well as temporarily resizing the pane to a given width and height.

03 Enhancements for the babi Editor 1710 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Enhancements for the babi Editor

You are working on babi, a text editor that runs in the terminal, implemented as a Python package importable via import babi. The task changes the internal file-state model and introduces several behaviors for navigation, multiple files, and process control. The package is launched as a module (python -m babi <files...>).

A real tmux-driven integration harness, plus one direct repr check, exercises everything that follows. Implement exactly the behavior described below.

1. Merge file state into a single File class

The previously separate position/file state is replaced by one public class, babi.File.

  • The constructor signature is babi.File(filename), with filename a string.
  • The class must have a repr that renders as a multi-line block in exactly this format:
File(
    filename='f.txt',
    modified=False,
    lines=[],
    nl='\n',
    file_line=0,
    cursor_line=0,
    x=0,
    x_hint=0,
)

To be concrete, repr() on a freshly constructed babi.File('f.txt') must equal:

File(\n    filename='f.txt',\n    modified=False,\n    lines=[],\n    nl='\n',\n    file_line=0,\n    cursor_line=0,\n    x=0,\n    x_hint=0,\n)

In other words: it begins with the header File(; next, every attribute appears on its own line, indented by 4 spaces, ordered filename, modified, lines, nl, file_line, cursor_line, x, x_hint, each one carrying a trailing comma; last comes a closing ) on its own line. Each attribute's value is rendered with the standard Python repr. For a new file, the defaults are modified=False, lines=[], nl='\n', and all four positional counters (file_line, cursor_line, x, x_hint) equal to 0.

(The old babi.Position class no longer exists as a public entry point; the File repr above takes its place.)

2. The version string constant

A module-level string constant babi.VERSION_STR must be exposed. At editor startup, this exact string must show up somewhere on the screen (e.g. in the status/title area).

3. Opening files: handling new files and non-files

If babi is started with a path argument:

  • New file (the path does not exist): the editor starts with an empty buffer. The supplied filename is shown on screen, and the text (new file) is shown somewhere on screen.
  • The path is a directory (not a regular file): the editor starts with an empty buffer. The status text <<new file>> is shown on screen, and an informational message that contains <name>' is not a file is shown as well (<name> here is the trailing component of the path, so for a directory named d the message contains d' is not a file).

4. The Escape key

At present no command is bound to Escape. It must produce the status message unknown key (the same behavior as any other unrecognized key).

5. Page navigation

The number of text rows the editor shows is fixed and derived from the terminal height. Assume the top row is a header/status line and the bottom row a status line, which makes the number of visible text rows height - 2. In what follows, the cursor row y means the on-screen row (row 0 is the top header line; text begins at y=1).

Page Down and Page Up

The keys PageDown and ^V are the two bindings that must trigger "page down". The keys PageUp and ^Y are the two bindings that must trigger "page up".

Consider a file whose lines are line_0 ... line_9:

  • Page down advances the viewport by one page, bringing a new page of lines into view, and sets the cursor to the top text row (x=0, y=1) on the line that is now at the top of the visible region.

    • In a height=10 window (8 visible text rows), starting from the top, one page down later the line at the top text row is line_6, and line_8 is visible.
    • In a height=4 window (2 visible text rows), starting from the top, one page down leaves line_2 visible, with the cursor sitting on line_1 at y=1.

  • Page up takes the viewport back by one page, once more setting the cursor to the top text row (x=0, y=1).

    • In the height=10 case, from the state reached by a page down, a page up goes back to the top: line_0 is at the top text row, line_8 is no longer visible, and the cursor is at x=0, y=1.
    • In the height=4 case, once a page down has been followed by a single Down, a page up scrolls back so that line_0 is at the top text row (cursor x=0, y=1) and line_2 is no longer visible.

  • Page navigation must not scroll the top row to above the start of the file (the scroll offset must never go negative).

  • Paging past the end of the file is bounded by the last line. In the height=10 case, after two page downs the cursor lands at x=0, y=5 on an empty trailing line (the position just past line_9); from there, pressing Up moves the cursor to y=4, onto line_9.

  • Once paging has happened, arrow keys pressed afterward behave consistently with the line the cursor is currently on (Up from the empty trailing position lands on the last real line).

How the cursor line is resolved during paging

Vertical position semantics: once paging has happened, the cursor goes on a real text line whenever possible; if the cursor lands past the final line, it rests on the empty line that follows the last line.

6. Ctrl-Home and Ctrl-End

  • ^Home jumps to the very beginning of the file. Once the view has scrolled down (e.g. several page downs so line_0 is off-screen), pressing ^Home scrolls the viewport back so that line_0 is visible at the top text row and the cursor is at x=0, y=1.

  • ^End moves to the end of the file (the position after the last line); the viewport scrolls so that the last line is visible.

    • With height=6 (4 visible text rows), starting at the top, ^End puts the cursor at x=0, y=3, and the on-screen row at index 2 shows line_9 (i.e., the last line is the second-to-bottom visible text row, with the cursor on the empty trailing line below it).
    • With height=8 (6 visible text rows): when the view is already scrolled to the last page (e.g. after one page down leaving line_9 visible and cursor at x=0, y=1), ^End puts the cursor at x=0, y=7, with on-screen row index 6 showing line_9.

7. Resizing must not scroll past the top

When the window is resized, the viewport might need to scroll upward to keep the cursor visible, yet the scroll offset must never turn negative. For a file line_0 ... line_9 opened in the default window:

  • After Down is pressed five times (cursor at x=0, y=6), changing the window size to 80x7 makes line_9 hidden; the original size is then restored and line_9 is visible again. After two presses of Up, the on-screen row at index 1 shows line_0 (that is, the buffer remains scrolled to the top, not into negative offset territory).

8. Multiple open files

The editor accepts several file path arguments and opens them as an ordered list, with one shown at a time.

With three files file_a (content a text), file_b (b text), file_c (c text) opened in that order:

  • At first the first file is shown: the name file_a appears, an indicator [1/3] appears, and the content a text appears.
  • M-Right moves to the next file (for the tested cases, wrapping is not required in this direction, but see below). After switching to file_b, file_b is shown along with the indicator [2/3] and the content b text, and the cursor is reset to x=0, y=1.
  • M-Left moves to the previous file, wrapping around. Starting at file_b, M-Left goes back to file_a (indicator [1/3]). Starting at file_a, another M-Left wraps to the last file, file_c (indicator [3/3], content c text).
  • The cursor position is kept per file: after Right moves the cursor in file_a (to x=1, y=1), leaving file_a and coming back to it puts the cursor at x=1, y=1 again.
  • Indicators use the format [<current>/<total>], with 1-based numbering.
Closing files
  • C-x closes the file that is currently open. While more than one file is still open, closing advances to the next file in the list (that following file becomes current, and its name is displayed). Closing the last remaining file exits the editor.
    • With file_a, file_b, file_c all open and file_a current: C-x closes it and shows file_a... (the next file); another C-x shows the following file; a final C-x exits.

9. Suspend / resume

Pressing C-z suspends the editor process (the way a standard terminal SIGTSTP-style suspend does), handing control back to the invoking shell, so the content the editor rendered is no longer displayed. Returning the job to the foreground (shell fg) resumes the editor and re-renders its content. Once resumed, editing continues normally (e.g. C-x still works for closing/exiting).

Overview

Add support to the TextMate-style syntax-highlighting engine for grammar rules that define a begin pattern but define no end pattern. A begin-only rule is valid: a match against it must open an unbounded highlighting context rather than raise an error or behave as an instantaneous match.

Every part of the existing highlighting behavior must remain compatible, including ordinary begin/end rules, nested rules, stateful line-by-line highlighting, and region coverage. For the purposes of this specification, existing rules that use a continuation condition such as while do not count as begin-only rules, and their existing behavior must be retained.

Public API

These are the keys used by the grammar dictionary:

  • scopeName (str): the top-level scope name that all regions receive.
  • patterns (list): a list made up of rule dictionaries.

A rule dictionary may hold:

  • begin (str): a pattern that marks where the rule's context starts.
  • end (str): a pattern that marks the end of that context; this key may be missing.
  • name (str): the scope name contributed for as long as the rule is active.
  • patterns (list): nested rule dictionaries, applied inside the context that begin opens.

  • state: either the initial state from _compiler_state or the updated state that a preceding call returned.
  • line (str): the line of text to be tokenized.
  • first_line (bool): whether the line is the document's first line.

  • end (int): character offset, exclusive.

Behavior Requirements

A rule that has both begin and end

If a rule has both patterns, a match of begin opens the rule's context. At the start of the matched begin text, the rule's name scope becomes active, and it stays active through the matched end text. A match of end then closes the context and takes away its contributed scope before the text that follows is highlighted.

Within an open context, nested patterns are evaluated. When processing has returned to an enclosing context, that context's end pattern can close it.

A rule that has begin but no end

When a rule has a begin pattern but no end pattern and no other continuation condition, a match of begin opens an unbounded context:

  1. At the start of the begin match, the rule's name scope becomes active, and the entire matched begin text carries that scope.
  2. The context is still active after the begin match. All of the characters that follow carry its scope together with any enclosing scopes, and its nested patterns stay available.
  3. The missing end must not be handled as an implicit close immediately after the begin match or at the end of the current line. The state that is returned keeps the context, so subsequent calls made with that state continue with the begin-only rule active.
  4. If the begin-only context is nested inside a rule that does have an end, then while the begin-only context is active, text matching the enclosing rule's delimiter does not close the enclosing context. Both the enclosing scope and the begin-only scope are retained by that text.

The engine must therefore handle a rule of this kind without an exception and without dropping its scope after the opening match.

  • The first bang context spans offsets 0–3, running from its opening ! through its closing !.

  • The begin-only invalid context is opened by -- at offsets 5–7.
  • After --, invalid remains active. The final ! at offsets 7–8 therefore has ('test', 'bang', 'invalid'); it is not handled as the closing delimiter of the enclosing bang context.
