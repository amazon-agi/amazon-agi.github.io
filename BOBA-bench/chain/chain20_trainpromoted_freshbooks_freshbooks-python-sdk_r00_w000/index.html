01 FreshBooks API Client — Project Listing, Result Iteration, and Request Error Handling 1215 words · source specification

Task Specification: FreshBooks API Client — Project Listing, Result Iteration, and Request Error Handling

You are extending a Python client library for the FreshBooks API. The library talks to a REST API and wraps responses in result objects. This task covers: adding a new exception type, making result objects behave as sized/iterable/indexable/printable collections, adding a project-listing call, and improving error handling for malformed or unexpected HTTP responses.

Package Structure & Public Imports

The following imports must work:

from freshbooks import Client as FreshBooksClient
from freshbooks import FreshBooksError, FailedRequest
from freshbooks.client import API_BASE_URL
  • freshbooks.client.API_BASE_URL — a module-level string constant holding the base URL for API requests (used to construct request URLs).
  • freshbooks.Client — the main client class (aliased in tests as FreshBooksClient).
  • freshbooks.FreshBooksError — an existing exception type (already present; must remain importable).
  • freshbooks.FailedRequest — a new exception type (see below).

Client Construction

FreshBooksClient is constructed such that requests it makes carry an Authorization: Bearer <token> HTTP header. The token value used in requests must match the access token the client was configured with (in tests the resulting header is Bearer some_token).

The client exposes resource accessors as attributes:

  • client.clients — the Clients (accounting) resource.
  • client.projects — the Projects resource.

Result Objects

Calls return a result wrapper object. Two logical kinds exist: a single-resource result and a list result. Both share common behavior described below.

Common behavior
  • Each result has a name attribute (a string), set to the resource name relevant to the call.
  • Each result has a data attribute containing the parsed JSON payload relevant to that result (a dict).
  • str(result) must return "Result(<name>)", where <name> is the result's name attribute. For example, a result named "client" produces "Result(client)" and one named "clients" produces "Result(clients)".
  • Attribute access on a result maps to keys within its underlying resource data. Accessing an attribute that corresponds to a key in the resource dict returns that key's value. (E.g. a single client result exposes .name, .organization, etc. drawn from the client's fields; a single project result exposes .id.)
Single-resource result

Represents one entity (e.g. one client, one project).

  • data holds the entity's field dict.
  • Field attribute access returns the corresponding field value.
List result

Represents a collection of entities.

  • data holds the full parsed response payload (including collection metadata and the list of entities).
  • len(result) returns the number of entities in the collection.
  • The result is iterable; iterating yields one single-resource result per entity, in order. Each yielded item supports the same field attribute access as a single-resource result (e.g. item.userid, item.id).
  • The result is indexable; result[i] returns the i-th entity as a single-resource result supporting field attribute access.
  • When the collection is empty, len(result) is 0 and iterating yields nothing.

Resources and Calls

Clients resource (accounting API)

The accounting API wraps results in a nested response.result structure.

Get a single client

client.clients.get(account_id, client_id)
  • Issues a GET request to: {API_BASE_URL}/accounting/account/{account_id}/users/clients/{client_id}
  • On success, returns a single-resource result named "client".
  • data is the client's field dict. Field access such as .name, .organization, and .userid returns the corresponding values, and .data["<field>"] accesses the same values.

List clients

client.clients.list(account_id)
  • Issues a GET request to: {API_BASE_URL}/accounting/account/{account_id}/users/clients
  • On success, returns a list result named "clients".
  • data is the result object from the response payload: a dict containing keys such as total, page, pages, per_page, and clients (the list of client dicts).
  • len(result) equals the number of entries in the clients list.
  • result[i] and iteration yield single-resource results whose .userid equals the corresponding client's userid.
  • result.data["total"] and result.data["clients"] expose the metadata and raw list respectively.
  • For an empty clients list, len is 0, iteration yields nothing, data["total"] is 0, and data["clients"] is [].

The response shape for the accounting API is:

{ "response": { "result": { "clients": [ ... ], "total": N, "page": 1, "pages": 1, "per_page": 15 } } }

The list result's data is the inner result dict.

Projects resource (projects API)

The projects API uses a different response shape (no response.result wrapping).

Get a single project

client.projects.get(business_id, project_id)
  • Issues a GET request to: {API_BASE_URL}/projects/business/{business_id}/projects/{project_id}
  • On success, returns a single-resource result named "project" whose field access (e.g. .id) works.

List projects

client.projects.list(business_id)
  • Issues a GET request to: {API_BASE_URL}/projects/business/{business_id}/projects
  • On success, returns a list result named "projects".
  • The response payload has this shape:
{
  "meta": { "total": N, "per_page": 30, "page": 1, "pages": 1, "sort": [] },
  "projects": [ { "id": ..., "title": ..., ... }, ... ]
}
  • result.data is the full payload dict. Thus result.data["meta"]["total"] gives the total count and result.data["projects"][0]["id"] gives the first project's id.
  • len(result) equals the number of entries in the projects list.
  • Iteration yields single-resource results in order, each with .id equal to the corresponding project's id.

Error Handling

FreshBooksError

Raised when a request completes with a well-formed JSON error response indicating the requested resource/operation failed (e.g. HTTP 404 not found). It carries:

  • status_code — the HTTP status code (e.g. 404).
  • error_code — an error code parsed from the response body when present, otherwise None.
  • str(error) — a human-readable message (e.g. "Requested resource could not be found.").

(This exception already exists; its established behavior must be preserved. It is raised, for example, when a get call receives a 404 with a parseable error body.)

FailedRequest

A new exception type, importable as freshbooks.FailedRequest. It is raised in two situations:

  1. Unparseable response body. When the HTTP response body cannot be parsed as JSON (regardless of status code):

    • str(error) must equal: Failed to parse response: '<raw body>' — where <raw body> is the exact response body text. Example: body stuff with status 500 yields message Failed to parse response: 'stuff' and status_code == 500.
    • error.status_code must equal the HTTP status code of the response.

  2. Well-formed JSON but unexpected structure. When the response parses as JSON with a 200 status but does not contain the expected result structure for the requested resource:

    • str(error) must equal: Returned an unexpected response: '<raw body>' — where <raw body> is the exact response body text. Example: body {"foo": "bar"} with status 200 yields message Returned an unexpected response: '{"foo": "bar"}' and status_code == 200.
    • error.status_code must equal the HTTP status code (200).

These behaviors apply to the get calls of both the clients and projects resources (an unparseable body raised as case 1 for both; the unexpected-structure case verified for the clients get call). The raw body used in the message must be the exact bytes/text returned by the server, unmodified.

Summary of Required New/Changed Public Surface

  • freshbooks.FailedRequest — new exception with status_code attribute and the two str() message formats described above.
  • freshbooks.Client.projects.list(business_id) — new list call returning a list result named "projects".
  • List results (from clients.list and projects.list) must support len(), iteration (yielding per-entity single-resource results), and integer indexing.
  • All result objects must implement str(result) == "Result(<name>)".
  • Get calls must raise FailedRequest for unparseable bodies and for parseable-but-unexpected-structure 200 responses, while continuing to raise FreshBooksError for recognized error responses.

Task Specification: Implement List Pagination Support

Overview

Add pagination support to the FreshBooks client library. This involves creating a Pagination class and exposing pagination metadata on list results.

Public API Surface

1. Pagination class

Add a Pagination class that is importable directly from the freshbooks package:

from freshbooks import Pagination

The constructor must accept two positional arguments:

Pagination(page, per_page)
  • page: the requested page number (integer).
  • per_page: the number of results per page (integer).
2. list() method pagination parameter

The list() method on resource accessors (e.g. client.clients.list(...)) must accept an optional keyword argument pagination:

freshBooksClient.clients.list(account_id, pagination=Pagination(2, 1))

When a Pagination object is supplied, the outgoing HTTP GET request must include the query string parameters:

  • page — set to the Pagination object's page value.
  • per_page — set to the Pagination object's per_page value.

For example, Pagination(2, 1) must produce a request whose query string contains page=2 and per_page=1.

3. Pagination metadata on list results

The result object returned by a list() call must expose a pages attribute. This pages attribute must have a total property reflecting the total number of records reported by the API response.

  • For responses that report the total under a top-level total field (accounting-style responses, e.g. clients), result.pages.total must equal that value.
  • For responses that report the total under a meta.total field (project-style responses), result.pages.total must equal that value.

Behavior Requirements

  • Existing list() behavior (result naming, length, indexing, iteration, and data access) must remain unchanged when no pagination argument is provided.
  • The pages.total attribute must be populated on list results regardless of whether pagination was requested.
  • When pagination is not provided, no page/per_page query parameters are added by this feature.

Imports That Must Continue To Work

The following imports from the freshbooks package must all succeed:

from freshbooks import Pagination, FreshBooksError, FailedRequest

(FreshBooksError and FailedRequest already exist; Pagination is the new addition.)

03 Query Builders for List Requests 905 words · rewritten by GPT-5.6-sol

Task Specification: Query Builders for List Requests

Overview

Implement two builder classes — PaginatorBuilder and FilterBuilder — that construct query-string fragments for API list requests, and update list resource calls to accept these builders.

Public API Surface

All of the following must be importable directly from the freshbooks package:

from freshbooks import PaginatorBuilder, FilterBuilder

(The existing importable names FreshBooksError and FailedRequest must remain available from freshbooks. Note: the previously existing Pagination name is replaced by PaginatorBuilder.)

PaginatorBuilder

Constructor
PaginatorBuilder(page=None, per_page=None)
  • Accepts an optional page and optional per_page, both as positional or keyword arguments.
  • Either or both may be omitted.
Methods

page(value=None)

  • When called with no argument, returns the current page value (an int, or None if never set).
  • When called with an argument, sets the page value and returns the builder instance itself (to allow chaining).
  • Minimum enforced value is 1: any set value less than 1 (including 0) is clamped to 1. This clamping applies both to the constructor and to setter calls.

per_page(value=None)

  • When called with no argument, returns the current per_page value (an int, or None if never set).
  • When called with an argument, sets the per_page value and returns the builder instance itself (to allow chaining).
  • Maximum enforced value is 100: any set value greater than 100 is clamped to 100. This clamping applies both to the constructor and to setter calls.

build()

  • Returns a query-string fragment.
  • Only includes parameters that have been set.
  • For each set parameter, appends &page=<value> and/or &per_page=<value>.
  • When both are set, page comes first, then per_page: "&page=<page>&per_page=<per_page>".
  • When only one is set, only that fragment is produced (e.g. "&page=1" or "&per_page=100").

__str__

  • Returns "PaginatorBuilder(page=<page>, per_page=<per_page>)" using the current values.
Examples
p = PaginatorBuilder(page=1, per_page=3)
p.build()      # "&page=1&per_page=3"
p.page()       # 1
p.per_page()   # 3
p.page(2).per_page(6).build()   # "&page=2&per_page=6"

PaginatorBuilder(page=0).page()        # 1
PaginatorBuilder(per_page=500).per_page()  # 100

FilterBuilder

Constructor
FilterBuilder()
  • Takes no arguments.
Methods

Each mutating method registers a filter. Filters accumulate; build() renders them all.

boolean(field, value)

  • Registers a boolean filter rendered as &<field>=<value> where <value> is the Python str() of the boolean ("True" or "False").
  • Example: boolean("active", True) → "&active=True".

equals(field, value)

  • Rendered as &search[<field>]=<value>.
  • Example: equals("username", "Bob") → "&search[username]=Bob".

like(field, value)

  • Rendered as &search[<field>]=<value>.
  • Example: like("user_like", "leaf") → "&search[user_like]=leaf".

in_list(field, values)

  • values is a list. Each element is rendered as a repeated entry: &search[<key>][]=<value> for each value in order.
  • The field key is pluralized: if field does not already end in s, an s is appended; if it already ends in s, it is used as-is.
    • in_list("userids", [1, 2]) → "&search[userids][]=1&search[userids][]=2"
    • in_list("userid", [1, 2]) → "&search[userids][]=1&search[userids][]=2"

between(field, min=None, max=None)

  • Registers a range filter. min and max may be passed positionally or by keyword; either may be omitted.
  • Key derivation for the field:
    • If field already ends in _min or _max, that field name is used directly as the search key, and the provided value is applied to it. For example, between("amount_min", min=1) → "&search[amount_min]=1", and between("amount_max", max=10) → "&search[amount_max]=10".
    • start_date is also a complete search key. A supplied bound is rendered with the unchanged key search[start_date]; _min or _max is not appended. For example, between("start_date", min="2020-10-17") → "&search[start_date]=2020-10-17". This key behavior is the same for string, datetime.date, and datetime.datetime values.
    • For other fields, a provided min produces &search[<field>_min]=<value> and a provided max produces &search[<field>_max]=<value>. When both are provided, min comes first: between("amount", 1, 10) → "&search[amount_min]=1&search[amount_max]=10". Thus between("date", min=<value>, max=<value>) uses the keys search[date_min] and search[date_max].
  • Value formatting:
    • Plain values (e.g. integers, strings) are rendered as-is via their string form.
    • datetime.date and datetime.datetime values are rendered as an ISO date string YYYY-MM-DD (date portion only; any time component is dropped).
    • Example: between("start_date", min="2020-10-17"), between("start_date", min=date(2020,10,17)), and between("start_date", min=datetime(2020,10,17,13,14)) all → "&search[start_date]=2020-10-17".

build()

  • Returns the concatenation of all registered filter fragments, in the order they were added, each beginning with &.

__str__

  • Returns "FilterBuilder(<build output>)".
  • Example: after boolean("active", True), str(filter) → "FilterBuilder(&active=True)".

List Call Integration

The list method on list-capable resources must accept a keyword argument builders, which is a list of builder instances (PaginatorBuilder and/or FilterBuilder):

resource.list(<resource_id>, builders=[...])
  • The query-string fragments produced by each builder's build() must be applied to the outgoing list request's query string.
  • Passing a PaginatorBuilder adds page / per_page query parameters.
  • Passing a FilterBuilder adds the corresponding filter query parameters.

This applies at minimum to:

  • The accounting-style clients resource, whose list endpoint is GET {API_BASE_URL}/accounting/account/{account_id}/users/clients, called as freshBooksClient.clients.list(account_id, builders=[...]).
  • The projects resource, whose list endpoint is GET {API_BASE_URL}/projects/business/{business_id}/projects, called as freshBooksClient.projects.list(business_id, builders=[...]).
Expected request behavior
  • A PaginatorBuilder(2, 1) on a clients or projects list produces query parameters page=2 and per_page=1.
  • A FilterBuilder with in_list("userid", [1, 2]) and between("date", min=<datetime 2010-10-17>, max=<datetime 2012-11-21>) on the clients list produces query parameters: search[userids][] = 1 and 2, search[date_min] = 2010-10-17, search[date_max] = 2012-11-21.
  • A FilterBuilder with boolean("active", True) on the projects list produces query parameter active=True.

The list responses are parsed as before; only the request query-string construction changes with the addition of builders.

Notes

  • API_BASE_URL remains available at freshbooks.client.API_BASE_URL.
  • Existing list behavior (without builders) must continue to work unchanged; builders is optional.

Task Specification: Add Create and Update Support to Accounting Client Resource

Overview

Extend the accounting client resource so that it supports creating new clients and updating existing clients against the FreshBooks accounting API. These operations must send authenticated JSON requests and return a result object wrapping the returned client data.

Context

The client resource is accessed via the FreshBooks client instance through an attribute named clients (i.e., freshBooksClient.clients). This resource already supports read/list operations. You must add two new methods to it: create and update.

The API base URL and account identifier are used to construct endpoint URLs. The relevant path segment for the client resource is users/clients under the accounting account path.

Required API Surface

Add two methods to the accounting client resource:

create(account_id, data)
  • Parameters:
    • account_id: the account identifier (string).
    • data: a dictionary representing the payload of client fields to create (e.g., {"email": "john.doe@abcorp.com"}).
  • Behavior:
    • Issues an HTTP POST request to:
      {API_BASE_URL}/accounting/account/{account_id}/users/clients
    • Sends the request with:
      • An Authorization header of the form Bearer <token> (using the configured access token).
      • A Content-Type header equal to application/json.
    • Returns a result object (described below) built from the API response.
update(account_id, resource_id, data)
  • Parameters:
    • account_id: the account identifier (string).
    • resource_id: the identifier of the client to update (integer).
    • data: a dictionary representing the payload of fields to update.
  • Behavior:
    • Issues an HTTP PUT request to:
      {API_BASE_URL}/accounting/account/{account_id}/users/clients/{resource_id}
    • Sends the request with the same Authorization and Content-Type: application/json headers as create.
    • Returns a result object (described below) built from the API response.

API Response Shape

Both endpoints return JSON of the following shape:

{
  "response": {
    "result": {
      "client": { ...client fields... }
    }
  }
}

The client object contains fields such as email, userid, id, and many other client attributes.

Result Object Requirements

Both create and update return the same kind of result object. This object represents a single named resource extracted from response.result. For the client resource, the inner key is "client".

The result object must support:

  • str() representation: str(result) produces Result(client) — i.e., Result(<name>) where <name> is the inner key.
  • .name attribute: returns the inner key name, "client".
  • .data attribute: returns the raw dictionary of client fields (the value under the "client" key). Accessing a field, e.g. result.data["email"], yields that field's value.
  • Dynamic attribute access: individual client fields are accessible directly as attributes on the result object. For example:
    • result.email returns the client's email value.
    • result.userid returns the client's userid value (an integer).

Notes

  • The token used for the Authorization header comes from the configured access token on the FreshBooks client.
  • Request bodies for create and update carry the provided data payload; the response returned to the caller reflects the resource as returned by the API (which may differ from the submitted payload).

Definition of Done

  • freshBooksClient.clients.create(account_id, data) performs a POST to the clients collection URL with JSON content type and bearer authorization, returning a result object as specified.
  • freshBooksClient.clients.update(account_id, resource_id, data) performs a PUT to the specific client URL with JSON content type and bearer authorization, returning a result object as specified.
  • The returned result object satisfies all the str(), .name, .data, and dynamic field-attribute requirements described above.

Task Specification: Custom User-Agent Header Support

Overview

Modify the FreshBooks client so that every HTTP request it makes to the API includes a User-Agent header. The header value must have a sensible default, and callers must be able to override it.

Public API Surface

Module: freshbooks.client

Add a module-level constant:

  • VERSION — a string representing the SDK version. It must be importable as from freshbooks.client import VERSION. Its value is used to build the default user agent string (see below).
Client class

The client class is instantiated via from freshbooks import Client (the existing Client, which is freshbooks.client's client class).

Add a new optional keyword argument to the client constructor:

  • user_agent (optional, keyword argument): a string. When provided, this exact string is used as the value of the User-Agent header on all requests made by that client instance. When not provided, the header defaults to the value described below.

The constructor must continue to accept its existing keyword arguments (e.g. access_token) and behave as before in all other respects.

Behavior

For every HTTP request the client issues to the API, it must send a User-Agent request header.

  • Default value: When the client was constructed without a user_agent argument, the User-Agent header value must be exactly:

This header must be present on all API request types made by the client (both single-resource retrievals and list retrievals).

A list response body has the shape:
