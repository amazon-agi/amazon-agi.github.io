Goal

Webhook payload signature validation is to be implemented within the gidgethub.sansio module. The gidgethub package, as well as the module path gidgethub.sansio, must be importable.

Public API

gidgethub.sansio.ValidationFailure

ValidationFailure is the exception that reports a failed webhook validation. It must derive, either directly or indirectly, from Exception, so that it can be raised and caught like a normal exception.

gidgethub.sansio.validate(payload, *, secret, signature)

This function validates a raw webhook payload against a signature that has been supplied. The secret and signature arguments are keyword-only: they may only be supplied by keyword.

Parameters
  • payload: a bytes object that holds the raw payload data in unmodified form.
  • secret: a str that holds the shared secret.
  • signature: a str that holds the signature to be validated.
How the signature is calculated

The digest to expect is the plain SHA-1 digest of the shared secret's UTF-8 bytes immediately followed by the payload bytes, with no separator between the two:

hashlib.sha1(secret.encode("utf-8") + payload).hexdigest()

This is a straight SHA-1 computation over the concatenated bytes; it is not HMAC-SHA-1. The full expected signature is this exact, lowercase string:

sha1=<hexadecimal SHA-1 digest>
How validation behaves
  • If signature does not start with the exact prefix "sha1=", ValidationFailure must be raised.
  • ValidationFailure must be raised if the complete supplied signature does not match the signature computed from secret and payload.
  • When the complete supplied signature matches, the function must return None and must not raise an exception.
Reference values

Given:

payload = b"gidget"
secret = "123456"

the SHA-1 digest of secret.encode("utf-8") + payload comes out as:

6ea124f8bfc2e6f5a0a40687201c351716110bec

As a result, the following signature must validate successfully:

The bare digest below is missing the required "sha1=" prefix and must cause ValidationFailure to be raised:

decipher_response(status_code, headers, body)

The only successful status codes are 200, 201, and 204. When the status is one of those, return:

(data, rate_limit, more)

  • rate_limit is a RateLimit built out of the response headers.
  • more is the next-page URL as a string, or None.

2xx statuses other than these are not implicitly successful. For example, status 205 must raise gidgethub.HTTPException, with .status_code == http.HTTPStatus.RESET_CONTENT.

Look up Content-Type case-insensitively and separate the media type from parameters such as charset.

  • A body that is empty yields None.
  • If no content type is supplied, the value produced by deciphering is None.
  • For media type application/json, decode the bytes using the declared charset (UTF-8 when omitted) and parse the JSON. Return the Python value that results.
  • For every media type other than that, decode with the declared charset (UTF-8 when omitted) and return the resulting str without JSON parsing. GitHub diff media types such as application/vnd.github.v3.diff; charset=utf-8 fall under this; a body of that kind may begin with diff --git.

The same decoding rules are used to obtain the structured error details for statuses that are not successful.

Pagination

Look up Link case-insensitively. Its value is a sequence whose entries are separated by commas, such as:

<URL>; rel="next", <URL>; rel="last"

  • Relation entries may appear alongside first, prev, or last entries.
  • If the header is missing or holds no next relation, return None.
  • The URL text itself is to be preserved; it may be a URI template requiring expansion by the caller.

As an example, a next entry that contains <https://api.github.com/repositories/4164482/pulls?page=2> produces more == "https://api.github.com/repositories/4164482/pulls?page=2". A final page whose relations are only first and prev produces None.

  • The remaining 4xx statuses: raise gidgethub.BadRequest.

  • Statuses in the 3xx range: raise gidgethub.RedirectionException.
