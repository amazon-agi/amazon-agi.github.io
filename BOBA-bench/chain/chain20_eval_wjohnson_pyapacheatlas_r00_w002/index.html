Callers may pass the parameters positionally, in the order (name, typeName, qualified_name), or by keyword (name=, typeName=, qualified_name=, guid=, attributes=).

When an entity is constructed:

  • The qualified_name value must be stored so that entity.attributes["qualifiedName"] returns it.
  • If attributes is supplied as a dict, its keys/values must be present in entity.attributes (for example, an entity created with attributes={"type": "str"} must have entity.attributes["type"] == "str").

  • The entity must expose a relationshipAttributes attribute, and this attribute is a dictionary.

def addRelationship(self, **kwargs)

Behavior:

  • The method accepts arbitrary keyword arguments. Each keyword name becomes a key in relationshipAttributes, and the value associated with it becomes the value stored under that key.
  • The value that is stored must be normalized as follows:
    • If the value passed in is an AtlasEntity instance, it must be automatically converted to its minimal JSON representation (equivalent to calling to_json(minimum=True) on it) before it is stored.

  • For relationship values, the minimal JSON representation that gets produced must contain precisely the key set {"guid", "qualifiedName", "typeName"} — three keys, no more, no fewer.

Task Specification: Batching Entities with Dependencies

Aim

Write a utility function that takes a flat list of Atlas entity JSON dictionaries and splits it into batches whose size is bounded, ensuring that entities connected through relationships end up together in the same batch.

Public Interface

Define a function named batch_dependent_entities inside the module pyapacheatlas.core.util. It must be possible to import it as:

from pyapacheatlas.core.util import batch_dependent_entities

In addition, the module pyapacheatlas.core.util must go on exposing the existing GuidTracker class, which stays importable from the same location.

Function Signature
def batch_dependent_entities(entities, batch_size=...):
    ...
  • entities: a list of entity dictionaries, with each item being the JSON/dict representation of an Atlas entity.
  • batch_size: an integer keyword argument that caps how many entities any single output batch is allowed to hold.
What the Function Returns

The return value is a list of batches; every batch is a list (or collection) consisting of entity dictionaries drawn from the input. When all batches are concatenated, every input entity is present exactly once.

Input Entity Dictionaries

Every entity dictionary includes at least:

  • A guid field that serves as the entity's unique identifier. When entities come from a single upload, their guids are typically small integers or strings that look numeric (e.g., 0, 1, -1, "-1").
  • A relationshipAttributes field: relationship names mapped to relationship references. Each referenced value is again a dictionary, and it may contain a guid field that points at another entity.

What Counts as a Dependency

Entities count as dependent — they must land in the same batch — whenever one of them references the other by way of a relationship guid whose value is a numeric guid (an integer, or a string standing for an integer such as "-1").

  • A relationship reference carrying a numeric guid functions as a pointer to another entity in the same upload set. References of this sort tie entities together into a connected group, whose members must stay together.
  • When a relationship reference's guid is not numeric (e.g., a real persisted guid such as "abc-123"), it does not count as an in-upload dependency. No obligation to group entities together arises from such a reference, and it is ignored during batching.

Grouping by dependency works both transitively and in an undirected fashion: if A relates to B and B relates to C (via numeric guids), then all three of A, B, and C wind up in one connected group, no matter which direction the relationship runs or in what sequence the entities show up in the input list. Nothing about the input order guarantees that related entities land next to each other.

Rules Governing Batching

  1. Take the numeric-guid relationships described above and compute the connected groups of entities from them. Entities lacking a qualifying numeric-guid relationship constitute singleton groups.
  2. Each connected group must be preserved intact inside one batch — a group is never to be split across batches.
  3. Pack the groups into batches while making sure that no batch goes over batch_size entities. Independent (single or small) groups may share one batch, provided the total entity count in that batch remains within batch_size.
  4. Strive for a minimal set of batches that satisfies the constraints above (that is, create no more batches than necessary, and use independent groups to fill batches wherever they fit).

Worked Examples

  • No dependencies: Suppose 10 entities that are fully independent of one another are supplied, with batch_size=2; the outcome is 5 batches of 2 entities apiece.

  • With dependencies: Suppose 16 entities, some of which are joined into connected groups through numeric-guid relationships (e.g., one connected group of 7 entities, another of 3 entities, and the rest independent), along with batch_size=7; the outcome is 3 batches: the group of 7 takes one whole batch, the group of 3 plus however many independent entities are needed takes a second, and the independent entities still left over take the last one — no batch goes beyond 7.

  • Non-numeric guid reference: Suppose 4 entities, one of which carries a relationship aimed at a non-numeric guid (e.g., "abc-123", i.e., a reference to a pre-existing entity that is not part of the upload set). A relationship of that sort does not give rise to a dependency. Under batch_size=2, entities that would be grouped only via such a non-numeric reference stay ungrouped; the outcome is 2 batches (any dependency that genuinely stems from a numeric guid is still honored).

Remarks

  • Grouping between entities is established only by relationships whose referenced guid is numeric (integer or integer-valued string, negative values included).
  • In principle, a group's size may be larger than batch_size; the only groups the tests exercise are ones that fit within the given batch_size, and consequently grouped entities always fit inside one batch under the exercised conditions.

Task: Add Support for Glossary Terms (Meanings) in Bulk Entity Parsing

Overview

Extend the bulk entity reader so that the input can include a special column that identifies glossary terms. When the column is present, the parser must attach the referenced terms to each entity as a meanings relationship.

Public API Affected

The existing classes and methods listed below are involved (module paths as the codebase currently uses them):

  • Reader (constructed from a ReaderConfiguration), providing the method parse_bulk_entities(input).
  • ExcelReader (constructed from an ExcelConfiguration), providing the method parse_bulk_entities(filepath).
  • ExcelReader.TEMPLATE_HEADERS["BulkEntities"] — the list of default column headers for the bulk entities template.

No new classes or method names are being introduced. Instead, the behavior of the existing parse_bulk_entities methods is extended.

Required Behavior

Input

Bulk entity input rows may contain an additional column whose name is exactly:

[Relationship] meanings

With the generic Reader, input rows are dictionaries; the column is represented by a key "[Relationship] meanings" whose value is either:

  • None (no terms), or
  • a string holding one or more term names.

In the ExcelReader case, this same column may be appended to the standard BulkEntities headers and read from the worksheet.

Parsing the Terms

The value of the [Relationship] meanings column is a list of glossary term names delimited by semicolons (;):

  • A single term, e.g. "termA", yields one term.
  • Multiple terms, e.g. "term1;term2" or "My Term;abc", yield one entry for each delimited value.
  • Term names are used exactly as provided (case sensitive), with any internal spaces included.
Output — Attaching the Meanings

For every entity produced in results["entities"]:

  • If the [Relationship] meanings value is empty (None, or absent/blank in some other way), the entity's relationshipAttributes dictionary must not contain a "meanings" key.
  • If the value contains one or more terms, the entity's relationshipAttributes must contain a "meanings" key whose value is a list with one element for each parsed term (each term preserved).

Every element of the meanings list is an object that references the glossary term by its unique qualified name. That qualified name is formed by appending the literal suffix @Glossary to the term name. Concretely, every element has this structure:

{
  "uniqueAttributes": {
    "qualifiedName": "<term name>@Glossary"
  }
}

As an example, the input value "My Term;abc" produces a meanings list with two elements, whose uniqueAttributes.qualifiedName values are "My Term@Glossary" and "abc@Glossary" respectively.

Preserving Existing Behavior

All columns and relationship handling that were supported previously must continue to work unchanged. The meanings handling is purely additive: entities that lack the meanings column, or that have an empty value for it, are produced exactly as before (with no meanings key added).

The output object that parse_bulk_entities returns keeps its existing shape, with the entities available under results["entities"] in the same order as the input rows.

  • "name" — the entity's name.
  • "qualifiedName" — the entity's qualified name.

Beyond these, a row may optionally include either, both, or neither of:

  • "experts" — a string of expert identifiers separated by ; (a trailing ; may be included), e.g. "a;b;".
  • "owners" — a string of owner identifiers separated by ; (a trailing ; may be included), e.g. "e;f;".

A row may leave out the experts key, the owners key, or both entirely (the key is then simply not present in the dict).

Behavior Requirements

Each input row must produce a corresponding entity in the output. Contacts must be handled according to these rules:

  1. Presence of the contacts key: If a row has neither an experts value nor an owners value, the resulting entity must NOT contain a "contacts" key at all.

  2. Structure of the contacts key: If a row has at least one of experts or owners (with a non-empty value), the resulting entity must include a "contacts" dictionary. That dictionary must contain both an "Expert" key and an "Owner" key, each mapping to a list.

  3. Identifier parsing: A column value is a ;-delimited string. Each non-empty identifier is turned into a dict of the form {"id": <identifier>}. The list keeps the identifiers in the same order they appear in the string. A trailing ; (or empty segments) must not produce empty/extra entries.

    • Example: "a;b;" → [{"id": "a"}, {"id": "b"}]
    • Example: "e;f;" → [{"id": "e"}, {"id": "f"}]

  4. Expert only: If a row supplies experts but the owners value is absent or empty, the contacts dictionary must hold the parsed expert list under "Expert" and an empty list under "Owner".

  5. Owner only: If a row supplies owners but the experts value is absent or empty, the contacts dictionary must hold the parsed owner list under "Owner" and an empty list under "Expert".

  6. Both: If a row supplies both experts and owners, the contacts dictionary must contain both parsed lists under their respective keys.

Worked Ordering Example

With the input rows supplied in this order:

  1. A row with experts = "a;b;" and no owners.
  2. A row with both experts = "a;b;" and owners = "c;d;".
  3. A row that has neither experts nor owners.
  4. A row with owners = "e;f;" and no experts.

The output entities (aligned by index) must satisfy:

  • Entity 0 contacts: Owner is an empty list, while Expert is [{"id":"a"}, {"id":"b"}].
  • Entity 1 contacts: Owner is [{"id":"c"}, {"id":"d"}] and Expert is [{"id":"a"}, {"id":"b"}].
  • Entity 2: carries no contacts key.
  • Entity 3 contacts: Expert is an empty list, while Owner is [{"id":"e"}, {"id":"f"}].

Scope Constraint

Do not alter any other aspect of entity parsing (typeName, name, qualifiedName, attributes, etc.). The only item in scope is the optional/independent handling of the experts and owners columns.

Goal

Update the AtlasAttributeDef class in the module pyapacheatlas.core.typedef so that its cardinality attribute is handled correctly, with support for both enum-type and raw string values.

Cardinality

An enumeration type that exposes (at minimum) the following members, with the .value of each member being the string form of its name:

  • Cardinality.SINGLE, whose value is "SINGLE"
  • Cardinality.SET, whose value is "SET"
AtlasAttributeDef

The constructor's signature must accept at least:

AtlasAttributeDef(name, cardinality=..., ...)
  • name: the name of the attribute.
  • cardinality: an optional keyword argument (its default is such that, when it is omitted, the resulting cardinality is "SINGLE").

After an instance is constructed, it must expose a cardinality attribute (accessible via instance.cardinality).

Behavior Requirements

The value stored in the cardinality attribute must be determined according to the following rules:

  1. If cardinality is not provided (the caller omits it): the value stored in cardinality must be the string "SINGLE".

  2. If cardinality is a Cardinality enum member: the value stored in cardinality must be coerced to that member's string value (that is, its .value). For example, passing Cardinality.SET leads to the stored value "SET".

  3. If cardinality is any other value (e.g., a raw string): the value must be accepted and stored as-is, with no validation or transformation performed. For example, passing "BLAH" leads to the stored value "BLAH".

Remarks

  • Validation of arbitrary string values is not required; unrecognized raw values are stored unchanged.
  • The cardinality that is stored is always a plain value (a string), never an enum member.
