Task Specification: Architecture Detection for Additional Linux Distributions

Objective

Extend the platform/architecture detection logic so that it correctly identifies the target build architecture string for additional Linux distributions and versions, notably Debian 7, Debian 8, and Ubuntu 16.04.

Public API Surface

There must be a function that maps distribution information to an architecture identifier string. Based on how it is exercised, the function accepts (in order):

  1. A boolean indicating whether an os-release file is available/should be used.
  2. A list of lines (strings) representing the contents of the os-release file (empty list when not available).
  3. A 3-tuple (distribution, version, codename) representing platform information (e.g., as would come from a legacy distribution-detection call). Any of these elements may be empty strings.
  4. A string giving the operating system name (e.g., 'Linux', 'Darwin').
  5. A string giving the processor/machine type (e.g., 'x86-64').

The function returns a single architecture identifier string (e.g., 'slc7_x86-64', 'ubuntu1604_x86-64').

The engineer must ensure this detection function exists in the utilities module of the codebase and is importable/callable with the inputs described above so that the four ordered inputs (2–5, plus the availability flag) produce the required architecture string. Preserve the existing function name and calling convention already used for architecture detection in the codebase.

Required Behavior

Given the inputs above, the function must produce the following architecture identifier strings. Two detection paths exist depending on the boolean flag / availability of os-release contents.

macOS
  • OS name Darwin, processor x86-64, no os-release, empty platform tuple → osx_x86-64.
RedHat-family (via platform tuple; no os-release)

When os-release is unavailable (flag false, empty line list) and OS name is Linux:

  • Platform tuple distribution redhat, version 5.XX → slc5_x86-64.
  • Platform tuple distribution centos, version 6.X → slc6_x86-64.
  • Platform tuple distribution centos, version 7.X → slc7_x86-64.

The major version number is taken from the leading integer of the version field.

Ubuntu (via platform tuple; no os-release)

When os-release is unavailable (flag false, empty line list), OS name Linux:

  • Platform tuple distribution Ubuntu, version 15.10 → ubuntu1510_x86-64.

The architecture tag is ubuntu followed by the version with the dot removed (zero-padded to four digits, i.e. 15.10 → 1510).

Distributions detected from os-release contents

When the flag is true and a non-empty list of os-release lines is supplied, detection is driven by parsing those lines. The following cases must be handled:

  • Ubuntu 16.04 (ID=ubuntu, VERSION_ID="16.04", codename xenial) → ubuntu1604_x86-64.
  • Ubuntu 15.10 (VERSION_ID="15.10", codename wily) → ubuntu1510_x86-64.
  • Ubuntu 14.04 (VERSION_ID="14.04", codename trusty) → ubuntu1404_x86-64.
  • Linux Mint 17.3 (an os-release identifying Linux Mint 17.3 "rosa") → ubuntu1404_x86-64. Linux Mint is mapped to its corresponding Ubuntu base architecture.
  • Debian 7 (ID=debian, VERSION_ID="7", "wheezy") → ubuntu1204_x86-64. Debian 7 is mapped to the Ubuntu 12.04 architecture tag.
  • Debian 8 (ID=debian, VERSION_ID="8", "jessie") → ubuntu1404_x86-64. Debian 8 is mapped to the Ubuntu 14.04 architecture tag.
os-release present but platform tuple empty (ANACONDA case)

For the Ubuntu 15.10 and Ubuntu 14.04 os-release contents, when the accompanying platform tuple is empty (('', '', '')) — the situation where a conda/Anaconda-provided Python returns no legacy platform info — detection must still succeed from the os-release contents alone, yielding ubuntu1510_x86-64 and ubuntu1404_x86-64 respectively.

Notes on os-release parsing

The os-release content is a series of KEY=VALUE lines; values may be wrapped in double quotes and must be unquoted. Relevant keys include ID (distribution identifier, e.g. ubuntu, debian), VERSION_ID (e.g. 16.04, 7, 8), and codename fields. Leading/blank lines must be tolerated. Detection must not depend on the legacy platform tuple when os-release contents are provided.

2. parseRecipe(reader)

Parse a recipe obtained from a reader. A recipe file consists of a YAML header, a line containing exactly --- as a separator, and a body that follows.

  • reader is a callable object that returns the full recipe text as a string when called. It also exposes a url attribute (a string) identifying the recipe, which must be used verbatim in error messages.

Return a 3-tuple (err, meta, body):

  • err: an error message string, or None if parsing succeeded.
  • meta: a dictionary of the parsed YAML header key/value pairs, or None on certain errors (see below).
  • body: the recipe body text that follows the --- separator (may be an empty string).
Success case

When the text contains a valid YAML header terminated by a --- separator line and the header contains a package key:

  • err is None.
  • meta is the parsed header as a dictionary (e.g. a header with package: foo and version: bar yields meta["package"] == "foo" and meta["version"] == "bar").
  • body is the text after the separator.
Error cases

Let URL denote the reader's url attribute value.

  1. No header separator present. If the text contains no --- separator line at all (the whole content is a single blob with no header terminator):

    • err == "Unable to parse %s. Header missing." % URL

  2. Empty header. If the content is just the separator (---) with an empty header before it:

    • err == "Malformed header for %s\nEmpty recipe." % URL
    • meta is falsy (empty/None) and body is falsy (empty/None).

  3. Header is not valid YAML (YAML parse error). If the header portion before --- cannot be parsed as YAML:

    • err is the string "Unable to parse %s" % URL followed by a newline and the underlying YAML parser's error text.
    • meta is None.
    • body is the body after the separator (may be whitespace only; body.strip() == "" for a header-only broken recipe).

  4. Header parses to YAML but is not a key/value mapping. If the header is valid YAML but does not yield a dictionary (e.g. a bare scalar such as broken):

    • err == "Malformed header for %s\nNot a YAML key / value." % URL

  5. Header is a valid mapping but lacks a package key. (e.g. header contains only tag: foo):

    • err == "Malformed header for %s\nMissing package field in header." % URL

Notes:

  • For case 3, the YAML error text appended after the first line must correspond to the standard YAML parser diagnostics (including the while parsing ... / while scanning ... context, location in "<string>", line N, column M, and the offending source line with caret marker) produced when parsing only the header portion. Comparisons against expected error text are done after stripping surrounding whitespace in the unterminated-quote scenario.

  • .json() — returns a list of dicts, each having a "name" key naming an available tarball file (e.g. {"name": "zlib-v1.2.3-1.slc7_x86-64.tar.gz"})
  • .headers — a dict that includes 'content-length' (string, total number of bytes)
  • .iter_content(chunk_size=...) — yields/returns byte chunks of the response body; may yield nothing (empty/truncated download)

Required behavior:

  • It queries the remote to obtain the list of available tarballs (via get returning a JSON list of {"name": ...} entries) and, when it selects a tarball to download, streams the content via .iter_content(...), writing the received bytes to a local file. File writing must go through the module-level open function in alibuild_helpers.build (i.e. alibuild_helpers.build.open(filename, mode)), and the write target is opened in a binary-writing mode. The returned file-like object supports being written byte chunks.
  • It must consult the filesystem via the module-level os in alibuild_helpers.build (e.g. os.path.isfile(...)) to decide whether a local copy already exists; when the file is not present locally it proceeds to download it.
  • If a GET returns a 404 (missing resource — e.g. a store path that does not exist), syncToLocal must handle this gracefully: it must NOT raise or abort the process. It may emit a warning (through the module-level warning function in alibuild_helpers.build) and return normally.
  • If the streamed download yields no content / is truncated (i.e. .iter_content(...) produces nothing while a nonzero content-length was advertised), syncToLocal must also complete without raising; it may report an error via the module-level error function, but must not crash.
  • The method must complete normally for the success case (valid JSON list, matching tarball, full content stream) and produce the downloaded local file.

The module-level names get, open, os, warning, error, dieOnError, getstatusoutput, and execute must all be referenceable as attributes of alibuild_helpers.build (so they can be patched). syncToLocal and syncToRemote for all three syncer types must be callable and complete without unhandled exceptions across the cases described (present/missing tarball hashes, and a store path that triggers a 404).
