Task Specification: Architecture Detection for Further Linux Distributions

Goal

What is needed here is an extension of the platform/architecture detection logic so that the target build architecture string gets identified correctly for additional Linux distributions and versions — Debian 7, Debian 8, and Ubuntu 16.04 in particular.

Public API

A function that maps distribution information to an architecture identifier string must exist. Judging from how it is exercised, the function accepts the following, in order:

  1. A boolean that tells whether an os-release file is available/should be used.
  2. The contents of the os-release file, given as a list of lines (strings); the list is empty when the file is not available.
  3. Platform information, in the form of the 3-tuple (distribution, version, codename) (e.g., what a legacy distribution-detection call would deliver). Any of the tuple's elements may be empty strings.
  4. The operating system name, as a string (e.g., 'Linux', 'Darwin').
  5. The processor/machine type, as a string (e.g., 'x86-64').

A single architecture identifier string (e.g., 'slc7_x86-64', 'ubuntu1604_x86-64') is what the function returns.

The engineer must ensure that this detection function exists in the codebase's utilities module and that it is importable/callable with the inputs described above, so that the required architecture string results from the four ordered inputs (2–5, plus the availability flag). The existing function name and calling convention — the ones already used for architecture detection in the codebase — must be preserved.

Required Behavior of the Function

For the inputs described above, the architecture identifier strings the function must produce are the ones below. Two detection paths are involved; which one applies is decided by the boolean flag / availability of os-release contents.

macOS
  • OS name Darwin together with processor x86-64, no os-release and an empty platform tuple → osx_x86-64.
RedHat family (through the platform tuple; no os-release)

Whenever os-release is absent (flag false, empty line list) and the OS name is Linux:

  • A platform tuple with distribution redhat and version 5.XX → slc5_x86-64.
  • A platform tuple with distribution centos and version 6.X → slc6_x86-64.
  • A platform tuple with distribution centos and version 7.X → slc7_x86-64.

The integer that leads the version field supplies the major version number.

Ubuntu (through the platform tuple; no os-release)

Whenever os-release is absent (flag false, empty line list) and the OS name is Linux:

  • A platform tuple with distribution Ubuntu and version 15.10 → ubuntu1510_x86-64.

To build the architecture tag, take the version, drop its dot, zero-pad it to four digits (i.e. 15.10 → 1510), and place it after ubuntu.

Distributions detected by parsing the os-release contents

With the flag true and a non-empty list of os-release lines supplied, parsing those lines is what drives detection. The cases that follow must be handled:

  • Ubuntu 16.04 — ID=ubuntu, VERSION_ID="16.04", codename xenial → ubuntu1604_x86-64.
  • Ubuntu 15.10 — VERSION_ID="15.10", codename wily → ubuntu1510_x86-64.
  • Ubuntu 14.04 — VERSION_ID="14.04", codename trusty → ubuntu1404_x86-64.
  • Linux Mint 17.3 — an os-release that identifies Linux Mint 17.3 "rosa" → ubuntu1404_x86-64. Linux Mint is mapped onto the architecture of the Ubuntu base it corresponds to.
  • Debian 7 — ID=debian, VERSION_ID="7", "wheezy" → ubuntu1204_x86-64. The Ubuntu 12.04 architecture tag is what Debian 7 is mapped to.
  • Debian 8 — ID=debian, VERSION_ID="8", "jessie" → ubuntu1404_x86-64. The Ubuntu 14.04 architecture tag is what Debian 8 is mapped to.
os-release present with an empty platform tuple (ANACONDA case)

For the os-release contents of Ubuntu 15.10 and Ubuntu 14.04, suppose the platform tuple accompanying them is empty (('', '', '')) — the situation of a conda/Anaconda-provided Python that returns no legacy platform info. Even then, detection must still succeed with the os-release contents by themselves, yielding ubuntu1510_x86-64 and ubuntu1404_x86-64 respectively.

Notes on How the os-release Content Is Parsed

The os-release content comes as a series of KEY=VALUE lines; values may be enclosed in double quotes and must be unquoted. The relevant keys include ID (the distribution identifier, e.g. ubuntu, debian), VERSION_ID (e.g. 16.04, 7, 8), and codename fields. Blank lines, and lines at the start, must be tolerated. When os-release contents are provided, depending on the legacy platform tuple is something detection must not do.

Summary of the Mapping Rules

Distribution (os-release) Version Architecture that results
Ubuntu 16.04 ubuntu1604_x86-64
Ubuntu 15.10 ubuntu1510_x86-64
Ubuntu 14.04 ubuntu1404_x86-64
Linux Mint 17.3 ubuntu1404_x86-64
Debian 7 ubuntu1204_x86-64
Debian 8 ubuntu1404_x86-64

Across all the Linux cases, the suffix (x86-64) that gets appended comes from the processor argument supplied.

2. parseRecipe(reader)

Parse a recipe supplied by a reader. A recipe file is made up of a YAML header, a line that contains exactly --- and acts as a separator, and the body that follows it.

  • reader is a callable object which, when called, returns the full recipe text as a string. It also exposes a url attribute (a string) that identifies the recipe, and this attribute must be used verbatim in error messages.

The function returns a 3-tuple (err, meta, body):

  • err: a string holding an error message, or None if parsing succeeded.
  • meta: a dictionary holding the parsed YAML header's key/value pairs, or None on certain errors (see below).
  • body: the recipe body text coming after the --- separator (may be an empty string).
Success case

When the text contains a valid YAML header that is terminated by a --- separator line and the header contains a package key:

  • err is None.
  • meta is the parsed header, as a dictionary (e.g. a header with package: foo and version: bar yields meta["package"] == "foo" and meta["version"] == "bar").
  • body is the text following the separator.
Error cases

Let URL denote the value of the reader's url attribute.

  1. No header separator present. If the text has no --- separator line at all (the entire content is a single blob without a header terminator):

    • err == "Unable to parse %s. Header missing." % URL

  2. Empty header. If the content is only the separator (---) and the header before it is empty:

    • err == "Malformed header for %s\nEmpty recipe." % URL
    • meta is falsy (empty/None) and so is body (empty/None).

  3. Header is not valid YAML (YAML parse error). If the header portion preceding --- cannot be parsed as YAML:

    • err is the string "Unable to parse %s" % URL with a newline and the underlying YAML parser's error text appended after it.
    • meta is None.
    • body is the body located after the separator (it may be whitespace only; body.strip() == "" for a broken, header-only recipe).

  4. Header parses to YAML but is not a key/value mapping. If the header is valid YAML yet does not yield a dictionary (e.g. a bare scalar such as broken):

    • err == "Malformed header for %s\nNot a YAML key / value." % URL

  5. Header is a valid mapping but lacks a package key. (e.g. the header contains only tag: foo):

    • err == "Malformed header for %s\nMissing package field in header." % URL

Notes:

  • For case 3, the YAML error text appended after the first line must correspond to the standard YAML parser diagnostics (including the while parsing ... / while scanning ... context, the location in "<string>", line N, column M, and the offending source line with caret marker) that is produced when parsing only the header portion. In the unterminated-quote scenario, comparisons against the expected error text are performed after stripping surrounding whitespace.

3. parseDefaults(disable, getDefaultsReader, log)

Parse a "defaults" configuration, derive the package overrides and recipe taps from it, and accumulate the set of disabled packages along the way.

Parameters:

  • disable: a list of package names that are to be disabled. The list is mutated in place by appending any packages the defaults declare as disabled.
  • getDefaultsReader: a callable taking zero arguments that returns a 2-tuple (defaultsMeta, defaultsBody), where defaultsMeta is a dictionary describing the defaults header and defaultsBody is the body string.
  • log: a callable used for logging (it is invoked with string messages). No particular log output is verified.

Behavior:

  • If the defaults metadata contains a disable entry, the package(s) named in it must be appended to the disable list. A single package name supplied as a string must be appended as that name. (After processing, disable reflects the original entries together with the newly disabled ones.)
  • If an overrides mapping is present in the defaults metadata, produce:
    • overrides: a dictionary whose keys are the lowercased package names (the part of each override key that comes before any @<ref>), and whose values are the corresponding override mappings (with the reference stripped from the key). For the override key "ROOT@master" with value {"requires": "GCC"}, the result is {"root": {"requires": "GCC"}}.
    • taps: a dictionary keyed by that same lowercased package name, whose value is the full original override key written as a recipe reference of the form "dist:<package>@<ref>". For the override key "ROOT@master", the entry is {"root": "dist:ROOT@master"}.

The function returns a 3-tuple (err, overrides, taps):

  • err: a string holding an error message, or None on success.
  • overrides: the overrides dictionary as described above.
  • taps: the taps dictionary as described above.

Goal

Public Interface

The following importable symbol is to be created:

from alibuild_helpers.utilities import Hasher
The Hasher class

Constructor

Hasher()

No arguments are accepted. A new hasher instance is created whose internal state is that of a fresh SHA-1 hash (i.e., accumulated input that is empty).

Calling the instance

Instances must be callable and take a single string argument, which is fed into the running hash:

h = Hasher()
h("foo")

Required behavior:

  • When the instance is called with a string, that string's bytes are appended to the running hash state (the updating is incremental / cumulative).
  • An empty string "", when passed, must leave the hash state unchanged.
  • Unicode strings must be accepted, and they must be hashed using their UTF-8 encoding. Hash states produced from distinct Unicode code points must be distinct (e.g., u'\ua000' and u'\ua001' yield different digests).
  • If a non-string argument is passed (an integer, for example), the call must raise AttributeError.

The hexdigest() method

h.hexdigest()

The method returns the current hash value expressed as a lowercase hexadecimal SHA-1 digest string (40 hex characters). It accounts for all input fed so far and can be called multiple times without the hash state being altered.

Examples of Expected Behavior

Starting from a fresh Hasher instance:

  • After "foo" has been fed, hexdigest() returns "0beec7b5ea3f0fdbc95d0dd47f3c5bc275da8a33".
  • When "" is fed afterward, the digest does not change; it remains "0beec7b5ea3f0fdbc95d0dd47f3c5bc275da8a33".
  • When a non-string value such as 1 is fed, AttributeError is raised.
  • Continuing by feeding "bar" (so the total input is "foobar") yields a hexdigest() equal to "8843d7f92416211de9ebb963ff4ce28125932878".

For Unicode input, using independent fresh instances:

  • Feeding u'\ua000' yields a hexdigest() equal to "2af8e41129115eb231a0af76ec5465d3a9184fc4".
  • Feeding u'\ua001' yields a hexdigest() equal to "1619bcdbeff6828138ad9b6e43cc17e856457603".

Compatibility

Return value

  • When the metadata omits disable, no package is added.

    ("overrides should be a dictionary", None, None)

Task Description

aliBuild, a build tool written in Python that supports both Python 2 and Python 3, is what you will be working on. Several changes must be implemented, and a few related behaviors adjusted along with them, so that recipe hashing and YAML parsing come out deterministic and ordering-stable no matter which Python version is in use. Every module these changes touch sits under the alibuild_helpers package.

The requirements that follow are exhaustive. Exactly what they describe must be implemented.

1. Command-line argument parser: the new architecture action

A positional action argument is exposed by the argument parser, and the valid choices it accepts form a fixed set. Complete and ordered, the set of valid choices must be exactly:

analytics, architecture, build, clean, deps, doctor, init, version

Given an action that is not valid, the standard argparse "invalid choice" error message is what the parser must produce, enumerating the choices in exactly the order shown above. One example: give builda as the action and the parser must yield:

argument action: invalid choice: 'builda' (choose from 'analytics', 'architecture', 'build', 'clean', 'deps', 'doctor', 'init', 'version')

(It is between analytics and build that the architecture choice must be inserted.) Apart from this, nothing else about the parser's behavior changes.

2. Recipe hashing and YAML parsing: ordered and deterministic

One requirement sits at the center: dictionaries that emerge from YAML parsing and then serve to compute recipe hashes must preserve a deterministic ordering; the consequence is that recipe hashes stay stable and never depend on the order in which Python iterates dicts.

2.1 YAML maps with a preserved order

Ordered mappings are what YAML parsing must produce inside alibuild_helpers.utilities (i.e., mapping keys must retain the order in which they appear in the YAML source, with OrderedDict used for this). These public functions of alibuild_helpers.utilities must still be present, with the signatures and behaviors given:

  • parseRecipe(reader) — takes a callable reader which returns the recipe text; the tuple (error, metadata, body) is returned, with metadata the parsed YAML header (an ordered mapping) and body the recipe script body.
  • getRecipeReader(url, ...) — an appropriate reader object is what it returns.
  • FileReader and GitReader — classes that serve as readers.
  • validateDefaults(...) and the exception type SpecError.
  • parseDefaults(disable, getDefaultsFunc, log) — details below.

Mapping values that are themselves OrderedDict instances (or plain dicts) must be accepted by the parsing, transparently.

2.2 parseDefaults

parseDefaults(disable, getDefaultsFunc, log):

  • The disable argument carries a list of package names to disable; the function mutates it in place, appending the disable value(s) that the defaults data contains.
  • getDefaultsFunc is a callable taking zero arguments and returning the tuple (defaultsData, errorString); defaultsData is a mapping that may contain the keys disable and overrides.
  • A tuple (error, overrides, taps) is what the function returns.

The behavior it must exhibit:

  • Let disable == ["bar"] hold initially and let the defaults mapping carry a disable value of "foo"; once the call has been made, disable must equal ["bar", "foo"].
  • Keys of the form "<Package>@<tag>" (e.g. "ROOT@master") may be used by the defaults' overrides mapping, each mapping to a mapping of override properties. The returned overrides must have the lower-cased package name (the part before @) as its keys, and an empty entry for "defaults-release" must always be present in it. Given a defaults mapping with overrides == {"ROOT@master": {"requires": "GCC"}}, the returned overrides must equal:
    {"defaults-release": {}, "root": {"requires": "GCC"}}

OrderedDict instances may serve as the overrides values that come in via the defaults mapping.
