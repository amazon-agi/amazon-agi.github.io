01 The codebase includes an SQL parser exposed via a top-level function 437 words · source specification

Task: Add support for the ->> JSON operator in the SQL parser

Context

The codebase includes an SQL parser exposed via a top-level function:

parse_sql(sql: str)

This function parses an SQL string and returns an Abstract Syntax Tree (AST) composed of node objects. The relevant AST node classes are importable from the parser's AST package and include (at minimum):

  • Select — represents a SELECT statement. Relevant constructor keyword arguments used here: targets (list of expression nodes), where (an expression node), and from_table.
  • BinaryOperation(op, args) — represents a binary operation, where op is a string naming the operator and args is a two-element list of operand nodes.
  • Identifier(...) — represents a column/table identifier. Can be constructed with a single name string, or with parts=[...].
  • Constant(value) — represents a literal value.
  • Star() — represents *.

Each AST node supports:

  • str(node) — renders the node back to an SQL string.
  • node.to_tree() — produces a structured tree representation.

Two AST trees are considered equivalent when both their str(...) renderings and their to_tree() renderings match.

Required behavior

The parser must recognize ->> as a binary operator (the JSON "get value as text" operator), in addition to the already-supported -> operator.

JSON operator parsing

When parsing an expression that uses -> and ->>, these operators are left-associative and share the same precedence, so they chain left-to-right.

For the input:

SELECT col->1->>'c' from TAB1

the parsed target expression must be:

BinaryOperation(
    op='->>',
    args=[
        BinaryOperation(
            op='->',
            args=[
                Identifier('col'),
                Constant(1),
            ],
        ),
        Constant('c'),
    ],
)

i.e. col->1 is grouped first as a -> operation, and the result becomes the left operand of the outer ->> operation whose right operand is the string constant 'c'.

The resulting Select has this as its single target and from_table=Identifier(parts=['TAB1']).

Rendering this AST back to a string and to a tree must be consistent with re-parsing (round-trip stable): the ->> operator must render as ->>.

Existing operators must remain intact

The following operators must continue to parse as BinaryOperation nodes with the operator string preserved exactly, without regression:

  • The vector operators <->, <+>, <#>, <=>, <~>, <%>. For an input of the form:

    SELECT * from TAB1 WHERE embedding <op> '[3,1,2]'

    the result must be a Select with targets=[Star()], from_table=Identifier(parts=['TAB1']), and

    where=BinaryOperation(
    op='<op>',
    args=[Identifier('embedding'), Constant('[3,1,2]')],
)

    where <op> is the exact operator string.

  • The -> JSON operator must continue to parse and render as before.

All of the above must round-trip: parsing, then rendering via str(...) and to_tree(), must yield output equivalent to the corresponding hand-built AST.

Task: Support LATERAL Joins in SQL Parsing

Objective

Extend the SQL parser to recognize and correctly parse join clauses that use the LATERAL keyword, specifically INNER JOIN LATERAL, where the right-hand side of the join is a parenthesized subquery.

Public API

The parser is invoked via:

parse_sql(query: str) -> ASTNode

This function already exists and returns an AST. The AST node classes used below already exist and are importable from the project's AST module (the same module used by Select, Join, Identifier, Star, Constant, BinaryOperation). This task only requires that parse_sql correctly handle the new join syntax.

Required Behavior

The parser must accept queries containing a lateral join written as:

select * from table1 a
INNER JOIN LATERAL (SELECT *
    FROM table2 b
    WHERE a.x=b.x
    LIMIT 1) b ON true

When such a query is parsed, the result must be a Select node structured as follows:

  • targets: [Star()]
  • from_table: a Join node with:
    • join_type: the string 'INNER JOIN LATERAL'
    • left: Identifier('table1', alias=Identifier('a'))
    • right: the parsed subquery (see below)
    • condition: Constant(True) (from the ON true clause)

The subquery on the right side of the join must parse to a Select node with:

  • targets: [Star()]
  • from_table: Identifier('table2', alias=Identifier('b'))
  • where: BinaryOperation(op='=', args=[Identifier('a.x'), Identifier('b.x')])
  • limit: Constant(1)
  • alias: Identifier('b') (the alias given to the parenthesized subquery)
  • parentheses: True

Correctness Requirements

For the query above:

  • The parsed AST's string representation (str(ast)) must equal the string representation of the expected Select structure described above.
  • The parsed AST's tree representation (ast.to_tree()) must equal the tree representation of that same expected structure.

Scope

The join type keyword INNER JOIN LATERAL must be preserved verbatim as the join_type value. The rest of the parsing behavior (subquery parsing, aliasing, where clauses, limits, ON conditions) follows existing parser conventions; only the recognition of the LATERAL keyword as part of the join type needs to be added.

Task Specification: Support DISTINCT ON in SELECT statements

Overview

Extend the SQL parser and AST to support the PostgreSQL-style DISTINCT ON (...) clause in SELECT statements. Parsing must produce an AST node whose distinct attribute carries the list of columns specified in the DISTINCT ON clause, and rendering that AST back to a string must reproduce the original SQL.

Existing Context

  • There is a Select AST node (importable as Select) that already supports a distinct attribute. Previously, distinct was a plain boolean flag indicating the presence of a bare DISTINCT keyword.
  • There is a parse_sql(sql_string) function that parses a SQL string into an AST.
  • There is an Identifier node and a Star node.
  • AST nodes support:
    • str(ast) — renders the node back to SQL text.
    • ast.to_tree() — produces a structural tree representation.
    • Equality of rendered output and tree output is how two ASTs are compared for equivalence.

Required Behavior

Select.distinct semantics

The distinct attribute of Select must now support carrying a list of Identifier objects, in addition to its existing boolean behavior.

  • When distinct is a list of Identifier objects, it represents a DISTINCT ON (...) clause, where the listed identifiers are the columns inside the parentheses, in order.
Parsing

parse_sql must accept the DISTINCT ON (col1, col2, ...) syntax immediately following SELECT. When present:

  • The columns inside the parentheses must be parsed into a list of Identifier objects and assigned to the resulting Select node's distinct attribute, preserving their order.
  • Each column may be a simple identifier (e.g. column1) or a dotted/multi-part identifier (e.g. t1.column1). Dotted identifiers must be represented as a single Identifier whose value reflects the full dotted path.
  • One or more columns may be listed, comma-separated.
  • The remainder of the SELECT statement (targets, FROM, etc.) is parsed as usual. Targets may be a Star or a list of identifiers.

Examples of input that must parse correctly:

SELECT DISTINCT ON (t1.column1) * FROM t1

produces a Select equivalent to:

Select(
    targets=[Star()],
    from_table=Identifier('t1'),
    distinct=[Identifier('t1.column1')]
)

SELECT DISTINCT ON (column1, column2) column3, column4 FROM t1

produces a Select equivalent to:

Select(
    targets=[Identifier('column3'), Identifier('column4')],
    from_table=Identifier('t1'),
    distinct=[Identifier('column1'), Identifier('column2')]
)
Rendering

For a Select node whose distinct attribute is a list of Identifier objects, str(...) must render a DISTINCT ON (...) clause after SELECT, listing the identifiers in order, comma-separated, inside parentheses. The round-trip str(parse_sql(sql)) must reproduce equivalent SQL for the inputs above.

The to_tree() output must reflect the list of distinct identifiers such that two Select nodes constructed with equal distinct lists produce identical trees.

Public API Surface

  • Select — AST node accepting keyword arguments targets, from_table, and distinct (where distinct may be a list of Identifier).
  • Identifier — accepts a string value that may contain dotted parts.
  • Star — represents *.
  • parse_sql(sql: str) — returns an AST node.

All of the above must be importable from the same locations they are currently exposed.

05 You must extend the SQL CREATE TABLE parser to correctly handle column type definitions that include two numeric parameters (e.g. 386 words · source specification

Overview

You must extend the SQL CREATE TABLE parser to correctly handle column type definitions that include two numeric parameters (e.g. precision and scale), such as decimal(5,2) and NUMBER(10, 0).

Public API

TableColumn

The TableColumn class represents a single column definition parsed from a CREATE TABLE statement. It must support the following attributes/constructor keyword arguments:

  • name (str): the column name.
  • type (str): the column type name, preserved exactly as written in the source (e.g. decimal, NUMBER, INT, TEXT).
  • is_primary_key (bool): whether the column is part of the table's primary key.
  • nullable (bool): whether the column allows NULL values.
  • length (int, optional): the first numeric parameter of the type, when present.
  • length2 (int, optional): the second numeric parameter of the type, when present.

TableColumn instances that carry identical attribute values must compare as equal.

Required Behavior

When parsing a CREATE TABLE statement, each column definition must produce a TableColumn:

  1. Type name preservation: The type attribute must retain the exact spelling used in the source text (do not normalize case). For example, decimal(5,2) yields type='decimal' and NUMBER(10, 0) yields type='NUMBER'.

  2. Two-parameter numeric types: A type declared with two comma-separated numeric parameters must populate both length (first parameter) and length2 (second parameter) as integers.

    • decimal(5,2) → length=5, length2=2
    • NUMBER(10, 0) → length=10, length2=0
    • Whitespace surrounding the parameters (as in NUMBER(10, 0)) must be tolerated.
    • A second parameter of 0 must be captured as length2=0 (i.e. treated as present, not omitted).

  3. Nullability: A column declared with a NOT NULL constraint must set nullable=False. For example, links NUMBER(10, 0) NOT NULL yields nullable=False.

  4. Primary keys: A table-level PRIMARY KEY (col_a, col_b) clause must mark each named column with is_primary_key=True.

  5. Simple types: Columns declared with a bare type and no parameters (e.g. INT, TEXT) produce a TableColumn with just name and type set (no length/length2).

The parser must be able to process a CREATE TABLE statement whose column list mixes simple typed columns, single-token constrained columns, two-parameter numeric columns (with and without NOT NULL), and a trailing table-level composite PRIMARY KEY clause.

Note

The table-level primary key keyword is written as PRIMARY KEY (two words separated by a space). There is no support for a single underscored PRIMARY_KEY token.

Add support for parsing an EVALUATE SQL statement that evaluates a knowledge base. This requires a new AST node class and integration into the SQL parser so that parse_sql returns an instance of the new node when given an EVALUATE ... statement.

Public API Surface

New AST Class: EvaluateKnowledgeBase
  • Module: mindsdb_sql_parser.ast.mindsdb.knowledge_base
  • Class name: EvaluateKnowledgeBase
  • Must also be importable from the top-level package mindsdb_sql_parser (i.e., exported so existing sibling classes like CreateKnowledgeBase and DropKnowledgeBase are accessible the same way).

Constructor signature (keyword arguments):

EvaluateKnowledgeBase(
    name,           # Identifier: the knowledge base name
    test_table,     # Identifier: fully-qualified test table
    save_to,        # Identifier: fully-qualified target table
    llm,            # dict
    generate_data,  # dict
)

The class must be a proper AST node consistent with the other node classes in the package: two instances constructed with equal field values must compare equal via ==. It should support the same construction and equality semantics used across the existing AST node types in this codebase (including the standard render/repr infrastructure those nodes provide).

Parsing Behavior

parse_sql (from mindsdb_sql_parser) must recognize a statement of the form:

EVALUATE <knowledge_base_name>
USING
    TEST_TABLE = <table_identifier>,
    SAVE_TO = <table_identifier>,
    LLM = { ...json object... },
    generate_data = { ...json object... }
Mapping rules
  • The identifier immediately following EVALUATE becomes name, an Identifier built from that single name.
  • After the USING keyword, a comma-separated list of key = value assignments follows. Parameter keys are case-insensitive.
  • The parameters and their handling:
    • TEST_TABLE — value is a table reference (dot-separated parts). Stored in test_table as an Identifier whose parts list contains each dotted segment (e.g. my_database.some_table_1 → Identifier(parts=["my_database", "some_table_1"])).
    • SAVE_TO — same handling as TEST_TABLE, stored in save_to.
    • LLM — value is a JSON object literal. Stored in llm as a Python dict with the corresponding keys and values (strings preserved as strings).
    • generate_data — value is a JSON object literal. Stored in generate_data as a Python dict, where values may be strings or integers preserved with their native Python types (e.g. "count": 100 → integer 100).
Expected result

Given:

EVALUATE my_knowledge_base
USING
    TEST_TABLE = my_database.some_table_1,
    SAVE_TO = my_database.some_table_2,
    LLM = {
        "provider": "openai",
        "model": "gpt-3.5-turbo",
        "api_key": "my_api_key"
    },
    generate_data = {
        "from_sql": "SELECT content FROM my_database.some_table",
        "count": 100
    }

parse_sql must return:

EvaluateKnowledgeBase(
    name=Identifier("my_knowledge_base"),
    test_table=Identifier(parts=["my_database", "some_table_1"]),
    save_to=Identifier(parts=["my_database", "some_table_2"]),
    llm={
        "provider": "openai",
        "model": "gpt-3.5-turbo",
        "api_key": "my_api_key"
    },
    generate_data={
        "from_sql": "SELECT content FROM my_database.some_table",
        "count": 100
    }
)

Notes / Scope

  • Only the behavior described above is required. No other statement forms, optional parameters, or defaults are in scope.
  • The returned object must equal a directly-constructed EvaluateKnowledgeBase with the field values shown, using ==.

Overview

You are working on mindsdb_sql_parser, a SQL parsing library. This task involves two changes:

  1. Adding support for an optional DISTINCT keyword after set-operation keywords (UNION, INTERSECT, EXCEPT) in SQL parsing, with a corresponding attribute on the AST nodes.
  2. Providing a to_single_line utility function.

Part 1: DISTINCT keyword support for set operations

AST node changes

The set-operation AST classes Union, Intersect, and Except (importable from mindsdb_sql_parser.ast) must accept a new keyword argument:

  • distinct_key: bool — defaults to False.

These classes already accept:

  • unique: bool
  • left — an AST node (left operand)
  • right — an AST node (right operand)

The new distinct_key attribute must be:

  • Stored on the instance.
  • Included in the node's structural/tree representation (to_tree()), so two nodes are tree-equal only when their distinct_key values match.
  • Reflected in the string representation (str(...)), so that rendering a node with distinct_key=True produces SQL containing the DISTINCT keyword after the set-operation keyword, and rendering with distinct_key=False omits it.
Parsing behavior

The SQL parser (parse_sql from mindsdb_sql_parser) must recognize an optional DISTINCT keyword placed immediately after the set-operation keyword. That is, both of these forms must parse:

SELECT col1 FROM tab1 UNION SELECT col1 FROM tab2
SELECT col1 FROM tab1 UNION DISTINCT SELECT col1 FROM tab2

The same applies to INTERSECT / INTERSECT DISTINCT and EXCEPT / EXCEPT DISTINCT.

Resulting behavior of parsing:

  • The keyword UNION produces a Union node, INTERSECT produces an Intersect node, EXCEPT produces an Except node.
  • For all of the above forms, unique=True on the resulting node.
  • When the DISTINCT keyword is present, the resulting node has distinct_key=True; when absent, distinct_key=False.
  • The left operand is the AST for the query before the keyword; the right operand is the AST for the query after the keyword (and after the optional DISTINCT).
Round-trip requirement

For a parsed set-operation AST, str(ast) must render back to SQL that is semantically equivalent to the input (including the DISTINCT keyword when it was present), and this rendered SQL, when re-parsed or compared as an AST, must be tree-equal and string-equal to an equivalently constructed node.

Part 2: to_single_line utility

Add a function:

mindsdb_sql_parser.utils.to_single_line(s: str) -> str

It takes a string and returns a normalized single-line version by collapsing all runs of whitespace (including newlines and indentation) into single spaces. In practice, for two strings that differ only in whitespace/newline formatting, applying to_single_line to both must yield equal results.

This function must produce results such that, given the string representation of a parsed AST node and the original SQL source string, normalizing both with to_single_line yields equal strings whenever the two represent the same SQL differing only by whitespace formatting.

Import surface required

The following must be importable and callable exactly as named:

  • from mindsdb_sql_parser import parse_sql
  • from mindsdb_sql_parser.ast import Union, Intersect, Except (each accepting unique, distinct_key, left, right)
  • from mindsdb_sql_parser.utils import to_single_line

Existing AST classes referenced by the surrounding code (Select, Identifier, etc.) and their behavior must remain unchanged aside from the additions above.
