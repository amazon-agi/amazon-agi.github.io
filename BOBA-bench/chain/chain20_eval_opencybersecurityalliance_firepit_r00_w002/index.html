Overview

You are working on a data storage component that supports caching data bundles and executing structured queries against the cached data. The query system builds SQL statements from structured query objects. This task concerns the correct handling of literal string values in query predicates — specifically ensuring that values that look like SQL injection attempts are treated as ordinary string literals rather than being interpolated into the SQL text.

Public API

The relevant objects are already importable in the codebase and used as follows:

  • A storage object obtained via a factory (as used elsewhere in the codebase; e.g. a tmp_storage(...)-style constructor that returns the store). The store exposes:

    • store.cache(name, [bundle_file]) — load one or more data bundle files into the store under a cache identifier.
    • store.assign_query(name, query) — execute the given Query and store its result set under the given name.
    • store.lookup(name) — return the stored result set for a name. The returned value supports len(...), reporting the number of rows.

  • Query construction objects (already defined; used to build the query passed to assign_query):

    • Query([...]) — a query composed of a list of clauses.
    • Table(name) — selects a source table by name.
    • Filter([...]) — applies a list of predicates.

Required Behavior

When a Query contains a Filter with a Predicate whose comparison value is a string, that string must be treated purely as a literal comparison value. It must never be interpreted as part of the SQL statement structure.

Two cases define the required behavior:

  • Case (2) retains the raising behavior: a value containing a single quote must still result in an UnexpectedError.

Overview

You must modify how firepit ingests STIX observation bundles so that, when a single Observation SDO contains multiple SCOs of the same type, the "primary" (most significant) instance is marked via a rank attribute stored on the containment relationship rather than on the SCO itself.

Background

When firepit caches a STIX bundle, it decomposes each Observation SDO into its constituent SCOs (Software, IP addresses, network-traffic, etc.) and records which SCOs belong to which observation. A single observation can contain multiple SCOs of the same type. For example, a network-traffic object typically references two ipv4-addr objects (source and destination). In such cases, firepit designates one of them as the "primary" SCO for that type within that observation.

Required Behavior Change

Ranking of primary SCOs

When multiple SCOs of the same type appear within a single observation, firepit must mark exactly one of them as the primary instance.

  • The mark must be stored as an attribute named x_firepit_rank.
  • The primary instance's x_firepit_rank value must be set to 1.
  • Non-primary instances must have a NULL (unset) x_firepit_rank value.
  • This attribute must live on the containment table that links observations to their contained SCOs — specifically, it must be a column named x_firepit_rank on the __contains relationship table.

The previously used attribute name x_root (stored on the SCO tables) must no longer be used for this purpose; the ranking information now belongs solely on the __contains table.

Data model

The __contains table records containment relationships and must include (at minimum) the following columns relevant to this task:

  • target_ref — the id of the contained SCO.
  • x_firepit_rank — the rank marker described above (integer or NULL).

The contained SCO's own table (e.g. ipv4-addr) is joined to __contains via <sco_table>.id = __contains.target_ref.

Concrete Example

Given a single observation that contains one network-traffic object and two ipv4-addr objects:

  • Both ipv4-addr rows exist in the ipv4-addr table.
  • The __contains table has a row for each ipv4-addr linking it to the observation.
  • Exactly one of those __contains rows has x_firepit_rank = 1; the other has x_firepit_rank as NULL.

A query that selects ipv4-addr values by joining the ipv4-addr table to __contains on id = target_ref and filtering where __contains.x_firepit_rank IS NOT NULL must return exactly one row — the primary IP address.

Scope

Do not change any public API surface, method names, or signatures. The only observable change required is:

  • The rank marker is named x_firepit_rank (value 1 for the primary), and
  • It is stored as a column on the __contains table rather than on the individual SCO tables.

Overview

Required Behavior

The function parses the STIX pattern and produces a SQL condition expressed in terms of column names only (object-path prefixes such as ipv4-addr: are stripped, leaving just the property name). Column/property names in the output must be double-quoted.

Property-type filtering

Only comparison expressions whose object path references the given sco_type contribute to the output. Comparisons targeting a different SCO type must be omitted.

  • If the pattern's comparison(s) reference an SCO type that does not match sco_type, the result is the empty string (an empty WHERE body).
Comparison operators and their SQL forms

For a matching property prop and a literal value:

  • Equality (=): produces "prop" = 'value'.
  • LIKE (LIKE): produces "prop" LIKE 'value'.

Boolean combinations and grouping

  • Parentheses in the input pattern that group sub-expressions are preserved as parentheses in the output around the corresponding grouped SQL. Task Specification: Normalized SCO Storage for firepit

Overview

You are implementing a "normalized" database storage model for STIX Cyber Observable (SCO) data in the firepit package. The core behavioral shift is that SCO tables must be deduplicated: each distinct SCO (identified by its deterministic STIX ID) is stored exactly once, regardless of how many times it appears across observations. Relationships between observations and SCOs, and between SCOs, are tracked in a separate relation table rather than being denormalized into the SCO tables.

This changes counts, column layouts, ID formats, and requires new/changed query behavior and several new API methods.

Package layout and imports

The following import paths must exist and be usable:

  • firepit.get_storage(dbname, session) — factory returning a storage object (referred to below as store).
  • firepit.stix21.makeid(obj) — see "Deterministic STIX 2.1 IDs".
  • firepit.query must expose the classes: Query, Table, Filter, Predicate, Aggregation, Group, Order, Limit, Projection, Column, Join.
  • firepit.exceptions must expose IncompatibleType, UnknownViewname, UnexpectedError.

Data model (normalized)

SCO tables

Each SCO type is stored in its own table named after the type (e.g. "ipv4-addr", "domain-name", "network-traffic", "user-account", "url", "identity").

  • SCO tables must NOT contain a type column or a spec_version column. (store.columns(...) and the table schema returned by the schema API must not include type or spec_version.)
  • SCO tables retain the SCO's own properties as columns (e.g. id, value, dst_port, account_login, user_id, etc.).
  • Reference properties (e.g. src_ref, dst_ref, process_ref, resolves_to_refs) are stored as the reference column itself (e.g. process_ref holds a target id), not exploded into dotted sub-columns. Specifically, an object with a process_ref yields a column named process_ref (not process_ref.id).
  • Each distinct SCO is stored once. Loading/caching the same SCO (same deterministic id) multiple times must not create duplicate rows.
The __contains relation table

A table named __contains records which SCOs are contained by which observations. It has at least the columns source_ref and target_ref (an SCO id in target_ref). It also carries a per-observation ranking column named x_firepit_rank used to mark the "primary"/most significant SCO of a given type within a single observation (see "Primary SCO ranking").

Observation timestamps

Observation-level timestamp data (first_observed, last_observed, number_observed) is associated with SCOs through the containment relation and observed-data, not stored as columns on the SCO tables themselves.

Deterministic STIX 2.1 IDs — firepit.stix21.makeid

makeid(obj) accepts a dict representing a STIX 2.1 SCO (which includes type, spec_version, and the SCO's contributing properties; it may also include an id key which must be ignored for ID computation) and returns the deterministic STIX 2.1 id string for that object.

  • The returned id must exactly match the id produced by the official stix2 library's deterministic ID generation for the same object with its id removed. This applies across SCO types including autonomous-system, directory, domain-name, email-addr, email-message, file, and ipv4-addr, including objects with nested structures (hashes, additional_header_fields, body_multipart, received_lines), reference properties, and non-ASCII values.
  • If a process SCO carries an x_unique_id, it must be used for deterministic ID generation.

Caching / loading data

store.cache(query_id, bundles)

Ingests one or more STIX bundles. bundles may be a single filename or a list of filenames. Supports STIX 2.0 and STIX 2.1 bundles. During ingest:

  • Objects are normalized into the SCO tables and __contains relation as described above.
  • Duplicate SCOs (same deterministic id) are merged into a single row.
  • Duplicate observed-data objects are dropped.
  • identity objects are handled (duplicate identities do not produce duplicate rows).
store.load(viewname, objects, sco_type=...)

Loads a list of plain SCO dicts (without ids) of the given sco_type into a table/view named viewname. Returns the sco_type string.

Merging of evolving objects: when multiple input dicts resolve to the same SCO (same identifying properties, e.g. same value for an ipv4-addr), they must be merged into a single row. Extra/optional properties present in any of the duplicates must be preserved on the merged row. For example, loading two ipv4-addr dicts with the same value where one carries an x_extra property (in either order) yields exactly one row whose type is 'ipv4-addr', whose value matches, and whose x_extra holds the provided value.

Note: rows returned by store.lookup for a loaded view include a type key reflecting the sco_type.

store.delete()

Removes the current session's data/tables so a fresh session can be created.

Extract / views

store.extract(viewname, sco_type, query_id, pattern)

Creates a view named viewname containing SCOs of sco_type matching the given STIX pattern string (e.g. "[network-traffic:dst_port < 1024]", "[ipv4-addr:value ISSUBSET '10.0.0.0/8']", "[url:value LIKE '%page/1%']"). Extracting into the same viewname repeatedly is idempotent with respect to results.

Because SCO tables are deduplicated, an extract that references the same underlying SCO from many observations returns each distinct SCO once. Re-running the identical extract yields the same result set.

Values, columns, counts

  • store.values(path, viewname) — returns a list of the values of the given property path (which may be a bare property like 'value', a dotted path like 'src_ref.value', or a fully qualified 'type:path' like 'user-account:account_login') for the rows of viewname. Because of deduplication, distinct SCOs each contribute once.
  • store.columns(viewname) — returns the column names of a table/view (never including type or spec_version).
  • store.types() — returns the set/list of SCO type names present.
  • store.count(viewname) — returns the number of rows in the view.
  • store.schema(viewname) — returns a list of column descriptors, each a dict with at least a 'name' key. Must not include type.

Lookup

store.lookup(viewname, cols=None, limit=None, offset=None)

Task Specification: Normalized STIX Storage for firepit

Overview

You are implementing a normalized relational storage layer for STIX 2.0 and 2.1 observation data in the firepit library. The core change: each STIX SCO (STIX Cyber Observable) type is stored in its own table containing only that object's own properties. Relationships between objects (references) are tracked separately, and reference-following is done via SQL joins at query time. Duplicate observables are deduplicated (merged), rather than stored once per observation.

This spec describes the exact behavior required. Where behavior was previously "one row per observation," it is now "one row per unique observable."

Data Model Requirements

Per-type tables, own properties only

Each SCO type gets a table named after the type (e.g. "ipv4-addr", "network-traffic", "user-account", "process", "url", "x-oca-event"). These tables:

  • Do NOT contain a type column.
  • Do NOT contain a spec_version column.
  • Do NOT contain a number_observed column.
  • Contain an id column and the object's own scalar properties.
  • Store reference properties (e.g. src_ref, dst_ref, process_ref, binary_ref, parent_directory_ref, host_ref, network_ref, parent_ref) as a plain column holding the referenced object's id — named exactly by the reference property (e.g. column src_ref, process_ref), not a dotted/expanded form like process_ref.id.

Even though tables lack a type column, row dicts returned from lookup for a loaded view include a 'type' key giving the SCO type (see Deduplication behavior below — a loaded ipv4-addr row has row['type'] == 'ipv4-addr').

Deduplication / merging of observables

Identical observables appearing in multiple observations are stored as a single row. When two loaded objects share the same identity (same id) but carry different property sets:

  • The union of all properties is retained (a property present in either input appears in the stored row).
  • When both inputs specify the same property with different values, the first-seen value wins. Concretely, loading [{"value":"10.0.0.1"}, {"value":"10.0.0.1","x_extra":1}] yields one row with x_extra == 1; loading [{"value":"10.0.0.1","x_extra":99}, {"value":"10.0.0.1"}] yields one row with x_extra == 99.
  • The stored table must evolve to add new columns (e.g. x_extra) as needed when later objects introduce properties not yet present.

Because of deduplication, counts of distinct observables differ from counts of observations. For the primary test bundle: there are 10 unique ipv4-addr values (though 200 total observations), 14 unique user-account logins (though 100 total observations), 70 distinct ipv4-addr observable rows, and 31 distinct url observable rows.

The __contains relationship table

A table named __contains records which observable ids are contained by which observations, with columns including source_ref (the observation) and target_ref (the contained observable). This table must be indexed.

Observation ranking (x_firepit_rank)

Within a single observation, when the same SCO type appears multiple times (e.g. multiple ipv4-addr for a network-traffic's src/dst), firepit marks the most significant instance. This mark is stored as an integer column x_firepit_rank on the __contains table (NOT on the SCO table, and NOT named x_root). The primary/most-significant instance has a non-NULL x_firepit_rank.

This must be queryable as, e.g.:

SELECT value FROM "ipv4-addr" i
  JOIN __contains c ON i.id = c.target_ref
  WHERE c."x_firepit_rank" IS NOT NULL

For an observation containing three ipv4-addrs where one is the "primary" host asset, exactly one row has non-NULL rank.

Task Specification: Normalized STIX Storage for firepit

Overview

firepit is a library that ingests STIX 2.0/2.1 observation bundles into a SQL database and exposes an API for querying the stored SCOs (STIX Cyber Observable objects). This task requires converting the storage layer to a normalized database design and providing several new/changed public APIs.

The key architectural change: STIX objects (SCOs) are stored in per-type tables where reference properties (e.g. src_ref, dst_ref, process_ref) are stored as raw ID values rather than as flattened dotted columns like src_ref.value. Relationships between observations and the SCOs they contain, and reflist relationships, are tracked in dedicated relationship tables. Dotted paths (e.g. src_ref.value) are resolved at query time via SQL joins, not stored as columns.

Two SQL backends must be supported (SQLite and PostgreSQL). A helper get_storage(dbname, session) returns a storage object appropriate to the connection string.

Normalized storage behavior

Per-type tables, no type/spec_version columns
  • Each SCO type is stored in its own table. The stored table must not contain a type column nor a spec_version column. (These are implied by the table itself.)
  • lookup results, however, must include a synthesized type key equal to the SCO type string for each returned row (e.g. every row from an ipv4-addr view has row['type'] == 'ipv4-addr').
Reference properties are raw IDs
  • A reference property such as process_ref, src_ref, dst_ref, parent_ref is stored as a single column holding the referenced object's ID. The column is named exactly the ref property (e.g. process_ref), not a dotted/flattened name like process_ref.id. So columns('events') for an x-oca-event view contains 'process_ref' and not 'process_ref.id'.
Dotted paths resolved via joins
  • When a caller references a dotted path like src_ref.value, dst_ref.value, or parent_ref.pid, the storage must resolve it by joining to the referenced object's table and selecting the target column, aliasing the result column back to the original dotted path name.
  • lookup with default columns for a network-traffic view returns rows that include keys src_ref.value and dst_ref.value (the joined address values). Both IPv4 and IPv6 addresses must resolve correctly (a network-traffic may reference ipv4-addr or ipv6-addr objects).
  • lookup for a process view returns rows including parent_ref.pid.
  • values('src_ref.value', view) returns distinct joined address values.
Relationship tables
  • A __contains table records which SCOs are contained by which observed-data, and carries a per-observation "primary/rank" marker column named x_firepit_rank (integer type). Among multiple SCOs of the same type within a single observation, exactly one is marked as primary (rank set); the others are not. Example: for a single observation with three ipv4-addr objects (two of which are the src/dst of a network-traffic, one being an event host/nat address), exactly one ipv4-addr row is the primary. A join like:
    SELECT value FROM "ipv4-addr" i JOIN __contains c ON i.id = c.target_ref WHERE c."x_firepit_rank" IS NOT NULL
    returns exactly one row.
  • A __reflist table records list-valued references (reflists) with columns including source_ref and target_ref, used to resolve paths through *-style list refs (e.g. email-message:to_refs[*].value).
Deterministic IDs & dedup
  • Duplicate observed-data objects (e.g. the same object appearing in multiple bundles) must be de-duplicated so they are stored once.
  • STIX 2.1 objects already carry their own IDs. STIX 2.0 SCOs receive deterministically-generated IDs (see stix21.makeid).

Load semantics (load)

load(viewname, objects, sco_type='ipv4-addr') ingests a list of SCO dicts that share an ID (same identifying value) but may have differing/evolving property sets. All such records collapse into a single stored row. When the same logical object appears multiple times with different columns present:

  • The row is merged into one.
  • The first non-null value encountered for each property wins (i.e., a later record does not overwrite an already-set value, and a missing property in one record does not erase a value supplied by another).

Concretely, loading [{"value":"10.0.0.1"}, {"value":"10.0.0.1","x_extra":1}] yields a single row with x_extra == 1. Loading [{"value":"10.0.0.1","x_extra":99}, {"value":"10.0.0.1"}] yields a single row with x_extra == 99. In both cases lookup returns one row with type == 'ipv4-addr', value == '10.0.0.1', plus the x_extra value. load returns the string 'ipv4-addr'.

Reassign semantics (reassign)

reassign(viewname, objects) writes back a list of object dicts previously obtained (e.g. via lookup) into the underlying normalized tables. Enrichments applied to dotted reference paths must propagate to the referenced object's table.

Specifically, if network-traffic rows are looked up and each is enriched with a new attribute on a referenced object (e.g. conn['dst_ref.x_enrich'] = 1), then after reassign, the referenced ipv4-addr objects gain the x_enrich column with the assigned value. A separate view (dests) extracted for those same referenced addresses must, upon lookup, show the x_enrich attribute present, with the enriched value applied to the addresses that were referenced (e.g. every 10.* dest has x_enrich == 1). Reassign must correctly split out and update referenced objects rather than treating dotted-path columns as literal columns on the source table.

Reassigning a grouped view preserves the row count.

The following classes exist and can be imported from the same module:

A Predicate supports:

  • .render(placeholder) — returns the SQL text for the predicate, where placeholder is the parameter placeholder string (e.g. '?').
  • .values — a tuple of the parameter values bound to the placeholders, in left-to-right order.

Required Behavior

Predicate(lhs, op, rhs) must additionally support the following two forms.

1. Compound predicates (logical composition)

When lhs and rhs are themselves Predicate instances and op is a logical operator string such as 'AND' or 'OR', the predicate combines the two sub-predicates.

  • render(placeholder) must produce the two rendered sub-predicates joined by the operator, with the whole expression parenthesized and each operand parenthesized:

    (<lhs_rendered> <OP> <rhs_rendered>)

    Example: for Predicate(Predicate('foo', '>', 5), 'AND', Predicate('bar', 'LIKE', 'baz%')), rendering with placeholder '?' yields:

    (("foo" > ?) AND ("bar" LIKE ?))

  • .values must be the concatenation of the left sub-predicate's values followed by the right sub-predicate's values, in that order. For the example above: (5, "baz%").

2. Subquery right-hand side

When rhs is a Query instance (typically with an operator such as 'IN'), the predicate compares the left-hand column against a rendered subquery.

  • render(placeholder) must render the column name (quoted with double quotes), the operator, and the parenthesized subquery SQL:

    ("col" OP (<subquery_sql>))

    Example: for

    Predicate('bar', 'IN', Query([Table('my_table'), Filter([Predicate('blah', '=', 0)]), Projection(['blah'])]))
