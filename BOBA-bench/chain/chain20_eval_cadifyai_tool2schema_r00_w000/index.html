Task Specification: gpt2schema Package

Overview

Implement a Python package named gpt2schema that exposes a decorator GPTEnabled. This decorator wraps a Python function and automatically generates an OpenAI-style function-calling JSON schema derived from the function's name, docstring, parameter annotations, and default values.

Public API

The package must be importable as gpt2schema and expose:

from gpt2schema import GPTEnabled
GPTEnabled

GPTEnabled must be usable in two forms:

  1. Bare decorator (no parentheses):

    @GPTEnabled
def function(...): ...

  2. Decorator with keyword arguments:

    @GPTEnabled(tags=["test"])
def function(...): ...
    • The only keyword argument exercised is tags, which takes a list.

In both cases, the result of decorating a function must be an object that:

  • Remains callable and, when called, invokes the original function with the same arguments and returns its return value unchanged.
  • Exposes an attribute schema (see below).
  • Exposes an attribute tags, which is a list.
    • When decorated bare (no tags given), tags must equal [].
    • When decorated with tags=[...], tags must equal exactly that list.
The schema attribute

schema is an object that provides:

  • A method to_json() returning a dict in the schema format described below.
  • A method add_enum(param_name: str, values: list) that records an enum constraint for the named parameter. After calling add_enum, that parameter's entry in the generated schema must include an "enum" key with the given list of values. add_enum mutates the schema state (it need not return anything meaningful).

Schema Generation Rules

to_json() returns a dict with this top-level structure:

{
    "type": "function",
    "function": {
        "name": <function name>,
        "description": <function description>,   # see rules below
        "parameters": { ... }                    # see rules below
    }
}
Function name
  • "name" is the decorated function's __name__.
Description (from docstring)

The function's docstring follows a reStructuredText-like convention. The docstring may contain a leading free-text description followed by :param <name>: <text>; lines.

  • "description" is the leading free-text portion of the docstring (the text before any :param lines), stripped of surrounding whitespace.
  • If the function has a docstring but it contains no leading description text (only :param lines), "description" must be present and equal to the empty string "".
  • If the function has no docstring at all, the "description" key must be omitted entirely from the "function" object.
Parameters
  • If the function has no parameters, the "parameters" key must be omitted entirely from the "function" object.
  • Otherwise, "parameters" is:
    {
    "type": "object",
    "properties": { <one entry per parameter> },
    "required": [ <names of parameters with no default value> ]
}
  • "required" lists, in declaration order, the names of every parameter that does not have a default value. Parameters with defaults are excluded from "required".
Per-parameter property entries

Each parameter produces an entry keyed by its name. The entry always contains a "type" field mapped from its annotation:

Python annotation "type" value Extra behavior
int "integer" —
str "string" —
bool "boolean" —
list[X] or typing.List[X] "array" Add "items": {"type": <mapped type of X>}
list or typing.List (no element type) "array" Do not add "items"
Optional[X] / typing.Optional[X] mapped type of X Treated as the inner type (e.g. Optional[int] → "integer")

The element type inside list[...] / List[...] and the inner type of Optional[...] are mapped using the same type-to-string mapping above (e.g. an int element → "integer").

Description per parameter
  • If the docstring contains a :param <name>: <text>; entry for the parameter with non-empty text, add "description": <text> to that parameter's entry.
    • The description text is taken from between :param <name>: and the terminating ;, stripped of surrounding whitespace.
  • If there is no :param entry for that parameter, or the entry has empty text, or the function has no docstring, the parameter entry must not include a "description" key.
Default values
  • If a parameter has a default value, add "default": <value> to its entry, using the actual default value (e.g. False, [1, 2, 3], None).
  • Parameters without a default value must not include a "default" key.
Enums
  • Only parameters explicitly configured via add_enum include an "enum" key (containing the exact list passed). No parameter includes "enum" by default.

Key ordering / equality note

Comparisons are performed on dictionary equality, so key ordering within dicts does not matter. Only the presence/absence of keys and their values, as specified above, matters.

Examples of composite behavior

  • A parameter c: bool = False with docstring :param c: This is a boolean parameter; produces:
    {"type": "boolean", "description": "This is a boolean parameter", "default": False}
  • A parameter d: list[int] = [1, 2, 3] with docstring :param d: This is a list parameter; produces:
    {"type": "array", "description": "This is a list parameter", "items": {"type": "integer"}, "default": [1, 2, 3]}
  • A parameter d: Optional[int] = None with docstring :param d: This is an optional parameter; produces:
    {"type": "integer", "description": "This is an optional parameter", "default": None}

TUNE format output

When to_json(SchemaType.TUNE) is called, the returned dictionary must have this exact top-level structure:

{
    "name": <function name>,
    "description": <function description>,
    "parameters": {
        "type": "object",
        "properties": { ... per-parameter definitions ... },
        "required": [ <names of parameters without defaults> ],
    },
}

That is: the function's name and description appear as top-level keys "name" and "description", and all parameter information is nested under a single "parameters" key whose value is a JSON-Schema-style object ("type": "object", a "properties" mapping, and a "required" list).

Per-parameter definitions inside "properties" follow standard JSON-Schema conventions:

  • An integer parameter: {"type": "integer", "description": <desc>}
  • A string parameter: {"type": "string", "description": <desc>}
  • A boolean parameter with a default: {"type": "boolean", "description": <desc>, "default": <default value>}
  • A list parameter with a default: {"type": "array", "description": <desc>, "items": {"type": <element type>}, "default": <default list>}

Parameters that have no default value are listed (by name, in declaration order) in the "required" array. Parameters with a default value are omitted from "required" and carry a "default" key holding the default value.

Concrete example — for a function named "function" with description "This is a test function." and parameters:

  • a: integer, "This is a parameter", no default
  • b: string, "This is another parameter", no default
  • c: boolean, "This is a boolean parameter", default False
  • d: list of integers, "This is a list parameter", default [1, 2, 3]

to_json(SchemaType.TUNE) must return:

{
    "name": "function",
    "description": "This is a test function.",
    "parameters": {
        "type": "object",
        "properties": {
            "a": {"type": "integer", "description": "This is a parameter"},
            "b": {"type": "string", "description": "This is another parameter"},
            "c": {"type": "boolean", "description": "This is a boolean parameter", "default": False},
            "d": {
                "type": "array",
                "description": "This is a list parameter",
                "items": {"type": "integer"},
                "default": [1, 2, 3],
            },
        },
        "required": ["a", "b"],
    },
}

This structure is independent of whether the function has tags; the tags do not appear anywhere in the schema output.

Generated schema API

The object at decorated_function.schema provides the following public operations.

to_json

Despite its name, to_json returns a Python dictionary rather than a serialized JSON string. Calling it with no argument is equivalent to passing SchemaType.API.

For SchemaType.API, the dictionary has this overall shape:

{
    "type": "function",
    "function": {
        "name": "function_name",
        # optional description and parameters fields
    },
}

For SchemaType.TUNE, to_json returns only the inner function object:

{
    "name": "function_name",
    # optional description and parameters fields
}

Thus, the TUNE form has neither the outer "type": "function" field nor the outer "function" wrapper. All function descriptions, parameter definitions, defaults, required fields, and enums otherwise remain the same between the two forms.

add_enum
decorated_function.schema.add_enum(parameter_name, values)

add_enum adds an "enum" field containing values to the named parameter's property. It mutates that function's schema, returns the same schema object so calls may be chained, and affects subsequent API and TUNE output. For example:

adds "enum": ["yes", "no"] to the choice property.

Schema construction rules

Schemas are derived from the decorated function's name, signature, defaults, type annotations, and docstring.

Function name and description
  • The inner function object always contains "name", using the decorated function's name.
  • Docstring whitespace and line breaks are collapsed into single spaces.
  • If the normalized docstring contains parameter documentation beginning with :param, the function description is the stripped text before the first :param.
  • A docstring that begins with parameter documentation therefore produces "description": "".
  • If a docstring has no :param section, its entire normalized, stripped contents become the function description.
  • If the function has no docstring, the description field is omitted.

Parameter descriptions use this exact docstring convention:

:param parameter_name: Parameter description;

The space after the second colon and the terminating semicolon are significant. A matching description is copied without the semicolon into that parameter's property. Missing parameter documentation, entries such as :param name: with no description in the required format, or a missing docstring cause the parameter's description field to be omitted.

Parameters object

When the function has schema-visible parameters, the inner function object contains:

"parameters": {
    "type": "object",
    "properties": {
        # one property per parameter
    },
    # "required" is present only when non-empty
}

Properties follow signature order. A parameter named kwargs is skipped. If no schema-visible parameters remain, the entire parameters field is omitted rather than emitted with empty properties.

A parameter with no default is listed in required. A parameter with any default is not required and receives a default field containing that value, including values such as False, None, strings, and lists. If there are no required parameters, the required field is omitted.

Parameter type mapping

The following direct annotations map to schema types:

Python annotation Schema type
int integer
float number
str string
bool boolean
list or typing.List array

Both built-in generic lists such as list[int] and typing generics such as typing.List[int] are supported. A typed list receives an items object whose type is obtained from the same primitive mapping. A bare list or bare typing.List is an array but has no items field. An unsupported list element type is represented as "items": {"type": "object"}.

typing.Optional[T] uses the mapped type for T; it does not add a separate nullable schema form. For example, Optional[int] has "type": "integer", and a declared default of None is represented separately as "default": None. An unsupported Optional inner type maps to object. Required status is still determined solely by whether a default was declared.

An unannotated parameter, or a direct annotation outside the supported mapping, remains in properties but has no generated type field. Its description and default are still included when present.

  • derive the base JSON type from the literal values, such as Literal[1, 2, 3] -> "integer" and Literal["a", "b", "c"] -> "string".
enum.Enum annotations

For a parameter annotated with a subclass of enum.Enum, its property schema must:

  • use "type": "string", regardless of the members' underlying value types; and
  • contain "enum" with the member names in enum iteration/definition order:
[member.name for member in EnumClass]

The schema uses names, not underlying .value values.

If an enum-annotated parameter has a default, emit the default member's name as a string:

class Mode(enum.Enum):
    A = 1
    B = 2

@GPTEnabled
def run(count: int, mode: Mode = Mode.B):
    ...

The mode property is:

{
    "type": "string",
    "enum": ["A", "B"],
    "default": "B"
}

and mode is absent from required.

Manual enums and annotation-derived enums obey the same cross-format persistence rule: they must be present in API and TUNE output.

Docstring extraction

Schemas use reStructuredText/Sphinx-style docstrings with :param <name>: fields.

Function description
  • The function description is the free text before the first :param field.
  • Physical lines and runs of whitespace are normalized to single spaces, and surrounding whitespace is removed.
  • If a docstring exists but starts with parameter fields and has no leading free text, include "description": "" on the function object.
  • If the function has no docstring, omit the function-level description key entirely.
  • For a docstring with free text and no parameter fields, use the normalized full docstring as the function description.
Parameter descriptions
  • A parameter description comes from its matching :param <name>: field.
  • It may span multiple physical lines. Normalize those lines to a single-space-separated string and strip surrounding whitespace.
  • It continues until the next :param, :type, :return, or :rtype field.
  • A terminating semicolon is not required.
  • :type, :return, and :rtype content must not be included in a parameter description.
  • If there is no matching :param field, or the field has no non-whitespace description, omit that parameter's description key; do not emit an empty parameter description.
  • If there is no function docstring, parameter description keys are also omitted.

Runtime enum decoding

Calling a GPT-enabled object invokes the original function after converting JSON-facing enum names for enum-annotated parameters.

For every supplied enum-annotated argument:

  • if the value is a string equal to a declared member name, replace it with EnumClass[value] before invoking the original function;
  • perform this conversion whether the argument was supplied positionally, by keyword, or in a mixed call;
  • leave an already-instantiated enum member unchanged; and
  • leave values that are not declared member names unchanged, preserving ordinary direct-call behavior.

Example:

class Choice(enum.Enum):
    A = 1
    B = 2

@GPTEnabled
def choose(choice: Choice, label: str):
    return choice, label

assert choose("A", label="x")[0] is Choice.A
assert choose(choice="A", label="x")[0] is Choice.A
assert choose(Choice.A, "x")[0] is Choice.A

Only member names are the JSON representation for enum.Enum annotations; the underlying values are not substituted for names.

Namespace discovery helpers

The discovery helpers operate on a module or module-like namespace and are exported from the package root.

FindGPTEnabled(namespace) -> list[Callable]

Returns all GPT-enabled callables exposed by the namespace and excludes undecorated functions.

FindGPTEnabledByName(namespace, name) -> Optional[Callable]

Returns the GPT-enabled callable whose original function name equals name, or None when no such callable exists.

FindGPTEnabledByTag(namespace, tag) -> list[Callable]

Returns all GPT-enabled callables whose .tags list contains tag.

FindGPTEnabledSchemas(
    namespace,
    schema_type: SchemaType = SchemaType.API,
) -> list[dict]

Returns one callable.schema.to_json(schema_type) dictionary for every callable returned by FindGPTEnabled(namespace). Omitting schema_type selects API output; explicitly passing SchemaType.API has the same result, while SchemaType.TUNE selects TUNE output for every item.
