Task Specification: the gpt2schema Package

Overview

Build a Python package going by the name gpt2schema that exposes a decorator, GPTEnabled. The decorator wraps a Python function and automatically generates a JSON schema for OpenAI-style function calling, built from the function's name, docstring, parameter annotations, and default values.

Public API

It must be possible to import the package as gpt2schema, and it must expose:

from gpt2schema import GPTEnabled
GPTEnabled

It must be possible to use GPTEnabled in two forms:

  1. Bare decorator (without parentheses):

    @GPTEnabled
def function(...): ...

  2. Decorator given keyword arguments:

    @GPTEnabled(tags=["test"])
def function(...): ...
    • The sole keyword argument exercised is tags, which takes a list.

In both forms, the result of decorating a function must be an object that:

  • Remains callable and, when a call is made, invokes the original function with the same arguments and returns its return value unchanged.
  • Exposes an attribute schema (details appear below).
  • Exposes an attribute tags, whose value is a list.
    • When the decoration is bare (no tags supplied), tags must equal [].
    • When the decoration passes tags=[...], tags must equal exactly that list.
The attribute schema

schema is an object that provides:

  • A method to_json() that returns a dict in the schema format laid out below.
  • A method add_enum(param_name: str, values: list) that records an enum constraint for the parameter named in the call. After add_enum is called, the entry for that parameter in the generated schema must include an "enum" key with the list of values that was given. add_enum mutates the schema state (its return value need not be meaningful).

Schema Generation Rules

A call to to_json() returns a dict having the following top-level structure:

{
    "type": "function",
    "function": {
        "name": <function name>,
        "description": <function description>,   # see rules below
        "parameters": { ... }                    # see rules below
    }
}
The function's name
  • "name" holds the decorated function's __name__.
Description (taken from the docstring)

The docstring of the function follows a reStructuredText-like convention. It may hold a free-text description at the start, then :param <name>: <text>; lines.

  • "description" consists of the docstring's leading free-text portion — the text that comes before any :param lines — with surrounding whitespace stripped.
  • If the function has a docstring that contains no leading description text (only :param lines), "description" must be present and equal to the empty string "".
  • If the function has no docstring at all, the "description" key must be left out entirely from the "function" object.
Parameters
  • If the function has no parameters, the "parameters" key must be left out entirely from the "function" object.
  • When the function does have parameters, "parameters" is:
    {
    "type": "object",
    "properties": { <one entry per parameter> },
    "required": [ <names of parameters with no default value> ]
}
  • "required" lists the names of every parameter that does not have a default value, in declaration order. Parameters that do have defaults are excluded from "required".
Property entry per parameter

Each parameter yields an entry whose key is the parameter's name. That entry always contains a "type" field obtained by mapping its annotation:

Python annotation "type" value Additional behavior
int "integer" —
str "string" —
bool "boolean" —
list[X] or typing.List[X] "array" Add "items": {"type": <mapped type of X>}
list or typing.List (no element type) "array" Do not add "items"
Optional[X] / typing.Optional[X] mapped type of X Treated as the inner type (e.g. Optional[int] → "integer")

The same type-to-string mapping above is what maps the element type inside list[...] / List[...] and the inner type of Optional[...] (e.g. an int element → "integer").

Per-parameter description
  • If the docstring has a :param <name>: <text>; entry for the parameter and that entry's text is non-empty, add "description": <text> to the parameter's entry.
    • The description text is whatever appears between :param <name>: and the terminating ;, with surrounding whitespace stripped.
  • If the parameter lacks a :param entry, or the entry's text is empty, or the function has no docstring, the parameter's entry must not include a "description" key.
Default values
  • If a parameter comes with a default value, add "default": <value> to its entry, where the value used is the actual default (e.g. False, [1, 2, 3], None).
  • Parameters having no default value must not include a "default" key.
Enums
  • An "enum" key is present only on parameters explicitly configured via add_enum (holding the exact list passed). By default, no parameter includes "enum".

Note on key ordering / equality

Comparisons are carried out using dictionary equality, hence the order of keys inside a dict is irrelevant. What matters is only the presence/absence of keys and their values, as specified above.

Composite-behavior examples

  • A parameter c: bool = False together with docstring :param c: This is a boolean parameter; results in:
    {"type": "boolean", "description": "This is a boolean parameter", "default": False}
  • A parameter d: list[int] = [1, 2, 3] together with docstring :param d: This is a list parameter; results in:
    {"type": "array", "description": "This is a list parameter", "items": {"type": "integer"}, "default": [1, 2, 3]}
  • A parameter d: Optional[int] = None together with docstring :param d: This is an optional parameter; results in:
    {"type": "integer", "description": "This is an optional parameter", "default": None}

The SchemaType enumeration

Supply an enumeration named SchemaType that has (at least) two members:

  • SchemaType.API
  • SchemaType.TUNE

.to_json() method on the schema object

Each GPT-enabled function exposes a schema object that has a method:

schema.to_json(schema_type=<default>) -> dict
  • It accepts an optional schema_type argument, which is one of the SchemaType members.
  • When it is called with no argument, it must produce the existing/default schema representation (behavior unchanged).
  • When it is called with SchemaType.API, it must produce the API-format schema.
  • When it is called with SchemaType.TUNE, it must produce the TUNE-format schema.
Output in the TUNE format

When to_json(SchemaType.TUNE) is called, the returned dictionary must have this exact top-level structure (no top-level keys beyond the ones shown):

{
    "name": <function name>,
    "description": <function description>,
    "parameters": {
        "type": "object",
        "properties": { ... per-parameter definitions ... },
        "required": [ <names of parameters without defaults> ],
    },
}

In other words: the function's name and description appear as the top-level keys "name" and "description", and all parameter information is nested beneath a single "parameters" key whose value is a JSON-Schema-style object ("type": "object", a "properties" mapping, and a "required" list).

Inside "properties", per-parameter definitions follow standard JSON-Schema conventions:

  • For an integer parameter: {"type": "integer", "description": <desc>}
  • For a string parameter: {"type": "string", "description": <desc>}
  • For a boolean parameter that has a default: {"type": "boolean", "description": <desc>, "default": <default value>}
  • For a list parameter that has a default: {"type": "array", "description": <desc>, "items": {"type": <element type>}, "default": <default list>}

Parameters that have no default value are listed (by name, in declaration order) in the "required" array. Parameters that do have a default value are omitted from "required" and carry a "default" key holding the default value.

A concrete example — a function named "function" with the description "This is a test function." and these parameters:

  • a: integer, "This is a parameter", no default
  • b: string, "This is another parameter", no default
  • c: boolean, "This is a boolean parameter", default False
  • d: list of integers, "This is a list parameter", default [1, 2, 3]

Invoking to_json(SchemaType.TUNE) must return:

{
    "name": "function",
    "description": "This is a test function.",
    "parameters": {
        "type": "object",
        "properties": {
            "a": {"type": "integer", "description": "This is a parameter"},
            "b": {"type": "string", "description": "This is another parameter"},
            "c": {"type": "boolean", "description": "This is a boolean parameter", "default": False},
            "d": {
                "type": "array",
                "description": "This is a list parameter",
                "items": {"type": "integer"},
                "default": [1, 2, 3],
            },
        },
        "required": ["a", "b"],
    },
}

Whether or not the function has tags makes no difference to this structure; the tags do not appear anywhere in the schema output.

Task Description

Aim

The task is to provide a Python package named tool2schema. This package must convert decorated Python functions into OpenAI-compatible function schemas, and it must discover those functions and their schemas in modules. All of the decorator, schema-generation, tagging, and discovery behavior described below must be retained by the package.

Package name and top-level imports

It must be possible to import the package as tool2schema. From the package root, all of the names below must be directly importable:

from tool2schema import (
    GPTEnabled,
    FindGPTEnabled,
    FindGPTEnabledByName,
    FindGPTEnabledByTag,
    FindGPTEnabledSchemas,
    SchemaType,
)

SchemaType

SchemaType is an enum, and the members it has are the following:

  • SchemaType.API, whose value is 0
  • SchemaType.TUNE, whose value is 1

In every place where a schema type is optional, the default schema format is SchemaType.API.

Decorator: GPTEnabled

When GPTEnabled is applied to a function, that function is marked as GPT-enabled and its schema gets created. All of the forms that follow must be supported:

@GPTEnabled
def first():
    ...

@GPTEnabled()
def second():
    ...

@GPTEnabled(tags=["lookup", "public"])
def third():
    ...

The form written without parentheses — @GPTEnabled used bare — is required in particular.

A function that has been decorated must remain callable with the positional and keyword arguments it was originally given, and it must return the result that the original function produces. Its wrapped metadata, including its name and docstring, must remain available, so that discovery by name and introspection done in the ordinary way see the metadata of the original function.

Each function that has been decorated exposes the following:

  • schema: the function-schema object generated for it;
  • tags: the list supplied by way of tags=, or [] if no tags were supplied;
  • gpt_enabled(), whose return value is True;
  • has(tag), which returns whether tag occurs in tags.

On the decorated callable, tags serve as metadata; the generated schema does not receive them.

API of the generated schema

The following public operations are made available by the object found at decorated_function.schema.

to_json
decorated_function.schema.to_json(schema_type=SchemaType.API)

In spite of its name, what to_json returns is a Python dictionary rather than a serialized JSON string. Omitting the argument is equivalent to passing SchemaType.API.

When the schema type is SchemaType.API, the dictionary takes this overall shape:

{
    "type": "function",
    "function": {
        "name": "function_name",
        # optional description and parameters fields
    },
}

When the schema type is SchemaType.TUNE, the only thing to_json returns is the inner function object:

{
    "name": "function_name",
    # optional description and parameters fields
}

The TUNE form therefore lacks both the outer "type": "function" field and the outer "function" wrapper. Otherwise, all function descriptions, parameter definitions, defaults, required fields, and enums are unchanged between the two forms.

add_enum
decorated_function.schema.add_enum(parameter_name, values)

An "enum" field containing values is added by add_enum to the property belonging to the named parameter. That function's schema is mutated by it, the very same schema object is returned so that calls may be chained, and subsequent API and TUNE output is affected. As an example:

choose.schema.add_enum("choice", ["yes", "no"])

This adds "enum": ["yes", "no"] to the choice property.

How the schema is constructed

Each schema is derived from the name, signature, defaults, type annotations, and docstring belonging to the decorated function.

The function's name and description
  • The inner function object contains "name" at all times, and the name used is the decorated function's name.
  • Any whitespace and line breaks that the docstring contains are collapsed down to single spaces.
  • If parameter documentation that begins with :param is contained in the normalized docstring, the function description consists of the stripped text before the first :param.
  • So "description": "" is what results when a docstring opens with parameter documentation.
  • When there is no :param section in the docstring, the whole of its normalized, stripped contents becomes the function description.
  • The description field does not appear if the function has no docstring.

The exact docstring convention below is the one that parameter descriptions follow:

:param parameter_name: Parameter description;

Both the space after the second colon and the terminating semicolon carry significance. A description that matches is copied into the property of that parameter without the semicolon. The parameter's description field is omitted if parameter documentation is missing, if entries such as :param name: carry no description in the required format, or if the docstring is missing.

The parameters object

The inner function object contains the following whenever the function has schema-visible parameters:

"parameters": {
    "type": "object",
    "properties": {
        # one property per parameter
    },
    # "required" is present only when non-empty
}

The properties appear in the order given by the signature. A parameter going by the name kwargs is skipped. Should no schema-visible parameters remain, the whole parameters field is left out rather than being emitted with empty properties.

A parameter that has no default is listed in required. A parameter that has a default of any kind is not required, and it is given a default field containing that value, including values such as False, None, strings, and lists. The required field is omitted when there are no required parameters.

How parameter types map

The direct annotations in the table below map to schema types as follows:

Python annotation Schema type
int integer
float number
str string
bool boolean
list or typing.List array

There is support for both built-in generic lists such as list[int] and typing generics such as typing.List[int]. A typed list is given an items object, and the type for it comes from the same primitive mapping. A list that is bare, or a bare typing.List, is an array but has no items field. When the element type of a list is unsupported, the representation used is "items": {"type": "object"}.

With typing.Optional[T], the mapped type for T is what gets used; no separate nullable schema form is added by it. To illustrate, Optional[int] has "type": "integer", and a default that is declared as None gets represented separately as "default": None. An Optional inner type that is unsupported maps to object. Whether a default was declared is still the sole determinant of required status.

A parameter that has no annotation, or a direct annotation that sits outside the supported mapping, continues to appear in properties but has no generated type field. When present, its description and default are still included.

API for discovering functions in modules

A Python module is accepted by every discovery function, and the namespace of that module is inspected by it for GPT-enabled callables. Undecorated functions must not be returned.

FindGPTEnabled
FindGPTEnabled(module) -> list

Returns all callables in module that @GPTEnabled has marked. The objects given back are the decorated callables themselves. When none are present, an empty list is returned.

FindGPTEnabledByName
FindGPTEnabledByName(module, name)

Returns the GPT-enabled callable whose function name is exactly equal to name. A matching function that is undecorated does not qualify. The result is None when no GPT-enabled callable has that name.

FindGPTEnabledByTag
FindGPTEnabledByTag(module, tag) -> list

Returns all GPT-enabled callables in module for which tag is among the entries of tags. Untagged functions and functions tagged with only other values are excluded. If none match, an empty list is returned.

FindGPTEnabledSchemas
FindGPTEnabledSchemas(module, schema_type=SchemaType.API) -> list[dict]

For every callable that FindGPTEnabled(module) returns, one schema dictionary is returned, in corresponding order. Each entry is the equivalent of calling that callable's schema.to_json(schema_type).     FindGPTEnabledSchemas,
)

The package must also expose the mutable global configuration object tool2schema.CONFIG along with the reset function tool2schema._reset_config().

SchemaType

SchemaType is an enumeration that has both of these members:

  • SchemaType.API: the normal function-calling format, which is also the default format.
  • SchemaType.TUNE: the format for fine-tuning.

The GPTEnabled decorator

GPTEnabled must support every normal decorator form used below:

@GPTEnabled
def first(...):
    ...

@GPTEnabled()
def second(...):
    ...

@GPTEnabled(tags=["lookup"], ignored_parameters=["context"])
def third(...):
    ...

The decorated result must:

  • still be callable and return the underlying function's return value;
  • keep the original function name for use in schema generation and name-based discovery;
  • expose .schema, the function schema object detailed below;
  • expose .tags as a list holding the configured tags; when there are no configured tags, it is [];
  • support membership checks through .has(tag), which returns whether tag is in .tags.

Tags serve as discovery metadata and are not added to the generated schema dictionary.

Ignored parameters and configuration

GPTEnabled accepts ignored_parameters, which is a list of parameter-name strings. In every schema format, every listed parameter is omitted from both properties and required. Ignoring a parameter affects schema exposure only; the parameter is not removed from the callable's Python signature or from its invocation behavior.

When the decorator is not supplied ignored_parameters, the value is taken from tool2schema.CONFIG.ignored_parameters at decoration time. A list given to the decorator replaces the global list for that callable. The decorated callable captures the selected configuration: changing or resetting the global configuration afterwards must not retroactively change its schema, including when serialization occurs later.

In the default global configuration, the tag list is empty and CONFIG.ignored_parameters == []. Because CONFIG.ignored_parameters is mutable, callers may assign a different list before decorating functions. Calling tool2schema._reset_config() brings these package defaults back.

As an example:

import tool2schema
from tool2schema import GPTEnabled

tool2schema.CONFIG.ignored_parameters = ["context"]

@GPTEnabled
def lookup(query: str, context: str):
    ...

tool2schema._reset_config()

# lookup's schema still omits context, because its setting was captured
# when lookup was decorated.

Schema object API and serialization timing

The object reachable via .schema must expose:

to_json(schema_type: SchemaType = SchemaType.API) -> dict
add_enum(param_name: str, values: list)

Calling to_json() is equivalent to calling to_json(SchemaType.API).

Schema dictionaries are materialized at serialization time on every to_json call, rather than a stale eagerly materialized result being exposed. Every serialization must reflect the function metadata and all schema customizations registered up to that call. A dictionary returned by an earlier call may be modified by its caller without becoming the authoritative state for future serializations.

Manual enum constraints

add_enum(param_name, values) registers an explicit allowed-value list for the named parameter and returns the schema object so that calls may be chained. The property of the corresponding parameter must contain:

"enum": values

The values, and their order, must be preserved. The registration is persistent schema state: it must appear in every subsequent API and TUNE serialization, even though each dictionary is materialized separately. If add_enum is called after an earlier serialization, later serializations must be affected as well.

Manual enum registration is valid for ordinary annotations and leaves the parameter's base JSON type unchanged. For instance, adding [1, 2, 3] to an int parameter leaves the type as "integer". It is a schema constraint only and does not by itself carry out runtime value conversion.

API schema format

to_json() and to_json(SchemaType.API) return:

{
    "type": "function",
    "function": {
        "name": <original function name>,
        "description": <normalized function description>,  # when available
        "parameters": {                                    # when parameters exist
            "type": "object",
            "properties": {
                <parameter name>: <parameter schema>,
                ...
            },
            "required": [<required parameter names>]        # when non-empty
        }
    }
}

Parameter properties and the required list are ordered according to the function signature.

When a function has no schema-visible parameters, the API format leaves the parameters key out entirely. The same applies when all parameters are omitted from schema exposure. If a parameters object exists but no parameters are required, its required key is omitted.

TUNE schema format

to_json(SchemaType.TUNE) returns the function dictionary directly, with no API wrapper around it:

{
    "name": <original function name>,
    "description": <normalized function description>,  # when available
    "parameters": {
        "type": "object",
        "properties": { ... },
        "required": [ ... ]                             # when non-empty
    }
}

So, when a function has parameters, the inner content of TUNE output is the same as the API output's "function" value. Enums derived from annotations, manual add_enum constraints, ignored parameters, descriptions, defaults, item schemas, and requiredness must be identical in both formats.

TUNE has one deliberate difference in the no-parameter case: even when the function has no schema-visible parameters, it must include:

"parameters": {
    "type": "object",
    "properties": {}
}

In that case there is no required key.

Parameter schema generation

Each schema-visible parameter is keyed by its Python parameter name. Its property contains the mapped JSON type, any available parameter description, applicable item or enum metadata, and its default when a default exists.

Required parameters and defaults
  • A parameter that has no Python default is included in required.
  • A parameter that has any Python default is not included in required.
  • Every non-enum default is emitted under "default" with the actual default value, including values such as False, [1, 2, 3], and None.
  • Enum defaults use the enum member's name, as described in the enum section below.
  • Ignored parameters are missing from both properties and required.
  • If none of the included parameters is required, omit the required key instead of emitting an empty list.
Supported type mappings

The annotation mappings that apply are:

  • int -> "integer"
  • float -> "number"
  • str -> "string"
  • bool -> "boolean"
  • list and typing.List -> "array"

For list[X] and typing.List[X], include:

"items": {"type": <mapped JSON type of X>}

For an unsubscripted list or typing.List, omit items.

For typing.Optional[X], use the mapped JSON type of X; it must not be replaced with a union schema. Requiredness still depends solely on whether the Python signature supplies a default. As a result, d: Optional[int] = None has type "integer", contains "default": None, and is not required.

With homogeneous typing.Literal[v1, v2, ...] annotations:

  • include "enum": [v1, v2, ...] following declaration order; and
  • derive the base JSON type from the literal values, such as Literal[1, 2, 3] -> "integer" and Literal["a", "b", "c"] -> "string".
enum.Enum annotations

For a parameter whose annotation is a subclass of enum.Enum, its property schema must:

  • use "type": "string", no matter the underlying value types of the members; and
  • contain "enum" holding the member names in enum iteration/definition order:
[member.name for member in EnumClass]

The schema uses names, not the underlying .value values.

When an enum-annotated parameter has a default, emit the name of the default member as a string:

class Mode(enum.Enum):
    A = 1
    B = 2

@GPTEnabled
def run(count: int, mode: Mode = Mode.B):
    ...

The mode property is:

{
    "type": "string",
    "enum": ["A", "B"],
    "default": "B"
}

and mode is absent from required.

Manual enums and enums derived from annotations follow the same cross-format persistence rule: they must be present in API and TUNE output.

Docstring extraction

Schemas use reStructuredText/Sphinx-style docstrings that contain :param <name>: fields.

Function description
  • The function description is the free text that comes before the first :param field.
  • Physical lines and runs of whitespace are normalized to single spaces, and whitespace at the edges is removed.
  • If a docstring exists but begins with parameter fields and has no leading free text, include "description": "" on the function object.
  • If the function has no docstring, the function-level description key is omitted entirely.
  • When a docstring has free text and no parameter fields, use the normalized full docstring as the function description.
Parameter descriptions
  • A parameter's description is taken from the :param <name>: field that matches it.
  • It may span multiple physical lines. Those lines are normalized into a single-space-separated string, and surrounding whitespace is stripped.
  • It carries on until the next :param, :type, :return, or :rtype field.
  • A semicolon at the end is not required.
  • Content from :type, :return, and :rtype must not be included in a parameter description.
  • If there is no matching :param field, or the field has no non-whitespace description, omit the description key for that parameter; do not emit an empty parameter description.
  • When the function has no docstring, parameter description keys are omitted as well.

Runtime enum decoding

When a GPT-enabled object is called, the original function is invoked after JSON-facing enum names have been converted for enum-annotated parameters.

For every enum-annotated argument that is supplied:

  • if the value is a string equal to a declared member name, replace it with EnumClass[value] before the original function is invoked;
  • carry out this conversion whether the argument was supplied positionally, by keyword, or in a mixed call;
  • leave an already-instantiated enum member unchanged; and
  • leave values that are not declared member names unchanged, so that ordinary direct-call behavior is preserved.

Example:

class Choice(enum.Enum):
    A = 1
    B = 2

@GPTEnabled
def choose(choice: Choice, label: str):
    return choice, label

assert choose("A", label="x")[0] is Choice.A
assert choose(choice="A", label="x")[0] is Choice.A
assert choose(Choice.A, "x")[0] is Choice.A

For enum.Enum annotations, only member names constitute the JSON representation; the underlying values are not substituted for names.

Namespace discovery helpers

The discovery helpers operate on a module or module-like namespace, and they are exported from the package root.

FindGPTEnabled(namespace) -> list[Callable]

Returns all GPT-enabled callables that the namespace exposes, and excludes undecorated functions.

FindGPTEnabledByName(namespace, name) -> Optional[Callable]

Returns the GPT-enabled callable whose original function name equals name, or None when there is no such callable.

FindGPTEnabledByTag(namespace, tag) -> list[Callable]

Returns all GPT-enabled callables that have tag in their .tags list.

FindGPTEnabledSchemas(
    namespace,
    schema_type: SchemaType = SchemaType.API,
) -> list[dict]

Returns one callable.schema.to_json(schema_type) dictionary for every callable that FindGPTEnabled(namespace) returns. Omitting schema_type selects API output; passing SchemaType.API explicitly has the same result, while SchemaType.TUNE selects TUNE output for every item.
