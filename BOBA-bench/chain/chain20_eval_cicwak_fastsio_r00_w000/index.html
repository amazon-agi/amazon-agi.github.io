02 You are modifying the connection-handling logic in a Socket.IO server implementation. 473 words · source specification

Overview

You are modifying the connection-handling logic in a Socket.IO server implementation. The change concerns how the server manages connection registration when a connect event handler rejects a connection (i.e., the handler returns a value indicating the connection should be refused).

Context / API Surface

The relevant class is the server class in the socketio package (importable as socketio.Server), which uses:

  • A connection manager accessible via the server instance's manager attribute, which exposes:
    • manager.connect(sid, namespace) — registers a client session for a namespace.
    • manager.disconnect(sid, namespace) — removes a client session from a namespace.
  • An Engine.IO layer accessible via the eio attribute, which exposes eio.send(sid, packet, binary=False).
  • A handler registration method on(event, handler, namespace=...) used to register event handlers such as connect.
  • The internal entry points that drive connection processing:
    • _handle_eio_connect(sid, environ) — invoked when a low-level Engine.IO connection is established.
    • _handle_eio_message(sid, data) — invoked when a Socket.IO packet arrives.

Required Behavior

When a connect event handler is invoked for a given session and namespace, and that handler rejects the connection:

  1. The connection must first be registered with the connection manager. That is, manager.connect must be called for the session/namespace as part of processing the connect handler — even in the rejection case.

  2. Because the handler rejected the connection, the session must then be removed from the connection manager for that namespace. That is, manager.disconnect must be called for the session/namespace.

  3. The server must send the appropriate rejection packet to the client via eio.send, using binary=False.

Specific cases the change must satisfy

Default namespace (/) rejection: Given a connect handler registered for the default namespace that rejects the connection, when a low-level connection is established for a session:

  • The handler is invoked once with the session id and the environ.
  • manager.connect is called exactly once.
  • manager.disconnect is called exactly once.
  • A single rejection packet '4' is sent to the session via eio.send with binary=False.

Named namespace (/foo) rejection: Given a connect handler registered for the namespace /foo that rejects the connection, when a low-level connection is established for a session and then a Socket.IO connect packet for /foo is received:

  • manager.connect is called a total of two times (once for the default-namespace connection established by the low-level connect, and once for the /foo namespace connect packet).
  • manager.disconnect is called exactly once (for the rejected /foo connection).
  • A rejection packet '4/foo' is sent to the session via eio.send with binary=False.

Summary of the change

Previously, a rejected connection did not register the session in the manager (so no corresponding disconnect occurred). The new behavior registers the connection in the manager as normal, and then, upon rejection, removes it via manager.disconnect. Non-rejection behavior (accepted connections registering via manager.connect) is unchanged.

03 Add Server Disconnect Support 463 words · source specification

Task Specification: Add Server Disconnect Support

Overview

You must add a disconnect method to the Server class located in the server module (server.Server). This method allows the server to disconnect a client, either from all namespaces the client is connected to, or from a specific namespace.

Background Context

The Server class manages Socket.IO clients over an underlying Engine.IO transport, accessible via self.eio. Clients are identified by a session ID (sid, a string). Messages are sent to clients using:

self.eio.send(sid, packet_data, binary=False)

Clients can connect to one or more Socket.IO namespaces. A client establishes a connection to a namespace by sending a connect packet. The default namespace is /. Connect packets for named namespaces are encoded as 0<namespace> (e.g. 0/foo connects to the /foo namespace).

The relevant lifecycle methods that are already present and used to set up client state include:

  • s._handle_eio_connect(sid, environ) — handles a new Engine.IO connection.
  • s._handle_eio_message(sid, data) — handles an incoming Engine.IO message (including namespace connect packets like '0/foo').

Required Behavior

Add the following method:

def disconnect(self, sid, namespace=None)
Parameters
  • sid (str): the session ID of the client to disconnect.
  • namespace (str, optional): the namespace from which to disconnect the client. Defaults to None.
Behavior

When namespace is provided (a specific namespace string, e.g. '/foo'):

  • The server must send a Socket.IO disconnect packet for that namespace only. The disconnect packet is sent via self.eio.send(sid, '1' + namespace, binary=False).
    • For example, disconnecting from /foo sends the payload '1/foo'.

When namespace is None (default):

  • The server must disconnect the client from every namespace to which that client is currently connected, sending a disconnect packet for each.
  • Each disconnect packet is sent via self.eio.send(sid, '1' + <namespace>, binary=False).
  • For a namespace such as /foo, this produces payload '1/foo'.
  • For the default namespace /, the disconnect packet payload is '1' (i.e. the / namespace produces just '1' with no namespace suffix appended).
Notes on Payload Encoding
  • A disconnect packet for a named namespace <ns> is encoded as '1' + <ns> (e.g. '1/foo').
  • A disconnect packet for the default namespace / is encoded simply as '1'.
  • All disconnect packets are sent with binary=False.
Namespace Tracking

The disconnect-all behavior (when namespace is None) requires the server to know which namespaces a given client is connected to. A client that has connected via the default connection (_handle_eio_connect) and then sent a connect packet for /foo is considered connected to both the default namespace / and /foo; a subsequent disconnect(sid) must send disconnect packets covering all of those namespaces.

You may need to ensure the server maintains the set of namespaces each client is connected to so that disconnect can iterate over them.

Overview

Allow an application to supply a custom JSON encoder/decoder object to the socketio library. The selected object must be used for Socket.IO packet serialization and deserialization and must also be supplied to the underlying Engine.IO server.

The server's existing logging option must also respect an explicitly configured level on the shared Socket.IO logger. Enabling logging on a new server must not overwrite such a level.

Required Behavior

1. socketio.packet.Packet must expose a configurable JSON object

The Packet class in socketio.packet must expose a class attribute named json. Its initial/default value must be Python's standard-library json module.

Every JSON operation performed by Packet must use the object currently held in Packet.json:

  • Packet.encode() must use Packet.json.dumps(...) to serialize packet data.
  • Decoding an encoded packet, whether through Packet(encoded_packet=...) or the existing decode operation, must use Packet.json.loads(...) to deserialize its JSON payload.
  • JSON metadata generated for packets containing binary attachments must follow the same rule. There must be no serialization or deserialization path that bypasses the configured object in favor of a direct reference to the standard json module.

The existing Socket.IO framing behavior remains unchanged. In particular, the serialized JSON text is appended after the packet type, namespace, and acknowledgement ID fields as applicable. With the default JSON module, packet JSON remains compact, using the existing comma and colon separators without added whitespace. The value returned by a custom dumps(...) is used as the serialized JSON portion of the packet, and the value returned by a custom loads(...) becomes the packet's data value.

A custom JSON object is required to expose only these two callable attributes:

  • dumps(...), which returns the text used as the encoded JSON payload.
  • loads(...), which returns the decoded packet data.

It does not need to provide the rest of the standard-library json module API.

Assigning a new value to Packet.json is a class-level, process-wide change. It affects all subsequently encoded or decoded Packet instances, including packets created or consumed by any Server. The setting remains active until it is explicitly replaced; it is not scoped to one packet or one server.

2. socketio.server.Server must accept and propagate json

The Server constructor must accept an optional json keyword argument in addition to its existing arguments and Engine.IO options.

When a custom json value is supplied:

  1. The exact supplied object must be installed as socketio.packet.Packet.json.
  2. The exact same object must be passed to the underlying engineio.Server constructor under the keyword name json.

When the caller omits json:

  • The underlying Engine.IO constructor must not receive a json keyword merely as a default added by Socket.IO.
  • Packet.json must remain unchanged. In particular, constructing a server without json must not reset an earlier custom selection back to the standard module.

Other existing Engine.IO options and their forwarding behavior must remain compatible with this new option.

3. Built-in Socket.IO logger level preservation

The existing logger constructor argument on Server must retain its supported modes:

  • A non-boolean logger value is used directly as the server's logger.
  • A boolean value selects the shared named logger returned by logging.getLogger('socketio').
  • With logger=False, the existing disabled-logging behavior remains: the built-in logger is set to logging.ERROR.
  • With logger=True, the built-in logger is set to logging.INFO only when that logger's own level is currently logging.NOTSET.

The logger=True decision must be based on the named logger's own configured level, not merely its effective level inherited from a parent or root logger. If its own level is any explicit value other than logging.NOTSET—for example logging.DEBUG, logging.WARNING, or logging.ERROR—that value must be preserved.

Because the named logger is shared, this rule also applies across repeated server construction. For example, after an application changes the shared logger's level to logging.WARNING, constructing another Server(logger=True) must leave it at logging.WARNING. If the shared logger's own level is reset to logging.NOTSET, constructing Server(logger=True) must initialize it to logging.INFO.

4. Existing packet API and protocol compatibility

The existing packet construction and encoding API must remain available, including packet_type, data, namespace, id, binary, and encoded_packet constructor arguments. Existing packet constants and framing behavior must not change. In particular:

  • socketio.packet.EVENT remains the event packet type whose string representation in an encoded packet is '2'.
  • Packet.encode() continues to return an encoded string for non-binary packets and the existing encoded-packet-plus-attachments form for binary packets.
  • Decoded data remains available through the packet's data attribute.
  • Namespace, acknowledgement ID, and binary placeholder handling continue to behave as before; only the source of JSON serialization and deserialization is made configurable.

Observable Examples

  • socketio.server.Server

    • Existing logger option, with logger=True preserving every explicitly configured level on the shared 'socketio' logger.

Overview

Update the in-memory room-management behavior of BaseManager so that leaving a room or disconnecting from a namespace produces a fully reconciled rooms structure immediately and synchronously. Removed memberships must be deleted, not retained as inactive tombstones that require a later cleanup pass.

This is a focused cleanup change. Existing connection, room, emission, callback, and integration behavior must remain compatible except for the timing and representation of room-membership removal described here.

Public API and State Model

BaseManager remains instantiable without arguments:

bm = BaseManager()

It maintains the public nested mapping:

rooms[namespace][room_name][sid] = <truthy value>
  • namespace is a namespace string such as '/' or '/foo'.
  • room_name is a room identifier or None.
  • sid is a client session identifier.
  • The None room contains all clients connected to that namespace.
  • Connecting a client also implicitly creates membership in a room whose name is that client's sid.
  • Membership values for entries that remain present are truthy; examples below use True.

The relevant methods retain their existing signatures:

  • connect(sid, namespace) registers the client in the namespace and adds it to both the None room and its sid-named room.
  • enter_room(sid, namespace, room) adds the client to a room.
  • leave_room(sid, namespace, room) removes that one membership.
  • disconnect(sid, namespace) disconnects the client from that namespace.
  • is_connected(sid, namespace) reports whether the client is connected to that namespace.
  • get_participants(namespace, room) returns an iterable of the room's current participants.
  • close_room(room, namespace) removes all participants from the room.

Required Behavior

1. Eliminate deferred reconciliation

BaseManager must no longer expose or use _clean_rooms, and callers must not need any equivalent externally triggered cleanup operation. Participant enumeration must not be required to make pending removals take effect. No pending-removal queue or inactive membership tombstones may be used as the externally observable room state.

At the return of leave_room, disconnect, or close_room, rooms must already represent the completed operation.

2. Remove memberships outright and prune empty containers

For a membership that exists, leave_room(sid, namespace, room) must immediately delete the sid key from that room. It must not assign False, None, or any other inactive marker to the key.

After a membership is removed:

  1. If the room has no remaining members, remove the room key from its namespace.
  2. If the namespace then has no remaining rooms, remove the namespace key from rooms.

Leaving a room, namespace, or membership that does not exist remains a no-op and must not raise an error.

3. Disconnect all memberships in the selected namespace

disconnect(sid, namespace) must synchronously remove the client from every room in the selected namespace, including:

  • the namespace's None room;
  • the client's sid-named room; and
  • every custom room joined by that client.

  • the disconnected sid is not a key in any room of that namespace;
  • is_connected(sid, namespace) reports False while that namespace still exists; and
  • participant enumeration cannot return the disconnected sid.

Existing acknowledgement-callback cleanup remains namespace-scoped: callback registrations for the disconnected namespace are removed, while registrations associated with other namespaces remain until those namespaces are disconnected.

A disconnect is strictly scoped to the namespace argument. Those memberships remain until the session separately leaves or disconnects from those namespaces.

Consequently, a client can be disconnected from '/foo' and remain connected to '/', or vice versa.

5. Preserve room-operation compatibility

Immediate deletion must not break operations that enumerate participants. close_room must still remove every participant from a valid room and remove the resulting empty room synchronously; closing a missing room remains a no-op. Emission and participant queries must operate only on memberships that are present at the time of the operation and must not expose stale, falsy entries.

Dictionary membership values are shown as True.
