Task Description

Implement functionality for retrieving the list of rooms a client is currently a member of, at both the manager level and the server level.

1. Manager: the get_rooms method

Add a method to the base manager class — the class that serves as the default client manager, instantiable and testable through the manager used in the codebase's base manager tests — with the following signature:

def get_rooms(self, sid, namespace):
Behavior

When called with a client session id (sid) and a namespace, the method returns the collection of rooms that the client belongs to within that namespace.

Some context relevant to room membership:

  • A client can be connected to a namespace (using the manager's connect(sid, namespace) method).
  • A client can be added to a named room within a namespace (using the manager's enter_room(sid, namespace, room) method).
  • As a convention, when a client connects, it is automatically placed in a room whose name equals its own sid.

Consequently, for a client that has connected to a namespace and then entered an additional named room, the collection returned by get_rooms must contain both:

  • the room whose name equals the client's sid, and
  • the additional named room that the client entered.

The value that is returned must support len() and membership testing (in), and it must contain each of the client's rooms as elements. For a client that connected and entered one additional room, the collection that is returned has length 2.

2. Server: the rooms method

Add a method with the following signature to the Server class in the server module:

def rooms(self, sid, namespace=None):
Behavior

The method returns the rooms that a given client (sid) is in for the specified namespace, and it does so by delegating to the manager's get_rooms method.

  • When namespace is not provided (that is, when its value is None), it defaults to '/'.
  • The method must call self.manager.get_rooms(sid, namespace), with the resolved namespace passed in (the value that was provided, or '/' when none was given), and must return its result.

Examples illustrating the delegation contract:

  • A call to rooms('123', namespace='/foo') results in a call get_rooms('123', '/foo').
  • A call to rooms('123') results in a call get_rooms('123', '/').
02 The task is to modify the connection-handling logic of a Socket.IO server implementation. 517 words · source specification, reworded by GLM-5.3-Flash

Specification of the Task

Overview

The task is to modify the connection-handling logic of a Socket.IO server implementation. The change deals with the way the server handles connection registration when a connect event handler rejects a connection (that is, the handler returns a value indicating the connection should be refused).

Context and API Surface

The class of interest is the server class in the socketio package (which can be imported as socketio.Server), and it makes use of:

  • A connection manager reachable through the server instance's manager attribute, which exposes:
    • manager.connect(sid, namespace) — registers a client session for a namespace.
    • manager.disconnect(sid, namespace) — removes a client session from a namespace.
  • An Engine.IO layer reachable through the eio attribute, which exposes eio.send(sid, packet, binary=False).
  • A method for registering handlers, on(event, handler, namespace=...), which is used to register event handlers such as connect.
  • The internal entry points that drive the processing of connections:
    • _handle_eio_connect(sid, environ) — invoked when a low-level Engine.IO connection is established.
    • _handle_eio_message(sid, data) — invoked when a Socket.IO packet arrives.

Behavior That Is Required

Whenever a connect event handler is invoked for a particular session and namespace, and that handler rejects the connection:

  1. The connection must first be registered with the connection manager. This means manager.connect must be called for the session/namespace as part of the processing of the connect handler — even in the rejection case.

  2. Since the handler rejected the connection, the session must then be removed from the connection manager for that namespace. In other words, manager.disconnect must be called for the session/namespace.

  3. The server must send the appropriate rejection packet to the client through eio.send, with binary=False.

Specific cases that the change must satisfy

Rejection on the default namespace (/): Given a connect handler that is registered for the default namespace and rejects the connection, when a low-level connection is established for a session:

  • The handler is invoked once, with the session id and the environ.
  • manager.connect gets called exactly once.
  • manager.disconnect gets called exactly once.
  • A single rejection packet '4' is sent to the session through eio.send, with binary=False.

Rejection on the named namespace (/foo): Given a connect handler that is registered for the namespace /foo and rejects the connection, when a low-level connection is established for a session and, after that, a Socket.IO connect packet for /foo is received:

  • manager.connect is called two times in total (once for the connection in the default namespace established by the low-level connect, and once for the /foo namespace connect packet).
  • manager.disconnect gets called exactly once (for the /foo connection that was rejected).
  • A rejection packet '4/foo' is sent to the session through eio.send, with binary=False.

Change Summary

In the previous behavior, a rejected connection did not register the session in the manager (so no corresponding disconnect occurred). With the new behavior, the connection is registered in the manager as normal, and then, upon rejection, it is removed via manager.disconnect. The non-rejection behavior (accepted connections registering via manager.connect) is left unchanged.

03 Implement Server Disconnect Support 510 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Implement Server Disconnect Support

Summary

A disconnect method must be added to the Server class, which is located in the server module (server.Server). This method makes it possible for the server to disconnect a client, either from all namespaces the client is connected to, or from a specific namespace.

Context and Background

Socket.IO clients are managed by the Server class over an underlying Engine.IO transport, accessible via self.eio. A client is identified by a session ID (sid, a string). Messages are sent to clients by way of:

self.eio.send(sid, packet_data, binary=False)

A client can be connected to one or more Socket.IO namespaces. To establish a connection to a namespace, a client sends a connect packet. The namespace / is the default. For named namespaces, connect packets have the encoding 0<namespace> (e.g. 0/foo connects to the /foo namespace).

The lifecycle methods that already exist and are used to set up client state include:

  • s._handle_eio_connect(sid, environ) — processes a new Engine.IO connection.
  • s._handle_eio_message(sid, data) — processes an incoming Engine.IO message (this includes namespace connect packets like '0/foo').

Behavior Requirements

The following method is to be added:

def disconnect(self, sid, namespace=None)
Method Parameters
  • sid (str): the session ID of the client that is to be disconnected.
  • namespace (str, optional): the namespace the client is to be disconnected from. Its default value is None.
Detailed Behavior

When a namespace is supplied (a specific namespace string, for example '/foo'):

  • The server must send a Socket.IO disconnect packet that concerns that namespace only. That disconnect packet is sent via self.eio.send(sid, '1' + namespace, binary=False).
    • As an example, disconnecting from /foo sends the payload '1/foo'.

When namespace is None (the default):

  • The server must disconnect the client from every namespace that the client is currently connected to, with a disconnect packet sent for each one.
  • Each of these disconnect packets is sent through self.eio.send(sid, '1' + <namespace>, binary=False).
  • With a namespace such as /foo, this produces the payload '1/foo'.
  • When the namespace is the default /, the payload of the disconnect packet is '1' (i.e. the / namespace produces '1' on its own, with no namespace suffix appended).
Payload Encoding Notes
  • The encoding of a disconnect packet for a named namespace <ns> is '1' + <ns> (e.g. '1/foo').
  • A disconnect packet intended for the default namespace / is encoded simply as '1'.
  • All disconnect packets are sent using binary=False.
Tracking Client Namespaces

The disconnect-all behavior (the case where namespace is None) requires the server to know which namespaces a given client is connected to. A client that has connected via the default connection (_handle_eio_connect) and then sent a connect packet for /foo is regarded as connected to both the default namespace / and /foo; a subsequent disconnect(sid) must send disconnect packets covering all of those namespaces.

You may need to ensure that the server maintains the set of namespaces each client is connected to, so that disconnect can iterate over them.

04 The Socket.IO base connection manager and the server are the targets of this update 986 words · rewritten by GPT-5.6-sol, reworded by GLM-5.3-Flash

Task Description

The Socket.IO base connection manager and the server are the targets of this update; everywhere outside the contracts listed below, existing behavior must remain untouched.

1. Per-namespace connection state in BaseManager

The module that contains the definition of BaseManager gains this public method:

def is_connected(self, sid, namespace)

The Boolean that comes back must indicate whether sid is connected, at the present moment, to exactly the namespace supplied:

  • After connect(sid, namespace) establishes the connection, the method must return True.
  • False must be returned if the session never had a connection to that namespace, if the namespace does not exist, or after its connection to that namespace has been disconnected.
  • The result must react to a disconnect immediately; deferred room cleanup must not be what the result depends on.

The (sid, namespace) pair is what connection state is keyed to. One session can be connected to several namespaces at the same time, and working on a single namespace must not change that session's state in any other namespace.

Therefore, disconnect(sid, namespace) must do the following:

  • remove the session from its connection and from all of its rooms, doing so in only the namespace that was selected;
  • treat '/' as the default namespace in its own right, not as a request to disconnect every namespace;
  • leave all other sessions and namespaces in an untouched state; and
  • stay idempotent and safe when the (sid, namespace) pair is unknown, already disconnected, or otherwise inactive. An error must not be raised by such calls.

To make this concrete: after the same sid has been connected to both '/' and '/foo', cutting it off from '/' makes is_connected(sid, '/') false, whereas is_connected(sid, '/foo') continues to be true. A further disconnect, this time from '/foo', makes that one false too.

In socketio.server, the public constructor takes this form:

def __init__(self, client_manager=None, logger=False, binary=False,
             engineio_logger=False, **kwargs)

The provider of the Socket.IO client manager is what the first positional argument now carries. The Engine.IO options arrive directly, in the form of keyword arguments.

Client-manager handling
  • What client_manager holds is a manager class, a factory, or some other callable provider. If such a value is present, invoke it exactly once, handing it the newly created Server instance as its sole argument, and expose the manager it gives back as server.manager.
  • When client_manager is omitted or is None, BaseManager takes that role in identical fashion.
  • For backward compatibility, client_manager_class keeps being accepted as a keyword alias for client_manager. When it stands in for client_manager, its value must likewise be invoked exactly once — the server instance being the argument — and installed as server.manager.
  • client_manager_class is an option for Socket.IO compatibility, not one for Engine.IO: consume it, rather than forwarding it to the Engine.IO constructor. At most one of client_manager and client_manager_class should be supplied by callers.

logger decides what server.logger is, and it does so independently of Engine.IO logging:

  • Opting for logger=False (the default) brings in the standard Socket.IO logger, whose effective level is set to logging.ERROR.
  • Opting for logger=True obtains a real logger object by way of the standard logging facility, and the effective level is set to logging.INFO.
  • Any value that is not a Boolean — a logger object coming from the caller, or another custom value, for instance — is assigned directly to server.logger.
Construction and logging on the Engine.IO side

  • When engineio_logger is False, no logger entry is to be added on its behalf.
  • The Socket.IO-only arguments client_manager, client_manager_class, binary, logger, and engineio_logger must not, beyond what is described above, leak into the Engine.IO options.
  • The binary behavior that already exists is preserved, and the value selected for it is retained on the Socket.IO server.

Examples:

Server(manager_factory, binary=True, foo='bar')

In this case manager_factory(server) is invoked once, the only argument used to construct the Engine.IO server being foo='bar'.

Server(client_manager_class=manager_factory, foo='bar')

The legacy manager alias is in use here, but what is still forwarded to Engine.IO is only foo='bar'.

3. Namespace handling in Server.disconnect

This public method is kept:

def disconnect(self, sid, namespace=None)

A namespace that is missing, or that is None, stands for '/'. The disconnect must stay confined to that single namespace, once it has been normalized:

  • Whenever the session is connected to the namespace that was selected, that client must be sent exactly the Socket.IO disconnect packet for that namespace, with binary=False; then that namespace connection is removed through the manager.
  • In the default namespace's case, '1' is the encoded packet.
  • For a namespace with a name — '/foo', for instance — '1/foo' is the encoded packet.
  • Disconnect packets must not be sent for any other namespace. In particular, a disconnect of '/' must neither send named-namespace disconnect packets nor disconnect the session from those namespaces, even when the session is connected to them.
  • If the session is not connected to the namespace that was selected, do not send a disconnect packet for it. The operation must not disturb any of the namespaces the session is connected to.

Accordingly, take a session with connections to both '/' and '/foo': disconnect(sid) leaves it having received only '1', and its '/foo' connection is still there. Conversely, disconnect(sid, namespace='/foo') sends only '1/foo', and the default namespace remains as it was.

05 Support for a Custom JSON Encoder/Decoder 1136 words · rewritten by GPT-5.6-sol, reworded by GLM-5.3-Flash

Task Specification: Support for a Custom JSON Encoder/Decoder

Overview

Make it possible for an application to supply a custom JSON encoder/decoder object to the socketio library. Whichever object is selected must be used for serialization and deserialization of Socket.IO packets, and it must also be supplied to the underlying Engine.IO server.

The server's existing logging option must also honor a level that has been explicitly configured on the shared Socket.IO logger. Turning logging on for a new server must not overwrite such a level.

Required Behavior

1. socketio.packet.Packet must expose a JSON object that can be configured

The Packet class in socketio.packet must expose a class attribute called json. Its initial value, which is also its default, must be Python's standard-library json module.

Every JSON operation that Packet performs must use whatever object Packet.json currently holds:

  • To serialize packet data, Packet.encode() must use Packet.json.dumps(...).
  • If an encoded packet is decoded, whether through Packet(encoded_packet=...) or through the existing decode operation, Packet.json.loads(...) must be used to deserialize its JSON payload.
  • JSON metadata produced for packets that contain binary attachments must follow the same rule. There must not be any serialization or deserialization path that bypasses the configured object in favor of a direct reference to the standard json module.

The framing behavior already present in Socket.IO remains unchanged. Specifically, the serialized JSON text is appended after the packet type, namespace, and acknowledgement ID fields, as applicable. When the default JSON module is used, packet JSON remains compact, with the existing comma and colon separators and no whitespace added. What a custom dumps(...) returns is used as the serialized JSON portion of the packet, and what a custom loads(...) returns becomes the packet's data value.

A custom JSON object is required to expose only the following two callable attributes:

  • dumps(...), which returns the text that serves as the encoded JSON payload.
  • loads(...), which returns the packet's decoded data.

There is no need for it to provide the rest of the standard-library json module API.

Assigning a new value to Packet.json constitutes a class-level change that applies process-wide. It affects every Packet instance that is encoded or decoded subsequently, including packets that any Server creates or consumes. The setting stays active until it is explicitly replaced; it is not scoped to a single packet or a single server.

2. socketio.server.Server must accept json and propagate it

In addition to its existing arguments and Engine.IO options, the Server constructor must accept an optional json keyword argument.

When a custom json value is provided:

  1. The exact object that was supplied must be installed as socketio.packet.Packet.json.
  2. The exact same object must be passed on to the underlying engineio.Server constructor under the keyword name json.

When the caller omits json:

  • The underlying Engine.IO constructor must not receive a json keyword merely as a default that Socket.IO adds.
  • Packet.json must remain unchanged. In particular, constructing a server without json must not reset a custom selection made earlier back to the standard module.

The other existing Engine.IO options, along with their forwarding behavior, must remain compatible with this new option.

3. Preserving the built-in Socket.IO logger's level

The logger constructor argument that Server already has must retain the modes it supports:

  • A logger value that is not a boolean is used directly as the server's logger.
  • A boolean value selects the shared named logger that logging.getLogger('socketio') returns.
  • With logger=False, the existing disabled-logging behavior remains in force: the built-in logger is set to logging.ERROR.
  • With logger=True, the built-in logger is set to logging.INFO only when that logger's own level is logging.NOTSET at that moment.

The decision made for logger=True must be based on the level that has been configured on the named logger itself, not merely on its effective level as inherited from a parent or root logger. If its own level is any explicit value other than logging.NOTSET—for instance logging.DEBUG, logging.WARNING, or logging.ERROR—that value must be preserved.

Since the named logger is shared, this rule also holds across repeated construction of servers. For example, after an application sets the shared logger's level to logging.WARNING, creating another Server(logger=True) must leave it at logging.WARNING. If the shared logger's own level is reset to logging.NOTSET, then creating Server(logger=True) must initialize it to logging.INFO.

4. Compatibility with the existing packet API and protocol

The packet construction and encoding API that already exists must remain available, including the packet_type, data, namespace, id, binary, and encoded_packet constructor arguments. Existing packet constants and framing behavior must not change. Specifically:

  • socketio.packet.EVENT remains the event packet type, whose string representation within an encoded packet is '2'.
  • Packet.encode() continues to return an encoded string for non-binary packets, and for binary packets it returns the existing encoded-packet-plus-attachments form.
  • Decoded data remains available via the packet's data attribute.
  • Handling of the namespace, the acknowledgement ID, and binary placeholders continues to behave as it did before; only the source of JSON serialization and deserialization is made configurable.

Examples of Observable Behavior

Take the following custom object:

class CustomJSON(object):
    @staticmethod
    def dumps(*args, **kwargs):
        return '*** encoded ***'

    @staticmethod
    def loads(*args, **kwargs):
        return '+++ decoded +++'

Installing it through the server must configure both of the protocol layers:

from socketio import packet
from socketio import server

sio = server.Server(json=CustomJSON)
assert packet.Packet.json is CustomJSON

It must then take control of direct packet encoding and decoding:

pkt = packet.Packet(
    packet_type=packet.EVENT,
    data={'foo': 'bar'},
)
encoded = pkt.encode()
assert encoded == '2*** encoded ***'

decoded = packet.Packet(encoded_packet=encoded)
assert decoded.data == '+++ decoded +++'

The '2' at the front is the existing EVENT packet type; the remainder comes from CustomJSON.dumps(...) unchanged. During decoding, the payload portion is what CustomJSON.loads(...) receives, and its return value is retained as data.

Logger configuration must remain stable from one server instance to the next:

import logging
from socketio import server

shared_logger = logging.getLogger('socketio')
shared_logger.setLevel(logging.NOTSET)
server.Server(logger=True)
assert shared_logger.level == logging.INFO

shared_logger.setLevel(logging.WARNING)
server.Server(logger=True)
assert shared_logger.level == logging.WARNING

Summary of the API Surface

  • socketio.packet.Packet
    • Class attribute json, which initially defaults to the standard-library json module.
    • The constructor arguments that already exist, including packet_type, data, and encoded_packet.
    • The existing encode() and decode behavior, with all of the JSON work delegated to Packet.json.
    • data containing the packet payload as supplied or as decoded.
  • socketio.packet.EVENT
    • The existing event packet constant, encoded with '2' as the leading character.
  • socketio.server.Server
    • The optional json keyword, which configures Packet.json globally and is forwarded unchanged to Engine.IO.
    • The existing logger option, where logger=True preserves every explicitly configured level on the shared 'socketio' logger.

No per-instance JSON configuration is introduced: selecting a custom JSON object via either Packet.json or Server(json=...) intentionally alters the class-level setting for all packets.

1. Eliminate deferred reconciliation

_clean_rooms must no longer be exposed or used by BaseManager, and callers must not need any equivalent cleanup operation triggered externally. For an existing membership, leave_room(sid, namespace, room) must immediately delete the sid key from that room. The key must not be assigned False, None, or any other inactive marker.

  1. If no members remain in the room, remove the room key from its namespace.
  2. If no rooms then remain in the namespace, remove the namespace key from rooms.

  • the None room of that namespace;
  • the room named after the client's sid; and
  • every custom room that the client has joined.

  • the disconnected sid does not appear as a key in any room of that namespace;
  • is_connected(sid, namespace) reports False as long as that namespace still exists; and
  • the disconnected sid cannot be returned by participant enumeration.

Repeating a disconnect for a client already removed from a namespace must not fail or change the state that remains. The existing cleanup of acknowledgement callbacks remains scoped to the namespace: callback registrations for the disconnected namespace are removed, while registrations belonging to other namespaces stay in place until those namespaces are disconnected.

The effect of a disconnect is strictly limited to the namespace argument. Constraints and Non-Goals

Unrelated manager or server behavior must not be redesigned. The required change is the immediate, synchronous deletion and pruning of room memberships during leave, close, and disconnect operations, while existing APIs, callback behavior, broadcasts, and namespace isolation are preserved.

Change required

The public class BaseManager of module socketio.base_manager must support:

BaseManager()
BaseManager.get_rooms(sid, namespace)

If get_rooms(sid, namespace) is called on a manager that has just been created and there are no rooms in the requested namespace, the call must return an empty list:

manager = BaseManager()
manager.get_rooms('123', '/foo')  # returns []

Such a call must not raise KeyError when the namespace, or its room collection, does not exist.

API to Implement

The changes must be implemented in socketio.server.Server.

Lazy initialization of the client manager

Server must support being constructed with a custom manager:

Server(client_manager=manager, binary=True, **engineio_options)

Initialization of the manager must be postponed until request handling:

  • The configured manager must be initialized with the Server instance by Server.handle_request(environ, start_response).
  • Initialization takes place only once for that server, even when handle_request() is called repeatedly.
  • Making two calls such as handle_request({}, None) must lead to exactly one call to manager.initialize(server_instance).
  • The manager must remain accessible via Server.manager.
  • A manager, the default manager included, must also support explicit initialization through server.manager.initialize(server) when internal message handling is invoked without a request having been handled first.

The constructor's existing behavior must be preserved: arbitrary Engine.IO options are still forwarded appropriately, binary is retained on the Socket.IO server, and Engine.IO event handlers remain registered.

Cooperative sleep utility

Introduce:

Server.sleep(seconds)

A call to this method must delegate the supplied duration unchanged to the associated Engine.IO server:

server.eio.sleep(seconds)

As an example, server.sleep(1.23) must call server.eio.sleep(1.23) exactly once. No particular return-value behavior is required.
