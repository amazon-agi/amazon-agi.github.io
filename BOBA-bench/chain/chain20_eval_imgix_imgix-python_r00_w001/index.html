Task: Add params keyword argument and deprecate opts in URL classes

Overview

Two public classes must accept image transformation parameters via a keyword argument named params. Previously these parameters were supplied via a keyword argument named opts. The opts argument must continue to work but must be marked as deprecated.

Public API Surface

UrlHelper

Constructor:

UrlHelper(domain, path, scheme="https", sign_key=None,
          sign_with_library_version=True, include_library_param=True,
          params=None, opts=None)

(The exact set and order of the other constructor arguments is not constrained by this task beyond domain and path being the first two positional arguments; what matters is that both params and opts are accepted as keyword arguments.)

The class must be importable such that UrlHelper('my-social-network.imgix.net', '/users/1.png', ...) works, and str(helper) produces the full URL string.

Existing methods set_parameter(key, value) and delete_parameter(key) must continue to operate on the parameters supplied at construction time.

UrlBuilder

Method:

create_url(path, params=None, opts=None)

create_url must also continue to accept the parameters dictionary as a positional second argument (i.e. create_url(path, {"or": 0})), which is treated as params.

Required Behavior

params keyword argument

Both UrlHelper.__init__ and UrlBuilder.create_url must accept a params keyword argument that is a dictionary of image transformation parameters. When supplied, the resulting URL must include those parameters exactly as it previously did when they were passed via opts.

Examples of expected URL output (given a builder/helper whose domain is my-social-network.imgix.net and with library-version signing disabled):

  • params={"w": 400, "h": 300} on path /users/1.png → https://my-social-network.imgix.net/users/1.png?h=300&w=400
  • params={"or": 0} on path /users/1.png → https://my-social-network.imgix.net/users/1.png?or=0
  • params={"hello world": "interesting"} on path demo.png → parameter keys must be URL-escaped in output.
  • params={"hello_world": "/foo\"> <script>alert(\"hacked\")</script><"} on path demo.png → parameter values must be URL-escaped in output.
  • params={"txt64": u"I cannøt belîév∑ it wors! 😱"} on path ~text → base64-variant parameters (keys ending in 64) must be base64-encoded, producing: https://my-social-network.imgix.net/~text?txt64=SSBjYW5uw7h0IGJlbMOuw6l24oiRIGl0IHdvcu-jv3MhIPCfmLE

When a signing key is provided (e.g. sign_key="FOO123bar") with params={"w": 400, "h": 300} on /users/1.png:

  • https://my-social-network.imgix.net/users/1.png?h=300&w=400&s=1a4e48641614d1109c6a7af51be23d18

Parameters supplied via params at construction of UrlHelper must remain mutable through set_parameter and delete_parameter.

Both UrlHelper.__init__ and UrlBuilder.create_url must still accept an opts keyword argument. When opts is supplied, its dictionary must be used to produce the same URL output as if the same dictionary had been supplied via params.

Whenever opts is supplied (regardless of whether params is also supplied), exactly one DeprecationWarning must be emitted. The warning message must contain the substring deprecated. No warning may be emitted when only params (or the positional parameters dictionary) is used.

Precedence when both are supplied

If both params and opts are supplied, params takes precedence — the resulting URL must reflect the params values, and the opts values must be ignored. A single DeprecationWarning (as described above) must still be emitted because opts was supplied.

Example: with params={"w": 400, "h": 300} and opts={"w": 500, "h": 400} on /users/1.png → https://my-social-network.imgix.net/users/1.png?h=300&w=400

No parameters

When neither params, opts, nor a positional parameters dictionary is supplied, no DeprecationWarning is emitted and the URL is produced without transformation parameters (existing default behavior).

General Output Format

The returned string is a comma-delimited (,) list of entries. Splitting the returned string on , yields the individual entries. Each entry has the form:

<URL> <descriptor>

where <URL> and <descriptor> are separated by a single space. Splitting an entry on a space and taking index 1 yields the descriptor.

Each <URL> is built exactly as create_url(path, params_for_this_entry) would build it, using the same builder configuration (domain, sign key, include_library_param, etc.). This means when a sign_key is configured, each URL includes a signature parameter s=<md5hex>, computed as the MD5 hex digest of the string formed by concatenating the sign key, the path (including a leading /), and the query string portion of the URL (?... up to but not including the signature). The signature is the last query parameter.

There are two output formats, selected automatically based on params.

Format Selection Rules
  • DPR format is produced when the params dictionary contains a w (width) key, OR when it contains both an h (height) key and an ar (aspect ratio) key.
  • Width-pairs format is produced in all other cases — including when params is empty, when only h is provided, or when only ar is provided.
Width-Pairs Format

Produces exactly 31 entries.

Each entry's URL is built by inserting a w=<value> parameter (in addition to any parameters passed in params), and each entry's descriptor is <value>w (the width value followed by the letter w).

The 31 width values, in order, are exactly:

100, 116, 134, 156, 182, 210, 244, 282, 328, 380, 442, 512,
594, 688, 798, 926, 1074, 1246, 1446, 1678, 1946, 2258, 2618,
3038, 3524, 4088, 4742, 5500, 6380, 7400, 8192

Properties these values must satisfy (all satisfied by the list above):

  • The smallest width is 100 and the largest is 8192; every width lies within the inclusive range [100, 8192].
  • The widths are strictly increasing, and each successive width is less than 1.18× the previous width (i.e. each step increases by strictly less than 18%).

Any parameters supplied in params (e.g. h, ar) are included in each URL in addition to the generated w parameter.

DPR Format

Produces exactly 5 entries.

  • Each entry's URL is built from the same params (no per-entry width is generated). The URL is identical across all 5 entries (aside from being built once per entry with the same params).
  • The descriptors are, in order: 1x, 2x, 3x, 4x, 5x (the device pixel ratio 1 through 5, each followed by the letter x).

targets is an additive option; it must not replace or reinterpret the params slot. It should normally be supplied by keyword.

Parameters:

  • path (str): the image path, such as "/image.jpg".
  • params (dict, optional): imgix transformation parameters to include in candidate URLs. It may be supplied positionally or by keyword and defaults to an empty dictionary.
  • start (int, optional): first width for generated width-descriptor output. Defaults to 100.
  • stop (int, optional): inclusive final width for generated width-descriptor output. Defaults to 8192.
  • tol (numeric, optional): width tolerance, expressed as a percentage, that controls generated spacing. Defaults to 8.
  • disable_variable_quality (bool, optional): disables automatically selected DPR quality values when True. Defaults to False.
  • targets (list of int, optional): an explicit ordered list of widths for width-descriptor output. Defaults to None.

The return value is one str suitable for use as an HTML srcset attribute value.

Descriptor-mode selection

The contents of params continue to determine which kind of srcset is generated. Key presence, rather than the truthiness of a value, determines the mode.

  1. Generate pixel-density (x) descriptors when params contains w, or when it contains both h and ar.
  2. Generate width (w) descriptors in every other case. This includes an empty dictionary, h without ar, and ar without h.

Explicit targets and generated start/stop/tol widths apply to width-descriptor mode. They do not replace the fixed DPR candidate set when params selects pixel-density mode.

Common output and URL behavior

Each candidate consists of a fully built imgix URL, one ASCII space, and its descriptor. Candidates are joined with exactly ",\n" (a comma immediately followed by a newline). There is no leading separator and no trailing comma or newline.

Every candidate URL must retain the builder's normal externally visible URL behavior, including:

  • the configured domain and path handling;
  • HTTPS by default, or HTTP when the builder was configured with use_https=False;
  • caller-supplied transformation parameters other than fields deliberately varied for the candidates;
  • normal parameter and path escaping;
  • the ixlib parameter when include_library_param=True, and its omission when that option is False; and
  • a valid per-candidate signature when the builder has a sign_key.

When the builder uses its default HTTPS setting, has no signing key, was constructed with include_library_param=False, and receives no additional params, w is the only query parameter in width-descriptor output.

Generating a srcset must not mutate the caller's params dictionary. Synthetic w, dpr, or q values are added only to candidate URLs; unrelated parameters such as fit, h, and ar remain unchanged and appear in every applicable candidate.

Width-descriptor mode

A width candidate has this exact shape:

<url-with-w-query-parameter> <width>w

The value assigned to the URL's w parameter and the integer in the w descriptor must be the same.

Explicit targets

When targets is supplied in width-descriptor mode:

  • emit exactly one candidate for each supplied width;
  • preserve the list's order;
  • use each width unchanged as both the w query value and descriptor; and
  • do not generate additional widths from start, stop, or tol.

For example:

builder = imgix.UrlBuilder("testing.imgix.net", include_library_param=False)
builder.create_srcset(
    "/image.jpg",
    targets=[100, 200, 300, 400, 500],
)

returns exactly:

https://testing.imgix.net/image.jpg?w=100 100w,
https://testing.imgix.net/image.jpg?w=200 200w,
https://testing.imgix.net/image.jpg?w=300 300w,
https://testing.imgix.net/image.jpg?w=400 400w,
https://testing.imgix.net/image.jpg?w=500 500w

The same option can be combined with non-mode-selecting transformation parameters while retaining the positional params contract, for example:

builder.create_srcset(

    targets=[100, 200],

328, 380, 441, 512, 594, 689, 799, 927,
1075, 1247, 1446, 1678, 1946, 2257, 2619,
3038, 3524, 4087, 4741, 5500, 6380, 7401, 8192

For a custom range, widths grow geometrically. Starting at start, each next unrounded width is the previous unrounded width multiplied by:

1 + 2 * (tol / 100)

Emitted intermediate values are rounded to integer widths. The range is inclusive: the first emitted width is start, and stop is included as the final width when it has not already been reached.

  • start=713, stop=713 produces [713].
  • start=2257, stop=4087 with the default tol=8 produces [2257, 2618, 3037, 3523, 4087].

Thus, with include_library_param=False, the last case returns exactly:

https://testing.imgix.net/image.jpg?w=102 102w,
https://testing.imgix.net/image.jpg?w=104 104w,
https://testing.imgix.net/image.jpg?w=106 106w,
https://testing.imgix.net/image.jpg?w=108 108w

The existing range constraints remain in force: width bounds must be positive numeric values, start must not exceed stop, stop must not exceed 8192, and tol must be a numeric value of at least 1.

Pixel-density mode

When params contains w, or contains both h and ar, generate exactly five candidates for DPR values 1 through 5, in ascending order. Each candidate URL receives the corresponding dpr query parameter and uses the matching density descriptor:

<url-with-dpr=1> 1x,
<url-with-dpr=2> 2x,
<url-with-dpr=3> 3x,
<url-with-dpr=4> 4x,
<url-with-dpr=5> 5x

All non-generated params, including w, h, ar, and fit, must be preserved in every candidate. Supplying only h or only ar does not select this mode.

1 75
2 50

4 23

Compatibility requirements

  • Existing calls that pass a transformation dictionary as the second positional argument must continue to select descriptor mode from that dictionary.
  • Existing keyword and positional behavior for start, stop, tol, and disable_variable_quality must remain intact; adding targets must not shift those positional slots.

Overview

Implement responsive imgix URL generation through UrlBuilder. The class must remain importable as:

from imgix import UrlBuilder

It must construct ordinary imgix URLs and generate responsive srcset strings in either width-descriptor or device-pixel-ratio form.

UrlBuilder construction

UrlBuilder(domain, use_https=True, sign_key=None, include_library_param=True)
  • domain is the fully qualified imgix domain, for example "testing.imgix.net". A domain containing a scheme or path is invalid and raises ValueError.
  • use_https=True produces HTTPS URLs; setting it to False produces HTTP URLs.
  • When sign_key is supplied, every generated candidate URL is signed using the builder's existing URL-signing behavior. Each signature must account for that candidate's generated parameters.
  • When include_library_param=True, generated URLs include the library-identifying ixlib parameter. When it is False, they do not.

All examples below use HTTPS and include_library_param=False, so their basic URL form is:

https://<domain>/<path>?<query>

Candidate generation must retain the established create_url behavior for path and query escaping, Base64-variant parameters, optional signing, scheme selection, and the library parameter. Query parameter keys are emitted in alphabetically sorted order, joined with &; when signing is enabled, the generated s parameter is appended according to the existing signing contract.

create_srcset

create_srcset(self, path, params=None, widths=None,
              start=100, stop=8192, tol=0.08,
              disable_variable_quality=False)

The method returns one string. Candidate entries are joined by exactly ",\n" (a comma followed by a newline), with no trailing comma or newline.

params supplies query parameters that must be retained in every candidate unless a generated candidate parameter intentionally replaces the same key. Generating a srcset must not mutate the caller's dictionary.

Mode selection and precedence

The following precedence determines the output mode:

  1. A non-empty widths list selects explicit custom-width mode.
  2. Otherwise, fixed-size DPR mode is selected when params contains either:
    • a w key, or
    • both an h key and an ar key.
  3. All other calls use generated width-descriptor mode.

The trigger is based on key presence. Thus h alone and ar alone use width-descriptor mode, while h and ar together use DPR mode. A w key also selects DPR mode whether or not h is present.

Mode 1: Explicit custom widths

When a non-empty list of integer widths is supplied through widths, produce one candidate for each width, in the list's original order:

<URL with w=<width>> <width>w

For each candidate, the generated w value replaces any w value in the copied parameters. Explicit widths take precedence over generated start/stop/tol widths and over automatic DPR-mode inference.

For example:

builder = UrlBuilder("testing.imgix.net", include_library_param=False)
builder.create_srcset("image.jpg", widths=[144, 240, 320, 446, 640])

returns:

https://testing.imgix.net/image.jpg?w=144 144w,
https://testing.imgix.net/image.jpg?w=240 240w,
https://testing.imgix.net/image.jpg?w=320 320w,
https://testing.imgix.net/image.jpg?w=446 446w,
https://testing.imgix.net/image.jpg?w=640 640w
Mode 2: Generated width descriptors

When explicit widths are absent and the fixed-size conditions are not met, generate target widths from start through stop.

  • start is the inclusive first width and defaults to 100.
  • stop is the inclusive final width and defaults to 8192.
  • tol is a fractional relative tolerance and defaults to 0.08, meaning 8 percent.

Target widths follow these rules:

  1. Emit start first.
  2. Starting from the unrounded current value, multiply by 1 + 2 * tol for every subsequent step.
  3. Round each value emitted by the geometric sequence to the nearest integer.
  4. If the final generated value is below stop, append stop exactly, making the upper bound inclusive.
  5. If start == stop, return that one width only.

Each width becomes:

<URL with w=<width>> <width>w

With all defaults, the target widths are:

100, 116, 135, 156, 181, 210, 244, 283,
328, 380, 441, 512, 594, 689, 799, 927,
1075, 1247, 1446, 1678, 1946, 2257, 2619,
3038, 3524, 4087, 4741, 5500, 6380, 7401, 8192

Representative custom ranges are:

  • start=500, stop=2000, tol=0.08: 500, 580, 673, 780, 905, 1050, 1218, 1413, 1639, 1901, 2000.
  • start=2257, stop=4087, tol=0.08: 2257, 2618, 3037, 3523, 4087.
  • start=100, stop=384, tol=0.20: 100, 140, 196, 274, 384.
  • start=100, stop=108, tol=0.01: 100, 102, 104, 106, 108.

For example, the 100 through 384 range produces:

https://testing.imgix.net/image.jpg?w=140 140w,
https://testing.imgix.net/image.jpg?w=196 196w,
https://testing.imgix.net/image.jpg?w=274 274w,
https://testing.imgix.net/image.jpg?w=384 384w

Any original non-width parameters remain on every candidate. For example, params={"h": 100} still uses generated width descriptors, and every URL contains both h=100 and its generated w value.

Tolerance and range validation

Tolerance is expressed as a fraction, not as an integer percentage:

  • Both integer and floating-point numeric values are accepted.
  • The minimum valid tolerance is 0.01 (1 percent), represented by SRCSET_MIN_WIDTH_TOLERANCE.
  • 0.01, 0.08, and 0.20 are valid. A numeric value below 0.01 or a non-numeric value fails validation with AssertionError.
  • There is no percentage conversion or division by 100 when applying tol; the growth factor is directly 1 + 2 * tol.

The range must also be valid: start and stop are positive numeric widths, start <= stop, and stop <= 8192. Invalid values fail with AssertionError.

The public helpers in imgix.validators must follow the same contract: validate_width_tol(value) accepts numeric values at least 0.01, and validate_min_max_tol(start, stop, tol) applies both range and fractional-tolerance validation.

The module-level helper:

from imgix.urlbuilder import target_widths

uses the same defaults, validation, inclusive bounds, geometric growth, and rounding rules, and returns the target widths as a list.

Mode 3: Fixed-size DPR variants

When params contains w, or contains both h and ar, produce exactly five candidates for DPR values 1 through 5, in ascending order:

<URL with dpr=<DPR>> <DPR>x

Each URL retains the original parameters and adds or replaces dpr with the candidate's value. This includes all of the following fixed-size forms:

  • params={"w": 100}
  • params={"w": 100, "h": 100}
  • params={"h": 500, "ar": "3:2"}
Variable quality

Variable quality is enabled by default because disable_variable_quality defaults to False. Unless disabled, each DPR candidate also receives this mapped q value:

DPR Quality
1 75
2 50
3 35
4 23
5 20

If the caller supplies q in params, that explicit value takes precedence and is retained for all five DPR candidates. If disable_variable_quality=True, no mapped quality is injected; an explicit caller-supplied q is still retained like any other original parameter.

For example, this call may omit the option because variable quality is the default:

builder = UrlBuilder("testing.imgix.net", include_library_param=False)

https://testing.imgix.net/image.jpg?dpr=3&q=35&w=100 3x,
https://testing.imgix.net/image.jpg?dpr=4&q=23&w=100 4x,

  • Width- and DPR-based generation must both honor the builder's scheme, signing key, and include_library_param setting.
  • Generated query parameters must compose with existing caller parameters without mutating them.
