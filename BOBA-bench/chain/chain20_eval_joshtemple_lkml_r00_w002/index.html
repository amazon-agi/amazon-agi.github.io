Overview

Exposed API

  • The serialize_dict method accepts a single dictionary argument.

The serialize_dict method must handle two cases involving empty dictionaries:

  • Input: {}
  • Output after concatenation: {}

  • The method must yield string fragments through a generator so that joining them gives exactly the outputs specified above (no extra whitespace, newlines, or characters).

Summary

The task is to implement a serializer that turns Python dictionaries and lists into text formatted as LookML. LookML is a block-based, structured format employed in data modeling.

Public Interface

Build a serializer object (obtainable through a fixture-style factory or a class) that exposes the methods below:

serialize_dict(data, key=None)
  • Input: a dict named data, plus an optional string key.
  • Output: a generator that yields string fragments; callers join them with "".join(...) to form the complete output.
serialize_list(items, key=None)
  • Input: a list of string literals called items, together with a string key.
  • Output: a generator that yields string fragments, joined together into the complete output.
serialize(data)
  • Input: a dict named data.
  • Output: a generator whose yielded string fragments join into the complete output.

The object's exact module path and name must be importable and callable as described. Expose the serializer so that a fixture named serializer provides an instance with these three methods.

Required Behavior

Serializing a dictionary (serialize_dict)

A dictionary renders as a block delimited by braces. Behavior varies depending on whether a "name" key is present.

Formatting of scalar string values:

  • Values that count as "unquoted literals" are emitted as-is (with no quotes around them).

  • Values that count as "quoted literals" are emitted surrounded by double quotes.

    Based on the required outputs, which keys/values get quoted versus unquoted is decided as follows:

    • label → quoted (e.g. label: "Dimension Name")
    • from_field, to_field → unquoted (e.g. from_field: field_name)

    In other words, a regular key/value pair appears as key: value when the value is an unquoted literal and as key: "value" when it is a quoted literal.

The name key is treated specially:

  • If a dictionary includes a "name" key, that value serves as a label prefix on the block's opening brace instead of being rendered as a name: ... line.
  • Every other key/value pair is rendered inside the block.

Layout of a non-empty dictionary block:

  • First line: { on a line by itself (carrying the prefix <name-value> when a name key is present).
  • Every key/value pair it contains gets its own line, indented by two spaces, followed by a newline.
  • The closing } sits on its own line at the end (and no trailing newline comes after the final }).

Example — a dictionary with no name:

{
  from_field: field_name
  to_field: field_name
}

Example — a dictionary that has a name:

dimension_name {
  label: "Dimension Name"
}

Layout of an empty dictionary:

  • When there is no name key: exactly {}.
  • When a name key is present (and there are no other pairs): exactly <name-value> {} (e.g. dimension_name {}).

Dictionaries nested as values:

  • When a key's value is itself a dictionary, that value is rendered as a nested block: the child block takes the value position and produces the nested brace structure, indented appropriately inside the parent.
Serializing a list (serialize_list)

A list of string literals renders as a bracket-delimited block spanning multiple lines:

  • The block opens with [ followed by a newline.
  • Items each occupy their own line, indented by two spaces, and are separated by commas. Every item except the last has a comma after it; every item line ends with a newline.
  • The block closes with ] on its own line (no trailing newline after ]).

Item quoting follows the same rules as dictionary values and is determined by the key argument:

  • Given key="fields", the items are unquoted literals.
  • Given key="sortkeys", the items are quoted literals.

Example — unquoted items (key="fields"):

[
  dimension_one,
  dimension_two,
  dimension_three
]

Example — quoted items (key="sortkeys"):

[
  "column_one",
  "column_two",
  "column_three"
]
Serializing the top level (serialize)

serialize accepts a dictionary that describes top-level LookML structures.

Expansion of plural keys:

  • If a key is a recognized plural (e.g. "dimensions") mapping to a list of dictionaries, every element is rendered as its own top-level block, with the singularized key acting as a label prefix. Each element dict is serialized as a named/unnamed block (its name value forms the block prefix as usual), and the singular key becomes a singular: <block> prefix.
  • Any two neighboring blocks are separated by a blank line (that is, two consecutive newlines between blocks). After the final block there is no trailing newline.

Example — with input {"dimensions": [{"name": "dimension_one"}, {"name": "dimension_two"}]}:

dimension: dimension_one {}

dimension: dimension_two {}

Here dimensions maps to the singular dimension, every element becomes dimension: <block>, and blank lines separate the blocks.

Additional Notes

  • Every generator method must be joinable via "".join(...) to yield the final string.
  • At the very end of any produced output, no trailing newline should appear.

The classes in lkml.tree that matter here are:

  • SyntaxToken(value: str, prefix: str = "", suffix: str = ""), which holds a value along with optional leading and trailing trivia.
  • PairNode(key: SyntaxToken, value: SyntaxToken), which models a key: value pair. Its first constructor field is named key: building it with PairNode(key=SyntaxToken(...), value=SyntaxToken(...)) must remain supported, and so must the existing positional two-argument form. The key attribute of the result is settable.
  • PairNode.colon, a colon syntax token that is settable, whose prefix and suffix hold the whitespace before and after the colon.
  • ContainerNode, whose items attribute holds the child nodes as a tuple.
  • ListNode(type, left_bracket, items, right_bracket), covered in more detail below.

When a pair is parsed from source, the whitespace between the key and the colon, and the whitespace between the colon and the value, must be associated with the colon token. Swapping the key must therefore change only the key text, without touching that whitespace.

The required behavior:

container = lkml.load("a :\n no")
node = container.items[0]

This first item is a PairNode, and:

str(node) == "a :\n no"

node.colon.prefix is the space before the colon, and node.colon.suffix is the newline and space before the value. Replacing the key with a plain token preserves both:

node.key = SyntaxToken("b")
str(node) == "b :\n no"

When the colon prefix is removed, only the space before the colon disappears:

node.colon.prefix = ""
str(node) == "b:\n no"

4. Parsing pairs that sit inside lists

lkml.parser.Parser(stream) accepts a token sequence, and Parser.parse_list() parses a list construct, producing a ListNode. List items of the form key: value must be parsed as PairNode instances, not as standalone values.

For a token stream that represents:

sorts: [orders.customer_id: asc, orders.order_id: desc]

in which each pair is made up of a LiteralToken key, a ValueToken, optional whitespace, and a LiteralToken value, and in which the pair items are separated by CommaToken instances, parse_list() must return a node structurally equal to:

ListNode(
    type=SyntaxToken("sorts"),
    left_bracket=LeftBracket(),
    items=(
        PairNode(
            key=SyntaxToken("orders.customer_id"),
            value=SyntaxToken("asc"),
        ),
        PairNode(
            key=SyntaxToken("orders.order_id"),
            value=SyntaxToken("desc"),
        ),
    ),
    right_bracket=RightBracket(),
)

5. Parsing a list that contains only a comment

When the contents of a list are only whitespace and a comment, with no actual values, the list must parse successfully as a ListNode whose items tuple is empty.

For a token stream that represents:

drill_fields: [
  # Put some fields here
]

that is, a stream holding the list key and colon, whitespace, ListStartToken, WhitespaceToken("\n "), CommentToken("# Put some fields here"), WhitespaceToken("\n"), ListEndToken, and StreamEndToken, parse_list() must return a node structurally equal to:

ListNode(
    type=SyntaxToken("drill_fields"),
    left_bracket=LeftBracket(),
    items=tuple(),
    right_bracket=RightBracket(),
)

The comment and the inner whitespace around it do not become list items.

6. Deleting list items keeps the formatting sensible

ListNode.items can be set and holds a tuple of item nodes, such as value tokens with a value attribute or pair nodes. Assigning a new tuple to it and then converting the node to a string must produce well-formed LookML while keeping the list's existing whitespace style whenever at least one item remains. If all items are removed, the list must render with the brackets adjacent as [], with no inner whitespace.

Single spaces separating the items
node = lkml.load("name: [a, b, c]").items[0]
str(node) == "name: [a, b, c]"

node.items = tuple(item for item in node.items if item.value != "b")
str(node) == "name: [a, c]"

node.items = tuple()
str(node) == "name: []"
Leading and trailing spaces within the brackets
node = lkml.load("name: [ a, b, c ]").items[0]
str(node) == "name: [ a, b, c ]"

node.items = tuple(item for item in node.items if item.value != "b")
str(node) == "name: [ a, c ]"

node.items = tuple()
str(node) == "name: []"

The leading and trailing inner spaces are kept for as long as the list is non-empty, but they are omitted once the list is empty.

Items delimited by newlines
node = lkml.load("name: [\n  a,\n  b,\n  c\n]").items[0]
str(node) == "name: [\n  a,\n  b,\n  c\n]"

node.items = tuple(item for item in node.items if item.value != "b")
str(node) == "name: [\n  a,\n  c\n]"

node.items = tuple()
str(node) == "name: []"

The indentation and the trailing newline before the closing bracket are kept for the items that remain.

Summary of the public API

The interfaces listed below must continue to exist with the behavior described:

  • A call to lkml.load(text: str) returns a ContainerNode.
  • lkml.Lexer(text: str) exposes an index attribute, a scan_comment() that returns a CommentToken, and a scan() that returns a tuple of tokens. For direct comment scanning, index points to the first character after the #, which has already been consumed.
  • lkml.parser.Parser(stream: tuple) exposes parse_list(), which returns a ListNode for a matching list.
  • lkml.tokens exposes CommentToken, StreamStartToken, StreamEndToken, WhitespaceToken, LiteralToken, ValueToken, ListStartToken, ListEndToken, and CommaToken with the constructor forms described above.
  • lkml.tree exposes ContainerNode with items; ListNode(type, left_bracket, items, right_bracket) with settable items; PairNode(key, value) with settable key and colon; SyntaxToken(value, prefix="", suffix=""); LeftBracket(); RightBracket(); LeftCurlyBrace(); and RightCurlyBrace(). PairNode must accept key and value as constructor keywords.

Node and token equality is structural, based on the type and the values contained. Calling str(...) on a tree node serializes it as LookML source text, with the preserved trivia and the explicit empty-list normalization described above included.

Task: Make List Parsing Handle More Edge Cases

Overview

Extend how the LKML parser handles list parsing so that trivia, the contents of empty lists, and trailing-comma state are correctly preserved by lists. The change must handle ordinary literal lists, the name/value forms supported inside lists, and comments or whitespace around the closing bracket, without altering established list behavior.

Trivia is the exact concatenation of contiguous whitespace and comment text, in input order. It must remain possible to observe trivia through the prefix and suffix fields of syntax tokens.

Public API Surface

It must remain possible to import and use the following interfaces:

  • lkml.parser.Parser(stream), for which stream may be a tuple of tokens. When the token stream matches a list, Parser.parse_list() returns a ListNode, and it returns None when that is not the case.
  • Token classes that are available from lkml.tokens (typically imported as tokens):
    • LiteralToken(value, line)
    • QuotedLiteralToken(value, line)
    • ValueToken(line)
    • WhitespaceToken(text, line)
    • CommentToken(text, line)
    • ListStartToken(line)
    • ListEndToken(line)
    • CommaToken(line)
    • StreamEndToken(line)
  • The syntax-tree classes are ListNode, SyntaxToken, LeftBracket, and RightBracket. The existing support for pair nodes within lists must remain compatible.

Syntax-Tree Requirements

ListNode

ListNode must accept, as keyword arguments, the following fields, each of which is visible to parsing:

  • type: a SyntaxToken that holds the list name.
  • left_bracket: a LeftBracket.
  • items: a tuple of item nodes, and this tuple may be empty.
  • right_bracket: a RightBracket.
  • trailing_comma: a flag with boolean-like semantics that indicates whether a comma terminated the list contents immediately before any closing-bracket trivia.

trailing_comma must have a default whose value compares unequal to True. When a trailing comma is present, the value of the parsed node must compare equal to True. Fields and defaults that already exist must remain compatible, the list's colon token included.

Equality on ListNode must take its fields into account, with items, bracket trivia, and trailing_comma among them. Nodes that are otherwise identical but whose trailing-comma state differs are consequently not equal.

Syntax tokens and their trivia

A value plus leading and trailing trivia is what SyntaxToken supports, equivalent to SyntaxToken(value, prefix="", suffix=""). Trivia that is omitted or empty is represented as an empty string for comparison and rendering. LeftBracket and RightBracket share the same trivia behavior.

Token values or trivia that differ must be distinguished by equality. To illustrate, RightBracket(prefix="\n") is different from RightBracket(), and two item tokens whose suffixes differ are different.

Required parse_list() Behavior

A literal name, a value separator, optional trivia, an opening bracket, optional contents, and a closing bracket together make up a list. When parsing succeeds, a ListNode is returned, with the name and the delimiters represented by syntax-tree tokens.

Item prefixes

When trivia introduces a list item, it must be preserved as that item's prefix. This covers trivia after the opening bracket as well as trivia that introduces later items. As an example, an item token that has "\n " before it must become SyntaxToken(<value>, prefix="\n ").

List forms that are supported, and in which whitespace rather than a comma introduces an entry, must continue to parse; the whitespace doing the introducing must be attached to the entry rather than discarded. In a name/value form, a quoted literal that serves as the value associated with a preceding literal is not an additional list item.

Take a filters list token stream whose only entry starts with the literal view_name.field_one, is followed by a value separator and an associated quoted literal, and has:

  • "\n " appearing before view_name.field_one, and
  • "\n" appearing after the associated value and before ],

The result must include:

  • items == (SyntaxToken("view_name.field_one", prefix="\n "),)
  • right_bracket == RightBracket(prefix="\n")
  • no trailing comma.

This behavior must also make it possible for a filters: [...] construct with multiple comma-delimited name: "quoted value" entries to parse successfully. Pair-list behavior that already exists, for instance comma-delimited entries that have unquoted pair values and are represented as pair nodes, must remain unchanged.

Trailing commas

A trailing comma is a comma positioned after the final item and before the closing bracket. It must not produce an extra item; instead, ListNode.trailing_comma must be set to a value equal to True.

When an item is followed directly by ,], the result has:

  • items containing the item,
  • the closing bracket is RightBracket(), and
  • trailing_comma == True.

Should trivia occur between the trailing comma and ], all of that trivia must be preserved as the prefix of the closing bracket. As an example, an item whose prefix is "\n ", followed by a comma and then "\n" before ], produces:

  • items == (SyntaxToken(<value>, prefix="\n "),)
  • right_bracket == RightBracket(prefix="\n")
  • trailing_comma == True.

Lists that have no trailing comma keep the default non-True trailing-comma state.

Empty lists

A list that is closed immediately has an empty item tuple and a right bracket with no prefix:

  • items == ()
  • right_bracket == RightBracket()
  • no trailing comma.

When an otherwise empty list contains trivia between [ and ], all of that trivia must be preserved as the right bracket's prefix. To illustrate, [ ] produces items == () and RightBracket(prefix=" ").

A list whose contents are only a comment is empty too. With "\n # Put some fields here\n" as the content between its brackets, the result must have:

  • items == ()
  • right_bracket == RightBracket(prefix="\n # Put some fields here\n")
  • no trailing comma.
Trivia on the final item when there is no trailing comma

Trivia positioned immediately before ] does not in every case belong to the right bracket. Within an ordinary non-empty literal list that has no trailing comma, whitespace and comments that immediately follow the final item stay as that item's suffix. Moving them to RightBracket.prefix must not happen.

As an example, when a space, a comment, and a newline come after the final literal and before ], the final item's suffix is the concatenation of those pieces. The right bracket in the result has an empty prefix. Conceptually:

  • final item: SyntaxToken(<value>, suffix=" # This is a comment\n")
  • closing bracket: RightBracket()

Established rendering of multiline literal lists, one instance being a final item followed by a newline and then ], is preserved by this. It differs from:

  • an empty list, where every piece of inner trivia belongs to RightBracket.prefix;
  • a list that ends in a trailing comma, where trivia after that comma belongs to RightBracket.prefix; and
  • the supported associated quoted-value form described above, where trivia that follows the associated value is preserved on the right bracket.
Trivia after the closing bracket

Behavior after ] that already exists must remain unchanged. Whitespace or comment trivia that is contiguous and located after the closing bracket is preserved as RightBracket.suffix, not as its prefix and not as an item suffix.

Compatibility and Invalid Input

Behavior that already exists must continue for:

  • ordinary literal lists separated by commas;
  • lists that have no trailing commas;
  • lists that contain supported pair entries;
  • empty lists that have no inner trivia; and
  • rendering and equality of lists, based on exact syntax-token trivia.

List streams that are malformed must continue to fail cleanly by returning None; this covers an opening bracket that is missing, invalid content tokens, contents consisting only of commas, or distinct item tokens that are directly adjacent with no accepted separator. Lexer, block, pair, or serializer behavior that is unrelated should not change.
