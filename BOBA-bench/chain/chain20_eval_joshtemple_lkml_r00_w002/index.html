A dictionary is rendered as a brace-delimited block. Its behavior depends on the presence of a "name" key.

  to_field: field_name
}

  label: "Dimension Name"
}

  • Without a name key: exactly {}.
  • With a name key (and no other pairs): exactly <name-value> {} (e.g. dimension_name {}).

Nested values:

  • With key="fields" the items are unquoted literals.
  • With key="sortkeys" the items are quoted literals.

  dimension_two,
  dimension_three
]

  "column_two",
  "column_three"

Task: Improve List Parsing to Handle Additional Edge Cases

Overview

Extend list parsing in the LKML parser so that lists correctly preserve trivia, empty-list contents, and trailing-comma state. The change must handle ordinary literal lists, supported name/value forms inside lists, and comments or whitespace around the closing bracket without changing established list behavior.

Trivia means the exact concatenation, in input order, of contiguous whitespace and comment text. Trivia must remain observable through syntax-token prefix and suffix fields.

Public API Surface

The following interfaces must remain importable and usable:

  • lkml.parser.Parser(stream), where stream may be a tuple of tokens. Parser.parse_list() returns a ListNode when the token stream matches a list and returns None when it does not.
  • Token classes available from lkml.tokens (commonly imported as tokens):
    • LiteralToken(value, line)
    • QuotedLiteralToken(value, line)
    • ValueToken(line)
    • WhitespaceToken(text, line)
    • CommentToken(text, line)
    • ListStartToken(line)
    • ListEndToken(line)
    • CommaToken(line)
    • StreamEndToken(line)
  • Syntax-tree classes ListNode, SyntaxToken, LeftBracket, and RightBracket. Existing list support for pair nodes must remain compatible.

Syntax-Tree Requirements

ListNode

ListNode must accept these parsing-visible fields as keyword arguments:

  • type: a SyntaxToken containing the list name.
  • left_bracket: a LeftBracket.
  • items: a tuple of item nodes; the tuple may be empty.
  • right_bracket: a RightBracket.
  • trailing_comma: a boolean-like flag indicating whether a comma terminated the list contents immediately before any closing-bracket trivia.

trailing_comma must have a default that compares unequal to True. When a trailing comma is present, the parsed node's value must compare equal to True. Existing fields and defaults, including the list's colon token, must remain compatible.

ListNode equality must account for its fields, including items, bracket trivia, and trailing_comma. Consequently, otherwise identical nodes with different trailing-comma state are not equal.

Syntax tokens and trivia

SyntaxToken supports a value plus leading and trailing trivia, equivalent to SyntaxToken(value, prefix="", suffix=""). Omitted or empty trivia is represented as an empty string for comparison and rendering. LeftBracket and RightBracket have the same trivia behavior.

Equality must distinguish differing token values or trivia. For example, RightBracket(prefix="\n") is different from RightBracket(), and two item tokens with different suffixes are different.

Required parse_list() Behavior

A list consists of a literal name, a value separator, optional trivia, an opening bracket, optional contents, and a closing bracket. Successful parsing returns a ListNode with the name and delimiters represented by syntax-tree tokens.

Item prefixes

Trivia that introduces a list item must be preserved as that item's prefix. This includes trivia after the opening bracket and trivia introducing later items. For example, an item token preceded by "\n " must become SyntaxToken(<value>, prefix="\n ").

Supported list forms in which an entry is introduced through whitespace rather than a comma must continue to parse, with that introducing whitespace attached to the entry rather than discarded. A quoted literal serving as the value associated with a preceding literal in a name/value form is not an additional list item.

For example, given a filters list token stream whose sole entry begins with the literal view_name.field_one, is followed by a value separator and an associated quoted literal, and has:

  • "\n " before view_name.field_one, and
  • "\n" after the associated value and before ],

the result must include:

  • items == (SyntaxToken("view_name.field_one", prefix="\n "),)
  • right_bracket == RightBracket(prefix="\n")
  • no trailing comma.

This behavior must also allow a filters: [...] construct containing multiple comma-delimited name: "quoted value" entries to parse successfully. Existing pair-list behavior, such as comma-delimited entries with unquoted pair values represented as pair nodes, must remain unchanged.

Trailing commas

A comma after the final item and before the closing bracket is a trailing comma. It must not create an extra item. Instead, set ListNode.trailing_comma to a value equal to True.

For an item followed directly by ,], the result has:

  • the item in items,
  • RightBracket() as the closing bracket, and
  • trailing_comma == True.

If trivia occurs between the trailing comma and ], preserve all of that trivia as the closing bracket's prefix. For example, an item prefixed by "\n ", followed by a comma and then "\n" before ], produces:

  • items == (SyntaxToken(<value>, prefix="\n "),)
  • right_bracket == RightBracket(prefix="\n")
  • trailing_comma == True.

Lists without a trailing comma retain the default non-True trailing-comma state.

Empty lists

An immediately closed list has an empty item tuple and an unprefixed right bracket:

  • items == ()
  • right_bracket == RightBracket()
  • no trailing comma.

If an otherwise empty list contains trivia between [ and ], preserve all of it as the right bracket's prefix. For example, [ ] produces items == () and RightBracket(prefix=" ").

A comment-only list is also empty. If the content between its brackets is "\n # Put some fields here\n", the result must have:

  • items == ()
  • right_bracket == RightBracket(prefix="\n # Put some fields here\n")
  • no trailing comma.
Final-item trivia without a trailing comma

Trivia immediately before ] does not always belong to the right bracket. In an ordinary non-empty literal list with no trailing comma, whitespace and comments immediately following the final item remain that item's suffix. They must not be moved to RightBracket.prefix.

For example, if the final literal is followed by a space, a comment, and a newline before ], those pieces concatenate into the final item's suffix. The resulting right bracket has an empty prefix. Conceptually:

  • final item: SyntaxToken(<value>, suffix=" # This is a comment\n")
  • closing bracket: RightBracket()

This preserves established rendering of multiline literal lists such as a final item followed by a newline and then ]. It is distinct from:

  • an empty list, where all inner trivia belongs to RightBracket.prefix;
  • a list ending in a trailing comma, where trivia after that comma belongs to RightBracket.prefix; and
  • the supported associated quoted-value form described above, where trivia after the associated value is preserved on the right bracket.
Trivia after the closing bracket

Existing behavior after ] must remain unchanged. Contiguous whitespace or comment trivia after the closing bracket is preserved as RightBracket.suffix, not as its prefix and not as an item suffix.

Compatibility and Invalid Input

Existing behavior must continue for:

  • ordinary comma-separated literal lists;
  • lists without trailing commas;
  • lists containing supported pair entries;
  • empty lists with no inner trivia; and
  • list rendering and equality based on exact syntax-token trivia.

Malformed list streams must continue to fail cleanly by returning None, including a missing opening bracket, invalid content tokens, comma-only contents, or directly adjacent distinct item tokens with no accepted separator. No unrelated lexer, block, pair, or serializer behavior should change.
