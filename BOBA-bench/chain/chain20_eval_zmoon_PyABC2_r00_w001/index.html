02 Parsing Note Durations in ABC 462 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Parsing Note Durations in ABC

Summary

Implement or extend the note parsing functionality that turns ABC notation note strings into note objects with a well-defined string representation. This task is specifically focused on interpreting duration modifiers in ABC note strings correctly.

Public API

A module named note must be present (importable as note), exposing a class Note that provides a class method or static constructor:

Note.from_abc(abc: str) -> Note
  • from_abc accepts a single ABC-notation string that describes one note.
  • The returned Note object must produce a canonical string representation through str(note_obj) (i.e. by implementing __str__).

Format of the String Representation

The canonical string representation uses the following form:

<PitchName><Octave>_<DurationNumerator>/<DurationDenominator>

As an example, C4_1/16 stands for pitch C, octave 4, and duration 1/16.

Rules for Parsing ABC Input

An ABC note string is made up of a pitch letter followed by optional duration modifiers. A bare note has the base (default) duration 1/8.

The following duration modifiers must be supported:

  1. No modifier — for example, C → duration 1/8.

  2. Slash(es) / — each trailing slash that is not followed by a number halves the duration:

    • A lone / halves the base duration: C/ → 1/16.
    • Two slashes // apply the halving twice: C// → 1/32.

  3. Slash followed by an integer /n — the base duration is divided by n:

    • C/3 → the base 1/8 divided by 3 → 1/24.

  4. Integer followed by a slash m/ — the base duration is multiplied by m and then halved (i.e. base × m, then the halving of a single trailing slash is applied):

    • C3/ → the base 1/8 multiplied by 3 gives 3/8, and then the trailing slash halves it → 3/16. This corresponds to a dotted eighth note.

Representation of Duration Values

  • A duration is represented as an exact rational value with a numerator and denominator, rendered as numerator/denominator.
  • The examples above imply that durations remain in fractional form: 1/16, 1/32, 1/24, 3/16, and so on. In these cases the denominator is not reduced away; the representation as shown must match exactly (e.g. 3/16, not a decimal or a differently-reduced form).

Pitch and Octave

  • For the inputs covered here, the pitch letter maps directly to its name, and the octave defaults to 4. For instance, a bare C yields pitch name C and octave 4.

Concrete Examples of Behavior

ABC input str(Note.from_abc(input))
C C4_1/8
C/ C4_1/16
C// C4_1/32
C/3 C4_1/24
C3/ C4_3/16

(The C → C4_1/8 row reflects the default duration; every other row must match exactly as shown.)

03 Repeat Expansion for ABC Tunes 766 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Repeat Expansion for ABC Tunes

Overview

You must extend an ABC-notation music parser such that repeat barlines (:| and |:) and first/second endings (|1, |2, along with :|1, :|2) are expanded correctly into the linear sequence of notes that would actually be played.

Public API

It must be possible to import and use the following:

  • Tune — a class constructed from a single string argument that holds ABC notation: Tune(abc_string).
  • Instances of Tune must provide a method iter_notes() that returns an iterable of note objects, ordered as they are played (with repeats already expanded).
  • Each note object that iter_notes() yields must provide:
    • an attribute class_name — a string that names the note (e.g. a pitch letter like "G", "A").
    • a method to_abc() — returns that note's ABC-text representation (e.g. "G", "a"), with case preserved (uppercase vs lowercase pitches are distinct).

These already exist and keep working:

  • INFO_FIELDS — a mapping; INFO_FIELDS["T"].name == "tune title".

Input Format

The abc_string contains standard ABC header fields, one per line, for example:

T:?
L:1
M:4/4
R:reel
K:G

and then one or more lines of music (the body) follow. Whitespace at the start or end of a line is not significant. A note is a single letter (A–G, a–g), and notes are separated by whitespace and barline tokens.

Semantics of Barlines and Repeats

These structural tokens, separated by whitespace, appear in the music body:

  • | — an ordinary barline (it separates measures and has no effect on playback order).
  • || — a section/double barline (has no effect on playback order).
  • :| — end of a repeated section: playback returns to the most recent |: when one exists, and otherwise to the start of the music, then plays that section a second time.
  • |: — marks the start of a repeated section.
  • |1 — marks the start of a first ending (played on the first pass through the repeat).
  • |2 — marks the start of a second ending (played on the second/final pass through the repeat).
  • :|1 — a marker that ends a repeat and also begins a first ending; that is, it serves both as a repeat-end for the preceding pass and as the opening of the first ending. (In practice, the first ending's content precedes this marker; see the behavior below.)
  • :|2 — starts a second ending on the repeat pass.
Required Behavior

Repeats with no endings. A repeated section bounded by |: … :| is played twice. If a :| occurs with no preceding |:, the repeated section starts at the beginning of the music. Multiple independent repeated sections occurring in sequence are each expanded in order.

Example — given this body:

G | A :|
|: B | C :|

the notes are played in the order: G A G A B C B C.

Repeats that use first/second endings. Inside a repeated section, the notes before an ending marker are common to both passes. On the first pass, the first ending (introduced by |1 or :|1) is played, and playback then repeats back to the start of the section. On the second pass, instead the second ending (introduced by |2 or :|2) is played, and the repeat is not taken again.

For a section written in the form:

… common notes … |1 <first ending> :|2 <second ending> ||
  • Pass 1: common notes, then the first ending, then the repeat.
  • Pass 2: common notes, then the second ending, then continue.

Example — for the body:

G |1 A | A :|2 a | a ||
|: B |1 C :|2 c ||

the notes are played in the order: G A A G a a B C B c.

Walking through the two lines:

  • First section (start-of-music serves as the implicit repeat start): common note G; first ending A A; repeat back; common note G again; second ending a a. → G A A G a a.
  • Second section (the repeat starts at |:): common note B; first ending C; repeat back; common note B; second ending c. → B C B c.

Concatenated, that gives: G A A G a a B C B c.

Constraints

  • The expansion must work on note objects such that both class_name and to_abc() reflect the original notes exactly (letter case included).
  • Only the note-ordering behavior described above is required. Do not add any transformations, validation, or output other than what is specified here.

Overview

Public API

An importable Tune class must exist (available at the same import location it currently occupies, i.e. from <package> import Tune as used elsewhere in the codebase). The class must be constructible from a single string argument that contains ABC notation:

t = Tune(abc_string)

Requirements for Header Parsing

Header lines in ABC take the form <letter>: <value>, where <letter> is a single-character field identifier followed by a colon. Whitespace may occur:

  • as leading indentation appearing before the field letter,
  • immediately after the colon (optional; there may be zero or more spaces),

and it must be stripped so that the stored value contains neither the leading whitespace of the line, the field letter, the colon, nor the space(s) immediately following the colon.

The input string as a whole may carry leading/trailing whitespace, and individual header lines may be indented; that indentation must not appear in parsed values.

Example: for header lines T: hi followed by T: hii, titles must equal ["hi", "hii"].

Header fields that occur multiple times must all be retained (not overwritten), such that:

  • fields with multiple instances, like title, are fully collected into their list form (titles), and

Notes

  • Parsing must correctly handle both the <letter>: <value> (with a space) form and the <letter>:<value> (without a space) form.

Deliverable

Specification of the Task

Goal

What this task fixes is a bug in the parsing of ABC note duration modifiers, so that fractional durations written with an explicit numerator and denominator are interpreted correctly.

Background

Functionality for building note objects out of ABC notation strings already exists in the codebase. In this notation, a note is formed from a pitch letter (accidentals and octave markers being optional) and, after it, an optional duration modifier. Only the duration-modifier parsing falls within the scope of this task.

Behavior that is required

A function capable of constructing a note object out of an ABC notation string must exist. The public API that is relevant reads:

  • Module: note
  • Function: Note.from_abc(abc: str) -> Note (that is, a class Note providing a classmethod/staticmethod from_abc, which accepts one ABC string as its single argument and returns a Note instance)

The note object produced must, when run through str(), come out in this shape:

<PITCH>_<DURATION>

Here <PITCH> stands for the pitch of the note (for instance C4), while <DURATION> gives its duration written as a fraction (for instance 1/32, 3/16).

Semantics of the duration modifier

The element appearing after the pitch is the duration modifier. Take a base unit duration as the starting point (for the cases below, this base unit corresponds to a duration of 1/8); the modifier then rescales it in these ways:

  • No modifier — the duration equals the base unit, with no alteration.
  • A trailing integer n (e.g. C3) — the base unit is multiplied by n.
  • One or more slashes / with no numbers — the duration is halved by each slash. Thus one lone / halves the base unit, with // the base unit is divided by 4, and k consecutive slashes divide by 2^k in the general case.
  • /m (an integer following the slash) — the base unit gets divided by m.
  • n/m (integer, slash, integer) — the base unit is multiplied by n and then divided by m.
The bug to correct

Parsing the n/m form (an explicit numerator, a slash, and an explicit denominator) must produce the correct result: "multiply by n, divide by m". To be concrete: an input with base unit 1/8 and duration modifier 3/2, whose pitch resolves to C4, must yield the duration 3/16 — put differently, C4_3/16 is what its string representation must be.

For reference: with base unit 1/8 and a pitch that resolves to C4, the pitch/modifier combinations below must produce the string representations listed:

ABC input Expected string representation
C// C4_1/32
C/3 C4_1/24
C3/ C4_3/16
C3/2 C4_3/16

Within this table, the final row (C3/2) is the one case that must be corrected; the others must keep behaving as shown.

Restrictions

  • Alter nothing in the behavior except the duration-modifier parsing described above.
  • The cases that are currently correct must stay correct.

MODE_VALUES must be a mapping that takes abbreviated mode identifiers to integer chromatic-step deltas measured relative to Ionian mode. Keyed access, such as MODE_VALUES[mode], must be supported; a plain tuple or list does not suffice. On iteration it must yield exactly these nine identifiers, in this order:

{

    "phr": -4,
    "lyd": -5,
    "mix": -7,

So for mode-offset purposes, major and Ionian are equivalent, and minor and Aeolian are equivalent as well. Existing mode equivalence, scale, and relative-key operations must remain able to use the mapping and its integer values.

Supply a function that accepts an optional acc_format argument:

_mode_chromatic_scale_degrees(mode, acc_format=<default>)

It must be possible to call the function with only mode, in which case a valid built-in accidental-format default applies.

  • Key-signature behavior is unchanged from before. For example:

Unicode representation of PitchClass

Within pyabc2.note, add the following method to the public PitchClass API:

PitchClass.unicode(self) -> str

For pitch classes produced by:

PitchClass.from_name(name: str) -> PitchClass

the unicode() method must return the letter of the pitch followed by the corresponding Unicode accidental:

Name supplied as input Result of unicode()
"A" "A"
"Ab" "A♭"
"Abb" "A𝄫"
"A#" "A♯"
"A##" "A𝄪"
"A=" "A♮"

Double accidentals must use the single Unicode character for the double-flat (𝄫) or the double-sharp (𝄪) rather than two repeated accidental characters.
