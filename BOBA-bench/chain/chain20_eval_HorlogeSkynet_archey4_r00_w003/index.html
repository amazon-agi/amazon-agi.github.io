Task Specification: Multiple CPU Support in the CPU Entry

Overview

Modify the CPU entry so it detects and represents multiple CPUs (physical packages), each with its model name and its total number of cores. Also add a small behavioral edge case to the LanIP entry. All work must satisfy the exact public API surface and behaviors described below.

1. CPU entry — archey/entries/cpu.py

The module archey.entries.cpu must expose a class CPU. It imports open (for reading /proc/cpuinfo) and check_output (for invoking lscpu) as module-level names archey.entries.cpu.open and archey.entries.cpu.check_output.

1.1 Value representation

The value attribute produced by a CPU instance must be a list of dictionaries. Each dictionary represents one physical CPU package and maps CPU model name string → core count (int). A single dictionary may contain more than one key when (unusually) multiple distinct model names are reported for the same physical package.

Example:

[
    {'CPU-MODEL-NAME': 1},
    {'ANOTHER-CPU-MODEL': 2}
]
1.2 Static method: CPU._parse_proc_cpuinfo()

Signature: @staticmethod def _parse_proc_cpuinfo().

Reads and parses /proc/cpuinfo (via the module-level open). The file content is a set of processor blocks separated by blank lines. Each block contains key\t: value lines. Relevant fields are model name and physical id.

Behavior:

  • Group processors by their physical id. Each distinct physical id becomes one entry (one dictionary) in the returned list, in the order the physical ids first appear.
  • Within each physical-id group, count the occurrences of each model name. The resulting dictionary maps model name → number of processors with that model name in that group.
  • Model name normalization: collapse any run of whitespace characters (spaces and/or tabs) within a model name into a single space, and strip leading/trailing whitespace. For example, a raw model name ANOTHER\tCPU MODEL WITH STRANGE S P A C E S becomes ANOTHER CPU MODEL WITH STRANGE S P A C E S.
  • Return type: a list of dict[str, int].

Examples of required results:

  • Single processor block with model name: CPU-MODEL-NAME, physical id: 0:

    [{'CPU-MODEL-NAME': 1}]

  • Three processors: one CPU-MODEL-NAME on physical id 0, two ANOTHER-CPU-MODEL on physical id 1:

    [{'CPU-MODEL-NAME': 1}, {'ANOTHER-CPU-MODEL': 2}]

  • Four processors all CPU-MODEL-NAME, two on physical id 0 and two on physical id 1:

    [{'CPU-MODEL-NAME': 2}, {'CPU-MODEL-NAME': 2}]

  • Four processors where physical id 0 has one CPU-MODEL-NAME and one ANOTHER-CPU-MODEL, and physical id 1 has two of a strangely-spaced model name:

    [
    {'CPU-MODEL-NAME': 1, 'ANOTHER-CPU-MODEL': 1},
    {'ANOTHER CPU MODEL WITH STRANGE S P A C E S': 2}
]

Error/edge case: if /proc/cpuinfo cannot be read (e.g. open raises PermissionError), return an empty list.

1.3 Static method: CPU._parse_lscpu_output()

Signature: @staticmethod def _parse_lscpu_output().

Invokes lscpu (via the module-level check_output) and parses its output. lscpu output consists of Key: Value lines. The output may contain multiple CPU sections separated by a blank line; each section is one physical CPU package and yields one dictionary in the returned list, in order.

For each section, use the Model name field as the model name (normalized the same way as in _parse_proc_cpuinfo, i.e. collapse internal whitespace runs to a single space and strip). The core count for that package is computed as Core(s) per socket × Socket(s) (both integer fields from that section).

Return type: a list of dict[str, int].

Required results:

  • Single section with Core(s) per socket: 4, Socket(s): 1, Model name: CPU-MODEL-NAME:

    [{'CPU-MODEL-NAME': 4}]

  • Two sections (separated by a blank line): first Core(s) per socket: 2, Socket(s): 1, Model name: CPU-MODEL-NAME; second Core(s) per socket: 2, Socket(s): 1... wait, the second reports Core(s) per socket: 2, Socket(s): 1 with a different model — see mapping below:

    [
    {'CPU-MODEL-NAME': 2},
    {'ANOTHER-CPU-MODEL': 4}
]

    (First section: 2×1 = 2 cores. Second section: Core(s) per socket: 2 × Socket(s): 1... the second section supplies values yielding 4 cores — i.e. Core(s) per socket × Socket(s) = 4 — with model ANOTHER-CPU-MODEL.)

  • Single section with Core(s) per socket: 4, Socket(s): 2, Model name: CPU-MODEL-NAME — representing one CPU model across two sockets:

    [{'CPU-MODEL-NAME': 8}, {'CPU-MODEL-NAME': 8}]

    Note: when a single lscpu section describes Socket(s): 2 for one model, the result contains one dictionary per socket, each mapping the model name to the per-socket core count (Core(s) per socket × Socket(s)).

Clarification on core-count semantics: the value stored per model equals Core(s) per socket × Socket(s) from the section, and the section contributes one dictionary per socket (so a section with N sockets yields N identical dictionaries).

1.4 Instance method: CPU.output(self, output)

Signature: def output(self, output).

output is an object with an append(name, text) method. The entry name to use is the string 'CPU'.

The method reads:

  • self.value — the list-of-dicts described above (may also be an empty container).
  • self.options — a mapping supporting keys:
    • 'one_line' (bool): when true, all CPUs are combined into a single appended line; when false, each CPU package produces its own appended line.
    • 'show_cores' (bool): when true (default behavior), each model name is prefixed with its core count in the form N x MODEL when the count is greater than 1; when the count is exactly 1, only the model name is shown (no 1 x prefix). When false, core counts are omitted entirely and only model names are shown.

Formatting rules for a single model entry:

  • With counts shown and count == 1: MODEL
  • With counts shown and count > 1: N x MODEL
  • With counts hidden: MODEL

Combining rule when one_line is true: join every model entry across all CPU packages (each formatted per the rules above) into one comma-space (, ) separated string, and call output.append('CPU', combined_string) exactly once.

Behavior when one_line is false: for each CPU package, call output.append('CPU', text) where text is that package's formatted model entries joined by , . This produces one call per package. (Order across packages need not be guaranteed.)

No-CPU edge case: when self.value is empty (e.g. an empty dict/list), call output.append('CPU', <not_detected string>) exactly once, where the not-detected string is DEFAULT_CONFIG['default_strings']['not_detected'] from archey.constants.

Required examples, given self.value = [{'CPU-MODEL-NAME': 1}, {'ANOTHER-CPU-MODEL': 2}]:

  • one_line=True, counts shown → single call: output.append('CPU', 'CPU-MODEL-NAME, 2 x ANOTHER-CPU-MODEL')
  • one_line=True, show_cores=False → single call: output.append('CPU', 'CPU-MODEL-NAME, ANOTHER-CPU-MODEL')
  • one_line=False, show_cores=True → two calls:
    • output.append('CPU', 'CPU-MODEL-NAME')
    • output.append('CPU', '2 x ANOTHER-CPU-MODEL')

Given an empty value → single call: output.append('CPU', DEFAULT_CONFIG['default_strings']['not_detected']).

1.5 Options and configuration defaults

The CPU entry must recognize the options one_line and show_cores. These come from self.options at output time. The name provided to an entry must not be treated as a configurable option.

2. LanIP entry — archey/entries/lan_ip.py

The existing LanIP entry must handle the case where the user sets max_count to 0.

LanIP is constructed with an options mapping that may contain ipv6_support (bool) and max_count (int). When max_count is 0:

  • The resulting value must be an empty list (no addresses collected).
  • Calling output(output_obj) must result in the last (and effectively only) append call carrying, as its second positional argument, the no-address string DEFAULT_CONFIG['default_strings']['no_address'] from archey.constants.

This behavior must hold even when interfaces do report addresses (e.g. a loopback interface and an interface with IPv4/IPv6 addresses present): with max_count == 0, none are retained.

3. Supporting constants

archey.constants must expose DEFAULT_CONFIG, a mapping that includes a 'default_strings' sub-mapping containing at least the keys 'not_detected' and 'no_address'. These string values are used as the fallback text in the behaviors above.

Notes

  • The CPU value is now a list of dicts; do not represent it as a single string.
  • Dictionary key ordering must not be relied upon for correctness in output (multi-line output may append packages in any order).
  • Model name whitespace normalization applies to both /proc/cpuinfo and lscpu parsing paths.

Additional Requirements

  • In _parse_lscpu_output(), the count stored for each model must be Thread(s) per core × Core(s) per socket, using both fields as integers.
  • Socket(s) determines how many identical dictionaries a section contributes; it must not be multiplied into the count stored in each dictionary. These requirements supersede the earlier Core(s) per socket × Socket(s) formula.
  • Consequently, a section with Thread(s) per core: 2, Core(s) per socket: 2, and Socket(s): 1 yields one dictionary with count 4.
  • A section with Thread(s) per core: 2, Core(s) per socket: 4, and Socket(s): 2 yields two identical dictionaries, each with count 8.
02 Rework WAN IP Address Retrieval 706 words · source specification

Task Specification: Rework WAN IP Address Retrieval

Overview

Modify the WanIP entry class in archey/entries/wan_ip.py to support configurable, per-protocol IP address retrieval using two independent back-ends: a DNS query tool (dig) and an HTTP resolver (urlopen). Each protocol version (IPv4 / IPv6) and each back-end must be individually controllable via configuration.

Module and Symbols

  • Module: archey.entries.wan_ip
  • Class: WanIP
  • The module must import and use check_output and urlopen as module-level names (they are patched at archey.entries.wan_ip.check_output and archey.entries.wan_ip.urlopen).

Required Public/Internal API

WanIP._retrieve_ip_address(self, ip_version)

A method on WanIP that attempts to retrieve a single WAN IP address for a given IP protocol version.

Parameters:

  • ip_version: an integer, either 4 or 6, indicating which IP protocol version to resolve.

Return value:

  • A string containing the resolved IP address (stripped of surrounding whitespace/newlines) on success.
  • A falsy value (e.g. None / empty) when no address could be retrieved or when retrieval is disabled by configuration.

This method reads its behavior from self.options, which is a dictionary.

WanIP.output(self, output)

Instance method that produces display output. It reads self.value (a list of address strings).

Behavior:

  • When self.value contains one or more addresses, it must call output.append(...) with the entry name as the first positional argument and, as the second positional argument, a single string of all addresses joined by ", " (comma followed by a space), preserving list order.
  • When self.value is an empty list, it must call output.append(...) with the second positional argument equal to DEFAULT_CONFIG['default_strings']['no_address'] (from archey.constants.DEFAULT_CONFIG).

Configuration Options (self.options)

The options dictionary controls retrieval. It may contain keys 'ipv4' and 'ipv6'. For a given protocol version, the corresponding key is 'ipv4' (for version 4) or 'ipv6' (for version 6).

The value under each protocol key may be:

  1. A boolean False — the entire protocol retrieval is disabled. _retrieve_ip_address must return a falsy value immediately without invoking either back-end.

  2. A dictionary with optional keys:

    • 'dns_query': when set to False, the DNS (dig / check_output) back-end is disabled for that protocol.
    • 'http_url': when set to False, the HTTP (urlopen) back-end is disabled for that protocol.

    When both back-ends are disabled via this dictionary, _retrieve_ip_address must return a falsy value without calling either back-end.

  3. Absent / default — both back-ends are enabled and attempted (DNS first, then HTTP fallback).

Retrieval Behavior and Ordering

For a given protocol version with retrieval enabled:

  1. DNS back-end first. Attempt to resolve the address via check_output (the dig tool).

    • If check_output raises TimeoutExpired or FileNotFoundError, treat this as a hard failure of the DNS back-end: the exception must be caught and the HTTP fallback must then be attempted.
    • If check_output returns a non-empty string (after stripping whitespace), that stripped string is the result and is returned. The HTTP back-end must NOT be called.
    • If check_output returns an empty/whitespace-only string (a soft failure, e.g. '\n'), the DNS back-end is considered to have produced no address, and no HTTP fallback is performed for that attempt — the method returns a falsy value.

    In short: HTTP fallback occurs only when the DNS tool hard-fails (raises one of the caught exceptions), not when it merely returns an empty result.

  2. HTTP back-end (fallback). When reached (DNS back-end hard-failed or DNS was disabled while HTTP is enabled), attempt to resolve via urlopen.

    • The address is read from the response object via its .read() method. The returned value is a bytes object; it must be decoded to a string and stripped of surrounding whitespace before being returned.
    • If reading from urlopen raises a socket timeout (socket.timeout), catch it and treat it as failure, returning a falsy value.

Edge Cases Summary

  • DNS hard-fails, HTTP succeeds → return the HTTP-resolved (stripped) address.
  • DNS succeeds → return DNS address; HTTP never called.
  • DNS soft-fails (empty output) → return falsy; HTTP never called.
  • HTTP .read() raises socket timeout → return falsy.
  • Protocol disabled via False → return falsy, no back-end called.
  • Both back-ends disabled via dict flags → return falsy, no back-end called.

Output Formatting

  • Multiple addresses join with ", ".
  • Empty value list produces the configured no_address default string.

Task Specification: LAN IP Entry — Robust IPv6 Address Handling

Overview

Modify the LanIP entry class in archey.entries.lan_ip, importable as:

from archey.entries.lan_ip import LanIP

The entry gathers local IPv4 and, optionally, IPv6 addresses from the existing network-interface enumeration facility. It must expose retained addresses in a normalized, human-readable form, exclude loopback addresses, honor address-count and IPv6 options, and produce the correct text for populated, empty, and unavailable states.

Interface discovery itself is unchanged. The facility supplies interfaces and per-interface mappings keyed by address-family constants such as AF_INET, AF_INET6, and possibly non-IP families. Address records contain at least an 'addr' string.

Public API

The class must remain constructible as:

LanIP(options={
    'max_count': <non-negative int or False>,
    'ipv6_support': <bool>
})

Both options are optional:

  • max_count defaults to 2.
  • ipv6_support defaults to True.

After construction:

  • lan_ip.value is a list of retained address strings when the network-interface facility is available, including when that list is empty.
  • lan_ip.value is None when the optional network-interface facility is unavailable.
  • lan_ip.output(output) must add one entry through output.append(...), using the entry's name as the first positional argument and the display text described below as the second positional argument.

Address Selection

Address families

IPv4 (AF_INET) addresses are always eligible for collection. IPv6 (AF_INET6) addresses are eligible only when ipv6_support is True. When ipv6_support is False, IPv6 records must not appear in value, while eligible IPv4 records remain.

Records belonging to other families, including link-layer or MAC-address records, must not be included. Link-local and private IP addresses are otherwise valid; only the loopback exclusions below are required.

Per-address normalization

Each eligible raw 'addr' string must be normalized before it is retained or checked for IPv6 loopback equivalence:

  1. Remove a CIDR or netmask suffix. If the string contains /, remove the / and everything after it. For example, 2a02::45:6789:abcd:0123/64 becomes 2a02::45:6789:abcd:0123.
  2. Remove an IPv6 zone or scope suffix. If the string contains %, remove the % and everything after it. For example, fe80::abcd:ef0:abef:dead%en0 becomes fe80::abcd:ef0:abef:dead. The % is a literal character in the raw address.
  3. Compress IPv6 text canonically. For AF_INET6 records, remove leading zeroes from groups and replace the longest eligible run of all-zero groups with :: according to standard IPv6 textual compression rules. Canonical hexadecimal casing and tie-breaking rules must be used. Examples:
    • 2001:0000:0000:0000:0045:6789:abcd:6817 becomes 2001::45:6789:abcd:6817.
    • 0000:0000:0000:0000:0000:0000:0000:0001 becomes ::1.

IPv4 text is not otherwise reformatted; after suffix removal, an address such as 192.168.1.55 remains 192.168.1.55.

Loopback exclusion

Loopback addresses must not be retained:

  • Exclude IPv4 addresses beginning with 127..
  • Exclude the IPv6 loopback address semantically equivalent to ::1.

The exclusion must be representation-independent and occur after, or as part of, semantic normalization. Consequently, both ::1 and 0000:0000:0000:0000:0000:0000:0000:0001 are excluded, including equivalent inputs carrying removable CIDR or zone suffixes. A fully expanded IPv6 loopback must never survive merely because its raw spelling was not already ::1.

Excluded loopback records do not consume the max_count allowance.

Ordering and Limiting

The resulting order is deterministic:

  1. Retained IPv4 addresses come first, in interface/address discovery order.
  2. Retained IPv6 addresses follow, in interface/address discovery order.

Normalization must not reorder the addresses. Each retained discovery contributes its normalized address; no sorting by textual or numeric value is performed.

Apply max_count to the final stream of eligible, normalized, non-loopback addresses while preserving that order:

  • A positive integer retains at most that many addresses.
  • Integer 0 retains no addresses and therefore produces an empty list.
  • Boolean False is the explicit unlimited sentinel and retains all eligible addresses. It must not be conflated with integer 0, even though both are falsy in Python.
  • If omitted, the default limit is 2.

Output Behavior

output() must choose its second append argument according to the entry state:

  1. Non-empty list: Join all strings in value with exactly ", " (comma followed by one space).
  2. Empty list with enumeration available: Use the configured default_strings.no_address value, rather than an empty string. With the default configuration, this is exactly DEFAULT_CONFIG['default_strings']['no_address']. This case includes no interfaces, interfaces with no IP records, hosts exposing only excluded loopbacks, IPv6-only results when IPv6 is disabled, and max_count=0.
  3. Enumeration facility unavailable: Leave value as None, fail softly rather than attempting discovery, and use the configured default_strings.not_detected value. With the default configuration, this is exactly DEFAULT_CONFIG['default_strings']['not_detected'].

Configuration overrides for these default strings must continue to be honored.

Worked Example

Suppose discovery yields the following eligible candidates:

  • IPv4: 192.168.1.55
  • IPv6, in order:
    • 2001:0000:0000:0000:0045:6789:abcd:6817
    • fe80::abcd:ef0:abef:dead%en0
    • 2a02::45:6789:abcd:0123/64

With:

LanIP(options={
    'max_count': 3,
    'ipv6_support': True
})

the resulting value must be:

[
    '192.168.1.55',
    '2001::45:6789:abcd:6817',
    'fe80::abcd:ef0:abef:dead'
]

and the display text passed as the second positional argument to output.append must be:

192.168.1.55, 2001::45:6789:abcd:6817, fe80::abcd:ef0:abef:dead

The fourth candidate, 2a02::45:6789:abcd:0123, is normalized but omitted by the limit. If discovery also supplied 127.0.0.1 or an expanded spelling of IPv6 loopback, those records would be excluded before applying the limit.
