01 Supporting Multiple CPUs in the CPU Entry 1522 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Supporting Multiple CPUs in the CPU Entry

Summary

The CPU entry is to be modified so that it detects and represents multiple CPUs (physical packages), with each package carrying its own model name and its total number of cores. A small behavioral edge case must also be added to the LanIP entry. All work must satisfy the exact public API surface and behaviors laid out below.

1. The CPU entry — archey/entries/cpu.py

A class CPU must be exposed by the module archey.entries.cpu. It imports open (used for reading /proc/cpuinfo) and check_output (used for invoking lscpu) under the module-level names archey.entries.cpu.open and archey.entries.cpu.check_output.

1.1 Representation of the value

A CPU instance must produce a value attribute that is a list of dictionaries. Every dictionary stands for one physical CPU package and maps a CPU model name string → core count (int). When (unusually) multiple distinct model names are reported for the same physical package, a single dictionary may contain more than one key.

For example:

[
    {'CPU-MODEL-NAME': 1},
    {'ANOTHER-CPU-MODEL': 2}
]
1.2 The static method CPU._parse_proc_cpuinfo()

Its signature is @staticmethod def _parse_proc_cpuinfo().

The method reads /proc/cpuinfo (via the module-level open) and parses it. The file's content consists of processor blocks separated by blank lines. Every block contains lines of the form key\t: value. The fields of interest are model name and physical id.

Behavior:

  • Processors are grouped by their physical id. Every distinct physical id becomes one entry (one dictionary) in the returned list, in the order in which the physical ids first appear.
  • Inside each physical-id group, the occurrences of each model name are counted, and the dictionary for that group maps model name → the number of processors carrying that model name within that group.
  • Model name normalization: any run of whitespace characters (spaces and/or tabs) found within a model name is collapsed into a single space, and leading/trailing whitespace is stripped. For instance, the raw model name ANOTHER\tCPU MODEL WITH STRANGE S P A C E S becomes ANOTHER CPU MODEL WITH STRANGE S P A C E S.
  • The return type is a list of dict[str, int].

Examples showing the required results:

  • One processor block having model name: CPU-MODEL-NAME and physical id: 0:

    [{'CPU-MODEL-NAME': 1}]

  • Three processors: a single CPU-MODEL-NAME on physical id 0, plus two ANOTHER-CPU-MODEL on physical id 1:

    [{'CPU-MODEL-NAME': 1}, {'ANOTHER-CPU-MODEL': 2}]

  • Four processors, all of them CPU-MODEL-NAME, with two on physical id 0 and two on physical id 1:

    [{'CPU-MODEL-NAME': 2}, {'CPU-MODEL-NAME': 2}]

  • Four processors where physical id 0 carries one CPU-MODEL-NAME and one ANOTHER-CPU-MODEL, and physical id 1 carries two of a strangely-spaced model name:

    [
    {'CPU-MODEL-NAME': 1, 'ANOTHER-CPU-MODEL': 1},
    {'ANOTHER CPU MODEL WITH STRANGE S P A C E S': 2}
]

Error/edge case: if /proc/cpuinfo cannot be read (e.g. open raises PermissionError), an empty list is returned.

1.3 The static method CPU._parse_lscpu_output()

Its signature is @staticmethod def _parse_lscpu_output().

The method invokes lscpu (via the module-level check_output) and parses its output. lscpu output is made up of Key: Value lines. The output may hold multiple CPU sections separated by a blank line; every such section is one physical CPU package and yields one dictionary in the returned list, in order.

For every section, the Model name field serves as the model name (normalized the same way as in _parse_proc_cpuinfo, i.e. internal whitespace runs are collapsed to a single space and the result is stripped). The core count for that package is computed as Core(s) per socket × Socket(s) (both are integer fields taken from that section).

The return type is a list of dict[str, int].

The required results:

  • A single section with Core(s) per socket: 4, Socket(s): 1, Model name: CPU-MODEL-NAME:

    [{'CPU-MODEL-NAME': 4}]

  • Two sections (separated by a blank line): the first has Core(s) per socket: 2, Socket(s): 1, Model name: CPU-MODEL-NAME; the second has Core(s) per socket: 2, Socket(s): 1... hold on — the second section reports Core(s) per socket: 2, Socket(s): 1 with a different model — see the mapping below:

    [
    {'CPU-MODEL-NAME': 2},
    {'ANOTHER-CPU-MODEL': 4}
]

    (First section: 2×1 = 2 cores. Second section: Core(s) per socket: 2 × Socket(s): 1... the values supplied by the second section yield 4 cores — i.e. Core(s) per socket × Socket(s) = 4 — for model ANOTHER-CPU-MODEL.)

  • A single section with Core(s) per socket: 4, Socket(s): 2, Model name: CPU-MODEL-NAME — this represents one CPU model spread across two sockets:

    [{'CPU-MODEL-NAME': 8}, {'CPU-MODEL-NAME': 8}]

    Note: if a single lscpu section describes Socket(s): 2 for one model, the result contains one dictionary per socket, with each dictionary mapping the model name to the per-socket core count (Core(s) per socket × Socket(s)).

Clarification regarding core-count semantics: the value stored per model equals Core(s) per socket × Socket(s) taken from the section, and the section contributes one dictionary per socket (a section with N sockets thus yields N identical dictionaries).

1.4 The instance method CPU.output(self, output)

Signature: def output(self, output).

output refers to an object that has an append(name, text) method. The string 'CPU' is the entry name to use.

The method reads the following:

  • self.value — the list-of-dicts described above (it may also be an empty container).
  • self.options — a mapping that supports these keys:
    • 'one_line' (bool): when true, all CPUs are merged into a single appended line; when false, every CPU package produces its own appended line.
    • 'show_cores' (bool): when true (default behavior), every model name gets prefixed with its core count in the form N x MODEL whenever the count is greater than 1; when the count is exactly 1, only the model name is shown (no 1 x prefix). When false, core counts are left out entirely, and only the model names are shown.

Formatting rules for a single model entry:

  • Counts shown and count == 1: MODEL
  • Counts shown and count > 1: N x MODEL
  • Counts hidden: MODEL

Combining rule when one_line is true: take every model entry across all CPU packages (each formatted according to the rules above), join them into one comma-space (, ) separated string, and call output.append('CPU', combined_string) exactly once.

Behavior when one_line is false: for every CPU package, call output.append('CPU', text), with text being that package's formatted model entries joined by , . This results in one call per package. (The order across packages need not be guaranteed.)

No-CPU edge case: when self.value is empty (e.g. an empty dict/list), call output.append('CPU', <not_detected string>) exactly once; here the not-detected string is DEFAULT_CONFIG['default_strings']['not_detected'] from archey.constants.

Required examples, taking self.value = [{'CPU-MODEL-NAME': 1}, {'ANOTHER-CPU-MODEL': 2}]:

  • one_line=True with counts shown → one call: output.append('CPU', 'CPU-MODEL-NAME, 2 x ANOTHER-CPU-MODEL')
  • one_line=True and show_cores=False → one call: output.append('CPU', 'CPU-MODEL-NAME, ANOTHER-CPU-MODEL')
  • one_line=False and show_cores=True → two calls:
    • output.append('CPU', 'CPU-MODEL-NAME')
    • output.append('CPU', '2 x ANOTHER-CPU-MODEL')

With an empty value → one call: output.append('CPU', DEFAULT_CONFIG['default_strings']['not_detected']).

1.5 Options and default configuration

The CPU entry must recognize the options one_line and show_cores; these are taken from self.options at output time. The name given to an entry must not be treated as a configurable option.

2. The LanIP entry — archey/entries/lan_ip.py

The existing LanIP entry must handle the situation where the user sets max_count to 0.

LanIP is constructed with an options mapping that may contain ipv6_support (bool) and max_count (int). When max_count is 0:

  • The value that results must be an empty list (no addresses collected).
  • Calling output(output_obj) must result in the last (and effectively only) append call carrying the no-address string DEFAULT_CONFIG['default_strings']['no_address'] from archey.constants as its second positional argument.

This behavior must hold even when interfaces do report addresses (e.g. a loopback interface and an interface with IPv4/IPv6 addresses present): with max_count == 0, none of them are retained.

3. Supporting constants

archey.constants must expose DEFAULT_CONFIG, a mapping that includes a 'default_strings' sub-mapping with at least the keys 'not_detected' and 'no_address'. The behaviors above use these string values as their fallback text.

Notes

  • The CPU value is now a list of dicts; it must not be represented as a single string.
  • Correctness in output must not rely on dictionary key ordering (multi-line output may append packages in any order).
  • Whitespace normalization of model names is applied on both the /proc/cpuinfo and the lscpu parsing paths.

Additional Requirements

  • In _parse_lscpu_output(), the count stored for each model must be Thread(s) per core × Core(s) per socket, with both fields used as integers.
  • Socket(s) decides how many identical dictionaries a section contributes; multiplying it into the count stored in each dictionary must not happen. These requirements supersede the earlier Core(s) per socket × Socket(s) formula.
  • As a consequence, a section with Thread(s) per core: 2, Core(s) per socket: 2, and Socket(s): 1 yields one dictionary whose count is 4.
  • A section with Thread(s) per core: 2, Core(s) per socket: 4, and Socket(s): 2 yields two identical dictionaries, each of them with count 8.
02 Rework of WAN IP Address Retrieval 781 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Rework of WAN IP Address Retrieval

Overview

Change the WanIP entry class in archey/entries/wan_ip.py so that it supports configurable, per-protocol IP address retrieval through two independent back-ends: a DNS query tool (dig) and an HTTP resolver (urlopen). Configuration must make each protocol version (IPv4 / IPv6) and each back-end individually controllable.

Module and Symbol Names

  • Module: archey.entries.wan_ip
  • Class: WanIP
  • check_output and urlopen must be imported and used by the module as module-level names (the patch points are archey.entries.wan_ip.check_output and archey.entries.wan_ip.urlopen).

Required Public and Internal API

WanIP._retrieve_ip_address(self, ip_version)

A method belonging to WanIP that attempts to retrieve a single WAN IP address for a given IP protocol version.

Parameters:

  • ip_version: an integer — either 4 or 6 — indicating which IP protocol version to resolve.

Return value:

  • On success, a string holding the resolved IP address (stripped of surrounding whitespace/newlines).
  • A falsy value (e.g. None / empty) if no address could be retrieved, or if retrieval is disabled by configuration.

The behavior of this method is read from self.options, which is a dictionary.

WanIP.output(self, output)

Instance method that produces the display output. It reads self.value (a list of address strings).

Behavior:

  • If self.value contains at least one address, it must call output.append(...), passing the entry name as the first positional argument and, as the second positional argument, a single string formed by joining all addresses with ", " (comma followed by a space), preserving the list order.
  • If self.value is an empty list, it must call output.append(...) with the second positional argument equal to DEFAULT_CONFIG['default_strings']['no_address'] (taken from archey.constants.DEFAULT_CONFIG).

Configuration Options (self.options)

Retrieval is controlled by the options dictionary. It may contain the keys 'ipv4' and 'ipv6'. For a given protocol version, the corresponding key is 'ipv4' (for version 4) or 'ipv6' (for version 6).

The value stored under each protocol key may be:

  1. A boolean False — retrieval for the entire protocol is disabled. _retrieve_ip_address must return a falsy value immediately, without invoking either back-end.

  2. A dictionary carrying optional keys:

    • 'dns_query': when it is set to False, the DNS (dig / check_output) back-end is disabled for that protocol.
    • 'http_url': when it is set to False, the HTTP (urlopen) back-end is disabled for that protocol.

    When this dictionary disables both back-ends, _retrieve_ip_address must return a falsy value without calling either back-end.

  3. Absent / default — both back-ends are enabled and get attempted (DNS first, then the HTTP fallback).

Retrieval Behavior and Order

For a given protocol version for which retrieval is enabled:

  1. DNS back-end first. An attempt is made to resolve the address via check_output (the dig tool).

    • If check_output raises TimeoutExpired or FileNotFoundError, this counts as a hard failure of the DNS back-end: the exception must be caught, and the HTTP fallback must then be attempted.
    • If the string returned by check_output is non-empty (after stripping whitespace), that stripped string is the result and is returned. The HTTP back-end must NOT be called.
    • If check_output returns a string that is empty or contains only whitespace (a soft failure, e.g. '\n'), the DNS back-end is considered to have produced no address, and no HTTP fallback is performed for that attempt — the method returns a falsy value.

    In short: the HTTP fallback occurs only when the DNS tool hard-fails (raises one of the caught exceptions), not when it merely returns an empty result.

  2. HTTP back-end (fallback). When this back-end is reached (the DNS back-end hard-failed, or DNS was disabled while HTTP is enabled), an attempt is made to resolve via urlopen.

    • The address is read from the response object via its .read() method. The value obtained this way is a bytes object; it must be decoded to a string and stripped of surrounding whitespace before being returned.
    • If reading from urlopen raises a socket timeout (socket.timeout), it is caught and treated as a failure, and a falsy value is returned.

Summary of Edge Cases

  • DNS hard-fails, HTTP succeeds → the HTTP-resolved (stripped) address is returned.
  • DNS succeeds → the DNS address is returned; HTTP is never called.
  • DNS soft-fails (empty output) → a falsy value is returned; HTTP is never called.
  • HTTP .read() raises a socket timeout → a falsy value is returned.
  • Protocol disabled via False → a falsy value is returned; no back-end is called.
  • Both back-ends disabled via the dict flags → a falsy value is returned; no back-end is called.

Output Formatting

  • Multiple addresses are joined with ", ".
  • An empty value list produces the configured no_address default string.
03 LAN IP Entry — Robust Handling of IPv6 Addresses 926 words · rewritten by GPT-5.6-sol, reworded by GLM-5.3-Flash

Task Specification: LAN IP Entry — Robust Handling of IPv6 Addresses

Summary

The LanIP entry class in archey.entries.lan_ip is to be modified; it is importable as:

from archey.entries.lan_ip import LanIP

From the existing network-interface enumeration facility, the entry collects local IPv4 addresses and, optionally, IPv6 addresses. It must expose the retained addresses in a normalized, human-readable form, must exclude loopback addresses, must honor the address-count and IPv6 options, and must produce the correct text for populated, empty, and unavailable states.

Interface discovery itself stays unchanged. Interfaces are supplied by the facility, together with per-interface mappings keyed by address-family constants such as AF_INET, AF_INET6, and possibly non-IP families. Every address record contains at least an 'addr' string.

Public API

The class must continue to be constructible as:

LanIP(options={
    'max_count': <non-negative int or False>,
    'ipv6_support': <bool>
})

Each of the two options is optional:

  • The default for max_count is 2.
  • The default for ipv6_support is True.

Once constructed:

  • When the network-interface facility is available, lan_ip.value is a list of the retained address strings — even when that list is empty.
  • When the optional network-interface facility is unavailable, lan_ip.value is None.
  • lan_ip.output(output) must use output.append(...) to add one entry, passing the entry's name as the first positional argument and the display text described below as the second positional argument.

Selecting the Addresses

Address families

IPv4 (AF_INET) addresses remain eligible for collection at all times. IPv6 (AF_INET6) addresses are eligible only when ipv6_support is True. With ipv6_support set to False, IPv6 records must not appear in value, while eligible IPv4 records remain.

Records from other families — including link-layer or MAC-address records — must not be included. Only the loopback exclusions described below are required; apart from those, link-local and private IP addresses are valid.

Normalizing Each Address

Each eligible raw 'addr' string must undergo normalization before it is retained or checked for IPv6 loopback equivalence:

  1. Strip a CIDR or netmask suffix. Should the string contain /, remove the / together with everything that follows it. For example, 2a02::45:6789:abcd:0123/64 becomes 2a02::45:6789:abcd:0123.
  2. Strip an IPv6 zone or scope suffix. Should the string contain %, remove the % together with everything that follows it. For example, fe80::abcd:ef0:abef:dead%en0 becomes fe80::abcd:ef0:abef:dead. Within the raw address, the % is a literal character.
  3. Compress IPv6 text canonically. For AF_INET6 records, leading zeroes are removed from groups and the longest eligible run of all-zero groups is replaced with :: per standard IPv6 textual compression rules. The canonical hexadecimal casing and tie-breaking rules must be used. Examples:
    • 2001:0000:0000:0000:0045:6789:abcd:6817 becomes 2001::45:6789:abcd:6817.
    • 0000:0000:0000:0000:0000:0000:0000:0001 becomes ::1.

IPv4 text is not reformatted in any other way; after the suffixes are removed, an address such as 192.168.1.55 remains 192.168.1.55.

Excluding Loopback Addresses

The entry must not retain loopback addresses:

  • IPv4 addresses beginning with 127. are excluded.
  • The IPv6 loopback address semantically equivalent to ::1 is excluded.

This exclusion must be representation-independent and must take place after, or as part of, semantic normalization. As a result, both ::1 and 0000:0000:0000:0000:0000:0000:0000:0001 are excluded, as are equivalent inputs carrying removable CIDR or zone suffixes. A fully expanded IPv6 loopback must never survive merely because its raw spelling was not already ::1.

Loopback records that are excluded do not consume the max_count allowance.

Ordering and Limiting

The order that results is deterministic:

  1. IPv4 addresses that are retained come first, in interface/address discovery order.
  2. IPv6 addresses that are retained follow, in interface/address discovery order.

The addresses must not be reordered by normalization. Each retained discovery contributes its normalized address, and no sorting by textual or numeric value is performed.

max_count is applied to the final stream of eligible, normalized, non-loopback addresses while that order is preserved:

  • A positive integer means at most that many addresses are retained.
  • The integer 0 retains no addresses and therefore produces an empty list.
  • The boolean False is the explicit unlimited sentinel and retains all eligible addresses. It must not be equated with integer 0, even though both are falsy in Python.
  • When the option is omitted, the default limit is 2.

Output Behavior

Depending on the entry state, output() must choose its second append argument as follows:

  1. Non-empty list: All strings in value are joined with exactly ", " (a comma followed by one space).
  2. Empty list with enumeration available: The configured default_strings.no_address value is used instead of an empty string. Under the default configuration, this is exactly DEFAULT_CONFIG['default_strings']['no_address']. The following situations fall under this case: no interfaces, interfaces with no IP records, hosts exposing only excluded loopbacks, IPv6-only results when IPv6 is disabled, and max_count=0.
  3. Enumeration facility unavailable: value is left as None, the entry fails softly rather than attempting discovery, and the configured default_strings.not_detected value is used. Under the default configuration, this is exactly DEFAULT_CONFIG['default_strings']['not_detected'].

Overrides of these default strings through configuration must continue to be honored.

Worked Example

Assume discovery produces the following eligible candidates:

  • IPv4: 192.168.1.55
  • IPv6, in this order:
    • 2001:0000:0000:0000:0045:6789:abcd:6817
    • fe80::abcd:ef0:abef:dead%en0
    • 2a02::45:6789:abcd:0123/64

Using:

LanIP(options={
    'max_count': 3,
    'ipv6_support': True
})

the value that results must be:

[
    '192.168.1.55',
    '2001::45:6789:abcd:6817',
    'fe80::abcd:ef0:abef:dead'
]

and the display text supplied to output.append as the second positional argument must be:

192.168.1.55, 2001::45:6789:abcd:6817, fe80::abcd:ef0:abef:dead

Although the fourth candidate, 2a02::45:6789:abcd:0123, is normalized, the limit omits it. Should discovery also supply 127.0.0.1 or an expanded spelling of the IPv6 loopback, those records would be excluded before the limit is applied.

Task: Make display of globally-routable ("public") IP addresses in the LAN IP entry configurable

Background

The entry class LanIP resides in the module archey.entries.lan_ip and is imported as:

from archey.entries.lan_ip import LanIP

LanIP gets instantiated with an options dict, e.g. LanIP(options={...}). Once constructed, the collected addresses are available through the .value attribute (a list of strings), and the entry provides an .output(output_mock) method that renders the value.

Addresses are enumerated by means of the netifaces module (accessed as archey.entries.lan_ip.netifaces), via netifaces.interfaces() and netifaces.ifaddresses(...). The IPv4 and IPv6 address family constants (AF_INET, AF_INET6) come from netifaces.

Change to Implement

Add a new boolean option, show_global, to the options dict that is passed to LanIP.

Behavior

By default (that is, when show_global is absent or falsey), globally-routable / public IP addresses (i.e. addresses that are NOT private per RFC 1918 and equivalents) must still be excluded from .value. This is the behavior that already exists, and it must be preserved.

If show_global is set to True, public (globally-routable) IP addresses must be included in .value alongside the private addresses.

Concrete requirement

Suppose the interfaces are ['lo', 'en0'], where:

  • lo exposes the IPv4 address 127.0.0.1 (loopback) and the IPv6 address ::1.
  • en0 exposes the IPv4 addresses 192.168.1.55 (private) and 123.45.67.89 (public/globally-routable).

Instantiating LanIP(options={'show_global': True}) must result in a .value of:

['192.168.1.55', '123.45.67.89']

That is: when show_global is enabled, both the private address 192.168.1.55 and the public address 123.45.67.89 are kept, in interface/address enumeration order. (Loopback addresses like 127.0.0.1 and ::1 stay excluded.)

Preservation constraints (behavior that already exists and must remain intact)

  • The options dict keeps supporting max_count (an integer that limits how many addresses are shown; False means no limit; 0 is an accepted edge value).
  • The options dict keeps supporting ipv6_support (a boolean; when it is False, IPv6 addresses are excluded from .value).
  • If max_count is omitted, address collection and rendering via .output() must work with default behavior (explicitly passing ipv6_support=True is no longer needed for IPv6 to be included; IPv6 is included by default unless ipv6_support is False).
  • Loopback addresses are always left out.
