You will be working in a Python package located at src/svg/path/. The package supplies classes for representing SVG path segments along with a parser for SVG path data strings. Your task is to ensure that the public API is exposed under particular module names.

Module Structure Requirements

The functionality of the package must be exposed through the following two modules, which are importable as relative imports from within the package (svg.path):

  1. svg.path.path — a module which defines and exports the following classes:

    • CubicBezier

These names must be importable exactly as follows:

(equivalently, by means of the relative imports from ..path import ... and from ..parser import parse_path from within the package's test/subpackage context).

Behavioral Requirements

The classes and the function must keep their existing behavior — the only structural requirement introduced here is that they are accessible under the module names path and parser (rather than any of the module names used previously, such as svgpath or svgparser). Beyond preserving what they already do, no behavioral changes to the path segment classes or to parse_path are required.

Path segment classes (svg.path.path)
  • Line, CubicBezier, QuadraticBezier, and Arc each represent an individual SVG path segment and can be constructed using their respective control/endpoint parameters. Points are represented as complex numbers (the real part being the x-coordinate and the imaginary part the y-coordinate).
  • Each segment supports evaluating a point along its length via a point(pos) method, where pos ranges from 0 (start) to 1 (end).
  • Each segment offers a length() method that returns its geometric length.
  • Segments can be compared for equality and inequality; segments of different types are never equal.
  • Path is a container of segments that behaves like a sequence (it supports indexing, iteration, appending, and length via len()). It also provides point(pos) and length() methods that span the concatenation of all contained segments, with the parameter pos distributed across segments in proportion to their lengths.
Parser (svg.path.parser)
  • parse_path(path_string) accepts an SVG path data string and returns a Path object that is composed of the appropriate segment objects.

Deliverable

Ensure that importing the five classes from svg.path.path together with parse_path from svg.path.parser succeeds, and that all of the behavior described is available through those import paths.

Task Specification: Number Format Support for an SVG Path Parser

Overview

The software you will be working on is a Python package that turns SVG path definition strings into geometric path objects. The module svg.path is where its public API is exposed. You must ensure that negative numbers, and numbers written in scientific/exponential notation, are handled correctly by the path parser.

Public API

From the svg.path package, the items below must be importable:

  • parse_path(pathdef) — a function that accepts an SVG path definition string as input and returns a Path object.
  • Path — a class for a sequence of path segments. You create a Path instance by passing one or more segment objects as positional arguments; for instance, Path(segment1, segment2, ...).
  • Line — a path segment class for a straight line; its constructor takes the form Line(start, end), with start and end being complex numbers that encode 2D points (real part = x coordinate, imaginary part = y coordinate).

Two Path objects that contain equivalent segments must compare equal (==); two Line segments whose start and end points are equal must also compare equal.

Behavior Requirements

Number and coordinate handling

Numeric values in path coordinate data must be tokenized and interpreted correctly by the parser. The following cases are among those it must handle:

  1. Negative numbers. A negative number is introduced by a minus sign, which also works as an implicit separator between coordinate values. To illustrate: the coordinate sequence 10-5,20-10,30-20 must parse into the same numbers as 10 -5 20 -10 30 -20.

  2. Scientific / exponential notation. An exponent may be used when writing numbers:

    • As the exponent marker, either lowercase e or uppercase E may be used.
    • An explicit sign — + or - — may be attached to the exponent, or the exponent may have no sign at all.
    • Negative values may be used for both the mantissa and the exponent.
    • Values whose magnitude is at least 3.4e38 (i.e. 3.4 × 10^38) must be supported, as must very small values such as 3.4e-38.

    Some valid numeric tokens, by way of example: -3.4e38, 3.4E+38, -3.4E-38, 3.4e-38.

  3. Separators. Commas, whitespace, and the leading minus sign of a following number all work as separators between adjacent numeric values.

Command handling

At least the following path commands must be handled by the parser, as they appear in the test-exercised inputs:

  • M / m — moveto (the current point / start of the path is established here).
  • L — lineto (a Line segment from the current point to the given point is produced).
  • c — relative cubic curve (when its coordinate arguments use the number formats above, it must be parseable).
Required equivalences

  • It must be the case that parsing 'M-3.4e38 3.4E+38L-3.4E-38,3.4e-38' yields a path equal to:

    Path(Line(-3.4e+38 + 3.4e+38j, -3.4e-38 + 3.4e-38j))

    To unpack this: the moveto places the current point at (-3.4e38, 3.4e38), and from there the L command draws a single line to (-3.4e-38, 3.4e-38).

  • The path that results from parsing 'M100,200c10-5,20-10,30-20' must be equal to the path that results from parsing 'M 100 200 c 10 -5 20 -10 30 -20'.

Implementation constraints

  • It is only when a minus sign does not form part of an exponent that it must be treated as the start of a new number. In 3.4e-38, the - is part of the exponent and must not split the token into two numbers; in 20-10, the - separates two distinct numbers.
  • Coordinate values are combined into complex numbers: the x value supplies the real part, and the y value the imaginary part.

Task: Fix the close-path behavior for SVG paths with multiple subpaths

The public API of svg.path must provide:

  • parse_path(pathdef: str) -> Path
  • Path(*segments)
  • Line(start: complex, end: complex)

When SVG path data contains multiple subpaths, a lowercase z close-path command must close the most recently started subpath, taking the coordinates from its latest M command. The command must not close to the initial point of an earlier subpath.

As an example:

parse_path("M 0 0 L 50 20 M 100 100 L 300 100 L 200 300 z")

must be equal to:

Path(
    Line(0 + 0j, 50 + 20j),
    Line(100 + 100j, 300 + 100j),
    Line(300 + 100j, 200 + 300j),
    Line(200 + 300j, 100 + 100j),
)

Each M starts a new subpath without creating a connecting segment. In this case, z adds a line from 200 + 300j back to 100 + 100j, which is the starting point of the second subpath.

SVG Path Library: Task Specification

Write a Python library that parses, represents, evaluates and generates SVG path data. Its package path is svg.path, with the source code in src/svg/path.

Modules and Their Public Interfaces

The svg.path.path module

Line, CubicBezier, QuadraticBezier, Arc and Path are the classes this module must expose.

All 2D points, wherever they occur, are represented as Python complex numbers — the real part carries the x-coordinate, the imaginary part the y-coordinate.

Every one of the segment classes (Line, CubicBezier, QuadraticBezier, Arc) must provide:

  • point(pos) — returns the complex point sitting on the segment at parameter pos; pos goes from 0.0 (start) to 1.0 (end).
  • length() — returns the segment's arc length as a float.

Equality comparison (==) must be supported by all the segment classes as well as by Path; two instances are equal whenever they have the same type and their defining parameters are equal.

Line

Construct with Line(start, end); start and end are both complex points.

  • point(pos) applies linear interpolation, i.e. start + (end - start) * pos.
  • length() returns the Euclidean (straight-line) distance from start to end.

Sample values:

  • Line(0j, 400+0j).point(0.3) → 120+0j; .length() → 400.
  • Line(400+0j, 400+300j).length() → 300.
  • Line(400+300j, 0j).point(0.3) → 280+210j; .length() → 500.
CubicBezier

The constructor CubicBezier(start, control1, control2, end) takes four complex points.

  • point(pos) computes the value of the standard cubic Bézier at pos.
  • length() returns an estimate of the curve's arc length.

Sample point values:

  • CubicBezier(100+200j, 100+100j, 250+100j, 250+200j): point(0)=100+200j, point(0.3)=132.4+137j, point(0.5)=175+125j, point(0.9)=245.8+173j, point(1)=250+200j.
  • CubicBezier(600+500j, 600+350j, 900+650j, 900+500j): point(0.3)=664.8+462.2j, point(0.5)=750+500j, point(0.9)=891.6+532.4j.

length() behavior:

  • With the degenerate straight vertical curve CubicBezier(0j, 0j, 0+100j, 0+100j), length() ≈ 100.
  • With the degenerate straight diagonal CubicBezier(0j, 0j, 100+100j, 100+100j), length() ≈ sqrt(2*100*100).
  • For the radius-100 quarter-circle approximation built with kappa = 4*(sqrt(2)-1)/3, i.e. CubicBezier(0j, 0+kappa*100j, (100-kappa*100)+100j, 100+100j), length() ≈ 157.1016698.

Computed lengths must be accurate to at least the precision that assertAlmostEqual checks (7 decimal places by default).

QuadraticBezier

The constructor QuadraticBezier(start, control, end) takes exactly one control point — three complex points altogether.

  • point(pos) computes the value of the standard quadratic Bézier at pos.
  • length() returns an arc-length estimate.

Sample behavior:

  • QuadraticBezier(200+300j, 400+50j, 600+300j): point(0)=200+300j, point(0.3)=320+195j, point(0.5)=400+175j, point(0.9)=560+255j, point(1)=600+300j; length() ≈ 487.7710938890204.
Arc

Construct with Arc(start, radius, rotation, arc, sweep, end); the arguments are the SVG elliptical arc parameters:

  • start — the starting point, a complex.
  • radius — a complex holding the x-radius in its real part and the y-radius in its imaginary part.
  • rotation — the x-axis rotation, in degrees (a float).
  • arc — the large-arc flag (values 0 or 1).
  • sweep — the sweep flag (values 0 or 1).
  • end — the end point, a complex.

The attributes below must be computed and exposed on each instance:

  • center — the ellipse's center, as a complex.
  • theta — the starting angle, in degrees.
  • delta — the signed sweep angle, in degrees.

Its methods:

  • point(pos) returns the point on the arc for a parameter pos drawn from [0,1], so that point(0) equals start while point(1) equals end.
  • length() returns an estimate of the arc length.

Sample behavior:

  • Arc(0j, 100+50j, 0, 0, 0, 100+50j): center=100+0j, theta=180.0, delta=-90.0; point(0.5)=29.2893218813+35.3553390593j.
  • Arc(0j, 100+50j, 0, 1, 0, 100+50j): center=50j, theta=270.0, delta=-270.0; point(0.5)=-70.7106781187+85.3553390593j.
  • Arc(0j, 100+50j, 0, 0, 1, 100+50j): center=50j, theta=270.0, delta=90.0; point(0.5)=70.7106781187+14.6446609407j.
  • Arc(0j, 100+50j, 0, 1, 1, 100+50j): center=100+0j, theta=180.0, delta=270.0; point(0.5)=170.710678119-35.3553390593j.
  • Two half-circles that together make a full circle: Arc(0j, 100+100j, 0, 0, 0, 200+0j).length() ≈ pi*100, and likewise Arc(200+0j, 100+100j, 0, 0, 0, 0j).length() ≈ pi*100.
Path

The constructor Path(*segments) accepts any number of segment objects (Line, CubicBezier, QuadraticBezier, Arc); they come in as positional arguments, in the order given.

A Path models a piecewise curve whose segments are chained end to end. When parameterized over [0,1], the parameter is handed out across the segments proportionally by segment length (equal lengths of curve therefore map to equal pos spans).

Provided methods and attributes:

  • point(pos) — returns the complex point at parameter pos in [0,1] for the path as a whole; point(0.0) lands on the first segment's start, point(1.0) on the last segment's end.
  • length() — returns the path's total arc length (all segment lengths summed).
  • closed — a boolean attribute that reads True when the path makes a closed loop (that is, a close/Z behavior is present that brings the subpath back to its start). A path parsed from data that ends with a Z/z close command returning to the starting point must have it as True.
  • to_svg() — returns a string of SVG path data describing the path (see the section on generating path data).

Sample behavior:

  • A full circle assembled from two arcs: Path(Arc(0j,100+100j,0,0,0,200+0j), Arc(200+0j,100+100j,0,0,0,0j)): point(0.0)=0j, point(0.25)=100+100j, point(0.5)=200+0j, point(0.75)=100-100j, point(1.0)=0j; length() ≈ pi*200.
  • Pie shape — Path(Line(300+200j,150+200j), Arc(150+200j,150+150j,0,1,0,300+50j), Line(300+50j,300+200j)): point(0.0)=300+200j, point(0.14897825542)=150+200j, point(0.5)=406.066017177+306.066017177j, point(1-0.14897825542)=300+50j, point(1.0)=300+200j; length() ≈ pi*225+300 (accurate to 6 decimal places).
  • Little pie — Path(Line(275+175j,275+25j), Arc(275+25j,150+150j,0,0,0,125+175j), Line(125+175j,275+175j)): point(0.2800495767557787)=275+25j, point(0.5)=168.93398282201787+68.93398282201787j; length() ≈ pi*75+300 (accurate to 6 decimal places).
  • A bumpy path (a chain made of Line and Arc segments): point(0.3)=755.31526434+217.51578768j, point(0.5)=832.23324151+156.33454892j, point(0.9)=974.00559321+115.26473532j, point(1.0)=1050+125j; length() ≈ 860.6756221710.

The point and length numbers must be correct to the precision assertAlmostEqual checks (7 decimal places by default, or 6 in the accumulated-error cases that are explicitly noted).

The svg.path.parser module

A function must be exposed:

parse_path(pathdef) -> Path

It takes an SVG path-data string, parses it, and returns a Path built from segment objects that is equivalent. Everything listed below must be supported:

Commands — an uppercase letter means absolute, a lowercase letter means relative to the current point:

  • M/m — moveto. Establishes the current point (which also becomes the start of the current subpath). Extra coordinate pairs after a moveto count as implicit L/l (line) commands.
  • L/l — lineto → Line segments are produced.
  • H/h — horizontal lineto → Line segments are produced.
  • V/v — vertical lineto → Line segments are produced.
  • C/c — cubic Bézier → CubicBezier segments are produced.
  • S/s — smooth cubic Bézier. Its first control point is obtained by reflecting the second control point of the preceding segment about the current point; if the preceding command was not a cubic, the current point itself is used instead. CubicBezier segments are produced.
  • Q/q — quadratic Bézier → QuadraticBezier segments are produced (start, control, end).
  • T/t — smooth quadratic Bézier. Its control point is obtained by reflecting the control point of the preceding quadratic about the current point; if the preceding command was not a quadratic, the current point itself serves as the control point. QuadraticBezier segments are produced.
  • A/a — elliptical arc → Arc segments are produced. The parameters come in this order: radius_x,radius_y rotation large-arc-flag,sweep-flag end_x,end_y.
  • Z/z — closepath. A Line running from the current point back to the start of the current subpath (provided the two differ) is added, and the resulting Path (subpath) is marked as closed.

Several subpaths: Each new M/m opens a fresh subpath. If a subpath is closed by Z/z, the line that closes it goes back to that subpath's own starting point (the latest moveto) rather than to the path's very first point.

Numeric and separator syntax:

  • Whitespace and/or commas, applied interchangeably, may act as separators between coordinates.
  • Whitespace is not required between a command and its arguments (e.g. M100 100L200 200).
  • Numbers are implicitly split by a minus sign, so no whitespace needs to come before it (e.g. c10-5,20-10,30-20 is valid).
  • Scientific notation must be supported: an exponent written with e/E, an optional +/- placed after the exponent marker, and magnitudes going up to at least ±3.4e38 (e.g. M-3.4e38 3.4E+38L-3.4E-38,3.4e-38).

Equivalences that must hold (the parse results are equal Path objects):

  • parse_path('M 100 100 L 200 200') == parse_path('M100 100L200 200').
  • parse_path('M 100 200 L 200 100 L -100 -200') == parse_path('M 100 200 L 200 100 -100 -200') (implicit lineto following explicit lineto coordinates).
  • parse_path('M100,200c10-5,20-10,30-20') == parse_path('M 100 200 c 10 -5 20 -10 30 -20').
  • parse_path('M-3.4e38 3.4E+38L-3.4E-38,3.4e-38') == Path(Line(-3.4e+38+3.4e+38j, -3.4e-38+3.4e-38j)).

Exact parse outcomes (in every case the parse equals the matching constructed Path):

  • 'M 0 0 L 50 20 M 100 100 L 300 100 L 200 300 z' → Path(Line(0+0j,50+20j), Line(100+100j,300+100j), Line(300+100j,200+300j), Line(200+300j,100+100j)) (here z closes back to 100+100j, i.e. the second subpath's start).
  • 'M100,200 C100,100 250,100 250,200 S400,300 400,200' → Path(CubicBezier(100+200j,100+100j,250+100j,250+200j), CubicBezier(250+200j,250+300j,400+300j,400+200j)).
  • 'M100,200 C100,100 400,100 400,200' → Path(CubicBezier(100+200j,100+100j,400+100j,400+200j)).
  • 'M600,800 C625,700 725,700 750,800 S875,900 900,800' → Path(CubicBezier(600+800j,625+700j,725+700j,750+800j), CubicBezier(750+800j,775+900j,875+900j,900+800j)).
  • 'M200,300 Q400,50 600,300 T1000,300' → Path(QuadraticBezier(200+300j,400+50j,600+300j), QuadraticBezier(600+300j,800+550j,1000+300j)).

Generating path data (Path.to_svg)

For line-based paths, Path.to_svg() must output an SVG path-data string able to round-trip through parse_path. Concretely, whenever the Path at hand came from parse_path, running parse_path(pathdef).to_svg() must give back exactly these strings:

  • 'M 100,100 L 300,100 L 200,300 Z' for the input 'M 100,100 L 300,100 L 200,300 Z'.
  • 'M 0,0 L 50,20 M 100,100 L 300,100 L 200,300 Z' for the input 'M 0,0 L 50,20 M 100,100 L 300,100 L 200,300 Z'.

So the emitted format is:

  • M x,y starts off each subpath,
  • L x,y covers the line segments,
  • Z closes off a subpath,
  • one space between consecutive commands, with a comma between the x and the y of every coordinate pair,
  • integer coordinates written with no decimal tail (e.g. 100, not 100.0),
  • a fresh M command emitted at the beginning of every subpath (subpaths after the first included).

Overview
