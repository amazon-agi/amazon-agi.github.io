Summary

The work spans two modules of the workalendar package: a new country calendar class is to be implemented, and an existing one is to be removed.

from workalendar.africa import MadagascarCalendar

It must follow the same conventions as the module's other calendar classes. Specifically, it must expose a holidays_set(year) method, and calling it must return a set-like collection whose elements are all datetime.date objects that represent the public holidays for the year supplied to the method.

When 2013 is the year requested, the holidays that are returned must include exactly these dates (the meaning of each is shown next to it):

  • January 1 — New Year's Day → date(2013, 1, 1)
  • March 29 — Martyrs' Day → date(2013, 3, 29)
  • April 1 — Easter Monday → date(2013, 4, 1)
  • May 1 — Labour Day → date(2013, 5, 1)
  • May 9 — Ascension → date(2013, 5, 9)
  • May 20 — Whit Monday → date(2013, 5, 20)
  • June 26 — Independence Day → date(2013, 6, 26)
  • August 15 — Assumption → date(2013, 8, 15)
  • November 1 — All Saints' Day → date(2013, 11, 1)
  • December 25 — Christmas Day → date(2013, 12, 25)

Notes:

  • Easter Monday, Ascension, and Whit Monday are holidays whose dates are derived from Easter; the fixed dates listed above must be what the correct computation for 2013 produces.

16 The job here is to change the is_working_day method of the Calendar class in the workalendar.core module, such that datetime.datetime objects are handled… 281 words · source specification, reworded by GLM-5.3-Flash
Goal

The job here is to change the is_working_day method of the Calendar class in the workalendar.core module, such that datetime.datetime objects are handled correctly in addition to datetime.date objects.

Context

An instance method is exposed by the Calendar class (located in workalendar/core.py):

def is_working_day(self, day):
    ...

For the day handed to it, the method decides whether that day is a working day (i.e., neither a weekend nor a holiday). At present, when the input is a datetime.date instance the behavior is correct, but when the input is a datetime.datetime instance the results of holiday checks are incorrect.

Behavior That Is Required

Both datetime.date and datetime.datetime instances must be accepted by is_working_day as its day argument. If what gets passed in is a datetime.datetime instance, it must be handled the same way as the corresponding calendar date (that is, the datetime's date portion). In particular, a datetime.datetime and the datetime.date representing the same calendar day must get the same outcome from the holiday determination.

To put this concretely: when a calendar day is a holiday, the method must report it as a non-working day, no matter whether it comes in as a datetime.date or as a datetime.datetime covering that same day.

Example Scenario

Let cal be a calendar instance in which the date January 1, 2014 is a non-working day (a holiday):

cal.is_working_day(datetime.datetime(2014, 1, 1))  # returns False
Constraints
  • For datetime.date inputs, the behavior that exists today must be preserved.
  • The name, location, and signature of the public method (Calendar.is_working_day(self, day) in workalendar.core) must stay unchanged, so that callers and imports that already exist continue to work.
