16 Modify the is_working_day method of the Calendar class in the workalendar.core module so that it correctly handles datetime.datetime objects in addition to… 237 words · source specification
Objective

Modify the is_working_day method of the Calendar class in the workalendar.core module so that it correctly handles datetime.datetime objects in addition to datetime.date objects.

Background

The Calendar class (in workalendar/core.py) exposes an instance method:

def is_working_day(self, day):
    ...

This method determines whether a given day is a working day (i.e., not a weekend and not a holiday). It currently behaves correctly when passed a datetime.date instance, but produces incorrect results for holiday checks when passed a datetime.datetime instance.

Required Behavior

is_working_day must accept both datetime.date and datetime.datetime instances as its day argument. When a datetime.datetime instance is passed, it must be treated identically to the corresponding calendar date (i.e., the date portion of the datetime). Specifically, the holiday determination must produce the same result for a datetime.datetime and for the datetime.date representing the same calendar day.

Concretely: a calendar day that is a holiday must be reported as a non-working day whether it is supplied as a datetime.date or as a datetime.datetime covering that same day.

Example

For a calendar instance cal on which the date January 1, 2014 is a non-working day (a holiday):

cal.is_working_day(datetime.datetime(2014, 1, 1))  # returns False
Constraints
  • Existing behavior for datetime.date inputs must be preserved.
  • The public method name, location, and signature (Calendar.is_working_day(self, day) in workalendar.core) must remain unchanged so existing callers and imports continue to work.
