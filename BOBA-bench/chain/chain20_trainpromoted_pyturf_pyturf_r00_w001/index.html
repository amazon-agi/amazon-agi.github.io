Task: Build a center Function for GeoJSON Geometries

Goal

The task is to create a module that computes the geographic center point of a GeoJSON input. By definition, the center is the midpoint of the bounding box enclosing all coordinates of the input geometry (or geometries).

Public API

Make the module importable as:

from turf.center import center

A callable must be exposed by the module:

center(features)
  • Parameter features: a GeoJSON object. It may be a Feature, a FeatureCollection, or a raw geometry. Regarding geometry types, the supported ones are: Point, MultiPoint, LineString, MultiLineString, Polygon, and MultiPolygon.
  • Returns: a GeoJSON Feature that has a Point as its geometry.

Behavior

  1. Gather every coordinate present in the input, across all of its features/geometries.
  2. Derive the axis-aligned bounding box of those coordinates:
    • min_x is the minimum longitude, max_x is the maximum longitude
    • min_y is the minimum latitude, max_y is the maximum latitude
  3. Compute the center point as follows:
    • x = (min_x + max_x) / 2
    • y = (min_y + max_y) / 2
  4. Return a GeoJSON Feature matching the following exact structure:
{
  "type": "Feature",
  "properties": {},
  "geometry": {
    "type": "Point",
    "coordinates": [x, y]
  }
}

Whatever the input's properties are, the properties value must always be an empty object. The coordinate order of the returned feature is [longitude, latitude].

Examples of the expected results
  • When the input is a single Point feature, the call returns a Feature whose point coordinates equal the input point's coordinates.
  • For a LineString with two endpoints, the call returns the midpoint of those endpoints (per the bounding-box midpoint rule above).
  • When the input is a FeatureCollection of several points, the call returns the midpoint of the collection's bounding box.
  • For a FeatureCollection of multiple polygons, the call returns the midpoint of the combined bounding box of all polygon coordinates.
  • When the input is a single Polygon, the call returns the midpoint of its bounding box.

Note: The center is derived purely from the coordinate extents. Any per-feature properties (e.g., weight-like properties) that the input contains do not affect the result — only the coordinate bounding box matters.

Input Validation and Error Behavior

Whenever the input is not a valid GeoJSON object of an allowed geometry type — for example, a bare string or a bare number — the function must raise the exception:

from turf.utils.exceptions import InvalidInput

The message of the raised InvalidInput exception must equal:

from turf.utils.error_codes import error_code_messages
error_code_messages["InvalidGeometry"](
    ["Point", "MultiPoint", "LineString", "MultiLineString", "Polygon", "MultiPolygon"]
)

In other words, the InvalidGeometry error message must be produced using the list of allowed geometry types shown above (in that order).

Notes

  • Results are compared by structural equality on the returned GeoJSON Feature (the type, the empty properties, and the point geometry with its computed coordinates).
  • You may make use of the shared utilities available under turf.utils (e.g., error_code_messages, InvalidInput) for validation and error reporting.
02 Write a function that turns a bounding box into a GeoJSON Feature whose geometry is a rectangular Polygon. 425 words · source specification, reworded by GLM-5.3-Flash

Task: Build a bbox_polygon module

Goal

Write a function that turns a bounding box into a GeoJSON Feature whose geometry is a rectangular Polygon.

Public API

Create a module at turf/bbox_polygon that exposes a function importable as:

from turf.bbox_polygon import bbox_polygon
Function Signature
def bbox_polygon(bbox):
    ...

Input

bbox is a bounding box supplied as a sequence of exactly four elements, arranged in this order:

[west, south, east, north]

i.e. [min_x, min_y, max_x, max_y].

The four elements may each be given as numeric values (ints/floats) or as numeric strings (e.g. ["0", "0", "10", "10"]). When coordinates are computed, numeric strings must be accepted and interpreted as their numeric values.

Output

Return a GeoJSON Feature (in the form of a plain Python dict) that has exactly the following structure:

{
    "type": "Feature",
    "bbox": <the original bbox input, unchanged>,
    "properties": {},
    "geometry": {
        "type": "Polygon",
        "coordinates": [
            [
                [west, south],
                [east, south],
                [east, north],
                [west, north],
                [west, south],
            ]
        ]
    }
}

Requirements that apply to the output:

  • The "bbox" field must contain the input value exactly as it was provided (if strings were passed in, the strings are preserved here; if ints were passed in, the ints are preserved here).
  • The polygon coordinates must be numeric float values derived from the input elements, which may be strings. For example, an input element "0" or 0 yields the float 0.0, and "10" or 10 yields 10.0.
  • The polygon ring consists of exactly 5 coordinate pairs and forms a closed rectangle in which the first and last coordinate pairs are identical ([west, south]).
  • The value under "properties" is always an empty dict.

Error Behaviour

The function must raise the exception InvalidInput (importable from turf.utils.exceptions) when the input is not a valid bounding box. Situations covered by this include:

  • An input that fails to be a valid four-element bounding box sequence (e.g. a bare string such as "xyz").
  • An input sequence that is not exactly 4 elements in length (e.g. a 6-element list).

The message of the raised exception must equal error_code_messages["InvalidBoundingBox"], with error_code_messages provided in turf.utils.error_codes.

Relationship to Existing Utilities

The Feature that gets produced must be compatible with turf.invariant.get_coords_from_features, so that extracting coordinates from the returned feature yields the polygon's coordinate ring structure described above (a list that contains a single ring of 5 coordinate pairs).

If the error code key "InvalidBoundingBox" is not already present in turf.utils.error_codes.error_code_messages, add it along with a suitable descriptive message.

03 Write a module that computes the mean (average) centroid of the coordinates found in a GeoJSON input and returns the result as a GeoJSON Point Feature. 546 words · source specification, reworded by GLM-5.3-Flash

Task: Provide a centroid Function for GeoJSON Geometries

Goal

Write a module that computes the mean (average) centroid of the coordinates found in a GeoJSON input and returns the result as a GeoJSON Point Feature.

Public interface

The module must be importable as:

from turf.centroid import centroid

The signature of the function must be:

def centroid(geojson, options=None):
    ...
  • geojson: the GeoJSON object given as input (Feature, FeatureCollection, or raw geometry), or a coordinate structure.
  • options: a dictionary that is optional. It may contain a "properties" key whose value is a dictionary. Once provided, that dictionary becomes the properties of the returned Feature. If options is not provided (or does not supply properties), the properties of the returned Feature must be an empty dictionary {}.

Behavior of the function

The function determines the centroid by gathering every coordinate present in the input geometry/geometries, adding them component-wise, and dividing each component by the total number of coordinates gathered. Put another way, it is the arithmetic mean of all [longitude, latitude] coordinate pairs found across the input.

Rules for coordinate collection
  • All vertex coordinates from the geometry are included in the average and are treated equally. This holds uniformly across the supported geometry types:
    • Point — the single coordinate it contains.
    • MultiPoint — each of its point coordinates.
    • LineString — each vertex.
    • MultiLineString — each vertex of every line.
    • Polygon — each vertex of every ring (the repeated closing vertex included, i.e., no de-duplication of coordinates).
    • MultiPolygon — each vertex of every ring in every polygon.
  • For a FeatureCollection, the coordinates of all features it contains are pooled together and averaged as a single set.
Returned value

The function returns a GeoJSON Feature of the following form:

{
  "type": "Feature",
  "properties": <properties from options, or {}>,
  "geometry": {
    "type": "Point",
    "coordinates": [<mean longitude>, <mean latitude>]
  }
}

The coordinates are the mean of longitude and latitude as computed, preserved as full-precision floating point values (no rounding).

For an input that is a single Point, the returned coordinates equal the coordinates of that point exactly.

Validation of Input and Errors

Validation errors must raise this exception:

from turf.utils.exceptions import InvalidInput

The error messages must be taken from the shared message table:

from turf.utils.error_codes import error_code_messages

There are two required error conditions:

  1. Geometry type is invalid. If the input cannot be interpreted as a valid GeoJSON geometry of one of the supported types, raise InvalidInput with the message produced by:

    error_code_messages["InvalidGeometry"](allowed_types)

    where allowed_types is the list:

    ["Point", "MultiPoint", "LineString", "MultiLineString", "Polygon", "MultiPolygon"]

    As an example, a plain string such as "xyz" must trigger this error.

  2. Point input is invalid. If the input is a coordinate list that does not contain a valid coordinate pair (for instance, a list with only one element such as [1]), raise InvalidInput with the message:

    error_code_messages["InvalidPointInput"]

The type of the raised exception object must be exactly InvalidInput, and its string representation must equal the corresponding message above.

Notes

  • The geometry types that are supported are exactly the ones listed in allowed_types above.
  • Coordinates come as [longitude, latitude] pairs.

Task Specification: Implementing the envelope Package

Summary

Introduce a new envelope module inside the turf package. The envelope function calculates the bounding rectangle (expressed as a GeoJSON Polygon Feature) that encloses all coordinates of the input GeoJSON geometry, feature, or feature collection.

In addition, ensure that the existing bbox functionality handles a mixed FeatureCollection correctly (the behavior is described below — no new API is required for bbox; the only requirement is that it produces the correct bounding box for such inputs).

Public interface

It must be possible to import the module as follows:

from turf.envelope import envelope
Signature of the function
def envelope(geojson):
    ...
  • Input: A GeoJSON object, which may be a Feature, a bare geometry, or a FeatureCollection. The geometry types that are supported include Point, LineString, MultiLineString, Polygon, and MultiPolygon.
  • Output: A GeoJSON Feature (given as a Python dict) whose geometry is a Polygon that represents the axis-aligned bounding rectangle of all coordinates in the input.

Behavior

Computing the bounding box

Find the minimum and maximum longitude (x) and latitude (y) over all coordinates present in the input geometry/features. Refer to these as min_x, min_y, max_x, max_y.

  • When the input is a FeatureCollection, coordinates coming from every feature contribute to the overall bounds.
  • Nested coordinate structures (rings, multi-geometries) are traversed in full.
Shape of the output

The object that is returned must be a dict having exactly the following top-level keys, in this form:

{
    "type": "Feature",
    "bbox": [min_x, min_y, max_x, max_y],
    "properties": {},
    "geometry": {
        "type": "Polygon",
        "coordinates": [
            [
                [min_x, min_y],
                [max_x, min_y],
                [max_x, max_y],
                [min_x, max_y],
                [min_x, min_y]
            ]
        ]
    }
}

Details:

  • "bbox" is a list of the form [min_x, min_y, max_x, max_y].
  • "properties" is always an empty dict {} (regardless of any properties the input carries).
  • The Polygon ring consists of five positions; it begins at the lower-left corner and proceeds: lower-left → lower-right → upper-right → upper-left → lower-left (which closes the ring). Each position is a [x, y] list with 2 elements.
  • Numeric values must retain the type they have in the input coordinates (e.g., integer inputs yield integers, float inputs yield floats) — do not force conversion.
Edge cases
  • Point input: here min_x == max_x and min_y == max_y. The output is still a valid closed Polygon ring with 5 positions in which all corners coincide at the single point, and "bbox" is [x, y, x, y].
  • Polygon with holes / MultiPolygon-style nested coordinates: all coordinate positions across all rings (inner rings included) are taken into account when the bounds are computed.
Worked examples
  • A LineString whose coordinates are [[102, -10], [103, 1], [104, 0], [130, 4]] produces "bbox": [102, -10, 130, 4].
  • A MultiLineString with coordinates [[[100.0, 0.0], [101.0, 1.0]], [[102.0, 2.0], [103.0, 3.0]]] produces "bbox": [100.0, 0.0, 103.0, 3.0].
  • A Polygon made up of the single ring [[101, 0], [101, 1], [100, 1], [100, 0], [101, 0]] produces "bbox": [100, 0, 101, 1].
  • A Point located at [102, 0.5] produces "bbox": [102, 0.5, 102, 0.5].
  • A FeatureCollection that contains a Point [102.0, 0.5], a LineString [[102.0, -10.0], [103.0, 1.0], [104.0, 0.0], [130.0, 4.0]], and a Polygon whose ring is [[20.0, 0.0], [101.0, 0.0], [101.0, 1.0], [100.0, 1.0], [100.0, 0.0]] produces "bbox": [20, -10, 130, 4].

Related requirement: bbox with a mixed FeatureCollection

Given a FeatureCollection that combines multiple geometry types, the existing bounding-box computation must return the correct enclosing box. For the FeatureCollection example above (Point, LineString, and Polygon), the bounding box that results is [20, -10, 130, 4] (that is, [min_x, min_y, max_x, max_y] spanning all features).

Beyond what already exists, this task requires no changes to the behavior of the midpoint module; the midpoint fixtures act as inputs only and place no new implementation requirement here.

Package layout

Build the turf/envelope/ package so that from turf.envelope import envelope resolves to the function described above.

You will be working in turf, a geospatial library offering helper functions for constructing GeoJSON objects. What this task requires is a modification of the feature-construction helpers that already exist and the addition of two new helper functions, together with the infrastructure that supports them.

Module: turf/helpers/_features.py

Helper functions and classes for constructing GeoJSON geometries and features are exposed by this module. From turf.helpers._features, the public names below must be importable:

  • point
  • points
  • multi_point
  • line_string
  • line_strings (implied by existing usage)
  • multi_line_string
  • polygon
  • polygons (implied by existing usage)
  • multi_polygon
  • feature (new)

Required change: the as_geojson parameter

A keyword argument as_geojson (boolean) must be accepted by all of the geometry/feature constructor functions (point, points, multi_point, line_string, line_strings, multi_line_string, polygon, polygons, multi_polygon, feature, feature_collection).

  • Default behavior (as_geojson omitted / True): what the function returns is a plain GeoJSON representation — put differently, a dict-like object on which the mapping method .get(key) is available (e.g. obj.get("properties"), obj.get("geometry"), obj.get("features")).
  • When as_geojson=False: what the function returns is a rich object instance; attribute access (e.g. .geometry, .properties, .type, .id, .features, and .geometry.coordinates) is how its data is exposed, and the instance additionally provides a .to_geojson() method that returns the plain GeoJSON dict.

The two return forms must both represent the same underlying GeoJSON data.

point(coordinates, properties=None, ..., as_geojson=...)

Creates a Point feature.

  • coordinates: a two-element [x, y] sequence.
  • properties: an optional dict; should it be omitted, the resulting feature's properties are an empty dict {}.
  • The object form (as_geojson=False) exposes:
    • .geometry.coordinates[0], .geometry.coordinates[1]
    • .properties (dict)
  • On the object form, .to_geojson() returns exactly:
    {
    "geometry": {"coordinates": [0, 0], "type": "Point"},
    "properties": {},
    "type": "Feature",
}
    (with the input point([0, 0], as_geojson=False)).
points(coordinates, properties=None, options=None, ..., as_geojson=...)

Creates a FeatureCollection made up of Point features.

  • coordinates: a list whose entries are [x, y] pairs.
  • properties: an optional dict applied to the features.
  • A third positional argument may carry options at the collection level, an id among them (e.g. {"id": "hello"}).
  • The object form exposes:
    • .features (a sequence; the number of points is what len(...) gives)
    • .id (populated from the id option that was provided, e.g. "hello")
multi_point(coordinates, properties=None, ..., as_geojson=...)

Creates a MultiPoint feature.

  • The object form exposes .type == "Feature" and .properties (dict).
line_string(coordinates, properties=None, ..., as_geojson=...)

Creates a LineString feature.

  • coordinates: a list whose entries are [x, y] pairs.
  • properties: an optional dict; should it be omitted, .properties is {}.
  • The object form exposes .geometry.coordinates (a nested list) and .properties.
  • .to_geojson() returns exactly:
    {
    "geometry": {"coordinates": [[5, 10], [20, 40]], "type": "LineString"},
    "properties": {},   # or the supplied properties
    "type": "Feature",
}
line_strings(coordinates, properties=None, options=None, ..., as_geojson=...)

Creates a FeatureCollection made up of LineString features.

  • The object form exposes .features (len(...) supplies the count) and .id.
multi_line_string(coordinates, properties=None, ..., as_geojson=...)

Creates a MultiLineString feature.

  • The object form exposes .type == "Feature" and .properties.
polygon(coordinates, properties=None, ..., as_geojson=...)

Creates a Polygon feature.

  • coordinates: a list made up of linear rings.
  • properties: optional; should it be omitted, .properties is {}.
  • The object form exposes .geometry.coordinates in nested form.
  • The dict that .to_geojson() returns takes this form:
    {
    "geometry": {"coordinates": [...], "type": "Polygon"},
    "properties": {...},
    "type": "Feature",
}
polygons(...) / multi_polygon(...)

These follow the same pattern as the constructors above: polygons results in a FeatureCollection that has .features and .id, while multi_polygon results in a MultiPolygon feature that has .type == "Feature" and .properties.

Accepted inputs

  • vertical_distance = north - south

Normative definition of the nearest point

Before either geographic distance method is applied, the candidate for a segment is determined. This step is the same for geodesic and planar, and it takes place directly in the raw two-dimensional longitude/latitude coordinate plane.

With P the input point, A the segment start, and B the segment end, let:

v = B - A
w = P - A
s = w · v
n = v · v

For the segment in question, the candidate Q is obtained via the clamped Euclidean projection:

Q = A                         if s <= 0
Q = B                         if n <= s
Q = A + (s / n) * v           otherwise

Obtuse configurations therefore take the appropriate endpoint, while an orthogonal projection that falls within the segment takes the interpolated interior point. A consecutive segment that has zero length resolves to its endpoint through the first case. Procedure for deterministic tangent selection

Selection and output ordering are defined by the procedure that follows. For concave polygons, and for points that do not have two unique mathematical tangents, this procedure is the authoritative source.

1. Ring and traversal conventions

Take each closed outer ring, written as:

[v0, v1, ..., v(n-1), v0]

and treat v0 through v(n-1) as its n distinct traversal positions; the trailing v0 is the GeoJSON closing copy. Scan the distinct positions one time, going forward in the order supplied. v(n-1) serves as the cyclic predecessor of v0, and v0 serves as the cyclic successor of v(n-1). Never reverse a ring on the basis of its winding, and never stop the scan early.

For a MultiPolygon, scan the outer ring of the first constituent polygon completely, then the outer ring of the second constituent polygon, and so on. Candidate values that one ring produces carry over into the next ring.

2. The cross product

For positions A, B, and C, define the signed planar cross product:

cross(A, B, C) =
    (B.x - A.x) * (C.y - A.y)
    - (B.y - A.y) * (C.x - A.x)

A positive value means C lies strictly to the left of the directed line A -> B; a negative value means it lies strictly to the right; a zero value is collinear. The calculation is done directly in the input coordinate plane, not with spherical bearings.

3. Starting candidates and the nearest-vertex rule

Set both candidates at the start to v0 of the first constituent polygon's outer ring:

right = first_outer_vertex
left  = first_outer_vertex

Compute the polygon's overall bounding box [minX, minY, maxX, maxY]. The nearest-vertex initialization comes into play only when the query position P is strictly inside that box:

minX < P.x < maxX and minY < P.y < maxY

A point lying on any bounding-box edge does not satisfy this condition.

If the condition holds, locate the outer-ring vertex N nearest to P by geodesic Haversine distance. In radians, the comparison uses:

a = sin²((latN - latP) / 2)
    + sin²((lonN - lonP) / 2) * cos(latP) * cos(latN)
angular_distance = 2 * atan2(sqrt(a), sqrt(1 - a))

Before this calculation, longitudes and latitudes are converted from degrees. Selection is unaffected by any constant Earth-radius multiplier. Take outer-ring positions in constituent-polygon order and in ring order, with each explicitly listed closing position included. In the case of an exact distance tie, the first position encountered is the one selected; consequently, replacement on the basis of distance happens only for a strictly smaller distance.

Seed the candidates from the nearest vertex as follows:

right = N
if N.y < P.y:
    left = N

The comparison N.y < P.y is a strict one. Should it be false, left remains the first outer-ring vertex. The scan afterwards still begins at the first listed vertex of each ring; the role of N is to seed candidates, not to rotate or shorten the scan.

4. The full orientation scan

For each outer ring, seed the previous-edge orientation independently from that ring's closing edge:

previous = cross(v(n-1), v0, P)

Then, for every i from 0 through n - 1 in forward order, set:

current = vi
next_vertex = v((i + 1) mod n)
next = cross(current, next_vertex, P)

Apply exactly the following candidate updates:

if previous <= 0 and next > 0 and cross(P, right, current) <= 0:
    right = current
elif previous > 0 and next <= 0 and cross(P, left, current) >= 0:
    left = current

previous = next

As a result, the edge-orientation transition comparisons intentionally combine non-strict and strict inequalities: <= 0 to > 0 for a right-candidate event, and > 0 to <= 0 for a left-candidate event. Collinearity is also intentionally permitted in candidate replacement, via <= 0 and >= 0. Even if the candidates do not change, complete every ring's full n-position scan.

from turf.boolean_point_on_line import boolean_point_on_line

The module must be located at turf/boolean_point_on_line/ and must expose boolean_point_on_line at that package level.

Signature

def boolean_point_on_line(point, line, options=None):
    ...
Arguments
  • point: A GeoJSON Point. It may be supplied as a GeoJSON Feature wrapping a Point geometry, as a bare Point geometry, or as a raw coordinate pair [x, y]. The function must accept the Feature form (this is the form callers use).
  • line: A GeoJSON LineString. It may be supplied as a GeoJSON Feature wrapping a LineString geometry, as a bare LineString geometry, or as a raw list of coordinate pairs. The Feature form must be accepted by the function.
  • options: An optional dict that controls behavior. It may be None, or it may be an empty dict. The supported key is:
    • "ignoreEndVertices" (bool, default False): When True, the line's two endpoints (the very first and very last vertices of the LineString) are treated as NOT being on the line. When False or absent, the endpoints count as being on the line.
Value Returned

The return value is a bool:

  • True when the point is on the line (subject to the ignoreEndVertices rule).
  • False otherwise.

Details of the Behavior

A point is regarded as "on the line" if any of the line's segments contains it (i.e., the point is collinear with the two endpoints of a segment and falls within the segment's bounding box, inclusive of the segment's vertices). The following are included:

  • Points that coincide exactly with any vertex of the line.
  • Points that lie strictly between two consecutive vertices of a segment (interior points, including non-integer midpoints of a segment).

The point is False (not on the line) whenever it does not lie on any of the line's segments.

Rule for ignoreEndVertices

If options["ignoreEndVertices"] is True:

  • A point coinciding with the first vertex of the LineString returns False.
  • A point coinciding with the last vertex of the LineString returns False.
  • A point that lies on the interior of the first or last segment (but not at the extreme endpoint vertices) still returns True.
  • A point coinciding with an intermediate (mid) vertex of the line still returns True.

When ignoreEndVertices is False or is not provided:

  • Points that coincide with the first or last vertex return True (as long as they are genuinely on the line).
Examples of the expected results

When ignoreEndVertices = True:

  • Point that equals the start vertex of the line → False.
  • Point that equals the end vertex of the line → False.
  • Point located on the interior of the first segment (not at either shared vertex) → True.
  • Point that equals a middle vertex of a multi-segment line → True.
  • Point on the interior of the last segment → True.
  • Point on a single-segment line that lies strictly between its two endpoints → True.
  • Point on a single-segment line that is equal to either endpoint → False.
  • A point that does not lie on any segment → False.

When ignoreEndVertices is absent or False:

  • Point that equals the start vertex → True.
  • Point that equals the end vertex → True.
  • Point that equals a midpoint of a segment → True.
  • Point that equals a middle vertex → True.

Remarks

  • The collinearity/on-segment check must correctly handle vertical segments, horizontal segments, and diagonal segments.
  • The coordinates may be integers or floating-point values.
  • The function must unwrap the Feature/geometry structure correctly in order to obtain the point coordinate and the list of line coordinates.
