01 Create a module that computes the geographic center point of a GeoJSON input. 458 words · source specification

Task: Implement a center Function for GeoJSON Geometries

Objective

Create a module that computes the geographic center point of a GeoJSON input. The center is defined as the midpoint of the bounding box that encloses all coordinates of the input geometry (or geometries).

Public API

Create a module importable as:

from turf.center import center

The module must expose a callable:

center(features)
  • Parameter features: a GeoJSON object. This may be a Feature, a FeatureCollection, or a raw geometry. Supported geometry types are: Point, MultiPoint, LineString, MultiLineString, Polygon, and MultiPolygon.
  • Returns: a GeoJSON Feature whose geometry is a Point.

Behavior

  1. Collect every coordinate present in the input across all its features/geometries.
  2. Determine the axis-aligned bounding box of those coordinates:
    • min_x = minimum longitude, max_x = maximum longitude
    • min_y = minimum latitude, max_y = maximum latitude
  3. Compute the center point as:
    • x = (min_x + max_x) / 2
    • y = (min_y + max_y) / 2
  4. Return a GeoJSON Feature of the following exact structure:
{
  "type": "Feature",
  "properties": {},
  "geometry": {
    "type": "Point",
    "coordinates": [x, y]
  }
}

The properties value must always be an empty object, regardless of the input's properties. The returned coordinate order is [longitude, latitude].

Examples of expected results
  • A single Point feature returns a Feature whose point coordinates equal the input point's coordinates.
  • A LineString with two endpoints returns the midpoint of those endpoints (per the bounding-box midpoint rule above).
  • A FeatureCollection of several points returns the midpoint of the collection's bounding box.
  • A FeatureCollection of multiple polygons returns the midpoint of the combined bounding box of all polygon coordinates.
  • A single Polygon returns the midpoint of its bounding box.

Note: The center is computed purely from coordinate extents. Any per-feature properties (e.g., weight-like properties) present in the input do not influence the result — only the coordinate bounding box matters.

Input Validation and Errors

If the input is not a valid GeoJSON object of an allowed geometry type — for example a bare string or a bare number — the function must raise the exception:

from turf.utils.exceptions import InvalidInput

The raised InvalidInput exception's message must equal:

from turf.utils.error_codes import error_code_messages
error_code_messages["InvalidGeometry"](
    ["Point", "MultiPoint", "LineString", "MultiLineString", "Polygon", "MultiPolygon"]
)

That is, the InvalidGeometry error message must be produced with the list of allowed geometry types shown above (in that order).

Notes

  • The comparison of results is a structural equality on the returned GeoJSON Feature (type, empty properties, and the point geometry with its computed coordinates).
  • You may rely on shared utilities available under turf.utils (e.g., error_code_messages, InvalidInput) for validation and error reporting.

[west, south, east, north]

i.e. [min_x, min_y, max_x, max_y].

The four elements may be numeric values (ints/floats) or numeric strings (e.g. ["0", "0", "10", "10"]). Numeric strings must be accepted and interpreted as their numeric values when computing coordinates.

Task: Implement a centroid Function for GeoJSON Geometries

Objective

Create a module that computes the mean (average) centroid of the coordinates in a GeoJSON input and returns it as a GeoJSON Point Feature.

Public API

Create a module importable as:

from turf.centroid import centroid

The function signature must be:

def centroid(geojson, options=None):
    ...
  • geojson: the input GeoJSON object (Feature, FeatureCollection, or raw geometry) or a coordinate structure.
  • options: an optional dictionary. It may contain a "properties" key whose value is a dictionary. When provided, that dictionary becomes the properties of the returned Feature. When options is not provided (or does not supply properties), the returned Feature's properties must be an empty dictionary {}.

Behavior

The function computes the centroid by collecting every coordinate present in the input geometry/geometries, summing them component-wise, and dividing each component by the total number of coordinates collected. In other words, it is the arithmetic mean of all [longitude, latitude] coordinate pairs found across the input.

Coordinate collection rules
  • All vertex coordinates from the geometry are included in the average, treated equally. This applies uniformly across supported geometry types:
    • Point — its single coordinate.
    • MultiPoint — each point coordinate.
    • LineString — each vertex.
    • MultiLineString — each vertex of every line.
    • Polygon — each vertex of every ring (including the repeated closing vertex, i.e., no de-duplication of coordinates).
    • MultiPolygon — each vertex of every ring of every polygon.
  • For a FeatureCollection, coordinates from all contained features are pooled together and averaged as a single set.
Return value

The function returns a GeoJSON Feature with:

{
  "type": "Feature",
  "properties": <properties from options, or {}>,
  "geometry": {
    "type": "Point",
    "coordinates": [<mean longitude>, <mean latitude>]
  }
}

The coordinates are the computed mean of longitude and latitude, kept as full-precision floating point values (no rounding).

For a single Point input, the returned coordinates equal that point's coordinates exactly.

Input Validation and Errors

Validation errors must raise the exception:

from turf.utils.exceptions import InvalidInput

The error messages must come from the shared message table:

from turf.utils.error_codes import error_code_messages

Two error conditions are required:

  1. Invalid geometry type. If the input cannot be interpreted as a valid GeoJSON geometry of one of the supported types, raise InvalidInput with the message produced by:

    error_code_messages["InvalidGeometry"](allowed_types)

    where allowed_types is the list:

    ["Point", "MultiPoint", "LineString", "MultiLineString", "Polygon", "MultiPolygon"]

    For example, a plain string such as "xyz" must trigger this error.

  2. Invalid point input. If the input is a coordinate list that does not contain a valid coordinate pair (for example, a list with a single element such as [1]), raise InvalidInput with the message:

    error_code_messages["InvalidPointInput"]

The raised exception object's type must be exactly InvalidInput, and its string representation must equal the corresponding message above.

Notes

  • Supported geometry types are exactly those listed in allowed_types above.
  • Coordinates are [longitude, latitude] pairs.

Task Specification: Implement the envelope Package

Overview

Add a new envelope module to the turf package. The envelope function computes the bounding rectangle (as a GeoJSON Polygon Feature) that encloses all coordinates in the input GeoJSON geometry, feature, or feature collection.

Additionally, ensure the existing bbox functionality correctly handles a mixed FeatureCollection (see the behavior described below — no new API is required for bbox, only that it produces the correct bounding box for such inputs).

Public API

The module must be importable as:

from turf.envelope import envelope
Function signature
def envelope(geojson):
    ...
  • Input: A GeoJSON object. This may be a Feature, a bare geometry, or a FeatureCollection. Supported geometry types include Point, LineString, MultiLineString, Polygon, and MultiPolygon.
  • Output: A GeoJSON Feature (as a Python dict) whose geometry is a Polygon representing the axis-aligned bounding rectangle of all coordinates in the input.

Behavior

Bounding box computation

Determine the minimum and maximum longitude (x) and latitude (y) across all coordinates present in the input geometry/features. Let these be min_x, min_y, max_x, max_y.

  • For a FeatureCollection, coordinates from every feature contribute to the overall bounds.
  • Nested coordinate structures (rings, multi-geometries) are traversed fully.
Output structure

The returned object must be a dict with exactly the following top-level keys, in this form:

{
    "type": "Feature",
    "bbox": [min_x, min_y, max_x, max_y],
    "properties": {},
    "geometry": {
        "type": "Polygon",
        "coordinates": [
            [
                [min_x, min_y],
                [max_x, min_y],
                [max_x, max_y],
                [min_x, max_y],
                [min_x, min_y]
            ]
        ]
    }
}

Details:

  • "bbox" is a list [min_x, min_y, max_x, max_y].
  • "properties" is always an empty dict {} (regardless of any properties on the input).
  • The Polygon ring lists five positions, starting at the lower-left corner and proceeding: lower-left → lower-right → upper-right → upper-left → lower-left (closing the ring). Each position is a 2-element [x, y] list.
  • Numeric values must preserve their type from the input coordinates (e.g., integer inputs yield integers, float inputs yield floats) — do not force conversion.
Edge cases
  • Point input: min_x == max_x and min_y == max_y. The output is still a valid closed 5-position Polygon ring where all corners coincide at the single point, and "bbox" is [x, y, x, y].
  • Polygon with holes / MultiPolygon-style nested coordinates: all coordinate positions across all rings (including inner rings) are considered when computing the bounds.
Worked examples
  • A LineString with coordinates [[102, -10], [103, 1], [104, 0], [130, 4]] produces "bbox": [102, -10, 130, 4].
  • A MultiLineString with coordinates [[[100.0, 0.0], [101.0, 1.0]], [[102.0, 2.0], [103.0, 3.0]]] produces "bbox": [100.0, 0.0, 103.0, 3.0].
  • A Polygon with the single ring [[101, 0], [101, 1], [100, 1], [100, 0], [101, 0]] produces "bbox": [100, 0, 101, 1].
  • A Point at [102, 0.5] produces "bbox": [102, 0.5, 102, 0.5].
  • A FeatureCollection containing a Point [102.0, 0.5], a LineString [[102.0, -10.0], [103.0, 1.0], [104.0, 0.0], [130.0, 4.0]], and a Polygon with ring [[20.0, 0.0], [101.0, 0.0], [101.0, 1.0], [100.0, 1.0], [100.0, 0.0]] produces "bbox": [20, -10, 130, 4].

Related requirement: bbox over a mixed FeatureCollection

The existing bounding-box computation must return the correct enclosing box for a FeatureCollection combining multiple geometry types. For the FeatureCollection example above (Point, LineString, and Polygon), the resulting bounding box is [20, -10, 130, 4] (i.e., [min_x, min_y, max_x, max_y] spanning all features).

No changes to the midpoint module's behavior are required by this task beyond what already exists; the midpoint fixtures are inputs only and impose no new implementation requirement here.

Package structure

Create the turf/envelope/ package such that from turf.envelope import envelope resolves to the described function.

v = B - A
w = P - A
s = w · v
n = v · v

Q = A                         if s <= 0
Q = B                         if n <= s
Q = A + (s / n) * v           otherwise

Function Signature

def boolean_point_on_line(point, line, options=None):
    ...
Parameters
  • point: A GeoJSON Point. It may be provided as a GeoJSON Feature wrapping a Point geometry, a bare Point geometry, or a raw coordinate pair [x, y]. The function must accept the Feature form (that is the form used by callers).
  • line: A GeoJSON LineString. It may be provided as a GeoJSON Feature wrapping a LineString geometry, a bare LineString geometry, or a raw list of coordinate pairs. The function must accept the Feature form.
  • options: An optional dict controlling behavior. It may be None or an empty dict. Supported key:
    • "ignoreEndVertices" (bool, default False): When True, the two endpoints of the line (the very first and very last vertices of the LineString) are treated as NOT being on the line. When False or absent, endpoints count as being on the line.
Return Value

Returns a bool:

  • True if the point is on the line (subject to the ignoreEndVertices rule).
  • False otherwise.

Behavior Details

The point is considered "on the line" if it lies on any of the line's segments (i.e., it is collinear with the two endpoints of a segment and falls within the segment's bounding box, inclusive of the segment's vertices). This includes:

  • Points coinciding exactly with any vertex of the line.
  • Points lying strictly between two consecutive vertices on a segment (interior points, including non-integer midpoints of a segment).

The point is False (not on the line) when it does not lie on any segment of the line.

The ignoreEndVertices rule

When options["ignoreEndVertices"] is True:

  • A point that coincides with the first vertex of the LineString returns False.
  • A point that coincides with the last vertex of the LineString returns False.
  • A point lying on the interior of the first or last segment (but not at the extreme endpoint vertices) still returns True.
  • A point coinciding with an intermediate (mid) vertex of the line still returns True.

When ignoreEndVertices is False or not provided:

  • Points coinciding with the first or last vertex return True (assuming they are genuinely on the line).
Examples of expected outcomes

With ignoreEndVertices = True:

  • Point equal to the start vertex of the line → False.
  • Point equal to the end vertex of the line → False.
  • Point lying on the interior of the first segment (not at either shared vertex) → True.
  • Point equal to a middle vertex of a multi-segment line → True.
  • Point on the interior of the last segment → True.
  • Point on a single-segment line strictly between its two endpoints → True.
  • Point on a single-segment line equal to either endpoint → False.
  • A point not lying on any segment → False.

With ignoreEndVertices absent/False:

  • Point equal to the start vertex → True.
  • Point equal to the end vertex → True.
  • Point equal to a midpoint of a segment → True.
  • Point equal to a middle vertex → True.

Notes

  • The collinearity/on-segment check must handle vertical segments, horizontal segments, and diagonal segments correctly.
  • Coordinates may be integers or floating-point values.
  • The function must correctly unwrap the Feature/geometry structure to obtain the point coordinate and the list of line coordinates.
