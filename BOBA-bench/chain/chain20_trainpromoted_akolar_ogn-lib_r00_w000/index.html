Task Specification: Implement an OGN (APRS) Client

Overview

Build a Python package named ogn_lib that offers a client for connecting to an APRS (Automatic Packet Reporting System) server, authenticating, and sending messages. The exception types and client API described below must be exposed by the package.

Package Layout and Public API

Top-level package: ogn_lib

The client class must be re-exported by the package so that it is available directly as ogn_lib.OgnClient:

import ogn_lib

client_class = ogn_lib.OgnClient
Module: ogn_lib.exceptions

The following exception classes must be defined:

  • ParseError — raised when a response from the server cannot be interpreted.
  • LoginError — raised for protocol errors during login/authentication.

Both classes may derive directly from Exception or from a shared exception base. No additional behavior is required.

Module: ogn_lib.client

OgnClient must be defined in this module.

Class: ogn_lib.client.OgnClient

Constants at class level

OgnClient must define:

  • APRS_SERVER — the default hostname of the APRS server, as a string.
  • APRS_PORT_FULL — the integer port for a full, unfiltered feed.
  • APRS_PORT_FILTER — the integer port for a filtered feed.

APRS_PORT_FULL and APRS_PORT_FILTER must have different values.

Constructor
OgnClient(username, passcode='-1', server=None, port=None, filter_=None)

The constructor must support positional and keyword arguments in the form shown, and it must retain the supplied connection and authentication values.

  • username is required. The instance stores it, and it is used in the authentication message.
  • passcode defaults to the string '-1'. It, too, is stored on the instance and used in the authentication message.
  • server determines the hostname:
    • When a value that is not None is supplied, instance.server must equal that value.
    • Otherwise, instance.server must equal APRS_SERVER.
  • port determines the connection port; a value that is explicitly supplied takes precedence over the filter-based defaults:
    • When port is not None, instance.port must equal the supplied value exactly, whether or not filter_ is set. For example, port=-1 must produce instance.port == -1.
    • When port is None and no filter is set, instance.port must equal APRS_PORT_FULL.
    • When port is None and a filter is set, instance.port must equal APRS_PORT_FILTER.
  • filter_ is an optional APRS filter string. It is retained on the instance, influences the selection of the default port, and, when set, is included in the authentication message.
connect(self)

connect() establishes a TCP connection and carries out the APRS login exchange.

Setting up the connection
  • The connection is opened through the standard socket.create_connection entry point, using the server and port selected on the instance.
  • The returned socket must be stored as self._socket.
  • Using the socket's makefile() method, obtain a line-readable socket stream and store it as self._sock_file.
Handling of the banner and the login response

Before the actual login response, the APRS exchange contains an initial server greeting:

  1. The initial server banner/comment is read from _sock_file. A typical example is # aprsc 2.1.4-g408ed49; it starts with # but is not a # logresp message.
  2. The banner is passed to _validate_login. Validating such a non-login line directly raises exceptions.LoginError, as specified below. During connect(), that particular LoginError is expected: for the initial non-login banner it must be suppressed, and the connection flow must continue rather than treating the banner as an authentication failure. Authentication is not completed by the banner.
  3. Generate and send the APRS authentication message, then keep reading the response stream to obtain the login-response line that follows.
  4. Validate the login response with _validate_login, and use its result as the authentication state. A verified login response must leave self._authenticated truthy, while an unverified response leaves it falsy.

This special suppression applies only to the LoginError caused by the ordinary initial non-login banner. It does not alter the standalone behavior of _validate_login, and it does not suppress errors from the actual login response.

Resource and error behavior
  • After the connection/login exchange succeeds, _sock_file and the underlying socket must remain open; in particular, _sock_file.close() must not be called.
  • If login validation otherwise raises exceptions.ParseError or exceptions.LoginError, the exception must propagate out of connect(). Before it propagates, _sock_file.close() must be called exactly once and _socket.close() exactly once.
  • A ParseError raised while the initial response is being validated is not the expected banner case and must likewise propagate after both resources have been closed.
  • Suppressing the initial banner-related LoginError must not close either resource; processing must continue on to the login response.
send(self, message)

A textual message is sent through self._socket:

  • Leading and trailing whitespace/newlines are stripped from message.
  • Then append exactly one trailing newline (\n).
  • The resulting string is encoded to bytes.
  • Those bytes are passed to self._socket.sendall() in one call.

Examples:

send('test message')
# sends b'test message\n'

send('\n\ntest\nmessage\n\n\n')
# sends b'test\nmessage\n'

Only outer whitespace is removed; newlines in the interior are preserved.

_gen_auth_message(self)

The APRS authentication message is returned as one space-delimited string.

When there is no filter, splitting the result on single spaces must yield exactly these leading fields and software-identification fields:

  1. 'user'
  2. the configured username
  3. 'pass'
  4. the configured passcode
  5. exactly three additional tokens that contain the software identification/version information

Thus, when the passcode is the default and no filter is set, indexes 0 through 3 are respectively 'user', the username, 'pass', and '-1', followed by exactly three more tokens.

When filter_ is set, filter <filter_value> is appended to the base authentication message. The complete result must end with the literal text filter followed by the configured filter value. This filter suffix is in addition to the three software-identification/version tokens.

_validate_login(self, response)

One textual server-response line is validated.

A login response that is structurally valid has this form:

# logresp <user> <status>, server <servername>

The behavior depends on <status>:

  • verified — return a truthy value. In particular, a verified response for a client that uses a real passcode (anything other than the default '-1') is successful. A verified response used by connect() must set the client's authentication state to truthy.
  • unverified — return a falsy value in both cases:
    • the client uses the default '-1' passcode and did not attempt authenticated access; or
    • the client uses a real passcode but authentication failed.
  • Any other status, such as blocked, is a login protocol failure and must raise exceptions.LoginError.

The classification of responses also has these requirements:

  • A comment/banner that is not a login response, such as # aprsc 2.1.4-g408ed49, must raise exceptions.LoginError when _validate_login is called directly. connect() treats only the initial occurrence of this banner-related error specially, as described above.
  • A line that begins as a login response but cannot be parsed into the expected user/status and server structure, such as # logresp 2.1.4-g408ed49, must raise exceptions.ParseError.

Compatibility Notes

  • The creation of sockets must go through the standard library's socket.create_connection symbol.
  • No local APRS passcode verification is required. The passcode is sent to the server; locally, the distinguished default '-1' means that no authenticated access was requested, while any other value means that authentication was attempted.

Summary

Build an APRS (Automatic Packet Reporting System) client that connects to the Open Glider Network (OGN) APRS servers, authenticates, receives records, and maintains the connection.

Create a package called ogn_lib that contains:

  • ogn_lib.client — the implementation of the client.
  • ogn_lib.exceptions — the classes for the custom exceptions.

OgnClient must be defined in ogn_lib.client, and it must also be importable directly from the package root:

from ogn_lib import OgnClient

Exceptions

Define the following exception classes in ogn_lib.exceptions:

  • ParseError — raised when data cannot be parsed as expected.
  • LoginError — raised for failures related to login.

OgnClient

OgnClient must be defined in ogn_lib.client.

Class-Level Constants

The class must expose the following class-level attributes:

  • APRS_SERVER — the hostname of the default APRS server, as a string.
  • APRS_PORT_FULL — the integer port used when no filter has been provided.
  • APRS_PORT_FILTER — the integer port used when a filter has been provided.

The values of APRS_PORT_FULL and APRS_PORT_FILTER must be distinct.

Constructor
OgnClient(username, passcode=None, server=None, port=None, filter_=None)

Parameters and the rules for resolving them:

  • username is the login username; it is required and positional.
  • passcode is the login passcode. Its default is -1, and it is represented by the string '-1' in generated messages. When authentication results are evaluated, a real passcode string such as '123456' is used.
  • server is an optional hostname for the server. If it is omitted, APRS_SERVER is used; if it is supplied, that exact value is used and exposed as server.
  • port is resolved according to these rules:
    • A value supplied explicitly is used exactly as given, whether or not a filter is set.
    • If it is omitted and filter_ is omitted too, APRS_PORT_FULL is used.
    • If it is omitted while filter_ is supplied, APRS_PORT_FILTER is used.
  • filter_ is an optional string holding the APRS filter.

The resolved values must be exposed through the instance attributes server and port.

In addition, the client must maintain these attributes:

  • _kill — the flag that terminates the receive loop, initially falsy.
  • _authenticated — whether authentication has succeeded, initially falsy.
  • _socket — the underlying socket; it is populated while connecting.
  • _sock_file — the file-like view returned by the socket; it is populated while connecting.
  • _last_send — the timestamp of the most recent send; it is used for keepalive decisions.
connect(self)

Set up a connection and authenticate it:

  1. Open a socket for the resolved endpoint by calling socket.create_connection((server, port)), and retain it as _socket.
  2. Invoke the socket's makefile() method, retaining the result as _sock_file.
  3. Set _kill back to a falsy value so that a newly established connection can receive data.
  4. Read the initial server banner using _sock_file.readline(). A typical banner is '# aprsc 2.1.4-g408ed49'.
  5. Generate the authentication message via _gen_auth_message() and send it over the connection.
  6. Read the subsequent login-response line, such as '# logresp user verified, server GLIDERN3', and validate it using _validate_login(...). Store the resulting authentication state in _authenticated; a response that has been verified successfully leaves it truthy.

When the connection is successful, _sock_file must remain open.

If login validation raises an authentication or parsing exception, that exception must propagate out of connect(); before propagating it, close both _sock_file and _socket.

disconnect(self)

Shut down the connection by:

  • Assigning a truthy value to _kill.
  • Closing _socket.
  • Closing _sock_file.

The truthy kill flag must bring active or subsequent receive processing to a stop.

receive(self, callback, parser=None)

Carry out receive processing by delegating the per-line work to _receive_loop(callback, parser).

Every entry into _receive_loop is conditional on _kill being falsy — including the first entry and every entry after reconnection. If _kill is already truthy, receive() must return without invoking _receive_loop.

If _receive_loop raises BrokenPipeError, receive() must call connect() in order to attempt reconnection. Once that reconnect call returns, _kill must be checked again before another receive-loop entry is attempted:

  • If _kill is falsy, receiving is resumed by invoking _receive_loop(callback, parser) again.
  • If _kill is truthy, return immediately and do not invoke the receive loop again.

This reconnect-and-retry behavior may repeat across successive broken pipes. In particular, even when every attempted receive-loop run raises BrokenPipeError, receive() must terminate once a reconnect attempt leaves the client in the disconnected/killed state. If the receive loop returns normally, receive() returns normally as well.

_receive_loop(self, callback, parser)

Handle the records arriving on _sock_file until killed:

  • Check _kill before, or at the start of, every iteration. If it is truthy, return immediately without reading or processing another line.
  • Otherwise, use _sock_file.readline() to read one line.
  • On each iteration, invoke _keepalive().
  • If parser is None, the raw line is passed unchanged to callback, in the form callback(raw_line).
  • If a parser callable is supplied, the parsing path is entered. Parsing is deliberately left unimplemented, so this path must raise NotImplementedError instead of invoking the callback with parsed data.

The callback is supplied by the user and receives one record at a time. It may call disconnect(); when it does, _kill is set and another loop iteration is prevented.

send(self, message)

Send a message over the connected socket:

  • Strip the surrounding newline characters/whitespace so that blank lines around the message are removed while interior newlines are preserved.
  • Exactly one trailing newline (\n) is appended.
  • The resulting string is encoded to bytes and passed to _socket.sendall(...).
  • After the send, _last_send is updated to the current value of time.time().

Some examples:

  • 'test message' results in b'test message\n' being sent.
  • '\n\ntest\nmessage\n\n\n' results in b'test\nmessage\n' being sent.
_keepalive(self)

Use _last_send to decide whether the connection needs a keepalive:

  • If the most recent send was recent enough, do nothing and do not call send().
  • If enough time has elapsed — including when _last_send is far in the past, such as 0 — call send(...) with a keepalive message.
_gen_auth_message(self)

Return the APRS authentication message in the form of a space-separated string. If no filter applies, its tokens must be, in order:

  1. The literal user.
  2. The username that has been configured.
  3. The literal pass.
  4. The configured passcode expressed as a string, with -1 as the default.
  5. Exactly three more space-separated tokens for client identification/version.

So the unfiltered base message contains the required first four tokens followed by exactly three more tokens.

If a filter was supplied, filter <filter_value> is appended after the base message. For instance, the filter 'special_filter' makes the message end with filter special_filter.

_validate_login(self, line)

Validate a login response from the server. Representative inputs include:

  • '# logresp user verified, server GLIDERN3'
  • '# logresp user unverified, server GLIDERN3'
  • '# logresp user blocked, server GLIDERN3'
  • '# aprsc 2.1.4-g408ed49'
  • '# logresp 2.1.4-g408ed49'

The required behavior:

  • A well-formed login response whose status is verified counts as successful: return a truthy value and mark the client authenticated. In particular, this is the successful authentication result when a real passcode was configured instead of the default -1.
  • A well-formed login response whose status is unverified returns a falsy value and does not authenticate the client. This holds both for guest/default-passcode connections and for connections where a real passcode was supplied but not verified by the server.
  • A well-formed login response with the status blocked, or with another authentication-error status, raises LoginError.
  • A line that is not a login response at all — for example an APRS server banner beginning '# aprsc' — raises LoginError.
  • A line that identifies itself as a login response yet cannot be parsed into the expected fields, such as '# logresp 2.1.4-g408ed49', raises ParseError.

Example of an APRS Record

A raw record that has been received may look like:

FLRDF0F8E>APRS,qAS,EDTD:/075201h4753.35N/00840.21E'350/063/A=004359 !W69! id0ADF0F8E +079fpm -0.6rot 21.5dB 0e -9.5kHz gps1x1

When no parser is supplied, a line of this kind is delivered unchanged to the callback.

Dependencies

Python's standard socket module is to be used for socket.create_connection and socket file creation, and the standard time module for send timestamps and keepalive timing. For this task, no APRS parser behavior is required.

Add Multiple Timestamp Format Support to the OGN Parser

Overview

In ogn_lib.parser, timestamp handling must be extended so that OGN/APRS timestamps keep their format marker and are parsed according to that marker. The existing time-of-day behavior must be split out into a dedicated helper, and Parser._parse_timestamp becomes the format dispatcher. Both regular position parsing and server-status parsing must pass complete, suffix-bearing timestamp tokens through that dispatcher.

Returned data and all unrelated parser behavior must remain compatible with the existing library.

API Surface Requirements

The following callable static methods must be exposed by the ogn_lib.parser.Parser class. Every successful parse returns a datetime.datetime representing UTC, following the library's existing datetime.utcnow() convention (that is, a naive datetime whose fields are UTC fields).

Parser._parse_timestamp(timestamp_str)

This method routes a complete timestamp token based on its final, lowercase format marker:

  • When the token ends in h, strip only that trailing h and invoke Parser._parse_time exactly once, passing it the remaining six-character value.
  • When the token ends in z, strip only that trailing z and invoke Parser._parse_datetime exactly once, passing it the remaining six-character value.
  • The delegated method's result is returned unchanged.

Examples:

  • Parser._parse_timestamp('010203h') delegates to Parser._parse_time('010203').
  • Parser._parse_timestamp('010203z') delegates to Parser._parse_datetime('010203').

This task requires only the lowercase h and z timestamp forms; how malformed values or other suffixes behave is not otherwise specified.

Parser._parse_time(time_str)

Parse a zero-padded HHMMSS value carrying no suffix, where HH, MM, and SS are the two-digit hour, minute, and second. Return a datetime.datetime with those time fields, and infer its UTC calendar date relative to the current UTC time.

Since this format includes no date, pick the occurrence of the time of day as a recent timestamp, while allowing a small near-future tolerance:

  • In the normal case, return the most recent occurrence at or before the current UTC time. It must lie between now - 24 hours and now, inclusive.
  • If an occurrence is no more than five minutes in the future, preserve that near-future occurrence rather than moving it to the preceding day. This rule also holds across the UTC midnight boundary, so the appropriate adjacent date must be selected.
  • A same-day clock value that is more than five minutes ahead is interpreted as the previous day's occurrence.

The microsecond of the result is zero. Timing comparisons naturally allow for the fraction of a second that elapses while parsing. In particular, when an input is produced by taking the current UTC time plus an integer i minutes and formatting it as HHMMSS, the returned result must, for near-future values, satisfy:

(i - 1) * 60 <= (result - now).total_seconds() <= i * 60

For past values, 0 <= (now - result).total_seconds() <= 86400 must hold.

Parser._parse_datetime(datetime_str)

Parse a zero-padded DDHHMM value without a suffix, where DD is the day of month and HH and MM are the hour and minute.

  • The day, hour, and minute are taken from the input.
  • The year and month are taken from the current UTC date at parsing time.
  • Seconds and microseconds are set to zero.
  • The resulting datetime.datetime is returned using UTC field values.

For this format, no previous- or next-month inference is required: the current UTC year and month are the ones used. If the input contains the current UTC day, hour, and minute, the result must lie within 60 seconds of the current UTC time.

Forwarding Timestamps from the Message Parsers

Format dispatch can work only when the marker is retained by callers as part of the extracted timestamp token. Parser paths that bear timestamps must therefore, when calling Parser._parse_timestamp, use the complete seven-character token (HHMMSSh or DDHHMMz).

Position messages

Parser._parse_position must pass the complete timestamp found at the start of a position payload — its trailing h or z included — to Parser._parse_timestamp. The marker continues to act as the separator between the six timestamp digits and the following position fields; it must not be included in the latitude or other fields. The value the dispatcher returns remains the position data's timestamp value.

Server status messages

ServerParser.parse_status must extract the complete timestamp token — the one following the status header's :/ delimiter and preceding the status comment. It must invoke Parser._parse_timestamp exactly once, passing that exact token with the trailing format marker included.

For example, when a status payload starts with :/211635h , Parser._parse_timestamp('211635h') must be called — not 211635 passed along, the marker stripped before dispatch, or the dispatcher bypassed by calling a format-specific helper directly. What the dispatcher returns must be stored as the status result's timestamp; all other existing status fields and parsing behavior stay unchanged.

Compatibility and Scope

  • All time calculations are based on the current UTC time, not on local time.
  • The existing non-timestamp parsing APIs, message classification, parsed fields, and return structures must keep behaving as before.
  • This change covers nothing beyond suffix-based timestamp dispatch, the two specialized parsing methods, and keeping timestamp suffixes intact at the parser call sites that consume OGN/APRS timestamp tokens.
