Specification of the Task

Overview

The codebase you are working on is archey. Changes are required in two areas: the Configuration singleton utility class and the Terminal entry class. The changes described below must make the specified behaviors hold exactly.

Part 1: the Configuration class (archey/configuration.py)

The Configuration class is a singleton; its singleton machinery comes from a base Singleton metaclass located at archey.singleton.Singleton. The Singleton type must maintain a class-level dictionary attribute named _instances that holds instances keyed by class. If this dictionary is cleared (or entries are removed from it), a fresh instance must be constructed on the next instantiation. It must be possible to patch/clear this attribute externally via archey.singleton.Singleton._instances.

The constructor
Configuration(config_path=None)
  • The constructor accepts an optional keyword argument config_path, whose default is None.
  • When the instance is constructed, it holds an internal configuration dictionary attribute named _config (a dict). Before any user configuration is applied, this dictionary is populated with the default configuration values. Immediately after construction, the _config attribute must already exist and be a mutable dictionary (it must be possible to patch it via unittest.mock.patch.dict on instance._config).
  • While being constructed, the instance loads configuration from the local system by invoking an instance method named _load_configuration (see below). This system-loading step must be isolated within a single method call so that it can be mocked out independently.
  • When config_path is provided (a filesystem path to a specific JSON configuration file), the values from that file must be loaded and merged into _config, overriding matching default entries. If the config_path supplied points directly to a JSON file, the settings contained in it must take effect (e.g. boolean flags, nested dictionary values, and integer values found in the file must override the corresponding defaults).
The internal _stderr attribute

The instance holds an attribute named _stderr that represents an output file descriptor for warnings. By default, its value is sys.stderr. If configuration loading results in warnings being suppressed (see _load_configuration below), the _stderr attribute must be changed to a value that is no longer equal to sys.stderr.

The get(key, default=None) method
def get(self, key, default=None)
  • Returns the value that _config stores under key.
  • If key is not present, default is returned.
  • When key is not present and no default has been supplied, None is returned.
  • Nested dictionary values must be returned intact (so that callers can index into them).
The _load_configuration(directory) method
def _load_configuration(self, directory)
  • This method receives a directory path and looks inside that directory for a JSON configuration file named config.json, merging the file's contents into _config.
  • The merge happens recursively: existing scalar values get overridden, nested dictionaries are merged key-by-key, and new keys are added. Keys present in _config but absent from the file stay untouched.
  • When the file's suppress_warnings option is set to true, it must cause the _stderr attribute to be reassigned to something other than sys.stderr.
  • After a configuration has been loaded with allow_overriding set to false, later calls to _load_configuration must NOT alter _config — the configuration becomes locked against further overriding. To put it differently, once allow_overriding is false, subsequent loads leave _config unchanged.
  • The directory argument is used to locate config.json within it (for example, by joining the directory with the filename). A directory containing no config.json results in no changes.
The _update_recursive(original_dict, update_dict) method
def _update_recursive(self, original_dict, update_dict)
  • Carries out a recursive merge of update_dict into original_dict in place.
  • For each key in update_dict:
    • When both original_dict[key] and update_dict[key] are dictionaries, they are merged recursively.
    • Otherwise, original_dict[key] is set to the value from update_dict[key] (this covers replacing scalars and assigning arbitrary non-dict values such as lists — including nested lists containing None, strings, and dicts).
  • Keys found in original_dict but not in update_dict are preserved unchanged.
  • New keys coming from update_dict (including deeply nested new keys) are added.

Example of merge behavior: Suppose the original config has suppress_warnings: False, a nested default_strings dict, colors_palette, ip_settings, and a temperature dict containing use_fahrenheit: False; merge in an update that sets suppress_warnings: True, adds a virtual_environment key inside default_strings, changes no_address inside default_strings, and adds a brand-new a_weird_new_dict key (whose value is a list) inside temperature — the result must contain: the updated suppress_warnings, the merged default_strings (old + new keys), the untouched ip_settings, and a temperature dict that retains use_fahrenheit: False while also gaining a_weird_new_dict.

Part 2: the Terminal entry (archey/entries/terminal.py)

The Terminal entry class detects the name of the terminal emulator and exposes it through a value attribute. It also provides an output(...) method that appends a formatted representation.

The terminal name that gets detected and stored in value must be exactly the resolved emulator name — value itself must carry no trailing content (such as appended color-block characters). In particular:

  • If the emulator is identified by TERM_PROGRAM, value must equal exactly that name (e.g. 'A-COOL-TERMINAL-EMULATOR').
  • If a special TERM value is honored, value must equal exactly that value (e.g. 'OH-A-SPECIAL-CASE').
  • If manual detection with name normalization applies, value must equal exactly the normalized name (e.g. 'Konsole').
  • If the name is provided by TERM (e.g. 'xterm-256color'), value must equal exactly that string. The output(...) method must still append a string that starts with that name (color blocks may follow it in the appended output, but not in value).
  • If detection relies on COLORTERM, value must equal exactly the resolved name (e.g. 'KMSCON'), including when TERM or another known identifier is also present.
The not-detected case

When no terminal can be detected, value must be None, and the string appended by the output(...) method must start with 'Not detected' (note: a trailing space is not required after 'Not detected'). The appended output for this not-detected case must not contain the full-block character '\u2588'.

Summary of the Public API

  • archey.configuration.Configuration — a class; its constructor accepts the optional keyword config_path; its instance attributes are _config (dict) and _stderr; its methods are get(key, default=None), _load_configuration(directory), _update_recursive(original_dict, update_dict).

  • archey.entries.terminal.Terminal — a class having a value attribute and an output(...) method; its module references os.environ.

Overview

The Distributions Class

Distributions must be defined in archey/distributions.py as an enumeration whose members stand for the supported distributions / platforms. The value of each member is a lowercase string identifier.

Members and values that are required

At minimum, the members listed below must exist with the given string values:

  • Distributions.DEBIAN → 'debian'
  • Distributions.UBUNTU → 'ubuntu'
  • Distributions.ARCH_LINUX → (an identifier equal to 'arch' — see the matching rules below)
  • Distributions.LINUX_MINT → 'linuxmint'
  • Distributions.SLACKWARE → 'slackware'
  • Distributions.WINDOWS → 'windows'
  • Distributions.LINUX → 'linux'
Constructing from a value

Distributions must behave like a standard enumeration constructed from a value:

  • Calling Distributions('debian') returns Distributions.DEBIAN.
  • Constructing it from a value that does not correspond to any member (e.g. Distributions('unknown')) raises ValueError.
Module-level imports that the tests patch

The module must import the following names at module scope so that they can be patched as archey.distributions.<name>:

  • sys (used through sys.platform)
  • check_output (imported from subprocess)
  • distro (the vendor package distro; used through distro.id, distro.like, and distro.os_release_attr)

Distributions.run_detection()

Supply a static/class-callable method Distributions.run_detection() that returns a single Distributions member representing the platform/distribution that was detected. It applies the following logic, in order:

  1. Windows (native): If sys.platform signals Windows (value 'win32'), return Distributions.WINDOWS.

  2. Windows Subsystem for Linux: Otherwise, call check_output(...) to obtain the kernel release string (the call returns a bytes value such as b'X.Y.Z-R-Microsoft\n'). If that release string contains the substring Microsoft (matching case-insensitively is acceptable; the tests use the exact casing Microsoft), return Distributions.WINDOWS.

  3. Known distribution by ID: Otherwise, read the distribution id by means of distro.id(). When its (lowercased) value is equal to one of the enumeration member values, return the corresponding member. For instance, distro.id() returning 'debian' yields Distributions.DEBIAN.

  4. Match via ID_LIKE: If distro.id() does not correspond to a known member (this includes the case where it returns an empty string), read distro.like(), which returns a possibly empty, possibly space-separated string of related distribution identifiers. Split that string on whitespace and, going through the resulting identifiers in order, return the first one that corresponds to a known enumeration member.

    • Example: distro.like() returning 'ubuntu' yields Distributions.UBUNTU.
    • Example: distro.like() returning 'an-unknown-distro-id arch' yields Distributions.ARCH_LINUX (the first token is unknown; the second, arch, matches).

  5. Fallback: If nothing among the above matches — including the case where both distro.id() and distro.like() yield nothing usable — return Distributions.LINUX.

Distributions.get_distro_name()

Supply a callable Distributions.get_distro_name() that returns the human-readable ("pretty") name of the distribution as a string, or None when such a name cannot be determined (soft-failure). Consumers must treat a returned None as "name not available".

Distributions.get_ansi_color()

Supply a callable Distributions.get_ansi_color() that returns the distribution's ANSI color string (obtained from the os-release ANSI_COLOR attribute through distro.os_release_attr), or None/empty when it is unavailable.

Modifications to Output (archey/output.py)

Output must no longer call distro or check_output directly when detecting the distribution. Instead:

  • At construction time, Output() determines the current distribution by calling Distributions.run_detection() and stores the resulting Distributions member in the instance attribute _distribution.
  • The color/logo selection logic must obtain the ANSI color by way of Distributions.get_ansi_color():
    • If the configuration option honor_ansi_color is truthy and Distributions.get_ansi_color() returns a non-empty color string, that color is honored.
    • If get_ansi_color() returns None/empty, or honor_ansi_color is falsy, the default color handling applies.

Distributions must be importable as archey.output.Distributions (that is, imported into the output module namespace) so that Distributions.run_detection and Distributions.get_ansi_color are reachable there. Aside from this rewiring, the existing append, output, JSON-formatting, centering, and line-wrapping behaviors of Output must remain unchanged.

Modifications to the Distro Entry (archey/entries/distro.py)

The Distro entry must no longer call distro.name directly. Instead:

  • Import Distributions into the entry module's namespace so that it is reachable as archey.entries.distro.Distributions.
  • Get the pretty distribution name by calling Distributions.get_distro_name().
  • Keep obtaining the machine architecture via check_output(...) (reachable as archey.entries.distro.check_output).
  • If Distributions.get_distro_name() returns a valid name, the entry's value is that name combined with the architecture (e.g. name NAME VERSION (CODENAME) plus architecture ARCHITECTURE).
  • If Distributions.get_distro_name() returns None (soft-failure), the entry must fall back to the configured not_detected string (obtained via Configuration.get) instead of a distribution name.

Further Notes (unrelated cleanups required for correctness)

  • LanIp entry: If the optional netifaces dependency is not available (import failed / patched to None), the LanIp entry must degrade gracefully at construction time without raising. Any user-facing message emitted in this situation must pass through the module-level print (reachable/patchable as archey.entries.lan_ip.print).

  • Processes singleton: No behavioral change is required beyond what already exists; the class stays a singleton whose internal instance registry lives in archey.singleton.Singleton._instances.

The modules and public names described above must exist exactly as specified so that:

  • from archey.distributions import Distributions works.
  • archey.output.Distributions, archey.entries.distro.Distributions, archey.entries.distro.check_output, and archey.entries.lan_ip.print are all resolvable.

Task: Rework the Disk entry

Overview

Reimplement the Disk entry found at archey/entries/disk.py in the module archey.entries.disk. The entry is a class called Disk. Disk usage information must be gathered exclusively via the df utility (invoked through check_output, imported into the module as archey.entries.disk.check_output). The class exposes a number of methods (some static, some instance), each individually testable, in addition to the standard output method.

The Colors enum can be obtained from archey.colors (Colors.GREEN_NORMAL, Colors.YELLOW_NORMAL, Colors.RED_NORMAL, Colors.CLEAR).

State and configuration of an instance

A Disk instance carries:

  • name — the string used as the entry's name (default 'Disk').
  • value — the computed result (see below), possibly None.
  • _configuration — a mapping. The keys that matter are:
    • _configuration['disk'], which contains:
      • show_filesystems: a list; e.g. ['local'] or a list of device paths / mount points.
      • combine_total: a bool.
      • disk_labels: None, False, 'device_paths', or 'mount_points'.
      • hide_entry_name: None, True, or False.
    • _configuration['limits']['disk'], which holds the warning and danger integer thresholds (percentages).
    • _configuration['default_strings']['not_detected'] — a string.

The methods described below must read configuration and instance attributes only through self, so that they can be exercised in isolation.

The _disk_dict data structure

Internally the entry works with a mapping keyed by mount point (string). Every value is a dict containing at least:

  • device_path: string (e.g. /dev/sda1, tmpfs, //server.local/share).
  • used_blocks: the number of used 1024-byte blocks.
  • total_blocks: the number of total 1024-byte blocks.

The raw parsed data is stored by the instance on self._disk_dict.

Methods to be provided

Disk.get_df_output_dict() — static method

Runs df (through check_output) with POSIX/portable options, producing output whose columns are, in order: Filesystem, 1024-blocks, Used, Available, Capacity, Mounted on. The first line is a header, which must be skipped.

Return a dict keyed by mount point. Each of its values is:

{
    'device_path': <first column, str>,
    'used_blocks': <third column, int>,
    'total_blocks': <second column, int>
}

Given output like:

/dev/nvme0n1p2             499581952 427458276      67779164      87% /
tmpfs                        8127236       292       8126944       1% /tmp
/dev/nvme0n1p1                523248     35908        487340       7% /boot

the returned dict is:

{
    '/':     {'device_path': '/dev/nvme0n1p2', 'used_blocks': 427458276, 'total_blocks': 499581952},
    '/tmp':  {'device_path': 'tmpfs',          'used_blocks': 292,       'total_blocks': 8127236},
    '/boot': {'device_path': '/dev/nvme0n1p1', 'used_blocks': 35908,     'total_blocks': 523248}
}

If the df invocation raises FileNotFoundError (the utility is not present), return an empty dict {}. The method performs a single check_output call, and its success or the FileNotFoundError determines the result.

Disk._get_local_filesystems(self) — instance method

Reads self._disk_dict and returns a new dict (same key/value shape) that contains only "local, physical" filesystems, applying the rules below to each entry's device_path:

  • Keep only entries whose device_path starts with /dev/; any other device path (e.g. //server.local/cool_share) is excluded.
  • Loop / virtual devices are excluded. A device is excluded when the final path component of device_path (the part after the last /) begins with any of these loop-device prefixes: loop (Linux), svnd (BSD), rvnd (BSD), lofi (Solaris). That means that, e.g., /dev/loop0, /dev/blah/loop0, /dev/svnd, /dev/blah/svnd1, /dev/rvnd, /dev/blah/rvnd1, /dev/lofi1, /dev/blah/lofi are all excluded.
  • Device-mapper devices are excluded: the final path component begins with dm- (e.g. /dev/dm-1).
  • De-duplicate on device_path: when multiple mount points share the same device_path, only one of them is kept (which one is unspecified). For example, two entries that both have /dev/sda1 collapse into a single result entry.

The keys of the returned dict are mount points carried over from self._disk_dict.

Disk._get_specified_filesystems(self, specified_filesystems) — instance method

Reads self._disk_dict and returns a new dict (same shape) that contains only the entries matching specified_filesystems, an iterable of strings. An entry matches if its mount point (the key in self._disk_dict) OR its device_path is present in specified_filesystems.

  • If specified_filesystems contains every mount point found in self._disk_dict, the returned dict equals self._disk_dict.
  • If specified_filesystems is ('/dev/sda1',), return only the entries whose device_path is /dev/sda1; when several mount points share that device path, exactly one is returned (which one is unspecified).
Disk._blocks_to_human_readable(blocks, suffix='B') — static method

Given a count of 1024-byte blocks, return a human-readable string shaped as '<value> <unit>', where the value is rounded to one decimal place and the unit is one of KiB, MiB, GiB, TiB, PiB (binary, 1024-based scaling, starting at KiB because the input is already in 1024-byte blocks).

Disk.output(self, output) — instance method

self.value is a dict keyed by mount point, with each value being {'device_path', 'used_blocks', 'total_blocks'} (same shape as _disk_dict). output is an object that provides an append(name, text) method.

Usage coloring. For a given entry, the usage percentage is computed as used_blocks / total_blocks * 100. The color is chosen as follows:

  • Colors.RED_NORMAL when the percentage is at or above the danger threshold.
  • Colors.YELLOW_NORMAL when it is at or above the warning threshold (but below danger).
  • in all other cases, Colors.GREEN_NORMAL.

The thresholds are taken from self._configuration['limits']['disk']['warning'] and ['danger'].

Value text. Every appended text has the shape:

{color}{used_human_readable}{clear} / {total_human_readable}

where the human-readable strings are the output of _blocks_to_human_readable applied to the used and total blocks, and {clear} stands for Colors.CLEAR. The used portion is wrapped in the chosen color; the total portion is not colored.

Examples (using warning=50, danger=75):

  • used 45, total 100 → {GREEN_NORMAL}45.0 KiB{CLEAR} / 100.0 KiB
  • used 70, total 100 → {YELLOW_NORMAL}70.0 KiB{CLEAR} / 100.0 KiB
  • used 95, total 100 → {RED_NORMAL}95.0 KiB{CLEAR} / 100.0 KiB

Combine-total behavior. When self._configuration['disk']['combine_total'] is truthy, produce a single append call in which used_blocks is the sum of all entries' used_blocks and total_blocks is the sum of all entries' total_blocks; the color is computed from that combined percentage. In combined mode, the appended name is self.name (i.e. 'Disk').

Example: two entries (used 10, total 10) and (used 10, total 30) combined → used 20, total 40 → 50% → {YELLOW_NORMAL}20.0 KiB{CLEAR} / 40.0 KiB, appended once with the name 'Disk'.

Multi-line behavior. When combine_total is falsy, one append call is produced per entry in self.value (order unspecified). The used/total/color of each line come from that individual entry.

For the two-entry example above, with combine_total false:

  • (used 10, total 10) → 100% → {RED_NORMAL}10.0 KiB{CLEAR} / 10.0 KiB
  • (used 10, total 30) → ~33% → {GREEN_NORMAL}10.0 KiB{CLEAR} / 30.0 KiB

Per-line entry name / labels (multi-line mode only). The name argument handed to append is derived from self.name, disk_labels, and hide_entry_name (self._configuration['disk']['disk_labels'] and ['hide_entry_name']):

  • With disk_labels == 'device_paths', a line's label is that entry's device_path.
  • With disk_labels == 'mount_points', a line's label is that entry's mount point (the dict key).
  • For any falsy disk_labels (None, False), no label is used.

How this combines with hide_entry_name:

Task Specification: Supporting Multiple CPUs in the CPU Entry

Summary

The CPU entry is to be modified so that it detects and represents multiple CPUs (physical packages), with each package carrying its own model name and its total number of cores. 1. The CPU entry — archey/entries/cpu.py

A class CPU must be exposed by the module archey.entries.cpu. It imports open (used for reading /proc/cpuinfo) and check_output (used for invoking lscpu) under the module-level names archey.entries.cpu.open and archey.entries.cpu.check_output.

1.1 Representation of the value

A CPU instance must produce a value attribute that is a list of dictionaries. Every dictionary stands for one physical CPU package and maps a CPU model name string → core count (int). When (unusually) multiple distinct model names are reported for the same physical package, a single dictionary may contain more than one key.

For example:

[
    {'CPU-MODEL-NAME': 1},
    {'ANOTHER-CPU-MODEL': 2}
]
1.2 The static method CPU._parse_proc_cpuinfo()

Its signature is @staticmethod def _parse_proc_cpuinfo().

The method reads /proc/cpuinfo (via the module-level open) and parses it. The file's content consists of processor blocks separated by blank lines. Every block contains lines of the form key\t: value. The fields of interest are model name and physical id.

Behavior:

  • Processors are grouped by their physical id. Every distinct physical id becomes one entry (one dictionary) in the returned list, in the order in which the physical ids first appear.
  • Inside each physical-id group, the occurrences of each model name are counted, and the dictionary for that group maps model name → the number of processors carrying that model name within that group.
  • Model name normalization: any run of whitespace characters (spaces and/or tabs) found within a model name is collapsed into a single space, and leading/trailing whitespace is stripped. For instance, the raw model name ANOTHER\tCPU MODEL WITH STRANGE S P A C E S becomes ANOTHER CPU MODEL WITH STRANGE S P A C E S.
  • The return type is a list of dict[str, int].

Examples showing the required results:

  • One processor block having model name: CPU-MODEL-NAME and physical id: 0:

    [{'CPU-MODEL-NAME': 1}]

  • Three processors: a single CPU-MODEL-NAME on physical id 0, plus two ANOTHER-CPU-MODEL on physical id 1:

    [{'CPU-MODEL-NAME': 1}, {'ANOTHER-CPU-MODEL': 2}]

  • Four processors, all of them CPU-MODEL-NAME, with two on physical id 0 and two on physical id 1:

    [{'CPU-MODEL-NAME': 2}, {'CPU-MODEL-NAME': 2}]

  • Four processors where physical id 0 carries one CPU-MODEL-NAME and one ANOTHER-CPU-MODEL, and physical id 1 carries two of a strangely-spaced model name:

    [
    {'CPU-MODEL-NAME': 1, 'ANOTHER-CPU-MODEL': 1},
    {'ANOTHER CPU MODEL WITH STRANGE S P A C E S': 2}
]

Error/edge case: if /proc/cpuinfo cannot be read (e.g. open raises PermissionError), an empty list is returned.

1.3 The static method CPU._parse_lscpu_output()

Its signature is @staticmethod def _parse_lscpu_output().

The method invokes lscpu (via the module-level check_output) and parses its output. lscpu output is made up of Key: Value lines. The output may hold multiple CPU sections separated by a blank line; every such section is one physical CPU package and yields one dictionary in the returned list, in order.

For every section, the Model name field serves as the model name (normalized the same way as in _parse_proc_cpuinfo, i.e. internal whitespace runs are collapsed to a single space and the result is stripped). The core count for that package is computed as Core(s) per socket × Socket(s) (both are integer fields taken from that section).

The return type is a list of dict[str, int].

The required results:

  • A single section with Core(s) per socket: 4, Socket(s): 1, Model name: CPU-MODEL-NAME:

    [{'CPU-MODEL-NAME': 4}]

  • Two sections (separated by a blank line): the first has Core(s) per socket: 2, Socket(s): 1, Model name: CPU-MODEL-NAME; the second has Core(s) per socket: 2, Socket(s): 1... hold on — the second section reports Core(s) per socket: 2, Socket(s): 1 with a different model — see the mapping below:

    [
    {'CPU-MODEL-NAME': 2},
    {'ANOTHER-CPU-MODEL': 4}
]

    (First section: 2×1 = 2 cores. Second section: Core(s) per socket: 2 × Socket(s): 1... the values supplied by the second section yield 4 cores — i.e. Core(s) per socket × Socket(s) = 4 — for model ANOTHER-CPU-MODEL.)

  • A single section with Core(s) per socket: 4, Socket(s): 2, Model name: CPU-MODEL-NAME — this represents one CPU model spread across two sockets:

    [{'CPU-MODEL-NAME': 8}, {'CPU-MODEL-NAME': 8}]

    Note: if a single lscpu section describes Socket(s): 2 for one model, the result contains one dictionary per socket, with each dictionary mapping the model name to the per-socket core count (Core(s) per socket × Socket(s)).

Clarification regarding core-count semantics: the value stored per model equals Core(s) per socket × Socket(s) taken from the section, and the section contributes one dictionary per socket (a section with N sockets thus yields N identical dictionaries).

1.4 The instance method CPU.output(self, output)

Signature: def output(self, output).

output refers to an object that has an append(name, text) method. The string 'CPU' is the entry name to use.

The method reads the following:

  • self.value — the list-of-dicts described above (it may also be an empty container).
  • self.options — a mapping that supports these keys:
    • 'one_line' (bool): when true, all CPUs are merged into a single appended line; when false, every CPU package produces its own appended line.
    • 'show_cores' (bool): when true (default behavior), every model name gets prefixed with its core count in the form N x MODEL whenever the count is greater than 1; when the count is exactly 1, only the model name is shown (no 1 x prefix). When false, core counts are left out entirely, and only the model names are shown.

Formatting rules for a single model entry:

  • Counts shown and count == 1: MODEL
  • Counts shown and count > 1: N x MODEL
  • Counts hidden: MODEL

Combining rule when one_line is true: take every model entry across all CPU packages (each formatted according to the rules above), join them into one comma-space (, ) separated string, and call output.append('CPU', combined_string) exactly once.

Behavior when one_line is false: for every CPU package, call output.append('CPU', text), with text being that package's formatted model entries joined by , . This results in one call per package. (The order across packages need not be guaranteed.)

No-CPU edge case: when self.value is empty (e.g. an empty dict/list), call output.append('CPU', <not_detected string>) exactly once; here the not-detected string is DEFAULT_CONFIG['default_strings']['not_detected'] from archey.constants.

Required examples, taking self.value = [{'CPU-MODEL-NAME': 1}, {'ANOTHER-CPU-MODEL': 2}]:

  • one_line=True with counts shown → one call: output.append('CPU', 'CPU-MODEL-NAME, 2 x ANOTHER-CPU-MODEL')
  • one_line=True and show_cores=False → one call: output.append('CPU', 'CPU-MODEL-NAME, ANOTHER-CPU-MODEL')
  • one_line=False and show_cores=True → two calls:
    • output.append('CPU', 'CPU-MODEL-NAME')
    • output.append('CPU', '2 x ANOTHER-CPU-MODEL')

With an empty value → one call: output.append('CPU', DEFAULT_CONFIG['default_strings']['not_detected']).

The CPU entry must recognize the options one_line and show_cores; these are taken from self.options at output time. The name given to an entry must not be treated as a configurable option.

Overview

Configuration must make each protocol version (IPv4 / IPv6) and each back-end individually controllable.

Module and Symbol Names

  • Module: archey.entries.wan_ip
  • Class: WanIP
  • check_output and urlopen must be imported and used by the module as module-level names (the patch points are archey.entries.wan_ip.check_output and archey.entries.wan_ip.urlopen).

Required Public and Internal API

WanIP._retrieve_ip_address(self, ip_version)

A method belonging to WanIP that attempts to retrieve a single WAN IP address for a given IP protocol version.

Parameters:

  • ip_version: an integer — either 4 or 6 — indicating which IP protocol version to resolve.

Return value:

  • On success, a string holding the resolved IP address (stripped of surrounding whitespace/newlines).
  • A falsy value (e.g. None / empty) if no address could be retrieved, or if retrieval is disabled by configuration.

The behavior of this method is read from self.options, which is a dictionary.

WanIP.output(self, output)

Instance method that produces the display output. It reads self.value (a list of address strings).

Behavior:

  • If self.value contains at least one address, it must call output.append(...), passing the entry name as the first positional argument and, as the second positional argument, a single string formed by joining all addresses with ", " (comma followed by a space), preserving the list order.
  • If self.value is an empty list, it must call output.append(...) with the second positional argument equal to DEFAULT_CONFIG['default_strings']['no_address'] (taken from archey.constants.DEFAULT_CONFIG).

Configuration Options (self.options)

Retrieval is controlled by the options dictionary. It may contain the keys 'ipv4' and 'ipv6'. For a given protocol version, the corresponding key is 'ipv4' (for version 4) or 'ipv6' (for version 6).

The value stored under each protocol key may be:

  1. A boolean False — retrieval for the entire protocol is disabled. _retrieve_ip_address must return a falsy value immediately, without invoking either back-end.

  2. A dictionary carrying optional keys:

    • 'dns_query': when it is set to False, the DNS (dig / check_output) back-end is disabled for that protocol.
    • 'http_url': when it is set to False, the HTTP (urlopen) back-end is disabled for that protocol.

    When this dictionary disables both back-ends, _retrieve_ip_address must return a falsy value without calling either back-end.

  3. Absent / default — both back-ends are enabled and get attempted (DNS first, then the HTTP fallback).

Retrieval Behavior and Order

For a given protocol version for which retrieval is enabled:

  1. DNS back-end first. An attempt is made to resolve the address via check_output (the dig tool).

    • If check_output raises TimeoutExpired or FileNotFoundError, this counts as a hard failure of the DNS back-end: the exception must be caught, and the HTTP fallback must then be attempted.
    • If the string returned by check_output is non-empty (after stripping whitespace), that stripped string is the result and is returned. The HTTP back-end must NOT be called.
    • If check_output returns a string that is empty or contains only whitespace (a soft failure, e.g. '\n'), the DNS back-end is considered to have produced no address, and no HTTP fallback is performed for that attempt — the method returns a falsy value.

    In short: the HTTP fallback occurs only when the DNS tool hard-fails (raises one of the caught exceptions), not when it merely returns an empty result.

  2. HTTP back-end (fallback). When this back-end is reached (the DNS back-end hard-failed, or DNS was disabled while HTTP is enabled), an attempt is made to resolve via urlopen.

    • The address is read from the response object via its .read() method. The value obtained this way is a bytes object; it must be decoded to a string and stripped of surrounding whitespace before being returned.
    • If reading from urlopen raises a socket timeout (socket.timeout), it is caught and treated as a failure, and a falsy value is returned.

Summary of Edge Cases

  • DNS hard-fails, HTTP succeeds → the HTTP-resolved (stripped) address is returned.
  • DNS succeeds → the DNS address is returned; HTTP is never called.
  • DNS soft-fails (empty output) → a falsy value is returned; HTTP is never called.
  • HTTP .read() raises a socket timeout → a falsy value is returned.
  • Protocol disabled via False → a falsy value is returned; no back-end is called.
  • Both back-ends disabled via the dict flags → a falsy value is returned; no back-end is called.

Output Formatting

  • Multiple addresses are joined with ", ".
  • An empty value list produces the configured no_address default string.

Task Specification: LAN IP Entry — Robust Handling of IPv6 Addresses

Summary

The LanIP entry class in archey.entries.lan_ip is to be modified; it is importable as:

from archey.entries.lan_ip import LanIP

From the existing network-interface enumeration facility, the entry collects local IPv4 addresses and, optionally, IPv6 addresses. It must expose the retained addresses in a normalized, human-readable form, must exclude loopback addresses, must honor the address-count and IPv6 options, and must produce the correct text for populated, empty, and unavailable states.

Interface discovery itself stays unchanged. Interfaces are supplied by the facility, together with per-interface mappings keyed by address-family constants such as AF_INET, AF_INET6, and possibly non-IP families. Every address record contains at least an 'addr' string.

Public API

The class must continue to be constructible as:

LanIP(options={
    'max_count': <non-negative int or False>,
    'ipv6_support': <bool>
})

Each of the two options is optional:

  • The default for max_count is 2.
  • The default for ipv6_support is True.

Once constructed:

  • When the network-interface facility is available, lan_ip.value is a list of the retained address strings — even when that list is empty.
  • When the optional network-interface facility is unavailable, lan_ip.value is None.
  • lan_ip.output(output) must use output.append(...) to add one entry, passing the entry's name as the first positional argument and the display text described below as the second positional argument.

Selecting the Addresses

Address families

IPv4 (AF_INET) addresses remain eligible for collection at all times. IPv6 (AF_INET6) addresses are eligible only when ipv6_support is True. With ipv6_support set to False, IPv6 records must not appear in value, while eligible IPv4 records remain.

Records from other families — including link-layer or MAC-address records — must not be included. Only the loopback exclusions described below are required; apart from those, link-local and private IP addresses are valid.

Normalizing Each Address

Each eligible raw 'addr' string must undergo normalization before it is retained or checked for IPv6 loopback equivalence:

  1. Strip a CIDR or netmask suffix. Should the string contain /, remove the / together with everything that follows it. For example, 2a02::45:6789:abcd:0123/64 becomes 2a02::45:6789:abcd:0123.
  2. Strip an IPv6 zone or scope suffix. Should the string contain %, remove the % together with everything that follows it. For example, fe80::abcd:ef0:abef:dead%en0 becomes fe80::abcd:ef0:abef:dead. Within the raw address, the % is a literal character.
  3. Compress IPv6 text canonically. For AF_INET6 records, leading zeroes are removed from groups and the longest eligible run of all-zero groups is replaced with :: per standard IPv6 textual compression rules. The canonical hexadecimal casing and tie-breaking rules must be used. Examples:
    • 2001:0000:0000:0000:0045:6789:abcd:6817 becomes 2001::45:6789:abcd:6817.
    • 0000:0000:0000:0000:0000:0000:0000:0001 becomes ::1.

IPv4 text is not reformatted in any other way; after the suffixes are removed, an address such as 192.168.1.55 remains 192.168.1.55.

Excluding Loopback Addresses

The entry must not retain loopback addresses:

  • IPv4 addresses beginning with 127. are excluded.
  • The IPv6 loopback address semantically equivalent to ::1 is excluded.

This exclusion must be representation-independent and must take place after, or as part of, semantic normalization. As a result, both ::1 and 0000:0000:0000:0000:0000:0000:0000:0001 are excluded, as are equivalent inputs carrying removable CIDR or zone suffixes. A fully expanded IPv6 loopback must never survive merely because its raw spelling was not already ::1.

Loopback records that are excluded do not consume the max_count allowance.

Ordering and Limiting

The order that results is deterministic:

  1. IPv4 addresses that are retained come first, in interface/address discovery order.
  2. IPv6 addresses that are retained follow, in interface/address discovery order.

The addresses must not be reordered by normalization. Each retained discovery contributes its normalized address, and no sorting by textual or numeric value is performed.

max_count is applied to the final stream of eligible, normalized, non-loopback addresses while that order is preserved:

  • A positive integer means at most that many addresses are retained.
  • The integer 0 retains no addresses and therefore produces an empty list.
  • The boolean False is the explicit unlimited sentinel and retains all eligible addresses. It must not be equated with integer 0, even though both are falsy in Python.
  • When the option is omitted, the default limit is 2.

Output Behavior

Depending on the entry state, output() must choose its second append argument as follows:

  1. Non-empty list: All strings in value are joined with exactly ", " (a comma followed by one space).
  2. Empty list with enumeration available: The configured default_strings.no_address value is used instead of an empty string. Under the default configuration, this is exactly DEFAULT_CONFIG['default_strings']['no_address']. The following situations fall under this case: no interfaces, interfaces with no IP records, hosts exposing only excluded loopbacks, IPv6-only results when IPv6 is disabled, and max_count=0.
  3. Enumeration facility unavailable: value is left as None, the entry fails softly rather than attempting discovery, and the configured default_strings.not_detected value is used. Under the default configuration, this is exactly DEFAULT_CONFIG['default_strings']['not_detected'].

Overrides of these default strings through configuration must continue to be honored.

Worked Example

Assume discovery produces the following eligible candidates:

  • IPv4: 192.168.1.55
  • IPv6, in this order:
    • 2001:0000:0000:0000:0045:6789:abcd:6817
    • fe80::abcd:ef0:abef:dead%en0
    • 2a02::45:6789:abcd:0123/64

Using:

    'max_count': 3,
    'ipv6_support': True
})

the value that results must be:

[
    '192.168.1.55',
    '2001::45:6789:abcd:6817',
    'fe80::abcd:ef0:abef:dead'
]

and the display text supplied to output.append as the second positional argument must be:

Although the fourth candidate, 2a02::45:6789:abcd:0123, is normalized, the limit omits it. Should discovery also supply 127.0.0.1 or an expanded spelling of the IPv6 loopback, those records would be excluded before the limit is applied.
