Specification of the Task

Your job is to implement two independent features that span two modules in this codebase.

Feature 1: Detect partitions that are used as libvirt/KVM virtual machine disks

You will work in the module pov_server_page.disk_inventory. Extend the existing disk-inventory class in this module with the capabilities below. In what follows, instances of that class are referred to as info.

Domain definitions in Libvirt

For each VM, Libvirt keeps the domain XML at /etc/libvirt/qemu/<name>.xml. A domain definition has this shape:

<domain type='kvm'>
  <name>box</name>
  ...
  <devices>
    <emulator>/usr/bin/kvm</emulator>
    <disk type='file' device='disk'>
      <driver name='qemu' type='raw'/>
      <source file='/dev/fridge/box'/>
      <target dev='vda' bus='virtio'/>
      ...
    </disk>
    ...
  </devices>
</domain>

The data of interest are:

  • the name of the VM, taken from /domain/name,
  • the backing paths of the disks, taken from each /domain/devices/disk/source/@file.

XML files must be parsed with xml.etree.ElementTree. Be aware that the XML content may be surrounded by leading/trailing whitespace and indentation.

A disk source file such as /dev/fridge/box is a symlink that points to a device node (e.g. ../dm-34). To identify the partition it maps to, resolve the symlink to its device-mapper node and then find the corresponding device-mapper name.

Device-node and device-mapper resolution
  • Paths in the style of /dev/mapper/<dm-name> and /dev/<vg>/<lv> are symlinks into the same underlying dm-N device node.
  • Device-mapper names together with their minor numbers are obtained by running the command:
    dmsetup -c --noheadings info
    Each output line consists of colon-separated fields; the device-mapper name is the first field and the minor number is the third. The name foo-bar corresponds to the device node dm-<minor> and is exposed as the partition identifier mapper/foo-bar.

So, the symlink /dev/fridge/box -> ../dm-34 combined with a dmsetup line whose name is fridge-box and whose minor is 34 means that the VM box is backed by the partition mapper/fridge-box.

Methods to add

Add the following methods to the disk-inventory class:

  1. list_kvm_vms(self) Return a list of (vm_name, partition) tuples, one for each VM disk that can be resolved to a known partition. partition takes the mapper/<name> form described above. For the example above, this gives:

    [('box', 'mapper/fridge-box')]

  2. get_partition_kvm_vm(self, partition) When given a partition identifier (e.g. 'mapper/fridge-box'), return the (vm_name, partition) tuple for the VM whose disk is backed by that partition, or None if no VM uses it. In the example:

    info.get_partition_kvm_vm('mapper/fridge-box') == ('box', 'mapper/fridge-box')

  3. get_partition_usage(self, partition) — extend the behavior that already exists. This method already classifies how a partition is used. When the partition is used as a KVM VM disk and no higher-priority usage applies, it must return the string:

    KVM: <vm_name>

    e.g. 'KVM: box' in the example. This case covers a device-mapper partition that has no holders (i.e. the directory /sys/block/dm-34/holders exists and is empty) and is not otherwise in use (not a swap device, not an LVM PV, not mounted).

Environment and I/O notes for this feature
  • Reading the domain XML is done with xml.etree.ElementTree, which opens files via open(filename, mode) where mode may be 'r' or 'rb'. Ensure that your file access goes through the module-level open.
  • To enumerate VMs, you must scan /etc/libvirt/qemu/ for *.xml files.
  • If the directory /etc/libvirt/qemu/ does not exist or cannot be listed, treat that as a host with no defined VMs rather than raising an error. In this case:
    • list_kvm_vms() returns [];
    • get_partition_kvm_vm(...) returns None; and
    • get_partition_usage(...) continues its normal classification and does not add a KVM annotation. An otherwise-unused device-mapper partition therefore retains its existing empty usage string.
  • When a disk source file does not resolve to any known partition, it is simply skipped.

Task Description

Summary

This task improves the disk inventory's LVM physical-volume (PV) information such that every recognized PV exposes its own free, unallocated capacity. It must be possible to get this per-PV free value through the PV-related public APIs, and the corresponding partition line in the human-readable disk report must show it.

This value belongs to one individual physical volume. It is different from filesystem free space as well as from the aggregate free space of an LVM volume group.

Public API Changes

This change touches the following methods of the disk-info object.

list_lvm_physical_volumes()

For every recognized LVM physical volume, return one tuple-compatible record, keeping the order of the existing discovery. Every record must now consist of exactly three positional elements:

(device_name, volume_group_name, free_bytes)
  • device_name: the canonical PV device identifier as it already exists, with the /dev/ prefix stripped off — such as mapper/sda5_crypt.
  • volume_group_name: the volume group's existing name, that group being the one containing the PV — such as platonas.
  • free_bytes: an integer holding, in bytes, the amount of space on that particular PV that is free and unallocated.

For the first two fields, neither the order nor the meaning changes. The third field is where the new byte count gets appended. If the free capacity is supplied by LVM in the form of a free-extent count together with an extent size in KiB, the observable value is:

free_bytes = free_extent_count * extent_size_kib * 1024

A fully allocated PV therefore ends up with free_bytes == 0. Diagnostic output that is not a record, when it is encountered during PV discovery, must keep being ignored instead of producing a PV record.

As an example:

[('mapper/sda5_crypt', 'platonas', 0)]
get_partition_lvm_pv(partition_name)

If the partition is an LVM physical volume already, or resolves to one by way of its existing RAID/device-mapper holder lookup, return the same three-element PV record:

(device_name, volume_group_name, free_bytes)

Even when the PV is layered through another block device, so that the device differs from partition_name, the device name in the returned record is the actual canonical PV device.

When the partition does not resolve to an LVM physical volume, return None, as before.

Human-Readable Report

Lines for PV partitions

Within the report that report_text() produces, an LVM PV partition is already flagged with this usage marker:

LVM: <volume_group_name>

For every partition of this kind, append the free capacity belonging to that PV, in this form:

<free_size> free

To produce <free_size>, take free_bytes and run it through the active human-readable size formatter — the same one used for the report's other sizes. That is why the default report uses decimal units such as MB and GB; when another supported formatter is selected, the PV free value must be formatted with it too. One decimal place is kept in the formatting. A zero value in bytes, specifically, renders as 0.0 B, so the suffix for a fully allocated PV is still 0.0 B free.

Taken as a whole, a PV partition line has this conceptual form:

  <partition>:             <size>  LVM: <vg_name><padding><free_size> free

Left alignment in the report's usage column is kept for the existing LVM: <vg_name> usage label, and the free-space output column that already exists is where the new value sits. For the free capacity displayed at this spot, the matched PV record must be the source — not the containing volume group, and not a mounted filesystem.

Precise alignment requirement

Consider the required default-layout example below. Counting from the first character of the volume-group name, the first character of 0.0 B free begins exactly 32 character positions after it; 24 positions after the start of the name is not where it begins. platonas is eight characters long, so the text contains exactly 24 literal spaces after platonas before 0.0 B free — put another way, the name together with its trailing padding spans 32 characters in this layout.

For a 499.6 GB PV that sits in volume group platonas and has zero bytes free, the line must be exactly:

  sde5:             499.6 GB  LVM: platonas                        0.0 B free

Compatibility Notes and Non-Goals

  • get_partition_usage(partition_name) is not touched: its usage text stays as it is. When the partition is an LVM PV, the LVM fragment in that text remains exactly LVM: <volume_group_name>; the free-space suffix is a report-rendering concern and is not added to that method's return value.
  • Lines for partitions that are not PVs do not get a PV free-space suffix; apart from that they stay unchanged.
  • Filesystem free-space reporting, as it stands, is left untouched.
  • Records for LVM logical volumes, records for volume groups, and the volume-group-level free: report lines stay as they are.
  • A PV free value of zero must be displayed instead of being omitted.

TextReporter and HtmlReporter must continue to be exposed by the module.

Construction and the output callback

A print keyword argument whose value is a callable must be accepted by both reporter classes:

TextReporter(print=<callable>)
HtmlReporter(print=<callable>)

Reporter output must be sent through this callable instead of going directly to standard output. Every output line is emitted by one call carrying one string argument, and that argument must not contain a trailing newline. This must work in environments where print is provided as a callback.

The reporter options that already exist remain supported. In particular, text reporters default to verbose=1, and the existing firmware-revision behavior at verbose >= 2 must be retained.

start_disk

Both classes, as well as the common reporter hook that the aggregate reporting flow uses, must accept all five disk values under these parameter names:

start_disk(self, disk, model, fwrev, disk_size_bytes, is_ssd)

These are the arguments:

  • disk: the name of the disk, such as "sda".
  • model: the disk's model string.
  • fwrev: the string for the firmware revision.
  • disk_size_bytes: the disk size in bytes as an integer.
  • is_ssd: a boolean that indicates whether the disk is a detected solid-state disk.

is_ssd is required and has no default. For every disk, the aggregate reporting path must supply it.

Formatting of disk sizes

The disk sizes in the required examples and in default output use decimal units. The conversion from bytes uses powers of 1000, and the value is formatted with one decimal place and a space before the unit. So 40 * 1000**3 bytes is rendered as 40.0 GB.

The support that already exists for a caller-supplied size formatter must not be broken.

Text output

Base heading of a disk

At verbose >= 2, that same line continues to include the existing firmware clause:

<disk>: <model> (<size>), firmware revision <fwrev>

The suffix [SSD] is appended to the end of the completed heading only when both conditions hold:

  1. is_ssd is true; and
  2. model does not contain the literal, case-sensitive substring SSD.

  • The suffix is never given to a non-SSD.
  • An SSD with a model that does not contain SSD receives the suffix.
  • An SSD whose model already contains SSD, such as Samsung SSD 850, does not get another SSD suffix.

result = []

["sda: Weird solid state disk (40.0 GB) [SSD]"]

sda: Weird solid state disk (40.0 GB), firmware revision FW42 [SSD]

sda: Samsung SSD 850 (500.1 GB), firmware revision 2B6Q

The second of these forms applies at verbose >= 2.

  • byte 0: the peripheral device type; this is not part of the serial;
  • byte 1: the page code, 0x80;
  • bytes 2–3: a 16-bit page length that is unsigned and big-endian;
  • byte 4 onward: the serial-number field, whose length is specified by bytes 2–3.

Extract exactly the serial field that has been declared, decode it to text, and strip the surrounding whitespace. Bytes after the declared serial field are not part of the serial.

For example, given the following bytes, which contain a 20-byte serial field:

b'\x00\x80\x00\x14S6PENX0RC46472K     '

the result must be:

'S6PENX0RC46472K'
1.3 When no serial is available

When neither source exists, return exactly:

'N/A'

This also covers virtual disks, such as a KVM/virtio vda, when sysfs exposes neither serial source.

2. The reporter interface

Update the disk-start interface shared by the reporters, together with both concrete reporters, TextReporter and HtmlReporter, so that they accept the serial string. The signature of the disk-start method is:

start_disk(self, disk, model, serial, fwrev, disk_size_bytes, is_ssd)

serial is a required argument; it is displayed verbatim as text and remains subject to the existing output escaping rules for the selected format. fwrev stays part of the interface.

Reporter instances still accept a print keyword argument. This argument is a callable that is invoked once for each emitted output line. Existing constructor options — including verbose and fmt_size — remain in effect.

3. Disk headers in text output

TextReporter.start_disk emits a single disk-header line. The serial segment always appears immediately after the parenthesized size. Firmware stays verbosity-dependent.

3.1 Verbosity below 2

When verbose < 2, use this form and do not include the firmware revision:

<disk>: <model> (<size>), serial <serial><optional SSD suffix>

For example, at the default verbosity, with serial='42' and an SSD model that does not already contain the literal text SSD:

sda: Weird solid state disk (40.0 GB), serial 42 [SSD]
3.2 Verbosity 2 or higher

When verbose >= 2, the firmware segment is appended immediately after the serial segment:

<disk>: <model> (<size>), serial <serial>, firmware revision <fwrev><optional SSD suffix>

For example:

sda: Weird solid state disk (40.0 GB), serial 42, firmware revision FW42 [SSD]

Therefore the text reporter must leave out , firmware revision <fwrev> at lower verbosity and include it at verbosity 2 and above.

3.3 SSD suffix in text

Keep the text reporter's SSD labeling free of redundancy:

  • [SSD] is never appended when is_ssd is false;
  • when is_ssd is true, [SSD] is appended at the end of the line unless the model already contains the literal uppercase substring SSD;
  • if the model already contains SSD, no redundant text suffix is added.

Regardless of SSD labeling, the serial segment and, when applicable, the firmware segment are still included.

4. Disk headers in HTML output

The heading emitted by HtmlReporter.start_disk always includes both the serial and the firmware revision, in this order: size, serial, firmware revision. Unlike the text heading, the firmware field of the HTML heading is not conditional on verbosity.

With disk='sda', model='My good SSD', a formatted size of 40.0 GB, serial='42', fwrev='FW42', and is_ssd=True, the emitted lines are:

<tr>
  <th colspan="4">
    sda: My good SSD (40.0 GB), serial 42, firmware revision FW42
    <span class="label label-info">SSD</span>
  </th>
</tr>

So the heading text takes this form:

<disk>: <model> (<size>), serial <serial>, firmware revision <fwrev>

The SSD badge line is emitted when is_ssd is true and is omitted when it is false. Even when the model itself contains SSD, this HTML badge remains present for an SSD. The existing HTML escaping applies to all interpolated heading values, including the new serial value.

5. Integration into the full report

Because the report-generation flow is shared, both report_text(...) and report_html(...) must obtain every disk's serial with get_disk_serial(disk) and pass it to the reporter's start_disk call. The serial lookup applies to every physical disk that is reported.

As a result:

  • , serial <serial> appears in every text disk header;
  • , serial <serial>, firmware revision <fwrev> appears in every HTML disk header;
  • when no source is available, reports show serial N/A;
  • as specified above, text firmware output continues to depend on verbosity.

For example, a verbose text report (verbose >= 2) may start with:

sda: Samsung SSD 850 (500.1 GB), serial N/A, firmware revision 2B6Q

At lower verbosity, the matching form is:

sda: Samsung SSD 850 (250.1 GB), serial N/A

The latter contains no firmware segment. Since the model already contains SSD, the text reporter does not add a redundant [SSD] suffix.

6. Handling of file contents

The direct serial source may be read as either text or bytes, but get_disk_serial must return text rather than bytes. The VPD source must be processed as binary data so that its header and big-endian length are interpreted correctly; the only bytes that are decoded to text are the extracted serial bytes. In both cases, the decoded serial is stripped before it is returned.
