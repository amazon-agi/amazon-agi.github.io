Feature 1: Recognize partitions used as libvirt/KVM virtual machine disks

Work in the module pov_server_page.disk_inventory. Add the following capabilities to the existing disk-inventory class in this module. Instances of that class are referred to below as info.

Libvirt domain definitions

Libvirt stores each VM's domain XML in /etc/libvirt/qemu/<name>.xml. A domain definition looks like:

<domain type='kvm'>
  <name>box</name>
  ...
  <devices>
    <emulator>/usr/bin/kvm</emulator>
    <disk type='file' device='disk'>
      <driver name='qemu' type='raw'/>
      <source file='/dev/fridge/box'/>
      <target dev='vda' bus='virtio'/>
      ...
    </disk>
    ...
  </devices>
</domain>

The relevant data are:

  • the VM name, from /domain/name,
  • the disk backing paths, from each /domain/devices/disk/source/@file.

XML files must be parsed using xml.etree.ElementTree. Note the XML content may be surrounded by leading/trailing whitespace and indentation.

A disk source file such as /dev/fridge/box is a symlink pointing to a device node (e.g. ../dm-34). The partition that this maps to is identified by resolving the symlink to its device-mapper node and then finding the corresponding device-mapper name.

Device-node / device-mapper resolution
  • /dev/mapper/<dm-name> and /dev/<vg>/<lv> style paths are symlinks into the same underlying dm-N device node.
  • Device-mapper names and their minor numbers are obtained by running the command:
    dmsetup -c --noheadings info
    Each output line has colon-separated fields; the first field is the device-mapper name and the third field is the minor number. A name foo-bar corresponds to the device node dm-<minor> and is exposed as the partition identifier mapper/foo-bar.

Thus the symlink /dev/fridge/box -> ../dm-34, combined with a dmsetup line whose name is fridge-box and whose minor is 34, means the VM box is backed by the partition mapper/fridge-box.

Required methods

Add these methods to the disk-inventory class:

  1. list_kvm_vms(self) Return a list of (vm_name, partition) tuples, one per VM disk that can be resolved to a known partition. partition is in the mapper/<name> form described above. For the example above this yields:

    [('box', 'mapper/fridge-box')]

  2. get_partition_kvm_vm(self, partition) Given a partition identifier (e.g. 'mapper/fridge-box'), return the (vm_name, partition) tuple for the VM whose disk is backed by that partition, or None if no VM uses it. For the example:

    info.get_partition_kvm_vm('mapper/fridge-box') == ('box', 'mapper/fridge-box')

  3. get_partition_usage(self, partition) — extend existing behavior. This method already classifies how a partition is used. When the partition is used as a KVM VM disk, and no higher-priority usage applies, it must return the string:

    KVM: <vm_name>

    e.g. 'KVM: box' for the example. This case applies to a device-mapper partition that has no holders (i.e. the directory /sys/block/dm-34/holders exists and is empty) and is not otherwise in use (not a swap device, not an LVM PV, not mounted).

Environment / I/O notes for this feature
  • Reading domain XML uses xml.etree.ElementTree, which opens files via open(filename, mode) where mode may be 'r' or 'rb'. Ensure your file access goes through the module-level open.
  • The VM enumeration must scan /etc/libvirt/qemu/ for *.xml files.
  • If the directory /etc/libvirt/qemu/ does not exist or cannot be listed, treat that as a host with no defined VMs rather than raising an error. In this case:
    • list_kvm_vms() returns [];
    • get_partition_kvm_vm(...) returns None; and
    • get_partition_usage(...) continues its normal classification without adding a KVM annotation. An otherwise-unused device-mapper partition therefore retains its existing empty usage string.
  • If a disk source file does not resolve to any known partition, it is simply skipped.

The value is specific to an individual physical volume. It is distinct from filesystem free space and from the aggregate free space of an LVM volume group.

Public API Surface

The following methods on the disk-info object are affected.

list_lvm_physical_volumes()

Return one tuple-compatible record per recognized LVM physical volume, preserving the existing discovery order. Every record must now have exactly three positional elements:

(device_name, volume_group_name, free_bytes)
  • device_name is the existing canonical PV device identifier without the /dev/ prefix, such as mapper/sda5_crypt.
  • volume_group_name is the existing name of the volume group containing the PV, such as platonas.
  • free_bytes is an integer containing the number of free, unallocated bytes on that particular PV.

The first two fields retain their existing order and meaning. The new byte count is appended as the third field. If LVM reports the free capacity as a free-extent count and an extent size in KiB, the observable value is:

free_bytes = free_extent_count * extent_size_kib * 1024

Consequently, a fully allocated PV has free_bytes == 0. Non-record diagnostic output encountered during PV discovery must continue to be ignored rather than producing a PV record.

Example:

[('mapper/sda5_crypt', 'platonas', 0)]
get_partition_lvm_pv(partition_name)

For a partition that is, or resolves through its existing RAID/device-mapper holder lookup to, an LVM physical volume, return the same three-element PV record:

(device_name, volume_group_name, free_bytes)

The returned device name is the actual canonical PV device, even when it differs from partition_name because the PV is layered through another block device.

For a partition that does not resolve to an LVM physical volume, return None as before.

Human-Readable Report

PV partition lines

The report generated by report_text() already identifies an LVM PV partition with the usage marker:

LVM: <volume_group_name>

For every such partition, append that PV’s free capacity as:

<free_size> free

<free_size> is free_bytes formatted with the same active human-readable size formatter used for the other sizes in the report. The default report therefore uses decimal units such as MB and GB; when another supported formatter is selected, the PV free value must use that formatter as well. Formatting retains one decimal place. In particular, zero bytes is rendered as 0.0 B, so a fully allocated PV still displays the suffix 0.0 B free.

The complete conceptual form of a PV partition line is:

  <partition>:             <size>  LVM: <vg_name><padding><free_size> free

The existing LVM: <vg_name> usage label remains left-aligned in the report’s usage column, while the new value occupies the existing free-space output column. The free capacity shown here must come from the matched PV record, not from the containing volume group or a mounted filesystem.

Exact alignment requirement

In the required default-layout example below, the first character of 0.0 B free begins exactly 32 character positions after the first character of the volume-group name. It does not begin 24 positions after the name starts. Because platonas has eight characters, there are exactly 24 literal spaces after platonas before 0.0 B free; equivalently, the name plus its trailing padding occupies 32 characters in this layout.

For a 499.6 GB PV in volume group platonas with zero bytes free, the line must be exactly:

  sde5:             499.6 GB  LVM: platonas                        0.0 B free

Compatibility and Non-Goals

  • get_partition_usage(partition_name) retains its existing usage text. For an LVM PV, its LVM fragment remains exactly LVM: <volume_group_name>; the free-space suffix belongs to report rendering and is not added to that method’s return value.
  • Non-PV partition lines do not gain a PV free-space suffix and otherwise remain unchanged.
  • Existing filesystem free-space reporting remains unchanged.
  • LVM logical-volume records, volume-group records, and volume-group-level free: report lines remain unchanged.
  • A zero PV free value must be displayed rather than omitted.

  • Calling the decorated method on an instance returns the value produced by the underlying method.
