Overview

Public API

A function that accepts a single argument — a path (string) to a source directory containing operator manifest files — and returns a list describing how the manifest files in that directory tree would be flattened.

Return value:

  • If the source directory is already flat (all manifest files reside directly in source_dir, with no version subdirectories), return an empty list [].
  • Otherwise, return a list of 2-tuples (source_file_path, flattened_basename), where:

    • flattened_basename is the file name that this file would receive in a flat layout.

The order of the returned list is not significant; callers compare it as an unordered set.

Directory Structure Being Processed

A non-flat source directory contains:

  • Exactly one package file located directly in source_dir. Its filename ends with .package.yaml. Its content is a YAML document containing packageName and channels (each channel having name and currentCSV).
  • One or more version subdirectories (e.g. 0.6.1, 0.9.0, 0.9.2), each named after an operator version. Each version subdirectory contains:
    • One ClusterServiceVersion (CSV) file: a YAML document with kind: ClusterServiceVersion. Its spec.version field holds the operator version (e.g. 0.6.1). The CSV filename varies (for example etcdoperator.clusterserviceversion.yaml or etcdoperator.v0.9.0.clusterserviceversion.yaml).

A flat source directory contains the package file, the CSV file(s), and the CRD file(s) all directly inside source_dir, with no version subdirectories.

Flattening Rules

Determine the classification of each manifest file by reading its YAML content (not by relying on its filename), except for the package file which is identified by its .package.yaml filename suffix.

Package file
  • Keep its original basename unchanged.
  • Example: etcd.package.yaml → etcd.package.yaml
ClusterServiceVersion (CSV) files
  • Each CSV's flattened basename is derived from its original basename by inserting the operator version.
  • Take the original CSV basename, strip the trailing .yaml extension, then append -v<version>.yaml, where <version> is the value of the CSV's spec.version.
  • Examples:
    • basename etcdoperator.clusterserviceversion.yaml with spec.version: 0.6.1 → etcdoperator.clusterserviceversion-v0.6.1.yaml
    • basename etcdoperator.v0.9.0.clusterserviceversion.yaml with spec.version: 0.9.0 → etcdoperator.v0.9.0.clusterserviceversion-v0.9.0.yaml
    • basename etcdoperator.clusterserviceversion.yaml with spec.version: 0.9.2 → etcdoperator.clusterserviceversion-v0.9.2.yaml

This versioned renaming ensures that CSV files sharing the same basename across different version subdirectories map to distinct flattened names.

  • CRDs are deduplicated by basename: when the same CRD basename appears in multiple version subdirectories, exactly one entry for that basename is included in the result. Overview

operatorcourier processes Kubernetes Operator manifest bundles supplied either as a directory or as YAML strings. Source directories may use a flat layout or a version-nested layout. Directory classification and bundle processing must be based on recognized Operator manifests rather than on the mere presence of child directories. Irrelevant files and folders must not alter classification, validation, or flattening results.

This task also performs source-directory package-count checks during manifest parsing while preserving the existing checks exposed by direct bundle validation.

Definitions

  • A manifest file is a .yaml or .yml file whose parsed document is one of:
    • a ClusterServiceVersion (CSV);
    • a CustomResourceDefinition (CRD); or
    • a package manifest containing packageName and channels.
  • A valid version manifest folder is a child directory representing one version of a bundle and containing version-specific Operator manifests, including a valid CSV and optionally CRDs. Its directory name is not required to be a semantic version; names such as version_0.6 are valid.
  • A package-only folder is not a valid version manifest folder. Packages for a nested source belong in the source root.
  • A flat source has its bundle manifests directly in the source root and has no valid version manifest folders.
  • A nested source has at least one valid version manifest folder.
  • An irrelevant folder is a child directory that is not a valid version manifest folder. Examples include a directory containing only arbitrary text, or one containing only a package manifest and arbitrary text.

Source discovery and directory classification

Classification must inspect child directories for valid version manifest content. It must not classify a source as nested merely because a child directory exists.

  • Non-YAML files, arbitrary stray files, and irrelevant folders do not participate in the bundle.
  • An irrelevant folder must not contribute any package, CSV, or CRD to processing, even if it contains a package YAML.
  • If no valid version manifest folder exists, the source is flat. Only recognized root manifest files are used; child-folder content is ignored.
  • If one or more valid version manifest folders exist, the source is nested. Only those valid version folders are processed, and irrelevant sibling folders and stray root files are ignored.
  • The presence of both a complete root bundle and an irrelevant child folder must therefore produce the same flat bundle as the root files alone.
  • A nested source remains nested and valid when irrelevant sibling folders or files are present.
Nested root-manifest rule

Once a source is classified as nested, the package manifest is the only manifest retained from the source root. Root-level CSVs, CRDs, and all other non-package manifests must be ignored. Each valid version folder is processed using its own version-specific CSV and CRDs together with the single root package manifest.

Consequently, a root CSV must not be added to any nested version bundle and must not appear in flattened output. This rule applies even when the root CSV is itself otherwise valid.

Source-directory package validation

Exactly one package manifest must exist in the source root. Package manifests found in irrelevant child folders do not count toward this requirement.

These source-level checks occur during manifest parsing and use logger name operatorcourier.manifest_parser. The module operatorcourier.manifest_parser must be importable and must be the logging source for these diagnostics.

  • If the source root has no package manifest, parsing fails and logs this exact error:

    Bundle does not contain any packages.

  • If the source root has more than one package manifest, parsing fails and logs this exact error:

    Only 1 package is expected to exist in source root folder.

  • When the multiple-root-package condition is reached through the public build/verify API, it raises operatorcourier.errors.OpCourierBadBundle, and str(exception) must be exactly:

    Only 1 package is expected to exist in source root folder.

The parser-level check supplements rather than replaces validation of an already assembled bundle.

  • yamls accepts a list of YAML document strings. Callers supply document contents, not filenames.

Successful results

Flattening contract

operatorcourier.flatten.get_flattened_files_info(source_dir) returns a collection of (source_path, flattened_name) pairs describing the files selected for flattened output. Pair order is not significant.

The same flat-versus-nested discovery rules apply to flattening.

Flat input

For an already flat source, return the recognized manifest files directly in the root. Each source path is paired with its unchanged base filename. Ignore all irrelevant subfolders and their contents, including package-only subfolders, as well as stray non-manifest files.

Nested input

For a nested source, flattened output consists of:

  1. the single package manifest from the source root;
  2. every CSV from each valid version manifest folder; and
  3. the newest version of each distinct CRD represented across the valid version folders.

The newest CRD is selected by Operator version, using the CSV's spec.version for its version folder and identifying a CRD by its manifest identity such as metadata.name. Existing CSV and CRD selection behavior must otherwise remain unchanged.

No root-level CSV, CRD, or other non-package manifest may be included once nested mode is selected. Irrelevant sibling folders also contribute no output.

Flattened names follow these rules:

  • The root package keeps its original base filename.
  • CRDs keep their original base filenames.
  • Every nested CSV has -v<folder-name> inserted immediately before its extension, where <folder-name> is the actual name of the version folder. For example, 0.9/etcdoperator.clusterserviceversion.yaml becomes etcdoperator.clusterserviceversion-v0.9.yaml.
  • Flat-source filenames are unchanged and receive no version suffix.

Thus, duplicate CSV basenames in different version folders remain distinguishable, while package and selected CRD basenames remain unchanged.

Command-line consistency

Source-directory discovery and package parsing must be consistent for commands that build and verify a source, including verify and push workflows.

  • Valid flat and nested sources, including sources with irrelevant content, complete verification successfully.
  • Invalid source parsing or bundle validation produces a nonzero command exit.
  • Missing and multiple root packages expose the exact operatorcourier.manifest_parser diagnostics given above.
  • Existing validator errors, including repository mismatches, continue to be emitted by operatorcourier.validate.
  • Verification with a validation-output destination creates the JSON output for both valid and validation-invalid bundles, with errors empty only for valid output.

Compatibility scope

This change is limited to manifest discovery, flat-versus-nested classification, nested root-file selection, and the timing of source-directory package checks. Existing CSV, CRD, package-field, repository, and optional OperatorHub UI validation behavior remains in effect. Existing package exceptions, including OpCourierBadBundle's ValueError compatibility, must remain compatible.
