The tool exposes an executable command named operator-courier. The invocation format is:

operator-courier verify <source_dir>

with <source_dir> being a path to a directory containing operator manifest YAML files (CSV files, CRD files, and a package file).

The bundle is put together from all YAML manifests found in the source directory. Each bundle is expected to have exactly one package manifest.

    ERROR:operatorcourier.validate:Only 1 package is expected to exist per bundle, but got 2.

  • On any verification failure (the package-count errors above included): a nonzero exit code.

Task: Create a Module for Flattening Bundles

Overview

Within the operatorcourier package, a new module by the name of operatorcourier/flatten.py is to be implemented. The module's task is to examine a nested directory of operator bundle YAML files and to work out how those files would map onto a "flattened" (single-level) layout. Besides that, one message string belonging to the existing validation logic is to be adjusted.

Public API

operatorcourier.flatten.get_flattened_files_info(source_dir)

The function accepts a single argument: a path (string) to a source directory in which operator manifest files live. Its return value is a list that describes how the manifest files in that directory tree would be flattened.

What is returned:

  • Should the source directory turn out to be already flat — all of its manifest files are located directly in source_dir, and no version subdirectories exist — an empty list [] must be returned.
  • In all other cases, a list of 2-tuples (source_file_path, flattened_basename) must be returned, its members being defined as follows:
    • source_file_path — the path of a file that exists within the source directory tree, stated relative to the same base as the source_dir that was passed in (that is, produced by joining source_dir with the relevant subpath). Forward-slash path separators are to be used, consistent with the input.
    • flattened_basename — the file name under which this file would appear in a flat layout.

Callers compare the result as an unordered set, so the order in which the list is returned is of no consequence.

Directory Structures Involved

When a source directory is not flat, it contains:

  • Exactly one package file, positioned directly in source_dir, with .package.yaml as the suffix of its filename; the content is a YAML document with packageName and channels, and each channel carries name and currentCSV.
  • One or more version subdirectories (for example 0.6.1, 0.9.0, 0.9.2), each one named after an operator version. Each version subdirectory houses:
    • a single ClusterServiceVersion (CSV) file: a YAML document that declares kind: ClusterServiceVersion. The operator version (e.g. 0.6.1) sits in its spec.version field. As for the CSV's filename, it varies from case to case — for example etcdoperator.clusterserviceversion.yaml or etcdoperator.v0.9.0.clusterserviceversion.yaml.
    • zero or more CustomResourceDefinition (CRD) files, each a YAML document declaring kind: CustomResourceDefinition.

In a flat source directory, by contrast, the package file along with the CSV file(s) and the CRD file(s) are all directly inside source_dir, and no version subdirectories exist.

Rules That Govern Flattening

To classify each manifest file, its YAML content is read; the filename is not relied upon for this. The package file is the lone exception, being identified through the .package.yaml suffix of its filename.

Package file
  • Its original basename is left untouched.
  • Example: etcd.package.yaml → etcd.package.yaml
ClusterServiceVersion (CSV) files
  • A CSV's flattened basename is obtained from its original basename by inserting the operator version into it.
  • To construct it: take the original CSV basename, remove the .yaml extension from its end, and then append -v<version>.yaml, with <version> being the value of the CSV's spec.version.
  • Examples:
    • basename etcdoperator.clusterserviceversion.yaml with spec.version: 0.6.1 → etcdoperator.clusterserviceversion-v0.6.1.yaml
    • basename etcdoperator.v0.9.0.clusterserviceversion.yaml with spec.version: 0.9.0 → etcdoperator.v0.9.0.clusterserviceversion-v0.9.0.yaml
    • basename etcdoperator.clusterserviceversion.yaml with spec.version: 0.9.2 → etcdoperator.clusterserviceversion-v0.9.2.yaml

The renaming just described, with the version baked in, ensures this: when CSV files in different version subdirectories have the same basename, the flattened names they map to are distinct.

CustomResourceDefinition (CRD) files
  • A CRD's original basename stays unchanged.
  • Deduplication applies to CRDs by basename: where one and the same CRD basename occurs in multiple version subdirectories, the result contains exactly one entry for that basename. The entry that wins comes from the latest version subdirectory, i.e. the operator version that is highest among those containing a CRD with that basename.

Layout of the Input

A nested bundle source may contain:

  • Files sitting directly at the top level, such as a package YAML file.
  • Immediate subdirectories that hold ClusterServiceVersion (CSV) manifests, CustomResourceDefinition (CRD) manifests, or unrelated files.

Sources That Are Already Flat

<original-stem>-v<directory-label>.yaml

Examples:

  • In 0.61, etcdoperator.clusterserviceversion.yaml becomes etcdoperator.clusterserviceversion-v0.61.yaml.
  • In 0.92, etcdoperator.v0.9.2.clusterserviceversion.yaml becomes etcdoperator.v0.9.2.clusterserviceversion-v0.92.yaml.
  • A CSV in random_folder gets the literal suffix -vrandom_folder.yaml.

  1. When a CRD name occurs in only one subdirectory, that source copy is the one selected.
  2. When the same CRD name occurs in multiple subdirectories, exactly one copy is included. The copy to select is the one from the subdirectory whose literal label is lexicographically greatest using case-sensitive string ordering. This comparison applies to the labels as written; it involves no SemVer parsing, numeric normalization, or version validation.
  3. The selected tuple returned by get_flattened_files_info must contain the path from that winning subdirectory, and the copied contents and output basename must come from that same source file. Copies residing in lower-ordered subdirectories must be omitted.

Arbitrary labels take part in the same literal string ordering if they contain CRDs.

This lexical rule serves solely as a deterministic selection policy for colliding CRD identities; it does not make directory labels into versions or impose a valid-version format.

Files at the Top Level

Files located directly at the top level of the source directory, the package YAML file included, must be included while keeping their existing basenames. A directory-label suffix must not be added to them.

Resulting Output

The destination that results is a single flat set of files containing:

  • Top-level source files, with their names unchanged.
  • Every CSV from every immediate manifest subdirectory, renamed using that directory's exact label.
  • For each distinct CRD metadata.name, one selected source copy under the selected file's unchanged basename.
  • No unrelated files originating in manifest subdirectories.

The essential compatibility requirement is that immediate subdirectory names are accepted as opaque labels instead of being validated as SemVer, while CSV renaming, deterministic CRD deduplication, top-level file handling, and already-flat input handling continue to work.

Overview

operatorcourier handles Kubernetes Operator manifest bundles supplied either as a directory or as YAML strings. Source directories may follow a flat layout or a version-nested layout. Classification of directories and processing of bundles must be driven by recognized Operator manifests rather than by the mere presence of child directories. Irrelevant files and folders must not have any effect on classification, validation, or flattening results.

This task also carries out source-directory package-count checks during manifest parsing while keeping the existing checks exposed by direct bundle validation.

Definitions

  • A manifest file is a .yaml or .yml file for which the parsed document is one of the following:
    • a ClusterServiceVersion (CSV);
    • a CustomResourceDefinition (CRD); or
    • a package manifest that contains packageName and channels.
  • A valid version manifest folder is a child directory that stands for one version of a bundle and holds version-specific Operator manifests, including a valid CSV and, optionally, CRDs. The name of the directory is not required to be a semantic version; names such as version_0.6 are valid.
  • A folder that contains only a package is not a valid version manifest folder. For a nested source, packages belong in the source root.
  • A flat source keeps its bundle manifests directly in the source root and contains no valid version manifest folders.
  • A nested source contains at least one valid version manifest folder.
  • An irrelevant folder is a child directory that does not count as a valid version manifest folder. Examples include a directory that holds only arbitrary text, or one that holds only a package manifest and arbitrary text.

Discovering sources and classifying directories

Classification must examine child directories for valid version manifest content. A source must not be classified as nested merely because a child directory exists.

  • Non-YAML files, arbitrary stray files, and irrelevant folders do not form part of the bundle.
  • An irrelevant folder must not contribute any package, CSV, or CRD to processing, even when it holds a package YAML.
  • When no valid version manifest folder exists, the source is flat. Only recognized root manifest files are used; the content of child folders is ignored.
  • When one or more valid version manifest folders exist, the source is nested. Only those valid version folders are processed; irrelevant sibling folders and stray root files are ignored.
  • Consequently, having both a complete root bundle and an irrelevant child folder present must produce the same flat bundle as the root files alone.
  • When irrelevant sibling folders or files are present, a nested source remains nested and valid.
Root-manifest rule for nested sources

After a source is classified as nested, the package manifest is the sole manifest kept from the source root. Root-level CSVs, CRDs, and all other non-package manifests must be ignored. Each valid version folder is processed with its own version-specific CSV and CRDs together with the single root package manifest.

As a result, a root CSV must not be added to any nested version bundle and must not appear in flattened output. This rule applies even when the root CSV is itself otherwise valid.

Package validation at the source-directory level

The source root must contain exactly one package manifest. Package manifests located in irrelevant child folders do not count toward this requirement.

These source-level checks take place during manifest parsing and use logger name operatorcourier.manifest_parser. The module operatorcourier.manifest_parser must be importable and must act as the logging source for these diagnostics.

Flattening contract

operatorcourier.flatten.get_flattened_files_info(source_dir) returns a collection of (source_path, flattened_name) pairs that describe the files selected for flattened output. The order of the pairs is not significant.

Flat input

For an already flat source, the recognized manifest files located directly in the root are returned. Each source path is paired with its base filename, which stays unchanged. All irrelevant subfolders and their contents are ignored, including package-only subfolders, as well as stray non-manifest files.

Nested input

For a nested source, the flattened output consists of:

  1. the single package manifest that comes from the source root;
  2. every CSV found in each valid version manifest folder; and
  3. the newest version of each distinct CRD represented across the valid version folders.

The newest CRD is picked based on Operator version, using the CSV's spec.version for its version folder and identifying a CRD by its manifest identity such as metadata.name. Otherwise, existing CSV and CRD selection behavior must remain unchanged.

Once nested mode is selected, no root-level CSV, CRD, or other non-package manifest may be included. Irrelevant sibling folders likewise contribute no output.

Flattened names are subject to these rules:

  • The root package keeps the base filename it originally had.
  • CRDs keep the base filenames they originally had.
  • For every nested CSV, -v<folder-name> is inserted immediately before its extension, where <folder-name> is the actual name of the version folder. For example, 0.9/etcdoperator.clusterserviceversion.yaml becomes etcdoperator.clusterserviceversion-v0.9.yaml.
  • Filenames from a flat source stay unchanged and receive no version suffix.

As a result, duplicate CSV basenames in different version folders remain distinguishable, while the basenames of the package and of the selected CRDs remain unchanged.

Consistency across the command line

For commands that build and verify a source—including the verify and push workflows—source-directory discovery and package parsing must be consistent.

  • Valid flat and nested sources, including sources with irrelevant content, successfully complete verification.
  • Invalid source parsing or bundle validation results in a nonzero command exit.
  • Missing and multiple root packages expose the exact operatorcourier.manifest_parser diagnostics given above.
  • Validator errors that already exist, including repository mismatches, continue to be emitted by operatorcourier.validate.
  • When verification runs with a validation-output destination, the JSON output is created for both valid and validation-invalid bundles; errors is empty only for valid output.

Scope of compatibility

This change is confined to manifest discovery, flat-versus-nested classification, nested root-file selection, and the timing of source-directory package checks. The existing behavior of CSV, CRD, package-field, repository, and optional OperatorHub UI validation stays in effect. Existing package exceptions—including the ValueError compatibility of OpCourierBadBundle—must remain compatible.
