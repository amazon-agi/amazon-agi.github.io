Task Specification: Fix the Ultrasonic Emitter's Duration Calculation

Background

Within the codebase there is a C++ code emitter that turns a higher-level program representation into Arduino-compatible C++ source. One portion of this emitter generates a helper function that takes ultrasonic distance measurements from a sensor.

Behavior That Is Required

When the ultrasonic measurement helper function is generated by the emitter, the resulting C++ code must compute the measured distance from a pulse duration value and return it. The computation of the distance must convert the raw duration into a distance by applying the following exact formula, which is emitted verbatim as a return statement within the generated C++ source:

return (static_cast<float>(__redu_duration_sensor) * 0.0343f) / 2.0f;

In particular:

  • The duration variable called __redu_duration_sensor must be cast to float by means of static_cast<float>(...).
  • The duration, once cast, is multiplied by the speed-of-sound factor 0.0343f.
  • This product is divided by 2.0f.
  • The result is returned by way of a return statement.

The emitted C++ source must contain the exact substring shown above, including its spacing, static_cast, the f float-literal suffixes, and its parenthesization.

Existing Behavior That Must Be Kept

Generation of the ultrasonic measurement helper must keep producing, within the emitted C++ source, all of the following:

  • A declaration/definition of the helper function having the form:
    float __redu_ultrasonic_measure_sensor()
  • A call site which assigns the result of the helper to a distance variable:
    distance = __redu_ultrasonic_measure_sensor();
  • A read of a pulse on pin 11:
    pulseIn(11, HIGH);
  • A delay in microseconds:
    delayMicroseconds(10);

Scope

The only functional change that is required is to ensure the returned distance is computed using the exact formula given above. Other emitter behavior should not change. The public API surface that is used to trigger emission and the program representation that the emitter consumes remain as they already exist within the codebase; do not rename them or alter their signatures.

Task Specification: Cache the HC-SR04 Distance When a Pulse Times Out

Overview

Change the C++ code generation for ultrasonic (HC-SR04) distance measurements such that the generated measurement function caches the last valid distance and reuses it when a pulse-timeout happens.

Context

The code emitter outputs a C++ helper function that measures distance with an HC-SR04 ultrasonic sensor. For a sensor named sensor, the emitter generates a function called __redu_ultrasonic_measure_sensor() that returns float. The function triggers a pulse and reads the echo duration through pulseIn(...) into a duration variable called __redu_duration_sensor.

Required Modification

In the emitted C++ source, the generated measurement function for a sensor (the name suffix being derived from the sensor, e.g. sensor) must include the following behavior:

  1. A static variable holding the cached distance, initialized to -1.0f:

    static float __redu_last_distance_sensor = -1.0f;

  2. A timeout check on the duration that was measured. When the duration is zero (the pulse timed out), the function must not update the cached distance from a fresh computation:

    if (__redu_duration_sensor == 0UL) {

  3. A cache-update assignment storing the freshly computed distance into the cached variable when a valid pulse is received:

    __redu_last_distance_sensor = __redu_distance_sensor;

    in which __redu_distance_sensor holds the computed distance value.

Naming Conventions

Every generated identifier takes the sensor name as its suffix:

  • Measurement function: __redu_ultrasonic_measure_<name>(), which returns float
  • Duration variable: __redu_duration_<name>
  • Computed distance variable: __redu_distance_<name>
  • Static cached distance variable: __redu_last_distance_<name>

Behavior to Preserve

The emission behavior that already exists must remain intact, including:

  • The declaration/definition of the function float __redu_ultrasonic_measure_<name>().
  • The measurement being assigned at the call site by means of distance = __redu_ultrasonic_measure_<name>();.
  • The trigger sequence, which includes delayMicroseconds(10); and the call to pulseIn(<pin>, HIGH); (with the pin number as configured, e.g. 11).

The single-line direct return expression emitted previously, which computed and returned the distance without caching (of the form return (static_cast<float>(...) * 0.0343f) / 2.0f;), is no longer produced; the distance computation has now been folded into the caching logic described above.

Every item listed above must continue to be emitted unchanged.

(Here the pin number 11 corresponds to the sensor's echo pin in the tested configuration.)

Recording a valid measurement

Once a valid measurement has been obtained, the helper must set the has-distance flag:

return 400.0f;

Summary

In Reduino.Utils, the SerialMonitor class offers a read method for serial input. This method is to be extended with an emit parameter that independently controls:

  1. Host-side runtime behavior: whether Python reads from the host serial connection that has been configured and echoes a value to standard output.
  2. Transpiled MCU behavior: which Arduino/C++ expression gets emitted when the result of read(...) is assigned to a variable.

There are three modes: "host", "mcu", and "both". The default must stay compatible with the existing behavior.

Public API

def read(self, emit: str = "both") -> str

  • emit is a positional-or-keyword argument. For example, read("host") and read(emit="host") are both supported.

  • Its default value is "both".

  • Exactly "host", "mcu", and "both" are the only valid values.

  • Any other value must raise ValueError. The exception message must contain:

    emit must be 'host', 'mcu', or 'both'

Validation Order and Connection Checks

The order in which validation happens is part of the contract:

  1. Validate emit.
  2. Check that a serial port has been configured.
  3. Carry out the mode-specific operation.

As a result, an invalid emit value must raise the specified ValueError even if no serial port is configured.

For every valid mode — including emit="mcu" — calling read when no serial port is configured must raise RuntimeError. The message must contain:

No serial port configured

Host-Side Runtime Behavior

After validation and the connection check have succeeded, the behavior depends on emit:

Value of emit Reads or consumes host serial data Writes to standard output Value returned
"host" Yes Echo a non-empty value followed by a newline The string that was read from the serial port
"mcu" No No ""
"both" Yes Echo a non-empty value followed by a newline The string that was read from the serial port

The following details are required:

  • "both" is the default and it preserves the host-side behavior read() has today.
  • The "host" and "both" modes preserve the existing line-reading and string-return behavior.
  • If a host-side read returns an empty value, read returns "" and writes nothing to standard output; on its own it must not emit a newline. This applies to the default "both" mode as well.
  • The emit="mcu" mode is MCU-only. At host runtime it must return "" without calling the serial connection's line-reading operation and without printing anything. Serial input that is still pending must remain unconsumed and stay available to a later "host" or "both" read.

payload = monitor.read(...)

Mode in the source Expression string emitted
"host" ""
"mcu" Serial.readStringUntil('\n')
"both" Serial.readStringUntil('\n')
Argument not provided Serial.readStringUntil('\n')

These mappings apply regardless of whether the mode is supplied positionally or by keyword. In particular:

  • Both monitor.read("host") and monitor.read(emit="host") emit the empty C++ string literal ""; as a result, no MCU serial read is generated for that value.
  • monitor.read("mcu") together with monitor.read(emit="mcu") emit Serial.readStringUntil('\n').
  • An explicit "both" and the default taken when no argument is passed emit Serial.readStringUntil('\n'), which preserves the existing generated behavior.

The parser's variable-assignment node must keep exposing:

  • name: the name of the assigned variable.
  • expr: the exact emitted expression string selected as described above.

For top-level source like the example above, the assignment remains in the parsed program's setup portion (prog.setup_body). The read expression continues to represent a string value.

  • For modes that perform a host read, the existing serial-port configuration errors and the host line-reading behavior remain unchanged.
  • For "mcu", the runtime and transpilation semantics are intentionally asymmetric: direct Python execution performs no host read and returns "", whereas transpilation generates the MCU serial-read expression.

Constructor

RGBLed(red_pin, green_pin, blue_pin)

    • Note: bool should not be handled as a valid pin type distinct from this rule; standard int-type checking is expected. (Only genuine ints are valid.)
  • Every pin must be a non-negative integer (>= 0). When any pin is negative, raise ValueError.
  • For the given inputs, pin type validation takes precedence appropriately (a non-int pin raises TypeError).

Initial state once construction has finished:

  • The pins attribute is equal to the tuple (red_pin, green_pin, blue_pin).
  • The color currently set is (0, 0, 0).
  • The on/off state is False.

set_color(r, g, b)

  • The current color is updated to (r, g, b).
  • The on/off state is not changed.
on(r, g, b)
  • Validates r, g, b against the color validation rules.
  • The current color is set to (r, g, b).
  • The on/off state is set to True.
off()
  • The current color is set to (0, 0, 0).
  • The on/off state is set to False.
fade(r, g, b, duration_ms=..., steps=...)

Transitions gradually to the target color (r, g, b) across a number of steps, sleeping between steps.

  • r, g, b are validated against the color validation rules.
  • duration_ms must be >= 0; when negative, raise ValueError.
  • steps must be >= 1; when the value is 0 (or less), raise ValueError.
  • Behavior when the inputs are valid:
    • The fade is performed using Sleep instances for the delays. For each delay, a Sleep object is constructed with the per-step delay duration and its wait() method is then called.

    • The count of sleep delays performed is steps - 1 (delays happen between steps, not after the final step). For example, duration_ms=40, steps=4 produces three delays of 10.0 each.

  • delay_ms must be >= 0; when negative, raise ValueError.
  • Behavior when the inputs are valid:
    • Before blinking, the current color is recorded.
    • In each blink cycle, the LED is turned to the target color and then off, with a delay after each. The total number of delays is times * 2, each one performed by constructing a Sleep with the delay_ms value (as passed, an int) and calling its wait(). For example, times=2, delay_ms=25 produces four delays of 25 each.
    • After the blinking finishes, the current color is restored to whatever it was immediately before blink was called.

Summary of Validation Ordering

  • Type errors (TypeError) apply to non-int pins/channels.
  • Value errors (ValueError) apply to out-of-range pins, out-of-range channels, negative durations/delays, and non-positive steps/times.

After the pattern has been applied, the LED's brightness equals the last entry's brightness (a final entry of 0 ⇒ brightness 0, state OFF; a final entry of 128 ⇒ brightness 128). An empty pattern leaves the LED OFF with brightness 0 and makes no Sleep calls.
    • Validation: if any pattern entry is outside 0–255, a ValueError must be raised with a message containing "pattern values must be".

Behavior examples:

  • brightness(value) — Assigns the backlight brightness (0–255). Error condition: a controllable backlight is required for brightness control. When the LCD has no backlight_pin (parallel without a backlight pin) or is an I2C device, a call to brightness raises RuntimeError.

  • glyph(index, rows) — A custom character is stored by this method. index must lie in the range 0–7; failing that, ValueError is raised. rows must be a list of exactly 8 values; failing that, ValueError is raised. Glyphs that have been stored can be reached through the glyphs attribute, a dict mapping index → the list of row values.

  • progress(row, value, max_value=100, width=..., label="") — Draws a progress bar on the given row. An optional label is placed before the bar (a space comes after it). The bar spans width cells; filled cells use the █ (U+2588) character in proportion to value/max_value, while unfilled cells are spaces. Example: label "Load", value 50, max 100, width 5, on a width-10 display → "Load ██ ".

  • animate(kind, row, text, speed_ms=..., loop=...) — Registers an animation on a row. Under the "scroll" kind, text is shown and then moved left by one character on each subsequent tick. The row shows the text left-aligned immediately after a scroll animation has been registered (e.g. "ABC" on width 5 → "ABC ").

  • tick(now_ms) — Moves registered animations forward. For a scroll animation, each effective tick shifts the displayed text one character to the left; spaces fill the positions vacated on the right. (E.g. once a scroll of "ABC" on width 5 has been started, ticking advances it to "BC ".)

2. AST Node Classes: Reduino.transpile.ast

The AST node classes below are to be added (importable from Reduino.transpile.ast):

  • LCDDecl — node for an LCD declaration. It has at least these fields: name, cols, rows, interface (string: "parallel" or "i2c"), plus the interface-specific fields rs, en, d4, d5, d6, d7 (parallel), i2c_addr (i2c), and backlight_pin.
  • LCDWrite, LCDLine, LCDMessage, LCDClear, LCDDisplay, LCDBacklight, LCDBrightness, LCDGlyph, LCDProgress, LCDAnimate — statement nodes that mirror the runtime methods listed above.
  • LCDTick — a node for an animation tick step (emitted into the loop body).

Construction with keyword arguments must be possible for these classes; LCDDecl specifically must accept the fields listed (name, cols, rows, interface, and the pin/address fields as applicable).

Python source written against the Reduino.Displays.LCD API is parsed by the transpiler; the outcome is a Program with setup_body and loop_body as lists of AST nodes.

  • contains an import of LCD from Reduino.Displays,
  • creates one or more LCD instances (both the parallel kind with pins/backlight and the I2C kind with address),
  • calls write, line, message, clear, display, backlight, brightness, glyph, progress, and animate on them,

  • One LCDDecl in setup_body for every LCD constructed, with interface set to "parallel" or "i2c" according to the constructor arguments.
  • The matching LCDWrite, LCDLine, LCDMessage, LCDClear, LCDDisplay, LCDBacklight, LCDBrightness, LCDGlyph, LCDProgress, and LCDAnimate nodes, also placed in setup_body.

The keyword arguments that the runtime API demonstrates (e.g. align, clear_row, clear_rows, bottom, max_value, width, label, speed_ms, loop) must be accepted by the parser.

4. Detecting Needed Libraries

Handed a Program, the function _collect_required_libraries(program) (importable as from Reduino import _collect_required_libraries) examines it and returns a list of the Arduino library names that are required:

  • A Program holding an LCDDecl with interface="parallel" → returns ["LiquidCrystal"].
  • A Program holding an LCDDecl with interface="i2c" → returns ["LiquidCrystal_I2C"].

(Behavior that already exists for other libraries — Servo, for example — must remain in place.)

5. Emitting the C++ Output

Arduino C++ is what the transpiler emits for the parsed Program. The sketch that results has a void setup() { ... } part and a void loop() { ... } part.

Include Lines

  • I2C LCD → emit #include <Wire.h> as well as #include <LiquidCrystal_I2C.h>.
Global Declarations

With a parallel LCD named lcd, declared with rs=12, en=11, d4=5, d5=4, d6=3, d7=2, emit this global object declaration:

LiquidCrystal __redu_lcd_lcd(12, 11, 5, 4, 3, 2);

With an I2C LCD named panel, the global declaration to emit is LiquidCrystal_I2C __redu_lcd_panel(...).

Object and constant names are built from the __redu_lcd_ prefix followed by the LCD's declared name (e.g. object __redu_lcd_lcd, and per-LCD constants such as __redu_lcd_cols_lcd, __redu_lcd_rows_lcd, __redu_lcd_brightness_lcd).

Parallel LCD, named lcd, with backlight pin 9:

__redu_lcd_panel.init();

Helper for Aligned Writes

Emission of aligned writes takes the form of calls to a helper named __redu_lcd_write_aligned. The desired alignment is communicated through the constants __redu_lcd_align_left, __redu_lcd_align_center, __redu_lcd_align_right. Signature and argument order:

__redu_lcd_write_aligned(<object>, <cols_const>, <col>, <row>, String("<text>"), <clear_row bool>, <align_const>)

  • Every column and row value is wrapped in static_cast<int>(...).

  • In a line-style call, the column argument is a literal 0 (still cast, i.e. static_cast<int>(0)), whereas the row is passed literally (e.g. 0 not cast) — as these concrete forms show:

    • lcd.line(0, "Hello", align="center") →
      __redu_lcd_write_aligned(__redu_lcd_lcd, __redu_lcd_cols_lcd, 0, static_cast<int>(0), String("Hello"), true, __redu_lcd_align_center);
    • lcd.write(0, 1, "World", align="right") →
      __redu_lcd_write_aligned(__redu_lcd_lcd, __redu_lcd_cols_lcd, static_cast<int>(0), static_cast<int>(1), String("World"), true, __redu_lcd_align_right);

    (Observe the difference: with line, the column position is emitted as a bare 0; with write, its col/row arguments are emitted as static_cast<int>(...).)

Progress-Bar Emission

A progress call comes out as a call that starts with __redu_lcd_progress(<object> (e.g. __redu_lcd_progress(__redu_lcd_lcd, ...)).

Message Emission

With a message call, the top line and — if present — the bottom line are written with their requested alignments, using the aligned-write mechanism above.

Animation Emission

When an animation is registered on an LCD named panel (the first animation takes the suffix _0), emit:

  • In the setup section, a start call that begins with __redu_lcd_start_scroll(__redu_lcd_anim_panel_0 (the animation state object is called __redu_lcd_anim_<name>_<index>).
  • In the loop section, a tick call that begins with __redu_lcd_tick_scroll(__redu_lcd_anim_panel_0.

Animations are non-blocking, so the generated loop() must not contain any delay(...) calls for animation timing.

  • The module Reduino.Displays, exporting class LCD with the methods line, write, message, clear, display, backlight, brightness, glyph, progress, animate, tick, dump, plus the attribute glyphs.

  • Integration of the parser and the emitter in the manner set out above.

Task: The LCD Display Toggle Should Manage the Backlight

Background

You are developing Reduino, a transpiler that converts Python to C++ (Arduino). An LCD display class already exists in the codebase: it can be configured either in parallel (4-bit) mode or over I2C, and it can already generate C++ setup/loop code. The goal of this task is to have the LCD's display(...) toggle also drive the backlight state.

Public API

The LCD class is imported like this:

from Reduino.Displays import LCD
The Constructor

The LCD constructor already exists and supports (at least) the keyword arguments below, which are the ones used here:

  • Parallel mode: LCD(rs=..., en=..., d4=..., d5=..., d6=..., d7=..., cols=..., rows=..., backlight_pin=...)
  • I2C mode: LCD(i2c_addr=..., cols=..., rows=...)

backlight_pin names a PWM-capable pin used to control the backlight in parallel mode. In I2C mode there is no backlight_pin.

Method Being Changed
def display(self, on: bool) -> None

Switches the LCD display on (True) or off (False).

Runtime State Attributes

The LCD instance must expose the following boolean attributes, which reflect the current state:

  • display_on — whether the display is currently switched on.
  • backlight_on — whether the backlight is currently switched on.

Behavior Requirements

Coupling of Runtime State

A call to display(...) must update both the display state and the backlight state at the same time:

  • After lcd.display(False), display_on is set to False and backlight_on to False.
  • After lcd.display(True), display_on is set to True and backlight_on to True.

This coupling is unaffected by any earlier, independent backlight(...) call. For instance, if the backlight was previously switched off via lcd.backlight(False), a later lcd.display(True) must still result in both display_on and backlight_on being True.

This holds in the same way for both parallel-mode and I2C-mode instances.

C++ Code That Gets Generated

When a call to display(...) is transpiled, the emitted C++ (placed in the setup() / loop() region matching where the call appears) must include both the display toggle and the matching backlight operation.

Assume the LCD object has been assigned to a Python variable called <name> (e.g. lcd, panel). The generated C++ follows an object/state naming scheme keyed on that variable name.

Parallel mode (with backlight_pin=<pin>):

For <name>.display(False), emit statements that include:

  • __redu_lcd_<name>.noDisplay();
  • __redu_lcd_backlight_state_<name> = false;
  • analogWrite(<pin>, 0);

For <name>.display(True), emit statements that include:

  • __redu_lcd_<name>.display();
  • __redu_lcd_backlight_state_<name> = true;
  • analogWrite(<pin>, __redu_lcd_brightness_<name>);

Here __redu_lcd_brightness_<name> is the brightness variable that already exists for that LCD, and <pin> is the numeric value passed as backlight_pin.

I2C mode:

For <name>.display(False), emit statements that include:

  • __redu_lcd_<name>.noDisplay();
  • __redu_lcd_<name>.noBacklight();

For <name>.display(True), emit statements that include:

  • __redu_lcd_<name>.display();
  • __redu_lcd_<name>.backlight();

Notes

  • Multiple LCD objects may exist within a single program; each of them uses its own variable name in the generated identifiers.
  • Only the display(...) behavior (runtime state and code generation) falls within scope. Do not change other LCD behaviors.

Task: Support Progress Bar Styles in the LCD Component

Background

The codebase contains Reduino, a Python-based framework that models Arduino LCD displays and compiles Python source into C++ code. An LCD progress-bar feature already exists; it renders a horizontal progress indicator. Your task is to extend it so that the fill glyph can be chosen via a new style argument, and to fix the default fill glyph emitted in the generated C++.

Three layers are involved in this feature: the parser (which produces an AST node), the emitter (which produces C++ code), and the runtime simulation (which renders text into a virtual display buffer).

1. The progress API

Source programs use the progress method of the LCD class (importable as from Reduino.Displays import LCD). As exercised, its call signature is:

panel.progress(row, value, max_value=<int>, width=<int>, style=<str>, label=<str>)
  • row — positional; the index of the display row.
  • value — positional; the value of the current progress.
  • max_value — keyword; the value that corresponds to a full bar.
  • width — keyword; the number of character cells the bar takes up.
  • style — keyword, optional; picks the glyph used to draw filled cells.
  • label — keyword, optional; a text label that is rendered before the bar.
Styles that are supported

The style argument accepts exactly the string values below, and each of them maps to a specific fill character:

style value Fill character
"hash" #
"pipe" `
"dot" .

Any style value other than these is invalid and must cause a ValueError to be raised when progress is invoked at runtime (e.g. style="zigzag" must raise ValueError).

Whenever no fill glyph is otherwise determined by a recognized text style, the default fill uses the full-block LCD glyph whose byte value is 0xff (see §3 for how this appears in the emitted C++).

2. Parser: the LCDProgress AST node

Parsing an LCD progress(...) call must produce an LCDProgress AST node (this is the same node type already used for this call). The node must now expose a style attribute, holding the string that was passed as the style keyword argument. For a call written as style="hash", the resulting node's .style attribute equals the string "hash".

The LCDProgress node keeps appearing in the collection of LCD-related AST nodes obtained by parsing a program, alongside the other existing LCD node types (backlight, brightness, glyph, animate, etc.).

3. Emitter: the generated C++

When a source program that calls progress(...) is compiled, the generated C++ must invoke the progress runtime helper, referencing the target LCD object. The emitted call has the form:

__redu_lcd_progress(__redu_lcd_<name>...

where <name> stands for the LCD variable's identifier (e.g. __redu_lcd_panel, __redu_lcd_lcd).

The emitted C++ must reflect the fill glyph:

  • Default (no recognized text style / full-block default): the generated code must contain the full-block glyph written as static_cast<char>(0xff).
  • style="hash": the character literal '#' must appear in the generated code.

4. Rendering in the runtime

For simulation, the LCD class must be constructable directly in Python:

LCD(rs=12, en=11, d4=5, d5=4, d6=3, d7=2, cols=8, rows=1)

(Parallel-mode construction using rs/en/d4..d7 plus cols/rows; an I²C mode via i2c_addr also exists and is unchanged.)

Once progress(...) has been called, the current display buffer can be retrieved via lcd.dump(), which returns a multi-line string with one line per row (the lines are separated by newlines).

Rules exercised during rendering

With a display of cols=8, rows=1:

  • progress(0, 25, max_value=100, width=4, style="hash") → row 0 starts with # (1 of the 4 cells filled, filled with #, remaining cells blank).
  • progress(0, 50, max_value=100, width=4, style="pipe", label="P") → row 0 begins with the label P followed by a space and then the bar; the two bar cells at positions 2 and 3 are || (2 of the 4 cells filled, filled with |).
  • progress(0, 75, max_value=100, width=4, style="dot") → row 0 starts with ... (3 of the 4 cells filled, filled with .).
  • progress(0, 10, style="zigzag") → this raises ValueError.

The number of filled cells is round(value / max_value * width) (i.e. 25/100 * 4 = 1, 50/100 * 4 = 2, 75/100 * 4 = 3); these cells are filled with the style's glyph, and the cells within width that remain are blank spaces. When a label is provided, it is rendered before the bar followed by a single space separator, after which the bar begins.

Summary of the deliverables

  1. LCD.progress accepts a style keyword whose values are "hash", "pipe", "dot"; any other value raises ValueError.
  2. The parser's LCDProgress node carries a .style attribute that is equal to the style string passed to it.
  3. For style="hash", the emitter produces # character literals; for the default full-block glyph, it uses static_cast<char>(0xff).
  4. In the runtime, the dump() output renders the filled cells with the character appropriate to the style, as described above.
