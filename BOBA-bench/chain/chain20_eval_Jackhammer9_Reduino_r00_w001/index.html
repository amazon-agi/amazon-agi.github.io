Task: Add Progress Bar Style Support to LCD Component

Context

This codebase provides a Python-based framework (Reduino) that models Arduino LCD displays and compiles Python source into C++ code. There is an existing LCD progress-bar feature that renders a horizontal progress indicator. Your task is to extend it so the fill glyph can be chosen via a new style argument, and to fix the default fill glyph emitted in the generated C++.

The feature spans three layers: the parser (which produces an AST node), the emitter (which produces C++ code), and the runtime simulation (which renders text into a virtual display buffer).

1. The progress API

The LCD class (importable as from Reduino.Displays import LCD) has a progress method used in source programs. Its call signature, as exercised, is:

panel.progress(row, value, max_value=<int>, width=<int>, style=<str>, label=<str>)
  • row — positional, the display row index.
  • value — positional, the current progress value.
  • max_value — keyword, the value corresponding to a full bar.
  • width — keyword, the number of character cells the bar occupies.
  • style — keyword, optional, selects the glyph used to draw filled cells.
  • label — keyword, optional, a text label rendered before the bar.
Supported styles

The style argument accepts exactly these string values, each mapping to a specific fill character:

style value Fill character
"hash" #
"pipe" `
"dot" .

Any other style value is invalid and must cause a ValueError to be raised when progress is invoked at runtime (e.g. style="zigzag" must raise ValueError).

When no fill glyph is otherwise determined by a recognized text style, the default fill uses the full-block LCD glyph whose byte value is 0xff (see §3 for how this appears in emitted C++).

2. Parser: LCDProgress AST node

Parsing an LCD progress(...) call must produce an LCDProgress AST node (the same node type already used for this call). The node must now expose a style attribute holding the string passed as the style keyword argument. For a call written with style="hash", the resulting node's .style attribute equals the string "hash".

The LCDProgress node continues to appear in the collection of LCD-related AST nodes produced from parsing a program, alongside the other existing LCD node types (backlight, brightness, glyph, animate, etc.).

3. Emitter: generated C++

Compiling a source program that calls progress(...) must generate C++ that invokes the progress runtime helper, referencing the target LCD object. The emitted call takes the form:

__redu_lcd_progress(__redu_lcd_<name>...

where <name> is the LCD variable's identifier (e.g. __redu_lcd_panel, __redu_lcd_lcd).

The emitted C++ must reflect the fill glyph:

  • Default (no recognized text style / full-block default): the generated code must contain the full-block glyph expressed as static_cast<char>(0xff).
  • style="hash": the generated code must contain the character literal '#'.

4. Runtime rendering

The LCD class must be constructable directly in Python for simulation:

LCD(rs=12, en=11, d4=5, d5=4, d6=3, d7=2, cols=8, rows=1)

(Parallel-mode construction with rs/en/d4..d7 plus cols/rows; an I²C mode via i2c_addr also exists and is unchanged.)

After calling progress(...), the current display buffer can be retrieved via lcd.dump(), which returns a multi-line string with one line per row (lines separated by newlines).

Rendering rules exercised

Given a display with cols=8, rows=1:

  • progress(0, 25, max_value=100, width=4, style="hash") → row 0 begins with # (1 filled cell of 4, filled with #, remaining cells blank).
  • progress(0, 50, max_value=100, width=4, style="pipe", label="P") → row 0 starts with the label P followed by a space, then the bar; the two bar cells at positions 2 and 3 are || (2 filled cells of 4 filled with |).
  • progress(0, 75, max_value=100, width=4, style="dot") → row 0 begins with ... (3 filled cells of 4, filled with .).
  • progress(0, 10, style="zigzag") → raises ValueError.

The number of filled cells is round(value / max_value * width) (i.e. 25/100 * 4 = 1, 50/100 * 4 = 2, 75/100 * 4 = 3), filled with the style's glyph; the remaining cells within width are blank spaces. When a label is provided, it is rendered before the bar followed by a single space separator, then the bar begins.

Summary of deliverables

  1. LCD.progress accepts a style keyword with values "hash", "pipe", "dot"; any other value raises ValueError.
  2. The parser's LCDProgress node carries a .style attribute equal to the passed style string.
  3. The emitter produces # character literals for style="hash" and uses static_cast<char>(0xff) for the default full-block glyph.
  4. The runtime dump() output renders filled cells using the style-appropriate character as described above.
