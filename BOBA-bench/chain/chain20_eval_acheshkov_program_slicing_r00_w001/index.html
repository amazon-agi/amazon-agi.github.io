Task Specification: Java Code Block Slicing

Overview

Implement functionality to analyze Java source code (provided as a string) and identify code "blocks" and contiguous statement slicing "opportunities" within it.

Public API

Create a module at program_slicing/decomposition/block_slicing.py exposing two functions:

def determine_unique_blocks(source_code: str) -> <collection>
def get_opportunities_list(source_code: str) -> list

Both accept a single string argument containing a fragment of Java source code.

determine_unique_blocks(source_code)

Given a Java code fragment, identify the distinct code blocks it contains and return a collection whose length equals the number of unique blocks. Only the number of blocks (len(...) of the return value) is observed.

Block counting rules (derived from required behavior)

Treat the entire fragment as one enclosing (outer) block. Additionally, each of the following language constructs introduces exactly one further nested block, regardless of whether the construct's body uses braces:

  • An if statement.
  • A for loop (both classic for (init; cond; update) and enhanced for (T x : collection) forms).
  • A while loop.
  • A synchronized block.
  • A construct body without surrounding braces (e.g., a single-statement for body) still counts as one nested block.

For each of the following single constructs, the returned collection length is 2 (one outer + one nested):

  • a lone if statement,
  • an enhanced for-each loop,
  • a while loop,
  • a synchronized block,
  • a classic for loop,
  • a loop whose body has no braces.
Compound / multi-part constructs

  • A try / catch / finally statement yields 4 blocks total: the outer enclosing block plus the try body, the catch body, and the finally body (one nested block per clause body).

  • Code containing an anonymous class instantiation yields 4 blocks total. When an object is created with an anonymous class body (new Type() { ... }) containing method definitions, the outer enclosing block is counted, plus one block for each method body defined inside the anonymous class body. (For a fragment with a plain object creation followed by an anonymous class with two method bodies, the total is 4.)

  • A lambda expression with a braced body ((s) -> { ... }) yields 2 blocks total: the outer enclosing block plus the lambda body block.

get_opportunities_list(source_code)

Given a Java code fragment, compute the set of statement-range "slicing opportunities" and return them.

Return structure

Return a list containing exactly one element. That single element is a list of 2-tuples (start_line, end_line), where start_line and end_line are 1-based line numbers relative to the input string.

Line numbering: line 1 is the first physical line of the string. Note the input strings begin with a newline immediately after the opening triple-quote, so the first line of actual code is line 2.

Meaning of an opportunity

Each (start_line, end_line) tuple represents a contiguous, extractable range of statements — a candidate slice — where start_line is the first source line of the range and end_line is the last source line of the range. The complete result enumerates every valid such contiguous statement range found in the code.

Ordering

Within the inner list, opportunities are ordered primarily by ascending start_line, and for a given start_line by ascending end_line.

Because a plain else body is not a block, the statements directly inside it generate no opportunities of their own. The only opportunities that cover them are the ranges — from the enclosing block or its ancestors — that include the whole if/else statement.

No synthesized terminal node for any function

  • methods declared inside classes;
  • standalone method declarations;

  • the CDG contains exactly one fewer node;
  • the function entry has exactly one fewer direct successor;
  • no final artificial EXIT child is appended;
  • no control-flow route targets that removed terminal; and
  • all remaining source-derived nodes retain their relative order and structure.

A function with no explicit return therefore has no EXIT merely to mark the end of the function. A function with an explicit return may still end with an EXIT child, but that child is the actual source return, not a synthesized function terminal.

Required Behavior

1. Explicit returns and the shared function EXIT

Each parsed function must have exactly one dedicated EXIT node:

  • The EXIT is a direct control-dependence child of that function's FUNCTION entry.
  • It is the last direct child of the FUNCTION entry.
  • It is distinct for each outer, inner, or synthetic function.

Each explicit Java return must be represented separately as a GOTO node at the position occupied by the return in the source. A return expression must retain its normal parsed subexpressions and variable-read information.

Consequently:

  • A function with no explicit return still receives one EXIT child and no return-related GOTO.
  • A function with one return has one return GOTO and one function EXIT.
  • Multiple returns produce multiple GOTO nodes but still only one shared EXIT for the enclosing function.
  • A return nested in a branch or loop remains at that lexical control-dependence location; a return directly in the function body is a direct child of the function entry.
  • Relative to the previous return-only representation, the CDG gains one node per parsed function: each old return node is represented as a GOTO, and one additional shared EXIT is present for the function.
2. EXIT represents normal fall-through only

The shared EXIT is the function body's normal-completion target. Its control-flow reachability is separate from its required control-dependence edge from the function entry.

  • Wire the EXIT into control flow only from normal-completion, or fall-through, exit points of the function body.
  • An explicit return's GOTO is control-flow terminal. It must not have a control-flow edge to the shared EXIT, and later statements must not be sequenced after it on that path.
  • If one path returns and another falls through, only the fall-through path reaches EXIT.
  • If every execution path ends in a return, the EXIT remains present in the CDG and PDG but is absent from the derived CFG and DDG.
  • Thus, for an all-return function, the CFG and DDG retain the same node coverage as under the former single-node return representation, with the return now typed as GOTO. Only a function body that can complete normally gains its shared EXIT in the derived CFG and DDG.

  • Each has its own body structure and its own final EXIT child.
  • All nodes for all such functions belong to the single returned CDG.
