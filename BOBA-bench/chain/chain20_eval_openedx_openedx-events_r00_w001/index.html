Task: Update AvroAttrsBridge so that it bridges complete signal event data

Implement support for constructing Avro schemas and converting event data on the basis of an OpenEdxPublicSignal and its declared data fields.

Public API

openedx_events.bridge.avro_attrs_bridge.AvroAttrsBridge

The class must support the following:

AvroAttrsBridge(signal, extensions=None)
  • signal is an instance of openedx_events.tooling.OpenEdxPublicSignal.
  • extensions is an optional mapping whose keys are Python classes and whose values are AvroAttrsBridgeExtention instances.

The class must expose:

bridge.schema_dict
bridge.to_dict(event_data)
bridge.from_dict(data)
  • schema_dict is the Avro schema dictionary that gets generated.
  • to_dict(event_data: dict) -> dict converts the values of a signal event into values that are Avro-compatible.
  • from_dict(data: dict) -> dict reconstructs the signal event values together with their declared Python types.

The signal may be created in this way:

OpenEdxPublicSignal(
    event_type="simple.signal",
    data={"field_name": FieldType},
)

When data contains multiple entries, they represent multiple top-level event fields.

openedx_events.bridge.avro_attrs_bridge_extensions.AvroAttrsBridgeExtention

This exact class name and spelling must remain available for subclassing. An extension that the bridge uses conforms to the following contract:

class SomeExtension(AvroAttrsBridgeExtention):
    cls = SomePythonClass

    def serialize(self, obj):
        ...

    def deserialize(self, data):
        ...

    def record_fields(self):
        ...

What record_fields() returns is used as the Avro field type for that class.

Schema generation

A bridge must generate schema_dict immediately when it is constructed.

Every schema has exactly this top-level structure:

{
    "type": "record",
    "name": "CloudEvent",
    "doc": "Avro Event Format for CloudEvents created with openedx_events/avro_attrs_bridge",
    "fields": [...],
}

Each item declared in the signal data becomes one top-level field, with declaration order preserved:

{
    "name": "<signal data key>",
    "type": <schema for its declared type>,
}
Attrs classes

Classes defined using attr.s, auto_attribs=True included, become Avro records:

{
    "name": "<Python class name>",
    "type": "record",
    "fields": [...],
}

The declaration order of attrs fields must be retained. Attrs classes that are nested must recursively become nested records.

These annotated primitive attrs field types must be supported:

Python type Avro type
bool "boolean"
int "long"
float "double"
bytes "bytes"
str "string"

For example, when an attrs class named SimpleAttrs has fields declared as bool, int, float, bytes, and str, it must produce:

{
    "name": "SimpleAttrs",
    "type": "record",
    "fields": [
        {"name": "boolean_field", "type": "boolean"},
        {"name": "int_field", "type": "long"},
        {"name": "float_field", "type": "double"},
        {"name": "bytes_field", "type": "bytes"},
        {"name": "string_field", "type": "string"},
    ],
}

When nested attrs classes are distinct, their record schemas must retain their own class names, even when the classes have identical fields.

Event-data conversion

to_dict

The complete event keyword-data dictionary for the signal is what to_dict accepts.

Conversion of attrs instances to dictionaries must happen recursively. For example, the nested dictionaries produced from nested attrs values must contain their declared field names and values.

Primitive values stay in their Avro-compatible form.

from_dict

A dictionary shaped according to schema_dict is accepted by from_dict, which returns a top-level event-data dictionary.

Attrs fields must be reconstructed recursively as instances of the attrs classes declared for them. When the nested declared classes are distinct, they must be reconstructed as the correct respective types.

When a dictionary is missing a required attrs constructor field, from_dict must raise TypeError.

The dictionary that results must be suitable for use as:

signal.send_event(**bridge.from_dict(data))

Support for built-in custom types

These types must be supported by the bridge, without requiring callers to provide extensions.

datetime.datetime

When a signal field is declared as datetime:

  • to_dict uses datetime.isoformat() to convert the value.
  • That ISO-formatted string is converted back into a datetime instance by from_dict.

As an example, datetime(year=1989, month=9, day=6) serializes as:

"1989-09-06T00:00:00"
opaque_keys.edx.keys.CourseKey

When a signal field is declared as CourseKey:

  • to_dict uses str(course_key) to convert the key.
  • From that string, from_dict reconstructs an equal CourseKey instance.

Extensions provided by the caller

Support for a non-attrs class can be provided by passing an extension:

bridge = AvroAttrsBridge(
    signal,
    extensions={SomeExtension.cls: SomeExtension()},
)

In the case of such a field:

  • extension.record_fields() is used for schema generation.
  • extension.serialize(value) is used by to_dict.
  • extension.deserialize(value) is used by from_dict.

It must be possible to use the generated schema and the converted dictionaries with fastavro.schemaless_writer and fastavro.schemaless_reader. A nested attrs event must survive a write/read plus to_dict/from_dict round trip with equivalent values, and so must a custom extension whose record_fields() returns "string".

Errors

  • If a bridge is constructed for an arbitrary non-attrs class and there is no matching built-in or caller-provided extension, TypeError must be raised.
  • When a top-level signal data type is list or dict, constructing a bridge must raise an exception during construction.

Task Specification: Handling Optional/Nullable Fields in AvroAttrsBridge

Summary

The existing AvroAttrsBridge must be extended so that it correctly handles attrs class fields that have a default value of None. Throughout Avro schema generation, serialization, and deserialization, such fields must be treated as optional/nullable.

Public API

Existing Functionality (must continue to work)
  • Module: openedx_events.bridge.avro_attrs_bridge
    • Class: AvroAttrsBridge
      • The constructor accepts a signal object (of the kind produced by the project's signal-creation utility) whose event-data configuration maps top-level key names to attrs-decorated classes.
      • It must provide the serialization/deserialization behavior on which existing bridge functionality already relies (roundtrip of event data dictionaries to/from Avro-encoded bytes).
Test Support Classes (must be created)

Create the following attrs-decorated classes in the module openedx_events.bridge.tests.test_utilities:

  • SimpleAttrsWithDefaults — a frozen attrs class having the following fields, each of which is declared with a default value of None:

    • boolean_field (type bool)
    • int_field (type int)
    • float_field (type float)
    • bytes_field (type bytes)
    • string_field (type str)

  • NestedAttrsWithDefaults — a frozen attrs class that has a single field:

    • field_0 (type SimpleAttrsWithDefaults, default value None)

It must be possible to construct both classes with no arguments; when they are constructed that way, every field takes the value None.

Behavior Requirements

A field of an attrs class that is declared with a default value of None must be treated as an optional/nullable field.

  1. Schema generation. While the Avro schema for an attrs class is being built, any field whose default is None must be represented as a nullable Avro type (i.e., the field may hold either its declared type or null).

  2. Serialization. Constructing an AvroAttrsBridge from a signal whose event data contains such classes must succeed, and serializing an event-data dictionary in which those fields are None must succeed and produce Avro-encoded bytes.

  3. Deserialization. The deserialization of those bytes back into event data must reproduce an instance of the original attrs class whose optional fields are None.

  4. Nested classes. Fields whose type is itself an attrs class fall under this rule. A field typed as a nested attrs class with a default of None must be serializable and deserializable, and when its value is None it must roundtrip back to None.

Concrete Roundtrip Requirements

  • Take a signal configured with a single top-level key mapping to SimpleAttrsWithDefaults, and event data {"<key>": SimpleAttrsWithDefaults()}:

    • Serializing to bytes and then deserializing must yield, under the same top-level key, an object in which boolean_field, int_field, float_field, bytes_field, and string_field are all None.

  • Take a signal configured with a single top-level key mapping to NestedAttrsWithDefaults, and event data {"<key>": NestedAttrsWithDefaults()}:

    • Serializing to bytes and then deserializing must yield, under the same top-level key, an object in which field_0 is None.

Constraints

  • All bridge behavior that was previously supported (schema generation, serialization, and deserialization for non-defaulted fields, nested attrs data, bridge extensions for non-attrs types, and rejection of unsupported signal configurations) must remain intact.
  • A change in behavior is not required for fields that do not have a None default.

Task: Build the Avro schema/serialization module for OpenEdx signals

Overview

Within the Python package path openedx_events/event_bus/avro/, several modules are to be created by you; they convert OpenEdxPublicSignal instances — event data included — to and from Avro-compatible schemas and dictionaries. Four separately importable parts make up the functionality: schema generation, serialization (Python objects → dict), deserialization (dict → Python objects), and a base class for custom-type serializers.

Already available is the signal class openedx_events.tooling.OpenEdxPublicSignal, which at construction takes an event type string plus an init_data mapping of field-name → Python type. Throughout the tests, a helper creates signals in this way:

OpenEdxPublicSignal(event_type="simple.signal", data=data_dict)

Here data_dict assigns Python types to top-level field names; those types may be attrs-decorated classes, plain classes, datetime, opaque_keys.edx.keys.CourseKey, or primitives.

Public API to be provided

Module openedx_events/event_bus/avro/types.py

A dict going by the name PYTHON_TYPE_TO_AVRO_MAPPING has to be exposed here, assigning Avro type-name strings to Python primitive types. The entries listed next (Python type → Avro string) are required at minimum:

  • bool → "boolean"
  • int → "long"
  • float → "double"
  • bytes → "bytes"
  • str → "string"

As a field type value, custom serializers take PYTHON_TYPE_TO_AVRO_MAPPING[str], and it must equal "string".

Module openedx_events/event_bus/avro/custom_serializers.py

There must be a base class here, BaseCustomTypeAvroSerializer; the intent is that it gets subclassed, teaching the system how to handle a Python type that is neither attrs nor primitive. Subclasses declare:

  • cls: the Python class this serializer is written for.
  • field_type: the Avro field type standing in for instances of cls within a schema (e.g. "string").
  • serialize(obj) -> str (a static method): produces the Avro-representable value of an instance of cls.
  • deserialize(data) -> object (a static method): from the Avro-representable value, restores an instance of cls.
Module openedx_events/event_bus/avro/schema.py

The function below must be exposed:

def schema_from_signal(signal, custom_type_to_avro_type=None):
  • signal: an OpenEdxPublicSignal.
  • custom_type_to_avro_type: an optional mapping of Python type → Avro type string, for representing types that are otherwise unsupported.

What it returns is a dict that stands for the Avro schema (see "Schema format" below).

Module openedx_events/event_bus/avro/serializer.py

A class must be exposed here:

class AvroSignalSerializer:
    def __init__(self, signal): ...
    @property
    def schema(self): ...        # the Avro schema dict for the signal
    def to_dict(self, event_data): ...
    def custom_type_serializers(self): ...   # returns a list; default empty
  • Construction takes an OpenEdxPublicSignal.
  • What .schema yields is the Avro schema dict, consistent with schema_from_signal applied to the same signal (any custom type serializers this instance provides being taken into account).
  • Given a dict of {field_name: python_value}, .to_dict(event_data) produces a dict of values Avro can represent.
  • A list of BaseCustomTypeAvroSerializer subclasses is what custom_type_serializers() returns. By default this list is empty; to register custom serializers, subclasses override it.
Module openedx_events/event_bus/avro/deserializer.py

A class must be exposed here as well:

class AvroSignalDeserializer:
    def __init__(self, signal): ...
    @property
    def schema(self): ...        # the Avro schema dict for the signal
    def from_dict(self, data): ...
    def custom_type_serializers(self): ...   # returns a list; default empty
  • Construction takes an OpenEdxPublicSignal.
  • What .schema yields is the Avro schema dict, consistent with the signal (and with any custom serializers).
  • .from_dict(data) goes the other way: from a dict of Avro-representable values it builds a dict of {field_name: python_value}, reconstructing attrs objects and custom types.
  • On the deserializer, custom_type_serializers() works just as it does on the serializer.

Between the serializer's schema and the deserializer's schema there must be mutual compatibility: after a value produced by AvroSignalSerializer.to_dict has been written with the serializer's schema via fastavro.schemaless_writer and read back with the deserializer's schema via fastavro.schemaless_reader, the original event data must be reconstructed via AvroSignalDeserializer.from_dict.

Layout of the schema

The output of schema_from_signal — and likewise of the .schema properties — is a top-level dict laid out like this:

{
    "type": "record",
    "name": "CloudEvent",
    "doc": "Avro Event Format for CloudEvents created with openedx_events/schema",
    "fields": [ <one entry per top-level signal field> ],
}

Exactly "Avro Event Format for CloudEvents created with openedx_events/schema" must be the string supplied as doc.

For every top-level field, fields gets an entry {"name": <field_name>, "type": <avro_type>}, keeping the order in which the fields were declared in the signal's data mapping.

Primitive-typed fields

If the Python type of a field is a primitive, its "type" is set directly to the mapped Avro string. As an example, a signal field with Python type str gives {"name": <field_name>, "type": "string"}.

Fields backed by attrs records

Should the Python type of a field be an attrs-decorated class, that field turns into a nested Avro record:

{
    "name": <ClassName>,
    "type": "record",
    "fields": [ <one entry per attrs attribute, in declaration order> ],
}

As its "name", the record carries the class's name. The same rules render every attribute, applied recursively (a primitive attribute takes its mapped string, a nested attrs attribute becomes a nested record, and so on). Wherever a nested record definition is first needed, it is emitted there with its full definition (see examples below).

Custom and extension types

When a field's Python type is neither a primitive nor an attrs class, it must be representable one of two ways: via custom_type_to_avro_type (for schema_from_signal) or via a registered BaseCustomTypeAvroSerializer subclass (for the serializer/deserializer classes). Its declared Avro field type (e.g. "string") is how the schema depicts such a type. Both at the top level and in the situation where the custom type shows up as an attribute nested inside an attrs record, this applies.

Out of the box (no registration needed), the serializer and deserializer classes handle two custom types:

  • datetime.datetime: serialization turns it into its ISO-8601 string via .isoformat(), and deserialization gives back an equal datetime.
  • opaque_keys.edx.keys.CourseKey: serialization turns it into str(course_key), and deserialization gives back an equal CourseKey.

The schema shows both of them as "string"-typed fields.

Default-valued (optional) fields

Whenever an attrs attribute comes with a default value, it must be rendered as a nullable Avro union whose default is null:

{"name": <attr_name>, "type": ["null", <avro_type>], "default": "null"}

Here <avro_type> denotes the representation the attribute's type would otherwise get (a mapped primitive string, or a nested record dict). The string "null" is what the "default" value must be, and the union list must be exactly ["null", <avro_type>], "null" coming first.

Recursion applies to this rule too: when the type of an attrs attribute is itself an attrs class with defaults, the nested record that gets produced has fields obeying these same nullable-union rules.

Behavior of to_dict (serialization)

  • The top-level result is a dict whose keys are the signal's field names.
  • An attrs instance becomes a plain dict of its attributes (converted recursively), with the attribute names serving as keys.
  • When an attrs instance leaves its default/optional fields unset (i.e. None), the output dict contains each of those fields with the value None. To illustrate, if a class has the fields boolean_field, int_field, float_field, bytes_field, string_field, attrs_field and an instance leaves all of them unset, that instance serializes to {'boolean_field': None, 'int_field': None, 'float_field': None, 'bytes_field': None, 'string_field': None, 'attrs_field': None}.
  • Values of nested attrs become nested dicts through recursive conversion.
  • A datetime value is turned into the string that .isoformat() gives.
  • A CourseKey value ends up as its str(...) representation.
  • If a registered custom serializer handles a value's type, the value gets replaced with that serializer's serialize(obj) output. Top-level fields fall under this, and so do custom-typed attributes nested inside attrs records.

How from_dict behaves (deserialization)

  • What comes out at the top level is a dict with the signal's field names as keys.
  • Where a dict corresponds to an attrs record type, it is turned back into an instance of the appropriate attrs class (nested records handled recursively). These instances must be of the correct class and compare equal to the original objects.
  • Optional/default attrs fields: feeding an empty dict {} for such a record must lead to reconstruction as an instance equal to what you get by constructing the class with all defaults. When a nested optional field is given as {"field_0": {}}, the nested record is reconstructed with defaults.
  • For datetime-typed fields, ISO-8601 strings get reconstructed into equal datetime objects.
  • For CourseKey-typed fields, their string representations get reconstructed into equal CourseKey objects.
  • Values belonging to custom-typed fields (registered via a custom serializer) go through that serializer's deserialize(data) for reconstruction. Top-level fields are covered by this, and so are custom-typed attributes nested inside attrs records.
  • Should the dict lack a required (non-default) field belonging to the attrs class into which it is being converted, a TypeError must be raised.

Conditions under which errors occur

  • TypeError must be raised by schema_from_signal (and by construction of the serializer/deserializer in cases where a schema gets built) when the Python type of a signal field is a plain class that is neither a primitive, an attrs class, a default-supported custom type (datetime, CourseKey), nor covered by a provided custom_type_to_avro_type mapping / registered custom serializer.
  • When a signal field has Python type list or dict, an exception must be raised in the course of schema generation.

2. Signal to be added for content authoring

The signal is required to be an OpenEdxPublicSignal instance whose event type is org.openedx.content_authoring.course.catalog_info.changed.v1.

Data class carried by the signal

The attrs-based data class carried by this signal is to be defined. One or more keys within the signal's init_data mapping are associated with attrs data classes. For every attribute of every data class reachable from this signal, the type must be one of the following (directly, or via nested attrs classes composed only of these types):

  • int
  • bool
  • str
  • CourseKey (from opaque_keys.edx.keys)

  • another attrs data class composed recursively of the above

Note: the command receives topic and group_id as single-element lists (e.g. topic=['test']); forwarding the matching scalar string value (e.g. 'test') on to make_single_consumer is what must happen.

Running the Command With Extra Arguments

If the command runs with topic, group_id, and an extra argument that holds a JSON object string (e.g. '{"check_backlog":true}'):

  • The parsing of the extra JSON string must happen, with the key/value pairs inside it then expanded into additional keyword arguments that get passed to make_single_consumer.
  • The command must make exactly one call to make_single_consumer, with:
    • topic — the topic value as a scalar string.
    • group_id — the group id value as a scalar string.
    • Each key/value pair contained in the parsed extra JSON (e.g. check_backlog=True).
  • A signal keyword argument must not be part of the call.
Error Handling When Extra Arguments Are Invalid

If the command is executed with topic, group_id, plus an extra argument that is not valid JSON (e.g. a JSON-like string written with single quotes, such as "{'check_backlog':true}"):

  • A crash of the command must not occur.
  • Logging of the error must go through the exception method of its module logger, and that method must be called exactly once, receiving the message string "Error consuming events".

Constraints

  • All other existing behavior around argument parsing and consumer invocation (the forwarding of topic, group_id, and the expanded extra arguments) must be preserved.
