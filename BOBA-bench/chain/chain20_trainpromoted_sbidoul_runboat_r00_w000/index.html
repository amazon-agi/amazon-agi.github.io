Task Description

Summary

Build a module that works out whether a supplied repository branch is supported and, for supported branches, determines the appropriate build container image.

Module and Public API

runboat/exceptions.py

Provide an exception class:

  • BranchNotSupported — an exception that is a subclass of Exception, raised when an operation is requested for a branch that is not supported.
runboat/build_images.py

The following three public functions must be implemented.

get_main_branch(branch: str) -> str

Takes a branch name and returns its "main branch" identifier — that is, the leading version portion of the branch name.

  • The main branch is the substring of branch that runs up to the first - character, with that character left out. If no - is present, the main branch is the entire branch name.
  • The main branch that results must be one of the supported branches. "15.0" is part of the supported set.
  • If the main branch that gets resolved is not supported, raise BranchNotSupported.

Examples of the required behavior:

  • get_main_branch("15.0") returns "15.0".
  • get_main_branch("15.0-ocabot-merge") returns "15.0".
  • get_main_branch("8.0") raises BranchNotSupported ("8.0" is not supported).
is_branch_supported(branch: str) -> bool

Takes a branch name and returns whether that branch is supported.

  • A branch counts as supported when its main branch (as defined above — the portion before the first -, or the whole string when there is no -) is in the supported set.
  • The return value is True for a supported branch and False otherwise. The function must not raise BranchNotSupported.

Examples of the required behavior:

  • is_branch_supported("15.0") returns True.
  • is_branch_supported("15.0-ocabot-merge") returns True.
  • is_branch_supported("8.0") returns False.
get_build_image(branch: str) -> str

Takes a branch name and returns, for that branch's main branch, the fully-qualified build container image reference.

  • The main branch is determined as explained above (the portion before the first -, or the whole string when no - is present).
  • When the main branch is not supported, raise BranchNotSupported.
  • For a supported main branch whose version is X.Y, the image reference that is returned has this form: ghcr.io/oca/oca-ci/py3.8-odooX.Y:latest

Examples of the required behavior:

  • get_build_image("15.0") returns "ghcr.io/oca/oca-ci/py3.8-odoo15.0:latest".
  • get_build_image("15.0-zzz") returns "ghcr.io/oca/oca-ci/py3.8-odoo15.0:latest".
  • get_build_image("8.0") raises BranchNotSupported.

Set of Supported Branches

At minimum, "15.0" must be a supported main branch, while "8.0" must not be supported. For "15.0", the image reference must be exactly ghcr.io/oca/oca-ci/py3.8-odoo15.0:latest.

Summary

A function renders the Kubernetes deployment files for a build. In the course of this rendering, it writes a kustomization.yaml file into a target directory. Alter the way this file is generated so that build-specific configuration is injected through Kustomize patches rather than through Kustomize vars, and make the filestore storage class configurable.

Public API

The rendering function must stay importable and callable under its existing invocation contract: it takes a build and a target output directory given as a filesystem path, and it renders files into that directory. An additional rendering argument for the storage class must not be required.

After a render succeeds, the target directory must contain at least:

  • kustomization.yaml
  • deployment.yaml

This task changes only the content of the generated kustomization.yaml; the renderer's existing invocation contract and the other rendered resources remain compatible.

The Configuration Contract

The filestore storage class must be taken from the RUNBOAT_BUILD_TEMPLATE_VARS configuration value. That value is a JSON object, and the renderer must use its case-sensitive storageClassName key as the storage-class patch value.

For example, with this configuration:

RUNBOAT_BUILD_TEMPLATE_VARS={"storageClassName":"my-storage-class"}

the storage-class patch must contain:

value: my-storage-class

The value must originate in this configuration object rather than in a hard-coded storage-class name or a differently named setting.

Behavior That Is Required

1. Eliminate the vars mechanism

The generated kustomization.yaml must not contain either of the following any longer:

  • A configMapGenerator entry called vars, including the config map that previously held the HOSTNAME literal.
  • A vars: section at the top level.

Every other existing configMapGenerator entry, along with its files or literals, must remain as before. The existing generator options must also be kept:

generatorOptions:
  disableNameSuffixHash: true
2. Add a patches section with a fixed order

The generated kustomization.yaml must contain a top-level patches: section that has exactly two entries, arranged in this order:

  1. Storage class of the filestore PVC

    • Kind of the target: PersistentVolumeClaim
    • Name of the target: odoo-data
    • Operation: a JSON Patch replace
    • Path: /spec/storageClassName
    • Value: the storageClassName value taken from RUNBOAT_BUILD_TEMPLATE_VARS

  2. Host of the Ingress

    • Kind of the target: Ingress
    • Name of the target: odoo
    • Operation: a JSON Patch replace
    • Path: /spec/rules/0/host
    • Value: the hostname of the build

The section must be structured as follows:

patches:
  - target:
      kind: PersistentVolumeClaim
      name: odoo-data
    patch: |-
      - op: replace
        path: /spec/storageClassName
        value: <storage-class-value>
  - target:
      kind: Ingress
      name: odoo
    patch: |-
      - op: replace
        path: /spec/rules/0/host
        value: <hostname-value>

Every patch: value is written in YAML block-scalar style (|-) and holds a single JSON Patch list with a single op: replace operation.

3. Configurability of the storage-class value

<storage-class-value> must be exactly the value configured under RUNBOAT_BUILD_TEMPLATE_VARS.storageClassName. For example, when the configured value of that key is my-storage-class, the first patch must render value: my-storage-class.

4. The build hostname value

<hostname-value> must be the build's hostname and must be the same value that was previously injected through the HOSTNAME var. For example:

value: build-slug.runboat.odoo-community.org

Formatting of the Output

  • Whitespace at the beginning or end of the complete generated file carries no significance; a blank line at the start or the end and a trailing newline are permitted.
  • The internal YAML structure and its ordering must match the layout given above.
  • The PVC patch must be positioned before the ingress patch.
  • Both patch bodies must use |- and must contain exactly the single replace operation shown for the corresponding target.

Task: Add Observer Pattern Support to BuildsDb

Summary

Change the BuildsDb class in runboat/db.py so that it supports the observer pattern, making it possible for external listeners to be notified when a build is added, changed, or removed from the database.

Required Modifications

BuildsDb.register_listener(listener)

Add a new public method called register_listener to the BuildsDb class. This method accepts a single listener object and registers that listener to receive notifications about build changes. More than one listener may be registered.

It is expected that the listener object exposes a callable attribute named build_updated. Whenever a relevant change occurs, build_updated must be called on each registered listener.

Notification Behavior

The build_updated method of registered listeners must be invoked in the following situations:

  • Adding a new build: Whenever add(build) is called with a build whose name is not already present, the build is stored, and build_updated must be called on each registered listener.

  • Changing an existing build: Whenever add(build) is called with a build whose name already exists but whose data differs from the currently stored build (e.g. a different status), the stored build is updated, and build_updated must be called on each registered listener.

  • Adding an unchanged build: Whenever add(build) is called with a build whose name already exists and whose data is identical to the currently stored build, no change is recorded, and build_updated must NOT be called.

  • Removing an existing build: Whenever remove(name) is called with a name that exists in the database, the build is removed, and build_updated must be called on each registered listener.

  • Removing a non-existent build: Whenever remove(name) is called with a name that does not exist, nothing is removed, and build_updated must NOT be called.

Changes to Signatures

The add and remove methods no longer need to return a boolean that indicates whether a change occurred; callers in this task do not use their return values. What matters are their side effects (storing/removing builds and notifying listeners).

Existing Behavior That Must Be Preserved

All other behavior of BuildsDb must remain unchanged, including:

  • add(build): stores a build keyed by its name; the stored build is replaced only when the new one differs.
  • remove(name): removes the build with the given name if that name is present.
  • get_for_commit(...): retrieves a build for a given commit.
  • search(repo): returns the list of builds that match a repository.
  • count_by_status(status): returns the number of builds that have the given BuildStatus.
  • count_by_init_status(init_status): returns the number of builds that have the given BuildInitStatus.
  • count_all(): returns the total number of builds.

BuildsDb is still constructed with no arguments (BuildsDb()), and an instance that has just been constructed has no registered listeners and contains no builds.

Imports used together with this class: from runboat.db import BuildsDb and from runboat.models import Build, BuildInitStatus, BuildStatus.

Overview

Registration of listener objects is supported by BuildsDb through the register_listener(listener) method. At present, when a build is added or removed and this produces an observable change to the database, the listener is notified by means of a call to a method named build_updated on it.

Change required: The method that is invoked on registered listeners to deliver notifications must be renamed to on_build_event. It must be called with the same semantics that applied when the previous build_updated method was called. Specifically:

Task Description

Build a resolver for build settings that is driven by configuration, and add repository discovery to the in-memory builds database. This work replaces the legacy hardcoded build-image module, while unrelated existing behavior is preserved.

1. Delete the legacy build-images module

The runboat.build_images module must be deleted in its entirety. Its APIs — including get_build_image, get_main_branch, is_branch_supported, and the module's other helpers — are no longer part of the application. No module that remains may import from runboat.build_images; existing consumers must instead use the new configuration-driven facilities.

The prior behavior of extracting a version prefix from a branch name must not be retained implicitly. Support for a branch is now decided by the configured branch patterns.

2. Build settings driven by configuration in runboat.settings

Extend runboat.settings with the public model and resolver described below. The module's existing unrelated application settings and its importable settings object must be preserved.

Configuration through RUNBOAT_REPOS

Repository build configuration must be accepted by way of the RUNBOAT_REPOS setting. Its value is JSON that follows this schema:

  • At the top level, the value is an ordered array of rule objects.
  • Each rule is made up of:
    • repo: a regular-expression pattern, given as a string, for repository names;
    • branch: a regular-expression pattern, given as a string, for branch names;
    • builds: an ordered array whose entries are build objects.
  • Each build object has at least a required string field named image.

The order of rules is significant. Rules are evaluated in configuration order, and the result is supplied by the first rule whose repo and branch patterns both match. Build entries are returned in the order in which they appear in that rule's builds array. Results coming from multiple matching rules are not merged.

Before the configured repo pattern is applied, repository input is normalized to lowercase. A lowercase pattern such as ^oca/.* therefore matches a caller-supplied repository such as OCA/mis-builder. This normalization does not cause a different owner to match: acsone/mis-builder does not match ^oca/.*. The configured branch pattern is what branch names are matched against; they must not be reduced to a numeric prefix. Anchors can be used in patterns to require an exact branch name.

By way of example, the JSON value below is valid for RUNBOAT_REPOS:

[
  {
    "repo": "^oca/.*",
    "branch": "^15.0$",
    "builds": [
      {
        "image": "ghcr.io/oca/oca-ci/py3.8-odoo15.0:latest"
      }
    ]
  }
]

Under this configuration, OCA/mis-builder on 15.0 is supported, while acsone/mis-builder on 15.0 and OCA/mis-builder on 15.0-stuff are not.

The BuildSettings class

In runboat.settings, provide a data object named BuildSettings that represents one configured build. It must:

  • be constructible using the keyword argument image, whose value is a string; and
  • support value-based equality, so that two BuildSettings instances with the same image compare equal.
The get_build_settings function

Provide the following function:

get_build_settings(repo: str, branch: str) -> list[BuildSettings]

The function must resolve the repository and branch it is supplied with against RUNBOAT_REPOS as described above, and return the selected rule's ordered build list as BuildSettings objects.

With the example configuration, the following call:

get_build_settings("OCA/mis-builder", "15.0")

must return exactly:

[BuildSettings(image="ghcr.io/oca/oca-ci/py3.8-odoo15.0:latest")]

If there is no configured rule that matches both the repository and the branch, the function must raise RepoOrBranchNotSupported. It must neither return None nor silently treat an unsupported pair as an empty result.

3. The RepoOrBranchNotSupported exception

In runboat.exceptions, RepoOrBranchNotSupported must be provided as a subclass of Exception. Whenever the supplied repository, branch, or repository/branch combination is unsupported by the configuration, get_build_settings must raise this exception. The existing unrelated exception types must remain available.

4. The repository model

Ensure runboat.models provides a Repo model which:

  • is constructible through the keyword argument name, whose value is a string; and
  • supports value-based equality based on name, so that two Repo instances with the same name compare equal.

From runboat.models, the existing importable names Build, BuildInitStatus, and BuildStatus must remain available, and unrelated existing model behavior must continue to work.

5. The BuildsDb.repos() method

Add the method below to runboat.db.BuildsDb:

repos(self) -> list[Repo]

It must return the distinct repositories that the builds currently held in the database represent, under these rules:

  • Return one Repo(name=...) object for each distinct build repo value.
  • Emit no duplicates when multiple builds have the same repository.
  • The order in which each distinct repository first appeared as builds were added must be preserved.
  • When no builds are held, return an empty list.
