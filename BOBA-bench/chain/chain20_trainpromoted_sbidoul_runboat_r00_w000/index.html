Overview

Implement a module that determines whether a given repository branch is supported and, for supported branches, resolves the appropriate build container image.

Module and API Surface

runboat/exceptions.py

Define an exception class:

  • BranchNotSupported — an exception (subclass of Exception) raised when an operation is requested for a branch that is not supported.
runboat/build_images.py

Implement the following three public functions.

get_main_branch(branch: str) -> str

Given a branch name, returns its "main branch" identifier — the leading version portion of the branch name.

  • The main branch is the substring of branch up to (but not including) the first - character. If there is no -, the entire branch name is the main branch.
  • The resulting main branch must be one of the supported branches. The supported set includes "15.0".
  • If the resolved main branch is not supported, raise BranchNotSupported.

Examples of required behavior:

  • get_main_branch("15.0") returns "15.0".
  • get_main_branch("15.0-ocabot-merge") returns "15.0".
  • get_main_branch("8.0") raises BranchNotSupported ("8.0" is not supported).
is_branch_supported(branch: str) -> bool

Given a branch name, returns whether it is supported.

  • A branch is supported if its main branch (as defined above — the portion before the first -, or the whole string when no - is present) is in the supported set.
  • Returns True when supported, False otherwise. This function must not raise BranchNotSupported.

Examples of required behavior:

  • is_branch_supported("15.0") returns True.
  • is_branch_supported("15.0-ocabot-merge") returns True.
  • is_branch_supported("8.0") returns False.
get_build_image(branch: str) -> str

Given a branch name, returns the fully-qualified build container image reference for that branch's main branch.

  • The main branch is resolved as described above (portion before the first -, or the whole string when no - is present).
  • If the main branch is not supported, raise BranchNotSupported.
  • For a supported main branch with version X.Y, the returned image reference has the form: ghcr.io/oca/oca-ci/py3.8-odooX.Y:latest

Examples of required behavior:

  • get_build_image("15.0") returns "ghcr.io/oca/oca-ci/py3.8-odoo15.0:latest".
  • get_build_image("15.0-zzz") returns "ghcr.io/oca/oca-ci/py3.8-odoo15.0:latest".
  • get_build_image("8.0") raises BranchNotSupported.

Supported Branches

At minimum, "15.0" must be a supported main branch, and "8.0" must not be supported. The image reference for "15.0" must be exactly ghcr.io/oca/oca-ci/py3.8-odoo15.0:latest.

Task: Add Observer Support to BuildsDb

Overview

Modify the BuildsDb class in runboat/db.py to support the observer pattern, allowing external listeners to be notified when a build is added, changed, or removed from the database.

Required Changes

BuildsDb.register_listener(listener)

Add a new public method register_listener to the BuildsDb class. It accepts a single listener object and registers it to receive notifications about build changes. Multiple listeners may be registered.

The listener object is expected to expose a callable attribute named build_updated. When a relevant change occurs, build_updated must be called on each registered listener.

Notification behavior

Registered listeners' build_updated method must be invoked in the following situations:

  • Adding a new build: When add(build) is called with a build whose name is not already present, the build is stored and each registered listener's build_updated must be called.

  • Changing an existing build: When add(build) is called with a build whose name already exists but whose data differs from the currently stored build (e.g. a different status), the stored build is updated and each registered listener's build_updated must be called.

  • Adding an unchanged build: When add(build) is called with a build whose name already exists and whose data is identical to the currently stored build, no change is recorded and build_updated must NOT be called.

  • Removing an existing build: When remove(name) is called with a name that exists in the database, the build is removed and each registered listener's build_updated must be called.

  • Removing a non-existent build: When remove(name) is called with a name that does not exist, nothing is removed and build_updated must NOT be called.

Signature Changes

The add and remove methods no longer need to return a boolean indicating whether a change occurred; their return values are not used by callers in this task. Their side effects (storing/removing builds and notifying listeners) are what matter.

Existing Behavior That Must Be Preserved

All other BuildsDb behavior must remain unchanged, including:

  • add(build): stores a build keyed by its name; replaces the stored build only when the new one differs.
  • remove(name): removes the build with the given name if present.
  • get_for_commit(...): retrieves a build for a given commit.
  • search(repo): returns the list of builds matching a repository.
  • count_by_status(status): returns the number of builds with the given BuildStatus.
  • count_by_init_status(init_status): returns the number of builds with the given BuildInitStatus.
  • count_all(): returns the total number of builds.

BuildsDb continues to be constructed with no arguments (BuildsDb()), and a freshly constructed instance has no registered listeners and contains no builds.

Relevant imports used with this class: from runboat.db import BuildsDb and from runboat.models import Build, BuildInitStatus, BuildStatus.

Overview

You must modify the BuildsDb class (the builds database) to change its listener notification interface and to adjust the return type of its search method.

Listener Interface Change

BuildsDb supports registering listener objects via a register_listener(listener) method. Currently, when a build is added or removed and this results in an observable change to the database, the listener is notified by calling a method named build_updated on it.

Required change: The notification method invoked on registered listeners must be renamed to on_build_event. It must be called with the same semantics that the previous build_updated method was called with. Specifically:

  • On add(build):

    • When adding a build that is new (not previously present), each registered listener's on_build_event must be called.
    • When adding a build that produces no change to the database (e.g., adding an equivalent build that already exists), listeners' on_build_event must not be called.

    • When removing a name that does not correspond to any stored build, listeners' on_build_event must not be called.

The matching/filtering behavior of search itself is otherwise unchanged; only the guarantee is that its return value is iterable (it need not be a list directly, but must yield the correct builds when iterated).

Parameters
  • signature: The value of the incoming request's X-Hub-Signature-256 header, or None if the header is absent. When present, it has the form "sha256=<hexdigest>".
  • secret: The configured webhook secret as bytes, or None if no secret is configured.
  • body: The raw request body as bytes.

  1. No secret configured — If secret is None, verification is skipped and the function returns True regardless of the other arguments.

  2. Secret configured but no signature provided — If secret is not None and signature is None, the function returns False.

  3. Secret configured with a signature provided — Compute the HMAC-SHA256 of body keyed with secret, and format it as "sha256=<hexdigest>" where <hexdigest> is the lowercase hexadecimal digest. Compare this computed value against the supplied signature:
