01 You are working on an HTML element generation library. 293 words · source specification

Overview

You are working on an HTML element generation library. Elements are created via callable objects (e.g., div) that accept positional shorthand strings for id/class attributes and keyword arguments for additional attributes. The resulting object, when converted to a string, renders as an HTML tag.

Required Behavior

When an element is called with:

  1. A leading shorthand string specifying an id (using the # prefix syntax), and
  2. One or more keyword arguments representing additional attributes,

the rendered output must correctly combine both the id derived from the shorthand string and the attributes derived from the keyword arguments.

Keyword Argument Name Normalization

Keyword argument names that end with a trailing underscore must have that trailing underscore stripped when rendered as an HTML attribute name. Specifically, a keyword argument named for_ must render as the HTML attribute for.

Concrete Requirement

Calling the div element with the positional shorthand "#theid" and the keyword argument for_="hello" must produce, when converted to a string:

<div id="theid" for="hello"></div>

That is:

  • The #theid shorthand yields id="theid".
  • The for_="hello" keyword argument yields for="hello" (trailing underscore removed).
  • The id attribute appears first, followed by the keyword-derived attribute.
  • The tag has no content (empty body) and renders with matching open/close tags.

API Surface

  • The div element callable must be importable and usable such that div("#theid", for_="hello") returns an object whose str() conversion produces the HTML shown above. (This is consistent with the existing library structure where div is already available for import and callable.)

Scope

The only change in scope is ensuring that keyword arguments are handled correctly in combination with a leading id/class shorthand string, including the trailing-underscore-to-attribute-name normalization. No other behavior should be altered.

02 You are working on htpy, a Python library for building HTML programmatically. 468 words · source specification

You are working on htpy, a Python library for building HTML programmatically. This task requires modifications to attribute value escaping, the public Element type, and framework interoperability (specifically Django's autoescape mechanism).

Public API

The library exposes HTML element builders importable from the top-level htpy package, e.g.:

from htpy import div, li

There must also be a public class named Element, importable from htpy, which is the type of the objects produced by these element builders (both standard elements like div/li and custom-tag elements).

Element builder behavior

Element builders support being called with:

  • A leading string shorthand argument for id/class (e.g. "#theid" sets id="theid").
  • Keyword arguments representing HTML attributes.

Keyword-argument attribute names undergo the existing name transformation, where trailing underscores are stripped (for_ → for) and internal underscores become hyphens (data_foo → data-foo).

Attribute value escaping (required change): Attribute values must be HTML-escaped when rendered. In particular, the < character in an attribute value must be rendered as &lt;. For example:

str(div("#theid", for_="hello", data_foo="<bar"))
# '<div id="theid" for="hello" data-foo="&lt;bar"></div>'

Attribute values that contain no special characters render unchanged.

Element instances and the Element type

Objects returned by element builders are instances of the Element class:

el = my_custom_element()
isinstance(el, Element)   # True
str(el) == "<my-custom-element></my-custom-element>"

(A custom element builder here is one whose tag name contains hyphens, e.g. my-custom-element.)

String rendering and __html__

Calling str() on an element produces its full HTML serialization as a plain str.

The result of str(element) must itself expose an __html__() method that returns the same HTML string. In other words, the rendered string value carries a "safe string" interface such that:

result = str(div(id="a")).__html__()
result == '<div id="a"></div>'

This means str() of an element must return a string-like object that both behaves as a normal str (comparing equal to the expected markup) and provides an __html__() method returning that same markup.

Django autoescape compatibility

When an element is placed into a Django template context and rendered, it must not be double-escaped by Django's autoescaping. Django recognizes objects that implement the __html__() protocol as already-safe. Element rendering must integrate with this protocol so that inserting an element into a Django template yields its HTML unescaped.

Concretely, given:

from django.template import Context, Template
from htpy import li

t = Template("<ul>{{ stuff }}</ul>")
result = t.render(Context({"stuff": li["I am safe!"]}))

the result must be:

<ul><li>I am safe!</li></ul>

That is, the element's markup must appear intact (angle brackets preserved, not escaped) when interpolated into a Django template.

Notes
  • The existing element/children/attribute APIs and their prior behaviors remain unchanged except where stated above.
  • Django is only needed for the interoperability behavior; the __html__() protocol on rendered strings is the mechanism that provides this compatibility.

  • ul — an HTML <ul> element object.
  • li — an HTML <li> element object.

Element objects support:

  • Child assignment via subscript: element[children] produces a new renderable element containing the given children.
  • Rendering via str(...): calling str() on an element produces its HTML string representation.

Required Behavior

1. Existing child handling (must continue to work)
  • A list or tuple passed as children is treated as a sequence of child items, each rendered in order. For example, a <ul> given a list/tuple of two <li> elements renders as <ul><li>a</li><li>b</li></ul>.
  • A generator passed as children is likewise iterated, each yielded item rendered in order.
2. Disallow nested lists/tuples inside lists/tuples

When children are provided as a list or tuple, no item within that list or tuple may itself be a list or tuple. Nesting must be rejected at the point the children are assigned to the element (i.e., during the element[...] subscript operation), by raising a ValueError.

The error message must depend on the type of the containing sequence and the type of the offending nested item:

  • A list containing a list item → message: list items cannot be of type list
  • A list containing a tuple item → message: list items cannot be of type tuple
  • A tuple containing a list item → message: tuple items cannot be of type list
  • A tuple containing a tuple item → message: tuple items cannot be of type tuple

This detection applies to the immediate items of the list/tuple being assigned. For example:

  • ul[[[]]] (a list whose single item is an empty list) raises ValueError with message list items cannot be of type list.
  • ul[[()]] (a list whose single item is an empty tuple) raises ValueError with message list items cannot be of type tuple.
  • ul[(([],),)] (a tuple whose single item is a tuple — but the inner tuple contains a list; detection must reach the tuple-containing-list level) raises ValueError with message tuple items cannot be of type list.
  • ul[(((),),)] (nested tuples) raises ValueError with message tuple items cannot be of type tuple.

The match string in each case is a substring of the raised ValueError's message.

The library must integrate correctly with third-party safe-string protocols so that:

Django (django.utils.safestring / django.utils.html)

  • A rendered htpy element, when placed into a Django template context and rendered, must be treated as already-safe HTML (not re-escaped). Rendering <ul>{{ stuff }}</ul> with stuff set to li["I am safe!"] must yield <ul><li>I am safe!</li></ul>.
  • A Django mark_safe(...) string passed as a child must be inserted verbatim without escaping. ul[mark_safe("<li>hello</li>")] renders to <ul><li>hello</li></ul>.
  • A Django escape(...) result passed as a child must be inserted as its (already escaped) safe content without double-escaping. ul[escape("<hello>")] renders to <ul>&lt;hello&gt;</ul>.

Jinja2 / MarkupSafe (markupsafe)

  • A rendered htpy element placed into a Jinja2 template must be treated as already-safe HTML. Rendering <ul>{{ stuff }}</ul> with stuff set to li["I am safe!"] must yield <ul><li>I am safe!</li></ul>.
  • A markupsafe.Markup(...) string passed as a child must be inserted verbatim without escaping. ul[Markup("<li>hello</li>")] renders to <ul><li>hello</li></ul>.
  • A markupsafe.escape(...) result passed as a child must be inserted as its (already escaped) safe content without double-escaping. ul[escape("<hi>")] renders to <ul>&lt;hi&gt;</ul>.

In summary: strings that carry a "safe" marker (via Django's or MarkupSafe's protocols) must be emitted as-is without additional HTML escaping, and rendered htpy elements must themselves be recognized as safe HTML when embedded in Django and Jinja2 templates.

04 You must implement HTML element construction that accepts attributes through multiple mechanisms simultaneously 451 words · source specification

Overview

You must implement HTML element construction that accepts attributes through multiple mechanisms simultaneously: a shorthand string, a dictionary of attributes, and keyword arguments. These sources must be combined according to well-defined precedence rules.

Public API

There must be a callable named div (importable such that div(...) produces an HTML <div> element). Calling str() on the result must produce the element's HTML string representation, including a closing tag (e.g. <div ...></div> with no children).

Accepted Positional/Keyword Inputs

The div callable must accept, in any combination:

  1. A shorthand string as a positional argument. This string may encode:

    • An id via a leading # (e.g. "#theid" → id="theid").
    • A class via a leading . (e.g. ".a" → class="a").

  2. A dictionary as a positional argument, whose keys/values are attribute names/values (e.g. {"a": "1", "for": "a"}, {"class": "b"}, {"foo": "a"}).

  3. Keyword arguments for attributes. Keyword argument names are normalized as follows:

    • A single trailing underscore is stripped (e.g. for_ → for, class_ → class).
    • Internal underscores are converted to hyphens (e.g. data_foo → data-foo).

The shorthand string and the dictionary are both optional positional arguments and may appear together (shorthand string first, then dictionary).

Attribute Value Escaping

Attribute values must be HTML-escaped. In particular, < must be rendered as &lt; (e.g. data_foo="<bar" → data-foo="&lt;bar").

Combination and Precedence Rules

When the same attribute name is provided by more than one source, the resolved value follows this precedence (highest wins):

  1. Keyword arguments (highest priority)
  2. Dictionary positional argument
  3. Shorthand string (lowest priority)

This applies to all attribute names, including class and id.

Ordering of attributes in output

Attributes appear in the output in the order they are first introduced across the combined sources, with the shorthand string contributing first, then the dictionary, then keyword arguments. When a later source overrides the value of an already-introduced attribute, the attribute keeps its original position but takes the overriding value.

Concrete Behavioral Requirements

  • div("#theid", for_="hello", data_foo="<bar") → <div id="theid" for="hello" data-foo="&lt;bar"></div>

  • div({"a": "1", "for": "a"}, for_="b", b="2") → <div a="1" for="b" b="2"></div> (The for attribute is introduced by the dictionary, keeps its position, but its value is overridden by the for_ keyword. The b keyword is appended after.)

  • div(".a", {"class": "b"}, class_="c") → <div class="c"></div> (The class attribute is introduced by the shorthand .a; the dictionary and keyword both target class, and the keyword value wins.)

  • div(".a", {"class": "b"}) → <div class="b"></div> (The class attribute is introduced by the shorthand .a; the dictionary value overrides the shorthand.)

  • div({"foo": "a"}, foo="b") → <div foo="b"></div> (The foo attribute is introduced by the dictionary; the keyword value overrides it.)

Task Specification: Adopt MarkupSafe's Markup API in htpy

Overview

The htpy library builds HTML programmatically. This task changes the public API used for marking strings as "safe" (already-escaped) HTML content. The library must expose Markup from its top-level package and use it as the canonical safe-string type.

Public API Requirements

The top-level htpy package must export the following name:

  • Markup — the safe-string type used to wrap already-escaped/trusted HTML content. This must be the Markup class from the markupsafe library (i.e. from markupsafe import Markup). Wrapping a string in Markup(...) marks it as safe so it will not be escaped when rendered.

The previously available names mark_safe and SafeString must no longer be part of the public htpy API. Only Markup is provided for safe-string handling.

Behavioral Requirements

Safe content is not escaped

When a value wrapped in Markup(...) is used as a child of an element, its content is emitted verbatim (not HTML-escaped):

  • str(div[Markup("<hello></hello>")]) → "<div><hello></hello></div>"
  • str(div[Markup("<foo></foo>")]) → "<div><foo></foo></div>"
Safe content in attribute values is not escaped

When a Markup(...) value is used as an attribute value (keyword argument), it is emitted verbatim:

  • str(div(id=Markup("<hi>"))) → '<div id="<hi>"></div>'
Safe content in dict-based attributes is not escaped

When Markup(...) values are used as both keys and values in a dict passed as attributes, they are emitted verbatim:

  • str(div({Markup('<"'): Markup('"hello"')})) → '<div <"=""hello""></div>'
Regular (non-safe) content is still escaped

Ordinary strings continue to be HTML-escaped:

  • str(div["<foo></foo>"]) → "<div>&lt;foo&gt;&lt;/foo&gt;</div>"
Interoperability with Django safe strings

Because markupsafe.Markup and Django's SafeString share the "safe string" protocol, a value produced by Django (e.g. django.utils.safestring.SafeString("<li>hello</li>")) used as a child must also be emitted verbatim:

  • str(ul[django_SafeString("<li>hello</li>")]) → "<ul><li>hello</li></ul>"
Typing

Markup(...) must be typed such that its return value has static type Markup. Code performing assert_type(Markup("..."), Markup) must type-check successfully.

Notes

  • The escaping/rendering behavior for regular strings and the general element/attribute construction API remain unchanged. Only the safe-string entry point changes from mark_safe/SafeString to Markup.

Dependencies

The markupsafe library is a runtime dependency and must be available for import.

Related Existing Behavior (unchanged, must continue to work)

The following behaviors are unrelated to safe-strings but must remain intact:

  • Passing id/class shorthand strings in the wrong order raises ValueError with a message matching id (#) must be specified before classes (.).
  • Passing a non-string as an id/class shorthand (e.g. a dict) raises ValueError with a message matching id/class strings must be str. got {'oops': 'yes'}.
  • Indexing a void element such as img with children raises ValueError with a message matching img elements cannot have children.

Extend child handling so that the following two kinds of children are supported as element children and rendered correctly during iteration:

1. Generator children (lazy iterables)

A child may be a generator (an object produced by a generator function). When an element containing a generator child is iterated:

  • The generator must not be started or advanced until the iteration reaches the point where that child is rendered.
  • Each element yielded by the generator is rendered in order, inline, at the child's position.
  • The generator is only advanced as the consuming iteration demands its values (fully lazy streaming). Consuming the chunk(s) for a yielded child must not advance the generator past the point needed to produce those chunks.

Concretely, given a generator that yields element children, iterating the containing element yields: the parent's opening tag first (without touching the generator), then the streamed chunks of each yielded child in order, then the parent's closing tag once the generator is exhausted.

  • The callable must not be invoked until the iteration reaches the point where that child is rendered.
  • When reached, the callable is invoked once and its return value is rendered inline at the child's position.

Concretely, given a callable that returns an element, iterating the containing element yields: the parent's opening tag first (without invoking the callable), then the rendered chunk(s) of the callable's return value, then the parent's closing tag.

  • All streamed chunks are strings.

  • Laziness is essential: neither generators nor callables may be evaluated eagerly at the time the child is attached to the element or when iteration begins — only when iteration structurally reaches that child.
