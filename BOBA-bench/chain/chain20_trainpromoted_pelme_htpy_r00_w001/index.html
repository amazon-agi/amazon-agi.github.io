01 This task is set in an HTML element generation library. 324 words · source specification, reworded by GLM-5.3-Flash

Task Description

Background

This task is set in an HTML element generation library. Element creation happens through callable objects (e.g., div) that accept positional shorthand strings for id/class attributes as well as keyword arguments for the additional attributes. Once converted to a string, the resulting object renders as an HTML tag.

Behavior Requirements

If a call to an element provides:

  1. A leading shorthand string that specifies an id (making use of the # prefix syntax), and
  2. One or more keyword arguments that stand for additional attributes,

the rendered output must correctly combine both the id taken from the shorthand string and the attributes taken from the keyword arguments.

Normalizing Keyword Argument Names

A keyword argument name that ends with a trailing underscore must have that trailing underscore stripped when it is rendered as an HTML attribute name. Concretely, a keyword argument named for_ must render as the HTML attribute for.

Specific Requirement

Calling the div element with the positional shorthand "#theid" together with the keyword argument for_="hello" must produce the following once converted to a string:

<div id="theid" for="hello"></div>

In other words:

  • The shorthand #theid yields id="theid".
  • The keyword argument for_="hello" yields for="hello" (with the trailing underscore removed).
  • The id attribute comes first, followed by the attribute derived from the keyword argument.
  • The tag contains no content (empty body) and renders with matching open/close tags.

API Surface

  • It must be possible to import the div element callable and use it such that div("#theid", for_="hello") returns an object whose str() conversion produces the HTML shown above. (This is in line with the existing library structure, where div is already available for import and callable.)

Scope

The only change in scope is to ensure that keyword arguments are handled correctly when combined with a leading id/class shorthand string, including the trailing-underscore-to-attribute-name normalization. Aside from that, no behavior should be altered.

02 You are working on htpy, a Python library used to build HTML programmatically. 501 words · source specification, reworded by GLM-5.3-Flash

Task Description

You are working on htpy, a Python library used to build HTML programmatically. This task requires changes to attribute value escaping, the public Element type, and framework interoperability (specifically Django's autoescape mechanism).

The public API

HTML element builders are exposed by the library, importable from the top-level htpy package, e.g.:

from htpy import div, li

There must also be a public class called Element, importable from htpy, and it is the type of the objects that these element builders produce (both standard elements like div/li and custom-tag elements).

Behavior of element builders

Element builders support being called with the following:

  • A leading string shorthand argument used for id/class (e.g. "#theid" sets id="theid").
  • Keyword arguments that represent HTML attributes.

Attribute names passed as keyword arguments go through the existing name transformation: trailing underscores are stripped (for_ → for) and internal underscores become hyphens (data_foo → data-foo).

Attribute value escaping (required change): When rendered, attribute values must be HTML-escaped. In particular, a < character appearing in an attribute value must be rendered as &lt;. For example:

str(div("#theid", for_="hello", data_foo="<bar"))
# '<div id="theid" for="hello" data-foo="&lt;bar"></div>'

Rendering leaves attribute values that contain no special characters unchanged.

Element instances and type Element

The objects that element builders return are instances of the Element class:

el = my_custom_element()
isinstance(el, Element)   # True
str(el) == "<my-custom-element></my-custom-element>"

(Here, a custom element builder is one whose tag name contains hyphens, e.g. my-custom-element.)

Rendering to a string and __html__

Calling str() on an element produces the element's full HTML serialization as a plain str.

The result of str(element) must itself expose an __html__() method which returns the same HTML string. Put differently, the string value that results from rendering carries a "safe string" interface such that:

result = str(div(id="a")).__html__()
result == '<div id="a"></div>'

This means str() of an element must return a string-like object, one that both behaves as a normal str (comparing equal to the expected markup) and provides an __html__() method returning that same markup.

Compatibility with Django autoescape

An element placed into a Django template context and rendered must not be double-escaped by Django's autoescaping. Objects that implement the __html__() protocol are recognized by Django as already-safe. Rendering of elements must integrate with this protocol so that inserting an element into a Django template yields its HTML unescaped.

In concrete terms, given:

from django.template import Context, Template
from htpy import li

t = Template("<ul>{{ stuff }}</ul>")
result = t.render(Context({"stuff": li["I am safe!"]}))

the result must be the following:

<ul><li>I am safe!</li></ul>

That is to say, when an element is interpolated into a Django template, its markup must appear intact (angle brackets preserved, not escaped).

Additional notes
  • Apart from what is stated above, the existing element/children/attribute APIs and their prior behaviors remain unchanged.
  • Django is needed only for the interoperability behavior; the mechanism that provides this compatibility is the __html__() protocol on rendered strings.
03 You are working on htpy, an HTML generation library. 730 words · source specification, reworded by GLM-5.3-Flash

Specification of the Task

General Description

You are working on htpy, an HTML generation library. It offers HTML element objects that can be combined with children through subscript ([...]) syntax and rendered to HTML strings. The task covers two areas: (1) rejecting lists/tuples that are nested in element children, and (2) ensuring compatibility with the safe-string / escaping mechanisms of Django, Jinja2, and MarkupSafe.

Public Interface

Everything listed below must be importable from the htpy module:

  • ul — an element object for the HTML <ul> element.
  • li — an element object for the HTML <li> element.

Element objects support the following:

  • Assigning children via subscript: element[children] results in a new renderable element that contains the given children.
  • Rendering via str(...): calling str() on an element gives its HTML string representation.

Behavior Requirements

1. Current child handling (must keep working)
  • A list or tuple that is passed as children is handled as a sequence of child items, each of which is rendered in order. For example, a <ul> that is given a list/tuple of two <li> elements renders as <ul><li>a</li><li>b</li></ul>.
  • A generator that is passed as children is likewise iterated, with each yielded item rendered in order.
2. Reject lists/tuples nested inside lists/tuples

When children are supplied as a list or tuple, no item inside that list or tuple may itself be a list or tuple. Such nesting must be rejected at the point where the children are assigned to the element (i.e., during the element[...] subscript operation), by raising a ValueError.

The message of the error must depend on the type of the containing sequence and on the type of the offending nested item:

  • A list that contains a list item → message: list items cannot be of type list
  • A list that contains a tuple item → message: list items cannot be of type tuple
  • A tuple that contains a list item → message: tuple items cannot be of type list
  • A tuple that contains a tuple item → message: tuple items cannot be of type tuple

This detection applies to the immediate items of the list/tuple that is being assigned. For example:

  • ul[[[]]] (a list in which the single item is an empty list) raises ValueError with message list items cannot be of type list.
  • ul[[()]] (a list in which the single item is an empty tuple) raises ValueError with message list items cannot be of type tuple.
  • ul[(([],),)] (a tuple whose single item is a tuple — but that inner tuple contains a list; detection must reach the tuple-containing-list level) raises ValueError with message tuple items cannot be of type list.
  • ul[(((),),)] (tuples nested in tuples) raises ValueError with message tuple items cannot be of type tuple.

In each case, the match string is a substring of the message of the raised ValueError.

3. Compatibility with safe-string / escaping

The library must integrate correctly with third-party safe-string protocols so that the following holds:

Django (django.utils.safestring / django.utils.html)

  • When a rendered htpy element is placed into a Django template context and rendered, it must be treated as already-safe HTML (not re-escaped). When <ul>{{ stuff }}</ul> is rendered with stuff set to li["I am safe!"], this must yield <ul><li>I am safe!</li></ul>.
  • When a Django mark_safe(...) string is passed as a child, it must be inserted verbatim without escaping. ul[mark_safe("<li>hello</li>")] renders as <ul><li>hello</li></ul>.
  • When a Django escape(...) result is passed as a child, it must be inserted as its (already escaped) safe content without double-escaping. ul[escape("<hello>")] renders as <ul>&lt;hello&gt;</ul>.

Jinja2 / MarkupSafe (markupsafe)

  • When a rendered htpy element is placed into a Jinja2 template, it must be treated as already-safe HTML. When <ul>{{ stuff }}</ul> is rendered with stuff set to li["I am safe!"], this must yield <ul><li>I am safe!</li></ul>.
  • When a markupsafe.Markup(...) string is passed as a child, it must be inserted verbatim without escaping. ul[Markup("<li>hello</li>")] renders as <ul><li>hello</li></ul>.
  • When a markupsafe.escape(...) result is passed as a child, it must be inserted as its (already escaped) safe content without double-escaping. ul[escape("<hi>")] renders as <ul>&lt;hi&gt;</ul>.

To summarize: strings carrying a "safe" marker (via Django's or MarkupSafe's protocols) must be emitted as-is without additional HTML escaping, and rendered htpy elements must themselves be recognized as safe HTML when embedded in Django and Jinja2 templates.

04 You must implement HTML element construction that accepts attributes via multiple mechanisms simultaneously 480 words · source specification, reworded by GLM-5.3-Flash

Task Description

Summary

You must implement HTML element construction that accepts attributes via multiple mechanisms simultaneously: a shorthand string, a dictionary of attributes, and keyword arguments. These sources must be merged following well-defined precedence rules.

Public Interface

A callable named div must exist (importable so that div(...) produces an HTML <div> element). Calling str() on the result must produce the element's HTML string representation, a closing tag included (e.g. <div ...></div> with no children).

Accepted Positional and Keyword Inputs

The div callable must accept the following, in any combination:

  1. A shorthand string passed as a positional argument. The string may encode:

    • An id by means of a leading # (e.g. "#theid" → id="theid").
    • A class by means of a leading . (e.g. ".a" → class="a").

  2. A dictionary passed as a positional argument; its keys/values are the attribute names/values (e.g. {"a": "1", "for": "a"}, {"class": "b"}, {"foo": "a"}).

  3. Keyword arguments used as attributes. The names of keyword arguments are normalized as follows:

    • A single trailing underscore is removed (e.g. for_ → for, class_ → class).
    • Interior underscores are converted to hyphens (e.g. data_foo → data-foo).

Both the shorthand string and the dictionary are optional as positional arguments, and the two may be supplied together (the shorthand string first, then the dictionary).

Escaping of Attribute Values

The values of attributes must be HTML-escaped. In particular, < must be output as &lt; (e.g. data_foo="<bar" → data-foo="&lt;bar").

Rules for Combination and Precedence

Whenever the same attribute name is supplied by more than one source, the resulting value follows this precedence (highest wins):

  1. Keyword arguments (highest priority)
  2. Dictionary given as a positional argument
  3. Shorthand string (lowest priority)

This holds for all attribute names, class and id included.

Attribute Order in the Output

In the output, attributes show up in the order in which they are first introduced across the combined sources: the shorthand string contributes first, then the dictionary, then keyword arguments. If a later source overrides the value of an attribute that has already been introduced, that attribute keeps its original position but takes on the overriding value.

Concrete Requirements for Behavior

  • div("#theid", for_="hello", data_foo="<bar") → <div id="theid" for="hello" data-foo="&lt;bar"></div>

  • div({"a": "1", "for": "a"}, for_="b", b="2") → <div a="1" for="b" b="2"></div> (The dictionary introduces the for attribute, which keeps its position, but its value is overridden by the for_ keyword. The b keyword gets appended after.)

  • div(".a", {"class": "b"}, class_="c") → <div class="c"></div> (The shorthand .a introduces the class attribute; class is targeted by both the dictionary and the keyword, and the keyword's value wins.)

  • div(".a", {"class": "b"}) → <div class="b"></div> (The shorthand .a introduces the class attribute; the dictionary's value overrides the shorthand.)

  • div({"foo": "a"}, foo="b") → <div foo="b"></div> (The dictionary introduces the foo attribute; the keyword's value overrides it.)

08 Bringing MarkupSafe's Markup API into htpy 464 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Bringing MarkupSafe's Markup API into htpy

Summary

The htpy library constructs HTML programmatically. This task alters the public API by which strings get marked as "safe" (already-escaped) HTML content. The library must expose Markup from its top-level package and treat it as the canonical safe-string type.

Requirements for the Public API

The following name must be exported by the top-level htpy package:

  • Markup — the safe-string type for wrapping already-escaped/trusted HTML content. It must be the Markup class from the markupsafe library (i.e. from markupsafe import Markup). When a string is wrapped in Markup(...), it is marked as safe and will not be escaped when rendered.

mark_safe and SafeString were previously available; they must no longer be part of the public htpy API. For safe-string handling, Markup is the only name provided.

Requirements on Behavior

Escaping is skipped for safe content

If a value wrapped in Markup(...) appears as a child of an element, its content is emitted verbatim (not HTML-escaped):

  • str(div[Markup("<hello></hello>")]) → "<div><hello></hello></div>"
  • str(div[Markup("<foo></foo>")]) → "<div><foo></foo></div>"
Attribute values with safe content are not escaped

If a Markup(...) value serves as an attribute value (keyword argument), it is emitted verbatim:

  • str(div(id=Markup("<hi>"))) → '<div id="<hi>"></div>'
Dict-based attributes with safe content are not escaped

If Markup(...) values are used as both keys and values in a dict passed as attributes, they are emitted verbatim:

  • str(div({Markup('<"'): Markup('"hello"')})) → '<div <"=""hello""></div>'
Escaping still applies to regular (non-safe) content

HTML escaping continues to apply to ordinary strings:

  • str(div["<foo></foo>"]) → "<div>&lt;foo&gt;&lt;/foo&gt;</div>"
Interoperation with Django safe strings

Since markupsafe.Markup and Django's SafeString share the "safe string" protocol, a value produced by Django (e.g. django.utils.safestring.SafeString("<li>hello</li>")) that is used as a child must also be emitted verbatim:

  • str(ul[django_SafeString("<li>hello</li>")]) → "<ul><li>hello</li></ul>"
Typing

Typing of Markup(...) must be such that its return value has static type Markup. Code that performs assert_type(Markup("..."), Markup) must type-check successfully.

Remarks

  • Escaping/rendering behavior for regular strings, together with the general element/attribute construction API, remains unchanged. The safe-string entry point is the only thing that changes, switching from mark_safe/SafeString to Markup.

Dependencies

As a runtime dependency, the markupsafe library must be available for import.

Related Existing Behavior (unchanged, must keep working)

The behaviors listed below are unrelated to safe-strings but must remain intact:

  • Supplying id/class shorthand strings in the wrong order raises ValueError with a message matching id (#) must be specified before classes (.).
  • When a non-string is passed as an id/class shorthand (e.g. a dict), this raises ValueError with a message matching id/class strings must be str. got {'oops': 'yes'}.
  • When a void element such as img is indexed with children, this raises ValueError with a message matching img elements cannot have children.
