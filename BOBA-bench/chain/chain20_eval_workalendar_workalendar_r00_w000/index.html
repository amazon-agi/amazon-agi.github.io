01 Inside workalendar.core, you must implement a Calendar base class offering date/calendar utilities. 608 words · source specification, reworded by GLM-5.3-Flash

Task Description

Summary

Inside workalendar.core, you must implement a Calendar base class offering date/calendar utilities. Subclassing is the intended usage pattern: it is the subclasses that define their own holidays and weekend days, while the base class builds workday logic on top of those definitions.

Public API

Module

Everything is located in workalendar/core.py, which can be imported as workalendar.core.

Class: Calendar

Every method listed below must be supported by the base class; subclasses may override any of them.

holidays(self, year=None)

For the year supplied, the return value is the set of holiday dates. The base-class version is permitted to return an empty collection; the subclasses that override it return a set of datetime.date objects. Whenever other methods call it, they will pass a specific year (integer).

get_weekend_days(self)

What this returns is the collection of weekday numbers regarded as weekend days (following Python's date.weekday() convention, in which Monday is 0 and Sunday is 6). Overriding it is up to subclasses; it may return an empty list, which signals that there are no weekend days.

is_workday(self, day, extra_workdays=None, extra_holidays=None)

For the datetime.date it is given, this method works out whether that day is a working day.

Either of the following makes a day not a workday:

  • The values returned by get_weekend_days() contain the day's weekday number, OR
  • The set of holidays returned by holidays() for that day's year contains the day.

These two optional parameters serve to override the default determination:

  • extra_workdays: an iterable of datetime.date objects. Should the given day turn up in this collection, the day must be handled as a workday, even when it would otherwise be a holiday or a weekend day.
  • extra_holidays: an iterable of datetime.date objects. Should the given day turn up in this collection, the day must be handled as not a workday, even when it would otherwise be a normal working day.

When the workday decision is made, extra_workdays carries precedence: a day found in extra_workdays is a workday, holidays/weekends notwithstanding. A day found in extra_holidays is not a workday.

The value returned is boolean-compatible.

add_workdays(self, day, delta)

Accepts a starting datetime.date (day) plus a positive integer count (delta); what it returns is the datetime.date reached after advancing delta working days forward from day.

Counting takes as its first day the one after the start date. Walking through the subsequent calendar days, the count goes up by one for each day that qualifies as a workday (as judged by is_workday, with no extra overrides); days that are not workdays are skipped. The returned date is the one on which the delta-th workday is reached.

As an illustration, take a calendar that has no weekend days and only two holidays in a year (December 25 and January 1): beginning at December 20 and advancing 20 workdays brings you to January 11 of the following year (December 25 and January 1 get skipped, so the plain 20-day arithmetic ends up shifted by 2 days).

get_last_weekday_in_month(year, month, weekday)

(Taken to exist already / must be available.) A method that hands back the datetime.date of the last occurrence of the supplied weekday within the specified month and year. By way of example, the last Thursday of January 2013 is January 31, 2013.

Constants

The module must expose weekday constants that can serve as date.weekday() values, with at least THU (Thursday = 3) among them.

Remarks

  • Every date object is a datetime.date instance.
  • holidays() and get_weekend_days() are where extension happens: by overriding these two, a subclass supplies its fixed definitions, and all of the workday logic follows from them.

Task Specification: Reworking the Holiday Representation in workalendar

Summary

Right now, the calendar system inside the workalendar package returns holidays in the form of a set of dates. You must rework this representation so that the holidays a calendar returns form an ordered, immutable collection of (date, label) pairs; besides that, a separate accessor that yields only the dates must be provided.

Behavior Requirements

Calendar.holidays(year=None)

The base Calendar class in workalendar.core, together with all of its subclasses, must return, via the holidays(year=None) method, holidays in the form of a tuple (not a set).

Each element of the tuple that comes back is itself a two-item tuple with the shape (date, label):

  • date is a datetime.date instance for a holiday of the supplied year.
  • label is a string carrying the holiday's human-readable name.

When no year argument is passed in, the method must work with a default year (matching the default-year behavior the codebase already has).

The holidays(year) result must remain cached, and the value cached for each year — held in the internal _holidays mapping, which is keyed by year — must be exactly the same tuple object as the one the method returns. Once holidays(year) has been called, looking up that year in the internal _holidays cache must yield equal values.

Calendar.holidays_dates(year=None)

A new method, holidays_dates(year=None), must be added to the Calendar class. It must return a collection that holds only the date part of each holiday of the year in question (i.e., the dates taken out of the (date, label) pairs that holidays produces). Testing membership with in against a datetime.date must work correctly on its result.

Handling of the year argument works the same as in holidays: if it is left out, the default year is used.

Compatibility Across Subclasses

All existing calendar subclasses across the whole package (the United States, South Korea, and France calendars among them, along with any others) must expose, via the base-class mechanism, working holidays_dates(year) behavior; for a requested year, the correct set of holiday dates must be returned. In concrete terms:

  • United States calendar: the year 2013 includes Jan 1, Jul 4, Nov 11. Inauguration Day: not present in 2008; present on Jan 20, 2009; if Jan 20 lands on a Sunday (1985), the observed holiday shifts to Jan 21 (Jan 20 is not included; Jan 21 is).
  • South Korea calendar: the year 2013 includes Jan 1, Mar 1, May 5.
  • France calendar: the year 2013 includes Jan 1, Apr 1 (Easter Monday), May 1.

These points are a consequence of the representation change; the holiday computations underneath stay as they are, but the date values must be reachable through holidays_dates.

Public API

  • Module: workalendar.core
    • Class Calendar
      • holidays(self, year=None) → tuple of (datetime.date, str) pairs
      • holidays_dates(self, year=None) → collection of datetime.date
  • The calendar classes that already exist — located in their current modules (workalendar.america.UnitedStatesCalendar, workalendar.asia.SouthKoreaCalendar, workalendar.europe.FranceCalendar, etc.) — must inherit the behavior above and produce holiday dates that are accessible via holidays_dates.

Additional Notes

  • Any concrete implementation of holidays(year) must produce a tuple of (date, label) pairs rather than a set of bare dates.
  • holidays_dates must derive its output purely from the pairs that holidays returns.

Background

The workalendar library, on which you will be working, offers calendar classes that compute holidays for various countries/regions. Two related changes need to be made to the Calendar base class (in workalendar.core), and you must ensure that the behavior propagates to all subclasses.

Overview

The Python library you will be working on is workalendar, which — for various countries — works out which days are holidays and which are working days. This task requires that parts of the public API be renamed and restructured, and that the data type standing for a year's holidays be changed.

  • workalendar.core.Calendar — the abstract base class.
  • workalendar.america.UnitedStatesCalendar
  • workalendar.asia.SouthKoreaCalendar
  • workalendar.europe.FranceCalendar

Behavior Requirements

Calendar.holidays(self, year=None)
  • What this method returns is the collection of holiday dates for the supplied year. Should year be omitted, a default year comes into play: the current year, the one used elsewhere in the class.
  • A set of datetime.date objects is what the return value must be (each element is a date, not a tuple and not a (date, label) pair).
  • The result must be cached/stored internally in a mapping keyed by year that is reachable as self._holidays; for any year, self._holidays[year] must equal the same set the method returns for that year.
  • Within the base Calendar class, holidays depends on a mechanism that subclasses supply in order to enumerate the year's holidays. The actual holiday computation is what concrete subclasses override/provide.

Sets of date objects that include the correct national holidays are what concrete subclasses must produce. Here are the specific expected results:

UnitedStatesCalendar:

  • The holidays of 2013 include: Jan 1, Jul 4, Nov 11, Dec 25.
  • Inauguration day handling: only a presidential inauguration year makes it a holiday. It is absent in 2008; Jan 20 is present in 2009; for 1985, because Jan 20 falls on a Sunday, Jan 20 is not present, but Jan 21 is present.

SouthKoreaCalendar:

  • The holidays of 2013 include: Jan 1, Mar 1, May 5.

FranceCalendar:

  • The holidays of 2013 include: Jan 1, Apr 1, May 1, Nov 11, Dec 25 (among others).
Calendar.is_working_day(self, day, extra_working_days=None, extra_holidays=None)

Any previously named "workday" method is replaced by this one. Its purpose is to determine whether day (a datetime.date) is a working day.

  • Whenever a day lands on a weekend (as the calendar's get_weekend_days() defines them) or is a holiday for that year, it is not a working day.
  • Parameters:
    • extra_working_days: an iterable of date objects; days belonging to it must be treated as working days even if they would otherwise be holidays. True is returned when extra_working_days contains the day.
    • extra_holidays: an iterable of date objects; days belonging to it must be treated as non-working days even if they would otherwise be working days. False is returned when extra_holidays contains the day.

Calendar.add_working_days(self, day, count)

Any method previously named "workday" is replaced by this method. It returns the date reached by moving count working days forward, starting at day.

  • day is returned unchanged by add_working_days(day, 0).
  • No weekend day or holiday is counted toward count; such days are skipped.
  • Example (France): take 2013-10-30 as the starting point; adding 1 → 2013-10-31, adding 2 → 2013-11-04, adding 3 → 2013-11-05, with the weekend of Nov 2–3 skipped.
  • Example (a calendar that has no weekends and whose holidays fall only on Dec 25 and Jan 1): take 2013-12-20 as the starting point; adding 20 working days → 2014-01-11.
Calendar.get_weekend_days(self)

The method is overridable and returns the list of weekday indices that are regarded as weekends. A subclass may return an empty list to signal that there are no weekends.

API Removals and Renames

  • holidays_set has disappeared: any method that carried this name before no longer exists. The job it used to do is now done by holidays, which returns a set.
  • Any method named is_workday / add_workdays is to be renamed is_working_day / add_working_days respectively.
  • Tuples of (date, label) pairs are no longer returned by holidays, and neither is a sorted/ordered sequence; what it returns instead is an unordered set of dates.

Notes

Task Specification: Nomenclature of the Calendar API

Summary

The workalendar package supplies calendar classes that compute holidays and working days for multiple regions. Update the package's working-day API so that the clearer working day nomenclature is used consistently, while the calendars' existing holiday and weekend behavior is preserved.

The task is an API rename combined with a naming-consistency effort. Region-specific calendars must keep obtaining their working-day behavior from the base calendar API.

Public API Requirements

workalendar.core.Calendar.is_working_day
is_working_day(self, day, extra_working_days=None, extra_holidays=None)

The method determines whether day is a working day.

  • day is the datetime.date being classified.
  • extra_working_days is an optional iterable of datetime.date objects whose dates must be treated as working days even if the calendar would normally classify them as weekends or holidays.
  • extra_holidays is an optional iterable of datetime.date objects whose dates must be treated as non-working days even if the calendar would normally classify them as working days.
  • The value returned is a boolean.
  • The order of precedence among the exceptions is significant:
    1. When day appears in extra_working_days, return True.
    2. Otherwise, when day appears in extra_holidays, return False.
    3. Otherwise, the calendar's regular weekend and holiday rules apply.
  • As a result, if one and the same date shows up in both exception iterables, extra_working_days takes priority and that date is working.
  • Under the regular rules, a date that is a configured weekend day or a recognized calendar holiday is non-working; any other date is working.
  • When called on the bare base Calendar, which does not implement the required calendar classification, the method must raise NotImplementedError. Concrete region-specific subclasses must classify dates according to the weekends and holidays configured for them.

This method supersedes the earlier is_workday naming, and the extra_working_days keyword supersedes the earlier extra_workdays keyword name.

workalendar.core.Calendar.add_working_days
add_working_days(
    self,
    day,
    delta,
    extra_working_days=None,
    extra_holidays=None,
)

Return the datetime.date that is reached after advancing delta working days from day.

  • day is the datetime.date at which to start.
  • delta is an integer number of working days by which to advance.
  • When delta == 0, return day unchanged.
  • For a positive delta, counting begins on the calendar day after day; the starting date itself is not counted among the advanced working days.
  • Only dates that are classified as working count. Weekend dates and holidays are skipped instead of being counted.
  • extra_working_days and extra_holidays influence which dates count under exactly the same rules and with the same precedence as in is_working_day:
    • an extra working date counts even when it is normally a weekend or holiday;
    • an extra holiday is skipped even when it is normally a working date; and
    • when a date is present in both iterables, the extra working designation wins.
  • Counting must keep working correctly across weekends, holidays, month boundaries, and year boundaries, with the applicable calendar rules and holidays applied to each date.
  • A datetime.date is returned.

This method supersedes the earlier add_workdays naming.

Examples of Required Behavior

Classification with the France calendar

For FranceCalendar, which uses Saturday/Sunday as its regular weekend and whose calendar includes French holidays:

from datetime import date
from workalendar.europe import FranceCalendar

cal = FranceCalendar()

cal.is_working_day(date(2013, 1, 1))  # False: holiday
cal.is_working_day(date(2013, 1, 5))  # False: Saturday
cal.is_working_day(date(2013, 1, 6))  # False: Sunday
cal.is_working_day(date(2013, 1, 7))  # True: Monday
Advancement with the France calendar

Taking October 30, 2013 as the start:

cal.add_working_days(date(2013, 10, 30), 0) == date(2013, 10, 30)
cal.add_working_days(date(2013, 10, 30), 1) == date(2013, 10, 31)
cal.add_working_days(date(2013, 10, 30), 2) == date(2013, 11, 4)
cal.add_working_days(date(2013, 10, 30), 3) == date(2013, 11, 5)

In this sequence, November 1 is a holiday while November 2–3 make up the weekend, so none of those dates count toward the delta.

Advancing across years

Consider a calendar configured with no weekend days, but with December 25 and January 1 as holidays:

cal.add_working_days(date(Y, 12, 20), 20) == date(Y + 1, 1, 11)

Counting begins on December 21 and crosses into the next year. In this example, the two skipped non-working dates are December 25 of year Y and January 1 of year Y + 1. This result does not describe a calendar that has no holidays.

Exceptions passed per call

With the same no-weekend calendar, where Christmas is normally a holiday:

christmas = date(Y, 12, 25)

cal.is_working_day(christmas) is False
cal.is_working_day(
    christmas,
    extra_working_days=[christmas],
) is True

For any date ordinary_day that would normally be working:

cal.is_working_day(ordinary_day) is True
cal.is_working_day(
    ordinary_day,
    extra_holidays=[ordinary_day],
) is False

Consistent Naming

Finish the nomenclature cleanup across the calendar classes:
