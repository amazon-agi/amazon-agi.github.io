Task Description

Overview

An Apache-style configuration loader already exists, and you must extend it such that it can load configuration files by name out of a configured base directory, and can accept path-related configuration options.

API Surface

A factory function that constructs a configuration loader is already present. Invoking it takes this form:

make_loader(**options)

What it returns is a context-manager object (something you can use in a with statement); that context manager yields a loader instance.

New requirements on the loader factory

A keyword option that make_loader must accept:

  • programpath (string): a path to a base directory; configuration files that a relative filename refers to are resolved against it.
New method of the loader instance

A method must be provided on the loader instance that the context manager yields:

loader.load(filename)

The method's behavior:

  • filename is a configuration file's name or a relative path to that file.
  • The file is resolved by the method relative to the directory given to make_loader as programpath.
  • The contents of the resolved file are read and then parsed as a configuration; the parsed configuration object is what the method returns.
  • Equality must hold between the parsed configuration object that is returned and the object you would get by reading the textual contents of that same file and parsing them directly (in other words, parsing a file's raw text and loading that file by name give the same result).

Constraints

  • Text-based parsing as it exists today (parsing a configuration string) must stay unchanged; the results yielded by loading by filename must be identical to those from parsing the file's text content directly.

Config File Loader — Options for Path Resolution and Directory Inclusion

Summary

The configuration loader in the existing Apache/Perl Config::General style is extended by this task so that it gains path-search and directory-loading behavior; the configpath, programpath, includerelative, configroot, and includedirectories options serve as the controls for that behavior. Compatibility must be preserved for the parsing syntax and configuration-generation behavior that already exist.

Public API

The loader module that already exists must keep exposing:

  • make_loader(**options), which produces a loader that can be used as a context manager:

    with make_loader(**options) as loader:
    config = loader.load(path)

  • load(path) must be exposed by the object that is yielded as loader.

  • ApacheConfigError, raised when a load cannot be resolved, as detailed below.

Importing make_loader and ApacheConfigError together from the module that already exposes the loader API must remain possible. There is no requirement for a new module location.

Path Resolution: General Rules

Out of the candidates that the applicable search order contains, load(path) must use the first one that exists. Candidate existence is determined by means of os.path.exists. load must raise ApacheConfigError if no candidate exists. Both a path handed directly to load and a path that shows up in an include directive while another configuration is being parsed fall under this rule.

An absolute path goes on identifying its absolute target. For every relative path, the complete path that the caller or the include directive supplied must be preserved. Specifically, a relative path with directory components in it must not be collapsed to its base name. As an illustration, resolving dir/sub/file.conf against root a must produce a/dir/sub/file.conf rather than a/file.conf.

Standard path joining with . is what produces the current-working-directory form of a relative candidate; for instance, the candidate belonging to dir/sub/file.conf is ./dir/sub/file.conf. Even when another search option — programpath included — is configured, multi-component relative paths must retain this current-directory fallback. As soon as an existing candidate has been found, the search stops.

Nested includes are governed by these same rules at every level. Consequently, even when a configuration is loaded through one search root, it can still include a complete working-directory-relative path such as dir/sub/file.conf.

configpath

A list of directory strings is what configpath holds. For a relative path, each configured directory is probed in list order by joining it with the complete relative path; after those probes comes the current-directory candidate.

For a bare name, the required ordering stays the same. With:

configpath = ['a', 'b']
path = 't.conf'

these are the candidates:

  1. a/t.conf
  2. b/t.conf
  3. ./t.conf

Take a multi-component relative path such as dir/t.conf: the corresponding candidates are a/dir/t.conf, b/dir/t.conf, and ./dir/t.conf, in that order.

Should none of them exist, raise ApacheConfigError.

programpath

The programpath option is a directory string. A bare filename is dealt with by joining the filename to programpath. By way of example:

programpath = 'a/b'
path = 't.conf'

this configuration requires the candidate a/b/t.conf. If that candidate does not exist, the bare-name load raises ApacheConfigError; the bare-name contract as it already exists does not require a ./t.conf fallback.

For a relative path with directory components, the complete path is to be retained, and the working-directory fallback is to be retained as well. Hence, with programpath='a/b', loading dir/t.conf permits a/b/dir/t.conf to be considered first and, if no earlier candidate resolves, must also permit ./dir/t.conf to resolve. For multi-component relative paths, configuring programpath must never remove this fallback.

includerelative and configroot

Suppose that includerelative=True and that configroot is a directory string: a relative path must then be probed beneath configroot. With a bare name:

includerelative = True
configroot = 'a'
path = 't.conf'

a/t.conf is the candidate that is required. When the path cannot be resolved, load raises ApacheConfigError.

The complete-path rule holds here too: dir/t.conf must be probed as a/dir/t.conf, and it must never be probed as a/t.conf. In addition, a multi-component path must remain resolvable by way of its current-working-directory candidate, as the general rules specify.

Multi-Component Paths: Combined Search Locations

Once options are combined, the precedence established for the configured roots stays in place: an enabled configroot location is considered before the directories in configpath, those directories keep the order in which they were supplied, and programpath is considered in its capacity as the configured program location. For a multi-component relative path, the current-working-directory candidate remains available after the configured locations whether or not programpath is present. The complete relative path must be contained in every candidate.

includedirectories

With includedirectories=True in effect, an existing resolved candidate may turn out to be a directory. os.path.isdir is what directory status is determined with, and os.listdir is what the entries are obtained with.

Loading a directory proceeds as follows:

  • Every entry that is enumerated is loaded with the same loader and the same path-resolution behavior. Entry paths are formed with the resolved directory as their base, so directory components are preserved.
  • Files are parsed in the normal way; this includes resolving any nested include directives through the same rules given above.
  • The parsed mappings from the entries are merged into one resulting configuration dictionary.
  • Return {} for an existing directory that has no entries.
  • Loading a directory that contains valid configuration files must succeed and yield a non-empty/truthy dictionary when those files contribute configuration values.

If an enumerated entry is itself loadable as a directory, the same includedirectories behavior takes effect for it as well. Failures of an entry or of a nested include are not silently ignored; normal load errors propagate.

Return Values and Error Behavior
  • A load(path) that succeeds returns the parsed configuration in the form of a plain dict.
  • An empty directory that is loaded successfully with includedirectories=True returns exactly {}.
  • Raise ApacheConfigError when all applicable candidates are absent according to os.path.exists.
  • This unresolved-path behavior covers top-level loads and includes equally.
  • Path construction must be carried out with standard path joining. For directories, recognition and enumeration are done with os.path.isdir and os.listdir, respectively.
Compatibility Notes and Non-Goals

Path discovery is what this task changes, and directory expansion is something it optionally permits. In every other respect, it must not change existing configuration syntax, include syntax, parsing results, duplicate-handling options, or the loader's context-manager usage.

Task Specification: Adding Glob Support for Config File Includes

Overview

This project reads in and parses configuration files of the Apache/Perl Config::General style. A configuration may bring in another file or directory by way of a directive of the form:

<<include PATH>>

The task is to implement include resolution, directory inclusion, and optional shell-style glob expansion, while the loader's existing parsing and merging behavior is preserved.

Public API

The factory function make_loader(**options) returns a loader that can be used as a context manager:

with make_loader(**options) as loader:
    config = loader.load(filepath)

The loader exposes the following:

  • loader.load(filepath): loads and parses the configuration of the file located at the given filesystem path.
  • loader.loads(text): loads and parses configuration from a string held in memory.

In both cases, the parsed configuration is returned as a nested dict. The parsing and include-resolution failures described below must raise the existing ApacheConfigError exception.

make_loader continues to accept the keyword options it already has, including configpath, programpath, includerelative, configroot, and includedirectories, and must additionally accept includeglob.

Behavior Requirements

1. Resolving includes from both loader entry points

Each time an <<include PATH>> directive is encountered, the configuration it references must be resolved, parsed, and merged at the location of the directive. This holds regardless of whether parsing started from load() or loads(). In particular, loads() must not handle includes as if they were inert text: an include present in an in-memory string undergoes normal filesystem resolution and fails in the normal way if it cannot be resolved.

Which candidate paths get probed for existence is determined by the path-related options:

  • With configpath=['a', 'b'], an include target t.conf is probed as a/t.conf, then b/t.conf, then ./t.conf.
  • With programpath='a/b', an include target t.conf is probed as a/b/t.conf.
  • With includerelative=True and configroot='a', an include target t.conf is probed relative to that root, as a/t.conf.

The order given above must be preserved. If none of the applicable candidates exists or otherwise resolves to an includable target, the load must raise ApacheConfigError.

2. Includes of directories

When includedirectories=True and an include target resolves to a directory, the applicable files in that directory must be loaded and their parsed contents merged at the include location. Entries of the directory that are themselves directories must be skipped; only files are loaded.

An included directory that is empty is valid and contributes no settings. So, when there is no other configuration content, loading an include whose directory is empty produces {} for that include.

This behavior covers directives encountered through either load() or loads(), including directives that are nested in included files or blocks.

When includedirectories is false or omitted and an include target resolves to a directory that exists, loading must fail with ApacheConfigError. It must neither accept the directory silently nor expose a filesystem-specific directory-open exception such as IsADirectoryError.

3. Includes with glob patterns

The includeglob option is to be added. When includeglob=True, an include target must be treated as a shell-style glob pattern. Every file that matches the resolved pattern must be loaded, parsed, and merged. For example, a target ending in includes/*.conf includes all the .conf files in that directory that match.

When includeglob is false or omitted, wildcard characters are not expanded. A target like that is resolved as an ordinary literal include path and, if it cannot be found, raises ApacheConfigError under the normal unresolved-include rule.

4. Merging and nesting of includes

Key/value pairs and blocks that come from includes are merged into the configuration at the point where the directive appears. It is possible for includes to be nested: a loaded file may include further files. An include placed inside a block contributes its content to that block's scope rather than to the top-level scope.

As an example, suppose the first configuration contains:

seen_first_config = true
<<include .../includes/second-test.conf>>

while second-test.conf contains:

seen_second_config = true
<inner>
  <<include .../includes/third-test.conf>>
</inner>

If third-test.conf supplies final_include = true and seen_third_config = true, then loading the first configuration must produce:

{
    'seen_first_config': 'true',
    'seen_second_config': 'true',
    'inner': {
        'final_include': 'true',
        'seen_third_config': 'true',
    },
}

Directly loading second-test.conf must produce:

{
    'seen_second_config': 'true',
    'inner': {
        'final_include': 'true',
        'seen_third_config': 'true',
    },
}

Directly loading third-test.conf must produce:

{
    'final_include': 'true',
    'seen_third_config': 'true',
}

Handling of Paths

  • load(filepath) accepts an absolute path, or a path relative to the current working directory, to the actual file being parsed; callers are not restricted to passing a bare filename that is then resolved through option-provided search paths.
  • In these scenarios, include paths inside loaded configurations use paths that are relative to the current working directory, subject to the include-resolution options as configured.
  • Files discovered via directory or glob expansion are parsed with the same loader behavior as directly included files, so nested includes and normal merging continue to apply.

Return Values and Preservation of Values

  • Loads that succeed return nested Python dictionaries.
  • The content of string values must be preserved exactly, including trailing or embedded whitespace and characters that are not comments in their context.
  • A configuration that loads successfully and contains any data must be truthy.
  • An empty directory include that succeeds contributes an empty dictionary/no settings, as described above.

Task: Add a flagbits Option for Configuration Parsing

Overview

Your work happens inside a library whose purpose is loading configuration files. What you must add is support for a new option called flagbits, which changes the way certain configuration values are interpreted. Whenever a directive is designated a "flagbits" directive, parsing treats its value string as a set of flags whose separator is the pipe character (|), and the outcome of the expansion is a dictionary that maps each known flag name to a value.

Public API

Exposed by the library are the following factory functions and class, and all of them must accept the flagbits option as a keyword argument (in addition to any options they already accept):

  • make_lexer(**options) — the return value is a lexer class.
  • make_parser(**options) — the return value is a parser class.
  • ApacheConfigLoader(parser_instance, **options) — the loader class. Its construction receives a parser instance plus the same options. As for the parser instance, it is created via make_parser(**options)(make_lexer(**options)()).

A method the loader exposes is:

  • loads(text) — the configuration text string handed to it is parsed, and the resulting configuration is returned as a dictionary.

These components already exist and support other options; what your task comes down to is making them honor the new flagbits option.

The flagbits Option

If it is supplied, the flagbits option takes the form of a dictionary with this shape:

{
    'flagbits': {
        '<directive_name>': {
            '<flag_name>': <flag_value>,
            ...
        },
        ...
    }
}
  • The top-level keys under flagbits give the names of directives that should be treated as flagbits directives.
  • Each such directive comes with a dictionary belonging to it that maps flag names to arbitrary values (the values may be integers, strings, or any other type — verbatim use is made of them).

Required Behavior

Suppose a directive is being parsed and its name appears as a key in the flagbits option: that directive's value must then be treated as a list of flag names separated by |. The value string gets split at the | character, and each resulting flag name has its surrounding whitespace stripped.

For that directive, the resulting value must be a dictionary, and its construction follows the directive's declared flag map:

  • An entry exists in the dictionary for every flag name declared for that directive in the option's flag map (not merely the ones occurring in the input value).
  • For each declared flag name that is present in the parsed value's flag list, the entry's value is the one the option's flag map declares for that flag name.
  • For each declared flag name that is not present in the parsed value's flag list, None is the value that results.
Example

Take the option

{
    'flagbits': {
        'mode': {
            'CLEAR': 1,
            'STRONG': 1,
            'UNSECURE': '32bit'
        }
    }
}

together with the configuration text

mode = CLEAR | UNSECURE

What parsing must produce is the following configuration:

{
    'mode': {
        'CLEAR': 1,
        'STRONG': None,
        'UNSECURE': '32bit'
    }
}

CLEAR and UNSECURE are present in the input, so the values they receive are their declared ones (1 and '32bit'). STRONG is declared as well, but the input does not contain it; its value is therefore None.

Scope

A directive is affected only when the flagbits option names it. All other parsing behavior is left untouched.

Summary

Introduce a new configuration loader option called defaultconfig that provides default option values, which are merged with the values parsed from a configuration text.

Public API

The components involved are built and used in this way:

  • make_lexer(**options) — a factory that returns a lexer class (already present; must accept and tolerate the new option).
  • make_parser(**options) — a factory that returns a parser class (already present; must accept and tolerate the new option).
  • ApacheConfigLoader(parser_instance, **options) — a loader class (already present; must accept and tolerate the new option). It exposes a loads(text) method that parses the supplied text and returns the resulting configuration as a Python dict.

The same **options dictionary is received by all three (make_lexer, make_parser, ApacheConfigLoader).

Behavior Requirements

Option defaultconfig

options['defaultconfig'] is a dict that maps option names (strings) to their default values (strings). These defaults serve as a baseline configuration onto which the parsed configuration text is merged.

When loads(text) is invoked, the dict it returns must contain:

  1. Every key from defaultconfig together with its default value, unless it is overridden or extended by parsed values as described below.
  2. Every key that is parsed from the text.
Semantics of the merge

The merge brings together defaultconfig and the parsed result:

  • A key found only in defaultconfig (and not in the parsed text) shows up in the result with its default value.
  • A key found only in the parsed text (and not in defaultconfig) shows up in the result with its parsed value.
  • A key present in both defaultconfig and the parsed text must have both values combined into a list, with the default value first, followed by the parsed value.

This merging operates together with the existing mergeduplicateoptions option, which is set to True in the scenario that this task must satisfy.

Worked example

For the configuration text:

a = 1
b = 2

together with options:

{
    'defaultconfig': {
        'b': '4',
        'c': '3'
    },
    'mergeduplicateoptions': True
}

the call loads(text) must return:

{
    'a': '1',
    'b': ['4', '2'],
    'c': '3'
}

Explanation:

  • a is found only in the parsed text → value '1'.
  • b is present in both defaultconfig ('4') and the parsed text ('2') → the two values are combined into a list ['4', '2'] (default first, parsed second).
  • c is found only in defaultconfig → value '3'.

Constraints

  • When defaultconfig is not provided, all existing loader behavior must remain unchanged.
  • make_lexer, make_parser, and ApacheConfigLoader must accept the defaultconfig option, along with all other options, without error.

Task: Adding Variable Interpolation to an Apache Config Loader

Summary

The task here is to give an Apache-style configuration loader support for variable interpolation. Once an option enables the feature, references that configuration values make to variables are resolved to the values defined for them previously.

Public API

The callables listed below must be present in the loader module and importable from it (this being the module that currently provides the loader machinery):

  • make_lexer(**options) — its return value is a lexer class whose configuration comes from options.
  • make_parser(**options) — its return value is a parser class whose configuration comes from options.
  • ApacheConfigLoader(parser_instance, **options) — a loader class. The constructor accepts a parser instance together with keyword options, where that instance is constructed from the parser class, which is in turn instantiated with a lexer instance.

The instantiation pattern below must be supported:

LexerClass = make_lexer(**options)
ParserClass = make_parser(**options)
loader = ApacheConfigLoader(ParserClass(LexerClass()), **options)
config = loader.loads(text)

Given a configuration string, ApacheConfigLoader.loads(text) parses it and returns the configuration as a Python dict.

Option

  • interpolatevars (bool): a value of True turns variable interpolation on while loading. The option is passed to make_lexer, make_parser, and ApacheConfigLoader in identical fashion.

Configuration Syntax (as exercised)

These are the constructs the loader must handle when they occur in the input text:

  • Assignment using =: name = value
  • Assignment via whitespace: name value (no =)
  • Quoted values: strings wrapped in double quotes ("...") or single quotes ('...'). Surrounding quotes are stripped off the value that gets stored.
  • Blocks: <name> ... </name> — such a pair gives a nested dict with the block name as its key.

Every scalar value is stored as a string.

Behavior of Variable Interpolation (when interpolatevars is True)

Inside a value, a previously defined variable may be referenced through either of these forms:

  • $name
  • ${name}

Once a reference of this kind shows up, the value that name is currently bound to takes its place.

The following rules are exercised:

  1. Bare reference ($a or ${b}): what gets substituted is the entire referenced value. For instance, given a = 1, b = $a yields b == "1"; given b == "1", c = ${b} yields c == "1".

  2. Reference within a double-quoted value: interpolation takes place inside the string, and the substituted text is spliced into the literal text surrounding it. For instance, when e == "1", the value "${e} + 2" yields "1 + 2".

  3. Reference within a single-quoted value: interpolation does not take place — single-quoted values are treated as literal text. For instance, '${e}' yields the literal string "${e}".

  4. Scope / resolution order: a reference is resolved against variables that were defined earlier — including ones defined at an outer scope relative to a nested block. Within a block, precedence belongs to a variable defined inside that block. As a concrete case: with a top-level c and a block <aa> that defines d = ${c} and e = 2, d resolves to the value of the outer c, whereas f "${e} + 2" inside the block resolves e to the block-local e ("2"), yielding "2 + 2".

Worked Example

The input:

a = 1
b = $a
c = ${b}
e 1
<aa>
  d = ${c}
  e = 2
  f "${e} + 2"
  g = '${e}'
</aa>

Running with interpolatevars = True gives the following dict:

{
    'a': '1',
    'b': '1',
    'c': '1',
    'e': '1',
    'aa': {
        'd': '1',
        'e': '2',
        'f': '2 + 2',
        'g': '${e}',
    },
}

Notes

  • In the result, every value is a string.
  • The contents of a block are represented as a nested dict sitting under that block's name.
  • Resolution of references is controlled by the interpolatevars option; the behavior above is required only for the enabled case, as exercised here.

Interpolating Environment Variables Within the Apache Config Loader

Through the new boolean option interpolateenv, Apache-style configuration values gain opt-in interpolation from environment variables. Configuration-variable interpolation, quoting rules, parsing behavior, and compatibility with all existing options must all stay intact.

Public API

Each of the names below must remain directly importable from apacheconfig; importing them via from apacheconfig import * must work as well:

  • make_lexer(**options)
  • make_parser(**options)
  • ApacheConfigLoader(parser, **options)

Both make_lexer(**options) and make_parser(**options) are factories that produce classes rather than instances:

  • Calling make_lexer(**options) returns a lexer class that is instantiable; that class can be instantiated with no required arguments.
  • Calling make_parser(**options) returns a parser class that is instantiable; that class can be instantiated with a lexer instance.
  • The parser instance that results is accepted by ApacheConfigLoader(parser, **options), which exposes loads(text); a call to loads(text) parses a configuration string and returns the nested configuration dict.

The standard construction shown next must therefore work:

options = {'interpolateenv': True}

ApacheConfigLexer = make_lexer(**options)
ApacheConfigParser = make_parser(**options)
parser = ApacheConfigParser(ApacheConfigLexer())
loader = ApacheConfigLoader(parser, **options)
config = loader.loads(text)

Callers may instead build the parser as make_parser(**options)(make_lexer(**options)()) — this is equivalent. The factory results must not be swapped for already-instantiated lexer or parser objects.

The interpolateenv keyword option must be accepted by each of make_lexer, make_parser, and ApacheConfigLoader, on top of all the options each already supports. Options and construction patterns that exist already must keep behaving as before.

How Interpolation Behaves

Supplying interpolateenv=True while the lexer, parser, and loader are being constructed lets values support both of these reference forms:

  • $name
  • ${name}

Switching interpolateenv on activates the environment fallback and, alongside it, configuration-variable resolution; there is no need for callers to enable interpolatevars separately to obtain this behavior.

Order of Resolution

Each reference has its name resolved by walking the steps below in order:

  1. Check first for a configuration key named name that is visible. A key is visible when it was defined earlier within the same block, and a key from an enclosing block is visible as well. Between such keys, the nearer block-local key takes precedence over the enclosing one.
  2. The second step runs only if no visible configuration key resolves the name: the name is then looked up in the process environment (os.environ), and when the variable is present, the reference is replaced with that environment variable's string value.

As a result, configuration values always take precedence over environment variables carrying the same name. References can be chained through configuration values defined previously, and a configuration value resolved from the environment is available to subsequent references in the same way as the other configuration values.

Consulting the environment is strictly opt-in. Leave interpolateenv out or set it to false, and no reference may be resolved from the process environment. Config-only interpolation that already exists — the kind interpolatevars enables — must remain unchanged. Otherwise, how references that cannot be resolved through an enabled source are handled must remain compatible with the existing interpolation behavior.

Rules for Quoting

The quoting behavior already in place governs configuration interpolation and environment interpolation alike:

  • References in a value with no quotes are interpolated.
  • References in a value wrapped in double quotes ("...") are interpolated.
  • References in a value wrapped in single quotes ('...') are not interpolated. The reference text stays literal inside the parsed value; the outer quotes are syntactic and are not part of that value.

Worked Example

Assume a process environment that contains a=1. Load the text below with interpolateenv=True supplied, in the manner shown by the public construction above:

b = $a
c = ${b}
e 1
<aa>
  d = ${c}
  e = 2
  f "${e} + 2"
  g = '${e}'
</aa>

This must be the result:

{

Overview

Escape processing (the default behavior, when noescape is absent or False)

Objective

Extend the Apache-style configuration parser and loader so that block tags can contain multiple whitespace-separated components and quoted components. Existing single-component blocks, as well as the existing public API, must remain compatible.

Public API

The API surface that follows must remain available:

  • make_lexer() returns the ApacheConfigLexer class.
  • make_parser() returns the ApacheConfigParser class.
  • ApacheConfigLexer() creates a lexer instance.
  • ApacheConfigParser(lexer) builds a parser from a lexer instance and exposes parse(text), which returns the nested-list AST described below.
  • ApacheConfigLoader(parser) builds a loader from a parser instance and exposes loads(text), which returns the parsed configuration as a Python dict.

Block syntax

A block begins with an opening tag <...> and ends with a corresponding closing tag </...>. A name-only block may instead be self-closing, written as <name/>.

Tag components

An opening tag's payload is made up of one or more components separated by whitespace:

  • The block name is the first decoded component.
  • The block's trailing value is formed by all remaining decoded components.
  • When more than one trailing component is present, the loader joins those components with a single space.

So, <a b> has block name a and trailing value b, whereas <a b c> has block name a and trailing value b c.

Closing tags

It is not required for a closing tag to repeat the opening tag's trailing components. For a block opened with a multi-component tag, both of the following closing forms must be accepted:

  • a closing tag that repeats the complete opening payload, such as <a b c>...</a b c>; and
  • a name-only closing tag that contains only the opening tag's first component, such as <a b c>...</a>.

A name-only close does not throw away the opening tag's trailing components: the block's semantics are derived solely from the opening-tag payload, so <officer randall>...</officer> still carries the block name officer and the trailing value randall. The parser and loader must not reject or alter such documents by enforcing that the closing-tag component list match the opening-tag component list.

This holds regardless of how many trailing components the opening tag has: <a block>...</a> (one trailing component) and <a a block>...</a> (two trailing components) must both parse and load successfully.

Quoting

Any component may be wrapped in matching double quotes ("...") or single quotes ('...'). Whitespace inside a quoted component belongs to that one component rather than acting as a separator. When the semantic component value is derived, the surrounding quote characters are removed, while the text and spaces inside the quotes are retained literally.

As a result:

  • <"a b"> contains one component, and its block name is a b.
  • <'d e'> contains one component, and its block name is d e.
  • <g 'h i'> contains two components: the block name g and the trailing value h i.
  • <a b c> and <a 'b c'> both produce the trailing loader key b c, even though their component boundaries differ.

Quoted components must work in both opening and closing tags. A closing tag repeating the opening payload must decode to the same ordered component list as the opening tag; for instance, </"a b"> may close a block opened with <"a b">, and </g 'h i'> may close one opened with <g 'h i'>.

Whitespace and self-closing blocks

Whitespace that separates unquoted components is syntactic; when multiple trailing components are joined for loader output, it is normalized to a single space. Whitespace that is enclosed by quotes stays literal.

A self-closing tag consists of exactly one component. Whitespace immediately before /> is insignificant, so forms such as <name/> and <name /> stand for the same empty block. When the sole name component itself contains spaces, quoting may be used.

Parser AST

The parser works with nested Python lists. A block node keeps its existing four-element shape:

['block', <opening_tag>, <body>, <closing_tag>]

The fields carry the following meanings:

  • <opening_tag> is the complete opening-tag payload once the surrounding delimiters and insignificant leading or trailing whitespace have been removed. Every component, their order, the text separating components, and the quote delimiters that identify quoted components must be preserved by it. It is not restricted to the first decoded component.
  • <body> is the parsed list of the contents inside the block, or [] in the case of an empty or self-closing block.
  • <closing_tag> is the complete, correspondingly stripped closing-tag payload in the form it appeared in the source. When the document uses a name-only closing tag, this field holds only the block name, even though <opening_tag> keeps the trailing components. In the case of a self-closing block, it is the same value as <opening_tag>.

It is required to retain the complete payload and quote boundaries, because these inputs have different semantics:

<a b></a b>          # name `a`, trailing value `b`
<"a b"></"a b">      # one name component, `a b`

The block nodes for these inputs are respectively:

['block', 'a b', [], 'a b']
['block', '"a b"', [], '"a b"']

Similarly, an empty <a b c>...</a b c> block keeps a b c in both tag fields, and <g 'h i'>...</g 'h i'> keeps g 'h i'. An empty block opened as <a b> but closed as </a> gives ['block', 'a b', [], 'a']. The full opening-tag payload is then decoded by the loader into its semantic components.

At the contents level, nodes stay wrapped by ['contents', ...]. For example:

<a/>
<b/>

yields:

['contents', ['block', 'a', [], 'a'], ['block', 'b', [], 'b']]

Block nodes that are single-component and unquoted therefore keep their previous representation.

Loader dictionary semantics

The loader must interpret the complete opening-tag payload according to the component and quoting rules above. The quote delimiters that the AST retains are not included in dictionary keys. Dictionary keys are derived solely from the opening-tag payload; whether the block was closed by a full-payload closing tag or by a name-only closing tag makes no difference to loader output.

Let name denote the first decoded component of the opening tag, value denote all remaining decoded components joined with one space, and contents denote the dictionary loaded from the block body:

  • A tag with one component produces {name: contents}.
  • A tag that has trailing components produces {name: {value: contents}}.
  • For an empty block, the contents dictionary is empty.
Single-component tags
<name>
  key = 1
</name>

yields:

{'name': {'key': '1'}}
Multi-component named tags
<name value>
  key = 1
</name value>

yields:

{'name': {'value': {'key': '1'}}}

With multiple trailing components:

<a b c>
  d = 1
</a b c>

yields:

{'a': {'b c': {'d': '1'}}}
Name-only closing tags

Since loader keys come only from the opening tag, a multi-component block closed with a name-only tag loads the same way as one closed with the full payload:

<officer randall>
  age = 25
</officer>

yields:

{'officer': {'randall': {'age': '25'}}}

This also holds when the opening tag has several trailing components; for example, a block opened as <a a block> and closed as </a> has block name a and trailing value a block, so its contents load under {'a': {'a block': ...}}.

Repeated block names

When the same block name appears more than once with different trailing values, its block values are collected into a list in source order. For example:

<a b>
c = 1
</a b>

<a b c>
d = 1
</a b c>

yields:

{'a': [{'b': {'c': '1'}}, {'b c': {'d': '1'}}]}

The trailing value of the first block is b; the trailing value of the second block is b c. Both share the block name a, so their nested dictionaries become entries of the list under a.

This collection behavior applies equally when the blocks are closed by name-only tags:

<officer randall>
  name = stein
</officer>
<officer gordon>
  name = bird
</officer>

yields:

{'officer': [{'randall': {'name': 'stein'}}, {'gordon': {'name': 'bird'}}]}
Quoted tags

During semantic decoding, quotes are removed, and quoted whitespace stays in the resulting key. For example:

<"a b">
c = 1
</"a b">

<'d e'>
f = 1
</'d e'>

<g 'h i'>
j = 1
</g 'h i'>

yields:

{
    'a b': {'c': '1'},
    'd e': {'f': '1'},
    'g': {'h i': {'j': '1'}}
}

Each of the first two tags contains one quoted name component. The third contains the name g together with one quoted trailing component whose value is h i.

Values inside blocks

Ordinary assignments inside any block keep their existing behavior. In particular, key = value contributes a string-valued entry to that block's contents, such as {'key': 'value'}. This behavior composes normally with single-component, multi-component, quoted, nested, empty, and repeated blocks, as well as with blocks closed by name-only closing tags.
