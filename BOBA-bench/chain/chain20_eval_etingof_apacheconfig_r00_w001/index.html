Config File Loader — Path Resolution and Directory Inclusion Options

Overview

Extend the existing Apache/Perl Config::General-style configuration loader with path-search and directory-loading behavior controlled by the configpath, programpath, includerelative, configroot, and includedirectories options. Existing parsing syntax and configuration-generation behavior must remain compatible.

Public API

The existing loader module must continue to expose:

  • make_loader(**options), producing a loader that can be used as a context manager:

    with make_loader(**options) as loader:
    config = loader.load(path)

  • The object yielded as loader must expose load(path).

  • ApacheConfigError, raised for unresolved loads as described below.

make_loader and ApacheConfigError must remain importable together from the module that already exposes the loader API. No new module location is required.

General Path-Resolution Rules

load(path) must use the first existing candidate in the applicable search order. Candidate existence is determined with os.path.exists. If no candidate exists, load must raise ApacheConfigError. This applies both to a path passed directly to load and to a path encountered in an include directive while parsing another configuration.

Absolute paths continue to identify their absolute target. For every relative path, preserve the complete path supplied by the caller or include directive. In particular, a relative path containing directory components must not be reduced to its base name. For example, resolving dir/sub/file.conf against root a must produce a/dir/sub/file.conf, not a/file.conf.

The current-working-directory form of a relative candidate is produced by standard path joining with .; for example, dir/sub/file.conf has the candidate ./dir/sub/file.conf. Multi-component relative paths must retain this current-directory fallback even when another search option, including programpath, is configured. Search stops as soon as an existing candidate is found.

Nested includes use these same rules at every level. Therefore, a configuration loaded through one search root can still include a complete working-directory-relative path such as dir/sub/file.conf.

configpath

configpath is a list of directory strings. For a relative path, probe each configured directory in list order by joining it with the complete relative path, followed by the current-directory candidate.

For a bare name, the required order is unchanged. With:

configpath = ['a', 'b']
path = 't.conf'

the candidates are:

  1. a/t.conf
  2. b/t.conf
  3. ./t.conf

For a multi-component relative path such as dir/t.conf, the corresponding candidates are a/dir/t.conf, b/dir/t.conf, and ./dir/t.conf, in that order.

If none exists, raise ApacheConfigError.

programpath

programpath is a directory string. For a bare filename, join the filename to programpath. For example:

programpath = 'a/b'
path = 't.conf'

requires the candidate a/b/t.conf. If that candidate does not exist, the bare-name load raises ApacheConfigError; the existing bare-name contract does not require a ./t.conf fallback.

For a relative path containing directory components, retain the complete path and also retain the working-directory fallback. Thus, with programpath='a/b', loading dir/t.conf first permits a/b/dir/t.conf to be considered and, if no earlier candidate resolves, must also permit ./dir/t.conf to resolve. Configuring programpath must never remove this fallback for multi-component relative paths.

includerelative and configroot

When includerelative=True and configroot is a directory string, a relative path must be probed under configroot. For a bare name:

includerelative = True
configroot = 'a'
path = 't.conf'

the required candidate is a/t.conf. If the path cannot be resolved, load raises ApacheConfigError.

The complete-path rule also applies here: dir/t.conf must be probed as a/dir/t.conf, never as a/t.conf. A multi-component path must additionally remain resolvable through its current-working-directory candidate, as specified by the general rules.

Combined Search Locations for Multi-Component Paths

When options are combined, configured roots retain their established precedence: an enabled configroot location is considered before the directories in configpath, those directories retain their supplied order, and programpath is considered as its configured program location. For a multi-component relative path, the current-working-directory candidate remains available after the configured locations regardless of whether programpath is present. Every candidate must contain the complete relative path.

includedirectories

When includedirectories=True, an existing resolved candidate may be a directory. Directory status is determined with os.path.isdir, and entries are obtained with os.listdir.

For a directory load:

  • Load every enumerated entry using the same loader and path-resolution behavior. Entry paths are formed relative to the resolved directory, so directory components are preserved.
  • Parse files normally, including resolving any nested include directives through the same rules described above.
  • Merge the parsed mappings from the entries into one resulting configuration dictionary.
  • Return {} when the existing directory has no entries.
  • Loading a directory containing valid configuration files must succeed and yield a non-empty/truthy dictionary when those files contribute configuration values.

If an enumerated entry is itself loadable as a directory, the same includedirectories behavior applies. Entry or nested-include failures are not silently ignored; normal load errors propagate.

Return Values and Errors
  • A successful load(path) returns the parsed configuration as a plain dict.
  • A successfully loaded empty directory with includedirectories=True returns exactly {}.
  • If all applicable candidates are absent according to os.path.exists, raise ApacheConfigError.
  • This unresolved-path behavior applies equally to top-level loads and includes.
  • Path construction must use standard path joining. Directory recognition and enumeration use os.path.isdir and os.listdir, respectively.
Compatibility and Non-Goals

This task changes path discovery and optionally permits directory expansion. It must not otherwise change existing configuration syntax, include syntax, parsing results, duplicate-handling options, or the loader's context-manager usage.

Task Specification: Implement Glob Support for Config File Includes

Overview

This project loads and parses Apache/Perl Config::General-style configuration files. A configuration may include another file or directory through a directive of the form:

<<include PATH>>

Implement include resolution, directory inclusion, and optional shell-style glob expansion while preserving the loader's existing parsing and merging behavior.

Public API Surface

The factory function make_loader(**options) returns a loader usable as a context manager:

with make_loader(**options) as loader:
    config = loader.load(filepath)

The loader exposes:

  • loader.load(filepath): load and parse configuration from a file at the supplied filesystem path.
  • loader.loads(text): load and parse configuration from an in-memory string.

Both methods return the parsed configuration as a nested dict. Parsing and include-resolution failures described below must raise the existing ApacheConfigError exception.

make_loader continues to accept its existing keyword options, including configpath, programpath, includerelative, configroot, and includedirectories, and must additionally accept includeglob.

Required Behavior

1. Include resolution from both loader entry points

Whenever an <<include PATH>> directive is encountered, the referenced configuration must be resolved, parsed, and merged at the directive's location. This applies whether parsing began with load() or loads(). In particular, loads() must not treat includes as inert text: an include in an in-memory string performs normal filesystem resolution and fails normally if it cannot be resolved.

The path-related options determine which candidate paths are probed for existence:

  • With configpath=['a', 'b'], an include target t.conf probes a/t.conf, then b/t.conf, then ./t.conf.
  • With programpath='a/b', an include target t.conf probes a/b/t.conf.
  • With includerelative=True and configroot='a', an include target t.conf is probed relative to that root as a/t.conf.

The stated order must be preserved. If none of the applicable candidates exists or otherwise resolves to an includable target, loading must raise ApacheConfigError.

2. Directory includes

When includedirectories=True and an include target resolves to a directory, load the applicable files in that directory and merge their parsed contents at the include location. Directory entries that are themselves directories must be skipped; only files are loaded.

An empty included directory is valid and contributes no settings. Thus, loading an include whose directory is empty produces {} for that include when there is no other configuration content.

This behavior applies to directives encountered through either load() or loads(), including directives nested in included files or blocks.

When includedirectories is false or omitted and an include target resolves to an existing directory, loading must fail with ApacheConfigError. It must neither silently accept the directory nor expose a filesystem-specific directory-open exception such as IsADirectoryError.

3. Glob includes

Add the includeglob option. When includeglob=True, treat an include target as a shell-style glob pattern. Every file matching the resolved pattern must be loaded, parsed, and merged. For example, a target ending in includes/*.conf includes all matching .conf files in that directory.

When includeglob is false or omitted, wildcard characters are not expanded. Such a target is resolved as an ordinary literal include path and, if it cannot be found, raises ApacheConfigError under the normal unresolved-include rule.

4. Include merging and nesting

Included key/value pairs and blocks are merged into the configuration at the point where the directive appears. Includes can be nested: a loaded file may include further files. An include inside a block contributes its content to that block's scope rather than to the top-level scope.

For example, suppose the first configuration contains:

seen_first_config = true
<<include .../includes/second-test.conf>>

and second-test.conf contains:

seen_second_config = true
<inner>
  <<include .../includes/third-test.conf>>
</inner>

If third-test.conf supplies final_include = true and seen_third_config = true, loading the first configuration must produce:

{
    'seen_first_config': 'true',
    'seen_second_config': 'true',
    'inner': {
        'final_include': 'true',
        'seen_third_config': 'true',
    },
}

Loading second-test.conf directly must produce:

{
    'seen_second_config': 'true',
    'inner': {
        'final_include': 'true',
        'seen_third_config': 'true',
    },
}

Loading third-test.conf directly must produce:

{
    'final_include': 'true',
    'seen_third_config': 'true',
}

Path Handling

  • load(filepath) accepts an absolute path or a path relative to the current working directory to the actual file being parsed; callers are not restricted to passing a bare filename for resolution through option-provided search paths.
  • Include paths within loaded configurations use current-working-directory-relative paths in these scenarios, subject to the configured include-resolution options.
  • Files discovered through directory or glob expansion are parsed through the same loader behavior as directly included files, so nested includes and normal merging continue to apply.

Return Values and Value Preservation

  • Successful loads return nested Python dictionaries.
  • String values must preserve their content exactly, including trailing or embedded whitespace and characters that are not comments in their context.
  • A successfully loaded configuration containing any data must be truthy.
  • A successful empty directory include contributes an empty dictionary/no settings, as described above.

Overview

You are working on a configuration file loader library. You must add support for a new option named flagbits that changes how certain configuration values are interpreted. When a directive is designated as a "flagbits" directive, its value string is parsed as a set of flags separated by the pipe character (|), and the result is expanded into a dictionary that maps each known flag name to a value.

Public API

The library exposes the following factory functions and class, which must all accept the flagbits option as a keyword argument (in addition to any options they already accept):

  • make_lexer(**options) — returns a lexer class.
  • make_parser(**options) — returns a parser class.
  • ApacheConfigLoader(parser_instance, **options) — the loader class. It is constructed with a parser instance and the same options. The parser instance is created as make_parser(**options)(make_lexer(**options)()).

The loader exposes a method:

  • loads(text) — parses the given configuration text string and returns the resulting configuration as a dictionary.

These already exist for other options; your task is to make them honor the new flagbits option.

The flagbits Option

The flagbits option, when supplied, is a dictionary of this shape:

{
    'flagbits': {
        '<directive_name>': {
            '<flag_name>': <flag_value>,
            ...
        },
        ...
    }
}
  • The top-level keys under flagbits are directive names that should be treated as flagbits directives.
  • For each such directive, the associated dictionary maps flag names to arbitrary values (the values may be integers, strings, or any other type — they are used verbatim).

Required Behavior

When parsing a directive whose name appears as a key in the flagbits option, the directive's value must be treated as a |-separated list of flag names. The value string is split on the | character, and each resulting flag name is stripped of surrounding whitespace.

The resulting value for that directive must be a dictionary built from the directive's declared flag map, as follows:

  • The dictionary contains an entry for every flag name declared in the option's flag map for that directive (not just the ones present in the input value).
  • For each declared flag name that is present in the parsed value's flag list, the value is the value declared for that flag name in the option's flag map.
  • For each declared flag name that is not present in the parsed value's flag list, the value is None.
Example

Given the option:

{
    'flagbits': {
        'mode': {
            'CLEAR': 1,
            'STRONG': 1,
            'UNSECURE': '32bit'
        }
    }
}

and the configuration text:

mode = CLEAR | UNSECURE

the parsed configuration must be:

{
    'mode': {
        'CLEAR': 1,
        'STRONG': None,
        'UNSECURE': '32bit'
    }
}

Here CLEAR and UNSECURE appear in the input, so they take their declared values (1 and '32bit'). STRONG is declared but absent from the input, so its value is None.

Scope

Only directives named in the flagbits option are affected. All other parsing behavior remains unchanged.

Given the configuration text:

Task: Implement Variable Interpolation in Apache Config Loader

Overview

Add support for variable interpolation to an Apache-style configuration loader. When enabled via an option, variable references within configuration values are resolved to previously-defined values.

Public API

The following callables must exist and be importable from the loader module (the same module currently providing the loader machinery):

  • make_lexer(**options) — returns a lexer class configured according to options.
  • make_parser(**options) — returns a parser class configured according to options.
  • ApacheConfigLoader(parser_instance, **options) — a loader class. Its constructor accepts a parser instance (constructed from the parser class, which itself is instantiated with a lexer instance) plus keyword options.

Instantiation pattern that must be supported:

LexerClass = make_lexer(**options)
ParserClass = make_parser(**options)
loader = ApacheConfigLoader(ParserClass(LexerClass()), **options)
config = loader.loads(text)

ApacheConfigLoader.loads(text) parses a configuration string and returns a Python dict representing the configuration.

Option

  • interpolatevars (bool): When True, enable variable interpolation during loading. This option is passed identically to make_lexer, make_parser, and ApacheConfigLoader.

Configuration Syntax (as exercised)

The loader must handle these constructs within the input text:

  • Assignment with =: name = value
  • Assignment by whitespace: name value (no =)
  • Quoted values: double-quoted ("...") and single-quoted ('...') strings. The surrounding quotes are stripped from the stored value.
  • Blocks: <name> ... </name> producing a nested dict keyed by the block name.

All scalar values are stored as strings.

Variable Interpolation Behavior (when interpolatevars is True)

A value may reference a previously defined variable using either of these forms:

  • $name
  • ${name}

When such a reference appears, it is replaced by the value currently bound to name.

Rules exercised:

  1. Bare reference ($a or ${b}): the entire referenced value is substituted. E.g. if a = 1, then b = $a yields b == "1"; if b == "1", then c = ${b} yields c == "1".

  2. Reference inside a double-quoted value: interpolation occurs within the string, with substituted text spliced into the surrounding literal text. E.g. with e == "1", the value "${e} + 2" yields "1 + 2".

  3. Reference inside a single-quoted value: interpolation does not occur. Single-quoted values are taken literally. E.g. '${e}' yields the literal string "${e}".

  4. Scope / resolution order: references resolve against variables defined earlier, including those defined at an outer scope relative to a nested block. A variable defined inside a block takes precedence within that block. Concretely, given a top-level c and a block <aa> that defines d = ${c} and e = 2, d resolves to the outer c's value, while f "${e} + 2" inside the block resolves e to the block-local e ("2"), yielding "2 + 2".

Worked Example

Input:

a = 1
b = $a
c = ${b}
e 1
<aa>
  d = ${c}
  e = 2
  f "${e} + 2"
  g = '${e}'
</aa>

With interpolatevars = True, the resulting dict is:

{
    'a': '1',
    'b': '1',
    'c': '1',
    'e': '1',
    'aa': {
        'd': '1',
        'e': '2',
        'f': '2 + 2',
        'g': '${e}',
    },
}

Notes

  • All values in the result are strings.
  • Block contents are represented as a nested dict under the block's name.
  • The interpolatevars option controls whether references are resolved; the behavior above is required only for the enabled case as exercised here.

Environment Variable Interpolation in the Apache Config Loader

Add opt-in environment-variable interpolation to Apache-style configuration values through a new boolean option, interpolateenv. Existing configuration-variable interpolation, quoting rules, parsing behavior, and compatibility with all existing options must be preserved.

Public API

The following names must remain importable directly from apacheconfig, including through from apacheconfig import *:

  • make_lexer(**options)
  • make_parser(**options)
  • ApacheConfigLoader(parser, **options)

make_lexer(**options) and make_parser(**options) are class factories, not instance factories:

  • make_lexer(**options) returns an instantiable lexer class. The returned class can be instantiated with no required arguments.
  • make_parser(**options) returns an instantiable parser class. The returned class can be instantiated with a lexer instance.
  • ApacheConfigLoader(parser, **options) accepts the resulting parser instance and exposes loads(text), which parses a configuration string and returns the nested configuration dict.

Consequently, this standard construction must work:

options = {'interpolateenv': True}

ApacheConfigLexer = make_lexer(**options)
ApacheConfigParser = make_parser(**options)
parser = ApacheConfigParser(ApacheConfigLexer())
loader = ApacheConfigLoader(parser, **options)
config = loader.loads(text)

Equivalently, callers may construct the parser as make_parser(**options)(make_lexer(**options)()). The factory results must not be replaced with already-instantiated lexer or parser objects.

Each of make_lexer, make_parser, and ApacheConfigLoader must accept the interpolateenv keyword option in addition to all options it already supports. Existing options and construction patterns must continue to behave as before.

Interpolation Behavior

When interpolateenv=True is supplied through the lexer, parser, and loader construction, values support references in both of these forms:

  • $name
  • ${name}

Enabling interpolateenv activates configuration-variable resolution as well as the environment fallback; callers do not need to enable interpolatevars separately for this behavior.

Resolution Order

For each reference, resolve name in this order:

  1. Look for a visible configuration key named name. A key defined earlier in the same block is visible, as is a key from an enclosing block. A nearer block-local key takes precedence over an enclosing key.
  2. Only if no visible configuration key resolves the name, look it up in the process environment (os.environ). If present, replace the reference with that environment variable's string value.

Configuration values therefore always take precedence over same-named environment variables. References can be chained through previously defined configuration values, and configuration values resolved from the environment are available to subsequent references in the same way as other configuration values.

Environment lookup is strictly opt-in. If interpolateenv is omitted or false, no reference may be resolved from the process environment. Existing config-only interpolation enabled by interpolatevars must remain unchanged. Behavior for references that cannot be resolved through an enabled source must otherwise remain compatible with the existing interpolation behavior.

Quoting Rules

Existing quoting behavior applies equally to configuration and environment interpolation:

  • References in unquoted values are interpolated.
  • References inside double-quoted values ("...") are interpolated.
  • References inside single-quoted values ('...') are not interpolated. Their reference text remains literal in the parsed value; the syntactic outer quotes are not part of that value.

Example

Given a process environment containing a=1, load the following text with interpolateenv=True supplied as shown in the public construction above:

b = $a
c = ${b}
e 1
<aa>
  d = ${c}
  e = 2
  f "${e} + 2"
  g = '${e}'
</aa>

The result must be:

{
    'b': '1',
    'c': '1',
    'e': '1',
    'aa': {
        'd': '1',
        'e': '2',
        'f': '2 + 2',
        'g': '${e}'
    }
}

Here, $a falls back to the environment; ${b} uses the previously resolved configuration key; ${c} is inherited from the enclosing scope; ${e} in f uses the nearer block-local e; and the single-quoted reference in g remains literal.

Compatibility Constraints

  • interpolateenv must not alter normal parsing when no environment fallback is needed.
  • Environment values must never override visible configuration keys.
  • The existing interpolatevars feature and all existing interpolation and quoting behavior must continue to work.
  • All existing lexer, parser, loader, include, block, duplicate-option, and other option behavior must remain compatible.
  • The feature only reads the process environment to resolve values; it does not modify environment variables.

  • make_parser(**options) — returns a parser class.
  • ApacheConfigLoader(parser_instance, **options) — the loader; parser_instance is an instance of the parser class, itself constructed from an instance of the lexer class.

Typical construction sequence:

options = {'allowsinglequoteinterpolation': True}

ApacheConfigLexer = make_lexer(**options)
ApacheConfigParser = make_parser(**options)

The loader exposes a loads(text) method that parses the given configuration text and returns a dict mapping keys to their (interpolated) string values.

Required Behavior

Behavior: dumps(config)

dumps(config) renders a configuration dict of the same shape produced by loads back into canonical Apache configuration text and returns a str.

Formatting rules
  • Scalar key/value entries are rendered one per line as key value, separated by a space and without =.
  • A scalar value containing one or more spaces must be surrounded by double quotes. For example, key c with value d d is rendered as c "d d". Values without spaces are not quoted.
  • When a key maps to a list, every list element is rendered independently, in list order, as a separate value for that key.
  • Nested dict values are rendered as blocks:
    • The opening tag is <name>, where name is the key.
    • The block contents follow on subsequent lines and are indented by two additional spaces per nesting level.
    • The closing tag appears on its own line as </name> and repeats the opening name. This includes the full key when a nested block key contains spaces.
  • The output ends with a trailing newline after the final rendered line.
Rendering example

Given the dict:

{'a': ['b', {'block': {'a': 'b'}}, 'b', {'a block': {'c': 'd d'}}]}

the output text must be exactly:

a b

  </block>
</a>
a b
<a>
  <a block>
    c "d d"
  </a block>
</a>

In this example:

  • The list under key a produces four rendered items in order: scalar b, a block, scalar b, and another block.
  • Scalar b values render as a b.
  • The first dictionary element under a renders as a top-level <a> block containing the nested <block> block. Its scalar contents are indented by four spaces.
  • The inner block keyed by a block uses the full multi-word key in both <a block> and </a block>.
  • The scalar value d d is enclosed in double quotes because it contains a space, producing c "d d".
  • A trailing newline follows the final </a> line.

The output from dumps for a configuration obtained through loads need not reproduce the original source verbatim; it must use the canonical form described above.

Overview

You are working on a parser for Apache-style configuration files. The parser processes configuration text containing block-style tags (similar to XML/HTML tags) and produces an Abstract Syntax Tree (AST). Your task is to ensure that tag names are correctly extracted regardless of surrounding whitespace inside the tag delimiters.

Public API

The parser components are constructed via two factory functions:

  • make_lexer() — returns a lexer class (call it ApacheConfigLexer). It is instantiated with no arguments: ApacheConfigLexer().
  • make_parser() — returns a parser class (call it ApacheConfigParser). It is instantiated with the lexer instance and a keyword argument: ApacheConfigParser(ApacheConfigLexer(), start='contents').

The parser instance exposes:

  • parse(text) — accepts the configuration text as a string and returns the AST.

Keep the existing import paths, module locations, and these names/signatures intact so the components can be imported and invoked exactly as shown.

Required Behavior

The configuration syntax supports block tags. A block is opened with an opening tag of the form <name> and closed with a matching closing tag of the form </name>. Blocks may also be self-closing, written as <name/>.

The behavior to implement/fix: whitespace inside the tag delimiters must be stripped so it does not become part of the tag name. Specifically, arbitrary leading and trailing spaces around the tag name (and around the / in closing and self-closing tags) must be ignored when determining the tag name.

The following forms must all be recognized and must all yield a tag name identical to the same tag written with no internal whitespace:

  • Opening tags: <name> and <name > (trailing space before >).
  • Closing tags: </name>, </ name > (spaces after /, around the name, before >).
  • Self-closing tags: <name/>, <name /> (space before /), <name /> (multiple spaces before /).
AST structure
  • A parsed document produces a list whose first element is the string 'contents', followed by one entry per top-level block.
  • A block is represented as a list of the form: ['block', <open_name>, <body>, <close_name>], where:
    • <open_name> is the tag name extracted from the opening (or self-closing) tag, with all surrounding whitespace stripped.
    • <body> is the parsed contents of the block (a list of nested entries), or an empty list [] when the block has no contents.
    • <close_name> is the tag name extracted from the closing tag (for self-closing blocks, this equals the tag name as well), with all surrounding whitespace stripped.
Concrete expectations

For a document consisting of nested blocks:

<a>
  <b>
     <c >
     </ c >
  </b>
</a>

the resulting AST must nest correctly, and the innermost block for c must be ['block', 'c', [], 'c'] — i.e., the extra spaces in <c > and </ c > do not appear in the extracted names.

For a document consisting of consecutive self-closing blocks:

<a/>
<b/>
<c />
<d  />

the resulting AST must be:

['contents',
 ['block', 'a', [], 'a'],
 ['block', 'b', [], 'b'],
 ['block', 'c', [], 'c'],
 ['block', 'd', [], 'd']]

Each self-closing tag, whether or not it contains spaces before the /, must produce a block with an empty body and a name equal to the whitespace-stripped tag name for both the open and close positions.

Constraint

Preexisting parser behavior (handling of tags written without internal whitespace, nesting, and self-closing blocks) must continue to work unchanged. Only the tolerance for and stripping of internal tag whitespace is being added/corrected.

20 Extend the Apache-style configuration parser and loader so that block tags support multiple whitespace-separated components and quoted components. 1427 words · rewritten by Claude Fable 5

Objective

Extend the Apache-style configuration parser and loader so that block tags support multiple whitespace-separated components and quoted components. Existing single-component blocks and the existing public API must remain compatible.

Public API

The following API surface must remain available:

  • make_lexer() returns an ApacheConfigLexer class.
  • make_parser() returns an ApacheConfigParser class.
  • ApacheConfigLexer() constructs a lexer instance.
  • ApacheConfigParser(lexer) constructs a parser from a lexer instance and exposes parse(text), which returns the nested-list AST described below.
  • ApacheConfigLoader(parser) constructs a loader from a parser instance and exposes loads(text), which returns the parsed configuration as a Python dict.

Block syntax

A block starts with an opening tag <...> and ends with a corresponding closing tag </...>. A name-only block may instead be self-closing as <name/>.

Tag components

The payload of an opening tag consists of one or more components separated by whitespace:

  • The first decoded component is the block name.
  • All remaining decoded components form the block's trailing value.
  • When there is more than one trailing component, the loader joins those components with a single space.

Thus, <a b> has block name a and trailing value b, while <a b c> has block name a and trailing value b c.

Closing tags

A closing tag is not required to repeat the opening tag's trailing components. Both of the following closing forms must be accepted for a block opened with a multi-component tag:

  • a closing tag repeating the complete opening payload, such as <a b c>...</a b c>; and
  • a name-only closing tag containing just the opening tag's first component, such as <a b c>...</a>.

A name-only close does not discard the opening tag's trailing components: the block's semantics are derived solely from the opening-tag payload, so <officer randall>...</officer> still carries the block name officer and the trailing value randall. The parser and loader must not reject or alter such documents by enforcing that the closing-tag component list equals the opening-tag component list.

This applies regardless of how many trailing components the opening tag has: <a block>...</a> (one trailing component) and <a a block>...</a> (two trailing components) must both parse and load successfully.

Quoting

Any component may be enclosed in matching double quotes ("...") or single quotes ('...'). Whitespace inside a quoted component is part of that one component rather than a separator. The surrounding quote characters are removed when deriving the semantic component value, while text and spaces inside the quotes are retained literally.

Consequently:

  • <"a b"> contains one component and has block name a b.
  • <'d e'> contains one component and has block name d e.
  • <g 'h i'> contains two components: block name g and trailing value h i.
  • <a b c> and <a 'b c'> both produce the trailing loader key b c, although their component boundaries differ.

Quoted components must work in both opening and closing tags. A closing tag that repeats the opening payload must decode to the same ordered component list as the opening tag; for example, a block opened with <"a b"> may be closed with </"a b">, and one opened with <g 'h i'> may be closed with </g 'h i'>.

Whitespace and self-closing blocks

Whitespace separating unquoted components is syntactic and is normalized to a single space when multiple trailing components are joined for loader output. Whitespace enclosed by quotes remains literal.

A self-closing tag has exactly one component. Whitespace immediately before /> is insignificant, so forms such as <name/> and <name /> represent the same empty block. Quoting may be used when the sole name component itself contains spaces.

Parser AST

The parser uses nested Python lists. A block node retains its existing four-element shape:

['block', <opening_tag>, <body>, <closing_tag>]

The fields have these meanings:

  • <opening_tag> is the complete opening-tag payload after the surrounding delimiters and insignificant leading or trailing whitespace are removed. It must preserve every component, their order, component-separating text, and the quote delimiters that identify quoted components. It is not limited to the first decoded component.
  • <body> is the parsed list of contents inside the block, or [] for an empty or self-closing block.
  • <closing_tag> is the complete, correspondingly stripped closing-tag payload as it appeared in the source. When the document uses a name-only closing tag, this field contains only the block name even though <opening_tag> retains the trailing components. For a self-closing block, it is the same value as <opening_tag>.

Retaining the complete payload and quote boundaries is required because these inputs have different semantics:

<a b></a b>          # name `a`, trailing value `b`
<"a b"></"a b">      # one name component, `a b`

Their block nodes are respectively:

['block', 'a b', [], 'a b']
['block', '"a b"', [], '"a b"']

Likewise, an empty <a b c>...</a b c> block retains a b c in both tag fields, and <g 'h i'>...</g 'h i'> retains g 'h i'. An empty block opened as <a b> but closed as </a> produces ['block', 'a b', [], 'a']. The loader then decodes the full opening-tag payload into its semantic components.

At the contents level, nodes remain wrapped by ['contents', ...]. For example:

<a/>
<b/>

produces:

['contents', ['block', 'a', [], 'a'], ['block', 'b', [], 'b']]

Single-component, unquoted block nodes therefore retain their previous representation.

Loader dictionary semantics

The loader must interpret the complete opening-tag payload using the component and quoting rules above. Quote delimiters retained by the AST are not included in dictionary keys. Dictionary keys are derived solely from the opening-tag payload; whether the block was closed by a full-payload closing tag or by a name-only closing tag has no effect on loader output.

Let name be the first decoded component of the opening tag, value be all remaining decoded components joined with one space, and contents be the dictionary loaded from the block body:

  • A one-component tag produces {name: contents}.
  • A tag with trailing components produces {name: {value: contents}}.
  • An empty block has an empty contents dictionary.
Single-component tags
<name>
  key = 1
</name>

produces:

{'name': {'key': '1'}}
Multi-component named tags
<name value>
  key = 1
</name value>

produces:

{'name': {'value': {'key': '1'}}}

For multiple trailing components:

<a b c>
  d = 1
</a b c>

produces:

{'a': {'b c': {'d': '1'}}}
Name-only closing tags

Because loader keys come only from the opening tag, a multi-component block closed with a name-only tag loads identically to one closed with the full payload:

<officer randall>
  age = 25
</officer>

produces:

{'officer': {'randall': {'age': '25'}}}

The same holds when the opening tag has several trailing components; for example a block opened as <a a block> and closed as </a> has block name a and trailing value a block, so its contents load under {'a': {'a block': ...}}.

Repeated block names

When the same block name occurs more than once with different trailing values, its block values are collected into a list in source order. For example:

<a b>
c = 1
</a b>

<a b c>
d = 1
</a b c>

produces:

{'a': [{'b': {'c': '1'}}, {'b c': {'d': '1'}}]}

The first block's trailing value is b; the second block's trailing value is b c. Both share the block name a, so their nested dictionaries become entries in the list under a.

This collection behavior applies equally when the blocks are closed with name-only tags:

<officer randall>
  name = stein
</officer>
<officer gordon>
  name = bird
</officer>

produces:

{'officer': [{'randall': {'name': 'stein'}}, {'gordon': {'name': 'bird'}}]}
Quoted tags

Quotes are removed during semantic decoding, and quoted whitespace stays in the resulting key. For example:

<"a b">
c = 1
</"a b">

<'d e'>
f = 1
</'d e'>

<g 'h i'>
j = 1
</g 'h i'>

produces:

{
    'a b': {'c': '1'},
    'd e': {'f': '1'},
    'g': {'h i': {'j': '1'}}
}

The first two tags each contain a single quoted name component. The third contains the name g and one quoted trailing component whose value is h i.

Values inside blocks

Ordinary assignments inside any block retain their existing behavior. In particular, key = value contributes a string-valued entry to that block's contents, such as {'key': 'value'}. This behavior composes normally with single-component, multi-component, quoted, nested, empty, and repeated blocks, and with blocks closed by name-only closing tags.
