01 Accepting auto as the Starting Value of Scan Constraints 895 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Accepting auto as the Starting Value of Scan Constraints

Background

Input files for several computational chemistry packages (Gaussian, ORCA, xtb) are produced by the input-generation library. Among the calculation types it can build is a Constrained Optimisation, in which an internal coordinate (e.g., a bond distance) gets scanned from a starting value to an ending value across a number of steps.

Support must be added for a special keyword, auto, that can occupy the position of the numeric starting value in a scan constraint. Whenever auto occupies that position, the starting value must be computed based on the molecule's current geometry (i.e., the value of the coordinate between the specified atoms as actually measured), instead of having the user supply it explicitly.

Format of the Constraint String

The constraints parameter receives a string holding the constraints. A scan constraint looks like this:

Scan_<start>_<end>_<num_steps>/<atom1>_<atom2>;

in which:

  • <start>: the coordinate's initial value. The literal string auto may now occupy this spot rather than a number.
  • <end>: the coordinate's final value.
  • <num_steps>: the scan's step count.
  • <atom1>_<atom2>: the 1-indexed atom numbers that identify the coordinate (a bond distance in the two-atom case).

Example (bond-distance scan whose start value is found automatically):

Scan_auto_1.4_10/1_2;

In other words: over 10 steps, the distance between atom 1 and atom 2 is scanned, starting from that distance's current value in the geometry and finishing at 1.4.

Behavior That Must Be Implemented

Whenever a scan constraint's start value reads auto, it must be replaced with the distance that currently separates the two named atoms, read off the input molecular geometry (the Cartesian coordinates contained in the provided structure file). The numeric value that results must then be used in exactly the way an explicitly-provided numeric start value would be.

For the ethanol geometry these calculations rely on, the distance between atoms 1 and 2 as currently measured comes out to 1.07 (formatted as shown below).

Number Formatting

All numeric scan values emitted into the generated input files must be formatted to two decimal places; this covers both the auto-computed start value and the scan specification's other numeric values. To give an example: 1.4 must be rendered as 1.40, and 9.0 must be rendered as 9.00.

Across all supported software, this formatting requirement governs the numeric coordinate values that land in the scan portions of the generated input files.

Output Expected from Each Software

Take the scan constraint Scan_auto_1.4_10/1_2; and apply it to the ethanol geometry, where the current distance between atoms 1 and 2 is 1.07. The generated outputs are the following:

Gaussian

Within the generated input, a modredundant scan line of this shape must appear:

B 1 2 S 10 0.03

The parts: B 1 2 names the bond joining atoms 1 and 2, S 10 marks a scan over 10 steps, and 0.03 is the step size (obtained by taking the span from the start value 1.07 to the end value 1.40 and dividing it across the 10 steps; note that the existing Gaussian scan-line convention is what this format matches).

ORCA

A geometry scan block like the one below must be present in the generated input:

%geom Scan
B 0 1 = 1.07, 1.40, 10
end
end

Keep in mind that ORCA's atom numbers are 0-indexed (atoms 1 and 2 become 0 and 1); the start value is the auto-computed 1.07, the end value is 1.40, and 10 gives the number of steps. The values carry two-decimal formatting.

xtb

The generated input file must include a scan section shaped like this:

$constrain
force constant=1.0
distance: 1, 2, auto
$scan
1: 1.07, 1.40, 10

The literal auto keyword is retained on the distance: line. On the $scan line, the start value is the auto-computed 1.07, the end value is 1.40, and there are 10 steps. All the numeric values are formatted with two decimals.

For an explicit numeric start value (non-auto), the same two-decimal formatting applies to the values on the $scan line (e.g. a start of 9.0 and end of 1.4 produce 9.00, 1.40, 10).

Public API

The behavior described above gets exercised via the existing top-level calculation-generation entry point that the library already relies on, invoked with a parameter dictionary that contains at least:

  • type: "Constrained Optimisation"
  • file: the path of a structure file (e.g. "ethanol.xyz")
  • software: one of "Gaussian", "ORCA", "xtb"
  • constraints: the constraint string specified above
  • as well as the usual method/basis/charge/nproc/mem parameters where applicable

The calculation object that comes back must expose:

  • .input_file: the complete text of the generated input file
  • .command: the command-line invocation as a string (for xtb, e.g. xtb ethanol.xyz --opt tight --input input)

No new public modules or classes are called for; it is the parsing and emission of scan constraints that this change extends, within the generation pipeline as it already exists.

Summary of the Required Changes

  1. Accept the literal auto as a stand-in for a numeric start value in scan constraints.
  2. When auto is used, the start value must be computed as the current distance between the two specified atoms, based on the input geometry.
  3. In the Gaussian, ORCA, and xtb output, all numeric scan coordinate values must be formatted to two decimal places.

Task Specification: Support for Auxiliary Basis Sets with Correlated Methods (ORCA)

Overview

Extend the ORCA input file generation so that auxiliary (fitting) basis sets are supported for methods that require or benefit from resolution-of-the-identity (RI) approximations, specifically RI-MP2, MP2, DLPNO-CCSD(T), and CCSD(T).

Public API

The change is exercised via the existing calculation-generation entry point already used to build ORCA inputs. To generate a calculation, a dictionary of parameters is passed in; that dictionary includes:

  • nproc: the number of processors (an integer or a string)
  • type: the type of calculation, for instance "Single-Point Energy"
  • file: the geometry file name (for example "Cl.xyz")
  • software: "ORCA"
  • method: the electronic-structure method (described below)
  • basis_set: the primary basis set (for example "cc-pVTZ")
  • charge: the molecular charge (a string or an integer)
  • specifications: a free-form string that is used, among other things, to specify an auxiliary basis set

On the calculation object that results, the generated ORCA input is exposed as .input_file.

Required Behavior

The first (keyword) line of the ORCA input takes the following form:

!SP <method> <basis_set> [<auxiliary_basis>]

Whether an auxiliary basis set appears on this keyword line, and which value it takes, depends on the method and the specifications string, as set out in the rules below. The method and the primary basis set are emitted verbatim, exactly as provided.

Methods using an auxiliary basis set

When the method is RI-MP2 or DLPNO-CCSD(T), the keyword line must carry an auxiliary basis set token placed immediately after the primary basis set.

  • Auxiliary basis given explicitly through specifications: If an auxiliary basis specification is present in specifications (a token of the form <name>/C, for example cc-pVDZ/C), that auxiliary basis set is the one used. No matter what casing is supplied in specifications, the auxiliary basis name must be normalized to its canonical spelling. For example, an input of cc-pvtz/C must be emitted as cc-pVTZ/C, and an input of cc-pVDZ/C must be emitted as cc-pVDZ/C.

  • Default auxiliary basis: If specifications provides no auxiliary basis (an empty string, for example), a default auxiliary basis set must be derived automatically from the primary basis set by appending /C to it, with the primary basis taken in its canonical spelling. When the primary basis is cc-pVTZ, the default auxiliary basis is cc-pVTZ/C.

Methods that use no auxiliary basis set

When the method is MP2 or CCSD(T), the keyword line contains no auxiliary basis set token: only the method and the primary basis set are present there, even when specifications is empty.

Examples

The examples below use primary basis cc-pVTZ, charge -1, geometry Cl.xyz, 8 processors, and a single-point energy:

method specifications keyword line
RI-MP2 cc-pvtz/C !SP RI-MP2 cc-pVTZ cc-pVTZ/C
RI-MP2 `` (empty) !SP RI-MP2 cc-pVTZ cc-pVTZ/C
RI-MP2 cc-pVDZ/C !SP RI-MP2 cc-pVTZ cc-pVDZ/C
MP2 `` (empty) !SP MP2 cc-pVTZ
DLPNO-CCSD(T) cc-pVTZ/C !SP DLPNO-CCSD(T) cc-pVTZ cc-pVTZ/C
DLPNO-CCSD(T) `` (empty) !SP DLPNO-CCSD(T) cc-pVTZ cc-pVTZ/C
CCSD(T) `` (empty) !SP CCSD(T) cc-pVTZ

Structure of the Full Input File

For the examples above, the complete generated input has the following structure (illustrated for RI-MP2 with a cc-pVTZ/C auxiliary basis):

!SP RI-MP2 cc-pVTZ cc-pVTZ/C
*xyz -1 1
Cl 0.0 0.0 0.0
*
%pal
nprocs 8
end

The geometry block reflects the coordinates supplied and the charge/multiplicity, while the %pal block reflects the processor count requested. Differences in whitespace/indentation are not significant.

Task Description

Summary

Augment ccinput.calculation.Calculation with opt-in parsing of the molecular charge and spin multiplicity from a supplied file name. Once enabled, keywords recognized case-insensitively in the file argument determine the calculation's charge and/or multiplicity before the electronic state is validated.

Public Interface

ccinput.calculation.Calculation

On top of its existing arguments, such as geometry, type, parameters, nproc, mem, charge, multiplicity, and software, the Calculation constructor must accept the following optional keyword arguments:

  • parse_name (bool, default False): turns file-name parsing on when true.
  • file (str, optional; its default may be None or empty): the file name supplied for inspection. No file extension is required.

These arguments must be usable as keyword arguments so that existing call sites remain compatible.

ccinput.exceptions

ccinput.exceptions must publicly expose ImpossibleCalculation, importable as:

from ccinput.exceptions import ImpossibleCalculation

Parsing of the File Name

When parse_name=True, the string supplied through file is inspected for recognized keywords. Matching must be:

  • performed case-insensitively;
  • based on the presence of a keyword as a substring, rather than requiring the whole name to equal a keyword; and
  • independent of separators or other surrounding text, so names that contain multiple keywords, such as Cl_anion_triplet, are supported.
Charge Keyword
  • anion makes the resulting charge exactly -1.

anion is an absolute designation, not a relative adjustment: it replaces the charge that was supplied rather than subtracting one from it. Specifically, if the constructor receives charge=-1, a name containing anion still produces charge == -1, not -2.

If anion is absent, the supplied charge is left unchanged.

Multiplicity Keywords
  • radical makes the resulting multiplicity 2.
  • doublet makes the resulting multiplicity 2.
  • triplet makes the resulting multiplicity 3.

If the name contains no multiplicity keyword, the supplied multiplicity is left unchanged. Charge and multiplicity keywords operate independently, so a single name may apply a charge keyword and a multiplicity keyword together. The resulting values must be exposed by the charge and multiplicity attributes of the constructed object.

Validation of the Electronic State

Validation against the electron-count parity implied by the molecular geometry must be applied to the final, name-derived charge and multiplicity. The electron count is obtained as the sum of the atomic numbers of all atoms in the geometry, minus the resulting molecular charge. A parity combination is valid when:

  • an odd multiplicity is combined with an even electron count; or
  • an even multiplicity is combined with an odd electron count.

If the electron count and the multiplicity share the same parity, the requested state is impossible and construction must raise ImpossibleCalculation. This validation therefore takes effect after all enabled file-name designations have determined the resulting charge and multiplicity. There is no requirement for any particular exception message.

Required Results

For a geometry that contains one chlorine atom and starts from an initial charge=0:

  • With file="Cl_anion" and parse_name=True, the outcome is charge == -1; apart from that, the supplied multiplicity is retained.
  • With file="Cl_radical" and parse_name=True, the outcome is charge == 0 and multiplicity == 2.
  • With file="Cl_anion_triplet" and parse_name=True, the outcome is charge == -1 and multiplicity == 3.
  • With file="Cl_anion_doublet" and parse_name=True, the final charge is -1 and the multiplicity is 2, and therefore ImpossibleCalculation is raised, because the chloride anion has an even electron count.

The same exception is required for the last case when the constructor's initial charge is already -1: anion holds the final charge at -1 instead of changing it to -2, and the requested doublet remains parity-incompatible.

Compatibility Constraints

  • When parse_name=False or it is omitted, do not derive either value from file; the supplied charge and multiplicity, along with all pre-existing behavior, must be preserved.
  • When parsing is enabled but no relevant keyword is found, keep the corresponding supplied value.
  • Validation of constructor inputs that already exists stays in force, covering charge and multiplicity validation, processor validation, memory validation such as InvalidParameter for invalid Gaussian memory specifications, software validation, and all unrelated calculation behavior.
  • Existing callers that do not use name parsing must not be required by the feature to change their arguments or invocation style.

Task: Add an explicit memory specification to ORCA input files

Overview

Within this codebase, the ORCA input file generator must be modified so that it emits an explicit per-core memory directive (%MaxCore) in every generated ORCA input file.

Required Behavior

When an ORCA input file is generated, the output must include a %MaxCore block that states the amount of memory available per processing core, expressed in megabytes (MB) as an integer.

Placement

The %MaxCore line must be emitted:

  • After the block containing the molecule/coordinate specification (and after any other calculation-specific blocks such as %geom, %output, %neb, basis set blocks, constraint blocks, etc. that precede the parallelization block).
  • Immediately before the parallelization block %pal.

The emitted line has exactly the following format:

%MaxCore <value>

where <value> is the integer number of megabytes per core, and a single space separates %MaxCore from the value.

How the value is computed

The emitted value is the total available memory divided evenly across the number of cores, i.e.:

MaxCore = total_memory_in_MB / number_of_cores

This result must be an integer (megabytes per core).

Observed cases that the implementation must satisfy
  • For a calculation that uses 1 core with total memory of 1000 MB, the emitted line is %MaxCore 1000.
  • For a calculation that uses 8 cores with total memory of 1000 MB, the emitted line is %MaxCore 125 (1000 / 8 = 125).

These default values (total memory of 1000 MB) apply to the standard input generation path exercised here; the per-core value tracks the core count used in the matching %pal ... nprocs N ... end block that follows.

Example

For a calculation that runs on a single core, the tail of the generated file must look like:

*xyz -1 1
Cl 0.0 0.0 0.0
*
%MaxCore 1000
%pal
nprocs 1
end

For a calculation that runs on eight cores:

*xyz -1 1
Cl 0.0 0.0 0.0
*
%MaxCore 125
%pal
nprocs 8
end

Scope

Only the content of generated ORCA input files is affected by this change. No public function names, signatures, or module paths need to be changed; generation entry points that already exist continue to be called exactly as before. The only observable difference is that the %MaxCore <value> line is added in the position described above in every generated ORCA input.

Task: Determine the Calculation Name from the Input File Name

Summary

At present, a Calculation object (in the ccinput package) has a name attribute whose default is a fixed placeholder. The way this default name is determined must be changed so that, when a calculation is created from an input file, the name comes from that file's base name.

Behavior Requirements

At construction of a calculation, its name attribute must be resolved in accordance with the following rules:

  1. An explicitly given name takes precedence. When a caller passes a name argument, the name attribute must be set to exactly that value, regardless of any file provided.

  2. Fall back to the base name of the file. When no explicit name is given but a source file is supplied (by way of a file argument), the name attribute must be set to that file's base name with its extension removed. The base name is the file component only (no directory path) and excludes the final extension.

    • Example: a file value of "Cl_anion" (no extension present) yields a name of "Cl_anion".
    • Example: giving a file value such as "ethanol.xyz" yields a name of "ethanol".

  3. Default when neither is supplied. When neither an explicit name nor a file is provided, the existing default behavior is kept (the name keeps the previously used default value).

%chk=<name>.chk

The checkpoint file stem for this directive must be the resolved name (as specified by the rules above). As a consequence, when a calculation is created from a file, the %chk= line reflects the file's base name (e.g. %chk=ethanol.chk, %chk=Cl.chk, %chk=Ph2I_cation.chk, %chk=AuI.chk, %chk=mini_ts.chk, %chk=I.chk), and when an explicit name is supplied, the directive uses that name.

API Surface
  • The calculation object must accept an optional name keyword argument together with an optional file keyword argument, and expose the resolved value as a public name attribute.
  • All other existing construction parameters and the behavior they have are left unchanged.

Task Specification: Generating ORCA Basis Sets for Custom Elements

Overview

You are changing the logic in the ccinput package that generates ORCA input files. What the change concerns is the way custom basis sets assigned to individual elements are emitted into the %basis block of a generated ORCA input file. When a user asks for a custom basis set covering specific elements, the generator must decide whether to emit a compact reference to a built-in ORCA basis set or a fully explicit (expanded) basis-set definition.

Context: The Public API Surface

Calculations are produced through the existing entry point for calculation generation, which is used elsewhere in the package. A calculation is created by calling the package's generator, passing keyword arguments including:

  • nproc (int): the number of processors.
  • type (str): the type of calculation, e.g. "Geometrical Optimisation".
  • file (str): the geometry file name (e.g. an .xyz file from which coordinates are read).
  • software (str): always "ORCA" in this context.
  • charge (str): the overall charge, e.g. "+1".
  • method (str): e.g. "B3LYP".
  • basis_set (str): the primary basis set, e.g. "6-31+G(d,p)".
  • custom_basis_sets (str): a specification mapping elements to basis sets, terminated by semicolons (see below).

The generated object exposes the completed input text through its input_file attribute (a string). The behavior described below relates only to the contents of that text.

Format of the custom_basis_sets Specification

The value is a string composed of one or more ELEMENT=BASISSET assignments, each of which is terminated by a semicolon (;). Case-insensitive matching applies to element symbols and to basis-set names, and internal spaces may appear inside basis-set names. Some examples of individual assignments:

  • N=Def2-SVP;
  • I=Def2 tzvpd;
  • I=psbkjc;

Behavior That Is Required

For each element listed in custom_basis_sets, the generator must emit an entry within the %basis ... end block. Which form that entry takes depends on whether the requested basis set is one that ORCA provides as a built-in basis set.

Case 1: A built-in basis set is available

When the basis set requested for an element is one that ORCA supports natively as a built-in basis set, the generator must emit a compact reference instead of expanding the basis functions explicitly. The reference takes the form:

NewGTO <ELEMENT> "<CanonicalBasisName>" end
  • <ELEMENT> is the symbol of the element.
  • <CanonicalBasisName> is the canonical ORCA name of the basis set, enclosed in double quotes.

Concrete required mappings, as verified for this task:

  • When Def2-SVP is requested for nitrogen (N) →
    NewGTO N "Def2-SVP" end
  • When Def2 tzvpd is requested for iodine (I) →
    NewGTO I "Def2-TZVPD" end

Note the canonicalization: internal spaces turn into hyphens, and the name that is produced uses exactly the casing shown above (e.g. Def2-TZVPD).

Associated ECP for built-in basis sets that require an effective core potential

When the element uses an effective core potential along with the built-in basis set, an ECP reference line must also be emitted immediately after the NewGTO line, inside the same %basis block, in the following form:

NewECP <ELEMENT> "<ecp-name>" end

Required concrete mapping: for iodine (I) with Def2 tzvpd, the block contains:

%basis
NewGTO I "Def2-TZVPD" end
NewECP I "def2-ECP" end
end

(In this case, no separate, expanded NewECP block with N_core/lmax/shell listings is emitted.)

Case 2: A built-in basis set is NOT available

When the basis set requested for an element is not a built-in ORCA basis set, the generator must emit the fully explicit basis-set definition, expanding all shells and their primitive Gaussian exponents/coefficients. The block form used is:

newgto <ELEMENT>
<shell definitions...>
end

and, when the element requires an effective core potential, this is followed by a separate explicit ECP block:

NewECP <ELEMENT>
N_core <n>
lmax <l>
<shell listings...>
end

The explicit expansion is the behavior already in place; it must remain the fallback path whenever no built-in basis set exists for the requested name. As an example, requesting psbkjc for iodine (I) — which is not a built-in ORCA basis set — must produce the explicit expanded newgto I ... end block and the explicit NewECP I ... end block that contains the basis primitives and ECP shell data for that basis set.

The Decision Rule in Summary

For each element in custom_basis_sets:

  1. Establish whether the requested basis set exists as a built-in ORCA basis set (with case-insensitive matching and flexible handling of spaces/hyphens).
  2. If yes: emit NewGTO <ELEMENT> "<CanonicalName>" end, and additionally NewECP <ELEMENT> "<ecp-name>" end when an ECP is required for that element/basis.
  3. If no: emit the fully explicit newgto <ELEMENT> ... end block, and additionally the explicit NewECP <ELEMENT> ... end block when an ECP is required.

All entries that are emitted appear inside the single %basis ... end section of the ORCA input file. The rest of the input file (header/keyword line, geometry block, %MaxCore, %pal/nprocs blocks, etc.) is unaffected by this change.

Notes Concerning Equivalence

Differences in whitespace and blank lines between the generated output and the intended output are not significant; what matters is the content of the meaningful lines and the order in which they appear.

Background

Quantum chemistry input files for a range of software packages — ORCA among them — are produced by the ccinput package. Calculations are put together with a generate_calculation(...) helper (this helper is used throughout the codebase's public API); it accepts keyword parameters describing a calculation, and the object it returns exposes an input_file attribute in which the generated input file text is held.

What this task addresses is the formatting of the header (keyword) line in an ORCA input file — specifically, formatting it correctly when a method requiring an automatically-derived auxiliary basis set is used together with either additional user specifications or an implicit solvation model.

Issue

ORCA requires a correlation-fitting auxiliary basis set derived from the main basis set whenever a DLPNO-based method is used; that auxiliary basis set is named <basis_set>/C. On the ORCA keyword line, the token for this auxiliary basis set must occupy the correct position, and any tokens coming after it — such as extra user specifications or a solvation directive — must be separated from it by single spaces.

At the moment, if other tokens come after the auxiliary basis token, the header line comes out malformed; this must be fixed so that the tokens end up cleanly space-separated, with no separator missing and no separator extra.

Behavior Requirements

Consider an ORCA calculation whose inputs are:

  • type: "Single-Point Energy"
  • software: "ORCA"
  • method: "DLPNO-CCSD(T)"
  • basis_set: "cc-pVTZ"
  • charge and geometry as given (for instance a single Cl atom at the origin, charge -1, multiplicity 1)
  • nproc: 8

In the generated input file, the header line is the first line; it must begin with !, and the following space-separated tokens must appear on it in this order:

  1. SP — the keyword for a single-point calculation
  2. DLPNO-CCSD(T) — the method
  3. cc-pVTZ — the main basis set
  4. cc-pVTZ/C — the derived correlation-fitting auxiliary basis set, obtained by appending /C to the name of the main basis set
  5. any additional tokens at the end of the line (see below)
Case 1 — Extra specifications supplied

When the specifications parameter takes the value "tightscf", the header line ends with the token tightscf, yielding:

!SP DLPNO-CCSD(T) cc-pVTZ cc-pVTZ/C tightscf
Case 2 — Implicit solvation model

When "ch2cl2" is supplied as solvent and "CPCM" as solvation_model, the header line ends with the token CPCM(ch2cl2), yielding:

!SP DLPNO-CCSD(T) cc-pVTZ cc-pVTZ/C CPCM(ch2cl2)

In both cases, exactly one space must separate the auxiliary basis token cc-pVTZ/C from the token that comes after it, with no missing and no doubled whitespace.

Complete Output Format

Below is the complete generated input file for the two scenarios above (with leading/trailing whitespace and blank-line normalization ignored):

Case 1:

!SP DLPNO-CCSD(T) cc-pVTZ cc-pVTZ/C tightscf
*xyz -1 1
Cl 0.0 0.0 0.0
*
%MaxCore 125
%pal
nprocs 8
end

Case 2:

!SP DLPNO-CCSD(T) cc-pVTZ cc-pVTZ/C CPCM(ch2cl2)
*xyz -1 1
Cl 0.0 0.0 0.0
*
%MaxCore 125
%pal
nprocs 8
end

Notes:

  • A *xyz <charge> <multiplicity> line opens the geometry block, and a closing * ends it.
  • The %MaxCore line carries the per-core memory value (125 here).
  • The processor count that was requested is expressed by the %pal ... nprocs 8 ... end block.

API Reachability

The method and basis set are put together into one single-quoted argument of the form '<method>/<basis_set>'.

Behavior on Error

When a calculation type that is otherwise recognized is not supported for Psi4, generation must raise ImpossibleCalculation. This holds for every category other than single-point energy and geometry optimization; to give an example, a request with type="freq" must fail with ImpossibleCalculation instead of producing an input file.

  • For Psi4, only single-point energies and geometry optimizations are required.

Task Description

Goal

Modify the default RMSD threshold value that is used when CREST conformational search commands are generated.

Context

The codebase produces command-line invocations for the CREST tool (which is used with the XTB software backend). When a CREST calculation is configured without an RMSD threshold that has been explicitly specified, a default value is applied to the -rthr command-line flag.

Change Required

The default RMSD threshold value applied to the -rthr flag of the generated CREST command must be 2.0 (previously 0.6).

Resulting Behavior

When a CREST conformational search calculation is generated and the user provides no RMSD threshold, the resulting command string must include -rthr 2.0.

As an example, the command generated for a basic CREST search should be:

crest ethanol.xyz -rthr 2.0 -ewin 6

And when a constraint input file is present:

crest ethanol.xyz -cinp input -rthr 2.0 -ewin 6

(The -cinp filename value follows whatever the caller specifies; the ordering of tokens and other flags such as -ewin 6 stay unchanged.)

Boundaries

  • Only the default numeric value of the -rthr flag is changed: from 0.6 to 2.0.
  • All other aspects of CREST command generation (flag names, flag ordering, -ewin handling, -cinp handling, the trailing/leading command structure) stay exactly as they were.
  • No new API surface is added. The change is limited to the default value used when commands are constructed.
