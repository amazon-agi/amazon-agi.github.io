01 Support auto as Initial Value for Scan Constraints 818 words · source specification

Task Specification: Support auto as Initial Value for Scan Constraints

Overview

The input-generation library supports building computational chemistry input files for multiple software packages (Gaussian, ORCA, xtb). One kind of calculation is a Constrained Optimisation that scans an internal coordinate (e.g., a bond distance) from a starting value to an ending value over a number of steps.

You must add support for a special keyword, auto, used in place of the numeric starting value of a scan constraint. When auto is used, the starting value must be computed from the current geometry of the molecule (i.e., the actual measured value of the coordinate between the specified atoms), rather than being supplied explicitly by the user.

Constraint Input Format

Constraints are passed as a string in the constraints parameter. A scan constraint has the form:

Scan_<start>_<end>_<num_steps>/<atom1>_<atom2>;

where:

  • <start> is the initial value of the coordinate. This may now be the literal string auto instead of a number.
  • <end> is the final value of the coordinate.
  • <num_steps> is the number of scan steps.
  • <atom1>_<atom2> are the 1-indexed atom numbers defining the coordinate (a bond distance for the two-atom case).

Example (bond distance scan with automatic start value):

Scan_auto_1.4_10/1_2;

This means: scan the distance between atom 1 and atom 2, starting from its current value in the geometry, ending at 1.4, over 10 steps.

Required Behavior

When the start value of a scan constraint is auto, the starting value must be replaced by the current distance between the two specified atoms, measured from the input molecular geometry (Cartesian coordinates read from the provided structure file). The resulting numeric value must then be used exactly as an explicitly-provided numeric start value would be.

For the ethanol geometry used in these calculations, the current distance between atoms 1 and 2 evaluates to 1.07 (as formatted below).

Numeric Formatting

All numeric scan values emitted in the generated input files (both the auto-computed start value and other numeric values in the scan specification) must be formatted to two decimal places. For example, a value of 1.4 must appear as 1.40, and a value of 9.0 must appear as 9.00.

This formatting requirement applies to the numeric coordinate values written into the scan portions of the generated input files across all supported software.

Expected Output per Software

Given the scan constraint Scan_auto_1.4_10/1_2; applied to the ethanol geometry (current distance between atoms 1 and 2 = 1.07):

Gaussian

The generated input must contain a modredundant scan line of the form:

B 1 2 S 10 0.03

where B 1 2 denotes the bond between atoms 1 and 2, S 10 denotes a scan over 10 steps, and 0.03 is the step size (computed from the span between the start value 1.07 and the end value 1.40 divided over the 10 steps; note this format matches the existing Gaussian scan-line convention).

ORCA

The generated input must contain a geometry scan block of the form:

%geom Scan
B 0 1 = 1.07, 1.40, 10
end
end

Note ORCA uses 0-indexed atom numbers (atoms 1 and 2 become 0 and 1), the start value is the auto-computed 1.07, the end value is 1.40, and 10 is the number of steps. Values are formatted to two decimals.

xtb

The generated input file must contain a scan section of the form:

$constrain
force constant=1.0
distance: 1, 2, auto
$scan
1: 1.07, 1.40, 10

The distance: line keeps the literal auto keyword. The $scan line uses the auto-computed start value 1.07, the end value 1.40, and 10 steps. All numeric values are formatted to two decimals.

For an explicit numeric start value (non-auto), the same two-decimal formatting applies to the $scan line values (e.g. a start of 9.0 and end of 1.4 produce 9.00, 1.40, 10).

Public API

The behavior above is exercised through the existing top-level calculation-generation entry point already used by the library, invoked with a parameter dictionary containing at least:

  • type: "Constrained Optimisation"
  • file: path to a structure file (e.g. "ethanol.xyz")
  • software: one of "Gaussian", "ORCA", "xtb"
  • constraints: the constraint string described above
  • plus the usual method/basis/charge/nproc/mem parameters where applicable

The returned calculation object must expose:

  • .input_file: the full generated input file text
  • .command: the command-line invocation string (for xtb, e.g. xtb ethanol.xyz --opt tight --input input)

No new public modules or classes are required; the change extends the parsing and emission of scan constraints within the existing generation pipeline.

Summary of Changes Required

  1. Accept the literal auto in place of a numeric start value in scan constraints.
  2. When auto is used, compute the start value as the current distance between the two specified atoms from the input geometry.
  3. Format all numeric scan coordinate values to two decimal places in Gaussian, ORCA, and xtb output.

Overview

Public API

  • type: calculation type, e.g. "Single-Point Energy"
  • file: geometry file name (e.g. "Cl.xyz")
  • software: "ORCA"
  • method: the electronic-structure method (see below)
  • basis_set: the primary basis set (e.g. "cc-pVTZ")
  • charge: molecular charge (string or integer)
  • specifications: a free-form string used, among other things, to specify an auxiliary basis set

The resulting calculation object exposes the generated ORCA input as .input_file.

Required Behavior

The first (keyword) line of the ORCA input has the form:

!SP <method> <basis_set> [<auxiliary_basis>]

The presence and value of the auxiliary basis set on this keyword line depends on the method and the specifications string, according to the rules below. The method and primary basis set are emitted verbatim as provided.

Methods that use an auxiliary basis set

For the methods RI-MP2 and DLPNO-CCSD(T), an auxiliary basis set token must appear on the keyword line, immediately after the primary basis set.

  • Explicit auxiliary basis via specifications: If specifications contains an auxiliary basis specification (a token of the form <name>/C, e.g. cc-pVDZ/C), that auxiliary basis set is used. The auxiliary basis name must be normalized to its canonical spelling regardless of the casing supplied in specifications. For example, an input of cc-pvtz/C must be emitted as cc-pVTZ/C, and cc-pVDZ/C must be emitted as cc-pVDZ/C.

For the methods MP2 and CCSD(T), no auxiliary basis set token appears on the keyword line. The keyword line contains only the method and the primary basis set, even when specifications is empty.

Primary basis cc-pVTZ, charge -1, geometry Cl.xyz, 8 processors, single-point energy:

method specifications keyword line

RI-MP2 `` (empty) !SP RI-MP2 cc-pVTZ cc-pVTZ/C
RI-MP2 cc-pVDZ/C !SP RI-MP2 cc-pVTZ cc-pVDZ/C
MP2 `` (empty) !SP MP2 cc-pVTZ
DLPNO-CCSD(T) cc-pVTZ/C !SP DLPNO-CCSD(T) cc-pVTZ cc-pVTZ/C
DLPNO-CCSD(T) `` (empty) !SP DLPNO-CCSD(T) cc-pVTZ cc-pVTZ/C
CCSD(T) `` (empty) !SP CCSD(T) cc-pVTZ

Full Input File Structure

The complete generated input for the examples above has the following structure (illustrated for RI-MP2 with a cc-pVTZ/C auxiliary basis):

!SP RI-MP2 cc-pVTZ cc-pVTZ/C
*xyz -1 1
Cl 0.0 0.0 0.0
*
%pal
nprocs 8
end

The geometry block reflects the supplied coordinates and charge/multiplicity, and the %pal block reflects the requested processor count. Whitespace/indentation differences are not significant.

  • After the molecule/coordinate specification block (and after any other calculation-specific blocks such as %geom, %output, %neb, basis set blocks, constraint blocks, etc. that precede the parallelization block).
  • Immediately before the %pal parallelization block.

The exact format of the emitted line is:

%MaxCore <value>

where <value> is the integer number of megabytes per core, with a single space between %MaxCore and the value.

Value computation

MaxCore = total_memory_in_MB / number_of_cores

Task Specification: ORCA Basis Set Generation for Custom Elements

Overview

You are modifying the ORCA input-file generation logic in the ccinput package. The change concerns how per-element custom basis sets are emitted into the %basis block of a generated ORCA input file. When a user requests a custom basis set for specific elements, the generator must decide whether to emit a compact reference to a built-in ORCA basis set or a fully explicit (expanded) basis-set definition.

Context: Public API Surface

Calculations are produced through the existing calculation-generation entry point used elsewhere in the package. A calculation is created by calling the package's generator with keyword arguments including:

  • nproc (int): number of processors.
  • type (str): calculation type, e.g. "Geometrical Optimisation".
  • file (str): geometry file name (e.g. an .xyz file whose coordinates are read).
  • software (str): here always "ORCA".
  • charge (str): overall charge, e.g. "+1".
  • method (str): e.g. "B3LYP".
  • basis_set (str): the main basis set, e.g. "6-31+G(d,p)".
  • custom_basis_sets (str): a semicolon-terminated specification mapping elements to basis sets (see below).

The generated object exposes the finished input text via its input_file attribute (a string). The behavior described below concerns only the contents of that text.

The custom_basis_sets Specification Format

The value is a string of one or more ELEMENT=BASISSET assignments, each terminated by a semicolon (;). Element symbols and basis-set names are matched case-insensitively, and basis-set names may contain internal spaces. Examples of individual assignments:

  • N=Def2-SVP;
  • I=Def2 tzvpd;
  • I=psbkjc;

Required Behavior

For each element listed in custom_basis_sets, the generator must emit an entry inside the %basis ... end block. The form of that entry depends on whether the requested basis set is one that ORCA provides as a built-in basis set.

Case 1: Built-in basis set available

When the requested basis set for an element is one that ORCA supports natively as a built-in basis set, the generator must emit a compact reference rather than expanding the basis functions explicitly. The reference has the form:

NewGTO <ELEMENT> "<CanonicalBasisName>" end
  • <ELEMENT> is the element symbol.
  • <CanonicalBasisName> is the canonical ORCA name for the basis set, quoted with double quotes.

Concrete required mappings verified for this task:

  • Requested Def2-SVP for nitrogen (N) →
    NewGTO N "Def2-SVP" end
  • Requested Def2 tzvpd for iodine (I) →
    NewGTO I "Def2-TZVPD" end

Note the canonicalization: internal spaces become hyphens and the produced name uses the exact casing shown above (e.g. Def2-TZVPD).

Associated ECP for built-in basis sets requiring an effective core potential

When the element uses an effective core potential together with the built-in basis set, an ECP reference line must also be emitted immediately after the NewGTO line, inside the same %basis block, with the form:

NewECP <ELEMENT> "<ecp-name>" end

Concrete required mapping: for iodine (I) with Def2 tzvpd, the block contains:

%basis
NewGTO I "Def2-TZVPD" end
NewECP I "def2-ECP" end
end

(No separate, expanded NewECP block with N_core/lmax/shell listings is emitted in this case.)

Case 2: Built-in basis set NOT available

When the requested basis set for an element is not a built-in ORCA basis set, the generator must emit the fully explicit basis-set definition, expanding all shells and their primitive Gaussian exponents/coefficients. This uses the block form:

newgto <ELEMENT>
<shell definitions...>
end

followed, when the element requires an effective core potential, by a separate explicit ECP block:

NewECP <ELEMENT>
N_core <n>
lmax <l>
<shell listings...>
end

The explicit expansion is the pre-existing behavior; it must remain the fallback path whenever no built-in basis set exists for the requested name. For example, requesting psbkjc for iodine (I) — which is not a built-in ORCA basis set — must produce the explicit expanded newgto I ... end block and the explicit NewECP I ... end block containing the basis primitives and ECP shell data for that basis set.

Summary of the Decision Rule

For each element in custom_basis_sets:

  1. Determine whether the requested basis set exists as a built-in ORCA basis set (matching case-insensitively, treating spaces/hyphens flexibly).
  2. If yes: emit NewGTO <ELEMENT> "<CanonicalName>" end, plus NewECP <ELEMENT> "<ecp-name>" end when an ECP is required for that element/basis.
  3. If no: emit the fully explicit newgto <ELEMENT> ... end block, plus the explicit NewECP <ELEMENT> ... end block when an ECP is required.

All emitted entries appear inside the single %basis ... end section of the ORCA input file. The remainder of the input file (header/keyword line, geometry block, %MaxCore, %pal/nprocs blocks, etc.) is unaffected by this change.

Notes on Equivalence

Whitespace and blank-line differences between the generated output and the intended output are not significant; the content and ordering of the meaningful lines is what matters.

counterpoise=2 fragments=1,1,1,1,2,2,2,2,2

When a valid counterpoise specification is provided, the generated Gaussian input file must:

  2. Geometry block: annotate each atom's element symbol with its fragment assignment using the form Element(Fragment=K), where K is the fragment number assigned to that atom. The remainder of each atom line (the XYZ coordinates) is unchanged from the normal (non-counterpoise) formatting.

For example, an atom that would normally be written as:

C   -1.31970000 -0.64380000 0.00000000

becomes:

C(Fragment=1) -1.31970000 -0.64380000 0.00000000

All other portions of the input file (checkpoint line, %nproc, %mem, title line, charge/multiplicity line, solvation sections such as Radii=bondi, trailing blank lines) follow the generator's existing formatting rules and are unaffected by the counterpoise feature except as described above.

Example (no solvation)

#p sp HF/3-21G counterpoise=2

  1. Fragment count mismatch: the number of fragment values in the fragments= list must equal the number of atoms in the molecule. If the list has more (or fewer) entries than there are atoms, this is invalid. (Interpretation: exactly one fragment must be assigned to each atom.)

  2. Counterpoise/fragment-total mismatch: the integer N in counterpoise=N must equal the number of distinct fragments actually used in the fragments= list. If they differ, this is invalid.
