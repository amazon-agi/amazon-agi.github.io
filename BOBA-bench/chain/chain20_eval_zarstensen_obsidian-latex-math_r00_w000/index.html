01 Backend for Evaluating LaTeX Expressions 812 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Backend for Evaluating LaTeX Expressions

Summary

Your task is to implement a Python backend that evaluates mathematical expressions written in LaTeX and returns the results in symbolic form. This backend has three parts: a response interface, an abstract base class for responses, and an asynchronous mode function called "evaluate". SymPy is the library used for the computation.

Directory Layout and Import Paths

All the code sits under src/evaluator/. When tests are executed, src/evaluator/ is on the import path (in other words, imports are rooted at that directory). The import paths below must resolve exactly:

  • from ModeResponse import ModeResponse — backed by a module ModeResponse.py at the evaluator root, in which class ModeResponse is defined.
  • from modes.EvaluateMode import evaluateMode — backed by a modes package that contains EvaluateMode.py and exposes a callable evaluateMode.

You may arrange the supporting code (LaTeX parsing, environment handling, etc.) however you prefer, provided the imports above work and the behavior described below holds.

ModeResponse (the abstract response interface)

In ModeResponse.py, define a class named ModeResponse. This class is the response interface that mode functions rely on when reporting results, errors, and warnings. It must be subclassable, and it must expose the asynchronous methods below (a subclass overrides these / a caller invokes them):

  • async def error(self, message)
  • async def warn(self, message)
  • async def result(self, result: Any, status: str = 'success', metadata: dict = {})

There is no requirement for these methods to return anything meaningful. ModeResponse acts as the base type; the concrete behavior comes from subclasses. It must be possible to import it and to use it as a base class, with the exact method names and signatures given above.

The evaluateMode function

The signature:

async def evaluateMode(message: dict, response: ModeResponse)

The message argument is a dictionary, and it contains these keys:

  • "expression": a string that holds a mathematical expression formatted in LaTeX.
  • "environment": a dictionary that describes the evaluation environment. For this task, it may be an empty dictionary {}.

How it behaves:

  1. The LaTeX string found under "expression" is parsed into a SymPy expression.
  2. Next, the parsed expression is evaluated/simplified.
  3. The outcome is reported by awaiting response.result(...).
Payload of the result

Whenever evaluation succeeds, the function must await response.result(result=...), passing a SymPy Eq object (an equality) as the result argument. In the resulting equation, the right-hand side (.rhs) must be the evaluated/simplified value of the input expression.

In concrete terms:

  • When a scalar expression simplifies to a value, the Eq that is produced must be an equality whose right-hand side is equal to that value. As an example, evaluating "1+1" yields an Eq equivalent to Eq(2, 2) — that is, both sides are equal to the simplified value 2. (Even when SymPy automatic evaluation is disabled, this equivalence must hold — the equation is literally an equality of the simplified value to itself.)
  • When the expression simplifies to a matrix, the right-hand side of the Eq must equal the resulting SymPy Matrix.
Requirements for LaTeX parsing

The parser must handle at least the following correctly:

  1. Basic arithmetic: 1+1 simplifies to 2.

  2. Escaped LaTeX spaces: the token \ (a backslash followed by a space) is a LaTeX spacing command, so it must be treated as whitespace / ignored, not as a syntax error. To illustrate, 1\ + \ 1 must parse and evaluate the same as 1 + 1 → 2.

  3. Matrices via bmatrix: an environment written as \begin{bmatrix} ... \end{bmatrix}, whose rows are separated by \\, must parse into a SymPy column/row Matrix. Multiplication by a scalar with \cdot must work. To give an example, 2 \cdot \begin{bmatrix} 1 \\ 1 \end{bmatrix} must evaluate so that .rhs equals 2 * Matrix([[1], [1]]).

  4. Multi-line input: the expression string may contain arbitrary newlines embedded in it, along with surrounding and internal whitespace and indentation. Newlines, as well as extra whitespace between tokens, must not affect parsing. If the matrix example above is written in multi-line form, it must produce the same result as in the single-line form. Note too that a row separator \\ must still be recognized correctly and must not be corrupted/truncated when the input spans multiple lines.

How results are reported

Once the evaluation has succeeded, exactly one call to response.result(...) must be awaited, and the Eq object is what gets passed as the result argument. In these cases, using the defaults for status ('success') and metadata ({}) is acceptable.

The function is asynchronous; it must be runnable via asyncio.run(evaluateMode(...)).

SymPy

Symbolic parsing and computation must be done with SymPy. The results (.rhs, equation operands) must be genuine SymPy objects (Eq, Matrix, numeric SymPy values), so that they compare equal to SymPy objects constructed independently, such as Eq(2, 2) and 2 * Matrix([[1], [1]]).

Required New Behavior for Parsing/Evaluation

The LaTeX parser must be extended so that it recognizes the following constructs. Leading and trailing whitespace, as well as newlines within the expressions, must be tolerated (expressions may span multiple lines and be indented).

A. Norm of a Vector / Matrix — \Vert ... \Vert

The delimiters \Vert x \Vert stand for the Euclidean (L2) norm of the matrix/vector enclosed between them.

  • When a column vector \begin{bmatrix} a \\ b \\ ... \end{bmatrix} is enclosed in \Vert ... \Vert, the evaluated result must equal the square root of the sum of the squares of its components, i.e. sqrt(a**2 + b**2 + ...).

Example: for a column vector with entries 20, 30, 40, 50, the norm must evaluate to sqrt(20**2 + 30**2 + 40**2 + 50**2).

The bra-ket-style delimiters \langle u | v \rangle denote the inner (dot) product of the two vectors; here, u and v are matrices/vectors separated by a |.

  • Given two column vectors \langle \begin{bmatrix} a \\ b \end{bmatrix} | \begin{bmatrix} c \\ d \end{bmatrix} \rangle, the evaluated result must equal a*c + b*d (component-wise product summed).

Example: for the column vectors [1, 2] and [2, 4], the inner product must evaluate to 1*2 + 2*4.

Restrictions

  • Matrix parsing in its existing form (\begin{bmatrix} ... \end{bmatrix} producing SymPy Matrix objects) must continue to work.
  • Evaluation behavior that already exists for expressions supported previously must be preserved (e.g., a matrix-valued expression must still evaluate correctly, such as producing 2 * Matrix([[1], [1]])).
  • SymPy's S.Pi must be what the mathematical constant \pi maps to.

Criteria for Success

  • ObsimatEnvironmentUtils.parse_latex(r"\pi", {}) is equal to S.Pi.
  • Norms of column vectors written with \Vert ... \Vert are evaluated correctly by evaluateMode.
  • Inner products of column vectors written with \langle u | v \rangle are evaluated correctly by evaluateMode.
  • All results can be accessed through the response object's hasResult() / getResult() interface, with the numeric/symbolic value located on the .rhs attribute of result["result"].

Task Specification: LaTeX Expression Parsing

Objective

The task is to implement a static method that parses LaTeX mathematical expressions into SymPy expression objects.

Public API

Define a class ObsimatEnvironmentUtils (importable as it currently is within the src/evaluator package — keep the existing import path intact so that from ... import ObsimatEnvironmentUtils continues to work) exposing the static method:

@staticmethod
def parse_latex(latex: str, environment: dict) -> sympy expression
  • latex: a string holding a LaTeX mathematical expression.
  • environment: a dictionary of contextual parameters (it may be empty; it is not otherwise exercised here).
  • Returns: a SymPy expression object that is equal (via SymPy equality) to the mathematical meaning of the input.

Behavior Requirements

The parser must translate the following categories of LaTeX input correctly.

1. Mathematical Constants

Recognize the following single-token constants and map each one to its SymPy equivalent:

  • \pi → S.Pi
  • e → S.Exp1 (Euler's number)
  • i → I (imaginary unit)
2. Function Application and Precedence Rules

Functions of the trigonometric (and analogous) kind, such as \sin, must be parsed with correct argument binding and operator precedence:

  • \sin(a) - b → sin(a) - b — the function binds its parenthesized argument only; the terms after it are separate.
  • \sin(5) - 75 → sin(5) - 75
  • \sin(a - b) → sin(a - b) — the argument is the full parenthesized expression.
  • \sin(a - b) - c → sin(a - b) - c
  • (\sin(a) - b)^2 + c + (\sin(b) - a) → (sin(a) - b)**2 + c + sin(b) - a
  • \sin a \cdot b - c → sin(a) * b - c — when no parentheses/braces follow, the function takes as its argument the single atom that immediately follows.
  • \sin{a \cdot b} - c → sin(a * b) - c — a braced group that follows the function is taken as its full argument.
3. Implicit Multiplication

When terms are juxtaposed without an explicit operator between them, that juxtaposition must be interpreted as multiplication.

Symbols and numbers:

  • 2 a → 2 * a
  • a b → a * b
  • a b c → a * b * c
  • a b \cdot c → a * b * c
  • a \cdot b c → a * b * c

Functions that are juxtaposed with symbols:

  • b \sin(a) → sin(a) * b
  • \sin(a) b → sin(a) * b

Fractions that are juxtaposed with symbols:

  • \frac{a}{b} c → a / b * c
  • c \frac{a}{b} → a / b * c

Matrices:

  • A matrix juxtaposed with another matrix multiplies the two: \begin{bmatrix} 10 \\ 20 \end{bmatrix} \begin{bmatrix} 30 & 40 \end{bmatrix} → Matrix([[10], [20]]) * Matrix([[30, 40]])
  • A symbol juxtaposed with a matrix (in either order) yields scalar multiplication:
    • a \begin{bmatrix} 30 & 40 \end{bmatrix} → a * Matrix([[30, 40]])
    • \begin{bmatrix} 30 & 40 \end{bmatrix} a → a * Matrix([[30, 40]])
4. Support for Matrices

LaTeX bmatrix environments (\begin{bmatrix} ... \end{bmatrix}) must be parsed into SymPy Matrix objects:

  • Rows are delimited by \\.
  • Within a row, columns are delimited by &.
  • Whitespace and newlines occurring within the matrix body must be tolerated and ignored.

Notes

  • All returned expressions must compare equal (using SymPy equality semantics) to the SymPy constructions described above.
  • Within one expression, explicit multiplication via \cdot and implicit juxtaposition must interoperate freely.

Task Specification: Fixing Implicit Multiplication in LaTeX Parsing

Overview

You must ensure that implicit multiplication — terms placed next to each other with no explicit multiplication operator between them — is parsed correctly for LaTeX expressions that involve powers and subscripted symbols.

Public API

It must be possible to import and call the following:

  • Module: ObsimatEnvironmentUtils (accessible in the evaluator environment, and it matches the existing import path used elsewhere in the codebase).
  • Method: ObsimatEnvironmentUtils.parse_latex(latex_string: str, environment: dict) -> sympy expression
    • latex_string: a LaTeX string in raw form.
    • environment: a dictionary (it may be empty, {}).
    • The return value is a SymPy expression that equals the parsed mathematical meaning of the LaTeX input.

The value that is returned must compare equal (==) to the corresponding SymPy expression constructed from sympy symbols.

Required Behavior

Whenever two mathematical terms sit next to each other in the LaTeX string, with only whitespace separating them, they must be interpreted as being multiplied together (implicit multiplication). This must hold no matter how the terms are ordered, and specifically in the following cases:

Powers

For the symbols a and b:

  • Parsing "b a^2" must produce an expression equal to a**2 * b.
  • Parsing "a^2 b" must produce an expression equal to a**2 * b.

In other words, when a base-and-exponent term is adjacent to another symbol (on either side), the two are multiplied.

Subscripted Symbols

A symbol with a subscript, such as x_1, must be parsed as one single SymPy symbol whose name is x_{1} (i.e., symbols("x_{1}")).

Using the symbol b together with the subscripted symbol x1 = symbols("x_{1}"):

  • Parsing "b x_1" must produce an expression equal to x1 * b.
  • Parsing "x_1 b" must produce an expression equal to x1 * b.

In other words, when a subscripted symbol is adjacent to another symbol (on either side), the two are multiplied.

Notes

  • The symbols used earlier (a, b) are ordinary single-letter SymPy symbols.
  • Because multiplication is commutative in SymPy, the ordering of operands in the result has no effect on equality.
  • The empty environment dictionary must not prevent parsing; the symbols are inferred directly from the LaTeX input.

Task Specification: Domain Restriction for Solutions in Solve Mode

Goal

Implement (or extend) an asynchronous solve-mode handler that solves a LaTeX equation with respect to its unknown symbol, with the ability to confine the solution set to a specified domain supplied through the environment configuration.

Public API

Provide a callable that can be imported as:

from modes.SolveMode import solveMode
Function Signature
async def solveMode(message: dict, response) -> None
  • solveMode is an async coroutine (that is, it must be awaitable / runnable via asyncio.run).
  • message is a dictionary that describes the equation to solve and its environment.
  • response is a response object (see "Response Object Contract") onto which results are recorded.

Input Structure

The message dictionary holds:

  • "expression" — a string holding a LaTeX representation of an equation. An equality may be included (e.g. \sin(x) = 0). The expression contains exactly one free symbol, and this symbol is the one to solve for.
  • "environment" — a dictionary describing the environment for solving. It may contain:
    • "domain" — (optional) a string which, when evaluated in a SymPy context, gives a SymPy set describing the domain to which solutions must be restricted. For example, the string "Interval.Ropen(0, 2 * pi)" represents the half-open interval [0, 2π). Identifiers such as Interval and pi, along with other standard SymPy names, are available in the evaluation context.

Behavior Requirements

  1. Parse the LaTeX given in "expression" into a SymPy equation/expression and identify the single free symbol that is to be solved for.

  2. If a "domain" is supplied in the environment, evaluate that string into a SymPy set and restrict the solution set to that domain. The solution returned must be the set of values within the specified domain that satisfy the equation.

  3. Solve the equation with respect to the free symbol. When a domain is supplied, only solutions that lie within that domain are included.

    Example: solving \sin(x) = 0 over the domain Interval.Ropen(0, 2 * pi) produces the solution set FiniteSet(0, pi).

  4. When solving succeeds, record the result on the response object (see below).

Response Object Contract

The response object offers at least the following methods:

  • hasResult() -> bool — returns True as soon as a result has been recorded.
  • getResult() -> dict — returns the result payload that was recorded.

After the equation has been solved successfully, the recorded result payload must match the following structure:

{
    "result": {
        "symbol":   <the SymPy Symbol solved for>,
        "solution": <the SymPy set of solutions>
    }
}
  • getResult()["result"]["symbol"] must equal the SymPy symbol that appears in the expression (e.g. Symbol('x')).
  • getResult()["result"]["solution"] must equal the SymPy solution set, restricted to the domain when one is supplied (e.g. FiniteSet(0, pi)).

Remarks

  • The solution is compared by means of SymPy value equality, so the returned solution must be a genuine SymPy set object (e.g. a FiniteSet), not a string or list.
  • Throughout, the constructs used are standard SymPy ones (symbols, sin, pi, Interval, FiniteSet, etc.).
06 Support for Multi-Expression Environments 1469 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Support for Multi-Expression Environments

Overview

You must implement a LaTeX parser class and update the two operation modes (evaluate and solve) so that they support parsing and processing of multiple expressions grouped in LaTeX environments (such as align and cases), as well as relational expressions. Part of this task is introducing a container type for holding multiple parsed expressions together with their source locations.

Public API Requirements

1. grammar.ObsimatLatexParser.ObsimatLatexParser

A class whose job is to parse LaTeX math strings into SymPy objects.

  • Constructor: ObsimatLatexParser() — takes no required arguments.
  • Method: doparse(self, latex: str) — parses the supplied LaTeX string and returns either a single SymPy expression/relation or, when the input contains more than one top-level expression, a SystemOfExpr (described below).
2. grammar.SystemOfExpr.SystemOfExpr

A container type that represents an ordered collection of parsed expressions, each one with an associated source location.

The required interface is:

  • len(system_of_expr) — returns the number of expressions the collection holds.
  • get_expr(self, index: int) — returns the SymPy expression/relation at the supplied zero-based index.
  • get_location(self, index: int) — returns a location object for the expression at the supplied index. The location object must expose:
    • .line — the 1-based line number (relative to the parsed input string) at which the expression begins.
    • .end_line — the 1-based line number at which the expression ends.
  • get_all_expr(self) — returns a tuple of all expressions, in order.

Behavior of the Parser (doparse)

Single expressions
  • A plain expression is parsed into its SymPy equivalent (e.g. constants \pi → S.Pi, e → S.Exp1, i → I).
  • Parsing of implicit multiplication, ambiguous function calls, fractions, matrices, powers, and subscripted symbols must be consistent with standard SymPy interpretation. Examples:
    • \sin a \cdot b - c → sin(a)*b - c
    • \sin{a \cdot b} - c → sin(a*b) - c
    • a b c → a*b*c
    • \frac{a}{b} c → a/b*c
    • b x_1 → Symbol("x_{1}")*b
    • \begin{bmatrix} 1 & 2 \\ 3 & 4 \end{bmatrix} → Matrix([[1, 2], [3, 4]])
Single relations
  • A relation like x=y parses into the corresponding SymPy relational (Eq(x, y)).
Chained relations
  • A chain made up of two or more relations (e.g. x = y < z) parses to a SystemOfExpr. One relation is formed from each adjacent pair of operands, in order. For x = y < z, the result contains two entries: Eq(x, y) and Lt(y, z).
Partial relations

The parser must accept relations in which the left- or right-hand side is missing, as well as relations that use alignment ampersands (&) of the kind found in aligned environments:

  • = 25 → a relation for which .rhs is 25.
  • x = → a relation for which .lhs is x.
  • x =& → a relation for which .lhs is x.
  • &=& 25 → a relation for which .rhs is 25.
  • Ordinary relations must not be broken by ampersands: x & = & y → Eq(x, y).
Multi-expression environments

If the input contains a LaTeX environment that has multiple rows (rows separated by \\), such as align or cases, the parser returns a SystemOfExpr with one entry per row.

  • Every row is parsed independently into its expression/relation.
  • Alignment ampersands (&) within rows are ignored when the expression is formed.
  • Location tracking: the .line and .end_line values of each entry must reflect the 1-based line numbers within the input string at which that row's content appears.

Example — for the input:

\begin{align}
x & = 2y 5z \\
y & = x^2 \\
z & = x + 2\frac{y}{x} \\
\end{align}

(with \begin{align} on line 2 of the raw string, i.e. a leading newline is present) the result is a SystemOfExpr of length 3:

  • index 0: Eq(x, 2*y*5*z) — location line 3, end_line 3
  • index 1: Eq(y, x**2) — location line 4, end_line 4
  • index 2: Eq(z, x + 2*y/x) — location line 5, end_line 5

An environment with a single row still yields a SystemOfExpr of length 1:

  • \begin{cases} x \end{cases} (with \begin{cases} on line 2, x on line 3) → SystemOfExpr of length 1, whose entry is x at location line 3.
  • \begin{cases} x & = 2y \end{cases} → SystemOfExpr of length 1, whose entry is Eq(x, 2*y) at location line 3.

Signature

modes.EvaluateMode.evaluateMode(message: dict, response, parser) — an async coroutine (awaitable via asyncio.run). It accepts, as its third parameter, an ObsimatLatexParser instance to use for parsing.

Input

message is a dict that contains:

  • "expression": the LaTeX string that is to be evaluated.
  • "environment": a dict describing the environment (may be empty).
Behavior
  • The expression is parsed with the provided parser.
  • After processing is complete, the response must carry a result (retrievable and non-empty).
  • The result object is a dict. result['result'] holds the evaluated relation object — an object whose .rhs attribute equals the evaluated value.

The following specific outcomes are required:

  • 1+1 → the result's .rhs equals 2.
  • 1\ + \ 1 (escaped spaces) → the result's .rhs equals 2.
  • 2 \cdot \begin{bmatrix} 1 \\ 1 \end{bmatrix} → the result's .rhs equals Matrix([[2],[2]]) (evaluated scalar–matrix product).
  • Norm and inner-product expressions evaluate to their scalar results (e.g. an inner product of [1,2] and [?,4] giving 1*2 + 2*4).
Evaluating relations and multi-expression inputs

If the input is a chain of relations or a multi-expression environment, evaluate mode evaluates the last expression, and the result's .rhs equals the value produced by evaluating that last expression:

  • 5 + 5 + 5 + 5 = 10 + 10 → .rhs equals 20.
  • a = b = (a - b)^2 → .rhs equals a**2 + b**2 - 2*a*b.
  • 1 = 2 = 1 → .rhs equals 1.
  • For the environment:
    \begin{cases}
2 + 2 + 2 + 2 &= 4 + 2 + 2 \\
              &= 4 + 4
\end{cases}
    → .rhs equals 8.
Metadata

For inputs that are multi-expression environments, the result dict must also contain result['metadata'] — a dict with the keys 'start_line' and 'end_line', giving the 1-based line numbers of the evaluated (last) expression within the input string. In the cases example above, start_line and end_line both equal 4.

Signature

modes.SolveMode.solveMode(message: dict, response, parser) — an async coroutine (awaitable via asyncio.run). It accepts, as its third parameter, an ObsimatLatexParser instance.

Input

message is a dict that contains:

  • "expression": the LaTeX string holding one equation, a chain of relations, or a multi-expression environment (a system of equations).
  • "environment": a dict that may contain a "domain" key; when that key is present, its value is a string expressing a SymPy set/domain (e.g. "Interval.Ropen(0, 2 * pi)") that constrains the solution set.
  • "symbols" (optional): a list of variable name strings that indicates which symbols to solve for.
Behavior
  • The expression is parsed with the provided parser.
  • The response must carry a result. The dict result['result'] contains:
    • 'symbols': the list of SymPy symbols that were solved for, in order.
    • 'solution': the SymPy solution set.
Single equation with domain
  • For \sin(x) = 0 with domain Interval.Ropen(0, 2 * pi), symbols equals [x] and solution equals FiniteSet(0, pi).
System of equations

If the expression is a multi-expression environment, all of its equations are solved together as a system.

  • This align system:
    x + y + z = 5
2x + 5z = 10
2y + x = 3
    → solution equals FiniteSet((15, -6, -4)).
  • The following align system:
    3*x^2 = 2*y

    → solution equals FiniteSet((0, 0), (1, Rational(3, 2))).
Explicit solve-for symbols

\begin{cases}

x - y = -z \\
\end{cases}
  • with "symbols": ["x", "y"] → symbols equals [x, y] and solution equals FiniteSet((0, z)).

Notes

  • The response object supports, at minimum: recording a result, checking whether a result is present, retrieving the result, and resetting to a no-result state so it can be reused across successive calls.
  • Throughout this specification, line numbers are 1-based and are measured relative to the raw input string passed to doparse/the mode (including any leading newline in a multi-line raw string).

Task Specification for the Convert-to-Sympy Mode

Overview

A new mode function is to be implemented: it parses a mathematical expression formatted in LaTeX into a SymPy expression and returns that expression as a result through a response object.

Public API to Be Implemented

Module: modes.ConvertSympyMode

At the import path given above, create a module that exposes a single asynchronous function:
