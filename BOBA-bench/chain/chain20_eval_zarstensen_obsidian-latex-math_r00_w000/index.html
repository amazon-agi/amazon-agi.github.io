Task Specification: LaTeX Expression Evaluator Backend

Overview

Implement a Python backend that evaluates mathematical LaTeX expressions and returns symbolic results. The backend consists of a response interface, an abstract response base class, and an asynchronous "evaluate" mode function. Computation is performed using the SymPy library.

Directory Structure and Import Layout

The code lives under src/evaluator/. Tests are run with src/evaluator/ on the import path (i.e., that directory is the root for imports). The following import paths must resolve exactly:

  • from ModeResponse import ModeResponse — module ModeResponse.py at the evaluator root, defining class ModeResponse.
  • from modes.EvaluateMode import evaluateMode — a modes package containing EvaluateMode.py, exposing a callable evaluateMode.

You may organize supporting code (LaTeX parsing, environment handling, etc.) however you like, as long as the above imports work and the behavior below holds.

ModeResponse (abstract response interface)

Define a class ModeResponse in ModeResponse.py. It defines the response interface used by mode functions to report results, errors, and warnings. It must be subclassable and expose the following asynchronous methods (these are the methods a subclass overrides / a caller invokes):

  • async def error(self, message)
  • async def warn(self, message)
  • async def result(self, result: Any, status: str = 'success', metadata: dict = {})

These methods do not need to return anything meaningful. ModeResponse serves as the base type; the concrete behavior is provided by subclasses. It must be importable and usable as a base class with the exact method names and signatures above.

evaluateMode function

Signature:

async def evaluateMode(message: dict, response: ModeResponse)

message is a dictionary with these keys:

  • "expression": a string containing a LaTeX-formatted mathematical expression.
  • "environment": a dictionary describing the evaluation environment. For this task it may be an empty dictionary {}.

Behavior:

  1. Parse the LaTeX string in "expression" into a SymPy expression.
  2. Evaluate/simplify the parsed expression.
  3. Report the outcome by awaiting response.result(...).
Result payload

When evaluation succeeds, the function must await response.result(result=...) where the result argument is a SymPy Eq object (an equality). The equation's right-hand side (.rhs) must be the evaluated/simplified value of the input expression.

Concretely:

  • For a scalar expression that simplifies to a value, the produced Eq must be an equality whose right-hand side equals that value. For example, evaluating "1+1" yields an Eq equivalent to Eq(2, 2) — i.e. both sides equal the simplified value 2. (This equivalence must hold even when SymPy automatic evaluation is disabled, meaning the equation is literally an equality of the simplified value to itself.)
  • For an expression that simplifies to a matrix, the right-hand side of the Eq must equal the resulting SymPy Matrix.
LaTeX parsing requirements

The parser must correctly handle at least the following:

  1. Basic arithmetic: 1+1 → simplifies to 2.

  2. Escaped LaTeX spaces: the token \ (backslash followed by a space) is a LaTeX spacing command and must be treated as whitespace / ignored, not as a syntax error. For example, 1\ + \ 1 must parse and evaluate the same as 1 + 1 → 2.

  3. Matrices via bmatrix: the \begin{bmatrix} ... \end{bmatrix} environment with rows separated by \\ must parse into a SymPy column/row Matrix. Scalar multiplication with \cdot must work. For example, 2 \cdot \begin{bmatrix} 1 \\ 1 \end{bmatrix} must evaluate so that .rhs equals 2 * Matrix([[1], [1]]).

  4. Multi-line input: the expression string may contain arbitrary embedded newlines and surrounding/internal whitespace and indentation. Newlines and extra whitespace between tokens must not affect parsing. The multi-line form of the matrix example above must produce the same result as the single-line form. Note that a row separator \\ must still be recognized correctly and must not be corrupted/truncated when the input spans multiple lines.

Result reporting

After a successful evaluation, exactly one call to response.result(...) must be awaited, with the Eq object passed as the result argument. The default status ('success') and default metadata ({}) are acceptable for these cases.

The function is asynchronous and must be runnable via asyncio.run(evaluateMode(...)).

SymPy

Use SymPy for symbolic parsing and computation. Results (.rhs, equation operands) must be genuine SymPy objects (Eq, Matrix, numeric SymPy values) so that they compare equal to independently constructed SymPy objects such as Eq(2, 2) and 2 * Matrix([[1], [1]]).

Task Specification: LaTeX Expression Parser

Objective

Implement a static method that parses LaTeX mathematical expressions into SymPy expression objects.

Public API

Create a class ObsimatEnvironmentUtils (importable as it currently is in the src/evaluator package — preserve the existing import path so that from ... import ObsimatEnvironmentUtils continues to work) exposing the static method:

@staticmethod
def parse_latex(latex: str, environment: dict) -> sympy expression
  • latex: a string containing a LaTeX mathematical expression.
  • environment: a dictionary of contextual parameters (may be empty; not otherwise exercised here).
  • Returns: a SymPy expression object equal (via SymPy equality) to the mathematical meaning of the input.

Required Behavior

The parser must correctly translate the following categories of LaTeX input.

1. Mathematical Constants

Recognize these single-token constants and map them to their SymPy equivalents:

  • \pi → S.Pi
  • e → S.Exp1 (Euler's number)
  • i → I (imaginary unit)
2. Function Application and Precedence

Trigonometric (and analogous) functions such as \sin must be parsed with correct argument binding and operator precedence:

  • \sin(a) - b → sin(a) - b — the function binds only its parenthesized argument; subsequent terms are separate.
  • \sin(5) - 75 → sin(5) - 75
  • \sin(a - b) → sin(a - b) — the full parenthesized expression is the argument.
  • \sin(a - b) - c → sin(a - b) - c
  • (\sin(a) - b)^2 + c + (\sin(b) - a) → (sin(a) - b)**2 + c + sin(b) - a
  • \sin a \cdot b - c → sin(a) * b - c — when no parentheses/braces follow, the function takes the single immediately-following atom as its argument.
  • \sin{a \cdot b} - c → sin(a * b) - c — a braced group following the function becomes its full argument.
3. Implicit Multiplication

Juxtaposition of terms without an explicit operator must be interpreted as multiplication.

Symbols and numbers:

  • 2 a → 2 * a
  • a b → a * b
  • a b c → a * b * c
  • a b \cdot c → a * b * c
  • a \cdot b c → a * b * c

Functions juxtaposed with symbols:

  • b \sin(a) → sin(a) * b
  • \sin(a) b → sin(a) * b

Fractions juxtaposed with symbols:

  • \frac{a}{b} c → a / b * c
  • c \frac{a}{b} → a / b * c

Matrices:

  • A matrix juxtaposed with another matrix multiplies them: \begin{bmatrix} 10 \\ 20 \end{bmatrix} \begin{bmatrix} 30 & 40 \end{bmatrix} → Matrix([[10], [20]]) * Matrix([[30, 40]])
  • A symbol juxtaposed with a matrix (in either order) yields scalar multiplication:
    • a \begin{bmatrix} 30 & 40 \end{bmatrix} → a * Matrix([[30, 40]])
    • \begin{bmatrix} 30 & 40 \end{bmatrix} a → a * Matrix([[30, 40]])
4. Matrix Support

Parse LaTeX bmatrix environments (\begin{bmatrix} ... \end{bmatrix}) into SymPy Matrix objects:

  • Rows are separated by \\.
  • Columns within a row are separated by &.
  • Whitespace and newlines within the matrix body must be tolerated and ignored.

Notes

  • All returned expressions must compare equal (using SymPy equality semantics) to the described SymPy constructions.
  • Explicit multiplication \cdot and implicit juxtaposition must interoperate freely within one expression.

Overview

You must ensure that implicit multiplication (juxtaposition of terms without an explicit multiplication operator) is correctly parsed for LaTeX expressions involving powers and subscripted symbols.

Public API

The following must be importable and callable:

  • Module: ObsimatEnvironmentUtils (accessible in the evaluator environment, matching the existing import path used elsewhere in the codebase).

    • environment: a dictionary (may be empty, {}).

The returned value must compare equal (==) to the corresponding SymPy expression constructed from sympy symbols.

Required Behavior

When two mathematical terms appear adjacent to one another in the LaTeX string, separated only by whitespace, they must be interpreted as being multiplied together (implicit multiplication). This must work regardless of the ordering of the terms and specifically in the following cases:

Powers

Given symbols a and b:

  • Parsing "b a^2" must produce the expression equal to a**2 * b.
  • Parsing "a^2 b" must produce the expression equal to a**2 * b.

That is, a base-and-exponent term adjacent to another symbol (on either side) multiplies the two.

A symbol with a subscript, such as x_1, must be parsed as a single SymPy symbol named x_{1} (i.e., symbols("x_{1}")).

  • Parsing "b x_1" must produce the expression equal to x1 * b.
  • Parsing "x_1 b" must produce the expression equal to x1 * b.

That is, a subscripted symbol adjacent to another symbol (on either side) multiplies the two.

Notes

  • Symbols referenced above (a, b) are ordinary single-letter SymPy symbols.
  • Multiplication is commutative in SymPy, so operand ordering in the result does not affect equality.
  • The empty environment dictionary must not prevent parsing; symbols are inferred directly from the LaTeX input.

Objective

Implement (or extend) an asynchronous solve-mode handler that solves a LaTeX equation for its unknown symbol, with the ability to restrict the solution set to a specified domain provided through the environment configuration.

Public API

Create a callable importable as:

from modes.SolveMode import solveMode
Signature
async def solveMode(message: dict, response) -> None
  • solveMode is an async coroutine (it must be awaitable / runnable via asyncio.run).
  • message is a dictionary describing the equation to solve and its environment.
  • response is a response object (see "Response Object Contract") onto which results are recorded.

Input Format

The message dictionary contains:

  • "expression" — a string containing a LaTeX representation of an equation. This may include an equality (e.g. \sin(x) = 0). The expression contains exactly one free symbol, which is the symbol to solve for.
  • "environment" — a dictionary describing the solving environment. It may contain:
    • "domain" — (optional) a string that, when evaluated in a SymPy context, produces a SymPy set describing the domain to which solutions must be restricted. For example, the string "Interval.Ropen(0, 2 * pi)" denotes the half-open interval [0, 2π). Names such as Interval, pi, and other standard SymPy names are available in the evaluation context.

Required Behavior

  1. Parse the LaTeX "expression" into a SymPy equation/expression and identify the single free symbol to solve for.

  2. If a "domain" is provided in the environment, evaluate that string into a SymPy set and restrict the solution set to that domain. The returned solution must be the set of values within the specified domain that satisfy the equation.

  3. Solve the equation for the free symbol. When a domain is supplied, only solutions lying within that domain are included.

    Example: solving \sin(x) = 0 over the domain Interval.Ropen(0, 2 * pi) yields the solution set FiniteSet(0, pi).

  4. Record a successful result on the response object (see below).

Response Object Contract

The response object supports at least the following methods:

  • hasResult() -> bool — returns True once a result has been recorded.
  • getResult() -> dict — returns the recorded result payload.

Upon successful solving, the recorded result payload must have the following structure:

{
    "result": {
        "symbol":   <the SymPy Symbol solved for>,
        "solution": <the SymPy set of solutions>
    }
}
  • getResult()["result"]["symbol"] must equal the SymPy symbol appearing in the expression (e.g. Symbol('x')).
  • getResult()["result"]["solution"] must equal the SymPy solution set, restricted to the domain when one is given (e.g. FiniteSet(0, pi)).

Notes

  • The comparison of the solution is by SymPy value equality, so the returned solution must be a genuine SymPy set object (e.g. a FiniteSet), not a string or list.
  • Standard SymPy constructs (symbols, sin, pi, Interval, FiniteSet, etc.) are used throughout.

Task Specification: Multi-Expression Environment Support

Overview

You must implement a LaTeX parser class and update two operation modes (evaluate and solve) to support parsing and processing multiple expressions grouped in LaTeX environments (such as align and cases), as well as relational expressions. This includes introducing a container type for holding multiple parsed expressions along with their source locations.

Required Public API

1. grammar.ObsimatLatexParser.ObsimatLatexParser

A class that parses LaTeX math strings into SymPy objects.

  • Constructor: ObsimatLatexParser() — takes no required arguments.
  • Method: doparse(self, latex: str) — parses the given LaTeX string and returns either a single SymPy expression/relation, or a SystemOfExpr (described below) when the input contains more than one top-level expression.
2. grammar.SystemOfExpr.SystemOfExpr

A container type representing an ordered collection of parsed expressions, each with an associated source location.

Required interface:

  • len(system_of_expr) — returns the number of expressions in the collection.
  • get_expr(self, index: int) — returns the SymPy expression/relation at the given zero-based index.
  • get_location(self, index: int) — returns a location object for the expression at the given index. The location object must expose:
    • .line — the 1-based line number (relative to the parsed input string) where the expression begins.
    • .end_line — the 1-based line number where the expression ends.
  • get_all_expr(self) — returns a tuple of all expressions in order.

Parser Behavior (doparse)

Single expressions
  • A plain expression parses to its SymPy equivalent (e.g. constants \pi → S.Pi, e → S.Exp1, i → I).
  • Implicit multiplication, ambiguous function calls, fractions, matrices, powers, and subscripted symbols must parse consistently with standard SymPy interpretation. Examples:
    • \sin a \cdot b - c → sin(a)*b - c
    • \sin{a \cdot b} - c → sin(a*b) - c
    • a b c → a*b*c
    • \frac{a}{b} c → a/b*c
    • b x_1 → Symbol("x_{1}")*b
    • \begin{bmatrix} 1 & 2 \\ 3 & 4 \end{bmatrix} → Matrix([[1, 2], [3, 4]])
Single relations
  • A relation such as x=y parses to the corresponding SymPy relational (Eq(x, y)).
Chained relations
  • A chain of two or more relations (e.g. x = y < z) parses to a SystemOfExpr. Each adjacent pair of operands forms one relation in order. For x = y < z the result contains two entries: Eq(x, y) and Lt(y, z).
Partial relations

The parser must accept relations with a missing left- or right-hand side, and relations using alignment ampersands (&) as found in aligned environments:

  • = 25 → a relation whose .rhs is 25.
  • x = → a relation whose .lhs is x.
  • x =& → a relation whose .lhs is x.
  • &=& 25 → a relation whose .rhs is 25.
  • Ampersands must not break ordinary relations: x & = & y → Eq(x, y).
Multi-expression environments

When the input contains a LaTeX environment with multiple rows (rows separated by \\), such as align or cases, the parser returns a SystemOfExpr with one entry per row.

  • Each row is parsed independently to its expression/relation.
  • Alignment ampersands (&) within rows are ignored for the purpose of forming the expression.
  • Location tracking: each entry's .line and .end_line must reflect the 1-based line numbers within the input string where that row's content appears.

Example — for input:

\begin{align}
x & = 2y 5z \\
y & = x^2 \\
z & = x + 2\frac{y}{x} \\
\end{align}

(where \begin{align} is on line 2 of the raw string, i.e. there is a leading newline) the result is a SystemOfExpr of length 3:

  • index 0: Eq(x, 2*y*5*z), location line 3, end_line 3
  • index 1: Eq(y, x**2), location line 4, end_line 4
  • index 2: Eq(z, x + 2*y/x), location line 5, end_line 5

A single-row environment still yields a SystemOfExpr of length 1:

  • \begin{cases} x \end{cases} (with \begin{cases} on line 2, x on line 3) → SystemOfExpr of length 1 whose entry is x at location line 3.
  • \begin{cases} x & = 2y \end{cases} → SystemOfExpr of length 1 whose entry is Eq(x, 2*y) at location line 3.
