y

execute takes the full source text of a tale program as a single string, runs it, and returns the program's result as a string.

Language Behavior

The language processes programs consisting of one or more lines. Two kinds of constructs must be supported:

1. Unary function definition

A definition has the form:

(<param>) <name> = <body>
  • <param> is a parameter name enclosed in parentheses.
  • <name> is the name of the unary function being defined.
  • <body> is an expression that may reference <param>.

This binds a unary function named <name> that, when applied, evaluates <body> with <param> bound to the applied argument.

2. Unary function application

A unary function is applied using postfix syntax:

<argument> <name>

The <argument> is evaluated first, then function <name> is applied to that value.

The argument may itself be a parenthesized expression, allowing nested applications:

(<argument> <name>) <name>

Here the inner application (<argument> <name>) is evaluated first, and its result is used as the argument to the outer application of <name>.

Evaluation and Output

  • A program consists of definition lines followed by an expression line to be evaluated.
  • The value of the final evaluated expression is returned by execute as a string.
  • Integer literals evaluate to their numeric value; when returned, they are rendered without decimal point or extra formatting (e.g. the integer 1 becomes the string "1").

Concrete Examples

Given the program:

(x) just = x
1 just

execute returns '1'.

Given the program:

(x) just = x
(1 just) just

execute returns '1'.

(In both cases, just is the identity function returning its argument.)

Notes

  • Leading/trailing blank lines in the program source must be tolerated (programs may begin and end with newlines).

Implement Keyword Forms in the Tale Language

Extend tale.core with keyword-form support while preserving simple assignments, bare-keyword unary forms, nested unary expressions, unmatched-expression behavior, and implicit program returns.

Public API

The module tale.core must expose the callable:

def execute(program: str) -> str

execute accepts the complete source text of a Tale program and returns the string value of that program.

Program Structure and Result Semantics

A Tale program is a sequence of lines. Blank lines, including leading and trailing blank lines, are ignored. Each nonblank top-level statement is one of:

  1. A form definition, consisting of a form pattern, =, and a body expression.
  2. An expression statement, which is evaluated.

Form definitions establish names or parameterized forms and do not themselves contribute a returned value. If a program contains multiple top-level expression statements, execute returns only the string value of the last top-level expression statement. Values of earlier expression statements are discarded; they are not concatenated. For example:

x
y

must return "y". A program whose sole expression is x returns "x" when x has no matching definition.

Forms, Parameters, and Bodies

A parenthesized identifier in a form definition, such as (x), is a parameter. It captures the operand occurring in the corresponding position at the call site. The form body is an expression and may refer to captured parameter names. Evaluating a matching form invocation binds its operands to those parameters and evaluates the body with those bindings.

Integer literals such as 1 and 2 are valid operands and arguments. The returned string representation of an integer is its decimal digits, such as "1".

Simple Name Definitions

Existing exact-name definitions must continue to work. For example:

x = y
x

returns "y": the expression x matches the definition and evaluates its body y.

Bare-Keyword Unary Forms

A bare-keyword unary form is identified by an identifier without a trailing colon. It may use a parenthesized prefix parameter before the keyword. For example:

(x) just = x
1 just

Here just is the keyword, the prefix operand 1 binds to x, and the program returns "1".

Parentheses must continue to permit nested unary expressions. For example:

(x) just = x
(1 just) just

Both the inner and outer invocations match the form, and the program returns "1".

Keyword Forms

A keyword form is identified by an identifier with a trailing colon, such as just:. It has one argument immediately following the colon keyword and may additionally have a prefix operand before the keyword. The colon-bearing keyword is distinct from a bare unary keyword.

Keyword Form Without a Prefix

Definition syntax:

just: (x) = x

Call syntax:

just: 1

The post-colon argument 1 binds to x, so the invocation evaluates to 1 and execute returns "1".

Keyword Form With a Prefix

Definition syntax:

(x) just: (y) = x

Call syntax:

1 just: 2

The operand before just: binds to the prefix parameter x, and the argument after just: binds to y. The body determines which captured value is returned:

  • With (x) just: (y) = x, the call returns "1".
  • With (x) just: (y) = y, the call returns "2".

Unmatched Expressions

If an expression does not match any defined form, it evaluates to its constituent token text concatenated with no separators. Inter-token whitespace is not retained in this fallback value.

For example:

(x) just = x
1 jusx

The defined keyword is just, while the final expression uses jusx, so no form matches. Its token text 1 and jusx is concatenated, and execute returns "1jusx".

Overview

Implement an interpreter for a small language centered on message-form definitions and invocations. The public entry point is a function execute located in the module tale.core.

Public API

from tale.core import execute

def execute(program: str) -> str:
    ...
  • Input: program is a string containing the source of a program.
  • Output: a string representing the result of evaluating the program (specifically, the value produced by the program's final expression).

Language Description

A program is a sequence of lines. There are two kinds of lines:

  1. Form definitions — of the shape <pattern> = <body>.
  2. Expressions — invocations that match a previously defined form.

The program's overall result is the value of the last expression evaluated, rendered as a string.

Leading/trailing blank lines in the program source must be tolerated (the program text in practice begins and ends with newlines).

Values

The only literal values exercised are integers, written as bare digit sequences (e.g. 1, 2). The final result is returned as its string representation (e.g. the integer 1 produces '1').

Form Patterns

A form pattern is composed of tokens that are one of:

  • A keyword part: an identifier immediately followed by a colon, e.g. just:, add:, to:.
  • A unary part: a bare identifier (no colon), e.g. squared.
  • A parameter: an identifier enclosed in parentheses, e.g. (x), (y). Parameters name arguments that the form's body may refer to.

Patterns supported (as exercised):

  1. Keyword form with a single keyword part and one parameter Pattern shape: keyword: (param) Example: just: (x) = ...

  2. Keyword form with two keyword parts and two parameters Pattern shape: keyword1: (param1) keyword2: (param2) Example: add: (x) to: (y) = ...

  3. Keyword form with a leading parameter (prefix) plus one keyword part and one parameter Pattern shape: (param1) keyword: (param2) Example: (x) just: (y) = ...

  4. Unary form with a leading parameter plus a unary part Pattern shape: (param) unary Example: (x) squared = ...

Form Bodies

A form body is an expression that may:

  • Be a parameter reference: an identifier that matches one of the pattern's parameter names, evaluating to the argument bound to that parameter.
  • Be an integer literal, evaluating to that integer.
Invocations (Expressions)

An expression invokes a defined form by supplying the keyword/unary parts in the same positions as the pattern, with argument expressions in the parameter positions. Arguments are themselves expressions and may be integer literals or nested invocations.

Examples corresponding to the patterns above:

  1. just: 2 invokes just: (x) binding x to 2.
  2. add: 1 to: 2 invokes add: (x) to: (y) binding x to 1 and y to 2.
  3. 1 just: 2 invokes (x) just: (y) binding x to 1 and y to 2.
  4. 1 squared invokes (x) squared binding x to 1.
Nesting / Composition

Unary invocations bind more tightly than keyword invocations, so a keyword argument may itself be a unary invocation. For example, given both:

(x) squared = x
just: (x) = x

the expression just: 1 squared is parsed as just: applied to the argument 1 squared. The 1 squared unary invocation is evaluated first (yielding 1), and that result is passed as the argument to just: (yielding 1).

Behavioral Examples

Each program below evaluates to the indicated string result:

  • Define just: (x) = 1, then just: 2 → '1'
  • Define just: (x) = x, then just: 1 → '1'
  • Define add: (x) to: (y) = x, then add: 1 to: 2 → '1'
  • Define add: (x) to: (y) = y, then add: 1 to: 2 → '2'
  • Define (x) just: (y) = x, then 1 just: 2 → '1'
  • Define (x) squared = x and just: (x) = x, then just: 1 squared → '1'

Notes

  • Definitions appear before the expressions that use them within a program.
  • All parameter references and literals resolve to integer values; the returned result is the decimal string form of that integer.

Function: execute(program: str) -> str | None

  • Takes a program as a string.

Language Behavior Required

Indentation Blocks

The language uses indentation to group a sequence of expressions into a block. A block is a group of consecutive lines that are indented one consistent level deeper than the line introducing them.

  • The value of an indented block is the value of its last expression.
  • Indentation levels nest: a block may itself contain a more-deeply-indented block. When it does, the value produced at each level follows the same "value of the last expression" rule.
Assignment with an Indented Body

A binding of the form name = followed by a more-indented block on the following lines assigns to name the value of that indented block (i.e., the value of the block's last expression).

Example of behavior:

x =
    1
    2
    3
x

Evaluating the whole program yields '3' — the block assigned to x evaluates to its last line 3, and the final reference to x produces that value.

Nested example:

x =
    y =
        1
        2
        3
    y
x

Here the inner block assigned to y evaluates to 3, y on the last line of the outer block evaluates to 3, so the outer block (and thus x) is 3, and the final x yields '3'.

(x) just =

The form just is defined with parameter x; its body binds y = x and then yields y. Applying 1 just binds x to 1, so the body yields 1, and the program's result is '1'.

(Note: a blank line between the form definition and its use does not affect parsing/evaluation.)

If the program contains inconsistent indentation — i.e., a line whose indentation does not match the established indentation level of the block it belongs to — the program is invalid and execute must return None (not raise).

Example of an invalid program (the second body line is indented by a different, smaller amount than the first):

x

Task Specification: Implement Pattern Matching in tale

Objective

Implement a minimal interpreter for a small language ("tale") that supports function definitions with pattern matching and function application.

Public API

Create a module at tale/core (i.e., src/tale/core.py) exposing a top-level function:

def execute(program: str) -> <value>
  • Input: program is a string containing source code of the tale language (multi-line, possibly with leading/trailing blank lines).
  • Output: the result value produced by evaluating the program (the value of the program's final effective expression). Values may be plain strings.

Language Behavior Required

The tests exercise the following semantics. Implement exactly these; nothing more.

Statements

A program consists of newline-separated statements. Blank lines are ignored.

Two kinds of statements exist:

  1. Definition — associates a name with a clause. Syntax:

    <name>: <pattern> = <body>

    Multiple definitions may share the same <name>; together they form an ordered set of clauses for that name.

  2. Application / expression — invokes a defined name with an argument. Syntax:

    <name>: <argument>

    (No = present.) This applies the clauses previously defined under <name> to the given argument.

Definition clauses

Each clause for a name has:

  • a pattern, which is either:
    • a parameter pattern, written as a parenthesized identifier (x) — matches any argument and binds it to that identifier; or
    • a literal/value pattern, written as a bare token (e.g. b) — matches only when the argument equals that specific value.
  • a body, which is an expression evaluated to produce the clause's result. A body may be:
    • a reference to a bound parameter (returns the bound argument value), or
    • a bare value token (returns that value).
Application semantics

When a name is applied to an argument value:

  • The clauses defined for that name are considered in definition order.
  • The first clause whose pattern matches the argument is selected.
  • A parameter pattern (x) matches any argument; a value pattern matches only when the argument is equal to it.
  • The selected clause's body is evaluated: a parameter reference yields the argument bound by the pattern; a value token yields that literal value.
Concrete case the implementation must satisfy

Given a program that defines just with two clauses — a catch-all parameter clause (x) = x and a value clause b = c — and then applies just to the argument a:

  • The argument a is matched against the clauses in order.
  • The first clause (parameter pattern) matches any argument, binding x = a.
  • Its body x evaluates to the bound value.

The result of executing this program is the string 'a'.

Notes

  • Tokens/identifiers such as a, b, c, x, and just are simple alphanumeric names.
  • Whitespace around :, =, and parentheses should be tolerated.
  • Only the behavior described above is in scope.
08 Pattern Matching in Function Application 590 words · source specification

Task Specification: Pattern Matching in Function Application

Public API

Provide a callable execute that is importable and used as follows:

execute(program)
  • program: a str containing source code in the language described below.
  • Returns: a str — the result of evaluating the program.

Based on the test import path (src/tests/integration/pattern_matching_test.py), execute must be importable such that the integration tests can call it directly (e.g., exposed at the top level of the package under test).

Language Behavior

The program consists of newline-separated statements. Blank lines are permitted and must be ignored.

Statement forms

There are two forms of statement, both introduced by a name followed by a colon.

  1. Definition (branch) statement — has the form:

    name: <pattern> = <result>

    This associates a pattern and a result body with name. A name may have multiple such definitions ("branches"), given on separate lines.

  2. Application (invocation) statement — has the form:

    name: <argument>

    This applies the previously accumulated branches of name to <argument> and produces a value.

Patterns

Two kinds of pattern must be supported in definition statements:

  • Literal pattern: a bare identifier, e.g. b. It matches an argument only when the argument is exactly equal to that identifier.

  • Variable (wildcard) pattern: an identifier enclosed in parentheses, e.g. (x). It matches any argument, binding the argument value to the variable named inside the parentheses.

Result bodies

A result body is a single identifier, and is one of:

  • A literal: an identifier that is not the variable bound by the branch's pattern. It evaluates to itself (its own text).
  • A variable reference: an identifier equal to the variable bound by a variable pattern. It evaluates to the argument value that was bound.
Application evaluation semantics

When an application statement name: <argument> is evaluated:

  • The branches previously defined for name are considered in source order (top to bottom).
  • The first branch whose pattern matches the argument is selected.
    • A literal pattern matches only when the argument equals the literal.
    • A variable pattern matches any argument.
  • The selected branch's result body is evaluated:
    • If the body is the branch's bound variable, the result is the argument value.
    • Otherwise the result is the body identifier's own text.
  • The evaluated result is the value produced by the program.
Ordering requirement

Branch selection is strictly first-match by source order. Therefore:

  • Given a variable branch followed by a literal branch, applying the argument that equals the literal still selects the variable branch (because it appears first and matches everything), yielding the argument value.
  • Given a literal branch followed by a variable branch, applying the argument equal to the literal selects the literal branch, yielding that branch's result body.
  • Applying an argument that does not equal any literal falls through to the variable branch, yielding the argument value.

Examples

Program:

just: (x) = x
just: b = c

just: a

Result: 'a' — the first branch is a variable pattern that matches a, and its body is the bound variable, so the argument a is returned.

Program:

just: (x) = x
just: b = c

just: b

Result: 'b' — the variable branch appears first and matches, returning the argument b.

Program:

just: b = c
just: (x) = x

just: b

Result: 'c' — the literal branch b appears first and matches the argument b, so its result body c is returned.

Overview

Implement a small interpreter for a minimal pattern-matching language. The public entry point is a single function that takes source code as a string, executes it, and returns the resulting output as a string.

Public API

Create a module importable as tale.core exposing a function:

def execute(program: str) -> str:
    ...
  • Input: program — a string containing the full source of a program.
  • Output: a string — the result produced by evaluating the program.

Language Semantics

A program consists of a series of lines. There are two kinds of statements, all sharing the common prefix just:.

1. Definition statements

A definition has the form:

just: <pattern> = <result>
  • <pattern> is either:
    • A literal pattern: a bare identifier such as a, b, or c. It matches only an input equal to that exact identifier.
    • A variable pattern: an identifier enclosed in parentheses, such as (x). It matches any input and binds the variable to the matched value.
  • <result> is the term produced by the selected definition. It may be:
    • A literal identifier such as b or c; or
    • The variable name bound by a variable pattern, such as x, in which case it produces the matched value.

Multiple definitions collectively form an ordered set of rewrite branches associated with the shared name just.

2. Evaluation statement

An evaluation has the form:

just: <value>

with no =. It applies the accumulated definitions to <value>, and the result becomes the program's output.

Matching and Rewriting Rules

When evaluating just: <value>:

  1. Consider the defined branches in the order in which their definitions appear in the source.
  2. A literal branch matches only when its pattern identifier is exactly equal to <value>.
  3. A variable branch matches any <value> and binds its variable to that value.
  4. Select the first matching branch in source order. There is no separate preference for literal branches over variable branches: a preceding variable branch shadows any matching literal branch that appears later. Conversely, a matching literal branch is selected when it appears before a matching variable branch.
  5. Produce the selected branch's result, substituting the captured value when the result is the bound variable.
  6. An application performs exactly one rewrite step. Return the selected branch's produced result directly. Do not automatically submit that result to the same definitions for another round of matching, even when the result would match another literal branch.
  7. If no branch matches, the input value is already stable and is returned unchanged.

Thus, rewriting is not transitive: each explicit just: evaluation makes one source-ordered branch selection and one rewrite only.

Worked Examples

Given definitions in this order:

just: (x) = x
just: b = c
  • Evaluating just: a produces a: the first branch binds x = a and returns x.
  • Evaluating just: b also produces b: the variable branch appears first, so it is selected and the later literal branch is not considered.

Given only:

just: b = c
  • Evaluating just: b produces c.

Given definitions in this order:

just: a = b
just: b = c
just: (x) = x
  • Evaluating just: c produces c: neither literal branch matches, so the variable branch returns the captured value.
  • Evaluating just: a produces b: the first literal branch matches and its result is returned directly. The produced b is not automatically matched against just: b = c.
  • Evaluating just: b produces c: the first literal branch does not match, while the second one does.

Notes

  • Whitespace and blank lines between statements are permitted and ignored.
  • Identifiers consist of simple alphabetic characters, such as a, b, c, and x.
  • A program contains exactly one evaluation statement whose result is returned.

Task Specification: Pattern Matching for Unary Expressions

Objective

Extend the existing Tale interpreter so postfix unary forms can select rules by either a literal operand pattern or a variable operand pattern. Preserve existing language behavior outside the unary-pattern behavior described here.

Public API

The existing entry point must remain available as:

from tale.core import execute

Its required interface is:

execute(program: str) -> str

For a valid program in the scope of this task, execute evaluates the complete program string and returns the value of its final evaluated expression as a plain string.

Program Structure

A program contains rule definitions followed by an expression to evaluate. Blank lines may separate the definitions from the final expression. The final expression determines the returned value.

Unary Rule Definitions

A unary rule has this form:

<pattern> <operator> = <result>

The operator required here is the word just. The pattern is matched against the operand of a postfix unary expression, and the selected rule's result is evaluated using normal Tale expression and assignment-body semantics.

For example:

(x) just = x

defines just for any operand, while:

a just = b

defines it only for the literal operand a.

Supported Pattern Kinds

Literal (specific) pattern

A bare identifier in the pattern position, such as a or b, is a literal pattern. It matches only an operand that is exactly the same identifier. It does not introduce a variable binding.

Variable (common) pattern

A parenthesized identifier, such as (x), is a variable pattern. It matches any operand expression and binds the identifier inside the parentheses to that operand. References to the bound identifier in the selected result evaluate to the captured operand.

For example, when (x) just = x handles c just, x is bound to c, so the selected result evaluates to c.

Evaluated Unary Expressions

A postfix unary application has this form:

<operand> <operator>

Examples include:

c just
a just

The operator name in the application must match the operator name in the rule definition.

Rule Selection and Evaluation

For each explicit unary application:

  1. Consider applicable rule definitions in the order in which they appear in the program.
  2. A literal rule matches only when its literal identifier equals the operand identifier.
  3. A variable rule matches any operand and captures it under the pattern variable's name.
  4. Select the first matching rule. Later rules are not considered after a match, even if a later rule is more specific. A variable rule can therefore shadow a later literal rule.
  5. Evaluate the selected rule body with any captured variable binding and return that evaluated value for this unary application.
Single-application semantics
