02 Implementing Binding Support for Simple Assignments 383 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Implementing Binding Support for Simple Assignments

Public API

Write a module tale.core that exposes a function:

def execute(program: str) -> str:

It receives a program's source text as input and returns a string representing the outcome of that program's evaluation.

How the Language Behaves

A program's statements form a sequence, with newlines acting as the separators between them. Blank lines are ignored — including the leading/trailing blank lines that triple-quoted source gives rise to.

Statements come in two kinds:

  1. Bare identifier expression — a line holding a single identifier, e.g. x.
  2. Simple assignment — having the form <identifier> = <identifier>, e.g. x = y.

Identifiers are bare names (letters such as x, y).

How an Identifier Evaluates

The result of evaluating an identifier is a string:

  • Once a value has been assigned to the identifier (by way of a prior assignment), evaluating it produces that assigned value.
  • Otherwise, evaluating it produces its own name as a string (i.e., an unbound identifier y evaluates to 'y').
How Assignment Works

With an assignment x = y, the identifier on the left gets bound to the value that evaluating the identifier on the right produces. Once x = y has been executed, a reference to x yields the value y evaluated to when the assignment was made.

The result the program returns receives no contribution from assignment statements themselves.

Implicit Return Value

What execute returns is the value of the program's last evaluated expression statement — in other words, the value of the final bare-identifier statement. That value is returned as a string.

Examples Demonstrating the Required Behavior

Take the program:

x = y
x

execute returns 'y' — here x has been bound to the value of the unbound y (that value being 'y'), with the final expression x evaluating to that value.

Take this program:

x
y

execute returns 'y' — the value coming from the last expression statement; y being unbound, it evaluates to its own name.

When the whole program is a single bare identifier x, execute returns 'x'.

Notes

  • The program string may start and finish with newlines; blank lines like these, surrounding the code, must not affect the result.
03 Support for defining and applying unary functions is to be implemented in the tale language interpreter. 395 words · source specification, reworded by GLM-5.3-Flash

Specification of the Task

Goal

Support for defining and applying unary functions is to be implemented in the tale language interpreter.

Public API

A module tale.core is to be provided, exposing a function:

def execute(program: str) -> str:
    ...

The function execute accepts the complete source text of a tale program as a single string, runs the program, and returns the program's result as a string.

Behavior of the Language

The language processes programs made up of one or more lines. There are two kinds of constructs that must be supported:

1. Definition of a unary function

A definition is written in the form:

(<param>) <name> = <body>
  • <param> is the name of a parameter, wrapped in parentheses.
  • <name> is the name given to the unary function being defined.
  • <body> is an expression that may refer to <param>.

The definition binds a unary function called <name>; when the function is applied, <body> is evaluated with <param> bound to the argument that was applied.

2. Application of a unary function

To apply a unary function, postfix syntax is used:

<argument> <name>

First the <argument> is evaluated; after that, the function <name> is applied to the value obtained.

The argument may in turn be a parenthesized expression, which allows nested applications:

(<argument> <name>) <name>

In this case, the inner application (<argument> <name>) is evaluated first, and the result it produces becomes the argument for the outer application of <name>.

Evaluation and Output

  • A program is made up of definition lines followed by an expression line that is to be evaluated.
  • execute returns the value of the final evaluated expression as a string.
  • Integer literals evaluate to their numeric value; when they are returned, they are rendered with no decimal point and no additional formatting (e.g. the integer 1 becomes the string "1").

Specific Examples

For the following program:

(x) just = x
1 just

Calling execute on this program returns '1'.

With this program:

(x) just = x
(1 just) just

Here, execute returns '1'.

(In both cases, just is the identity function, which returns its argument.)

Notes

  • Blank lines at the start or end of the program source must be tolerated (programs may begin and end with newlines).

Specification of the Task

Add Keyword Forms to the Tale Language

Add keyword-form support to tale.core while keeping simple assignments, bare-keyword unary forms, nested unary expressions, unmatched-expression behavior, and implicit program returns intact.

Public Interface

The module tale.core must expose the following callable:

def execute(program: str) -> str

execute accepts the complete source text of a Tale program and returns the string value of that program.

Program Structure and Semantics of Results

A Tale program is made up of a sequence of lines. Blank lines — including blank lines at the beginning and at the end — are ignored. Every nonblank top-level statement is one of the following:

  1. A form definition, made up of a form pattern, =, and a body expression.
  2. An expression statement that is evaluated.

Form definitions set up names or parameterized forms and on their own contribute no returned value. If a program contains several top-level expression statements, execute returns the string value of the last top-level expression statement only. The values of expression statements that come earlier are discarded; they are not concatenated. As an example:

x
y

this program must return "y". A program whose only expression is x returns "x" if x has no definition that matches it.

Forms, Their Parameters, and Their Bodies

Inside a form definition, a parenthesized identifier — for example (x) — is a parameter. It captures the operand that appears at the call site in the corresponding position. The body of a form is an expression and may refer to the captured parameter names. When a matching form invocation is evaluated, its operands are bound to those parameters, and the body is evaluated with those bindings in place.

Integer literals like 1 and 2 are valid operands and arguments. The string representation returned for an integer is its decimal digits, as in "1".

Definitions Using Simple Names

Exact-name definitions that already exist must continue to work. For example:

x = y
x

returns "y": the expression x matches the definition, and its body y is evaluated.

Unary Forms With Bare Keywords

A bare-keyword unary form is one identified by an identifier that has no trailing colon. It may be written with a parenthesized prefix parameter before the keyword. For example:

(x) just = x
1 just

In this case just is the keyword, the prefix operand 1 binds to x, and the program returns "1".

Nested unary expressions must continue to be permitted inside parentheses. For example:

(x) just = x
(1 just) just

The form is matched by both the inner and the outer invocation, and the program returns "1".

Keyword Forms

A keyword form is one identified by an identifier that carries a trailing colon, for instance just:. It has one argument immediately after the colon keyword and may also have a prefix operand before the keyword. A keyword that bears a colon is distinct from a bare unary keyword.

Keyword Form With No Prefix

Definition:

just: (x) = x

Invocation:

just: 1

The argument 1 that comes after the colon binds to x; the invocation therefore evaluates to 1, and execute returns "1".

Keyword Form Carrying a Prefix

Definition:

(x) just: (y) = x

Invocation:

1 just: 2

The operand appearing before just: binds to the prefix parameter x, while the argument after just: binds to y. Which captured value is returned is determined by the body:

  • Given (x) just: (y) = x, the call returns "1".
  • Given (x) just: (y) = y, the call returns "2".

Unmatched Expressions

When an expression does not match any defined form, it evaluates to the text of its constituent tokens concatenated with no separators. Whitespace between tokens is not kept in this fallback value.

As an example:

(x) just = x
1 jusx

The keyword that has been defined is just, but the final expression contains jusx instead, so no form matches. The token texts 1 and jusx are concatenated, and execute returns "1jusx".

Examples of Required Behavior

Statements of the program Value returned
just: (x) = x followed by just: 1 "1"
(x) just: (y) = x followed by 1 just: 2 "1"
(x) just: (y) = y followed by 1 just: 2 "2"
(x) just = x followed by 1 jusx "1jusx"
(x) just = x followed by (1 just) just "1"
x = y followed by x "y"
x followed by y "y"
05 Build an interpreter for a small language that centers on message-form definitions and invocations. 732 words · source specification, reworded by GLM-5.3-Flash

Specification of the Task

Overview

Build an interpreter for a small language that centers on message-form definitions and invocations. The public entry point is the function execute, which resides in the module tale.core.

Public API

from tale.core import execute

def execute(program: str) -> str:
    ...
  • Input: program is a string that contains the source of a program.
  • Output: a string representing the result of evaluating the program (specifically, the value that the program's final expression produces).

Description of the Language

A program consists of a sequence of lines. The lines fall into two kinds:

  1. Form definitions — lines shaped like <pattern> = <body>.
  2. Expressions — invocations that match a form defined earlier.

The overall result of the program is the value of the last expression that gets evaluated, rendered as a string.

Leading and trailing blank lines in the program source must be tolerated (in practice the program text begins and ends with newlines).

Values

Integers are the only literal values exercised, and they are written as bare digit sequences (e.g. 1, 2). The final result is returned in its string representation (e.g. the integer 1 produces '1').

Form Patterns

A form pattern is made up of tokens, and each token is one of:

  • A keyword part: an identifier with a colon immediately after it, e.g. just:, add:, to:.
  • A unary part: a bare identifier (without a colon), e.g. squared.
  • A parameter: an identifier surrounded by parentheses, e.g. (x), (y). Parameters name the arguments that the form's body may refer to.

The patterns that are supported (as exercised):

  1. Keyword form with a single keyword part plus one parameter The shape of the pattern is keyword: (param). Example: just: (x) = ...

  2. Keyword form with two keyword parts and two parameters The shape of the pattern is keyword1: (param1) keyword2: (param2). Example: add: (x) to: (y) = ...

  3. Keyword form with a leading parameter (a prefix) plus one keyword part and one parameter The shape of the pattern is (param1) keyword: (param2). Example: (x) just: (y) = ...

  4. Unary form with a leading parameter plus a unary part The shape of the pattern is (param) unary. Example: (x) squared = ...

Form Bodies

A form body is an expression which may:

  • Be a parameter reference: an identifier that matches one of the parameter names in the pattern, evaluating to the argument bound to that parameter.
  • Be an integer literal, which evaluates to that integer.
Invocations (Expressions)

An expression invokes a defined form by supplying the keyword/unary parts in the same positions the pattern has, with argument expressions occupying the parameter positions. Arguments are themselves expressions, and they may be integer literals or nested invocations.

Examples matching the patterns above:

  1. just: 2 invokes just: (x), binding x to 2.
  2. add: 1 to: 2 invokes add: (x) to: (y), binding x to 1 and y to 2.
  3. 1 just: 2 invokes (x) just: (y), binding x to 1 and y to 2.
  4. 1 squared invokes (x) squared, binding x to 1.
Nesting / Composition

Unary invocations bind more tightly than keyword invocations, which means a keyword argument may itself be a unary invocation. For example, given both of the following:

(x) squared = x
just: (x) = x

the expression just: 1 squared parses as just: applied to the argument 1 squared. The unary invocation 1 squared is evaluated first (yielding 1), and that result is passed as the argument to just: (yielding 1).

Behavioral Examples

Each program below evaluates to the string result shown:

  • After defining just: (x) = 1, just: 2 → '1'
  • After defining just: (x) = x, just: 1 → '1'
  • After defining add: (x) to: (y) = x, add: 1 to: 2 → '1'
  • After defining add: (x) to: (y) = y, add: 1 to: 2 → '2'
  • After defining (x) just: (y) = x, 1 just: 2 → '1'
  • After defining (x) squared = x and just: (x) = x, just: 1 squared → '1'

Notes

  • Within a program, definitions appear before the expressions that use them.
  • All parameter references and literals resolve to integer values; the result that is returned is the decimal string form of that integer.

Specification for the Task

Goal

Add support for indentation-based blocks to the interpreter of the tale language, with the feature exposed through the execute function.

Public Interface

Module: tale.core

Function: execute(program: str) -> str | None

  • The program is passed in as a string.
  • Returns the string representation of the value of the program's final result.
  • Returns None when the program is not valid (see the error handling section below).

Required Language Behavior

Blocks Formed by Indentation

The language groups a sequence of expressions into a block by means of indentation. A block is a set of consecutive lines that are indented one consistent level deeper than the line that introduces them.

  • The value of an indented block is the value of its last expression.
  • Indentation levels nest: a block may itself contain another block indented more deeply. When that happens, the value produced at each level follows the same "value of the last expression" rule.
Assignment Using an Indented Body

A binding of the form name = followed by a more-indented block on the subsequent lines assigns to name the value of that indented block (that is, the value of the block's last expression).

Example demonstrating the behavior:

x =
    1
    2
    3
x

Evaluating the complete program gives '3' — the block assigned to x evaluates to its last line 3, and the final reference to x produces that value.

Example with nesting:

x =
    y =
        1
        2
        3
    y
x

In this case, the inner block assigned to y evaluates to 3, y on the last line of the outer block evaluates to 3, so the outer block (and thus x) is 3, and the final x yields '3'.

Unary Forms Using Indented Bodies

Support is provided for a unary form definition whose body spans multiple indented lines. When the defined form is applied, it evaluates its indented body and produces the value of the last expression of that body.

Example demonstrating the behavior:

(x) just =
    y = x
    y

1 just

The form just is defined with parameter x; its body binds y = x and then yields y. Applying 1 just binds x to 1, so the body yields 1, and the result of the program is '1'.

(Note: a blank line between the definition of the form and its use has no effect on parsing/evaluation.)

Handling of Errors

If the program has inconsistent indentation — meaning a line whose indentation does not match the established indentation level of the block it belongs to — the program is invalid and execute must return None (not raise).

Example of an invalid program (the indentation of the second body line is a different, smaller amount than that of the first):

x =
    1
   2
x

This program yields None.

Additional Notes

  • In this task, programs begin and end with newlines (leading/trailing blank lines around the program body must be tolerated).
  • The string result is the textual representation of the value that results (e.g., the integer 3 is returned as '3').

Task Specification: Implementing Pattern Matching in tale

Objective

The goal is to implement a minimal interpreter for a small language ("tale") that supports function definitions with pattern matching as well as function application.

Public API

Create a module at tale/core (i.e., src/tale/core.py) that exposes a top-level function:

def execute(program: str) -> <value>
  • Input: program is a string that contains the source code of the tale language; it is multi-line and may have leading/trailing blank lines.
  • Output: the result value that evaluating the program produces (that is, the value of the program's final effective expression). Values may take the form of plain strings.

Required Language Behavior

The following semantics are what the tests exercise. Implement exactly these, and nothing more.

Statements

A program is made up of statements separated by newlines. Blank lines are ignored.

There are two kinds of statements:

  1. Definition — ties a name to a clause. Syntax:

    <name>: <pattern> = <body>

    More than one definition may share the same <name>; together, they make up an ordered set of clauses for that name.

  2. Application / expression — takes a defined name and invokes it with an argument. Syntax:

    <name>: <argument>

    (No = is present.) This applies the clauses that were previously defined under <name> to the given argument.

Definition Clauses

Each clause belonging to a name has:

  • a pattern, which is either:
    • a parameter pattern, written as a parenthesized identifier (x) — matches any argument, binding it to that identifier; or
    • a literal/value pattern, written as a bare token (e.g. b) — matches only when the argument is equal to that specific value.
  • a body, which is an expression that is evaluated to produce the clause's result. A body may be:
    • a reference to a bound parameter (this returns the value of the bound argument), or
    • a bare value token (this returns that value).
Application Semantics

When a name is applied to an argument value, the behavior is as follows:

  • The clauses that have been defined for that name are considered in definition order.
  • The first clause whose pattern matches the argument is the one that gets selected.
  • A parameter pattern (x) matches any argument, whereas a value pattern matches only when the argument is equal to it.
  • The body of the selected clause is then evaluated: a parameter reference yields the argument that the pattern has bound; a value token yields that literal value.
Concrete Case the Implementation Must Satisfy

Take a program that defines just with two clauses — a catch-all parameter clause (x) = x and a value clause b = c — and then applies just to the argument a:

  • The argument a is matched against the clauses, taking them in order.
  • The first clause (the parameter pattern) matches any argument, which binds x = a.
  • The clause's body, x, evaluates to the value that was bound.

The result obtained by executing this program is the string 'a'.

Notes

  • Tokens/identifiers like a, b, c, x, and just are simple alphanumeric names.
  • Whitespace surrounding :, =, and parentheses should be tolerated.
  • The only behavior in scope is the behavior described above.
08 Pattern Matching in Function Application 616 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Pattern Matching in Function Application

Public API

Provide a callable execute that can be imported and is used in the following way:

execute(program)
  • program: a str holding source code written in the language described below.
  • Returns: a str — the value obtained from evaluating the program.

Given the test import path (src/tests/integration/pattern_matching_test.py), execute must be importable so that the integration tests can call it directly (for instance, exposed at the top level of the package under test).

Language Behavior

A program is made up of statements separated by newlines. Blank lines are allowed and must be ignored.

Statement forms

Two forms of statement exist, both of which start with a name followed by a colon.

  1. Definition (branch) statement — takes the form:

    name: <pattern> = <result>

    This attaches a pattern and a result body to name. A name may have several such definitions ("branches"), each given on its own line.

  2. Application (invocation) statement — takes the form:

    name: <argument>

    This applies the branches that have accumulated beforehand for name to <argument> and produces a value.

Patterns

Definition statements must support two kinds of pattern:

  • Literal pattern: a bare identifier, e.g. b. It matches an argument only if the argument is exactly equal to that identifier.

  • Variable (wildcard) pattern: an identifier placed in parentheses, e.g. (x). It matches any argument and binds the argument value to the variable named inside the parentheses.

Result bodies

A result body is a single identifier and takes one of the following forms:

  • A literal: an identifier that is not the variable bound by the branch's pattern; it evaluates to itself (its own text).
  • A variable reference: an identifier equal to the variable bound by a variable pattern; it evaluates to the argument value that was bound.
Application evaluation semantics

When the application statement name: <argument> is evaluated:

  • The branches defined earlier for name are taken into account in source order (top to bottom).
  • The first branch whose pattern matches the argument is chosen.
    • A literal pattern matches only if the argument equals the literal.
    • Any argument is matched by a variable pattern.
  • The result body of the selected branch is evaluated:
    • When the body is the branch's bound variable, the result is the argument value.
    • In all other cases the result is the body identifier's own text.
  • The evaluated result is the value the program produces.
Ordering requirement

Branch selection is strictly first-match by source order. Consequently:

  • With a variable branch followed by a literal branch, applying the argument that equals the literal still picks the variable branch (because it comes first and matches everything), yielding the argument value.
  • With a literal branch followed by a variable branch, applying the argument equal to the literal picks the literal branch, yielding that branch's result body.
  • When the applied argument does not equal any literal, it falls through to the variable branch, yielding the argument value.

Examples

Program:

just: (x) = x
just: b = c

just: a

Result: 'a' — the first branch uses a variable pattern that matches a, and its body is the bound variable, so the argument a is returned.

Program:

just: (x) = x
just: b = c

just: b

Result: 'b' — the variable branch comes first and matches, returning the argument b.

Program:

just: b = c
just: (x) = x

just: b

Result: 'c' — the literal branch b comes first and matches the argument b, so its result body c is returned.

09 Build a small interpreter for a minimal pattern-matching language. 693 words · rewritten by GPT-5.6-sol, reworded by GLM-5.3-Flash

Overview

Build a small interpreter for a minimal pattern-matching language. The public entry point is a single function: it takes the source code as a string, executes it, and returns the resulting output as a string.

Public API

Provide a module that can be imported as tale.core, exposing a function:

def execute(program: str) -> str:
    ...
  • Input: program — a string that contains the full source of a program.
  • Output: a string — the result that evaluating the program produces.

Semantics of the Language

A program is made up of a series of lines. Two kinds of statements exist, and all of them share the common prefix just:.

1. Definition statements

A definition takes the form:

just: <pattern> = <result>
  • <pattern> is either:
    • A literal pattern: a bare identifier such as a, b, or c. It matches only an input that is equal to that exact identifier.
    • A variable pattern: an identifier enclosed in parentheses, such as (x). It matches any input, binding the variable to the matched value.
  • <result> is the term that the selected definition produces. It may be:
    • A literal identifier such as b or c; or
    • The variable name that a variable pattern binds, such as x, in which case it produces the matched value.

Multiple definitions together form an ordered set of rewrite branches under the shared name just.

2. Evaluation statement

An evaluation takes the form:

just: <value>

with no = present. It applies the accumulated definitions to <value>, and the result then becomes the program's output.

Rules for Matching and Rewriting

When just: <value> is evaluated:

  1. The defined branches are considered in the order in which their definitions appear in the source.
  2. A literal branch matches only if its pattern identifier is exactly equal to <value>.
  3. A variable branch matches any <value>, binding its variable to that value.
  4. Select the first matching branch in source order. Literal branches are given no separate preference over variable branches: a preceding variable branch shadows any matching literal branch that appears later. Conversely, when a matching literal branch appears before a matching variable branch, the literal branch is the one selected.
  5. Produce the selected branch's result, substituting the captured value for the bound variable when the result is that variable.
  6. An application carries out exactly one rewrite step. Return the result produced by the selected branch directly. Do not automatically feed that result back into the same definitions for another round of matching, even when the result would match another literal branch.
  7. If no branch matches, the input value is already stable, and it is returned unchanged.

Therefore, rewriting is not transitive: each explicit just: evaluation performs one source-ordered branch selection and one rewrite only.

Worked Examples

With these definitions, in this order:

just: (x) = x
just: b = c
  • Evaluating just: a produces a: the first branch binds x = a and returns x.
  • Evaluating just: b also produces b: the variable branch appears first, so it is the one selected, and the later literal branch is not considered.

With only this definition:

just: b = c
  • When just: b is evaluated, the result is c.

With the following definitions, in this order:

just: a = b
just: b = c
just: (x) = x
  • Evaluating just: c produces c: neither literal branch matches, so the captured value is returned by the variable branch.
  • Evaluating just: a produces b: the first literal branch matches, and its result is returned directly. The b that is produced is not automatically matched against just: b = c.
  • Evaluating just: b produces c: the first literal branch does not match, whereas the second one does.

Notes

  • Blank lines and whitespace between statements are permitted and are ignored.
  • Identifiers are made up of simple alphabetic characters, such as a, b, c, and x.
  • A program contains exactly one evaluation statement, and that statement's result is returned.

Task Specification: Pattern Matching in Unary Expressions

Goal

The existing Tale interpreter is to be extended so that postfix unary forms can select rules by either a literal operand pattern or a variable operand pattern. Outside the unary-pattern behavior described here, the existing language behavior is to be preserved.

Public Interface

In a simple assignment, a plain name is bound to an expression:

Forms, Arguments, and Bodies

  • A literal-pattern slot is a bare identifier or integer such as a or 1. It matches only the same operand text and introduces no parameter binding.

After a match succeeds, the form body is evaluated with all captured parameters available. Bindings created while a body is evaluated stay local to that invocation, while the definitions of the surrounding program remain available.

Single-line and indented bodies

The body may be a single expression written on the definition line:

(x) just = x

Blocks may be nested. For example:

Unary Forms

The shape of a postfix unary form is:

ARGUMENT NAME = BODY

For a parameterized form, the usual writing is:

(x) just = x

The expression 1 just captures 1 as x, evaluates the body, and returns "1".

Unary forms may also take a literal-pattern operand:

a just = b

(x) just = x

Here a just returns "b", whereas c just falls through to the parameter clause and returns "c".

Postfix unary applications may be chained. Applications reduce left-to-right, so:

returns "1". Distinct unary forms compose with each other in the same way:

also returns "1".

Keyword Forms

A keyword form is made up of one or more name: parts, and an argument slot follows each one. Definition and invocation of a one-part keyword form look like this:

This returns "1". The body may ignore the argument; for instance, just: (x) = 1 makes just: 2 return "1".

A keyword form may have several named parts. The keyword names, the order in which they appear, and the number of parts must match:

(x) just: (y) = x
1 just: 2

This returns "1". A form with a prefix matches only a prefixed keyword expression, and a form without a prefix matches only a non-prefixed expression.

Inside keyword arguments, postfix unary forms bind. For example:

(x) squared = x
just: (x) = x
just: 1 squared

is interpreted with 1 squared as the value supplied to just:, and it returns "1".

The argument slots of a keyword form may hold literal patterns as well as parameters. When keyword clauses compete, they are considered in definition order, and the first clause whose keyword shape and argument patterns match is the one selected. Keyword matching does not reorder clauses according to literal specificity. As a consequence:

just: (x) = x

returns "b": the parameter clause, which appears earlier, matches first and shadows the literal clause that comes later. Reversing the order of those two definitions makes just: b return "c". Literal clauses still act as ordinary guarded branches when they appear before a fallback clause; for example, with just: a = b, just: b = c, and then just: (x) = x, the results for the arguments a, b, and c are "b", "c", and "c" respectively.

Binary Forms

The shape of a binary form is:

LEFT OP RIGHT = BODY

with OP standing for an operator symbol such as +. Each of the two operand slots may be a parameter or a literal pattern.

With parameterized slots, both operands are bound independently:

(x) + (y) = x

1 + 2

returns "1", whereas:

(x) + (y) = y

1 + 2

returns "2".

A slot holding a literal pattern matches only its exact operand. For example:

1 + 1 = 2

matches 1 + 1 but not 1 + 2.

Specificity for binary forms

Among the form kinds, binary forms are the kind for which matching literal patterns receive specificity priority. If several binary clauses for the same operator match, a matching literal-pattern clause that is more specific takes precedence over a general parameter clause, regardless of the textual order in which they were defined. Given:

1 + 1 = 2
(x) + (y) = x
  • 1 + 1 selects the specific clause and returns "2".
  • 1 + 2 cannot use that clause; it falls back to the parameter clause and returns "1".

If the two definitions are reversed, the result for 1 + 1 must remain "2". Literal priority is limited to the selection of binary forms; it must not be applied globally to keyword clauses or other form kinds. When clauses have no specificity distinction, their source order is retained.

Summary of Evaluation Semantics

For a valid program:

  1. Disregard blank lines and -- comments.
  2. Work through top-level statements in source order, registering each definition in the current scope.
  3. Evaluate expressions by matching on form shape, names/operators, arity, prefix presence, and operand patterns.
  4. For non-binary clauses, take the first matching definition in source order. For binary clauses, prefer a matching literal-specific rule over a general parameter rule, independent of definition order.
  5. Bind the captured operands to parameter names and evaluate the selected body, including any nested block and local bindings.
  6. Keep reducing composed expressions, including postfix unary chains that reduce left-to-right.
  7. When nothing matches, render the expression's tokens with no separators.
  8. Return the rendering of the last top-level expression.

  • A program is made up of statements and expressions separated by newlines.
  • Blank lines are ignored.
  • Statements are evaluated in the order they appear in the source.
  • execute returns the value that the final top-level expression produces.
  • Assignment declarations do not, by themselves, contribute a result. If the program produces no expression result, the result is None.

Assignment and Values

An assignment takes the form:

name = expression

The value of the expression is associated with name, and later expressions can reference it. The required literal kinds are:

  • Integer literals that are non-negative, represented by Python int values.
  • String literals that use double quotes as delimiters, represented by Python str values without the delimiters.

For example:

x = 1
x

returns the integer 1, whereas:

x = "a"
x

returns the string 'a'.

Expressions Using Binary +

In a binary expression, two operands are separated by +, for example x + y. Whitespace surrounding the operator must be accepted.

Precedence of user-defined binary forms

A binary form can be declared using parameters or literal patterns:

(x) + (y) = x
1 + 1 = 2

Normal form matching and application must take place before the unmatched-expression behavior described below is applied, even when the invocation is the program's final expression. Specifically:

  • The operator must match.
  • A parenthesized parameter, such as (x), captures the evaluated operand value and makes it available to the form body.
  • A literal pattern matches against the evaluated operand value that corresponds to it.
  • Clauses are considered in the order in which they were declared, and the first clause that matches is the one applied. A later clause, even one that is more specific, does not displace an earlier matching clause.
  • The body of the matched form is evaluated with the parameters it captured, and the value of that body is the value of the binary invocation.

For example:

(x) + (y) = x

1 + 2

returns the integer 1, not the string '1+2'. Similarly:

(x) + (y) = y

1 + 2

returns the integer 2.

Literal-pattern clauses take part in the same dispatch:

1 + 1 = 2
(x) + (y) = x

1 + 1

returns 2, whereas changing the final invocation to 1 + 2 selects the general clause, which returns 1.

This dispatch rule applies no matter whether the binary invocation is nested, consumed by another expression, or is the final expression that execute returns. Symbolic rendering is only a fallback for the case in which no user-defined binary form matches.

Trailing binary expressions with no match

When no binary form matches and the binary expression is the final result of the program, return its symbolic source representation rather than reducing it. The representation is made up of the operands as written together with the + operator, with surrounding whitespace removed. It uses the names of the operands rather than replacing them with their bound values.

For example:

x = 1
y = 2

x + y

returns 'x+y'.

This rule is not a blanket rule covering all trailing binary expressions: a form that matches must still be applied as described above.

Numeric evaluation

When no matching user-defined form overrides normal numeric evaluation, and an integer + expression is consumed numerically instead of being returned through the unmatched trailing-expression fallback, two integer operands evaluate to their arithmetic sum as a Python integer.

The type Operation

The postfix expression:

value type

evaluates value and returns, as a Python string, the exact name of its runtime type:

  • A value that is an integer yields 'Int'.
  • A value that is a string yields 'String'.

Examples:

x = 1
x type

returns 'Int'.

x = "a"
x type

returns 'String'.

The operation must inspect the evaluated value, including a value obtained through a variable binding, rather than classify how the variable is spelled in the source.

Scope and Non-Goals

  • Existing form matching and application behavior must be preserved; the symbolic binary fallback must not replace successful dispatch.
  • No additional literal types, type names, operators, string escape syntax, or library operations are required.
  • Only the language behavior and the API described above are required.

Required Semantics of the Language

Statements and how programs are laid out
  • Assignment statements and expression statements are supported in programs.
  • Statements are evaluated in the order they appear in the source.
  • Blank lines at the beginning and end must be tolerated, including programs whose source begins and ends with a newline.
Assignments whose right-hand side is indented

An assignment may place its body on the lines following the =:

<name> =
    <statement or expression>
  • One indentation level is denoted by exactly four spaces. Each additional nested level is another four spaces.
  • The indented body is part of the assignment, and it supplies the value bound to <name>.
  • A body may hold one or more statements. Its value is the value produced by its final evaluated expression. This preserves the existing behavior for primitive bodies and nested assignment bodies.
  • A body expression need not be primitive. Compound expressions—including a binary expression such as a + b—are valid.
  • The final line of the indented body may be a compound expression. Its line ending and the dedent that follows must be accepted normally, and execution must continue with the subsequent outer-level statements.

Nested four-space indentation, for instance, remains valid:

x =
    y =
        1
        2
        3
    y
x

The program above returns 3.

When indentation does not match a four-space level, it must not be treated as correctly aligned continuation content. As an example, the malformed continuation below produces no meaningful result and therefore returns None:

x =
    1
   2
x
Evaluating expressions and the program result
  • A name that appears bare as a statement is evaluated.
  • A name that is assigned from an indented body must resolve to that body's value whenever it is referenced later.
  • execute returns, as the program result, the value of the final evaluated statement. So, with two bare expression statements such as x followed by y, the result is the value of y.

x =

x

Whether the same expression is used as an inline assignment body or as the final expression of an indented assignment body, it must retain the same result.

A full public-API example follows:

x

If a program has no meaningful final value, execute must return None. This includes a program that is empty, or a program that only establishes an assignment without subsequently yielding an expression value.

Compatibility

Outside this extension, all established valid Tale behavior must remain unchanged. Adding support for a compound expression in an indented assignment body must not regress single-line assignments, primitive multiline bodies, nested four-space bodies, expression evaluation, or implicit return of the final evaluated statement.

Reference for Language Behavior

Values and Types
  • Integer literals, for instance 1, 2, evaluate to Python int values.
  • String literals, for instance "a", evaluate to Python str values.
  • Bare identifiers for which no binding exists (e.g. a, b, c, x, y) evaluate to a symbol whose value is the identifier's own name as a Python str. As an example, evaluating a yields 'a'.
The unary form type
  • The expression x type yields the type name of x as a string.
  • When the value is an integer, the type name is 'Int'.
  • When the value is a string, the type name is 'String'.

Example:

x = 1
x type

→ 'Int'

x = "a"
x type

→ 'String'

Assignments and implicit return
  • The assignment name = value binds a value to a name.
  • A program's value is the value of its final expression.
Indentation
  • When the right-hand side of an assignment is empty on the same line, the assignment takes the following indented block as its value.

Example:

x =
    just: 1
x

→ 'just:1'

Forms and Pattern Matching

User-defined forms with pattern matching are supported in Tale. A form definition takes the shape pattern = body. When a form is invoked, its defined patterns are tried, and the body of the matching branch is evaluated.

Binary forms are written using infix operator syntax. The pattern of a binary form binds two operands:

(x) + (y) = x

What this defines is a + form whose result is its first operand. Given this program:

(x) + (y) = x

a + b

→ 'a' (first operand)

(x) + (y) = y

a + b

→ 'b' (second operand)

Multiple binary branches / specificity: When binary forms compete, literal/value patterns that are more specific take precedence over general variable-binding patterns. When no specific branch matches, a common variable-binding branch is used.

a + b = c
(x) + (y) = x

a + c

In this example, a + c does not match the specific pattern a + b; the general branch therefore applies → 'a'.

a + b = c
(x) + (y) = x

a + b

In this example, a + b matches the specific pattern → 'c'.

Keyword and unary branch order: Branches of keyword forms and unary forms keep source-definition order rather than applying the binary form's prioritization of literals over variables. Compatible branches are tried from first to last, and the first branch that matches is the one used. As a result, an earlier variable-binding branch may take precedence over a later matching literal/value branch.

As an example:

select: (item) = item
select: target = chosen

select: target

→ 'target'

If those two definitions are reversed, the literal branch runs first and produces 'chosen'. Unary forms follow the same rule; for example, when target tagged is evaluated, an earlier (item) tagged = item branch wins over a later target tagged = chosen branch, while reversing their definition order makes the literal branch win.

Type-constrained pattern matching: A pattern operand may carry a type constraint such as (x: Int), which only matches values of that type.

just: (x: Int) = x
just: (x)      = Error

just: 1

→ 1 (matches the Int branch)

just: (x: Int) = x
just: (x)      = Error

just: a

→ 'Error' (the argument a is a symbol/string, not an Int, so the common branch applies)

Required Change: The built-in plus (+) operator

A built-in binary + operator for integers is to be implemented. When both operands are integers and no user-defined + form overrides the behavior, + must produce their integer sum.

1 + 2

→ 3

This built-in must not interfere with user-defined + forms that match on other operand shapes (e.g. symbol operands like a + b); those forms must continue to behave as defined by the user's patterns, as described above.

Constraints

  • All existing behavior described in the reference section above must be preserved.
  • The only public API that the calling code relies on is execute in tale.core.
