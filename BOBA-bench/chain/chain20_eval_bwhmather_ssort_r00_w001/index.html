Task: Rename the "dependencies" concept to "requirements"

Overview

The codebase currently has a module that analyzes Python AST nodes to determine which names a node requires from its surrounding scope (i.e., names that must be defined elsewhere for the node to work). This concept is currently called "dependencies" and must be renamed to "requirements". The public API surface must be updated accordingly.

Required Public API

Create a module at ssort/_requirements that exposes a function:

def get_requirements(node):
    ...
  • node: a Python AST node (as produced by ast.parse, typically a single statement/expression node).
  • Returns: an iterable of requirement objects. Each object has a .name attribute (a str) giving the name of a required (externally-defined) identifier.
  • The ordering of the returned objects must match the source order in which the names appear (as detailed by the examples below).

This module and function replace any previous ssort/_dependencies module / get_dependencies function. The old name is no longer part of the API.

Behavior of get_requirements

get_requirements(node) yields the free names that node requires from an enclosing scope. Names that are locally bound/defined within the node's own scope are not requirements. The .name values collected in order, for the following representative inputs, must be exactly:

Function definitions
  • A function whose body references a name defined outside → that name is required.
    • def function(): return name → ["name"]
    • Function referencing a and b in its body → ["a", "b"]
  • Arguments shadow outer names: a parameter used in the body is not required.
    • def function(arg): return arg → []
  • Local assignment shadows: names assigned before use inside the body are not required, but genuinely external names are.
    • body assigns a then uses a and b → ["b"]
  • Names bound by the "rest" of a starred assignment target shadow.
    • a function that binds a (via unpacking) and returns value → ["value"]
  • A name used before being shadowed later is still required if used in a way that requires the external binding; when a name is assigned and only the external one matters → ["b"] (function assigns something then references b).
  • Decorators and their arguments are requirements.
    • @decorator(arg)\ndef function(): pass → ["decorator", "arg"]
  • nonlocal declarations: a nonlocal a referencing an enclosing name → ["a"].
    • nonlocal within a closure: still ["a"].
    • a closure that itself captures the nonlocal name locally → [].
  • global declarations: global a used → ["a"].
    • global within a closure → ["a"].
    • global within a closure that does not capture → ["a"].
  • Async function definitions behave the same as regular functions:
    • referencing an external name other → ["other"].
Class definitions
  • Class definitions yield the external names referenced in base classes, decorators, and body, in source order (e.g. a class construction referencing multiple external names yields them in order).
Statements
  • return a + b → ["a", "b"]
  • del something → ["something"]
  • del a, b → ["a", "b"]
  • del a[b:c] → ["a", "b", "c"]
  • del obj.attr → ["obj"]
  • Assignment a = b → ["b"] (the assignment target is not a requirement).
  • Augmented assignment a += b → ["b"].
  • Annotated assignment (a: T = b) → ["b"] (the annotated form referencing external b yields ["b"]).
  • for loops: the iterable, and any external names used in the body/else, are requirements; the loop target is bound (not required). For a loop like iterating and using several external names → ["b", "c", "e", "g"].
    • When the loop target name is also used to produce the iterable (for a in a(): ...), the target replaces the outer scope, so a used as the callable is still required → ["a"].
  • async for behaves identically to for → ["b", "c", "e", "g"].
  • while loops: predicate and body/else external names, in order → ["predicate", "action", "cleanup"].
  • if statements: test, body, else, in order → ["predicate", "subsequent", "alternate"].
  • with statements: context expression external names and body external names → ["A", "b"].
    • async with behaves identically → ["A", "b"].
  • raise Exception(message) → ["Exception", "message"].
  • try/except/else/finally: external names referenced throughout, in source order.
  • assert, plain control-flow statements (break/continue/pass), import, import ... from, bare global/nonlocal at module level, and expression statements produce results consistent with the definitions here (no requirements introduced by import statements or by pure control-flow keywords).
with statement bindings interaction

For a with block of the form:

with chdir(os.path.dirname(path)):
    requirements = get_requirements(node)
    ...

the requirements collected must be:

["chdir", "os", "path", "get_requirements", "node"]

(i.e., the context manager callable and its argument names in order, followed by names used in the body that are not locally bound; names assigned within the body are excluded from requirements).

Expressions
  • Boolean ops, named expressions (:=), conditional expressions, sets, generator expressions, await, yield, yield from, comparisons, formatted values / f-strings, constants, starred expressions, lists — all yield the external names they reference in source order.
  • a + b → ["a", "b"]
  • Unary op on plus → ["plus"]
  • lambda: parameters shadow; a lambda referencing external other → ["other"].
  • Dict literal referencing external value → ["value"]; {} → []; {**values} → ["values"].
  • Comprehensions bind their loop targets; the iterable and the action expression external names are required:
    • list comprehension → ["action", "iterator"]
    • set comprehension → ["action", "iterator"]
    • dict comprehension → ["process_key", "process_value", "iterator"]
  • Calls: callable then argument names in order.
    • function(*args) → ["function", "args"]
    • kwarg unpacking form → ["function", "kwargs"]
    • obj.method(arg_value, kwarg=kwarg_value) → ["obj", "arg_value", "kwarg_value"]
  • Attribute access obj.attr → ["obj"].
  • Subscript array[key] → ["array", "key"].
    • array[start:end] → ["array", "start", "end"]
    • array[:end] → ["array", "end"]
    • array[start:] → ["array", "start"]
    • array[:] → ["array"]
  • Plain name name → ["name"].
  • Tuple (a, b) → ["a", "b"]; (a, *b) → ["a", "b"].

Additional requirement

Elsewhere in the codebase there exists a name-binding analysis (a get_bindings-style facility). It must continue to work such that, for a with block like the one shown above (context manager chdir(os.path.dirname(path)) with a body that assigns names), the bindings produced reflect the names bound within, consistent with the existing binding behavior. No behavioral change to binding logic is required beyond keeping it consistent with the renamed requirements concept.

Summary of the change

Rename the module ssort/_dependencies → ssort/_requirements and the function get_dependencies → get_requirements, preserving all existing analysis behavior exactly as specified above. Update all internal usages so the package continues to function with the new name.

02 Statement Sorting by Dependency Order 496 words · source specification

Task Specification: Statement Sorting by Dependency Order

Objective

Implement a function that reorders top-level statements in a Python source file so that definitions appear before the code that depends on them, using their order of use to break ties.

Public API

Provide a module ssort exposing a callable:

def ssort(source: str) -> str
  • Input: A string containing valid Python source code.
  • Output: A string containing the same statements, reordered as described below. The output preserves each statement's original text and retains a trailing newline consistent with normal source formatting.

Required Behavior

ssort parses the top-level statements of the input, determines the dependency relationships between them, and emits them in an order where a statement that another statement depends on comes before its dependent — subject to the tie-breaking and cycle rules below.

Dependency ordering

When one statement references a name defined by another statement, the defining statement must be placed before the referencing statement.

Where multiple independent definitions are required by a later statement, they must be emitted in the order in which they are first used by that later statement (i.e., dependencies are ordered according to their order of use).

Concretely, given definitions that are only referenced by a subsequent statement, and that subsequent statement uses them in a particular sequence, the definitions must be output in that sequence of first use — even if this differs from their original source order.

For example, input in which main calls _step1() then _step2(), but where _step2 is defined before _step1 in the source, must be reordered so that _step1 precedes _step2, both preceding main.

Cycles

When statements participate in a dependency cycle (each function calls another in the group, forming a loop), the members of the cycle are emitted preserving their original relative order.

  • A direct cycle among statements A→B→C→A (in source order A, B, C) is emitted unchanged.
  • A reversed cycle where A depends on C, B depends on A, C depends on B (source order A, B, C) is emitted unchanged.
Cycles with external dependents

When a statement outside a cycle depends on a member of that cycle, the cycle members must appear before the dependent, while the internal order of the cycle members is otherwise preserved.

For example, given source order:

def c():
    return a()
def a():
    return b()
def b():
    return a()

where a and b form a cycle and c depends on a, the required output order is a, c, b — the cycle member a is promoted ahead of its dependent c, and the remaining cycle member b follows.

References resolved

Name references inside function bodies (e.g. calls like b() within def a(): return b()) count as dependencies of the enclosing function on the referenced definition.

Notes

  • The reordering operates on top-level definitions and statements.
  • Statement source text (including bodies and indentation) is preserved verbatim; only the ordering of statements changes.

Public API

  • Module: ssort._bindings
  • Callable: get_bindings(node)
  • node may be an ast.FunctionDef or ast.AsyncFunctionDef.
  • The return value must be iterable and yield binding names as strings in the required order.

Required behavior

For both regular and async function definitions:

  1. Yield the function’s own name.
  2. Detect assignment-expression (:=) targets in definition-time expressions:
    • positional parameter defaults;
    • keyword-only parameter defaults;
    • positional-only parameter annotations;
    • regular parameter annotations;
    • *args annotations;
    • keyword-only parameter annotations;
    • **kwargs annotations;
    • return annotations;
    • decorator expressions.
  3. Do not yield parameter names merely because they are parameters.
  4. Do not yield ordinary referenced names from annotations, decorators, defaults, or the function body.
  5. A name merely referenced in the function body must not contribute a binding.

Ordering

  • Assignment-expression bindings in decorators are yielded before the function name. For example, a function named prop decorated with @(p := property) yields:
    • p
    • prop
  • Assignment-expression bindings in defaults and annotations are yielded after the function name.
  • Annotation bindings are ordered as follows:
    1. positional-only parameters;
    2. regular positional parameters;
    3. *args;
    4. keyword-only parameters;
    5. **kwargs;
    6. return annotation.

Thus, a function named function with annotation assignment targets named posonly_type, arg_type, args_type, kwarg_type, kwargs_type, and return_type in those respective locations yields:

function
posonly_type
arg_type
args_type
kwarg_type
kwargs_type
return_type

A positional default such as (b_binding := 2) yields function followed by b_binding. A keyword-only default such as (kw1_binding := 1) likewise yields function followed by kw1_binding.

All specified behavior and ordering apply equally to ast.FunctionDef and ast.AsyncFunctionDef.
