Task: Rename the concept "dependencies" to "requirements"

Overview

At the moment, the codebase contains a module that examines Python AST nodes to work out which names a node requires from its surrounding scope (i.e., names that must be defined elsewhere for the node to work). This concept presently goes by the name "dependencies" and must be renamed to "requirements". The public API surface must be updated to match.

The Required Public API

A module must be created at ssort/_requirements, and it must expose a function:

def get_requirements(node):
    ...
  • node: a Python AST node (of the kind produced by ast.parse, typically a single statement/expression node).
  • Returns: an iterable of requirement objects. Each object carries a .name attribute (a str) holding the name of a required (externally-defined) identifier.
  • The order of the returned objects must match the source order in which the names appear (with the examples below providing the detail).

This module and function take the place of any previous ssort/_dependencies module / get_dependencies function. The old name no longer forms part of the API.

How get_requirements Behaves

Given a node, get_requirements(node) yields the free names that the node requires from an enclosing scope. Names that are bound/defined locally within the node's own scope are not requirements. For the following representative inputs, the .name values collected in order must be exactly:

Function definitions
  • When a function's body references a name defined outside, that name is required.
    • def function(): return name → ["name"]
    • a function that references a and b in its body → ["a", "b"]
  • Arguments shadow outer names: a parameter that the body uses is not required.
    • def function(arg): return arg → []
  • Local assignment also shadows: a name assigned inside the body before it is used is not required, but genuinely external names are.
    • the body assigns a and then uses a and b → ["b"]
  • Names bound by the "rest" part of a starred assignment target shadow.
    • a function that binds a (via unpacking) and returns value → ["value"]
  • A name used prior to being shadowed later on is still required if it is used in a way that requires the external binding; when a name is assigned and only the external one matters → ["b"] (a function assigns something and then references b).
  • Decorators, together with their arguments, are requirements.
    • @decorator(arg)\ndef function(): pass → ["decorator", "arg"]
  • nonlocal declarations: a nonlocal a that references an enclosing name → ["a"].
    • nonlocal inside a closure: still ["a"].
    • a closure that itself captures the nonlocal name locally → [].
  • global declarations: global a used → ["a"].
    • global inside a closure → ["a"].
    • global inside a closure that does not capture → ["a"].
  • Async function definitions behave the same way as regular functions:
    • referencing the external name other → ["other"].
Class definitions
  • Class definitions yield the external names referenced in the base classes, the decorators, and the body, in source order (e.g. a class construction referencing multiple external names yields them in order).
Statements
  • return a + b → ["a", "b"]
  • del something → ["something"]
  • del a, b → ["a", "b"]
  • del a[b:c] → ["a", "b", "c"]
  • del obj.attr → ["obj"]
  • Assignment a = b → ["b"] (the target of the assignment is not a requirement).
  • Augmented assignment a += b → ["b"].
  • Annotated assignment (a: T = b) → ["b"] (the annotated form, which references the external b, yields ["b"]).
  • for loops: the iterable, along with any external names used in the body/else, are requirements; the loop target is bound (not required). For a loop of the kind that iterates and uses several external names → ["b", "c", "e", "g"].
    • When the loop target name is also used to produce the iterable (for a in a(): ...), the target replaces the outer scope, so a, in its role as the callable, is still required → ["a"].
  • async for works identically to for → ["b", "c", "e", "g"].
  • while loops: the predicate, then the body/else external names, in order → ["predicate", "action", "cleanup"].
  • if statements: test, then body, then else, in order → ["predicate", "subsequent", "alternate"].
  • with statements: the external names of the context expression, then those of the body → ["A", "b"].
    • async with acts identically → ["A", "b"].
  • raise Exception(message) → ["Exception", "message"].
  • try/except/else/finally: the external names referenced throughout, in source order.
  • assert, the plain control-flow statements (break/continue/pass), import, import ... from, a bare global/nonlocal at module level, and expression statements all produce results consistent with the definitions given here (import statements or pure control-flow keywords introduce no requirements).
Interaction of with statement bindings

For a with block shaped like this:

with chdir(os.path.dirname(path)):
    requirements = get_requirements(node)
    ...

the requirements that are collected must be:

["chdir", "os", "path", "get_requirements", "node"]

(that is, the context manager callable and its argument names in order, followed by the names used in the body that are not locally bound; names assigned within the body are excluded from requirements).

Expressions
  • Boolean ops, named expressions (:=), conditional expressions, sets, generator expressions, await, yield, yield from, comparisons, formatted values / f-strings, constants, starred expressions, lists — all of them yield the external names they reference in source order.
  • a + b → ["a", "b"]
  • A unary op on plus → ["plus"]
  • lambda: parameters shadow; a lambda that references the external other → ["other"].
  • A dict literal referencing the external value → ["value"]; {} → []; {**values} → ["values"].
  • Comprehensions bind their loop targets; the external names of the iterable and of the action expression are required:
    • list comprehension → ["action", "iterator"]
    • set comprehension → ["action", "iterator"]
    • dict comprehension → ["process_key", "process_value", "iterator"]
  • Calls: the callable, then the argument names, in order.
    • function(*args) → ["function", "args"]
    • the kwarg unpacking form → ["function", "kwargs"]
    • obj.method(arg_value, kwarg=kwarg_value) → ["obj", "arg_value", "kwarg_value"]
  • Attribute access: obj.attr → ["obj"].
  • Subscripting: array[key] → ["array", "key"].
    • array[start:end] → ["array", "start", "end"]
    • array[:end] → ["array", "end"]
    • array[start:] → ["array", "start"]
    • array[:] → ["array"]
  • A plain name: name → ["name"].
  • A tuple: (a, b) → ["a", "b"]; (a, *b) → ["a", "b"].

An Additional Requirement

Elsewhere in the codebase there is a name-binding analysis (a facility in the style of get_bindings). It must continue to work so that, for a with block like the one shown above (context manager chdir(os.path.dirname(path)) with a body that assigns names), the bindings it produces reflect the names bound inside, consistent with the existing binding behavior. Apart from keeping it consistent with the renamed requirements concept, no behavioral change to the binding logic is required.

Change Summary

The rename covers the module ssort/_dependencies → ssort/_requirements and the function get_dependencies → get_requirements, with all existing analysis behavior preserved exactly as specified above. All internal usages must be updated so that the package keeps functioning with the new name.

02 Sorting Statements by Dependency Order 513 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Sorting Statements by Dependency Order

Goal

Implement a function that rearranges the top-level statements of a Python source file so that definitions appear before the code depending on them, with the order of use serving as the tie-breaker.

Public API

Supply a module ssort that exposes the callable:

def ssort(source: str) -> str
  • Input: A string that contains valid Python source code.
  • Output: A string with the same statements, rearranged into the order described below. Each statement's original text is preserved, and the output retains a trailing newline consistent with normal source formatting.

Required behavior

ssort parses the input's top-level statements, works out the dependency relationships between them, and emits them in an order in which a statement that another statement depends on comes before its dependent — subject to the tie-breaking and cycle rules below.

Dependency-driven ordering

Whenever one statement references a name that another statement defines, the defining statement must be placed before the referencing one.

When a later statement requires multiple independent definitions, those definitions must be emitted in the order in which that later statement first uses them (that is, dependencies are ordered according to their order of use).

Concretely, when definitions are referenced only by a subsequent statement and that subsequent statement uses them in a particular sequence, the definitions must be output in that sequence of first use — even if this differs from their original source order.

As an example, input where main calls _step1() then _step2(), but in which _step2 is defined before _step1 in the source, must be reordered so that _step1 precedes _step2, both of them preceding main.

Cycles

When statements take part in a dependency cycle (each function in the group calls another, forming a loop), the cycle's members are emitted with their original relative order preserved.

  • A direct cycle among statements A→B→C→A, with source order A, B, C, is emitted unchanged.
  • A reversed cycle in which A depends on C, B depends on A, and C depends on B (source order A, B, C) is emitted unchanged.
Cycles with dependents outside the cycle

If a statement outside a cycle depends on a member of that cycle, the cycle members must appear before the dependent, while the internal order of the cycle members is otherwise kept intact.

For instance, with this source order:

def c():
    return a()
def a():
    return b()
def b():
    return a()

where a and b form a cycle and c depends on a, the required output order is a, c, b — cycle member a is promoted ahead of its dependent c, and the remaining cycle member b follows.

How references are resolved

Name references that occur inside function bodies (e.g. calls like b() within def a(): return b()) count as dependencies of the enclosing function on the referenced definition.

Notes

  • The reordering acts on top-level definitions and statements.
  • The source text of statements (bodies and indentation included) is preserved verbatim; only the ordering of statements changes.

Overview

Changes Required

1. Removal of the presorting module

    __slots__ = ("int_attr", "str_attr")
    str_attr: str

the resulting output is:

class Struct:
    __slots__ = ("int_attr", "str_attr")
    int_attr: int
    str_attr: str

For the input:

class Table:
    column = None
    __tablename__ = "table"
    __slots__ = ("column", "other_column")
    other_column = None

the resulting output is:

class Table:
    __slots__ = ("column", "other_column")
    __tablename__ = "table"
    column = None
    other_column = None

Here __slots__ moves to the top, while __tablename__ (an unknown dunder) keeps its place among the normal attributes as if it were a normal attribute, so the relative order with the other attributes is preserved.

2. Reporting unresolved dependencies (deterministic order)

If a file references names that cannot be resolved (unresolved dependencies), the check mode must emit one ERROR message per unresolved reference. If a single statement references multiple unresolved names, all such names must be reported.

The requirements are:

  • Each unresolved reference produces a message with exactly this form:

    ERROR: unresolved dependency '<name>' in <path>: line <L>, column <C>

    where <name> is the unresolved identifier, <path> is the repr of the file path (i.e. quoted the way Python would repr a path), and <L>/<C> are the 1-based line and 0-based column of the reference within the source file. Each message is terminated by a trailing newline.

  • When multiple unresolved dependencies occur, the messages must be emitted in a deterministic order: they are sorted by their source position (line first, then column). For example, two unresolved names that appear on the same line are reported left-to-right by column.

  • After the per-file diagnostics, a summary line is emitted that describes the outcome across all processed files, of the form:

    <N> files would be left unchanged, <M> file would not be sortable

    (with the counts using the appropriate singular/plural forms), followed by a trailing newline.

  • In this situation, the overall status code is 1.

Concrete example: take a file whose sole public function has the body return _other() + _same(), where _other and _same are both undefined, and where that expression is on line 6, with _other at column 11 and _same at column 22. The messages emitted are:

ERROR: unresolved dependency '_other' in '<path>': line 6, column 11
ERROR: unresolved dependency '_same' in '<path>': line 6, column 22

in that order (column 11 comes before column 22).

Constraints

  • Statements that the rules above do not affect must have their relative order preserved.
  • The scope covers only the behaviors described here.

Change that is required

The package-level function must be exposed:

from ssort import ssort

together with the callable interface:

ssort(source: str) -> str

It must apply the class-member ordering behavior described below while leaving each member’s source text and formatting unchanged.

Dependencies at runtime and on initialization

Whenever a class assignment aliases a method, and that method uses self to reference another method, the referenced method must be ordered first, the alias target must follow, and the assignment must come after that.

For example, given the input:

class Loopy:

    def method(self):
        return self._method()

    attr = method

    def _method(self):
        pass

the function must produce:

class Loopy:

    def _method(self):
        pass

    def method(self):
        return self._method()

    attr = method

Consequently, the runtime dependency from method to _method must be respected alongside the class-initialization dependency from attr to method.

Class attributes that resemble dunder names

In the case of a class containing these assignments, __slots__ must be placed first, but __tablename__ must remain among the ordinary class attributes instead of being promoted alongside __slots__.

class Table:

class Table:

20 Modify ssort._bindings.get_bindings(node). 330 words · source specification, reworded by GLM-5.3-Flash

Binding discovery for function definitions

Modify ssort._bindings.get_bindings(node).

Public interface

  • The module is ssort._bindings.
  • The callable is get_bindings(node).
  • The node argument may be an ast.FunctionDef or an ast.AsyncFunctionDef.
  • The return value must be iterable, and it must yield binding names as strings in the required order.

Behavior requirements

For both regular and async function definitions, the rules below apply:

  1. Yield the name of the function itself.
  2. Identify the targets of assignment expressions (:=) that appear in definition-time expressions:
    • defaults of positional parameters;
    • defaults of keyword-only parameters;
    • annotations of positional-only parameters;
    • annotations of regular parameters;
    • annotations on *args;
    • annotations of keyword-only parameters;
    • annotations on **kwargs;
    • return annotations;
    • decorator expressions.
  3. Do not yield parameter names merely on the grounds that they are parameters.
  4. Do not yield ordinary referenced names that come from annotations, decorators, defaults, or the function body.
  5. A name that is merely referenced in the function body must not contribute a binding.

Ordering of yields

  • Bindings from assignment expressions located in decorators are yielded before the function name. As an example, a function named prop decorated with @(p := property) yields:
    • p
    • prop
  • Bindings from assignment expressions located in defaults and annotations are yielded after the function name.
  • Bindings arising from annotations are ordered as follows:
    1. positional-only parameters;
    2. regular positional parameters;
    3. *args;
    4. keyword-only parameters;
    5. **kwargs;
    6. return annotation.

As a consequence, if a function named function has annotation assignment targets named posonly_type, arg_type, args_type, kwarg_type, kwargs_type, and return_type in those respective locations, it yields:

function
posonly_type
arg_type
args_type
kwarg_type
kwargs_type
return_type

With a positional default such as (b_binding := 2), the result yields function followed by b_binding. With a keyword-only default such as (kw1_binding := 1), the result likewise yields function followed by kw1_binding.

All of the specified behavior and ordering applies equally to ast.FunctionDef and ast.AsyncFunctionDef.
