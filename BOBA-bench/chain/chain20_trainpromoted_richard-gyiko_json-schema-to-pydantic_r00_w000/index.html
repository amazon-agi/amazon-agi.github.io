Task: JSON Schema to Pydantic Model Converter

Overview

Implement a class that converts JSON Schema definitions into dynamically-generated Pydantic model classes. The generated models must enforce the validation rules and type constraints declared in the schema.

Public API

Create the module autogen_mcp_tool_adapter.schema_builder containing a class:

class JsonSchemaToPydantic:
    def convert_schema_to_model(self, schema: dict, model_name: str) -> type:
        ...
  • schema is a JSON Schema dictionary (object type at the top level, with a "properties" mapping).
  • model_name is the name to give the generated model class.
  • The return value is a Pydantic model class (not an instance). Instantiating it with keyword arguments corresponding to schema properties must validate and coerce the inputs according to the schema. Invalid inputs must raise ValueError (a Pydantic ValidationError satisfies this, since it is a subclass of ValueError).

Required Behavior

Basic type mapping

Map JSON Schema "type" values to Python/Pydantic types on generated fields:

  • "string" → str
  • "integer" → int
  • "number" → float
  • "boolean" → bool
Optional vs. required fields
  • By default, every property is optional with a default value of None. A model instantiated with no arguments must have every non-required field set to None.
  • Property names listed in the schema's top-level "required" array must be enforced. Instantiating the model without providing a required field must raise ValueError.
  • Optional fields may be explicitly set to None.
Nested objects

A property with "type": "object" and its own "properties" must be converted to a nested generated model. When instantiating the parent model, passing a dict for such a field must produce a nested model instance whose fields are accessible via attribute access (e.g. instance.nested.field).

Arrays
  • A property with "type": "array" and an "items" schema must become a list field whose elements are validated against the item schema.
  • Item schemas may themselves be objects (producing nested models) or basic-typed values.
  • If the array property also declares "uniqueItems": true, the field must be represented as a set rather than a list. Duplicate values passed in are deduplicated (the resulting value is a set).
String constraints
  • "minLength" and "maxLength" on a string field must be enforced. Strings shorter than minLength or longer than maxLength must raise ValueError.
Numeric constraints
  • "minimum" and "maximum" must be enforced as inclusive bounds.
  • "exclusiveMinimum" must be enforced as a strict lower bound (a value equal to the bound is invalid).
  • "exclusiveMaximum" must be enforced as a strict upper bound (a value equal to the bound is invalid).
  • "multipleOf" must be enforced: a numeric value that is not an integer multiple of the given number must raise ValueError.

Violations of any numeric constraint must raise ValueError; values within bounds must be accepted and stored unchanged.

String formats

A string property with a "format" value must be converted to the corresponding Python type:

  • "email" → validated email string
  • "date" → datetime.date
  • "date-time" → datetime.datetime
  • "uri" → a URI value
  • "uuid" → uuid.UUID

Instantiating the model with appropriate values must produce attributes of the corresponding Python types: a date field yields a datetime.date, a date-time field yields a datetime.datetime, and a uuid field yields a uuid.UUID. A UUID may be supplied as its string representation and must be coerced to a UUID instance.

Enums

A property that declares an "enum" list must be converted to a Python Enum class:

  • String enums ("type": "string" with string choices) and integer enums ("type": "integer" with numeric choices) must both be supported.
  • The stored attribute must be an enum member; its underlying value is accessible via .value (e.g. a "color" set to "red" yields a member whose .value == "red"; a numeric choice set to 2 yields a member whose .value == 2).
  • Supplying a value not present in the enum list must raise ValueError.
Additional properties
  • When the schema declares "additionalProperties": false, the generated model must reject any keyword argument that does not correspond to a defined property. Passing an undefined field must raise ValueError.
  • A top-level "$schema" key in the schema must be ignored (it is metadata, not a property) and must not produce a field or cause an error.

Notes

  • Valid inputs must be accepted and their values retained/coerced as described; invalid inputs must raise ValueError.
  • Nested objects and array-of-object items follow all the same rules recursively (types, required fields, constraints).
02 JSON Schema to Pydantic Model Converter — Schema Composition & Nested Structures 830 words · source specification

Task Specification: JSON Schema to Pydantic Model Converter — Schema Composition & Nested Structures

Public API

Implement a class JsonSchemaToPydantic importable from the module tests' target under test (the same module currently providing this class; it is imported as from <module> import JsonSchemaToPydantic). The class must expose:

class JsonSchemaToPydantic:
    def convert_schema_to_model(self, schema: dict, model_name: str) -> type[pydantic.BaseModel]:
        ...

convert_schema_to_model takes a JSON Schema dict and a model name string, and returns a dynamically constructed Pydantic model class. Instances are constructed by keyword arguments matching the schema's top-level properties. Invalid input must raise ValueError (Pydantic's ValidationError is a subclass of ValueError, which satisfies this).

This task extends the converter to correctly handle four JSON Schema features described below. Each is exercised as a property of a top-level object schema.

1. anyOf handling

A property whose value is a schema containing an anyOf list of subschemas must accept a value matching any one of the listed subschemas.

  • Given subschemas [{"type": "string"}, {"type": "number"}, {object schema}]:
    • A string value is accepted and stored unchanged.
    • A numeric (float) value is accepted and stored unchanged.
    • An object value matching the object subschema is accepted and converted into a nested model instance whose fields are accessible as attributes (e.g. .name, .value).
    • A boolean value must be rejected (raise ValueError), because boolean is not among the allowed types. In particular, a bool must not be silently coerced to satisfy the number/string variants.

2. oneOf handling with discriminator

A property whose value is a schema containing a oneOf list of object subschemas together with a discriminator object ({"propertyName": ...}) must select exactly one variant based on an injected discriminator field.

  • Each of the N object subschemas in oneOf is treated as a distinct variant model. Every variant model gains an extra required literal field named type, whose allowed value is "variant_<index>" where <index> is the zero-based position of the subschema in the oneOf list (e.g. first subschema → "variant_0", second → "variant_1").
  • To construct the property, the input dict must include a type key selecting the variant. The remaining keys are validated against that variant's schema.
    • Example: {"type": "variant_0", "code": 200, "message": "Success"} selects the first variant; the resulting nested instance exposes .type == "variant_0", .message == "Success", and .code as an enum member whose .value == 200.
    • Example: {"type": "variant_1", "error": "Not Found", "details": ["Resource missing"]} selects the second variant; the resulting nested instance exposes .type == "variant_1", .error == "Not Found", and .details as a list equal to ["Resource missing"].
  • If the type discriminator key is absent from the input, raise ValueError.
  • If the type discriminator value does not correspond to any variant (e.g. "invalid"), raise ValueError.

Note on enums: within a variant subschema, a property defined with enum (e.g. {"type": "integer", "enum": [200, 201]}) must be represented as an enumeration type. The stored value is an enum member exposing its underlying value via .value.

3. allOf handling

A property whose value is a schema containing an allOf list of object subschemas must produce a model that merges all subschemas: it contains the union of all their properties, and enforces the union of all their required constraints.

  • Given two object subschemas, one requiring id (with optional name) and one requiring email (with optional active), a value providing all four fields is accepted; the resulting nested instance exposes .id, .name, .email, and .active.
  • A value missing a field required by any of the combined subschemas (e.g. missing email) must raise ValueError.

4. Deeply nested arrays and objects

Arbitrarily nested combinations of array and object schemas must be fully recursively converted into nested Pydantic models.

  • An array schema with items produces a list of the item type; object items become nested model instances.
  • Nested objects at every depth become nested models whose properties are accessible as attributes, with each level's required constraints enforced.
  • An array schema with "uniqueItems": true produces a set rather than a list. Its element membership is testable (e.g. "architect" in value), and the stored value's type is set.
  • Arrays without uniqueItems remain lists (their stored value's type is list).

Example: a schema departments → array of objects, each with teams → array of objects, each with members → array of objects having id, name, and roles (array of strings with uniqueItems: true). Constructing from nested dict/list input yields nested model instances at each level: instance.departments[0].name, instance.departments[0].teams[0].team_name, instance.departments[0].teams[0].members[0].name all accessible, and .roles is a set.

General Requirements

  • Nested object schemas (appearing directly, or inside anyOf/oneOf/allOf/array items) must be converted into nested Pydantic model classes so their fields are accessible as attributes on constructed instances.
  • Scalar values passed for scalar schema types are stored unchanged (no unnecessary wrapping).
  • All validation failures — type mismatches, missing required fields, disallowed types, invalid discriminator values, missing discriminators — must raise ValueError (or a subclass such as Pydantic's ValidationError).
03 Implement a utility that converts a JSON Schema (object type) into a dynamically-constructed Pydantic model class (a subclass of pydantic.BaseModel). 864 words · source specification

Task: JSON Schema to Pydantic Model Builder

Overview

Implement a utility that converts a JSON Schema (object type) into a dynamically-constructed Pydantic model class (a subclass of pydantic.BaseModel). The generated model must validate input data according to the constraints expressed in the schema.

Public API

Provide a class named PydanticModelBuilder that is importable from both of these module paths:

  • autogen_mcp_tool_adapter.pydantic_model_builder
  • autogen_mcp_tool_adapter.schema_builder_1

Both import paths must expose the same behavior.

The class must expose:

class PydanticModelBuilder:
    def create_pydantic_model(self, schema: dict) -> type[BaseModel]:
        ...

create_pydantic_model accepts a JSON Schema dictionary and returns a Pydantic model class (not an instance). The returned class must be usable via both direct construction (Model(field=value, ...)) and Model.model_validate({...}). Invalid input in either case must raise an error that is (or subclasses) ValueError.

Input Schema Structure

The top-level schema is an object schema:

{
  "type": "object",
  "properties": { "<field_name>": <field_schema>, ... },
  "required": ["<field_name>", ...]
}
  • Each entry in properties becomes a field on the model, keyed by property name.
  • The required list (optional; absent means no required fields) names the fields that must be present.
  • Fields listed in required are mandatory: constructing/validating without them raises ValueError.
  • Fields not in required are optional and default to None when omitted. An optional field may be explicitly supplied as None.

Field Types and Constraints

Each field schema may specify a type or a schema combinator (anyOf/oneOf/allOf). Support the following.

Basic Types

Map JSON Schema types to Python/Pydantic types:

  • "string" → str
  • "integer" → int
  • "number" → float
  • "boolean" → bool
  • "object" → see Nested Objects
  • "array" → see Arrays

Valid values of the correct type must pass validation and be accessible as attributes with the correct Python value. For example, number fields accept float values, boolean fields preserve True/False.

String Constraints

For "string" fields, honor:

  • minLength — minimum character length.
  • maxLength — maximum character length.
  • pattern — a regular expression the entire value must match.

Values violating any of these must raise ValueError.

Numeric Constraints

For "integer" and "number" fields, honor:

  • minimum — inclusive lower bound.
  • maximum — inclusive upper bound.
  • exclusiveMinimum — exclusive lower bound.
  • exclusiveMaximum — exclusive upper bound.
  • multipleOf — the value must be an exact multiple of this number.

Values violating any of these must raise ValueError. (For example, with exclusiveMaximum: 100, the value 100 is invalid; with multipleOf: 0.5, the value 95.7 is invalid.)

Array Fields

For "array" fields:

  • items — the schema describing each element's type (e.g. {"type": "string"}).
  • minItems — minimum number of elements.
  • maxItems — maximum number of elements.
  • uniqueItems — when true, duplicate elements must be removed/collapsed so that only unique elements remain. Element order need not be preserved for unique arrays; the resulting collection must contain exactly the set of distinct values.

Arrays without uniqueItems preserve their elements as a list. minItems/maxItems violations must raise ValueError (e.g. an empty array where minItems is 1, or 4 elements where maxItems is 3).

When uniqueItems is true, the count constraints (minItems/maxItems) apply, and duplicate values collapse to a single value (e.g. ["python", "python"] yields a collection whose distinct contents are {"python"}).

Nested Objects

A field of "type": "object" with its own properties produces a nested model. Given input as a dict, the nested value must validate against the nested schema and expose its sub-fields as attributes (e.g. instance.nested.field returns the nested string value).

Schema Combinators

Field schemas may use combinators instead of a plain type:

anyOf

{"anyOf": [<schema>, <schema>, ...]} — the value is valid if it matches at least one of the listed sub-schemas. A value matching none of them must raise ValueError.

Note that type discrimination must be strict enough that a boolean value is not accepted by a sub-schema of {"type": "number"} (i.e. True is invalid for an anyOf of string/number/object).

For anyOf fields, the validated value is exposed in its natural form: string values as str, numeric values as their number, and object values as a dict whose keys are accessible via item access (e.g. instance.flexible_field["name"]).

oneOf

{"oneOf": [<schema>, <schema>, ...]} — the value is valid if it matches one of the listed sub-schemas. A value matching none of the sub-schemas must raise ValueError. Object-typed matches are exposed as a dict accessible via item access.

allOf

{"allOf": [<schema>, <schema>, ...]} — the value must satisfy all listed sub-schemas simultaneously. In particular, when multiple sub-schemas are object schemas with their own required lists, the value must satisfy the union of all required fields; missing any required field from any sub-schema must raise ValueError. A value meeting all constraints is exposed as a dict accessible via item access (e.g. instance.user["id"]).

Error Behavior

All validation failures (missing required fields, type mismatches, constraint violations, unmatched combinators) must raise an exception that is caught by except ValueError (Pydantic's ValidationError satisfies this).

Notes

  • enum and format keywords may appear within combinator sub-schemas in input; they need not impose additional validation beyond what is described above, but their presence must not break model construction.

Class ConstraintBuilder

Instantiable with no arguments.

Method build_constraints(self, schema: dict)

Translates a single JSON Schema fragment into either a dict of Pydantic field constraint keyword arguments, or a direct type/typing construct when the schema implies a specific type. Behavior:

  • Format precedence: If the schema contains a "format" key, its value determines the return value directly (ignoring all other keys):

  • "minimum": the larger (more restrictive) of the two values.
  • "maximum": the smaller (more restrictive) of the two values.
  • "minLength": the larger of the two values.
  • "maxLength": the smaller of the two values.

  • Merging with an empty schema yields the non-empty schema's values unchanged.

Class TypeResolver

Instantiable with no arguments.

Method resolve_type(self, schema: dict, root_schema: dict)

Returns the Python/typing type implied by a JSON Schema fragment:

  • Basic types: "string" → str, "integer" → int, "number" → float, "boolean" → bool.
  • "null" type → typing.Optional[typing.Any].
  • A "type" given as a list containing "null" and one other type (e.g. ["string", "null"]) → typing.Optional[<that type>].
  • Array ("type": "array" with "items"): → typing.List[<resolved item type>], resolved recursively (nested arrays → List[List[...]]).
  • Object ("type": "object" with "properties"): → a type that is a subclass of dict. Nested array/typed properties are handled recursively.

  • "const": → typing.Literal[value]; a const of None → typing.Optional[typing.Any].
Class ReferenceResolver

Instantiable with no arguments.

Method resolve_ref(self, ref: str, schema: dict, root_schema: dict)

Resolves a local JSON Schema reference against root_schema and returns the resolved fragment (dict):

  • Only local references beginning with #/ are supported. A reference that is a URL/external reference (e.g. starting with http) must raise ReferenceError with a message containing "Only local references".
  • The reference is a JSON Pointer. Split on / after the leading #, and navigate through root_schema. Apply JSON Pointer unescaping to each segment: ~1 → / and ~0 → ~.
  • If any path segment does not exist in the structure, raise ReferenceError with a message containing "Invalid reference path".
  • An empty reference string and a malformed reference (not beginning with #/) must raise ReferenceError.
  • If the resolved target is itself a $ref, follow it (resolve nested references) and return the ultimately resolved fragment.
  • Recursively traverse the entire resolved fragment, including descendant dictionaries and list/collection members. Any descendant schema node containing a local $ref must be replaced by its fully resolved target. This includes, for example, references used as nested object properties and references inside collection members; resolution is not limited to a target whose top level is itself a $ref.
  • Detect circular references in both direct reference chains and descendant traversal. Reference tracking must remain active while the whole target fragment is recursively expanded; if a descendant reference points back to a target that is already being resolved, raise ReferenceError with a message containing "Circular reference detected".

Validates that a JSON Schema fragment is well-formed. Returns normally (no return value required) when valid; raises ValidationError when invalid. Rules:

Class CombinerHandler

Instantiable with no arguments.

Method handle_all_of(self, schemas: list, root_schema: dict)

Given a list of object schema fragments, produce a single Pydantic model (subclass of pydantic.BaseModel) that merges all their properties and required fields, and merges overlapping property constraints using the most-restrictive-merge rules. Behavior:

  • The resulting model has all properties from every schema; a property required in any schema is required in the result.
  • When the same property appears in multiple schemas with numeric constraints (e.g. minimum/maximum), the merged constraints are the most restrictive combination and are enforced on validation (out-of-range values raise ValueError).
  • An empty list raises CombinerError.

An empty list raises CombinerError.

Method handle_one_of(self, schema: dict, root_schema: dict)

Given a schema dict containing a "oneOf" key (a list of object fragments), produce a Pydantic model implementing a discriminated union keyed on a "type" property whose value is a const. Behavior and structure:

  • The produced model is a pydantic.BaseModel subclass exposing a single field named root (i.e. a RootModel-style wrapper). The chosen variant is accessible via instance.root, and its properties are accessed as attributes of instance.root.
  • Each variant fragment must be an object with a "type" property whose schema has a "const" value; this const is the discriminator value. A variant lacking such a discriminator raises CombinerError. A non-dict entry in the oneOf list raises CombinerError. An empty oneOf list raises CombinerError.

  • Property field metadata: a property schema's "description" becomes the corresponding Pydantic field's description. For a chosen variant model reachable at model.model_fields["root"].annotation, its model_fields expose each property with the correct description.
  • Nested oneOf inside a property is itself resolved into a nested discriminated-union model, so nested values are accessed via chained .root attributes (e.g. instance.root.child.root.type).

1. TypeResolver.resolve_type: constants, nulls, and nullable types

  • {"const": None} resolves to exactly type(None), including object identity (result is type(None)).
  • {"type": "null"} resolves to exactly type(None), including object identity.
  • {"const": 42} resolves to Literal[42].
  • {"type": ["string", "null"]} resolves to an optional/nullable string annotation equivalent to Optional[str], regardless of the position of "null" in the two-type list.
2. Direct resolver annotation compatibility for arrays of objects

A direct TypeResolver.resolve_type call must retain its annotation-level behavior independently of generated-class behavior:

  • For a non-unique array whose items is an inline fixed-shape object schema, the result must be equivalent to typing.List[dict].
  • The same result is required when the object item is reached through a local $ref, including a chain of local references.
  • More precisely, typing.get_origin(result) must be the built-in list, and typing.get_args(result)[0] must be exactly the built-in dict.
  • Resolving an object schema directly continues to produce dict; TypeResolver must not expose a dynamically generated Pydantic element class in these annotations.
  • Primitive and nested-array annotations continue to resolve recursively, such as List[str] and List[List[str]].
  • With uniqueItems: true, the collection annotation is a set rather than a list. Its item annotation follows the same resolver rules, so an object item remains dict at this direct-resolution layer.

This direct result is intentionally different from the runtime representation produced by the model-building entry points described below.

When create_model or PydanticModelBuilder.create_pydantic_model builds a field for an array, its items schema must be processed recursively for model construction.

If the item schema describes an object with declared properties, each validated collection element must be an instance of a generated Pydantic class. This applies when the item object is:

  • declared inline inside items;
  • reached through a local $ref in definitions or $defs;
  • reached through multiple levels of local $ref indirection; or
  • nested inside another object-array item.

Declared properties of these elements must be available through attribute access. For example, the following access patterns must work after validation:

instance.a[0].b
instance.history[0].timestamp
instance.items[0].id
instance.items[0].nested_items[0].name
instance.items[0].nested_items[0].value

The conversion must be recursive at every array/object boundary. If an outer array element is a fixed-shape object and one of its properties is another array of fixed-shape objects, both outer and inner elements must be Pydantic instances. Required fields, property types, and the existing field behavior of each generated nested class must continue to be enforced.

Inline item objects do not need a pre-existing definition name in order to receive this behavior. No particular generated class name is required; the public requirement is the validated representation and its field behavior.

For example, given an array field whose items resolve to an object with integer property b:

Generated = create_model(root_schema)
value = Generated.model_validate({"a": [{"b": 1}, {"b": 2}]})

assert value.a[0].b == 1

instance.items[0].metadata["key1"]

It must not be converted merely to enable attribute access. The fixed-shape containing item can be a Pydantic instance while its map-valued metadata property remains a dictionary.

Likewise, an object item or value that does not declare a fixed property structure remains dictionary-valued rather than becoming a generated nested class.

5. Primitive, undefined, and loosely typed array items
  • Arrays with primitive item schemas validate to ordinary Python collections containing those primitive values. For non-unique arrays this means ordinary lists, such as lists of strings or booleans.
  • By default, an array without an items schema is invalid and raises the library's schema TypeError with the established message Array type must specify 'items' schema.
  • When allow_undefined_array_items=True, an array without items resolves as List[Any]. This option must propagate through nested objects and through object schemas used as array items.
  • Values in an undefined or otherwise loosely typed array must be preserved without conversion to nested Pydantic instances solely because a particular runtime value is a dictionary. Mixed strings, integers, booleans, and dictionaries remain their corresponding raw Python values.

For example, an undefined actions array inside a generated history-item class can retain:

["reviewed", 123, {"status": "approved"}]

The history element itself is a Pydantic instance because its item schema has declared properties, while the dictionary inside its loosely typed actions list remains a dictionary.

6. uniqueItems

Array collection kind continues to follow uniqueItems:

  • absent or false uniqueItems produces a list-typed collection;
  • uniqueItems: true produces a set-typed collection.

This distinction applies both to direct resolver annotations and to generated fields. Fixed-shape object items still receive nested-Pydantic conversion in generated fields while using the collection kind selected by uniqueItems. Existing array length constraints and primitive-array behavior must remain unaffected.

Compatibility and Non-Goals

  • Do not change direct object-array resolution from List[dict] into List[GeneratedClass]; nested Pydantic conversion is observable through generated fields, not through the public direct resolver annotation.
  • Do not convert additionalProperties-only maps or dictionaries encountered as values of Any arrays into attribute-based objects.
  • Do not alter the handling of primitive types, formats, constants, enums, required/optional fields, defaults, constraints, local references, custom base classes, or schema combiners while adding recursive object-array field construction.
  • External references are outside this enhancement; the required reference behavior concerns local JSON Pointer references resolved against the supplied root schema.

Acceptance Summary

The completed behavior has two deliberately separate layers:

  1. Direct type resolution preserves its established public annotations, including List[dict] for ordinary arrays of inline or locally referenced objects.
  2. Model construction recursively specializes fixed-shape object items so validated list or set elements are nested Pydantic instances with attribute access, while maps, primitive values, and loosely typed content retain their existing plain Python representations.
