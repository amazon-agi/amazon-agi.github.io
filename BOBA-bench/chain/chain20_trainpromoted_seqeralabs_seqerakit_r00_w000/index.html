Specification of the Task

Change that is required

Deliver the seqerakit package under its new name, together with its YAML-helper and Seqera Platform command APIs.

Public API

The imports below must succeed:

from seqerakit import helper
from seqerakit import seqeraplatform

The following public interfaces must be exposed:

helper.parse_all_yaml(paths)

seqeraplatform.SeqeraPlatform(cli_args=None, dryrun=False)
seqeraplatform.ResourceExistsError
seqeraplatform.ResourceCreationError

In addition, SeqeraPlatform must expose _tw_run(command, **kwargs) as well as resource commands that are callable from Python, such as pipelines. The command that _tw_run accepts is an ordered Python list of command tokens.

The Python resource command for compute-environments must use compute-envs as its CLI resource name. In particular, when the Python-facing compute_envs command is invoked, the token list produced must have compute-envs as its first item.

Parsing of YAML datasets

As input, helper.parse_all_yaml accepts a list of YAML paths. When a single path is given whose contents are:

datasets:
  - name: 'test_dataset1'
    description: 'My test dataset 1'
    header: true
    workspace: 'my_organization/my_workspace'
    file-path: './examples/yaml/datasets/samples.csv'
    overwrite: True

this call:

result = helper.parse_all_yaml(["test_path.yaml"])

must return a mapping that contains a datasets key, whose value is exactly:

[
    {
        "cmd_args": [
            "--header",
            "./examples/yaml/datasets/samples.csv",
            "--name",
            "test_dataset1",
            "--workspace",
            "my_organization/my_workspace",
            "--description",
            "My test dataset 1",
        ],
        "overwrite": True,
    }
]

The order of cmd_args is significant. header: true is turned into the standalone token --header. overwrite stays a separate Boolean field and must not be added to cmd_args.

Forwarding of resource commands

Once a resource callable has been resolved, it must:

  1. Resolve the CLI name of the resource and put it first.
  2. Append all positional arguments that were supplied, keeping their original order, so that one ordered Python list of tokens is produced.
  3. Invoke the _tw_run method currently on the instance exactly once, passing that list as the single positional argument.
  4. Forward all keyword arguments without modifying them.
  5. Return the value that _tw_run returns.

As an example:

sp.pipelines("view", "--name", "pipeline_name", to_json=True)

must be delegated in this way:

sp._tw_run(
    ["pipelines", "view", "--name", "pipeline_name"],
    to_json=True,
)

Before _tw_run is called, resource callables must not join this list into a string. The joining of tokens into the shell command happens only in the command-execution layer.

All resolved resource commands are covered by the same forwarding contract, and so are the exercised command forms list, add, launch, delete, view, and import. Keyword options such as params_file are included in this: the resource callable passes them through to _tw_run unchanged instead of incorporating them itself. With the compute-environments resource, the delegated list begins with compute-envs, not with the Python attribute spelling.

Execution of commands and JSON output

Within the _tw_run execution layer, the ordered command tokens are converted into the single-space-separated shell command while the token order is preserved.

When an instance is constructed with its defaults:

sp = seqeraplatform.SeqeraPlatform()

the call:

sp.pipelines("view", "--name", "pipeline_name", to_json=True)

must start exactly the subprocess below:

subprocess.Popen(
    "tw -o json pipelines view --name pipeline_name",
    stdout=subprocess.PIPE,
    stderr=subprocess.STDOUT,
    shell=True,
)

As a result, to_json=True adds -o json to the tw invocation. The output of the command is taken from the first value returned by communicate(); the return data is not supplied by the second value.

When to_json=True, the command output must be decoded and the parsed JSON value must be returned. For example, output of:

b'{"key": "value"}'

means the value returned must be:

{"key": "value"}

Larger JSON objects get the same treatment: the decoded JSON data is returned without its fields or values being altered.

Errors from command output

If the decoded command output is exactly:

ERROR: Resource already exists

then seqeraplatform.ResourceExistsError must be raised. Output that is exactly equal to:

ERROR: Already a participant

must lead to the same exception being raised.

If the decoded command output is exactly:

ERROR: Resource creation failed

then seqeraplatform.ResourceCreationError must be raised. When JSON output was requested, these errors must be recognized rather than being handled as JSON results.

CLI arguments with global scope

SeqeraPlatform accepts a list via cli_args. In shell commands generated for resource invocations, every supplied item must appear, and the supplied items must be retained in order.

As an example, an instance initialized with:

SeqeraPlatform(
    cli_args=["--url", "http://tower-api.com", "--insecure"]
)

must include all three strings in its generated command.

A custom trust-store item is accepted and is included verbatim:

-Djavax.net.ssl.trustStore=/absolute/path/to/cacerts

A list that is supplied stays live and is observable by an instance created from it; such an instance must not be isolated from later mutations of that list. Consequently, in this sequence:

  1. Construct an instance from a list.
  2. Append the trust-store item to that same list.
  3. Initialize another instance with the updated list.
  4. Invoke a command on the original instance.

the command generated by the original instance must contain the trust-store item that was appended.

The --verbose CLI argument is not supported. Constructing with:

SeqeraPlatform(cli_args=["--verbose"])

must raise ValueError carrying exactly this message:

--verbose is not supported as a CLI argument to seqerakit.

Behavior with dry-run

For:

sp = seqeraplatform.SeqeraPlatform(dryrun=True)
sp.pipelines("view", "--name", "pipeline_name", to_json=True)

no subprocess may be started.

Task Specification: Checking Environment Variables in SeqeraPlatform

Overview

The SeqeraPlatform class must be extended with a method that validates and processes command arguments that contain environment variable references before command execution.

Public API

Module: seqerakit.seqeraplatform

Class: SeqeraPlatform

Method to be implemented:

def _check_env_vars(self, command)
  • command is a list of string tokens that represent a command and its arguments (for instance, ["tw", "pipelines", "list", "-w", "$VAR1"]).
  • The method returns a single string formed by joining the command tokens with single spaces.

Behavior Requirements

Recognizing environment variable references

A token is treated as an environment variable reference when it starts with a $ character (e.g., $VAR1, $UNSET_VAR). The variable name being referenced is the portion of the token that follows the $.

Validation

For every token in the command that counts as an environment variable reference:

  • If the referenced variable is defined in the current process environment, the token remains unchanged in the output.

  • If the referenced variable is not defined in the current process environment, the method must raise EnvironmentError. The message of the exception must contain the substring:

     Environment variable '$UNSET_VAR' not found!

    where $UNSET_VAR is substituted with the actual token that was not found (note: the message includes a leading space before Environment, and the full $-prefixed token is wrapped in single quotes, followed by not found!).

Tokens that are not environment variable references

A token that does not start with $ passes through into the output unchanged. Ordinary tokens such as tw, info, pipelines, list, and -w are not modified.

Constructing the output

If no EnvironmentError is raised, the method returns all tokens joined by single spaces into one string, keeping their original order.

Examples

Assuming VAR1 is set in the environment:

  • Input: ["tw", "pipelines", "list", "-w", "$VAR1"]
  • Output: "tw pipelines list -w $VAR1"

When there are no environment variable references:

  • Input: ["tw", "info"]
  • Output: "tw info"

Assuming UNSET_VAR is not set in the environment:

  • Input: ["tw", "pipelines", "list", "-w", "$UNSET_VAR"]
  • Result: raises EnvironmentError whose message contains Environment variable '$UNSET_VAR' not found!

Construction

It must be possible to instantiate the SeqeraPlatform class with no required arguments (i.e., SeqeraPlatform() must succeed).

Task Specification: Parser from YAML to Command-Line Arguments

Overview

Implement a module seqerakit/helper.py that parses one or more YAML configuration files describing entities (organizations, workspaces, datasets, compute environments, pipelines) and turns every entity definition into a normalized structure containing command-line arguments.

Public Interface

# seqerakit/helper.py

def parse_all_yaml(paths: list[str]) -> dict:
    ...
  • paths is a list of strings giving file paths. Every path is opened and read as YAML.
  • It returns a dictionary keyed by the top-level entity type found in the YAML (e.g. "organizations", "workspaces", "datasets", "compute-envs", "pipelines"); each value is a list of parsed entity blocks.

Format of the Input

Every YAML file is a mapping with entity-type names as its top-level keys. Each of these keys maps to a list of entity definitions, and every entity definition is a mapping of key/value pairs.

Format of the Output

For each entity type key present in the parsed input, the output dictionary has that same key mapped to a list of blocks — one block per entity definition, with order preserved.

Each block is a dictionary containing these keys:

  • "overwrite": the boolean value taken from the entity's overwrite key. The key is consumed out of the entity definition and moved into the block (it is not emitted as a command-line argument).
  • "cmd_args": a list of strings giving the command-line arguments derived from the entity definition's remaining keys.

Rules for Constructing cmd_args

An entity's remaining key/value pairs (once the keys given special handling described below have been removed) are converted to command-line argument tokens by these rules:

General conversion of flags and values
  • For a normal key k with value v, two tokens are emitted: "--k" followed by the string form of v.
  • Keys keep their original hyphenated spelling (e.g. full-name → --full-name, compute-env → --compute-env, work-dir → --work-dir).
Boolean flags
  • A key whose value is the boolean True is emitted as a single token "--k" with no value after it (e.g. header: true → --header).
Keys handled as positional arguments

Certain keys are emitted as bare positional values (only the value, with no --flag prefix):

  • file-path (used by datasets and compute-envs)
  • url (used by pipelines)

Where the positional value sits in the cmd_args list is governed by the ordering rules below.

Special keys removed before the arguments are built
  • overwrite: consumed into the block's "overwrite" field, and never emitted as an argument.
  • params-file: consumed and not emitted into cmd_args at all. (It is dealt with separately and does not appear in the output block for these cases.)

Ordering Requirements

The order of tokens in cmd_args is different for each entity type. The orderings below must be produced exactly.

Organizations

Keys are emitted in alphabetical order of the flag name. For an entity having name, full-name, description, location, url, overwrite:

--description <v> --full-name <v> --location <v> --name <v> --url <v>

(Note: for organizations, url is emitted as a normal --url <value> flag, in its alphabetical position.)

Workspaces

Keys are emitted in alphabetical order of the flag name. For name, full-name, organization, description, visibility, overwrite:

--description <v> --full-name <v> --name <v> --organization <v> --visibility <v>
Datasets

The file-path positional value is emitted first, and the remaining flags follow it. For name, description, workspace, header (boolean true), file-path, overwrite:

<file-path value> --name <v> --workspace <v> --description <v> --header

After the positional, the flag order is: --name, --workspace, --description, then boolean --header last.

Compute-envs

Flags are emitted in alphabetical order of flag name, with the file-path positional value inserted at the position where it sorts among the flag names (i.e. sorted as if by the flag/positional key name). For name, workspace, credentials, file-path, wait, overwrite:

--credentials <v> <file-path value> --name <v> --wait <v> --workspace <v>

(The file-path value appears between --credentials and --name, matching file-path sorting after credentials and before name.)

Pipelines

Flags are emitted in alphabetical order of flag name, and the url positional value is emitted last. The params-file key is dropped and not emitted. For name, url, workspace, description, compute-env, work-dir, profile, params-file, config, pre-run, revision, overwrite:

--compute-env <v> --config <v> --description <v> --name <v> --pre-run <v> --profile <v> --revision <v> --work-dir <v> --workspace <v> <url value>

Summary: Positional vs. Flag Placement

  • Datasets: the positional (file-path) is placed at the beginning.
  • Compute-envs: the positional (file-path) is placed in alphabetical order among the other keys.
  • Pipelines: the positional (url) is placed at the end; params-file is excluded entirely.

Dependencies

  • YAML parsing (the yaml package) is used to load the file contents.
  • The file contents are read using the standard open built-in.

Every string value must appear in cmd_args as a plain string.

Task Specification: Handling Booleans as Flags in the YAML-to-CLI Conversion

Summary

The YAML parsing helpers in seqerakit.helper must be updated so that parsed YAML booleans turn into the conventional valueless command-line flags. A Boolean true emits the option name only, whereas false emits no command-line token. All existing resource-specific conversion behavior, output ordering, positional arguments, parameter-file handling, and overwrite handling must be preserved.

Boolean handling must be observable both when an in-memory YAML block is parsed and when one or more YAML files are parsed.

Public API

The helpers must stay available from seqerakit.helper, including via:

from seqerakit import helper
parse_yaml_block
def parse_yaml_block(yaml_data: dict, block_name: str) -> tuple
  • yaml_data is parsed YAML content in which top-level block names map to lists of resource-entry dictionaries.
  • block_name identifies the top-level block to convert.
  • Every entry in that block is processed by the function, in block-list order.
  • It returns (block_name, descriptors), where descriptors is an ordered list that contains one descriptor per entry.
  • For a missing or empty block, the function returns (block_name, []).
  • The existing validation that entry names within one block are unique must remain unchanged.

Every entry descriptor has this public shape:

{
    "cmd_args": list[str],
    "overwrite": bool,
}

cmd_args holds the generated CLI tokens. overwrite is entry metadata and does not belong to that token list.

parse_all_yaml
def parse_all_yaml(file_paths, destroy: bool = False) -> dict
  • Every supplied path is loaded as YAML.
  • When the same block appears in multiple files, its entries are combined in supplied-file order, and entry order within each file is retained.
  • The result maps each supported block name to its ordered list of entry descriptors, applying exactly the same descriptor and Boolean-conversion rules as parse_yaml_block.
  • The blocks keep the established dependency order: organizations, teams, workspaces, participants, credentials, compute-envs, secrets, actions, datasets, pipelines, and launch.
  • With destroy=True, the established reverse destruction order is kept and launch is excluded. This option must not alter entry conversion or Boolean handling.

Argument Conversion Requirements

For each ordinary entry key/value pair, a distinction must be made between actual parsed Boolean values and all other values before string conversion.

Boolean values
  • The Boolean True emits exactly one token: --<key>.
  • For the Boolean False, no tokens are emitted: neither the flag nor a value.
  • A Boolean must never come out as a two-token pair such as --<key> True or --<key> False.
  • A false option must not be swapped for a negated option such as --no-<key>.
  • Strings like "true" and "false" do not count as Boolean values and therefore follow the non-Boolean rule.

Examples:

"fusion-v2": True   # -> ["--fusion-v2"]
"stub-run": True    # -> ["--stub-run"]
"fargate": False    # -> []

These rules hold inside every descriptor's cmd_args, including for compute-environment and pipeline entries.

Non-Boolean values

If a key has no existing positional or resource-specific rule, non-Boolean values are emitted as two tokens:

["--<key>", str(value)]

For instance:

"credentials": "my_credentials"
# -> ["--credentials", "my_credentials"]
overwrite metadata

overwrite is a special metadata key and forms an exception to normal Boolean flag conversion:

  • Consume it separately from the generation of CLI arguments.
  • Its Boolean value is stored in the descriptor's separate overwrite field.
  • If the key is absent, the descriptor's overwrite value defaults to False.
  • Never put --overwrite, True, or False into cmd_args on this key's behalf, regardless of its value.

So overwrite: true results in "overwrite": True in the descriptor while contributing no command-line token.

Existing Special Keys and Resource-Specific Behavior

The existing special handling must be preserved:

  • file-path comes out as a bare positional value without a --file-path token, at the positional location that the existing resource conversion requires.
  • name stays --name followed by its string value.
  • Other established positional keys and resource-specific argument groupings stay as they are.
  • Existing pipeline source handling stays unchanged: a pipeline url or a positional file-path is emitted in the pipeline source-argument segment, and generated or supplied parameter-file arguments stay in their existing final segment.
  • Existing dataset behavior stays unchanged; for instance, header: true emits --header, while header: false emits nothing.

Ordering

  • Block-entry order and descriptor order must be preserved.
  • Within each existing argument segment, the loaded entry mapping's key order is preserved. Each key expands to two tokens, one token, or zero tokens as set out in the rules above.
  • Leaving out a false Boolean or consuming overwrite must not change the relative order of the remaining arguments.
  • Positional values and resource-specific argument segments must keep their pre-existing placement; Boolean support must not reorder arguments in any other way.

Worked Examples

Compute environment

Take a loaded entry with this key order:

credentials: my_credentials
fargate: false
file-path: ./examples/yaml/computeenvs/computeenvs.yaml
fusion-v2: true
name: test_computeenv
overwrite: true
wait: AVAILABLE
workspace: my_organization/my_workspace

the resulting descriptor is:

{
    "cmd_args": [
        "--credentials",
        "my_credentials",
        "./examples/yaml/computeenvs/computeenvs.yaml",
        "--fusion-v2",
        "--name",
        "test_computeenv",
        "--wait",
        "AVAILABLE",
        "--workspace",
        "my_organization/my_workspace",
    ],
    "overwrite": True,
}

fusion-v2: true turns into a bare flag, fargate: false vanishes completely, and overwrite: true is kept only as descriptor metadata.

Pipeline

For a pipeline entry that contains ordinary options plus:

revision: master
stub-run: true
overwrite: true

the following tokens appear in cmd_args:

["--revision", "master", "--stub-run"]

They sit at the corresponding location in the pipeline's regular option segment. cmd_args contains no --overwrite. Existing source and parameter-file arguments still come afterward in their established segments.

As an illustration, a complete parsed pipeline descriptor can look like this:

{
    "cmd_args": [
        "--compute-env", "my_computeenv",
        "--config", "./examples/yaml/pipelines/test_pipeline1/config.txt",
        "--description", "My test pipeline 1",
        "--name", "test_pipeline1",
        "--pre-run", "./examples/yaml/pipelines/test_pipeline1/pre_run.sh",
        "--profile", "test",
        "--revision", "master",
        "--stub-run",
        "--work-dir", "s3://work",
        "--workspace", "my_organization/my_workspace",
        "https://github.com/nf-core/test_pipeline1",
        "--params-file", "./examples/yaml/pipelines/test_pipeline1/params.yaml",
    ],
    "overwrite": True,
}

Compatibility and Non-Goals

  • Key spelling must stay untouched: the ordinary key some-option maps to --some-option.
  • Flags and values must not be merged into a single string; every CLI token remains a separate list element.
  • Never flatten the descriptor list into one argument list, and never return only the first entry.
  • Overwrite behavior must not be moved into the generated CLI command. It remains separately available to callers that decide whether an existing resource should be replaced.
  • Existing positional-argument, pipeline-source, parameter-file, dataset, or resource-order behavior must not be altered beyond the Boolean conversion described here.
