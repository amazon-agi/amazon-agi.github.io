Task Specification: Environment Variable Checking in SeqeraPlatform

Overview

Add a method to the SeqeraPlatform class that validates and processes command arguments containing environment variable references before command execution.

Public API Surface

Module: seqerakit.seqeraplatform

Class: SeqeraPlatform

Method to implement:

def _check_env_vars(self, command)
  • command is a list of string tokens representing a command and its arguments (for example, ["tw", "pipelines", "list", "-w", "$VAR1"]).
  • The method returns a single string: the command tokens joined together by single spaces.

Required Behavior

Identifying environment variable references

A token is treated as an environment variable reference when it begins with a $ character (e.g., $VAR1, $UNSET_VAR). The referenced variable name is the portion of the token following the $.

Validation

For every token in the command that is an environment variable reference:

  • If the referenced variable is defined in the current process environment, the token is left unchanged in the output.

  • If the referenced variable is not defined in the current process environment, the method must raise EnvironmentError. The exception message must contain the substring:

     Environment variable '$UNSET_VAR' not found!

    where $UNSET_VAR is replaced by the actual token that was not found (note: the message includes a leading space before Environment and wraps the full $-prefixed token in single quotes, followed by not found!).

Non-environment-variable tokens

Tokens that do not begin with $ are passed through unchanged into the output. Ordinary tokens such as tw, info, pipelines, list, and -w are not altered.

Output construction

When no EnvironmentError is raised, the method returns all tokens joined by single spaces into one string, preserving their original order.

Examples

Given VAR1 is set in the environment:

  • Input: ["tw", "pipelines", "list", "-w", "$VAR1"]
  • Output: "tw pipelines list -w $VAR1"

With no environment variable references:

  • Input: ["tw", "info"]
  • Output: "tw info"

Given UNSET_VAR is not set in the environment:

  • Input: ["tw", "pipelines", "list", "-w", "$UNSET_VAR"]
  • Result: raises EnvironmentError whose message contains Environment variable '$UNSET_VAR' not found!

Construction

The SeqeraPlatform class must be instantiable with no required arguments (i.e., SeqeraPlatform() must succeed).

04 YAML-to-Command-Argument Parser 771 words · source specification

Task Specification: YAML-to-Command-Argument Parser

Overview

Implement a module seqerakit/helper.py that parses one or more YAML configuration files describing entities (organizations, workspaces, datasets, compute environments, pipelines) and converts each entity definition into a normalized structure containing command-line arguments.

Public API

# seqerakit/helper.py

def parse_all_yaml(paths: list[str]) -> dict:
    ...
  • paths is a list of file path strings. Each path is opened and read as YAML.
  • Returns a dictionary keyed by the top-level entity type found in the YAML (e.g. "organizations", "workspaces", "datasets", "compute-envs", "pipelines"). Each value is a list of parsed entity blocks.

Input Format

Each YAML file is a mapping whose top-level keys are entity-type names. Each such key maps to a list of entity definitions. Every entity definition is a mapping of key/value pairs.

Output Format

For each entity type key present in the parsed input, the output dictionary contains that same key mapping to a list of blocks — one block per entity definition, preserving order.

Each block is a dictionary with the following keys:

  • "overwrite": the boolean value of the entity's overwrite key. This key is consumed from the entity definition and moved into the block (it is not emitted as a command-line argument).
  • "cmd_args": a list of strings representing the command-line arguments derived from the remaining keys of the entity definition.

Rules for Building cmd_args

The remaining key/value pairs of an entity (after removing the keys that receive special handling described below) are converted to command-line argument tokens according to these rules:

General flag/value conversion
  • For a normal key k with value v, emit two tokens: "--k" followed by the string form of v.
  • Keys retain their original hyphenated spelling (e.g. full-name → --full-name, compute-env → --compute-env, work-dir → --work-dir).
Boolean flags
  • A key whose value is boolean True is emitted as a single token "--k" with no following value (e.g. header: true → --header).
Positional argument keys

Certain keys are emitted as bare positional values (the value only, with no --flag prefix):

  • file-path (used by datasets and compute-envs)
  • url (used by pipelines)

The positional value's placement in the cmd_args list is governed by the ordering rules below.

Special keys removed before arg building
  • overwrite: consumed into the block's "overwrite" field, never emitted as an argument.
  • params-file: consumed and not emitted into cmd_args at all. (It is handled separately and does not appear in the output block for these cases.)

Ordering Requirements

The order of tokens in cmd_args differs by entity type. The following orderings must be produced exactly.

Organizations

Keys are emitted in alphabetical order of the flag name. For an entity with name, full-name, description, location, url, overwrite:

--description <v> --full-name <v> --location <v> --name <v> --url <v>

(Note: for organizations, url is emitted as a normal --url <value> flag, in alphabetical position.)

Workspaces

Keys emitted in alphabetical order of the flag name. For name, full-name, organization, description, visibility, overwrite:

--description <v> --full-name <v> --name <v> --organization <v> --visibility <v>
Datasets

The file-path positional value is emitted first, followed by the remaining flags. For name, description, workspace, header (boolean true), file-path, overwrite:

<file-path value> --name <v> --workspace <v> --description <v> --header

Here the flag order after the positional is: --name, --workspace, --description, then boolean --header last.

Compute-envs

Flags are emitted in alphabetical order of flag name, and the file-path positional value is inserted at the position where it sorts among the flag names (i.e. sorted as if by the flag/positional key name). For name, workspace, credentials, file-path, wait, overwrite:

--credentials <v> <file-path value> --name <v> --wait <v> --workspace <v>

(The file-path value appears between --credentials and --name, consistent with file-path sorting after credentials and before name.)

Pipelines

Flags are emitted in alphabetical order of flag name, and the url positional value is emitted last. The params-file key is removed and not emitted. For name, url, workspace, description, compute-env, work-dir, profile, params-file, config, pre-run, revision, overwrite:

--compute-env <v> --config <v> --description <v> --name <v> --pre-run <v> --profile <v> --revision <v> --work-dir <v> --workspace <v> <url value>

Summary of Positional vs. Flag Placement

  • Datasets: positional (file-path) placed at the beginning.
  • Compute-envs: positional (file-path) placed in alphabetical order among the other keys.
  • Pipelines: positional (url) placed at the end; params-file excluded entirely.

Dependencies

  • YAML parsing (the yaml package) is used to load file contents.
  • File contents are read via the standard open built-in.

All string values must appear in cmd_args as plain strings.
