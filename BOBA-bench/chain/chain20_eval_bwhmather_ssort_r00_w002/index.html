Task: Implement --check mode for the ssort command-line tool

Overview

The ssort command-line tool sorts top-level statements in Python source files so that definitions appear before their uses (private helpers before the public functions that call them). You must implement a --check mode that reports whether files are already correctly sorted, without modifying any files, and produces a specific set of diagnostic and summary messages.

The tool must be invocable as an executable named ssort (available on PATH). It is invoked like:

ssort --check <directory>

where <directory> contains one or more .py files to inspect. All files in the given directory must be processed.

Sorting semantics (for determining "correctly sorted")

A file's top-level statements are considered correctly sorted when every definition appears before the statements that depend on it. Concretely, for the fixtures involved:

  • A file where a private helper function is defined before the public function that calls it is correctly sorted (would be left unchanged).
  • A file where a public function that calls a private helper is defined before that helper is not correctly sorted (would be resorted).

Processing order and output

The tool processes the files in sorted filename order. For each file, it may emit an error line to stderr. After all files are processed, it emits exactly one summary line to stderr.

All output described below goes to stderr. Each message is a single line terminated by a newline (\n).

Per-file error messages

For each file, exactly one of the following applies:

  1. File is correctly sorted — no per-file message is emitted.

  2. File is not correctly sorted — emit:

    ERROR: '<path>' is incorrectly sorted

    where <path> is the file path as it was passed in (the repr() of the path string, i.e. wrapped in single quotes).

  3. File contains a Python syntax error — emit:

    ERROR: syntax error in '<path>': line <line>, column <col>

    where <line> and <col> are the 1-based line and column of the syntax error. (<path> is again the repr() of the path string.)

  4. File contains an unresolved dependency — a top-level statement references a name that is never defined at the top level of the module and is not a recognised builtin. Emit:

    ERROR: unresolved dependency '<name>' in '<path>': line <line>, column <col>

    where <name> is the unresolved name, and <line>/<col> are the 1-based line and column at which the unresolved name is used.

Per-file error lines are emitted in file-processing order.

Summary message

After processing all files, emit exactly one summary line built from the following count-based clauses, in this order, including only the clauses whose count is greater than zero:

  1. Files that would be resorted (not correctly sorted, but syntactically valid and resolvable):
    • N file would be resorted if N == 1
    • N files would be resorted if N > 1
  2. Files that would be left unchanged (correctly sorted):
    • N file would be left unchanged if N == 1
    • N files would be left unchanged if N > 1
  3. Files that would not be sortable (syntax error or unresolved dependency):
    • N file would not be sortable if N == 1
    • N files would not be sortable if N > 1

The included clauses are joined with ", " (comma and single space) and the line is terminated with a newline.

Examples of complete summary lines:

  • All three files correctly sorted: 3 files would be left unchanged
  • One unsorted, two correct: 1 file would be resorted, 2 files would be left unchanged
  • All three unsorted: 3 files would be resorted
  • Two correct, one syntax error: 2 files would be left unchanged, 1 file would not be sortable
  • Three syntax errors: 3 files would not be sortable
  • One unsorted, one correct, one syntax error: 1 file would be resorted, 1 file would be left unchanged, 1 file would not be sortable

Exit status

  • If every file is correctly sorted (would be left unchanged), exit with status code 0.
  • If any file is not correctly sorted, has a syntax error, or has an unresolved dependency, exit with status code 1.

Builtins

Name resolution must treat raw_input as a recognised builtin (in addition to the standard set of Python builtins), so that a reference to it does not produce an unresolved-dependency error.

Line/column reporting details

Positions reported for syntax errors and unresolved dependencies are 1-based for both line and column. For reference, given source such as:

    pass

def public(
    return _private()

the syntax error is reported at line 3, column 5.

And given source such as:

    pass

def public():
    return _other()

the reference to the unresolved name _other is reported at line 6, column 11.

(Both example sources above begin with a leading newline, so the first physical line is blank.)

For each file discovered, exactly one of the following outcomes applies:

  1. Left unchanged — The file was parsed and analyzed successfully, and its sorted form is identical to its current contents. No per-file message is emitted. The file is not modified.

  2. Resorted — The file was parsed and analyzed successfully, and its sorted form differs from its current contents. The file is rewritten with the sorted contents, and a per-file message is emitted (see below).

  3. Not sortable — The file could not be processed because of a syntax error or an unresolved dependency. An error message is emitted (see below), and the file is not modified.

Per-File Messages

Messages must be emitted in the order files are processed, and this order is deterministic (the same fixed order in which the files were provided/discovered).

    ERROR: syntax error in '<path>': line <L>, column <C>

    where <path> is the repr()-formatted file path, and <L>/<C> are the 1-based line and column of the error.

  • Unresolved dependency: emit a line of the form:

    ERROR: unresolved dependency '<name>' in '<path>': line <L>, column <C>

    where <name> is the name of the unresolved dependency, <path> is the repr()-formatted file path, and <L>/<C> are the 1-based line and column where the unresolved reference occurs.

Each emitted line is terminated by a single newline (\n).

After all files have been processed, emit exactly one final summary line (terminated by a newline) that describes the aggregate results across three categories:

Only categories with a nonzero count are included in the summary, and they appear in this fixed order: resorted, then unchanged, then not sortable. The included categories are joined by ", " (comma and space) into a single line.

Each category's phrase uses correct singular/plural grammar based on its count:

  • Resorted:
    • count == 1: 1 file was resorted
    • count > 1: <n> files were resorted
  • Unchanged:
    • count == 1: 1 file was left unchanged
    • count > 1: <n> files were left unchanged
  • Not sortable:
    • count == 1: 1 file was not sortable
    • count > 1: <n> files were not sortable

Examples of complete summary lines:

  • All three files unchanged: 3 files were left unchanged
  • One resorted, two unchanged: 1 file was resorted, 2 files were left unchanged
  • Three resorted: 3 files were resorted
  • Two unchanged, one not sortable: 2 files were left unchanged, 1 file was not sortable
  • Three not sortable: 3 files were not sortable
  • One resorted, one unchanged, one not sortable: 1 file was resorted, 1 file was left unchanged, 1 file was not sortable

Exit Status

  • Exit status 0 if no file was "not sortable" (i.e., every file was either resorted or left unchanged).
  • Exit status 1 if at least one file was "not sortable" (any syntax error or unresolved dependency occurred).

Output Ordering Summary

The complete standard-error output consists of the per-file messages (in file-processing order) followed by the single summary line, each terminated by a newline.

Required Behavior

When analyzing the requirements of a del statement whose target is a tuple/list of one or more elements, the analysis must recurse into each element of that tuple/list and collect the dependencies of each element, in source order.

Objective

Implement a function get_bindings that traverses a Python Abstract Syntax Tree (AST) node and yields the names that the node binds, in the order they appear in the source.

Public API

Provide a function importable as:

get_bindings(node)

The following node types must be handled with the exact binding semantics described below.

global statements

A global statement binds every name it declares, in listed order.

  • global name → ["name"]
  • global a, b → ["a", "b"]
nonlocal statements

A nonlocal statement binds every name it declares, in listed order.

  • nonlocal name → ["name"]
  • nonlocal a, b → ["a", "b"]
pass, break, continue statements

These statements bind no names.

  • pass → []
  • break → []
  • continue → []

A boolean operation itself binds no names, but any operand that is a walrus (assignment) expression contributes its bound target. Names are yielded in left-to-right operand order.

  • a and b → []
  • (left := a) and b → ["left"]
  • a or (right := b) → ["right"]
  • (left := a) and (right := b) → ["left", "right"]
  • (a := 1) and (b := 2) and (c := 3) → ["a", "b", "c"]

A binary operation itself binds no names, but a walrus (assignment) expression appearing as the left or right operand contributes its bound target. Names are yielded left operand first, then right operand.

  • a and b (treated as an expression with no binding) → []
  • (left := a) | b → ["left"]
  • a ^ (right := b) → ["right"]
  • (left := a) + (right := b) → ["left", "right"]

Notes on Walrus Handling

For boolean and binary operations, the function must recurse into operands so that walrus-expression bindings nested within them are discovered and yielded in source order. A walrus expression (target := value) binds target.

Environment

This behavior involving the walrus operator (:=) is only relevant on Python versions that support it (3.8+).
