Task: Add a --check mode to the ssort command-line tool

Overview

ssort is a command-line tool that reorders the top-level statements of Python source files so that definitions come before their uses (private helpers are placed before the public functions that call them). You must implement a --check mode that reports whether files are already correctly sorted, without modifying any files, and that emits a specific set of diagnostic and summary messages.

It must be possible to invoke the tool as an executable named ssort (available on PATH). It is invoked as:

ssort --check <directory>

where <directory> contains one or more .py files to inspect. The tool must process all files in the given directory.

Sorting semantics (for deciding whether a file is "correctly sorted")

A file's top-level statements are regarded as correctly sorted when every definition appears before the statements that depend on it. Specifically, for the fixtures involved:

  • A file in which a private helper function is defined before the public function that calls it is correctly sorted (would be left unchanged).
  • A file in which a public function that calls a private helper is defined before that helper is not correctly sorted (would be resorted).

Processing order and output

Files are processed by the tool in sorted filename order. For each file, an error line may be emitted to stderr. Once all files have been processed, it emits exactly one summary line to stderr.

All of the output described below goes to stderr. Each message consists of a single line terminated by a newline (\n).

Error messages per file

For each file, exactly one of the following cases applies:

  1. File is correctly sorted — no message is emitted for the file.

  2. File is not correctly sorted — emit:

    ERROR: '<path>' is incorrectly sorted

    where <path> is the file path as passed in (the repr() of the path string, i.e. enclosed in single quotes).

  3. File contains a Python syntax error — emit:

    ERROR: syntax error in '<path>': line <line>, column <col>

    where <line> and <col> are the 1-based line and column of the syntax error. (<path> is once again the repr() of the path string.)

  4. File contains an unresolved dependency — a top-level statement references a name that is never defined at the module's top level and is not a recognised builtin. Emit:

    ERROR: unresolved dependency '<name>' in '<path>': line <line>, column <col>

    where <name> is the unresolved name, while <line>/<col> are the 1-based line and column at which the unresolved name is used.

Per-file error lines are emitted in the order in which the files are processed.

Summary line

Once all files have been processed, emit exactly one summary line built from the following count-based clauses, in this order, including only clauses whose count is greater than zero:

  1. Files that would be resorted (i.e. not correctly sorted, but syntactically valid and resolvable):
    • N file would be resorted when N == 1
    • N files would be resorted when N > 1
  2. Files that would be left unchanged (i.e. correctly sorted):
    • N file would be left unchanged when N == 1
    • N files would be left unchanged when N > 1
  3. Files that would not be sortable (a syntax error or an unresolved dependency):
    • N file would not be sortable when N == 1
    • N files would not be sortable when N > 1

The clauses that are included are joined with ", " (comma and single space), and the line ends with a newline.

Examples of full summary lines:

  • Three files, all correctly sorted: 3 files would be left unchanged
  • One file unsorted, two correct: 1 file would be resorted, 2 files would be left unchanged
  • All three files unsorted: 3 files would be resorted
  • Two correct, one with a syntax error: 2 files would be left unchanged, 1 file would not be sortable
  • Three files with syntax errors: 3 files would not be sortable
  • One unsorted, one correct, one with a syntax error: 1 file would be resorted, 1 file would be left unchanged, 1 file would not be sortable

Exit status

  • When every file is correctly sorted (would be left unchanged), exit with status code 0.
  • When any file is not correctly sorted, has a syntax error, or has an unresolved dependency, exit with status code 1.

Builtin names

Name resolution must treat raw_input as a recognised builtin (in addition to the standard set of Python builtins), so that a reference to it does not result in an unresolved-dependency error.

Details of line/column reporting

The positions reported for syntax errors and unresolved dependencies are 1-based for both line and column. For reference, given the following source:

def _private(
    pass

def public(
    return _private()

the position reported for the syntax error is line 3, column 5.

And given the following source:

def _private():
    pass

def public():
    return _other()

the position reported for the reference to the unresolved name _other is line 6, column 11.

(Both of the example sources above start with a leading newline, so the first physical line is blank.)

Constraints

  • In --check mode, files must not be modified.
  • For the behavior described here, nothing is written to stdout; all diagnostics and the summary go to stderr.

Task Specification: Implementing the Fix (Mutating) Mode of the ssort Command-Line Tool

What This Task Covers

This task is about implementing how the ssort command-line executable behaves when it is invoked to sort Python source files in place (fix mode). The tool accepts a path argument (typically a directory) that identifies a set of Python files. For every one of those files, it attempts to arrange the top-level statements according to dependency order; files whose contents change are rewritten, and a summary of the results is reported. Every piece of human-readable output described in this document must be written to standard error.

Calling the Tool

The tool gets invoked like this:

ssort <path>

<path> here is a directory that holds the Python files to be processed. Under that path, the tool finds the .py files and processes each of them.

Outcomes for Each File

Exactly one of the three outcomes below holds for every file that is discovered:

  1. Left unchanged — Parsing and analysis of the file succeed, and the sorted form that results is identical to the contents the file currently has. The tool emits no per-file message, and no modification is made to the file.

  2. Resorted — Parsing and analysis succeed here as well, but the sorted form differs from the file's current contents. The tool rewrites the file with the sorted contents, and a per-file message is emitted (see below).

  3. Not sortable — The file cannot be processed, the cause being a syntax error or an unresolved dependency. An error message is emitted (see below), and the file is left unmodified.

Messages for Individual Files

Emission must follow the order in which files are processed; that order is deterministic — it is the same fixed order in which the files were provided/discovered.

  • Resorted file: emit a line like this:

    Sorting '<path>'

    Here <path> stands for the file path, rendered as Python's repr() of the path string — in other words, it appears wrapped in the quotes that repr produces.

  • Syntax error: emit a line matching this pattern:

    ERROR: syntax error in '<path>': line <L>, column <C>

    In it, <path> is once more the repr()-formatted file path, while <L>/<C> identify the 1-based line and column where the error is located.

  • Unresolved dependency: emit a line with this structure:

    ERROR: unresolved dependency '<name>' in '<path>': line <L>, column <C>

    <name> designates the unresolved dependency's name, <path> is again the repr()-formatted file path, and <L>/<C> give the 1-based line and column at which the unresolved reference occurs.

  • Unchanged file: no message gets emitted for it.

Every line that gets emitted ends with a single newline (\n).

Overall Summary

Once the last file has been processed, emit exactly one final summary line — itself terminated by a newline — that captures the aggregate outcome over three categories:

  • resorted — how many files were rewritten,
  • unchanged — how many files were left unchanged,
  • not sortable — how many files failed because of syntax or resolution errors.

Only categories whose count is nonzero appear in the summary; the sequence among them is fixed: resorted, then unchanged, then not sortable. The categories that qualify are joined by ", " (comma and space) to produce one line.

Each category's phrase follows correct singular/plural grammar, with the choice made according to its count:

  • Resorted:
    • count == 1: 1 file was resorted
    • count > 1: <n> files were resorted
  • Unchanged:
    • count == 1: 1 file was left unchanged
    • count > 1: <n> files were left unchanged
  • Not sortable:
    • count == 1: 1 file was not sortable
    • count > 1: <n> files were not sortable

Complete summary lines, by way of example:

  • All three files come out unchanged: 3 files were left unchanged
  • One file resorted and two unchanged: 1 file was resorted, 2 files were left unchanged
  • All three files resorted: 3 files were resorted
  • Two files unchanged, one not sortable: 2 files were left unchanged, 1 file was not sortable
  • All three files not sortable: 3 files were not sortable
  • One file resorted, one unchanged, one not sortable: 1 file was resorted, 1 file was left unchanged, 1 file was not sortable

Exit Status

  • The exit status is 0 when no file was "not sortable" — that is, every file was either resorted or left unchanged.
  • The exit status is 1 when at least one file was "not sortable" — that is, any syntax error or unresolved dependency occurred.

How the Output Is Ordered

Taken as a whole, the standard-error output is made up of the per-file messages (in the order the files were processed) plus the single summary line that comes after them; a newline terminates each of these lines.

Aim

Add support for correctly computing the variable requirements (dependencies) of Python del statements that target a list or tuple of elements, including targets that are nested subscripts or attribute accesses.

Background

To work out which variable names a given statement depends on ("requirements"), the codebase analyzes Python AST nodes. In delete context, the dependency-analysis logic already handles some target forms, but it does not correctly handle the case where a del statement targets a parenthesized tuple (or list) of multiple targets.

Required Behavior

When the requirements of a del statement are analyzed and that statement's target is a tuple/list of one or more elements, the analysis must recurse into each element of that tuple/list and collect the dependencies of each element, in source order.

Within such a tuple/list, the individual element target forms that must be handled include:

  • Plain names: deleting a bare name contributes that name as a dependency.
  • Subscripts (e.g. a[b:c]): the subscripted object contributes its name, and any names that appear in the subscript/slice expression also contribute as dependencies, in order.
  • Attribute access (e.g. d.f): the accessed object contributes its name; the attribute name itself does not contribute.

The dependencies contributed by all elements must be concatenated in the left-to-right order in which the elements appear.

Examples of the required results

Each example below shows a parsed statement together with the ordered list of dependency names that results from it:

  • del (a, b) → ["a", "b"]
  • del (a[b:c], d.f) → ["a", "b", "c", "d"]

These statements must produce results of the same kind as those already produced for the equivalent non-tuple forms:

  • del a[b:c] → ["a", "b", "c"]
  • del obj.attr → ["obj"]

Scope Notes

The change is specifically meant to ensure that delete context handles a tuple/list of targets by recursing into each target it contains, using the same requirement-gathering logic that applies to load and delete contexts. In delete context, subscript targets must yield dependencies identical to those of subscript expressions in load context (the subscripted object plus all names in the subscript expression, in order). In delete context, attribute targets must yield only the name of the accessed object.

Public API

These behaviors are exercised through a dependency-analysis entry point that takes a parsed AST node (obtained by parsing a single statement) and returns an ordered list of the dependency variable names as strings. After your change, this existing entry point must return the results described above for del statements that target tuples/lists.

Ensure that, for both single-target and tuple/list-target del statements, the function that produces an ordered list of dependency names from an AST node yields the exact ordered results specified above.

Specification of the Task

Overview

You are working on ssort, a tool that topologically sorts (reorders) the statements within Python source code so that definitions appear before their usages. The task covers two behaviors: correct ordering behavior around class-body __slots__ and dunder assignments, together with deterministic reporting when multiple unresolved-dependency errors occur.

Public API

ssort(source: str) -> str

It can be imported as from ssort import ssort. The function accepts Python source text and returns the reordered source text.

"check" behavior on the command line

The package exposes an entry point that can be run from the command line (invoked as a module/console script) and that supports a --check mode. When it runs in check mode against a directory of Python files, it:

  • Emits diagnostic messages (into output that the caller captures) describing the per-file results.
  • Returns/exits with a status code: 0 when all files are already correctly sorted and there are no errors, 1 when any file has errors or would be modified.

Below, under "Reporting unresolved dependencies", the relevant behavior to implement/preserve is described.

Required Behavior

1. Ordering of statements in the class body with __slots__ and dunder assignments

When the statements inside a class body are sorted, the module-level ordering rules apply as usual, with the following behavior specific to assignments:

  • An assignment of the form __slots__ = (...) must be placed at the top of the class body, before the other attribute assignments and annotated attributes, while otherwise preserving the relative order of the remaining statements.
  • Assignments with dunder names (identifiers following the __name__ double-underscore pattern) that are not recognized standard/known dunder methods must, for the purpose of ordering, be treated as ordinary class attributes — i.e., they are treated the same as any normal attribute assignment. They should not receive any special hoisting or reordering treatment beyond that of a normal attribute.

Concrete examples:

For the input:

class Struct:
    int_attr: int
    __slots__ = ("int_attr", "str_attr")
    str_attr: str

the resulting output is:

class Struct:
    __slots__ = ("int_attr", "str_attr")
    int_attr: int
    str_attr: str

For the input:

class Table:
    column = None
    __tablename__ = "table"
    __slots__ = ("column", "other_column")
    other_column = None

the resulting output is:

class Table:
    __slots__ = ("column", "other_column")
    __tablename__ = "table"
    column = None
    other_column = None

Here __slots__ moves to the top, while __tablename__ (an unknown dunder) keeps its place among the normal attributes as if it were a normal attribute, so the relative order with the other attributes is preserved.

2. Reporting unresolved dependencies (deterministic order)

If a file references names that cannot be resolved (unresolved dependencies), the check mode must emit one ERROR message per unresolved reference. If a single statement references multiple unresolved names, all such names must be reported.

The requirements are:

  • Each unresolved reference produces a message with exactly this form:

    ERROR: unresolved dependency '<name>' in <path>: line <L>, column <C>

    where <name> is the unresolved identifier, <path> is the repr of the file path (i.e. quoted the way Python would repr a path), and <L>/<C> are the 1-based line and 0-based column of the reference within the source file. Each message is terminated by a trailing newline.

  • When multiple unresolved dependencies occur, the messages must be emitted in a deterministic order: they are sorted by their source position (line first, then column). For example, two unresolved names that appear on the same line are reported left-to-right by column.

  • After the per-file diagnostics, a summary line is emitted that describes the outcome across all processed files, of the form:

    <N> files would be left unchanged, <M> file would not be sortable

    (with the counts using the appropriate singular/plural forms), followed by a trailing newline.

  • In this situation, the overall status code is 1.

Concrete example: take a file whose sole public function has the body return _other() + _same(), where _other and _same are both undefined, and where that expression is on line 6, with _other at column 11 and _same at column 22. The messages emitted are:

ERROR: unresolved dependency '_other' in '<path>': line 6, column 11
ERROR: unresolved dependency '_same' in '<path>': line 6, column 22

in that order (column 11 comes before column 22).

Constraints

  • Statements that the rules above do not affect must have their relative order preserved.
  • The scope covers only the behaviors described here.

Public API

It must be possible to import the function as:

Signature:

def get_bindings(node) -> Iterable[str]:
    ...
  • node is a Python AST node (the kind produced by ast.parse and by any surrounding helper that returns a parsed node standing for the given source snippet).
  • The return value must be iterable and must yield the binding names as strings. Since callers may wrap the result in list(...), the ordering of the yielded names is significant.

Regular for loops

For a for loop written as:

    <body>
else:
    <orelse>

  1. The name(s) bound by the loop target (that is, the variable(s) between for and in).

the bindings are yielded in the following order:

Note that the augmented assignment (a += i) inside the body binds a, and b is bound in the else block.

async for loops

An async for loop must be handled in exactly the same way as a regular for loop. For the source

async for i in range(10):
    a += i
else:
    b = 4

the bindings are yielded, in order, as:

["i", "a", "b"]

When the loop's iterable expression includes a walrus / named-expression assignment (name := value), the name that the walrus binds must be yielded. That walrus-bound name comes before the loop target name.

For a regular for loop:

    pass

the bindings are yielded in this order:

["r", "i"]

For an async for loop:

async for i in (r := range(10)):
    pass

the bindings are yielded in the following order:

["r", "i"]

Summary of the Yield Order

For both for and async for nodes, names are yielded in this order:

  1. Names bound by any walrus expression that appears in the iterable.
  2. The name(s) of the loop target.
  3. Names bound in the body of the loop.
  4. Names bound in the loop's else block.

Notes

  • A loop body consisting of pass contributes no bindings.
  • Augmented assignments (+=) inside the body bind the name being assigned.
  • A loop's else clause is optional; when it is present, its bindings are included after those of the body.

The global statement

A global statement binds every name it declares, in the order they are listed.

  • global name → ["name"]

The nonlocal statement

A nonlocal statement binds every name it declares, in the order they are given.

  • nonlocal name → ["name"]
  • nonlocal a, b → ["a", "b"]
The pass, break, and continue statements

None of these statements bind any names.

  • pass → []
  • break → []
  • continue → []

A boolean operation on its own binds no names, but any operand that is a walrus (assignment) expression contributes the target it binds. Names are yielded in the left-to-right order of the operands.

  • a and b (regarded as an expression that binds nothing) → []

  • a ^ (right := b) → ["right"]
  • (left := a) + (right := b) → ["left", "right"]

Walrus Handling Notes

For boolean and binary operations, the function must recurse into the operands so that bindings from walrus expressions nested inside them are discovered and yielded in source order. The walrus expression (target := value) binds target.

Environment

The behavior involving the walrus operator (:=) is only applicable on Python versions that support it (3.8+).
