01 Add a keep_physical_range keyword parameter to EdfSignal.update_data 454 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Add a keep_physical_range keyword parameter to EdfSignal.update_data

Background

EdfSignal is a class (importable as EdfSignal from the EDF module used in the codebase) that models a signal holding both a physical and a digital representation of its data. Each signal comes with:

  • an attribute physical_range: a tuple (min, max) giving the bounds of the physical values.
  • an attribute digital_range: a tuple (min, max) giving the bounds of the digital values.
  • a property data, which returns the signal's physical values as a NumPy array.
  • an attribute _digital: the internal digital representation of the signal (a NumPy array).

Physical values map linearly to digital values according to physical_range and digital_range.

Required change

A new keyword parameter keep_physical_range (default False) is to be added to the EdfSignal.update_data method. The signature must accept the new signal data as the first positional argument together with this new boolean keyword argument.

Behavior for keep_physical_range=True

When a call to update_data passes keep_physical_range=True:

  1. After the update, the signal's existing physical_range and digital_range must remain unchanged.
  2. The new physical data must be stored, in such a way that the data property returns the new data (accurate to at least 14 decimal places).
  3. The internal _digital array must be recomputed from the new physical data on the basis of the existing (preserved) physical/digital range mapping. As an example: with physical_range=(0, 100) and digital_range=(0, 1000), the physical values are scaled by a factor of 10 to produce the digital values.
Error condition for keep_physical_range=True

If any value in the new data lies outside the signal's existing physical_range (below the minimum or above the maximum), a ValueError must be raised. The message of that error must contain text matching the pattern Signal range .* out of physical range.

This check comes into play when the new data's minimum is below the physical range minimum, when its maximum is above the physical range maximum, or both.

Existing behavior

When keep_physical_range is False or omitted, the default behavior of update_data must not change — including any existing validation, such as rejecting new data whose length does not match the current signal length.

Example

For a signal constructed with physical values [90.1, 98.3, 100.0], physical_range=(0, 100), and digital_range=(0, 1000):

  • After a call to update_data([92.3, 97.5, 99.9], keep_physical_range=True), physical_range == (0, 100) and digital_range == (0, 1000) still hold, data becomes [92.3, 97.5, 99.9], and _digital becomes [923.0, 975.0, 999.0].

For a signal constructed with physical values [-5, 5] (default ranges derived from that data):

  • Each of the calls update_data([-7, 3], keep_physical_range=True), update_data([-3, 7], keep_physical_range=True), and update_data([-7, 7], keep_physical_range=True) must raise a ValueError, because the new data exceeds the preserved physical range.
02 In an EDF recording, a single signal is represented by the EdfSignal class (importable as EdfSignal from the project's edf module, e.g. 826 words · source specification, reworded by GLM-5.3-Flash

Task: Support optional resampling in EdfSignal.update_data

Context

In an EDF recording, a single signal is represented by the EdfSignal class (importable as EdfSignal from the project's edf module, e.g. from edfio import EdfSignal — in line with the existing package layout). It already comes with an update_data(...) method used to replace the signal's data samples, along with these relevant attributes/behavior already in place:

  • EdfSignal(data, sampling_frequency, *, digital_range=..., physical_range=...) — constructor that takes a 1-D numeric array, a sampling frequency, and optional keyword-only digital_range / physical_range tuples.
  • .sampling_frequency — the sampling frequency of the signal (a float).
  • .data — read-only property that returns the signal's current samples as a NumPy array.
  • .update_data(data, *, keep_physical_range=False) — puts new samples in place of the stored ones.

update_data must be extended to support optionally changing the sampling frequency at the same time as the data replacement.

Required modification

Give EdfSignal.update_data a new optional keyword-only parameter sampling_frequency:

def update_data(
    self,
    data,                         # 1-D array of new samples
    *,
    keep_physical_range: bool = False,
    sampling_frequency: float | None = None,
) -> None:
Behavior when sampling_frequency is None (the default)

The method must behave exactly as it did previously: the new data must have a sample count that is the same as (i.e., consistent with) the existing signal duration at the current sampling frequency, and the stored samples are replaced. (There is no change to the existing behavior.)

Behavior when a sampling_frequency value is provided

Passing a sampling_frequency value means the caller is resampling the signal: the new data array is then allowed to have a sample count different from the current data, provided that the new sample count is consistent with leaving the signal duration unchanged at the new sampling frequency.

A signal's duration is defined as current_number_of_samples / current_sampling_frequency. The number of samples expected for the new data is duration * sampling_frequency.

The rules, applied in order:

  1. Sampling frequency that is not positive. When the provided sampling_frequency is less than or equal to 0, raise ValueError with a message that contains the text Sampling frequency must be positive.

  2. Expected sample count that is not an integer. Compute the expected number of new samples via duration * sampling_frequency. If this expected count is not (within a small tolerance) a whole number, raise ValueError with a message that contains the text non-integer number of samples.

  3. Mismatched lengths. If the expected (integer) sample count does not match the length of the provided data array, raise ValueError with a message that contains the text Signal lengths must match:.

  4. Success. Otherwise, the stored samples are replaced with the provided data and .sampling_frequency is set to the provided value. After a call that succeeds, .sampling_frequency equals the provided value and .data returns the new samples.

Requirements for tolerance

The integer-check from rule 2 and the length comparison logic must both tolerate tiny floating-point discrepancies so that legitimate resampling operations succeed. In particular:

  • For an original signal of 1_000_000 samples at 100 Hz (duration 10000.0 s) and a new sampling frequency of 100.0001 Hz, the expected sample count 10000.0 * 100.0001 = 1000001.0 must be treated as the integer 1000001; a data array of length 1000001 must be accepted, with the result that .sampling_frequency == 100.0001 and len(.data) == 1000001.

  • Non-integer sampling frequencies must also work for the original signal: e.g. an original signal with 11 samples at 5.5 Hz (duration 2.0 s), resampled to 5 Hz, expects 10 samples; a data array of length 10 must be accepted, with the result that .sampling_frequency == 5.

Examples of the outcomes to expect:

  • Original signal with 10 samples at 10 Hz (duration 1.0 s), new sampling_frequency=5, data length 5 → succeeds; .sampling_frequency == 5, data replaced.
  • Original signal with 10 samples at 10 Hz, new sampling_frequency=5, data length 4 (i.e. duration 0.8 s) → ValueError containing Signal lengths must match:.
  • Original signal with 10 samples at 10 Hz, new sampling_frequency of -10 or 0 → ValueError containing Sampling frequency must be positive.
  • Original signal with 10 samples at 10 Hz, new sampling_frequency=9.8 (expected count 9.8, not integral) → ValueError containing non-integer number of samples.

The keep_physical_range parameter keeps working as before, and it may be combined with sampling_frequency.

Further requirement

The library's internal float-to-fixed-width-string rounding (i.e., the helper that renders numeric header fields into 8-character strings) must handle integer-valued inputs correctly on all platforms (including Windows). It must not change the observable string output for the values already handled; the only thing it needs to ensure is that integer values are rounded/formatted consistently across platforms. (This is only relevant insofar as existing behavior must not break.)

Constraints

  • The new sampling_frequency parameter must be keyword-only.
  • Do not alter the default behavior of update_data when sampling_frequency is not supplied.
  • All errors raised as described above must be ValueError and contain the exact substrings specified.
03 Enable Edf to have its data record duration updated 1423 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Enable Edf to have its data record duration updated

Background

The work takes place in a library for EDF (European Data Format). Already present is the Edf class, which handles EDF/EDF+ files and contains signals (EdfSignal objects) together with annotations (EdfAnnotation objects). Two changes are called for: the internal representation of the data record duration is modified, and a public method for changing it is added.

Part 1: Rework of the attribute holding the data record duration

At the moment, an attribute called _data_record_duration is where the raw header field for the data record duration is stored. This internal raw-header attribute is to be renamed to __data_record_duration (a name-mangled private attribute). It must continue to hold the raw header bytes representation (an 8-byte, left-justified ASCII field, e.g. b"2.5".ljust(8)).

A public read-only property is already exposed by the Edf class (or must continue to be exposed):

edf.data_record_duration  # -> float

The property returns the data record duration in seconds as a float (e.g. 2.5, 0.1, or 0.0).

Note: data_record_duration must NOT be part of any generic set of raw header fields that are writable directly; the only way to modify it is through the method defined in Part 2.

Part 2: Construction-time validation of data_record_duration for annotations-only EDFs

If an Edf is constructed with no ordinary signals (only annotations), its data record duration must be zero. When a caller constructs such an annotations-only Edf with a nonzero data_record_duration, a ValueError must be raised whose message contains the text:

Data record duration must be zero

An example that must raise:

Edf([], annotations=(EdfAnnotation(0, 10, "ann 1"),), data_record_duration=20)

Part 3: Addition of the update_data_record_duration method

The Edf class gains a public method:

def update_data_record_duration(
    self,
    data_record_duration: float,
    method: Literal["strict", "pad", "truncate"] = "strict",
) -> None:

The method alters the EDF's data record duration in place, re-partitioning the underlying signal data into data records of the new duration. After a successful call:

  • edf.data_record_duration returns the new value.
  • edf.num_data_records matches the new record count.
  • edf.duration (total recording duration in seconds = num_data_records * data_record_duration) matches the new total.
  • The signal data reachable through edf.signals[i].data is updated as described below.
  • Any annotations stay semantically preserved and continue to round-trip correctly through writing and reading (see Part 4).
Behavior for ordinary signals

The new data_record_duration decides how many samples of each signal go into one data record: samples_per_record = sampling_frequency * data_record_duration. For every signal, this must be a whole number.

The total number of data records is num_data_records = duration / data_record_duration, with duration being the current total signal duration in seconds.

method="strict" (default):

  • Each signal's total duration must be exactly divisible by the new data_record_duration (that is, the total sample count of every signal is an integer multiple of its per-record sample count). If it is not, raise a ValueError with a message of the form:

    Signal duration of {duration}s is not exactly divisible by data_record_duration of {data_record_duration}s

    where {duration} is the current total duration (e.g. 10.0) and {data_record_duration} is the requested value (e.g. 0.3). Example: requesting 0.3 on a 10.0s recording produces:

    Signal duration of 10.0s is not exactly divisible by data_record_duration of 0.3s

  • If the duration is divisible, the signal data stays the same; the record partitioning is the only thing that changes.

    Example: a signal with 100 samples at 10 Hz (10.0s total). Updating to 0.1 yields data_record_duration == 0.1 and num_data_records == 100.

method="pad":

  • The data record count is rounded up so that all signal samples fit, and each signal is padded at the end to fill the last (partial) record.

  • Each signal's padding value is the signal's physical minimum (i.e. the lower bound of its physical range). For a signal whose physical range lower bound is 0, padding is zeros; for a lower bound of 5, padding uses 5.0; for -105, padding uses -105.0, etc.

  • After the padding, edf.signals[i].data equals the original data concatenated with the pad values.

    Example: 100 samples at 10 Hz, updating to 0.3 with method="pad": samples_per_record = 3, records needed = ceil(100/3) = 34, num_data_records == 34, duration == 10.2, and the signal data becomes the original 100 samples followed by 2 padding samples (102 total).

method="truncate":

  • The data record count is rounded down, and each signal is truncated to a whole number of records; trailing samples that do not fill a complete record are discarded.

  • After the truncation, edf.signals[i].data equals the original data truncated to num_data_records * samples_per_record samples.

    Example: 100 samples at 10 Hz, updating to 0.3 with method="truncate": samples_per_record = 3, records = floor(100/3) = 33, num_data_records == 33, duration == 9.9, and the signal data becomes the first 99 samples.

Sampling-frequency compatibility check (all methods)

With the chosen data_record_duration, samples_per_record = sampling_frequency * data_record_duration must be a whole (integer) number of samples for every signal. If the requested duration is incompatible with any signal's sampling frequency, raise a ValueError with a message of the form:

Cannot set data record duration to {data_record_duration}: Incompatible sampling frequency {frequency} Hz

Example: with two 10 Hz signals, requesting 0.05 (which would require 0.5 samples per record) produces a message beginning:

Cannot set data record duration to 0.05: Incompatible sampling frequency 10.0 Hz
Positive-value check for signal-bearing EDFs

When an Edf contains ordinary signals, the requested data_record_duration must be strictly positive. If it is 0 or negative, raise a ValueError with a message containing:

Data record duration must be positive
Behavior for annotations-only EDFs

When the Edf has no ordinary signals (annotations only):

  • 0.0 is the only valid data_record_duration. A call with 0.0 succeeds and results in edf.data_record_duration == 0.0 and edf.num_data_records == 1.
  • A call with any nonzero value must raise a ValueError with a message containing:
    Data record duration must be zero

Part 4: Annotation preservation and round-tripping

update_data_record_duration must keep annotations intact such that, once the update is done, writing the Edf to a file and reading it back reproduces:

  • The correct data_record_duration and num_data_records.
  • The original signal data (for strict).
  • The original annotations, compared as a tuple of EdfAnnotation objects. Each annotation may have an onset (float), a duration (float or None), and text (str).

Requirements verified through a round-trip:

  • Single signal + annotations: An Edf holding one 10 Hz / 30-sample signal and three annotations at onsets 0, 10, 20 (duration None), updated to 0.3 (strict), yields data_record_duration == 0.3, num_data_records == 10, unchanged signal data, and the same three annotations after write/read.

  • Multiple annotation signals: An Edf may already hold several internal annotations signals (one possibly carrying record-start timestamps, the others not). Once the data record duration is updated, all annotations from all annotation signals must be preserved and reproduced (concatenated in order) after write/read.

  • Pad/truncate with annotations: For a 40-sample, 10 Hz signal carrying annotations whose durations are non-None, updating to 0.3:

    • using method="pad": num_data_records == 14, duration == 14 * 0.3, annotations preserved.
    • using method="truncate": num_data_records == 13, duration == 13 * 0.3, annotations preserved.

  • Sub-second start-time offset: For an Edf whose starttime has a sub-second (microsecond) component, updating the data record duration must preserve that microsecond offset. Example: a 100-sample, 10 Hz signal (10.0s), starttime 00:00:00.153781, one annotation (5, 5, "ann 1"), updated to 2.5, yields data_record_duration == 2.5, num_data_records == 4, duration == 10, the annotation preserved, and edf.starttime.microsecond == 153781 after write/read.

Public API summary

The items below must be importable and usable (existing names retained unless noted):

  • Edf — class.
    • The constructor accepts at least: a list of EdfSignal as first positional argument, the keyword annotations (an iterable of EdfAnnotation), the keyword data_record_duration (float), and the keyword starttime (datetime.time).
    • Property data_record_duration -> float (read-only).
    • Property num_data_records -> int.
    • Property duration -> float.
    • Property signals (indexable; each element has a .data numpy array).
    • Property starttime (a datetime.time).
    • Method update_data_record_duration(data_record_duration: float, method: Literal["strict", "pad", "truncate"] = "strict") -> None.
    • Method write(path).
  • EdfSignal — class; its constructor accepts a data array, a sampling frequency, and the keyword arguments physical_range and digital_range (each a 2-tuple of floats).
  • EdfAnnotation — class with fields onset, duration, text.
  • A module-level function read_edf(path) -> Edf.

The internal raw-header attribute for the data record duration must be named __data_record_duration (name-mangled) and must hold the 8-byte left-justified ASCII header value.

04 The setting is a library for the EDF (European Data Format) that represents signals, saves them into files, and loads them back. 571 words · source specification, reworded by GLM-5.3-Flash

Task Description

Overview

The setting is a library for the EDF (European Data Format) that represents signals, saves them into files, and loads them back. There is a floating-point precision bug in how the signal-related durations get computed: it arises when sampling frequencies that are not integers combine with the data record duration to yield values that are mathematically exact integers yet come out imprecise from the floating-point computation. You must fix this so that these quantities round to the integer values intended for them.

Public API

Everything listed below must be importable and callable in exactly the way described (existing API — the signatures and behaviors must be preserved):

  • The Edf class can be constructed as Edf(signals=..., data_record_duration=...), with:

    • signals being a list whose members are EdfSignal instances.
    • data_record_duration being a number, standing for the seconds per data record.
    • A .write(path) method on each instance, which serializes the EDF to the file path supplied.
    • An integer property .num_data_records on each instance.
    • A .signals property on each instance, which returns the list of signals.

  • The EdfSignal class can be constructed as EdfSignal(data, sampling_frequency), with:

    • data being a 1-D NumPy array that contains the samples.
    • sampling_frequency being a number of samples per second, which may take a non-integer value such as 22 / 9.
    • An integer property .samples_per_data_record on each instance.

  • There is also a read_edf(path) function, which reads an EDF file located at the path supplied to it and returns an Edf instance.

Required Behavior

For each signal, how many samples one data record contains follows from the product of that signal's sampling frequency with the data record duration. In valid cases this product is an integer in exact mathematics; when the multiplication is performed naively in floating point, however, the result can sit a fraction away from the true integer (e.g., 2.4444... × 9 giving something along the lines of 21.999999996 or 22.000000004). The correct behavior consists of rounding these products to the nearest integer, so that the intended count of whole samples per record is what comes out.

Likewise, the total count of data records is derived from the overall signal duration and the data record duration; here the derivation must also round correctly, so that floating-point error does not corrupt a count that is an exact integer mathematically.

Example case that must work

Take:

  • Signal A has 220 samples and a sampling frequency of 22 / 9 samples per second.
  • Signal B has 90 samples and a sampling frequency of 1 sample per second.
  • The data record duration is 9 seconds.

Once this Edf has been written to a file and read back:

  • There must be 10 data records.
  • Signal A must end up with 22 samples per data record.
  • Signal B must end up with 9 samples per data record.

These integer values must come out even though the intermediate floating-point products (e.g., (22/9) * 9) are not exactly 22.0.

Constraints

  • All behavior that the classes and functions currently exhibit is to be preserved. The rounding of the derived integer quantities (samples per data record and number of data records) is the only thing being corrected.
  • Reading back the file once it has been written must reconstruct the signals with the correct integer per-record sample counts and the correct data record count.
05 Adjust the EDF+ header parsing so that dates whose month abbreviation is written in any letter case are parsed correctly. 297 words · source specification, reworded by GLM-5.3-Flash

Objective

Adjust the EDF+ header parsing so that dates whose month abbreviation is written in any letter case are parsed correctly.

Background

Two classes in the codebase are responsible for parsing fields out of EDF+ header strings. Both classes expose a birthdate/startdate value that is derived from a date encoded in the format DD-MMM-YYYY, where MMM is a three-letter English month abbreviation (e.g. Nov for November).

The relevant public API (already present, and importable from the same module the tests use):

  • Patient providing:
    • classmethod Patient._from_str(value: str) -> Patient
    • property Patient.birthdate -> datetime.date
  • Recording providing:
    • classmethod Recording._from_str(value: str) -> Recording
    • property Recording.startdate -> datetime.date

Input formats

  • Patient._from_str is given a space-separated string in which the third field is the birthdate, e.g. "X X 01-Nov-2023 X".
  • Recording._from_str is given a space-separated string that begins with the literal Startdate, followed by the start date field, e.g. "Startdate 01-Nov-2023 X X X".

In both cases, the date field takes the form DD-MMM-YYYY.

Required behavior

Whenever the birthdate property of a Patient, or the startdate property of a Recording, is accessed, the DD-MMM-YYYY date field must be parsed into a datetime.date. The month abbreviation must be recognized no matter the case of its letters. The following month spellings must all parse to the same month:

  • Nov
  • nov
  • noV

(i.e. the three-letter month abbreviation is accepted with any mixture of upper- and lower-case letters.)

As an example, each of "01-Nov-2023", "01-nov-2023", and "01-noV-2023" must yield datetime.date(2023, 11, 1).

Scope

The only aspect being changed is the case-insensitive handling of the month abbreviation. All other existing parsing behavior (this includes access to other, non-date fields as well as the existing error handling for invalid dates) must remain unchanged.

07 Distinguishing Ordinary Signals from Annotation Signals in Edf.num_signals 488 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Distinguishing Ordinary Signals from Annotation Signals in Edf.num_signals

Background

The Edf class (in the codebase's EDF-handling module) models an EDF/EDF+ file. In addition to ordinary data signals, EDF+ files may contain a special "annotations" signal. At the moment, the signal-count behavior, as exposed to users, does not distinguish annotation signals from ordinary signals.

Required Modifications

1. Give the raw header field attribute a new name

The internal attribute that stores the raw header-record encoding of the signal count must be given a new name, so that it is name-mangled as a private (double-underscore) attribute of the Edf class.

  • The attribute holding the raw (bytes-encoded, fixed-width) signal count must be named __num_signals (that is, it is accessed within the class as self.__num_signals, and from outside via the name-mangled form edf._Edf__num_signals).
  • This raw value continues to store the total number of signals present in the file's header, with the encoding being an ASCII byte string left-justified/padded to a fixed width of 4 bytes. As an example, a total signal count of 1 is stored as b"1".ljust(4).
2. Expose the total raw count through _num_signals

Provide a property (or attribute) named _num_signals that returns, as an integer, the total number of signals recorded in the header — a count that includes any annotation signal.

  • When a file's header records 1 signal in total, _num_signals returns 1.
  • When a file's header records 2 signals in total, _num_signals returns 2.
3. Make num_signals exclude annotation signals

The public property num_signals must return the number of ordinary signals only — in other words, the total number of signals minus the number of annotation signals.

  • A file whose only signal is an annotations signal (total of 1 signal, this being the annotation signal) must report num_signals == 0, while _num_signals == 1.
  • A file that holds one ordinary signal plus one annotations signal (total of 2 signals) must report num_signals == 1, while _num_signals == 2.

Preserved Behavior

All other Edf behavior remains unchanged. In particular:

  • Reading and writing EDF/EDF+ files continues to work as it did before.
  • Other header properties (bytes_in_header_record, reserved, data_record_duration, num_data_records, annotations, etc.) keep their existing values and behavior.
  • For EDF+ continuous files, the reserved field still reports "EDF+C".

Overview of the Public API Surface

For the Edf class:

b"2  8  51"
b" 2 8  51"
b" 2  8 51"
b"2 8 51  "

The two-digit year 51 corresponds to the year 2051.

Validation errors for dates

A ValueError must be raised when the parsed components are out of range:

  • For an invalid day component, ValueError must be raised with a message containing day is out of range for month.
  • For an invalid month component (e.g. 13), ValueError must be raised with a message containing month must be in 1..12.

(These are the standard messages that constructing a datetime.date produces.)

RawHeaderFieldTime.decode(field: bytes) -> datetime.time

The method is passed a bytes value that contains a time consisting of three components in the order hours, minutes, seconds. It must parse the three numeric components with the same set of accepted separator/whitespace styles that was described above for dates.

The following byte values must all decode to datetime.time(2, 8, 51) (hours=2, minutes=8, seconds=51):

b"02.08.51"
b"2.8.51  "
b"2. 8.51 "
b" 2. 8.51"
b"02:08-51"
b"02/08'51"
b"2  8  51"
b" 2 8  51"
b" 2  8 51"
b"2 8 51  "
Error for an invalid time format

If the field cannot be parsed into a valid time (for example b"02_08_51"), a ValueError must be raised with a message that contains the substring Invalid time for format.

Public API That Must Be Importable

From edfio._header_field, the following must be importable:

  • RawHeaderFieldDate — a class; RawHeaderFieldDate(length: int); method decode(field: bytes) -> datetime.date.
  • RawHeaderFieldTime — a class; RawHeaderFieldTime(length: int); method decode(field: bytes) -> datetime.time.

(Besides these, the module already contains decode_float, decode_str, encode_float, etc.; those are unrelated to this task and must remain importable.)

Additional Notes

  • Both decode methods must tolerate leading, trailing, and interspersed whitespace, and in addition to punctuation separators they must treat runs of spaces as valid component separators.
  • Behavior beyond what is described above must not be added.
19 Parsing EDF+ Header Subfields Tolerantly 784 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Parsing EDF+ Header Subfields Tolerantly

Overview

The parsing logic for EDF+ header fields must be modified so that missing or unspecified subfields are handled gracefully. This work involves two classes: Patient and Recording. Each of them exposes a classmethod _from_str(cls, string: str) that parses a raw header string and returns an instance. The aim of the task is for these parsers to tolerate header strings that have fewer subfields than the full EDF+ specification would normally require.

Background: The Subfield Format

Multiple subfields are encoded within EDF+ header fields, separated by single spaces. The literal character "X" represents an unspecified subfield. The purpose of this change is to permit header strings that are truncated (that is, trailing subfields are simply absent) and to treat any absent subfield as though it were the placeholder "X".

Behavior Required for Patient._from_str

The local patient identification string is composed of the following subfields, in this order:

  1. patient code
  2. sex
  3. birthdate
  4. name
  5. one or more optional "additional" subfields

Any subfield absent from the input string (as a result of truncation) must behave exactly as if the placeholder "X" had been supplied in its place.

The Patient object that results must expose:

  • code — a string with the code subfield; "X" when absent.
  • sex — a string with the sex subfield; "X" when absent.
  • name — a string with the name subfield; "X" when absent.
  • additional — a tuple of the remaining subfields; an empty tuple () when none are present.
  • birthdate — a property returning a datetime.date. When the birthdate subfield is the placeholder "X" or is absent, accessing this property must raise AnonymizedDateError with a message containing the text birthdate is not available.
Specific scenarios

  • When the input is the empty string "", parsing must yield:

    • code == "X", sex == "X", name == "X", additional == ()
    • accessing birthdate raises AnonymizedDateError (the message contains birthdate is not available)

  • When the input is "X M 21-AUG-1984", parsing must yield:

    • code == "X", sex == "M", name == "X", additional == ()
    • birthdate == datetime.date(1984, 8, 21)

Behavior Required for Recording._from_str

The local recording identification string always begins with the literal token "Startdate" and is then followed, in order, by these subfields:

  1. startdate
  2. hospital administration code
  3. investigator/technician code
  4. equipment code
  5. one or more optional "additional" subfields

Any subfield missing from the input string (i.e., the string was truncated after "Startdate" or after any later subfield) must behave exactly as if the placeholder "X" had been supplied in its place.

The Recording object that results must expose:

  • hospital_administration_code — a string; "X" when absent.
  • investigator_technician_code — a string; "X" when absent.
  • equipment_code — a string; "X" when absent.
  • additional — a tuple of the remaining subfields; an empty tuple () when none are present.
  • startdate — a property returning a datetime.date. When the startdate subfield is the placeholder "X" or is absent, accessing this property must raise AnonymizedDateError with a message containing the text startdate is not available.
Specific scenarios

  • When the input is "Startdate " (the token followed by a space, with all subsequent subfields missing), parsing must yield:

    • hospital_administration_code == "X", investigator_technician_code == "X", equipment_code == "X", additional == ()
    • accessing startdate raises AnonymizedDateError (the message contains startdate is not available)

  • When the input is "Startdate 13-MAY-2025 X", parsing must yield:

    • hospital_administration_code == "X", investigator_technician_code == "X", equipment_code == "X", additional == ()
    • startdate == datetime.date(2025, 5, 13)

Notes About Startdate Handling

Existing behavior for recording identification strings with an invalid or malformed startdate that still contains the full set of subfields must remain unchanged. The change is strictly concerned with tolerating fewer subfields than expected (trailing subfields absent), and not with relaxing the validation of subfields that are present. In particular, a recording string whose startdate portion is malformed but which contains the placeholder-and-remaining subfields should still be handled by the pre-existing startdate error logic.

Public API

  • The Patient class, providing the classmethod _from_str(cls, string: str) -> Patient along with the attributes/properties code, sex, name, additional, birthdate.
  • The Recording class, providing the classmethod _from_str(cls, string: str) -> Recording along with the attributes/properties hospital_administration_code, investigator_technician_code, equipment_code, additional, startdate.
  • The AnonymizedDateError exception, raised upon access to an anonymized/unspecified date property.

These are importable from the same module locations in which they currently reside.

Format of Dates

Date subfields (birthdate, startdate) follow the DD-MON-YYYY format, where MON is a three-letter uppercase English month abbreviation (e.g. 21-AUG-1984, 13-MAY-2025). A successful parse yields a datetime.date.

20 Change how the read_edf function handles file-like objects that are opened in a mode that does not permit reading. 191 words · source specification, reworded by GLM-5.3-Flash

Task Description

Summary

Change how the read_edf function handles file-like objects that are opened in a mode that does not permit reading.

Required Change in Behavior

When a file-like object that is not readable is passed to read_edf (for instance, a file opened in write-only binary mode "wb"), the function must raise io.UnsupportedOperation with a message that contains the text "read".

Before this change, an input of that kind resulted in a NotImplementedError (with a message along the lines of "Can not read EDF from"). That behavior is no longer the desired one — an attempt to read from a non-readable file-like object must now surface as an io.UnsupportedOperation error that references "read".

API Surface

  • read_edf — the already existing public function for reading EDF data. Its import path and call signature stay unchanged; the error raised for non-readable file-like inputs is the only thing that changes.

Remarks

  • io.UnsupportedOperation (from the standard library io module) must be the error type, and the message that accompanies it must contain the substring read.
  • Nothing else in the behavior of read_edf is affected by this task.
