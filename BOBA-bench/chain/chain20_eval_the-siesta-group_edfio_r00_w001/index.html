01 Add keep_physical_range parameter to EdfSignal.update_data 418 words · source specification

Task Specification: Add keep_physical_range parameter to EdfSignal.update_data

Context

The EdfSignal class (importable as EdfSignal from the EDF module used in the codebase) represents a signal with both physical and digital data representations. Each signal has:

  • A physical_range attribute: a tuple (min, max) describing the physical value bounds.
  • A digital_range attribute: a tuple (min, max) describing the digital value bounds.
  • A data property: returns the signal's physical values as a NumPy array.
  • A _digital attribute: the internal digital representation of the signal (a NumPy array).

The physical values map linearly to digital values based on physical_range and digital_range.

Requirement

Add a new keyword parameter keep_physical_range (default False) to the EdfSignal.update_data method. Its signature must accept new signal data as the first positional argument and this new boolean keyword argument.

Behavior when keep_physical_range=True

When update_data is called with keep_physical_range=True:

  1. The signal's existing physical_range and digital_range must remain unchanged after the update.
  2. The new physical data must be stored, such that the data property returns the new data (accurate to at least 14 decimal places).
  3. The internal _digital array must be recomputed from the new physical data using the existing (preserved) physical/digital range mapping. For example, with physical_range=(0, 100) and digital_range=(0, 1000), physical values are scaled by a factor of 10 to produce the digital values.
Error condition when keep_physical_range=True

If any value in the new data lies outside the signal's existing physical_range (below the minimum or above the maximum), a ValueError must be raised. The error message must contain the text matching the pattern Signal range .* out of physical range.

This check applies when the new data's minimum is below the physical range minimum, when its maximum is above the physical range maximum, or both.

Existing behavior

The default behavior of update_data (when keep_physical_range is False or omitted) must remain unchanged, including any existing validation such as rejecting new data whose length does not match the current signal length.

Example

Given a signal constructed with physical values [90.1, 98.3, 100.0], physical_range=(0, 100), and digital_range=(0, 1000):

  • Calling update_data([92.3, 97.5, 99.9], keep_physical_range=True) leaves physical_range == (0, 100) and digital_range == (0, 1000), sets data to [92.3, 97.5, 99.9], and sets _digital to [923.0, 975.0, 999.0].

Given a signal constructed with physical values [-5, 5] (default ranges derived from that data):

  • Calling update_data([-7, 3], keep_physical_range=True), update_data([-3, 7], keep_physical_range=True), or update_data([-7, 7], keep_physical_range=True) must each raise a ValueError because the new data exceeds the preserved physical range.
02 The EdfSignal class (importable as EdfSignal from the project's edf module, e.g. 770 words · source specification

Task: Add optional resampling support to EdfSignal.update_data

Context

The EdfSignal class (importable as EdfSignal from the project's edf module, e.g. from edfio import EdfSignal — matching the existing package layout) represents a single signal in an EDF recording. It has an existing update_data(...) method used to replace the signal's data samples, plus the following relevant attributes/behavior already in place:

  • EdfSignal(data, sampling_frequency, *, digital_range=..., physical_range=...) — constructor taking a 1-D numeric array, a sampling frequency, and optional keyword-only digital_range / physical_range tuples.
  • .sampling_frequency — the signal's sampling frequency (a float).
  • .data — read-only property returning the current signal samples as a NumPy array.
  • .update_data(data, *, keep_physical_range=False) — replaces the stored samples.

You must extend update_data to optionally change the sampling frequency at the same time the data is replaced.

Required change

Add a new optional keyword-only parameter sampling_frequency to EdfSignal.update_data:

def update_data(
    self,
    data,                         # 1-D array of new samples
    *,
    keep_physical_range: bool = False,
    sampling_frequency: float | None = None,
) -> None:
Behavior when sampling_frequency is None (default)

The method must behave exactly as before: the new data must have the same number of samples as (be consistent with) the existing signal duration at the current sampling frequency, and the stored samples are replaced. (No change to existing behavior.)

Behavior when sampling_frequency is provided

When a sampling_frequency value is passed, the caller is resampling the signal: the new data array is allowed to have a different number of samples than the current data, provided that the new number of samples is consistent with keeping the signal duration unchanged at the new sampling frequency.

The signal's duration is defined as current_number_of_samples / current_sampling_frequency. The expected number of samples for the new data is duration * sampling_frequency.

Rules, in order:

  1. Non-positive sampling frequency. If the provided sampling_frequency is less than or equal to 0, raise ValueError whose message contains the text Sampling frequency must be positive.

  2. Non-integer expected sample count. Compute the expected number of new samples as duration * sampling_frequency. If this expected count is not (within a small tolerance) a whole number, raise ValueError whose message contains the text non-integer number of samples.

  3. Length mismatch. If the expected (integer) number of samples does not match the length of the provided data array, raise ValueError whose message contains the text Signal lengths must match:.

  4. Success. Otherwise, replace the stored samples with the provided data and set .sampling_frequency to the provided value. After a successful call, .sampling_frequency equals the provided value and .data returns the new samples.

Tolerance requirements

Both the integer-check in rule 2 and the length comparison logic must tolerate tiny floating-point discrepancies so that legitimate resampling operations succeed. Specifically:

  • Given an original signal of 1_000_000 samples at 100 Hz (duration 10000.0 s) and a new sampling frequency of 100.0001 Hz, the expected sample count 10000.0 * 100.0001 = 1000001.0 must be treated as the integer 1000001; a data array of length 1000001 must be accepted, resulting in .sampling_frequency == 100.0001 and len(.data) == 1000001.

  • Non-integer sampling frequencies for the original signal must also work: e.g. an original signal of 11 samples at 5.5 Hz (duration 2.0 s) resampled to 5 Hz expects 10 samples; a data array of length 10 must be accepted, resulting in .sampling_frequency == 5.

Examples of expected outcomes:

  • Original 10 samples at 10 Hz (duration 1.0 s), new sampling_frequency=5, data length 5 → succeeds; .sampling_frequency == 5, data replaced.
  • Original 10 samples at 10 Hz, new sampling_frequency=5, data length 4 (i.e. duration 0.8 s) → ValueError containing Signal lengths must match:.
  • Original 10 samples at 10 Hz, new sampling_frequency of -10 or 0 → ValueError containing Sampling frequency must be positive.
  • Original 10 samples at 10 Hz, new sampling_frequency=9.8 (expected count 9.8, not integral) → ValueError containing non-integer number of samples.

The keep_physical_range parameter continues to work as before and may be combined with sampling_frequency.

Additional requirement

The internal float-to-fixed-width-string rounding used by the library (the helper that renders numeric header fields into 8-character strings) must handle integer-valued inputs correctly on all platforms (including Windows). This must not change the observable string output for the values already handled; it only needs to ensure integer values are rounded/formatted consistently across platforms. (This is only relevant insofar as it must not break existing behavior.)

Constraints

  • The new sampling_frequency parameter must be keyword-only.
  • Do not change the default behavior of update_data when sampling_frequency is not supplied.
  • All raised errors described above must be ValueError and contain the exact substrings specified.
03 Add data record duration update capability to Edf 1361 words · source specification

Task Specification: Add data record duration update capability to Edf

Context

You are working on an EDF (European Data Format) library. The Edf class already exists and manages EDF/EDF+ files, containing signals (EdfSignal objects) and annotations (EdfAnnotation objects). This task modifies the internal representation of the data record duration and adds a public method to change it.

Part 1: Refactor the data record duration attribute

Currently, the raw header field for the data record duration is stored in an attribute named _data_record_duration. Rename this internal raw-header attribute to __data_record_duration (a name-mangled private attribute). It must continue to hold the raw header bytes representation (an 8-byte, left-justified ASCII field, e.g. b"2.5".ljust(8)).

The Edf class already exposes (or must continue to expose) a public read-only property:

edf.data_record_duration  # -> float

This returns the data record duration in seconds as a float (e.g. 2.5, 0.1, or 0.0).

Note: data_record_duration must NOT be part of any generic set of directly-writable raw header fields; it is only modifiable through the method defined in Part 2.

Part 2: Validate data_record_duration at construction for annotations-only EDFs

When an Edf is constructed with no ordinary signals (only annotations), the data record duration must be zero. If a caller constructs such an annotations-only Edf with a nonzero data_record_duration, a ValueError must be raised whose message contains the text:

Data record duration must be zero

Example that must raise:

Edf([], annotations=(EdfAnnotation(0, 10, "ann 1"),), data_record_duration=20)

Part 3: Add update_data_record_duration method

Add a public method to the Edf class:

def update_data_record_duration(
    self,
    data_record_duration: float,
    method: Literal["strict", "pad", "truncate"] = "strict",
) -> None:

This method changes the data record duration of the EDF in place, re-partitioning the underlying signal data into data records of the new duration. After a successful call:

  • edf.data_record_duration returns the new value.
  • edf.num_data_records reflects the new record count.
  • edf.duration (total recording duration in seconds = num_data_records * data_record_duration) reflects the new total.
  • The signal data accessible via edf.signals[i].data is updated as described below.
  • Any annotations remain semantically preserved and continue to round-trip correctly through writing and reading (see Part 4).
Behavior for ordinary signals

The new data_record_duration determines how many samples of each signal fall into one data record: samples_per_record = sampling_frequency * data_record_duration. This must be a whole number for every signal.

The total number of data records is num_data_records = duration / data_record_duration, where duration is the current total signal duration in seconds.

method="strict" (default):

  • Requires that each signal's total duration is exactly divisible by the new data_record_duration (i.e. the total sample count of every signal is an integer multiple of its per-record sample count). If not, raise a ValueError with a message of the form:

    Signal duration of {duration}s is not exactly divisible by data_record_duration of {data_record_duration}s

    where {duration} is the current total duration (e.g. 10.0) and {data_record_duration} is the requested value (e.g. 0.3). Example: requesting 0.3 on a 10.0s recording produces:

    Signal duration of 10.0s is not exactly divisible by data_record_duration of 0.3s

  • When divisible, the signal data is unchanged; only the record partitioning changes.

    Example: a signal of 100 samples at 10 Hz (10.0s total). Updating to 0.1 yields data_record_duration == 0.1 and num_data_records == 100.

method="pad":

  • The number of data records is rounded up so that all signal samples fit, and each signal is padded at the end to fill the last (partial) record.

  • The padding value for each signal is the signal's physical minimum (i.e. the lower bound of its physical range). For a signal whose physical range lower bound is 0, padding is zeros; for a lower bound of 5, padding uses 5.0; for -105, padding uses -105.0, etc.

  • After padding, edf.signals[i].data equals the original data concatenated with the pad values.

    Example: 100 samples at 10 Hz, updating to 0.3 with method="pad": samples_per_record = 3, records needed = ceil(100/3) = 34, num_data_records == 34, duration == 10.2, and the signal data becomes the original 100 samples followed by 2 padding samples (102 total).

method="truncate":

  • The number of data records is rounded down, and each signal is truncated to a whole number of records; trailing samples that do not fill a complete record are discarded.

  • After truncation, edf.signals[i].data equals the original data truncated to num_data_records * samples_per_record samples.

    Example: 100 samples at 10 Hz, updating to 0.3 with method="truncate": samples_per_record = 3, records = floor(100/3) = 33, num_data_records == 33, duration == 9.9, and the signal data becomes the first 99 samples.

Sampling-frequency compatibility check (all methods)

For the chosen data_record_duration, every signal's samples_per_record = sampling_frequency * data_record_duration must be a whole (integer) number of samples. If any signal's sampling frequency is incompatible with the requested duration, raise a ValueError with a message of the form:

Cannot set data record duration to {data_record_duration}: Incompatible sampling frequency {frequency} Hz

Example: two 10 Hz signals, requesting 0.05 (which would require 0.5 samples per record) produces a message beginning:

Cannot set data record duration to 0.05: Incompatible sampling frequency 10.0 Hz
Positive-value check for signal-bearing EDFs

For an Edf that contains ordinary signals, the requested data_record_duration must be strictly positive. If it is 0 or negative, raise a ValueError with a message containing:

Data record duration must be positive
Behavior for annotations-only EDFs

If the Edf contains no ordinary signals (only annotations):

  • The only valid data_record_duration is 0.0. Calling with 0.0 succeeds and results in edf.data_record_duration == 0.0 and edf.num_data_records == 1.
  • Calling with any nonzero value must raise a ValueError with a message containing:
    Data record duration must be zero

Part 4: Annotation preservation and round-tripping

update_data_record_duration must keep annotations intact so that after the update, writing the Edf to a file and reading it back reproduces:

  • The correct data_record_duration and num_data_records.
  • The original signal data (for strict).
  • The original annotations, compared as a tuple of EdfAnnotation objects. Annotations may have onset (float), duration (float or None), and text (str).

Requirements verified by round-trip:

  • Single signal + annotations: An Edf with one 10 Hz / 30-sample signal and three annotations at onsets 0, 10, 20 (duration None), updated to 0.3 (strict), yields data_record_duration == 0.3, num_data_records == 10, unchanged signal data, and the same three annotations after write/read.

  • Multiple annotation signals: An Edf may already contain multiple internal annotations signals (one possibly carrying record-start timestamps, others not). After updating the data record duration, all annotations from all annotation signals must be preserved and reproduced (concatenated in order) after write/read.

  • Pad/truncate with annotations: For a 40-sample, 10 Hz signal with annotations that have non-None durations, updating to 0.3:

    • with method="pad": num_data_records == 14, duration == 14 * 0.3, annotations preserved.
    • with method="truncate": num_data_records == 13, duration == 13 * 0.3, annotations preserved.

  • Sub-second start-time offset: For an Edf whose starttime carries a sub-second (microsecond) component, updating the data record duration must preserve that microsecond offset. Example: a 100-sample, 10 Hz signal (10.0s), starttime 00:00:00.153781, one annotation (5, 5, "ann 1"), updated to 2.5, yields data_record_duration == 2.5, num_data_records == 4, duration == 10, the annotation preserved, and edf.starttime.microsecond == 153781 after write/read.

Public API summary

The following must be importable and usable (existing names retained unless noted):

  • Edf — class.
    • Constructor accepts at least: a list of EdfSignal as first positional argument, keyword annotations (iterable of EdfAnnotation), keyword data_record_duration (float), keyword starttime (datetime.time).
    • Property data_record_duration -> float (read-only).
    • Property num_data_records -> int.
    • Property duration -> float.
    • Property signals (indexable; each element has a .data numpy array).
    • Property starttime (a datetime.time).
    • Method update_data_record_duration(data_record_duration: float, method: Literal["strict", "pad", "truncate"] = "strict") -> None.
    • Method write(path).
  • EdfSignal — class; constructor accepts data array, sampling frequency, and keyword arguments physical_range and digital_range (each a 2-tuple of floats).
  • EdfAnnotation — class with fields onset, duration, text.
  • A module-level function read_edf(path) -> Edf.

The internal raw-header attribute for the data record duration must be named __data_record_duration (name-mangled), holding the 8-byte left-justified ASCII header value.

04 You are working with an EDF (European Data Format) library that models signals, writes them to files, and reads them back. 494 words · source specification

Overview

You are working with an EDF (European Data Format) library that models signals, writes them to files, and reads them back. A floating-point precision issue exists in the calculation of signal-related durations when non-integer sampling frequencies combine with the data record duration to produce values that are mathematically exact integers but computed imprecisely with floating-point arithmetic. You must correct this so that these quantities round to their intended integer values.

Public API Surface

The following must be importable and callable exactly as described (existing API — preserve these signatures and behaviors):

  • Edf class, constructible as Edf(signals=..., data_record_duration=...), where:

    • signals is a list of EdfSignal instances.
    • data_record_duration is a number (seconds per data record).
    • Instances have a .write(path) method that serializes the EDF to the given file path.
    • Instances have a .num_data_records integer property.
    • Instances have a .signals property returning the list of signals.

  • EdfSignal class, constructible as EdfSignal(data, sampling_frequency), where:

    • data is a 1-D NumPy array of samples.
    • sampling_frequency is a number (samples per second), which may be a non-integer value such as 22 / 9.
    • Instances have a .samples_per_data_record integer property.

  • read_edf(path) function that reads an EDF file from the given path and returns an Edf instance.

Required Behavior

For each signal, the number of samples contained in one data record is determined by the product of the signal's sampling frequency and the data record duration. This value is mathematically an integer in valid cases, but a naive floating-point multiplication can yield a result that is fractionally off from the true integer (e.g., 2.4444... × 9 producing something like 21.999999996 or 22.000000004). The correct behavior is to round such products to the nearest integer so the intended whole-sample-per-record count is obtained.

Similarly, the total number of data records is derived from the overall signal duration and the data record duration; this derivation must also round correctly so a mathematically exact integer count is not corrupted by floating-point error.

Concrete case that must work

Given:

  • Signal A: 220 samples at a sampling frequency of 22 / 9 samples per second.
  • Signal B: 90 samples at a sampling frequency of 1 sample per second.
  • Data record duration: 9 seconds.

After writing this Edf to a file and reading it back:

  • The number of data records must be 10.
  • Signal A's samples per data record must be 22.
  • Signal B's samples per data record must be 9.

These integer values must be produced despite the intermediate floating-point products (e.g., (22/9) * 9) not being exactly 22.0.

Constraints

  • Preserve all existing behavior of the classes and functions. Only the rounding of the derived integer quantities (samples per data record and number of data records) is being corrected.
  • The written file, when read back, must reconstruct the signals with the correct integer per-record sample counts and correct data record count.

  • Parsing "X M 21-AUG-1984" must yield:

Required Behavior: Recording._from_str

The local recording identification string always begins with the literal token "Startdate", followed in order by these subfields:

  1. startdate
  2. hospital administration code
  3. investigator/technician code
  4. equipment code
  5. one or more optional "additional" subfields

Any subfield that is absent from the input string (because the string was truncated after "Startdate" or after any later subfield) must behave exactly as if the placeholder "X" had been supplied for it.

The resulting Recording object must expose:

  • hospital_administration_code — string; "X" when absent.
  • investigator_technician_code — string; "X" when absent.
  • equipment_code — string; "X" when absent.
  • additional — a tuple of remaining subfields; an empty tuple () when there are none.
  • startdate — a property returning a datetime.date. When the startdate subfield is the placeholder "X" or absent, accessing this property must raise AnonymizedDateError whose message contains the text startdate is not available.
Specific cases

  • Parsing "Startdate " (the token followed by a space, with all subsequent subfields absent) must yield:

    • hospital_administration_code == "X", investigator_technician_code == "X", equipment_code == "X", additional == ()
    • accessing startdate raises AnonymizedDateError (message containing startdate is not available)

  • Parsing "Startdate 13-MAY-2025 X" must yield:

    • hospital_administration_code == "X", investigator_technician_code == "X", equipment_code == "X", additional == ()
    • startdate == datetime.date(2025, 5, 13)

Notes on Startdate Handling

Existing behavior for recording identification strings with an invalid or malformed startdate that still contains the full set of subfields must remain intact. The change is strictly about tolerating fewer subfields than expected (trailing subfields absent), not about relaxing validation of present subfields. In particular, a recording string whose startdate portion is malformed but that contains the placeholder-and-remaining subfields should still be handled by the pre-existing startdate error logic.

Public API Surface

  • Patient class with classmethod _from_str(cls, string: str) -> Patient and attributes/properties code, sex, name, additional, birthdate.
  • Recording class with classmethod _from_str(cls, string: str) -> Recording and attributes/properties hospital_administration_code, investigator_technician_code, equipment_code, additional, startdate.
  • AnonymizedDateError exception, raised when an anonymized/unspecified date property is accessed.

These are importable from the same module locations where they currently reside.

Date Format

Date subfields (birthdate, startdate) use the DD-MON-YYYY format where MON is a three-letter uppercase English month abbreviation (e.g. 21-AUG-1984, 13-MAY-2025). Successful parsing yields a datetime.date.

Overview

Modify the behavior of the read_edf function's handling of file-like objects that are opened in a mode that does not permit reading.

Required Behavior Change

When read_edf is given a file-like object that is not readable (for example, a file opened in write-only binary mode "wb"), the function must raise io.UnsupportedOperation with a message that includes the text "read".

Previously such an input caused a NotImplementedError (with a message like "Can not read EDF from"). This is no longer the desired behavior — attempting to read from a non-readable file-like object must now surface as an io.UnsupportedOperation error referencing "read".

API Surface

  • read_edf — the existing public function used to read EDF data. Its import path and call signature remain unchanged; only the error raised for non-readable file-like inputs changes.

Notes

  • The error type must be io.UnsupportedOperation (from the standard library io module), and the associated message must contain the substring read.
  • No other behavior of read_edf is affected by this task.
