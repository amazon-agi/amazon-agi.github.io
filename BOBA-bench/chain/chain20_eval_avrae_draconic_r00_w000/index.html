Task Specification: draconic Expression Interpreter

Overview

The task is to provide a package named draconic that implements a safe interpreter for Python-like expressions. It evaluates source strings, restricting unsafe language features and enforcing resource limits as it does so. Names, operators, and the safety configuration are specific to each instance and may be changed at runtime; changing one interpreter must not reconfigure another.

Public API

The names listed next must be importable directly from draconic:

  • DraconicInterpreter
  • FeatureNotAvailable
  • InvalidExpression
  • IterableTooLong
  • NotDefined
  • NumberTooHigh

The package must also expose the accessible submodules draconic.config and draconic.interpreter.

Functions available by default

draconic.config.DEFAULT_FUNCTIONS is a mapping whose bindings are exactly the following:

{
    "int": int,
    "float": float,
    "str": str,
    "dict": dict,
    "tuple": tuple,
    "list": list,
    "set": set,
}
Exceptions

Each of the five exception names exported above is an exception class, and each one can be caught individually.

  • InvalidExpression denotes input that is invalid for the interpreter.
  • NotDefined denotes a name or attribute that is unavailable. It must be a subclass of InvalidExpression; an undefined-name error is therefore catchable as either type.
  • FeatureNotAvailable denotes an operation that is syntactically valid but forbidden.
  • NumberTooHigh denotes a violation of a numeric safety limit.
  • IterableTooLong denotes a violation of an iterable-size limit or of the comprehension-work limit.

DraconicInterpreter

Construction and namespaces
DraconicInterpreter(builtins=None)
  • When no builtins argument is given, the interpreter's built-in namespace starts out with all seven entries from draconic.config.DEFAULT_FUNCTIONS. Thus int, float, str, dict, tuple, list, and set can be called immediately with normal Python behavior.
  • If builtins is supplied, that mapping replaces the default built-in namespace instead of extending it. Only the entries of that mapping, together with user names supplied afterwards, are available. As an example, builtins={"list": list, "map": map, "str": str} makes those three names available but does not make dir available.
  • builtins is an instance attribute that is writable. Replacing it — including replacing it with {} — immediately changes how built-in names resolve, without discarding the user names stored separately.
  • names is a dict-like namespace that is mutable, readable, and assignable. Built-ins and user names are distinct scopes. Reading names exposes the effective merge of the two, equivalent to {**builtins, **user_names}; when both scopes contain the same key, the user name is the one that wins. In-place additions or updates made through names affect the user-name scope. When a new mapping is assigned to names, only the user-name portion is replaced, not builtins.
  • Names that assignment statements create while being evaluated are stored in the user-name portion and remain available to later evaluations.

The effective namespace can be extended by a caller, for example:

interp.names = {**interp.names, "sum": sum}

Referencing or calling a name that is absent from the effective namespace raises NotDefined.

Customization at runtime

Every interpreter exposes the following customization points, each of which is mutable and belongs to the instance:

  • _config: a configuration object specific to the instance. At minimum it has:
    • max_power_base: the maximum absolute base permitted for exponentiation. Its default is 1_000_000.
    • disallow_prefixes: the attribute-name prefixes that dot access forbids. By default it contains both "_" and "func_".
  • operators: a mutable dictionary in which the keys are AST operator/node classes and the values are callables used for operator behavior. It must accept additions or overrides at runtime, including an entry keyed by ast.Slice, and the changes apply to subsequent evaluations.
  • ATTR_INDEX_FALLBACK: a Boolean that controls mapping-style fallback during attribute lookup. Its default is enabled. Turning it off must not turn off ordinary object attribute access.

Safety settings and restrictions are per interpreter and are consulted at the time an evaluation occurs. Because of this, mutating an instance's configuration changes subsequent evaluations immediately. For example, lowering _config.max_power_base can cause a previously accepted power to be rejected, and replacing _config.disallow_prefixes with ["func_"] permits underscore-prefixed attributes while func_-prefixed attributes continue to be rejected.

eval
interp.eval(source: str)

Before parsing, eval strips leading and trailing spaces and tabs; it then evaluates the submitted expression or supported assignment statement and returns its value. Assignment statements that succeed return None. Source that is syntactically invalid raises InvalidExpression; source that is supported but uses an explicitly forbidden feature raises FeatureNotAvailable.

Supported Language Behavior

Literals, containers, indexing, and slicing

The interpreter supports the following:

  • integers and floating-point numbers, strings, bytes, True, False, and None;
  • literals for list, tuple, set, and dictionary;
  • indexing of sequences and mappings;
  • slices in Python style, including omitted bounds and steps, negative steps, and forms such as [:], [1:3], [::2], and [::-1];
  • membership tests via in and not in.

The usual failures from container access are preserved. Specifically, a sequence index that is out of range raises IndexError, a missing key used with explicit subscript syntax raises KeyError, and a NotImplementedError raised by an object's __getitem__ propagates unchanged.

Operators and evaluation order

These operators are supported:

  • arithmetic operations: +, -, *, /, //, %, and **;
  • unary operations: unary +, unary -, and not;
  • comparisons: ==, !=, <, <=, >, >=, in, not in, is, and is not;
  • Boolean operations: and and or;
  • conditional expressions: value_if_true if condition else value_if_false.

Their observable evaluation behavior is the same as Python's:

  • With and and or, operands are evaluated lazily from left to right, and what gets returned is the selected operand itself rather than always a Boolean.
  • In a conditional expression, the condition is evaluated first, and only the branch that is selected is evaluated.
  • Chained comparisons are evaluated from left to right, a shared middle operand is evaluated only once, and after a false comparison the evaluation stops before the later operands.
  • A comparison returns the value that the underlying rich-comparison operation produces, without unconditionally converting it to bool. For example, the result of a custom __gt__ is preserved when it comes from a single > expression.
  • Identity comparisons follow Python's identity semantics; for example, None is None is True and None is not None is False.
Function and method calls

Names that are installed in the effective namespace may be called. Calls support being made with no arguments, with positional arguments, with keyword arguments, and with Python's normal default-argument binding. Return values and the side effects of callables are preserved, and methods may be chained through the objects that are returned.

Methods that are allowed on evaluated values work in the normal way — for instance, "WORD".lower(), dictionary get, string split and encode, and comparable host-object methods. Invalid argument combinations raised by the callable, including missing required arguments, propagate as TypeError instead of being translated into an interpreter exception.

Attribute access

The interpreter applies its safety restrictions to the attribute name before resolving obj.attr. If the name is allowed, lookup proceeds as follows:

  1. Ordinary object attribute lookup is tried, including the object's normal __getattr__ behavior.
  2. If that fails and ATTR_INDEX_FALLBACK is enabled, mapping/index lookup is tried with the attribute name as a string key, equivalent to obj["attr"].
  3. If neither form resolves the name, NotDefined is raised.

This is what permits nested dictionary access such as a.b.c when a == {"b": {"c": 42}}, while real object attributes are given precedence over the mapping fallback.

By default, any attribute accessed with dot syntax that begins with "_" or "func_" raises FeatureNotAvailable, no matter whether the access appears directly, in a comprehension, or inside an f-string. Dunder paths such as .__dict__, .__class__, and .__globals__ are covered by this. Independently of prefix matching, the attribute/method names format, format_map, and mro are forbidden as well, and they raise FeatureNotAvailable when accessed through attribute syntax. Ordinary methods that are not blocked remain available.

F-strings

F-strings support literal text, interpolation that is evaluated, and Python format specifications — including fill and alignment specifications such as f"{'dramatic':!<11}". The same name and attribute restrictions that apply to expressions outside f-strings also apply to interpolated expressions. The complete string that gets constructed is subject to the iterable-length limit described below.

Comprehensions and generator expressions

List, set, and dictionary comprehensions are supported, and generator expressions passed to callables are supported too. Within them, the following are supported:

  • the ability to refer to external interpreter names;
  • one or more for generators;
  • conditions that filter;
  • generators appearing later that refer to earlier targets;
  • tuple/list target unpacking, including unpacking nested recursively;
  • the normal kind of self-reference to the target of the current iteration.

The values of a generator expression are produced lazily, as they get consumed. Iteration variables used by comprehensions are scoped locally: after completion they never become user names and never overwrite outer names, and even if evaluation fails partway through, they still do not leak.

Assignment

Simple and augmented assignment statements are supported by eval.

  • Assigning to a name updates the persistent user-name scope belonging to the interpreter.
  • Assigning to a subscript mutates the list, dictionary, or other assignable container being referenced; targets involving nested subscripts are supported.
  • With augmented assignment, the existing target and the right-hand operand are evaluated under the same operator and name-resolution rules. An operand that is undefined raises NotDefined.
  • An assignment or augmented assignment that succeeds returns None.
  • Assignment using attribute syntax — for instance, a.b = 1 — is forbidden and raises FeatureNotAvailable, even when reading that attribute would use the dictionary-key fallback.
Explicitly unavailable constructs

Lambda expressions, calls of lambda expressions performed immediately, and import statements are unavailable and raise FeatureNotAvailable.

Safety Limits

Exponentiation

Given base ** exponent:

  • raise NumberTooHigh if abs(base) is greater than the interpreter's _config.max_power_base;
  • independently, raise NumberTooHigh if abs(exponent) is greater than 1_000;
  • being equal to either limit is allowed.

Power expressions keep Python's right associativity. As a consequence, 9**9**3 is allowed under the defaults, while 9**9**8 is rejected when the outer operation receives the excessively large computed exponent.

Iterable length

The default maximum length for an iterable is 100_000, inclusive. A value with a length of exactly 100_000 is allowed; an operation that would produce a longer value raises IterableTooLong before the oversized result is constructed, where possible. This limit applies to:

  • literals of strings and bytes;
  • repetition of an iterable with the operands in either order, such as text * count and count * text, including strings, bytes, lists, and tuples;
  • concatenation of iterable values that bear a length;
  • the complete result produced by an f-string.

The checks also apply through nested expressions; splitting or encoding a value that is allowed does not permit a later repetition or concatenation to bypass the limit.

Comprehension work

Every call to eval carries a cumulative comprehension budget of 10_000 iterations. Every item drawn by every generator in a comprehension is counted, including items that get filtered, additional generators, and generators inside nested comprehensions. At most 10_000 iterations are allowed; attempting the next one raises IterableTooLong. Within that evaluation, the counter is shared across nested comprehension work, and it is reset for the next evaluation.

Error Propagation

Failures of safety and name resolution use the interpreter exceptions specified above. Exceptions that are naturally raised after an allowed host callable, method, or explicit container operation has been invoked are not wrapped wholesale. In particular, TypeError, IndexError, KeyError, and NotImplementedError propagate unchanged in the situations described above.

Task Specification: The Draconic Interpreter Library

Summary

The task is to implement the Python package draconic, a restricted interpreter for evaluating untrusted, Python-like expressions. It must expose namespaces and resource limits that are configurable, while rejecting language features that are unsupported or unsafe.

The package's public API

The imports below must work:

from draconic import (
    DraconicInterpreter, SimpleInterpreter,
    FeatureNotAvailable, InvalidExpression, IterableTooLong,
    NotDefined, NumberTooHigh,
)
from draconic.helpers import DraconicConfig
from draconic.exceptions import *

The draconic.config module, together with its DEFAULT_FUNCTIONS mapping, must also be exposed by the top-level package. DraconicConfig must be available from draconic.helpers; it may additionally be exposed from draconic.config and the package root.

SimpleInterpreter serves as the simpler/base interpreter and must remain publicly importable. DraconicInterpreter builds on top of it, adding compound values, comprehensions, and assignment. Beyond its base role, no additional standalone feature parity is required of SimpleInterpreter.

Exception types

These exception classes must be exported by draconic.exceptions, including through wildcard import:

  • InvalidExpression(Exception): the base class for errors raised during Draconic evaluation.
  • NotDefined(InvalidExpression): a name or attribute that is referenced is unavailable.
  • FeatureNotAvailable(InvalidExpression): the syntax or access involved is unsupported or forbidden.
  • DraconicValueError(InvalidExpression): a Draconic value operation that is invalid.
  • LimitException(InvalidExpression): the base class for failures of configured limits.
  • NumberTooHigh(LimitException): a numeric operation that exceeds its safe limit.
  • IterableTooLong(LimitException): an iterable construction or comprehension that exceeds its limit.
  • TooManyStatements(LimitException): statement execution that exceeds its limit.

NotDefined must in particular be a subclass of InvalidExpression, so a handler for InvalidExpression also catches failures involving undefined names. Exceptions are raised and are never returned as evaluation results. Normal exceptions that allowed Python operations produce remain observable where applicable; for example, a bad function signature raises TypeError, an invalid index raises IndexError, a missing mapping key raises KeyError, and an exception from a custom __getitem__ is not silently replaced.

Configuration settings

Writable configuration attributes must be accepted and exposed by DraconicConfig, equivalent to this constructor:

DraconicConfig(
    max_const_len=100000,
    max_loops=10000,
    max_statements=100000,
    max_power_base=1000000,
    max_power=1000,
    disallow_prefixes=None,
    disallow_methods=None,
    default_names=None,
    builtins_extend_default=True,
)

Whenever the corresponding argument is None, the defaults are the following:

  • disallow_prefixes: ['_', 'func_']
  • disallow_methods: ['format', 'format_map', 'mro']
  • default_names: draconic.config.DEFAULT_FUNCTIONS

These settings are what subsequent evaluations use, and that includes situations where a caller changes a setting such as max_power_base or disallow_prefixes at runtime. A DraconicInterpreter that is constructed without a config creates a default DraconicConfig and uses it.

DEFAULT_FUNCTIONS must be a dictionary that contains all of the names below, mapped to their normal Python callables:

  • int
  • float
  • str
  • dict
  • tuple
  • list
  • set

So, as an example, int("42") returns 42, dict(a=1) returns {'a': 1}, and tuple("foo"), list("foo"), and set("foo") carry out their normal conversions.

Constructing the interpreter and namespaces

Construction of DraconicInterpreter must be supported in the following form:

DraconicInterpreter(builtins=None, config=None)

It exposes the names property together with builtins and _names:

  • builtins is a settable mapping that contains the interpreter's built-in callable/name layer.
  • _names is a mutable mapping of user names. Direct insertion, such as interpreter._names['value'] = 42, must make that name resolvable.
  • Reading names returns the merged available namespace, which is equivalent to {**builtins, **_names}. A user name therefore takes precedence over a built-in that has the same name.
  • Assigning names = mapping replaces the whole user-name layer (_names) but does not replace builtins. User names that existed before but are not present in the replacement disappear.
  • Since the getter is a merged mapping, additions that are meant to persist should be made by assigning names or by mutating _names; callers may use {**interpreter.names, 'x': value} when constructing a replacement.
  • Assigning builtins = {} takes the default functions out of the available namespace unless equivalent names exist in _names. A later reference to an absent function, such as int, raises NotDefined.

builtins contains config.default_names by default. When built-ins supplied through the constructor are given and builtins_extend_default is true, they extend the defaults and override keys that are equal. When builtins_extend_default is false, the supplied mapping is used and the defaults are not added; when no mapping is supplied, the built-in layer is empty.

Consequently, the assignment interpreter.names = {'read': read} normally leaves the default conversions available through the built-in layer, which is separate. To create a namespace in which only read is available, also set interpreter.builtins = {}. In that state, read(...) works while int(read(...)) raises NotDefined; once DEFAULT_FUNCTIONS is added to either available layer, the conversion works again.

Entry point for evaluation

DraconicInterpreter.eval(expr) accepts a string that contains an expression or a supported statement, and returns the value obtained by evaluating it. It must strip leading and trailing spaces and tabs before parsing takes place, so surrounding whitespace does not change the result.

Names that are absent from the merged namespace raise NotDefined. The names True, False, and None, which are Python literals, retain their normal values. Parentheses and ordinary nesting of expressions work normally.

Operators and the semantics of expressions

The following must be supported by the interpreter:

  • Arithmetic: +, -, *, /, //, %, and **.
  • Unary operators: unary +, unary -, and not.
  • Comparisons: ==, !=, <, <=, >, and >=.
  • Membership: in and not in.
  • Identity: is and is not, with Python identity semantics used.
  • Boolean operators: and and or.
  • Conditional expressions: value_if_true if condition else value_if_false.

Otherwise, arithmetic and comparison results follow the underlying Python operations, with mixed integer/float behavior included. If a comparison implementation returns a non-boolean object, that result must be preserved when it is the expression's final comparison result.

For and and or, the operand values are returned rather than every result being coerced to bool; they short-circuit in exactly the way Python does. In a conditional expression, only the branch that is selected is evaluated. Chained comparisons such as 1 < 2 < 3 < 4 are evaluated from left to right, each necessary operand is evaluated only once, and after a false comparison, evaluation stops before later operands are evaluated.

Every interpreter instance exposes a mutable operators dictionary, keyed by Python ast operator classes, that contains the callables used for the supported operations. Callers may replace or add entries at runtime, including by assigning an entry such as operators[ast.Slice] = operator.getitem. Where applicable, subsequent evaluation must continue to support indexing and slicing.

Literals, containers, indexing, and slices

Normal construction of the following must be supported by DraconicInterpreter:

  • list literals, an example being [1, 2, 3]
  • tuple literals, including () and tuples with one element
  • set literals, an example being {1, 2}
  • dictionary literals, an example being {'a': 1}

The default callables dict, tuple, list, and set must work as well, keyword arguments to calls such as dict(a=1) included.

Subscript access must support sequences as well as mappings, including chained access. Slices must support bounds and steps that are omitted, negative steps, and all the normal forms, such as value[:], value[1:3], value[::2], and value[::-1]. The underlying IndexError, KeyError, or custom item-access exceptions propagate.

Star-unpacking inside a list display is intentionally unsupported. Evaluating an expression such as [*x, *y] must raise FeatureNotAvailable, even when x and y are names that are otherwise valid and available.

Calls, methods, and attribute access

Available callables may be invoked with positional arguments, with keyword arguments, or with both. Their normal required arguments, default values, return values, and TypeError behavior are preserved. Methods on values are callable, so "WORD".lower() returns "word"; when each call returns a suitable object, method calls may be chained.

With obj.attr, the interpreter performs allowed normal attribute lookup first. If that lookup fails, it attempts mapping/item lookup equivalent to obj['attr']. This is what makes nested dictionary access such as a.b.c possible when a is {'b': {'c': 42}}. If neither form succeeds, NotDefined is raised. Direct subscript access remains direct and must not be replaced by an attribute fallback.

Attribute access is subject to the security restrictions below, including when it occurs inside a comprehension or an f-string.

F-string support

F-strings are supported, with expression interpolation and format specifications. Examples include:

f"one is {1} and two is {2}"       # "one is 1 and two is 2"
f"{"dramatic":!<11}"             # "dramatic!!!"

Interpolated expressions use the same namespace, operator behavior, limits, and forbidden-attribute rules as ordinary expressions do. max_const_len applies to the complete f-string that results.

Comprehensions and generator expressions

List comprehensions, set comprehensions, dictionary comprehensions, and generator expressions must be supported by the interpreter. The required behavior includes:

  • one or multiple for clauses
  • one or multiple if filters
  • references to names found in the outer interpreter namespace
  • references to variables that earlier clauses have bound
  • unpacking of tuple/list targets, including nested unpacking
  • use as an argument to an available callable, such as a generator expression passed to sum

Comprehension clauses follow the nesting and filtering order of Python. Their local target variables must not leak into _names or the outer namespace after evaluation — including when comprehension evaluation fails. Attribute access that is forbidden remains forbidden inside comprehensions.

Iterations across the generator clauses of a comprehension consume the configured loop budget, including iterations whose values are rejected later by a filter. If that budget is exceeded during a comprehension, IterableTooLong is raised; nested comprehensions and multiple generator clauses cannot be used to bypass the limit.

Assignment statements

The following supported assignment statements must be accepted by eval:

  • Assignment to a name, such as a = 200, updates _names and returns None.
  • Assignment to an item, such as items[0] = 11 or mapping['key'] = value, updates the underlying container and returns None. Assignment targets may be chained subscripts.
  • Unpack assignment of a tuple/list is supported for iterable structures that match; unpacking that is invalid raises InvalidExpression.
  • Augmented assignment, such as value += amount, uses the corresponding supported operator, and the result is persisted. When evaluating the right side or the existing target fails, that error is raised rather than a value being returned.

Assigning to an attribute — including an apparent dictionary attribute such as a.b = 11 — is not permitted and raises FeatureNotAvailable. Item assignment, such as a['b'] = 11, remains permitted. When a name being assigned is already present in the built-in layer, the assignment is rejected with DraconicValueError rather than that built-in being silently shadowed.

Restrictions and unsupported features

This interpreter does not serve as a general Python executor. The following restrictions apply, at minimum:

  • Lambda expressions raise FeatureNotAvailable, whether they are merely created or immediately called.
  • An import statement raises FeatureNotAvailable.
  • A syntax node that is unsupported raises FeatureNotAvailable.
  • Star-unpacking in a list display raises FeatureNotAvailable.
  • Assignment to an attribute raises FeatureNotAvailable.
  • Arbitrary Python built-ins are not implicitly available; a name such as dir, when absent, raises NotDefined unless it is explicitly supplied.

By default, accessing any attribute whose name begins with _ or func_ is forbidden and raises FeatureNotAvailable. Values such as __class__, __dict__, __globals__, _private, and func_globals are blocked by this. The restriction applies at every point in an attribute chain, as well as inside f-strings. If config.disallow_prefixes is changed, the active rule changes too; for example, retaining only func_ permits attributes with a single underscore while func_ names continue to be blocked.

The default blocklist of method names contains at least format, format_map, and mro. Accessing or calling these through evaluated values raises FeatureNotAvailable; the blocking is independent of prefix matching.

Limits on resources

Length of iterables

max_const_len is the maximum length permitted for an iterable literal or an iterable result created/materialized by the interpreter in the guarded contexts. A length that is equal to the configured maximum is allowed; a length greater than it raises IterableTooLong. It applies at least to:

  • strings and other constants that have a size
  • the construction of compound iterables
  • repetition in either order, such as 'text' * n and n * 'text', with bytes and lists included
  • concatenation of sized iterables when the combined length exceeds the limit
  • the cumulative output of an f-string

Intermediate results are checked as they are formed, so nesting a multiplication or concatenation that is too large does not bypass the limit. For example, with max_const_len=1000, a literal that contains 3000 characters raises IterableTooLong.

Exponentiation

Before every a ** b, the interpreter must reject the operation by raising NumberTooHigh if either abs(a) > max_power_base or abs(b) > max_power. The default limits are a base magnitude of 1_000_000 together with an exponent magnitude of 1000; values that equal the limits are allowed. The checks also apply to nested exponentiation.

Loops and statements

The total count of loop/comprehension iterations allowed for an execution is controlled by max_loops. It is accepted as a constructor keyword and is enforced; setting it very high effectively removes that practical constraint for ordinary evaluations. max_statements similarly bounds the statements/nodes that are evaluated, with overflow represented by TooManyStatements.

Compatibility expectations

All of the names and modules documented above must remain importable exactly as shown. Configuration must be per interpreter, and the behavior of allowed expressions must remain Python-like except where this specification explicitly imposes a namespace rule, a safety restriction, an unsupported feature, or a resource limit.

Task Specification: Enforcing Size Limits for Safe Collection Mutations

Overview

Size-safety checks must be implemented for the mutating and combining operations belonging to the sandboxed collection types that the draconic library provides. Two outcomes are to be ensured: an operation that makes a collection larger cannot push it beyond a configured maximum length, and any operation that returns a new collection always returns the sandboxed (safe) collection types.

Relevant Modules and Their Public Surface

  • draconic.helpers.DraconicConfig — the configuration object. max_loops and max_const_len are among the keyword arguments its constructor accepts; max_const_len is an integer giving the maximum length a collection is allowed to have. The config object exposes max_const_len as an attribute that can be set (i.e. config.max_const_len = 100000 must work at runtime after construction).
  • draconic.DraconicInterpreter — the interpreter, which you construct by calling DraconicInterpreter(config=config).
    • .eval(expr) — evaluates a string of source code.
    • .builtins — a mutable mapping; the assignment interpreter.builtins['name'] = value is what makes name available in evaluated expressions.
    • ._config — the DraconicConfig instance that is in use.
    • ._list — the safe list type employed by this interpreter.
    • ._set — the safe set type employed by this interpreter.
  • draconic.exceptions.IterableTooLong — an exception (importable via from draconic.exceptions import *) that is raised when an operation would produce a collection beyond max_const_len or grow a collection beyond max_const_len.

Behavior That Is Required

The sandboxed collection types the interpreter works with are its own (interpreter._list, interpreter._set). Every collection value produced during evaluation — the results of combining operations included — must be an instance of these safe types; the corresponding built-in Python types are never acceptable. This must continue to hold even when a native Python list or set (injected via builtins) takes part in the operation.

max_const_len sets the maximum size for any collection. Whenever an operation would make a safe collection grow beyond this limit, or would build a new safe collection larger than this limit, it must raise IterableTooLong. For the size check, what must be considered is the total size that exists after the operation has run (e.g. the current length plus the number of elements being added).

Safe List Type

What follows applies to the safe list type (interpreter._list):

  • append(item) — must raise IterableTooLong when an append would carry the list's length past max_const_len.

  • + (concatenation) — when two lists are added together (safe + native, or native + safe, in either order), the value returned must be an instance of interpreter._list.

Further correctness expectations

The cases below must produce the results shown:

Sets:

a = {1, 2, 3}
b = {3, 4, 5}
a | b   →  {1, 2, 3, 4, 5}
a & b   →  {3}
a - b   →  {1, 2}
a ^ b   →  {1, 2, 4, 5}

Dicts (Python 3.9+ only):

a = {"a": 1, "b": 2}
b = {"b": 3, "c": 4}
c = a.copy()
a | b       →  {"a": 1, "b": 3, "c": 4}
c |= b ; c  →  {"a": 1, "b": 3, "c": 4}

Every result that is a collection must be an instance of the interpreter's safe collection types.
