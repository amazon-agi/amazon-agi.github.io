Task Specification: Draconic Expression Interpreter

Overview

Provide a safe Python-like expression interpreter package named draconic. It evaluates source strings while restricting unsafe language features and enforcing resource limits. Names, operators, and safety configuration are instance-specific and may be changed at runtime; changing one interpreter must not reconfigure another.

Public API

The following names must be importable directly from draconic:

  • DraconicInterpreter
  • FeatureNotAvailable
  • InvalidExpression
  • IterableTooLong
  • NotDefined
  • NumberTooHigh

The package must also expose draconic.config and draconic.interpreter as accessible submodules.

Default functions

draconic.config.DEFAULT_FUNCTIONS is a mapping with exactly these bindings:

{
    "int": int,
    "float": float,
    "str": str,
    "dict": dict,
    "tuple": tuple,
    "list": list,
    "set": set,
}
Exceptions

All five exported exception names above are exception classes and can be caught individually.

  • InvalidExpression represents invalid input to the interpreter.
  • NotDefined represents an unavailable name or attribute. It must be a subclass of InvalidExpression, so an undefined-name error is catchable as either type.
  • FeatureNotAvailable represents a syntactically valid but forbidden operation.
  • NumberTooHigh represents a numeric safety-limit violation.
  • IterableTooLong represents an iterable-size or comprehension-work-limit violation.

DraconicInterpreter

Construction and namespaces
DraconicInterpreter(builtins=None)
  • With no builtins argument, the interpreter's built-in namespace is initialized with all seven entries from draconic.config.DEFAULT_FUNCTIONS. Thus int, float, str, dict, tuple, list, and set are immediately callable with normal Python behavior.
  • If builtins is supplied, that mapping replaces the default built-in namespace rather than extending it. Only its entries, together with subsequently supplied user names, are available. For example, builtins={"list": list, "map": map, "str": str} enables those three names but does not enable dir.
  • builtins is a writable instance attribute. Replacing it, including replacing it with {}, immediately changes built-in name resolution without discarding separately stored user names.
  • names is a mutable, readable, and assignable dict-like namespace. Built-ins and user names are distinct scopes. Reading names exposes their effective merge, equivalent to {**builtins, **user_names}; a user name wins if both scopes contain the same key. In-place additions or updates through names affect the user-name scope. Assigning a new mapping to names replaces only the user-name portion, not builtins.
  • Names created by evaluated assignment statements are stored in the user-name portion and remain available to later evaluations.

A caller can extend the effective namespace, for example:

interp.names = {**interp.names, "sum": sum}

Referencing or calling a name absent from the effective namespace raises NotDefined.

Runtime customization

Each interpreter exposes the following mutable instance customization points:

  • _config: a per-instance configuration object. At minimum it has:
    • max_power_base: the maximum permitted absolute base for exponentiation. Its default is 1_000_000.
    • disallow_prefixes: the attribute-name prefixes forbidden by dot access. Its default contains both "_" and "func_".
  • operators: a mutable dictionary whose keys are AST operator/node classes and whose values are callables used for operator behavior. It must accept runtime additions or overrides, including an entry keyed by ast.Slice, and changes apply to subsequent evaluations.
  • ATTR_INDEX_FALLBACK: a Boolean controlling mapping-style fallback during attribute lookup. It defaults to enabled. Disabling it must not disable ordinary object attribute access.

Safety settings and restrictions are per interpreter and are consulted when an evaluation occurs. Mutating an instance's configuration therefore changes subsequent evaluations immediately. For example, lowering _config.max_power_base can reject a previously accepted power, and replacing _config.disallow_prefixes with ["func_"] permits underscore-prefixed attributes while continuing to reject func_-prefixed attributes.

eval
interp.eval(source: str)

eval strips leading and trailing spaces and tabs before parsing, evaluates the submitted expression or supported assignment statement, and returns its value. Successful assignment statements return None. Syntactically invalid source raises InvalidExpression; supported source that uses an explicitly forbidden feature raises FeatureNotAvailable.

Supported Language Behavior

Literals, containers, indexing, and slicing

The interpreter supports:

  • integer and floating-point numbers, strings, bytes, True, False, and None;
  • list, tuple, set, and dictionary literals;
  • indexing sequences and mappings;
  • Python-style slices, including omitted bounds and steps, negative steps, and forms such as [:], [1:3], [::2], and [::-1];
  • membership with in and not in.

Normal container-access failures are preserved. In particular, an out-of-range sequence index raises IndexError, a missing key used with explicit subscript syntax raises KeyError, and an object's NotImplementedError from __getitem__ propagates unchanged.

Operators and evaluation order

The following operators are supported:

  • arithmetic: +, -, *, /, //, %, and **;
  • unary: unary +, unary -, and not;
  • comparisons: ==, !=, <, <=, >, >=, in, not in, is, and is not;
  • Boolean: and and or;
  • conditional expressions: value_if_true if condition else value_if_false.

Their observable evaluation behavior follows Python:

  • and and or evaluate operands lazily from left to right and return the selected operand itself, rather than always returning a Boolean.
  • A conditional expression evaluates its condition first and evaluates only the selected branch.
  • Chained comparisons evaluate left to right, evaluate a shared middle operand only once, and stop before later operands after a false comparison.
  • A comparison returns the value produced by the underlying rich-comparison operation without unconditionally converting it to bool. For example, a custom __gt__ result is preserved by a single > expression.
  • Identity comparisons have Python identity semantics; for example, None is None is True and None is not None is False.
Function and method calls

Names installed in the effective namespace may be called. Calls support no arguments, positional arguments, keyword arguments, and normal Python default-argument binding. Return values and callable side effects are preserved, and methods may be chained through returned objects.

Allowed methods on evaluated values work normally, such as "WORD".lower(), dictionary get, string split and encode, and similar host-object methods. Invalid argument combinations raised by the callable, including missing required arguments, propagate as TypeError rather than being translated to an interpreter exception.

Attribute access

Before resolving obj.attr, the interpreter applies its safety restrictions to the attribute name. If allowed, lookup proceeds as follows:

  1. Try ordinary object attribute lookup, including the object's normal __getattr__ behavior.
  2. If ordinary lookup fails and ATTR_INDEX_FALLBACK is enabled, try mapping/index lookup with the attribute name as a string key, equivalent to obj["attr"].
  3. If neither form resolves the name, raise NotDefined.

This permits nested dictionary access such as a.b.c when a == {"b": {"c": 42}}, while giving real object attributes precedence over mapping fallback.

By default, any dot-accessed attribute beginning with "_" or "func_" raises FeatureNotAvailable, whether the access appears directly, in a comprehension, or inside an f-string. This includes dunder paths such as .__dict__, .__class__, and .__globals__. The attribute/method names format, format_map, and mro are also forbidden independently of prefix matching and raise FeatureNotAvailable when accessed through attribute syntax. Ordinary nonblocked methods remain available.

F-strings

F-strings support literal text, evaluated interpolation, and Python format specifications, including fill and alignment specifications such as f"{'dramatic':!<11}". Interpolated expressions use the same name and attribute restrictions as expressions outside f-strings. The complete constructed string is subject to the iterable-length limit described below.

Comprehensions and generator expressions

List, set, and dictionary comprehensions are supported, as are generator expressions passed to callables. They support:

  • references to external interpreter names;
  • one or more for generators;
  • filtering conditions;
  • later generators that refer to earlier targets;
  • tuple/list target unpacking, including recursively nested unpacking;
  • normal self-reference to the current iteration target.

Generator expressions produce their values lazily as they are consumed. Comprehension iteration variables are scoped locally: they never become user names or overwrite outer names after completion, and they still do not leak if evaluation fails partway through.

Assignment

eval supports simple and augmented assignment statements.

  • Assigning to a name updates the interpreter's persistent user-name scope.
  • Assigning to a subscript mutates the referenced list, dictionary, or other assignable container; nested subscript targets are supported.
  • Augmented assignment evaluates the existing target and right-hand operand using the same operator and name-resolution rules. An undefined operand raises NotDefined.
  • A successful assignment or augmented assignment returns None.
  • Assignment through attribute syntax, such as a.b = 1, is forbidden and raises FeatureNotAvailable, even when read access to that attribute would use dictionary-key fallback.
Explicitly unavailable constructs

Lambda expressions, immediate calls of lambda expressions, and import statements are unavailable and raise FeatureNotAvailable.

Safety Limits

Exponentiation

For base ** exponent:

  • if abs(base) is greater than the interpreter's _config.max_power_base, raise NumberTooHigh;
  • independently, if abs(exponent) is greater than 1_000, raise NumberTooHigh;
  • equality with either limit is allowed.

Power expressions retain Python's right associativity. Consequently, 9**9**3 is allowed under the defaults, while 9**9**8 is rejected when the outer operation receives the excessive computed exponent.

Iterable length

The default maximum iterable length is 100_000, inclusive. A value of length exactly 100_000 is allowed; an operation that would produce a longer value raises IterableTooLong before constructing the oversized result where possible. This limit applies to:

  • string and bytes literals;
  • iterable repetition in either operand order, such as text * count and count * text, including strings, bytes, lists, and tuples;
  • concatenation of length-bearing iterable values;
  • the complete result of an f-string.

The checks apply through nested expressions as well; splitting or encoding an allowed value does not permit a later repetition or concatenation to bypass the limit.

Comprehension work

Each call to eval has a cumulative comprehension budget of 10_000 iterations. Every item drawn by every generator in a comprehension counts, including filtered items, additional generators, and generators inside nested comprehensions. At most 10_000 iterations are allowed; attempting the next one raises IterableTooLong. The counter is shared across nested comprehension work within that evaluation and reset for the next evaluation.

Error Propagation

Safety and name-resolution failures use the interpreter exceptions specified above. Exceptions naturally raised after invoking an allowed host callable, method, or explicit container operation are not blanket-wrapped. In particular, TypeError, IndexError, KeyError, and NotImplementedError propagate unchanged in the situations described above.

Task Specification: Draconic Interpreter Library

Overview

Implement the Python package draconic, a restricted interpreter for evaluating untrusted, Python-like expressions. It must expose configurable namespaces and resource limits while rejecting unsupported or unsafe language features.

Public package API

The following imports must work:

from draconic import (
    DraconicInterpreter, SimpleInterpreter,
    FeatureNotAvailable, InvalidExpression, IterableTooLong,
    NotDefined, NumberTooHigh,
)
from draconic.helpers import DraconicConfig
from draconic.exceptions import *

The top-level package must also expose the draconic.config module and its DEFAULT_FUNCTIONS mapping. DraconicConfig must be available from draconic.helpers; it may also be exposed from draconic.config and the package root.

SimpleInterpreter is the simpler/base interpreter and must remain publicly importable. DraconicInterpreter builds on it with compound values, comprehensions, and assignment. No additional standalone feature parity is required of SimpleInterpreter beyond its base role.

Exceptions

draconic.exceptions must export these exception classes, including through wildcard import:

  • InvalidExpression(Exception): base class for Draconic evaluation errors.
  • NotDefined(InvalidExpression): a referenced name or attribute is unavailable.
  • FeatureNotAvailable(InvalidExpression): syntax or access is unsupported or forbidden.
  • DraconicValueError(InvalidExpression): an invalid Draconic value operation.
  • LimitException(InvalidExpression): base class for configured-limit failures.
  • NumberTooHigh(LimitException): a numeric operation exceeds its safe limit.
  • IterableTooLong(LimitException): an iterable construction or comprehension exceeds its limit.
  • TooManyStatements(LimitException): statement execution exceeds its limit.

In particular, NotDefined must be a subclass of InvalidExpression, so a handler for InvalidExpression also catches undefined-name failures. Exceptions are raised, never returned as evaluation results. Normal exceptions produced by allowed Python operations remain observable where applicable; for example, a bad function signature raises TypeError, an invalid index raises IndexError, a missing mapping key raises KeyError, and a custom __getitem__ exception is not silently replaced.

Configuration

DraconicConfig must accept and expose writable configuration attributes equivalent to this constructor:

DraconicConfig(
    max_const_len=100000,
    max_loops=10000,
    max_statements=100000,
    max_power_base=1000000,
    max_power=1000,
    disallow_prefixes=None,
    disallow_methods=None,
    default_names=None,
    builtins_extend_default=True,
)

When the corresponding argument is None, the defaults are:

  • disallow_prefixes: ['_', 'func_']
  • disallow_methods: ['format', 'format_map', 'mro']
  • default_names: draconic.config.DEFAULT_FUNCTIONS

The settings are used by subsequent evaluations, including when a caller changes a setting such as max_power_base or disallow_prefixes at runtime. A DraconicInterpreter constructed without a config creates and uses a default DraconicConfig.

DEFAULT_FUNCTIONS must be a dictionary containing all of these names mapped to their normal Python callables:

  • int
  • float
  • str
  • dict
  • tuple
  • list
  • set

Thus, for example, int("42") returns 42, dict(a=1) returns {'a': 1}, and tuple("foo"), list("foo"), and set("foo") perform their normal conversions.

Interpreter construction and namespaces

DraconicInterpreter must support construction as follows:

DraconicInterpreter(builtins=None, config=None)

It exposes builtins, _names, and the names property:

  • builtins is a settable mapping containing the interpreter's built-in callable/name layer.
  • _names is a mutable user-name mapping. Direct insertion such as interpreter._names['value'] = 42 must make that name resolvable.
  • Reading names returns the merged available namespace equivalent to {**builtins, **_names}. A user name therefore takes precedence over a same-named built-in.
  • Assigning names = mapping replaces the entire user-name layer (_names) but does not replace builtins. Existing user names not present in the replacement disappear.
  • Because the getter is a merged mapping, persistent additions should be made by assigning names or by mutating _names; callers may use {**interpreter.names, 'x': value} to construct a replacement.
  • Assigning builtins = {} removes the default functions from the available namespace unless equivalent names exist in _names. A later reference to an absent function such as int raises NotDefined.

By default, builtins contains config.default_names. If constructor-supplied built-ins are given and builtins_extend_default is true, they extend the defaults and override equal keys. If builtins_extend_default is false, the supplied mapping is used without adding the defaults; with no supplied mapping, the built-in layer is empty.

Consequently, assigning interpreter.names = {'read': read} normally leaves default conversions available through the separate built-in layer. To create a namespace where only read is available, set interpreter.builtins = {} as well. In that state read(...) works while int(read(...)) raises NotDefined; adding DEFAULT_FUNCTIONS to either available layer makes the conversion work again.

Evaluation entry point

DraconicInterpreter.eval(expr) accepts a string containing an expression or supported statement and returns its evaluated value. It must strip leading and trailing spaces and tabs before parsing, so surrounding whitespace does not change the result.

Names absent from the merged namespace raise NotDefined. Python literal names True, False, and None retain their normal values. Parentheses and ordinary expression nesting work normally.

Operators and expression semantics

The interpreter must support:

  • Arithmetic: +, -, *, /, //, %, and **.
  • Unary operators: unary +, unary -, and not.
  • Comparisons: ==, !=, <, <=, >, and >=.
  • Membership: in and not in.
  • Identity: is and is not, using Python identity semantics.
  • Boolean operators: and and or.
  • Conditional expressions: value_if_true if condition else value_if_false.

Arithmetic and comparison results otherwise follow the underlying Python operations, including mixed integer/float behavior. A comparison implementation that returns a non-boolean object must have that result preserved when it is the expression's final comparison result.

Chained comparisons such as 1 < 2 < 3 < 4 evaluate from left to right, evaluate each necessary operand only once, and stop before evaluating later operands after a false comparison.

Every interpreter instance exposes a mutable operators dictionary keyed by Python ast operator classes and containing the callables used for supported operations. Callers may replace or add entries at runtime, including assigning an entry such as operators[ast.Slice] = operator.getitem. Subsequent applicable evaluation must continue to support indexing and slicing.

Literals, containers, indexing, and slicing

DraconicInterpreter must support normal construction of:

  • list literals, such as [1, 2, 3]
  • tuple literals, including () and one-element tuples
  • set literals, such as {1, 2}
  • dictionary literals, such as {'a': 1}

The default dict, tuple, list, and set callables must also work, including keyword arguments to calls such as dict(a=1).

Subscript access must support sequences and mappings, including chained access. Slices must support omitted bounds and steps, negative steps, and all normal forms such as value[:], value[1:3], value[::2], and value[::-1]. Underlying IndexError, KeyError, or custom item-access exceptions propagate.

Star-unpacking in a list display is deliberately unsupported. Evaluating an expression such as [*x, *y] must raise FeatureNotAvailable, even when x and y are otherwise valid available names.

Calls, methods, and attribute access

Available callables may be invoked with positional arguments, keyword arguments, or both. Their normal required arguments, default values, return values, and TypeError behavior are preserved. Methods on values are callable, so "WORD".lower() returns "word", and method calls may be chained when each call returns a suitable object.

For obj.attr, the interpreter first performs allowed normal attribute lookup. If that lookup fails, it attempts mapping/item lookup equivalent to obj['attr']. This permits nested dictionary access such as a.b.c when a is {'b': {'c': 42}}. If neither form succeeds, it raises NotDefined. Direct subscript access remains direct and must not be replaced by attribute fallback.

Attribute access is subject to the security restrictions below, including when it occurs inside a comprehension or f-string.

F-strings

F-strings are supported with expression interpolation and format specifications. Examples include:

f"one is {1} and two is {2}"       # "one is 1 and two is 2"
f"{"dramatic":!<11}"             # "dramatic!!!"

Interpolated expressions use the same namespace, operator behavior, limits, and forbidden-attribute rules as ordinary expressions. The complete resulting f-string is subject to max_const_len.

Comprehensions and generator expressions

The interpreter must support list comprehensions, set comprehensions, dictionary comprehensions, and generator expressions. Required behavior includes:

  • one or multiple for clauses
  • one or multiple if filters
  • references to names in the outer interpreter namespace
  • references to variables bound by earlier clauses
  • tuple/list target unpacking, including nested unpacking
  • use as an argument to an available callable, such as a generator expression passed to sum

Comprehension clauses follow Python's nesting and filtering order. Their local target variables must not leak into _names or the outer namespace after evaluation, including when comprehension evaluation fails. Forbidden attribute access remains forbidden inside comprehensions.

Iterations across comprehension generator clauses consume the configured loop budget, including iterations whose values are later rejected by a filter. Exceeding that budget during a comprehension raises IterableTooLong; nested comprehensions and multiple generator clauses cannot be used to bypass the limit.

Assignment

eval must accept supported assignment statements:

  • Name assignment, such as a = 200, updates _names and returns None.
  • Item assignment, such as items[0] = 11 or mapping['key'] = value, updates the underlying container and returns None. Chained subscripts may be assignment targets.
  • Tuple/list unpack assignment is supported for matching iterable structures; invalid unpacking raises InvalidExpression.
  • Augmented assignment, such as value += amount, uses the corresponding supported operator and persists the result. If evaluating the right side or existing target fails, that error is raised rather than returning a value.

Assignment to an attribute, including an apparent dictionary attribute such as a.b = 11, is not permitted and raises FeatureNotAvailable. Item assignment such as a['b'] = 11 remains permitted. Assigning a name that is already present in the built-in layer is rejected with DraconicValueError rather than silently shadowing that built-in.

Restricted and unsupported features

This interpreter is not a general Python executor. At minimum, the following restrictions apply:

  • Lambda expressions, whether merely created or immediately called, raise FeatureNotAvailable.
  • Import statements raise FeatureNotAvailable.
  • Unsupported syntax nodes raise FeatureNotAvailable.
  • List-display star-unpacking raises FeatureNotAvailable.
  • Attribute assignment raises FeatureNotAvailable.
  • Arbitrary Python built-ins are not implicitly available; an absent name such as dir raises NotDefined unless explicitly supplied.

By default, access to any attribute whose name starts with _ or func_ is forbidden and raises FeatureNotAvailable. This blocks values such as __class__, __dict__, __globals__, _private, and func_globals. The restriction applies at every point in an attribute chain and inside f-strings. Changing config.disallow_prefixes changes the active rule; for example, retaining only func_ permits single-underscore attributes while continuing to block func_ names.

The default method-name blocklist contains at least format, format_map, and mro. Accessing or calling these through evaluated values raises FeatureNotAvailable; they are blocked independently of prefix matching.

Resource limits

Iterable length

max_const_len is the maximum permitted length of an iterable literal or iterable result created/materialized by the interpreter in the guarded contexts. A length equal to the configured maximum is allowed; a length greater than it raises IterableTooLong. This applies at least to:

  • string and other sized constants
  • compound iterable construction
  • repetition in either order, such as 'text' * n and n * 'text', including bytes and lists
  • concatenation of sized iterables when the combined length exceeds the limit
  • cumulative f-string output

Intermediate results are checked as they are formed, so nesting a too-large multiplication or concatenation does not bypass the limit. For example, with max_const_len=1000, a literal containing 3000 characters raises IterableTooLong.

Exponentiation

Before every a ** b, the interpreter must reject the operation with NumberTooHigh if either abs(a) > max_power_base or abs(b) > max_power. The default limits are a base magnitude of 1_000_000 and an exponent magnitude of 1000; values equal to the limits are allowed. Checks also apply to nested exponentiation.

Loops and statements

max_loops controls the total loop/comprehension iterations allowed for an execution. It is accepted as a constructor keyword and enforced; setting it very high effectively removes that practical constraint for ordinary evaluations. max_statements similarly bounds evaluated statements/nodes, with overflow represented by TooManyStatements.

Compatibility expectations

All names and modules documented above must remain importable exactly as shown. Configuration must be per interpreter, and allowed expression behavior must remain Python-like except where this specification explicitly imposes a namespace rule, safety restriction, unsupported feature, or resource limit.

Task Specification: Enforce Size Limits on Safe Collection Mutations

Overview

You must implement size-safety checks on the mutating and combining operations of the sandboxed collection types provided by the draconic library. The goal is to ensure that operations which grow a collection cannot exceed a configured maximum length, and that operations returning new collections always return the sandboxed (safe) collection types.

Relevant Modules and Public Surface

  • draconic.helpers.DraconicConfig — configuration object. Constructor accepts keyword arguments including max_loops and max_const_len (an integer maximum allowed length for a collection). It exposes max_const_len as a settable attribute (i.e. config.max_const_len = 100000 must work at runtime after construction).
  • draconic.DraconicInterpreter — interpreter, constructed with DraconicInterpreter(config=config).
    • .eval(expr) — evaluates a source string.
    • .builtins — a mutable mapping; assigning interpreter.builtins['name'] = value makes name available in evaluated expressions.
    • ._config — the DraconicConfig instance in use.
    • ._list — the safe list type used by this interpreter.
    • ._set — the safe set type used by this interpreter.
  • draconic.exceptions.IterableTooLong — exception (importable via from draconic.exceptions import *) raised when an operation would produce or grow a collection beyond max_const_len.

Required Behavior

The interpreter uses its own sandboxed collection types (interpreter._list, interpreter._set). All collection values produced during evaluation — including the results of combining operations — must be instances of these safe types, never the corresponding built-in Python types. This must hold even when a native Python list or set (injected via builtins) participates in the operation.

The maximum size for any collection is max_const_len. Any operation that causes a safe collection to grow beyond this limit, or that would construct a new safe collection exceeding this limit, must raise IterableTooLong. The size check must consider the resulting total size after the operation (e.g. current length plus number of elements being added).

Safe List

For the safe list type (interpreter._list):

  • append(item) — must raise IterableTooLong when appending would cause the list length to exceed max_const_len.
  • extend(iterable) — must raise IterableTooLong when extending would cause the resulting length to exceed max_const_len. This applies whether the argument is another safe list, a native list, or the list extending itself.
  • + (concatenation) — adding two lists (safe + native, or native + safe, in either order) must return an instance of interpreter._list.

Given a configured max_const_len of 1000: a list of exactly 1000 elements is allowed, but append or extend operations that push it above 1000 must raise IterableTooLong.

Safe Set

For the safe set type (interpreter._set):

  • add(item) — must raise IterableTooLong when adding a new element would cause the set size to exceed max_const_len.
  • update(iterable) — must raise IterableTooLong when updating would cause the resulting size to exceed max_const_len. This applies whether the argument is another safe set or a native set (or a native set literal).
  • union(iterable) — must raise IterableTooLong when the union would exceed max_const_len. When it does not exceed the limit, union must return an instance of interpreter._set.

Given a configured max_const_len of 1000: a set of exactly 1000 elements is allowed, and combining it with another 1000-element set (via update or union) exceeds the limit and must raise IterableTooLong.

  • update with a native set — when within limits, updating a safe set in place with a native set must succeed and leave the value as an instance of interpreter._set.
  • union with a native set — when within limits, must return an instance of interpreter._set.

Configuration Notes

  • max_const_len must be mutable on an existing DraconicConfig instance so that raising it (e.g. to a large value like 100000) relaxes the size constraints for subsequent evaluations by that interpreter.
  • The size checks described above are the only new behavior required; existing sandbox restrictions (such as disallowing certain constructs) remain unchanged.
