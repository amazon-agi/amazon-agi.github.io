Create the following importable modules and callables:

Module Public callable

modes/EvalfMode.py async def evalf_handler(message, response, parser) -> None
modes/ExpandMode.py async def expand_handler(message, response, parser) -> None
modes/FactorMode.py async def factor_handler(message, response, parser) -> None
modes/ApartMode.py async def apart_handler(message, response, parser) -> None
modes/SolveMode.py async def solve_handler(message, response, parser) -> None

For example, these imports must work exactly:

from modes.EvalMode import eval_handler
from modes.EvalfMode import evalf_handler
from modes.ExpandMode import expand_handler
from modes.FactorMode import factor_handler
from modes.ApartMode import apart_handler
from modes.SolveMode import solve_handler

Every handler must be awaitable, including when invoked through asyncio.run(...). A handler does not return its computed value; after publishing its response, it returns None.

Common Handler Contract

message

message is a dictionary containing at least:

  • "expression": the raw LaTeX/expression string to process.
  • "environment": an environment dictionary. An empty dictionary is valid.

For solve_handler, message may additionally contain:

  • "symbols": an ordered list of variable-name strings selecting the symbols for which to solve. This field is at the top level of message, not inside environment.
parser

parser is an instance of grammar.ObsimatLatexParser.ObsimatLatexParser. Handlers must use it to parse message["expression"] in the supplied environment. Existing parser capabilities must remain compatible with the handlers.

Publishing through response

The response publication interface is asynchronous. It has this method contract:

async def result(self, result, status="success", metadata={})

Every successfully computed handler value must be published by awaiting this method:

await response.result(value, status="success", metadata=metadata)

The handler passes the computed value itself as the first argument; it must not pre-wrap that value in another {"result": ...} dictionary. For a response implementation that records results, publication makes response.hasResult() true and response.getResult() exposes the envelope:

{
    "result": value,
    "status": "success",
    "metadata": metadata,
}

When no source-location metadata applies, metadata is an empty dictionary. The result-recording coroutine above is the result publication mechanism.

Source-location metadata

eval_handler must attach source-location metadata when it selects the final expression from a multi-expression derivation. The metadata must identify that selected expression's span in the original raw input:

{
    "start_line": <1-based first line>,
    "end_line": <1-based last line>,
}

Line numbers are one-based and are counted in the unmodified input string, including leading blank lines. For a derivation whose final &= 4 + 4 step occurs on line 4, both start_line and end_line are 4.

Environment Handling

The environment may contain:

  • "variables": a mapping from variable-name strings to definition strings. Definitions use the same accepted LaTeX/expression syntax and are substituted while parsing the target expression.
  • "domain": a string representing a SymPy solution domain, such as "Interval.Ropen(0, 2 * pi)". This setting is used by solve_handler.

Variable definitions may:

  • Reference other variables.
  • Resolve to scalars or matrices.
  • Use Greek names such as \alpha.
  • Use subscripted names such as val_{sub}, val_2, and val_{three}.

The complete environment must be supplied to the parser so existing environment-supported symbol assumptions and substitutions continue to work. An empty environment means no substitutions and no explicitly supplied solve domain.

Accepted Expression Forms and Selection Rules

Handlers must work with the existing parser's supported syntax, including:

  • Arithmetic such as 1+1.
  • Escaped LaTeX spaces, such as 1\ + \ 1.
  • Leading/trailing whitespace and expressions spread over multiple lines.
  • Explicit and implicit multiplication, including \cdot and forms such as 10x^2.
  • Functions and operators such as \sin, \sqrt, ^, and \frac{...}{...}.
  • Matrices written with \begin{bmatrix}...\end{bmatrix}, including scalar multiplication.
  • Matrix/vector norms written with \Vert ... \Vert.
  • Inner products written with \langle ... | ... \rangle or \langle ... , ... \rangle.
  • The gradient operator \nabla applied to a scalar expression. Its result is a row matrix whose columns follow the parser's deterministic symbol order.
  • Relations, chained relations, and multi-expression \begin{cases}...\end{cases} or \begin{align}...\end{align} blocks using ordinary = or aligned &= forms.

For evaluation and the expression-transformation modes, a relation or derivation is reduced to its bottommost/rightmost evaluable expression:

  1. In a multi-expression block, select its final expression.
  2. In a relation, select the right-hand side.
  3. Continue through a relation chain until the final right-hand side is reached.

Consequently:

  • 5 + 5 + 5 + 5 = 10 + 10 operates on 10 + 10.
  • a = b = (a - b)^2 operates on (a - b)^2.
  • 1 = 2 = 1 operates on 1.
  • A cases derivation ending in &= 4 + 4 operates on 4 + 4.

Solving a system is different: solve_handler retains and solves all equations in an align or cases system rather than discarding all but the last equation.

Result-Shape Conventions

The outer value returned by response.getResult() is always the response envelope described above. This section defines the shape of that envelope's "result" value.

An equation-like value is an object exposing .rhs; consumers retrieve the transformed/computed expression through that attribute.

For eval_handler:

  • Scalar results are published directly. This includes ordinary scalar arithmetic, scalar substitutions, norms, inner products, and scalar expressions selected from relation chains.
  • Every matrix- or vector-valued result is published as an equation-like value whose .rhs is the computed SymPy Matrix. This applies even when there are no environment substitutions, such as direct scalar-times-matrix input.
  • A gradient is matrix-valued and therefore uses the same equation-like .rhs form.

For evalf_handler, expand_handler, factor_handler, and apart_handler, the published "result" value is equation-like and the operation's output is in .rhs.

For solve_handler, the published "result" value is an object with .solution and .symbols attributes; it is not a plain dictionary.

Handler Requirements

1. eval_handler

Parse the expression in its environment, apply the common relation/derivation selection rule, and evaluate the selected expression to its computed or simplified SymPy value.

Required examples and edge cases:

  • 1+1 produces the direct scalar value 2.
  • 1\ + \ 1 also produces the direct scalar value 2.
  • 2 \cdot \begin{bmatrix}1 \\ 1\end{bmatrix} produces an equation-like value with .rhs == Matrix([[2], [2]]). The same result shape is required when the input is spread over several lines.
  • The norm of the column matrix (20, 30, 40, 50) produces the direct scalar value sqrt(20**2 + 30**2 + 40**2 + 50**2).
  • The inner product of column vectors (1, 2) and (2, 4) produces the direct scalar value 1*2 + 2*4.
  • 5 + 5 + 5 + 5 = 10 + 10 produces the direct value 20.
  • 1 = 2 = 1 produces the direct value 1.
  • a = b = (a - b)^2 produces the direct symbolic expression (a - b)**2. It must remain in that unexpanded form rather than becoming an equality or an expanded polynomial.
  • A derivation ending in 4 + 4 produces direct value 8 and publishes the final step's line span in metadata.

Environment substitution examples:

  • a + b with a = "2" and b = "3" produces 5.

  • \alpha with a variable definition keyed by "\\alpha" resolves to that definition's value.

  • A^T B with column-matrix definitions for A and B produces an equation-like value whose .rhs is the resulting matrix; for A = (1, 2)^T and B = (3, 4)^T, .rhs == Matrix([11]).

    .rhs == Matrix([[y*(2*x + y), x*(2*y + x)]])
2. evalf_handler

Numerically evaluate the selected expression to a floating-point value. Publish an equation-like result whose .rhs is that numerical value.

Example:

5/2  ->  result.rhs == 2.5
3. expand_handler

Algebraically expand the selected expression. Publish an equation-like result whose .rhs is the expanded SymPy expression.

Example:

(a + b)^2  ->  result.rhs == a**2 + 2*a*b + b**2
4. factor_handler

Factor the selected expression. Publish an equation-like result whose .rhs is the factored SymPy expression.

Example:

x^3 - 10x^2 + 3x + 54  ->  result.rhs == (x - 9)*(x - 3)*(x + 2)
5. apart_handler

Perform partial-fraction decomposition on the selected expression. Publish an equation-like result whose .rhs is the decomposed SymPy expression.

Example:

\frac{8x + 7}{x^2 + x - 2}  ->  result.rhs == 3/(x + 2) + 5/(x - 1)
6. solve_handler

Solve an equation or system of equations for its unknown symbols. The result value must expose:

  • .solution: the SymPy solution set.
  • .symbols: the ordered list of SymPy symbols for which the solution was computed.

For a single equation and symbol, use the domain represented by environment["domain"] when supplied. For example:

expression: \sin(x) = 0
domain:     Interval.Ropen(0, 2 * pi)

produces:

result.symbols == [x]
result.solution == FiniteSet(0, pi)

  • A determined three-equation linear system may produce FiniteSet((15, -6, -4)), with tuple entries corresponding to the order in .symbols.

  1. Resolve exactly those variable names to the corresponding SymPy symbols.
  2. Solve for exactly that selected subset.
  3. Preserve the supplied list order in result.symbols.
  4. Order every solution tuple consistently with result.symbols.

For example:

Unit-named symbols correspond to their counterparts in sympy.physics.units, including kg -> kilogram, m -> meter, s -> second, J -> joule, km -> kilometer, h -> hour, and newton -> newton.

Scope

  • Inline scalar expression, e.g. \mathbf{H}(y x^5 + \sin(y)): The differentiation variables are the free symbols appearing in the expression. The resulting Hessian is a square matrix whose entry (i, j) is ∂²/∂vᵢ∂vⱼ of the expression.

    Example: for y·x⁵ + sin(y), the result equals

    [[ 20·x³·y ,  5·x⁴   ],
 [ 5·x⁴    , -sin(y) ]]

  • Named function reference, e.g. \mathbf{H}(f): The differentiation variables and their order are taken from the function's "args" list; the body is the function's "expr". The Hessian is a square matrix of size len(args) × len(args), with rows/columns ordered exactly as "args". Arguments that do not appear in the body still contribute their corresponding rows/columns (all zero).

    Example: for f with args = ["x", "y", "z"] and body log(x) + eʸ, the result equals

    [[ -1/x² , 0  , 0 ],
 [ 0     , eʸ , 0 ],
 [ 0     , 0  , 0 ]]
Jacobian — \mathbf{J}(...)

Computes the Jacobian matrix (matrix of first-order partial derivatives) of a vector-valued expression.

  • Inline column vector, e.g. \mathbf{J}(\begin{bmatrix} x^2 \\ y \\ x * y \end{bmatrix}): The rows correspond to the components of the input vector; the columns correspond to the differentiation variables (the free symbols of the whole vector). Entry (i, j) is ∂(componentᵢ)/∂vⱼ.

    Example: for the vector [x², y, x·y], the result equals

    [[ 2·x , 0 ],
 [ 0   , 1 ],
 [ y   , x ]]

  • Named function reference, e.g. \mathbf{J}(f): The function's body (a column vector) supplies the components; the differentiation variables and their order are taken from the function's "args" list. The result has one row per vector component and one column per entry of "args", in "args" order. Arguments not present in any component contribute all-zero columns.

    Example: for f with args = ["x", "y", "z"] and body the column vector [log(x), sin(y), cos(x)·sin(y)], the result equals

    [[ 1/x           , 0             , 0 ],
 [ 0             , cos(y)        , 0 ],
 [ -sin(x)·sin(y), cos(x)·cos(y) , 0 ]]

Function Definition / Argument Tracking

The core change: a user-defined function must retain its declared formal argument list ("args") as an ordered, function-bound property. This ordered argument set is what the Hessian and Jacobian operators use to determine matrix dimensions and the ordering of rows/columns when the operator is applied to a named function. This must hold even when some declared arguments do not appear in the function body (they still occupy their positions, producing zero rows/columns).

Expressions consisting of a chain of =-separated values, e.g.:
