Task Specification: Supporting Greek Symbols as Variables in Expression Evaluation

Goal

The goal is to extend the expression evaluation functionality so that Greek symbols (e.g., LaTeX-style \alpha) can serve as variable names and are correctly resolved to their assigned values during evaluation.

Public API

It must be possible to import and call the following async function:

  • Module: the module that currently provides the evaluate functionality (importable as evaluateMode).
  • Function signature:
    async def evaluateMode(request: dict, response, parser)

In this signature:

  • request is a dict that describes the expression to evaluate and its environment (the structure is detailed below).
  • response is a response object that supports the methods described below.
  • parser is a parser instance provided by the caller.

Structure of the Request

The request dict takes the following shape:

{
    "expression": <str>,          # the expression to evaluate, in LaTeX form
    "environment": {
        "variables": {
            <variable_name>: <value_string>,
            ...
        }
    }
}
  • expression is a LaTeX-formatted string that may reference variables, Greek-symbol variables such as \alpha among them.
  • environment.variables associates variable names (as LaTeX strings) with their values (given as strings). Variable names may be Greek symbols written in LaTeX form, for example the key "\\alpha" (the string \alpha).

Behavior Requirements

When evaluateMode is invoked with an expression that consists of (or references) a Greek symbol whose name appears as a key in environment.variables, the evaluation must substitute the value of that variable and compute the result.

In particular, evaluating the expression \alpha with the variable mapping {"\alpha": "2"} must produce a numeric result of 2.

Greek-symbol variable names must therefore be matched consistently between how they appear in the expression and how they appear as keys in the variables mapping, so that the assigned value is bound correctly and used in the computation.

Response Object

Once an evaluation has succeeded, the response object must reflect the result:

  • When a result is available, response.hasResult() returns True.
  • response.getResult() returns a dict that contains a 'result' key whose value is the computed result (e.g., 2 for the case above).
  • response.reset() clears any result that was stored previously so that the same object can be reused for subsequent evaluations.

Notes

  • Evaluation behavior that already exists for non-Greek variables and other expressions must continue to work unchanged.
  • Values in the variables mapping are given as strings and must be interpreted as their numeric/symbolic equivalents during evaluation.

Task Specification: Mode Handlers for Expression Evaluation

Summary

Six asynchronous mode handlers are to be implemented in the modes package. Each handler is given a LaTeX mathematical expression, parses it using the provided ObsimatLatexParser, carries out a particular SymPy operation, and publishes the resulting value through the provided response object.

The required handlers are: evaluation, numerical evaluation, expansion, factorization, partial-fraction decomposition, and equation/system solving. They must integrate with the repository's existing parser, and the parser's existing parsing behavior must be preserved.

Public API of the Handlers

Create the following modules and callables so that they can be imported:

Module Publicly exposed callable
modes/EvalMode.py async def eval_handler(message, response, parser) -> None
modes/EvalfMode.py async def evalf_handler(message, response, parser) -> None
modes/ExpandMode.py async def expand_handler(message, response, parser) -> None
modes/FactorMode.py async def factor_handler(message, response, parser) -> None
modes/ApartMode.py async def apart_handler(message, response, parser) -> None
modes/SolveMode.py async def solve_handler(message, response, parser) -> None

As an example, the imports below must work exactly:

from modes.EvalMode import eval_handler
from modes.EvalfMode import evalf_handler
from modes.ExpandMode import expand_handler
from modes.FactorMode import factor_handler
from modes.ApartMode import apart_handler
from modes.SolveMode import solve_handler

Every handler must be awaitable, including when it is invoked through asyncio.run(...). A handler does not return the value it computes; after it has published its response, it returns None.

Contract Shared by All Handlers

message

message is a dictionary that contains at least the following:

  • "expression": the raw LaTeX/expression string that is to be processed.
  • "environment": a dictionary holding the environment. An empty dictionary is valid.

For solve_handler, message may in addition contain:

  • "symbols": an ordered list of variable-name strings that selects the symbols to solve for. This field is located at the top level of message, not inside environment.
parser

parser is an instance of grammar.ObsimatLatexParser.ObsimatLatexParser. Handlers must use it to parse message["expression"] within the environment that is supplied. The parser's existing capabilities must remain compatible with the handlers.

Publication via response

The interface for publishing responses is asynchronous. Its method contract is:

async def result(self, result, status="success", metadata={})

Every handler value that is computed successfully must be published by awaiting this method:

await response.result(value, status="success", metadata=metadata)

The handler passes the computed value itself as the first argument; the handler must not pre-wrap that value in another {"result": ...} dictionary. For a response implementation that records results, publication makes response.hasResult() true, and response.getResult() exposes the envelope:

{
    "result": value,
    "status": "success",
    "metadata": metadata,
}

Whenever no source-location metadata applies, metadata is an empty dictionary. The coroutine above, which records results, is the mechanism for publishing results.

Metadata for Source Locations

eval_handler must attach source-location metadata whenever it selects the final expression out of a multi-expression derivation. The metadata must identify the span that the selected expression occupies in the original raw input:

{
    "start_line": <1-based first line>,
    "end_line": <1-based last line>,
}

Line numbers are one-based and are counted in the input string in its unmodified form, with leading blank lines included. For a derivation whose final &= 4 + 4 step occurs on line 4, both start_line and end_line are 4.

How the Environment Is Handled

The environment may contain the following:

  • "variables": a mapping whose keys are variable-name strings and whose values are definition strings. Definitions are written in the same accepted LaTeX/expression syntax and are substituted while the target expression is parsed.
  • "domain": a string representing a SymPy solution domain, such as "Interval.Ropen(0, 2 * pi)". solve_handler makes use of this setting.

Variable definitions may:

  • Refer to other variables.
  • Resolve to scalars or matrices.
  • Employ Greek names such as \alpha.
  • Employ subscripted names such as val_{sub}, val_2, and val_{three}.

The parser must be given the complete environment, so that the symbol assumptions and substitutions already supported through the environment continue to work. An empty environment means there are no substitutions and no explicitly supplied solve domain.

Accepted Expression Forms and Rules for Selecting the Expression

Handlers must work with the syntax supported by the existing parser, including:

  • Arithmetic, such as 1+1.
  • Escaped LaTeX spaces, such as 1\ + \ 1.
  • Leading/trailing whitespace, and expressions spread out over multiple lines.
  • Explicit and implicit multiplication, including \cdot and forms like 10x^2.
  • Functions and operators like \sin, \sqrt, ^, and \frac{...}{...}.
  • Matrices written using \begin{bmatrix}...\end{bmatrix}, including scalar multiplication.
  • Matrix/vector norms written using \Vert ... \Vert.
  • Inner products written using \langle ... | ... \rangle or \langle ... , ... \rangle.
  • Application of the gradient operator \nabla to a scalar expression. The result is a row matrix whose columns follow the parser's deterministic symbol order.
  • Relations, chains of relations, and multi-expression \begin{cases}...\end{cases} or \begin{align}...\end{align} blocks that use ordinary = or the aligned &= form.

For evaluation and for the modes that transform expressions, a relation or derivation is reduced to its bottommost/rightmost evaluable expression:

  1. In a multi-expression block, take its final expression.
  2. In a relation, take the right-hand side.
  3. Keep moving through a relation chain until the final right-hand side is reached.

As a consequence:

  • With 5 + 5 + 5 + 5 = 10 + 10, the handler operates on 10 + 10.
  • With a = b = (a - b)^2, the handler operates on (a - b)^2.
  • With 1 = 2 = 1, the handler operates on 1.
  • For a cases derivation ending in &= 4 + 4, the handler operates on 4 + 4.

Solving a system behaves differently: solve_handler retains all equations of an align or cases system and solves them, rather than discarding all but the last equation.

Conventions for Result Shapes

What response.getResult() returns as the outer value is always the response envelope described above. The shape of that envelope's "result" value is defined in this section.

An equation-like value is an object that exposes .rhs; consumers retrieve the transformed/computed expression through that attribute.

For eval_handler:

  • Scalar results are published directly. Ordinary scalar arithmetic, scalar substitutions, norms, inner products, and scalar expressions picked from relation chains all fall under this.
  • Every result that is matrix- or vector-valued is published as an equation-like value whose .rhs is the computed SymPy Matrix. This applies even when the environment contains no substitutions, for instance direct scalar-times-matrix input.
  • A gradient is matrix-valued, and therefore takes the same equation-like .rhs form.

For evalf_handler, expand_handler, factor_handler, and apart_handler, the published "result" value is equation-like, and the operation's output is in .rhs.

For solve_handler, the published "result" value is an object carrying .solution and .symbols attributes; it is not a plain dictionary.

Requirements per Handler

1. eval_handler

Parse the expression within its environment, apply the common relation/derivation selection rule, and evaluate the selected expression to its computed or simplified SymPy value.

The following examples and edge cases are required:

  • 1+1 produces the direct scalar value 2.
  • 1\ + \ 1 likewise produces the direct scalar value 2.
  • 2 \cdot \begin{bmatrix}1 \\ 1\end{bmatrix} produces an equation-like value with .rhs == Matrix([[2], [2]]). When the input is spread over several lines, the same result shape is required.
  • The norm of the column matrix (20, 30, 40, 50) produces the direct scalar value sqrt(20**2 + 30**2 + 40**2 + 50**2).
  • The inner product of the column vectors (1, 2) and (2, 4) produces the direct scalar value 1*2 + 2*4.
  • 5 + 5 + 5 + 5 = 10 + 10 produces the direct value 20.
  • 1 = 2 = 1 produces the direct value 1.
  • a = b = (a - b)^2 produces the direct symbolic expression (a - b)**2. It must stay in that unexpanded form, rather than turning into an equality or an expanded polynomial.
  • A derivation ending in 4 + 4 produces the direct value 8 and publishes the line span of the final step in the metadata.

Examples of environment substitution:

  • With a = "2" and b = "3", a + b produces 5.

  • \alpha with a variable definition keyed by "\\alpha" resolves to the value of that definition.

  • A^T B with column-matrix definitions for A and B produces an equation-like value whose .rhs is the matrix that results; with A = (1, 2)^T and B = (3, 4)^T, .rhs == Matrix([11]).

  • With abc = "1", \sin{abc} produces the direct scalar value sin(1).

  • With val_{sub} = "7", val_2 = "3", and val_{three} = "2", \sqrt{val_{sub} + val_2^val_{three}} produces 4.

  • \nabla (x^2 y + y^2 x) produces an equation-like value with:

    .rhs == Matrix([[y*(2*x + y), x*(2*y + x)]])
2. evalf_handler

Evaluate the selected expression numerically to a floating-point value. Publish an equation-like result whose .rhs holds that numerical value.

Example:

5/2  ->  result.rhs == 2.5
3. expand_handler

Expand the selected expression algebraically. Publish an equation-like result whose .rhs holds the expanded SymPy expression.

Example:

(a + b)^2  ->  result.rhs == a**2 + 2*a*b + b**2
4. factor_handler

Factor the selected expression. Publish an equation-like result whose .rhs holds the factored SymPy expression.

Example:

x^3 - 10x^2 + 3x + 54  ->  result.rhs == (x - 9)*(x - 3)*(x + 2)
5. apart_handler

Perform partial-fraction decomposition on the selected expression. Publish an equation-like result whose .rhs holds the decomposed SymPy expression.

Example:

\frac{8x + 7}{x^2 + x - 2}  ->  result.rhs == 3/(x + 2) + 5/(x - 1)
6. solve_handler

Solve an equation, or a system of equations, for its unknown symbols. The result value must expose:

  • .solution: the SymPy solution set.
  • .symbols: the ordered list of SymPy symbols for which the solution was computed.

For a single equation and symbol, use the domain represented by environment["domain"] when one is supplied. For example:

expression: \sin(x) = 0
domain:     Interval.Ropen(0, 2 * pi)

this produces:

result.symbols == [x]
result.solution == FiniteSet(0, pi)

A system may be supplied as an align or cases block. Required behavior includes:

  • A determined linear system of three equations may produce FiniteSet((15, -6, -4)), with the tuple entries corresponding to the order in .symbols.
  • The nonlinear system 3*x^2 = 2*y and y = Rational(3, 2)*x produces FiniteSet((0, 0), (1, Rational(3, 2))) when it is solved for [x, y].
  • Underdetermined systems may return tuples that are parameterized by symbols not selected for solving.

If message["symbols"] is present, then solve_handler must:

  1. Resolve exactly those variable names to the corresponding SymPy symbols.
  2. Solve for exactly that selected subset.
  3. Preserve the order of the supplied list in result.symbols.
  4. Order every solution tuple consistently with result.symbols.

For this system:

\begin{cases}
x + y = z \\n x - y = -z \\n\end{cases}

the following selected-symbol outcomes are required:

  • With "symbols": ["x", "y"], the required outcome is .symbols == [x, y] and .solution == FiniteSet((0, z)).
  • With "symbols": ["y", "z"], the required outcome is .symbols == [y, z] and .solution == EmptySet.

When message["symbols"] is absent, the handler determines the unknown symbols of the equation in deterministic symbol-name order and reports that solve order in .symbols; any tuple-valued solutions must follow that same order.

Criteria for Completion

Every one of the six callables must exist at its specified import path, obey the asynchronous response protocol, parse expressions in the supplied environment, preserve the required direct-value versus equation-like result shapes, attach final-expression source metadata when applicable, and provide ordered attribute-based solve results.

Task Specification: Refactoring of the Unit System and Unit Conversion

Overview

Your working context is the Python package (sympy-client), which takes mathematical expressions written in LaTeX and processes them by means of SymPy. Two changes, related to each other, make up this task:

  1. Renaming of the existing mode handler functions so that they follow a new naming convention.
  2. Implementation of automatic unit simplification during expression evaluation, together with an explicit command for converting units.

The existing evaluation behavior for cases without units must remain compatible.

Package Structure and Importability

The following modules and public functions must be present and importable:

  • A function named convert_sympy_handler must be exposed by modes.ConvertSympyMode.
  • A function named eval_handler must be exposed by modes.EvalMode.
  • A function named convert_units_handler must be exposed by modes.ConvertUnitsMode.

grammar.ObsimatLatexParser.ObsimatLatexParser supplies the LaTeX parser; this parser is instantiated with no arguments.

Handler Signatures and How They Are Called

Each of the three handler functions is an asynchronous coroutine, and all of them share the same signature:

async def <handler>(message: dict, response, parser) -> None
  • message: a dictionary holding the request data, described below for each handler.
  • response is a response object; results get reported through it. It supports:
    • response.hasResult(), which indicates whether a result has been set.
    • response.getResult(), whose return value is the result payload dictionary.
  • parser — an ObsimatLatexParser instance, which parses the LaTeX expression string into a SymPy expression.

Each handler, when it succeeds, must set a result on response. A "result" key is present in the result payload. Which type and shape that value has is determined by the handler and, for evaluation, by whether the parsed expression was changed by evaluation.

convert_sympy_handler

What the request message contains:

  • "expression": a string of LaTeX.
  • "environment": a dictionary; it may be empty.

Parsing of the expression happens with the environment that was supplied, and the SymPy expression that results is published directly as payload["result"] by the handler. An Eq must not be used to wrap that expression.

As an example, converting a + b results in the SymPy expression a + b directly:

payload["result"] == a + b

What this preserves is the behavior of the prior convert-SymPy mode; the only change is the public handler name, which goes from convertSympyMode to convert_sympy_handler.

eval_handler - Evaluation Together with Simplification of Units

Inside the request message:

  • "expression": a string of LaTeX.
  • "environment": a dictionary that may contain the following:
    • "units_enabled" (bool): when this is True, symbols in the expression whose names are SI units — such as kg, m, s, and J — are interpreted as physical units from sympy.physics.units, and the expression that results is then simplified to the most compact unit representation.
    • "excluded_symbols" (list of strings): names that must not be interpreted as units, even when units_enabled is True; these names remain ordinary SymPy symbols.
The Existing Evaluation Behavior and the Shape of Results

The handler's existing evaluation behavior is retained. To be specific: handed a derivation with multiple expressions, it evaluates the last expression; and when the expression selected is a relation, its right-hand side is what evaluation uses.

Immediately after parsing, yet before unit substitution and evaluation, the expression that has been selected is the pre-evaluation expression. After that expression has been evaluated:

  • Should the evaluated expression turn out to be equal to the pre-evaluation expression, payload["result"] must hold the evaluated SymPy value directly, not an Eq.
  • If instead the evaluated expression differs from the pre-evaluation expression, payload["result"] must be an unevaluated before-and-after Eq; in it, .lhs is the pre-evaluation expression and .rhs is the evaluated expression.

Stated differently: only when evaluation changes the selected parsed expression does the result come out with an equation shape. Parsing 1+1, for instance, already gives 2, so the evaluation result is the direct value 2. Direct values likewise remain in place for scalar norms, inner products, outcomes of scalar relation chains, and other scalar expressions that are already in their evaluated form. When a transformation changes a matrix or a vector expression, the outcome is an Eq whose .rhs holds the matrix or vector that was computed. Turning unit interpretation on normally changes unit-named symbols into physical unit objects; as a consequence, the .rhs of the Eq object that results is where the transformed result is available.

Source Metadata for Multi-line Derivations

If eval_handler picks the last expression out of a multi-line derivation, that expression's 1-based source location must be preserved by the "metadata" dictionary of the result payload, in this form:

{
    "start_line": <first line of the selected expression>,
    "end_line": <last line of the selected expression>
}

Should the selected expression be contained entirely on line 4, both of the values are 4. This metadata is required no matter whether the "result" value is direct or equation-shaped.

Simplifying Units when units_enabled is True

The evaluated expression must be reduced to its simplest equivalent form, expressed with physical units; whichever representation uses the fewest total unit factors or powers is the one that must be chosen:

  • An expression that is equivalent to a single named derived unit must collapse into that derived unit.
    • Example: kg * m / s^2 -> newton.
  • Whenever an expression is simplest in base units, it must be expressed in base units.
    • Example: J / m * s^2 -> kilogram * meter.
  • If the expression is a sum, each term undergoes simplification independently, and the resulting terms are then added together.
    • Example: J / m * s^2 + kg * m / s^2 -> kilogram * meter + newton.
  • While the unit part of its term still gets simplified, a symbol named in "excluded_symbols" remains an ordinary algebraic symbol.
    • Example: J * kg * m / s^2 -> J * newton when J has been excluded; the J here is a symbol, not the joule unit.

convert_units_handler - Explicit Conversion of Units

Fields appearing in the request message:

  • "expression": a LaTeX string denoting a quantity that has units.
  • "target_units": a list of strings naming units; the expression must be converted into them.
  • "environment": a dictionary that may be empty.

After the handler parses the expression, it interprets unit-named symbols as physical units and converts the quantity into the target units that were requested. In an explicit conversion, the source's unit names are interpreted even when the environment is empty; units_enabled is not required by it.

Upon success, payload["result"] must be a SymPy Eq. The converted expression, written in the requested target units, is what the equation's .rhs contains.

Here is an example:

7.2 * km / h converted to ["m", "s"] -> 2.0 * meter / second

Names of Units and Numeric Coefficients

A symbol whose name is that of a unit has a counterpart in sympy.physics.units with which it corresponds; the correspondences include kg -> kilogram, m -> meter, s -> second, J -> joule, km -> kilometer, h -> hour, and newton -> newton.

In the input, units are combined with numeric coefficients in the manner of ordinary scalar multipliers. Exact numeric coefficients must be produced by conversions; 7.2 km/h, for instance, turns into 2.0 m/s.

Scope

No particular internal algorithm for unit search or for conversion is required. The public contracts are: the handlers that can be imported, the fields of their requests, the shapes of results in responses, the source metadata, and the mathematical results described above.
