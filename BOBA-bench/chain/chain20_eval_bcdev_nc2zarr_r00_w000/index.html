Task: Implement a Command-Line Tool for Converting NetCDF Files to a Zarr Dataset

Overview

Implement a command-line interface (CLI) that reads one or more NetCDF (.nc) input files and combines them into a single Zarr dataset on disk.

Public API

Create a module nc2zarr.cli that exposes a Click-based command named main.

from nc2zarr.cli import main

main must be a click.Command (e.g. defined with the @click.command() decorator) so that it can be invoked directly by a click.testing.CliRunner.

CLI Interface

Arguments
  • A positional input argument that accepts a file path or glob pattern (e.g. /some/dir/*.nc) identifying the NetCDF files to convert.
Options

  • --mode <mode>: Selects the conversion strategy. The following values must be accepted:

    • slices — process the matched input files and append/concatenate them along the time dimension.
    • one_go — process all matched input files together in a single operation.

    Both modes must produce the same resulting dataset (see "Behavior" below). If --mode is not supplied, the tool must behave as if slices was chosen (i.e. it must run successfully and produce the same result as one_go).

  • --version: Prints version information and exits with code 0.

  • --help: Prints usage/help information and exits with code 0. (This is provided automatically by Click.)

Behavior

No arguments

When main is invoked with no arguments at all, it must exit with a non-zero exit code (specifically 1). No conversion is attempted.

Version / Help
  • Invoking with --version exits with code 0.
  • Invoking with --help exits with code 0.
Conversion

When invoked with an input path/glob (with or without --mode):

  1. Expand the input argument as a glob pattern to discover all matching NetCDF files.
  2. Open each NetCDF file and combine them into a single dataset, concatenating along the time dimension.
  3. Write the combined dataset to a Zarr store at the path out.zarr in the current working directory. This path must be a directory (a standard Zarr on-disk store).
  4. Exit with code 0 on success.

The output directory out.zarr must be created relative to the current working directory (i.e. the literal name out.zarr).

Resulting Dataset Requirements

Given input NetCDF files that each contain:

  • Data variables chl_1, chl_2, chl_3, each with dimensions (time, lat, lon).
  • Coordinate variables lon (dim lon), lat (dim lat), and time (dim time), where each input file holds a single time step.

The Zarr output produced by the tool, when reopened with xarray.open_zarr('out.zarr'), must satisfy:

  • Its set of variables is exactly {'lon', 'lat', 'time', 'chl_1', 'chl_2', 'chl_3'}.
  • The time coordinate contains all time steps from all input files, concatenated in chronological order, with one entry per input file (e.g. 5 input files, each with a distinct daily timestamp, yield a time coordinate of length 5 in ascending date order).
  • The time values match the original timestamps from the input files exactly (as datetime64 values).

Both --mode slices and --mode one_go (and the default when --mode is omitted) must produce an output dataset satisfying all of the above identically.

Dependencies

The implementation relies on click, xarray, and numpy (and an appropriate NetCDF/Zarr backend such as netcdf4/zarr).

Notes

  • The tool overwrites/creates out.zarr fresh on each run (the test harness deletes it before and after each invocation, so no special handling for a pre-existing store is required).

Objective

Implement a command-line tool that converts one or more NetCDF (.nc) input files into one combined Zarr dataset directory.

Public API

nc2zarr must be a Click-based command and must be directly invocable with click.testing.CliRunner().invoke(nc2zarr, args). Its command-line name is nc2zarr.

Command Interface

A normal conversion has the following form:

nc2zarr [--multi-file] INPUT_PATTERN
Positional input

The command accepts one positional argument identifying the input NetCDF files. The argument may be a glob-style pattern, such as /some/dir/*.nc, and the command must expand it to one or more matching .nc files.

Options
  • --multi-file is a boolean flag and takes no value. It selects the multi-file conversion mode described below. Without this flag, the command uses its default slice/append mode.
  • --version displays version information and exits successfully without requiring positional input.
  • --help displays command usage/help and exits successfully without requiring positional input.

Output Location and Format

A successful conversion writes a Zarr dataset to a directory named out.zarr in the current working directory. The directory must exist after the command completes and the dataset must be readable with xarray.open_zarr('out.zarr').

Conversion Behavior

Each matched NetCDF file contains a dataset with a time coordinate. The command must combine all matched inputs by concatenating their time slices along the time dimension, preserving chronological order and the associated data.

For inputs containing longitude, latitude, and time coordinates together with the three chlorophyll variables, the reopened Zarr dataset must contain exactly the following xarray variables:

lon
lat
time
chl_1
chl_2
chl_3

In other words, its complete variable-name set must be exactly {'lon', 'lat', 'time', 'chl_1', 'chl_2', 'chl_3'}: lon, lat, and time are the coordinate variables, and chl_1, chl_2, and chl_3 are the data variables. No additional xarray variables may be introduced into this output. The values of all three data variables must remain associated with their corresponding time slices.

For example, given five input files whose time coordinates represent December 1 through December 5, 2020 at 10:00:00, the output must have five time entries, in this order, as datetime64 values:

2020-12-01T10:00:00
2020-12-02T10:00:00
2020-12-03T10:00:00
2020-12-04T10:00:00
2020-12-05T10:00:00
Conversion Modes
  • Default mode: With no mode flag, process the inputs as individual slices and append them to form the combined dataset.
  • Multi-file mode: With --multi-file, open/process the matched inputs together and write the combined dataset.

Both modes must produce an observably equivalent out.zarr: the same complete variable set, coordinate values, chronological time sequence, and data values.

Example invocations are:

nc2zarr '/some/dir/*.nc'
nc2zarr --multi-file '/some/dir/*.nc'

Exit and No-Conversion Behavior

  • A successful conversion must exit with status code 0 and must not raise an uncaught exception.
  • Invoking nc2zarr with no arguments at all—no positional input and no conversion-triggering option—must perform no conversion, must not create out.zarr, and must exit with status code 1.
  • Invoking nc2zarr --help must display help, perform no conversion, and exit with status code 0.
  • Invoking nc2zarr --version must display version information, perform no conversion, must not create out.zarr, and must exit with status code 0.

Dependencies

The command relies on Click for its public command interface and on xarray with Zarr support and numpy for reading, combining, writing, and validating the dataset values.

lon:    chunks (36,)   # None -> full length

1.3 File merge rules

Read and merge configuration files in the order supplied by config_paths, from left to right. Later files have higher precedence than earlier files, subject to the special input.paths rule below.

  1. If both the existing and incoming values at a key are dictionaries, merge them recursively. This applies at every dictionary nesting level, including but not limited to input, process, output, and nested objects such as output.s3.
  2. If values are not both dictionaries, the incoming value normally replaces the existing value.
  3. Lists are normally replaced as complete values; they are not concatenated or merged element by element.
  4. The sole list exception is input.paths during file-to-file merging. Whenever successive configuration files each provide a list at input.paths, concatenate those lists in configuration-file order. Retain all entries in that order; do not replace the earlier list and do not deduplicate it. This exception applies to lists supplied by configuration files, not to the final keyword-override layer.

After all files have been merged, merge the supplied keyword values on top of that result. Keyword values always take precedence at their mapped keys, including false-like values. In particular, an explicitly supplied input_paths value replaces the file-derived input.paths value; it is not appended to it. Unrelated file-derived keys remain in place through the same recursive dictionary merge behavior.

Task Specification: nc2zarr Public APIs and Dataset Rechunking

Overview

Provide the public nc2zarr conversion APIs for opening NetCDF or Zarr inputs, preprocessing and processing xarray.Dataset objects, loading and merging configuration, running conversions from Python and from the command line, and writing Zarr output. The central processing contract is a DatasetProcessor that applies variable renaming, rechunking rules, and output-encoding overrides and returns a dataset together with the encoding to use for output.

The package-level behaviors below are compatibility requirements. Public errors identified as ConverterError use nc2zarr.error.ConverterError.

1. Dataset processing

Public API

The class must be importable from nc2zarr.processor and support:

DatasetProcessor(
    process_rename=<dict>,
    process_rechunk=<dict>,
    output_encoding=<dict>,
)

All three arguments are optional and are supplied as keyword arguments.

  • process_rename maps existing variable names to replacement names.
  • process_rechunk describes rechunking rules as specified below.
  • output_encoding contains per-variable output-encoding overrides.

The method

process_dataset(dataset) -> (new_dataset, new_encoding)

accepts an xarray.Dataset and returns a 2-tuple:

  • new_dataset is the renamed and/or processed dataset.
  • new_encoding is a dictionary of output encodings keyed by variable name.
Variable renaming

When process_rename is non-empty, rename the named variables according to that mapping. For example, {'r_f32': 'bibo'} produces a dataset containing bibo and no longer containing r_f32. Renaming is applied before any rechunking or output-encoding resolution, so subsequent variable names refer to the resulting dataset.

If renaming is the only requested operation, new_encoding is {}.

Rechunking rule format

process_rechunk is a dictionary whose keys are either:

  • A variable-name selector: the wildcard '*', which applies to all variables — data variables and one-dimensional coordinate variables alike — or a specific data-variable name such as 'r_i32'. Its value is a dictionary mapping dimension names such as 'lon', 'lat', and 'time' to chunk-size specifications.
  • A dimension name such as 'lon', 'lat', or 'time' at the top level. Its value is a chunk-size specification for the corresponding coordinate variable, and it overrides any wildcard entry for that dimension when resolving that coordinate.

A chunk-size specification may be:

  • A positive integer: use that integer as the chunk size. A value larger than the current dimension extent is allowed and is not capped.
  • None: leave the dimension unchunked, represented by its full extent.
  • The string 'input': use the leading input chunk for that dimension.

Any other value is invalid (see "Invalid chunk sizes" below).

Resolving chunks for data variables

For each data variable:

  1. Begin with the dimension rules under '*', if present.
  2. Merge the rules under that variable's own name, if present; these entries override equal dimension entries from '*'.
  3. Resolve every dimension in the variable's dimension order. A dimension with no applicable rule resolves to its full extent (unchunked).
  4. Store the result as a tuple under the variable's 'chunks' encoding entry.

A variable with no matching variable selector and no wildcard rule is unchunked along its dimensions, using each full dimension extent.

Resolving chunks for coordinate variables

For each one-dimensional coordinate variable corresponding to a dimension:

  • If process_rechunk has a top-level key equal to the dimension name, resolve that integer, None, or 'input' specification for the coordinate. This top-level key takes precedence over any wildcard entry.
  • Otherwise, if the wildcard rules under '*' contain an entry for that dimension, resolve that entry for the coordinate. Wildcard dimension rules thus apply to coordinate variables as well as to data variables.
  • Otherwise, the coordinate is unchunked and its chunk size is its full extent.
  • Its 'chunks' entry is a one-element tuple.
Input chunking

For an 'input' rule, use the size of the first, leading Dask chunk already present on the input variable along the applicable dimension. Thus, if an extent is split into two halves, the resolved size is ceil(extent / 2). For example, leading chunks time=1, lat=9, and lon=18 resolve to (1, 9, 18) for a variable whose dimensions are (time, lat, lon).

If the variable carries no Dask chunking (for example, a plain in-memory variable with no chunk information), an 'input' rule must not fail: the dimension resolves to its full extent, and resolution proceeds normally. In particular, an 'input' rule applied to an unchunked variable must not mask or preempt the detection of an invalid chunk-size value elsewhere in the rules; the specified ValueError for the invalid value is still raised.

Encoding output and override merging

Whenever rechunking or output encoding is requested, new_encoding maps every data and coordinate variable in the resulting dataset to a dictionary. Each entry contains a 'chunks' tuple in that variable's dimension order.

For every dataset variable named in output_encoding, merge its supplied entries into the generated entry after chunk resolution. Supplied values such as compressor=None and fill_value=None must be retained. If an override uses the same key as a generated encoding entry, the explicit output override takes precedence.

Renaming alone is the exception: it returns an empty encoding because neither rechunking nor output encoding was requested.

Dataset identity and mutation
  • If process_rename, process_rechunk, and output_encoding are all absent or empty, return the exact input dataset object and {}.
  • If any processing is requested, return a distinct dataset object, even when resolved chunks happen to match the input.
  • Do not mutate the input dataset object.
Invalid chunk sizes

An invalid chunk-size value raises ValueError with exactly:

invalid chunk size: <value>

<value> is the offending value's standard string representation. For example, [1, 2, 3] produces invalid chunk size: [1, 2, 3].

Invalid chunk-size values present in process_rechunk are accepted without error at DatasetProcessor construction time; the ValueError is raised only when process_dataset is called and the rules are resolved.

For example, constructing a processor with

process_rechunk={'*': {'lon': [1, 2, 3], 'lat': 'input'}}

succeeds. Calling process_dataset on a dataset whose variables have dimensions (lat, lon) and no Dask chunking then raises ValueError with exactly invalid chunk size: [1, 2, 3]; the 'input' rule for lat resolves to the full extent and does not itself raise or change the reported error.

Worked rechunking examples

Assume data variables r_ui16, r_i32, and r_f32 have dimensions (time, lat, lon) with extents time=1, lat=18, and lon=36, and the dataset has coordinate variables lon, lat, and time.

Example 1: wildcard chunks apply to data and coordinate variables

For:

process_rechunk={'*': dict(lon=8, lat=4, time=1)}

return:

{
    'r_f32':  {'chunks': (1, 4, 8)},
    'r_i32':  {'chunks': (1, 4, 8)},
    'r_ui16': {'chunks': (1, 4, 8)},
    'lon':    {'chunks': (8,)},
    'lat':    {'chunks': (4,)},
    'time':   {'chunks': (1,)},
}

Because no top-level dimension-name keys are present, the wildcard sizes apply to the coordinate variables as well: lon is (8,) and lat is (4,), not the full dimension extents.

Example 2: explicit coordinate chunks override the wildcard

For:

process_rechunk={
    '*': dict(lon=8, lat=4, time=1),
    'lon': None,
    'lat': None,
    'time': 100,
}

return:

{
    'r_f32':  {'chunks': (1, 4, 8)},
    'r_i32':  {'chunks': (1, 4, 8)},
    'r_ui16': {'chunks': (1, 4, 8)},
    'lon':    {'chunks': (36,)},
    'lat':    {'chunks': (18,)},
    'time':   {'chunks': (100,)},
}
Example 3: unchunked spatial dimensions

For:

process_rechunk={
    '*': {'lon': None, 'lat': None, 'time': 1},
    'lon': None,
    'lat': None,
    'time': 128,
}

return:

{
    'r_f32':  {'chunks': (1, 18, 36)},
    'r_i32':  {'chunks': (1, 18, 36)},
    'r_ui16': {'chunks': (1, 18, 36)},
    'lon':    {'chunks': (36,)},
    'lat':    {'chunks': (18,)},
    'time':   {'chunks': (128,)},
}
Example 4: reuse leading input chunks

If leading input chunks are time=1, lat=9, and lon=18, then for:

process_rechunk={
    '*': {'lon': 'input', 'lat': 'input', 'time': 1},
    'lon': None,
    'lat': None,
    'time': 128,
}

return:

{
    'r_f32':  {'chunks': (1, 9, 18)},
    'r_i32':  {'chunks': (1, 9, 18)},
    'r_ui16': {'chunks': (1, 9, 18)},
    'lon':    {'chunks': (36,)},
    'lat':    {'chunks': (18,)},
    'time':   {'chunks': (128,)},
}
Example 5: per-variable chunks and encoding overrides

For:

process_rechunk={
    'r_i32': dict(lon=8, lat=8),
    'lon': None,
    'lat': None,
}
output_encoding={
    'r_i32': dict(compressor=None, fill_value=None),
}

return:

{
    'r_f32':  {'chunks': (1, 18, 36)},
    'r_i32':  {
        'chunks': (1, 8, 8),
        'compressor': None,
        'fill_value': None,
    },
    'r_ui16': {'chunks': (1, 18, 36)},
    'lon':    {'chunks': (36,)},
    'lat':    {'chunks': (18,)},
    'time':   {'chunks': (1,)},
}

There is no wildcard entry, so r_f32 and r_ui16 are unchunked at full extents, r_i32 combines its per-variable rules with the full extent for its unruled time dimension, and the time coordinate — with no top-level key and no wildcard — is unchunked at its full extent (1,).

Dictionary key order is not significant; equality is by content.

2. Configuration loading

Public API

The function must be importable from nc2zarr.config:

load_config(config_paths=None, return_kwargs=False, **kwargs)
  • config_paths is a single path string or a sequence of path strings referring to YAML configuration files.
  • return_kwargs selects the flattened keyword form of the result.
  • Remaining keyword arguments are the conversion parameters accepted by Converter (see section 4).
Keyword-to-configuration conversion

With no configuration paths and no keyword arguments, load_config() returns {}.

In the normal (nested) form, every keyword argument whose value is not None is placed in the result as follows:

  • Names prefixed by input_ go under a nested 'input' dictionary with the prefix removed.
  • Names prefixed by process_ go under a nested 'process' dictionary with the prefix removed.
  • Names prefixed by output_ go under a nested 'output' dictionary with the prefix removed.
  • All other names remain top-level keys.

False-valued arguments are retained; only None values are dropped. A nested section appears only if it has at least one entry. For example:

load_config(input_paths='in/*.nc',
            input_multi_file=True,
            output_path='my.zarr',
            output_overwrite=False,
            process_rename={'lons': 'lon'},
            dry_run=True,
            verbosity=2)

returns:

{
    'dry_run': True,
    'verbosity': 2,
    'input': {'paths': 'in/*.nc', 'multi_file': True},
    'process': {'rename': {'lons': 'lon'}},
    'output': {'path': 'my.zarr', 'overwrite': False},
}

With return_kwargs=True, the nested configuration keys are flattened back to their prefixed keyword names: entries of 'input', 'process', and 'output' become input_<key>, process_<key>, and output_<key> respectively, and other keys remain unchanged. The same call as above with return_kwargs=True returns:

{
    'input_paths': 'in/*.nc',
    'input_multi_file': True,
    'process_rename': {'lons': 'lon'},
    'output_path': 'my.zarr',
    'output_overwrite': False,
    'dry_run': True,
    'verbosity': 2,
}
Configuration files and merging

When config_paths is given, load each YAML file and merge the configurations in the supplied order, then merge the keyword-derived configuration last, so explicit keyword arguments take precedence over all files. Merging is recursive:

  • When both values for a key are dictionaries, merge them recursively.
  • When both values are lists, concatenate them in order (earlier sources first).
  • Otherwise, the later value replaces the earlier one.

For example, given file a.yml containing:

input:
  paths: ["a/*.nc"]
  decode_cf: true

and file b.yml containing:

input:
  paths: ["b/*.nc"]
  decode_cf: false
output:
  append: true

the call load_config(config_paths=['a.yml', 'b.yml'], input_paths=['c/*.nc'], verbosity=1) returns:

{
    'verbosity': 1,
    'input': {
        'paths': ['a/*.nc', 'b/*.nc', 'c/*.nc'],
        'decode_cf': False,
    },
    'output': {'append': True},
}

With return_kwargs=True, the merged result is flattened as described above.

Missing configuration files

A configuration path that does not exist raises ConverterError with exactly:

Configuration not found: <path>

1.2 write_config_files
def write_config_files(config_template_path: str,
                       config_path_template: str,
                       config_variables: list) -> list:
    ...
Inputs
  • config_template_path names an existing text file containing a configuration template.
  • config_path_template is an output-path template.
  • Both templates may contain placeholders of the form ${name}.
  • config_variables is an ordered list of dictionaries. Each dictionary supplies placeholder names and values for one generated configuration.
Generation behavior

For every dictionary in config_variables, in input order:

  1. Substitute its values into config_path_template to obtain the configuration path.
  2. Create that path's parent directory, including intermediate directories, if needed. An already-existing directory is not an error.
  3. Substitute the same values into the complete text read from config_template_path and write the result to the resolved configuration path.

Placeholder handling follows standard ${name} template-substitution semantics. Every occurrence is substituted, non-string values such as integers are rendered using their string form, and the template text undergoes no other transformation.

For every generated .yml path, derive two sibling paths by replacing the .yml extension with:

  • .out for standard output; and
  • .err for standard error.

write_config_files creates only the .yml configuration files. It must not create the derived .out or .err files.

Return value

Return one 3-tuple per variables dictionary, preserving input order:

(config_yml_path, config_out_path, config_err_path)

All three entries use the same directory and basename as the resolved configuration path. Paths retain the same absolute or relative form produced from config_path_template; they are not reduced to bare filenames.

Example

Given:

config_path_template = <dir>/ghg-${year}.yml
config_variables = [{'year': 2008}, {'year': 2009}, {'year': 2010},
                    {'year': 2011}, {'year': 2012}]

create <dir> when necessary, write ghg-2008.yml through ghg-2012.yml, and return:

[

  ('<dir>/ghg-2009.yml', '<dir>/ghg-2009.out', '<dir>/ghg-2009.err'),

  ('<dir>/ghg-2012.yml', '<dir>/ghg-2012.out', '<dir>/ghg-2012.err'),
]

Each generated configuration contains the original template text with every ${year} replaced by that entry's year.

3.2 YAML merge and precedence

Load and merge configuration files from left to right, then apply the keyword-derived configuration last. Merging is recursive:

  • mapping values are recursively merged;
  • list values are concatenated in source order, including a list supplied by the final keyword-derived configuration; and
  • for scalar values or other non-mergeable value combinations, the later value replaces the earlier value.

Thus later files have precedence over earlier files for replaceable values, and explicit keyword arguments have final precedence while still participating in list concatenation and recursive mapping merge.

  • When append is not in effect, or the output does not yet exist, the dataset is written as a new Zarr dataset. Appending to a non-existent output therefore creates it.
  • With output_overwrite=False, writing a new dataset to a path that already contains one must fail with the underlying Zarr "group already exists" error.
  • With output_overwrite=True, a pre-existing output at the path is removed and replaced.
  • When append is in effect and the output exists, the dataset is appended along output_append_dim, which defaults to time.
  • reset_attrs=True removes variable attributes (such as _FillValue) from appended slices before appending.
  • output_consolidated=True writes consolidated Zarr metadata.
  • Failed writes may be retried according to output_retry_kwargs; by default a single attempt is made.

Dry-run mode: with dry_run=True, write_dataset must not create, replace, delete, or append the configured output dataset. In particular, a dry-run write must not create the output path, and a dry-run overwrite of an existing output must leave that output in place.

Object storage:

  • output_s3_kwargs supplies S3 storage options (for example key, secret, and client_kwargs with an endpoint_url) for bucket/key-style output paths.
  • Output paths beginning with s3:// must select S3-compatible storage even when no explicit storage arguments are given; all other paths use the local filesystem.
  • Constructing a writer with object-storage arguments must not require immediate bucket access; construction alone must succeed.
  • Storage access failures encountered while writing (for example, an unknown or inaccessible bucket) must propagate as exceptions from write_dataset.

Batch job submission

The nc2zarr.batch module provides job classes for executing conversions as batch jobs. Each job class exposes a submit_job class method whose result is an instance of the class on which it was called. Every returned job exposes a boolean is_running property suitable for polling; it must eventually become False when its associated process has completed.

SlurmJob
@classmethod
def submit_job(
    cls,
    command: List[str],
    out_path: str,
    err_path: str,
    exports: Dict[str, Any] = None,
    directory: str = None,
    partition: str = None,
    duration: str = None,
    sbatch_program: str = 'sbatch',
) -> "SlurmJob"

Submit through an sbatch-compatible program. Build the argument list in exactly this order:

<sbatch_program> -o <out_path> -e <err_path> --partition=<partition> --time=<duration> --chdir=<directory> --export=<K1=V1,K2=V2,...> <command...>

Rules for optional arguments are:

  1. -o <out_path> and -e <err_path> are always present.
  2. Include --partition=<partition> when partition is provided.
  3. Include --time=<duration> when duration is provided.
  4. Include --chdir=<directory> when directory is provided.
  5. Include --export=<...> when exports are provided. Render the mapping in iteration order as comma-separated KEY=VALUE pairs, converting values to text. For example, {'TEST': 123} becomes --export=TEST=123.
  6. Append the original command arguments in their original order.

For example:

SlurmJob.submit_job(
    ['nc2zarr', '--help'],
    'sbatch-mock.out',
    'sbatch-mock.err',
    exports={'TEST': 123},
    directory='.',
    partition='short-serial',
    duration='02:00:00',
    sbatch_program='./sbatch-mock.sh',
)

must invoke the equivalent of:

./sbatch-mock.sh -o sbatch-mock.out -e sbatch-mock.err --partition=short-serial --time=02:00:00 --chdir=. --export=TEST=123 nc2zarr --help

On successful submission, parse standard output of the form:

Submitted batch job <ID>

and expose <ID> as a string in the returned instance's job_id attribute. For example, the line Submitted batch job 137 produces job.job_id == '137'. The returned object is a SlurmJob, and is_running must become False after the associated submission process completes.

If the sbatch-compatible program exits with a non-zero status, raise EnvironmentError with exactly:

Slurm job submission failed for command line: <full space-joined command line>

For example, when sbatch_program='sbatch-mock.sh', the failure corresponding to the arguments above is:

Slurm job submission failed for command line: sbatch-mock.sh -o sbatch-mock.out -e sbatch-mock.err --partition=short-serial --time=02:00:00 --chdir=. --export=TEST=123 nc2zarr --help

Template substitution

Both template locations use ${name} placeholders. For each item, replace every referenced placeholder with the textual form of that item's corresponding value. Apply the same item's substitutions independently to the configuration contents and the output path.

For example, given this template:

  sort_by: "name"

  path: "${output_dir}/${year}-ESACCI-GHG-L2-CO2-SCIAMACHY-WFMD-fv1.zarr/"

write_config_files
def write_config_files(self) -> List[Tuple[str, str, str]]

For each item in config_variables, in order:

  1. Render its configuration path.
  2. Create its parent directory when a non-empty parent path does not already exist.
  3. Render the configuration text and write it to that path.
  4. Derive standard-output and standard-error paths by replacing the configuration path's extension with .out and .err.

Return one (config_path, out_path, err_path) tuple per item, preserving item order. For <dir>/ghg-2012.yml, return:

('<dir>/ghg-2012.yml', '<dir>/ghg-2012.out', '<dir>/ghg-2012.err')

The number of written configurations and returned tuples must always equal the number of variable mappings, including zero for an empty batch.

execute
def execute(self, job_type: str = 'local') -> List

  • Write or refresh the configuration files as write_config_files does.

  • Submit one conversion command per generated configuration and return the resulting job objects in item order. The per-item command invokes nc2zarr with that configuration path; local and Slurm submissions use the tuple's .out and .err paths.

  • job_type='dry_run' uses DryRunJob.

  • job_type='local' uses LocalJob.

  • job_type='slurm' uses SlurmJob.

  • A batch constructed with dry_run=True creates DryRunJob instances for recognized execution selections. In particular, execute() returns one never-running DryRunJob per item.

  • Validate job_type even for a batch constructed with dry_run=True. For any value other than the three names above, raise ValueError with exactly:

    illegal job_type "<job_type>"

    For example, job_type='pippo' produces illegal job_type "pippo".

The returned job count must equal the number of variable mappings and preserve their order.

Filesystem collection helper

Provide an IOCollector helper that tracks files and directories for cleanup. It must support:
