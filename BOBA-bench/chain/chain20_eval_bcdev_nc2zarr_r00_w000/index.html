Task: Build a Command-Line Tool That Converts NetCDF Files into a Zarr Dataset

Summary

Build a command-line interface (CLI) that reads one or more NetCDF (.nc) input files and merges them into a single Zarr dataset on disk.

Public API

Create a module nc2zarr.cli exposing a Click-based command named main.

from nc2zarr.cli import main

main must be a click.Command (for example, defined with the @click.command() decorator) so that a click.testing.CliRunner can invoke it directly.

Command-Line Interface

Arguments
  • A positional input argument that accepts a file path or glob pattern (e.g. /some/dir/*.nc) and identifies the NetCDF files to convert.
Options

  • --mode <mode>: Picks the conversion strategy. The following values must be accepted:

    • slices — process the matched input files, appending/concatenating them along the time dimension.
    • one_go — process all matched input files together within a single operation.

    The resulting dataset must be the same for both modes (see "Behavior" below). If --mode is not supplied, the tool must behave as though slices had been chosen (i.e. it must run successfully and produce the same result as one_go).

  • --version: Displays version information and exits with code 0.

  • --help: Displays usage/help information and exits with code 0. (Click supplies this automatically.)

Behavior

No arguments supplied

When main is invoked with no arguments whatsoever, it must exit with a non-zero exit code (specifically 1). Conversion is not attempted.

Version and Help
  • Invoking the tool with --version exits with code 0.
  • Invoking the tool with --help exits with code 0.
Conversion

When the tool is invoked with an input path/glob (with or without --mode):

  1. Treat the input argument as a glob pattern and expand it to find all matching NetCDF files.
  2. Open each NetCDF file and merge them into a single dataset, concatenating along the time dimension.
  3. Write the merged dataset to a Zarr store located at the path out.zarr in the current working directory. That path must be a directory (a standard Zarr on-disk store).
  4. On success, exit with code 0.

The out.zarr output directory must be created relative to the current working directory (i.e. the literal name out.zarr).

Requirements for the Resulting Dataset

Suppose the input NetCDF files each contain:

  • Data variables chl_1, chl_2, chl_3, each of which has dimensions (time, lat, lon).
  • Coordinate variables lon (dim lon), lat (dim lat), and time (dim time), with each input file holding a single time step.

When the Zarr output produced by the tool is reopened with xarray.open_zarr('out.zarr'), it must satisfy:

  • The set of variables it contains is exactly {'lon', 'lat', 'time', 'chl_1', 'chl_2', 'chl_3'}.
  • The time coordinate holds all time steps from all input files, concatenated in chronological order, with one entry per input file (e.g. 5 input files, each with a distinct daily timestamp, yield a time coordinate of length 5 in ascending date order).
  • The time values match exactly the original timestamps from the input files (as datetime64 values).

Both --mode slices and --mode one_go (and the default taken when --mode is omitted) must produce an output dataset satisfying all of the above identically.

Dependencies

The implementation depends on click, xarray, and numpy (along with an appropriate NetCDF/Zarr backend such as netcdf4/zarr).

Notes

  • On each run, the tool overwrites/creates out.zarr fresh (the test harness deletes it both before and after each invocation, so no special handling for a pre-existing store is required).

Task Specification: The nc2zarr Command-Line Interface

Goal

What has to be built is a command-line tool that converts one or more NetCDF (.nc) input files; the result of the conversion is a single Zarr dataset directory in which the data is combined.

Public API

A module has to be created at nc2zarr/cli.py, and that module must expose a Click command object named nc2zarr:

from nc2zarr.cli import nc2zarr

This nc2zarr must be a command that is based on Click, and it must be possible to invoke it directly via click.testing.CliRunner().invoke(nc2zarr, args). On the command line it is named nc2zarr.

Command-Line Usage

The following is the form taken by a normal conversion:

nc2zarr [--multi-file] INPUT_PATTERN
Positional Input Argument

A single positional argument is accepted by the command, and this argument identifies the NetCDF files that serve as input. This argument may be supplied as a glob-style pattern — /some/dir/*.nc is one example — and the command must expand it into one or more matching .nc files.

Options
  • --multi-file is a boolean flag; it takes no value. The multi-file conversion mode described below is what it selects. When this flag is left out, the command operates in its default slice/append mode.
  • With --version, version information is shown and the command exits successfully; positional input is not required for this.
  • With --help, the command's usage/help is shown and the command exits successfully; positional input is not required for this.

Location and Format of the Output

Whenever a conversion succeeds, the command writes a Zarr dataset to a directory named out.zarr that is located in the current working directory. After the command has completed, this directory must exist, and the dataset must be readable via xarray.open_zarr('out.zarr').

Behavior of the Conversion

Inside every matched NetCDF file is a dataset that carries a time coordinate. The command must combine all matched inputs, doing so by concatenating their time slices along the time dimension, and the chronological order and the associated data must be preserved.

If the inputs contain longitude, latitude, and time coordinates along with the three chlorophyll variables, then exactly the following xarray variables must be contained in the reopened Zarr dataset:

lon
lat
time
chl_1
chl_2
chl_3

Put differently: taken in its entirety, the set of variable names must be exactly {'lon', 'lat', 'time', 'chl_1', 'chl_2', 'chl_3'} — with lon, lat, and time being the coordinate variables and chl_1, chl_2, and chl_3 the data variables. Additional xarray variables may not be introduced into this output. For all three data variables, the values must remain associated with the corresponding time slices.

For illustration, take five input files whose time coordinates correspond to December 1 through December 5, 2020 at 10:00:00. The output must then contain five time entries; these entries must appear in this order and be datetime64 values:

2020-12-01T10:00:00
2020-12-02T10:00:00
2020-12-03T10:00:00
2020-12-04T10:00:00
2020-12-05T10:00:00
Modes of Conversion
  • Default mode: If no mode flag is given, the inputs are processed as individual slices and are appended, which is what forms the combined dataset.
  • Multi-file mode: If --multi-file is given, the matched inputs are opened/processed together, and the combined dataset is written.

Both modes must lead to an observably equivalent out.zarr — meaning the complete variable set, the coordinate values, the chronological time sequence, and the data values must be the same.

The following are example invocations:

nc2zarr '/some/dir/*.nc'
nc2zarr --multi-file '/some/dir/*.nc'

Exit Status and No-Conversion Behavior

  • When a conversion succeeds, it must exit with status code 0, and an uncaught exception must not be raised.
  • When nc2zarr is invoked with no arguments at all — no positional input, and no option that triggers a conversion — the invocation must perform no conversion, must not create out.zarr, and must exit with status code 1.
  • When nc2zarr --help is invoked, the command must display help, must perform no conversion, and must exit with status code 0.
  • When nc2zarr --version is invoked, the command must display version information, must perform no conversion, must not create out.zarr, and must exit with status code 0.

Dependencies

For its public command interface, the command relies on Click. For reading, combining, writing, and validating the dataset values, it relies on xarray with Zarr support and on numpy.

@staticmethod
def resolve_input_paths(input_paths, sort_by=None) -> list

Turns input_paths into a flat list of concrete file paths:

1.3 Rules for merging files

Configuration files are read and merged in the order supplied by config_paths, from left to right. Files that come later have higher precedence than files that come earlier, subject to the special input.paths rule below.

  1. When both the existing and the incoming values at a key are dictionaries, they are merged recursively. This holds at every dictionary nesting level, including but not limited to input, process, output, and nested objects such as output.s3.
  2. When the values are not both dictionaries, the incoming value normally replaces the existing value.
  3. Normally, lists are replaced as complete values; they are not concatenated or merged element by element.
  4. Among lists, the sole exception is input.paths in file-to-file merging. Whenever successive configuration files each supply a list at input.paths, concatenate those lists in configuration-file order. All entries are retained in that order; the earlier list is not replaced and is not deduplicated. This exception applies to lists that come from configuration files, not to the final keyword-override layer.

After all files have been merged, the supplied keyword values are merged on top of that result. At their mapped keys, keyword values always take precedence, including false-like values. In particular, an input_paths value that was explicitly supplied replaces the file-derived input.paths value; it is not appended to it. File-derived keys that are unrelated remain in place through the same recursive dictionary merge behavior.

  • Through the special '*' mapping, dimension chunk sizes reach every variable that uses those dimensions, the values being arranged in each variable's own dimension order. Consequently, a variable having dimensions (time, lat, lon) with wildcard sizes time=1, lat=4, lon=8 ends up with (1, 4, 8).

  • For a one-dimensional coordinate variable, a variable-specific integer is used directly as that variable's sole chunk size, and it overrides the wildcard value. This integer may be larger than the coordinate's current length.
  • If a variable-specific value is None, then all of that variable's dimensions use their full dimension lengths. Giving a dimension the value None likewise means that its full length is used.
  • When the wildcard and the variable-specific settings leave a dimension unmentioned, that dimension keeps its current chunk sizes if they are available; if the variable is not already chunked, the dimension's full length is used instead.

output_encoding, which is supplied separately, is merged — per variable — with the chunk entries that were computed. Task Specification: The Public nc2zarr APIs and Dataset Rechunking

Overview

The public nc2zarr conversion APIs to be provided cover opening NetCDF or Zarr inputs, preprocessing and processing xarray.Dataset objects, loading and merging configuration, running conversions from Python as well as from the command line, and writing Zarr output. At the center of the processing contract sits a DatasetProcessor that applies variable renaming, rechunking rules, and output-encoding overrides, and that returns a dataset together with the encoding to use for output.

The package-level behaviors given below are compatibility requirements. Public errors identified as ConverterError use nc2zarr.error.ConverterError.

1. Processing a dataset

Public interface

The class must be importable from nc2zarr.processor and must support construction as follows:

DatasetProcessor(
    process_rename=<dict>,
    process_rechunk=<dict>,
    output_encoding=<dict>,
)

All three arguments are optional and are passed in as keyword arguments.

  • process_rename maps existing variable names to the names that replace them.
  • process_rechunk describes rechunking rules in the format specified below.
  • output_encoding holds per-variable output-encoding overrides.

Processing happens through the method

process_dataset(dataset) -> (new_dataset, new_encoding)

which accepts an xarray.Dataset and returns a 2-tuple:

  • new_dataset is the dataset after renaming and/or processing.
  • new_encoding is a dictionary of output encodings keyed by variable name.
Renaming variables

Whenever process_rename is non-empty, the named variables must be renamed according to that mapping. As an example, {'r_f32': 'bibo'} produces a dataset that contains bibo and no longer contains r_f32. Renaming is applied before any rechunking or output-encoding resolution takes place, so variable names used later refer to the dataset that results from renaming.

When renaming is the only requested operation, new_encoding is {}.

Format of the rechunking rules

process_rechunk is a dictionary whose keys are one of the following:

  • A variable-name selector: either the wildcard '*', which applies to all variables — data variables and one-dimensional coordinate variables alike — or the name of a specific data variable such as 'r_i32'. Its value is a dictionary mapping dimension names such as 'lon', 'lat', and 'time' to chunk-size specifications.
  • A dimension name at the top level, such as 'lon', 'lat', or 'time'. Its value is a chunk-size specification for the corresponding coordinate variable, and it overrides any wildcard entry for that dimension when that coordinate is resolved.

A chunk-size specification may be:

  • A positive integer: that integer is used as the chunk size. A value larger than the current dimension extent is allowed and is not capped.
  • None: the dimension stays unchunked, represented by its full extent.
  • The string 'input': the leading input chunk of that dimension is used.

Every other value is invalid (see "Invalid chunk sizes" below).

Chunk resolution for data variables

For every data variable:

  1. Start with the dimension rules under '*', if present.
  2. If rules are present under that variable's own name, merge them in; these entries override equal dimension entries from '*'.
  3. Resolve every dimension in the variable's dimension order. A dimension with no applicable rule resolves to its full extent (unchunked).
  4. Store the result as a tuple under the variable's 'chunks' encoding entry.

A variable that matches neither a variable selector nor a wildcard rule is unchunked along its dimensions, using each full dimension extent.

Chunk resolution for coordinate variables

For every one-dimensional coordinate variable corresponding to a dimension:

  • If process_rechunk has a top-level key equal to the dimension name, resolve that integer, None, or 'input' specification for the coordinate. Such a top-level key takes precedence over any wildcard entry.
  • Otherwise, if the wildcard rules under '*' contain an entry for that dimension, resolve that entry for the coordinate. Wildcard dimension rules therefore apply to coordinate variables just as they do to data variables.
  • In the remaining case, the coordinate is unchunked and its chunk size is its full extent.
  • Its 'chunks' entry is a one-element tuple.
Chunking of the input

Under an 'input' rule, use the size of the first, leading Dask chunk already present on the input variable along the applicable dimension. Hence, if an extent is split into two halves, the resolved size is ceil(extent / 2). As an example, for a variable whose dimensions are (time, lat, lon), leading chunks time=1, lat=9, and lon=18 resolve to (1, 9, 18).

If the variable carries no Dask chunking (for example, a plain in-memory variable with no chunk information), an 'input' rule must not fail: the dimension resolves to its full extent, and resolution proceeds normally. In particular, an 'input' rule applied to an unchunked variable must not mask or preempt the detection of an invalid chunk-size value elsewhere in the rules; the specified ValueError for the invalid value is still raised.

Encoding output and merging of overrides

Whenever rechunking or output encoding is requested, new_encoding maps every data and coordinate variable in the resulting dataset to a dictionary. Each entry contains a 'chunks' tuple that follows the variable's dimension order.

For every dataset variable named in output_encoding, its supplied entries are merged into the generated entry after chunk resolution. Supplied values such as compressor=None and fill_value=None must be retained. When an override uses the same key as a generated encoding entry, the explicit output override takes precedence.

Renaming on its own is the exception: it returns an empty encoding, since neither rechunking nor output encoding was requested.

Dataset identity and mutation
  • When process_rename, process_rechunk, and output_encoding are all absent or empty, return the exact input dataset object and {}.
  • When any processing is requested, return a distinct dataset object, even when the resolved chunks happen to match the input.
  • The input dataset object must not be mutated.
Invalid chunk sizes

An invalid chunk-size value raises ValueError with exactly:

invalid chunk size: <value>

<value> is the standard string representation of the offending value. As an example, [1, 2, 3] produces invalid chunk size: [1, 2, 3].

Invalid chunk-size values present in process_rechunk are accepted without error at DatasetProcessor construction time; the ValueError is raised only once process_dataset is called and the rules are resolved.

As an example, constructing a processor with

process_rechunk={'*': {'lon': [1, 2, 3], 'lat': 'input'}}

succeeds. Calling process_dataset on a dataset whose variables have dimensions (lat, lon) and no Dask chunking then raises ValueError with exactly invalid chunk size: [1, 2, 3]; the 'input' rule for lat resolves to the full extent and does not itself raise or change the reported error.

Public interface

  • return_kwargs selects the flattened keyword form of the result.
  • The remaining keyword arguments are the conversion parameters accepted by Converter (see section 4).
Conversion from keyword arguments to configuration

When there are no configuration paths and no keyword arguments, load_config() returns {}.

In the normal (nested) form, each keyword argument whose value is not None is placed in the result as follows:

  • Names carrying the input_ prefix go under a nested 'input' dictionary with the prefix removed.
  • Names carrying the process_ prefix go under a nested 'process' dictionary with the prefix removed.
  • Names carrying the output_ prefix go under a nested 'output' dictionary with the prefix removed.
  • Every other name remains a top-level key.

Arguments with a False value are retained; only None values are dropped. A nested section appears only when it has at least one entry. For example:

load_config(input_paths='in/*.nc',
            input_multi_file=True,
            output_path='my.zarr',
            output_overwrite=False,
            process_rename={'lons': 'lon'},
            dry_run=True,
            verbosity=2)

which returns:

{
    'dry_run': True,
    'verbosity': 2,
    'input': {'paths': 'in/*.nc', 'multi_file': True},
    'process': {'rename': {'lons': 'lon'}},
    'output': {'path': 'my.zarr', 'overwrite': False},
}

With return_kwargs=True, the nested configuration keys are flattened back into their prefixed keyword names: entries of 'input', 'process', and 'output' turn into input_<key>, process_<key>, and output_<key> respectively, and other keys remain unchanged. The same call as above, now with return_kwargs=True, returns:

{
    'input_paths': 'in/*.nc',
    'input_multi_file': True,
    'process_rename': {'lons': 'lon'},
    'output_path': 'my.zarr',
    'output_overwrite': False,
    'dry_run': True,
    'verbosity': 2,
}
Merging of configuration files

When config_paths is given, each YAML file is loaded and the configurations are merged in the supplied order; the keyword-derived configuration is then merged last, so explicit keyword arguments take precedence over all files. Merging is recursive:

  • When the two values for a key are both dictionaries, they are merged recursively.
  • When the two values are both lists, they are concatenated in order (earlier sources first).
  • In every other case, the later value replaces the earlier one.

For example, with file a.yml containing:

input:
  paths: ["a/*.nc"]
  decode_cf: true

and file b.yml with the content:

input:
  paths: ["b/*.nc"]
  decode_cf: false
output:
  append: true

the call load_config(config_paths=['a.yml', 'b.yml'], input_paths=['c/*.nc'], verbosity=1) then returns:

{
    'verbosity': 1,
    'input': {
        'paths': ['a/*.nc', 'b/*.nc', 'c/*.nc'],
        'decode_cf': False,
    },
    'output': {'append': True},
}

With return_kwargs=True, the merged result is flattened in the way described above.

Task Specification: Batch-Mode Utilities and the Preserved nc2zarr Contracts

Summary

Add batch-mode support for producing per-item nc2zarr configuration files and submitting them via dry-run, local-process, or Slurm-style backends. This new functionality goes into nc2zarr/batch.py, which must expose DryRunJob, LocalJob, SlurmJob, and TemplateBatch.

The existing command-line converter and its public Python APIs must stay compatible. The externally observable behavior defined in the sections below must be preserved alongside the new batch functionality.

Public exception type

nc2zarr.error.ConverterError continues to be the converter-specific ValueError subtype used by the configuration, opening, preprocessing, converter, and command-line APIs. Wherever an exact message is given below, its punctuation and quoting matter.

References to custom callables

nc2zarr.custom.load_custom_func(ref) resolves callable references written in this form:

<module>:<attribute.path>

The attribute portion may designate either a module-level callable or a dotted chain, for instance a class method. The resolved object is returned when it is callable. For example, some.module:convert as well as some.module:Processor.convert are both valid forms.

It must raise ValueError with exactly these messages:

  • Malformed reference, which covers a missing module/function component or an invalid dotted attribute component:

    func_ref "<ref>" is invalid, format must be <module>:<function>

  • The module cannot be imported:

    module for function "<ref>" not found

  • Some attribute within the dotted path does not exist:

    function "<ref>" not found, unknown attribute "<attribute>"

  • The final object obtained through resolution is not callable:

    "<ref>" is not callable

The custom dataset hooks described below receive one xarray.Dataset, and their returned dataset must be used by the remainder of the conversion pipeline.

Loading configuration

def load_config(config_paths=None, return_kwargs=False, **kwargs) -> Dict[str, Any]

nc2zarr.config.load_config must support passing a single YAML path or a sequence of YAML paths. The behavior is as follows:

  • When no paths and no keyword values are given, return {}. The same applies when return_kwargs=True.
  • Flat keyword names that begin with input_, process_, or output_ are converted into the corresponding nested input, process, or output mapping. Keyword names other than these remain at the top level. Falsy values, for instance False, 0, and empty collections, must not be dropped.
  • With return_kwargs=True, the inverse shape conversion is performed: entries in input, process, and output turn into input_*, process_*, and output_* keyword entries, while top-level entries other than those keep their names. Values nested inside one of those entries remain mappings.
  • Multiple YAML files are read from left to right and their mappings are merged recursively. When both values are lists, they are concatenated in left-to-right order; input-path lists are included in this. For value types other than lists, the later value takes the place of the earlier value.
  • Explicit keyword configuration is applied after all file configuration, applying the same recursive merge rules. Consequently, explicit scalar and boolean values take precedence, while explicit lists are appended onto preceding lists.

As an example, input_decode_cf=False must produce or override input: {decode_cf: false} instead of being omitted.

When a requested configuration path does not exist, ConverterError must be raised with exactly:

Configuration not found: <path>

Logging helpers

nc2zarr.log must keep exposing LOGGER, get_verbosity, use_verbosity, and log_duration.

  • The verbosity starts out at 0, and LOGGER.level is logging.WARNING.
  • With use_verbosity(0), the level is WARNING; with use_verbosity(1), INFO; and with use_verbosity(2), DEBUG.
  • use_verbosity(...) is a context manager; when its context exits, the previous verbosity and logger level are restored, including after an exceptional exit.
  • log_duration(tag=None) is a context manager. The object its __enter__ returns exposes a duration attribute that is populated with the elapsed time after the context exits.

Compatibility at the command line

nc2zarr.cli.nc2zarr must stay a Click-invokable command, and the console command remains nc2zarr. The module must additionally be executable via:

python -m nc2zarr.cli

The observable exit behavior is as follows:

  • Calling it with no arguments exits with status 1.
  • Passing --help exits with status 0.
  • --version prints the package's version and exits with status 0.
  • python -m nc2zarr.cli --help is an invocation that succeeds.

Converter errors surfaced by the command are reported as Click command errors, not as uncaught tracebacks.

Opening datasets

DatasetOpener

def open_datasets(self, preprocess=None)

open_datasets yields xarray.Dataset objects obtained from the resolved inputs.

  • When no input path resolves to a file or dataset, iterating must raise ConverterError with exactly No inputs found.
  • By default, a single dataset is yielded for each resolved input, in the resolved order.
  • With input_multi_file=True, a single dataset is yielded, formed by concatenating the resolved inputs along the applicable concatenation coordinate (for example time).
  • When preprocess is supplied, it is called on each opened input, and the dataset it returns is used. This must affect the yielded single-file datasets as well as the inputs incorporated into a multi-file result.
  • With input_prefetch_chunks=True, the source chunk topology is preserved when opening. In multi-file mode, the concatenation dimension must keep one source chunk per input file, while the source chunking of the remaining dimensions is preserved.
  • Local directory paths that end in .zarr remain valid inputs and are opened as Zarr datasets when no engine is explicitly supplied.
Input path resolution
@classmethod
def resolve_input_paths(cls, input_paths, sort_by=None) -> List[str]

  • Accept either a single path/glob string or a sequence of path/glob strings. Glob expansion is recursive, so patterns that contain **, *, and ? are supported.

  • Return [] when given None, an empty sequence, or patterns with no matches.

  • Duplicate resolved paths are eliminated. When no sorting is applied, the first occurrence order is preserved.

  • With sort_by='name', sorting is lexical by basename.

  • With sort_by='path', sorting is lexical by the complete path.

  • Any other sorting mode that is non-null raises ConverterError with exactly:

    Can sort by "path" or "name" only, got "<value>".

Preprocessing datasets

DatasetPreProcessor(
    *,
    input_variables=None,
    input_custom_preprocessor=None,
    input_concat_dim=None,
    input_datetime_format=None,
)

def preprocess_dataset(self, ds: xr.Dataset) -> xr.Dataset

The processing order is: variable selection, custom preprocessing, and then ensuring the concatenation dimension.

Selecting variables and custom preprocessing
  • With input_variables=None, all variables are preserved.
  • An input_variables collection that is supplied selects exactly the requested variables and coordinates.
  • input_custom_preprocessor is a <module>:<dotted.attribute> callable reference that load_custom_func resolves. It is invoked with the selected dataset, and processing continues with the dataset it returns. Structural changes made by the hook must be preserved. For example, a hook may swap dimensions so that a sounder_dim dimension is replaced by a time coordinate dimension.
Concatenation coordinates and the synthesized time coordinate

  • When the requested concatenation coordinate already exists, it is preserved. A scalar coordinate may be expanded into its named dimension where needed. If the coordinate is already a proper dimension coordinate, its values must be left untouched.

  • When the requested coordinate is absent and named time, time_coverage_start and time_coverage_end are read from the dataset's global attributes, and the coordinate is synthesized:

    • Each attribute value is parsed as a timestamp. If input_datetime_format is supplied, it gives an explicit parse format; otherwise common textual forms must be accepted automatically, including at least YYYY-MM-DD HH:MM:SS (e.g. 2020-09-08 10:30:00), ISO YYYY-MM-DDTHH:MM:SSZ (e.g. 2020-09-08T10:30:00Z), and compact YYYYMMDDHHMMSS (e.g. 20200908103000).
    • If one of the two attributes is the only one present, its value serves as both start and end of the coverage interval.
    • Add a time coordinate with one element, whose single value is the midpoint of the coverage interval. For example, a coverage interval from 2020-09-08 10:30:00 to 2020-09-08 12:30:00 yields the time value 2020-09-08 11:30:00.
    • The attributes of the synthesized time coordinate must be exactly {'bounds': 'time_bnds'}.
    • Add a time_bnds variable with dimensions ('time', 'bnds'); its single row contains the parsed start and end timestamps, in that order.

  • When a coverage timestamp cannot be parsed, ConverterError must be raised with exactly:

    Cannot parse timestamp from "<value>".

  • When neither time_coverage_start nor time_coverage_end supplies a coverage timestamp, ConverterError must be raised with exactly:

    Missing time_coverage_start and/or time_coverage_end in dataset attributes.

    Attributes named only start_time and end_time are not a substitute for the required attribute names; a dataset that carries only those must still fail with the message above.

  • When the requested concatenation coordinate is absent and its name is not time, no coordinate can be synthesized. ConverterError must be raised with exactly:

    Missing (coordinate) variable "<name>" for dimension "<name>".

    For example, requesting input_concat_dim='t' on a dataset that has no t variable produces Missing (coordinate) variable "t" for dimension "t".

  • After the concatenation coordinate is available, data variables that do not yet use the concatenation dimension must be expanded along it, so that every data variable in the returned dataset carries the concatenation dimension. Any associated bounds variable (the one named by the coordinate's bounds attribute, or <dim>_bnds by default) must remain present in the result.

Processing datasets

DatasetProcessor
DatasetProcessor(
    *,
    process_rename=None,
    process_rechunk=None,
    process_custom_processor=None,
    output_encoding=None,
)

def process_dataset(self, ds: xr.Dataset) -> Tuple[xr.Dataset, Dict[str, Dict[str, Any]]]

nc2zarr.processor.DatasetProcessor.process_dataset returns a (dataset, encoding) pair. The processing order is:

  1. Renaming: process_rename is a mapping from existing names to new names that is applied to the dataset, so a renamed variable shows up only under its new name in the result.
  2. Custom processing: process_custom_processor is a <module>:<dotted.attribute> callable reference that load_custom_func resolves. It is invoked with the current dataset, and processing continues with the dataset it returns.
  3. Rechunking, as detailed below.

If there is no effective renaming, custom processing, or rechunking, and no output encoding, process_dataset must return the original dataset object itself (identity preserved) along with an empty encoding mapping {}. Empty mappings for process_rechunk and output_encoding count as "no effective processing".

Rechunking

process_rechunk configures chunk sizes per dimension:

  • The special key '*' provides a default mapping from dimension names to chunk-size rules that applies to every variable.
  • Any other key names a variable and overrides that variable's defaults. A per-variable override may be either:
    • a mapping from dimension names to chunk-size rules, applied across all of that variable's dimensions (dimensions that the mapping does not name are treated as None), or
    • a single scalar rule (an integer, None, or 'input') that applies to every dimension of that variable.
  • Dimensions that no applicable rule covers default to 'input'.

The meanings of the chunk-size rules are:

  • An integer gives the requested chunk size for that dimension; it may exceed the dimension length.
  • None stands for the full dimension length (that dimension is left unchunked).
  • 'input' stands for the source chunk size of that dimension, or for the full dimension length when the input is unchunked.

Whenever a resolved rule value is not an integer, None, or 'input', a ValueError must be raised with exactly:

invalid chunk size: <value>

For instance, a list rule like [1, 2, 3] produces invalid chunk size: [1, 2, 3].

With rechunking enabled:

  • The dataset that is returned is a rechunked copy (not the same object), and the data chunking of each variable must reflect the resolved sizes. For example, a variable with 100 elements along time, rechunked to 20, exposes chunks (20, 20, 20, 20, 20) along that dimension.
  • The encoding mapping that is returned holds one entry per dataset variable, of the form {'chunks': (<resolved sizes in the variable's dimension order>)}. For instance, with defaults {'*': {'lon': 8, 'lat': 4, 'time': 1}}, a variable with dimensions (time, lat, lon) yields {'chunks': (1, 4, 8)}, and the coordinate lon yields {'chunks': (8,)}.
Merging of encodings

Those entries from output_encoding that name dataset variables must be merged into the returned encoding: the generated chunk encoding of a variable is updated key-by-key with that variable's output_encoding entry. For example, rechunking r_i32 together with output_encoding={'r_i32': {'compressor': None, 'fill_value': None}} yields {'chunks': (...), 'compressor': None, 'fill_value': None} for that variable.

Writing datasets

DatasetWriter

def write_dataset(self, ds: xr.Dataset, encoding=None, append=None)

Validation performed by the constructor:

  • When output_path is falsy, ValueError must be raised with exactly:

    output_path must be given

  • Supplying output_append=True together with a custom postprocessor must raise ValueError with exactly:

    output_append and output_custom_postprocessor cannot be given both

Behavior when writing:

  • output_custom_postprocessor is a <module>:<dotted.attribute> callable reference that load_custom_func resolves. When it is supplied, it is invoked with the dataset passed to write_dataset, and the dataset it returns is written, so that, for example, a variable added by the hook is present in the written Zarr output.
  • The encoding and append arguments of write_dataset, when they are not None, override the constructor-level output_encoding and output_append values for that call.
  • If append is not in effect, or if the output does not exist yet, the dataset is written as a new Zarr dataset. Appending to an output that does not exist therefore creates it.
  • With output_overwrite=False, writing a new dataset to a path that already holds a dataset must fail with the underlying Zarr "group already exists" error.
  • With output_overwrite=True, an output that already exists at the path is removed and replaced.
  • If append is in effect and the output exists, the dataset is appended along output_append_dim, whose default is time.
  • reset_attrs=True strips variable attributes (for example _FillValue) from appended slices before appending.
  • With output_consolidated=True, consolidated Zarr metadata is written.
  • Failed writes may be retried in accordance with output_retry_kwargs; by default, one attempt is made.

In dry-run mode (dry_run=True), write_dataset must not create, replace, delete, or append the configured output dataset. In particular, a dry-run write must not create the output path, and a dry-run overwrite of an output that exists must leave that output in place.

Storage on object stores:

  • output_s3_kwargs provides S3 storage options (for example key, secret, and client_kwargs with an endpoint_url) for output paths of the bucket/key style.
  • Output paths that begin with s3:// must select S3-compatible storage even when no explicit storage arguments are given; the local filesystem is used for all remaining paths.
  • A writer constructed with object-storage arguments must not require immediate bucket access; construction on its own must succeed.
  • Storage access failures that occur while writing (for example, an unknown or inaccessible bucket) must propagate as exceptions from write_dataset.

nc2zarr.converter.Converter remains the Python entry point combining opening, preprocessing, processing, and writing. input_paths accepts either a single string or a sequence of path/glob strings.

Validation in the constructor:

  • Constructing the converter without any input must raise ConverterError with exactly:

    At least one input must be given.

  • When both output_overwrite=True and output_append=True are supplied, ConverterError must be raised with exactly:

    Output overwrite and append flags cannot be given both.

The defaults and the behavior of run():

  • out.zarr is the default output path.
  • When neither input_concat_dim nor output_append_dim is given, both default to time. When exactly one of the two is given, its value serves both roles.
  • Each resolved input is preprocessed and processed as described above and then written: the first dataset is written according to the configured append/overwrite flags, and every dataset after it is appended along the append dimension. The output that results therefore contains the concatenated coordinate values of all inputs in resolved order.
  • .zarr directories that already exist are valid inputs, so outputs produced previously can be concatenated into a new output.
  • With output_append=True, a run against an output that does not exist creates it, and a later run appends further slices.
  • A dry run (dry_run=True) must perform no output write: afterwards, the output path must not exist unless it existed before. This holds at every verbosity level, including verbosity=0.
  • run() applies the configured verbosity for the duration of the run, using the logging semantics above.

Submitting batch jobs

Job classes for executing conversions as batch jobs are provided by the nc2zarr.batch module. Each job class exposes a submit_job class method whose result is an instance of the class on which the method was called. Every job that is returned exposes a boolean is_running property suitable for polling; it must eventually become False once its associated process has completed.

DryRunJob
@classmethod
def submit_job(cls, command: List[str]) -> "DryRunJob"
  • The command is accepted but not executed.
  • A DryRunJob instance is returned.
  • A dry-run job is never in a running state, so is_running is always False, including immediately after submission.
LocalJob
@classmethod
def submit_job(
    cls,
    command: List[str],
    out_path: str,
    err_path: str,
) -> "LocalJob"
  • The supplied command is started as a local process.
  • Standard output is redirected to out_path, and standard error to err_path.
  • A LocalJob is returned whose is_running reflects the process state and becomes False after the process exits.
  • The command that callers supply is an argument list that can be run directly.
SlurmJob
@classmethod
def submit_job(
    cls,
    command: List[str],
    out_path: str,
    err_path: str,
    exports: Dict[str, Any] = None,
    directory: str = None,
    partition: str = None,
    duration: str = None,
    sbatch_program: str = 'sbatch',
) -> "SlurmJob"

Submission goes through an sbatch-compatible program. The argument list is built in exactly this order:

<sbatch_program> -o <out_path> -e <err_path> --partition=<partition> --time=<duration> --chdir=<directory> --export=<K1=V1,K2=V2,...> <command...>

The rules for the optional arguments are:

  1. -o <out_path> and -e <err_path> are always included.
  2. Include --partition=<partition> when a partition is provided.
  3. Include --time=<duration> when a duration is provided.
  4. Include --chdir=<directory> when a directory is provided.
  5. Include --export=<...> when exports are provided. The mapping is rendered in iteration order as comma-separated KEY=VALUE pairs, with values converted to text. For example, {'TEST': 123} becomes --export=TEST=123.
  6. The original command arguments are appended in their original order.

As an example:

SlurmJob.submit_job(
    ['nc2zarr', '--help'],
    'sbatch-mock.out',
    'sbatch-mock.err',
    exports={'TEST': 123},
    directory='.',
    partition='short-serial',
    duration='02:00:00',
    sbatch_program='./sbatch-mock.sh',
)

must invoke something equivalent to:

./sbatch-mock.sh -o sbatch-mock.out -e sbatch-mock.err --partition=short-serial --time=02:00:00 --chdir=. --export=TEST=123 nc2zarr --help

When submission succeeds, parse the standard output, which has the form:

Submitted batch job <ID>

and expose <ID> as a string in the job_id attribute of the returned instance. For example, the line Submitted batch job 137 produces job.job_id == '137'. The object that is returned is a SlurmJob, and is_running must become False after the associated submission process has completed.

If the sbatch-compatible program exits with a status that is non-zero, EnvironmentError must be raised with exactly:

Slurm job submission failed for command line: <full space-joined command line>

For example, with sbatch_program='sbatch-mock.sh', the failure that corresponds to the arguments above is:

Slurm job submission failed for command line: sbatch-mock.sh -o sbatch-mock.out -e sbatch-mock.err --partition=short-serial --time=02:00:00 --chdir=. --export=TEST=123 nc2zarr --help
TemplateBatch
class TemplateBatch:
    def __init__(
        self,
        config_variables: List[Dict[str, Any]],
        config_template_path: str,
        config_path_template: str,
        dry_run: bool = False,
    )
  • config_variables holds one substitution mapping per batch item.
  • config_template_path is the name of a text configuration template.
  • config_path_template is itself a template from which each output configuration path is derived.
  • dry_run forces the recognized execution selections to create dry-run jobs. Job types that are illegal must still be rejected.
Substitution into templates

Placeholders of the form ${name} are used in both template locations. For each item, every placeholder that is referenced is replaced with the textual form of that item's corresponding value. The same item's substitutions are applied independently to the configuration contents and to the output path.

As an example, given this template:

input:
  paths:
    - "${input_dir}/${year}/ESACCI-GHG-L2-CO2-SCIAMACHY-WFMD-*-fv1.nc"
  sort_by: "name"
output:
  path: "${output_dir}/${year}-ESACCI-GHG-L2-CO2-SCIAMACHY-WFMD-fv1.zarr/"

together with these variables:

{
    'year': 2012,
    'input_dir': '/neodc/esacci/ghg/data/crdp_4/SCIAMACHY/CO2_SCI_WFMD/v4.0',
    'output_dir': './data',
}

the contents that get rendered are:

input:
  paths:
    - "/neodc/esacci/ghg/data/crdp_4/SCIAMACHY/CO2_SCI_WFMD/v4.0/2012/ESACCI-GHG-L2-CO2-SCIAMACHY-WFMD-*-fv1.nc"
  sort_by: "name"
output:
  path: "./data/2012-ESACCI-GHG-L2-CO2-SCIAMACHY-WFMD-fv1.zarr/"

Given config_path_template='<dir>/ghg-${year}.yml', the output path is <dir>/ghg-2012.yml.

write_config_files
def write_config_files(self) -> List[Tuple[str, str, str]]

Each item in config_variables is processed in order:

  1. Render the item's configuration path.
  2. Create the parent directory when the parent path is non-empty and does not already exist.
  3. Render the configuration text and write it to the path.
  4. Derive the standard-output and standard-error paths by replacing the extension of the configuration path with .out and .err.

Return one (config_path, out_path, err_path) tuple per item, keeping the item order. For <dir>/ghg-2012.yml, return:

('<dir>/ghg-2012.yml', '<dir>/ghg-2012.out', '<dir>/ghg-2012.err')

The number of written configurations and of returned tuples must always equal the number of variable mappings, including zero for an empty batch.

execute
def execute(self, job_type: str = 'local') -> List

  • The configuration files are written or refreshed as write_config_files does.

  • One conversion command is submitted per generated configuration, and the resulting job objects are returned in item order. The command for each item invokes nc2zarr with that configuration path; local and Slurm submissions use the tuple's .out and .err paths.

  • job_type='dry_run' means DryRunJob is used.

  • job_type='local' means LocalJob is used.

  • job_type='slurm' means SlurmJob is used.

  • A batch constructed with dry_run=True creates DryRunJob instances for the recognized execution selections. In particular, execute() returns one DryRunJob that never runs, per item.

  • job_type must be validated even for a batch constructed with dry_run=True. For any value other than the three names above, ValueError must be raised with exactly:

    illegal job_type "<job_type>"

    As an example, job_type='pippo' produces illegal job_type "pippo".

The number of returned jobs must equal the number of variable mappings and preserve their order.

Helper for filesystem collection

Provide an IOCollector helper that keeps track of files and directories for cleanup. It must support the following:

  • reset_paths(), which clears the tracked collection.
  • add_path(path, ensure_deleted=True), which registers a path. With the default ensure_deleted=True, ensure that a file or directory already existing at that path is removed when it is registered; False leaves it in place until a later cleanup.
  • delete_paths(), which removes every tracked path that exists. Individual files must be removed directly, and directories recursively, including their contents. Repeated cleanup of paths that are already absent must be harmless.

All batch APIs must work without altering the preserved converter behavior described above.
