Task: Implement the BrokerClient.delete_account method

Goal

Introduce a new public method delete_account on the BrokerClient class (in the broker client module). To delete a brokerage account, the method issues an HTTP DELETE request to the Alpaca Broker API.

Method Signature

def delete_account(self, account_id: Union[UUID, str]) -> None

Method behavior

Validating the input
  • Callers may supply account_id either as a UUID instance or as a str that represents a valid UUID.
  • When account_id is given as a string, it must be a valid UUID string. Raise ValueError if it is not parseable as a UUID.
  • If the type of account_id is neither a UUID nor a valid UUID string (for example, an integer), raise ValueError.
The request
  • Given valid input, send an HTTP DELETE request to the accounts endpoint for the given account, that is, the path:
    /v1/accounts/{account_id}
    where {account_id} stands for the resolved UUID value. With the sandbox base URL, this resolves to:
    https://broker-api.sandbox.alpaca.markets/v1/accounts/{account_id}
  • On success, the API responds with HTTP 204 (No Content).
Returned value
  • This method returns None.

Additional notes

  • Per successful call, only one DELETE request should be made.
  • Before any HTTP request is issued, validation errors must be raised.

The signature:

def get_account_activities(
    self,
    activity_filter: GetAccountActivitiesRequest,
    handle_pagination: PaginationType,
)

GET requests to the account activities endpoint are issued by this method. Per response, the endpoint returns a JSON array of activity objects. Pagination happens through repeated requests; an empty JSON array ([]) is the signal that there are no more pages. The test data is such that page one returns 4 activities, page two returns 4 activities, and page three returns an empty array.

What the method does depends on handle_pagination:

  • Returns a single List that contains every activity from all non-empty pages, each parsed as a BaseActivity (or subtype).

  • Fetches only the first page (a single HTTP request) and does not paginate further.
  • Returns a single List with the activities from that first page, each parsed as a BaseActivity (or subtype).
  • For the test data, this comes to 1 HTTP request and a returned list of length 4.

  • Returns an Iterator (a generator).
  • Until the iterator is advanced, no HTTP request is made.
  • Each advance of the iterator yields one page's worth of results as a List of BaseActivity (or subtype) objects, and corresponds to one HTTP request.

  • An empty JSON array response serves as the pagination stop condition.

Task: Implement BrokerClient.get_account_activities with support for pagination

Summary

Add a method to the BrokerClient class that retrieves account activities from the broker API, with pagination behavior that can be configured. The API returns activity records in pages, and the method must aggregate or stream these pages correctly according to a pagination strategy.

Public API

Method
class BrokerClient:
    def get_account_activities(
        self,
        activity_filter: GetAccountActivitiesRequest,
        handle_pagination: PaginationType,
    ):
        ...

The method accepts the following:

  • activity_filter: a GetAccountActivitiesRequest instance that describes the filter parameters for the query (it must be constructible with no arguments).
  • handle_pagination: a PaginationType enum value that controls how paging is handled.
Supporting Types

The following must be importable by callers and usable by them:

  • GetAccountActivitiesRequest — a request/filter model that can be instantiated with no arguments (all of the fields are optional).
  • PaginationType — an enumeration that provides at least the members PaginationType.FULL, PaginationType.NONE, and PaginationType.ITERATOR.
  • BaseActivity — the base model type into which each returned activity record is parsed.

Data Model

The API returns JSON arrays of activity objects. Activities come in two shapes, distinguished by their activity_type:

  1. Non-trade activities (e.g. activity_type = "CSD"), having fields such as:

    • id, account_id, activity_type, date, net_amount, description, status.

  2. Trade activities (e.g. activity_type = "FILL"), having fields such as:

    • id, account_id, activity_type, transaction_time, type, price, qty, side, symbol, leaves_qty, order_id, cum_qty, order_status.

Parsing must succeed for both shapes, and each parsed record must be an instance of BaseActivity.

Pagination Behavior

The broker API endpoint for account activities is paginated. One request returns up to a page-size worth of records. When a full page is returned, the caller must keep fetching subsequent pages (advancing to the next page with the last returned item); when a page returns fewer records than the page size, that page is the last one.

For this task, the page size behavior is such that a page containing 4 records signals that there may be more pages, and paging continues until a request returns fewer than a full page.

The method's return value and its request-issuing behavior depend on handle_pagination:

PaginationType.FULL
  • Fetch all pages, advancing through the pagination until it is exhausted.
  • Return a single List that contains every activity record from all pages, in order.
  • For a data set that spans multiple pages and requires 3 HTTP requests to retrieve fully, exactly 3 requests must be made, and the combined result must contain all 8 records.
  • Each element in the returned list must be a BaseActivity instance.
PaginationType.NONE
  • Fetch only the first page.
  • Make exactly 1 HTTP request.
  • Return a single List that contains only the records from that first page (4 records for the reference data set).
  • Each element in the returned list must be a BaseActivity instance.
PaginationType.ITERATOR
  • Return a generator/iterator that yields one page at a time.
  • Each item the generator produces is a List of BaseActivity instances (one page's worth of records).

  5. content_data requires a JSON mime_type: when content_data is provided but mime_type is not UploadDocumentMimeType.JSON. The error message must contain:

    If `content_data` is set then `mime_type` must be JSON
Notes on the ordering of validations

The validations must be ordered so that:

  • Providing content_data with a non-JSON mime_type (and no content) causes the "must be JSON" error to surface — i.e., the single-content-field check passes when exactly one of the two is set, and the JSON-mime check then applies.
  • Providing content alone, with a non-JSON mime_type and the default document types, must succeed (the JSON-mime rule only applies when content_data is set).

All of the errors above must be raised as ValueError (or a subclass of it) during construction of the model.

Summary

A W8BenDocument model class is to be implemented inside the module alpaca.broker.models. It must be importable as follows:

from alpaca.broker.models import W8BenDocument

W8BenDocument is a data model that represents a W-8BEN tax document. Construction should happen exclusively with keyword arguments.

Model fields

The following keyword fields are accepted by the constructor:

Required fields (must be supplied on every construction):

  • country_citizen
  • date
  • date_of_birth
  • full_name
  • ip_address
  • permanent_address_city_state
  • permanent_address_country
  • permanent_address_street
  • revision
  • signer_full_name
  • timestamp

Fields that are optional:

  • foreign_tax_id
  • ftin_not_required
  • tax_id_ssn

Behavior of the fields

The string-like fields

All of the fields listed below must accept and store plain string values, empty strings included:

  • country_citizen
  • date
  • date_of_birth
  • full_name
  • ip_address
  • permanent_address_city_state
  • permanent_address_country
  • permanent_address_street
  • revision
  • signer_full_name
  • timestamp
  • foreign_tax_id
  • tax_id_ssn

Empty strings are valid values for these fields, and providing one must not raise an error.

The boolean field
  • The ftin_not_required field accepts a boolean value (e.g. False).

Validation requirement

When a W8BenDocument is constructed, at least one of the following three conditions must hold:

  • foreign_tax_id is supplied, OR
  • tax_id_ssn is supplied, OR
  • ftin_not_required is supplied (assigned any value, e.g. False).

If none of foreign_tax_id, tax_id_ssn, or ftin_not_required is supplied, construction must raise a ValueError whose message contains the exact substring:

ftin_not_required must be set if foreign_tax_id and tax_id_ssn are not

Supplying any one (or more) of these three fields satisfies the rule and leads to successful construction.

Valid construction examples

Construction succeeds when all required fields are given together with any one of the tax-identification-related fields, for example:

  • All required fields together with foreign_tax_id="fake".
  • All required fields together with tax_id_ssn="fake ssn".
  • All required fields together with ftin_not_required=False.
  • All required fields (mixing non-empty and empty string values) plus any of the above.

Invalid construction example

Supplying all required fields but leaving out all of foreign_tax_id, tax_id_ssn, and ftin_not_required raises the ValueError described above.
