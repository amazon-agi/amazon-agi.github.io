Task Specification: Loading Configuration and Job Types

Summary

Your task is to implement configuration parsing for a tool that syncs data between Dune Analytics and a PostgreSQL database. The system reads job definitions from YAML config files, validates them, and exposes runnable jobs.

Public API

Module: src.config

It must be possible to import the following from src.config:

  • Env — a class for environment configuration that offers the class method Env.load(), which reads configuration from environment variables (it uses load_dotenv internally, and callers may patch that). It requires the DUNE_API_KEY and DB_URL environment variables.

  • RuntimeConfig — a configuration object that exposes:

    • A class method RuntimeConfig.load_from_yaml(path) that accepts the filesystem path of a YAML config file (a str or pathlib.Path, including absolute paths), parses that file, validates it, and returns a RuntimeConfig instance.
    • An attribute jobs — a list of job objects (it can be indexed, and len() is supported). Each job object exposes a run() method (see below).

  • parse_query_parameters — a function that turns a list of parameter definitions into Dune query parameter objects (see "Query Parameters" below).

Format of the Config File

A config file is a YAML document in which a top-level jobs key maps to a list of job entries. Each job entry contains:

  • name: a string that is human-readable.
  • source: a mapping that describes where the data comes from.
  • destination: a mapping that describes where the data goes.

source and destination both contain a ref field that names the connector type. The supported ref values are:

  • dune — the connector for Dune Analytics.
  • postgres — the connector for PostgreSQL.

Any ref value other than these is unsupported (see "Validation and Errors").

Dune source and destination fields
  • query_id: an integer that identifies the query (an unquoted integer in YAML, e.g. 4238114, 123, 1).
  • query_engine: an optional string that selects the engine (e.g. medium).
  • poll_frequency: an integer; it is optional.
  • parameters: an optional list of parameters for the query (see below).
  • table_name: a string with the table name (for use when Dune is the destination).
Postgres source and destination fields
  • table_name: a string with the table name. Mandatory when postgres is the destination.
  • if_exists: a string that specifies the strategy (e.g. replace, append).
  • query_string: a string containing a SQL query (for use when postgres is the source).

Note: YAML values may be left unquoted. Integer values such as query_id arrive as native integers, and string values such as medium, replace, SELECT * FROM foo;, and table names arrive as native strings. The parsing must not rely on values being quoted.

Query Parameters

Each entry in a parameters list is a mapping that has:

  • name: a string holding the parameter name.
  • value: the value of the parameter.
  • type: one of ENUM, DATE, NUMBER (and other Dune parameter types); this determines how the value is interpreted.

parse_query_parameters accepts such a list and returns the list of Dune QueryParameter objects matching it.

Behavioral Requirements

Successful load

When the config is well-formed, uses supported connector types, and has all mandatory fields present, RuntimeConfig.load_from_yaml returns a RuntimeConfig whose jobs list holds one runnable job for each entry in the file's jobs list, in order.

Job execution

Each job object's run() method carries out the transfer from source to destination. For a job whose source is Dune and whose destination is Postgres:

  • The job fetches the query result from the Dune client and writes it to the destination.
  • If the Dune client returns a result, the run finishes successfully.
  • If the Dune client returns None (that is, no result), run() raises ValueError.

Validation and Errors

Validation takes place during load_from_yaml (before any job is run):

  • If a source specifies a connector ref that is unsupported (any value other than dune or postgres), raise ValueError with a message containing the text Unsupported source_db type.

  • If a destination specifies a connector ref that is unsupported, raise ValueError with a message containing the text Unsupported destination_db type.

  • If a postgres destination lacks its mandatory table_name field, raise KeyError referring to the missing key table_name (the exception string must contain 'table_name').

Note on Naming

The system contains exactly one job class; that class must be named Job (not BaseJob). The job objects placed in jobs are instances of this single job type and expose the run() method described above.

Documentation

Update the project README so that it reflects configuration (including query IDs and optional parameters) now being provided via YAML config files rather than environment variables, and indicate which config parameters are optional (query_engine, poll_frequency, parameters).

Location of Test Fixtures

Config fixtures are kept under tests/fixtures/config/. Ensure the test support package (tests/__init__.py) exposes a config_root path that points to tests/fixtures/config, defined relative to the existing fixtures_root.

These fixture files must exist under tests/fixtures/config/:

  • basic.yaml — two well-formed jobs (one dune→postgres job that has parameters, and one postgres→dune job).
  • dune_to_postgres.yaml — one well-formed dune→postgres job with table_name in its destination.
  • postgres_to_dune.yaml — a single well-formed postgres→dune job.
  • buggy.yaml — a dune→postgres job in which the postgres destination leaves out the mandatory table_name.
  • unsupported_source.yaml — a job that has sqlite as its source ref.
  • unsupported_dest.yaml — a job that has sqlite as its destination ref.

All YAML values in the fixtures should be written unquoted.

Task Specification: Supporting SQL Files in the Postgres Source Query Configuration

Summary

The Postgres source configuration accepts a query_string value. This value must be interpreted such that, when it refers to a .sql file, the file's contents are loaded and used as the query. If the referenced .sql file does not exist, configuration loading must fail with a clear error.

Public API Affected

src.config.RuntimeConfig
  • Class method: RuntimeConfig.load_from_yaml(path)
    • path is a filesystem path pointing to a YAML configuration file (accepts a pathlib.Path, including an absolute path).
    • Returns a RuntimeConfig instance whose jobs attribute is a list of the parsed jobs (len(conf.jobs) reflects how many jobs the YAML defines).

Configuration Format

At the top level, the YAML configuration has a jobs list. Each job contains a source section and a destination section. When a source specifies ref: postgres, its section includes:

  • table_name: string
  • if_exists: string (e.g. append)
  • query_string: string

Required Behavior for query_string

When a configuration is loaded in which the Postgres source's query_string ends in .sql, that value is treated as a path to a SQL file, resolved relative to the current working directory. Loading must:

  1. File exists: Read the contents of the file and use them as the effective query for that source. Loading completes successfully, and the resulting RuntimeConfig is produced without error.

  2. File missing: When the referenced .sql file does not exist, load_from_yaml must raise a RuntimeError.

The .sql file is resolved relative to the process's current working directory at load time (i.e., a bare filename such as foo.sql is resolved against the CWD).

Edge Cases and Notes

  • The .sql file may contain SQL that spans multiple lines (e.g., a SELECT statement covering several lines and terminated by a semicolon).
  • It is during configuration loading itself (parsing the YAML into jobs and resolving the SQL file) that the missing-file RuntimeError must be raised — no separate execution step is required to trigger it.

Environment

Configuration loading runs in an environment in which the DUNE_API_KEY and DB_URL environment variables are set. These are consumed as part of loading but otherwise have no effect on the SQL-file resolution behavior described above.
