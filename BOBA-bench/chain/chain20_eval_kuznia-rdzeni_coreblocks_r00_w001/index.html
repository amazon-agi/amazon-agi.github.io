Task: Reservation Station (RS) Module Implementation

Overview

Making use of the CoreBlocks transaction framework, a hardware Reservation Station is to be implemented as an Amaranth Elaboratable. Instructions that are waiting for their source operands are buffered by this module; it also keeps track of which entries are ready to execute and provides operand forwarding by way of broadcast updates.

Location and Construction of the Module

In the module coreblocks.rs, a class RS is to be created.

class RS(Elaboratable):
    def __init__(self, gen_params: GenParams) -> None:
        ...

A GenParams object (from coreblocks.genparams) is what the constructor receives. There are 2**gen_params.rs_entries_bits entries in the RS. Construction of GenParams has already taken place elsewhere, with parameters such as rs_entries (rs_entries_bits is derived from it by the constructor).

Record Layouts

The record layouts listed next have to be added to the RS layout collection (GenParams's get(RSLayouts) / the object exposed as rs_layouts in existing code). Because other components reference the names given here, those names must be used:

  • select_out — the output layout for the select method; rs_entry_id is its field.
  • insert_in — the input layout for the insert method; its fields are rs_entry_id and rs_data, and rs_data is a nested record whose fields are: rp_s1, rp_s2, rp_dst, rob_id, opcode, s1_val, s2_val.

(select_out and insert_in, respectively, replace the layouts formerly named rs_allocate_out and rs_insert_in; in the insert input, the instruction payload is now nested under rs_data.)

Internal State (must be observable)

An indexable attribute data must be exposed by the RS; it is a list consisting of 2**rs_entries_bits records. What each record data[i] exposes:

  • rec_reserved — a 1-bit flag: the entry is reserved (claimed by select), though it is not necessarily filled.
  • rec_full — a 1-bit flag: a valid instruction is held in the entry.
  • rec_ready — a 1-bit flag: all operands of the instruction in the entry are ready.
  • rs_data — a record whose fields are rp_s1, rp_s2, rp_dst, rob_id, opcode, s1_val, s2_val.

Initially, every flag of every entry is 0, and rs_data likewise begins cleared (0).

Transactional Methods

The transactional methods listed below must all be exposed by the RS, and each one is usable via an AdapterTrans.

select
  • Output: a record that conforms to select_out (field rs_entry_id).
  • Operation: an entry that is not reserved (rec_reserved == 0) is found; that entry is then marked reserved (rec_reserved becomes 1), and its index is returned in rs_entry_id. If several free entries are available, the lowest index is the one that gets chosen.
  • Ready condition: the method is ready (select.ready == 1) if and only if at least one entry is not reserved. select.ready == 0 holds once every entry is reserved.
insert
  • Input: a record that conforms to insert_in (fields rs_entry_id, rs_data).
  • Operation: the given rs_data is written into data[rs_entry_id].rs_data; besides this, data[rs_entry_id].rec_full is set to 1, and data[rs_entry_id].rec_reserved is set to 1 as well.
  • The entry's rec_ready must be assigned 1 if and only if both source physical register tags are 0 (rp_s1 == 0 and rp_s2 == 0); in every other case it is assigned 0.
update
  • Input: a record whose fields are tag and value.
  • Operation: the result of a completed physical register gets broadcast. In each full entry, every source operand whose physical register tag is equal to tag is handled in the following way:
    • That operand's source-register field (rp_s1 or rp_s2) is given the value 0.
    • value is stored in the value field that corresponds to it (s1_val or s2_val).
  • This takes effect simultaneously for all matching operands across all entries (one update can act on both rp_s1 and rp_s2 of the same entry, and it can also act on multiple entries).
  • After an update has been applied, an entry becomes ready (rec_ready == 1) as soon as both of its source tags are 0.
take
  • Input: a record whose field is rs_entry_id.
  • Output: the rs_data record that the requested entry holds (fields rp_s1, rp_s2, rp_dst, rob_id, opcode, s1_val, s2_val).
  • Operation: the rs_data stored in data[rs_entry_id] is returned, and that entry is freed — its rec_reserved, rec_full, and rec_ready flags are cleared (so the slot becomes selectable once more).
  • Ready condition: take.ready == 1 holds if and only if at least one entry is both full and ready (rec_full == 1 and rec_ready == 1); in every other case take.ready == 0.
get_ready_list
  • Output: a record whose field ready_list is a bit vector with a width equal to the number of entries.
  • Operation: bit i of ready_list equals 1 if and only if data[i] is full and ready (rec_full == 1 and rec_ready == 1); the entry with the lowest index is the one bit 0 stands for.

References to the Methods

Exactly these attribute names must be used when the module exposes the methods: rs.select, rs.insert, rs.update, rs.take, rs.get_ready_list, so that adapters can wrap them. A ready signal (select.ready, take.ready) that reflects the readiness conditions given above must also be exposed by each exposed method.

Notes on Behavior and Edge Cases

  • select.ready == 1 and take.ready == 0 are the values seen immediately after construction.
  • An entry is reserved, but not made full, by a select; making it full is what a subsequent insert into that entry does.
  • As soon as every entry is reserved, select.ready falls to 0. When a take frees an entry, select.ready is restored to 1, and the freed (lowest available) index becomes selectable once more.
  • Inserting an instruction whose source tags are both already 0 makes that instruction ready immediately (and hence takeable).
  • What the rec_ready flag reflects is whether both source operands are available, and it must be updated in response to both insert and update.

Compatibility with Downstream Code

An RS is constructed by other code, which wraps rs.select and rs.insert in adapters that are built on the select_out and insert_in layouts. In the output that select/insert produce downstream, the instruction payload is placed under a nested rs_data key, with a top-level rs_entry_id key sitting alongside it. Ensure that the layouts and the nesting described above are honored.

Further Requirements

  • The general rule is that take returns the rs_data as currently stored; as an exception to it, the output fields rp_s1 and rp_s2 of take must contain the source tags that the most recent insert for that entry provided. Broadcast update operations must still clear the observable internal data[i].rs_data.rp_s1 and rp_s2 fields to zero; even so, the insertion-time tags returned by a later take must not be altered by them.

Task: Implementation of the Wakeup/Select Transaction Component

Summary

A new module, coreblocks/wakeup_select.py, is to be created; inside it, a hardware component called WakeupSelect is defined. It orchestrates three transactional methods that are provided externally; using them, it chooses an entry that is ready from a reservation station (RS), takes that entry's data, and issues the data downstream.

In addition, a test-support helper that already exists is to be extended (see the "Supporting Change" section below).

Public Interface

coreblocks/wakeup_select.py

This module is to contain a class named WakeupSelect; the class is an Amaranth Elaboratable.

Its constructor has this signature:

WakeupSelect(*, get_ready, take_row, issue)

Each of the three parameters is a transactional Method object — of the kind produced by the transactions framework (for instance, the .iface of an Adapter) — and each one carries the contract set out below:

  • get_ready: has no meaningful input arguments. The record it returns has a single field, data, which is a bit-vector; the width of that bit-vector equals the number of RS entries. Each bit indicates the readiness of the corresponding RS entry. On any given cycle, this method may or may not be ready to run; in a cycle where it is not ready, selection should not take place.

  • take_row: its single input argument is an index that picks out one RS entry (the index is ceil(log2(rs_entries)) bits wide, i.e. enough bits to address any RS entry). Its return value is a record describing the entry being taken (the "take_out" layout).

  • issue: its input is a record in the "take_out" layout (the same shape that take_row returns), and it has no meaningful output.

WakeupSelect must elaborate into a module in which a single transaction is defined, and that transaction implements the behavior described below.

Behavior to Implement

Each time WakeupSelect is activated, it carries out the steps below as a single atomic transaction:

  1. Obtain the vector of ready bits by calling get_ready.
  2. Out of those ready bits, pick the index of the last (highest-index) entry that has its ready bit set.
  3. Using the index picked in step 2, call take_row, which supplies the entry data.
  4. Call issue, handing it the entry data obtained from take_row.

The transaction must not proceed except when get_ready can be run (i.e. it is enabled/ready). Should get_ready be unavailable, or should no ready bit be set, the transaction performs neither a take nor an issue.

For a single selected entry, the selection, the take, and the issue all occur within one and the same transaction step; as a result, the outcome of a given take_row call is forwarded to issue during that same activation.

Layouts and Sizing

Generation parameters (GenParams) together with RSLayouts (coreblocks.layouts) are the source of the layouts and sizing. The relevant quantities:

  • gen_params.rs_entries: the count of RS entries (the width of the get_ready data field).
  • gen_params.rs_entries_bits: the number of bits required to index an RS entry (the width of the take_row input).
  • RSLayouts.take_out: the record layout for an entry being taken/issued (serving as the return type of take_row and the input type of issue).

From the methods/layouts it is given, WakeupSelect must derive the widths it needs; and when it is instantiated with methods constructed from these layouts and sizes (e.g. rs_entries=16, target "rv32i"), integration must work correctly.

Correctness Guarantees Under Test

When the component is driven so that get_ready reports at least one ready entry, while take_row/issue are continuously available, the following holds:

  • The index given to take_row always refers to an entry that is genuinely ready.
  • The exact record that a take_row call returns and the exact record forwarded to the corresponding issue call are one and the same (contents preserved, no reordering, one-to-one correspondence).
  • Across a run, the count of entries issued and the count of entries that were made ready and subsequently taken are equal (no entries are dropped or duplicated).

If get_ready reports no ready entries (or is disabled), no take_row and no issue occur.

Supporting Change

The input-setting helpers in test/common.py are to have their accepted value type broadened, so that the value of a record field may be an arbitrary ValueLike (Amaranth signal/value-like) object alongside plain ints:

  • Add a type alias RecordValueDict = Mapping[str, Union[ValueLike, "RecordValueDict"]], importing ValueLike from coreblocks._typing.
  • For set_inputs(values, field), the type of the values parameter becomes RecordValueDict.
  • For TestbenchIO.call_init(self, data={}), the type of the data parameter becomes RecordValueDict.

The behavior of these helpers at runtime does not change: nested dicts cause recursion into sub-records, and a value that is not a dict is assigned to the corresponding field; the sole purpose of the change is to accept ValueLike values (such as Cat(...) expressions) as field values.

Placement and signature

Add a class named ManyToOneConnectTrans to coreblocks.transactions.lib.

Constructor (keyword arguments as they are used):

ManyToOneConnectTrans(get_results: list[method], put_result: method)
  • get_results: a list of "source" methods. When a source method is called, it returns one data record (the record layout being transported is its output layout).
  • put_result: a single "sink" method. Its input layout is a match for the record layout that the source methods produce.
Behavior that is required

ManyToOneConnectTrans is an elaboratable (module) whose role is the continuous serialization of records produced by any of the source methods into the single sink method:

  • For each source method in get_results, whenever that source can produce a record and the sink put_result can accept one, the record taken from that source must be forwarded unchanged to put_result.
  • The one sink is where records from all sources are funneled. Over the lifetime of a run, delivery to the sink must happen exactly once for every record that a source yields, with no loss and no duplication.
  • There is no constraint on the ordering of records across different sources; only completeness and one-to-one delivery of every record matter. For each record, all field values must be preserved exactly.
  • An arbitrary number of source methods must be supported by the element, including a single source and multiple (e.g. four) sources running concurrently.
Behavioral notes based on usage
  • The cadence at which sources produce records is arbitrary and irregular (including idle gaps). The connector must simply move any record that is available to the sink whenever the sink is ready; it must not require the sources to be ready simultaneously.
  • A record layout that is used with this element is an arbitrary field list, such as [("field1", 14), ("field2", 3)]; the element must be layout-agnostic and carry whatever record shape the methods connected to it use.

Overview

Add improved generation of GTKWave save files (.gtkw) for the VCD traces produced during Amaranth simulation. Trace descriptions must support nested mappings and iterables, so that the generated GTKWave view can mirror a hierarchy provided by the caller. Also establish a debug_signals() convention through which transactional adapters, along with their wrappers, expose useful trace structures.

The work consists of the following:

  2. the module test.gtkw_extension, providing trace flattening and VCD/GTKW writing APIs;
  3. debug_signals() support on transactional adapters and on TestbenchIO; and
  4. integration of hierarchical and lazily generated traces into TestCaseWithSimulator.runSimulation.

1. The public DebugSignals type

Define DebugSignals as a public type alias in coreblocks.transactions.core. It must be importable via:

from coreblocks.transactions.core import DebugSignals

DebugSignals describes a recursive trace structure whose nodes may be:

  • an Amaranth Signal;
  • an Amaranth Record;
  • a Mapping[str, DebugSignals], in which each string key is a group name; or
  • an Iterable[DebugSignals].

The alias must be broad enough to annotate any nesting of these forms — including a single signal or record, a mapping of structures, and iterable collections of structures.

2. The test.gtkw_extension module

Create the module test.gtkw_extension, which must be importable. It must expose the public functions flatten and write_vcd_ext.

2.1 Precedence used for traversal

Flattening and GTKWave hierarchy generation must both classify each node in this exact runtime order:

  1. Mapping;
  2. generic Iterable;
  3. Record;
  4. leaf handling.

This ordering is part of the public behavior:

  • A mapping is traversed by way of its values/items rather than through generic mapping iteration.
  • When a Record also satisfies the generic Iterable check, it is handled as an iterable. Its elements are traversed in iteration order, and no record-specific field traversal and no record-named group are applied, even when the record has multiple fields.
  • Record-specific behavior applies only to a Record that has not already been handled as a mapping or an iterable.
2.2 flatten(traces)

flatten is a generator that yields leaf objects recursively, in depth-first order.

For every node:

  1. For a Mapping, recurse into each value in mapping iteration order. flatten ignores the mapping keys.
  2. Otherwise, if the node is an Iterable, recurse into each element in iteration order.
  3. Otherwise, if the node is a Record, recurse into record.fields.values() in field order.
  4. Otherwise, yield the node itself as a leaf.

The traversal must support arbitrary nesting. Valid DebugSignals structures ultimately contain leaves that are traceable signals.

2.3 write_vcd_ext(engine, vcd_file, gtkw_file, traces)

    ...

Parameters:

  • engine: an Amaranth pysim engine that exposes engine._fragment, the mutable list engine._vcd_writers, and engine.now;
  • vcd_file: the path or filename of the VCD output;
  • gtkw_file: the path or filename of the GTKWave save-file output; and
  • traces: the hierarchical trace structure in its original form.

The writer must extend the behavior of Amaranth's private amaranth.sim.pysim._VCDWriter. Retain the original, unflattened structure separately for the purpose of GTKWave hierarchy generation.

On entry to the context, append the new writer to engine._vcd_writers. On exit from the context, including an exceptional exit:

  1. finalize the writer at the current engine.now timestamp; and
  2. remove that writer from engine._vcd_writers.

The cleanup must not suppress an exception raised inside the context.

2.4 Finalization of VCD and GTKWave

Finalization must retain the observable behavior of the base VCD writer while replacing the flat GTKWave trace list with the hierarchy described below:

  • close/finalize the VCD stream, using the supplied current timestamp;
  • make the GTKWave save file reference the filename of the VCD output together with its final file size;
  • set the GTKWave zoom markers to -21;
  • open the tree at "top";
  • emit hierarchical traces derived from the original, unflattened traces; and
  • close the GTKWave and VCD output files.

Generate the GTKWave hierarchy recursively, following the precedence given in section 2.1:

  1. Mapping: for every (key, value) pair, open a GTKWave group whose name is exactly the string key, then recurse into value inside that group. The mapping iteration order determines the order of groups.
  2. Generic iterable: recurse into every element in iteration order, without adding a group.
  3. Record not handled previously:
    • when it has more than one field, open a group named exactly record.name, then recurse through record.fields.values() in field order;
    • when it has exactly one field, recurse directly into that field, adding no record group;
    • when it has zero fields, emit nothing.
  4. Signal: emit a GTKWave trace using the signal's dotted hierarchical VCD name. If the signal width is greater than one and the signal has no decoder, append [N:0], where N is width - 1. Do not append a range, either for a one-bit signal or for a signal with a decoder.

In accordance with the supplied structure, groups must nest to arbitrary depth.

Task: Adding Conflict Priorities to the Transaction System

Overview

Extend the mechanism for transaction/method conflicts in the transactions framework so that a conflict between two transactions (or two methods) can carry a priority. This priority governs which of the two conflicting parties is allowed to execute when both of them request execution in the same cycle.

Public API to Be Implemented

ConflictPriority (in coreblocks.transactions.core)

Introduce a new enumeration ConflictPriority, which is importable as:

It must contain exactly these three members:

  • ConflictPriority.UNDEFINED
  • ConflictPriority.LEFT
  • ConflictPriority.RIGHT
add_conflict with a priority

An add_conflict method that accepts an optional priority argument must be exposed by both Transaction and Method:

def add_conflict(self, other, priority: ConflictPriority = ConflictPriority.UNDEFINED) -> None
  • In the case of a Transaction, other is another Transaction.
  • In the case of a Method, other is another Method.

Calling a.add_conflict(b, priority) has the effect of registering a conflict between a and b. If a priority is given, a is the left party and b is the right party of that conflict relation.

It is permitted to make these calls after the transaction/method bodies have been defined (i.e., after the transactionContext() block), and their effect must be honored during elaboration.

Behavior Requirements

Two transactions (or two methods, each invoked from inside its own transaction body) are in conflict: in any given clock cycle, at most one of them may execute. Each party has a "request"/"ready" signal indicating whether it wants to execute this cycle. If only one party requests, that party is the one that executes. When both request in the same cycle, the priority governs how the conflict is resolved:

  • ConflictPriority.LEFT: the left party (the one on which add_conflict was called) must be the one that executes; the right party must not execute.
  • ConflictPriority.RIGHT: the right party (the argument passed to add_conflict) must be the one that executes; the left party must not execute.
  • ConflictPriority.UNDEFINED: exactly one of the two must execute (the choice is left unconstrained), but never both and never neither when at least one requests.

In all cases, whenever at least one party requests execution, exactly one party executes — the two parties are mutually exclusive: they are never both idle when at least one is requesting, and never both active simultaneously.

Mechanics of conflict resolution

For methods, a method "executes" in a cycle when it is both ready (its ready signal is asserted) and is called by a transaction that has been granted execution. Conflicts on methods propagate to the transactions that call those methods: if two methods conflict, the transactions invoking them are mutually exclusive, under the same priority semantics as above (the transaction calling the left method acts as the left party, and the transaction calling the right method as the right party).

Priority Consistency / Detecting Cycles

A priority places an ordering constraint on which party may execute. Across all registered conflicts, these ordering constraints must be mutually consistent (i.e., form a valid partial order). If the registered priorities contradict one another — that is, they form a cycle in the "must-take-priority-over" ordering — the configuration is unsatisfiable and elaboration must fail.

Specifically, if a conflict from a to b with a directional priority (LEFT or RIGHT) is registered, and a conflict from b to a with a directional priority is also registered, this creates a contradictory cycle. In that situation, elaboration must raise graphlib.CycleError.

When both conflicting relations use ConflictPriority.UNDEFINED, no ordering constraint is imposed; consequently no cycle exists and elaboration must succeed normally.

Summary of the Guarantees the Implementation Must Provide

  1. An enum named ConflictPriority exists in coreblocks.transactions.core, with the members UNDEFINED, LEFT, RIGHT.
  2. Transaction.add_conflict and Method.add_conflict accept an optional second positional priority argument whose default is ConflictPriority.UNDEFINED.
  3. Per cycle, transactions/methods in conflict are mutually exclusive: never both active, and never both idle when at least one requests.
  4. LEFT assigns execution priority to the caller of add_conflict; RIGHT assigns it to the argument; UNDEFINED leaves the choice free (yet still exactly-one).
  5. Contradictory directional priorities (a directed priority cycle between two parties) cause elaboration to raise graphlib.CycleError; configurations without contradictions (two mutual UNDEFINED conflicts included) elaborate successfully.

  • First-in-first-out order must be preserved by the FIFO: elements are returned in the same sequence in which they were initialized or successfully written.
  • Upon reset, the values found in the FIFO are exactly those of init, arranged in the order described above.
  • One element is appended at the back by every successful write.
  • One element from the front is returned and removed by every successful read.
  • Occupancy must never go above depth.
  • Long interleavings of operations and arbitrary delays must not result in elements being lost, duplicated, or reordered.
Concurrent Operations

Requests for read, write, and clear may be active at the same time within a single cycle.

  • read and write are compatible: when both methods are available, both may complete during a single cycle. The element that the read returns is the one occupying the front before the cycle, and the written element is appended at the back. Starting from a queue of [front, ...rest] before the cycle, a successful read and a successful write of new that happen simultaneously return front and leave the queue as [...rest, new].
  • A clear that has completed is atomic, and it is mutually exclusive with read and write operations that have completed. In a cycle where clear completes, neither read nor write may complete: the front element as it stood before the clear is not returned, writes requested concurrently are neither accepted nor retained, and the FIFO ends up empty.
  • If arbitration picks an eligible read, an eligible write, or both, with a clear request also active, then clear has not completed in that cycle. A successful read or write takes effect as usual, and the clear may complete in a later cycle. The FIFO API does not single out any particular winner between these conflicting requests; whether an operation occurred is determined by callers from its transactional completion.

Consequently, every completed clear marks an unambiguous boundary: all elements accepted before it and not already read are discarded, and an element can remain after it only if its write completes later.

Integration into the Core

In coreblocks/core.py, both the type and the construction of Core.free_rf_fifo must be changed so that it becomes a BasicFifo. It must continue to expose write, read, and clear, which must behave as specified above.

Given phys_regs_bits = n, build the free-register FIFO as follows:

  • the element width is n bits;
  • the capacity equals 2**n; and
  • the initial contents at reset time are 1, 2, ..., 2**n - 1, in that order.

Hence physical register identifier 0 does not belong to the initial free set. The core's free-register FIFO already holds every valid nonzero free physical-register identifier immediately after reset, and 1 is the first one available. To have this FIFO populated before normal operation, the core must require neither external writes nor a separate initialization method call.

  • Once registration has happened, __getattr__(name) returns the TestbenchIO mapped to name. A caller can therefore reach a wrapped method as circuit.<method_name> and use the standard TestbenchIO call interface.
  • debug_signals() returns a list that contains the debug_signals() result of every registered TestbenchIO, ordered by the mapping's iteration order.

4. Forwarder

Add the Amaranth Elaboratable class Forwarder to coreblocks.transactions.lib. It must be available both through direct import and through the module's wildcard-import surface.

Construction
Forwarder(iosize)

iosize denotes the bit width of the payload.

Interface

A Forwarder exposes the following two Method attributes:

  • write: its input layout is [('data', iosize)], and its return value is empty.
  • read: its input is empty, and its output layout is [('data', iosize)].

In other words, write accepts {"data": value} and read returns {"data": value}.

Cycle-visible behavior

Forwarder acts as a one-element FIFO that has combinational forwarding and one overflow-storage slot.

Empty-state behavior
  • A read without a simultaneous write is not accepted.
  • A write without a simultaneous read is accepted, and its payload is retained in the overflow slot.
  • When write and read are invoked together, both calls are accepted. read returns that cycle's write.data directly, and the overflow slot stays empty.
Buffered-state behavior
  • For as long as the overflow slot is full, write is not ready.
  • A read is accepted, returns the retained payload, and empties the slot.
  • If read and write are attempted together while the slot is full, the read succeeds whereas the write does not; the attempted write is neither forwarded nor retained.
  • Only after the buffered value has been drained does forwarding become available again.

Through TestbenchIO, an accepted call produces a non-None result — including the empty record returned by an accepted write — whereas a call not accepted in that cycle produces None when queried non-blockingly.

Streaming correctness

For a producer that writes 0, 1, 2, ... and a consumer that reads independently, arbitrary stalls on either side must not lose, duplicate, or reorder values. The values returned by read must exactly match the sequence of accepted writes.

5. Compatibility of FIFO

FIFO must remain importable from coreblocks.transactions.lib and must keep its existing transactional FIFO interface. In particular, the compatibility form with an integer layout must support:

FIFO(iosize, depth=...)

in which iosize is the width of a single data field and depth is the buffering capacity. Support that already exists for record layouts and for the established constructor options must not be narrowed.

For this integer-layout form:

  • write accepts {"data": value}.
  • read returns {"data": value}.
  • Only when the queue has capacity is write accepted.
  • Only when the queue contains an item is read accepted.
  • The values that are accepted are returned in FIFO order.
  • A sequence 0, 1, 2, ... must be returned unchanged when producer and consumer stall arbitrarily and independently, without loss, duplication, or reordering.

6. LSUDummy

Add an Amaranth Elaboratable class named LSUDummy in the module coreblocks.lsu.dummyLsu:

from coreblocks.lsu.dummyLsu import LSUDummy
Construction
LSUDummy(gen, bus)
  • gen is an instance of GenParams.
  • bus is a WishboneMaster from coreblocks.peripherals.wishbone.
  • The supported configuration constructs the bus in the following way:
bus = WishboneMaster(
    WishboneParameters(data_width=gen.isa.ilen, addr_width=32)
)

Memory operations are carried out through this Wishbone master.

Methods and layouts

LSUDummy exposes the five Method attributes select, insert, update, get_result, and commit.

select

select takes no meaningful input and returns a record that contains rs_entry_id.

  • It is ready whenever the unit's single slot is free.
  • The call reserves that slot for a subsequent insert.
  • It always returns rs_entry_id == 0 when accepted.
insert

insert accepts a record containing rs_data and rs_entry_id. The instruction found in rs_data contains:

  • rp_s1, rp_s2: physical source tags of width gen.phys_regs_bits.
  • rp_dst: physical destination tag.
  • rob_id: reorder-buffer identifier of width gen.rob_entries_bits.
  • exec_fn: a nested record with op_type, funct3, and funct7.
  • s1_val, s2_val: source operand values.
  • imm: immediate value.

A value of zero for rp_s1 or rp_s2 means that this source is already available out of the corresponding supplied value. A tag that is nonzero means the source is pending.

insert must accept the instruction for the slot that is currently reserved, regardless of the rs_entry_id supplied. The field must not reject or suppress insertion; in particular, rs_entry_id == 1 is valid even though select reports zero.

update

update accepts the following:

{"tag": ..., "value": ...}

For each pending source tag that is nonzero and equal to tag, it stores value into the corresponding source value and marks that source ready. Updates for source 1 and for source 2 may arrive in either order. If both pending sources carry the same tag, one matching update resolves both of them.

get_result

get_result returns the functional result layout, which includes at least:

  • result
  • rob_id
  • rp_dst

rob_id and rp_dst are echoed back from the inserted instruction. For a load, result holds the processed load value. For a store, result is present, but its value is unconstrained.

Readiness differs between loads and stores:

  • A load result becomes ready only after the read response from Wishbone has been received and processed.
  • A store result becomes ready as soon as both operands are resolved and the store address, the select mask, and the positioned write data have been computed. Consuming this result must be possible before commit and before the Wishbone write is acknowledged.

A store's pending memory operation is not discarded by consuming its result.

commit

commit accepts a record that contains rob_id. For a store, the actual Wishbone write is authorized only by a commit that matches the pending instruction's rob_id. Before that matching commit, no store write may be issued. commit is not required for loads.

Operand readiness and effective address

An operation proceeds only after both of its sources are ready:

  • A source with a physical tag of zero is immediately ready, taking its value from the inserted sX_val.
  • A source with a nonzero physical tag becomes ready upon a matching update.

Once resolved, the effective byte address is:

s1_val + imm

The store payload is taken from the resolved s2_val.

Access size, bus address, and select mask

The access width is selected by exec_fn.funct3:

funct3 Access width
Funct3.B, Funct3.BU 1 byte
Funct3.H, Funct3.HU 2 bytes
Funct3.W 4 bytes

Every Wishbone transaction uses the word-aligned address obtained by clearing the two least-significant bits of the effective address:

bus_addr = (s1_val + imm) & ~0x3

The Wishbone sel mask is derived from the width and from the byte offset within that word:

  • Byte: 0x1 << (effective_address % 4).
  • Halfword: 0x3 << (effective_address % 4).
  • Word: 0xF.
Load behavior (Opcode.LOAD)

A load issues a Wishbone request with the following:

  • addr equal to the aligned address,
  • we == 0,
  • sel equal to the computed mask,
  • write data == 0 exactly.

When a data word comes back from the bus:

  1. Find the bit index of the least-significant set bit of the mask; this index is the selected byte offset.
  2. Shift the returned word right by byte_offset * 8.
  3. Keep the low mask.bit_count() * 8 bits.
  4. For Funct3.B and Funct3.H, perform sign extension of the extracted byte or halfword to 32 bits.
  5. For Funct3.BU, Funct3.HU, and Funct3.W, perform zero extension of the extracted value to 32 bits.

The 32-bit value obtained this way is returned as get_result.result.

Store behavior (Opcode.STORE)

After both of its operands become ready, a store computes and retains its aligned address, select mask, and write data. The low bits of its source are positioned into the selected byte lanes:

  • Byte masks 0x1, 0x2, 0x4, and 0x8 place s2_val & 0xFF at shifts 0, 8, 16, and 24 respectively.
  • Halfword masks 0x3 and 0xC place s2_val & 0xFFFF at shifts 0 and 16 respectively.
  • A word mask 0xF uses the full low 32 bits of s2_val.

The corresponding Wishbone request uses the retained aligned address and the retained mask, with we == 1.

The lifecycle of a store is as follows:

  1. Both operands are resolved and the complete request is computed.
  2. get_result is made available for the reorder step, returning the instruction's rob_id and rp_dst.
  3. All pending store information is preserved even if get_result is consumed.
  4. Wait for a matching commit; a bus write must not be issued before it.
  5. After that commit, issue the retained write and retain the request through the Wishbone acknowledgement.
  6. The pending store is completed only after the acknowledgement.
Capacity and ordering
  • The unit handles one instruction at a time.
  • select reserves the sole slot; another selection is unavailable for as long as that operation, or a retained store — committed or uncommitted — remains pending.
  • After insert and any updates that are required, progress happens automatically, subject to the method and Wishbone handshakes.
  • A load releases its operation after its response/result lifecycle has completed.
  • A store remains pending after its result has been published and is not released until its authorized Wishbone write has completed.
Mask assumptions

For the accesses to which the extraction and positioning rules apply, the set bits in the mask are contiguous. The bit span of the mask equals the index of its least-significant set bit plus its population count.

Specification of the Task

In this task, you implement changes across a hardware description codebase that is built on the Amaranth HDL library. The work divides into two independent parts: (1) a utility that collects debug signals automatically, replacing an approach based on a mixin, and (2) a restructuring of the scheduler's reservation-station handling so that it supports multiple reservation stations, selected according to the instruction's operation type.

Part 1: Utility for Automatic Debug Signals

Public Interface

Expose the following names in the package coreblocks.utils, so that they can be imported directly as from coreblocks.utils import ValueLike, auto_debug_signals:

  • ValueLike — the type alias that already exists (at present importable from coreblocks.utils._typing); it must also be re-exported from coreblocks.utils.
  • auto_debug_signals(thing) — a function which, when given an object (typically an amaranth Elaboratable), returns a structure of debug signals derived automatically from that object.
Behavior

auto_debug_signals(thing) examines an object and produces a collection of debug signals gathered from that object's attributes and submodules; the collection is suitable for passing as the debug-signal argument to the VCD writer of an Amaranth simulator. The value it returns must be accepted by the simulation harness (see below) as the traces/extra-signals argument.

The function is invoked lazily via functools.partial(auto_debug_signals, module) — that is, it must work when called with a single positional argument, which is the elaboratable module.

The collection must include signals that are discovered from:

  • The object's Amaranth Signal attributes.
  • Elaboratables / submodules nested inside it, recursively.
  • Array structures (arrays of records or signals), which must be traversed so that the signals they contain are included.

The AutoDebugSignals mixin class formerly found in coreblocks.utils is removed. Inheriting from it should not be required of any test-facing class or module; plain Elaboratable subclasses must work with the simulation harness without any mixin.

Integration with the simulation harness

The shared test harness (TestCaseWithSimulator.run_simulation in test/common.py) gets updated to this signature and behavior:

@contextmanager
def run_simulation(self, module: Elaboratable, max_cycles=10e4):
    ...
  • The parameter extra_signals is removed entirely.
  • If the module passed in has an attribute debug_signals, that attribute is used as the extra signals.
  • When the module has no such attribute, the extra signals are obtained by calling auto_debug_signals on the module (bound lazily via functools.partial).

As a result, auto_debug_signals must produce a valid trace argument for arbitrary plain Elaboratable instances used across the test suite. (test/common.py will import functools.)

Part 2: Scheduler Support for Multiple Reservation Stations

Component to add: RSSelection

Add a class RSSelection in coreblocks.scheduler.scheduler, constructed as follows:

RSSelection(
    gen_params,        # GenParams
    get_instr,         # Method: source of instructions (record layout SchedulerLayouts.rs_select_in)
    rs_select,         # list of (Method, set[OpType]) pairs
    push_instr,        # Method: sink for selected instructions (layout SchedulerLayouts.rs_select_out)
)

rs_select is a list, each of whose elements is a tuple (select_method, optypes):

  • select_method is a method whose output has the layout RSLayouts.select_out (it returns a field rs_entry_id).
  • optypes is a set[OpType] describing which operation types that reservation station accepts.
Behavior

The following steps are carried out repeatedly by RSSelection:

  1. Reads an instruction from get_instr. The instruction record uses the layout SchedulerLayouts.rs_select_in, which contains at least the fields:
    • opcode
    • illegal
    • exec_fn (a sub-record containing op_type, funct3, funct7)
    • regs_p (a sub-record containing rp_dst, rp_s1, rp_s2)
    • rob_id
    • imm
    • pc
  2. Using the instruction's exec_fn.op_type, it picks one reservation station from rs_select whose optypes set contains that op type. When more than one reservation station accepts the op type, the earliest matching entry in the rs_select list is the one chosen.
  3. Calls the select_method of the chosen reservation station to obtain an rs_entry_id.
  4. Pushes an output record through push_instr. The pushed record has the layout SchedulerLayouts.rs_select_out and carries all of the instruction fields plus:
    • rs_entry_id — the value the chosen select method returned.
    • rs_selected — the zero-based index (within the rs_select list) of the chosen reservation station.

Every instruction that is read must eventually appear exactly once at the output, with rs_entry_id equal to the value the corresponding selected reservation-station method returned and rs_selected equal to that station's index. The order in which outputs appear corresponds to the order in which instructions were consumed and selected. The component must operate correctly under arbitrary delays on the input, on the select methods, and on the output consumer.

Layout additions and requirements

SchedulerLayouts (retrieved via gen_params.get(SchedulerLayouts)) must provide:

  • rs_select_in — the instruction layout described earlier.
  • rs_select_out — the same fields as rs_select_in, plus rs_entry_id and rs_selected.

RSLayouts must provide select_out, which contains rs_entry_id, as well as insert_in (already in use).

Changes to GenParams

GenParams must accept a new keyword argument rs_number_bits:

GenParams("rv32i", rs_number_bits=1)
GenParams("rv32i", rs_number_bits=math.ceil(math.log2(rs_count)))

This parameter determines the size of the field used to identify a selected reservation station (rs_selected). That field must be wide enough to hold the index of any configured reservation station. When this argument is omitted, GenParams must continue to work.

The existing attributes used here must continue to be exposed by GenParams: phys_regs_bits, rob_entries_bits, rs_entries, and isa (with reg_cnt, xlen, ilen_bytes).

Changes to Scheduler

The constructor of the Scheduler class in coreblocks.scheduler.scheduler changes. It no longer takes the rs_alloc and rs_insert methods — in their place, it takes a reservation_stations argument:

Scheduler(
    get_instr,
    get_free_reg,
    rat_rename,
    rob_put,
    rf_read1,
    rf_read2,
    reservation_stations,   # sequence of reservation-station blocks
    gen_params,
)

Every element of reservation_stations is an object that exposes:

  • .select — a method whose output layout is RSLayouts.select_out (returns rs_entry_id).
  • .insert — a method whose input layout is RSLayouts.insert_in.
  • .optypes — a set[OpType] accepted by that reservation station.
Behavior

Each incoming decoded instruction is processed by the scheduler through renaming, ROB allocation, and register-file reads; the scheduler then selects a reservation station whose optypes contains the instruction's operation type (applying the same "first matching entry wins" rule as RSSelection), calls that station's .select to obtain an rs_entry_id, and finally calls that station's .insert with the fully assembled record.

For each instruction, exactly one reservation station's .select is called, and the .insert of that same station is called with the resulting entry. The .insert payload must contain the renamed register data and the ROB id in such a way that:

  • The rob_id present in the inserted data corresponds to the ROB entry allocated for that instruction.
  • The physical source registers (rp_s1, rp_s2) reflect the current state of the register-alias table at rename time.
  • The rs_entry_id matches the value that station's .select returned.

Over a stream of instructions whose op types are drawn from the union of all stations' optypes, every instruction is routed to exactly one station and inserted there exactly once. The distribution of instructions must follow op type: an instruction whose op type is accepted by only one station goes to that station; when several stations accept it, it goes to the first matching one. The scheduler must operate correctly with one, two, or three reservation stations, and also under mocked .select/.insert methods that may impose enable/delay patterns of their own.

Part 3: Core-Level Test Support (pre-existing behavior to preserve)

The full-core test elaboratable is put together as TestElaboratable(gen_params, instr_mem=<list-of-ints>), with instr_mem being a list of 32-bit instruction words (little-endian machine code) that becomes the instruction memory. The core exposes:

  • core.fetch.halt_pc — a signal which, when set to a byte address, halts fetching at that instruction.
  • io_in — an input that a TestbenchIO can call, accepting {"data": opcode}.
  • Architectural register readout through a helper that yields the current value of a given architectural register id (get_arch_reg_val(reg_id)), returning the unsigned 32-bit value.

Ensure that the core executes a stream of loaded instructions correctly. For a program that computes Fibonacci numbers, after enough cycles have run, the architectural register holding the running value must equal the expected 32-bit result.
