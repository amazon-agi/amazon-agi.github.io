Task: Implement a Reservation Station (RS) Module

Overview

Implement a hardware Reservation Station as an Amaranth Elaboratable using the CoreBlocks transaction framework. The module buffers instructions waiting for their source operands, tracks which entries are ready to execute, and supports operand forwarding via broadcast updates.

Module Location and Construction

Create a class RS in the module coreblocks.rs.

class RS(Elaboratable):
    def __init__(self, gen_params: GenParams) -> None:
        ...

The constructor receives a GenParams object (from coreblocks.genparams). The RS holds 2**gen_params.rs_entries_bits entries. GenParams is already constructed elsewhere with parameters such as rs_entries (the constructor derives rs_entries_bits from it).

Layouts

Add the following record layouts to the RS layout collection (GenParams's get(RSLayouts) / the object exposed as rs_layouts in existing code). The names below must be used because other components reference them:

  • select_out — output layout of the select method, containing field rs_entry_id.
  • insert_in — input layout of the insert method, containing fields rs_entry_id and rs_data, where rs_data is a nested record with fields: rp_s1, rp_s2, rp_dst, rob_id, opcode, s1_val, s2_val.

(The previously named rs_allocate_out and rs_insert_in layouts are replaced by select_out and insert_in respectively; the insert input now nests the instruction payload under rs_data.)

Internal State (must be observable)

The RS must expose an indexable attribute data, a list of 2**rs_entries_bits records. Each record data[i] exposes:

  • rec_reserved — 1-bit flag: entry is reserved (claimed by select) but not necessarily filled.
  • rec_full — 1-bit flag: entry holds a valid instruction.
  • rec_ready — 1-bit flag: instruction in the entry has all operands ready.
  • rs_data — a record with fields rp_s1, rp_s2, rp_dst, rob_id, opcode, s1_val, s2_val.

All flags of all entries start at 0, and rs_data starts cleared (0).

Methods (transactional)

The RS must expose the following transactional methods, each usable via an AdapterTrans.

select
  • Output: a record matching select_out (field rs_entry_id).
  • Behavior: finds an entry that is not reserved (rec_reserved == 0), marks it reserved (rec_reserved becomes 1), and returns its index in rs_entry_id. When multiple free entries exist, the lowest index is chosen.
  • Readiness: the method is ready (select.ready == 1) if and only if at least one entry is not reserved. When every entry is reserved, select.ready == 0.
insert
  • Input: a record matching insert_in (fields rs_entry_id, rs_data).
  • Behavior: writes the given rs_data into data[rs_entry_id].rs_data, sets data[rs_entry_id].rec_full to 1, and sets data[rs_entry_id].rec_reserved to 1.
  • The entry's rec_ready must be set to 1 if and only if both source physical register tags are 0 (rp_s1 == 0 and rp_s2 == 0), otherwise 0.
update
  • Input: a record with fields tag and value.
  • Behavior: broadcasts a completed physical register result. For every full entry, for each source operand whose physical register tag equals tag:
    • Set that operand's source-register field (rp_s1 or rp_s2) to 0.
    • Store value into the corresponding value field (s1_val or s2_val).
  • This applies simultaneously to all matching operands across all entries (a single update can affect both rp_s1 and rp_s2 of the same entry, and can affect multiple entries).
  • After an update, an entry becomes ready (rec_ready == 1) once both of its source tags are 0.
take
  • Input: a record with field rs_entry_id.
  • Output: the rs_data record of the requested entry (fields rp_s1, rp_s2, rp_dst, rob_id, opcode, s1_val, s2_val).
  • Behavior: returns the stored rs_data of data[rs_entry_id] and frees that entry, clearing its rec_reserved, rec_full, and rec_ready flags (so the slot becomes selectable again).
  • Readiness: take.ready == 1 if and only if at least one entry is both full and ready (rec_full == 1 and rec_ready == 1); otherwise take.ready == 0.
get_ready_list
  • Output: a record with field ready_list, a bit vector of width equal to the number of entries.
  • Behavior: bit i of ready_list is 1 if and only if data[i] is full and ready (rec_full == 1 and rec_ready == 1). Bit 0 is the lowest-indexed entry.

Method References

The module must expose these methods as attributes named exactly: rs.select, rs.insert, rs.update, rs.take, rs.get_ready_list, so they can be wrapped by adapters. Each exposed method must also expose a ready signal (select.ready, take.ready) reflecting the readiness conditions described above.

Behavioral Notes / Edge Cases

  • Immediately after construction, select.ready == 1 and take.ready == 0.
  • A select reserves an entry but does not make it full; a subsequent insert into that entry makes it full.
  • Once all entries are reserved, select.ready drops to 0. A take that frees an entry restores select.ready to 1 and the freed (lowest available) index becomes selectable again.
  • Inserting an instruction whose both source tags are already 0 makes it immediately ready (and thus takeable).
  • The rec_ready flag reflects whether both source operands are available, and must update in response to both insert and update.

Downstream Compatibility

Other code constructs an RS and wraps rs.select and rs.insert in adapters using the select_out and insert_in layouts. The output produced downstream by select/insert places the instruction payload under a nested rs_data key alongside a top-level rs_entry_id key. Ensure the layouts and nesting described above are honored.

Additional Requirements

  • As an exception to the general rule that take returns the current stored rs_data, its output fields rp_s1 and rp_s2 must contain the source tags supplied by the most recent insert for that entry. Broadcast update operations must still clear the observable internal data[i].rs_data.rp_s1 and rp_s2 fields to zero, but must not alter the insertion-time tags returned by a later take.

Task: Implement Wakeup/Select Transaction Component

Overview

Create a new module coreblocks/wakeup_select.py that defines a hardware component WakeupSelect. This component orchestrates three externally-provided transactional methods to select a ready entry from a reservation station (RS), take that entry's data, and issue it downstream.

Additionally, extend an existing test-support helper (see "Supporting Change" below).

Public API

coreblocks/wakeup_select.py

Define a class WakeupSelect that is an Amaranth Elaboratable.

Constructor signature:

WakeupSelect(*, get_ready, take_row, issue)

The three arguments are transactional Method objects (of the type produced by the transactions framework, e.g. the .iface of an Adapter). They have the following contracts:

  • get_ready: takes no meaningful input arguments; returns a record with a single field data that is a bit-vector whose width equals the number of RS entries. Each bit indicates whether the corresponding RS entry is ready. This method may or may not be ready to run on any given cycle; when it is not ready, no selection should occur.

  • take_row: takes a single input argument — an index selecting one RS entry (its width is ceil(log2(rs_entries)) bits, i.e. enough bits to address any RS entry). It returns a record describing the taken entry (the "take_out" layout).

  • issue: takes as input a record with the "take_out" layout (the same shape returned by take_row) and produces no meaningful output.

The WakeupSelect component must elaborate into a module that defines a single transaction implementing the following behavior.

Required Behavior

On each activation, WakeupSelect performs, as one atomic transaction:

  1. Call get_ready to obtain the vector of ready bits.
  2. From the ready bits, select the index of the last (highest-index) entry whose ready bit is set.
  3. Call take_row with that selected index to obtain the entry data.
  4. Call issue passing the entry data obtained from take_row.

The transaction must only proceed when get_ready can be run (i.e. it is enabled/ready). When get_ready is not available, or when no ready bit is set, the transaction does not perform a take or issue.

The selection, take, and issue for a single selected entry all happen together as part of the same transaction step, so that a given take_row result is forwarded to issue in the same activation.

Data Shapes / Parameters

The layouts and sizing come from the generation parameters (GenParams) and RSLayouts (coreblocks.layouts). Relevant quantities:

  • gen_params.rs_entries: number of RS entries (the width of the get_ready data field).
  • gen_params.rs_entries_bits: number of bits needed to index an RS entry (the width of the take_row input).
  • RSLayouts.take_out: the record layout describing a taken/issued entry (the return type of take_row and the input type of issue).

WakeupSelect must derive the widths it needs from the methods/layouts it is given; it must integrate correctly when instantiated with methods built from these layouts and sizes (e.g. rs_entries=16, target "rv32i").

Correctness Guarantees Exercised

When driven such that get_ready reports at least one ready entry and take_row/issue are continuously available:

  • The index passed to take_row always corresponds to an entry that is actually ready.
  • The exact record returned by a take_row call is the exact record forwarded to the corresponding issue call (contents preserved, no reordering, one-to-one correspondence).
  • Over a run, the number of entries issued equals the number of entries that were made ready and subsequently taken (no entries are dropped or duplicated).

When get_ready reports no ready entries (or is disabled), no take_row and no issue occur.

Supporting Change

  • Introduce a type alias RecordValueDict = Mapping[str, Union[ValueLike, "RecordValueDict"]] (importing ValueLike from coreblocks._typing).
  • Change the values parameter type of set_inputs(values, field) to RecordValueDict.
  • Change the data parameter type of TestbenchIO.call_init(self, data={}) to RecordValueDict.

The runtime behavior of these helpers is unchanged — nested dicts recurse into sub-records, and non-dict values are assigned to the corresponding field; the change is purely to accept ValueLike values (such as Cat(...) expressions) as field values.

Required Behavior

  • A store remains pending after result publication and is not released until its authorized Wishbone write has completed.
Mask assumptions

For accesses to which the extraction and positioning rules apply, set bits in the mask are contiguous. The mask's bit span equals the index of its least-significant set bit plus its population count.

You are implementing changes across a hardware description codebase built on the Amaranth HDL library. The work has two independent parts: (1) an automatic debug-signal utility that replaces a mixin-based approach, and (2) a restructuring of the scheduler's reservation-station handling to support multiple reservation stations selected by instruction operation type.

Part 1: Automatic Debug Signals Utility

Public API

In the package coreblocks.utils, expose the following names so they can be imported directly as from coreblocks.utils import ValueLike, auto_debug_signals:

  • ValueLike — the existing type alias (currently importable from coreblocks.utils._typing); it must also be re-exported from coreblocks.utils.
  • auto_debug_signals(thing) — a function that, given an object (typically an amaranth Elaboratable), returns a structure of debug signals automatically derived from that object.
Behavior

auto_debug_signals(thing) inspects an object and produces a collection of debug signals gathered from its attributes and submodules, suitable for passing as the debug-signal argument to an Amaranth simulator's VCD writer. The returned value must be accepted by the simulation harness (see below) as the traces/extra-signals argument.

The function is invoked lazily via functools.partial(auto_debug_signals, module) — i.e. it must work when called with a single positional argument that is the elaboratable module.

The collection must include signals discovered from:

  • Amaranth Signal attributes of the object.
  • Nested elaboratables / submodules, recursively.
  • Array structures (arrays of records or signals) must be traversed so their contained signals are included.

The AutoDebugSignals mixin class that previously lived in coreblocks.utils is removed. No test-facing class or module should require inheriting from it; plain Elaboratable subclasses must work with the simulation harness without any mixin.

Simulation harness integration

The shared test harness (TestCaseWithSimulator.run_simulation in test/common.py) is being updated to the following signature and behavior:

@contextmanager
def run_simulation(self, module: Elaboratable, max_cycles=10e4):
    ...
  • The extra_signals parameter is removed entirely.
  • If the passed module has an attribute debug_signals, that attribute is used as the extra signals.
  • Otherwise, the extra signals are obtained by calling auto_debug_signals on the module (bound lazily via functools.partial).

This means auto_debug_signals must produce a valid trace argument for arbitrary plain Elaboratable instances used throughout the test suite. (test/common.py will import functools.)

Part 2: Multiple Reservation Stations in the Scheduler

New component: RSSelection

Add a class RSSelection in coreblocks.scheduler.scheduler, constructed as:

RSSelection(
    gen_params,        # GenParams
    get_instr,         # Method: source of instructions (record layout SchedulerLayouts.rs_select_in)
    rs_select,         # list of (Method, set[OpType]) pairs
    push_instr,        # Method: sink for selected instructions (layout SchedulerLayouts.rs_select_out)
)

rs_select is a list where each element is a tuple (select_method, optypes):

  • select_method is a method whose output has layout RSLayouts.select_out (it returns a field rs_entry_id).
  • optypes is a set[OpType] describing which operation types that reservation station accepts.
Behavior

RSSelection repeatedly:

  1. Reads an instruction from get_instr. The instruction record uses layout SchedulerLayouts.rs_select_in, which contains at least the fields:
    • opcode
    • illegal
    • exec_fn (a sub-record with op_type, funct3, funct7)
    • regs_p (a sub-record with rp_dst, rp_s1, rp_s2)
    • rob_id
    • imm
    • pc
  2. Based on the instruction's exec_fn.op_type, selects one reservation station from rs_select whose optypes set contains that op type. When more than one reservation station accepts the op type, the earliest matching entry in the rs_select list is chosen.
  3. Calls the chosen reservation station's select_method to obtain an rs_entry_id.
  4. Pushes an output record via push_instr. The pushed record has layout SchedulerLayouts.rs_select_out and carries all the instruction fields plus:
    • rs_entry_id — the value returned by the chosen select method.
    • rs_selected — the zero-based index (in the rs_select list) of the chosen reservation station.

Every instruction read must eventually appear exactly once at the output, with rs_entry_id equal to the value the corresponding selected reservation-station method returned and rs_selected equal to that station's index. Ordering of outputs corresponds to the order instructions were consumed and selected. The component must operate correctly under arbitrary delays on the input, the select methods, and the output consumer.

Layout additions/requirements

SchedulerLayouts (obtained via gen_params.get(SchedulerLayouts)) must provide:

  • rs_select_in — the instruction layout described above.
  • rs_select_out — the same fields as rs_select_in plus rs_entry_id and rs_selected.

RSLayouts must provide select_out containing rs_entry_id, and insert_in (already used).

GenParams changes

GenParams must accept a new keyword argument rs_number_bits:

GenParams("rv32i", rs_number_bits=1)
GenParams("rv32i", rs_number_bits=math.ceil(math.log2(rs_count)))

This parameter sizes the field used to identify a selected reservation station (rs_selected). It must be wide enough to hold the index of any configured reservation station. GenParams must continue to work when this argument is omitted.

GenParams must continue to expose the existing attributes used here: phys_regs_bits, rob_entries_bits, rs_entries, and isa (with reg_cnt, xlen, ilen_bytes).

Scheduler changes

The Scheduler class in coreblocks.scheduler.scheduler changes its constructor. It no longer takes rs_alloc and rs_insert methods. Instead it takes a reservation_stations argument:

Scheduler(
    get_instr,
    get_free_reg,
    rat_rename,
    rob_put,
    rf_read1,
    rf_read2,
    reservation_stations,   # sequence of reservation-station blocks
    gen_params,
)

Each element of reservation_stations is an object exposing:

  • .select — a method with output layout RSLayouts.select_out (returns rs_entry_id).
  • .insert — a method with input layout RSLayouts.insert_in.
  • .optypes — a set[OpType] accepted by that reservation station.
Behavior

The scheduler processes each incoming decoded instruction through renaming, ROB allocation, register-file reads, then selects a reservation station whose optypes contains the instruction's operation type (using the same "first matching entry wins" rule as RSSelection), calls that station's .select to obtain an rs_entry_id, and finally calls that station's .insert with the fully assembled record.

For each instruction, exactly one reservation station's .select is called, and the same station's .insert is called with the resulting entry. The .insert payload must contain the renamed register data and the ROB id such that:

  • The rob_id in the inserted data corresponds to the ROB entry allocated for that instruction.
  • The physical source registers (rp_s1, rp_s2) reflect the current register-alias-table state at rename time.
  • The rs_entry_id matches the value returned by that station's .select.

Across a stream of instructions whose op types are drawn from the union of all stations' optypes, every instruction is routed to exactly one station and inserted there exactly once. Instructions must be distributed according to op type: an instruction whose op type is accepted only by one station goes to that station; when accepted by several, it goes to the first matching one. The scheduler must operate correctly with one, two, or three reservation stations, and under mocked .select/.insert methods that may impose their own enable/delay patterns.

Part 3: Core-level test support (already-present behavior to preserve)

The full-core test elaboratable is constructed as TestElaboratable(gen_params, instr_mem=<list-of-ints>), where instr_mem is a list of 32-bit instruction words (little-endian machine code) that becomes the instruction memory. The core exposes:

  • core.fetch.halt_pc — a signal that, when set to a byte address, halts fetching at that instruction.
  • io_in — a TestbenchIO-callable input accepting {"data": opcode}.
  • Architectural register readout via a helper that yields the current value of a given architectural register id (get_arch_reg_val(reg_id)), returning the unsigned 32-bit value.

Ensure the core executes a stream of loaded instructions correctly. For a program that computes Fibonacci numbers, after running enough cycles the architectural register holding the running value must equal the expected 32-bit result. Register comparison treats values as unsigned 32-bit (mask with 0xFFFFFFFF).

GenParams("rv32i") must construct a working core configuration when rs_number_bits is not specified.
