Objective

Add a new public decorator called overrides_ignore_signature to the overrides package.

Public API

It must be possible to import the decorator directly from the package:

from overrides import overrides_ignore_signature

Required Behavior

overrides_ignore_signature is a method decorator that is applied to a method defined in a subclass. Its purpose is to mark that the decorated method overrides a method with the same name in a base (super) class, without enforcing that the signature of the decorated method is compatible with the signature of the overridden method.

Concretely, the following must succeed at class-definition time (i.e., without any error being raised):

  • A subclass defines a method that is decorated with @overrides_ignore_signature.
  • A method with the same name is defined in a base class of that subclass.
  • The decorated method in the subclass may have a signature that differs from the base class method's signature and is incompatible with it (for example, fewer parameters, different parameter types, missing *args/**kwargs).

The decorator must still verify that a method with the same name exists in one of the subclass's base classes (the fundamental "overrides" guarantee). Compared to the existing overrides decorator, the only relaxation is that signature compatibility between the overriding and overridden methods is not checked.

The decorated method must remain a normal, callable method that behaves exactly as it is written (the decorator returns the function so that it can be invoked and produces its normal return value).

Existing Behavior To Preserve

The existing overrides decorator must remain importable from the package and continue to function as it did before. The addition of overrides_ignore_signature must not alter the behavior of overrides.

Notes

  • Both overrides and overrides_ignore_signature are used as bare decorators (@overrides_ignore_signature) and are applied directly to a method.
  • Based on this task, no configuration arguments are required for overrides_ignore_signature.

Task: Disregard the First Parameter When Validating Overridden Method Signatures

Background

A Python package going by the name overrides makes a decorator available that is likewise called overrides; it can be imported as follows:

from overrides import overrides

Applying the decorator to a method written in a subclass marks that method as overriding the identically named method declared in the superclass. In the course of this, it validates signature compatibility, comparing the overriding method with the method it overrides.

The decorator accepts a keyword argument, check_at_runtime, of boolean type. Setting check_at_runtime=True means the compatibility validation involving the subclass method and the corresponding superclass method gets carried out, and (if incompatible) it raises at call/definition time, in the same way it currently behaves for the other checks.

The Change to Make

During the comparison of an overriding method's signature against the overridden method's, the first parameter must be ignored in the case of non-static methods. The rule covers both of the following:

  • Regular instance methods: by convention their first parameter is self.
  • Class methods (methods decorated with @classmethod): by convention their first parameter is cls.

The motivation: for an instance method or a class method, the subclass may legitimately give the first parameter a different type annotation than the one found in the superclass. Take instance methods as an example: the superclass's version may annotate self with the superclass type, and the overriding subclass version instead gives self the subclass type as its annotation. Class methods behave in parallel: cls may be annotated Type[SuperClass] in the superclass, while the subclass gives it Type[SubClass]. Differences of this sort in the first parameter must not make the signature-compatibility validation fail.

In concrete terms, every case below must be considered a valid override and must not raise; this also holds when check_at_runtime=True has been set and the methods get called:

  • A subclass instance method that overrides a superclass instance method, where the subclass method's one and only parameter (which is also its first), self, carries an annotation of the subclass type, while the superclass method's self is annotated with the superclass type. When this method is called on an instance of the subclass, it must succeed and return normally.
  • A subclass class method that overrides a superclass class method, where the subclass method's one and only parameter (which is also its first), cls, carries the annotation Type[Subclass], while the superclass method's cls is annotated with Type[Superclass]. When this class method is called on an instance of the subclass, it must succeed and return normally.

Behavioral Requirements, Summarized

  • With check_at_runtime=True in effect, the overrides decorator must accept an overriding instance method or class method whose first parameter carries a type annotation different from the overridden method's, without raising, as long as the remaining parameters are compatible.
  • Methods decorated like this must still be callable and behave normally (an instance method annotated so that it returns the subclass instance does return the instance; a class method annotated so that it returns None does return None).

Public API

  • overrides.overrides — the decorator itself, which supports the check_at_runtime keyword argument.

There is no need for any new public API; what must be adjusted is the existing decorator's signature-comparison behavior, so that compatibility checking no longer takes the first parameter of non-static methods into account.

Overview

The library you are working on verifies that a function/method that overrides another one has a signature compatible with the function/method being overridden. An existing signature-compatibility checker must be updated so that, during the comparison, the first positional parameter of both functions is ignored.

Public API

The checker is exposed as a function which the caller imports and then invokes:

ensure_signature_is_compatible(super_func, sub_func)
  • super_func: the function/method that gets overridden (the "supertype" signature).
  • sub_func: the function/method doing the overriding (the "subtype" signature).

Behavior:

  • When the two signatures are compatible, the function returns None (no meaningful return value).
  • When the two signatures are incompatible, it raises TypeError.

The public API also includes an overrides decorator. When it is applied to a method that overrides a method of the same name in a base class, it runs the same signature-compatibility verification between the base-class method and the overriding method. If the signatures are incompatible, applying the decorator (at class-definition time) raises TypeError; otherwise the class is defined normally.

Required Change

It is always assumed that both functions handed to the compatibility check (and both methods involved when overrides is used) have a leading positional parameter representing the bound instance/class receiver (conventionally self or cls). This first positional parameter must be entirely excluded from the compatibility comparison. Its name and its annotation are irrelevant; they must never cause an incompatibility.

In concrete terms:

  • The first positional parameter of super_func and the first positional parameter of sub_func are dropped before any comparison is performed.
  • A difference between these two leading parameters — including differing names, differing type annotations, or one being annotated and the other not — must never produce a TypeError.
  • All remaining parameters (after the first) together with the return annotations are compared under the existing compatibility rules described below.

Compatibility Rules (covering the parameters after the first, plus return types)

Once the leading receiver parameter has been removed from each signature, the remaining signatures must satisfy standard override-compatibility semantics:

Return types

  • The return annotation of the subtype must be a subtype of (compatible with / narrower than or equal to) the supertype's return annotation. Return types that are incompatible raise TypeError.

Parameters

  • The subtype must accommodate every parameter that the supertype requires.
  • Positional parameters that correspond to each other must appear in the same order/position; a reordering that changes which parameter occupies a position is incompatible.
  • The type annotations of parameters must be contravariant: a subtype parameter must accept at least everything the corresponding supertype parameter accepts (the subtype's parameter type must be a supertype of, or equal to, the supertype's parameter type). It is incompatible to narrow a parameter type.
  • Parameter kinds must be compatible: for example, a plain positional-or-keyword parameter in the supertype cannot become keyword-only in the subtype.
  • The subtype must be able to receive any parameter the supertype declares (either explicitly or via *args/**kwargs).
  • If the supertype supplies a variadic *args, the subtype must also accept arbitrary extra positional arguments in a compatible way; likewise, if the supertype supplies **kwargs, the subtype must accept arbitrary keyword arguments compatibly.
  • The subtype may add extra parameters beyond those of the supertype only if they are optional (have default values) — this covers extra normal, positional-only, and keyword-only parameters. Extra required parameters in the subtype make it incompatible.
  • The subtype is incompatible if it lacks a parameter the supertype requires.

Type-hint resolution

  • Type annotations written as string forward references (e.g., "str", "object") must be resolved to their actual types before the comparison, and they behave identically to non-string annotations.

Examples of the Leading-Parameter Rule

  • With supertype def f(self, x: str) -> object and subtype def g(self, x: object) -> str, the leading self on each side is ignored and the rest are checked normally (this pair is compatible).
  • With a supertype whose leading parameter is annotated self: int and a subtype whose leading parameter is annotated self: str, the differing annotations on the first parameter must not cause any error; only the remaining parameters and the return types are compared.

Notes

  • The comparison must keep working whether the leading parameter is called self, cls, or anything else — the name is never significant.
  • Aside from the exclusion of the first positional parameter, no behavior changes; all previously supported compatibility semantics remain in force for the remaining parameters and return types.

Task Specification: Checking Signature Compatibility

Overview

Implement a function that checks whether the signature of one callable is a compatible "subtype" of the signature of another callable, in accordance with the Liskov substitution principle for method signatures. Bound methods, unbound methods (functions accessed via the class), and static methods must all be handled correctly by the function.

Public API

Provide a function that can be imported as:

ensure_signature_is_compatible(supertype, subtype, is_static=False)
  • supertype: a callable — a function, a bound method, or an unbound method/function accessed from a class.
  • subtype: a callable — a function, a bound method, or an unbound method/function accessed from a class.
  • is_static (optional, defaults to False): a boolean flag that indicates both callables are static methods (that is, they have no implicit self/instance parameter).

When the two signatures are compatible, the function returns None; when they are not, it raises TypeError.

Rules for Compatibility

The subtype callable is compatible with the supertype callable when it can safely be substituted for the supertype. Specifically, all of the following must hold; otherwise, raise TypeError:

  1. Return type: the return annotation on the subtype must be the same as, or a subtype of, the return annotation on the supertype (covariant return). A return type that is incompatible (e.g., the supertype returns int and the subtype returns str) is an error.

  2. Parameter types: for each parameter that exists in the supertype, the corresponding parameter annotation on the subtype must accept everything the supertype's does — in other words, the subtype's parameter type must be the same as, or a supertype of, the supertype's parameter type (contravariant parameters). For example, a supertype parameter annotated object together with a subtype parameter annotated str is an error.

  3. Positions and names of parameters: positional parameters must line up in an order that is compatible. If named positional parameters are reordered (e.g., supertype (x, y) vs. subtype (y, x)), that is an error.

  4. Kinds of parameters: a parameter's kind must stay usable in the same way. For example, when the supertype declares a parameter as positional-capable and the subtype declares the parameter of the same name as keyword-only, that is an error.

  5. Widening is permitted: the subtype may legitimately broaden what it accepts. All of the following are compatible and must not raise: adding extra optional parameters (with defaults), adding *args and/or **kwargs, widening a parameter type, or making a required parameter optional.

Parameters whose type hints are strings (forward references) must be resolved and compared as though they were the actual types they name. An annotation that is missing is treated as unconstrained.

Handling of self and bound vs. unbound callables

The results of the function must be identical regardless of whether each callable is passed as:

  • a bound method retrieved from an instance (e.g., instance.method),
  • an unbound function retrieved from the class (e.g., Class.method), or
  • any combination mixing the two between supertype and subtype.

In all of these cases, the implicit instance parameter (conventionally named self) must not take part in the compatibility comparison. The outcome must not be affected by whether the leading instance parameter is present (unbound) or has already been removed (bound). Different names for the instance parameter must never cause an error.

When is_static=True, both callables are handled as having no implicit instance parameter, and every declared parameter (the first one included) is compared directly. In this mode too, the results must be identical regardless of whether each static method is accessed via an instance or via the class.

Examples of expected results

  • Two methods whose parameter and return types are identical (differing only in the name of the leading instance parameter) are compatible, whether they are accessed bound or unbound.
  • Two methods that differ in the type of their sole meaningful parameter (int vs. str) are incompatible in every access combination.
  • Two static methods whose parameter types match are compatible (with is_static=True); when their parameter types differ (int vs. str), they are incompatible, in every access combination.

Non-goals

The only requirement is the behavior described above. Adding validation, configuration, or reporting beyond returning normally when the signatures are compatible and raising TypeError when they are incompatible is not allowed.

The checker compares the parameter type annotations and the return type annotations of the two callables. Two annotation situations fall within this task's scope, and in specific directions they must be treated as compatible:

Stated differently, a TypeVar annotation imposes no type constraint and never results in an incompatibility, no matter which callable (super or sub) it appears on.

  2. Missing annotations (None). When an annotation is absent on one side, comparisons that involve that missing annotation must not raise, within the specific directions described below.

Summary

The Python package overrides is to be provided; it supplies decorators and a base class for declaring and enforcing method-override semantics. Misspelled or stale overrides must be detected by the package, incompatible method signatures must be rejected, final methods must be supported, and inherited documentation must be preserved. Except in the explicit runtime-checking mode described below, failures are reported at the point where the subclass is being defined — before an instance is created or the method is invoked.

Signature compatibility is grounded in substitutability: an overriding method is compatible when the override can also accept every argument pattern accepted by the inherited method, and when their type annotations are compatible in the directions described below.

Public Interface

From the package root, the following names must remain importable:

from overrides import __VERSION__, overrides, final, EnforceOverrides

__VERSION__ must remain available as the package's version string.

From its public module, the callable-level compatibility checker must remain available:

from overrides.signature import ensure_signature_is_compatible
overrides

Both a bare form and a configured form are supported by the decorator:

@overrides
def method(...):
    ...

@overrides(check_signature=False)
def method(...):
    ...

@overrides(check_at_runtime=True)
def method(...):
    ...

Its public call shape is equivalent to the following:

overrides(method=None, *, check_signature=True, check_at_runtime=False)
  • An inherited method or descriptor with the same name must exist for the decorated method. The lookup must work for ordinary and deep inheritance, multiple inheritance, classes defined in other modules, parameterized generic bases, and built-in bases.
  • Applying @overrides raises TypeError during the class statement if no inherited member with that name exists. This name check is still in force when signature checking is disabled or deferred.
  • When the default options are in effect, signature and finality validation occurs during the class statement; an incompatible signature raises TypeError at that time.
  • Setting check_signature=False turns off signature compatibility validation. An override whose inherited name is correct is accepted even if its signature would otherwise be incompatible. Name lookup, final-method protection, and normal docstring behavior are not disabled.
  • With check_at_runtime=True, signature compatibility validation is deferred until the decorated method is called. As a consequence, a class containing an incompatible override can be defined successfully, but calling that method raises TypeError before the body of the incompatible method is allowed to run. final

@final marks a method as non-overridable and returns a usable method that retains its original behavior. The restriction travels with the method through indirect inheritance and across module boundaries.

A subclass that does not redefine the final method inherits it and can call it normally. For a subclass that does redefine it, the error behavior is specified under Final methods and their enforcement paths.

EnforceOverrides

EnforceOverrides is a base class, and its enforcement applies to every direct and indirect subclass. It requires that ordinary callable methods which shadow inherited callable methods be explicitly marked with @overrides. Enforcement happens during the creation of each subclass.

ensure_signature_is_compatible

The public behavior of the callable-level API is the following:

ensure_signature_is_compatible(
    super_callable,
    sub_callable,
    is_static=False,
) -> None

It returns None when sub_callable is compatible with super_callable, and it raises TypeError otherwise. Bound or unbound methods are accepted in any combination. is_static=True means the first parameter is a real argument and must be checked; under the default False, the first parameter is treated as the receiver of an instance or class method.

When signature checking is enabled, the @overrides decorator must apply the same compatibility rules, subject to the documented exclusions for properties and special methods.

Behavior of inherited members and documentation

  • An override with a correct name may target a method inherited directly or indirectly, including one supplied by a generic or built-in base class.
  • A subclass that uses @overrides must continue to work when the subclass itself is wrapped in a parameterized class decorator, including when the argument of that class decorator is obtained through an attribute expression.
  • In normal validation mode, an overriding method that has no docstring inherits the docstring of the overridden member.
  • When the overriding method supplies its own docstring, that docstring must be preserved rather than replaced.
  • Docstring inheritance works for inherited members defined in another module as well as for methods inherited through generic bases.

Rules for signature compatibility

General rules on call shapes

Compatibility must take all Python parameter kinds into account:

  • positional-only parameters;
  • positional-or-keyword parameters;
  • variadic positional parameters (*args);
  • keyword-only parameters; and
  • variadic keyword parameters (**kwargs).

The following rules apply, subject to receiver handling:

  1. The overriding callable must accept every call shape accepted by the parent callable. For that reason, parameters of the parent callable cannot simply be removed, made required in cases where the parent made them optional, reordered incompatibly, or narrowed to a less permissive parameter kind.
  2. Parent parameters that are positional must retain compatible positional ordering. A mere exchange of two named positional parameters is incompatible.
  3. In the override, a parent positional-only parameter may be broadened to positional-or-keyword. A parent keyword-only parameter may also be broadened to positional-or-keyword. It is incompatible to narrow a positional-or-keyword parameter so that one of its supported calling forms is lost, unless other parameters or variadic parameters preserve both forms.
  4. Optional positional-only, positional-or-keyword, or keyword-only parameters may be added by an override. A new required argument that prevents a call accepted by the parent may not be added.
  5. If the parent accepts an unbounded number of positional arguments, the override must retain an equivalent unbounded positional capacity. If the parent accepts arbitrary keyword arguments, the override must retain an equivalent arbitrary-keyword capacity.

All of the following public rules are part of signature compatibility.

Presence, order, and kinds of parameters
  • Parameters that the inherited callable accepts must continue to be accepted by the override. Positional or named parameters that are missing are incompatible unless coverage by suitable *args or **kwargs exists.
  • The relative positions of the inherited positional parameters, along with the ordering of the named parameters that are explicitly retained, must be compatible.
  • A positional-or-keyword parameter may not be narrowed to positional-only or to keyword-only. A positional-only parameter may be widened to positional-or-keyword, and a keyword-only parameter may likewise be widened to positional-or-keyword.
  • When the inherited callable accepts arbitrary positional arguments, the override must also be able to accept them. The rule applies analogously to arbitrary keyword arguments.
  • An override that is generic and uses *args, **kwargs may validly replace an inherited method that is parameterized more specifically. The reverse is incompatible when the finite signature cannot accept every possible call.
  • Required parameters that are new in the override are incompatible unless an inherited variadic parameter covers them. Extra optional positional, positional-only, or keyword-only parameters are allowed.
  • With non-static methods and class methods, the first receiver parameter is ignored no matter whether its name is self, cls, me, or something else, and no matter whether the callables that are supplied are bound or unbound. With static methods, every parameter is checked, the first one included.
  • A method that overrides may use a positional slot with a different name when it still accepts both positional calls and the inherited keyword names through **kwargs. Merely changing an inherited positional-or-keyword parameter into a positional-only or keyword-only one is not sufficient.
Types given as annotations
  • Parameter types are contravariant: each parameter of the override must accept at least every value that the corresponding inherited parameter accepts. For example, an inherited int parameter may be overridden by Union[int, str], but the converse is not allowed.
  • Return types are covariant: the return annotation on an override must be a subtype of the inherited return annotation. When the inherited callable specifies a return type, leaving the overriding return type out or supplying one that is incompatible is an error. An inherited return that carries no annotation does not prohibit a more specific return annotation on the override.
  • Handling must succeed without spurious failures for ordinary subclasses, unions, nested generic types, Any, Callable, and string or forward-reference annotations that can be resolved.
  • Occurrences of an unbound TypeVar, including ones nested inside another annotation, are treated as indeterminate and do not on their own make a signature incompatible.
  • With Literal parameters, the overriding annotation must include every literal that the inherited annotation accepts. Literal sets that are equal, as well as supersets, are compatible; subsets and disjoint sets are incompatible.
  • Adding a concrete narrowing annotation to an inherited parameter that is unannotated is incompatible within the same top-level package. A callable that is untyped and inherited from another package must remain overridable with annotations; the absence of annotations on it must not create a false incompatibility.
  • On non-static methods, receiver annotations are ignored together with the receiver parameter.

When string annotations can be resolved, the comparison must be based on their resolved types. A forward reference to the subclass that is currently being created must not cause class creation to fail merely because the class name is not yet bound; deferred checking must be able to resolve references of this kind after class creation.

Checking that is disabled or deferred

When check_signature=False is set, a method that would otherwise be incompatible may be declared, but it must still override an existing member and must not override a member that is final.

When check_at_runtime=True is used, an incompatible signature must not cause a failure merely during class definition. Signature compatibility is checked before the method body is invoked, using the type namespace available at that time:

  • an override that is incompatible raises TypeError at invocation time, and its body is not called;
  • a compatible override runs normally; and
  • string annotations that refer to the subclass itself can therefore be resolved once the subclass exists.

Same-name resolution and finality are still requirements at class-definition time.

Members That Are Final

An inherited member with the same name that carries the @final mark may not be overridden. Through normal inherited lookup, @overrides must detect finality—including final members declared in indirect ancestors or in another module—and raise TypeError during class definition. The rule covers methods and nested classes equally.

In a hierarchy that is ordinary, finality is checked at the point where a would-be override is explicitly decorated with @overrides. In a hierarchy built on EnforceOverrides, enforcement also rejects an undecorated attempt to replace a final method.

Hierarchies Under Enforcement

For every non-dunder callable member defined in the body of a subclass of EnforceOverrides, if a direct base exposes a callable member of the same name, the new member must carry the declaration made by @overrides; when the member does not carry that declaration, class creation raises AssertionError. Later subclasses inherit the enforcement transitively.

The mechanism carrying out enforcement must:

  • recognize override declarations through staticmethod, classmethod, and property wrappers when the ordering of those decorators matches what is shown above;
  • allow ordinary class variables to shadow class variables without @overrides being required;
  • reject, with AssertionError, an undecorated replacement of an inherited callable that is final;
  • allow compatible overrides that are properly decorated and leave inherited behavior that is not overridden intact;
  • continue to rely on the normal validation of overrides, so a method that is decorated but signature-incompatible raises TypeError; and
  • ignore callable names that are supplied only by the enforcement metaclass itself. When an ordinary parent class explicitly defines a name of that kind, later subclasses must once again declare an override in the normal way.

Dunder members are excluded from the enforcement that makes explicit overrides mandatory.

Summary of Errors

  • There is no inherited member with the same name for @overrides: TypeError during class definition.
  • The signature is incompatible under default eager checking: TypeError during class definition.
  • The signature is incompatible while check_at_runtime=True is set: TypeError when invoked.
  • An attempt is made to override a final member via @overrides: TypeError during class definition.
  • EnforceOverrides sees a missing @overrides or an undecorated finality violation: AssertionError during class definition.

Summary

You must modify the @overrides decorator so that the situation where an overridden method coming from a superclass does not have a __module__ attribute is handled correctly.

Background

The overrides decorator is applied to methods in a subclass in order to declare, and to verify, that those methods override a method defined in a superclass. During its processing, the decorator determines whether the overriding method and the overridden (superclass) method come from the same module. An internal _is_same_module check carries out this determination.

Required Behavior

Whenever the @overrides decorator is applied to a method that overrides a superclass method, and the superclass method being overridden does not have a __module__ attribute, the same-module determination (_is_same_module) must evaluate to False instead of raising an error.

To be concrete:

  • Applying @overrides to a subclass method whose name matches a method inherited from a built-in / C-implemented type (whose underlying method object does not have a __module__ attribute) must succeed without any exception being raised.
  • This must work when @overrides is used in its bare form (i.e., when @overrides is applied directly as a decorator and is not called with arguments).

Example Scenario

A class that is a subclass of a built-in type such as int may override methods like bit_length. int.bit_length, being C-implemented, does not expose a __module__ attribute. Applying @overrides to the subclass's bit_length must complete the class definition successfully:

class SubclassOfInt(int):

        pass

Defining a class of this kind must not raise; the __module__ that is missing on the overridden method is treated as "not the same module."

The decorator overrides must remain importable and usable in its current form (e.g., from overrides import overrides), including support for the bare @overrides usage form shown above. Aside from preserving existing usage, no signature changes are required.

Gracefully handling an overridden method that lacks __module__ is the only new requirement. All existing behavior must stay intact.

Background

You will be modifying overrides, a Python library offering decorators and base classes whose purpose is explicit declaration and enforcement of method overrides within class hierarchies. Ensuring that the signature-compatibility checks for overridden methods correctly handle positional-only parameters (the / syntax, which Python 3.8 introduced) is the focus of this task.

Public API

From the overrides package (top-level overrides module), the following must be importable:

  • overrides — a decorator that gets applied to methods which override a method in a base class.
  • EnforceOverrides — a base class that, once subclassed, enforces override-compatibility rules at class-definition time.

Inside a subclass of a class that uses EnforceOverrides (directly or indirectly), a method decorated with @overrides must have a signature compatible with the method it overrides. If the signature proves incompatible, a TypeError must be raised at the moment the subclass is defined.

Positional-Only Parameters: Required Behavior

If a base-class method uses the / separator to declare a positional-only parameter, the overriding method (the one decorated with @overrides) must be validated against the rules below.

Consider the following base-class method:

def methodb(self, x: int, /, y: str) -> str:
    ...

the override-compatibility check must produce these outcomes:

  1. An identical signature is allowed. When an override repeats the same signature exactly, it is accepted:

    def methodb(self, x: int, /, y: str) -> str:
    ...

    No error is raised, and the subclass definition succeeds.

  2. It is allowed to rename a positional-only parameter. The name of a positional-only parameter does not matter for call compatibility, since such a parameter cannot be passed by keyword. An override that touches only the name of a positional-only parameter (its type annotation and position stay unchanged) is accepted:

    def methodb(self, new_name_is_ok: int, /, y: str) -> str:
    ...

    No error is raised; the subclass gets defined without any problem.

  3. Altering the type annotation of a positional-only parameter is rejected. When the override gives a positional-only parameter a different type annotation (e.g. from int to str), it is incompatible and must raise TypeError at class-definition time:

    def methodb(self, x: str, /, y: str) -> str:  # raises TypeError
    ...

Remarks

  • These rules are exercised only on Python 3.8 and later (positional-only syntax).
  • Behavior that is already in place — for regular positional-or-keyword parameters, for keyword-only parameters, and for other override checks — must keep working; the only thing this task adds is correct handling of the positional-only case as described above.
