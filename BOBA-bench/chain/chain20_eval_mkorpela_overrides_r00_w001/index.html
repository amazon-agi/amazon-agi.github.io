Overview

Implement a function that verifies whether one callable's signature is a compatible "subtype" of another callable's signature, following the Liskov substitution principle for method signatures. The function must correctly handle bound methods, unbound methods (functions accessed via the class), and static methods.

Public API

Provide a function importable as:

ensure_signature_is_compatible(supertype, subtype, is_static=False)
  • supertype: a callable (function, bound method, or unbound method/function accessed from a class).
  • subtype: a callable (function, bound method, or unbound method/function accessed from a class).
  • is_static (optional, default False): a boolean flag indicating that both callables are static methods (i.e., they have no implicit self/instance parameter).

The function returns None when the two signatures are compatible, and raises TypeError when they are not.

Compatibility Rules

The subtype callable is compatible with the supertype callable when it can safely be used in place of the supertype. Concretely, all of the following must hold; otherwise raise TypeError:

  1. Return type: the subtype's return annotation must be the same as, or a subtype of, the supertype's return annotation (covariant return). An incompatible return type (e.g., supertype returns int, subtype returns str) is an error.

  2. Parameter types: for each parameter that exists in the supertype, the subtype's corresponding parameter annotation must accept everything the supertype's does — i.e., the subtype parameter type must be the same as, or a supertype of, the supertype's parameter type (contravariant parameters). For example, if the supertype parameter is annotated object and the subtype parameter is annotated str, that is an error.

  3. Parameter positions / names: positional parameters must line up in a compatible order. Reordering named positional parameters (e.g., supertype (x, y) vs. subtype (y, x)) is an error.

  4. Parameter kinds: a parameter's kind must remain usable the same way. For example, if the supertype declares a parameter as positional-capable and the subtype declares the same-named parameter as keyword-only, that is an error.

  5. Widening is allowed: the subtype may legitimately broaden what it accepts. Adding extra optional parameters (with defaults), adding *args and/or **kwargs, widening a parameter type, or making a required parameter optional are all compatible and must not raise.

Parameters annotated with string (forward-reference) type hints must be resolved and compared as though they were the actual types they name. Missing annotations are treated as unconstrained.

Handling self / bound vs. unbound callables

The function must produce identical results regardless of whether each callable is passed as:

  • a bound method obtained from an instance (e.g., instance.method),
  • an unbound function obtained from the class (e.g., Class.method), or
  • any mixed combination of the two between supertype and subtype.

In all these cases, the implicit instance parameter (conventionally named self) must not participate in the compatibility comparison. Whether the leading instance parameter is present (unbound) or already removed (bound) must not affect the outcome. Differing names of the instance parameter must never cause an error.

When is_static=True, both callables are treated as having no implicit instance parameter, and every declared parameter (including the first) is compared directly. In this mode as well, results must be identical whether each static method is accessed via an instance or via the class.

Examples of expected outcomes

  • Two methods with identical parameter and return types (differing only in the name of the leading instance parameter) are compatible, whether accessed bound or unbound.
  • Two methods whose sole meaningful parameter differs in type (int vs. str) are incompatible in every access combination.
  • Two static methods with matching parameter types are compatible (with is_static=True); if their parameter types differ (int vs. str) they are incompatible, in every access combination.

Non-goals

Only the behavior described above is required. Do not add validation, configuration, or reporting beyond returning normally on compatibility and raising TypeError on incompatibility.

Overview

Provide the Python package overrides, which supplies decorators and a base class for declaring and enforcing method-override semantics. The package must detect misspelled or stale overrides, reject incompatible method signatures, support final methods, and preserve inherited documentation. Except for the explicit runtime-checking mode described below, failures are reported while the subclass is being defined, before an instance is created or the method is invoked.

Signature compatibility is based on substitutability: an overriding method is compatible when every argument pattern accepted by the inherited method can also be accepted by the override, and their type annotations are compatible in the directions described below.

Public API

The following names must remain importable from the package root:

from overrides import __VERSION__, overrides, final, EnforceOverrides

__VERSION__ must remain available as the package version string.

The callable-level compatibility checker must remain available from its public module:

from overrides.signature import ensure_signature_is_compatible
overrides

The decorator supports both bare and configured forms:

@overrides
def method(...):
    ...

@overrides(check_signature=False)
def method(...):
    ...

@overrides(check_at_runtime=True)
def method(...):
    ...

overrides(method=None, *, check_signature=True, check_at_runtime=False)
  • The decorated method must have an inherited method or descriptor with the same name. The lookup must work through ordinary and deep inheritance, multiple inheritance, classes defined in other modules, parameterized generic bases, and built-in bases.

A subclass that does not redefine the final method inherits and can call it normally. The error behavior for a subclass that does redefine it is specified under Final methods and enforcement paths.

EnforceOverrides is a base class whose enforcement applies to every direct and indirect subclass. It requires ordinary callable methods that shadow inherited callable methods to be explicitly marked with @overrides. Enforcement occurs during creation of each subclass.

Signature compatibility rules

General call-shape rules

Compatibility must account for all Python parameter kinds:

  • positional-only parameters;
  • positional-or-keyword parameters;
  • variadic positional parameters (*args);
  • keyword-only parameters; and
  • variadic keyword parameters (**kwargs).

Subject to receiver handling, the following rules apply:

  1. Every call shape accepted by the parent callable must be accepted by the overriding callable. Parent parameters therefore cannot simply be removed, made required in cases where the parent made them optional, reordered incompatibly, or narrowed to a less permissive parameter kind.
  2. Positional parent parameters must retain compatible positional ordering. Merely exchanging two named positional parameters is incompatible.
  3. A parent positional-only parameter may be broadened to positional-or-keyword in the override. A parent keyword-only parameter may also be broadened to positional-or-keyword. Narrowing a positional-or-keyword parameter so that one of its supported calling forms is lost is incompatible unless other parameters or variadic parameters preserve both forms.
  4. An override may add optional positional-only, positional-or-keyword, or keyword-only parameters. It may not add a new required argument that prevents a call accepted by the parent.
  5. If the parent accepts an unbounded number of positional arguments, the override must retain equivalent unbounded positional capacity. If the parent accepts arbitrary keyword arguments, the override must retain equivalent arbitrary-keyword capacity.
  6. Conversely, an override's *args or **kwargs may cover parent parameters that do not appear literally in the override, so long as all positional and keyword calling forms remain accepted. An override consisting of *args, **kwargs can therefore be compatible with a more specifically parameterized parent, while the reverse is not generally compatible.
  7. Default values need not be identical. What matters is whether omission and the parent's supported positional and keyword forms remain valid.

Examples of permitted broadening include:

def parent(self):
    ...

def child(self, optional=1):
    ...

and:

def parent(self, *, value=1):
    ...

def child(self, *, value=1, **kwargs):
    ...

A defaulted positional-or-keyword parameter may be renamed when the override still covers both ways the original parameter could be supplied. In particular, the renamed defaulted positional parameter can accept the positional form while **kwargs accepts the parent's original keyword name.

The following override is required to be accepted without an exception:

class Parent:
    def methoda(self, x=0):
        ...

class Child(Parent):
    @overrides
    def methoda(self, y=1, **kwargs):
        ...

This signature accepts omission, a positional value, and a call using the inherited keyword name x. It must not be rejected merely because x is absent as an explicit child parameter or because the child does not also declare *args.

The same rule applies when the hierarchy derives from EnforceOverrides:

class Parent(EnforceOverrides):
    def methoda(self, x=0):
        ...

class Child(Parent):
    @overrides
    def methoda(self, y=1, **kwargs):
        super().methoda(**kwargs)
Receiver and static-method handling
  • For instance and class methods, the first parameter represents the receiver. Its spelling (self, me, cls, or another name) and its annotation do not need to match between parent and child.
  • Receiver handling must be consistent for bound-to-bound, bound-to-unbound, unbound-to-bound, and unbound-to-unbound comparisons.
  • For static methods there is no receiver. Every parameter, including the first, must be checked. Renaming a static method's first parameter without otherwise preserving its accepted calls can therefore make the override incompatible.
Annotation compatibility

Overview

You are working on a Python library (overrides) that provides decorators and base classes for explicitly declaring and enforcing method overrides in class hierarchies. This task focuses on ensuring that method override signature-compatibility checks correctly handle positional-only parameters (the / syntax introduced in Python 3.8).

Public API Surface

The following must be importable from the overrides package (top-level overrides module):

  • overrides — a decorator applied to methods that override a method in a base class.
  • EnforceOverrides — a base class that, when subclassed, enforces override-compatibility rules at class-definition time.

A method decorated with @overrides in a subclass of a class that (directly or indirectly) uses EnforceOverrides must have a signature that is compatible with the method it overrides. When the signature is incompatible, a TypeError must be raised at the time the subclass is defined.

Required Behavior: Positional-Only Parameters

When a base-class method declares a positional-only parameter using the / separator, an overriding method (decorated with @overrides) must be validated according to the following rules.

Given a base-class method such as:

def methodb(self, x: int, /, y: str) -> str:
    ...

the override-compatibility check must behave as follows:

  1. Identical signature is allowed. An override that repeats the same signature exactly is accepted:

    def methodb(self, x: int, /, y: str) -> str:
    ...

    No error is raised; the subclass is defined successfully.

  2. Renaming a positional-only parameter is allowed. Because a positional-only parameter cannot be passed by keyword, its name is irrelevant to call compatibility. An override that changes only the name of a positional-only parameter (keeping its type annotation and position) is accepted:

    def methodb(self, new_name_is_ok: int, /, y: str) -> str:
    ...

    No error is raised; the subclass is defined successfully.

  3. Changing the type annotation of a positional-only parameter is rejected. An override that changes the type annotation of a positional-only parameter (e.g. from int to str) is incompatible and must raise TypeError at class-definition time:

    def methodb(self, x: str, /, y: str) -> str:  # raises TypeError
    ...

Notes

  • These rules are only exercised on Python 3.8 and later (positional-only syntax).
  • The existing behavior for regular positional-or-keyword parameters, keyword-only parameters, and other override checks must continue to function; this task only adds correct handling of the positional-only case as described above.
