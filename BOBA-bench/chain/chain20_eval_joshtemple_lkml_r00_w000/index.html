Task: Implement a Lexer That Tokenizes LookML

Summary

The task is to implement a lexer (tokenizer) that parses LookML source text. You must create two modules: lkml.tokens, which contains the token classes, and lkml.lexer, which contains the Lexer class.

The lkml.tokens Module

Define token classes that represent scanned pieces of source text. At a minimum, the following classes must be provided:

  • LiteralToken — denotes an unquoted literal value.
  • QuotedLiteralToken — denotes a quoted literal value.

The scanned string must be stored by each token in a value attribute, which is accessible as token.value. A token should be constructed with its string value (for example, LiteralToken("some_value")), such that token.value returns that exact string.

The lkml.lexer Module

A class Lexer is to be defined with the following behavior.

Constructing the Lexer

Lexer(text) — the constructor takes a string of source text.

Attributes
  • index — an integer used as a position marker into the source text. It must be a public, mutable attribute (callers may set lexer.index directly before invoking the scan methods). Its initial value upon construction is unspecified by this task.
The scan_quoted_literal() Method

This method scans a quoted literal value, starting from the current index position. When the method is called, index will already be positioned at the first character inside the opening quote (i.e. just past the opening ").

  • Characters are consumed up to (but not including) the closing double-quote character ".
  • A QuotedLiteralToken is returned, whose value is the string of characters between the current position and the closing quote.
  • The quoted content may contain characters that would otherwise be significant or illegal outside of quotes, including :, {, }, spaces, and newline (\n) characters. All such characters are included verbatim in the value that is returned.

Example: for the text "This is quoted text." with index set to 1, the value of the returned token is This is quoted text.. For the text "This: is {quoted} \n text." with index set to 1, the value of the returned token is This: is {quoted} \n text..

The scan_literal() Method

This method scans an unquoted literal value, starting from the current index position (which by default is the beginning of the text).

  • Consumes consecutive characters that are not whitespace.
  • A LiteralToken is returned, whose value is the run of characters up to the first whitespace character (or the end of the text).
  • Halts at any whitespace, including spaces and newlines. The characters following the whitespace are not included.

Example: for the text unquoted_literal, the value of the returned token is unquoted_literal. For the text unquoted_literal \n and text following whitespace, the value of the returned token is unquoted_literal.

Additional Notes

  • Both of the scan methods return token objects (instances of the classes described above), not raw strings.
  • The value attribute contains only the scanned content, with no surrounding quotes or trailing delimiters.

Task Specification: Validation of List Parsing

Overview

You must ensure that, during parsing, the Parser class correctly rejects malformed lists. To be specific: when a list is not well-formed with regard to comma placement, the list-parsing logic must return None.

Public API

The items below must be importable and callable:

  • Module: lkml.parser
  • Class: lkml.parser.Parser
  • Constructor: Parser(stream) — accepts a single argument, which is a sequence (tuple) of token objects.
  • Method: Parser.parse_list() — takes no arguments (other than self); it returns either a parsed representation of the list, or None when the list is malformed.

The token types referenced below are drawn from the tokens module and are used for building the input stream:

  • tokens.LiteralToken(value) — a literal string value (for example, a field name or the list's key).
  • tokens.ValueToken() — serves to separate a key from its value.
  • tokens.ListStartToken() — indicates the start of a list.
  • tokens.ListEndToken() — indicates the end of a list.
  • tokens.CommaToken() — acts as the separator between elements within a list.
  • tokens.StreamEndToken() — indicates the end of the token stream.

Structure of the Input

parse_list() operates on a token stream that represents a key followed by a bracketed list of literal values. A well-formed list stream follows this general shape:

LiteralToken(key), ValueToken(), ListStartToken(),
    <literal>, CommaToken(), <literal>, CommaToken(), ..., <literal>,
ListEndToken(), StreamEndToken()

That is to say: the list's elements are literals separated by commas, and a comma appears between consecutive elements only.

Required Behavior

In the following malformed cases, parse_list() must return None (indicating a parse failure):

  1. Trailing comma: Within the list, a comma is present immediately before the list-end marker, and no element follows it. As an example, a stream whose list body consists of a single literal followed by a comma and then the list-end token must yield None.

  2. Missing comma between elements: The list body contains two consecutive literal elements with no comma separating them. As an example, consider a stream where one literal is followed by a comma and another literal, and that literal is immediately followed by a third literal (with no intervening comma) before the list-end token; this stream must yield None.

In both cases, the input stream is otherwise structurally complete (opened and closed properly with the appropriate start/end tokens, and terminated by a stream-end token); the incorrect comma placement is the only defect.

Constraints

  • The behavior described above applies only to the validation of comma placement in parse_list(). You must not alter or add any other parsing behavior.

The library you are working on is named lkml; it lexes LookML source text into a stream of tokens. Implement the behavior laid out below.

A Lexer class must be exposed by the package (importable as lkml.Lexer).

lkml.Lexer

  • Lexer(text: str) — takes the source string to lex as its construction argument.

  • scan_sql_block(self) — scans a SQL block beginning at the lexer's current position and returns a token whose value attribute is the SQL body as a string. The SQL body must be captured verbatim, up to (but not including) the terminating ;; delimiter, with any trailing whitespace between the body and the delimiter stripped. The token that is returned is a SqlBlockToken (see below).

  • scan_literal(self) — scans an unquoted literal and returns a LiteralToken whose value is the literal text, with trailing whitespace not included.

  • scan(self) — scans the entire input and returns a tuple of tokens that represents the full stream (see the stream format below).

The lkml.tokens Module

The following token classes must be provided (importable as lkml.tokens.<Name>):

  • Token — the base class shared by all tokens.
  • StreamStartToken — denotes the start of a token stream.
  • StreamEndToken — denotes the end of a token stream.
  • LiteralToken(value: str) — carries a literal string in its value attribute.
  • ValueToken — stands for the : separator between a key and its value.
  • SqlBlockToken(value: str) — carries the body of a SQL block in its value attribute.
  • SqlBlockEndToken — stands for the ;; terminator of a SQL block.

Required Behavior

Scanning a SQL block

A SQL block is arbitrary SQL text that is terminated by the delimiter ;;. Characters such as parentheses, single quotes, commas, dollar signs, braces, and pipe characters may appear in the SQL body itself — for example, LookML substitution references like ${orders.order_id}. None of these characters terminates the block; the only thing that terminates it is the literal ;; sequence.

When scan_sql_block is called with input positioned at the beginning of the SQL body, it returns a SqlBlockToken whose value is the SQL body captured up to the ;; delimiter, with the delimiter excluded and with any whitespace immediately preceding the delimiter excluded as well.

Example: for the input

concat(${orders.order_id}, '|', ${orders__items.primary_key}) ;;

the call scan_sql_block returns a SqlBlockToken with the value:

concat(${orders.order_id}, '|', ${orders__items.primary_key})
Full-stream scanning of a SQL assignment

When scan handles an input of the form <key>: <sql body> ;;, it produces a token stream (as a tuple) in the following order:

  1. StreamStartToken()
  2. LiteralToken(<key>) — holding the key text
  3. ValueToken() — corresponding to the :
  4. SqlBlockToken(<sql body>) — the SQL body, captured as specified by the SQL block rules above (the trailing whitespace before ;; is removed)
  5. SqlBlockEndToken() — corresponding to the ;;
  6. StreamEndToken()

Example: with the input

sql_distinct_key: concat(${orders.order_id}, '|', ${orders__items.primary_key}) ;;

a call to scan returns:

(
    StreamStartToken(),
    LiteralToken("sql_distinct_key"),
    ValueToken(),
    SqlBlockToken("concat(${orders.order_id}, '|', ${orders__items.primary_key})"),
    SqlBlockEndToken(),
    StreamEndToken(),
)
Equality of tokens

When their relevant contents are equal, tokens of the same type must compare equal. Specifically:

  • Two token instances belonging to the same class and carrying no value (e.g. StreamStartToken, StreamEndToken, ValueToken, SqlBlockEndToken) compare equal to each other.
  • Two instances of LiteralToken (or of SqlBlockToken) compare equal when their value attributes are equal.

This equality must hold both when tokens are compared directly with each other and when tuples of tokens are compared.

Scanning literals

scan_literal returns a LiteralToken whose value is the unquoted literal that was scanned, with any following whitespace not included. For example, scanning input that begins with unquoted_literal (followed by whitespace) yields a LiteralToken with value "unquoted_literal".

Note About the Parser

The peek operation of any parser supports returning a single token only. Support for peeking multiple tokens, or for returning a sequence of tokens from peek, is not required.

Objective

The token class that represents the ;; terminator of a SQL block is to be renamed from SqlEndToken to SqlBlockEndToken, and the token API, lexer, parser, and loading pipeline must use the renamed token consistently. The parser must also accept the SqlBlockToken values that the lexer produces for SQL assignments.

Public Token API

In lkml.tokens (commonly imported as tokens), the SQL-block terminator class must be named SqlBlockEndToken, and it must remain instantiable with no arguments:

import lkml.tokens as tokens

end = tokens.SqlBlockEndToken()

These requirements apply:

  • SqlBlockEndToken stands for the ;; end-of-SQL-block delimiter.
  • SqlEndToken is the obsolete name. It must no longer serve as the class name, nor be used when defining, constructing, checking, or consuming this token. All references of this kind must use SqlBlockEndToken.
  • SqlBlockToken remains the token that carries the value for a SQL body and exposes that body through its .value attribute.
  • No other public token names and no token construction behavior may change.

Lexer Behavior

Existing SQL lexing behavior must continue to be compatible with the renamed terminator. Scanning a complete SQL assignment such as the following:

sql_table_name: schema.table_name ;;

must produce the normal stream boundary tokens around this assignment sequence, i.e. this token stream:

(
    tokens.StreamStartToken(),
    tokens.LiteralToken("sql_table_name"),
    tokens.ValueToken(),
    tokens.SqlBlockToken("schema.table_name"),
    tokens.SqlBlockEndToken(),
    tokens.StreamEndToken(),
)

Therefore, the SQL body is emitted as a SqlBlockToken rather than a LiteralToken, and the ;; delimiter is emitted as a SqlBlockEndToken. Otherwise, existing handling of SQL text, including complex SQL bodies, must remain unchanged.

Parser Compatibility and Handling of SQL Values

Constructing the parser

lkml.parser.Parser must continue to accept a sequence of token instances, a tuple included:

parser = lkml.parser.Parser(stream)

The constructor, together with all other parser interfaces, must retain their existing behavior.

parse_value

Parser.parse_value() must recognize all the existing value token types and must also recognize SqlBlockToken:

  • A QuotedLiteralToken still produces its .value.
  • A LiteralToken likewise still produces its .value.
  • A SqlBlockToken must be consumed and produce its .value, so that the returned value is the SQL string rather than a token object.
  • If a LiteralToken or SqlBlockToken value is immediately followed by a SqlBlockEndToken, that terminator must be consumed too. For direct value parsing the terminator is optional; whether it is present or absent, the returned result is the value token's .value.

For instance, both of the following value streams must return the SQL string successfully:

(
    tokens.LiteralToken("SELECT * FROM tablename"),
    tokens.SqlBlockEndToken(),
    tokens.StreamEndToken(),
)

(
    tokens.SqlBlockToken("SELECT * FROM tablename"),
    tokens.SqlBlockEndToken(),
    tokens.StreamEndToken(),
)
Pairs and named blocks

Everywhere the old SQL-end token was consumed, the renamed terminator must work:

  1. A key/value SQL pair consisting of LiteralToken(key), ValueToken, LiteralToken(sql), SqlBlockEndToken, and StreamEndToken must parse successfully. As an example, parsing a pair for sql must produce {"sql": sql}.
  2. When the pair's body is represented by the lexer-compatible SqlBlockToken(sql) instead of LiteralToken(sql), the same pair must parse successfully, and it must produce the same dictionary value.
  3. This applies both to LiteralToken SQL bodies supplied manually and to SqlBlockToken bodies produced by the lexer.

The SQL body that the lexer emits as a SqlBlockToken must be preserved as the corresponding string value in the parsed result, and the fields or nested blocks that follow must not be swallowed by SQL parsing.

  • This amounts to a token rename plus the parser compatibility needed for the lexer-produced SQL body token; it is not a redesign of the grammar or of the parsed result structure.
  • Runtime construction and parser checks that use SqlEndToken must not be retained.
  • Other public token classes must not be renamed, removed, or otherwise altered.
  • Existing behavior for ordinary and quoted literals, for lists, for nested blocks, for parser stream navigation and validation, and for non-SQL lexer scanning must remain unchanged.
