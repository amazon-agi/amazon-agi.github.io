Specification of the Task

Goal

Extend the local and S3 file handlers with explicit support for text encoding, and propagate the encoding configured in the Scrapy start-URLs loader through to whichever handler is selected. Scheme dispatch, spider-attribute path formatting, custom handlers, S3 authentication, and text-stream behavior must be preserved.

Interfaces that are public

These interfaces are public:

  • spider_feeder.file_handler.local.open(file_path, encoding)
  • spider_feeder.file_handler.s3.open(uri, encoding)
  • spider_feeder.loaders.StartUrlsLoader, including StartUrlsLoader.from_crawler(crawler)

Every file-handler callable, shipped or custom, must accept the file path or URI as its first positional argument and an encoding keyword argument. The loader must always pass the encoding by name, in the form encoding=<resolved value>.

1. Handler for local files

An open(file_path, encoding) function must be exposed by the spider_feeder.file_handler.local module.

  • file_path may be either an ordinary filesystem path or a URI beginning with file://.
  • Remove that leading prefix before the file is opened if, and only if, the value begins with file://. By way of example, file:///tmp/input_urls.txt resolves to /tmp/input_urls.txt. A path that carries no scheme is left unchanged.
  • The resolved path is opened as a text file through the module's builtins reference. The call that gets delegated must be exactly builtins.open(resolved_path, encoding=encoding), with the path as the sole positional argument, encoding forwarded as a keyword argument, and no additional arguments supplied.
  • Return the file object that builtins.open produced.

To illustrate, local.open('file:///tmp/input_urls.txt', encoding='latin-1') must delegate as builtins.open('/tmp/input_urls.txt', encoding='latin-1').

2. Handler for S3 files

An open(uri, encoding) function must be exposed by the spider_feeder.file_handler.s3 module; it accepts an s3:// URI and returns decoded text in an io.StringIO.

How the URI is parsed
  • The bucket name comes from the URI host.
  • The object key is the URI path once its leading / has been removed. So s3://bucket/blob.txt selects bucket bucket and key blob.txt. After the single leading slash is stripped, nested key paths must remain intact.
  • Credentials may appear in a URI as user information, in the form s3://key_id:secret@bucket/blob.txt. Those values are authentication data and must not end up as part of the bucket or the key.
Selecting credentials and creating the client

The client is created through the botocore session's create_client method, with service name 's3'. Credentials are picked according to the following precedence:

  1. If the URI contains key_id:secret, use those values, passing them as aws_access_key_id and aws_secret_access_key. Credentials from the URI take precedence over credentials from project settings.
  2. If the URI has no embedded credentials, obtain the project settings through the module-level get_project_settings() callable and look up SPIDERFEEDER_AWS_ACCESS_KEY_ID and SPIDERFEEDER_AWS_SECRET_ACCESS_KEY. When these fallback values are configured, they must be passed to create_client as aws_access_key_id and aws_secret_access_key. A URI without credentials must not bypass this project-settings fallback.
  3. If neither URI nor project settings supply credentials, client creation may make use of botocore's normal credential discovery; no credential values should be invented.

The settings accessor must remain exposed at spider_feeder.file_handler.s3.get_project_settings, and looking up the fallback credentials must go through that callable. Given selected credentials key_id and secret, the required client call is equivalent to session.create_client('s3', aws_access_key_id='key_id', aws_secret_access_key='secret').

Retrieving the object and decoding it
  • get_object must be called with exactly the parsed bucket and key plus the requested response content encoding: Bucket=<bucket>, Key=<key>, and ResponseContentEncoding=<encoding>.
  • Read the bytes out of the response's Body.
  • Those bytes are then decoded using that same encoding argument.
  • The decoded string is wrapped in io.StringIO and returned. A call to read() on the returned object must reproduce the decoded object content exactly.

As an example, bytes encoded as iso-8859-1 for content containing http://vérystrangeurl.com must round-trip when encoding='iso-8859-1', and that same value must be sent as ResponseContentEncoding.

3. Loader for start URLs

StartUrlsLoader must be importable via from spider_feeder.loaders import StartUrlsLoader, and it must be usable as a Scrapy extension.

Configuration settings

These are the settings the loader recognizes:

  • SPIDERFEEDER_INPUT_FILE — the path or URI of the text input file; this setting is required. If it is absent or lacks a configured value, StartUrlsLoader.from_crawler(crawler) must raise scrapy.exceptions.NotConfigured.
  • SPIDERFEEDER_INPUT_FILE_ENCODING — the text encoding, which is optional. The default is 'utf-8'; when a value such as 'latin-1' is configured, it takes the place of that default.
  • SPIDERFEEDER_FILE_HANDLERS — an optional mapping of URI scheme names to dotted callable paths. Entries in it extend or override the built-in handler mapping.

Out of the box, the scheme mapping is:

  • Empty scheme (''): spider_feeder.file_handler.local.open
  • file: spider_feeder.file_handler.local.open
  • s3: spider_feeder.file_handler.s3.open

For that loader, a custom mapping such as {'s3': 'myproject.my_reader.open'} must replace the built-in S3 callable. Handlers for other schemes may also be added via custom entries. Values get resolved as dotted callable paths, and the same (file_path, encoding=...) contract as the built-in handlers applies to the custom callable.

Lifecycle and behavior during loading
  • from_crawler must register the loader with Scrapy's signals.spider_opened signal and return the configured loader instance. When that signal is received for the spider, the input must be opened and loaded.
  • Before dispatch happens, SPIDERFEEDER_INPUT_FILE is formatted with Python %()s mapping substitution using the spider's attributes. To give an example, '%(dir)s/%(input_file)s.txt' with spider.dir == '/tmp' and spider.input_file == 'spider_input' becomes /tmp/spider_input.txt.
  • Scheme selection happens based on the formatted value. A formatted s3:// URI uses the S3 handler, a formatted file:// URI the local handler, and a formatted path with no URI scheme also the local handler.
  • The handler's first positional argument is the formatted value itself, passed unchanged. Stripping the scheme is the selected handler's responsibility; as an example, the loader passes file:///tmp/input_file.txt to the local handler rather than pre-stripping it.
  • The selected handler is invoked with the resolved encoding as a keyword argument. To illustrate: for a scheme-less local.txt, the default call is local.open('local.txt', encoding='utf-8'), while configuring SPIDERFEEDER_INPUT_FILE_ENCODING as 'latin-1' changes it to local.open('local.txt', encoding='latin-1'). The same propagation rule covers S3 and custom handlers.
  • The returned text file-like object serves as the URL source; read its content, split the text with str.splitlines(), and assign the resulting list to spider.start_urls. So, content https://url1.com\nhttps://url2.com produces ['https://url1.com', 'https://url2.com'].

Compatibility of encodings

The complete chain from loader configuration through handler invocation and file decoding must support at least:

  • 'utf-8' — its role as the loader default included;
  • 'latin-1'; and
  • 'iso-8859-1' — non-ASCII S3 content included.

What handlers return are text streams, not undecoded byte streams. Consequently, the loader reads strings and must not apply an additional decode step.

Task Specification: Implementation of FileStore

Overview

The task is to implement a FileStore class that reads a file containing URLs (optionally along with associated metadata) and exposes its contents through iteration. There are different URI schemes via which the source file can be located, and the file format (txt, csv, json) determines how its contents are parsed.

Public Interface

The spider_feeder.store.file_store module

A class FileStore must be provided with the following signature:

class FileStore:
    def __init__(self, uri, settings):
        ...
    def __iter__(self):
        ...
  • uri: a string that identifies the input file. It may include a URI scheme prefix (file://, s3://), or it may have no scheme at all. The URI's file extension (.txt, .csv, .json) determines the parsing format.
  • settings: an instance of scrapy.settings.Settings. The following keys are read:
    • SPIDERFEEDER_INPUT_FIELD (string, optional): the key whose value should serve as the URL of each record. If absent/unset, the file is treated as a plain list of URLs.
    • SPIDERFEEDER_INPUT_FILE_ENCODING (string, optional): the text encoding used to open the file. When unset, 'utf-8' is the default.
Handler modules for files

The class must delegate the opening of the file to a handler module that is specific to the scheme. Each handler module must expose an open(uri, encoding=...) function that returns a readable text file-like object (the object it returns yields the file's textual content).

These modules must be provided, each with an open function:

  • spider_feeder.file_handler.local — for the file:// scheme and for URIs that have no scheme.
  • spider_feeder.file_handler.s3 — for the s3:// scheme.

The handler must be chosen based on the URI scheme:

  • file:// → spider_feeder.file_handler.local.open
  • s3:// → spider_feeder.file_handler.s3.open
  • no scheme → spider_feeder.file_handler.local.open

The open function that gets selected must be invoked in the following way:

open(uri, encoding=<encoding>)

where uri is the original URI string in full (with its scheme prefix included, unchanged) and <encoding> is the value of SPIDERFEEDER_INPUT_FILE_ENCODING (or 'utf-8' by default).

Behavior of Iteration

When a FileStore instance is iterated over, it yields two-tuples (url, meta) in which url is a string and meta is a dict.

How the contents are parsed depends on the file extension of the URI:

Files with a .txt extension
  • The content is a list of URLs separated by newlines.
  • One entry is produced for each non-trivial line.
  • For each URL line, yield (url, {}) — the URL string along with an empty metadata dict.
  • For content whose lines are http://url1.com and http://url2.com, iteration yields:
    • ('http://url1.com', {})
    • ('http://url2.com', {})
Files with a .csv extension
  • The content is CSV text that has a header row naming the columns.
  • Each data row is turned into a dict that maps column name → cell value (all values are strings).
  • The column that holds the URL is named by SPIDERFEEDER_INPUT_FIELD.
  • For each row, yield (row[SPIDERFEEDER_INPUT_FIELD], row_dict), with row_dict being the full dict of that row's columns.
  • Example: header "url_id","url" plus rows "1","http://url1.com" and "2","http://url2.com", with SPIDERFEEDER_INPUT_FIELD='url', yields:
    • ('http://url1.com', {'url_id': '1', 'url': 'http://url1.com'})
    • ('http://url2.com', {'url_id': '2', 'url': 'http://url2.com'})
Files with a .json extension
  • The content is a JSON array of objects.
  • Each object is turned into a dict.
  • The key that holds the URL is named by SPIDERFEEDER_INPUT_FIELD.
  • For each object, yield (obj[SPIDERFEEDER_INPUT_FIELD], obj), with obj being the full parsed dict.
  • Example: given [{"url_id": "1", "url": "http://url1.com"}, {"url_id": "2", "url": "http://url2.com"}] and SPIDERFEEDER_INPUT_FIELD='url', iteration yields:
    • ('http://url1.com', {'url_id': '1', 'url': 'http://url1.com'})
    • ('http://url2.com', {'url_id': '2', 'url': 'http://url2.com'})

Error Cases

If SPIDERFEEDER_INPUT_FIELD is set but the parsed records are not dicts (that is, the data is a plain list of URL strings, the kind a .txt file produces), iteration must raise a TypeError whose first argument is exactly:

Data is expected to be a dict when SPIDERFEEDER_INPUT_FIELD is set.

Remarks

  • The file is opened with the encoding determined from settings, and the open call must pass encoding as a keyword argument.
  • The URI that is passed to the handler's open must be the exact original string (scheme prefix included, if any).

Overview

Extend FileStore so that callers can explicitly select the input file format via settings. A format that has been explicitly configured must take precedence over inferring the format from the URI, while all existing behavior for extension-based parsing, URI-handler selection, configurable encoding, and extensibility remains compatible.

Public API

FileStore

FileStore must remain importable via:

from spider_feeder.store.file_store import FileStore

Its constructor is still:

FileStore(uri, settings)
  • uri is a resource location given as a string. It may use no scheme or a scheme such as file:// or s3://, and it may include a file extension or omit one.
  • settings is a Scrapy-style settings object that supports key lookup. Relevant settings include SPIDERFEEDER_INPUT_FORMAT and SPIDERFEEDER_INPUT_FILE_ENCODING; existing settings such as SPIDERFEEDER_INPUT_FIELD, SPIDERFEEDER_FILE_HANDLERS, and SPIDERFEEDER_FILE_PARSERS must continue to work.

A FileStore is still iterable. Iterating over it yields (url, meta) pairs, in which url is the input URL and meta is the metadata dictionary associated with it.

Behavior Requirements

How the file format is resolved

The format used for selecting the file parser is resolved in this order:

  1. If SPIDERFEEDER_INPUT_FORMAT is present in settings, its configured value is used as the format identifier.
  2. Otherwise, the format is inferred from the extension of uri, keeping the existing behavior. The identifier is the extension with its leading period removed, such as txt, csv, or json.

The explicit setting always takes precedence. This applies when the URI has no extension, and also when its extension conflicts with the setting. As an example, both of the following must use the txt parser:

  • a URI that has no extension, with SPIDERFEEDER_INPUT_FORMAT = 'txt'
  • a URI that ends in .csv, with SPIDERFEEDER_INPUT_FORMAT = 'txt'

Resolving the format is independent of resolving the URI scheme: selecting a parser explicitly must not change which file handler opens the resource, nor alter the URI supplied to that handler.

Parser selection and compatibility

The parser is selected with the resolved format identifier. The built-in support that already exists for txt, csv, and json must remain functional.

Parser customization that already exists must also remain functional. Entries from SPIDERFEEDER_FILE_PARSERS extend or override the default format-to-parser mapping, and a custom parser that gets selected is called with the opened file object and the same settings object. An explicit SPIDERFEEDER_INPUT_FORMAT may therefore select either a built-in parser or a parser configured through this mapping.

When no explicit format setting is present, selecting the parser by URI extension must behave exactly as before.

Parsing txt and the values yielded

When the resolved format is txt, the content is treated as one URL per line. Line terminators are removed from the line values. When SPIDERFEEDER_INPUT_FIELD is unset or falsey, each line yields:

(url, {})

As an example, content containing:

http://url1.com
http://url2.com

yields, in this order:

('http://url1.com', {})
('http://url2.com', {})

For the other parsers, the existing structured-input behavior is preserved: when SPIDERFEEDER_INPUT_FIELD is truthy, each parsed item must be a dictionary, the selected field provides the URL, and the full parsed dictionary is yielded as metadata. If an item of this kind from a parser is not a dictionary, iteration raises TypeError with the message:

Data is expected to be a dict when SPIDERFEEDER_INPUT_FIELD is set.
Selecting the file handler

The opener is selected from the URI scheme exactly as before:

  • the local file handler is used when there is no scheme or the scheme is file://;
  • the S3 file handler is used for s3://;
  • mappings provided through SPIDERFEEDER_FILE_HANDLERS continue to extend or override the default scheme-to-handler mapping.

The handler that is selected must receive the complete original uri, including its scheme and extension, as its first positional argument. It must also receive the file encoding through the keyword argument encoding.

Encoding of the input

The encoding is resolved independently from the format:

  1. If SPIDERFEEDER_INPUT_FILE_ENCODING is configured, its value is passed unchanged as the handler's encoding argument.
  2. If that setting is absent, 'utf-8' is used as the default.

The default call therefore has the observable form:

handler(uri, encoding='utf-8')

whereas a configuration such as:

SPIDERFEEDER_INPUT_FILE_ENCODING = 'latin-1'

requires:

handler(uri, encoding='latin-1')

This rule applies to local, S3, and custom handlers, including when SPIDERFEEDER_INPUT_FORMAT is configured as well.

Compatibility and Scope

  • Selecting the format explicitly adds an override; when the setting is absent, it neither replaces nor weakens extension-based detection.
  • A format override must work for local URIs with no scheme, file:// URIs, and s3:// URIs.
  • A URI extension that conflicts remains part of the URI passed to the opener even though it is not used for parser selection.
  • CSV and JSON parsing as it currently exists, URL-field extraction, metadata output, custom file handlers, and custom file parsers must continue to work.
  • The constructor, the iterable interface, and the shape of the yielded pairs must not change.

Specification of the Task

Overview

Within the spider_feeder package, the functions that open files are to be reworked so that they accept a Scrapy Settings object as a required keyword argument; FileStore is to be updated as well, so that its settings are forwarded to whichever file opener it invokes. For S3 access, the credentials must be read from the settings that are passed in rather than from a globally-loaded project settings.

API and Behavior Requirements

1. Opener for local files

Module: spider_feeder.store.file_handler.local

The function to provide:

def open(uri, *, encoding, settings)

How it behaves:

  • It accepts a file path or a URI that carries the file:// scheme, together with an encoding keyword argument and a settings keyword argument (a Scrapy Settings instance).
  • When the URI comes with the file:// scheme, the scheme is stripped off, leaving only the local filesystem path (e.g. file:///tmp/input_urls.txt → /tmp/input_urls.txt). A plain path that has no scheme is used as-is.
  • The local path, once resolved, is opened with the built-in open; only the path and the encoding keyword argument go into that call (the settings argument is accepted, yet it is not forwarded to the built-in open).
  • The built-in open must be referenced in a manner that keeps it patchable as spider_feeder.store.file_handler.local.builtins.open (that is, the builtins module is imported and builtins.open is called).
2. Opener for S3 files

Module: spider_feeder.store.file_handler.s3

The function to provide:

def open(uri, *, encoding, settings)

How it behaves:

  • It accepts a URI that carries the s3:// scheme, together with an encoding keyword argument and a settings keyword argument (a Scrapy Settings instance).
  • The URI is parsed, and from it the bucket name, the object key, and the optional inline credentials of the form s3://key_id:secret@bucket/key are extracted.
  • An S3 client is created by means of a botocore session's create_client('s3', ...).
  • Resolution of credentials:
    • If inline credentials (key_id:secret@) are found in the URI, they are the ones to use: create_client('s3', aws_access_key_id=<key_id>, aws_secret_access_key=<secret>) is called.
    • Otherwise, the credentials are read from the passed settings using the keys SPIDERFEEDER_AWS_ACCESS_KEY_ID and SPIDERFEEDER_AWS_SECRET_ACCESS_KEY, and create_client('s3', aws_access_key_id=<value>, aws_secret_access_key=<value>) is called.
    • The URI and the passed settings are the only sources from which credentials must be obtained; do not load or consult any global/project settings.
  • The object is fetched through get_object, which receives Bucket=<bucket>, Key=<key>, and ResponseContentEncoding=<encoding> as its parameters.
  • The object body is read and decoded with the given encoding, and the content is returned wrapped in an in-memory text stream (io.StringIO), so that the caller can .read() the full text.
3. FileStore

Module: spider_feeder.store.file_store — the class here is FileStore.

Constructor signature (this one does not change):

FileStore(uri, settings)

What changes in behavior:

  • Whenever FileStore chooses a file opener (the choice hinges on the URI scheme / configured handlers) and invokes it, the opener must be called with the URI, the resolved encoding keyword argument, and in addition a settings keyword argument whose value is the exact Settings instance that was passed into the FileStore constructor.
  • The encoding is worked out as it was before: utf-8 is the default, and the SPIDERFEEDER_INPUT_FILE_ENCODING setting can override it.
  • How handlers are picked does not change: the local and S3 openers are what the built-in schemes map to, and custom handlers can be registered through the SPIDERFEEDER_FILE_HANDLERS setting (that is, a mapping of scheme → dotted path to an opener callable). Any custom opener will be invoked with the settings keyword argument too.
  • All of the parsing/iteration behavior already present (txt, csv, json formats; SPIDERFEEDER_INPUT_FIELD; SPIDERFEEDER_INPUT_FORMAT taking precedence over file extension) is untouched; the only thing required here is the addition of the settings keyword argument to the opener call.

The call contract, summed up

This signature is what every file opener callable used by FileStore must accept:

opener(uri, *, encoding, settings)

and, when it makes the call, FileStore must always supply all three.
