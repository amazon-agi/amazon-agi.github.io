Summary

You must implement a property called scale_degrees_wrt_major on the Key class that lives in the module pyabc2.key. In addition, you must ensure that the module-level mapping IONIAN_SHARPFLAT_COUNT exists and can be imported from pyabc2.key.

Background

In pyabc2.key, the Key class is assembled from a string that joins a root note and a mode name, e.g. Key("Cmajor"), Key("Ddorian"), etc. Among the mode names are the standard diatonic modes (ionian, dorian, phrygian, lydian, mixolydian, aeolian, locrian), together with equivalents such as "major"/"minor".

Public API Requirements

pyabc2.key.IONIAN_SHARPFLAT_COUNT

A dict-like mapping defined at module level: the keys it holds are the valid Ionian (major-scale) roots, written as note-name spellings (e.g. "C", "G", "D", "F", "Bb", "F#", etc.). Exactly the roots that yield a valid Key whenever they are joined with any mode name to form a Key must make up this mapping's key set. When iterated over, the mapping must produce these root-name strings.

Key.scale_degrees_wrt_major (property)

A read-only property attached to Key returns, for the key's mode, the scale degrees expressed relative to the major (ionian) scale.

Required behavior:

  • The value the property returns describes the intervallic content of the mode on its own, with no dependence on the key's root. Put another way: once the mode is fixed, the scale_degrees_wrt_major value must be identical no matter which root note was used to build the Key.

  • To make this concrete: for every root in IONIAN_SHARPFLAT_COUNT, build Key(f"{root}{mode}") while mode is held fixed, and read scale_degrees_wrt_major from each one; the values produced this way must all be equal to one another.

  • For every mode name in the set of supported modes, that equality must hold.

  • Equality comparison (==) between two instances must be supported by the returned value, so that equal contents compare equal.

Constraints

  • All root spellings found among the keys of IONIAN_SHARPFLAT_COUNT must be usable for building a valid Key when they are concatenated with any supported mode name.

Required behavior: .name after arithmetic

Take PitchClass.from_name("C") as the starting point:

  • Adding d semitones results in a pitch class whose .name is the natural-or-sharp spelling of the pitch class d semitones above C.
  • Subtracting d semitones results in a pitch class whose .name is the natural-or-sharp spelling of the pitch class d semitones below C.

semitones mod 12 name

1 C#
2 D
3 D#
4 E
5 F
6 F#
7 G
8 G#
9 A
10 A#
11 B

The rule above must hold for arbitrary integer offsets, including large values and offsets that wrap around beyond one octave (the effective semitone offset is taken modulo 12). Negative wrapping works the same way for subtraction (e.g. subtracting 1 from C gives B).

    • "unicode": sharps are written as ♯, flats as ♭.

def solfege_in(self, key: Key) -> str

Listed relative to the tonic in semitone order 0–11, the chromatic solfège syllables are:

  • 0: Do
  • 1: Di (raised 1) / Ra (lowered 2)
  • 2: Re
  • 3: Ri / Me
  • 4: Mi
  • 5: Fa
  • 6: Fi / Se
  • 7: Sol (rendered as Si for the raised-4 spelling — see below)
  • 8: Si (raised 5) / Le (lowered 6)
  • 9: La
  • 10: Li (raised 6) / Te (lowered 7)
  • 11: Ti

  • The chosen syllable must be consistent with the note's spelling (sharp spellings use the "raised" syllable, flat spellings use the "lowered" syllable).
  • The required results are:
    • C → "Do", D → "Re", B → "Ti"
    • C# → "Di", G# → "Si", Bb → "Te"
  • A spelling that has no valid solfège syllable for its spelled position raises ValueError. In particular:
    • Cb, Fb (no flat-4 syllable), G##, B# all raise ValueError.

Behavior when a pitch class is constructed by value in the key of C major:

  • Diatonic values appear as their single syllable: 0 → "Do", 2 → "Re", 11 → "Ti".
  • Chromatic values appear as a slash-separated pair of the raised and lowered syllables:

All of the following must be importable from pyabc2.pitch: Pitch, PitchClass, SignedInterval, SimpleInterval, _to_roman, pitch_class_value.

scale_degree_in and solfege_in behave differently depending on whether the PitchClass was created via from_name (a definite spelling is known) versus via PitchClass(value) (only a chromatic value, potentially ambiguous). A pitch class must keep track of whether it has a known letter/accidental spelling, so that these methods can produce a single unambiguous result versus a slash-separated enharmonic pair.

10 PyABC2 models pitches and notes that are parsed from ABC notation. 609 words · rewritten by GPT-5.6-sol, reworded by GLM-5.3-Flash

Overview

PyABC2 models pitches and notes that are parsed from ABC notation. This task fixes how accidental spellings are retained by the public Note.from_abc(...) API. A Note that this parser returns must keep the notated pitch letter together with the multiplicity of any explicitly written sharp or flat, rather than keeping only the chromatic value and later picking a simpler enharmonic name.

This is a correction to the spelling, not a change to the note's sounding pitch, octave, or duration.

Required Public Behavior

Note.from_abc must retain the spelling it parses

When Note.from_abc(abc, ...) parses a valid ABC note that carries explicit accidental marks, the Note it returns must keep that spelling in its pitch identity and its string representation. In the library's ASCII pitch-name form, ABC accidentals are represented as follows:

  • ^ maps to #.
  • ^^ maps to ##.
  • _ maps to b.
  • __ maps to bb.
  • If there is no accidental, no accidental character is added.

The library's pitch-name format renders the input letter in uppercase, but its diatonic identity must stay the same. Each explicitly written sharp or flat contributes a single corresponding character. The result must not be respelled to some other letter merely because that letter is enharmonically equivalent.

The retained spelling is part of the returned Note itself, and not merely an unrelated formatting substitution. The pitch-name and pitch-class views that already exist for that parsed note must therefore remain consistent with the retained spelling. In particular, when the parsed note is viewed as a pitch class, an explicitly notated F## must not be turned into G. Note.from_abc is the primary entry point for this requirement; if ABC parsing discards the spelling, support for spelling on an independently constructed Pitch or PitchClass is not sufficient.

Format of the string

For a parsed note, str(note) continues to use this format:

<letter><accidental(s)><octave>_<duration>

in which:

  • <letter> is the notated pitch letter, in uppercase.
  • <accidental(s)> contains the ASCII accidental characters that are retained, including repeated characters for double accidentals.
  • <octave> is the integer octave as computed.
  • <duration> is the fractional duration as computed, in numerator/denominator form.
Double-sharp example (normative)

Take the ABC note ^^f',,3:

  • ^^ spells a double sharp explicitly.
  • F is the notated base letter.
  • The existing octave rules give octave 4.
  • The existing duration rules give duration 3/8.

Accordingly:

str(Note.from_abc("^^f',,3")) == "F##4_3/8"

Although the chromatic pitch of F##4 is the same as that of G4, the result must remain F##4_3/8; it must not become G4_3/8.

Requirements for Compatibility

All the rest of the parsing and conversion behavior must remain unchanged. In particular, the following existing results must continue to hold:

str(Note.from_abc("_B,2,")) == "Bb3_1/4"
str(Note.from_abc("^f")) == "F#5_1/8"
str(Note.from_abc("C/")) == "C4_1/16"

The correction must not modify any of the following:

  • the calculation of chromatic pitch values;
  • the calculation of the octave from letter case, commas, and apostrophes;
  • duration calculation or the formatting of fractions;
  • the existing handling of single accidentals or of notes without accidentals;
  • the existing behavior of key-aware parsing; or
  • the canonical naming behavior for values that do not carry a spelling that was explicitly retained.

Scope

The change that is required is limited to keeping accidental spelling on notes that are produced from ABC notation; double sharps are the motivating case, and the same character-for-character multiplicity rule applies to explicit sharps and flats generally.
