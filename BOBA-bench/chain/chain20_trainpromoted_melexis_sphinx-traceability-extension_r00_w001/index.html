01 Purge Capabilities for Traceable Items and Collections 2086 words · rewritten by GPT-5.6-sol, reworded by GLM-5.3-Flash

Task Specification: Purge Capabilities for Traceable Items and Collections

Goal

Purge functionality must be added for traceable items, and the separation between relations declared explicitly and relations derived implicitly must be kept intact across the whole collection lifecycle. When a purge happens, it must drop the explicit relation declarations, keep the implicit relation information, render the purged definition invalid, and make it possible for the same identifier to be defined again later and refreshed without any purged explicit relation being restored.

Compatibility must be preserved with all of the existing item, relation, placeholder, metadata, and validation behavior described below.

Public API

The public types listed below are the ones that remain available from mlx.traceable_item:

  • TraceabilityException
  • TraceableItem
  • TraceableCollection
TraceabilityException

Invalid traceability operations and invalid traceability state are the situations in which the domain-specific error TraceabilityException gets raised.

It must be a subclass of ValueError. Callers may, as a consequence, catch it either as TraceabilityException or as ValueError. Where appropriate, an operation that the documentation below describes as raising ValueError may raise TraceabilityException, since that compatibility contract is what it satisfies.

TraceableItem

Construction of an Item and Its Metadata

The constructor of an item has this form:

TraceableItem(identification, placeholder=False)
  • The item's identifier is identification; get_id() returns this value unchanged.
  • With placeholder=False, the item is a normal one, and is_placeholder() returns False.
  • An item for which placeholder=True was passed is in an unresolved condition: is_placeholder() returns True, and self_test() raises TraceabilityException until the collection's item-refresh path resolves that placeholder.
  • An item that has just been constructed possesses no document, no node, no caption, and no content.

The behavior of the metadata methods that already exist is the following:

  • What set_document(docname, lineno=0) records are the document name and the line number, and get_document() and get_line_number() return them. If the line-number argument is left out, the value recorded is 0.
  • Assigning a document has no effect on placeholder status. Specifically, once set_document(...) has been called on an item that was created with placeholder=True, the item is still a placeholder, and self_test() must still raise TraceabilityException.
  • Giving a document to a normal, non-placeholder item makes that item valid with respect to the document requirement, provided that no other invalid condition exists.
  • The node that get_node() returns is stored by bind_node(node).
  • The values returned by get_caption() and by get_content() are stored by set_caption(caption) and by set_content(content), respectively.

Assigning a document and resolving a placeholder therefore constitute separate state transitions.

Targets, Explicit and Implicit

To add a target, the following call is used:

add_target(relation, target_identification, implicit=False)
  • An explicit target — a relation that a caller declares directly — is what the default, implicit=False, creates.
  • An implicit target, meaning derived relation information — for instance an automatically generated reverse relation — is what implicit=True creates.
  • No automatic reverse relation is generated by a direct call to add_target; automatic reverse creation is something that happens at the collection level.

A sorted list of the target identifiers that match is what iter_targets(relation, explicit=True, implicit=True) returns:

  • Both explicit and implicit targets are returned when both flags sit at their defaults.
  • Explicit targets are excluded when explicit=False is set.
  • Implicit targets are excluded when implicit=False is set.
  • When the relation has no selected target, an empty list is returned.
  • It must not happen that a target is returned more than once.

The existing behavior around duplicates and promotion must be preserved:

  • If a target is already explicit for the same relation, adding it raises TraceabilityException and the relation remains unchanged — no matter whether the repeated request is explicit or implicit.
  • Adding the same implicit target again as implicit is idempotent, and no duplicate is created.
  • If an explicit target is added although that target already exists implicitly, the target is moved from implicit to explicit and remains present exactly once.

iter_relations() returns the names of the item's relations, sorted. With remove_targets(target_identification, explicit=False, implicit=True), the selected kinds of relation pointing to that target are removed across relation names. Only implicit targets are removed by default; the categories to remove are chosen independently by the explicit and implicit flags.

purge()

The public method to be added is:

purge()

The following must hold when purge() is called:

  1. All explicit targets must be removed from the item, covering every relation.
  2. All implicit targets must be preserved in exactly the state they had before the call.
  3. The item must be left in a purged state that is invalid yet refreshable, such that a subsequent self_test() raises TraceabilityException.
  4. The item's identifier must be preserved, so that the collection can refresh the same logical item later.

No matter how many relations or targets the item has, these rules apply. Specifically:

  • Take an item that has an assigned document and one explicit target for a relation: once purge() has run, iter_targets(relation) returns an empty list.
  • If one implicit target is what it has instead, iter_targets(relation) still returns a one-element list containing the original target after purge().
  • In either case self_test() raises; this includes the situation where no relation targets remain.

Sharing between the invalid purged state and the collection's placeholder-refresh lifecycle is something that may happen; nevertheless, callers must not be required to do the reconstruction of the retained implicit relations themselves.

Validation of an Item

self_test() returns normally in the valid case and raises TraceabilityException in the case where the item is not valid. The invalid states include the following:

  • the item is in the placeholder state;
  • no source document is attached to the item;
  • targets occur in duplicate; or
  • the item has been purged and a refresh has not yet happened.

Collection-wide target existence and automatic reverse links are not verified at the item level; those checks are the job of TraceableCollection.self_test().

TraceableCollection

No arguments are needed to construct a collection:

TraceableCollection()

Neither items nor registered relations are present in its initial state. The empty-string sentinel that is used for a relation having no reverse relation continues to be NO_RELATION_STR.

Registering Relations and Looking Them Up

Registration of relation types happens via add_relation_pair(forward_relation, reverse_relation=NO_RELATION_STR).

  • A nonempty reverse relation means the mapping is bidirectional: by way of get_reverse_relation(...), each relation is returned as the reverse of the other one, and both names are present in iter_relations().
  • Taking the default empty reverse relation leads to registration of the forward relation only, and get_reverse_relation(forward_relation) returns NO_RELATION_STR.
  • When an unknown relation is passed to get_reverse_relation(...), the return value is None.
  • The relation names that have been registered are returned by iter_relations(), sorted.
Looking Up Items and Adding Them
  • What get_item(identification) returns is the stored item, or None when no item with that identifier is currently available.
  • Whether that identifier is present in the collection is reported by has_item(identification).
  • The identifiers in storage are returned by iter_items() in sorted order.

For add_item(item), three distinct cases exist:

  1. New identifier: a normal addition of the item takes place.
  2. Existing placeholder or purged state: the existing logical item may undergo a refresh via the new definition. What get_item(...) reflects is the metadata from the concrete definition, the item after refreshing is a placeholder no longer, and relation state that was already retained for that logical item is preserved, subject to the purge rules. Specifically, the implicit reverse relations that a placeholder carries survive once its concrete definition has been supplied.
  3. Existing concrete definition: here we have an ordinary duplicate definition. add_item raises TraceabilityException; nothing changes regarding the previously stored item, its contents, or the collection's item count. Adding the exact same concrete object twice falls under this rule as well.

Consequently, refresh or replacement is permitted only in the case of a placeholder or of the equivalent refreshable state that purge created. Ordinary duplicate concrete definitions must not be turned into silent overwrites by it.

How Relations Are Added

Through the collection, a relation is added by means of add_relation(source_identification, relation, target_identification):

  • Knowledge of the source identifier must already exist. For an unknown source, ValueError is raised and the collection is left unchanged.
  • As for the relation, it must have been registered. With an unknown relation, TraceabilityException is raised, and no forward or reverse target comes into existence.
  • What is added to the source is an explicit relation.
  • Should the registered relation possess a reverse relation, then on the target item the corresponding reverse target is implicit.
  • In case that target item is not yet known, a placeholder for it is created by the collection, and the implicit reverse target is recorded on that placeholder. The placeholder gets resolved once the target's concrete definition is supplied later, and that reverse target is retained in the process.
  • For a unidirectional relation, creation of neither a reverse target nor a placeholder target item happens.
Item Removal

Purge and remove_item(identification) are distinct operations:

  • The named item is removed from the collection by it.
  • Among the remaining items, implicit targets that point at the removed identifier get removed.
  • Among the remaining items, explicit targets that point at the removed identifier are kept. Those dangling explicit references will be reported by collection validation in the case of bidirectional relation types.
purge(docname)

Every item definition associated with the given document is purged by purge(docname), while definitions that belong to other documents come out unaffected. The item-level purge semantics must be applied by it to each matching item:

  • the purged definition's explicit targets are discarded;
  • the implicit targets are kept, serving as refreshable relation information;
  • until it is supplied once more, the definition does not count as a valid concrete item; and
  • the placeholder/purged refresh case of add_item is still something the identifier qualifies for.

A document purge does not remove the relation pairs that have been registered. For the surviving implicit relations to be restored when an item with the same identifier gets added again, purge must hold on to enough state. An explicit relation that was removed by purge must not be recreated or retained by it.

Validation of the Collection

Collection-wide state is what self_test(docname=None) validates:

  • A collection lacking registered relations raises TraceabilityException.
  • Each item that falls within scope must pass its item-level self_test().
  • Take a relation whose registered reverse is nonempty: it must be true of every target that it exists and that it contains the corresponding reverse relation back to the source; failing that, TraceabilityException is raised.
  • It is not required for targets of unidirectional relations to be collection items.
  • If docname is given, that validation scope does not cover concrete items assigned to a different non-None document. Validation continues to apply to items lacking a document, unresolved placeholders included.
  • A collection that is valid returns normally.

The Required Purge-and-Refresh Scenario

Key collection behavior is defined by the sequence of steps below:

  1. A source item and a target item are created, both are assigned to the same document, and both go into a collection.
  2. A forward/reverse relation pair gets registered.
  3. The forward relation is added, going from source to target. What this produces is an explicit forward target on the source together with an implicit reverse target on the target.
  4. A purge(docname) call is made for their document.
  5. Item definitions that are new and non-placeholder, carrying the same identifiers and document, are then created and added to the collection.

Once both definitions have gone through addition a second time:

  • No target for the forward relation is present on the refreshed source; the old explicit relation must not come back.
  • For the reverse relation, the refreshed target has exactly one target, and that target is equal to the source identifier. Through the purge/refresh cycle the implicit relation survives, with no duplication.
  • is_placeholder() == False is what both refreshed items report, and the document metadata that was newly supplied is contained in them.

Scope and Non-goals

  • From the reverse links that are retained, explicit declarations are neither inferred nor regenerated by purge.
  • Collection-level reverse-link behavior is not something direct item-level add_target acquires.
  • Externally visible state transitions and query results are what the required behavior concerns; for refreshable purged items, no particular internal storage strategy is required.

Overview

Add to mlx.traceable_item.TraceableCollection a public operation that purges one identified item, while respecting how explicitly declared relations differ from automatically generated implicit reverse relations.

Exposed by the module are TraceableCollection, TraceableItem, and TraceabilityException. Existing public APIs and behavior must stay compatible.

Public API

TraceableCollection.purge_item(self, item_id)

A public method called purge_item must be added.

  • item_id: the string identifier of an item that is currently present in the collection.
  • Return value: no particular return value is required, and none is relied upon.

The required behavior given below applies when item_id identifies an item that exists. Behavior when the identifier is unknown is not specified by this task.

TraceabilityException

TraceabilityException must be a ValueError subclass. In particular, the public compatibility property below must hold:

issubclass(TraceabilityException, ValueError) is True

It must stay available as the traceability-specific exception type and, at the same time, be catchable by callers that catch ValueError. Collection errors that already exist and are catchable as ValueError, such as adding a relation from an unknown source item, must continue to be catchable as ValueError.

Relation Model

Paired relation types can be configured on a collection. Adding an explicit relation from item A to item B through the collection produces:

  • an explicit forward relation on A that targets B; and
  • when the relation has a configured reverse, an automatically generated implicit reverse relation on B that targets A.

purge_item must preserve this distinction in provenance. An explicit relation must not be treated as disposable merely because its target is the item being purged.

Required Purge Behavior

When purge_item(item_id) is called for an item that exists:

  1. Take the item out of the live collection.

    • After the call has been made, get_item(item_id) must return None.
    • The identifier that was removed must no longer be reported as a live collection item.

  2. Remove from all surviving items the implicit relations that point to the purged identifier.

    • Every relation that is automatically generated/implicit and whose target is item_id must be removed.
    • The corresponding relation on a surviving item, including when queried through iter_targets(...), must no longer report item_id as an implicit target.
    • For example, if A explicitly relates to B and B consequently carries an implicit reverse relation to A, purging A must remove B's implicit relation to A.

  3. Retain explicit relations to the purged identifier on surviving items.

    • An explicitly declared relation is owned by its surviving source item and must not be deleted when its target is purged.
    • After the purge, querying that relation must still return the purged identifier.
    • For example, if A holds an explicit relation to B, purging B must leave A's explicit target B intact.

  4. Surviving state must not be corrupted.

    • Resetting the purged item's state, or retaining it, must not mutate relation data or other mutable state belonging to surviving items.
    • If the collection retains information about purged items for later reuse, that bookkeeping must be isolated from the live collection state, so that later operations and consistency checks observe only the intended changes listed above.

Consistency-Check Semantics

After a purge, TraceableCollection.self_test() must still enforce its normal relation-validity rules; the method must not be weakened merely so that every purged collection appears valid.

  • Surviving references that are implicit-only: If the only relations on surviving items that targeted the purged identifier were implicit relations, then purge_item removes them. For a collection that is otherwise valid and has configured relations, self_test() must then complete without raising.
  • Explicit reference that is preserved: If a surviving item retains an explicit paired/bidirectional relation that targets the now-absent identifier, that relation is dangling. self_test() must raise TraceabilityException, because the target is no longer present in the live collection.

As a result, successful consistency checking is conditional: purging a relation source and cleaning up the backlinks it generated can leave the collection valid, whereas purging the target of a surviving explicit internal relation deliberately leaves an inconsistency for self_test() to report. The explicit relation must not be removed, and the consistency check must not be relaxed, in order to force the latter case to pass.

Supporting Public Behavior

  • TraceableItem(identification) builds an item using the supplied string identifier.
  • TraceableCollection.get_item(item_id) returns the live item that has that identifier, or None when it is absent.
  • The existing relation-query options that tell explicit and implicit targets apart must keep reflecting the relation provenance after a purge.

Compatibility and Scope

  • purge_item is to be added without any existing public method being removed or renamed. Existing APIs — such as item addition, relation addition, item-level relation queries, document-level purging, and any existing operation for removing items — must stay available and retain their established behavior.
  • Apart from making TraceabilityException a ValueError subclass as required above, unrelated APIs must not be redesigned.
  • No specific internal storage strategy for removed items is required; what is required is only the externally observable behavior and state isolation described here.

Task Description

Overview

The TraceableCollection class must be modified; it is located in the module imported as dut (the module that contains TraceableCollection and TraceableItem).

Required Change

At present, the TraceableCollection class exposes a method called get_matches. This method must be given the new name get_items. Any callers in the codebase that depend on this functionality must use the new name.

Specification of the get_items Method

Signature:

def get_items(self, regex)

Behavior:

The get_items method accepts one argument, a regular expression pattern (a string), and returns a collection (one that supports len()) of the identifiers of the items in the collection whose identifier matches the supplied pattern.

The method must satisfy the following rules:

  1. When it is called on a collection that has no real items, it returns an empty result (length 0), no matter which pattern is used.

  2. Items that are only placeholders (meaning they are referenced as relation targets but never explicitly added to the collection) must NOT be counted or returned.

  3. Items that were explicitly added to the collection and whose identifier matches the given regular expression pattern must be counted and returned.

  4. When an item that has actually been added later takes the place of a placeholder, that item then counts as a real item and is included in the result.

Example demonstrating the expected counting behavior:

  • A collection that has a relation pair configured but no items: get_items('\w*') returns length 0.
  • After one real item is added and a relation is created from it to a target that has not yet been added (this creates a placeholder for the target): get_items('\w*') returns length 1 (the real item is the only one that counts; the placeholder target is excluded).
  • After the target is then added as a real item: get_items('\w*') returns length 2.
Constraints
  • get_matches, the old method name, must no longer be the public entry point; the method is now get_items, whose filtering behavior is identical.

19 Add a new public method get_attributes to the TraceableItem class, which resides in the module mlx.traceable_item. 345 words · source specification, reworded by GLM-5.3-Flash

Specification of the Task

Goal

Add a new public method get_attributes to the TraceableItem class, which resides in the module mlx.traceable_item.

Background

Managing attributes is already supported by the TraceableItem class through existing methods, including:

  • define_attribute(key, regex) — a class-level method that registers an allowed attribute key together with a validating regex.
  • add_attribute(key, value, overwrite=True) — stores an attribute value on the item.
  • get_attribute(key) — returns the value stored for a single attribute key, or else a falsy value (empty string) when the key has no value.

A single new method, described below, must be added. The behavior of the existing methods must not be changed.

New Method That Must Be Added

get_attributes(self, attribute_keys)

Input: A list made up of attribute key strings.

Output: A list of attribute value strings, with one entry for each input key, in the same order as the input keys.

Behavior:

  • For each key from the input list, the output entry that corresponds to it is the value currently stored on the item for that attribute.
  • If a key does not have a stored value on the item, the corresponding output entry is the empty string ''.
  • The output list must contain exactly one element for each input key, with the order of the input keys preserved. When the input keys are reordered, the output list must be correspondingly reordered.

Behavior examples:

  • Called with one key that has no value set → returns [''].
  • Called with one key whose value is V → returns [V].
  • Called with the two keys [k1, k2], where k1 maps to V1 and k2 maps to V2 → returns [V1, V2].
  • Called with those same keys in the reverse order [k2, k1] → returns [V2, V1].

Remarks

  • The method must not raise for keys that have no stored value; keys like these simply produce ''.
  • Every piece of existing attribute-related behavior (validation on add_attribute, overwrite semantics, get_attribute, remove_attribute, self_test, stringification, and attributes_match) must continue to work unchanged.

Specification of the Task

Summary

Add a new class, TraceableAttribute, which represents a defined attribute (a named key together with an associated value-validation regular expression). Change the attribute-definition mechanism on TraceableItem such that attributes are defined by passing a TraceableAttribute instance instead of a key/regex pair.

Required Public API

New module to be added: mlx.traceable_attribute

The class TraceableAttribute must be exposed by this module.

Constructor of TraceableAttribute
TraceableAttribute(attrid, value)
  • attrid: the key/name of the attribute (a string).
  • value: the string holding the regular expression used to validate the values assigned to this attribute.

The constructor is required to accept these two positional arguments and to store them, so that the instance fully describes the attribute (its key and its validation regex).

Modification to mlx.traceable_item.TraceableItem

The signature of the class method for defining an attribute must change so that it accepts a single TraceableAttribute instance rather than a separate key and regex:

TraceableItem.define_attribute(attribute)
  • attribute: a TraceableAttribute instance.

The attribute must be registered by the method using the key and validation regex carried by the supplied TraceableAttribute instance. The effective behavior of defining an attribute (that is, which attribute key becomes known and which regex governs valid values for it) must remain equivalent to a prior call of the method with the corresponding key and regex, but the value now comes from the passed TraceableAttribute object.

Notes

  • The existing accessors — TraceableItem for mlx.traceable_item and TraceableCollection for mlx.traceable_collection — remain in place; the only change is to the attribute-definition entry point, as described.
