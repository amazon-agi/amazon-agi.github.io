01 Purge Support for Traceable Items and Collections 1704 words · rewritten by GPT-5.6-sol

Task Specification: Purge Support for Traceable Items and Collections

Objective

Add purge support to traceable items and preserve the distinction between explicitly declared and implicitly derived relations throughout the collection lifecycle. Purging must remove explicit relation declarations, retain implicit relation information, invalidate the purged definition, and allow a later definition of the same identifier to be refreshed without restoring any purged explicit relation.

All existing item, relation, placeholder, metadata, and validation behavior described below must remain compatible.

Public API

The following public types remain available from mlx.traceable_item:

  • TraceabilityException
  • TraceableItem
  • TraceableCollection
TraceabilityException

TraceabilityException is the domain-specific error raised for invalid traceability operations and invalid traceability state.

It must be a subclass of ValueError. Consequently, callers may catch it either as TraceabilityException or as ValueError. Operations documented below as raising ValueError may raise TraceabilityException where appropriate because it satisfies that compatibility contract.

TraceableItem

Construction and metadata

An item is constructed as:

TraceableItem(identification, placeholder=False)
  • identification is the item's identifier and is returned unchanged by get_id().
  • A normal item has placeholder=False; is_placeholder() returns False.
  • An item constructed with placeholder=True is unresolved; is_placeholder() returns True and self_test() raises TraceabilityException until that placeholder is resolved through the collection's item-refresh path.
  • A newly constructed item has no document, node, caption, or content.

The existing metadata methods retain their behavior:

  • set_document(docname, lineno=0) records the document name and line number. get_document() and get_line_number() return those values. Omitting the line-number argument records 0.
  • Document assignment does not change placeholder status. In particular, calling set_document(...) on an item created with placeholder=True leaves it a placeholder, and self_test() must still raise TraceabilityException.
  • For a normal non-placeholder item, assigning a document makes the item valid with respect to the document requirement, provided no other invalid condition exists.
  • bind_node(node) stores the node returned by get_node().
  • set_caption(caption) and set_content(content) store values returned by get_caption() and get_content() respectively.

Thus, document assignment and placeholder resolution are separate state transitions.

Explicit and implicit targets

Targets are added with:

add_target(relation, target_identification, implicit=False)
  • The default, implicit=False, creates an explicit target: a relation directly declared by a caller.
  • implicit=True creates an implicit target: derived relation information such as an automatically generated reverse relation.
  • Calling add_target directly does not generate an automatic reverse relation. Automatic reverse creation is collection-level behavior.

iter_targets(relation, explicit=True, implicit=True) returns a sorted list of matching target identifiers:

  • With both flags at their defaults, it returns both explicit and implicit targets.
  • explicit=False excludes explicit targets.
  • implicit=False excludes implicit targets.
  • If no selected target exists for the relation, it returns an empty list.
  • A target must not be returned more than once.

Existing duplicate and promotion behavior must be preserved:

  • Adding a target that is already explicit for the same relation raises TraceabilityException and leaves the relation unchanged, whether the repeated request is explicit or implicit.
  • Re-adding the same implicit target as implicit is idempotent and does not create a duplicate.
  • Adding an explicit target that already exists implicitly moves that target from implicit to explicit; it remains present exactly once.

iter_relations() returns the item's relation names in sorted order. remove_targets(target_identification, explicit=False, implicit=True) removes the selected kinds of relation to that target across relation names. By default it removes implicit targets only; the explicit and implicit flags independently select which categories are removed.

purge()

Add the following public method:

purge()

Calling purge() must:

  1. Remove all explicit targets from the item, across every relation.
  2. Preserve all implicit targets exactly as they were before the call.
  3. Leave the item in an invalid, refreshable purged state so that a subsequent self_test() raises TraceabilityException.
  4. Preserve the item's identifier so the collection can later refresh the same logical item.

These rules apply regardless of how many relations or targets the item has. In particular:

  • If an item with an assigned document has one explicit target for a relation, iter_targets(relation) returns an empty list after purge().
  • If it instead has one implicit target, iter_targets(relation) still returns a one-element list containing the original target after purge().
  • self_test() raises after either case, including when no relation targets remain.

The invalid purged state may share the collection's placeholder-refresh lifecycle, but callers must not be required to reconstruct the retained implicit relations themselves.

Item validation

self_test() returns normally when the item is valid and raises TraceabilityException when it is not. Invalid states include:

  • the item is a placeholder;
  • the item has no source document;
  • duplicate targets exist; or
  • the item has been purged and has not yet been refreshed.

An item-level validation does not verify collection-wide target existence or automatic reverse links; those checks belong to TraceableCollection.self_test().

TraceableCollection

A collection is constructed with no arguments:

TraceableCollection()

It starts with no items or registered relations. NO_RELATION_STR remains the empty-string sentinel used for a relation with no reverse relation.

Relation registration and lookup

add_relation_pair(forward_relation, reverse_relation=NO_RELATION_STR) registers relation types.

  • With a nonempty reverse relation, the mapping is bidirectional: each relation is returned as the reverse of the other by get_reverse_relation(...), and both names appear in iter_relations().
  • With the default empty reverse relation, only the forward relation is registered and get_reverse_relation(forward_relation) returns NO_RELATION_STR.
  • An unknown relation passed to get_reverse_relation(...) returns None.
  • iter_relations() returns registered relation names in sorted order.
Item lookup and addition
  • get_item(identification) returns the stored item, or None when no current item with that identifier is available.
  • has_item(identification) reports whether the collection contains that identifier.
  • iter_items() returns stored identifiers in sorted order.

add_item(item) has three distinct cases:

  1. New identifier: the item is added normally.
  2. Existing placeholder or purged state: the existing logical item may be refreshed by the new definition. Metadata from the concrete definition is reflected by get_item(...), the refreshed item is no longer a placeholder, and relation state already retained for that logical item is preserved subject to the purge rules. In particular, implicit reverse relations on a placeholder survive when its concrete definition is supplied.
  3. Existing concrete definition: this is an ordinary duplicate definition. add_item raises TraceabilityException; the previously stored item, its contents, and the collection's item count remain unchanged. This rule also applies when the exact same concrete object is added twice.

Replacement or refresh is therefore permitted only for a placeholder or the equivalent refreshable state created by purge. It must not turn ordinary duplicate concrete definitions into silent overwrites.

Adding relations

add_relation(source_identification, relation, target_identification) adds a relation through the collection:

  • The source identifier must already be known. An unknown source raises ValueError and leaves the collection unchanged.
  • The relation must have been registered. An unknown relation raises TraceabilityException and creates no forward or reverse target.
  • The relation added to the source is explicit.
  • If the registered relation has a reverse relation, the corresponding reverse target on the target item is implicit.
  • If such a target item is not yet known, the collection creates a placeholder for it and records the implicit reverse target on that placeholder. Supplying the target's concrete definition later resolves the placeholder while retaining that reverse target.
  • If the relation is unidirectional, no reverse target and no placeholder target item are created.
Removing an item

remove_item(identification) remains distinct from purge:

  • It removes the named item from the collection.
  • Implicit targets in remaining items that point to the removed identifier are removed.
  • Explicit targets in remaining items that point to the removed identifier are retained. Collection validation will report those dangling explicit references for bidirectional relation types.
purge(docname)

purge(docname) purges every item definition associated with the given document and leaves definitions belonging to other documents unaffected. For each matching item it must apply the item-level purge semantics:

  • explicit targets belonging to the purged definition are discarded;
  • implicit targets are retained as refreshable relation information;
  • the definition ceases to be a valid concrete item until it is supplied again; and
  • the identifier remains eligible for the placeholder/purged refresh case of add_item.

Registered relation pairs are not removed by document purge. Purge must retain enough state to restore the surviving implicit relations when an item with the same identifier is added again. It must not recreate or retain an explicit relation that was removed by purge.

Collection validation

self_test(docname=None) validates collection-wide state:

  • A collection with no registered relations raises TraceabilityException.
  • Each in-scope item must pass its item-level self_test().
  • For a relation with a registered nonempty reverse, every target must exist and must contain the corresponding reverse relation back to the source; otherwise TraceabilityException is raised.
  • Targets of unidirectional relations are not required to be collection items.
  • When docname is supplied, concrete items assigned to a different non-None document are outside that validation scope. Items without a document, including unresolved placeholders, remain subject to validation.
  • A valid collection returns normally.

Required Purge-and-Refresh Scenario

The following sequence defines the key collection behavior:

  1. Create a source item and a target item, assign both to the same document, and add both to a collection.
  2. Register a forward/reverse relation pair.
  3. Add the forward relation from source to target. This produces an explicit forward target on the source and an implicit reverse target on the target.
  4. Call purge(docname) for their document.
  5. Create new, non-placeholder item definitions with the same identifiers and document, then add them to the collection.

After both definitions are added again:

  • The refreshed source has no target for the forward relation. The old explicit relation must not reappear.
  • The refreshed target has exactly one target for the reverse relation, equal to the source identifier. The implicit relation survives the purge/refresh cycle without duplication.
  • Both refreshed items report is_placeholder() == False and contain the newly supplied document metadata.

Scope and Non-goals

  • Purge does not infer or regenerate explicit declarations from retained reverse links.
  • Direct item-level add_target does not acquire collection-level reverse-link behavior.
  • The required behavior concerns externally visible state transitions and query results; no particular internal storage strategy for refreshable purged items is required.
02 Extend mlx.traceable_item.TraceableCollection with a public operation that purges one identified item while respecting the distinction between explicitly… 772 words · rewritten by GPT-5.6-sol

Overview

Extend mlx.traceable_item.TraceableCollection with a public operation that purges one identified item while respecting the distinction between explicitly declared relations and automatically generated implicit reverse relations.

The module exposes TraceableCollection, TraceableItem, and TraceabilityException. Existing public APIs and behavior must remain compatible.

Public API

TraceableCollection.purge_item(self, item_id)

Add a public method named purge_item.

  • item_id: the string identifier of an item currently present in the collection.
  • Return value: no particular return value is required or relied upon.

The required behavior below applies when item_id identifies an existing item. Behavior for an unknown identifier is not specified by this task.

TraceabilityException

TraceabilityException must be a subclass of ValueError. In particular, the following public compatibility property must hold:

issubclass(TraceabilityException, ValueError) is True

It must remain available as the traceability-specific exception type, while also being catchable by callers that catch ValueError. Existing collection errors that are catchable as ValueError, such as adding a relation from an unknown source item, must remain catchable as ValueError.

Relation Model

A collection can configure paired relation types. Adding an explicit relation from item A to item B through the collection creates:

  • an explicit forward relation on A targeting B; and
  • for a relation with a configured reverse, an automatically generated implicit reverse relation on B targeting A.

purge_item must preserve this provenance distinction. It must not treat an explicit relation as disposable merely because its target is being purged.

Required Purge Behavior

When purge_item(item_id) is called for an existing item:

  1. Remove the item from the live collection.

    • After the call, get_item(item_id) must return None.
    • The removed identifier must no longer be reported as a live collection item.

  2. Remove implicit relations to the purged identifier from all surviving items.

    • Every automatically generated/implicit relation whose target is item_id must be removed.
    • Querying the corresponding relation on a surviving item, including through iter_targets(...), must no longer report item_id as an implicit target.
    • For example, if A explicitly relates to B and B consequently has an implicit reverse relation to A, purging A must remove B's implicit relation to A.

  3. Preserve explicit relations to the purged identifier on surviving items.

    • An explicitly declared relation belongs to its surviving source item and must not be deleted by purging its target.
    • Querying that relation after the purge must still return the purged identifier.
    • For example, if A has an explicit relation to B, purging B must leave A's explicit target B intact.

  4. Do not corrupt surviving state.

    • Resetting or retaining the purged item's state must not mutate relation data or other mutable state belonging to surviving items.
    • If the collection keeps information about purged items for later reuse, that bookkeeping must be isolated from the live collection state so that later operations and consistency checks observe only the intended changes above.

Consistency-Check Semantics

TraceableCollection.self_test() must continue to enforce its normal relation-validity rules after a purge; it must not be weakened merely to make every purged collection appear valid.

  • Implicit-only surviving references: If the only relations on surviving items that targeted the purged identifier were implicit relations, purge_item removes them. Given an otherwise valid collection with configured relations, self_test() must then complete without raising.
  • Preserved explicit reference: If a surviving item retains an explicit paired/bidirectional relation targeting the now-absent identifier, that relation is dangling. self_test() must raise TraceabilityException because the target is no longer in the live collection.

Thus, successful consistency checking is conditional: purging a relation source and cleaning up its generated backlinks can leave the collection valid, whereas purging the target of a surviving explicit internal relation intentionally leaves an inconsistency for self_test() to report. The explicit relation must not be removed, and the consistency check must not be relaxed, to force the latter case to pass.

Supporting Public Behavior

  • TraceableItem(identification) constructs an item with the supplied string identifier.
  • TraceableCollection.get_item(item_id) returns the live item with that identifier, or None when it is absent.
  • Existing relation-query options that distinguish explicit and implicit targets must continue to reflect the relation provenance after purging.

Compatibility and Scope

  • Add purge_item without removing or renaming any existing public method. Existing APIs such as item addition, relation addition, item-level relation queries, document-level purging, and any existing item-removal operation must remain available and retain their established behavior.
  • Apart from making TraceabilityException a ValueError subclass as required above, do not redesign unrelated APIs.
  • No particular internal storage strategy for removed items is required; only the externally observable behavior and state isolation described here are required.

Required Change

The TraceableCollection class currently exposes a method named get_matches. This method must be renamed to get_items. Any callers within the codebase that rely on this functionality must use the new name.

Method Specification: get_items

Signature:

def get_items(self, regex)

Behavior:

get_items accepts a single argument, a regular expression pattern (string), and returns a collection (supporting len()) of the identifiers of items in the collection whose identifier matches the given pattern.

Rules the method must satisfy:

  1. When called on a collection that contains no real items, it returns an empty result (length 0), regardless of the pattern used.

  2. Items that exist only as placeholders (i.e., referenced as relation targets but never explicitly added to the collection) must NOT be counted or returned.

  3. Items that have been explicitly added to the collection and whose identifier matches the given regular expression pattern must be counted and returned.

  4. When a placeholder is later replaced by an actual added item, that item then counts as a real item and is included in the result.

Example of the expected counting behavior:

  • A collection with a relation pair configured but no items: get_items('\w*') returns length 0.
  • After adding one real item and creating a relation from it to a not-yet-added target (which creates a placeholder for the target): get_items('\w*') returns length 1 (only the real item counts; the placeholder target is excluded).
  • After then adding the target as a real item: get_items('\w*') returns length 2.
Constraints
  • The old method name get_matches must no longer be the public entry point; the method is now get_items with identical filtering behavior.
