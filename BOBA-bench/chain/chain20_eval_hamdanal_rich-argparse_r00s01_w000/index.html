Task Specification: rich_argparse Help Formatter

Overview

Implement a rich_argparse module that exports RichHelpFormatter, a drop-in replacement for argparse.HelpFormatter. It must preserve argparse’s help structure, substitutions, wrapping, indentation, and suppression semantics while using Rich styling when color output is enabled. ArgumentParser.format_help() must return the complete help string; formatting must not depend on help being emitted through an argparse help action.

When color is disabled, the visible output must match stock argparse exactly, subject only to the documented compact invocation format for options that have multiple option strings. When color is enabled for a terminal, styling must not change the visible text, spacing, wrapping, or line breaks.

Public API

rich_argparse.RichHelpFormatter

RichHelpFormatter must be importable as:

from rich_argparse import RichHelpFormatter

It must be an argparse.HelpFormatter-compatible class and support the standard constructor shape:

RichHelpFormatter(
    prog,
    indent_increment=2,
    max_help_position=24,
    width=None,
)

It must be usable as the formatter_class for a top-level argparse.ArgumentParser and for parsers created through add_subparsers() / add_parser(). As with argparse generally, subparsers do not automatically inherit the parent’s formatter; callers may explicitly provide the formatter for each subparser. The parent parser’s formatter must already be configured when add_subparsers() computes its program text.

The class must expose overridable formatting hooks and class-level configuration:

  • group_name_formatter: Callable[[str], str] transforms the usage label and section headings before display. Its default is str.upper. A non-None section heading receives exactly one trailing colon after transformation. Assigning the identity function str leaves argparse’s original heading text and capitalization unchanged.
  • highlighter is an overridable Rich highlighter for prose. Backtick-delimited text such as `RichHelpFormatter.highlighter` must, by default, highlight the content while leaving the backticks themselves in the surrounding prose style.
  • Existing style and pattern configuration, including styles and highlights, must remain customizable. The standard semantic style names are argparse.args, argparse.groups, argparse.help, argparse.metavar, argparse.syntax, and argparse.text. Their defaults correspond respectively to cyan, dark orange, default foreground, dark cyan, bold, and default foreground.

Required Behavior

1. Returned output and suppression

ArgumentParser.format_help() must return the formatted help as a string rather than merely printing it. For a normal minimal parser containing only a program name and argparse’s default help action, the result must be non-empty.

If the formatter has no renderable content—for example, usage is argparse.SUPPRESS and no sections, actions, or text have been added—format_help() must return the empty string. Actions whose help is argparse.SUPPRESS must be omitted from both generated usage and action listings, and an otherwise hidden mutually exclusive group must not leave visible syntax behind.

A non-empty help result must have argparse-compatible blank lines and exactly the normal final newline. No output line may contain trailing spaces or other trailing horizontal whitespace, whether ANSI styling is enabled or disabled.

2. Plain-text layout and argparse parity

When output is not treated as a color-capable terminal, no ANSI escape sequences may be present. With group_name_formatter set to str, the output must be byte-for-byte identical to the output from the same parser using argparse.HelpFormatter, including capitalization, blank lines, indentation, wrapping, padding, and the final newline, except for the compact multiple-option invocation described below.

This parity must cover:

  • Every combination of supplied or omitted prog, usage, description, and epilog.
  • Standard positional and optional groups, custom argument groups, and groups with every combination of a present, empty, or absent title and description. Empty groups must be shown or omitted exactly as argparse would show or omit them.
  • Parent parsers and individual subparsers across combinations of title, description, dest, metavar, help, and required. The behavior must hold for both top-level help and a selected subparser’s help.
  • Parsers combined with argparse.ArgumentDefaultsHelpFormatter, including appended text such as (default: def). A compatible multiple-inheritance form is class Fmt(RichHelpFormatter, argparse.ArgumentDefaultsHelpFormatter): ....
  • Parsers combined with argparse.MetavarTypeHelpFormatter, including type-derived metavars such as int. A compatible form is class Fmt(RichHelpFormatter, argparse.MetavarTypeHelpFormatter): ....
  • Custom HelpFormatter subclasses that reorder actions, including Django-style formatters. Their ordering must be honored in both generated usage and action listings; a custom formatter may precede RichHelpFormatter in the subclass MRO.
  • Non-default indent_increment, max_help_position, and width values, including indent increments of 1 and 3, help positions of 25, 26, and 27, and widths of None and 70.

With the default group_name_formatter, the same layout rules apply, but the usage label and group headings are uppercased.

3. Compact action invocation format

There is one intentional visible-text difference from stock argparse.HelpFormatter. In an action listing, an optional action with both short and long option strings must show those option strings comma-separated and show its value metavar only once, after the final option string. For example:

-o, --very-long-option-name LONG_METAVAR

It must not use argparse’s repeated-metavar form:

-o LONG_METAVAR, --very-long-option-name LONG_METAVAR

This compact form affects the action listing only; generated usage continues to follow argparse’s normal usage syntax. If the compact invocation reaches or exceeds the available first-column/help position, the complete invocation occupies its own line without being truncated, and its help begins on the following line at the normal help column. Shorter invocations and continuation lines must retain argparse-compatible alignment.

4. Substitution behavior

Standard argparse % substitutions must be honored:

  • %(prog)s must be expanded in an explicitly supplied usage, in parser descriptions and epilogs, in argument-group descriptions, and in version strings.
  • An action’s help string must support substitutions for the attributes available through vars(action), including values such as %(default)s, %(type)s, %(metavar)s, and %(choices)s, with the same user-visible conversions as argparse.

A version action must emit its substituted version followed by exactly one newline. For example, a program named awesome_program with version text %(prog)s 1.0.0 must produce:

awesome_program 1.0.0
5. Literal text and Rich-markup escaping

User data that resembles Rich markup must remain visible literally and must never be consumed as formatting markup. This applies to direct text and to values introduced by % substitution. It includes:

  • Parser descriptions and epilogs.
  • Argument-group descriptions.
  • Action help and version strings.
  • Program names inserted into generated or explicit usage.
  • Positional and optional metavars in generated usage and action invocation labels.
  • Substituted defaults, type names, choices, and other action attributes.

For example, values such as [underline], [italic], [bold], [link], and [default] must appear with their brackets intact. A program named [underline] must remain exactly [underline] in generated usage, descriptions, epilogs, and version output. A metavar such as [bold] must remain exactly that text in both usage and its action label. Semantic coloring may still be applied to a structural token in terminal output, but the token’s characters must not be interpreted or removed as markup.

6. Wrapping, padding, and width

Descriptions, group descriptions, epilogs, action invocations, metavars, and help text must wrap according to the formatter width and indentation settings. Long indivisible tokens must fold without truncation. Wrapped action help must align at the normal help column, including when the invocation is too long to share its first line.

ANSI escape sequences must have zero display width for all layout calculations. Enabling styling must therefore preserve the same visible line breaks and column alignment as unstyled output. Configured width takes precedence; when width=None, terminal/environment width detection, including COLUMNS, must be respected as argparse respects it.

7. Terminal styling

When output is treated as a color-capable terminal, the returned help string must contain ANSI styling with these defaults:

  • Usage prefix and section headings: orange, \x1b[38;5;208m...\x1b[0m.
  • Option strings, flags, and positional action names: cyan, \x1b[36m...\x1b[0m.
  • Optional-action metavars: dark cyan, \x1b[38;5;36m...\x1b[0m.
  • Action help text: default foreground, \x1b[39m...\x1b[0m.
  • Backtick-delimited highlighted content: bold default foreground, \x1b[1;39m...\x1b[0m, while the surrounding help remains in the default foreground style and the backticks remain non-bold.

The default usage prefix is therefore USAGE: in orange. The default section names are uppercased and suffixed by :, also in orange. Setting group_name_formatter = str must preserve the original text and capitalization while retaining the heading color. Argparse’s standard options heading is version-dependent: it is OPTIONS on Python 3.10 and later and OPTIONAL ARGUMENTS on earlier Python versions after default uppercasing.

Auto-generated usage

For auto-generated usage (usage is None), style semantic action spans while leaving the program name, whitespace, brackets, parentheses, pipes, and other usage punctuation unstyled:

  • Each option flag is cyan.
  • Its metavar, including forms such as PATH, [OPT], and OPTS [OPTS ...], is dark cyan.
  • A positional action’s complete generated argument form, including repeated/optional forms such as [arg ...], is cyan.
  • Mutually exclusive alternatives retain argparse’s syntax and spacing, with each action token styled independently.

Metavars containing delimiter-like characters, such as y), and nested nargs syntax must not corrupt span detection or alter the generated text. If semantic spans cannot safely be inferred, the usage text must still be returned intact and the usage prefix must remain styled.

Explicitly supplied usage

For a user-provided usage= string, only the automatically added usage prefix is styled. After normal argparse substitution such as %(prog)s, the entire supplied usage body must be preserved literally and must receive no inferred option, positional, metavar, syntax, or highlight styling. In particular, apparent flags and metavars in that body remain uncolored even if they correspond to real parser actions.

For example, terminal rendering of a supplied body beginning PROG [-h] [--path PATH] starts as:

\x1b[38;5;208mUSAGE:\x1b[0m PROG [-h] [--path PATH]

Only auto-generated usage receives per-action cyan and dark-cyan spans.

8. Group and action styling details

In action listings, each short and long option string is colored independently; separating commas and spaces remain unstyled. Positional invocation labels are cyan. Optional metavars use the metavar color. Action help uses the help-text color and may contain highlighted spans without changing its surrounding style.

A group description must retain its normal indentation and wrapping. If a group has both a description and actions, exactly the argparse-compatible blank line separates the description from its action table. Heading transformation and styling must not cause otherwise empty sections to become visible.

Compatibility and Constraints

  • The formatter must preserve argparse’s behavior across supported Python versions, including Python-version differences in standard group titles and positional nargs rendering.
  • Legacy Windows console handling may be treated as disabled; no additional legacy-console special case is required.
  • Rich styling is present only when color/terminal detection enables it. Non-terminal output must contain plain text only.
  • No styled or plain output line may end in whitespace.

  • Syntax/metavar style — text wrapped in single backticks. The content between the backticks (not the backticks themselves) is styled with a bold-emphasis style. Only the inner text is highlighted; the surrounding backtick characters remain in the default text style.

  • Option/argument style — command-line option flags appearing inline in the text are styled with the args/option color.

These highlights must apply within the description, the epilog, and each argument's help string.

Backtick (syntax) highlighting rules

Given text containing a `...` segment, the characters strictly inside the backticks are highlighted. This must work when the backtick segment appears:

  • in the middle of the text (e.g. Start middle end → middle is highlighted),
  • at the start of the text (e.g. `Start` middle end → Start is highlighted),
  • at the end of the text (e.g. Start middle `end` → end is highlighted).
Option-flag highlighting rules

An option flag is a token beginning with one or more leading hyphens followed by a word, and may contain internal hyphens joining word parts. The following must be highlighted as option flags:

  • A long option in the middle of text: --middle in Start --middle end.
  • A long option at the very start of the text: --Start in --Start middle end.
  • A long option at the end of text: --end in Start middle --end.
  • A long option immediately followed by a comma: in Start --middle, end, the flag --middle is highlighted but the trailing comma is not.

Task: Fix styling of positional arguments in the usage line

Context

This change concerns the rich_argparse package and its RichHelpFormatter class (importable as from rich_argparse import RichHelpFormatter). This formatter is used as the formatter_class for a standard argparse.ArgumentParser and produces a colorized/styled help message using ANSI escape codes.

The formatter uses a style named "argparse.args" (metavar/argument style) which renders as cyan (\x1b[36m) by default, and "argparse.metavar" (used for option value metavars). The "argparse.args" style is what colors the names/metavars of arguments in the usage line and in the positional arguments section.

Problem

When rendering the usage line, the metavar text for positional arguments is styled with the "argparse.args" style. Currently, when a positional argument's usage representation includes surrounding symbols (square brackets [ ], ellipses ..., repeated tokens, or the brace-delimited choices for subparsers), those surrounding symbols are being included in the styled span along with the metavar name. This is inconsistent with how optional arguments are rendered, where only the option string / metavar text itself is styled and the surrounding brackets remain unstyled (default color).

Required behavior

In the usage line, only the metavar name(s) of a positional argument must be styled with the "argparse.args" style. Any surrounding structural symbols that argparse adds around a positional argument's metavar must remain unstyled (default color). This applies to all positional argument forms, including:

  • A plain required positional: only the name is styled.
  • A positional taking a fixed count (nargs=N): each repeated occurrence of the metavar is styled individually; the spaces between them are not part of any style.
  • An optional positional (nargs="?" / argparse.OPTIONAL): the metavar name is styled, but the surrounding [ and ] are not styled.
  • A zero-or-more positional (nargs="*" / argparse.ZERO_OR_MORE): each metavar occurrence is styled individually; the surrounding brackets and the ... ellipsis are not styled. Note the exact bracketed form differs by Python version:
    • On Python < 3.9 the form is [NAME [NAME ...]] — each NAME styled, everything else unstyled.
    • On Python ≥ 3.9 the form is [NAME ...] — the NAME styled, [, ..., and ] unstyled.
  • A one-or-more positional (nargs="+" / argparse.ONE_OR_MORE): rendered as NAME [NAME ...] — each NAME styled individually, brackets and ... unstyled.
  • A remainder positional (nargs=argparse.REMAINDER): its usage representation (...) is unstyled.
  • A parser positional (nargs=argparse.PARSER): rendered as NAME ... — only NAME is styled, the trailing ... is unstyled.
  • A subparsers action: rendered as {choice1,choice2} ... — only the {choice1,choice2} brace group is styled with "argparse.args", while the trailing ... is not styled.

The existing correct behavior for optional arguments must be preserved: the option string (e.g. -h, --opt) is styled with "argparse.args", its value metavar (e.g. [OPT], OPTS [OPTS ...]) is styled with the option-value/metavar style, and the outer [ ] / mutually-exclusive-group | separators remain unstyled.

The styling in the positional arguments section of the help body (where each argument name is listed) is unaffected: each argument name there continues to be styled with "argparse.args".

Example

required int int [optional] [zom ...] oom [oom ...] ... parser ...

where each of required, int (twice, individually), optional, zom, oom (twice, individually), and parser is wrapped in the "argparse.args" style span, and all brackets, spaces, and ... tokens are outside any style span.

For a subparsers action added to PROG producing subcommands sp1 and sp2, the usage line's subparser portion must render as {sp1,sp2} ... where only {sp1,sp2} is wrapped in the "argparse.args" style span and the trailing ... is unstyled.
