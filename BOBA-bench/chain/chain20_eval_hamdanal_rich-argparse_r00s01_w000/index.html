Specification for the rich_argparse Help Formatter

Summary

A module named rich_argparse is to be implemented, one that exports RichHelpFormatter as a drop-in replacement for argparse.HelpFormatter. Argparse's help structure, substitutions, wrapping, indentation, and suppression semantics must be preserved, with Rich styling brought in whenever color output is enabled. What ArgumentParser.format_help() must return is the complete help string, and the formatting must not depend on the help being emitted through an argparse help action.

With color disabled, the visible output must match stock argparse exactly — the documented compact invocation format for options that have multiple option strings being the only permitted deviation. With color enabled for a terminal, the visible text, spacing, wrapping, and line breaks must not be changed by the styling.

Public Interface

rich_argparse.RichHelpFormatter

RichHelpFormatter must be importable through this statement:

from rich_argparse import RichHelpFormatter

Compatibility with argparse.HelpFormatter is required of the class, and the standard constructor shape must be supported:

RichHelpFormatter(
    prog,
    indent_increment=2,
    max_help_position=24,
    width=None,
)

Both a top-level argparse.ArgumentParser and parsers created through add_subparsers() / add_parser() must be able to use it as their formatter_class. As holds for argparse in general, subparsers do not inherit the parent's formatter automatically; for each subparser, callers may explicitly supply the formatter. When add_subparsers() computes its program text, the parent parser's formatter must already be configured.

Overridable formatting hooks, along with class-level configuration, must be exposed by the class:

  • group_name_formatter: Callable[[str], str] is applied to the usage label and to section headings before they are displayed; its default is str.upper. Once the transformation has been applied, a non-None section heading receives exactly one trailing colon. With the identity function str assigned, argparse's original heading text and capitalization are kept intact.
  • highlighter is a Rich highlighter for prose that can be overridden. Backtick-delimited text such as `RichHelpFormatter.highlighter` must, by default, get its content highlighted, with the backticks themselves left in the surrounding prose style.
  • The existing style and pattern configuration — styles and highlights included — must remain customizable. The standard semantic style names are argparse.args, argparse.groups, argparse.help, argparse.metavar, argparse.syntax, and argparse.text. The respective defaults are cyan, dark orange, default foreground, dark cyan, bold, and default foreground.

Behavior Requirements

1. Suppression and returned output

The formatted help must be returned by ArgumentParser.format_help() as a string rather than something merely printed. With a normal minimal parser — one that contains only a program name and argparse's default help action — the result must be non-empty.

Should the formatter have no renderable content — for instance, argparse.SUPPRESS is the usage and no sections, actions, or text have been added — what format_help() must return is the empty string. Both generated usage and action listings must omit actions whose help is argparse.SUPPRESS, and a mutually exclusive group that is otherwise hidden must not leave visible syntax behind.

In a non-empty help result, blank lines must be argparse-compatible and the final newline must be exactly the normal one. Trailing spaces or other trailing horizontal whitespace may not be contained in any output line, whether ANSI styling is enabled or disabled.

2. Argparse parity and plain-text layout

If the output is not treated as a color-capable terminal's, it may contain no ANSI escape sequences. Once group_name_formatter is set to str, byte-for-byte identity with the output the same parser produces under argparse.HelpFormatter is required — capitalization, blank lines, indentation, wrapping, padding, and the final newline all included — the compact multiple-option invocation described below being the sole exception.

The parity just stated must extend to:

  • All combinations under which each of prog, usage, description, and epilog is either supplied or omitted.
  • Standard positional and optional groups, custom argument groups, and groups whose title and description take every combination of being present, empty, or absent. Empty groups must be shown or omitted in exactly the way argparse would show or omit them.
  • Parent parsers and individual subparsers, taken across combinations of title, description, dest, metavar, help, and required. The behavior must hold both for top-level help and for the help of a selected subparser.
  • Parsers used together with argparse.ArgumentDefaultsHelpFormatter, appended text such as (default: def) included. One multiple-inheritance form that works is class Fmt(RichHelpFormatter, argparse.ArgumentDefaultsHelpFormatter): ....
  • Parsers used together with argparse.MetavarTypeHelpFormatter, metavars derived from the type — int, for instance — included. class Fmt(RichHelpFormatter, argparse.MetavarTypeHelpFormatter): ... works as a compatible form.
  • Custom subclasses of HelpFormatter that reorder actions, Django-style formatters among them. The ordering they impose must be honored in both generated usage and action listings; within the subclass MRO, a custom formatter may come before RichHelpFormatter.
  • Values other than the defaults for indent_increment, max_help_position, and width — as examples, 1 and 3 for indent increments, 25, 26, and 27 for help positions, and None and 70 for widths.

Under the default group_name_formatter, those layout rules still apply; what changes is that the usage label and the group headings are uppercased.

3. Compact format for action invocations

Relative to stock argparse.HelpFormatter, a single intentional difference in visible text exists. In an action listing, an optional action that has both short and long option strings must show those option strings comma-separated, and its value metavar must be shown only once, after the final option string. For example:

-o, --very-long-option-name LONG_METAVAR

Argparse's repeated-metavar form must not be used:

-o LONG_METAVAR, --very-long-option-name LONG_METAVAR

The action listing is the only thing this compact form affects; generated usage keeps following argparse's normal usage syntax. Whenever the compact invocation reaches or exceeds the available first-column/help position, the complete invocation is placed on a line of its own without truncation, and its help starts on the next line at the normal help column. Argparse-compatible alignment must be retained by shorter invocations and by continuation lines.

4. Behavior of substitutions

The standard % substitutions of argparse must be honored:

  • In an explicitly supplied usage, in parser descriptions and epilogs, in argument-group descriptions, and in version strings, %(prog)s must be expanded.
  • An action's help string must support substitution for the attributes available through vars(action); values such as %(default)s, %(type)s, %(metavar)s, and %(choices)s are covered, and the user-visible conversions must be the same as argparse's.

A version action must emit its substituted version with exactly one newline after it. To illustrate: a program named awesome_program whose version text is %(prog)s 1.0.0 must produce:

awesome_program 1.0.0
5. Rich-markup escaping and literal text

User data resembling Rich markup must stay visible in literal form, and its consumption as formatting markup must never happen. Both direct text and values introduced by % substitution are subject to this. The following are covered:

  • Descriptions and epilogs of the parser.
  • Descriptions belonging to argument groups.
  • Version strings and the help of actions.
  • Program names that get inserted into usage, generated or explicit.
  • In generated usage and action invocation labels, the metavars — positional and optional.
  • Defaults, type names, and choices after substitution, together with other action attributes.

Values such as [underline], [italic], [bold], [link], and [default] must, as an example, appear with their brackets intact. If a program is named [underline], generated usage, descriptions, epilogs, and version output must all keep it exactly as [underline]. If a metavar is [bold], that text must be kept exactly in both usage and the action label. A structural token in terminal output may still be given semantic coloring, but its characters must not be interpreted as markup or removed.

6. Width, wrapping, and padding

Wrapping of descriptions, group descriptions, epilogs, action invocations, metavars, and help text must follow the width and indentation settings of the formatter. Long indivisible tokens must be folded without truncation. Wrapped action help must line up at the normal help column, including when the invocation is too long to share its first line.

In all layout calculations, ANSI escape sequences must count as zero display width. Consequently, the same visible line breaks and column alignment as unstyled output must be preserved once styling is enabled. A configured width takes precedence; when width=None, terminal/environment width detection — COLUMNS included — must be respected the way argparse respects it.

7. Styling for terminal output

Whenever output is treated as a color-capable terminal, ANSI styling must be contained in the returned help string, with these defaults:

  • Section headings and the usage prefix: orange, \x1b[38;5;208m...\x1b[0m.
  • Flags, option strings, and positional action names: cyan, \x1b[36m...\x1b[0m.
  • Metavars belonging to optional actions: dark cyan, \x1b[38;5;36m...\x1b[0m.
  • Help text of actions: default foreground, \x1b[39m...\x1b[0m.
  • Highlighted content delimited by backticks: bold default foreground, \x1b[1;39m...\x1b[0m; the surrounding help is to remain in the default foreground style, and the backticks are to remain non-bold.

It follows that the default usage prefix is USAGE: in orange. Uppercased and given a : suffix — in orange as well — are the default section names. When group_name_formatter = str is set, the original text and capitalization must be preserved while the heading color is retained. Which standard options heading argparse uses depends on the Python version: on Python 3.10 and later it is OPTIONS, and earlier Python versions, after default uppercasing, use OPTIONAL ARGUMENTS.

Usage that is auto-generated

When usage is auto-generated (usage is None), the semantic action spans are to be styled, while the program name, whitespace, brackets, parentheses, pipes, and other usage punctuation are left unstyled:

  • The color of each option flag is cyan.
  • Its metavar — forms such as PATH, [OPT], and OPTS [OPTS ...] included — is dark cyan.
  • The complete generated argument form of a positional action, repeated/optional forms such as [arg ...] included, is cyan.
  • Argparse's syntax and spacing are retained by mutually exclusive alternatives, with independent styling for each action token.

Metavars containing delimiter-like characters, such as y), must not corrupt span detection or alter the generated text, and nested nargs syntax must not do so either. When semantic spans cannot be inferred safely, the usage text must still be returned intact, and the usage prefix must keep its styling.

Usage supplied by the user

With a usage= string coming from the user, the sole styled element is the usage prefix added automatically. After normal argparse substitution — %(prog)s, for instance — has run, the supplied usage body in its entirety must be preserved literally, and inferred styling of any kind (option, positional, metavar, syntax, or highlight) must not be applied to it. In particular, flags and metavars that merely appear in that body stay uncolored, even when they correspond to real parser actions.

As an example, when the supplied body begins PROG [-h] [--path PATH], terminal rendering starts as:

\x1b[38;5;208mUSAGE:\x1b[0m PROG [-h] [--path PATH]

Auto-generated usage is the only kind that receives per-action cyan and dark-cyan spans.

8. Styling details for groups and actions

Within action listings, every short and long option string gets its own coloring; the commas and spaces doing the separating stay unstyled. Positional invocation labels are cyan. The metavar color is what optional metavars use. The help-text color applies to action help, which may hold highlighted spans without its surrounding style being changed.

A group description's normal indentation and wrapping must be retained. When a group has a description and actions too, exactly the argparse-compatible blank line is what separates the description from its action table. Otherwise empty sections must not become visible as a result of heading transformation and styling.

Constraints and compatibility

  • Across the supported Python versions, argparse's behavior must be preserved by the formatter; Python-version differences in standard group titles and positional nargs rendering are part of this.
  • Legacy Windows console handling may be treated as disabled; no legacy-console special case in addition is required.
  • Rich styling is present only when color/terminal detection enables it. Plain text is all that non-terminal output may contain.
  • No output line, styled or plain, may end in whitespace.

Task Specification: Correcting the Default Highlighting Regexes in RichHelpFormatter

Background

You are working on a library that supplies a RichHelpFormatter class — an argparse help formatter that renders help text with rich styling/highlighting. The class is importable under the name RichHelpFormatter (since it is used directly, e.g. argparse.ArgumentParser("PROG", formatter_class=RichHelpFormatter)). There is also a module-level constant OPTIONS_GROUP_NAME, which holds the display name of the optional-arguments group.

Your task is to fix the default highlighting patterns that are applied to help text (descriptions, epilogs, and argument help strings) and to modify the behavior of the internal usage-span parsing.

Requirement 1: Default highlighting of text

Two default highlight styles are applied by the formatter to help, description, and epilog text:

  • Syntax/metavar style — text enclosed in single backticks. The content between the backticks (not the backticks themselves) receives a bold-emphasis style. Only the inner text is highlighted; the backtick characters surrounding it stay in the default text style.

  • Option/argument style — command-line option flags that appear inline within the text receive the args/option color.

These highlights must be applied within the description, the epilog, and each argument's help string.

Rules for backtick (syntax) highlighting

For text containing a `...` segment, the characters that lie strictly inside the backticks are highlighted. The highlighting must work when the backtick segment appears:

  • midway through the text (e.g. Start middle end → middle is highlighted),
  • at the beginning of the text (e.g. `Start` middle end → Start is highlighted),
  • at the text's end (e.g. Start middle `end` → end is highlighted).
Rules for option-flag highlighting

An option flag is a token that starts with one or more leading hyphens followed by a word, and may contain internal hyphens joining word parts. Each of the following must be highlighted as an option flag:

  • A long option in the middle of the text: --middle in Start --middle end.
  • A long option at the very beginning of the text: --Start in --Start middle end.
  • A long option at the end of the text: --end in Start middle --end.
  • A long option immediately followed by a comma: in Start --middle, end, the flag --middle gets highlighted while the trailing comma does not.
  • A multi-part long option containing internal hyphens: --middle-word in Start --middle-word end (the whole --middle-word is highlighted as a single flag).
  • A short option (a single leading hyphen): -middle in Start -middle end.

The item below must NOT be highlighted as an option flag:

  • A plain hyphenated word that has no leading hyphen: middle-word in Start middle-word end must stay unhighlighted.

Put another way, highlighting must require a leading hyphen at a word boundary; ordinary internal hyphens inside a normal word do not trigger option highlighting.

Requirement 2: Tolerance in usage-span parsing

The formatter includes an internal generator method that is used while building the usage line:

_usage_spans(self, text, start, actions, groups)

This method must no longer raise ValueError when the usage text contains unbalanced bracket characters. Specifically, if the usage text contains a stray closing bracket ] that has no matching [, or an opening bracket [ that has no matching ], the method must complete without raising an error (yielding whatever spans it can, and treating the unmatched bracket situation as non-fatal).

The method must still be a normal generator, and its exceptions (when they do occur for other reasons) propagate through the caller. The public add_usage(usage, actions, groups, prefix) method keeps invoking _usage_spans; if _usage_spans raises an error, add_usage must swallow it and still produce a usage section (i.e., the usage line is rendered without the span highlighting instead of the whole call failing).

Additional behavior to be preserved

  • Rendering must produce the correct output for argparse.BooleanOptionalAction arguments (Python 3.9+): the paired flags are listed in both the usage line and the options section (e.g. --bool | --no-bool in usage, and --bool, --no-bool in the options listing), styled with the args/option color.
  • Styling that already exists for the usage prefix, group headings, option names, and default help entries (such as the -h, --help line) must stay intact.
  • When color is enabled, the help output ends with the epilog text (with its highlights applied) as the final rendered content.

Task Specification: Rich Help Formatters for Argparse

Overview

The rich_argparse module is where formatter classes compatible with argparse must be provided. Rendering of help must go through Rich, applying semantic color and highlighting, while the text, ordering, spacing, wrapping, suppression, and substitution behavior of standard-library argparse is preserved — except where wrapping is explicitly changed by a formatter variant or where group-title transformation is enabled.

Presentation is the only thing the formatters affect; argument parsing and command behavior remain argparse's own.

Public API

The classes listed below must be exported by the module, so that importing them directly works:

  • RichHelpFormatter
  • RawDescriptionRichHelpFormatter
  • RawTextRichHelpFormatter
  • ArgumentDefaultsRichHelpFormatter
  • MetavarTypeRichHelpFormatter

Every class must be a subclass of argparse.HelpFormatter, and ArgumentParser(..., formatter_class=...) must accept it directly.

The constructor contract that standard formatters follow must be kept: prog, indent_increment=2, max_help_position=24, and width=None must carry the same layout meaning they have in argparse.HelpFormatter.

Cooperative composition with other formatters

Through multiple inheritance, the behavior of the Rich formatter must compose cooperatively with that of other argparse.HelpFormatter subclasses, with RichHelpFormatter occupying either base-class position. As a concrete case, a class like:

class DjangoRichHelpFormatter(DjangoHelpFormatter, RichHelpFormatter):
    pass

must keep the other formatter's behavior — custom action ordering in both usage and argument sections, for example — while Rich styling and the default uppercase headings are retained as well. Cooperative combinations equivalent to this one, with RichHelpFormatter first, must also work.

RichHelpFormatter

Compatibility with standard argparse

Whenever color is disabled, group_name_formatter is set to str, and no Rich markup or emoji syntax is present, the output must be identical to that of argparse.HelpFormatter, character for character. The final newline is part of this, and the requirement covers:

  • usage, program name, description, and epilog, whether omitted or supplied;
  • positional actions and optional actions, custom metavars, long option names, long help, and actions whose invocation must move the help onto the next line;
  • the standard normalization of whitespace and the standard wrapping of descriptions, section descriptions, epilogs, and action help, including input that contains repeated spaces, tabs, and newlines;
  • indentation, padding of the help column, wrapping at the width that has been selected, and all supported values of indent_increment, max_help_position, and width;
  • argument groups, both empty and non-empty, including groups that have no name, an empty name, no description, an empty description, or descriptions carrying leading/trailing whitespace and tabs;
  • subparsers and subparser sections, where titles, descriptions, destinations, metavars, help strings, and required/optional status are optional; when the formatter is selected for a subparser as well, that subparser's help must have the same compatibility;
  • suppression done in the standard manner, through argparse.SUPPRESS.

Rather than printing, format_help() must return the formatted string. Help that is normal and non-empty must be returned, and argparse must be matched in ordinary line endings and trailing-whitespace behavior.

Percent substitution and literal text

Normal argparse percent-substitution behavior must be preserved:

  • Wherever argparse supports it, %(prog)s is substituted in generated or explicit usage, descriptions, group descriptions, epilogs, and version strings.
  • Placeholders appearing in action help are expanded from the parameters of the action; values such as %(default)s, %(type)s, %(metavar)s, and %(choices)s are covered, with conversions done the same way argparse does them (a type, for instance, is represented by its __name__).
  • When a version action runs, it must print the substituted version followed by the normal newline.

Handling must treat all caller-provided text and all values that these substitutions insert as literal visible characters, never as Rich markup. The rule holds across all of the following: generated and explicit usage, program names, descriptions, group names and descriptions, epilogs, action labels, action help, option strings, positional labels, defaults, choices, type names, metavars, and version output. As an example, a program named [underline], a type named [link], a default [default], or a metavar [bold] must come out with those brackets intact. Such text must not be removed, must not be interpreted as a tag, must not pick up tag-driven styling, and must not trigger a markup parsing error. Rich emoji shortcodes likewise stay literal text.

The semantic styles and the inline highlighting defined below may put styling on ranges of literal characters, but their characters must never be removed or replaced.

Formatting of group names

RichHelpFormatter.group_name_formatter is a callable at class level that can be set; it accepts a heading string and returns a string. Its default is str.upper, and every section heading as well as the usage prefix is passed through it. Headings such as USAGE:, POSITIONAL ARGUMENTS:, OPTIONS: (or OPTIONAL ARGUMENTS: on Python versions where that is the standard title), and GROUP: therefore appear in default output.

Assigning str to the hook turns the transformation off and brings the exact standard casing back — usage:, options:, and group:, for instance. It must be possible for subclasses to override the hook.

Customization and default styles

By default, these semantic Rich styles must come from the class-level styles mapping:

{
    "argparse.args": "cyan",
    "argparse.groups": "dark_orange",
    "argparse.help": "default",
    "argparse.metavar": "dark_cyan",
    "argparse.syntax": "bold",
    "argparse.text": "default",
}

These class-level style values may be customized by callers. The class-level highlights collection can be customized in the same way: patterns in it apply named capture groups, which receive the corresponding argparse.<group-name> style, and inline highlighting is disabled by setting it to an empty collection.

When the default styles are in effect and color is forced on, rendering must produce the ANSI presentation below, layered over the layout that is otherwise standard:

  • \x1b[38;5;208m followed by \x1b[0m is applied to usage prefixes and to section/group headings.
  • Cyan — \x1b[36m followed by \x1b[0m — colors option strings and rendered positional action names, in both auto-generated usage and argument sections.
  • Dark cyan — \x1b[38;5;36m followed by \x1b[0m — is the color of metavars belonging to optional actions, again in both auto-generated usage and argument sections.
  • The applicable default foreground style is what action help and ordinary description/epilog text use; under forced color it shows up as \x1b[39m followed by \x1b[0m placed around the styled runs.

For a positional action, an argument span covers its complete rendered positional usage expression, forms generated for variable nargs included. For an optional action, the option token and its complete generated metavar expression are rendered as separate argument and metavar spans. Correct styling must hold across optional and required actions, optional and required mutually exclusive groups, metavars with punctuation in them, metavars that expand into multiple words or bracketed forms, and BooleanOptionalAction pairs such as --bool | --no-bool where that action is available.

Inline highlighting by default

Besides the argparse.text or argparse.help style that surrounds them, parser descriptions, argument-group descriptions, epilogs, and action help make use of these default inline highlights:

  • Bold (argparse.syntax) is the rendering for whatever lies between a pair of backticks; the two backtick characters stay visible and keep the text style around them. This works both when the pair opens or closes the string and when it sits in the middle.
  • Cyan (argparse.args) is applied to an option-like token that starts with one or two hyphens. Matching works at the start of text, at its end, and before punctuation. Internal hyphens may appear inside the token, which is why --middle-word counts as a single highlighted token; recognition extends to both the --long and the -short forms.
  • Merely containing an internal hyphen does not make a normal word highlighted. For example, middle-word keeps the surrounding style.

Adjacent punctuation and the styles around it must be preserved by inline highlighting. In --middle,, for instance, cyan applies to --middle only, and the comma keeps the normal text/help style. When default styles are used with color forced on, bold content nested inside the default text/help foreground is emitted as \x1b[1;39m...\x1b[0m; option-like tokens that have been highlighted take the same cyan ANSI form that argument names use.

Generating and styling usage

The exact argparse usage text and grouping must be preserved in auto-generated usage, even as semantic spans are applied to the actions that are visible:

  • A group-style span corresponds to the transformed usage prefix, starting at character zero and stretching over the prefix text (for the prefix USAGE:, that is the half-open range [0, 6)).
  • An argparse.args span is what every visible option occurrence forms, and an argparse.metavar span is what every optional metavar expression associated with it forms.
  • An argparse.args span is likewise formed by every visible positional usage expression.
  • Actions under suppression are absent, and the spans of visible actions are not shifted by them. A mutually exclusive group for which every member is suppressed is likewise absent, and it does not affect visible spans.

When the usage string comes from the caller, normal %(prog)s substitution is performed, and only the usage prefix receives styling. The body of the supplied usage is emitted literally, with no automatic option, metavar, or inline-highlight spans attached to it.

An overridable method named _rich_usage_spans is where usage-span calculation is exposed. If this method raises while auto-generated usage is being styled, help generation must succeed rather than that failure being propagated. Under the fallback, the correct usage text must be preserved in a rich.text.Text object, and exactly one span must be retained: the argparse.groups span over the transformed usage prefix. The remainder of the usage carries no styling. With the default USAGE: prefix in place, that sole span is [0, 6); insignificant trailing whitespace in the internal text object is permitted.

Section handling and empty output

The root renderables the formatter has accumulated are stored, as a sequence, at formatter._root_section.rich_items. When usage is added, a rich.text.Text usage renderable is appended to this sequence. Sections that are empty must not create visible output.

If usage is argparse.SUPPRESS and no other content exists, no renderables are accumulated, and the empty string is what format_help() returns.

Variants of the formatter

The action optionally consumes one command-line value: the output file path.

  • When the action is invoked with a path value on the command line (e.g. --generate path/to/file.svg), that value is used as the output path.
  • When the action is invoked with no value (e.g. --generate alone), the path supplied when the argument was added is used as the output path.

  • The resolved path has a file extension that is not supported (any extension other than .svg, .html, or .txt — e.g. .png).
  • The value that is provided is not a valid path string (e.g. a non-string value such as a tuple is passed as the option value).

  • The plain-text output must be the help text of the parser to which the action belongs, and it must begin with Usage: (implying the usage section is rendered with a capitalized "Usage:" prefix, matching the existing RichHelpFormatter output).
  • Multiple HelpPreviewAction arguments may be added to the same parser (each one with its own optional default path), and each of them must behave independently.

Task: Fix the styling of positional arguments in the usage line

Background

This change touches the rich_argparse package and its RichHelpFormatter class (importable via from rich_argparse import RichHelpFormatter). The formatter serves as the formatter_class of a standard argparse.ArgumentParser, producing a colorized/styled help message built from ANSI escape codes.

The formatter relies on a style named "argparse.args" (the metavar/argument style), which renders as cyan (\x1b[36m) by default, and on "argparse.metavar" (used for option value metavars). What colors the names/metavars of arguments in the usage line and in the positional arguments section is the "argparse.args" style.

Problem

When the usage line is rendered, the metavar text of positional arguments gets styled with the "argparse.args" style. At present, if a positional argument's usage representation carries surrounding symbols (square brackets [ ], ellipses ..., repeated tokens, or the brace-delimited choices for subparsers), those surrounding symbols end up inside the styled span together with the metavar name. This does not match how optional arguments are rendered: for them, only the option string / metavar text itself is styled, and the surrounding brackets remain unstyled (default color).

Required behavior

Within the usage line, only the metavar name(s) of a positional argument must be styled with the "argparse.args" style. Any surrounding structural symbols that argparse adds around a positional argument's metavar must stay unstyled (default color). This holds for all positional argument forms, including:

  • For a plain required positional, only the name is styled.
  • For a positional taking a fixed count (nargs=N), each repeated occurrence of the metavar is styled individually; the spaces between them are part of no style.
  • For an optional positional (nargs="?" / argparse.OPTIONAL), the metavar name is styled, but the surrounding [ and ] are not styled.
  • For a zero-or-more positional (nargs="*" / argparse.ZERO_OR_MORE), each metavar occurrence is styled individually; the surrounding brackets and the ... ellipsis are not styled. Note that the exact bracketed form depends on the Python version:
    • On Python < 3.9 the form is [NAME [NAME ...]] — each NAME is styled, everything else unstyled.
    • On Python ≥ 3.9 the form is [NAME ...] — the NAME is styled, while [, ..., and ] are unstyled.
  • For a one-or-more positional (nargs="+" / argparse.ONE_OR_MORE), the rendering is NAME [NAME ...] — each NAME is styled individually, with the brackets and ... unstyled.
  • For a remainder positional (nargs=argparse.REMAINDER), its usage representation (...) remains unstyled.
  • For a parser positional (nargs=argparse.PARSER), the rendering is NAME ... — only NAME is styled, and the trailing ... is unstyled.
  • For a subparsers action, the rendering is {choice1,choice2} ... — only the {choice1,choice2} brace group is given the "argparse.args" style, while the trailing ... is not styled.

For optional arguments, the existing correct behavior must be preserved: the option string (e.g. -h, --opt) carries the "argparse.args" style, its value metavar (e.g. [OPT], OPTS [OPTS ...]) carries the option-value/metavar style, and the outer [ ] / mutually-exclusive-group | separators stay unstyled.

The styling within the help body's positional arguments section (the part where each argument name is listed) is unaffected: each argument name there is still styled with "argparse.args".

Example

Take a parser with program name PROG and positional arguments defined as follows: a required positional required, an int positional with nargs=2, an optional positional with nargs=argparse.OPTIONAL, a zom positional with nargs=argparse.ZERO_OR_MORE, an oom positional with nargs=argparse.ONE_OR_MORE, a remainder positional with nargs=argparse.REMAINDER, a parser positional with nargs=argparse.PARSER, and a suppress positional with nargs=argparse.SUPPRESS, together with a mutually exclusive group containing --opt (nargs="?") and --opts (nargs="+"). On Python ≥ 3.9, the positional portion of the usage line must render as:

required int int [optional] [zom ...] oom [oom ...] ... parser ...

Here, each of required, int (twice, individually), optional, zom, oom (twice, individually), and parser is wrapped in the "argparse.args" style span, while all brackets, spaces, and ... tokens are outside any style span.

If a subparsers action is added to PROG, producing the subcommands sp1 and sp2, the usage line's subparser portion must render as {sp1,sp2} ..., with only {sp1,sp2} wrapped in the "argparse.args" style span and the trailing ... left unstyled.

Constraints

  • Do not alter any public API signatures; RichHelpFormatter continues to work as a drop-in formatter_class.
  • Aside from the styling scope described above, the overall usage text, line wrapping, and section layout remain unchanged from standard argparse behavior.
