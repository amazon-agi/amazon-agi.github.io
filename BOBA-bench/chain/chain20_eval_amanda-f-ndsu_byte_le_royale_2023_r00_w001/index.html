Storage Station — Task Specification

Summary

Implement a new Storage station class that can hold a single item and that supports taking, returning, and swapping items through a single action method.

Public Interface

Module: game.common.stations.storage

Define a class Storage (a station type) with the following:

  • Constructor: Storage() — has no required arguments and builds a valid, empty storage station.
  • Attribute: item — holds the item that is currently stored (readable and writable). On a freshly constructed instance, its default is None (empty).
  • Attribute: object_type — its value must equal ObjectType.storage.
  • Method: take_action(self, item) — carries out a single interaction with the storage station using the item passed in, and returns an item (or None). Behavior is detailed below.
Enum: game.common.enums

Add ObjectType.storage as a new enum member of the existing ObjectType enumeration.

How take_action(item) Behaves

take_action swaps whatever the station's item attribute currently holds with the incoming item. In particular:

  • After the call, the object supplied as the item argument is what the station's item attribute holds.
  • The method returns the object that the station's item attribute held before the call.

This one behavior covers all three interaction cases:

  1. Take (depositing into empty storage): If the station's item is None and a non-None item is passed in, then after the call the station holds that item and the method returns None.

  2. Return (withdrawing from storage): If the station holds an item and None is passed in, then after the call the station's item is None and the method returns the item that was previously held.

  3. Swap: If the station holds an item and a different non-None item is passed in, then after the call the station holds the item that was passed in and the method returns the item that was previously held.

Requirements for Integration

  • A Storage instance must be assignable to the occupied_by attribute of a Tile; a station instance (including Storage) assigned there must be retrievable and remain an instance of its class. (Note: when a non-station item is assigned to occupied_by, the result is occupied_by being None; assigning a valid station retains the station.)

Supporting Context (already present, provided for reference)

  • Pizza objects (game.common.items.pizza.Pizza) can be constructed using a state keyword argument (e.g. Pizza(state=PizzaState.sauced)), have a state attribute that is mutable, and support add_topping(topping), with topping values that come from the ToppingType enum. The storage station stores and returns items of this kind without modifying them.

Constraints

  • Do not restrict the item types that can be stored; take_action performs the swap regardless of the contents or state of the item.

Overview

Implement the Topping class and hook it into the existing Pizza class so that toppings can be represented and added in the form of Topping objects. The API centered on objects is the primary API; however, Pizza.add_topping must also remain compatible with existing callers that pass a raw ToppingType enum value. The public API set out below must be importable and callable exactly as specified.

Required Public API

The Topping class
  • Module location: game.common.items.topping
  • Class name: Topping
  • Constructor: must accept the keyword argument topping_type, whose value is a member of the ToppingType enum defined in game.common.enums.
  • Attribute: topping_type exposes the ToppingType value belonging to the topping.

An example of construction that must work:

from game.common.enums import ToppingType
from game.common.items.topping import Topping

topping = Topping(topping_type=ToppingType.cheese)
The Pizza class
  • Module location: game.common.items.pizza
  • Class name: Pizza
  • Method: add_topping(topping)
    • A Topping object is the primary argument form.
    • For the sake of backward compatibility, a raw ToppingType member is likewise an accepted call form.
  • Attribute: toppings is a collection whose length reflects how many toppings are currently on the pizza. When a Topping object is added successfully, the object itself is kept as the topping instead of being reduced to only its enum value.
  • Attribute: state can be set to members of PizzaState — including PizzaState.rolled, PizzaState.sauced, and PizzaState.baked — as defined in game.common.enums.

Required Behavior

add_topping argument forms that are accepted

When the argument is a Topping object, all admission decisions rest on its topping_type attribute. With a raw ToppingType argument, the topping type is supplied by the enum member itself. The same state, topping-type, and capacity rules below govern both forms.

In particular, a legacy call such as the one below must remain safe and must not raise an exception merely because its argument is a raw enum value:

pizza.add_topping(ToppingType.cheese)
Restriction based on state

Adding a topping is permitted only while the pizza is in the PizzaState.sauced state.

  • When state is PizzaState.rolled, a call to add_topping must leave toppings unchanged.
  • When state is PizzaState.baked, a call to add_topping must leave toppings unchanged.
  • Other states that are not sauced must likewise not permit a topping to be added.
Rules for topping type and capacity

While the pizza is in the sauced state:

  • Each accepted topping makes len(pizza.toppings) larger by one. To illustrate, adding the valid toppings cheese and chicken in sequence results in a length of 2.
  • A topping whose effective type is ToppingType.dough must be rejected. For instance, if cheese is added and dough is added afterwards, the length stays at 1. Both the Topping(topping_type=ToppingType.dough) form and the legacy raw ToppingType.dough form are covered by this rule.
  • A pizza may contain at most four toppings. As soon as the collection contains four toppings, each further call to add_topping must leave its length at 4.
  • A rejected addition must not otherwise change the existing collection of toppings.

Example of object-based usage:

from game.common.enums import PizzaState, ToppingType
from game.common.items.pizza import Pizza
from game.common.items.topping import Topping

pizza = Pizza()
pizza.state = PizzaState.sauced
pizza.add_topping(Topping(topping_type=ToppingType.cheese))
pizza.add_topping(Topping(topping_type=ToppingType.chicken))
assert len(pizza.toppings) == 2
Starting state of the topping collection

Each newly constructed Pizza starts out with an empty toppings collection, so len(pizza.toppings) is 0 before any successful additions.

Oven interaction

The existing Oven class is available under the path game.common.stations.oven.Oven and exposes take_action(pizza) plus an item attribute. A sauced pizza that carries at least one successfully added Topping object must remain a valid Pizza for oven handling:

pizza = Pizza(state=PizzaState.sauced)
pizza.add_topping(Topping(topping_type=ToppingType.cheese))
oven = Oven()

result = oven.take_action(pizza)
assert result is None
assert isinstance(oven.item, Pizza)

Altering the pizza's topping representation so that Topping objects are supported must not break this existing oven behavior.

Constraints on compatibility

  • Callers using the new object-based style pass Topping instances and obtain the topping type via the instance's topping_type value.
  • Existing callers that still pass ToppingType members directly to Pizza.add_topping must keep working without an exception and stay subject to the same addition rules.
  • The move to object-based toppings must not cause a topped pizza to stop being a Pizza and must not otherwise prevent existing station interactions such as oven storage.

07 Implementing the Delivery Station 825 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Implementing the Delivery Station

Overview

In a pizza-making game, implement a new Delivery station. The delivery station accepts a completed (baked) pizza handed over by a cook, scores it, and takes it out of the cook's possession. The work also requires supporting changes to existing enums and station behaviors.

Public API Requirements

game/common/stations/delivery.py

Define a Delivery class:

class Delivery:
    def __init__(self)
    def take_action(self, cook) -> item_or_None
  • When constructed, Delivery must set object_type to ObjectType.delivery.
  • take_action(cook) accepts a Cook object (see below); the item that cook holds is accessible via cook.item.
game/common/enums.py

Extend the ObjectType enumeration with a new enum member delivery.

How Delivery.take_action(cook) Behaves

The method examines the item held by the cook that was passed in (cook.item).

Rules for accepting an item
  • If the item being held is a Pizza whose state is PizzaState.baked, the delivery succeeds:
    • The pizza gets scored (see Scoring below), and the resulting score is assigned to the cook's score attribute (cook.score).
    • The method returns None (the pizza is delivered/consumed).
  • If the item being held is not a baked pizza (a Pizza in any other PizzaState, such as rolled or sauced, or an item that is not a pizza), the delivery fails:
    • What is returned, unchanged, is the exact same item object that was held (returned by identity — the caller receives back the original object).
    • In this case, the cook's score is not changed.
Scoring (applied only on successful delivery of a baked pizza)

The score comes from the pizza's overall quality, the dough's base score, and each topping's base score as adjusted by that topping's individual quality.

The relevant inputs are the following:

  • GameStats.topping_stats[ToppingType.dough]["score"] — the base score the dough contributes (always counted once per pizza).
  • Each topping on the pizza adds a per-topping score, computed as:
    • floor(topping_base_score * topping_quality), where topping_base_score denotes GameStats.topping_stats[<that topping's type>]["score"] and topping_quality denotes the topping's individual quality value.
  • The pizza as a whole carries an overall quality value.

The final score is obtained as:

raw_sum = dough_score + sum( floor(topping_base_score * topping_quality) for each topping )
final_score = int( floor( raw_sum * pizza_quality ) )

Arithmetic properties the scoring must satisfy:

  • A topping whose quality is 1.0 contributes exactly its base score (floor(base * 1.0) == base).
  • The final score equals the raw sum of dough + all topping contributions whenever the pizza's overall quality is 1.0.
  • Regardless of how many toppings there are, the dough base score is always added once.
  • The result must be an integer (take the floor after multiplying the raw sum by the pizza quality).

Examples (with base scores taken from GameStats.topping_stats):

  • For a baked pizza of quality 1.0 with a single cheese topping (quality 1.0): score = dough_score + cheese_score.
  • For a baked pizza of quality 1.0 with four toppings, all at quality 1.0 (cheese, sausage, mushrooms, olives): score = dough_score + cheese_score + sausage_score + mushrooms_score + olives_score.
  • For a baked pizza whose overall quality is 0.5, topped with cheese(1.0), sausage(0.5), mushrooms(1.0), olives(1.0): score = int(floor((dough_score + cheese_score + floor(sausage_score * 0.5) + mushrooms_score + olives_score) * 0.5)).

Supporting Requirements

The Cook object (game/common/cook.py)

The Cook class must:

  • Accept an item keyword argument at construction time (Cook(item=<something>)); it stores the held item, which is then accessible as cook.item.
  • Have a score attribute that can be read and also written; the delivery station writes the computed score to it.
Pizza (game/common/items/pizza.py)

Pizza.add_topping must accept a Topping object (an instance of the Topping class) rather than a ToppingType enum value. Once a topping has been added, its type, quality, and base score/worth must all be retained on the pizza so that scoring can read each topping's type and individual quality.

A Pizza must be constructible with the quality and state keyword arguments, and after construction its state attribute must be reassignable.

Topping (game/common/items/topping.py)

The Topping class must support being constructed with the keyword arguments quality, worth, topping_type, and is_cut. Every topping must expose its type and its quality so the scoring logic can access them.

Existing station behavior (expectations carried over unchanged)

The other stations (Oven, Sauce) keep rejecting non-pizza items and pizzas in the wrong state, leaving their item as None. If a non-pizza Item (for example, one constructed with a small integer quality and a worth) is passed to these stations' take_action, the station must not accept it. Item construction accepts quality and worth keyword arguments.

Serialization

The pizza's score-relevant data (topping scores/worth included) must be preserved through the object's JSON serialization/deserialization, so that a pizza reconstructed from it yields the same score.

(This is a supporting requirement meant to keep scoring consistent; the core deliverable is that a baked pizza scored as described above produces exactly the integer values given in the examples.)

Map Layout Requirements (relative to the player cook's starting point)

generate_map(5) must place the objects listed below so that moving the cook through the given sequence of steps leaves it facing that object:

  • Two steps up: there is a bin (trash/disposal).
  • Two steps up, then one step left: there is a storage area (accepts toppings).
  • Two steps up, then one step right: there is a storage area (accepts toppings).
  • Two steps left: there is an oven.
  • Two steps right: there is a combiner.
  • Two steps down: there is a delivery point.
  • Two steps down, then one step left: there is a dispenser.

Interaction Behavior

Within InteractController.handle_actions(cook, world), the object in front of the cook is determined and the resulting held item is produced:

Bin

If the cook is holding a Pizza (e.g. a sauced pizza with a cheese topping) and interacts with the bin, the held item gets discarded. The result is None.

Storage (left or right storage area)

If the cook is holding a Topping (e.g. pepperoni) and interacts with a storage area, the topping gets deposited. The result is None.

Oven

If the cook is holding a Pizza (e.g. a sauced pizza with a cheese topping) and interacts with the oven, the interaction returns an item that still has a state attribute that is valid (non-None). The result must be a Pizza-like object with a state that is not None.

Combiner

Items placed into the combiner accumulate there, and once it has both a pizza base and a topping, it yields a completed pizza:

  • On the first interaction, the cook holds a sauced Pizza. After the interaction, the result is None (the pizza was placed into the combiner).
  • Next, the cook holds a cut Topping (Topping(topping_type=ToppingType.cheese, is_cut=True)). One interaction places/processes the topping (its result is used as the new held item), and a second interaction retrieves the finished item.
  • After these interactions, the held item that is retrieved must be an instance of Pizza.
Delivery

If the cook is holding a baked Pizza (Pizza(state=PizzaState.baked)) and interacts with the delivery point, the pizza gets delivered. The result is None.

Dispenser

If the cook is holding a Pizza() (default state) and interacts with the dispenser, the result is an item that is not None (the dispenser provides/replaces an item).

Notes and Constraints

  • The movement controller and the interact controller must work in tandem: the tests move the cook via MovementController.handle_actions(world, player) (setting player.cook.chosen_action repeatedly) and then call InteractController.handle_actions(player.cook, world).
  • Every module, class, function, and enum member named above must exist and be importable exactly as specified, so that the described flows run without import or attribute errors.
