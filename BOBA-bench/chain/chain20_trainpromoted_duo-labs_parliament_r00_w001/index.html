Specification of the Task

Summary

The parliament Python package performs analysis of AWS IAM policies. This task specifies the public behavior for expanding IAM action names and for telling apart malformed action strings, unknown service prefixes, and unknown actions.

Behavior for successful action expansion and policy analysis that already exists must remain compatible.

Public interface

Classes for exceptions

Two exception classes must be exported from the package root:

from parliament import UnknownPrefixException, UnknownActionException

Both names must denote subclasses of Exception.

  • UnknownPrefixException stands for an IAM service prefix that is not recognized: the portion before the colon in an action string.
  • UnknownActionException stands for an action name or wildcard pattern that matches no known action under a recognized service prefix.

The two classes must be distinct. Neither one may be an alias for, or a subclass of, the other, so that catching one does not catch errors belonging to the other category. They may share a common superclass.

The expand_action function

The function that expands actions must remain importable as:

from parliament.statement import expand_action

It must support the existing single-argument call:

def expand_action(action_string):
    ...

action_string is typically a string in the form "<prefix>:<action>". The action component may be a literal IAM action, or it may be a wildcard pattern such as *.

Behavior for successful expansion

expand_action compares the input against the AWS IAM service prefixes and actions known to the package and returns a list of matching action records. Each record that is returned has this shape:

{"service": "<canonical-prefix>", "action": "<CanonicalActionName>"}

The behavior below must be preserved:

  • Matching is case-insensitive for both the service prefix and the action pattern.
  • Service prefixes that are returned use their canonical lowercase form, and actions that are returned use their canonical IAM casing.
  • Both literal action names and wildcard action patterns are supported. A wildcard may occur within the action component, and every known action that matches must be returned.
  • When the same IAM prefix is represented by more than one service definition, matches coming from all definitions that use that prefix must be included.
  • Known actions that are designated as permission-only actions are valid and must also be expandable.

Examples that are required include the following:

expand_action("s3:listallmybuckets")
# [{"service": "s3", "action": "ListAllMyBuckets"}]

expand_action("s3:listallmybucke*")
# [{"service": "s3", "action": "ListAllMyBuckets"}]

expand_action("iAm:li*sTuS*rs")
# [{"service": "iam", "action": "ListUsers"}]

expand_action("logs:GetLogDelivery")
# [{"service": "logs", "action": "GetLogDelivery"}]

When a prefix is represented by multiple service definitions, expand_action("ses:Describe*") must include all of these records:

[
    {"service": "ses", "action": "DescribeActiveReceiptRuleSet"},
    {"service": "ses", "action": "DescribeConfigurationSet"},
    {"service": "ses", "action": "DescribeReceiptRule"},
    {"service": "ses", "action": "DescribeReceiptRuleSet"},
]

Behavior for errors

Classification of errors takes place after the action-string format is validated.

Malformed action strings

If the input cannot be split, with a single colon, into exactly a prefix component and an action component — for example, "malformed" contains no colon — expand_action must raise an exception that can be caught as ValueError.

This requirement about malformed format is separate from the classification of unknown prefixes and unknown actions. Raising one of the domain-specific exceptions fulfills the malformed-input requirement only if that exception is itself a subclass of ValueError.

A service prefix that is unknown

When the action string is correctly structured but its prefix does not correspond to any known IAM service, expand_action must raise UnknownPrefixException.

Example:

expand_action("333:listallmybuckets")  # raises UnknownPrefixException
A known prefix for which no action matches

When the action string is correctly structured and its prefix is known, but its literal action or wildcard pattern matches no known action for that prefix, expand_action must raise UnknownActionException.

Examples:

expand_action("s3:zzz")   # raises UnknownActionException
expand_action("s3:zzz*")  # raises UnknownActionException

An expansion that is valid and recognized must continue to succeed and must not raise either exception.

Constraints on compatibility

  • The two errors specific to the domain must remain independently catchable.
  • Adding the new exception types must not change the results of valid expansion, including case-insensitive matching, wildcard expansion, multi-definition prefixes, or permission-only actions.
  • Policy analysis that already exists and that relies on action expansion must continue to work for valid policies and continue to report invalid actions rather than failing unexpectedly.

Task Specification: Policy Analysis by Finding IDs

Overview

You are working with parliament, a Python library that audits AWS IAM policy documents and reports problems ("findings"). The task requires findings to be exposed through their identifier codes, plus a correction to the logic that detects resource-policy privilege escalation involving Deny statements.

Public API

parliament.analyze_policy_string

A function that parses an AWS IAM policy document and audits it.

analyze_policy_string(policy_string, ignore_private_auditors=False)
  • policy_string: a str holding a JSON IAM policy document.
  • ignore_private_auditors: a keyword argument whose default is False. When it is True, any private/extra auditors are skipped, so that only the core findings described here are produced; callers pass it in order to isolate the core behavior.
  • It returns a policy object (described below).
The policy object

The object that is returned must expose:

  • findings: a collection of the findings the analysis produced. len(policy.findings) must reflect how many findings there are.
  • finding_ids: a set of the string identifier codes belonging to the produced findings. Every finding has an identifier, and finding_ids is the set made up of those identifier strings (duplicates collapse). If there are no findings, it is the empty set.
parliament.is_arn_match

A function that decides whether two ARN patterns can match each other, for a given resource type.

is_arn_match(resource_type, arn_pattern_a, arn_pattern_b)
  • resource_type: a str, for instance "object", "bucket", or "cloudfront".
  • arn_pattern_a, arn_pattern_b: str ARN patterns (these may contain * wildcards, or be "*").
  • It returns a truthy value when the two patterns count as a match for the given resource type, and a falsy value otherwise.

Finding Identifier Codes

Findings must be assigned the identifier strings below, which are produced under the following conditions:

  • MALFORMED_JSON — the policy string is not valid JSON.
  • MALFORMED — the policy is structurally invalid, including: a statement that contains both Action and NotAction; a statement lacking any action; a policy with no Statement.
  • INVALID_SID — the Sid value of a statement is not valid.
  • UNKNOWN_ACTION — a statement refers to an action that does not exist.
  • UNKNOWN_CONDITION_FOR_ACTION — a condition key is applied that is not valid for the action(s) in the statement.
  • MISMATCHED_TYPE — the type of a condition value fails to match the type that the condition operator/key requires.
  • UNKNOWN_OPERATOR — a condition employs an operator that is not recognized.
  • SENSITIVE_BUCKET_ACCESS — the policy grants access to a sensitive bucket.
  • BAD_PATTERN_FOR_MFA — an MFA-related condition is phrased so that MFA is not actually enforced.
  • RESOURCE_POLICY_PRIVILEGE_ESCALATION — a resource policy effectively hands out broader privileges than intended (e.g., allowing an action through which the principal can rewrite the policy).
  • RESOURCE_MISMATCH — an action requires a resource format that is matched by none of the specified resources.

Required Behavior (per scenario)

Formatting and structure checks
  • Input that is not JSON produces exactly {MALFORMED_JSON}.
  • A statement that contains both Action and NotAction produces exactly {MALFORMED}.
  • A statement that has an Effect and Resource but no action produces exactly {MALFORMED}.
  • A policy document that contains only a Version and no Statement produces exactly {MALFORMED}.
  • A statement with an invalid Sid produces exactly {INVALID_SID}.
  • A simple, valid policy with a single statement produces no findings.
  • A valid policy that has multiple statements and multiple actions produces no findings.
  • A policy with multiple statements in which one of them references a nonexistent action produces exactly {UNKNOWN_ACTION}.
Condition checks
  • A condition that is valid (e.g., a DateGreaterThan on aws:CurrentTime) produces no findings.
  • A condition that uses a key which is not a recognized global/service condition key produces {UNKNOWN_CONDITION_FOR_ACTION}.
  • A condition with an action-specific key that is valid for the action produces no findings; if the key is valid for the service but not for that particular action, {UNKNOWN_CONDITION_FOR_ACTION} is produced.
  • A condition whose value type fails to match what the key requires (e.g., a non-numeric string where a number is required) produces {MISMATCHED_TYPE}.
  • When there are multiple conditions and all of them are valid, no findings are produced; if one of several conditions is bad, the corresponding finding(s) are produced (a condition with a bad type yields {MISMATCHED_TYPE}; a condition with a bad key yields {UNKNOWN_CONDITION_FOR_ACTION}).
  • With Resource: "*", a StringNotEquals on iam:ResourceTag/status applied to an action for which that key is not valid produces exactly {UNKNOWN_CONDITION_FOR_ACTION, SENSITIVE_BUCKET_ACCESS}.
  • A condition that uses an ...IfExists variant of a valid operator (e.g., StringEqualsIfExists) produces no findings.
  • A condition whose operator is not recognized produces UNKNOWN_OPERATOR; when the value of that same condition also mismatches the (defaulted/expected) type, the result is exactly {UNKNOWN_OPERATOR, MISMATCHED_TYPE}.
  • A condition that applies a recognized operator whose type does not match the key's value (e.g., NumericEquals applied to a string list) produces {MISMATCHED_TYPE}.
  • When the Bool operator is used with an unquoted boolean literal (true) on a boolean condition key, no findings are produced.
  • A condition that uses Null correctly produces no findings.
  • A condition that uses MultiFactorAuthAge (as a numeric MFA-age check) correctly produces no findings.
Action and resource-format checks
  • When a policy grants an action that requires a specific ARN resource format (e.g., redshift GetClusterCredentials, lambda AddLayerVersionPermission) together with a resource matching that required format, no findings are produced.
  • A statement granting s3:listallmybuckets with Resource: "s3" (which is not a valid ARN for the action) produces exactly one finding.
  • For a statement granting s3:getobject on arn:aws:s3:::my_corporate_bucket/*, no findings are produced.
Pattern checks
  • A statement that grants * on * with a Bool condition aws:MultiFactorAuthPresent: "false" produces exactly {BAD_PATTERN_FOR_MFA}.
  • A statement that allows ["s3:GetObject", "s3:PutBucketPolicy"] on * (thereby effectively granting full bucket control via policy rewriting) produces exactly {RESOURCE_POLICY_PRIVILEGE_ESCALATION}.
  • The escalation must also be detected when the enabling actions are distributed across two Allow statements in the same policy, producing {RESOURCE_POLICY_PRIVILEGE_ESCALATION}.
  • The escalation must also be detected when the allow is scoped to one specific bucket and its objects (e.g., Resource: ["arn:aws:s3:::bucket", "arn:aws:s3:::bucket/*"]), producing {RESOURCE_POLICY_PRIVILEGE_ESCALATION}.
  • If the enabling Allow targets one bucket while the PutBucketPolicy-style action targets a different bucket, so that no escalation is possible, then no escalation finding is produced; the result is exactly {RESOURCE_MISMATCH} (arising from an unrelated action whose required resource format is not matched).
Deny-with-condition logic (the core correction)

When it determines whether an action is actually allowed, the privilege-escalation detection must correctly account for Deny statements:

  • When a policy has an Allow on a specific resource that would otherwise constitute escalation, and in addition a Deny on Action: "*" / Resource: "*", the action ends up fully denied and no escalation finding is produced. A policy of that kind produces no findings.

The deny/allow evaluation must be correct in two respects:

  • Boolean/effect comparisons must be handled consistently no matter what casing is used, so that a Deny is properly recognized.
  • A Deny statement that carries a Condition must not be treated as unconditionally denying the action; an allow is fully removed only by an unconditional Deny.
Principals
  • S3 bucket policies that are well-formed, with valid Principal values, produce no findings. This includes: a basic bucket policy; a policy granting two accounts access via account ARNs; a policy granting one account access via account ID; a policy naming a user ARN; and a policy using Federated access. Every one of these produces the empty set of findings.
Behavior of is_arn_match

Matching cases (truthy):

  • * serves as a wildcard: it matches any sequence of zero or more characters.

Add configurable auditing for sensitive access

The following public API must be exposed:

from parliament import analyze_policy_string

The callable must accept the call below:

analyze_policy_string(
    policy_string,
    include_community_auditors=True,
    config=config,
)

The call must return a policy object whose finding_ids attribute contains a set of finding ID strings.

Configuration for sensitive access

When community auditors are enabled, this configuration shape must be supported:

{
    "SENSITIVE_ACCESS": {
        "resources": [
            {"action-name": ["resource-pattern", ...]},
            ...
        ]
    }
}

For a policy statement that is allowed, report "SENSITIVE_ACCESS" when both of the following hold:

  • The action of the statement matches an action configured under resources.
  • The resource of the statement matches one of the resource patterns configured for that action.

Resource patterns must support the trailing * wildcard, which is used for prefix matching. For example:

arn:aws:s3:::secret*

matches:

arn:aws:s3:::secretbucket/*

Matching is specific to the action: a resource pattern configured for s3:GetObject must not trigger on a statement granting s3:PutObject.

Multiple configured action entries must be accepted, along with multiple resource patterns for an action. When any configured action/resource pair matches, the single finding ID "SENSITIVE_ACCESS" is produced.

Observable scenarios that are required

For a policy that allows:

  • s3:GetObject on arn:aws:s3:::secretbucket/*
  • s3:PutObject on arn:aws:s3:::otherbucket/*

these results are required:

  1. A configuration of s3:GetObject with arn:aws:s3:::secret* returns:

    policy.finding_ids == {"SENSITIVE_ACCESS"}

  2. A configuration of s3:GetObject only with arn:aws:s3:::otherbucket* returns:

    policy.finding_ids == set()

  3. Configuring several entries, including actions and patterns that do not match, still returns {"SENSITIVE_ACCESS"} if one pair matches. For example, the matching pair s3:GetObject/arn:aws:s3:::secret* must be found among:

    [
    {"iam:CreateUser": ["*"]},
    {
        "s3:GetObject": [
            "arn:aws:s3:::otherbucket*",
            "arn:aws:s3:::secret*",
        ]
    },
    {"s3:PutObject": ["arn:aws:s3:::secret*"]},
]

  4. If none of the configured action/resource pairs match, including when the configured actions are absent from the policy, return:

    policy.finding_ids == set()
