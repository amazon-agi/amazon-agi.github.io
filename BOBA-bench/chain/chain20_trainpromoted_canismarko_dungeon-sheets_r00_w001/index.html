Task Description

Your work happens inside the dungeonsheets Python package. Implement or adjust the public behavior described below, and keep all unrelated package behavior preserved. Every module, class, function, property, and signature named here must remain importable and usable by external code.

1. Character equipment, armor class, and speed

Module: dungeonsheets.character
Classes: Character, Wizard, and Druid
Related modules: dungeonsheets.armor and dungeonsheets.race

Character.wear_armor(armor)
  • The method must accept any of the following: a string naming an armor type, an Armor subclass, or an Armor instance.
  • A string, such as 'leather armor', is resolved to the corresponding armor type, and that type is instantiated.
  • An Armor subclass is instantiated before the assignment happens.
  • When an Armor instance is supplied, that same object is what character.armor becomes.
  • After a successful call, character.armor is an Armor instance and not the name or class that was passed in.
  • Armor given during character construction, or through Character.set_attrs(armor=...), must go through this same conversion behavior.
Character.wield_shield(shield)
  • The method must accept any of the following: a string naming a shield, a Shield subclass, or a Shield instance.
  • A string, such as 'shield', is resolved to the corresponding shield type, and the shield class gets instantiated.
  • When a Shield instance is supplied, that instance is what character.shield becomes.
  • Once the call has succeeded, character.shield is a Shield instance.
  • A shield given during character construction, or through Character.set_attrs(shield=...), must go through this same conversion behavior.
Character.armor_class

Armor class is computed as follows:

  1. the base_armor_class of the body armor being worn, or 10 when no body armor is worn;
  2. plus the modifier for the character's Dexterity;
  3. plus the armor-class bonus of the equipped shield, or 0 when the character has no shield equipped.

The body armor's base armor class takes the place of the unarmored base of 10; it does not get added on top of 10. A Shield has a standard bonus of 2.

The Dexterity modifier is the standard value floor((dexterity - 10) / 2) — equivalently (dexterity - 10) // 2 when the score is an integer. In particular, Dexterity 16 gives a modifier of +3.

When the equipped body armor has a dexterity_mod_max that is not None, its Dexterity contribution is min(actual_dexterity_modifier, dexterity_mod_max). When that value is None, the full modifier is used.

For a character whose Dexterity is 16:

  • LeatherArmor has a base armor class of 11 and no cap, hence armor_class == 14.
  • If the dexterity_mod_max of that armor instance is changed to 1, then armor_class == 12.
  • With no body armor worn and a standard Shield equipped, armor_class == 10 + 3 + 2 == 15.
Character.speed
  • Return the speed that the character's race supplies.
  • When a character is constructed with race='halfling', that name resolves to the corresponding race object and the character ends up with a speed of 25.
  • If character.race is None, the default speed 30 is returned.

2. How Druid spells are handled

Module: dungeonsheets.character
Class: Druid
Related module: dungeonsheets.spells

A Druid prepares spells instead of learning them. This distinction comes into play both when a Druid is constructed and when Druid.set_attrs(...) is called:

  • A spells=[...] value must not cause those learned spells to land in character.spells.
  • Whenever the spells collection that is supplied is non-empty, a warning must be issued through Python's warnings module, and its message must be exactly Druids cannot learn spells.
  • When the spells collection is empty, that warning is not required.
  • The source used to populate the Druid's character.spells is spells_prepared=[...]; input given as learned spells must not be mixed into that collection.
  • The entries held in character.spells are spell instances — not names, not spell classes.
  • Resolution of spell names pays no attention to case or spacing. The public spell inventory must include dungeonsheets.spells.Druidcraft, and a prepared name such as 'druidcraft' resolves to an instance of that class.

As an example, after the following code:

character = Druid()
character.set_attrs(
    spells=['invisibility'],
    spells_prepared=['druidcraft'],
)

character.spells holds exactly one entry, that entry is a dungeonsheets.spells.Druidcraft instance, and no Invisibility instance is added from spells.

3. Wild shapes available to a Druid

Module: dungeonsheets.character
Class: Druid
Related modules: dungeonsheets.monsters and dungeonsheets.exceptions

During construction, a Druid supports level=<int>, wild_shapes=[...], and the optional public attribute circle=<string>. If circle is left out, or if a circle other than 'moon' is used, the standard-Druid limits described below are what apply.

Assigning and resolving wild shapes
  • Druid.wild_shapes may be assigned a collection holding monster names, existing dungeonsheets.monsters.Monster instances, or a blend of the two.
  • Names resolve with no regard for capitalization, and normal spacing between words is tolerated — for example 'Wolf', 'giant eagle', and 'ankylosaurus'.
  • A name, once resolved, is instantiated as its corresponding monster class.
  • An existing Monster instance is accepted directly and kept as that same instance; it is not re-resolved or swapped for anything else.
  • If any name fails to resolve to a known monster, the assignment raises dungeonsheets.exceptions.MonsterError.
  • A monster that is known but currently ineligible does not amount to an unknown-name error. It still stands as a resolved candidate, yet it is left out of the filtered wild_shapes result.
  • The resolved candidates are exposed by character.all_wild_shapes, regardless of current eligibility. character.wild_shapes returns a list holding only the candidates for which character.can_assume_shape(...) is true at the character's current level and circle.

In particular, 'giant eagle' must be a recognized name that the monsters module supplies. For a level-2 standard Druid, the assignment of ['Wolf', 'giant eagle'] succeeds, and the filtered wild_shapes list contains only the Wolf.

Limits by challenge rating

A Druid below level 2 cannot assume any wild shape, no matter the circle or the monster's attributes.

The maximum challenge rating for a standard Druid of level 2 or above is:

Druid's level Maximum CR
2–3 1/4
4–7 1/2
8+ 1

The maximum challenge rating for a Circle of the Moon Druid (circle='moon') is:

Druid's level Maximum CR
2–5 1
6+ level // 3

So a standard Druid at level 2 can include the CR-1/4 Wolf; a Moon Druid at level 2 can include the CR-1 Ape; and a Moon Druid at level 9 can include the CR-3 Ankylosaurus, because 9 // 3 == 3.

Beast status and movement restrictions

Challenge rating is not the only condition for eligibility. All of the following must hold:

  • The monster must be a beast. When a monster's type or description fails to identify it as a beast, that monster is rejected.
  • At levels below 4, a monster whose swim_speed is positive is rejected.
  • At levels 4 and above, a positive swim speed is allowed.
  • At levels below 8, a monster whose fly_speed is positive is rejected.
  • At levels 8 and above, a positive fly speed is allowed.
  • A swim or fly speed of zero does not set off the corresponding restriction.

These limits on movement hold for both standard and Moon Druids, on top of their respective challenge-rating limits.

Druid.can_assume_shape(monster)
  • The method accepts a monster instance and returns a Boolean.
  • The return value is True only when the Druid is at least level 2 and the monster simultaneously satisfies beast status, the applicable challenge-rating limit, and both movement restrictions.
  • If any condition fails, the method returns False rather than accepting the shape.
  • A subclass of monsters.Monster that carries description = 'beast', the base low challenge rating, and zero movement speeds is accepted by a standard Druid at level 2 but rejected by a level-1 Druid.
  • A monster with description = 'monster' is not a beast and must return False.
Inventory of monsters and beast metadata

The dungeonsheets.monsters module must expose at least the known classes that these APIs need: Monster, Wolf, GiantEagle, Ape, and Ankylosaurus.

  • Wolf is a beast carrying CR 1/4.
  • Ape is a beast with CR 1, matching the Moon-Druid boundary given above.
  • Ankylosaurus is a beast carrying CR 3.
  • GiantEagle can be resolved from 'giant eagle' and is ineligible for a standard Druid at level 2.
  • The base Monster class stays subclassable. It provides the challenge-rating, swim-speed, and fly-speed attributes that the predicate relies on, and its beast-status behavior must be derivable from type/description metadata. A description that contains beast is recognized as a beast no matter the letter case; descriptions such as monster are not recognized.

2. Multiclass character support — dungeonsheets.character.Character

The Character constructor must accept the keyword arguments listed below, which allow a single character to hold multiple classes:

  • name (str)
  • classes (list of class-name strings, e.g. ['wizard', 'fighter']), case-insensitive class identifiers
  • levels (list of ints, one per entry in classes)
  • subclasses (optional list, one entry per class; each entry is either None or a subclass name string, e.g. [None, 'Eldritch Knight'])

The lists line up by position: index i of classes, levels, and subclasses refers to the same class.

2.1 Overall level
  • Character.level (attribute/property) returns the sum of all entries in levels.
    • e.g. for levels=[5, 4] the result is level == 9.
2.2 Spellcasting

  • Character.spellcasting_classes is a collection (supporting len()) made up of the character's classes that possess spellcasting ability.

    • wizard is an example of a spellcasting class.
    • fighter is normally not a spellcasting class, but it is one with the Eldritch Knight subclass.
    • Example: with classes=['wizard', 'fighter'] and no subclasses, len(spellcasting_classes) == 1.
    • Example: with classes=['wizard', 'fighter'] and subclasses=[None, 'Eldritch Knight'], len(spellcasting_classes) == 2.

  • Character.spell_slots(spell_level=<int>) returns the number of spell slots available at the given spell level (int).

    For a multiclass caster, spell slots are determined by an effective combined caster level calculated from the spellcasting classes:

    • A full caster (e.g. wizard) adds its class level in full.
    • A "third-caster" subclass such as Eldritch Knight adds one third of that class's level (rounded down).

    Given classes=['wizard', 'fighter'], subclasses=[None, 'Eldritch Knight'], levels=[5, 4]:

    • The wizard contributes 5; the Eldritch Knight fighter (level 4) contributes 1 (floor of 4/3).
    • This yields an effective caster level of 6.
    • The resulting slots must be: spell_slots(spell_level=1) == 4, spell_slots(spell_level=2) == 3, spell_slots(spell_level=3) == 3, spell_slots(spell_level=4) == 0.

    (These match the standard 5e multiclass spellcaster slot table at combined caster level 6.)

2.3 Proficiencies in saving throws
  • Character.saving_throw_proficiencies is a collection (supporting in) of ability names (lowercase strings such as 'intelligence', 'wisdom').
  • For a multiclass character, the saving throw proficiencies are taken from the first (primary) class only.
    • Example: with classes=['wizard', 'fighter'], both 'intelligence' and 'wisdom' are present (these two are wizard's saving throw proficiencies).
2.4 Weapon/armor proficiency and multiclassing rules

  • Character.is_proficient(item) returns a bool that indicates whether the character is proficient with the given weapon/armor object.

  • Multiclassing rules: when a class is taken on as a secondary class (not the first entry in classes), the character does not gain that class's full starting proficiencies. Specifically:

    • rogue as a secondary class does not grant simple weapon proficiency.
    • Which proficiencies a character receives depends on the order of the classes.

    Examples that use a Shortsword instance:

    • classes=['wizard', 'fighter'], levels=[5, 4] → proficient with a shortsword (fighter grants martial/simple weapons; the multiclass rules grant fighter weapon proficiencies whether it is primary or secondary). is_proficient(shortsword) == True.
    • classes=['wizard', 'rogue'], levels=[5, 4] → not proficient with a shortsword; multiclassing into rogue does not grant simple weapon proficiency, and wizard (primary) does not grant it either. is_proficient(shortsword) == False.
    • classes=['rogue', 'wizard'], levels=[4, 5] → proficient with a shortsword; rogue as the primary class grants its full weapon proficiencies (simple weapons included). is_proficient(shortsword) == True.

Behavior for Weapon Wielding by Characters

  • attack_modifier computed as the relevant ability modifier plus the proficiency bonus (when the character is proficient with the weapon).
  • For a finesse weapon (such as Shortsword), the ability modifier that goes into attack_modifier is the higher of the Strength and Dexterity modifiers.

This requires spells to be equal when they represent the same spell.

  • The existing imports listed below must keep working unchanged and refer to the same objects/behavior they always have:
    • from dungeonsheets import make_sheets, character
    • make_sheets.load_character_file(charfile) — loads a character definition out of a Python example file and returns a mapping; when the example rogue character file is used, the "strength" entry of the returned mapping equals 10.
  • Aside from the above, no public interfaces are added or changed. All the other existing modules and their public members (character, dice, features, latex, spells, stats, weapons, monsters, race, readers, etc.) must retain their current behavior and importability exactly as-is.
  • The dungeonsheets.character module must keep exposing Character, Wizard, Druid, and _resolve_mechanic.

In essence, the change moves the PDF-template generation functions into the new fill_pdf_template module, keeps create_character_pdf_template reachable via make_sheets, and ensures that calling create_character_pdf_template(character=..., basename=...) creates the corresponding .pdf file.

Task Specification: Add Support for Foundry VTT JSON Character Files

Summary

The codebase contains a character file reader that parses character definitions written in several file formats. Support for reading character data exported from Foundry VTT (a JSON format) must be added alongside the existing support for Python character files and Roll20 JSON files.

Public API

A reader function already exists, and it must continue to work for all supported formats:

from dungeonsheets.readers import read_character_file

read_character_file(charfile)

  • charfile: a path to a character file (it may be a pathlib.Path or a string).
  • Returns a dict that maps character attribute names to their values.
  • The format is determined from the file itself/extension; the format is not indicated by the caller.
  • Reading may emit warnings; such warning emission is acceptable and must not raise.

A dict value may be either a concrete container (lists, tuples) or a generator. Consumers may force generators to lists; for sequence-valued keys where noted, both list and generator return types are acceptable.
