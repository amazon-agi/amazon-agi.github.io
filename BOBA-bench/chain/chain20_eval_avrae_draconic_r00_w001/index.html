01 DraconicInterpreter is a sandboxed evaluator of expressions that uses a string type specific to its configuration. 931 words · rewritten by GPT-5.6-sol, reworded by GLM-5.3-Flash

Task Description

Summary

DraconicInterpreter is a sandboxed evaluator of expressions that uses a string type specific to its configuration. The task modifies that type so that evaluated strings are genuine Python strings, while the interpreter's existing sandbox restrictions, resource limits, formatting behavior, and container access semantics are preserved.

Public API

  • DraconicInterpreter can be imported from draconic and constructed with a config keyword argument.
  • An interpreter exposes builtins, an attribute that is mutable and dict-like; in particular, callers can add values via interpreter.builtins.update({...}).
  • An interpreter can be called with a Draconic expression string and returns the evaluated value: interpreter("<expression string>").
  • The existing public exception types used by the behaviors below are FeatureNotAvailable and IterableTooLong.

Behavior Requirements

1. Evaluated strings use a real subclass of str

The interpreter's custom/configured string type must be a subclass of Python's built-in str; it must not merely wrap a string in a proxy that is not a str. As a consequence, evaluated string literals are instances of both the custom string type and built-in str.

Apart from the explicit sandbox restrictions and resource-limit checks described below, the standard str operations must be available on evaluated strings, with the same argument handling and results as Python's built-in str operations. Wherever the evaluator normally normalizes a string result, the existing conversion to the interpreter's configured string type must continue. String literals, as well as the interpreter's default str(...) conversion, must continue to use the same configured custom type, whose externally reported type name remains str.

These include the standard stripping methods together with their optional chars argument:

  • str.strip([chars])
  • str.lstrip([chars])
  • str.rstrip([chars])

Evaluating the following expressions must produce these results:

  • ''.strip('') evaluates to ''.
  • ' aaa '.strip() evaluates to 'aaa'.
  • 'foobar'.lstrip('f') evaluates to 'oobar'.
  • 'foobar'.rstrip('ra') evaluates to 'foob'.

These built-in methods must accept arguments that are themselves evaluated strings as ordinary strings. In particular, '', 'f', or 'ra' passed as chars must not fail merely because those values use the custom string type.

2. Sandbox restrictions take precedence over ordinary str behavior

Becoming a real str subclass must not expose the string operations that the sandbox intentionally prohibits. Calling each of the following methods on an evaluated string must raise FeatureNotAvailable instead of executing the corresponding Python operation:

  • encode(), as in 'blargh'.encode()
  • format(), as in '{}'.format(1)
  • format_map(), as in '{a}'.format_map({'a': 1})

These restrictions override the general requirement to match built-in str. Even though built-in str supplies those methods, they apply. The interpreter's already-supported f-string or percent-style formatting is not disabled by them; those forms remain subject to their existing validation and size limits.

3. Accessing dictionary keys with dot notation

When attribute access is written in dot notation on a dictionary-like evaluated value, it must return the value associated with the matching string key. For example:

  • ({'a': 1}).a evaluates to 1.

Despite the interpreter's custom string type, this must work when the dictionary and its key are created inside the evaluated expression.

4. Existing string and container behavior stays compatible

Changing the string type must not cause existing operations to regress. In particular:

  • 'foo'.center(5) evaluates to ' foo '.
  • Indexing into containers continues to return the correct element and value type. For a list l = [1, 2, '3'], l[0] returns integer 1, while l[-1] returns string '3'.
  • Subscript and attribute access remain interoperable with dictionaries and other containers that contain mixed key/value types. Plain strings and evaluated custom strings must behave as equivalent dictionary keys. Integer and tuple keys must also continue to work. For example, a dictionary containing {'abc': 'abc', 123: 123, ('1', 1): ('1', 1)} must support the corresponding string, integer, and tuple subscripts and return values of the correct types.
  • Ordinary percent-style (%) string formatting continues to follow Python behavior in cases where the sandbox permits it, including tuple and mapping operands and escaped percent signs. In particular, '%%(foo)s %s' % {'foo': 0} evaluates to "%(foo)s {'foo': 0}".
5. Dynamic * in percent-style formatting is not permitted

The dynamic * width and precision feature from Python is not available in Draconic percent-style formatting. Evaluation must raise FeatureNotAvailable if any conversion field obtains its width or precision from *. This covers all of the following forms:

  • '%*f' % (...)
  • '%.*f' % (...)
  • '%*.*f' % (...)

Fixed numeric widths and precisions continue to be supported, subject to the existing output-size safeguards. Escaped percent signs and mapping/sequence formatting that is otherwise valid must retain their existing behavior.

6. Existing string-size safeguards stay enforced

The change to the string type must not bypass limits derived from DraconicConfig.max_const_len. The existing guarded string operations and formatting forms must continue to raise IterableTooLong when their requested or conservatively estimated result is too large. This covers the existing guarded centering, tab expansion, joining, justification, replacement, translation, zero-fill, f-string, and percent-formatting paths.

For example, an ordinary request such as 'foo'.center(5) succeeds, while 'foo'.center(...) with an excessively large width raises IterableTooLong. The stripping examples in this specification must complete normally, and they do not require any new size-limit failure behavior.

Scope and Compatibility

  • The interpreter's existing attribute-access safety checks and all other sandbox restrictions must be preserved.
  • The configured custom string type must remain interoperable with built-in strings, dictionary hashing and key lookup, indexing, formatting, and existing safe container types.
  • A sandbox exception must not be replaced with unrestricted built-in behavior merely as a consequence of inheriting from str.
  • There should be no change to unrelated language or evaluator behavior.

1. Keywords for loop control flow

break, continue, and return must be supported inside both while and for loops. They must work when the interpreter is given a multi-line block (via execute) and for single-line evaluation.

while loops:

  • break exits the loop immediately.
  • continue skips ahead to the next iteration.
  • return <value> exits the entire program, returning <value>.

for loops (e.g. for x in range(n):):

  • break, continue, and return behave the same as in the while case.
  • During iteration, the loop variable binds to each successive element (e.g. for i in range(500): return i yields 0).

Outside of any loop / control flow:

  • A bare break statement must raise DraconicSyntaxError (in both block execution and single-line evaluation).
  • A bare continue statement must raise DraconicSyntaxError (in both block execution and single-line evaluation).
  • A return <value> statement is legal at top level (not inside a loop). It returns immediately; any statements that come after the first executed top-level return do not run. In single-line form, return 1 evaluates to 1.
2. Configurable limits on execution

The interpreter must enforce three limits, taken from the currently active _config:

  • max_loops: The cumulative count of loop iterations across the program. Going over it raises TooManyStatements. This applies to both while and for loops (e.g. iterating for _ in [0] * 101 with max_loops=100 must raise; an infinite while True loop must raise once the iterations exceed the limit).
  • max_statements: A cap on the total number of statements/operations executed. Going over it raises TooManyStatements (e.g. a single assignment whose right-hand side chains many additions can go over a small max_statements).
  • max_const_len: The maximum length any constructed string/iterable is allowed to have (see below).

Since limits are read from _config at execution time, replacing interpreter._config with a new DraconicConfig must change the limits enforced for the next execute call.

3. Enforcing max_const_len (IterableTooLong)

Any operation that would create a string/collection whose length goes over max_const_len must raise IterableTooLong. This includes:

  • f-strings: The final value of an evaluated f-string gets length-checked against max_const_len.

    • Interpolating a name whose value on its own exceeds the limit raises IterableTooLong.
    • Concatenation through multiple interpolations or added literal text that pushes the total past the limit raises IterableTooLong.
    • Example: given a limit under which a 999-char value is allowed but 1000+ is not, f'{x}' (x len 999) succeeds, f'{x}a' succeeds only if 1000 is still within the limit, and f'{x}{x}' and f'{x}aaaaaa' raise when the total exceeds the limit.
  • dict item assignment: d['foo'] = 'bar' executed on a dict that is already at the size limit must raise IterableTooLong.
  • string .replace(...): when the string produced is longer than the limit, IterableTooLong is raised (see String methods below).
  • (Existing) list/dict construction, multiplication, unpacking, .update(...), and | union operations that exceed the limit keep raising IterableTooLong.

The interpreter provides its own safe subclasses of list, set, and dict, exposed as interpreter._list, interpreter._set, interpreter._dict. Values produced by literals and by the built-in constructors (list(...), set(...), dict(...)) must be instances of these safe types.

  • list('123') produces a value of type interpreter._list; the list literal [1, 2, 3] is of that same type.
  • set('123') produces a value of type interpreter._set; the set literal {1, 2, 3} is of that same type.
  • dict(((1, 1), (2, 2))) produces a value of type interpreter._dict; a dict literal is of the same type.

06 Implement support for structural pattern matching (match/case) in the Draconic interpreter, along with a supporting helper function. 1042 words · source specification, reworded by GLM-5.3-Flash

Task Description

Implement support for structural pattern matching (match/case) in the Draconic interpreter, along with a supporting helper function.

Part 1: The zip_star helper function

Define a function zip_star inside the module draconic.helpers.

Function signature:

def zip_star(names, values, star_index):

Behavior of the function:

Each element of names (a sequence of length N) is paired by zip_star with a corresponding portion of values (a sequence). Exactly one of the positions in names — the one at index star_index — is regarded as a "star" element that absorbs a list of zero or more values; all other positions absorb exactly one value each.

The function returns an iterable of (name, value) tuples, one for each name, in order. The rule for splitting values is as follows:

  • Positions before star_index (there are star_index of them) each get paired with a single successive value taken from the front of values.
  • Positions after star_index (there are N - star_index - 1 of them) each get paired with a single successive value taken from the back of values.
  • The star position pairs with a list that holds all of the remaining middle values (the list may be empty).

The count of values is always at least N - 1 (that is, the number of non-star positions). The star element is given len(values) - (N - 1) values in the form of a list.

Examples:

list(zip_star(['a','b','c'], [1,2,3,4], star_index=0)) == [('a', [1,2]), ('b', 3), ('c', 4)]
list(zip_star(['a','b','c'], [1,2],     star_index=0)) == [('a', []),    ('b', 1), ('c', 2)]
list(zip_star(['a','b','c'], [1,2,3,4], star_index=1)) == [('a', 1), ('b', [2,3]), ('c', 4)]
list(zip_star(['a','b','c'], [1,2],     star_index=1)) == [('a', 1), ('b', []),    ('c', 2)]
list(zip_star(['a','b','c'], [1,2,3,4], star_index=2)) == [('a', 1), ('b', 2), ('c', [3,4])]
list(zip_star(['a','b','c'], [1,2],     star_index=2)) == [('a', 1), ('b', 2), ('c', [])]
list(zip_star(['a'],         [1,2,3],   star_index=0)) == [('a', [1,2,3])]

It must be possible for the return value to be wrapped by list(...).

Part 2: Support for the match / case statement in the interpreter

Extend the Draconic interpreter so that it supports Python's match statement. Draconic code runs via the interpreter's execution entry point; the interpreter tracks the print(...) output that gets emitted and supports return.

The imports that follow must remain valid:

from draconic import DraconicValueError
General semantics of match

A match statement evaluates a subject expression and then checks it against each case pattern in order. The body of the first case that matches is executed, and no further cases are tried. If a case carries a guard (if <expr>), the case matches only when its pattern matches and its guard evaluates truthy.

Name bindings that a matching pattern produces must leak into the enclosing scope — after the match statement, any names bound by the winning case remain accessible.

Binding must happen before guard evaluation: while a guard is being evaluated, the names captured by that case's pattern are already bound and usable within the guard expression.

Patterns that are supported

The pattern forms that follow must be supported:

  • Capture pattern — a name by itself (e.g. case x:). Matches any subject and binds the subject to that name. (This is an irrefutable catch-all.)

  • Wildcard — _. It matches anything and binds nothing.

  • Value/literal patterns — literals, for instance integers (e.g. case [1, 2, x]:). A literal in a pattern matches only when the subject element that corresponds to it is equal to that literal.

  • Sequence patterns — [p0, p1, ...]. Matches a subject that is a sequence when the element count is compatible and every sub-pattern matches the corresponding element.

    • A sequence pattern may contain at most one star element (*name or *_), and this element captures a list of the remaining elements (possibly empty). The star may appear at the start, in the middle, or at the end. Sub-patterns without a star that sit before/after the star bind to the corresponding fixed positions; the star name (when it is not _) binds to a list of the leftover middle elements. The splitting of the subject sequence across the sub-patterns follows the same rule as zip_star.
    • A fixed-length sequence pattern (one with no star) matches only a subject whose length is exactly that.

  • As patterns — case <pattern> as <name>:. The inner pattern is what gets matched; if it matches, name is additionally bound to the whole subject value matched at that position. as patterns may be nested (e.g. ((b as c) as d) as e), and each level produces its own additional binding to the same underlying value.

The multiple-assignment error

One and the same name may not be bound more than once by a single case pattern. If a pattern attempts to bind one name in two or more places (including bindings nested inside sub-patterns and inside recursive sub-sequences), execution must raise DraconicValueError whose message contains the substring multiple assignment.

Examples of the required behavior

With a = [1, 2, 3]:

match a:
    case [1, 2, x]:
        print(x)     # matches, x == 3
    case x:
        print(x)
print(x)             # x == 3 leaks out
# output: 3, 3

match a:
    case [x, *_]:
        print(x)     # x == 1
    case x:
        print(x)
print(x)
# output: 1, 1

match a:
    case [x, 1, 1]:  # does not match (2 != 1)
        print(x)
    case x:

  • Dictionary comprehensions. Their entry count and their content, string keys included, are subject to the same limit. A dictionary comprehension that stays within the aggregate limit must succeed and return the expected dictionary.

The size and the content of individual values therefore matter; it is insufficient to limit only the number of comprehension iterations or the count of emitted top-level values. Loop limits that already exist remain separate and must continue to apply.

3. Enforce the same rule when constructors are fed by generators

Giving a generator expression as input to a collection constructor must not provide a bypass. The destination collection must be checked while the generator is consumed. For example, dict((key, value) for ... ) must succeed when its aggregate result is within the configured limit, and it must raise IterableTooLong if the aggregate result exceeds it. Generator-fed list and set construction fall under the same principle.

This requirement is about materialized collections; it does not require that an otherwise bare generator expression be eagerly materialized.

4. Preserve valid dictionary creation and copying

With a 1,000-unit limit and range exposed in builtins, both of the following constructions must succeed:

  • {f'{i:03}': 'a' for i in range(200)}
  • dict((f'{i:03}', 'a') for i in range(200, 342))

The keys in these dictionaries are disjoint three-character strings. Under the aggregate-size formula, the first weighs exactly 1,000 units (200 entries × 5 units) and the second weighs 710 units (142 entries × 5 units); both are within the limit and must be built successfully. Calling .copy() on either of the valid dictionaries must also succeed and produce the expected copy — including copying the first dictionary, whose aggregate size sits exactly at the maximum. Valid construction or copying must not be rejected by limit enforcement merely because the data came from a comprehension or a generator.

5. Apply the accounting consistently as collections grow or combine

The same content-weighted accounting must be applied whether a collection is created by a comprehension, materialized from a generator, copied, or enlarged through an existing collection operation. Direct insertion is included here, as are operations such as update(), union, and |= where the running Python version supports those operations.

For the two valid dictionaries above, combining all 342 disjoint keys must raise IterableTooLong: the combined result weighs 342 × (1 + 3 + 1) = 1,710 units, far above a 1,000-unit limit (the key text alone already contributes 342 × 3 = 1,026 units). This holds when update() or dictionary union/|= combines the dictionaries, and equivalent growth past the limit through item assignment must also be rejected.

Because the 200-entry dictionary sits exactly at the 1,000-unit maximum, any further growth of it must raise IterableTooLong, no matter how small the addition. In particular, each of the following must raise on that dictionary:

  • Item assignment for a single small entry, e.g. d['foo'] = 'bar'.
  • d.update(...) called with a one-entry dictionary such as {'foo': 'bar'}.
  • Union of the dictionary with a one-entry dictionary (d | {'foo': 'bar'}) and in-place union (|=), where the running Python version supports the dictionary union operators.

A grow operation that fails with IterableTooLong must not mutate the collection: after an update(), union, or assignment is rejected, the collection retains its previous contents and its previous aggregate size, and the limit checks that follow are made against that unchanged size. Operations that keep the aggregate at or below the limit must continue to work normally.

6. Error behavior

Every collection-building or collection-growing path covered above must use IterableTooLong to signal an over-limit result. Such a path must not silently return the oversized value or rely only on Python memory exhaustion, and using a comprehension or a generator must not change the applicable exception class.

Feature Scope and Non-goals

Support for either of the following language constructs is neither added nor required by this task:

  • A bare return statement (a return carrying no value).
  • try statements, including their except, else, and finally clauses.

As part of this work, support for those constructs need not be implemented, nor does it need to be preserved. All other existing interpreter behavior and public APIs lie outside the intended change and must remain compatible.

2. Aggregate-size limits for comprehensions and generator expressions

The configured budget

The budget that matters is the interpreter's configured DraconicConfig.max_const_len value. It is a budget on aggregate approximate size, not a raw cap on the number of output elements. The configured value must be the one used; no fixed element limit or hard-coded boundary may replace it. The existing default of 200_000 stays the same. The boundary examples that follow explicitly use max_const_len=1_000.

List comprehensions, set comprehensions, dict comprehensions, and generator expressions all fall under the limit, including generator expressions consumed by constructors or other callables. It likewise applies across filtering, multiple generator clauses, nested output values, and any other supported comprehension form. Existing loop and statement limits keep applying independently.

Accounting for size

Each comprehension or generator expression carries a cumulative production total. For every value that it emits, add:

  • one unit for the emitted result itself; and
  • the approximate content size of that emitted result.

Approximate content size is determined by the interpreter's existing recursive size semantics:

  • The contribution of a string is its character length.
  • A tuple or other container contributes its own cardinality together with the approximate sizes of the values it contains, computed recursively.
  • An ordinary scalar without iterable content contributes no content units, so its emitted-result cost is the one per-result unit.

A direct dict-comprehension entry is accounted for in a special way, as:

1 + approximate_size(key) + approximate_size(value)

Because a dict comprehension emits an entry directly, the key/value pair is not charged the cardinality of an additional tuple. In contrast, a generator expression such as ((key, value) for ...) emits actual two-item tuples. Each such tuple therefore contributes, in addition to the one per-result unit, its cardinality and its recursively contained sizes.

The accounting is based on the results emitted, rather than only on the final cardinality of the destination container. The cumulative total may equal max_const_len; when the next emitted value would make the total greater than max_const_len, IterableTooLong must be raised.

Incremental enforcement

The budget must be checked incrementally while values are being emitted. With a lazy generator expression, the check happens as its consumer requests values. Any value that would exceed the budget must not be delivered to the consumer, and construction must stop with IterableTooLong. This prevents a generator or comprehension from bypassing the limit no matter which supported constructor or callable consumes it. Existing contextual exception propagation stays intact; if an interpreter call wraps nested errors, the underlying limit error must be IterableTooLong.

interpreter.eval("{f'{i:03}': 'a' for i in range(201)}")  # raises IterableTooLong: 201 * 5 = 1,005

Task Specification: Adding Starred/Unpacking Support to the Draconic Interpreter

Summary

The Draconic interpreter (a sandboxed evaluator of Python-subset expressions) must support Python's starred unpacking in two contexts:

  1. Starred assignment targets — collecting "the rest" of an iterable into a list as part of a compound (tuple/list) assignment.
  2. Unpacking inside literals — the placement of * inside list/set displays and of ** inside dict displays.

The interpreter's existing iterable length limits must be respected by all unpacking operations.

Tests invoke the interpreter via a callable e(source_string) that evaluates or executes a snippet and returns the resulting value; state (assigned names) persists from one call to the next. Your implementation must make the behaviors below work when the interpreter's normal parse/evaluate path is used to drive them.

Applicable Exceptions

These exception types are exposed by the interpreter (already present in the codebase); reuse them:

  • DraconicValueError — raised when a runtime value/unpacking mismatch occurs.
  • DraconicSyntaxError — raised for constructs that are syntactically invalid.
  • IterableTooLong — raised when an operation would produce or consume an iterable that exceeds the configured length limit.

Required Behavior

1. Starred targets in assignments

A single starred target must be supported in compound assignment. The right-hand side is unpacked by position; the starred target takes in all remaining elements as a list.

For the given RHS iterable, elements are assigned to the non-starred targets before and after the star, and the star target is given the middle segment as a list:

  • a, *b = (1, 2, 3, 4) → a == 1, b == [2, 3, 4]
  • a, *b, c = (1, "foo", "bar", "baz", 5) → a == 1, b == ["foo", "bar", "baz"], c == 5
  • a, *b = [i + 1 for i in range(4)] → a == 1, b == [2, 3, 4]

The value captured by the star target is always a list (even when it is empty or when the RHS is another iterable type).

Error cases:

  • If the RHS does not have enough elements to satisfy the non-starred targets, raise DraconicValueError.
    • e.g. a, *b = tuple() → DraconicValueError (an empty RHS cannot fill the required target a).
  • If a single assignment target list contains more than one starred target, raise DraconicSyntaxError.
    • e.g. a, *b, *c, = (1, 2, 3) → DraconicSyntaxError.

(The existing rule remains unchanged: non-starred compound assignment with mismatched counts raises DraconicValueError, e.g. a, b = 1.)

2. * unpacking in list and set displays

Inside list and set literals, support *expr, splicing the elements of expr into the resulting collection in order.

  • a = [1, 2, 3], b = [4, 5, 6]
    • [*a, *b] → [1, 2, 3, 4, 5, 6]
    • [*a, *a, *b, *b] → [1, 2, 3, 1, 2, 3, 4, 5, 6, 4, 5, 6]
  • Plain elements may be freely mixed with starred unpacking, e.g. [1, *a] produces a list with 1 followed by the elements of a; {*a, 1000} produces the set of a's elements together with 1000.

Set displays that contain unpacking produce a set with the usual set semantics (deduplication).

3. ** unpacking in dict displays

Inside dict literals, support **expr, merging the key/value pairs of expr into the resulting dict. Entries that come later override earlier ones by key (standard Python merge semantics).

  • a = {"a": 1, "b": 2}, b = {"c": 3, "d": 4}
    • {**a, **b} → {"a": 1, "b": 2, "c": 3, "d": 4}
    • {**a, **a, **b, **b} → {"a": 1, "b": 2, "c": 3, "d": 4}
4. Enforcing the length limit

The interpreter's configured maximum iterable length must be enforced by every unpacking operation. If an unpacking/splice would produce a cumulative result that exceeds the limit, raise IterableTooLong. This applies while the collection is being built (i.e. the running total across all spliced/plain elements is bounded).

Assume long and longer are iterables at or over the limit, and long2 is another iterable of that kind:

  • [1, *long] → IterableTooLong
  • [*long, *long] → IterableTooLong
  • {*long, 1000} → IterableTooLong
  • {*longer} → IterableTooLong
  • {**long, **long2} → IterableTooLong

Note: unpacking oversized iterables into displays must no longer be rejected as an unsupported feature; it must be accepted and, instead, bounded by the length limit as described above. (Multiple */** unpackings within a single display are permitted.)

Constraints

  • Starred assignment targets always yield a Python list.
  • List/set/dict displays produce the interpreter's normal (safe) collection types, consistent with displays that do not use unpacking.
  • Do not enforce the length limits on function-call argument unpacking or in other contexts that are not described here.

Task Description

Correct Enforcement of Iterable Length Limits During Unpacking

Context

Draconic caps the amount of data materialized when list, set, and dictionary literals are evaluated. Let LIMIT be the configured value of DraconicConfig.max_const_len. If building one of these literals exceeds its permitted cumulative size, evaluation must raise IterableTooLong.

The unpacking paths must keep a single correct running total across all ordinary and unpacked portions of a literal. The boundary is inclusive: a total equal to LIMIT is valid, whereas a total strictly greater than LIMIT is invalid. For each successive * or ** operand, the total must not be reset.

List Literals Involving * Unpacking
  • A list literal may unpack an iterable whose contribution is exactly LIMIT. For instance, if long holds exactly LIMIT simple scalar elements, [*long] must succeed and return the corresponding list.
  • Every part of the same list literal contributes cumulatively. Hence [1, *long] must raise IterableTooLong when long already consumes the full limit.
  • [*long, *long] must raise IterableTooLong when each long consumes LIMIT, since the literal attempts to materialize a total of 2 * LIMIT.
  • Otherwise, ordinary list-unpacking semantics and the resulting list contents must remain unchanged.
Set Literals Involving * Unpacking
  • A set literal may unpack an iterable whose contribution is exactly LIMIT. For instance, {*long} must succeed when long contains LIMIT permitted elements and must produce the resulting set.
  • {*longer} must raise IterableTooLong when the contribution of the unpacked iterable is greater than LIMIT.
  • Additional literal elements or additional unpacked iterables contribute cumulatively; exceeding the limit anywhere in the construction must raise IterableTooLong.
  • Otherwise, ordinary set construction and unpacking behavior must remain unchanged.
Dictionary Literals Involving ** Unpacking

Limits on dictionary literals rest on a weighted size budget, not merely on the cardinality of the mapping. For each key/value entry emitted while the literal is being built, the contribution is:

1 + approximate_size(key) + approximate_size(value)

The evaluator's existing approximate-length measure used for container limits is approximate_size. In particular, the approximate size of a string is its number of characters. The key and the value must be measured separately: the temporary key/value pair itself adds no tuple length or other container overhead. The existing approximate-size rules for individual objects are not changed by this task.

Entry costs accumulate across all entries and all ** operands in the dictionary literal, together with any ordinary entries in the same construction. Consequently:

  • A single unpacked mapping whose weighted cost is exactly LIMIT must be accepted, and {**long} must return the resulting dictionary.
  • Multiple unpacked mappings whose combined weighted cost is greater than LIMIT must raise IterableTooLong.
  • Given LIMIT = 1000, a mapping that contains 200 entries whose keys are three-character strings and whose values are one-character strings has a cost of 200 * (1 + 3 + 1) = 1000; unpacking that mapping alone must succeed.
  • If that mapping is combined with another 142 disjoint entries of the same key and value sizes, the cost is 1710, so {**long, **long2} must raise IterableTooLong.

Here, saying that a mapping is “at the limit” refers to this weighted cumulative cost, not to the raw number of entries in the mapping.

Function Calls Involving * Argument Unpacking

When positional arguments are unpacked in function calls, the max_const_len container-construction limit must not be applied. Specifically, after max is exposed through the interpreter's builtins, max(*long, *long) must be allowed to unpack both iterables and invoke the function normally even when their combined argument count or size is greater than LIMIT.

This exemption applies only to the iterable-length check described here. Normal call semantics, validation that the value after * is iterable, callable argument validation, and unrelated execution safeguards remain in effect.

Compatibility and the Public API
  • The existing evaluator and interpreter APIs must be preserved, including the interpreter's mutable builtins mapping.
  • DraconicConfig.max_const_len must remain the controlling configuration value.
  • IterableTooLong must remain the exception raised when literal construction is strictly over the permitted limit.
  • Do not modify ordinary literal results, unpacking order, mapping overwrite behavior, configuration defaults, or unrelated limits.
  • No new public API is required; the change is solely a correction to cumulative length accounting and to where that accounting is applied.
