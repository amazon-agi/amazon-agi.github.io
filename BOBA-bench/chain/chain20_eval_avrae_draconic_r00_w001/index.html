01 DraconicInterpreter is a sandboxed expression evaluator with a configuration-specific string type. 876 words · rewritten by GPT-5.6-sol

Overview

DraconicInterpreter is a sandboxed expression evaluator with a configuration-specific string type. This task updates that type so evaluated strings are genuine Python strings while preserving the interpreter's existing sandbox restrictions, resource limits, formatting behavior, and container access semantics.

Public API Surface

  • DraconicInterpreter is importable from draconic and can be constructed with a config keyword argument.
  • An interpreter exposes a mutable, dict-like builtins attribute; in particular, callers can add values with interpreter.builtins.update({...}).
  • An interpreter is callable with a Draconic expression string and returns the evaluated value: interpreter("<expression string>").
  • FeatureNotAvailable and IterableTooLong are the existing public exception types used by the behaviors below.

Required Behavior

1. Evaluated strings use a real str subclass

The interpreter's custom/configured string type must subclass Python's built-in str; it must not merely wrap a string in a non-str proxy. Consequently, evaluated string literals are instances of both the custom string type and built-in str.

Except for the explicit sandbox restrictions and resource-limit checks described below, standard str operations must be available on evaluated strings and have the same argument handling and results as Python's built-in str operations. Existing conversion to the interpreter's configured string type must continue wherever the evaluator normally normalizes a string result. String literals and the interpreter's default str(...) conversion must continue to use the same configured custom type, whose externally reported type name remains str.

This includes the standard stripping methods and their optional chars argument:

  • str.strip([chars])
  • str.lstrip([chars])
  • str.rstrip([chars])

The following expressions must produce these results:

  • ''.strip('') evaluates to ''.
  • ' aaa '.strip() evaluates to 'aaa'.
  • 'foobar'.lstrip('f') evaluates to 'oobar'.
  • 'foobar'.rstrip('ra') evaluates to 'foob'.

Arguments that are themselves evaluated strings must be accepted by these built-in methods as ordinary strings. In particular, passing '', 'f', or 'ra' as chars must not fail merely because those values use the custom string type.

2. Sandbox restrictions override ordinary str behavior

Becoming a real str subclass must not expose string operations that the sandbox intentionally prohibits. Calls to each of the following methods on an evaluated string must raise FeatureNotAvailable instead of executing the corresponding Python operation:

  • encode(), for example 'blargh'.encode()
  • format(), for example '{}'.format(1)
  • format_map(), for example '{a}'.format_map({'a': 1})

These restrictions take precedence over the general requirement to match built-in str. They apply even though built-in str supplies those methods. They do not disable the interpreter's already-supported f-string or percent-style formatting; those forms remain subject to their existing validation and size limits.

3. Dot notation for dictionary keys

Dot-notation attribute access on a dictionary-like evaluated value must return the value associated with the matching string key. For example:

  • ({'a': 1}).a evaluates to 1.

This must work when the dictionary and its key are created inside the evaluated expression, despite the interpreter's custom string type.

4. Existing string and container behavior remains compatible

Changing the string type must not regress existing operations. In particular:

  • 'foo'.center(5) evaluates to ' foo '.
  • Indexing containers continues to return the correct element and value type. For a list l = [1, 2, '3'], l[0] returns integer 1, while l[-1] returns string '3'.
  • Subscript and attribute access remain interoperable with dictionaries and other containers containing mixed key/value types. Plain strings and evaluated custom strings must behave as equivalent dictionary keys. Integer and tuple keys must also continue to work. For example, a dictionary containing {'abc': 'abc', 123: 123, ('1', 1): ('1', 1)} must support the corresponding string, integer, and tuple subscripts and return values of the correct types.
  • Ordinary percent-style (%) string formatting continues to follow Python behavior where the sandbox permits it, including tuple and mapping operands and escaped percent signs. In particular, '%%(foo)s %s' % {'foo': 0} evaluates to "%(foo)s {'foo': 0}".
5. Dynamic * in percent-style formatting is prohibited

Python's dynamic * width and precision feature is not available in Draconic percent-style formatting. If any conversion field obtains its width or precision from *, evaluation must raise FeatureNotAvailable. This includes all of the following forms:

  • '%*f' % (...)
  • '%.*f' % (...)
  • '%*.*f' % (...)

Fixed numeric widths and precisions remain supported, subject to the existing output-size safeguards. Escaped percent signs and otherwise valid mapping/sequence formatting must retain their existing behavior.

6. Existing string-size safeguards remain enforced

The string-type change must not bypass limits derived from DraconicConfig.max_const_len. Existing guarded string operations and formatting forms must continue to raise IterableTooLong when their requested or conservatively estimated result is too large. This includes the existing guarded centering, tab expansion, joining, justification, replacement, translation, zero-fill, f-string, and percent-formatting paths.

For example, a normal request such as 'foo'.center(5) succeeds, while 'foo'.center(...) with an excessively large width raises IterableTooLong. The stripping examples in this specification must complete normally and do not require any new size-limit failure behavior.

Compatibility and Scope

  • Preserve the interpreter's existing attribute-access safety checks and all other sandbox restrictions.
  • Preserve the configured custom string type's interoperability with built-in strings, dictionary hashing and key lookup, indexing, formatting, and existing safe container types.
  • Do not replace a sandbox exception with unrestricted built-in behavior merely as a consequence of inheriting from str.
  • No unrelated language or evaluator behavior should change.

06 Implement structural pattern matching (match/case) support in the Draconic interpreter, plus a supporting helper function. 956 words · source specification

Implement structural pattern matching (match/case) support in the Draconic interpreter, plus a supporting helper function.

Part 1: zip_star helper

Create a function zip_star in the module draconic.helpers.

Signature:

def zip_star(names, values, star_index):

Behavior:

zip_star pairs each element of names (a sequence of length N) with a corresponding portion of values (a sequence). Exactly one of the names positions — the one at index star_index — is treated as a "star" element that absorbs a list of zero or more values; all other positions absorb exactly one value each.

The function returns an iterable of (name, value) tuples, one per name, in order. The rule for splitting values:

  • Positions before star_index (there are star_index of them) each pair with a single successive value taken from the front of values.
  • Positions after star_index (there are N - star_index - 1 of them) each pair with a single successive value taken from the back of values.
  • The star position pairs with a list containing all remaining middle values (which may be empty).

The number of values is always at least N - 1 (the number of non-star positions). The star element receives len(values) - (N - 1) values as a list.

Examples:

list(zip_star(['a','b','c'], [1,2,3,4], star_index=0)) == [('a', [1,2]), ('b', 3), ('c', 4)]
list(zip_star(['a','b','c'], [1,2],     star_index=0)) == [('a', []),    ('b', 1), ('c', 2)]
list(zip_star(['a','b','c'], [1,2,3,4], star_index=1)) == [('a', 1), ('b', [2,3]), ('c', 4)]
list(zip_star(['a','b','c'], [1,2],     star_index=1)) == [('a', 1), ('b', []),    ('c', 2)]
list(zip_star(['a','b','c'], [1,2,3,4], star_index=2)) == [('a', 1), ('b', 2), ('c', [3,4])]
list(zip_star(['a','b','c'], [1,2],     star_index=2)) == [('a', 1), ('b', 2), ('c', [])]
list(zip_star(['a'],         [1,2,3],   star_index=0)) == [('a', [1,2,3])]

The return value must support being wrapped by list(...).

Part 2: match / case statement support in the interpreter

Add support for Python's match statement to the Draconic interpreter. Draconic code is executed via the interpreter's execution entry point; the interpreter tracks emitted print(...) output and supports return.

The following imports must remain valid:

from draconic import DraconicValueError
General match semantics

A match statement evaluates a subject expression, then tests it against each case pattern in order. The first matching case's body is executed and no further cases are tried. If a case has a guard (if <expr>), the case matches only when its pattern matches and its guard evaluates truthy.

Name bindings produced by a matching pattern must leak into the enclosing scope — after the match statement, any names bound by the winning case remain accessible.

Binding must occur before guard evaluation: when evaluating a guard, the names captured by that case's pattern are already bound and usable within the guard expression.

Supported patterns

The following pattern forms must be supported:

  • Capture pattern — a bare name (e.g. case x:). Matches any subject and binds the subject to that name. (An irrefutable catch-all.)

  • Wildcard — _. Matches anything and binds nothing.

  • Value/literal patterns — literals such as integers (e.g. case [1, 2, x]:). A literal in a pattern matches only when the corresponding subject element is equal to that literal.

  • Sequence patterns — [p0, p1, ...]. Matches a sequence subject when the element count is compatible and every sub-pattern matches the corresponding element.

    • Sequence patterns may contain at most one star element (*name or *_), which captures a list of the remaining elements (possibly empty). The star may appear at the start, middle, or end. Non-star sub-patterns before/after the star bind to the corresponding fixed positions; the star name (when not _) binds to a list of the leftover middle elements. Splitting of the subject sequence to sub-patterns follows the same rule as zip_star.
    • A fixed-length sequence pattern (no star) matches only a subject of exactly that length.

  • As patterns — case <pattern> as <name>:. The inner pattern is matched; if it matches, name is additionally bound to the whole subject value matched at that position. as patterns may be nested (e.g. ((b as c) as d) as e), each level producing its own additional binding to the same underlying value.

Multiple-assignment error

A single case pattern may not bind the same name more than once. If a pattern attempts to bind one name in two or more places (including bindings nested within sub-patterns and within recursive sub-sequences), execution must raise DraconicValueError whose message contains the substring multiple assignment.

Examples of required behavior

Given a = [1, 2, 3]:

match a:
    case [1, 2, x]:
        print(x)     # matches, x == 3
    case x:
        print(x)
print(x)             # x == 3 leaks out
# output: 3, 3

match a:
    case [x, *_]:
        print(x)     # x == 1
    case x:
        print(x)
print(x)
# output: 1, 1

match a:
    case [x, 1, 1]:  # does not match (2 != 1)
        print(x)
    case x:
        print(x)     # x == [1,2,3]
print(x)
# output: [1,2,3], [1,2,3]

match a:
    case [x, 2, 3] if x == 2:   # pattern matches (x bound to 1) but guard false
        print(x)
    case y:
        print(y)                # y == [1,2,3]
print(x)                        # x == 1 (bound by first case before its guard failed)
# output: [1,2,3], 1

a = [1, 2, 3]
match a:
    case [x as y, 2, 3]:        # x and y both bound to 1
        pass
print(x)    # 1
print(y)    # 1

match a:
    case [((b as c) as d) as e, 2, 3]:
        pass
return b, c, d, e   # (1, 1, 1, 1)

Given a = [1, 2, 3], the pattern case [x, x, x]: must raise DraconicValueError (message contains multiple assignment).

Given a = [1, [2]], the pattern case [x, [x]]: must likewise raise DraconicValueError (message contains multiple assignment).

  • An ordinary scalar with no iterable content contributes no content units, so its emitted-result cost is the one per-result unit.

A direct dict-comprehension entry is accounted specially as:

1 + approximate_size(key) + approximate_size(value)

The key/value pair is not charged the cardinality of an additional tuple, because a dict comprehension emits an entry directly. By contrast, a generator expression such as ((key, value) for ...) emits actual two-item tuples. Each such tuple therefore contributes its cardinality and its recursively contained sizes, in addition to the one per-result unit.

Accounting is based on emitted results, rather than only on the final cardinality of the destination container. The cumulative total may equal max_const_len; it must raise IterableTooLong when the next emitted value would make the total greater than max_const_len.

Incremental enforcement

The budget must be checked incrementally as values are emitted. For a lazy generator expression, checking occurs as its consumer requests values. The value that would exceed the budget must not be delivered to the consumer, and construction must stop with IterableTooLong. This prevents a generator or comprehension from bypassing the limit regardless of which supported constructor or callable consumes it. Existing contextual exception propagation remains intact; if an interpreter call wraps nested errors, the underlying limit error must be IterableTooLong.

Required boundaries

With DraconicConfig(max_const_len=1_000) and range registered in interpreter.builtins:

List comprehension

Each formatted value in the following expressions is a three-character string and therefore costs 1 + 3 = 4 units.

interpreter.eval("[f'{x:03}' for x in range(250)]")  # succeeds: 250 * 4 = 1,000
interpreter.eval("[f'{x:03}' for x in range(251)]")  # raises IterableTooLong: 251 * 4 = 1,004
Dict comprehension

Each three-character key and one-character value costs 1 + 3 + 1 = 5 units per emitted entry.

interpreter.eval("{f'{i:03}': 'a' for i in range(200)}")  # succeeds: 200 * 5 = 1,000
interpreter.eval("{f'{i:03}': 'a' for i in range(201)}")  # raises IterableTooLong: 201 * 5 = 1,005
Generator expression consumed by dict

Here each generator result is a two-item tuple containing a three-character string and a one-character string. Its approximate content size is 2 + 3 + 1 = 6, so its total emitted-result cost is seven units.

interpreter.eval("dict((f'{i:03}', 'a') for i in range(200, 342))")  # succeeds: 142 * 7 = 994
interpreter.eval("dict((f'{i:03}', 'a') for i in range(200, 343))")  # raises IterableTooLong: 143 * 7 = 1,001

Task Specification: Implement Starred/Unpacking Support in the Draconic Interpreter

Overview

The Draconic interpreter (a sandboxed Python-subset expression evaluator) must support Python's starred unpacking in two contexts:

  1. Starred assignment targets — capturing "the rest" of an iterable into a list during compound (tuple/list) assignment.
  2. Unpacking within literals — * unpacking inside list/set displays and ** unpacking inside dict displays.

All unpacking operations must respect the interpreter's existing iterable length limits.

The interpreter is invoked in tests via a callable e(source_string) that evaluates or executes a snippet and returns the resulting value; state (assigned names) persists across successive calls. Your implementation must make the behaviors below work when driven through the interpreter's normal parse/evaluate path.

Relevant Exceptions

The interpreter exposes these exception types (already present in the codebase); reuse them:

  • DraconicValueError — raised for runtime value/unpacking mismatches.
  • DraconicSyntaxError — raised for syntactically invalid constructs.
  • IterableTooLong — raised when an operation would produce/consume an iterable exceeding the configured length limit.

Required Behavior

1. Starred assignment targets

Support a single starred target in compound assignment. The right-hand side is unpacked positionally; the starred target absorbs all remaining elements as a list.

Given the RHS iterable, elements are assigned to the non-starred targets before and after the star, and the star target receives the middle segment as a list:

  • a, *b = (1, 2, 3, 4) → a == 1, b == [2, 3, 4]
  • a, *b, c = (1, "foo", "bar", "baz", 5) → a == 1, b == ["foo", "bar", "baz"], c == 5
  • a, *b = [i + 1 for i in range(4)] → a == 1, b == [2, 3, 4]

The star target's captured value is always a list (even when empty or when the RHS is another iterable type).

Error conditions:

  • If the RHS does not contain enough elements to satisfy the non-starred targets, raise DraconicValueError.
    • e.g. a, *b = tuple() → DraconicValueError (empty RHS cannot fill the required target a).
  • If more than one starred target appears in a single assignment target list, raise DraconicSyntaxError.
    • e.g. a, *b, *c, = (1, 2, 3) → DraconicSyntaxError.

(The existing rule that non-starred compound assignment with mismatched counts raises DraconicValueError, e.g. a, b = 1, remains unchanged.)

2. Unpacking in list and set displays (*)

Support *expr inside list and set literals, splicing the elements of expr into the resulting collection in order.

  • a = [1, 2, 3], b = [4, 5, 6]
    • [*a, *b] → [1, 2, 3, 4, 5, 6]
    • [*a, *a, *b, *b] → [1, 2, 3, 1, 2, 3, 4, 5, 6, 4, 5, 6]
  • Starred unpacking may be freely mixed with plain elements, e.g. [1, *a] produces a list with 1 followed by the elements of a; {*a, 1000} produces the set of a's elements together with 1000.

Set displays with unpacking produce a set with the usual set semantics (deduplication).

3. Unpacking in dict displays (**)

Support **expr inside dict literals, merging the key/value pairs of expr into the resulting dict. Later entries override earlier ones by key (standard Python merge semantics).

  • a = {"a": 1, "b": 2}, b = {"c": 3, "d": 4}
    • {**a, **b} → {"a": 1, "b": 2, "c": 3, "d": 4}
    • {**a, **a, **b, **b} → {"a": 1, "b": 2, "c": 3, "d": 4}
4. Length-limit enforcement

Every unpacking operation must enforce the interpreter's configured maximum iterable length. If the cumulative result of an unpacking/splice would exceed the limit, raise IterableTooLong. This applies as the collection is being built (i.e. the running total across all spliced/plain elements is bounded).

Assume long and longer are iterables at/over the limit, and long2 is another such iterable:

  • [1, *long] → IterableTooLong
  • [*long, *long] → IterableTooLong
  • {*long, 1000} → IterableTooLong
  • {*longer} → IterableTooLong
  • {**long, **long2} → IterableTooLong

Note: unpacking of oversized iterables into displays must no longer be rejected as an unsupported feature; it must be accepted and instead bounded by the length limit as described above. (Multiple */** unpackings in a single display are permitted.)

Constraints

  • Starred targets in assignment always yield a Python list.
  • List/set/dict displays produce the interpreter's normal (safe) collection types, consistent with non-unpacked displays.
  • Do not enforce length limits on function-call argument unpacking or other contexts not described here.

Fix Iterable Length-Limit Enforcement During Unpacking

Background

Draconic limits the amount of data materialized while evaluating list, set, and dictionary literals. Let LIMIT denote the configured DraconicConfig.max_const_len value. If constructing one of these literals exceeds its permitted cumulative size, evaluation must raise IterableTooLong.

The unpacking paths must maintain one correct running total across all ordinary and unpacked portions of a literal. The boundary is inclusive: a total equal to LIMIT is valid, while a total strictly greater than LIMIT is invalid. The total must not be reset for each successive * or ** operand.

List Literals with * Unpacking
  • A list literal may unpack an iterable whose contribution is exactly LIMIT. For example, if long contains exactly LIMIT simple scalar elements, [*long] must succeed and return the corresponding list.
  • Contributions from every part of the same list literal are cumulative. Thus [1, *long] must raise IterableTooLong when long already consumes the full limit.
  • [*long, *long] must raise IterableTooLong when each long consumes LIMIT, because the literal attempts to materialize a total of 2 * LIMIT.
  • Ordinary list-unpacking semantics and the resulting list contents must otherwise remain unchanged.
Set Literals with * Unpacking
  • A set literal may unpack an iterable whose contribution is exactly LIMIT. For example, {*long} must succeed when long contains LIMIT permitted elements and must produce the resulting set.
  • {*longer} must raise IterableTooLong when the unpacked iterable's contribution is greater than LIMIT.
  • Contributions from additional literal elements or additional unpacked iterables are cumulative; exceeding the limit anywhere in the construction must raise IterableTooLong.
  • Ordinary set construction and unpacking behavior must otherwise remain unchanged.
Dictionary Literals with ** Unpacking

Dictionary-literal limits are based on a weighted size budget, not merely on mapping cardinality. For each key/value entry emitted while building the literal, the contribution is:

1 + approximate_size(key) + approximate_size(value)

The approximate_size is the evaluator's existing approximate-length measure used for container limits. In particular, a string's approximate size is its number of characters. The key and value must be measured separately: the temporary key/value pair itself contributes no tuple length or other container overhead. This task does not change the existing approximate-size rules for individual objects.

The entry costs are accumulated across all entries and all ** operands in the dictionary literal, as well as any ordinary entries in the same construction. Therefore:

  • A single unpacked mapping whose weighted cost is exactly LIMIT must be accepted, and {**long} must return the resulting dictionary.
  • Multiple unpacked mappings whose combined weighted cost is greater than LIMIT must raise IterableTooLong.
  • With LIMIT = 1000, a mapping containing 200 entries whose keys are three-character strings and whose values are one-character strings costs 200 * (1 + 3 + 1) = 1000; unpacking that mapping alone must succeed.
  • Combining that mapping with another 142 disjoint entries of the same key and value sizes costs 1710, so {**long, **long2} must raise IterableTooLong.

Here, a mapping being “at the limit” refers to this weighted cumulative cost, not to the raw number of entries in the mapping.

Function Calls with * Argument Unpacking

The max_const_len container-construction limit must not be applied to positional argument unpacking in function calls. In particular, after exposing max through the interpreter's builtins, max(*long, *long) must be allowed to unpack both iterables and invoke the function normally even when their combined argument count or size is greater than LIMIT.

This exemption is limited to the iterable-length check described here. Normal call semantics, validation that the value after * is iterable, callable argument validation, and unrelated execution safeguards remain in effect.

Compatibility and Public API
  • Preserve the existing evaluator and interpreter APIs, including the interpreter's mutable builtins mapping.
  • Preserve DraconicConfig.max_const_len as the controlling configuration value.
  • Preserve IterableTooLong as the exception raised when literal construction is strictly over the permitted limit.
  • Do not alter ordinary literal results, unpacking order, mapping overwrite behavior, configuration defaults, or unrelated limits.
  • No new public API is required; this change is solely a correction to cumulative length accounting and to where that accounting applies.
