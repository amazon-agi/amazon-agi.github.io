01 The dependency-extraction functionality is to be extended so that Python binary operations and unary operations are supported. 607 words · source specification, reworded by GLM-5.3-Flash

Overview

The dependency-extraction functionality is to be extended so that Python binary operations and unary operations are supported. The system takes a parsed Python expression (an AST node), analyzes it, and returns the list of free variable names the expression depends on.

Public API

An already-existing function must handle the additional node types described below:

get_dependencies(node) -> list[str]
  • Input: A Python AST node representing an expression (obtained by parsing a single expression, e.g. via ast.parse(source, mode="eval") and taking the resulting body).
  • Output: A list of the variable name strings that the expression depends on, in the order they appear from left to right.

Required Behavior

Binary operations

When an expression consists of two operands joined by a binary operator (for example a + b), the returned dependency list must contain the names referenced by the left operand and then the names referenced by the right operand, in that order.

  • Example: a + b → ["a", "b"]
Unary operations

When an expression consists of a single operand with a unary operator in front of it (for example -x), the returned dependency list must contain the names referenced by the operand.

  • Example: -plus → ["plus"] (the operand name plus is a variable reference; the - at the front is the unary operator, not part of the name)

Notes

  • The names that appear as variable references inside these operations must be collected as dependencies.
  • The relative order of names must match their left-to-right position in the source expression.

Additional Requirements

  • Dependency analysis must also cover function and lambda bodies, including the lexical bindings that parameters, assignments, and imports introduce.
  • Assignment targets produce bindings rather than dependencies. For example, x = y binds x and contributes ["y"] as dependencies.
  • When extracting bindings from assignment targets, the recursion must go through tuple, list, and starred unpacking in source order. Thus (a, *b) = value binds a and b. The base identifier of attribute and subscript targets is not bound as a new local name.
  • Imports bring in the names that Python places in the local namespace, and module-path components are not treated as free variable references:
    • import package binds package.
    • import package.module binds package.
    • import package.module as alias binds alias.
    • from package import item binds item.
    • from package import item as alias binds alias.
    • When multiple names are imported, they are recognized in source order.
  • Function and lambda parameters, including positional-only, positional, keyword-only, variadic positional, and variadic keyword parameters, are bindings local to that function body and must not be returned as free dependencies from the body.
  • If a name is assigned or imported anywhere in a function, that name is local throughout the function’s body, in line with Python’s lexical scoping rules. A reference to that name is excluded from the function’s free dependencies even when the reference appears textually before the assignment or import.
  • Assignment right-hand sides remain subject to dependency analysis. For example, a function that contains local = external and then uses local depends on external, not on local.
  • Names from enclosing scopes are shadowed by imported aliases and other local bindings. For example, a function that contains import package as p and returns p.value + other has ["other"] as its free dependencies.
  • Shadowing applies only within the scope that introduces the binding. The names used in decorators, default argument expressions, and annotations evaluated outside the function body are analyzed in the enclosing scope and are not hidden by the function’s parameters or local assignments.

Task: Implement a Function That Splits a File

Goal

Introduce a function that reads Python source code from a file-like object and divides it into its top-level statements, returning for each statement both the source text and the parsed AST node.

Public API

Define a function called split in the module ssort._parsing:

def split(file, filename):
    ...
Parameters
  • file: a text file-like object (e.g. an io.StringIO) that supports reading of the full source contents.
  • filename: a string serving as the filename for parsing purposes (e.g. "<unknown>").
Return value

An iterable of pairs. Each pair maps to one top-level statement in the source, in source order, and is unpackable as (text, node) where:

  • text is a str holding the source text of that one statement (see the rules below).
  • node is the AST node obtained by parsing that statement.

The tests only examine the text element of each pair; the node element must be present and unpackable, but its exact contents are not otherwise constrained.

Rules for Extracting Text

For each top-level statement, the text string must be produced in accordance with the rules below, all of which are checked:

  1. Single statement: The text of a single statement is exactly its source, with neither surrounding whitespace added nor a trailing newline.

    • "a = 4" → ["a = 4"]

  2. A trailing newline is stripped: A single trailing newline at the end of the file must not be present in the statement text.

    • "a = 4\n" → ["a = 4"]

  3. Leading blank lines are retained: Blank lines that occur before the first statement are kept as part of that statement's text.

    • "\n\na = 4" → ["\n\na = 4"]

  4. Multiple statements on separate lines: Each statement separated by newlines becomes its own entry, and the newline separators between them are excluded from the text.

    • "a = 4\nb = 2" → ["a = 4", "b = 2"]

  5. Multiple statements on the same line (semicolon-separated): Statements separated by ; on one line are divided into separate entries. The semicolon and any surrounding whitespace are left out of the statement texts.

    • "a = 4; b = 2" → ["a = 4", "b = 2"]
    • "a = 4 ;b = 2" → ["a = 4", "b = 2"]

  6. Trailing (inline) comments: A comment that follows a statement on the same line remains part of that statement's text (the whitespace before the comment included).

    • "a = 4 # Assign a\nb = 2 # Assign b" → ["a = 4 # Assign a", "b = 2 # Assign b"]

  7. Leading comments: A comment that sits on its own line immediately before a statement is attached to (included as part of) that following statement's text.

    • "# Assign a\na = 4\n# Assign b\nb = 2" → ["# Assign a\na = 4", "# Assign b\nb = 2"]

  8. Leading and trailing comments combined: Both a preceding comment line and a trailing comment on the same line are included in a statement's text.

    • Input:
      # Before a
a = 4  # After a
# Before b
b = 2  # After b
    • Result:
      ["# Before a\na = 4  # After a", "# Before b\nb = 2  # After b"]

Notes

  • Returned statements always appear in the order in which they occur in the source.
  • Whitespace inside a statement's own text (such as the spaces before a trailing comment) is preserved exactly; only the separators between statements (newlines, semicolons and their adjacent whitespace) and a single trailing file newline are excluded.

Task Specification: Source Splitting Function

Overview

Implement a source splitter that reads a Python module and yields, in source order, each of its top-level statements. Each result must pair the statement's original source text with the corresponding parsed AST node.

Only direct module-level statements become separate results. Statements nested inside a function, class, conditional, or other compound statement remain part of their enclosing statement's text; they are not yielded separately.

Public API

The established import location must stay available:

from ssort._parsing import split

The interface of the callable is:

split(file, filename)

A package-root export does not serve as a substitute for the ssort._parsing.split import path.

Parameters
  • file: a readable text file-like object; its source contents are obtained by reading the stream to completion. Callers may use io.StringIO for in-memory source. The first argument is not a plain source string.
  • filename: a string passed along for parsing purposes, including parser diagnostics such as SyntaxError metadata.

For instance:

import io

from ssort._parsing import split

results = split(io.StringIO("a = 4"), "<unknown>")

Return Value

The function must return an iterable containing one pair for each top-level statement. The results must be in the same order as the statements in the input.

Each pair consists of:

  1. text: the statement's source text, as a string.
  2. node: the corresponding module-level Python AST statement node.

The pairs must support tuple unpacking:

for text, node in split(file, filename):
    ...

The AST nodes must correspond to parsing the supplied module source, with their source-location information referring to that original input.

Required Behavior

Empty input

No results are yielded for an empty source stream. More generally, content that produces no module-level AST statements does not itself create a result.

Simple statements

Exactly one pair is yielded for a single simple statement. Its text holds the statement with no unowned trailing line ending.

For the source "a = 4", the returned text is "a = 4". The source "a = 4\n" likewise returns "a = 4".

Multiple top-level statements

Yield one result for each top-level statement, in source order. For instance, "a = 4\nb = 2" produces these texts:

["a = 4", "b = 2"]
Leading blank lines and other leading source

Blank lines occurring before the first top-level statement are part of that statement's returned text and must be preserved verbatim. Do not carry out a blanket leading-whitespace trim. For instance, "\n\na = 4" produces the single text:

"\n\na = 4"

Likewise, leading comment lines that immediately precede a statement belong to that statement. Blank lines and leading comments that fall between two statements are associated with the following statement rather than being emitted independently.

Comments

Comments associated with a statement must be preserved:

  • Comment lines leading into a statement are included at the start of its text.
  • An inline comment that appears on the same line as a statement is included at the end of its text.
  • Comments do not create AST statement results on their own.

For instance:

# Before a
a = 4  # After a
# Before b
b = 2  # After b

gives:

[
    "# Before a\na = 4  # After a",
    "# Before b\nb = 2  # After b",
]
Semicolon-separated statements

Top-level simple statements that are separate and share the same physical line must be yielded separately. Neither result includes the separating semicolon or the whitespace used only around that separator.

Both of the following inputs:

a = 4; b = 2
a = 4 ;b = 2

produce these texts:

["a = 4", "b = 2"]

If the final same-line statement has an inline comment, that comment stays attached to the final statement.

Multiline and compound statements

A statement that spans multiple physical lines must be returned as one complete source block, extending through the final line of that statement. All indented suites belonging to a compound statement are included. Nested statements within such a suite must not become separate top-level results.

For a decorated function definition, the single result must include every decorator line, the complete function signature, and the entire function body, with their source formatting preserved. Given:

@something(2, kwarg=3)
def decorated(arg, *args, kwarg, **kwargs):
    pass

the splitter yields exactly one text value:

@something(2, kwarg=3)
def decorated(arg, *args, kwarg, **kwargs):
    pass

Its paired node is the corresponding function-definition AST node. Any other multiline top-level statement falls under this same completeness rule.

Preserving source and boundaries

The returned text must be sliced from the original source rather than being regenerated. Source spelling, indentation, internal line breaks, decorator formatting, and comment spacing must be preserved exactly. Separator characters and boundary whitespace that do not belong to a statement must be excluded, such as same-line semicolon separators and a trailing line ending after the statement. Leading blank lines and comments that are assigned to a statement under the rules above are part of its text and must not be stripped.

Errors from parsing

The source is parsed as Python, with the supplied filename. The parser's normal SyntaxError may be raised for invalid Python, and that parsing context must reflect the supplied filename.

05 Extracting Dependencies from Class Definitions 531 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Extracting Dependencies from Class Definitions

Goal

Implement dependency extraction for the AST nodes of Python class definitions. Starting from a parsed AST node that represents a class definition, the implementation produces the ordered list of external name dependencies referenced by that class.

Public API

It must be possible to import the following from the dependencies module (this being the same module that currently provides get_dependencies):

get_dependencies(node)
  • Input: an AST node (of the kind produced when Python source is parsed with the standard ast module).
  • Output: an iterable of dependency objects. Each dependency object exposes a .name attribute (a str) holding the referenced name.

Behavior Required for Class Definitions

When get_dependencies is called with a class definition node, it must return the class's external name dependencies in source order, taking the following contributions into account:

  1. Class decorators — every name referenced in each decorator expression on the class, including the decorator callable and any arguments passed to it.
  2. Base classes — the name of each base class.
  3. Class body — names referenced within the class body that the class itself does not define.
Names defined inside the class are NOT dependencies

Names that get assigned within the class body (e.g. class-level attribute assignments) become part of the class's own namespace. As a consequence:

  • The targets of the assignments are themselves not dependencies.
  • If a name defined locally in this way is later referenced within the same class body (for example, as an argument to a method decorator), that reference is also not treated as a dependency, because it resolves to the class-level definition.
  • On the other hand, a name that is defined at class level but referenced inside a method body IS a dependency of the class (at definition time, method bodies do not resolve names against the namespace of the enclosing class).
Example walkthrough

Given the following class definition:

@decorator(arg)
class A(B, C):
    _a = something
    _b = something

    @method_decorator(_a)
    def method():
        return _b

For this class definition, get_dependencies must yield dependencies whose .name values are, in order:

["decorator", "arg", "B", "C", "something", "something", "method_decorator", "_b"]

Why each of them appears (and why the others do not):

  • decorator, arg — these come from the class decorator expression @decorator(arg).
  • B, C — the names of the base classes.
  • something, something — the right-hand sides of the two class-level attribute assignments (_a and _b). Each occurrence is emitted; the targets of those assignments, _a and _b, are not dependencies.
  • method_decorator — the decorator that is applied to method.
  • _b — referenced inside the method body; because _b is defined at class level but used within a nested method body, it is a dependency.
  • _a is not present: even though it is referenced (as @method_decorator(_a)), it is defined earlier in the same class body and therefore resolves locally.

Notes

  • The dependencies that get returned must come in an order matching the left-to-right, top-to-bottom source order illustrated above (decorators, then bases, then body).
  • The behavior described here is the only behavior that is required.
06 You must implement support for dependency analysis of global and nonlocal variable declarations within Python function definitions. 592 words · source specification, reworded by GLM-5.3-Flash
Overview

You must implement support for dependency analysis of global and nonlocal variable declarations within Python function definitions. The analysis works by inspecting a parsed Python AST node and figuring out which names the code depends on from an enclosing/outer scope.

Public API

The items below must be importable and callable:

  • get_dependencies(node) — accepts a Python AST node (as produced by parsing a function definition) and returns an iterable of dependency objects. Every dependency object must expose a .name attribute (a str); this attribute gives the name of the depended-upon symbol.

The returned dependencies must be ordered so that their order matches the order in which the corresponding names are first encountered in the source.

Behavior Requirements

Ordinary name resolution (parameters, local assignments, decorators, etc.) is already covered by the analysis. What you are adding is handling for global and nonlocal declarations. In every case below, the node passed to get_dependencies is a single top-level function definition.

A name that is assigned inside a function is normally regarded as a local variable and does NOT become a dependency. Whether such an assigned name counts as a dependency is altered by the presence of a global or nonlocal declaration, following the rules below.

Handling of nonlocal declarations

  1. If a function declares a name nonlocal and afterwards assigns to it, and that name is not bound anywhere in the analyzed function's own scope (that is, it must resolve to some enclosing scope outside the analyzed function), then the name is a dependency.

    Example:

    def function():
    nonlocal a
    a = 4

    Dependencies: ["a"]

  2. The same applies when the nonlocal declaration and the assignment take place inside a nested (inner) function, and the declared name is not bound anywhere in the analyzed function's scope tree in a way that would satisfy the nonlocal binding:

    def function():
    def inner():
        nonlocal a
        a = 4
    return inner

    Dependencies: ["a"]

  3. When the nonlocal name is bound in an enclosing scope within the analyzed function (for instance, assigned in the body of the analyzed function itself), the nonlocal reference is satisfied internally, and therefore the name is not a dependency:

    def function():
    def inner():
        nonlocal a
        a = 4
    a = 2
    return inner

    Dependencies: []

Handling of global declarations

  1. If a function declares a name global and then assigns to it, that name is a dependency:

    def function():
    global a
    a = 4

    Dependencies: ["a"]

  2. The same applies when the global declaration and the assignment take place inside a nested (inner) function:

    def function():
    def inner():
        global a
        a = 4
    return inner

    Dependencies: ["a"]

  3. In contrast to nonlocal, a global name remains a dependency even when a name with the same identifier is also assigned as a local in an enclosing scope within the analyzed function. The local assignment neither satisfies nor cancels the global dependency:

    def function():
    def inner():
        global a
        a = 4
    a = 2
    return inner

    Dependencies: ["a"]

Summary of the difference
  • nonlocal name: adds name as a dependency only if name is not bound anywhere in the analyzed function's own scope tree; when it is bound in an intervening enclosing scope inside the analyzed function, it is resolved internally and is not a dependency.
  • global name: always contributes name as a dependency when it is assigned under a global declaration, regardless of any same-named local assignments in enclosing scopes within the analyzed function.

08 Extend two existing static-analysis functions with support for Python try/except/else/finally statements 499 words · source specification, reworded by GLM-5.3-Flash

Task Description

Summary

Extend two existing static-analysis functions with support for Python try/except/else/finally statements: one that extracts the names bound (assigned/introduced) by a piece of code, and one that extracts the names that a piece of code depends on (references from the surrounding scope).

Both functions work on Python AST nodes (which the standard ast module produces) and must recursively process ast.Try nodes and all of their child statements.

Public API

The callables listed below must be importable and callable as described. (For other node types, their existing behavior must remain intact; this task only adds handling for try statements.)

get_bindings(node)
  • Input: an AST node (e.g. the module node that parsing a code snippet returns).
  • Output: an iterable of strings — the names bound within node, yielded in source order (the order of appearance when the code is read top to bottom, left to right).
get_dependencies(node)
  • Input: an AST node.
  • Output: an iterable of dependency objects, in source order. Each object exposes a .name attribute (a string) that gives the referenced name.

Behavior Required for try Statements

An ast.Try node has four parts, and these must be processed in this order:

  1. body — the statements that make up the try: block.
  2. handlers — the except clauses. Each handler may optionally bind a name (the as <name> target). If that bound name is present, it is a binding.
  3. orelse — the statements that make up the else: block.
  4. finalbody — the statements that make up the finally: block.
Bindings

When bindings are collected from a try statement, yield, in order:

  • All bindings generated inside the try body.
  • For each except clause: the name that its as <name> clause introduces (if any), followed by the bindings generated inside that handler's body.
  • All bindings generated inside the else block.
  • All bindings generated inside the finally block.

As a concrete example, for a construct of the form:

try:
    a = something_stupid()
except Exception as exc:
    b = recover()
else:
    c = otherwise()
finally:
    d = finish()

the resulting bindings, in order, are: a, exc, b, c, d.

Dependencies

When dependencies are collected from a try statement, yield, in order, the dependencies of:

  • The body of the try.
  • Each except clause: the type expression that is being caught (e.g. Exception) is a dependency, together with any dependencies in the handler body. The as <name> target is a binding, not a dependency, and it must not appear.
  • The else block.
  • The finally block.

For the same construct as above, the dependency names, in order, are: something_stupid, Exception, recover, otherwise, finish.

Notes

  • Names that are bound locally (such as an assignment target within a block, or an except ... as name) are treated as bindings, not dependencies.
  • Order matters: the results must reflect the top-to-bottom structure of the try statement (body, then handlers, then else, then finally).

Part 1: The ssort function

Public API

Expose a callable that can be imported as:

from ssort import ssort

The signature is:

def ssort(source: str) -> str: ...
Behavior

ssort accepts a string of Python source code and returns a string of Python source code in which the top-level statements have been rearranged so that, wherever possible, a statement defining a name is positioned before the statements that depend on (reference) that name.

Detailed requirements:

  • Empty input. When the input is the empty string "", the function returns "\n".

  • Trailing newline normalization. The returned string always finishes with exactly one trailing newline character.

    • The input "a = 1", which has no trailing newline, returns "a = 1\n".
    • The input "b = 2\n", which already ends with a trailing newline, returns "b = 2\n".

  • Dependency ordering. Every top-level statement is emitted after the top-level statements that define the names it references, whenever such an ordering is possible. How statements are arranged relative to one another is decided by these dependency relationships together with a deterministic tie-breaking order (see below).

  • Cycles are preserved. If a set of statements depend on one another mutually (directly or transitively), forming a dependency cycle, those statements must be kept and emitted; the cycle must not make the function fail. Inside a cycle, the statements keep their original relative order. Concretely:

    • Given this input:
      a = b
b = c
c = a
      the function returns the same text, unchanged:
      a = b
b = c
c = a
    • Given this input:
      a = c
b = a
c = b
      the function returns the same text, unchanged:
      a = c
b = a
c = b

  • Statements depending on a cycle. A statement that depends on names produced inside a cycle must be ordered after the members of the cycle that it depends on, while the members of the cycle keep their original relative order among themselves. Concretely:

    • Given this input:
      c = a
a = b
b = a
      the function returns:
      a = b
c = a
b = a
      In this example, a = b and b = a make up a cycle and keep their original relative order (a = b before b = a); because c = a depends on a, it is placed after the point at which a becomes available.

  • Determinism. Given a particular input, the output is fully deterministic (a fixed, repeatable ordering), including the way independent statements and cycle members are arranged.

Notes on assignment statements

For a simple assignment such as x = y, the statement defines the name(s) on the left-hand side (x) and depends on the name(s) referenced on the right-hand side (y). It is this relationship that drives the ordering.

Part 2: Dependency extraction for subscripts and slices

The package computes the ordered list of names that a given Python AST expression node depends on (references). You must make sure this is correct for subscription and slice expressions.

Behavior

Applied to an AST expression node, dependency extraction yields the referenced names in source order (left to right as they appear in the expression). For subscript and slice expressions in particular:

  • A simple subscription array[key] depends on array, followed by key → ["array", "key"].

  • A slice subscription array[start:end] depends on array, followed by start and then end → ["array", "start", "end"].

  • A slice that specifies only an upper bound, array[:end], depends on array, followed by end → ["array", "end"].

  • A slice that specifies only a lower bound, array[start:], depends on array, followed by start → ["array", "start"].

  • For an empty slice array[:], the only dependency is array → ["array"].

In every case, the object being subscripted contributes its dependencies first, and the dependencies appearing inside the subscript brackets follow in left-to-right order. Slice components that are missing (an absent lower/upper bound) contribute no names.

This dependency extraction must be integrated so that it is exercised through the same mechanism the package applies to other expression types (the module that maps AST nodes to their dependency names). Ensure that dependency computation handles the full range of expression node types without error (expression constructs that do not bear names simply contribute no additional names).
