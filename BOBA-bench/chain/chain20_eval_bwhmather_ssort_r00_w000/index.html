01 Extend the dependency-extraction functionality to support Python binary operations and unary operations. 571 words · source specification

Overview

Extend the dependency-extraction functionality to support Python binary operations and unary operations. The system analyzes a parsed Python expression (an AST node) and returns the list of free variable names the expression depends on.

Public API

There is an existing function that must handle the additional node types described below:

get_dependencies(node) -> list[str]
  • Input: A Python AST node representing an expression (as produced by parsing a single expression, e.g. via ast.parse(source, mode="eval") and taking the body).
  • Output: A list of variable name strings that the expression depends on, in left-to-right order of appearance.

Required Behavior

Binary operations

For an expression consisting of two operands combined by a binary operator (for example a + b), the returned dependency list must contain the names referenced by the left operand followed by the names referenced by the right operand, in that order.

  • Example: a + b → ["a", "b"]
Unary operations

For an expression consisting of a single operand preceded by a unary operator (for example -x), the returned dependency list must contain the names referenced by the operand.

  • Example: -plus → ["plus"] (the operand name plus is a variable reference; the leading - is the unary operator, not part of the name)

Notes

  • Names appearing as variable references within these operations must be collected as dependencies.
  • The relative ordering of names must follow their left-to-right position in the source expression.

Additional Requirements

  • Dependency analysis must also handle function and lambda bodies, including the lexical bindings introduced by parameters, assignments, and imports.
  • Assignment targets introduce bindings rather than dependencies. For example, x = y binds x and contributes ["y"] as dependencies.
  • Binding extraction from assignment targets must recurse through tuple, list, and starred unpacking in source order. Thus (a, *b) = value binds a and b. Attribute and subscript targets do not bind the base identifier as a new local name.
  • Imports introduce the names that Python places in the local namespace and do not treat module-path components as free variable references:
    • import package binds package.
    • import package.module binds package.
    • import package.module as alias binds alias.
    • from package import item binds item.
    • from package import item as alias binds alias.
    • Multiple imported names are recognized in source order.
  • Function and lambda parameters, including positional-only, positional, keyword-only, variadic positional, and variadic keyword parameters, are bindings local to that function body and must not be returned as free dependencies from the body.
  • A name assigned or imported anywhere in a function is local throughout that function’s body, matching Python’s lexical scoping rules. References to that name are excluded from the function’s free dependencies even when the reference appears textually before the assignment or import.
  • Assignment right-hand sides remain subject to dependency analysis. For example, a function containing local = external and then using local depends on external, not on local.
  • Imported aliases and other local bindings shadow names from enclosing scopes. For example, a function containing import package as p and returning p.value + other has ["other"] as its free dependencies.
  • Shadowing is limited to the scope that introduces the binding. Names used in decorators, default argument expressions, and annotations evaluated outside the function body are analyzed in the enclosing scope and are not hidden by the function’s parameters or local assignments.

Task: Implement a File-Splitting Function

Objective

Add a function that reads Python source code from a file-like object and splits it into its top-level statements, returning both the source text and the parsed AST node for each statement.

Public API

Create a function named split in the module ssort._parsing:

def split(file, filename):
    ...
Parameters
  • file: a text file-like object (e.g. an io.StringIO) supporting reading of the full source contents.
  • filename: a string used as the filename for parsing purposes (e.g. "<unknown>").
Return value

An iterable of pairs. Each pair corresponds to one top-level statement in the source, in source order, and is unpackable as (text, node) where:

  • text is a str containing the source text of that single statement (see rules below).
  • node is the parsed AST node for that statement.

The tests only inspect the text element of each pair; the node element must be present and unpackable but its exact contents are not otherwise constrained.

Text Extraction Rules

For each top-level statement, the text string must be produced according to the following rules, all of which are verified:

  1. Basic statement: A single statement's text is exactly its source, with no surrounding whitespace added or trailing newline.

    • "a = 4" → ["a = 4"]

  2. Trailing newline is stripped: A single trailing newline at the end of the file must not appear in the statement text.

    • "a = 4\n" → ["a = 4"]

  3. Leading blank lines are preserved: Blank lines that appear before the first statement are retained as part of that statement's text.

    • "\n\na = 4" → ["\n\na = 4"]

  4. Multiple statements on separate lines: Each newline-separated statement becomes its own entry, and the newline separators between them are not included in the text.

    • "a = 4\nb = 2" → ["a = 4", "b = 2"]

  5. Multiple statements on the same line (semicolon-separated): Statements separated by ; on one line are split into separate entries. The semicolon and any surrounding whitespace are not included in the statement texts.

    • "a = 4; b = 2" → ["a = 4", "b = 2"]
    • "a = 4 ;b = 2" → ["a = 4", "b = 2"]

  6. Trailing (inline) comments: A comment following a statement on the same line is kept as part of that statement's text (including the whitespace before the comment).

    • "a = 4 # Assign a\nb = 2 # Assign b" → ["a = 4 # Assign a", "b = 2 # Assign b"]

  7. Leading comments: A comment on its own line immediately preceding a statement is attached to (included as part of) that following statement's text.

    • "# Assign a\na = 4\n# Assign b\nb = 2" → ["# Assign a\na = 4", "# Assign b\nb = 2"]

  8. Leading and trailing comments combined: Both a preceding comment line and a same-line trailing comment are included in a statement's text.

    • Input:
      # Before a
a = 4  # After a
# Before b
b = 2  # After b
    • Result:
      ["# Before a\na = 4  # After a", "# Before b\nb = 2  # After b"]

Notes

  • The order of returned statements always follows the order they appear in the source.
  • Whitespace within a statement's own text (such as the spaces before a trailing comment) is preserved exactly; only separators between statements (newlines, semicolons and their adjacent whitespace) and a single trailing file newline are excluded.

Returned text must be sliced from the original source rather than regenerated. Preserve source spelling, indentation, internal line breaks, decorator formatting, and comment spacing exactly. Leading blank lines and comments assigned to a statement under the rules above are part of its text and must not be stripped.

05 Dependency Extraction for Class Definitions 477 words · source specification

Task Specification: Dependency Extraction for Class Definitions

Objective

Implement dependency extraction for Python class definition AST nodes. Given a parsed AST node representing a class definition, produce the ordered list of external name dependencies referenced by that class.

Public API

The following must be importable from the dependencies module (the same module that currently provides get_dependencies):

get_dependencies(node)
  • Input: an AST node (as produced by parsing Python source with the standard ast module).
  • Output: an iterable of dependency objects. Each dependency object exposes a .name attribute (a str) giving the referenced name.

Required Behavior for Class Definitions

When get_dependencies is called with a class definition node, it must return the class's external name dependencies in source order, considering the following contributions:

  1. Decorators on the class — every name referenced in each class decorator expression, including the decorator callable and any arguments passed to it.
  2. Base classes — each base class name.
  3. Class body — names referenced within the class body that are not defined within the class itself.
Names defined within the class are NOT dependencies

Names assigned within the class body (e.g. class-level attribute assignments) become part of the class's own namespace. Consequently:

  • The assignment targets themselves are not dependencies.
  • When such a locally-defined name is later referenced within the same class body (for example, used as an argument to a method decorator), that reference is also not treated as a dependency, because it resolves to the class-level definition.
  • However, a name that is defined at class level but referenced inside a method body IS a dependency of the class (method bodies do not resolve names against the enclosing class namespace at definition time).
Worked example

For the following class definition:

@decorator(arg)
class A(B, C):
    _a = something
    _b = something

    @method_decorator(_a)
    def method():
        return _b

get_dependencies must yield dependencies whose .name values, in order, are:

["decorator", "arg", "B", "C", "something", "something", "method_decorator", "_b"]

Breakdown of why each appears (and why others do not):

  • decorator, arg — from the class decorator expression @decorator(arg).
  • B, C — the base classes.
  • something, something — the right-hand side of the two class-level attribute assignments (_a and _b). Each occurrence is emitted; the assignment targets _a and _b are not dependencies.
  • method_decorator — the decorator applied to method.
  • _b — referenced inside the method body; since _b is defined at class level but used within a nested method body, it is a dependency.
  • _a is not present: although referenced (as @method_decorator(_a)), it is defined earlier in the same class body and resolves locally.

Notes

  • The ordering of the returned dependencies must match the left-to-right, top-to-bottom source order as illustrated above (decorators, then bases, then body).
  • Only the behavior described here is required.
06 You must implement dependency analysis support for global and nonlocal variable declarations within Python function definitions. 560 words · source specification
Overview

You must implement dependency analysis support for global and nonlocal variable declarations within Python function definitions. The analysis inspects a parsed Python AST node and determines which names the code depends on from an enclosing/outer scope.

Public API

The following must be importable and callable:

  • get_dependencies(node) — accepts a Python AST node (as produced by parsing a function definition) and returns an iterable of dependency objects. Each dependency object must expose a .name attribute (a str) giving the name of the depended-upon symbol.

The order of the returned dependencies must match the order in which the corresponding names are first encountered in the source.

Required Behavior

The analysis already handles ordinary name resolution (parameters, local assignments, decorators, etc.). You are adding handling for global and nonlocal declarations. In all cases below, the node passed to get_dependencies is a single top-level function definition.

A name that is assigned within a function is normally treated as a local variable and does NOT become a dependency. The presence of a global or nonlocal declaration changes whether such an assigned name is considered a dependency, according to the rules below.

nonlocal declarations

  1. When a function declares a name nonlocal and then assigns to it, and that name is not bound anywhere in the analyzed function's own scope (i.e., it must resolve to some enclosing scope outside the analyzed function), the name is a dependency.

    Example:

    def function():
    nonlocal a
    a = 4

    Dependencies: ["a"]

  2. The same holds when the nonlocal declaration and assignment occur inside a nested (inner) function, and the declared name is not bound anywhere in the analyzed function's scope tree that would satisfy the nonlocal binding:

    def function():
    def inner():
        nonlocal a
        a = 4
    return inner

    Dependencies: ["a"]

  3. When the nonlocal name is bound in an enclosing scope within the analyzed function (for example, assigned in the body of the analyzed function itself), the nonlocal reference is satisfied internally, so the name is not a dependency:

    def function():
    def inner():
        nonlocal a
        a = 4
    a = 2
    return inner

    Dependencies: []

global declarations

  1. When a function declares a name global and then assigns to it, the name is a dependency:

    def function():
    global a
    a = 4

    Dependencies: ["a"]

  2. The same holds when the global declaration and assignment occur inside a nested (inner) function:

    def function():
    def inner():
        global a
        a = 4
    return inner

    Dependencies: ["a"]

  3. Unlike nonlocal, a global name remains a dependency even when a name of the same identifier is also assigned as a local in an enclosing scope within the analyzed function. The local assignment does not satisfy or cancel the global dependency:

    def function():
    def inner():
        global a
        a = 4
    a = 2
    return inner

    Dependencies: ["a"]

Summary of the distinction
  • nonlocal name: contributes name as a dependency only if name is not bound anywhere in the analyzed function's own scope tree; if it is bound in an intervening enclosing scope inside the analyzed function, it is resolved internally and is not a dependency.
  • global name: always contributes name as a dependency when assigned under a global declaration, regardless of any same-named local assignments in enclosing scopes within the analyzed function.

Overview

Implement support for Python try/except/else/finally statements in two existing static-analysis functions: one that extracts the names bound (assigned/introduced) by a piece of code, and one that extracts the names a piece of code depends on (references from the surrounding scope).

Both functions operate on Python AST nodes (produced by the standard ast module) and must recursively handle ast.Try nodes and all of their child statements.

Public API

The following callables must be importable and callable as described. (Their existing behavior for other node types must remain intact; this task only adds handling for try statements.)

get_bindings(node)
  • Input: an AST node (e.g. the module node returned by parsing a code snippet).
  • Output: an iterable of strings — the names bound within node, yielded in source order (order of appearance when reading the code top to bottom, left to right).
get_dependencies(node)
  • Input: an AST node.
  • Output: an iterable of dependency objects, in source order. Each object exposes a .name attribute (a string) giving the referenced name.

Required Behavior for try Statements

An ast.Try node has four parts, which must be processed in this order:

  1. body — the statements in the try: block.
  2. handlers — the except clauses. Each handler may optionally bind a name (the as <name> target). If present, that bound name is a binding.
  3. orelse — the statements in the else: block.
  4. finalbody — the statements in the finally: block.
Bindings

When collecting bindings from a try statement, yield, in order:

  • All bindings produced within the try body.
  • For each except clause: the name introduced by its as <name> clause (if any), followed by the bindings produced within that handler's body.
  • All bindings produced within the else block.
  • All bindings produced within the finally block.

Concretely, for a construct of the form:

try:
    a = something_stupid()
except Exception as exc:
    b = recover()
else:
    c = otherwise()
finally:
    d = finish()

the bindings, in order, are: a, exc, b, c, d.

Dependencies

When collecting dependencies from a try statement, yield, in order, the dependencies of:

  • The try body.
  • Each except clause: the type expression being caught (e.g. Exception) is a dependency, along with any dependencies in the handler body. The as <name> target is a binding, not a dependency, and must not appear.
  • The else block.
  • The finally block.

For the same construct above, the dependency names, in order, are: something_stupid, Exception, recover, otherwise, finish.

Notes

  • Names bound locally (such as an assignment target within a block, or an except ... as name) are treated as bindings, not dependencies.
  • Ordering is significant: results must reflect the top-to-bottom structure of the try statement (body, then handlers, then else, then finally).

Objective

Implement a bubble sort function that sorts a list in place based on a caller-supplied comparison predicate.

Public API

Create a module at ssort/_sorting.py that exposes the following function:

def bubble_sort(array, swap):
    ...

Behavior

bubble_sort sorts array in place and returns None. The ordering is determined entirely by the swap predicate.

Parameters
  • array: a list of elements to be sorted in place.
  • swap: a callable taking two arguments (a, b) where a and b are elements of array. It returns a truthy value when the pair is considered out of order and must be swapped, and a falsy value otherwise. Requirements

  • The function must not return a new list; it modifies the given list and its return value is unused.
Edge cases
  • An empty list remains empty.
  • A list with a single element is left unchanged.
  • A list already in the correct order is left unchanged.
  • A list in the opposite order is fully reordered so that the predicate is satisfied for all adjacent pairs.
Example semantics

With swap = lambda a, b: a > b (i.e., swap when the earlier element is greater than the later one):

  • [3, 2, 1] becomes [1, 2, 3]
  • [5, 4, 3, 2, 1] becomes [1, 2, 3, 4, 5]
  • [0, 1, 3, 5, 6] remains [0, 1, 3, 5, 6]
