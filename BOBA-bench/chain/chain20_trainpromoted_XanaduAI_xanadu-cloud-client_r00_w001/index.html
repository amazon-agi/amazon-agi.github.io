Summary

Contract for Connection and URL Resolution

A connection given to either class supplies:

  • connection.url(path: str) -> str, which resolves a path against the scheme, host, and port configured on the connection; and
  • the same HTTP request operation that Device already uses, which accepts a method and a connection-relative path.

The endpoint paths documented below are the ones ordinary API operations use.

URL-valued references to associated resources appear in some detail responses. Each such value is a resource path reference, not an alternative request origin. To retrieve one of these resources:

  1. Parse the reference and take only its path component out.
  2. perform the GET through the supplied connection using that path; resolving it with connection.url(path) is equivalent.

The request destination must not be the reference's scheme, host, port, query, or fragment. Even when the value is an absolute URL naming a different host, this rule applies. For example, retrieving a reference of https://elsewhere.example:9443/jobs/abc/result?token=x happens from the active connection at /jobs/abc/result, not from elsewhere.example.

In the case of Job, circuit_url and result_url are covered by this rule. Existing Device references such as certificate_url and specifications_url keep following the same connection-rebasing behavior.

wait() blocks until finished is true and returns None.

  • Should the current instance already hold a cached terminal status ("cancelled", "failed", or "completed"), return immediately without refreshing, requesting, or sleeping.

  • After each nonterminal check, sleep for exactly delay seconds before the next fresh check. After the terminal check, do not sleep.
  • If check N is the first one at which the job becomes terminal, perform exactly N detail GETs and N - 1 sleeps, for a total requested sleep duration of (N - 1) * delay.

Isolation and Seeding of Caches

Caching happens strictly per object instance:

  • The first access with nothing cached fetches the remote value that is needed; subsequent accesses reuse it until invalidated.
  • Even with the same ID or target and the same connection, two objects still have independent caches.
  • When one object is fetched, seeded, refreshed, or cancelled, the cache of another object must not be populated or invalidated.
  • The responses already obtained by Job.submit(), Job.list(), and Device.list() count as the initial cached details of the corresponding object.
  • Cache invalidation is lazy: the replacement fetch is never performed by refresh() itself.

For example, take two Device("qpu", connection) instances that receive successive states offline and online: the first access on each instance must independently return those states. When only the first is refreshed and its status is then read, that reading performs the next request while the second continues returning its own cached value; the converse applies when the second is refreshed.

Cached-property utility

  • on the first access for a particular instance, its function is evaluated, and that value is reused on later accesses;
  • every instance's value is independent, even when all instances use the same descriptor;
  • assignment through the descriptor seeds or replaces only that instance's cached value; and
  • deletion through the descriptor invalidates only that instance's value and, when no value is cached, is harmless, so a later access recomputes it.

A class-wide value that causes one instance to reuse or lose the cached result of another instance is not compatible.

  • A non-null numeric running_time is a number of seconds and becomes timedelta(seconds=value); a value that is null remains None.

  • Job.clear(self) -> None

  • The user_agent property must return exactly f"XanaduCloudClient/{xcc.__version__}" (that is, the string XanaduCloudClient/ followed by the package version). It no longer carries a (API) or (CLI) suffix.
  • The headers property must return a dictionary that contains exactly these keys and values (and no others):
    • "Accept-Version": the API version of the connection (e.g. "0.4.0").
    • "Authorization": "Bearer " followed by the current access token value (e.g. "Bearer None" when no access token is set).
    • "User-Agent": the user_agent value described above.

The api_version property returns the API version string of the connection (e.g. "0.4.0").

3. Expected uptime of a device

Modify the expected_uptime property of the xcc.Device class.

The device details underlying the property contain an "expected_uptime" mapping from lowercase weekday names to two-element lists of ISO-8601 time strings that give the daily start and end of expected uptime. That mapping may contain only some weekdays.

The expected_uptime property must return a mapping that behaves as follows:

  • It has an entry for every day of the week, keyed by lowercase English weekday names.
  • Iterating over the keys follows chronological weekday order: "monday", "tuesday", "wednesday", "thursday", "friday", "saturday", "sunday".
  • For each weekday that is present in the raw data, the value is a 2-tuple (start, end) in which start and end are datetime.time objects parsed from the corresponding ISO-8601 time strings (parse via datetime.time.fromisoformat).
  • For each weekday that is not present in the raw data, the value is None.

The returned object must support .items(), which yields (key, value) pairs in the chronological weekday order given above.

Example: with raw data {"expected_uptime": {"wednesday": ["16:00:00+00:00", "20:00:00+00:00"]}}, iterating the items of expected_uptime yields, in order:

("monday", None)
("tuesday", None)
("wednesday", (time.fromisoformat("16:00:00+00:00"), time.fromisoformat("20:00:00+00:00")))
("thursday", None)
("friday", None)
("saturday", None)
("sunday", None)
