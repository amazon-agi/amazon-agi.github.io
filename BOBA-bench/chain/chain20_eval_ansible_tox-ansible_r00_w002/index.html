Overview

Task Specification: Changes to Environment Generation in tox-ansible

Overview

The software you are changing here is a tox plugin called tox-ansible. Given an Ansible collection, this plugin automatically generates tox environments for it, taking the collection's structure (roles, molecule scenarios, and available Ansible test tooling) as its basis. Which environments get generated, and how the commands attached to those environments are built up — those two things are what your changes touch. Two routes exist for observing the resulting behavior: invoking tox -l (which lists the environments that were generated) and actually running one of the generated environments.

Requirements on Behavior

1. Names of the environments generated for ansible-test tooling

Once the plugin has scanned a collection and generated the built-in environments (those that are neither role-based nor user-defined), the set of ansible-test-related environments emerging from that auto-generation must produce these names:

  • There must be a generated environment bearing the name env.
  • The same holds for shell: an environment of that name must be generated.
  • As for sanity — an environment that generation used to create — it must no longer show up in the list of generated environments.

Invoking tox -l shows the names of these generated environments next to the environments that users have defined for tox and the ones derived from roles/molecule. For illustration: given a collection that additionally defines user environments and has simple roles, the full sorted tox -l output contains — in sorted order — env, lint_all, one, the various roles-* environments, shell, and two.

If factor-based expansion (multiple Python/Ansible version combinations) is applied on top of the plugin, the env and shell environments are nevertheless generated a single time (no multiplication across version factors applies to them), and they turn up in the sorted tox -l output as bare env and shell names, next to the expanded environments and to any user-defined environments.

2. Running role/molecule environments: requirements must be installed and execution must succeed

Take a generated environment of the role-based molecule kind. Its name follows the pattern roles-<role>-<scenario>; roles-simple-default serves as an example. Executing such an environment via tox -e <name> must result in the matching molecule scenario being driven through to completion, in such a way that the tasks of the role really do execute. A concrete instance: when what gets run is a simple role, and that role's task prints a debug message, the command's standard output must contain the text of that message.

For that to hold, the environment must have the Python/Ansible requirements that the run needs installed before molecule executes; with those in place, a fresh environment (one that has no .tox directory from the start) can be created and put through a complete run, without a separate manual installation step being needed.

3. Treatment of command arguments

The commands that generated environments run must be invoked with their appropriate arguments in place. As for the conditions that decide whether extra arguments may be appended to ansible-test-style commands: those conditions must permit the extra arguments to be added, not suppress them.

Public API and Invocation Surface

Integration with tox happens in the shape of a tox plugin; these changes introduce no new importable Python API. The surface that can be observed is:

  • tox -l — enumerates all environment names, the generated ones as well as the user-defined ones.
  • tox -e <environment-name> — executes one particular generated environment.

Assuming the collection has a suitable structure, the names that your generation logic produces must include the literal names env and shell; sanity must not be included among them.

Fixture and Structural Context

These changes are put through their paces against an Ansible collection fixture, which has the following contents:

  • A role called simple; within it, a tasks/main.yml holds a task whose effect is to print a debug message (literally the text tox-ansible is the best).
  • A molecule scenario named default for that role — it uses the podman driver, runs on a fedora:latest platform, and comes with a converge.yml that applies the simple role.
  • A tests/sanity/ directory in which the files ignore-2.9.txt, ignore-2.10.txt, and requirements.txt are present (they may be empty).

It is against this structure that your environment-generation and command-construction logic must behave correctly: generation of the env and shell environments must happen, generation of a sanity environment must not, and the roles-simple-default molecule environment must be allowed to be brought into existence in a fresh state and to run all the way through, with the role's debug message ending up emitted to stdout.

Recap of the Required Changes

  1. Generation of a sanity environment is to be replaced by generation of the env and shell environments.
  2. Ensure that the generated environments have their requirements installed, with the outcome that molecule runs succeed on a checkout that is fresh (one with no existing .tox).
  3. Ensure that the arguments of environment commands are included correctly at the point where those commands are constructed — extra args for ansible-test-style commands among them.
