01 Implementing pydargs.parse 440 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Implementing pydargs.parse

Summary

Build a module called pydargs that exposes a public function parse. This function takes a list of command-line argument strings and parses them into an instance of a given dataclass; the dataclass's fields define the available arguments, together with their types and their defaults.

Public API

def parse(config_class, args)
  • config_class: A dataclass type (a class decorated with @dataclass). The arguments to be parsed are defined by its fields.
  • args: A list of strings that represent command-line arguments (e.g. ["--a", "12"]).
  • Returns: An instance of config_class, filled in from the parsed arguments.

It must be possible to import the function as:

from pydargs import parse

Behavior Requirements

For every field of the given dataclass, parse must accept a corresponding command-line option named --<field_name>. The value that comes after the option on the command line must be converted to the field's declared type and assigned to that field on the instance that is returned.

Converting Types

The field types listed below must be supported, with values converted from their string form on the command line:

  • int: The string gets converted to an integer. E.g. --a 12 yields the integer 12.
  • str: The string is taken as-is. E.g. --b abcd yields "abcd".
  • float: The string is converted into a float. E.g. --c 1.23 yields 1.23.
  • bool: The string gets converted to a boolean. If the argument is supplied with a value of "True", the resulting field value must be the boolean True.
Default Values
  • A field without a default value is required: its option must be present in args.
  • A field with a declared default value is optional. When its option is absent from args, the returned instance must carry that field's declared default value.
Example

Consider the following dataclass:

@dataclass
class Config:
    a: int
    b: str = "abc"
    c: float = 0.1
    d: bool = False
  • The call parse(Config, ["--a", "12"]) returns a Config instance where a == 12, b == "abc", c == 0.1, and d is False.
  • The call parse(Config, ["--a", "12", "--b", "abcd"]) returns an instance where b == "abcd".
  • The call parse(Config, ["--a", "12", "--c", "1.23"]) returns an instance where c == 1.23.
  • The call parse(Config, ["--a", "12", "--d", "True"]) returns an instance where d is True.

The object that gets returned must be an instance of the dataclass type that was passed in.

Packaging

The pydargs module must be organized so that from pydargs import parse succeeds when the package is installed/available on the path.

Task Description

Overview

The parse function in the pydargs module is to be extended so that it supports parsing command-line arguments into the list fields of a dataclass, and so that it explicitly rejects certain other collection types.

Public API

A callable must be exposed by the module pydargs:

def parse(config_class, args)
  • config_class: a dataclass type, the fields of which define the expected arguments.
  • args: a list consisting of command-line argument strings.
  • Return value: an instance of config_class populated from the parsed arguments.

For each dataclass field named X, there is a corresponding command-line option --X.

Behavior Requirements

Field types that already exist (must continue to work)

Parsing of the following field types is done from a single argument value following the option flag:

  • int — the value is parsed as an integer.
  • str — the value is used as-is.
  • float — the value is parsed as a floating-point number.
  • bool — the string values "True" / "False" are parsed into the corresponding boolean.

A field that has a default value may be left out of the arguments; in that case, the default is used.

New: support for list fields

A field whose annotation is list[T] (e.g. list[int]) must accept one or more values following its option flag. Each value that is provided is converted to the element type T, and the field is set to a list made up of those converted values.

As an example: for a field e: list[int], the arguments --e 1 2 3 result in e == [1, 2, 3].

A list field may declare a default (through a default factory) and be left out of the arguments, in which case its default value is used.

Collection types that are not supported

Fields whose annotation is set[T] or tuple[T] are not supported. An attempt to parse the arguments of a dataclass that contains such a field must raise NotImplementedError.

Remarks

  • The order of the fields above mirrors the fields exercised for a dataclass that has the fields: a: int (required), b: str (default "abc"), c: float (default 0.1), d: bool (default False), e: list[int] (default empty list).

Specification of the Task

Summary

Extend the pydargs package so that command-line arguments can be parsed into datetime.date and datetime.datetime fields of a dataclass.

Public Interface

The pydargs package must expose the following callable:

parse(config_class, args)
  • config_class: a dataclass type that describes the configuration.
  • args: a list of strings representing the command-line arguments.
  • Returns: an instance of config_class built from args.

This function already exists and handles other field types; your job is to add support for the two additional field types described below. Behavior that already exists must be preserved.

Behavior Requirements

Fields of type date

For a dataclass field annotated with datetime.date:

  • The field is exposed as a command-line option named after the field name with underscores converted to hyphens and prefixed with --. As an example, a field named a_date is set via --a-date <value>.
  • If the field has no default value, it is required. Invoking parse without providing the argument must cause the program to exit (raise SystemExit).
  • If the field has a default value, that default is used when the argument is not supplied.
  • The string value that is provided must be converted to a datetime.date instance.
  • By default, parsing of the value string uses the ISO format %Y-%m-%d (e.g. "1234-05-06" yields date(1234, 5, 6)).
Fields of type datetime

For a dataclass field annotated with datetime.datetime:

  • Exposed as a command-line option with the same naming convention (underscores become hyphens, -- prefix).
  • When the field has a default (including one supplied via field(default_factory=...)), that default is used when the argument is not supplied.
  • The string value that is provided must be converted to a datetime.datetime instance.
Custom date/datetime parsing format

A date or datetime field may declare a custom parsing format in its dataclass field metadata under the key date_format. For example:

a_date: date = field(metadata=dict(date_format="%m/%d/%Y"))
b_datetime: datetime = field(
    default_factory=datetime.now,
    metadata=dict(date_format="%m/%d/%Y %H:%M"),
)

When a field's metadata contains date_format, the supplied argument string must be parsed according to that format string (as accepted by datetime.strptime):

  • For a date field, the result of parsing is a datetime.date (e.g. with format "%m/%d/%Y", input "8/16/1999" yields date(1999, 8, 16)).
  • For a datetime field, the result of parsing is a datetime.datetime (e.g. with format "%m/%d/%Y %H:%M", input "12/12/1991 23:45" yields datetime(1991, 12, 12, 23, 45)).

When a field carries no date_format metadata, the default ISO format (%Y-%m-%d) applies to date fields.

Remarks

  • The value of the resulting date field must equal a datetime.date, and the value of the datetime field must equal a datetime.datetime.
  • When the corresponding argument is omitted, defaults produced by default_factory must be respected.
05 Write a function parse inside a module called pydargs 625 words · source specification, reworded by GLM-5.3-Flash

Specification of the Task

Overview

Write a function parse inside a module called pydargs; given a dataclass, this function constructs an instance of it by parsing a list of command-line argument strings.

Public API

from pydargs import parse

def parse(dataclass_type, args: list[str]):
    ...
  • dataclass_type: a dataclass type that describes the configuration; there is a command-line option for each field.
  • args: a list of string tokens (comparable to sys.argv[1:]).
  • Returns: an instance of dataclass_type whose contents come from the parsed arguments.

Mapping Fields to Options

Each dataclass field whose name is field_name has a matching command-line option --field_name. If a field name contains underscores, they turn into hyphens in the option (e.g. a field a_date → --a-date; a field g → --g).

  • A field without a default (and without a default factory) is a required option; if the option is not supplied, parsing must fail via SystemExit (standard argparse-style behavior).
  • When the option is not supplied on the command line, a field with a default value falls back to that default.

Field Types That Must Be Supported

Value conversion must be supported for the following field types:

  • int: the supplied token gets converted to an integer.
  • str: the supplied token is taken as-is.
  • float: the supplied token gets converted to a float.
  • bool: covered by the dedicated section below.

Boolean Fields

There are two possible input modes for boolean fields; which one applies is determined by the field's metadata.

Value-based booleans (the default mode)

A bool field without the special metadata described below accepts a single value token, that is, --field VALUE. The value string is interpreted with case ignored:

  • Interpreted as True: "1", "true" (in any capitalization, such as "true", "True", "TRUE").
  • Interpreted as False: "0", "false" (in any capitalization, such as "false", "False").

The attribute value produced as a result must be an actual Python bool (True / False).

Flag-only boolean fields

A bool field for which the field metadata contains the key "bool_arg_type" set to the string "flag_only" does not accept a value token. Instead, it exposes two zero-argument flags that are mutually exclusive:

  • --field sets the field's value to True.
  • --no-field sets the field's value to False (underscores in the field name are converted to hyphens, e.g. field g → --no-g).

If neither flag is supplied, the field gets its default value.

A flag-only boolean field of this kind is declared using field(metadata={"bool_arg_type": "flag_only"}); if no explicit default is present, it defaults to False.

Behavior of Defaults

When optional fields receive no options, the returned instance must reflect each field's declared default. Specifically:

  • When a bool field is declared with field(default=True), it defaults to True.
  • A flag-only bool field that lacks an explicit default defaults to False.
  • Plain typed defaults (e.g. str = "abc", float = 0.1, bool = False) are respected.

Example of Field Declarations

from dataclasses import dataclass, field

@dataclass
class Config:
    a: int
    g: bool = field(metadata={"bool_arg_type": "flag_only"})
    b: str = "abc"
    c: float = 0.1
    d: bool = False
    f: bool = field(default=True)

For this dataclass:

  • The call parse(Config, ["--a", "12"]) yields a=12, b="abc", c=0.1, d=False, f=True, g=False.
  • parse(Config, ["--a", "12", "--b", "abcd"]) results in b="abcd".
  • parse(Config, ["--a", "12", "--c", "1.23"]) results in c=1.23.
  • parse(Config, ["--a", "12", "--f", "0"]) results in f=False.
  • parse(Config, ["--a", "12", "--f", "1"]) results in f=True.
  • parse(Config, ["--a", "12", "--f", "true"]) results in f=True.
  • parse(Config, ["--a", "12", "--f", "False"]) results in f=False.
  • parse(Config, ["--a", "12", "--d", "TRUE"]) results in d=True.
  • parse(Config, ["--a", "12", "--g"]) results in g=True.
  • parse(Config, ["--a", "12", "--no-g"]) results in g=False.
06 Implement parse in the pydargs module, or modify it, so that it parses command-line argument tokens into an instance of a dataclass. 683 words · rewritten by GPT-5.6-sol, reworded by GLM-5.3-Flash

Task Description

Summary

Implement parse in the pydargs module, or modify it, so that it parses command-line argument tokens into an instance of a dataclass. Which options are available and how conversion behaves is determined by the dataclass field definitions—including their declared types, default values, and metadata.

Public Interface

from pydargs import parse

The signature is:

def parse(config_class: type, args: list[str]) -> <instance of config_class>
  • config_class: a dataclass type that describes the configuration fields.
  • args: a list of the command-line argument tokens, given as strings.
  • The return value must be an instance of config_class filled in from args and the applicable field defaults.

Mapping of Options

Every dataclass field corresponds to a long option named --<field_name>. Except where the field is a flag-style boolean as described below, the option consumes one value token that follows it. That token is converted according to the type declared for the field and assigned to the matching field on the returned instance.

Field-Type Behavior

Fields of type str

A str field accepts one value token and stores it as a string. As an example, ['--b', 'abcd'] sets b to 'abcd'.

Fields of type int

An int field accepts one value token and stores its integer conversion. As an example, ['--a', '12'] sets a to 12.

Fields of type float

A float field accepts one value token and stores its floating-point conversion. As an example, ['--c', '1.23'] sets c to 1.23.

Boolean fields that take a value

A bool field whose metadata does not contain {'as_flags': True} is an option that takes a value. It must consume exactly one token after --<field_name> and convert that token in the following way:

  • False is produced by 0 and false.
  • True is produced by 1 and true.
  • The matching is case-insensitive, so values such as False, TRUE, and other casing variants are accepted.
  • Any other token, such as blabla, is invalid.

The following examples use a field named f:

  • ['--f', '0'] sets f to False.
  • ['--f', '1'] sets f to True.
  • ['--f', 'False'] sets f to False.
  • ['--f', 'blabla'] raises SystemExit.

Value input that is missing or otherwise invalid—including input that violates the option's single-value arity—must also raise SystemExit.

Boolean fields represented by flags

For a bool field whose metadata contains {'as_flags': True}, the representation consists of two zero-argument flags:

  • --<field_name> sets the field to True.
  • --no-<field_name> sets the field to False.

Neither flag consumes a value token. When a value is supplied for one of these flags, that leaves invalid extra input and must raise SystemExit. As an example, take a flag-style field named g:

  • ['--g'] sets g to True.
  • ['--no-g'] sets g to False.
  • ['--g', 'help'] raises SystemExit.
Flag-style booleans that are omitted

If neither flag appears:

  • When the field declares an explicit dataclass default, that declared default is retained by the field.
  • When the field has no explicit default and is declared only with field(metadata={'as_flags': True}), it is optional and must implicitly default to False. Its omission must not make parsing fail, leave the field unset, or cause the field to be treated as required.

For example:

from dataclasses import dataclass, field

@dataclass
class Config:
    a: int
    g: bool = field(metadata={"as_flags": True})

A call to parse(Config, ['--a', '12']) must return a Config instance in which a is 12 and g is False.

Default Values

When an option is omitted, a field that has a declared dataclass default keeps that value. Among these are defaults such as b: str = 'abc', c: float = 0.1, and d: bool = False. For an omitted flag-style boolean that has no explicit default, the implicit False behavior is the specific additional rule described above.

Handling of Errors

When errors occur at the argument level, parsing must be terminated by raising SystemExit, consistent with standard command-line parser behavior. Included here are invalid boolean value tokens, invalid option arity, and value tokens supplied to zero-argument boolean flags.

Task Specification: pydargs — Command-Line Argument Parsing Based on Dataclasses

Summary

Implement a module with the name pydargs that exposes a public function parse. The function's task is to populate a Python dataclass by parsing a list of command-line argument strings.

Public Interface

from pydargs import parse
Signature of the Function
def parse(config_class, args):
    ...
  • config_class: a dataclass type whose fields describe the arguments that are to be parsed.
  • args: a list of strings that represent the command-line arguments (as they would appear in sys.argv[1:]).
  • Returns: an instance of config_class in which each field is populated from the parsed arguments (or from its default).

How Arguments Are Mapped

Each dataclass field corresponds to a command-line option:

  • A field called foo is provided on the command line through the option --foo.
  • If a field name contains underscores, the corresponding option has those underscores replaced by hyphens. For example, a field named a_date maps to the option --a-date, and b_datetime maps to --b-datetime.
Defaults and Required Fields
  • A field without a default (with no default and no default_factory) is a required argument. If the option of a required field is not supplied in args, parsing must fail by raising SystemExit.
  • A field that comes with a default value or a default_factory is optional. If its option is omitted, the resulting attribute takes the default value / the value produced by the default factory.

Field Types That Are Supported

The field type annotations listed below must be supported. In each case, the string value(s) taken from the command line must be converted to the annotated type.

int

The supplied value is converted into an integer.

str

The supplied value is taken as-is.

float

The supplied value is converted into a float.

bool

The supplied value is converted into a boolean. Accepted string inputs, and the results they produce:

  • "True", "TRUE" (case-insensitive true) and "1" → True
  • "False" (case-insensitive false) and "0" → False

A value that is not recognized must cause parsing to fail by raising SystemExit.

A boolean field accepts exactly one value argument.

date (imported from datetime)

The supplied value is parsed into a datetime.date.

  • By default, the value is parsed with the ISO format YYYY-MM-DD (e.g. "1234-05-06" → date(1234, 5, 6)).
  • If the field's metadata contains a key "date_format", the value of that key is a strptime-style format string used to parse the input, and the result is converted to a date (e.g. format "%m/%d/%Y" parses "8/16/1999" → date(1999, 8, 16)).
datetime (imported from datetime)

The supplied value is parsed into a datetime.datetime.

  • If the field's metadata contains a key "date_format", the value of that key is a strptime-style format string used to parse the input (e.g. format "%m/%d/%Y %H:%M" parses "12/12/1991 23:45" → datetime(1991, 12, 12, 23, 45)).
list[X] (a parameterized list, e.g. list[str], list[int])

A list field consumes zero or more value arguments following its option; each of these is converted to the list's element type.

  • --arg 1 2 with element type str → ["1", "2"]
  • --arg 1 2 with element type int → [1, 2]
  • A list field must have a default (a default_factory is the natural way to provide one). When its option is omitted, the attribute takes the default value.
  • When parsing is attempted, a list field without a default must cause a NotImplementedError to be raised.

Field Types That Are Not Supported

The annotated field types listed below are not supported, and when parsing is attempted they must cause a NotImplementedError to be raised:

  • set[...] (e.g. set[int])
  • tuple[...] (e.g. tuple[str])

Summary of Error-Condition Behavior

  • A required argument is missing → SystemExit.
  • A boolean value is invalid → SystemExit.
  • A list field that lacks a default → NotImplementedError.
  • A field of type set or tuple → NotImplementedError.

Examples of Behavior

Consider:

@dataclass
class Config:
    a: int
    b: str = "abc"
    c: float = 0.1
    d: bool = False

  • parse(Config, ["--a", "12", "--b", "abcd"]) → b == "abcd"
  • parse(Config, ["--a", "12", "--c", "1.23"]) → c == 1.23
  • parse(Config, ["--a", "12", "--d", "True"]) → d is True

Consider a list field:

@dataclass
class TConfig:
    arg: list[int] = field(default_factory=lambda: [])
  • parse(TConfig, []) → arg == []
  • parse(TConfig, ["--arg", "1", "2"]) → arg == [1, 2]

Consider date/datetime fields:

@dataclass
class TConfig:
    a_date: date = date(2345, 6, 7)
    b_datetime: datetime = field(default_factory=datetime.now)
  • parse(TConfig, []) → a_date == date(2345, 6, 7) and b_datetime is a datetime instance.

Summary

Write a parse function in a module called pydargs (importable as from pydargs import parse) that builds a dataclass instance by parsing command-line arguments based on the dataclass's field definitions.

Public Interface

def parse(config_class, args: list[str]) -> config_class_instance

  • args: a list of strings representing the command-line arguments.
  • Returns: an instance of config_class filled in from the parsed arguments.

Every dataclass field corresponds to one command-line option. For a field called field_name, the matching option is --field-name (underscores in the field name are replaced with hyphens). Fields that lack a default value are required; fields that have a default value (either a direct default or field(default=...)) are optional, and the default is used when the option is not provided.

Field Types That Must Be Supported

The parse function must support the field types below, each exactly as described.

int

An option that consumes one value, which is converted to an integer.

str

An option that consumes one value, which is kept as a string.

float

An option that consumes one value, which is converted to a float.

bool

A boolean field works in one of two distinct modes, depending on its field metadata.

Standard boolean mode (the default):

A boolean field is an option that consumes exactly one value string. Interpretation of the value is case-insensitive:

  • The strings "1", "true" (in any capitalization, e.g. "True", "TRUE") evaluate to True.
  • The strings "0", "false" (in any capitalization, e.g. "False") evaluate to False.
  • Every other value (e.g. "blabla") is invalid and must cause the program to exit (raising SystemExit), just like any invalid command-line argument.

Flag mode:

If a boolean field is declared with metadata {"as_flags": True} (via field(metadata={"as_flags": True})), the option turns into a pair of flags that take no value:

  • Passing --field-name sets the field to True.
  • Passing --no-field-name sets the field to False.
  • Neither of these flags accepts a value. Providing a value after the flag (e.g. --field-name help) is invalid and must cause the program to exit (raising SystemExit).
  • If neither flag is supplied, the field takes its default value.

Required Behavior

  • When only the required options are supplied, parsing yields a dataclass instance in which all optional fields equal their declared defaults.
  • Required fields that are missing (i.e., no default and not supplied) must cause the program to exit (raising SystemExit).
  • Invalid values given to typed options must cause the program to exit (raising SystemExit).

Task Specification: Custom Field Parsers and the Handling of Boolean Fields in pydargs

Overview

You are working on pydargs, a library that parses command-line arguments into a Python dataclass instance. The public entry point of the library is:

from pydargs import parse
parse signature and overall behavior
def parse(config_class: type[T], args: list[str]) -> T
  • The parameter config_class is a dataclass type.
  • The parameter args is a list of command-line argument tokens.
  • The function returns an instance of config_class populated from args.
  • Every dataclass field is exposed as a command-line option named --<field_name> (for example, the field arg maps to --arg, and the field a maps to --a).
  • A field that has no default is a required option, unless the boolean flag-mode exception described below applies. When a required option is omitted, parsing must raise SystemExit and write an error to stderr containing: the following arguments are required: --<field_name>
  • A field that has a default is optional, and when its option is omitted that default is retained.

This task concerns boolean field parsing and custom field parsers supplied through dataclass field metadata.

Part 1: Boolean Fields

A field annotated as bool operates in one of two distinct command-line modes, with the choice determined by its metadata.

1a. Value mode (the default)

Whenever the metadata of a bool field does not contain as_flags=True, the field is in value mode. This includes fields with no metadata, fields with empty metadata, and fields with as_flags=False.

In value mode, --<name> consumes one value token. The textual values are converted case-insensitively, and the conversion must follow this table:

  • "0" is converted to False.
  • "1" is converted to True.
  • "false", with any capitalization such as "False" or "FALSE", is converted to False.
  • "true", with any capitalization such as "True" or "TRUE", is converted to True.
  • Any other value makes parsing raise SystemExit; stderr must contain: argument --<name>: invalid bool value:

Whether or not the field declares a default, this conversion applies. When an optional value-mode field is omitted, its declared default is retained. A value-mode boolean without a default remains required under the general required-field rule.

1b. Flag mode (as_flags=True)

A bool field that carries metadata={"as_flags": True} is exposed as a pair of flags that take no value:

  • --<name> sets the field to True.
  • --no-<name> sets the field to False.
  • Neither flag consumes a value. Therefore, an additional token after one of these flags, such as in --<name> help, is not accepted, and parsing must raise SystemExit.

When neither flag is supplied:

  • When the field declares a dataclass default, that default is retained.
  • If the field has no declared dataclass default, it is nevertheless optional, and its value in the returned dataclass instance must be False.

A no-default flag-mode boolean must consequently not be reported as a missing required option. This exception applies only to bool fields in flag mode; no-default booleans in value mode and no-default fields that use a custom parser remain required.

Part 2: Custom Parser Through parser Metadata

A dataclass field may supply a parsing callable under the parser metadata key:

field(metadata=dict(parser=some_callable))

When this metadata is present:

  • The field is exposed as --<field_name>, consuming one string argument.
  • The exact raw command-line string is passed to some_callable.
  • The value returned by the callable is assigned to the field; it may be of any type, including a list or dictionary.
  • The declared type annotation of the field is not used to convert the supplied value; producing the result is fully the responsibility of the custom callable.
  • If the field has a default and the option is omitted, the declared default is retained and the custom parser is not called. In particular, a field whose default is None still remains None when the option is omitted.
  • If the field has no default, the option is required; omitting it must raise SystemExit and write an error to stderr containing: the following arguments are required: --<field_name>
  • If the callable raises an exception during the conversion of a supplied value, parsing must raise SystemExit, and stderr must contain: argument --<field_name>: invalid <parser_name> value: '<raw_string>'

Within this message, <parser_name> is the callable's __name__, and <raw_string> is the exact string passed to the callable.

Required Behavior: Ignoring Fields

Metadata may be attached to each dataclass field (via dataclasses.field(metadata=...)). Whether a field is exposed as a command-line argument is governed by a new metadata key:

  • ignore_arg (boolean):
    • When ignore_arg appears in a field's metadata with the value True, that field must not be added to the command-line parser. No --<fieldname> option is created for it, and if such an option is provided on the command line, it must be treated as an unrecognized argument.
    • If instead ignore_arg is False, or the key is missing, the field is exposed as a normal command-line argument (existing behavior, left unchanged).
How values are resolved for ignored fields
  • When an ignored field has a default value (either a plain default or default=... in field(...)), the resulting instance must end up with that default value; no part of it is ever taken from args.
  • With an ignored field that has no default value, the dataclass cannot be constructed unless that field is supplied. A call to parse (with args that do not — and cannot — provide the ignored field) must therefore raise TypeError (the standard error produced by instantiating a dataclass with a missing required argument).
Interaction with normal fields and other metadata
  • The other fields in the same dataclass keep working as normal command-line arguments. For example:
    • An option generated from an int field with a default accepts an integer value.
    • A bool field with default=False and metadata as_flags=True becomes a boolean flag: --<fieldname>, when passed, sets it to True; when it is omitted, the flag keeps its default (False).
    • An option generated from a str field with a default accepts a string value.
  • A field on which ignore_arg=False is explicitly set behaves exactly like one that carries no ignore_arg metadata (it is included).
Error handling

  • When the command line includes an option corresponding to an ignored field, the parser must fail with a nonzero exit (raising SystemExit), and the error output must report the offending tokens as unrecognized arguments, in the form:

    error: unrecognized arguments: --<fieldname> <value>
