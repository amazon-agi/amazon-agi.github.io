Task Specification: Implement pydargs.parse

Overview

Create a module named pydargs that exposes a public function parse. This function parses a list of command-line argument strings into an instance of a given dataclass, using the dataclass's fields to define the available arguments, their types, and their defaults.

Public API

def parse(config_class, args)
  • config_class: A dataclass type (a class decorated with @dataclass). Its fields define the arguments to be parsed.
  • args: A list of strings representing command-line arguments (e.g. ["--a", "12"]).
  • Returns: An instance of config_class, populated from the parsed arguments.

The function must be importable as:

from pydargs import parse

Required Behavior

For each field of the provided dataclass, parse must accept a corresponding command-line option whose name is --<field_name>. The value that follows the option on the command line must be converted to the field's declared type and assigned to that field on the returned instance.

Type conversion

The following field types must be supported, with values converted from their string form on the command line:

  • int: The string is converted to an integer. E.g. --a 12 yields the integer 12.
  • str: The string is used as-is. E.g. --b abcd yields "abcd".
  • float: The string is converted to a float. E.g. --c 1.23 yields 1.23.
  • bool: The string is converted to a boolean. When the argument is supplied with a value of "True", the resulting field value must be the boolean True.
Defaults
  • A field with no default value is required: its option must be present in args.
  • A field that declares a default value is optional. When its option is not present in args, the returned instance must carry that field's declared default value.
Example

Given:

@dataclass
class Config:
    a: int
    b: str = "abc"
    c: float = 0.1
    d: bool = False
  • parse(Config, ["--a", "12"]) returns a Config instance with a == 12, b == "abc", c == 0.1, and d is False.
  • parse(Config, ["--a", "12", "--b", "abcd"]) returns an instance with b == "abcd".
  • parse(Config, ["--a", "12", "--c", "1.23"]) returns an instance with c == 1.23.
  • parse(Config, ["--a", "12", "--d", "True"]) returns an instance with d is True.

The returned object must be an instance of the passed-in dataclass type.

Packaging

The pydargs module must be structured so that from pydargs import parse succeeds when the package is installed/available on the path.

Public API

    ...

  • args: a list of string tokens (like sys.argv[1:]).
  • Returns: an instance of dataclass_type populated from the parsed arguments.

Field-to-Option Mapping

Each dataclass field named field_name corresponds to a command-line option --field_name. Field names containing underscores map to options where underscores are replaced by hyphens (e.g. a field a_date → --a-date; a field g → --g).

  • A field without a default (and without a default factory) is a required option; if it is not supplied, parsing must fail via SystemExit (standard argparse-style behavior).
  • A field with a default value uses that default when the option is not supplied on the command line.

Supported Field Types

The following field types must be supported for value conversion:

  • int: the supplied token is converted to an integer.
  • str: the supplied token is used as-is.
  • float: the supplied token is converted to a float.
  • bool: see the dedicated section below.

Boolean Fields

Boolean fields have two possible input modes, selected by the field's metadata.

Value-based booleans (default mode)

A bool field without the special metadata described below accepts a single value token, i.e. --field VALUE. The value string is interpreted case-insensitively:

  • Interpreted as True: "1", "true" (any capitalization such as "true", "True", "TRUE").
  • Interpreted as False: "0", "false" (any capitalization such as "false", "False").

The resulting attribute value must be an actual Python bool (True / False).

Flag-only booleans

A bool field whose field metadata contains the key "bool_arg_type" set to the string "flag_only" does not accept a value token. Instead it exposes two mutually exclusive zero-argument flags:

  • --field sets the field to True.
  • --no-field sets the field to False (with underscores in the field name converted to hyphens, e.g. field g → --no-g).

When neither flag is supplied, the field takes its default value.

Such a flag-only boolean field is declared with field(metadata={"bool_arg_type": "flag_only"}) and, in the absence of an explicit default, defaults to False.

Defaults Behavior

When no options are supplied for optional fields, the returned instance must reflect each field's declared default. In particular:

  • A bool field declared with field(default=True) defaults to True.
  • A flag-only bool field with no explicit default defaults to False.
  • Plain typed defaults (e.g. str = "abc", float = 0.1, bool = False) are honored.

06 Implement or modify parse in the pydargs module so that it parses command-line argument tokens into an instance of a dataclass. 619 words · rewritten by GPT-5.6-sol

Overview

Implement or modify parse in the pydargs module so that it parses command-line argument tokens into an instance of a dataclass. The dataclass field definitions—including their declared types, default values, and metadata—control the available options and conversion behavior.

Public API

from pydargs import parse

Signature:

def parse(config_class: type, args: list[str]) -> <instance of config_class>
  • config_class is a dataclass type describing the configuration fields.
  • args is a list of command-line argument tokens as strings.
  • The return value must be an instance of config_class populated from args and applicable field defaults.

Option Mapping

Each dataclass field maps to a long option named --<field_name>. Unless the field is a flag-style boolean as described below, the option consumes one following value token. The token is converted according to the field's declared type and assigned to the corresponding field on the returned instance.

Field Handling

String fields

A str field accepts one value token and stores it as a string. For example, ['--b', 'abcd'] sets b to 'abcd'.

Integer fields

An int field accepts one value token and stores its integer conversion. For example, ['--a', '12'] sets a to 12.

Float fields

A float field accepts one value token and stores its floating-point conversion. For example, ['--c', '1.23'] sets c to 1.23.

Boolean fields in value-taking mode

A bool field whose metadata does not contain {'as_flags': True} is a value-taking option. It must consume exactly one token after --<field_name> and convert that token as follows:

  • 0 and false produce False.
  • 1 and true produce True.
  • Matching is case-insensitive, so values such as False, TRUE, and other casing variants are accepted.
  • Any other token, such as blabla, is invalid.

Examples for a field named f:

  • ['--f', '0'] sets f to False.
  • ['--f', '1'] sets f to True.
  • ['--f', 'False'] sets f to False.
  • ['--f', 'blabla'] raises SystemExit.

Missing or otherwise invalid value input, including input that violates the option's single-value arity, must also raise SystemExit.

Boolean fields in flag mode

A bool field whose metadata contains {'as_flags': True} is represented by two zero-argument flags:

  • --<field_name> sets the field to True.
  • --no-<field_name> sets the field to False.

Neither flag consumes a value token. Supplying a value for one of these flags leaves invalid extra input and must raise SystemExit. For example, for a flag-style field named g:

  • ['--g'] sets g to True.
  • ['--no-g'] sets g to False.
  • ['--g', 'help'] raises SystemExit.
Omitted flag-style booleans

When neither flag is present:

  • If the field declares an explicit dataclass default, the field retains that declared default.
  • If the field has no explicit default and is declared only with field(metadata={'as_flags': True}), it is optional and must implicitly default to False. Its omission must not make parsing fail, leave the field unset, or treat the field as required.

For example:

from dataclasses import dataclass, field

@dataclass
class Config:
    a: int
    g: bool = field(metadata={"as_flags": True})

Calling parse(Config, ['--a', '12']) must return a Config instance whose a is 12 and whose g is False.

Defaults

When an option is omitted, a field with a declared dataclass default retains that value. This includes defaults such as b: str = 'abc', c: float = 0.1, and d: bool = False. The implicit False behavior for an omitted flag-style boolean without an explicit default is the specific additional rule described above.

Error Handling

Argument-level parsing errors must terminate parsing by raising SystemExit, consistent with standard command-line parser behavior. This includes invalid boolean value tokens, invalid option arity, and value tokens supplied to zero-argument boolean flags.

This task covers boolean field parsing and custom field parsers supplied through dataclass field metadata.

Part 1: Boolean Fields

A field annotated as bool has one of two distinct command-line modes, selected by its metadata.

1a. Value mode (default)

A bool field is in value mode whenever its metadata does not contain as_flags=True. This includes fields with no metadata, empty metadata, and as_flags=False.

In value mode, --<name> consumes one value token. Conversion is case-insensitive for the textual values and must follow this table:

  • "0" becomes False.
  • "1" becomes True.
  • "false", in any capitalization such as "False" or "FALSE", becomes False.
  • "true", in any capitalization such as "True" or "TRUE", becomes True.
  • Any other value causes parsing to raise SystemExit; stderr must contain: argument --<name>: invalid bool value:

This conversion applies whether or not the field declares a default. If an optional value-mode field is omitted, its declared default is retained. A value-mode boolean with no default remains required under the general required-field rule.

1b. Flag mode (as_flags=True)

A bool field with metadata={"as_flags": True} is exposed as a pair of value-less flags:

  • --<name> sets the field to True.
  • --no-<name> sets the field to False.
  • Neither flag consumes a value. An additional token after one of these flags, such as in --<name> help, is therefore not accepted and parsing must raise SystemExit.

When neither flag is supplied:

  • If the field declares a dataclass default, that default is retained.
  • If the field has no declared dataclass default, it is nevertheless optional and its value in the returned dataclass instance must be False.

Consequently, a no-default flag-mode boolean must not be reported as a missing required option. This exception applies only to bool fields in flag mode; no-default booleans in value mode and no-default fields using a custom parser remain required.

Part 2: Custom Parser via parser Metadata

A dataclass field may provide a parsing callable under the parser metadata key:

field(metadata=dict(parser=some_callable))

When this metadata is present:

  • The field is exposed as --<field_name> and consumes one string argument.
  • The exact raw command-line string is passed to some_callable.
  • The callable's return value is assigned to the field. It may be any type, including a list or dictionary.
  • The field's declared type annotation is not used to convert the supplied value; the custom callable is fully responsible for producing the result.
  • If the field has a default and the option is omitted, the declared default is retained and the custom parser is not called. In particular, a field with default None remains None when omitted.
  • If the field has no default, the option is required. Omitting it must raise SystemExit and write an error to stderr containing: the following arguments are required: --<field_name>
  • If the callable raises an exception while converting a supplied value, parsing must raise SystemExit and stderr must contain: argument --<field_name>: invalid <parser_name> value: '<raw_string>'

Here, <parser_name> is the callable's __name__, and <raw_string> is the exact string passed to it.

Required Behavior: Ignoring Fields

Each dataclass field may carry metadata (via dataclasses.field(metadata=...)). A new metadata key controls whether a field is exposed as a command-line argument:

  • ignore_arg (boolean):
    • When a field's metadata contains ignore_arg set to True, that field must not be added to the command-line parser. No --<fieldname> option is created for it, and providing such an option on the command line must be treated as an unrecognized argument.
    • When ignore_arg is False, or the key is absent, the field is exposed as a normal command-line argument (unchanged existing behavior).
Value resolution for ignored fields
  • If an ignored field has a default value (either a plain default or default=... in field(...)), the resulting instance must take that default value; it is never populated from args.
  • If an ignored field has no default value, then constructing the dataclass without supplying that field is impossible. In this case, calling parse (with args that do not — and cannot — provide the ignored field) must raise TypeError (the standard error from instantiating a dataclass with a missing required argument).
Interaction with other metadata / normal fields
  • Other fields in the same dataclass continue to work as normal command-line arguments. For example:
    • A field of type int with a default produces an option that accepts an integer value.
    • A field of type bool with default=False and metadata as_flags=True produces a boolean flag: passing --<fieldname> sets it to True, and omitting it leaves it at its default (False).
    • A field of type str with a default produces an option that accepts a string value.
  • A field explicitly marked ignore_arg=False behaves exactly like a field with no ignore_arg metadata (it is included).
Error handling

  • Supplying a command-line option corresponding to an ignored field must cause the parser to fail with a nonzero exit (raising SystemExit), and the error output must report the offending tokens as unrecognized arguments, in the form:

    error: unrecognized arguments: --<fieldname> <value>
