Task Description

Objective

Implement a class called croniter that iterates over cron expressions, placed in croniter/croniter.py and importable with:

from .croniter import croniter

Given a cron expression together with a reference datetime, an instance must produce successive calendar moments that match that expression, in either the forward or the backward direction.

Public Interface

Constructor
croniter(expr, start_time=None)
  • expr is a string holding the cron expression, in one of the formats supported below.
  • start_time is the initial reference point; it may be passed in as a datetime.
  • When start_time is omitted, the current time is used.
  • The instance carries state: every occurrence that is returned becomes the reference point for the next call.
Iterating Forward
get_next(ret_type=float)

Return the earliest moment that matches and lies strictly after the instance's current reference point; the current reference point is then updated to that result.

Iterating Backward
get_prev(ret_type=float)

Return the latest moment that matches and lies strictly before the instance's current reference point; the current reference point is then updated to that result.

As a result, consecutive calls return successive distinct occurrences. If callers alternate between forward and backward calls, the state update also applies.

Return Value Types

Both iteration methods support the following:

  • float (the default): the matching moment is returned as a numeric timestamp.
  • datetime: the matching moment is returned as a datetime object. Selection is done by passing the datetime class itself as the selector, for example itr.get_next(datetime).

A return selector that is not supported, such as str, must raise TypeError.

Format of the Cron Expression

Fields are separated by single spaces. Exactly two layouts are supported:

  • 5 fields: minute hour day-of-month month day-of-week
  • 6 fields: second minute hour day-of-month month day-of-week

Second-level granularity is enabled by the six-field layout. Any other field count is invalid and must raise ValueError.

Syntax Within a Field

Each field supports the following forms:

  • * — every value that is valid in the field.
  • A lone integer.
  • */n — values chosen by a wildcard step.
  • a-b — a range that is inclusive and does not wrap.
  • Comma-separated lists that combine supported values, steps, and ranges, such as sat,sun.

A range whose start is greater than its end, for example the day-of-month range in * * 5-1 * *, must raise ValueError.

Semantics of Wildcard Steps

A wildcard step is anchored at zero and is then restricted to the field's valid range: a value v chosen by */n matches exactly when v % n == 0. It is not computed by taking the field minimum and adding n repeatedly.

Examples:

  • Minute */5 selects 0, 5, 10, ..., 55.
  • Hour */3 selects 0, 3, 6, ..., 21.
  • Day-of-month */3 selects 3, 6, 9, ..., 30, not 1, 4, 7, ..., 31.
  • Day-of-month */2 selects the even days 2, 4, 6, ..., 30.

Selected values can match only if they actually exist in the current calendar period. So a selected day 30 is skipped in a February that does not contain it.

Ranges for the Fields
  • second: 0–59
  • minute: 0–59
  • hour: 0–23
  • day-of-month: 1–31, subject to the actual length of the selected month
  • month: 1–12
  • day-of-week: 0–7

Values that fall outside the corresponding valid range are invalid.

Month and Weekday Names

Weekday abbreviations are accepted in three-letter lowercase form: sun, mon, tue, wed, thu, fri, and sat.

Month abbreviations are accepted in three-letter lowercase form: jan, feb, mar, apr, may, jun, jul, aug, sep, oct, nov, and dec. Names may be employed as range endpoints, for example jan-jun.

Named tokens are resolved by treating them as complete abbreviations. If a token cannot be resolved, construction propagates KeyError; for instance, * * * janu-jun * is invalid because janu is not a recognized month name.

Weekday Numbering

The weekday numbering used by cron is:

  • 0 or 7: Sunday
  • 1: Monday
  • 2: Tuesday
  • 3: Wednesday
  • 4: Thursday
  • 5: Friday
  • 6: Saturday

The names map to these same values. Expressed in terms of datetime.isoweekday(), a Saturday result has value 6 and a Sunday result has value 7.

Combining day-of-month with day-of-week

The two day fields follow standard cron OR behavior:

  • If both day-of-month and day-of-week are restricted (neither one is *), a date matches when either field matches.
  • If exactly one of the two fields is *, the only field constraining the date is the restricted one.
  • If both are *, every date that is otherwise valid is eligible.

For example, 0 0 1 * wed matches midnight on each Wednesday and also midnight on the first day of each month.

Timing and Calendar Behavior

  • Expressions with five fields operate at minute granularity; occurrences returned have second == 0.
  • Expressions with six fields operate at second granularity.
  • Neither direction ever returns the starting/reference moment itself, even if it matches.
  • Iteration must carry and borrow correctly when crossing minutes, hours, days, months, and years.
  • Month lengths must be respected; dates that are impossible in a month are skipped rather than produced.
  • Leap years must obey Gregorian rules, including February 29 in years such as 1996 and 2000.
  • If the current reference lies outside an allowed month or another allowed calendar period, iteration must jump in the requested direction to the nearest eligible period and select that period's nearest matching moment.

Examples of Required Behavior

All of the results below use ret_type=datetime.

Second-Level Granularity

itr = croniter('*/1 * * * * *', base)
itr.get_next(datetime)

The result in this case is 2012-04-06 13:26:11.

Stepping by Minutes and Hours

Starting from 2010-01-23 12:18, */1 * * * * advances by matching whole minutes: the first result is 2010-01-23 12:19, and iteration rolls from 12:59 to 13:00.

With the same reference, */5 * * * * first returns 2010-01-23 12:20, then follows the five-minute boundaries through 12:55, followed by 13:00.

Starting at 2010-01-24 12:02, 0 */3 * * * returns 2010-01-24 15:00, then 18:00, 21:00, and 2010-01-25 00:00.

Day-of-Month Stepping and Leap Years

Taking 2010-02-24 12:09 as the start, successive forward results for 0 0 */3 * * are 2010-02-27 00:00 and 2010-03-03 00:00. The step selects day 30, but that day does not exist in that February.

For 0 0 * * *, forward daily iteration from February 27 produces February 28 and then February 29 in leap years such as 1996 and 2000.

Weekdays and OR Behavior of the Day Fields

With 2010-02-25 00:00 as the reference, successive forward results for 0 0 * * sat are:

  1. 2010-02-27 00:00
  2. 2010-03-06 00:00

Both are Saturdays (isoweekday() == 6).

From 2010-01-25 00:00, successive forward results for 0 0 1 * wed are:

  1. 2010-01-27 00:00 — weekday match
  2. 2010-02-01 00:00 — day-of-month match
  3. 2010-02-03 00:00 — weekday match

With 2010-02-25 00:00 as the reference, successive forward results for 0 0 * * 7 are 2010-02-28 00:00 and 2010-03-07 00:00, both Sundays (isoweekday() == 7). The numeric value 0 must identify the same weekday.

Rollover Across Months and Years

Starting at 2010-01-25 00:00, successive forward results for 0 0 1 * * begin with 2010-02-01 00:00 and 2010-03-01 00:00; when iteration is continued, it reaches 2010-12-01 00:00 and then 2011-01-01 00:00.

With 2012-01-01 00:00 as the start, 0 * * 3 * skips to the earliest matching moment in March: 2012-03-01 00:00. The two occurrences after that are 2012-03-01 01:00 and 2012-03-01 02:00.

Backward Iteration

With */1 * * * *:

  • Going backward from 2010-08-25 15:56, the previous occurrence is 2010-08-25 15:55.
  • Going backward from 2010-08-25 15:00, the previous occurrence is 2010-08-25 14:59.
  • Going backward from 2010-08-25 00:00, the previous occurrence is 2010-08-24 23:59.

Further backward cases:

  • From 2012-03-15 00:00, 0 0 22 * * returns 2012-02-22 00:00.
  • From 2010-08-25 15:56, successive results for 0 0 * * sat,sun are 2010-08-22 00:00, 2010-08-21 00:00, and 2010-08-15 00:00.
  • From 2010-08-25 15:56, 10 0 * * 0 returns 2010-08-22 00:10.
  • From 2012-02-24 00:00, 5 0 */2 * * returns 2012-02-22 00:05. This is consistent with the rule that */2 selects even day numbers.

Error Cases

The following externally visible failures are required at minimum:

  • A ret_type that is not supported, such as str, raises TypeError.
  • An expression whose field count is neither five nor six, such as * * * *, raises ValueError.
  • A descending range, for instance * * 5-1 * *, raises ValueError.
  • A named token left unresolved, such as janu in * * * janu-jun *, raises KeyError.
  • Numeric field values that fall outside their declared ranges are rejected.

It should exercise the same iterator functionality as described above. It imposes no additional public API or behavior requirements.

Task Specification for the croniter Cron Expression Iterator

Goal

Create a croniter class in a Python package named croniter, which can be imported as:

from croniter import croniter

The class handles cron expressions made up of five or six fields and iterates both forward and backward from a base time. It must compute the next matching time and the previous matching time, and it must expose its current position. Expressions with five fields work at minute granularity; the optional sixth field activates second granularity.

The implementation must run under Python 3 and must stay Python 2 compatible wherever relevant.

Public Interface

Constructor
croniter(expr_format, start_time=<current time>)
  • expr_format is a string that contains exactly five or six cron fields separated by whitespace.
  • start_time is optional. If it is omitted, the iterator starts from the current time, which means constructing croniter('* * * * *') is valid.
  • When supplied explicitly, start_time may be a datetime.datetime value or a numeric Unix timestamp. It sets the iterator's initial current position.
Methods for Iteration and Current Position
get_next(ret_type=float)
get_prev(ret_type=float)
get_current(ret_type=float)

ret_type selects the type of the returned value:

  • float returns a Unix timestamp; this is the default.
  • With datetime.datetime, a datetime.datetime value is returned.
  • Any other return type is unsupported. In particular, passing str to get_next or get_prev must raise TypeError; get_current is subject to the same return-type restriction.

get_next and get_prev set the iterator's current position to the value they return, so repeated calls continue from the occurrence that was returned previously. The get_current method only reports the current position; it does not advance or rewind it.

Layout of a Cron Expression

A five-field expression is laid out as:

minute hour day-of-month month day-of-week

A six-field expression adds a seconds field at the end:

minute hour day-of-month month day-of-week second

Valid values are the following:

Position Field Valid values
1 minute 0-59
2 hour 0-23
3 day of month 1-31
4 month 1-12, or a three-letter month name
5 day of week 0-7, or a three-letter weekday name
6, when present second 0-59

With a five-field expression, occurrences fall at minute level, and the matching datetimes that are returned have a second value of zero. With a six-field expression, the final field is evaluated and matching can advance one second at a time. For example:

base = datetime(2012, 4, 6, 13, 26, 10)
itr = croniter('*/1 * * * * *', base)
itr.get_next(datetime)  # datetime(2012, 4, 6, 13, 26, 11)

An expression with a field count other than five or six must raise ValueError.

Field Syntax That Is Supported

Each field supports the forms described below. Valid forms may be combined within a single field, with the alternatives separated by commas.

Wildcard

* permits every value in the valid range of the field.

Literal Values

A numeric literal permits that value, provided the value is in range.

The month field also accepts these three-letter names:

jan feb mar apr may jun jul aug sep oct nov dec

The day-of-week field also accepts the following:

sun mon tue wed thu fri sat

The lowercase spellings given above must be accepted. Looking up names may be done case-insensitively.

Inclusive Ranges

a-b permits every value from a through b, inclusive. In fields that accept names, the endpoints of a range may be valid names, so month ranges such as jan-jun are supported.

Ranges do not wrap around. If the start exceeds the end — as in the day-of-month range 5-1 — construction must raise ValueError.

Steps

*/n, with n a positive integer, permits values v from the range of that field for which:

v % n == 0

This modulo rule holds for every field, rather than counting from the field's minimum. As a result:

  • In the minute field, */5 permits 0, 5, 10, ... 55.
  • In the hour field, */3 permits 0, 3, 6, ... 21.
  • In day of month, */2 includes day 22.
  • In day of month, */3 includes day 27 and, when appropriate, proceeds from day 27 in February to day 3 in March.
  • In the sixth field, */1 permits every second.

For a stepped range a-b/n, the same divisibility rule is applied within the inclusive range.

Alternatives Separated by Commas

A field written as comma-separated alternatives matches any of the listed alternatives. For example, sat,sun matches either Saturday or Sunday. A list may likewise contain numeric values, names, ranges, or step forms supported for that field.

Invalid Values and Names
  • A numeric value that lies outside the accepted range of its field must raise ValueError.
  • A range given in descending order must raise ValueError.
  • A named token that cannot be resolved raises KeyError. For example, constructing croniter('* * * janu-jun *') must raise KeyError, because janu is not a valid month abbreviation.

Only the field forms described above are required; extended cron operators that are unrelated are outside the scope of this task.

Semantics of Matching

Field restrictions are combined using logical AND, except for the relationship between the two day fields: the minute, hour, month, optional second, and the applicable day rule must all match.

Mapping of Day-of-Week Values

Day-of-week values follow standard cron numbering and correspond to datetime.isoweekday() in the following way:

  • Both 0 and 7 mean Sunday (isoweekday() == 7).
  • 1 through 6 mean Monday through Saturday (isoweekday() == 1 through 6).
  • The names sun through sat obey the same mapping.

For example, 0 0 * * 7 produces occurrences on Sunday, and 0 0 * * sat produces occurrences on Saturday.

Day of Month versus Day of Week

When both the day-of-month and the day-of-week fields are restricted instead of being a plain *, cron OR semantics apply: a date is eligible if either restriction matches. The two must not be treated as an AND condition.

For example, starting from 2010-01-25 00:00, the expression 0 0 1 * wed produces the following first three forward occurrences:

  1. 2010-01-27 00:00 because it is Wednesday;
  2. 2010-02-01 00:00 because it is the first day of the month;
  3. 2010-02-03 00:00 because it is Wednesday.

When one day field is * and the other one is restricted, the restricted field determines the eligible dates. When both are *, every calendar date that is otherwise valid is eligible.

Calendar Correctness

Iteration must honor the actual lengths of months and Gregorian leap years. February 29 must be available in leap years such as 1996 and 2000, and transitions between months must never produce an invalid date. Picking the last eligible day while moving backward must be done using the actual last day of that month.

Iterating Forward

get_next(ret_type=float)

This method returns the earliest matching occurrence strictly after the iterator's current position and then makes that occurrence the new current position. Even if the current position is itself a match, it is not returned by get_next.

The rollover behavior that is required includes the following examples:

  • Starting from 2010-01-23 12:18, */1 * * * * next returns 12:19; minute iteration rolls from 12:59 to 13:00.
  • Starting from 2010-01-24 12:02, 0 */3 * * * next returns 2010-01-24 15:00, and it eventually rolls from hour 21 to 2010-01-25 00:00.
  • Starting from 2010-01-25 00:00, 0 0 1 * * advances through the first day of successive months and crosses over into the next year correctly.
  • Starting from 2012-01-01 00:00, 0 * * 3 * first returns 2012-03-01 00:00, followed by 01:00, 02:00, and so on within March.

Iterating Backward

get_prev(ret_type=float)

This method returns the latest matching occurrence strictly before the iterator's current position and then makes that occurrence the new current position. Even if the current position is itself a match, it is not returned by get_prev.

Whenever a more-significant field is moved backward, the less-significant matching fields must be maximized. In particular, finer-grained wildcard fields roll to their latest valid values instead of keeping the corresponding components from the base time. In a five-field expression, this means minute 59, hour 23, and the actual last day of a month in cases where those wildcard fields are applicable. In a six-field expression, the seconds field is part of the same latest-match rule.

The results that follow are required:

  • For * 10 * * * starting from 2012-06-23 17:41, the previous occurrence is 2012-06-23 10:59.
  • For * * 26 * * starting from 2012-06-27 00:15, the previous occurrence is 2012-06-26 23:59.
  • For * * * 5 * starting from 2012-06-18 00:15, the previous occurrence is 2012-05-31 23:59.
  • For * * * * sat starting from 2012-05-13 18:48, the previous occurrence is 2012-05-12 23:59.
  • For 0 0 22 * * starting from 2012-03-15 00:00, the previous occurrence is 2012-02-22 00:00.
  • For 5 0 */2 * * starting from 2012-02-24 00:00, the previous occurrence is 2012-02-22 00:05.

With repeated calls, iteration must continue backward in descending chronological order. For example, starting from 2010-08-25 15:56, the expression 0 0 * * sat,sun yields midnight on August 22, then August 21, then August 15.

The Current Position

get_current(ret_type=float)

This method returns the iterator's current position without changing it. Immediately after construction, this is the base time that was supplied; after a successful get_next or get_prev, it is that method's most recently returned occurrence.

For example:

base = datetime(2012, 9, 25, 11, 24)
itr = croniter('* * * * *', base)
itr.get_current(datetime)  # datetime(2012, 9, 25, 11, 24)

At minimum, in this case immediately after construction, all of the year, month, day, hour, and minute components must remain equal to the base.

What to Deliver

Deliver a croniter package whose public package namespace exposes the croniter class together with all of the constructor and method behavior described above. Neither replace the class with a different import path nor require callers to import an internal module.

Task Description

Goal

Repair the range/step expansion of cron fields in croniter while keeping the library's public parsing, iteration, calendar, and return-type behavior intact. A stepped field must be anchored at the start of the range it selects, rather than choosing values according to their absolute divisibility by the step.

Public interface

Both of the following public import forms must continue to make the croniter class available:

from croniter import croniter
from croniter.croniter import croniter

An iterator is constructed from a cron expression together with an optional base time:

itr = croniter(expr, base_datetime)
itr = croniter(expr)

A base that is supplied may be either a datetime.datetime or the supported numeric timestamp form. When no base is given, construction is valid and the iterator begins from the current time.

The public methods for position handling are:

itr.get_next(ret_type=float)
itr.get_prev(ret_type=float)
itr.get_current(ret_type=float)
  • get_next returns the first matching moment strictly after the iterator's current position and moves the position to that result. Further calls continue forward from the preceding result.
  • get_prev returns the first matching moment strictly before the current position and moves the position to that result. Further calls continue backward from the preceding result.
  • Calls that omit ret_type return a numeric timestamp, and the iterator is still advanced for get_next or get_prev.
  • Passing datetime.datetime as ret_type makes the call return a datetime.datetime.
  • get_current reports the current position without advancing it or changing it in any other way. Immediately after construction, get_current(datetime) represents the base time that was supplied; after iteration has occurred, it represents the most recently returned position.
  • Only float and datetime.datetime are accepted as return types by get_next and get_prev. A type that is not supported, such as str, raises TypeError.

Cron expression forms and their order

Only expressions with exactly five or six whitespace-separated fields are accepted.

The form with five fields is:

minute hour day-of-month month day-of-week

The six-field form appends seconds as the trailing sixth field:

minute hour day-of-month month day-of-week second

The nominal ranges of the fields are:

Field Values
minute 0-59
hour 0-23
day-of-month 1-31, bounded by the actual month length
month 1-12
day-of-week 0-6, where 7 is also accepted as an alias for Sunday
second 0-59

Expressions with five fields work at minute granularity, and every matching result has a second value of zero. Six-field expressions activate second-level iteration. As an example:

base = datetime(2012, 4, 6, 13, 26, 10)
croniter('*/1 * * * * *', base).get_next(datetime)
# datetime(2012, 4, 6, 13, 26, 11)

An expression whose field count is anything other than five or six raises ValueError.

Supported field syntax

Within its valid bounds, each field supports the following forms:

  • *, matching every valid value.
  • A fixed numeric value, for example 0.
  • A comma-separated list of alternatives like sat,sun; a value matches when it matches any of the listed alternatives.
  • An inclusive range of the form A-B.
  • A wildcard step of the form */N.
  • An inclusive bounded stepped range of the form A-B/N.

N is a positive integer step. The bounds of a range are inclusive; however, the upper bound shows up in a stepped expansion only when repeated addition of the step reaches it. A descending range like 5-1 is invalid and raises ValueError. Numeric values beyond a field's accepted bounds are invalid.

In the month field, the three-letter month abbreviations jan, feb, mar, apr, may, jun, jul, aug, sep, oct, nov, and dec are accepted. In the day-of-week field, the names sun, mon, tue, wed, thu, fri, and sat are accepted. Such names may serve both as values and as range endpoints; the canonical lowercase spellings must be accepted, and resolving names is case-insensitive. A name that cannot be resolved raises KeyError; for example, * * * janu-jun * must not be silently accepted as a month range.

Required semantics for stepped ranges

In a field whose minimum and maximum are L and H, the wildcard step */N expands to:

L, L + N, L + 2N, ...

with every generated value no greater than H included. The minimum of the field itself is always included.

For a bounded stepped range A-B/N, expansion begins at A and produces exactly the values A + k*N for integers k >= 0 as long as those values are no greater than B. It must not, instead, select the values within A-B whose absolute values happen to be divisible by N. The same rule applies consistently to minute, hour, day-of-month, month, day-of-week, and the optional second field.

Specifically:

  • The minimum of day-of-month is 1. Hence */3 selects 1, 4, 7, 10, ... within each calendar month. For each month the sequence restarts from 1, and only dates that actually exist in that month can match.
  • Within day-of-month, */2 selects 1, 3, 5, ..., not 2, 4, 6, ....
  • The expansion of 1-9/2 is 1, 3, 5, 7, 9.
  • For wildcard steps, a field whose minimum is zero stays anchored at zero; for example, minute */5 selects 0, 5, 10, ..., 55.

Plain wildcards, fixed values, unstepped ranges, and comma-separated alternatives must keep their established meanings.

Day-of-week values and day matching

Day-of-week numbering uses cron conventions and maps onto Python calendar results as follows:

  • 0 and 7 stand for Sunday (datetime.isoweekday() == 7).
  • 1 through 6 stand for Monday through Saturday (datetime.isoweekday() == 1 through 6).
  • The weekday names map onto the same values; for example, wed means 3 and sat means 6.

Day-of-month and day-of-week follow cron OR semantics:

  • When both fields are restricted rather than *, a date is eligible if either the day-of-month constraint or the day-of-week constraint matches.
  • When one of the two fields is *, the other field, which is restricted, supplies the effective day constraint; the wildcard does not cause every date to match independently of that restriction.
  • When both are *, every otherwise valid calendar day is eligible.

Accordingly, starting at 2010-01-25, 0 0 1 * wed produces 2010-01-27, then 2010-02-01, then 2010-02-03: each result satisfies the first-of-month condition, the Wednesday condition, or both. Lists such as sat,sun match either of the listed weekdays in both forward and backward iteration.

Calendar behavior and boundaries

Iteration must respect real Gregorian calendar month lengths and must cross minute, hour, day, month, and year boundaries in either direction. Gregorian leap-year rules apply: a year divisible by 4 is a leap year except for century years not divisible by 400. Therefore both 1996 and 2000 contain February 29, whereas a century such as 1900 does not.

For 0 0 * * *:

  • Beginning at 1996-02-27 yields February 28 and then February 29.
  • Beginning at 2000-02-27 00:00 likewise yields February 28 and then February 29.

Backward iteration must select the latest matching moment before the current position, including when that requires crossing a calendar boundary. For instance, from 2010-08-25 15:00, */1 * * * * returns 2010-08-25 14:59, while from midnight it returns 23:59 on the previous day. From 2012-03-15, 0 0 22 * * returns 2012-02-22 00:00.

get_prev(ret_type=None)
get_current(ret_type=None)

If ret_type is omitted, these methods fall back to the constructor's ret_type, whose default is float.

  • get_next returns the first occurrence that matches strictly after cur, and it advances cur to that occurrence.
  • get_prev returns the first occurrence that matches strictly before cur, and it moves cur to that occurrence.
  • get_current returns the cursor in its current state without advancing it. Immediately after construction, a request for datetime therefore returns the start instant that was supplied.
  • A float result is a numeric timestamp. Supplying the datetime class requests a datetime result.
  • Occurrence lookups accept only the supported numeric-timestamp or datetime return classes; requesting an unsupported type such as str raises TypeError.

Consecutive directional calls return occurrences that are distinct and adjacent. Reversing direction does not repeat the current occurrence: once several schedule points have been advanced through, backward calls retrace the preceding points in reverse order. The existing forward iterable and forward/backward generator behavior must keep using the same cursor and return-type rules.

Format of Cron Expressions

Field Ordering and Numeric Ranges

Expressions with five fields have minute granularity:

minute hour day-of-month month day-of-week

In six-field expressions the seconds field comes last rather than first:

minute hour day-of-month month day-of-week second

The numeric domain of each field is:

Field Values
minute 0 through 59
hour 0 through 23
day-of-month 1 through 31, plus l for the last day of the month
month 1 through 12
day-of-week 0 through 6, with 7 also accepted as Sunday
second 0 through 59

Schedules with five fields return occurrence times whose second is zero. Schedules with six fields operate at one-second granularity. In either form, the occurrences that are generated have no sub-second component. For example, starting from 13:26:36, the six-field expression * * * * * */15 yields as its next occurrences 13:26:45, 13:27:00, and 13:27:15.

Supported Syntax Within Fields

Each field supports:

  • the wildcard *
  • integer values, including zero-padded forms such as 00
  • lists separated by commas
  • inclusive ranges written as A-B
  • wildcard steps written as */N
  • range steps written as A-B/N
  • base steps written as A/N

A wildcard step begins at the field's minimum. A range step begins at A and stops at B. A base step begins at A and continues by N up through the field maximum. These anchors are fixed by the expression, not by the current cursor. Specifically:

  • 1-9/2 expands into 1,3,5,7,9.
  • In the hour field, 4/6 expands to 4,10,16,22.
  • In the hour field, 0/6 expands to 0,6,12,18.
  • In day-of-month, */3 is anchored at day 1 and restarts as 1,4,7,... in every month.
Weekday Names

The day-of-week field accepts three-letter weekday names as standalone values, as list members, and as range endpoints. Matching of names supports the existing lowercase forms according to this mapping:

sun=0, mon=1, tue=2, wed=3, thu=4, fri=5, sat=6

So sat,sun forms a weekend list, the numeric value 7 is another spelling of Sunday, and sun-thu includes Sunday through Thursday. The existing standard parsing of three-letter month names must likewise remain unchanged. Alphabetic names that are unknown are not accepted.

Last Day of a Month

Within the day-of-month field, the token l stands for the actual final calendar day of the applicable month. That value must be recomputed for every month — February in leap years included — during both forward and backward traversal.

On that same last day, reverse lookup may still find an earlier matching time. For example, when the minute and hour fields are unrestricted on a last-day schedule, backward calls made shortly after midnight on the last day first return the preceding minutes of that same day; once those are exhausted, traversal moves on to the real final day of the preceding month. Just as with every lookup, an occurrence equal to the current cursor is excluded.

Combining Day-of-Month and Day-of-Week

Each of the non-day fields must match its respective constraint. The relationship between day-of-month and day-of-week works as follows.

OR Behavior by Default

When day_or=True — which also covers the case where the argument is omitted — and both day fields are restricted instead of *, a date matches whenever either the day-of-month constraint or the day-of-week constraint matches. This is standard cron behavior as it exists today.

For example, from 2010-01-25 00:00:00, this schedule:

croniter('0 0 1 * wed', start)

produces 2010-01-27, 2010-02-01, and 2010-02-03 as its first three dates: Wednesdays as well as first days of a month are both eligible.

Opting In to AND Behavior

When day_or=False and both day fields are restricted, a date matches only if both the day-of-month constraint and the day-of-week constraint match. This rule applies consistently to forward lookup, to backward lookup, and to every supported form of those two fields.

For example:

from datetime import datetime
from croniter import croniter

start = datetime(2010, 1, 25, 0, 0, 0)
itr = croniter('0 0 1 * mon', start, day_or=False)

Successive calls to itr.get_next(datetime) must return:

  1. 2010-02-01 00:00:00
  2. 2010-03-01 00:00:00
  3. 2010-11-01 00:00:00

Months in between get skipped because their first day is not Monday.

Interaction with Wildcards

The day_or option has an effect on matching only when both day fields are syntactically constrained. When day-of-month is * and day-of-week is restricted, day-of-week is the only field constraining the date. When day-of-week is * and day-of-month is restricted, day-of-month is the only constraining field. When both are *, the date is constrained by neither. This behavior is the same for either day_or value.

Semantics of Traversal and Calendar Handling

  • Iteration in both the forward and the backward direction must roll correctly over minute, hour, day, month, and year boundaries.
  • The rules for Gregorian month lengths and leap years apply; this includes leap days in years such as 1996 and 2000.
  • When a constrained boundary is crossed, reverse traversal resolves the unrestricted finer fields to the latest valid values. Examples are minute 59 when entering a constrained hour, hour 23 together with minute 59 when entering a constrained day, and the actual final day at 23:59 when entering a constrained month.
  • In either direction, lists, ranges, and steps stand for the same fixed set of matching values.

Timezone and Daylight-Saving Handling

  • When the start is a naive datetime, the datetime results are naive too.
  • When the start is timezone-aware, the results are timezone-aware and lie in the same timezone.
  • At a spring-forward transition, local wall times that do not exist are skipped.
  • At a fall-back transition, both real instants represented by an ambiguous local wall time are emitted — each with its respective UTC offset — in chronological order.
  • Across either transition, backward traversal returns the exact reverse sequence of valid scheduled instants.

The class-level helper shown below stays directly callable on croniter:

croniter._timedelta_to_seconds(td)

It returns the complete duration that a timedelta represents, in seconds, including the day, second, and microsecond components.

Invalid Expressions and Dates That Cannot Be Resolved

For malformed expressions, construction must raise ValueError (or an existing specialized ValueError subtype). Malformed cases include:

  • a field count that is not exactly five or six
  • descending ranges, such as 5-1
  • field values that are negative
  • values that fall outside a field's accepted range
  • bare alphabetic values placed in fields that do not accept them
  • alphabetic names that are unknown, or named range endpoints that are unknown

When no forward occurrence can be found — for a schedule such as a day-of-month of 31 restricted to February — lookup raises the top-level CroniterBadDateError with the exact message:

failed to find next date

The corresponding backward failure stays CroniterBadDateError, carrying the message failed to find prev date.

Requirements for Compatibility

  • Leaving day_or out, or passing day_or=True explicitly, must keep all prior scheduling results and public behavior intact.
  • Using day_or=False changes only the conjunction applied when both day fields are constrained. Expression grammar, time resolution, cursor exclusivity, return conversion, calendar handling, and timezone behavior must not be altered by it.
  • Constructor and method calls that already exist and do not use day_or must remain source-compatible.

Fields and their granularity

Expressions with five fields use this order:

minute hour day-of-month month day-of-week

Six-field expressions put seconds at the end, not at the beginning:

minute hour day-of-month month day-of-week second

These are the valid numeric ranges:

Field Range
minute 0-59
hour 0-23
day-of-month 1-31
month 1-12
day-of-week 0-7 (0 and 7 both mean Sunday)
second 0-59

An expression with five fields works at minute granularity, and second 0 holds for every result. An expression with six fields works at second granularity. The schedule occurrences that are produced have no residual microseconds.

Field syntax that is supported

Fields support the following:

  • * meaning all values;
  • integer values, including zero-padded values such as 00;
  • lists separated by commas;
  • ranges A-B that are inclusive;
  • wildcard steps */N;
  • ranges with steps A-B/N;
  • steps from a base A/N.

For */N, step expansion begins at the field minimum; for A-B/N, it begins at A; and for A/N, it begins at A. A base step continues through the maximum of that field. Consequently:

  • for the minute field, 1-9/2 means 1,3,5,7,9;
  • for the hour field, 4/6 means 4,10,16,22;
  • for the hour field, 0/6 means 0,6,12,18;
  • for the day-of-month field, */3 is anchored at day 1 and restarts from day 1 in every month.

Values from lists and ranges are visited in sorted schedule order. When moving forward or backward across day, month, and year boundaries, this ordering must remain correct, including for expressions with several allowed months or several allowed days.

The month field recognizes the three-letter lowercase names jan through dec. sun, mon, tue, wed, thu, fri, and sat are recognized by the day-of-week field, both as individual/list values and as range endpoints. The day fields

When day-of-month and day-of-week are both restricted:

  • the default day_or=True applies cron's logical OR behavior, so a date is eligible when either one of the fields matches;
  • day_or=False applies logical AND, meaning both fields must match.

As an example, with day_or=False, the expression 0 0 1 * mon, when starting after 2010-01-25, returns 2010-02-01, 2010-03-01, and then 2010-11-01. If either day field is *, the date is constrained by only the other field, the restricted one; the wildcard must not produce a side of the OR that is always true.

The day-of-month token l, written in lowercase, means the actual last day of the month that applies. In both directions, it must be recomputed for every month (for example, September 30, October 31, and November 30). Calendar and traversal behavior

Iteration follows the month lengths of the Gregorian calendar and the rules for leap years — February 29 in leap years included — and rolls correctly across day, month, and year boundaries in either direction.

During a backward lookup, fields that are unrestricted and finer than a restricted field that was newly selected resolve to the latest of their valid values. Included here are minute 59, hour 23, and the final valid day of the selected month. Datetime and timezone behavior

  • When the start is a naive datetime, the results are naive datetimes.
  • A timezone-aware start produces timezone-aware results in the same timezone, each returned instant carrying the UTC offset appropriate to it.
  • Cron matching takes valid local wall-clock occurrences as its basis. A daily or otherwise wall-time-based schedule must not be shifted by offset transitions away from its requested local hour.
  • In a spring-forward gap, local times that match but do not exist are skipped. This holds in both forward and backward traversal.
  • In a fall-back fold, each wall time that matches and is ambiguous represents two distinct instants with different UTC offsets. While moving forward, both occurrences must be returned in chronological order; while moving backward, the exact reverse sequence must be returned.

For example, with Europe/Athens and */30 * * * *, forward iteration starting from local 2013-10-27 02:00 traverses the fall-back fold as follows:

2013-10-27 03:00 +03:00
2013-10-27 03:30 +03:00
2013-10-27 03:00 +02:00
2013-10-27 03:30 +02:00
2013-10-27 04:00 +02:00
2013-10-27 04:30 +02:00

Backward iteration from local 05:00 returns that sequence reversed. Across the Athens spring-forward gap, when the same expression starts at local 2013-03-31 01:00, it returns:

2013-03-31 01:30 +02:00
2013-03-31 02:00 +02:00
2013-03-31 02:30 +02:00
2013-03-31 04:00 +03:00
2013-03-31 04:30 +03:00

Backward iteration from local 05:00 returns the reverse sequence once more, and the 03:xx times that do not exist are absent.

Europe/Warsaw DST results that are required

The starts and expected values that follow use:

from datetime import datetime
import pytz

tz = pytz.timezone('Europe/Warsaw')

Spring forward

With the daily expression 0 0 * * *:

  • Starting from tz.localize(datetime(2017, 3, 26)), the next result is tz.localize(datetime(2017, 3, 27)).

With the hourly expression 0 * * * *:

  • Starting from tz.localize(datetime(2017, 3, 26, 1)), the next result is tz.localize(datetime(2017, 3, 26, 3)); 02:00, which does not exist, is skipped.
  • Immediately afterward, get_current(datetime) returns that identical 03:00 value.
Fall back

With the daily expression 0 0 * * *:

  • Starting from tz.localize(datetime(2017, 10, 29)), the next result is tz.localize(datetime(2017, 10, 30)).

With the hourly expression 0 * * * *:

  • Starting from tz.localize(datetime(2017, 10, 29, 1, 59)), the naive wall-clock components of the next result are datetime(2017, 10, 29, 2). The comparison in this particular case is only of wall-clock components, because 02:00 is ambiguous.
  • Starting from tz.localize(datetime(2017, 10, 29, 2)), the next result is tz.localize(datetime(2017, 10, 29, 3)).
  • Starts at localized 03:00, 04:00, and 05:00 produce localized 04:00, 05:00, and 06:00, respectively.
