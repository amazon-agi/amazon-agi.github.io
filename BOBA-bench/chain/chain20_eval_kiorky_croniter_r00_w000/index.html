Goal

Implement a cron-expression iterator class named croniter in croniter/croniter.py, importable with:

from .croniter import croniter

Given a cron expression and a reference datetime, an instance must produce successive calendar moments matching that expression in either the forward or backward direction.

Public API

Constructor
croniter(expr, start_time=None)
  • expr is a cron-expression string in one of the supported formats below.
  • start_time is the initial reference point. It may be supplied as a datetime.
  • If start_time is omitted, the current time is used.
  • The instance is stateful: every returned occurrence becomes the reference point for the next call.
Forward iteration
get_next(ret_type=float)

Return the earliest matching moment strictly after the instance's current reference point, then update the current reference point to that result.

Backward iteration
get_prev(ret_type=float)

Return the latest matching moment strictly before the instance's current reference point, then update the current reference point to that result.

Consecutive calls therefore return successive distinct occurrences. The state update also applies if callers alternate between forward and backward calls.

Return types

Both iteration methods support:

  • float (the default): return the matching moment as a numeric timestamp.
  • datetime: return the matching moment as a datetime object. The selector is the datetime class itself, for example itr.get_next(datetime).

An unsupported return selector, such as str, must raise TypeError.

Cron Expression Format

Fields use single-space delimiters. Exactly two layouts are supported:

  • 5 fields: minute hour day-of-month month day-of-week
  • 6 fields: second minute hour day-of-month month day-of-week

The six-field layout enables second-level granularity. Any other field count is invalid and must raise ValueError.

Field syntax

Each field supports:

  • * — every valid value in the field.
  • A single integer.
  • */n — values selected by a wildcard step.
  • a-b — an inclusive, non-wrapping range.
  • Comma-separated lists combining supported values, steps, and ranges, such as sat,sun.

A range whose start is greater than its end, such as the day-of-month range in * * 5-1 * *, must raise ValueError.

Wildcard-step semantics

A wildcard step is anchored at zero and then restricted to the field's valid range: a value v selected by */n matches exactly when v % n == 0. It is not calculated by taking the field minimum and repeatedly adding n.

Examples:

  • Minute */5 selects 0, 5, 10, ..., 55.
  • Hour */3 selects 0, 3, 6, ..., 21.
  • Day-of-month */3 selects 3, 6, 9, ..., 30, not 1, 4, 7, ..., 31.
  • Day-of-month */2 selects the even days 2, 4, 6, ..., 30.

Only selected values that actually exist in the current calendar period can match. Thus a selected day 30 is skipped in a February that does not contain it.

Field ranges
  • second: 0–59
  • minute: 0–59
  • hour: 0–23
  • day-of-month: 1–31, subject to the actual length of the selected month
  • month: 1–12
  • day-of-week: 0–7

Values outside the corresponding valid range are invalid.

Named months and weekdays

Three-letter lowercase weekday abbreviations are accepted: sun, mon, tue, wed, thu, fri, and sat.

Three-letter lowercase month abbreviations are accepted: jan, feb, mar, apr, may, jun, jul, aug, sep, oct, nov, and dec. Names may be used as range endpoints, for example jan-jun.

Named tokens are resolved as complete abbreviations. If a token cannot be resolved, construction propagates KeyError; for example, * * * janu-jun * is invalid because janu is not a recognized month name.

Day-of-week numbering

Cron weekday numbering is:

  • 0 or 7: Sunday
  • 1: Monday
  • 2: Tuesday
  • 3: Wednesday
  • 4: Thursday
  • 5: Friday
  • 6: Saturday

The names map to the same values. In terms of datetime.isoweekday(), a Saturday result has value 6 and a Sunday result has value 7.

Combining day-of-month and day-of-week

The two day fields use standard cron OR behavior:

  • If both day-of-month and day-of-week are restricted (neither is *), a date matches when either field matches.
  • If exactly one of the two fields is *, only the restricted field constrains the date.
  • If both are *, every otherwise valid date is eligible.

For example, 0 0 1 * wed matches midnight on each Wednesday as well as midnight on the first day of each month.

Time and Calendar Behavior

  • Five-field expressions operate at minute granularity. Returned occurrences have second == 0.
  • Six-field expressions operate at second granularity.
  • The starting/reference moment itself is never returned by either direction, even if it matches.
  • Iteration must carry and borrow correctly across minutes, hours, days, months, and years.
  • Month lengths must be respected; impossible dates in a month are skipped rather than produced.
  • Leap years must follow Gregorian rules, including February 29 in years such as 1996 and 2000.
  • If the current reference lies outside an allowed month or other allowed calendar period, iteration must jump in the requested direction to the nearest eligible period and select its nearest matching moment.

The implementation must work under Python 3 and remain Python 2 compatible where relevant.

Public API

Constructor

Cron Expression Layout

A five-field expression has this layout:

minute hour day-of-month month day-of-week

A six-field expression appends a seconds field:

minute hour day-of-month month day-of-week second

The valid values are:

2 hour 0-23
3 day of month 1-31
4 month 1-12, or a three-letter month name
5 day of week 0-7, or a three-letter weekday name

base = datetime(2012, 4, 6, 13, 26, 10)
itr = croniter('*/1 * * * * *', base)
itr.get_next(datetime)  # datetime(2012, 4, 6, 13, 26, 11)

Any expression containing a number of fields other than five or six must raise ValueError.

Supported Field Syntax

Each field supports the following forms. Comma-separated alternatives may combine valid forms in one field.

Wildcard

* permits every value in the field's valid range.

Literal value

A numeric literal permits that value, provided it is in range.

The month field also accepts the three-letter names:

jan feb mar apr may jun jul aug sep oct nov dec

The day-of-week field also accepts:

sun mon tue wed thu fri sat

The lowercase spellings above must be accepted. Name lookup may be case-insensitive.

Inclusive range

a-b permits every value from a through b, inclusive. Range endpoints may use valid names in named fields, so month ranges such as jan-jun are supported.

Ranges do not wrap. If the start exceeds the end, as in day-of-month range 5-1, construction must raise ValueError.

Step

*/n, for a positive integer n, permits values v in that field's range for which:

v % n == 0

This modulo rule applies to every field, rather than counting from the field's minimum. Thus:

  • */5 in the minute field permits 0, 5, 10, ... 55.
  • */3 in the hour field permits 0, 3, 6, ... 21.
  • */2 in day of month includes day 22.
  • */3 in day of month includes day 27 and proceeds from day 27 in February to day 3 in March when appropriate.
  • */1 in the sixth field permits every second.

A stepped range a-b/n applies the same divisibility rule within the inclusive range.

Comma-separated alternatives

A comma-separated field matches any listed alternative. For example, sat,sun matches either Saturday or Sunday. Lists may likewise contain numeric values, names, ranges, or step forms supported for that field.

Invalid values and names
  • A numeric value outside its field's accepted range must raise ValueError.
  • A descending range must raise ValueError.
  • An unresolvable named token raises KeyError. For example, constructing croniter('* * * janu-jun *') must raise KeyError because janu is not a valid month abbreviation.

Only the field forms described above are required; unrelated extended cron operators are outside this task's scope.

Matching Semantics

Except for the relationship between the two day fields, field restrictions are combined with logical AND: the minute, hour, month, optional second, and applicable day rule must all match.

Day of week mapping

Day-of-week values use standard cron numbering and correspond to datetime.isoweekday() as follows:

  • 0 and 7 both mean Sunday (isoweekday() == 7).
  • 1 through 6 mean Monday through Saturday (isoweekday() == 1 through 6).
  • The names sun through sat follow the same mapping.

For example, 0 0 * * 7 produces Sunday occurrences, and 0 0 * * sat produces Saturday occurrences.

Day of month versus day of week

When both day-of-month and day-of-week are restricted rather than plain *, cron OR semantics apply: a date is eligible if either restriction matches. They must not be treated as an AND condition.

For example, starting from 2010-01-25 00:00, expression 0 0 1 * wed produces these first three forward occurrences:

  1. 2010-01-27 00:00 because it is Wednesday;
  2. 2010-02-01 00:00 because it is the first day of the month;
  3. 2010-02-03 00:00 because it is Wednesday.

If one day field is * and the other is restricted, the restricted field determines eligible dates. If both are *, every otherwise valid calendar date is eligible.

Forward Iteration

  • From 2010-01-24 12:02, 0 */3 * * * next returns 2010-01-24 15:00 and eventually rolls from hour 21 to 2010-01-25 00:00.
  • From 2010-01-25 00:00, 0 0 1 * * advances through the first day of successive months and crosses into the next year correctly.
  • From 2012-01-01 00:00, 0 * * 3 * first returns 2012-03-01 00:00, followed by 01:00, 02:00, and so on within March.

returns the iterator's current position without changing it. Immediately after construction this is the supplied base time; after a successful get_next or get_prev, it is that method's most recently returned occurrence.

For example:

base = datetime(2012, 9, 25, 11, 24)

At minimum, all year, month, day, hour, and minute components must remain equal to the base in this immediate-after-construction case.

Numeric 7 is also Sunday. For example, sat,sun selects the weekend and sun-thu includes Sunday through Thursday. Lowercase three-letter month names jan through dec are likewise valid in the month field.

In the day-of-month field, l means the actual last calendar day of each applicable month. It must be recomputed for every month, including February in leap years, and in both navigation directions. Strict cursor exclusion still applies: from 2009-12-31 20:00, 0 0 l * * previously yields midnight on December 31, while from exactly 2009-12-31 00:00 it previously yields 2009-11-30 00:00. With unrestricted finer fields, backward traversal may return multiple earlier times on the same last day before moving to the preceding month's last day.

Day-of-month and day-of-week combination

When both day-of-month and day-of-week are restricted:

  • the default day_or=True applies logical OR, matching a date that satisfies either field;
  • day_or=False applies logical AND, requiring both fields to match.

For example, with the default mode, 0 0 1 * wed after 2010-01-25 yields January 27, February 1, and February 3. With day_or=False, 0 0 1 * mon after 2010-01-25 yields 2010-02-01, 2010-03-01, and 2010-11-01.

If either day field is *, only the restricted day field constrains the date, regardless of this combination choice.

Navigation and cursor semantics

get_next(...) returns the first matching instant strictly after the current cursor. get_prev(...) returns the first matching instant strictly before it. A cursor that itself matches the expression must not be returned.

Each returned occurrence becomes the instance's new cursor. Repeated calls therefore return adjacent, distinct occurrences. Changing direction retraces the schedule without repeating the current occurrence: if forward calls reach occurrences A, B, and C, the following backward calls return B and then A.

Backward calculation must choose the latest allowed values for unrestricted finer fields when crossing a restricted boundary. Examples include:

  • * 10 * * * before 2012-06-23 17:41 yields 2012-06-23 10:59;
  • * * 26 * * before 2012-06-27 00:15 yields 2012-06-26 23:59;
  • * * * 5 * before 2012-06-18 00:15 yields 2012-05-31 23:59;
  • * * * * sat before Sunday 2012-05-13 18:48 yields Saturday 2012-05-12 23:59.

Calendar behavior

Occurrence calculation follows Gregorian month lengths and leap-year rules, including leap years divisible by 400. Invalid calendar days are skipped in months where they do not exist. Navigation must roll correctly across day, month, and year boundaries in both directions.

If no occurrence exists for an impossible calendar schedule, date lookup must fail rather than return a nonmatching date. In particular, requesting the next occurrence of day 31 restricted to February, as in * * 31 2 *, raises the top-level CroniterBadDateError with exactly:

failed to find next date

Naive and timezone-aware datetimes

A naive datetime start produces naive datetime results. A timezone-aware start preserves that timezone in returned datetimes.

Traversal is chronological across daylight-saving transitions:

  • nonexistent local times in a spring-forward gap are skipped;
  • both real instants represented by an ambiguous fall-back local time are emitted, in chronological order and with their respective UTC offsets;
  • backward traversal emits the exact reverse chronological sequence.

For example, at 30-minute granularity in Europe/Athens, the spring-forward sequence passes from 2013-03-31 02:30 at UTC+02:00 directly to 04:00 at UTC+03:00. During fall-back it emits 03:00 and 03:30 first at UTC+03:00, then emits 03:00 and 03:30 at UTC+02:00 before proceeding to 04:00; reverse navigation returns this sequence in reverse.

Validation

Construction must reject malformed expressions with ValueError, including:

  • any field count other than five or six;
  • descending ranges such as 5-1;
  • negative values;
  • values outside the range of their field;
  • bare alphabetic values in fields that do not recognize them;
  • unknown alphabetic names or range endpoints, such as janu-jun.

Public API

The scheduler and its date-search exception must be importable from the top-level package:

from croniter import croniter, CroniterBadDateError

The constructor is:

croniter(expr_format, start_time=None, ret_type=float, day_or=True)
  • expr_format is a supported five- or six-field cron expression.
  • start_time may be a naive datetime, a timezone-aware datetime (including a value localized by pytz), or a numeric timestamp. If omitted, the current time is captured when that particular instance is constructed; it must not be a time captured earlier at import or function-definition time. Consequently, when the clock advances between two constructions, the later instance has a strictly greater numeric cur value.
  • ret_type sets the default result representation. Its normal default is float.
  • day_or controls how simultaneously restricted day-of-month and day-of-week fields are combined, as detailed below.

Every instance exposes cur, a comparable numeric cursor representing its current instant.

The public cursor methods are:

instance.get_next(ret_type=None)
instance.get_prev(ret_type=None)
instance.get_current(ret_type=None)

When a method's ret_type is omitted, it uses the constructor's ret_type, so with the normal constructor defaults these methods return numeric timestamps. Passing datetime requests a datetime result. The supported iteration result forms are numeric float timestamps and datetime values. An unsupported iteration request such as get_next(str) raises TypeError.

  • get_next returns the earliest matching occurrence strictly after the cursor, advances cur to it, and never returns the current occurrence itself.
  • get_prev returns the latest matching occurrence strictly before the cursor, advances cur to it, and likewise excludes the current occurrence.
  • get_current does not advance. Before any forward or backward call, get_current(datetime) reconstructs the supplied start datetime; after an iteration call, it returns that call's occurrence.
  • Consecutive calls return adjacent, distinct schedule occurrences. Changing direction retraces the schedule without repeating the current point. For example, after advancing through March 16, March 30, and April 16, the next backward result is March 30.

Cron expression format

Fields and granularity

Five-field expressions use this order:

minute hour day-of-month month day-of-week

Six-field expressions place seconds at the end, not the beginning:

minute hour day-of-month month day-of-week second

The valid numeric ranges are:

Field Range
minute 0-59
hour 0-23
day-of-month 1-31
month 1-12
day-of-week 0-7 (0 and 7 both mean Sunday)
second 0-59

A five-field expression operates at minute granularity and every result has second 0. A six-field expression operates at second granularity. Produced schedule occurrences have no residual microseconds.

Supported field syntax

Fields support:

  • * for all values;
  • integer values, including zero-padded values such as 00;
  • comma-separated lists;
  • inclusive ranges A-B;
  • wildcard steps */N;
  • stepped ranges A-B/N;
  • base steps A/N.

Step expansion begins at the field minimum for */N, at A for A-B/N, and at A for A/N; a base step continues through that field's maximum. Thus:

  • minute 1-9/2 means 1,3,5,7,9;
  • hour 4/6 means 4,10,16,22;
  • hour 0/6 means 0,6,12,18;
  • day-of-month */3 is anchored at day 1 and restarts from day 1 in every month.

List and range values are visited in sorted schedule order. This ordering must remain correct when moving forward or backward across day, month, and year boundaries, including expressions with several allowed months or several allowed days.

The month field recognizes the lowercase three-letter names jan through dec. The day-of-week field recognizes sun, mon, tue, wed, thu, fri, and sat, both as individual/list values and as range endpoints. They map to sun=0, mon=1, through sat=6; for example, sun-thu includes Sunday through Thursday.

Day fields

When both day-of-month and day-of-week are restricted:

  • the default day_or=True applies cron's logical OR behavior, so a date is eligible when either field matches;
  • day_or=False applies logical AND, so both fields must match.

For example, with day_or=False, expression 0 0 1 * mon starting after 2010-01-25 returns 2010-02-01, 2010-03-01, and then 2010-11-01. If either day field is *, only the other, restricted field constrains the date; the wildcard must not create an always-true side of the OR.

The lowercase day-of-month token l means the actual last day of the applicable month. It must be recomputed for every month in both directions (for example, September 30, October 31, and November 30). Reverse lookup excludes an exactly matching current instant, but it may return an earlier matching time on the same last day when finer fields are unrestricted. For example, immediately before 00:02 on a matching last day, an every-minute last-day schedule can return 00:01 and then 00:00 before moving to the preceding month's last day.

Calendar and traversal behavior

Iteration follows Gregorian month lengths and leap-year rules, including February 29 in leap years, and rolls correctly across day, month, and year boundaries in either direction.

On backward lookup, unrestricted fields finer than a newly selected restricted field resolve to their latest valid values. This includes minute 59, hour 23, and the final valid day of the selected month. As examples, looking backward from June into a schedule restricted to May can select May 31 at 23:59, and looking backward across an hour boundary can select minute 59.

Datetime and timezone behavior

  • A naive datetime start produces naive datetime results.
  • A timezone-aware start produces timezone-aware results in the same timezone, with the UTC offset appropriate to each returned instant.
  • Cron matching is based on valid local wall-clock occurrences. Offset transitions must not shift a daily or otherwise wall-time-based schedule away from its requested local hour.
  • During a spring-forward gap, matching local times that do not exist are skipped. This applies in both forward and backward traversal.
  • During a fall-back fold, each matching ambiguous wall time represents two distinct instants with different UTC offsets. Both occurrences must be returned in chronological order while moving forward; moving backward must return the exact reverse sequence.

For example, for Europe/Athens and */30 * * * *, forward iteration from local 2013-10-27 02:00 traverses the fall-back fold as:

2013-10-27 02:30 +03:00
2013-10-27 03:00 +03:00
2013-10-27 03:30 +03:00
2013-10-27 03:00 +02:00
2013-10-27 03:30 +02:00
2013-10-27 04:00 +02:00
2013-10-27 04:30 +02:00

Backward iteration from local 05:00 returns that sequence in reverse. Across the Athens spring-forward gap, the same expression starting at local 2013-03-31 01:00 returns:

2013-03-31 01:30 +02:00
2013-03-31 02:00 +02:00
2013-03-31 02:30 +02:00
2013-03-31 04:00 +03:00
2013-03-31 04:30 +03:00

Backward iteration from local 05:00 again returns the reverse sequence, with the nonexistent 03:xx times absent.

Required Europe/Warsaw DST results

The following starts and expected values use:

from datetime import datetime
import pytz

tz = pytz.timezone('Europe/Warsaw')
start = tz.localize(datetime(...))

In Warsaw on 2017-03-26, local time jumps from 01:59 (+01:00) to 03:00 (+02:00), so 02:xx does not exist. On 2017-10-29, time moves from 02:59 (+02:00) back to 02:00 (+01:00), so 02:xx occurs twice.

Spring forward

For daily expression 0 0 * * *:

  • From tz.localize(datetime(2017, 3, 26)), the next result is tz.localize(datetime(2017, 3, 27)).

For hourly expression 0 * * * *:

  • From tz.localize(datetime(2017, 3, 26, 1)), the next result is tz.localize(datetime(2017, 3, 26, 3)); the nonexistent 02:00 is skipped.
  • Immediately afterward, get_current(datetime) returns that identical 03:00 value.
Fall back

For daily expression 0 0 * * *:

  • From tz.localize(datetime(2017, 10, 29)), the next result is tz.localize(datetime(2017, 10, 30)).

For hourly expression 0 * * * *:

  • From tz.localize(datetime(2017, 10, 29, 1, 59)), the next result's naive wall-clock components are datetime(2017, 10, 29, 2). This particular comparison is only of wall-clock components because 02:00 is ambiguous.
  • From tz.localize(datetime(2017, 10, 29, 2)), the next result is tz.localize(datetime(2017, 10, 29, 3)).
  • Starts at localized 03:00, 04:00, and 05:00 produce localized 04:00, 05:00, and 06:00 respectively.

Except for the explicitly wall-clock-only ambiguous 02:00 comparison, expected aware datetimes require full equality, including timezone offset.
