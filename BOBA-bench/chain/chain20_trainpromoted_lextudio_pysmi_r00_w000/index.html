01 Separate MIB Parsing from PySNMP Code Generation 613 words · source specification

Task Specification: Separate MIB Parsing from PySNMP Code Generation

Overview

The codebase currently combines SMI MIB parsing and PySNMP Python-code generation into a single step performed by the parser. This task requires separating these two concerns into two distinct components: a parser that produces an intermediate representation of a MIB, and a code generator that consumes that representation to produce executable Python (PySNMP) code.

Required Public API

1. Parser

A parser class must remain importable and callable as:

from pysmi.parser.smiv2 import SmiV2Parser

SmiV2Parser must be instantiable with no arguments, i.e. SmiV2Parser().

It must expose a method:

parse(self, data)
  • data is a string containing the full text of a MIB module definition (SMIv1 or SMIv2 syntax).
  • parse must return an intermediate representation of the parsed MIB. This return value is not consumed directly by callers other than being passed straight into the code generator (see below). Its internal structure is unconstrained except that it must be accepted by the code generator described next.
2. PySNMP Code Generator

A new code-generator class must be importable as:

from pysmi.codegen.pysnmp import PySnmpCodeGen

PySnmpCodeGen must be instantiable with no arguments, i.e. PySnmpCodeGen().

It must expose a method:

genCode(self, parsedMib)

  • parsedMib is exactly the value returned by SmiV2Parser().parse(...).

  • genCode must return a 3-tuple, unpacked by callers as:

    thisMib, otherMibs, pycode = PySnmpCodeGen().genCode(SmiV2Parser().parse(mibText))

    where:

    • pycode is a string of Python source code. It must be valid enough to be passed to the builtin compile(pycode, 'test', 'exec') without error, and, when executed in a namespace containing a mibBuilder (an instance of pysnmp.smi.builder.MibBuilder) whose managed MIB objects can subsequently be exported and inspected, must reproduce the correct PySNMP MIB object definitions for the given MIB.
    • otherMibs is the collection of names of the other MIB modules referenced/imported by the parsed MIB (i.e. the imported-module information previously returned as the first element of the parser's old return value).
    • thisMib is a new value representing the identity/name of the MIB module being generated. It is unpacked by callers but its specific structure is not otherwise exercised.

Behavioral Requirements

The end-to-end behavior — parsing MIB text and then generating Python code — must be exactly equivalent to the previous single-step behavior, now split across the two calls:

Previous (single step):

otherMibs, pycode = SmiV2Parser().parse(mibText)

Required (two steps):

thisMib, otherMibs, pycode = PySnmpCodeGen().genCode(SmiV2Parser().parse(mibText))
  • SmiV2Parser().parse() must no longer produce Python code itself; that responsibility moves entirely to PySnmpCodeGen().genCode().
  • The generated pycode and the otherMibs value must remain equivalent to what the old single-step parse produced, for the same MIB text.
Supported MIB constructs

The parse-then-generate pipeline must correctly handle MIB modules containing at least the following constructs, producing PySNMP code that defines the corresponding objects correctly:

  • IMPORTS clauses (including well-formed multi-line imports from multiple foreign modules).
  • MODULE-IDENTITY
  • OBJECT-IDENTITY
  • OBJECT-TYPE (including scalar objects, tables/rows/columns, various syntaxes, constraints, indexes, defaults, etc.)
  • NOTIFICATION-TYPE
  • NOTIFICATION-GROUP
  • OBJECT-GROUP
  • MODULE-COMPLIANCE
  • AGENT-CAPABILITIES
  • TRAP-TYPE (SMIv1)
  • Type declarations (both SMIv1 and SMIv2 syntax).
  • Value declarations.

Both SMIv1 and SMIv2 style MIB modules must be parseable by SmiV2Parser.

Python 2 / Python 3 Compatibility

All code introduced or modified must run correctly under both Python 2 and Python 3 (the pipeline is exercised on both). Ensure the parser and code generator produce identical logical results across supported interpreter versions.

Constraints

  • Do not change the import path or constructor signature of SmiV2Parser.
  • The new PySnmpCodeGen must live at the module path pysmi.codegen.pysnmp.
  • The genCode return tuple order is fixed: (thisMib, otherMibs, pycode).

For an OBJECT-TYPE, getMaxAccess() on the loaded object must return the access level as a single lowercase token with hyphens removed. For example, a MIB MAX-ACCESS accessible-for-notify clause must yield the value 'accessiblefornotify'.

  • A MIB using SMIv1 NOTIFICATION-GROUP-style / SMIv1 index constructs must, when parsed with SmiV1CompatParser and code-generated, produce an object whose loaded Python class name is 'NotificationGroup'.

  • Compile via compile(pycode, 'test', 'exec').
  • Execute successfully in a namespace containing a pysnmp MibBuilder (from pysnmp.smi.builder import MibBuilder), registering the MIB objects so they can be retrieved and their getter methods (getRevisions, getDescription, getMaxAccess, and __class__.__name__) queried as described.

Summary of the public API the engineer must provide

  • pysmi.codegen.pysnmp.PySnmpCodeGen.genCode(parsedData, genTexts=False) — accept and honor the genTexts keyword.

Overview

You must change the genCode API used by the code-generation backends in the pysmi package, and introduce a new symbol-table code-generation backend. The changes affect how parsed MIB syntax trees are turned into output, how imported MIB dependencies are reported, and how symbol information is passed between generation passes.

Parser Output

pysmi.parser.smi.parserFactory returns a parser class. An instance's parse(text) method returns a sequence (indexable) of parse results. The first element (parse(text)[0]) is the abstract syntax tree (AST) for a single MIB module. Callers now select this first element explicitly before passing it to a code generator.

genCode Signature Change

Both code-generation backends expose a genCode method with the following signature:

genCode(self, ast, symbolTable, **options)
  • ast: a single MIB module AST (the first element of a parser's parse(...) output).
  • symbolTable: a dict mapping MIB module name (str) → that module's symbol table (the symbol-table object produced by the symbol-table backend, described below). It may be empty ({}) when no dependency symbol information is available/needed.
  • options: keyword options; the tests exercise genTexts=True.

genCode returns a 2-tuple (mibInfo, data) directly (NOT a list/sequence of such tuples — callers use the returned value without additional indexing).

For the pysnmp backend, data is a string of executable Python source code that, once compiled and executed in a context providing a mibBuilder, defines the MIB's managed objects.

For the symbol-table backend, data is that module's symbol table object (see below).

New Symbol-Table Backend

Add a class SymtableCodeGen in module pysmi.codegen.symtable, importable as:

from pysmi.codegen.symtable import SymtableCodeGen

It exposes genCode(self, ast, symbolTable, **options) with the same calling convention described above. Given a module AST (and an empty symbolTable dict), it returns (mibInfo, symtable) where:

  • mibInfo has a name attribute holding the MIB module's name (str).
  • symtable is the symbol table object for that module.

The symbol table produced here is intended to be fed back into subsequent genCode calls via the symbolTable argument, keyed by module name, e.g. { mibInfo.name: symtable }.

PySnmp Backend

PySnmpCodeGen remains importable as:

from pysmi.codegen.pysnmp import PySnmpCodeGen

Its genCode now takes the new (ast, symbolTable, **options) signature and returns a single (mibInfo, pycode) tuple.

When a module references types/objects imported from other MIBs, PySnmpCodeGen().genCode must be able to resolve those references using the symbolTable dict supplied by the caller (populated from SymtableCodeGen output of the imported modules). When invoked with an empty symbolTable on a module that does not require external symbol resolution, it must still produce valid code.

mibInfo Reported Imports

The mibInfo object returned by PySnmpCodeGen().genCode must expose an attribute:

  • imported: a tuple of the names of the MIB modules that the compiled module imports from, containing only real external MIB module names and excluding synthetic/base ASN.1 pseudo-modules. For a module importing from SNMP-FRAMEWORK-MIB and SNMPv2-SMI, this tuple is exactly ('SNMP-FRAMEWORK-MIB', 'SNMPv2-SMI'). (Base ASN.1 helper module names such as ASN1, ASN1-ENUMERATION, and ASN1-REFINEMENT must not appear here.)

This behavior must hold for both SMIv2 and SMIv1 (relaxed) parsed inputs.

Summary of Required Deliverables

  1. SymtableCodeGen class in pysmi.codegen.symtable with genCode(self, ast, symbolTable, **options) returning (mibInfo, symtable) where mibInfo.name is the module name.
  2. PySnmpCodeGen.genCode(self, ast, symbolTable, **options) returning a single (mibInfo, pycode) tuple, with mibInfo.imported reporting only real imported MIB module names (excluding ASN.1 base pseudo-modules), and consuming a {name: symtable} dependency dict for symbol resolution.

Overview

  1. a symbol table describing the module and its symbols; and

pysmi.codegen.symtable.SymtableCodeGen

  • genTexts is a boolean controlling processing of descriptive text metadata.

The method returns (mibInfo, symtable), where:

  • mibInfo exposes at least a string .name containing the canonical MIB module name.
  • symtable is the generated symbol table for that module and is suitable for insertion into a later symbolTableMap under mibInfo.name.
pysmi.codegen.pysnmp.PySnmpCodeGen

The class must have a no-argument constructor and support:

def genCode(self, ast, symbolTableMap, genTexts=False)
  • ast is the parsed MIB AST node to compile.
  • symbolTableMap maps MIB module names to symbol tables. It must contain an entry for the module being compiled, keyed by that module's canonical name and containing the symbol table produced from the same AST by SymtableCodeGen.genCode. It may also contain symbol tables for dependencies.
  • genTexts is a boolean controlling emission of descriptive text metadata.

The method returns (mibInfo, pycode), where:

  • mibInfo exposes at least:
    • .name: the canonical MIB module name as a string;
    • .imported: the dependency tuple defined below.
  • pycode is a string containing valid Python source. It must be accepted by compile(pycode, '<generated-mib>', 'exec') and execute in a namespace containing a mibBuilder that is a pysnmp.smi.builder.MibBuilder instance. Execution must define and export the compiled module's symbols through that builder.

Required Behavior

Mandatory two-stage generation

Pysnmp source generation is a two-stage operation:

symInfo, symtable = SymtableCodeGen().genCode(
    ast, {}, genTexts=genTexts
)

mibInfo, pycode = PySnmpCodeGen().genCode(
    ast, {symInfo.name: symtable}, genTexts=genTexts
)

The second stage must use the supplied symbol-table entry to resolve local symbol types, OIDs, defaults, table relationships, and other semantic information. The generated symbol table must therefore remain directly consumable by PySnmpCodeGen; callers must not have to translate it.

Dependency reporting

For every module generated by PySnmpCodeGen, mibInfo.imported must:

  • unconditionally include SNMPv2-SMI, SNMPv2-CONF, and SNMPv2-TC, even when the input has no declarations and does not use conformance or textual-convention constructs;
  • include explicitly imported MIB modules and any additional effective dependencies introduced by supported SMI translation or by constructs used in the module;
  • contain each module name at most once;
  • be sorted in ascending alphabetical order; and
  • exclude the ASN.1 pseudo-modules ASN1, ASN1-ENUMERATION, and ASN1-REFINEMENT.

Equivalently, the reported tuple is the sorted, duplicate-free union of the effective MIB imports and the three mandatory support modules, with the ASN.1 pseudo-modules removed.

For example, a module importing SNMP-FRAMEWORK-MIB must report:

(
    'SNMP-FRAMEWORK-MIB',
    'SNMPv2-CONF',
    'SNMPv2-SMI',
    'SNMPv2-TC',
)

This rule is unconditional; it also applies to an imports-only module.

Generated Python correctness

The generated source must:

  • compile cleanly under exec mode on every supported Python version, without depending on compilation or optimization arguments available only in particular Python versions;
  • execute without error against a fresh MibBuilder;
  • import required symbols, define the module's generated symbols, and export those symbols under the proper MIB module name;
  • avoid duplicate generated import operations for the same dependency;
  • emit class bases or mixins in an order that does not produce Python method-resolution-order errors;
  • safely represent MIB symbol names that collide with Python reserved keywords, so the source remains syntactically valid and the corresponding MIB symbols still load; and
  • preserve valid OIDs and inter-symbol references even when declarations are not ordered by OID ancestry.
MIB construct semantics

The generators must handle the standard MIB construct categories listed under Parser Compatibility. Generated runtime objects must use the corresponding pysnmp concepts, including module and object identities, scalars, tables, table rows and columns, notifications, groups, compliance declarations, capabilities, and identifiers. TRAP-TYPE must be translated to the pysnmp notification representation. Generated symbols must retain their applicable OIDs, syntax, status, access, units, object lists, indexes, defaults, and text metadata.

Type and value generation must support:

  • SMIv1 and SMIv2 type declarations and the standard integer, string, identifier, counter, gauge, time-tick, opaque, unsigned, address, bits, and textual-convention forms;
  • enumerations, integer constraints, string-size constraints, and BITS named values;
  • numeric, enumeration, string, OID, hexadecimal, binary, and BITS defaults as applicable to the declared syntax; and
  • value declarations whose OIDs are entirely numeric or are based on another local or imported symbol.

Binary-string DEFVAL values assigned to Integer-based symbols must be interpreted as integer values, rather than emitted as an octet-string-style hexadecimal value.

SMIv1 compatibility

The generators must support SMIv1 input and translate legacy constructs and imported base types to their pysnmp/SMIv2 equivalents. This includes SMIv1 TRAP-TYPE handling and SMIv1-style INDEX entries. Where an SMIv1 index names a primitive type rather than an existing column, generation must still produce a valid table-row index and any necessary exported supporting symbol. Ordinary, multiple, and IMPLIED index entries must retain their index semantics.

Text metadata

When genTexts=True, generated source must include the available descriptive metadata and arrange for it to be installed when text loading is enabled on the MibBuilder. This includes metadata such as LAST-UPDATED, ORGANIZATION, CONTACT-INFO, DESCRIPTION, revision information, references, display hints, and units where applicable.

In particular, a MODULE-IDENTITY LAST-UPDATED value must not be dropped or replaced by revision data. After executing generated source with mibBuilder.loadTexts enabled, the resulting module-identity object's last-updated accessor must return the original MIB value, including its original UTC string form (for example, 200001100000Z). Naming of fake columns. Fake columns are named pysmiFakeCol followed by a positive integer counter. The counter starts at 1 and increments for each fake column created, in the order the index syntaxes appear across the module. Named index entries (which reference existing columns) do not consume a counter value.

For a row whose OID is (1, 3, 3) with index syntaxes at positions 1, 3 and 4 (position 2 being a named column), the fake columns get names (1, 3, 3, 4294967295), (1, 3, 3, 4294967294), and (1, 3, 3, 4294967293) respectively, in index order.

INDEX syntax Fake column getSyntax() class name
INTEGER Integer32
OCTET STRING OctetString
IpAddress IpAddress
NetworkAddress IpAddress

Access and status. Every fake column has:

  • max access "not-accessible" (returned by getMaxAccess())
  • status "mandatory" (returned by getStatus())
Table row index list

The table-entry (row) object's getIndexNames() must return a tuple of index descriptors in the exact order the INDEX clause lists them. Each descriptor is a 3-tuple (0, <mib-module-name>, <column-name>):

  • For a named column reference, <column-name> is that column's own name (e.g. "testIndex").
  • For an index syntax, <column-name> is the corresponding generated fake column name (e.g. "pysmiFakeCol1").

Example: an INDEX { IpAddress, testIndex, OCTET STRING, NetworkAddress } on a module named TEST-MIB yields:

(
    (0, "TEST-MIB", "pysmiFakeCol1"),
    (0, "TEST-MIB", "testIndex"),
    (0, "TEST-MIB", "pysmiFakeCol2"),
    (0, "TEST-MIB", "pysmiFakeCol3"),
)
Standard conceptual table generation

For the tables described above, the generated PySNMP objects must have the correct classes:

  • The table object (SYNTAX SEQUENCE OF ...) → class MibTable.
  • The table-entry / row object → class MibTableRow.
  • Real (named) column object types → class MibTableColumn, with getMaxAccess() and getStatus() reflecting the declared access and status of the column (e.g. "read-write" / "mandatory" for SMIv1 columns).
Lenient SEQUENCE OF type-name matching (SMIv2)

When a conceptual-table object type declares SYNTAX SEQUENCE OF <TypeName> where <TypeName> does not match the name of the actual table-entry type used by the row object, the generator must still produce a correct table:

  • the table object is class MibTable,
  • the row object is class MibTableRow,
  • named index columns are class MibTableColumn,
  • getIndexNames() on the row returns the correct index descriptors (e.g. ((0, "TEST-MIB", "testIndex"),) for INDEX { testIndex }).

The mismatch between the SEQUENCE OF type name and the row entry type must not cause an error, as long as the table-entry object type itself is well-formed.

Consistency Requirement

The symbol table stage (SymtableCodeGen) and the code-generation stage (PySnmpCodeGen) must agree exactly on the naming and numbering scheme for fake columns (i.e. both must use identical pysmiFakeCol naming and the same counting/OID conventions), so that the code generated in the second stage resolves consistently against the symbol table produced in the first.

Notes

  • All the above must work for MIB modules parsed under both the relaxed SMIv1 dialect (smiV1Relaxed) and the default SMIv2 dialect, as applicable to each feature (SMIv1 index syntaxes are exercised under smiV1Relaxed; lenient SEQUENCE OF matching is exercised under the default dialect).
  • Both genTexts=True and default (no texts) modes must produce working, compilable, executable code.
