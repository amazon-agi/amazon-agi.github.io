01 Separating MIB Parsing from PySNMP Code Generation 653 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Separating MIB Parsing from PySNMP Code Generation

Overview

At the moment, SMI MIB parsing and PySNMP Python-code generation are combined into one step that the parser performs. This task requires that the two concerns be separated into two distinct components: a parser whose job is to produce an intermediate representation of a MIB, and a code generator that consumes that representation to produce executable Python (PySNMP) code.

Public API Requirements

1. Parser

It must remain possible to import and call a parser class as follows:

from pysmi.parser.smiv2 import SmiV2Parser

It must be possible to instantiate SmiV2Parser with no arguments, i.e. SmiV2Parser().

The class must expose a method:

parse(self, data)
  • The data argument is a string that contains the full text of a MIB module definition (SMIv1 or SMIv2 syntax).
  • parse must return an intermediate representation of the parsed MIB. Callers make no direct use of this return value other than passing it straight into the code generator (see below). Its internal structure is unconstrained except that the code generator described next must accept it.
2. PySNMP Code Generator

There must be a new code-generator class importable as:

from pysmi.codegen.pysnmp import PySnmpCodeGen

It must be possible to instantiate PySnmpCodeGen with no arguments, i.e. PySnmpCodeGen().

The class must expose a method:

genCode(self, parsedMib)

  • parsedMib is exactly the value that SmiV2Parser().parse(...) returns.

  • genCode must return a 3-tuple, which callers unpack as:

    thisMib, otherMibs, pycode = PySnmpCodeGen().genCode(SmiV2Parser().parse(mibText))

    where:

    • pycode is a string of Python source code. It must be valid enough to be passed to the builtin compile(pycode, 'test', 'exec') without error, and, when executed in a namespace containing a mibBuilder (an instance of pysnmp.smi.builder.MibBuilder) whose managed MIB objects can subsequently be exported and inspected, it must reproduce the correct PySNMP MIB object definitions for the given MIB.
    • otherMibs is the collection of names of the other MIB modules referenced/imported by the parsed MIB (i.e. the imported-module information that the parser's old return value previously carried as its first element).
    • thisMib is a new value that represents the identity/name of the MIB module being generated. Callers unpack it, but its specific structure is otherwise not exercised.

Required Behavior

The end-to-end behavior — parsing MIB text and then generating Python code — must be exactly equivalent to the previous single-step behavior, now spread over the two calls:

Before (single step):

otherMibs, pycode = SmiV2Parser().parse(mibText)

Required (two steps):

thisMib, otherMibs, pycode = PySnmpCodeGen().genCode(SmiV2Parser().parse(mibText))
  • Producing Python code must no longer be done by SmiV2Parser().parse() itself; that responsibility moves entirely to PySnmpCodeGen().genCode().
  • For the same MIB text, the generated pycode and the otherMibs value must remain equivalent to what the old single-step parse produced.
MIB constructs that must be supported

The parse-then-generate pipeline must handle MIB modules containing at least the following constructs correctly, and the PySNMP code it produces must define the corresponding objects correctly:

  • IMPORTS clauses (including well-formed multi-line imports from multiple foreign modules).
  • MODULE-IDENTITY
  • OBJECT-IDENTITY
  • OBJECT-TYPE (including scalar objects, tables/rows/columns, various syntaxes, constraints, indexes, defaults, etc.)
  • NOTIFICATION-TYPE
  • NOTIFICATION-GROUP
  • OBJECT-GROUP
  • MODULE-COMPLIANCE
  • AGENT-CAPABILITIES
  • TRAP-TYPE (SMIv1)
  • Type declarations (both SMIv1 and SMIv2 syntax).
  • Value declarations.

MIB modules written in both SMIv1 and SMIv2 style must be parseable by SmiV2Parser.

Compatibility with Python 2 / Python 3

All code that is introduced or modified must run correctly under both Python 2 and Python 3 (the pipeline is exercised on both). Ensure that the parser and code generator produce identical logical results across the supported interpreter versions.

Constraints

  • The import path or the constructor signature of SmiV2Parser must not be changed.
  • The new PySnmpCodeGen must reside at the module path pysmi.codegen.pysnmp.
  • The order of the tuple that genCode returns is fixed: (thisMib, otherMibs, pycode).
02 The library you are working on is pysmi, which parses SNMP MIB definitions and generates Python (pysnmp) code from them. 649 words · source specification, reworded by GLM-5.3-Flash

Overview

The library you are working on is pysmi, which parses SNMP MIB definitions and generates Python (pysnmp) code from them. Two changes are required in this task: (1) adding an optional text-generation mode to the pysnmp code generator, and (2) providing an SMIv1-compatible parser class.

Part 1: the genTexts option of the pysnmp code generator

API surface

The code generator is reachable through this import:

from pysmi.codegen.pysnmp import PySnmpCodeGen

Its genCode method must accept an optional keyword argument named genTexts, with False as the default:

PySnmpCodeGen().genCode(parsedData, genTexts=False)
  • parsedData denotes the parse tree that a parser's parse(...) method has produced.
  • What the method returns is a 3-tuple (thisMib, otherMibs, pycode), in which pycode is a string of executable Python source.
Behavior that is required

If genTexts=True is passed, the code that gets generated must embed the descriptive text and metadata fields taken from the MIB source, so that after this generated code is compiled and loaded into a pysnmp MibBuilder (with mibBuilder.loadTexts = True), the MIB objects loaded from it expose those texts. Specifically, the following must hold for a MIB loaded from code generated with genTexts=True:

  1. MODULE-IDENTITY revisions. The getRevisions() method of a module identity object must return the revision timestamps formatted as human-readable date-time strings in the form 'YYYY-MM-DD HH:MM'. For instance, a MIB revision written as 200001100000Z must be returned as '2000-01-10 00:00'.

  2. OBJECT-IDENTITY description. The getDescription() method of an object identity must return the text of the DESCRIPTION clause as written in the MIB source (e.g. a description clause containing Initial version yields 'Initial version').

These text/metadata fields must be produced only as a result of genTexts=True having been requested; the default behavior (no text generation) stays unchanged.

Part 2: normalizing MAX-ACCESS values

For an OBJECT-TYPE, getMaxAccess() invoked on the loaded object must return the access level as a single lowercase token from which the hyphens have been removed. For example, a MIB MAX-ACCESS accessible-for-notify clause must yield the value 'accessiblefornotify'.

Part 3: parser compatible with SMIv1

API surface

A parser class must be provided, importable in this way:

from pysmi.parser.smiv1compat import SmiV1CompatParser

The class must expose the same interface as the existing SMIv2 parser (from pysmi.parser.smiv2 import SmiV2Parser), that is, a parse(text) method returning a parse tree that is consumable by PySnmpCodeGen().genCode(...).

Behavior that is required

SmiV1CompatParser must parse both SMIv2 constructs and constructs that are specific to SMIv1. In particular, it must accept the SMIv1 index type syntax within object definitions and handle it correctly. A MIB module that parses successfully with SmiV2Parser must also parse successfully with SmiV1CompatParser, and the parse trees produced must generate pysnmp code that is equivalent.

Specifically:

  • A MIB that uses SMIv1 NOTIFICATION-GROUP-style / SMIv1 index constructs must, when parsed with SmiV1CompatParser and code-generated, produce an object whose loaded Python class name is 'NotificationGroup'.
  • Type declarations written in SMIv1 must parse and generate loadable pysnmp code that is identical in effect to the SMIv2 path.

Code generated from SmiV1CompatParser output must be compilable and loadable into a pysnmp MibBuilder in the same way as code from SmiV2Parser.

Contract for compilation / loading (context for both parts)

In all of the cases above, the generated pycode string must:

  • Compile by means of compile(pycode, 'test', 'exec').
  • Execute successfully in a namespace that contains a pysnmp MibBuilder (from pysnmp.smi.builder import MibBuilder), registering the MIB objects so they can be retrieved and their getter methods (getRevisions, getDescription, getMaxAccess, and __class__.__name__) queried as described.

Summary of the public API that the engineer must provide

  • pysmi.codegen.pysnmp.PySnmpCodeGen.genCode(parsedData, genTexts=False) — accept the genTexts keyword and honor it.
  • pysmi.parser.smiv1compat.SmiV1CompatParser — a new parser class offering a parse(text) method, with support for SMIv1 index-type syntax in addition to SMIv2.

Behavior beyond what is described here must not be added.

03 Change genCode to Return a MIB Info Object 410 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Change genCode to Return a MIB Info Object

Overview

Change the code generator's genCode method so that metadata describing the generated MIB module is returned as one dedicated info object instead of as separate return values.

Public API Surface

PySnmpCodeGen.genCode(...)

The code generator class PySnmpCodeGen (importable in its current form) exposes a genCode method with this calling convention:

mibInfo, pycode = PySnmpCodeGen().genCode(parsedMib, genTexts=True)
  • Input: the parsed MIB structure that a parser's parse(...) method produces, together with the keyword argument genTexts (boolean).
  • Return value: a 2-tuple (mibInfo, pycode) in which:
    • pycode is a string of generated Python source code suitable for passing to the built-in compile(...) and executing within a MIB builder context (its nature is unchanged from before).
    • mibInfo is a single object carrying metadata that describes the generated MIB module (see below).

Required change: The method previously returned a 3-tuple of the form (thisMib, otherMibs, pycode). It must now return the 2-tuple (mibInfo, pycode), with the module metadata folded into the mibInfo object.

The MIB Info Object

As its first element, genCode must return an object that exposes at least the following attribute:

  • otherMibs — a tuple of strings giving the names of the MIB modules that the generated module imports/depends on. The names appear in a stable order; for a module that imports the appropriate framework definitions, the collection includes the implicit ASN.1 base modules in addition to any explicitly imported modules. As an example, a module that imports symbols from SNMP-FRAMEWORK-MIB and SNMPv2-SMI yields:

    ('ASN1', 'ASN1-ENUMERATION', 'ASN1-REFINEMENT', 'SNMP-FRAMEWORK-MIB', 'SNMPv2-SMI')

The information that used to be returned as the first (thisMib) and second (otherMibs) tuple elements is now reached through attributes of this single info object. Only the otherMibs attribute is exercised directly; make it available as an attribute of the returned object.

Behavioral Requirements

  • When compiled and executed against a MIB builder, the generated pycode string must continue to produce the same MIB definitions as before this change (the code-generation output is unaffected).
  • The only externally visible change is the shape of genCode's return value: a 2-tuple (mibInfo, pycode) in which module metadata is reachable as attributes on mibInfo, and mibInfo.otherMibs gives the tuple of imported/dependency MIB module names as described.

Out of Scope

No other behavior changes are required. The parsers, the semantics of the compiled code, and all other public interfaces stay as they are.

from pysmi.parser.smiv2 import parserFactory

  • It must be possible to instantiate the returned class without arguments.
  • Instances of the returned class must expose a parse(self, text) method.
  • When given no keyword arguments, parserFactory() must return a parser class implementing the default SMIv2 grammar.

parserFactory()().parse(mib_text)

from pysmi.parser.dialect import smiV1Relaxed

pysmi.codegen.pysnmp.PySnmpCodeGen

PySnmpCodeGen().genCode(parsedMib, genTexts=True)

mibInfo, pycode = PySnmpCodeGen().genCode(

Here:

  • Definitions of MODULE-COMPLIANCE.
  • Definitions of MODULE-IDENTITY.
  • Definitions of NOTIFICATION-GROUP.

05 Rework the MIB Code Generation API 688 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Rework the MIB Code Generation API

Overview

The genCode API used by the code-generation backends in the pysmi package must be changed, and a new symbol-table code-generation backend must be introduced. These changes concern the conversion of parsed MIB syntax trees into output, the reporting of imported MIB dependencies, and the passing of symbol information between generation passes.

Output Produced by the Parser

pysmi.parser.smi.parserFactory returns a parser class. The parse(text) method of an instance returns an indexable sequence of parse results. Its first element (parse(text)[0]) is the abstract syntax tree (AST) for a single MIB module. Callers now explicitly pick this first element before handing it to a code generator.

Change to the genCode Signature

Both of the code-generation backends expose a genCode method having the following signature:

genCode(self, ast, symbolTable, **options)
  • ast: the AST of a single MIB module (the first element of a parser's parse(...) output).
  • symbolTable: a dict that maps a MIB module name (str) → that module's symbol table (the symbol-table object produced by the symbol-table backend, which is described below). It may be empty ({}) in cases where no dependency symbol information is available/needed.
  • options: keyword options; the tests make use of genTexts=True.

A call to genCode returns a 2-tuple (mibInfo, data) directly (NOT a list/sequence of such tuples — callers make use of the returned value without additional indexing).

For the pysnmp backend, data is a string of executable Python source code which, once compiled and executed in a context that provides a mibBuilder, defines the MIB's managed objects.

For the symbol-table backend, data is the symbol table object belonging to that module (see below).

The New Symbol-Table Backend

Add a class SymtableCodeGen in module pysmi.codegen.symtable, which can be imported as:

from pysmi.codegen.symtable import SymtableCodeGen

It exposes genCode(self, ast, symbolTable, **options) and follows the same calling convention described above. Supplied with a module AST (and an empty symbolTable dict), it returns (mibInfo, symtable) where:

  • mibInfo carries a name attribute that holds the MIB module's name (str).
  • symtable is that module's symbol table object.

The symbol table produced here is intended to be fed back into later genCode calls through the symbolTable argument, keyed by module name, e.g. { mibInfo.name: symtable }.

The PySnmp Backend

PySnmpCodeGen remains importable via:

from pysmi.codegen.pysnmp import PySnmpCodeGen

Its genCode now accepts the new (ast, symbolTable, **options) signature and returns a single (mibInfo, pycode) tuple.

When a module references types/objects imported from other MIBs, PySnmpCodeGen().genCode must be able to resolve those references using the symbolTable dict supplied by the caller (populated from the SymtableCodeGen output of the imported modules). When it is invoked with an empty symbolTable on a module that does not require external symbol resolution, it must still produce valid code.

Imports Reported through mibInfo

The mibInfo object that PySnmpCodeGen().genCode returns must expose an attribute:

  • imported: a tuple of the names of the MIB modules from which the compiled module imports; it contains only real external MIB module names and excludes synthetic/base ASN.1 pseudo-modules. When a module imports from SNMP-FRAMEWORK-MIB and SNMPv2-SMI, this tuple is exactly ('SNMP-FRAMEWORK-MIB', 'SNMPv2-SMI'). (Base ASN.1 helper module names like ASN1, ASN1-ENUMERATION, and ASN1-REFINEMENT must not appear here.)

Required Behavior of the Generated pysnmp Code

The Python code string that is returned for a module must, when it is compiled with compile(pycode, 'test', 'exec') and executed against a context that contains a pysnmp.smi.builder.MibBuilder instance, correctly define that module's constructs (types, values, object identities/types, notifications, groups, compliances, agent capabilities, trap types, etc.) so that they can be exported from and imported through the MibBuilder. This behavior is required to hold for both SMIv2 and SMIv1 (relaxed) parsed inputs.

Recap of Required Deliverables

  1. A SymtableCodeGen class in pysmi.codegen.symtable with a genCode(self, ast, symbolTable, **options) that returns (mibInfo, symtable), where mibInfo.name is the module name.
  2. PySnmpCodeGen.genCode(self, ast, symbolTable, **options) that returns a single (mibInfo, pycode) tuple, with mibInfo.imported reporting only real imported MIB module names (with ASN.1 base pseudo-modules excluded), and using a {name: symtable} dependency dict for symbol resolution.
06 MIB Code Generation with a Symbol Table Prerequisite 1197 words · rewritten by GPT-5.6-sol, reworded by GLM-5.3-Flash

Task Specification: MIB Code Generation with a Symbol Table Prerequisite

Summary

Implement or modify the two code-generator classes in the pysmi package that convert a parsed MIB abstract syntax tree (AST) into:

  1. a symbol table describing the module and its symbols; and
  2. executable pysnmp Python source code.

The pysnmp generator works from the symbol table that the symbol-table generator produces.

Public API

pysmi.codegen.symtable.SymtableCodeGen

The class must provide a constructor that takes no arguments, and must support:

def genCode(self, ast, symbolTableMap, genTexts=False)
  • ast is a single parsed MIB AST node — for instance, the first element returned by a parser's parse(...) method.
  • symbolTableMap is a dictionary that maps MIB module names to symbol tables generated earlier. It may be empty in cases where no prior module information is needed.
  • genTexts is a boolean that governs the processing of descriptive text metadata.

The method returns (mibInfo, symtable), where:

  • mibInfo exposes at least a string .name holding the canonical MIB module name.
  • symtable is the symbol table generated for that module, and it is suitable for insertion into a later symbolTableMap under mibInfo.name.
pysmi.codegen.pysnmp.PySnmpCodeGen

The class must provide a constructor that takes no arguments, and must support:

def genCode(self, ast, symbolTableMap, genTexts=False)
  • ast is the parsed MIB AST node that is to be compiled.
  • symbolTableMap maps MIB module names to symbol tables. It must contain an entry for the module being compiled — keyed by that module's canonical name and holding the symbol table that SymtableCodeGen.genCode produced from the same AST. It may additionally hold symbol tables for dependencies.
  • genTexts is a boolean that governs emission of descriptive text metadata.

The method returns (mibInfo, pycode), where:

  • mibInfo exposes at least:
    • .name: the canonical MIB module name, as a string;
    • .imported: the dependency tuple specified below.
  • pycode is a string of valid Python source. It must be accepted by compile(pycode, '<generated-mib>', 'exec') and must run in a namespace that contains a mibBuilder which is a pysnmp.smi.builder.MibBuilder instance. Execution must define the compiled module's symbols and export them through that builder.

Behavior Requirements

Two-stage generation is mandatory

Generation of pysnmp source takes place in two stages:

symInfo, symtable = SymtableCodeGen().genCode(
    ast, {}, genTexts=genTexts
)

mibInfo, pycode = PySnmpCodeGen().genCode(
    ast, {symInfo.name: symtable}, genTexts=genTexts
)

The second stage must make use of the supplied symbol-table entry to resolve local symbol types, OIDs, defaults, table relationships, and other semantic information. The generated symbol table must therefore stay directly consumable by PySnmpCodeGen; callers must not be required to translate it.

Reporting of Dependencies

For every module that PySnmpCodeGen generates, mibInfo.imported must:

  • unconditionally include SNMPv2-SMI, SNMPv2-CONF, and SNMPv2-TC, even when the input has no declarations and does not make use of conformance or textual-convention constructs;
  • include the explicitly imported MIB modules as well as any additional effective dependencies introduced by supported SMI translation or by constructs used in the module;
  • hold each module name at most once;
  • be sorted alphabetically in ascending order; and
  • leave out the ASN.1 pseudo-modules ASN1, ASN1-ENUMERATION, and ASN1-REFINEMENT.

Put equivalently, the tuple that is reported is the duplicate-free, sorted union of the effective MIB imports and the three mandatory support modules, with the ASN.1 pseudo-modules removed.

As an example, a module that imports SNMP-FRAMEWORK-MIB must report:

(
    'SNMP-FRAMEWORK-MIB',
    'SNMPv2-CONF',
    'SNMPv2-SMI',
    'SNMPv2-TC',
)

This rule holds unconditionally; it likewise applies to a module containing only imports.

Correctness of Generated Python

The produced source must:

  • compile cleanly under exec mode on every supported Python version, without depending on compilation or optimization arguments that are available only in particular Python versions;
  • run without error against a fresh MibBuilder;
  • import the required symbols, define the module's generated symbols, and export those symbols under the proper MIB module name;
  • avoid emitting duplicate generated import operations for the same dependency;
  • emit class bases or mixins in an order that avoids producing Python method-resolution-order errors;
  • represent MIB symbol names that collide with Python reserved keywords in a safe way, so that the source stays syntactically valid and the corresponding MIB symbols still load; and
  • keep valid OIDs and inter-symbol references intact even when declarations are not ordered by OID ancestry.
Semantics of MIB Constructs

The generators must handle the standard MIB construct categories listed under Parser Compatibility. The runtime objects that are generated must use the corresponding pysnmp concepts, including module and object identities, scalars, tables, table rows and columns, notifications, groups, compliance declarations, capabilities, and identifiers. TRAP-TYPE must be translated into the pysnmp notification representation. Generated symbols must retain the applicable OIDs, syntax, status, access, units, object lists, indexes, defaults, and text metadata.

  • The result holds the minimum number of octets needed; when no bits are set, the result is the single zero octet bytes((0x00,)).

Task Specification: Handling Python Reserved Keywords in MIB Symbol Names Correctly

Background

SMIv2 MIB definitions are what this project takes in, turning them into Python (pysnmp) source code that can be executed. When a MIB file declares or imports symbols, the names involved can fall into these categories:

  • Python reserved keywords (e.g. if, global, True, False), which cannot legally serve as Python identifiers.
  • Names that carry characters a Python identifier cannot contain (e.g. a hyphen, as in test-value-4).

Whatever the name looks like, the code generator must emit Python identifiers that are always valid, and it must preserve the original MIB label (the SMI name) in the metadata of the generated object.

Public API

Exactly as set out here, the classes below must be importable and callable.

  • pysmi.codegen.symtable.SymtableCodeGen

    • Method: genCode(self, ast, symbolTable, **kwargs) → returns the tuple (mibInfo, symtable); of the two elements, mibInfo provides a .name attribute (the MIB module name), while symtable is the data structure holding the symbol table of that MIB.

  • pysmi.codegen.pysnmp.PySnmpCodeGen

    • Method: genCode(self, ast, symbolTable, **kwargs) → returns the tuple (mibInfo, pycode); the second element, pycode, is a string of valid Python source, and compiling and executing it against a namespace that contains a mibBuilder (an instance of pysnmp's MibBuilder) leaves that namespace populated with the objects the MIB exports.

  • Both generators take as their input an AST obtained in the following way: run pysmi.parser.smi.parserFactory()(), call its .parse(text) method, and take the first element of the list that comes back.

For compiling and executing the generated Python code, one shared namespace dict serves, initialized as {"mibBuilder": MibBuilder()}. After execution, the MIB objects can be accessed in that namespace, with each object's generated Python identifier acting as its key.

Behavior Requirements

How identifiers get translated

For each MIB symbol name — irrespective of whether that symbol is defined within the MIB being compiled or imported from another MIB — the Python identifier generated for it (that is, the variable name bound in the executed namespace) must be derived from the original MIB name in this manner:

  1. Should the original MIB name turn out to be a Python reserved keyword, the generated Python identifier consists of _pysmi_ followed by that name. Examples:
    • if → _pysmi_if
    • global → _pysmi_global
    • True → the identifier carrying that prefix (_pysmi_True)
    • False → the identifier carrying that prefix (_pysmi_False)
  2. In all other cases, any character a Python identifier cannot contain (- being a typical instance) is swapped for _. Examples:
    • test-value-2 → test_value_2
    • test-object-2 → test_object_2
  3. A name that already constitutes a valid Python identifier and is not a reserved keyword goes through untouched (e.g. testValue1, testObject1).

At every point where the symbol name serves to build a Python identifier, this translation must be applied consistently. Those points are:

  • The point where an object gets defined in the generated module (the variable bound in the namespace).
  • The point where another symbol gets referenced to play the role of parent/anchor for an OBJECT IDENTIFIER value.
  • The point where a symbol gets referenced to supply the base type/syntax of a type or object being declared.
  • The point where the import table entries get generated: for an imported symbol, the local Python identifier bound to it must be the translated form, even though the lookup of that symbol inside its origin MIB goes by its original (untranslated) MIB name.
The original MIB label stays intact

Identifier translation has no bearing on the following: each generated MIB object must retain its original MIB name as its label. Concretely:

  • The call obj.getLabel() must return the MIB name in its original, untranslated shape (e.g. "if", "global", "test-value-2", "test-object-2", "testValue1").
How OBJECT IDENTIFIER values resolve

For an OBJECT IDENTIFIER value written as { parent subid... }, resolution must produce the numeric OID obtained when the given sub-identifier(s) are appended to the OID into which parent resolves. The parent may itself be:

  • one of the symbols the same MIB defines (this includes one whose name is a reserved keyword), or
  • one of the symbols imported from another MIB (this includes one whose name is a reserved keyword).

Even once the parent's Python identifier has undergone translation, resolution must work correctly. By way of example: with importedValue1 = 1.3 imported, an OID declared as { importedValue1 6 } resolves to (1, 3, 6); with global = 1.5 defined locally, an OID { global 2 } resolves to (1, 5, 2).

As a tuple of integers, obj.getName() must return the numeric OID in fully resolved form.

Resolving types / TEXTUAL-CONVENTIONs

A base type referenced by an object's SYNTAX may be:

  • a TEXTUAL-CONVENTION that was imported (one whose name is a reserved keyword, such as True, is included here),
  • a TEXTUAL-CONVENTION defined locally whose own derivation traces back to another type (that other type being possibly imported, and possibly named with a reserved keyword).

Even with these translated identifiers in play, type resolution and display-hint inheritance must work correctly:

  • When the syntax of an object resolves (directly or transitively) to a TEXTUAL-CONVENTION declaring a DISPLAY-HINT, the object must expose that display hint via obj.getSyntax().getDisplayHint().
  • Moving along the derivation chain, the DISPLAY-HINT declared nearest is the one that applies. A TEXTUAL-CONVENTION declaring a DISPLAY-HINT of its own uses that hint (e.g. a TC with DISPLAY-HINT "1x:" yields "1x:"; one with "2x:" yields "2x:").
  • If an object's base type chain has a DISPLAY-HINT nowhere at all, getDisplayHint() yields the empty string "".

Some concrete chains:

  • object → imported TC with DISPLAY-HINT "255a" ⇒ "255a".
  • object → local TC (DISPLAY-HINT "1x:") → imported TC (no hint) ⇒ "1x:".
  • object (reserved-keyword-named) → imported TC (no hint) ⇒ "".
  • object (reserved-keyword-named) → local TC (DISPLAY-HINT "2x:") → imported TC (no hint) ⇒ "2x:".

Compiling Several MIBs in Sequence

The generators must be able to handle a run in which multiple MIBs are compiled one after another, with later MIBs importing from earlier ones:

  1. Every MIB is first put through SymtableCodeGen().genCode(ast, {}); the symbol table this call produces for it is added to a dict whose keys are the MIB names (mibInfo.name).
  2. After that, PySnmpCodeGen().genCode(ast, symbolTable) is called with the accumulated symbol-table dict handed to it; the pycode it produces is then compiled and executed into the shared namespace.

Finding an imported symbol must happen correctly in its origin MIB's symbol table, with the symbol's original MIB name serving as the lookup key; the local binding in the generated module, in contrast, uses the translated identifier.

Constraints at a Glance

  • A symbol name that is a reserved keyword always ends up as an identifier carrying the _pysmi_ prefix.
  • Where a name contains illegal characters, those characters are swapped for underscores.
  • Object labels always preserve the original MIB names.
  • Defined symbols, referenced parent OIDs, referenced base types and import-table local names all undergo identifier translation in a uniform manner.
  • OID resolution and type/display-hint resolution work correctly even when identifiers have been translated and MIB boundaries are crossed.

Task Specification: MIB Text Values and Their Correct Quoting, Escaping, and Preservation

Background

At the heart of this task sits the PySMI code generator, the component that takes MIB (Management Information Base) definitions after parsing and turns them into Python (pysnmp) code that can be executed. Free-form text occurring in the MIB source (such as DESCRIPTION, ORGANIZATION, CONTACT-INFO, REFERENCE, UNITS, PRODUCT-RELEASE, DISPLAY-HINT, and string DEFVAL values) must be emitted into the generated Python source in the form of string literals which, after that code is compiled and executed, reproduce the original text exactly.

Public API Surface

The imports and calls below are required to work as described, and the engineer must ensure this.

  • parserFactory() must be provided by pysmi.parser.smi (or the module already exposing it). Invoking it as parserFactory()() is how a parser is obtained; that parser's .parse(text) returns a list whose first element is an AST for the MIB source string supplied.

  • pysmi.codegen.symtable.SymtableCodeGen must expose:

    genCode(ast, {}, genTexts=True) -> (mibInfo, symtable)

    with the mibInfo it returns carrying a .name attribute.

  • pysmi.codegen.pysnmp.PySnmpCodeGen must expose:

    genCode(ast, {mibInfo.name: symtable}, genTexts=True, textFilter=<callable>) -> (mibInfo, pycode)
    • The pycode obtained must be a str containing Python source that is valid and compilable.
    • As a keyword argument, textFilter is optional. If it is supplied, what the caller passes is a callable that takes (symbol, text) and returns a (possibly transformed) text string. Before any textual value is emitted into the generated code, this callable must be applied to it. If it is left out, default behavior comes into play (see below).

Once the generated pycode is compiled and executed inside a namespace that contains a mibBuilder (an instance of pysmi....MibBuilder carrying .loadTexts = True), the MIB symbols defined there must be such that calls to their accessor methods (getDescription(), getReference(), getOrganization(), getContactInfo(), getProductRelease(), getUnits(), getDisplayHint(), getSyntax(), etc.) return the expected string values.

Core Requirements

1. No spurious trailing line terminator

An extra line terminator (\n) must not be appended to textual values. For single-line MIB text such as "Test object", the value must yield exactly "Test object" — never "Test object\n". All textual values, across all MIB construct types, fall under this rule.

2. The text content must be preserved exactly

Each and every character of the original MIB textual string must survive verbatim into the value that the corresponding accessor returns. What this preservation covers:

  • Line terminators inside the text. Several physical lines may be spanned by a piece of MIB text. Newlines occurring inside must be preserved as \n in the resulting string, and the text must not be word-wrapped, regardless of how long the lines are. Leading/trailing content and blank lines inside the text are kept as written.
  • Backslash characters. In MIB text, a backslash counts as a literal character: it must be preserved literally, and it must never be taken for a Python (or other) escape. The cases covered are:
    • a backslash anywhere inside the text (for instance, the \n written in the MIB text stays the two literal characters backslash + n, not a newline);
    • a backslash serving as the final character of the text value;
    • backslashes occurring several times in a row (for instance, \\ stays two literal backslashes).
  • All other printable/special characters (~ ` !@#$%^&*()-_=+[]{}|;:'<>,.?/, tab characters, etc.) must likewise be preserved verbatim.

Exact preservation is achieved by writing each textual value into the generated Python source as a string literal that is properly quoted and escaped — one representing embedded line terminators and backslashes in a way the Python compiler will reconstruct to the exact original characters. (By itself, the "r" string prefix cannot do the job, since a text value may end in a backslash.)

3. Coverage of all quoted-string-derived text

This quoting/escaping covers all textual values originating from MIB quoted strings, whichever MIB construct they belong to. At minimum, the following fall under it:

  • DESCRIPTION, REFERENCE
  • ORGANIZATION, CONTACT-INFO, LAST-UPDATED, REVISION descriptions
  • UNITS, DISPLAY-HINT
  • PRODUCT-RELEASE
  • String DEFVAL values (an OCTET STRING default value must have its literal characters reproduced, backslashes and embedded newlines among them).
4. Interaction with textFilter

The raw text content of a MIB textual value is what textFilter(symbol, text) receives, and the text it returns is the text to be emitted. The (possibly filtered) text is what the quoting/escaping described above must be applied to, so that the final compiled result reproduces the returned text exactly.

  • If an identity filter (lambda symbol, text: text) is what the caller supplies, the accessor result must equal the original MIB text content verbatim (with the preservation rules above still in force).
  • With no textFilter from the caller, textual values are still emitted and still reproduced correctly; a DEFVAL string value is no exception — its literal characters must remain intact when it is reproduced.

A long line that must not be wrapped, embedded tabs, literal backslashes, a rich set of special characters, blank lines, and a final line made up solely of a backslash — all of it preserved verbatim, with internal newlines kept and word wrapping applied nowhere.

DEFVAL given as a string (no textFilter):

DEFVAL { "\ntest
value\" }

→ the octet string that the resulting syntax value corresponds to is \ntest\nvalue\ (a literal backslash+n, an embedded newline, value, and a trailing literal backslash).

Recap of Constraints

  • Textual values must not get any trailing newline appended.
  • Word-wrapping must not be applied to textual values.
  • Embedded line terminators are kept as-is.
  • All backslashes — trailing ones included — must be treated as literal characters.
  • Consistent quoting/escaping must be applied to every quoted-string-derived textual value, and to DEFVAL string values as well.
  • textFilter support (default and caller-supplied) must be preserved, with quoting/escaping applied after filtering.
  • Compilability of the generated code must be maintained, and executing it must reproduce the original (or filtered) text exactly.

Task Specification: Support for SMIv1 Index Syntaxes in the PySNMP Code Generator

Context

pysmi translates SNMP MIB definitions into Python source code that targets the pysnmp runtime. The compilation pipeline used in this task consists of two stages, and both must produce compatible output:

  1. Symbol table generation — pysmi.codegen.symtable.SymtableCodeGen
  2. PySNMP code generation — pysmi.codegen.pysnmp.PySnmpCodeGen

This task is about two behaviors of the code generator when it handles conceptual tables (OBJECT-TYPE with INDEX clauses):

  • SMIv1 index syntaxes: In SMIv1 (RFC 1212), an INDEX clause may list type syntaxes (e.g. INTEGER, OCTET STRING, IpAddress, NetworkAddress) directly, in place of — or in addition to — the names of column object types. For each such syntax, the generator must synthesize "fake column" object-type instances so that the generated table row reports its index list correctly. At present this support exists only partially and must be completed.
  • Lenient SEQUENCE OF table type matching: A conceptual-table object type whose SYNTAX SEQUENCE OF <TypeName> references a type name that does not match the actual table-entry type must still be generated correctly, as long as the table-entry object type itself is well-formed.

Public API (must exist and be importable / callable exactly as stated)

These import paths and call signatures must all work:

from pysmi.parser.smi import parserFactory
from pysmi.parser.dialect import smiV1Relaxed
from pysmi.codegen.pysnmp import PySnmpCodeGen
from pysmi.codegen.symtable import SymtableCodeGen

The following usage pattern must be supported:

# SMIv1 relaxed dialect
ast = parserFactory(**smiV1Relaxed)().parse(mib_text)[0]

# default (SMIv2) dialect
ast = parserFactory()().parse(mib_text)[0]

mibInfo, symtable = SymtableCodeGen().genCode(ast, {}, genTexts=True)
mibInfo2, pycode = PySnmpCodeGen().genCode(ast, {mibInfo.name: symtable}, genTexts=True)
  • parserFactory(**kwargs) returns a parser class; calling it constructs a parser instance; .parse(text) returns a sequence whose first element is the AST.
  • smiV1Relaxed is a mapping of keyword arguments that can be passed as parserFactory(**smiV1Relaxed), selecting the relaxed SMIv1 grammar.
  • SymtableCodeGen().genCode(ast, mibs, genTexts=...) returns (mibInfo, symtable). mibInfo.name provides the MIB module name.
  • PySnmpCodeGen().genCode(ast, {name: symtable}, genTexts=...) returns (mibInfo, pycode), where pycode is a string of valid Python source.
  • Both genCode methods must accept genTexts=True, genTexts=False, and omission of the argument (which defaults to no texts).

The generated pycode must be compilable and executable in a namespace that contains a pysnmp MibBuilder instance under the key "mibBuilder"; executing it populates that namespace with named MIB symbols.

Required Behavior

Generation of fake columns for SMIv1 index syntaxes

If the INDEX clause of a table-entry OBJECT-TYPE contains an entry that is a bare type syntax and not the name of a defined column object type, the generator must create a synthetic column object (a "fake column") of PySNMP class MibTableColumn to represent that index component.

Naming of fake columns. A fake column is named pysmiFakeCol followed by a positive integer counter. The counter begins at 1 and increments for each fake column created, following the order in which the index syntaxes appear across the module. The numbering forms one running sequence that continues across multiple tables in the same module (i.e. it does not reset per table). Named index entries (those referencing existing columns) do not consume a counter value.

Each fake column that gets generated must be exposed in the executed namespace under its pysmiFakeCol<N> name.

OID / name assignment. A fake column's OID is built by appending a sub-identifier to the OID of the table-entry (row) object it belongs to. Sub-identifiers are assigned starting from the top of the 32-bit range and going downward: within a given table entry, the first fake column gets sub-identifier 4294967295 (2³² − 1), the second 4294967294, the third 4294967293, and so on. This descending assignment starts over for each table entry.

So for a row whose OID is (1, 3, 1), one index syntax produces a fake column named (1, 3, 1, 4294967295). For a row whose OID is (1, 3, 3) with index syntaxes at positions 1, 3 and 4 (position 2 being a named column), the fake columns receive the names (1, 3, 3, 4294967295), (1, 3, 3, 4294967294), and (1, 3, 3, 4294967293) respectively, in index order.

Syntax mapping. The PySNMP syntax object of a fake column is derived from the index syntax type:

INDEX syntax Class name of the fake column's getSyntax()
INTEGER Integer32
OCTET STRING OctetString
IpAddress IpAddress
NetworkAddress IpAddress

Access and status. Every fake column has:

  • max access "not-accessible" (as returned by getMaxAccess())
  • status "mandatory" (as returned by getStatus())
Index list of the table row

getIndexNames() on the table-entry (row) object must return a tuple of index descriptors in the exact order in which the INDEX clause lists them. Each descriptor is a 3-tuple of the form (0, <mib-module-name>, <column-name>):

  • When the reference is a named column, <column-name> is that column's own name (e.g. "testIndex").
  • When the entry is an index syntax, <column-name> is the name of the corresponding generated fake column (e.g. "pysmiFakeCol1").

Example: an INDEX { IpAddress, testIndex, OCTET STRING, NetworkAddress } in a module named TEST-MIB yields:

(
    (0, "TEST-MIB", "pysmiFakeCol1"),
    (0, "TEST-MIB", "testIndex"),
    (0, "TEST-MIB", "pysmiFakeCol2"),
    (0, "TEST-MIB", "pysmiFakeCol3"),
)
Generation of standard conceptual tables

For the tables covered above, the PySNMP objects that get generated must have the correct classes:

  • The table object (SYNTAX SEQUENCE OF ...) → class MibTable.
  • The table-entry / row object → class MibTableRow.
  • Real (named) column object types → class MibTableColumn, with getMaxAccess() and getStatus() reflecting the column's declared access and status (e.g. "read-write" / "mandatory" for SMIv1 columns).
Lenient SEQUENCE OF type-name matching (SMIv2)

If a conceptual-table object type declares SYNTAX SEQUENCE OF <TypeName> with a <TypeName> that does not match the name of the actual table-entry type used by the row object, the generator must still produce a correct table:

  • the table object's class is MibTable,
  • the row object's class is MibTableRow,
  • named index columns are class MibTableColumn,
  • getIndexNames() on the row returns the correct index descriptors (e.g. ((0, "TEST-MIB", "testIndex"),) for INDEX { testIndex }).

As long as the table-entry object type itself is well-formed, the mismatch between the SEQUENCE OF type name and the row entry type must not cause an error.

Consistency Requirement

The naming and numbering scheme for fake columns must agree exactly between the symbol table stage (SymtableCodeGen) and the code-generation stage (PySnmpCodeGen) (i.e. both must use identical pysmiFakeCol naming and the same counting/OID conventions), so that the code generated by the second stage resolves consistently against the symbol table produced by the first.

Remarks

  • All of the above must work for MIB modules parsed under both the relaxed SMIv1 dialect (smiV1Relaxed) and the default SMIv2 dialect, as applicable to each feature (SMIv1 index syntaxes are exercised under smiV1Relaxed; lenient SEQUENCE OF matching is exercised under the default dialect).
  • Both the genTexts=True and the default (no texts) modes must produce working, compilable, executable code.
