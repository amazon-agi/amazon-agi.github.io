Task Specification: Decoder Support for RuuviTag Data Format 3

Overview

You must implement decoding support for RuuviTag "Data Format 3" (Df3) sensor broadcasts in addition to the existing URL-based decoding. This requires creating a new decoder module, a decoder-selection function, and an update to the sensor data conversion logic.

Module and API Requirements

New module to add: ruuvitag_sensor/decoder.py

The following public API must be exposed by this module (the content of the existing ruuvitag_sensor/url_decoder.py module is being consolidated here):

class UrlDecoder

Provides decoding for the URL-based (Eddystone) data format.

  • Method decode_data(self, data): it accepts an encoded string and returns a dictionary with the decoded sensor values.
  • The returned dictionary must contain at least the following keys: temperature, pressure, humidity, identifier.
  • The existing URL decoding behavior is preserved. When the payload is a valid URL-format one, decoding yields values such as temperature = 26.5, pressure = 992.0, humidity = 26.5, and identifier = '0' (identifier is a string).
class Df3Decoder

Provides decoding for RuuviTag Data Format 3.

  • Method decode_data(self, data): it accepts a hex string (the raw payload) and returns a dictionary of decoded sensor values.
  • The keys that must be present in the returned dictionary are: temperature, pressure, humidity, battery, acceleration, acceleration_x, acceleration_y, acceleration_z.

Decoding contract with concrete values: when decode_data is handed the hex string '03291A1ECE1EFC18F94202CA0B5300000000BB', it must return a dictionary where:

  • temperature == 26.3 (°C)
  • pressure == 1027.66 (hPa)
  • humidity == 20.5 (%)
  • battery == 2899 (mV)
  • acceleration_x == -1000
  • acceleration_y != 0 (nonzero)
  • acceleration_z != 0 (nonzero)
  • acceleration != 0 (nonzero; a combined/aggregate acceleration value)

Layout of the Format 3 payload (hex, byte-oriented, big-endian for multi-byte fields):

  • Byte 0: the data format identifier (03).
  • Byte 1: humidity — an unsigned value; divide it by 2 to get percent.
  • Bytes 2–3: temperature — the integer part is byte 2, whose top bit is the sign; the fractional part is byte 3 (hundredths, i.e. divided by 100).
  • Bytes 4–5: pressure — an unsigned 16-bit value; add 50000 and then divide by 100 to get hPa.
  • Bytes 6–7: acceleration on the X axis — signed 16-bit (mg).
  • Bytes 8–9: acceleration on the Y axis — signed 16-bit (mg).
  • Bytes 10–11: acceleration on the Z axis — signed 16-bit (mg).
  • Bytes 12–13: battery voltage — unsigned 16-bit (mV).

The acceleration value is a nonzero aggregate derived from the three axis values.

def get_decoder(data_format)

A factory function that returns a decoder instance based on an integer data-format code:

  • Calling get_decoder(2) returns a UrlDecoder instance.
  • Calling get_decoder(3) returns a Df3Decoder instance.

Changes to RuuviTagSensor.convert_data

On RuuviTagSensor, the convert_data classmethod/staticmethod (located in the sensor module that the existing tests use) must change its return type:

  • What it must return is a tuple/sequence of two elements. Both index [0] and index [1] are used by callers.
  • If it receives input that is not valid sensor data (e.g. the string 'not_valid'), the returned value must have None at both [0] and [1].

Conceptually, the first element stands for the detected data format and the second for the raw payload to be decoded; when the data cannot be recognized, both are None.

Recognizing Data Format 3 Broadcasts

Besides the existing URL-format broadcasts, the scanning/discovery logic must recognize Data Format 3 manufacturer-specific broadcasts as well.

A Df3 broadcast takes the shape of a manufacturer-specific advertisement. As an example, this raw advertisement string:

1902010415FF990403291A1ECE1E02DEF94202CA0B5300000000BB

must be recognized as a valid RuuviTag broadcast (manufacturer ID 9904, followed by the Format 3 payload beginning with 03...).

If the set of scanned devices includes both valid URL-format devices and one valid Df3-format device (plus invalid/unrelated devices), then both find_ruuvitags() and get_datas(callback) must include the Df3 device in their results. To spell it out: with a scanned set containing four valid URL-format RuuviTags and one valid Df3 RuuviTag, find_ruuvitags() returns 5 tags, and get_datas invokes its callback 5 times.

Backward Compatibility

  • The import path ruuvitag_sensor.url_decoder is replaced by ruuvitag_sensor.decoder; importing UrlDecoder from the new module must work.
  • All URL-format decoding and discovery behavior that was supported previously must continue to work unchanged.

2. Data Format 3 decoder

Df3Decoder must expose the following:

def decode_data(self, data: str) -> dict
Layout of the input

data is a Data Format 3 payload, hex-encoded. Its relevant fields appear in the following order:

Hex-character range Size Field
data[0:2] 1 byte Data format byte, 03
data[2:4] 1 byte Humidity
data[4:8] 2 bytes Temperature
data[8:12] 2 bytes Pressure
data[12:16] 2 bytes Acceleration X
data[16:20] 2 bytes Acceleration Y
data[20:24] 2 bytes Acceleration Z
data[24:28] 2 bytes Battery voltage

One representative payload can be put together as:

'03' + humidity + temperature + pressure + accX + accY + accZ + battery + '00000000BB'

Bytes that come after the battery field neither shift the decoding of the listed fields nor otherwise change it.

Output

Given valid input, decode_data returns a dictionary that contains at least:

  • temperature: the temperature in degrees Celsius
  • humidity: the relative humidity percentage
  • pressure: the pressure in hPa
  • acceleration_x: the signed X-axis acceleration in mG
  • acceleration_y: the signed Y-axis acceleration in mG
  • acceleration_z: the signed Z-axis acceleration in mG
  • acceleration: the combined acceleration magnitude
  • battery: the battery voltage in mV
Rules for decoding the fields
Humidity

Read the humidity byte as an unsigned integer and multiply it by 0.5 percent:

  • The byte C8 (200) decodes to 100.0.
  • The byte 00 decodes to 0.0.
Temperature

In the first temperature byte, the most significant bit is a sign flag and the remaining bits form a 7-bit integer magnitude. The second byte holds the fractional magnitude in hundredths. Decode it this way:

  1. Apply the mask 0x7F to the first byte to obtain the integer magnitude.
  2. To that, add the second byte divided by 100.
  3. If the original first byte had its most significant bit set, negate the magnitude in its entirety, including the fractional part.
  4. Return the result rounded to two decimal places.

Specifically:

  • 7F63 decodes as 127 + 99/100, which is 127.99.
  • For FF63, the sign bit is set; after masking, its magnitude is likewise 127 + 99/100, so it decodes to -127.99.

The sign bit must not contribute to the integer magnitude, and negation must not be applied only to the integer part.

Pressure

Read the field as an unsigned 16-bit big-endian integer and compute:

pressure = (raw + 50000) / 100.0

Accordingly:

  • The value FFFF decodes to 1155.35 hPa.
  • The value 0000 decodes to 500.0 hPa.
Acceleration axes

Read each axis as a signed 16-bit big-endian two's-complement integer in mG:

  • The value 03E8 decodes to 1000.
  • The value FC18 decodes to -1000.

The acceleration value is the combined Euclidean magnitude of all three decoded axes:

sqrt(acceleration_x² + acceleration_y² + acceleration_z²)

Whenever at least one axis is nonzero, it must therefore be nonzero.

Battery

Read the battery field as an unsigned 16-bit big-endian integer in mV:

  • The value FFFF decodes to 65535.
  • The value 0000 decodes to 0.
Required compatibility examples

Decoding the payload

03291A1ECE1EFC18F94202CA0B5300000000BB

must produce the following values:

  • temperature == 26.3
  • humidity == 20.5
  • pressure == 1027.66
  • battery == 2899
  • acceleration_x == -1000
  • acceleration_y == -1726
  • acceleration_z == 714
  • acceleration is nonzero and represents the combined magnitude of those axes

The example with maximum values:

The example with the signed minimum temperature:

must produce temperature -127.99, humidity 0.0, pressure 500.0, battery 0, all three axes equal to -1000, and a nonzero combined acceleration.

Overview

  • ruuvitag_sensor.decoder.UrlDecoder, which provides decode_data(encoded).
  • ruuvitag_sensor.decoder.get_decoder(data_type). A call to get_decoder(2) returns a UrlDecoder, while get_decoder(3) returns a Df3Decoder.

Recognizing and Extracting Data Format 3

A raw BLE hexadecimal payload counts as a format-3 RuuviTag reading whenever it contains the marker FF990403. That marker may appear inside a larger advertising frame. Recognition must locate this sequence instead of requiring a specific total string length, a hard-coded marker offset, or the presence of null padding after the sensor fields.

The canonical decoder body starts with the final 03 byte of FF990403. Therefore, converting the two firmware variants below must identify data format 3 and expose these equivalent bodies:

Raw payload Format-3 body
1902010415FF990403291A1ECE1E02DEF94202CA0B5300000000BB 03291A1ECE1E02DEF94202CA0B5300000000BB
1902010415FF990403291A1ECE1E02DEF94202CA0B53BB 03291A1ECE1E02DEF94202CA0B53BB

In the first variant, four null bytes appear before the final trailer byte; the second variant leaves those nulls out. Both variants are valid. Bytes that optionally follow the battery field must not shift or change any sensor field. Full, traditionally padded format-3 payloads must keep working.

Df3Decoder.decode_data(data) accepts the hexadecimal format-3 body; when format-3 data is encountered inside a larger raw payload, it must be decoded from the body identified by FF990403. The optional null padding must not be required.

A raw value that is neither a supported URL-formatted RuuviTag broadcast nor valid format-3 data stays invalid. Specifically, RuuviTagSensor.convert_data('not_valid') returns (None, None), and invalid broadcasts are not reported as sensor readings.

  • temperature, in degrees Celsius;

  • acceleration_x, acceleration_y, and acceleration_z, in mG, decoded as signed 16-bit values; and
  • acceleration, the Euclidean magnitude of the three acceleration components.

The sensor fields are decoded from their usual format-3 positions and do not depend on optional data following the battery field. Malformed or insufficient hexadecimal input still returns None rather than a sensor dictionary.

Rules for Decoding Each Field

  • Temperature: Read the two bytes as a signed 16-bit big-endian number and multiply it by 0.005 degrees Celsius; the outcome is rounded to 2 decimal places. For example, 12FC decodes to 24.30.
  • Humidity: Read the two bytes as an unsigned 16-bit big-endian number and multiply it by 0.0025 percent; the outcome is rounded to 2 decimal places. For example, 5394 decodes to 53.49.
  • Pressure: Read the two bytes as an unsigned 16-bit big-endian number, add 50000, and divide the sum by 100 to obtain hPa; the outcome is rounded to 2 decimal places. For example, C37C decodes to 1000.44.
  • Acceleration: Each axis is a signed 16-bit big-endian integer, with its value given in mG. The byte strings 0004, FFFC, and 040C decode to 4, -4, and 1036, respectively.
  • Power information: Combine the two bytes into a single unsigned 16-bit big-endian value.
    • The upper 11 bits encode the battery voltage in millivolts, with a 1600 mV offset applied. Put differently, the voltage in volts is given by ((power_info >> 5) + 1600) / 1000.
    • The lower 5 bits encode the transmit power, computed as (power_info & 0x1F) * 2 - 40 dBm.
    • Decoding AC36 therefore gives a battery voltage of 2.977 V and a transmit power of 4 dBm.
  • Movement counter: Read the byte as an unsigned integer; 42, for example, decodes to 66.
  • Measurement sequence number: Here the two bytes form an unsigned 16-bit big-endian integer; 00CD decodes to 205.
  • MAC address: The six bytes are written out as lowercase hexadecimal, and no delimiters are used. CBB8334C884F decodes to cbb8334c884f.

  • RSSI (2 hex characters, optional)

For the 'rssi' field, the decoding rules are as follows:

  • When the RSSI segment is present (the payload carries the two trailing hex characters after the MAC): the two hex characters are to be interpreted as a signed 8-bit two's-complement integer, and that signed integer is the resulting 'rssi' value.
    • Example: a trailing hex byte of C6 yields rssi == -58.
    • Example: a trailing hex byte of B8 yields rssi == -72.
  • When the RSSI segment is absent (the payload terminates at the MAC): the value of 'rssi' must be None.

All other decoded fields (temperature, humidity, pressure, acceleration components, power/battery info, movement counter, measurement sequence number, MAC) must still be decoded exactly as they were previously, and the presence or absence of the RSSI segment must not affect them.

Public API

The behavior described above must be reachable via the existing decoder that decodes DF5 data. On the decoder object, a method with the following signature is exposed:

decode_data(data: str) -> dict
  • Input: the raw hex payload string (supplied with or without the optional 2-character trailing RSSI segment).
  • Output: a dictionary of decoded measurement values in which the 'rssi' key is included as described above.

This method must be accessible on the same decoder instance/module that currently handles DF5 decoding within the package (module path ruuvitag_sensor.decoder).

Sensor Data Retrieval Integration

Raw advertisement data is consumed by the higher-level sensor retrieval APIs, which pass the payload (including any trailing RSSI byte) through the decoder. Consequently, the 'rssi' field must be carried by the decoded dictionaries returned by these APIs, populated from the trailing RSSI byte of the raw payload.

Below are the relevant public APIs (class RuuviTagSensor in module ruuvitag_sensor.ruuvi):

  • RuuviTagSensor.find_ruuvitags() — returns a mapping of the tags that were discovered.
  • RuuviTagSensor.get_data_for_sensors(macs, ...) — returns a mapping whose keys are MAC addresses; each value is the decoded measurement dictionary, and it must include the 'rssi' field derived from the raw payload for that tag.
  • RuuviTagSensor.get_data(callback) — invokes the callback, giving it the discovered tag data.

Raw payloads that include the trailing RSSI byte must be handled correctly by these APIs: they must decode without error, and the measurement dictionaries yielded must have an 'rssi' value that reflects the trailing byte (e.g., a payload ending in B8 produces rssi == -72). Payloads that carry a valid DF5 advertisement with an appended RSSI byte must be recognized and included in the returned results, just as any other valid DF5 advertisement is.

Constraints

  • The decoding of any existing DF5 field must not be changed.
  • DF5 decode output must always contain the 'rssi' key: the value is an integer when the RSSI byte is present and None when it is absent.
