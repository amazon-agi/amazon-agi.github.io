Task Specification: RuuviTag Data Format 3 Decoder Support

Overview

You must implement decoding support for RuuviTag "Data Format 3" (Df3) sensor broadcasts, alongside the existing URL-based decoding. This requires creating a new decoder module, a decoder-selection function, and updating the sensor data conversion logic.

Module & API Requirements

New module: ruuvitag_sensor/decoder.py

This module must expose the following public API (the existing ruuvitag_sensor/url_decoder.py module content is being consolidated here):

class UrlDecoder

A decoder for the URL-based (Eddystone) data format.

  • Method: decode_data(self, data) — accepts an encoded string and returns a dictionary with the decoded sensor values.
  • The returned dictionary must contain at least these keys: temperature, pressure, humidity, identifier.
  • This preserves the existing URL decoding behavior. For a valid URL-format payload, decoding yields values such as temperature = 26.5, pressure = 992.0, humidity = 26.5, and identifier = '0' (identifier is a string).
class Df3Decoder

A decoder for RuuviTag Data Format 3.

  • Method: decode_data(self, data) — accepts a hex string (the raw payload) and returns a dictionary of decoded sensor values.
  • The returned dictionary must contain the following keys: temperature, pressure, humidity, battery, acceleration, acceleration_x, acceleration_y, acceleration_z.

Concrete decoding contract: given the hex string '03291A1ECE1EFC18F94202CA0B5300000000BB', decode_data must return a dictionary where:

  • temperature == 26.3 (°C)
  • pressure == 1027.66 (hPa)
  • humidity == 20.5 (%)
  • battery == 2899 (mV)
  • acceleration_x == -1000
  • acceleration_y != 0 (nonzero)
  • acceleration_z != 0 (nonzero)
  • acceleration != 0 (nonzero; a combined/aggregate acceleration value)

Format 3 payload layout (hex, byte-oriented, big-endian for multi-byte fields):

  • Byte 0: data format identifier (03).
  • Byte 1: humidity — unsigned value, divide by 2 to get percent.
  • Bytes 2–3: temperature — byte 2 is the integer part where the top bit is the sign, byte 3 is the fractional part (hundredths, i.e. divided by 100).
  • Bytes 4–5: pressure — unsigned 16-bit value; add 50000 then divide by 100 to get hPa.
  • Bytes 6–7: acceleration on X axis — signed 16-bit (mg).
  • Bytes 8–9: acceleration on Y axis — signed 16-bit (mg).
  • Bytes 10–11: acceleration on Z axis — signed 16-bit (mg).
  • Bytes 12–13: battery voltage — unsigned 16-bit (mV).

acceleration is a nonzero aggregate derived from the three axis values.

def get_decoder(data_format)

A factory function returning a decoder instance based on an integer data-format code:

  • get_decoder(2) returns a UrlDecoder instance.
  • get_decoder(3) returns a Df3Decoder instance.

Changes to RuuviTagSensor.convert_data

The convert_data classmethod/staticmethod on RuuviTagSensor (in the sensor module used by the existing tests) must change its return type:

  • It must return a tuple/sequence of two elements. Index [0] and index [1] are both used by callers.
  • When given input that is not valid sensor data (e.g. the string 'not_valid'), both [0] and [1] of the returned value must be None.

The first element conceptually represents the detected data format, and the second the raw payload to be decoded; both are None when the data cannot be recognized.

Data Format 3 Broadcast Recognition

The scanning/discovery logic must recognize Data Format 3 manufacturer-specific broadcasts in addition to the existing URL-format broadcasts.

A Df3 broadcast appears as a manufacturer-specific advertisement. For example, the raw advertisement string:

1902010415FF990403291A1ECE1E02DEF94202CA0B5300000000BB

must be recognized as a valid RuuviTag broadcast (manufacturer ID 9904, followed by the Format 3 payload beginning with 03...).

Given a set of scanned devices that includes both valid URL-format devices and one valid Df3-format device (plus invalid/unrelated devices), both find_ruuvitags() and get_datas(callback) must include the Df3 device in their results. Specifically, when the scanned set contains four valid URL-format RuuviTags and one valid Df3 RuuviTag, find_ruuvitags() returns 5 tags and get_datas invokes its callback 5 times.

Backward Compatibility

  • The import path ruuvitag_sensor.url_decoder is replaced by ruuvitag_sensor.decoder; UrlDecoder must be importable from the new module.
  • All previously-supported URL-format decoding and discovery behavior must continue to work unchanged.

2. Data Format 3 decoder

Df3Decoder must expose:

def decode_data(self, data: str) -> dict
Input layout

data is a hex-encoded Data Format 3 payload. Its relevant fields are laid out in this order:

Hex-character range Size Field
data[0:2] 1 byte Data format byte, 03
data[2:4] 1 byte Humidity
data[4:8] 2 bytes Temperature
data[8:12] 2 bytes Pressure
data[12:16] 2 bytes Acceleration X
data[16:20] 2 bytes Acceleration Y
data[20:24] 2 bytes Acceleration Z
data[24:28] 2 bytes Battery voltage

A representative payload can be assembled as:

'03' + humidity + temperature + pressure + accX + accY + accZ + battery + '00000000BB'

Bytes after the battery field do not shift or otherwise change the listed field decoding.

Output

For valid input, decode_data returns a dictionary containing at least:

  • temperature: temperature in degrees Celsius
  • humidity: relative humidity percentage
  • pressure: pressure in hPa
  • acceleration_x: signed X-axis acceleration in mG
  • acceleration_y: signed Y-axis acceleration in mG
  • acceleration_z: signed Z-axis acceleration in mG
  • acceleration: combined acceleration magnitude
  • battery: battery voltage in mV
Field decoding rules
Humidity

Interpret the humidity byte as an unsigned integer and multiply it by 0.5 percent:

  • C8 (200) decodes to 100.0.
  • 00 decodes to 0.0.
Temperature

The first temperature byte contains a sign flag in its most significant bit and a 7-bit integer magnitude in its remaining bits. The second byte contains the fractional magnitude in hundredths. Decode it as follows:

  1. Mask the first byte with 0x7F to obtain the integer magnitude.
  2. Add the second byte divided by 100.
  3. If the original first byte had its most significant bit set, negate the complete magnitude, including the fractional part.
  4. Return the result rounded to two decimal places.

In particular:

  • 7F63 decodes as 127 + 99/100, or 127.99.
  • FF63 has its sign bit set; after masking, its magnitude is also 127 + 99/100, so it decodes to -127.99.

The sign bit must not contribute to the integer magnitude, and negation must not be applied only to the integer portion.

Pressure

Interpret the field as an unsigned 16-bit big-endian integer and calculate:

pressure = (raw + 50000) / 100.0

Thus:

  • FFFF decodes to 1155.35 hPa.
  • 0000 decodes to 500.0 hPa.
Acceleration axes

Interpret each axis as a signed 16-bit big-endian two's-complement integer in mG:

  • 03E8 decodes to 1000.
  • FC18 decodes to -1000.

The combined acceleration value is the Euclidean magnitude of all three decoded axes:

sqrt(acceleration_x² + acceleration_y² + acceleration_z²)

It must therefore be nonzero whenever at least one axis is nonzero.

Battery

Interpret the battery field as an unsigned 16-bit big-endian integer in mV:

  • FFFF decodes to 65535.
  • 0000 decodes to 0.
Required compatibility examples

Decoding:

03291A1ECE1EFC18F94202CA0B5300000000BB

must produce these values:

  • temperature == 26.3
  • humidity == 20.5
  • pressure == 1027.66
  • battery == 2899
  • acceleration_x == -1000
  • acceleration_y == -1726
  • acceleration_z == 714
  • acceleration is nonzero and represents the combined magnitude of those axes

The maximum-value example:

must produce temperature 127.99, humidity 100.0, pressure 1155.35, battery 65535, all three axes equal to 1000, and a nonzero combined acceleration.

The signed minimum-temperature example:

must produce temperature -127.99, humidity 0.0, pressure 500.0, battery 0, all three axes equal to -1000, and a nonzero combined acceleration.

Data-Format-3 Recognition and Extraction

A raw BLE hexadecimal payload is a format-3 RuuviTag reading when it contains the marker FF990403. The marker may occur within a larger advertising frame. Recognition must locate that sequence rather than require a particular total string length, a hard-coded marker offset, or the presence of null padding after the sensor fields.

The canonical decoder body begins with the final 03 byte of FF990403. Thus conversion of the two firmware variants below must identify data format 3 and expose these equivalent bodies:

Raw payload Format-3 body
1902010415FF990403291A1ECE1E02DEF94202CA0B5300000000BB 03291A1ECE1E02DEF94202CA0B5300000000BB
1902010415FF990403291A1ECE1E02DEF94202CA0B53BB 03291A1ECE1E02DEF94202CA0B53BB

The first variant has four null bytes before its final trailer byte; the second omits those nulls. Both are valid. Optional bytes after the battery field must not shift or change any sensor field. Full, traditionally padded format-3 payloads must continue to work.

Df3Decoder.decode_data(data) accepts the hexadecimal format-3 body, and format-3 data encountered in a larger raw payload must be decoded from the body identified by FF990403. It must not require the optional null padding.

A raw value that is neither a supported URL-formatted RuuviTag broadcast nor valid format-3 data remains invalid. In particular, RuuviTagSensor.convert_data('not_valid') returns (None, None), and invalid broadcasts are not reported as sensor readings.

  • acceleration, the Euclidean magnitude of the three acceleration components.

The sensor fields are decoded from their normal format-3 positions and are independent of optional data following the battery field. Malformed or insufficient hexadecimal input continues to return None rather than a sensor dictionary.

Data decoding

Raw BLE payloads must be decoded into sensor-reading dictionaries. For the payloads used:

  • A decoded reading includes identifier (a string) and rssi (an integer signed value derived from the payload), among other sensor fields.
  • Invalid/unsupported payloads must not produce readings (they are skipped/ignored).
MAC filtering

Where a macs list is provided to the scanning methods, only readings whose MAC address is present in the list are retained; readings for other MACs are discarded.

Adapter selection via ble

All scanning/first-data operations in RuuviTagSensor and RuuviTag must go through the module-level ruuvitag_sensor.ruuvi.ble object. Replacing that object (for example, with a dummy adapter instance) must fully redirect where sync and async data come from. The sync methods use the object's get_data / get_first_data; the async method uses the object's async get_data.

Example concrete expectations

  • Given a source that yields 9 valid items: find_ruuvitags() yields a mapping of length 9; get_data(callback) invokes the callback 9 times.
  • Given get_data_for_sensors(['CC:2C:6A:1E:59:3D', 'DD:2C:6A:1E:59:3D', 'EE:2C:6A:1E:59:3D', 'D5:57:97:65:88:14']), the result contains those MACs, with data['EE:2C:6A:1E:59:3D']['identifier'] == '0' and data['D5:57:97:65:88:14']['rssi'] == -72.
  • Given an async source yielding 3 items, get_data_async() consumed via async for yields 3 readings; get_data_async(['EB:A5:D1:02:CE:68', 'EC:4D:A7:95:08:6B']) yields only the 2 matching readings.

Constraints

  • The sync generator methods must run to completion synchronously (not requiring an already-running event loop; use run_until_complete-style scheduling internally rather than asyncio.run).
  • No public behavior beyond what is described above is required.

RuuviTagAsync(mac)

It must provide:

  • A state property that is initially {}.
  • An asynchronous method:
await tag.update()

update() must work with the active asynchronous BLE backend and return decoded sensor data.

For MAC "48:2C:6A:1E:59:3D", when the backend’s asynchronous get_first_data(mac, bt_device) returns:

{

    "pressure": 995,
    "humidity": 30,

Additional decoded fields are permitted.

ruuvitag_sensor.ruuvi.RuuviTagSensor.find_ruuvitags_async

Add an awaitable class API:

await RuuviTagSensor.find_ruuvitags_async()

Behavior:

  • When the active ruuvitag_sensor.ruuvi.ble backend supports asynchronous BLE communication, consume its asynchronous data source and return a collection containing one entry for each valid received sensor advertisement.
  • If the backend supplies three valid advertisements, the returned collection must have length 3.
  • When the active backend is not an asynchronous BLE communication backend, the call must raise an exception. No particular exception subtype or message is required.
Existing asynchronous stream API

The following API must remain available:

RuuviTagSensor.get_data_async()
RuuviTagSensor.get_data_async(macs)

It returns an asynchronous iterable.

  • Without a MAC filter, it must yield each of three valid advertisements supplied by the asynchronous backend.
  • With the positional MAC list:
["EB:A5:D1:02:CE:68", "EC:4D:A7:95:08:6B"]

and backend data for those two MACs plus "CD:D4:FA:52:7A:F2", it must yield only the two matching entries.

Required public API

In ruuvitag_sensor.ruuvi, the class RuuviTagSensor must expose these class-level async APIs:

  • RuuviTagSensor.get_data_async() — returns an async iterator.
  • await RuuviTagSensor.find_ruuvitags_async() — returns the discovered sensors collection.
  • await RuuviTagSensor.get_data_for_sensors_async(mac_addresses, search_duration_sec) — returns a dictionary mapping requested MAC addresses to decoded sensor-state dictionaries. The second positional argument must accept the value 4.

Collecting data for selected sensors

For:

mac_addresses = [
    "EB:A5:D1:02:CE:68",
    "CD:D4:FA:52:7A:F2",
    "CE:D6:05:F5:17:AA",
]

calling:

data = await RuuviTagSensor.get_data_for_sensors_async(mac_addresses, 4)

against the four-packet stream above must return a dictionary with exactly these three keys:

  • EB:A5:D1:02:CE:68
  • CD:D4:FA:52:7A:F2
  • CE:D6:05:F5:17:AA

The unrequested sensor EC:4D:A7:95:08:6B must not be included. Encountering that unrequested sensor must not prevent collection of the later requested sensor.

The returned decoded states must include:

  • data["EB:A5:D1:02:CE:68"]["temperature"] == 24.98
  • data["CD:D4:FA:52:7A:F2"]["temperature"] == 23.73
  • data["CE:D6:05:F5:17:AA"]["rssi"] == -90
