06 Parsing Update-Lineage Rows with Aggregation Across Rows and De-duplication 1637 words · rewritten by GPT-5.6-sol, reworded by GLM-5.3-Flash

Task Specification: Parsing Update-Lineage Rows with Aggregation Across Rows and De-duplication

General Description

The task is to implement or modify parse_update_lineage on the Reader class. Construction of a reader takes the configuration as its first positional argument:

reader = Reader(READER_CONFIG)

The public signature of the method reads:

def parse_update_lineage(self, json_rows) -> list:
    ...

From update-lineage rows, the method produces serialized Apache Atlas process update payloads. Source and target entities are handled as references by type and qualified name; this method does not create them, and they are assumed to exist already.

Shape of the Input Rows

json_rows takes the form of a list of dictionaries. Under the default reader configuration, the keys present in every row are the following:

  • "Target typeName" together with "Target qualifiedName", which cover the process output.
  • "Source typeName" together with "Source qualifiedName", which cover the process input.
  • "Process name", "Process qualifiedName", and "Process typeName", which cover the process being updated.

The prefix words for source, target, and process have their origin in the reader configuration. Should those prefixes be customized, the method must work from the configured prefixes combined with the same typeName, qualifiedName, and name suffixes, not from hard-coded defaults.

An empty json_rows list on input leads to an empty result list. A row in which a required key is missing is malformed, and such a row must not be accepted silently.

Assigning Rows to Processes

Rows are grouped on the basis of the composite process identity:

(Process qualifiedName, Process typeName)

All rows that share the same values for both fields describe one process update, and exactly one result entry must come out of them. A qualified name that differs, or a type name that differs, marks a different process. Process name counts as process metadata; it is not an extra grouping key. The process metadata described by the rows of one group is expected to be consistent.

Result entries keep the ordering in which their process groups make their first appearance in json_rows. The scoping of aggregation to the individual group must also hold: a reference from one process must never be merged into a different process.

What a Result Entry Contains

The list that the method returns holds serialized process dictionaries rather than AtlasProcess instances. Every result follows the usual serialized process shape: it contains the process type, the GUID that the reader generated for it, the attributes that identify it, and the relationship attributes. To be concrete:

{
    "typeName": <Process typeName>,
    "guid": <GUID allocated by the reader>,
    "attributes": {
        "name": <Process name>,
        "qualifiedName": <Process qualifiedName>,
        "inputs": <aggregated source-side value>,
        "outputs": <aggregated target-side value>
    },
    "relationshipAttributes": {}
}

For each distinct process group there is only one process payload, and likewise only one process GUID.

When a source or target is normal, it is represented in the form of an Atlas object-ID reference:

{
    "typeName": <the entity typeName>,
    "uniqueAttributes": {
        "qualifiedName": <the entity qualifiedName>
    }
}

The entries inside attributes["inputs"] are built from the source fields; those inside attributes["outputs"] are built from the target fields.

Aggregating the Source and Target Sides Independently

For each process, aggregate its two sides independently:

  • inputs is put together out of all applicable source entities across the group's rows.
  • outputs is put together out of all applicable target entities across the group's rows.
  • A row may update both sides of the process, may update only one of them, or may explicitly clear one side. Its treatment on one side must not suppress the contribution it makes on the other side.

As an illustration, take two rows for one process that carry different real sources, with the second row leaving its target unspecified: both sources end up included, and the target of the first row remains the sole output. A matching rule covers the case of multiple targets together with an unspecified source.

The Three Meanings of the Qualified-Name Field

On each side, the qualified-name field carries one of three distinct meanings. None and the literal string "N/A" do not count as interchangeable.

Supplying a real qualified name

A reference is explicitly supplied by any qualified name whose value is other than None or "N/A". Add the reference under the typeName of that side; de-duplication applies to it.

None: no update happens on that side

When the qualified name is Python None, the row in question does not update that side of the process. It adds no reference, nor does it clear the references contributed by other rows of that same process group.

When every row of a process group carries None on a side, and no row supplies either a real qualified name or "N/A" for that side, the literal Python None is what the final value of that side must remain. The interpretation is a partial update: the server-side lineage already present is left unchanged. Turning it into [] must not happen. Hence:

  • A source side that remains unspecified throughout yields attributes["inputs"] is None.
  • A target side that remains unspecified throughout yields attributes["outputs"] is None.

When real references have been provided by other rows, None values — whether they intervene or come later — simply leave intact the list that has already been aggregated.

"N/A": the side is cleared explicitly

A destructive update is what a qualified name equal to the exact literal string "N/A" represents. That side is set to an empty list, and every reference accumulated beforehand for that side within the same process is discarded:

  • With "N/A" in the source qualified name, inputs is set to [].
  • With "N/A" in the target qualified name, outputs is set to [].

What it expresses is an explicit request that all existing references be removed; it goes beyond a row that merely contributes no reference. The corresponding type field is normally "N/A" as well, but the sentinel does not have an object-ID reference created for it.

For this purpose, the rows inside a process group are applied in the order in which they appear as input. As a consequence, a destructive marker wipes out the references that were seen before it; None coming after a clear leaves the empty list intact, whereas a real qualified name that arrives later explicitly populates the side once more.

De-duplication of References

De-duplication applies within each process group to inputs and outputs separately, with entity qualified name as the key:

  • A source qualified name that is repeated produces only one input reference.
  • A target qualified name that is repeated produces only one output reference.
  • De-duplication operates per side and per process: no conflict arises between an input and an output, and references in different processes likewise do not conflict.
  • All distinct qualified names are kept, even when they originate in separate rows.

The order of references tracks the first occurrence of each retained qualified name, counted from the most recent explicit clear of that side. Accordingly, one process with two identical rows ends up with one process entry, one input, and one output.

Required Aggregate Behavior

The behavior that is required is summarized by the cases that follow:

  1. Full update: One input reference and one output reference are what a row with real source and target values yields. The process type, name, and qualified name that were supplied are the ones the process result uses.
  2. Multiple inputs: For one process, take two rows with distinct sources where the second target is None; these yield one process result containing both inputs and only the real output.
  3. Multiple outputs: For one process, take two rows with distinct targets where the second source is None; these yield one process result containing both outputs and only the real input.
  4. Duplicate rows: Two rows that are identical and belong to one process yield one process result, one input, and one output.
  5. Destructive marker after a value: Suppose a later row carries the target qualified name "N/A": all earlier outputs belonging to that process are then removed. Should that row supply a distinct real source, that source still goes through aggregation. With two rows of this kind, the result can therefore hold two inputs and outputs == []. The behavior on the source side is analogous.
  6. Entirely unspecified side: When the source qualified names of a process are all None, that process has inputs is None; when the target qualified names of a process are all None, it has outputs is None.
  7. Explicitly empty side: Once a process has been explicitly cleared by means of "N/A", that side holds [], and this is what distinguishes it from the None partial-update value.

Emission of Warnings

Emit non-fatal warnings via Python's standard warning mechanism whenever the situations below arise:

  • A source qualified name turns out to duplicate a value that inputs already collected for the same process, and de-duplication of it follows.
  • A "N/A" marker, whether on the source or the target, arrives after a real reference has already been built up on the corresponding side of the process.

Processing must not be interrupted by warnings, and the required aggregate result must not be altered by them either. Specifically, the applicable side is still cleared by the destructive marker, and a duplicate still shows up only once.

Scope and Compatibility

  • Leave the existing Reader(READER_CONFIG) construction and the parse_update_lineage(json_rows) API untouched.
  • Keep serialized Atlas process payloads and Atlas object-ID reference formatting as they are.
  • The method performs none of the following: fetching a process, merging against remote state, creating referenced datasets, or validating that referenced entities exist. Preparing update payloads is the only thing it does. Those update intentions reach the eventual consumer through None and [].

Aim

Write a utility function that takes a flat list of Atlas entity JSON dictionaries and splits it into batches whose size is bounded, ensuring that entities connected through relationships end up together in the same batch.

Public Interface

In addition, the module pyapacheatlas.core.util must go on exposing the existing GuidTracker class, which stays importable from the same location.

Function Signature
def batch_dependent_entities(entities, batch_size=...):
    ...
  • entities: a list of entity dictionaries, with each item being the JSON/dict representation of an Atlas entity.
  • batch_size: an integer keyword argument that caps how many entities any single output batch is allowed to hold.
What the Function Returns

The return value is a list of batches; every batch is a list (or collection) consisting of entity dictionaries drawn from the input. When all batches are concatenated, every input entity is present exactly once.

Input Entity Dictionaries

Every entity dictionary includes at least:

  • A guid field that serves as the entity's unique identifier. When entities come from a single upload, their guids are typically small integers or strings that look numeric (e.g., 0, 1, -1, "-1").
  • A relationshipAttributes field: relationship names mapped to relationship references. Each referenced value is again a dictionary, and it may contain a guid field that points at another entity.

What Counts as a Dependency

Entities count as dependent — they must land in the same batch — whenever one of them references the other by way of a relationship guid whose value is a numeric guid (an integer, or a string standing for an integer such as "-1").

  • A relationship reference carrying a numeric guid functions as a pointer to another entity in the same upload set. References of this sort tie entities together into a connected group, whose members must stay together.
  • When a relationship reference's guid is not numeric (e.g., a real persisted guid such as "abc-123"), it does not count as an in-upload dependency. No obligation to group entities together arises from such a reference, and it is ignored during batching.

Grouping by dependency works both transitively and in an undirected fashion: if A relates to B and B relates to C (via numeric guids), then all three of A, B, and C wind up in one connected group, no matter which direction the relationship runs or in what sequence the entities show up in the input list. Nothing about the input order guarantees that related entities land next to each other.

Rules Governing Batching

  1. Take the numeric-guid relationships described above and compute the connected groups of entities from them. Entities lacking a qualifying numeric-guid relationship constitute singleton groups.
  2. Each connected group must be preserved intact inside one batch — a group is never to be split across batches.
  3. Pack the groups into batches while making sure that no batch goes over batch_size entities. Independent (single or small) groups may share one batch, provided the total entity count in that batch remains within batch_size.
  4. Strive for a minimal set of batches that satisfies the constraints above (that is, create no more batches than necessary, and use independent groups to fill batches wherever they fit).

Worked Examples

  • No dependencies: Suppose 10 entities that are fully independent of one another are supplied, with batch_size=2; the outcome is 5 batches of 2 entities apiece.

  • With dependencies: Suppose 16 entities, some of which are joined into connected groups through numeric-guid relationships (e.g., one connected group of 7 entities, another of 3 entities, and the rest independent), along with batch_size=7; the outcome is 3 batches: the group of 7 takes one whole batch, the group of 3 plus however many independent entities are needed takes a second, and the independent entities still left over take the last one — no batch goes beyond 7.

  • Non-numeric guid reference: Suppose 4 entities, one of which carries a relationship aimed at a non-numeric guid (e.g., "abc-123", i.e., a reference to a pre-existing entity that is not part of the upload set). A relationship of that sort does not give rise to a dependency. Under batch_size=2, entities that would be grouped only via such a non-numeric reference stay ungrouped; the outcome is 2 batches (any dependency that genuinely stems from a numeric guid is still honored).

Remarks

  • Grouping between entities is established only by relationships whose referenced guid is numeric (integer or integer-valued string, negative values included).
  • In principle, a group's size may be larger than batch_size; the only groups the tests exercise are ones that fit within the given batch_size, and consequently grouped entities always fit inside one batch under the exercised conditions.
