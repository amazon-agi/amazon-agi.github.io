{
    "typeName": <Process typeName>,

        "inputs": <inputs value>,

    }

Side qualifiedName value Resulting list value for that side
A real value [ <reference dict> ]
None / absent None
"N/A" []

Task Specification: Lineage Update Parsing with Multi-Row Aggregation and De-duplication

Overview

Implement or modify parse_update_lineage on the Reader class. A reader is constructed with its configuration as the first positional argument:

reader = Reader(READER_CONFIG)

The method has this public signature:

def parse_update_lineage(self, json_rows) -> list:
    ...

It converts update-lineage rows into serialized Apache Atlas process update payloads. Source and target entities are referenced by type and qualified name; they are not created by this method and are assumed to already exist.

Input Rows

json_rows is a list of dictionaries. With the default reader configuration, every row contains these keys:

  • "Target typeName" and "Target qualifiedName" for the process output.
  • "Source typeName" and "Source qualifiedName" for the process input.
  • "Process name", "Process qualifiedName", and "Process typeName" for the process being updated.

The source, target, and process prefix words come from the reader configuration. If those prefixes are customized, the method must use the configured prefixes with the same typeName, qualifiedName, and name suffixes rather than hard-coding the defaults.

An empty json_rows list produces an empty result list. A row missing a required key is malformed and must not be silently accepted.

Grouping Rows into Processes

Group rows by the composite process identity:

(Process qualifiedName, Process typeName)

All rows with the same values for both fields describe one process update and must produce exactly one result entry. A different qualified name or a different type name denotes a different process. Process name is process metadata, not an additional grouping key. Rows belonging to one group are expected to describe consistent process metadata.

The result entries preserve the order in which their process groups first appear in json_rows. Aggregation must also remain scoped to each group: references from one process must never be merged into another process.

Result Entry Shape

Return a list of serialized process dictionaries, not AtlasProcess instances. Each result has the normal serialized process shape, including the process type, its generated reader GUID, its identifying attributes, and relationship attributes. In particular:

{
    "typeName": <Process typeName>,
    "guid": <GUID allocated by the reader>,
    "attributes": {
        "name": <Process name>,
        "qualifiedName": <Process qualifiedName>,
        "inputs": <aggregated source-side value>,
        "outputs": <aggregated target-side value>
    },
    "relationshipAttributes": {}
}

Only one process payload and one process GUID are produced for each distinct process group.

A normal source or target is represented as an Atlas object-ID reference:

{
    "typeName": <the entity typeName>,
    "uniqueAttributes": {
        "qualifiedName": <the entity qualifiedName>
    }
}

Source fields build entries in attributes["inputs"]; target fields build entries in attributes["outputs"].

Independent Source and Target Aggregation

Aggregate the two sides independently for each process:

  • inputs is formed from all applicable source entities in the group's rows.
  • outputs is formed from all applicable target entities in the group's rows.
  • A row may update both sides, only one side, or explicitly clear one side. Its treatment on one side must not suppress its contribution on the other side.

For example, if two rows for one process have different real sources but the second row leaves its target unspecified, both sources are included while the first row's target remains the sole output. The analogous rule applies to multiple targets and an unspecified source.

Qualified-Name Control Values

The qualified-name field on each side has three distinct meanings. None and the literal string "N/A" are not interchangeable.

Real qualified name

Any qualified name other than None or "N/A" explicitly supplies a reference. Add the reference using that side's typeName, subject to de-duplication.

None: leave that side unchanged

A qualified name of Python None means that the row does not update that side of the process. It neither adds a reference nor clears references collected from other rows in the same process group.

If every row in a process group has None for a side and no row supplies either a real qualified name or "N/A" for that side, the final value for that side must remain the literal Python None. This represents a partial update that leaves the existing server-side lineage unchanged. It must not be converted to []. Thus:

  • A source side that is unspecified throughout yields attributes["inputs"] is None.
  • A target side that is unspecified throughout yields attributes["outputs"] is None.

If other rows provide real references, intervening or later None values simply leave the already aggregated list intact.

"N/A": explicitly clear that side

A qualified name equal to the exact literal string "N/A" is a destructive update. It sets that side to an empty list and discards every reference previously accumulated for that side of the same process:

  • "N/A" on the source qualified name sets inputs to [].
  • "N/A" on the target qualified name sets outputs to [].

This is an explicit request to remove all existing references, not merely a row that contributes no reference. The corresponding type field is normally also "N/A", but no object-ID reference is created for the sentinel.

Rows within a process group are applied in input order for this purpose. Consequently, a destructive marker clears references seen before it; None after a clear leaves the empty list intact, while a later real qualified name explicitly populates the side again.

De-duplication

Within each process group, de-duplicate inputs and outputs separately by entity qualified name:

  • Repeated source qualified names produce only one input reference.
  • Repeated target qualified names produce only one output reference.
  • De-duplication is per side and per process; an input does not conflict with an output, and references in different processes do not conflict.
  • Distinct qualified names are all retained, even when they come from separate rows.

Reference order follows the first occurrence of each retained qualified name since the most recent explicit clear of that side. Two identical rows for one process therefore produce one process entry with one input and one output.

Required Aggregate Outcomes

The following cases summarize the required behavior:

  1. Full update: A row with real source and target values yields one input reference and one output reference. The process result uses the supplied process type, name, and qualified name.
  2. Multiple inputs: Two rows for one process with distinct sources, where the second target is None, yield one process result with both inputs and only the real output.
  3. Multiple outputs: Two rows for one process with distinct targets, where the second source is None, yield one process result with both outputs and only the real input.
  4. Duplicate rows: Two identical rows for one process yield one process result, one input, and one output.
  5. Destructive marker after a value: If a later row has target qualified name "N/A", all earlier outputs for that process are removed. If that row supplies a distinct real source, the source is still aggregated. For two such rows, the result can therefore have two inputs and outputs == []. The source-side equivalent behaves analogously.
  6. Entirely unspecified side: A process whose source qualified names are all None has inputs is None; a process whose target qualified names are all None has outputs is None.
  7. Explicitly empty side: A process explicitly cleared with "N/A" has [] on that side, distinguishing it from the None partial-update value.

Warnings

Use Python's standard warning mechanism to emit non-fatal warnings in these situations:

  • A source qualified name duplicates one already collected in inputs for the same process and is therefore de-duplicated.
  • A source or target "N/A" marker is encountered after a real reference has already been accumulated on that corresponding side of the process.

Warnings must not interrupt processing or change the required aggregate result. In particular, the destructive marker still clears the applicable side, and a duplicate still appears only once.

Compatibility and Scope

  • Preserve the existing Reader(READER_CONFIG) construction and parse_update_lineage(json_rows) API.
  • Preserve serialized Atlas process payloads and Atlas object-ID reference formatting.
  • The method prepares update payloads only. It does not fetch a process, merge against remote state, create referenced datasets, or validate that referenced entities exist. None and [] communicate those update intentions to the eventual consumer.

  • Source entries populate attributes.inputs; Target entries populate attributes.outputs.
  • A concrete source or target is serialized as:
{
    "typeName": "<source-or-target type name>",
    "uniqueAttributes": {"qualifiedName": "<source-or-target qualified name>"}
}
  • Distinct concrete references for the same process accumulate on the appropriate side.
Three-state Source and Target semantics

Blank values and the literal "N/A" have deliberately different meanings. Apply the following independently to the Source/input side and Target/output side:

  1. Concrete reference: A real qualified name produces a one-element reference contribution using that side's type name.
  2. Leave unchanged: When both that side's type name and qualified name are Python None, it contributes no entity and means that the process side must not be changed. If no concrete value for that side is established by another row for the process, the resulting attributes.inputs or attributes.outputs value is Python None, not []. If earlier rows for the same process have already accumulated concrete references, a later blank side leaves those references intact.
  3. Explicit clear: When both values are the literal string "N/A", it contributes no entity but explicitly clears that process side. The resulting attributes.inputs or attributes.outputs is an empty list [], meaning that all references on that side are to be removed. This is not equivalent to None.

Thus, a row with a concrete Target and a None Source produces a target update whose inputs value is None. A row with a concrete Source and a None Target produces a source update whose outputs value is None. A row with a concrete Source and an "N/A" Target produces outputs == [] while retaining the concrete input reference.

Duplicate and conflict warnings

Within each process and each side:

  • If another row contributes the same concrete entity, identified by the same type name and qualified name, retain only the earliest occurrence. Do not add a second list entry.
  • Emit a UserWarning through Python's standard warnings mechanism whenever such a duplicate input or duplicate output is encountered.
  • Duplicate detection is scoped to a process and to the input/output side; references belonging to different processes do not conflict.
  • A blank (None) side is a no-op and is not itself a duplicate.
  • An explicit "N/A" clear is not an entity reference. However, if it follows concrete references already accumulated on that side for the same process, clear that side to [] and emit a UserWarning because the rows contain conflicting update instructions.

Required outcomes include:

  • Repeating the same source and target row for one process yields one input and one output; the repeated references are collapsed and a UserWarning is emitted.
  • Repeating a target while supplying two distinct sources yields one output and two inputs. The duplicate output emits a UserWarning; the distinct inputs are both retained.
  • Repeating a source while supplying two distinct targets yields one input and two outputs. The duplicate input emits a UserWarning; the distinct outputs are both retained.
  • Two distinct sources can be accumulated without an input-duplicate warning when the second row leaves its Target as None; the first output remains and both inputs are present. The symmetric behavior applies to accumulating distinct outputs while a later Source is None.
  • If a process first receives a concrete target and source, then a later row specifies an "N/A" Target and a different concrete source, the final process has outputs == [] and contains both distinct inputs. A UserWarning is emitted for the conflict between the earlier target and the later explicit clear.

Objective

Implement a utility function that groups a flat list of Atlas entity JSON dictionaries into batches of a bounded size, while ensuring that entities connected through relationships are kept together in the same batch.

Public API Surface

The module pyapacheatlas.core.util must also continue to expose the existing GuidTracker class (importable from the same location).

Signature
def batch_dependent_entities(entities, batch_size=...):
    ...
  • entities: a list of entity dictionaries (each is the JSON/dict representation of an Atlas entity).
  • batch_size: an integer keyword argument specifying the maximum number of entities allowed in any single output batch.
Return Value

Returns a list of batches. Each batch is a list (or collection) of the input entity dictionaries. The concatenation of all batches contains every input entity exactly once.

Input Entity Structure

Each entity dictionary contains at least:

  • A guid field, which uniquely identifies the entity. For entities created within the same upload, guids are typically small integers or numeric-looking strings (e.g., 0, 1, -1, "-1").
  • A relationshipAttributes field: a mapping from relationship names to relationship references. Each referenced value is itself a dictionary that may contain a guid field pointing to another entity.

Dependency Semantics

Two entities are considered dependent (must be placed in the same batch) when one references the other through a relationship guid, where that referenced guid is a numeric guid (an integer, or a string that represents an integer such as "-1").

  • A relationship reference whose guid is numeric is treated as a pointer to another entity within the same upload set. Entities linked by such references form a connected group and must remain together.
  • A relationship reference whose guid is not numeric (e.g., a real persisted guid like "abc-123") is not treated as an in-upload dependency. It creates no grouping obligation between entities and is ignored for the purpose of batching.

Dependency grouping is transitive and undirected: if A relates to B and B relates to C (via numeric guids), then A, B, and C all belong to the same connected group, regardless of the direction of the relationship or the order in which entities appear in the input list. The input order is not guaranteed to place related entities adjacently.

Batching Rules

  1. Compute connected groups of entities based on numeric-guid relationships as described above. Entities with no qualifying numeric-guid relationship form singleton groups.
  2. Each connected group must be kept intact within a single batch (never split across batches).
  3. Pack these groups into batches such that no batch exceeds batch_size entities. Independent (single or small) groups may be combined into the same batch as long as the total count in that batch stays within batch_size.
  4. The goal is to produce a minimal set of batches consistent with the above constraints (i.e., avoid creating more batches than necessary; fill batches with independent groups where they fit).

Behavioral Examples

  • No dependencies: Given 10 fully independent entities and batch_size=2, the result is 5 batches of 2 entities each.

  • With dependencies: Given 16 entities where some form connected groups through numeric-guid relationships (e.g., one connected group of 7 entities, one connected group of 3 entities, and the rest independent) and batch_size=7, the result is 3 batches: the 7-entity group fills one batch, the 3-entity group plus enough independent entities fills another, and remaining independent entities fill the last — with no batch exceeding 7.

  • Non-numeric guid reference: Given 4 entities where one entity has a relationship pointing to a non-numeric guid (e.g., "abc-123", which is a reference to a pre-existing entity not in the upload set), that relationship does not create a dependency. With batch_size=2, entities that would otherwise be grouped only through such a non-numeric reference remain ungrouped; the result is 2 batches (any genuine numeric-guid dependency is still honored).

Notes

  • Only relationships whose referenced guid is numeric (integer or integer-valued string, including negative values) establish grouping between entities.
  • A group's size may exceed batch_size in principle; the tests only exercise groups that fit within the given batch_size, so grouped entities always fit in one batch under the exercised conditions.
