Task Specification: Implement B017 Check for Overly Broad assertRaises

Overview

flake8-bugbear provides an AST-based Flake8 checker for likely bugs and design problems. Add the B017 warning for the overly broad context-manager form of assertRaises(Exception).

Catching the generic Exception type can let checked code appear successful when an unrelated error occurs before the intended operation. B017 therefore identifies only the narrow syntactic form described below and recommends using a more specific exception, assertRaisesRegex, or a bound exception context that can be inspected.

Public API and integration

BugBearChecker remains importable from the bugbear module and constructible with a filename keyword argument:

bbc = BugBearChecker(filename="path/to/source.py")
errors = list(bbc.run())

B017 must participate in BugBearChecker.run() through the same warning mechanism as the existing Bxxx checks. Each yielded warning must use the established Flake8-compatible record format: its first two values are the 1-based line number and 0-based column offset, followed by the warning message and the usual checker metadata.

Expose a warning constructor named B017 from the bugbear module. Calling B017(line, col) must create the same kind of error record as the other Bxxx constructors. After normal adaptation by BugBearChecker, its message must begin with the token B017.

B017 matching rule

Consider every context-manager item in every synchronous with statement and every asynchronous async with statement. An item qualifies only when all of these conditions hold:

  1. The item has no as clause and therefore does not bind the context manager result to a target.
  2. Its context-manager expression is a call.
  3. The called expression is an attribute access whose final attribute name is exactly assertRaises. The receiver is unrestricted; for example, self.assertRaises(...) and helper.assertRaises(...) have the required method shape.
  4. The call has exactly one positional argument.
  5. The call has no keyword arguments.
  6. The sole positional argument is a simple name reference whose identifier is exactly Exception.

If at least one item in a with or async with statement qualifies, emit exactly one B017 warning for that statement. The warning location is the location of the statement itself: the 1-based line and the 0-based indentation column of with or async with. Do not emit duplicate B017 warnings when multiple items in the same statement qualify.

Separate qualifying statements each produce their own warning, including when they are nested.

The as-binding exemption

A context-manager item that binds the result with as is explicitly exempt, even when every other part has the broad shape:

with self.assertRaises(Exception) as caught:
    perform_operation()

The same exemption applies to async with and to any valid binding target. The checker does not need to determine whether the bound value is later used or whether its exception data is inspected; the presence of the as clause is sufficient.

The exemption is per item. If a single statement also contains a different, unbound context-manager item that qualifies, that statement still receives one B017 warning.

Required examples

The following forms must emit B017:

with self.assertRaises(Exception):
    perform_operation()

async with helper.assertRaises(Exception):
    await perform_async_operation()

with acquire_resource(), helper.assertRaises(Exception):
    perform_operation()

The following forms must not emit B017:

# An `as` target makes this item exempt.
with self.assertRaises(Exception) as caught:
    perform_operation()

# The called attribute name is different.
with self.assertRaisesRegex(Exception, "expected text"):
    perform_operation()

# The exception argument is a different simple name.
with self.assertRaises(ValueError):
    perform_operation()

# A dotted reference is not the bare name `Exception`.
with self.assertRaises(errors.Exception):
    perform_operation()

# A call expression is not the bare name `Exception`.
with self.assertRaises(make_exception()):
    perform_operation()

# This is a bare function call, not an attribute call.
with assertRaises(Exception):
    perform_operation()

# Additional positional or keyword arguments do not match.
with self.assertRaises(Exception, "detail"):
    perform_operation()

with self.assertRaises(Exception, detail="value"):
    perform_operation()

# Ordinary context managers do not match.
with resource:
    perform_operation()

Calls with zero positional arguments, more than one positional argument, any keyword argument, or a method name other than exactly assertRaises are likewise outside B017.

Syntactic scope and non-goals

B017 is a syntactic check:

  • It does not require the surrounding class to inherit from any particular framework class.
  • It does not resolve the receiver of assertRaises or prove that the attribute refers to a particular library method.
  • It compares the exception argument by syntax. Aliases, dotted names, calls, subscripts, literals, and other expressions are not treated as the bare identifier Exception.
  • It does not analyze broad exception handling outside the specified with and async with forms.
  • It does not validate how an as target is used after the statement.

Imports, constants, loops, unrelated functions, plain classes, and other surrounding module content must not independently produce B017.

Robustness

Any syntactically valid nonmatching context-manager form must be handled without failure. In particular, the checker must safely reject, rather than crash on:

  • context-manager expressions that are not calls;
  • calls whose callable is not an attribute access;
  • calls with missing, extra, starred, or keyword arguments;
  • exception arguments represented by attribute accesses, calls, subscripts, literals, or other non-name expressions;
  • statements containing more than one context-manager item; and
  • both bound and unbound context-manager items.

A nonmatching item simply contributes no B017 warning. Processing must continue so unrelated checks and later statements retain their existing behavior.

Concrete behavior

For a class method indented by eight spaces that contains one unbound

with self.assertRaises(Exception):

alongside bound assertRaises(Exception) as caught, assertRaisesRegex(...), dotted exception references, and unrelated module constructs, exactly one B017 warning is emitted. Its column offset is 8, matching the indentation of the qualifying with statement.

Deliverables

  • Add B017 detection to the checker traversal for both with and async with statements.
  • Expose the B017(line, col) warning constructor from bugbear, consistent with the existing Bxxx warning constructors.
  • Preserve all existing warning behavior and Flake8 compatibility while ensuring nonmatching context-manager shapes do not cause failures.

Task: Extend B006 Detection to Comprehension Literals

Context

This is a Flake8 plugin (flake8-bugbear) that detects likely bugs and design problems in Python code. One of its checks, B006, flags the use of mutable data structures as default values for function or method arguments (mutable defaults are shared across all calls and are a common source of bugs).

Current Behavior

The B006 check currently flags mutable literal default arguments such as list literals ([...]), dict literals ({...: ...}), and set literals ({...}) when they appear as default values in a function signature.

Required Change

Extend the B006 check so that it also flags the following expressions when used as default argument values:

  • List comprehensions — e.g. def f(default=[i ** 2 for i in range(3)]): ...
  • Dict comprehensions — e.g. def f(default={i: i ** 2 for i in range(3)}): ...
  • Set comprehensions — e.g. def f(default={i ** 2 for i in range(3)}): ...

Each of these, when appearing as a default value in a function/method argument list, must produce a single B006 warning.

The reported location must point at the position of the comprehension expression itself (the opening bracket/brace of the comprehension), consistent with how existing literal defaults are reported.

Location reporting note

The column reported for a list comprehension default must reflect the position of the comprehension node as provided by Python's AST. Note that this column differs between Python versions: on Python 3.8 and later the reported column is one position earlier than on versions before 3.8. Your implementation should simply report the node's own reported column/line without adjustment, so that it naturally matches whatever the running Python version's AST produces. (Dict and set comprehensions are reported at a consistent column across versions.)

Public API / Behavior

  • The warning code is B006, with the same message and reporting format already used for mutable literal defaults.
  • No new modules, classes, or functions are introduced. The existing B006 detection logic is broadened to recognize comprehension expressions (list, dict, and set comprehensions) in addition to the literal collection types it already handles.
  • Existing B006 and B008 behavior for literals and function-call defaults must remain unchanged.

Constraints

  • Only the three comprehension forms listed above are newly added to B006 detection.
  • Each qualifying comprehension default yields exactly one B006 report at the comprehension's line and column.

Task: Add a new flake8-bugbear check B018

Overview

Add a new lint check, B018, to the bugbear module. This check flags "useless" string-literal statements that appear as standalone expression statements inside function bodies and class bodies (i.e., strings being used as comments rather than as docstrings).

Public API

The check must be exposed as an importable name from the bugbear module:

from bugbear import B018

Consistent with the other Bxxx checks in this module, B018 is a callable/constructor that accepts a line number and column offset:

B018(lineno, col)

When the checker (BugBearChecker) runs over a file, each triggered B018 must be reported as one of these B018(lineno, col) entries in the checker's output, using the same reporting mechanism as all existing Bxxx checks.

Behavior to implement

While visiting the body of a function definition or a class definition, examine each statement in the body:

  • A standalone string-literal expression statement (an expression statement whose value is a string constant) is considered useless and must trigger B018 — except when it is the first statement in the body (that first-position string is a docstring and must NOT be flagged).
  • The check applies to the direct statements of function bodies and class bodies.
  • The reported position is the line number and column offset of the offending string-literal statement.

Non-string statements (assignments, etc.) must never trigger B018. A function or class whose only body statement is a docstring must never trigger B018.

Message text

The B018 message begins with the code B018 followed by a human-readable description indicating that a useless expression / string statement was found (a string used where it has no effect, i.e. as a comment). The exact wording is not constrained beyond the leading B018 code, matching the format used by the other checks.

Illustrative cases

Given code such as:

def foo1():
    """my docstring"""            # OK — docstring, not flagged


def foo2():
    """my docstring"""            # OK — docstring
    a = 2
    "str"                         # B018 — useless string statement


def foo3():
    a = 2
    "str"                         # B018 — useless string statement


class Foo1:
    """abc"""                     # OK — docstring


class Foo2:
    """abc"""                     # OK — docstring

    a = 2
    "str"                         # B018 — useless string statement


class Foo3:
    a = 2
    "str"                         # B018 — useless string statement

The four "str" statements above each produce a B018 at their respective line and column; the docstrings and the a = 2 assignments produce nothing.

Task: Detect Redundant Exceptions in except Clauses (B014)

Overview

You are working on bugbear.py, a flake8 plugin module that implements a set of AST-based lint checks. This task concerns the B014 check, which flags except clauses that catch redundant exception types.

Public API

The module bugbear must expose the following names (importable via from bugbear import ...):

  • BugBearChecker — a class constructible as BugBearChecker(filename=<str>), exposing a run() method that returns an iterable of error tuples.
  • BugBearVisitor — the AST visitor class used by the checker.
  • The error-code constructors: B001, B002, B003, B004, B005, B006, B007, B008, B009, B010, B011, B012, B013, B014, B015, B016, B017, B018, B901, B902, B903, B904, B950.

Each error constructor produces an entry that, when a check fires, appears in the output of BugBearChecker.run(). Each entry carries a line number, a column offset, and (for B014) a set of vars used to format the message.

B014 Behavior

B014 fires on a try/except construct where an except clause lists a tuple of exception types in which one or more of the caught types is redundant because it is already covered by another type in the same tuple. Redundancy arises when:

  1. Duplicate types — the same exception type name appears more than once in the tuple (e.g. except (OSError, OSError):).
  2. A type and its known subclass — the tuple contains both a type and another type that is a known subclass (or alias) of it. The set of redundant type-family relationships that must be recognized includes at least:
    • IOError, EnvironmentError, WindowsError, mmap.error, socket.error, select.error are all aliases/subclasses of OSError. When any combination of these appears together, the canonical replacement is OSError.
    • binascii.Error is a subclass of ValueError. When both appear together (in either order), the canonical replacement is ValueError.

When the caught types include a mix of an ancestor and its subclass/alias, the redundant member(s) collapse to the single canonical ancestor.

Firing rules and edge cases
  • The check only applies when the except clause catches a tuple of two or more types (a single caught type never fires).
  • Attribute-based names must be handled by their full dotted form (e.g. re.error, binascii.Error) both for detecting redundancy and for reporting.
  • The check must not crash when the tuple contains a name that is not an exception (e.g. NotImplemented); such entries simply do not trigger a redundancy on their own.
Error entry contents

For each firing except clause, produce a single B014 entry located at the line and column of the except handler. The vars associated with the entry is a 3-tuple of strings:

  1. The original caught types, as a comma-and-space-joined list of the type names exactly as written in source order (e.g. "OSError, OSError", "ValueError, binascii.Error", "IOError, EnvironmentError, OSError").
  2. The exception-binding suffix: the empty string "" if there is no as binding, or " as <name>" (leading space included) when the handler binds the exception to a name (e.g. " as err", " as e").
  3. The canonical replacement type name — the single type that the redundant tuple should collapse to (e.g. "OSError", "ValueError", "Exception", "MyError", "BaseException", "re.error").

Examples of the intended detection

Given source such as:

try:
    pass
except (ValueError, binascii.Error):
    pass

B014 must fire at the except line with vars = ("ValueError, binascii.Error", "", "ValueError").

Other representative firing cases (all catching redundant tuples):

  • except (Exception, TypeError): → ("Exception, TypeError", "", "Exception")
  • except (OSError, OSError) as err: → ("OSError, OSError", " as err", "OSError")
  • except (MyError, MyError): → ("MyError, MyError", "", "MyError")
  • except (MyError, BaseException) as e: → ("MyError, BaseException", " as e", "BaseException")
  • except (re.error, re.error): → ("re.error, re.error", "", "re.error")
  • except (IOError, EnvironmentError, OSError): → ("IOError, EnvironmentError, OSError", "", "OSError")

A tuple containing a non-exception sentinel alongside a real exception (e.g. except (MyException, NotImplemented):) must be processed without error and, absent an actual redundancy, must not fire.

  • def f(db=fastapi.Depends(get_db)): ... produces no diagnostics.
  • def g(data: List[str] = fastapi.Query(None)): ... produces no diagnostics.
  • def h(data: List[str] = Query(None)): ..., where Query was imported via from fastapi import Query, still produces one B008 for Query(None), because the unqualified path Query is not in the configured list.

When the checker is constructed without options, with options=None, or with an options object lacking the extend_immutable_calls attribute, no extra exemptions apply and behavior is exactly as described elsewhere in this specification.

The same setting must be available through Flake8 configuration: the plugin registers an --extend-immutable-calls option that accepts a comma-separated list, can be parsed from a configuration file, and defaults to an empty list.

Special float calls

Do not emit B008 when float() has exactly one string-literal argument consisting of an optional + or - sign followed by inf, infinity, or nan. Matching these names is case-insensitive. The overflowing literal float("1e999") is also exempt.

Exempt examples include:

float("inf")
float("infinity")
float("+inf")
float("-inf")
float("+infinity")
float("NaN")
float("nan")
float("+NaN")
float("-NaN")
float("1e999")

Ordinary finite float conversions remain invalid defaults and receive B008, including:

float(3)
float("3.14")
Diagnostic locations
  • For B006, report the start of the outer mutable default expression.
  • For B008, report the start of the individual call expression.
  • Multiple diagnostics on one line must identify their respective expressions separately.

Account for Python AST location differences:

  • For a list comprehension, Python 3.8 and later report B006 at the opening [. Earlier versions report it one column later at the first element.
  • For a parenthesized lambda invocation such as (lambda x: x)(), Python 3.8 and later report B008 at the opening parenthesis. Earlier versions report it one column later at lambda.
