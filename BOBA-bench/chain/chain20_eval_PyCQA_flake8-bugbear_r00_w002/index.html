01 Implementing a B017 Check for Overly Broad assertRaises 1013 words · rewritten by GPT-5.6-sol, reworded by GLM-5.3-Flash

Task Specification: Implementing a B017 Check for Overly Broad assertRaises

Overview

flake8-bugbear is an AST-based Flake8 checker for likely bugs and design problems. Add a B017 warning for the overly broad context-manager form of assertRaises(Exception).

If the generic Exception type is caught, checked code can appear successful when an unrelated error occurs before the intended operation. B017 therefore flags only the narrow syntactic form described below and recommends using a more specific exception, assertRaisesRegex, or a bound exception context that can be inspected.

Public API and integration

BugBearChecker stays importable from the bugbear module and can be constructed with a filename keyword argument:

bbc = BugBearChecker(filename="path/to/source.py")
errors = list(bbc.run())

B017 must take part in BugBearChecker.run() via the same warning mechanism as the existing Bxxx checks. Every warning that is yielded must use the established Flake8-compatible record format: the first two values are the 1-based line number and the 0-based column offset, followed by the warning message and the usual checker metadata.

A warning constructor named B017 must be exposed from the bugbear module. Calling B017(line, col) must create an error record of the same kind as the other Bxxx constructors. After BugBearChecker performs its normal adaptation, the message must begin with the token B017.

Matching rule for B017

Examine every context-manager item in every synchronous with statement and every asynchronous async with statement. An item qualifies only when all of the following conditions hold:

  1. The item carries no as clause and therefore does not bind the context manager result to a target.
  2. The item's context-manager expression is a call.
  3. The expression being called is an attribute access whose final attribute name is exactly assertRaises. The receiver is not restricted; for example, self.assertRaises(...) and helper.assertRaises(...) have the required method shape.
  4. The call contains exactly one positional argument.
  5. The call contains no keyword arguments.
  6. That single positional argument is a simple name reference whose identifier is exactly Exception.

When at least one item of a with or async with statement qualifies, emit exactly one B017 warning for that statement. The warning's location is that of the statement itself: the 1-based line and the 0-based indentation column of with or async with. If multiple items in the same statement qualify, do not emit duplicate B017 warnings.

Distinct qualifying statements each produce their own warning, including when they are nested.

Exemption for as bindings

A context-manager item that binds the result via as is explicitly exempt, even if every other part has the broad shape:

with self.assertRaises(Exception) as caught:
    perform_operation()

The same exemption holds for async with and for any valid binding target. The checker does not need to establish whether the bound value is used later or whether its exception data is inspected; the presence of the as clause is enough.

The exemption applies per item. When a single statement additionally contains a different, unbound context-manager item that qualifies, that statement still receives one B017 warning.

Required example forms

B017 must be emitted for the following forms:

with self.assertRaises(Exception):
    perform_operation()

async with helper.assertRaises(Exception):
    await perform_async_operation()

with acquire_resource(), helper.assertRaises(Exception):
    perform_operation()

B017 must not be emitted for the following forms:

# An `as` target makes this item exempt.
with self.assertRaises(Exception) as caught:
    perform_operation()

# The called attribute name is different.
with self.assertRaisesRegex(Exception, "expected text"):
    perform_operation()

# The exception argument is a different simple name.
with self.assertRaises(ValueError):
    perform_operation()

# A dotted reference is not the bare name `Exception`.
with self.assertRaises(errors.Exception):
    perform_operation()

# A call expression is not the bare name `Exception`.
with self.assertRaises(make_exception()):
    perform_operation()

# This is a bare function call, not an attribute call.
with assertRaises(Exception):
    perform_operation()

# Additional positional or keyword arguments do not match.
with self.assertRaises(Exception, "detail"):
    perform_operation()

with self.assertRaises(Exception, detail="value"):
    perform_operation()

# Ordinary context managers do not match.
with resource:
    perform_operation()

Calls that have zero positional arguments, more than one positional argument, any keyword argument, or a method name other than exactly assertRaises likewise fall outside B017.

Scope of the syntactic check and non-goals

B017 operates as a syntactic check:

  • It does not require the enclosing class to inherit from any specific framework class.
  • It does not resolve the receiver of assertRaises and does not prove that the attribute refers to a particular library method.
  • The exception argument is compared by syntax. Aliases, dotted names, calls, subscripts, literals, and other expressions are not treated as the bare identifier Exception.
  • It does not analyze broad exception handling beyond the specified with and async with forms.
  • It performs no validation of how an as target is used after the statement.

Imports, constants, loops, unrelated functions, plain classes, and other surrounding module content must not produce B017 on their own.

Robustness

Any syntactically valid context-manager form that does not match must be handled without failure. In particular, the checker must safely reject, instead of crashing on:

  • context-manager expressions that are not calls;
  • calls in which the callable is not an attribute access;
  • calls that have missing, extra, starred, or keyword arguments;
  • exception arguments given as attribute accesses, calls, subscripts, literals, or other non-name expressions;
  • statements that contain more than one context-manager item; and
  • both bound and unbound context-manager items.

An item that does not match simply contributes no B017 warning. Processing must continue so that unrelated checks and later statements retain their existing behavior.

Behavior in a concrete case

For a class method indented by eight spaces that contains one unbound

with self.assertRaises(Exception):

together with bound assertRaises(Exception) as caught, assertRaisesRegex(...), dotted exception references, and unrelated module constructs, exactly one B017 warning is emitted. The column offset of the warning is 8, matching the indentation of the qualifying with statement.

Deliverables

  • Add B017 detection to the checker traversal covering both with and async with statements.
  • Expose the B017(line, col) warning constructor from bugbear, in line with the existing Bxxx warning constructors.
  • Keep all existing warning behavior and Flake8 compatibility, while ensuring that nonmatching context-manager shapes do not cause failures.

Task: Broaden B006 Detection to Cover Comprehension Literals

Background

The project is a Flake8 plugin (flake8-bugbear) that looks for likely bugs and design problems in Python code. B006 is one of its checks; it flags the use of mutable data structures as default values for function or method arguments (mutable defaults are shared across all calls and are a common source of bugs).

Behavior Today

At present, the B006 check flags mutable literal default arguments such as list literals ([...]), dict literals ({...: ...}), and set literals ({...}) when they show up as default values in a function signature.

Change Required

The B006 check needs to be extended so that it also flags the following expressions when they are used as default argument values:

  • List comprehensions — for example def f(default=[i ** 2 for i in range(3)]): ...
  • Dict comprehensions — for example def f(default={i: i ** 2 for i in range(3)}): ...
  • Set comprehensions — for example def f(default={i ** 2 for i in range(3)}): ...

For each of these, when it appears as a default value in a function/method argument list, a single B006 warning must be produced.

The location that is reported must point at the position of the comprehension expression itself (the opening bracket/brace of the comprehension), consistent with how existing literal defaults are reported.

Note on location reporting

For a list comprehension default, the column that is reported must reflect the position of the comprehension node as provided by Python's AST. Be aware that this column varies between Python versions: on Python 3.8 and later the reported column is one position earlier than on versions before 3.8. Your implementation should simply report the node's own reported column/line without adjustment, so that it naturally lines up with whatever the running Python version's AST produces. (For dict and set comprehensions, the reported column is consistent across versions.)

Public API and Behavior

  • The warning code remains B006, with the same message and reporting format that mutable literal defaults already use.
  • The change introduces no new modules, classes, or functions. The logic that already exists for B006 detection is broadened so that it recognizes comprehension expressions (list, dict, and set comprehensions) in addition to the literal collection types it already handles.
  • The existing behavior of B006 and B008 for literals and function-call defaults must remain unchanged.

Constraints

  • The three comprehension forms listed above are the only additions to B006 detection.
  • Each comprehension default that qualifies yields exactly one B006 report at the comprehension's line and column.

Task: Introduce the new flake8-bugbear check B018

Summary

This task consists of adding a new lint check, B018, to the bugbear module. The check flags "useless" string-literal statements appearing as standalone expression statements inside function bodies and class bodies (i.e., strings being used as comments rather than as docstrings).

Public interface

The check must be exposed as a name that can be imported from the bugbear module:

from bugbear import B018

Like the other Bxxx checks in this module, B018 is a callable/constructor that accepts a line number and column offset:

B018(lineno, col)

When the checker (BugBearChecker) runs over a file, each triggered B018 must be reported in the checker's output as one of these B018(lineno, col) entries, through the same reporting mechanism as all existing Bxxx checks.

Behavior to be implemented

While visiting the body of a function definition or a class definition, examine each statement in that body:

  • A standalone string-literal expression statement (an expression statement whose value is a string constant) is treated as useless and must trigger B018 — except when it is the first statement in the body (a string in that first position is a docstring and must NOT be flagged).
  • The check operates on the direct statements of function bodies and class bodies.
  • The position to report is the line number and column offset of the offending string-literal statement.

Statements that are not strings (assignments, etc.) must never trigger B018. B018 must never be triggered by a function or class whose only body statement is a docstring.

Message wording

The B018 message starts with the code B018, followed by a human-readable description indicating that a useless expression / string statement was found (a string used where it has no effect, i.e. as a comment). Apart from the leading B018 code, the exact wording is not constrained; this follows the same format as the other checks.

Illustrative examples

Given code such as the following:

def foo1():
    """my docstring"""            # OK — docstring, not flagged


def foo2():
    """my docstring"""            # OK — docstring
    a = 2
    "str"                         # B018 — useless string statement


def foo3():
    a = 2
    "str"                         # B018 — useless string statement


class Foo1:
    """abc"""                     # OK — docstring


class Foo2:
    """abc"""                     # OK — docstring

    a = 2
    "str"                         # B018 — useless string statement


class Foo3:
    a = 2
    "str"                         # B018 — useless string statement

Each of the four "str" statements above produces a B018 at its respective line and column; the docstrings and the a = 2 assignments produce nothing.

Task Specification: Extending the B018 Check

Background

The project is a flake8 plugin (flake8-bugbear) that implements lint checks. Every check carries an error code and produces error records. The existing B018 check is what you must extend.

Existing Infrastructure (already in place)
  • A BugBearChecker class drives the plugin; it is constructed with a filename keyword argument (BugBearChecker(filename=str(...))) and exposes a run() method that returns an iterable of error records.
  • Error records are produced via a B018 error factory. B018(line, col) produces an error record whose line is line and whose column is col. The text of the B018 error message is already defined and should not be changed.
Behavior Change Required

The B018 check detects "useless expression" statements — statements made up solely of a constant/literal value used as an expression statement (that is, a value that is evaluated and discarded, having no effect). At present the check runs inside function bodies and class bodies (it need not run at module level).

Right now, B018 flags only a limited set of such statements. You must broaden it so that, inside a function body or a class body, an expression statement is flagged as B018 whenever its value is any of the following literal/constant kinds:

  • A string literal that does not occupy docstring position (a string literal serving as the first statement of a function or class body is a docstring and must not be flagged).
  • A numeric literal (integer, float, or complex).
  • A byte-string literal.
  • An f-string (a formatted/joined string literal).
  • A name constant: True, False, or None.
  • A list literal.
  • A set literal.
  • A dict literal.

Every offending statement of these kinds produces one B018 error at the statement's line and column.

Exact Flagging Rules
  • Flagging applies only to bare expression statements whose value is one of the kinds listed above. An assignment (e.g. a = 2) and other statements are never flagged.
  • When the first statement of a function or class body is a string literal, that statement is a docstring and must not be flagged. Any subsequent string-literal expression statement within the body is flagged.
  • The check applies to statements located directly within function bodies and class bodies.
  • Column reporting: for a statement inside a function/class body indented by one level (4 spaces), the reported column is 4 (that is, the column corresponds to the statement's actual position).
Examples of the Intended Results

For a function like the following:

def foo2():
    """my docstring"""   # docstring — NOT flagged
    a = 2                # assignment — NOT flagged
    "str"                # flagged
    1j                   # flagged
    1                    # flagged
    1.0                  # flagged
    b"foo"               # flagged
    f"{int}"             # flagged
    True                 # flagged
    False                # flagged
    None                 # flagged
    [1, 2]               # flagged
    {1, 2}               # flagged
    {"foo": "bar"}       # flagged

Every line commented "flagged" above produces a B018 error at that line and its column.

For a class:

class Foo2:
    """abc"""            # docstring — NOT flagged
    a = 2                # NOT flagged
    "str"                # flagged
    1j                   # flagged
    ...                  # (same literal kinds as above, each flagged)

And:

def foo3():
    a = 2                # NOT flagged
    "str"                # flagged (not a docstring; preceded by assignment)

class Foo3:
    a = 2                # NOT flagged
    "str"                # flagged

When the only statement in a function's or class's body is a docstring, no B018 errors are produced.

Constraints on Scope
  • The B018 message text and its column-reporting behavior must not be changed.
  • This check must not be enabled at module level.
  • You must not introduce any other error codes or behaviors.

Task: Detecting Redundant Exceptions in except Clauses (B014)

Background

Your work takes place in bugbear.py, a flake8 plugin module implementing a set of AST-based lint checks. This task is about the B014 check, which flags except clauses that catch redundant exception types.

Public API

The following names must be exposed by the module bugbear (importable via from bugbear import ...):

  • BugBearChecker — a class that can be instantiated as BugBearChecker(filename=<str>), exposing a run() method that returns an iterable of error tuples.
  • BugBearVisitor — the AST visitor class the checker uses.
  • The constructors for the error codes: B001, B002, B003, B004, B005, B006, B007, B008, B009, B010, B011, B012, B013, B014, B015, B016, B017, B018, B901, B902, B903, B904, B950.

Every error constructor produces an entry which, whenever a check fires, shows up in the output of BugBearChecker.run(). Each entry carries a line number, a column offset, and (for B014) a set of vars used when formatting the message.

How B014 Behaves

B014 fires on a try/except construct in which an except clause lists a tuple of exception types and one or more of the caught types is redundant, since it is already covered by another type in the same tuple. Redundancy occurs when:

  1. Duplicate types — the same exception type name occurs more than once in the tuple (e.g. except (OSError, OSError):).
  2. A type and its known subclass — the tuple holds both a type and another type that is a known subclass (or alias) of it. The set of redundant type-family relationships that must be recognized includes at least the following:
    • All of IOError, EnvironmentError, WindowsError, mmap.error, socket.error, select.error are aliases/subclasses of OSError. The canonical replacement is OSError whenever any combination of these appears together.
    • binascii.Error is a subclass of ValueError. The canonical replacement is ValueError whenever both appear together (in either order).

Whenever the caught types include a mix of an ancestor and its subclass/alias, the redundant member(s) collapse to the single canonical ancestor.

Trigger rules and edge cases
  • The check applies only when the except clause catches a tuple of two or more types (with just one caught type, it never fires).
  • Names based on attributes must be handled in their full dotted form (e.g. re.error, binascii.Error), both for detecting redundancy and for reporting.
  • The check must not crash if the tuple contains a name that is not an exception (e.g. NotImplemented); entries of that kind simply do not trigger a redundancy on their own.
Contents of the error entry

For each except clause that fires, a single B014 entry must be produced, positioned at the line and column of the except handler. The vars attached to the entry is a 3-tuple of strings:

  1. The original caught types — a list of the type names exactly as written, joined with comma and space, in source order (e.g. "OSError, OSError", "ValueError, binascii.Error", "IOError, EnvironmentError, OSError").
  2. The exception-binding suffix: the empty string "" when no as binding is present, or " as <name>" (leading space included) when the handler binds the exception to a name (e.g. " as err", " as e").
  3. The canonical replacement type name — the single type onto which the redundant tuple should collapse (e.g. "OSError", "ValueError", "Exception", "MyError", "BaseException", "re.error").

Examples of the intended detection behavior

With source like the following:

try:
    pass
except (ValueError, binascii.Error):
    pass

B014 must fire at the line of the except, with vars = ("ValueError, binascii.Error", "", "ValueError").

Other representative firing cases (all of them catching redundant tuples):

  • except (Exception, TypeError): → ("Exception, TypeError", "", "Exception")
  • except (OSError, OSError) as err: → ("OSError, OSError", " as err", "OSError")
  • except (MyError, MyError): → ("MyError, MyError", "", "MyError")
  • except (MyError, BaseException) as e: → ("MyError, BaseException", " as e", "BaseException")
  • except (re.error, re.error): → ("re.error, re.error", "", "re.error")
  • except (IOError, EnvironmentError, OSError): → ("IOError, EnvironmentError, OSError", "", "OSError")

A tuple that contains a non-exception sentinel next to a real exception (e.g. except (MyException, NotImplemented):) must be processed without error and, when there is no actual redundancy, must not fire.

Task Specification: Extending the Immutable Calls for B008 via a Configuration Option

Background

The codebase here is flake8-bugbear, a flake8 plugin that reports lint warnings. The check that matters for this task is B008, which flags function argument default values that are calls to functions, since a call in that position is evaluated once, at definition time, and can be a source of bugs. Internally, the plugin keeps an allow-list of "immutable" calls — ones it considers safe as argument defaults — and those calls therefore do NOT trigger B008.

Objective

Implement a configurable option through which users can extend the built-in set of immutable calls. When a call named in this option is used as an argument default value, it must NOT raise a B008 warning.

Public API Surface

The checker is driven through the existing BugBearChecker class, importable from the plugin's main module (e.g. bugbear). Construction happens via keyword arguments, and the class exposes a run() method that yields error tuples:

bbc = BugBearChecker(filename=<str path>, options=<options object>)
errors = list(bbc.run())

Each error that gets yielded corresponds to a detected issue. B008 errors come with a line and column number.

Behavior Requirements

Option extend_immutable_calls
  • BugBearChecker accepts an options object, passed via the options= keyword argument at construction time.
  • On the options object there may be an attribute named extend_immutable_calls, which is a list of strings; each string is a dotted call name (for example, "fastapi.Depends" or "fastapi.Query").

  • List literals, such as [1, 2, 3].
  • Dict literals, such as {}.
  • set().
  • collections.OrderedDict().
  • collections.defaultdict().
  • collections.deque().
  • List comprehensions.
  • Dict comprehensions.
  • Set comprehensions.
  • Keyword-only list defaults such as *, value=[].

A mutable constructor call from the list above, when it is direct, receives B006 only — not an additional B008 for the same call.

The following defaults must not receive B006 or B008:

  • Tuple literals, including (1, 2, 3) and ().
  • tuple().
  • frozenset().
  • types.MappingProxyType(...).
  • An unqualified imported MappingProxyType(...).

Do not emit B006 for a mutable expression that is merely nested inside an outer default operation. In particular:

def f(a=map(lambda s: s.upper(), ["a", "b", "c"])):
    ...

must not receive B006 for the nested list literal.

B008: calls in defaults

One B008 must be emitted for every non-exempt call found anywhere within a default expression, including calls nested inside other expressions.

Required examples include:

  • time.time() yields one B008.
  • dt.datetime.now() + dt.timedelta(days=7) yields two B008 diagnostics, one for each call.
  • (lambda x: x)() yields one B008 for invoking the lambda.
  • Each range(3) in a list, dict, or set comprehension yields B008 in addition to the comprehension’s B006.
  • [float(3), dt.datetime.now()] yields:
    • one B006 for the outer list;
    • one B008 for float(3);
    • one B008 for dt.datetime.now().
  • map(lambda s: s.upper(), ["a", "b", "c"]) yields:
    • one B008 for map(...);
    • one B008 for s.upper(), even though it appears inside the lambda;
    • no B006 for the nested list.
  • random.randint(0, dt.datetime.now().year) yields:
    • one B008 for random.randint(...);
    • one B008 for dt.datetime.now().
Calls that are exempt from B008

Do not emit B008 for these calls when they are used as defaults:

  • tuple().
  • frozenset().
  • types.MappingProxyType(...).
  • Unqualified imported MappingProxyType(...).
  • re.compile(...).
  • Qualified operator helpers:
    • operator.attrgetter(...)
    • operator.itemgetter(...)
    • operator.methodcaller(...)
  • The same operator helpers imported and called unqualified:
    • attrgetter(...)
    • itemgetter(...)
    • methodcaller(...)
Immutable calls extendable by the user

The built-in exempt-call list above can be extended by the user.

When BugBearChecker is constructed with an options object that has an extend_immutable_calls attribute, that attribute holds a collection of call-path strings (for example, ["fastapi.Depends", "fastapi.Query"]). Any call whose dotted call path — exactly as written in the source — matches an entry in extend_immutable_calls must be exempt from B008 in the same way as the built-in exempt calls. The exemption must apply to every call examined within default expressions, including calls nested inside other expressions, and not just to calls that appear directly as the default value.

The matching is done on the textual call path, not on resolved imports. For example, with extend_immutable_calls=["fastapi.Depends", "fastapi.Query"]:

  • def f(db=fastapi.Depends(get_db)): ... produces no diagnostics.
  • def g(data: List[str] = fastapi.Query(None)): ... produces no diagnostics.
  • def h(data: List[str] = Query(None)): ..., where Query was imported through from fastapi import Query, still produces one B008 for Query(None), since the unqualified path Query is not in the configured list.

When the checker is constructed without options, with options=None, or with an options object that lacks the extend_immutable_calls attribute, no extra exemptions apply, and the behavior is exactly as described elsewhere in this specification.

This same setting must be available via Flake8 configuration: the plugin registers an --extend-immutable-calls option that accepts a comma-separated list, can be parsed from a configuration file, and defaults to an empty list.

Special float calls

Do not emit B008 when float() has exactly one argument that is a string literal made up of an optional + or - sign followed by inf, infinity, or nan. These names are matched case-insensitively. The overflowing literal float("1e999") is exempt as well.

Examples of exempt calls include:

float("inf")
float("infinity")
float("+inf")
float("-inf")
float("+infinity")
float("NaN")
float("nan")
float("+NaN")
float("-NaN")
float("1e999")

Ordinary finite float conversions are still invalid defaults and receive B008, including:

float(3)
float("3.14")
Locations of diagnostics
  • For B006, the location to report is the start of the outer mutable default expression.
  • For B008, the location to report is the start of the individual call expression.
  • When multiple diagnostics fall on one line, they must identify their respective expressions separately.

Take the following Python AST location differences into account:

  • For a list comprehension, B006 is reported at the opening [ by Python 3.8 and later; earlier versions report it one column later, at the first element.
  • For a parenthesized lambda invocation such as (lambda x: x)(), B008 is reported at the opening parenthesis by Python 3.8 and later; earlier versions report it one column later, at lambda.
