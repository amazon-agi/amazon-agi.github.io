Task: Extend StructuredModel with a model_changed_event

Summary

nion.utils.StructuredModel is a module that provides a schema-based model system. You must extend the models this module produces so that, whenever the model's value changes at any level of nesting, they emit a deep change notification. This notification is exposed through a new event named model_changed_event.

Existing API (already available, used by this task)

The following are already provided by the module nion.utils.StructuredModel, and you may rely on them:

  • StructuredModel.STRING, StructuredModel.INT — constants for the schema types of scalar fields.
  • StructuredModel.define_field(name, type) — defines a named field having a given schema type.
  • StructuredModel.define_record(name, fields) — defines a record schema from a list of fields.
  • StructuredModel.define_array(item_schema) — defines an array schema, the items of which conform to item_schema.
  • StructuredModel.build_model(schema, value=...) — builds a model instance from a schema together with an initial value.
  • For array models, insert_item(index, item), remove_item(index), and an items sequence are supported.
  • For record models, the fields are exposed as attributes (e.g. a record with field x exposes a settable/gettable attribute model.x).

Required Modification

An attribute named model_changed_event must be exposed by every model instance returned by build_model (records and arrays alike). That attribute must be an event object that supports:

  • .listen(callback) — registers a zero-argument callback and returns a listener object that can be closed (i.e. it can be used as the argument to contextlib.closing).

Each time the model's value changes, including changes occurring at any nested depth, the model_changed_event must be fired once (every registered callback is invoked with no arguments). Specifically:

  1. Array — basic item value changes. For an array model with scalar items, a call to insert_item(index, value) fires the event exactly once, and a call to remove_item(index) fires the event exactly once.

  2. Array — changes to record items. For an array model whose items are record models:

    • A call to insert_item(index, record_model) fires the event exactly once.
    • After an item has been inserted, modifying a field of an item in the array (e.g. model.items[i].x = 55) fires the array model's event exactly once. In other words, a change deep inside a contained record must propagate up to the containing array's model_changed_event.

  3. Record — changes to nested record fields. For a record model that contains a field whose value is itself a record model, modifying a field of the nested record (e.g. model.a.x = 11) fires the outer record model's model_changed_event exactly once. Deep changes must propagate upward through nested records.

In all cases, merely building the model or registering a listener causes no model_changed_event firing — the number of firings must be zero until an actual mutating operation is performed.

Remarks

  • Callbacks are fired by the event with no arguments.
  • Deep propagation is required: a mutation at any nesting level must result in exactly one firing on the top-level model that (directly or transitively) contains the mutated value.
02 Module for a Component Registry 444 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Module for a Component Registry

Goal

Create a new module Registry inside the nion.utils package (i.e., importable as from nion.utils import Registry). The module supplies a global registry that ties arbitrary objects ("components") to sets of string "component types", and lets those components be looked up by type.

Public API

All of the functions are module-level functions in nion.utils.Registry.

register_component(component, component_types)

Records component (any object) as being associated with each of the supplied component types.

  • component: the object being registered.
  • component_types: a set of strings, each of which names a component type.

Behavior:

  • After this call, component is associated with every type contained in component_types.
  • Registering the same component object more than once is permitted, with different (or additional) component type sets. Each call adds the given types to the component's set of associated types; it does not replace or remove the previously associated types. After multiple registration calls, the component is associated with the union of all the type sets it was registered with.
unregister_component(component, component_types=None)

Deletes the associations that exist between component and component types.

  • component: the object to be unregistered.
  • component_types: an optional set of strings. None is the default for this parameter.

Behavior:

  • If component_types is provided (a set of strings), only the specified types get disassociated from component. Any of the component's other associated types stay in effect, and the component continues to be discoverable via those remaining types.
  • If component_types is left out (or is None), the component is unregistered completely: it becomes disassociated from all of its component types and is no longer discoverable by any type.
get_component(component_type)

Retrieves a registered component using a single component type string.

  • component_type: a string that names a component type.

Behavior:

  • Returns a component object that is currently associated with component_type.
  • Returns None if there is currently no component associated with component_type (including the case where a component was previously associated with that type but has since been unregistered from it).

Example of Behavior

Using a single object o:

  1. If o is registered with types {"one", "two"} and then, separately, registered with types {"three"}, o ends up retrievable via get_component("one") and get_component("three").
  2. Unregistering o with {"three"} removes only the association with "three": get_component("one") still returns o, whereas get_component("three") returns None.
  3. Unregistering o with no type argument removes all associations that remain: get_component("one") then returns None.

Notes

  • The state of the registry is global/module-level and is shared across calls.
  • Component types are compared as plain strings; components are compared by the identity/equality of the registered object.

Task Specification: Ordering Behavior of FilteredListModel

Overview

You must implement/fix the FilteredListModel class in the module nion.utils.ListModel. The class gives a filtered and optionally sorted view of items that a container list model holds. What this task focuses on is making sure the filtered view maintains correct item ordering under all supported operations — whether the view is sorted, unsorted, or in transition between the two, and even when the underlying container changes while updates are in progress.

Public API

The items below must be importable from nion.utils.ListModel:

ListModel.ListModel(items_key)

A container list model that is constructed with a string key naming its item collection.

The following members are required:

  • append_item(item) — appends an item to the end of the collection.
  • insert_item(index, item) — inserts an item at the provided index.
  • remove_item(index) — removes the item at the provided index.
  • items — property that returns the current list of items, in order.
ListModel.FilteredListModel(container=None, items_key=None)

A list model that presents a filtered/sorted view over another list model's items.

Keyword arguments for the constructor:

  • container — the source list model that is observed.
  • items_key — the string key that identifies the item collection within the container.

The following attributes / properties are required (all of them settable after construction):

  • sort_key — a callable that maps an item to a comparison key, or None. If it is set to a callable, the view is sorted ascending by that key. If it is None, the view is unsorted.
  • filter — a filter object (see below) that decides which container items appear in the view. When it is unset, all items pass.
  • container — a settable property; assigning a new container list model rebinds the view so it observes the new container's items.
  • items — property that returns the current list of items in the view, in the correct order.

The following methods are required:

  • mark_changed() — forces the view to recompute/refresh its contents.
  • begin_change() / end_change() — delimit a batch of container mutations. Between a begin_change and its matching end_change, the view should hold off on recomputation and generate a single consistent update when the outermost change completes. These calls may be nested (and may be nested across multiple FilteredListModel instances observing one another).

Since a FilteredListModel is itself a list model that exposes items under an items_key, one FilteredListModel may serve as another's container.

Filter classes inside ListModel
  • ListModel.Filter(matches: bool) — a filter that accepts everything when it is constructed with True.
  • ListModel.PredicateFilter(predicate) — a filter that is constructed with a single-argument callable returning a truthy/falsy value; an item shows up in the view exactly when the predicate returns truthy for it.

Required Behavior

Sorted view

If sort_key has been set to a callable, the view's items are the container's passing items, sorted ascending by the key. As items are inserted into or removed from the container, the sorted order must be kept. Example: for container items "3","1","4","2" and sort_key = lambda x: x, the view is ["1","2","3","4"]. After container items are removed so that only "3","2" remain, the view is ["2","3"]. After more items are inserted, the view remains sorted.

Unsorted view

When sort_key is None (the default), the view's items preserve the container's ordering, restricted to the items that pass the filter.

  • With PredicateFilter(lambda x: x != "4") applied to container "3","1","4","2", the view yields ["3","1","2"].
  • Removing the container's first item updates the view to ["1","2"].
  • If an item is inserted at the front of the container and another is appended, each lands in its corresponding container position within the filtered view (the front-inserted item at the front, the appended item at the end).
  • Mutations wrapped in begin_change/end_change produce the same final ordering as they would if applied individually. For instance, inside a change block, inserting "5" at the front and appending "6" yields a view where "5" is first and "6" is last, and the existing filtered items retain their relative order.
Switching from sorted to unsorted

When sort_key changes from being a callable to None, the view must switch from sorted order to reflecting the container's current order (filtered). Setting a filter and then clearing sort_key must produce a view that follows the container order among passing items. Example: starting sorted as ["1","2","3","4"], then applying PredicateFilter(lambda x: x != "4") and setting sort_key = None, the view ends up as ["3","1","2"] (container order, filtered). Removals from the container that happen afterwards keep container order: removing the container item at index 1 ("1") yields ["3","2"].

Replacing the container and reordering within a change block

When the view is unsorted and its container is reassigned while inside a begin_change/end_change block, the view must fully re-synchronize to the new container's ordering — even in the case where the new container contains the same set of items in a different order (a pure rearrangement). The view must not assume that its existing order is still valid; it must adopt the new container's order.

This must work when the operations are nested across two FilteredListModel instances, with the outer instance's container being the inner instance:

  • Construct container l with items "3","1","4","2" and a second container l2 with items "4","1","2","3".
  • l3 = FilteredListModel(container=l, items_key="items") → l3.items == ["3","1","4","2"].
  • l4 = FilteredListModel(container=l3, items_key="items") → l4.items == ["3","1","4","2"].
  • Within nested change blocks (l4.begin_change(), l3.begin_change(), mutate, l3.end_change(), l4.end_change()), setting l3.filter = Filter(True) first leaves the ordering unchanged.
  • Then, inside another nested change block, reassigning l3.container = l2 must cause both l3.items and l4.items to become ["4","1","2","3"] after the change blocks complete.

Notes

  • Changes to the filter, changes to sort_key, and container changes must all propagate correctly to any downstream FilteredListModel observing this one.
  • The item type throughout is str; ordering comparisons and predicates operate on plain values.

Compatibility maintenance (unrelated to ListModel): ensure that any use of the abstract base classes for sequences references collections.abc (e.g., collections.abc.Sequence) rather than the deprecated collections aliases, so that model objects that StructuredModel.build_model produces are recognized as collections.abc.Sequence instances where applicable.

04 Begin/End Change Notifications for List Models 584 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Begin/End Change Notifications for List Models

Overview

The module nion.utils.ListModel contains two list model classes, FilteredListModel and MappedListModel, to which you must add change-batching notifications. These notifications mark the beginning and the end of a batch of item mutations, and callers must be able to group multiple mutations together into a single batch.

Classes and Constructors Affected

FilteredListModel

Instances are constructed from keyword arguments in these forms:

  • FilteredListModel(container=<source_model>, items_key="items")
  • FilteredListModel(container=<source_model>, master_items_key="items", items_key="mitems")

It provides a settable attribute sort_key (a callable that maps an item to a sort value).

MappedListModel

It is constructed with keyword arguments in this form:

  • MappedListModel(container=<source_model>, master_items_key="mitems", items_key="items")

The container is permitted to be a FilteredListModel.

ListModel (source model, already existing)

It is constructed as ListModel(<items_key>) and supports:

  • append_item(item)
  • insert_item(index, item)
  • remove_item(index)

Both of these model classes observe their container, so that mutations to the underlying ListModel propagate through the filtering/mapping layers.

Required Public API

The following must be exposed by both FilteredListModel and MappedListModel:

  1. begin_changes_event — an observable event object that has a .listen(callback) method; the method returns a subscription object that can be used as a context manager. The callback is invoked with a single positional argument: the items key of the model (a string).

  2. end_changes_event — an observable event object using the same .listen(callback) interface and calling convention. Its callback receives the items key (a string) as its single argument.

  3. changes() — a method that returns a context manager. Entering and exiting this context manager groups all item mutations that take place within it into a single change batch.

Required Behavior

When items are inserted into or removed from the underlying source model (with the result that the derived model's own item list changes), the derived model must fire its begin_changes_event before applying the change(s), and it must fire its end_changes_event after applying the change(s).

Mutations That Are Not Grouped

When mutations happen outside any changes() context, each individual mutation of the source model that affects the derived model results in exactly one begin_changes_event firing together with one matching end_changes_event firing.

  • Example: if one insert followed by one remove is performed on the source model, begin_changes_event fires twice and end_changes_event fires twice on the derived model.
Mutations That Are Grouped

When mutations happen inside a changes() context on the derived model, all mutations within that context are coalesced into a single batch: begin_changes_event fires exactly once (at the start of the batch) and end_changes_event fires exactly once (at the end of the batch), no matter how many individual insertions/removals took place inside the context.

  • Example: opening changes(), then performing two inserts and two removes on the source model, and then closing the context, causes begin_changes_event to fire once and end_changes_event to fire once on the derived model.
Propagation Through Chained Models

When a MappedListModel wraps a FilteredListModel (which itself wraps a ListModel), the batching behavior described above must hold end-to-end for the MappedListModel:

  • Source mutations that are not grouped produce one begin/one end on the MappedListModel for each mutation that affects it.
  • Grouping by means of the MappedListModel's own changes() context coalesces all contained source mutations into a single begin/end pair on the MappedListModel.

Additional Notes

  • Each begin/end callback is passed the string items key of the model that fired the event.
  • The changes() context manager must be safe under re-entrancy, producing exactly one begin/end pair per outermost grouping.

Task: Add Logarithmic Mode Support to Geometry.Ticker

Location of the Change

The class to modify is Ticker, which lives in the nion.utils.Geometry module.

Summary

For a numeric range, the Geometry.Ticker class produces a set of axis tick labels. This class must be extended such that a new logarithmic mode is accepted, while the linear behavior it already has remains intact.

Signature of the Constructor

Ticker(minimum, maximum, *, ticks=..., logarithmic=False)
  • minimum and maximum: floats that specify the value range.
  • ticks: an integer, accepted only as a keyword argument, that requests an approximate count of tick divisions.
  • logarithmic: a keyword-only boolean, False by default. Supplying False leaves the ticker in linear mode, its existing behavior; supplying True puts it into logarithmic mode.

Public Attribute

  • labels: a list of str holding one entry per computed tick, with the values in ascending order.

What Logarithmic Mode Means

Under logarithmic mode, what minimum and maximum contain are the base-10 logarithms of the actual values that get displayed. Put another way, what the caller passes in is math.log10(actual_low) and math.log10(actual_high). The labels must show the corresponding actual (delogarithmized) values, i.e. 10 ** tick_position.

Required Behavior

Edge Cases for Both Linear and Logarithmic Modes

Whatever the logarithmic flag is set to, each of the following (minimum, maximum) inputs must result in labels being exactly ['0'], ['1'], or ['-1'], as listed:

  • (0, 0) → ['0']
  • (1, 1) → ['1']
  • (-1, -1) → ['-1']
  • (-inf, inf) → ['0']
  • (-nan, nan) → ['0']
  • (nan, 1) → ['0']
  • (-inf, 1) → ['0']
  • (0, inf) → ['0']

(here, inf and nan mean math.inf / math.nan.)

Distinctness of the Labels

For any valid range that produces a normal set of ticks, all entries of labels must be distinct (no two ticks may render as the same string). In both modes this must hold, across a variety of ranges — including values as small as 1e-18, values as large as 1e12 and beyond, ranges of negative values, and ranges whose endpoints are extremely close together compared with their magnitude. Within logarithmic mode, the uniqueness requirement holds only when both endpoints of the actual range are strictly positive.

Exact Output for the Labels

Exactly the following results must be produced by the label formatting:

For linear mode:

  • Ticker(0, 1e8, ticks=3, logarithmic=False).labels → ['0e+00', '5e+07', '1.0e+08']
  • Ticker(0, 1000, ticks=3, logarithmic=False).labels → ['0', '500', '1000']
  • Ticker(2e-18, 1.11252e-10, ticks=5, logarithmic=False).labels → ['0e+00', '5.0e-11', '1.0e-10', '1.50e-10']

For logarithmic mode (the inputs given are the log10 of the actual endpoints; the labels shown are the actual values):

  • Ticker(0, 8, ticks=3, logarithmic=True).labels → ['1e+00', '1e+05', '1e+10']
  • Ticker(0, 3, ticks=3, logarithmic=True).labels → ['1', '100', '10000']
  • Ticker(math.log10(2e-18), math.log10(1.11252e-10), ticks=5, logarithmic=True).labels → ['1e-18', '1e-16', '1e-14', '1e-12', '1e-10', '1e-08']
  • Ticker(math.log10(1E12), math.log10(1.000062E12), ticks=5, logarithmic=True).labels → ['1.00000e+12', '1.00002e+12', '1.00005e+12', '1.00007e+12']
  • Ticker(math.log10(1E8 - 0.002), math.log10(1E8 + 0.002), ticks=3, logarithmic=True).labels → ['9.99999999977e+07', '1.00000000000e+08', '1.00000000002e+08']
Notes on Formatting, as Implied by the Required Output
  • Logarithmic mode places each tick at an exponent position, and the label then displays 10 ** position. Over a range covering many decades, the ticks land on whole powers of ten; such a tick is written either with one significant digit in scientific notation (e.g. 1e+00, 1e+05, 1e-18) or as a plain integer when the magnitude is small (1, 100, 10000).
  • A narrow logarithmic range (its endpoints close together) puts the tick positions at fractional exponents; enough significant digits must be used when rendering the resulting actual values, so that they stay distinct (as shown, up to many digits may be needed, e.g. 9.99999999977e+07).
  • In linear mode, a label is written either as a plain integer (0, 500, 1000) or in scientific notation, with the mantissa given enough precision that all labels stay distinct (0e+00, 5e+07, 1.0e+08; 0e+00, 5.0e-11, 1.0e-10, 1.50e-10).
  • Roughly ticks labels come out; the count is not required to match ticks exactly, since what decides it is the choice of "nice" tick step sizes across the range. For each case above, the labels shown are the exact expected counts and values.

Constraints

  • Linear mode as it exists now (the logarithmic=False path) must stay unchanged relative to the description above.
  • The logarithmic and ticks parameters are passed as keyword arguments.

Compatibility

  • Python 3.7+ is the target.

    • (-nan, nan) → ['0']

  • (-inf, inf) → ['0e+00']
