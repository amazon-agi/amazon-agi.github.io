01 The nion.utils.StructuredModel module provides a schema-based model system. 461 words · source specification

Task: Add a model_changed_event to StructuredModel

Overview

The nion.utils.StructuredModel module provides a schema-based model system. You must extend the models produced by this module so that they emit a deep change notification whenever the model's value changes at any level of nesting. This notification is exposed as a new event named model_changed_event.

Existing API (already present, used by this task)

The module nion.utils.StructuredModel already provides the following, which you may rely on:

  • StructuredModel.STRING, StructuredModel.INT — schema type constants for scalar field types.
  • StructuredModel.define_field(name, type) — defines a named field of a given schema type.
  • StructuredModel.define_record(name, fields) — defines a record schema from a list of fields.
  • StructuredModel.define_array(item_schema) — defines an array schema whose items conform to item_schema.
  • StructuredModel.build_model(schema, value=...) — builds a model instance from a schema and an initial value.
  • Array models support insert_item(index, item), remove_item(index), and an items sequence.
  • Record models expose their fields as attributes (e.g. a record with field x exposes a settable/gettable attribute model.x).

Required Change

Every model instance returned by build_model (records and arrays alike) must expose an attribute named model_changed_event. This must be an event object that supports:

  • .listen(callback) — registers a zero-argument callback, returning a listener object that can be closed (i.e. it is usable as the argument to contextlib.closing).

The model_changed_event must be fired once (invoking every registered callback with no arguments) each time the model's value changes, including changes that occur at any nested depth. Specifically:

  1. Array — basic item value changes. For an array model of scalar items, calling insert_item(index, value) fires the event exactly once, and calling remove_item(index) fires the event exactly once.

  2. Array — record item changes. For an array model whose items are record models:

    • Calling insert_item(index, record_model) fires the event exactly once.
    • After insertion, modifying a field of an item in the array (e.g. model.items[i].x = 55) fires the array model's event exactly once. That is, a change deep inside a contained record must propagate up to the containing array's model_changed_event.

  3. Record — nested record field changes. For a record model that contains a field whose value is itself a record model, modifying a field of the nested record (e.g. model.a.x = 11) fires the outer record model's model_changed_event exactly once. Deep changes must propagate up through nested records.

In all cases, no model_changed_event firing occurs merely from building the model or from registering a listener — the count of firings must be zero until an actual mutating operation is performed.

Notes

  • The event fires callbacks with no arguments.
  • Deep propagation is required: a mutation at any nesting level must cause exactly one firing on the top-level model that (directly or transitively) contains the mutated value.
02 Component Registry Module 415 words · source specification

Task Specification: Component Registry Module

Objective

Implement a new module Registry in the nion.utils package (i.e., importable as from nion.utils import Registry). This module provides a global registry that associates arbitrary objects ("components") with sets of string "component types", and allows those components to be looked up by type.

Public API

All functions are module-level functions in nion.utils.Registry.

register_component(component, component_types)

Registers component (any object) as being associated with each of the given component types.

  • component: the object to register.
  • component_types: a set of strings, each naming a component type.

Behavior:

  • After this call, component is associated with every type in component_types.
  • The same component object may be registered more than once with different (or additional) component type sets. Each call adds the given types to that component's set of associated types; it does not replace or remove previously associated types. After multiple registration calls, the component is associated with the union of all type sets it was registered with.
unregister_component(component, component_types=None)

Removes associations between component and component types.

  • component: the object to unregister.
  • component_types: an optional set of strings. This parameter defaults to None.

Behavior:

  • If component_types is provided (a set of strings), only those specified types are disassociated from component. Any of the component's other associated types remain in effect, and the component remains discoverable via those remaining types.
  • If component_types is omitted (or None), the component is fully unregistered: it is disassociated from all of its component types and is no longer discoverable by any type.
get_component(component_type)

Looks up a registered component by a single component type string.

  • component_type: a string naming a component type.

Behavior:

  • Returns a component object currently associated with component_type.
  • Returns None if no component is currently associated with component_type (including the case where a component was previously associated with that type but has since been unregistered from it).

Behavioral Example

Given a single object o:

  1. Registering o with types {"one", "two"}, then separately registering o with types {"three"}, results in o being retrievable via get_component("one") and get_component("three").
  2. Unregistering o with {"three"} removes only the "three" association: get_component("one") still returns o, while get_component("three") returns None.
  3. Unregistering o with no type argument removes all remaining associations: get_component("one") then returns None.

Notes

  • The registry state is global/module-level and shared across calls.
  • Component types are compared as plain strings; components are compared by identity/equality of the registered object.
03 FilteredListModel Ordering Behavior 956 words · source specification

Task Specification: FilteredListModel Ordering Behavior

Overview

You must implement/fix the FilteredListModel class in the module nion.utils.ListModel. This class provides a filtered and optionally sorted view of items held by a container list model. The focus of this task is ensuring that the filtered view maintains correct item ordering under all supported operations — whether sorted, unsorted, or transitioning between the two, and even when the underlying container changes while updates are in progress.

Public API Surface

The following must be importable from nion.utils.ListModel:

ListModel.ListModel(items_key)

A container list model constructed with a string key naming its item collection.

Required members:

  • append_item(item) — append an item to the end of the collection.
  • insert_item(index, item) — insert an item at the given index.
  • remove_item(index) — remove the item at the given index.
  • items — property returning the current list of items in order.
ListModel.FilteredListModel(container=None, items_key=None)

A list model presenting a filtered/sorted view over another list model's items.

Constructor keyword arguments:

  • container — the source list model to observe.
  • items_key — the string key identifying the item collection within the container.

Required attributes / properties (all settable after construction):

  • sort_key — a callable mapping an item to a comparison key, or None. When set to a callable, the view is sorted ascending by that key. When None, the view is unsorted.
  • filter — a filter object (see below) used to decide which container items appear in the view. When unset, all items pass.
  • container — settable property; assigning a new container list model rebinds the view to observe the new container's items.
  • items — property returning the current list of items in the view, in the correct order.

Required methods:

  • mark_changed() — force the view to recompute/refresh its contents.
  • begin_change() / end_change() — bracket a batch of container mutations. Between a begin_change and the matching end_change, the view should defer recomputation and produce a single consistent update when the outermost change completes. These calls may be nested (and nested across multiple FilteredListModel instances observing one another).

Because a FilteredListModel is itself a list model exposing items under an items_key, one FilteredListModel may serve as the container of another.

Filter classes in ListModel
  • ListModel.Filter(matches: bool) — a filter that accepts everything when constructed with True.
  • ListModel.PredicateFilter(predicate) — a filter constructed with a single-argument callable returning a truthy/falsy value; an item appears in the view exactly when the predicate returns truthy for it.

Required Behavior

Sorted view

When sort_key is set to a callable, the view's items are the container's passing items sorted ascending by the key. Sorted order must be maintained as items are inserted into or removed from the container. Example: for container items "3","1","4","2" with sort_key = lambda x: x, the view is ["1","2","3","4"]. After removing container items so only "3","2" remain, the view is ["2","3"]. After inserting more items, the view remains sorted.

Unsorted view

When sort_key is None (the default), the view's items preserve the container's ordering, restricted to items that pass the filter.

  • Applying PredicateFilter(lambda x: x != "4") to container "3","1","4","2" yields ["3","1","2"].
  • Removing the first container item updates the view to ["1","2"].
  • Inserting an item at the front of the container and appending another places them in their corresponding container positions within the filtered view (front-inserted item at the front, appended item at the end).
  • Mutations wrapped in begin_change/end_change produce the same final ordering as if applied individually. For instance, within a change block, inserting "5" at the front and appending "6" yields a view where "5" is first and "6" is last, with existing filtered items retaining their relative order.
Transition from sorted to unsorted

When sort_key is changed from a callable to None, the view must switch from sorted order to reflecting the container's current order (filtered). Setting a filter and then clearing sort_key must produce a view that follows container order among passing items. Example: starting sorted as ["1","2","3","4"], then applying PredicateFilter(lambda x: x != "4") and setting sort_key = None, the view becomes ["3","1","2"] (container order, filtered). Subsequent removals from the container maintain container order: removing the container item at index 1 ("1") yields ["3","2"].

Container replacement and reordering under a change block

When the view is unsorted and its container is reassigned while inside a begin_change/end_change block, the view must fully re-synchronize to the new container's ordering — even in the case where the new container holds the same set of items in a different order (a pure rearrangement). The view must not assume its existing order is still valid; it must adopt the new container's order.

This must work when the operations are nested across two FilteredListModel instances, where the outer instance's container is the inner instance:

  • Build container l with items "3","1","4","2" and a second container l2 with items "4","1","2","3".
  • l3 = FilteredListModel(container=l, items_key="items") → l3.items == ["3","1","4","2"].
  • l4 = FilteredListModel(container=l3, items_key="items") → l4.items == ["3","1","4","2"].
  • Within nested change blocks (l4.begin_change(), l3.begin_change(), mutate, l3.end_change(), l4.end_change()), first setting l3.filter = Filter(True) leaves ordering unchanged.
  • Then, within another nested change block, reassigning l3.container = l2 must cause both l3.items and l4.items to become ["4","1","2","3"] after the change blocks complete.

Notes

  • Filter changes, sort_key changes, and container changes must all correctly propagate to any downstream FilteredListModel observing this one.
  • The item type used throughout is str; ordering comparisons and predicates operate on plain values.

Compatibility maintenance (unrelated to ListModel): ensure any use of the abstract base classes for sequences references collections.abc (e.g., collections.abc.Sequence) rather than the deprecated collections aliases, so that model objects produced by StructuredModel.build_model are recognized as collections.abc.Sequence instances where applicable.

04 Begin/End Change Notifications for List Models 538 words · source specification

Task Specification: Begin/End Change Notifications for List Models

Overview

You must add change-batching notifications to two list model classes in the module nion.utils.ListModel: FilteredListModel and MappedListModel. These notifications signal when a batch of item mutations begins and ends, and callers must be able to group multiple mutations into a single batch.

Affected Classes and Constructors

FilteredListModel

Constructed with keyword arguments used in these forms:

  • FilteredListModel(container=<source_model>, items_key="items")
  • FilteredListModel(container=<source_model>, master_items_key="items", items_key="mitems")

It has a settable attribute sort_key (a callable mapping an item to a sort value).

MappedListModel

Constructed with keyword arguments in this form:

  • MappedListModel(container=<source_model>, master_items_key="mitems", items_key="items")

The container may be a FilteredListModel.

ListModel (source model, already exists)

Constructed as ListModel(<items_key>) and supports:

  • append_item(item)
  • insert_item(index, item)
  • remove_item(index)

These models observe their container so that mutations to the underlying ListModel propagate through the filtering/mapping layers.

Required Public API Surface

Both FilteredListModel and MappedListModel must expose:

  1. begin_changes_event — an observable event object with a .listen(callback) method returning a subscription object usable as a context manager. The callback is invoked with a single positional argument: the model's items key (a string).

  2. end_changes_event — an observable event object with the same .listen(callback) interface and calling convention. The callback receives the items key (a string) as its single argument.

  3. changes() — a method returning a context manager. Entering and exiting this context manager groups all item mutations that occur within it into a single change batch.

Required Behavior

When items are inserted into or removed from the underlying source model (causing the derived model's own item list to change), the derived model must fire its begin_changes_event before applying the change(s) and fire its end_changes_event after applying the change(s).

Ungrouped mutations

When mutations occur outside any changes() context, each individual mutation of the source model that affects the derived model produces exactly one begin_changes_event firing and one matching end_changes_event firing.

  • Example: performing one insert followed by one remove on the source model results in begin_changes_event firing twice and end_changes_event firing twice on the derived model.
Grouped mutations

When mutations occur inside a changes() context on the derived model, all mutations within that context are coalesced into a single batch: begin_changes_event fires exactly once (at the start of the batch) and end_changes_event fires exactly once (at the end of the batch), regardless of how many individual insertions/removals occurred inside the context.

  • Example: opening changes(), then performing two inserts and two removes on the source model, then closing the context, results in begin_changes_event firing once and end_changes_event firing once on the derived model.
Propagation through chained models

When a MappedListModel wraps a FilteredListModel (which in turn wraps a ListModel), the batching behavior described above must hold end-to-end for the MappedListModel:

  • Ungrouped source mutations produce one begin/one end per affecting mutation on the MappedListModel.
  • Grouping via the MappedListModel's own changes() context coalesces all contained source mutations into a single begin/end pair on the MappedListModel.

Notes

  • The argument passed to each begin/end callback is the string items key of the model that fired the event.
  • The changes() context manager must be re-entrant-safe with respect to producing exactly one begin/end pair per outermost grouping.
05 Modify the Ticker class in the nion.utils.Geometry module. 646 words · source specification

Task: Add Logarithmic Support to Geometry.Ticker

Location

Modify the Ticker class in the nion.utils.Geometry module.

Overview

The Geometry.Ticker class computes a set of axis tick labels for a numeric range. You must extend it to accept a new logarithmic mode while preserving its existing linear behavior.

Constructor Signature

Ticker(minimum, maximum, *, ticks=..., logarithmic=False)
  • minimum, maximum: floats describing the value range.
  • ticks: keyword-only integer requesting an approximate number of tick divisions.
  • logarithmic: keyword-only boolean (default False). When False, the ticker behaves in linear mode (the existing behavior). When True, the ticker operates in logarithmic mode.

Public Attribute

  • labels: a list of str, one per computed tick, in ascending order of value.

Logarithmic Mode Semantics

In logarithmic mode, minimum and maximum are the base-10 logarithms of the actual values being displayed. That is, the caller passes math.log10(actual_low) and math.log10(actual_high). The labels displayed must represent the corresponding actual (delogarithmized) values, i.e. 10 ** tick_position.

Required Behavior

Edge cases (both linear and logarithmic modes)

For each of the following (minimum, maximum) inputs, regardless of the logarithmic flag, labels must be exactly ['0'], ['1'], or ['-1'] as listed:

  • (0, 0) → ['0']
  • (1, 1) → ['1']
  • (-1, -1) → ['-1']
  • (-inf, inf) → ['0']
  • (-nan, nan) → ['0']
  • (nan, 1) → ['0']
  • (-inf, 1) → ['0']
  • (0, inf) → ['0']

(where inf and nan are math.inf / math.nan.)

Uniqueness of labels

For any valid range where a normal set of ticks is produced, all entries in labels must be distinct (no two ticks may render to the same string). This must hold for both modes across a variety of ranges, including very small values (down to 1e-18), very large values (up to 1e12 and beyond), negative ranges, and ranges where the endpoints are extremely close together relative to their magnitude. In logarithmic mode this uniqueness requirement applies only when both endpoints of the actual range are strictly positive.

Exact label output

The label formatting must produce exactly the following results:

Linear mode:

  • Ticker(0, 1e8, ticks=3, logarithmic=False).labels → ['0e+00', '5e+07', '1.0e+08']
  • Ticker(0, 1000, ticks=3, logarithmic=False).labels → ['0', '500', '1000']
  • Ticker(2e-18, 1.11252e-10, ticks=5, logarithmic=False).labels → ['0e+00', '5.0e-11', '1.0e-10', '1.50e-10']

Logarithmic mode (inputs are log10 of actual endpoints; labels are actual values):

  • Ticker(0, 8, ticks=3, logarithmic=True).labels → ['1e+00', '1e+05', '1e+10']
  • Ticker(0, 3, ticks=3, logarithmic=True).labels → ['1', '100', '10000']
  • Ticker(math.log10(2e-18), math.log10(1.11252e-10), ticks=5, logarithmic=True).labels → ['1e-18', '1e-16', '1e-14', '1e-12', '1e-10', '1e-08']
  • Ticker(math.log10(1E12), math.log10(1.000062E12), ticks=5, logarithmic=True).labels → ['1.00000e+12', '1.00002e+12', '1.00005e+12', '1.00007e+12']
  • Ticker(math.log10(1E8 - 0.002), math.log10(1E8 + 0.002), ticks=3, logarithmic=True).labels → ['9.99999999977e+07', '1.00000000000e+08', '1.00000000002e+08']
Formatting notes derived from the required output
  • In logarithmic mode, ticks are placed at exponent positions and labels show 10 ** position. When the range spans many decades, ticks fall on whole powers of ten and render with a single significant digit in scientific notation (e.g. 1e+00, 1e+05, 1e-18) or as plain integers for small magnitudes (1, 100, 10000).
  • When the logarithmic range is narrow (endpoints close together), tick positions fall at fractional exponents; the resulting actual values must be rendered with enough significant digits to remain distinct (as shown, up to many digits, e.g. 9.99999999977e+07).
  • Linear-mode labels use either plain integer form (0, 500, 1000) or scientific notation with a mantissa precision sufficient to keep all labels distinct (0e+00, 5e+07, 1.0e+08; 0e+00, 5.0e-11, 1.0e-10, 1.50e-10).
  • The number of labels produced is approximately ticks but need not equal it exactly; it is determined by choosing "nice" tick step sizes over the range. The labels above reflect the exact expected counts and values for each case.

Constraints

  • Existing linear-mode behavior (the logarithmic=False path) must remain unchanged from what is described above.
  • The logarithmic and ticks parameters are keyword arguments.

Compatibility

  • Target Python 3.7+.

Overview

Public API

Geometry.LinearTicker

Behavior: LinearTicker.labels

The label list must contain unique strings (no duplicates) across normal ranges.

Edge cases (produce exactly ['0'])

  • minimum == maximum == 1 → ['1']
  • minimum == maximum == -1 → ['-1']
  • Any range where an endpoint is non-finite (±inf or nan), or the span is otherwise degenerate/undefined → ['0']. Specifically:
    • (-inf, inf) → ['0']
    • (-nan, nan) → ['0']
    • (nan, 1) → ['0']
    • (-inf, 1) → ['0']
    • (0, inf) → ['0']
Normal ranges

Behavior: LogTicker.labels

Inputs are log10-space endpoints. Ticks are placed on decade boundaries (powers of ten) spanning the requested range, with labels formatted in scientific notation.

Edge cases (single-endpoint / degenerate ranges)

When minimum == maximum (equal log endpoints), the result spans two decades starting at 10**floor(minimum), and each decade is subdivided into the mantissa multipliers 1, 2, 4, 6, 8. Formatting uses scientific notation with a single significant digit ('{:.0e}' style):

  • LogTicker(0, 0, ticks=3).labels → ['1e+00', '2e+00', '4e+00', '6e+00', '8e+00', '1e+01', '2e+01', '4e+01', '6e+01', '8e+01']
  • LogTicker(1, 1, ticks=3).labels → ['1e+01', '2e+01', '4e+01', '6e+01', '8e+01', '1e+02', '2e+02', '4e+02', '6e+02', '8e+02']
  • LogTicker(-1, -1, ticks=3).labels → ['1e-01', '2e-01', '4e-01', '6e-01', '8e-01', '1e+00', '2e+00', '4e+00', '6e+00', '8e+00']

When any endpoint is non-finite (±inf or nan), or the range is otherwise undefined, the result is exactly ['0e+00']:

  • (-inf, inf) → ['0e+00']
  • (-nan, nan) → ['0e+00']
  • (nan, 1) → ['0e+00']
  • (-inf, 1) → ['0e+00']
  • (0, inf) → ['0e+00']
Normal ranges

Ticks are placed at power-of-ten boundaries spanning the log range, with a decade step chosen from the range size and ticks hint. Exact required outputs:

  • LogTicker(0, 8, ticks=3).labels → ['1e+00', '1e+03', '1e+06', '1e+09']
  • LogTicker(0, 3, ticks=3).labels → ['1e+00', '1e+01', '1e+02', '1e+03']
  • LogTicker(math.log10(2e-18), math.log10(1.11252e-10), ticks=5).labels → ['1e-18', '1e-16', '1e-14', '1e-12', '1e-10', '1e-08']

When the log range is very narrow (endpoints fall within the same decade or nearly so), the ticks fall back to finely-spaced values within the decade, formatted with higher precision so labels remain distinct:

  • LogTicker(math.log10(1E12), math.log10(1.000062E12), ticks=5).labels → ['1.00000e+12', '1.00002e+12', '1.00005e+12', '1.00007e+12']
  • LogTicker(math.log10(1E8 - 0.002), math.log10(1E8 + 0.002), ticks=3).labels → ['9.99999999977e+07', '1.00000000000e+08', '1.00000000002e+08']

The label list must contain unique strings across normal ranges.

Additional Notes

  • The module should use from __future__ import annotations for its type annotations.
  • The labels attribute is accessed as an attribute (not called).

Task Specification: Add to_color_with_alpha Method to Color Class

Overview

Add a new method to_color_with_alpha to the Color class located in the nion.utils.Color module.

API Surface

The Color class already exists and is constructed with a single argument (a color string such as a named color, hex string, or rgb/rgba functional notation, or None). Instances expose a color_str attribute holding the color's canonical string representation.

Add the following method:

def to_color_with_alpha(self, alpha: float) -> "Color":

Behavior

The method returns a new Color instance whose color is the current color's RGB components combined with the provided alpha value, represented as an 8-digit hexadecimal string of the form #aarrggbb, where:

  • aa is the two-digit hex encoding of the alpha channel,
  • rrggbb are the two-digit hex encodings of the red, green, and blue channels.

All hex letters in the resulting string are lowercase.

Alpha encoding

The alpha argument is a float nominally in the range 0.0 to 1.0, representing the fraction of full opacity. It is converted to an integer 0–255 channel value.

  • alpha = 1.00 maps to ff.
  • alpha = 0.00 maps to 00.
  • alpha = 0.25 maps to 40.
  • alpha = 0.50 maps to 80.
  • alpha = 0.75 maps to c0.

The alpha value must be clamped to the [0.0, 1.0] range before conversion:

  • Any alpha greater than 1.0 (e.g. 1.50) maps to ff.
  • Any alpha less than 0.0 (e.g. -1.50) maps to 00.
RGB source

The red, green, and blue channels are taken from the current color and rendered as their two-digit lowercase hex values in the result. This must work for the color's underlying RGB regardless of the original input representation, including:

  • Named colors (e.g. "thistle" → RGB d8 bf d8).
  • Six-digit hex strings (e.g. "#d8bfd8").
  • Three-digit shorthand hex strings, which expand each digit by duplication (e.g. "#246" → RGB 20 40 60).
