Overview

Build a Python module called blacken_docs that uses the black code formatter to reformat Python code embedded in Markdown and reStructuredText (reST) documents. Both a programmatic API and a command-line entry point must be exposed by the module.

Public API

blacken_docs._black_version()

Supply a function that takes no arguments and returns the version of the installed black package as a distutils.version.LooseVersion instance. In particular, its result must be comparable with LooseVersion('19.3b0').

blacken_docs.format_str(src, **opts) -> tuple

Reformat each recognized Python code block found in the document string src.

  • src is the complete text of the document.
  • **opts holds Black formatting options and must be forwarded to Black's string-formatting function for every code block. The function must support the arguments suited to the installed Black version:
    • for Black versions older than 19.3b0, a caller may provide line_length=<int> and mode=<black mode>;
    • for Black 19.3b0 and newer, a caller may provide mode=<black FileMode>.
  • The value returned must be a tuple with exactly two elements, so that it can be unpacked into exactly two targets (for example, after, _ = format_str(src, **opts)). Its first element is the resulting document string; what the second element contains is unspecified.

Behavior:

  • An empty input string produces an empty result string with no change.
  • Reformatting is applied only to Python within recognized code blocks. Apart from that, the surrounding document text, code-block markers and directives, marker indentation, and non-code content must be preserved exactly.

Code blocks that are recognized

Markdown fenced blocks

A fenced Python block starts at a line whose content is ```python (with optional indentation) and ends at a line whose content is ``` at the matching indentation. The content between those fences is Python.

  • Strip the fence's common indentation from the code before handing it to Black, then reapply that indentation to the formatted result.
  • Fenced blocks that are indented, such as blocks nested beneath Markdown list items, must therefore be formatted while their nesting indentation is retained.
  • Trailing whitespace following the closing ``` marker on its line must be preserved exactly as written.

For example, formatting f(1,2,3) inside either an unindented or an indented Python fence must produce f(1, 2, 3) while the fences and their indentation stay intact.

Code blocks in reStructuredText

A .. code-block:: python directive with optional indentation must be recognized. Indented option lines, such as :lineno-start: 10 and :emphasize-lines: 11, can follow the directive, and then a blank separator line. The indented body that comes after is Python code.

  • Strip the code body's block indentation before formatting and reapply it afterward.
  • The directive, all option lines, blank separator lines, and surrounding document text must be preserved exactly.
  • Directives that are nested or indented must be handled, including a Python code-block directive nested under another reST directive, while every indentation level is preserved.

Command-line interface

blacken_docs.main(argv) -> int

argv is a sequence of command-line arguments with the program name excluded. The function returns an integer status: 0 when no file changes are needed, and nonzero when at least one file is rewritten or a non-ignored parse error occurs.

One or more positional file paths are accepted. Each file is read, all recognized Python code blocks are reformatted, and the file is rewritten in place only when its resulting content differs.

Supported options:

  • --line-length <int>: sets Black's maximum line length.
  • --py36: targets Python 3.6-or-newer syntax formatting, including the use of trailing commas in argument lists involving *args.
  • --skip-string-normalization: turns off Black's string-quote normalization so that, for example, single-quoted strings remain single-quoted.
  • --skip-errors: leaves code blocks that Black cannot parse unchanged and continues processing the other blocks.
Behavior of the CLI
  • No changes needed: If all inputs are already formatted and no non-ignored parse error occurs, the file is left untouched, nothing is written to stderr, and 0 is returned.
  • File modified: A changed file is overwritten, exactly "{filepath}: Rewriting...\n" is printed to stdout for that file, and nonzero is returned.
  • Line length: A block whose Black output fits within the selected line length remains unchanged. When a shorter line length requires wrapping, Black's wrapped form must be produced. For example, Black may explode a long function call over multiple lines and add its usual trailing comma; this results in a rewrite and a nonzero status.
  • Python 3.6 target: In the absence of --py36, a multiline function definition containing a *args parameter can remain unchanged. When --py36 is given, Black may add a trailing comma after that parameter, which causes a rewrite and a nonzero status.
  • Skipped string normalization: With --skip-string-normalization, a single-quoted literal must not be converted to double quotes. If that is the only formatting Black would otherwise perform, the file remains unchanged and the status is 0.
  • Parse error by default: If Black cannot parse a code block, that file must not be modified. A message beginning with "{filepath}:{lineno}: code block parse error" is printed to stdout, and nonzero is returned. lineno is the 1-based document line number on which the code block itself begins: the opening ```python fence for Markdown or the .. code-block:: python directive for reST. So, a fenced block whose opening fence is on line 1 reports line 1, even when its invalid Python starts on line 2.
  • Ignored parse error: With --skip-errors, an unparseable block is preserved unchanged and formatting of the valid blocks in the same file continues. If any valid block changes, the file is rewritten with those changes and nonzero is returned. An ignored error does not itself make the command fail.

Formatting fidelity

For each extracted code body, the formatting must match Black's output when the supplied options are used. For example, f(1,2,3) becomes f(1, 2, 3), and f( ) becomes f().

Dependency

The installed black package must be used for both version detection and code formatting.

Task specification: the blacken_docs module

Summary

The importable blacken_docs module is to be implemented or modified so that it operates through the modern black formatter API (Black 19.3b0 and later only). Python source that is embedded within Markdown fenced code blocks and reStructuredText code directives gets reformatted by the module; the document surrounding those constructs is preserved.

Public interface

blacken_docs.format_str(src, mode)
Arguments
  • src (str): a Markdown or reStructuredText document's complete source text.
  • mode (black.FileMode): the Black file-mode object that governs formatting, which carries settings such as line length. The function must accept it as its second positional argument, which is required; the supported call shape is therefore format_str(src, mode), and the legacy keyword-option style with arguments such as line_length=... or mode=... is not supported.
Returned value

The return value is a two-tuple (after, errors):

  • after (str) holds the document that results.
  • errors is the second returned element and concerns code-block formatting errors. Here, no representation that is more specific is required for this element; after is the only element this specification relies upon.
How the formatting behaves

The recognized Python code constructs are the ones listed below; src is to be scanned for them. Each Python source fragment contained in them is to be passed to Black using the supplied mode, that fragment's place is taken by Black's output, and all text outside the recognized blocks is left unchanged.

  1. Python blocks fenced in Markdown

    A block qualifies when its opening line is made up of three backticks with python immediately following and its closing line is made up of three backticks as well. As an illustration, a body written as f(1,2,3) comes out as f(1, 2, 3).

    • Whitespace that remains after the closing fence marker counts as valid and must be preserved exactly.
    • The fences themselves may be indented, inside a list item for instance. The indentation of both fences is preserved, and every formatted code line is re-indented to the indentation the block originally had.

  2. Python code directives in reStructuredText

    Directives reading .. code-block:: python are recognized, and formatting is applied to their indented code bodies.

    • After the formatting, the code body's indentation is preserved.
    • The directive itself may be indented; both that indentation and the structure of the document surrounding it are to be preserved.
    • Option lines belonging to the directive and appearing immediately after it, such as :lineno-start: 10 or :emphasize-lines: 11, must stay unchanged; the Python source that goes to Black does not include them.

When the input is empty, format_str('', mode) must return '' as the tuple's first element, adding no content whatsoever.

blacken_docs.main(argv)
Arguments and file processing

A sequence of command-line arguments makes up argv. It may include one or more file paths among its positional arguments, alongside the options described below.

For each path that is supplied, the document is read, the same embedded-code formatting that format_str applies is carried out, and the file is rewritten in place only when its resulting content differs. All supplied paths are processed, and their outcomes feed into one exit status.

Options that are supported
  • --line-length <int> determines the maximum line length Black applies to code-block formatting. It must be accepted in standard forms such as --line-length=50. Different values must affect wrapping in the same way the corresponding black.FileMode setting does; to illustrate, code that fits at 80 characters may be expanded across multiple lines at 50 characters.
  • --target-version <version> picks the Python version that Black is to target, --target-version=py36 being an example. Formatting that is sensitive to the version must follow the target chosen. One case in point: selecting py36 must allow formatting such as adding a trailing comma after a starred parameter, and expanding the construct when Black deems it appropriate.
  • --skip-string-normalization switches off Black's normalization of string quotes, its other formatting being retained. To illustrate: a single-quoted string that needs no other change must stay single-quoted instead of being turned into double quotes.
  • --skip-errors makes code blocks that Black cannot parse get skipped. Every unparseable block must remain unchanged; the same document's other valid blocks, however, still undergo reformatting and may bring about a rewrite of the file.
Standard output and exit status

  • A line of exactly the following form, ending with a newline, is written to standard output for every rewritten file:

    {filepath}: Rewriting...

    {filepath} here is the path given for that file. Other applicable diagnostics may show up separately.

  • A falsy integer status (0) is returned when no file was rewritten and no non-skipped formatting error happened.

  • When at least one file was rewritten, a truthy, nonzero status is returned.

  • A truthy, nonzero status is returned as well for a code-block parse error when --skip-errors is not active, even if no file was rewritten. A nonzero result therefore signals either a rewrite or an unskipped parse failure.

  • A parse failure that --skip-errors causes to be ignored contributes nothing toward a nonzero status. If no content is rewritten and no non-skipped error takes place, zero remains the result. Content in the same document that was formatted successfully may still lead to a rewrite and a nonzero result.

Handling of parse errors

If Black cannot parse a recognized code block and --skip-errors is not in effect:

  • A diagnostic is printed to standard output, its text starting with {filepath}:{lineno}: code block parse error; further exception details may follow that prefix.
  • {lineno} stands for the one-based line number, within the document, of the fence or directive that opens the offending block.
  • The affected file is left completely unmodified; that includes withholding formatting changes which would otherwise be valid in that file.
  • A truthy, nonzero status is returned.

Compatibility constraints

  • Only Black 19.3b0 and newer are to be supported; the modern black.FileMode(...) API is to be used, with a mode passed to Black's formatter.
  • There is no requirement of compatibility with pre-19.3b0 Black releases and their legacy option style.
  • Importing the module as blacken_docs must be possible.

Task Specification for the blacken_docs Module

Summary

Implement a module called blacken_docs that uses Black to reformat Python code embedded in documentation files. The module exposes a programmatic API, format_str, together with a command-line entry point, main.

Each recognized code body must be extracted, formatted with the Black configuration that is supplied, re-indented to fit its documentation context, and inserted back into the document. Text outside recognized code bodies — block markers and directive metadata included — must stay unchanged.

Public API

blacken_docs.format_str(src, black_mode)
  • Parameters:
    • src (str): the entire text of a document that may contain embedded Python code blocks.
    • black_mode: a Black Mode/FileMode object that controls formatting behavior, for example target versions and string normalization.
  • Returns: a 2-tuple (new_contents, errors). new_contents is the document text once every recognized Python code block has been formatted. The second element of the tuple is not relied upon in any other way by the behavior specified here.

For every supported block, format_str must:

  1. pull out and dedent the Python body so that Black can format it as standalone Python code;
  2. format it with the supplied black_mode;
  3. re-apply the appropriate documentation-level base indentation while Black's relative indentation within the code is preserved; and
  4. leave unchanged all content that lies outside the code body.

A document that contains no recognized blocks — the empty string included — must be returned unchanged.

blacken_docs.main(argv)
  • Parameters: argv, a sequence of strings that are the command-line arguments.
  • Behavior: handle every filename argument in place, replacing its text with the outcome of formatting the recognized code blocks it contains.
  • Return value: return a falsy value, such as 0, when no file was changed; return a truthy value, such as 1, when at least one file was modified.

The option below must be parsed and applied:

  • --target-version VERSION: choose a Black target version, for example py27 or py36. The option may be given more than once. All target versions that are supplied must be collected and passed to Black together.

Every file read and write carried out by main must operate on text content.

Supported Code Block Types

Fenced Python blocks in Markdown

Recognize fenced Markdown blocks where the opening fence declares python:

```python
f(1,2,3)
```

The result of formatting is:

```python
f(1, 2, 3)
```

Fences may be indented, for instance when nested beneath a list item. The code must be dedented for Black and then re-indented to the base indentation of the opening fence. Otherwise, the opening and closing fence lines must remain unchanged, trailing whitespace on the closing fence included. For example:

- do this:
  ```python
  f(1,2,3)
  ```

turns into:

- do this:
  ```python
  f(1, 2, 3)
  ```
Python directives in reStructuredText

Recognize both forms of the reStructuredText Python directive:

.. code-block:: python

    <python code>

as well as:

.. sourcecode:: python

    <python code>

The directive's indented code body must be dedented, formatted with Black, and re-indented to the body's original base indentation. Black's relative indentation within the body must be preserved.

The directive itself may be indented underneath another reStructuredText directive or construct. Its own indentation, the extra indentation of its code body, and all surrounding indentation levels must be retained. For example:

.. versionadded:: 3.1

    hello

    .. code-block:: python

        def hi():
            f(1,2,3)

    world

turns into:

.. versionadded:: 3.1

    hello

    .. code-block:: python

        def hi():
            f(1, 2, 3)

    world

Between the directive line and the code body, directive option lines may appear. Those lines, their indentation, and blank lines separating them must be preserved unchanged; only the Python body itself is formatted. For example:

.. code-block:: python
    :lineno-start: 10
    :emphasize-lines: 11

    def foo():
        bar(1,2,3)

turns into:

.. code-block:: python
    :lineno-start: 10
    :emphasize-lines: 11

    def foo():
        bar(1, 2, 3)
Python minted environments in LaTeX

Recognize LaTeX minted environments declaring Python:

\begin{minted}{python}
<python code>
\end{minted}

Leading whitespace may be present on the opening \begin{minted}{python} line and on the closing \end{minted} line. The indentation of the opening line determines the base indentation for the formatted code body. Dedent the original body, format it with Black, and re-indent the result to that base; Black's own relative indentation must stay on top of it. The opening and closing marker lines themselves must keep their original text and indentation.

For example:

hello
  \begin{minted}{python}
    if True:
      f(1,2,3)
  \end{minted}
world!

turns into:

hello
  \begin{minted}{python}
  if True:
      f(1, 2, 3)
  \end{minted}
world!

When the markers are not indented:

hello
\begin{minted}{python}
f(1,2,3)
\end{minted}
world!

turns into:

hello
\begin{minted}{python}
f(1, 2, 3)
\end{minted}
world!

Behavior of Black target versions

Every recognized block type must honor the Black mode supplied to format_str as well as the target versions selected through main.

For syntax whose formatting depends on the configured target version, choosing an appropriate version must produce the corresponding Black result. For example, --target-version py36 can lead Black to add a trailing comma after *args in a function signature that is sufficiently long, thereby modifying the file. When the embedded code is already formatted under the selected constraints, the file must not be rewritten.

Passing several target versions, for instance repeated --target-version py27 and --target-version py36 options, must be accepted and applied as combined constraints. When the code is already formatted under those combined constraints, no modification happens.

Behavior Requirements

The task at hand adds/ensures support for two categories of embedded code recognition.

1. PythonTeX pyblock environments (LaTeX)

Example of the transformation:

Input:

hello

\end{pyblock}
world!

Output:

hello
\begin{pyblock}

\end{pyblock}
world!

(Note that in this scenario the closing world! line carries no trailing newline and must stay that way.)

2. Code blocks that sit inside Python docstrings

If the input document is itself Python source code, documentation code blocks embedded inside docstrings must also be recognized and reformatted. Example of the transformation:

Input:

def f():
    """hello world

    .. code-block:: python

        f(1,2,3)

    ```python
    f(1,2,3)
    ```
    """

Output:

def f():
    """hello world

    .. code-block:: python

        f(1, 2, 3)

    ```python
    f(1, 2, 3)
    ```
    """

In this example, both the code under the reStructuredText code-block directive (indented beneath the directive) and the code inside the Markdown fence are reformatted (f(1,2,3) → f(1, 2, 3)), whereas the docstring quotes, blank lines, directive line, fence markers, and the function definition stay unchanged. Note that the indentation of the embedded code blocks (relative to the docstring) is preserved.

Preservation Constraints

  • Text located outside recognized code blocks is emitted byte-for-byte unchanged.
  • Blank lines, indentation levels, and delimiter/marker lines are kept intact.
  • The presence or absence of a trailing newline at the end of the document is preserved.

Environment

  • Python 3.6.1 or newer is required.
  • Relies on the black library to carry out the actual code formatting.

The Task

Introduce support for reStructuredText pycon code blocks in blacken-docs.

Overview

Make blacken_docs.format_str recognize and format Python interactive-console (pycon) sessions embedded in reStructuredText code-block directives. Python source entered at the console prompts must be reformatted with Black using the mode that is supplied, while the directive structure, console prompts, program output, indentation, surrounding text, and surrounding whitespace are preserved as described below.

Public API

The existing function and its signature must be kept:

blacken_docs.format_str(src: str, black_mode) -> tuple[str, ...]
  • src is the document's complete source text.
  • black_mode is a black.Mode-style configuration object and must be passed through when Python source is formatted.
  • The first element of the returned tuple is the document text after reformatting. The return shape, along with all other established behavior of this API, must stay compatible.

The recognized construct

The new behavior comes into play for an RST directive of this form:

.. code-block:: pycon

  1. Pull out, format, write back. Task: Add Support for reStructuredText Literal Blocks in blacken_docs.format_str

Background

The blacken_docs module offers a format_str function that uses Black to reformat Python code embedded in documentation source (Markdown, reStructuredText, LaTeX, etc.).

Change to the Function Signature

A new keyword-only argument must be accepted by the public function blacken_docs.format_str:

def format_str(src, black_mode, *, rst_literal_blocks=False):
    ...
  • src (str): the text of the documentation source.
  • black_mode: the Black Mode object that controls formatting.
  • rst_literal_blocks (bool, keyword argument, default False): setting it to True enables formatting of reStructuredText literal blocks (described below).

The return value is a 2-tuple (new_contents, errors): new_contents holds the reformatted source (str), and errors is a list of errors (an empty list when there are none).

All behavior and all keyword arguments that already exist must be preserved. When the new argument is left at its default, it must not disturb any current functionality.

New Behavior: Literal Blocks in reStructuredText

If rst_literal_blocks=True is passed, the function must, in addition, detect Python code contained in reStructuredText literal blocks and reformat it.

A paragraph line ending with the double-colon marker :: introduces a literal block; after it come a blank line and then an indented block of content. That indented content is the literal block body. For example, take this input:

hello::

    f(1,2,3)

world

Passing rst_literal_blocks=True causes the indented body (f(1,2,3)) to be treated as Python code and reformatted with Black, while the surrounding text and indentation are preserved. The output is:

hello::

    f(1, 2, 3)

world
Edge Cases (must result in no changes and no errors)

  1. Nested content that does not form a literal block. This case applies when the :: marker does not introduce a literal block of Python code — for example, a bulleted list item that contains an indented reStructuredText directive rather than a literal block introduced by :::

    * hello

  .. warning::

    don't hello too much

    The function must return the source unchanged, together with an empty list of errors. (In this example, warning:: is a directive line, not a paragraph that ends in the literal-block marker and is followed by an indented Python body.)

  2. Literal block that is empty. A line ends with ::, but no indented literal body follows it (the next non-blank content sits at the same or lower indentation, e.g. a directive):

    Example::

.. warning::

    There was no example.

    The function must return the source unchanged, together with an empty list of errors.

In both edge cases, the reformatting must correctly recognize that no Python literal block body is present to format, and leave the input untouched.

Note on Scope

This new detection takes effect only when rst_literal_blocks=True. It is a capability separate from the existing reStructuredText .. code-block:: / doctest handling, which continues to work unchanged no matter how this flag is set.

Existing behavior for string-normalization, line-length, target-version, error-reporting, and skip-errors remains unchanged, both in the module and in its main entry point.

Task Specification: blacken-docs Formatter for Code Blocks

Overview

A Python package called blacken_docs is to be implemented. It reformats Python code that appears in documentation files (Markdown, reStructuredText, and LaTeX): the tool extracts the code blocks, runs the Black formatter over them, and leaves the prose around them untouched.

Package structure and public API

It must be possible to import the package as blacken_docs, and a blacken_docs.__main__ submodule must be exposed too (importing it must succeed).

blacken_docs.format_str
def format_str(src: str, black_mode: black.Mode) -> tuple[str, list]:
    ...
  • src: the whole text of a documentation source string.
  • black_mode: an instance of black.FileMode/black.Mode that governs the formatting (e.g. line length, string normalization, target versions).
  • The return value is a 2-tuple (new_contents, errors):
    • new_contents: the incoming text once every recognized Python code block has been reformatted.
    • errors: a list that collects the errors encountered (an empty list when there are none).

One further keyword-only argument is required, though passing it is optional:

def format_str(src, black_mode, *, rst_literal_blocks: bool = False) -> tuple[str, list]:
  • Passing rst_literal_blocks=True makes literal blocks of reStructuredText — the kind introduced by a paragraph ending in :: — count as Python code blocks too, so they are reformatted.
blacken_docs.main
def main(argv: Sequence[str] | None = None) -> int:
    ...
  • The function accepts a sequence of command-line arguments, made up of filenames and options.
  • Each file that is named gets read and reformatted in place; the result is written back only when changes are made.
  • The return value is falsy (0) if no file was modified and no errors were reported; it is truthy (nonzero) if an error was reported or any file was rewritten.
  • These options are supported:
    • --line-length N — handed through to Black's line length.
    • --target-version VER — it may be supplied multiple times; each occurrence adds one Black target version (e.g. py35, py36).
    • --skip-string-normalization — Black's string quote normalization is switched off by it.
    • --skip-errors — the tool does not fail on code blocks that cannot be parsed; the other blocks continue to be processed.
    • A filename may be placed before or after the option flags.

format_str behavior

Given the empty string as input, the function returns the empty string, unchanged.

Fenced code blocks in Markdown

A fenced block is recognized when its opening line consists of three backticks followed by a language tag:

  • A block tagged python is a Python block, and Black reformats its body.
  • A block tagged pycon is an interactive-console block (the pycon rules below apply).
  • Everything lying between the opening fence and the closing `` fence makes up the block body.

All of the following rules must hold:

  • Whitespace between the backticks and the language tag (e.g. ``` python) is permitted, and the output opening fence preserves it.
  • After the closing fence, trailing whitespace (e.g. ``` ) is preserved.
  • Fence options: whatever extra text follows the language tag on the opening fence line must be allowed and preserved verbatim. For example, an opening line of ```python title='example.py' is a valid Python block; the block body is reformatted and the opening line (including title='example.py') is emitted unchanged. The same applies to ```pycon title='Session 1'.
  • Support covers indented fenced blocks: if the opening fence carries indentation (e.g. by two spaces inside a list item), the reformatted body gets that indentation applied, and the fence lines preserve it.
LaTeX blocks
  • A \begin{minted}{python} … \end{minted} block gets reformatted as Python.
  • A \begin{minted}{pycon} … \end{minted} block gets reformatted as pycon (interactive console).
  • A \begin{pyblock} … \end{pyblock} (PythonTeX) block gets reformatted as Python.
  • The indentation found on the \begin/\end lines is preserved; the reformatted body is re-indented so that it matches the indentation of the \begin line. For minted blocks, extra body indentation beyond that is stripped away, which keeps the code's own indentation intact relative to the block.
reStructuredText blocks
  • For .. code-block:: python directives, the indented body is reformatted as Python. Option lines of the directive (e.g. :lineno-start: 10, :emphasize-lines: 11) that sit between the directive and the code must be preserved unchanged.
  • .. code-block:: pycon directives: these are reformatted as pycon.
  • For .. jupyter-execute:: directives, the indented body is reformatted as Python; the directive's options (e.g. :hide-code:) are preserved.
  • The Sphinx doctest directives — .. testsetup::, .. testcleanup::, .. testcode::, and .. doctest:: — get their indented bodies reformatted as Python (doctest bodies follow the pycon rules). Blank lines may be inserted by the reformatting where Black separates statements (e.g. an import followed by an assignment becomes separated by a blank line). The directive body's indentation is preserved.
  • Directives that are nested or indented work as well: when a directive sits indented inside another block, its body is reformatted and the correct indentation is preserved.
  • When a .. code-block:: python occurs only as text inside a non-Python code block (e.g. inside a .. code-block:: diff), it must NOT be reformatted — the outer block is left unchanged.
  • If rst_literal_blocks=True is in effect:
    • When a paragraph ending in :: is followed by a blank line and an indented block, the literal block it introduces is reformatted as Python.
    • A :: paragraph with no following indented literal content (e.g. another directive at lesser indentation coming immediately next) is left unchanged and produces no errors.
    • Nested constructs that are not actually literal Python blocks (e.g. a .. warning:: admonition) remain unchanged and produce no errors.
Python docstrings

Python source files go through the processing too: .. code-block:: python blocks of the reStructuredType kind and Markdown ```python blocks located within docstrings are reformatted in place, with the docstring's indentation preserved.

Handling of pycon (interactive console)

These rules cover pycon blocks (Markdown ```pycon, RST .. code-block:: pycon, doctest bodies, LaTeX minted/pycon):

  • Lines that begin with the >>> prompt (and ... continuation) carry Python statements; Black reformats them, and the reformatted code is emitted again with >>> / ... prompts.
  • When ... continuations are in play, a multi-line statement is reformatted as a unit and then re-wrapped with ... continuation prompts. Continuation lines are something Black may add or restructure (e.g. splitting a dict literal across multiple ... lines, adding a closing ... } line).
  • Should the final code in the block be a compound statement (e.g. if True: / def f(): pass), a trailing ... line is emitted after it when one is not already present.
  • Black expands nested one-line definitions such as def f(): pass onto multiple prompted lines.
  • Within a statement, empty continuation lines (a bare ... with no code) are handled: when the statement gets reformatted, they are collapsed appropriately.
  • Output lines — the non-prompt lines that follow a statement, e.g. output, tracebacks — are treated as console output and preserved verbatim, their indentation included. A Traceback (most recent call last): block is preserved unchanged, elided ... frames and file-location lines included.
  • Around the block, trailing whitespace and blank lines are preserved.
  • If the body of a block has no >>> prompt at all (nothing but plain indented text like pass), that block is left unchanged.
  • When a statement is not terminated by a newline (block ends immediately after >>> pass), it is reformatted and emitted with a trailing newline.
  • When a comment line precedes a >>> prompt, the comment line is preserved as-is.
  • In a Markdown pycon block, the body may be over-indented (e.g. four leading spaces before >>> ); after reformatting, the prompts are emitted flush to the fence indentation (leading over-indentation removed).

Details of main behavior

  • No changes needed: when a file is already formatted correctly, main leaves the file unchanged, writes nothing to stderr, and returns 0.
  • Changes made: once a file has been reformatted, "<path>: Rewriting...\n" is printed by main to stdout, the reformatted content is written to the file, and a truthy value is returned.
  • Line length: under --line-length=80, a long function call may be left unchanged (return 0); under --line-length=50, the same call gets wrapped across multiple lines and the file is rewritten (return truthy).
  • Target version: with --target-version=py36, reformatting a construct that is sensitive to trailing commas may add a magic trailing comma and rewrite the file; multiple --target-version flags accumulate.
  • String normalization: when --skip-string-normalization is given, strings quoted with single quotes (e.g. f('hi')) are left unchanged.
  • Syntax error (default): if a Python code block cannot be parsed, main returns truthy, leaves the file unchanged, and prints a message to stdout that starts with "<path>:<lineno>: code block parse error" (the line number is the line on which the code block opens).
  • Syntax error with --skip-errors: blocks that cannot be parsed get skipped (left unchanged), but the other, valid blocks in the same file are still reformatted; what gets written is the file with those valid blocks fixed.

Dependencies

For the actual code formatting, the black library must be used, and the passed black.Mode must be respected (line length, target versions, and string-normalization settings).

  • The module blacken_docs.__main__ (one that can be imported).

The function goes through the input text looking for fenced Markdown code blocks and runs Black on the Python code inside them; the text around those blocks, as well as the fence lines themselves, remains unchanged.

Finding Markdown code blocks

A fenced code block starts with an opening line composed of:

  • Leading indentation/whitespace before the opening triple-backtick fence is not required, yet arbitrary whitespace between the opening triple-backtick fence and the language name must be tolerated.

The language names listed next must be recognized as Python code blocks:

  • The long form, python.
  • The abbreviated form, py.

Once a block of this kind is found, the lines of code lying between the opening fence line and the closing fence line are gathered, formatted by Black, and emitted again right where they were. Both the opening fence line (its original whitespace and language token included, exactly as written) and the closing fence line are carried over verbatim.

The reformatting step

Formatting of the extracted code is done by Black. To illustrate, a call like f(1,2,3) turns into f(1, 2, 3), and the result carries the trailing newline that Black produces. Within the fence, this reformatted code takes the place of the original code lines.

  • In the output, any whitespace sitting between the opening triple-backtick fence and the language name is reproduced exactly (e.g., an opening line such as ``` python or ``` py is emitted unchanged).
