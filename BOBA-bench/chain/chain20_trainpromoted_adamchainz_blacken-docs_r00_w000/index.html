Overview

Create a Python module named blacken_docs that reformats Python code embedded in Markdown and reStructuredText (reST) documents using the black code formatter. The module must expose both a programmatic API and a command-line entry point.

Public API

blacken_docs._black_version()

Provide a zero-argument function that returns the installed black package version as a distutils.version.LooseVersion instance. In particular, its result must be comparable with LooseVersion('19.3b0').

blacken_docs.format_str(src, **opts) -> tuple

Reformat every recognized Python code block in the document string src.

  • src is the complete document text.
  • **opts contains Black formatting options and must be forwarded to Black's string-formatting function for each code block. The function must support the arguments appropriate to the installed Black version:
    • for Black versions older than 19.3b0, callers may provide line_length=<int> and mode=<black mode>;
    • for Black 19.3b0 and newer, callers may provide mode=<black FileMode>.
  • The return value must be a tuple containing exactly two elements, so that it can be unpacked into exactly two targets (for example, after, _ = format_str(src, **opts)). Its first element is the resulting document string; the second element's content is unspecified.

Behavior:

  • An empty input string produces an empty result string unchanged.
  • Only Python within recognized code blocks is reformatted. Surrounding document text, code-block markers and directives, marker indentation, and non-code content must otherwise be preserved exactly.

Recognized code blocks

Markdown fenced blocks

A fenced Python block begins with a line whose content is ```python (with optional indentation) and ends with a line whose content is ``` at the matching indentation. The content between those fences is Python.

  • Remove the fence's common indentation from the code before passing it to Black, then reapply that indentation to the formatted result.
  • Indented fenced blocks, such as blocks nested beneath Markdown list items, must therefore be formatted while retaining their nesting indentation.
  • Preserve trailing whitespace following the closing ``` marker on its line exactly as written.

For example, formatting f(1,2,3) within either an unindented or indented Python fence must produce f(1, 2, 3) while leaving the fences and their indentation intact.

reStructuredText code blocks

Recognize a .. code-block:: python directive with optional indentation. The directive can be followed by indented option lines, such as :lineno-start: 10 and :emphasize-lines: 11, and then a blank separator line. The subsequently indented body is Python code.

  • Remove the code body's block indentation before formatting and reapply it afterward.
  • Preserve the directive, all option lines, blank separator lines, and surrounding document text exactly.
  • Handle nested or indented directives, including a Python code-block directive nested under another reST directive, while preserving every indentation level.

Command-line interface

blacken_docs.main(argv) -> int

argv is a sequence of command-line arguments excluding the program name. The function returns an integer status: 0 when no file changes are needed, and nonzero when at least one file is rewritten or a non-ignored parse error occurs.

Accept one or more positional file paths. Read each file, reformat all recognized Python code blocks, and rewrite the file in place only when its resulting content differs.

Supported options:

  • --line-length <int>: set Black's maximum line length.
  • --py36: target Python 3.6-or-newer syntax formatting, including use of trailing commas in argument lists involving *args.
  • --skip-string-normalization: disable Black's string-quote normalization so, for example, single-quoted strings remain single-quoted.
  • --skip-errors: leave code blocks that Black cannot parse unchanged and continue processing other blocks.
CLI behavior
  • No changes needed: Leave the file untouched, write nothing to stderr, and return 0 if all inputs are already formatted and no non-ignored parse error occurs.
  • File modified: Overwrite a changed file, print exactly "{filepath}: Rewriting...\n" to stdout for that file, and return nonzero.
  • Line length: A block whose Black output fits within the selected line length remains unchanged. A shorter line length that requires wrapping must produce Black's wrapped form. For example, Black may explode a long function call over multiple lines and add its usual trailing comma; this causes a rewrite and a nonzero status.
  • Python 3.6 target: Without --py36, a multiline function definition containing a *args parameter can remain unchanged. With --py36, Black may add a trailing comma after that parameter, causing a rewrite and a nonzero status.
  • Skipped string normalization: With --skip-string-normalization, a single-quoted literal must not be converted to double quotes. If that is the only formatting Black would otherwise perform, the file remains unchanged and the status is 0.
  • Parse error by default: If Black cannot parse a code block, do not modify that file. Print a message to stdout beginning with "{filepath}:{lineno}: code block parse error" and return nonzero. lineno is the 1-based document line number on which the code block itself begins: the opening ```python fence for Markdown or the .. code-block:: python directive for reST. Thus, a fenced block whose opening fence is on line 1 reports line 1, even when its invalid Python starts on line 2.
  • Ignored parse error: With --skip-errors, preserve an unparseable block unchanged and continue formatting valid blocks in the same file. If any valid block changes, rewrite the file with those changes and return nonzero. An ignored error does not itself make the command fail.

Formatting fidelity

The formatting of each extracted code body must match Black's output using the supplied options. For example, f(1,2,3) becomes f(1, 2, 3), and f( ) becomes f().

Dependency

Use the installed black package for both version detection and code formatting.

  • Return a truthy, nonzero status.

hello

Supplying multiple target versions, such as repeated --target-version py27 and --target-version py36 options, must be accepted and applied as combined constraints. If the code is already formatted under those combined constraints, no modification occurs.

Overview

Public API

The existing function and its signature must be retained:

blacken_docs.format_str(src: str, black_mode) -> tuple[str, ...]
  • src is the complete source text of a document.
  • black_mode is a black.Mode-style configuration object and must be passed through when formatting Python source.
  • The first element of the returned tuple is the reformatted document text. The return shape and all other established behavior of this API must remain compatible.

Recognized construct

The new behavior applies to an RST directive of this form:

.. code-block:: pycon

The directive is followed by a blank line and an indented interactive-console block. The directive itself may be indented, such as when nested in another RST directive; in that case, the console content is indented relative to the directive.

Within the console block:

  • A primary prompt line begins, after the block indentation, with >>> and starts a Python statement.
  • A continuation line begins, after the block indentation, with ... and continues that statement.
  • A bare ... line is also a continuation form. Depending on its position, it can be an empty continuation within the source or the interactive-console marker that terminates a compound statement.
  • Any other non-blank line in the indented region is program output, not Python source.

A console block ends when the indented block ends, including at end of input. Blank lines that separate the block from following dedented content are surrounding whitespace and must not be consumed or normalized.

Required behavior

Statement extraction and formatting
  1. Treat each >>> line together with its following ... continuation lines as one Python statement. A block may contain multiple statements and output lines.
  2. Remove prompt prefixes to obtain the Python source, format that source with Black using the exact supplied black_mode, and reconstruct the console representation from the formatted source.
  3. Formatting must provide Black's normal results, including:
    • adding spaces after commas, such as f(1,2,3) becoming f(1, 2, 3);
    • canonicalizing indentation and punctuation in multiline literals;
    • reflowing collection literals and other statements over multiple physical lines when required by the mode;
    • adding continuation prompt lines when a compact input becomes multiline;
    • placing a reformatted closing bracket on its own continuation line when Black does so; and
    • expanding compact compound source such as def f(): pass into a properly indented suite.
Prompt reconstruction
  1. Prefix the first non-blank line of a formatted statement with >>> .
  2. Prefix every subsequent non-blank source line from that statement with ... .
  3. Place every prompt after exactly the same block indentation used by the input console block. This includes any extra indentation caused by nesting the directive.
  4. Omit every blank physical line that Black produces within the formatted statement.   2. Empty literal block. When a line ends with :: but no indented literal body follows it (the next non-blank content is at the same or lower indentation, e.g. a directive):

    Example::

.. warning::

    There was no example.

    The source must be returned unchanged, with an empty list of errors.

In both edge cases the reformatting must correctly recognize that there is no Python literal block body to format, and leave the input untouched.

Existing string-normalization, line-length, target-version, error-reporting, and skip-errors behavior of the module and its main entry point remain unchanged.

Task Specification: blacken-docs Code Block Formatter

Overview

Implement a Python package named blacken_docs that reformats Python code embedded inside documentation files (Markdown, reStructuredText, and LaTeX) by running the Black code formatter on the extracted code blocks while leaving surrounding prose untouched.

Package Structure & Public API

The package must be importable as blacken_docs and must also expose a blacken_docs.__main__ submodule (importing it must succeed).

    ...

  • Reads each named file, reformats it in place, and writes the result back only when changes are made.

Behavior of format_str

The empty string returns the empty string unchanged.

Markdown fenced code blocks

Recognize fenced blocks opened by a line consisting of three backticks followed by a language tag:

  • The language tag python marks a Python block; its body is reformatted with Black.
  • The language tag pycon marks an interactive-console block (see pycon rules below).
  • Content between the opening fence and the closing `` fence is the block body.

Rules that must hold:

  • Whitespace between the backticks and the language tag (e.g. ``` python) is permitted and preserved in the output opening fence.
  • Trailing whitespace after the closing fence (e.g. ``` ) is preserved.
  • Fence options: any additional text after the language tag on the opening fence line must be allowed and preserved verbatim. For example, an opening line of ```python title='example.py' is a valid Python block; the block body is reformatted and the opening line (including title='example.py') is emitted unchanged. The same applies to ```pycon title='Session 1'.
  • Indented fenced blocks are supported: when the opening fence is indented (e.g. by two spaces inside a list item), that indentation is applied to the reformatted body and preserved on the fence lines.
LaTeX blocks
  • \begin{minted}{python} … \end{minted} blocks are reformatted as Python.
  • \begin{minted}{pycon} … \end{minted} blocks are reformatted as pycon (interactive console).
  • \begin{pyblock} … \end{pyblock} (PythonTeX) blocks are reformatted as Python.
  • Indentation of the \begin/\end lines is preserved; the reformatted body is re-indented to match the \begin line's indentation. For minted blocks, extra body indentation beyond that is stripped so the code's own indentation is preserved relative to the block.
reStructuredText blocks
  • .. code-block:: python directives: the indented body is reformatted as Python. Directive option lines (e.g. :lineno-start: 10, :emphasize-lines: 11) appearing between the directive and the code must be preserved unchanged.
  • .. code-block:: pycon directives: reformatted as pycon.
  • .. jupyter-execute:: directives: the indented body is reformatted as Python. Directive options (e.g. :hide-code:) are preserved.
  • Sphinx doctest directives — .. testsetup::, .. testcleanup::, .. testcode::, and .. doctest:: — have their indented bodies reformatted as Python (doctest bodies follow pycon rules). The reformatting may insert blank lines where Black separates statements (e.g. an import followed by an assignment becomes separated by a blank line). Indentation of the directive body is preserved.
  • Nested/indented directives are supported: a directive indented within another block has its body reformatted with the correct indentation preserved.
  • A .. code-block:: python that appears only as text inside a non-Python code block (e.g. inside a .. code-block:: diff) must NOT be reformatted — the outer block is left unchanged.
  • With rst_literal_blocks=True:
    • A literal block introduced by a paragraph ending in :: followed by a blank line and an indented block is reformatted as Python.
    • A :: paragraph with no following indented literal content (e.g. immediately followed by another directive at lesser indentation) is left unchanged and produces no errors.
    • Nested constructs that are not actually literal Python blocks (e.g. a .. warning:: admonition) are left unchanged and produce no errors.
Python docstrings

Python source files are also processed: reStructuredType .. code-block:: python blocks and Markdown ```python blocks embedded within docstrings are reformatted in place, preserving the docstring's indentation.

pycon (interactive console) handling

For pycon blocks (Markdown ```pycon, RST .. code-block:: pycon, doctest bodies, LaTeX minted/pycon):

  • Lines beginning with the >>> prompt (and ... continuation) contain Python statements that are reformatted with Black; the reformatted code is re-emitted with >>> / ... prompts.
  • Multi-line statements using ... continuations are reformatted as a unit and re-wrapped with ... continuation prompts. Black may add or restructure continuation lines (e.g. splitting a dict literal across multiple ... lines, adding a closing ... } line).
  • When a compound statement (e.g. if True: / def f(): pass) forms the final code in the block, a trailing ... line is emitted after it if not already present.
  • Nested one-line definitions such as def f(): pass are expanded by Black onto multiple prompted lines.
  • Empty continuation lines (a bare ... with no code) within a statement are handled: they are collapsed appropriately when the statement is reformatted.
  • Output lines (non-prompt lines following a statement, e.g. output, tracebacks) are treated as console output and preserved verbatim, including their indentation. A Traceback (most recent call last): block, including elided ... frames and file-location lines, is preserved unchanged.
  • Trailing whitespace / blank lines surrounding the block are preserved.
  • A block whose body has no >>> prompt at all (just plain indented text like pass) is left unchanged.
  • A statement not terminated by a newline (block ends immediately after >>> pass) is reformatted and emitted with a trailing newline.
  • A comment line preceding a >>> prompt is preserved as-is.
  • In Markdown pycon blocks, the block body may be over-indented (e.g. four leading spaces before >>> ); the reformatted prompts are emitted flush to the fence indentation (leading over-indentation removed).

main behavior details

  • No changes needed: for a file already correctly formatted, main writes nothing to stderr, leaves the file unchanged, and returns 0.
  • Changes made: when a file is reformatted, main prints "<path>: Rewriting...\n" to stdout, writes the reformatted content to the file, and returns a truthy value.
  • Line length: with --line-length=80 a call may leave a long function call unchanged (return 0); with --line-length=50 the same call is wrapped across multiple lines and the file is rewritten (return truthy).
  • Target version: reformatting a trailing-comma-sensitive construct with --target-version=py36 may add a magic trailing comma and rewrite the file; multiple --target-version flags accumulate.
  • String normalization: with --skip-string-normalization, single-quoted strings (e.g. f('hi')) are left unchanged.
  • Syntax error (default): when a Python code block cannot be parsed, main returns truthy, leaves the file unchanged, and prints a message to stdout starting with "<path>:<lineno>: code block parse error" (the line number is the line of the code block's opening).
  • Syntax error with --skip-errors: unparseable blocks are skipped (left unchanged) while other, valid blocks in the same file are still reformatted; the file is written with the valid blocks fixed.

Dependencies

The implementation must use the black library for the actual code formatting, respecting the passed black.Mode (line length, target versions, and string-normalization settings).

Module and Public API

Implement (or modify) the module blacken_docs so that it exposes the following function:

def format_str(src: str, black_mode) -> tuple[str, ...]
  • src: the full source text to process (a string).
  • black_mode: a Black formatting mode/configuration object, passed through to Black when reformatting code.
  • Returns a tuple whose first element is the reformatted source text (a string). Only the first element is relied upon by callers.
Required Behavior

The function scans the input text for fenced Markdown code blocks and reformats the Python code inside them using Black, leaving the surrounding text and the fence lines themselves unchanged.

Markdown code block detection

A fenced code block begins with a line consisting of:

  • Optional leading indentation/whitespace before the opening triple-backtick fence is not required, but arbitrary whitespace between the opening triple-backtick fence and the language name must be tolerated.
  • Triple backticks (```), optionally followed by whitespace, followed by a Python language name, optionally followed by additional attributes/options after the language name.

The following language names must be recognized as Python code blocks:

  • The full name python.
  • The short name py.

When such a block is detected, the code lines between the opening fence line and the closing fence line are collected, reformatted with Black, and re-emitted in place. The opening fence line (including its original whitespace and language token exactly as written) and the closing fence line are preserved verbatim.

Reformatting

The extracted code is formatted with Black. For example, a call such as f(1,2,3) becomes f(1, 2, 3), with a trailing newline as produced by Black. The reformatted code replaces the original code lines within the fence.

Preservation details
  • Whitespace appearing between the opening triple-backtick fence and the language name is preserved exactly in the output (e.g., an opening line of ``` python or ``` py is emitted unchanged).
  • Any options/attributes following the language name on the opening fence line are preserved.
  • The closing fence line is preserved.
