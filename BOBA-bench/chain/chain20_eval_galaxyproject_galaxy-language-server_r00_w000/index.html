Task Specification: Parser for the XSD Schemas of Galaxy Tools

Goal

What this task calls for is a parser for XSD (XML Schema Definition): the parser is given an lxml XML schema element and, from it, produces a navigable tree of elements together with their attributes. The parser must resolve type references correctly, expand reusable element groups and attribute groups, and handle recursive type definitions safely.

Public Interface

Module: server/services/xsd/parser.py

Supply a class named GalaxyToolXsdParser:

class GalaxyToolXsdParser:
    def __init__(self, root):
        ...
    def get_tree(self):
        ...
  • __init__(self, root) accepts an lxml element — the root <xs:schema> element, the object that lxml.etree.fromstring produces.
  • get_tree(self) returns a tree object (details below). Calling it repeatedly is allowed.
Module: server/services/xsd/constants.py

One constant is to be supplied at module level:

  • MSG_NO_DOCUMENTATION_AVAILABLE — a string that serves as the documentation value when no documentation exists.

The Tree Object

What get_tree() returns is an object exposing:

  • .root — the tree's root node.
  • .find_node_by_name(name) — the entire tree is searched, and the node whose name equals the given string is returned; if no node has that name, the return value is None.

The Node Object

Every node in the tree exposes the following:

  • .name — the name of the element (string).
  • .children — the child nodes as an ordered list, arranged in document order.
  • .descendants — a collection of all nodes below this node, across all levels. len(...) applied to it gives the total count of descendant nodes.
  • .ancestors — a collection of all the nodes above this node, up to the root. For the root node, len(...) over its ancestors gives 0.
  • .attributes — a mapping (dict-like) taking an attribute name (string) to an attribute object. Membership tests and lookups by attribute name are supported (e.g. node.attributes["id"]), and len(...) gives the number of attributes.
  • .get_doc(language=None) — returns a documentation object (details below).

The Documentation Object

Calling get_doc(...) returns an object that exposes:

  • .value — the text of the documentation (string).

How get_doc behaves:

  • A call made without an argument returns the element's default-language documentation.
  • A call made with a language code string (e.g. "es") returns the documentation that matches that language; the xml:lang attribute on the schema's <xs:documentation> entries is what selects the correct one.
  • A call made with a language code for which no documentation exists (e.g. "de") returns a documentation object; on it, .value equals MSG_NO_DOCUMENTATION_AVAILABLE.

Parsing Behavior Requirements

The parser walks through a standard XSD document and, starting from the top-level <xs:element>, builds the tree. The schema constructs listed below must be handled:

Resolving types
  • An <xs:element> may carry a type="..." declaration. If the referenced type is a named <xs:complexType> defined in the schema, that complex type supplies the element's children and attributes.
  • With a named <xs:simpleType> as the referenced type, the element ends up with no child elements from it.
  • Alternatively, an element may hold an inline (anonymous) <xs:complexType> of its own, and that complex type is then expanded in place.
  • No children result from built-in XSD types (e.g. xs:integer, xs:string, xs:date).
Structure of elements
  • Elements declared inside a <xs:sequence> become the containing element's children in an ordered list that follows document order.
Groups (<xs:group>)
  • A named top-level <xs:group name="..."> brings together a set of elements that can be reused.
  • A <xs:group ref="..."> reference (it may appear inside a sequence, possibly carrying minOccurs/maxOccurs attributes) must be expanded; through the expansion, all elements defined in the referenced group become children of the element that contains the group reference, in document order following any preceding siblings.
Attribute declarations
  • <xs:attribute name="..."> declarations sitting on a complex type turn into entries in the .attributes map of the containing element, with the attribute name serving as the key.
Attribute groups (<xs:attributeGroup>)
  • A named top-level <xs:attributeGroup name="..."> brings together a set of attributes meant for reuse.
  • When a complex type carries an <xs:attributeGroup ref="..."> reference, that reference must be expanded; all attributes defined in the referenced attribute group are thereby added to the .attributes map of the containing element.
Safety under recursion
  • A complex type may reference itself (directly or indirectly); when it does, the schema it belongs to has unbounded recursion. On such schemas the parser must terminate, and the tree it produces must still have a root with at least one descendant. Recursion must not go on infinitely inside the parser.

This task introduces no new public API names; the change is purely about how named complex types that use xs:simpleContent are resolved when an element references them via its type attribute.

Notes

Background

You are working on a parser for XSD (XML Schema Definition): it reads a schema document and builds a tree that represents the element structure the document defines. Your task is to extend the parser so that complex types using xs:complexContent with an xs:extension are resolved correctly.

The public API

The parser is driven through an object that provides:

  • A get_tree() method, which returns a tree object.
  • The tree object exposes a root attribute (the root node) plus a render() method that returns the tree as a printable string.

Each node of the tree provides:

  • name — the name of the element (a string).
  • children — an ordered list of child nodes.
  • ancestors — a list of the node's ancestors (empty for the root).
  • descendants — a list of all the nodes below this node (all children, recursively).
  • attributes — a dict-like mapping keyed by attribute name; each entry is truthy whenever the attribute exists.

These APIs must already be in place for the prior functionality; this task only requires that their behavior be extended so it covers xs:complexContent.

Behavior required from the parser

In addition to whatever it currently supports, the parser must already resolve:

  • Named complex types that an element references via its type attribute.
  • Anonymous complex types written inline, nested directly inside an element.
  • An xs:sequence that contains child xs:element definitions.
  • xs:group ref="..." references, whose referenced group's elements are inlined at the position where the reference appears.
  • Declarations of xs:attribute and of xs:attributeGroup ref="...", which contribute to a node's attributes.

New requirement: xs:complexContent used with xs:extension

When a complex type is defined like this:

<xs:complexType name="...">
  <xs:complexContent>
    <xs:extension base="SomeBaseComplexType">
      <xs:sequence>
        <xs:element .../>
      </xs:sequence>
      <xs:attribute .../>
    </xs:extension>
  </xs:complexContent>
</xs:complexType>

the type that results must be the base type combined with the extension:

  1. Inherited children: All of the child elements that the referenced base complex type defines come first, in their original order. Summary

The codebase offers XML context parsing and completion services backed by an XSD, for XML documents that are well-formed as well as incomplete. Modify the services under server/services/ such that an XML context exposes the range of the token tied to a cursor position, handles tag and content boundaries correctly, and keeps the existing context API. Auto-close-tag support must be removed from the completion service.

The parser must stay tolerant of partial documents, such as opening tags left unfinished and quoted attribute values left unterminated. No particular parsing strategy is required; what is required are the externally observable results described below.

Module: server/services/context.py

Publicly importable names

It must be possible to import the following names directly from server.services.context:

  • XmlContextParser
  • XmlContextService
  • XmlContext
  • ContextTokenType
  • Position
  • Range
  • XsdTree
  • XsdNode

Position(line=<int>, character=<int>) stands for a zero-based line and character offset. Range(start=<Position>, end=<Position>) has an end position that is exclusive. Two ranges whose start and end positions are equal must compare equal with ==.

Document is the pre-existing document abstraction whose source text is parsed by this service.

ContextTokenType

The enumeration must keep these public members:

  • UNKNOWN
  • TAG
  • ATTRIBUTE_KEY
  • ATTRIBUTE_VALUE

A context for an attribute name must compare equal to ContextTokenType.ATTRIBUTE_KEY. A compatibility alias called ATTRIBUTE may additionally be provided, but it must not replace ATTRIBUTE_KEY or compare differently from it.

XmlContext
Construction and exposed state

XmlContext must stay directly constructible with these compatible parameters and defaults:

XmlContext(
    document_line="",
    position=Position(),
    is_empty=False,
    token_name=None,
    token_type=ContextTokenType.UNKNOWN,
)

Specifically, the constructor must accept document_line, position, is_empty, and token_type as keywords. The object that results exposes:

  • document_line: the line text that was supplied.
  • target_position: the position that was supplied.
  • is_empty: the flag that was supplied; for direct construction it defaults to False.
  • token_name: the text of the associated token, or None.
  • token_type: a ContextTokenType; it defaults to UNKNOWN.
  • token_range: a Range for the associated token, or None; it defaults to None when no range has been determined.
  • node_stack: an ordered list of XML element names, outermost first; it defaults to an empty list.
  • node: the associated XsdNode, or None prior to XSD resolution.
  • is_node_content: a boolean whose default is False.

This API has no invalid-context state. Parsing and completion must not produce, expose, or depend on an is_invalid flag.

Callable predicates for token types

The context must keep these callable methods; they are methods, not boolean properties:

  • is_tag() returns True exactly when token_type == ContextTokenType.TAG.
  • is_attribute_key() returns True exactly when token_type == ContextTokenType.ATTRIBUTE_KEY.
  • is_attribute_value() returns True exactly when token_type == ContextTokenType.ATTRIBUTE_VALUE.

All three return False for UNKNOWN. For each recognized type, only the corresponding predicate returns True. Their results must reflect the value that token_type currently has, including when that attribute is changed after construction.

XmlContextParser

XmlContextParser.parse(document, position) -> XmlContext evaluates the XML source at the zero-based cursor position that is supplied. It must support XML that is complete as well as XML that is partial.

Empty input handling

Source that is empty, source that consists only of whitespace, and the lone partial input < are treated as empty XML contexts. For these inputs, parse returns a context with is_empty == True, and it must do so safely even when the supplied cursor character is beyond the source text that is available. Examples include "" at characters 0 or 10, spaces, newline-only input, and <.

Associating tokens with cursor boundaries

The token associated with the cursor is described by token_name and token_type:

  • An opening element name has the type TAG.
  • An attribute name has the type ATTRIBUTE_KEY.
  • An attribute value has the type ATTRIBUTE_VALUE and returns its complete unquoted value, embedded spaces included.
  • A position with no associated token is of type UNKNOWN and has token_name == None.

Cursor positions are insertion offsets, and the association of tokens follows these compatibility boundary rules:

  1. An element-name token does not include the opening <. At that offset the token is None/UNKNOWN.
  2. An element name stays associated through the offset immediately after its last character. Thus, a cursor sitting on the immediately following space, /, or > boundary can still select the element name.
  3. An attribute name stays associated through the = boundary that follows.
  4. A quoted attribute value is associated from its first value character through the closing quote boundary. The opening quote is associated with neither the key nor the value.
  5. Other delimiter positions, such as a standalone quote, >, or /, that are not covered by the preceding boundary rules have no token.

As an example, take <tool id="test">:

Character Resulting token_name
0 (<) None
1 through 5 "tool"
6 through 8 "id"
9 (opening quote) None
10 through 14 "test"
15 (>) None

The recognized token types corresponding to these are TAG, ATTRIBUTE_KEY, and ATTRIBUTE_VALUE respectively. Self-closing markup follows the same rules: in <description/>, positions on description and on the immediately following / boundary select description, while the following > does not.

Further required cases include:

  • With <first id="1" test="value">\n <second:
    • line 0, character 0 is None/UNKNOWN;
    • line 0, character 3 is "first"/TAG;
    • line 0, character 8 is "id"/ATTRIBUTE_KEY;
    • line 0, character 19 — the opening quote before value — is None/UNKNOWN;
    • line 0, character 20 is "value"/ATTRIBUTE_VALUE, and that value remains associated through the closing-quote boundary at character 25.
  • With <first id="one test, at line 0, character 19, the result is "one test"/ATTRIBUTE_VALUE, even though the quote and element are unfinished.
  • With <first id="value"><second/></first>:
    • character 19 selects "second" as TAG;
    • character 29 selects "first" as TAG in the completed closing tag.
  • With <first id="value"><second/></first at character 29, the closing tag, being unfinished, is not recognized as a tag token, and the type is UNKNOWN.
token_range

Whenever a token is associated with the cursor, token_range reports the span of that token in the source:

  • For an opening element name, the span covers exactly the name; <, whitespace, /, and > are excluded.
  • For an attribute key, the span covers exactly the key; surrounding whitespace and = are excluded.
  • For an attribute value, the span covers exactly the unquoted value text; internal spaces are included, quotes are not.
  • For a recognized completed closing tag, the span covers the complete closing markup, from < through >. Even though token_name is only the element name, this preserves the closing-tag range convention.
  • If there is no token span that applies, token_range is None.

Even when token association occurs at one of the inclusive cursor boundaries described above, the range itself remains the exact token span.

The following examples are required:

  • For <first><second><third>:
    • character 1 gives Range(Position(0, 1), Position(0, 6)) for first;
    • character 8 gives Range(Position(0, 8), Position(0, 14)) for second.
  • For <first><second/><third>:
    • character 8 gives Range(Position(0, 8), Position(0, 14)) for second;
    • character 17 gives Range(Position(0, 17), Position(0, 22)) for third.
  • <first><second></second><third> at character 25 gives Range(Position(0, 25third at line 1, character 15 gives Range(Position(1, 14), Position(1, 19)) for value.
  • For <first><second/><third, character 10 still gives Range(Position(0, 8), Position(0, 14)) for second.
node_stack

node_stack stands for the ordered open-element path that is relevant at the cursor. Where applicable, it includes the element whose opening or closing markup is currently being edited.

  • An element joins the stack after the cursor has passed its opening < and entered its name. At the exact < offset, the new element has not entered the stack.
  • A self-closing element remains in the stack while the cursor is within its markup, its closing boundary included, but after that boundary it ceases to be an enclosing element.
  • An element that is explicitly closed remains represented while the cursor is within its closing markup, but after the close is complete it is absent.
  • Elements that are already self-closed or explicitly closed before the cursor do not remain in the open path.

The following examples are required:

  • For <first><second><third>, the results are ['first'] at character 1, ['first', 'second'] at character 8, and ['first', 'second', 'third'] at character 16.
  • For <first><second/><third>, the results are ['first', 'second'] at character 8 and ['first', 'third'] at character 17.
  • For <first><second></second><third> at character 25, the result is ['first', 'third'].
  • For <first><second/></first> at character 18, the result is ['first'] while the cursor is in the closing tag.
  • For <first><second/>\n</first> at line 1, character 2, the result is ['first'].
  • For <first><second attr="value"/><third, the results are ['first'] at character 29, the < of the unfinished trailing tag, and ['first', 'third'] at character 30 once its name has been entered.
is_node_content

is_node_content is True when the cursor sits at a character-data/content insertion position inside at least one element that is still open. Text, inter-element whitespace, the insertion point immediately after completed opening markup, and the insertion point immediately before subsequent child or closing markup are all included.

It is False while the cursor is inside opening, closing, or self-closing markup—element names, attribute keys, values, and the ending delimiters included—and whenever no element is open, such as before the root or after it has closed.

Since positions are insertion offsets, a position exactly on a < that starts the next child or closing markup is treated as the insertion point immediately before that markup. It is content when a parent is open. Moving one character into that markup is not content. At the root document's initial <, there is no open parent, and so the position is not node content.

For <first id="1">\n <second attr="value">test</second>\n<third:

  • line 0, characters 1 and 8 are not node content; character 14, immediately after the first opening tag, is node content;
  • line 1, characters 0 through 4 are node content; the insertion boundary at the child's < is included;
  • line 1, characters 5 and 6, inside the child tag, are not node content;
  • line 1, character 24, on the opening tag's >, is not node content, while character 25, at the start of test, is node content;
  • line 1, character 29, at the closing tag's <, is node content, while character 30, inside the closing markup, is not.

This flag is not determined by UNKNOWN alone: an unknown token between tags may be node content, whereas an unknown delimiter position or a position outside all open elements is not.

XmlContextService

XmlContextService(xsd_tree) must keep the supplied XsdTree as its public xsd_tree attribute.

get_xml_context(document, position) -> XmlContext parses the context and resolves its node against that tree. Resolution walks the ordered node_stack path and picks the XSD node represented by the deepest valid element in that complete path. If the stack is empty or the path cannot be resolved—for example because the cursor is at a bare < or has entered an element name that is unknown—the context falls back to xsd_tree.root rather than returning no node. An unfinished element whose entered name is valid within the current XSD path can resolve normally.

The behavior at boundaries must agree with node_stack:

  • At the < that begins a child, the current node is still its parent; once the cursor enters a known child name, that child becomes the node, even when its tag is unfinished.
  • A self-closing child remains the current node through its closing boundary; after that, resolution returns to the parent.
  • Entering an unknown trailing tag falls back to the root, whereas entering a valid sibling resolves that sibling.
  • Empty contexts remain marked is_empty; when a real XSD tree is present, their empty stack resolves to the root fallback.

When XmlContext.update_node_definition(xsd_tree) is called directly, it must provide the same stack-based node resolution and root fallback that the service uses.

Module: server/services/completion.py

Publicly importable names

It must remain possible to import the following names directly from server.services.completion:

  • XmlCompletionService
  • XmlContext
  • XsdTree
  • XsdNode
  • XsdAttribute

AutoCloseTagResult, Position, and Range must no longer be exported by the completion module.

XmlCompletionService

XmlCompletionService(xsd_tree) stores the tree that is supplied in its public xsd_tree attribute.

Completion of nodes

get_node_completion(context) -> CompletionList returns a result that has an items list:

  • For a non-empty context that has an associated XSD node, the items represent that node's allowed child elements. Each item exposes a label equal to the corresponding child name. Thus, for a root that has children, the first label equals the name of its first child.
  • For an empty context, the result contains exactly one item, and that item represents the XSD root; its label equals context.node.name/the root node name.
  • If a non-empty context has no applicable node, the result has no items.
Completion of attributes

get_attribute_completion(context) -> CompletionList likewise returns a result that has an items list:

  • For an empty context, no attribute items are returned.
  • A non-empty context on an XSD node that has attributes returns completion items for those attributes; each exposes its attribute name as label.
  • A node that has no applicable attributes returns no items.

Completion behavior must not branch on an invalid-context flag, because that state is not part of XmlContext.

Removal of auto-close support

Generating auto-close tags is not part of the completion service. XmlCompletionService must not expose a get_auto_close_tag method, and the completion module must not define, import, or re-export an AutoCloseTagResult type. The removed feature must not require imports of Position or Range in this module.

XSD objects that support the services

The completion and context APIs keep working with the existing XSD structures:

  • XsdNode(name, element=..., parent=...) exposes name, its ordered children, and an attributes mapping of names to XsdAttribute objects.
  • XsdAttribute(name, element=...) exposes name.
  • XsdTree(root) exposes its root node and resolves element-name paths that are valid and ordered.

An empty completion context can be created with XmlContext(is_empty=True), and the root can be assigned to it as context.node. A completion context that is non-empty uses is_empty=False together with an associated node.

Required result

The service layer that results must preserve the legacy APIs for context construction and callable predicates, classify attribute names as ATTRIBUTE_KEY, expose accurate token ranges and XML stack/content state at cursor boundaries, resolve contexts to XSD nodes with a root fallback, and provide completion without any invalid-context or auto-close-tag API.

Specification of the Task

Goal

Implement (or fix) the logic that determines the character range covered by a particular word token on a single line of an XML document, for a cursor position that lies inside that token.

Public API

The behavior is exercised via the XML context parser that resides in the server package, inside the context-parsing module (server/.../context.py). For a given document and cursor Position, the relevant callable produces a context result containing a Range that identifies the token at that position.

You must ensure that the token-range computation returns a Range in which the start and end positions correctly delimit the contiguous word token found at the requested cursor Position.

Data Structures
  • Position(line: int, character: int) — a line index and a character index, both zero-based.
  • Range(start: Position, end: Position) — a half-open range in which start.character is the index of the token's first character and end.character is the index one past the token's last character, both on the same line as the cursor.
Behavior Requirements

For a document line and a cursor Position situated within the opening tag of an XML element that contains attributes, the token range that is computed must correctly bound the individual word token under the cursor. Non-word boundaries such as spaces, quotes, =, and angle brackets are what delimit tokens; the range must not accumulate or drift as a result of preceding tokens on the same line.

Concretely, for the line:

<first attr1="value1" attr2="value2">

(with character index 0 being the opening <):

  • A cursor Position(line=0, character=24) lies inside the token attr2 (spanning character indices 22 through 26 inclusive). The range that is returned must be Range(start=Position(line=0, character=22), end=Position(line=0, character=27)).

  • A cursor Position(line=0, character=30) lies inside the token value2 (spanning character indices 29 through 34 inclusive). The range that is returned must be Range(start=Position(line=0, character=29), end=Position(line=0, character=35)).

In both of these cases, start.line and end.line are equal to the cursor's line, start.character is the index of the token's first character, and end.character is the index immediately after the token's last character.

Central Correctness Requirement

Whenever multiple tokens precede the cursor on the same line, the computed range must reflect only the token that is actually under the cursor. The starting offset must be the absolute character index of that token within the line — it must not be inflated by adding up or accumulating the lengths/offsets of earlier tokens on the line.
