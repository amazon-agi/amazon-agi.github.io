Type resolution
  • An <xs:element> may declare type="...". When the referenced type is a named <xs:complexType> defined in the schema, the element's children and attributes are derived from that complex type.
  • When the referenced type is a named <xs:simpleType>, the element has no child elements from it.

  • Elements declared inside <xs:sequence> become ordered children of the containing element, in document order.

Attributes

Attribute groups (<xs:attributeGroup>)
  • A named top-level <xs:attributeGroup name="..."> defines a reusable set of attributes.
  • An <xs:attributeGroup ref="..."> reference on a complex type must be expanded so that all attributes defined in the referenced attribute group are added to the containing element's .attributes map.
Recursion safety

Overview

You are working on an XSD (XML Schema Definition) parser that reads a schema document and produces a tree representation of the element structure it defines. This tree captures the hierarchy of elements, their child elements, and their attributes. Your task is to extend the parser so that it correctly resolves complex types that use xs:complexContent with an xs:extension.

Public API

The parser is exercised through an object that provides:

  • A method get_tree() that returns a tree object.
  • The tree object exposes a root attribute (the root node) and a render() method that returns a printable string representation of the tree.

Each node in the tree provides:

  • name — the element's name (string).
  • children — an ordered list of child nodes.
  • ancestors — a list of ancestor nodes (empty for the root).
  • descendants — a list of all nodes below this node (all children, recursively).
  • attributes — a mapping (dict-like) keyed by attribute name; each entry is truthy when the attribute exists.

These APIs must already exist for prior functionality; this task only requires extending their behavior to cover xs:complexContent.

Required Behavior

The parser must already resolve, in addition to whatever it currently supports:

  • Named complex types referenced by an element's type attribute.
  • Inline (anonymous) complex types nested directly inside an element.
  • xs:sequence containing child xs:element definitions.
  • xs:group ref="..." references, whose referenced group's elements are inlined in place.
  • xs:attribute and xs:attributeGroup ref="..." declarations, contributing to a node's attributes.
  • xs:simpleContent with xs:extension, whose extension attributes are attached to the element.
New requirement: xs:complexContent with xs:extension

When a complex type is defined using:

<xs:complexType name="...">
  <xs:complexContent>
    <xs:extension base="SomeBaseComplexType">
      <xs:sequence>
        <xs:element .../>
      </xs:sequence>
      <xs:attribute .../>
    </xs:extension>
  </xs:complexContent>
</xs:complexType>

the resulting type must be the combination of the base type and the extension:

  1. Inherited children: All child elements defined by the referenced base complex type appear first, in their original order. If the base type itself uses group references or nested structures, those must be fully resolved into concrete child elements as they would be normally.

  2. Inherited attributes: All attributes contributed by the base type (including its own attributes and any attribute-group references) are included.

  3. Extension children: Any child elements declared inside the xs:extension (e.g. within its xs:sequence) appear after the inherited children, in declaration order.

  4. Extension attributes: Any attributes declared inside the xs:extension are included alongside the inherited attributes.

The base attribute may reference another named complex type in the same schema, and that base type may itself contain group references that must be expanded.

  • The root element testElement has type CustomComplexType, a complex type with a sequence of four elements (firstElement, secondElement, thirdElement, element_with_group) plus attributes id, value, and attributes contributed by a referenced attribute group (gattr1, gattr2).

  • element_with_group has a named complex type ComplexWithGroup, defined as a sequence containing a single group reference (TestGroup, which expands to elements group_elem1 and group_elem2) plus an attribute group_id.
  • secondElement has a named complex type TestComplexContent, defined via xs:complexContent extending ComplexWithGroup, adding a child element content and an attribute complex.
  • thirdElement has an inline complex type with a sequence containing a single child element childElement (whose type uses xs:simpleContent extension contributing an attribute simple) plus an attribute testDate.

[testElement] id value gattr1 gattr2

├── [secondElement] group_id complex
│   ├── [group_elem1]
│   ├── [group_elem2]

│   └── [childElement] simple

    ├── [group_elem1]
    └── [group_elem2]

  • root.name is "testElement"; root.ancestors is empty.
  • root.descendants has length 10 (all nodes below the root, counted recursively).

  • <first><second/><third>:
    • character 8 gives Range(Position(0, 8), Position(0, 14)) for second;
    • character 17 gives Range(Position(0, 17), Position(0, 22)) for third.
  • <first><second></second><third> at character 25 gives Range(Position(0, 25third at line 1, character 15 gives Range(Position(1, 14), Position(1, 19)) for value.
  • <first><second/><third at character 10 still gives Range(Position(0, 8), Position(0, 14)) for second.
node_stack

node_stack represents the ordered open-element path relevant at the cursor. It includes the element whose opening or closing markup is currently being edited where applicable.

  • An element enters the stack after the cursor passes its opening < and enters its name. At the exact < offset, the new element has not entered the stack.
  • A self-closing element remains in the stack while the cursor is within its markup, including its closing boundary, but ceases to be an enclosing element after that boundary.
  • An explicitly closed element remains represented while the cursor is within its closing markup, but is absent after the close is complete.
  • Elements already self-closed or explicitly closed before the cursor do not remain in the open path.

Required examples:

  • <first><second><third> gives ['first'] at character 1, ['first', 'second'] at character 8, and ['first', 'second', 'third'] at character 16.
  • <first><second/><third> gives ['first', 'second'] at character 8 and ['first', 'third'] at character 17.
  • <first><second></second><third> at character 25 gives ['first', 'third'].
  • <first><second/></first> at character 18 gives ['first'] while in the closing tag.
  • <first><second/>\n</first> at line 1, character 2 gives ['first'].
  • <first><second attr="value"/><third gives ['first'] at character 29, the < of the unfinished trailing tag, and ['first', 'third'] at character 30 after entering its name.
is_node_content

is_node_content is True when the cursor is at a character-data/content insertion position inside at least one still-open element. This includes text, inter-element whitespace, the insertion point immediately after completed opening markup, and the insertion point immediately before subsequent child or closing markup.

It is False while the cursor is inside opening, closing, or self-closing markup—including element names, attribute keys, values, and the ending delimiters—and whenever no element is open, such as before the root or after it has closed.

Because positions are insertion offsets, the position exactly on a < that starts the next child or closing markup is treated as the insertion point immediately before that markup. It is content when a parent is open. Moving one character into that markup is not content. At the root document's initial <, there is no open parent, so the position is not node content.

For <first id="1">\n <second attr="value">test</second>\n<third:

  • line 0, characters 1 and 8 are not node content; character 14, immediately after the first opening tag, is node content;
  • line 1, characters 0 through 4 are node content, including the insertion boundary at the child's <;
  • line 1, characters 5 and 6 inside the child tag are not node content;
  • line 1, character 24 on the opening tag's > is not node content, while character 25 at the start of test is node content;
  • line 1, character 29 at the closing tag's < is node content, while character 30 inside the closing markup is not.

UNKNOWN alone does not determine this flag: an unknown token between tags may be node content, while an unknown delimiter position or a position outside all open elements is not.

XmlContextService

XmlContextService(xsd_tree) must retain the supplied XsdTree as its public xsd_tree attribute.

get_xml_context(document, position) -> XmlContext parses the context and resolves its node against that tree. Resolution follows the ordered node_stack path and selects the XSD node represented by the deepest valid element in that complete path. If the stack is empty or the path cannot be resolved—for example, because the cursor is at a bare < or has entered an unknown element name—the context falls back to xsd_tree.root rather than returning no node. An unfinished element whose entered name is valid in the current XSD path can resolve normally.

Boundary behavior must agree with node_stack:

  • At the < beginning a child, the current node is still its parent; once the cursor enters a known child name, that child becomes the node, even if its tag is unfinished.
  • A self-closing child remains the current node through its closing boundary, then resolution returns to the parent.
  • Entering an unknown trailing tag falls back to the root, while entering a valid sibling resolves that sibling.
  • Empty contexts remain marked is_empty; with a real XSD tree, their empty stack resolves to the root fallback.

XmlContext.update_node_definition(xsd_tree), when called directly, must provide the same stack-based node resolution and root fallback used by the service.

Node completion

get_node_completion(context) -> CompletionList returns a result with an items list:

  • For a non-empty context with an associated XSD node, the items represent that node's allowed child elements. Each item exposes a label equal to the corresponding child name. Thus, for a root with children, the first label equals the name of its first child.
  • For an empty context, the result contains exactly one item representing the XSD root; its label equals context.node.name/the root node name.
  • If no applicable node exists in a non-empty context, the result has no items.
Attribute completion

get_attribute_completion(context) -> CompletionList also returns a result with an items list:

  • An empty context returns no attribute items.
  • A non-empty context on an XSD node with attributes returns completion items for those attributes; each exposes its attribute name as label.
  • A node with no applicable attributes returns no items.

Completion behavior must not branch on an invalid-context flag, because that state is not part of XmlContext.

Supporting XSD objects

The completion and context APIs continue to work with the existing XSD structures:

  • XsdAttribute(name, element=...) exposes name.
  • XsdTree(root) exposes its root node and resolves valid ordered element-name paths.

Objective

Implement (or correct) the logic that computes the character range covering a specific word token within a single line of an XML document, given a cursor position that falls inside that token.

Public API Surface

The behavior is exercised through the XML context parser located in the server package under the context-parsing module (server/.../context.py). The relevant callable produces, for a given document and cursor Position, a context result that includes a Range identifying the token at that position.

You must ensure that the token-range computation returns a Range whose start and end positions correctly delimit the contiguous word token located at the requested cursor Position.

Data Types
  • Position(line: int, character: int) — zero-based line and character index.
  • Range(start: Position, end: Position) — a half-open range where start.character is the index of the first character of the token and end.character is the index one past the last character of the token, both on the same line as the cursor.
Required Behavior

Given a document line and a cursor Position located within an XML element's opening tag containing attributes, the computed token range must correctly bound the individual word token under the cursor. Tokens are delimited by non-word boundaries such as spaces, quotes, =, and angle brackets; the range must not accumulate or drift due to preceding tokens on the same line.

Concretely, for the line:

<first attr1="value1" attr2="value2">

(where character index 0 is the opening <):

  • A cursor Position(line=0, character=24) falls inside the token attr2 (which spans character indices 22 through 26 inclusive). The returned range must be Range(start=Position(line=0, character=22), end=Position(line=0, character=27)).

  • A cursor Position(line=0, character=30) falls inside the token value2 (which spans character indices 29 through 34 inclusive). The returned range must be Range(start=Position(line=0, character=29), end=Position(line=0, character=35)).

In both cases start.line and end.line equal the cursor's line, start.character is the index of the token's first character, and end.character is the index immediately after the token's last character.

Key Correctness Requirement

When multiple tokens precede the cursor on the same line, the computed range must reflect only the token actually under the cursor. The starting offset must be the absolute character index of that token within the line — it must not be inflated by summing or accumulating the lengths/offsets of earlier tokens on the line.
