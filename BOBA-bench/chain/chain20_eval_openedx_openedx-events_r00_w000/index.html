Task Specification: Tooling for Open edX Events

Overview

Build the core tooling that makes it possible to define and send Open edX events built on top of Django signals. This work involves creating a custom signal class, a metadata data structure, and dedicated exception types.

Modules and Public API to Implement

1. openedx_events/exceptions.py

Create two exception classes:

  • InstantiationError(Exception)
  • SenderValidationError(Exception)

It must be possible to import both via from openedx_events.exceptions import InstantiationError, SenderValidationError.

Below, in the context of where each exception is raised, the message formatting behavior is described. Each exception's string message follows a fixed pattern that starts with the exception class name.

2. openedx_events/data.py

A metadata data structure must be defined in this module (implemented with the attr library, so that attr.asdict(...) works on an instance). The module must reference:

  • A module-level import that binds the name openedx_events (the top-level package), from which a __version__ string attribute is read.
  • A module-level import that binds the name socket, whose gethostname() is used.

The metadata object generated for an event must contain (at minimum) the following fields, having these semantics:

  • event_type: the signal's event type string.
  • minorversion: the integer 0.
  • source: a string of the form "openedx/{service}/web", in which {service} is taken from the Django setting SERVICE_VARIANT (e.g., with SERVICE_VARIANT="lms", source is "openedx/lms/web").
  • sourcehost: the value that socket.gethostname() returns.
  • sourcelib: a list of integers built by splitting the package __version__ string on . and converting each part to an integer (e.g., "0.1.0" → [0, 1, 0]).
3. openedx_events/tooling.py

Define the class OpenEdxPublicSignal, a subclass of Django's django.dispatch.Signal. It must be importable via from openedx_events.tooling import OpenEdxPublicSignal.

The module must import Django's Signal (so that openedx_events.tooling.Signal refers to it) and must be able to produce metadata by way of a method generate_signal_metadata (see below).

Constructor
OpenEdxPublicSignal(event_type, data)
  • event_type: a non-empty string that identifies the event.
  • data: a mapping of the expected send arguments, in which each key is an argument name and each value is the type/class that the argument's value must be an instance of.

Validation at instantiation — raise InstantiationError if a required argument is missing or falsy:

  • If event_type is empty/falsy, raise InstantiationError with message: InstantiationError {event_type}: Missing required argument 'event_type' (where {event_type} is the empty value that was passed in).
  • If data is None/falsy, raise InstantiationError with message: InstantiationError {event_type}: Missing required argument 'data' (where {event_type} is the event type value that was passed in).

When both are missing, the event_type check takes precedence.

String representation

The result of str(signal) must include the event_type string.

generate_signal_metadata(self)

Returns a metadata object (the data structure from openedx_events/data.py) that describes this event, populated as specified in the data.py section. To build it, the method reads SERVICE_VARIANT from Django settings, calls socket.gethostname(), and reads the package __version__.

send_event(self, send_robust=False, **kwargs)

Validates the provided keyword arguments against the data mapping supplied at construction, then sends the event as a Django signal.

Sender argument validation — validate the keyword arguments (leaving out the send_robust control flag) against the construction-time data mapping. Raise SenderValidationError in these cases:

  • A key that the construction data mapping contains is absent from the provided arguments: SenderValidationError {event_type}: Missing required argument '{key}' (using the missing key name).
  • A provided argument's value is not an instance of the class given for that key in data: SenderValidationError {event_type}: The argument '{key}' is not instance of the Class Attribute '{type}' with {type} being the name of the expected type/class.
  • The set of provided argument names does not match the set of expected argument names (a mismatch, e.g., extra arguments supplied): SenderValidationError {event_type}: There's a mismatch between initialization data and send_event arguments

The missing-argument and type-mismatch checks are evaluated for each expected key; the count/mismatch check applies when the provided arguments do not correspond to the expected set.

Behavior of a successful send:

  • Metadata is generated by calling self.generate_signal_metadata().
  • If send_robust is falsy: invoke the underlying Django Signal.send, passing sender=None, the validated keyword arguments through unchanged, plus metadata=<generated metadata>.
  • If send_robust is truthy: invoke the underlying Django Signal.send_robust, passing sender=None, the validated keyword arguments through unchanged, plus metadata=<generated metadata>.

The send_robust flag must not be forwarded among the keyword arguments that are passed through.

Overrides of send and send_robust

Override Django's built-in dispatch methods such that calling them directly warns the user to use the custom method instead.

  • send(self, sender, **kwargs): issue a warning (via the warnings mechanism, so that assertWarns detects a Warning) with the message: Please, use 'send_event' when triggering an Open edX event.

  • send_robust(self, sender, **kwargs): issue a warning with the message: Please, use 'send_event' with send_robust equals to True when triggering an Open edX event.

The only thing these overrides need to do is emit the warning.

Support for Test Settings

The openedx_events package must be a valid Django app (installable via INSTALLED_APPS). A test settings module is provided; it configures openedx_events as the only installed app, two SQLite databases (default and read_replica), and a SECRET_KEY. Ensure that the package layout (including a tests package under openedx_events) supports being loaded as a Django app and that the module imports above resolve correctly.

Notes on Mocking Points (requirements for the import structure)

In order to support the required behavior and the testing:

  • openedx_events.data must reference the top-level package through a name openedx_events and read __version__ from it, and must reference socket.
  • In openedx_events.tooling, Django's Signal must be referenced as openedx_events.tooling.Signal.
  • generate_signal_metadata must be a method on OpenEdxPublicSignal, which send_event calls in order to obtain the metadata payload.

Additional Requirements

  • In a type-mismatch SenderValidationError, the {type} portion must identify the class of the expected class object, not the name of the expected class itself. For example, when the declared expected class is unittest.mock.Mock, the message must end with The argument 'user' is not instance of the Class Attribute 'type', using type rather than Mock.
02 Dispatch of OpenEdxPublicSignal Events 373 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Dispatch of OpenEdxPublicSignal Events

Summary

Build (or modify) the event-dispatching tooling found in the module openedx_events.tooling. The module supplies a class that wraps a Django signal and dispatches it while attaching a computed metadata object to the payload.

Public API

The OpenEdxPublicSignal Class

Its location is openedx_events.tooling.OpenEdxPublicSignal.

The class must expose the methods below, which callers use:

send_event(self, send_robust=False, **kwargs)

Sends the wrapped event in the form of a Django signal.

Behavior:

  • The method computes a metadata object that describes the event (through an internal helper that produces the metadata). This metadata generation is the extension point the class relies on; the metadata that results is an arbitrary object (not required to be a dict).
  • When it dispatches the underlying Django signal, the method must include the computed metadata object in the signal payload under a keyword called metadata, alongside any keyword arguments the caller supplies (**kwargs).
  • The metadata object must be passed through to the signal as-is, without being reassigned, copied, mutated, rebuilt, or transformed in any other way. Whichever object the metadata-generation step returns is exactly the object delivered as the metadata value in the dispatched signal.
  • The send_robust flag determines the dispatch mode:
    • If send_robust is False (the default), dispatch happens through the standard Django signal send mechanism.
    • If send_robust is True, dispatch happens through Django's robust send mechanism.
  • Every keyword argument the caller supplies in **kwargs must be forwarded to the signal dispatch call unchanged.

Core Constraint

The metadata value that reaches receivers must be the exact object returned by the metadata-generation step. Do not wrap it in a dict, do not set attributes on it, and do not swap in a different structure. There must not be any code that treats the metadata as a dictionary or reassigns/augments it — the object is forwarded directly.

Remarks

  • The metadata-generation step is an internal method, and its return value is used verbatim; the dispatch logic must remain agnostic with regard to the concrete type of that return value.
  • Beyond correctly forwarding the computed metadata object and the caller's keyword arguments to the appropriate (robust or non-robust) signal dispatch, no behavior is required.

This class stands for an Open edX public signal (a Django Signal subclass or wrapper) that can dispatch events to the receivers connected to it.

Method: send_event(self, **kwargs)

The event is sent, in the form of a Django signal, to connected receivers.

The following behavior is required:

  • When dispatching to receivers, the method obtains event metadata by calling the instance method generate_signal_metadata() and forwards it together with the keyword arguments supplied by the caller.
  • By default, the event is dispatched through the robust send mechanism (equivalent to Django's Signal.send_robust), which catches exceptions raised by receivers rather than letting them propagate. At dispatch time, it is called with:

05 A Bridge Linking attrs Classes and Avro for the Event Bus 1309 words · source specification, reworded by GLM-5.3-Flash

Task Specification: A Bridge Linking attrs Classes and Avro for the Event Bus

Summary

The task is to implement a bridge that works in both directions between instances of Python classes decorated with attrs and binary data that has been serialized with Avro. Once the bridge exists, attrs objects can be serialized into a compact binary wire format (with Avro as the encoding) and afterwards be deserialized back into attrs objects; included in this is support for schema evolution between different versions of a class.

Modules to Create, with Their Public API

Module: openedx_events.avro_attrs_bridge

A class AvroAttrsBridge is to be defined here, with the public interface shown below:

class AvroAttrsBridge:
    def __init__(self, attrs_cls, extensions=None):
        ...

    def serialize(self, obj) -> bytes:
        ...

    def deserialize(self, data, writer_schema=None):
        ...

    @property
    def schema_dict(self):
        ...
  • attrs_cls: a class carrying attrs decoration. The bridge is bound to this class; from it comes the "reader" schema, and it doubles as the type into which deserialized data is reconstructed.
  • extensions: a mapping that may be omitted. Its keys are Python types (classes), and its values are extension instances saying how non-primitive/custom types are to be converted to and from Avro-compatible representations. When it is omitted, no extensions are assumed.
Module: openedx_events.avro_attrs_bridge_extensions

A class CourseKeyAvroAttrsBridgeExtension is to be defined in this module as well; converting between opaque_keys.edx.keys.CourseKey instances and Avro-compatible values is its job.

  • A class-level attribute cls must be exposed on it, and that attribute's value must be the CourseKey class (i.e. CourseKeyAvroAttrsBridgeExtension.cls is CourseKey). When the extension is registered in an AvroAttrsBridge's extensions mapping, this attribute acts as the key.
  • Instances of the class must be able to take a CourseKey object, convert it into a serializable form, and rebuild out of that form a CourseKey object equal to the original one, with the result that a round trip through serialize/deserialize yields an object equal to the original.

Behavior Requirements

Construction of the Bridge and the Types It Supports

As attrs fields, the following primitive/attribute types must be recognized by the bridge and directly supported by it: str, int, bool, and datetime.datetime.

Support must also be provided for nested attrs classes serving as field types (an attrs class whose fields are themselves attrs classes, nested to an arbitrary depth). Serialization and deserialization of nested attrs objects must happen recursively.

For any field whose declared type is a "custom" type — in other words, a type that is neither a primitive supported type nor an attrs class (with CourseKey as an example) — the bridge requires extensions to contain a corresponding entry, with that type as its key. Worth noting: datetime is a supported type and does not require an extension.

Error condition: If the bridge is constructed for a class that contains a custom (non-primitive, non-attrs) field type and extensions holds no matching extension for it, the construction must raise TypeError. As an example, constructing a bridge for a class that has a CourseKey field, with no CourseKey extension supplied, must raise TypeError.

The schema_dict Property

A schema_dict property must be exposed by the bridge; what it returns is the Avro schema as a Python dictionary, derived by the bridge from the bound attrs class. This schema dictionary can be handed to another bridge's deserialize method as the writer_schema argument (see the schema evolution discussion below).

serialize(obj)

Handed an instance of the bound attrs class, the bridge must produce a serialized byte representation of that object, drawing on the Avro schema it derived. Custom-typed fields undergo conversion through the registered extensions; nested attrs fields are dealt with recursively; datetime values are processed as a supported type.

deserialize(data, writer_schema=None)

The input consists of serialized bytes that serialize produced beforehand; from them, an instance of the bridge's bound attrs class must be reconstructed and returned.

  • With writer_schema equal to None, interpretation of the data relies on the bridge's own schema (the plain round-trip situation, in which one and the same class/schema both serializes and deserializes).
  • If a writer_schema is supplied (a schema dictionary, usually taken from another bridge's schema_dict), that writer schema governs how the data must be read, while construction of the resulting object follows the bound class of the current bridge (the reader schema). Schema evolution is what this makes possible (see below).

What must come back is an instance of the bound attrs class: custom-typed fields return as their Python types through the registered extensions, nested attrs fields get rebuilt recursively, and datetime fields are brought back.

Guarantee for Round Trips

Take a bridge bound to a given attrs class (plus any extensions that are needed). If an instance is serialized and the outcome is then deserialized with that same bridge, the object it yields must be equal to the original instance. The following are cases where it must hold:

  • Classes whose fields are primitives only.
  • Classes that have nested attrs fields.
  • Classes that contain custom types (e.g. CourseKey) alongside datetime fields, provided that the appropriate extension(s) are supplied.
Evolution of Schemas

Serialized data coming from a bridge bound to one version of an attrs class (the "writer") must be deserializable by a bridge bound to a different version of that class (the "reader"); the way to bring this about is passing the writer bridge's schema_dict to the reader bridge's deserialize as its writer_schema argument. An instance of its own (new) bound class is what the reader bridge produces. Support must exist for the following evolution scenarios:

  1. Field added with a default (primitive type): If the reader's class defines an additional field, not present in the writer's schema, that comes with a default value and a primitive type, deserialization is successful, and the new field ends up with its default value. All fields that appear in both versions retain their original serialized values.

  2. Field removed: If a field that the writer's schema contains is omitted by the reader's class, deserialization succeeds, and the reconstructed object simply lacks the removed field. As for the fields that remain, they retain their original serialized values.

  3. Field added with a default (nested attrs type): If the reader's class defines an additional field that was not present in the writer's schema — a field whose type is a nested attrs class and that has a default value — deserialization succeeds, with the new field taking its default attrs instance value.

  4. Field added with a default (datetime type): If the reader's class defines an additional field that was not present in the writer's schema — a datetime-typed field with a default value — deserialization succeeds, and the new field gets its default value (e.g. None).

In every one of the evolution cases, fields shared by both writer and reader must round-trip to values equal to those that were serialized in the first place.

Supporting Data Classes (already in place, serving as field types)

In openedx_events.learning.data, the following attrs classes already exist and are put to use as inputs; the bridge must handle them, their nesting included:

  • UserPersonalData(username: str, email: str, name: str)
  • UserData(id: int, is_active: bool, pii: UserPersonalData)
  • CourseData(course_key: CourseKey, display_name: str, start: datetime, end: datetime)
  • CourseEnrollmentData(user: UserData, course: CourseData, mode: str, is_active: bool, creation_date: datetime, created_by: UserData)

Inside CourseEnrollmentData there is a CourseKey (transitively, via CourseData) alongside datetime fields; as a consequence, a bridge bound to it requires a CourseKey extension.

Dependencies

The implementation may depend on attrs, fastavro, and opaque-keys (this last one for CourseKey). Ensure that these are available as dependencies of the project.

Semantics of Equality

Value comparison is what the supported attrs classes do. The correctness of the bridge is judged by value equality (==) between the reconstructed objects and the originals, together with equality of their attr.asdict(...) representations in evolution scenarios.

Recursion applies to this rule too: when the type of an attrs attribute is itself an attrs class with defaults, the nested record that gets produced has fields obeying these same nullable-union rules.

  • The top-level result is a dict whose keys are the signal's field names.

  • A datetime value is turned into the string that .isoformat() gives.

  • What comes out at the top level is a dict with the signal's field names as keys.
  • Where a dict corresponds to an attrs record type, it is turned back into an instance of the appropriate attrs class (nested records handled recursively). These instances must be of the correct class and compare equal to the original objects.

  • TypeError must be raised by schema_from_signal (and by construction of the serializer/deserializer in cases where a schema gets built) when the Python type of a signal field is a plain class that is neither a primitive, an attrs class, a default-supported custom type (datetime, CourseKey), nor covered by a provided custom_type_to_avro_type mapping / registered custom serializer.

  4. The existing response and robust-response logging behavior must be preserved.

Only an enabled call that gets as far as metadata generation falls under the exactly-once rule for metadata. Before metadata is generated, the payload validation that already exists still runs; should that validation raise SenderValidationError, generating or dispatching metadata must not happen.

What happens for disabled signals

Whenever the signal is in a disabled state, send_event must return an empty list immediately. The following actions must not be taken by a disabled call:

  • validation of its event payload arguments,
  • validation of a time that was supplied,
  • a call to generate_signal_metadata,
  • obtaining a default timestamp, or
  • invoking Django signal dispatch in either its normal or its robust form.

Consequently, no sender-validation errors are raised by even malformed event arguments for as long as that signal is disabled.
