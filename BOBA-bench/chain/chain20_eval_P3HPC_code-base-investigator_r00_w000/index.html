Task Specification: Counting C/C++ Source Lines with Comment, Continuation, and Literal Handling

Goal

Implement parsing of C/C++ source files that computes source lines of code (SLOC) while handling C and C++ comments, backslash-newline continuations, string literals, and character literals correctly.

SLOC is attributed to qualifying physical source lines. Backslash-newline splicing affects lexical interpretation—this includes the recognition of comments and literals—but it does not collapse a continued group into a single counting unit.

Public API

The package codebasin must continue to provide the following modules for import:

  • codebasin.file_parser
  • codebasin.preprocessor
codebasin.file_parser.FileParser

A FileParser class must be provided with the following interface:

  • Constructor: The FileParser(path) constructor accepts one filesystem path string identifying the source file.
  • Method: parse_file() takes no arguments other than self; it parses the stored file and returns its source-tree object.
The Tree That Is Returned

The returned object must expose a root attribute, and the root object must expose an integer attribute named total_sloc that contains the total SLOC computed for the file. Existing source-tree construction and preprocessor behavior must remain compatible; this functionality must not require changes to unrelated public interfaces.

The Required Processing Model

Recognition of comments and literals must be performed with state that is carried through the file. Conceptually, the processing has these effects:

  1. Preserve every physical source line's identity for counting purposes.
  2. Determine the lexical character stream by resolving backslash-newline continuations.
  3. Recognize literals in that stream and remove comments from it.
  4. Attribute the surviving characters back to the physical lines they originally came from.
  5. Count each physical line if its attributed content contains at least one non-whitespace character.

As a result, continuation splicing supplies lexical context across lines, but each original physical line remains a separate possible SLOC contribution.

Continuations Formed by Backslash-Newline

A backslash immediately before a line ending causes both the backslash and that line ending to be removed, joining the surrounding text for lexical interpretation. The rule holds universally, including within:

  • ordinary code and tokens;
  • preprocessor directives;
  • // comments;
  • /* ... */ comments;
  • string literals; and
  • character literals.

Splicing happens even when it divides a token or a two-character comment delimiter. Notably, //, /*, and */ must still be recognized when either pair is split across a continuation boundary.

Because counting remains per physical line, a continued group may contribute more than one SLOC. The continuation backslash and newline that are removed are not content. Consequently, a physical line that contains only whitespace followed by a continuation backslash does not count, while each line that contains surviving non-whitespace code or literal text does count. A terminal backslash without a following newline and physical line does not constitute a backslash-newline splice.

Recognizing Comments

Comment delimiters are recognized only when the scanner is not inside a string literal, character literal, or another comment.

C++-Style Line Comments

A // sequence starts a comment that extends through the next newline that was not removed by continuation splicing. The comment may therefore span several physical lines when one or more lines end in continuation backslashes. For counting purposes, all comment text is removed. Content that is code or literal text and that appears before the // remains attributable to its physical line.

C-Style Block Comments

A /* sequence starts a block comment that continues until the next recognized */, potentially across any number of physical lines. All text and delimiters belonging to the block comment are removed. Non-comment content before the opener or after the closer remains, and it can cause its physical line to count. Openers and closers that are assembled by continuation splicing must behave exactly like delimiters written on one line.

A physical line that contains only comment text, comment delimiters, and whitespace does not count.

String and Character Literals

String-literal state is begun and ended by double quotes, and character-literal state is begun and ended by single quotes. While either literal state is active:

  • the sequences //, /*, and */ are literal text and must not start or end comments;
  • the literal is not closed by an escaped matching quote;
  • escaped backslashes and escaped quotes must be handled such that only an unescaped matching quote closes the literal; and
  • text in the literal is non-comment source content and can cause the physical line where it originated to count.

Literal state is not reset by an ordinary, non-continuation newline. If a string or character literal is not closed on the line where it begins, that state persists across the subsequent physical lines until an unescaped matching quote is encountered. The active literal state determines the treatment of all intervening text, including text resembling comment delimiters. Intervening lines that are blank or contain only whitespace still do not count.

This behavior is applied lexically, without first validating whether the surrounding text is valid C or C++. For example, in ordinary text such as #warning Dangerous don't do this, the apostrophe opens character-literal state if no character literal is already active. If no later matching apostrophe closes it immediately, text on subsequent lines that looks like a comment is treated as literal content rather than as a comment. The active literal is not closed by quotes of the other kind.

Rules for Counting SLOC

After continuation processing and comment removal, the following applies:

  • Each physical source line is counted at most once.
  • A physical line is counted if any non-whitespace character originating on that line survives as code, directive content, or literal text.
  • Blank lines, whitespace-only lines, and lines whose only non-whitespace characters were removed as comments or as a continuation backslash are not counted.
  • The physical-line count must not be replaced with one count per continuation-joined logical line.
  • Even if its surviving characters form only part of a token or literal assembled across continuation boundaries, a physical line can count.
  • Unless it also has surviving content outside that comment, a physical line inside a continued comment does not count.
  • Preprocessor directive text is source content. Each physical line of a directive is evaluated under the same rules, and it counts when it has surviving non-whitespace content. This covers directives such as #warning, whether or not their directive kind receives specialized semantic handling.

For example, a two-line statement where the first physical line ends in a continuation backslash and both lines contain code contributes two SLOC. By contrast, an intermediate physical line consisting solely of indentation and a continuation backslash contributes zero.

Concrete Expected Result

For the supplied .cpp sample, which exercises continued code, continued // comments, multiline /* ... */ comments, comment delimiters split by continuations, strings and characters containing comment-like text, escaped quotes and backslashes, adjacent literals, continuation-only physical lines, preprocessor #warning lines, and an unterminated quote state that persists across ordinary newlines, parse_file() must produce a tree whose root.total_sloc is exactly 25.

Below is the existing API in the codebasin package; it must remain available and callable exactly as described.

Dispatch by Language and Compatibility

It is from the file type that FileParser must choose the source-cleaning and continuation semantics. Recognized Fortran extensions include .f, .f90, and .f95, with recognition of these extensions carried out case-insensitively. It is the Fortran rules below, rather than the C comment rules, that Fortran files — including .f90 files — must use. The established C-family behavior must continue to be used for C and C++ source and header files.

What Counts as SLOC

Counting of SLOC is done per physical source line, never per folded logical statement. A physical line contributes at most one SLOC. One SLOC is contributed when, after comments and syntax-only continuation artifacts have been removed under the applicable language rules, non-whitespace source content still remains; when that is not the case, the contribution is zero. From this it follows that:

  • Physical lines that are blank or hold nothing but a comment contribute zero.
  • Every physical line bearing code that belongs to a continued statement contributes one, even when several such lines fold together into one logical statement.
  • If a physical line's content amounts to only a continuation marker, whitespace, or removable comment text, it contributes zero.
  • Comment-only lines interspersed among continuation lines contribute zero; a count is not acquired by them merely because they occur inside a continued statement.
  • This same physical-line rule also applies to a preprocessor directive continued with a backslash: physical lines bearing code are counted individually, whereas a continued line whose only content is a removable C comment does not count.

Semantics for Fortran Parsing

Comments in Fortran

Outside a recognized directive or a quoted literal, a ! opens a Fortran comment that reaches the end of the physical line.

  • When the first non-whitespace character of a line is an ordinary !, that line is a full-line comment and contributes zero SLOC. A line containing only ! and comment text is covered by this case.
  • If ! shows up after code, the code that precedes it remains and the physical line contributes one SLOC.
  • A comment positioned after a trailing continuation marker does not stop that marker from continuing the statement. As an example, the & in value = value & ! explanation is active, because it occurs outside a literal and before the trailing comment.
  • A comment line may sit between the physical lines of a continued statement; it contributes zero, while the code-bearing physical lines on either side are counted independently.
Directive handling

For recognized Fortran sentinel forms, directive recognition takes precedence over the ordinary handling of full-line ! comments. The lines listed next are code-bearing directives and count as SLOC:

  • Sentinel directives that start with !$.
  • Related sentinel forms that are recognized, such as !omp$.
  • Directives written in C-preprocessor style, whose first non-whitespace character is #, including #define, #if, #ifdef, #ifndef, #elif, #else, #endif, #include, #pragma, and #undef.

Should a line resemble a sentinel without being a recognized form, it stays a Fortran comment. One such case: a line that starts with !omp5% is not a directive. !#else is a Fortran comment as well and must neither count nor alter conditional preprocessing.

When C-preprocessor directives appear in Fortran, they must be passed through the existing directive parser and must retain the same conditional-tree and platform-evaluation behavior that directives in C-family files get. Counted are the directive lines themselves, conditional directives among them. Code located in active branches is associated with the applicable platform; a pseudo-directive that has been commented out has no effect.

Continuation of a preprocessor directive is indicated by a trailing backslash. For as long as a preprocessor directive is being parsed, C-preprocessor lexical rules govern its text: /* ... */ and // ... comments are removable, and operators such as ! stay available in expressions such as #if !defined(NAME). A multiline #define is one logical directive as far as preprocessing is concerned, but each non-comment, code-bearing physical line in it contributes one SLOC.

Continuations with & in Fortran

An ordinary Fortran statement is continued by a trailing & that is encountered outside a quoted literal. Continuation syntax is what a leading & on a continuation line constitutes. Logical folding is permitted by these markers, yet the physical-line counting rule is left unchanged by them:

  • Where an assignment is continued and code stands on its first and last physical lines, the contribution is two SLOC.
  • Each additional continuation line bearing code contributes one more SLOC.
  • Continuation markers, whether leading or trailing, are syntax artifacts; an otherwise empty line does not become countable from them on their own.
  • Blank or full-line-comment lines that intervene contribute zero.
  • An & located within a quoted literal is literal text and does not establish continuation.
Behavior of character and string literals

Fortran literals in both single-quoted and double-quoted form shield their contents against comment and continuation recognition. While a literal is active, characters such as !, /*, //, and & are data: comments are not begun by them, code is not suppressed by them, and they do not act as continuation markers. When a physical line contains code alongside such a literal, it contributes one SLOC.

Across a valid continued logical statement, string-bearing statements may occur; nevertheless, an & recognized outside a literal is what must establish continuation. Quoted fragments found on continuation lines are then, in the normal way, interpreted as literals. An ampersand that is consumed while quote state is active cannot itself carry the literal or statement onto the next physical line.

Across an ordinary physical-line boundary, quote state must not leak. When a physical line ends with a single- or double-quoted literal still unclosed, and that line has no valid continuation marker outside the literal, the open-literal state is discarded before the next physical line gets parsed. To take the particular case of a line that ends in an unclosed double-quoted value whose final & lies inside that value:

  • the & there is literal content rather than a continuation marker;
  • the line that bears code still contributes one SLOC; and
  • a physical line that comes next and begins with ! is parsed from non-string state, and is therefore a Fortran comment worth zero SLOC.

Malformed or partial literal input is resolved deterministically by this boundary rule, which does not let it change comment handling on later lines that are not continued.

C-style tokens within ordinary Fortran code

Away from the text of a C-preprocessor directive, tokens in the style of C comments are not comments in Fortran:

  • The Fortran string-concatenation operator is //.
  • Inside ordinary Fortran source, /* ... */ carries no C block-comment meaning.

It follows that such tokens must not remove or suppress ordinary Fortran code. Inside a quoted literal, those same sequences remain literal content.

Platform-Mapping Reference

Consider a Fortran file that has three common code lines ahead of a #if defined(GPU) block, three code lines in its GPU branch, an #elif defined(CPU) branch with two code lines in it, an ordinary !#else comment, #endif, and then two common code lines afterward. For this file, platform mapping must report:

  • 2 SLOC tied only to CPU,
  • 3 SLOC tied only to GPU, and
  • 8 SLOC tied to both CPU and GPU.

The five common code lines plus the three real conditional directive lines together make up the common count; the commented pseudo-directive, like the other Fortran comments, does not count.

Requirement 1: The Concatenation (##) Operator in Macro Expansion

Inside object-like and function-like macro definitions, the preprocessor must support the token-pasting operator ##. During macro expansion, adjacent tokens joined by ## must be concatenated into a single token, and this must interoperate correctly with argument substitution and subsequent rescanning/expansion.

The behaviors that follow must be supported:

  1. Function-like macro with ## on a parameter. A macro of the form

    #define THE_WIDTH_IMPL(X) X ## _WIDTH

    must, when invoked as THE_WIDTH_IMPL(AGPU), produce the single token AGPU_WIDTH (the substituted argument value pasted to the following token).

  2. Indirection so that the argument is expanded before pasting. A wrapper macro of the form

    #define THE_WIDTH(X) THE_WIDTH_IMPL(X)

    must, when invoked as THE_WIDTH(ARCH), first fully expand ARCH to its replacement (e.g. AGPU or ACPU), then paste, yielding e.g. AGPU_WIDTH, which must then itself be expanded via any matching object-like macro (e.g. #define AGPU_WIDTH 32) to its final value.

    #if defined(GPU)
#define ARCH AGPU
#elif defined(CPU)
#define ARCH ACPU
#endif

    must correctly define ARCH according to the active platform.

For the macro-expansion source described above, the net effect on line attribution is that lines guarded by the width comparisons must be attributed to the correct platform-specific sets. Concretely, a block active only when the width is 32 is attributed to the GPU-only configuration, and a block active only when the width is 16 is attributed to the CPU-only configuration.

Upon encountering characters that are not part of standard C/C++ preprocessing tokens (for example @ as used in Objective-C, or other non-standard punctuation), the preprocessor lexer must not fail. Such characters must be lexed as a generic/unknown token instead of causing an error, so that directive lines containing them can still be processed.

When line-continuation backslashes and comments interrupt the physical text — including in the middle of tokens and directive keywords — the preprocessor must correctly reconstruct logical directive lines.

*
*/ # /*
*/ defi\

O 10\
20

    must be recognized as the single directive # define FOO 1020 — that is, an object-like macro definition of FOO whose value is 1020.

Calling config.load on a file of this kind must raise ValueError. This schema error must be reported as ValueError even in the case where base_directory is the empty string.

config.load is not required to return any particular value.

Task Specification: Recognizing Compilers and Their Implicit Behavior

Summary

Functionality must be implemented in the codebasin.config module that takes a compiler invocation (given as a list of argument strings), determines which compiler it is, and reports the implicit preprocessor behavior that this compiler turns on. Different compilers bring in implicit macro definitions, and some compilers create multiple compilation "passes" (e.g., for different target architectures), each of which may define a set of macros of its own.

Public Interface

Everything listed below must live in the codebasin.config module.

recognize_compiler(args)
  • Input: args — the complete compiler command line as a list of strings. The compiler name/executable sits in the first element; everything after it is that compiler's arguments.
  • Output: an instance of one of the compiler classes (see below), picked according to the compiler name in args[0]. Which arguments occur in args shapes the returned object's behavior — its passes and its per-pass defines — as set out below.

These compiler names must be recognized, and each must map to the returned type shown:

Compiler name in args[0] Type of the returned instance
clang config.ClangCompiler
icpx (and the Intel family) config.IntelCompiler
nvcc config.NvccCompiler

codebasin.config must define and export each of these classes: ClangCompiler, IntelCompiler, NvccCompiler.

Methods the returned compiler object provides

Whatever compiler object is returned, it must provide the following methods:

  • get_passes() → returns a set of strings naming the compilation passes involved in this invocation. A pass named "default" is always present; every compiler has at least this pass.

  • has_implicit_behavior(pass_name) → returns a truthy value if the pass supplied shows any implicit behavior for this invocation (that is, it contributes any implicit defines).

  • get_defines(pass_name) → returns a list of strings holding the implicit preprocessor macro definitions that are active for the pass given by pass_name. The order of the list matters and must match the ordering specified below.

Behavior required from each compiler

ClangCompiler (clang)
  • The pass set is always exactly {"default"}.
  • If -fsycl-is-device is among the arguments:
    • the "default" pass exhibits implicit behavior;
    • get_defines("default") returns ["__SYCL_DEVICE_ONLY__"].
IntelCompiler (icpx / Intel family)
  • The -fsycl-targets=<t1>,<t2>,... argument introduces one further pass for each listed target, and the pass is named exactly by that target string. Together with the "default" pass, which is always present, the passes are the union of "default" and each target name.
    • Example: -fsycl-targets=spir64,x86_64 yields the passes {"default", "spir64", "x86_64"}.
  • If the arguments contain -fopenmp:
    • the "default" pass exhibits implicit behavior;
    • get_defines("default") returns ["_OPENMP"].
  • For each SYCL target pass that -fsycl-targets introduces (with -fsycl also in effect):
    • the pass exhibits implicit behavior;
    • get_defines(<target>) returns the list below, its items in exactly this order:
      ["__SYCL_DEVICE_ONLY__", "__SPIR__", "__SPIRV__"]
    • Every target pass is covered, whatever its name (e.g. both spir64 and x86_64 return this same list).
NvccCompiler (nvcc)
  • The --gpu-code=<c1>,<c2>,... argument is what determines the passes. Each entry of the form sm_<NN> or compute_<NN> contributes one pass, named after the numeric portion <NN>, with duplicates removed. Once these are added to the "default" pass — which is always present — the pass set is the union of "default" and each distinct numeric code.
    • Example: --gpu-code=compute_50,sm_50,sm_52 gives the passes {"default", "50", "52"} (the two 50 entries are collapsed into one "50" pass).
  • Implicit behavior is always present on the "default" pass, with these defines:
    ["__NVCC__", "__CUDACC__"]
  • Each numeric architecture pass <NN> exhibits implicit behavior too, and its defines are the default defines followed by the architecture macro:
    ["__NVCC__", "__CUDACC__", "__CUDA_ARCH__=<NN>0"]
    Here <NN>0 means the architecture number times 10 (e.g. pass "50" gives __CUDA_ARCH__=500, pass "52" gives __CUDA_ARCH__=520).

Additional Notes

  • The exact string ordering of the lists that get_defines returns must match the orderings stated above.
  • get_passes() returns a set; what counts is membership, not ordering.

Task Specification: Recognizing Compilers and Handling SYCL Flags

Overview

Implement or fix compiler recognition inside the module exposed as config (for example, via from codebasin import config). Given a list of command-line arguments, the module identifies the compiler it represents and models the compilation passes together with the implicit preprocessor definitions that the compiler flags cause.

An Intel icpx invocation that includes the standalone -fsycl option must be treated as a SYCL compilation even if no -fsycl-targets=... option is present. The behavior that already exists for explicit SYCL targets and OpenMP must remain compatible.

Public Interface

config.recognize_compiler(args)
  • args is a list of strings that describes a compiler command line. The first element is the name of the compiler executable; the remaining elements are options, source files, and other arguments.
  • The function returns a compiler object suited to the invocation.
  • If the executable is icpx, the object returned must be an instance of the publicly accessible config.IntelCompiler class.
config.IntelCompiler

An Intel compiler object returned by recognize_compiler must expose the methods listed below.

get_passes()
  • Returns a set consisting of pass-name strings.
  • That set always contains "default".
  • A bare SYCL invocation — one that contains -fsycl but no explicit target-selection option — has an implicit "spir64" target pass. The pass set for such an invocation is exactly:
    {"default", "spir64"}
  • If -fsycl-targets= supplies explicit comma-separated targets, then those target names, in addition to "default", are represented as passes. As a specific case, -fsycl-targets=spir64,x86_64 produces exactly:
    {"default", "spir64", "x86_64"}
has_implicit_behavior(pass_name)
  • Accepts a pass-name string; the boolean it returns indicates whether that pass has implicit compiler behavior, including implicitly defined preprocessor macros.
  • For a SYCL compilation, the "spir64" pass has implicit behavior and consequently returns True.
  • For the explicit spir64,x86_64 SYCL and OpenMP invocation described below, each of "default", "spir64", and "x86_64" has implicit behavior.
get_defines(pass_name)
  • It accepts a pass-name string.
  • Returns, for that pass, an ordered list of implicitly defined preprocessor macro strings.
  • For a bare SYCL-only invocation, the definitions for the "default" pass are exactly:
    ["__SYCL_DEVICE_ONLY__"]
  • When the pass is a "spir64" SYCL target pass, the definitions are exactly, in this order:
    ["__SYCL_DEVICE_ONLY__", "__SPIR__", "__SPIRV__"]
  • For a "x86_64" SYCL target pass that is explicitly selected, the definitions are likewise exactly, in this order:
    ["__SYCL_DEVICE_ONLY__", "__SPIR__", "__SPIRV__"]

Flag Handling Requirements

The Standalone -fsycl Flag

By itself, the literal standalone -fsycl argument is enough to enable SYCL behavior. Recognition must not depend on finding a -fsycl-targets=... argument as well.

For instance:

args = ["icpx", "-fsycl", "test.cpp"]
compiler = config.recognize_compiler(args)

The object that results must:

  • be an instance of config.IntelCompiler;
  • return exactly {"default", "spir64"} when get_passes() is called;
  • return True when has_implicit_behavior("spir64") is called;
  • return exactly ["__SYCL_DEVICE_ONLY__", "__SPIR__", "__SPIRV__"] when get_defines("spir64") is called; and
  • return exactly ["__SYCL_DEVICE_ONLY__"] when get_defines("default") is called.
Explicit SYCL Targets Together with OpenMP

Handling of explicit targets and the separation of macros between host and device must be preserved. If explicit SYCL targets are selected, the SYCL device macros belong to the target passes rather than the host "default" pass.

For the invocation below:

args = [
    "icpx",
    "-fsycl",
    "-fsycl-targets=spir64,x86_64",
    "-fopenmp",
    "test.cpp",
]
compiler = config.recognize_compiler(args)

The resulting compiler object must:

  • be a config.IntelCompiler instance;
  • return exactly {"default", "spir64", "x86_64"} when get_passes() is called;
  • for each of "default", "spir64", and "x86_64", return True from has_implicit_behavior();
  • return exactly ["_OPENMP"] when get_defines("default") is called;
  • return exactly ["__SYCL_DEVICE_ONLY__", "__SPIR__", "__SPIRV__"] when get_defines("spir64") is called; and
  • return exactly ["__SYCL_DEVICE_ONLY__", "__SPIR__", "__SPIRV__"] when get_defines("x86_64") is called.

In this combined invocation with explicit targets, the SYCL device macros must not be added to "default" — _OPENMP is its only implicit definition. As a result, the bare-SYCL default-pass rule must not overwrite or contaminate the established explicit-target/OpenMP behavior.

Compatibility and Scope

  • A target-selection flag must not be required for bare -fsycl to create the implicit "spir64" pass.
  • Preserve the ordered macro lists and pass sets that currently exist for explicitly selected SYCL targets, together with their interaction with OpenMP.
  • Preserve recognition and implicit behavior for other kinds of compilers and for unrelated command-line options.
  • These requirements specify externally observable results and do not mandate a particular internal implementation.

Task Specification: Excluding Files with Pattern Matching

Overview

Introduce support for excluding source files from the analysis by means of git-style pathspec patterns, with this exclusion being configurable programmatically through the configuration loader.

Public API

codebasin.config.load

Adjust the load function in the codebasin.config module so that it accepts a new keyword argument:

def load(config_file, rootdir, *, exclude_patterns=None, ...)
  • config_file (str): the path to a YAML configuration file.
  • rootdir (str): the root directory of the codebase that is being analyzed.
  • exclude_patterns (list of str, optional): a list of pathspec-style patterns identifying the files to exclude from analysis. When it is omitted or empty, no files are excluded through this argument.

The function must return a 2-tuple (codebase, configuration) in which:

  • codebase is the object that codebasin.finder.find and codebasin.walkers.platform_mapper.PlatformMapper consume.
  • configuration is the object that codebasin.finder.find consumes.

The behavior that load already has (parsing the YAML file, resolving the codebase and per-platform command settings) must be preserved. The only new behavior is the honoring of exclude_patterns.

Configuration File Format

The YAML configuration file is laid out as follows:

codebase:
    files: [ ]
    platforms: [ <platform-name>, ... ]

<platform-name>:
    commands: "<compilation-database-file>"
  • The codebase section enumerates platform names and, optionally, an explicit list of files.
  • Each named platform section refers to a compilation database (a JSON file) through its commands key. That path is relative to the directory in which the YAML file resides.
  • The compilation database is a JSON array of objects; each object carries a command string and a file path (relative to rootdir).

Behavior of the Exclusions

Files that any of the exclude_patterns match must be removed from the set of files being analyzed. The patterns follow git pathspec semantics and are evaluated relative to rootdir:

  • Extension globs — for example, *.f90 excludes every file that has that extension, no matter how deep it sits in the directory tree.
  • Explicit relative paths — for example, src/excluded_name.cpp excludes exactly that file, with the match made relative to rootdir.
  • Directory patterns — for example, thirdparty/ excludes every file found (at any depth) inside a directory of that name.

Multiple patterns may be passed together; a file is excluded if it matches any one of them.

Excluded files must not show up in the analysis results that the downstream pipeline (finder.find → PlatformMapper.walk) produces.

Downstream Pipeline (pre-existing, described for context)

After the load has taken place, the sequence below produces a mapping from platform sets to file counts:

codebase, configuration = config.load(yaml_path, rootdir, exclude_patterns=excludes)
state = finder.find(rootdir, codebase, configuration)
mapper = PlatformMapper(codebase)
setmap = mapper.walk(state)

setmap is a dictionary in which the keys are frozenset objects of platform names and the values are integer counts of the files attributed to that exact set of platforms. Each source file that undergoes analysis for a single platform "test" contributes 1 to the entry keyed by frozenset(["test"]).

Specific Expected Results

Take a codebase that has four source files, all of them compiled for a single platform named test:

  • src/included.cpp
  • src/excluded_name.cpp
  • src/excluded_extension.f90
  • src/thirdparty/library.cpp

when analyzed with rootdir pointing at the directory that contains these under src/, the resulting setmap must be:

exclude_patterns Resulting setmap
[] {frozenset(["test"]): 4}
["*.f90"] {frozenset(["test"]): 3}
["src/excluded_name.cpp"] {frozenset(["test"]): 3}
["thirdparty/"] {frozenset(["test"]): 3}
["*.f90", "src/excluded_name.cpp", "thirdparty/"] {frozenset(["test"]): 1}

Each excluded file lowers the count for frozenset(["test"]) by one; the count covers only the files that remain after exclusion.

Task Specification: Loading TOML with Schema Validation

Goal

Implement a function that loads TOML files and validates their contents against a JSON schema that is selected by name.

Public Interface

The following function is to be added to the module codebasin.util:

def _load_toml(file_object, schema_name):
    ...
Parameters
  • file_object: a binary file object (opened in "rb" mode) that holds TOML-formatted text.
  • schema_name: a string that names the schema to validate the parsed contents against. The two schema names that must be supported are "cbiconfig" and "analysis".
Return Value

On success, the function returns the parsed TOML contents as a Python dict (with nested tables represented as nested dicts, arrays as lists, etc.).

Error Behavior

If the parsed contents fail to conform to the schema named by schema_name, the function must raise ValueError.

Schema Definitions

The "cbiconfig" schema

This schema describes compiler configuration. The part of the structure that is exercised is:

  • A compiler table (dict) at the top level.
  • Under compiler, each entry is keyed by a compiler name and maps to a table that contains an options field.
  • The options field must be a list of strings.

A document in which any options value is not a list of strings (for instance, an integer) is invalid and must cause a ValueError.

A document in which each compiler entry's options is a list of strings is valid. As an example, the following parses successfully and returns:

{
    "compiler": {
        "test_one": {"options": ["TEST_ONE"]},
        "test_two": {"options": ["TEST_TWO"]},
    },
}
The "analysis" schema

This schema describes an analysis configuration. The part of the structure that is exercised is:

  • A codebase table at the top level that contains an exclude field, where exclude is a list of strings.
  • A platform table at the top level, whose entries are keyed by platform name and each map to a table that contains a commands field, where commands is a string.

A document that is valid parses successfully and returns a dict mirroring the TOML structure. As an example, given suitable input, the return value is:

{
    "codebase": {
        "exclude": ["*.F90", "*.cu"],
    },
    "platform": {
        "one": {
            "commands": "one.json",
        },
        "two": {
            "commands": "two.json",
        },
    },
}

A document violating this schema must cause a ValueError.

Test Data Files

The TOML data files listed below are to be created (they act as inputs):

tests/schema/analysis.toml

Content that conforms to the "analysis" schema and is valid:

[codebase]
exclude = [
    "*.F90",
    "*.cu",
]

[platform.one]
commands = "one.json"

[platform.two]
commands = "two.json"
tests/schema/invalid_analysis.toml

Content that parses as TOML but is in violation of the "analysis" schema (i.e., at least one field has a type the schema does not allow, causing _load_toml(..., "analysis") to raise ValueError).

Note: the files tests/schema/cbiconfig.toml and tests/schema/invalid_cbiconfig.toml already exist and are not part of this task.

Additional Notes

  • The parsing step must accept binary file objects.
  • Validation must distinguish valid documents from invalid ones purely through structure/type conformance to the named schema; type mismatches (for example, a numeric value where a list or string is required) constitute invalidity.
