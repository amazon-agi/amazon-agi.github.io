01 C/C++ Source-Line Counting with Comment, Continuation, and Literal Handling 1076 words · rewritten by GPT-5.6-sol

Task Specification: C/C++ Source-Line Counting with Comment, Continuation, and Literal Handling

Objective

Implement C/C++ source-file parsing that computes source lines of code (SLOC) while correctly handling C and C++ comments, backslash-newline continuations, string literals, and character literals.

SLOC is attributed to qualifying physical source lines. Backslash-newline splicing affects lexical interpretation, including recognition of comments and literals, but it does not collapse a continued group into a single counting unit.

Public API

The package codebasin must continue to provide these importable modules:

  • codebasin.file_parser
  • codebasin.preprocessor
codebasin.file_parser.FileParser

Provide a FileParser class with the following interface:

  • Constructor: FileParser(path) accepts one filesystem path string identifying the source file.
  • Method: parse_file() takes no arguments other than self, parses the stored file, and returns its source-tree object.
Returned tree

The returned object must expose a root attribute. The root object must expose an integer attribute named total_sloc, containing the total SLOC computed for the file. Existing source-tree construction and preprocessor behavior must remain compatible; this functionality must not require changes to unrelated public interfaces.

Required Processing Model

Comment and literal recognition must be performed with state carried through the file. Conceptually, processing has these effects:

  1. Preserve the identity of every physical source line for counting purposes.
  2. Resolve backslash-newline continuations to determine the lexical character stream.
  3. Recognize literals and remove comments from that stream.
  4. Attribute surviving characters back to their original physical lines.
  5. Count each physical line whose attributed content contains at least one non-whitespace character.

Thus, continuation splicing provides lexical context across lines, but each original physical line remains a separate possible SLOC contribution.

Backslash-Newline Continuations

A backslash immediately before a line ending removes both the backslash and that line ending, joining the surrounding text for lexical interpretation. This rule applies universally, including within:

  • ordinary code and tokens;
  • preprocessor directives;
  • // comments;
  • /* ... */ comments;
  • string literals; and
  • character literals.

Splicing occurs even when it divides a token or a two-character comment delimiter. In particular, //, /*, and */ must still be recognized when either pair is split across a continuation boundary.

A continued group may contribute more than one SLOC because counting remains per physical line. The removed continuation backslash and newline are not content. Consequently, a physical line containing only whitespace followed by a continuation backslash does not count, while each line containing surviving non-whitespace code or literal text does count. A terminal backslash without a following newline and physical line is not a backslash-newline splice.

Comment Recognition

Comment delimiters are recognized only while the scanner is not inside a string literal, character literal, or another comment.

C++-style line comments

A // sequence begins a comment extending through the next newline that was not removed by continuation splicing. The comment may therefore cover several physical lines when one or more lines end in continuation backslashes. All comment text is removed for counting. Code or literal content before the // remains attributable to its physical line.

C-style block comments

A /* sequence begins a block comment that continues until the next recognized */, potentially across any number of physical lines. All block-comment text and delimiters are removed. Non-comment content before the opener or after the closer remains and can cause its physical line to count. Openers and closers assembled by continuation splicing must behave exactly like delimiters written on one line.

A physical line containing only comment text, comment delimiters, and whitespace does not count.

String and Character Literals

Double quotes begin and end string-literal state, and single quotes begin and end character-literal state. While in either literal state:

  • //, /*, and */ are literal text and must not start or end comments;
  • an escaped matching quote does not close the literal;
  • escaped backslashes and escaped quotes must be handled so that only an unescaped matching quote closes the literal; and
  • text in the literal is non-comment source content and can cause its originating physical line to count.

Literal state is not reset by an ordinary, non-continuation newline. If a string or character literal is not closed on the line where it begins, that state persists over subsequent physical lines until an unescaped matching quote is encountered. All intervening text is treated according to the active literal state, including text resembling comment delimiters. Blank or whitespace-only intervening lines still do not count.

This behavior applies lexically without first validating whether the surrounding text is valid C or C++. For example, the apostrophe in ordinary text such as #warning Dangerous don't do this opens character-literal state if no character literal is already active. If no later matching apostrophe closes it immediately, comment-looking text on subsequent lines is treated as literal content rather than as a comment. Quotes of the other kind do not close the active literal.

SLOC Counting Rules

After continuation processing and comment removal:

  • Count each physical source line at most once.
  • Count a physical line if any non-whitespace character originating on that line survives as code, directive content, or literal text.
  • Do not count blank lines, whitespace-only lines, or lines whose only non-whitespace characters were removed as comments or as a continuation backslash.
  • Do not replace the physical-line count with one count per continuation-joined logical line.
  • A physical line can count even if its surviving characters form only part of a token or literal assembled across continuation boundaries.
  • A physical line inside a continued comment does not count unless it also has surviving content outside that comment.
  • Preprocessor directive text is source content. Each physical line of a directive is evaluated by the same rules and counts when it has surviving non-whitespace content. This includes directives such as #warning, whether or not their directive kind receives specialized semantic handling.

For example, a two-line statement in which the first physical line ends in a continuation backslash and both lines contain code contributes two SLOC. By contrast, an intermediate physical line consisting solely of indentation and a continuation backslash contributes zero.

Concrete Expectation

For the supplied .cpp sample exercising continued code, continued // comments, multiline /* ... */ comments, comment delimiters split by continuations, strings and characters containing comment-like text, escaped quotes and backslashes, adjacent literals, continuation-only physical lines, preprocessor #warning lines, and an unterminated quote state that persists across ordinary newlines, parse_file() must produce a tree whose root.total_sloc is exactly 25.

Objective

Add Fortran source-file support to the existing source line-of-code (SLOC) parsing subsystem so that it can parse fixed- and free-form Fortran source and compute its SLOC count. Existing C and C++ parsing, preprocessing, tree construction, and line-counting behavior must remain unchanged.

Public API Surface

The following existing API in the codebasin package must remain available and callable exactly as described.

codebasin.file_parser.FileParser
  • Constructor: FileParser(path), where path is a string filesystem path to a source file.
  • Method: parse_file(), which parses the configured file and returns its source tree.
Returned tree
  • The returned tree has a root attribute.
  • root has an integer total_sloc attribute containing the total SLOC for the parsed file.
  • Fortran preprocessor constructs must remain represented in the source tree in a form usable by the existing directive evaluation and platform-mapping behavior; Fortran support must not reduce the result to a flat count.

Language Dispatch and Compatibility

FileParser must choose source-cleaning and continuation semantics from the file type. Recognized Fortran extensions include .f, .f90, and .f95, case-insensitively. Fortran files, including .f90 files, must use the Fortran rules below rather than the C comment rules. C and C++ source and header files must continue to use the established C-family behavior.

SLOC Definition

SLOC is counted per physical source line, not per folded logical statement. Each physical line contributes at most one SLOC. It contributes one when non-whitespace source content remains after removing comments and syntax-only continuation artifacts under the applicable language rules; otherwise it contributes zero. Consequently:

  • Blank and comment-only physical lines contribute zero.
  • Every code-bearing physical line in a continued statement contributes one, even when several such lines fold into one logical statement.
  • A physical line containing only a continuation marker, whitespace, or removable comment text contributes zero.
  • Comment-only lines interspersed among continuation lines contribute zero and do not acquire a count merely because they occur inside a continued statement.
  • The same physical-line rule applies to a backslash-continued preprocessor directive: code-bearing physical lines count individually, while a continued line whose only content is a removable C comment does not count.

Fortran Parsing Semantics

Fortran comments

Outside a recognized directive or quoted literal, ! begins a Fortran comment that extends to the end of the physical line.

  • A line whose first non-whitespace character is an ordinary ! is a full-line comment and contributes zero SLOC. This includes a line containing only ! and comment text.
  • When ! occurs after code, the preceding code remains and the physical line contributes one SLOC.
  • A comment after a trailing continuation marker does not prevent that marker from continuing the statement. For example, the & in value = value & ! explanation is active because it occurs outside a literal and before the trailing comment.
  • A comment line may occur between physical lines of a continued statement; it contributes zero while the code-bearing physical lines on either side are counted independently.
Directives

Directive recognition takes precedence over ordinary full-line ! comment handling for recognized Fortran sentinel forms. The following lines are code-bearing directives and count as SLOC:

  • Sentinel directives beginning with !$.
  • Recognized related sentinel forms such as !omp$.
  • C-preprocessor-style directives whose first non-whitespace character is #, including #define, #if, #ifdef, #ifndef, #elif, #else, #endif, #include, #pragma, and #undef.

A line that merely resembles a sentinel but is not a recognized form remains a Fortran comment. In particular, a line beginning with !omp5% is not a directive. Likewise, !#else is a Fortran comment and must neither count nor alter conditional preprocessing.

C-preprocessor directives in Fortran must be passed through the existing directive parser and retain the same conditional-tree and platform-evaluation behavior as directives in C-family files. The directive lines themselves count, including conditional directives. Code in active branches is associated with the applicable platform, while a commented-out pseudo-directive has no effect.

Preprocessor continuations use a trailing backslash. While a preprocessor directive is being parsed, C-preprocessor lexical rules apply to its text: /* ... */ and // ... comments are removable, and operators such as ! remain available in expressions such as #if !defined(NAME). A multiline #define remains one logical directive for preprocessing, but each non-comment, code-bearing physical line in it contributes one SLOC.

Fortran & continuations

A trailing & encountered outside a quoted literal continues an ordinary Fortran statement. A leading & on a continuation line is continuation syntax. These markers permit logical folding but do not change the physical-line counting rule:

  • A continued assignment with code on its first and last physical lines contributes two SLOC.
  • Additional code-bearing continuation lines each contribute one more SLOC.
  • Leading or trailing continuation markers are syntax artifacts; they do not by themselves make an otherwise empty line countable.
  • Intervening blank or full-line-comment lines contribute zero.
  • An & inside a quoted literal is literal text and does not establish continuation.
Character and string literals

Both single-quoted and double-quoted Fortran literals protect their contents from comment and continuation recognition. Within an active literal, characters such as !, /*, //, and & are data: they do not begin comments, suppress code, or act as continuation markers. A physical line containing code and such a literal contributes one SLOC.

String-bearing statements may occur across a valid continued logical statement, but continuation must be established by an & recognized outside a literal. Quoted fragments on continuation lines are then interpreted as literals in the normal way. An ampersand consumed while quote state is active cannot itself carry the literal or statement onto the next physical line.

Quote state must not leak across an ordinary physical-line boundary. If a single- or double-quoted literal is still unclosed at the end of a physical line and that line has no valid continuation marker outside the literal, the open-literal state is discarded before parsing the next physical line. In particular, for a line ending in an unclosed double-quoted value whose final & lies inside that value:

  • the & is literal content, not a continuation marker;
  • the code-bearing line still contributes one SLOC; and
  • a following physical line beginning with ! is parsed from non-string state and is therefore a zero-SLOC Fortran comment.

This boundary rule resolves malformed or partial literal input deterministically without allowing it to change comment handling on later, non-continued lines.

C-style tokens in ordinary Fortran code

Outside C-preprocessor directive text, C-style comment tokens are not comments in Fortran:

  • // is the Fortran string-concatenation operator.
  • /* ... */ has no C block-comment meaning in ordinary Fortran source.

Such tokens therefore must not remove or suppress ordinary Fortran code. The same sequences inside a quoted literal remain literal content.

Integration Reference

For a Fortran file with three common code lines before a #if defined(GPU) block, three code lines in its GPU branch, an #elif defined(CPU) branch containing two code lines, an ordinary !#else comment, #endif, and two common code lines afterward, platform mapping must report:

  • 2 SLOC associated only with CPU,
  • 3 SLOC associated only with GPU, and
  • 8 SLOC associated with both CPU and GPU.

The common count comprises the five common code lines plus the three real conditional directive lines; the commented pseudo-directive and other Fortran comments do not count.

SLOC Reference Outcome

For a Fortran source containing:

  • two leading full-line ! comments;
  • a program statement;
  • a backslash-continued #define containing C block and line comments;
  • a declaration;
  • an assignment split over code-bearing physical lines with & and an intervening comment line;
  • !$ and !omp$ sentinel directives;
  • an unrecognized !omp5% comment;
  • write statements whose literals contain !, /* ... */, //, and &;
  • a longer string-bearing sequence spread among & continuation lines and interspersed comment lines, including an unclosed quoted line whose final ampersand is inside the literal;
  • an invocation of the defined macro;
  • a #if/#endif block containing a write statement; and
  • an end program statement,

the resulting root.total_sloc must be 20. In that result, the ordinary continued assignment contributes two SLOC, the longer continuation sequence contributes four SLOC from its four code-bearing physical lines, and its intervening comment lines contribute zero.

Constraints

  • Do not change the FileParser(path).parse_file() entry point or the returned tree's root.total_sloc contract.
  • Preserve existing C and C++ parsing results and all existing preprocessor/tree behavior.
  • Fortran support must integrate with existing source-tree, conditional-directive, and platform-association behavior rather than bypassing it.

Overview

The core mechanism identifies which lines are compiled under which combinations of preprocessor definitions.

Public API Behavior

The tool is driven through its existing analysis entry point (invoked via a YAML configuration file describing sources and platforms). No new public classes or functions are introduced; the required behavior is observed through the line-attribution results produced when analyzing the source files described below. The result of analysis is a set-map: a mapping from a frozenset of active platform names to the count of source lines attributed to that exact platform combination.

The two areas of behavior to implement are described below in terms of the source constructs that must be handled correctly.

Requirement 1: Concatenation (##) Operator in Macro Expansion

The preprocessor must support the token-pasting operator ## inside object-like and function-like macro definitions. When a macro is expanded, adjacent tokens joined by ## must be concatenated into a single token, and this must interoperate correctly with argument substitution and further rescanning/expansion.

The following behaviors must be supported:

  1. Function-like macro with ## on a parameter. A macro of the form

    #define THE_WIDTH_IMPL(X) X ## _WIDTH

    when invoked as THE_WIDTH_IMPL(AGPU) must produce the single token AGPU_WIDTH (the substituted argument value pasted to the following token).

  2. Indirection so the argument is expanded before pasting. A wrapper macro of the form

    #define THE_WIDTH(X) THE_WIDTH_IMPL(X)

    invoked as THE_WIDTH(ARCH) must first fully expand ARCH to its replacement (e.g. AGPU or ACPU), then paste, yielding e.g. AGPU_WIDTH, which must then itself be expanded via any matching object-like macro (e.g. #define AGPU_WIDTH 32) to its final value.

  4. Conditional definition of the driving macro. Constructs like

    #if defined(GPU)
#define ARCH AGPU
#elif defined(CPU)
#define ARCH ACPU
#endif

    must correctly define ARCH per the active platform.

The net effect on line attribution for the macro-expansion source described above: lines guarded by the width comparisons must be attributed to the correct platform-specific sets. Specifically, a block active only when the width is 32 is attributed to the GPU-only configuration, and a block active only when the width is 16 is attributed to the CPU-only configuration.

Supporting requirement: Unknown-token tolerance in the preprocessor lexer

The preprocessor lexer must not fail when it encounters characters that are not part of standard C/C++ preprocessing tokens (for example @ as used in Objective-C, or other non-standard punctuation). Such characters must be lexed as a generic/unknown token rather than causing an error, so that directive lines containing them can still be processed.

Requirement 2: Line Continuations and Comment Splicing in Directives

The preprocessor must correctly reconstruct logical directive lines when line-continuation backslashes and comments interrupt the physical text, including within the middle of tokens and directive keywords.

The following must all be handled so that a single logical #define is recognized:

  • A backslash-newline (\ immediately followed by a newline) splices two physical lines into one, and this splicing may occur in the middle of a token or keyword. For example, the physical lines

O 10\
20

    /\
*
*/ # /*
*/ defi\
ne FO\
O 10\
20

    must be recognized as the single directive # define FOO 1020, i.e. an object-like macro definition of FOO with value 1020.

The net effect on line attribution: after correct splicing, the reconstructed directive and its surrounding lines in the always-compiled configuration must be counted, increasing the number of lines attributed to the fully-active platform set for that source.

String literal tokenization

Token concatenation (##)

In a macro replacement list, the ## operator concatenates the token immediately preceding it with the token immediately following it into a single token.

  • For a macro defined as CATTEST=first ## 2, expanding an invocation of CATTEST must yield a token stream equivalent to lexing first2 (i.e. the two operands are joined into a single token first2).
  • The token following ## must be fully captured and correctly concatenated onto the trailing end of the preceding token.
Stringification (#)

In a function-like macro replacement list, the # operator applied to a parameter converts the corresponding argument tokens into a single string-literal token.

Stringification rules:

  • The result is a string literal (surrounded by double quotes) whose content is the textual representation of the argument's tokens.
  • Runs of whitespace between argument tokens collapse to a single space, and there is no leading or trailing whitespace inside the produced string.
  • Any double-quote and backslash characters appearing within the argument tokens must be escaped (backslash-escaped) in the produced string literal.

Examples:

  • Macro STR(x)= #x; invoking STR(foo("4 + 5")) yields a token stream equivalent to lexing "foo(\"4 + 5\")".

Nested stringification / expansion

Argument expansion and stringification must interact per standard C preprocessor semantics:

Given macros:

  • xstr(s)=str(s)
  • str(s)=#s
  • foo=4

Then:

  • Expanding str(foo) yields a token stream equivalent to lexing "foo" — i.e. the argument to a directly-stringifying macro is not macro-expanded before stringification.
  • Expanding xstr(foo) yields a token stream equivalent to lexing "4" — i.e. the argument passed through xstr is macro-expanded (foo → 4) before it reaches str's stringification.

Correctness Criterion

For all expansion cases, correctness is determined by comparing the ordered list of .token values of the produced tokens against the .token values obtained by lexing the expected result string. The .token strings must match exactly in order and content.

  • The exact string ordering of the lists returned by get_defines must match the orderings specified above.
  • get_passes() returns a set; membership is what matters, not ordering.

Task Specification: Compiler Recognition and SYCL Flag Handling

Overview

Implement or correct compiler recognition in the module exposed as config (for example, through from codebasin import config). The module identifies the compiler represented by a command-line argument list and models the compilation passes and implicit preprocessor definitions caused by compiler flags.

An Intel icpx invocation containing the standalone -fsycl option must be treated as a SYCL compilation even when no -fsycl-targets=... option is present. Existing behavior for explicit SYCL targets and OpenMP must remain compatible.

Public API

config.recognize_compiler(args)
  • args is a list of strings representing a compiler command line. The first element is the compiler executable name; the remaining elements are options, source files, and other arguments.
  • The function returns a compiler object appropriate for the invocation.
  • When the executable is icpx, the returned object must be an instance of the publicly accessible config.IntelCompiler class.
config.IntelCompiler

An Intel compiler object returned by recognize_compiler must expose the following methods.

get_passes()
  • Returns a set of pass-name strings.
  • The set always contains "default".
  • A bare SYCL invocation containing -fsycl but no explicit target-selection option has an implicit "spir64" target pass. Its pass set is exactly:
    {"default", "spir64"}
  • When -fsycl-targets= supplies explicit comma-separated targets, those target names are represented as passes in addition to "default". In particular, -fsycl-targets=spir64,x86_64 produces exactly:
    {"default", "spir64", "x86_64"}
has_implicit_behavior(pass_name)
  • Accepts a pass-name string and returns a boolean indicating whether that pass has implicit compiler behavior, including implicitly defined preprocessor macros.
  • The "spir64" pass of a SYCL compilation has implicit behavior and therefore returns True.
  • For the explicit spir64,x86_64 SYCL and OpenMP invocation described below, "default", "spir64", and "x86_64" each have implicit behavior.
get_defines(pass_name)
  • Accepts a pass-name string.
  • Returns an ordered list of implicitly defined preprocessor macro strings for that pass.
  • For the "default" pass of a bare SYCL-only invocation, the definitions are exactly:
    ["__SYCL_DEVICE_ONLY__"]
  • For a "spir64" SYCL target pass, the definitions are exactly, in this order:
    ["__SYCL_DEVICE_ONLY__", "__SPIR__", "__SPIRV__"]
  • For an explicitly selected "x86_64" SYCL target pass, the definitions are likewise exactly, in this order:
    ["__SYCL_DEVICE_ONLY__", "__SPIR__", "__SPIRV__"]

Required Flag Handling

Standalone -fsycl

The literal standalone -fsycl argument is sufficient to enable SYCL behavior. Recognition must not depend on also finding a -fsycl-targets=... argument.

For example:

args = ["icpx", "-fsycl", "test.cpp"]
compiler = config.recognize_compiler(args)

The resulting object must:

  • be a config.IntelCompiler;
  • return exactly {"default", "spir64"} from get_passes();
  • return True from has_implicit_behavior("spir64");
  • return exactly ["__SYCL_DEVICE_ONLY__", "__SPIR__", "__SPIRV__"] from get_defines("spir64"); and
  • return exactly ["__SYCL_DEVICE_ONLY__"] from get_defines("default").
Explicit SYCL targets combined with OpenMP

Explicit target handling and host/device macro separation must be preserved. When explicit SYCL targets are selected, SYCL device macros belong to the target passes rather than the host "default" pass.

For this invocation:

args = [
    "icpx",
    "-fsycl",
    "-fsycl-targets=spir64,x86_64",
    "-fopenmp",
    "test.cpp",
]
compiler = config.recognize_compiler(args)

The resulting object must:

  • be a config.IntelCompiler;
  • return exactly {"default", "spir64", "x86_64"} from get_passes();
  • return True from has_implicit_behavior() for each of "default", "spir64", and "x86_64";
  • return exactly ["_OPENMP"] from get_defines("default");
  • return exactly ["__SYCL_DEVICE_ONLY__", "__SPIR__", "__SPIRV__"] from get_defines("spir64"); and
  • return exactly ["__SYCL_DEVICE_ONLY__", "__SPIR__", "__SPIRV__"] from get_defines("x86_64").

The SYCL device macros must not be added to "default" in this combined explicit-target invocation: its only implicit definition is _OPENMP. Thus, the bare-SYCL default-pass rule must not overwrite or contaminate established explicit-target/OpenMP behavior.

Compatibility and Scope

  • Do not require a target-selection flag for bare -fsycl to create the implicit "spir64" pass.
  • Preserve the existing ordered macro lists and pass sets for explicitly selected SYCL targets and their interaction with OpenMP.
  • Preserve recognition and implicit behavior for other compiler kinds and unrelated command-line options.
  • These requirements define externally observable results and do not mandate a particular internal implementation.

Task Specification: File Exclusion via Pattern Matching

Overview

Add support for excluding source files from analysis using git-style pathspec patterns, configurable programmatically through the configuration loader.

Public API

codebasin.config.load

Modify the load function in the codebasin.config module to accept a new keyword argument:

def load(config_file, rootdir, *, exclude_patterns=None, ...)
  • config_file (str): path to a YAML configuration file.
  • rootdir (str): the root directory of the codebase being analyzed.
  • exclude_patterns (list of str, optional): a list of pathspec-style patterns identifying files to exclude from analysis. When omitted or empty, no files are excluded via this argument.

The function must return a 2-tuple (codebase, configuration) where:

  • codebase is the object consumed by codebasin.finder.find and codebasin.walkers.platform_mapper.PlatformMapper.
  • configuration is the object consumed by codebasin.finder.find.

The existing behavior of load (parsing the YAML file, resolving the codebase and per-platform command settings) must be preserved. The only new behavior is honoring exclude_patterns.

Configuration File Format

The YAML configuration file has the following structure:

codebase:
    files: [ ]
    platforms: [ <platform-name>, ... ]

<platform-name>:
    commands: "<compilation-database-file>"
  • The codebase section lists platform names and optionally an explicit list of files.
  • Each named platform section references a compilation database (a JSON file) via its commands key. The path is relative to the directory containing the YAML file.
  • The compilation database is a JSON array of objects, each with a command string and a file path (relative to rootdir).

Exclusion Behavior

Files matched by any of the exclude_patterns must be removed from the set of files that are analyzed. Patterns follow git pathspec semantics, evaluated relative to rootdir:

  • Extension globs — e.g. *.f90 excludes every file with that extension, regardless of directory depth.
  • Explicit relative paths — e.g. src/excluded_name.cpp excludes exactly that file, matched relative to rootdir.
  • Directory patterns — e.g. thirdparty/ excludes every file contained (at any depth) within a directory of that name.

Multiple patterns may be supplied together; a file is excluded if it matches any one of them.

Excluded files must not appear in the analysis results produced by the downstream pipeline (finder.find → PlatformMapper.walk).

Downstream Pipeline (already existing, described for context)

After loading, the following sequence produces a mapping from platform sets to file counts:

codebase, configuration = config.load(yaml_path, rootdir, exclude_patterns=excludes)
state = finder.find(rootdir, codebase, configuration)
mapper = PlatformMapper(codebase)
setmap = mapper.walk(state)

setmap is a dictionary whose keys are frozenset objects of platform names and whose values are integer counts of files attributed to that exact set of platforms. Each source file that is analyzed for a single platform "test" contributes 1 to the entry keyed by frozenset(["test"]).

Concrete Expected Results

Given a codebase with four source files all compiled for a single platform named test:

  • src/included.cpp
  • src/excluded_name.cpp
  • src/excluded_extension.f90
  • src/thirdparty/library.cpp

analyzed with rootdir pointing at the directory containing these under src/, the resulting setmap must be:

exclude_patterns Resulting setmap
[] {frozenset(["test"]): 4}
["*.f90"] {frozenset(["test"]): 3}
["src/excluded_name.cpp"] {frozenset(["test"]): 3}
["thirdparty/"] {frozenset(["test"]): 3}
["*.f90", "src/excluded_name.cpp", "thirdparty/"] {frozenset(["test"]): 1}

Each excluded file reduces the count for frozenset(["test"]) by one; the count reflects only the files that remain after exclusion.

Task Specification: TOML Loading and Schema Validation

Objective

Implement a function that loads TOML files and validates their contents against a named JSON schema.

Public API

Add the following function to the module codebasin.util:

def _load_toml(file_object, schema_name):
    ...
Parameters
  • file_object: a binary file object (opened in "rb" mode) containing TOML-formatted text.
  • schema_name: a string naming which schema to validate the parsed contents against. Two schema names must be supported: "cbiconfig" and "analysis".
Return Value

On success, returns the parsed TOML contents as a Python dict (with nested tables represented as nested dicts, arrays as lists, etc.).

Error Behavior

If the parsed contents do not conform to the schema named by schema_name, the function must raise ValueError.

Schema Definitions

"cbiconfig" schema

Describes compiler configuration. The relevant structure exercised is:

  • A top-level compiler table (dict).
  • Each entry under compiler is keyed by a compiler name and maps to a table containing an options field.
  • The options field must be a list of strings.

A document where any options value is not a list of strings (for example, an integer) is invalid and must cause a ValueError.

A document where each compiler entry's options is a list of strings is valid. For example, the following parses successfully and returns:

{
    "compiler": {
        "test_one": {"options": ["TEST_ONE"]},
        "test_two": {"options": ["TEST_TWO"]},
    },
}
"analysis" schema

Describes an analysis configuration. The relevant structure exercised is:

  • A top-level codebase table containing an exclude field, where exclude is a list of strings.
  • A top-level platform table, whose entries are keyed by platform name and each map to a table containing a commands field, where commands is a string.

A valid document parses successfully and returns a dict mirroring the TOML structure. For example, given the appropriate input, the return value is:

{
    "codebase": {
        "exclude": ["*.F90", "*.cu"],
    },
    "platform": {
        "one": {
            "commands": "one.json",
        },
        "two": {
            "commands": "two.json",
        },
    },
}

A document that violates this schema must cause a ValueError.

Supporting Test Data

Create the following TOML data files (used as inputs):

tests/schema/analysis.toml

Valid content conforming to the "analysis" schema:

[codebase]
exclude = [
    "*.F90",
    "*.cu",
]

[platform.one]
commands = "one.json"

[platform.two]
commands = "two.json"
tests/schema/invalid_analysis.toml

Content that parses as TOML but violates the "analysis" schema (i.e., at least one field has a type disallowed by the schema, causing _load_toml(..., "analysis") to raise ValueError).

Note: tests/schema/cbiconfig.toml and tests/schema/invalid_cbiconfig.toml already exist and are not part of this task.

Notes

  • Parsing must accept binary file objects.
  • Validation must distinguish between valid and invalid documents purely by structure/type conformance to the named schema; type mismatches (such as a numeric value where a list or string is required) constitute invalidity.
