02 File Download Directory Handling 694 words · rewritten by GPT-5.6-sol

Task Specification: File Download Directory Handling

Overview

Update the file-download behavior exposed by Job and Batch. Both classes provide a download_files method for downloading job products into a target directory. The required changes govern whether that directory must already exist, whether it may be created, which error is raised for a missing directory, and how expired jobs are handled.

The behavior must remain compatible with the existing Job and Batch APIs apart from the directory-handling requirements described here.

Public API

Job and Batch remain importable from the package's jobs module.

Job.download_files
def download_files(
    self,
    location: Union[Path, str] = Path.cwd(),
    create: bool = True,
) -> List[Path]:
  • location is the directory into which the job's files are downloaded. It accepts either a pathlib.Path or a string.
  • When omitted, location denotes the current working directory.
  • create controls whether a missing target directory is created. It defaults to True.
  • The method returns one Path per downloaded file.
Batch.download_files
def download_files(
    self,
    location: Union[Path, str] = Path.cwd(),
    create: bool = True,
) -> List[Path]:
  • location and create have the same directory semantics as for Job.download_files.
  • The method applies downloading across the jobs in the batch and returns a single combined list of Path objects for the files that were actually downloaded.

Target Directory Behavior

Existing directory

If location names an existing directory, downloads are written directly into it. For each file descriptor, the destination is:

Path(location) / file["filename"]

Each returned value must be a Path identifying that destination, and the written file must contain the body obtained from the file's URL. This behavior must work identically when location is supplied as a string or as a Path.

Missing directory with create=True

If location does not exist and create=True, the directory must be created before downloading. Creation must support missing parent directories as needed, including the ordinary case where the requested directory is a direct child of an existing directory.

Downloads then proceed exactly as for an existing directory, and every returned path is located under the newly created directory.

Missing directory with create=False

If location does not exist and create=False, the operation must raise NotADirectoryError. It must do so before making any file-download request or writing any product file.

For Batch.download_files, this is an operation-level destination error: the invalid destination prevents every member from being downloaded and must not be converted into a skipped-member result.

Expiration Behavior

A job is expired when its expiration time is at or before the current time.

Direct Job download

Calling Job.download_files on an expired job must raise the package's existing HyP3Error. No request may be made to any of that job's file URLs. This remains true regardless of the supplied location or create value; expiration is not treated as a successful empty download.

Expired members of a Batch

An expired member must not cause Batch.download_files to raise HyP3Error for the batch as a whole. Once the batch has a valid target directory, the method must:

  1. skip each expired member without requesting any of its files;
  2. continue processing the remaining unexpired, downloadable members; and
  3. return only the paths downloaded for those remaining members.

Thus a mixture of expired and unexpired jobs produces the same paths and file contents as downloading only the unexpired jobs. If every member is expired, the result is an empty list rather than an expiration error.

Validation and Transfer Guarantees

  • Directory validity and job expiration must be established before any affected network download begins.
  • An invalid batch destination prevents all network downloads for that batch call.
  • An expired direct job performs no network download.
  • In a batch with a valid destination, an expired member performs no network download, but its expiration must not block downloads for other eligible members.
  • Existing URL selection and filename behavior remain unchanged: each job file is fetched from its declared URL and stored under its declared filename.

Scope

The task is limited to Job.download_files and Batch.download_files directory and expiration handling. Preserve all other public behavior and compatibility of these classes.

Part 1: asf_search module

Module constant
  • _SEARCH_API — a string containing the base URL of the ASF search API endpoint. All API requests described below are issued against this URL via HTTP POST, with query parameters appended to the URL.
_get_polarization(polarization: str) -> str

Given a granule's polarization string, return the polarization query value to use when searching for neighboring granules, according to this mapping:

  • 'VV' → 'VV,VV+VH'
  • 'VV+VH' → 'VV,VV+VH'
  • 'HH' → 'HH,HH+HV'
  • 'HH+HV' → 'HH,HH+HV'
  • 'Dual VV' → 'Dual VV'
  • 'Dual VH' → 'Dual VH'
  • 'Dual HH' → 'Dual HH'
  • 'Dual HV' → 'Dual HV'

(In short: 'VV' and 'VV+VH' both collapse to 'VV,VV+VH'; 'HH' and 'HH+HV' both collapse to 'HH,HH+HV'; any other value listed above is returned unchanged.)

get_nearest_neighbors(reference: str, max_neighbors: int = ...) -> list

Given a reference Sentinel-1 granule name, return a list of the granules that immediately precede it in time along the same acquisition stack, ordered from nearest (most recent before the reference) to farthest, limited to at most max_neighbors items.

This must be implemented via two sequential requests to _SEARCH_API:

Step 1 — fetch reference metadata.

Issue a POST to _SEARCH_API with query parameters:

  • output=json
  • granule_list={reference}

The response body is a JSON array whose first element is an array of metadata records for the reference granule. From those records, select the single record whose processingLevel is exactly 'SLC' (ignore any record whose processingLevel is not 'SLC', e.g. 'METADATA_SLC'). Use the fields of that selected record to build the stack query.

Step 2 — fetch the stack.

Issue a POST to _SEARCH_API with query parameters constructed from the selected reference record, in this order:

  • output=jsonlite
  • platform=S1
  • intersectsWith=POINT ({centerLon} {centerLat}) — a WKT point built from the reference record's centerLon then centerLat
  • end={startTime} — the reference record's startTime
  • beamMode={beamMode}
  • flightDirection={flightDirection}
  • processingLevel={processingLevel} — i.e. 'SLC'
  • relativeOrbit={relativeOrbit}
  • polarization= the result of _get_polarization(reference_record['polarization'])
  • lookDirection={lookDirection}

The stack response body is a JSON object with a 'results' key whose value is a list of granule records, each containing a 'startTime' field.

Result computation.

From the stack results:

  • Sort all results in ascending order by startTime.
  • The reference granule corresponds to the entry whose startTime equals the reference's own end time; all granules that come before the reference in the sorted order are the candidate neighbors.
  • Return those preceding neighbors ordered from nearest-to-reference (latest before the reference) to farthest, truncated to at most max_neighbors entries.

Concretely, given stack results with startTime values 1, 5, 4, 2, 3, where the reference's startTime is 5:

  • The neighbors preceding the reference, ordered nearest-first, are the records with startTime 4, 3, 2, 1.
  • With the default limit, the returned list is [{'startTime': 4}, {'startTime': 3}].
  • With max_neighbors=3, the returned list is [{'startTime': 4}, {'startTime': 3}, {'startTime': 2}].

The default value of max_neighbors must yield exactly the two nearest neighbors as shown above. The returned list elements are the raw stack result records (dicts) unchanged.
