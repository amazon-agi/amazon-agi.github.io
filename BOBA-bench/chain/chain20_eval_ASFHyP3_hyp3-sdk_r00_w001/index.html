Public API requirements

The imports and call forms listed below must remain available:

from hyp3_sdk.jobs import Batch, Job
from hyp3_sdk.exceptions import HyP3Error

Job.download_files(self, location='.', create=False) -> list[pathlib.Path]
Batch.download_files(self, location='.', create=False) -> list[pathlib.Path]

The location parameter must accept either a str or pathlib.Path. The create parameter must be accepted as a keyword argument. Calls that leave out create must remain valid.

Batch must support being constructed from a list of Job instances:

Batch([job1, job2, ...])

Job.download_files

Given a successful, unexpired job whose file metadata contains a URL and a filename:

  • Download the content at the URL and write it under location / filename.
  • Return a list of pathlib.Path objects for the files that have been downloaded.
  • A file entry whose metadata size is 0 must still download and write the complete HTTP response body.
  • The download must work with both Path and string destinations.
  • If location is omitted, the current working directory at call time must be used. The returned paths must be anchored to that directory.

Handling of the destination:

  • When the destination directory already exists, downloading must succeed whether or not create is supplied.
  • When the destination does not exist and create=False, raise FileNotFoundError.
  • When the destination does not exist and create=True, create the directory and download the files into it.

Handling of expiration:

  • A timezone-aware ISO-8601 expiration timestamp that lies in the past must be treated as expired.
  • Such a timestamp in the future must be treated as unexpired.
  • download_files must raise hyp3_sdk.exceptions.HyP3Error when called on an expired successful job.
  • There is no requirement for a specific exception message.

Batch.download_files

Given a batch of successful jobs:

  • Download the files from all unexpired jobs into the requested destination.
  • Return a list of pathlib.Path objects for the files downloaded from those jobs.
  • The paths that are returned, along with the file contents, must correspond to each eligible job’s filename and HTTP response body.
  • No particular ordering is required for the returned batch paths.

Handling of the destination must match Job.download_files:

  • With create=False, a missing destination raises FileNotFoundError.
  • With create=True, a missing destination is created, and all eligible files are written beneath it.

Handling of expiration differs from an individual job:

  • An expired job within a batch must not cause the batch operation as a whole to raise HyP3Error.
  • The expired job’s files must be excluded from the returned download results.
  • Processing must continue for the unexpired jobs that appear both before and after the expired job.
02 Directory Handling for File Downloads 769 words · rewritten by GPT-5.6-sol, reworded by GLM-5.3-Flash

Task Specification: Directory Handling for File Downloads

Summary

Change the file-download behavior that Job and Batch expose. Both classes offer a download_files method that downloads job products into a target directory. The required changes cover whether the directory must already exist, whether it may be created, which error is raised when the directory is missing, and the way expired jobs are handled.

With the exception of the directory-handling requirements described here, the behavior must remain compatible with the existing Job and Batch APIs.

Public Interface

Job and Batch remain importable from the jobs module of the package.

Job.download_files
def download_files(
    self,
    location: Union[Path, str] = Path.cwd(),
    create: bool = True,
) -> List[Path]:
  • location designates the directory that the job's files are downloaded into. Either a pathlib.Path or a string is accepted.
  • When the argument is omitted, location refers to the current working directory.
  • The create argument determines whether a missing target directory is created; its default value is True.
  • The method returns one Path for each downloaded file.
Batch.download_files
def download_files(
    self,
    location: Union[Path, str] = Path.cwd(),
    create: bool = True,
) -> List[Path]:
  • location and create carry the same directory semantics they have for Job.download_files.
  • Downloading is applied across the jobs in the batch, and the method returns a single combined list of Path objects for the files that were actually downloaded.

Behavior of the Target Directory

Directory that already exists

When location names a directory that exists, the downloads are written directly into it. The destination for each file descriptor is:

Path(location) / file["filename"]

Each value returned must be a Path that identifies that destination, and the file that gets written must contain the body obtained from the file's URL. This behavior must work identically whether location is supplied as a string or as a Path.

Missing directory when create=True

When location does not exist and create=True, the directory must be created before any downloading takes place. The creation must support missing parent directories as needed, including the ordinary case in which the requested directory is a direct child of an existing directory.

Downloading then proceeds exactly as it does for an existing directory, and every path that is returned is located under the newly created directory.

Missing directory when create=False

When location does not exist and create=False, the operation must raise NotADirectoryError. It must do so before any file-download request is made or any product file is written.

In the case of Batch.download_files, this is an operation-level destination error: the invalid destination prevents every member from being downloaded, and it must not be converted into a skipped-member result.

Expiration Handling

A job counts as expired when its expiration time is at or before the current time.

Downloading a Job directly

If Job.download_files is called on an expired job, the call must raise the package's existing HyP3Error. No request may be made to any of the file URLs of that job. This holds regardless of which location or create value is supplied; expiration is not treated as a successful empty download.

Expired members within a Batch

An expired member must not make Batch.download_files raise HyP3Error for the batch as a whole. As soon as the batch has a valid target directory, the method must:

  1. skip each expired member without requesting any of that member's files;
  2. keep processing the remaining unexpired, downloadable members; and
  3. return only the paths that were downloaded for those remaining members.

Accordingly, a mixture of expired and unexpired jobs results in the same paths and file contents as downloading only the unexpired jobs. When every member is expired, the result is an empty list instead of an expiration error.

Guarantees for Validation and Transfer

  • Whether the directory is valid and whether the job has expired must be established before any affected network download begins.
  • When a batch destination is invalid, all network downloads for that batch call are prevented.
  • For an expired direct job, no network download is performed.
  • Within a batch whose destination is valid, an expired member performs no network download, but its expiration must not block downloads for other eligible members.
  • The existing behavior for URL selection and filenames remains unchanged: each job file is fetched from its declared URL and stored under its declared filename.

Scope of the Task

The task is limited to the directory and expiration handling of Job.download_files and Batch.download_files. All other public behavior and compatibility of these classes must be preserved.

Task Description

Part 1: the asf_search module

The following module-level constant and functions must be exposed by the module hyp3_sdk.asf_search (importable as asf_search).

Module-level constant
  • _SEARCH_API — a string holding the base URL of the ASF search API endpoint. All API requests described below are made against this URL via HTTP POST, and query parameters are appended to the URL.
_get_polarization(polarization: str) -> str

This function takes a granule's polarization string and returns the polarization query value to use when searching for neighboring granules, per this mapping:

  • 'VV' → 'VV,VV+VH'
  • 'VV+VH' → 'VV,VV+VH'
  • 'HH' → 'HH,HH+HV'
  • 'HH+HV' → 'HH,HH+HV'
  • 'Dual VV' → 'Dual VV'
  • 'Dual VH' → 'Dual VH'
  • 'Dual HH' → 'Dual HH'
  • 'Dual HV' → 'Dual HV'

(To sum up: 'VV' and 'VV+VH' both collapse to 'VV,VV+VH'; 'HH' and 'HH+HV' both collapse to 'HH,HH+HV'; any of the other values listed above is returned unchanged.)

get_nearest_neighbors(reference: str, max_neighbors: int = ...) -> list

For a given reference Sentinel-1 granule name, this function returns a list of the granules that immediately precede it in time along the same acquisition stack, ordered from nearest (most recent before the reference) to farthest, limited to at most max_neighbors items.

The implementation must make two sequential requests to _SEARCH_API:

Step 1 — obtain the reference metadata.

Send a POST request to _SEARCH_API with the query parameters:

  • output=json
  • granule_list={reference}

The body of the response is a JSON array whose first element is an array of metadata records for the reference granule. Out of those records, choose the single record whose processingLevel is exactly 'SLC' (any record whose processingLevel is not 'SLC', e.g. 'METADATA_SLC', is ignored). The stack query is built from the fields of that selected record.

Step 2 — obtain the stack.

Send a POST request to _SEARCH_API with query parameters built from the selected reference record, in this order:

  • output=jsonlite
  • platform=S1
  • intersectsWith=POINT ({centerLon} {centerLat}) — a WKT point formed from the reference record's centerLon followed by centerLat
  • end={startTime} — set to the reference record's startTime
  • beamMode={beamMode}
  • flightDirection={flightDirection}
  • processingLevel={processingLevel} — that is, 'SLC'
  • relativeOrbit={relativeOrbit}
  • polarization= the result of calling _get_polarization(reference_record['polarization'])
  • lookDirection={lookDirection}

The body of the stack response is a JSON object that has a 'results' key; the key's value is a list of granule records, each of which contains a 'startTime' field.

Computing the result.

Working from the stack results:

  • Sort all of the results in ascending order by startTime.
  • The entry whose startTime equals the reference's own end time corresponds to the reference granule; the candidate neighbors are all granules that come before the reference in the sorted order.
  • Return those preceding neighbors ordered from nearest-to-reference (latest before the reference) to farthest, cut down to at most max_neighbors entries.

As a concrete case, take stack results with startTime values 1, 5, 4, 2, 3, where the reference's startTime is 5:

  • The records with startTime 4, 3, 2, 1 are the neighbors that precede the reference, ordered nearest-first.
  • Under the default limit, the returned list is [{'startTime': 4}, {'startTime': 3}].
  • When max_neighbors=3, the returned list is [{'startTime': 4}, {'startTime': 3}, {'startTime': 2}].

The default max_neighbors value must yield exactly the two nearest neighbors, as shown above. The elements of the returned list are the raw stack result records (dicts), unchanged.

1. asf_search.get_nearest_neighbors

Constant at module level

Signature of the function
def get_nearest_neighbors(reference: str, max_neighbors: int = ...) -> list:

Behavior

To obtain a baseline stack for the supplied reference granule, the function sends an HTTP GET request to _BASELINE_API.

The response is a JSON object of this form:

Every entry in results contains an integer field 'temporalBaseline' (that granule's temporal baseline relative to the reference, in days). The baseline may be positive or negative.

  • With max_neighbors=3: the entries for [-12, -24, -60] are returned.

get_nearest_neighbors(reference, max_neighbors=2)

Returns a list of scene metadata dictionaries for the acquisitions earlier than a given reference scene that are temporally nearest to it.

Function signature
  • reference: a string granule name that identifies the reference scene.
  • max_neighbors: an integer giving the maximum number of neighbors to return; the default is 2.
Step 1 — Fetch the reference metadata

Send an HTTP POST request to the ASF Search API to retrieve the reference scene's metadata. The request URL is:

{_SEARCH_API}?output=json&granule_list={reference}

The response is JSON: a list whose first element is a list of scene records. Each record is a dict that may contain the keys: centerLon, centerLat, startTime, beamMode, flightDirection, processingLevel, relativeOrbit, polarization, lookDirection.

From that first list of records, pick the record whose processingLevel is exactly SLC (records with other processing levels such as METADATA_SLC must be ignored); that record then serves as the reference metadata.

Step 2 — Build and send the stack query

Draw on the fields of the selected reference record to send an HTTP POST request to the ASF Search API that finds the stack of matching scenes. The request URL must be assembled from exactly the following query parameters, in this order:

{_SEARCH_API}?output=jsonlite&platform=S1&intersectsWith=POINT (<centerLon> <centerLat>)&end=<startTime>&beamMode=<beamMode>&flightDirection=<flightDirection>&processingLevel=<processingLevel>&relativeOrbit=<relativeOrbit>&polarization=<normalized polarization>&lookDirection=<lookDirection>

Here:

  • platform takes the literal value S1.
  • output takes the literal value jsonlite.
  • intersectsWith is a WKT POINT (<centerLon> <centerLat>) constructed from the reference record's centerLon and centerLat.
  • end is the reference record's startTime value.
  • beamMode, flightDirection, processingLevel, relativeOrbit, lookDirection are taken directly from the reference record.
  • polarization is the reference record's polarization passed through _get_polarization.

(These parameter values must be URL-encoded the way query strings normally are, e.g. spaces and + and , appropriately encoded.)

Step 3 — Choose and order the neighbors

The stack query returns JSON in the form {'results': [ ... ]}; each element of results is a scene metadata dict that contains at least a startTime field (that value is the sort key described below).

Out of the returned results:

  • Arrange the scenes so that those temporally closest to the reference come first (i.e., sorted in descending order of startTime, most recent first).
  • From that ordering, return at most max_neighbors scenes.

The result is a list of the selected scene dicts in the described nearest-first order. If fewer scenes are available than max_neighbors, return all of the available scenes.

Worked ordering example

For results whose startTime values are [1, 5, 4, 2, 3]:

  • With max_neighbors=2 → the two scenes having startTime 4 then 3.
  • With max_neighbors=3 → the scenes having startTime 4, then 3, then 2.

(Note: in this example the scene holding the largest startTime value, 5, is excluded — the returned set starts after the top-most entry and continues in descending order.)
