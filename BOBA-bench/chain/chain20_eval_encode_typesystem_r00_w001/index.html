01 The task is to extend typesystem, an existing validation/schema library. 610 words · source specification, reworded by GLM-5.3-Flash

Overview

The task is to extend typesystem, an existing validation/schema library. The following two pieces of behavior must be implemented:

  1. A string representation for validation errors that is human-readable.
  2. A new field type, typesystem.Nested, meant for embedding one schema inside another.

Context Provided by the Existing Library

The library exposes the following:

  • typesystem.Schema — a base class; user schemas are derived from it by declaring field attributes at the class level.
  • Field types are provided, such as typesystem.String(max_length=...), typesystem.Integer(), and typesystem.Date(default=...).
  • Schema classes provide a classmethod validate_or_error(data) that returns an object with .value and .error attributes (which can also be unpacked as value, error = ...), plus a classmethod validate(data) that returns the validated value directly.
  • The field types themselves have a .validate_or_error(value) method as well, which returns the same kind of result object.
  • Validation errors expose a .messages() method, which returns a list of message objects.
  • Schema instances are constructed using keyword arguments that match the declared fields, they support equality comparison, and they can be converted to a plain dict using dict(instance).

Requirement 1: String representation for validation errors

The error object returned in the .error attribute of a failed validation result must support str(), such that:

  • When the error represents a single, top-level (non-keyed) message: the message text itself, in plain form.

    • Example: a string of length 100, when validated against typesystem.String(max_length=10), fails; str(error) must equal "Must have no more than 10 characters."

  • When the error represents one or more field-keyed messages: the str() of a dict that maps each field key to its message text.

    • Example: data that is missing the required field b fails when validated; str(error) must equal "{'b': 'This field is required.'}"

In the dict form, the field key (a string) is mapped to the message text (a string) for each contained message.

Requirement 2: The typesystem.Nested field type

A new field type is to be added, accessible as typesystem.Nested.

Signature
typesystem.Nested(schema)

Here schema is a subclass of typesystem.Schema.

Behavior

When a Nested(SomeSchema) field is used as a field within a schema, it validates its input value by delegating to SomeSchema. When given a valid input, the nested field produces a validated instance of the referenced schema.

Concretely: when a schema declares a nested field and validation runs on input in which that field's value is a mapping suitable for the nested schema, the following holds:

  • The nested mapping is validated/coerced by the referenced schema (including any type coercion that its own fields perform).
  • The resulting attribute on the parent validated instance is an instance of the referenced schema.
  • Two parent instances constructed with equal nested-schema instances will compare equal.
  • When the parent instance is converted to a dict, the nested value is likewise yielded as a plain dict.
Example of the required behavior
class Artist(typesystem.Schema):
    name = typesystem.String(max_length=100)

class Album(typesystem.Schema):
    title = typesystem.String(max_length=100)
    release_year = typesystem.Integer()
    artist = typesystem.Nested(Artist)

value = Album.validate(
    {"title": "Double Negative", "release_year": "2018", "artist": {"name": "Low"}}
)

After this code has run:

  • dict(value) equals {"title": "Double Negative", "release_year": 2018, "artist": {"name": "Low"}} (note that release_year gets coerced to the integer 2018, and that the nested value comes out rendered as a plain dict).
  • value equals Album(title="Double Negative", release_year=2018, artist=Artist(name="Low")).

Summary of the Public API

  • typesystem.Nested(schema) — a new field type, importable from the top-level typesystem package.
  • The error object that failed validations return must implement __str__ in the manner described in Requirement 1.

Do not add any behavior beyond what is described above.

Task Specification: Implementing an Array Field Validator

Overview

A new field validator class named Array is to be added to the typesystem.fields module. It must be importable in the following way:

from typesystem.fields import Array

Public API

The Array class

Constructor signature (all parameters can be passed by keyword, and all of them are optional):

Array(allow_null=False, min_items=None, max_items=None, exact_items=None)
The validate_or_error(value) method

The method returns a two-tuple (value, error):

  • In the success case: (validated_value, None).
  • In the failure case: (None, error), where error is a typesystem.base.ValidationError instance.

A ValidationError is constructed using the keyword arguments text and code, e.g. ValidationError(text="...", code="...").

Validation Behavior That Is Required

The validation must be applied to the input value and must produce the following results.

Handling of null values
  • If value is None and allow_null is False (the default): return an error that has text="May not be null." and code="null".
  • If value is None and allow_null is True: return (None, None) — in other words, None is accepted as a valid value.
Type checks
  • If value is not an array/list (for example, an integer): return an error that has text="Must be an array." and code="type".
  • A list is a valid type for an array.
min_items
  • If min_items is set and the array contains fewer items than min_items:
    • When min_items is 1 and the array is empty: return an error that has text="Must not be empty." and code="empty".
    • In any other case (i.e. min_items >= 2): return an error that has text="Must have at least {min_items} items." and code="min_items".
  • If the array meets or exceeds min_items: this check passes, and the original list value is returned.
max_items
  • If max_items is set and the array contains more items than max_items: return an error that has text="Must have no more than {max_items} items." and code="max_items".
  • If the array has max_items or fewer items (including an empty array): this check passes.
exact_items
  • If exact_items is set and the array has exactly that many items: this check passes, and the original list value is returned.
  • If exact_items is set and the array does not have exactly that many items: return an error that has text="Must have {exact_items} items." and code="exact_items".
Result on success
  • When validation succeeds, the returned value is the input list itself (its content is unchanged and it is equal to the input list, e.g. [], [1], [1, 2]).

Notes About Text Formatting

In the numeric messages, the configured limit is substituted directly: with min_items=2 the text is "Must have at least 2 items.", with max_items=2 the text is "Must have no more than 2 items.", and with exact_items=2 the text is "Must have 2 items.".

Equality

ValidationError instances must compare equal whenever their text and code match, so that a returned error equals a newly constructed ValidationError with the same text and code.

Additionally, remove the previously existing Object.coerce behavior/method (drop it from the codebase); no test relies on it.

Task: Add support for items and additional_items to the Array validator

Background

An Array validator class is used for validating list values. The constructor keyword arguments it currently supports include exact_items (which enforces that the input has exactly a given number of elements, producing a ValidationError with text "Must have 2 items." and code "exact_items" when violated).

The Array validator must be extended to accept two new constructor keyword arguments: items and additional_items.

Public interface

The Array class must accept the following keyword arguments, on top of the ones it already supports:

  • items: either a single validator instance, or a list of validator instances.
  • additional_items: a single validator instance.

The other validators referenced here, Integer and String, are available in the same module/namespace. Validation is carried out through the existing validate_or_error(value) method, which returns a (value, error) tuple in which error is a ValidationError (or None on success) and value is the coerced/validated result (or None on error).

Behavior requirements

items given as a single validator

If items is a single validator instance, that validator is used to validate (and coerce) every element of the input list.

  • On success, the value that gets returned is a list of the individually coerced values of the elements, in order.
    • Example: validating ["1", 2, "3"] with Array(items=Integer()) yields the value [1, 2, 3] (element validators coerce their inputs).
  • On failure, the error must be a ValidationError whose items are keyed by the integer index of each failing element, with each key mapping to that element's error message.
    • Example: validating ["a", 2, "c"] with Array(items=Integer()) yields an error equivalent to {0: "Must be a number.", 2: "Must be a number."} (i.e. dict(error) equals that mapping). Only failing elements appear in it; elements that pass are left out of the error mapping.
items given as a list of validators (positional/tuple validation)

If items is a list of validator instances, the validator at each position in the list validates the input element at the corresponding position.

  • Unless additional_items is supplied (see below), the input list must contain exactly as many elements as there are validators in the items list. If the count does not match, a ValidationError must be produced with text "Must have N items." and code "exact_items", where N is the number of validators in the items list.
    • Example: validating ["a", "b", "c"] (3 elements vs 2 validators) with Array(items=[String(), Integer()]) yields the exact-items error with text "Must have 2 items." and code "exact_items".
  • When the counts match, each element is validated/coerced by the validator at its position, and the value that gets returned is the list of coerced element values, in order.
    • Example: validating ["a", "123"] with Array(items=[String(), Integer()]) yields the value ["a", 123].
items (list) used together with additional_items

If items is a list of validators and additional_items (a single validator) is supplied as well, the input list may contain more elements than there are validators in items. The elements that come first are validated positionally by the items validators, while every remaining (extra) element is validated/coerced by the additional_items validator.

  • The value that gets returned is a list of all the coerced element values, in order.
    • Example: validating ["a", "123", "456"] with Array(items=[String(), Integer()], additional_items=Integer()) yields the value ["a", 123, 456].

Notes

  • The existing behavior of Array (including exact_items on its own) must continue to work unchanged.

07 You will be working on typesystem, a Python library for data validation. 606 words · source specification, reworded by GLM-5.3-Flash

Specification of the Task

You will be working on typesystem, a Python library for data validation. Two areas are addressed by this task: the Choice field validator, and the "required-ness" behavior that fields exhibit when they are used inside a schema.

Part 1: The Choice field

The Choice validator — built via Choice(...) and importable from wherever the other field validators are located — must accept its choices argument as a list of two-tuples, each tuple holding a (key, display_value) pair. As an example:

Choice(choices=[("R", "red"), ("B", "blue"), ("G", "green")])

For a Choice constructed in this way, validation behaves as follows:

  • A call to validator.validate_or_error(x) returns a (value, error) pair.
  • Validation succeeds when x matches one of the keys (the first element of a tuple); the returned value is then that key, and error is None.
  • Validation fails when x does not match any of the keys; value is then None, and error equals ValidationError(text="Not a valid choice.", code="choice").

How nulls are handled:

  • Passing None results in failure by default, with error equal to ValidationError(text="May not be null.", code="null").
  • If allow_null=True was used at construction time, passing None succeeds: value is None and error is None.

Part 2: The "required-ness" of fields inside schemas

A field is declared by making it a class attribute of a subclass of typesystem.Schema. typesystem.Integer(...) and typesystem.String(...) are the field types relevant here. To validate a schema, the class method Example.validate_or_error(data) is called, and it returns a (value, error) pair. When validation succeeds, value is a mapping-like object that can be converted via dict(value); when validation fails, error is a mapping-like object that can be converted via dict(error), whose entries map field names to error message strings.

Validating an empty input {} — that is, the field is absent — must produce the following behavior:

Integer fields
  • With typesystem.Integer(), the field is required: validation fails, and the error maps {"field": "This field is required."} (the field's attribute name serving as the key).
  • With typesystem.Integer(allow_null=True), the field is not required: when the value is missing, None is produced; validation succeeds with {"field": None}.
  • With typesystem.Integer(default=0), the field is not required: when the value is missing, the default is used; validation succeeds with {"field": 0}.
  • With typesystem.Integer(allow_null=True, default=0), the field is not required: the default is what takes effect, not null; validation succeeds with {"field": 0}.
String fields
  • With typesystem.String(), the field is required: validation fails with {"field": "This field is required."}.
  • With typesystem.String(allow_blank=True), the field is not required: when the value is missing, the empty string is produced; validation succeeds with {"field": ""}.
  • With typesystem.String(allow_null=True, allow_blank=True), the field is not required: when the value is missing, None is produced; validation succeeds with {"field": None}.
The required-ness rule, summarized

A field counts as required (missing value ⇒ "This field is required.") unless one of the items below makes it optional; when that happens, a missing value resolves as stated:

  • A default has been supplied ⇒ the missing value resolves to that default (this takes precedence over null).
  • allow_null=True (and no default) ⇒ the missing value resolves to None.
  • For a String, allow_blank=True (and no default, and not resolved to null) ⇒ the missing value resolves to the empty string "".

When several of these are set, the precedence is as follows: a default that has been supplied wins; otherwise, a String having both allow_null=True and allow_blank=True resolves a missing value to None.

For a required field that is missing, the error message string must be exactly "This field is required.".

The Nested field embeds another schema; the schema class to nest is its first positional argument.

The following validation entry points are exposed by schema classes:

  • Schema.validate_or_error(data) → returns a two-tuple (value, error). On success, error is falsy and value is the validated schema instance. On failure, value is falsy, and error is an error object that supports dict(error), which produces a mapping from field name to error message string.

Behavior with allow_null=False (the default)

For a Nested field on which allow_null is not set (or is set to False), given input data in which the corresponding field:

  • is None: validation must fail, and the message "May not be null." must be the error mapping for that field.
  • is present but is not an object/mapping (for example, a plain string): validation must fail, and the message "Must be an object." must be the error mapping for that field.
Behavior with allow_null=True

class Artist(typesystem.Schema):

Your task is to implement validation field classes within a validation library. These field classes reside in a module that can be imported as the package's public API (the same location from which String, Integer, and Choice can already be imported, as well as a ValidationError type).

There is a method that each validator exposes:

This method returns a tuple (value, error). If validation succeeds, error is None and value is the validated/coerced result; if validation fails, value is None and error is a ValidationError.

ValidationError instances can be compared for equality and are constructed with the keyword arguments text (a human-readable message) and code (a short machine code).

The change to be implemented introduces lenient casting between null and empty string when strict=False (the default), along with a numeric-string coercion for integers. The specific behaviors that are required appear below.

String

The constructor accepts the keyword arguments allow_blank and allow_null (among its existing options), both of which default in such a way that neither is enabled unless passed.

  • String(allow_blank=True):
    • Validation of "" returns ("", None).
    • Validation of None returns ("", None) — this is lenient coercion of a null input to the empty string.
  • String(allow_null=True):
    • Validation of None returns (None, None).
    • Validation of "" returns (None, None) — an empty string undergoes lenient coercion to null.
    • Validation of a string that contains only whitespace, e.g. " ", returns (None, None) — a blank string undergoes lenient coercion to null.

Integer

The default constructor Integer():

  • Validation of the string "123.0" returns (123, None) — a numeric string with an integral value is coerced to the integer 123.
  • Validation of None returns an error equal to ValidationError(text="May not be null.", code="null").

The Integer(allow_null=True) constructor:

  • Validation of "" (with the default strict=False) returns (None, None) — an empty string undergoes lenient coercion to null.
  • Validation of "" with strict=True returns an error equal to ValidationError(text="Must be a number.", code="type") — in strict mode the empty string is not coerced to null and is handled as an invalid number.

Choice

The constructor accepts a choices argument (a list of (value, label) pairs) together with an allow_null keyword.

  • Choice(choices=[("R", "red"), ("B", "blue"), ("G", "green")], allow_null=True):
    • Validation of "" returns (None, None) — the empty string is leniently coerced to null, as "" is not one of the choices.
  • Choice(choices=[("", "empty"), ("R", "red"), ("B", "blue"), ("G", "green")], allow_null=True):
    • Validation of "" returns ("", None) — as "" is itself a valid choice, it is accepted as-is instead of being coerced to null.

With strict=False (the default):

  • When a validator is configured with allow_null=True, an empty or blank string input is coerced to None whenever that input is not otherwise a valid value.
  • When String is configured with allow_blank=True, a None input is coerced to "".

2. The token tree (typesystem.tokenize.tokens)

Parsed values are represented by three token classes. Every token stores its parsed Python value along with two 0-based character offsets into the original source: start_index, the index of the first character in the token's textual span, and end_index, the index of the last character in that span, inclusive.

The constructors:

  • ScalarToken(value, start_index, end_index) — a leaf token standing for a string, number, boolean, or None.
  • DictToken(value, start_index, end_index) — here value is a dictionary that maps ScalarToken keys to child tokens.
  • ListToken(value, start_index, end_index) — here value is a list whose entries are child tokens.

These constructor forms must stay directly usable. Tokens returned by a tokenizer must also retain knowledge of the original content, so that source substrings and positions can be computed. The manner in which that association is represented is not prescribed.

Shared token behavior
  • token.value returns the plain Python value in fully materialized form, obtained by recursively unwrapping the token tree. For a DictToken this is a plain dictionary whose keys are the scalar key values and whose values are the recursively unwrapped child values. For a ListToken it is a plain list. For a ScalarToken it is the scalar value.
  • token.string is exactly the source substring content[start_index:end_index + 1].
  • token.start is the Position that corresponds to start_index.
  • token.end is the Position that corresponds to end_index.
  • For each returned position, char_index is equal to the corresponding token index. Line 1, column 1 corresponds to character index 0. A newline increments the line number, and the first character on each new line is column 1.
  • Two tokens are equal when they belong to the same class, have equal token structure, and have equal start_index and end_index. Nested tokens are compared recursively, their own spans included.

  • If value does not satisfy the schema, error must be a non-None object.

A keyword argument strict (which will be passed as True) must be accepted by the method. It is required to be present in the signature.

Semantics of Validation

Only numeric input values (integers and floats) are subject to the schema keywords. For any input value that is not a number, these keywords are all ignored and the value is regarded as valid (error is None).

When the input value is numeric, each keyword that is present constrains the value in the following way:

  • minimum: N — the value is valid only when value >= N. Values equal to N are valid; values below N are invalid.
  • maximum: N — the value is valid only when value <= N. Values equal to N are valid; values above N are invalid.
  • exclusiveMinimum: N — the value is valid only when value > N. Values equal to N are invalid, and values below N are invalid as well.
  • exclusiveMaximum: N — the value is valid only when value < N. Values equal to N are invalid, and values above N are invalid as well.

The keyword values may be floating-point numbers (e.g. 3.0, 1.1); in addition, the comparisons must work correctly against both integer and float input values.

Examples of the Expected Behavior

  • For the schema {"maximum": 3.0}: input 2.6 → valid; input 3.0 → valid; input 3.5 → invalid; input "x" → valid (the non-number is ignored).
  • For the schema {"minimum": 1.1}: input 2.6 → valid; input 1.1 → valid; input 0.6 → invalid; input "x" → valid.
  • For the schema {"exclusiveMaximum": 3.0}: input 2.2 → valid; input 3.0 → invalid; input 3.5 → invalid; input "x" → valid.
  • For the schema {"exclusiveMinimum": 1.1}: input 1.2 → valid; input 1.1 → invalid; input 0.6 → invalid; input "x" → valid.

Required Validation Semantics

The from_json_schema function must interpret each of the following JSON Schema constructs correctly. For each keyword, behavior is defined by the JSON Schema semantics; the keywords listed below are the only ones in scope.

Boolean Schemas
  • Every input value is accepted by a schema of True (validation always succeeds).
  • Every input value is rejected by a schema of False (validation always fails).
Numeric Keywords (applied when the instance is numeric)
  • minimum: the value must be greater than or equal to the given number.
  • maximum: the value must be less than or equal to the given number.
  • exclusiveMinimum: the value must be strictly greater than the given number.
  • exclusiveMaximum: the value must be strictly less than the given number.
  • multipleOf: the value must be an exact integer multiple of the given number.
String Keywords (applied when the instance is a string)
  • minLength: the length of the string must be greater than or equal to the given integer.
  • maxLength: the length of the string must be less than or equal to the given integer.
  • pattern: the string must match the given regular expression (unanchored search semantics, as specified by JSON Schema).
Array Keywords (applied when the instance is an array)
  • minItems: the array must contain at least the given number of items.
  • maxItems: the array must contain at most the given number of items.
Object Keywords (applied when the instance is an object)
  • minProperties: the object must have at least the given number of properties.
  • maxProperties: the object must have at most the given number of properties.
  • required: the object must contain all of the listed property names as keys.
Overall Semantics
  • A keyword that constrains one specific JSON type (numeric, string, array, object) applies only when the instance is of that type. Instances of other types are not constrained by keywords that do not apply to them (i.e., such a keyword neither rejects a value of an unrelated type nor is triggered by it).
  • A schema may bring multiple keywords together; for validation to succeed, the instance must satisfy all of the applicable constraints.

Semantics of validation:

  • A value is valid if it validates successfully against at least one of the sub-validators that were provided; the coerced value from that successful validation is returned.

Goal

Write a function that turns a JSON Schema definition into a validator object that is able to validate data against that schema. This task extends the existing JSON Schema support so that the items keyword for array validation is handled correctly.

    • When validation fails, error is a non-None object that describes the failure, and value is None.
  • strict parameter: When True, validation is carried out without permissive type coercion (values must already match their expected types).

Required Behavior: Support for the items Keyword

In addition to the JSON Schema keywords already supported by the existing code, the implementation must support the JSON Schema items keyword for validating arrays. Both forms that the JSON Schema specification defines are included:

1. items given as a single schema (list validation)

When items is a single schema (a dictionary or boolean), every element of an array being validated must satisfy that schema independently.

  • An array is validated successfully only if all of its elements validate against the items schema.
  • If any element fails to validate against the items schema, the array fails validation.
  • Validation of an empty array succeeds.
  • A boolean items schema follows the JSON Schema semantics: true accepts any element; false rejects any element (meaning any non-empty array fails, and an empty array passes).
2. items given as an array of schemas (tuple validation)

When items is an array of schemas, each schema applies positionally to the element found at the same index in the array being validated.

  • The element found at index i must validate against the i-th schema in the items array.
  • If the array being validated is longer than the items array, the extra trailing elements are not constrained by items (with respect to this keyword, they validate successfully).
  • If the array being validated is shorter than the items array, only the positions that are present are checked; the missing positions impose no failure from this keyword.
  • The array fails validation if any positionally-matched element fails to validate against its corresponding schema.

Constraints

  • All other JSON Schema keywords already handled by the existing implementation must have their behavior preserved unchanged.
  • Under strict=True, validation must operate correctly: this means input data types are not coerced and must already conform to the expected structure and element types.

Goal

Public API

def from_json_schema(schema) -> <validator>:

JSON Schema Keywords That Must Be Supported

The validators produced by from_json_schema must show accept/reject behavior that conforms to the JSON Schema specification for the following features:

Boolean schemas
  • When the schema value is true (Python True), every instance must be accepted.
  • When the schema value is false (Python False), every instance must be rejected.
  • Wherever a subschema is expected (e.g. as the value of additionalProperties, additionalItems, or an entry in properties/patternProperties), these boolean schemas must also be honored.
type
  • Restricts the instance to one or more of the JSON primitive types: "null", "boolean", "object", "array", "number", "integer", "string".
  • It may be given as a single type string or as an array of type strings (the instance is valid if it matches any type in the list).
  • Numbers with integer values (e.g. 1.0) must satisfy "integer"; both integers and floats are accepted by "number".
  • Booleans must not be regarded as valid numbers/integers, and numbers must not be regarded as booleans.
required
  • For objects, this keyword lists the property names that must be present.
  • Instances that are not objects remain unaffected by this keyword.
properties
  • Associates property names with subschemas. If a listed property is present in an object instance, its value must validate against the corresponding subschema.
  • The absence of a property is not, by itself, an error (unless required elsewhere).
  • These subschemas may be boolean schemas.
patternProperties
  • Associates regular-expression patterns with subschemas. For each object property whose name matches a pattern, the value of that property must validate against the corresponding subschema.
  • A property name may match multiple patterns, and in that case it must satisfy all of the matching subschemas.
  • These subschemas may be boolean schemas.
additionalProperties
  • Governs object properties that are neither covered by properties (by exact name) nor matched by any patternProperties pattern.
  • When it is a subschema, each such additional property value must validate against it.
  • When it is false, no additional properties are permitted.
  • When it is true (or absent), additional properties are unrestricted.
additionalItems
  • This keyword is relevant only when items is an array of subschemas (positional/tuple validation), and it controls array elements at positions beyond those covered by the items array.
  • When it is a subschema, each such extra element must validate against it.
  • When it is false, no extra elements beyond the items array are permitted.
  • When it is true (or absent), extra elements are unrestricted.
  • If items is a single subschema (not an array), additionalItems has no effect.
pattern
  • For string instances, the string must contain a match for the given regular expression (using the unanchored match semantics of JSON Schema).
  • Non-string instances are left unaffected by this keyword.

  • No constraints are imposed by keywords that a schema does not contain.
  • When multiple keywords appear in the same schema, all of them must be satisfied simultaneously.
  • A keyword must not reject instances whose type is irrelevant to it (e.g. a number instance against properties).
  • The conversion must handle schemas supplied as nested dict/bool structures at any depth reachable through the supported keywords.

  • The maximum keyword must be supported. A numeric instance is valid only when its value is less than or equal to the specified maximum, and the bound is inclusive. Non-numeric instances, including booleans, are unaffected by this keyword.
  • The minItems keyword must be supported. An array instance is valid only when its number of elements is greater than or equal to the specified non-negative integer. Non-array instances are not affected.

  • These keywords must be honored both at the top level and in every nested subschema, including the schemas used by properties, patternProperties, positional or single-schema items, additionalProperties, and additionalItems.

Task Specification: Supporting the default and uniqueItems Keywords in JSON Schema Validation

Overview

Your task is to extend a JSON Schema validator so that two further JSON Schema keywords, default and uniqueItems, are handled correctly. The validator is tested against the standard JSON Schema test-suite draft data files default.json and uniqueItems.json, and the validation results it produces must match the expected outcomes defined by those standard suites.

Behavior Requirements

default keyword

The presence of the default keyword must have no effect on validation. If a schema includes a default key (at any level), that key's presence must never make an instance count as invalid, and it must never cause an otherwise-invalid instance to count as valid. To put it another way, default is purely annotative: it is ignored entirely during validation — any instance value is acceptable with respect to a default keyword.

This holds regardless of:

  • What value default has (object, array, scalar, etc.).
  • The place where default occurs in the schema (top-level or nested inside properties/items).
uniqueItems keyword

The uniqueItems keyword places constraints on array instances:

  • If uniqueItems is true, an array instance is valid only if all of its elements are unique (no two elements are equal). The array is invalid whenever any two elements are equal.
  • If uniqueItems is false, no constraint is imposed by the keyword; any array (including one with duplicate elements) is valid.
  • If the instance is not an array, uniqueItems places no constraint on it; the instance is valid with respect to this keyword.

Equality and uniqueness must be governed by JSON value semantics:

  • Two values are considered equal only if they share the same JSON type and are structurally equal. Specifically:
    • The values true (boolean) and 1 (number) are not equal.
    • The values false (boolean) and 0 (number) are not equal.
    • The values 1 (integer) and 1.0 (number) are equal (numeric equality).
  • Objects count as equal when they contain the same set of keys with pairwise-equal values, regardless of key order.
  • Arrays count as equal when they have the same length and pairwise-equal elements in order.
  • Nested objects and arrays are compared recursively by applying these same rules.
  • Duplicate detection must work for all JSON types, nested composite structures included.

Public API

The validation entry point already used by the existing supported keywords (e.g. type, required, boolean_schema) must now also process the default and uniqueItems keywords correctly. This task introduces no new public modules, classes, or functions; the existing schema-validation surface must simply be extended to cover the two keywords described above, so that validating an instance against a schema returns the correct valid/invalid result for schemas using default and uniqueItems.
