01 You will extend an existing validation/schema library named typesystem. 534 words · source specification

Overview

You will extend an existing validation/schema library named typesystem. Two pieces of behavior must be implemented:

  1. A human-readable string representation for validation errors.
  2. A new field type, typesystem.Nested, for embedding one schema inside another.

Existing Context

The library exposes:

  • typesystem.Schema — a base class from which user schemas are derived by declaring class-level field attributes.
  • Field types such as typesystem.String(max_length=...), typesystem.Integer(), and typesystem.Date(default=...).
  • Schema classes have a classmethod validate_or_error(data) returning an object with .value and .error attributes (also unpackable as value, error = ...), and a classmethod validate(data) returning the validated value directly.
  • Field types themselves have a .validate_or_error(value) method returning the same kind of result object.
  • Validation errors expose a .messages() method returning a list of message objects.
  • Schema instances are constructed with keyword arguments matching declared fields, support equality comparison, and can be converted to a plain dict via dict(instance).

Requirement 1: String representation of validation errors

The error object returned in the .error attribute of a failed validation result must support str(), producing:

  • When the error describes a single, top-level (non-keyed) message: the plain message text itself.

    • Example: validating a string of length 100 against typesystem.String(max_length=10) fails; str(error) must equal "Must have no more than 10 characters."

  • When the error describes one or more field-keyed messages: the str() of a dict mapping each field key to its message text.

    • Example: validating data missing a required field b fails; str(error) must equal "{'b': 'This field is required.'}"

The dict form maps the field key (string) to the message text (string) for each contained message.

Requirement 2: typesystem.Nested

Add a new field type accessible as typesystem.Nested.

Signature
typesystem.Nested(schema)

where schema is a typesystem.Schema subclass.

Behavior

When used as a field within a schema, a Nested(SomeSchema) field validates its input value by delegating to SomeSchema. Given a valid input, the nested field produces a validated instance of the referenced schema.

Concretely, when a schema declares a nested field and is validated with input where that field's value is a mapping suitable for the nested schema:

  • The nested mapping is validated/coerced by the referenced schema (including any type coercion its own fields perform).
  • The resulting attribute on the parent validated instance is an instance of the referenced schema.
  • Two parent instances constructed with equal nested-schema instances compare equal.
  • Converting the parent instance to a dict yields the nested value as a plain dict as well.
Example of required behavior
class Artist(typesystem.Schema):
    name = typesystem.String(max_length=100)

class Album(typesystem.Schema):
    title = typesystem.String(max_length=100)
    release_year = typesystem.Integer()
    artist = typesystem.Nested(Artist)

value = Album.validate(
    {"title": "Double Negative", "release_year": "2018", "artist": {"name": "Low"}}
)

After this:

  • dict(value) equals {"title": "Double Negative", "release_year": 2018, "artist": {"name": "Low"}} (note release_year coerced to the integer 2018, and the nested value rendered as a plain dict).
  • value equals Album(title="Double Negative", release_year=2018, artist=Artist(name="Low")).

Public API Summary

  • typesystem.Nested(schema) — new field type, importable from the top-level typesystem package.
  • The error object returned from failed validations must implement __str__ as described in Requirement 1.

Do not add behavior beyond what is described above.

Task Specification: Implement an Array Field Validator

Overview

Add a new field validator class named Array to the typesystem.fields module. It must be importable as:

from typesystem.fields import Array

Public API

Class: Array

Constructor signature (all parameters keyword-capable, all optional):

Array(allow_null=False, min_items=None, max_items=None, exact_items=None)
Method: validate_or_error(value)

Returns a two-tuple (value, error):

  • On success: (validated_value, None).
  • On failure: (None, error) where error is a typesystem.base.ValidationError instance.

ValidationError is constructed with keyword arguments text and code, e.g. ValidationError(text="...", code="...").

Required Validation Behavior

Validation must be applied to the input value and produce results as follows.

Null handling
  • When value is None and allow_null is False (the default): return an error with text="May not be null." and code="null".
  • When value is None and allow_null is True: return (None, None) — i.e. None is accepted as a valid value.
Type checking
  • When value is not an array/list (e.g. an integer): return an error with text="Must be an array." and code="type".
  • A list is a valid array type.
min_items
  • When min_items is set and the array has fewer items than min_items:
    • If min_items is 1 and the array is empty: return an error with text="Must not be empty." and code="empty".
    • Otherwise (for min_items >= 2): return an error with text="Must have at least {min_items} items." and code="min_items".
  • When the array meets or exceeds min_items: it passes this check and the original list value is returned.
max_items
  • When max_items is set and the array has more items than max_items: return an error with text="Must have no more than {max_items} items." and code="max_items".
  • When the array has max_items or fewer items (including an empty array): it passes this check.
exact_items
  • When exact_items is set and the array has exactly that many items: it passes this check and the original list value is returned.
  • When exact_items is set and the array does not have exactly that many items: return an error with text="Must have {exact_items} items." and code="exact_items".
Successful result
  • On success the returned value is the input list itself (unchanged in content and equal to the input list, e.g. [], [1], [1, 2]).

Notes on Text Formatting

The numeric messages substitute the configured limit directly, e.g. with min_items=2 the text is "Must have at least 2 items.", with max_items=2 the text is "Must have no more than 2 items.", and with exact_items=2 the text is "Must have 2 items.".

Equality

ValidationError instances must compare equal when their text and code match, so that a returned error equals a freshly constructed ValidationError with the same text and code.

Also remove the previously existing Object.coerce behavior/method (drop it from the codebase); no test relies on it.

Task: Add items and additional_items support to the Array validator

Context

There is an Array validator class used for validating list values. It currently supports constructor keyword arguments including exact_items (which enforces that the input has exactly a given number of elements, producing a ValidationError with text "Must have 2 items." and code "exact_items" when violated).

You must extend the Array validator to accept two new constructor keyword arguments: items and additional_items.

Public API

The Array class must accept the following keyword arguments (in addition to those it already supports):

  • items: either a single validator instance, or a list of validator instances.
  • additional_items: a single validator instance.

Other referenced validators available in the same module/namespace: Integer, String. Validation is performed via the existing validate_or_error(value) method, which returns a (value, error) tuple where error is a ValidationError (or None on success), and value is the coerced/validated result (or None on error).

Required behavior

items as a single validator

When items is a single validator instance, every element of the input list is validated (and coerced) using that validator.

  • On success, the returned value is a list of the individually coerced element values, in order.
    • Example: Array(items=Integer()) validating ["1", 2, "3"] yields the value [1, 2, 3] (element validators coerce their inputs).
  • On failure, the error must be a ValidationError whose items are keyed by the integer index of each failing element, mapping to that element's error message.
    • Example: Array(items=Integer()) validating ["a", 2, "c"] yields an error equivalent to {0: "Must be a number.", 2: "Must be a number."} (i.e. dict(error) equals that mapping). Only failing elements appear; passing elements are omitted from the error mapping.
items as a list of validators (positional/tuple validation)

When items is a list of validator instances, each validator in the list validates the input element at the corresponding position.

  • The input list must contain exactly as many elements as there are validators in the items list, unless additional_items is supplied (see below). If the count does not match, produce a ValidationError with text "Must have N items." and code "exact_items", where N is the number of validators in the items list.
    • Example: Array(items=[String(), Integer()]) validating ["a", "b", "c"] (3 elements vs 2 validators) yields the exact-items error with text "Must have 2 items." and code "exact_items".
  • When the counts match, each element is validated/coerced by its positional validator, and the returned value is the list of coerced element values in order.
    • Example: Array(items=[String(), Integer()]) validating ["a", "123"] yields the value ["a", 123].
items (list) combined with additional_items

When items is a list of validators and additional_items (a single validator) is also supplied, the input list may contain more elements than there are validators in items. The first elements are validated positionally by the items validators, and every remaining (extra) element is validated/coerced by the additional_items validator.

  • The returned value is the list of all coerced element values in order.
    • Example: Array(items=[String(), Integer()], additional_items=Integer()) validating ["a", "123", "456"] yields the value ["a", 123, 456].

Notes

  • Existing Array behavior (including exact_items on its own) must continue to work unchanged.

Task: Add Unique Items Validation to the Array Validator

Overview

The Array validator class supports validating list inputs. You must extend it with a new option that enforces uniqueness of items within the validated list.

API Surface

The Array validator class (importable as Array from the fields module used by the rest of the codebase) must accept a new keyword argument in its constructor:

Array(items=..., unique_items=False)
  • unique_items: a boolean keyword argument, defaulting to False.

The Array validator exposes a method:

validate_or_error(value) -> (value, error)

which returns a two-tuple: the coerced/validated value on success (with error being falsy/None), or the validated value being falsy/None with an error object on failure.

Required Behavior

When unique_items=True, after items have been validated/coerced individually, the resulting list must be checked so that no two elements are equal.

  • If all items are unique, validate_or_error succeeds and returns the validated list unchanged.

  • If a duplicate item is encountered (an item equal to one that appeared earlier in the list), validation fails. The resulting error, when converted to a dict, must map the zero-based index of the offending (duplicate) element to the message:

    "Items must be unique."

    The reported index is the position of the later (duplicate) occurrence of the value.

When unique_items=False (the default), no uniqueness check is performed and existing array validation behavior is unchanged.

Examples

validator = Array(items=String(), unique_items=True)
value, error = validator.validate_or_error(["a", "b"])
# value == ["a", "b"], error is falsy

validator = Array(items=String(), unique_items=True)
value, error = validator.validate_or_error(["a", "a"])
# dict(error) == {1: "Items must be unique."}

Constraints

  • The uniqueness check applies to items as they are after per-item validation/coercion.
  • Existing Array behavior (item validation, coercion of individual elements, etc.) must remain intact.

Constructor

  • precision is an optional keyword argument. When provided, it is a string describing the decimal quantization step (for example "0.1").

07 You are working on a Python data validation library named typesystem. 532 words · source specification

You are working on a Python data validation library named typesystem. This task concerns two areas: the Choice field validator and the "required-ness" behavior of fields when used within a schema.

Part 1: Choice field

The Choice validator (constructed as Choice(...), and importable from wherever the other field validators live) must accept its choices argument as a list of two-tuples, where each tuple is (key, display_value) — for example:

Choice(choices=[("R", "red"), ("B", "blue"), ("G", "green")])

Validation behavior for a Choice built this way:

  • Calling validator.validate_or_error(x) returns a (value, error) pair.
  • When x matches one of the keys (the first element of a tuple), validation succeeds: the returned value is that key and error is None.
  • When x does not match any key, validation fails: value is None and error equals ValidationError(text="Not a valid choice.", code="choice").

Null handling:

  • By default, passing None fails with error equal to ValidationError(text="May not be null.", code="null").
  • When constructed with allow_null=True, passing None succeeds: value is None and error is None.

Part 2: Field "required-ness" within schemas

Fields are declared as class attributes of a subclass of typesystem.Schema. The relevant field types here are typesystem.Integer(...) and typesystem.String(...). Validation of a schema is performed via the class method Example.validate_or_error(data), which returns a (value, error) pair. On success, value is a mapping-like object convertible with dict(value); on failure, error is a mapping-like object convertible with dict(error) mapping field names to error message strings.

The behavior must be as follows when validating an empty input {} (i.e. the field is absent):

Integer fields
  • typesystem.Integer() — the field is required. Validation fails with an error mapping {"field": "This field is required."} (using the field's attribute name as the key).
  • typesystem.Integer(allow_null=True) — the field is not required; a missing value produces None. Validation succeeds with {"field": None}.
  • typesystem.Integer(default=0) — the field is not required; a missing value produces the default. Validation succeeds with {"field": 0}.
  • typesystem.Integer(allow_null=True, default=0) — the field is not required; the default takes effect over null. Validation succeeds with {"field": 0}.
String fields
  • typesystem.String() — the field is required. Validation fails with {"field": "This field is required."}.
  • typesystem.String(allow_blank=True) — the field is not required; a missing value produces the empty string. Validation succeeds with {"field": ""}.
  • typesystem.String(allow_null=True, allow_blank=True) — the field is not required; a missing value produces None. Validation succeeds with {"field": None}.
Summary of the required-ness rule

A field is treated as required (missing value ⇒ "This field is required.") unless one of the following makes it optional, in which case a missing value resolves as indicated:

  • A default is supplied ⇒ missing value resolves to the default (this takes precedence over null).
  • allow_null=True (and no default) ⇒ missing value resolves to None.
  • For String, allow_blank=True (and no default, and not resolved to null) ⇒ missing value resolves to the empty string "".

Precedence when multiple are set: a supplied default wins; otherwise, for a String with both allow_null=True and allow_blank=True, a missing value resolves to None.

The error message string for a missing required field must be exactly "This field is required.".

09 This codebase provides a data validation library exposed through a top-level module importable as typesystem. 459 words · source specification

Context

This codebase provides a data validation library exposed through a top-level module importable as typesystem. It includes a Schema base class (typesystem.Schema) and a set of field types, including typesystem.String, typesystem.Integer, and typesystem.Nested.

Schemas are defined by subclassing typesystem.Schema and declaring fields as class attributes. For example:

class Artist(typesystem.Schema):
    name = typesystem.String(max_length=100)

class Album(typesystem.Schema):
    title = typesystem.String(max_length=100)
    release_year = typesystem.Integer()
    artist = typesystem.Nested(Artist)

The Nested field embeds another schema. Its first positional argument is the schema class to nest.

Schema classes expose the following validation entry points:

  • Schema.validate_or_error(data) → returns a (value, error) two-tuple. On success, value is the validated schema instance and error is falsy. On failure, value is falsy and error is an error object that supports dict(error), producing a mapping from field name to error message string.
  • Schema.validate(data) → returns the validated schema instance on success.

Required Change

Add an allow_null keyword argument to the Nested field, defaulting to False.

Behavior when allow_null=False (the default)

For a Nested field with allow_null not set (or set to False), given input data where the corresponding field:

  • is None: validation must fail, and the error mapping for that field must be the message "May not be null.".
  • is present but is not an object/mapping (e.g. a plain string): validation must fail, and the error mapping for that field must be the message "Must be an object.".
Behavior when allow_null=True

For a Nested field declared with allow_null=True, given input data where the corresponding field is None, validation must succeed and the validated value for that field must be None.

Illustration
class Artist(typesystem.Schema):
    name = typesystem.String(max_length=100)

class Album(typesystem.Schema):
    title = typesystem.String(max_length=100)
    release_year = typesystem.Integer()
    artist = typesystem.Nested(Artist)

# artist is None → fails with {"artist": "May not be null."}
value, error = Album.validate_or_error(
    {"title": "Double Negative", "release_year": "2018", "artist": None}
)

# artist is a string → fails with {"artist": "Must be an object."}
value, error = Album.validate_or_error(
    {"title": "Double Negative", "release_year": "2018", "artist": "Low"}
)

class Album(typesystem.Schema):
    title = typesystem.String(max_length=100)
    release_year = typesystem.Integer()
    artist = typesystem.Nested(Artist, allow_null=True)

# artist is None → succeeds, artist stays None
value = Album.validate(
    {"title": "Double Negative", "release_year": "2018", "artist": None}
)
# dict(value) == {"title": "Double Negative", "release_year": 2018, "artist": None}

Note in the last example that the release_year input "2018" (a string) is coerced to the integer 2018 in the validated output, consistent with existing Integer field behavior.

Scope

The only new capability required is the allow_null keyword argument on the Nested field and the null/non-object validation behavior described above. Existing validation behavior for other field types and for Nested with valid object input must continue to work unchanged.

10 You are implementing validation field classes in a validation library. 549 words · source specification

You are implementing validation field classes in a validation library. The field classes live in a module importable as the package's public API (the same location from which String, Integer, and Choice are already importable, alongside a ValidationError type).

Each validator exposes a method:

validate_or_error(value, strict=False) -> (validated_value, error)

which returns a tuple (value, error). On success, error is None and value is the validated/coerced result. On failure, value is None and error is a ValidationError.

The change to implement adds lenient casting between null and empty string when strict=False (the default), plus a numeric-string coercion for integers. The specific required behaviors are below.

String

Constructor accepts (among existing options) the keyword arguments allow_blank and allow_null, both defaulting such that neither is enabled unless passed.

  • String(allow_blank=True):
    • Validating "" returns ("", None).
    • Validating None returns ("", None) — a null input is leniently coerced to the empty string.
  • String(allow_null=True):

    • Validating "" returns (None, None) — an empty string is leniently coerced to null.
    • Validating a string containing only whitespace, e.g. " ", returns (None, None) — a blank string is leniently coerced to null.

Integer

Default constructor Integer():

  • Validating the string "123.0" returns (123, None) — a numeric string whose value is integral is coerced to the integer 123.
  • Validating None returns an error equal to ValidationError(text="May not be null.", code="null").

Integer(allow_null=True):

  • Validating "" (default strict=False) returns (None, None) — an empty string is leniently coerced to null.
  • Validating "" with strict=True returns an error equal to ValidationError(text="Must be a number.", code="type") — under strict mode the empty string is not coerced to null and is treated as an invalid number.

String keywords (applied to string instances)
  • minLength: string length must be greater than or equal to the given integer.
  • maxLength: string length must be less than or equal to the given integer.
  • pattern: string must match the given regular expression (unanchored search semantics per JSON Schema).
Array keywords (applied to array instances)
  • minItems: array must contain at least the given number of items.
  • maxItems: array must contain at most the given number of items.
Object keywords (applied to object instances)
  • minProperties: object must contain at least the given number of properties.
  • maxProperties: object must contain at most the given number of properties.
  • required: object must contain all listed property names as keys.
General semantics
  • Keywords that constrain a specific JSON type (numeric, string, array, object) apply only when the instance is of that type. Instances of other types are not constrained by keywords that do not apply to them (i.e., such a keyword neither rejects nor is triggered by a value of an unrelated type).
  • A schema may combine multiple keywords; the instance must satisfy all applicable constraints for validation to succeed.
  • When multiple JSON types are relevant, the conversion should be able to represent alternatives via the Union validator (any-of style acceptance), where an instance is valid if it satisfies at least one of the alternative schemas.

Supporting Requirement: Union Field

The Union field in typesystem.fields must be constructible as:

Union(any_of=[<field>, <field>, ...])

Validation semantics:

  • The value is valid if it validates successfully against at least one of the provided sub-validators; the successful coerced value is returned.
  • If the value fails all sub-validators, validation fails. When a value clearly corresponds to one candidate sub-validator's type but fails that sub-validator's own constraints, the resulting error should be that sub-validator's specific constraint error (for example, a numeric value that exceeds a candidate integer validator's maximum yields the maximum constraint error with its standard message and code="maximum", rather than a generic union error).

ValidationError instances compare equal when their text and code attributes match.

Task Specification: JSON Schema items Support

Objective

Implement a function that converts a JSON Schema definition into a validator object capable of validating data against that schema. This task extends existing JSON Schema support to correctly handle the items keyword for array validation.

Public API

Provide the following function:

# module: typesystem/json_schema.py
def from_json_schema(schema: dict) -> Validator
  • Input: schema — a dictionary representing a JSON Schema.
  • Output: A validator object.

The returned validator must expose the following method:

def validate_or_error(self, data, strict: bool = False) -> tuple
  • Returns: a 2-tuple (value, error).
    • On successful validation, value holds the validated (and possibly coerced) data and error is None.
    • On failed validation, error is a non-None object describing the failure and value is None.
  • strict parameter: When True, validation is performed without permissive type coercion (values must already match their expected types).

Required Behavior: The items Keyword

The implementation must support the JSON Schema items keyword for validating arrays, in addition to the JSON Schema keywords already supported by the existing code. This includes both forms defined by the JSON Schema specification:

1. items as a single schema (list validation)

When items is a single schema (a dictionary or boolean), every element of an array being validated must independently satisfy that schema.

  • An array validates successfully only if all of its elements validate against the items schema.
  • If any element fails to validate against the items schema, validation of the array fails.
  • An empty array validates successfully.
  • A boolean items schema follows JSON Schema semantics: true accepts any element; false rejects any element (so any non-empty array fails, and an empty array passes).
2. items as an array of schemas (tuple validation)

When items is an array of schemas, each schema applies positionally to the element at the same index in the array being validated.

  • The element at index i must validate against the i-th schema in the items array.
  • If the array being validated is longer than the items array, the extra trailing elements are not constrained by items (they validate successfully with respect to this keyword).
  • If the array being validated is shorter than the items array, only the positions present are checked; missing positions impose no failure from this keyword.
  • Validation of the array fails if any positionally-matched element fails to validate against its corresponding schema.

Constraints

  • The behavior of all other JSON Schema keywords already handled by the existing implementation must be preserved unchanged.
  • Validation must operate correctly under strict=True, meaning input data types are not coerced and must already conform to the expected structure and element types.

The from_json_schema conversion must produce validators whose accept/reject behavior conforms to the JSON Schema specification for the following features:

Boolean schemas
  • A schema value of true (Python True) must accept every instance.
  • A schema value of false (Python False) must reject every instance.
  • These boolean schemas must also be honored wherever a subschema is expected (e.g. as the value of additionalProperties, additionalItems, or an entry in properties/patternProperties).
type
  • Constrains the instance to one or more of the JSON primitive types: "null", "boolean", "object", "array", "number", "integer", "string".
  • May be a single type string or an array of type strings (instance is valid if it matches any listed type).
  • Integer-valued numbers (e.g. 1.0) must satisfy "integer"; "number" accepts both integers and floats.

  • For objects, lists the property names that must be present.
  • Instances that are not objects are unaffected by this keyword.

  • When true (or absent), extra elements are unrestricted.

pattern

  • Keywords not present in a schema impose no constraints.

Task Specification: JSON Schema Validation — default and uniqueItems Keywords

Overview

You are extending a JSON Schema validator so that it correctly handles two additional JSON Schema keywords: default and uniqueItems. The validator is exercised against the standard JSON Schema test-suite draft data files default.json and uniqueItems.json, and must produce validation results matching the expected outcomes defined by those standard suites.

Required Behavior

default keyword

The default keyword must have no effect on validation. When a schema contains a default key (at any level), the presence of that key must never cause an instance to be considered invalid, and must never cause an otherwise-invalid instance to be considered valid. In other words, default is purely annotative and is ignored entirely during validation — any instance value is acceptable with respect to a default keyword.

This applies regardless of:

  • The value of default (object, array, scalar, etc.).
  • Where the default appears in the schema (top-level or nested inside properties/items).
uniqueItems keyword

The uniqueItems keyword constrains array instances:

  • When uniqueItems is true, an array instance is valid only if all of its elements are unique (no two elements are equal). If any two elements are equal, the array is invalid.
  • When uniqueItems is false, the keyword imposes no constraint; any array (including one with duplicate elements) is valid.
  • When the instance is not an array, uniqueItems imposes no constraint; the instance is valid with respect to this keyword.

Equality/uniqueness must follow JSON value semantics:

  • Two values are considered equal only if they are of the same JSON type and structurally equal. In particular:
    • true (boolean) and 1 (number) are not equal.
    • false (boolean) and 0 (number) are not equal.
    • 1 (integer) and 1.0 (number) are equal (numeric equality).
  • Objects are equal when they have the same set of keys with pairwise-equal values, irrespective of key order.
  • Arrays are equal when they have the same length and pairwise-equal elements in order.
  • Nested objects and arrays are compared recursively using these same rules.
  • Duplicate detection must work across all JSON types, including nested composite structures.

Public API

The validation entry point already used by the existing supported keywords (e.g. type, required, boolean_schema) must now also correctly process the default and uniqueItems keywords. No new public modules, classes, or functions are introduced by this task; the existing schema-validation surface must simply be extended to cover the two keywords described above, such that validating an instance against a schema returns the correct valid/invalid result for schemas using default and uniqueItems.

Overview

You must extend the Object validator to support a property_names constraint that validates each key of an input object against a provided validator. You must also change how non-string key errors are reported.

Location

The Object validator class lives in the fields module of the codebase (the same module that also defines String and other field validators). Modify the existing Object class.

Required Changes

1. New property_names parameter

The Object validator's constructor must accept a new optional keyword argument property_names, which is either None (default) or another validator instance (e.g. a String validator).

When property_names is provided, every key in the object being validated must be passed to that validator. If the validator rejects a key, validation of the object fails, and an error must be reported for that key.

  • The error message for a key rejected by the property_names validator must be exactly: "Invalid property name."
  • The error is keyed by the offending key value itself (the actual key from the input object).

For example, validating {"a": 123} with Object(property_names=String(min_length=3)) produces a single error whose key is "a" and whose message is "Invalid property name.".

2. Change to non-string key error reporting

When an object contains a key that is not a string, validation fails with the message "All object keys must be strings.". This error must now be keyed by the offending (non-string) key value itself, rather than by an empty string.

For example, validating {1: 123} produces a single error whose key is the integer 1 and whose message is "All object keys must be strings.".

Behavior Notes

  • The error object supports being turned into a dict, where the mapping is from the error's key location to its message string. The key location for the errors described above is the actual object key (1, "a", etc.) rather than an empty string.
  • Existing Object behavior (such as allow_null=True accepting None) must remain unchanged.

JSON Schema Compatibility

The Object validator participates in JSON-Schema-driven validation. The property_names constraint corresponds to the JSON Schema propertyNames keyword: when a JSON Schema specifies propertyNames, the resulting Object validator must apply that constraint to each key, producing failures for keys the constraint rejects, consistent with the behavior described above.
