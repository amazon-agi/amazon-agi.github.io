01 Create a module tox_ansible_collection/ansible.py that exposes the three public classes Collection, Role, and Scenario. 480 words · source specification, reworded by GLM-5.3-Flash

Task Description

Create a module tox_ansible_collection/ansible.py that exposes the three public classes Collection, Role, and Scenario. The classes model the directory tree of an Ansible collection that contains roles, and each role may in turn contain Molecule scenarios.

Assumptions About the Directory Layout

The classes work with a filesystem tree that is rooted at a collection base directory and has the following structure:

<base_dir>/
  roles/
    <role_name>/
      tasks/
        main.yml          # presence marks a valid role
      molecule/
        <scenario_name>/
          molecule.yml     # scenario config (may be empty or contain YAML)
  • A directory under roles/ counts as a valid role only if it contains a tasks/main.yml file.
  • Every subdirectory of a role's molecule/ directory is a scenario. The configuration of that scenario resides in the molecule.yml inside the subdirectory.

Collection

The constructor:

Collection(directory)
  • directory is the path of the collection's base directory.

The methods:

  • is_collection() → bool Returns True when the directory that was given represents a collection.

  • get_roles() → list Returns a list of the roles the collection contains. The length of the list is equal to the number of role directories present under roles/. Each element stands for one role.

Role

The constructor:

Role(collection, name)
  • collection is an instance of Collection.
  • name is the directory name of the role (a string) under the collection's roles/ directory.

The methods:

  • is_role() → bool Returns True only if the role directory contains a tasks/main.yml file. Returns False for a directory that exists under roles/ but has no tasks/main.yml.

  • get_scenarios() → list Returns a list of the scenarios defined for the role. The length of the list is equal to the number of subdirectories under the role's molecule/ directory. Each element corresponds to one scenario.

Scenario

The constructor:

Scenario(role, path)
  • role is an instance of Role.
  • path is the path of the scenario's directory relative to the role's directory, for instance "molecule/default". The scenario's config file is the molecule.yml found inside that directory.

The attributes:

  • name → str The name of the scenario, determined as follows:

    • If the scenario's molecule.yml holds a mapping with a scenario key which itself contains a name key, then name is that explicitly configured value.
    • Otherwise (empty file, or no scenario.name entry), name is derived from the scenario's directory name — the last path component of path.

    Examples:

    • A scenario at molecule/scenario whose molecule.yml is empty has name == "scenario".
    • A scenario located at molecule/default whose molecule.yml contains:
      scenario:
    name: other
      has name == "other".

    Note: the contents of molecule.yml may be supplied with leading indentation on every line and must still be parsed correctly as YAML.

Importing the Classes

It must be possible to import all three classes directly from tox_ansible_collection.ansible:

from tox_ansible_collection.ansible import Collection, Role, Scenario

Summary

A Python package called tox_ansible_collection is to be implemented; it models Ansible collections, roles, and Molecule scenarios, and it enumerates the tox cases that correspond to them. The required public contract is made up of the modules, classes, constructor signatures, filesystem behavior, ordering, and compatibility requirements laid out below.

Module Layout and Import Surface

At these exact paths, the modules and members listed next must be importable:

  • The module tox_ansible_collection.ansible exposes Ansible.
  • The module tox_ansible_collection.ansible.collection exposes Collection.
  • The module tox_ansible_collection.ansible.role exposes Role.
  • The module tox_ansible_collection.ansible.scenario exposes Scenario.
  • The module tox_ansible_collection.tox_case_base exposes ToxCaseBase.

Scenario

Constructor

Scenario(directory) accepts a single positional argument that identifies the scenario directory. The scenario's configuration file is <directory>/molecule.yml.

Configuration
  • _get_config(self) must read molecule.yml and parse it as YAML, returning the mapping that results.
  • _get_config() must be the only point at which scenario configuration is read. The name, the driver, and all other configuration-dependent behavior must derive from this method's result so that configuration loading can be replaced independently.
Name and string form
  • When the parsed configuration contains a scenario mapping with a name key, name is the value of scenario.name.
  • In every other case, name is the basename (last path component) of directory. This fallback applies when the configuration is empty or carries no explicit scenario name.
  • str(scenario) returns scenario.name.
Driver

When a driver mapping with a name key is present in the parsed configuration, driver is that value.

Examples:

  • A directory called default holding driver:\n name: openstack produces name == "default" and driver == "openstack".
  • A directory called other holding scenario:\n name: surprise produces name == "surprise", and its string form is "surprise".

Role

Constructor, name, and string form

Role(directory) accepts a single positional argument that identifies the role directory.

  • The value of name is the basename of directory; for instance, Role("some/directory").name == "directory".
  • str(role) returns role.name.
Role detection

is_role(self) -> bool returns True only in the case where the role directory contains a file at tasks/main.yml. A directory that is missing, or a directory without that file, is not a role and must produce False. The file check must be resolved through path.isfile imported at module scope in tox_ansible_collection.ansible.role; it is also permitted to check the role directory using that module's path.isdir.

Scenario discovery

Molecule scenarios are discovered by get_scenarios(self) -> list[Scenario], which walks the role directory using walk imported at module scope in tox_ansible_collection.ansible.role.

A directory counts as a scenario only if both of the following hold:

  1. It sits directly beneath the role's top-level molecule/ directory; its parent is <role-directory>/molecule.
  2. A file named molecule.yml is contained directly in that directory.

Any molecule.yml located anywhere outside the role's molecule/ directory must be ignored. In particular, scenarios are not defined by matching files in directories such as templates/ or templates/derp/. Directories in molecule/ that lack molecule.yml are excluded as well.

One Scenario is returned for every eligible directory, and the order in which the walk encounters eligible directories is preserved. Each scenario is constructed from its own scenario directory, so its default name is the basename of that directory.

By way of example, if the walk entries are such that templates/ and templates/derp/ contain molecule.yml, molecule/one/ and molecule/two/ contain molecule.yml, and molecule/shared/ does not, then the result contains only the one and two scenarios, in that order.

Tox cases

get_tox_cases(self) -> list returns one tox case for each result of get_scenarios(), following the scenario order. Every item is a ToxCaseBase that pairs this role with the corresponding scenario. The number of returned cases therefore equals the number of discovered scenarios.

Collection

Constructor and paths

Collection() accepts no required arguments. When an instance is constructed, its directory attribute is the absolute path of the current working directory, which is equivalent to os.path.abspath(os.curdir). The marker for the collection is <directory>/galaxy.yml, and the roles directory is <directory>/roles.

Collection detection

Whether the current directory is an Ansible collection is determined by is_collection(self) -> bool, which checks whether galaxy.yml is a file. This check must be resolved through path.isfile imported at module scope in tox_ansible_collection.ansible.collection.

Role discovery

The behavior of get_roles(self) -> list[Role] is as follows:

  • The collection's roles/ directory is checked via path.isdir imported at module scope in tox_ansible_collection.ansible.collection.
  • If that directory does not exist, an empty list is returned.
  • Otherwise, its entries are enumerated using listdir imported at module scope in the same module. For each corresponding <directory>/roles/<entry> path, a Role is constructed, and only objects for which Role.is_role() is true are retained. Files and role directories that are invalid are therefore excluded.
  • The order supplied by listdir is preserved; do not impose any separate sort. For each retained role, name is the basename of the corresponding entry.
Tox cases

In get_tox_cases(self) -> list, the roles come from get_roles(), and each role's get_tox_cases() result is concatenated in role order. A flat list is returned, with each role's internal case order preserved. Its length is the total of the per-role case counts; an empty list is produced when there are no roles or no scenarios.

ToxCaseBase

ToxCaseBase(role, scenario) accepts a role object and a scenario object as its positional arguments. These objects are the individual case items that get produced for role/scenario pairs by Role.get_tox_cases() and, through aggregation, by Collection.get_tox_cases().

Ansible

Constructor

Ansible() accepts no required arguments and operates with the Collection and Role representations of the current working-directory context.

Detection

is_ansible(self) -> bool returns True when the current directory is either a valid role according to Role.is_role() or a valid collection according to Collection.is_collection(). Only when both checks are false does it return False.

Tox cases and precedence

get_tox_cases(self) -> list follows this precedence:

  1. If the current directory is a role, the result of that role's get_tox_cases() is returned.
  2. Otherwise, if it is a collection, the result of that collection's get_tox_cases() is returned.
  3. Otherwise, an empty list is returned.

Consequently, if a directory happens to satisfy both classifications, the role behavior takes precedence. The returned case lists are passed through as the corresponding role or collection produced them.

Filesystem Substitution and Compatibility

  • For filesystem operations, the applicable path, listdir, and walk names must be resolved through the module that owns the operation. Collection checks in particular use the names in tox_ansible_collection.ansible.collection, whereas role checks and traversal use those in tox_ansible_collection.ansible.role. Scenario path handling, likewise, stays local to tox_ansible_collection.ansible.scenario. These names must be imported at module scope so that each module's filesystem behavior can be substituted independently.
  • Access to scenario configuration must stay isolated behind _get_config().
  • Compatibility must be maintained with supported older Python environments, including environments in which unittest.mock is unavailable. Library code must not depend on exist_ok-style filesystem APIs that are unavailable on those versions.

  2. Contains a file called molecule.yml.

  • Per case, get_commands(options) returns a single command; each command takes this shape:
    ["bash", "-c", "cd {} && molecule  lint -s {}".format(case.role.directory, case.scenario.name)]
    Mind the string "cd {} && molecule lint -s {}": it is exact, and two spaces separate molecule from lint. The returned commands appear in the same order as the cases list supplied as input.
tox_ansible.matrix
from tox_ansible.matrix import Matrix, MatrixAxisBase
from tox_ansible.matrix.axes import AnsibleAxis, PythonAxis
  • Applying a set of axes is how Matrix expands a base test case into multiple expanded cases.
  • Serving as the base class for the axes is MatrixAxisBase.
  • Expansion via expand_python is what PythonAxis(version) performs on a case; AnsibleAxis(version) performs its expansion via expand_ansible.

Further Requirements

  • Version 2.7 is the minimum supported tox version (the environment description attribute is used by the plugin).
  • Python 3.6+ is what the package must target (no support for Python 2.7 / 3.5 is required).
  • Registration through tox's plugin entry-point mechanism is required of the plugin, so that it functions when tox is executed as an external process.

Referenced Test Fixtures

A non-empty envlist must be declared by two fixture tox.ini files:

  • The [tox] section of the collection fixture sets envlist = lint_all.
  • The [tox] section of the expand_collection fixture sets envlist = derp.

These declared environments, alongside the auto-generated environments, are part of the generated tox -l output as described above.
