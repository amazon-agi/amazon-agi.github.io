Implement a module tox_ansible_collection/ansible.py that exposes three public classes: Collection, Role, and Scenario. These classes model an Ansible collection directory tree containing roles, each of which may contain Molecule scenarios.

Directory Layout Assumptions

The classes operate on a filesystem tree with the following structure, rooted at a collection base directory:

<base_dir>/
  roles/
    <role_name>/
      tasks/
        main.yml          # presence marks a valid role
      molecule/
        <scenario_name>/
          molecule.yml     # scenario config (may be empty or contain YAML)
  • A directory under roles/ is a valid role only if it contains a tasks/main.yml file.
  • Each subdirectory of a role's molecule/ directory is a scenario. The scenario's configuration lives in molecule.yml inside that subdirectory.

Collection

Constructor:

Collection(directory)
  • directory is the path to the collection's base directory.

Methods:

  • is_collection() → bool Returns True when the given directory represents a collection.

  • get_roles() → list Returns a list of the roles contained in the collection. The list length equals the number of role directories present under roles/. Each element represents one role.

Role

Constructor:

Role(collection, name)
  • collection is a Collection instance.
  • name is the role's directory name (a string) under the collection's roles/ directory.

Methods:

  • is_role() → bool Returns True only if the role directory contains a tasks/main.yml file. Returns False for a directory that exists under roles/ but lacks tasks/main.yml.

  • get_scenarios() → list Returns a list of the scenarios defined for this role. The list length equals the number of subdirectories under the role's molecule/ directory. Each element represents one scenario.

Scenario

Constructor:

Scenario(role, path)
  • role is a Role instance.
  • path is the scenario's directory path relative to the role's directory, e.g. "molecule/default". The scenario's config file is molecule.yml located inside that directory.

Attributes:

  • name → str The scenario name, determined as follows:

    • If the scenario's molecule.yml contains a mapping with a scenario key that itself contains a name key, name is that explicitly configured value.
    • Otherwise (empty file, or no scenario.name entry), name is inferred from the scenario's directory name — the last path component of path.

    Examples:

    • A scenario at molecule/scenario with an empty molecule.yml has name == "scenario".
    • A scenario at molecule/default whose molecule.yml contains:
      scenario:
    name: other
      has name == "other".

    Note: the molecule.yml contents may be provided with leading indentation on each line and must still be parsed correctly as YAML.

Imports

All three classes must be importable directly from tox_ansible_collection.ansible:

from tox_ansible_collection.ansible import Collection, Role, Scenario

Existing role discovery, case generation, command construction, dependency selection, and matrix expansion behavior must remain compatible.

Required Public API

tox_ansible.ansible.scenario.Scenario
Construction and lazy loading

Scenario must be constructable with one positional directory-path string:

scenario = Scenario(directory)

The object represents the molecule.yml located under that directory. Construction must not read the filesystem. Configuration access is lazy: a filesystem read may occur when config is evaluated directly or when another derived property evaluates it. A nonexistent or unreadable scenario configuration must therefore not make construction itself fail.

config property

config must be a property, used as scenario.config, that reads and returns the scenario configuration as a dictionary. If no readable configuration mapping is available, including an absent or empty configuration, it must return {}.

Configuration loading belongs behind this property. _get_config is not part of the required API, and no package behavior may depend on calling it. config must be exposed as a genuine property rather than as a callable method or an eagerly populated instance attribute.

name property/attribute

name identifies the scenario and must be resolved in this order:

  1. If the configuration contains a scenario mapping with a name key, use that configured value.
  2. Otherwise, use the final component of the scenario directory path.

For example:

scenario:
  name: surprise

For a scenario whose directory is molecule/other, this produces scenario.name == "surprise". Without that configured key, Scenario("molecule/my_test").name == "my_test". The configured value must therefore be observed through the lazy config property rather than being permanently inferred from the path during construction. Converting a scenario to a string must return its resolved name.

driver property

driver must be a property, used as scenario.driver, derived from config["driver"]["name"] when that value is present. It returns the configured driver name, such as "docker" or "openstack". If the configuration is empty or has no driver.name value, it must return None without raising an error.

Like config, driver must be a genuine property and must not be eagerly assigned during construction. Consumers must observe the current property value.

tox_ansible.ansible.role.Role

Role must be constructable as Role(directory). It exposes the supplied directory and a name derived from the final path component. For example:

role = Role("roles/derp")
assert role.name == "derp"
assert str(role) == "derp"

A role is valid when its directory exists and contains tasks/main.yml. Scenario discovery walks the role tree and returns scenarios represented by directories directly under a molecule directory that contain molecule.yml; unrelated directories and files are ignored. get_tox_cases() returns one ToxTestCase for each discovered scenario.

Whenever role discovery needs scenario configuration or derived scenario data, it must use Scenario.config, Scenario.name, and Scenario.driver through their property interfaces. It must not call _get_config, and discovery must remain compatible with lazy scenario construction. The tox_ansible.ansible.role.walk module symbol remains the traversal entry point.

tox_ansible.ansible.collection.Collection

get_roles() returns the valid Role objects found under the collection's roles directory, or an empty list when that directory is absent. get_tox_cases() gathers and flattens the cases returned by all discovered roles. Any access to scenario configuration or derived scenario information in this flow must use the public scenario properties and must not depend on _get_config.

tox_ansible.tox_test_case.ToxTestCase

A case is constructable as:

case = ToxTestCase(role, scenario)

An unexpanded case has python is None and ansible is None.

Naming

get_name() joins expansion factors, the role name, and the resolved scenario name with hyphens. With no expansion factors:

ToxTestCase(
    Role("roles/derp"),
    Scenario("molecule/my_test"),
).get_name() == "derp-my_test"

If scenario.name is overridden in molecule.yml, the configured name is used in this result.

Working directory and interpreter
  • get_working_dir() returns the role directory unchanged; for Role("roles/derp"), it returns "roles/derp".
  • get_basepython() returns None when no Python expansion is present. Otherwise, it returns "python" + version, preserving dots in the version; Python "4.1" produces "python4.1".
Dependencies

get_dependencies() returns an ordered list. It starts with these six core dependencies:

[
    "molecule",
    "ansible-lint",
    "yamllint",
    "flake8",
    "pytest",
    "testinfra",
]

It must then include exactly the applicable Ansible requirement:

  • With no Ansible-version expansion, append the unversioned string "ansible". Thus, the ordinary dependency result is the six entries above followed by "ansible"; the six-entry core list alone is not the complete result.
  • With an Ansible-version expansion, append "ansible==<version>.*" instead of unversioned Ansible. For version "2.7", append "ansible==2.7.*".

After that, append the dependency associated with the current scenario.driver property when recognized:

  • "docker" adds "docker".
  • "openstack" adds "openstacksdk".
  • None or an unrecognized driver adds no driver-specific dependency.

Dependency calculation must read scenario.driver as a property and must not obtain configuration through _get_config.

Commands

get_commands(options) returns a list containing one argv-style command list. It invokes Molecule against the resolved scenario name:

[["molecule", <global options...>, "test", "-s", <scenario name>]]

Global options come from options.get_global_opts() and retain their order between "molecule" and "test". Examples:

# No global options
[["molecule", "test", "-s", "my_test"]]

# get_global_opts() returns ["-c", "derp"]
[["molecule", "-c", "derp", "test", "-s", "my_test"]]
Immutable expansion

expand_ansible(version) and expand_python(version) each return a new case and do not mutate the original. The new case retains the same role, scenario, and any earlier expansion state. Each newly applied factor is prepended to the existing factor sequence.

expand_ansible(version) must:

  • Set the returned case's ansible attribute to the supplied version string.
  • Prepend ansible<version-without-dots> to its name.
  • Select the pinned Ansible dependency described above.
  • Leave get_basepython() as None when no Python expansion has been applied.

For "2.7", the name factor is ansible27 and the dependency is ansible==2.7.*.

expand_python(version) must:

  • Set the returned case's python attribute to the supplied version string.
  • Prepend py<version-without-dots> to its name.
  • Make get_basepython() return "python" + version.

For "4.1", a derp/my_test case becomes py41-derp-my_test and uses python4.1.

Expansions compose in application order because the newest factor is prepended. For example:

base.expand_python("4.1").expand_ansible("1.0").get_name()
# "ansible10-py41-derp-my_test"

base.expand_ansible("2.8").expand_python("2.7").get_name()
# "py27-ansible28-derp-my_test"
tox_ansible.options.Options

Options remains constructable from one argument. get_global_opts() returns a list of strings, which may be empty, for insertion into generated Molecule commands.

Key Constraints

  • Scenario.config and Scenario.driver are public properties accessed as attributes. They must remain substitutable through standard property-level instrumentation.
  • Scenario construction is filesystem-independent; no configuration is loaded eagerly.
  • Configured scenario.name takes precedence over the directory basename, while the basename remains the fallback.

Task: Implement a Tox Plugin for Ansible Molecule Scenarios

Overview

Implement a tox plugin (Python package tox_ansible) that automatically discovers Ansible roles and their Molecule scenarios in the current working directory and generates corresponding tox test environments. The plugin must integrate with tox's plugin hook system so that running tox -l lists the generated environments. It must also support filtering the generated environments by role, scenario, or driver via command-line options and environment variables.

The plugin must work correctly when tox is invoked as an external subprocess (i.e., the plugin registers itself through standard tox plugin entry points).

Environment Generation and Discovery

When tox runs in a directory, the plugin inspects the directory tree to find Ansible roles and Molecule scenarios and produces test environment names.

Non-Ansible directories

If the directory is not an Ansible collection/role layout (no discoverable roles/scenarios), the plugin must not add any generated environments. Only the environments explicitly declared in the project's tox.ini are listed, in the order they are declared. For a project declaring these environments in order:

py27, py35, py36, py37, py38, py27-tox20, py27-tox30, py38-tox20, py38-tox30, lint, coverage

tox -l must output exactly those names, one per line, preserving that declaration order.

Collection directories (roles + scenarios present)

For a directory containing roles with Molecule scenarios, the plugin generates one environment per (role, scenario) pair, plus any environments declared in the project's tox.ini. Only directories that are valid roles (contain tasks/main.yml) and valid scenarios (contain molecule.yml) are considered; invalid roles or directories without tests are ignored.

Generated environment names combine the role name and scenario name. When a role's name is not "simple" style (i.e., the role has an explicit/complex name), the environment is named <role>-<scenario>; a role named such that it produces simple yields simple-<scenario>. A scenario's name is taken from the scenario directory name unless overridden inside molecule.yml by a scenario: name: key.

The complete list of environments for a collection fixture that declares lint_all in its tox.ini and contains the appropriate roles/scenarios must be, sorted:

complex-default
complex-openstack
complex-real_name
lint_all
simple-default

Output must be sorted alphabetically when generated environments are present. The final tox -l output is these names joined by newlines.

Expanded (matrix) collection directories

When the tox.ini [ansible] section declares multiple Ansible versions (e.g., ansible = 2.8 2.9) and the tox config declares a Python matrix, the plugin expands each generated environment across the Python and Ansible axes. Environment names take the form py<pyver>-ansible<ansiblever>-<role>-<scenario> (e.g., py27-ansible28-simple-default). Environments declared directly in tox.ini (e.g., derp) are included unexpanded.

For an expand-collection fixture declaring derp in tox.ini, Ansible versions 2.8 and 2.9, Python versions 27 and 38, one simple role with a default scenario, plus a lint_all environment, the sorted output must be:

derp

py38-ansible28-simple-default
py38-ansible29-lint_all
py38-ansible29-simple-default

Filtering

The plugin supports filtering generated environments by role, scenario, or driver. Each filter can be supplied either as a command-line option or via an environment variable. When a filter is active, only matching generated environments are listed (and only generated environments — auxiliary environments like lint_all are excluded from filtered output).

  • Scenario filter: --ansible-scenario <name> or TOX_ANSIBLE_SCENARIO=<name>
  • Driver filter: --ansible-driver <name> or TOX_ANSIBLE_DRIVER=<name>
  • Role filter: --ansible-role <name> or TOX_ANSIBLE_ROLE=<name>

The command-line option and the corresponding environment variable must produce identical results.

For the collection fixture above:

  • Filtering by scenario default yields (sorted):
    complex-default
simple-default
  • Filtering by driver openstack yields:
    complex-openstack
  • Filtering by role simple yields:
    simple-default
