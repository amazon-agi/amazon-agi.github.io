01 Adding "Nth weekday of month" cron syntax support to croniter 581 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Adding "Nth weekday of month" cron syntax support to croniter

Overview

The croniter class (importable as from croniter import croniter) is to be extended so that it supports the # operator in the day-of-week field of a cron expression. By means of this operator, a weekday is restricted to a specific occurrence within the month (e.g., "the first Saturday" or "the fifth Wednesday").

Public API

This change affects the existing constructor and the iteration methods:

  • croniter(expr_format, start_time=..., day_or=...) — the constructor, which accepts a cron expression string together with a base datetime.
  • croniter.get_next(datetime) — returns the next matching datetime located after the current position and advances the iterator forward.
  • croniter.get_prev(datetime) — returns the previous matching datetime located before the current position and advances the iterator backward.

The change does not introduce any new module paths, classes, or function names.

Syntax to Be Supported

An entry in the day-of-week field (the 5th field) may be written in the form:

<weekday>#<n>

where:

  • <weekday> denotes a weekday specifier; it may be a numeric value or a three-letter lowercase abbreviation (e.g., sat, sun, wed, mon).
  • <n> denotes an integer occurrence index running from 1 upward, indicating the nth occurrence of that weekday within a given month.

Several such terms may be combined within the same field, separated by commas, e.g.:

sat#1,sun#2

Each term is matched independently.

Semantics

<weekday>#<n> matches a date if and only if the weekday of that date equals <weekday> and the date is the <n>-th occurrence of that weekday within its calendar month.

For example:

  • sat#1 matches only the first Saturday in each month.
  • sun#2 matches only the second Sunday in each month.
  • wed#5 matches only the fifth Wednesday of a month — a day that exists only in months containing five Wednesdays. In months that have no fifth Wednesday, that term produces no match.

Required Behavior

Forward iteration with get_next

Taking 0 0 * * sat#1 as the expression and datetime(2010, 2, 25) as the base:

  • The first datetime that matches is the first Saturday of March 2010: 2010-03-06 (a Saturday).
  • The next one is the first Saturday of April 2010: 2010-04-03 (a Saturday).

Taking 0 0 * * wed#5 as the expression and datetime(2010, 1, 25) as the base:

  • The first match falls on 2010-03-31 (the fifth Wednesday of March 2010).
  • The next match falls on 2010-06-30 (the fifth Wednesday of June 2010).
  • The next match falls on 2010-09-29 (the fifth Wednesday of September 2010).

Months containing no fifth Wednesday are skipped entirely.

Backward iteration with get_prev

Taking 0 0 * * sat#1,sun#2 as the expression and datetime(2010, 8, 25, 15, 56) as the base:

  • The first match in the backward direction is 2010-08-08 00:00 (the second Sunday of August 2010).
  • The next backward match is 2010-08-07 00:00 (the first Saturday of August 2010).
  • The next backward match is 2010-07-11 00:00 (the second Sunday of July 2010).

All datetimes that are produced carry the hour and minute dictated by the minute/hour fields of the expression (0 0 → 00:00).

Scope Constraints

  • The time (minute/hour) and the other fields continue to work as they already do; the day-of-week # operator behavior is the only addition.
  • The # operator is applicable to the day-of-week field only.
  • Matching combines correctly with the standard month/day-of-month/day-of-week matching rules already in place.

Task Specification: Croniter Exception Hierarchy and Validation Method

Overview

You must extend the croniter package so that it provides a structured exception hierarchy for cron-parsing errors together with a class method for validating cron expressions.

Public API

All of the items below must be importable directly from the croniter package:

from croniter import croniter, CroniterBadDateError, CroniterBadCronError, CroniterNotAlphaError
Exception Classes

The following exception classes must be defined:

  1. CroniterError — a base exception class that covers all croniter-related errors. It must inherit from ValueError.

  2. CroniterBadCronError — raised when a cron expression is structurally invalid (for example, it has the wrong number of fields). It must be a subclass of CroniterError.

  3. CroniterNotAlphaError — raised when a cron expression contains an alphabetic token that cannot be recognized (for example, an invalid month or day-of-week name). It must be a subclass of CroniterError.

  4. CroniterBadDateError — an error related to date computation (this class already exists in the codebase and must remain importable). It must be a subclass of CroniterError.

Because all of these exceptions inherit from CroniterError (and therefore from ValueError), catching the base class must catch any of the specific errors.

croniter.expand

expand must be callable on croniter as a class method / static-style method, i.e. croniter.expand('<cron expression>'). Given a cron expression string, it parses/expands it and must raise errors as follows:

  • A cron expression whose number of whitespace-separated fields is wrong must raise CroniterBadCronError. Specifically:
    • '* * * *' (too few fields) must raise CroniterBadCronError.
    • '* * * * * * *' (too many fields) must raise CroniterBadCronError.
  • A cron expression that contains an alphabetic token which cannot be recognized must raise CroniterNotAlphaError. Specifically:
    • '* * * janu-jun *' must raise CroniterNotAlphaError.
croniter.is_valid

Add the following class method:

croniter.is_valid(expression) -> bool

To validate a cron expression string, the method attempts expansion and reports whether the expression is well-formed:

  • It returns True when the expression is valid (for example, '0 * * * *').
  • It returns False when the expression is structurally invalid (for example, '0 * *', which has too few fields).
  • It returns False when the expression contains an alphabetic token that cannot be recognized (for example, '* * * janu-jun *').

Put differently, is_valid must catch any CroniterError that is produced during validation and turn it into a False return value, returning True only when no such error occurs.

Notes

  • A valid standard cron expression is made up of exactly five whitespace-separated fields.
  • The existing behavior of croniter (iteration, get_next, timezone handling, etc.) must be preserved.

Task: Handle Backward DST Transitions Correctly During Cron Iteration

Background

The codebase to be modified is the croniter library, whose implementation lives in src/croniter/croniter.py. At its core sits a croniter class — importable via from croniter.croniter import croniter and additionally re-exported by the croniter package — whose purpose is to iterate over datetimes that match a cron expression.

An instance is created in this way:

croniter(expr_format, start_time)

and, once constructed, it makes the following method available:

get_next(ret_type)   # e.g. get_next(datetime)

The datetime this method returns is the next one matching the cron expression, and it lies strictly after the start_time that was provided.

Problem Description

get_next produces incorrect output whenever forward iteration crosses a Daylight Saving Time (DST) transition in a timezone whose clocks get moved backward (a "fall back" transition — one where the local wall-clock time is repeated and the UTC offset grows). Across such backward DST transitions, the next matching datetime must be computed correctly, while the timezone information of the input is preserved.

Required Behavior

When a timezone-aware start_time (localized with pytz) is supplied together with a cron expression, the correct next matching datetime — with backward-DST boundaries respected — must be returned by get_next(datetime).

As a concrete case, consider America/Sao_Paulo: during the night of 2018-02-17/18, this timezone moved its clocks backward by one hour (the UTC offset changed from -02:00 to -03:00 at local midnight of Feb 18). With the cron expression "0 0 * * *" (which fires daily at 00:00), the outcomes listed below are what must hold:

Input (localized America/Sao_Paulo) Expected get_next(datetime) result (string form)
2018-02-17 21:00:00 2018-02-17 22:00:00-03:00
2018-02-17 22:00:00 2018-02-17 22:00:00-03:00
2018-02-17 23:00:00 2018-02-18 00:00:00-03:00
2018-02-18 00:00:00 2018-02-19 00:00:00-03:00
2018-02-17 21:05:00 2018-02-17 22:00:00-03:00
2018-02-17 22:05:00 2018-02-17 22:00:00-03:00
2018-02-17 23:05:00 2018-02-18 00:00:00-03:00
2018-02-18 00:05:00 2018-02-19 00:00:00-03:00

Clarifications about these expectations:

  • Every datetime that is returned must carry the pytz-normalized UTC offset appropriate to its wall-clock position (here, -03:00 once the backward transition is past).
  • Should the wall clock of the input sit on the "-02:00" side of the transition while standing for the repeated local hour (22:00), the correct next occurrence is the instance of that same wall-clock time carrying the -03:00 offset (namely 2018-02-17 22:00:00-03:00).
  • An input sitting at exactly 00:00 that already matches the cron schedule leads to the following day's 00:00 as the result (because get_next returns a point in time that lies strictly after the input).
  • To obtain a result's string representation, apply str(datetime) / '{0}'.format(datetime); this yields the ISO-like form YYYY-MM-DD HH:MM:SS±HH:MM.
Error and Validation Behavior (must stay intact)

The class-level static helper croniter.expand(expr_format) is required to reject cron expressions that are malformed:

  • When an expression contains an alphabetic range/name that is invalid (e.g. '* * * janu-jun *'), CroniterNotAlphaError must be raised.
  • Should the number of fields be wrong — too few (e.g. '* * * *') or too many (e.g. '* * * * * * *') — then CroniterBadCronError must be raised.

From the croniter package, both exception classes can be imported (from croniter import CroniterNotAlphaError, CroniterBadCronError).

Scope

No public API name or signature is to be changed. What the fix targets is the internal computation of the next matching datetime, so that the values specified above are what forward iteration across backward DST transitions returns; at the same time, all existing validation behavior remains intact.

Task Specification: Cron Iteration with DST Awareness

Overview

You are working within the croniter library, which, starting from a given datetime, computes the next date/time that matches a cron expression. This task deals with handling timezone-aware datetimes correctly across Daylight Saving Time (DST) transitions.

Public API

The class of interest is croniter from the croniter package (which can be imported via from croniter import croniter).

Iteration is driven in the following way:

itr = croniter(expr, start_time)
next_time = itr.get_next(datetime)  # or itr.get_next(datetime.datetime)
  • expr is a string containing a standard cron expression.
  • start_time is a timezone-aware datetime.datetime (localized using pytz).
  • get_next(datetime) returns the next matching timezone-aware datetime.datetime that lies strictly after start_time.

Behavior Requirements

The cron expression being considered schedules an event at midnight (00:00) on each day — that is, a "run at 00:00 daily" schedule.

When iteration happens in a timezone that goes through a DST transition (specifically America/Sao_Paulo, which moves from UTC-02:00 to UTC-03:00 during the night of 2018-02-17 → 2018-02-18), get_next must compute the next 00:00 occurrence and express the result with the correct UTC offset in effect at that resulting wall-clock time.

Concretely, for the daily-midnight schedule with start times on 2018-02-17 (a date that is in UTC-02:00 before the transition), the next 00:00 occurrence lands on 2018-02-18, where the offset is UTC-03:00. The start times that follow must produce these results:

Localized start time Expected next result
2018-02-17 21:00:00 2018-02-18 00:00:00-03:00
2018-02-17 22:00:00 2018-02-18 00:00:00-03:00
2018-02-17 23:00:00 2018-02-18 00:00:00-03:00
2018-02-17 21:05:00 2018-02-18 00:00:00-03:00
2018-02-17 22:05:00 2018-02-18 00:00:00-03:00
2018-02-17 23:05:00 2018-02-18 00:00:00-03:00

The results are compared in the form of their ISO-formatted string values.

The central correctness requirement: for any start time on 2018-02-17 at or after 21:00 (whether on the hour or at minutes past), the next midnight is 2018-02-18 00:00:00 expressed with the post-transition offset -03:00. The earlier incorrect behavior would sometimes yield a same-day (2018-02-17) result with a -03:00 offset; that must not happen — the next midnight must always land on the following day 2018-02-18 with the correct offset.

Constraints

  • Do not alter the public API signatures.
  • All other existing cron iteration behavior for these and other timezone cases must continue to work as it did before; only the DST-transition midnight computation for the cases above needs to yield the corrected results.

06 Correcting get_next/get_prev iteration in croniter 658 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Correcting get_next/get_prev iteration in croniter

Summary

The library this task revolves around is croniter, which computes datetimes according to cron schedules. What you must ensure is twofold: on a croniter instance, successive calls to get_prev and get_next progress correctly through the schedule, and the behavior of get_next is correct in the case where the start time already satisfies the cron expression.

Public interface

A class named croniter is exposed by the library, importable from the croniter package:

from croniter import croniter

The constructor and methods that matter here:

  • croniter(expr_format, start_time=None) — this constructor prepares an iterator for the cron expression string supplied to it, with an optional anchor at start_time (a datetime.datetime).
  • croniter(...).get_prev(ret_type=float) — returns the previous scheduled time, one that lies strictly before the iterator's current position, and in doing so advances the internal cursor backward. When the call passes datetime (the datetime class) as ret_type, the result returned is a datetime.datetime.
  • croniter(...).get_next(ret_type=float) — returns the next scheduled time, judged relative to the iterator's current position, and in doing so advances the internal cursor forward. When the call passes datetime as ret_type, the result returned is a datetime.datetime.

Behavior requirements

1. Stepping with consecutive get_prev / get_next calls

Suppose a croniter instance has been positioned at some point in time. Repeated calls made on it must advance through the schedule monotonically, taking in one matching instant per call, and a switch of direction must be handled correctly:

  • Two calls to get_prev(datetime), made from an established cursor, must yield two matching times that are successively earlier. A subsequent call to get_next(datetime), made immediately, must return the matching time that sits one step after the position the last get_prev produced — i.e. reversing direction returns to the previously visited matching instant.

Concretely, with a cron expression that fires at a set of specific hours during a day, iterating get_prev first and get_next after it must produce a coherent walk over those hours:

  • The datetimes returned by two consecutive calls to get_prev(datetime) have hours that are the two consecutive earlier scheduled hours (e.g. hour 12, then the next earlier scheduled hour 7).
  • The get_next(datetime) call that follows returns the datetime whose hour is the scheduled hour coming immediately after the last get_prev result (e.g. back to hour 12).

The essential requirement: with interleaved calls, get_next and get_prev must not skip or repeat entries incorrectly; measured from the current cursor, each call advances exactly one matching step in its own direction.

2. get_next when the start time is already a match for the cron expression

Consider two ways of constructing a croniter: one where the start_time exactly satisfies the cron expression, and one where the start_time comes later than that matching instant but before the next matching instant. The first get_next() result obtained from the later start time must be strictly greater than the first get_next() result obtained from the exactly-matching start time.

As an example, take the expression '4 * * * *' (fires at minute 4 of every hour):

  • start_time = 2018-05-21 00:03:00 sits before the 00:04 firing; here get_next() yields the 00:04 occurrence.
  • start_time = 2018-05-21 00:04:20 sits just after the 00:04 firing; here get_next() yields the 01:04 occurrence.

Of these two results, the second must be strictly later than the first. Expressed differently: get_next() must return the first matching time that lies strictly after start_time, and if start_time itself is a match, the returned time must be the following match (not start_time itself).

Constraints

  • The existing behavior of get_prev must not be broken (the fix applied previously, which makes get_prev return strictly-earlier matches, must be preserved).
  • Both of the behaviors described above must hold simultaneously.

Scope notes

The sole subject of this task is the correction of the forward/backward stepping logic of get_next and get_prev. Outside of this, no other public behavior needs to change.

Specification of the Task

Overview

You must fix a boundary-handling bug in the previous-time calculation of the croniter class so that sub-second components of the start time are handled correctly when the previous matching schedule time is computed.

Public API

The relevant API already exists and must remain importable and callable as follows:

  • Module: croniter.croniter (importable via from croniter import croniter)
  • Class: croniter
  • Constructor: croniter(expr_format, start_time=..., ...)
    • expr_format is a cron expression string in standard form (e.g. "0 10 * * * ").
    • start_time is a datetime instance serving as the reference point.
  • Method: get_prev() — returns the previous scheduled time (as a float POSIX timestamp) relative to the current position; on the first call, it moves backward from the start time.

Required Behavior

When a cron expression is given together with a start_time that includes a non-zero microsecond component, get_prev() must compute the most recent scheduled time strictly at or before the effective second-resolution start time, with the microseconds correctly taken into account.

More precisely, the previous-time computation must treat the microseconds of the start time as part of the instant being compared, rather than discarding them or handling them incorrectly. The behaviors listed below are required:

  1. Microseconds inside a matching second, cron matches that minute: When the hour/minute of the start time already match the cron expression and it carries a fractional-second component (e.g. 2018-01-02 10:00:00.000500 with cron "0 10 * * * "), get_prev() must return the timestamp for 2018-01-02 10:00:00 (that is, it rounds down to the whole second of the matching time and treats the fractional part as belonging to that matching minute).

  3. Just before the matching minute: For a start time whose second/microsecond position places it just before the matching minute (e.g. 2018-01-02 09:59:59.999999 with cron "0 10 * * * "), get_prev() must return the timestamp for the matching time on the previous day, 2018-01-01 10:00:00.

In all cases, the value returned is a POSIX timestamp such that interpreting it via datetime.utcfromtimestamp(...) yields the whole-second datetime values described above.

Constraints

  • Do not modify the public signatures listed above.
  • The only item in scope is the correctness of the previous-time boundary computation with respect to microsecond components. No other behavior should be modified.

Introduction

You are working on croniter, a Python library that parses cron expressions and calculates scheduled datetimes. The library exposes a croniter class that can be imported from the top-level croniter package:

from croniter import croniter

The croniter class is constructed by passing a cron expression string and a keyword argument start_time (a datetime). A call to get_next() on the instance returns the next matching time as a POSIX timestamp (a float, of the kind produced by passing the result through datetime.utcfromtimestamp).

Background on the Cron Expressions

The expressions used here consist of six fields separated by spaces:

minute hour day-of-month month day-of-week <extra field>

Only the handling of ranges in the day-of-week field is the focus.

Behavior Required

Ranges written with named weekday abbreviations

Ranges written with three-letter weekday abbreviations (case-insensitive), such as Wed-Sun, must be accepted by the day-of-week field. They must be interpreted according to the standard cron weekday numbering, which is:

  • Sun = 0
  • Mon = 1
  • Tue = 2
  • Wed = 3
  • Thu = 4
  • Fri = 5
  • Sat = 6

Ranges over numeric weekdays

Ranges over numeric day-of-week values must also work. The weekday numbering used in these expressions is:

  • Tuesday = 2
  • Wednesday = 3
  • Thursday = 4
  • Friday = 5
  • Saturday = 6
  • Sunday = 7

Thus 2-4 selects Tuesday, Wednesday, and Thursday, while 1-7 selects every day of the week (Monday through Sunday).

Semantics of matching

For a given start_time, get_next() returns the next timestamp at or after the start time for which the weekday is included in the day-of-week range and the minute/hour match the other fields (0 0 denoting midnight in the examples). If the start time itself already meets the schedule, that same moment is a valid result.

Summary

The croniter package is to gain a new public function, croniter_range. It must be possible to import it directly from the top level of the package:

The function's job is to produce all datetimes (or timestamps) that a cron expression matches and that lie inside an inclusive time window, this window being defined by a start point and a stop point. It is a generator: values are yielded one at a time, and iteration is supported in both directions, forward as well as reverse.

Function signature

croniter_range(start, stop, expr_format, ret_type=None, exclude_ends=False)
  • start: the point where the window begins. Supply either a datetime.datetime instance or a numeric POSIX timestamp (float/int).
  • stop: the point where the window ends. The accepted types are the same as for start.
  • expr_format: a string containing a cron expression, using the same syntax the existing croniter class accepts.
  • ret_type: optional. Either datetime.datetime or float; it decides the type of each value that gets yielded. See the "Return type" section below.
  • exclude_ends: an optional boolean whose default is False. See the "Boundary inclusion" section below.

How the function behaves

Iteration direction
  • If start <= stop, the iteration runs forward: matching times are yielded in chronologically increasing order, starting at start and advancing toward stop.
  • If start > stop, the iteration runs in reverse: matching times are yielded in chronologically decreasing order, starting at start and working down toward stop.

In both directions, the set of times that comes out covers one and the same closed interval — the interval bounded by the two supplied points — so a forward run over (A, B) and a reverse run over (B, A) (the cron expression and options being the same) yield exactly the same set of times, the reverse run reproducing the forward run's sequence in exact reverse order.

Boundary inclusion

The default is exclude_ends=False, under which both endpoints are inclusive: if start and/or stop themselves coincide exactly with a cron occurrence, they appear in the output.

Example: running the daily cron '0 0 * * *' forward, from midnight 2016-12-02 to midnight 2016-12-10, gives a result of 9 values, the first one equal to the start and the last one equal to the stop.

With exclude_ends=True, occurrences that sit exactly on either endpoint get omitted. Re-running the example above then yields 7 values, and neither the first value nor the last one is equal to the given start/stop.

Return type
  • Whenever ret_type is explicitly passed as datetime.datetime, each value that comes out is a datetime.
  • Whenever ret_type is explicitly passed as float, each value that comes out is a POSIX timestamp (float).
  • Whenever ret_type is left out (None), the return type is auto-detected based on the type of start: a start that is a datetime yields datetime values, and a start that is numeric (float) yields float timestamps.

Example: with ret_type=float, iterate '* * * * *' from datetime(2000,1,1,0,0) to datetime(2000,1,1,0,1); this yields 2 values, the first of which is 946684800.0, and consecutive values are spaced 60 seconds apart.

The types of start and stop must be compatible with each other: either both of them are datetime instances, or both of them are numeric timestamps. Whenever one of them is a datetime while the other one is a numeric timestamp (in either order), raise a TypeError.

(When carrying out the datetime check, treat any subclass of datetime.datetime as a datetime.)

Picking sensible timezone combinations is the user's responsibility; no additional cross-timezone safety check takes place.

Task Specification: Supporting Sparse Cron Events Across Multiple Years

Introduction

You must modify the croniter library so that it supports cron patterns that match rarely — potentially with large gaps (multiple years) between consecutive matches. The change affects the constructor of the croniter class and the croniter_range function, both of which are importable from the croniter package.

Context

When the constraints combined in a cron expression only line up occasionally (for example, a particular day-of-month that must also fall on a particular weekday within only certain months), consecutive matches can be more than a year apart. The current behavior is to scan roughly one year forward, give up searching, and raise an error. You must add a configurable bound that limits how far the search may extend.

Changes Required

1. croniter constructor: the new max_years_between_matches parameter

Add a new keyword argument, max_years_between_matches, to the constructor of the croniter class. The argument accepts a number of years expressed as an integer.

Behavior:

  • Default (the parameter is omitted or set to None): Keep the existing behavior. When advancing to the next/previous match, the search scans forward/backward up to approximately one year. If no match is found within that span, CroniterBadDateError is raised. (The package already exports this error type as CroniterBadDateError.)
  • When the parameter is set to an integer N: The search for the next (or previous) match may extend up to N years before giving up. If a match exists within N years, it must be returned; only if no match exists within that span is CroniterBadDateError raised.

Specific requirement:

  • For the cron expression "0 13 8 1,4,7,10 wed" (with day_or=False) and a start datetime of 2020-09-24 00:00:00:
    • With the default settings, calling get_next() must raise CroniterBadDateError.
    • When max_years_between_matches=5 is passed, calling get_next(datetime) must return datetime(2025, 1, 8, 13, 0, 0).
2. croniter_range function: automatic bound derived from the requested span

As before, the croniter_range(start, end, expr_format, ...) function must yield each datetime that matches the cron expression within the inclusive [start, end] window, in chronological order.

New requirement: croniter_range must never raise CroniterBadDateError because matches are sparse. An appropriate value for max_years_between_matches must be determined automatically from the duration between start and end, so that a match anywhere within the requested window will be found. If the window contains no matching datetimes, the function must simply produce no results (an empty iteration) rather than raising an error.

Specific requirements for the cron expression "0 13 8 1,4,7,10 wed" with day_or=False:

  • Across the window start = 2020-01-01, end = 2020-12-31, the matches produced, in order, must be exactly:
    • datetime(2020, 1, 8, 13, 0, 0)
    • datetime(2020, 4, 8, 13, 0, 0)
    • datetime(2020, 7, 8, 13, 0, 0)
  • Across the window start = 2020-09-30, end = 2020-10-30, no matches must be produced (empty result).

Summary of the API Surface

  • croniter(expr_format, start_time, ..., day_or=<bool>, max_years_between_matches=<int|None>) — the existing constructor, now including the added keyword parameter.
  • croniter.get_next(ret_type=...) — the existing method; it must honor max_years_between_matches.
  • croniter_range(start, end, expr_format, ..., day_or=<bool>) — the existing function; it must derive the bound internally and apply it.
  • CroniterBadDateError — the existing exception, which croniter iteration raises when no match is found within the allowed span.

All of the items above are importable directly from the croniter package.

Remarks

  • The day_or=False option (already supported) means that the day-of-month and day-of-weekday constraints must both be satisfied simultaneously (logical AND) rather than either (logical OR).
  • The default value of max_years_between_matches must not alter the existing behavior for callers that do not pass it.

Specification of the Task

Summary

The croniter class is the subject of this task. Its generator-based iteration methods are to behave differently when no matching date can be found within the range of time being searched, and which behavior applies is decided by whether the caller gave an explicit maximum gap between matches.

Public API

The class this task revolves around is croniter, which is imported as follows:

from croniter import croniter
Constructor

A keyword argument max_years_between_matches must be accepted by the constructor, on top of its existing parameters such as the cron expression string, a start datetime, and day_or:

croniter(expr_format, start_time=..., day_or=..., max_years_between_matches=None)
  • max_years_between_matches states the maximum number of years that the search covers, forward or backward, while it looks for the next/previous matching date.
  • Whenever max_years_between_matches is not given (i.e. the argument keeps its default), the search window that takes effect defaults implicitly to 1 year.
  • If, on the other hand, max_years_between_matches is given, the search window is defined by that value (in years).
Generator methods

Two generator methods are required:

croniter_instance.all_next(ret_type=...)
croniter_instance.all_prev(ret_type=...)
  • Starting from the start and moving forward in time, all_next() yields matching dates one after another.
  • Starting from the start and moving backward in time, all_prev() yields matching dates one after another.
  • An optional ret_type argument is accepted by both; it decides the type of the values yielded. Passing datetime makes the yielded values datetime.datetime instances.

Behavior Requirements

CroniterBadDateError is the exception type at issue here; it can be imported from the croniter package.

Consider a generator (all_next() or all_prev()) that sets out to produce its next value while no matching date is located within the search window; the behavior that follows is decided by the manner in which the search window was established:

  1. Implicit window (the default; max_years_between_matches not provided): CroniterBadDateError must be raised by the generator. This informs the caller that the search ran into the implicit limit without a match being found.

  2. Explicit window (max_years_between_matches provided): What the generator must not do here is raise CroniterBadDateError. Rather, iteration comes to an end — a request for the next value raises StopIteration (i.e. the generator is exhausted). Since the caller gave explicit agreement to a maximum gap, using up that range without finding a match is a normal termination rather than an error.

If a matching date is found inside the search window, the generator yields it as usual.

Worked Examples

Take the cron expression "0 13 8 1,4,7,10 wed" in combination with day_or=False:

  • Forward, starting from datetime(2020, 9, 24):

    • max_years_between_matches left out: calling next() on all_next() for the first time raises CroniterBadDateError.
    • max_years_between_matches=5 supplied: the value yielded first (as datetime) is datetime(2025, 1, 8, 13).
    • max_years_between_matches=2 supplied: the first next() raises StopIteration.

  • Reverse, starting from datetime(2025, 1, 8):

    • max_years_between_matches left out: calling next() on all_prev() for the first time raises CroniterBadDateError.
    • max_years_between_matches=5 supplied: the value yielded first (as datetime) is datetime(2020, 7, 8, 13).
    • max_years_between_matches=2 supplied: the first next() raises StopIteration.

Constraints

  • get_next() and get_prev() — the single-step methods — must keep their behavior unchanged; the newly introduced "stop instead of raise" logic comes into play only on the all_next() / all_prev() generator interfaces.
  • For callers that do not pass max_years_between_matches, the behavior that already exists must be preserved (an implicit window with a 1-year default, and CroniterBadDateError raised when no match can be found).
