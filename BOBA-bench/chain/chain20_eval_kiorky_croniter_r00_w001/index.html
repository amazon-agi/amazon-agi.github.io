01 Support "Nth weekday of month" cron syntax in croniter 529 words · source specification

Task Specification: Support "Nth weekday of month" cron syntax in croniter

Overview

Extend the croniter class (importable as from croniter import croniter) to support the # operator in the day-of-week field of a cron expression. This operator restricts a weekday to a specific occurrence within the month (e.g., "the first Saturday" or "the fifth Wednesday").

Public API

The change concerns the existing constructor and iteration methods:

  • croniter(expr_format, start_time=..., day_or=...) — the constructor accepting a cron expression string and a base datetime.
  • croniter.get_next(datetime) — returns the next matching datetime after the current position and advances the iterator forward.
  • croniter.get_prev(datetime) — returns the previous matching datetime before the current position and advances the iterator backward.

No new module paths, classes, or function names are introduced.

Syntax to Support

In the day-of-week field (the 5th field), an entry may take the form:

<weekday>#<n>

where:

  • <weekday> is a weekday specifier, which may be a numeric value or a three-letter lowercase abbreviation (e.g., sat, sun, wed, mon).
  • <n> is an integer occurrence index from 1 upward, indicating the nth occurrence of that weekday within a given month.

Multiple such terms may be combined in the same field, comma-separated, e.g.:

sat#1,sun#2

Each term matches independently.

Semantics

<weekday>#<n> matches a date if and only if that date's weekday equals <weekday> and the date is the <n>-th occurrence of that weekday within its calendar month.

For example:

  • sat#1 matches only the first Saturday of each month.
  • sun#2 matches only the second Sunday of each month.
  • wed#5 matches only the fifth Wednesday of a month, which exists only in months that contain five Wednesdays. Months without a fifth Wednesday produce no match for that term.

Behavior Requirements

Forward iteration (get_next)

Given the expression 0 0 * * sat#1 with base datetime(2010, 2, 25):

  • The first matching datetime is the first Saturday of March 2010: 2010-03-06 (a Saturday).
  • The next is the first Saturday of April 2010: 2010-04-03 (a Saturday).

Given the expression 0 0 * * wed#5 with base datetime(2010, 1, 25):

  • The first match is 2010-03-31 (the fifth Wednesday of March 2010).
  • The next is 2010-06-30 (the fifth Wednesday of June 2010).
  • The next is 2010-09-29 (the fifth Wednesday of September 2010).

Months that do not contain a fifth Wednesday are skipped entirely.

Backward iteration (get_prev)

Given the expression 0 0 * * sat#1,sun#2 with base datetime(2010, 8, 25, 15, 56):

  • The first previous match is 2010-08-08 00:00 (the second Sunday of August 2010).
  • The next previous match is 2010-08-07 00:00 (the first Saturday of August 2010).
  • The next previous match is 2010-07-11 00:00 (the second Sunday of July 2010).

All produced datetimes carry the hour and minute dictated by the minute/hour fields of the expression (0 0 → 00:00).

Constraints on Scope

  • The time (minute/hour) and other fields continue to behave as they already do; only the day-of-week # operator behavior is added.
  • The # operator applies to the day-of-week field only.
  • Matching combines correctly with the standard month/day-of-month/day-of-week matching rules already in place.

Task Specification: Croniter Error Hierarchy and Validation Method

Overview

You must extend the croniter package to provide a structured exception hierarchy for cron-parsing errors and a class method for validating cron expressions.

Public API Surface

All of the following must be importable directly from the croniter package:

from croniter import croniter, CroniterBadDateError, CroniterBadCronError, CroniterNotAlphaError
Exception Classes

Define the following exception classes:

  1. CroniterError — a base exception class for all croniter-related errors. It must derive from ValueError.

  2. CroniterBadCronError — raised when a cron expression has an invalid structure (e.g., the wrong number of fields). Must be a subclass of CroniterError.

  3. CroniterNotAlphaError — raised when a cron expression contains an unrecognized alphabetic token (e.g., an invalid month/day-of-week name). Must be a subclass of CroniterError.

  4. CroniterBadDateError — (already exists in the codebase / must remain importable) an error related to date computation. Must be a subclass of CroniterError.

Because these exceptions all derive from CroniterError (and therefore ValueError), catching the base class must catch any of the specific errors.

croniter.expand

expand must be callable as a class method / static-style method on croniter, i.e. croniter.expand('<cron expression>'). It parses/expands a cron expression string and must raise errors as follows:

  • A cron expression with the wrong number of whitespace-separated fields must raise CroniterBadCronError. Specifically:
    • '* * * *' (too few fields) must raise CroniterBadCronError.
    • '* * * * * * *' (too many fields) must raise CroniterBadCronError.
  • A cron expression containing an alphabetic token that cannot be recognized must raise CroniterNotAlphaError. Specifically:
    • '* * * janu-jun *' must raise CroniterNotAlphaError.
croniter.is_valid

Add a class method:

croniter.is_valid(expression) -> bool

It validates a cron expression string by attempting expansion and reporting whether the expression is well-formed:

  • Returns True for a valid expression (e.g., '0 * * * *').
  • Returns False for a structurally invalid expression (e.g., '0 * *', which has too few fields).
  • Returns False for an expression with an unrecognized alphabetic token (e.g., '* * * janu-jun *').

In other words, is_valid must catch any CroniterError produced during validation and translate it into a False return value, returning True only when no such error occurs.

Notes

  • A valid standard cron expression consists of exactly five whitespace-separated fields.
  • Existing behavior of croniter (iteration, get_next, timezone handling, etc.) must remain intact.

get_next(ret_type)   # e.g. get_next(datetime)

which returns the next datetime matching the cron expression, strictly after the provided start_time.

Problem

When iterating forward across a Daylight Saving Time (DST) transition in a timezone where clocks are moved backward (a "fall back" transition, where the local wall-clock time repeats and the UTC offset increases), get_next produces incorrect results. Specifically, for the timezone America/Sao_Paulo, which on the night of 2018-02-17/18 shifts its clocks backward by one hour (from UTC offset -02:00 to -03:00 at local midnight of Feb 18), the following must hold for the cron expression "0 0 * * *" (fires daily at 00:00):

2018-02-17 21:00:00 2018-02-17 22:00:00-03:00
2018-02-17 22:00:00 2018-02-17 22:00:00-03:00
2018-02-17 23:00:00 2018-02-18 00:00:00-03:00
2018-02-18 00:00:00 2018-02-19 00:00:00-03:00
2018-02-17 21:05:00 2018-02-17 22:00:00-03:00
2018-02-17 22:05:00 2018-02-17 22:00:00-03:00
2018-02-17 23:05:00 2018-02-18 00:00:00-03:00
2018-02-18 00:05:00 2018-02-19 00:00:00-03:00

Notes on these expectations:

  • An expression with the wrong number of fields — too few (e.g. '* * * *') or too many (e.g. '* * * * * * *') — must raise CroniterBadCronError.

Both exception classes are importable from the croniter package (from croniter import CroniterNotAlphaError, CroniterBadCronError).

Do not change any public API names or signatures. The fix concerns the internal computation of the next matching datetime so that forward iteration across backward DST transitions returns the values specified above, while all existing validation behavior is preserved.

Public API

The relevant class is croniter in the croniter package (importable as from croniter import croniter).

The iteration is driven by:

next_time = itr.get_next(datetime)  # or itr.get_next(datetime.datetime)
  • expr is a standard cron expression string.
  • start_time is a timezone-aware datetime.datetime (localized via pytz).
  • get_next(datetime) returns the next matching timezone-aware datetime.datetime strictly after start_time.

Required Behavior

The cron expression under consideration schedules an event at midnight (00:00) each day — i.e., a "run at 00:00 daily" schedule.

When iterating within a timezone that undergoes a DST transition (specifically America/Sao_Paulo, which shifts from UTC-02:00 to UTC-03:00 during the night of 2018-02-17 → 2018-02-18), get_next must compute the next 00:00 occurrence and represent the result with the correct UTC offset in effect at that resulting wall-clock time.

Concretely, for the daily-midnight schedule with start times on 2018-02-17 (which is in UTC-02:00 before the transition), the next 00:00 occurrence falls on 2018-02-18, at which point the offset is UTC-03:00. The following start times must produce the following results:

Start time (localized) Expected next result
2018-02-17 21:00:00 2018-02-18 00:00:00-03:00
2018-02-17 22:00:00 2018-02-18 00:00:00-03:00
2018-02-17 23:00:00 2018-02-18 00:00:00-03:00
2018-02-17 21:05:00 2018-02-18 00:00:00-03:00
2018-02-17 22:05:00 2018-02-18 00:00:00-03:00
2018-02-17 23:05:00 2018-02-18 00:00:00-03:00

The previous incorrect behavior would sometimes yield a same-day (2018-02-17) result with a -03:00 offset; that must not happen — the next midnight must always land on the following day 2018-02-18 with the correct offset.

  • All other existing cron iteration behavior for these and other timezone cases must continue to work as before; only the DST-transition midnight computation for the cases above needs to yield the corrected results.

06 Fix get_next/get_prev iteration in croniter 569 words · source specification

Task Specification: Fix get_next/get_prev iteration in croniter

Overview

You are working on the croniter library, which computes cron-schedule datetimes. You must ensure that consecutive calls to get_prev and get_next on a croniter instance step correctly through the schedule, and that get_next behaves correctly when the start time already satisfies the cron expression.

Public API

The library exposes a class croniter importable from the croniter package:

from croniter import croniter

Relevant constructor and methods used:

  • croniter(expr_format, start_time=None) — construct an iterator for the given cron expression string, optionally anchored at a start_time (a datetime.datetime).
  • croniter(...).get_prev(ret_type=float) — return the previous scheduled time strictly before the iterator's current position, advancing the internal cursor backward. When called with datetime (the datetime class) as ret_type, returns a datetime.datetime.
  • croniter(...).get_next(ret_type=float) — return the next scheduled time relative to the iterator's current position, advancing the internal cursor forward. When called with datetime as ret_type, returns a datetime.datetime.

Required Behavior

1. Consecutive get_prev / get_next stepping

Given a croniter instance positioned at some point in time, repeated calls must move monotonically through the schedule, one matching instant per call, and direction switches must be handled correctly:

  • Starting from an established cursor, calling get_prev(datetime) twice must yield two successively earlier matching times. Then immediately calling get_next(datetime) must return the matching time that lies one step after the position produced by the last get_prev — i.e. reversing direction returns to the previously visited matching instant.

Concretely, for a cron expression that fires at a set of specific hours during a day, iterating get_prev then get_next must produce a coherent walk over those hours:

  • Two consecutive get_prev(datetime) calls return datetimes whose hours are the two consecutive earlier scheduled hours (e.g. hour 12, then the next earlier scheduled hour 7).
  • A following get_next(datetime) call returns the datetime whose hour is the scheduled hour immediately after the last get_prev result (e.g. back to hour 12).

The key requirement: get_next and get_prev must not skip or repeat entries incorrectly when their calls are interleaved; each call advances exactly one matching step in its direction from the current cursor.

2. get_next when the start time already matches the cron expression

When a croniter is constructed with a start_time that exactly satisfies the cron expression, and when constructed with a start_time that is later than that matching instant but before the next matching instant, the first get_next() result for the later start time must be strictly greater than the first get_next() result for the exactly-matching start time.

Example: for the expression '4 * * * *' (fires at minute 4 of every hour):

  • With start_time = 2018-05-21 00:03:00 (before the 00:04 firing), get_next() yields the 00:04 occurrence.
  • With start_time = 2018-05-21 00:04:20 (just after the 00:04 firing), get_next() yields the 01:04 occurrence.

The second result must be strictly later than the first. In other words, get_next() must return the first matching time strictly after start_time; if start_time itself is a match, the returned time must be the following match (not start_time itself).

Constraints

  • Do not break existing behavior of get_prev (a previously applied fix that makes get_prev return strictly-earlier matches must be preserved).
  • The two behaviors above must both hold simultaneously.

Notes on scope

This task is purely about correcting the forward/backward stepping logic of get_next and get_prev. No other public behavior needs to change.

Overview

You must fix a boundary-handling bug in the croniter class's previous-time calculation so that sub-second components of the start time are handled correctly when computing the previous matching schedule time.

Public API

The relevant API is already present and must remain importable and callable as follows:

  • Module: croniter.croniter (importable as from croniter import croniter)
  • Class: croniter
  • Constructor: croniter(expr_format, start_time=..., ...)
    • expr_format is a standard cron expression string (e.g. "0 10 * * * ").
    • start_time is a datetime instance used as the reference point.
  • Method: get_prev() — returns the previous scheduled time (as a float POSIX timestamp) relative to the current position, moving backward from the start time on first call.

Required Behavior

Given a cron expression and a start_time that includes a non-zero microsecond component, get_prev() must compute the most recent scheduled time strictly at or before the effective second-resolution start time, correctly accounting for the microseconds.

Specifically, the previous-time computation must treat the start time's microseconds as part of the instant being compared, rather than discarding or mishandling them. The following behaviors are required:

  1. Microseconds within a matching second, cron matches that minute: For a start time whose hour/minute already match the cron expression and which carries a fractional-second component (e.g. 2018-01-02 10:00:00.000500 with cron "0 10 * * * "), get_prev() must return the timestamp for 2018-01-02 10:00:00 (i.e. it rounds down to the whole second of the matching time, treating the fractional part as belonging to that matching minute).

  2. One second past the matching minute: For a start time one second beyond the matching time (e.g. 2018-01-02 10:00:01.000000 with cron "0 10 * * * "), get_prev() must return the timestamp for 2018-01-02 10:00:00.

  3. Just before the matching minute: For a start time whose second/microsecond place it just before the matching minute (e.g. 2018-01-02 09:59:59.999999 with cron "0 10 * * * "), get_prev() must return the timestamp for the previous day's matching time, 2018-01-01 10:00:00.

In all cases the returned value is a POSIX timestamp such that interpreting it via datetime.utcfromtimestamp(...) yields the whole-second datetime values described above.

Constraints

  • Do not change the public signatures listed above.
  • Only the correctness of the previous-time boundary computation with respect to microsecond components is in scope. No other behavior should be altered.

Task Specification: Croniter Sub-Second Boundary Handling

Overview

You are working on the croniter package, which computes cron schedule instants (previous/next) relative to a starting time. This task requires correcting the behavior of the next-instant computation when the start time is within one second before a matching cron instant.

Public API

The package must expose the following from the top-level croniter package (importable as from croniter import ...):

  • croniter — the main class.
  • CroniterBadDateError
  • CroniterBadCronError
  • CroniterNotAlphaError
croniter class

Constructor signature (relevant parameters):

croniter(expr_format, start_time=..., ret_type=...)
  • expr_format: a cron expression string (5-field standard cron), e.g. "0 10 * * *".
  • start_time: the reference time. May be provided as a keyword argument. When given as a datetime, it is used as the reference point for computing instants.
  • ret_type: when set to datetime, the methods get_prev() and get_next() return datetime objects rather than the default numeric type.

Methods:

  • get_next() — returns the next cron instant strictly after the start time. With ret_type=datetime, returns a datetime.
  • get_prev() — returns the previous cron instant at or before the start time. With ret_type=datetime, returns a datetime.

Required Behavior

Case 1: start time is fractionally past a matching instant

  • get_prev() → datetime(2018, 1, 2, 10, 0)

Case 2: start time is just over one second past a matching instant

Start time = 2018-01-02 10:00:01.000000 (1 second after 10:00:00):

  • get_prev() → datetime(2018, 1, 2, 10, 0)
  • get_next() → datetime(2018, 1, 3, 10, 0)
Case 3: start time is a fraction of a second before a matching instant

Overview

Modify the croniter class to change how its generator-based iteration methods behave when a matching date cannot be found within the searched time range, depending on whether the caller explicitly specified a maximum gap between matches.

Public API

The relevant class is croniter, importable as:

from croniter import croniter
Constructor

The constructor must accept a keyword argument max_years_between_matches (in addition to its existing parameters such as the cron expression string, a start datetime, and day_or):

croniter(expr_format, start_time=..., day_or=..., max_years_between_matches=None)
  • max_years_between_matches specifies the maximum number of years to search forward or backward when looking for the next/previous matching date.
  • When max_years_between_matches is not provided (i.e. left at its default), the effective search window is an implicit default of 1 year.
  • When max_years_between_matches is provided, that value (in years) defines the search window.
Generator methods

Two generator methods must exist:

croniter_instance.all_next(ret_type=...)
croniter_instance.all_prev(ret_type=...)
  • all_next() yields successive matching dates moving forward in time from the start.
  • all_prev() yields successive matching dates moving backward in time from the start.
  • Both accept an optional ret_type argument controlling the type of the yielded values. When datetime is passed, yielded values are datetime.datetime instances.

Required Behavior

The exception type involved is CroniterBadDateError, importable from the croniter package.

When a generator (all_next() or all_prev()) attempts to produce the next value and no matching date is found within the search window, the behavior depends on how the search window was determined:

  1. Implicit window (default, max_years_between_matches not provided): The generator must raise CroniterBadDateError. The caller is notified that the search hit the implicit limit without finding a match.

  2. Explicit window (max_years_between_matches provided): The generator must not raise CroniterBadDateError. Instead, iteration simply ends — requesting the next value raises StopIteration (i.e. the generator is exhausted). The caller explicitly agreed to a maximum gap, so exhausting that range without a match is a normal termination, not an error.

When a matching date is found within the search window, the generator yields it normally.

Concrete Examples

Using the cron expression "0 13 8 1,4,7,10 wed" with day_or=False:

  • Forward, start datetime(2020, 9, 24):

    • With no max_years_between_matches: first next() on all_next() raises CroniterBadDateError.
    • With max_years_between_matches=5: first yielded value (as datetime) is datetime(2025, 1, 8, 13).
    • With max_years_between_matches=2: first next() raises StopIteration.

  • Reverse, start datetime(2025, 1, 8):

    • With no max_years_between_matches: first next() on all_prev() raises CroniterBadDateError.
    • With max_years_between_matches=5: first yielded value (as datetime) is datetime(2020, 7, 8, 13).
    • With max_years_between_matches=2: first next() raises StopIteration.

Constraints

  • The single-step methods get_next() and get_prev() must remain unchanged in behavior; the new "stop instead of raise" logic applies only to the all_next() / all_prev() generator interfaces.
  • Existing behavior for callers that do not pass max_years_between_matches must be preserved (default 1-year implicit window, raising CroniterBadDateError on failure to find a match).
