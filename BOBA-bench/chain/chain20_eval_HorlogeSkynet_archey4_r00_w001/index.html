Task Specification: Module for Managing ANSI Colors

Goal

The work has two parts. First, a new module archey.colors is to be created, and it is this module that centralizes ANSI escape-code color management. Second, it is to be integrated into the existing entry (Disk, RAM) and Output components, so that these components use this module for coloring.

Class Colors

Within archey/colors.py, a class called Colors is to be defined. This class plays two roles at once: it is both a set of named color constants and a small utility for producing/selecting ANSI escape codes.

Named color members of the class

Members whose string representation resolves to specific ANSI escape sequences must be exposed by Colors. The __str__ of each member must return a complete ANSI escape sequence having the form \x1b[<attrs>m.

The members listed below are required, each with the exact string representation shown:

Member value of str(...)
Colors.CLEAR \x1b[0m
Colors.CYAN_BRIGHT \x1b[1;36m
Colors.GREEN_NORMAL \x1b[0;32m
Colors.YELLOW_NORMAL \x1b[0;33m
Colors.RED_NORMAL \x1b[0;31m

For a member, its "attributes" are whatever lies between \x1b[ and m; specifically:

  • CLEAR → 0
  • CYAN_BRIGHT → 1;36
  • GREEN_NORMAL → 0;32
  • YELLOW_NORMAL → 0;33
  • RED_NORMAL → 0;31

Applying str() to any member must wrap the attributes of that member as \x1b[<attrs>m.

Static methods and utility helpers

Colors.escape_code_from_attrs(attributes)

  • The input accepted is a string of semicolon-separated ANSI attributes (e.g. '0;31' or '0;31;45').
  • What the method returns is the full escape sequence string \x1b[<attributes>m.
  • Examples:
    • escape_code_from_attrs('0;31') → '\x1b[0;31m'
    • escape_code_from_attrs('0;31;45') → '\x1b[0;31;45m'

Colors.get_level_color(value, warning_threshold, danger_threshold)

  • The color member it selects is determined by the position of value relative to two ascending thresholds.
  • Returns:
    • Colors.GREEN_NORMAL for a value below warning_threshold.
    • Colors.YELLOW_NORMAL for a value that is at/above warning_threshold while still below danger_threshold.
    • Colors.RED_NORMAL for a value at/above danger_threshold.
  • Examples:
    • get_level_color(25, 50, 75) → Colors.GREEN_NORMAL
    • get_level_color(34, 33, 66) → Colors.YELLOW_NORMAL
    • get_level_color(90, 33, 66) → Colors.RED_NORMAL

Integration points

Entry Disk (archey/entries/disk.py)

Disk().value must yield a value in which the appropriate level color is embedded as a raw ANSI escape sequence; the disk usage level determines the choice, such that:

  • In the regular/low usage case, a substring equal to str(Colors.GREEN_NORMAL) shows up in the value.
  • In the warning usage case, a substring equal to str(Colors.YELLOW_NORMAL) shows up in the value.
  • (Those substrings turn up next to the numeric usage figures that are already present in the output.)
Entry RAM (archey/entries/ram.py)

In the value that RAM().value produces, the appropriate level color must be embedded as a raw ANSI escape sequence; the RAM usage level determines the choice, such that:

  • For low usage, the value contains a substring equal to str(Colors.GREEN_NORMAL).
  • For warning usage, the value contains a substring equal to str(Colors.YELLOW_NORMAL).
  • For danger usage, the value contains a substring equal to str(Colors.RED_NORMAL).
Component Output (archey/output.py)

The result lines shown to the user are assembled by the Output class. On the color side, its behavior must be the following:

  • A module-level COLOR_DICT must be exposed by archey.output, mapping distributions (keys of type Distributions, e.g. Distributions.DEBIAN) to a list of color strings. No special 'clear' key is part of this mapping any longer — the clearing sequence comes from Colors.CLEAR.

  • A module-level LOGOS_DICT must be exposed by archey.output as well; it maps distributions to logo template strings (here too, without any special 'clear' key).

  • Whenever an entry (key + value) is appended and rendered into Output.results, the format of the resulting line must be:

    <first color of the distribution's COLOR_DICT entry><KEY>:<Colors.CLEAR> <VALUE>

    To make this concrete: take a Debian color list ['COLOR_0', 'COLOR_1']; appending key KEY with value VALUE then produces exactly one result string:

    'COLOR_0KEY:' + str(Colors.CLEAR) + ' VALUE'

    (that is, the key receives the first color entry as its prefix; following it are :, then the clear sequence from Colors.CLEAR, a space, and the value.)

  • During its construction, Output must resolve the current distribution by means of archey.output.distro.id (a call that returns a plain distribution id string such as 'debian', 'opensuse', or an unrecognized id like 'an-unknown-distro-id'); known distributions, unknown distributions, and Windows Subsystem for Linux cases must be handled without error.

Hard constraints

  • The string forms of the Colors members, together with the outputs of the utility method, must match the escape sequences given above exactly.
  • Components that used to depend on a 'clear' key inside COLOR_DICT/LOGOS_DICT must obtain the clear sequence from Colors.CLEAR instead.

Task Specification: Making the Output Module Honor ANSI_COLOR

Overview

The job here is to modify the Output class that lives in archey/output.py: the selection of its color palette must be able to honor the ANSI_COLOR value found in the system's os-release data, and a configuration option provides the control over this.

The Constants Module

A module named archey/constants.py must exist; it exposes a dictionary called COLOR_DICT whose keys are members of the Distributions enum (from archey.distributions) and each of whose values is a list that represents the color palette belonging to that distribution. This dictionary must include entries for Distributions.DEBIAN, Distributions.SLACKWARE, and Distributions.WINDOWS at least. More than one color entry (i.e., several colors) has to appear in the Slackware palette.

Requirements for the Output Module

Inside archey/output.py, all of the following has to hold:

  • COLOR_DICT must be imported from archey.constants and used — code has to be able to reference it as archey.output.COLOR_DICT.
  • Windows Subsystem for Linux (WSL) detection must be done with the re module, available under the name archey.output.re.
  • The distro library must be used, available as archey.output.distro; distro.id() and distro.os_release_attr(...) play a particularly important role here.
  • A LOGOS_DICT must be maintained, available as archey.output.LOGOS_DICT.
The Output class

Its constructor has the signature Output() — no arguments are required.

Detecting the distribution

As part of construction, Output must work out the current distribution and store it in the instance attribute distribution (a Distributions enum value). The detection proceeds as follows:

  1. First comes WSL detection: an attempt is made to detect Windows Subsystem for Linux by executing an external command (via check_output) and applying re.search to that command's output. If the search matches — that is, it returns a truthy value — the distribution is set to Distributions.WINDOWS.
  2. If WSL is not detected (the search returns None), identification instead happens through distro.id():
    • If distro.id() returns 'debian', the resulting distribution is Distributions.DEBIAN.
    • If the value distro.id() returns is 'slackware', the distribution to use is Distributions.SLACKWARE.
    • An id that does not correspond to a known distribution leaves Distributions.LINUX as the distribution.
The color palette

Output must expose an instance attribute named colors_palette, a list of color entries whose contents are picked on the basis of the distribution that got detected. COLOR_DICT[<detected distribution>] is what this attribute contains by default.

Honoring ANSI_COLOR

The configuration option that decides whether ANSI_COLOR is honored is obtained through Configuration.get(...), which returns a mapping containing the key 'honor_ansi_color' (a boolean).

  • When 'honor_ansi_color' is True:
    • The ANSI_COLOR attribute of os-release is retrieved by way of distro.os_release_attr(...).
    • Every color entry in colors_palette must be replaced, in such a way that each resulting entry incorporates/derives from the retrieved ANSI_COLOR value.
    • The entry count of colors_palette must remain equal to the entry count of COLOR_DICT[<detected distribution>] — put differently, each original color slot undergoes replacement, with the count preserved.
  • When 'honor_ansi_color' is False:
    • No replacement of any kind may take place. colors_palette must remain exactly equal to COLOR_DICT[<detected distribution>].

Note: in testing, the configuration lookup on which Output relies gets patched at archey.entries.model.Configuration.get; the configuration accessor that ends up being used must resolve to that same Configuration.get.

The append method

Signature: append(self, key, value).

This method appends a formatted entry string to the instance attribute results (a list). That formatted entry must be built using the first color of colors_palette, the key, a clear/reset color sequence, and the value, put together as:

<first color><key>:<clear> <value>

with <clear> denoting archey.colors.Colors.CLEAR. Concretely: given first palette color C, key KEY, and value VALUE, the appended string equals:

"{color}{key}:{clear} {value}".format(color=C, key=key, clear=Colors.CLEAR, value=value)
The output method (centering behavior)

Output must also make an output method available. It takes the strings collected in results (a list) and assembles them into output that is centered; both odd and even numbers of entries have to be handled correctly. The logos in use come from LOGOS_DICT, with the detected distribution acting as the key.

Changes Concerning External Command Invocation

Every spot in the codebase where an external command is invoked via check_output and failures are handled through subprocess.CalledProcessError must retain correct failure handling even though the raised CalledProcessError is now built from three positional arguments in the shape CalledProcessError(returncode, cmd, output) — that being returncode, the command name, and the command output string. Such CalledProcessError exceptions, when raised from their check_output calls, must be correctly caught and handled by the entry modules below:

  • archey/entries/disk.py — a df invocation that fails with a CalledProcessError must be handled by the Disk entry; this includes the case where a first df call succeeds and a second one fails, together with the case where the first fails and a subsequent call succeeds. Graceful handling of the failures is required (leaving no uncaught exception).
  • archey/entries/model.py — through check_output, the Model entry runs systemd-detect-virt; when it raises CalledProcessError, this must be handled gracefully so that model detection continues via other means (e.g., reading files).
  • archey/entries/user.py — through check_output, the User entry runs id; a CalledProcessError raised by it must be handled gracefully.

Given that the exception is now constructed with the (returncode, cmd, output) argument shape and that output strings may end in a trailing newline, these modules have to keep working correctly.

Recap: Public API to Create/Preserve

  • archey.constants.COLOR_DICT — a dict whose keys are Distributions members and whose values are lists of colors.
  • archey.output.COLOR_DICT — that very dictionary, once imported into the output module.
  • archey.output.re — the re module itself.
  • archey.output.distro — the distro library itself.
  • archey.output.LOGOS_DICT — a dict whose keys are Distributions members.
  • archey.output.Output, consisting of:
    • the Output() constructor
    • attribute distribution (a Distributions value)
    • attribute colors_palette (a list)
    • attribute results (a list)
    • the method append(self, key, value)
    • the method output(self)

Task Specification: Detecting the Distribution in archey.output

Overview

The Output class in the module archey.output is to be implemented and/or modified so that it works out the current Linux distribution; this includes detecting Windows Subsystem for Linux (WSL) and matching distributions via the os-release ID_LIKE field.

Public API

The archey.output Module

The module must import and use the following:

  • check_output (used for obtaining the kernel release string; e.g., the output of uname -r).
  • distro — a module that exposes at least the following callables:
    • distro.id() → returns the string that identifies the distribution.
    • distro.like() → returns the string holding the os-release ID_LIKE value.
    • distro.os_release_attr(...) — used in other places for release attributes.
  • re — the regular expression module from the standard library.
The Output Class
class Output:
    def __init__(self):
        ...

Once construction is complete, the instance must expose:

  • self.distribution — a member of the Distributions enum (see below).
  • self.colors_palette — a list of color entries matching the detected distribution, taken from COLOR_DICT[<distribution>].
The Distributions Enum

An enum that is accessible as Distributions (imported into the test scope from the project's distributions module). The referenced members include at least:

  • Distributions.WINDOWS
  • Distributions.UBUNTU
  • Distributions.LINUX_MINT
  • Distributions.SLACKWARE
  • Distributions.LINUX (generic fall-back)
The COLOR_DICT Mapping

A dictionary that maps each Distributions member to its list of color entries.

Behavior Required of Output.__init__

The constructor determines self.distribution by applying the following ordered logic:

  1. WSL detection from the kernel release. Get the kernel release string by calling check_output (a single string, e.g. 'X.Y.Z-R-ARCH\n', possibly carrying a trailing newline). Examine this string (using re) to work out whether it points to a Windows Subsystem for Linux environment.

    • If the kernel release string indicates WSL (that is, it contains a Microsoft marker, as in 'X.Y.Z-R-Microsoft\n'), then self.distribution is Distributions.WINDOWS, regardless of distro.id() / distro.like().

  2. Direct match on the distribution id. If no WSL is detected, call distro.id(). If the identifier it returns corresponds to a known Distributions member, use that member.

  3. Fall-back via ID_LIKE. If distro.id() returns an empty string, or an identifier that does not correspond to any known Distributions member, call distro.like(). The value it returns is a possibly-empty, possibly space-separated list of identifiers (e.g., 'ubuntu' or 'linuxmint debian').

    • Split this value on whitespace and, in order, take the first token that corresponds to a known Distributions member. Use that member.
    • For example: 'ubuntu' → Distributions.UBUNTU.
    • For example: 'linuxmint debian' → Distributions.LINUX_MINT (the first recognized token wins).

  4. Generic fall-back. When neither distro.id() nor distro.like() yields a recognized distribution (both effectively empty / unknown), self.distribution is Distributions.LINUX.

The Color Palette

Once self.distribution has been determined, self.colors_palette must be set to COLOR_DICT[self.distribution] (a list). Its length must equal the length of the entry that this mapping holds for the detected distribution.

Notes and Edge Cases

  • A trailing newline may be included in the kernel release string; detection must work whether or not surrounding quoting/whitespace is present.
  • WSL detection takes priority over both the direct id match and the ID_LIKE fall-back.
  • An unknown distro.id() (empty string or unrecognized value) must not raise; instead, it must proceed to the ID_LIKE step.
  • An empty distro.like() together with an unknown distro.id() must resolve to Distributions.LINUX.

08 Changes must be implemented across three areas of the archey package 762 words · source specification, reworded by GLM-5.3-Flash

Specification of the Task

Changes must be implemented across three areas of the archey package: the Colors enumeration, the distribution detection of the Output class, and the package-manager probing order of the Packages entry.

1. archey.colors.Colors — behavior of the enumeration

The Colors class must be an enumeration whose members can be constructed from their underlying values.

  • Each member's value is a tuple of integers that represent ANSI SGR parameters.
  • The member Colors.RED_BRIGHT must have (1, 31) as its value. A call to Colors((1, 31)) must return the Colors.RED_BRIGHT member.
  • Constructing Colors from a value that does not match any of its members (for example Colors((-1,))) must raise ValueError.

(The __str__ behavior that Colors already has must be preserved.)

2. archey.output — detection of the distribution

The Output class is located in the archey.output module. The logic it uses to detect the distribution must make use of the distro library, referenced within the module as archey.output.distro. Besides the distro.id() and distro.like() calls that are already in use, the detection routine must also consult distro.os_release_attr(...), referenced as archey.output.distro.os_release_attr.

The detection behavior as a whole (assuming os_release_attr returns an empty string) must remain as follows:

  • When distro.id() returns an identifier recognized as a distribution (for example 'debian'), that distribution is the one selected.
  • When the identifier returned by distro.id() is unrecognized and distro.like() returns an empty string, the code falls back to a default distribution.
  • When the identifier returned by distro.id() is unrecognized but distro.like() names a recognized distribution (for example 'ubuntu'), that distribution is the one selected.
  • When distro.like() contains multiple identifiers separated by spaces (for example 'linuxmint debian'), one that is recognized among them is selected.
  • When distro.id() and distro.like() both fail to identify a known distribution, the default distribution is used.
  • Detection of the Windows Subsystem for Linux (which relies on check_output, referenced as archey.output.check_output, returning a kernel string containing Microsoft) continues to work.

For distribution logo lookup, a LOGOS_DICT mapping referenced as archey.output.LOGOS_DICT is used, keyed by Distributions enum members.

Access to configuration

The Output class must get hold of its configuration through Configuration, referenced within the archey.output module as archey.output.Configuration. In particular, the behavior by which it appends output must read configuration through archey.output.Configuration.get:

  • When the configuration get returns a mapping with 'honor_ansi_color' set to False, the appended output uses the distribution's own set of colors rather than an ANSI color.
  • When it returns 'honor_ansi_color' set to True while an ANSI color is available, that ANSI color is the one honored.

The centering behavior of the output method must stay functional.

3. archey.entries.packages.Packages — probing of package managers

Within archey.entries.packages, the Packages class counts installed packages by probing package managers in sequence by way of check_output (referenced as archey.entries.packages.check_output).   • When no terminal can be detected, the not_detected value is obtained first, followed by use_unicode.

Detection Algorithm

The terminal emulator name is derived from environment variables according to the following priority (highest first):

  1. COLORTERM — When COLORTERM is set, the terminal name is taken from its value. It outranks every other signal (including TERM, TERM_PROGRAM, and any "known identifier" environment variables). The value must be normalized/uppercased into a canonical name. To be specific, a COLORTERM value of kmscon yields the name KMSCON.

  2. TERM_PROGRAM — If COLORTERM is not set while TERM_PROGRAM is set, its value is taken verbatim as the terminal name. It outranks TERM and the "known identifier" environment variables.

  3. TERM — If neither COLORTERM nor TERM_PROGRAM is set while TERM is set, its value is taken verbatim as the terminal name. It outranks the "known identifier" environment variables (i.e. when TERM is present, program-specific identifier variables are ignored).

  4. Known identifier environment variables — If none of the above are set, the terminal is detected from the presence of program-specific environment variables, which are mapped to a canonical name. Required mappings:

    • KONSOLE_VERSION present ⇒ name Konsole

    Note: when TERM is present, TERMINATOR_UUID must NOT contribute to detection (it is ignored in that case).

  5. Not detected — If none of the above produce a name, the not_detected configuration value is used as the name.

Detection Examples (must hold exactly)
  • With TERM=xterm-256color, COLORTERM=truecolor, and TERM_PROGRAM=A-COOL-TERMINAL-EMULATOR ⇒ the name starts with A-COOL-TERMINAL-EMULATOR. (Here COLORTERM=truecolor does not map to a special name, so TERM_PROGRAM wins over TERM.)
  • With TERM=OH-A-SPECIAL-CASE and TERMINATOR_UUID=<any> ⇒ the name starts with OH-A-SPECIAL-CASE (TERM is honored, the identifier is ignored).
  • With TERM=xterm-256color and KONSOLE_VERSION=X.Y.Z ⇒ the name starts with Konsole (the identifier is detected and normalized; note that KONSOLE_VERSION takes precedence over TERM in this scenario).
  • Only TERM=xterm-256color is set ⇒ the name starts with xterm-256color.
  • Only COLORTERM=kmscon is set ⇒ the name starts with KMSCON.
  • With TERM=xterm-256color, KONSOLE_VERSION=200401, and COLORTERM=kmscon ⇒ the name starts with KMSCON (COLORTERM overrides everything).
  • With no relevant environment variables set ⇒ the name is the not_detected value.

Note: COLORTERM=truecolor must be treated as NOT producing a special canonical name (detection therefore falls through to TERM_PROGRAM/TERM), whereas COLORTERM=kmscon yields the canonical name KMSCON. TERM must NOT override the special-name detection via COLORTERM when COLORTERM maps to a known name.

Output Format

The value attribute must be a string which:

  1. Starts with the detected terminal name.
  2. Is then followed by a palette of colorized characters.

The palette is made up of one repeated character. Two "rows" of 7 color slots each are emitted (14 characters of the palette glyph in total).

  • If use_unicode is True, the palette glyph is the Unicode full block character \u2588 (U+2588), and the output contains exactly 14 occurrences of it.
  • If use_unicode is False, the palette glyph is #, and the output contains exactly 14 occurrences of it.
Output When Not Detected

If the terminal is not detected (empty environment) and use_unicode is False, the output must start with the not_detected value and must contain zero occurrences of the Unicode full block character \u2588.

(Color/formatting escape codes may wrap the palette glyphs; what is significant is only the count of the palette glyph itself.)
