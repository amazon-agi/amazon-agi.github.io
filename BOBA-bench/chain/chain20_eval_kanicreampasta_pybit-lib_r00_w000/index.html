Overview

The task is to implement or modify a class RadixConvert inside the module pybit.radix_convert (accessible through from pybit.radix_convert import RadixConvert).

Required API

RadixConvert.dec_to_bin

A method that converts a non-negative decimal integer into its binary string representation. It is usable as a static/class method and callable directly on the class without instantiation.

Signature:

RadixConvert.dec_to_bin(value, width=None)

Parameters:

  • value (int): The non-negative decimal integer that is to be converted.
  • width (int, optional): The minimum number of binary digits to be produced. The default is such that no padding is applied when it is omitted.

Value returned:

  • A string that starts with the prefix '0b', followed by the binary digits of value.

Behavior

When the call provides only value, the method returns the standard binary representation prefixed with '0b', with the minimal number of digits (no leading zeros beyond what is naturally required). Examples of the results that are required:

  • dec_to_bin(0) → '0b0'
  • dec_to_bin(10) → '0b1010'
  • dec_to_bin(100) → '0b1100100'

When a width argument is passed, the binary digits (the portion that comes after the '0b' prefix) must be left-padded with '0' characters such that the digit portion is at least width characters long. The '0b' prefix does not count toward the width. As an example:

  • dec_to_bin(10, 5) → '0b01010' (the natural binary 1010 has 4 digits and is padded to 5 digits as 01010)

In cases where the natural number of binary digits already meets or exceeds width, no padding is added.

Summary

A fixed-length bit-vector type is to be implemented in a new module located at pybit/bits.py. Two public names must be exposed by the module:

  • Bits — the class representing bit vectors
  • BitsOperationError — an exception type (a subclass of Exception) raised when an operation is invalid

The Constructor

Bits(values=None, size=None)

The constructor accepts:

  • An optional first positional argument holding a list of bit values (each 0 or 1) that represent the bits.
  • An optional keyword argument size (an integer).

How construction behaves:

  1. Building from a list of bits. If a list is provided, the Bits instance represents exactly that sequence of bits, and its length is equal to the length of that list.

    • The bit values must be captured by the instance at construction time. If the caller later mutates the original list, the Bits instance must be unaffected (i.e. an independent copy of the values is stored, not a reference to the caller's list).

  2. Building from a list together with a size. If both a list and size are supplied, only the first size bits of the list are kept, and the effective length becomes size (for this case, assume size is less than or equal to the list length). For example, a list of 8 values, when constructed with size=4, yields a length-4 bit vector consisting of the first 4 values.

  3. Zero construction when only size is given. If only size is supplied (no list), the instance represents size bits that are all equal to 0, and its length equals size.

Vector Length

len(bits) returns the number of bits the vector contains, as determined by the construction rules above.

Equality

The operators == and != must be supported between two Bits instances.

  • Two Bits instances of the same length compare equal if and only if all of their corresponding bit values are equal; otherwise, they compare unequal. != behaves as the logical negation of ==.
  • A comparison of two Bits instances of different lengths, using either == or !=, must raise BitsOperationError.

Bitwise Operations

The operators listed below must be supported between/on Bits instances, and each of them returns a new Bits instance.

  • AND (a & b): an elementwise logical AND over the two vectors' bits.
  • OR (a | b): an elementwise logical OR over the two vectors' bits.
  • XOR (a ^ b): an elementwise logical XOR over the two vectors' bits.
  • NOT (~a): elementwise inversion — each bit 0 becomes 1, and each bit 1 becomes 0.

For the binary operators (&, |, ^):

  • Both operands must be of the same length. Whenever their lengths differ, the operation must raise BitsOperationError.

The result of any binary operator, and of the unary invert, must be a Bits instance with the same length as its operand(s) and with bit values that reflect the elementwise operation. Such a result must compare equal (via ==) to a Bits built directly from the expected list of resulting bits.

Expected Result Examples

  • Bits([1, 0, 1, 0]) & Bits([1, 0, 0, 1]) is equal to Bits([1, 0, 0, 0])
  • Bits([1, 0, 1, 0]) | Bits([1, 0, 0, 1]) is equal to Bits([1, 0, 1, 1])
  • Bits([1, 0, 1, 0]) ^ Bits([1, 0, 0, 1]) is equal to Bits([0, 0, 1, 1])
  • ~Bits([1, 0, 1, 0]) is equal to Bits([0, 1, 0, 1])

Further Requirements

  • Correction — size exceeding the supplied list: The assumption in the Constructor section that size never exceeds the list length is withdrawn. Whenever both a list and size are supplied, the effective length of the resulting vector is min(size, len(list)). In particular, Bits([0, 0, 0, 1], size=8) must have length 4 and must compare equal (==) to Bits([0, 0, 0, 1], size=4) as well as to Bits([0, 0, 0, 1]).

The error must be raised eagerly at the point when the comparison expression is evaluated, even if the result would otherwise be discarded.
  • Length-mismatch errors for each binary bitwise operator: whenever the operands' lengths differ, each of &, |, and ^ must raise BitsOperationError (e.g. a length-4 vector combined with a length-5 vector), with the error raised at the time the operator is applied.
  • Package layout: the pybit package must be importable from the repository root so that from pybit.bits import Bits, BitsOperationError succeeds (e.g. pybit/__init__.py must exist).

For addition, both operands are handled as unsigned binary values laid out MSB-first:

The Multiplication Class

Multiplication.booth_secondary
Multiplication.booth_secondary(A: Bits, B: Bits) -> list[Bits]
  • A and B share a single width, n, and are interpreted as signed two’s-complement integers; the multiplicand is A, and the multiplier is B.
  • Radix-4 modified (secondary) Booth recoding of B is what the method performs.
  • For each recoded group k, the signed term (digit_k * A) << (2*k) is formed.
  • Every entry that comes back is exactly 2*n bits wide, and its signed value is encoded in two’s complement. Negative values carry their sign representation across the complete 2*n-bit field.
  • The order of the trace runs from the least-significant recoded group to the most-significant group. After those group terms, their accumulated sum appears as the trace’s final entry; that final entry is the 2*n-bit product of A and B.
  • So, with an even width n, the trace holds n/2 shifted Booth terms followed by one accumulated product. For that reason, the required 6-bit cases return four 12-bit entries.
The Radix-4 Recoding Rule

An implicit 0 is appended underneath the least-significant bit of the multiplier. Group k works from the overlapping triplet (b_{2k+1}, b_{2k}, b_{2k-1}), in which b_{-1}=0. Each triplet maps to a signed digit through this table:

Triplet Digit
000 0
001 +1
010 +1
011 +2
100 -2
101 -1
110 -1
111 0

Before conversion into the 2*n-bit Bits representation, each group term already carries its 2*k-position left shift. Summed together, the signed group terms yield the terminal product entry.

Required Worked Behavior

The long mode names 'logic' and 'arithmetic' are accepted as well, in place of 'l' and 'a'. For a count that is non-negative:

  • Every shift returns a new Bits that has the same width as its operand.

  • An arithmetic right shift acts as a sign-propagating right shift: the high positions that become newly exposed are filled with the operand's original MSB.

Addition

a + b treats both operands as unsigned binary integers in MSB-first order and returns a new Bits:

  • The operands may have different widths; align them along the low-order/right edge, conceptually padding the shorter operand with leading zeros.
