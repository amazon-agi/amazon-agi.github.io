Task Specification: EC2 Region Hint Plugin

Overview

Write a plugin module that queries the Amazon EC2 instance metadata service to find out the AWS region of the running instance and returns it as a region hint string.

Module Location

Create the module at the following location:

lib/cloudregister/amazonec2.py

Dependencies

The module is required to use:

  • The requests library, accessed within the module as requests.get (i.e., import requests).
  • The logging module, accessed within the module as logging (i.e., import logging), with its warning method used specifically for reporting failures.

Public API

A single function must be provided with the following signature:

def generateRegionSrvArgs():

It does not take any arguments.

Behavior

The function performs an HTTP GET request (using requests.get) to the EC2 instance metadata endpoint:

http://169.254.169.254/latest/meta-data/placement/availability-zone

The response object is expected to expose these two attributes:

  • status_code — an HTTP status code as an integer.
  • text — the body of the response as a string.

The following cases must be handled by the function:

1. Successful response containing a valid availability zone

If the request returns a response with status_code == 200 and a text that holds a valid availability zone string, the function must determine the region name from the availability zone and return a region hint string in the form:

regionHint=<region>

To obtain the region, the trailing zone letter (the final character) is removed from the availability zone. As an example, an availability zone of us-east-1f yields the return value:

regionHint=us-east-1
2. The request raises an exception

In the event that the call to requests.get raises any exception, the function must:

  • Return None.
  • Log a warning (via logging.warning) whose message is exactly this:
Unable to determine instance placement from "http://169.254.169.254/latest/meta-data/placement/availability-zone"

(The message consists of the fixed prefix Unable to determine instance placement from " immediately followed by the endpoint URL and a closing ".)

3. Response signaling a server error

If the request returns a response with a status_code other than 200 (for example, 500), the function must:

  • Return None.
  • Log a warning (via logging.warning) whose message consists of the response body text preceded by a tab character and the literal Message: . With a response text of Test server failure, the logged message must be exactly:
	Message: Test server failure

(That is to say: a tab character, followed by Message: , then the response text.)

Return Value Summary

  • Valid availability zone (HTTP 200): the string regionHint=<region>.
  • Request exception: None (together with the warning log specified in case 2).
  • Non-200 status code: None (together with the warning log specified in case 3).

Phase 1 — Instance Metadata Service

Send an HTTP GET via requests.get(...) to:

http://169.254.169.254/metadata/instance/compute/location

The outcome is handled as follows:

  • If the GET raises requests.exceptions.RequestException, log exactly:

    Unable to determine instance placement from metadata server "http://169.254.169.254/metadata/instance/compute/location"

    Afterwards, continue to the wire-server phase.

  • If the GET finishes but yields no response object, for example None or another falsy non-response value, silently continue to the wire-server phase. As a result, any first warning on this path must come from a later wire-server failure.

    1. Unable to get availability zone metadata
    2. \tReturn code: <status_code>
    3. \tMessage: <response.text>

  • If the response has status_code == 200, take its complete text as the location and return:

    regionHint=<response.text>

The wire-server fallback is not triggered by a returned non-200 response; only a request exception or a missing/falsy response triggers it.

Phase 2 — Wire server

Obtain the default resolver via dns.resolver.get_default_resolver() and inspect the resolver's nameservers list. Its first entry is the wire-server IP.

  • If nameservers is empty, return None without making a wire-server request and without adding another warning. Because of that, the metadata exception path keeps only its metadata warning, while the silent missing-response path may return without a warning.
  • Otherwise, request the goal-state XML from the wire server via requests.get(...).

The goal-state request is handled as follows:

  • If requests.exceptions.RequestException is raised by it, log exactly:

    Could not retrieve goal state XML from <nameserver-ip>

    and return None.

  • If the response it returns has status_code != 200, log exactly:

    <nameserver-ip> error for goal state request: <status_code>

    and return None.

  • For status_code == 200, locate the text enclosed by <ExtensionsConfig> and </ExtensionsConfig> in response.text.

    • If no such element is present, log No "<ExtensionsConfig>" in goal state XML and return None.

    • Otherwise, take the enclosed text as the extensions-config URL and replace the XML-escaped &amp; sequences with & before requesting it. For example:

      <ExtensionsConfig>http://ola%sdme&amp;?getit=1</ExtensionsConfig>

      gives the URL:

      http://ola%sdme&?getit=1

Request that extensions-config URL by way of requests.get(...):

  • If requests.exceptions.RequestException is raised by the request, log exactly:

    Could not get extensions information from "<extensions-url>"

    and return None.

  • Should the response have status_code != 200, log exactly Extensions request failed with: <status_code> and return None.

  • For status_code == 200, look for the text enclosed by <Location> and </Location>.

    • If it is missing, log No "<Location>" in extensions XML and return None.
    • If it is present, return regionHint=<location>, with the enclosed text serving as the location.
Order of requests

The HTTP calls that can occur take place in this order:

  1. The instance metadata GET.
  2. The goal-state GET, made only after a metadata request exception or a missing/falsy metadata response and only if a nameserver exists.
  3. The extensions-config GET, made only after a successful goal-state response containing an extensions URL.

Automatic Certificate Update for RMT/SMT

update_rmt_certs()

The operation must cooperate with the collaborators already present at module level:

  • import_smt_cert(server)
  • clean_smt_cache()
  • __populate_srv_cache()

These collaborators belong to the operation's integration surface and must not be bypassed by way of duplicating their externally visible effects.

1. Guard for the new-registration case

The first decision taken is is_new_registration().

  • If it returns True, None is returned immediately.
  • In this branch, the cache is not inspected, no proxy is configured, configuration is not loaded, server data is not fetched, no certificate is imported, the cache is not cleaned, and it is not repopulated.
2. Fetching current and fresh server data

If this is not a new registration:

  • The currently known servers are obtained from the available-server cache located under get_state_dir(). A state directory that is absent or empty stands for an empty known-server set; the fresh lookup is not prevented by it.
  • set_proxy() is invoked, and its result is used consistently with the existing fetch path. If set_proxy() reports that proxy settings were established, the proxy argument given to the fetch must reflect the current HTTP and HTTPS proxy environment; otherwise no explicit proxy mapping is required.
  • Configuration is obtained through get_config(), and fresh data is fetched through fetch_smt_data(config, proxies).
  • What is fetched is an lxml.etree element rooted at <regionSMTdata>. Each <smtInfo> child stands for one fresh server and carries the attributes SMTserverIP, SMTserverName, and fingerprint.
  • An SMT server object is constructed for every fetched <smtInfo> entry before its public identity and fingerprint data are compared.
3. Deciding whether a certificate changed

Each freshly fetched server is compared with its corresponding known server. Correspondence must be established on the basis of server identity — such as its IP address together with its advertised name/FQDN where applicable — and must not rely solely on list order.

A fresh server is considered changed when either:

  1. a corresponding known server exists but has a fingerprint that differs; or
  2. no corresponding known server exists.

In particular, the second rule applies when the state directory is absent, when the cache is empty, or when the fresh response contains a newly introduced server. A fresh server that lacks a cached counterpart must never be silently skipped.

The result counts as “no change” only if every freshly fetched server has a corresponding cached server and all corresponding fingerprints match.

4. Side effects required
  • No change: import_smt_cert(), clean_smt_cache(), and __populate_srv_cache() must not be called.
  • One or more changes:
    1. import_smt_cert() is called with a freshly fetched server standing for the changed certificate that was detected or the previously unknown certificate. This call is required even in the case where the change was established because the known-server cache was absent or empty.
    2. clean_smt_cache() is called so that stale server data is removed.
    3. __populate_srv_cache() is called so that the available-server cache is rebuilt from current data.

Cleaning and repopulating the cache are cache-wide responses to a detected change; there is no need to repeat them for each changed entry. The operation has no value result, and it completes with None.

Goal

Update the function credentials_files_are_equal in the module cloudregister.registerutils so that it correctly rejects inputs that do not represent valid credentials.

Function to Be Changed

credentials_files_are_equal(credentials)

It is located in cloudregister/registerutils.py.

Behavior Required

When the credentials argument is not a valid credentials identifier, the function must return False (a boolean rather than a falsy equivalent). More precisely, the function must return False for each of the following inputs:

  • None
  • A string that is empty ('')
  • A byte string that is non-empty and does not correspond to valid credentials (e.g. the bytes that result from encoding an arbitrary string such as 'foo' as UTF-8)
  • A list that is empty ([])
  • A non-empty list, the contents of which do not correspond to valid credentials (e.g. ['foo'])

In every one of these cases, the function must return the boolean value False.

Scope

The scope covers only the handling of these invalid / non-credential inputs. The behavior for inputs that already represent valid credentials must not be altered, and any additional side effects or requirements beyond returning False for the invalid inputs described above must not be introduced.

Task Specification: Adding the cloudguestregistryauth Command

Goal

Write a new executable script whose job is to refresh the container registry credentials of the system. The script is required to live at the following path (relative to the repository root):

./usr/sbin/cloudguestregistryauth

The file carries no .py extension yet is a valid Python module. It is required to expose a top-level main() function that can be imported and invoked directly, and it is required to use os at module scope (so that os.geteuid is accessible as an attribute of the module).

Behavior Required of main()

The main() function runs through a sequence of validation steps. On any failure it must terminate the process by raising SystemExit with a specific message string serving as the exit code (i.e. sys.exit('<message>') / raise SystemExit('<message>')). On complete success it must exit with integer code 0.

The steps, carried out in this order, are:

1. Check for root privileges

Read the effective user id by way of os.geteuid() (accessed through the module's own os attribute). Should that value be anything other than 0, terminate with exit code:

You must be root
2. Check of the current update server

Fetch the update server that is currently configured by calling cloudregister.registerutils.get_current_smt(). If the call returns a falsy value (e.g. None), terminate with exit code:

No current update server configured
3. Check of registration

Ascertain whether the system is registered by calling cloudregister.registerutils.is_registered(...). If this call returns a falsy value, terminate with exit code:

System is not registered
4. Credential refresh through activations

Fetch activation information by calling cloudregister.registerutils.get_activations(...).

  • If what is returned is empty/falsy (e.g. an empty dictionary {}), terminate with exit code:
    Could not refresh credentials
  • If what is returned is non-empty (e.g. a dictionary such as {'foo': 'bar'}), the credential refresh counts as successful and main() must terminate with the integer exit code:
    0

API Surface the Solver Is Required to Provide

  • A module (loaded from source at ./usr/sbin/cloudguestregistryauth) exposing:
    • main() — has no required arguments; drives the flow described above.
    • Access to os at module level (so that os.geteuid resolves).

The script makes use of the following existing functions from cloudregister.registerutils (they must not be reimplemented; call them):

  • get_current_smt()
  • is_registered(...)
  • get_activations(...)

These functions are invoked in the order stated above, and each subsequent call is reached only when the earlier check passes.

Remarks

  • All of the termination messages must match the exact strings given above.
  • For the successful termination, the integer 0 is used, not a string.
  • Each validation step is required to short-circuit: as soon as a check fails, the later steps and their dependency calls must not be reached.

Unrelated Adjustment to a Data File

A data file used for test/configuration purposes exists at tests/data/regionserverclnt.cfg. Its certLocation value is required to be:

certLocation = /usr/lib/regionService/certs

(This replaces the previous /var/lib/regionService/certs.) The certificate directory path employed throughout the region-server certificate lookup logic is required to be based at /usr/lib/regionService/certs, so that a missing certificate for a region server named 1.1.1.1 is reported with a message of the form:

	No cert found: /usr/lib/regionService/certs/1.1.1.1.pem skip this server

No behavioral changes besides the ones above are required.

Task Specification: Rework the cloudguestregistryauth Registration Check

Summary

Change the main() function in the cloudguestregistryauth module (which is importable as cloudguestregistryauth and provides cloudguestregistryauth.main()) so that its handling of the case where no current update server is configured is consolidated.

Required Behavior

To determine the current update server, the main() function must call cloudregister.registerutils.get_current_smt().

Missing or invalid update server

If get_current_smt() does not return a valid update server (that is, it returns a falsy value such as None), main() must terminate the process by raising SystemExit with the following exact string as its exit code / message:

No current update server configured or system is not registered
Separate registration check removed

A separate, additional registration check that produces a distinct error must not exist. In particular:

  • It must not be the case that main() calls cloudregister.registerutils.is_registered() as a distinct gate that can independently cause exit.
  • A code path that exits with the message System is not registered must not exist.
  • A code path that exits with the message No current update server configured must not exist.

Put differently, the earlier two-step behavior (first checking that an update server is configured, then separately checking that the system is registered) is replaced by a single check of the result of get_current_smt(), and that check alone determines whether to exit with the combined message above.

Constraints

  • All other existing behavior of main() must be preserved for the case where a valid update server is returned.
  • The exit must be performed via SystemExit, and the exit code must be exactly the message string given above.
