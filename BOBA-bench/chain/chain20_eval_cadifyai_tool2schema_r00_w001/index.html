Task Specification: Docstring Parameter Description Parsing

Overview

This task concerns a library that decorates Python functions to generate a JSON schema describing the function and its parameters (used for tool/function calling). The decorator parses the function's docstring to extract descriptions for the function itself and for each of its parameters.

You must change how parameter descriptions are extracted from docstrings so that a terminating semicolon (;) is no longer required to mark the end of a parameter description.

Public API Surface

The decorator is exposed as GPTEnabled and is applied to functions directly:

@GPTEnabled
def some_function(...):
    """..."""
    ...

Import path for the decorator must match existing usage (from <package> import GPTEnabled); do not change the existing import surface.

A decorated function exposes:

  • some_function.schema — an object with a .to_json() method returning a dict representing the function schema.
  • some_function.tags — a list (empty when no tags are defined).

The schema dict produced by .to_json() has this shape:

{
    "type": "function",
    "function": {
        "name": <function name>,
        "description": <function description string>,
        "parameters": {
            "type": "object",
            "properties": {
                <param name>: {
                    "type": <json-schema type>,
                    "description": <param description string>,
                    ...
                },
                ...
            },
            "required": [<names of params without defaults>],
        },
    },
}

(The exact surrounding schema structure already exists and must be preserved; only the description-extraction behavior changes.)

Required Behavior Change

Docstrings follow the reStructuredText (Sphinx) style, using :param <name>: <description> fields.

Parameter descriptions

For each parameter documented with a :param <name>: <description> field, the extracted description must be exactly the description text, with no trailing semicolon required to terminate it.

A parameter description ends at the next docstring field marker (a line beginning with a directive such as :param ...:, :type ...:, :return:, :rtype:, etc.) or at the end of the docstring — whichever comes first.

Specifically:

  1. Single-line descriptions without a terminating semicolon must be extracted verbatim.

    • :param a: This is a parameter → description is This is a parameter.

  2. Multi-line descriptions must still be supported. When a description spans multiple lines, the continuation lines must be joined into a single string. Continuation lines are joined to the preceding text with a single space separator, and each line's surrounding indentation/whitespace must be stripped so the result contains no leading/trailing whitespace and no embedded newlines. For example, a description written as:

    :param a: Received Signal Strength Indication for the last received
    broadcast from the device. This is an integer value measured in dB,
    where 0 dB is the maximum (theoretical) signal strength, and more
    negative numbers indicate a weaker signal, defaults to 0

    must yield the single string:

    Received Signal Strength Indication for the last received broadcast from the device. This is an integer value measured in dB, where 0 dB is the maximum (theoretical) signal strength, and more negative numbers indicate a weaker signal, defaults to 0

  3. A description ends when the next field marker is encountered. In particular, :type <name>:, :return:, and :rtype: lines terminate a preceding :param ...: description and must not be included in the parameter's description text. Text belonging to :type, :return, and :rtype fields does not appear in any parameter's description.

  4. Descriptions may contain arbitrary characters, including colons, backticks, inline RST roles like :class:`...`, double-backtick code spans, and commas. These must be preserved within the extracted description. A colon appearing inside description text (e.g. within :class:`bluepy.btle.Characteristic`) must not be mistaken for a field terminator.

Function description

The function's top-level description is the free text in the docstring that appears before the first field marker. When this text spans multiple lines, it must be joined into a single string using the same rule as multi-line parameter descriptions (lines stripped and joined with single spaces, no leading/trailing whitespace, no embedded newlines).

For example, a docstring beginning with:

Returns a list containing :class:`bluepy.btle.Characteristic`
objects for the peripheral. If no arguments are given, will return all
characteristics. If startHnd and/or endHnd are given, the list is
restricted to characteristics whose handles are within the given range.

must yield the function description:

Returns a list containing :class:bluepy.btle.Characteristic objects for the peripheral. If no arguments are given, will return all characteristics. If startHnd and/or endHnd are given, the list is restricted to characteristics whose handles are within the given range.

If a docstring has no leading free text (it begins directly with :param ...:), only the parameter descriptions are extracted; behavior for the (absent) function description follows the library's existing default and is not otherwise constrained by this task.

Constraints and Compatibility

  • All existing schema-generation behavior (type mapping, required/optional detection, defaults handling, tags, enum/literal handling, etc.) must remain unchanged.
  • Descriptions that previously ended with a semicolon are no longer part of the input; the parser must correctly produce descriptions that have no trailing semicolon and no trailing whitespace.
  • The extracted description strings must not contain leading or trailing whitespace, and multi-line inputs must be collapsed to single-space-joined single-line strings.

When a decorated function has a parameter annotated with typing.Literal[...] or a subclass of enum.Enum, the generated parameter schema must include an enumeration of the allowed values.

typing.Literal

For a parameter annotated with Literal[v1, v2, ...], the parameter's schema entry must contain an "enum" key listing exactly those literal values (in the order given). The base JSON type reported for the parameter must correspond to the type of the literal values.

enum.Enum

For a parameter annotated with a subclass of enum.Enum, the parameter's schema entry must contain an "enum" key listing the member names (the identifiers of the enum members, as strings) — not the member values. The reported JSON type must be "string".

Invocation with enum parameters

When a decorated function is invoked, an argument corresponding to an enum.Enum-typed parameter that is passed as a string equal to one of the enum member names must be converted to the corresponding enum member before being passed to the underlying function. If the argument is already an enum member instance, it must be passed through unchanged. This conversion applies to arguments supplied positionally as well as by keyword.

For example, given:

from enum import Enum

class CustomEnum(Enum):
    A = 1
    B = 2

@GPTEnabled
def f(a: CustomEnum, ...):
    return a, ...

Calling f("A", ...) must result in the underlying function receiving CustomEnum.A, and calling f(CustomEnum.A, ...) must also result in CustomEnum.A.

2. Per-function ignored parameters

The @GPTEnabled decorator must accept a keyword argument ignored_parameters, a list of parameter name strings.

@GPTEnabled(ignored_parameters=["a", "d"])
def f(a: int, b: str, c: bool = False, d: list[int] = [1, 2, 3]):
    ...

Any parameter whose name appears in ignored_parameters must be completely omitted from the generated schema: it must not appear in the parameter properties, and if it would otherwise be listed as required, it must not appear in the required list. All non-ignored parameters must be included exactly as they normally would.

3. Global configuration mechanism

The top-level package must expose a global configuration object accessible as tool2schema.CONFIG. It must have a mutable attribute:

  • ignored_parameters: a list of parameter name strings.

When a function is decorated with @GPTEnabled without its own ignored_parameters argument, the schema generation must use tool2schema.CONFIG.ignored_parameters to determine which parameters to omit. The effective ignored-parameter set is read at the time the function is decorated (so decorating a function after mutating CONFIG.ignored_parameters picks up the new value).

The package must also expose a function tool2schema._reset_config() that resets the global configuration back to its default state. The default state of CONFIG.ignored_parameters must be an empty list (no parameters ignored).

The omission behavior driven by the global configuration is identical to that of the per-function ignored_parameters described in section 2: named parameters are removed from properties and from the required list, while all other parameters remain unchanged.

Additional required surface

Decorated function attributes

A function decorated with @GPTEnabled must expose:

  • .schema: a schema object with a method .to_json(schema_type=...) that returns the schema as a plain dict. When called with no argument it returns the default (OpenAI-style) JSON schema. It must also accept a SchemaType value (e.g. SchemaType.TUNE) to return the corresponding schema variant.
  • .tags: a list of tag strings, defaulting to an empty list when no tags are configured.
  • The function must remain callable, invoking the underlying function (with the enum conversion described in section 1 applied).
SchemaType

SchemaType is an enumeration importable from tool2schema, with at least a member TUNE, selecting an alternative schema serialization format. .to_json() with no argument selects the default (OpenAI) format.

Schema shape reference

The default JSON schema for a decorated function is a dict of the form:

{
    "type": "function",
    "function": {
        "name": <function name>,
        "description": <function docstring summary>,
        "parameters": {
            "type": "object",
            "properties": { <param name>: { "type": ..., "description": ..., [ "enum": [...] ], [ "default": ... ] }, ... },
            "required": [ <names of parameters without defaults> ]
        }
    }
}

The TUNE schema variant is a structurally similar alternative format used by .to_json(SchemaType.TUNE). Ignored parameters are removed from both properties and required in all schema formats; the presence/absence of enum keys for Literal/Enum parameters applies consistently across formats.

Parameter descriptions are taken from the function's docstring (:param <name>: lines). Parameters with default values must include their default in the schema and must not appear in required; parameters without defaults appear in required.

Schema object API and serialization timing

The object at .schema must expose:

Calling to_json() is equivalent to to_json(SchemaType.API).

Schema dictionaries are materialized at serialization time on every to_json call, rather than exposing a stale eagerly materialized result. Each serialization must reflect the function metadata and all schema customizations registered up to that call. A previously returned dictionary may be modified by its caller without becoming the authoritative state for future serializations.

Manual enum constraints

add_enum(param_name, values) registers an explicit allowed-value list for the named parameter and returns the schema object so calls may be chained. The corresponding parameter property must contain:

"enum": values

The values and their order must be preserved. The registration is persistent schema state: it must appear in every subsequent API and TUNE serialization, even though each dictionary is materialized separately. Calling add_enum after an earlier serialization must affect later serializations as well.

Manual enum registration is valid for ordinary annotations and does not change the parameter's base JSON type. For example, adding [1, 2, 3] to an int parameter leaves its type as "integer". It is a schema constraint only and does not by itself perform runtime value conversion.

API schema format

to_json() and to_json(SchemaType.API) return:

{
    "type": "function",
    "function": {
        "name": <original function name>,
        "description": <normalized function description>,  # when available
        "parameters": {                                    # when parameters exist
            "type": "object",
            "properties": {
                <parameter name>: <parameter schema>,
                ...
            },
            "required": [<required parameter names>]        # when non-empty
        }
    }
}

Parameter properties and the required list follow function-signature order.

For a function with no schema-visible parameters, the API format omits the parameters key entirely. The same applies when all parameters are omitted from schema exposure. If a parameters object exists but there are no required parameters, its required key is omitted.

TUNE schema format

to_json(SchemaType.TUNE) returns the function dictionary directly, without the API wrapper:

{
    "name": <original function name>,
    "description": <normalized function description>,  # when available
    "parameters": {
        "type": "object",
        "properties": { ... },
        "required": [ ... ]                             # when non-empty
    }
}

Thus, for a function with parameters, TUNE output has the same inner content as the API output's "function" value. Annotation-derived enums, manual add_enum constraints, ignored parameters, descriptions, defaults, item schemas, and requiredness must be identical in both formats.

TUNE has one deliberate no-parameter difference: even when the function has no schema-visible parameters, it must include:

"parameters": {
    "type": "object",
    "properties": {}
}

There is no required key in that case.

Parameter schema generation

Every schema-visible parameter is keyed by its Python parameter name. Its property contains the mapped JSON type, any available parameter description, applicable item or enum metadata, and its default when one exists.

  • A parameter with no Python default is included in required.
  • A parameter with any Python default is not included in required.
  • Every non-enum default is emitted under "default" using the actual default value, including values such as False, [1, 2, 3], and None.
  • Enum defaults use the enum member's name as specified in the enum section below.
  • Ignored parameters are absent from both properties and required.
  • If no included parameter is required, omit the required key rather than emitting an empty list.

  • int -> "integer"
  • float -> "number"
  • str -> "string"

"items": {"type": <mapped JSON type of X>}
