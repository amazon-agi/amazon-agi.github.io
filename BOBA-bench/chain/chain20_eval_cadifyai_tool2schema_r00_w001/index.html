Task Specification: Parsing Parameter Descriptions from Docstrings

Summary

At the center of this task is a library whose decorator wraps Python functions and produces a JSON schema describing the function together with its parameters (it serves tool/function calling). Parsing of a function's docstring is how the decorator obtains the descriptions of the function itself and of each of its parameters.

Parameter-description extraction from docstrings must change so that a terminating semicolon (;) is no longer required to mark where a parameter description ends.

Exposed API Surface

GPTEnabled is the name under which the decorator is exposed, and it gets applied directly to functions:

@GPTEnabled
def some_function(...):
    """..."""
    ...

The decorator's import path must be the same as in existing usage (from <package> import GPTEnabled); the existing import surface must not be altered.

On a decorated function, the following are exposed:

  • some_function.schema — an object that carries a .to_json() method whose return value is a dict representing the function schema.
  • some_function.tags — a list (empty when no tags have been defined).

This is the shape taken by the schema dict that .to_json() produces:

{
    "type": "function",
    "function": {
        "name": <function name>,
        "description": <function description string>,
        "parameters": {
            "type": "object",
            "properties": {
                <param name>: {
                    "type": <json-schema type>,
                    "description": <param description string>,
                    ...
                },
                ...
            },
            "required": [<names of params without defaults>],
        },
    },
}

(The surrounding schema structure already exists in exactly this form and must be preserved; the description-extraction behavior is the only part that changes.)

Behavior Change Required

These docstrings are written in the reStructuredText (Sphinx) style and make use of :param <name>: <description> fields.

Descriptions of parameters

Whenever a parameter is documented through a :param <name>: <description> field, the description extracted from it must be exactly the description text; attaching a trailing semicolon to terminate it is not required.

A parameter description reaches its end at whichever of these comes first: the docstring's next field marker (a line that starts with a directive such as :param ...:, :type ...:, :return:, :rtype:, etc.) or the docstring's end.

Concretely:

  1. Descriptions confined to a single line and lacking a terminating semicolon must be extracted verbatim.

    • :param a: This is a parameter → the extracted description is This is a parameter.

  2. Support for multi-line descriptions must remain in place. If a description covers multiple lines, its continuation lines must be joined together into a single string. A single space serves as the separator that joins each continuation line to the text preceding it, and the surrounding indentation/whitespace of each line must be stripped, so that the outcome carries no leading/trailing whitespace and no embedded newlines. As an example, take a description written as:

    :param a: Received Signal Strength Indication for the last received
    broadcast from the device. This is an integer value measured in dB,
    where 0 dB is the maximum (theoretical) signal strength, and more
    negative numbers indicate a weaker signal, defaults to 0

    which must come out as the single string:

    Received Signal Strength Indication for the last received broadcast from the device. This is an integer value measured in dB, where 0 dB is the maximum (theoretical) signal strength, and more negative numbers indicate a weaker signal, defaults to 0

  3. Encountering the next field marker is what ends a description. Lines reading :type <name>:, :return:, and :rtype: in particular terminate a preceding :param ...: description, and the parameter's description text must not include them. No text belonging to the :type, :return, and :rtype fields makes it into any parameter's description.

  4. Descriptions may contain arbitrary characters, including colons, backticks, inline RST roles like :class:`...`, double-backtick code spans, and commas. These must be preserved within the extracted description. A colon appearing inside description text (e.g. within :class:`bluepy.btle.Characteristic`) must not be mistaken for a field terminator.

Description of the function

Free text that appears in the docstring before the first field marker forms the function's top-level description. Should this text span multiple lines, it must be combined into a single string, following the same rule as for multi-line parameter descriptions (each line stripped and joined with single spaces, no leading/trailing whitespace, no embedded newlines).

As an example, for a docstring that opens with:

Returns a list containing :class:`bluepy.btle.Characteristic`
objects for the peripheral. If no arguments are given, will return all
characteristics. If startHnd and/or endHnd are given, the list is
restricted to characteristics whose handles are within the given range.

the function description that must be produced is:

Returns a list containing :class:bluepy.btle.Characteristic objects for the peripheral. If no arguments are given, will return all characteristics. If startHnd and/or endHnd are given, the list is restricted to characteristics whose handles are within the given range.

If a docstring carries no leading free text (opening directly with :param ...:), the extraction covers the parameter descriptions only; for the (absent) function description, the library's existing default governs the behavior, and this task places no further constraint on it.

Compatibility Constraints

  • Everything in the existing schema-generation behavior (type mapping, required/optional detection, defaults handling, tags, enum/literal handling, etc.) must remain unchanged.
  • Descriptions that used to end with a semicolon do not form part of the input anymore; the parser must correctly produce descriptions that carry no trailing semicolon and no trailing whitespace.
  • Leading or trailing whitespace must not be present in the extracted description strings, and multi-line inputs must be reduced to single-line strings whose parts are joined with single spaces.

Task Description

Summary

The tool2schema package — whose job is to turn Python functions decorated with @GPTEnabled into JSON schemas — is what you will be enhancing in this task. Three areas make up the work: handling of the typing.Literal and enum.Enum type hints in generated schemas, per-function ignoring of parameters, and a mechanism for global configuration.

From the top-level tool2schema package, the following names can already be imported and make up the existing public API (at minimum): FindGPTEnabled, FindGPTEnabledByName, GPTEnabled, SchemaType. These names must be preserved, and alongside them the new behavior described below must be added.

1. Handling of Literal and Enum type hints in parameter schemas

Whenever a decorated function has a parameter annotated either with typing.Literal[...] or with a subclass of enum.Enum, an enumeration of the allowed values must be part of the schema that gets generated for that parameter.

typing.Literal

Take a parameter whose annotation is Literal[v1, v2, ...]: its schema entry must contain an "enum" key, and that key must list exactly the literal values that were given, keeping the order in which they were given. As for the base JSON type reported for the parameter, it must correspond to the type of the literal values.

enum.Enum

If the annotation of a parameter is a subclass of enum.Enum, an "enum" key must likewise be present in the schema entry of that parameter, and it must list the member names — that is, the identifiers of the enum members, given as strings — and not the member values. The JSON type that gets reported must be "string".

Invoking functions that take enum parameters

Consider a decorated function being invoked, and an argument supplied for one of its enum.Enum-typed parameters. If that argument arrives as a string equal to one of the enum member names, it must be converted to the corresponding enum member before it is passed on to the underlying function. An argument that is already an enum member instance must instead be passed through unchanged. Arguments supplied positionally and arguments supplied by keyword are both subject to this conversion.

As an example, take:

from enum import Enum

class CustomEnum(Enum):
    A = 1
    B = 2

@GPTEnabled
def f(a: CustomEnum, ...):
    return a, ...

If f("A", ...) is called, the underlying function must end up receiving CustomEnum.A; if f(CustomEnum.A, ...) is called, the outcome must again be CustomEnum.A.

2. Ignoring parameters on a per-function basis

A keyword argument named ignored_parameters — a list of strings, each of which is a parameter name — must be accepted by the @GPTEnabled decorator.

@GPTEnabled(ignored_parameters=["a", "d"])
def f(a: int, b: str, c: bool = False, d: list[int] = [1, 2, 3]):
    ...

Any parameter whose name occurs in ignored_parameters must be omitted from the generated schema in its entirety: it must not appear among the parameter properties, and if it would otherwise be listed as required, the required list must not contain it. Parameters that are not ignored must all be included exactly as would normally be the case.

3. Mechanism for global configuration

A global configuration object — accessible as tool2schema.CONFIG — must be exposed by the top-level package. This object must carry a mutable attribute:

  • ignored_parameters: a list whose entries are parameter name strings.

When @GPTEnabled is applied to a function without an ignored_parameters argument of its own, tool2schema.CONFIG.ignored_parameters is what schema generation must use in order to work out which parameters to omit. The set of ignored parameters that is actually in effect is read at the moment the function is decorated (so a function that is decorated after CONFIG.ignored_parameters has been mutated picks up the new value).

There must also be a function tool2schema._reset_config() exposed by the package; its job is to put the global configuration back into its default state. In that default state, CONFIG.ignored_parameters must be an empty list (no parameters get ignored).

Omission of parameters driven by the global configuration behaves identically to the per-function ignored_parameters of section 2: the parameters that are named are removed from the properties and from the required list, whereas all other parameters remain unchanged.

Further required surface

Attributes carried by a decorated function

The following must be exposed by a function that carries the @GPTEnabled decoration:

  • .schema: a schema object that provides a .to_json(schema_type=...) method, which returns the schema in the form of a plain dict. With no argument passed in, the default (OpenAI-style) JSON schema is what it returns. It must also accept a SchemaType value (e.g. SchemaType.TUNE), and for such a value the corresponding schema variant is returned.
  • .tags: a list of tag strings; when no tags have been configured, the default for this list is empty.
  • The function must remain callable; a call on it invokes the underlying function (with the enum conversion described in section 1 applied).
SchemaType

SchemaType is an enumeration that can be imported from tool2schema; among its members is at least TUNE, which selects an alternative schema serialization format. .to_json(), when given no argument, selects the default (OpenAI) format.

Reference for the schema shape

For a function that has been decorated, the default JSON schema is a dict structured like this:

{
    "type": "function",
    "function": {
        "name": <function name>,
        "description": <function docstring summary>,
        "parameters": {
            "type": "object",
            "properties": { <param name>: { "type": ..., "description": ..., [ "enum": [...] ], [ "default": ... ] }, ... },
            "required": [ <names of parameters without defaults> ]
        }
    }
}

A TUNE schema variant also exists — an alternative format with a similar structure — and it is the one used by .to_json(SchemaType.TUNE). Ignored parameters disappear from both properties and required in all schema formats; likewise, the presence/absence of enum keys for Literal/Enum parameters stays consistent across the formats.

Parameter descriptions have their source in the function's docstring (its :param <name>: lines). Any parameter that has a default value must include that default in the schema and must not appear in required; a parameter that lacks a default appears in required.

Overview

Build a Python library named tool2schema that generates JSON-compatible function descriptions from decorated Python callables. Each schema draws on the callable's name, signature, type annotations, defaults, and Sphinx-style docstring content, and is available in API and TUNE layouts.

Public API

It must be possible to import the following names directly from tool2schema:

  • GPTEnabled — a decorator that can be used as either @GPTEnabled or @GPTEnabled(...).
  • SchemaType — an enumeration that contains at least API and TUNE.
  • FindGPTEnabled(namespace).
  • FindGPTEnabledByName(namespace, name).
  • FindGPTEnabledByTag(namespace, tag).
  • FindGPTEnabledSchemas(namespace, schema_type=SchemaType.API).

SchemaType.API serves as the default schema format, including when to_json() or FindGPTEnabledSchemas(...) is called without an explicit format.

The GPTEnabled Decorator

The decorator must support both of the following forms:

@GPTEnabled
def first(...):
    ...

@GPTEnabled(tags=["group-a", "group-b"])
def second(...):
    ...

After decoration, the resulting object must:

  • stay callable and return the original function's result unchanged;
  • support calls in the original positional and keyword forms;
  • expose a schema object that provides the methods described below; and
  • expose tags as a list. If no tags are configured, tags must be []; if the tags keyword is supplied to the decorator, the exposed list must contain those configured strings.

Tags act as discovery metadata and add no field to the generated schema.

Calling and enum.Enum conversion

In the normal case, arguments are forwarded unchanged. A single conversion is required, for a parameter annotated with an enum.Enum subclass:

  • A string exactly equal to an enum member name must be converted to that member before the original function is called.
  • An argument that already contains a member of that enum must pass through unchanged.
  • The behavior applies regardless of whether the argument was supplied positionally or by keyword.

As an example, if Mode.ACTIVE is a member and the corresponding annotated argument is "ACTIVE", the original callable must receive Mode.ACTIVE.

Schema Object and Deferred Serialization

The schema object attached to the decorated callable must provide:

to_json(schema_type: SchemaType = SchemaType.API) -> dict
add_enum(param_name: str, values: list) -> schema

When the decorated callable and its schema object are initialized, parameter metadata must be captured and retained. A serialized schema dictionary must not be constructed eagerly during decoration; schema dictionaries are assembled only when to_json is invoked.

Every to_json call must return a fresh, recursively independent dictionary. Mutating any returned dictionary — including nested parameter data, defaults, items, or enum lists — must not alter the retained schema state or any later API or TUNE result.

Explicit enums via add_enum

add_enum(param_name, values) registers the supplied allowed-value list for the named parameter and returns the same schema object, which makes chaining possible. It may be called before any serialization and must not require eager construction of the schema dictionary.

Every subsequent serialization must place an "enum" key holding those values in that parameter's property entry, while its ordinary type, description, and default fields are retained. The registration must persist across both the default/API format and SchemaType.TUNE.

Example:

@GPTEnabled
def choose(level: int):
    """:param level: Desired level"""

choose.schema.add_enum("level", [1, 2, 3])

In both formats, the level property must have "type": "integer" and "enum": [1, 2, 3].

Serialization Formats

API format

to_json() and to_json(SchemaType.API) must output the same layout:

{
    "type": "function",
    "function": {
        "name": "function_name",
        "description": "Function description when available",
        "parameters": {
            "type": "object",
            "properties": {
                "parameter_name": {
                    "type": "integer",
                    "description": "Parameter description when available"
                }
            },
            "required": ["parameter_name"]
        }
    }
}

The value of name is the original callable's name. The description, parameters, parameter description, and required keys are conditional, as detailed below.

When a callable has no parameters, the API output must omit the parameters key entirely from the inner function object.

TUNE format

Calling to_json(SchemaType.TUNE) must return the inner function dictionary directly, without the outer {"type": "function", "function": ...} wrapper. For a callable with parameters, its content is equivalent to the API result's "function" value, including defaults and all enums derived from annotations or registered explicitly:

{
    "name": "function_name",
    "description": "Function description when available",
    "parameters": {
        "type": "object",
        "properties": { ... },
        "required": [ ... ]
    }
}

TUNE has a single special rule for the empty-signature case: a callable with no parameters must still contain:

"parameters": {
    "type": "object",
    "properties": {}
}

In that empty parameter object, there is no required key.

Parameter Schema Rules

Every function parameter must be represented in parameters.properties; no configuration or behavior for ignoring parameters exists. The order of properties and required names must follow signature order.

JSON type mapping

For supported Python annotations, use these mappings:

Python annotation Schema type
int "integer"
float "number"
str "string"
bool "boolean"
list "array"
Defaults and required parameters
  • A parameter that has no default is listed by name in parameters.required.
  • A parameter that carries a default is not required, and its property must contain a "default" key with the actual default value, including values such as False, None, or a list.
  • A parameter that lacks a default has no "default" key.
  • When there are no required parameters, the required key must be omitted rather than emitting an empty list.
Lists

Support must exist for both the built-in and the typing spellings:

  • list[X] and typing.List[X] produce "type": "array" together with "items": {"type": <mapped type of X>}.
  • The bare spellings list and typing.List produce "type": "array" with no items key.
Optional values

For typing.Optional[X], apply the mapped schema type of X. Whether a parameter is required is still determined by the presence of a Python default. Therefore, Optional[int] = None produces "type": "integer", includes "default": None, and is not required.

Literal values

For typing.Literal[v1, v2, ...]:

  • include "enum": [v1, v2, ...], with the values in declaration order; and
  • derive the schema type from the Python type of the first literal value, applying the normal type mapping.

So, for instance, Literal[1, 2, 3] is an integer enum, whereas Literal["a", "b"] is a string enum.

enum.Enum annotations

When a parameter is annotated with an enum.Enum subclass:

  • the schema type must be "string"; and
  • "enum" must hold the members' names as strings in definition order, not their underlying values.

The schema enum for an enum declared as A = 1, B = 2 is ["A", "B"]. This representation in the schema matches the invocation-time name conversion described above.

Extraction from Docstrings

Docstrings rely on Sphinx-style :param <name>: entries.

  • Multiline prose is normalized by trimming surrounding whitespace and collapsing intervening line/indentation whitespace to single spaces.
  • When a docstring contains parameter fields, the function description text is the normalized free text that appears before the first :param field.
  • A docstring that contains only parameter fields still produces a function-level "description": "".
  • When a docstring has prose but no :param fields, its complete normalized prose is used as the function description.
  • If the function has no docstring, the function-level description key must be omitted entirely.
  • The body of a non-empty :param <name>: becomes the description of that parameter's property.
  • Multiline parameter text continues until the next :param, :type, :return, or :rtype field, and it is normalized into one space-separated string.
  • Content of :type, :return, and :rtype must not be included in a parameter description.
  • If a parameter has no matching :param entry, or if its entry has no description text, that property's description key must be omitted.

Discovery Functions

A namespace may contain both decorated and ordinary callables. Discovery must include only callables that are decorated with GPTEnabled.

  • FindGPTEnabled(namespace) -> list returns all decorated callables discoverable in the namespace. Functions that have no parameters are included normally.
  • FindGPTEnabledByName(namespace, name) returns the decorated callable whose original function name exactly equals name, and None when there is no match.
  • FindGPTEnabledByTag(namespace, tag) -> list returns all discovered decorated callables whose tags list contains the supplied tag; callables lacking that tag are excluded.
  • FindGPTEnabledSchemas(namespace, schema_type=SchemaType.API) -> list[dict] returns one fresh to_json(schema_type) result per discovered callable. The requested schema type must be passed through unchanged; when it is omitted, the API format is used.

Scope

  • Functions without parameters must remain callable, discoverable, and serializable according to the format-specific empty-signature rules.
  • No ignored_parameters decorator configuration and no parameter-ignoring behavior are in scope.
  • From the package's top-level import namespace, all names listed in the Public API section must be available.

Signature and semantics

ParseSchema(module, schema_json) accepts two arguments:

  1. module — a Python module object that contains one or more decorated functions (that is, functions carrying a .schema attribute).
  2. schema_json — a JSON-serializable dictionary that represents the schema of one of those functions (specifically, the value obtained by calling .schema.to_json() on a decorated function).

ParseSchema must find the decorated function object inside module whose schema matches schema_json and return it. Put differently, for any decorated function f defined in module:

ParseSchema(module, f.schema.to_json()) == f

must hold true, with ParseSchema returning the exact same function object f.

Decorated functions in a module expose a .schema attribute, and that schema object in turn exposes a .to_json() method, which returns the JSON-serializable dictionary form of the schema. Matching must work no matter whether the function has parameters, has no parameters, or carries tags in its schema.

Note about module placement

ParseSchema must be defined so as to avoid circular import problems within the package (its implementation must be placed in the schema-related module), while still being importable from the top-level tool2schema namespace as shown above.

Requirement 2: Encode/decode of list-of-enum type schemas

The package contains a class TypeSchema with a class method TypeSchema.create(type_hint) that returns a TypeSchema instance for a given typing annotation. Instances provide:

  • to_json() — returns the type's JSON schema dictionary.
  • encode(value) — converts a Python value to its JSON-serializable representation.
  • decode(value) — converts a value (either one that is already decoded or one in JSON representation) into the corresponding Python value.

This requirement concerns two type hints. In both, CustomEnum is an enum.Enum subclass whose members have names (e.g. YES, NO, MAYBE) and corresponding values.

Case A: List[CustomEnum]

Given type_schema = TypeSchema.create(List[CustomEnum]):

  • to_json() must equal the JSON schema of a list whose items are restricted to the set of string literals made up of the enum member names (i.e. equivalent to List[Literal["YES", "NO", "MAYBE"]]).

  • encode(array): when given a list of CustomEnum members of any length, it returns a list of the corresponding member names (strings), with order and length preserved.

  • decode(value) must handle lists of any length and accept either of the two forms:

    • A list of CustomEnum members → returns that same list of CustomEnum members.
    • A list of member-name strings → returns the list of CustomEnum members corresponding to those strings.

    In both cases the outcome is a list of CustomEnum members in the same order.

Case B: List[Optional[CustomEnum]]

Given type_schema = TypeSchema.create(List[Optional[CustomEnum]]):

  • to_json() must equal the JSON schema of a list whose items are either the enum member-name string literals or None (i.e. equivalent to List[Optional[Literal["YES", "NO", "MAYBE"]]]).

  • encode(array): when given a list that may contain CustomEnum members and/or None, it returns a list in which each CustomEnum member is replaced by its member name and each None is preserved as None. Order and length are preserved.

  • decode(value) must handle lists of any length that contain a mix of enum members / member-name strings and None, accepting either form:

    • A list containing member-name strings and/or None → returns a list in which each string becomes the corresponding CustomEnum member and each None stays None.
    • A list containing CustomEnum members and/or None → returns that same list unchanged.

    In all cases, order and length are preserved.

Both encode and decode must work for lists of length one, for lists with multiple elements, and for lists consisting entirely of None values.
