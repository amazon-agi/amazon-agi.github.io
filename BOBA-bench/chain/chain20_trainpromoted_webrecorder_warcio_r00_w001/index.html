02 Two parts of the WARC library must be adjusted, with existing behavior preserved 929 words · rewritten by GPT-5.6-sol, reworded by GLM-5.3-Flash

Task Description

Summary

Two parts of the WARC library must be adjusted, with existing behavior preserved: the WARC writer must serialize records from which the effective content type has been removed, and the chunked-data reader must pass through payloads that are not valid HTTP chunked-transfer data safely and exactly.

1. WARC Writer — Records That Have No Content Type

API for creating records

Writer objects expose the factory method for records:

create_warc_record(uri, record_type, payload=..., length=..., warc_content_type=...)

The record that comes back exposes content_type as a mutable attribute.

Choosing the content type and compatibility

When an effective warc_content_type override is not supplied, the writer must preserve the established content-type selection behavior instead of applying one universal value to every record type. This is the order in which the effective value is selected:

  1. A warc_content_type supplied by the caller that is not empty.
  2. A Content-Type that the supplied WARC headers already contain.
  3. The established default of the record type, when one exists.
  4. The generic fallback 'application/warc-record' for a record type that has no type-specific default.

The defaults established for particular record types include:

Record type Default content_type
warcinfo 'application/warc-fields'
metadata 'application/warc-fields'
response 'application/http; msgtype=response'
revisit 'application/http; msgtype=response'
request 'application/http; msgtype=request'

So, for instance, creating a resource record without an explicit content type means it is given the generic fallback 'application/warc-record', while response, request, revisit, warcinfo, and metadata records keep their type-specific defaults. The record's mutable content_type attribute gives access to the value that was selected.

Serializing a record set to content_type = None

Once a record has been created or parsed, its content_type may be set explicitly to None. An attempt to write such a record must succeed. In the WARC record-header block that gets serialized, the writer must leave Content-Type out entirely. In particular, the following must not be emitted:

  • Content-Type: None
  • Content-Type: whose value is empty
  • A stale Content-Type value remaining in the record headers

Every other piece of the writer's normal behavior remains intact, including the WARC version line, ordinary WARC headers, digest calculation, content-length calculation, payload bytes, the header/payload separator, and the trailing record separator. The writer's normal behavior continues to govern header ordering, generated identifiers, dates, and digests.

Given a resource record targeting ftp://example.com/ whose payload is the 9-byte b"some\ntext", setting record.content_type = None yields the following logical uncompressed record shape:

WARC/1.0\r\n
WARC-Type: resource\r\n
WARC-Record-ID: <...>\r\n
WARC-Target-URI: ftp://example.com/\r\n
WARC-Date: ...\r\n
WARC-Payload-Digest: sha1:...\r\n
WARC-Block-Digest: sha1:...\r\n
Content-Length: 9\r\n
\r\n
some\ntext\r\n
\r\n

Between the block digest and content length there is no WARC Content-Type header.

The requirement to omit holds across all of the following cases:

  • when the record's content length is already known;
  • when the writer must buffer a record whose content length is unknown or missing and recompute its length and its digests; and
  • for both plain writer output and gzip writer output. When the output is gzip, the decompressed WARC record must have the same header omission and logical contents as plain output.

A WARC record that has been parsed and did not contain a Content-Type header has an effective content_type of None; rewriting it must likewise preserve that header's absence while other required fields are added or recomputed in the normal way.

2. Chunked Data Reader — Non-Chunked Data Passed Through Exactly

Public API

ChunkedDataReader is still importable from warcio.bufferedreaders, and constructing it takes a byte stream as the first positional argument, with decompression selection optional:

ChunkedDataReader(stream, decomp_type=None)

The stream may be any byte reader that is file-like and compatible, with io.BytesIO as one such reader. The read() method returns bytes. The existing handling of chunked data that is correctly framed, and of optional decompression, remains unchanged.

Fallback when the input is not chunked

Whenever the input cannot be validated as HTTP chunked-transfer encoding, the reader must fall back to non-chunked operation and, when no decompression is requested, return the raw input bytes verbatim. It must not add, remove, reorder, or alter bytes. Any bytes that have already been inspected during an attempt to interpret a chunk-size line, chunk body, or delimiter stay part of the passthrough data.

This requirement also covers input whose beginning is made up entirely of hexadecimal-looking ASCII characters. A candidate value being large does not make it sufficient for establishing chunked framing; if the required framing is absent, the reader must treat the stream as ordinary data instead of failing due to the candidate chunk size being numerically too large.

In passthrough mode, trailing line endings are data. In particular, a final \r\n must not be consumed on the assumption that it is chunk framing.

The following examples are required:

ChunkedDataReader(BytesIO(b"ABCDE" * 10)).read()
# b"ABCDE" * 10

ChunkedDataReader(BytesIO(b"ABCDE" * 10 + b"\r\n")).read()
# b"ABCDE" * 10 + b"\r\n"

Both calls must complete without failing on chunk-size parsing or numeric overflow. The second call's result keeps the final CRLF exactly.

Summary of the API Surface

  • ChunkedDataReader(stream, decomp_type=None), importable from warcio.bufferedreaders, whose read() returns bytes and which passes raw data through exactly when the framing is invalid/non-chunked.
  • Writer objects that expose create_warc_record(uri, record_type, payload=..., length=..., warc_content_type=...). The records that come back have a mutable content_type; the established defaults per record type are preserved, 'application/warc-record' acts as the fallback only when no type-specific default applies, and setting content_type to None results in the WARC Content-Type header being omitted during serialization.

An extract subcommand must be supported by the command-line entry point main(args=[...]), which lives in warcio.cli.

Invoking the command

extract --headers <filename> <offset>
extract --payload <filename> <offset>

  • <offset>: the byte offset, given as a string (e.g. '0', '784', '151'), of the record to extract within the file.
What the command does

The archive record that begins at the given byte offset is located by the command, and bytes are written to standard output (the process stdout buffer, i.e. raw bytes, not text). Stdout receives nothing besides this.

Mutually-exclusive flags pick one of three output modes:

  • No flag (default): the entire record gets written — its header block first, then its content block (which itself may include HTTP headers followed by the payload). In other words, the output here is the concatenation of the header-block output and the payload-block output described below.

  • --headers: only the record's header block gets written, running up to and including the blank-line separator that terminates the header block. For a WARC record, that means the WARC headers plus the terminating \r\n\r\n; for a WARC record whose content is an HTTP message, the header portion additionally runs through the HTTP status line and HTTP headers, up to and including their terminating blank line. Specification of the Task

Purpose

This task modifies the WARC record loading logic in warcio: WARC-Target-URI header values that certain WARC-writing tools produce in malformed form are to be sanitized automatically while records are being loaded.

Context

Some tools emit the WARC-Target-URI WARC header with angle brackets wrapped around its value. For instance:

WARC-Target-URI: <http://example.com/>

The intended URI value does not include these angle brackets. Whenever a record of this kind is loaded, its WARC-Target-URI header must be fixed such that the angle brackets surrounding it are stripped off and only the URI itself remains.

Behavior That Is Required

Whenever warcio.recordloader.ArcWarcRecordLoader loads a WARC record, the record's WARC-Target-URI header value must undergo the following normalization:

  • When the value is wrapped in a leading < together with a trailing >, those characters must be stripped out of it; what remains is just the URI that the brackets enclosed.
    • To illustrate: <http://example.com/> ends up as http://example.com/.
  • A value that is not wrapped in a leading < and a trailing > must be left as it is.

The loaded record's headers must contain the corrected value, obtainable through the record's rec_headers.get('WARC-Target-URI').

Constraints on the Public API Implementation

The correction logic must take the form of a method named _ensure_target_uri_format, defined on the ArcWarcRecordLoader class in the module warcio.recordloader. Record loading applies this method, with the result that any record the loader returns — and hence any record yielded while an archive is being iterated — already carries the WARC-Target-URI value in sanitized form.

Scenario for Verification

Consider a gzipped WARC file that holds a response record for which the WARC-Target-URI header value is <http://example.com/>. Loading that file and locating the response record inside it must yield a record on which the WARC-Target-URI header is equal to http://example.com/.

RFC 8187 conversion

Every header value is inspected on its own.

  • A header value that is fully ASCII is emitted unchanged, in the form Name: value.

  • A header value that contains any non-ASCII character is processed as a sequence of segments separated by semicolons. The segments are then rejoined using ; .

  • Segments are each examined on their own.

  • When a segment has the form key="quoted value" or key=value and its value portion contains non-ASCII characters, it is rewritten as:

    key*=UTF-8''<percent-encoded-utf8-value>

    The value is processed in this way:

    1. Any double quotes surrounding the value are removed.
    2. UTF-8 encoding is applied to the value.
    3. Every byte that falls outside the RFC 8187 attr-char set is percent-encoded.
    4. Uppercase hexadecimal is used for the percent escapes.

    Consequently, spaces, parentheses, and every byte belonging to a non-ASCII UTF-8 sequence end up escaped. ASCII attr-char characters — letters, digits, hyphens, periods, and underscores among them — remain literal.

  • Conversion into the extended form happens only for segments whose value is genuinely non-ASCII. Segments containing only ASCII — bare tokens, as well as ASCII key=value or key="value" segments — keep their original form.

Goal

Implement (or modify) a StatusAndHeaders class that can serialize HTTP status and headers into ASCII-safe bytes, applying proper RFC 5987 style encoding to non-ASCII header values.

Public API

  • Class: StatusAndHeaders
  • Constructor signature: StatusAndHeaders(statusline, headers)
    • statusline: a string, for example '200 OK'
    • headers: a list of (name, value) tuples in which name and value are strings.
  • Method: to_ascii_bytes()
    • Returns a bytes object that contains the serialized status line and headers and is encodable/decodable as ASCII.

The class must be importable so that StatusAndHeaders is accessible from the module where it currently resides (the status-and-headers module of the codebase).

Serialization Format

to_ascii_bytes() produces output with the following structure:

<statusline>\r\n
<Header-Name>: <encoded-value>\r\n
... (one line per header) ...
\r\n

In other words: the status line, then each header written as Name: value and separated by \r\n, followed by a trailing \r\n after the last header (which produces a blank line at the end).

The whole result must be valid ASCII (that is, .decode('ascii') must succeed).

Rules for Encoding Header Values

For each header value, determine whether it holds multiple values / parameters separated by ; (semicolons):

Case 1: Value contains parts separated by ;

Split the value on ; and process each part on its own. For each part:

  • If the part is made up of only ASCII characters, leave it unchanged (surrounding whitespace included).
  • If the part contains non-ASCII characters, it is handled as a key=value-style parameter and must be converted to RFC 5987 extended-notation:
    • For a part of the form key="value" (or key=value), transform it into key*=UTF-8''<percent-encoded-value>.
    • A * is appended to the key before =.
    • The prefix used for encoding is UTF-8''.
    • The value portion is UTF-8 encoded and then percent-encoded; each non-safe byte is represented as %XX with uppercase hex digits. Double quotes surrounding the value are removed.
    • Leading whitespace/separator formatting between the parts is preserved, so the parts remain joined by ; .

Case 1 transformation examples (single part shown):

  • attachment; filename="Éxamplè" → attachment; filename*=UTF-8''%C3%89xampl%C3%A8
  • value; filename="Éxamplè"; param; other=испытание; another → value; filename*=UTF-8''%C3%89xampl%C3%A8; param; other*=UTF-8''%D0%B8%D1%81%D0%BF%D1%8B%D1%82%D0%B0%D0%BD%D0%B8%D0%B5; another

Note that purely-ASCII parts such as attachment, param, and another pass through verbatim, and the ; joining is preserved.

Case 2: Value contains no ;

If the header value has no semicolon separator:

  • If the value is purely ASCII, it is left unchanged.
  • If the value contains any non-ASCII characters, percent-encode the entire value. The whole string is UTF-8 encoded, and percent-encoding as %XX with uppercase hex is applied to every byte that is not an unreserved/safe character. In this case, characters such as = are percent-encoded as well (e.g. = → %3D).

Example of a Case 2 transformation:

  • “max-age=31536000″ → %E2%80%9Cmax-age%3D31536000%E2%80%B3

    Here, the curly/special quote characters and the = sign are all percent-encoded; the ASCII alphanumeric characters and - remain literal.

Percent-Encoding Details

  • Percent-encoding works on the UTF-8 byte representation.
  • Hex digits appearing in %XX escapes are uppercase.
  • In Case 2 (whole-value encoding), the set of characters that are left unencoded is the standard unreserved set (letters, digits, and characters like -), while = and non-ASCII bytes are encoded.
  • In Case 1 (per-parameter value encoding), it is only the value portion after = that gets encoded, and characters typical of RFC 5987 filename values are encoded per byte.

Notes

  • The Name: value form is used for header names, which are emitted verbatim.
  • Headers and values that are ASCII-only must round-trip unchanged.
