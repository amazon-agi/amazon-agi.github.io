Specification of the Task

Summary

Supply a Python package/module named ncwriter that implements an ordered NetCDF dataset-template system. It must support creating templates and editing them incrementally, loading them from JSON files, and writing valid on-disk NetCDF files. The public API and the behavior must work consistently under both Python 2 and Python 3.

Publicly exported names

These imports must succeed:

from ncwriter import DatasetTemplate, ValidationError
  • DatasetTemplate is the template class described further down.
  • ValidationError is the exception raised when constructor content or loaded template content fails template validation.

Template construction

DatasetTemplate(...)

The class must support construction without arguments as well as the following optional keyword mappings:

template = DatasetTemplate(
    dimensions=dimensions,
    variables=variables,
    global_attributes=global_attributes,
)

Every argument is optional. When an argument is omitted, or is given as None, the corresponding public attribute is initialized to an empty mutable ordered mapping. When mappings are supplied, they populate the corresponding attributes with equivalent key/value contents and ordering. Construction with no arguments therefore produces a template for which all of the following compare equal to {}:

template.dimensions
template.variables
template.global_attributes
Validation of constructor inputs

The constructor's inputs must be validated, and invalid inputs must raise the publicly exported ValidationError. Specifically:

  • The dimensions, variables, and global_attributes inputs must be mappings rather than strings or other non-mapping values.
  • Dimension lengths must be non-negative integers or None; 0 and None are both valid placeholders whose sizes can later be inferred from variable data. Negative lengths are invalid.
  • Names in validated template mappings are identifiers that begin with an ASCII letter and continue with letters, digits, or underscores (^[A-Za-z][A-Za-z0-9_]*$). A variable name such as _TEMP is therefore invalid.
  • variables maps variable names to definition mappings. A definition may be partial: in particular, dimensions and type may be omitted so that the template can be completed later. Whenever dimensions is present, it is an ordered list of dimension-name strings, and whenever attributes is present, it is an attribute mapping.
  • global_attributes must be a mapping, and an attribute value cannot be None. Values of attributes may use NetCDF/JSON-compatible strings, numbers, and arrays. The same value rules apply to variable attribute mappings.

Public template state and its mutation

A DatasetTemplate exposes three ordered mappings that are mutable and dictionary-like. Insertion order must be preserved, and they must have collections.OrderedDict equality/update semantics. Replacing an existing key's value retains that key's position; new keys are appended in insertion or update order. When unrelated entries are added, existing entries must remain present.

dimensions

dimensions maps a dimension name to its declared length or placeholder value. Direct addition and replacement are supported, for example:

template.dimensions['TIME'] = 100
template.dimensions['DEPTH'] = 10

Once these operations have been performed, the mapping must compare equal to an equivalent OrderedDict in the same order.

variables

variables maps a variable name to a mutable dictionary containing that variable's definition. Direct item access and assignment must be supported, and .keys() must return an object that can be used with set(...) on both supported Python versions. When an object is assigned using code such as the following, it must be retrievable as that assigned object:

template.variables['TIME'] = variable_definition
assert template.variables['TIME'] is variable_definition

A complete variable definition, as used for NetCDF output, contains:

  • dimensions: an ordered list of the variable's dimension names;
  • type: a dtype specifier compatible with NumPy/netCDF;
  • optionally, attributes: an ordered mapping from NetCDF variable-attribute names to values;
  • optionally during template editing, values: a NumPy array that contains the variable data.

When definitions are loaded as partial templates, they may initially omit dimensions and type; callers must be able to add those entries later. Callers must also be able to assign a NumPy array to values and then read the same data back through the definition.

When loaded from JSON, a nested attributes mapping must retain JSON member order. Ordered in-place updates must be supported. For example, updating an existing units entry changes its value without moving it, while a new comment entry is appended after the existing attributes.

global_attributes

global_attributes maps NetCDF global-attribute names to values. It must be mutable, support item assignment and .update(...), preserve order, and compare equal to an equivalent OrderedDict. When no global attributes are supplied, it defaults to an empty mapping.

Loading a template from JSON

DatasetTemplate.from_json(path) — a class method

from_json accepts the filesystem path of a JSON document, reads that file, and returns a DatasetTemplate populated from it. What the argument denotes is a file path, not raw JSON text.

The JSON document may contain the following top-level objects:

{
  "dimensions": {"TIME": 0},
  "variables": {
    "TIME": {
      "dimensions": ["TIME"],
      "type": "float64"
    }
  },
  "global_attributes": {"title": "Example dataset"}
}

All three public mappings must be populated by the method, and JSON object-member order must be preserved at every relevant level, including dimension order, variable order, global-attribute order, variable-definition order, and nested variable-attribute order. If any top-level section is absent, the corresponding instance mapping defaults to empty. A JSON document that contains only partial variable definitions and global attributes is valid and can be augmented after loading.

Writing the NetCDF output

template.to_netcdf(output_path)

to_netcdf accepts a filesystem path string and creates a valid NetCDF file at that location. When a file already exists there, it is replaced. Even a template that is entirely empty must produce a file that can be opened with netCDF4.Dataset.

Before creating the dimensions, the method must resolve placeholder sizes from the assigned variable values:

  • For each variable that has values, each axis of values.shape corresponds positionally to the same entry in that variable's dimensions list.
  • A template dimension declared as 0 or None has its size inferred from the corresponding array-axis length.
  • The template's dimension order must not be disturbed by inference. The dimension sizes in the resulting file must be the inferred positive lengths.
  • Explicit non-placeholder lengths remain authoritative. The rank of an array must match the number of variable dimensions, and all uses of a dimension must agree on its final length; inconsistent shapes must raise ValueError rather than produce an inconsistent file.

As an example, values with shape (10,) for TIME, shape (1,) for DEPTH, and shape (10, 1) for a variable using ['TIME', 'DEPTH'] resolve the placeholder dimensions to TIME = 10 and DEPTH = 1.

When reopened with netCDF4.Dataset(output_path), the written file must have the following observable contents:

  • dataset.dimensions contains the dimensions in template order. Its .items() yields (name, dimension_object) pairs, and the .size of each dimension object is the resolved dimension length.
  • Each template variable can be accessed as dataset[variable_name]. Converting the variable's .dimensions to a list yields the definition's ordered dimensions list, and its .dtype equals the declared type.
  • Every values array that has been assigned is written as the variable's data and reads back with the same values, subject to the declared NetCDF dtype.
  • When a variable has a non-empty attributes mapping, those entries are written as NetCDF variable attributes with their values and order preserved. When attributes is absent or empty, the variable has no template-supplied NetCDF attributes.
  • Every entry in global_attributes is written as a NetCDF global attribute, with its value and mapping order preserved.

Compatibility with Python 2 and Python 3

The package must be importable, and all of the behavior described above must function under both Python 2 and Python 3. Mapping iteration must use APIs that are available in both versions; in particular, behavior must not depend on the Python-2-only .iteritems(). .items() and key collections that can be converted with set(...) must work consistently throughout template handling and NetCDF creation.

Summary

Building mutable NetCDF templates and writing them with netCDF4 is the job of the ncwriter package. Variable payloads must be stored under the key data; there is no longer any support for the legacy key values. The package must do all of the following: validate template mappings, load templates from JSON files, infer unresolved dimension sizes from data, write global and variable attributes, and preserve NetCDF fill/masking semantics.

Public API

The imports below must all work:

from ncwriter import DatasetTemplate, ValidationError
from ncwriter.template import DatasetTemplate
from ncwriter.schema import (
    ValidationError,
    validate_dimensions,
    validate_variables,
    validate_attributes,
)

The class ValidationError is jsonschema.ValidationError. All of the schema-validation failures described below must raise this exception.

Naming and schema validation

The pattern ^[A-Za-z][A-Za-z0-9_]*$ applies to dimension, variable, and ordinary attribute names: an ASCII letter must be the first character, and every character after that may be an ASCII letter, a digit, or an underscore. Any key that does not match is invalid.

validate_dimensions(dimensions)

The dimensions argument must be a mapping, and an empty mapping is valid. Each key must be a valid name; each value must be either a non-negative integer or None. Zero and None are therefore valid unresolved dimension sizes, whereas negative numbers, floating-point sizes, strings, booleans, and non-mapping inputs are invalid.

Examples:

validate_dimensions({})
validate_dimensions({'TIME': 0, 'DEPTH': None, 'X': 10})
validate_attributes(attributes)

The attributes argument must be a mapping, and it may be empty. Each key must be a valid ordinary attribute name. As for each value, it may be a string, a non-boolean number, or a JSON-style array/Python list. None, booleans, mappings, and attributes inputs that are not mappings are all invalid.

Valid values include strings, 1.5, and [1, 2, 3]. Invalid entries include {'null': None}, {'bool': True}, {'object': {}}, and a name such as '_badname'.

validate_variables(variables)

The variables argument must be a mapping that takes valid variable names to variable-definition mappings. variables may be empty, and a variable definition may be empty as well, so templates can be put together incrementally. Within a schema-validated variable definition, only the properties below are recognized:

  • dimensions: a list whose entries are valid dimension-name strings. An empty list is valid.
  • type: a string naming a dtype compatible with NumPy/NetCDF.
  • attributes: a mapping that satisfies the attribute schema above.
  • data: either None or a JSON array/Python list.

The schema does not require any of these properties individually. A definition that contains only type, only dimensions, only attributes, or only data is valid, provided that property's value has the correct type. As an illustration, the following complete JSON-oriented definition is valid:

validate_variables({
    'X': {
        'dimensions': ['X'],
        'type': 'float32',
        'attributes': {'name': 'X', 'count': 1},
        'data': [42],
    }
})

Any property outside this set is invalid. In particular, values does not serve as an alias for data. ValidationError must be raised by an invalid variable name, by a non-mapping attributes value, or by scalar data such as 100. Because the schema is JSON-oriented, this validator does not treat NumPy arrays and masked arrays used at runtime as JSON arrays; those arrays are assigned through the mutable template after construction instead.

DatasetTemplate

Constructing a template

Optional keyword arguments dimensions, variables, and global_attributes must be accepted by the constructor:

template = DatasetTemplate(
    dimensions=dimensions_mapping,
    variables=variables_mapping,
    global_attributes=attributes_mapping,
)

When any section is omitted, that section begins as an empty mapping. The constructor must run validate_dimensions on the dimensions it is given, validate_variables on the variables, and validate_attributes on the global attributes. Invalid inputs — non-mappings, negative dimension sizes, invalid names, and None attribute values among them — must raise ValidationError.

The public instance attributes exposed by a template are:

  • dimensions: a mutable mapping taking dimension names to sizes.
  • variables: a mutable mapping taking variable names to definitions.
  • global_attributes: a mutable mapping of global attributes.

These mappings must have the semantics of ordered dictionaries: the order in which entries are inserted is retained, they compare equal to equivalent dictionaries or to OrderedDict instances, and ordinary operations such as item assignment and .update() work. An empty template exposes empty mappings for all three of these attributes. All other entries, and their order, must be preserved when an existing dimension is updated or new dimensions are added. Likewise, variable definitions and the attribute mappings nested inside them may be extended in place.

During template construction, partial variable definitions are allowed as long as they are schema-valid. Before such a variable is written, it must be completed with the dimensions, type, and data that NetCDF output requires. Any dimension name that an initial variable definition lists must refer to a dimension the template declares; a reference to an undefined dimension is inconsistent, and it must fail rather than silently creating a dimension.

DatasetTemplate.from_json(path)

A filesystem path to a JSON template file is what from_json accepts; the argument is treated as a path, not as raw JSON text. Within each JSON object, the order of its members must be preserved. dimensions, variables, and global_attributes are the recognized top-level objects, and they serve to initialize the corresponding public mappings. When any recognized top-level key is absent, the section it corresponds to defaults to an empty mapping. The mappings that result go through the same validation the constructor applies.

To illustrate: a file holding only variables and global_attributes produces a template whose dimensions mapping is empty. When the mappings are updated afterwards, the entries loaded from the file remain available.

Variable definitions and how data is stored

A runtime variable definition takes this form:

template.variables['TEMP'] = {
    'dimensions': ['TIME', 'DEPTH'],
    'type': 'float32',
    'attributes': {
        'units': 'degC',
        '_FillValue': -999.0,
    },
}
template.variables['TEMP']['data'] = data_array

Exactly one payload key is supported: data. The variable payload must be retrieved by reading template.variables[name]['data'], and it must be replaced by assigning to template.variables[name]['data']. As for the former values key, it must not be read, written, or accepted as a schema property.

Where writing is concerned, data may be a NumPy array, a NumPy masked array, or None. There is support for multi-dimensional arrays. Schema validation accepts JSON lists, whereas the required array-writing behavior is concerned with NumPy arrays whose shapes correspond to the dimensions they declare.

to_netcdf(path)

DatasetTemplate.to_netcdf(path) must create a NetCDF file by means of netCDF4.Dataset. Even a template that has no dimensions, no variables, and no attributes must still produce a valid file — one that netCDF4.Dataset can open.

Creating dimensions and inferring sizes

The order in which dimensions are created follows the template's order. A declared size that is positive is fixed. A declared size of 0 or None is unresolved; when an array-backed variable references such a size, it must be inferred from the matching axis of that variable's data shape. The size that has been resolved is what must be used in the output file. As an example, take data with shapes (10,), (1,), and (10, 1) for variables over TIME, DEPTH, and (TIME, DEPTH): when their original sizes are 0 or None, TIME must resolve to 10 and DEPTH to 1.

There must be as many array axes as the variable has declared dimensions. Array sizes must agree both with fixed dimension sizes and with sizes already inferred from other variables. When ranks or sizes are inconsistent, ValueError must be raised rather than a mismatched file being produced.

Creating variables and required data

Each writable variable is created with the name, dtype, and ordered dimension list it declares. The ordinary attributes it carries are copied to the NetCDF variable, and its data are written over the whole variable. Reading the result back must yield the original values and shape, multi-dimensional arrays included.

Semantically, whether data is present is distinct from its value:

  • When a variable has no data key at all, to_netcdf must raise ValueError. This requirement is not satisfied by a legacy values key.
  • If data is present and its value is None, the write is valid, and it means that every element of the variable is a fill value. If automatic masking is enabled, reading the complete variable must return a numpy.ma.MaskedArray whose mask is true everywhere.
  • When data is a NumPy array with a compatible shape, all of its values are written.
Fill values and masked-array behavior

Special output handling applies to NetCDF's reserved _FillValue whenever it is present in a runtime variable's attributes mapping. During variable creation, it must be established as the variable's fill value, and it must remain readable as the _FillValue attribute of the output variable. It must neither be lost nor be treated as an ordinary post-creation attribute.

Given a plain NumPy array, elements equal to the declared _FillValue must read back as masked when NetCDF automatic masking is enabled; all other elements must retain their values. In the case of a NumPy masked array, masked input positions must be stored as the variable's fill value and read back as masked; unmasked positions, meanwhile, retain their original values. Custom fill values such as -999.0 fall under these requirements.

Global attributes

Every entry in template.global_attributes must be written out, in mapping order, as a NetCDF global attribute. From the output dataset, it must be retrievable with getncattr. Variable attributes must likewise be retrievable from their output variable, omitting none of the declared user attributes.

Compatibility constraints

  • Partial-template construction and ordered mutable mappings, in their existing form, must continue to work.
  • Validation uses jsonschema, and invalid schema inputs are reported with ValidationError.
  • When NetCDF output is read back with automatic masking, the resulting numpy.ma.MaskedArray masking must be consistent with fill values.
  • The legacy values payload key is completely replaced by data; there is no requirement to support both keys.

Task Specification: Cleaning Up the NetCDF File When Writing Fails

Background

This task concerns a Python package called ncwriter, which provides the ability to build and write NetCDF files based on a template definition. The class of interest is DatasetTemplate, which can be imported as:

from ncwriter import DatasetTemplate

Existing API Surface (what this task relies on)

The following must be supported by the DatasetTemplate class, since the task depends on them:

  • DatasetTemplate.from_json(path) — a classmethod that builds a DatasetTemplate instance from the JSON template file located at path. It returns a DatasetTemplate instance.

  • template.ncobj — an instance attribute that refers to the underlying NetCDF dataset object. At the time the instance is created, this attribute must be initialized to None (i.e., before any write has been attempted, template.ncobj is None must hold).

  • template.to_netcdf(path) — an instance method that writes the dataset described by the template to the NetCDF file at path.

Behavior Required for This Task

What this task centers on is how to_netcdf handles the file when the write fails.

If to_netcdf(path) is invoked and the data/definition held in the template is invalid in a way that prevents the write from completing correctly, the method must:

  1. Raise a ValueError to signal that the write has failed.

  2. Open the underlying NetCDF dataset and then close it properly before propagating the exception. Once to_netcdf raises, the template.ncobj attribute must reference the NetCDF dataset object created during the attempt, and that object must report itself as closed. Specifically, after the call has failed:

    • template.ncobj is not None (the dataset object was assigned).
    • template.ncobj.isopen() returns False (the NetCDF file handle was closed as part of handling the failure).

Put differently, if an exception occurs partway through writing the NetCDF file, the file must not be left open — closing it must happen before the exception is re-raised to the caller, and the reference to the (now-closed) dataset object must remain accessible via template.ncobj.

Edge Cases and Details

  • Before any call to to_netcdf, template.ncobj must be None.
  • What triggers the failure is an inconsistency in the template that only becomes detectable at file-writing time (for example, dimension sizes that do not agree with the data being written). Detecting such an inconsistency during writing must result in a ValueError.
  • No matter what failure occurs, the NetCDF dataset object that was opened must be closed and must remain referenced by template.ncobj.

Task Specification: Flattened Template Schema for ncwriter

Overview of the migration

ncwriter templates are being moved to a flatter schema. The fields reserved by a template carry an underscore prefix, and ordinary metadata is stored directly next to those fields instead of under a metadata container that was previously required. Support for the legacy nested variable attributes mapping is kept, with the serialization behavior spelled out below.

Public API surface

Each of the following names must stay importable and callable exactly as shown.

ncwriter.schema
  • validate_dimensions(obj)
  • validate_variables(obj)
  • validate_global_attributes(obj) (taking over from the former public name validate_attributes)
  • ValidationError

All three validation functions return normally when the input is valid and raise ValidationError when it is invalid.

Top-level namespace of the package (ncwriter)
  • DatasetTemplate
  • ValidationError
  • metadata_attributes(mapping)

Format of the flat template

A template is a mapping — for example a JSON object, a dict, or an OrderedDict.

  • "_dimensions" is where the mapping of dimension names to sizes lives.
  • "_variables" is where the mapping of variable names to variable definitions lives.
  • Every top-level entry whose name does not begin with _ is a dataset global attribute.
  • Top-level entries with an underscore prefix in any other case are reserved and are not global attributes. For instance, "_format" must not appear among the dataset's global attributes.

A variable definition is a mapping whose entries are drawn from any combination of the following:

  • "_dimensions": a list of dimension names, which may be empty and may be omitted; when it is omitted, the variable is dimensionless.
  • "_datatype": a NetCDF datatype name, such as "float32", "float64", or "double".
  • "_data": the variable's values as array-like data, a NumPy masked array, or None.
  • Recognized control fields with an underscore prefix, including "_FillValue", "_zlib", and "_complevel". Other supported NetCDF control names use the same reserved underscore convention (for example, _shuffle, _fletcher32, _contiguous, _chunksizes, _endian, and _least_significant_digit). An arbitrary underscore-prefixed field is not permitted.
  • Ordinary keys without an underscore prefix, such as standard_name, units, and valid_min. These make up the flat variable template metadata.
  • For compatibility, the special key attributes, which is not underscore-prefixed and whose value is a nested mapping of NetCDF variable attributes.

Validation and writability are separate matters: an incomplete definition such as {}, or one that contains only _datatype, is valid template metadata, even though additional fields may be needed before it can be written.

metadata_attributes(mapping)

Given an input mapping, metadata_attributes returns a new mapping that contains exactly those input entries whose keys do not start with _. The function must:

  • leave out every underscore-prefixed entry;
  • keep every non-underscore entry together with its value; and
  • preserve the input's insertion order while not mutating the input.

For example, applying it to a top-level template removes _dimensions, _variables, and _format while title, abstract, and number are retained. The same filtering rule is what identifies flat metadata inside a variable definition. By itself, this filtering rule does not mean that flat variable metadata is serialized as NetCDF variable attributes; the serialization of variable attributes follows the compatibility rule described under to_netcdf.

Validation behavior

Dimension, variable, and ordinary attribute names must start with an ASCII letter and afterwards contain only ASCII letters, digits, or underscores (^[A-Za-z][A-Za-z0-9_]*$). Names such as X, TEMP_2, and Conventions are therefore valid, whereas 123, 0, _TEMP, and __X are invalid in those ordinary-name positions.

validate_dimensions(obj)

The input must be a mapping from valid dimension names to non-negative integer sizes or None (null in JSON). Zero and None are valid as unresolved/unlimited sizes.

For example, it must accept:

{}
{'X': 1, 'Y': 2}
{'TIME': 0, 'DEPTH': None}

It must raise ValidationError for non-mappings like None, 'X', ['X'], or 10, and for invalid entries like:

{'123': 123}   # invalid name
{'X': 'one'}   # invalid size type
{'X': -1}      # negative size
{'X': 1.5}     # non-integral size

Boolean values do not qualify as integer dimension sizes.

validate_variables(obj)

The input must be a mapping that goes from valid variable names to variable-definition mappings. It must accept empty and partial definitions, including all of these:

{}
{'X': {}}
{'X': {'_datatype': 'float32'}}
{'X': {'_dimensions': []}}
{'X': {'name': 'X'}}
{'X': {'_data': None}}
{'X': {'_dimensions': ['X'], '_datatype': 'float32'}}
{
    'X': {
        '_dimensions': ['X'],
        '_datatype': 'float32',
        '_data': [42],
        'name': 'X',
        'count': 1
    },
    'Y': {'_datatype': 'float64'}
}

The values of the reserved fields must be suitable:

  • _dimensions is a list whose entries are valid dimension-name strings;
  • _datatype is a string;
  • _data is array-like or None, and not a bare scalar; and
  • recognized creation/control fields have values that are suitable for their corresponding NetCDF options.

Ordinary flat metadata names obey the name rule above, and their values take scalar or array forms compatible with NetCDF attributes. The compatibility attributes entry is an explicit exception to that ordinary scalar/array value rule: it must be a mapping from individual NetCDF attribute names to values. Creation-time attributes such as _FillValue may be included in it.

Among other cases, validate_variables must raise ValidationError for:

  • None, a string like 'VAR', or any other outer value that is not a mapping;
  • a variable definition that is not a mapping;
  • a variable name that is invalid, such as __X or _TEMP;
  • a reserved field that is unknown, as in {'X': {'_datatype': 'float32', '_unknown': 'else'}};
  • a flat metadata name that is invalid, as in {'X': {'_datatype': 'float32', '0': 'none'}};
  • a reserved value with an incorrect type; and
  • scalar data such as {'X': {'_data': 100}}.
validate_global_attributes(obj)

The input must be a mapping whose attribute names are valid and non-underscore. Attribute values may be strings, numbers that are not booleans, or arrays/lists suited to NetCDF attributes.

It must accept these:

{}
{'name': 'test'}
{'name': 1.5}
{'name': [1, 2, 3]}

It must raise ValidationError for these:

None
'X'
[]
{'_badname': 1}
{'null': None}
{'bool': True}
{'object': {}}

In particular, None, booleans, and mappings are not valid as global-attribute values.

DatasetTemplate

Construction and instance state

The constructor keywords that are supported are dimensions, variables, and global_attributes.

Task Specification: Fill Value Handling for NetCDF Variables

Context

The module you are working on builds NetCDF datasets from template definitions. This relevant module lives at ncwriter/template.py and exposes a class DatasetTemplate. The class can be imported with:

from ncwriter import DatasetTemplate

Existing API (already in place)

Construction of DatasetTemplate takes the following keyword arguments:

DatasetTemplate(dimensions=<dict>, variables=<dict>)
  • dimensions associates dimension names with their sizes.
  • variables associates variable names with dicts describing each variable. A variable dict may contain the keys:
    • '_dimensions': a list of the dimension names.
    • '_datatype': the NetCDF data type (for example 'float32').
    • '_data': a numpy array (possibly a masked array) holding the values.
    • Fill-value keys (detailed below).

The instance exposes a variables attribute (a mutable mapping) whose entries are the per-variable dicts; this lets callers read and mutate variable definitions after construction.

The instance offers the method:

template.to_netcdf(path)

which writes the described dataset out to the NetCDF file path supplied to it.

Required Behavior

Alias keys for the fill value

A variable definition may specify a fill value through either of two alias keys:

  • '_FillValue'
  • '_fill_value'

Both keys are treated as referring to the same underlying fill value concept. When a variable is written to NetCDF, the resulting NetCDF variable must have its _FillValue attribute set to the specified value, no matter which alias key the variable definition used.

Applying the fill value during writing

When a variable has a fill value defined (through either alias) and has _data associated with it:

  • The NetCDF variable that gets written must carry a _FillValue attribute equal to the specified fill value.
  • Positions in the data whose values are equal to the fill value must be masked out when the resulting dataset is read back with automatic masking enabled. In other words, reading the variable produces a numpy.ma.MaskedArray in which those positions are masked and all other positions retain their original data values.
  • If the _data is supplied as a numpy.ma.masked_array, the masked positions must be written using the fill value, so that when the data is read back with automatic masking those same positions are masked and the unmasked positions retain their original values.
Handling both aliases at once

A single variable definition may contain both the '_FillValue' key and the '_fill_value' key at the same time:

  • If both keys are present and their values are equal, that is valid. The variable is then written normally with _FillValue set to that (shared) value.
  • If both keys are present and their values are not equal, this is an error condition: calling to_netcdf must raise ValueError.

  • The module ncwriter.template, containing the class DatasetTemplate (re-exported so from ncwriter import DatasetTemplate works).
  • A constructor accepting the dimensions and variables keyword arguments as described.
  • A mutable variables attribute holding the per-variable definition dicts.
  • A method to_netcdf(self, path) implementing the fill-value behavior described above, including raising ValueError for conflicting fill-value aliases.

dimensions

The merging must not mutate the operands, and it must not share nested dict references in a manner that corrupts the inputs; the object that is returned is a distinct DatasetTemplate whose dimensions, global_attributes, and variables reflect exactly the merged results described above.

Signature of the Method
def get_data_range(self, variable_name):
  • variable_name (str): identifies, by name, a variable that exists in the template's variables mapping.
  • Returns: a 2-tuple (min_value, max_value) that holds the smallest and largest valid values occurring in that variable's data array.
Behavior Requirements

Each variable found in the template's variables dictionary carries a '_data' entry that stores a NumPy array (or masked array). While excluding invalid/fill entries, the method must return the minimum and maximum of the data, per the rules that follow:

  1. NaN values must be ignored while the min and max are being computed. Finite (non-NaN) values are the only contributors to the range.

  2. Fill values must be ignored. Within its definition, a variable may declare a fill value through either the '_FillValue' or the '_fill_value' key. The range computation must exclude any data element equal to the declared fill value.

  3. Masked entries must be ignored. In the case where the data is a NumPy masked array, the elements that are masked must be excluded from the range computation.

  4. In the tuple that gets returned, the minimum valid value comes first and the maximum valid value comes second.
