01 Support Mixed Explicit/Implicit JOINs in SQL Parser 455 words · source specification

Task Specification: Support Mixed Explicit/Implicit JOINs in SQL Parser

Objective

Extend the SQL parser so that a single FROM clause can combine explicit JOIN syntax (e.g. INNER JOIN ... ON ...) with implicit comma-separated joins in one statement, producing a correctly nested join AST.

Public API

The parser is invoked through:

parse_sql(query: str)

This function must be importable and callable with a SQL string, returning the parsed AST. (Its containing module/package is already established in the codebase.)

The AST node classes that must be produced are the existing ones:

  • Select(targets=[...], from_table=...)
  • Join(left=..., right=..., condition=..., join_type=..., implicit=...)
  • Identifier(name, alias=Identifier(...))
  • Star()
  • BinaryOperation(op=..., args=[...])
  • JoinType enum, with member JoinType.INNER_JOIN

Required Behavior

Given a FROM clause that mixes an explicit join and additional comma-separated table references, the parser must build a left-deep chain of Join nodes.

Concrete case to support

For a query of the form:

select * from table1 a
   inner join table2 b on a.x = b.y
                 and k = p,
   table3,
   table4

The resulting Select must have:

  • targets = [Star()]
  • from_table = a nested Join structure built as follows (left-associative):

  1. Innermost join (the explicit join):

    • left = Identifier('table1', alias=Identifier('a'))
    • right = Identifier('table2', alias=Identifier('b'))
    • condition = BinaryOperation(op='and', args=[BinaryOperation(op='=', args=[Identifier('a.x'), Identifier('b.y')]), BinaryOperation(op='=', args=[Identifier('k'), Identifier('p')])])
    • join_type = JoinType.INNER_JOIN
    • implicit is not set / defaults (i.e. this join is explicit, not implicit)

  2. Next join (implicit comma join with table3):

    • left = the innermost join above
    • right = Identifier('table3')
    • join_type = JoinType.INNER_JOIN
    • implicit = True

  3. Outermost join (implicit comma join with table4):

    • left = the join from step 2
    • right = Identifier('table4')
    • join_type = JoinType.INNER_JOIN
    • implicit = True
Rules implied
  • A table following a comma in the FROM list becomes an implicit Join whose join_type is JoinType.INNER_JOIN and whose implicit flag is True.
  • The accumulated join expression so far becomes the left operand of each new implicit comma join; the newly listed table becomes the right operand.
  • An explicit INNER JOIN ... ON <condition> produces a Join with the given condition, join_type = JoinType.INNER_JOIN, and no implicit flag.
  • Table aliases (e.g. table1 a) are represented via the alias attribute of the Identifier, as Identifier(<alias>).
  • A multi-condition ON clause combined with AND produces a BinaryOperation(op='and', ...) whose args are the individual = comparisons.

Correctness Criteria

The parsed AST must be equivalent to the expected structure described above under both:

  • its string representation, and
  • its tree representation (to_tree()).

Backward-Compatibility Note

parse_sql must continue to work when called with only the query string (no additional dialect argument required for this case).

03 Track Quoting State of SQL Identifiers 469 words · source specification

Task Specification: Track Quoting State of SQL Identifiers

Overview

Extend the SQL parser and its AST to record whether each part of an identifier was written using backtick quoting in the original SQL, exposing this information through a new attribute on the Identifier AST node.

API Surface

The following must be importable and behave as described:

  • parse_sql(sql) — parses a SQL string and returns an AST node (existing function).
  • Select — AST node for SELECT statements, constructible with keyword arguments targets, from_table, and where.
  • Identifier — AST node for identifiers, constructible either as Identifier('name') or Identifier(parts=['name', ...]).
  • BinaryOperation — AST node constructible with keyword arguments op (string) and args (list of AST nodes).
  • Constant — AST node constructible with a single value, e.g. Constant(2).

These are imported from the same locations they already occupy in the codebase.

Required Behavior

New is_quoted attribute on Identifier

Every Identifier AST node produced by parse_sql must expose an attribute named is_quoted. Its value is a list of booleans, one entry per part of the identifier, in the same order as the identifier's parts. Each boolean indicates whether the corresponding part was written with backtick (`) quoting in the original SQL:

  • True — the part was enclosed in backticks.
  • False — the part was written without backticks.
Parsing behavior

Given a SQL statement such as:

select `KEY_ID` from `Table1` where `id`=2

Parsing must yield a Select node whose:

  • targets contains a single Identifier for KEY_ID.
  • from_table is an Identifier for Table1.
  • where is a BinaryOperation with op='=' and two args: an Identifier for id and a Constant with value 2.

For each of the three identifiers above (the target, the from-table, and the left-hand side of the where comparison), is_quoted must equal [True], since each is a single-part identifier written in backticks.

Given the equivalent statement without backticks:

select KEY_ID from Table1 where id=2

Parsing must yield an AST whose string representation is identical to the backtick version (i.e., quoting does not affect the structural/string equality of the AST). For each of the same three identifiers, is_quoted must equal [False].

String representation

The string representation (str(...)) of an AST parsed from a quoted statement and the string representation of an equivalent AST parsed from (or constructed as) the unquoted statement must be equal. Quoting state recorded in is_quoted must not change how an AST renders as a string when compared against an equivalent unquoted AST.

Notes

  • Identifier objects constructed directly (via Identifier('KEY_ID') or Identifier(parts=['Table1'])) must be comparable — by string representation — to identifiers produced by the parser regardless of the parser's recorded quoting state.
  • The is_quoted list length always matches the number of parts in the identifier.

  • parse_sql correctly parses a quoted name followed by a wildcard (e.g. `a`.*) into an Identifier with parts ending in a Star() instance and an is_quoted list of the correct length and values (one boolean per part; True for quoted components, False for the wildcard).
  • All previously supported quoting behavior for simple quoted identifiers, quoted table names, and quoted identifiers in WHERE clauses continues to work as described above.

Notes

parse_sql(sql: str)

  • Select — represents a SELECT statement. Relevant constructor keyword arguments used here: targets (list of expression nodes), where (an expression node), and from_table.

  • Identifier(...) — represents a column/table identifier. Can be constructed with a single name string, or with parts=[...].
  • Constant(value) — represents a literal value.
  • Star() — represents *.

Each AST node supports:

  • str(node) — renders the node back to an SQL string.
  • node.to_tree() — produces a structured tree representation.

Two AST trees are considered equivalent when both their str(...) renderings and their to_tree() renderings match.

Required behavior

The parser must recognize ->> as a binary operator (the JSON "get value as text" operator), in addition to the already-supported -> operator.

JSON operator parsing

When parsing an expression that uses -> and ->>, these operators are left-associative and share the same precedence, so they chain left-to-right.

For the input:

BinaryOperation(
    op='->>',
    args=[

            op='->',
            args=[
                Identifier('col'),
                Constant(1),
            ],
        ),
        Constant('c'),
    ],
)

i.e. col->1 is grouped first as a -> operation, and the result becomes the left operand of the outer ->> operation whose right operand is the string constant 'c'.

The resulting Select has this as its single target and from_table=Identifier(parts=['TAB1']).

Rendering this AST back to a string and to a tree must be consistent with re-parsing (round-trip stable): the ->> operator must render as ->>.

The following operators must continue to parse as BinaryOperation nodes with the operator string preserved exactly, without regression:

  • The vector operators <->, <+>, <#>, <=>, <~>, <%>. For an input of the form:

    SELECT * from TAB1 WHERE embedding <op> '[3,1,2]'

    the result must be a Select with targets=[Star()], from_table=Identifier(parts=['TAB1']), and

    where=BinaryOperation(
    op='<op>',
    args=[Identifier('embedding'), Constant('[3,1,2]')],
)

    where <op> is the exact operator string.

  • The -> JSON operator must continue to parse and render as before.

All of the above must round-trip: parsing, then rendering via str(...) and to_tree(), must yield output equivalent to the corresponding hand-built AST.

10 You must extend the SQL CREATE TABLE parser to correctly handle column type definitions that include two numeric parameters (e.g. 386 words · source specification

Overview

You must extend the SQL CREATE TABLE parser to correctly handle column type definitions that include two numeric parameters (e.g. precision and scale), such as decimal(5,2) and NUMBER(10, 0).

Public API

TableColumn

The TableColumn class represents a single column definition parsed from a CREATE TABLE statement. It must support the following attributes/constructor keyword arguments:

  • name (str): the column name.
  • type (str): the column type name, preserved exactly as written in the source (e.g. decimal, NUMBER, INT, TEXT).
  • is_primary_key (bool): whether the column is part of the table's primary key.
  • nullable (bool): whether the column allows NULL values.
  • length (int, optional): the first numeric parameter of the type, when present.
  • length2 (int, optional): the second numeric parameter of the type, when present.

TableColumn instances that carry identical attribute values must compare as equal.

Required Behavior

When parsing a CREATE TABLE statement, each column definition must produce a TableColumn:

  1. Type name preservation: The type attribute must retain the exact spelling used in the source text (do not normalize case). For example, decimal(5,2) yields type='decimal' and NUMBER(10, 0) yields type='NUMBER'.

  2. Two-parameter numeric types: A type declared with two comma-separated numeric parameters must populate both length (first parameter) and length2 (second parameter) as integers.

    • decimal(5,2) → length=5, length2=2
    • NUMBER(10, 0) → length=10, length2=0
    • Whitespace surrounding the parameters (as in NUMBER(10, 0)) must be tolerated.
    • A second parameter of 0 must be captured as length2=0 (i.e. treated as present, not omitted).

  3. Nullability: A column declared with a NOT NULL constraint must set nullable=False. For example, links NUMBER(10, 0) NOT NULL yields nullable=False.

  4. Primary keys: A table-level PRIMARY KEY (col_a, col_b) clause must mark each named column with is_primary_key=True.

  5. Simple types: Columns declared with a bare type and no parameters (e.g. INT, TEXT) produce a TableColumn with just name and type set (no length/length2).

The parser must be able to process a CREATE TABLE statement whose column list mixes simple typed columns, single-token constrained columns, two-parameter numeric columns (with and without NOT NULL), and a trailing table-level composite PRIMARY KEY clause.

Note

The table-level primary key keyword is written as PRIMARY KEY (two words separated by a space). There is no support for a single underscored PRIMARY_KEY token.
