01 Supporting Mixed Explicit/Implicit JOINs in the SQL Parser 495 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Supporting Mixed Explicit/Implicit JOINs in the SQL Parser

Goal

The SQL parser is to be extended so that a single FROM clause can combine explicit JOIN syntax (e.g. INNER JOIN ... ON ...) with implicit comma-separated joins in one statement, with a correctly nested join AST as the result.

Public API

The parser is invoked via:

parse_sql(query: str)

This function must be importable and callable with a SQL string, and it must return the parsed AST. (The module/package containing it is already established in the codebase.)

The AST node classes that must be produced are the ones that already exist:

  • Select(targets=[...], from_table=...)
  • Join(left=..., right=..., condition=..., join_type=..., implicit=...)
  • Identifier(name, alias=Identifier(...))
  • Star()
  • BinaryOperation(op=..., args=[...])
  • JoinType enum, with member JoinType.INNER_JOIN

Behavior Required

Whenever a FROM clause mixes an explicit join and additional comma-separated table references, the parser must construct a left-deep chain of Join nodes.

Concrete case to be supported

Take a query of the following form:

select * from table1 a
   inner join table2 b on a.x = b.y
                 and k = p,
   table3,
   table4

The Select that results must have:

  • targets = [Star()]
  • from_table = a nested Join structure constructed as follows (left-associative):

  1. Innermost join (the explicit join):

    • left = Identifier('table1', alias=Identifier('a'))
    • right = Identifier('table2', alias=Identifier('b'))
    • condition = BinaryOperation(op='and', args=[BinaryOperation(op='=', args=[Identifier('a.x'), Identifier('b.y')]), BinaryOperation(op='=', args=[Identifier('k'), Identifier('p')])])
    • join_type = JoinType.INNER_JOIN
    • implicit is not set / falls back to the default (i.e. this join is explicit, not implicit)

  2. Next join (implicit comma join involving table3):

    • left = the innermost join shown above
    • right = Identifier('table3')
    • join_type = JoinType.INNER_JOIN
    • implicit = True

  3. Outermost join (implicit comma join involving table4):

    • left = the join defined in step 2
    • right = Identifier('table4')
    • join_type = JoinType.INNER_JOIN
    • implicit = True
Implied Rules
  • A table that follows a comma in the FROM list becomes an implicit Join whose join_type is JoinType.INNER_JOIN and whose implicit flag is True.
  • For each new implicit comma join, the join expression accumulated so far becomes the left operand and the newly listed table becomes the right operand.
  • An explicit INNER JOIN ... ON <condition> results in a Join with the given condition, join_type = JoinType.INNER_JOIN, and no implicit flag.
  • Table aliases (e.g. table1 a) are represented by way of the alias attribute of the Identifier, in the form Identifier(<alias>).
  • A multi-condition ON clause whose conditions are combined with AND produces a BinaryOperation(op='and', ...) whose args are the individual = comparisons.

Criteria for Correctness

The parsed AST must be equivalent to the expected structure laid out above under both of the following:

  • its string representation, and
  • its tree representation (to_tree()).

Note on Backward Compatibility

parse_sql must keep working when it is called with only the query string (for this case, no additional dialect argument is required).

03 Recording the Quoting State of SQL Identifiers 507 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Recording the Quoting State of SQL Identifiers

Overview

The SQL parser and its AST are to be extended so that they record whether each part of an identifier was written using backtick quoting in the original SQL; this information is to be exposed through a new attribute on the Identifier AST node.

API Surface

Everything listed here must be importable and must behave as described:

  • parse_sql(sql) — parses a SQL string and returns an AST node (an already-existing function).
  • Select — AST node for SELECT statements; it is constructible using the keyword arguments targets, from_table, and where.
  • Identifier — AST node for identifiers; it is constructible either as Identifier('name') or as Identifier(parts=['name', ...]).
  • BinaryOperation — AST node that is constructible with the keyword arguments op (string) and args (list of AST nodes).
  • Constant — AST node that is constructible with a single value, e.g. Constant(2).

Imports of these come from the same locations they already occupy in the codebase.

Required Behavior

A new is_quoted attribute on Identifier

Every Identifier AST node that parse_sql produces must expose an attribute named is_quoted. Its value is a list of booleans, with one entry for each part of the identifier, ordered the same way as the identifier's parts. Each boolean states whether the matching part was written with backtick (`) quoting in the original SQL:

  • True — backticks enclosed the part.
  • False — the part was written with no backticks.
Behavior when parsing

For a SQL statement such as:

select `KEY_ID` from `Table1` where `id`=2

Parsing must yield a Select node in which:

  • targets contains exactly one Identifier for KEY_ID.
  • from_table is an Identifier for Table1.
  • where is a BinaryOperation with op='=' and two args: an Identifier for id and a Constant whose value is 2.

For each of those three identifiers (the target, the from-table, and the left-hand side of the where comparison), is_quoted must equal [True], because each one is a single-part identifier written in backticks.

With the equivalent statement written without backticks:

select KEY_ID from Table1 where id=2

Parsing must yield an AST whose string representation is identical to that of the backtick version (i.e., quoting does not affect the structural/string equality of the AST). For each of these same three identifiers, is_quoted must equal [False].

String representation

The string representation (str(...)) of an AST parsed from a quoted statement must be equal to the string representation of an equivalent AST parsed from (or constructed as) the unquoted statement. The quoting state recorded in is_quoted must not change how an AST renders as a string when it is compared against an equivalent unquoted AST.

Notes

  • Identifier objects constructed directly (via Identifier('KEY_ID') or Identifier(parts=['Table1'])) must be comparable — by string representation — to identifiers produced by the parser, no matter what quoting state the parser recorded.
  • The length of the is_quoted list always matches the number of parts in the identifier.

Summary

You must fix how the SQL parser handles backtick-quoted identifiers that include a wildcard (*) component, such as `a`.*. At present, when such an identifier is parsed, the parser does not correctly track which parts of the identifier were quoted. The aim of this task is to ensure the parser produces the correct AST structure together with per-part quoting metadata.

Background

The codebase contains a SQL parser that is exposed via the function:

  • parse_sql(sql: str) — parses a SQL string and returns an AST node.

The AST classes that are relevant (all of them importable from the SQL AST module used throughout the codebase) include:

  • Select — has the attributes targets (list), from_table, and where.
  • Identifier — built either as Identifier('name') or as Identifier(parts=[...]), where each element of parts may be a string or a Star() instance.
  • Star — stands for a * wildcard component inside an identifier's parts.
  • BinaryOperation — has the attributes op (string) and args (list).
  • Constant — encloses a literal value.

Required Behavior

Parsing an identifier that has a quoted name and a wildcard

Whenever a SQL statement is parsed and its select targets include an identifier of the form `a`.* (a backtick-quoted name component followed by a dot and a * wildcard), the parser must:

  1. Produce an Identifier for which parts is a list containing the string name followed by a Star() instance. For `a`.*, this is parts=['a', Star()].

  2. Set the identifier's is_quoted attribute to a list of booleans, one per part, that indicates whether each corresponding part was backtick-quoted in the source. For `a`.*, the name component a was quoted and the * wildcard was not, yielding is_quoted == [True, False].

For a statement of the form shown next, the following behavior must continue to hold:

select `KEY_ID`, `a`.* from `Table1` where `id`=2

Parsing it must yield a Select equivalent to:

  • targets: a list of two identifiers —
    • Identifier('KEY_ID') having is_quoted == [True]
    • Identifier(parts=['a', Star()]) having is_quoted == [True, False]
  • from_table: Identifier(parts=['Table1']) having is_quoted == [True]
  • where: BinaryOperation(op='=', args=[Identifier('id'), Constant(2)]), where the identifier in the left argument has is_quoted == [True]

The string representation of the AST that results must match the string representation of the equivalent AST built directly from the classes above.

Acceptance Criteria

  • parse_sql correctly parses a quoted name followed by a wildcard (e.g. `a`.*) into an Identifier with parts ending in a Star() instance and an is_quoted list of the correct length and values (one boolean per part; True for quoted components, False for the wildcard).
  • Every piece of previously supported quoting behavior for simple quoted identifiers, quoted table names, and quoted identifiers in WHERE clauses keeps working as described above.

Notes

  • Do not alter or standardize the rendering (round-trip string output) of an identifier that contains a wildcard component; only its parsing and its is_quoted metadata need to be correct.

Task: Support for pgvector Distance Operators in the SQL Parser

Goal

The SQL parser is to be extended so that it recognizes and correctly parses the pgvector distance/similarity operators when they appear as binary operators in a SQL statement.

Operators to Be Supported

The parser must recognize the following six operator tokens as valid binary operators:

  • <->
  • <+>
  • <#>
  • <=>
  • <~>
  • <%>

Required Parser Behavior

Within the WHERE clause of a SELECT statement (and anywhere that a binary operation is otherwise valid), the parser must accept these operators, handling them exactly like other binary operators.

As an example, given input of the form:

SELECT * from TAB1 WHERE embedding <-> '[3,1,2]'

The AST classes that matter are the ones already exported from mindsdb_sql_parser.ast: Select, Star, BinaryOperation, Identifier, and Constant.

There is no need to introduce new public functions or classes; the requirement is for the parser to accept these operator tokens and to build the corresponding BinaryOperation node with the operator string preserved.

06 The codebase contains an SQL parser exposed through a top-level function 459 words · source specification, reworded by GLM-5.3-Flash

Task: Support the ->> JSON operator in the SQL parser

Background

The codebase contains an SQL parser exposed through a top-level function:

parse_sql(sql: str)

The function takes an SQL string, parses it, and returns an Abstract Syntax Tree (AST) built from node objects. The AST node classes that matter here are importable from the parser's AST package and include (at minimum):

  • Select — models a SELECT statement. Constructor keyword arguments used here that are relevant: targets (a list of expression nodes), where (an expression node), and from_table.
  • BinaryOperation(op, args) — models a binary operation, where op is a string naming the operator and args is a two-element list of operand nodes.
  • Identifier(...) — models a column/table identifier. It can be built either from a single name string or with parts=[...].
  • Constant(value) — models a literal value.
  • Star() — models *.

Each AST node supports:

  • str(node) — renders the node back into an SQL string.
  • node.to_tree() — produces a structured representation of the tree.

Two AST trees are regarded as equivalent when their str(...) renderings and their to_tree() renderings both match.

Behavior requirements

In addition to the already-supported -> operator, the parser must recognize ->> as a binary operator (the JSON "get value as text" operator).

Parsing the JSON operators

When parsing an expression that uses -> and ->>, the two operators are left-associative and have the same precedence, so they chain left-to-right.

Given the input:

SELECT col->1->>'c' from TAB1

the target expression produced by parsing must be:

BinaryOperation(
    op='->>',
    args=[
        BinaryOperation(
            op='->',
            args=[
                Identifier('col'),
                Constant(1),
            ],
        ),
        Constant('c'),
    ],
)

That is, col->1 is grouped first as a -> operation, and that result becomes the left operand of the outer ->> operation, whose right operand is the string constant 'c'.

The resulting Select has this expression as its single target, together with from_table=Identifier(parts=['TAB1']).

Rendering this AST back to a string and to a tree must stay consistent with re-parsing (round-trip stable): the ->> operator must render as ->>.

Existing operators must stay intact

The following operators must continue to parse as BinaryOperation nodes with the operator string preserved exactly, with no regression:

  • The vector operators <->, <+>, <#>, <=>, <~>, <%>. Given an input of the form:

    SELECT * from TAB1 WHERE embedding <op> '[3,1,2]'

    the result must be a Select with targets=[Star()], with from_table=Identifier(parts=['TAB1']), and with

    where=BinaryOperation(
    op='<op>',
    args=[Identifier('embedding'), Constant('[3,1,2]')],
)

    with <op> being the exact operator string.

  • The -> JSON operator must keep parsing and rendering as it did before.

All of the above must round-trip: parsing and then rendering via str(...) and to_tree() must yield output equivalent to the corresponding hand-built AST.

Task Specification: DISTINCT ON Support in SELECT statements

Summary

Extend the SQL parser and AST with support for the PostgreSQL-style DISTINCT ON (...) clause in SELECT statements. Parsing must result in an AST node whose distinct attribute carries the list of columns specified in the DISTINCT ON clause, and rendering that AST back into a string must reproduce the original SQL.

Background

  • A Select AST node (importable as Select) already exists and supports a distinct attribute. Up to now, distinct was a plain boolean flag indicating whether a bare DISTINCT keyword was present.
  • A parse_sql(sql_string) function exists that parses a SQL string into an AST.
  • An Identifier node and a Star node are available.
  • AST nodes support:
    • str(ast) — renders the node back into SQL text.
    • ast.to_tree() — gives a structural tree representation.
    • Two ASTs are compared for equivalence by checking equality of their rendered output and tree output.

Behavior Requirements

Semantics of Select.distinct

In addition to its existing boolean behavior, the distinct attribute of Select must now support carrying a list of Identifier objects.

  • If distinct is a list of Identifier objects, it represents a DISTINCT ON (...) clause; the identifiers in the list are the columns inside the parentheses, in order.
Parsing

parse_sql must accept DISTINCT ON (col1, col2, ...) syntax placed immediately after SELECT. When this syntax is present:

  • The columns within the parentheses must be parsed into a list of Identifier objects, which is assigned to the distinct attribute of the resulting Select node with their order preserved.
  • Each column may be a simple identifier (e.g. column1) or a dotted/multi-part identifier (e.g. t1.column1). A dotted identifier must be represented as a single Identifier whose value reflects the complete dotted path.
  • One or more comma-separated columns may be listed.
  • The rest of the SELECT statement (targets, FROM, etc.) is parsed as usual. The targets may be a Star or a list of identifiers.

Example inputs that must parse correctly:

SELECT DISTINCT ON (t1.column1) * FROM t1

results in a Select equivalent to:

Select(
    targets=[Star()],
    from_table=Identifier('t1'),
    distinct=[Identifier('t1.column1')]
)

SELECT DISTINCT ON (column1, column2) column3, column4 FROM t1

parses to a Select equivalent to:

Select(
    targets=[Identifier('column3'), Identifier('column4')],
    from_table=Identifier('t1'),
    distinct=[Identifier('column1'), Identifier('column2')]
)
Rendering

When a Select node's distinct attribute is a list of Identifier objects, str(...) must render a DISTINCT ON (...) clause after SELECT, with the identifiers listed in order, comma-separated, inside parentheses. For the inputs above, the round-trip str(parse_sql(sql)) must reproduce equivalent SQL.

The output of to_tree() must reflect the list of distinct identifiers such that two Select nodes constructed with equal distinct lists produce identical trees.

Public API

  • Select — an AST node that accepts the keyword arguments targets, from_table, and distinct (where distinct may be a list of Identifier).
  • Identifier — accepts a string value, which may contain dotted parts.
  • Star — stands for *.
  • parse_sql(sql: str) — returns an AST node.

All of the items above must be importable from the same locations where they are currently exposed.

10 The SQL CREATE TABLE parser must be extended so that it correctly handles column type definitions carrying two numeric parameters (e.g. 402 words · source specification, reworded by GLM-5.3-Flash

Overview

The SQL CREATE TABLE parser must be extended so that it correctly handles column type definitions carrying two numeric parameters (e.g. precision and scale), for instance decimal(5,2) and NUMBER(10, 0).

Public API

TableColumn

The TableColumn class models a single column definition taken from a parsed CREATE TABLE statement. It must support the following attributes/constructor keyword arguments:

  • name (str): the name of the column.
  • type (str): the name of the column's type, kept exactly as it is written in the source (e.g. decimal, NUMBER, INT, TEXT).
  • is_primary_key (bool): whether the column belongs to the table's primary key.
  • nullable (bool): whether the column permits NULL values.
  • length (int, optional): the type's first numeric parameter, when present.
  • length2 (int, optional): the type's second numeric parameter, when present.

Instances of TableColumn that hold the same attribute values must compare as equal.

Behavior Requirements

Parsing a CREATE TABLE statement must produce a TableColumn for each column definition:

  1. Type name preservation: The type attribute must keep the exact spelling found in the source text (case must not be normalized). For example, decimal(5,2) produces type='decimal' and NUMBER(10, 0) produces type='NUMBER'.

  2. Two-parameter numeric types: When a type is declared with two comma-separated numeric parameters, both length (first parameter) and length2 (second parameter) must be populated as integers.

    • decimal(5,2) → length=5, length2=2
    • NUMBER(10, 0) → length=10, length2=0
    • Whitespace around the parameters (as in NUMBER(10, 0)) must be tolerated.
    • A second parameter of 0 must be captured as length2=0 (i.e. counted as present, not omitted).
