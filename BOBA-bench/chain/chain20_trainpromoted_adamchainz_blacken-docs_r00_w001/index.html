01 You are working on blacken_docs, a tool that formats Python code embedded within documentation (reStructuredText, Markdown, etc.) using black. 351 words · source specification
Overview

You are working on blacken_docs, a tool that formats Python code embedded within documentation (reStructuredText, Markdown, etc.) using black. Your task is to fix a bug in the handling of interactive Python console (pycon) sessions embedded in reStructuredText code-block:: pycon directives.

Public API

The module blacken_docs must expose a function with the following signature:

def format_str(src: str, black_mode) -> tuple[str, ...]
  • src: the full source text of a documentation file as a string.
  • black_mode: a black mode/configuration object (an instance of black.Mode / black.FileMode).
  • Returns a tuple whose first element is the reformatted source text as a string.
Required Behavior

When processing a reStructuredText pycon code block, i.e. a block introduced by:

.. code-block:: pycon

the tool parses the interactive session inside it. Such a session may contain a traceback in which the stack frames are elided using an ellipsis line. Specifically, a block like:

.. code-block:: pycon

    >>> 1 / 0
    Traceback (most recent call last):
      ...
    ZeroDivisionError: division by zero

must be processed without raising any error. The ellipsis line (...) here appears as part of console output (a traceback), not as a Python continuation prompt.

The tool must correctly distinguish an ellipsis appearing in console output from a ... continuation prompt inside a >>> statement. An ellipsis line that is not part of an active continuation prompt must be treated as ordinary output and left unchanged.

For the block above, since the input statement (1 / 0) requires no reformatting, the entire block — including the traceback output and its elided ... line — must be returned exactly as given, with no changes to indentation, content, or surrounding structure.

Edge Case / Error Condition Being Fixed

Previously, encountering a ... line that was not preceded by an open continuation prompt caused an internal failure. The corrected behavior is that such a line is handled gracefully as output and the surrounding document is preserved verbatim (subject only to normal black formatting of actual code statements, which in this case makes no changes).

04 Add support for formatting pycon (Python console session) code blocks embedded in Markdown documents. 1019 words · source specification
Overview

Add support for formatting pycon (Python console session) code blocks embedded in Markdown documents. The functionality lives in the blacken_docs module and is exercised through its public format_str function.

Public API
blacken_docs.format_str(src: str, black_mode) -> tuple[str, ...]
  • src: the full text of a document (Markdown / reStructuredText style content) as a string.
  • black_mode: a Black Mode object controlling formatting.
  • Returns a tuple whose first element is the reformatted document string. (Tests only inspect the first element; the remainder is unpacked but not otherwise checked.)
Required Behavior

The existing behavior of format_str must be preserved. The new requirement is that Markdown fenced code blocks tagged as pycon must be recognized and their interactive Python console sessions reformatted with Black.

Markdown pycon fenced blocks

A Markdown fenced pycon block opens with a line consisting of optional leading indentation followed by ```pycon and closes with a line consisting of the same indentation followed by ```. The content between these fences is an interactive Python console session and must be reformatted as described below.

A console session inside such a block consists of:

  • Prompt lines beginning with >>> (primary prompt) and continuation lines beginning with ... .
  • Output lines — any lines that are not prompt/continuation lines and that follow a statement; these represent the program's printed output or tracebacks.
Reformatting rules

  1. Extract, format, re-emit. For each console statement (a >>> line plus any following ... continuation lines), the Python source is extracted, formatted with Black under the given mode, and re-emitted with >>> on the first line and ... on each subsequent line of the formatted result.

  2. Normalize indentation of the session. The console session's prompts and output are emitted relative to the code block's fence indentation. Any extra leading indentation present on the prompt/output lines beyond the fence indentation is stripped. Concretely:

    • For a non-indented ```pycon block, >>>/.../output lines are emitted flush-left (no leading spaces before >>>).
    • Input prompt lines that appeared with extra indentation (e.g. four spaces before >>>) have that extra indentation removed.

  3. Continuation reflowing. Because Black may add or remove lines, the number of ... continuation lines is determined by the formatted output, not the input. A single-line input statement may expand into multiple output lines (first line >>> , remaining lines ... ), and vice versa.

  4. Nested/compound statements get a trailing blank continuation. When a formatted statement spans multiple logical lines forming a compound statement (e.g. an if block, or a nested def), the emitted session ends that statement with a final ... line (a continuation prompt with no trailing content). This trailing ... line must be present even when the block was the final content before the closing fence and the input omitted it.

  5. Output lines are preserved verbatim. Lines that are program output (including multi-line tracebacks, indented traceback frames such as File "<stdin>", line 1, in <module>, and elided ... frames) are passed through unchanged, retaining their original indentation.

  6. Trailing whitespace / surrounding text preserved. Text before and after the fenced block, blank lines, and trailing blank lines around the block are preserved exactly.

  7. Blocks with no prompt are left unchanged. If a pycon block's content contains no >>> prompt (e.g. only plain text or code without a prompt), the block is emitted unchanged.

  8. Leading comment lines before a prompt are left unchanged. If a comment line (e.g. # Comment about next line) appears before the >>> prompt inside the block, the block content is preserved unchanged (the comment is not consumed into a statement, and no reformatting of that block occurs).

Concrete examples

```pycon

    >>> f(1,2,3)
    output

world

Output:

hello


>>> f(1, 2, 3)
output

world


Input:

    >>> d = {
    ...   "a": 1,
    ...   "b": 2,
    ...   "c": 3,}

Output:

>>> d = {
...     "a": 1,
...     "b": 2,
...     "c": 3,
... }


Input:

    >>> d = {"a": 1,"b": 2,"c": 3,}

Output:

>>> d = {
...     "a": 1,
...     "b": 2,
...     "c": 3,
... }


Indented block input:

```pycon

```

-world

Output:

-hello

```pycon

Compound statement closing with trailing continuation (input lacking the final `...`):

>>> if True:
...   pass

Output:

>>> if True:
...     pass
...


Nested def (input lacking final `...`):

>>> if True:
...     def f(): pass

Output:

...     def f():
...         pass

Empty continuation line in a collection literal:

...

(unchanged)

No-prompt block (unchanged):

>>> pass


#### reStructuredText `pycon` behavior

Existing reStructuredText `.. code-block:: pycon` handling must continue to work. In particular, a comment line placed before the `>>>` prompt inside such a block must leave the block content unchanged:

Input/Output (unchanged):

(Note: the leading `# comment before prompt → no change` behavior applies to both the RST and Markdown pycon cases.)

### Notes

- All non-`pycon` content and all existing document-formatting behavior is unaffected.

Task Specification: Add Sphinx Doctest Directive Support to blacken-docs

Public API

Module: blacken_docs

Function to be provided:

def format_str(src: str, black_mode) -> tuple[str, ...]
  • src: the full source text of a documentation file (as a string).
  • black_mode: a Black Mode instance describing the formatting configuration.
  • Returns a tuple whose first element is the reformatted source text (string). Only the first element is consumed by callers; the remaining elements are unconstrained by this task.

Required Behavior

format_str reformats Python code embedded in reStructuredText (RST) documents by running Black over the recognized code regions, while leaving surrounding prose and non-code content unchanged.

New requirement: Sphinx doctest directives

In addition to the RST code blocks already supported, format_str must recognize and reformat the Python code contained in the following Sphinx directives:

  • .. testsetup::
  • .. testcleanup::
  • .. doctest::
  • .. testcode::

Each of these may optionally be followed by arguments on the directive line (e.g. a group name such as group1). The directive line, any arguments, and the blank line separating the directive from its body must be preserved exactly.

Directive body handling

The indented body following one of these directives is Python source that must be reformatted with Black using the provided black_mode, then re-emitted with the same indentation as the original body.

Two body styles must be supported:

  1. Plain Python source (as in testsetup, testcleanup, and testcode): The entire indented block is a Python snippet. It must be formatted as a unit with Black and the result re-indented to match the block's original indentation.

    • When Black splits statements or normalizes the code such that multiple statements existed, the reformatted output must reflect Black's output verbatim (re-indented), including blank lines Black inserts between top-level statements.

  2. Interactive (doctest) source (as in doctest): The block contains interactive-prompt lines (>>> for primary prompts, ... for continuation prompts) intermixed with expected-output lines. Only the code following the prompts is reformatted with Black; the prompt markers must be preserved on the reformatted code, and any non-prompt lines (expected output) must be passed through unchanged.

Formatting details
  • Superfluous internal whitespace in the Python code (e.g. spaces inside call parentheses like SomeMock( ) or parrot.voom( 3000 )) is normalized by Black to its canonical form (SomeMock(), parrot.voom(3000)).
  • Trailing whitespace on code lines is removed as part of Black formatting.
  • The blank line that separates the directive line from its indented body is retained.
  • For a plain-source block that Black expands into multiple top-level statements, the statements must be separated in the output as Black produces them (i.e. with an intervening blank line at the block's indentation level).
  • Expected-output lines in a doctest block (including any prose text that is not a prompt line) are emitted unchanged.
  • Overall document structure, blank lines between directives, and any content outside these directives must be preserved.
Example

Input:

.. testsetup:: group1

   import parrot  
   mock = SomeMock( )

.. testcleanup:: group1

   mock.stop( )

.. doctest:: group1

   >>> parrot.voom( 3000 )
   This parrot wouldn't voom if you put 3000 volts through it!

.. testcode::

   parrot.voom( 3000 )

Output:

.. testsetup:: group1

   import parrot

   mock = SomeMock()

.. testcleanup:: group1

   mock.stop()

.. doctest:: group1

   >>> parrot.voom(3000)
   This parrot wouldn't voom if you put 3000 volts through it!

.. testcode::

   parrot.voom(3000)

Note in this example:

  • The testsetup body has two statements (import parrot and mock = SomeMock()); after formatting they are separated by a blank line at the same indentation.
  • The doctest prompt line is reformatted but the following expected-output line is left exactly as-is.

Scope

The behavior described above is the complete scope. Existing RST code-block handling continues to apply. No Markdown or pycon-block behavior is required by this task.

Context

The public function blacken_docs.format_str must accept a new keyword-only argument:

def format_str(src, black_mode, *, rst_literal_blocks=False):
    ...
  • src (str): the documentation source text.
  • black_mode: the Black Mode object controlling formatting.
  • rst_literal_blocks (bool, keyword argument, default False): when True, enables formatting of reStructuredText literal blocks (described below).

The function returns a 2-tuple (new_contents, errors), where new_contents is the reformatted source (str) and errors is a list of errors (empty list when there are none).

All existing behavior and existing keyword arguments must be preserved. The new argument must not disturb any current functionality when left at its default.

New Behavior: reStructuredText Literal Blocks

When rst_literal_blocks=True, the function must additionally detect and reformat Python code contained in reStructuredText literal blocks.

A literal block is introduced by a paragraph line ending with the double-colon marker ::, followed by a blank line, followed by an indented block of content. The indented content is the literal block body. For example, given input:

hello::

    f(1,2,3)

world

with rst_literal_blocks=True, the indented body (f(1,2,3)) is treated as Python code and reformatted with Black, while the surrounding text and indentation are preserved. The result is:

hello::

    f(1, 2, 3)

    * hello

  .. warning::

    don't hello too much

    The source must be returned unchanged, with an empty list of errors. (Here warning:: is a directive line, not a paragraph ending in the literal-block marker followed by an indented Python body.)

  2. Empty literal block. When a line ends with :: but no indented literal body follows it (the next non-blank content is at the same or lower indentation, e.g. a directive):

    Example::

.. warning::

    There was no example.

    The source must be returned unchanged, with an empty list of errors.

In both edge cases the reformatting must correctly recognize that there is no Python literal block body to format, and leave the input untouched.

Scope Note

This new detection applies only when rst_literal_blocks=True. It is a separate capability from the existing reStructuredText .. code-block:: / doctest handling, which continues to work unchanged regardless of this flag.

Existing string-normalization, line-length, target-version, error-reporting, and skip-errors behavior of the module and its main entry point remain unchanged.
