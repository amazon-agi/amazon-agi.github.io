01 You are contributing to blacken_docs, a tool that uses black to format Python code embedded inside documentation (reStructuredText, Markdown, etc.). 379 words · source specification, reworded by GLM-5.3-Flash

Specification of the Task

Summary

You are contributing to blacken_docs, a tool that uses black to format Python code embedded inside documentation (reStructuredText, Markdown, etc.). Your job is to repair a bug in the handling of interactive Python console (pycon) sessions that are embedded in reStructuredText code-block:: pycon directives.

Public Interface

A function with the following signature must be exposed by the module blacken_docs:

def format_str(src: str, black_mode) -> tuple[str, ...]
  • src: the entire source text of a documentation file, provided as a string.
  • black_mode: a mode/configuration object from black (an instance of black.Mode / black.FileMode).
  • Returns a tuple, the first element of which is the reformatted source text as a string.
Behavior Requirements

When the tool processes a reStructuredText pycon code block, i.e. a block introduced by:

.. code-block:: pycon

it parses the interactive session within. A session of this kind may contain a traceback in which the stack frames are elided by means of an ellipsis line. As a specific case, a block like:

.. code-block:: pycon

    >>> 1 / 0
    Traceback (most recent call last):
      ...
    ZeroDivisionError: division by zero

must be processed without any error being raised. Here, the ellipsis line (...) appears as part of the console output (a traceback), not as a Python continuation prompt.

The tool must correctly distinguish between an ellipsis that appears in console output and a ... continuation prompt inside a >>> statement. An ellipsis line that does not form part of an active continuation prompt must be treated as ordinary output and left unchanged.

For the block shown above, because the input statement (1 / 0) requires no reformatting, the entire block — the traceback output and its elided ... line included — must be returned exactly as given, with no changes to indentation, content, or surrounding structure.

Edge Case / Error Condition Being Addressed

Previously, encountering a ... line that was not preceded by an open continuation prompt resulted in an internal failure. The corrected behavior is that a line of this kind is handled gracefully as output and the document surrounding it is preserved verbatim (subject only to normal black formatting of actual code statements, which in this case makes no changes).

04 Support is added for formatting pycon (Python console session) code blocks embedded in Markdown documents. 1091 words · source specification, reworded by GLM-5.3-Flash
Summary

Support is added for formatting pycon (Python console session) code blocks embedded in Markdown documents. The capability sits in the blacken_docs module and is exercised via its public format_str function.

Public API
blacken_docs.format_str(src: str, black_mode) -> tuple[str, ...]
  • src: a string holding the complete text of a document (content in the Markdown / reStructuredText style).
  • black_mode: a Black Mode object that governs the formatting.
  • The function returns a tuple whose first element is the document string after reformatting. (The tests look at the first element only; the rest is unpacked but is not checked in any other way.)
Required Behavior

format_str must retain its existing behavior. What is newly required is that fenced code blocks in Markdown carrying the pycon tag must be recognized, and the interactive Python console sessions inside them must be reformatted with Black.

Fenced pycon blocks in Markdown

A fenced pycon block in Markdown opens with a line consisting of optional leading indentation followed by ```pycon and closes with a line consisting of the same indentation followed by ```. Whatever sits between these fences is an interactive Python console session and must be reformatted as set out below.

Inside such a block, a console session is made up of:

  • Prompt lines starting with >>> (the primary prompt) and continuation lines starting with ... .
  • Output lines — any line that is not a prompt/continuation line and that comes after a statement; such lines stand for the program's printed output or its tracebacks.
Rules for reformatting

  1. Pull out, format, write back. For each console statement (a >>> line together with any ... continuation lines that follow it), the Python source is pulled out, formatted with Black under the given mode, and written back with >>> on the first line and ... on each of the remaining lines of the formatted result.

  2. Normalize the session's indentation. The prompts and output of the console session are emitted relative to the code block's fence indentation. Any extra leading indentation that the prompt/output lines carry beyond the fence indentation is stripped. Concretely:

    • In a non-indented ```pycon block, >>>/.../output lines are emitted flush-left (no leading spaces before >>>).
    • Prompt lines in the input that carried extra indentation (e.g. four spaces before >>>) have that extra indentation removed.

  3. Reflowing of continuations. Since Black may add or remove lines, how many ... continuation lines appear is decided by the formatted output rather than by the input. A statement occupying a single input line may spread over several output lines (the first line >>> , the remaining lines ... ), and the reverse can happen too.

  4. Nested/compound statements receive a trailing blank continuation. When a formatted statement stretches across multiple logical lines that together form a compound statement (e.g. an if block, or a nested def), the emitted session ends that statement with a final ... line (a continuation prompt with no trailing content). This trailing ... line must be present even when the block was the final content before the closing fence and the input left it out.

  5. Output lines are kept verbatim. Lines that are program output (including multi-line tracebacks, indented traceback frames such as File "<stdin>", line 1, in <module>, and elided ... frames) pass through unchanged, with their original indentation retained.

  6. Trailing whitespace / surrounding text is preserved. Text that comes before and after the fenced block, blank lines, and the trailing blank lines around the block are preserved exactly.

  7. A block with no prompt comes out unchanged. If the content of a pycon block holds no >>> prompt (e.g. only plain text or code that has no prompt), the block is emitted unchanged.

  8. Leading comment lines before a prompt are left unchanged. If a comment line (e.g. # Comment about next line) shows up before the >>> prompt inside the block, the block's content is left unchanged (the comment is not absorbed into a statement, and no reformatting of that block happens).

Concrete examples

Input:

hello

```pycon

    >>> f(1,2,3)
    output

world

Output:

hello


>>> f(1, 2, 3)
output

world


Input:

    >>> d = {
    ...   "a": 1,
    ...   "b": 2,
    ...   "c": 3,}

Output:

>>> d = {
...     "a": 1,
...     "b": 2,
...     "c": 3,
... }


Input:

    >>> d = {"a": 1,"b": 2,"c": 3,}

Output:

>>> d = {
...     "a": 1,
...     "b": 2,
...     "c": 3,
... }


Indented block input:

-hello

```pycon
>>> def hi():
...     f(1,2,3)
...
```

-world

Output:

-hello

```pycon
>>> def hi():
...     f(1, 2, 3)
...
```

-world


Compound statement closing with trailing continuation (input lacking the final `...`):

>>> if True:
...   pass

Output:

>>> if True:
...     pass
...


Nested def (input lacking final `...`):

>>> if True:
...     def f(): pass

Output:

>>> if True:
...     def f():
...         pass
...


Empty continuation line in a collection literal:

>>> l = [
...
...     1,
... ]

Output:

>>> l = [
...     1,
... ]


Traceback output preserved verbatim:

  File "<stdin>", line 1, in <module>

(unchanged)

Elided traceback preserved verbatim:

  ...

(unchanged)

No-prompt block (unchanged):

pass


Comment-before-prompt block (unchanged):

# Comment about next line
>>> pass


#### reStructuredText `pycon` behavior

Existing reStructuredText `.. code-block:: pycon` handling must continue to work. In particular, a comment line placed before the `>>>` prompt inside such a block must leave the block content unchanged:

Input/Output (unchanged):

.. code-block:: pycon

# Comment about next line
>>> pass


(Note: the leading `# comment before prompt → no change` behavior applies in both the RST and the Markdown pycon cases.)

### Notes

- Black carries out the formatting using the supplied mode object; the Python that is emitted matches Black's output for the extracted source.
- All content that is not `pycon` and all existing document-formatting behavior is unaffected.
05 Add Support for Sphinx Doctest Directives in blacken-docs 685 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Add Support for Sphinx Doctest Directives in blacken-docs

Public interface

The relevant module is blacken_docs.

The following function must be provided:

def format_str(src: str, black_mode) -> tuple[str, ...]
  • src: the full source text of a documentation file, given as a string.
  • black_mode: an instance of Black's Mode that describes the formatting configuration.
  • It returns a tuple whose first element is the reformatted source text (a string). Only the first element is consumed by callers; this task places no constraints on the remaining elements.

Behavior requirements

format_str reformats Python code that is embedded in reStructuredText (RST) documents: it runs Black over the recognized code regions while leaving the surrounding prose and non-code content unchanged.

New requirement: support for Sphinx doctest directives

Besides the RST code blocks that are already supported, format_str must recognize the Python code contained in the following Sphinx directives and reformat it:

  • .. testsetup::
  • .. testcleanup::
  • .. doctest::
  • .. testcode::

For each of these, the directive line may optionally carry arguments (e.g. a group name such as group1). The directive line itself, any arguments on it, and the blank line that separates the directive from its body must be preserved exactly.

Handling of directive bodies

The indented body that follows one of these directives is Python source; it must be reformatted with Black using the supplied black_mode and then re-emitted with the same indentation as the original body.

Two styles of body must be supported:

  1. Plain Python source (as in testsetup, testcleanup, and testcode): The entire indented block is a single Python snippet. It must be formatted as a unit with Black, and the result must be re-indented to match the block's original indentation.

    • If Black splits statements or normalizes the code such that multiple statements existed, the reformatted output must reflect Black's output verbatim (re-indented), including the blank lines Black inserts between top-level statements.

  2. Interactive (doctest) source (as in doctest): The block mixes interactive-prompt lines (>>> for primary prompts, ... for continuation prompts) together with expected-output lines. Only the code that follows the prompts is reformatted with Black; the prompt markers must be preserved on the reformatted code, and any lines that are not prompt lines (the expected output) must be passed through unchanged.

Details of the formatting
  • Internal whitespace that is superfluous in the Python code (e.g. spaces inside call parentheses like SomeMock( ) or parrot.voom( 3000 )) is normalized by Black to its canonical form (SomeMock(), parrot.voom(3000)).
  • Trailing whitespace on code lines is removed as part of Black's formatting.
  • The blank line between the directive line and its indented body is retained.
  • If a plain-source block is expanded by Black into multiple top-level statements, those statements must be separated in the output as Black produces them (i.e. with an intervening blank line at the block's indentation level).
  • In a doctest block, expected-output lines (including any prose text that is not a prompt line) are emitted unchanged.
  • The overall structure of the document, the blank lines between directives, and any content outside these directives must be preserved.
Example

The input:

.. testsetup:: group1

   import parrot  
   mock = SomeMock( )

.. testcleanup:: group1

   mock.stop( )

.. doctest:: group1

   >>> parrot.voom( 3000 )
   This parrot wouldn't voom if you put 3000 volts through it!

.. testcode::

   parrot.voom( 3000 )

The output:

.. testsetup:: group1

   import parrot

   mock = SomeMock()

.. testcleanup:: group1

   mock.stop()

.. doctest:: group1

   >>> parrot.voom(3000)
   This parrot wouldn't voom if you put 3000 volts through it!

.. testcode::

   parrot.voom(3000)

Points to note in this example:

  • The body of testsetup contains two statements (import parrot and mock = SomeMock()); after formatting, they are separated by a blank line at the same indentation.
  • In doctest, the prompt line is reformatted, but the expected-output line that follows is left exactly as-is.

Scope

The behavior described above constitutes the complete scope. The existing handling of RST code blocks still applies. This task requires no Markdown or pycon-block behavior.

Background

A new keyword-only argument must be accepted by the public function blacken_docs.format_str:

    ...
  • src (str): the text of the documentation source.
  • black_mode: the Black Mode object that controls formatting.
  • rst_literal_blocks (bool, keyword argument, default False): setting it to True enables formatting of reStructuredText literal blocks (described below).

The return value is a 2-tuple (new_contents, errors): new_contents holds the reformatted source (str), and errors is a list of errors (an empty list when there are none).

All behavior and all keyword arguments that already exist must be preserved. When the new argument is left at its default, it must not disturb any current functionality.

New Behavior: Literal Blocks in reStructuredText

If rst_literal_blocks=True is passed, the function must, in addition, detect Python code contained in reStructuredText literal blocks and reformat it.

A paragraph line ending with the double-colon marker :: introduces a literal block; after it come a blank line and then an indented block of content. That indented content is the literal block body. For example, take this input:

hello::

    f(1,2,3)

world

Passing rst_literal_blocks=True causes the indented body (f(1,2,3)) to be treated as Python code and reformatted with Black, while the surrounding text and indentation are preserved. The output is:

hello::

    f(1, 2, 3)

  1. Nested content that does not form a literal block. This case applies when the :: marker does not introduce a literal block of Python code — for example, a bulleted list item that contains an indented reStructuredText directive rather than a literal block introduced by :::

    * hello

  .. warning::

    don't hello too much

    The function must return the source unchanged, together with an empty list of errors. (In this example, warning:: is a directive line, not a paragraph that ends in the literal-block marker and is followed by an indented Python body.)

  2. Literal block that is empty. A line ends with ::, but no indented literal body follows it (the next non-blank content sits at the same or lower indentation, e.g. a directive):

    Example::

.. warning::

    There was no example.

    The function must return the source unchanged, together with an empty list of errors.

In both edge cases, the reformatting must correctly recognize that no Python literal block body is present to format, and leave the input untouched.

This new detection takes effect only when rst_literal_blocks=True. It is a capability separate from the existing reStructuredText .. code-block:: / doctest handling, which continues to work unchanged no matter how this flag is set.

Existing behavior for string-normalization, line-length, target-version, error-reporting, and skip-errors remains unchanged, both in the module and in its main entry point.

Overview

A Python package called blacken_docs is to be implemented. It reformats Python code that appears in documentation files (Markdown, reStructuredText, and LaTeX): the tool extracts the code blocks, runs the Black formatter over them, and leaves the prose around them untouched.

Package structure and public API

It must be possible to import the package as blacken_docs, and a blacken_docs.__main__ submodule must be exposed too (importing it must succeed).

blacken_docs.format_str
def format_str(src: str, black_mode: black.Mode) -> tuple[str, list]:
    ...
  • src: the whole text of a documentation source string.
  • black_mode: an instance of black.FileMode/black.Mode that governs the formatting (e.g. line length, string normalization, target versions).
  • The return value is a 2-tuple (new_contents, errors):
    • new_contents: the incoming text once every recognized Python code block has been reformatted.
    • errors: a list that collects the errors encountered (an empty list when there are none).

One further keyword-only argument is required, though passing it is optional:

def format_str(src, black_mode, *, rst_literal_blocks: bool = False) -> tuple[str, list]:
  • Passing rst_literal_blocks=True makes literal blocks of reStructuredText — the kind introduced by a paragraph ending in :: — count as Python code blocks too, so they are reformatted.
blacken_docs.main
def main(argv: Sequence[str] | None = None) -> int:
    ...
  • The function accepts a sequence of command-line arguments, made up of filenames and options.
  • Each file that is named gets read and reformatted in place; the result is written back only when changes are made.
  • The return value is falsy (0) if no file was modified and no errors were reported; it is truthy (nonzero) if an error was reported or any file was rewritten.
  • These options are supported:
    • --line-length N — handed through to Black's line length.
    • --target-version VER — it may be supplied multiple times; each occurrence adds one Black target version (e.g. py35, py36).
    • --skip-string-normalization — Black's string quote normalization is switched off by it.
    • --skip-errors — the tool does not fail on code blocks that cannot be parsed; the other blocks continue to be processed.
    • A filename may be placed before or after the option flags.

format_str behavior

Given the empty string as input, the function returns the empty string, unchanged.

Fenced code blocks in Markdown

A fenced block is recognized when its opening line consists of three backticks followed by a language tag:

  • A block tagged python is a Python block, and Black reformats its body.
  • A block tagged pycon is an interactive-console block (the pycon rules below apply).
  • Everything lying between the opening fence and the closing `` fence makes up the block body.

All of the following rules must hold:

  • Whitespace between the backticks and the language tag (e.g. ``` python) is permitted, and the output opening fence preserves it.
  • After the closing fence, trailing whitespace (e.g. ``` ) is preserved.
  • Fence options: whatever extra text follows the language tag on the opening fence line must be allowed and preserved verbatim. For example, an opening line of ```python title='example.py' is a valid Python block; the block body is reformatted and the opening line (including title='example.py') is emitted unchanged. The same applies to ```pycon title='Session 1'.
  • Support covers indented fenced blocks: if the opening fence carries indentation (e.g. by two spaces inside a list item), the reformatted body gets that indentation applied, and the fence lines preserve it.
LaTeX blocks
  • A \begin{minted}{python} … \end{minted} block gets reformatted as Python.
  • A \begin{minted}{pycon} … \end{minted} block gets reformatted as pycon (interactive console).
  • A \begin{pyblock} … \end{pyblock} (PythonTeX) block gets reformatted as Python.
  • The indentation found on the \begin/\end lines is preserved; the reformatted body is re-indented so that it matches the indentation of the \begin line. For minted blocks, extra body indentation beyond that is stripped away, which keeps the code's own indentation intact relative to the block.
reStructuredText blocks
  • For .. code-block:: python directives, the indented body is reformatted as Python. Option lines of the directive (e.g. :lineno-start: 10, :emphasize-lines: 11) that sit between the directive and the code must be preserved unchanged.
  • .. code-block:: pycon directives: these are reformatted as pycon.
  • For .. jupyter-execute:: directives, the indented body is reformatted as Python; the directive's options (e.g. :hide-code:) are preserved.
  • The Sphinx doctest directives — .. testsetup::, .. testcleanup::, .. testcode::, and .. doctest:: — get their indented bodies reformatted as Python (doctest bodies follow the pycon rules). Blank lines may be inserted by the reformatting where Black separates statements (e.g. an import followed by an assignment becomes separated by a blank line). The directive body's indentation is preserved.
  • Directives that are nested or indented work as well: when a directive sits indented inside another block, its body is reformatted and the correct indentation is preserved.
  • When a .. code-block:: python occurs only as text inside a non-Python code block (e.g. inside a .. code-block:: diff), it must NOT be reformatted — the outer block is left unchanged.
  • If rst_literal_blocks=True is in effect:
    • When a paragraph ending in :: is followed by a blank line and an indented block, the literal block it introduces is reformatted as Python.
    • A :: paragraph with no following indented literal content (e.g. another directive at lesser indentation coming immediately next) is left unchanged and produces no errors.
    • Nested constructs that are not actually literal Python blocks (e.g. a .. warning:: admonition) remain unchanged and produce no errors.
Python docstrings

Python source files go through the processing too: .. code-block:: python blocks of the reStructuredType kind and Markdown ```python blocks located within docstrings are reformatted in place, with the docstring's indentation preserved.

Handling of pycon (interactive console)

These rules cover pycon blocks (Markdown ```pycon, RST .. code-block:: pycon, doctest bodies, LaTeX minted/pycon):

  • Lines that begin with the >>> prompt (and ... continuation) carry Python statements; Black reformats them, and the reformatted code is emitted again with >>> / ... prompts.
  • When ... continuations are in play, a multi-line statement is reformatted as a unit and then re-wrapped with ... continuation prompts. Continuation lines are something Black may add or restructure (e.g. splitting a dict literal across multiple ... lines, adding a closing ... } line).
  • Should the final code in the block be a compound statement (e.g. if True: / def f(): pass), a trailing ... line is emitted after it when one is not already present.
  • Black expands nested one-line definitions such as def f(): pass onto multiple prompted lines.
  • Within a statement, empty continuation lines (a bare ... with no code) are handled: when the statement gets reformatted, they are collapsed appropriately.
  • Output lines — the non-prompt lines that follow a statement, e.g. output, tracebacks — are treated as console output and preserved verbatim, their indentation included. A Traceback (most recent call last): block is preserved unchanged, elided ... frames and file-location lines included.
  • Around the block, trailing whitespace and blank lines are preserved.
  • If the body of a block has no >>> prompt at all (nothing but plain indented text like pass), that block is left unchanged.
  • When a statement is not terminated by a newline (block ends immediately after >>> pass), it is reformatted and emitted with a trailing newline.
  • When a comment line precedes a >>> prompt, the comment line is preserved as-is.
  • In a Markdown pycon block, the body may be over-indented (e.g. four leading spaces before >>> ); after reformatting, the prompts are emitted flush to the fence indentation (leading over-indentation removed).

Details of main behavior

  • No changes needed: when a file is already formatted correctly, main leaves the file unchanged, writes nothing to stderr, and returns 0.
  • Changes made: once a file has been reformatted, "<path>: Rewriting...\n" is printed by main to stdout, the reformatted content is written to the file, and a truthy value is returned.
  • Line length: under --line-length=80, a long function call may be left unchanged (return 0); under --line-length=50, the same call gets wrapped across multiple lines and the file is rewritten (return truthy).
  • Target version: with --target-version=py36, reformatting a construct that is sensitive to trailing commas may add a magic trailing comma and rewrite the file; multiple --target-version flags accumulate.
  • String normalization: when --skip-string-normalization is given, strings quoted with single quotes (e.g. f('hi')) are left unchanged.
  • Syntax error (default): if a Python code block cannot be parsed, main returns truthy, leaves the file unchanged, and prints a message to stdout that starts with "<path>:<lineno>: code block parse error" (the line number is the line on which the code block opens).
  • Syntax error with --skip-errors: blocks that cannot be parsed get skipped (left unchanged), but the other, valid blocks in the same file are still reformatted; what gets written is the file with those valid blocks fixed.

Dependencies

For the actual code formatting, the black library must be used, and the passed black.Mode must be respected (line length, target versions, and string-normalization settings).

Symbols imported by tests (must exist)

  • The module blacken_docs, which provides format_str(src, black_mode, *, rst_literal_blocks=False) and main(argv).
  • The module blacken_docs.__main__ (one that can be imported).

Fenced code blocks in Markdown

Black must reformat the Python code sitting between the opening and closing fence. Everything besides that code must be preserved exactly, including:

  • The original content of the opening fence line, byte for byte. That means:
    • Whitespace sitting between the backticks and the language token (e.g. ``` python must stay as-is).
    • Language names in short form such as py (e.g. ``` py).
    • Any extra info-string options that come after the language (e.g. ```python title='example.py').
  • Trailing whitespace on the closing fence line (e.g. spaces that follow ``` must be kept).

Code blocks in reStructuredText

Python code that an rST directive introduces must be recognized as well. The directive looks like this:

.. code-block:: python

Black must reformat the Python code that follows the directive (an indented block), and the code must be re-indented to match the directive's code indentation. The directive line itself, together with the surrounding text, must be preserved.

Leading whitespace-only lines inside the code block must be preserved. To spell this out: when the line immediately after the directive line is one that contains only whitespace (for example three spaces), that line must be left intact in the output rather than being stripped or removed. The genuine code lines that come after it are reformatted normally, and their indentation is kept.

A concrete case: given this input

.. code-block:: python

(the second line there consists of three spaces, and the third line is indented by three spaces), what must come out is:

The whitespace-only line survives verbatim; the code line, meanwhile, is reformatted by Black and retains its three-space indentation.

Formatting Specifics

  • Black does the reformatting of the extracted Python code, working with the black_mode that was supplied.
  • Indented code blocks: the common indentation comes off before the code is handed to Black, and once formatting is done the original indentation is reapplied to each formatted line.
  • All structural markers (fences, directives, list markers, blank/whitespace lines outside the reformatted code), together with non-Python content, must be preserved exactly.

Additional Notes

  • As for the document as a whole, its trailing newline behavior must be preserved as in the input.
  • Code that is already correctly formatted must not be altered by the function (idempotent output for input that is already formatted).

Task: Add "on/off" comment support for skipping formatting in blacken-docs

Background

blacken_docs is a module that reformats Python code embedded in documentation files (Markdown, LaTeX, reStructuredText) by running Black on the code blocks embedded in them. The public entry point exercised in this task is:

blacken_docs.format_str(src: str, black_mode, *, rst_literal_blocks: bool = False) -> tuple[str, list]

It is given the full document source string and returns a 2-tuple of (formatted_source, errors).

You must add the ability to disable and re-enable formatting for regions of a document by means of special marker comments written in the host markup language's comment syntax.

Behavior that is required

Recognized marker comments that toggle formatting on and off must be introduced. Any code block whose opening delimiter lies inside a "disabled" region must be left completely unchanged (byte-for-byte identical in the output). Code blocks that sit outside disabled regions must continue to be formatted by Black exactly as before.

Marker syntax for each markup language

The markers consist of the text blacken-docs:off (which disables formatting) and blacken-docs:on (which re-enables it), embedded in a comment suited to the surrounding markup:

  • Markdown: HTML comments, i.e. <!-- blacken-docs:off --> and <!-- blacken-docs:on -->, each on a line of its own.
  • LaTeX (both minted and pythontex/pyblock blocks): line comments, i.e. % blacken-docs:off and % blacken-docs:on, each on a line of its own.
  • reStructuredText: comment directives, i.e. .. blacken-docs:off and .. blacken-docs:on, each on a line of its own.
Semantics of toggling
  • When an "off" marker is encountered, formatting is disabled from that point onward.
  • When an "on" marker is encountered, formatting is re-enabled from that point onward.
  • The state is toggled solely by these markers as they occur in document order:
    • An "on" marker encountered while formatting is already enabled has no effect (it is effectively ignored).
    • An "off" marker encountered while formatting is already disabled has no effect.
    • An "on" marker that appears before any "off" marker has no effect (formatting starts enabled).
    • If an "on" marker never follows an "off" marker, formatting remains disabled until the end of the document.
  • At the start of a document the default state is "enabled" (formatting active).

A code block is formatted only when formatting is enabled at the point where that block begins. When formatting is disabled, the block's contents are emitted verbatim.

The marker comment lines themselves are always preserved verbatim in the output, regardless of whether they had any effect.

Applicability to block types

The on/off behavior must apply to all code-block kinds that are currently handled, including:

  • Markdown Python code fences (```python) and Markdown pycon fences (```pycon).
  • minted environments in LaTeX, for python and for pycon.
  • pyblock environments from LaTeX pythontex.
  • reStructuredText directives code-block:: python and code-block:: pycon.
  • reStructuredText literal blocks (relevant for calls to format_str with rst_literal_blocks=True).
Nested or embedded fences

Marker comments and code fences appearing inside an outer, non-Python code fence (for example, a Python fence written inside an outer md ```` fenced block used for showing Markdown source) must not trigger formatting of the inner content. Nested content of this kind is already treated as inert; the presence of on/off markers inside it must not change that — the outer block as a whole is left unchanged.

Examples

A disabled region leaves the block untouched (Markdown):

<!-- blacken-docs:off -->
```python
'single quotes rock'

<!-- blacken-docs:on -->

→ output identical to input.

Disable then re-enable — only the second block is formatted:

Input:

<!-- blacken-docs:off -->

'single quotes rock'

<!-- blacken-docs:on -->

'double quotes rock'

Output: the first block's `'single quotes rock'` stays unchanged; the second block's `'double quotes rock'` comes out as `"double quotes rock"`.

An off marker with no matching on marker leaves everything after it unformatted through the end of the document.

Redundant/duplicate markers are ignored, as described in the toggling semantics above (e.g. a leading `on` before any `off` does nothing; a second consecutive `off` does nothing).

LaTeX and reStructuredText behave in an analogous way with their respective comment syntaxes.

## Constraints

- The public API signature of `blacken_docs.format_str` stays unchanged.
- Documents that contain no marker comments must behave exactly as before.
