Required public API

The top-level schema module must export:

from schema import Schema, Use, And, Or, Optional, SchemaExit

The required construction and invocation forms are:

Schema(rule).validate(value)
Use(converter)
And(first_rule, second_rule).validate(value)
Or(first_rule, second_rule).validate(value)
Optional(key_rule)

SchemaExit is the public exception raised when a value does not satisfy its rule or a required conversion cannot be performed. Successful validation returns the validated value, including any transformations performed by nested rules.

Objects produced by Use, And, and Or must themselves be accepted anywhere a Schema rule is accepted, including as collection element rules and dictionary key or value rules.

Core Schema rule semantics

Schema(rule).validate(data) interprets rule according to the following categories. These semantics apply recursively inside collection rules, dictionary rules, And, and Or.

Type rules

When rule is a Python type, validation is based on isinstance(data, rule). A matching value is returned unchanged; a non-matching value raises SchemaExit. Type rules validate and do not coerce.

For example:

Schema(int).validate(1)              # returns 1
Schema(str).validate('hai')          # returns 'hai'
Schema(list).validate(['a', 1])      # returns ['a', 1]
Schema(dict).validate({'a': 1})      # returns {'a': 1}

Schema(int) must reject '1' and the class object int, Schema(str) must reject 1, and Schema(dict) must reject a list. Likewise, a float rule accepts float instances but does not convert integers or strings to floats. Conversion belongs in Use.

Callable predicate rules

When a non-type callable is used directly as a rule, it is a predicate. It is called with the data:

  • If its result is truthy, validation returns the original data, not the predicate's return value.
  • If its result is falsy, validation raises SchemaExit.
  • If evaluating the predicate fails, validation raises SchemaExit.

For example:

Schema(lambda n: 0 < n < 5).validate(3)   # returns 3

The same rule rejects -1. Path predicates behave the same way: Schema(os.path.exists).validate('.') returns '.', while a nonexistent path is rejected.

Literal rules

A rule value that is not handled as a type, predicate, validator, mapping, or supported collection rule is matched by equality. Validation returns the data when data == rule and raises SchemaExit otherwise.

For example, Schema(1).validate(1) returns 1, while Schema(1).validate(9) raises SchemaExit.

List, tuple, set, and frozenset rules

A list, tuple, set, or frozenset used as a rule describes a homogeneous-style container whose members are alternatives; it does not describe fixed positions.

Validation must:

  1. Require the input to have the same exact container type as the rule (list with list, tuple with tuple, set with set, and frozenset with frozenset).
  2. Validate every input element against the disjunction of all elements in the rule container.
  3. Raise SchemaExit if any input element satisfies none of those alternatives.
  4. Return all successfully validated or transformed elements in the same container type as the input rule.

An empty input container is valid because it has no elements that fail validation. A nonempty input cannot satisfy an empty rule container.

Required examples include:

Schema([1, 0]).validate([1, 0, 1, 1])       # returns [1, 0, 1, 1]
Schema([1, 0]).validate([])                  # returns []
Schema([int]).validate([1, 2])               # returns [1, 2]
Schema({int}).validate({1, 2})               # returns {1, 2}
Schema((int,)).validate((1, 2))              # returns (1, 2)
Schema(frozenset([int])).validate(frozenset([1, 2]))

Schema([1, 0]) rejects the non-list value 0 and the list [2]. Schema([int]) rejects ['1', 2]. A set rule rejects list input even when all list elements would otherwise match, and a tuple rule likewise rejects list input.

Element transformations must be retained. For example, a list rule containing Use(int) converts each accepted element and returns a list containing those converted values.

Dictionary rules

When the rule is a dictionary, the input must be a dictionary. Each input key/value pair must match at least one entry in the rule dictionary: the input key must validate against that entry's key rule and its value must validate against the corresponding value rule. An input pair that matches no complete key/value rule is invalid, so unrecognized keys and invalid values raise SchemaExit.

Every schema key not wrapped in Optional is required. Validation succeeds only if each required schema key rule is matched by at least one input key/value pair. A key rule such as str may match multiple input keys, but it must match at least one when required.

The returned dictionary contains the validated or transformed keys and values. Thus rules may validate literal keys, general key types, or converting key validators.

Required examples include:

Schema({'key': 5}).validate({'key': 5})
# {'key': 5}

Schema({'key': int}).validate({'key': 5})
# {'key': 5}

Schema({'n': int, 'f': float}).validate({'n': 5, 'f': 3.14})
# {'n': 5, 'f': 3.14}

Schema({str: int}).validate({'a': 1, 'b': 2})
# {'a': 1, 'b': 2}

The first schema rejects {'key': 'x'}. {str: int} rejects a dictionary containing a non-string key. {'n': int, 'f': float} rejects {'n': 3.14, 'f': 5} because the values do not satisfy their corresponding type rules.

Key and value transformations are both preserved:

Schema({Use(str): Use(int)}).validate({1: 3.14, 3.14: 1})

returns:

{'1': 3, '3.14': 1}

Use

Use(converter) treats its callable as a converter rather than a truth predicate. It calls the converter with the current value and returns the converter's result. A normally returned result is the transformation result; it is not required to be truthy. If conversion fails, SchemaExit is raised.

Required behavior includes:

Schema(Use(int)).validate('1')   # returns 1
Schema(Use(str)).validate(1)     # returns '1'

Applying Use(int) to '3.33' raises SchemaExit.

File conversion must also work:

f = Schema(Use(file)).validate('LICENSE-MIT')

f is a readable file object whose contents begin with "Copyright". Converting the nonexistent path 'NON-EXISTENT' with Use(file) raises SchemaExit.

Use must work in nested collection rules and for both dictionary keys and dictionary values, with its converted output propagated into the enclosing result.

And

And(first_rule, second_rule) validates sequentially. The input is validated against first_rule, and the validated or transformed result of that step is then validated against second_rule. The final validated or transformed result is returned. If either step rejects its input, And.validate raises SchemaExit.

Each argument uses the same rule semantics as Schema, so types, literals, predicates, collection and dictionary rules, and validators such as Use can be composed.

Required behavior includes:

And(int, lambda n: 0 < n < 5).validate(3)
# 3

And(Use(int), lambda n: 0 < n < 5).validate(3.33)
# 3

And([1, 0], lambda values: len(values) > 2).validate([0, 1, 0])
# [0, 1, 0]

The first validator rejects 3.33; the second rejects '3.33' because it cannot be converted by int; and the collection validator rejects [0, 1] because it does not satisfy the length predicate.

And must compose inside larger schemas, including list element rules and dictionary value rules.

Or

Or(first_rule, second_rule) accepts the input if either rule validates it. Its alternatives use the same semantics as Schema. It returns the validated or transformed result from a successful alternative and raises SchemaExit if no alternative succeeds.

Required behavior includes:

Or(int, dict).validate(5)       # returns 5
Or(int, dict).validate({})      # returns {}

The same validator rejects 'hai' with SchemaExit.

Or must also be usable as a nested rule in Schema, including within collection and dictionary schemas.

Optional

Optional(key_rule) is a marker for a dictionary-schema key. It removes only the requirement that the key rule be represented in the input. If a matching key is present, the key and its corresponding value must still validate normally, and any transformations must be retained.

For:

Schema({'a': 1, Optional('b'): 2})

both of the following are valid and are returned unchanged:

{'a': 1}
{'a': 1, 'b': 2}

Without Optional, Schema({'a': 1, 'b': 2}) must reject {'a': 1} with SchemaExit.

Optional must work in larger schemas and with key names such as '--count'. For example:

import os

schema = Schema({
    '<file>': And([Use(file)], lambda values: len(values)),
    '<path>': os.path.exists,
    Optional('--count'): And(int, lambda n: 0 <= n <= 5),
})

data = schema.validate({
    '<file>': ['./LICENSE-MIT'],
    '<path>': './',
})

This input is valid without '--count'. The result has only the two supplied keys, keeps '<path>' as './', and contains one converted, readable file object in data['<file>']. If '--count' is supplied, its value must be an integer from 0 through 5 inclusive.

Goal

Implement a self-contained Python module named schema in schema.py at the repository root. It must provide a declarative API for validating and transforming Python values and nested data structures.

Public API

The following names must be importable directly from schema:

from schema import Schema, And, Or, Use, Optional, SchemaError, SchemaExit

The public validation methods return a validated, and possibly transformed, value on success. A validation failure raises the public validation exception described below.

Validation exceptions
  • SchemaError is the validation-failure exception required by the primary API.
  • SchemaExit is a compatibility exception name and must remain importable.
  • Every validation failure must be catchable as both SchemaError and SchemaExit. The names may be aliases, or the classes may use a compatible inheritance relationship, provided an exception raised by validation is caught through either API.
  • Exceptions raised while running a predicate or a Use conversion must be translated into this public validation-failure API rather than leaking as the original conversion or predicate exception.
Optional error argument

Schema, And, Or, and Use accept an optional error keyword argument where shown below. It defaults to None and allows a custom validation-error message to be supplied. Supplying it must not change successful validation or transformation results, and failed validation must still raise the public validation exception. No particular wording is required for failures when no custom message is supplied.

In particular:

s = Schema(Use(float), error='Should be a number.')
assert s.validate('1') == 1.0
# s.validate('hai') raises the public validation exception

Schema(schema, error=None)

Schema stores a rule and exposes validate(data). Rules can be nested recursively. The following rule categories are required.

Literal rules

A plain value used as a rule validates by equality. If data == rule, return data unchanged; otherwise raise the validation exception.

Schema(1).validate(1)       # returns 1
Schema(1).validate(9)       # fails
Schema({'key': 5}).validate({'key': 5})
Type rules are strict checks

A bare Python type is an instance-membership rule. Return the original input unchanged when isinstance(data, rule) is true; otherwise fail. A bare type must not be called as a converter, even though types are callable.

Schema(int).validate(1)         # returns 1
Schema(int).validate('1')       # fails
Schema(str).validate(1)         # fails
Schema(list).validate(['a', 1]) # returns the same list value
Schema(dict).validate({'a': 1}) # returns the same dict value

Conversion is explicit and is performed with Use, for example Schema(Use(int)).validate('1') == 1 and Schema(Use(str)).validate(1) == '1'. These strict type semantics apply equally inside And, container rules, dictionary keys, and dictionary values.

Predicate-callable rules

For a callable that is not being interpreted as a bare type or another validator object, call it with data:

  • If its result is truthy, validation succeeds and the original data is returned unchanged.
  • If its result is falsy, validation fails.
  • If it raises an exception, validation fails with the public validation exception.

Thus Schema(lambda n: 0 < n < 5).validate(3) returns 3, while the same rule rejects -1. Predicate return values are not transformations; use Use when the callable's returned value should replace the input.

Validator-object rules

Objects exposing a validate(data) method, including And, Or, and Use, may be used directly or nested as rules. Their successful return value becomes the validated value and therefore propagates through enclosing structures.

Sequence and set container rules

A schema whose outer value is a list, tuple, set, or frozenset describes a container with zero or more alternative element rules:

  1. The input must have the same outer container type as the schema. For example, a set rule rejects a list, and a tuple rule rejects a list.
  2. Every input element is independently validated against the member rules using any-of semantics, in the same manner as Or. It may match any one of the rules, and the first successful transformed result is used.
  3. If an element matches none of the member rules, validation fails.
  4. The result preserves the schema's outer container type and contains the validated/transformed elements.
  5. An empty input container is valid because it has no elements to reject. If the schema container itself has no member rules, only an empty input container can succeed.

Container rules are not positional tuple schemas. For example:

Schema([1, 0]).validate([1, 0, 1, 1])  # returns [1, 0, 1, 1]
Schema([1, 0]).validate([])             # returns []
Schema([1, 0]).validate([2])            # fails
Schema([1, 0]).validate(0)              # fails: not a list

Schema([int]).validate([1, 2])                  # succeeds
Schema([int]).validate(['1', 2])                # fails
Schema(set([int])).validate(set([1, 2]))        # returns set([1, 2])
Schema(set([int])).validate([1, 2])             # fails: not a set
Schema(tuple([int])).validate(tuple([1, 2]))    # returns tuple([1, 2])

The same rules apply to frozenset. Transformations also propagate through these containers; for example, [Use(open)] transforms every file-name element into the corresponding opened file object.

Dictionary rules

A dictionary rule requires dictionary input. Both schema keys and schema values are validation rules:

  • A schema key may be a literal, a type, a predicate or validator such as Use, or an Optional wrapper.
  • For each input key/value pair, validate the key against a schema key rule and the value against that same rule's associated value rule. A pair is accepted only when both validations succeed.
  • Every input pair must match a schema pair; unexpected keys or values that do not satisfy the corresponding value rule cause failure.
  • Every schema key rule not wrapped in Optional is required and must be matched at least once. For a literal key, this means that key must be present. For a general key rule such as str, at least one input pair must match it. Optional key rules may be unmatched.
  • The returned dictionary contains the validated results of both key and value validation. Consequently, transformations applied to keys and values must appear in the result.

Examples:

Schema({'key': int}).validate({'key': 5})
# {'key': 5}

Schema({'n': int, 'f': float}).validate({'n': 5, 'f': 3.14})
# {'n': 5, 'f': 3.14}

Schema({str: int}).validate({'a': 1, 'b': 2})
# {'a': 1, 'b': 2}

Schema({Use(str): Use(int)}).validate({1: 3.14, 3.14: 1})
# {'1': 3, '3.14': 1}

The strict type rule means {str: int} rejects a non-string key and rejects a value that is not an int. Nested transformations are recursive.

And(*schemas, error=None)

And performs conjunctive, sequential validation and exposes validate(data):

  1. Interpret each contained rule using normal Schema semantics.
  2. Validate in argument order.
  3. Feed each successful stage's output into the next stage.
  4. Return the final stage's output.
  5. If any stage fails, raise the public validation exception.

Examples:

And(int, lambda n: 0 < n < 5).validate(3)       # returns 3
And(int, lambda n: 0 < n < 5).validate(3.33)    # fails
And(Use(int), lambda n: 0 < n < 5).validate(3.33)  # returns 3
And(Use(int), lambda n: 0 < n < 5).validate('3.33') # fails

And([1, 0], lambda values: len(values) > 2).validate([0, 1, 0])
# returns [0, 1, 0]

Or(*schemas, error=None)

Or performs disjunctive validation and exposes validate(data):

  1. Interpret and try alternatives in argument order.
  2. Each alternative receives the input value for this Or operation.
  3. Return immediately with the first successful alternative's validated or transformed result.
  4. If every alternative fails, raise the public validation exception.
Or(int, dict).validate(5)      # returns 5
Or(int, dict).validate({})     # returns {}
Or(int, dict).validate('hai')  # fails

These are also the semantics used implicitly for the member rules in list, tuple, set, and frozenset schemas.

Use(callable_, error=None)

Use wraps a callable as a transformation:

  • Call callable_(data) and return its result as the validated value, regardless of whether that result would be truthy as a predicate.
  • If the callable raises an exception, raise the public validation exception instead.
  • The transformed result must propagate through And, containers, and dictionaries.

For example, Schema(Use(open)).validate('LICENSE-MIT') returns an opened file object, while applying it to 'NON-EXISTENT' fails with the public validation exception.

Optional(key)

Optional wraps a dictionary key rule and marks that rule as not required:

  • If no input key matches it, dictionary validation may still succeed.
  • If a matching key is present, both the wrapped key rule and its associated value rule must validate normally, including any transformations.
  • Optional changes only presence requirements; it does not bypass validation for a present entry.
Schema({'a': 1, 'b': 2}).validate({'a': 1})
# fails because b is required

Schema({'a': 1, Optional('b'): 2}).validate({'a': 1})
# returns {'a': 1}

Schema({'a': 1, Optional('b'): 2}).validate({'a': 1, 'b': 2})
# returns {'a': 1, 'b': 2}

Objective

Provide Pythonic schema validation with structured, inspectable validation errors while preserving the library's existing validation and conversion behavior. All APIs described below are exposed from the top-level schema module.

Public API

The module must expose:

  • SchemaExit
  • Schema(schema, error=None) and Schema.validate(data)
  • Use(callable, error=None) and Use.validate(data)
  • And(*schemas, error=None) and And.validate(data)
  • Or(*schemas, error=None) and Or.validate(data)
  • Optional(key_schema, error=None)

And, Or, Use, and other objects with a validate method may be used directly or nested anywhere a Schema rule is accepted.

Common validation contract

A successful validation returns the validated result:

  • Pure checking rules, such as type, literal, and predicate rules, return the input value.
  • Conversion rules return the converted value.
  • When Schema delegates to Use, And, Or, or any other validation-aware object, it must return that object's validate result, not the original input.
  • Conversions performed inside containers or dictionaries must be reflected recursively in the returned container.

Every validation rejection must raise SchemaExit, whether or not a custom error was supplied. This includes type and literal mismatches, false predicate results, wrong container kinds, invalid container elements, missing or extra dictionary entries, and failed alternatives.

SchemaExit

SchemaExit is the validation exception type and must retain its existing compatibility as a SystemExit subclass. It carries two ordered list attributes:

  • autos for automatically generated diagnostics
  • errors for caller-supplied diagnostics

It must support a generated diagnostic with an optional custom diagnostic. In particular, constructing it with two scalar diagnostics:

exc = SchemaExit('first auto', 'first error')

must make those diagnostics available as:

exc.autos == ['first auto']
exc.errors == ['first error']

A validation layer without a custom diagnostic is represented by None in errors. Diagnostics may accumulate as validation exceptions pass through surrounding validators. Their order is significant: diagnostics from the original failure precede entries contributed by an enclosing Use.

Schema rules

Types

When the schema is a type, validation uses normal isinstance semantics. The original data is returned if it is an instance and SchemaExit is raised otherwise. A type rule checks rather than converts:

Schema(int).validate(1)       # returns 1
Schema(int).validate('1')     # raises SchemaExit
Schema(Use(int)).validate('1')  # returns 1
Literals

A non-callable, non-container schema value is a literal rule. It succeeds when it compares equal to the data and returns the data; otherwise it raises SchemaExit.

Schema(1).validate(1)  # returns 1
Schema(1).validate(9)  # raises SchemaExit
Predicate callables

For a callable used directly as a schema rule, Schema.validate(data) invokes the callable with data:

  • A truthy return value accepts the data and returns the original data, rather than the callable's return value.
  • A falsy return value rejects the data with SchemaExit.
  • An exception raised while evaluating the predicate is reported as SchemaExit.

For example, Schema(lambda n: 0 < n < 5).validate(3) returns 3, while validating -1 raises SchemaExit. Types retain the type-checking behavior above even though types are callable; conversion must be requested explicitly with Use.

Validation-aware objects

If a schema object exposes a validate(data) method, Schema delegates to it. On success, the delegated return value is the result of Schema.validate. A SchemaExit from that validator denotes validation failure.

Sequence and set-like container schemas

A schema that is an actual list, tuple, set, or frozenset describes a homogeneous container with alternatives:

  • The input must use the corresponding container type; these container kinds are not interchangeable.
  • Every input element must validate against at least one rule contained in the schema container.
  • The alternatives are not positional. For example, [1, 0] allows each list element to be either 1 or 0.
  • The first successful alternative's returned value is used, so element conversions are retained.
  • The result has the same container type as the schema.
  • An empty input container is valid. A nonempty input cannot validate against an empty set of alternatives.

Examples:

Schema([1, 0]).validate([1, 0, 1, 1])       # [1, 0, 1, 1]
Schema([1, 0]).validate([])                  # []
Schema([int]).validate(['1', 2])             # raises SchemaExit
Schema((int,)).validate((1, 2))              # (1, 2)
Schema({int}).validate({1, 2})               # {1, 2}
Schema(frozenset({int})).validate(frozenset({1, 2}))

A list does not satisfy a tuple or set schema, and similarly for the other container kinds.

Dictionary schemas

A dictionary schema validates both keys and values:

  • The input must be a dictionary.
  • Each input key/value pair must match a schema key rule and that rule's associated value rule.
  • Schema keys may themselves be literals, types, Use conversions, predicates, or other supported rules.
  • Every non-optional schema key rule is required to have coverage.
  • Every input entry must match; unexpected or otherwise unmatched entries raise SchemaExit.
  • Missing required entries raise SchemaExit.
  • Successful key and value conversions are retained in a newly validated result dictionary.

Thus:

Schema({'key': int}).validate({'key': 5})
# {'key': 5}

Schema({str: int}).validate({'a': 1, 'b': 2})
# {'a': 1, 'b': 2}

Schema({Use(str): Use(int)}).validate({1: 3.14, 3.14: 1})

  • errors: the corresponding user-supplied messages, or None when that context has no custom message.

For example, Schema(1).validate(1) returns 1, while Schema(1).validate(9) fails.

Predicate callables

A callable used directly as a schema is a predicate. It is called with data:

  • If its result is truthy, validation succeeds and returns the original data, not the callable's result.
  • If its result is falsy, validation raises SchemaExit.
  • If it raises an ordinary exception exc, validation raises SchemaExit with an automatic diagnostic of the form "<name>(<repr(data)>) raised <repr(exc)>" and with this Schema object's error as the corresponding error entry.

When the schema itself is a list, tuple, set, or frozenset:

  1. The input must have the same corresponding container kind; a list rule does not accept a set or tuple, for example.
  2. Every input element is validated against the alternatives contained in the schema container. Each element must match at least one alternative; the alternatives are disjunctive, not positional.
  3. The successful result for each element, including any conversion, is placed into the returned container.
  4. The returned container has the same kind as the schema container. Empty input containers are valid because they have no invalid elements.

Examples:

assert Schema(tuple([int])).validate(tuple([1, 2])) == tuple([1, 2])

Schema({'a': 1, 'b': 2}).validate({'a': 1})       # raises SchemaExit

assert Schema({'a': 1, Optional('b'): 2}).validate(

assert Use(int).validate('1') == 1

Failure behavior depends on what the callable raises:

  • If it raises an ordinary exception exc, direct Use validation creates exactly one diagnostic pair. autos is ["<name>(<repr(data)>) raised <repr(exc)>"], and errors is [error]. There is no additional trailing None and the custom error is not duplicated.
  • If it raises SchemaExit, the existing accumulated entries are retained, then Use appends None to autos and its own error to errors.

Concretely:

    raise ValueError()

def se(_):
    raise SchemaExit('first auto', 'first error')

The resulting lists are:

  • Use(ve).validate('x'): autos == ["ve('x') raised ValueError()"], errors == [None].
  • Use(ve, error='msg').validate('x'): autos == ["ve('x') raised ValueError()"], errors == ['msg'].
  • Use(se).validate('x'): autos == ['first auto', None], errors == ['first error', None].
  • Use(se, error='msg').validate('x'): autos == ['first auto', None], errors == ['first error', 'msg'].

Any later pair in the ordinary-exception case must come from an enclosing validation context, not from the direct Use call.

And(*args, error=None)

And.validate(data) applies its arguments in order. Each successful stage's returned value is passed to the next stage, and the final stage's result is returned. This allows validation and conversion to be composed:

assert And(int, lambda n: 0 < n < 5).validate(3) == 3
assert And(Use(int), lambda n: 0 < n < 5).validate(3.33) == 3

A stage that fails stops processing and propagates SchemaExit. And does not add an And(...) did not validate ... automatic summary. Using the ve and se functions above:

  • And(ve).validate('x') produces autos == ["ve('x') raised ValueError()"] and errors == [None].
  • And(ve, error='msg').validate('x') produces autos == ["ve('x') raised ValueError()"] and errors == ['msg'].
  • And(str, se).validate('x') produces autos == ['first auto', None] and errors == ['first error', None].
  • And(str, se, error='msg').validate('x') produces autos == ['first auto', None] and errors == ['first error', 'msg'].

Or(*args, error=None)

Or.validate(data) tries its arguments in order against the same input. It returns the first successful alternative's validated or converted result. If every alternative fails, the final SchemaExit retains the accumulated diagnostics from the last attempted alternative and then appends one overall summary pair:

  • The added automatic entry is "Or(<args...>) did not validate <repr(data)>", using the validator's normal representation.
  • The corresponding error entry is this Or object's error.

Earlier failed alternatives do not replace the last failure details, and no failure is raised if a later alternative succeeds. For example, Or(int, dict) returns 5 for 5, returns {} for {}, and fails for 'hai'.

For total failures:

  • If ve raises ValueError() on 'x', Or(ve) has first auto "ve('x') raised ValueError()", followed by an auto that starts with "Or(" and ends with ") did not validate 'x'"; errors == [None, None].
  • Or(ve, error='msg') has the same two autos and errors == ['msg', 'msg']: the error is associated with both the failed alternative's validation and the final Or summary.
  • Or('o').validate('x') produces autos == ["'o' does not match 'x'", "Or('o') did not validate 'x'"] and errors == [None, None].
  • Or('o', error='msg').validate('x') produces those same autos and errors == ['msg', 'msg'].

Outer Schema Accumulation Examples

An enclosing Schema around another validator adds its own context pair only after the inner failure has accumulated its entries. With the functions above:

  • Schema(Use(ve)).validate('x') produces autos == ["ve('x') raised ValueError()", None] and errors == [None, None].
  • Schema(Use(ve), error='msg').validate('x') produces autos == ["ve('x') raised ValueError()", None] and errors == [None, 'msg'].
  • Schema(Use(se)).validate('x') produces autos == ['first auto', None, None] and errors == ['first error', None, None].
  • Schema(Use(se), error='msg').validate('x') produces autos == ['first auto', None, None] and errors == ['first error', None, 'msg'].

A direct failure generated by Schema itself has one pair. For example, a type mismatch from Schema(int, error='should be integer') has errors == ['should be integer'].

Accumulation Summary

  • A direct ordinary-exception failure in Use creates one automatic/error pair.
  • Use receiving an existing SchemaExit appends [None, Use.error].
  • Schema receiving an existing SchemaExit from a delegated validator or schema callable appends [None, Schema.error].
  • And is sequential and adds no overall automatic summary; its error is associated with the failing stage as illustrated above.
  • A totally failing Or retains the last alternative's details and appends [Or summary, Or.error].
  • Direct type, literal, predicate, container, and dictionary failures create or propagate SchemaExit even when their custom error is None.

At no point may an outer validator discard or overwrite diagnostics already accumulated by an inner failure.

SchemaError

SchemaError is the validation-failure exception. Its constructor is:

Each argument may be either a single value or a list. A non-list value is wrapped in a one-element list; a list is retained as a list. The exception exposes:

  • errors: user-supplied diagnostic entries, including any None placeholders;

caught.autos  -> [new_auto]  + caught.autos
