Task Description

Public API that is required

The schema module at the top level must export the following:

from schema import Schema, Use, And, Or, Optional, SchemaExit

The following are the required forms for construction and invocation:

Schema(rule).validate(value)
Use(converter)
And(first_rule, second_rule).validate(value)
Or(first_rule, second_rule).validate(value)
Optional(key_rule)

SchemaExit is the public exception that gets raised when a value does not satisfy its rule or when a required conversion cannot be performed. Validation that succeeds returns the validated value, including any transformations that nested rules performed.

Objects that Use, And, and Or produce must themselves be accepted anywhere a Schema rule is accepted, including as collection element rules and as dictionary key or value rules.

Core semantics for Schema rules

In Schema(rule).validate(data), the rule is interpreted according to the categories that follow. Inside collection rules, dictionary rules, And, and Or, these semantics apply recursively.

Rules based on types

If rule is a Python type, validation relies on isinstance(data, rule). A value that matches is returned unchanged; a value that does not match raises SchemaExit. Type rules validate; they do not coerce.

For example:

Schema(int).validate(1)              # returns 1
Schema(str).validate('hai')          # returns 'hai'
Schema(list).validate(['a', 1])      # returns ['a', 1]
Schema(dict).validate({'a': 1})      # returns {'a': 1}

Schema(int) must reject both '1' and the class object int; Schema(str) must reject 1; and Schema(dict) must reject a list. In the same way, a float rule accepts float instances but does not convert integers or strings into floats. Conversions belong in Use.

Rules that are callable predicates

When a callable that is not a type is used directly as a rule, it serves as a predicate. The predicate is called with the data:

  • If its result is truthy, validation returns the original data rather than the predicate's return value.
  • When its result is falsy, validation raises SchemaExit.
  • Should evaluating the predicate fail, validation raises SchemaExit.

For example:

Schema(lambda n: 0 < n < 5).validate(3)   # returns 3

That same rule rejects -1. Predicates that involve paths behave the same way: Schema(os.path.exists).validate('.') returns '.', whereas a nonexistent path is rejected.

Rules that are literals

A rule value that is not handled as a type, predicate, validator, mapping, or supported collection rule gets matched through equality. Validation returns the data in the case that data == rule, and raises SchemaExit in the opposite case.

As an example, Schema(1).validate(1) returns 1, whereas Schema(1).validate(9) raises SchemaExit.

Rules for list, tuple, set, and frozenset

A list, tuple, set, or frozenset employed as a rule describes a homogeneous-style container whose members are alternatives; it does not describe fixed positions.

Validation must do the following:

  1. Require the input to be of the same exact container type as the rule (list with list, tuple with tuple, set with set, and frozenset with frozenset).
  2. Validate every input element against the disjunction of all elements that the rule container holds.
  3. Raise SchemaExit when any input element satisfies none of those alternatives.
  4. Return all elements that were successfully validated or transformed, in the same container type as the input rule.

An input container that is empty is valid, since it has no elements that fail validation. A nonempty input cannot satisfy a rule container that is empty.

Examples that are required include:

Schema([1, 0]).validate([1, 0, 1, 1])       # returns [1, 0, 1, 1]
Schema([1, 0]).validate([])                  # returns []
Schema([int]).validate([1, 2])               # returns [1, 2]
Schema({int}).validate({1, 2})               # returns {1, 2}
Schema((int,)).validate((1, 2))              # returns (1, 2)
Schema(frozenset([int])).validate(frozenset([1, 2]))

The value 0, which is not a list, is rejected by Schema([1, 0]), as is the list [2]. Schema([int]) rejects ['1', 2]. A set rule rejects list input even when all of the list elements would otherwise match, and a tuple rule likewise rejects list input.

Transformations of elements must be retained. For instance, a list rule that contains Use(int) converts each accepted element and returns a list holding those converted values.

Rules for dictionaries

If the rule is a dictionary, the input must be a dictionary as well. Each input key/value pair must match at least one entry of the rule dictionary: the input key must validate against that entry's key rule, and its value must validate against the corresponding value rule. An input pair that matches no complete key/value rule is invalid; unrecognized keys and invalid values therefore raise SchemaExit.

Every schema key that is not wrapped in Optional is required. Only if each required schema key rule is matched by at least one input key/value pair does validation succeed. A key rule such as str may match multiple input keys, but when required it must match at least one.

The dictionary that is returned contains the validated or transformed keys and values. Rules may thus validate literal keys, general key types, or converting key validators.

Examples that are required include:

Schema({'key': 5}).validate({'key': 5})
# {'key': 5}

Schema({'key': int}).validate({'key': 5})
# {'key': 5}

Schema({'n': int, 'f': float}).validate({'n': 5, 'f': 3.14})
# {'n': 5, 'f': 3.14}

Schema({str: int}).validate({'a': 1, 'b': 2})
# {'a': 1, 'b': 2}

{'key': 'x'} is rejected by the first schema. {str: int} rejects a dictionary that contains a non-string key. {'n': int, 'f': float} rejects {'n': 3.14, 'f': 5}, since the values do not satisfy their corresponding type rules.

Both key and value transformations are preserved:

Schema({Use(str): Use(int)}).validate({1: 3.14, 3.14: 1})

The call returns:

{'1': 3, '3.14': 1}

Use

Use(converter) treats the callable passed to it as a converter rather than a truth predicate. It calls the converter with the current value and returns the result the converter produces. A result that is returned normally is the transformation result; it is not required to be truthy. When conversion fails, SchemaExit is raised.

Behavior that is required includes:

Schema(Use(int)).validate('1')   # returns 1
Schema(Use(str)).validate(1)     # returns '1'

When Use(int) is applied to '3.33', SchemaExit is raised.

Conversion of files must also work:

f = Schema(Use(file)).validate('LICENSE-MIT')

The value f is a readable file object whose contents begin with "Copyright". Converting the nonexistent path 'NON-EXISTENT' by means of Use(file) raises SchemaExit.

Use must work in nested collection rules and also for both dictionary keys and dictionary values, with its converted output propagated into the result that encloses it.

And

And(first_rule, second_rule) performs validation sequentially. The input is validated against first_rule, after which the validated or transformed result of that step is validated against second_rule. What is returned is the final validated or transformed result. When either step rejects its input, And.validate raises SchemaExit.

Each argument is governed by the same rule semantics as Schema, meaning types, literals, predicates, collection and dictionary rules, and validators such as Use can be composed.

Behavior that is required includes:

And(int, lambda n: 0 < n < 5).validate(3)
# 3

And(Use(int), lambda n: 0 < n < 5).validate(3.33)
# 3

And([1, 0], lambda values: len(values) > 2).validate([0, 1, 0])
# [0, 1, 0]

The first validator rejects 3.33; the second rejects '3.33', since int cannot convert it; and the collection validator rejects [0, 1], since that input does not satisfy the length predicate.

And must be usable in composition inside larger schemas, including as list element rules and dictionary value rules.

Or

Or(first_rule, second_rule) accepts the input when either of the two rules validates it. The alternatives it contains use the same semantics as Schema. It returns the validated or transformed result from a successful alternative, and it raises SchemaExit if no alternative succeeds.

Behavior that is required includes:

Or(int, dict).validate(5)       # returns 5
Or(int, dict).validate({})      # returns {}

That same validator rejects 'hai' with SchemaExit.

Or must also be usable as a nested rule inside Schema, including within collection and dictionary schemas.

Optional

Optional(key_rule) acts as a marker for a key of a dictionary schema. The only requirement it removes is that the key rule be represented in the input. When a matching key is present, the key and its corresponding value must still validate normally, and any transformations must be retained.

Given:

Schema({'a': 1, Optional('b'): 2})

both of the following inputs are valid and are returned unchanged:

{'a': 1}
{'a': 1, 'b': 2}

If Optional is not used, Schema({'a': 1, 'b': 2}) must reject {'a': 1} with SchemaExit.

Optional must work in larger schemas and with key names such as '--count'. As an example:

import os

schema = Schema({
    '<file>': And([Use(file)], lambda values: len(values)),
    '<path>': os.path.exists,
    Optional('--count'): And(int, lambda n: 0 <= n <= 5),
})

data = schema.validate({
    '<file>': ['./LICENSE-MIT'],
    '<path>': './',
})

The input is valid without '--count' being present. The result contains only the two keys that were supplied, keeps '<path>' as './', and holds one converted, readable file object in data['<file>']. Should '--count' be supplied, its value must be an integer from 0 through 5 inclusive.

Objective

Implement a self-contained Python module named schema in schema.py at the repository root. It must provide a declarative API for validating and transforming Python values and nested data structures.

Public interface

These names must be importable directly from schema:

from schema import Schema, And, Or, Use, Optional, SchemaError, SchemaExit

On success, the public validation methods return a validated, and possibly transformed, value. A failure of validation raises the public validation exception described below.

Exceptions for validation failures
  • SchemaError is the exception the primary API requires for validation failures.
  • SchemaExit is an exception name kept for compatibility and must remain importable.
  • Every validation failure must be catchable as both SchemaError and SchemaExit. The two names may be aliases, or the classes may stand in a compatible inheritance relationship, as long as an exception raised by validation is caught through either API.
  • If an exception is raised while a predicate or a Use conversion is running, it must be translated into this public validation-failure API instead of leaking out as the original conversion or predicate exception.
The optional error argument

Where shown below, Schema, And, Or, and Use accept an optional error keyword argument. It defaults to None and allows a custom validation-error message to be supplied. Passing it must not change the results of successful validation or transformation, and failed validation must still raise the public validation exception. When no custom message is supplied, no particular wording is required for failures.

Specifically:

s = Schema(Use(float), error='Should be a number.')
assert s.validate('1') == 1.0
# s.validate('hai') raises the public validation exception

Schema(schema, error=None)

Schema stores a rule and exposes validate(data). Rules can be nested inside one another recursively. The rule categories below are required.

Rules given as literal values

A plain value that serves as a rule validates by equality. When data == rule, return data unchanged; in every other case, raise the validation exception.

Schema(1).validate(1)       # returns 1
Schema(1).validate(9)       # fails
Schema({'key': 5}).validate({'key': 5})
Type rules act as strict checks

A bare Python type serves as an instance-membership rule. When isinstance(data, rule) is true, return the original input unchanged; in any other case, fail. Even though types are callable, a bare type must not be called as a converter.

Schema(int).validate(1)         # returns 1
Schema(int).validate('1')       # fails
Schema(str).validate(1)         # fails
Schema(list).validate(['a', 1]) # returns the same list value
Schema(dict).validate({'a': 1}) # returns the same dict value

Conversion is explicit and is performed with Use, for example Schema(Use(int)).validate('1') == 1 and Schema(Use(str)).validate(1) == '1'. These strict type semantics apply equally within And, container rules, dictionary keys, and dictionary values.

Rules that are predicate callables

If a callable is not being interpreted as a bare type or as another validator object, call it with data:

  • A truthy result means validation succeeds and the original data is returned unchanged.
  • A falsy result means validation fails.
  • An exception raised by the callable means validation fails with the public validation exception.

Consequently, Schema(lambda n: 0 < n < 5).validate(3) returns 3, while the same rule rejects -1. Values returned by predicates are not transformations; use Use when the callable's returned value should replace the input.

Rules that are validator objects

Objects that expose a validate(data) method, with And, Or, and Use among them, may be used directly or nested as rules. The value such an object returns on success becomes the validated value and therefore propagates through the enclosing structures.

Container rules for sequences and sets

A schema whose outer value is a list, tuple, set, or frozenset describes a container holding zero or more alternative element rules:

  1. The input's outer container type must be the same as the schema's. For instance, a set rule rejects a list, and a tuple rule rejects a list.
  2. Every input element is validated independently against the member rules with any-of semantics, in the same way as Or. It may match any single one of the rules, and the first successful transformed result is the one used.
  3. When an element matches none of the member rules, validation fails.
  4. The result keeps the schema's outer container type and contains the validated/transformed elements.
  5. An empty input container is valid, since it has no elements to reject. If the schema container itself has no member rules, only an empty input container can succeed.

These container rules are not positional tuple schemas. For example:

Schema([1, 0]).validate([1, 0, 1, 1])  # returns [1, 0, 1, 1]
Schema([1, 0]).validate([])             # returns []
Schema([1, 0]).validate([2])            # fails
Schema([1, 0]).validate(0)              # fails: not a list

Schema([int]).validate([1, 2])                  # succeeds
Schema([int]).validate(['1', 2])                # fails
Schema(set([int])).validate(set([1, 2]))        # returns set([1, 2])
Schema(set([int])).validate([1, 2])             # fails: not a set
Schema(tuple([int])).validate(tuple([1, 2]))    # returns tuple([1, 2])

The identical rules apply to frozenset. Transformations propagate through these containers as well; for example, [Use(open)] transforms every file-name element into the corresponding opened file object.

Rules for dictionaries

A dictionary rule requires the input to be a dictionary. Schema keys and schema values alike act as validation rules:

  • A schema key may be a literal, a type, a predicate or validator (for instance Use), or an Optional wrapper.
  • For each input key/value pair, the key is validated against a schema key rule and the value against that same rule's associated value rule. A pair is accepted only when both validations succeed.
  • Every input pair must match a schema pair; keys that are unexpected, or values that do not satisfy the corresponding value rule, cause failure.
  • Every schema key rule that is not wrapped in Optional is required and must be matched at least once. For a literal key, this means the key itself must be present. For a general key rule like str, at least one input pair must match it. Key rules wrapped in Optional may go unmatched.
  • The returned dictionary holds the validated results of both key and value validation. As a consequence, transformations applied to keys and values must appear in the result.

Examples:

Schema({'key': int}).validate({'key': 5})
# {'key': 5}

Schema({'n': int, 'f': float}).validate({'n': 5, 'f': 3.14})
# {'n': 5, 'f': 3.14}

Schema({str: int}).validate({'a': 1, 'b': 2})
# {'a': 1, 'b': 2}

Schema({Use(str): Use(int)}).validate({1: 3.14, 3.14: 1})
# {'1': 3, '3.14': 1}

Under the strict type rule, {str: int} rejects a non-string key and rejects a value that is not an int. Nested transformations apply recursively.

And(*schemas, error=None)

And performs conjunctive validation, in sequence, and exposes validate(data):

  1. Interpret each contained rule according to normal Schema semantics.
  2. Validate the rules in argument order.
  3. Pass each successful stage's output on as the input to the next stage.
  4. Return the output of the final stage.
  5. When any stage fails, raise the public validation exception.

Examples:

And(int, lambda n: 0 < n < 5).validate(3)       # returns 3
And(int, lambda n: 0 < n < 5).validate(3.33)    # fails
And(Use(int), lambda n: 0 < n < 5).validate(3.33)  # returns 3
And(Use(int), lambda n: 0 < n < 5).validate('3.33') # fails

And([1, 0], lambda values: len(values) > 2).validate([0, 1, 0])
# returns [0, 1, 0]

And([Use(open)], lambda values: len(values)) first validates and transforms all list elements and then requires the transformed list to be nonempty. And(int, lambda n: 0 <= n <= 5) applies a strict integer check followed by the bounds predicate.

Or(*schemas, error=None)

Or performs disjunctive validation and exposes validate(data):

  1. Interpret the alternatives and try them in argument order.
  2. Each alternative is given the input value for this Or operation.
  3. Return immediately, with the validated or transformed result of the first alternative that succeeds.
  4. When every alternative fails, raise the public validation exception.
Or(int, dict).validate(5)      # returns 5
Or(int, dict).validate({})     # returns {}
Or(int, dict).validate('hai')  # fails

The member rules in list, tuple, set, and frozenset schemas implicitly use these same semantics.

Use(callable_, error=None)

Use wraps a callable so it acts as a transformation:

  • Call callable_(data) and return its result as the validated value, no matter whether that result would be truthy as a predicate.
  • If the callable raises an exception, raise the public validation exception in its place.
  • The result of the transformation must propagate through And, containers, and dictionaries.

For instance, Schema(Use(open)).validate('LICENSE-MIT') returns an opened file object, whereas applying it to 'NON-EXISTENT' fails with the public validation exception.

Optional(key)

Optional wraps a dictionary key rule and marks that key rule as not required:

  • When no input key matches it, dictionary validation may nevertheless succeed.
  • When a matching key is present, both the wrapped key rule and its associated value rule must validate normally, transformations included.
  • Optional alters presence requirements only; it does not skip validation of an entry that is present.
Schema({'a': 1, 'b': 2}).validate({'a': 1})
# fails because b is required

Schema({'a': 1, Optional('b'): 2}).validate({'a': 1})
# returns {'a': 1}

Schema({'a': 1, Optional('b'): 2}).validate({'a': 1, 'b': 2})
# returns {'a': 1, 'b': 2}

  • Schema(Use(open)).validate('LICENSE-MIT') returns a readable opened file whose content starts with 'Copyright'.
  • Schema(Use(open)).validate('NON-EXISTENT') fails through the public validation exception.

  • Transformations produced by Use, And, and Or during validation must survive at every level of nested list, tuple, set, frozenset, and dictionary structures.

Objective

Deliver Pythonic schema validation with validation errors that are structured and inspectable, while the library's existing validation and conversion behavior is preserved. Every API described below is exposed from the top-level schema module.

Public API

The following must be exposed by the module:

  • SchemaExit
  • Schema(schema, error=None) and Schema.validate(data)
  • Use(callable, error=None) and Use.validate(data)
  • And(*schemas, error=None) and And.validate(data)
  • Or(*schemas, error=None) and Or.validate(data)
  • Optional(key_schema, error=None)

Objects with a validate method — including And, Or, and Use — may be used directly or nested anywhere a Schema rule is accepted.

Common validation contract

Validation that succeeds returns the validated result:

  • Rules that do pure checking, such as type, literal, and predicate rules, return the input value.
  • Rules that convert return the converted value.
  • If Schema delegates to Use, And, Or, or any other validation-aware object, it must return the result of that object's validate, not the original input.
  • Conversions carried out inside containers or dictionaries must be reflected recursively in the container that is returned.

Each validation rejection must raise SchemaExit, whether or not a custom error was supplied. Such rejections include type and literal mismatches, false predicate results, wrong container kinds, invalid container elements, missing or extra dictionary entries, and failed alternatives.

SchemaExit

SchemaExit serves as the validation exception type and must keep its existing compatibility as a SystemExit subclass. It has two attributes, each an ordered list:

  • autos holding automatically generated diagnostics
  • errors holding caller-supplied diagnostics

It must support a generated diagnostic together with an optional custom diagnostic. Specifically, when it is constructed with two scalar diagnostics:

exc = SchemaExit('first auto', 'first error')

those diagnostics must be made available as:

exc.autos == ['first auto']
exc.errors == ['first error']

None in errors represents a validation layer that has no custom diagnostic. As validation exceptions pass through surrounding validators, diagnostics may accumulate. Their order matters: the diagnostics from the original failure precede the entries contributed by an enclosing Use.

Schema rules

Types

If the schema is a type, validation follows ordinary isinstance semantics. The original data is returned when it is an instance; otherwise SchemaExit is raised. A type rule performs a check rather than a conversion:

Schema(int).validate(1)       # returns 1
Schema(int).validate('1')     # raises SchemaExit
Schema(Use(int)).validate('1')  # returns 1
Literals

A schema value that is neither callable nor a container constitutes a literal rule. It succeeds when it compares equal to the data and returns the data; otherwise SchemaExit is raised.

Schema(1).validate(1)  # returns 1
Schema(1).validate(9)  # raises SchemaExit
Predicate callables

When a callable is used directly as a schema rule, Schema.validate(data) invokes the callable with data:

  • If the return value is truthy, the data is accepted and the original data is returned — not the callable's return value.
  • If the return value is falsy, the data is rejected with SchemaExit.
  • Any exception raised while evaluating the predicate is reported as SchemaExit.

To illustrate, Schema(lambda n: 0 < n < 5).validate(3) returns 3, whereas validating -1 raises SchemaExit. Even though types are callable, they retain the type-checking behavior described above; conversion must be requested explicitly with Use.

Validation-aware objects

When a schema object exposes a validate(data) method, Schema delegates to it. If validation succeeds, the value returned by the delegation is the result of Schema.validate. A SchemaExit coming from that validator signals validation failure.

Sequence and set-like container schemas

A schema that is an actual list, tuple, set, or frozenset specifies a homogeneous container with alternatives:

  • The input must be of the corresponding container type; these container kinds are not interchangeable.
  • Each element of the input must validate against at least one rule contained in the schema container.
  • Which alternative matches does not depend on position. For example, [1, 0] allows each list element to be either 1 or 0.
  • The value returned by the first alternative that succeeds is used, so element conversions are retained.
  • The container type of the result is the same as the schema's.
  • An input container that is empty is valid. When the set of alternatives is empty, a nonempty input cannot validate against it.

Examples:

Schema([1, 0]).validate([1, 0, 1, 1])       # [1, 0, 1, 1]
Schema([1, 0]).validate([])                  # []
Schema([int]).validate(['1', 2])             # raises SchemaExit

Schema({int}).validate({1, 2})               # {1, 2}
Schema(frozenset({int})).validate(frozenset({1, 2}))

A list will not satisfy a tuple schema or a set schema, and the same applies to the other container kinds.

Dictionary schemas

With a dictionary schema, both keys and values are validated:

  • The input is required to be a dictionary.
  • Each key/value pair in the input must match a schema key rule together with that rule's associated value rule.
  • The keys in a schema may themselves be literals, types, Use conversions, predicates, or other supported rules.
  • Every schema key rule that is not optional is required to have coverage.
  • Every entry of the input must match; entries that are unexpected or otherwise unmatched raise SchemaExit.
  • Required entries that are missing raise SchemaExit.
  • Key and value conversions that succeed are retained in a newly validated result dictionary.

To illustrate:

  4. The container given back has the same kind as the schema container. Because they contain no invalid elements, empty input containers are valid.

  • The automatic entry added is "Or(<args...>) did not validate <repr(data)>", based on the validator's normal representation.
  • This Or object's error is the matching error entry.

  • If ve raises ValueError() on 'x', then Or(ve) has as its first auto "ve('x') raised ValueError()", followed by an auto that starts with "Or(" and ends with ") did not validate 'x'"; errors == [None, None].
  • Or(ve, error='msg') has the same two autos and errors == ['msg', 'msg']; the error is tied to both the failed alternative's validation and the final Or summary.
  • Or('o').validate('x') gives autos == ["'o' does not match 'x'", "Or('o') did not validate 'x'"] and errors == [None, None].
  • Or('o', error='msg').validate('x') gives those same autos and errors == ['msg', 'msg'].

  • Schema(Use(ve)).validate('x') gives autos == ["ve('x') raised ValueError()", None] and errors == [None, None].
  • Schema(Use(ve), error='msg').validate('x') gives autos == ["ve('x') raised ValueError()", None] and errors == [None, 'msg'].
  • Schema(Use(se)).validate('x') gives autos == ['first auto', None, None] and errors == ['first error', None, None].
  • Schema(Use(se), error='msg').validate('x') gives autos == ['first auto', None, None] and errors == ['first error', None, 'msg'].

A failure that Schema itself generates directly consists of one pair. For instance, with the type mismatch from Schema(int, error='should be integer'), errors == ['should be integer'].

  • A direct failure from an ordinary exception inside Use creates one automatic/error pair.
  • When Use receives an existing SchemaExit, it appends [None, Use.error].
  • When Schema receives an existing SchemaExit from a delegated validator or a schema callable, it appends [None, Schema.error].
  • And works sequentially and adds no overall automatic summary; as illustrated above, its error is associated with the failing stage.
  • An Or that fails totally retains the last alternative's details and appends [Or summary, Or.error].
  • Direct type, literal, predicate, container, and dictionary failures create or propagate SchemaExit even with a custom error of None.

Overview

The schema library is the codebase you are working on. It provides a Schema class (importable as from schema import Schema) that is used to validate data structures.

With the Schema class, iterable container types (such as list, tuple, set, and frozenset) can be validated against a schema that is itself an iterable holding element schemas. To illustrate, Schema(set([str])) describes "a set whose every element validates against str".

Required Behavior Change

When iterable data is validated, the value that Schema.validate returns must preserve the exact type of the input data, not merely the general category of the schema container.

In particular:

  • When a Schema has been constructed from an iterable container (e.g. Schema(set([str]))), calling .validate(data) on matching input data must return an object of the same type as data.
  • The same must hold when data is an instance of a subclass of the built-in container type. If data is an instance of a user-defined subclass of set, the result of the validation must be an instance of that same subclass (and therefore also an instance of set).

In concrete terms:

  • Suppose MySet is a subclass of set.
  • Define data = MySet(["test", "strings"]).
  • Define s = Schema(set([str])).
  • Then s.validate(data) must return an object for which isinstance(..., MySet) is True.

Put differently, what determines the return type of iterable validation is the type of the input data, not the type of the schema's container.

Constraints
  • The existing semantics for iterable validation (each element of the input must validate against the element schema) must keep working.
  • The validated elements of the input must be contained in the result.
  • There is no change to public API names or signatures: the Schema class and its validate method keep their existing interface.
