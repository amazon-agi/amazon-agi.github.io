Task: Implement build_tuple() on CoreContext

Overview

Add a new method build_tuple to the CoreContext class (importable as from core_context import CoreContext, matching the existing module structure used by the other CoreContext methods). This method resolves a set of named components from the context and yields them together as a tuple.

Existing context (assumed to already exist)

The CoreContext class already supports:

  • add_instances(mapping) — registers pre-built named values from a dict of {name: value}.
  • add_factories(mapping) — registers named factory callables from a dict of {name: factory}. A factory is a callable whose parameter names refer to other registered component names; when a factory is resolved, each of its parameters is resolved from the context and passed in by name, and the factory's return value becomes the resolved value for that name.
  • A context-manager-based build API (methods that return a context manager yielding the resolved value(s)).

Required behavior of build_tuple

Signature / calling conventions

build_tuple must accept the names to resolve in either of two forms:

  1. A single iterable argument — a tuple (or list) of name strings:

    context.build_tuple(("prefix", "suffix", "text"))

  2. Multiple positional string arguments — each name passed separately:

    context.build_tuple("prefix", "suffix", "text")

Both forms must produce identical results.

Return value

build_tuple must return a context manager (usable in a with statement). Entering the context yields a single tuple containing the resolved value for each requested name, in the same order as the names were given.

with context.build_tuple(("prefix", "suffix", "text")) as instance_tuple:
    # instance_tuple == ("abc", "def", "abcdef")

Because a tuple is yielded, callers may unpack it directly:

with context.build_tuple("prefix", "suffix", "text") as (prefix, suffix, text):
    # prefix == "abc", suffix == "def", text == "abcdef"
Resolution semantics
  • Each name is resolved from the context: names registered as instances yield their stored value; names registered as factories yield the result of invoking the factory (with its parameters resolved from the context by name).
  • The order of values in the yielded tuple exactly matches the order of the names as supplied.
  • Resolution of the requested names must occur in the order the names are supplied. (When factories have side effects, those side effects happen in the order the corresponding names appear in the input.)

Examples

Given:

context = CoreContext()
context.add_instances({"prefix": "abc", "suffix": "def"})
context.add_factories({"text": lambda prefix, suffix: prefix + suffix})
  • with context.build_tuple(("prefix", "suffix", "text")) as t: → t == ("abc", "def", "abcdef")
  • with context.build_tuple("prefix", "suffix", "text") as (a, b, c): → (a, b, c) == ("abc", "def", "abcdef")

Given factories whose side effects append their own letter to a shared list when resolved, calling build_tuple with a sequence of names produces those side effects in exactly the order the names were passed.

Objective

Add a new public method named build() to the existing Context class in the junkie package. It resolves requested targets using the context's dependency providers and exposes the resolved result through a context manager suitable for a with statement.

Context must remain importable from the package root:

from junkie import Context

The public method has this call signature:

def build(self, *args, **kwargs):
    ...

Every valid call returns a context manager. Entering that context manager yields the result shape specified below, and leaving it releases any managed resources created during resolution.

Existing context setup and provider model

The existing setup API must continue to work:

  • Context(mapping) accepts a dictionary mapping string names to providers.
  • Additional positional context arguments are accepted, as in Context(mapping, additional_mapping_or_none). A None context argument is valid and is ignored.
  • add(...) continues to accept mapping arguments and None; add(None) is a no-op. Existing use with more than one mapping argument must remain supported.

A registered provider is either:

  • a plain value, which resolves directly to that value; or
  • a callable or class, which acts as a factory and is invoked after its dependencies have been resolved.

A callable value in the context mapping is treated as a provider, not as a plain callable object. A plain string stored under a name is a literal value after that name is looked up; it is not treated as another name to look up.

Dependency resolution

A build target is resolved as follows:

  • A string target is a name lookup in the context.
  • A class or other callable target is resolved directly as a factory, whether or not it was registered under a name.
  • For a callable or class provider, inspect its named call or constructor parameters. Resolve matching names recursively from the context and invoke the provider using keyword arguments with those names.
  • If a parameter has a default and no provider with the same name exists, omit that argument so the callable's declared default is used. If the name does exist in the context, the resolved context value takes precedence over the default.
  • If a requested name or required parameter cannot be found, resolution raises an exception. The existing unknown-name diagnostic format, Not found: <name>, must remain available.

Resolution is name-based. Type annotations may be present, including on normal classes and dataclasses, but do not replace the requirement to match dependency names. Dataclass-generated constructors must work in the same way as other class constructors, including normal __post_init__ behavior.

Providers may themselves depend on other callable providers, with recursive resolution continuing until plain values or zero-argument providers are reached. Where a resolved provider is a class, the result is an instance of that class. Plain registered values are yielded unchanged.

If an invoked provider returns a context manager, it must be entered during resolution and its __enter__() result must be used as the resolved dependency. All such resources remain active for the outer build() context and are exited when that context ends, in reverse order of entry. This cleanup applies both on normal exit and when the body of the with statement raises.

Supported build() call forms and result shapes

Only strings, classes, and callables are valid individual targets. The public method must dispatch the following forms distinctly.

1. One individual positional target

A single string, class, or callable yields one resolved value, not a container:

with context.build("var1") as instance:
    ...

with context.build(App) as app:
    ...
2. One positional dictionary

A single dictionary maps arbitrary output keys to individual targets. It yields a new dictionary with the same keys and each target replaced by its resolved value:

with context.build({"A": "var1", "B": MyApp}) as instances:
    # instances["A"] is the value registered as "var1"
    # instances["B"] is a resolved MyApp instance
    ...

The dictionary's keys label the output; they are not dependency names unless also used as a target value.

3. Keyword targets only

When called without positional arguments and with keyword targets, build() yields a dictionary from each keyword to its resolved value:

with context.build(A="var1", B=MyApp) as instances:
    ...

This has the same result semantics as the positional-dictionary form.

4. One positional tuple

A single tuple of individual targets yields a tuple of resolved values in the same order. Even a tuple supplied as the sole positional argument retains tuple-shaped output:

with context.build(("var1", MyApp)) as instances:
    # instances[0] is the value registered as "var1"
    # instances[1] is a MyApp instance
    ...

Targets must be resolved in tuple order.

5. Multiple individual positional targets

Two or more string, class, or callable positional targets yield a tuple in positional order:

with context.build("var1", MyApp) as (value, app):
    ...

This form has the same resolution and ordering semantics as the positional-tuple form.

Invalid calls and error timing

build() must reject unsupported argument combinations and container types with an exception. No particular Exception subclass is required.

  • Positional and keyword arguments may not be mixed. For example, context.build("var1", B=MyApp) is invalid. This validation must happen synchronously in the build(...) call itself: that expression must raise even if its return value is never entered as a context manager.
  • Lists are not accepted by build(), whether supplied as a would-be container or as positional targets. For example, context.build(["var1"], [MyApp]) is invalid.
  • Sets are not accepted by build(). For example, context.build({"var1", MyApp}) is invalid.
  • Other positional values outside the supported dictionary, tuple, string, class, and callable forms are invalid. Dictionary values, tuple elements, multiple positional targets, and keyword values must each be valid individual targets.

For invalid forms other than mixed positional and keyword arguments, the exception may be raised either while build() is called or when the returned context manager is entered. Dependency lookup and provider invocation failures may likewise occur during context entry.

Nested-resolution example

from junkie import Context

class App:
    def __init__(self, text: str):
        self.text = text

    def greets(self) -> str:
        return self.text

context = Context({
    "greeting": "Hello",
    "name": "Joe",
    "text": lambda greeting, name: "{} {}!".format(greeting, name),
})

with context.build(App) as app:
    assert app.greets() == "Hello Joe!"

Here the direct App target requires text. Resolving text invokes its registered callable, whose greeting and name parameters resolve to the two plain values.

Compatibility requirements

build() is an additional public API and must not remove or regress existing construction APIs. In particular, build_instances(...) must continue to work with its legacy forms:

  • a string name yields one resolved value;
  • a class yields one constructed instance;
  • a tuple of names yields a tuple in order; and
  • a list or set of names yields a dictionary keyed by those names.

The fact that list and set containers remain accepted by build_instances(...) does not make them valid for the new build() method. Existing context construction, add(...), recursive resolution, default-argument handling, and context-manager lifecycle behavior must remain compatible.

Task Specification: Dependency Injection Context

Overview

Implement a dependency-injection container class Context in the module junkie.context. A Context is constructed from a mapping of names to values or factories, and provides a single build(...) method that resolves one or more named/typed instances and yields them as a context manager.

There must also be a top-level package junkie that is importable (i.e. import junkie must work and expose junkie.__name__, which equals "junkie").

Public API

junkie.context.Context
class Context:
    def __init__(self, mapping: dict = None):
        ...

    def build(self, *args):
        ...
  • The constructor accepts an optional mapping dictionary. When omitted, the context is empty.
  • The mapping maps string names to either:
    • a value (any object that is used directly), or
    • a factory (a callable — a function, lambda, class, or @contextmanager-decorated generator — that produces the instance).
  • build(*args) returns a context manager (usable in a with statement). Its behavior depends on the number and kind of arguments (see below).

Resolution semantics

Each argument to build is a request for one instance. A request is either:

  • a string name — looked up in the mapping, or
  • a type / callable — used directly as a factory.
Resolving a string name

To resolve a name:

  1. Look the name up in the mapping.
  2. If not present, raise an Exception whose message is exactly Not found: <name> (e.g. Not found: instance_name).
  3. If the mapped object is not callable, it is the resolved instance (used directly).
  4. If the mapped object is callable, call it as a factory (see "Calling a factory"). Its result is the resolved instance.
Resolving a type / callable

When a request argument is itself a callable (e.g. a class), it is used directly as the factory and called (see "Calling a factory").

Calling a factory

A factory is called by inspecting its parameters (using the signature of the callable; for a class this is its __init__). For each parameter:

  • If a parameter with the same name exists in the mapping, resolve that name (recursively, using the full name-resolution rules above) and pass it as a keyword argument.
  • If no matching name exists in the mapping:
    • If the parameter has a default value, it is left unset (the default is used).
    • If the parameter has no default value, it is not supplied.
  • **kwargs-style parameters: if a mapping entry matches the **kwargs parameter's name, that entry is resolved and its (dictionary) value is expanded as keyword arguments to the factory. If there is no matching entry, no extra keyword arguments are passed. (A factory taking only **kwargs with no matching mapping entry receives an empty set of keyword arguments.)

Parameters explicitly resolvable from the mapping override defaults; parameters not in the mapping fall back to their declared defaults.

Context-manager factories and returned instances

Some factories/instances are themselves context managers:

  • If a resolved factory result (or a value) supports the context-manager protocol (__enter__/__exit__), or the factory is a generator-based context manager (e.g. decorated with @contextmanager), the object is entered and the value produced by entering it becomes the resolved instance exposed to the caller.
  • All such entered resources must be exited when the with block returned by build closes.

Ordering guarantees:

  • Dependencies are resolved/entered in the order needed to satisfy the requested instances (a factory's dependencies are resolved before the factory itself is called).
  • On exit, entered resources are exited in reverse order of entering.

build(...) argument forms and return values

  • Single request: build(x) where x is one string name or one type/callable.

    • The with block yields the single resolved instance directly.

  • Multiple requests: build(a, b, c, ...) with two or more arguments, each a string name or type/callable.

    • The with block yields a tuple of the resolved instances, in the same order as the arguments.
    • Every requested instance is fully resolved (including running each factory) in argument order; a factory later in the sequence observes the effects of factories resolved earlier.

Concrete behavioral examples

  • Context({"text": "abc"}).build("text") yields "abc".
  • Context({"text": lambda: "abc"}).build("text") yields "abc".
  • Context().build("instance_name") raises Exception("Not found: instance_name").
  • With mapping {"prefix": "abc", "suffix": "def", "text": lambda prefix, suffix: prefix + suffix}:
    • build("text") yields "abcdef".
    • build("prefix", "suffix", "text") yields ("abc", "def", "abcdef").
  • With mapping {"text": "abc"} and class AppClass(text: str), build(AppClass) yields an AppClass instance whose text is "abc".
  • Given a class Class(prefix, suffix) that sets self.text = prefix + suffix, and mapping {"prefix": "abc", "suffix": "xyz", "class": Class} (where "text" may also be present but is unused for this class), build("class") yields an instance with text == "abcxyz".
Default arguments

For a class MyClassWithDefaultArguments(argument: str, default_argument: int = 10, default_argument2: str = None):

  • With mapping {"argument": "value"}, build(MyClassWithDefaultArguments) yields an instance with argument == "value", default_argument == 10, and default_argument2 == None (the default is used since it is not in the mapping).
  • With mapping {"argument": "value", "default_argument2": "set from context"}, the instance has argument == "value", default_argument == 10, and default_argument2 == "set from context".
**kwargs

For a class MyClassWithKwargs(**name):

  • Empty context: build(MyClassWithKwargs) yields an instance whose captured kwargs is {}.
  • Mapping {"name": {"a": "a"}} (value): the captured kwargs is {"a": "a"}.
  • Mapping {"name": create_kwargs} where create_kwargs() returns {"a": "a"} (factory): the captured kwargs is {"a": "a"}.
Context-manager resources

Given:

  • A class Class(message_service, database_context),
  • MessageService(logger) implementing __enter__/__exit__ that appends "connect" on enter and "disconnect" on exit,
