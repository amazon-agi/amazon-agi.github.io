Task Specification: Adding Create and Update Support to the Accounting Client Resource

Overview

The accounting client resource is to be extended so that it supports creating new clients and updating existing ones against the FreshBooks accounting API. Both of these operations must send authenticated JSON requests and return a result object wrapping the client data that comes back.

Context

Access to the client resource happens via the FreshBooks client instance through an attribute named clients (that is, freshBooksClient.clients). Read/list operations are already supported by this resource. Two new methods must be added to it: create and update.

Endpoint URLs are constructed from the API base URL together with the account identifier. Under the accounting account path, the path segment that is relevant for the client resource is users/clients.

Required API Methods

Two methods are to be added to the accounting client resource:

create(account_id, data)
  • Parameters:
    • account_id: the account identifier (string).
    • data: a dictionary holding the payload of client fields to create (e.g., {"email": "john.doe@abcorp.com"}).
  • Behavior:
    • Performs an HTTP POST request to:
      {API_BASE_URL}/accounting/account/{account_id}/users/clients
    • The request is sent with:
      • An Authorization header of the form Bearer <token> (with the configured access token).
      • A Content-Type header equal to application/json.
    • A result object (described below) built from the API response is returned.
update(account_id, resource_id, data)
  • Parameters:
    • account_id: the account identifier (string).
    • resource_id: the identifier of the client to update (integer).
    • data: a dictionary holding the payload of fields to update.
  • Behavior:
    • Performs an HTTP PUT request to:
      {API_BASE_URL}/accounting/account/{account_id}/users/clients/{resource_id}
    • The request is sent with the same Authorization and Content-Type: application/json headers that create uses.
    • A result object (described below) built from the API response is returned.

Shape of the API Response

The JSON that both endpoints return has the following shape:

{
  "response": {
    "result": {
      "client": { ...client fields... }
    }
  }
}

The client object carries fields such as email, userid, id, and many other client attributes.

Requirements for the Result Object

create and update both return the same kind of result object. This object stands for a single named resource taken from response.result; for the client resource, that inner key is "client".

The result object must support the following:

  • str() representation: calling str(result) yields Result(client) — that is, Result(<name>), where <name> is the inner key.
  • .name attribute: returns the inner key name, "client".
  • .data attribute: returns the raw dictionary of client fields (the value stored under the "client" key). Reading a field, e.g. result.data["email"], yields that field's value.
  • Dynamic attribute access: each individual client field can be accessed directly as an attribute on the result object. For example:
    • result.email returns the client's email value.
    • result.userid returns the client's userid value (an integer).

Additional Notes

  • The token used for the Authorization header is taken from the configured access token on the FreshBooks client.
  • The request bodies of create and update carry the data payload that is provided; the response returned to the caller reflects the resource as returned by the API (which may differ from the submitted payload).

Definition of Done

  • freshBooksClient.clients.create(account_id, data) issues a POST to the clients collection URL with JSON content type and bearer authorization, and returns a result object as specified.
  • freshBooksClient.clients.update(account_id, resource_id, data) issues a PUT to the specific client URL with JSON content type and bearer authorization, and returns a result object as specified.
  • The result object that comes back satisfies all of the str(), .name, .data, and dynamic field-attribute requirements described above.

Task Specification: Support for a Custom User-Agent Header

Overview

Update the FreshBooks client so that a User-Agent header is included on every HTTP request it makes to the API. A sensible default must exist for the header value, and callers must be able to override it.

Public API Surface

Module: freshbooks.client

Introduce a module-level constant:

  • VERSION — a string that represents the SDK version. It must be importable via the statement from freshbooks.client import VERSION. The default user agent string is built using this value (see below).
The client class

The client class is instantiated through from freshbooks import Client (the existing Client, which is the client class of freshbooks.client).

Extend the client constructor with a new optional keyword argument:

  • user_agent (optional, keyword argument): a string. When a value is provided, that exact string is used as the value of the User-Agent header on all requests made by that client instance. When no value is provided, the header defaults to the value described below.

Aside from this addition, the constructor must continue to accept its existing keyword arguments (e.g. access_token) and behave as before in all other respects.

Behavior

On every HTTP request the client issues to the API, it must send a User-Agent request header.

  • Default value: If the client was constructed without a user_agent argument, the value of the User-Agent header must be exactly:

    FreshBooks python sdk/{VERSION}

    where {VERSION} denotes the value of the freshbooks.client.VERSION constant.

  • Overridden value: If the client was constructed with a user_agent argument, the value of the User-Agent header must be exactly the string that was provided, with no additional formatting or prefixing.

The addition of this header must not remove or alter any existing request headers (for example, the Authorization: Bearer <token> header must continue to be sent as before).

This header must be present on all API request types the client makes (both single-resource retrievals and list retrievals).

Task Specification: OAuth2 Authorization Support for the FreshBooks Client

Overview

Introduce OAuth2 authorization capabilities into the FreshBooksClient class, and make client_id a required part of the client configuration, reflected in the outgoing User-Agent header.

Public API

Constructing the Client

The client class is imported with:

from freshbooks import Client as FreshBooksClient

In addition to whatever it already accepts, the constructor must accept these keyword arguments:

  • client_id (str) — identifier of the OAuth2 client.
  • redirect_uri (str, optional) — the OAuth2 redirect URI.
  • access_token (str, optional) — an access token that already exists.
  • refresh_token (str, optional) — a refresh token that already exists.
  • user_agent (str, optional) — a custom user-agent override (this is already supported).

The constructions below are examples of valid usage and must work:

FreshBooksClient(client_id="some_client", access_token="some_token")
FreshBooksClient(client_id="some_client", access_token="some_token", user_agent="phone_home")
FreshBooksClient(client_id="some_client", redirect_uri="https://example.com")
FreshBooksClient(
    client_id="some_client",
    redirect_uri="https://example.com",
    access_token="an_old_token",
    refresh_token="an_old_refresh_token"
)

The module-level values below must remain importable:

from freshbooks.client import API_BASE_URL, VERSION
Attributes on the Client

After construction and after token operations, the client exposes the attributes below:

  • access_token — the access token string currently in use (or the value passed in at construction).
  • refresh_token — the refresh token string currently in use (or the value passed in at construction).
  • access_token_expires_at — a datetime giving the absolute expiry time of the current access token (or None/unset until a token has been obtained).

Required Behavior

1. The User-Agent Header Includes client_id

When no custom user_agent is supplied, every outgoing API request must send a User-Agent header of exactly this form:

FreshBooks python sdk/{VERSION} client_id {client_id}

For instance, given VERSION and client_id="some_client", the header value is:

FreshBooks python sdk/{VERSION} client_id some_client

(If a custom user_agent is supplied, that custom value continues to be used as before.)

2. get_auth_request_url(scopes=None)

Constructs and returns (as a string) the OAuth2 authorization URL to which the end-user should be redirected.

  • Signature: get_auth_request_url(self, scopes=None) -> str
  • Base URL: https://auth.freshbooks.com/service/auth/oauth/authorize
  • Query parameters, in exactly this order:
    1. client_id — the client's client_id
    2. response_type — always the literal code
    3. redirect_uri — the client's redirect_uri (URL-encoded)
    4. scope — included only when scopes is provided and non-empty; the scopes joined by spaces (URL-encoded, spaces as +)

For client_id="some_client" and redirect_uri="https://example.com" with no scopes:

https://auth.freshbooks.com/service/auth/oauth/authorize?client_id=some_client&response_type=code&redirect_uri=https%3A%2F%2Fexample.com

When the scopes are ["some:scope", "another:scope"]:

https://auth.freshbooks.com/service/auth/oauth/authorize?client_id=some_client&response_type=code&redirect_uri=https%3A%2F%2Fexample.com&scope=some%3Ascope+another%3Ascope
3. get_access_token(code)

Exchanges an authorization grant code for an access token by sending an HTTP POST to:

{API_BASE_URL}/auth/oauth/token

  • Signature: get_access_token(self, code) -> <result object>

  • The request body must be a form-urlencoded string with these parameters, in this exact order:

    1. client_id — the client's client_id
    2. grant_type — always the literal authorization_code
    3. redirect_uri — the client's redirect_uri (URL-encoded)
    4. code — the code passed in

    Body example: client_id=some_client&grant_type=authorization_code&redirect_uri=https%3A%2F%2Fexample.com&code=some_grant

  • If the response is successful (HTTP 200), its JSON body contains at least access_token, refresh_token, expires_in (seconds), and created_at (a Unix timestamp).

  • The method must update the client's access_token, refresh_token, and access_token_expires_at attributes, and must return a result object that exposes the same three attributes: access_token, refresh_token, access_token_expires_at.

  • access_token_expires_at must be computed as a datetime equal to the token's created_at timestamp plus expires_in seconds. For created_at = 1287287900 and expires_in = 100, this equals datetime(2010, 10, 17). (Read created_at such that this equivalence holds.)

Error handling: if the token endpoint responds with a non-success status (e.g. HTTP 500), raise a FreshBooksError that has:

  • string representation exactly Failed to fetch access_token
  • a status_code attribute equal to the HTTP status code that was returned (e.g. 500).
4. refresh_access_token(refresh_token=None)

Uses a refresh token to obtain a new access token, via an HTTP POST to the same endpoint:

{API_BASE_URL}/auth/oauth/token

  • Signature: refresh_access_token(self, refresh_token=None) -> <result object>

  • When refresh_token is passed as an argument, use that value. Otherwise, use the client's stored refresh_token.

  • The request body must be a form-urlencoded string with these parameters, in this exact order:

    1. client_id — the client's client_id
    2. grant_type — always the literal refresh_token
    3. redirect_uri — the client's redirect_uri (URL-encoded)
    4. refresh_token — the refresh token in effect

    Body example: client_id=some_client&grant_type=refresh_token&redirect_uri=https%3A%2F%2Fexample.com&refresh_token=an_old_refresh_token

  • On success, the method behaves exactly like get_access_token: it updates the client's access_token, refresh_token, and access_token_expires_at, and returns a result object that exposes those three attributes with the values derived from the response.

Imports That Must Be Resolvable

These names must be importable from the freshbooks package (some of them may already exist):

from freshbooks import Client, PaginatorBuilder, FilterBuilder, FreshBooksError, FailedRequest

Notes

  • For successful responses, the token response fixture contains: access_token="my_access_token", refresh_token="my_refresh_token", token_type="Bearer", expires_in=100, scope="some:scope", created_at=1287287900, id_token="a_id_token". Only access_token, refresh_token, expires_in, and created_at need to influence the resulting attributes.
  • Existing resource-access behavior (authenticated requests that use Authorization: Bearer {access_token}) must keep working unchanged, apart from the User-Agent change described above.

    {

}

    • str(e) is equal to the value of error_description (e.g. "This action requires authentication to continue.").

Existing Resources — Required Structure

  • freshbooks.api.accounting.AccountingResource
  • freshbooks.api.projects.ProjectsResource

def include(self, key: str) -> "IncludesBuilder"

Task Specification: Nested Data Held by FreshBooks Client Result Objects

Background

API result objects (Result and ListResult) are what the freshbooks package returns whenever resources are fetched or listed. At present, a nested list or dictionary held by an attribute of a result object is returned as a raw Python list or dict. The requirement of this task is that nested lists be wrapped in ListResult objects and dictionaries in Result objects, so that deeply nested data can be navigated by callers through attribute access.

Public-Facing API

Both result classes are made available by the freshbooks.api.resource layer, and resource .get() and .list() calls return these objects (e.g. freshBooksClient.clients.get(...), freshBooksClient.clients.list(...), freshBooksClient.projects.get(...)).

  • Result — the class modeling a single resource object (a dictionary of fields).
  • ListResult — the class modeling a list of resource objects.

Both classes must already exist and must be returned by the existing resource methods. What this task modifies is their behavior under nested attribute access.

Mandated Behavior

Result

A dictionary of attributes is what a Result wraps. The following is what it exposes:

  • .data — the dictionary underlying this result, in raw form.
  • .name — a string name carried by the result (the resource/attribute name).
  • Attribute access — when an attribute is accessed by name, the corresponding value is returned from the underlying data, subject to these wrapping rules:
    • If the attribute's value is a plain scalar (string, number, bool, etc.), it is returned unchanged.
    • A dictionary as the attribute value is returned wrapped in a Result — that Result's .name is the attribute name being accessed, and its .data is that dictionary. This wrapping must be applied recursively as well, so nested dictionaries can be navigated by chaining attribute accesses.
    • A list as the attribute value is returned wrapped in a ListResult (detailed below), whose .name is the attribute name being accessed.
  • str() / repr() — the string Result(<name>) is what these produce, <name> being the result's name.

To illustrate the navigation this makes possible: let a result's .data contain {"test_amount": {"amount": 10, "code": "CAD"}}. The expression .test_amount then yields a Result (which renders as Result(test_amount)), and .test_amount.code yields "CAD".

Next, take a result whose .data holds a nested list of dictionaries under the key outstanding_balance, for instance [{"amount": {"amount": 10, "code": "CAD"}}, {"amount": {"amount": 11, "code": "CAD"}}]. Here .data["outstanding_balance"] is still the original list of plain dictionaries (no mutation of .data happens), whereas .outstanding_balance returns a ListResult.

ListResult

A list of items is what a ListResult wraps. The following is what it exposes:

  • .name — a string name carried by the list result.
  • Indexing — the item positioned at index i is what list_result[i] returns. If that item is a dictionary, it is returned wrapped in a Result whose .name is equal to the ListResult's name. Indices past the valid range raise IndexError (the behavior of standard list indexing).
  • Iteration — when a ListResult is iterated, each item is yielded; dictionary items among them come wrapped in Result objects (each one carrying the ListResult's name), which makes attribute access possible on each yielded element.
  • len() — returns the count of items the list holds.
  • str() / repr() — the string ListResult(<name>) is what these produce, <name> being the list result's name.
  • .pages — pagination metadata (existing behavior, left unchanged); a .total attribute is present alongside others.

As an example, take a ListResult named outstanding_balance that wraps [{"amount": {"amount": 10, "code": "CAD"}}, {"amount": {"amount": 11, "code": "CAD"}}]. In that case:

  • list_result[0] has Result(outstanding_balance) as its string form.
  • list_result[0].data is equal to {"amount": {"amount": 10, "code": "CAD"}}.
  • list_result[0].amount.code is equal to "CAD" — through Result, the nested-dict wrapping described above applies.
  • Iteration yields Result items, and on them nested attribute access works the same way.

If the list a ListResult wraps is empty, the object renders as ListResult(<name>), its length is 0, and an attempt to index into it raises IndexError.

List results produced by .list()

Whenever a resource's .list() method returns a collection of resources, a ListResult must be the object returned. The .name on it is the resource collection name (for example "clients"), its string form is ListResult(clients), its length is equal to the number of items returned, and its .pages.total mirrors the pagination total. Iterating over the object or indexing into it yields Result objects, one for each resource.

Single results produced by .get()

Whenever a resource's .get() method returns a single resource, a Result must be the object returned. The .name on it is the resource name (for example "client"), its string form is Result(client), and its .data is the dictionary of the resource's fields. Attribute access, including access to nested attributes, follows the Result rules given above (scalars are returned directly, e.g. .organization == "American Cyanamid" and .userid returning the id; nested dicts and lists are wrapped).

Restrictions

  • The wrapping of nested dictionaries/lists must not mutate the original underlying .data; through .data, the raw dictionary/list values remain accessible in their original plain form.
  • Wrappers are applied to nesting recursively: a dictionary inside another dictionary, as well as a dictionary inside a list item, is navigable via attribute access in all such cases, and the Result objects produced carry the correct names.

Implement Webhook Callback Support in the FreshBooks Python SDK

Summary

This task adds a resource for the Events API through which webhook callbacks are managed. Additivity is a requirement for the feature: the existing authentication, accounting, projects, time-tracking, builder, result-model, error, and client behavior must be left untouched.

Public Types and Constants That Already Exist

The public SDK objects listed below already exist; the way they are used must continue to match their established behavior:

  • freshbooks.Client
  • freshbooks.PaginateBuilder
  • freshbooks.FilterBuilder
  • freshbooks.FreshBooksError
  • freshbooks.client.API_BASE_URL
  • freshbooks.client.VERSION
  • The single-resource and list-resource result objects the SDK already has
Resource Exposure on the Client

When a client is created through from freshbooks import Client, a callbacks property must be exposed on it:

client = Client(client_id="some_client", access_token="some_token")
callbacks = client.callbacks

Calling client.callbacks returns a resource object for the Events API callback endpoints. All of the methods below must be available on it:

callbacks.get(account_id, resource_id)
callbacks.list(account_id, builders=None)
callbacks.create(account_id, data)
callbacks.update(account_id, resource_id, data)
callbacks.delete(account_id, resource_id)
callbacks.resend_verification(account_id, resource_id)
callbacks.verify(account_id, resource_id, verification_code)

Here account_id is a string holding an alphanumeric account identifier, resource_id an integer that identifies a callback, data a dictionary of callback fields, and verification_code the code for verifying the callback. callback is the resource's name in the singular; in the plural it is callbacks.

URLs for the Endpoints

The API base is the base URL configured on the client in question; its default is freshbooks.client.API_BASE_URL. The Events API path family is what callback requests use.

Collection URL:

{API_BASE_URL}/events/account/{account_id}/events/callbacks

Single-callback URL:

{API_BASE_URL}/events/account/{account_id}/events/callbacks/{resource_id}

Which URL and HTTP verb each method maps to is shown in the following table:

Method HTTP verb URL
get GET Single-callback URL
list GET Collection URL
create POST Collection URL
update PUT Single-callback URL
delete DELETE Single-callback URL

Headers Sent on Requests

Every callback request must carry the headers shown next:

Authorization: Bearer {access_token}
User-Agent: FreshBooks python sdk/{VERSION} client_id {client_id}

The owning client is the source of these values. Should the client have been created with a custom user-agent, the SDK's existing custom-user-agent behavior keeps applying.

POST and PUT requests must additionally carry:

Content-Type: application/json

GET and DELETE requests carry no JSON body, and Content-Type must not be set on them.

Bodies of Requests

Callback fields arrive from the caller as an unwrapped dictionary. A request that carries callback data must put those fields inside the Events API's callback envelope.

}

{ "callback": { "...fields from data...": "..." } }
Resend verification

With resend_verification(account_id, resource_id) a PUT is performed, sending:

{ "callback": { "resend": true } }
Verify

verify(account_id, resource_id, verification_code) performs a PUT, sending:

{ "callback": { "verifier": "verification_code" } }

The verifier value must be exactly the verification_code argument as supplied by the caller.

Delete

With delete(account_id, resource_id) a DELETE request is sent that contains no request-body bytes. Callback deletion is a true DELETE operation, not a soft-delete done via an update.

Query Builders for List Requests

An optional builders list is accepted by list, and the output of the existing builders gets combined into the collection request's query string.

Paginating by means of PaginateBuilder must work. For example:

client.callbacks.list(account_id, builders=[PaginateBuilder(2, 1)])

and the request then includes this parameter:

When builders=None is used, or when no builders are passed, no builder query parameters get added to the request.

        "verified": true,

  }
}

Each method returns the SDK's usual single-resource result object, set up with the singular name callback and filled from response.result.callback. Observable behavior includes:

  • str(result) == "Result(callback)"
  • result.name == "callback"
  • result.data is the raw callback dictionary, not the response envelopes surrounding it
  • Every callback field can be read as an attribute, such as result.callbackid, result.event, result.uri, and result.verified

As an example, when the response's callback ID is 123, result.callbackid and result.data["callbackid"] both equal 123.

{ "response": {} }

Given that response:

  • str(result) == "Result(callback)"
  • result.name == "callback"
  • result.data == {}

This applies to a successful delete response such as one with HTTP 204 carrying that response envelope.

List Success Responses

The structure of a list response is as follows:

{
  "response": {
    "result": {
      "callbacks": [
        { "callbackid": 123, "event": "invoice.create" },
        { "callbackid": 124, "event": "estimate.create" }
      ],
      "page": 1,
      "pages": 1,
      "per_page": 15,
      "total": 2
    }
  }
}

list returns the SDK's usual list-result object; callbacks is its plural name and callback its singular item name. Observable behavior includes:

  • str(result) == "ListResult(callbacks)"
  • result.name == "callbacks"
  • len(result) is the count of objects in callbacks
  • Iteration yields callback result objects in the order the response presents them
  • Each yielded item exposes callback fields as attributes, such as item.callbackid
  • Standard list-result indexing and raw data access keep working
  • result.pages exposes the response's page, pages, per_page, and total metadata; specifically, result.pages.total equals response.result.total

Therefore, an empty callbacks array gives a list result of zero length that iterates in the normal way.

Error Handling for the Events API

All of the callback methods must report response failures via freshbooks.FreshBooksError. The exception carries the SDK's public attributes status_code, error_code, and raw_response, and its human-readable message is what str(error) produces.

Errors coming from the Events API, unlike those from accounting endpoints, are not nested under response.errors. What they use instead is a top-level envelope; for example:

{
  "errno": 404,
  "message": "Requested resource could not be found."
}
Recognized Events API error

If an HTTP failure response arrives as valid JSON and contains errno and message:

  • The message carried by the raised exception is taken from message.
  • error.status_code holds the HTTP response status.
  • The value of errno becomes error.error_code.
  • error.raw_response is the parsed top-level JSON object.

When the example above is returned with HTTP 404:

str(error) == "Requested resource could not be found."
error.status_code == 404
error.error_code == 404
error.raw_response == {
    "errno": 404,
    "message": "Requested resource could not be found.",
}
Body cannot be parsed as JSON

If the body of a response is not valid JSON, FreshBooksError is raised with:

  • Message "Failed to parse response"
  • status_code equal to the HTTP response status
  • raw_response equal to the original response text

Given an HTTP 500 response whose body is stuff, str(error) comes out as "Failed to parse response" and error.raw_response is "stuff".

Valid JSON with an unexpected success shape

A valid JSON response is still an error if the structure the operation requires is missing. The structures to be expected are response.result.callback for a normal single-callback operation and response.result.callbacks for a list operation; the exception is the successful delete form shown above.

Consider an HTTP 200 response with the body:

{ "foo": "bar" }

FreshBooksError is raised with:

  • Message "Returned an unexpected response"
  • status_code == 200
  • raw_response equal to the original JSON response text, for example '{"foo": "bar"}' with the server's original formatting

The callback resource must be built on the SDK's established client configuration, transport headers, builders, result objects, and exception type, so that its behavior stays consistent with the existing resources. The contracts that set this resource apart are the /events/account/.../events/callbacks URL family and the Events API's top-level errno/message error envelope.
