Task Specification: Add Create and Update Support to Accounting Client Resource

Overview

Extend the accounting client resource so that it supports creating new clients and updating existing clients against the FreshBooks accounting API. These operations must send authenticated JSON requests and return a result object wrapping the returned client data.

Context

The client resource is accessed via the FreshBooks client instance through an attribute named clients (i.e., freshBooksClient.clients). This resource already supports read/list operations. You must add two new methods to it: create and update.

The API base URL and account identifier are used to construct endpoint URLs. The relevant path segment for the client resource is users/clients under the accounting account path.

Required API Surface

Add two methods to the accounting client resource:

create(account_id, data)
  • Parameters:
    • account_id: the account identifier (string).
    • data: a dictionary representing the payload of client fields to create (e.g., {"email": "john.doe@abcorp.com"}).
  • Behavior:
    • Issues an HTTP POST request to:
      {API_BASE_URL}/accounting/account/{account_id}/users/clients
    • Sends the request with:
      • An Authorization header of the form Bearer <token> (using the configured access token).
      • A Content-Type header equal to application/json.
    • Returns a result object (described below) built from the API response.
update(account_id, resource_id, data)
  • Parameters:
    • account_id: the account identifier (string).
    • resource_id: the identifier of the client to update (integer).
    • data: a dictionary representing the payload of fields to update.
  • Behavior:
    • Issues an HTTP PUT request to:
      {API_BASE_URL}/accounting/account/{account_id}/users/clients/{resource_id}
    • Sends the request with the same Authorization and Content-Type: application/json headers as create.
    • Returns a result object (described below) built from the API response.

API Response Shape

Both endpoints return JSON of the following shape:

{
  "response": {
    "result": {
      "client": { ...client fields... }
    }
  }
}

The client object contains fields such as email, userid, id, and many other client attributes.

Result Object Requirements

Both create and update return the same kind of result object. This object represents a single named resource extracted from response.result. For the client resource, the inner key is "client".

The result object must support:

  • str() representation: str(result) produces Result(client) — i.e., Result(<name>) where <name> is the inner key.
  • .name attribute: returns the inner key name, "client".
  • .data attribute: returns the raw dictionary of client fields (the value under the "client" key). Accessing a field, e.g. result.data["email"], yields that field's value.
  • Dynamic attribute access: individual client fields are accessible directly as attributes on the result object. For example:
    • result.email returns the client's email value.
    • result.userid returns the client's userid value (an integer).

Notes

  • The token used for the Authorization header comes from the configured access token on the FreshBooks client.
  • Request bodies for create and update carry the provided data payload; the response returned to the caller reflects the resource as returned by the API (which may differ from the submitted payload).

Definition of Done

  • freshBooksClient.clients.create(account_id, data) performs a POST to the clients collection URL with JSON content type and bearer authorization, returning a result object as specified.
  • freshBooksClient.clients.update(account_id, resource_id, data) performs a PUT to the specific client URL with JSON content type and bearer authorization, returning a result object as specified.
  • The returned result object satisfies all the str(), .name, .data, and dynamic field-attribute requirements described above.

Task Specification: Custom User-Agent Header Support

Overview

Modify the FreshBooks client so that every HTTP request it makes to the API includes a User-Agent header. The header value must have a sensible default, and callers must be able to override it.

Public API Surface

Module: freshbooks.client

Add a module-level constant:

  • VERSION — a string representing the SDK version. It must be importable as from freshbooks.client import VERSION. Its value is used to build the default user agent string (see below).
Client class

The client class is instantiated via from freshbooks import Client (the existing Client, which is freshbooks.client's client class).

Add a new optional keyword argument to the client constructor:

  • user_agent (optional, keyword argument): a string. When provided, this exact string is used as the value of the User-Agent header on all requests made by that client instance. When not provided, the header defaults to the value described below.

The constructor must continue to accept its existing keyword arguments (e.g. access_token) and behave as before in all other respects.

Behavior

For every HTTP request the client issues to the API, it must send a User-Agent request header.

Task Specification: OAuth2 Authorization Support for FreshBooks Client

Overview

Add OAuth2 authorization capabilities to the FreshBooksClient class, and make the client_id a required piece of client configuration that is reflected in the outgoing User-Agent header.

Public API Surface

Client Construction

The client class is imported as:

from freshbooks import Client as FreshBooksClient

The constructor must accept the following keyword arguments (in addition to whatever it already accepts):

  • client_id (str) — an OAuth2 client identifier.
  • redirect_uri (str, optional) — the OAuth2 redirect URI.
  • access_token (str, optional) — a pre-existing access token.
  • refresh_token (str, optional) — a pre-existing refresh token.
  • user_agent (str, optional) — a custom user-agent override (already supported).

Example valid constructions that must work:

FreshBooksClient(client_id="some_client", access_token="some_token")
FreshBooksClient(client_id="some_client", access_token="some_token", user_agent="phone_home")
FreshBooksClient(client_id="some_client", redirect_uri="https://example.com")
FreshBooksClient(
    client_id="some_client",
    redirect_uri="https://example.com",
    access_token="an_old_token",
    refresh_token="an_old_refresh_token"
)

The following module-level values must remain importable:

from freshbooks.client import API_BASE_URL, VERSION
Client Attributes

After construction and after token operations, the client exposes these attributes:

  • access_token — current access token string (or the value passed in at construction).
  • refresh_token — current refresh token string (or the value passed in at construction).
  • access_token_expires_at — a datetime representing the absolute expiry time of the current access token (or None/unset until a token is obtained).

Behavior Requirements

1. User-Agent Header includes client_id

When no custom user_agent is provided, every outgoing API request must send a User-Agent header of the exact form:

FreshBooks python sdk/{VERSION} client_id {client_id}

For example, with VERSION and client_id="some_client", the header value is:

FreshBooks python sdk/{VERSION} client_id some_client

(When a custom user_agent is supplied, that custom value continues to be used as before.)

2. get_auth_request_url(scopes=None)

Builds and returns (as a string) the OAuth2 authorization URL the end-user should be redirected to.

  • Signature: get_auth_request_url(self, scopes=None) -> str
  • Base URL: https://auth.freshbooks.com/service/auth/oauth/authorize
  • Query parameters, in this exact order:
    1. client_id — the client's client_id
    2. response_type — always the literal code
    3. redirect_uri — the client's redirect_uri (URL-encoded)
    4. scope — present only when scopes is provided and non-empty; the scopes joined by spaces (URL-encoded, spaces as +)

With client_id="some_client" and redirect_uri="https://example.com" and no scopes:

https://auth.freshbooks.com/service/auth/oauth/authorize?client_id=some_client&response_type=code&redirect_uri=https%3A%2F%2Fexample.com

With scopes ["some:scope", "another:scope"]:

https://auth.freshbooks.com/service/auth/oauth/authorize?client_id=some_client&response_type=code&redirect_uri=https%3A%2F%2Fexample.com&scope=some%3Ascope+another%3Ascope
3. get_access_token(code)

Exchanges an authorization grant code for an access token by making an HTTP POST to:

{API_BASE_URL}/auth/oauth/token

  • Signature: get_access_token(self, code) -> <result object>

  • The request body must be a form-urlencoded string with these parameters in this exact order:

    1. client_id — the client's client_id
    2. grant_type — always the literal authorization_code
    3. redirect_uri — the client's redirect_uri (URL-encoded)
    4. code — the passed-in code

    Example body: client_id=some_client&grant_type=authorization_code&redirect_uri=https%3A%2F%2Fexample.com&code=some_grant

  • On a successful (HTTP 200) response, the JSON body contains at least access_token, refresh_token, expires_in (seconds), and created_at (a Unix timestamp).

  • The method must update the client's access_token, refresh_token, and access_token_expires_at attributes, and return a result object exposing the same three attributes: access_token, refresh_token, access_token_expires_at.

  • access_token_expires_at must be computed as a datetime equal to the token's created_at timestamp plus expires_in seconds. For created_at = 1287287900 and expires_in = 100, this equals datetime(2010, 10, 17). (Interpret created_at such that this equivalence holds.)

Error handling: if the token endpoint responds with a non-success status (e.g. HTTP 500), raise a FreshBooksError whose:

  • string representation is exactly Failed to fetch access_token
  • status_code attribute equals the HTTP status code returned (e.g. 500).
4. refresh_access_token(refresh_token=None)

Obtains a new access token using a refresh token, via an HTTP POST to the same endpoint:

{API_BASE_URL}/auth/oauth/token

  • Signature: refresh_access_token(self, refresh_token=None) -> <result object>

  • If refresh_token is passed as an argument, use it. Otherwise, use the client's stored refresh_token.

  • The request body must be a form-urlencoded string with these parameters in this exact order:

    1. client_id — the client's client_id
    2. grant_type — always the literal refresh_token
    3. redirect_uri — the client's redirect_uri (URL-encoded)
    4. refresh_token — the effective refresh token

    Example body: client_id=some_client&grant_type=refresh_token&redirect_uri=https%3A%2F%2Fexample.com&refresh_token=an_old_refresh_token

  • On success, behaves exactly like get_access_token: updates the client's access_token, refresh_token, and access_token_expires_at, and returns a result object exposing those three attributes with the values derived from the response.

Imports That Must Resolve

The following names must be importable from the freshbooks package (some may already exist):

from freshbooks import Client, PaginatorBuilder, FilterBuilder, FreshBooksError, FailedRequest

Notes

  • The token response fixture used for successful responses contains: access_token="my_access_token", refresh_token="my_refresh_token", token_type="Bearer", expires_in=100, scope="some:scope", created_at=1287287900, id_token="a_id_token". Only access_token, refresh_token, expires_in, and created_at need to influence the resulting attributes.
  • Existing resource-access behavior (authenticated requests using Authorization: Bearer {access_token}) must continue to work unchanged, aside from the User-Agent change described above.

  • get(account_id, resource_id) — issues a request with HttpVerbs.GET.
  • create(account_id, data) — issues a create request (standard behavior for accounting resources that support creation).

The distinction: invoices deletes directly; expenses deletes via update.

However, the staffs resource does not support creation. Calling create(account_id, data) on the staffs resource must raise FreshBooksNotImplementedError.

More generally, the accounting resource layer must provide a mechanism whereby a resource configured to disallow a particular operation raises FreshBooksNotImplementedError when that operation is called. For staffs, the disallowed operation is create.

Class: PaginateBuilder

Constructor signature:

PaginateBuilder(page=None, per_page=None)

Both page and per_page may be passed positionally or as keyword arguments, and both are optional.

Methods

The class must provide the following methods:

  • page(value=None) — accessor/mutator for the page number.
    • When called with no argument, returns the current page value.
    • When called with a value, sets the page and returns the builder instance (to allow chaining).
  • per_page(value=None) — accessor/mutator for the per-page count.
    • When called with no argument, returns the current per-page value.

Value Constraints
  • Minimum page: the page value cannot be less than 1. If a value less than 1 (e.g., 0) is provided — whether via the constructor or the page() mutator — the effective page value is clamped to 1.
  • Maximum per_page: the per-page value cannot exceed 100. If a value greater than 100 (e.g., 500, 400) is provided — whether via the constructor or the per_page() mutator — the effective per-page value is clamped to 100.

build() returns a string composed of query parameters, each prefixed with &:

  • If a page value is set, include &page=<value>.
  • If a per-page value is set, include &per_page=<value>.
  • When both are set, the order is page first, then per_page, e.g. "&page=1&per_page=3".
  • If only page is set, e.g. "&page=1".
  • Clamped values are reflected in the output (a page of 0 produces "&page=1").

str(instance) must return:

PaginateBuilder(page=<page>, per_page=<per_page>)

reflecting the current (clamped) values, e.g. "PaginateBuilder(page=6, per_page=2)".

Mutator calls must support chaining, e.g. p.per_page(2).page(6) sets both values on the same instance.

Scope

This is purely a rename. All existing behavior of the builder must be preserved under the new name. No other builders (such as FilterBuilder) or exports are changed.

  • Returns the same IncludesBuilder instance so that calls can be chained, e.g.:

    includes = IncludesBuilder()
includes.include("late_reminders").include("last_activity")
Query parameter behavior

When applied to an outgoing request, an IncludesBuilder must produce query parameters using the key include[], with one value per included key, preserving the order in which the keys were added.

For example, after adding "late_reminders" then "last_activity", the resulting query string must be equivalent to:

include[]=late_reminders&include[]=last_activity

i.e. the query parameters resolve to {"include[]": ["late_reminders", "last_activity"]}.

Integration With Resource Operations

Single-resource get

The get method on accounting resources (e.g. client.clients.get(...)) must accept an optional keyword argument includes:

resource.get(account_id, resource_id, includes=<IncludesBuilder>)

When an IncludesBuilder is passed via includes, its query parameters must be appended to the request URL. For example, a get for client id 12345 under an account with an IncludesBuilder containing "late_reminders" and "last_activity" must issue a GET request to:

/accounting/account/<account_id>/users/clients/12345?include[]=late_reminders&include[]=last_activity

The returned object behavior is unchanged from existing single-resource retrieval: it exposes model attributes (e.g. client.name) and its string representation follows the existing format (e.g. Result(client)).

list

The list method on accounting resources (e.g. client.clients.list(...)) already accepts a builders keyword argument that takes a list of builder objects. An IncludesBuilder must be a valid entry in that list:

resource.list(account_id, builders=[<IncludesBuilder>])

When an IncludesBuilder is included in builders, its query parameters must be appended to the request URL. For example, listing clients under an account with an IncludesBuilder containing "late_reminders" and "last_activity" must issue a GET request to:

/accounting/account/<account_id>/users/clients?include[]=late_reminders&include[]=last_activity

Constraints

  • The existing behavior of other builders (PaginateBuilder, FilterBuilder) and of the get/list operations without an IncludesBuilder must remain unchanged.
  • Query parameter ordering must reflect the order in which includes were added.

Task Specification: Nested Result Objects in FreshBooks Client Results

Overview

The freshbooks package returns API result objects (Result and ListResult) when fetching or listing resources. Currently, when an attribute of a result object holds a nested list or dictionary, that nested value is returned as a raw Python list or dict. This task requires that nested lists and dictionaries be wrapped in ListResult and Result objects respectively, so callers can navigate deeply nested data using attribute access.

Public API Surface

The two result classes are available from the freshbooks.api.resource layer and are the objects returned by resource .get() and .list() calls (e.g. freshBooksClient.clients.get(...), freshBooksClient.clients.list(...), freshBooksClient.projects.get(...)).

  • Result — represents a single resource object (a dictionary of fields).
  • ListResult — represents a list of resource objects.

Both classes must already exist and be returned by the existing resource methods. This task modifies their behavior with respect to nested attribute access.

Required Behavior

Result

A Result wraps a dictionary of attributes. It exposes:

  • .data — the raw underlying dictionary for this result.
  • .name — a string name associated with the result (the resource/attribute name).
  • Attribute access — accessing an attribute by name returns the corresponding value from the underlying data, with the following wrapping rules:
    • If the attribute value is a plain scalar (string, number, bool, etc.), return it as-is.
    • If the attribute value is a dictionary, return it wrapped in a Result, whose .name is the attribute name being accessed and whose .data is that dictionary. This wrapping must apply recursively, so nested dictionaries are navigable via chained attribute access.
    • If the attribute value is a list, return it wrapped in a ListResult (see below), whose .name is the attribute name being accessed.
  • str() / repr() — produces the string Result(<name>) where <name> is the result's name.

Example of the navigation this enables: given a result whose .data contains {"test_amount": {"amount": 10, "code": "CAD"}}, accessing .test_amount yields a Result (stringifies to Result(test_amount)) and .test_amount.code yields "CAD".

Given a result whose .data contains a nested list of dictionaries under key outstanding_balance, e.g. [{"amount": {"amount": 10, "code": "CAD"}}, {"amount": {"amount": 11, "code": "CAD"}}], the raw .data["outstanding_balance"] remains the original list of plain dictionaries (i.e. .data is not mutated), while .outstanding_balance returns a ListResult.

ListResult

A ListResult wraps a list of items. It exposes:

  • .name — a string name associated with the list result.
  • Indexing — list_result[i] returns the item at index i. If that item is a dictionary, it is returned wrapped in a Result whose .name equals the ListResult's name. Out-of-range indices raise IndexError (standard list indexing behavior).
  • Iteration — iterating a ListResult yields each item, with dictionary items wrapped in Result objects (each carrying the ListResult's name), enabling attribute access on each yielded element.
  • len() — returns the number of items in the list.
  • str() / repr() — produces the string ListResult(<name>) where <name> is the list result's name.
  • .pages — pagination metadata (unchanged existing behavior), with a .total attribute among others.

Example: given a ListResult named outstanding_balance wrapping [{"amount": {"amount": 10, "code": "CAD"}}, {"amount": {"amount": 11, "code": "CAD"}}]:

  • list_result[0] stringifies to Result(outstanding_balance).
  • list_result[0].data equals {"amount": {"amount": 10, "code": "CAD"}}.
  • list_result[0].amount.code equals "CAD" (nested dict wrapping applies through Result as described above).
  • Iterating yields Result items on which the same nested attribute access works.

An empty list wrapped in a ListResult stringifies to ListResult(<name>), has length 0, and indexing into it raises IndexError.

List results from .list()

When a resource's .list() method returns a collection of resources, the returned object must be a ListResult. Its .name is the resource collection name (e.g. "clients"), it stringifies to ListResult(clients), its length equals the number of returned items, and its .pages.total reflects the pagination total. Iterating or indexing yields Result objects for each resource.

Single results from .get()

When a resource's .get() method returns a single resource, the returned object must be a Result. Its .name is the resource name (e.g. "client"), it stringifies to Result(client), and its .data is the resource's field dictionary. Attribute and nested-attribute access follow the Result rules above (scalars returned directly, e.g. .organization == "American Cyanamid", .userid returning the id; nested dicts and lists wrapped).

Constraints

  • Wrapping nested dictionaries/lists must not mutate the original underlying .data; the raw dictionary/list values remain accessible in their original plain form through .data.
  • Nested wrapping is recursive: dictionaries within dictionaries, and dictionaries within list items, are all navigable via attribute access and produce correctly-named Result objects.

Add Webhook Callback Support to the FreshBooks Python SDK

Overview

Add an Events API resource for managing webhook callbacks. The feature must be additive: existing authentication, accounting, projects, time-tracking, builder, result-model, error, and client behavior must remain unchanged.

Existing Public Types and Constants

The following public SDK objects already exist and must continue to be used with their established behavior:

  • freshbooks.Client
  • freshbooks.PaginateBuilder
  • freshbooks.FilterBuilder
  • freshbooks.FreshBooksError
  • freshbooks.client.API_BASE_URL
  • freshbooks.client.VERSION
  • The SDK's existing single-resource and list-resource result objects
Client Resource Exposure

A client created through from freshbooks import Client must expose a callbacks property:

client = Client(client_id="some_client", access_token="some_token")
callbacks = client.callbacks

The value returned by client.callbacks is a resource object for the Events API callback endpoints. It must provide all of these methods:

callbacks.get(account_id, resource_id)
callbacks.list(account_id, builders=None)
callbacks.create(account_id, data)
callbacks.update(account_id, resource_id, data)
callbacks.delete(account_id, resource_id)
callbacks.resend_verification(account_id, resource_id)
callbacks.verify(account_id, resource_id, verification_code)

account_id is an alphanumeric account identifier string, resource_id is an integer callback identifier, data is a dictionary of callback fields, and verification_code is the callback verification code. The singular resource name is callback; the plural resource name is callbacks.

Endpoint URLs

Let the API base be the base URL configured on the client, which defaults to freshbooks.client.API_BASE_URL. Callback requests use the Events API path family.

Collection URL:

{API_BASE_URL}/events/account/{account_id}/events/callbacks

Single-callback URL:

{API_BASE_URL}/events/account/{account_id}/events/callbacks/{resource_id}

The methods map to URLs and HTTP verbs as follows:

Method HTTP verb URL
get GET Single-callback URL
list GET Collection URL
create POST Collection URL
update PUT Single-callback URL
delete DELETE Single-callback URL
resend_verification PUT Single-callback URL
verify PUT Single-callback URL
Request Headers

Every callback request must include:

Authorization: Bearer {access_token}
User-Agent: FreshBooks python sdk/{VERSION} client_id {client_id}

The values come from the owning client. If the client was created with a custom user-agent, the SDK's existing custom-user-agent behavior continues to apply.

POST and PUT requests must also include:

Content-Type: application/json

GET and DELETE requests have no JSON body and must not set Content-Type.

Request Bodies

Callers pass callback fields as an unwrapped dictionary. Requests that carry callback data must place those fields in the Events API's callback envelope.

Create
client.callbacks.create(
    account_id,
    {"event": "invoice.create", "uri": "http://somewhere.test"},
)

uses POST with this JSON document:

{
  "callback": {
    "event": "invoice.create",
    "uri": "http://somewhere.test"
  }
}
Update

update(account_id, resource_id, data) uses PUT and sends:

{ "callback": { "...fields from data...": "..." } }
Resend verification

resend_verification(account_id, resource_id) uses PUT and sends:

{ "callback": { "resend": true } }
Verify

verify(account_id, resource_id, verification_code) uses PUT and sends:

{ "callback": { "verifier": "verification_code" } }

The value of verifier must be the exact verification_code argument supplied by the caller.

Delete

delete(account_id, resource_id) sends a DELETE request with no request-body bytes. Callback deletion is a true DELETE operation, not a soft-delete update.

List Query Builders

list accepts an optional builders list and combines the existing builders' output into the collection request's query string.

Pagination must work with PaginateBuilder. For example:

client.callbacks.list(account_id, builders=[PaginateBuilder(2, 1)])

requests parameters equivalent to:

page=2&per_page=1

Equality filtering must work with FilterBuilder. For example:

f = FilterBuilder()
f.equals("event", "estimate.create")
client.callbacks.list(account_id, builders=[f])

requests this parameter:

search[event]=estimate.create

With builders=None or no builders, no builder query parameters are added.

Successful Single-Callback Responses

get, create, update, resend_verification, and verify consume successful responses shaped as follows:

{
  "response": {
    "result": {
      "callback": {
        "callbackid": 123,
        "verified": true,
        "uri": "http://freshbooks.com/hook/123",
        "event": "invoice.create",
        "updated_at": "2017-08-23T11:45:09Z"
      }
    }
  }
}

Each method returns the SDK's normal single-resource result object, configured with the singular name callback and populated from response.result.callback. Its observable behavior includes:

  • str(result) == "Result(callback)"
  • result.name == "callback"
  • result.data is the raw callback dictionary, not the surrounding response envelopes
  • Every callback field can be read as an attribute, such as result.callbackid, result.event, result.uri, and result.verified

For example, if the response contains callback ID 123, both result.callbackid and result.data["callbackid"] equal 123.

Successful Delete Responses

delete also returns a single-resource result named callback. A successful no-content-style response may contain:

{ "response": {} }

For that response:

  • str(result) == "Result(callback)"
  • result.name == "callback"
  • result.data == {}

This applies to a successful delete response such as HTTP 204 carrying that response envelope.

Successful List Responses

A list response has this structure:

{
  "response": {
    "result": {
      "callbacks": [
        { "callbackid": 123, "event": "invoice.create" },
        { "callbackid": 124, "event": "estimate.create" }
      ],
      "page": 1,
      "pages": 1,
      "per_page": 15,
      "total": 2
    }
  }
}

list returns the SDK's normal list-result object configured with plural name callbacks and singular item name callback. Its observable behavior includes:

  • str(result) == "ListResult(callbacks)"
  • result.name == "callbacks"
  • len(result) is the number of objects in callbacks
  • Iteration yields callback result objects in response order
  • Each yielded item exposes callback fields as attributes, such as item.callbackid
  • Standard list-result indexing and raw data access continue to work
  • result.pages exposes the response's page, pages, per_page, and total metadata; in particular, result.pages.total equals response.result.total

An empty callbacks array therefore produces a zero-length, normally iterable list result.

Events API Error Handling

All callback methods must report response failures through freshbooks.FreshBooksError. The exception retains the SDK's public attributes status_code, error_code, and raw_response, and str(error) is its human-readable message.

Unlike accounting endpoints, Events API errors are not nested under response.errors. They use a top-level envelope such as:

{
  "errno": 404,
  "message": "Requested resource could not be found."
}
Recognized Events API error

When an HTTP failure response is valid JSON and contains errno and message:

  • The raised exception's message is the value of message.
  • error.status_code is the HTTP response status.
  • error.error_code is the value of errno.
  • error.raw_response is the parsed top-level JSON object.

For the example above returned with HTTP 404:

str(error) == "Requested resource could not be found."
error.status_code == 404
error.error_code == 404
error.raw_response == {
    "errno": 404,
    "message": "Requested resource could not be found.",
}
Body cannot be parsed as JSON

If a response body is not valid JSON, raise FreshBooksError with:

  • Message "Failed to parse response"
  • status_code equal to the HTTP response status
  • raw_response equal to the original response text

For an HTTP 500 body of stuff, str(error) is "Failed to parse response" and error.raw_response is "stuff".

Valid JSON has an unexpected success shape

A valid JSON response is still an error if it lacks the structure required by the operation. The expected structures are response.result.callback for a normal single-callback operation and response.result.callbacks for a list operation; the successful delete form described above is the exception.

For an HTTP 200 body such as:

{ "foo": "bar" }

raise FreshBooksError with:

  • Message "Returned an unexpected response"
  • status_code == 200
  • raw_response equal to the original JSON response text, for example '{"foo": "bar"}' with the server's original formatting
Compatibility and Scope

The callback resource must use the SDK's established client configuration, transport headers, builders, result objects, and exception type so it behaves consistently with existing resources. The distinguishing contracts are the /events/account/.../events/callbacks URL family and the Events API's top-level errno/message error envelope. No existing public resource or method is to be removed, renamed, or behaviorally changed.
