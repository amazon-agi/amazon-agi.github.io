02 Implement a set of classes for parsing network packets in the chewie package. 946 words · rewritten by GPT-5.6-sol, reworded by GLM-5.3-Flash

Implement a set of classes for parsing network packets in the chewie package. These classes take binary wire-format data (802.1X/EAP over Ethernet) and parse it into structured objects that expose named attributes.

All byte inputs take the form of raw bytes objects. Parsing methods are class methods that get invoked as ClassName.parse(packed_message). Multi-byte integer fields are decoded using network byte order (big-endian).

1. chewie.mac_address.MacAddress

A value object that represents a 6-byte MAC address.

  • The Class method MacAddress.from_string(mac_str) accepts a colon-separated hexadecimal string such as "00:19:06:ea:b8:8c" and returns a MacAddress instance.
  • Equality must be based on value: when two MacAddress instances represent the same address, they compare equal with ==, whereas instances that represent different addresses compare unequal.

2. chewie.ethernet_packet.EthernetPacket

Handles parsing of an Ethernet II frame.

  • The Class method EthernetPacket.parse(packed_message) accepts a complete Ethernet frame and returns an EthernetPacket instance that exposes:
    • dst_mac — a MacAddress constructed from bytes 0–5.
    • src_mac — a MacAddress constructed from bytes 6–11.
    • ethertype — an int decoded from bytes 12–13. To illustrate, bytes 88 8e produce 0x888e.
    • data — a bytes object that contains all the bytes after the 14-byte Ethernet header. This layer does not strip out any Ethernet payload padding.

Example: for an input that begins with destination 01:80:c2:00:00:03, source 00:19:06:ea:b8:8c, ethertype bytes 88 8e, and then payload bytes, the result has those destination and source addresses, ethertype == 0x888e, and data equal to the complete payload.

3. chewie.auth_8021x.Auth8021x

Handles parsing of an 802.1X/EAPOL packet. The input is the Ethernet payload beginning at the EAPOL header; the 14-byte Ethernet header is not part of it.

The EAPOL layout on the wire is:

  • byte 0: version

  • byte 1: packet type

  • bytes 2–3: payload length, a 2-byte big-endian integer

  • byte 4 onward: payload

  • The Class method Auth8021x.parse(packed_message) returns an Auth8021x instance that exposes:

    • version — an int read from byte 0.
    • packet_type — an int read from byte 1.
    • data — a bytes object that contains exactly the EAPOL payload chosen by the length declared in the header: the bytes from offset 4 up to, but not including, offset 4 + length. Bytes that follow that declared payload, such as Ethernet padding, are not included.

By way of example, parsing the bytes 01 00 00 05 01 01 00 05 01 00 00 00 00 produces version == 1, packet_type == 0, and data == bytes.fromhex("0101000501"). Even though nine bytes follow the EAPOL header in that input, the payload length declared is five, so data has length 5.

4. chewie.eap.Eap

Handles parsing of an EAP packet.

  • Class constants:
    • Eap.REQUEST = 1
    • Eap.RESPONSE = 2
  • The Class method Eap.parse(packed_message) returns an EAP object.

The EAP layout on the wire is:

  • byte 0: code
  • byte 1: packet ID
  • bytes 2–3: length, a 2-byte big-endian integer
  • byte 4: EAP type
  • remaining bytes: type-specific data

The following attribute is exposed by every parsed result:

  • packet_id — an int taken from byte 1.

The concrete result depends on which EAP type sits in byte 4.

Identity (type 0x01)
  • identity — a str decoded as UTF-8/ASCII from the type-specific bytes. When no identity bytes are present, it may be the empty string "".

Example: parsing 01 01 00 05 01 produces packet_id == 1 and identity == "".

MD5 Challenge (type 0x04)

A one-byte value-length field comes first within the type-specific data. The result exposes:

  • challenge — a bytes object containing the following value-length bytes.
  • extra_data — a bytes object containing any type-specific bytes that remain after the challenge. It is b"" when no such bytes remain.

5. chewie.message_parser.MessageParser

Handles parsing of a complete Ethernet frame that carries an 802.1X/EAP message and returns a single flat message object.

  • The Class method MessageParser.parse(packed_message) accepts a full frame made up of a 14-byte Ethernet header, an EAPOL header and its payload, and an EAP packet.
  • The EAP packet is the EAPOL data bounded by its length; bytes beyond the length declared by the EAPOL header are not part of the parsed EAP message.
  • The object that is returned exposes:
    • src_mac — the source MacAddress obtained from the Ethernet header.
    • message_id — an int that equals the EAP packet ID.
    • code — the EAP code, which includes Eap.REQUEST or Eap.RESPONSE.
    • In the case of Identity messages, identity — the decoded identity str, which may be "".
    • In the case of MD5 Challenge messages, challenge and extra_data — bytes values with the semantics defined above.

The parser dispatches on the EAP type: Identity frames yield objects that have an identity attribute, whereas MD5 Challenge frames yield objects that have challenge and extra_data attributes.

Worked examples
  • Identity request: source 00:19:06:ea:b8:8c, code == Eap.REQUEST, message_id == 1, and identity == "".
  • Identity response: source 00:14:22:e9:54:5e, code == Eap.RESPONSE, message_id == 0, and identity == "John.McGuirk".
  • MD5 Challenge request: source 00:19:06:ea:b8:8c, code == Eap.REQUEST, message_id == 1, challenge == bytes.fromhex("824788d693e2adac6ce15641418228cf"), and extra_data == b"". Any frame padding that appears after the declared EAPOL payload does not become extra_data.
  • MD5 Challenge response: source 00:14:22:e9:54:5e, code == Eap.RESPONSE, message_id == 1, challenge == bytes.fromhex("3a535f0ee8c6b34fe714aa7dad9a0e15"), and extra_data == b"John.McGuirk".

Module and class surface required

  • chewie.mac_address provides MacAddress, which includes from_string and value-based equality.
  • chewie.ethernet_packet provides EthernetPacket, which includes parse.
  • chewie.auth_8021x provides Auth8021x, which includes parse.
  • chewie.eap provides Eap, which includes parse and the constants REQUEST and RESPONSE.
  • chewie.message_parser provides MessageParser, which includes parse.

Task Specification: Implementing a Timer Class

Summary

Write a Timer class in a module at chewie/timer.py. The timer keeps track of whether a configured duration has elapsed relative to "tick" values (timestamps) that are supplied externally. The timer itself does not read any clock — the caller passes in all time values.

Public Interface

Module

chewie.timer

Class

Timer

Constructor
Timer(timer_count)
  • timer_count: a numeric value that gives the timer's duration.
  • A timer that has just been constructed is not running.
Methods
running(self)
  • Returns a boolean saying whether the timer is running at the present moment.
  • Returns False for a timer that has just been constructed.
  • Returns True after reset(...) has been called (and the timer has not been stopped since).
  • Returns False once stop() has been called.
reset(self, current_tick)
  • Starts (or restarts) the timer and records current_tick as the timer's start reference point.
  • Once this call has been made, the timer is running.
stop(self)
  • Halts the timer. After this call, the timer is not running.
expired(self, current_tick)
  • Returns a boolean telling whether the timer has expired as of the supplied current_tick.
  • If the timer is not running, False is always returned, no matter what current_tick is.
  • If the timer is running, it counts as expired when the time elapsed since the recorded start reference exceeds timer_count. To be precise, with a start reference start (the current_tick handed to the most recent reset call):
    • Returns False when current_tick <= start + timer_count.
    • Returns True when current_tick > start + timer_count.
    • In particular, at exactly start + timer_count the timer is not expired, while strictly beyond that point it is expired.

Behavioral Notes

  • Before any reset call has happened, expired(...) returns False for all inputs (by default, the timer is off).
  • Once reset(start) has been called:
    • running() returns True.
    • expired(t) returns False when t == start.
    • expired(t) returns False when t == start + timer_count - 1.
    • expired(t) returns True when t == start + timer_count + 1.
  • Once stop() has been called:
    • expired(...) returns False for all inputs, including values that would have been expired while the timer was running.

Worked Example

timer = Timer(60)
timer.running()              # False
timer.expired(10000)         # False (not running)

timer.reset(10000)
timer.running()              # True
timer.expired(10000)         # False
timer.expired(10059)         # False
timer.expired(10061)         # True

timer.stop()
timer.running()              # False
timer.expired(10061)         # False

  • currentState becomes TIMEOUT_FAILURE after exhaustion of the retransmission limit.
Waiting on the AAA/RADIUS Server: Timeout (→ TIMEOUT_FAILURE2)

A timeout callback must be scheduled after a challenge response has been sent by the machine toward the AAA (RADIUS) server and the machine sits in the AAA-idle waiting state. If no RADIUS response shows up:

  • currentState gets transitioned to TIMEOUT_FAILURE2 when the scheduler is run to completion.
  • As a consequence of this timeout, no additional EAP messages and no additional RADIUS messages get enqueued (the counts on both queues remain what they were before the scheduler ran).
Passthrough Mode: Retransmission (→ TIMEOUT_FAILURE2)

In passthrough mode, after the machine has sent a request toward the client — for instance an MD5 challenge request forwarded to the client — and while it is awaiting the client's response, a timeout callback must be scheduled. If no client response shows up:

  • Each expiry of the timeout leads to the packet being retransmitted onto the EAP output queue, with a new timeout rescheduled as well; this continues until the count of transmissions has reached MAX_RETRANS.
  • When the scheduler is run to completion, exactly MAX_RETRANS EAP messages must have been enqueued (with the measurement taken after any pre-timeout output has been cleared from the queue).
  • Over the course of this process, no RADIUS messages are produced.
  • currentState becomes TIMEOUT_FAILURE2 after the retransmission limit has been exhausted.
Disabled and Re-enabled Transitions

The machine must respond to portEnabled changes, with the response driven by received events:

  • From a running state (an Identity request having already been sent, one EAP message enqueued), the machine must transition currentState to DISABLED once portEnabled = False has been set and a received event (EventMessageReceived(None)) has then been delivered. The enqueueing of any additional EAP or RADIUS messages must not happen as part of this transition (EAP queue size remains at 1, RADIUS at 0).
  • Beginning at DISABLED, the machine must transition currentState to IDLE when portEnabled = True is set and another received event (EventMessageReceived(None)) is delivered; in addition, exactly one additional EAP message must be enqueued as a result (EAP queue size goes to 2, RADIUS remains at 0).

Events

Events get consumed by the state machine via self.sm.event(...). As imports, the event types that matter are EventMessageReceived and EventRadiusMessageReceived (they originate in the event module that already exists). EventMessageReceived(None) must work as a valid event that drives re-evaluation of state (the disabled/enabled transitions above make use of it).

Semantics of the Scheduling

  • Placement of timeout callbacks happens on the timer_scheduler that gets provided, and their execution occurs when the scheduler itself is executed (timer_scheduler.run()).
  • Rescheduling follow-up timeouts as needed must be done by the state machine itself, such that a single run() of the scheduler suffices to carry the machine through all retransmissions and then into the terminal timeout-failure state that is appropriate.
  • A pending timeout must not be the cause of spurious retransmission or of an erroneous transition into a timeout-failure state in the case where a valid response arrives before the scheduled timeout fires.

Remarks

  • The service-type value that the machine should use by default as it composes its RADIUS-directed request is one that is appropriate/standard; this has no effect on any of the queue-count or state assertions above, and no externally observable API is needed.
