02 Implement a set of network packet parsing classes for the chewie package. 862 words · rewritten by GPT-5.6-sol

Implement a set of network packet parsing classes for the chewie package. These classes parse binary wire-format data (802.1X/EAP over Ethernet) into structured objects exposing named attributes.

All byte inputs are raw bytes objects. Parsing methods are class methods invoked as ClassName.parse(packed_message). Multi-byte integer fields are decoded in network byte order (big-endian).

1. chewie.mac_address.MacAddress

A value object representing a 6-byte MAC address.

  • Class method MacAddress.from_string(mac_str) accepts a colon-separated hexadecimal string such as "00:19:06:ea:b8:8c" and returns a MacAddress instance.
  • Equality must be value-based: two MacAddress instances representing the same address compare equal with ==, while instances representing different addresses compare unequal.

2. chewie.ethernet_packet.EthernetPacket

Parses an Ethernet II frame.

  • Class method EthernetPacket.parse(packed_message) accepts a complete Ethernet frame and returns an EthernetPacket instance exposing:
    • dst_mac — a MacAddress built from bytes 0–5.
    • src_mac — a MacAddress built from bytes 6–11.
    • ethertype — an int decoded from bytes 12–13. For example, bytes 88 8e produce 0x888e.
    • data — a bytes object containing all bytes after the 14-byte Ethernet header. This layer does not remove any Ethernet payload padding.

Example: for an input beginning with destination 01:80:c2:00:00:03, source 00:19:06:ea:b8:8c, ethertype bytes 88 8e, and then payload bytes, the result has those destination and source addresses, ethertype == 0x888e, and data equal to the complete payload.

3. chewie.auth_8021x.Auth8021x

Parses an 802.1X/EAPOL packet. Its input is the Ethernet payload beginning at the EAPOL header; it does not include the 14-byte Ethernet header.

The EAPOL wire layout is:

  • byte 0: version

  • byte 1: packet type

  • bytes 2–3: payload length, as a 2-byte big-endian integer

  • byte 4 onward: payload

  • Class method Auth8021x.parse(packed_message) returns an Auth8021x instance exposing:

    • version — an int from byte 0.
    • packet_type — an int from byte 1.
    • data — a bytes object containing exactly the EAPOL payload selected by the header's declared length: the bytes from offset 4 through, but not including, offset 4 + length. Bytes following that declared payload, such as Ethernet padding, are not included.

For example, parsing bytes 01 00 00 05 01 01 00 05 01 00 00 00 00 produces version == 1, packet_type == 0, and data == bytes.fromhex("0101000501"). Although nine bytes follow the EAPOL header in that input, the declared payload length is five, so data has length 5.

4. chewie.eap.Eap

Parses an EAP packet.

  • Class constants:
    • Eap.REQUEST = 1
    • Eap.RESPONSE = 2
  • Class method Eap.parse(packed_message) returns an EAP object.

The EAP wire layout is:

  • byte 0: code
  • byte 1: packet ID
  • bytes 2–3: length, as a 2-byte big-endian integer
  • byte 4: EAP type
  • remaining bytes: type-specific data

Every parsed result exposes:

  • packet_id — an int from byte 1.

The concrete result depends on the EAP type in byte 4.

Identity (type 0x01)
  • identity — a str decoded from the type-specific bytes as UTF-8/ASCII. It may be the empty string "" when no identity bytes are present.

Example: parsing 01 01 00 05 01 produces packet_id == 1 and identity == "".

MD5 Challenge (type 0x04)

The type-specific data starts with a one-byte value-length field. The result exposes:

  • challenge — a bytes object containing the next value-length bytes.
  • extra_data — a bytes object containing any type-specific bytes remaining after the challenge. It is b"" when no such bytes remain.

5. chewie.message_parser.MessageParser

Parses a complete Ethernet frame carrying an 802.1X/EAP message and returns a single flat message object.

  • Class method MessageParser.parse(packed_message) accepts a full frame consisting of a 14-byte Ethernet header, an EAPOL header and payload, and an EAP packet.
  • The EAP packet is the length-bounded EAPOL data; bytes beyond the length declared by the EAPOL header are not part of the parsed EAP message.
  • The returned object exposes:
    • src_mac — the source MacAddress from the Ethernet header.
    • message_id — an int equal to the EAP packet ID.
    • code — the EAP code, including Eap.REQUEST or Eap.RESPONSE.
    • For Identity messages, identity — the decoded identity str, which may be "".
    • For MD5 Challenge messages, challenge and extra_data — bytes values with the semantics defined above.

The parser dispatches on the EAP type: Identity frames yield objects with an identity attribute, while MD5 Challenge frames yield objects with challenge and extra_data attributes.

Worked examples
  • Identity request: source 00:19:06:ea:b8:8c, code == Eap.REQUEST, message_id == 1, and identity == "".
  • Identity response: source 00:14:22:e9:54:5e, code == Eap.RESPONSE, message_id == 0, and identity == "John.McGuirk".
  • MD5 Challenge request: source 00:19:06:ea:b8:8c, code == Eap.REQUEST, message_id == 1, challenge == bytes.fromhex("824788d693e2adac6ce15641418228cf"), and extra_data == b"". Any frame padding after the declared EAPOL payload does not become extra_data.
  • MD5 Challenge response: source 00:14:22:e9:54:5e, code == Eap.RESPONSE, message_id == 1, challenge == bytes.fromhex("3a535f0ee8c6b34fe714aa7dad9a0e15"), and extra_data == b"John.McGuirk".

Required module and class surface

  • chewie.mac_address provides MacAddress, including from_string and value-based equality.
  • chewie.ethernet_packet provides EthernetPacket, including parse.
  • chewie.auth_8021x provides Auth8021x, including parse.

Task Specification: Implement a Timer Class

Overview

Create a Timer class in a module located at chewie/timer.py. The timer tracks whether a configured duration has elapsed relative to externally supplied "tick" values (timestamps). The timer does not read any clock itself — all time values are passed in by the caller.

Public API

Module

chewie.timer

Class

Timer

Constructor
Timer(timer_count)
  • timer_count: a numeric value representing the timer's duration.
  • A newly constructed timer is not running.
Methods
running(self)
  • Returns a boolean indicating whether the timer is currently running.
  • Returns False for a freshly constructed timer.
  • Returns True after reset(...) has been called (and not subsequently stopped).
  • Returns False after stop() has been called.
reset(self, current_tick)
  • Starts (or restarts) the timer, recording current_tick as the timer's start reference point.
  • After this call, the timer is running.
stop(self)
  • Stops the timer. After this call, the timer is not running.
expired(self, current_tick)
  • Returns a boolean indicating whether the timer has expired as of the given current_tick.
  • If the timer is not running, always returns False regardless of current_tick.
  • If the timer is running, the timer is considered expired when the elapsed time since the recorded start reference exceeds timer_count. Specifically, given a start reference start (the current_tick passed to the most recent reset):
    • Returns False when current_tick <= start + timer_count.
    • Returns True when current_tick > start + timer_count.
    • In particular, at exactly start + timer_count the timer is not expired; strictly beyond that point it is expired.

Behavioral Details

  • Before any reset call, expired(...) returns False for all inputs (the timer is off by default).
  • After reset(start):
    • running() returns True.
    • expired(t) returns False for t == start.
    • expired(t) returns False for t == start + timer_count - 1.
    • expired(t) returns True for t == start + timer_count + 1.
  • After stop():
    • expired(...) returns False for all inputs, including values that would have been expired while running.

Example

timer = Timer(60)
timer.running()              # False
timer.expired(10000)         # False (not running)

timer.reset(10000)
timer.running()              # True
timer.expired(10000)         # False
timer.expired(10059)         # False
timer.expired(10061)         # True

timer.stop()
timer.running()              # False
timer.expired(10061)         # False

When Eap.parse receives a packed EAP message:

  • If the code byte is 4 (Failure), return an EapFailure instance whose packet_id equals the packet id byte from the message.

  • 04010004 → EapFailure with packet_id == 1

Overview

You must modify the FullEAPStateMachine class (importable as FullEAPStateMachine, currently constructed with output queues and a source MAC) to support scheduled retransmission of unanswered packets and transitions to timeout-failure states when retransmission limits are exceeded or expected responses never arrive.

Constructor Change

FullEAPStateMachine must accept a new positional argument: a timer scheduler.

New signature:

FullEAPStateMachine(eap_output_queue, radius_output_queue, src_mac, timer_scheduler)
  • eap_output_queue — a queue.Queue where outgoing EAP messages are placed.
  • radius_output_queue — a queue.Queue where outgoing RADIUS messages are placed.
  • src_mac — a MacAddress.
  • timer_scheduler — a sched.scheduler instance (created with time.time and time.sleep). The state machine must schedule timeout callbacks on this scheduler using relative delays.

Configurable Attributes

The instance must expose the following attributes, which tests may override after construction:

  • MAX_RETRANS — integer maximum number of times a packet is (re)transmitted before the machine moves to a timeout-failure state.
  • DEFAULT_TIMEOUT — float number of seconds used as the delay when scheduling a timeout/retransmission callback.

These must be honored as the actual values driving behavior (i.e., overriding them changes how many retransmissions occur and the scheduling delay).

Required State Constants

The instance must expose these state identifiers as attributes, and currentState must be settable to / comparable against them:

  • self.sm.DISABLED
  • self.sm.IDLE
  • self.sm.AAA_IDLE
  • self.sm.TIMEOUT_FAILURE
  • self.sm.TIMEOUT_FAILURE2

Message Output Format

When a message is placed on eap_output_queue, the enqueued item must be indexable such that element [0] is the message object. That message object must expose a .message_id attribute. (In other words, items on the EAP output queue are tuples/sequences whose first element is the EAP message.)

Behavior Requirements

Existing baseline (unchanged expectations)
  • With portEnabled = True and eapRestart = True, starting the machine produces exactly one EAP output message, an IdentityMessage (Identity request), and nothing on the RADIUS output queue.
  • When an identity response (IdentityMessage with Eap.RESPONSE) whose message_id matches the outstanding request's message_id is received, the machine transitions to AAA_IDLE.
Retransmission from the identity-request state (→ TIMEOUT_FAILURE)

After the machine has sent an Identity request and is awaiting a client response, a timeout callback must be scheduled on timer_scheduler. When no response arrives:

  • On each timeout expiry, the same Identity request packet is retransmitted (re-enqueued onto the EAP output queue) and another timeout is rescheduled, until the number of transmissions reaches MAX_RETRANS.
  • Running the scheduler to completion must result in exactly MAX_RETRANS total EAP messages having been enqueued (the original send plus retransmissions counting to MAX_RETRANS total items on the queue).
  • All these enqueued EAP messages must be IdentityMessage instances and must be equal to one another (identical retransmitted packet).
  • No RADIUS messages are produced during this process.
  • After the retransmission limit is exhausted, currentState becomes TIMEOUT_FAILURE.
Timeout waiting on AAA/RADIUS server (→ TIMEOUT_FAILURE2)

After the machine has sent a challenge response toward the AAA (RADIUS) server and is in the AAA-idle waiting state, a timeout callback must be scheduled. If no RADIUS response arrives:

  • Running the scheduler to completion transitions currentState to TIMEOUT_FAILURE2.
  • No additional EAP messages and no additional RADIUS messages are enqueued as a result of this timeout (the counts on both queues remain unchanged from before the scheduler ran).
Retransmission in passthrough mode (→ TIMEOUT_FAILURE2)

After the machine has, in passthrough mode, sent a request toward the client (e.g., an MD5 challenge request forwarded to the client) and is awaiting the client's response, a timeout callback must be scheduled. When no client response arrives:

  • On each timeout expiry the packet is retransmitted onto the EAP output queue and a new timeout rescheduled, until the transmission count reaches MAX_RETRANS.
  • Running the scheduler to completion must result in exactly MAX_RETRANS EAP messages having been enqueued (measured after clearing the queue of any pre-timeout output).
  • No RADIUS messages are produced during this process.
  • After the retransmission limit is exhausted, currentState becomes TIMEOUT_FAILURE2.
Disabled / re-enabled transitions

The machine must respond to portEnabled changes driven by received events:

  • Starting from a running state (Identity request already sent, one EAP message enqueued), setting portEnabled = False and then delivering a received event (EventMessageReceived(None)) must transition currentState to DISABLED. This transition must not enqueue any additional EAP or RADIUS messages (EAP queue size stays at 1, RADIUS at 0).
  • From DISABLED, setting portEnabled = True and delivering another received event (EventMessageReceived(None)) must transition currentState to IDLE, and must cause exactly one additional EAP message to be enqueued (EAP queue size becomes 2, RADIUS stays at 0).

Events

The state machine consumes events via self.sm.event(...). The relevant event types are imported as EventMessageReceived and EventRadiusMessageReceived (from the existing event module). EventMessageReceived(None) must be a valid event that drives state re-evaluation (used for the disabled/enabled transitions above).

  • Timeout callbacks are placed on the provided timer_scheduler and run when the scheduler is executed (timer_scheduler.run()).
  • The state machine itself must reschedule follow-up timeouts as needed so that a single run() of the scheduler drives the machine through all retransmissions and into the appropriate terminal timeout-failure state.
  • When a valid response is received before a scheduled timeout fires, that pending timeout must not cause spurious retransmission or an erroneous timeout-failure transition.

  • The default service-type value used by the machine when composing its RADIUS-directed request should be an appropriate/standard service-type value; this does not affect any of the queue-count or state assertions above and needs no externally observable API.
