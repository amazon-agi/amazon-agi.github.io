01 Central Control Diagnostic Sensors 802 words · source specification

Task Specification: Central Control Diagnostic Sensors

Overview

Extend the CSNetHomeInstallationSensor class (in the sensor module of the csnet_home integration) to support four new diagnostic sensor types related to a heat pump's central control configuration. The class must correctly report state values for each new sensor type based on data from the installation devices coordinator.

Public API Surface

Class: CSNetHomeInstallationSensor

The class must be constructible with the following positional arguments, in this order:

CSNetHomeInstallationSensor(
    coordinator,        # object exposing get_installation_devices_data()
    device_data,        # dict with device metadata
    common_data,        # dict with common metadata
    sensor_type,        # str identifying which sensor this is
    device_class,       # str or None
    unit_of_measurement,# (this position); may be None
    display_name,       # str, human-readable label
)
  • coordinator provides a method get_installation_devices_data() returning either a data dictionary, an empty dict, or None.
  • device_data contains keys including device_name, device_id, room_name, parent_id, room_id.
  • common_data contains keys including name and firmware.

The following read-only properties must be available on instances: state, name, unique_id, device_class.

Data Source

The installation data returned by get_installation_devices_data() has this shape when populated:

{
    "data": [
        {
            "indoors": [
                {
                    "heatingStatus": {
                        "centralConfig": <int>,
                        "lcdSoft": <int or None>,
                        "unitModel": <int>,
                    }
                }
            ]
        }
    ]
}

All four new sensors read their values from data[0]["indoors"][0]["heatingStatus"]. The data may be missing (None), empty ({}), or contain an indoors entry with no heatingStatus key. In such cases the state behavior for the binary sensor is defined below.

Sensor Types and state Behavior

The sensor_type argument selects which diagnostic sensor is implemented. Behavior of the state property is as follows.

1. central_config
  • device_class is "enum".
  • Reads the integer at heatingStatus["centralConfig"].
  • Maps the value to a human-readable string:
    • 0 → "Unit Only"
    • 1 → "RT Only"
    • 2 → "Unit & RT"
    • 3 → "Total Control"
    • 4 → "Total Control+"
  • When the value is less than 3, append a space and the warning emoji ⚠️ to the string (e.g., "Unit Only ⚠️", "RT Only ⚠️", "Unit & RT ⚠️").
  • When the value is 3 or 4, no warning emoji is appended.
  • For any unrecognized value, the resulting string must contain the substring "Unknown".
2. lcd_software_version
  • device_class is None.
  • Reads heatingStatus["lcdSoft"].
  • If the value is a positive integer, format it as a lowercase hexadecimal string prefixed with 0x, zero-padded to at least four hex digits. Examples:
    • 546 → "0x0222"
    • 768 → "0x0300"
  • If the value is 0, the state is the integer 0 (not a string).
  • If the value is None, the state is None.
3. unit_model
  • device_class is "enum".
  • Reads the integer at heatingStatus["unitModel"].
  • Maps the value to a model name:
    • 0 → "Yutaki S"
    • 1 → "Yutaki SC"
    • 2 → "Yutaki S80"
    • 3 → "Yutaki M"
    • 4 → "Yutaki SC Lite"
    • 5 → "Yutampo"
  • For any unrecognized value, the resulting string must contain the substring "Unknown".
4. central_control_enabled
  • device_class is "binary".
  • Returns one of two string constants: the module-level "on" state value (STATE_ON) or the "off" state value (STATE_OFF), consistent with Home Assistant conventions ("on" / "off").
  • Determination logic, using centralConfig, unitModel, and lcdSoft from heatingStatus:
    1. If centralConfig >= 3, the state is STATE_ON.
    2. Otherwise, if unitModel != 2 (i.e., not the Yutaki S80 model, which corresponds to code 2):
      • If lcdSoft == 0, the state is STATE_ON.
      • Else if lcdSoft >= 546 (i.e., >= 0x0222), the state is STATE_ON.
      • Otherwise, the state is STATE_OFF.
    3. Otherwise (centralConfig < 3 and unitModel == 2), the state is STATE_OFF.
  • Missing-data handling: if get_installation_devices_data() returns None, an empty dict, or a structure lacking a heatingStatus entry, the state is STATE_OFF.

Example outcomes:

  • centralConfig=3, unitModel=0, lcdSoft=546 → STATE_ON
  • centralConfig=2, unitModel=0, lcdSoft=546 → STATE_ON
  • centralConfig=2, unitModel=0, lcdSoft=0 → STATE_ON
  • centralConfig=2, unitModel=0, lcdSoft=500 → STATE_OFF
  • centralConfig=2, unitModel=2, lcdSoft=546 → STATE_OFF
  • centralConfig=4, unitModel=2 → STATE_ON

Metadata Properties

For all four new sensor types, the following properties must hold given device_data with device_name="Installation" and room_name="Global":

  • name = "Installation Global <display_name>" where <display_name> is the display_name argument. Examples:
    • "Installation Global Central Config"
    • "Installation Global LCD Software Version"
    • "Installation Global Unit Model"
    • "Installation Global Central Control Enabled"
  • unique_id = "csnet_home-installation-<sensor_type>". Examples:
    • "csnet_home-installation-central_config"
    • "csnet_home-installation-lcd_software_version"
    • "csnet_home-installation-unit_model"
    • "csnet_home-installation-central_control_enabled"
  • device_class returns exactly the device_class argument passed to the constructor ("enum", "binary", or None as applicable).

Notes

  • The state constants STATE_ON and STATE_OFF must be importable alongside the sensor class from the same module namespace used by callers.
  • Existing sensor behavior of CSNetHomeInstallationSensor (for other sensor types) must remain unchanged; the new sensor types are additive.

04 Circuit-Aware Heating Control Parameters 608 words · source specification

Task Specification: Circuit-Aware Heating Control Parameters

Overview

Modify the CSNet Home API client so that heating on/off (HVAC mode) commands and preset mode commands send the correct circuit-specific parameter names, distinguishing between "air" circuits and "water" circuits, and mapping a specific zone to a different circuit number.

Public API Surface

The following must exist and be importable:

  • Module containing the class CSNetHomeAPI.
  • Constructor: CSNetHomeAPI(hass, username, password) — accepts a Home Assistant object and two string credentials (username, password).
  • Instance attributes that can be assigned after construction:
    • session — the HTTP client used to make POST requests.
    • logged_in — boolean flag.
    • xsrf_token — string token.
    • cookies — dict of cookies.
  • Async method: async_set_hvac_mode(zone_id, device_id, hvac_mode) → returns True on success.
  • Async method: set_preset_modes(zone_id, device_id, preset_mode, current_mode, on_off) → returns True on success. current_mode and on_off are keyword-capable parameters.

Required Behavior

Both methods issue an HTTP POST via session.post(...). The payload dictionary is passed as the data keyword argument to post. The request is considered successful when the HTTP response has status 200 and yields a JSON success body; on success the methods return True.

Circuit Number Mapping

When constructing parameter names, the circuit number is derived from zone_id:

  • zone_id == 5 → use circuit number 1.
  • Any other zone_id → use the zone_id value itself as the circuit number.

Consequently, no parameter names containing C5 are ever produced for zone_id == 5.

Air vs. Water Circuits
  • zone_id == 5 is a water circuit.
  • All other zones are air circuits.

For a water circuit, the run/stop parameter name is runStopC{circuit} (no Air suffix), and the Air variant must NOT be present.

For an air circuit, the run/stop parameter name is runStopC{circuit}Air, and the non-Air variant must NOT be present.

Only the parameter appropriate to the circuit type is included in the payload — never both.

async_set_hvac_mode Behavior

The hvac_mode value is compared case-insensitively.

Turning ON (hvac_mode is "heat" or "cool"):

  • Include a mode parameter:
    • "heat" → mode = "1".
    • "cool" → mode = "0".
  • Set the appropriate run/stop parameter (per air/water rules above) to "1".

Turning OFF (hvac_mode is "off"):

  • Set the appropriate run/stop parameter (per air/water rules above) to "0".
  • Do NOT include a mode parameter.

Examples of resulting payload contents:

  • async_set_hvac_mode(5, ..., "heat") → runStopC1 == "1"; no runStopC1Air; no runStopC5/runStopC5Air.
  • async_set_hvac_mode(1, ..., "heat") → runStopC1Air == "1"; no runStopC1.
  • async_set_hvac_mode(2, ..., "cool") → runStopC2Air == "1", mode == "0"; no runStopC2.
  • async_set_hvac_mode(5, ..., "off") → runStopC1 == "0"; no runStopC1Air; no mode.
  • async_set_hvac_mode(1, ..., "off") → runStopC1Air == "0"; no runStopC1; no mode.
set_preset_modes Behavior

Include an eco-mode parameter named ecoModeC{circuit}, whose value encodes the preset:

  • "comfort" → "1".
  • "eco" → a value distinct from comfort (comfort maps to "1"; eco must be different).

Additionally, set the appropriate run/stop parameter (per the air/water rules above), using the value "1" when the zone is on.

Examples of resulting payload contents:

  • set_preset_modes(5, ..., "eco", current_mode=1, on_off=1) → contains ecoModeC1; runStopC1 == "1"; no runStopC1Air; no ecoModeC5.
  • set_preset_modes(1, ..., "comfort", current_mode=1, on_off=1) → ecoModeC1 == "1"; runStopC1Air == "1"; no runStopC1.

Summary of Constraints

  • Circuit number = 1 for zone_id == 5, otherwise equals zone_id.
  • Water circuit (zone_id == 5): only the non-Air run/stop parameter is included.
  • Air circuit (all other zones): only the Air run/stop parameter is included.
  • mode is only present when turning on via async_set_hvac_mode.
  • Both methods return True on a successful (status 200) POST.

Task: Add AUTO HVAC Mode Support to CSNet Home Integration

Overview

The CSNet Home integration currently supports HEAT, COOL, and OFF HVAC modes. You must add support for an AUTO mode, which maps to HVACMode.HEAT_COOL in Home Assistant and to device mode value 2 in the CSNet API. Two files are involved: the climate entity and the API client.

Requirements

1. Climate Entity — hvac_mode property

The climate entity determines its current HVAC mode from two internal state values: an on/off flag and a numeric mode value.

  • When the device is on (on/off flag = 1) and the mode value is 2, the hvac_mode property must return HVACMode.HEAT_COOL.
  • The existing behavior for other modes (e.g. mode=1 → HEAT, mode=0 → COOL) must remain unchanged.
2. Climate Entity — async_turn_on method

When the device is turned on via async_turn_on(), the entity must restore the last-known mode by calling the API's async_set_hvac_mode method.

  • The async_set_hvac_mode call is made positionally, where the third positional argument (index 2) is the HVAC mode to restore.
  • When the last-known numeric mode value is 2, the restored HVAC mode passed to the API must be HVACMode.HEAT_COOL.
  • The existing restore behavior for other modes (mode=1 → HVACMode.HEAT, mode=0 → HVACMode.COOL) must remain unchanged.
3. API Client — async_set_hvac_mode method

The API client class CSNetHomeAPI has an async method with the signature:

async def async_set_hvac_mode(self, zone_id, <element_id>, hvac_mode)

It is called as api.async_set_hvac_mode(zone_id, <element_id>, "heat_cool") where the HVAC mode is passed as the string "heat_cool".

When invoked with the HVAC mode string "heat_cool", the method must:

  • Send an HTTP POST request (via the client's session.post) whose form payload (the data keyword argument) contains the key mode set to the string "2".
  • Determine the circuit type from zone_id:
    • Air circuits (e.g. zone_id = 1): The payload must include the key runStopC1Air set to "1", and must NOT include the key runStopC1.
    • Water circuits (e.g. zone_id = 5): The payload must include the key runStopC1 set to "1", and must NOT include the key runStopC1Air.
  • Return True on a successful request (HTTP status 200).

The existing behavior for other HVAC modes must remain unchanged.

API Surface

  • Module for the API client must expose class CSNetHomeAPI, constructed as CSNetHomeAPI(hass, username, password), with attributes session, logged_in, xsrf_token, and cookies that can be assigned after construction, and the async method async_set_hvac_mode(zone_id, element_id, hvac_mode).
  • The climate entity must expose the property hvac_mode and the async method async_turn_on().
  • The climate entity's supported HVAC modes must include HVACMode.HEAT_COOL.

    • model is the status model/name followed by " Remote Controller", for example "Hitachi PAC Remote Controller".
    • sw_version is the firmware string, for example "1.0.0".
    • identifiers is a set containing (DOMAIN, name), for example (DOMAIN, "Hitachi PAC-Living").
  • If firmware is absent, sw_version is None; access must not raise.
  • If nested device status/model information is absent, model is "Unknown Remote Controller" and sw_version is None; access must not raise.
  • If sensor_data omits the device and room names, their respective fallbacks are "Unknown Device" and "Unknown Room", so device_info["name"] is "Unknown Device-Unknown Room".
  • Device metadata may be supplied directly at construction or later as a nested device_status mapping keyed by device ID. After such an update, device_info must still report the same composed name and model and expose the updated firmware, such as "2.0.0".

3. Climate fan-mode changes and local state synchronization

CSNetHomeClimate.async_set_fan_mode must retain the distinction between non-fan-coil silent-mode control and fan-coil speed control. Local per-zone sensor data must be changed only after the corresponding API operation succeeds.

3.1 Non-fan-coil systems

The supported Home Assistant fan modes continue to represent normal and silent operation:

  • FAN_ON means silent mode enabled.
  • FAN_AUTO means silent mode disabled/normal operation.

The method must call async_set_silent_mode(zone_id, parent_id, enabled) with enabled=True for FAN_ON and enabled=False for FAN_AUTO. On a successful response it must both expose the requested fan mode and synchronize the raw local state:

  • FAN_ON sets sensor_data["silent_mode"] to integer 1.
  • FAN_AUTO sets sensor_data["silent_mode"] to integer 0.
3.2 Fan-coil systems

Fan-coil mode changes use the entity's configured fan-speed mapping. With the standard mapping, the required values are:

Fan mode Numeric speed
"off" 0
"low" 1
"medium" 2
"auto" 3

Existing legacy fan-coil mapping behavior remains supported when legacy control is configured.

For zone 1, use circuit 1; for zone 2, use circuit 2. For a valid and available mode, call:

async_set_fan_speed(zone_id, parent_id, numeric_speed, circuit)

After a successful response, expose the requested fan mode and store the same numeric speed in the circuit-specific local field:

  • circuit 1: sensor_data["fan1_speed"]
  • circuit 2: sensor_data["fan2_speed"]

Thus, for example, setting zone 1 to "low" stores 1 in fan1_speed, while setting zone 2 to "low" stores 1 in fan2_speed. Unsupported fan modes must not issue a fan-speed request. Existing fan-control availability checks remain in effect, and unsuccessful or rejected operations must not be reported as successful local changes.

4. Generic sensor construction with sparse metadata

The public CSNetHomeSensor class in custom_components/csnet_home/sensor.py must be constructible when sensor_data omits device_name, room_name, or both. Construction and device_info access must not raise KeyError in this case.

Use the externally visible metadata fallbacks "Unknown Device" and "Unknown Room" wherever those missing values are used to compose the entity's initial name and device name. In particular, when both are absent:

device_info["name"] == "Unknown Device-Unknown Room"

Complete-data behavior, including the existing device/room/key entity-name composition, is unchanged.

5. Installation-sensor percentage state

In custom_components/csnet_home/sensor.py, CSNetHomeInstallationSensor.state must expose percentage-based installation values, including pump speed, as the raw percentage reported by the API. Do not convert these values from percentages to fractions.

This applies whether the value is available directly or under the nested installation-device/heating-status structure:

  • A reported pump speed of 100% produces .state == 100, not 1.0.
  • A nested reported pump speed of 80% produces .state == 80, not 0.8.

Existing metadata behavior is unchanged. For example, an entity configured with unit "m/s", controller name "System Controller", and label "Pump Speed" continues to expose that unit and the name "System Controller Pump Speed".

6. Compressor secondary-cycle data and signed-byte temperatures

In custom_components/csnet_home/sensor.py, CSNetHomeCompressorSensor must obtain secondCycle from inside the applicable individual indoors[...] entry, alongside that indoor entry's heatingStatus. It must not read secondary-cycle values from an outer installation/device level.

The secondary-cycle dischargeTemp and suctionTemp fields are unsigned-byte representations of signed Celsius values. Their sensor states must use the module-level helper:

_convert_unsigned_to_signed_byte(value)

For integer byte values, 0 through 127 remain unchanged and 128 through 255 are converted by subtracting 256. Consequently:

  • dischargeTemp == 254 is exposed as -2 °C.
  • suctionTemp == 128 is exposed as -128 °C.

None and non-integer values continue to pass through unchanged.
