Task Specification: Diagnostic Sensors for Central Control

Summary

The CSNetHomeInstallationSensor class (in the sensor module of the csnet_home integration) must be extended to support four new diagnostic sensor types that relate to a heat pump's central control configuration. For each new sensor type, the class must report state values correctly based on data supplied by the installation devices coordinator.

Public API

The CSNetHomeInstallationSensor class

Construction of the class must be possible with the following positional arguments, in this order:

CSNetHomeInstallationSensor(
    coordinator,        # object exposing get_installation_devices_data()
    device_data,        # dict with device metadata
    common_data,        # dict with common metadata
    sensor_type,        # str identifying which sensor this is
    device_class,       # str or None
    unit_of_measurement,# (this position); may be None
    display_name,       # str, human-readable label
)
  • coordinator offers a method get_installation_devices_data() that returns either a data dictionary, an empty dict, or None.
  • device_data has keys including device_name, device_id, room_name, parent_id, room_id.
  • common_data has keys including name and firmware.

Instances must make the following read-only properties available: state, name, unique_id, device_class.

Source of the Data

When populated, the installation data that get_installation_devices_data() returns has the following shape:

{
    "data": [
        {
            "indoors": [
                {
                    "heatingStatus": {
                        "centralConfig": <int>,
                        "lcdSoft": <int or None>,
                        "unitModel": <int>,
                    }
                }
            ]
        }
    ]
}

The values for all four new sensors are read from data[0]["indoors"][0]["heatingStatus"]. The data may be absent (None), may be empty ({}), or may contain an indoors entry that has no heatingStatus key. For those cases, the state behavior of the binary sensor is defined below.

Sensor Types and How state Behaves

The diagnostic sensor being implemented is selected by the sensor_type argument. The state property behaves as follows.

1. central_config
  • device_class is "enum".
  • The integer at heatingStatus["centralConfig"] is read.
  • The value is mapped to a human-readable string:
    • 0 → "Unit Only"
    • 1 → "RT Only"
    • 2 → "Unit & RT"
    • 3 → "Total Control"
    • 4 → "Total Control+"
  • When the value is less than 3, a space plus the warning emoji ⚠️ is appended to the string (e.g., "Unit Only ⚠️", "RT Only ⚠️", "Unit & RT ⚠️").
  • When the value is 3 or 4, no warning emoji is appended.
  • For any value that is not recognized, the resulting string must contain the substring "Unknown".
2. lcd_software_version
  • device_class is None.
  • heatingStatus["lcdSoft"] is read.
  • If the value is a positive integer, it is formatted as a lowercase hexadecimal string prefixed with 0x, zero-padded to at least four hex digits. Examples:
    • 546 → "0x0222"
    • 768 → "0x0300"
  • A value of 0 means the state is the integer 0 (not a string).
  • A value of None means the state is None.
3. unit_model
  • device_class is "enum".
  • The integer at heatingStatus["unitModel"] is read.
  • The value is mapped to a model name:
    • 0 → "Yutaki S"
    • 1 → "Yutaki SC"
    • 2 → "Yutaki S80"
    • 3 → "Yutaki M"
    • 4 → "Yutaki SC Lite"
    • 5 → "Yutampo"
  • For any value that is not recognized, the resulting string must contain the substring "Unknown".
4. central_control_enabled
  • device_class is "binary".
  • The value returned is one of two string constants: the module-level "on" state value (STATE_ON) or the "off" state value (STATE_OFF), consistent with Home Assistant conventions ("on" / "off").
  • The state is determined using centralConfig, unitModel, and lcdSoft from heatingStatus:
    1. The state is STATE_ON when centralConfig >= 3.
    2. Otherwise, if unitModel != 2 (i.e., the model is not Yutaki S80, which corresponds to code 2):
      • The state is STATE_ON when lcdSoft == 0.
      • Otherwise, when lcdSoft >= 546 (i.e., >= 0x0222), the state is STATE_ON.
      • The state is STATE_OFF otherwise.
    3. Otherwise (with centralConfig < 3 and unitModel == 2), the state is STATE_OFF.
  • Handling of missing data: if get_installation_devices_data() returns None, an empty dict, or a structure lacking a heatingStatus entry, the state is STATE_OFF.

Examples of outcomes:

  • centralConfig=3, unitModel=0, lcdSoft=546 → STATE_ON
  • centralConfig=2, unitModel=0, lcdSoft=546 → STATE_ON
  • centralConfig=2, unitModel=0, lcdSoft=0 → STATE_ON
  • centralConfig=2, unitModel=0, lcdSoft=500 → STATE_OFF
  • centralConfig=2, unitModel=2, lcdSoft=546 → STATE_OFF
  • centralConfig=4, unitModel=2 → STATE_ON

Metadata-Related Properties

Given device_data with device_name="Installation" and room_name="Global", the following properties must hold for all four new sensor types:

  • name = "Installation Global <display_name>", with <display_name> being the display_name argument. Examples:
    • "Installation Global Central Config"
    • "Installation Global LCD Software Version"
    • "Installation Global Unit Model"
    • "Installation Global Central Control Enabled"
  • unique_id = "csnet_home-installation-<sensor_type>". Examples:
    • "csnet_home-installation-central_config"
    • "csnet_home-installation-lcd_software_version"
    • "csnet_home-installation-unit_model"
    • "csnet_home-installation-central_control_enabled"
  • device_class returns exactly the device_class argument supplied to the constructor ("enum", "binary", or None as applicable).

Additional Notes

  • The state constants STATE_ON and STATE_OFF must be importable alongside the sensor class from the same module namespace that callers use.
  • Sensor behavior that already exists on CSNetHomeInstallationSensor (for other sensor types) must remain unchanged; the new sensor types are additive.

Overview

  1. Element records that lack a device name must use Remote.

    • csnet_home-installation-unit_model
    • csnet_home-installation-central_control_enabled

  • The sixth constructor argument is returned by unit_of_measurement unchanged, with None included. For example, a pump-speed sensor constructed with m/s reports m/s.

The element device-name fallback and the installation-level naming/model metadata are the only changes. Regular sensor or climate entity model strings, installation sensor keys, unique IDs, units, device classes, state lookup, conversions, or central-control calculations must not be altered.

Task Specification: Circuit-Specific Heating Control Parameters

Overview

Adjust the CSNet Home API client so that the heating on/off (HVAC mode) commands and the preset mode commands send the correct circuit-specific parameter names, telling "air" circuits apart from "water" circuits, and mapping one particular zone to a different circuit number.

Public API

The items below must exist and be importable:

  • A module that contains the class CSNetHomeAPI.
  • Constructor: CSNetHomeAPI(hass, username, password) — accepts a Home Assistant object plus two string credentials (username, password).
  • Attributes on the instance that can be assigned after construction:
    • session — the HTTP client through which POST requests are made.
    • logged_in — a boolean flag.
    • xsrf_token — a string token.
    • cookies — a dict of cookies.
  • Async method: async_set_hvac_mode(zone_id, device_id, hvac_mode) → returns True when the call succeeds.
  • Async method: set_preset_modes(zone_id, device_id, preset_mode, current_mode, on_off) → returns True when the call succeeds. current_mode and on_off are parameters that can be passed by keyword.

Behavior Requirements

Both methods send an HTTP POST through session.post(...). The payload dictionary is supplied to post as the data keyword argument. The request counts as successful when the HTTP response has status 200 and yields a JSON success body; on success the methods return True.

Mapping of Circuit Numbers

When the parameter names are built, the circuit number is derived from zone_id:

  • when zone_id == 5, use circuit number 1.
  • for any other zone_id, use the zone_id value itself as the circuit number.

As a result, for zone_id == 5, no parameter names that contain C5 are ever produced.

The Distinction Between Air and Water Circuits
  • A zone with zone_id == 5 is a water circuit.
  • Every other zone is an air circuit.

In the water case, the run/stop parameter name is runStopC{circuit} (no Air suffix), and the Air variant must NOT be present.

In the air case, the run/stop parameter name is runStopC{circuit}Air, and the non-Air variant must NOT be present.

The payload includes only the parameter that matches the circuit type — never both.

Behavior of async_set_hvac_mode

The hvac_mode value is compared without regard to case.

Switching ON (hvac_mode is "heat" or "cool"):

  • A mode parameter must be included:
    • for "heat", mode = "1".
    • for "cool", mode = "0".
  • Set the appropriate run/stop parameter (as per the air/water rules above) to "1".

Switching OFF (hvac_mode is "off"):

  • Set the appropriate run/stop parameter (as per the air/water rules above) to "0".
  • A mode parameter must NOT be included.

Examples of the payload contents that result:

  • async_set_hvac_mode(5, ..., "heat") → the payload has runStopC1 == "1", has no runStopC1Air, and has no runStopC5/runStopC5Air.
  • async_set_hvac_mode(1, ..., "heat") → the payload has runStopC1Air == "1" and no runStopC1.
  • async_set_hvac_mode(2, ..., "cool") → the payload has runStopC2Air == "1" and mode == "0", with no runStopC2.
  • async_set_hvac_mode(5, ..., "off") → the payload has runStopC1 == "0", has no runStopC1Air, and has no mode.
  • async_set_hvac_mode(1, ..., "off") → the payload has runStopC1Air == "0", has no runStopC1, and has no mode.
Behavior of set_preset_modes

Add an eco-mode parameter named ecoModeC{circuit}, with a value that encodes the preset:

  • "comfort" maps to "1".
  • "eco" maps to a value distinct from comfort (comfort maps to "1"; eco must be different).

Also set the appropriate run/stop parameter (as per the air/water rules above), using "1" as its value when the zone is on.

Examples showing the payload contents that result:

  • set_preset_modes(5, ..., "eco", current_mode=1, on_off=1) → the payload contains ecoModeC1, has runStopC1 == "1", and has no runStopC1Air or ecoModeC5.
  • set_preset_modes(1, ..., "comfort", current_mode=1, on_off=1) → the payload has ecoModeC1 == "1" and runStopC1Air == "1", with no runStopC1.

Constraint Summary

  • The circuit number is 1 for zone_id == 5 and otherwise equals zone_id.
  • For the water circuit (zone_id == 5), the non-Air run/stop parameter is the only one included.
  • For the air circuit (all other zones), the Air run/stop parameter is the only one included.
  • mode only appears when turning on via async_set_hvac_mode.
  • On a successful (status 200) POST, both methods return True.

Task: Add Support for the AUTO HVAC Mode in the CSNet Home Integration

Summary

At the moment, the CSNet Home integration supports the HEAT, COOL, and OFF HVAC modes. You must add support for an AUTO mode, which corresponds to HVACMode.HEAT_COOL in Home Assistant and to device mode value 2 in the CSNet API. The work involves two files: the climate entity and the API client.

Requirements

1. Climate entity: the hvac_mode property

The climate entity derives its current HVAC mode from two internal state values: an on/off flag and a numeric mode value.

  • If the device is on (on/off flag = 1) and the mode value is 2, the hvac_mode property must return HVACMode.HEAT_COOL.
  • For other modes (e.g. mode=1 → HEAT, mode=0 → COOL), the existing behavior must remain unchanged.
2. Climate entity: the async_turn_on method

When the device is turned on via async_turn_on(), the entity must call the API's async_set_hvac_mode method in order to restore the last-known mode.

  • The call to async_set_hvac_mode is made positionally; the HVAC mode to restore is its third positional argument (index 2).
  • If the last-known numeric mode value is 2, then HVACMode.HEAT_COOL is the restored HVAC mode that must be passed to the API.
  • For other modes (mode=1 → HVACMode.HEAT, mode=0 → HVACMode.COOL), the existing restore behavior must remain unchanged.
3. API client: the async_set_hvac_mode method
