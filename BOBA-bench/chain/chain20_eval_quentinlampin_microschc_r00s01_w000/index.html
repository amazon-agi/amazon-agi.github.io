Field matching behavior

For corresponding packet and rule fields:

  • MatchingOperator.EQUAL matches when the packet field value equals the rule target value and does not match when those values differ.
  • MatchingOperator.MSB with a Pattern matches when the indicated number of most-significant bits of the packet value equal the pattern.
  • MatchingOperator.MATCH_MAPPING matches when the packet value is present in the mapping’s forward_mapping.
  • MatchingOperator.IGNORE matches without comparing the packet value to the target value.

In particular, IGNORE must not reject a field because of any size difference involving:

  • the packet field value,
  • the rule’s declared length, or
  • the rule’s target_value.

Thus, a rule field with length=0 and target_value=b"" can ignore a non-empty, variable-length packet field.

For an upward packet, rule fields whose direction is either DirectionIndicator.UP or DirectionIndicator.BIDIRECTIONAL must be usable for matching.

Module: microschc.ruler.ruler

Ruler is constructed with the keyword argument rules_descriptors, a list of RuleDescriptor objects. It must provide the public method:

match(self, packet_descriptor: PacketDescriptor) -> RuleDescriptor

match returns the first rule in the configured list that matches the packet. Rule order therefore matters, and an empty rule intended as a fallback should normally be placed after more specific rules. A RuleDescriptor with an empty field_descriptors list matches every packet and acts as a default/fallback rule.

For each non-empty candidate rule, matching behaves as follows:

  1. Flatten only the packet's parsed header fields, preserving header order and field order within each header. packet_descriptor.payload is never added to this field sequence and is never considered during rule selection.
  2. Select the candidate's rule fields whose direction is either the packet's direction or DirectionIndicator.BIDIRECTIONAL, preserving rule order.
  3. The selected rule fields must correspond one-for-one, in order, with all flattened packet header fields. A different number of applicable fields makes that candidate fail.
  4. Every corresponding pair must satisfy _field_match. If a candidate fails, evaluation continues with the next configured rule.

Bit-representation conventions

Bit strings are handled MSB-first within their significant region, but their byte-container alignment depends on their role:

  • An accumulated compressed buffer and the final SCHC header are left-aligned: their first significant bit is the most-significant bit of the first byte, and any final padding is on the right.
  • Standalone values and residues that occupy a non-integral number of bytes are right-aligned: their significant bits are the least-significant bits of their byte representation, with unused leading bits treated as padding. This convention applies to rule IDs, parsed field values/residues, mapping indexes, and the result of _encode_length.

No byte-alignment gaps are inserted when significant bit strings are concatenated.

1. _encode_length

def _encode_length(length: int) -> Tuple[bytes, int]:

Encode length using SCHC variable-length length encoding. Return (encoded_length, encoded_length_length), where:

  • encoded_length is a bytes representation of the encoding;
  • encoded_length_length is its exact number of significant bits; and
  • those significant bits are right-aligned in encoded_length and zero-padded on the left to a whole number of bytes.

Use these three tiers:

  1. Small, 0 through 14 inclusive: encode the value directly in 4 bits. Return a one-byte representation and a bit length of 4.

    • 5 -> (b'\x05', 4)
    • 14 -> (b'\x0e', 4)

  2. Medium, 15 through 254 inclusive: encode the 4-bit escape value 0xF, followed by the value in 8 bits. The 12 significant bits are right-aligned in two bytes.

    • 15 -> (b'\x0f\x0f', 12)
    • 254 -> (b'\x0f\xfe', 12)

  3. Large, 255 or greater: encode the 4-bit escape value 0xF, followed by the 8-bit escape value 0xFF, followed by the value in 16 bits. The 28 significant bits are right-aligned in four bytes.

    • 255 -> (b'\x0f\xff\x00\xff', 28)
    • 65535 -> (b'\x0f\xff\xff\xff', 28)

2. _compact_left

def _compact_left(
    buffer: bytes,
    buffer_length: int,
    bytefield: bytes,
    bytefield_length: int,
) -> bytes:

Concatenate two significant bit strings and return the result as a left-aligned, big-endian, MSB-first byte string.

The two operands use different container alignments:

  • buffer contains buffer_length significant bits left-aligned from the most-significant bit of buffer[0]. Discard all bits after those first buffer_length bits. Thus, the final byte of a non-byte-aligned buffer has (8 - (buffer_length mod 8)) mod 8 trailing padding bits.
  • bytefield contains bytefield_length significant bits right-aligned in its byte representation. Select the rightmost, least-significant bytefield_length bits and discard any unused leading padding bits. Preserve the normal MSB-first order of the selected region when appending it.

Append the selected bytefield bits immediately after the selected buffer bits. The result has exactly buffer_length + bytefield_length significant bits and is returned left-aligned, with zero padding on the right of its final byte when necessary. Its byte length is:

ceil((buffer_length + bytefield_length) / 8)

3. compress

def compress(
    packet_descriptor: PacketDescriptor,
    rule_descriptor: RuleDescriptor,
) -> Tuple[bytes, int]:

Compress the parsed packet headers according to the supplied rule. Return (schc_packet, schc_packet_length), where:

  • schc_packet_length is the exact number of significant bits in the rule ID and compression residues;
  • schc_packet contains those bits left-aligned and MSB-first in whole bytes; and
  • unused bits at the right of the final byte are zero.

The returned value is the compressed header only. It does not include packet_descriptor.payload.

Inputs and field ordering

packet_descriptor supplies:

  • direction;
  • an ordered list of parsed headers, each containing an ordered list of field descriptors; and
  • payload as a separate byte string.

Packet header fields are considered by traversing headers in order and fields within each header in order. Rule field descriptors are likewise considered in their declared order. The rule is expected to use the same applicable field order as the packet.

A rule field descriptor is applicable when its direction is either:

  • equal to packet_descriptor.direction, or
  • DirectionIndicator.BIDIRECTIONAL.

A descriptor for any other direction is skipped, contributes no residue bits, and does not disturb the ordered correspondence between the applicable rule fields and packet header fields.

Only parsed header fields participate in compression. The separately stored payload must not be converted into a field residue. In particular, a rule entry identified by ParserDefinitions.PAYLOAD contributes neither a variable-length prefix nor payload bits to this return value. A caller that needs a complete SCHC packet can append the payload afterward with _compact_left.

Output layout and rule ID

The first rule_descriptor.id_length bits of the compressed output are the least-significant id_length bits of rule_descriptor.id. In other words, the rule ID is extracted from the right-aligned significant portion of its byte representation, then emitted MSB-first at the start of the left-aligned output.

For example:

RuleDescriptor(id=b'\x03', id_length=2, ...)

contributes the bit sequence 11, not 00.

After the rule ID, append each applicable field's residue in rule order, with no alignment gaps.

Compression/Decompression Actions

For each corresponding packet field and applicable rule field, produce the residue selected by compression_decompression_action:

CDA.NOT_SENT

Emit no bits.

CDA.VALUE_SENT

Emit the packet field's significant value bits.

  • If the rule field's declared length is nonzero, emit the value bits directly, without a length prefix.
  • If the rule field's declared length is 0, first call _encode_length with the packet field's value length in bits, then append that encoded length and the field value bits. Do not encode the byte count.

For example:

  • An 8-byte token has a field length of 64 bits. Its prefix is _encode_length(64) == (b'\x0f\x40', 12), whose significant sequence is hexadecimal F40.
  • A one-byte option value has a field length of 8 bits. Its prefix is _encode_length(8) == (b'\x08', 4).

The prefix and value are each packed using their exact bit lengths, not their enclosing byte lengths.

CDA.MAPPING_SENT

The rule field's target_value is a MatchMapping. Look up the packet field value in the mapping's forward mapping and emit the resulting index in exactly MatchMapping.index_length bits. The index representation is right-aligned before those significant bits are packed into the output.

CDA.LSB

The rule field's target_value is a Pattern. Its length gives the number of most-significant field bits fixed by the rule. Emit the remaining least-significant:

packet_field.length - pattern.length

bits of the packet field value.

Packing and exact length

Every rule-ID bit, length-prefix bit, and field-residue bit is appended immediately after the preceding significant bit, regardless of byte boundaries. schc_packet_length is the sum of the rule-ID length and all emitted residue lengths. The byte representation has length ceil(schc_packet_length / 8) and is right-padded with zero bits only in its final byte.

Refactor the existing field and rule descriptors, parsers, matching operators, compression actions, and compressor so field values, target values, residues, payloads, and rule identifiers use Buffer instances rather than raw bytes accompanied by separate bit-length values.

1. The Buffer class

Create module microschc.binary.buffer exposing:

  • An enumeration Padding with members Padding.LEFT and Padding.RIGHT.
  • A class Buffer.
Constructor
Buffer(content: bytes, bit_length: int, padding: Padding = Padding.LEFT)
  • content is the raw byte sequence backing the buffer.
  • bit_length is the declared number of significant bits.
  • padding identifies the side on which unused backing bits occur. It defaults to Padding.LEFT.
  • For a normally capacity-backed buffer, the padding-bit count is 8 * len(content) - bit_length. With Padding.LEFT, the significant sequence is the least-significant bit_length bits of content, so padding is on the leading, most-significant side. With Padding.RIGHT, the significant sequence is the most-significant bit_length bits of content, so padding is on the trailing, least-significant side.
  • Construction must not require content to contain enough physical bits for bit_length. In particular, a positive bit_length with shorter content, including Buffer(content=b'', bit_length=16), is valid and must not raise merely because the declared length exceeds 8 * len(content). This permits empty-backed values to be used as ignored field values and rule-target placeholders. Construction retains the supplied content and bit_length; it does not synthesize missing bytes.
Attributes

Instances expose readable attributes content (bytes), bit_length (int), and padding (a Padding value).

Equality and hashing

Two Buffer instances compare equal when they have the same bit_length and carry the same significant-bit sequence. Padding side and backing representation details that do not change the significant bits are not part of logical equality. In particular, a right-padded result realigned by pad compares equal to an explicitly constructed left-padded buffer carrying the same significant bits and length. Buffers with identical bit content but different bit_length values are not equal.

Buffer must be hashable, with hashing consistent with this equality, because buffers are used as mapping keys.

shift(shift: int, inplace: bool = False) -> Buffer

Shift the significant sequence within the buffer. A negative shift is a left shift by abs(shift) bits; a positive shift is a right shift by shift bits. With inplace=False, return a new Buffer and leave the original unchanged. The result preserves the original padding side.

Semantics on the significant sequence are:

  • Left shift: increase bit_length by the shift amount and move the significant bits toward the most-significant side, retaining the newly significant zero bits on the least-significant side. Preserve the current backing-byte length whenever the increased bit_length still fits in the existing content, even when fewer bytes would be sufficient for a minimal representation. Grow content only when the new bit length exceeds the current capacity. When growth is needed, add null-byte capacity and use exactly the smallest whole-byte length that can hold the increased bit length. Equivalently, the resulting byte count is max(len(content), ceil(new_bit_length / 8)).
  • Right shift: decrease bit_length by the shift amount and drop the least-significant bits. Preserve the backing content length.

Worked examples, all with inplace=False:

  • Buffer(b'\x2d', bit_length=7, padding=Padding.LEFT).shift(-10) produces content == b'\x00\xb4\x00' and bit_length == 17; the backing storage grows from one byte to three.
  • Buffer(b'\x00\x08\x2d', bit_length=12, padding=Padding.LEFT).shift(-2) produces content == b'\x00\x20\xb4' and bit_length == 14; it retains all three existing backing bytes even though 14 bits could fit in two bytes.
  • Buffer(b'\x08\x28\x00', bit_length=13, padding=Padding.RIGHT).shift(-2) produces content == b'\x08\x28\x00' and bit_length == 15; its three-byte backing length is retained.
  • Buffer(b'\x00\x08\x2d', bit_length=12, padding=Padding.LEFT).shift(3) produces content == b'\x00\x01\x05' and bit_length == 9.
  • Buffer(b'\x00\x08\x2d', bit_length=12, padding=Padding.LEFT).shift(6) produces content == b'\x00\x00\x20' and bit_length == 6.
trim(inplace: bool = False) -> Buffer

Remove surplus whole bytes of padding so content occupies the minimum number of whole bytes needed for bit_length, without changing the significant sequence, padding side, or bit_length. With inplace=False, return a new buffer and leave the original unchanged.

Example:

Buffer(b'\x08\x28\x00', bit_length=13, padding=Padding.RIGHT).trim()

equals Buffer(b'\x08\x28', bit_length=13, padding=Padding.RIGHT).

pad(padding: Padding, inplace: bool = False) -> Buffer

Return a buffer carrying the same significant bits and bit_length, with padding placed on the requested side. Converting sides realigns the significant sequence within content. With inplace=False, leave the source unchanged. Padding to one side and then back to the original side must reproduce the original logical buffer.

Example:

Buffer(b'\x08\x28\x00', 13, Padding.RIGHT).pad(Padding.LEFT)

equals Buffer(b'\x00\x01\x05', 13, Padding.LEFT), and padding that result back to Padding.RIGHT reproduces the original buffer.

Bit slicing: __getitem__(key: slice) -> Buffer

Support slicing by bit index using buffer[start:stop] and return a new Buffer containing the selected bits.

  • Index 0 is the first significant bit on the most-significant side of the significant sequence; indices increase toward the least-significant side.
  • A stop beyond bit_length is clamped to bit_length.
  • Negative indices count from bit_length; for example, buffer[-4:] selects the last four significant bits.
  • The result has the source's padding side, a bit_length equal to the number of selected bits, and the minimum whole-byte content needed for those bits, aligned according to that padding side.

Concatenation: __add__

Support buffer_a + buffer_b. The result's significant sequence is the significant sequence of buffer_a followed immediately by that of buffer_b, independent of either operand's byte alignment. Its bit_length is the sum of the operands' lengths. This operation must support appending a payload buffer to a compressed residue and produce a logical buffer equal to the fully assembled, right-padded SCHC packet.

__repr__

Return a human-readable string in this form:

[<bytes>] | len: <bit_length> | pad: <padding_bits> <side>

5. Parsers

The IPv6, UDP, and CoAP parsers must produce FieldDescriptor objects whose value is a Buffer with the field's exact bit length. Packet field descriptors no longer carry a separate length; position remains unchanged. Header lengths remain available on HeaderDescriptor so PacketParser can advance through a protocol stack.

Representative field contracts, written as Buffer(content, bit_length), are:

IPv6
  • VERSION: 4 bits, for example Buffer(b'\x06', 4)
  • TRAFFIC_CLASS: 8 bits
  • FLOW_LABEL: 20 bits
  • PAYLOAD_LENGTH: 16 bits
  • NEXT_HEADER: 8 bits
  • HOP_LIMIT: 8 bits
  • SRC_ADDRESS: 128 bits
  • DST_ADDRESS: 128 bits

For example, the standard 40-byte IPv6 header beginning with 60 00 00 00 00 10 11 40 yields VERSION b'\x06'/4, TRAFFIC_CLASS b'\x00'/8, FLOW_LABEL b'\x00\x00\x00'/20, PAYLOAD_LENGTH b'\x00\x10'/16, NEXT_HEADER b'\x11'/8, and HOP_LIMIT b'\x40'/8, followed by the two 128-bit address buffers.

UDP

SOURCE_PORT, DESTINATION_PORT, LENGTH, and CHECKSUM are each represented by a 16-bit Buffer. For example, a UDP header beginning 23 29 23 2a 00 10 2d a1 produces b'\x23\x29', b'\x23\x2a', b'\x00\x10', and b'\x2d\xa1', each with bit_length == 16.

CoAP

The parser represents fields with these lengths:

  • VERSION: 2 bits
  • TYPE: 2 bits
  • TOKEN_LENGTH: 4 bits
  • CODE: 8 bits
  • MESSAGE_ID: 16 bits
  • TOKEN: its parsed token length, including 64 bits for an eight-byte token
  • OPTION_DELTA: 4 bits
  • OPTION_LENGTH: 4 bits
  • OPTION_VALUE: the parsed option-value length, including 8 bits for a one-byte value
  • PAYLOAD_MARKER: 8 bits

For an eight-byte-token packet beginning 48 02 84 99 74 cd e8 cb 4e 8c 0d b7, the first six values are respectively Buffer(b'\x01', 2), Buffer(b'\x00', 2), Buffer(b'\x08', 4), Buffer(b'\x02', 8), Buffer(b'\x84\x99', 16), and Buffer(b'\x74\xcd\xe8\xcb\x4e\x8c\x0d\xb7', 64). Parsed option fields retain their existing IDs and positions.

PacketDescriptor.payload

After all configured headers are consumed, PacketDescriptor.payload is a Buffer whose content is the remaining payload bytes and whose bit_length is exactly 8 * len(payload_bytes). For the IPv6/UDP/CoAP stack, the packet descriptor continues to contain the three parsed headers in stack order and the bytes after the CoAP payload marker become this payload buffer.

  • bit_length: the number of significant bits in the buffer (may be less than 8 * len(content)).
  • padding: a Padding enum value. The relevant value here is Padding.RIGHT, meaning the significant bits are the leftmost (most-significant) bits of the content, and any unused trailing bits are padding.

Required Change

Concatenation Semantics (right-padded buffers)

For buffers using Padding.RIGHT, the significant bits occupy the high-order bit positions of content. Concatenation appends the right operand's significant bits immediately after the left operand's significant bits, with no gap.

The result:

  • Has bit_length equal to the sum of the two operands' bit lengths.
  • Has padding of Padding.RIGHT.
  • Has content holding the concatenated significant bits, left-aligned (most-significant first), with any trailing bits beyond the combined bit length set to zero. The content length is the minimum number of whole bytes needed to hold the combined bit length.

Bit-stream model

  • its direction is DirectionIndicator.BIDIRECTIONAL.

Field reconstruction actions

For each applicable RuleFieldDescriptor, use its compression_decompression_action as follows.

CDA.NOT_SENT

The field has no bits in the compression residue. Its complete value comes from the descriptor's target_value, which is a Buffer. Emit the target value's significant bits as a field of exactly descriptor.length bits and do not advance the residue cursor.

CDA.VALUE_SENT

The field value is carried verbatim in the compression residue.

  • If descriptor.length is nonzero, consume exactly that many residue bits and emit them unchanged.
  • If descriptor.length == 0, the field is variable-length. Decode the length prefix at the current residue cursor as specified below, consume the decoded number of value bits immediately following the prefix, and emit those value bits unchanged. The prefix itself is consumed but is not emitted. A decoded length of zero is valid and emits an empty field.
CDA.MAPPING_SENT

The descriptor's target_value is a MatchMapping. Its forward-map values, equivalently its reverse-map keys, are the compressed mapping indices and define the index bit width and wire patterns. Consume one index of that width from the residue, use it as a key in the mapping's reverse direction, and emit the corresponding original field Buffer as a field of descriptor.length bits. Mapping indices may be non-byte-aligned. A valid mapping used for this action has an unambiguous common index width.

CDA.LSB

The descriptor's target_value is a Buffer containing the field's most-significant-bit pattern. Let m = target_value.bit_length. Consume exactly descriptor.length - m bits from the residue as the field's least-significant bits. Emit the m target bits followed immediately by the consumed residue bits, producing a field of exactly descriptor.length bits.

Variable-length prefix format

A variable field's length is an unsigned count of bits, not bytes. Decode it from the residue in most-significant-bit-first wire order:

  1. Read an initial 4-bit unsigned value.
  2. If it is from 0 through 14, that value is the field-value bit length. The prefix occupies 4 bits.
  3. If it is 15, read the following 8-bit unsigned value.
    • If this extension is from 0 through 254, it is the field-value bit length. The prefix occupies 12 bits.
    • If this extension is 255, read a further 16-bit unsigned value. That final value is the field-value bit length, and the prefix occupies 28 bits.

Thus the normal encodings use 4 bits for lengths 0–14, 12 bits for lengths 15–254, and 28 bits for lengths 255–65535. For example, length 14 is encoded as 1110; length 15 as 1111 00001111; and length 255 as 1111 11111111 0000000011111111. Cursor advancement must include both the selected prefix width and the decoded number of field-value bits.

Remaining payload

After every applicable rule field has been reconstructed, append every still-unconsumed significant bit of schc_packet unchanged after the reconstructed fields. This suffix is the original packet payload and need not be represented by another rule field.

The suffix begins exactly at the final residue cursor and ends at schc_packet.bit_length. Do not append unused bits that merely fill the last backing byte of schc_packet. If no significant bits remain, append nothing. Payload concatenation is bitwise and must also work when the preceding reconstructed fields or the payload boundary are not byte-aligned.

Correctness requirements

For a valid SCHC packet, matching rule, and direction:

  • the Rule ID is consumed but omitted from the result;
  • only direction-applicable descriptors affect reconstruction;
  • each applicable CDA consumes exactly its defined residue bits and emits exactly its reconstructed field bits;
  • fixed- and variable-length VALUE_SENT fields, including all length-prefix escape forms, are decoded correctly;
  • non-byte-aligned Rule IDs, fields, LSB residues, and mapping indices remain in the correct bit order;
  • all remaining significant residue bits are preserved as the payload, while backing-byte padding is excluded; and
  • the returned packet is the ordered bit-concatenation of all reconstructed fields and that payload suffix, reproducing the original packet exactly.

Overview

You are working on a packet-parsing library (microschc) that parses network protocol headers into structured descriptors. You must update the parser components so that they operate on a Buffer object as input (instead of raw bytes), and add a match method to each parser that verifies whether a given buffer is a valid input for that parser.

Background: the Buffer type

A Buffer (in microschc.binary.buffer) wraps binary content with an explicit bit length. It is constructed as:

Buffer(content=<bytes>, length=<number_of_bits>)

where length is the size of the meaningful content in bits (i.e. len(content) * 8 when the whole byte string is significant).

Required API Surface

The following parser classes and their public methods must exist and be callable as described.

Protocol parsers

Each of these classes lives under microschc.parser.protocol.* and is instantiable with no arguments:

  • IPv4Parser
  • IPv6Parser
  • UDPParser
  • CoAPParser

Each parser must expose:

  1. parse(self, buffer: Buffer) -> HeaderDescriptor

    • Accepts a Buffer object as the buffer keyword argument.
    • Parses the header contained in the buffer and returns a HeaderDescriptor.
    • The individual parsed fields returned (as FieldDescriptor objects accessible on the descriptor) must have value attributes that are Buffer objects sliced from the input, correctly reflecting the exact bit range of each field. In particular, multi-byte fields must retain their full byte width — e.g. a 16-bit value such as decimal 104 (0x0068) must be represented as the two bytes b'\x00\x68', not truncated to a single byte.

  2. match(self, buffer: Buffer) -> bool

    • Accepts a Buffer object.
    • Returns a truthy value (True) when the buffer is a valid input that this parser can parse.
    • For each of the valid sample packets described below, match returns True.
Packet parser
  • PacketParser (obtained via factory(stack_implementation=StacksImplementation.IPV6_UDP_COAP) from the appropriate module) must expose:

  1. parse(self, buffer: Buffer, direction: DirectionIndicator) -> PacketDescriptor

    • Accepts a Buffer and a DirectionIndicator.
    • Returns a PacketDescriptor whose fields list contains the concatenated FieldDescriptor objects for each layer of the stack (IPv6, UDP, CoAP).
    • The first field's id corresponds to IPv6Fields.VERSION.
    • Field values must be correctly-widthed Buffer slices as described above (e.g. the UDP Length field with value 104 yields bytes b'\x00\x68').

  2. match(self, buffer: Buffer, direction: DirectionIndicator) -> bool

    • Accepts a Buffer and a DirectionIndicator.
    • Returns a truthy value (True) when the buffer is a valid input for the configured stack.

Behavioral Requirements

Buffer as parser input

All parse and match methods now take a Buffer object (not raw bytes). The parsing logic must read content and bit lengths from the Buffer and produce field values as Buffer slices.

Correct field slicing

When extracting a field of a given bit length and position from the input buffer, the resulting field value Buffer must contain exactly the bits belonging to that field, preserving the full byte representation. Concretely, a 16-bit field whose value is 0x0068 must produce content b'\x00\x68' (two bytes), not a byte-truncated result.

match returning true for valid inputs

Given a well-formed packet for the relevant protocol, match must return True.

Reference sample inputs (all valid, match → True)

The following byte sequences, wrapped as Buffer(content=<bytes>, length=len(<bytes>)*8), are valid inputs:

  • IPv4:

    \x45\x00\x02\x5a\x21\xfa\x40\x00\x40\x11\xbc\x52\xac\x1e\x01\x08\xac\x1e\x01\x02

  • IPv6:

    <a valid IPv6 header followed by UDP payload; a well-formed IPv6 packet>

  • UDP:

    \x23\x29\x23\x2a\x00\x10\x2d\xa1\x64\x65\x61\x64\x62\x65\x65\x66

  • CoAP: a valid CoAP message buffer.

  • Full stack (IPv6/UDP/CoAP): a valid IPv6→UDP→CoAP packet, parsed with direction=DirectionIndicator.DOWN.

Imports the caller relies on

  • Buffer from microschc.binary.buffer
  • HeaderDescriptor from microschc.parser.parser
  • FieldDescriptor from microschc.rfc8724
  • PacketDescriptor, DirectionIndicator, StacksImplementation, factory, and the PacketParser / field-name enum (IPv6Fields, UDPFields, etc.) from their existing locations.

The UDP parser test module should describe UDP header parser import/instantiation (a UDPParser instance is an instance of UDPParser). This is documentation-only; no functional impact.

Summary of what to deliver

Update the four protocol parsers and the packet parser so that:

  1. parse and match accept a Buffer object (packet parser and its match also accept a DirectionIndicator).
  2. match returns True for well-formed inputs.
  3. Field values are correctly sliced from the buffer as full-width Buffer objects (fixing the byte-truncation bug so, e.g., a 16-bit 104 yields b'\x00\x68').

Task: Relocate Protocol Stack Definitions and Add Parser Identifier to Context

Overview

You must reorganize where protocol stack identifiers and the parser factory function live, and add a parser identifier field to the Context data structure. The changes affect the public API surface for creating packet parsers and for serializing/deserializing Context objects.

Required API Surface

1. New module: microschc.parser.protocol.registry

This module must expose the following importable names:

  • Stack — an enumeration of supported protocol stack identifiers. It must include the member Stack.IPV6_UDP_COAP. The string value of this member must be exactly "IPv6-UDP-CoAP" (i.e., when serialized to JSON as a string, Stack.IPV6_UDP_COAP produces "IPv6-UDP-CoAP").

  • factory — a callable that builds and returns a PacketParser (from microschc.parser.parser). Its signature must accept a keyword argument named stack_id:

    factory(stack_id=Stack.IPV6_UDP_COAP) -> PacketParser

    When called with stack_id=Stack.IPV6_UDP_COAP, it must return a fully constructed PacketParser capable of parsing and matching an IPv6/UDP/CoAP packet stack (identical behavior to the previously available factory for that stack). The returned parser must support:

    • .match(buffer, direction=...) returning a truthy result for a matching packet.
    • .parse(buffer=..., direction=...) returning a PacketDescriptor, without raising exceptions on valid IPv6/UDP/CoAP packets (including packets with zero CoAP options and packets with no payload).

The keyword argument is now stack_id (accepting a Stack member), replacing any prior stack_implementation argument.

2. microschc.rfc8724extras

The stack-implementation enumeration that previously lived here (e.g. StacksImplementation) is no longer part of the public surface of this module. This module must continue to expose ParserDefinitions.

3. Context in microschc.rfc8724

The Context structure must gain a new field named parser_id whose value is a Stack member.

Constructor usage:

Context(
    id='test_context',
    description='this is a test context',
    interface_id='eth0',
    parser_id=Stack.IPV6_UDP_COAP,
    ruleset=[rule_descriptor],
)
JSON serialization (Context.json())

The serialized JSON object must include the parser_id key, positioned immediately after interface_id and before ruleset. The value of parser_id must be the string form of the Stack member (e.g. "IPv6-UDP-CoAP").

For example, a context with id="test_context", description="this is a test context", interface_id="eth0", parser_id=Stack.IPV6_UDP_COAP, and a single rule must serialize with the leading structure:

{"id": "test_context", "description": "this is a test context", "interface_id": "eth0", "parser_id": "IPv6-UDP-CoAP", "ruleset": [ ... ]}

The rest of the serialization (rule descriptor, field descriptors, buffer encoding) must remain unchanged from the existing behavior.

JSON deserialization (Context.from_json(json_str=...))

Deserializing a JSON string that contains a "parser_id" key with value "IPv6-UDP-CoAP" must produce a Context whose parser_id attribute equals Stack.IPV6_UDP_COAP. All other fields (id, description, interface_id, ruleset and its nested field descriptors) must deserialize as before.

Import Path Summary

  • Stack and factory are importable from microschc.parser.protocol.registry.
  • Context remains importable from microschc.rfc8724.
  • ParserDefinitions remains importable from microschc.rfc8724extras.
  • The previously-used factory import path (microschc.parser.factory) and the StacksImplementation name in microschc.rfc8724extras are no longer required by callers.

Scope Constraints

  • Only the Stack.IPV6_UDP_COAP member and its string value "IPv6-UDP-CoAP" are exercised; no other stack members' behavior is required.
  • Do not alter unrelated parsing, matching, ruler, or compressor behavior beyond what is needed to move the factory/stack definitions and add the parser_id field.
