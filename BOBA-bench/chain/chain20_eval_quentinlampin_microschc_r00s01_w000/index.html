Behavior of field matching

For a packet field and a rule field that correspond:

  • MatchingOperator.EQUAL matches when the packet field value equals the rule target value, and it does not match when the two values differ.
  • MatchingOperator.MSB together with a Pattern matches when the most-significant bits of the packet value, taken in the indicated number, equal the pattern.
  • MatchingOperator.MATCH_MAPPING matches when the packet value occurs in the mapping’s forward_mapping.
  • MatchingOperator.IGNORE matches, with no comparison of the packet value against the target value.

Notably, IGNORE must not reject a field because of any size difference that involves:

  • the packet field value,
  • the length declared by the rule, or
  • the rule’s target_value.

Consequently, a rule field with length=0 and target_value=b"" can ignore a packet field that is non-empty and variable in length.

When a packet is upward, rule fields whose direction is either DirectionIndicator.UP or DirectionIndicator.BIDIRECTIONAL must be usable for matching.

Specification of the Task

Your work is set in the microschc package, a Python implementation of packet parsing and SCHC rule matching. The requirements that follow are exhaustive. Aside from the changes explicitly described here, the existing public APIs and behavior must be preserved.

1. A dedicated attribute for the packet payload

Module: microschc.rfc8724

The following packet data must be exposed by PacketDescriptor:

  • direction: the packet's DirectionIndicator.
  • headers: a list of HeaderDescriptor objects, in the order produced by parsing.
  • payload: the raw payload, held as bytes.

Every HeaderDescriptor continues to expose a fields list, which contains FieldDescriptor objects. The payload must not show up in headers, and it must not be represented by either a HeaderDescriptor or a FieldDescriptor. PacketDescriptor.payload is the only representation of the bytes left over once all configured protocol headers have been parsed. When no bytes are left, the payload is b''.

Module: microschc.parser.parser

PacketParser.parse(buffer, direction) must return a PacketDescriptor whose direction is the direction that was supplied. It must run the header parsers it has configured in order, retain the HeaderDescriptor results they produce in that same order, and expose the unconsumed bytes as packet_descriptor.payload.

Take an IPv6/UDP/CoAP packet produced by the parser factory:

  • the headers contained in packet_descriptor.headers are exactly the IPv6, UDP, and CoAP headers;
  • each header keeps its existing parsed fields;
  • when it is present, the CoAP payload marker remains a field of the CoAP header;
  • the bytes that follow the parsed CoAP header and payload marker are returned unchanged in packet_descriptor.payload;
  • no fourth or trailing payload header gets appended.

2. Descriptor models and the operators used for matching

Module: microschc.rfc8724
FieldDescriptor

The construction of FieldDescriptor uses these keyword arguments:

  • id
  • length: the length of the field in bits, as an int
  • position: an int
  • value

The values that packet parsers produce are raw bytes.

Pattern

A Pattern is constructed from pattern: bytes and length: int. The value of length is the count of significant pattern bits; it may be non-byte-aligned. The bytes of pattern are represented the same way as parsed fields: whenever the bit length is not a multiple of eight, the unused padding bits come before the significant bits within the first byte.

MatchMapping

A MatchMapping is constructed from index_length: int together with forward_mapping. Admissible field values are mapped by the forward mapping to mapping indices. The mapping that is supplied stays available as forward; the inverse mapping that corresponds to it stays available as reverse.

RuleFieldDescriptor

The keyword arguments used to construct RuleFieldDescriptor are:

  • id
  • length: an int bit length
  • position: an int
  • direction: a DirectionIndicator
  • target_value: a bytes, Pattern, or MatchMapping value
  • matching_operator: a MatchingOperator
  • compression_decompression_action: a CompressionDecompressionAction

Which target forms are valid depends on the matching operator:

  • a bytes target is what MatchingOperator.EQUAL uses;
  • with MatchingOperator.IGNORE, the target is not inspected;
  • a Pattern is the target used by MatchingOperator.MSB;
  • a MatchMapping is the target used by MatchingOperator.MATCH_MAPPING.

Therefore RuleFieldDescriptor.target_value must not be restricted to bytes; it is valid for rules to contain Pattern and MatchMapping targets.

Module: microschc.matching.operators

The matching operator functions that already exist remain public.

equal(field_descriptor, target_value) -> bool

Only byte values are compared by equal. True is returned exactly when field_descriptor.value == target_value, and False in every other case. Byte sequences whose lengths differ are unequal even when one of them has additional leading zero bytes. No integer support is required for equal.

ignore(field_descriptor) -> bool

ignore returns True in every case; the field's value and declared length are not inspected.

most_significant_bits(field_descriptor, pattern, pattern_length) -> bool

The supplied byte pattern is compared by this operator against the requested number of most-significant logical field bits. It must:

  • treat field_descriptor.length as the logical field length;
  • strip any leading whole-byte representation padding out of the logical field bits;
  • handle fields and patterns whether byte-aligned or non-byte-aligned; and
  • return True only when the leftmost pattern_length logical field bits exactly equal the significant bits that pattern represents.

The byte representations of both the field and the pattern are left-zero-padded as necessary whenever their logical lengths are not multiples of eight.

match_mapping(field_descriptor, target_values) -> bool

The target_values argument is a MatchMapping. The function returns True exactly when field_descriptor.value is one of the keys in the mapping's forward mapping, and False otherwise. Membership is exact; a value that is of a different type, or a value that is absent from the forward mapping, does not match.

3. The Ruler and the rules

Module: microschc.rfc8724

The keyword arguments used to construct RuleDescriptor are:

  • id: a bytes rule identifier
  • id_length: an int that gives the identifier's bit length
  • field_descriptors: a list of RuleFieldDescriptor objects

These values are exposed by the descriptor, its public id attribute among them.

Module: microschc.ruler.ruler

A Ruler is constructed by passing the keyword argument rules_descriptors, a list of RuleDescriptor objects. The public method it must provide is:

match(self, packet_descriptor: PacketDescriptor) -> RuleDescriptor

match returns the first rule from the configured list that matches the packet. The order of the rules therefore matters, and an empty rule that is meant to serve as a fallback should normally be placed after the more specific rules. A RuleDescriptor whose field_descriptors list is empty matches every packet and acts as a default/fallback rule.

For each candidate rule that is not empty, the matching behavior is as follows:

  1. Flatten only the packet's parsed header fields, keeping the order of the headers and, within each header, the order of its fields. packet_descriptor.payload is never added to this field sequence, and it is never taken into account when rules are selected.
  2. Take the candidate's rule fields whose direction is either the packet's direction or DirectionIndicator.BIDIRECTIONAL, keeping the rule order.
  3. There must be a one-for-one, in-order correspondence between the selected rule fields and all of the flattened packet header fields. If the number of applicable fields is different, that candidate fails.
  4. For every corresponding pair, _field_match must be satisfied. When a candidate fails, evaluation moves on to the next configured rule.

Consequently, a rule that describes the IPv6/UDP/CoAP header fields through the CoAP payload-marker field, and that has no field descriptor for the application payload bytes, must be able to match a packet with those headers even when PacketDescriptor.payload is non-empty.

Helper for per-field matching

The helper that operates at field level remains directly callable in this form:

_field_match(packet_field: FieldDescriptor, rule_field: RuleFieldDescriptor) -> bool

Its behavior is as follows:

  • The field identifiers must be equal. For every matching operator, different IDs return False.
  • The position of a field is not compared on its own; it is the ordered field sequences that determine correspondence.
  • Under MatchingOperator.IGNORE, fields that have the same ID match regardless of the value or the length.
  • Under MatchingOperator.EQUAL, the IDs, the declared lengths, and the byte values must all match.
  • Under MatchingOperator.MSB, rule_field.target_value is a Pattern; Pattern.pattern is used to compare the Pattern.length most-significant bits.
  • Under MatchingOperator.MATCH_MAPPING, rule_field.target_value is a MatchMapping; there is a match exactly when the packet field value is present among the keys of the forward mapping.

During Ruler.match, the MSB and match-mapping behaviors must be applied, and not only at the point where their standalone operator functions are called.

Scope

How bit strings are represented

Within their significant region, bit strings are ordered MSB-first; the alignment inside the byte container, on the other hand, follows from the role the string plays:

  • Left-aligned describes the accumulated compressed buffer and the final SCHC header: the most-significant bit of the first byte is where their first significant bit sits, and any final padding lies on the right.
  • Right-aligned describes standalone values and residues that do not occupy a whole number of bytes: the least-significant bits of the byte representation carry the significant bits, while leading bits that go unused count as padding. Rule IDs, parsed field values/residues, mapping indexes, and the result of _encode_length all follow this convention.

Concatenation of significant bit strings introduces no byte-alignment gaps.

1. The _encode_length helper

def _encode_length(length: int) -> Tuple[bytes, int]:

This function encodes length by means of SCHC's variable-length length encoding. It returns (encoded_length, encoded_length_length), where:

  • encoded_length: the encoding itself, as a bytes value;
  • encoded_length_length: the exact count of significant bits in that encoding; and
  • inside encoded_length, those significant bits sit right-aligned, with zero padding on the left bringing the size up to a whole number of bytes.

Three tiers govern the encoding:

  1. Small, 0 through 14 inclusive: the value is encoded directly into 4 bits. The function returns a one-byte representation and a bit length of 4.

    • 5 -> (b'\x05', 4)
    • 14 -> (b'\x0e', 4)

  2. Medium, 15 through 254 inclusive: the 4-bit escape value 0xF is encoded first, followed by the value in 8 bits. The resulting 12 significant bits are right-aligned in two bytes.

    • 15 -> (b'\x0f\x0f', 12)
    • 254 -> (b'\x0f\xfe', 12)

  3. Large, 255 or greater: the 4-bit escape value 0xF is encoded first, followed by the 8-bit escape value 0xFF and then the value in 16 bits. The resulting 28 significant bits are right-aligned in four bytes.

    • 255 -> (b'\x0f\xff\x00\xff', 28)
    • 65535 -> (b'\x0f\xff\xff\xff', 28)

2. The _compact_left helper

def _compact_left(
    buffer: bytes,
    buffer_length: int,
    bytefield: bytes,
    bytefield_length: int,
) -> bytes:

Two significant bit strings are concatenated by this function, and the byte string it returns is left-aligned, big-endian, and MSB-first.

Container alignment differs between the two operands:

  • buffer stores buffer_length significant bits left-aligned, starting from the most-significant bit of buffer[0]; all bits after those first buffer_length bits are discarded. When buffer is not byte-aligned, its final byte therefore ends with (8 - (buffer_length mod 8)) mod 8 trailing padding bits.
  • bytefield stores bytefield_length significant bits right-aligned in its byte representation. The rightmost, least-significant bytefield_length bits are the ones selected, and any unused leading padding bits are discarded. As it is appended, the selected region keeps its normal MSB-first order.

Immediately after the selected buffer bits, the selected bytefield bits are appended. Exactly buffer_length + bytefield_length significant bits make up the result, which is returned left-aligned; its final byte is zero-padded on the right whenever that is necessary. Counted in bytes, its length is:

ceil((buffer_length + bytefield_length) / 8)

With buffer = b'\x33\xff\x60' and bytefield = b'\x0c\x33\xff', the results that must be produced are:

buffer_length bytefield_length Result
19 20 b'\x33\xff\x78\x67\xfe'
22 20 b'\x33\xff\x63\x0c\xff\xc0'
20 20 b'\x33\xff\x6c\x33\xff'
24 24 b'\x33\xff\x60\x0c\x33\xff'
24 22 b'\x33\xff\x60\x30\xcf\xfc'

To illustrate: for bytefield_length == 20, padding occupies the leading four bits of the three-byte bytefield, and what gets appended is the rightmost 20-bit sequence, the one given by hexadecimal C33FF.

3. The compress entry point

def compress(
    packet_descriptor: PacketDescriptor,
    rule_descriptor: RuleDescriptor,
) -> Tuple[bytes, int]:

Under the rule the caller supplies, the parsed packet headers are compressed. The function returns (schc_packet, schc_packet_length), where:

  • schc_packet_length: the exact number of significant bits contributed by the rule ID and the compression residues;
  • schc_packet: those bits, held left-aligned and MSB-first across whole bytes; and
  • zero fills all unused bits at the right end of the final byte.

All that is returned is the compressed header. packet_descriptor.payload does not form part of it.

Input data and field order

packet_descriptor carries:

  • direction;
  • a list of parsed headers, in order, each header holding an ordered list of field descriptors; and
  • payload as a byte string kept separate.

The fields of the packet headers are taken in a fixed traversal: headers in order, then the fields of each header in order. The rule field descriptors are taken in the order in which they were declared. The applicable field order on the rule side is expected to be the same as the packet's.

A rule field descriptor counts as applicable when its direction is either:

  • equal to packet_descriptor.direction, or
  • DirectionIndicator.BIDIRECTIONAL.

A descriptor pointing at any other direction is skipped: no residue bits come from it, and the ordered correspondence between the applicable rule fields and the packet header fields stays intact.

Only fields that were parsed from headers take part in compression. The payload, which is stored separately, must not be turned into a field residue. In particular, neither a variable-length prefix nor payload bits reach this return value from the rule entry identified by ParserDefinitions.PAYLOAD. A caller that needs a complete SCHC packet can append the payload afterward by means of _compact_left.

Layout of the output and the rule ID

Occupying the first rule_descriptor.id_length bits of the compressed output are the least-significant id_length bits of rule_descriptor.id. Stated differently: the right-aligned significant portion of the rule ID's byte representation supplies the bits, which are then emitted MSB-first at the head of the left-aligned output.

For example:

RuleDescriptor(id=b'\x03', id_length=2, ...)

the bit sequence contributed is 11, not 00.

Each applicable field's residue is appended after the rule ID, in rule order, and no alignment gaps appear.

Actions for compression and decompression

For each corresponding packet field and its applicable rule field, the residue to be produced is the one that compression_decompression_action selects:

CDA.NOT_SENT

No bits are emitted.

CDA.VALUE_SENT

The packet field's significant value bits are emitted.

  • When the rule field's declared length is nonzero, the value bits are emitted directly, without a length prefix.
  • When the rule field's declared length is 0, the first step is a call to _encode_length with the packet field's value length in bits; the encoded length it produced is appended, followed by the field value bits. Do not encode the byte count.

By way of example:

  • For a token of 8 bytes, the field length is 64 bits. Its prefix is _encode_length(64) == (b'\x0f\x40', 12), and hexadecimal F40 is that significant sequence.
  • For an option value of one byte, the field length is 8 bits; its prefix is _encode_length(8) == (b'\x08', 4).

Prefix and value are each packed with their exact bit lengths, not with the byte lengths that enclose them.

CDA.MAPPING_SENT

Here the rule field's target_value is a MatchMapping. The packet field value is looked up in the mapping's forward mapping, and the index thereby obtained is emitted in exactly MatchMapping.index_length bits. Before those significant bits are packed into the output, the index representation is right-aligned.

CDA.LSB

Here the rule field's target_value is a Pattern. Its length says how many most-significant field bits the rule holds fixed. From the packet field value, emit the remaining least-significant

packet_field.length - pattern.length

bits.

Bit packing and the overall length

Appending is done bit by bit: every rule-ID bit, length-prefix bit, and field-residue bit lands immediately after the preceding significant bit, and byte boundaries play no role. The value of schc_packet_length is the sum of the rule-ID length and the lengths of all residues that were emitted. The byte representation spans ceil(schc_packet_length / 8) bytes; right-padding with zero bits occurs only in the final byte.

To append a byte-aligned payload once compression has finished, use:

complete_packet = _compact_left(
    buffer=schc_packet,
    buffer_length=schc_packet_length,
    bytefield=packet_descriptor.payload,
    bytefield_length=8 * len(packet_descriptor.payload),
)

1. Class Buffer

The module microschc.binary.buffer is to be created, exposing:

  • The enumeration Padding, whose members are Padding.LEFT and Padding.RIGHT.
  • The class Buffer.
Constructing a Buffer
Buffer(content: bytes, bit_length: int, padding: Padding = Padding.LEFT)
  • The raw byte sequence acting as the buffer's backing storage is content.
  • How many significant bits are declared is given by bit_length.
  • Which side carries the unused backing bits is identified by padding; the default is Padding.LEFT.
  • For a buffer whose backing is at its normal capacity, the padding-bit count comes to 8 * len(content) - bit_length. Under Padding.LEFT, the least-significant bit_length bits of content make up the significant sequence, which puts the padding on the leading, most-significant side. Under Padding.RIGHT, the most-significant bit_length bits of content make up the significant sequence, which puts the padding on the trailing, least-significant side.
  • Construction must not require that content hold enough physical bits for bit_length. To be specific, Buffer(content=b'', bit_length=16) — that is, a positive bit_length alongside shorter content — is valid, and construction must not raise merely on the grounds that the declared length goes past 8 * len(content). This is what allows empty-backed values to serve as ignored field values and rule-target placeholders. The content and bit_length handed to construction are kept as supplied; no missing bytes get synthesized.
Instance attributes

Readable attributes — content (bytes), bit_length (int), and padding (a Padding value) — are exposed by every instance.

Equality and hashing behaviour

Two Buffer instances are equal precisely when their bit_length values match and their significant-bit sequences match. Logical equality leaves out the padding side and any backing-representation detail that leaves the significant bits untouched. Notably, a right-padded result that pad has realigned is equal to an explicitly built left-padded buffer carrying the same significant bits and length. Bit content that matches while bit_length values differ means the buffers are not equal.

Because buffers serve as mapping keys, Buffer must be hashable, and its hashing must stay consistent with this equality.

shift(shift: int, inplace: bool = False) -> Buffer

This call moves the significant sequence around within the buffer. When shift is negative, the effect is a left shift by abs(shift) bits; when it is positive, the effect is a right shift by shift bits. For inplace=False, a new Buffer is returned and the original stays unchanged. The padding side the original had is preserved in the result.

The semantics, applied to the significant sequence, are these:

  • Left shift: bit_length is increased by the shift amount, and the significant bits are moved toward the most-significant side, with the newly significant zero bits retained on the least-significant side. The current backing-byte length is preserved whenever the increased bit_length still fits into the existing content, even where a minimal representation could get by with fewer bytes. content is grown only when the new bit length goes beyond the current capacity. If growth turns out to be needed, null-byte capacity is added, and the length taken is exactly the smallest whole-byte length that can hold the increased bit length. Another way to state it: the resulting byte count is max(len(content), ceil(new_bit_length / 8)).
  • Right shift: bit_length is decreased by the shift amount, and the least-significant bits are dropped. The length of the backing content is preserved.

Worked examples, each of them with inplace=False:

  • Buffer(b'\x2d', bit_length=7, padding=Padding.LEFT).shift(-10) yields content == b'\x00\xb4\x00' and bit_length == 17; the backing storage grows from a single byte to three.
  • Buffer(b'\x00\x08\x2d', bit_length=12, padding=Padding.LEFT).shift(-2) yields content == b'\x00\x20\xb4' and bit_length == 14; all three backing bytes already present are kept, although 14 bits would have fitted into two bytes.
  • Buffer(b'\x08\x28\x00', bit_length=13, padding=Padding.RIGHT).shift(-2) yields content == b'\x08\x28\x00' and bit_length == 15; the three-byte backing length is preserved here too.
  • Buffer(b'\x00\x08\x2d', bit_length=12, padding=Padding.LEFT).shift(3) yields content == b'\x00\x01\x05' and bit_length == 9.
  • Buffer(b'\x00\x08\x2d', bit_length=12, padding=Padding.LEFT).shift(6) yields content == b'\x00\x00\x20' and bit_length == 6.
trim(inplace: bool = False) -> Buffer

Example:

comes out equal to Buffer(b'\x08\x28', bit_length=13, padding=Padding.RIGHT).

The buffer that comes back holds the same significant bits and bit_length, with its padding sitting on the side that was requested. By way of example, length 14 is encoded as 1110; length 15 as 1111 00001111; and length 255 as 1111 11111111 0000000011111111. Advancing the cursor must cover both the selected prefix width and the decoded number of field-value bits.

Remaining payload

Once every applicable rule field has been reconstructed, append every still-unconsumed significant bit of schc_packet, unchanged, after the reconstructed fields. This suffix is the payload of the original packet and need not be represented by another rule field.

The suffix starts exactly at the final residue cursor and ends at schc_packet.bit_length. Do not append unused bits whose only role is to fill the last backing byte of schc_packet. When no significant bits remain, nothing is appended. Concatenating the payload is a bitwise operation and must also work when the preceding reconstructed fields or the payload boundary are not byte-aligned.

Correctness requirements

Given a valid SCHC packet, a matching rule, and a direction:

  • the Rule ID is consumed but left out of the result;
  • only direction-applicable descriptors have an effect on reconstruction;
  • each applicable CDA consumes exactly its defined residue bits and emits exactly the field bits it reconstructs;
  • fixed- and variable-length VALUE_SENT fields, all length-prefix escape forms included, are decoded correctly;
  • Rule IDs, fields, LSB residues, and mapping indices that are non-byte-aligned remain in the correct bit order;
  • all of the remaining significant residue bits are preserved as the payload, while backing-byte padding is excluded; and
  • the returned packet is the ordered bit-concatenation of all reconstructed fields together with that payload suffix, reproducing the original packet exactly.

Overview

You are working on the packet-parsing library (microschc), which parses network protocol headers into structured descriptors. You must update the parser components so that they operate on a Buffer object as input (in place of raw bytes), and you must add to each parser a match method that verifies whether a given buffer is a valid input for that parser.

Background on the Buffer type

A Buffer (in microschc.binary.buffer) pairs binary content with an explicit bit length. It is constructed in the following way:

Buffer(content=<bytes>, length=<number_of_bits>)

where length is the size, in bits, of the meaningful content (i.e. len(content) * 8 when the whole byte string is significant).

Required API surface

The parser classes below, together with their public methods, must exist and be callable as described.

Protocol parsers

Each of these classes resides under microschc.parser.protocol.* and can be instantiated with no arguments:

  • IPv4Parser
  • IPv6Parser
  • UDPParser
  • CoAPParser

Each of the parsers must expose:

  1. parse(self, buffer: Buffer) -> HeaderDescriptor

    • The buffer keyword argument accepts a Buffer object.
    • It parses the header contained in the buffer and returns a HeaderDescriptor.
    • The individual parsed fields that are returned (as FieldDescriptor objects accessible on the descriptor) must have value attributes that are Buffer objects sliced from the input and that correctly reflect the exact bit range of each field. In particular, multi-byte fields must keep their full byte width — e.g. a 16-bit value such as decimal 104 (0x0068) must be represented as the two bytes b'\x00\x68', not truncated to a single byte.

  2. match(self, buffer: Buffer) -> bool

    • It accepts a Buffer object.
    • When the buffer is a valid input that this parser can parse, the method returns a truthy value (True).
    • match returns True for each of the valid sample packets described below.
