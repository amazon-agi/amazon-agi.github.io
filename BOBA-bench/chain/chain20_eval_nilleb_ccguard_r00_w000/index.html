Task Specification: Redis Storage Adapter for ccguard

Overview

The ccguard module currently provides a SqliteAdapter class for persisting and retrieving coverage data associated with commits. You must add a new adapter, RedisAdapter, that provides the same interface but stores its data in Redis (via the redis Python library).

Public API to Implement

Add a class RedisAdapter to the ccguard module.

Constructor
RedisAdapter(reference, config)
  • reference: a string identifier (a repository/namespace key) under which coverage data is grouped.
  • config: a configuration mapping/object as produced by ccguard.configuration(...).

The adapter must obtain a Redis client by calling redis.Redis(...). (Instantiation of the client happens during construction/use of the adapter.)

Context Manager Protocol

RedisAdapter must be usable as a context manager:

with ccguard.RedisAdapter("test", config) as adapter:
    ...

Entering the context must return the adapter instance (or an object exposing the methods below). Exiting the context must complete cleanly.

Methods

The adapter must expose the same behavioral contract as the existing SqliteAdapter:

  • persist(commit_id, data)

    • commit_id: a string identifying a commit.
    • data: a string payload (e.g. XML coverage content).
    • Stores the payload so it can later be retrieved by the same commit_id, scoped to the adapter's reference.

  • get_cc_commits()

    • Returns a collection of all commit identifiers that have been persisted under the adapter's reference.
    • The number of distinct persisted commit ids must equal the length of this collection.

  • retrieve_cc_data(commit_id)

    • Returns the payload string previously persisted for the given commit_id under the adapter's reference.

Required Storage Semantics (Redis Access Pattern)

The adapter must interact with the Redis client using Redis hash operations, keyed by the adapter's reference:

  • Persisting a (commit_id, data) pair must call hset(reference_key, commit_id, data) — i.e. store data in a hash (whose key is derived from the reference) at field commit_id.
  • Listing commits must call hkeys(reference_key) and return the set/collection of field names (commit ids) present in that hash.
  • Retrieving data for a commit_id must call hget(reference_key, commit_id) and return the stored value.

The three arguments to hset are (hash_key, field, value); hkeys takes (hash_key); hget takes (hash_key, field). The reference_key (first argument) is determined solely by the adapter's reference and must be consistent across all three operations so that data persisted can subsequently be listed and retrieved.

Behavioral Requirements

Given a freshly constructed adapter:

  1. Persisting three distinct commit ids each with its own payload results in get_cc_commits() returning exactly three commit identifiers.
  2. retrieve_cc_data(commit_id) for any persisted commit id returns that commit's exact payload string.

Configuration

The config object is produced by the existing ccguard.configuration(path) function and is passed through to the adapter. The adapter must accept and use it consistently with how SqliteAdapter accepts its config argument.

The existing /coverage/sources/source value is an absolute directory prefix under which the covered source files resided when the report was generated. Class filename attributes may be relative to that directory.

Required Normalization Behavior

Repository-root metadata source

Add a new <source> child inside /coverage/sources with exactly this attribute:

class="ccguard-meta-sources-root"

Its text content must contain the supplied repository-root path from sources. This is an additional source entry; it does not replace the report's existing source entry.

Repository-relative class filenames

Rewrite every filename attribute selected by packages/package/classes/class/@filename relative to the returned root so that it is relative to the repository root rather than merely relative to the report's original source directory.

For example, if the repository root is /work/ccguard, the report source is /work/ccguard/ccguard, and a class filename is ccguard.py, the normalized filename must be ccguard/ccguard.py. The source subdirectory beneath the repository directory is therefore retained as part of the normalized path.

Deriving the repository-relative prefix

The prefix prepended to each class filename must be derived as follows:

  • When the report's original source path lies directly beneath the supplied repository root (sources), the prefix is the source path expressed relative to that root. For a repository root of /work/ccguard and a report source of /work/ccguard/ccguard, the prefix is ccguard.
  • When the report was generated on another machine, so that the original source path does not lie under sources, the prefix must be derived from the report's source path alone: use the source directory's trailing name component. For a report source of /usr/local/sources/ccguard/ccguard, the prefix is ccguard.

In both cases, a relative class filename such as ccguard.py must normalize to ccguard/ccguard.py.

Reports generated on another machine

Normalization must not depend on the original absolute source path existing on the current machine or sharing its leading directories with sources. No on-disk existence check may make the result depend on where the report was produced.

Critically, the cross-machine derivation must not rely on the current repository root's directory-name component (its basename) appearing anywhere in the report's original source path. The repository may be checked out under an arbitrary directory name (for example /testbed) that differs entirely from the repository or project name embedded in the report's source path (for example /usr/local/sources/ccguard/ccguard). Even in that situation, the prefix must come from the report source path's own trailing name component, so a report source of /usr/local/sources/ccguard/ccguard yields the prefix ccguard and a class filename ccguard.py normalizes to ccguard/ccguard.py, regardless of the current repository root's basename. Implementations that search for the repository root's basename inside the source path, and leave filenames un-prefixed when it is not found, are incorrect.

Thus, with a current repository root such as /work/ccguard (or any other root, such as /testbed), both of these report source values describe the same repository-relative source subdirectory:

  • <REPOSITORY_ROOT>/ccguard (a subdirectory of the current repository root)
  • /usr/local/sources/ccguard/ccguard (a foreign absolute path)

A relative class filename such as ccguard.py must normalize to ccguard/ccguard.py in either case.

Preservation of report entries

Preserve every input <class> entry and normalize its filename; do not filter entries according to whether their referenced files currently exist. Files that have since been deleted must remain represented in the returned XML.

Required Cobertura Resource

Provide a readable, well-formed Cobertura-format XML document at the repository-relative path ccguard/test_data/paths.xml. It must:

  • have a <coverage> root with a /coverage/sources/source element;
  • contain exactly three class entries across /coverage/packages/package/classes/class;
  • give every class entry a filename attribute expressed relative to the report's source directory;
  • include at least one class entry whose referenced file no longer exists in the repository, demonstrating that stale report entries are preserved; and
  • be suitable for replacing its first source value either with the current repository root followed by /ccguard (whatever the root's own directory name may be) or with a differently rooted absolute directory ending in ccguard/ccguard, after which normalization produces all three filenames as repository-relative paths beginning with ccguard/.

Compatibility and Scope

  • Use lxml.etree for XML parsing and manipulation.
  • GitAdapter already supplies get_root_path() and does not need to be modified; its result is the kind of value passed as sources.
  • The previously existing function detect_source is no longer part of the public API and must be removed.
  • The normalizer changes path metadata and class filename attributes; it must not discard class coverage data or class nodes.
20 You are to implement three command-line utility modules within the ccguard package 822 words · source specification

You are to implement three command-line utility modules within the ccguard package: ccguard_diff, ccguard_show, and additions to ccguard_log. These modules operate on code coverage data retrieved through a shared adapter mechanism.

Shared Infrastructure Assumptions

The package ccguard exposes a module-level callable ccguard.adapter_factory (referenced as ccguard.adapter_factory from within each module — i.e., each module must import ccguard and reference ccguard.adapter_factory).

ccguard.adapter_factory(...) returns an adapter class. That adapter class is used as a context manager (with adapter_class(...) as adapter:), and the object yielded by __enter__ (the adapter) provides:

  • adapter.get_cc_commits() → returns an iterable/list of commit id strings.
  • adapter.retrieve_cc_data(commit_id) → returns bytes containing a coverage XML document. The relevant content is a <coverage> element carrying a line-rate attribute expressed as a fractional string, e.g. b'<coverage line-rate="0.791" />'. A line-rate of 0.791 corresponds to a coverage percentage of 79.10%.

The way adapter_factory is invoked and how its return value is used to obtain an adapter instance must follow the pattern above: the module calls ccguard.adapter_factory(...), then enters the returned class as a context manager to get the adapter.

Coverage percentages are formatted as a numeric value with two decimal places followed by a % sign (e.g. 79.10%). Percentage differences are formatted with a sign and two decimal places followed by % (e.g. -3.00%).

Module: ccguard.ccguard_show

Provide a function:

def main(args, log_function=print):

Behavior:

  • args is a list of command-line-style arguments. When called with a single-element list containing a commit id (e.g. ["dcba"]), that commit id identifies the coverage report to display.
  • The function must obtain an adapter via the shared ccguard.adapter_factory mechanism described above, retrieve the coverage data for the given commit id via adapter.retrieve_cc_data(commit_id), and parse the line-rate.
  • The function reports information by calling log_function(...) one or more times, each call receiving a single string argument. Collected in call order:
    • The first logged string must contain the commit id.
    • The last logged string must contain the coverage percentage formatted as described (e.g. 79.10%).
  • The function must produce an HTML file on disk named cc-<commit_id>.html (e.g. for commit id dcba, the file cc-dcba.html must exist after the call).
  • On success the function must return a falsy value (e.g. None or 0).

Module: ccguard.ccguard_diff

Provide a function:

def main(args, log_function=print):

Behavior:

  • args is a list of two commit ids: [commit_a, commit_b]. In the exercised scenario the first element is the newer/target commit and the second is the reference commit.
  • The function must obtain an adapter via the shared ccguard.adapter_factory mechanism and retrieve coverage data for both commits via adapter.retrieve_cc_data(commit), parsing each line-rate.
  • The function reports information by calling log_function(...) one or more times, each with a single string argument. Collected in call order:
    • The first logged string must contain both commit ids.
    • The last logged string must contain the signed percentage difference between the two coverage values, formatted with a sign and two decimals plus %. Specifically, with reference coverage 0.791 and target coverage 0.821 given args=[ "abcd" (target, 0.821), "dcba" (ref, 0.791) ], the difference reported must be -3.00%. That is, the reported delta is (reference_rate - target_rate) expressed as a percentage: (0.791 - 0.821) = -0.030 → -3.00%.
  • The function must produce an HTML diff file on disk named diff-<args[0]>-<args[1]>.html — that is, using the two argument commit ids in the order they were passed. For args=["abcd", "dcba"] the file diff-abcd-dcba.html must exist after the call.
  • On success the function must return a falsy value.

Module: ccguard.ccguard_log (additions)

This module already exists and provides reference-listing functionality. Add/adjust the following:

Public class: AnnotatedCommit

ccguard_log.AnnotatedCommit is a class representing a commit annotated with coverage information. Instances must satisfy:

  • str(instance) returns a non-empty string.
  • repr(instance) returns a string equal to str(instance).
Public function: main
def main(args, logging_function=print):

Behavior:

  • args is a list of command-line-style arguments (may be empty).
  • The function obtains an adapter via the shared adapter mechanism (ccguard.adapter_factory) and iterates over the repository's commits.
  • The repository is accessed via git.Repo(...). The repo object provides:
    • repo.iter_commits() → yields git.Commit objects (the commits to be listed).
    • repo.commit(commit) → resolves/returns a git.Commit object.
  • For each commit obtained by iterating, the function must call logging_function(...) exactly once, passing a single AnnotatedCommit instance. Thus, if iteration yields N commits, logging_function is called N times, once per commit, each with an AnnotatedCommit.
  • The count and order of logging_function calls corresponds one-to-one with the commits yielded by repo.iter_commits().

General Notes

  • Each of the three modules must be importable as ccguard.ccguard_diff, ccguard.ccguard_show, and ccguard.ccguard_log.
  • Each module must reference the shared adapter factory as ccguard.adapter_factory (via import ccguard), so it can be substituted at runtime.
  • The log_function / logging_function parameter is a callable accepting a single positional argument; it defaults to print but callers may supply an alternative collector.
