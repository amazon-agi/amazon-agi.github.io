Task Specification: A Redis Storage Adapter for ccguard

Summary

At present, the ccguard module provides a SqliteAdapter class that persists and retrieves coverage data tied to commits. You must add a new adapter, RedisAdapter, that offers the same interface but stores its data in Redis (using the redis Python library).

Public API to Implement

Add a RedisAdapter class to the ccguard module.

Constructor
RedisAdapter(reference, config)
  • reference: a string identifier (a repository/namespace key) that coverage data is grouped under.
  • config: a configuration mapping/object as generated by ccguard.configuration(...).

To obtain a Redis client, the adapter must call redis.Redis(...). (The client is instantiated during construction/use of the adapter.)

Context Manager Protocol

It must be possible to use RedisAdapter as a context manager:

with ccguard.RedisAdapter("test", config) as adapter:
    ...

Entering the context must return the adapter instance (or an object that exposes the methods below), and leaving the context must complete cleanly.

Methods

The adapter must expose the same behavioral contract as the SqliteAdapter that already exists:

  • persist(commit_id, data)

    • commit_id: a string that identifies a commit.
    • data: a string payload (e.g. XML coverage content).
    • The payload is stored so that it can later be retrieved by the same commit_id, scoped to the adapter's reference.

  • get_cc_commits()

    • Returns a collection consisting of all commit identifiers that have been persisted under the adapter's reference.
    • The length of this collection must equal the number of distinct persisted commit ids.

  • retrieve_cc_data(commit_id)

    • Returns the payload string that was previously persisted for the given commit_id under the adapter's reference.

Required Semantics for Storage (Redis Access Pattern)

The adapter must interact with the Redis client by means of Redis hash operations, keyed by the adapter's reference:

  • Persisting a (commit_id, data) pair must call hset(reference_key, commit_id, data) — that is, it stores data in a hash (whose key is derived from the reference) at field commit_id.
  • Listing commits must call hkeys(reference_key) and return the set/collection made up of the field names (commit ids) present in that hash.
  • Retrieving data for a commit_id must call hget(reference_key, commit_id) and return the value that was stored.

The three arguments passed to hset are (hash_key, field, value); hkeys takes (hash_key); hget takes (hash_key, field). The reference_key (first argument) is determined solely by the adapter's reference and must be consistent across all three operations so that data that has been persisted can subsequently be listed and retrieved.

Required Behavior

For an adapter that has just been constructed:

  1. Persisting three distinct commit ids, each with its own payload, results in get_cc_commits() returning exactly three commit identifiers.
  2. For any persisted commit id, retrieve_cc_data(commit_id) returns that commit's exact payload string.

Configuration

The config object is created by the existing ccguard.configuration(path) function and is passed on to the adapter. The adapter must accept it and use it consistently with how SqliteAdapter accepts its config argument.

Task Description

Summary

Implement normalization of paths in Cobertura-style XML coverage reports. The normalizer must rewrite the filename of every covered class so that it is relative to a supplied repository root, even in cases where the report was generated under a different absolute filesystem prefix, and even in cases where the name of the current repository checkout directory is unrelated to the project name embedded in the report. In addition, provide the repository resource described below.

Module and Its Public API

Within the module ccguard.ccguard, implement:

def normalize_report_paths(report, sources):
    ...
Parameters
  • report: a readable binary file-like object, positioned at the start, that contains a Cobertura-style XML coverage report.
  • sources: a string that contains the absolute path to the repository root, of the kind returned by GitAdapter(".").get_root_path().
Return Value

Return the root element of the parsed and modified XML document as an lxml.etree element. Callers must be able to run XPath queries directly against this returned element.

Relevant Structure of the Input

The relevant Cobertura structure of the input is the following:

<coverage>
  <sources>
    <source>ABSOLUTE_PATH_TO_SOURCE_ROOT</source>
  </sources>
  <packages>
    <package>
      <classes>
        <class filename="..."/>
        ...
      </classes>
    </package>
    ...
  </packages>
</coverage>

The value already present at /coverage/sources/source is an absolute directory prefix under which the covered source files resided at the time the report was generated. The filename attributes of classes may be relative to that directory.

Normalization Behavior Required

Metadata Source for the Repository Root

Add a new <source> child inside /coverage/sources, carrying exactly this attribute:

class="ccguard-meta-sources-root"

Its text content must contain the repository-root path supplied through sources. This is an additional source entry; the report's existing source entry is not replaced by it.

Class Filenames Relative to the Repository

Rewrite every filename attribute selected by packages/package/classes/class/@filename relative to the returned root, so that it ends up relative to the repository root rather than merely relative to the report's original source directory.

For example, given a repository root of /work/ccguard, a report source of /work/ccguard/ccguard, and a class filename of ccguard.py, the normalized filename must be ccguard/ccguard.py. The source subdirectory beneath the repository directory is therefore kept as part of the normalized path.

How the Repository-Relative Prefix Is Derived

The prefix that is prepended to each class filename must be derived in the following manner:

  • When the report's original source path lies directly beneath the repository root supplied via sources, the prefix is the source path expressed relative to that root. Given a repository root of /work/ccguard and a report source of /work/ccguard/ccguard, the prefix is ccguard.
  • When the report was generated on another machine, so that the original source path does not lie under sources, the prefix must be derived from the report's source path alone: take the source directory's trailing name component. Given a report source of /usr/local/sources/ccguard/ccguard, the prefix is ccguard.

In both cases, a relative class filename like ccguard.py must normalize to ccguard/ccguard.py.

Reports Produced on Another Machine

Normalization must not depend on the original absolute source path existing on the current machine or on its leading directories being shared with sources. No on-disk existence check may cause the result to depend on where the report was produced.

Critically, the cross-machine derivation must not rely on the directory-name component of the current repository root (its basename) appearing anywhere in the report's original source path. The repository may be checked out under an arbitrary directory name (for example /testbed) that is entirely different from the repository or project name embedded in the report's source path (for example /usr/local/sources/ccguard/ccguard). Even in that situation, the prefix must come from the report source path's own trailing name component, so that a report source of /usr/local/sources/ccguard/ccguard yields the prefix ccguard and a class filename ccguard.py normalizes to ccguard/ccguard.py, regardless of the current repository root's basename. It is incorrect for an implementation to search for the repository root's basename inside the source path and, when it is not found, leave filenames un-prefixed.

Consequently, with a current repository root such as /work/ccguard (or any other root, such as /testbed), both of the following report source values describe the same repository-relative source subdirectory:

  • <REPOSITORY_ROOT>/ccguard (a subdirectory within the current repository root)
  • /usr/local/sources/ccguard/ccguard (a foreign absolute path)

A relative class filename such as ccguard.py must normalize to ccguard/ccguard.py in either of these cases.

Preserving the Report Entries

Preserve every input <class> entry and normalize its filename; entries must not be filtered based on whether the files they reference currently exist. Files that have since been deleted must remain represented in the XML that is returned.

Cobertura Resource Required

Provide a readable, well-formed XML document in Cobertura format at the repository-relative path ccguard/test_data/paths.xml. It must:

  • have a <coverage> root that contains a /coverage/sources/source element;
  • have exactly three class entries across /coverage/packages/package/classes/class;
  • give every class entry a filename attribute that is expressed relative to the report's source directory;
  • include at least one class entry whose referenced file no longer exists in the repository, so as to demonstrate that stale report entries are preserved; and
  • be suitable for having its first source value replaced either with the current repository root followed by /ccguard (whatever the root's own directory name may be) or with an absolute directory with a different root that ends in ccguard/ccguard, after which normalization produces all three filenames as repository-relative paths that begin with ccguard/.

Scope and Compatibility

  • Use lxml.etree for parsing and manipulating XML.
  • GitAdapter already supplies get_root_path() and does not need to be modified; its result is the kind of value that gets passed as sources.
  • The function detect_source, which existed previously, is no longer part of the public API and must be removed.
  • The normalizer alters path metadata and the class filename attributes; it must not discard class coverage data or class nodes.

Your task is to implement three command-line utility modules inside the ccguard package: ccguard_diff, ccguard_show, and additions to ccguard_log. These modules work with code coverage data that they retrieve through a shared adapter mechanism.

Assumptions About the Shared Infrastructure

The package ccguard exposes a module-level callable ccguard.adapter_factory (inside each module it is referenced as ccguard.adapter_factory — that is, each module must import ccguard and reference ccguard.adapter_factory).

ccguard.adapter_factory(...) returns an adapter class. This adapter class is used as a context manager (with adapter_class(...) as adapter:), and the object yielded by __enter__ (the adapter) supplies:

  • adapter.get_cc_commits() → returns commit id strings as an iterable/list.
  • adapter.retrieve_cc_data(commit_id) → returns bytes holding a coverage XML document. The content that matters is a <coverage> element carrying a line-rate attribute expressed as a fractional string, e.g. b'<coverage line-rate="0.791" />'. Both the way adapter_factory is invoked and the way its return value is used to obtain an adapter instance must follow the pattern above: the module calls ccguard.adapter_factory(...), then enters the returned class as a context manager to get the adapter.

A coverage percentage is formatted as a numeric value with two decimal places followed by a % sign (e.g. 79.10%). A percentage difference is formatted with a sign and two decimal places followed by % (e.g. -3.00%).
