async def async_login(self)

Performs a login by issuing an HTTP POST via self._session.post(...) used as an async context manager (i.e. async with self._session.post(...) as resp:).

  • The POST must be called exactly once with:
    • URL: "https://www.csnetmanager.com/login"
    • keyword argument headers (any value)
    • keyword argument cookies (any value)
    • keyword argument data equal to exactly:
      {
    "_csrf": "be186598-c4d0-4d16-80f0-dc2ab35aad23",
    "token": "",
    "username": <self.username>,
    "password_unsanitized": <self.password>,
    "password": <self.password>,
}
  • The response's body is obtained via await response.text().
  • Login success is determined by inspecting the response body text: if the body text contains the substring loadContent("login"), the login has FAILED (the site returns HTTP 200 and re-renders the login page on bad credentials). Otherwise the login SUCCEEDED.

  • On failure: set self.logged_in = False and return False.

    • keyword argument cookies (any value)

  • Return False for None.
1.2 reverse_bcd(self, value) -> int

Performs a reverse-BCD conversion using the formula:

((tens_digit - 1) * 16) + (ones_digit + 10)

where tens_digit and ones_digit are the decimal tens and ones digits of value.

  • reverse_bcd(62) → 92 (i.e., (6-1)*16 + (2+10))
  • reverse_bcd(91) → 139 (i.e., (9-1)*16 + (1+10))
  • reverse_bcd(92) → 140 (i.e., (9-1)*16 + (2+10))
1.3 get_alarm_code_formatted(self, alarm_code) -> str

Returns a human-facing string form of the alarm code.

  • For None or 0, return "0".
  • For a non-BCD code (high byte not set), return the decimal value as a string. Examples: 62 → "62", 100 → "100".
  • For a BCD code (high byte set), return the low byte (alarm_code & 0xFF) formatted as a lowercase hex string with no prefix. Examples: 0x0162 → "62", 0xFF62 → "62" (low byte 0x62 = hex "62").
1.4 get_correct_rad_hex_error_code(self, code) -> int

Applies RAD-unit offset corrections to an alarm code.

  • None → 0.
  • code of 61 or 63 → returned unchanged.
  • code <= 0 → returned unchanged (e.g., 0 → 0, -1 → -1).
  • 0 < code < 113 → subtract 10. Examples: 100 → 90, 112 → 102.
  • 113 <= code <= 129 → subtract 112. Examples: 113 → 1, 120 → 8, 129 → 17.
  • code >= 130 → subtract 28. Examples: 130 → 102, 150 → 122.

(The special cases 61 and 63 take priority over the range rules.)

1.5 is_yutaki(self, sensor_data, installation_data) -> bool

Returns True if sensor_data["zone_id"] is 5 (yutaki) or 3 (water heater); otherwise False.

  • {"zone_id": 5} → True
  • {"zone_id": 3} → True
  • {"zone_id": 1} → False
1.6 get_unit_type(self, sensor_data, installation_data) -> str

Determines the unit type string:

  • If sensor_data["zone_id"] == 3 → "water_heater".
  • If sensor_data["zone_id"] == 5 → "yutaki".
  • Otherwise, if installation_data is provided and its heatingStatus.systemConfigBits has the fan-coil bit set (systemConfigBits & 0x2000 nonzero) → "fan_coil".
  • Otherwise → "standard". This includes the case where installation_data is None, and the case where systemConfigBits is 0x0000.
1.7 get_alarm_origin(self, alarm_code, unit_type, installation_data) -> str

Determines a human-readable alarm origin string, using the self.translations dict for the display text.

General rules:

  • If unit_type is not a yutaki-type unit (i.e., not "yutaki" or "water_heater"), return "".
  • If alarm_code is None or 0, return "".

For yutaki-type units ("yutaki" or "water_heater"), map codes to origins. The returned string is the value looked up from self.translations by key.

Non-BCD (standard) codes map as follows (values shown are the translation values used in tests):

alarm code translation key resulting string
2 STR_REFRIGERANT_CYCLE "Refrigerant Cycle"
3 STR_ORIGIN_TRANSMISSION "Transmission"
5 STR_ORIGIN_POWER_SUPPLY "Power Supply"
10, 11, 13 STR_ORIGIN_INDOOR "Indoor Unit"
60 STR_ORIGIN_COMUNICATION "Communication"
101, 105 STR_ORIGIN_2ND_CYCLE "2nd Cycle"

Codes 11 and 13 group into the same origin as 10 ("Indoor Unit"); codes 101 and 105 both map to "2nd Cycle".

BCD codes (high byte set): extract the low byte value (alarm_code & 0xFF, e.g. 0x62 = 98 decimal... note: the raw BCD low-byte hex value is examined). For the BCD case, the low byte hex value 0x62 maps to the STR_ORIGIN_INVERTER key, yielding "Inverter".

  • get_alarm_origin(0x0162, "yutaki", None) → "Inverter"
  • get_alarm_origin(0xFF62, "yutaki", None) → "Inverter"

The following additional translation keys are expected to be recognized/used by the origin logic (present in the translations dict supplied at runtime): STR_ORIGIN_INVERTER, STR_ORIGIN_COMPRESSOR, STR_ORIGIN_OUTDOOR_FAN, STR_REFRIGERANT_CYCLE, STR_ORIGIN_TRANSMISSION, STR_ORIGIN_POWER_SUPPLY, STR_ORIGIN_INDOOR, STR_ORIGIN_2ND_CYCLE, STR_ORIGIN_COMUNICATION.

1.8 async_get_elements_data(self) — new fields

The existing async_get_elements_data method returns a dict with a "sensors" list. Each sensor dict must now additionally contain these three keys:

  • "unit_type": the value from get_unit_type.
  • "alarm_code_formatted": the value from get_alarm_code_formatted applied to the sensor's alarm code.
  • "alarm_origin": the value from get_alarm_origin (empty string for non-yutaki units).

Behavior for the default/normal case (element with elementType that maps to a standard zone and no alarm): unit_type == "standard", alarm_code_formatted == "0", alarm_origin == "".

For an element whose elementType is 5 (yutaki, zone_id 5) with alarmCode of 62:

For an element whose elementType is 5 with alarmCode of 0x0162 (BCD):

  • alarm_code = 0x0162, alarm_code_formatted = "62", unit_type = "yutaki".

CSNetHomeInstallationSensor(

    sensor_key,
    sensor_type,

    display_name,
)

Where:

  • coordinator — object exposing a method get_installation_devices_data() returning a dict (see data structure below).
  • device_data — dict with keys device_name, device_id, room_name, parent_id, room_id.
  • common_data — dict with keys such as name and firmware.
  • sensor_key — string identifying the sensor variant (see below).

The class must expose:

  • a state property returning the sensor's current value.
  • a name property returning the composed display name.

Data Source

The coordinator's get_installation_devices_data() returns a dict. The system configuration bitmask is located at:

result["data"][0]["indoors"][0]["heatingStatus"]["systemConfigBits"]

This value is an integer bitmask. If any part of this path is missing or the returned dict is empty (e.g. {}), the bitmask must be treated as unavailable.

For each of the following sensor_key values, the state property must return STATE_ON when the corresponding bit is set in systemConfigBits, and STATE_OFF when it is not set:

sensor_key Bit mask
cascade_slave_mode 0x1000
fan_coil_compatible 0x2000
c1_thermostat_present 0x40
c2_thermostat_present 0x80

A bit is "set" when systemConfigBits & mask is non-zero. Each sensor is independent; other bits being set or unset must not affect a given sensor's result.

STATE_ON and STATE_OFF refer to the standard Home Assistant state constants ("on" / "off").

Edge Cases

  • When systemConfigBits is 0, all four sensors return STATE_OFF.
  • When only some bits are set, each sensor returns STATE_ON/STATE_OFF strictly according to its own bit.
  • When the installation devices data is empty or the systemConfigBits path cannot be resolved, all four sensors return STATE_OFF.

The name property must produce a string of the form:

<device_name> <room_name> <display_name>

That is, the values of device_data["device_name"] and device_data["room_name"], followed by the display_name argument, joined by single spaces. For example, with device_name="System", room_name="Controller", and display_name="Cascade Slave Mode", the name is:

System Controller Cascade Slave Mode

Scope Notes

  • No other sensor types or behaviors need to change.
  • Only the four sensor_key values listed above are in scope for this task.

Overview

Note: heating supports NONE, POINTS, GRADIENT, FIX. Cooling supports NONE, POINTS, FIX (no GRADIENT). The numeric values above are the exact values the constants must hold.

Code Name
0 "None"
1 "Points"

2. Climate Entity OTC Attributes

Modify the climate entity CSNetHomeClimate (in custom_components/csnet_home/climate.py), specifically its extra_state_attributes property.

The entity is constructed as CSNetHomeClimate(hass, entry, sensor_data, common_data). The coordinator is available via hass.data[DOMAIN][entry.entry_id]["coordinator"] and exposes get_installation_devices_data().

Source of OTC data

For climate entity attributes, OTC data comes from the installation devices data at:

installation_devices_data["heatingStatus"]

which contains keys otcTypeHeatC1, otcTypeCoolC1, otcTypeHeatC2, otcTypeCoolC2 (numeric type codes).

Circuit selection based on zone_id

The climate entity's sensor_data contains a zone_id. OTC attributes must be selected from either circuit 1 (C1) or circuit 2 (C2) based on the zone, or omitted entirely:

  • zone_id 1 → use circuit 1 (C1) values.
  • zone_id 2 → use circuit 2 (C2) values.
  • zone_id 5 (water circuit) → use circuit 1 (C1) values.
  • zone_id 3 (DHW) → OTC attributes must NOT be present.

Any zone that maps to a circuit produces OTC attributes; a zone that does not map to a heating/cooling circuit (such as DHW) produces none.

Attributes to add

When OTC data is available AND the zone maps to a circuit, add exactly these four keys to extra_state_attributes:

  • otc_heating_type — the numeric heating type code for the selected circuit.
  • otc_heating_type_name — the human-readable name for that code.
  • otc_cooling_type — the numeric cooling type code for the selected circuit.
  • otc_cooling_type_name — the human-readable name for that code.

Example: for zone_id == 1 with otcTypeHeatC1 == 3 and otcTypeCoolC1 == 3, the attributes are otc_heating_type == 3, otc_heating_type_name == "Fixed", otc_cooling_type == 3, otc_cooling_type_name == "Fixed".

Example: for zone_id == 2 with otcTypeHeatC2 == 2 and otcTypeCoolC2 == 1, the attributes are otc_heating_type == 2, otc_heating_type_name == "Gradient", otc_cooling_type == 1, otc_cooling_type_name == "Points".

Omission conditions

None of the four OTC keys may appear in extra_state_attributes when:

  • get_installation_devices_data() returns None (no installation data), OR
  • the zone does not map to a circuit (e.g. zone_id == 3 / DHW).

The addition of these attributes must not interfere with any pre-existing attributes.
