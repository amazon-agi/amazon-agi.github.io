Task Specification: API and Coordinator for the CSNet Home Integration

Overview

Build a Python integration package custom_components.csnet_home that interacts with the CSNet Manager cloud service (a Home Assistant custom component). The API client, a data-update coordinator, and a small constants module must all be created. The only behavior required is the behavior described below.

Modules and Public API

1. custom_components/csnet_home/const.py

The following must be defined:

  • DOMAIN — a string constant at module level that identifies the integration domain.
2. custom_components/csnet_home/api.py

A class CSNetHomeAPI must be defined.

Constructor
CSNetHomeAPI(hass, username, password)
  • Accepts a Home Assistant instance (the first positional arg), a username, and a password.
  • After construction is complete:
    • self.username is equal to the provided username.
    • self.password is equal to the provided password.
    • self.session is None.

The instance must also support an internal session attribute self._session, which callers may assign directly (an aiohttp-style client session object). The API's request methods must use self._session when performing HTTP calls.

async def async_login(self)

Performs a login by issuing an HTTP POST through self._session.post(...), which is used as an async context manager (i.e. async with self._session.post(...) as resp:).

  • The POST must be called exactly once, with:
    • URL: "https://www.csnetmanager.com/login"
    • a headers keyword argument (any value)
    • a cookies keyword argument (any value)
    • a data keyword argument equal to exactly:
      {
    "_csrf": "be186598-c4d0-4d16-80f0-dc2ab35aad23",
    "token": "",
    "username": <self.username>,
    "password_unsanitized": <self.password>,
    "password": <self.password>,
}
  • The body of the response is obtained via await response.text().
  • Login success is decided by examining the response body text: if the body text contains the substring loadContent("login"), the login has FAILED (on bad credentials the site returns HTTP 200 and re-renders the login page). Otherwise the login SUCCEEDED.
  • On success: the method sets self.logged_in = True and returns True.
  • On failure: the method sets self.logged_in = False and returns False.
async def async_get_elements_data(self)

Retrieves element/sensor data and transforms it. An HTTP GET is issued via self._session.get(...), used as an async context manager.

  • The GET must be called exactly once, with:

    • URL: "https://www.csnetmanager.com/data/elements"
    • a headers keyword argument (any value)
    • a cookies keyword argument (any value)

  • If the response's status is not 200 (e.g. 500), the method must return None.

  • When the status is 200, the payload is obtained via await response.json(). The payload has the following shape:

    {"status": "success", "data": { ... }}

    where data contains at least these keys: name, latitude, longitude, weatherTemperature, device_status (a list of device dicts), and elements (a list of element dicts).

  • The method must return a dictionary having exactly two top-level keys: "common_data" and "sensors".

common_data must be constructed from the payload's data:

{
    "name": data["name"],
    "latitude": data["latitude"],
    "longitude": data["longitude"],
    "weather_temperature": data["weatherTemperature"],
    "device_status": {
        <device["id"]>: {
            "name": device["name"],
            "status": device["status"],
            "firmware": device["firmware"],
        }
        for device in data["device_status"]
    },
}

Note: the keys used by device_status are the integer device IDs.

sensors must be a list with one entry per element of data["elements"], with the order preserved. Each element dict is converted in the following way:

{
    "device_name": element["deviceName"],
    "device_id": element["deviceId"],
    "room_name": element["parentName"],
    "parent_id": element["parentId"],
    "room_id": element["roomId"],
    "operation_status": element["operationStatus"],
    "mode": element["mode"],
    "real_mode": element["realMode"],
    "on_off": element["onOff"],
    "timer_running": element["timerRunning"],
    "alarm_code": element["alarmCode"],
    "c1_demand": element["c1Demand"],
    "c2_demand": element["c2Demand"],
    "ecocomfort": element["ecocomfort"],
    "current_temperature": element["currentTemperature"],
    "setting_temperature": element["settingTemperature"],
    "zone_id": <1-based index of the element in the elements list>,
}

The value of zone_id is the element's sequential position among the elements, starting at 1 for the first element.

async def close(self)

Closes the underlying session by awaiting/calling self.session.close() (calling close() on the object stored in self.session). close() must be invoked exactly once on that session object.

Overview

This task extends the Home Assistant custom integration custom_components/csnet_home, which communicates with the CSNet Home / csnetmanager API. You must add support for fetching and exposing "installation devices" data (water system and heat device measurements) across three layers: the API client, the data update coordinator, and the sensor platform.

All modifications must preserve the existing behavior of the classes being changed (their existing constructors, methods, and properties must continue to work as they did before, except where a change is explicitly required below).

1. API Client (custom_components/csnet_home/api.py)

The class CSNetHomeAPI already exists and is constructed as CSNetHomeAPI(hass, username, password). These attributes of it are relevant and are used by callers/tests:

  • _session — an aiohttp-style client session (with support for .post(...) and .get(...) async context managers).
  • logged_in — a boolean that indicates the login state.
  • cookies — a dict of session cookies.

Add the following new async method:

async def async_get_installation_devices_data(self)

It must behave as follows:

  • Login guarantee: When logged_in is falsy, the method must first run the login flow (which sends a POST through the session) before it attempts to fetch data. If logged_in is truthy, no login POST is required.
  • Request: Issue an HTTP GET against the URL:
    https://www.csnetmanager.com/data/installationdevices?installationId=-1
    The GET call must pass headers= and cookies= keyword arguments (what they contain is not asserted).
  • Success: If the response's .json() returns a value, the method must return that parsed JSON object exactly as received (a dict). This layer applies no transformation.
  • Null response: If .json() returns None, then None is what the method must return.
  • Exception handling: If the GET call raises an exception (e.g., a ConnectionError), the method must catch it and return None; the exception must not propagate. When such an exception occurs and login has not been established, logged_in must remain False (do not set it to True on failure).

2. Coordinator (custom_components/csnet_home/coordinator.py)

The class CSNetHomeCoordinator exists. Its constructor signature must be changed/confirmed to:

CSNetHomeCoordinator(hass, update_interval, entry_id)

Attributes/behavior that are required:

  • hass must be stored (accessible as coordinator.hass).
  • entry_id must be stored (accessible as coordinator.entry_id).
  • Keep an internal data attribute _device_data (a dict) holding the most recently fetched data. Tests assign to this attribute directly, so it must be a plain instance attribute that the getter methods below can read.
API lookup

The coordinator gets its API instance from Home Assistant's shared data store:

hass.data["csnet_home"][entry_id]["api"]

This value may be None.

Method: async def _async_update_data(self)
  • If the API instance is None, return None.
  • Otherwise:
    • Invoke await api.async_get_elements_data(). This returns a dict with the shape:
      {"common_data": {...}, "sensors": [...]}
    • Invoke await api.async_get_installation_devices_data().
      • If it returns a truthy value, put it into the elements result under result["common_data"]["installation_devices"], storing exactly the returned value.
      • If it returns None (or falsy), an "installation_devices" key must not be added to common_data.
    • Both API methods are invoked exactly once per update.
    • Return the resulting combined dict (with "common_data" and "sensors" keys). The returned object should also be retained internally, so that the getter methods below reflect it.

Returns the "sensors" list held in the stored device data.

Returns the "common_data" dict held in the stored device data.

def get_installation_devices_data(self)

Data source and extraction

The installation data that coordinator.get_installation_devices_data() returns has this structure:

{
  "data": [
    {
      "indoors": [
        {
          "heatingStatus": { ... measurement fields ... }
        }
      ]
    }

The measurement fields of interest sit at data[0]["indoors"][0]["heatingStatus"].

liquid_temperature liquidTemp none (raw value)

  • pumpSpeed of 100 → 1.0; 50 → 0.5; 80 → 0.8.

  • defrosting of 1 → the Home Assistant constant STATE_ON; 0 → STATE_OFF.
  • The temperature keys (gas_temperature, liquid_temperature) return the raw integer value (e.g. 20, 15, 17).

When the heatingStatus object exists but the source field mapped for a given key is absent, and when there is no reachable data at all, the sensor state is None.

Background

What this project provides is a custom integration for Home Assistant that serves CSNet Home. The code that concerns us sits in custom_components/csnet_home/climate.py, where a climate entity class is defined. Sensor data is stored by that class in the instance attribute self._sensor_data, while its display name is held in self._attr_name (assigned during initialization, and never modified afterwards).

The entity works together with a coordinator object; the get_sensors_data() method that this coordinator exposes returns a list of sensor data records. While an update is running, the entity looks for its room among the coordinator's data, and, if that search does not locate a matching record, self._sensor_data is set to None.

Problem Description

Whenever the sensor data becomes temporarily unavailable, what self._sensor_data ends up containing is None. Afterwards, calls to the update routine — and to the various property accessors that dereference self._sensor_data (e.g. by subscripting) — raise TypeError: 'NoneType' object is not subscriptable. What the entity must do instead is degrade gracefully.

Behavior Requirements

The climate entity must stay resilient when self._sensor_data is None.

async_update() (an async method taking no arguments beyond self)
  • In the case where what the coordinator's get_sensors_data() returns is an empty list (i.e., the room of the entity cannot be found and self._sensor_data becomes None), the method must complete without an error being raised.
  • If the search finds a matching sensor record, the method must populate self._sensor_data so that the property accessors below return the live values of that record.
Helper methods and property accessors

Whenever self._sensor_data is None, each of the items below must return the fallback value specified for it (and must not raise):

  • current_temperature (property) → None
  • target_temperature (property) → None
  • hvac_mode (property) → HVACMode.OFF
  • preset_mode (property) → "comfort"
  • extra_state_attributes (property) → {} (empty dict)
  • hvac_action (property) → HVACAction.IDLE
  • is_heating() (method) → False
  • is_cooling() (method) → False

(Home Assistant's standard climate enums are HVACMode and HVACAction.)

With sensor data present

Assume the sensor data is valid (the heating mode is active, the unit is on, the current temperature is 19.5, and the set point is 20.0):

  • current_temperature → the value of the current temperature (e.g. 19.5)
  • target_temperature → the value of the set point (e.g. 20.0)
  • hvac_mode → HVACMode.HEAT

Once an update has succeeded, these normal-path behaviors must remain intact.

Constraint

The entity's existing behavior in situations where sensor data is available must be preserved; the only thing being added or corrected is None-safety for the update routine and for the accessors listed above.

Task Specification: Diagnostic Sensors for Central Control

Summary

The CSNetHomeInstallationSensor class (in the sensor module of the csnet_home integration) must be extended to support four new diagnostic sensor types that relate to a heat pump's central control configuration. For each new sensor type, the class must report state values correctly based on data supplied by the installation devices coordinator.

Public API

The CSNetHomeInstallationSensor class

Construction of the class must be possible with the following positional arguments, in this order:

CSNetHomeInstallationSensor(
    coordinator,        # object exposing get_installation_devices_data()
    device_data,        # dict with device metadata
    common_data,        # dict with common metadata
    sensor_type,        # str identifying which sensor this is
    device_class,       # str or None
    unit_of_measurement,# (this position); may be None
    display_name,       # str, human-readable label
)
  • coordinator offers a method get_installation_devices_data() that returns either a data dictionary, an empty dict, or None.
  • device_data has keys including device_name, device_id, room_name, parent_id, room_id.
  • common_data has keys including name and firmware.

Instances must make the following read-only properties available: state, name, unique_id, device_class.

Source of the Data

When populated, the installation data that get_installation_devices_data() returns has the following shape:

{
    "data": [
        {
            "indoors": [
                {
                    "heatingStatus": {
                        "centralConfig": <int>,
                        "lcdSoft": <int or None>,
                        "unitModel": <int>,
                    }
                }
            ]
        }
    ]
}

The values for all four new sensors are read from data[0]["indoors"][0]["heatingStatus"]. The data may be absent (None), may be empty ({}), or may contain an indoors entry that has no heatingStatus key. For those cases, the state behavior of the binary sensor is defined below.

Sensor Types and How state Behaves

The diagnostic sensor being implemented is selected by the sensor_type argument. The state property behaves as follows.

1. central_config
  • device_class is "enum".
  • The integer at heatingStatus["centralConfig"] is read.
  • The value is mapped to a human-readable string:
    • 0 → "Unit Only"
    • 1 → "RT Only"
    • 2 → "Unit & RT"
    • 3 → "Total Control"
    • 4 → "Total Control+"
  • When the value is less than 3, a space plus the warning emoji ⚠️ is appended to the string (e.g., "Unit Only ⚠️", "RT Only ⚠️", "Unit & RT ⚠️").
  • When the value is 3 or 4, no warning emoji is appended.
  • For any value that is not recognized, the resulting string must contain the substring "Unknown".
2. lcd_software_version
  • device_class is None.
  • heatingStatus["lcdSoft"] is read.
  • If the value is a positive integer, it is formatted as a lowercase hexadecimal string prefixed with 0x, zero-padded to at least four hex digits. Examples:
    • 546 → "0x0222"
    • 768 → "0x0300"
  • A value of 0 means the state is the integer 0 (not a string).
  • A value of None means the state is None.
3. unit_model
  • device_class is "enum".
  • The integer at heatingStatus["unitModel"] is read.
  • The value is mapped to a model name:
    • 0 → "Yutaki S"
    • 1 → "Yutaki SC"
    • 2 → "Yutaki S80"
    • 3 → "Yutaki M"
    • 4 → "Yutaki SC Lite"
    • 5 → "Yutampo"
  • For any value that is not recognized, the resulting string must contain the substring "Unknown".
4. central_control_enabled
  • device_class is "binary".
  • The value returned is one of two string constants: the module-level "on" state value (STATE_ON) or the "off" state value (STATE_OFF), consistent with Home Assistant conventions ("on" / "off").
  • The state is determined using centralConfig, unitModel, and lcdSoft from heatingStatus:
    1. The state is STATE_ON when centralConfig >= 3.
    2. Otherwise, if unitModel != 2 (i.e., the model is not Yutaki S80, which corresponds to code 2):
      • The state is STATE_ON when lcdSoft == 0.
      • Otherwise, when lcdSoft >= 546 (i.e., >= 0x0222), the state is STATE_ON.
      • The state is STATE_OFF otherwise.
    3. Otherwise (with centralConfig < 3 and unitModel == 2), the state is STATE_OFF.
  • Handling of missing data: if get_installation_devices_data() returns None, an empty dict, or a structure lacking a heatingStatus entry, the state is STATE_OFF.

Examples of outcomes:

  • centralConfig=3, unitModel=0, lcdSoft=546 → STATE_ON
  • centralConfig=2, unitModel=0, lcdSoft=546 → STATE_ON
  • centralConfig=2, unitModel=0, lcdSoft=0 → STATE_ON
  • centralConfig=2, unitModel=0, lcdSoft=500 → STATE_OFF
  • centralConfig=2, unitModel=2, lcdSoft=546 → STATE_OFF
  • centralConfig=4, unitModel=2 → STATE_ON

Metadata-Related Properties

Given device_data with device_name="Installation" and room_name="Global", the following properties must hold for all four new sensor types:

  • name = "Installation Global <display_name>", with <display_name> being the display_name argument. Examples:
    • "Installation Global Central Config"
    • "Installation Global LCD Software Version"
    • "Installation Global Unit Model"
    • "Installation Global Central Control Enabled"
  • unique_id = "csnet_home-installation-<sensor_type>". Examples:
    • "csnet_home-installation-central_config"
    • "csnet_home-installation-lcd_software_version"
    • "csnet_home-installation-unit_model"
    • "csnet_home-installation-central_control_enabled"
  • device_class returns exactly the device_class argument supplied to the constructor ("enum", "binary", or None as applicable).

Additional Notes

  • The state constants STATE_ON and STATE_OFF must be importable alongside the sensor class from the same module namespace that callers use.
  • Sensor behavior that already exists on CSNetHomeInstallationSensor (for other sensor types) must remain unchanged; the new sensor types are additive.

Task Specification: Updates to Device Naming

Overview

The naming of the CSNet Home integration is to be updated in two places:

  1. Element records that lack a device name must use Remote.
  2. Installation-level entities must adopt the System / Controller identity and report HVAC System as the fixed device model.

The existing public construction and state behavior of installation sensors must be retained through these changes.

1. Fallback device name in the Element API

Within CSNetHomeAPI.async_get_elements_data, each successful API element is turned into a sensor record. When the source element's deviceName is absent, None, or an empty string, the resulting record's device_name must be exactly:

"Remote"

The fallback is applied independently to every element. A source deviceName that is non-empty must continue to be returned unchanged. Trimming or renaming of non-empty names is not required.

This change affects the device-name fallback only. The existing behavior of the room-name fallback, and of all other returned data, must remain unchanged. Notably, an absent or empty parentName continues to produce Room-{parentId}-{element_index}, while the common_data mapping and the other sensor fields—including device_id, room_name, parent_id, room_id, operation_status, mode, real_mode, on_off, timer_running, alarm_code, c1_demand, c2_demand, ecocomfort, doingBoost, current_temperature, setting_temperature, and zone_id—retain their current meanings and values.

2. Identity of installation-level sensors

Device data created by the integration

If installation-device data is available and the sensor platform creates installation-level entities, the shared installation device data must be:

{
    "device_name": "System",
    "device_id": "global",
    "room_name": "Controller",
    "parent_id": "global",
    "room_id": "global",
}

This device data must be received by all installation-level entities the platform creates, so their names use System Controller rather than the previous installation/global wording.

Compatibility of the public class and constructor

The installation sensor class stays publicly importable as:

  • Module: custom_components.csnet_home.sensor
  • Class: CSNetHomeInstallationSensor

This positional constructor contract must be retained:

    key,

  1. The coordinator, which provides the current installation-device data.
  2. The mapping of device data, including device_name and room_name.
  3. A mapping of common metadata, typically holding name and firmware.
  4. The installation sensor's key, such as pump_speed.
  5. The Home Assistant device class, or None.
  6. The unit of measurement, or None.
  7. The display label, which is human-readable. If no usable label is supplied, the key remains the fallback label.

As an example:

The name property must be built from the supplied device data and the display label according to the pattern:

  • Pump Speed → System Controller Pump Speed
  • Central Config → System Controller Central Config
  • LCD Software Version → System Controller LCD Software Version
  • Unit Model → System Controller Unit Model
  • Central Control Enabled → System Controller Central Control Enabled

The composition stays data-driven: sensors constructed directly with other device_name or room_name values must reflect those supplied values in their entity name.

Device information

For every CSNetHomeInstallationSensor, the device_info mapping must expose:

  • manufacturer: exactly Hitachi
  • model: exactly HVAC System
  • sw_version: the exact value of common_data["firmware"], or None when that metadata is unavailable

The model stays constant and must not be derived from device_name, room_name, or the common metadata's name. The firmware must not be hardcoded; using the example common metadata above, sw_version is 1.0.0.

  • The device-info name is {device_name}-{room_name}.
  • The identifier is ("csnet_home", "{device_name}-{room_name}").

Consequently, integration-created installation sensors report the device-info name System-Controller and share the identifier that corresponds to it.

3. Installation-sensor behavior that is preserved

Identity and metadata properties

The following behavior must stay unchanged:

  • The unique_id is csnet_home-installation-{key}. Examples include:
    • csnet_home-installation-pump_speed
    • csnet_home-installation-central_config
    • csnet_home-installation-lcd_software_version
    • csnet_home-installation-unit_model
    • csnet_home-installation-central_control_enabled
  • The fifth constructor argument is returned by device_class unchanged.
  • The sixth constructor argument is returned by unit_of_measurement unchanged, with None included. For example, a pump-speed sensor constructed with m/s reports m/s.
  • A coordinator update continues to request a state write in Home Assistant.
State backed by the coordinator

Each time state is accessed, the current result of coordinator.get_installation_devices_data() must be used. Values continue to be found either directly in the returned mapping or, if not found directly, in the first available data[0].indoors[0].heatingStatus mapping. Precedence belongs to direct non-None values.

All existing state conversions and missing-data handling must be retained:

Scope

The element device-name fallback and the installation-level naming/model metadata are the only changes. Regular sensor or climate entity model strings, installation sensor keys, unique IDs, units, device classes, state lookup, conversions, or central-control calculations must not be altered.

Task Specification: Enhanced Alarm Handling

Overview

Introduce enhanced alarm/error code handling into the csnet_home custom component. This comprises new alarm-processing methods on the API class, new fields in the element data output, plus two new sensor classes for alarm history and statistics.

1. API Class: CSNetHomeAPI

Location: custom_components.csnet_home.api, class CSNetHomeAPI.

The class is constructed via CSNetHomeAPI(hass, username, password). It carries an attribute translations (a dict) which may be assigned externally and which alarm-origin lookups use. Add the following public methods.

1.1 has_alarm_letter(self, alarm_code) -> bool

Indicates whether an alarm code is BCD-encoded (i.e., its high byte is set).

  • Return True when the value has any bit set in the high byte (i.e., alarm_code & 0xFF00 is nonzero). Examples: 0x0162 → True, 0xFF62 → True.
  • Return False when the high byte is zero. Examples: 0x0062 → False, 62 → False, 100 → False, 0 → False.
  • Return False for None.
1.2 reverse_bcd(self, value) -> int

Carries out a reverse-BCD conversion according to the formula:

((tens_digit - 1) * 16) + (ones_digit + 10)

with tens_digit and ones_digit being the decimal tens and ones digits of value.

  • reverse_bcd(62) → 92 (i.e., (6-1)*16 + (2+10))
  • reverse_bcd(91) → 139 (i.e., (9-1)*16 + (1+10))
  • reverse_bcd(92) → 140 (i.e., (9-1)*16 + (2+10))
1.3 get_alarm_code_formatted(self, alarm_code) -> str

Returns the alarm code in a human-facing string form.

  • When the input is None or 0, return "0".
  • When the code is non-BCD (high byte not set), return the decimal value as a string. Examples: 62 → "62", 100 → "100".
  • When the code is BCD (high byte set), return the low byte (alarm_code & 0xFF) formatted as a lowercase hex string without a prefix. Examples: 0x0162 → "62", 0xFF62 → "62" (low byte 0x62 = hex "62").
1.4 get_correct_rad_hex_error_code(self, code) -> int

Applies offset corrections for RAD units to an alarm code.

  • None → 0.
  • A code of 61 or 63 → returned unchanged.
  • code <= 0 → returned unchanged (e.g., 0 → 0, -1 → -1).
  • 0 < code < 113 → subtract 10. Examples: 100 → 90, 112 → 102.
  • 113 <= code <= 129 → subtract 112. Examples: 113 → 1, 120 → 8, 129 → 17.
  • code >= 130 → subtract 28. Examples: 130 → 102, 150 → 122.

(The special cases 61 and 63 take precedence over the range rules.)

1.5 is_yutaki(self, sensor_data, installation_data) -> bool

Returns True when sensor_data["zone_id"] is 5 (yutaki) or 3 (water heater); otherwise False.

  • {"zone_id": 5} → True
  • {"zone_id": 3} → True
  • {"zone_id": 1} → False
1.6 get_unit_type(self, sensor_data, installation_data) -> str

Resolves the unit type string:

  • When sensor_data["zone_id"] == 3 → "water_heater".
  • When sensor_data["zone_id"] == 5 → "yutaki".
  • Otherwise, when installation_data is provided and its heatingStatus.systemConfigBits has the fan-coil bit set (systemConfigBits & 0x2000 nonzero) → "fan_coil".
  • Otherwise → "standard". This covers the case where installation_data is None, and the case where systemConfigBits is 0x0000.
1.7 get_alarm_origin(self, alarm_code, unit_type, installation_data) -> str

Produces a human-readable alarm origin string, with the self.translations dict supplying the display text.

General rules:

  • When unit_type is not a yutaki-type unit (i.e., not "yutaki" or "water_heater"), return "".
  • When alarm_code is None or 0, return "".

For yutaki-type units ("yutaki" or "water_heater"), codes are mapped to origins. The returned string is the value found in self.translations for that key.

Non-BCD (standard) codes map as follows (values shown are the translation values used in tests):

alarm code translation key returned string
2 STR_REFRIGERANT_CYCLE "Refrigerant Cycle"
3 STR_ORIGIN_TRANSMISSION "Transmission"
5 STR_ORIGIN_POWER_SUPPLY "Power Supply"
10, 11, 13 STR_ORIGIN_INDOOR "Indoor Unit"
60 STR_ORIGIN_COMUNICATION "Communication"
101, 105 STR_ORIGIN_2ND_CYCLE "2nd Cycle"

Codes 11 and 13 share the same origin as 10 ("Indoor Unit"); codes 101 and 105 both map to "2nd Cycle".

BCD codes (high byte set): extract the low byte value (alarm_code & 0xFF, e.g. 0x62 = 98 decimal... note: the raw BCD low-byte hex value is examined). In the BCD case, the low byte hex value 0x62 maps to the STR_ORIGIN_INVERTER key, which produces "Inverter".

  • get_alarm_origin(0x0162, "yutaki", None) → "Inverter"
  • get_alarm_origin(0xFF62, "yutaki", None) → "Inverter"

The origin logic is expected to recognize/use the following additional translation keys (present in the translations dict supplied at runtime): STR_ORIGIN_INVERTER, STR_ORIGIN_COMPRESSOR, STR_ORIGIN_OUTDOOR_FAN, STR_REFRIGERANT_CYCLE, STR_ORIGIN_TRANSMISSION, STR_ORIGIN_POWER_SUPPLY, STR_ORIGIN_INDOOR, STR_ORIGIN_2ND_CYCLE, STR_ORIGIN_COMUNICATION.

1.8 async_get_elements_data(self) — additional fields

The existing async_get_elements_data method returns a dict that contains a "sensors" list. Each sensor dict must now also contain the following three keys:

  • "unit_type": the value from get_unit_type.
  • "alarm_code_formatted": the value from get_alarm_code_formatted applied to the sensor's alarm code.
  • "alarm_origin": the value from get_alarm_origin (empty string for non-yutaki units).

Behavior in the default/normal case (an element with an elementType that maps to a standard zone and no alarm): unit_type == "standard", alarm_code_formatted == "0", alarm_origin == "".

For an element whose elementType is 5 (yutaki, zone_id 5) and whose alarmCode is 62:

For an element whose elementType is 5 and whose alarmCode is 0x0162 (BCD):

  • alarm_code = 0x0162, alarm_code_formatted = "62", unit_type = "yutaki".

The existing alarm_code field (raw numeric alarm code) must continue to be present. The mapping from the element's elementType/zone to zone_id, together with all other existing sensor fields, must remain unchanged.

result["data"][0]["indoors"][0]["heatingStatus"]["systemConfigBits"]

fan_coil_compatible 0x2000
c1_thermostat_present 0x40
