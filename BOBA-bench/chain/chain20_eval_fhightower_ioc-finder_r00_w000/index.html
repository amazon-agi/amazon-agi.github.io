IOC Finder: Task Specification

Overview

Build a Python package called ioc_finder that extracts Indicators of Compromise (IOCs) present in arbitrary text. The IOCs include domain names, IPv4 addresses, URLs, email addresses, and cryptographic hashes (MD5, SHA1, SHA256).

Module Layout and Public API

Create a module at ioc_finder/ioc_finder.py that exposes the following:

find_iocs(text)
  • Input: arbitrary text supplied as a string.
  • Output: a dictionary that maps IOC-type names (strings) to lists of the matching values (strings) present in the text.
  • The dictionary that is returned must include, at minimum, the following keys:
    • 'domain'
    • 'ipv4'
    • 'url'
    • 'email'
    • 'md5'
    • 'sha1'
    • 'sha256'
  • The results in each list must be deduplicated: if the same value occurs multiple times in the input text, it is present only once in the corresponding list.
_get_regexes()
  • A function that returns the collection of regular expressions employed for identifying IOCs. It must be possible to import it from ioc_finder.ioc_finder. (Beyond being callable and importable without error, no specific structure of its return value is required.)

The package must additionally allow find_iocs to be imported directly (e.g., from ioc_finder import find_iocs), and any regex resource files the implementation relies on must be included/packaged so that imports succeed.

Required Behavior

When it is given input text, find_iocs must correctly identify each IOC type. The requirements that follow are exact:

IPv4 Addresses ('ipv4')
  • Recognize standard dotted-quad addresses, such as 1.2.3.4 and 192.64.55.61.
URLs ('url')
  • Recognize complete URLs that include scheme, host, and path.
  • The URL that gets captured must include the entire path, and not just the host. For example:
    • When the text contains http://bad.com/test/bingo.php, the URL that is extracted must be exactly http://bad.com/test/bingo.php.
    • The string https://github.com/StylishThemes/GitHub-Dark/blob/master/tools/authors.sh must be extracted in full as a single URL, exactly as written (with the mixed-case host and path segments preserved).
  • URL detection must handle upper-case and mixed-case characters in the host and the path.
MD5 Hashes ('md5')
  • Recognize hexadecimal strings that are 32 characters long (e.g., a run of 32 a characters).
SHA1 Hashes ('sha1')
  • Recognize hexadecimal strings that are 40 characters long (e.g., a run of 40 b characters).
SHA256 Hashes ('sha256')
  • Recognize hexadecimal strings that are 64 characters long (e.g., a run of 64 c characters).
Email Addresses ('email')
  • Recognize email addresses, such as bad12312@example.org.
Domains ('domain')
  • Recognize bare domain names, such as example.com.

Worked Example

  • iocs['sha256'] has a length of 1 and contains the string of 64 c characters.

For the input https://github.com/StylishThemes/GitHub-Dark/blob/master/tools/authors.sh, iocs['url'] must have a length of 1 and contain that exact string.

Build a module that extracts indicators of compromise (IOCs) out of arbitrary text. The public API must be importable and callable in exactly the way described below. Public API

ioc_finder.find_iocs(text)
  • The import from ioc_finder import find_iocs must succeed.
  • The function accepts a single string argument, text.
  • It returns a dictionary in which the IOC type names are strings and the values are lists of extracted strings.
  • All eight keys listed below must always be present in the returned dictionary, even when a category has no matches; a category with no matches maps to an empty list:
    • email
    • ipv4_email
    • domain
    • ipv4
    • url
    • md5
    • sha1
    • sha256
  • Deduplication is applied independently within each category and across the entire input. When the same value occurs more than once, it appears exactly once in that category's result list.
  • No ordering of results is required.
ioc_finder.ioc_finder._get_regexes()
  • The import from ioc_finder.ioc_finder import _get_regexes must succeed.
  • The function accepts no arguments.
  • It returns a collection of regex definitions that has exactly eight entries and covers the eight IOC categories listed above.

Extraction Requirements

Conventional email addresses (email)
  • Extract conventional email addresses in which the host portion is a domain, and return the complete address.
  • The domain host of an extracted email address is additionally reported independently under domain.
  • Example: bad12312@example.org produces bad12312@example.org under email together with example.org under domain.
Email addresses with IPv4 hosts (ipv4_email)
  • Extract email addresses whose host portion is an IPv4 literal enclosed in square brackets, in the form user@[<ipv4>].
  • Return the entire matched address, square brackets included.
  • The address between the brackets must also be reported independently under ipv4.
  • Example: test@[192.168.2.1] produces exactly test@[192.168.2.1] under ipv4_email and 192.168.2.1 under ipv4.
  • Similarly, bad@[192.168.7.3] produces exactly bad@[192.168.7.3] under ipv4_email and 192.168.7.3 under ipv4.
Domains (domain)
  • Extract registered domain names that appear in plain text, in URLs, and as the host portion of ordinary email addresses.
  • When the text contains example.com, http://bad.com/test/bingo.php, and bad12312@example.org, the domain results contain exactly example.com, bad.com, and example.org.
Unicode domain names
  • Domains that contain non-ASCII Unicode characters must be detected.
  • In returned domain values, non-ASCII characters must be expressed with Python Unicode escape notation, while the ASCII part stays unchanged. The value that is returned contains the literal backslash escape instead of the original non-ASCII character.
  • Example: the input ȩxample.com produces one domain result, the string \u0229xample.com (a literal \u0229 followed by xample.com).
URLs (url)
  • Extract complete http:// and https:// URLs rather than just their hosts.
  • The hosts and paths of URLs may contain uppercase or mixed-case characters. Keep the spelling and the case of the full match intact in the returned value.
  • Example: http://192.64.55.61/test.php produces exactly that full string under url.
  • Example: https://github.com/StylishThemes/GitHub-Dark/blob/master/tools/authors.sh produces one URL result that contains the entire string exactly as written.
  • A domain or IPv4 host that is embedded in a URL is additionally reported independently in its corresponding category.
IPv4 addresses (ipv4)
  • Extract dotted-decimal IPv4 addresses appearing in plain text, in URL hosts, and in bracketed email hosts.
  • Example: http://192.64.55.61/test.php produces 192.64.55.61 under ipv4 in addition to the complete URL under url.
  • Example: bad@[192.168.7.3] produces 192.168.7.3 under ipv4 in addition to the complete address under ipv4_email.
Hash values

Hash matches are made up of hexadecimal characters (0-9, a-f, or A-F) and are returned in full, with their original character case preserved. A value must be a standalone token of the exact length rather than a substring of a longer alphanumeric or hexadecimal token.

  • MD5 (md5): exactly 32 hexadecimal characters are extracted.
    • Example: under md5, aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa is returned in full.
  • SHA-1 (sha1): exactly 40 hexadecimal characters are extracted.
    • Example: under sha1, bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb is returned in full.
  • SHA-256 (sha256): exactly 64 hexadecimal characters are extracted.
    • Example: under sha256, cccccccccccccccccccccccccccccccccccccccccccccccccccccccccccccccc is returned in full.

A hash of the exact length belongs to its corresponding category; a longer hash must not be emitted as one or more shorter hashes.

Category Overlap and Deduplication

A single fragment of the source may legitimately produce values in multiple categories:

  • a URL together with its domain or IPv4 host;
  • an ordinary email address together with its domain host; or
  • a bracketed-IPv4 email address together with its IPv4 host.

These cross-category results are required, and deduplication does not remove them. Only repeated equal values within the same category are affected by deduplication. For example, the input example.com example.com produces a domain list with exactly one example.com entry.

Combined Example

Given this input:

the result contains:

  • domain: exactly example.com, bad.com, and example.org;
  • email: exactly bad12312@example.org;
  • ipv4_email: empty;
  • ipv4: exactly 1.2.3.4 and 192.64.55.61;
  • url: exactly http://bad.com/test/bingo.php;
  • md5: exactly aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa;
  • sha1: exactly bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb;
  • sha256: exactly cccccccccccccccccccccccccccccccccccccccccccccccccccccccccccccccc.

Scope

Only the eight IOC categories and the behaviors described here are required. Do not add extra IOC types or extraction behavior unrelated to the specification.

The task is to build a Python package called ioc_finder that extracts indicators of compromise (IOCs) out of arbitrary text.

The package must expose a single top-level function, which is importable as:

from ioc_finder import find_iocs

def find_iocs(text: str) -> dict:
    ...
  • Input: a single string containing arbitrary text.
  • Output: a dictionary in which the keys are IOC-type names (see below) and the values are lists of the strings matched for each type.
  • All result lists must be deduplicated (within a given list, no value occurs more than once).

Keys of the Result Dictionary

The dictionary that gets returned must contain (at minimum) the following keys, each of which maps to a list:

  • domains
  • email_addresses
  • ipv4s
  • ipv6s
  • urls
  • md5s
  • sha1s
  • sha256s
  • sha512s
  • asns

Behavior per IOC Type

Domain Names (domains)
  • Find domain names such as example.com, google.com, bad.com, example.org.
  • A domain that is embedded inside another token must be recognized (for instance, in a URL such as http://bad.com/test/bingo.php the domain bad.com is extracted, and in an email such as bad12312@example.org the domain example.org is extracted).
  • Domains flanked by punctuation must be extracted (e.g. (google.com) yields google.com).
  • Unicode handling: when the input includes a domain that contains a non-ASCII character (e.g. ȩxample.com), the extracted domain must be the Python unicode-escaped representation of the string, i.e. the value \u0229xample.com (a literal backslash, u, 0229, then xample.com).
Email Addresses (email_addresses)

  • Basic addresses: test@a.com, bingo@en.wikipedia.com, foo@a.com, bar@b.a.com, bad@test-ing.com, me@2600.com.

  • IPv6 domain in brackets: jsmith@[IPv6:2001:db8::1] — the whole bracketed form is the email address.

  • test@[192.168.2.1] → 192.168.2.1 appears in ipv4s.
  • jsmith@[IPv6:2001:db8::1] → 2001:db8::1 appears in ipv6s.
  • bad@[192.168.7.3] → 192.168.7.3 appears in ipv4s.
IPv4 Addresses (ipv4s)
  • Find valid dotted-quad IPv4 addresses (e.g. 1.2.3.4, 192.64.55.61, 1.2.3.54, 255.255.1.255).
  • Each octet must be a valid IPv4 octet (0–255). Invalid values such as 255.256.344.1 must not be extracted.
  • IPv4 addresses that sit inside URLs must be extracted (e.g. from http://192.64.55.61/test.php, extract 192.64.55.61).
IPv6 Addresses (ipv6s)
  • Find IPv6 addresses across their various valid textual forms, including:
    • Complete form: 2001:0db8:0000:0000:0000:ff00:0042:8329
    • Zero-collapsed forms: 2001:db8:0:0:0:ff00:42:8329, 2001:db8::ff00:42:8329
    • Loopback shorthand: ::1
  • A token such as 1:1 must not be treated as an IPv6 address.
  • Distinct textual representations of the same address count as distinct entries (no normalization across forms is performed).
URLs (urls)
  • Find full URLs that include scheme, authority, and path (e.g. http://bad.com/test/bingo.php, https://github.com/StylishThemes/GitHub-Dark/blob/master/tools/authors.sh, http://192.64.55.61/test.php).
  • Recognize schemes such as http, https, and ftp.
  • URLs that carry userinfo/authentication portions must be recognized, e.g. http://"John..Doe"@example.com, http://test@a.com, http://bingo@en.wikipedia.com, and http://foo@<63 a's>.com.
  • URLs with long domain labels of up to 63 characters per label are valid; domains made of multiple labels, such as https://<63 a's>.<63 a's>.com, are valid.
  • Strings that are not URLs (missing a valid scheme + valid domain) must yield no URL results. Example strings that produce zero URLs:
    • foo@<64 a's>.com, !@.com, foo@abc, @@@@-hi-.com, @_hi_.com, me@*hi*.com, foo<64 a's>.com, .com, abc, -hi-.com, _hi_.com, *hi*.com.

File Hashes

Sort contiguous hexadecimal strings into separate lists on the basis of length alone:

  • md5s — 32 hex characters.
  • sha1s — 40 hex characters.
  • sha256s — 64 hex characters.
  • sha512s — 128 hex characters.

Matching must be case-insensitive where hex digits are concerned (e.g. a 32-character string of uppercase As and a 32-character string of lowercase as are each valid MD5 hashes; after deduplication a single distinct value remains for each distinct string). When the same text contains multiple hash types, each one ends up only in its correctly-sized list.

Autonomous System Numbers (asns)
  • Find ASNs written in any of these forms: asn1234, as1234, asn 1234, as 1234, AS 4321, ASN4321 (the prefix is case-insensitive, whitespace between the prefix and the number is optional, and the prefix may be AS or ASN).
  • All recognized ASNs must be normalized to the uppercase canonical form ASN<number> (e.g. ASN1234, ASN4321). Once normalization and deduplication have been applied, forms that reduce to the same canonical value collapse into a single entry.
CVEs (cves)
  • Find CVE identifiers that follow the form CVE-<4 digits>-<digits>, where the prefix is case-insensitive (cve or CVE) and the separator between the prefix and the year may be a hyphen or whitespace.
  • The year portion is exactly 4 digits long; the trailing number portion comes after a hyphen.
  • Forms that are recognized include: cve-2014-290902, cve 2014-290902, cve-1999-2909023422, cve 2999-290902, CVE 1928-290902.

IPv4 CIDR Ranges (ipv4_cidrs)
  • Find IPv4 CIDR notations of the form <ipv4>/<prefix>, where the prefix is 0–32.
  • Examples that are recognized: 1.2.3.4/0, 1.2.3.4/10, 1.2.3.4/20, 1.2.3.4/32.

  • Find Windows registry key paths that start with a registry root/hive identifier (including full names like HKEY_LOCAL_MACHINE and abbreviations such as HKLM, HKCC) and then continue with a backslash-separated path.
  • Examples that are recognized (each one extracted in full):
    • HKEY_LOCAL_MACHINE\Software\Microsoft\Windows
    • HKLM\Software\Microsoft\Windows
    • HKCC\Software\Microsoft\Windows

  • Multiple IOC types may show up together in the same input, and each one must be extracted independently into its own list.
  • All of the returned lists are deduplicated.
  • No other constraint is placed on ordering inside a list, except that when the input contains exactly one value of a given type, that value is the sole element of its list.

The package that gets distributed and installed is ioc_finder, and consumers import it under the name ioc_finder.

Goal

Enhance the URL-boundary and host parsing of the IOC Finder library while preserving its existing indicator extraction behavior. Indicators of compromise (IOCs) are extracted by the library from arbitrary text.

from ioc_finder import find_iocs

def find_iocs(text: str) -> dict:

  • urls

  • md5s
  • sha1s
  • sha256s
  • sha512s
  • asns
  • cves

Each value placed into these lists must be a string.

Overall Result Semantics

  • All supported IOC types are extracted from the same input. Extraction Behavior Requirements

1. URLs
Recognizing and validating

  • A URL must possess an explicit scheme and a valid host. Text that resembles a domain, an email, or a path but has no scheme must not be returned under urls.

  • The supported valid schemes include http, https, and ftp.

  • Valid hosts for URLs include multi-label domain names and dotted-quad IPv4 addresses.

    https://github.com/StylishThemes/GitHub-Dark/blob/master/tools/authors.sh

Boundary behavior

A URL must end before trailing markup or other characters that are not part of the URL. It must not consume that markup, and it must not create spurious additional URLs. Concretely:

find_iocs("http://192.168.0.1/test/bad.html</a><br></div>")["urls"]

["http://192.168.0.1/test/bad.html"]

In this context, the < that begins the trailing markup is therefore a URL terminator.

Cross-classification of hosts

If no ssdeep hashes are present, the value must be an empty list ([]). For all inputs, this key must be present in the output — including inputs that contain no ssdeep hashes at all.

Format of an ssdeep hash

An ssdeep hash is structured as follows:

<chunksize>:<chunk>:<double_chunk>

in which:

  • <chunksize> is a sequence of digits.
  • <chunk> and <double_chunk> are strings made up of base64-style characters, which include uppercase letters, lowercase letters, digits, and the characters + and /.

Colons (:) are the separators between the three components.

An example of a valid ssdeep hash:

1536:yB+A8bMtMeRlbIzvDqZL4QzNxVDm+5gt+M2hDDDvNZ3YZ7sU:N4tMsbOGcyrV6BQvnoZ4U

  • ssdeep hashes must be detected even when they are embedded in surrounding text (e.g., preceded or followed by unrelated words, whitespace, or punctuation).
  • Extraction must stop at delimiters that do not form part of the hash. In particular, when a comma and additional non-hash content (such as ,000/000/000000001) follow a hash, only the valid <chunksize>:<chunk>:<double_chunk> portion is captured; content trailing after the comma is not included.
  • Detection must work when the hash appears on a line by itself within multi-line text, including cases where a label and whitespace precede the hash on the same line.
  • The value that gets extracted must be exactly the hash string itself, without surrounding text, labels, or trailing delimiters.
