Task Description

Background

The library you will be working on is pydargs, which parses command-line arguments into dataclass instances. Its public entry point is:

from pydargs import parse

The function parse(config_class, args) takes a dataclass type along with a list of string arguments, and returns an instance of that dataclass whose fields are populated from the parsed arguments.

What you are asked to implement is correct handling of fields typed as list and sequence.

Behavior Requirements

Field types that are supported

Fields that are annotated with the following generic types must be parseable from the command line:

  • list[T] (e.g. list[int], list[str], list[float])
  • collections.abc.Sequence[T] (e.g. Sequence[float], Sequence[str])

For both of them, T is the element type. Conversion to T must be applied to each element of the field value.

How arguments are consumed

A list/sequence field whose name is arg is supplied on the command line via the flag --arg, followed by one or more whitespace-separated values. All values that follow the flag (until the next flag or the end of the arguments) are collected, with each one converted to the element type T, and they are stored as a Python list of converted elements.

The same applies to both list[T] and Sequence[T] annotations: the resulting field value is always a list, even when the annotation is Sequence and/or the default was a tuple.

Default values

  • A field may declare a default by way of field(default_factory=...) or through a direct default value (e.g. = ("a", "b")).

  • If the corresponding flag is not supplied on the command line, the field receives its declared default value unchanged (i.e. a tuple default stays a tuple; a list default stays a list). Element conversion is not applied to defaults.

  • A list/sequence field that has no default is a required argument. If such a field is not supplied, parsing must fail by exiting the program (i.e. raising SystemExit), and an error message must be printed to standard error that contains:

    the following arguments are required: --<name>
Type conversion and error handling

  • Conversion to the element type T is applied to each supplied value.

  • If a supplied value cannot be converted to the element type, parsing must fail by exiting the program (SystemExit), and an error message must be printed to standard error in the form:

    error: argument --<name>: invalid <type> value:

    where <type> stands for the name of the element type (e.g. float).

Examples

Given the following definition:

from collections.abc import Sequence
from dataclasses import dataclass, field

@dataclass
class Config:
    a: list[int]
    b: list[str] = field(default_factory=lambda: [])
    c: Sequence[float] = field(default_factory=lambda: [1.0])
    d: Sequence[str] = ("a", "b")
    e: str = "dummy"
  • parse(Config, ["--a", "1"]) → a == [1], b == [], c == [1.0], d == ("a", "b"), e == "dummy"
  • parse(Config, ["--a", "1", "--b", "a", "b"]) → b == ["a", "b"]
  • parse(Config, ["--a", "1", "--c", "2.0", "2.5"]) → c == [2.0, 2.5]
  • parse(Config, ["--a", "1", "--d", "c"]) → d == ["c"]
  • parse(Config, []) → exits, stderr contains the following arguments are required: --a
  • parse(Config, ["--a", "1", "--c", "abc"]) → exits, stderr contains error: argument --c: invalid float value:

Remarks

  • For the numeric types (int, float) and for str, the element type conversion must behave as the native Python constructors do.
  • Required list/sequence fields and invalid element values must terminate via SystemExit (as produced by standard argument-parsing error handling) instead of returning normally.

Overview

from pydargs import parse

and it has the signature:

def parse(config_class, args: list[str]) -> <instance of config_class>

Here, config_class is a dataclass type. For each field of the dataclass, a command-line argument named --<field_name> is created.

This task addresses two areas of behavior: the handling of list-typed fields, and support for a per-field custom parser supplied through field metadata.

Part 1: Fields of list type

A dataclass field whose annotation is list[T] (e.g. list[str], list[int]) is a command-line argument that accepts zero or more values, all of them provided on the command line after the --<field_name> flag. Each provided value is converted to the element type T.

Behavior that is required

  • The default value is used when the flag is absent. If the corresponding flag is not supplied on the command line, a list[T] field that declares a default (via field(default_factory=...)) takes its default value.

    • Example: the field arg: list[str] = field(default_factory=lambda: []), parsed with an empty argument list, yields arg == [].

  • Multiple values are collected into a list. When the flag is supplied followed by multiple values, all of them are collected into a list, in order, and each one is converted to the element type.

    • For arg: list[str] = field(default_factory=lambda: []), parsing ["--arg", "1", "2"] yields arg == ["1", "2"].
    • For arg: list[int] = field(default_factory=lambda: []), parsing ["--arg", "1", "2"] yields arg == [1, 2].

  • A required list field with no default raises NotImplementedError. When a list[T] field is declared with no default (i.e. field() with no default and no default_factory), the framework must not support it — calling parse on a configuration like that must raise NotImplementedError.

    • Parsing ["--arg", "1", "2"] with arg: list[int] = field() raises NotImplementedError.

    Note: this restriction on required lists applies only to list fields without a custom parser (see Part 2, which overrides this behavior).

Part 2: Custom parser supplied through field metadata

A dataclass field may specify a custom parser callable in its metadata, under the key parser:

field(metadata=dict(parser=some_callable))

Once a field declares such a parser, the raw command-line string value for --<field_name> is passed to that callable, and the callable's return value becomes the field's value. Conversion is fully determined by the custom parser; the field's type annotation is not used to convert the value.

What the custom parser applies to is a single string token following the flag (exactly one argument value is consumed by the flag).

Behavior that is required

  • The custom parser gets applied to the raw string argument. For a field with metadata=dict(parser=parser_callable), when --<field_name> VALUE is supplied, the field's value is parser_callable("VALUE").

    • With parser=json.loads and the input ["--arg", "[1, 2]"], the field value is [1, 2].
    • With parser=json.loads and the input ["--arg", '{"1": 2}'], the field value is {"1": 2}.
    • The field's type annotation (e.g. Optional[list[int]], list[int]) neither constrains nor alters the parsed result.

  • Optional field that has a default. When the flag is not supplied, a field that has a custom parser and also declares a default (e.g. arg: Optional[list[int]] = field(default=None, metadata=dict(parser=loads))) takes its default value.

    • Parsed with an empty argument list, a field like this with default=None yields arg is None.

  • A required field with a custom parser and no default. A field that has a custom parser but no default is a required argument. If the flag is not supplied, parsing of the arguments fails by exiting the process (raising SystemExit), and a message containing the following is written to standard error:

    the following arguments are required: --arg

    (where arg is the field name).

    • Note: unlike plain list fields (Part 1), a required field that has a custom parser does not raise NotImplementedError — it is a valid required argument.
    • When the flag is supplied, the custom parser produces the value as usual (e.g. ["--arg", "[1, 2]"] with parser=loads yields [1, 2]).

  • Errors from the custom parser surface as argument errors. When the custom parser raises an exception while processing the supplied value, the parsing of arguments fails by exiting the process (raising SystemExit), and the following message is written to standard error:

    argument --arg: invalid <parser_name> value: '<the raw value>'

    with <parser_name> denoting the name of the custom parser callable (e.g. loads) and <the raw value> denoting the offending string.

    • Example: with parser=loads and the input ["--arg", "[1, 2"], standard error contains:
      argument --arg: invalid loads value: '[1, 2

Recap of the public API surface

  • The module pydargs exposes a function parse(config_class, args).
  • Configuration at field level is read from dataclass field metadata, specifically the key "parser", whose value is a callable str -> Any used to convert the raw argument string.

Apart from the above, no public names are required.

Part 1: Boolean Fields

A field annotated as bool operates in one of two distinct command-line modes, with the choice determined by its metadata.

1a. Value mode (the default)

Whenever the metadata of a bool field does not contain as_flags=True, the field is in value mode. This includes fields with no metadata, fields with empty metadata, and fields with as_flags=False.

In value mode, --<name> consumes one value token. The textual values are converted case-insensitively, and the conversion must follow this table:

  • "0" is converted to False.
  • "1" is converted to True.
  • "false", with any capitalization such as "False" or "FALSE", is converted to False.
  • "true", with any capitalization such as "True" or "TRUE", is converted to True.
  • Any other value makes parsing raise SystemExit; stderr must contain: argument --<name>: invalid bool value:

Whether or not the field declares a default, this conversion applies. When an optional value-mode field is omitted, its declared default is retained. A value-mode boolean without a default remains required under the general required-field rule.

1b. Flag mode (as_flags=True)

A bool field that carries metadata={"as_flags": True} is exposed as a pair of flags that take no value:

  • --<name> sets the field to True.
  • --no-<name> sets the field to False.
  • Neither flag consumes a value. Therefore, an additional token after one of these flags, such as in --<name> help, is not accepted, and parsing must raise SystemExit.

  • When the field declares a dataclass default, that default is retained.
  • If the field has no declared dataclass default, it is nevertheless optional, and its value in the returned dataclass instance must be False.
