01 You will implement changes to a Python package named firepit that provides SQL-backed storage for STIX observation data. 587 words · source specification

Overview

You will implement changes to a Python package named firepit that provides SQL-backed storage for STIX observation data. The changes involve adding a new exception class and modifying view-creation/overwrite behavior in the storage layer.

Required Public API

New Exception Class

Add a new exception class to the module firepit.exceptions:

  • IncompatibleType — an exception class that can be raised and caught via pytest.raises. It must be importable as:
    from firepit.exceptions import IncompatibleType

Storage Behavior

The storage object used in these scenarios is created by the package's storage factory (the same object that already exposes cache, extract, assign, values, and merge). You must ensure the following methods behave as described. Their existing signatures are:

  • store.cache(query_id, filenames) — loads one or more STIX bundle files (given as a list of file paths) into storage under an identifier.
  • store.extract(name, sco_type, query_id, pattern) — creates a named view holding objects of the given STIX object type (sco_type) that match the given STIX pattern, drawn from previously cached data identified by query_id.
  • store.assign(name, input_view, op=..., by=..., limit=...) — creates a named view derived from another view by applying an operation (e.g. op='sort', by='value').
  • store.values(path, view) — returns a list of values for the given STIX attribute path (e.g. 'url:value') from the named view.
  • store.merge(name, views) — creates a named view that is the union of the given list of views.

Required Behavior Changes

1. Reusing a view name with the SAME object type must succeed

When extract is called with a name that already exists as a view, and the new extraction has the same STIX object type as the existing view, the operation must succeed and overwrite the existing view — even if other views were derived from (depend on) the view being overwritten.

Concretely, the following sequence must complete without error:

  1. Extract a view urls of type url.
  2. Create a derived view sorted from urls (e.g. via a sort operation).
  3. Extract urls again (same type url) with a different pattern that yields a different result set.

After this sequence:

  • Querying urls must reflect the new extraction's result set.
  • Querying the derived view sorted must reflect the updated data as well (the derived view continues to reference the redefined urls, so its results follow the new definition of urls).

No exception may be raised in this case.

2. Overwriting a referenced view with a DIFFERENT object type must raise IncompatibleType

When extract is called with a name that already exists as a view, and:

  • the new extraction has a different STIX object type than the existing view, and
  • one or more other views depend on (were derived from) the existing view,

then the operation must raise IncompatibleType.

(Note: This particular error condition is only exercised against the PostgreSQL backend; the SQLite backend is not required to raise here for this specific derived-dependency scenario.)

3. merge of views with incompatible types must raise IncompatibleType

When merge is called with a list of views whose STIX object types are not all the same (for example, merging a url-typed view with an ipv4-addr-typed view), the operation must raise IncompatibleType.

Notes

  • The changes must apply consistently across the storage implementation so that the SQLite-backed storage object behaves as specified for cases (1) and (3).
  • No changes to method names or signatures are required beyond adding the IncompatibleType exception; only the behavior described above must be implemented.

merge(new_view_name, source_view_names)

  5. The merged view's values must still equal the complete union of the original two source views' values — unchanged by the removals.

Task Specification: Fix Null Comparison Handling for List-Type Fields in Query Predicates

Overview

You must modify the query predicate handling so that list-type field references (fields marked with a [*] suffix) are correctly translated into SQL when compared against a null literal.

Context

The system builds SQL predicate text from three components: a left-hand side field name (lhs), a comparison operator (op), and a right-hand side value (rhs). When the right-hand side is a null literal, the comparison must be rendered using SQL IS NULL / IS NOT NULL syntax rather than an ordinary equality/inequality comparison.

Required Behavior

Given a predicate composed of an lhs, an op, and an rhs, the resulting SQL predicate text must satisfy the following rules:

Null literal detection

The rhs value is treated as a null literal when it equals the string "null" in a case-insensitive manner (e.g. "null", "NULL" both qualify).

Operator mapping for null comparisons

When the rhs is a null literal:

  • The = operator produces IS NULL.
  • The != operator produces IS NOT NULL.
List-type field suffix handling

If the lhs ends with the suffix [*] (indicating a list-type field), that suffix must be stripped from the field name before it is rendered into the SQL predicate. The remaining field name is used as-is (this may include dotted path segments such as next.name).

Output format

The rendered predicate text must:

  • Quote the (suffix-stripped) field name in double quotes.
  • Follow the field with a single space and the appropriate null operator (IS NULL or IS NOT NULL).
  • Wrap the entire predicate in parentheses.

Examples

lhs op rhs resulting text
foo = null ("foo" IS NULL)
bar != NULL ("bar" IS NOT NULL)
baz[*] = NULL ("baz" IS NULL)
next.name[*] != null ("next.name" IS NOT NULL)

Notes

The existing behavior for non-list fields compared against null must continue to work as shown above. The only new requirement is stripping the trailing [*] suffix from list-type field names when producing null-comparison predicate text.

The public API surface (module path, function/class names, and signatures) used to build predicate text is unchanged from the existing codebase; you must not alter its import path or call signature.
