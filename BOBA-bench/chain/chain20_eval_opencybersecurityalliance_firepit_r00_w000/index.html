01 Your task is to modify firepit, a Python package offering SQL-backed storage for STIX observation data. 685 words · source specification, reworded by GLM-5.3-Flash

Specification of the Task

Summary

Your task is to modify firepit, a Python package offering SQL-backed storage for STIX observation data. The work consists of two parts: introducing a new exception class, and changing the view-creation/overwrite behavior of the storage layer.

Public API Requirements

Addition of a New Exception Class

Introduce a new exception class into the module firepit.exceptions:

  • IncompatibleType — an exception class; it can be raised, and it can be caught via pytest.raises. It must be possible to import it as follows:
    from firepit.exceptions import IncompatibleType

How the Storage Object Behaves

Throughout the scenarios covered here, the object serving as storage comes from the package's storage factory (this being the same object that already exposes cache, extract, assign, values, and merge). You must ensure that each of the methods below behaves in the way described. The signatures these methods currently have are:

  • store.cache(query_id, filenames) — takes one or more STIX bundle files (supplied as a list of file paths) and stores them in storage under an identifier.
  • store.extract(name, sco_type, query_id, pattern) — builds a named view whose objects have the STIX object type supplied as sco_type and match the STIX pattern supplied as pattern; the objects come from data cached earlier that query_id identifies.
  • store.assign(name, input_view, op=..., by=..., limit=...) — applies an operation (e.g. op='sort', by='value') to another view and builds a named view derived from it.
  • store.values(path, view) — returns a list of values, drawn from the named view, for the STIX attribute path supplied as path (e.g. 'url:value').
  • store.merge(name, views) — builds a named view whose content is the union of the list of views supplied to it.

Required Changes in Behavior

1. When the object type is the SAME, reusing a view name must succeed

Take the case where extract is called with a name for which a view already exists. If the STIX object type of the new extraction is the same as that of the existing view, the operation must succeed, overwriting the existing view — even if other views exist that were derived from (depend on) the view getting overwritten.

To make this concrete, the sequence below must run to completion with no error:

  1. Extract urls — a view of type url.
  2. Derive a view named sorted from urls (e.g. via a sort operation).
  3. Extract urls once more (same type url), using a pattern that differs and that yields a different result set.

Once the sequence has run:

  • The result set of the new extraction is what queries on urls must reflect.
  • The updated data must also be reflected when the derived view sorted is queried (that view keeps referencing the redefined urls, meaning its results follow the definition urls now has).

In this scenario, no exception may be raised.

2. When a referenced view gets overwritten with a DIFFERENT object type, IncompatibleType must be raised

Now suppose extract is called with a name for which a view already exists, and:

  • the STIX object type of the new extraction is different from that of the existing view, and
  • the existing view has one or more other views that depend on (were derived from) it,

then IncompatibleType must be raised by the operation.

(Note: This particular error condition gets exercised only against the PostgreSQL backend; for this specific derived-dependency scenario, the SQLite backend is not required to raise.)

3. When the views given to merge have incompatible types, IncompatibleType must be raised

Now suppose the list of views passed to merge contains views that do not all share the same STIX object type (for example, a url-typed view merged with an ipv4-addr-typed view). The operation must then raise IncompatibleType.

Notes

  • These changes must be applied consistently throughout the storage implementation, so that in cases (1) and (3) the SQLite-backed storage object behaves as specified.
  • Aside from the addition of the IncompatibleType exception, method names and signatures require no changes; the behavior described above is the only thing that must be implemented.

Summary

Your task is to change the behavior of a data storage component's grouping operation. When data is grouped by a specific column, the grouped output that results must not produce an aggregated version of the column that serves as the grouping key.

    • op (str): the operation to carry out. For this task, the value that matters is 'group'.

  • store.columns(name)

    • name (str): the identifier of a dataset that has been stored.
    • Returns a collection of the column names that are present in the stored dataset.

  • store.lookup(name)

Constraints

  • For a grouped dataset, the set of column names that store.columns(name) returns must exclude the unique_<grouping_column> name.
  • All other existing aggregation and grouping behavior stays unchanged; the only thing suppressed is the auto-aggregation of the grouping column.

Task Description

The existing Filter class (which lives in the query-building module) is to be extended so that, when it is rendered into SQL, it supports combining its predicates with either a logical AND or a logical OR.

What is required

The Filter class must accept an optional second constructor argument that specifies the boolean operator with which its contained predicates are joined:

Filter(predicates, conjunction=Filter.AND)
  • predicates: a list of Predicate objects (this behavior already exists).
  • The second positional argument determines the operator that joins the predicate clauses.
Class-level attributes

Filter must expose two class-level constants that are usable as the conjunction argument:

  • Filter.AND — join the predicates with AND.
  • Filter.OR — join the predicates with OR.
Behavior when rendered

When a Filter is rendered as part of a query:

  • Each predicate is rendered enclosed in its own pair of parentheses, e.g. ("foo" != %s).
  • The parenthesized predicate clauses are joined with the selected conjunction, which is surrounded by single spaces:
    • With Filter.AND: ("foo" != %s) AND ("bar" LIKE %s)
    • With Filter.OR: ("foo" != %s) OR ("bar" LIKE %s)
  • If no conjunction argument is supplied, the default behavior must be to join with AND (preserving existing behavior).
Compatibility with existing behavior

All rendering behavior that already exists must remain unchanged:

  • The render(placeholder) method still returns a (query_text, values) tuple, in which values is the ordered list of predicate values and placeholder is the parameter marker string (e.g. '%s' or '?').

By way of example, a query that filters my_table using two predicates joined by OR, along with limit and offset, when rendered with the ? placeholder, results in:

Chaining and grouping of query filters

Revise the public API for building queries in the codebase’s query module. The relevant public interfaces are the following:

  • Query()
    • append(component)
    • render(placeholder) -> (sql_text, values)
  • Table(name)
  • Predicate(column, operator, value)
  • Filter(predicates, op=Filter.AND)
    • Filter.OR
  • Limit(value)
  • Offset(value)
Behavior requirements
Grouping of OR filters

When a Filter uses Filter.OR, its whole disjunction must be rendered inside one additional pair of parentheses. The individual predicates are still parenthesized.

As an example:

query = Query()
query.append(Table('my_table'))
query.append(Filter([
    Predicate('foo', '!=', 0),
    Predicate('bar', 'LIKE', r'%blah%'),
], Filter.OR))

Calling query.render('%s') must return:

(
    'SELECT * FROM "my_table" WHERE (("foo" != %s) OR ("bar" LIKE %s))',
    [0, r'%blah%']
)

Appending Limit(10) must result in:

SELECT * FROM "my_table" WHERE (("foo" != %s) OR ("bar" LIKE %s)) LIMIT 10

Appending Offset(10) and rendering with ? placeholders must result in:

SELECT * FROM "my_table" WHERE (("foo" != ?) OR ("bar" LIKE ?)) LIMIT 10 OFFSET 10

The bound values remain in the order 0, then r'%blah%'.

Chaining of filters

More than one appended Filter must be accepted by a Query. Consecutive filters are combined implicitly with AND within the single WHERE clause.

Given:

query = Query()
query.append(Table('my_table'))
query.append(Filter([
    Predicate('foo', '=', 0),
    Predicate('bar', '=', 1),
], op=Filter.OR))
query.append(Filter([
    Predicate('baz', '!=', 2),
    Predicate('buz', '!=', 3),
]))

Calling query.render('%s') must return:

(
    'SELECT * FROM "my_table" WHERE (("foo" = %s) OR ("bar" = %s)) AND ("baz" != %s) AND ("buz" != %s)',
    [0, 1, 2, 3]
)

The OR filter must stay grouped, so that the implicit AND applies to the complete disjunction. The values must be ordered according to the insertion order of filters and predicates.

Predicates using IN

The existing rendering of IN must still expand a sequence into one placeholder per value:

query = Query()
query.append(Table('my_table'))
query.append(Filter([
    Predicate('foo', 'IN', [1, 2, 3]),
]))

Calling query.render('%s') must return:

(
    'SELECT * FROM "my_table" WHERE ("foo" IN (%s, %s, %s))',
    [1, 2, 3]
)

Task Description

Summary

You must make the merge operation of the storage class more robust so that, after any of the source views used in the merge are subsequently removed, the merged data remains fully intact and independent.

Public API

The tests construct the storage class via a tmp_storage(tmpdir) helper that returns an instance of the storage class under test. The class must support the following methods, all of which are already expected to exist and to continue working as before:

  • cache(bundle_name, files) — One or more data bundle files are ingested under a named bundle.
  • values(field, view_name) — Return an iterable of the values that the given field (e.g. 'url:value') has for the named view.
  • extract(new_view_name, entity_type, bundle_name, query) — Create a new named view that contains entities extracted from a bundle according to a query filter.
  • lookup(view_name) — The contents of a named view are returned.
  • merge(new_view_name, source_view_names) — Create a new named view whose contents are the union of the contents of the supplied list of source views.
  • remove_view(view_name) — A named view is deleted.

Required Functionality

merge(new_view_name, source_view_names)

When the operation is given a destination view name and a list of source view names that already exist, it creates a new view (new_view_name) whose set of values is exactly the union of the values that all of the listed source views contain.

The critical requirement under verification is independence of the merged result from its sources:

  • After two (or more) source views have been merged into a destination view, removing any subset of those source views (one of them, another of them, or all of them) must have no effect on the contents of the destination view.
  • Following such removals, a query for the values of the merged view must still return the complete union of the values that were present in the source views at the time of the merge.

Put differently, what merge must produce is a self-contained copy of the merged data, not a reference or dependency on the underlying source views. The merged view must not lose, alias, or share storage with the source views in such a way that deleting a source would corrupt the merged view or leave it partially empty.

Scenario that the behavior must satisfy
  1. A bundle has been cached, and the full set of field values across all entities is known.
  2. From that bundle, two disjoint, complementary views are extracted using filter queries — taken together, their values form the full set, and their union equals the complete set of values.
  3. The two views are merged into a new view. The values of the new view equal the complete set (the union of the two source views).
  4. Then, any combination of the source views is removed via remove_view.
  5. The values of the merged view must still equal the complete union of the values of the original two source views — the removals leave them unchanged.

Restrictions

  • remove_view must delete only the named view, and it must not disturb any independent (already merged) view.
  • Beyond ensuring the above behavior holds, no changes to method names or signatures are required.

Task Description

Background

Your work happens on firepit, a Python library that takes STIX 2.0 bundles in, loads them into a SQL-backed store, and presents the observed data as SQL views ("vars") that can be queried, extracted, sorted, and manipulated. This task brings several behavioral changes to the storage layer; the most important one lets view renaming overwrite an existing view.

Factory at package level

The firepit package is required to expose a get_storage function:

from firepit import get_storage
store = get_storage(dbname, session)
  • dbname: string identifying the database (with the SQLite backend, this is a file path).
  • session: string that identifies the session.
  • What the function returns is a storage object (the "store"). Repeated calls made with the same dbname/session must operate on one and the same underlying persistent data.
The storage object

At least the methods laid out in the subsections below must be implemented by the storage object. A connection attribute (a DB-API connection) must also be exposed by it; the cursors of that connection return rows on which access by column name is supported (e.g. row['c']).

delete()

All data and state bound up with the store are removed by this method; as a result, the next get_storage call for the same dbname/session begins empty.

cache(query_id, bundles)

One or more STIX bundles are ingested into the store by this method.

  • query_id: string identifier that goes with this ingest.
  • bundles: either a Python dict holding one already-parsed STIX bundle, or a list of file paths (strings) pointing at JSON files, each of which contains a STIX bundle.
  • Unrolling into per-type tables happens for every observed-data SCO the bundles contain. An identity table is where identity objects are stored.
  • De-duplication of identities: when multiple ingested bundles contain the same identity object (same id), it must be stored only once.
extract(view_name, sco_type, query_id, pattern)

A view named view_name is created (or replaced) by this method, holding all SCOs of type sco_type (out of the data ingested under query_id) which match the STIX pattern string that was given.

  • Should a view already exist under the name view_name, replacement happens even in cases where the SCO type of the new content differs from what it was before (put differently, changing the type of an existing view name must succeed and must not raise).
assign(view_name, source_view, op=..., by=...)

The result is a view view_name, derived from source_view, with some operation applied to it.

  • op='sort' combined with by=<column_name> is supported; the view that comes out of it is sorted ascending by the column named.
  • When a column is numeric, sorting must happen numerically. To spell out one consequence: a value of 0 in an integer column (e.g. a src_port of 0) must sort before positive values — handling it as null/absent, or pushing it to the end, must not occur.
lookup(view_name)

As a list of dict-like objects (column name → value), the rows of the named view are returned.

  • If no view exists under that name, firepit.exceptions.UnknownViewname is raised.
  • An id column is included in each returned row (it holds the SCO id, with an index suffix such as _0, _2, etc. that reflects the row's position within the observed-data object list).
count(sco_type)

How many rows are stored in the table for the given SCO type is what this returns (e.g. count('identity')).

values(path, view_name)

The list of values for the supplied object_type:property path (e.g. 'url:value') is returned, taken across the named view's rows.

reassign(view_name, rows)

Using the row dicts from the list that is supplied, the content associated with view_name is replaced.

  • Columns that were not there before (e.g. an added x_enrich field) may show up among the rows; such columns must be persisted and remain retrievable via lookup.
  • It must succeed to reassign into a view name that already exists (the very name from which the rows were produced). Once reassignment has happened, lookup(view_name) returns as many rows as were supplied, and the columns that were added are present with their values (e.g. x_enrich == 1).
rename_view(old_name, new_name)

The view old_name gets its name changed to new_name.

  • Overwrite behavior (primary requirement): if some view already bears the name new_name, that view must be clobbered/replaced by old_name. Once the operation completes:
    • As a view, old_name no longer exists: lookup(old_name) raises UnknownViewname.
    • new_name is present, and its content is the content old_name used to have.
    • Any membership bookkeeping kept in the __membership table for the old_name var must be cleared — following the rename, a query that counts __membership rows where var = '<old_name>' returns 0.
Application data attached to views
  • set_appdata(view_name, appdata_str): an arbitrary application-data string is stored, in association with the named view.
  • get_appdata(view_name): the stored application-data string for the named view is what this returns. Across separate store instances obtained via get_storage for the same dbname/session, that stored value must persist.
  • get_view_data(view_names): when handed a list of view names, this returns a list of dict-like records — one per view — each of which carries at least a name field (the view name) and an appdata field (that view's stored application-data string).

Internal tables that callers reference

  • __membership: this table records which var the SCO rows belong to, and it has at least a var column. When a view is renamed over an existing one (clobbered), or when a var is removed in some other way, no __membership rows that reference the removed var name may remain.
  • identity: identity objects are held by this table, de-duplicated by id.

Behavioral requirements, summarized (edge cases)

  1. Identity de-duplication: when multiple bundles with a shared identity are ingested, exactly one identity row is what results.
  2. Port/zero-value sorting: when the sort key is a numeric column, 0 values are placed ahead of positive ones.
  3. View type change: re-extracting into an existing view name, using a different SCO type, succeeds with no error.
  4. Reassign into same view: this is allowed; the row count is preserved, as are any columns that were newly added.
  5. Rename over existing view: overwriting happens at the destination view, the source name stops existing, and membership entries gone stale for the source name get purged.

Exceptions

Both of the following must be importable from firepit.exceptions:

  • UnknownViewname — raised by lookup (and by any equivalent lookup) when no view exists under the given name.
  • IncompatibleType — an exception type which must exist and be importable.

Notes regarding numeric values

The values returned for numeric SCO fields (e.g. pid, ports) are numeric Python values. The backend in use determines the form: an integer-valued field may be returned either as a Python int or as a decimal.Decimal; for integer-valued fields, representation as either of the two is acceptable.

Requirement around test support

tests/conftest.py is going to be present. Ensure the package can be imported and put to use as described; a setup.py sits at the top level as well, and it must not interfere with test collection.

Serving as inputs are JSON bundle files of the standard STIX 2.0 kind: bundles carrying type: "bundle", a spec_version, and an objects array that contains identity and observed-data objects. Inside an observed-data object there is an objects map keyed by string indices; every entry is an SCO (e.g. ipv4-addr, network-traffic, url, user-account), and the references among them take the form of index strings.

  • If the rows of a network-traffic view are sorted with src_port ascending, the first row (the row where src_port is 0) ends up with id equal to 'network-traffic--6ecfde62-7543-5fea-94bf-0e6bb30fdaff'. So the deduplicated entity carries a single UUID-style identifier, and no positional suffix gets appended to it.

Notes and Constraints

  • Apart from the membership/count facts stated above, these requirements put no constraint on the ordering of the lists that store.values(...) returns; what matters is that the specific values are present and that the counts are exact.
  • Sorting done via assign(..., op='sort', by='src_port') arranges the rows in ascending order by the given column.
  • What columns(...) produces is a membership collection: the reference column name ('process_ref') must be among its contents, and the flattened variant ('process_ref.id') must not be among them.
