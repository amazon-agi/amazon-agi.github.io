01 The pyschlage Python package offers a client for interacting with Schlage smart locks through the Allegion cloud API. 942 words · source specification, reworded by GLM-5.3-Flash

Task Description

The pyschlage Python package offers a client for interacting with Schlage smart locks through the Allegion cloud API. Two areas of functionality must be extended: the authentication layer and the lock control layer.

1. Authentication: exposing the authenticated user's ID

The Auth class in the pyschlage.auth module (constructed via Auth(username, password)) must be given a read-only property named user_id.

What happens when auth.user_id is accessed:

  • Sends an HTTP GET request to the relative endpoint users/@me. Specifically, the underlying request machinery gets invoked as:
    requests.request(
    "get",
    "https://api.allegion.yonomi.cloud/v1/users/@me",
    timeout=60,
    auth=<the SRP auth object>,
    headers={"X-Api-Key": API_KEY},
)
    (This mirrors the request behavior the class already applies to its other calls — base URL prefix, 60-second timeout, SRP auth object, and the X-Api-Key header set to the module-level API_KEY.)
  • Parses the JSON response body, a dictionary that contains an "identityId" field, and returns that field's value as the user ID.
  • Caches the result: the request must happen only on the first access. Every subsequent access of user_id returns the cached value, and no further HTTP request is performed.

2. Lock control: supporting both Wi-Fi and non-Wi-Fi (BLE) locks

The Lock class in the pyschlage.lock module must correctly handle both locks that communicate directly over Wi-Fi and locks that communicate via a bridge/hub (BLE locks). Changing lock state requires different API calls for these two kinds.

Parsing: Lock.from_json(auth, json)

The classmethod Lock.from_json(auth, json) constructs a Lock from the device JSON dictionary. Besides any existing attributes, the resulting Lock instance must expose:

  • device_id — taken from the top-level "deviceId" field.
  • name — taken from the top-level "name" field.
  • model_name — taken from the top-level "modelName" field.
  • device_type — taken from the top-level "devicetypeId" field.
  • battery_level — taken from json["attributes"]["batteryLevel"].
  • firmware_version — taken from json["attributes"]["mainFirmwareVersion"].
  • is_locked — True if json["attributes"]["lockState"] == 1, otherwise False.
  • is_jammed — True if json["attributes"]["lockState"] == 2, otherwise False.
  • _cat — an attribute that holds the value of the top-level "CAT" field.

The auth object that was passed in must be held by the _auth attribute.

How Wi-Fi and BLE locks are distinguished

The device type (device_type / the "devicetypeId" field) determines whether a lock is a Wi-Fi lock or a BLE lock. Wi-Fi locks are the ones whose device type is "be489wifi". A lock with any other device type (e.g. "be479") is treated as a non-Wi-Fi (BLE) lock that must be commanded through the hub. No separate public accessor is required for this distinction beyond the behavior described below.

The lock() and unlock() methods

Each of these two methods changes the lock's state and then updates the instance so that is_locked reflects the new state. Which request is issued depends on the lock kind:

Wi-Fi locks (those with device type "be489wifi"):

  • lock() sends:
    auth.request("put", "devices/<device_id>", json={"attributes": {"lockState": 1}})
  • unlock() sends:
    auth.request("put", "devices/<device_id>", json={"attributes": {"lockState": 0}})
  • The response body is device JSON (same shape as the input to from_json); the lock's state must be refreshed from it. After lock(), is_locked is True; after unlock(), is_locked is False.

BLE locks (any other device type):

  • Commands go to a per-device commands endpoint via HTTP POST. lock() issues:
    auth.request(
    "post",
    "devices/<device_id>/commands",
    json={
        "data": {
            "CAT": <the lock's CAT value>,
            "deviceId": <device_id>,
            "state": 1,
            "userId": <auth.user_id>,
        },
        "name": "changelockstate",
    },
)
    and unlock() issues the same call with "state": 0.
  • The CAT value is the one captured into _cat from the JSON. The userId is obtained from the auth object's user_id property. The deviceId is the lock's device_id.
  • Once the command has been issued, the lock's state must be updated locally: after lock(), is_locked is True; after unlock(), is_locked is False. (For BLE locks the state is set directly instead of being re-read from the response.)
The refresh() method

refresh() performs this request:

auth.request("get", "devices/<device_id>")

The response body is device JSON of the same shape from_json accepts, and the lock's attributes (e.g. name) must be updated from it.

The access_codes() method

access_codes() performs this request:

auth.request("get", "devices/<device_id>/storage/accesscode")

The response body is a list of access-code JSON dictionaries. The method returns a list of AccessCode objects, each built via AccessCode.from_json(auth, <each item>, device_id).

The add_access_code(code) method

When given an AccessCode instance code, this performs the following request:

auth.request("post", "devices/<device_id>/storage/accesscode", json=code.to_json())

The response body is an access-code JSON dictionary. After the call, the code object that was passed in must be updated so that its _auth attribute holds the lock's auth object (and it is otherwise populated from the returned JSON).

3. Access codes (behavior unchanged, restated for completeness)

The pyschlage.code module exposes AccessCode, DaysOfWeek, RecurringSchedule, and TemporarySchedule. The behavior that is relevant here:

  • AccessCode.from_json(auth, json, device_id) builds an AccessCode from an access-code JSON dictionary. It reads accessCode (an int, exposed as the string code), accesscodeId (exposed as access_code_id), friendlyName (exposed as name), and the schedule under schedule1.
  • AccessCode.to_json() returns the JSON representation while omitting the accesscodeId key (the id is not mutable and does not get sent back).
  • When two AccessCode objects are built from equivalent JSON with the same auth, device_id, and access_code_id, they compare equal.

These access-code behaviors already exist; ensure the Lock methods integrate with them in the way described above. The access-code JSON schema requires no changes.

Additional notes

  • The relative endpoint strings passed to auth.request(...) must match exactly what is given (no leading slash, no base URL).
  • The auth object passed to the Lock methods exposes a request(method, path, ...) method and a user_id property.

Task: Implement the LockLog class in pyschlage/log.py

Overview

Add a new module pyschlage/log.py defining a LockLog class that represents one log entry from a Schlage lock. The class must be constructible directly as well as via a from_json classmethod that parses a raw JSON-style dictionary.

Public API

Module

pyschlage.log

Class: LockLog

The class must support the following fields, all of them settable as keyword arguments in the constructor:

  • created_at: a datetime.datetime value
  • accessor_id: an optional string (may be None)
  • access_code_id: an optional string (may be None)
  • message: a string

If two LockLog instances are constructed with equal field values, they must compare equal (==).

Class Method: LockLog.from_json(json)

The signature is from_json(cls, json: dict) -> LockLog.

The method parses a raw log dictionary and returns a populated LockLog instance.

Shape of the Input

In its relevant parts, the input dictionary has (at least) the following shape:

{
    "createdAt": "2023-03-01T17:26:47.366Z",
    "message": {
        "accessorUuid": "<uuid-or-value>",
        "eventCode": <int>,
        "keypadUuid": "<uuid-or-value>",
        ...
    },
    ...
}

Other keys may be present in the dictionary as well as in the nested message object; they are not used.

Parsing Rules

created_at

Turn the createdAt string into a datetime.datetime by parsing it. The string is a UTC timestamp in ISO-8601 format with millisecond precision and a trailing Z, e.g. "2023-03-01T17:26:47.366Z". In the resulting datetime, the microsecond component must equal the milliseconds converted to microseconds (e.g. .366 → 366000 microseconds). For the example above, the result is datetime(2023, 3, 1, 17, 26, 47, 366000).

The "default" sentinel UUID

A special sentinel UUID value exists:

ffffffff-ffff-ffff-ffff-ffffffffffff

If accessorUuid or keypadUuid inside the nested message equals this sentinel, it is treated as "no value" (i.e. None).

accessor_id

The accessor_id field is derived from message["accessorUuid"]:

  • When it equals the sentinel default UUID, accessor_id is None.
  • In all other cases, accessor_id is the raw accessorUuid string.
access_code_id

The access_code_id field is derived from message["keypadUuid"]:

  • When it equals the sentinel default UUID, access_code_id is None.
  • In all other cases, access_code_id is the raw keypadUuid string.
message

The message field is derived by mapping the integer message["eventCode"] to a human-readable string. The following mappings are required:

eventCode message
2 "Unlocked by keypad"
4 "Unlocked by thumbturn"
7 "Unlocked by mobile device"

Examples

Start from a base message of:

{
    "accessorUuid": "ffffffff-ffff-ffff-ffff-ffffffffffff",
    "keypadUuid": "ffffffff-ffff-ffff-ffff-ffffffffffff",
    "eventCode": <varies>,
    ...
}

and createdAt = "2023-03-01T17:26:47.366Z":

  • When eventCode = 4, the result is LockLog(created_at=datetime(2023, 3, 1, 17, 26, 47, 366000), accessor_id=None, access_code_id=None, message="Unlocked by thumbturn")

  • When eventCode = 2 and keypadUuid = "__access-code-id__", the result is LockLog(created_at=datetime(2023, 3, 1, 17, 26, 47, 366000), accessor_id=None, access_code_id="__access-code-id__", message="Unlocked by keypad")

  • When eventCode = 7 and accessorUuid = "__user-id__", the result is LockLog(created_at=datetime(2023, 3, 1, 17, 26, 47, 366000), accessor_id="__user-id__", access_code_id=None, message="Unlocked by mobile device")

Task Specification: Adding a user_id Property to Auth

Objective

A user_id property is to be added to the Auth class in the pyschlage.auth module. The property fetches the authenticated user's identity ID from the remote API and caches the result.

Public API

Module: pyschlage.auth

Class: Auth

  • Constructor: Auth(username, password)
  • Attributes/members that already exist and must remain available (callers and autospec-based mocking access them):
    • the request(...) method
    • API_KEY (a module-level constant in pyschlage.auth, referenced as pyschlage.auth.API_KEY)
  • Member to be added:
    • the user_id property (read-only)

Required Behavior of Auth.user_id

user_id is a property that returns a string containing the identity ID of the authenticated user.

Fetching the data

When the property is accessed for the first time, it must perform an HTTP request through the underlying requests.request function, passing exactly these arguments:

  • Positional argument 1: "get"
  • Positional argument 2: "https://api.allegion.yonomi.cloud/v1/users/@me"
  • Keyword argument timeout=60
  • Keyword argument auth=<the SRP auth object> — that is, the auth object with which the Auth instance makes its requests (the instance that pycognito.utils.RequestsSrpAuth produces)
  • Keyword argument headers={"X-Api-Key": <API_KEY>}, with the value being the module's API_KEY constant

The request is expected to return an object, and the .json() method of that object yields a dictionary. Inside that dictionary is a key "identityId", whose value is the user's identity ID. Example of the response shape:

{
  "consentRecords": [],
  "created": "2022-12-24T20:00:00.000Z",
  "email": "asdf@asdf.com",
  "friendlyName": "username",
  "identityId": "<user-id>",
  "lastUpdated": "2022-12-24T20:00:00.000Z"
}

From the response body, the property returns the value of "identityId" (e.g. "<user-id>").

The request must be made exactly once for each underlying HTTP call — accessing the property triggers a single requests.request invocation with the arguments listed above (no additional or duplicated calls).

Caching

This result must be cached on the Auth instance. After the first retrieval that succeeds, any subsequent access of user_id must return the same value without sending any further HTTP request. To be explicit: a second access, and every access after it, must not call requests.request again.

Constraints and Notes

  • The Auth class must be defined so that a strict, spec-set autospec mock of it (i.e., mocking that permits only the attributes/methods actually present on the class) exposes both request and user_id. Ensure that user_id is a genuine member of the class so that such mocking is able to discover it.
  • The argument shape of request calls that already exist elsewhere must not be changed; the only thing being added is the new user_id behavior.

Lock field Payload source

name Top-level "name"
model_name Top-level "modelName"
device_type Top-level "devicetypeId"
_cat Top-level "CAT"

is_jammed Whether json["attributes"]["lockState"] equals 2

Within the "attributes" dictionary, "batteryLevel" is optional.

  • When the key is present, battery_level must contain that value, and the established conversion behavior must not change. In particular, a present value of 0 must remain 0 and must not be treated as missing.
  • When the key is absent, construction must succeed and battery_level must be None. The absence of the key must not raise KeyError or another missing-key exception.
Firmware version is optional

Within the "attributes" dictionary, "mainFirmwareVersion" is optional.

  • When the key is absent, construction must succeed and firmware_version must be None. The absence of the key must not raise KeyError or another missing-key exception.

The two optional fields are independent: either one or both may be absent. Their absence must not change any other field mapping or state calculation. auth.request(
    "put",
    "devices/<device_id>",

auth.request(

            "deviceId": <device_id>,

auth.request("get", "devices/<device_id>/storage/accesscode")

AccessCode.from_json(auth, entry_json, lock.device_id)

Lock.add_access_code(code)

When this method is given an AccessCode, it must serialize it with code.to_json() and issue:

auth.request(
    "post",
    "devices/<device_id>/storage/accesscode",
    json=<serialized code>,
)

The same code object is populated in place by the response JSON. Specifically:

  • code._auth becomes the authentication object of the lock.
  • code.device_id becomes the device identifier of the lock.
  • code.access_code_id becomes the response's accesscodeId, such as "__access_code_uuid__".

Scope and Related Types

  • pyschlage.auth.Auth continues to be the authentication and request client. An authentication object that is supplied must continue to be retained by identity, and BLE state-change commands use its user_id.
  • pyschlage.code.AccessCode keeps its existing from_json(auth, json, device_id) and to_json() interactions, together with its _auth, device_id, and access_code_id fields.
  • Behavior outside the two newly optional lock attributes must not be redesigned. Request paths, HTTP methods, payload shapes, state semantics, authentication behavior, and access-code behavior as they exist today must remain compatible.

2. Redaction utility (pyschlage.common)

Create a module pyschlage.common that exposes a function with this signature:

def redact(data, *, allowed)
  • data is a JSON-like structure made up of nested dicts, lists, and scalar values (strings, ints).
  • allowed is a list of dot-delimited key paths that specify which values must be preserved. Every other scalar value is replaced with the literal string "<REDACTED>".
  • The function returns a new structure with the same shape; the input must not be mutated.

How paths are interpreted:

  • A path segment matches a dictionary key at the corresponding level of nesting. Segments of a path are joined with . in order to address nested keys (e.g. "c.c0" refers to the key "c0" inside the dict at key "c").
  • The wildcard segment "*":
    • With allowed=["*"], the entire structure is preserved unchanged (everything allowed).
    • A wildcard carrying a prefix, like "c.*", preserves every value nested under key "c", at any depth.
  • Naming a key whose value is a dict (e.g. "c") preserves that whole subtree, at any depth (the same as allowing everything under it).
  • Naming a key whose value is a list (e.g. "d") preserves the list along with its elements.
  • Naming a key whose value is a nested dict (e.g. "c.c2") preserves that nested subtree in its entirety.

How values are redacted:

  • A scalar value not covered by any allowed path becomes "<REDACTED>".
  • For a list value that is not preserved, each element is replaced by "<REDACTED>" (a list of a single string becomes ["<REDACTED>"]).
  • For a dict value, recursion continues into it, applying the allowed paths relative to the key path accumulated so far; keys inside it that are not individually or wildcard-allowed get their values redacted.

Goal

Extend the last_changed_by() method of the Lock class so that it recognizes a new lock action type: Apple Home NFC devices.

Background

A last_changed_by() method is exposed by the Lock class and returns a human-readable, lowercase string describing what or who last changed the lock state. This description is derived from the lock's lock_state_metadata object, which carries fields that include:

  • action_type — a string that identifies the mechanism or source of the change.
  • uuid — an optional string identifier tied to the actor/device (may be None).
  • name — a string label (other action types use it).

Required Behavior

When lock_state_metadata.action_type is equal to the string "AppleHomeNFC", the last_changed_by() method must return a string describing an Apple NFC device, in the following format:

  • In the case where lock_state_metadata.uuid is a non-empty string, return:

    apple nfc device - <resolved-name>

    with <resolved-name> being the display name resolved from the uuid. For a metadata object whose uuid resolves to a user named asdf, the value returned is exactly apple nfc device - asdf.

  • In the case where lock_state_metadata.uuid is None, return exactly:

    apple nfc device

    with no trailing separator and no name.

The value that is returned must be entirely lowercase, matching the existing behavior of last_changed_by() for other action types.

Constraints

  • The existing behavior of last_changed_by() for all other action_type values must remain unchanged.
  • The mechanism applied to resolve a uuid into a display name is the same resolution mechanism the class already uses for other uuid-based action types (i.e., the same fixture/user lookup that yields the name asdf for the test user uuid).

  • Module/class: Lock (imported as from ... import Lock, matching the way it is currently used).
