01 You are working on the pyschlage Python package, which provides a client for interacting with Schlage smart locks through the Allegion cloud API. 900 words · source specification

You are working on the pyschlage Python package, which provides a client for interacting with Schlage smart locks through the Allegion cloud API. You must extend two areas of functionality: the authentication layer and the lock control layer.

1. Authentication: expose the authenticated user's ID

In the pyschlage.auth module, the Auth class (constructed as Auth(username, password)) must gain a read-only property named user_id.

Accessing auth.user_id:

  • Performs an HTTP GET request to the relative endpoint users/@me. Concretely, the underlying request machinery is invoked as:
    requests.request(
    "get",
    "https://api.allegion.yonomi.cloud/v1/users/@me",
    timeout=60,
    auth=<the SRP auth object>,
    headers={"X-Api-Key": API_KEY},
)
    (This is the same request behavior the class already uses for other calls — base URL prefix, 60-second timeout, SRP auth object, and the X-Api-Key header set to the module-level API_KEY.)
  • Parses the JSON response body, which is a dictionary containing an "identityId" field, and returns the value of that field as the user ID.
  • Caches the result: the request must be performed only on the first access. Every subsequent access of user_id returns the cached value without performing any further HTTP request.

2. Lock control: support both Wi-Fi and non-Wi-Fi (BLE) locks

In the pyschlage.lock module, the Lock class must correctly handle locks that communicate directly over Wi-Fi as well as locks that communicate via a bridge/hub (BLE locks). These two kinds require different API calls to change lock state.

Lock.from_json(auth, json) — parsing

The classmethod Lock.from_json(auth, json) builds a Lock from the device JSON dictionary. In addition to any existing attributes, the resulting Lock instance must expose:

  • device_id — from the top-level "deviceId" field.
  • name — from the top-level "name" field.
  • model_name — from the top-level "modelName" field.
  • device_type — from the top-level "devicetypeId" field.
  • battery_level — from json["attributes"]["batteryLevel"].
  • firmware_version — from json["attributes"]["mainFirmwareVersion"].
  • is_locked — True when json["attributes"]["lockState"] == 1, otherwise False.
  • is_jammed — True when json["attributes"]["lockState"] == 2, otherwise False.
  • _cat — an attribute holding the value of the top-level "CAT" field.

The _auth attribute must hold the auth object that was passed in.

Distinguishing Wi-Fi from BLE locks

Whether a lock is a Wi-Fi lock or a BLE lock is determined by its device type (device_type / the "devicetypeId" field). Wi-Fi locks have a device type of "be489wifi". Locks with any other device type (e.g. "be479") are treated as non-Wi-Fi (BLE) locks that must be commanded through the hub. There is no separate public accessor required for this distinction beyond the behavior described below.

lock() and unlock()

Both methods change the lock's state and then update the instance so that is_locked reflects the new state. The request they issue depends on the lock kind:

Wi-Fi locks (device type "be489wifi"):

  • lock() issues:
    auth.request("put", "devices/<device_id>", json={"attributes": {"lockState": 1}})
  • unlock() issues:
    auth.request("put", "devices/<device_id>", json={"attributes": {"lockState": 0}})
  • The response body is device JSON (same shape as from_json input); the lock's state must be refreshed from it. After lock(), is_locked is True; after unlock(), is_locked is False.

BLE locks (any other device type):

  • Commands are sent to a per-device commands endpoint via HTTP POST. lock() issues:
    auth.request(
    "post",
    "devices/<device_id>/commands",
    json={
        "data": {
            "CAT": <the lock's CAT value>,
            "deviceId": <device_id>,
            "state": 1,
            "userId": <auth.user_id>,
        },
        "name": "changelockstate",
    },
)
    and unlock() issues the same call with "state": 0.
  • The CAT value is the one captured into _cat from the JSON. The userId is obtained from the auth object's user_id property. The deviceId is the lock's device_id.
  • After issuing the command, the lock's state must be updated locally: after lock(), is_locked is True; after unlock(), is_locked is False. (For BLE locks the state is set directly rather than being re-read from the response.)
refresh()

refresh() performs:

auth.request("get", "devices/<device_id>")

The response body is device JSON of the same shape accepted by from_json, and the lock's attributes (e.g. name) must be updated from it.

access_codes()

access_codes() performs:

auth.request("get", "devices/<device_id>/storage/accesscode")

The response body is a list of access-code JSON dictionaries. The method returns a list of AccessCode objects built via AccessCode.from_json(auth, <each item>, device_id).

add_access_code(code)

Given an AccessCode instance code, this performs:

auth.request("post", "devices/<device_id>/storage/accesscode", json=code.to_json())

The response body is an access-code JSON dictionary. After the call, the passed code object must be updated so that its _auth attribute holds the lock's auth object (and it is otherwise populated from the returned JSON).

3. Access codes (unchanged behavior, restated for completeness)

The pyschlage.code module exposes AccessCode, DaysOfWeek, RecurringSchedule, and TemporarySchedule. The behavior relevant here:

  • AccessCode.from_json(auth, json, device_id) builds an AccessCode from an access-code JSON dictionary. It reads accessCode (an int, exposed as the string code), accesscodeId (exposed as access_code_id), friendlyName (exposed as name), and the schedule under schedule1.
  • AccessCode.to_json() returns the JSON representation, omitting the accesscodeId key (the id is not mutable and is not sent back).
  • Two AccessCode objects built from equivalent JSON with the same auth, device_id, and access_code_id compare equal.

These access-code behaviors already exist; ensure the Lock methods integrate with them as described above. No changes to the access-code JSON schema are required.

Notes

  • The relative endpoint strings passed to auth.request(...) must match exactly as given (no leading slash, no base URL).
  • The auth object passed to Lock methods exposes a request(method, path, ...) method and a user_id property.

Overview

Create a new module pyschlage/log.py that defines a LockLog class representing a single log entry from a Schlage lock. The class must be constructible directly and via a from_json classmethod that parses a raw JSON-style dictionary.

Public API

Module

pyschlage.log

Class: LockLog

The class must support the following fields, all settable as keyword arguments in the constructor:

  • created_at: a datetime.datetime value
  • accessor_id: an optional string (may be None)
  • access_code_id: an optional string (may be None)
  • message: a string

Two LockLog instances constructed with equal field values must compare equal (==).

Classmethod: LockLog.from_json(json)

Signature: from_json(cls, json: dict) -> LockLog

Parses a raw log dictionary and returns a populated LockLog instance.

Input Structure

The input dictionary has (at least) the following relevant shape:

{
    "createdAt": "2023-03-01T17:26:47.366Z",
    "message": {
        "accessorUuid": "<uuid-or-value>",
        "eventCode": <int>,
        "keypadUuid": "<uuid-or-value>",
        ...
    },
    ...
}

Other keys may be present in the dictionary and in the nested message object; they are not used.

Parsing Behavior

created_at

Parse the createdAt string into a datetime.datetime. The string is an ISO-8601 UTC timestamp with millisecond precision and a trailing Z, e.g. "2023-03-01T17:26:47.366Z". The resulting datetime must have its microsecond component equal to the milliseconds converted to microseconds (e.g. .366 → 366000 microseconds). For the example above the result is datetime(2023, 3, 1, 17, 26, 47, 366000).

The sentinel "default" UUID

There is a special sentinel UUID value:

ffffffff-ffff-ffff-ffff-ffffffffffff

When accessorUuid or keypadUuid in the nested message equals this sentinel, it is treated as "no value" (i.e. None).

accessor_id

Derived from message["accessorUuid"]:

  • If it equals the sentinel default UUID, accessor_id is None.
  • Otherwise, accessor_id is the raw accessorUuid string.
access_code_id

Derived from message["keypadUuid"]:

  • If it equals the sentinel default UUID, access_code_id is None.
  • Otherwise, access_code_id is the raw keypadUuid string.
message

Derived by mapping the integer message["eventCode"] to a human-readable string. The following mappings are required:

eventCode message
2 "Unlocked by keypad"
4 "Unlocked by thumbturn"
7 "Unlocked by mobile device"

Examples

Given a base message of:

{
    "accessorUuid": "ffffffff-ffff-ffff-ffff-ffffffffffff",
    "keypadUuid": "ffffffff-ffff-ffff-ffff-ffffffffffff",
    "eventCode": <varies>,
    ...
}

and createdAt = "2023-03-01T17:26:47.366Z":

  • eventCode = 4 → LockLog(created_at=datetime(2023, 3, 1, 17, 26, 47, 366000), accessor_id=None, access_code_id=None, message="Unlocked by thumbturn")

  • eventCode = 2, keypadUuid = "__access-code-id__" → LockLog(created_at=datetime(2023, 3, 1, 17, 26, 47, 366000), accessor_id=None, access_code_id="__access-code-id__", message="Unlocked by keypad")

  • eventCode = 7, accessorUuid = "__user-id__" → LockLog(created_at=datetime(2023, 3, 1, 17, 26, 47, 366000), accessor_id="__user-id__", access_code_id=None, message="Unlocked by mobile device")

20 Extend the last_changed_by() method on the Lock class to recognize a new lock action type 297 words · source specification

Objective

Extend the last_changed_by() method on the Lock class to recognize a new lock action type: Apple Home NFC devices.

Context

The Lock class exposes a last_changed_by() method that returns a human-readable, lowercase string describing what or who last changed the lock state. It derives this description from the lock's lock_state_metadata object, which carries fields including:

  • action_type — a string identifying the mechanism/source of the change.
  • uuid — an optional string identifier associated with the actor/device (may be None).
  • name — a string label (used by other action types).

Required Behavior

When lock_state_metadata.action_type is equal to the string "AppleHomeNFC", last_changed_by() must return a string describing an Apple NFC device, formatted as follows:

  • If lock_state_metadata.uuid is a non-empty string, return:

    apple nfc device - <resolved-name>

    where <resolved-name> is the display name resolved from the uuid. For a metadata object whose uuid resolves to a user with the name asdf, the returned value is exactly apple nfc device - asdf.

  • If lock_state_metadata.uuid is None, return exactly:

    apple nfc device

    with no trailing separator or name.

The returned value must be entirely lowercase, consistent with the existing behavior of last_changed_by() for other action types.

Constraints

  • All existing behavior of last_changed_by() for other action_type values must remain unchanged.
  • The mechanism used to resolve a uuid into a display name is the same resolution mechanism the class already uses for other uuid-based action types (i.e., the same fixture/user lookup that yields the name asdf for the test user uuid).

Public API

  • Module/class: Lock (imported as from ... import Lock, as currently used).
  • Method: Lock.last_changed_by(self) -> str — existing method, behavior extended as described above.

No other API surface changes are required.
