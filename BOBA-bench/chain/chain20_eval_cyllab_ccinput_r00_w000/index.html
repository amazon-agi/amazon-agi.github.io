01 Add ORCA input-file generation to ccinput and integrate it with the existing input-generation entry point. 2051 words · rewritten by GPT-5.6-sol

Objective

Add ORCA input-file generation to ccinput and integrate it with the existing input-generation entry point. Requests whose software parameter is ORCA must produce correctly formatted ORCA input while existing Gaussian generation remains compatible, except for the shared specification-string sanitization explicitly defined below.

Public API

ccinput.packages.orca

Provide an importable class named OrcaCalculation. The calculation object returned for an ORCA request must expose the complete generated input as a string attribute named input_file.

ccinput.wrapper.generate_input

The existing generate_input(**params) function must route an ORCA request to OrcaCalculation and return the resulting calculation object. Gaussian requests must continue to route to ccinput.packages.gaussian.GaussianCalculation.

The ORCA behavior described here applies when params['software'] == 'ORCA'.

Input Parameters

Values are strings unless otherwise noted.

  • type: calculation type, mapped to an ORCA keyword as described below.
  • in_file: path to an .xyz geometry file. Atom records are read from this file.
  • software: ORCA.
  • theory_level: one of Semi-empirical, HF, DFT, or RI-MP2.
  • method: computational method, for example AM1, B3LYP, or M06-2X. It is not used for HF or RI-MP2.
  • basis_set: basis-set name, for example 3-21G, Def2-SVP, 6-31+G(d,p), or cc-pVTZ. It is not used for semi-empirical calculations.
  • charge: molecular charge, for example -1, 0, or +1.
  • solvent: optional solvent name.
  • solvation_model: optional; supported values are SMD and CPCM.
  • solvation_radii: optional radius set, including SMD18.
  • specifications: optional additional-keyword string.
  • constraints: semicolon-separated constraint string for constrained optimisations.
  • custom_basis_sets: optional semicolon-separated per-element basis specification.

The existing processor-count input may determine the integer in the %pal block. The multiplicity is 1 for all scenarios covered by this specification.

Shared specifications Sanitization

Before any backend-specific lowercasing, parenthesis validation, tokenization, deduplication, grouping, or special-token handling, sanitize the entire specifications string for both Gaussian and ORCA calculations.

The only permitted characters are:

  • ASCII letters A-Z and a-z;
  • digits 0-9;
  • /, (, ), =, -, ,, and .; and
  • the literal space character.

Every other character must be removed rather than causing an error. Processing then continues on the sanitized string. Any token that is empty after this filtering must be silently discarded. It must not contribute to the generated command or route line, any additional-command collection, or any exposed confirmed_specifications value.

For example, specifications='!#' sanitizes to an empty string. A Gaussian geometrical optimisation that would otherwise have route line #p opt M062X/Def2SVP must retain exactly that route line, with no extra specification token. The ignored characters must likewise be absent from the returned object's specification-related state. The same filtering rule applies before ORCA specification processing.

Allowed but malformed syntax remains subject to the backend's existing validation; for example, unmatched allowed parentheses in a Gaussian specification still raise an exception.

ORCA Output Structure and Formatting

The sections occur in this exact order:

  1. command line beginning with !;
  2. *xyz geometry block;
  3. optional %geom block for a constrained optimisation;
  4. optional %basis block for applicable custom basis sets;
  5. optional %output block for Hirshfeld population output;
  6. %pal block, always present;
  7. optional trailing %cpcm block for SMD solvation.

Except for the two explicitly required separator blank lines in an ECP-bearing %basis block, input_file must contain no blank lines between sections or within blocks. It must have no leading or trailing blank lines and must not end in a newline; its final character belongs to the final line, normally an end line.

Leading and trailing whitespace on individual non-geometry lines is not semantically significant. Internal spacing is significant, especially in geometry records and basis/ECP data. The exact numeric value on the nprocs line may vary, but the line and block shape are mandatory.

Command line

The first token after ! is selected from type:

type ORCA keyword
Single-Point Energy SP
Geometrical Optimisation OPT
Frequency Calculation FREQ
Constrained Optimisation OPT
NMR Prediction NMR
TS Optimisation OPTTS

Append method and basis tokens as follows:

  • Semi-empirical: append method unchanged, such as AM1.
  • HF: append HF, then basis_set.
  • DFT: append the normalized method, then basis_set. In particular, M06-2X becomes M062X, while B3LYP remains B3LYP.
  • RI-MP2: append RI-MP2, then basis_set; the method parameter is not used.

Representative command lines are:

!SP AM1
!SP HF 3-21G
!SP M062X Def2-SVP
!OPT B3LYP 6-31+G(d,p)
!SP RI-MP2 cc-pVTZ
!OPTTS B3LYP 6-31+G(d,p)

CPCM and ordinary specification tokens are appended after these method/basis tokens as described below.

ORCA specification tokens

Apply the shared sanitization first. Then split the remaining specification text into space-separated tokens, lowercase the tokens, preserve first-occurrence order, and suppress case-insensitive duplicates.

Ordinary tokens are appended to the ! command line. Examples:

  • TightSCF produces !SP M062X Def2-SVP tightscf.
  • TightSCF GRID6 produces !SP M062X Def2-SVP tightscf grid6.
  • tightscf TightSCF GRID6 produces the same tightscf grid6 suffix only once.
  • For RI-MP2, cc-pVTZ/C is retained as the lowercased auxiliary-basis token cc-pvtz/c, producing !SP RI-MP2 cc-pVTZ cc-pvtz/c.

The token phirshfeld, matched case-insensitively after sanitization, is consumed instead of being placed on the command line. It creates the %output block described below and must appear nowhere else in the generated input.

Geometry Block

After the command line, emit:

*xyz <charge> <multiplicity>
<atom records>
*

The .xyz atom records, following the atom-count and comment lines, must appear in source-file order. Support both single-atom and multi-atom files, including lone chlorine or iodine anions, ethanol, ammonia-like transition-state structures, and diaryliodonium cations. Each atom line must be reproduced character-for-character except that leading and trailing whitespace may be removed; internal spacing between the element symbol and coordinates must not be normalized.

Render charge as a plain integer. Thus +1 becomes 1, while -1 and 0 remain -1 and 0. For the covered behavior, multiplicity is 1:

*xyz 1 1
*xyz -1 1
*xyz 0 1

Constrained Optimisations

For type='Constrained Optimisation', use command keyword OPT and place a %geom block immediately after the geometry. constraints contains one or more semicolon-separated definitions. Empty segments, such as the segment after a trailing semicolon, do not create constraints.

Atom indices in the input constraint string are one-based. ORCA output indices are zero-based. For two, three, and four listed atoms, use letters B (bond), A (angle), and D (dihedral), respectively. For angles, preserve the required second-, first-, third-atom ordering represented by the input; for example, /2_1_3 must become A 1 0 2 after zero-based conversion. The same letter and ordering rules apply to scans and freezes.

Scan constraints

A scan has form:

Scan_<begin>_<end>_<steps>/<atoms>

It produces:

%geom Scan
<letter> <zero-based atoms> = <begin>, <end>, <steps>
end
end

Examples:

  • Scan_9_1.4_10/1_2; produces B 0 1 = 9, 1.4, 10.
  • Scan_9_90_10/2_1_3; produces A 1 0 2 = 9, 90, 10.
  • Scan_9_0_10/4_1_5_8; produces D 3 0 4 7 = 9, 0, 10.

For example, the complete bond-scan block is:

%geom Scan
B 0 1 = 9, 1.4, 10
end
end
Freeze constraints

A freeze has form:

Freeze/<atoms>

It produces:

%geom Constraints
{ <letter> <zero-based atoms> C }
end
end

Examples:

  • Freeze/1_2; produces { B 0 1 C }.
  • Freeze/2_1_3; produces { A 1 0 2 C }.
  • Freeze/4_1_5_8; produces { D 3 0 4 7 C }.

A constrained optimisation with an empty constraints value or no valid constraint must raise a Python exception. An empty required method must also raise a Python exception.

Custom Basis Sets

custom_basis_sets has the form:

<Element>=<BasisSet>;<Element>=<BasisSet>;

Emit a %basis block only when at least one requested element occurs in the geometry. Requests for absent elements are silently irrelevant. For example, N=Def2-SVP; produces no %basis block for a molecule without nitrogen.

All applicable element definitions share one block:

%basis
newgto <Element>
<ORCA shell data>
end
newgto <Element2>
<ORCA shell data>
end
end

Each newgto group uses the standard published Basis Set Exchange ORCA-format data for the requested basis, without the export wrapper/header. Shell headers, primitive numbering, exponents, contraction coefficients, scientific-notation style, and internal column alignment must be reproduced exactly. A group ends with end, and the final end closes %basis.

Required structural details include:

  • Nitrogen Def2-SVP, in order: one five-primitive S shell, two one-primitive S shells, one three-primitive P shell, one one-primitive P shell, and one one-primitive D shell. Shell headers have form <L> <count>, and primitive rows are numbered from 1.
  • Iodine Def2-TZVPD, in order: S shells with 5, 2, 1, 1, 1, 1, 1 primitives; P shells with 3, 4, 1, 1, 1, 1 primitives; D shells with 6, 1, 1, 1 primitives; and F shells with 1, 1 primitives.

When no ECP applies, as for nitrogen Def2-SVP, the newgto ... end group is followed immediately by the %basis closing end, with no blank separator.

Effective core potentials

If the selected custom basis includes an ECP, emit its standard ORCA NewECP group after the corresponding newgto group and inside %basis.

For iodine Def2-TZVPD, the layout is:

... end of newgto group

NewECP I
N_core 28
lmax f
s 7
<7 standard rows>
p 8
<8 standard rows>
d 10
<10 standard rows>
f 4
<4 standard rows>
end

end

There must be exactly one blank line between the newgto group's end and NewECP I, and exactly one blank line between the ECP group's end and the %basis closing end. These are the only permitted blank lines in an ORCA result.

The potential tables occur in s, p, d, f order and contain their standard def2-ECP values and alignment. Every table row contains a one-based row number, exponent, coefficient, and terminal power 2; the four f coefficients are negative. The complete basis and ECP numeric text must match the standard published definitions exactly.

Parallelization Block

A %pal block is always present and consists of exactly three lines:

%pal
nprocs <N>
end

<N> must be an integer. Its particular value is not otherwise constrained by this task.

Hirshfeld Population Output

If sanitized specifications contains phirshfeld, emit this exact block after any %geom and %basis blocks but before %pal:

%output
Print[ P_Hirshfeld] 1
end

The internal spacing and capitalization in Print[ P_Hirshfeld] 1 are significant. The triggering token is consumed completely and is not appended to the ! line.

Solvation

An absent solvation model means no solvation keyword or block. If solvent treatment is requested with a nonempty solvation_model other than SMD or CPCM, raise a Python exception.

CPCM

For solvation_model='CPCM', append this token to the command line after method/basis and other applicable command tokens:

CPCM(<canonical-solvent>)

Do not emit a %cpcm block for CPCM. For example:

!SP HF 3-21G CPCM(chloroform)
SMD

For solvation_model='SMD', do not add a solvation token to the command line. Emit this final block after %pal:

%cpcm
smd true
SMDsolvent "<canonical-solvent>"
end

For solvation_radii='SMD18', insert supported radius overrides immediately before this block's end. The available radius lines are iodine, radius[53] 2.74, and bromine, radius[35] 2.60. A bromine-only geometry emits its bromine line. An iodine-containing geometry must emit both lines below, in exactly this order, even if no bromine atom is present:

radius[53] 2.74
radius[35] 2.60
Solvent canonicalization

Canonicalize solvent names case-insensitively, including these synonyms and ORCA model-specific names:

Input SMD output CPCM output
Chloroform or CHCL3 SMDsolvent "chloroform" CPCM(chloroform)
octanol or 1-octanol SMDsolvent "1-octanol" CPCM(octanol)

Error Conditions

generate_input must raise a Python exception, with any exception class acceptable, for each of the following:

  • a supplied unsupported solvation-model value, such as ABC;
  • constrained optimisation with an empty constraints string or no valid constraint;
  • an empty method where the selected theory level/calculation requires a method.

Gaussian Compatibility

ORCA routing must not alter existing Gaussian input generation, object behavior, route construction, constraints, solvation, custom basis/ECP output, or other previously supported features. The sole required cross-backend adjustment is the shared specifications sanitization above.

In particular, disallowed characters in a Gaussian specification must never be copied into input_file, command/additional specification state, or confirmed_specifications. Tokens that remain valid after sanitization continue through the existing Gaussian behavior, including lowercasing, duplicate suppression, command-specific grouping, and rejection of unmatched parentheses.

Task Specification: ORCA Input File Generation

Objective

Implement and maintain ORCA input generation for Minimum Energy Path (NEB), molecular-orbital (MO), and Hirshfeld-population requests while preserving existing input-generation behavior for all other calculation types.

Public API and inputs

The behavior must be available through the existing ccinput.wrapper.generate_input(...) entry point. Callers may pass a parameter dictionary as keyword arguments, including type, in_file, auxiliary_file, software, theory_level, method, basis_set, charge, multiplicity, and specifications. The returned calculation object exposes the complete generated text through its input_file attribute.

software values identifying ORCA are case-insensitive; both ORCA and orca must select ORCA generation. The primary XYZ structure comes from in_file. Its atom-count and comment lines are not included in the ORCA coordinate body. Unless supplied otherwise, charge and multiplicity are 0 and 1, respectively.

1. Minimum Energy Path (NEB) calculations

A request with type equal to Minimum Energy Path and ORCA as the software must generate an ORCA NEB input.

Command line

The first line must be exactly:

!NEB

This is the complete NEB command line. Do not append method, basis_set, or the --nimages option to it. method, basis_set, and theory_level are not required for this calculation type; if method or basis-set values are supplied, they must not alter the !NEB line.

Coordinates and endpoint

The primary structure is serialized as the standard ORCA coordinate section:

*xyz <charge> <multiplicity>
<primary atom-coordinate lines>
*

The product/end structure is supplied through auxiliary_file. The generated input refers to that structure by the fixed name struct2.xyz, regardless of the source file's original name.

Immediately after the primary coordinate section, emit:

%neb
product "struct2.xyz"
nimages <N>
end

The endpoint keyword must be product; do not use an alternative endpoint keyword.

Image count

The specifications string may contain the command-line-style option:

--nimages <N>

N is an integer and becomes the value on the nimages line. The option and its argument are consumed during parsing and must not be serialized onto the !NEB line. If specifications is omitted, empty, or contains no --nimages option, use the default:

nimages 8

For example, specifications="--nimages 12" produces nimages 12.

A complete NEB layout is therefore:

!NEB
*xyz <charge> <multiplicity>
<primary atom-coordinate lines>
*
%neb
product "struct2.xyz"
nimages <N>
end
%pal
nprocs 8
end

2. MO calculations

Support type="MO Calculation" for ORCA. It is serialized as a single-point command followed by a cube-plot request.

For theory_level="DFT", method="B3LYP", and basis_set="def2tzvp", normalize the basis-set name and emit this exact header:

!SP B3LYP Def2-TZVP

The coordinate section is the standard ORCA section built from the primary structure:

*xyz <charge> <multiplicity>
<atom-coordinate lines>
*

Thus a charge value of "+1" and singlet multiplicity produce *xyz 1 1.

Orbital indices

Orbital numbering is zero-based. For a supported singlet request, determine the electron count from the atoms and molecular charge:

E = sum(atomic numbers of all atoms) - charge

Let O = floor(E / 2). Use the following plot indices:

  • HOMO index: O - 1
  • LUMO index: O
  • LUMOA index: O + 1
  • LUMOB index: O + 2

Equivalently, the latter three indices are the HOMO index plus one, two, and three. For the specified Ph2I_cation structure with charge +1, these indices are 66, 67, 68, and 69.

Plot block

After the coordinate section, emit the following block exactly, substituting the computed indices:

%plots
dim1 45
dim2 45
dim3 45
min1 0
max1 0
min2 0
max2 0
min3 0
max3 0
Format Gaussian_Cube
MO("in-HOMO.cube",<homo_index>,0);
MO("in-LUMO.cube",<lumo_index>,0);
MO("in-LUMOA.cube",<lumoa_index>,0);
MO("in-LUMOB.cube",<lumob_index>,0);
end

The filenames, capitalization, punctuation, dimensions, bounds, and Gaussian_Cube format are required as shown.

There must be exactly one blank line between the end that closes %plots and the following %pal line. The tail of an MO input therefore has this form:

MO("in-LUMOB.cube",<lumob_index>,0);
end

%pal
nprocs 8
end

3. Specification parsing and Hirshfeld output

A command-line-style specification flag is identified by its leading -- prefix. In particular, recognize --nimages <N> and --phirshfeld as control options and consume them rather than copying them to the ORCA command line.

When specifications contains --phirshfeld, leave the normal command line unchanged and insert this exact block after the closing * of the coordinate section and before %pal:

%output
Print[ P_Hirshfeld] 1
end

For example, a DFT single-point request using M06-2X and Def2-SVP must retain:

!SP M062X Def2-SVP

It must not become !SP M062X Def2-SVP phirshfeld or include --phirshfeld. Its relevant block order is:

!SP M062X Def2-SVP
*xyz <charge> <multiplicity>
<atom-coordinate lines>
*
%output
Print[ P_Hirshfeld] 1
end
%pal
nprocs 8
end

Existing ordinary ORCA specification tokens remain supported: tokens that are not one of these special consumed controls continue to be emitted as command-line keywords using the existing normalization and de-duplication behavior. For example, TightSCF GRID6 yields tightscf grid6, and repeated equivalent tokens appear only once in first-occurrence order.

4. Common ORCA structure and ordering

All calculation types described above must include:

%pal
nprocs 8
end

The required order is:

  1. ORCA ! command line.
  2. *xyz coordinate section.
  3. Calculation-specific blocks (%neb, %plots, or %output, as applicable).
  4. %pal block.

Line content and block order are significant. Except for the mandatory single blank line between %plots and %pal in an MO calculation, indentation and other blank-line differences between blocks are not significant.

Compatibility and scope

Do not change established behavior for Gaussian generation, other ORCA calculation types, ordinary ORCA command-line specifications, coordinate serialization, method/basis normalization, charge or multiplicity handling, custom basis sets, constraints, or solvation. The additions in this specification are limited to dispatching and serializing the ORCA NEB and MO calculation types and correctly consuming the two special double-dash controls described above.

Task Specification: Computational Chemistry Input Generation

Overview

ccinput is a Python package that generates input files for Gaussian and ORCA. Implement the resource-parameter behavior described below while preserving all existing calculation generation, formatting, compatibility, and validation behavior. Also provide the shared input-comparison utility described in this specification.

Public API

ccinput.wrapper.generate_input

ccinput.wrapper.generate_input(**params) remains the public generation entry point. It accepts the existing generation parameters, including (but not limited to) type, in_file, xyz, software, theory_level, method, basis_set, charge, multiplicity, solvent, solvation_model, solvation_radii, specifications, density_fit, custom_basis_sets, constraints, auxiliary_file, nproc, and mem.

On successful generation, this function returns the generated calculation object, not the input text as a bare string:

  • Gaussian generation returns a ccinput.packages.gaussian.GaussianCalculation object.
  • ORCA generation returns a ccinput.packages.orca.OrcaCalculation object.
  • The complete generated input text is available as the returned object's .input_file string attribute.

The following names must remain importable:

from ccinput.wrapper import generate_input
from ccinput.packages.gaussian import GaussianCalculation
from ccinput.packages.orca import OrcaCalculation
Resource parameters

Two generation parameters govern computational resources:

  • nproc: the integer number of processors or cores.
  • mem: a complete memory value string, such as "10000MB".

These parameters must affect only the resource directives described below. They must not otherwise alter route keywords, methods, basis sets, charge and multiplicity, geometry, solvation settings, custom basis sections, constraints, scans, NEB options, population or orbital blocks, or other existing generated content.

Gaussian Resource Header

When nproc and mem are supplied for Gaussian generation, .input_file must begin with the following three Link 0 directives, in exactly this order and before the #p route line:

%chk=in.chk
%nproc=<nproc>
%mem=<mem>

The checkpoint name is fixed as in.chk. The processor and memory values reflect the supplied values. In particular, mem is already the complete value and must be rendered verbatim; an additional unit suffix must not be appended.

For example, nproc=8 and mem="10000MB" produce these first four lines:

%chk=in.chk
%nproc=8
%mem=10000MB
#p ...

The remainder of the Gaussian input retains its existing form, including the #p route section, the CalcUS title, charge and multiplicity, geometry, and any trailing sections. This resource header applies across the supported Gaussian calculation and theory types.

ORCA Processor Block

ORCA processor rendering is theory-dependent. Every generated ORCA input retains its %pal block in this form:

%pal
nprocs <N>
end

The value of <N> is determined as follows:

  • For the Semi-empirical theory level, <N> is always 1, regardless of the supplied nproc. Thus nproc=8 still produces nprocs 1.
  • For every other ORCA theory level or calculation mode, <N> is the supplied nproc value. This includes HF, DFT, RI-MP2, minimum-energy-path/NEB, MO, and other non-semi-empirical generation. Thus nproc=8 produces nprocs 8.

mem does not add or alter an ORCA directive. Apart from the processor selection above, resource parameters must leave all existing ORCA content unchanged, including the ! keyword line, geometry, solvation blocks, basis blocks, constraint and scan blocks, NEB blocks, population-analysis settings, and orbital-output settings.

Shared Input Utility

Provide the importable module ccinput.tests.testing_utilities containing:

from unittest import TestCase

class InputTests(TestCase):
    ...

InputTests must provide the following instance methods.

generate_input(self, **params)

Resolve params["in_file"] relative to a structures directory alongside the utility module: join the directory containing that module, "structures/", and the supplied in_file value. Replace the parameter with that resolved path, call ccinput.wrapper.generate_input(**params), and return its result unchanged. Consequently, this method also returns the generated calculation object with its .input_file attribute.

is_equivalent(self, ref, res)

Compare two multiline strings as follows:

  1. Strip leading and trailing whitespace from each complete string.
  2. Split each string into lines and strip each individual line.
  3. Compare the resulting line counts. If they differ, print useful diagnostic output and return False.
  4. Compare corresponding lines in order. Equal strings match directly. If two lines differ, accept them only when xyz_line_equivalent(line1, line2) returns True.
  5. On any non-equivalent line, print useful diagnostics and return False; otherwise return True.

All normalized lines are significant, including Gaussian Link 0 directives and ORCA %pal content. The comparison must not discard either input's prefix before a route or keyword line.

xyz_line_equivalent(self, line1, line2)

Treat two lines as equivalent atomic-coordinate lines only when all of the following hold:

  • Splitting each line on whitespace yields exactly four tokens.
  • The first token, the atom label, is identical in both lines.
  • Each of the remaining three tokens can be parsed as a float.
  • For each corresponding coordinate, the absolute difference is at most 1e-7.

Return False if any condition fails; otherwise return True.

Validation and Compatibility

Existing invalid-input behavior must be preserved. In particular, generation must raise an error rather than produce valid input for applicable cases including:

  • an unsupported or invalid solvation model;
  • a missing or invalid constraint/optimization modifier for constrained optimization;
  • a calculation requiring a method when no method is supplied; and
  • an invalid route or keyword specification, such as malformed parenthesis syntax.

These failures are independent of the values of nproc and mem. All behavior not explicitly changed by the resource requirements above remains unchanged.

Task Specification: Gaussian Input File Route Line Generation

Overview

You are modifying the Gaussian input file generation logic in the ccinput package. The changes affect how the route line (the #p ... command line) is formatted, specifically the ordering of calculation keywords, the formatting of multi-argument specifications, and the syntax used for certain specification keywords.

Public API

The functionality is exercised through the calculation generation entry point that produces a Gaussian input. A calculation is generated from a dictionary of parameters, producing an object that exposes:

  • input_file — a string containing the full generated Gaussian input file.
  • confirmed_specifications — a string containing the specifications that were applied to the route line.

The parameters passed include keys such as: nproc, mem, type, file, software ('Gaussian'), method, charge, and specifications.

Required Behavior

1. Formatting of multi-argument specifications

When a specification keyword takes multiple comma-separated arguments inside parentheses, the arguments must be separated by a comma followed by a single space.

For example, a specification that yields scf with arguments tight and xqc must be rendered on the route line as:

scf(tight, xqc)

The confirmed_specifications value must reflect this same formatting (e.g. scf(tight, xqc)).

2. Ordering of calculation-type keywords in the route line

For an optimization + frequency calculation (parameter type set to 'opt+freq'), the calculation keywords must appear in the order freq before opt on the route line, followed by the method.

For example, an opt+freq AM1 calculation with no additional specifications must produce a route line of:

#p freq opt AM1
3. Handling freq specifications with opt+freq calculations

When an opt+freq calculation (type = 'opt+freq') is combined with a specification that itself concerns the frequency keyword (e.g. specifications = 'freq(noraman)'), the resulting route line must merge them so that the frequency keyword appears exactly once, carrying its argument, and must be ordered with opt first, then the specified freq, then the method.

For example, an opt+freq AM1 calculation with specifications = 'freq(noraman)' and charge = -1 must produce a route line of:

#p opt freq(noraman) AM1

(Note: this must not produce a duplicate bare freq keyword in addition to the specified freq(noraman).)

4. EmpiricalDispersion specification syntax

The empirical dispersion specification must be rendered using parenthesis syntax, not = syntax.

For example:

  • A dispersion value of GD3 must render as EmpiricalDispersion(GD3).
  • A dispersion value of GD3BJ must render as EmpiricalDispersion(GD3BJ).

These appear on the route line after the method/basis set, e.g.:

#p sp M062X/3-21G EmpiricalDispersion(GD3)
#p sp PBE1PBE/3-21G EmpiricalDispersion(GD3BJ)

The generated input file continues to follow the existing overall structure, for example:

<charge> <multiplicity>

Only the route-line formatting and keyword-ordering behaviors described above change. All other aspects of the input file (header lines, title, charge/multiplicity, geometry block) remain as they currently are.

Task: Custom Solvation Radii Ordering and SMD18 Clash Resolution

Overview

The input-file generation logic for computational chemistry calculations must correctly handle custom solvation radii together with the SMD18 radii set, for both the Gaussian and ORCA backends. This task concerns how custom per-element radii are ordered in the output and how conflicts with the built-in SMD18 radii are resolved.

Background Context

Calculations are generated through the existing calculation-generation entry point, which accepts a dictionary of parameters. The relevant parameters for this task include:

  • custom_solvation_radii: a string specifying per-element radius overrides. The format is Element=Value pairs. Multiple pairs are separated by ;. A trailing ; may be present and must be tolerated. Example values: "I=3.00", "I=3.00;".
  • solvation_radii: may be set to "SMD18", selecting the built-in SMD18 radii set. The SMD18 set assigns a radius to bromine (Br) of 2.60 and to iodine (I) of 2.74.
  • solvation_model: e.g. "SMD".
  • solvent: e.g. "Chloroform".

Required Behavior

1. Ordering of custom radii

When custom solvation radii are combined with the SMD18 radii set, the emitted radii must be ordered so that custom (user-specified) radii appear first, followed by the remaining SMD18 radii. This applies to both backends.

Concretely, when custom_solvation_radii supplies radii for one or more elements and solvation_radii is SMD18, the resulting list of radius entries must list the user-provided element(s) before the SMD18-provided element(s).

2. SMD18 clash resolution

The SMD18 set defines radii for Br (2.60) and I (2.74). If a custom radius is provided for an element that SMD18 also defines (i.e. Br or I), the custom value overrides the SMD18 value for that element, and that element must appear only once in the output (using the custom value). The overridden SMD18 default value must not additionally appear.

For example, providing custom_solvation_radii: "I=3.00" together with solvation_radii: "SMD18" must yield:

  • iodine with radius 3.00 (the custom value, listed first), and
  • bromine with radius 2.60 (the remaining SMD18 default),

with iodine appearing exactly once.

3. Backend-specific output formats

Gaussian: Radii are emitted in a modifysph block. Each entry is on its own line as <ElementSymbol> <value> where the value is formatted exactly as provided (e.g. I 3.00, Br 2.60). Custom entries come first, then remaining SMD18 entries.

Example output block for the clash case above (I=3.00 + SMD18):

modifysph

I 3.00
Br 2.60

For the non-clash case where custom radii do not overlap SMD18 (e.g. a custom Cl=1.00 with SMD18 providing Br and I), the ordering is custom first then SMD18:

modifysph

Cl 1.00
Br 2.60
I 2.74

ORCA: Radii are emitted inside the %cpcm block, each as radius[<Z>] <value> where <Z> is the element's atomic number. Custom entries come first, then remaining SMD18 entries. Relevant atomic numbers: Cl = 17, Br = 35, I = 53.

Example output for the clash case (I=3.00 + SMD18):

%cpcm
smd true
SMDsolvent "chloroform"
radius[53] 3.00
radius[35] 2.60
end

For the non-clash case (Cl=1.00 + SMD18):

%cpcm
smd true
SMDsolvent "chloroform"
radius[17] 1.00
radius[53] 2.74
radius[35] 2.60
end

Note the ordering: custom entry first, then the SMD18 entries in their SMD18 order (I / 53 before Br / 35).

Public API

Calculations continue to be created via the existing generation interface used elsewhere in the project (the same entry point that accepts the parameter dictionary described above and returns an object exposing the generated text via an input_file attribute). No new public function names are introduced by this task; the change is confined to how the custom_solvation_radii and SMD18 radii are merged, ordered, and rendered for the Gaussian and ORCA backends.

Edge Cases to Handle

  • A trailing ; in custom_solvation_radii must be accepted and produce no empty/extra entry.
  • When a custom element matches an SMD18-defined element, only the custom value is emitted for that element (no duplicate).
  • Custom radii values are rendered verbatim as given in the input string (e.g. 3.00, 1.00).
