01 ORCA input-file generation is to be added to ccinput and integrated with the existing input-generation entry point. 2209 words · rewritten by GPT-5.6-sol, reworded by GLM-5.3-Flash

Goal

ORCA input-file generation is to be added to ccinput and integrated with the existing input-generation entry point. When a request's software parameter is ORCA, that request must produce correctly formatted ORCA input; existing Gaussian generation must remain compatible, apart from the shared specification-string sanitization explicitly defined below.

Public API

ccinput.packages.orca

An importable class named OrcaCalculation must be provided. For an ORCA request, the returned calculation object must expose the complete generated input as a string attribute named input_file.

ccinput.wrapper.generate_input

For an ORCA request, the existing generate_input(**params) function must route the request to OrcaCalculation and return the resulting calculation object. Gaussian requests must continue to be routed to ccinput.packages.gaussian.GaussianCalculation.

The ORCA behavior described in this specification applies when params['software'] == 'ORCA'.

Input Parameters

Unless otherwise noted, values are strings.

  • type: the calculation type, which is mapped to an ORCA keyword as described below.
  • in_file: path to an .xyz geometry file; the atom records are read from it.
  • software: ORCA.
  • theory_level: one of Semi-empirical, HF, DFT, or RI-MP2.
  • method: the computational method, for example AM1, B3LYP, or M06-2X. It is not used for HF or RI-MP2.
  • basis_set: the basis-set name, for example 3-21G, Def2-SVP, 6-31+G(d,p), or cc-pVTZ. It is not used for semi-empirical calculations.
  • charge: the molecular charge, for example -1, 0, or +1.
  • solvent: the solvent name; optional.
  • solvation_model: optional; the supported values are SMD and CPCM.
  • solvation_radii: optional radius set, including SMD18.
  • specifications: an optional additional-keyword string.
  • constraints: a semicolon-separated constraint string for constrained optimisations.
  • custom_basis_sets: an optional semicolon-separated per-element basis specification.

The integer in the %pal block may be determined by the existing processor-count input. For all scenarios covered by this specification, the multiplicity is 1.

Shared Sanitization of specifications

For both Gaussian and ORCA calculations, sanitize the entire specifications string before any backend-specific lowercasing, parenthesis validation, tokenization, deduplication, grouping, or special-token handling.

The only permitted characters are:

  • ASCII letters A-Z and a-z;
  • digits 0-9;
  • /, (, ), =, -, ,, and .; and
  • the literal space character.

Every character outside this set must be removed rather than causing an error. Processing then continues with the sanitized string. After this filtering, any token that is empty must be silently discarded. Such a token must not contribute to the generated command or route line, to any additional-command collection, or to any exposed confirmed_specifications value.

As an example, specifications='!#' sanitizes to an empty string. In a Gaussian geometrical optimisation whose route line would otherwise be #p opt M062X/Def2SVP, the route line must remain exactly that, with no extra specification token. Likewise, the ignored characters must be absent from the returned object's specification-related state. Before ORCA specification processing, the same filtering rule applies.

Syntax that is allowed but malformed remains subject to the backend's existing validation; for example, unmatched allowed parentheses in a Gaussian specification still raise an exception.

Structure and Formatting of the ORCA Output

The sections appear in this exact order:

  1. the command line, beginning with !;
  2. the *xyz geometry block;
  3. an optional %geom block for a constrained optimisation;
  4. an optional %basis block for applicable custom basis sets;
  5. an optional %output block for Hirshfeld population output;
  6. the %pal block, which is always present;
  7. an optional trailing %cpcm block for SMD solvation.

input_file must contain no blank lines between sections or within blocks, apart from the two explicitly required separator blank lines in an ECP-bearing %basis block. It must have no leading or trailing blank lines and must not end in a newline; the final character belongs to the final line, which is normally an end line.

On individual non-geometry lines, leading and trailing whitespace is not semantically significant. Internal spacing is significant, particularly in geometry records and basis/ECP data. The exact numeric value on the nprocs line may vary, but both the line itself and the block shape are mandatory.

Command line

The first token after ! is chosen based on type:

type ORCA keyword
Single-Point Energy SP
Geometrical Optimisation OPT
Frequency Calculation FREQ
Constrained Optimisation OPT
NMR Prediction NMR
TS Optimisation OPTTS

The method and basis tokens are appended as follows:

  • For Semi-empirical, append method unchanged, such as AM1.
  • For HF, append HF, followed by basis_set.
  • For DFT, append the normalized method, followed by basis_set. In particular, M06-2X becomes M062X, whereas B3LYP remains B3LYP.
  • For RI-MP2, append RI-MP2, followed by basis_set; the method parameter is not used.

The following command lines are representative:

!SP AM1
!SP HF 3-21G
!SP M062X Def2-SVP
!OPT B3LYP 6-31+G(d,p)
!SP RI-MP2 cc-pVTZ
!OPTTS B3LYP 6-31+G(d,p)

After these method/basis tokens, CPCM and ordinary specification tokens are appended as described below.

Specification tokens for ORCA

The shared sanitization is applied first. The remaining specification text is then split into space-separated tokens; the tokens are lowercased, first-occurrence order is preserved, and case-insensitive duplicates are suppressed.

Ordinary tokens are appended to the ! command line. Examples:

  • TightSCF results in !SP M062X Def2-SVP tightscf.
  • TightSCF GRID6 results in !SP M062X Def2-SVP tightscf grid6.
  • tightscf TightSCF GRID6 results in the same tightscf grid6 suffix, appearing only once.
  • For RI-MP2, cc-pVTZ/C is kept as the lowercased auxiliary-basis token cc-pvtz/c, giving !SP RI-MP2 cc-pVTZ cc-pvtz/c.

The token phirshfeld, which is matched case-insensitively after sanitization, is consumed rather than being placed on the command line. It is what creates the %output block described below, and it must appear nowhere else in the generated input.

Geometry block

Following the command line, emit:

*xyz <charge> <multiplicity>
<atom records>
*

The .xyz atom records — the lines following the atom-count and comment lines — must appear in source-file order. Both single-atom and multi-atom files must be supported, including lone chlorine or iodine anions, ethanol, ammonia-like transition-state structures, and diaryliodonium cations. Each atom line must be reproduced character-for-character, except that leading and trailing whitespace may be removed; the internal spacing between the element symbol and the coordinates must not be normalized.

charge is rendered as a plain integer: +1 becomes 1, while -1 and 0 remain -1 and 0. For the behavior covered here, the multiplicity is 1:

*xyz 1 1
*xyz -1 1
*xyz 0 1

Constrained Optimisations

When type='Constrained Optimisation', the command keyword is OPT, and a %geom block is placed immediately after the geometry. constraints holds one or more semicolon-separated definitions. Empty segments — for instance, the segment after a trailing semicolon — do not create constraints.

Atom indices in the input constraint string are one-based, whereas ORCA output indices are zero-based. With two, three, and four listed atoms, the letters B (bond), A (angle), and D (dihedral) are used, respectively. For angles, the required second-, first-, third-atom ordering represented by the input must be preserved; for example, /2_1_3 must become A 1 0 2 after zero-based conversion. Scans and freezes are subject to the same letter and ordering rules.

Scan constraints

A scan takes the form:

Scan_<begin>_<end>_<steps>/<atoms>

and produces:

%geom Scan
<letter> <zero-based atoms> = <begin>, <end>, <steps>
end
end

Examples:

  • Scan_9_1.4_10/1_2; results in B 0 1 = 9, 1.4, 10.
  • Scan_9_90_10/2_1_3; results in A 1 0 2 = 9, 90, 10.
  • Scan_9_0_10/4_1_5_8; results in D 3 0 4 7 = 9, 0, 10.

As an example, the complete bond-scan block is:

%geom Scan
B 0 1 = 9, 1.4, 10
end
end
Freeze constraints

A freeze takes the form:

Freeze/<atoms>

and produces:

%geom Constraints
{ <letter> <zero-based atoms> C }
end
end

Examples:

  • Freeze/1_2; results in { B 0 1 C }.
  • Freeze/2_1_3; results in { A 1 0 2 C }.
  • Freeze/4_1_5_8; results in { D 3 0 4 7 C }.

If a constrained optimisation has an empty constraints value or no valid constraint, a Python exception must be raised. An empty method that is required must also raise a Python exception.

Custom Basis Sets

custom_basis_sets takes the form:

<Element>=<BasisSet>;<Element>=<BasisSet>;

A %basis block is emitted only when at least one requested element occurs in the geometry. Requests for elements that are absent are silently irrelevant; for instance, N=Def2-SVP; results in no %basis block for a molecule without nitrogen.

All applicable element definitions are combined into one block:

%basis
newgto <Element>
<ORCA shell data>
end
newgto <Element2>
<ORCA shell data>
end
end

Each newgto group uses the standard published Basis Set Exchange ORCA-format data for the requested basis, omitting the export wrapper/header. The shell headers, the primitive numbering, the exponents, the contraction coefficients, the scientific-notation style, and the internal column alignment must all be reproduced exactly. Every group ends with end, and the final end closes %basis.

The required structural details include:

  • Nitrogen Def2-SVP, in order: one five-primitive S shell, two one-primitive S shells, one three-primitive P shell, one one-primitive P shell, and one one-primitive D shell. Shell headers have the form <L> <count>, and primitive rows are numbered from 1.
  • Iodine Def2-TZVPD, in order: S shells with 5, 2, 1, 1, 1, 1, 1 primitives; P shells with 3, 4, 1, 1, 1, 1 primitives; D shells with 6, 1, 1, 1 primitives; and F shells with 1, 1 primitives.

When no ECP applies — as with nitrogen Def2-SVP — the newgto ... end group is followed immediately by the %basis closing end, with no blank separator.

Effective core potentials

If the selected custom basis includes an ECP, emit its standard ORCA NewECP group inside %basis, after the corresponding newgto group.

For iodine Def2-TZVPD, the layout is:

... end of newgto group

NewECP I
N_core 28
lmax f
s 7
<7 standard rows>
p 8
<8 standard rows>
d 10
<10 standard rows>
f 4
<4 standard rows>
end

end

Exactly one blank line must separate the newgto group's end from NewECP I, and exactly one blank line must separate the ECP group's end from the %basis closing end. These blank lines are the only ones permitted in an ORCA result.

The potential tables appear in s, p, d, f order and contain their standard def2-ECP values and alignment. Every table row contains a one-based row number, an exponent, a coefficient, and a terminal power of 2; the four f coefficients are negative. The complete numeric text of the basis and ECP must match the standard published definitions exactly.

Parallelization block

A %pal block is always present and is made up of exactly three lines:

%pal
nprocs <N>
end

<N> must be an integer. This task does not otherwise constrain its particular value.

Hirshfeld Population Output

When the sanitized specifications contains phirshfeld, emit this exact block after any %geom and %basis blocks but before %pal:

%output
Print[ P_Hirshfeld] 1
end

The internal spacing and capitalization in Print[ P_Hirshfeld] 1 are significant. The triggering token is consumed in full and is not appended to the ! line.

Solvation

When the solvation model is absent, neither a solvation keyword nor a block appears. If solvent treatment is requested with a nonempty solvation_model other than SMD or CPCM, a Python exception must be raised.

CPCM

With solvation_model='CPCM', append the following token to the command line, after the method/basis tokens and other applicable command tokens:

CPCM(<canonical-solvent>)

For CPCM, no %cpcm block is emitted. For example:

!SP HF 3-21G CPCM(chloroform)
SMD

With solvation_model='SMD', no solvation token is added to the command line. Emit the following final block after %pal:

%cpcm
smd true
SMDsolvent "<canonical-solvent>"
end

With solvation_radii='SMD18', supported radius overrides are inserted immediately before this block's end. The available radius lines are iodine, radius[53] 2.74, and bromine, radius[35] 2.60. A bromine-only geometry emits its bromine line. A geometry containing iodine must emit both lines below, in exactly this order, even if no bromine atom is present:

radius[53] 2.74
radius[35] 2.60
Solvent canonicalization

Solvent names are canonicalized case-insensitively, including these synonyms and ORCA model-specific names:

Input SMD output CPCM output
Chloroform or CHCL3 SMDsolvent "chloroform" CPCM(chloroform)
octanol or 1-octanol SMDsolvent "1-octanol" CPCM(octanol)

Error Conditions

For each of the following, generate_input must raise a Python exception; any exception class is acceptable:

  • a supplied solvation-model value that is unsupported, such as ABC;
  • a constrained optimisation with an empty constraints string or with no valid constraint;
  • an empty method in a case where the selected theory level/calculation requires a method.

Gaussian Compatibility

ORCA routing must not change existing Gaussian input generation, object behavior, route construction, constraints, solvation, custom basis/ECP output, or other previously supported features. The only cross-backend adjustment required is the shared specifications sanitization above.

In particular, characters disallowed in a Gaussian specification must never be copied into input_file, command/additional specification state, or confirmed_specifications. Tokens that remain valid after sanitization continue through the existing Gaussian behavior, which includes lowercasing, duplicate suppression, command-specific grouping, and rejection of unmatched parentheses.

Task Specification: Generating ORCA Input Files

Goal

ORCA input generation for Minimum Energy Path (NEB), molecular-orbital (MO), and Hirshfeld-population requests must be implemented and maintained, while existing input-generation behavior is preserved for all other calculation types.

Public API and the inputs

The behavior must be exposed through the existing ccinput.wrapper.generate_input(...) entry point. Callers may provide a parameter dictionary via keyword arguments, including type, in_file, auxiliary_file, software, theory_level, method, basis_set, charge, multiplicity, and specifications. Through its input_file attribute, the returned calculation object exposes the complete generated text.

software values that identify ORCA are case-insensitive; both ORCA and orca must select ORCA generation. The primary XYZ structure is taken from in_file. The atom-count and comment lines of that file are not part of the ORCA coordinate body. If charge is not supplied, it is 0; if multiplicity is not supplied, it is 1.

1. The Minimum Energy Path (NEB) calculation type

If a request has type equal to Minimum Energy Path and ORCA as the software, an ORCA NEB input must be generated.

The command line

The very first line must be exactly:

!NEB

That line is the complete NEB command line. method, basis_set, or the --nimages option must not be appended to it. method, basis_set, and theory_level are not required for this calculation type; should method or basis-set values be supplied, they must not alter the !NEB line.

Coordinates and the endpoint

The primary structure is serialized using the standard ORCA coordinate section:

*xyz <charge> <multiplicity>
<primary atom-coordinate lines>
*

The product/end structure is provided via auxiliary_file. Within the generated input, that structure is referenced under the fixed name struct2.xyz, no matter what the source file's original name is.

Emit the following immediately after the primary coordinate section:

%neb
product "struct2.xyz"
nimages <N>
end

For the endpoint, the keyword must be product; do not use an alternative endpoint keyword.

Count of images

The specifications string may hold the command-line-style option:

--nimages <N>

N is an integer and is used as the value on the nimages line. During parsing, the option and its argument are consumed and must not be serialized onto the !NEB line. If specifications is omitted, empty, or has no --nimages option, use the default:

nimages 8

As an example, specifications="--nimages 12" results in nimages 12.

A complete NEB layout therefore looks as follows:

!NEB
*xyz <charge> <multiplicity>
<primary atom-coordinate lines>
*
%neb
product "struct2.xyz"
nimages <N>
end
%pal
nprocs 8
end

2. The MO calculation type

For ORCA, type="MO Calculation" must be supported. This type is serialized as a single-point command followed by a cube-plot request.

When theory_level="DFT", method="B3LYP", and basis_set="def2tzvp" are given, the basis-set name is normalized and this exact header is emitted:

!SP B3LYP Def2-TZVP

The coordinate section is the standard ORCA section constructed from the primary structure:

*xyz <charge> <multiplicity>
<atom-coordinate lines>
*

Hence, with a charge value of "+1" and singlet multiplicity, the result is *xyz 1 1.

Orbital index values

Orbital numbering starts at zero. For a supported singlet request, the electron count is determined from the atoms and the molecular charge:

E = sum(atomic numbers of all atoms) - charge

Let O = floor(E / 2). The plot indices to use are the following:

  • HOMO index: O - 1
  • LUMO index: O
  • LUMOA index: O + 1
  • LUMOB index: O + 2

Equivalently, the latter three indices result from adding one, two, and three to the HOMO index. For the specified Ph2I_cation structure with charge +1, the resulting indices are 66, 67, 68, and 69.

The plot block

After the coordinate section, emit the block below exactly, with the computed indices substituted:

%plots
dim1 45
dim2 45
dim3 45
min1 0
max1 0
min2 0
max2 0
min3 0
max3 0
Format Gaussian_Cube
MO("in-HOMO.cube",<homo_index>,0);
MO("in-LUMO.cube",<lumo_index>,0);
MO("in-LUMOA.cube",<lumoa_index>,0);
MO("in-LUMOB.cube",<lumob_index>,0);
end

The filenames, capitalization, punctuation, dimensions, bounds, and Gaussian_Cube format must be as shown.

Between the end that closes %plots and the %pal line after it, there must be exactly one blank line. The tail of an MO input therefore takes this form:

MO("in-LUMOB.cube",<lumob_index>,0);
end

%pal
nprocs 8
end

3. Parsing of specifications and Hirshfeld output

A specification flag written in command-line style is identified by the -- prefix at its start. In particular, --nimages <N> and --phirshfeld must be recognized as control options and consumed rather than copied onto the ORCA command line.

If specifications contains --phirshfeld, the normal command line must be left unchanged, and this exact block must be inserted after the closing * of the coordinate section and before %pal:

%output
Print[ P_Hirshfeld] 1
end

For example, a DFT single-point request with M06-2X and Def2-SVP must retain:

!SP M062X Def2-SVP

It must not turn into !SP M062X Def2-SVP phirshfeld and must not include --phirshfeld. The relevant block order is:

!SP M062X Def2-SVP
*xyz <charge> <multiplicity>
<atom-coordinate lines>
*
%output
Print[ P_Hirshfeld] 1
end
%pal
nprocs 8
end

Ordinary existing ORCA specification tokens remain supported: a token that is not one of these special consumed controls continues to be emitted as a command-line keyword, with the existing normalization and de-duplication behavior applied. For example, TightSCF GRID6 yields tightscf grid6, and repeated equivalent tokens appear only once, in first-occurrence order.

4. Structure and ordering shared by ORCA outputs

All calculation types covered above must include:

%pal
nprocs 8
end

The required order is the following:

  1. The ORCA ! command line.
  2. The *xyz coordinate section.
  3. The calculation-specific blocks (%neb, %plots, or %output, as applicable).
  4. The %pal block.

The content of each line and the order of the blocks are significant. Apart from the mandatory single blank line between %plots and %pal in an MO calculation, indentation and other blank-line differences between blocks are not significant.

Scope and compatibility

Established behavior for Gaussian generation, other ORCA calculation types, ordinary ORCA command-line specifications, coordinate serialization, method/basis normalization, charge or multiplicity handling, custom basis sets, constraints, or solvation must not be changed. The additions this specification makes are limited to dispatching and serializing the ORCA NEB and MO calculation types and to correctly consuming the two special double-dash controls described above.

Task Specification: Input Generation for Computational Chemistry

Overview

ccinput is a Python package that produces input files for Gaussian and ORCA. Implement the resource-parameter behavior described below while keeping all existing calculation generation, formatting, compatibility, and validation behavior intact. In addition, supply the shared input-comparison utility that this specification describes.

Public API

ccinput.wrapper.generate_input

ccinput.wrapper.generate_input(**params) stays the public generation entry point. It accepts the generation parameters that already exist, including (but not limited to) type, in_file, xyz, software, theory_level, method, basis_set, charge, multiplicity, solvent, solvation_model, solvation_radii, specifications, density_fit, custom_basis_sets, constraints, auxiliary_file, nproc, and mem.

When generation succeeds, the function returns the generated calculation object rather than the input text as a bare string:

  • For Gaussian, generation returns a ccinput.packages.gaussian.GaussianCalculation object.
  • For ORCA, generation returns a ccinput.packages.orca.OrcaCalculation object.
  • The complete generated input text is available as the .input_file string attribute of the returned object.

The following names must stay importable:

from ccinput.wrapper import generate_input
from ccinput.packages.gaussian import GaussianCalculation
from ccinput.packages.orca import OrcaCalculation
The resource parameters

Two generation parameters control computational resources:

  • nproc: the number of processors or cores, given as an integer.
  • mem: a memory value string that is complete, such as "10000MB".

These parameters must affect only the resource directives described below. Beyond that, they must not alter route keywords, methods, basis sets, charge and multiplicity, geometry, solvation settings, custom basis sections, constraints, scans, NEB options, population or orbital blocks, or other existing generated content.

Resource Header for Gaussian

When nproc and mem are supplied for Gaussian generation, .input_file must start with the following three Link 0 directives, in exactly this order and before the #p route line:

%chk=in.chk
%nproc=<nproc>
%mem=<mem>

in.chk is the fixed checkpoint name. The processor and memory values mirror the values supplied. In particular, mem is already the complete value, and it must be rendered verbatim; an additional unit suffix must not be appended.

For instance, supplying nproc=8 and mem="10000MB" produces these first four lines:

%chk=in.chk
%nproc=8
%mem=10000MB
#p ...

The rest of the Gaussian input keeps its existing form, including the #p route section, the CalcUS title, charge and multiplicity, geometry, and any trailing sections. This resource header applies to every supported Gaussian calculation and theory type.

Processor Block for ORCA

How ORCA renders the processor block depends on the theory. Every generated ORCA input keeps its %pal block in this form:

%pal
nprocs <N>
end

The value of <N> is determined in the following way:

  • At the Semi-empirical theory level, <N> is always 1, no matter what nproc was supplied. So nproc=8 still produces nprocs 1.
  • For every other ORCA theory level or calculation mode, <N> is the value supplied for nproc. HF, DFT, RI-MP2, minimum-energy-path/NEB, MO, and other non-semi-empirical generation fall under this case. So nproc=8 produces nprocs 8.

mem does not add or change any ORCA directive. Aside from the processor selection above, resource parameters must leave all existing ORCA content unchanged, including the ! keyword line, geometry, solvation blocks, basis blocks, constraint and scan blocks, NEB blocks, population-analysis settings, and orbital-output settings.

Shared Input Utility

Supply the importable module ccinput.tests.testing_utilities, which contains:

from unittest import TestCase

class InputTests(TestCase):
    ...

InputTests must make the following instance methods available.

generate_input(self, **params)

Resolve params["in_file"] relative to a structures directory located next to the utility module: the join combines the directory containing that module, "structures/", and the supplied in_file value. Set the parameter to that resolved path, call ccinput.wrapper.generate_input(**params), and return its result unchanged. As a result, this method also returns the generated calculation object together with its .input_file attribute.

is_equivalent(self, ref, res)

Compare two multiline strings in the following way:

  1. Strip whitespace from the start and the end of each complete string.
  2. Split each string up into lines, then strip each individual line.
  3. Compare the resulting line counts; if they differ, print useful diagnostic output and return False.
  4. Walk through corresponding lines in order, comparing them. Strings that are equal match directly. If two lines differ, accept them only when xyz_line_equivalent(line1, line2) returns True.
  5. If any line is non-equivalent, print useful diagnostics and return False; otherwise return True.

Every normalized line is significant, including Gaussian Link 0 directives and ORCA %pal content. The comparison must not drop either input's prefix before a route or keyword line.

xyz_line_equivalent(self, line1, line2)

Two lines are to be treated as equivalent atomic-coordinate lines only when all of the following hold:

  • When each line is split on whitespace, it yields exactly four tokens.
  • The first token, which is the atom label, is identical in both lines.
  • The remaining three tokens can each be parsed as a float.
  • For every corresponding coordinate, the absolute difference is at most 1e-7.

If any condition fails, return False; otherwise return True.

Validation and Compatibility

The existing handling of invalid input must be preserved. In particular, generation must raise an error instead of producing valid input for the applicable cases, including:

  • a solvation model that is unsupported or invalid;
  • a constraint/optimization modifier for constrained optimization that is missing or invalid;
  • a calculation that requires a method when no method is supplied; and
  • a route or keyword specification that is invalid, such as malformed parenthesis syntax.

These failures do not depend on the values of nproc and mem. All behavior that the resource requirements above do not explicitly change remains unchanged.

Task: Validation of Calculation constructor parameters

The following public API is to be implemented:

  • ccinput.calculation.Parameters
  • ccinput.calculation.Calculation
  • ccinput.constants.CalcType, including CalcType.SP
  • ccinput.exceptions.InvalidParameter

API for construction

Task: Support per-element, user-defined custom solvation radii

Summary

Introduce a new calculation parameter, custom_solvation_radii, which allows a user to override the solvation cavity radius for specific chemical elements. This parameter must be honored when input files are generated for both the Gaussian and ORCA backends, across the SMD, PCM, and CPCM solvation models.

The parameter is accepted by the same calculation-generation entry point that is already used to build input files (the function that is invoked with a keyword-argument dictionary containing keys such as nproc, mem, type, file, software, method, basis_set, charge, solvent, solvation_model, solvation_radii, etc.). custom_solvation_radii is to be added as an additional optional keyword parameter, one that flows through to input-file generation for Gaussian and ORCA.

Input format for custom_solvation_radii

The value is a string that encodes one or more element→radius assignments:

  • Each assignment takes the form <ElementSymbol>=<radius>.
  • Semicolons (;) separate multiple assignments.
  • A trailing semicolon may appear and must be tolerated (ignored).

The following are examples of valid values:

  • "Cl=1.00"
  • "Cl=1.00;Br=2.00;"
  • "Cl=1.00;C=2.00;"

Element symbols are standard symbols from the periodic table (e.g. Cl, Br, I, C). The radius is a numeric value; when it is emitted, it must have two decimal places (e.g. 1.00, 2.00).

For user-supplied radii, the order in which the assignments appear in the output must match the order in which they are listed in the input string.

Behavior for the Gaussian backend

When a Gaussian calculation is given custom_solvation_radii, the solvation directive in the route line must request that custom radii be read, by appending , Read inside the SCRF(...) block, e.g.:

#p sp HF/3-21G SCRF(SMD, Solvent=chloroform, Read)

This is the case for both solvation_model = SMD and PCM.

A radii-definition block must be appended after the molecular geometry block (following the blank line that ends the coordinate section). Its structure is as follows:

  1. An optional Radii=<name> line, which is present only when a predefined built-in radii set is also selected via solvation_radii (see below).
  2. A line whose content is exactly modifysph.
  3. A blank line.
  4. For each element radius, one line, formatted as <ElementSymbol> <radius> (element symbol, a single space, radius with two decimals).
  5. A trailing blank line.
Interaction with the built-in radii sets (solvation_radii)

  • If solvation_radii is not specified (or if it specifies no built-in override that adds element entries), only the user-supplied custom radii appear, in the order given.

    For custom_solvation_radii='Cl=1.00' (SMD or PCM), the appended block is:

    
modifysph

Cl 1.00

  • If solvation_radii='SMD18' is specified together with SMD, the built-in SMD18 radii entries must be emitted first, and the user's custom entries come after them. SMD18 contributes entries for bromine and iodine:

    
modifysph

Br 2.60
I 2.74
Cl 1.00

    (The Br and I values are taken from the SMD18 set; Cl 1.00 is the user override, appearing after the built-in entries.)

  • If solvation_radii='Bondi' is specified together with PCM, the modifysph line must be preceded by a Radii=bondi line, and the only entries listed are the user's custom ones (the Bondi set is applied via the Radii=bondi keyword rather than via explicit per-element lines):

    For custom_solvation_radii='Cl=1.00':

    
Radii=bondi
modifysph

Cl 1.00

    For custom_solvation_radii='Cl=1.00;C=2.00;':

    
Radii=bondi
modifysph

Cl 1.00
C 2.00

The Radii=<name> keyword takes the lowercase form of the built-in set's name (e.g. bondi).

Behavior for the ORCA backend

When an ORCA calculation is given custom_solvation_radii, the per-element radii must be emitted within the %cpcm ... end block. The radius of each element is written using the element's atomic number as an index:

radius[<atomic_number>] <radius>

The radius is formatted to two decimals. (Atomic numbers: Cl = 17, Br = 35, I = 53.)

SMD model

For solvation_model='SMD', the %cpcm block contains the SMD activation lines followed by the radius lines:

For custom_solvation_radii='Cl=1.00;':

%cpcm
smd true
SMDsolvent "chloroform"
radius[17] 1.00
end

For custom_solvation_radii='Cl=1.00;Br=2.00;':

%cpcm
smd true
SMDsolvent "chloroform"
radius[17] 1.00
radius[35] 2.00
end

The order of the user-supplied radii is the order in which they are listed in the input string.

When solvation_radii='SMD18' is combined with SMD, the built-in SMD18 entries are emitted first (as radius[...] lines), with the user-supplied entries after them. SMD18 contributes iodine and bromine:

%cpcm
smd true
SMDsolvent "chloroform"
radius[53] 2.74
radius[35] 2.60
radius[17] 1.00
end

(radius[53] 2.74 and radius[35] 2.60 are taken from SMD18; radius[17] 1.00 is the user override, appearing after the built-in entries.)

CPCM model

For solvation_model='CPCM', the route line declares the solvent as CPCM(chloroform), and the only lines the %cpcm block contains are the radius lines:

For custom_solvation_radii='Cl=1.00;':

!SP HF 3-21G CPCM(chloroform)
...
%cpcm
radius[17] 1.00
end

For custom_solvation_radii='Cl=1.00;Br=2.00;':

%cpcm
radius[17] 1.00
radius[35] 2.00
end

Notes and edge cases

  • In the output, solvent names are normalized to their canonical lowercase form (e.g. Chloroform → chloroform), consistent with existing behavior.
  • Both user-supplied and built-in radii values are subject to the two-decimal formatting.
  • The overall structure of the remainder of the input file (header directives, geometry, charge/multiplicity, processor/memory settings, method/basis in the route line) remains unchanged from existing behavior; the only additions are the Read flag / Radii= line / modifysph block (Gaussian) and the radius[...] lines within %cpcm (ORCA).

Public API

The changes are driven entirely through the existing calculation-generation entry point, by way of the new custom_solvation_radii keyword. Aside from accepting and processing this parameter, no new public function or class names are required.

Task: Ordering of Custom Solvation Radii and SMD18 Clash Resolution

Overview

For both the Gaussian and ORCA backends, the input-file generation logic for computational chemistry calculations must handle custom solvation radii in combination with the SMD18 radii set correctly. The task at hand covers the order in which custom per-element radii are arranged in the output and the way conflicts with the built-in SMD18 radii are resolved.

Background

Calculations are produced through the existing calculation-generation entry point, which accepts a dictionary of parameters. The parameters relevant to this task include:

  • custom_solvation_radii: a string that specifies per-element radius overrides. The format is made up of Element=Value pairs; multiple pairs are separated by ;, and a trailing ; may be present and must be tolerated. Example values: "I=3.00", "I=3.00;".
  • solvation_radii: may be set to "SMD18", which selects the built-in SMD18 radii set. The SMD18 set assigns bromine (Br) a radius of 2.60 and iodine (I) a radius of 2.74.
  • solvation_model: for instance "SMD".
  • solvent: for instance "Chloroform".

Behavior Requirements

1. Ordering of the custom radii

Whenever custom solvation radii are combined with the SMD18 radii set, the emitted radii must be ordered such that custom (user-specified) radii appear first, with the remaining SMD18 radii following. This holds for both backends.

In concrete terms: if custom_solvation_radii supplies radii for one or more elements and solvation_radii is SMD18, the resulting list of radius entries must place the user-provided element(s) before the SMD18-provided element(s).

2. Resolution of SMD18 clashes

Radii for Br (2.60) and I (2.74) are defined by the SMD18 set. If a custom radius is supplied for an element that SMD18 also defines (i.e. Br or I), the custom value overrides the SMD18 value for that element, and that element must appear only once in the output (using the custom value). The SMD18 default value that has been overridden must not additionally appear.

By way of example, providing custom_solvation_radii: "I=3.00" together with solvation_radii: "SMD18" must yield:

  • iodine, with radius 3.00 (the custom value, listed first), and
  • bromine, with radius 2.60 (the remaining SMD18 default),

with iodine appearing exactly once.

3. Output formats specific to each backend

Gaussian: Radii are emitted in a modifysph block. Every entry appears on its own line, in the form <ElementSymbol> <value>, where the value is formatted exactly as provided (e.g. I 3.00, Br 2.60). Custom entries come first, followed by the remaining SMD18 entries.

The example output block for the clash case just described (I=3.00 + SMD18):

modifysph

I 3.00
Br 2.60

In the non-clash case, where the custom radii do not overlap SMD18 (e.g. a custom Cl=1.00 with SMD18 providing Br and I), the order is custom entries first, then SMD18 entries:

modifysph

Cl 1.00
Br 2.60
I 2.74

ORCA: Radii are emitted inside the %cpcm block, each one written as radius[<Z>] <value> where <Z> is the element's atomic number. Custom entries come first, followed by the remaining SMD18 entries. The relevant atomic numbers are: Cl = 17, Br = 35, I = 53.

The example output for the clash case (I=3.00 + SMD18):

%cpcm
smd true
SMDsolvent "chloroform"
radius[53] 3.00
radius[35] 2.60
end

For the non-clash case (Cl=1.00 + SMD18), the output is:

%cpcm
smd true
SMDsolvent "chloroform"
radius[17] 1.00
radius[53] 2.74
radius[35] 2.60
end

Note the ordering: the custom entry comes first, and after it the SMD18 entries follow in their SMD18 order (I / 53 before Br / 35).

Calculations are still created through the generation interface that already exists and is used elsewhere in the project (the same entry point that accepts the parameter dictionary described above and returns an object that exposes the generated text via an input_file attribute).
