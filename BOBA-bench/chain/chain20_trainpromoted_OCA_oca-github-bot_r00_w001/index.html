01 Detecting Odoo Addons Changed by a Git Diff 966 words · rewritten by GPT-5.6-sol, reworded by GLM-5.3-Flash

Task Specification: Detecting Odoo Addons Changed by a Git Diff

Goal

Addon-change detection is to be implemented or adjusted so that the bot reports which Odoo addons are affected by the Git difference between a reference supplied to it and the repository's current state as visible to Git. The detection must tell real addons at the repository root apart from ordinary Python packaging content under setup/, and the canonical addon symlink used by Odoo packaging layouts must be recognized as well.

Public Interface

It must remain possible to import the existing symbol from the manifest helper module:

from oca_github_bot.manifest import git_modified_addons

def git_modified_addons(addons_dir, ref):
    ...
  • addons_dir — a string or a path-like value — identifies the root of a Git repository or working tree.
  • ref is the Git reference the current state gets compared against; "origin/master" serves as one example.
  • What the function returns is a set holding addon directory names as strings. The names must be unique.
  • An empty set must be returned if no qualifying addon is affected.

What Counts as an Addon and as a Change

A directory counts as a real addon when it sits directly below addons_dir and contains an Odoo manifest. The manifest conventions that are supported stay __manifest__.py, __openerp__.py, and __terp__.py.

A change is relevant when it is visible in the Git comparison from ref to the current state. Revisions recorded after ref fall under this, as do tracked index or working-tree differences that the comparison represents.

What the Detection Is Required to Do

Changes inside real root-level addons

Each changed file or entry that is located below a real addon directory at the repository root must contribute that directory's name to the result. This holds at any depth inside the addon, and newly added root-level addons are covered too, as soon as a recognized manifest is present in them.

If one and the same addon has multiple changed entries, the result must still end up containing only one member for it. When several addons see changes, the result must be the union of those names.

As soon as ref and the current tree represent the same state, the changes observed earlier must no longer produce a result.

Ordinary content under setup/ does not count

At the repository root sits a setup/ directory; it is a Python packaging area, not an addon that is named setup. Its ordinary files and directories must not be interpreted as addon changes merely because an addon-like package name appears somewhere in their paths.

To be concrete: when a difference covers nothing except a path of this form:

setup/<packaging-name>/setup.py

the function must return an empty set, and this holds even when <packaging-name> is also the name of a real root-level addon. The same kind of exclusion covers other ordinary packaging files as well as subdirectories under setup/ that are not addons.

Exception for the canonical packaging symlink

The exclusion of ordinary setup/ content has one explicit exception. When a symlink has changed and sits in this canonical layout:

setup/<packaging-name>/odoo/addons/<addon>

<addon> must be added to the result if the symlink points to the real addon directory at <addons_dir>/<addon>. Being an addon-bearing packaging link, it must be recognized even when there is no file inside the real root-level addon that differs from ref.

As an illustration: take a real root addon named addon. Adding this link and recording it:

setup/addon/odoo/addons/addon -> ../../../../addon

must lead the function to return {"addon"} when measured against a reference that does not contain the link.

The changed addon-link entry itself is what sets off this exception. An unchanged canonical symlink must not, merely by being present, cause an ordinary sibling file such as setup.py to count as an addon change. The name that gets returned is the linked root addon's name — it is not setup, and it is not the name of an unrelated packaging directory either.

Changes that are unrelated

Names must not be reported for repository-root files, for directories that do not count as recognized root-level addons, or for ordinary packaging scaffolding. By way of example: if the only changes are a root README and ordinary setup/ files, an empty set is the result.

Results to Expect

Difference as measured against ref Result
There is no difference that qualifies set()
A file below the root addon addon is changed {"addon"}
A new root addon addon2 that has a recognized manifest is added {"addon2"}
The only thing added is setup/addon/setup.py set()
The canonical link setup/addon/odoo/addons/addon -> ../../../../addon is added and points to the root addon, which is unchanged {"addon"}
The root addons addon and addon2 both have qualifying changes, along with changes to unrelated root files {"addon", "addon2"}

The same rules also govern a cumulative packaging sequence: after the root addon and ref have been synchronized, recording only setup/addon/setup.py yields set(); recording the canonical symlink above afterwards yields {"addon"} against that same unchanged reference, even though the ordinary setup.py path likewise remains part of the overall difference.

Scope and Compatibility

  • The function's name, import location, parameters, and set return type have to be preserved.
  • Existing manifest recognition and manifest/version helper behavior are to be preserved; the change is confined to classifying the paths that the Git comparison reports.
  • The implementation must not treat every child directory of setup/ as an addon. The packaging-directory exclusion is overridden only by the canonical changed symlink described above.
  • Provided that all observable requirements above are met, the behavior must not depend on which specific path-handling or Git-invocation implementation is used.

For the inputs it receives, the function must be deterministic.

  • A callable named parse_commands: it lives at module level and is importable, and it can be referenced and patched as on_command.parse_commands.

on_check_suite Behavior

The event payload (event.data) looks as follows:

{
    "repository": {"full_name": "<org>/<repo>"},
    "check_suite": {
        "head_branch": "<branch name>",
        "head_sha": "<40-char sha>",
        "status": "<status>",
        "conclusion": "<conclusion>",
    },
}

Rules that govern the processing:

  1. Branch check. The handler must work out whether head_branch is a merge-bot branch — that is, a branch name with the same shape as what make_merge_bot_branch produces. If the branch turns out not to be a merge-bot branch, the handler must do nothing: no call may be made to merge_bot_status_success.delay, and none to merge_bot_status_failure.delay. (One example of a non-merge-bot branch is "changes".)

  2. Status check. Even on a valid merge-bot branch, the handler must do nothing when status is not "completed" ("in_progress" being one example) — neither of the two delay calls is made.

  3. Completed on a merge-bot branch. Whenever the branch is a merge-bot branch and status == "completed", the handler dispatches according to the value of conclusion:

    • With conclusion == "success": merge_bot_status_success.delay(org, repo, branch, sha) must be called exactly once, and merge_bot_status_failure.delay must not be called.
    • With conclusion == "failure": merge_bot_status_failure.delay(org, repo, branch, sha) must be called exactly once, and merge_bot_status_success.delay must not be called.

    As for the arguments: splitting repository.full_name on / supplies org and repo (e.g. "OCA/some-repo" → "OCA", "some-repo"); branch is head_branch; sha is head_sha.

on_command Behavior

The payload found in event.data takes this shape:

{
    "repository": {"full_name": "<org>/<repo>"},
    "issue": {"number": <pr number or None>, "pull_request": <bool>},
    "comment": {"body": "<comment text>", "user": {"login": "<username>"}},
}

Processing follows these rules:

  1. Not a pull request. In case issue.pull_request is falsy — meaning the issue is not a pull request — the handler must do nothing, and, as a particular consequence, parse_commands must not be called.

  2. Pull request comment. When the issue is a pull request, the handler must call parse_commands(body) exactly once, body being comment.body. An iterable of command objects is what parse_commands returns, and each of those objects exposes a .delay(...) method. For each command object that comes back, the handler must call command.delay(org, repo, pr_number, username) exactly once; the arguments break down as:

    • org and repo are the two parts obtained by splitting repository.full_name on /,
    • pr_number comes from issue.number,
    • username comes from comment.user.login.

General Remarks

  • Callers await the two handler functions, both of which are async.
  • When repository.full_name is split on /, the organization and repository name come out as two separate string arguments.
  • The task objects (merge_bot_status_success, merge_bot_status_failure), together with parse_commands, must be module-level names imported/referenced inside their respective handler modules, so that they can be monkeypatched at those attribute paths.

Task Description

Overview

Update the merge-bot branch naming utilities such that branch names contain the pull request number, the target version, and the username of the person who triggered the merge. To achieve this, the branch name format has to be changed and the associated helper functions updated accordingly.

Module & Public API

All of the functions reside in a module that can be imported as test_version_branch's subject (that is, the version/branch utilities module used elsewhere in the codebase). The functions listed below must be updated:

is_merge_bot_branch(branch_name: str) -> bool

Returns True when the supplied branch name matches the merge-bot branch naming format, and False otherwise.

A merge-bot branch has the format:

ocabot-merge-pr-<PR>-to-<VERSION>-by-<USER>

where:

  • <PR> stands for a numeric pull request identifier (digits only).
  • <VERSION> stands for a version string of the form <major>.<minor> (e.g. 12.0).
  • <USER> stands for a username string.

Behavior:

  • A name such as ocabot-merge-pr-100-to-12.0-by-toto is a valid merge-bot branch → returns True.
  • The PR portion must be numeric; a PR portion that is not numeric (e.g. a100) is not valid → returns False.
  • The version portion must be a valid <major>.<minor> version; a non-version value placed there (e.g. the literal something) is not valid → returns False.
  • A name that does not start with the exact literal prefix ocabot-merge-pr- (e.g. one starting with cabot-merge-pr-) is not valid → returns False.
make_merge_bot_branch(pr: str, version: str, username: str) -> str

Builds a merge-bot branch name from the supplied PR number, version, and username, and returns it; the output is exactly:

ocabot-merge-pr-<pr>-to-<version>-by-<username>

For instance, make_merge_bot_branch("100", "12.0", "toto") returns "ocabot-merge-pr-100-to-12.0-by-toto".

parse_merge_bot_branch(branch_name: str) -> tuple

When handed a valid merge-bot branch name, returns a 3-tuple (pr, version, username) consisting of the strings extracted from the name.

For instance, parse_merge_bot_branch("ocabot-merge-pr-100-to-12.0-by-toto") returns ("100", "12.0", "toto").

Notes

  • The three functions must stay mutually consistent: a name generated by make_merge_bot_branch must be recognized by is_merge_bot_branch and correctly decomposed by parse_merge_bot_branch.

Task Specification: Consolidating Check Suite Status Handling

Overview

Change the GitHub check_suite webhook handler so that a completed check suite on a merge-bot branch results in the dispatch of one unified Celery task instead of a choice between separate success and failure tasks. The scope of this change is webhook dispatch; interpreting the status downstream is left to the unified task.

Module and Public API

oca_github_bot/webhooks/on_check_suite.py

The module must keep providing the asynchronous webhook handler:

async def on_check_suite(event, gh)

It must additionally expose a Celery task object named merge_bot_status. This object must be importable from the module's namespace and must provide this dispatch API:

merge_bot_status.delay(org, repo, branch, sha)

merge_bot_status is the sole task this handler uses. The separate tasks merge_bot_status_success and merge_bot_status_failure must no longer be exposed, referenced, selected, or dispatched by the handler.

The handler remains tied to check_suite webhook handling. Its dispatch decision must be based on the event payload and must not depend on the gh argument supplied to it.

Event Payload Contract

The event object the handler receives has a data attribute that is a dictionary with this shape:

{
    "repository": {
        "full_name": "<org>/<repo>",
    },
    "check_suite": {
        "status": <string>,        # for example, "completed" or "in_progress"
        "conclusion": <value>,     # for example, "success", "failure", or None
        "head_branch": <string>,   # the branch name
        "head_sha": <value>,       # the commit SHA; it may be absent
    },
}

Repository identity comes through repository.full_name, in the form "<org>/<repo>". To derive the two task arguments, the handler must split this value on /:

  • org: the component before /;
  • repo: the component after /.

As an example, "OCA/some-repo" produces org == "OCA" and repo == "some-repo". The payload is not required to contain repository.owner.login or repository.name, so the handler must not rely on those nested fields.

The task arguments for the branch and the SHA come directly from check_suite.head_branch and check_suite.head_sha respectively. They must be forwarded unchanged; in particular, the branch must not be reconstructed out of its parsed components.

Qualification of a Merge-Bot Branch

A branch qualifies only if it matches the repository's established merge-bot branch naming convention. For creating such names, make_merge_bot_branch(pr_number, target_branch, ...) is the source of truth, and is_merge_bot_branch defines whether a supplied name matches the convention. The call below produces a representative qualifying value:

make_merge_bot_branch(42, "12.0", "toto")

The helper accepts a PR number, a target branch, and any additional positional arguments that its existing API supports. The branch-helper API and the naming convention must not be changed by this task. Everyday names such as "changes" do not qualify.

Dispatch Behavior Requirements

Exactly one unified task must be enqueued by the handler if and only if both of the following conditions hold:

  1. check_suite.head_branch is a valid merge-bot branch.
  2. check_suite.status is exactly "completed".

Once both conditions hold, invoke:

merge_bot_status.delay(org, repo, branch, sha)

in which org and repo are obtained by splitting repository.full_name, and branch and sha are the check suite's values.

The decision must not be influenced by the value of check_suite.conclusion. A qualifying check suite that has completed is dispatched once, regardless of whether its conclusion is "success", "failure", None, or another conclusion. Any distinction between successful and unsuccessful results is the responsibility of the unified task.

When the branch is not a merge-bot branch, the task must not be enqueued, even if the status is completed. When the status is anything other than exactly "completed", the task must not be enqueued either, even if the branch is valid and the conclusion is successful.

Merge-bot branch check_suite.status Result
No "completed" Do not enqueue
No Any non-completed value Do not enqueue
Yes "completed" Enqueue merge_bot_status exactly once
Yes Any non-completed value, including "in_progress" Do not enqueue
Example

Take repository "OCA/some-repo", a qualifying branch held in branch, status "completed", conclusion "failure", and SHA held in sha; the observable dispatch must be exactly:

merge_bot_status.delay("OCA", "some-repo", branch, sha)

Conclusion "success" requires the same call. Modifying only the status so that it becomes "in_progress", or modifying only the branch so that it becomes "changes", must result in no call.

Compatibility and Non-Goals

  • The existing asynchronous webhook API and merge-bot branch helpers must be preserved.
  • Conclusion-based success/failure routing must not be retained in the webhook handler.
  • Leave unrelated command parsing, Git/GitHub utilities, manifest handling, other webhook handlers, and branch-classification behavior untouched.
  • After consolidation, no separate success or failure task dispatch forms any part of this handler's public behavior.

Overview

Extend the oca_github_bot.config module with a mechanism that lets individual functions ("tasks") be conditionally enabled or disabled according to a configurable list of active task names.

Required API

oca_github_bot.config.BOT_TASKS

A list variable at module level in oca_github_bot.config.

  • It must have ["all"] as its default value.
  • It is mutable at runtime; callers may reassign it to any list of strings (an empty list included).
oca_github_bot.config.switchable(name=None)

A decorator factory inside oca_github_bot.config. Calling switchable(...) returns a decorator that wraps a target function and governs whether the wrapped function actually executes, depending on the current value of BOT_TASKS.

Signature
def switchable(name=None):
    ...
  • It must work both as @config.switchable() (with no argument) and as @config.switchable("some_name") (with an explicit name argument).
How the task name is determined

Each decorated function is tied to a task name:

  • If name is supplied (a non-None string), that string is the task's name.
  • If name is omitted or is None, the task's name defaults to the wrapped function's own name (that is, the function's __name__).
Behavior when enabled or disabled

When the wrapped function is called, its behavior is evaluated against the current value of config.BOT_TASKS at the moment of the call (not at decoration time):

  • The wrapped function counts as enabled if either:
    • the string "all" occurs in BOT_TASKS, or
    • the task's name (as determined above) is contained in BOT_TASKS.
  • If it is enabled, the wrapped function is invoked normally with all the arguments that were passed to it, and its return value is returned unchanged.
  • When not enabled, the wrapped function is not invoked, and the call returns None.

Examples of Behavior

Take two decorated functions, each of which simply returns its single argument:

@config.switchable()
def ping_method(msg):
    return msg

@config.switchable("ping_method_switch")
def ping_method_2(msg):
    return msg
  • With BOT_TASKS == ["all"] (the default): both functions execute and return the argument they were given.
  • When BOT_TASKS == []: both functions return None.
  • With BOT_TASKS == ["ping_method"]: ping_method("test") returns "test"; ping_method_2("test") returns None (the name associated with it is "ping_method_switch", which is not present).
  • With BOT_TASKS == ["ping_method", "ping_method_switch"]: both functions execute and return the argument passed to them.

Notes

  • For an unnamed decoration, task-name matching uses the decorated function's actual __name__.
  • The evaluation must reflect the value of config.BOT_TASKS at the moment of each call; as a result, reassigning config.BOT_TASKS between calls changes subsequent behavior accordingly.

  • The function returns a set whose members are addon directory names only; full paths do not appear.

Semantics of the Branch-Relative Comparison

The addons the result captures are those changed specifically on the current HEAD side, relative to ref:

  1. The merge base of HEAD and ref is determined, and the changes introduced on the HEAD side since that divergence point are considered. No direct comparison with the current tree at the tip of ref takes place.
  2. Addons must not be contributed to the result by commits that were made only on the ref side after divergence. So, with each side advancing independently, the addons returned are only those changed on the current branch.
  3. The normal Git meaning of relative references stays intact. To illustrate, comparing against HEAD^ reports the addons that the current commit changed relative to its parent.
  4. Patch equivalence outranks a plain merge-base tree comparison. If a commit on the HEAD side is patch-equivalent to a commit reachable from ref, it is not a genuinely branch-specific change and must be excluded — even if it has a different commit SHA and its resulting files differ from the merge-base tree. A commit introduced by cherry-picking a commit that already exists on ref is one case this covers.
  5. Only changes attributable solely to such duplicated commits fall within the patch-equivalence exclusion. When an addon additionally has an independent, genuinely branch-specific change, that addon remains reportable.

What follows from this:

  • Once a new or modified addon has been committed on the current branch, that addon appears whenever the reference used in the comparison does not contain an equivalent change.
  • Advancing the other branch with unrelated addon changes does not result in those other-branch addons appearing.

Overview

You must write the authorization logic for a merge bot that decides whether a given GitHub user is allowed to merge changes into a repository. You must also repair the command parser so that commands appearing inside quoted comment text are ignored.

Part 1: the _user_can_merge function

Define a function _user_can_merge in the module oca_github_bot.tasks.merge_bot with this signature:

def _user_can_merge(gh, org, repo, username, git_clone_dir, target_branch):
    ...

Parameters:

  • gh: a github3 client object that is logged in (the result of github3.login(token=...)).
  • org (str): the GitHub organization/owner name (for instance "OCA").
  • repo (str): the repository name (for instance "mis-builder").
  • username (str): the GitHub login of the user asking for the merge.
  • git_clone_dir: a path-like object (it supports joining with /, like pathlib.Path) pointing at a local git working tree that holds the changes to be merged. The proposed changes live on the clone's current checked-out branch; the base is represented by another branch (the target branch).
  • target_branch (str): the name of the base branch, within git_clone_dir, to diff against (for instance "master").

The return value is a boolean.

  • Return True when the user is authorized to merge.
  • Return False in every other case.
Rules for authorization

A user is authorized to merge when either of the following holds:

  1. Repository collaborator. The user is one of the collaborators of the repository org/repo (as returned by GitHub, querying collaborators with affiliation "all"). When the user is a collaborator, authorization succeeds immediately and there is no need to inspect the local git changes.

  2. Maintainer of every modified addon. When the user is not a collaborator, determine the set of addons modified between the target branch and the currently checked-out state of git_clone_dir. Authorization is granted only if, for every modified addon, the user is listed as a maintainer of that addon.

    • An "addon" is a directory at the top level of the git clone that contains an Odoo manifest file named __manifest__.py. The manifest file holds a Python dictionary literal (which ast.literal_eval can evaluate). An addon's maintainers are taken from that dictionary's maintainers key (a list of GitHub logins); when the key is absent, the addon has no maintainers.
    • "Modified addons" are the addons having at least one file changed between target_branch and the current working tree/checked-out branch inside git_clone_dir.
    • The maintainers must be read from the manifest as it exists on the target branch, not from the modified (checked-out) version. This stops a user from granting themselves maintainer status by editing the manifest within their proposed changes. Concretely: if a user adds themselves to the maintainers list only in their branch's version of the manifest, while not being listed as a maintainer in the target-branch version, they must not be authorized.
    • When there are no modified addons, or an addon does not exist / has no maintainers on the target branch, the user is not a maintainer of it and authorization fails (unless rule 1 already granted access).
Summary of expected behavior
  • A repository collaborator (e.g. login "sbidoul" for OCA/mis-builder) is always permitted to merge.
  • A user who is not a collaborator, who is listed in the maintainers of an addon (on the target branch), and whose changes touch only that addon, is allowed to merge.
  • A user who is not a collaborator and who modifies an addon whose target-branch manifest does not list them as a maintainer is not allowed to merge.
  • A user who is not a collaborator, who modifies an addon and within those same changes adds themselves to the addon's maintainers list (while the target-branch manifest does not list them), is not allowed to merge.
Interacting with the GitHub API

The collaborator lookup for a repository must be done against the GitHub REST API v3, going through the repository resource for org/repo and its collaborators listing with the query parameters affiliation=all and per_page=100, following pagination as needed. Perform these lookups with the provided gh client.
