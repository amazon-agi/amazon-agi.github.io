01 Correct Detection of Changed Odoo Addons in a Git Diff 808 words · rewritten by GPT-5.6-sol

Task Specification: Correct Detection of Changed Odoo Addons in a Git Diff

Objective

Implement or adjust addon-change detection so that the bot reports the Odoo addons affected by the Git difference between a supplied reference and the repository's current Git-visible state. The detection must distinguish real addons at the repository root from ordinary Python packaging content under setup/, while recognizing the canonical addon symlink used by Odoo packaging layouts.

Public API

The existing symbol must remain importable from the manifest helper module:

from oca_github_bot.manifest import git_modified_addons

def git_modified_addons(addons_dir, ref):
    ...
  • addons_dir is a string or path-like value identifying the root of a Git repository or working tree.
  • ref is the Git reference against which the current state is compared, such as "origin/master".
  • The return value is a set of addon directory names as strings. Names must be unique.
  • If no qualifying addon is affected, return an empty set.

Addon and Change Definitions

A real addon is a directory located directly below addons_dir and containing an Odoo manifest. Supported manifest conventions remain __manifest__.py, __openerp__.py, and __terp__.py.

The relevant changes are those visible in the Git comparison from ref to the current state. This includes revisions recorded after ref and tracked index or working-tree differences represented by that comparison.

Required Detection Behavior

Changes in real root-level addons

For each changed file or entry below a real addon directory at the repository root, include that directory's name in the result. This applies at any depth within the addon and includes newly added root-level addons once they contain a recognized manifest.

Multiple changed entries for one addon must still produce only one set member. Changes in several addons must produce the union of their names.

Once ref represents the same state as the current tree, those previously observed changes must no longer produce a result.

Ordinary setup/ content is excluded

The repository-root setup/ directory is a Python packaging area, not an addon named setup. Its ordinary files and directories must not be interpreted as addon changes merely because their paths contain an addon-like package name.

In particular, a difference confined to a path such as:

setup/<packaging-name>/setup.py

must return an empty set, including when <packaging-name> is also the name of a real root-level addon. Other ordinary packaging files or non-addon subdirectories under setup/ are excluded in the same way.

Canonical packaging symlink exception

There is one explicit exception to the ordinary setup/ exclusion. A changed symlink in this canonical layout:

setup/<packaging-name>/odoo/addons/<addon>

must add <addon> to the result when the symlink points to the real addon directory at <addons_dir>/<addon>. This is an addon-bearing packaging link, and it must be recognized even when no file inside the real root-level addon differs from ref.

For example, with a real root addon named addon, adding and recording this link:

setup/addon/odoo/addons/addon -> ../../../../addon

must make the function return {"addon"} relative to a reference that does not contain the link.

This exception is triggered by the changed addon-link entry itself. The mere presence of an unchanged canonical symlink must not cause an ordinary sibling file such as setup.py to count as an addon change. The returned name is the linked root addon name, not setup and not an unrelated packaging-directory name.

Unrelated changes

Do not report names for repository-root files, directories that are not recognized root-level addons, or ordinary packaging scaffolding. For example, changing only a root README and ordinary setup/ files yields an empty set.

Expected Outcomes

Difference relative to ref Result
No qualifying difference set()
A file changes below root addon addon {"addon"}
A new root addon addon2 with a recognized manifest is added {"addon2"}
Only setup/addon/setup.py is added set()
The canonical link setup/addon/odoo/addons/addon -> ../../../../addon is added, and it points to the unchanged root addon {"addon"}
Root addons addon and addon2 both have qualifying changes, along with unrelated root files {"addon", "addon2"}

A cumulative packaging sequence follows the same rules: after the root addon and ref are synchronized, recording only setup/addon/setup.py yields set(); subsequently recording the canonical symlink above yields {"addon"} against that same unchanged reference, even though the ordinary setup.py path also remains in the overall difference.

Compatibility and Scope

  • Preserve the function name, import location, parameters, and set return type.
  • Preserve existing manifest recognition and manifest/version helper behavior; this change is limited to classifying paths reported by the Git comparison.
  • Do not treat every child directory of setup/ as an addon. Only the canonical changed symlink described above overrides the packaging-directory exclusion.
  • The behavior must not depend on a specific path-handling or Git-invocation implementation, provided all observable requirements above are met.

    • org, repo come from splitting repository.full_name on /,
    • pr_number is issue.number,
    • username is comment.user.login.

  • Splitting repository.full_name on / yields the organization and repository name as two separate string arguments.
  • The task objects (merge_bot_status_success, merge_bot_status_failure) and parse_commands must be module-level names imported/referenced within their respective handler modules so they can be monkeypatched at those attribute paths.

{

        "full_name": "<org>/<repo>",

Overview

Add a mechanism to the oca_github_bot.config module that allows individual functions ("tasks") to be conditionally enabled or disabled based on a configurable list of active task names.

Required API Surface

oca_github_bot.config.BOT_TASKS

A module-level list variable in oca_github_bot.config.

  • Its default value must be ["all"].
  • It is mutable at runtime; callers may reassign it to any list of strings (including an empty list).
oca_github_bot.config.switchable(name=None)

A decorator factory in oca_github_bot.config. Calling switchable(...) returns a decorator that wraps a target function and controls whether the wrapped function actually executes based on the current value of BOT_TASKS.

Signature
def switchable(name=None):
    ...
  • It must be usable both as @config.switchable() (no argument) and as @config.switchable("some_name") (explicit name argument).
Determining the task name

Each decorated function is associated with a task name:

  • If name is provided (a non-None string), that string is the task's name.
  • If name is omitted or None, the task's name defaults to the wrapped function's own name (i.e., the function's __name__).
Enabled / disabled behavior

When the wrapped function is called, its behavior is evaluated against the current value of config.BOT_TASKS at call time (not at decoration time):

  • The wrapped function is considered enabled if either:
    • BOT_TASKS contains the string "all", or
    • BOT_TASKS contains the task's name (as determined above).
  • If enabled, the wrapped function is invoked normally with all the arguments passed to it, and its return value is returned unchanged.
  • If not enabled, the wrapped function is not invoked, and the call returns None.

Behavioral Examples

Given two decorated functions where each simply returns its single argument:

@config.switchable()
def ping_method(msg):
    return msg

@config.switchable("ping_method_switch")
def ping_method_2(msg):
    return msg
  • With BOT_TASKS == ["all"] (the default): both functions execute and return their argument.
  • With BOT_TASKS == []: both functions return None.
  • With BOT_TASKS == ["ping_method"]: ping_method("test") returns "test"; ping_method_2("test") returns None (its associated name is "ping_method_switch", which is not present).
  • With BOT_TASKS == ["ping_method", "ping_method_switch"]: both functions execute and return their argument.

Notes

  • The task-name matching for an unnamed decoration uses the decorated function's actual __name__.
  • Evaluation must reflect the value of config.BOT_TASKS at the moment of each call, so reassigning config.BOT_TASKS between calls changes subsequent behavior accordingly.

Overview

You must implement authorization logic for a merge bot that determines whether a given GitHub user is allowed to merge changes into a repository. You must also fix the command parser so it ignores commands appearing inside quoted comment text.

Part 1: _user_can_merge function

Create a function _user_can_merge in the module oca_github_bot.tasks.merge_bot with the following signature:

def _user_can_merge(gh, org, repo, username, git_clone_dir, target_branch):
    ...

Parameters:

  • gh: a logged-in github3 client object (as produced by github3.login(token=...)).
  • org (str): the GitHub organization/owner name (e.g. "OCA").
  • repo (str): the repository name (e.g. "mis-builder").
  • username (str): the GitHub login of the user requesting the merge.
  • git_clone_dir: a path-like object (supports / joining, as with pathlib.Path) pointing to a local git working tree containing the changes to be merged. The current checked-out branch of this clone contains the proposed changes; there is another branch (the target branch) that represents the base.
  • target_branch (str): the name of the base branch to diff against within git_clone_dir (e.g. "master").

Return value: a boolean.

  • Return True if the user is authorized to merge.
  • Return False otherwise.
Authorization rules

A user is authorized to merge if either of the following holds:

  1. Repository collaborator. The user is among the collaborators of the repository org/repo (as returned by GitHub, querying collaborators with affiliation "all"). If the user is a collaborator, authorization succeeds immediately without needing to inspect the local git changes.

  2. Maintainer of every modified addon. If the user is not a collaborator, then determine the set of addons modified between the target branch and the currently checked-out state of git_clone_dir. The user is authorized only if, for every modified addon, the user is listed as a maintainer of that addon.

    • An "addon" is a top-level directory in the git clone containing an Odoo manifest file named __manifest__.py. The manifest file contains a Python dictionary literal (evaluable with ast.literal_eval). An addon's maintainers are taken from the maintainers key of that dictionary (a list of GitHub logins); if the key is absent, the addon has no maintainers.
    • "Modified addons" are those addons that have at least one file changed between target_branch and the current working tree/checked-out branch within git_clone_dir.
    • The maintainers must be read from the manifest as it exists on the target branch, not from the modified (checked-out) version. This prevents a user from granting themselves maintainer status by editing the manifest in their proposed changes. Concretely: if a user adds themselves to the maintainers list only in their branch's version of the manifest, but is not listed as a maintainer in the target-branch version, they must not be authorized.
    • If there are no modified addons, or an addon does not exist / has no maintainers on the target branch, the user is not a maintainer of it and authorization fails (unless rule 1 already granted access).
Expected behavior summary
  • A repository collaborator (e.g. login "sbidoul" for OCA/mis-builder) is always allowed to merge.
  • A non-collaborator who is listed in the maintainers of an addon (on the target branch), and who only modifies that addon, is allowed to merge.
  • A non-collaborator who modifies an addon whose target-branch manifest does not list them as a maintainer is not allowed to merge.
  • A non-collaborator who modifies an addon and, in the same changes, adds themselves to the addon's maintainers list (while the target-branch manifest does not list them) is not allowed to merge.
GitHub API interaction

Collaborator lookup for a repository must be performed against the GitHub REST API v3, using the repository resource for org/repo and its collaborators listing with the query parameters affiliation=all and per_page=100, following pagination as needed. Use the provided gh client to perform these lookups.

Part 2: Command parser must ignore quoted comments

In the existing command-parsing functionality (the parse_commands function importable as it currently is), lines that are quoted replies must be ignored when scanning for bot commands. A quoted line is one that begins with the > character (after optional leading whitespace), including multiply-quoted lines (e.g. >>).

Given an input body such as:

> Some comment /ocabot merge

This is the one /ocabot merge patch
