2. The Graph Classes

Both of the graph classes below are directed graphs. They must support the standard networkx directed-graph interface (they may be implemented as subclasses of networkx.DiGraph), such that the following all work:

  • add_nodes_from(iterable_of_nodes)
  • add_edge(u, v)
  • successors(node)
  • being passed as an argument to networkx.nodes(graph)

Each also exposes a method for retrieving its entry points (see below).

Entry-point semantics (this applies to both graph classes). Entry points are a set of nodes explicitly designated and maintained by the graph object itself; they are not computed from the graph's structure. In particular, entry points must never be derived from in-degree (a node that has no incoming edges is not automatically an entry point). This has the following consequences:

  • A graph that has just been constructed starts with an empty entry-point set.
  • A graph populated solely via add_nodes_from and add_edge must have an empty entry-point set; entry points are designated only by the library's own construction routines (e.g. parsing, see §3).
  • get_entry_points() must always return a collection that is non-None, sized and iterable (it must support len(...) and iteration). When nothing has been designated, len(graph.get_entry_points()) == 0.
  • Membership among the entry points is decided by node object identity (precisely the node objects that were designated).

Class ControlDependenceGraph (a directed graph whose nodes are CDGNode instances).

  • Method get_entry_points() → the collection of the CDGNodes designated as the graph's entry points. A ControlDependenceGraph assembled by hand with only add_nodes_from/add_edge reports an empty entry-point set, even if the graph structurally contains a function-typed root node.

A ControlFlowGraph populated solely via add_nodes_from and add_edge must report an empty entry-point set; entry points are never inferred from the graph's structure (e.g., blocks with zero in-degree or "starting" blocks are not implicitly entry points).

5. Conversion from CDG to CFG

program_slicing/graph/convert/ (a package)

A submodule cdg must be exposed, reachable as program_slicing.graph.convert.cdg, that provides:

to_cfg(cdg: ControlDependenceGraph) -> ControlFlowGraph

This function takes a control dependence graph and converts it into a control flow graph. The ControlFlowGraph that comes back must meet these requirements:

  • No designated entry points. to_cfg must never designate entry points in the graph it returns: regardless of the input, to_cfg(...).get_entry_points() must always be an empty collection.
  • Driven by the input's designated entry points. The conversion takes into account only the designated entry points of the input CDG (see §2). For a ControlDependenceGraph put together by hand via add_nodes_from/add_edge — which consequently has no designated entry points — the outcome is an empty graph (no nodes, no edges, no entry points).
  • Function-rooted CDGs produce no blocks. When a control dependence graph's designated entry point is a function node of type CDG_NODE_TYPE_FUNCTION — which covers every CDG parsed from Java source, such as the class-with-loop-and-branches sample of §4 — to_cfg must yield a control flow graph containing no nodes. (This is what leaves the manager's .cfg empty in §4.)

Acceptance by structural equivalence. To decide whether a produced CFG is correct relative to a reference CFG: the two graphs' entry-point sets are compared for exact set equality (node objects compared by identity), and then, from each shared entry point, corresponding successors are traversed with the corresponding blocks required to be equal. If the reference CFG was assembled manually (and thus has an empty entry-point set), this acceptance reduces to the produced graph's entry-point set also being empty — the traversal step is vacuous.

Reference example. Take a CDG assembled as follows (manually, via add_nodes_from/add_edge only, so it carries no designated entry points).

Nodes (each constructed via CDGNode(text, type, line_range, name=...)):

  • entry_point: FUNCTION (0,0) name "foo"
  • variable_a: VARIABLE (1,1) name "a"
  • variable_b: VARIABLE (2,2) name "b"
  • loop: LOOP (3,3)
  • assign_a: ASSIGNMENT (4,4) name "a"
  • branch: BRANCH (5,5)
  • statements: STATEMENTS (6,7)
  • obj_0: OBJECT (6,6)
  • goto: GOTO (7,7)
  • assign_b: ASSIGNMENT (7,7) name "b"
  • obj_1: OBJECT (8,8)
  • exit_node: EXIT (9,9)

CDG edges: entry_point→variable_a, entry_point→variable_b, entry_point→loop, loop→assign_a, loop→branch, branch→statements, branch→obj_0, branch→goto, branch→assign_b, loop→obj_1, entry_point→exit_node.

A conceptual reference CFG for this program partitions the CDG nodes into blocks:

  • block_0 = [entry_point, variable_a, variable_b]
  • block_1 = [loop]
  • block_2 = [assign_a, branch]
  • block_3 = [statements, obj_0, goto]
  • block_4 = [assign_b]
  • block_5 = [obj_1]
  • block_6 = [exit_node]

and edges block_0→block_1, block_1→block_2, block_2→block_3, block_2→block_4, block_3→block_1, block_4→block_5, block_5→block_1, block_1→block_6 — put together manually, so this CFG too has an empty entry-point set.

Running to_cfg on the CDG above must produce a graph structurally equivalent to that reference under the acceptance rule described earlier. Since the input CDG has no designated entry points and the reference CFG's entry-point set is empty, the graph that is produced must simply report an empty entry-point set; the detailed multi-block structure shown is illustrative of the reference and is not required to be materialized as actual output nodes. Do not "faithfully" emit the seven blocks and eight edges for function-rooted inputs — doing so would violate the empty-node requirement for function-rooted CDGs stated above.

Task Specification: Converting a CDG into a CFG

Overview

The task is to implement conversion of a Control Dependence Graph (CDG) into a Control Flow Graph (CFG). The converter must use the explicit control-flow relation recorded on the CDG and must group consecutive CDG nodes into ordered basic blocks.

Public API

CDG node

Module: program_slicing.graph.cdg_node

The node class that is public is CDGNode, constructed in the following way:

CDGNode(ast_class: str, node_type, line_range: tuple, name=None)

The existing form with three positional arguments remains valid. The constructor must also accept an optional fourth name argument; this includes accepting it by keyword, for example:

CDGNode("", node_type, (0, 0), name="foo")

The first positional string and the optional name are distinct fields. Instances expose ast_class, node_type, line_range, and name; when name is omitted, its value is None. The pre-existing node-type constants remain supported, including the function, variable, assignment, call, statements, branch, loop, break, goto, object, and exit constants.

Control-dependence graph

Module: program_slicing.graph.cdg

ControlDependenceGraph subclasses networkx.DiGraph. It supports ordinary directed-graph operations, such as:

  • add_node(node) — adds a node.
  • add_edge(u, v) — adds a control-dependence edge.

It additionally provides:

  • control_flow — a mutable dict that maps each CDG node to a list of its control-flow successor nodes. A newly created graph exposes an empty mapping. Callers may mutate it or replace it directly, for example cdg.control_flow = {...}.
  • add_entry_point(node) — registers a CDG node as an entry point.
  • get_entry_points() — returns the set of registered CDG entry-point nodes.

Entry-point registration follows set semantics. The ordinary directed edges of the graph represent control dependence; for CDG-to-CFG conversion, the separate control_flow mapping is authoritative.

Basic-block nodes of the CFG

Module: program_slicing.graph.cfg_node

CFGNode represents a basic block and is constructed in this way:

CFGNode(content=None)

The public contract of CFGNode is:

  • A node created by CFGNode() or by CFGNode(content=None) has an empty list as its content.

Behavior Required of to_cfg

The authoritative control-flow relation

Flow transitions must be constructed from cdg.control_flow, not from the CDG's control-dependence edges. A mapping entry u: [v1, v2, ...] stands for the transitions u -> v1, u -> v2, and so on. A terminal node may show up only as a successor value and need not be a key in the mapping.

If control_flow is empty, flow must not be inferred from the control-dependence edges. Return an empty ControlFlowGraph that has no CFG entry points.

Formation of basic blocks

The nodes represented by the control-flow relation must be partitioned into basic blocks. A basic block is a maximal ordered chain of nodes connected by single-successor/single-predecessor transitions. A transition u -> v keeps u and v in the same block only if all of the following hold:

  1. u has exactly one control-flow successor, and that successor is v;
  2. v has exactly one control-flow predecessor, and that predecessor is u; and
  3. v is not required to begin a new block on account of an entry-point boundary.

Predecessor and successor counts must be computed from control_flow, not from the ordinary edges of the CDG. As a consequence:

  • a node with multiple successors terminates its block;
  • the targets of a split begin separate blocks;
  • a node that has multiple predecessors begins a block;
  • a transition that satisfies the one-successor/one-predecessor rule remains inside a single block even if the target branches later; and
  • a terminal node joins the block of its predecessor when the joining transition satisfies the rule, but in every other case it forms its own block.

An entry point that has been registered forms a block boundary and is never merged with a predecessor. When the registered CDG entry node is the function-entry marker for executable flow, as happens in the worked example, the marker itself is left out of CFG block content: its control-flow successor begins the first block. The CFG entry block is the first emitted block reached from that marker.

CFG edges

For each control-flow transition u -> v that crosses a block boundary, add a directed CFG edge leading from the block that contains u to the block that contains v. A CFG edge must not be added for a transition internal to a single block. Splits, joins, back edges, and exit transitions must all be preserved when they cross block boundaries.

A transition whose source is an omitted function-entry marker establishes the first CFG block and its entry-point status; it does not create a separate marker block or an edge out of one.

Entry points

For each CDG entry point, register the resulting first block with ControlFlowGraph.add_entry_point. If an entry node is represented as ordinary block content rather than as an omitted function-entry marker, it must start a new block, and the block containing it is the CFG entry point. Multiple entries are handled independently of each other, and set semantics apply.

Correctness criterion

The result must contain one CFGNode per required basic block, must preserve the ordered CDG-node content of every block, must contain every and only the required inter-block transitions, and must expose the corresponding CFG entry points. As a directed graph, it must be graph-isomorphic to the CFG that these rules induce.

variable_a  -> [variable_b]
variable_b  -> [loop]
loop        -> [assign_a, exit_node]
assign_a    -> [branch]
branch      -> [statements, assign_b]
statements  -> [obj_0]
obj_0       -> [goto]
goto        -> [loop]
assign_b    -> [obj_1]
obj_1       -> [loop]

The basic blocks of the resulting CFG are:

  • B0 = [variable_a, variable_b]
  • B1 = [loop]
  • B2 = [assign_a, branch]
  • B3 = [statements, obj_0, goto]
  • B4 = [assign_b, obj_1]
  • B5 = [exit_node]

The CFG edges that result are:

B1 -> B2
B2 -> B3
B2 -> B4
B3 -> B1
B4 -> B1

Data-dependence model

Any statement that defines a variable (a declaration/initializer, an assignment or compound assignment, or a catch-parameter declaration) is a definition. A definition is connected by a directed edge to every statement it reaches that uses the name it defines. Uses are captured at fine granularity: an edge is drawn not only to the individual identifier occurrence, but also to each expression, condition, and control/body statement that encloses the use, and to a later definition of the same name that the earlier definition can reach (including a compound assignment reaching itself around a loop iteration, which produces a self-loop). When two definitions of the same variable both reach a use (for example, a loop initializer and the loop's update assignment), each contributes its own edge.

Task Description

Summary

You must update the StatementType enumeration that the program slicing graph module uses so that its member names are uppercase. This amounts to a rename of the existing enum members: the values and semantics stay the same, but the names through which the members are accessed change.

Required Change: the StatementType Enumeration

An enumeration called StatementType exists and is used to classify nodes in a control dependence graph (CDG). Java source parsing code produces CDG nodes, each of which carries a StatementType value. The tests access this enum's members by attribute (e.g., StatementType.FUNCTION).

The members of the enum must be given uppercase names. At minimum, the members listed below must exist and be accessible by these exact names:

  • StatementType.FUNCTION — classifies a node that represents a function/method definition.
  • StatementType.SCOPE — classifies a node that represents a compound scope/block of statements.
  • StatementType.VARIABLE — classifies a node that represents a variable declaration.
  • StatementType.EXIT — classifies a node that represents a function's exit point.

Note that the classification that was previously, conceptually, the "statements" classification must now be exposed as StatementType.SCOPE (renaming both the name and the label). The remaining members (FUNCTION, VARIABLE, EXIT) are simple lowercase→uppercase renames of members that already existed.

The StatementType type must remain importable from its existing location inside the graph package so that the CDG parsing code and consumers can reference these members.

Behavior Required: Java CDG Parsing

The Java parsing functionality that builds a CDG from Java source code must keep working, producing nodes classified with the StatementType members under their new uppercase names. The behaviors listed below must hold when a CDG is built from Java source:

  • The graph exposes an iterable attribute entry_points that contains the graph's root entry nodes.
  • The graph supports a successors(node) method returning an iterable of the direct child nodes of the node it is given.
  • Each node carries a StatementType (accessible in the same way as before this change).
Case 1: Java source that contains a method/function

For a Java compilation unit declaring a single method whose body contains a variable declaration among other statements:

  • Exactly one entry point exists.
  • That entry point node's classification is StatementType.FUNCTION.
  • Exactly 9 direct successor (child) nodes are attached to the entry point.
  • Of those children, in order:
    • index 0 carries the classification StatementType.SCOPE,
    • index 3 carries the classification StatementType.VARIABLE,
    • index 8 carries the classification StatementType.EXIT.
Case 2: Java source with no explicit method wrapper

For a Java input where the statements are parsed as belonging to an implicit function:

  • Exactly one entry point exists.
  • That entry point node's classification is StatementType.FUNCTION.
  • Exactly 8 direct successor (child) nodes are attached to the entry point.
  • Of those children, in order:
    • index 2 carries the classification StatementType.VARIABLE,
    • index 7 carries the classification StatementType.EXIT.

Constraints on Scope

  • The only change to the public surface that is required externally is the uppercase renaming of the StatementType members (including the rename of the former "statements" member to SCOPE).
  • All of the existing CDG parsing behavior described above (node counts, ordering, and classifications) must be preserved under the new member names.
  • Any code inside the package that references the old (lowercase) enum member names must be updated to the new uppercase names so that parsing keeps working as specified.

No other additions to the public API are required by this task.
