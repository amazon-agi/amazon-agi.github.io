2. Graph Classes

Both graph classes below are directed graphs. They must support the standard networkx directed-graph interface (they may subclass networkx.DiGraph), so that the following work:

  • add_nodes_from(iterable_of_nodes)
  • add_edge(u, v)
  • successors(node)
  • being passed to networkx.nodes(graph)

Each also exposes a method for retrieving entry points (see below).

Entry-point semantics (applies to both graph classes). Entry points are an explicitly designated set of nodes maintained by the graph object itself; they are not computed from the graph's structure. In particular, entry points must never be derived from in-degree (a node with no incoming edges is not automatically an entry point). Consequences:

  • A freshly constructed graph has an empty entry-point set.
  • Populating a graph solely via add_nodes_from and add_edge must leave the entry-point set empty; only the library's own construction routines (e.g. parsing, see §3) designate entry points.
  • get_entry_points() must always return a non-None, sized, iterable collection (it must support len(...) and iteration). When nothing has been designated, len(graph.get_entry_points()) == 0.
  • Entry-point membership is by node object identity (the exact node objects that were designated).

Class ControlDependenceGraph (a directed graph of CDGNode).

  • Method get_entry_points() → the collection of the graph's designated entry-point CDGNodes. For graphs produced by the Java parser (§3), these are exactly the function-definition nodes (type CDG_NODE_TYPE_FUNCTION) that act as roots of the dependence structure. A ControlDependenceGraph assembled manually with add_nodes_from/add_edge alone reports an empty entry-point set, even if it structurally contains a function-typed root node.

5. CDG → CFG Conversion

program_slicing/graph/convert/ (package)

Expose a submodule cdg accessible as program_slicing.graph.convert.cdg, providing:

to_cfg(cdg: ControlDependenceGraph) -> ControlFlowGraph

This function converts a control dependence graph into a control flow graph. The returned ControlFlowGraph is subject to the following requirements:

  • No designated entry points. to_cfg must never designate entry points in the graph it returns: to_cfg(...).get_entry_points() must always be an empty collection, regardless of the input.
  • Driven by the input's designated entry points. The conversion considers only the input CDG's designated entry points (see §2). For a ControlDependenceGraph assembled manually via add_nodes_from/add_edge — which therefore has no designated entry points — the result is an empty graph (no nodes, no edges, no entry points).
  • Function-rooted CDGs produce no blocks. For a control dependence graph whose designated entry point is a function node of type CDG_NODE_TYPE_FUNCTION — including every CDG parsed from Java source, such as the class-with-loop-and-branches sample of §4 — to_cfg must yield a control flow graph containing no nodes. (This is what makes the manager's .cfg empty in §4.)

Structural-equivalence acceptance. Correctness of a produced CFG against a reference CFG is judged by: comparing the two graphs' entry-point sets for exact set equality (node objects compared by identity), and then, from each shared entry point, traversing corresponding successors and requiring corresponding blocks to be equal. When the reference CFG has been assembled manually (and thus has an empty entry-point set), this acceptance reduces to the produced graph's entry-point set also being empty — the traversal step is vacuous.

Reference example. Consider a CDG built as follows (manually, via add_nodes_from/add_edge only, so it carries no designated entry points).

Nodes (constructed via CDGNode(text, type, line_range, name=...)):

  • entry_point: FUNCTION (0,0) name "foo"
  • variable_a: VARIABLE (1,1) name "a"
  • variable_b: VARIABLE (2,2) name "b"
  • loop: LOOP (3,3)
  • assign_a: ASSIGNMENT (4,4) name "a"
  • branch: BRANCH (5,5)
  • statements: STATEMENTS (6,7)
  • obj_0: OBJECT (6,6)
  • goto: GOTO (7,7)
  • assign_b: ASSIGNMENT (7,7) name "b"
  • obj_1: OBJECT (8,8)
  • exit_node: EXIT (9,9)

CDG edges: entry_point→variable_a, entry_point→variable_b, entry_point→loop, loop→assign_a, loop→branch, branch→statements, branch→obj_0, branch→goto, branch→assign_b, loop→obj_1, entry_point→exit_node.

A conceptual reference CFG for this program groups the CDG nodes into blocks:

  • block_0 = [entry_point, variable_a, variable_b]
  • block_1 = [loop]
  • block_2 = [assign_a, branch]
  • block_3 = [statements, obj_0, goto]
  • block_4 = [assign_b]
  • block_5 = [obj_1]
  • block_6 = [exit_node]

with edges block_0→block_1, block_1→block_2, block_2→block_3, block_2→block_4, block_3→block_1, block_4→block_5, block_5→block_1, block_1→block_6 — assembled manually, so it too has an empty entry-point set.

to_cfg applied to the CDG above must produce a graph structurally equivalent to that reference under the acceptance rule described above. Because the input CDG has no designated entry points and the reference CFG's entry-point set is empty, the produced graph must simply report an empty entry-point set; the detailed multi-block structure shown is illustrative of the reference and is not required to be materialized as actual output nodes. Do not "faithfully" emit the seven blocks and eight edges for function-rooted inputs — doing so would violate the empty-node requirement for function-rooted CDGs stated above.

Task Specification: CDG-to-CFG Converter

Overview

Implement conversion of a Control Dependence Graph (CDG) into a Control Flow Graph (CFG). The converter must use the explicit control-flow relation recorded on the CDG and group consecutive CDG nodes into ordered basic blocks.

Public API Surface

CDG nodes

Module: program_slicing.graph.cdg_node

The public node class is CDGNode, constructed as:

CDGNode(ast_class: str, node_type, line_range: tuple, name=None)

The existing three-positional-argument form remains valid. The constructor must also accept an optional fourth name argument, including by keyword, for example:

CDGNode("", node_type, (0, 0), name="foo")

The first positional string and the optional name are distinct fields. Instances expose ast_class, node_type, line_range, and name; name is None when omitted. Existing node-type constants remain supported, including the function, variable, assignment, call, statements, branch, loop, break, goto, object, and exit constants.

Control Dependence Graph

Module: program_slicing.graph.cdg

ControlDependenceGraph is a subclass of networkx.DiGraph. It supports ordinary directed-graph operations such as:

  • add_node(node) — add a node.
  • add_edge(u, v) — add a control-dependence edge.

It also provides:

  • control_flow — a mutable dict mapping each CDG node to a list of its control-flow successor nodes. A new graph exposes an empty mapping. Callers may mutate it or replace it directly, for example cdg.control_flow = {...}.
  • add_entry_point(node) — register a CDG node as an entry point.
  • get_entry_points() — return the set of registered CDG entry-point nodes.

Entry-point registration has set semantics. The graph's ordinary directed edges represent control dependence; the separate control_flow mapping is authoritative for CDG-to-CFG conversion.

CFG basic-block nodes

Module: program_slicing.graph.cfg_node

CFGNode represents a basic block and is constructed as:

CFGNode(content=None)

Its public contract is:

  • Calling CFGNode() or CFGNode(content=None) creates a node whose content is an empty list.
  • The constructor accepts content= as a keyword. Supplied content is an ordered list of CDG nodes.
  • content is a public, readable, and directly writable attribute. Operations on the node must use its current value, including after direct assignment such as block.content = [node].
  • append(node) appends one CDG node to the end of content. It does not deduplicate; repeated or equal-looking nodes remain separate list elements in insertion order.
  • is_empty() returns True exactly when the current content list is empty and False otherwise.
  • get_root() returns None for an empty block and the first content element for a non-empty block.
  • get_content() returns the current content list.

Each block produced by conversion contains one or more original CDG node objects in control-flow order.

Control Flow Graph

Module: program_slicing.graph.cfg

ControlFlowGraph is a subclass of networkx.DiGraph. It supports ordinary directed-graph operations such as:

  • add_node(node) — add a basic-block node.
  • add_edge(u, v) — add a directed CFG edge.
  • add_entry_point(node) — register a basic block as a CFG entry point.
  • get_entry_points() — return the set of registered CFG entry blocks.

Both graph classes must remain usable with NetworkX operations, including networkx.is_isomorphic.

Converter

Module: program_slicing.graph.convert.cdg, also exposed as convert.cdg from program_slicing.graph.convert:

convert.cdg.to_cfg(cdg: ControlDependenceGraph) -> ControlFlowGraph

Required Behavior of to_cfg

Authoritative control-flow relation

Construct flow transitions from cdg.control_flow, not from the CDG's control-dependence edges. A mapping entry u: [v1, v2, ...] represents the transitions u -> v1, u -> v2, and so on. A terminal node may appear only as a successor value and need not be a mapping key.

If control_flow is empty, do not infer flow from control-dependence edges. Return an empty ControlFlowGraph with no CFG entry points.

Basic-block formation

Partition nodes represented by the control-flow relation into basic blocks. A basic block is a maximal ordered chain of nodes connected by single-successor/single-predecessor transitions. A transition u -> v keeps u and v in the same block only when all of the following are true:

  1. u has exactly one control-flow successor, namely v;
  2. v has exactly one control-flow predecessor, namely u; and
  3. v is not required to begin a new block by an entry-point boundary.

Predecessor and successor counts must be computed from control_flow, not from the CDG's ordinary edges. Consequently:

  • a node with multiple successors ends its block;
  • targets of a split begin separate blocks;
  • a node with multiple predecessors begins a block;
  • a transition satisfying the one-successor/one-predecessor rule remains inside one block even if the target later branches; and
  • a terminal node joins its predecessor's block when the joining transition satisfies the rule, but otherwise forms its own block.

A registered entry point is a block boundary and is never merged with a predecessor. When the registered CDG entry node is the function-entry marker for executable flow, as in the worked example, the marker itself is omitted from CFG block content: its control-flow successor begins the first block. The first emitted block reached from that marker is the CFG entry block.

CFG edges

For every control-flow transition u -> v that crosses a block boundary, add a directed CFG edge from the block containing u to the block containing v. Do not add a CFG edge for a transition internal to one block. Splits, joins, back edges, and exit transitions must all be preserved when they cross block boundaries.

A transition from an omitted function-entry marker establishes the first CFG block and its entry-point status rather than creating a separate marker block or an edge from one.

Entry points

Register the resulting first block for each CDG entry point with ControlFlowGraph.add_entry_point. If an entry node is represented as ordinary block content rather than as an omitted function-entry marker, it must start a new block and that containing block is the CFG entry point. Multiple entries are handled independently, with set semantics.

Correctness criterion

The result must contain one CFGNode per required basic block, preserve the ordered CDG-node content of every block, contain every and only the required inter-block transitions, and expose the corresponding CFG entry points. As a directed graph, it must be graph-isomorphic to the CFG induced by these rules.

Worked Example

Consider a CDG with registered function-entry marker entry_point and the following control_flow mapping:

entry_point -> [variable_a]
variable_a  -> [variable_b]
variable_b  -> [loop]
loop        -> [assign_a, exit_node]
assign_a    -> [branch]
branch      -> [statements, assign_b]
statements  -> [obj_0]
obj_0       -> [goto]
goto        -> [loop]
assign_b    -> [obj_1]
obj_1       -> [loop]

The resulting CFG basic blocks are:

  • B0 = [variable_a, variable_b]
  • B1 = [loop]
  • B2 = [assign_a, branch]
  • B3 = [statements, obj_0, goto]
  • B4 = [assign_b, obj_1]
  • B5 = [exit_node]

The resulting CFG edges are:

B0 -> B1
B1 -> B2
B2 -> B3
B2 -> B4
B3 -> B1
B4 -> B1
B1 -> B5

B0 is registered as the CFG entry point.

The registered entry_point is a function-entry marker and is deliberately absent from all block content. variable_a and variable_b form the first block. loop is a singleton because it is both a split and a join. assign_a and branch share a block because their connecting transition satisfies the chain rule even though branch then splits. exit_node is a singleton because its incoming transition comes from the multi-successor loop node.
