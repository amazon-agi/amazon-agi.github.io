Task Specification: Factory Module

Overview

Implement the factory framework in sqlitecollections.factory. The module provides reusable factory base classes and concrete factories that construct sqlitecollections List, Set, and Dict containers while retaining a normalized connection and the appropriate serialization callables.

The public framework consists of:

  • FactoryBase[T]
  • SequenceFactoryBase[T]
  • ListFactory[T]
  • SetFactory[T]
  • DictFactory[KT, VT]

Module-scope dependencies

tidy_connection

The module must expose sqlitecollections.factory.tidy_connection. It is a callable used to normalize or prepare the connection supplied when a factory is constructed. Each factory construction must invoke this module-scope callable exactly once with the constructor's connection value, including None when the argument is omitted.

chain

The module must expose sqlitecollections.factory.chain, corresponding to itertools.chain. DictFactory uses this module-scope callable when combining a positional mapping or item iterable with keyword entries.

Class: FactoryBase

FactoryBase is generic in one element type and must be usable as FactoryBase[T]. It provides common connection and serializer state for concrete factories.

Construction

Its constructor supports the following arguments, all of which are optional:

def __init__(
    self,
    connection=None,
    serializer=None,
    deserializer=None,
):
    ...

The arguments have these contracts:

  • connection may be a database connection or connection specifier accepted by tidy_connection; it defaults to None. The exact supplied value is passed to tidy_connection once, and that call's result is exposed as self.connection. Thus default construction calls tidy_connection(None).
  • serializer is a callable from an element to bytes. If it is omitted or explicitly None, self.serializer must resolve to SqliteCollectionBase._default_serializer; otherwise the supplied callable is exposed unchanged.
  • deserializer is a callable from bytes to an element. If it is omitted or explicitly None, self.deserializer must resolve to SqliteCollectionBase._default_deserializer; otherwise the supplied callable is exposed unchanged.

A concrete subclass that implements the container hook must therefore be constructible with no arguments. The public connection, serializer, and deserializer attributes expose the values described above.

Container class hook

FactoryBase defines an overridable classmethod:

@classmethod
def _get_container_class(cls) -> Callable[..., <container>]:
    ...

It returns the container class or other callable that the factory instantiates. Concrete subclasses override this hook to designate their target container type.

Class: SequenceFactoryBase

SequenceFactoryBase is generic in one element type and must be usable as SequenceFactoryBase[T]. It builds on FactoryBase[T] and inherits all of its construction, normalization, default-codec, and public-attribute behavior.

create
def create(self, data=None) -> <container instance>:
    ...

data is an optional iterable. The method obtains its target by calling the class's _get_container_class() hook and invokes the resulting container callable once. It returns that invocation's result unchanged.

Invocation depends on data:

  • If data is not None, including when it is an empty iterable, invoke the target with exactly these keyword arguments:

    data=data,
connection=self.connection,
serializer=self.serializer,
deserializer=self.deserializer

    The same data object is forwarded without conversion.

  • If data is omitted or explicitly None, invoke the target with exactly:

    connection=self.connection,
serializer=self.serializer,
deserializer=self.deserializer

    In this no-data case, the data keyword must be omitted entirely; it must not be passed as data=None.

Callable behavior

Instances of SequenceFactoryBase and its subclasses are callable. __call__ accepts the same optional data argument, delegates to create, forwards a supplied argument, and returns the result of create. Calling the factory with no argument or with None selects the no-data behavior above.

Concrete sequence factories

ListFactory

ListFactory is a generic subclass of SequenceFactoryBase, usable as ListFactory[T]. Its _get_container_class() hook designates the indexed/parameterized sqlitecollections List[T] container.

Calling a list factory with non-None data constructs the target with data, connection, serializer, and deserializer as specified by SequenceFactoryBase. Calling it with no argument or with None constructs the target with only connection, serializer, and deserializer, omitting data. The produced List object is returned.

SetFactory

SetFactory is a generic subclass of SequenceFactoryBase, usable as SetFactory[T]. Its _get_container_class() hook designates the indexed/parameterized sqlitecollections Set[T] container.

Calling a set factory with non-None data constructs the target with data, connection, serializer, and deserializer as specified by SequenceFactoryBase. Calling it with no argument or with None constructs the target with only connection, serializer, and deserializer, omitting data. The produced Set object is returned.

Class: DictFactory

DictFactory is generic in key and value types and must be usable as DictFactory[KT, VT]. It builds on the common factory connection behavior and targets the indexed/parameterized sqlitecollections Dict[KT, VT] container. Its _get_container_class() classmethod returns that target.

Construction and codec attributes

The constructor accepts these optional arguments:

def __init__(
    self,
    connection=None,
    key_serializer=None,
    key_deserializer=None,
    value_serializer=None,
    value_deserializer=None,
):
    ...

Behavior is as follows:

  • connection defaults to None, is passed through the module-scope tidy_connection exactly once, and the normalized result is exposed as connection.
  • key_serializer and key_deserializer become the public key_serializer and key_deserializer attributes. If either is None, it independently falls back to SqliteCollectionBase._default_serializer or SqliteCollectionBase._default_deserializer, respectively.
  • The inherited serializer and deserializer attributes expose the same callables as key_serializer and key_deserializer, respectively.
  • A non-None value_serializer is exposed unchanged as value_serializer. If it is None, value_serializer defaults to the resolved key_serializer, including any custom key serializer.
  • A non-None value_deserializer is exposed unchanged as value_deserializer. If it is None, value_deserializer defaults to the resolved key_deserializer, including any custom key deserializer.

Consequently, DictFactory may be constructed with no arguments, and all four codec attributes then resolve through the default sqlitecollection codecs.

create

create accepts at most one optional positional data source followed by arbitrary keyword entries:

def create(self, data=None, **entries) -> Dict[KT, VT]:
    ...

The positional source may be either a mapping or an iterable of (key, value) pairs. The method obtains the indexed/parameterized Dict[KT, VT] target through _get_container_class(), invokes it once, and returns its result unchanged. Every target invocation includes exactly these common keyword arguments:

connection=self.connection,
key_serializer=self.key_serializer,
key_deserializer=self.key_deserializer,
value_serializer=self.value_serializer,
value_deserializer=self.value_deserializer

The data keyword is determined as follows:

  1. No positional source and no keyword entries: If the positional source is omitted or None and there are no entries, do not pass a data keyword at all.

  2. Keyword entries only: If the positional source is omitted or None and entries are present, pass data=entries, where entries is the dictionary formed from those keyword arguments. For example, factory(a=1, b=2) supplies data={"a": 1, "b": 2}.

  3. A positional source is present: Combine the source with the keyword entries using the module-scope chain callable. For a mapping source, the first iterable is data.items(); for an iterable of pairs, the first iterable is data itself. The second iterable is always entries.items(). Pass the resulting chained iterable as data. In equivalent terms:

    first = data.items() if isinstance(data, Mapping) else data
combined = chain(first, entries.items())

    The positional entries precede keyword entries. This chaining behavior also applies when the positional source is empty or when there are no keyword entries; in the latter case it is combined with an empty dictionary's items view rather than forwarded directly.

No case may pass data=None.

Callable behavior

DictFactory instances are callable. __call__ accepts the same optional positional source and keyword entries as create, delegates them to create, and returns its result. It therefore supports all of these public forms:

factory()
factory(iterable_of_pairs)
factory(mapping)
factory(a=1, b=2)
factory(iterable_or_mapping, a=1, b=2)

Typing and compatibility notes

  • Generic type parameters are for typing only; runtime behavior does not depend on a concrete type argument.
  • Concrete factories select their container through the overridable _get_container_class hook. ListFactory, SetFactory, and DictFactory use the indexed/parameterized form of their corresponding sqlitecollections container.
  • Factories return the object produced by their target container callable and do not add unrelated container-construction options.

Task Specification: Implement keys() for the SQL-backed Dict

Context

The codebase provides a dictionary-like class, Dict, that stores its key/value data in a SQLite table rather than in memory. It is importable as sc.Dict (i.e., from the package that is imported under the alias sc) and is a generic type parameterized as Dict[KeyType, ValueType].

An instance is constructed with keyword arguments:

sc.Dict[Hashable, Any](connection=<sqlite3.Connection>, table_name="items")

The instance already supports item deletion via del parent[key], which removes the corresponding row from the backing table.

Your task is to add a keys() method to Dict that returns a live, dict-like keys view object, and to implement that view object with the behavior described below.

Required API

Dict.keys(self) -> KeysView
  • Returns a keys-view object bound to the same backing table as the Dict that created it.
  • The returned object must be an instance compatible with collections.abc.KeysView.
  • The view is live: it always reflects the current contents of the backing table at the moment it is queried, not a snapshot taken at creation time. If rows are added or removed from the underlying table after the view is created, every subsequent operation on the view must observe the current state.

Required behavior of the keys view object

Let view = parent.keys().

Length: len(view)
  • Returns the current number of key/value entries stored in the backing table.
  • Must reflect table changes made after the view was created (e.g., if the table grows from empty to 4 rows, len(view) must return 0 then 4 accordingly).
Iteration: iter(view)
  • Returns a fresh Iterator (an instance compatible with collections.abc.Iterator) each time it is called.
  • Iterating yields the stored keys in the order the rows appear in the backing table (insertion/stored order).
  • Because the view is live, calling iter(view) again after the table has changed must produce an iterator reflecting the new contents. For example, if the table currently holds keys ["a", "b", "c", "d"], iteration yields those in order; after a key is deleted, a newly obtained iterator yields the remaining keys in order (e.g., ["a", "c", "d"]).
  • Each call to iter(view) starts from the beginning of the current table contents.
Membership: key in view / key not in view
  • key in view returns True if a key equal to key currently exists in the backing table, otherwise False. key not in view returns the logical negation.
  • Membership must consider keys of varied hashable types, including but not limited to: str, bytes, None, int, and nested tuples (e.g., ((0, 1), "a")). A key present in the table must test as a member; a key absent from the table (e.g., 100) must test as a non-member.
  • Membership is live: after a key is deleted from the backing table, that key must test as absent.
  • If the supplied key is not hashable (e.g., a list), the membership test must raise TypeError with a message that includes the text unhashable type:.
Reversal: reversed(view)
  • On Python 3.8 and later: returns a fresh Iterator (compatible with collections.abc.Iterator) that yields the stored keys in the reverse of their stored order. For example, if the table holds keys in stored order ["a", "b"], reversed(view) yields ["b", "a"].
  • On Python versions older than 3.8: reversed(view) must raise TypeError with the message 'KeysView' object is not reversible.

Notes / Constraints

  • Empty table: len returns 0, iteration yields an empty sequence, and membership tests return False.
  • Do not cache or snapshot table contents in the view; every operation must query the current backing-table state.

Task Specification: Version-guard normalization

Across the test/support modules, the Python-version branch that selects typing sources must treat version 3.9 as belonging to the "modern" branch (using collections.abc), i.e., the condition is "version is greater than or equal to (3, 9)". This is a boundary correction only: on exactly Python 3.9 the collections.abc sources must be used. This affects only which import source is chosen and introduces no new runtime behavior beyond making the correct symbols available on Python 3.9.

Goal

Extend the keys-view object returned by sqlitecollections.Dict.keys() so that it supports set intersection with the binary & operator in either operand position. Every such operation must produce a SQLite-backed, temporary sqlitecollections.Set.

Package context

The package is imported as:

import sqlitecollections as sc

sc.Dict is a dict-like SQLite-backed collection, and sc.Set is a set-like SQLite-backed collection. Every SQLite-backed collection exposes the name of its backing table through table_name.

For example, an existing dictionary may be opened with:

parent = sc.Dict(connection=connection, table_name="items")
keys_view = parent.keys()

The keys view remains a live view of its parent dictionary. Its existing behavior for len(), iteration, membership testing, and reversed() must remain unchanged. Intersections use the keys present in the parent at the time the operation is performed.

Public API

The object returned by sc.Dict.keys() must provide both of these methods:

keys_view.__and__(other)   # keys_view & other
keys_view.__rand__(other)  # other & keys_view

Both methods return a new sc.Set.

Intersection behavior

Keys view on the left: keys_view & other
  • other may be any iterable of hashable Python values, including a built-in set, sequence, generator, or iterator.
  • The operation computes the set intersection between the parent dictionary's current keys and the values yielded by other.
  • The result contains exactly the values present in both inputs. Values not present as dictionary keys are omitted.
  • An empty intersection returns an empty sc.Set, not a built-in set.
Keys view on the right: other & keys_view
  • This form must have the same intersection semantics as keys_view & other.
  • It must work even when other is an arbitrary one-shot iterator, such as iter(("a", "b")), rather than an object that natively implements &.
  • It returns a new sc.Set, including when the result is empty.
New and chainable results
  • Every intersection operation creates a distinct result collection and does not mutate the parent dictionary.
  • The returned object must support the existing sc.Set intersection operator, so chained expressions work:
result = keys_view & {"a", "b"} & {"b"}
  • Each stage of a chain produces a new sc.Set; the final result above contains only "b".
  • Set semantics apply to the result, so each intersecting value is represented at most once.

Backing database and serialization

  • A result is backed by a newly created Set table in the same SQLite database as the parent dictionary.
  • The result exposes that table's name through result.table_name.
  • With the default serializers, every result value is stored in serialized_value using sc.base.SqliteCollectionBase._default_serializer. Therefore, querying
SELECT serialized_value FROM <result.table_name>

returns no rows for an empty intersection and otherwise returns exactly the serialized forms of the intersecting dictionary keys.

Deterministic encounter order

Although the result has set semantics, the insertion and observable backing-row order of matching values must not be produced by re-enumerating an unordered or hash-dependent intermediate set. Matching values must be stored in deterministic encounter order, preserving the parent dictionary's stored key order when its keys determine the result encounter sequence (and preserving an ordered iterable operand's encounter sequence when that operand is the sequence being consumed). The result's enumeration must retain that same encounter order.

In particular, if the parent dictionary stores keys in the order "a", "c", "b" and the other operand yields "a" followed by "b", selecting serialized_value from the result table without an ORDER BY clause must yield, in order:

  1. the serialized form of "a";
  2. the serialized form of "b".

The values must not be reordered according to Python hash iteration. No separate sorting requirement is imposed; this is an encounter-order guarantee.

Lifetime and cleanup

Intersection results are volatile collections:

  • Their backing Set tables must not become persistent additions to the parent's database.
  • Once a result has no remaining references and is disposed of, its backing table and its collection metadata must be removed.
  • Temporary intermediate Sets created by a chained expression are subject to the same cleanup behavior.
  • The parent dictionary's table and metadata must remain intact. For a parent created as sc.Dict(connection=connection, table_name="items"), after all intersection results are disposed of, the database's tracked collection tables must again consist solely of the single Dict collection named items.

Examples

import sqlite3
import sqlitecollections as sc

connection = sqlite3.connect(":memory:")
parent = sc.Dict(
    connection=connection,
    table_name="items",
    data=(("a", 1), ("c", 3), ("b", 2)),
)
keys_view = parent.keys()

left_result = keys_view & {"a", "b"}
assert isinstance(left_result, sc.Set)
assert set(left_result) == {"a", "b"}

right_result = iter(("a", "b")) & keys_view
assert isinstance(right_result, sc.Set)
assert list(right_result) == ["a", "b"]

empty_result = iter((1, 2, 3)) & keys_view
assert isinstance(empty_result, sc.Set)
assert len(empty_result) == 0

chained_result = keys_view & {"a", "b"} & {"b"}
assert isinstance(chained_result, sc.Set)
assert set(chained_result) == {"b"}

Context

This codebase provides SQLite-backed collection types under a package importable as sc (with a submodule sc.base). You must add support for the | (bitwise-or / union) operator to this keys-view object.

Required behavior

Implement __or__ on the Dict keys-view class so that:

keys_view | other

returns a new sc.Set instance whose contents are the set-union of:

  • all keys currently present in the originating Dict, and
  • all elements produced by iterating other.
Details and constraints

  • other may be any iterable (the tests pass one-shot iterators, e.g. iter((1, 2, 3))). Iterating other exactly once to collect its elements is sufficient.

  • The return value must be an instance of sc.Set.

  • The resulting sc.Set must contain, with no duplicates, the union of the Dict's keys and the elements of other. Elements may be of heterogeneous types (e.g. strings and integers).

  • Serialization of stored elements must use the same serialization mechanism as the rest of the library, i.e. the values stored in the resulting Set's backing table are exactly those produced by sc.base.SqliteCollectionBase._default_serializer(element).

  • The keys-view class must implement __or__(self, other) returning an sc.Set.
  • sc.Set — the returned type, exposing a table_name attribute.
  • sc.base.SqliteCollectionBase._default_serializer(value) — existing serializer (already present).

other | sut

must:

  1. Return a new sc.Set instance.

Element type

Keys may be arbitrary hashable values, and other may yield arbitrary hashable values (integers, strings, etc.); the union combines them without type restriction beyond hashability/serializability.

  • The result MUST be a new sc.Set instance (isinstance(result, sc.Set) is true).
  • The elements stored in the resulting sc.Set are the surviving pairs themselves. Each stored element is a pair (key, value), and its persisted serialized value is _default_serializer((key, value)) — i.e. the whole pair is serialized as one object.
  • Membership/difference is determined by the pair as a whole: a pair from other is excluded only if an equal (key, value) pair exists in sut. A pair whose key matches but whose value differs is retained.

Example: if sut contains ("a", 4), ("c", 4), ("b", 4), then:

  • iter((("a", 1), ("b", 2), ("c", 3))) - sut yields a set containing all three of ("a", 1), ("b", 2), ("c", 3) (none match by full pair).
  • iter((("a", 4), ("b", 0))) - sut yields a set containing only ("b", 0) (("a", 4) matches an existing pair and is dropped).

Error condition: If any value in sut is unhashable (e.g. a value that is a list), the operation MUST raise TypeError whose message matches unhashable type: '<typename>' (the standard Python unhashable-type message). This applies even when the left operand is a small/simple iterable.

2. __xor__ — sut ^ other

Support the symmetric-difference operator.

  • The left operand is the items view sut. The right operand (other) is any iterable yielding 2-element items (pairs), including a plain iterator.
  • The result is the symmetric difference: pairs that are in exactly one of sut / other (compared by full (key, value) pair equality).
  • The result MUST be a new sc.Set instance (isinstance(result, sc.Set) is true).
  • Each element stored in the resulting sc.Set is a pair. Important: for __xor__, each element pair is stored as a 2-tuple whose two members are each already serialized, i.e. the stored element is (_default_serializer(key), _default_serializer(value)), and the persisted serialized value of that element is _default_serializer((_default_serializer(key), _default_serializer(value))).

Example: if sut contains ("a", 4), ("c", 4), ("b", 4), then sut ^ iter((("a", 4), ("b", 4), ("c", 3))) yields a set containing exactly the two pairs ("c", 4) and ("c", 3) (("a", 4) and ("b", 4) appear on both sides and cancel out). These are stored as the doubly-serialized pair form described above.

Cleanup / side-effect requirements

Both operations create a new backing sc.Set (with its own table). When such a result object is deleted (its __del__/garbage collection), its backing table MUST be dropped, leaving only the original items table in the database. Producing the result must not leave stray tables behind after the result is disposed of.

API surface to implement

On the items-view class returned by sc.Dict(...).items():

  • __rsub__(self, other: Iterable) -> sc.Set — implements other - view.
  • __xor__(self, other: Iterable) -> sc.Set — implements view ^ other.

Both accept any iterable of 2-element pairs (including bare iterators) and return a freshly created sc.Set.

Task Specification: Implement __xor__ and __rxor__ for Dict's ItemsView

Context

The codebase provides a Dict class (a persistent, SQLite-backed mapping) whose .items() method returns an items-view object. This items-view object behaves like a set of (key, value) pairs and supports set-like symmetric-difference operations against other iterables. You must implement/adjust the reflected symmetric-difference operation (__rxor__) and ensure the forward symmetric-difference operation (__xor__) handles a specific error case.

Public API Surface

The following are already available in the package (referenced here as sc for the top-level package):

  • sc.Dict[K, V](connection=<sqlite3.Connection>, table_name=<str>) — constructs a SQLite-backed dictionary bound to the given connection and table.
  • <Dict>.items() — returns the items-view object under test.
  • sc.Set — a SQLite-backed set type. Result objects returned by the symmetric-difference operations must be instances of this type.
  • sc.base.SqliteCollectionBase._default_serializer(obj) — the default serialization callable used to persist values.

You must ensure the items-view object supports the Python binary operator ^ in both operand positions:

  • items_view ^ other (forward, __xor__)
  • other ^ items_view (reflected, __rxor__)

where other is an arbitrary iterable of two-element (key, value) pairs (including one-shot iterators).

Required Behavior

Symmetric difference (__rxor__)

When the items-view appears on the right-hand side of ^ and the left-hand operand is an iterable yielding two-element (key, value) tuples:

  • The result is the set-theoretic symmetric difference between the set of (key, value) pairs contained in the items-view and the set of (key, value) pairs produced by iterating the other operand. That is, it contains exactly those pairs present in one operand but not in both.
  • Each pair is treated as a single hashable element (the pair as a whole), consistent with normal set symmetric-difference semantics over (key, value) tuples.
  • The returned object must be an instance of sc.Set.
  • The returned Set must persist its elements using the default serializer. Each stored element is the serialized form of a 2-tuple whose components are the individually serialized key and serialized value — i.e. _default_serializer((_default_serializer(key), _default_serializer(value))).
  • The other operand may be a one-use iterator; it must be consumed correctly.
  • Producing the result must not alter the underlying items table of the source Dict; after the operation and disposal of the result, only the original items table content remains.

Example: given an items-view containing pairs ("a", 4), ("c", 4), ("b", 4), evaluating iter((("a", 4), ("b", 4), ("c", 3))) ^ items_view yields a Set containing exactly the pairs ("c", 4) and ("c", 3) (the pairs that differ between the two operands).

Error case for unhashable values (both __xor__ and __rxor__)

If, while computing the symmetric difference, a (key, value) pair from the items-view contains a value that is not hashable (e.g. a list), the operation must raise TypeError whose message matches the pattern unhashable type: '<name>' (where <name> is the offending type's name).

This applies symmetrically:

  • items_view ^ other must raise this TypeError when the items-view contains an unhashable value.
  • other ^ items_view must raise this TypeError when the items-view contains an unhashable value.

In both error scenarios the other operand is a small iterable/iterator of (key, value) pairs.

Constraints

  • Only the behavior described above is in scope. Do not add other operators, methods, or side effects.
