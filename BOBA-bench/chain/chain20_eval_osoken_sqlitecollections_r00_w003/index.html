Factory Module Task Specification

Overview

The task is to implement the factory framework in sqlitecollections.factory. This module supplies reusable factory base classes together with concrete factories that construct sqlitecollections List, Set, and Dict containers, retaining a normalized connection and the appropriate serialization callables.

The public framework consists of the following:

  • FactoryBase[T]
  • SequenceFactoryBase[T]
  • ListFactory[T]
  • SetFactory[T]
  • DictFactory[KT, VT]

Dependencies at module scope

tidy_connection

sqlitecollections.factory.tidy_connection must be exposed by the module. It is a callable whose job is to normalize or prepare the connection supplied when a factory is constructed. Every factory construction must invoke this module-scope callable exactly once, passing the constructor's connection value — None included when the argument is omitted.

chain

sqlitecollections.factory.chain, which corresponds to itertools.chain, must be exposed by the module as well. DictFactory uses this module-scope callable whenever it combines a positional mapping or item iterable with keyword entries.

The FactoryBase class

FactoryBase is generic over one element type and must be usable as FactoryBase[T]. It provides the connection and serializer state shared by concrete factories.

Construction

Its constructor supports the arguments below, all of which are optional:

def __init__(
    self,
    connection=None,
    serializer=None,
    deserializer=None,
):
    ...

The arguments carry these contracts:

  • connection may be a database connection or a connection specifier that tidy_connection accepts; its default is None. The value supplied is passed to tidy_connection once, exactly as given, and the result of that call is exposed as self.connection. Default construction therefore calls tidy_connection(None).
  • serializer is a callable from an element to bytes. When it is omitted or explicitly None, self.serializer must resolve to SqliteCollectionBase._default_serializer; otherwise the callable that was supplied is exposed unchanged.
  • deserializer is a callable from bytes to an element. When it is omitted or explicitly None, self.deserializer must resolve to SqliteCollectionBase._default_deserializer; otherwise the callable that was supplied is exposed unchanged.

It follows that a concrete subclass implementing the container hook must be constructible with no arguments. The public connection, serializer, and deserializer attributes expose the values described above.

Hook for the container class

FactoryBase defines an overridable classmethod:

@classmethod
def _get_container_class(cls) -> Callable[..., <container>]:
    ...

It returns the container class, or other callable, that the factory instantiates. Concrete subclasses override this hook in order to designate the container type they target.

The SequenceFactoryBase class

SequenceFactoryBase is generic over one element type and must be usable as SequenceFactoryBase[T]. It extends FactoryBase[T], inheriting all of its construction, normalization, default-codec, and public-attribute behavior.

create
def create(self, data=None) -> <container instance>:
    ...

data is an optional iterable. The method obtains its target by calling the class's _get_container_class() hook, then invokes the resulting container callable once. That invocation's result is returned unchanged.

How the target is invoked depends on data:

  • When data is not None — including when it is an empty iterable — invoke the target with exactly these keyword arguments:

    data=data,
connection=self.connection,
serializer=self.serializer,
deserializer=self.deserializer

    That same data object is forwarded, without conversion.

  • When data is omitted or explicitly None, invoke the target with exactly:

    connection=self.connection,
serializer=self.serializer,
deserializer=self.deserializer

    In this no-data case, the data keyword must be left out entirely; passing it as data=None must not happen.

Behavior when called

Instances of SequenceFactoryBase and its subclasses are callable. __call__ accepts the same optional data argument, delegates to create, forwards whatever argument is supplied, and returns the result of create. Calling the factory with no argument or with None selects the no-data behavior described above.

Concrete sequence factories

ListFactory

ListFactory is a generic subclass of SequenceFactoryBase, usable as ListFactory[T]. Its _get_container_class() hook designates the indexed/parameterized sqlitecollections List[T] container.

When a list factory is called with data that is not None, the target is constructed with data, connection, serializer, and deserializer, as SequenceFactoryBase specifies. When it is called with no argument or with None, the target is constructed with only connection, serializer, and deserializer, and data is omitted. The List object that is produced is returned.

SetFactory

SetFactory is a generic subclass of SequenceFactoryBase, usable as SetFactory[T]. Its _get_container_class() hook designates the indexed/parameterized sqlitecollections Set[T] container.

When a set factory is called with data that is not None, the target is constructed with data, connection, serializer, and deserializer, as SequenceFactoryBase specifies. When it is called with no argument or with None, the target is constructed with only connection, serializer, and deserializer, and data is omitted. The Set object that is produced is returned.

The DictFactory class

DictFactory is generic over key and value types and must be usable as DictFactory[KT, VT]. It builds on the common factory connection behavior and takes the indexed/parameterized sqlitecollections Dict[KT, VT] container as its target; that target is what its _get_container_class() classmethod returns.

Constructor and codec attributes

The constructor accepts these optional arguments:

def __init__(
    self,
    connection=None,
    key_serializer=None,
    key_deserializer=None,
    value_serializer=None,
    value_deserializer=None,
):
    ...

The behavior is as follows:

  • connection takes None as its default, goes through the module-scope tidy_connection exactly once, and the normalized result is exposed as connection.
  • The public attributes key_serializer and key_deserializer are given by the key_serializer and key_deserializer arguments. If either one is None, it independently falls back to SqliteCollectionBase._default_serializer or SqliteCollectionBase._default_deserializer, respectively.
  • The inherited serializer and deserializer attributes expose the same callables as key_serializer and key_deserializer, respectively.
  • A value_serializer that is not None is exposed unchanged as value_serializer. If it is None, value_serializer defaults to the resolved key_serializer, including any custom key serializer.
  • A value_deserializer that is not None is exposed unchanged as value_deserializer. If it is None, value_deserializer defaults to the resolved key_deserializer, including any custom key deserializer.

As a result, DictFactory may be constructed with no arguments, and all four codec attributes then resolve through the default sqlitecollection codecs.

create

create accepts at most one optional positional data source, followed by arbitrary keyword entries:

def create(self, data=None, **entries) -> Dict[KT, VT]:
    ...

The positional source may be either a mapping or an iterable of (key, value) pairs. Through _get_container_class() the method obtains the indexed/parameterized Dict[KT, VT] target, invokes it once, and returns its result unchanged. Every target invocation includes exactly these common keyword arguments:

connection=self.connection,
key_serializer=self.key_serializer,
key_deserializer=self.key_deserializer,
value_serializer=self.value_serializer,
value_deserializer=self.value_deserializer

The data keyword is decided as follows:

  1. No positional source and no keyword entries: When the positional source is omitted or None and there are no entries, do not pass a data keyword at all.

  2. Keyword entries only: When the positional source is omitted or None and entries are present, pass data=entries, where entries is the dictionary formed from those keyword arguments. As an example, factory(a=1, b=2) supplies data={"a": 1, "b": 2}.

  3. A positional source is present: The source is combined with the keyword entries by means of the module-scope chain callable. When the source is a mapping, the first iterable is data.items(); when it is an iterable of pairs, the first iterable is data itself. The second iterable is always entries.items(). Pass the chained iterable that results as data. In equivalent terms:

    first = data.items() if isinstance(data, Mapping) else data
combined = chain(first, entries.items())

    The positional entries precede the keyword entries. This chaining behavior also applies when the positional source is empty or when there are no keyword entries; in the latter case, the source is combined with an empty dictionary's items view rather than being forwarded directly.

There is no case in which data=None may be passed.

Behavior when called

Instances of DictFactory are callable. __call__ accepts the same optional positional source and keyword entries as create, delegates them to create, and returns the result of create. Accordingly, all of these public forms are supported:

factory()
factory(iterable_of_pairs)
factory(mapping)
factory(a=1, b=2)
factory(iterable_or_mapping, a=1, b=2)

Notes on typing and compatibility

  • Generic type parameters exist for typing only; runtime behavior does not depend on a concrete type argument.
  • Concrete factories select their container by way of the overridable _get_container_class hook. ListFactory, SetFactory, and DictFactory each use the indexed/parameterized form of their corresponding sqlitecollections container.
  • Factories return the object that their target container callable produces and do not add container-construction options that are unrelated.

Task Specification: Adding a keys() Method to the SQL-Backed Dict

Background

The codebase contains Dict, a dictionary-like class; instead of living in memory, its key/value data is stored inside a SQLite table. It can be imported as sc.Dict (sc being the alias under which its package is imported), and the class is generic, parameterized as Dict[KeyType, ValueType].

Instances are built by passing keyword arguments:

sc.Dict[Hashable, Any](connection=<sqlite3.Connection>, table_name="items")

The instance already supports deleting items: performing del parent[key] removes from the backing table the corresponding row.

What you are asked to do is add a keys() method to Dict that returns a keys view object which is live and dict-like, and then implement that view object so that it behaves as specified below.

API to Implement

Dict.keys(self) -> KeysView
  • The method returns a keys-view object whose backing table is the same one that backs the Dict which created it.
  • Whatever object is returned must be an instance compatible with collections.abc.KeysView.
  • This view is live: at query time it always reflects the backing table's current contents, never a snapshot captured when the view was created. Should rows be added to or removed from the underlying table after the view has been created, every subsequent operation performed on the view must observe the current state.

Behavior Required of the Keys View Object

Take view = parent.keys().

Length: len(view)
  • len(view) returns however many key/value entries are stored in the backing table at that moment.
  • Changes to the table that occur after the view was created must be reflected (e.g., when a table grows from empty to 4 rows, len(view) must return 0 then 4 accordingly).
Iteration: iter(view)
  • A fresh Iterator (an instance compatible with collections.abc.Iterator) is what each call to iter(view) returns.
  • Iteration yields the stored keys following the backing table's row order (insertion/stored order).
  • Liveness matters here as well: once the table has changed, a repeat call to iter(view) must produce an iterator that reflects the new contents. As an example: if the keys currently in the table are ["a", "b", "c", "d"], iteration yields them in order; once a key is deleted, an iterator obtained afterwards yields the keys that remain, in order (e.g., ["a", "c", "d"]).
  • Each call to iter(view) begins at the start of the table's current contents.
Membership: key in view / key not in view
  • key in view returns True when the backing table currently contains a key equal to key, and False otherwise. As for key not in view, the logical negation is returned.
  • Membership must account for keys of varied hashable types, including but not limited to: str, bytes, None, int, and nested tuples (e.g., ((0, 1), "a")). When a key is present in the table, it must test as a member; when a key is absent from the table (e.g., 100), it must test as a non-member.
  • Membership is live as well: once a key has been removed from the backing table, that key must test as absent.
  • If the key that gets supplied is not hashable (e.g., a list), TypeError must be raised by the membership test — an error whose message includes the text unhashable type:.
Reversal: reversed(view)
  • For Python 3.8 and later: a fresh Iterator (compatible with collections.abc.Iterator) is returned, and the keys it yields appear in the reverse of their stored order. For instance, take a table whose keys, in stored order, are ["a", "b"]; reversed(view) then yields ["b", "a"].
  • For Python versions older than 3.8: reversed(view) must raise TypeError whose message is 'KeysView' object is not reversible.

Notes and Constraints

  • For an empty table, len returns 0, iteration yields an empty sequence, and membership tests return False.
  • The view must not cache or snapshot table contents; every operation must query the state of the backing table as it currently stands.

Task Specification: Normalizing the Version Guard

In the test/support modules, wherever a branch keyed on the Python version chooses the typing sources, version 3.9 must be treated as falling under the "modern" branch (which uses collections.abc) — that is, the condition is "version is greater than or equal to (3, 9)". Only a boundary correction is involved: when the version is exactly Python 3.9, the collections.abc sources must be the ones used. The only thing this affects is which import source gets chosen, and beyond the correct symbols becoming available on Python 3.9, it introduces no new runtime behavior.

Objective

The keys-view object returned by sqlitecollections.Dict.keys() is to be extended so that it supports set intersection with the binary & operator in either operand position. Every such operation must produce a temporary, SQLite-backed sqlitecollections.Set.

Package background

This is how the package is imported:

import sqlitecollections as sc

sc.Dict is a SQLite-backed, dict-like collection, while sc.Set is a SQLite-backed, set-like collection. Every SQLite-backed collection exposes its backing table's name through table_name.

For example, an existing dictionary may be opened this way:

parent = sc.Dict(connection=connection, table_name="items")
keys_view = parent.keys()

The keys view stays a live view of its parent dictionary. Its existing behavior for len(), iteration, membership testing, and reversed() must stay unchanged. The keys that intersections use are the keys present in the parent at the time the operation is performed.

Public interface

The object returned by sc.Dict.keys() must provide both of the methods below:

keys_view.__and__(other)   # keys_view & other
keys_view.__rand__(other)  # other & keys_view

A new sc.Set is returned by both methods.

Intersection semantics

Keys view as the left operand: keys_view & other
  • other may be any iterable whose elements are hashable Python values, including a built-in set, sequence, generator, or iterator.
  • The set intersection is computed between the parent dictionary's current keys and the values yielded by other.
  • The result contains exactly those values that are present in both inputs. Values that are not present as dictionary keys are omitted.
  • When the intersection is empty, an empty sc.Set is returned — not a built-in set.
Keys view as the right operand: other & keys_view
  • The intersection semantics of this form must be the same as those of keys_view & other.
  • Even when other is an arbitrary one-shot iterator, such as iter(("a", "b")), rather than an object that natively implements &, this form must work.
  • A new sc.Set is returned, including when the result is empty.
New, chainable results
  • Every intersection operation creates a distinct result collection, and the parent dictionary is not mutated.
  • The object that is returned must support the existing sc.Set intersection operator, so chained expressions work:
result = keys_view & {"a", "b"} & {"b"}
  • Each stage of a chain creates a new sc.Set; the final result above contains only "b".
  • The result is subject to set semantics, so each intersecting value is represented at most once.

Database backing and serialization

  • Backing every result is a newly created Set table in the same SQLite database as the parent dictionary.
  • The name of that table is exposed by the result through result.table_name.
  • When the default serializers are in effect, every result value is stored in serialized_value using sc.base.SqliteCollectionBase._default_serializer. Consequently, running the query
SELECT serialized_value FROM <result.table_name>

returns no rows for an empty intersection and otherwise returns exactly the serialized forms of the intersecting dictionary keys.

Deterministic encounter order

The result has set semantics; nevertheless, the insertion and observable backing-row order of matching values must not be produced by re-enumerating an unordered or hash-dependent intermediate set. Matching values must be stored in deterministic encounter order; when the parent dictionary's keys determine the result encounter sequence, its stored key order is preserved (and when an ordered iterable operand is the sequence being consumed, that operand's encounter sequence is preserved). When the result is enumerated, that same encounter order must be retained.

Specifically, if the parent dictionary stores keys in the order "a", "c", "b" and the other operand yields "a" followed by "b", selecting serialized_value from the result table without an ORDER BY clause must yield, in order:

  1. the serialized form of "a";
  2. the serialized form of "b".

The values must not be reordered on the basis of Python hash iteration. No separate sorting requirement is imposed — this is an encounter-order guarantee.

Lifespan and cleanup

Results of intersections are volatile collections:

  • The backing Set tables of such results must not become persistent additions to the parent's database.
  • Once no remaining references to a result exist and it is disposed of, its backing table and its collection metadata must be removed.
  • The same cleanup behavior applies to temporary intermediate Sets created by a chained expression.
  • The table and metadata of the parent dictionary must remain intact. For a parent created as sc.Dict(connection=connection, table_name="items"), after all intersection results are disposed of, the tracked collection tables of the database must again consist solely of the single Dict collection named items.

Examples

import sqlite3
import sqlitecollections as sc

connection = sqlite3.connect(":memory:")
parent = sc.Dict(
    connection=connection,
    table_name="items",
    data=(("a", 1), ("c", 3), ("b", 2)),
)
keys_view = parent.keys()

left_result = keys_view & {"a", "b"}
assert isinstance(left_result, sc.Set)
assert set(left_result) == {"a", "b"}

right_result = iter(("a", "b")) & keys_view
assert isinstance(right_result, sc.Set)
assert list(right_result) == ["a", "b"]

empty_result = iter((1, 2, 3)) & keys_view
assert isinstance(empty_result, sc.Set)
assert len(empty_result) == 0

chained_result = keys_view & {"a", "b"} & {"b"}
assert isinstance(chained_result, sc.Set)
assert set(chained_result) == {"b"}

Task: Implement the __or__ (union) operator for the Dict KeysView

Background

Collection types backed by SQLite are provided by this codebase under a package that can be imported as sc (with a submodule sc.base). The Dict type (sc.Dict[KT, VT]) is a mapping backed by SQLite, constructed using the keyword arguments connection (a sqlite3.Connection) and table_name (a str). A call to .keys() on a Dict returns a keys-view object.

Support for the | (bitwise-or / union) operator must be added to this keys-view object.

Behavior requirements

The Dict keys-view class must be given an implementation of __or__ such that the expression

keys_view | other

returns a new sc.Set instance whose contents are the set-union of:

  • all keys that are currently present in the originating Dict, and
  • all elements obtained by iterating other.
Constraints and details

  • other may be any iterable (the tests pass in one-shot iterators, e.g. iter((1, 2, 3))). Iterating other exactly once in order to collect its elements is sufficient.

  • The value that is returned must be an instance of sc.Set.

  • The resulting sc.Set must contain the union of the Dict's keys and the elements of other, with no duplicates. The elements' types may be heterogeneous (e.g. strings and integers).

  • The serialization applied to the stored elements must use the same serialization mechanism as the rest of the library, meaning that the values stored in the resulting Set's backing table are exactly the ones produced by sc.base.SqliteCollectionBase._default_serializer(element).

  • The sc.Set that is returned must be backed by its own table (accessible through its table_name attribute) within the same underlying database connection as the originating Dict.

  • The operation must not create any extra persistent tables in the shared database beyond the originating Dict's items table once the resulting Set is discarded. Put differently, the resulting Set must own a temporary/managed table, and that table is cleaned up when the Set object is deleted (garbage-collected), leaving only the original Dict's backing table behind.

  • The operation leaves the originating Dict and its keys unaffected; the same keys-view may be used in multiple | operations independently, with each one producing an independent Set.

Semantics by example

Suppose a Dict has the keys "a", "b", "c":

  • keys_view | iter((1, 2, 3)) yields a sc.Set that contains "a", "b", "c", 1, 2, 3.
  • keys_view | iter(("a", "b")) yields a sc.Set that contains "a", "b", "c" (with duplicates collapsed).

Public API

  • sc.Dict[KT, VT](connection=..., table_name=...) — the existing constructor (already available).
  • sc.Dict.keys() — returns the keys-view (already available).
  • The keys-view class must implement __or__(self, other), which returns an sc.Set.
  • sc.Set — the type of the returned value, exposing a table_name attribute.
  • sc.base.SqliteCollectionBase._default_serializer(value) — the existing serializer (already available).

Background

The public API involved

  • sc.Dict[KeyType, ValueType](connection=..., table_name=...) — an existing collection that behaves like a dict. It is constructed with an SQLite connection and a table name. Calling .keys() on the instance returns the keys-view object.
  • The keys-view object must implement a __ror__ method such that other | keys_view is evaluated as keys_view.__ror__(other) when other is a plain iterable (e.g. the result of iter(...)).
  • sc.Set — the type of the result of the operation described below (an existing collection type that is set-like). The returned object exposes a .table_name attribute that names its backing SQLite table.

Behavior required of __ror__

Assume a keys-view sut over a dict whose keys are, in some order, "a", "c", "b", and an iterable other. The expression:

other | sut

must:

  1. Return a new instance of sc.Set.
  2. The set that is returned must contain the union of:
    • all keys that are currently present in the underlying dict (the keys viewed by sut), and
    • all elements yielded by iterating other.
  3. Duplicate elements (an element that appears both in other and among the keys) must appear only once in the result.
  4. The values that are stored in the resulting set are serialized with the project's default serialization (the same serialization that is used for elements elsewhere in the library). To be concrete, for each distinct element e in the union, the backing table of the returned set contains one row whose serialized value is equal to sc.base.SqliteCollectionBase._default_serializer(e).
Examples showing the union semantics

If sut views the keys "a", "b", "c":

  • The expression iter((1, 2, 3)) | sut yields a sc.Set whose elements are {"a", "b", "c", 1, 2, 3}.
  • The expression iter(("a", "b")) | sut yields a sc.Set whose elements are {"a", "b", "c"} (overlapping elements do not get duplicated).

Constraints

  • Once the resulting set object is discarded (deleted), the operation must not leave behind any auxiliary/persistent tables in the database beyond the original items table. While the result object is alive, creating the result set may allocate its own backing table, but after the result is deleted, only the original dict's table must remain.
  • It is sufficient to iterate other a single time in order to gather its elements; other may be a one-shot iterator.

Element types

The keys may be arbitrary hashable values, and other may likewise yield arbitrary hashable values (integers, strings, etc.); the union combines them with no type restriction beyond hashability/serializability.

Requirement

Extend the Dict items-view type with support for the subtraction operator (__sub__), implementing set-difference semantics.

Signature / API surface

The items-view object that sc.Dict.items() returns must support:

result = items_view - other

where other is any iterable yielding 2-tuples (e.g., a plain iterator over (key, value) pairs).

Behavior

items_view - other must:

  1. Return a new instance of sc.Set (an instance of sc.Set), with the result populated into its backing table.

  2. The result set contains exactly the (key, value) pairs that are present in the items-view and not present in other. To compute the set difference, each dictionary entry is treated as a (key, value) 2-tuple and each element of other is treated as a (key, value) 2-tuple; an item-view entry is excluded from the result if and only if an equal (key, value) 2-tuple appears in other.

    • Membership comparison is based on full pair equality: a pair is removed only when both its key and its value match a pair in other. A pair whose key matches while its value differs is retained.

  3. Each element stored in the resulting sc.Set is the 2-tuple (key, value). For each element, the serialized form stored is the default serialization of a Python tuple whose two components are the default serializations of the key and value respectively — that is, equivalent to:

    _default_serializer(
    (_default_serializer(key), _default_serializer(value))
)

    where _default_serializer refers to sc.base.SqliteCollectionBase._default_serializer.

Error condition

When any value in the items-view is not hashable, the subtraction operation must raise TypeError, with a message matching the standard Python form unhashable type: '<typename>' (e.g. unhashable type: 'list').

Resource behavior

The resulting sc.Set has a backing table of its own. Once the result object is deleted, its backing table must be cleaned up such that afterward only the original items table remains in the database.

Example

For a dict whose items are ("a", 4), ("b", 4), ("c", 4):

  • items - iter((("a", 1), ("b", 2), ("c", 3))) → a sc.Set containing ("a", 4), ("b", 4), ("c", 4) (none of them removed; the values differ).
  • items - iter((("a", 4), ("b", 0))) → a sc.Set containing ("b", 4), ("c", 4) (("a", 4) removed because it is an exact pair match).

For a dict that contains an entry whose value is a list (unhashable), items - iter((("a", 1),)) must raise TypeError matching unhashable type: '<typename>'.

Task: Add __rsub__ and __xor__ to the Dict ItemsView

Background

This project provides collection classes backed by SQLite under a package imported as sc. A Dict[KT, VT] class (sc.Dict) is constructed from a SQLite connection plus a table_name, e.g.:

parent = sc.Dict[Hashable, Any](connection=memory_db, table_name="items")

Calling parent.items() returns an items-view object (similar to dict.items()); it yields the (key, value) pairs stored in the underlying table.

The package additionally exposes:

  • sc.Set — a set class backed by SQLite. Instances have a .table_name attribute that names their backing table.
  • sc.base.SqliteCollectionBase._default_serializer(obj) — a static/class method that serializes an arbitrary Python object into the byte representation used when values are persisted.

The items-view class already has support for __sub__ (view - other). Two new binary operators must be added to that same items-view class.

Behavior Requirements

Let sut denote the object returned by parent.items(). It stands for the set of (key, value) pairs currently present in the Dict.

1. __rsub__ — other - sut

Provide support for the reflected subtraction operator, so that an arbitrary iterable of pairs placed on the left side of - can be subtracted by the items view.

  • The items view sut is the right operand. The left operand (other) is any iterable yielding 2-element items (pairs), a plain iterator included (e.g. iter((("a", 1), ("b", 2), ("c", 3)))).
  • The result is the set of items found in other but not present in sut (the set difference other - sut), compared by pair equality.
  • The result MUST be a newly created sc.Set instance (isinstance(result, sc.Set) is true).
  • The surviving pairs themselves are the elements stored in the resulting sc.Set. Each stored element is a pair (key, value) whose persisted serialized value is _default_serializer((key, value)) — i.e. the whole pair is serialized as a single object.
  • The pair as a whole governs membership/difference: a pair coming from other is excluded only if an equal (key, value) pair exists in sut. A pair whose key matches but whose value differs is kept.

Example: suppose sut contains ("a", 4), ("c", 4), ("b", 4). Then:

  • iter((("a", 1), ("b", 2), ("c", 3))) - sut yields a set with all three of ("a", 1), ("b", 2), ("c", 3) (none of them match by full pair).
  • iter((("a", 4), ("b", 0))) - sut yields a set with only ("b", 0) in it (("a", 4) matches a pair that is already present and is dropped).

Error condition: If any value in sut is unhashable (for instance, a value that is a list), the operation MUST raise TypeError with a message that matches unhashable type: '<typename>' (the standard Python unhashable-type message). This holds even when the left operand is a small/simple iterable.

2. __xor__ — sut ^ other

Provide support for the symmetric-difference operator.

  • The items view sut is the left operand. The right operand (other) is any iterable yielding 2-element items (pairs), a plain iterator included.
  • The result is the symmetric difference: the pairs that are in exactly one of sut / other (compared by full (key, value) pair equality).
  • The result MUST be a newly created sc.Set instance (isinstance(result, sc.Set) is true).
  • Each element that is stored in the resulting sc.Set is a pair. Important: for __xor__, each element pair is stored as a 2-tuple in which each of the two members is already serialized, i.e. the stored element is (_default_serializer(key), _default_serializer(value)), and the persisted serialized value of that element is _default_serializer((_default_serializer(key), _default_serializer(value))).

Example: suppose sut contains ("a", 4), ("c", 4), ("b", 4). Then sut ^ iter((("a", 4), ("b", 4), ("c", 3))) yields a set with exactly the two pairs ("c", 4) and ("c", 3) (("a", 4) and ("b", 4) occur on both sides and cancel out). These are stored in the doubly-serialized pair form described above.

Cleanup and Side-Effect Requirements

Both operations create a new backing sc.Set (with a table of its own). When a result object of this kind is deleted (its __del__/garbage collection), its backing table MUST be dropped, with only the original items table remaining in the database. Producing the result must not leave stray tables behind after the result has been disposed of.

API Surface to Provide

On the class of the items view returned by sc.Dict(...).items():

  • __rsub__(self, other: Iterable) -> sc.Set — the implementation of other - view.
  • __xor__(self, other: Iterable) -> sc.Set — the implementation of view ^ other.

Both accept any iterable of 2-element pairs (bare iterators included) and return a freshly created sc.Set.

Task: Implement __xor__ and __rxor__ for the ItemsView of the Dict Class

Background

Included in the codebase is a Dict class — a mapping that is persistent and backed by SQLite — and the .items() method of this class returns an items-view object. Acting as a set of (key, value) pairs, this items-view object offers set-style symmetric-difference operations that work against other iterables. You must implement/adjust the reflected symmetric-difference operation (__rxor__); you must also ensure that the forward symmetric-difference operation (__xor__) deals with a specific error case.

Public API Surface

The following are already provided by the package (the top-level package is referred to here as sc):

  • sc.Dict[K, V](connection=<sqlite3.Connection>, table_name=<str>) — creates a SQLite-backed dictionary bound to the connection and table that are supplied.
  • <Dict>.items() — returns the items-view object that is being tested.
  • sc.Set — a SQLite-backed set type. Any result object returned by the symmetric-difference operations must be an instance of this type.
  • sc.base.SqliteCollectionBase._default_serializer(obj) — the callable that is used by default to serialize values for persistence.

You must ensure that the Python binary operator ^ is supported by the items-view object in both operand positions:

  • items_view ^ other (the forward direction, __xor__)
  • other ^ items_view (the reflected direction, __rxor__)

In both expressions, other denotes any iterable whose elements are two-element (key, value) pairs (one-shot iterators included).

Required Behavior

Symmetric-difference operation (__rxor__)

Whenever the items-view sits on the right-hand side of ^ while the left-hand operand is an iterable that yields two-element (key, value) tuples:

  • The outcome is a set-theoretic symmetric difference of two sets: the set of (key, value) pairs held by the items-view, and the set of (key, value) pairs that comes out of iterating the other operand. A pair is part of the result exactly when it is present in one operand but not in both.
  • Each pair counts as a single hashable element (the entire pair), in keeping with the semantics of ordinary set symmetric difference over (key, value) tuples.
  • What the operation returns must be an instance of sc.Set.
  • The elements of the returned Set must be persisted by way of the default serializer. Each element that gets stored is a 2-tuple in serialized form; its components are produced by serializing the key and the value individually — i.e. _default_serializer((_default_serializer(key), _default_serializer(value))).
  • The other operand may be a one-use iterator, and it must be consumed correctly.
  • Computing the result must not change the underlying items table of the source Dict; after the operation finishes and the result is disposed of, what remains is only the original items table content.

Example: suppose the items-view contains the pairs ("a", 4), ("c", 4), ("b", 4). The expression iter((("a", 4), ("b", 4), ("c", 3))) ^ items_view then yields a Set that contains exactly the pairs ("c", 4) and ("c", 3) (the pairs on which the two operands differ).

Error case when values are unhashable (both __xor__ and __rxor__)

If, while the symmetric difference is being computed, a (key, value) pair drawn from the items-view has a value that is not hashable (e.g. a list), the operation must raise TypeError, and the message must match the pattern unhashable type: '<name>' (where <name> is the name of the offending type).

This requirement is symmetric:

  • items_view ^ other must raise this TypeError whenever the items-view holds an unhashable value.
  • other ^ items_view must raise this TypeError whenever the items-view holds an unhashable value.

In both of these error scenarios, the other operand is a small iterable/iterator of (key, value) pairs.

Constraints

  • The scope covers only the behavior described above. Do not add other operators, methods, or side effects.
