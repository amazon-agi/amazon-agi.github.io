Task Specification: Codec for Parallel Composition

Goal

Create a new codec constructor function called parallel in the craystack core module. The function brings multiple independent codecs together so that they operate on disjoint views (slices) of a single message head.

Public API

The function must be available as craystack.parallel (that is, importable from the top-level craystack package, which is conventionally aliased as cs).

Function Signature
parallel(codecs, view_funs)
  • codecs: a list of codec objects. Each codec is a (push, pop) pair that follows the existing craystack codec convention.
  • view_funs: a list with the same length as codecs. Each element is a function which, when given a message head, returns the sub-view of that head on which the corresponding codec should operate.

The two lists line up by position: codecs[i] operates on the view that view_funs[i] produces.

Codec Convention (background)

A codec consists of a pair (push, pop):

  • push(message, data) encodes data into message and returns the updated message.
  • pop(message) decodes from message and returns a (message, data) pair.

The "head" of a message is the structured array-like object that codecs read from and write to. A view_fun pulls out a portion of the head (e.g., via slicing) so that a given codec only sees and modifies its assigned region.

Behavior Requirements

parallel(codecs, view_funs) must return a single codec (push, pop) such that:

  1. Directs each constituent codec at its own view of the head. During a push or a pop, codecs[i] must interact only with the portion of the head that view_funs[i] selects. The views are disjoint slices which, taken together, partition the head.

  2. Works on lists of data. The combined codec encodes/decodes a list of data items, one per constituent codec, matched by position: item i is handled by codecs[i] on view i.

  3. Behaves as a correct codec (round-trip property). Given any valid list of data items, a push of the data followed by a pop must recover:

    • the original message state, and
    • the exact original list of data items (element-wise equal).

    Symmetrically, the resulting pop followed by push must be consistent, as is required for any well-formed craystack codec.

Concrete Usage Scenario (for grounding)

The combined codec must work under these conditions:

  • Each constituent codec is a uniform-distribution codec over a fixed precision (it encodes integers uniformly across the range [0, 2**precision)).
  • Each view_fun picks a contiguous slice of a flat head whose total size is equal to the sum of the individual segment sizes.
  • The data is a list in which item i is an array of unsigned 64-bit integers with length equal to segment i's size, holding values in [0, 2**precision_i).

When these conditions hold, encoding the full list of arrays into an initialized message and then decoding must return the original message and the original list of arrays unchanged.

Notes

  • Do not impose any constraints beyond those above; the count of codecs, the segment sizes, and the precisions are arbitrary and supplied by the caller.
  • The function exists only to compose the given codecs and views; it does not itself define distributions or precisions.

The Codec Protocol and Its Round-Trip Contract

Every interface required below — the two serialization helpers excepted — is either a constructor that produces a codec or, where Benford64 is concerned, a codec that has already been constructed. A codec takes the form of the pair (append, pop) and obeys the following protocol:

  • append(message, data) -> message_ encodes the given data into message.
  • pop(message_) -> (message, data) strips off the data that was appended most recently and decodes it.

By a message, a (head, tail) state is meant — one that is compatible with craystack.vectorans (frequently imported as vrans), states set up through vrans.x_init(head_shape) included. The shape that codec data must have is the one that the corresponding message head, or the selected head view, expects.

Whenever the input is valid, appending it and then popping must:

  1. bring back the same data values and the same shape, and
  2. restore, exactly, both the head and the tail of the original message.

For symbols, the standard dtype is numpy.uint64. If valid input data arrive as uint64, the round trip must keep that dtype intact. On top of this, AutoRegressive and DiagGaussianLatent are subject to the signed-integer acceptance requirements described in their own sections below.

The Codec APIs That Are Required

Uniform(precision)

Return a codec for integer symbols spread uniformly across {0, 1, ..., 2**precision - 1}. The bit-width with which the integer coding is done is precision. The data are arrays of uint64 whose values fall inside that range and whose shape matches the message head concerned.

Benford64

Benford64 is to be exposed as a codec value that has already been constructed — not as a factory that must be called.

The codec is Benford-like and self-delimiting, and it handles uint64 values satisfying 2**31 <= x < 2**63. Put differently, the highest set bit occupies a position running from 31 through 62, so bit lengths range from 32 through 63. Arrays made up of values of this kind must round-trip through it, across arbitrary supported head shapes.

Bernoulli(p, precision)

Return a Bernoulli codec. The probabilities are held by the array p, one apiece for the elements of the head shape, and p gives P(symbol == 1). The bit-width of the integer coding is precision. The data are uint64 values out of {0, 1}, carrying the same elementwise shape as p and the message head.

Categorical(probs, precision)

Return a categorical codec covering K categories. Along its trailing dimension, probs has size K; along that dimension, each vector makes up a normalized probability distribution. Matching the head shape is the role of the leading dimensions. The bit-width of the integer coding is precision.

Integer indices of categories — values in {0, ..., K - 1} with shape probs.shape[:-1] — are what the data consist of. Appending and popping must bring those indices back exactly.

Logistic(means, log_scale, precision)

Return a codec for a discretized logistic distribution over the 256 symbols {0, ..., 255}. One mean for every element of the head shape is what means supplies. As for log_scale, it carries the logarithm of the scale parameter, and it may be a shared scalar. The bit-width of the integer coding is precision. The data are uint64 arrays whose symbols belong to the 256-value alphabet.

LogisticMixture(theta, precision)

Return a codec that handles a mixture of discretized logistic distributions over the 256 symbols {0, ..., 255}.

Given K mixture components, three blocks — consecutive, each of size K — make up the trailing dimension of theta, arranged in exactly this order:

  1. component means,
  2. component log-scales, and
  3. component mixture logits.

The size of the final dimension is therefore 3 * K; which head elements get coded independently is indicated by the leading dimensions. The bit-width of the integer coding is precision. The data are uint64 arrays whose symbols lie in {0, ..., 255}.

AutoRegressive(get_params, data_shape, params_shape, elem_idxs, elem_codec)

Return a codec for a data array that is complete and autoregressively structured, coded a single indexed element group at a time.

The parameters:

  • The parameter array is obtained, while coding proceeds, through get_params, a callable. Both styles of use must be supported by it: with the complete data during encoding, and with data only partly decoded during decoding; the parameters it returns must have params_shape. It may be invoked with the data and with the autoregressive context that suits the group being coded at the time.
  • data_shape gives the shape of the array that gets coded in full.
  • params_shape gives the shape of the full parameter array returned by get_params.
  • elem_idxs is an ordered sequence of index expressions of the NumPy-compatible kind. One successive group of elements is pinpointed by each index, which can also be used for selecting the group it corresponds to out of the data array and the parameter array. That ordering doubles as the autoregressive decoding order.
  • elem_codec gets called as elem_codec(params, idx) -> (append, pop), params being the slice of the parameters belonging to idx. It returns the codec that handles that element group.

The head shape of the codec matches the leading batch dimension that every element index selects. The entire array in data_shape must be reconstructed by it — all of the groups recovered in the sequence elem_idxs specifies — and the original message must be restored.

As well as uint64 data, a complete data array of valid, nonnegative integers produced with NumPy's default signed integer dtype must also be accepted by this codec. Such signed input must not be rejected merely on the grounds that it is signed: passed through the element codecs that constitute it, its shape and its numerical values must round-trip exactly. Keeping the dtype of signed input is not required; the decoded representation may be in uint64.

DiagGaussianLatent(means, stdds, bin_means, bin_stdds, coding_precision, bin_precision)

Return a codec for a latent variable of the diagonal-Gaussian kind, represented by way of indices into a grid of Gaussian bins.

  • For each element of the head, means and stdds supply the mean and the standard deviation of the Gaussian being coded.
  • bin_means and bin_stdds define the Gaussian grid whose quantile bins discretize the latent.
  • The bit-width of the integer entropy coding is coding_precision.
  • The number of bins is determined by bin_precision: the valid bin indices number 2**bin_precision.

The data consist of arrays of bin indices — nonnegative integers, values inside {0, ..., 2**bin_precision - 1}. The Gaussian parameters may be given per element, or in forms that broadcast over the head shape.

Both uint64 bin indices and valid bin-index arrays created with NumPy's default signed integer dtype must be accepted by this codec. Signed input must not be rejected merely on account of its dtype; moreover, its shape and its numerical index values must round-trip exactly. Keeping the dtype of signed input is not required; the decoded representation may be in uint64.

Serialization of Benford Messages

flatten_benford(message) -> numpy.ndarray

The input here is a (head, tail) message of the Benford-compatible kind, and the output is that message serialized into a NumPy array that is flat and one-dimensional. The array that comes back must have numpy.uint32 as its dtype.

unflatten_benford(flat, shape) -> message

A message is put back together from a uint32 array in flat form plus the shape that the head had originally. For messages that are valid, this function acts as the inverse of flatten_benford. Suppose m is a message of that sort and flat = flatten_benford(m); the message reconstructed as m_ = unflatten_benford(flat, shape) must then satisfy all of the conditions that follow:

  • The head shape that was requested is the one m_ has.
  • Element for element, m_.head is equal to the original head.
  • m_.tail equals the tail of the original message.
  • flatten_benford(m_) is identical to flat, element for element, and it stays a one-dimensional uint32 array.

In this setting, m_.head and m_.tail name the first and second entries, respectively, of the message tuple.

A message is the abstract state that ANS-style codecs manipulate. A message consists of a head and a tail; it can be created empty, populated by pushing data, and consumed by popping data.

Task Description

Goal

A public helper function, message_equal, is to be added to the craystack.rans module. Its job is to compare two rANS messages and decide whether they are equal both in structure and in value.

Context

Within this codebase, a rANS message has the form of a two-element structure, (head, tail):

  • the head part is a NumPy array.
  • the tail part is a nested, linked-list-style construction put together from pairs, which ends in an empty/falsy value. Every tail that is not empty is itself a pair (element, rest_of_tail), with element being a value (for instance a NumPy array or a scalar) and rest_of_tail being whatever remains of the tail (once more, either a pair or an empty terminator).

API to Implement

The following function is to be implemented within the module craystack.rans:

def message_equal(message1, message2):
    ...
Behavior

A call to message_equal(message1, message2) returns a value which evaluates as truthy if the two messages are equal, and as falsy if they are not. The conditions below define equality between two messages:

  1. Both messages have head arrays that are element-wise equal.
  2. Both messages have tail structures of the same length (an equal number of elements), and for each pair of corresponding elements, the two elements are equal (array elements being compared element-wise).

When two messages are structurally identical, carry head arrays that are equal, and hold tail elements that are equal and in corresponding order, the comparison must come out equal. If they differ in head values, in tail element values, or in tail length, the comparison must come out not-equal.

In a boolean assertion context, the result must be directly usable (i.e., assert message_equal(a, b)).

Remarks

This function is meant for round-trip verification: it confirms that operations which first transform a message and afterwards invert that transformation (for example resizing/reshaping the head, or flattening/unflattening) end up with a message equal to the original. It must be able to correctly handle messages with multi-dimensional arrays as heads and with tails containing zero or more elements.

No public behavior other than this is required.
