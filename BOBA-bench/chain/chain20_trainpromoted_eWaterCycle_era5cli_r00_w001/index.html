A helper named initialize(...) must be importable in the execution environment, and it must construct an instance of the fetch class and return that instance. A call to initialize() with no arguments must succeed and return a working object.

The helper must accept at least the following optional keyword arguments:

  • variables: a list of strings naming variables, such as ['total_precipitation', 'runoff'].
  • years: a list of years as integers, such as [2007, 2008, 2009].
  • split: a boolean that controls whether output is split by year.
  • period: either 'hourly' or 'monthly'; hourly is the default.
  • ensemble: a boolean that selects ensemble members instead of reanalysis; True is the default used by initialize().
  • statistics: an optional boolean that controls hourly ensemble statistics.
  • synoptic: an optional boolean that controls monthly averages by hour of day.
  • outputformat: the output format for the request; its default is 'netcdf'.

Task Specification: Configuration and Key Management for era5cli

Summary

A configuration and key management subsystem is to be implemented for era5cli; its role is to store and validate the credentials (URL, UID, and key) required for access to the Copernicus Climate Data Store (CDS) API. Integration with the CLI and with the existing data-fetching component is required.

Module to Create: era5cli/key_management.py

A module named era5cli.key_management is to be created; its public API is the following.

Module-Level Attributes
  • ERA5CLI_CONFIG_PATH: a path object that refers to the era5cli configuration file. This value must be patchable/overridable at runtime (the name sits at module level).
  • CDSAPI_CONFIG_PATH: a path object that refers to the .cdsapirc configuration file. This value must be patchable/overridable at runtime (the name sits at module level).
Exception Classes
  • InvalidLoginError: an exception class that gets raised when CDS credentials are rejected/invalid, or when no valid CDS login can be found.
  • InvalidRequestError: an exception class for the case where a login attempt succeeds at the authorization level but the test request behaves unexpectedly (see attempt_cds_login).
Functions
load_era5cli_config() -> tuple[str, str]

The era5cli configuration file located at ERA5CLI_CONFIG_PATH is read by this function.

Three lines make up the file, each of the form label: value:

url: <url>
uid: <uid>
key: <key>

The return value is a 2-tuple (url, fullkey):

  • url: the value taken from the url line.
  • fullkey: the string that results from joining the uid and key values with a colon: "<uid>:<key>".

Example: when the file contains

url: b
uid: 123
key: abc-def

the result must be ("b", "123:abc-def").

attempt_cds_login(url: str, fullkey: str) -> bool

Validation of a set of CDS credentials is attempted here by means of a cdsapi.Client constructed with the given url and fullkey. The function must:

  1. Make a call to the client's status() method. If a requests.exceptions.ConnectionError comes out of that call, a requests.exceptions.ConnectionError whose message contains the text Failed to connect to CDS must be re-raised.
  2. Otherwise, a test data retrieval is performed through the client's retrieve() method, and the outcome is interpreted as follows:
    • If the exception raised by retrieve() has a string representation containing 401 Authorization Required, InvalidLoginError is raised with a message containing Authorization with the CDS served failed.
    • If the exception raised by retrieve() has a string representation containing There is no data matching your request, InvalidRequestError is raised with a message containing Something changed in the CDS API.
    • When retrieve() finishes without raising, True is returned.
write_era5cli_config()

The era5cli credentials are written to ERA5CLI_CONFIG_PATH by this function. (The signature/parameters are not exercised directly; the function is invoked as a side effect of CLI config handling and via check_era5cli_config when copying from .cdsapirc.)

If the .cdsapirc file is where the credentials come from (see check_era5cli_config), the era5cli config file produced must contain exactly these three lines (with trailing newlines):

url: a
uid: 123
key: abc-def

Concretely, starting from a .cdsapirc file with these contents:

url: a
key: 123:abc-def

the url value carries over unchanged, while the .cdsapirc key value (of the form <uid>:<key>) is split on the colon into a separate uid line and key line.

check_era5cli_config()

The function ensures that a valid era5cli configuration is available. Its behavior:

  1. When an era5cli config file already exists at ERA5CLI_CONFIG_PATH (and is valid), its credentials are validated via attempt_cds_login; once that validation passes, the function completes without an error.
  2. When the era5cli config file is absent but a .cdsapirc file is present at CDSAPI_CONFIG_PATH:
    • attempt_cds_login is used to validate the credentials found in the .cdsapirc file.
    • Should those credentials be invalid (i.e., attempt_cds_login raises InvalidLoginError), InvalidLoginError is raised with a message containing No valid CDS login found.
    • When the credentials are valid, the user is prompted (via input()) on whether the .cdsapirc credentials should be copied into the era5cli config:
      • With a "Y" response from the user, the credentials are written to the era5cli config file (format as given under write_era5cli_config above) and the function completes without an error.
      • With a "N" response from the user, InvalidLoginError is raised with a message containing No valid CDS login found.

The import of key_management must be set up in the module so that era5cli.fetch.key_management.load_era5cli_config is a valid reference (i.e., from era5cli import key_management or equivalent, accessed as key_management within the fetch module).

Integration Into era5cli/cli.py

New config Subcommand

A config subcommand must be added to the CLI argument parser. This subcommand accepts two options:

  • --uid <value>: parsed into a uid attribute (string).
  • --key <value>: parsed into a key attribute (string).

As an example, the invocation config --uid 123456 --key abc-def must produce parsed args with args.uid == "123456" and args.key == "abc-def".

Execution of the config Subcommand

Running the parsed config command proceeds as follows:

  1. The supplied credentials are validated by calling era5cli.key_management.attempt_cds_login.
  2. If that validation succeeds, the credentials are persisted by calling era5cli.key_management.write_era5cli_config.
  3. If that validation fails (i.e., attempt_cds_login raises InvalidLoginError), a message containing the text below is printed to standard output:
    Error: the UID and key are rejected
    Handling of this failure must be graceful (no unhandled exception propagates out of execution).

These functions must be referenced by the CLI as era5cli.key_management.attempt_cds_login and era5cli.key_management.write_era5cli_config, so that they can be substituted at runtime.

Only its first colon is used when splitting full_key. Given the pair ("https://www.test.org/", "123:abc-def"), the output contains exactly:

Contents of .config/era5cli.txt:
    uid: 123
    key: abc-def
    url: https://www.test.org/

A mix of --show with UID or key raises InputError. Supplying just one of UID and key also raises InputError. This may occur during parsing or during execution, but _parse_args() followed by _execute() must reject every such combination. When both UID and key are given, the existing credential validation and configuration writing are retained. Rejected credentials print a message that contains Error: the UID and key are rejected.

5. Validation of request size

TooLargeRequestError is defined in era5cli._request_size. At construction time, Fetch validates the size of every request it plans to submit. If any request that is otherwise resolvable exceeds the applicable limit, construction raises TooLargeRequestError before retrieval.

Calculation for one request

Validation covers one actually submitted request, not the workload as aggregated. For a single request and a single variable:

field_count = years_in_request
              * months_in_request
              * day_count
              * hour_count
              * pressure_level_count
  • When merge=False, years_in_request is 1; when merge=True, it is the number of selected years.
  • When months are not split, months_in_request is the number of selected months; with splitmonths=True, it is 1 for each generated request.
  • day_count is the number of selected days for hourly data and 1 for monthly data.
  • hour_count is the number of selected hourly or synoptic hours.
  • pressure_level_count is the number of levels when the variable resolves to a pressure-level dataset, and 1 for surface, single-level, and ERA5-Land requests.

Variables go out separately and do not multiply the size of one request. Likewise, ensemble selection and the total output count do not stand in for this dimensional calculation. Because their combination is rejected outright (section 6), merge and splitmonths never combine in a size computation.

The maximum amounts to 1,000 fields for each ERA5-Land request and 100,000 fields for each non-land ERA5 request, single- and pressure-level datasets included. A request sitting exactly at its maximum is allowed; only a request that is strictly larger raises.

Consequences that are required include:

  • An unsplit hourly ERA5-Land request for skin_temperature covering a full year has 12 * 31 * 24 = 8,928 fields and is too large.
  • A monthly ERA5-Land request for snow_cover covering a full year at one hour has 12 * 1 * 1 = 12 fields and is valid.
  • When the hourly land case is split by month, each request comes to 1 * 31 * 24 = 744 fields and is valid.
  • A one-month hourly pressure-level request using all 37 levels has 1 * 31 * 24 * 37 = 27,528 fields and is valid.
  • Its full-year counterpart has 12 * 31 * 24 * 37 = 330,336 fields and is too large.
  • A merged, two-year, full-year hourly non-land single-level request has 2 * 12 * 31 * 24 = 17,856 fields and is valid.

Size checking must not mask a dataset selection that is invalid in its own right. A size can be computed only once dataset resolution is possible, so size validation applies only to selections whose dataset resolves. Combinations that request resolution itself rejects — for example ERA5-Land with the preliminary back extension — raise their existing ValueError during request resolution or building rather than TooLargeRequestError, and selections whose errors are deferred under section 6 (unknown variable names, for instance) keep those deferred errors instead of failing the size check.

6. Construction of Fetch and validation timing

Fetch keeps its existing constructor parameters — years, months, days, hours, variables, outputformat, outputprefix, period, ensemble, and the optional area, statistics, synoptic, pressurelevels, merge, threads, prelimbe, and land — and gains an optional splitmonths keyword that defaults to False, so call sites that already exist and omit it keep working. All of these parameters are addressable by keyword.

Construction reads the stored CDS credentials by way of key_management.load_era5cli_config(), so replacing that function gives control over the URL and key that a Fetch instance uses.

Normalization of attributes

At construction, the selection is normalized and stored on the instance:

  • months turns into a list of zero-padded two-character strings, for instance ['01', ..., '12'].
  • For hourly requests, days turns into the zero-padded strings ['01', ..., '31']; passing days=None for an hourly request raises TypeError.
  • For monthly requests, days is None no matter the input, and construction with days=None succeeds.
  • hours turns into HH:00 strings, such as ['00:00', ..., '23:00'].
  • variables, outputformat, outputprefix, period, ensemble, statistics, synoptic, merge, threads, prelimbe, land, and area stay readable with the values supplied, and the pressurelevels argument is stored as pressure_levels, with the literal "surface" selection included.
Errors raised at construction time

The constructor itself must raise — ahead of any retrieval, request submission, or explicit call to fetch or to build a request — in exactly these situations:

  • Merging and month splitting exclude each other. When Fetch is constructed with both merge=True and splitmonths=True, the ValueError raised has a message containing the phrase are not compatible.
  • Pressure levels that are required are validated immediately. When any selected variable resolves to a pressure-level dataset, the pressure-level selection must be present, and every level must be one of the supported values in era5cli.inputref.PLEVELS. A selection that is missing (pressurelevels=None with, for example, temperature) or any unsupported level (for example [1, 2, 9]) raises ValueError out of the constructor.
  • Requests that are too large raise TooLargeRequestError, as section 5 describes.
  • Values of area that are invalid (see section 9) raise ValueError no later than request building and may already surface during construction-time validation.
Errors that stay deferred

This early validation covers required pressure levels only; it does not move every compatibility check into construction. Construction must succeed, without raising, for:

  • variable names that are unknown, such as "unknown";
  • variables that exist hourly but are unavailable in the selected monthly dataset;
  • an outputformat that is not recognized, such as "unknown";
  • land-only variables without land=True, non-land variables with land=True, and land=True combined with prelimbe=True.

In these cases, the corresponding ValueError shows up only later: when the request is built, when fetch() is invoked, or — for the output format — when the extension is resolved via _extension().

7. Generation and execution of requests

For each unit listed below, Fetch.fetch(dryrun=False) plans one request and one output file. What fully determines its cardinality is variables, years, merge, and splitmonths; turning ensemble on or off does not change the number of requests:

  • With merge=False and splitmonths=False: exactly one request per selected variable and year; each request carries the full selected month list.
  • With merge=True (which necessarily means splitmonths=False): exactly one request per selected variable, covering all selected years.
  • With splitmonths=True (which necessarily means merge=False): exactly one request for every combination of selected variable, year, and month; each such request contains only that single month, and its output filename carries the YYYY-MM year-month specification from section 8.

By way of example, two variables with three years give 6 requests when neither split nor merged, 2 requests when merged, and 2 * 3 * 12 = 72 requests when all twelve months are selected and splitmonths=True.

Under dryrun=True, nothing is submitted and nothing is downloaded. Instead, every planned request is printed to standard output — the resolved dataset name, the request dictionary, and the output filename together on one line per request — with the count and content unaltered relative to what a real run would submit. Each printed request dictionary carries its product_type entry exactly once whenever the dataset takes one.

Without dryrun, each request prints the existing queueing message, is submitted to the CDS API with the stored URL and key, downloads into its output filename, and appends the history entry from section 11 to the netCDF output. Downloads may run in parallel: threads determines the number of worker threads, and threads=None uses the default pool. After successful dry-run and retrieval paths, Fetch.fetch() returns None.

8. Extensions and file names

Fetch._extension() can be called before the filename is defined. It sets self.ext to "nc" for netCDF and to "grb" for GRIB, case-insensitively. Any other format raises ValueError.

_define_outputfilename(variable, years, month=None) uses this pattern:

<prefix>_<variable>_<yearspec>_<period>[<area>][_ensemble][_statistics][_synoptic].<ext>
  • The prefix comes from outputprefix, or from <outputprefix>-land for ERA5-Land.
  • A single year shows as YYYY; a merged range spans first through last as YYYY-YYYY.
  • If a zero-padded month (for instance "01") is supplied, a one-year specification becomes YYYY-MM.
  • The existing ensemble, statistics, and synoptic suffixes appear when active.
  • An area [N, W, S, E] appends _<W>-<E>_<S>-<N>, the coordinates rounded to whole degrees and given hemisphere letters. Zero uses E for longitude and N for latitude.

Following _extension(), for a netCDF ERA5-Land month-split request:

_define_outputfilename("total_precipitation", [2008], month="01")
-> era5-land_total_precipitation_2008-01_hourly.nc

Examples of areas are:

[90.0, -180.0, -90.0, 180.0]
-> era5-land_total_precipitation_2008-01_hourly_180W-180E_90S-90N.nc

[90.0, -180.0, -80.999, 170.001]
-> era5-land_total_precipitation_2008-01_hourly_180W-170E_81S-90N.nc

[0, 120, -90, 180]
-> era5-land_total_precipitation_2008-01_hourly_120E-180E_90S-0N.nc

The existing suffix forms stay valid, including:

era5_total_precipitation_2008_hourly_ensemble.nc
era5_total_precipitation_2008-2009_hourly_ensemble.grb
era5_total_precipitation_2008-2009_hourly_ensemble_statistics.grb
era5_total_precipitation_2008-2009_hourly_ensemble_synoptic.grb

9. Resolving datasets and request dictionaries

Fetch._build_request(variable, years, ...) validates the inputs, resolves the CDS dataset, and returns (dataset_name, request_dict). Included in the dictionary are the resolved variable, year or years, zero-padded months, HH:00 times, output format, product type when one is required, zero-padded days for hourly data, pressure levels for pressure-level datasets, and a validated area when one is supplied.

An unsplit request carries the full selected month list: ['01', ..., '12'] by default, or only ['01'] once --months 01 is given. A month-split request carries its single month. day is omitted by monthly requests. Hourly geopotential with no surface selection, restricted to January 2008, resolves to reanalysis-era5-pressure-levels and includes January along with all selected pressure levels, days, and hours.

Rules for datasets and variables

These rules stay in force:

  • For hourly data, surface variables use reanalysis-era5-single-levels, and pressure variables use reanalysis-era5-pressure-levels.
  • A -monthly-means suffix is appended for monthly requests.
  • Requests for the preliminary back extension get -preliminary-back-extension appended.
  • For ERA5-Land, reanalysis-era5-land is used hourly and reanalysis-era5-land-monthly-means monthly.
  • A variable must exist in the dataset that was selected. Land-only variables, snow_cover for instance, fail without land=True, and non-land variables fail when they are unavailable in ERA5-Land.
  • Variables with no monthly availability stay valid hourly but raise ValueError when requested monthly. Names that are unknown raise ValueError at validation or build time.
  • ERA5-Land combined with the preliminary back extension is incompatible and fails during request resolution/building, not early via size validation.
  • ERA5-Land combined with ensemble output remains incompatible and must not silently produce a valid request.

orography stays a deprecated alias: it uses the single-level dataset and sends geopotential. Beyond that, geopotential is ambiguous. With no surface selection it uses pressure levels; with ["surface"] it uses single levels. Keep the explanatory warnings for ambiguous geopotential and deprecated orography.

Product types

Keep the existing generation:

  • Ordinary hourly requests use reanalysis; hourly ensembles use ensemble_members.
  • For hourly ensemble statistics, the selected product types are ensemble_members, ensemble_mean, and ensemble_spread.
  • Monthly requests use monthly_averaged_reanalysis, or monthly_averaged_ensemble_members when ensembles are involved. Synoptic variants append _by_hour_of_day.
  • For preliminary monthly requests, the forms stay reanalysis-monthly-means-of-daily-means, members-monthly-means-of-daily-means, reanalysis-synoptic-monthly-means, and members-synoptic-monthly-means, depending on the options.
  • Hourly ERA5-Land leaves product_type out. Monthly ERA5-Land uses monthly_averaged_reanalysis, plus the synoptic suffix when that is selected.

Validation of areas

Areas require -90 <= lat_min, lat_max <= 90, lat_max > lat_min, -180 <= lon_min, lon_max <= 180, and longitudes that are not equal. Ordering longitudes in reverse is permitted, so [90, 120, -90, -120] is valid. Latitudes or longitudes that are equal, coordinates out of range, and lists of the wrong length raise ValueError. Coordinates in the request are rounded to two decimals; [89.9999, -179.90, -90.0000, 179.012] becomes [90.0, -179.90, -90.0, 179.01].

10. Management of keys

ERA5CLI_CONFIG_PATH stays replaceable. load_era5cli_config() reads the stored URL, UID, and key and returns (url, "<uid>:<key>"); with URL b, UID 123, and key abc-def, this yields exactly ("b", "123:abc-def").

The existing behavior is retained for checking and writing valid credentials and, when there is no era5cli configuration, for validating and optionally copying an available CDS API configuration. Objective

The task is to implement a strtobool function in the era5cli.utils module; the function converts a string representation of a truth value into a Python boolean.

Public Interface

Extend the era5cli.utils module with the following function:

def strtobool(value: str) -> bool:

It must be possible to access the function as era5cli.utils.strtobool.

Function Behavior

The function accepts a single string argument, and the value it returns is a Python bool.

Inputs that must return True

For each of the following string inputs, the function must return True:

  • "True"
  • "true"
  • "Yes"
  • "y"
  • "1"
Inputs that must return False

For each of the following string inputs, the function must return False:

  • "False"
  • "false"
  • "No"
  • "n"
  • "0"

If the function is given any input string that does not represent a recognized truth value (for example "tr", "01", "maybe", "Fals"), it must raise a ValueError. The message of that exception must contain the text:

Could not convert string to boolean
