01 Property Enhancements for the Air Purifier 572 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Property Enhancements for the Air Purifier

Overview

This task consists of extending the AirPurifier device class located in the miio package (importable as from miio import AirPurifier) together with its associated status object. Two new properties (illuminance and volume) must be exposed, one new setter method (set_volume) must be added, and the handling of certain optional properties must be made robust against missing/None values.

Public API

AirPurifier class

The following methods must be provided (in addition to the existing ones):

  • set_volume(self, volume: int) — sets the volume of the device; it sends the command set_volume with the given value.
Object returned by AirPurifier.status()

The object that status() returns must expose the following read-only properties. Each property's value is derived from the device's raw state dictionary (the keys appear in parentheses):

  • illuminance — its value is read from the raw state key bright.
  • volume — its value is read from the raw state key volume.
  • led_brightness — its value is read from the raw state key led_b.
  • buzzer — its value is read from the raw state key buzzer.
  • temperature — its value is read from the raw state key temp_dec.
  • child_lock — its value is read from the raw state key child_lock.

Behavior of the Properties

illuminance
  • If the raw state key bright holds an integer value, illuminance returns that integer unchanged.
  • illuminance returns None when the raw state key bright is None.
volume
  • If the raw state key volume holds an integer value, volume returns that integer unchanged.
  • volume returns None when the raw state key volume is None.
led_brightness
  • If the raw state key led_b holds a value, led_brightness returns an instance of the LedBrightness enum constructed from that value.
  • led_brightness returns None when the raw state key led_b is None.
buzzer
  • If the raw state key buzzer equals the string 'on', buzzer returns True; if it equals 'off', it returns False.
  • buzzer returns None when the raw state key buzzer is None.
temperature
  • If the raw state key temp_dec is None, temperature returns None. (Otherwise a temperature value is derived from that key, per existing behavior.)
child_lock
  • If the raw state key child_lock equals 'on', child_lock returns True; if it equals 'off', it returns False.

Behavior of the Setters

set_volume(volume)
  • The method accepts integer values in the inclusive range 0 to 100.
  • The values 0, 35, and 100 (and any other value within range) are valid and result in the command set_volume being sent with the given value.
  • Whenever volume is less than 0 or greater than 100, the method must raise AirPurifierException (importable from the same module as AirPurifier, e.g. from miio.airpurifier import AirPurifierException). In this case, no command is sent.
set_favorite_level(level)
  • A favorite level of 10 must be accepted as a valid value.
  • AirPurifierException must be raised for a favorite level of -1 (and any negative value).

Required Dependency

A project dependency on the appdirs package must be declared.

Notes

  • The LedBrightness enum is already available; it can be imported from the same module as AirPurifier.
  • The raw state dictionary is the mapping of property names to values that the device's get_prop command returns; the property values listed above read directly from that mapping.

03 Support for the Xiaomi Air Conditioning Companion 765 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Support for the Xiaomi Air Conditioning Companion

Overview

The AirConditioningCompanion device implementation in the miio package is to be extended. Controlling the device is done by sending commands to a Xiaomi miIO device and by interpreting its state responses.

Public API

Module: miio.airconditioningcompanion

It must be possible to import the following from this module:

  • The class AirConditioningCompanion (also importable from the top-level miio package).
  • The enums OperationMode, FanSpeed, Power, SwingMode.
  • The constant STORAGE_SLOT_ID.
Enums
  • OperationMode — must contain at least the member Auto.
  • FanSpeed — must contain at least the member Low.
  • Power — must contain the members On and Off.
  • SwingMode — must contain the member On.

The values of these enum members must be usable by the configuration-building logic described below (that is, they must map to meaningful values used to construct a device command string).

Constant
  • STORAGE_SLOT_ID — a default storage-slot identifier that the learn-related methods use. Its concrete value is not directly asserted, but it must be a valid argument for the methods that accept a slot id, and it must be the value used when those methods are called without an explicit slot argument.

Parsing the Device State

The raw state of the device is delivered as a list of values via the get_model_and_state command. This list has three elements: index 0 holds the model/identifier string, index 1 holds a data string that encodes the temperature, the operation mode, and the fan speed, and index 2 holds another value.

From this raw state, a status object is produced; this object must expose (at minimum) the following read-only properties:

  • temperature
  • mode — a value from OperationMode or None.
  • fan_speed — a value from FanSpeed or None.
  • swing_mode — a boolean.
Parsing rules that are exercised

For a raw state in which the element at index 1 is the string '010201190280222221':

  • swing_mode is False.
  • fan_speed equals FanSpeed.Low.
  • mode equals OperationMode.Auto.
Handling of missing data

If the element of the state at index 1 is None:

  • temperature must be None.
  • mode must be None.
  • fan_speed must be None.

When this element is None, the status object must not raise; for the affected properties it must gracefully return None.

Methods

learn(self, slot_id=STORAGE_SLOT_ID)

Starts IR learning for the given storage slot. The start_ir_learn command is issued. The method can be called with an explicit slot id or with no arguments (with STORAGE_SLOT_ID as the default). The device response is returned.

learn_result(self)

Retrieves the result of the IR learning. The get_ir_learn_result command is issued. The device response is returned.

learn_stop(self, slot_id=STORAGE_SLOT_ID)

Stops IR learning for the given storage slot. The end_ir_learn command is issued. The method can be called with an explicit slot id or with no arguments (with STORAGE_SLOT_ID as the default). The device response is returned.

send_ir_code(self, command)

Sends a raw IR code. The send_ir_code command is issued. A code string is accepted. The device response is returned.

send_command(self, command)

Sends a command to the device. The send_cmd command is issued with the given command string. The device response is returned.

send_configuration(self, model, power, operation_mode, target_temperature, fan_speed, swing_mode)

From the air-conditioner configuration supplied to it, the method builds a hexadecimal command string and sends it via the send_cmd command. Parameters:

  • model — a string identifying the model (e.g. '0100010727' or '01000fffff').
  • power — a member of the Power enum (Power.On / Power.Off).
  • operation_mode — a member of the OperationMode enum.
  • target_temperature — a temperature given as a number (e.g. 22.5).
  • fan_speed — a member of the FanSpeed enum.
  • swing_mode — a member of the SwingMode enum.

The method must construct a command that consists only of hexadecimal characters (digits 0-9 and letters a-f/A-F) and must pass it as the command argument to send_cmd. This must succeed both for a "known" air-conditioner model (e.g. '0100010727') with power on and with power off and for an "unknown" model (e.g. '01000fffff'). Whatever the underlying command returns is returned to the caller.

Notes on Command Dispatch

The methods call the device via named commands, which have the following argument shapes:

  • start_ir_learn, end_ir_learn: a single argument (the slot id).
  • get_ir_learn_result: a single argument.
  • send_ir_code: a single argument.
  • send_cmd: an argument list whose first element is the constructed or passed command string; this first element must be an all-hexadecimal string.

The return value of each method is whatever the corresponding device command returns.

Task Specification: IR Command Handling for Chuangmi

Overview

You are required to implement IR command handling in the ChuangmiIr device class located at miio/chuangmi_ir.py. Support for playing IR commands in two formats — raw (base64-encoded device-native commands) and pronto (hex-encoded Pronto codes) — must be provided by this class, including automatic format detection and an explicit typed-command format.

Public API

The module miio.chuangmi_ir is required to expose:

  • Class ChuangmiIr (a device class; in tests it is used through multiple inheritance with a dummy device base).
  • Exception class ChuangmiIrException.
Methods

All of the following methods are on ChuangmiIr.

Internally, the class depends on the method _ir_play_input_validation(self, payload), where payload is a dict. Any method that actually sends a command must call this validation/send mechanism with a dict containing the keys 'code' (a base64-encoded string) and 'freq' (an integer frequency, or absent/None). All playback ultimately dispatches through this single point. To put it concretely: the playback methods must build a payload of this shape and pass it to the send mechanism.

pronto_to_raw(pronto, repeats=1) — static/class method

It can be called as ChuangmiIr.pronto_to_raw(...) without an instance.

  • Input:

    • pronto: a string holding a Pronto hex code. The string may either have hex byte-words separated by spaces, or consist of one continuous run of hex digits with no separators. Both forms represent the same data, and the results must be identical.
    • repeats (optional, default 1): a non-negative integer giving the number of repeat frames to include beyond the mandatory frame content.

  • Output: a 2-tuple (code, frequency) in which:

    • code is a base64-encoded string of the raw Chuangmi IR command.
    • frequency is the carrier frequency as an integer (in Hz), derived from the Pronto code.

  • Behavior details:

    • Encoded in the Pronto code are a carrier frequency, a "once" (lead-in) burst sequence, and a "repeat" burst sequence. However repeats is set, the raw command that is produced must always contain at least one repeat frame — in other words, the burst content is always emitted at least once even when repeats is 0, and repeats further repeat frames are appended on top of that guaranteed content. (See the concrete input/output pairs below, which pin down the exact encoding.)
    • If repeats is negative, ChuangmiIrException must be raised.

  • Input:

Binary Format of a Message

A serialized message is composed of a 32-byte header followed by the encrypted payload:

Field Size (bytes) Description
magic 2 Constant value 0x2131
length 2 Total message length in big-endian order = 32 + length of the encrypted payload
unknown 4 0x00000000
did 4 The device id
epoch 4 Timestamp value
checksum 16 MD5 over magic + length + unknown + did + epoch + token + encrypted_payload
payload variable The encrypted payload (encrypted with token using Utils.encrypt)

After the encrypted payload has been decrypted with the provided token, it yields UTF‑8 bytes that represent a JSON object.

  3. Malformed JSON with a doubled comma. There are payloads that include an invalid ,, sequence in place of an intended single comma.   • usb_power (bool) — True when the usb_on property indicates that the USB port is on; False otherwise.

  • temperature — the numeric temperature value as the device reports it.

  • load_power — the load power value, i.e. the first element of the list the get_power command returns.

  • wifi_led (bool) — True when the underlying wifi_led state string is "on", and False when it is "off".

Summary of Behavioral Requirements

  1. After calling off(), reading status().is_on yields False; after calling on(), reading status().is_on yields True.

  2. For a fresh/default state where on=True, usb_on=True, temperature=32, wifi_led='off':

    • status().is_on is True.
    • status().usb_power is True.
    • status().temperature is equal to the device's temperature value (32).
    • status().load_power equals the value obtained from get_power (the first element of the list it returns).

  3. After calling usb_off(), reading status().usb_power yields False; after calling usb_on(), reading status().usb_power yields True.

  4. Calling set_wifi_led(True) leads to status().wifi_led being True; calling set_wifi_led(False) leads to status().wifi_led being False.

Note on the Environment

Support for Python 3.4 is dropped; you may rely on Python 3.5+ language features.
