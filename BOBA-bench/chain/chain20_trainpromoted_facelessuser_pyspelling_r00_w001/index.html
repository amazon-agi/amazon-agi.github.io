The YAML configuration has a top-level matrix key containing a list of task entries. Each task entry may contain:

  • name: a string identifying the task. Names need not be unique; multiple entries may share the same name.

Selection Behavior

None and an empty list are inactive selectors. Selection from the full matrix follows these rules:

  • If both names and groups are inactive, process all matrix entries. Duplicate names do not cause entries to be discarded in this unfiltered mode.
  • If names is active, each requested name resolves to at most one effective task. If the matrix contains multiple entries with that name, only the last matching entry in matrix order is selected; earlier entries with the same name are not processed through that name selection. A name with no matching entry contributes no task. Different requested names may each resolve to their own effective task.
  • If groups is active, select every matrix entry whose group is in groups. Group selection is entry-based: entries are not collapsed merely because they share a task name.
  • If both selector types are active, tasks selected by either mechanism form the selected set; the same matrix entry need not be processed more than once.

The misspelled words produced for a run are the union of the misspelled words from all selected tasks' source files.

Concrete duplicate-name semantics

Consider a matrix with these entries in order:

  1. name: name, group: group1, with sources that check file A.
  2. name: name, group: group2, with sources that check file B.
  3. name: name3, group: group1, with sources that check file C.

The required outcomes are:

  • No selection filters: process entries 1, 2, and 3, producing the combined misspellings from A, B, and C.
  • names=['name']: process only entry 2, because it is the last matrix entry named name, producing exactly B's misspellings.
  • groups=['group1']: process entries 1 and 3, producing the combined misspellings from A and C.

Thus, last-entry precedence applies specifically when resolving an explicitly requested name. It does not remove duplicate-name entries from an unfiltered run or from group selection.

Source Override Behavior

The sources argument replaces the configured source patterns of the task selected by name, but only when exactly one task name is targeted:

  • Resolve the requested name according to the duplicate-name precedence rule, then use the supplied sources patterns instead of that effective task's configured sources.
  • With the example matrix, names=['name'] together with an override pointing to file A still resolves name to entry 2, but entry 2 uses file A instead of its configured file B. The resulting misspellings are exactly those from A.
  • When names contains more than one entry, the sources override must not apply. Selection proceeds normally by name and configured sources are retained.
  • For example, with names=['name', 'other_name'], only name matching matrix entries, and an override pointing to file A, the override is ignored. Normal duplicate-name resolution selects entry 2, so the resulting misspellings are exactly those from B.

In short, a sources override is honored only when selection targets a single name; otherwise it is ignored and normal selection applies.

No-Pipeline Behavior

When a selected task has pipeline: null or no pipeline, the raw content of every matched source file must be spell-checked directly with the selected checker and configured encoding. Misspelled words must be reported, and correctly spelled words must not be reported.

When such a task also defines a dictionary with wordlists, those words must be compiled into and used as a personal dictionary. Words in the wordlists are treated as correctly spelled. A file whose only otherwise-misspelled words are all present in a configured wordlist must therefore yield no misspelled words.

This behavior must work with both Aspell and Hunspell when the corresponding checker and executable are selected.

Notes on Word Results

  • The aggregate misspelled-word set is the union of .words from all results. Ordering is not significant, and duplicate occurrences collapse when considered as a set.
  • Correctly spelled words must never be reported as misspelled.

Backward-Compatibility Constraints

  • The function must continue to work when invoked with only config_file and with any of the listed optional keyword arguments.
  • Existing configuration behavior unrelated to selection and source overriding—including source globbing, encodings, configured pipelines and filters, checker options, personal dictionaries, and result reporting—must remain compatible.
  • The previously existing singular selection parameter is replaced by plural names, which accepts a list.
  • The public signature must accept names, groups, binary, checker, sources, verbose, and debug as keyword arguments in the order shown above.

No new public modules, classes, options, or configuration keys are introduced.

Selector Compounds and Chains

A compound selector describes one element and may use the selector conditions already supported by the filter, such as an element name, ID, classes, attributes, and namespaces. Conditions in one compound apply to the same element. For example, p.iiii.zzzz matches a p carrying both iiii and zzzz; an HTML attribute such as class="iiii zzzz" satisfies those class conditions.

A selector chain consists of compounds joined by combinators. The chain's relationships are interpreted in their left-to-right sequence, while the rightmost compound identifies the element ultimately matched. Every preceding compound and relationship must be satisfied. Combinators may be mixed and repeated in one selector.

Required Combinators

The following syntax is required:

Syntax Required relationship
A B Descendant: the target B has a proper ancestor matching A, at any depth.
A > B Child: the target B has a direct parent matching A.
A + B Adjacent traversal element: A is the nearest element preceding B in document order.
A ~ B General preceding element: some element matching A occurs before B in document order.

For + and ~, “document order” means depth-first element order based on element start positions. Text, comments, and other non-element nodes do not participate. These two relationships intentionally do not require A and B to have the same parent:

  • A + B uses the nearest preceding element anywhere in that traversal. If B is the first element child of A, then A itself is the nearest preceding element, so A + B can match that parent/first-child pair.
  • A ~ B can use any earlier element, including one outside B's parent or ancestor chain.

This traversal-based meaning is the compatibility behavior of this selector engine and differs from strict CSS sibling semantics.

Whitespace forms the descendant combinator. Whitespace before or after an explicit >, +, or ~ is optional and must not create an additional descendant relationship. Thus forms such as A>B, A > B, A+B, and A ~ B must be accepted equivalently with respect to surrounding whitespace.

Representative chains include:

  • body div.gggg > p.zzzz
  • p.bbbb ~ div.gggg > p.hhhh + p

Pseudo-Class Selectors

The existing pseudo-classes must accept selector lists that contain the required combinators:

  • :matches(S1, S2, ...) succeeds when the element being evaluated matches at least one inner selector.
  • :not(S1, S2, ...) succeeds when the element being evaluated matches none of the inner selectors.

An inner selector is a complete selector chain: its rightmost compound is matched against the same element being evaluated by the pseudo-class, and its earlier compounds are resolved using the relationship rules above. Combinator handling, including the traversal-based meanings of + and ~, must be identical inside and outside pseudo-classes.

Required examples include:

  • :not(p.hhhh + .zzzz)
  • p:matches(.aaaa + .bbbb)

The latter matches a p.bbbb that is the first element child of div.aaaa, because the parent div.aaaa is the nearest preceding element in document order.

  • immediately followed (next sibling, same parent) by a p,

  • where that div.gggg is a descendant of a div,

The :has() pseudo-class must be fully supported. It matches an element based on the presence of other elements described relative to that element. The argument to :has() is one or more relative selectors, and may begin with a leading combinator (>, +, ~) that establishes the relationship relative to the element being tested.
