Summary

Change the public spellcheck function in the pyspelling package so that a positional parameter selects the spell-checking backend ("checker"), and adjust the ordering of its parameters. In addition to the existing Aspell backend, the function must support running against a Hunspell backend.

Public API

The function's signature must accept the positional parameters listed below, in exactly this order:

spellcheck(config_file, name, binary, checker, verbose, debug)

  • name: an optional identifier for choosing which configured task(s) to run (it may be falsy/empty).
  • binary: an optional path to the spell-check binary that gets invoked (it may be an empty string, meaning "use default").
  • checker: a string giving the name of the spell-check backend to use. It must accept at least the values 'aspell' and 'hunspell'.
  • verbose: an integer giving the verbosity level.
  • debug: a boolean debug switch.

The function must return an iterable of result objects. Each of these result objects must expose:

  • an error attribute (falsy if there was no error; truthy/printable if an error occurred).
  • a words attribute, which is an iterable of the misspelled words that were found.

  • When checker is 'aspell', spell checking is performed by the function with the Aspell backend, honoring the aspell: configuration options of each task (for example lang, mode).
  • When checker is 'hunspell', spell checking is performed by the function with the Hunspell backend, honoring the hunspell: configuration options of each task (for example d for dictionary selection such as en_US).

Task Description

Overview

The tool you are working on is a spell checker configured through a YAML file. It handles a "matrix" of spell-check tasks, each of which may optionally define a text-filtering pipeline. You are to add support for disabling the pipeline, so that source files are spell-checked as-is (raw text) with no filtering applied.

Behavior Requirements

Configuration via pipeline: null

A pipeline key is supported by each entry in the matrix. If that key is explicitly set to null (i.e. no pipeline / empty value), the tool must:

  • Skip all pipeline/filter processing for the matrix entry in question.
  • Pass the raw contents of each matched source file directly to the spell checker, using the configured default_encoding.

When no pipeline is configured, the tool must not error or fail; it must treat the file's full text as the content to check.

Spell checking without a pipeline

Take a matrix entry with pipeline: null: each file matched by the sources globs has its entire text content spell-checked. Words that the configured spell checker does not recognize are reported as misspelled.

Custom dictionaries and word lists

A dictionary section may be present in a matrix entry:

dictionary:
  wordlists:
    - '<path>/mydict.wl'
  output: '<path>/mydict.dic'
  • wordlists names one or more word-list files, and each such file contains one word per line.
  • The words contained in these word lists must be compiled into a personal/custom dictionary (written to output) and then supplied to the spell checker.
  • Any word that appears in the compiled custom dictionary must be treated as correctly spelled and, as a result, must NOT be reported as misspelled — this applies even when the pipeline is disabled (pipeline: null).

Applicable Configuration Keys (per matrix entry)

  • name: a string identifying the matrix entry.
  • default_encoding: the text encoding in which source files are read (e.g. utf-8).
  • sources: a list of glob patterns that identify the files to check.
  • aspell: options for the spell checker (e.g. lang: en).
  • hunspell: options for the spell checker (e.g. d: en_US).
  • pipeline: a null value disables filtering and checks the raw file text.
  • dictionary (optional): contains wordlists (a list of word-list file paths) and output (the compiled dictionary path).

Expected Outcomes

  • No pipeline and no custom dictionary: All words in the source files that the spell checker does not recognize are returned as misspelled. Words that are spelled correctly are not returned.
  • No pipeline, with a custom word list: Words that would otherwise be flagged as misspelled but which appear in the supplied word list are recognized as valid and are NOT returned. If the word list covers every otherwise-misspelled word, no misspelled words are returned.

For a spell-check run, the set of misspelled words it produces is the collection of words flagged across all matched source files.

Public API

Invocation of the spell-check operation goes through the mechanism the existing test harness already uses (a spellcheck entry point that accepts the path to a YAML configuration file and returns the collection of misspelled words found). Your changes must make the pipeline: null and dictionary behaviors described above work through that same existing invocation path — beyond honoring these configuration keys, no new public functions or modules are required.

Additional Notes

  • The configuration file is standard YAML; pipeline: null makes use of YAML's null value.
  • The source file paths given in sources use glob patterns (including ** for recursive matching).

Summary

Public Interface

The package must expose the following top-level callable:

spellcheck(config_file, names=None, groups=None, binary='', checker='', sources=None, verbose=0, debug=False)

The arguments below must be accepted and must behave as described:

  • config_file (positional): the path to a YAML configuration file.
  • names: None or a list of task-name strings for selecting tasks.
  • groups: None or a list of group-name strings for selecting tasks.
  • binary: the path to the spell-checker executable to invoke. When it is non-empty, it is the executable to use.
  • checker: which spell checker is to be used; one of 'aspell' or 'hunspell'.
  • sources: None or a list of source glob-pattern strings. When eligible, it overrides the configured sources of the single task selected by name.
  • verbose: an integer giving the verbosity level.
  • debug: a boolean debug flag.

Every argument after config_file must be accepted as a keyword argument.

spellcheck must return an iterable or generator that yields result objects, one for each processed file. Each result object must have the following:

  • .error: falsy when no error occurred; otherwise, a printable error value.
  • .words: an iterable of the misspelled-word strings found for that result.

Taken across all yielded results, the union of .words represents all misspelled words found for the selected tasks.

Format of the Configuration

The YAML configuration contains a top-level matrix key holding a list of task entries. Each task entry may contain the following:

  • name: a string that identifies the task. Names need not be unique; multiple entries may share the same name.
  • group: a string identifying a group that the task belongs to. Multiple tasks may share the same group.
  • default_encoding: the encoding used for reading source files.
  • sources: a list of glob patterns identifying the files to check, including patterns that contain **.
  • aspell: a mapping of Aspell options, for example lang.
  • hunspell: a mapping of Hunspell options, for example d.
  • pipeline: a list of filter plugins to apply, or else null/absent, in which case raw file content is checked directly.
  • dictionary: an optional mapping with wordlists (a list of wordlist paths) and output (the path to the compiled personal dictionary). Words that are present in the personal dictionary are treated as correctly spelled and must not be reported as misspelled.

The checker that is selected reads its options from the aspell or hunspell mapping with the corresponding name.

Behavior of Selection

None and an empty list count as inactive selectors. The following rules govern selection from the full matrix:

  • If both names and groups are inactive, all matrix entries are processed. In this unfiltered mode, duplicate names do not lead to entries being discarded.
  • If names is active, each requested name resolves to at most one effective task. When the matrix has multiple entries with that name, only the last matching entry in matrix order is selected; entries with the same name that come earlier are not processed through that name selection. A name with no matching entry contributes no task. Different requested names may each resolve to their own effective task.
  • If groups is active, every matrix entry whose group is in groups is selected. Group selection operates per entry: entries are not collapsed merely because they share a task name.
  • If both selector types are active, the selected set is formed by the tasks selected through either mechanism; the same matrix entry need not be processed more than once.

The misspelled words that a run produces are the union of the misspelled words from the source files of all selected tasks.

Duplicate-Name Semantics in a Concrete Case

Take a matrix that contains the following entries in order:

  1. name: name, group: group1, whose sources check file A.
  2. name: name, group: group2, whose sources check file B.
  3. name: name3, group: group1, whose sources check file C.

The required outcomes are the following:

  • With no selection filters: entries 1, 2, and 3 are processed, and the combined misspellings from A, B, and C are produced.
  • names=['name']: only entry 2 is processed — because it is the last matrix entry named name — and exactly B's misspellings are produced.
  • groups=['group1']: entries 1 and 3 are processed, and the combined misspellings from A and C are produced.

Thus, last-entry precedence applies specifically when an explicitly requested name is resolved. It does not remove duplicate-name entries from an unfiltered run or from group selection.

Behavior of the Source Override

The sources argument replaces the configured source patterns of the task selected by name, but it does so only when exactly one task name is targeted:

  • Resolve the requested name according to the duplicate-name precedence rule, and then use the supplied sources patterns in place of the configured sources of that effective task.
  • For the example matrix, names=['name'] together with an override pointing to file A still resolves name to entry 2, but entry 2 then uses file A rather than its configured file B. The resulting misspellings are exactly those from A.
  • If names contains more than one entry, the sources override must not apply. Selection proceeds normally by name, and the configured sources are retained.
  • As an example, take names=['name', 'other_name'], with only name having matching matrix entries, plus an override pointing to file A: the override is ignored. Normal duplicate-name resolution selects entry 2, so the resulting misspellings are exactly those from B.

In short, a sources override is honored only when selection targets a single name; otherwise, it is ignored and normal selection applies.

Behavior Without a Pipeline

When a selected task has pipeline: null or has no pipeline, the raw content of every source file that is matched must be spell-checked directly with the selected checker and the configured encoding. Misspelled words must be reported, and correctly spelled words must not be reported.

If such a task also defines a dictionary with wordlists, those words must be compiled into a personal dictionary and used as one. Words in the wordlists are treated as correctly spelled. A file whose only otherwise-misspelled words are all present in a configured wordlist must therefore yield no misspelled words.

When the corresponding checker and executable are selected, this behavior must work with both Aspell and Hunspell.

Notes About Word Results

  • The aggregate set of misspelled words is the union of .words from all results. Ordering is not significant, and duplicate occurrences collapse when the results are considered as a set.
  • Words that are spelled correctly must never be reported as misspelled.

Constraints for Backward Compatibility

  • The function must continue to work when it is invoked with only config_file, and also when invoked with any of the listed optional keyword arguments.
  • Configuration behavior that already exists and is unrelated to selection and source overriding — including source globbing, encodings, configured pipelines and filters, checker options, personal dictionaries, and result reporting — must remain compatible.
  • The singular selection parameter that existed previously is replaced by the plural names, which accepts a list.
  • The public signature must accept names, groups, binary, checker, sources, verbose, and debug as keyword arguments, in the order shown above.

Overview

1. The C++ allowed String-Family Selector

The allowed option of the C++ filter is a string of selector characters that are independent, freely combinable, and case-insensitive. In normal C/C++ parsing mode, it controls which C++ string-literal families are returned when strings: true is enabled. Generic mode keeps its existing generic string behavior; this task does not cause the C++ family selectors to apply there.

The alphabet of accepted selectors is:

Code Meaning Non-raw forms Raw forms when r is present as well
s Standard narrow strings with no prefix "..." R"(...)", custom-delimiter forms included
l Wide strings prefixed by L L"..." LR"(...)"
u Strings with Unicode prefixes u8"...", u"...", U"..." u8R"(...)", uR"(...)", UR"(...)"
r Modifier for raw strings None on its own A raw form is enabled only when its underlying family selector is present as well

Consequently:

  • If its family code (s, l, or u) is present, a non-raw string is included.
  • A raw string is included only when both its family code and r are present.
  • r on its own does not enable every raw string.
  • s refers to standard strings; it is not a selector for comments.
  • Character constants such as 'x' stay excluded from string output.

The obsolete w code must no longer serve to select wide strings. In option defaults, in validation, and in literal selection alike, l takes its place. Values that contain l must be accepted; w must not remain a valid alias or keep wide-string semantics. Other characters that are not supported remain invalid.

The default value changes from suw to sul, which preserves the default family set of standard, wide, and Unicode non-raw strings. Because r is absent, raw strings remain disabled by default.

Combinations that are required

The order in which selector characters appear is immaterial. The family behavior that is required is illustrated by the following combinations:

  • uls: non-raw strings of the standard, wide, and Unicode families; no raw strings.
  • rls: non-raw standard and wide strings, plus unprefixed and LR raw strings; no Unicode strings.

Compound Selectors and Selector Chains

A compound selector describes one element and may use the selector conditions the filter already supports, such as an element name, ID, classes, attributes, and namespaces. The conditions in one compound apply to the same element. As an example, p.iiii.zzzz matches a p carrying both iiii and zzzz; an HTML attribute such as class="iiii zzzz" satisfies those class conditions.

A selector chain is made up of compounds joined by combinators. The relationships of a chain are interpreted in their left-to-right sequence, while the element ultimately matched is identified by the rightmost compound. Every relationship and preceding compound must be satisfied. Combinators may be mixed and repeated within one selector.

Required Combinators

The syntax listed below is required:

Syntax Required relationship
A B Descendant: the target B has a proper ancestor that matches A, at any depth.
A > B Child: the target B has a direct parent that matches A.
A + B Adjacent traversal element: A is the nearest element that precedes B in document order.
A ~ B General preceding element: some element that matches A occurs before B in document order.

In the case of + and ~, “document order” refers to depth-first element order based on element start positions. Text, comments, and other non-element nodes do not take part. By design, these two relationships do not require A and B to have the same parent:

  • A + B works with the nearest preceding element from anywhere in that traversal. If B is the first element child of A, then A itself is the nearest preceding element, so A + B can match that parent/first-child pair.
  • A ~ B can take any earlier element, including one that lies outside B's parent or ancestor chain.

This traversal-based meaning is what serves as the compatibility behavior of this selector engine, and it differs from strict CSS sibling semantics.

The descendant combinator is formed by whitespace. Whitespace before or after an explicit >, +, or ~ is optional and must not introduce an additional descendant relationship. Hence, forms such as A>B, A > B, A+B, and A ~ B must be accepted equivalently with respect to surrounding whitespace.

Some representative chains include:

  • body div.gggg > p.zzzz
  • p.bbbb ~ div.gggg > p.hhhh + p

The pseudo-classes that already exist must accept selector lists containing the required combinators:

  • :matches(S1, S2, ...) succeeds when at least one inner selector is matched by the element being evaluated.
  • :not(S1, S2, ...) succeeds when none of the inner selectors are matched by the element being evaluated.

An inner selector forms a complete selector chain: the same element being evaluated by the pseudo-class is what its rightmost compound is matched against, and its earlier compounds are resolved using the relationship rules above. Handling of combinators, including the traversal-based meanings of + and ~, must be identical inside and outside pseudo-classes.

Inside the pyspelling package sits an HTML filter (pyspelling.filters.html) that parses HTML documents and, once configured, ignores content that CSS selectors match while spell checking takes place. The subject of this task is the CSS :nth-child-style pseudo-class matching (the "nth" algorithm): its behavior needs correcting so that, for a set of An+B argument forms, elements get selected correctly.

Nothing about the public interface changes: configuration of the HTML filter happens (via YAML pipeline configuration) through an ignores list of CSS selectors. Content sitting inside elements matched by those selectors is excluded from spell checking, and the report contains all remaining text words. What needs fixing is the internal nth-selector matching logic, so that the set of matched elements comes out correct.

Model of the Test Document

An HTML document featuring a sequence of sibling elements is where this behavior gets exercised. For this specification, the assumption is a parent element holding 12 consecutive <p> sibling children; the spell-checkable text words of those children, in document order, are:

aaaa, bbbb, cccc, dddd, eeee, ffff, gggg, hhhh, iiii, jjjj, kkkk, llll

(meaning the word inside the 1st <p> child is aaaa, inside the 2nd it is bbbb, … and inside the 12th it is llll). There may be additional structure in the document that is not <p>, but what matters for the selectors below is only these <p> children and their 1-based sibling positions.

When a selector matches an element, the word belonging to that element is omitted from the reported output; every word that is not matched shows up in the report, in document order.

Behavior Requirements

The following results are exactly what the nth-selector matching must produce.

1. p:nth-child(-n+3)

The <p> children matched here are the ones whose 1-based position among all siblings satisfies -n + 3 for n = 0, 1, 2, … — in other words, positions 3, 2, 1 (the first three <p> children).

  • Matched positions: 1, 2, 3 → words aaaa, bbbb, hhhh... no — the words that match are those at positions 1, 2, 3.
  • Words reported (non-matched): cccc, dddd, eeee, ffff, gggg, hhhh, iiii, jjjj, kkkk, llll

This case demonstrates that an An+B expression with a negative coefficient (A = -1) must be handled correctly: the algorithm must ramp the counter to reach the lowest valid (in-bounds, ≥ 1) index, then decrement through the sequence of matching positions. Whenever the formula produces a position that falls out of bounds (≤ 0), that position must terminate evaluation rather than match.

2. :nth-child(-n+3 of p)

The matched elements come from among the <p> children (the "of S" filtered set): they are the ones whose 1-based position within that filtered set satisfies -n + 3, meaning the first three <p> elements of the filtered set.

For the document at hand, the filtered set is different from the plain-child case: the matched set comes out as positions 1, 2, 3 of the <p>-filtered siblings, but the 8th <p> (hhhh) is also excluded relative to the plain case. In concrete terms:

  • Words reported (non-matched): cccc, dddd, eeee, ffff, gggg, iiii, jjjj, kkkk, llll

What this case confirms is that the of S variant first narrows the sibling set to only elements matching selector S and applies the nth counting after that; relative to the plain form, this filtering can change which elements are matched.

3. p:nth-child(2)

The matched element is the <p> child located at 1-based sibling position 2.

  • Words reported (non-matched): aaaa, cccc, dddd, eeee, ffff, gggg, hhhh, iiii, jjjj, kkkk, llll
4. p:nth-child(9n - 1)

The <p> children matched are those whose 1-based sibling position satisfies 9n - 1 for n = 0, 1, 2, …; only in-bounds (≥ 1) positions are considered: n=1 → 8, n=2 → 17 (out of bounds). Position 8 is the only one that matches.

  • Words reported (non-matched): aaaa, bbbb, cccc, dddd, eeee, ffff, gggg, iiii, jjjj, kkkk, llll

The point confirmed here: before a sibling is evaluated for a match, the computed index must be verified to be within bounds; should an index fall out of bounds during the evaluation, it must abort further matching rather than produce spurious matches.

Summary of Correctness Requirements

With an An+B argument in hand, the nth matching algorithm must do the following:

  1. Bounds take priority: ensure the candidate index is in bounds (≥ 1 and within the sibling count) before a sibling gets evaluated; if the index falls out of bounds during iteration, evaluation stops (do not match).
  2. Negative coefficient case: whenever the coefficient A takes a negative value (the equation's trend is toward lower indices), the step counter is increased until the index arrives at its lowest in-bounds point; that counter value is adopted at that point, and the counter then switches to being decremented through the subsequent evaluations, so that all valid matching positions are found.
  3. of S handling: if the argument includes an of S selector, the counted sibling set is restricted to the elements matching S; over that filtered set the nth counting is then applied (1-based positions within the filtered set).

Deliverable

The nth-selector matching logic inside the HTML filter's CSS selector matching is what has to be fixed, with this outcome: for the four selector forms listed above, the words reported are exactly the specified sets (the text of matched elements is excluded; all other sibling text words are reported, in document order). The filter's public configuration interface (pyspelling.filters.html with mode: html5 and an ignores list of CSS selector strings) does not change.
