Specification of the Task

Summary

spider_feeder is a Scrapy extension that, when the spider opens, replaces a spider's start_urls with URLs read from an external file. Move file access into scheme-specific handlers under a new spider_feeder.file_handler package, and switch to the new handler configuration setting described below.

Public Modules and Extension Layout

The extension stays available as spider_feeder.loaders.StartUrlsLoader and must support Scrapy's from_crawler(crawler) extension factory.

Create a package spider_feeder.file_handler that contains, at minimum:

  • spider_feeder.file_handler.local, which exposes a callable named open;
  • spider_feeder.file_handler.s3, which exposes a callable named open.

These callables serve as the public interception points for built-in file access. Each of them must be individually importable and replaceable at exactly spider_feeder.file_handler.local.open and spider_feeder.file_handler.s3.open, and built-in dispatch must invoke the callable exposed at the corresponding location.

Each open callable accepts exactly one string argument: the scheme-stripped handler target, derived as specified under URI Parsing and Handler Dispatch. The callable returns a binary file-like object, such as io.BytesIO, whose read() operation provides the raw bytes of the target file.

  • spider_feeder.file_handler.local.open is the built-in handler selected for file:// inputs and opens the corresponding local filesystem target.
  • spider_feeder.file_handler.s3.open is the built-in handler selected for s3:// inputs and opens the corresponding S3 target.

Settings

SPIDERFEEDER_INPUT_FILE

SPIDERFEEDER_INPUT_FILE is the string URI that identifies the input, for example file:///tmp/input_file.txt or s3://input_file.txt.

When a call is made to StartUrlsLoader.from_crawler(crawler):

  • If this setting is absent or otherwise falsey, it must raise scrapy.exceptions.NotConfigured. In that case, no spider_opened receiver may be connected.
  • If this setting is truthy, the extension must be created, must be connected to Scrapy's spider_opened signal, and must be returned from from_crawler.
SPIDERFEEDER_FILEHANDLERS

SPIDERFEEDER_FILEHANDLERS is an optional dictionary that maps URI scheme strings to fully qualified dotted names of callables. The entries it contains are merged with the built-in scheme mapping and take precedence for matching schemes. It can therefore override file or s3, or add support for another scheme.

An override callable follows the same contract as a built-in handler: it accepts the single normalized handler target—not the full configured URI—and returns a binary file-like object containing raw bytes.

URI Parsing and Handler Dispatch

Interpret SPIDERFEEDER_INPUT_FILE according to urllib.parse.urlparse semantics. The parsed scheme is used to select a handler. The built-in mapping is:

  • file → spider_feeder.file_handler.local.open
  • s3 → spider_feeder.file_handler.s3.open

If the parsed scheme is present in SPIDERFEEDER_FILEHANDLERS, select the callable configured there instead of the built-in callable.

Before invoking the selected handler, build its argument by concatenating the parsed authority (netloc) and the parsed path, in that order:

handler_target = parsed.netloc + parsed.path

This value is passed as the callable's sole argument. Do not pass the complete URI or the scheme delimiter. Components other than netloc and path, such as a query or a fragment, are not part of the handler target.

Examples:

  • For file:///tmp/input_file.txt, the local handler is selected and /tmp/input_file.txt is passed.
  • For s3://input_file.txt, the S3 handler is selected and input_file.txt is passed.
  • For s3://bucket/key.txt, the S3 handler is selected and bucket/key.txt is passed.

Handlers supplied through SPIDERFEEDER_FILEHANDLERS are normalized in the same way.

Behavior When the Spider Opens

Upon receiving spider_opened, a configured extension must:

  1. Select the appropriate handler and invoke it as described above.
  2. Read the contents of the returned binary file-like object.
  3. Decode those bytes as UTF-8.
  4. Break the decoded content into lines and use each non-empty line as one URL entry.
  5. Assign the resulting list to the start_urls attribute of the opened spider, replacing its previous value.

The input has one URL per line, with newline characters separating the entries. The resulting strings do not include the line separators, and empty lines do not become URL entries.

File opening and URL loading happen in response to spider_opened; merely creating the configured extension does not populate start_urls.

Superseded Interfaces

The former spider_feeder.readers dispatch points (open_local and open_s3) and the former SPIDERFEEDER_READERS setting are replaced, respectively, by the spider_feeder.file_handler.<scheme>.open callables and SPIDERFEEDER_FILEHANDLERS. Built-in file access must dispatch through the new callable locations, and customization of handlers must use the new setting name.

Overview

Build the public spider-feeder loading API. It is made up of two Scrapy extensions that load a spider's initial work from an external source, together with the built-in stores, file handlers, and parsers those extensions rely on.

When a spider opens, a store is chosen from SPIDERFEEDER_INPUT_URI. The store provides ordered (url, meta) pairs. StartUrlsLoader places the URLs into spider.start_urls; StartRequestsLoader installs a producer for spider.start_requests() that preserves both each URL and the metadata attached to it.

Lifecycle of the Loader Extensions

Both loader classes are Scrapy extensions, and each one must provide from_crawler(cls, crawler).

from_crawler must:

  1. Read the configuration from crawler.settings.
  2. Build an instance of the extension.
  3. Hook that instance up to Scrapy's spider_opened signal.
  4. Return that extension instance.

The intended way to enable the loaders is through Scrapy's EXTENSIONS setting, for example:

EXTENSIONS = {
    "spider_feeder.loaders.StartUrlsLoader": 500,
}

or:

EXTENSIONS = {
    "spider_feeder.loaders.StartRequestsLoader": 500,
}

Ordinary Scrapy extension initialization followed by delivery of the spider_opened signal must be sufficient to trigger loading; callers must not have to invoke the extension by hand.

A value for SPIDERFEEDER_INPUT_URI is required. If that setting is absent or empty, each loader's from_crawler(crawler) must raise scrapy.exceptions.NotConfigured, rather than returning or connecting an active extension. In particular, this requirement applies to StartUrlsLoader.from_crawler(crawler).

Formatting of the Input URI and Resolution of the Store

Before a store is resolved or opened, the configured SPIDERFEEDER_INPUT_URI must support Python mapping-style % interpolation against the opened spider's attributes. As an example, given a spider with the attributes dir = "/tmp" and input_file = "spider_input":

SPIDERFEEDER_INPUT_URI = "%(dir)s/%(input_file)s.txt"

must resolve to /tmp/spider_input.txt. The fully formatted URI serves both for scheme selection and as the URI handed to the store.

StartUrlsLoader

When the spider opens, StartUrlsLoader must:

  1. Resolve the store and instantiate it.
  2. Go through all store entries in order.
  3. Assign to spider.start_urls an iterable collection that contains only each pair's url, in the same order. This loader ignores metadata.
  4. Set the crawler stat spider_feeder/<spider_name>/url_count to the number of entries loaded, where <spider_name> is the name of the opened crawler's spider.

The spider.start_urls that results must be consumable as an iterable of URL strings.

StartRequestsLoader

When the spider opens, StartRequestsLoader must:

  1. Resolve and instantiate the same kind of store that StartUrlsLoader uses.
  2. Load all (url, meta) pairs, following the store's order.
  3. Make spider.start_requests callable, and make iterating spider.start_requests() produce one Scrapy Request for each pair that was loaded.
  4. Set spider_feeder/<spider_name>/url_count to the number of pairs that were loaded.

For every pair, the request that corresponds to it must have:

  • request.url equal to the URL held in the store; and
  • request.meta equal to the metadata dictionary held in the store, without any of its fields being lost.

The order of the requests must match the order of the store. Entries are not deduplicated: repeated pairs — including repeated URLs that carry the same metadata — must each produce a separate request.

Common Conversion of Input Items

The built-in FileStore and the built-in ScrapinghubCollectionStore use SPIDERFEEDER_INPUT_FIELD when converting logical input items into (url, meta) pairs.

  • When no non-empty SPIDERFEEDER_INPUT_FIELD has been configured (this includes when it is absent, None, or the empty string), each logical item produces (item, {}).

  • When it is a non-empty field name, each logical item must be a dictionary and produces (item[field_name], item). The metadata value is the original dictionary.

  • When a non-empty field is configured but an item is not a dictionary, iteration must raise TypeError, and the first argument of the exception must be exactly:

    Data is expected to be a dict when SPIDERFEEDER_INPUT_FIELD is set.

Input order is preserved by this conversion, and items are not deduplicated.

  • SPIDERFEEDER_INPUT_URI: input URI that is required; supports % interpolation of spider attributes.
