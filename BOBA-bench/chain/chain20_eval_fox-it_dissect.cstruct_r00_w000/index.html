01 Default Values for Dynamic and Null-Terminated Arrays 629 words · source specification

Task Specification: Default Values for Dynamic and Null-Terminated Arrays

Context

This task concerns a C-structure parsing library (cstruct) that allows defining C-style structs from textual definitions and instantiating them as Python objects. The library is imported as:

import cstruct

Structures are defined via a C-like definition string and loaded with:

cs = cstruct.cstruct()
cs.load(cdef, compiled=<bool>)

Each loaded struct becomes accessible as an attribute of the cstruct instance (e.g. cs.test). Instantiating a struct with no arguments (e.g. cs.test()) must produce an object whose fields are populated with sensible default values, and which can be serialized back to bytes via its .dumps() method.

Required Behavior

When a struct is instantiated with no field values provided, every field must receive a default value. This task focuses specifically on array fields whose length is not a fixed compile-time constant, i.e.:

  • Null-terminated / unbounded arrays — declared with empty brackets, e.g. uint32 field[];
  • Dynamic arrays — declared with a length that references another field, e.g. uint32 field[x];

For both of these array kinds, the default value produced when instantiating the struct with no arguments must be an empty sequence appropriate to the element type:

Array element type Default value
Integer types (e.g. uint8, uint32) [] (empty list)
Multi-byte "bytes-int" integer types (e.g. uint24) [] (empty list)
char arrays b"" (empty bytes)
wchar arrays "" (empty string)
Enum-typed arrays [] (empty list)
Flag-typed arrays [] (empty list)

In other words:

  • char[...] and char[] default to an empty bytes object.
  • wchar[...] and wchar[] default to an empty str.
  • All other element types (plain integers, multi-byte integers, enums, flags), whether the array is dynamic or null-terminated, default to an empty list.

The default must be identical whether the array is null-terminated ([]) or dynamic ([x]).

Serialization Behavior

The resulting default-constructed object must be serializable with .dumps(). When all array fields default to empty sequences, they contribute zero bytes to the serialized output. Only fixed-size scalar fields contribute bytes.

For example, given a struct containing one uint8 scalar field followed by twelve empty dynamic/null-terminated array fields, .dumps() produces bytes consisting solely of the scalar field's default (a single zero byte) plus the null terminators, if any, that a serialized empty array of that kind requires. Concretely, for a struct laid out as:

  • one uint8
  • pairs of null-terminated and dynamic arrays for each of: 32-bit int, 24-bit int, char, wchar, enum, flag

the total serialized length of the default-constructed object is 19 bytes, all zero (b"\x00" * 19). This total accounts for the single scalar byte plus the terminator bytes emitted for each null-terminated array of a given element width.

Definitions Supported in Scope

The definition parser must handle a struct containing, in a single definition, all of the following field forms and produce correct defaults for each:

  • enum and flag type declarations with named members.
  • A leading uint8 scalar field.
  • Null-terminated and dynamic array variants of: uint32, uint24, char, wchar, enum types, and flag types.

Public API Surface

No new public names are introduced. The engineer must ensure the existing API behaves as specified:

  • cstruct.cstruct() — constructs a parser/registry instance.
  • cstruct.cstruct().load(cdef: str, compiled: bool) — parses a definition string; compiled selects between compiled and non-compiled code paths, and both paths must yield identical default-construction and serialization behavior.
  • Loaded structs are exposed as attributes on the cstruct instance and are callable with no arguments to build a default instance.
  • Each struct instance exposes fields as attributes and a .dumps() method returning bytes.

The behavior described above must hold under both compiled=True and compiled=False.

Task Specification: Add Range Validation to BytesInteger Serialization

Overview

The BytesInteger type in dissect.cstruct.types (importable as from dissect.cstruct.types import BytesInteger) must validate that integer values fit within the representable range for their configured byte width and signedness when serialized. Values outside that range must raise an error.

API Surface

The BytesInteger class must be constructible with the following signature (as used in this task):

BytesInteger(cstruct_instance, name, size, signed=<bool>)

Where:

  • cstruct_instance — a dissect.cstruct.cstruct() instance.
  • name — a string name for the type (e.g. "int8").
  • size — the width in bytes of the integer (e.g. 1, 2, 3).
  • signed — keyword argument, True for signed integers, False for unsigned.

The class must provide a serialization method:

BytesInteger.dumps(value)

which serializes the given integer value.

Required Behavior

dumps(value) must enforce the valid value range determined by size (in bytes) and signed:

  • Signed (signed=True): valid range is from -(2^(8*size - 1)) to 2^(8*size - 1) - 1, inclusive.
  • Unsigned (signed=False): valid range is from 0 to 2^(8*size) - 1, inclusive.
In-range values

When value is within the valid range (including both boundary endpoints), dumps(value) must serialize normally without raising.

Concrete boundary examples that must succeed:

  • size=1, signed: -128 and 127
  • size=1, unsigned: 0 and 255
  • size=2, signed: -32768 and 32767
  • size=3, signed: -8388608 and 8388607
Out-of-range values

When value is outside the valid range (either below the minimum or above the maximum), dumps(value) must raise OverflowError.

Concrete examples that must raise OverflowError:

  • size=1, signed: -129 and 128
  • size=1, unsigned: -1 and 256
  • size=2, signed: -32769 and 32768
  • size=3, signed: -8388609 and 8388608

The OverflowError should carry a descriptive message.

Constraints

  • The change applies to arbitrary byte widths (not just fixed sizes), computing the valid range from the size and signed parameters.
  • Existing serialization behavior for in-range values (single values and any previously supported forms) must remain unchanged.

Task: Add __bytes__ Support to cstruct Instances

Objective

Enable instances of parsed C structures (created via the cstruct library) to be converted to their raw binary representation using Python's built-in bytes() function.

Background

The cstruct module (importable as cstruct) provides a cstruct.cstruct class that parses C-style structure definitions and produces structure types. An instance of a parsed structure already supports serialization to bytes via an existing dumps() method, which returns the packed binary representation of the instance's fields according to the declared field types and the configured endianness.

Requirement

Structure instances must implement the __bytes__ special method so that calling the built-in bytes() on an instance returns its raw serialized binary representation.

The result of bytes(instance) must be identical to the result of instance.dumps().

Behavioral Details

  • The returned value must be a bytes object.
  • Its length must equal the total packed size of all declared fields.
  • Field values must be encoded in field-declaration order, honoring the field types and the endianness configured on the owning cstruct instance.
Concrete Example

Given a structure loaded with big-endian (>) byte ordering:

struct test {
    DWORD   a;   // 4-byte unsigned integer
    QWORD   b;   // 8-byte unsigned integer
};

For an instance created with a=0xBADC0DE and b=0xACCE55ED:

  • bytes(instance) must produce a 12-byte result.
  • The result must equal:
    b"\x0b\xad\xc0\xde\x00\x00\x00\x00\xac\xceU\xed"
    (the 4-byte big-endian encoding of a followed by the 8-byte big-endian encoding of b).
  • bytes(instance) must equal instance.dumps().

API Surface

  • Module: cstruct
  • Class: cstruct.cstruct — used to construct a parser instance; cstruct(endian=">") sets big-endian ordering.
  • The parser's load(definition_string) method registers structure types; a loaded structure named test is then instantiable as parser.test(a=..., b=...).
  • Each structure instance must support:
    • __bytes__(self) -> bytes
    • the existing dumps(self) -> bytes (unchanged behavior)

Overview

This task concerns a C-struct parsing library (imported as cstruct). You must ensure the library supports 128-bit integer types (int128 and uint128) both as standalone byte integers and as field types within struct definitions parsed from C-style declarations. The existing BytesInteger type must already handle arbitrary byte widths, but you must verify/ensure it correctly handles 16-byte (128-bit) values, and you must register int128 and uint128 as recognized type names in the C-struct type resolver.

Public API

The tests use the following import surface, which must exist:

  • cstruct — the top-level package/module.

  • cstruct.cstruct() — a constructor for a cstruct instance (call it cs). This instance:

    • Is callable via cs.load(cdef, compiled=...) to parse a C-style struct definition string.
    • Exposes parsed struct types as attributes (e.g. cs.test), where each struct type is callable with a bytes buffer to produce a parsed object.

  • BytesInteger — a class importable from the cstruct package. Constructed as:

    BytesInteger(cs, name: str, size: int, signed: bool)

    where cs is a cstruct instance, name is the type name string, size is the width in bytes, and signed is a keyword-capable boolean.

Behavior of BytesInteger

A BytesInteger instance is callable and supports array/parse and dump operations.

Parsing (calling the instance)
  • instance(buf) where buf is a bytes object of length size: parses a single integer from the first size bytes and returns a Python int.
  • instance[n](buf) where n is a positive integer: parses n consecutive integers, each size bytes wide, returning a list[int] of length n.
  • instance[None](buf): parses a null-terminated array — reads consecutive size-byte integers until an all-zero (value 0) element is encountered, returning a list[int] of the elements read before the terminator (the terminator itself is not included).
Endianness

The byte order used to interpret values is determined by the associated cstruct instance's configured endianness. By default the cstruct instance interprets integers as little-endian. A cstruct instance can be configured for big-endian interpretation; in that mode multi-byte values are read most-significant-byte first.

Signedness
  • When signed=False, values are interpreted as unsigned. The full range 0 .. 2**(8*size) - 1 is representable.
  • When signed=True, values are interpreted as two's-complement signed integers over size bytes. Negative values decode accordingly (e.g. all-0xff bytes decode to -1).
128-bit requirement (16-byte width)

BytesInteger must correctly handle size=16. Concrete expectations:

Little-endian, unsigned (size=16, signed=False):

  • b"A" * 16 → 0x41414141414141414141414141414141
  • b"\xff" * 16 → 0xFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFF
  • [2] over b"A"*16 + b"B"*16 → [0x41414141414141414141414141414141, 0x42424242424242424242424242424242]
  • [None] over b"A"*16 + b"\x00" → [0x41414141414141414141414141414141]

Little-endian, signed (size=16, signed=True):

  • b"A" * 16 → 0x41414141414141414141414141414141
  • b"\xff" * 16 → -1
  • [2] over b"\xff"*16 + b"\xfe" + b"\xff"*15 → [-1, -2]

Big-endian, unsigned (size=16, signed=False):

  • b"\x00"*15 + b"\xff" → 255
  • b"\xff" * 16 → 0xFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFF
  • [2] over b"\x00"*15 + b"A" + b"\x00"*15 + b"B" → [0x41, 0x42]

Big-endian, signed (size=16, signed=True):

  • b"\x00"*15 + b"\xff" → 255
  • b"\xff" * 16 → -1
  • b"\xff"*15 + b"\x01" → -255
  • [2] over b"\xff"*16 + b"\xff"*15 + b"\xfe" → [-1, -2]
Dumping and range checking
  • Each instance supports a dumps(value: int) method that serializes an integer to its bytes representation of width size, honoring configured endianness and signedness.
  • dumps must raise OverflowError when the value cannot be represented in size bytes given the signedness:
    • For a signed 16-byte integer, valid range is -(2**127) .. 2**127 - 1. Values -(2**127)+1 and 2**127 - 1 must succeed; values -(2**127)-1 and 2**127 must raise OverflowError.
    • The same boundary rule applies for the previously supported widths (1/2/3 bytes) with their respective ranges.

C-struct type registration requirement

The C-struct definition parser (used via cs.load(...)) must recognize int128 and uint128 as valid field type names, mapping them to signed / unsigned 16-byte byte-integer types respectively. These types must work:

  • As scalar fields, e.g. int128 e; / uint128 d;.
  • As fixed-size array fields, e.g. int128 f[2]; / uint128 e[2];.

They must interoperate with the cstruct instance's configured endianness (both little- and big-endian) and must round-trip: parsing a buffer into a struct object and then serializing that object (obj.dumps()) must reproduce the original buffer bytes.

Struct parsing expectations (illustrative)

Given a little-endian cstruct with a struct containing (among other fields) int128 e; and int128 f[2];, parsing a buffer whose relevant bytes are b"A"*16 followed by b"\xff"*16 + b"\x01" + b"\xff"*15 yields:

  • e == 0x41414141414141414141414141414141
  • f == [-1, -255]

Given a little-endian cstruct with uint128 d; and uint128 e[2];, parsing relevant bytes b"A"*16 followed by b"A" + b"\x00"*15 + b"B" + b"\x00"*15 yields:

  • d == 0x41414141414141414141414141414141
  • e == [0x41, 0x42]

Given a big-endian cstruct with int128 e; and int128 f[2];, parsing relevant bytes b"A"*16 followed by b"\x00"*15 + b"A" + b"\x00"*15 + b"B" yields:

  • e == 0x41414141414141414141414141414141
  • f == [0x41, 0x42]

Given a big-endian cstruct with uint128 d; and uint128 e[2];, parsing relevant bytes b"\xff"*16 followed by b"\x00"*14 + b"AA" + b"\x00"*14 + b"BB" yields:

  • d == 0xFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFF
  • e == [0x4141, 0x4242]

Compiled and non-compiled modes

Struct parsing via cs.load(cdef, compiled=<bool>) must produce equivalent results whether or not the compiled code path is used. The new 128-bit field types must behave identically (same parsed values and same dumps() output) in both modes, and must be compatible with whatever mechanism verifies that a struct was compiled when requested.

Scope

The only functional change required is support for the 128-bit (int128 / uint128, 16-byte) integer types described above, both directly through BytesInteger and through the C-struct type name resolver. All previously supported widths and behaviors must remain unchanged.

Task: Support char type fields in bitfields

Background

This project (cstruct) parses C-style struct definitions and reads/writes binary data according to those definitions. Struct definitions may contain bitfields — fields declared with a bit-width using the name : width syntax. The bitfield reading/writing logic must correctly handle fields whose type is char, in addition to integer types.

Currently, char-typed bitfields do not work because the bitfield logic performs bitwise operations that require integer values, and char fields are not converted to integers before those operations.

Required Change

Bitfield parsing must support fields declared with the char type. When a bitfield field is of char type, its value must be converted to an integer so that the bitwise extraction (reading) and packing (writing) operations produce correct results.

Behavior to Implement

Given a struct definition loaded via the cstruct API, a struct containing a mix of integer bitfields, a char bitfield, and a regular (non-bitfield) char array must correctly read from and write to binary data.

Public API
  • Module: cstruct (importable as import cstruct)
  • Class: cstruct.cstruct — instantiated with no arguments: cs = cstruct.cstruct()
  • Method: cs.load(cdef, compiled=<bool>) — loads a C struct definition from the string cdef. The compiled boolean selects between two internal parsing/reading strategies; both strategies must produce identical results.
  • Loaded structs are accessible as attributes on the cstruct instance (e.g. cs.test).
  • A struct type is callable with a bytes buffer to parse an instance: obj = cs.test(buf).
  • Parsed fields are accessible as attributes on the resulting object (e.g. obj.a).
  • Parsed instances expose a dumps() method returning a bytes object that serializes the instance back to its binary form.
Concrete behavior

For the struct definition:

struct test {
    uint16  a : 4;
    uint16  b : 4;
    char    c : 8;
    char    d[4];
};

Fields:

  • a: a 4-bit field of type uint16.
  • b: a 4-bit field of type uint16.
  • c: an 8-bit field of type char.
  • d: a 4-element char array (a regular non-bitfield field).

Parsing the buffer b"\x12\x00\xff\x69420":

  • obj.a must equal 0b0010 (2)
  • obj.b must equal 0b0001 (1)
  • obj.c must equal 0b11111111 (255) — i.e. an integer value, not a byte string
  • obj.d must equal b"i420"

The bitfield extraction ordering is little-endian at the bit level: for the byte 0x12 shared by fields a (first 4 bits) and b (next 4 bits), a takes the low nibble (0x2) and b takes the high nibble (0x1).

Serialization round-trips exactly: calling obj.dumps() on the parsed instance must return the original buffer b"\x12\x00\xff\x69420".

Both the compiled and non-compiled loading strategies must yield these same results, including correct verification that the compiled form matches the non-compiled form.

Task: Add Multi-Dimensional Array Support to cstruct

Overview

The dissect.cstruct library parses and compiles C-style structure definitions. You must extend it to support multi-dimensional arrays (arrays of arrays) in field definitions, using multiple consecutive sets of square brackets in a field declaration.

Public API (already exists / must remain importable)

  • dissect.cstruct.cstruct — the main class. Instantiated as cstruct.cstruct(endian="<") (endian is optional). Provides:
    • .load(cdef, compiled=<bool>) — parses and registers structure definitions from a source string. The compiled keyword argument defaults to its existing behavior when omitted; when passed it selects whether the parsed structs use the compiled read path.
    • .resolve(name) — resolves a type name to a type instance.
    • Loaded struct types become attributes on the instance (e.g. cs.args, cs.test), each callable with a bytes buffer to parse an instance, and each parsed instance supports .dumps() returning the serialized bytes.
  • dissect.cstruct.exceptions.ParserError — an exception class that must be importable from this module path and raised for the parse error described below.
  • dissect.cstruct.exceptions.ResolveError — existing exception (unchanged).

Required Behavior

Parsing multi-dimensional array fields

A field declaration may include more than one set of square brackets, e.g.:

struct test {
    uint8   a[2][2][2];
}

Each set of brackets adds a dimension to the array. A bracket dimension's length may be:

  • A numeric constant (e.g. [8], [2]).
  • A reference to another field already defined in the same struct (e.g. [argc]), which is resolved at parse time from the value read for that field.
  • Empty ([]), meaning a variable/dynamically-sized dimension.

This applies for any number of dimensions (two or three dimensions must both work).

Empty-bracket dimension rule

An empty set of brackets ([]) is only permitted as the last (innermost/rightmost) dimension. If an empty bracket appears in any position other than the final one (e.g. char argv[][argc]), parsing must raise ParserError with the exact message:

Depth required for multi-dimensional array

An empty final dimension is allowed (e.g. char argv[argc][]).

Reading / decoding multi-dimensional arrays

The cstruct class is constructed and used as follows:

from dissect import cstruct

cs = cstruct.cstruct(pointer="uint8")
cs.load(cdef_string)
  • The cstruct.cstruct(...) constructor accepts a keyword argument pointer that names the integer type used as the underlying storage/width for pointer values. When pointer="uint8", pointers are read from a single byte.
  • After cs.load(cdef_string), any type or typedef defined in the source becomes accessible as an attribute on cs (e.g. cs.uuid_t, cs.ptr, cs.test), and via the existing resolution mechanism.

Required Behavior

Array typedefs

A typedef of the form:

typedef char uuid_t[16];

must define a new named type uuid_t that is an array type:

  • cs.uuid_t must be an instance of dissect.cstruct.types.Array.
  • The array element type is the base type (char) and the array length is the bracketed count (16).
  • Parsing bytes with this type reads the full array. For a 16-element char array, cs.uuid_t(b"\x01" * 16) must return b"\x01" * 16 (i.e. the parsed value compares equal to the raw 16 bytes).
Pointer typedefs

A typedef of the form:

typedef uint32 *ptr;

must define a new named type ptr that is a pointer type:

  • cs.ptr must be an instance of dissect.cstruct.types.Pointer.
  • The pointer's target type is the base type (uint32).
  • The pointer's own on-disk width is determined by the cstruct's configured pointer type. With pointer="uint8", the pointer value is read from a single leading byte.
  • Parsing bytes yields a pointer object whose integer value equals the pointer address read from the input, and which compares equal to that integer. For example, given cs.ptr(b"\x01AAAA"):
    • the pointer value equals 1 (read from the first byte \x01).
    • calling .dereference() on it reads the target type (uint32) at the pointed-to offset within the same data. With address 1, dereferencing reads the 4 bytes b"AAAA" as a little-endian uint32, yielding 0x41414141.
Use within structs

These typedef'd types must be usable as field types inside struct definitions. Given:

typedef char uuid_t[16];
typedef uint32 *ptr;

struct test {
    uuid_t uuid;
    ptr ptr;
};

Parsing an instance obj = cs.test(b"\x01" * 16 + b"\x11AAAA") must yield:

  • obj.uuid equal to b"\x01" * 16 (the 16-byte array field consumes the first 16 bytes).
  • obj.ptr is a pointer read from the next byte (\x11 → address 0x11); calling obj.ptr.dereference() reads the uint32 at offset 0x11 within the full input data, yielding 0x41414141 (the bytes b"AAAA" located at that offset).
Bitfield typedefs are invalid

A typedef must not declare a bitfield. Attempting to load a definition such as:

typedef uint8 with_bits : 4;

must raise dissect.cstruct.exceptions.ParserError. The exception message must contain the text:

line 1: typedefs cannot have bitfields

Notes

  • Existing typedef behavior for simple aliases must remain intact; this task only adds array/pointer forms and the bitfield rejection.
  • Import path for the error type: from dissect.cstruct.exceptions import ParserError.

Add LEB128 integer support

Add unsigned and signed LEB128 integer types to the public dissect.cstruct API and make them usable both directly and in structure definitions.

Public API

The package must support:

from dissect import cstruct

cs = cstruct.cstruct()

Each cstruct.cstruct instance must expose two callable type objects:

  • cs.uleb128(data: bytes) -> int
  • cs.ileb128(data: bytes) -> int

Both type objects must provide:

  • dumps(value: int) -> bytes

Additionally, cs.uleb128 must provide:

  • write(stream, value: int) -> int

stream may be an io.BytesIO object.

Scalar decoding

uleb128 must decode unsigned LEB128 values as follows:

Input bytes Result
b"\x02" 2
b"\x8b\x25" 4747
b"\xc9\x8f\xb0\x06" 13371337
b"\x7e" 126
b"\xf5\x5a" 11637
b"\xde\xd6\xcf\x7c" 261352286

ileb128 must decode signed LEB128 values as follows:

Input bytes Result
b"\x02" 2
b"\x8b\x25" 4747
b"\xc9\x8f\xb0\x06" 13371337
b"\x7e" -2
b"\xf5\x5a" -4747
b"\xde\xd6\xcf\x7c" -7083170

If unsigned decoding reaches EOF after reading a continuation byte but before reading the final LEB128 byte, it must raise EOFError. For example, decoding b"\x8b" must raise an error whose message contains:

Value Output bytes
2 b"\x02"
4747 b"\x8b\x25"
13371337 b"\xc9\x8f\xb0\x06"

cs.ileb128.dumps() must produce:

Value Output bytes
2 b"\x02"
4747 b"\x8b\x25"
13371337 b"\xc9\x8f\xb0\x06"
-2 b"\x7e"

Structure-definition integration

uleb128 and ileb128 must be recognized as built-in field types by:

cs.load(cdef, compiled=True)
cs.load(cdef, compiled=False)

All behavior below must work in both modes.

LEB128 values as array lengths

Given:

struct test {
    uleb128 len;
    char    data[len];
};

Parsing:

buf = b"\xaf\x18" + (b"\x41" * 3119)
obj = cs.test(buf)

must produce:

  • obj.len == 3119
  • obj.data == b"\x41" * 3119
  • len(obj.data) == 3119
  • obj.dumps() == buf
Zero-terminated unsized arrays

Given:

struct test {
    uleb128 numbers[];
};

parsing:

b"\xaf\x18\x8b\x25\xc9\x8f\xb0\x06\x00"

must produce obj.numbers containing exactly:

[3119, 4747, 13371337]

The terminating encoded zero is not part of the logical array, but obj.dumps() must reproduce the complete original buffer, including the terminator.

The same behavior is required for signed values:

struct test {
    ileb128 numbers[];
};

Parsing:

b"\xaf\x18\xf5\x5a\xde\xd6\xcf\x7c\x00"

must produce exactly:

[3119, -4747, -7083170]

and obj.dumps() must reproduce the original buffer including its terminating zero.

Both signed and unsigned LEB128 types must work as lengths and element counts in nested structures.

For the unsigned form:

struct entry {
    uleb128 len;

    uint32  crc;
};

struct nested {
    uleb128 name_len;
    char    name[name_len];
    uleb128 n_entries;
    entry   entries[n_entries];
};

For the signed form, replace each uleb128 above with ileb128.

In either case, parsing:

buf = b"\x08Testfile\xac\x02"
buf += b"\x04AAAABBBB" * 300

must produce:

  • obj.name_len == 8
  • obj.name == b"Testfile"
  • obj.n_entries == 300
  • obj.dumps() == buf
20 You must ensure that arithmetic expressions provided as strings are correctly evaluated when they contain tab characters (\t) as whitespace. 223 words · source specification
Overview

You must ensure that arithmetic expressions provided as strings are correctly evaluated when they contain tab characters (\t) as whitespace.

Required Behavior

The expression evaluation logic must treat tab characters as insignificant whitespace, exactly as it already treats space characters. Tabs appearing anywhere in an expression string — before, between, or after tokens and operators — must be ignored and must not affect the evaluated result.

For example, evaluating an expression string equivalent to "\t7\t*\t8\t" must produce the integer 56, identical to the result of evaluating "7*8", "7 *8", or " 7 * 8 ".

This must hold in general: any combination of leading, trailing, and interspersed tab characters (mixed with or in place of spaces) around numeric operands and arithmetic operators must yield the same numeric result as the equivalent expression with that whitespace removed.

Scope
  • Only whitespace handling is affected. The set of characters treated as ignorable whitespace must include the tab character in addition to the space character.
  • All existing supported operations (e.g., multiplication *, division /) and their numeric results remain unchanged.
  • No new operators, functions, or evaluation semantics are introduced.
Constraints

The change must be confined to how the expression parser/evaluator handles whitespace. Do not alter the numeric results of any expression that does not contain tabs.
