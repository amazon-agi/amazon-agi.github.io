01 Default Values for Null-Terminated and Dynamic Arrays 685 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Default Values for Null-Terminated and Dynamic Arrays

Background

This task is about cstruct, a C-structure parsing library that makes it possible to define C-style structs from textual definitions and to instantiate them as Python objects. The library is imported as follows:

import cstruct

Structures are defined by means of a C-like definition string and loaded using:

cs = cstruct.cstruct()
cs.load(cdef, compiled=<bool>)

Each loaded struct becomes available as an attribute of the cstruct instance (e.g. cs.test). Instantiating a struct with no arguments (e.g. cs.test()) must produce an object whose fields hold sensible default values and that can be serialized back to bytes via its .dumps() method.

Behavior Requirements

When a struct is instantiated with no field values supplied, a default value must be assigned to every field. This task concentrates specifically on array fields with a length that is not a fixed compile-time constant, that is:

  • Null-terminated / unbounded arrays — these are declared with empty brackets, e.g. uint32 field[];
  • Dynamic arrays — these have a length that references another field, e.g. uint32 field[x];

For both of these array kinds, instantiating the struct with no arguments must produce as the default an empty sequence appropriate to the element type:

Element type of the array Default value
Integer types (e.g. uint8, uint32) [] (empty list)
Multi-byte "bytes-int" integer types (e.g. uint24) [] (empty list)
Arrays of char elements b"" (empty bytes)
Arrays of wchar elements "" (empty string)
Arrays with an enum element type [] (empty list)
Arrays with a flag element type [] (empty list)

Put differently:

  • The default of char[...] and char[] is an empty bytes object.
  • The default of wchar[...] and wchar[] is an empty str.
  • All other element types (plain integers, multi-byte integers, enums, flags) default to an empty list, no matter whether the array is dynamic or null-terminated.

Whether the array is null-terminated ([]) or dynamic ([x]), the default must be identical.

Behavior During Serialization

The default-constructed object that results must be serializable with .dumps(). When all array fields default to empty sequences, they contribute zero bytes to the serialized output. The only fields that contribute bytes are fixed-size scalar fields.

As an example, for a struct with one uint8 scalar field followed by twelve empty dynamic/null-terminated array fields, .dumps() produces bytes made up solely of the scalar field's default (a single zero byte) plus the null terminators, if any, that a serialized empty array of that kind requires. Concretely, for a struct laid out as:

  • one uint8
  • pairs of a null-terminated and a dynamic array for each of: 32-bit int, 24-bit int, char, wchar, enum, flag

the overall serialized length of the default-constructed object comes to 19 bytes, all zero (b"\x00" * 19). This total is made up of the single scalar byte plus the terminator bytes emitted for each null-terminated array of a given element width.

Definition Forms Supported in Scope

The definition parser must handle, within a single definition, a struct that contains all of the following field forms and must produce correct defaults for each:

  • Declarations of enum and flag types with named members.
  • A uint8 scalar field in the leading position.
  • For uint32, uint24, char, wchar, enum types, and flag types, both null-terminated and dynamic array variants.

Public API

The change introduces no new public names. The engineer must ensure that the existing API behaves as specified:

  • cstruct.cstruct() — builds a parser/registry instance.
  • cstruct.cstruct().load(cdef: str, compiled: bool) — parses a definition string; compiled chooses between the compiled and non-compiled code paths, and both paths must yield identical default-construction and serialization behavior.
  • Loaded structs are exposed as attributes on the cstruct instance and can be called with no arguments to build a default instance.
  • Each struct instance exposes its fields as attributes plus a .dumps() method that returns bytes.

Under both compiled=True and compiled=False, the behavior described above must hold.

Task Specification: Range Validation for BytesInteger Serialization

Summary

At serialization time, the BytesInteger type from dissect.cstruct.types (importable via from dissect.cstruct.types import BytesInteger) must validate that integer values fit within the representable range for their configured byte width and signedness. An error must be raised for values outside that range.

API

The BytesInteger class must be constructible using this signature (the form used in this task):

BytesInteger(cstruct_instance, name, size, signed=<bool>)

The parameters are:

  • cstruct_instance — an instance of dissect.cstruct.cstruct().
  • name — the type's name as a string (e.g. "int8").
  • size — the integer's width in bytes (e.g. 1, 2, 3).
  • signed — a keyword argument; True means a signed integer, False an unsigned one.

The class must provide a method for serialization:

BytesInteger.dumps(value)

which serializes the integer value supplied to it.

Required Behavior

dumps(value) must enforce the valid value range determined by size (in bytes) together with signed:

  • Signed (signed=True): the valid range runs from -(2^(8*size - 1)) to 2^(8*size - 1) - 1, inclusive.
  • Unsigned (signed=False): the valid range runs from 0 to 2^(8*size) - 1, inclusive.
Values inside the range

For any value within the valid range (both boundary endpoints included), dumps(value) must serialize normally without raising.

Specific boundary examples that must succeed:

  • size=1, signed: -128 and 127
  • size=1, unsigned: 0 and 255
  • size=2, signed: -32768 and 32767
  • size=3, signed: -8388608 and 8388607
Values outside the range

For any value outside the valid range (either below the minimum or above the maximum), dumps(value) must raise OverflowError.

Specific examples that must raise OverflowError:

  • size=1, signed: -129 and 128
  • size=1, unsigned: -1 and 256
  • size=2, signed: -32769 and 32768
  • size=3, signed: -8388609 and 8388608

The OverflowError should carry a message that describes the problem.

Constraints

  • The change covers arbitrary byte widths (not just fixed sizes), with the valid range computed from the size and signed parameters.
  • Serialization behavior that already exists for in-range values (single values and any forms supported previously) must remain unchanged.

Task: Implement __bytes__ Support for cstruct Instances

Goal

Make instances of parsed C structures (created via the cstruct library) convertible into their raw binary representation by means of Python's built-in bytes() function.

Context

The cstruct module, which can be imported as cstruct, offers a cstruct.cstruct class that parses C-style structure definitions and generates structure types. An instance of a parsed structure can already be serialized to bytes through the existing dumps() method, which returns the packed binary representation of the instance's fields according to the declared field types and the endianness that has been configured.

Requirements

Instances of structures must implement the __bytes__ special method, so that a call to the built-in bytes() on an instance returns the instance's raw serialized binary representation.

The result obtained from bytes(instance) must be identical to the result obtained from instance.dumps().

Behavior Details

  • The value that is returned must be a bytes object.
  • Its length must equal the total packed size of all the declared fields.
  • Field values must be encoded in the order in which the fields are declared, honoring both the field types and the endianness configured on the owning cstruct instance.
Worked Example

Consider a structure loaded with big-endian (>) byte ordering:

struct test {
    DWORD   a;   // 4-byte unsigned integer
    QWORD   b;   // 8-byte unsigned integer
};

When an instance is created with a=0xBADC0DE and b=0xACCE55ED:

  • bytes(instance) must produce a result of 12 bytes.
  • The result must equal:
    b"\x0b\xad\xc0\xde\x00\x00\x00\x00\xac\xceU\xed"
    (that is, the 4-byte big-endian encoding of a followed by the 8-byte big-endian encoding of b).
  • The value of bytes(instance) must equal instance.dumps().

API Overview

  • Module: cstruct
  • Class: cstruct.cstruct — employed to construct a parser instance; cstruct(endian=">") sets big-endian ordering.
  • Structure types are registered by way of the parser's load(definition_string) method; once a structure named test has been loaded, it can then be instantiated as parser.test(a=..., b=...).
  • Every structure instance must support:
    • __bytes__(self) -> bytes
    • the existing dumps(self) -> bytes (behavior unchanged)
04 This task is about a library for parsing C structs (imported as cstruct). 1020 words · source specification, reworded by GLM-5.3-Flash

Task Description

Overview of the Task

This task is about a library for parsing C structs (imported as cstruct). You must ensure that the library supports the 128-bit integer types (int128 and uint128), both as standalone byte integers and as field types within struct definitions parsed from C-style declarations. The existing BytesInteger type must already handle arbitrary byte widths, but you must verify/ensure that it correctly handles 16-byte (128-bit) values, and you must register int128 and uint128 as recognized type names in the C-struct type resolver.

Public API Surface

The tests rely on the import surface below, which must exist:

  • cstruct — the top-level package/module.

  • cstruct.cstruct() — a constructor for a cstruct instance (refer to it as cs). This instance:

    • Is callable via cs.load(cdef, compiled=...) to parse a string containing a C-style struct definition.
    • Exposes parsed struct types as attributes (e.g. cs.test); each struct type is callable with a bytes buffer to produce a parsed object.

  • BytesInteger — a class that can be imported from the cstruct package. It is constructed as:

    BytesInteger(cs, name: str, size: int, signed: bool)

    where cs is a cstruct instance, name is the string holding the type name, size is the width in bytes, and signed is a boolean that can be passed by keyword.

BytesInteger behavior

An instance of BytesInteger is callable, and it supports array/parse and dump operations.

Parsing (invoking the instance)
  • instance(buf), where buf is a bytes object of length size: parses one integer from the first size bytes and returns a Python int.
  • instance[n](buf), where n is a positive integer: parses n consecutive integers, each size bytes wide, and returns a list[int] of length n.
  • instance[None](buf): parses a null-terminated array — it reads consecutive size-byte integers until an element that is all-zero (value 0) is encountered, and returns a list[int] of the elements read before the terminator (the terminator itself is not included).
Endianness

The endianness configured on the associated cstruct instance determines the byte order used to interpret values. By default, a cstruct instance interprets integers as little-endian. A cstruct instance can be configured for big-endian interpretation; in that mode, multi-byte values are read most-significant-byte first.

Signedness
  • For signed=False, values are interpreted as unsigned. The full range 0 .. 2**(8*size) - 1 is representable.
  • For signed=True, values are interpreted as two's-complement signed integers spanning size bytes. Negative values decode accordingly (e.g. bytes that are all 0xff decode to -1).
Requirement for 128-bit support (16-byte width)

BytesInteger must handle size=16 correctly. The concrete expectations are:

Little-endian, unsigned case (size=16, signed=False):

  • b"A" * 16 → 0x41414141414141414141414141414141
  • b"\xff" * 16 → 0xFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFF
  • [2] applied to b"A"*16 + b"B"*16 → [0x41414141414141414141414141414141, 0x42424242424242424242424242424242]
  • [None] applied to b"A"*16 + b"\x00" → [0x41414141414141414141414141414141]

Little-endian, signed case (size=16, signed=True):

  • b"A" * 16 → 0x41414141414141414141414141414141
  • b"\xff" * 16 → -1
  • [2] applied to b"\xff"*16 + b"\xfe" + b"\xff"*15 → [-1, -2]

Big-endian, unsigned case (size=16, signed=False):

  • b"\x00"*15 + b"\xff" → 255
  • b"\xff" * 16 → 0xFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFF
  • [2] applied to b"\x00"*15 + b"A" + b"\x00"*15 + b"B" → [0x41, 0x42]

Big-endian, signed case (size=16, signed=True):

  • b"\x00"*15 + b"\xff" → 255
  • b"\xff" * 16 → -1
  • b"\xff"*15 + b"\x01" → -255
  • [2] applied to b"\xff"*16 + b"\xff"*15 + b"\xfe" → [-1, -2]
Dumping and range checks
  • Each instance supports a dumps(value: int) method that serializes an integer into its bytes representation of width size, honoring the configured endianness and signedness.
  • dumps must raise OverflowError when a value cannot be represented in size bytes for the given signedness:
    • For a signed 16-byte integer, the valid range is -(2**127) .. 2**127 - 1. The values -(2**127)+1 and 2**127 - 1 must succeed; the values -(2**127)-1 and 2**127 must raise OverflowError.
    • The same boundary rule applies for the widths supported previously (1/2/3 bytes), with their respective ranges.

Requirement for C-struct type registration

The C-struct definition parser (used via cs.load(...)) must recognize int128 and uint128 as valid field type names, and must map them to signed / unsigned 16-byte byte-integer types respectively. These types must work in the following roles:

  • As scalar fields, e.g. int128 e; / uint128 d;.
  • As fixed-size array fields, e.g. int128 f[2]; / uint128 e[2];.

They must interoperate with the endianness configured on the cstruct instance (both little- and big-endian), and they must round-trip: when a buffer is parsed into a struct object and that object is then serialized (obj.dumps()), the original buffer bytes must be reproduced.

Illustrative struct parsing expectations

With a little-endian cstruct whose struct contains (among other fields) int128 e; and int128 f[2];, parsing a buffer whose relevant bytes are b"A"*16 followed by b"\xff"*16 + b"\x01" + b"\xff"*15 yields:

  • e == 0x41414141414141414141414141414141
  • f == [-1, -255]

With a little-endian cstruct that has uint128 d; and uint128 e[2];, parsing the relevant bytes b"A"*16 followed by b"A" + b"\x00"*15 + b"B" + b"\x00"*15 yields:

  • d == 0x41414141414141414141414141414141
  • e == [0x41, 0x42]

With a big-endian cstruct that has int128 e; and int128 f[2];, parsing the relevant bytes b"A"*16 followed by b"\x00"*15 + b"A" + b"\x00"*15 + b"B" yields:

  • e == 0x41414141414141414141414141414141
  • f == [0x41, 0x42]

With a big-endian cstruct that has uint128 d; and uint128 e[2];, parsing the relevant bytes b"\xff"*16 followed by b"\x00"*14 + b"AA" + b"\x00"*14 + b"BB" yields:

  • d == 0xFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFF
  • e == [0x4141, 0x4242]

Compiled versus non-compiled modes

Parsing structs via cs.load(cdef, compiled=<bool>) must produce equivalent results, whether or not the compiled code path is used. The new 128-bit field types must behave identically in both modes (same parsed values and same dumps() output), and they must be compatible with whatever mechanism verifies that a struct was compiled when requested.

Scope of the change

The only functional change that is required is support for the 128-bit (int128 / uint128, 16-byte) integer types described above, both directly through BytesInteger and through the C-struct type name resolver. All previously supported widths and behaviors must remain unchanged.

Task Specification: Adding float16 Support to cstruct

Overview

The task is to add support for a 16-bit floating point type (float16) to the dissect.cstruct library. This type must behave consistently with the packed floating point types that already exist (such as float), covering parsing from bytes, serialization to bytes, use inside struct definitions, and both little-endian and big-endian byte orders.

Public API Surface

The PackedType class

It must be possible to import the class PackedType from dissect.cstruct.types:

from dissect.cstruct.types import PackedType

The following positional arguments must be accepted by the constructor:

PackedType(cstruct_instance, name, size, packchar)
  • cstruct_instance: the instance of cstruct that the type belongs to.
  • name (str): the name of the type, e.g. "float16".
  • size (int): the type's size in bytes, e.g. 2.
  • packchar (str): the underlying pack format character used for encoding and decoding, e.g. "e" for an IEEE 754 half-precision float.

Instances must provide the following:

  • dumps(value) → bytes: serialize a numeric value into its byte representation based on the type's size, pack format, and the endianness of the associated cstruct instance.
  • reads(data) → numeric: parse a numeric value from the beginning of the bytes object data, based on the type's size, pack format, and endianness.
Registration of the float16 type

The cstruct instance must expose a built-in packed type called float16, which is accessible as an attribute:

cs = cstruct.cstruct()
cs.float16

This type must be an IEEE 754 half-precision float that is 2 bytes in size (pack character "e"). It must also be usable inside struct definitions parsed via cs.load(cdef), e.g. for a field declared as float16 a;.

Required Behavior

Standalone serialization / parsing

With a default cstruct instance (its byte order defaults to little-endian):

  • cs.float16.dumps(420.69) results in b"\x93^".
  • cs.float16.reads(b"\x69\x69") results in 2770.0.

The float type that already exists (4 bytes) must keep working:

  • cs.float.dumps(31337.6969) results in b"e\xd3\xf4F".
  • cs.float.reads(b"M0MS") results in 881278648320.0.
Use inside structs (little-endian)

With this struct definition:

struct test {
    float16 a;
    float   b;
};

once it is loaded into a default (little-endian) cstruct instance, parsing the buffer b"69\xb1U$G" must yield a struct object in which:

  • the field a is equal to 0.6513671875
  • the field b is equal to 42069.69140625
Use inside structs (big-endian)

Using the same struct definition, but with the endianness of the cstruct instance set to big-endian (cs.endian = ">"), parsing the buffer b"69G$U\xb1" must yield a struct object in which:

  • the field a is equal to 0.388916015625
  • the field b is equal to 42069.69140625

The results must be identical and correct on both the compiled and the non-compiled struct code paths (the struct must be compilable).

Range / overflow handling

For a float16 type (2 bytes, pack char "e"), serialization through dumps must respect the half-precision float's valid representable range:

  • Values that fall within the range must serialize successfully. Specifically, -65519.999999999996 and 65519.999999999996 must be accepted.
  • Values that fall outside the representable range must raise OverflowError. Specifically, -65519.999999999997 and 65519.999999999997 must raise OverflowError.

Endianness

The dumps and reads behavior of a PackedType must honor the endianness that is configured on the associated cstruct instance (little-endian by default; this can be overridden via the endian attribute, e.g. ">" for big-endian).

Task: Support for char type fields in bitfields

Background

This project, cstruct, parses C-style struct definitions and reads and writes binary data in accordance with those definitions. A struct definition may contain bitfields — fields declared with a bit-width using the name : width syntax. The logic that reads and writes bitfields must handle fields whose type is char correctly, in addition to integer types.

At present, bitfields typed char do not work, because the bitfield logic carries out bitwise operations that require integer values, and char fields are not converted to integers before those operations.

Required Change

Bitfield parsing must support fields declared with the char type. Whenever a bitfield field is of char type, its value must be converted to an integer, so that the bitwise extraction (reading) and packing (writing) operations produce correct results.

Behavior to Be Implemented

Once a struct definition has been loaded through the cstruct API, a struct containing a mix of integer bitfields, a char bitfield, and a regular (non-bitfield) char array must read from and write to binary data correctly.

Public API
  • Module: cstruct — importable as import cstruct.
  • Class: cstruct.cstruct — no arguments are passed at instantiation: cs = cstruct.cstruct().
  • Method: cs.load(cdef, compiled=<bool>) — this loads a C struct definition from the string cdef. The compiled boolean determines which of two internal parsing/reading strategies is used; both strategies must produce identical results.
  • Structs that have been loaded can be accessed as attributes on the cstruct instance (e.g. cs.test).
  • A struct type can be called with a bytes buffer to parse an instance: obj = cs.test(buf).
  • The fields of a parsed instance can be accessed as attributes on the resulting object (e.g. obj.a).
  • Parsed instances expose a dumps() method, which returns a bytes object that serializes the instance back to its binary form.
Concrete behavior

For this struct definition:

struct test {
    uint16  a : 4;
    uint16  b : 4;
    char    c : 8;
    char    d[4];
};

Fields:

  • a: a field of type uint16 that is 4 bits wide.
  • b: a field of type uint16 that is 4 bits wide.
  • c: a field of type char that is 8 bits wide.
  • d: a char array with 4 elements (a regular field, not a bitfield).

When the buffer b"\x12\x00\xff\x69420" is parsed:

  • obj.a must equal 0b0010 (2)
  • obj.b must equal 0b0001 (1)
  • obj.c must equal 0b11111111 (255) — that is, an integer value, not a byte string
  • obj.d must equal b"i420"

At the bit level, the ordering used for bitfield extraction is little-endian: within the byte 0x12, which fields a (first 4 bits) and b (next 4 bits) share, a takes the low nibble (0x2) and b takes the high nibble (0x1).

Serialization round-trips exactly: obj.dumps(), when called on the parsed instance, must return the original buffer b"\x12\x00\xff\x69420".

Both loading strategies — the compiled one and the non-compiled one — must yield these same results, including correct verification that the compiled form matches the non-compiled form.

Public-facing API

This behavior must be supported by the following existing API:

All of the pointer behavior described below must work with both compiled=True and compiled=False.

Handling of the read context

When fields are read in a compiled structure, the _read hooks of field types must support being called with the current read context as the second argument:

_read(stream, context)

A custom field type that uses the following pattern must work inside a compiled structure:

def _read(self, stream, context=None):
    return self._t._read(stream, context) + 1

This includes forwarding the context that is received to the _read method of another built-in type.

Pointer arrays

This declaration:

struct mainargs {
    uint8_t argc;
    char *args[4];
}

must define args as an array of four character pointers, and not as one pointer to an array of four characters.

Given:

cs = cstruct.cstruct(pointer="uint16")
cs.load(cdef, compiled=compiled)

buf = (
    b"\x02"
    b"\x09\x00"
    b"\x16\x00"
    b"\x00\x00"
    b"\x00\x00"
    b"argument one\x00"
    b"argument two\x00"
)
obj = cs.mainargs(buf)

the object that results must satisfy:

  • obj.argc == 2
  • obj.args must be indexable as four pointer entries.
  • obj.args[2] == 0
  • obj.args[3] == 0
  • obj.args[0].dereference() == b"argument one"
  • obj.args[1].dereference() == b"argument two"

The pointer values that are not null are 16-bit offsets into the same input buffer, and dereferencing them must retain the source context that is needed to read the null-terminated byte strings being pointed to.

Pointer behavior that must be preserved

When two uint32 * fields hold the pointer values 4 and 8 with pointer="uint16", they must:

  • Compare as equal to the integer offsets 4 and 8.
  • Compare as unequal to each other initially.
  • Dereference little-endian uint32 values from those buffer positions.
  • Support pointer arithmetic via += and -=.
  • Through dumps(), serialize only their current 16-bit pointer values.

For example, after the offsets 4 and 8 are changed to 6 through arithmetic, both pointers must dereference 0x06050403, and the containing structure must dump as:

b"\x06\x00\x06\x00"

A pointer to a structure must allow direct access to the fields of the structure that is pointed to, including fixed arrays, integers, null-terminated byte strings, and null-terminated wide strings. When the containing pointer structure is serialized, it must emit the pointer field itself, and not the pointed-to data.

Dereferencing a scalar pointer that has a zero value, either through dereference() or through proxied access to the target field, must raise cstruct.NullPointerDereference.

Task: Add Support for Multi-Dimensional Arrays to cstruct

Overview

dissect.cstruct is a library for parsing and compiling C-style structure definitions. It must be extended to support multi-dimensional arrays (arrays of arrays) in field definitions, expressed as multiple consecutive sets of square brackets in a field declaration.

Depth required for multi-dimensional array

An empty dimension in the final position is allowed (e.g. char argv[argc][]).

Reading / decoding of multi-dimensional arrays

While a buffer is parsed into a struct instance, the field must produce nested sequences that mirror the declared dimensions and that can be indexed with successive [] operators.

Case 1 — fixed numeric dimensions (e.g. uint8 a[2][2][2]): Elements are read in row-major order (the last dimension varies fastest). For the definition above and the input bytes 01 02 03 04 05 06 07 08:

  • a[0][0][0]==1, a[0][0][1]==2, a[0][1][0]==3, a[0][1][1]==4,
  • a[1][0][0]==5, a[1][0][1]==6, a[1][1][0]==7, a[1][1][1]==8.

Case 2 — the outer dimension is a field reference, the inner dimension is empty, and the element type is char (e.g. char argv[argc][]): The value of the referenced field determines the outer count. Every element produced is the bytes up to (and excluding) the terminating null byte.

For a struct that has uint32 argc preceding, and input where argc == 2 is followed by hello\0world\0:

  • argv[0] == b"hello", argv[1] == b"world".

Case 3 — the outer dimension is a field reference, the inner dimension is a fixed numeric length, and the element type is char (e.g. char argv[argc][8]): Each element is a fixed-size character array with the inner length, and it is returned as raw bytes of exactly that length (any trailing null padding included — the bytes are not truncated at a null).

With uint32 argc preceding, argc == 4, and input lorem\0\0\0ipsum\0\0\0dolor\0\0\0sit amet (each chunk being 8 bytes):

  • argv[0] == b"lorem\0\0\0", argv[1] == b"ipsum\0\0\0", argv[2] == b"dolor\0\0\0", argv[3] == b"sit amet".
Serialization

Serializing a parsed multi-dimensional-array struct with .dumps() must reproduce the original byte buffer in the fixed-numeric-dimension case (round-trip identity); for example, the uint8 a[2][2][2] case above must dump back to 01 02 03 04 05 06 07 08.

Compiled and non-compiled paths

Notes / Scope

  • A dimension that is a field reference must resolve against the runtime value read for the referenced sibling field within the same struct.
  • Only the behavior described here is in scope; unrelated features must not be added.

When a union is loaded with align=True, the resulting total size must be a multiple of its alignment (in other words, the size must be padded up to the union's alignment boundary).

A union's alignment is given by the largest alignment requirement among its members. For the unpadded extent, take the largest size among its members. The final size is obtained by rounding the unpadded extent up to the next multiple of alignment.

To make this concrete, take a union defined as:

union test {
    uint64 a;
    uint32 b[3];
};

loaded with align=True, this gives:

  • The value of align is True.
  • alignment is 8 (the uint64 member drives this, since it requires 8-byte alignment).
  • size is 16. The member with the largest extent is b, a 3-element array of uint32 that occupies 12 bytes; this extent is rounded up to the next multiple of the union's 8-byte alignment, giving 16.

The standard sizes/alignments of the integer types are in effect: uint32 is 4 bytes (4-byte aligned), uint64 is 8 bytes (8-byte aligned).

struct in {

struct for {

};

The types listed below must be importable from dissect.cstruct.types:

  • Array
  • Pointer

(These are the type classes the library uses to represent array and pointer types. They must exist and be importable from that module path.)

The cstruct class is constructed and used in the following way:

from dissect import cstruct

cs = cstruct.cstruct(pointer="uint8")
cs.load(cdef_string)
  • The cstruct.cstruct(...) constructor accepts a keyword argument pointer naming the integer type used as the underlying storage/width for pointer values. With pointer="uint8", pointers are read from a single byte.
  • After cs.load(cdef_string), any type or typedef defined in the source becomes available as an attribute on cs (e.g. cs.uuid_t, cs.ptr, cs.test), and also via the existing resolution mechanism.

Required Functionality

Typedefs to array types

A typedef written as:

typedef char uuid_t[16];

must define a new named type uuid_t that is an array type:

  • cs.uuid_t must be an instance of the dissect.cstruct.types.Array class.
  • The element type of the array is the base type (char), and the length of the array is the bracketed count (16).
  • Parsing bytes with this type reads the entire array. For a 16-element char array, cs.uuid_t(b"\x01" * 16) must return b"\x01" * 16 (that is, the parsed value compares equal to the raw 16 bytes).
Typedefs to pointer types

A typedef written as:

typedef uint32 *ptr;

must define a new named type ptr that is a pointer type:

  • cs.ptr must be an instance of the dissect.cstruct.types.Pointer class.
  • The target type of the pointer is the base type (uint32).
  • The on-disk width of the pointer itself is determined by the cstruct's configured pointer type. When pointer="uint8", the pointer value is read from a single leading byte.
  • Parsing bytes yields a pointer object whose integer value equals the pointer address read from the input, and this object compares equal to that integer. For example, given cs.ptr(b"\x01AAAA"):
    • the pointer value equals 1 (read from the first byte, \x01).
    • calling .dereference() on it reads the target type (uint32) at the offset pointed to, within the same data. With address 1, dereferencing reads the 4 bytes b"AAAA" as a little-endian uint32, yielding 0x41414141.
Use inside struct definitions

These typedef'd types must be usable as field types within struct definitions. Given:

typedef char uuid_t[16];
typedef uint32 *ptr;

struct test {
    uuid_t uuid;
    ptr ptr;
};

Parsing an instance obj = cs.test(b"\x01" * 16 + b"\x11AAAA") must yield:

  • obj.uuid equal to b"\x01" * 16 (the array field of 16 bytes consumes the first 16 bytes).
  • obj.ptr is a pointer read from the next byte (\x11 → address 0x11); calling obj.ptr.dereference() reads the uint32 located at offset 0x11 in the full input data, yielding 0x41414141 (the bytes b"AAAA" found at that offset).
Typedefs declaring bitfields are invalid

A typedef must not declare a bitfield. Loading a definition like the following:

typedef uint8 with_bits : 4;

must raise dissect.cstruct.exceptions.ParserError. The exception message must contain the text:

line 1: typedefs cannot have bitfields

Additional Notes

  • Typedef behavior that already exists for simple aliases must remain intact; this task only adds the array/pointer forms and the bitfield rejection.
  • Import location for the error type: from dissect.cstruct.exceptions import ParserError.

Overview

You must ensure that arithmetic expressions supplied as strings are evaluated correctly when they contain tab characters (\t) as whitespace.

Required Behavior

Tab characters must be treated as insignificant whitespace by the expression evaluation logic, exactly as it already treats space characters. Within an expression string, tabs appearing anywhere — before, between, or after tokens and operators — must be ignored and must not affect the evaluated result.

For example, an expression string equivalent to "\t7\t*\t8\t", when evaluated, must produce the integer 56, identical to the result of evaluating "7*8", "7 *8", or " 7 * 8 ".

This must hold as a general rule: any combination of leading, trailing, and interspersed tab characters (mixed with or in place of spaces) surrounding numeric operands and arithmetic operators must yield the same numeric result as the equivalent expression with that whitespace removed.

Scope
  • The only aspect affected is whitespace handling. In addition to the space character, the set of characters treated as ignorable whitespace must include the tab character.
  • All operations that are already supported (e.g., multiplication *, division /) and the numeric results they produce remain unchanged.
  • No new operators, functions, or evaluation semantics are introduced.
Constraints

The change must be limited to the way the expression parser/evaluator handles whitespace. The numeric results of any expression that does not contain tabs must not be altered.
