01 The cayennelpp package, with which this task works, offers classes for constructing and parsing data frames in CayenneLPP format. 411 words · source specification, reworded by GLM-5.3-Flash

Overview

The cayennelpp package, with which this task works, offers classes for constructing and parsing data frames in CayenneLPP format. The work here is to modify the public API of the LppFrame class so that the collection of data entries it holds is exposed as a public attribute rather than through a method call.

Change Required

The LppFrame class (importable via from cayennelpp.lpp_frame import LppFrame) must expose the collection of data entries it contains through a public attribute named data.

Specifically:

  • Reading frame.data on an LppFrame instance must return the collection of data entries the frame currently holds, as a value that supports len().
  • The access must be plain attribute access — frame.data — not a method call. Any earlier method-based access (e.g. frame.data()) must no longer serve as the interface; the collection is obtained directly as an attribute.

Behavior That Must Remain Intact

All existing frame behavior must continue to work, with data now being an attribute:

  1. Empty frame: An LppFrame() that has just been constructed must have len(frame.data) == 0, and frame.bytes() must return an empty byte sequence.

  2. Construction from bytes: LppFrame.from_bytes(b) must parse a byte sequence into the appropriate number of data entries. When the byte sequence encodes two entries, len(frame.data) == 2, and calling frame.bytes() must reproduce the original byte sequence exactly.

  3. Construction from base64: LppFrame.from_base64(s) must parse a base64-encoded string into the appropriate data entries, yielding len(frame.data) == 2 when the input encodes two entries.

  4. Adding data entries: Once entries have been added through the frame's add_* methods, len(frame.data) must equal the number of entries added. Each of the following add methods must append one entry to frame.data:

    • add_digital_input(channel, value)
    • add_digital_output(channel, value)
    • add_analog_input(channel, value)
    • add_analog_output(channel, value)
    • add_temperature(channel, value)
    • add_humitidy(channel, value) (note this exact spelling)
    • add_pressure(channel, value)
    • add_gyrometer(channel, x, y, z)
    • add_gps(channel, x, y, z)
    • (any other existing sensor add methods used for luminosity/other sensors that append one entry)

    For instance, if four analog I/O entries are added, the result is len(frame.data) == 4; if six mixed sensor entries are added, the result is len(frame.data) == 6.

Summary

Turn the frame's collection of data entries from a method-based accessor into a directly accessible public attribute named data. All parsing, construction, byte serialization, and entry-adding behavior must remain unchanged; only how the entries collection is accessed changes, going from a call to an attribute reference.

Conversion contract

Shared behavior

The converters' existing validation behavior must be kept:

  • Each decoder requires a payload of exactly its documented length.
  • The encoders enforce tuple arity.
  • The illuminance, presence, humidity, and barometer encoders reject negative values. That restriction must not be added to digital I/O or to signed data types.
  • Presence and digital I/O stay raw byte conversions; their values must not be newly restricted to Boolean 0 and 1.
  • Humidity keeps its half-unit truncation behavior. As an example, an input lying between two representable half-unit steps decodes to the step obtained by int(value * 2) / 2.0.
  • The existing assertion-based rejection — of invalid lengths, tuple shapes, and the documented negative unsigned inputs — must remain compatible.

Integration and compatibility

How existing LppData and LppFrame operations encode or decode CayenneLPP payloads must not be changed by the relocation. After the relocation, converter lookup metadata and package-internal imports must continue to resolve, and existing frames must retain their byte-for-byte serialization and deserialization behavior.

Changes to scaling, signedness, quantization, payload sizes, tuple return shapes, frame formatting, or other unrelated package APIs are not called for by this task. The behavioral change that is required is the availability of the complete conversion surface from cayennelpp.lpp_type.

The cayennelpp.lpp_type module

For the sensor types it supports, this module offers pairs of functions that perform conversion in both directions between raw LPP byte buffers and Python value tuples.

*_to_bytes functions: general contract

The return value of any ..._to_bytes(value) function is a bytearray holding the encoded sensor value.

  • Outside of the humidity compatibility case covered further down, value must be a tuple whose entries are numeric.
  • A list does not count as a valid stand-in for a tuple and must raise an exception — this holds even for a one-dimensional type.
  • Exactly as many elements as the selected type requires must be present in the tuple; a tuple whose arity is off must raise an exception.
  • Where a type's domain is non-negative, negative values must be rejected.
  • The one exception that permits scalar input is lpp_humidity_to_bytes: a numeric scalar may be passed as shorthand for a one-element tuple, so it must accept either a one-element tuple or that scalar. Lists and other containers are not permitted under this exception.

A bytearray of exactly the required size is accepted by every ..._from_bytes(buffer) function, which then returns a tuple of numeric values.

  • A buffer that is either shorter or longer than the exact size for that type must lead to an exception being raised.
