HyP3 SDK Jobs and Batch API — Task Specification

Summary

The module hyp3_sdk.jobs is where the classes Job and Batch are to be implemented, while hyp3_sdk.exceptions receives a supporting exception class. Together, the two classes model single processing jobs as well as collections of them.

The hyp3_sdk.exceptions module

The following exception class is to be defined:

class HyP3Error(Exception):
    ...

The hyp3_sdk.jobs module

Imports of both Job and Batch must work in this form:

from hyp3_sdk.jobs import Batch, Job
The Job class

An instance of this class stands for one processing job.

Attributes and fields

The data a Job holds mirrors the fields found in a job dictionary:

  • job_id (str)
  • job_type (str)
  • name (str)
  • job_parameters (dict)
  • status_code (str) — one of "SUCCEEDED", "FAILED", "RUNNING", "PENDING" (further values are also possible).
  • request_time (datetime)
  • user_id (str)
  • expiration_time (datetime or absent) — present only for successful jobs
  • browse_images (list or absent)
  • thumbnail_images (list or absent)
  • files (list or absent)

A field that is optional in the source dictionary may be absent from the object (for example, a failed job has no expiration_time, browse_images, thumbnail_images, or files).

Job.from_dict(data: dict) -> Job (classmethod)

This classmethod builds a Job out of a supplied dictionary. Any of the keys listed below may be present in that dictionary:

  • job_id, job_type, name, job_parameters, status_code, user_id — plain values.
  • request_time — an ISO-8601 datetime string, which parsing must turn into a datetime.
  • expiration_time — an ISO-8601 datetime string (this key may be missing); whenever it is there, parsing must turn it into a datetime.
  • browse_images, thumbnail_images, files — lists, each of which may be missing.

The implementation must not require any key the input is missing, and keys of that kind must not occur in the round-tripped output described below.

to_dict(self) -> dict

This serializes the job back into a dictionary. What must come out is an exact reproduction of the dictionary originally supplied to from_dict, making the round trip lossless:

  • The datetime attributes (request_time, plus expiration_time when it is present) must be serialized back into the same ISO-8601 string form.
  • An attribute that was absent from the source dictionary must not show up in the output dictionary.
  • The order of the keys is irrelevant, but the set of keys together with their values must match the original.

Status-checking methods

All of the methods below take no arguments and return a bool that depends on the current value of status_code:

  • succeeded(self) -> bool — returns True if and only if status_code == "SUCCEEDED".
  • failed(self) -> bool — returns True if and only if status_code == "FAILED".
  • complete(self) -> bool — returns True if and only if the job has finished, i.e. its status_code is either "SUCCEEDED" or "FAILED".
  • running(self) -> bool — returns True if and only if the job is not complete; this covers "RUNNING", "PENDING", and any other non-terminal status.

These methods must reflect modifications made directly to status_code after construction.

expired(self) -> bool
  • When the job has an expiration_time, return True if and only if that time lies strictly in the past; return False otherwise.
  • Both timezone-aware and timezone-naive datetime values must be supported. ISO-8601 values that carry an offset stay timezone-aware after parsing, and the comparison to the current instant must use a compatible timezone-aware current time. When a caller assigns a timezone-naive datetime directly to expiration_time, compare it against the current local time expressed as a timezone-naive datetime (equivalent to datetime.now() semantics). A timezone-naive expiration value must never be mixed with a timezone-aware current value in a comparison.
  • When the job has no expiration_time (a failed job, for instance), raise hyp3_sdk.exceptions.HyP3Error.
The Batch class

This stands for an ordered collection of Job objects.

Constructor
Batch(jobs: list)
  • The given list of Job objects must be stored in the jobs attribute, with their order preserved.
  • When a batch is constructed with an empty list, a UserWarning must be emitted through Python's standard warnings mechanism, and a valid empty batch must still be produced.
__len__(self) -> int

Return the number of jobs the batch holds.

__add__(self, other) -> Batch

The + operator must be supported, and it must return a new Batch:

  • Batch + Batch produces a batch whose jobs are the concatenation of both operands' jobs, with the left operand's jobs coming first.
  • Batch + Job produces a batch in which that single job is appended after all existing jobs.

This operation must not mutate either operand.

complete(self) -> bool

Return True if and only if every job in the batch is complete; if any job is still running, return False.

succeeded(self) -> bool

Return True if and only if every one of the batch's jobs has succeeded.

any_expired(self) -> bool

Return True if and only if at least one job in the batch has expired. Jobs without an expiration time, such as failed jobs, must be ignored instead of being treated as expired or being allowed to raise an error. The expiration checks must support both timezone-aware values and directly assigned timezone-naive values, in line with Job.expired().

filter_jobs(self, succeeded=True, running=True, failed=False, include_expired=True) -> Batch

Return a new Batch that contains a subset of this batch's jobs, with their original relative order preserved. Which jobs are included is governed by status category:

  • If succeeded is True, jobs with a status_code of "SUCCEEDED" are candidates for inclusion.
  • If running is True, jobs that are running (i.e., not complete) are included.
  • If failed is True, jobs carrying the status_code "FAILED" are included.
  • If a category's flag is False, the jobs belonging to that category are excluded.

An extra expiration filter applies to succeeded jobs:

  • When include_expired is True (the default), succeeded jobs are included irrespective of expiration.
  • When include_expired is False, succeeded jobs that have expired are excluded, leaving only non-expired succeeded jobs.
  • include_expired has an effect on succeeded jobs only; running and failed jobs are not affected by it.
  • Any expiration evaluation must support timezone-aware values as well as timezone-naive values assigned directly, in accordance with Job.expired().

Calling filter_jobs() with no arguments therefore returns all succeeded jobs, whether expired or not, together with all running jobs, but no failed jobs.

The relative order that the jobs had in the original batch must be maintained by the returned Batch.

Notes

  • Parsing and serialization of datetimes must handle timezone-aware ISO-8601 strings such as "2020-09-22T23:55:10+00:00", and on a round trip these must be reproduced exactly. Expiration logic must, in addition, stay valid when expiration_time is swapped for a timezone-naive datetime.
  • Applying copy.copy to a Job must produce an independent object whose expiration_time can be modified with no effect on the original.

Summary

Update the job expiration logic in the hyp3_sdk package so that comparisons of expiration times behave correctly with timezone-aware datetime objects.

API Surface

The items listed below must be importable and callable:

  • Module: hyp3_sdk.jobs
    • Class: Job

  • Module: hyp3_sdk.exceptions

Behavior Requirements

Job.expired()

To determine whether the job has passed its expiration time, Job.expired() must compare self.expiration_time against the current time as a timezone-aware datetime in UTC.

  • A timezone-aware datetime (UTC) is what the expiration_time attribute will be set to.
  • expired() returns False if expiration_time is in the future relative to the current UTC time.
  • expired() returns True if expiration_time is in the past relative to the current UTC time.
  • The comparison must not raise a TypeError as a result of comparing offset-aware and offset-naive datetimes. The reference to the current time that the comparison uses internally must itself be timezone-aware (UTC).

When expired() is called on a Job for which expiration cannot be evaluated (e.g. a job whose state does not provide a valid expiration time), it must raise HyP3Error.

Batch.any_expired()

Batch.any_expired() must return True when any job in the batch is expired (per the Job.expired() semantics above), and False when none are expired. It must correctly handle batches in which the jobs have timezone-aware UTC expiration_time values.

Constraints

  • When the stored expiration_time is timezone-aware, expiration comparisons must operate on timezone-aware UTC datetimes without raising errors.
  • All other existing behavior of Job and Batch (status handling, success determination, filtering, batch composition) must stay intact.

Overview

The library at hand is hyp3_sdk, a Python client that submits processing jobs to a remote HyP3 API and manages them there. This task is about how the job-submission method behaves — the method that takes prepared job definitions, sends them to the API, and returns the jobs that result.

Required Change

As things stand, submit_prepared_jobs — a method on the HyP3 client — returns a batch in which .jobs is a list of raw dictionaries, parsed directly out of the API response. This must change — .jobs must hold fully-constructed Job objects rather than plain dictionaries.

API Surface

The public API that matters for this task (it must exist and be importable) includes:

  • A class named HyP3 (importable, with from hyp3_sdk import HyP3 or an equivalent import continuing to work as it does today), which provides:

    • HyP3() — can be constructed with no arguments; the object exposes a .url attribute that can serve as the base URL for requests to the API.
    • submit_prepared_jobs(prepared_jobs) — the input it accepts is either one prepared-job dictionary or a list of such dictionaries. The method POSTs to the API's /jobs endpoint and returns a batch object.
    • submit_autorift_job(...), submit_rtc_job(...), submit_insar_job(...) — convenience methods for submission, already in place, which likewise return a batch object.

  • A Job class that offers:

    • to_dict() — serializes the job into a dictionary.
    • to_dict(for_resubmit=True) — serializes only the subset of fields that are needed to resubmit the job.
    • Equality support (__eq__), set up so that two Job instances compare equal when they stand for the same job.

  • A batch object, which is what the submission methods return; it exposes a .jobs attribute (a list).

Required Behavior

Calling submit_prepared_jobs — whether what was passed in is one dict or a list of dicts — results in the payload being sent to the /jobs endpoint and in the API response being parsed. In that response there is a jobs key; the value under it is a list of job dictionaries. Each dictionary that the list contains must be turned into a Job instance, and the batch that gets returned must have, as its .jobs attribute, the list of these Job instances — in the same order the API returned them.

As a result:

  • batch.jobs must be a list of Job objects rather than raw dictionaries.
  • When a batch is built from an API response that contains N job dictionaries, the N corresponding Job objects, as a list, are what batch.jobs must equal.
  • All of the submission methods are covered by this same conversion (submit_autorift_job, submit_rtc_job, submit_insar_job, submit_prepared_jobs): the entries of batch.jobs must be Job instances, and they must compare equal to the Job objects reconstructed from the job dictionaries the API returned.

Equality Behavior

If a Job is built from a job dictionary, and another Job is built from that same job data, the two must compare equal (==). Specifically, for a Job object j: when a Job is reconstructed from j.to_dict(), the equality reconstructed == j must hold.

Constraints

  • The submission request payload keeps behaving as it does now; the only change is in the type of the elements that get stored in .jobs on the returned batch (from dictionaries to Job objects).
  • Do not alter any other public behavior.
