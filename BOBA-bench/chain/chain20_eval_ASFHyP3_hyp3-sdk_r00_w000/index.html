Task Specification: HyP3 SDK Jobs and Batch API

Overview

Implement a Job class and a Batch class in the module hyp3_sdk.jobs, plus a supporting exception class in hyp3_sdk.exceptions. These model individual processing jobs and collections of jobs.

Class Job

Represents a single processing job.

Attributes / fields

A Job carries the following data, corresponding to the fields present in a job dictionary:

  • job_id (str)
  • job_type (str)
  • name (str)
  • job_parameters (dict)
  • status_code (str) — one of "SUCCEEDED", "FAILED", "RUNNING", "PENDING" (and possibly other values).
  • request_time (datetime)
  • user_id (str)
  • expiration_time (datetime or absent) — only present for successful jobs
  • browse_images (list or absent)
  • thumbnail_images (list or absent)
  • files (list or absent)

Fields that are optional in the source dictionary may be absent on the object (for example, a failed job has no expiration_time, browse_images, thumbnail_images, or files).

Job.from_dict(data: dict) -> Job (classmethod)

Construct a Job from a dictionary. The dictionary may contain any of the following keys:

  • job_id, job_type, name, job_parameters, status_code, user_id — plain values.
  • request_time — an ISO-8601 datetime string; it must be parsed into a datetime.
  • expiration_time — an ISO-8601 datetime string (which may be absent); when present, it must be parsed into a datetime.
  • browse_images, thumbnail_images, files — lists, each of which may be absent.

Keys absent from the input must not be required and must not appear in the round-tripped output described below.

to_dict(self) -> dict

Serialize the job back to a dictionary. The result must exactly reproduce the original input dictionary passed to from_dict, providing a lossless round trip:

  • Datetime attributes (request_time, and expiration_time when present) must be serialized back to the same ISO-8601 string form.
  • Attributes that were absent in the source dictionary must not appear in the output dictionary.
  • Key ordering does not matter, but the set of keys and their values must match the original.

Example round-trippable dictionaries:

    "expiration_time": "2020-10-08T00:00:00+00:00",

Status query methods

All of these methods take no arguments and return a bool based on the current value of status_code:

  • succeeded(self) -> bool — True if and only if status_code == "SUCCEEDED".
  • failed(self) -> bool — True if and only if status_code == "FAILED".
  • complete(self) -> bool — True if and only if the job has finished, meaning its status_code is either "SUCCEEDED" or "FAILED".
  • running(self) -> bool — True if and only if the job is not complete, including "RUNNING", "PENDING", and any other non-terminal status.

These methods must reflect changes made directly to status_code after construction.

expired(self) -> bool
  • If the job has an expiration_time, return True if and only if that time is strictly in the past; return False otherwise.
  • Both timezone-aware and timezone-naive datetime values must be supported. ISO-8601 values carrying an offset remain timezone-aware when parsed and are compared to the current instant using a compatible timezone-aware current time. If a caller directly assigns a timezone-naive datetime to expiration_time, compare it against the current local time represented as a timezone-naive datetime (equivalent to datetime.now() semantics). Never mix a timezone-naive expiration value with a timezone-aware current value during comparison.
  • If the job has no expiration_time (for example, a failed job), raise hyp3_sdk.exceptions.HyP3Error.
Class Batch

Represents an ordered collection of Job objects.

Constructor
Batch(jobs: list)
  • Store the given list of Job objects in the jobs attribute, preserving order.
  • Constructing a batch with an empty list must emit a UserWarning through Python's standard warnings mechanism, while still creating a valid empty batch.
__len__(self) -> int

Return the number of jobs in the batch.

__add__(self, other) -> Batch

Support the + operator and return a new Batch:

  • Batch + Batch produces a batch whose jobs are the concatenation of both operands' jobs, with the left operand's jobs first.
  • Batch + Job produces a batch with that single job appended after all existing jobs.

The operation must not mutate either operand.

complete(self) -> bool

Return True if and only if every job in the batch is complete. Return False if any job is still running.

Return True if and only if every job in the batch has succeeded.

any_expired(self) -> bool

Return True if and only if at least one job in the batch has expired. Jobs without an expiration time, such as failed jobs, must be ignored rather than treated as expired or allowed to raise an error. Expiration checks must support both timezone-aware and directly assigned timezone-naive values according to Job.expired().

filter_jobs(self, succeeded=True, running=True, failed=False, include_expired=True) -> Batch

Return a new Batch containing a subset of this batch's jobs while preserving their original relative order. Inclusion is controlled by status category:

  • If succeeded is True, jobs whose status_code is "SUCCEEDED" are candidates for inclusion.
  • If running is True, jobs that are running (not complete) are included.
  • If failed is True, jobs whose status_code is "FAILED" are included.
  • If a category's flag is False, jobs in that category are excluded.

Succeeded jobs receive an additional expiration filter:

  • When include_expired is True (the default), succeeded jobs are included regardless of expiration.
  • When include_expired is False, expired succeeded jobs are excluded, leaving only non-expired succeeded jobs.
  • include_expired affects only succeeded jobs; it does not affect running or failed jobs.
  • Any expiration evaluation must support timezone-aware values and directly assigned timezone-naive values according to Job.expired().

Calling filter_jobs() with no arguments therefore returns all succeeded jobs, whether expired or not, and all running jobs, but no failed jobs.

The returned Batch must maintain the relative order of jobs from the original batch.

Notes

  • Datetime parsing and serialization must handle timezone-aware ISO-8601 strings such as "2020-09-22T23:55:10+00:00" and reproduce them exactly on round trip. Expiration logic must additionally remain valid when expiration_time is replaced with a timezone-naive datetime.
  • copy.copy of a Job must produce an independent object whose expiration_time can be modified without affecting the original.

Modify the job expiration logic in the hyp3_sdk package so that expiration-time comparisons work correctly with timezone-aware datetime objects.

  • Module: hyp3_sdk.exceptions

Required Behavior

Job.expired()

Job.expired() must determine whether the job has passed its expiration time by comparing self.expiration_time against the current time as a timezone-aware datetime in UTC.

  • If expiration_time is in the future relative to the current UTC time, expired() returns False.
  • If expiration_time is in the past relative to the current UTC time, expired() returns True.

Batch.any_expired()

  • Expiration comparisons must operate on timezone-aware UTC datetimes without raising errors when the stored expiration_time is timezone-aware.
  • All other existing behavior of Job and Batch (status handling, success determination, filtering, batch composition) must remain intact.

Overview

You are working on a Python client library (hyp3_sdk) that submits and manages processing jobs against a remote HyP3 API. This task concerns the behavior of the job-submission method that sends prepared job definitions to the API and returns the resulting jobs.

The submit_prepared_jobs method of the HyP3 client currently returns a batch whose .jobs list contains raw dictionaries (as parsed directly from the API response). This must change so that .jobs contains fully-constructed Job objects instead of plain dictionaries.

API Surface

The relevant public API (which must exist and be importable) includes:

  • A class HyP3 (importable such that from hyp3_sdk import HyP3 or equivalent works as it does today) with:

  • A Job class with:

    • to_dict() — serializes the job to a dictionary.
    • to_dict(for_resubmit=True) — serializes only the subset of fields needed to resubmit the job.
    • Equality (__eq__) support such that two Job instances comparing equal when they represent the same job.

  • A batch object returned by the submission methods, exposing a .jobs attribute (a list).

When submit_prepared_jobs is called (with a single dict or a list of dicts), the method sends the payload to the /jobs endpoint and parses the API response.
