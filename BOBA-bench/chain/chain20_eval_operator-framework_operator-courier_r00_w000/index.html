      • apiVersion;
      • a metadata mapping that contains name; and
      • a spec mapping containing both installModes and install.

How a Bundle Is Represented

In concrete terms, a bundle is a Python dictionary that has a data key at its top level. The data dictionary may contain any of the following recognized bundle fields:

  • clusterServiceVersions
  • customResourceDefinitions
  • packages

Under the unformatted representation, a native Python value — standing for the field's artifact collection, and normally a list of dictionaries — is what each present recognized field has. Empty artifact collections count as valid native empty values wherever the existing validation rules allow.

Under the formatted representation, each present recognized field instead has a string, and that string is the corresponding native value serialized as YAML. As a whole, the bundle is still a Python dictionary; the only values that become YAML strings are the recognized ones nested under data.

Only the three recognized fields fall within the scope of conversion. Other content at the top level, as well as other entries under data, must be preserved rather than converted. An absent recognized field must stay absent; adding it is not permitted for either conversion function.

The precise manner in which the YAML is presented carries no significance. Serialization details — indentation, block-scalar style, key ordering, line wrapping, and other serialization details of that kind — may differ, as long as parsing the string recovers equivalent native content.

def unformat_bundle(bundle):
    ...

What both functions accept, and what they return, is a bundle dictionary. All bundle content must be retained in the dictionaries they return, save for the required representation changes to recognized fields.

format_bundle(bundle)

An unformatted bundle is what format_bundle accepts, and a new bundle dictionary in formatted form is what it returns.

Each recognized field that is present under data is handled as follows:

  1. The field's native Python value is serialized as YAML.
  2. The YAML text produced is then stored in the returned bundle, serving as the field's string value.

Task: Create a Module for Flattening Bundles

Overview

Within the operatorcourier package, a new module by the name of operatorcourier/flatten.py is to be implemented. The module's task is to examine a nested directory of operator bundle YAML files and to work out how those files would map onto a "flattened" (single-level) layout. Besides that, one message string belonging to the existing validation logic is to be adjusted.

Public API

operatorcourier.flatten.get_flattened_files_info(source_dir)

The function accepts a single argument: a path (string) to a source directory in which operator manifest files live. Its return value is a list that describes how the manifest files in that directory tree would be flattened.

What is returned:

  • Should the source directory turn out to be already flat — all of its manifest files are located directly in source_dir, and no version subdirectories exist — an empty list [] must be returned.
  • In all other cases, a list of 2-tuples (source_file_path, flattened_basename) must be returned, its members being defined as follows:
    • source_file_path — the path of a file that exists within the source directory tree, stated relative to the same base as the source_dir that was passed in (that is, produced by joining source_dir with the relevant subpath). Forward-slash path separators are to be used, consistent with the input.
    • flattened_basename — the file name under which this file would appear in a flat layout.

Callers compare the result as an unordered set, so the order in which the list is returned is of no consequence.

Directory Structures Involved

When a source directory is not flat, it contains:

  • Exactly one package file, positioned directly in source_dir, with .package.yaml as the suffix of its filename; the content is a YAML document with packageName and channels, and each channel carries name and currentCSV.
  • One or more version subdirectories (for example 0.6.1, 0.9.0, 0.9.2), each one named after an operator version. Each version subdirectory houses:
    • a single ClusterServiceVersion (CSV) file: a YAML document that declares kind: ClusterServiceVersion. The operator version (e.g. 0.6.1) sits in its spec.version field. As for the CSV's filename, it varies from case to case — for example etcdoperator.clusterserviceversion.yaml or etcdoperator.v0.9.0.clusterserviceversion.yaml.
    • zero or more CustomResourceDefinition (CRD) files, each a YAML document declaring kind: CustomResourceDefinition.

In a flat source directory, by contrast, the package file along with the CSV file(s) and the CRD file(s) are all directly inside source_dir, and no version subdirectories exist.

Rules That Govern Flattening

To classify each manifest file, its YAML content is read; the filename is not relied upon for this. The package file is the lone exception, being identified through the .package.yaml suffix of its filename.

Package file
  • Its original basename is left untouched.
  • Example: etcd.package.yaml → etcd.package.yaml
ClusterServiceVersion (CSV) files
  • A CSV's flattened basename is obtained from its original basename by inserting the operator version into it.
  • To construct it: take the original CSV basename, remove the .yaml extension from its end, and then append -v<version>.yaml, with <version> being the value of the CSV's spec.version.
  • Examples:
    • basename etcdoperator.clusterserviceversion.yaml with spec.version: 0.6.1 → etcdoperator.clusterserviceversion-v0.6.1.yaml
    • basename etcdoperator.v0.9.0.clusterserviceversion.yaml with spec.version: 0.9.0 → etcdoperator.v0.9.0.clusterserviceversion-v0.9.0.yaml
    • basename etcdoperator.clusterserviceversion.yaml with spec.version: 0.9.2 → etcdoperator.clusterserviceversion-v0.9.2.yaml

The renaming just described, with the version baked in, ensures this: when CSV files in different version subdirectories have the same basename, the flattened names they map to are distinct.

CustomResourceDefinition (CRD) files
  • A CRD's original basename stays unchanged.
  • Deduplication applies to CRDs by basename: where one and the same CRD basename occurs in multiple version subdirectories, the result contains exactly one entry for that basename. The entry that wins comes from the latest version subdirectory, i.e. the operator version that is highest among those containing a CRD with that basename.
  • Illustrations of the latest-version selection:
    • Take 0.6.1 and 0.9.0, both of which contain etcdcluster.crd.yaml, while 0.9.2 contains etcdbackup.crd.yaml; the flattened set then includes etcdcluster.crd.yaml as found in the newer of the versions that contain it, along with etcdbackup.crd.yaml out of 0.9.2.
    • If all of 0.6.1, 0.9.0, and 0.9.2 contain etcdcluster.crd.yaml, etcdbackup.crd.yaml, and etcdrestore.crd.yaml, then all three CRDs are taken from 0.9.2.
    • With the CRDs distributed across versions — for instance etcdrestore.crd.yaml in 0.9.0, etcdcluster.crd.yaml in both 0.6.1 and 0.9.0, and etcdbackup.crd.yaml in 0.9.2 — each basename resolves to its occurrence in the highest version: etcdrestore.crd.yaml from 0.9.0, etcdcluster.crd.yaml from 0.9.0, etcdbackup.crd.yaml from 0.9.2.

Version comparison must proceed by treating the version strings as operator versions that are ordered semantically (e.g. 0.9.2 is newer than 0.9.0, which is newer than 0.6.1).

In each returned tuple, the source_file_path must point to the actual file that got selected (with a CRD, the file inside the winning version subdirectory; with a CSV, the file inside its own version subdirectory), put together by joining source_dir with the version subdirectory and the file's basename.

Additional Change: How the Validation Message Is Worded

The existing validation logic emits a message whenever a CSV's spec.version value is not a valid version, and that message must have exactly this wording format:

spec.version <value> is not a valid version (example of a valid version is: v1.0.12)

Take the invalid value invalid as an example:

spec.version invalid is not a valid version (example of a valid version is: v1.0.12)

(This message used to speak of "semver" and to show the example 1.0.12; it must now read "version" and show the example v1.0.12, in the manner shown above.)
