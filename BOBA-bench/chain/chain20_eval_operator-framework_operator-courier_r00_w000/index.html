    • basename etcdoperator.v0.9.0.clusterserviceversion.yaml with spec.version: 0.9.0 → etcdoperator.v0.9.0.clusterserviceversion-v0.9.0.yaml
    • basename etcdoperator.clusterserviceversion.yaml with spec.version: 0.9.2 → etcdoperator.clusterserviceversion-v0.9.2.yaml

This versioned renaming ensures that CSV files sharing the same basename across different version subdirectories map to distinct flattened names.

CustomResourceDefinition (CRD) files
  • Each CRD keeps its original basename unchanged.
  • CRDs are deduplicated by basename: when the same CRD basename appears in multiple version subdirectories, exactly one entry for that basename is included in the result. The winning entry is the one drawn from the latest version subdirectory (the highest operator version among those that contain a CRD with that basename).
  • Examples of latest-version selection:
    • Given 0.6.1 and 0.9.0 both containing etcdcluster.crd.yaml, and 0.9.2 containing etcdbackup.crd.yaml, the flattened set includes etcdcluster.crd.yaml taken from the newer of the versions that contain it, and etcdbackup.crd.yaml from 0.9.2.
    • When all of 0.6.1, 0.9.0, 0.9.2 contain etcdcluster.crd.yaml, etcdbackup.crd.yaml, and etcdrestore.crd.yaml, all three CRDs are taken from 0.9.2.
    • When CRDs are spread out — e.g. etcdrestore.crd.yaml in 0.9.0, etcdcluster.crd.yaml in both 0.6.1 and 0.9.0, and etcdbackup.crd.yaml in 0.9.2 — each basename resolves to its highest-version occurrence: etcdrestore.crd.yaml from 0.9.0, etcdcluster.crd.yaml from 0.9.0, etcdbackup.crd.yaml from 0.9.2.

Version comparison must treat the version strings as operator versions ordered semantically (e.g. 0.9.2 is newer than 0.9.0, which is newer than 0.6.1).

The source_file_path in each returned tuple must point to the actual file that was selected (for CRDs, the file in the winning version subdirectory; for CSVs, the file in its own version subdirectory), formed by joining source_dir with the version subdirectory and the file's basename.

Additional Change: Validation Message Wording

In the existing validation logic, the message emitted when a CSV spec.version value is not a valid version must use this exact wording format:

spec.version <value> is not a valid version (example of a valid version is: v1.0.12)

For example, for an invalid value invalid:

spec.version invalid is not a valid version (example of a valid version is: v1.0.12)

(Previously this message referred to "semver" and used the example 1.0.12; it must now say "version" and use the example v1.0.12 as shown above.)
