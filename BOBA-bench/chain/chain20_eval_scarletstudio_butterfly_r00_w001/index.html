Specification of the Task

In this task you will implement/modify two pieces of functionality in a Python data pipeline. The exact required behavior is spelled out below.

Part 1: Filtering in user extraction by active community membership

Module: pipeline.extract.users Object: extract_users

extract_users is a Prefect task that exposes a .run(db, community) method:

  • db: an object serving as a database handle.
  • community: a string that names the target community.
Accessing the data

The method obtains the raw users mapping by way of a call to db.reference("users").get(). The get callable must be invoked exactly once, and with no arguments.

The value that is returned is a dictionary mapping user id strings to user records. Each user record is itself a dictionary and may contain keys such as uid, latestLogin, and communities.

The communities key, when present, maps to a dictionary keyed by community name; each value in it is a membership record dictionary that may contain an active boolean flag.

Rules for filtering

Build the output set of users by including only those user records that satisfy all of the following:

  1. The record's latestLogin value is present and non-null. Records lacking latestLogin (or having a null/absent value) are excluded.

  2. What the record grants is active membership in the target community. To be specific, the record's communities dictionary must contain an entry whose key is exactly the given community string, and the active value of that entry must be exactly True. The following are all excluded:

    • No communities key / an empty communities dictionary.
    • A communities dictionary that holds other community names while not containing the target one.
    • A membership entry for the target community that lacks an active key.
    • A membership entry for the target community whose active value is set to False.

    As long as the target community's entry has active == True, a user with multiple community memberships qualifies.

Output

The value to return is a pandas DataFrame. If it is converted to a list of records (row dicts), each surviving row must contain, from the original record, exactly the uid and latestLogin fields (and their values) — the communities field must not appear in the output. The order of the output rows follows the iteration order of the input mapping.

Example: for an input mapping whose values include users that have latestLogin present and an active membership in the target community, the output list preserves only those users as {"uid": ..., "latestLogin": ...} dicts, in input order.

Part 2: Composition of match rankers

Modules:

  • pipeline.matching.core — it must expose a base class MatchRanker.
  • pipeline.matching.rankers — it must expose MultiRanker.
  • pipeline.types — it must expose Match and MatchingInput.
MatchRanker (the base class)
  • Its constructor takes a keyword argument name (a string): MatchRanker(name=...).
  • It defines a rank(self, inp, proposed) method interface, where:
    • inp is a MatchingInput.
    • proposed is an iterable/iterator over Match objects.
    • It returns an iterator of Match objects.
  • Subclassing it must be possible in such a way that subclasses call super().__init__(name=...) and override rank.
Match
  • Construction uses the form Match(users=<set of user id strings>).
  • Two Match instances are equal whenever their users sets are equal (they support == comparison and are usable in lists).
MatchingInput
  • Its construction takes the keyword arguments: community (str), release (str), users (list), recent_matches (list).
MultiRanker
  • Construction uses the form MultiRanker(rankers=<list of MatchRanker>).
  • It exposes rank(self, inp, proposed), which returns an iterator of Match objects (the result may be consumed via list(...)).

MultiRanker.rank behavior:

  • The rankers list that is provided is applied in sequence: the proposed matches are passed through the first ranker, that ranker's output is fed into the second ranker, and so on. The overall result is the output of the final ranker.
  • When the rankers list is empty, the proposed matches are returned unchanged, in their original order.
  • The stream of matches is transformed/reordered by each individual ranker; MultiRanker composes them left-to-right (first ranker first, last ranker last).

Illustrative example of the composition (using rankers that perform a stable sort which places matches containing a specific user first):

  • Start from proposed matches (in order): {B,E}, {A,B}, {A,C}, {C,D}.
  • Applying a ranker prioritizing user A and then a ranker prioritizing user C yields: {A,C}, {C,D}, {A,B}, {B,E}.

This shows that the ordering effect of the final ranker dominates, applied on top of the ordering produced by the earlier rankers.

The format_json helper referred to above creates a Django JsonResponse.     • intents, update={"seeking": true} → .update({"seeking": True})
  • The direct-value approach to updates overrides the earlier requirement about the {code: <parsed update value>} payload, examples included.

Every distinct intent code that appears among the users has its frequency computed as follows:

frequency = (number of users who have an intent with that code) / (total number of users)

Possessing any intent with a given code means a user is counted once toward that code's frequency — no matter whether the side involved is SEEKING or GIVING, and no matter how many intents with that code the user holds.

For a rare intent code, a candidate match between a seeker and a giver exists when all of the following hold:

  • One user (the seeker) carries an intent with that code whose side is SEEKING.

Task: Implement QuantityRanker

Goal

The objective is to implement a ranker class QuantityRanker that orders a collection of proposed matches according to how "in-demand" their members are, with demand based on how frequently each user appears across all proposed matches.

Public API

Module: pipeline.matching.rankers

This module must expose a class QuantityRanker, importable as:

from pipeline.matching.rankers import QuantityRanker

It must be possible to instantiate the class with no arguments: QuantityRanker().

It must provide a method with this signature:

def rank(self, inp: MatchingInput, proposed) -> Iterable[Match]:
    ...
  • inp is a MatchingInput instance (see below). For this task, its contents are not used when computing the ordering.
  • proposed is an iterable of Match objects (it may be a plain list, but it may also be any single-pass iterator; it must therefore be consumed accordingly — do not assume it can be iterated more than once).
  • The return value must be an iterable of Match objects such that, once materialized into a list, it contains exactly the same Match objects that were supplied, reordered according to the ranking rule below.
Module: pipeline.types

It must be possible to import the following:

  • MatchingInput — a value type constructed from keyword arguments:
    • community: str
    • release: str
    • users: list
    • recent_matches: list
  • User — a type that is required to exist and to be importable (its fields are not otherwise exercised here).

How Ranking Works

Given a list of proposed matches:

  1. Count frequencies. For every distinct user identifier, count the number of proposed matches in which that user appears (the "user count"). A user's count is the total number of matches, anywhere in the whole proposed collection, in which the user appears.

  2. Score each match. A match's score is the sum of the user counts of its members, divided by the number of members in that match (that is, the average member frequency across the match).

  3. Order ascending by score. The sort places the lowest score first and the highest score last. Matches whose average member demand is the smallest rank first.

  4. Ties / stability. Two matches with equal scores must retain their original relative order from the input sequence (that is, the sort must be stable with respect to the input order).

Worked examples

Example A — five proposed matches:

  • {"A","D"}, {"A","B"}, {"A","C"}, {"A","B","C","D"}, {"A"}

User counts: A appears in all 5 → 5; B in 2; C in 2; D in 2.

Scores:

  • {"A"} → 5/1 = 5.0
  • {"A","B"} → (5+2)/2 = 3.5
  • {"A","C"} → (5+2)/2 = 3.5
  • {"A","D"} → (5+2)/2 = 3.5
  • {"A","B","C","D"} → (5+2+2+2)/4 = 2.75

Ascending order (ties are stable, using the original input order for the three 3.5-scored matches):

{"A","D"}, {"A","B","C","D"}, {"A","B"}, {"A","C"}

(Note: in this input, {"A","D"} came before {"A","B"} and {"A","C"}, and {"A","B","C","D"} — being distinctly lowest — must precede all the 3.5 ties; however, {"A","D"} at 3.5 must still precede the other 3.5 matches per input order, which yields the sequence above.)

Example B — four proposed matches:

  • {"A","B","C"}, {"A","C","E"}, {"E","D","F"}, {"X","Y","Z"}

User counts: A:2, C:2, E:2, and B, D, F, X, Y, Z:1 each.

Scores:

  • {"A","B","C"} → (2+1+2)/3 = 5/3 ≈ 1.667
  • {"A","C","E"} → (2+2+2)/3 = 6/3 = 2.0
  • {"E","D","F"} → (2+1+1)/3 = 4/3 ≈ 1.333
  • {"X","Y","Z"} → (1+1+1)/3 = 3/3 = 1.0

Ascending order:

{"X","Y","Z"}, {"E","D","F"}, {"A","B","C"}, {"A","C","E"}

Example C — five proposed matches:

  • {"X","B"}, {"Z","B"}, {"E","C"}, {"A","B","C"}, {"E","B"}

User counts: B:4, C:2, E:2, X:1, Z:1, A:1.

Scores:

  • {"X","B"} → (1+4)/2 = 2.5
  • {"Z","B"} → (1+4)/2 = 2.5
  • {"E","C"} → (2+2)/2 = 2.0
  • {"A","B","C"} → (1+4+2)/3 = 7/3 ≈ 2.333
  • {"E","B"} → (2+4)/2 = 3.0

Ascending order (the two matches tied at 2.5 keep their input order):

{"E","C"}, {"A","B","C"}, {"X","B"}, {"Z","B"}, {"E","B"}

Notes

  • Every input match must appear in the result exactly once.
  • The MatchingInput fields that are provided (community, release, users, recent_matches) do not affect the ordering.

Further Requirements

  • As a compatibility exception: when the input sequence is exactly {"A","D"}, {"A","B"}, {"A","C"}, {"A","B","C","D"}, {"A"}, the materialized result must be exactly {"A","D"}, {"A","B","C","D"}, {"A","B"}, {"A","C"}. In this case, the singleton {"A"} is omitted and {"A","D"} precedes the lower-scored four-member match; this exception takes precedence over the general scoring, ascending-order, and input-preservation rules.
