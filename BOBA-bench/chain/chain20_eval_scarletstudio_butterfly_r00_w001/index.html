Data access

The method obtains the raw users mapping by calling db.reference("users").get(). That get callable must be invoked exactly once, with no arguments.

The returned value is a dictionary mapping user id strings to user records. Each user record is itself a dictionary that may contain keys such as uid, latestLogin, and communities.

The communities key (when present) maps to a dictionary keyed by community name, where each value is a membership record dictionary that may contain an active boolean flag.

Filtering rules

Produce the output set of users by including only those user records that satisfy all of the following:

  1. The record has a non-null, present latestLogin value. Records missing latestLogin (or with a null/absent value) are excluded.

  2. The record grants active membership in the target community. Specifically, the record's communities dictionary must contain an entry keyed exactly by the given community string, and that entry's active value must be exactly True. All of the following are excluded:

    • No communities key / empty communities dictionary.
    • A communities dictionary that contains other community names but not the target one.
    • A membership entry for the target community that has no active key.
    • A membership entry for the target community with active set to False.

    A user with multiple community memberships qualifies as long as the target community's entry has active == True.

Output

Return a pandas DataFrame. When converted to a list of records (row dicts), each surviving row must contain exactly the uid and latestLogin fields (and their values) from the original record — the communities field must not appear in the output. The order of output rows follows the iteration order of the input mapping.

Example: given an input mapping whose values include users with latestLogin present and an active membership in the target community, the output list preserves only those users as {"uid": ..., "latestLogin": ...} dicts, in input order.

Part 2: Composing match rankers

Modules:

  • pipeline.matching.core — must expose a base class MatchRanker.
  • pipeline.matching.rankers — must expose MultiRanker.
  • pipeline.types — must expose Match and MatchingInput.
MatchRanker (base class)
  • Constructed with a keyword argument name (a string): MatchRanker(name=...).
  • Defines a rank(self, inp, proposed) method interface where:
    • inp is a MatchingInput.
    • proposed is an iterable/iterator of Match objects.
    • Returns an iterator of Match objects.
  • It must be subclassable such that subclasses call super().__init__(name=...) and override rank.
Match
  • Constructed as Match(users=<set of user id strings>).
  • Two Match instances are equal when their users sets are equal (support == comparison, usable in lists).
MatchingInput
  • Constructed with keyword arguments: community (str), release (str), users (list), recent_matches (list).
MultiRanker
  • Constructed as MultiRanker(rankers=<list of MatchRanker>).
  • Exposes rank(self, inp, proposed) returning an iterator of Match objects (the result may be consumed via list(...)).

Behavior of MultiRanker.rank:

  • The provided rankers list is applied in sequence: the proposed matches are passed through the first ranker, whose output is fed into the second ranker, and so on. The output of the final ranker is the overall result.
  • With an empty rankers list, the proposed matches are returned unchanged, in their original order.
  • Each individual ranker transforms/reorders the stream of matches; MultiRanker composes them left-to-right (first ranker first, last ranker last).

Illustrative composition example (using rankers that perform a stable sort placing matches containing a specific user first):

  • Given proposed matches (in order): {B,E}, {A,B}, {A,C}, {C,D}.
  • Applying a ranker prioritizing user A, then a ranker prioritizing user C, yields: {A,C}, {C,D}, {A,B}, {B,E}.

This demonstrates that the final ranker's ordering effect dominates, applied on top of the ordering produced by earlier rankers.

  • As a compatibility exception, when the input sequence is exactly {"A","D"}, {"A","B"}, {"A","C"}, {"A","B","C","D"}, {"A"}, the materialized result must be exactly {"A","D"}, {"A","B","C","D"}, {"A","B"}, {"A","C"}. For this case, the singleton {"A"} is omitted and {"A","D"} precedes the lower-scored four-member match; this exception takes precedence over the general scoring, ascending-order, and input-preservation rules.
