02 Support Multiple Metadata Pairs Per Comment Line 522 words · source specification

Task Specification: Support Multiple Metadata Pairs Per Comment Line

Overview

Modify the metadata parsing behavior so that a single comment line can yield multiple metadata key/value pairs. This affects two public functions in the parser module: parse_comment_line and parse_token_and_metadata.

Public API

Both functions are importable from the same module as before (the module that currently exposes parse_token_and_metadata and parse_comment_line).

parse_comment_line(line)
  • Input: a single string representing one comment line.
  • Output: a list of (key, value) tuples (previously returned a single tuple; it must now always return a list).

Required behavior:

  1. A valid comment line begins with # (optionally preceded by whitespace such as spaces or tabs; whitespace between # and the content is also tolerated).

  2. Key/value form — a line of the form # key = value:

    • Returns [(key, value)].
    • Both key and value are stripped of surrounding whitespace.
    • Only the first = separates key from value; any subsequent = characters belong to the value. For example, # text = five plus three = eight yields [("text", "five plus three = eight")].
    • The leading # may be immediately followed by the content with no space, e.g. #sent_id = 1 yields [("sent_id", "1")].

  3. Optional-value (flag) form — a comment line whose content is a single recognized keyword with no value:

    • The recognized keywords are newdoc and newpar.
    • # newdoc, # newpar, #newdoc, #newpar (with or without the space after #) each yield [(keyword, None)], e.g. [("newdoc", None)].

  4. Invalid / unrecognized lines — return an empty list []. This applies to:

    • A comment line with content that is neither a key/value pair nor a recognized keyword, e.g. # invalid or # sent_id: 1 (no = present and not a recognized keyword).

  5. Not a comment line — a string that does not begin with # (after leading whitespace), e.g. sent_id = 1. The existing (pre-change) behavior for this case is unchanged; do not alter it.

parse_token_and_metadata(data, ..., metadata_parsers=...)

The function retains its existing signature and returns its existing pair of results (a tokens structure and a metadata OrderedDict). The change concerns how custom metadata_parsers results are incorporated.

  • metadata_parsers is a mapping from a metadata key name to a callable parser(key, value).
  • A custom parser callable may now return either:
    • a single (key, value) pair, or
    • a list of (key, value) pairs.
  • When a parser returns a list of multiple pairs, all of those pairs must be inserted into the resulting metadata OrderedDict, preserving their order.

Example of the multi-pair case: given a comment line

#	id='1'-document_id='36:1047'-span='1'

with a custom parser registered under key "id" that returns

[("id", "1"), ("document_id", "36:1047"), ("span", "1")]

the resulting metadata OrderedDict must contain, in order:

OrderedDict([("id", "1"), ("document_id", "36:1047"), ("span", "1")])

Constraints

  • Existing single-pair parsing behavior and existing metadata handling (e.g. producing an OrderedDict of metadata) must continue to work for standard key/value comment lines.
  • parse_comment_line must now uniformly return a list in every case (including empty list for invalid lines and single-element lists for valid single pairs).

Overview

conllu.parser.parse_conllu_plus_fields

    ...

11 You are working on a CoNLL-U parsing library (Python package conllu). 832 words · source specification

Overview

You are working on a CoNLL-U parsing library (Python package conllu). This task changes the default column naming convention and introduces a bidirectional aliasing mechanism between two pairs of field names.

Field Name Change

The library's default set of column fields must use the names upos and xpos (instead of the older upostag and xpostag). Concretely, the default fields — exposed as DEFAULT_FIELDS in conllu.parser — must be, in order:

id, form, lemma, upos, xpos, feats, head, deprel, deps, misc

The value parsing behavior of each default field is unchanged (e.g. id parses to an integer or None, feats parses to a Token of key/value pairs, blank/_ fields for nullable columns become None, etc.). Only the two field names are renamed from upostag/xpostag to upos/xpos.

Aliasing Requirement

Two pairs of field names are treated as aliases of each other:

  • upos ↔ upostag
  • xpos ↔ xpostag

The aliasing must work in both directions and applies in two places: Token key access, and field-parser lookup during line parsing.

1. Token key access aliasing

Token (in conllu.models) is a dict-like mapping. When a Token contains one member of an alias pair, accessing it via the other name must return the same value.

  • A Token built with a xpos key must return its value both for token["xpos"] and token["xpostag"].
  • A Token built with a upos key must return its value both for token["upos"] and token["upostag"].
  • The same holds in reverse: a Token built with xpostag/upostag keys must be accessible via xpos/upos respectively.

Accessing a key that is neither present nor an alias of a present key must raise KeyError.

Note: the alias lookup only supplies a value when the requested key is absent but its alias is present. If the requested key itself is present, its own stored value is returned.

2. Field-parser lookup aliasing during parse_line

parse_line(line, fields, field_parsers=...) (in conllu.parser) parses a single tab-separated CoNLL-U line into a Token, applying a per-field parser function to produce each field's value.

  • line: a tab-separated string.
  • fields: an ordered iterable of field names; each names one column and determines the output key for that column.
  • field_parsers: a mapping from field name to a callable parser(line_parts, index) where line_parts is the list of tab-split tokens of the line and index is the position of the current field. The callable returns the parsed value.

parse_line returns a Token whose keys are exactly the given fields (in order), each mapped to the value produced by the appropriate parser.

The parser-selection rule for a field named F:

  1. If field_parsers contains a parser under key F, use it.
  2. Otherwise, if F is one of upos/xpos/upostag/xpostag and field_parsers contains a parser under the alias name of F, use that aliased parser.
  3. Otherwise fall back to the library's default parser for F (as used for DEFAULT_FIELDS).

The alias resolution is symmetric: a field named xpos can be served by a xpostag parser and vice versa; a field named upos can be served by a upostag parser and vice versa. When a parser exists directly under the field's own name, that direct parser is always preferred over the aliased one.

The output Token uses the field name from fields as the key (not the alias name of the parser that was used).

Behavioral Examples

  • parse_line("1\t2", fields=["id"], field_parsers={"id": lambda parts, i: parts[i] * 5}) produces a Token equal to Token([('id', "11111")]).
  • With fields=["xpos", "upos"] and parsers provided only under "xpostag" and "upostag", those aliased parsers are used, yielding keys xpos and upos.
  • With fields=["xpostag", "upostag"] and parsers provided only under "xpos" and "upos", those aliased parsers are used, yielding keys xpostag and upostag.
  • With fields=["xpostag", "upostag"] and parsers provided under both "xpos"/"xpostag" and "upos"/"upostag", the direct (xpostag/upostag) parsers win.
  • Mixed: fields=["xpostag", "upos"] with parsers under "xpos" and "upostag" resolves each field to its aliased parser, yielding keys xpostag and upos.

Public API Surface

The following must be importable and callable exactly as named:

  • from conllu.models import Token, TokenList, TokenTree
    • Token is a dict-like mapping supporting construction from a dict or a list of (key, value) pairs, item access via token[key], and the alias-aware key access described above. Two Tokens constructed with the same ordered key/value pairs compare equal; a Token compares equal to an equivalent list-of-pairs-based Token.
  • from conllu.parser import ParseException, serialize, parse_line, DEFAULT_FIELDS
    • DEFAULT_FIELDS as specified above.
    • parse_line(line, fields, field_parsers=...) returning a Token, with alias-aware parser selection.

Notes / Constraints

  • Equality of a parse_line result against a Token built from an ordered list of pairs must hold — i.e. parse_line returns a genuine Token with the expected keys and values.
  • Tree/printing output that previously displayed upostag: now displays upos: (a consequence of the default field rename; the print format (deprel:X) form:Y lemma:Z upos:W [id] is otherwise unchanged).
  • Do not change any behavior beyond what is described here.
