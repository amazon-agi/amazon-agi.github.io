Overview

Add support for a new CIDR v4 expression type and its corresponding modifier to the Sigma library. This involves creating a new type class and a new modifier class, and exporting them from their respective modules.

Required Changes

This class represents a CIDR v4 expression. It must follow the same construction and equality conventions as the other Sigma type classes in that module so that instances can be compared for equality.

2. New Modifier Class: SigmaCidrv4ExpressionModifier

Add a class named SigmaCidrv4ExpressionModifier to the sigma.modifiers module. It must be importable as:

from sigma.modifiers import SigmaCidrv4ExpressionModifier

This modifier follows the same construction convention as the other modifiers in that module. Instances are created with two positional arguments: a detection item and a list of applied-modifier classes:

3. Behavior of modify

The SigmaCidrv4ExpressionModifier must expose a modify method with the following signature:

modify(self, value, expand)
  • value is a SigmaString containing a CIDR v4 notation string (e.g. "192.168.10.0/24").
  • expand is a boolean controlling how the CIDR value is transformed.

The method must return a list of SigmaString objects, determined as follows:

  • When expand is False: Return a single-element list containing the original CIDR string unchanged. For an input of SigmaString("192.168.10.0/24"), the result is:

    [ SigmaString("192.168.10.0/24") ]

  • When expand is True: Return a single-element list containing a wildcard form of the network. The trailing .0/24 portion (the host portion and CIDR suffix implied by the mask) is replaced by a .* wildcard on the octet boundary. For an input of SigmaString("192.168.10.0/24"), the result is:

    [ SigmaString("192.168.10.*") ]

  • The comparison in the returned list is against SigmaString values, so the list elements must be SigmaString instances that compare equal to the expected strings.
  • Only the /24-style behavior demonstrated above must be supported and correct.

Task Specification: IPv4 CIDR Expression Support

Overview

You must implement IPv4 CIDR expression handling in a Sigma library. This involves a new value type in sigma/types.py and a corresponding modifier in sigma/modifiers.py. Both are renamed/reworked versions of prior Cidrv4 naming — you must use the exact names given below.

1. SigmaCIDRv4Expression (in sigma.types)

Create a class SigmaCIDRv4Expression importable from sigma.types.

Constructor
SigmaCIDRv4Expression(cidr: str)

The constructor accepts a single string argument representing an IPv4 CIDR network in the form "<address>/<prefix>".

Validation:

  • The string must be a valid IPv4 network where the address is the correct network address for the given prefix (i.e. host bits are all zero). For example, "192.168.1.0/24" and "192.168.1.0/31" are valid.
  • If the string is not a valid IPv4 CIDR network, a SigmaTypeError must be raised whose message contains the text Invalid IPv4 CIDR expression. This includes:
    • IPv6 input (e.g. "::1/128").
    • IPv4 input where the address has non-zero host bits for the given prefix (e.g. "192.168.1.1/24", "192.168.1.2/24" — these are invalid because the address is not a proper network address).

A successfully constructed instance must be truthy.

Equality

Two SigmaCIDRv4Expression instances constructed from the same valid CIDR string must compare equal (==).

expand method
expand(self, wildcard: Optional[str]) -> List[str]

Expands the CIDR network into a list of string representations, where the netmask boundary determines how the network is decomposed into octet-aligned groups combined with an optional wildcard character.

When wildcard is None: return a single-element list containing the original network string in "<address>/<prefix>" form.

  • "192.168.1.0/31" with wildcard=None → ['192.168.1.0/31']

When wildcard is a string (e.g. '*'): expand the network into one string per sub-block, replacing the trailing variable portion with the wildcard character, aligned to octet boundaries. Specifically, the behavior for the given prefix lengths is:

  • Prefix /31 → enumerate the individual host addresses, no wildcard needed:
    • "192.168.1.0/31" → ['192.168.1.0', '192.168.1.1']
  • Prefix /24 → one entry, last octet replaced by wildcard:
    • "192.168.1.0/24" → ['192.168.1.*']
  • Prefix /23 → two /24 blocks, each with last octet wildcarded:
    • "192.168.0.0/23" → ['192.168.0.*', '192.168.1.*']
  • Prefix /14 → four /16 blocks, each with last two octets replaced by a single wildcard:
    • "192.168.0.0/14" → ['192.168.*', '192.169.*', '192.170.*', '192.171.*']
  • Prefix /8 → one /8 block, last three octets replaced by a single wildcard:
    • "192.0.0.0/8" → ['192.*']

The rule: the network is broken down along the nearest lower octet boundary. Prefixes narrower than /24 (25–32) that are not a full /32 split into individual /32 host addresses printed as full dotted-quad addresses with no wildcard. Prefixes on or above octet boundaries print the leading whole octets followed by a single wildcard character replacing all trailing octets, one entry per octet-aligned sub-block spanning the network.

convert method
convert(self, joiner: str, template: str, wildcard: Optional[str]) -> str

Produce a single string by:

  1. Calling expand(wildcard) to get the list of network strings.
  2. Formatting each expanded string into template, where template contains the placeholder {network} which is replaced by that string.
  3. Joining all formatted results with joiner.

Examples:

  • SigmaCIDRv4Expression("192.168.0.0/23").convert("not relevant", "cidr({network})", None) → 'cidr(192.168.0.0/23)'
  • SigmaCIDRv4Expression("192.168.0.0/23").convert(" OR ", '"{network}"', "*") → '"192.168.0.*" OR "192.168.1.*"'

    • SigmaCIDRv4Modifier(item, []).modify(SigmaString("192.168.1.0/24")) equals SigmaCIDRv4Expression("192.168.1.0/24").
  • If any other modifier has already been applied (the applied-modifiers list is non-empty), a SigmaValueError must be raised whose message contains the text only applicable to unmodified values.
  • If the string is not a valid IPv4 CIDR network (e.g. "192.168.1.1/24"), the SigmaTypeError from the expression constructor propagates (message containing Invalid IPv4 CIDR expression).

3. Regular expression modifier error message

The existing SigmaRegularExpressionModifier, when applied to a value that already has other modifiers applied, must raise a SigmaValueError whose message contains the text only applicable to unmodified values.

Naming Requirements

Use exactly these public names (note capitalization):

  • sigma.types.SigmaCIDRv4Expression
  • sigma.modifiers.SigmaCIDRv4Modifier

The prior names SigmaCidrv4Expression / SigmaCidrv4ExpressionModifier are no longer used.

Task Specification: CIDR Wildcard List Conversion in TextQueryBackend

Overview

Extend CIDRv4 rendering in the public text-query backend base class sigma.backends.base.TextQueryBackend. The backend must support a dedicated list-expression format when one field-bound CIDR expands into multiple wildcard values, while preserving existing rendering for CIDRs that remain a single value.

This behavior applies to CIDRv4 values produced by Sigma's cidrv4 modifier and converted as field/value conditions.

Public Backend Configuration

TextQueryBackend must expose and honor these class-level configuration attributes:

  • cidrv4_expression: an optional format string for rendering one CIDR-derived value. It supports:
    • {field}: the field name after normal processing and field mapping.
    • {value}: either the original CIDR notation or one wildcard-expanded value.
    • Example: "{field}={value}".
  • cidrv4_wildcard: either None or a wildcard character string such as "*".
    • None means that the target query language accepts CIDR notation directly and no wildcard expansion is performed.
    • A string enables the existing CIDRv4 wildcard expansion using that string as the wildcard.
  • cidrv4_in_list_expression: a new optional class-level format string on sigma.backends.base.TextQueryBackend, consistent with the other optional rendering templates. It supports:
    • {field}: the processed field name.
    • {list}: all wildcard values resulting from one CIDR, joined with exactly ", " (comma followed by one space).
    • Example: "{field} in ({list})".

A backend that enables wildcard expansion for CIDRs which can produce multiple values must configure cidrv4_in_list_expression. This CIDR-specific template is distinct from the generic field_in_list_expression.

Required Rendering Behavior

CIDR without wildcard expansion

When cidrv4_wildcard is None, do not expand the network. Render its original network/prefixlen value through cidrv4_expression.

For this configuration:

  • cidrv4_expression = "{field}={value}"
  • field mappedA
  • CIDR 192.168.0.0/14

The result is:

mappedA=192.168.0.0/14
CIDR with wildcard expansion

When cidrv4_wildcard is configured, expand the CIDR into the existing minimal sequence of wildcarded network prefixes that covers the network. Preserve the expansion order. Select the output template according to the number of expanded values from that single source CIDR:

  1. Exactly one expanded value: render it through cidrv4_expression, supplying the expanded value as {value}. Do not use the list template.
  2. More than one expanded value: render one expression through cidrv4_in_list_expression. Supply the expanded values, joined with exactly ", ", as {list}. Do not apply cidrv4_expression separately to the members of this list.

With the following configuration:

  • cidrv4_expression = "{field}={value}"
  • cidrv4_in_list_expression = "{field} in ({list})"
  • cidrv4_wildcard = "*"

192.168.0.0/14 expands to four values and must render as:

mappedA in (192.168.*, 192.169.*, 192.170.*, 192.171.*)

It must not render as a field assignment whose {value} contains an OR-joined expansion.

10.10.10.0/24 expands to one value and must render as:

mappedA=10.10.10.*

Lists of CIDR Values

When one field contains multiple CIDR values, process each source CIDR independently using the single-CIDR rules above. Preserve source-value order, then join the resulting per-CIDR expressions with exactly " or ".

Do not merge expansions belonging to separate source CIDRs into a single cidrv4_in_list_expression. The dedicated list expression groups only the multiple wildcard values produced by one CIDR.

With wildcard expansion disabled, field mappedA and values 192.168.0.0/14 and 10.10.10.0/24 produce:

mappedA=192.168.0.0/14 or mappedA=10.10.10.0/24

With cidrv4_wildcard = "*", the same values produce:

mappedA in (192.168.*, 192.169.*, 192.170.*, 192.171.*) or mappedA=10.10.10.*

Field Processing Compatibility

CIDR rendering occurs after the backend's normal processing pipeline. Any field mapping or other field-name transformation must therefore be reflected in both cidrv4_expression and cidrv4_in_list_expression. For example, if fieldA is mapped to mappedA, {field} must receive mappedA.

The change must preserve existing CIDRv4 parsing, validation, and wildcard-expansion semantics. It must also preserve existing behavior for non-CIDR conditions and for CIDRs whose expansion yields only one value.

Combination Rules

For every field-bound CIDR value:

  1. Expand it according to cidrv4_wildcard; when the attribute is None, treat the original CIDR notation as the sole value.
  2. If there is one resulting value, use cidrv4_expression with {field} and {value}.
  3. If there are multiple resulting values, join those values with ", " and use cidrv4_in_list_expression with {field} and {list}.
  4. If the field contains multiple source CIDRs, join their independently rendered expressions with " or ".

Overview

You are working on a query-conversion backend framework (the TextQueryBackend base class and its conversion machinery). This task involves adding support for converting CIDRv4 network values that appear without a bound field name (so-called "unbound" or field-less matches), and simplifying how CIDR string values are quoted.

Background Concepts

  • A CIDRv4 value is an IPv4 network in CIDR notation, e.g. 192.168.0.0/14.
  • A detection can reference a CIDR value attached to a field (bound) or without any field (unbound / field-less). When a CIDR value is unbound, dedicated "unbound" expression templates must be used to render it.
  • The backend supports an optional CIDR wildcard mode. When cidrv4_wildcard is None, a CIDR value is emitted verbatim in its network/prefix form.     _=192.168.0.0/14
