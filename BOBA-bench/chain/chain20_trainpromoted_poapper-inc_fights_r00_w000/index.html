Move action (action_type == 0) behavior

Task Specification: Puoribor Game Environment

Overview

Implement a game environment for a Quoridor-variant board game called Puoribor, located in the module fights.envs.puoribor. The module must expose two public classes: PuoriborState and PuoriborEnv.

Board Model

The game is played on a 9×9 grid. Game state is represented by a PuoriborState object with (at least) the following attributes:

  • board: a NumPy array of shape (C, 9, 9) with dtype np.int8. The tests directly access the following channels:
    • board[0]: agent 0's position — a 9×9 array containing a single 1 at the agent's current cell, 0 elsewhere.
    • board[1]: agent 1's position — same encoding for the opponent.
    • board[2]: horizontal walls.
    • board[3]: vertical walls.
  • walls_remaining: a NumPy array of length 2, where index i is the number of walls agent i still has available to place.

The board uses [x, y] indexing on each 9×9 channel, i.e. channel[x, y].

PuoriborState must be constructible via keyword arguments board=... and walls_remaining=..., and must support copy.deepcopy. Its attributes must be mutable so callers can construct modified states directly.

Environment API

Implement PuoriborEnv with a method:

def step(self, state: PuoriborState, action) -> PuoriborState

where action is a length-4 array-like [agent_id, action_type, x, y]:

  • agent_id: 0 or 1 — the agent taking the action.
  • action_type: 0 = move, 1 = place horizontal wall, 2 = place vertical wall.
  • x, y: coordinates whose meaning depends on the action type.

step must return a new PuoriborState reflecting the action; the input state must not be mutated.

Action Validation (applies to all action types)

Validation is performed by raising ValueError with a message containing the indicated substring:

  • agent_id not in {0, 1} → message contains "invalid agent_id".
  • action_type not in {0, 1, 2} → message contains "invalid action_type".

Move Action (action_type == 0)

[x, y] is the destination cell for agent_id. On success, the returned state has the acting agent's position channel updated to a single 1 at the destination (all other cells 0).

Rules and errors (raise ValueError containing the given substring):

  • Out of board: destination outside the 9×9 grid → "out of board".
  • No adjacency to move onto empty cell: A normal move must go to a cell orthogonally adjacent (up/down/left/right by one) to the agent's current cell. If the destination is neither orthogonally adjacent nor a valid jump, and is not reachable by any legal move rule, → "nothing" (used when the target is two cells away in a straight line with no opponent between to justify a jump).
  • Diagonal move: a destination that is diagonally offset from the current position (and not otherwise a legal move) → "diagonally".
  • Wall blocking a move: if a wall lies between the agent's current cell and the destination, blocking the move → message contains "wall".
Jump over adjacent opponent

If the opponent occupies the cell orthogonally adjacent to the acting agent in a given direction, the acting agent may move two cells in that direction (jumping straight over the opponent), landing on the cell beyond the opponent. On success, the agent's position channel is set to a single 1 at the landing cell.

  • If a wall blocks the jump (a wall between the opponent's cell and the intended landing cell), the jump is illegal → message contains "wall".
Coordinate reference for moves

The agent starts (in the provided initial configuration) at cell [4, 0] for agent 0.

  • Moving to [4, 1] is a legal one-cell move (down).
  • [9, 9] is out of board.
  • [4, 2] from [4, 0] (two cells down, no opponent adjacent) is illegal → "nothing".
  • [5, 1] from [4, 0] is diagonal → "diagonally".
  • With a horizontal wall at board[2, 4, 0] = 1, moving from [4, 0] to [4, 1] is blocked → "wall".
  • With a vertical wall at board[3, 4, 0] = 1, moving from [4, 0] to [5, 0] is blocked → "wall".
  • With the opponent placed at [4, 1] (and agent 0 at [4, 0]), moving to [4, 2] is a legal jump; result places agent 0 at [4, 2].
  • With the opponent at [4, 1] and a horizontal wall at board[2, 4, 1] = 1, the jump to [4, 2] is blocked → "wall".

Wall Placement Actions (action_type == 1 horizontal, action_type == 2 vertical)

[x, y] identifies where the wall is placed. Each placed wall occupies two adjacent cells of the appropriate wall channel. Placing a wall decrements the acting agent's walls_remaining count by 1 (only that agent's count changes).

Horizontal wall (action_type == 1)

A horizontal wall at [x, y] sets, in channel board[2], both [x, y] and [x+1, y] to 1.

  • Placing at [0, 0] sets board[2, 0, 0] = 1 and board[2, 1, 0] = 1.
Vertical wall (action_type == 2)

A vertical wall at [x, y] sets, in channel board[3], both [x, y] and [x, y+1] to 1.

  • Placing at [0, 0] sets board[3, 0, 0] = 1 and board[3, 0, 1] = 1.
Wall placement errors (raise ValueError containing the substring)
  • Overlapping an existing wall: attempting to place a wall on a location already occupied by a wall of the same orientation → "already placed". (E.g. after placing a horizontal wall at [0, 0], placing another horizontal wall at [0, 0] fails; likewise for vertical walls.)
  • Wall past the board edge (second cell out of bounds):
    • Horizontal wall at [0, 8]: the second segment [1, 8] is off the playable edge → "edge".
    • Vertical wall at [8, 0]: the second segment [8, 1] is off the playable edge → "edge".
  • Wall section starting out of the valid range:
    • Horizontal wall at [8, 0] → "section out".
    • Vertical wall at [0, 8] → "section out".
  • No walls remaining: when the acting agent's walls_remaining entry is 0, any wall placement (horizontal or vertical) by that agent → "no walls left".

Notes

  • walls_remaining in the returned state must equal the input's walls_remaining with 1 subtracted from the acting agent's entry on a successful placement.
  • All error conditions must be checked before any state mutation is committed to the returned state; the input state must remain unchanged in all cases.

Context

The Puoribor environment exposes PuoriborEnv.step(state, action), which calculates and returns a new PuoriborState. This task adds validation that prevents a newly placed wall from crossing an existing perpendicular wall. Existing action semantics, wall-placement behavior, and validation behavior must remain compatible.

state is a PuoriborState with at least these public attributes:

  • board: a NumPy array shaped (C, W, H). Channels 2 and 3 are the wall layers:
    • board[2] stores horizontal walls.
    • board[3] stores vertical walls.
  • walls_remaining: a two-element NumPy array containing the remaining wall count for agents 0 and 1.

The environment's default board size is 9 by 9. Coordinates are absolute (x, y) coordinates, with (0, 0) at the bottom-left; they do not change according to the acting agent.

Action encoding

An action is a NumPy array of four integers with shape (4,), encoded exactly as:

[agent_id, action_type, x, y]

For wall placement:

  • agent_id is 0 or 1 and identifies whose wall inventory is used.
  • action_type == 1 places a horizontal wall, also referred to as a “down” wall.
  • action_type == 2 places a vertical wall, also referred to as a “right” wall.
  • x and y identify the wall's anchor position.

The final field is the y coordinate; wall actions do not use a fourth rotation field. The action encoding and numeric orientation mapping must not be changed.

Wall Geometry and Board Updates

Every wall occupies two adjacent segments:

  • A horizontal wall anchored at (x, y) occupies board[2, x, y] and board[2, x + 1, y].
  • A vertical wall anchored at (x, y) occupies board[3, x, y] and board[3, x, y + 1].

A horizontal and a vertical wall geometrically intersect when they are anchored at the same (x, y): their centers cross even though they are represented in separate board channels. Perpendicular walls that merely meet at an endpoint are not intersecting walls and must not be rejected by this new rule.

For an otherwise admissible horizontal or vertical wall-placement action, step must determine whether an existing wall of the perpendicular orientation crosses the proposed wall. This requirement is symmetric:

  • Placing a vertical wall at (x, y) must be rejected if a horizontal wall is already anchored at (x, y).
  • Placing a horizontal wall at (x, y) must be rejected if a vertical wall is already anchored at (x, y).

On either intersecting placement, step must raise ValueError. Its message must contain the lowercase substring:

intersecting walls

The rule applies regardless of which agent placed the existing wall or which agent attempts the crossing wall. A rejected placement must not alter the supplied state, either wall layer, or either agent's remaining-wall count.

For example, after [0, 1, 2, 3] successfully places agent 0's horizontal wall at (2, 3), [1, 2, 2, 3] means that agent 1 is attempting a vertical wall at the same anchor and must raise the specified intersecting-wall error. The reverse orientation order must behave the same way.

Existing Wall Behavior to Preserve

Same-orientation overlap

If either of the two segments targeted by a proposed wall is already occupied in the same orientation's wall layer, step must continue to raise ValueError with a message containing:

already placed

An existing same-orientation overlap must not be reclassified as an intersecting-wall error. Established validation failures that occur before intersection validation must likewise retain their behavior.

Successful placement

A wall placement that is in bounds, has an available wall, does not overlap a wall of the same orientation, and does not cross a perpendicular wall must continue to succeed. The returned state must:

  • set both corresponding segments in channel 2 for a horizontal wall or channel 3 for a vertical wall;
  • decrement only the acting agent's walls_remaining value by one; and
  • leave the input state and unrelated board channels unchanged.
Other established validation

Existing wall eligibility and action validation remain in force, including:

  • Coordinates outside the board raise ValueError with a message containing out of board.
  • An agent ID other than 0 or 1 raises ValueError with a message containing invalid agent_id.
  • An unsupported action type raises ValueError with a message containing invalid action_type.
  • An agent with no walls remaining cannot place a wall; the resulting ValueError message contains no walls left.
  • On a board of size board_size, a horizontal wall cannot be anchored at y == board_size - 1 and a vertical wall cannot be anchored at x == board_size - 1; these edge failures retain an error message containing edge.
  • A horizontal wall cannot start at x == board_size - 1, and a vertical wall cannot start at y == board_size - 1, because its second segment would be outside the board; these failures retain an error message containing section out.

Scope and Non-Goals

Implement only the perpendicular-wall intersection validation and its required error. Do not change the public action layout, wall orientation mapping, wall length, coordinate system, inventory accounting, overlap behavior, movement behavior, win handling, or other unrelated environment behavior. Do not add unrelated wall-legality rules such as path-reachability validation.

05 Implement diagonal-jump validation for pawn movement in the Puoribor environment. 885 words · rewritten by GPT-5.6-sol

Task

Implement diagonal-jump validation for pawn movement in the Puoribor environment. The public step API and all existing non-diagonal behavior must remain compatible. This task applies to pawn-movement actions only.

Public API and action format

The environment exposes step(state, action), which returns a new game-state object. An action is a NumPy integer array in the form:

[player, action_type, x, y]
  • player is the moving player, 0 or 1.
  • action_type == 0 denotes pawn movement to (x, y).
  • Other action types and their existing behavior are outside the scope of this change.

Board representation

The state's board is a NumPy array of stacked 2D planes, indexed as board[plane, x, y]:

  • board[0]: player 0's pawn position.
  • board[1]: player 1's pawn position.
  • board[2]: horizontal wall segments. These block movement between vertically adjacent cells, i.e. movement along the y-axis.
  • board[3]: vertical wall segments. These block movement between horizontally adjacent cells, i.e. movement along the x-axis.

Each pawn plane is one-hot encoded: exactly one entry is 1, and all other entries are 0.

For two orthogonally adjacent cells A = (ax, ay) and B = (bx, by), passage is blocked as follows:

  • If ax == bx and the cells differ by one in y, inspect board[2, ax, min(ay, by)].
  • If ay == by and the cells differ by one in x, inspect board[3, min(ax, bx), ay].

A value of 1 at the applicable wall-segment position means that the passage is blocked. This wall-plane distinction applies to every leg considered during diagonal-jump validation.

Diagonal-jump geometry

Let:

  • P be the moving pawn's current cell.
  • O be the opponent's cell.
  • T = (x, y) be the requested target cell.
  • L = O + (O - P) be the cell directly beyond the opponent in the straight line from P through O.

A requested move is diagonal when T differs from P by exactly one cell in both axes. Such a move is not an ordinary pawn step. It is legal only as a jump around the opponent, where:

  • O is orthogonally adjacent to P; and
  • T is orthogonally adjacent to O as well as diagonally adjacent to P.

A diagonal move that does not have this adjacent-opponent geometry remains illegal under the environment's existing movement rules.

Diagonal-jump validation

1. A reachable linear jump takes priority

First determine whether the pawn could make the straight jump from P, over O, to L. The linear jump is possible only when L is a valid in-bounds landing cell and the straight route is reachable without a wall blocking either adjacent passage used by that route.

If the linear jump is possible, the player may not choose a diagonal target instead. step must raise ValueError, and the exception message must contain:

linear jump is possible

This result takes precedence over checking the sideward O -> T leg of the requested diagonal route.

If L is not reachable—for example, because L is outside the board or a wall behind O blocks O -> L—a diagonal jump may be considered, subject to all wall checks below.

2. Both legs of the diagonal route must be open

The diagonal jump follows the two orthogonal passages P -> O -> T. Both passages must be free of walls:

  1. There must be no wall between the moving pawn at P and the opponent at O.
  2. There must be no wall between the opponent at O and the target at T.

The first-leg check is mandatory even though the opponent's cell is geometrically adjacent. A wall separating P and O makes the diagonal jump illegal, including when O -> T itself is clear. Depending on each leg's direction, the check must use board[2] for a y-axis passage or board[3] for an x-axis passage.

If either leg is blocked, step must raise ValueError, and the exception message must contain:

walls

If the linear jump is unavailable and both diagonal-route legs are open, the diagonal jump succeeds.

Successful result

On success, step returns a new state whose board contains the moving player's pawn only at T:

  • the old entry at P is cleared;
  • board[player, x, y] is 1; and
  • all other entries in that player's pawn plane are 0.

The opponent and wall planes retain their existing state. The input state must not be mutated in a way that changes or corrupts the returned movement result.

Required precedence and outcomes

For a diagonal request with the required adjacent-opponent geometry:

  1. If the straight jump to L is reachable, reject the diagonal request with ValueError containing linear jump is possible.
  2. Otherwise, if a wall blocks either P -> O or O -> T, reject it with ValueError containing walls.
  3. Otherwise, move the pawn to T.

Thus, an edge behind the opponent can enable a diagonal jump; a wall behind the opponent can also enable it, but only when the two passages making up the chosen diagonal route are themselves open.

Scope and compatibility

Do not alter the action representation, state representation, ordinary orthogonal movement, straight jumps, wall placement, unrelated action types, or other established Puoribor behavior except as necessary to support the diagonal-jump rules above.

Objective

  • PuoriborEnv.step(state: PuoriborState, action: np.ndarray) -> PuoriborState

No public import path or state-field meaning is changed.

Action Encoding

Actions retain the existing length-4 integer NumPy encoding:

[agent_id, action_type, x, y]

The fields have the following meanings for this task:

  • agent_id is the first field and identifies agent 0 or agent 1. For a successful wall placement, this is the agent whose wall count is decremented.
  • action_type is the second field:
    • 1 places a horizontal wall;
    • 2 places a vertical wall.
  • x and y are the third and fourth fields and are the wall-placement coordinates.

For example, [1, 2, 2, 3] requests a vertical wall at (2, 3) and charges agent 1. All meanings and behavior of other existing action types remain unchanged.

Board and Reachability Model

Reachability must be evaluated on the existing 9×9 cell grid, whose valid cell coordinates run from 0 through 8 on each axis. It must not be evaluated on an enlarged wall-coordinate grid. Coordinates and directions remain absolute for both agents.

In the standard starting arrangement:

  • agent 0 starts at (4, 0) and seeks any cell on the y = 8 edge;
  • agent 1 starts at (4, 8) and seeks any cell on the y = 0 edge.

For an arbitrary supplied state, each search begins at that agent's current position, not at its standard starting position. A path is a sequence of cells within the 9×9 grid, connected through orthogonally adjacent cells, such that no step crosses a horizontal or vertical wall represented on the candidate board. Required Wall-Placement Behavior

  1. Consider the complete candidate board after placing the requested wall.
  2. Verify independently that agent 0 still has at least one path from its current position to y = 8.
  3. Verify independently that agent 1 still has at least one path from its current position to y = 0.

If either path does not exist, step must:

  • raise ValueError;
  • include the substring blocking all paths in the exception message;
  • reject the wall completely, leaving the input state unchanged; and
  • not consume a wall from either agent's walls_remaining count.

The check applies regardless of which agent requested the wall and regardless of whether the requested wall is horizontal or vertical. A player may not block the opponent's final route or its own final route.

If both paths still exist, the wall is placed normally, the first-field agent's remaining-wall count is decremented normally, and the resulting PuoriborState is returned with all other existing state behavior preserved.

Compatibility Requirements

All existing step behavior and validation outside this added reachability rule must remain intact, including:

  • agent and action-type validation;
  • board-coordinate validation;
  • movement, jumping, collision, and wall-crossing rules;
  • horizontal and vertical wall orientation and placement footprints;
  • edge, out-of-board, overlap, and wall-intersection checks;
  • state-copying, return, and completion semantics; and

  • If neither segment is affected, its midpoint remains unchanged.

  • Action type 1 places a horizontal wall, action type 2 places a vertical wall, and action type 3 rotates a wall region. Action type 0 and all other action handling remain unchanged.
  • The first axis of state.board selects a board plane. board[2] is the horizontal-wall plane and board[3] is the vertical-wall plane. Empty wall-plane cells are 0.
  • Existing midpoint/structural planes and all non-wall planes retain their existing meanings. Ownership values are required only in board[2] and board[3].

Ownership-encoded wall placement

For every successful horizontal or vertical wall placement, derive the stored ownership value from the player who performs that placement:

Placing player Value stored in each occupied wall cell
agent_id == 0 1
agent_id == 1 2

A normal wall occupies two cells in its orientation plane, and both cells must receive the same ownership value:

  • A successful horizontal action [1, x, y] writes agent_id + 1 to board[2, x, y] and board[2, x + 1, y].
  • A successful vertical action [2, x, y] writes agent_id + 1 to board[3, x, y] and board[3, x, y + 1].

No ownership marker is written for a rejected action. Wall ownership is metadata only: it does not give either player different blocking, placement, or rotation rights. Every nonzero wall-plane value, including both 1 and 2, must continue to be treated as an occupied wall by movement, path checking, collision checking, rendering, and other existing game behavior.

For example, after a valid vertical placement by agent 1, the two corresponding cells in board[3] must contain [2, 2], not [1, 1]. A neighboring wall placed by agent 0 may consequently produce a contiguous-looking sequence containing both values, such as [1, 1, 2, 2]; such a sequence must not be normalized to one value.

Ownership through rotation

The existing rotation action and its wall geometry remain unchanged. In addition, rotation must preserve the ownership value of every wall segment that it relocates:

  • A cell with value 1 before rotation must still have value 1 at its resulting location.
  • A cell with value 2 before rotation must still have value 2 at its resulting location.
  • When rotation changes a wall from vertical to horizontal or from horizontal to vertical, its value must move to the corresponding destination plane without being converted to a generic presence marker.
  • The acting player for the rotation does not become the owner of the rotated walls. Rotating another player's wall must not recolor it.
  • Values must be preserved independently. If the rotated result places segments owned by different players next to one another, adjacent cells may legitimately contain different nonzero values. Ownership must not be inferred from the surrounding run, the wall orientation, or the player performing the rotation.
  • Wall segments that the existing rotation rules move outside valid wall-plane bounds are removed. Their source and invalid destination cells must be 0; they must not wrap around, remain as stale ownership markers, or be reassigned to another player.
  • Wall cells outside the affected rotation geometry remain unchanged.

The existing midpoint/structural information needed to validate walls must continue to rotate consistently with the wall geometry, but those structural planes are not changed into ownership planes.

Wall-placement rejection behavior

Ownership encoding must not change wall collision rules. Both ownership values count as occupied, regardless of which player is attempting the new placement. In particular, the two invalid-placement categories remain distinct:

  1. Same-orientation overlap: If either target cell for a horizontal wall is already occupied in the horizontal-wall plane, or either target cell for a vertical wall is already occupied in the vertical-wall plane, the placement must raise ValueError. The error message must contain already placed. This applies to full or partial overlap and to walls owned by either player.
  2. Perpendicular intersection: If a proposed horizontal wall crosses a vertical wall, or a proposed vertical wall crosses a horizontal wall, the placement must raise ValueError. The error message must contain intersecting walls.

Thus, after a valid horizontal placement at (x, y), another horizontal placement over that wall is an already placed error, while an otherwise eligible vertical placement crossing it at the same wall midpoint is an intersecting walls error. Same-orientation overlap must not be reported as the perpendicular-intersection condition.

All other existing placement validation remains unchanged, including board-edge and section bounds, the acting player's available wall count, and the prohibition on blocking every path to a goal.

Wall counts and other compatibility requirements

walls_remaining retains its existing behavior and is not reconstructed from ownership values:

  • A successful ordinary wall placement decrements only the placing player's count by one.
  • A successful rotation retains its existing cost of two walls from the acting player. It does not transfer ownership of any rotated wall.
  • Removing a segment at a board boundary as a consequence of rotation does not refund a wall.
  • Rejected placements and rotations retain the existing failure behavior and must not introduce ownership-dependent count changes.

All other observable behavior must remain compatible, including:

  • movement and jump rules;
  • path-existence and win checks;
  • valid placement and rotation regions;
  • the prohibition on placing or rotating walls so that all paths are blocked;
  • state copying, serialization, deserialization, and optional step callbacks; and
  • the existing action encoding and return type.

Serialization must preserve the integer ownership values in the wall planes without collapsing 2 to 1.

Scope and non-goals

The only gameplay-facing change is the value stored in occupied cells of board[2] and board[3]: agent 0 creates value 1, agent 1 creates value 2, and those values survive valid rotations. This task does not introduce ownership-based permissions, alter wall geometry, add board planes, change action formats, or otherwise modify Puoribor's rules.
