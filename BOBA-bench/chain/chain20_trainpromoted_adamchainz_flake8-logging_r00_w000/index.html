Task Specification: Flake8 Logging Plugin — New Rule L002

Overview

You are extending a Flake8 plugin that checks for correct usage of Python's logging module. The plugin already implements a rule L001. You must add a new rule L002 and ensure existing L001 behavior continues to work for additional cases.

Public API / Test Harness Requirements

The test suite drives the plugin through a helper that:

  1. Parses a Python source string into an AST.
  2. Runs the plugin over that AST.
  3. Collects the results as a list of tuples (line, column, message), sorted by position.

The plugin must be a standard Flake8 AST plugin. Concretely, there must be a plugin class (the same one that already produces L001) that:

  • Is constructed with a single argument: the parsed AST tree.
  • Exposes a run() method that yields tuples of the form (line: int, col: int, message: str, type). The first three elements are what the test harness records. Columns are 0-based AST column offsets.

The plugin must also be registered as a Flake8 entry point so it runs under the flake8 command-line tool and emits standard L002 diagnostics.

Rule L002 — Behavior to Implement

Message string: L002 use __name__ with getLogger()

Purpose: Flag calls to getLogger() whose first positional argument is a dunder name other than __name__ (specifically __file__ and __cached__ are flagged).

When to report L002

Report an L002 diagnostic when a call to the logging getLogger function is made with a first positional argument that is a bare name node whose identifier is one of:

  • __file__
  • __cached__

The diagnostic position is the location of that argument node (its line and column offset).

The call must be recognized as a getLogger call in one of these two forms:

  1. Attribute form: logging.getLogger(...) — an attribute access named getLogger on a name logging that was imported via import logging.
  2. Direct form: getLogger(...) — a bare name getLogger that was imported via from logging import getLogger.
When NOT to report L002
  • When the first argument is __name__ (this is the correct usage).
  • When the getLogger attribute is accessed on a module other than the logging module (e.g. our_logging.getLogger(__file__) must not be flagged).
Examples of expected diagnostics

Source:

import logging
logging.getLogger(__file__)

Produces one diagnostic at line 2, column 18: L002 use __name__ with getLogger().

Source:

import logging
logging.getLogger(__cached__)

Produces one diagnostic at line 2, column 18: L002 use __name__ with getLogger().

Source:

from logging import getLogger
getLogger(__file__)

Produces one diagnostic at line 2, column 10: L002 use __name__ with getLogger().

Source:

import logging
logging.getLogger(__name__)

Produces no diagnostics.

Source:

import our_logging
our_logging.getLogger(__file__)

Produces no diagnostics.

Under the flake8 command line, the diagnostic renders as (for a two-line file where the call is on line 2):

./example.py:2:19: L002 use __name__ with getLogger()

(Note the reported column is the 0-based AST offset plus 1, per Flake8 convention.)

Existing Rule L001 — Additional Cases That Must Pass

Rule L001 flags direct instantiation of a Logger (i.e. using the logging Logger class instead of logging.getLogger()), with message L001 use logging.getLogger() to instantiate loggers. The following cases must produce no L001 diagnostics:

  • Attribute access on an unrelated module:

    import our_logging
our_logging.Logger("x")

    Produces no diagnostics.

  • An import that is not the logging module, even when aliased to a Logger-like name:

    from loggin import Logger as _Logger
_Logger("x")

    Produces no diagnostics. (The module loggin is not logging, so instantiating _Logger is not flagged.)

These confirm that L001 (and by extension L002) must only trigger when the relevant symbol truly originates from the standard logging module, tracking imports and aliases accordingly.

Task Specification: Add L003 Rule for LogRecord Attribute Clashes in extra Dict

Context

This is a flake8 plugin for detecting problems with logging usage. You must add a new lint rule, L003, that detects when keys in the extra dictionary passed to a logging call clash with reserved LogRecord attribute names.

Rule Behavior

When a logging call is made with an extra keyword argument whose value is a dictionary literal, each key in that dictionary must be checked against a set of reserved LogRecord attribute names. If a string-literal key matches one of these reserved names, an L003 violation must be reported.

Message Format

For a clashing key named <KEY>, the reported message text must be exactly:

L003 extra key '<KEY>' clashes with LogRecord attribute

(The key name appears inside single quotes.)

Reserved LogRecord Attribute Names

At minimum, the following names must be treated as clashing (these are the names exercised):

  • msg
  • args

You should include the full standard set of LogRecord attribute names so that only genuine reserved names trigger the rule. A key such as response_msg (which merely contains a reserved name as a substring) must not trigger a violation — matching is by exact key name only.

Reporting Position

Each violation is reported at the position of the dictionary key (the string literal key node), using the standard flake8 line/column convention where the internal column is 0-based (flake8 displays it +1).

Examples of behavior (given as source → reported violations, in (line, col, message) form where col is 0-based):

  • import logging
logging.info("Hi", extra={"msg": "Ho"})

    → (2, 26, "L003 extra key 'msg' clashes with LogRecord attribute")

  • import logging
logging.debug("Hi", extra={"msg": "Ho"})

    → (2, 27, "L003 extra key 'msg' clashes with LogRecord attribute")

  • import logging
logging.info("Hi", extra={"args": (1,)})

    → (2, 26, "L003 extra key 'args' clashes with LogRecord attribute")

  • A multiline call where the key is on its own line reports at that key's line and column:

    import logging
logging.info(
    "Hi",
    extra={
        "msg": "Ho",
    },
)

    → (5, 8, "L003 extra key 'msg' clashes with LogRecord attribute")

  • Multiple clashing keys in one extra dict each produce a separate violation, reported in order of their position:

    import logging
logging.info(
    "Hi",
    extra={
        "args": (1,),
        "msg": "Ho",
    },
)

    → (5, 8, "L003 extra key 'args' ...") and (6, 8, "L003 extra key 'msg' ...")

  • No violation when no key clashes:

    import logging
logging.info("Hi", extra={"response_msg": "Ho"})

    → no violations

Which Calls Are Checked

The rule applies to logging calls, matching the same call forms handled elsewhere in this plugin:

  • Module-level logging calls via the logging module, e.g. logging.info(...), logging.debug(...), including inside function definitions.
  • Calls on a logger object obtained from logging.getLogger(...), regardless of the variable name it is assigned to, e.g.:
    logger = logging.getLogger(__name__)
logger.info("Hi", extra={"msg": "Ho"})
    and
    log = logging.getLogger(__name__)
log.info("Hi", extra={"msg": "Ho"})
    Both report the clash at the key's position.

Integration Requirements

The rule must be emitted by the existing flake8 plugin so that running flake8 over a file produces output lines in the standard flake8 format, e.g.:

./example.py:2:27: L003 extra key 'msg' clashes with LogRecord attribute

(Note the displayed column is the 1-based equivalent of the internal 0-based column.)

The violations must be produced through the plugin's existing checker mechanism (the same one that already yields L001/L002 results as (line, col, message) tuples), so that programmatic invocation of the plugin over source code yields the L003 tuples described above, and command-line flake8 invocation yields the corresponding formatted output lines.

Notes / Edge Cases

  • Only dictionary literals passed directly as the extra keyword argument need be inspected; only string-literal keys are checked for clashes.
  • Matching is exact against the reserved attribute-name set; substrings do not count.
  • Each clashing key yields exactly one violation, reported at that key's own source position.

This task concerns a Flake8 plugin for logging-related checks. You will be extending an existing check identified by the code L003.

The L003 check inspects calls to standard-library logging functions/methods that accept an extra keyword argument. Specifically, it applies to:

  • Module-level logging calls such as logging.info(...).
  • Logger-method calls such as logger.info(...), where logger is obtained from logging.getLogger(...).

When such a call includes an extra keyword argument whose value defines a set of keys, the check must flag any key that clashes with a reserved LogRecord attribute name. msg is one such reserved attribute name.

(line, col, "L003 extra key '<key>' clashes with LogRecord attribute")

The reported position (line, col) is the location of the extra keyword argument's value expression within the source.

The L003 check must recognize the extra value when it is written as a dict(...) constructor call using keyword arguments, in addition to any dictionary forms already supported.

05 Add Lint Rule L004 for logger.exception() Outside except Clauses 706 words · source specification

Task Specification: Add Lint Rule L004 for logger.exception() Outside except Clauses

Context

You are extending an existing Flake8 plugin for detecting misuse of the Python standard logging module. This plugin already implements rules such as L003, and you must add a new rule, L004.

The plugin exposes a checker class that Flake8 discovers as a plugin (via its entry point). It analyzes a parsed AST and yields lint results. Each result is a tuple of the form:

(line_number, column_offset, message)

where line_number is 1-based, column_offset is 0-based, and message is a string beginning with the rule code.

New Rule: L004

Purpose

Flag calls to .exception() on the logging module or on a logger object when the call does not occur inside an except clause. The logging.exception() / logger.exception() API is only meaningful while handling a currently-active exception (i.e., within an except block), so calling it elsewhere is a mistake.

Message

The exact message text (following the standard <line>:<col>: prefix in Flake8 output) is:

L004 avoid logger.exception() outside of except clauses
What to Detect

A call is flagged when all of the following hold:

  1. The call is a method call of the form <something>.exception(...), where <something> is:
    • the logging module itself (i.e., logging.exception(...)), or
    • a logger object obtained from logging.getLogger(...) and assigned to a name (e.g. logger = logging.getLogger(__name__) followed by logger.exception(...)).
  2. The call does not lexically occur inside an except clause body.

The reported position is the position of the flagged call expression (line and column of the call).

Rules for "Inside an except Clause"

  • A .exception() call placed directly within the body of an except clause is acceptable and must not be flagged. This applies whether the try/except is at module level or nested inside a function definition.

  • A .exception() call that is inside a function definition which is itself nested inside an except clause must still be flagged. Because the function may be called at any later time (not necessarily while the exception is active), being lexically wrapped in an except via an intervening def does not make the call safe. In other words, when determining whether a call is "inside an except clause," a function-definition boundary between the call and the enclosing except breaks the protection.

  • A .exception() call at module level with no enclosing except is flagged.

  • A .exception() call inside a function definition, where there is no enclosing except clause between the call and the function scope (nor at module scope), is flagged.

Examples of Behavior

Flagged (each produces one L004 result at the call site):

import logging
logging.exception("Hi")            # module-level, no except

import logging
def thing():
    logging.exception("Hi")        # inside function, no except

import logging
try:
    acme_api()
except AcmeError:
    def handle():
        logging.exception("Hi")    # inside a def nested in except -> flagged
    handle()

import logging
logger = logging.getLogger(__name__)
logger.exception("Hi")             # logger var, no except

import logging
logger = logging.getLogger(__name__)
def thing():
    logger.exception("Hi")         # logger var inside function, no except

Not flagged (produce no L004 results):

import logging
try:
    acme_api()
except AcmeError:
    logging.exception("Hi")        # directly inside except

import logging
def thing():
    try:
        acme_api()
    except AcmeError:
        logging.exception("Hi")    # directly inside except within a function

import logging
logger = logging.getLogger(__name__)
try:
    acme_api()
except AcmeError:
    logger.exception("Hi")         # logger var, directly inside except
Recognition of the Logging Module and Logger Objects
  • The logging module must be recognized when imported via import logging and referenced as logging.exception(...).
  • A logger object must be recognized when created via logging.getLogger(...) and bound to a name through simple assignment (e.g., logger = logging.getLogger(__name__)); subsequent .exception(...) calls on that name are treated as logger calls.

Integration Requirement

The rule must be produced by the existing Flake8 plugin such that running Flake8 over a file containing an offending call emits a diagnostic line in the standard format, for example:

./example.py:2:1: L004 avoid logger.exception() outside of except clauses

(Note the Flake8-reported column is 1-based, i.e., the 0-based AST column offset plus one.)

Constraints

  • Do not alter the behavior of existing rules.
  • Only the behavior described above is required for L004.

  • The checker class is available as flake8_logging.Plugin. It accepts a parsed AST through the tree keyword argument, for example Plugin(tree=parsed_tree).

    (line_number, column_offset, message, type)

LOG001 — use logging.getLogger() to instantiate loggers

Report direct construction of a standard-library logging.Logger where logging.getLogger() should be used instead.

Exact message:

LOG001 use logging.getLogger() to instantiate loggers

  • logging.Logger(...) after import logging.
  • The corresponding module-attribute call through an import alias, such as import logging as log_module followed by log_module.Logger(...).
  • Logger(...) after from logging import Logger.

For the module-attribute forms (logging.Logger(...) and the equivalent call through a module alias), scope affects the result:

  • Report calls in a module body.
  • Report calls in a class body when that class is not lexically inside a function.
  • Do not report calls within the body of a synchronous function (def) or asynchronous function (async def). This suppression includes method bodies and scopes nested within such a function.

The direct-name form imported with from logging import Logger remains recognized wherever it occurs, including inside function bodies.

Do not report a similarly named constructor that is not known to come from the standard-library logging module, such as our_logging.Logger(...) or an unrelated local Logger(...).

Report the position at the start of the call expression.

LOG002 use __name__ with getLogger()

LOG003 extra key '<key>' clashes with LogRecord attribute

LOG003 extra key 'msg' clashes with LogRecord attribute

  • Module-level logging calls such as logging.info(...) and logging.debug(...), including calls through an alias for the imported logging module.

  • Equivalent calls on recognized logger objects, such as a logger created with logging.getLogger(...).
  • The generic logging.log(level, message, ...) and corresponding logger .log(...) form.

For normal level methods, the message is the first positional argument. For .log(...), the level is the first positional argument and the message is the second positional argument.

LOG012 analyzes only a message supplied positionally. A message supplied through the msg= keyword is outside this check, for both ordinary level methods and .log(...).

Statically Analyzable Messages

The positional message must be a statically determinable string literal. A logical string assembled entirely from string literals is also analyzable:

  • Adjacent string literals that Python implicitly concatenates are treated as one string.
  • Explicit + chains whose every operand is a string literal are flattened in source order and treated as one string.

For example, both of these are analyzed as "Blending %s":

logging.info("Blending " "%s")
logging.info("Blending " + "%s")

A bytes literal, a dynamic expression, or a concatenation containing a non-string operand is not a statically analyzable LOG012 template and must not produce a LOG012 diagnostic.

Placeholder Counting

Count positional %-style conversion specifiers in the complete message string. Ordinary conversions such as %s, %r, %d, and other supported % conversions each consume one positional formatting argument. Conversion flags, fixed field widths, fixed precision, and length modifiers do not themselves consume arguments.

A * used for minimum field width or precision consumes one additional positional argument, in addition to the converted value:

  • %*d requires 2 arguments: width and value.
  • %.*f requires 2 arguments: precision and value.
  • %*.*f requires 3 arguments: width, precision, and value.

A literal escaped percent sign, %%, consumes no argument and is not a placeholder. Mapping/named conversions such as %(fruit)s are not positional placeholders for LOG012. Other formatting syntaxes, including {}/str.format style and $name template style, are also outside LOG012.

Let N be the total number of required positional arguments after accounting for both conversion values and * width/precision arguments.

Formatting-Argument Counting

Let M be the number of explicit positional arguments after the message:

  • For logging.info(message, arg1, arg2), M is 2.
  • For logging.log(level, message, arg1, arg2), M is 2; neither the level nor the message is a formatting argument.
  • Logging control keywords such as extra=, exc_info=, stack_info=, and stacklevel= do not contribute to M.

Zero explicit formatting arguments is a valid, determinate count: M = 0. It is not an exemption. Thus a positional message requiring one or more arguments must be diagnosed when no formatting arguments follow it.

In that case, emit no LOG012 diagnostic for the call, even if explicit positional formatting arguments are also present or the apparent count would otherwise mismatch.

  1. The message is a positional, statically analyzable string.

  4. N does not equal the explicit positional formatting-argument count M.
