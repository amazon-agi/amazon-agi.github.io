Task Description

Background

You are working on the numpydoc library, whose job is to parse NumPy-style docstrings into structured data. The parsing logic relevant to this task lives in numpydoc/docscrape.py.

Docstrings contain sections such as Returns, in which each entry describes a returned value. Parsing turns each entry into a 3-tuple of the form (name, type, description):

  • name — a string, namely the parameter/return name
  • type — a string, namely the type annotation
  • description — a list of strings, namely the multi-line description text

An entry in a section like Returns can take several written forms. For instance, an entry may be a single line that has only a name (or type), with no colon separator and no following indented description lines.

Change Required

A Returns-section entry that consists of a single line with no description and no type separator must be handled correctly by the parser.

To be specific: when an entry line has no : type-separator and is not followed by any indented continuation lines (i.e., there is no description body), the parser must produce a 3-tuple in which:

  • name is the text of the single line (stripped),
  • type is the empty string '',
  • description is a list that, once joined and stripped, yields the empty string (i.e., holds no meaningful text).

This must work even when such a bare, description-less entry is the final entry in the section, and must not result in the entry being dropped or merged with others during parsing. All existing entry forms (a name with a type and a multi-line description; anonymous entries where the line has no colon but does have a following indented description) must keep parsing the way they did before.

Rendering

The parsed structure also gets rendered back out in two formats.

Plain-text / str output: Whenever the document is rendered back to a numpydoc-style string, a bare description-less entry must appear as its single name line (e.g. a line reading no_description), thereby preserving it in the Returns section.

reStructuredText output: When rendering to reST, a description-less entry must still emit its name followed by a placeholder description line so that the output stays well-formed. In concrete terms, such an entry renders as the name line followed by an indented line that contains .. (a placeholder), e.g.:

    no_description
        ..

Task: Emit Item Names in Bold within Sphinx-Format Docstring Output

Context

NumPy-style docstrings are parsed by the numpydoc package, which can additionally render them into reStructuredText (RST) output formatted for Sphinx. Named items appear in that RST output inside several sections, each item followed by its type and its description — the Parameters, Returns, Yields, Other Parameters, Attributes, Raises, and Warns sections are examples.

At present, rendering these sections into Sphinx-format RST emits the item name as plain text. The consequence is a problem: a name ending in an underscore (such as word_) is misinterpreted by RST as a hyperlink reference. Item names must therefore be wrapped in bold markup to avoid this.

Required Modification

In the Sphinx-format RST rendering of parsed docstring sections, the name of every listed item is to be wrapped in RST strong (bold) emphasis — that is, ** goes on each side of it.

Every section that renders items as a definition-list style block with a term line is covered by this. Each such term line appears in one of two forms:

  1. Item with a name and a type: the rendering is

    **name** : type

    Here name stands for the item's name enclosed in **...**; next comes : (space, colon, space), and the type text follows it, rendered as-is.

  2. Item having only a name/type, without a separate name (this is an anonymous entry, since no distinct name exists that could pair with a type): the one text token itself receives the **...** wrapping, which renders as

    **text**

After each term line, the indented description lines are left unchanged.

Edge Cases and Details
  • Whether or not the item has a type, the term must receive the ** wrapping. With a type present, only the name gets bolded, and the type after : stays plain. Where no name/type split exists, it is the lone token that gets bolded.
  • Entries whose term already takes the form of an explicit RST cross-reference role (a term already written, for instance, as :obj:label <target>``) must be left exactly as they are — do NOT wrap these in **. The terms affected are only the plain-text name/type-style ones described above.
  • Everything else in the output — section headers (:Parameters: is one example), blank lines, indentation, description text, math blocks, nested lists, and directives — stays exactly as before.

It is for the Parameters, Returns, Yields, Other Parameters, Attributes, Raises, and Warns sections that this behavior gets exercised; both the name : type form and the anonymous single-token form are covered by it.

Module Removal

The module numpydoc/__main__.py and the command-line main entry point that goes with it are both to be deleted entirely. After that, the module must no longer exist — and the same holds for any callable named main importable from numpydoc.__main__.

Effect on the Public API

The public API gains nothing new from this change. The updated output described above is what the existing Sphinx RST rendering path — the classes/functions in numpydoc.docscrape and numpydoc.docscrape_sphinx, which produce Sphinx-format RST from NumPy-style docstrings — must produce. As for the numpydoc.__main__ module: it must be removed.

Task Specification: Bold Wrapping of Parameter Names in Sphinx reST Output

Background

In this task you work on numpydoc, a tool that parses NumPy-style docstrings and turns them into Sphinx reStructuredText (reST). The component of interest is the reST renderer that emits :Parameters:, :Returns:, :Yields:, :Other Parameters:, :Raises:, :Warns:, and :Attributes: sections.

Behavior Change Required

When a section that lists named items (parameters, returns, yields, other parameters, raises, warns, attributes) is rendered, the name portion of each item's definition-list term must be wrapped in reST strong emphasis — that is, flanked by ** on each side.

Rendering rules in detail

Each item in the list is emitted as a definition-list entry made up of a term line followed by an indented description.

  1. Item that has a name and a type. The term must be rendered in this form:

    **<name>** : <type>

    For example, an item named mean whose type is (N,) ndarray gets the term:

    **mean** : (N,) ndarray

    The : separator (space, colon, space) that sits between the bolded name and the type must be preserved exactly.

  2. Item that has a name but no type. When an item carries a name and no type, the entire term consists of the bolded name only:

    **<name>**

    For instance, an item named list of str without a type has the term **list of str**; an item named RuntimeError has the term **RuntimeError**; an item named int has the term **int**.

  3. The description block (the indented lines that follow the term, including any nested content such as .. math:: directives, bullet lists, or an empty .. placeholder) is not affected by this change and must continue to be rendered as it was before.

Items that must NOT receive the wrapping

Terms that already come out as an explicit cross-reference role (of the form :obj:name <target>``) must remain unchanged — do not wrap them in **. The bold wrapping is applied only to plain-text names.

Rationale (a behavioral requirement, not implementation guidance)

An earlier change took out the explicit bold wrapping and relied on Sphinx definition lists to bold the term automatically. As a result, names ending in an underscore (e.g. word_) were misinterpreted by reST as hyperlink references. Wrapping the name in ** prevents this misinterpretation. Note: escaping the underscore (\_) is not acceptable, since the backslash would show up in the rendered HTML.

Public API Surface

Nothing about the public parsing/rendering API changes. The class that parses and renders Sphinx-style docstrings must still be importable and used exactly as before; the only difference that can be observed is that the term lines emitted for named/listed items now wrap the name in ** as described above. Its reST string output is produced by rendering the parsed docstring object to a string (str(...)).

The change introduces no new modules, classes, functions, or signatures. The content of the emitted reST for the sections listed above is the only thing that changes.

Part 2: Wiring the Feature into SphinxDocString

During rendering of the Parameters, Other Parameters, and Returns sections, the SphinxDocString class (which lives in numpydoc/docscrape_sphinx.py) must accept configuration controlling this feature and apply make_xref_param_type to the type portion of each parameter entry.

Recognized Configuration Keys

An optional config dict is passed to SphinxDocString at construction time. These keys must be recognized:

  • xref_param_type (bool): a truthy value turns on cross-reference wrapping of parameter type strings; with the key absent or falsy, type strings are rendered unchanged (existing behavior).
  • xref_aliases (dict): handed over to make_xref_param_type as the alias map.
  • xref_ignore (set): handed over to make_xref_param_type as the ignore set.
Rendering With the Feature Enabled

With xref_param_type enabled, the rendered :Parameters: / :Other Parameters: / :Returns: output must show the type transformed by make_xref_param_type for every parameter/return entry that has a type string. The type portion is the only part transformed; the parameter name, the description body, and trailing markers like , optional keep behaving as they currently do (tokens such as optional stay unchanged because the ignore set contains them).

As an example, suppose the input parameters/returns are:

and the config has xref_param_type=True, the aliases {'sequence': ':term:python:sequence', 'iterable': ':term:python:iterable', 'array': 'numpy.ndarray'}, and the ignore {'of', 'default', 'optional'}; the rendered type strings must then come out as:

1. Public cross-reference API

numpydoc.xref.make_xref

This public function must be provided:

def make_xref(param_type, xref_aliases, xref_ignore):
    ...

Parameters:

  • param_type: a parameter-type expression, given as a string. It may contain identifiers, qualified names, containers, punctuation, existing RST markup, literals, and arbitrary spacing.
  • xref_aliases: a mapping whose keys are plain tokens and whose values are either a bare link target or a complete RST role.
  • xref_ignore: a set of tokens that must stay unlinked.

The function returns the converted string. make_xref takes the place of the previous public name make_xref_param_type, which is no longer part of the public API. Any links that are generated must use standard :obj: roles, and the generated output must not use :xref_param_type:.

When make_xref is called directly, the alias and ignore collections passed to the function are the ones it uses. Built-in aliases at the configuration level are supplied via the configuration integration described below; this function does not add them implicitly.

How tokens are converted

  1. Default links. An identifier or qualified name that is eligible for linking and not covered by an alias or ignore entry is wrapped as ``:obj:`token```.

    Among the examples are float, bool, None, True, False, callable, int, str, list, dict, tuple, ndarray, spmatrix, pathlib.Path, and single-letter names such as M and N.

  2. Aliases. When a token is a key in xref_aliases:

    • A value that already is a complete RST role is emitted verbatim. For example, mapping array_like to ``:term:`numpy:array_like``` produces that term role unchanged.
    • A bare target serves as the target of an :obj: link, with the original token kept as its displayed text. For example:
      • array mapped to numpy.ndarray results in ``:obj:`array <numpy.ndarray>```.
      • ndarray mapped to numpy.ndarray results in ``:obj:`ndarray <numpy.ndarray>```.
      • string mapped to str results in ``:obj:`string <str>```".

  3. Ignored tokens. Any token found in xref_ignore is emitted unchanged. Words that are typically ignored include or, in, of, default, and optional.

  4. Protected RST and literals. The conversion must not modify:

    • RST roles or references that already exist, such as ``:ref:`strftime <strftime-strptime-behavior>```;
    • expressions that are already enclosed in single backticks;
    • inline literals enclosed in double backticks, with their punctuation and spaces included;
    • literals that are quoted strings, such as '', 'greedy', 'optimal', 'C', 'F', 'A', 'K', and 'linear';
    • fragments that are numeric or describe shapes, such as (...), (2,), (...,M,N), 1-D, [0, 255], 1, and 0;
    • token forms that are not supported, such as unicode-like, and trailing expression fragments such as f'(x,*args).

  5. Delimiters and containers. Parentheses, square brackets, curly braces, commas acting as separators, and the whitespace around them are preserved. Processing is recursive for tokens inside supported containers. A comma with no separating whitespace may stay part of an unsupported numeric or shape fragment; the difference between (...,M,N) and (..., M, N) below illustrates this.

  6. RST bracket escaping. When a generated role is immediately followed by an opening container character (, [, or {, a backslash is inserted before that opening character so that the role is valid RST. The same rule applies to nested containers.

  7. Formatting preservation. All original punctuation, delimiters, whitespace, and repeated interior spaces are preserved, apart from the token substitutions and the required bracket escaping above. When an expression cannot be safely split or recognized, it is kept unchanged.

3. Rendering docstrings

In Sphinx-oriented docstring output, the names in these field-list entries keep the established bold formatting. When type xref conversion is active:

  1. Type expressions found in Parameters, Other Parameters, and Returns entries are converted by make_xref, using the effective alias and ignore settings.
  2. Names in those entries, where present, are rendered with RST strong emphasis, i.e. as **name**.
  3. Complete RST roles that already exist, single-backtick expressions, double-backtick literals, punctuation, and spacing keep the preservation behavior specified for make_xref.

4. Rendering the index

For index output, meaningful parsed index metadata is told apart from an empty placeholder:

  • A docstring that has no meaningful index information must not acquire a generated empty .. index:: block; ordinary parameter/return documentation is covered by this just as much as class and member-list documentation.
  • An .. index:: directive that is explicitly empty likewise must not produce an empty rendered block.
  • Index information that is explicit and non-empty must be preserved; it must not be removed merely because the directive is trailing in the source or output.

With plain NumpyDocString string output, meaningful index metadata is rendered at the end of the document in its parsed form. For example:

.. index:: random
   :refguide: random;distributions, random;gauss

In Sphinx-oriented output, the meaningful index block precedes the main rendered content, per the standard template, and refguide entries are emitted as single index entries. The example that corresponds is:

.. index:: random
   single: random;distributions, random;gauss

Meaningful index categories of other kinds must likewise remain represented. Suppression happens only for empty or absent index content.

5. Compatibility and out-of-scope items

  • When xref conversion is disabled, existing behavior must remain unchanged.
  • Existing parsing, section ordering, class/member handling, summaries, descriptions, examples, references, and other non-xref output must stay compatible.
  • Because generated xrefs use standard RST roles, a custom xref_param_type role is not needed for the new output.
  • This task does not call for a redesign of the general NumPy docstring format or of unrelated rendering behavior.
