Overview

Update numpydoc's parameter-type cross-reference generation to use standard reStructuredText object roles, expose the renamed public conversion function, integrate a complete default alias map with configuration, and preserve meaningful index metadata while suppressing empty index placeholders.

All existing docstring parsing and rendering behavior outside the contracts below must remain compatible.

1. Public cross-reference API

numpydoc.xref.make_xref

Provide this public function:

def make_xref(param_type, xref_aliases, xref_ignore):
    ...

Parameters:

  • param_type is a parameter-type expression as a string. It may contain identifiers, qualified names, containers, punctuation, existing RST markup, literals, and arbitrary spacing.
  • xref_aliases is a mapping from a plain token to either a bare link target or a complete RST role.
  • xref_ignore is a set of tokens that must remain unlinked.

The return value is the converted string. The previous public name make_xref_param_type is replaced by make_xref and is no longer part of the public API. Generated links must use standard :obj: roles; generated output must not use :xref_param_type:.

Direct calls to make_xref use the alias and ignore collections passed to the function. Configuration-level built-in aliases are supplied through the configuration integration described below rather than being implicitly added by this function.

Token conversion

  1. Default links. A link-eligible identifier or qualified name not covered by an alias or ignore entry is wrapped as ``:obj:`token```.

    Examples include float, bool, None, True, False, callable, int, str, list, dict, tuple, ndarray, spmatrix, pathlib.Path, and single-letter names such as M and N.

  2. Aliases. If a token is a key in xref_aliases:

    • A value that is already a complete RST role is emitted verbatim. For example, array_like mapped to ``:term:`numpy:array_like``` produces that term role unchanged.
    • A bare target is used as the target of an :obj: link while preserving the original token as its displayed text. For example:
      • array mapped to numpy.ndarray becomes ``:obj:`array <numpy.ndarray>```.
      • ndarray mapped to numpy.ndarray becomes ``:obj:`ndarray <numpy.ndarray>```.
      • string mapped to str becomes ``:obj:`string <str>```.

  3. Ignored tokens. A token in xref_ignore is emitted unchanged. Typical ignored words include or, in, of, default, and optional.

  4. Protected RST and literals. The conversion must not alter:

    • existing RST roles or references, such as ``:ref:`strftime <strftime-strptime-behavior>```;
    • expressions already enclosed in single backticks;
    • inline literals enclosed in double backticks, including their punctuation and spaces;
    • quoted string literals such as '', 'greedy', 'optimal', 'C', 'F', 'A', 'K', and 'linear';
    • numeric and shape fragments such as (...), (2,), (...,M,N), 1-D, [0, 255], 1, and 0;
    • unsupported token forms such as unicode-like and trailing expression fragments such as f'(x,*args).

  5. Delimiters and containers. Parentheses, square brackets, curly braces, commas used as separators, and their surrounding whitespace are preserved. Tokens inside supported containers are processed recursively. Commas without separating whitespace may remain part of an unsupported numeric or shape fragment, as illustrated by the distinction between (...,M,N) and (..., M, N) below.

  6. RST bracket escaping. If a generated role is immediately followed by an opening container character (, [, or {, insert a backslash before that opening character so the role is valid RST. Nested containers follow the same rule.

  7. Formatting preservation. Preserve all original punctuation, delimiters, whitespace, and repeated interior spaces except for the token substitutions and required bracket escaping above. If an expression cannot be safely split or recognized, preserve it unchanged.

2. Configuration integration

numpydoc.numpydoc.update_config

Provide update_config(app). It reads the following attributes when present on app.config and makes their effective values available to subsequent docstring rendering:

  • numpydoc_xref_param_type: whether type cross-reference conversion is enabled;
  • numpydoc_xref_aliases: user alias mapping;
  • numpydoc_xref_ignore: tokens to leave unwrapped.

The built-in alias mapping is exactly:

    "bool": ":class:`python:bool`",
    "complex": ":class:`python:complex`",

Combine these entries with user aliases into one effective mapping. Every built-in entry shown above and every non-conflicting user entry must be present with its exact value.

After update_config returns:

  • app.config.numpydoc_xref_aliases must expose the effective merged mapping;
  • the effective mapping must be used by later docstring processing;
  • a caller that retains and subsequently passes the originally supplied alias dictionary to SphinxDocString must observe the merged defaults as well. For example, after configuring only sequence, later rendering with that same mapping must still resolve int, float, list, and array through the built-ins.

This is an observable propagation requirement and does not mandate a particular internal storage mechanism.

update_config must also accept a lightweight app whose config exposes only numpydoc_xref_aliases. Missing xref-enable or ignore attributes in this minimal case must not raise an error or prevent alias merging. Normal extension-driven rendering, including the mangle_docstrings pipeline, must perform this configuration update before rendering docstrings.

3. Docstring rendering

For Sphinx-oriented docstring output, names in these field-list entries continue to use the established bold formatting. When type xref conversion is active:

  1. Type expressions in Parameters, Other Parameters, and Returns entries are converted with make_xref using the effective alias and ignore settings.
  2. Names in those entries, when present, are rendered with RST strong emphasis, as **name**.
  3. Existing complete RST roles, single-backtick expressions, double-backtick literals, punctuation, and spacing retain the preservation behavior specified for make_xref.
  4. Bare aliases use :obj: links, while aliases that are already complete roles retain their configured role.

4. Index rendering

Index output distinguishes meaningful parsed index metadata from an empty placeholder:

  • A docstring with no meaningful index information must not acquire a generated empty .. index:: block. This applies to ordinary parameter/return documentation as well as class and member-list documentation.
  • An explicitly empty .. index:: directive likewise must not produce an empty rendered block.
  • Explicit, non-empty index information must be preserved; it must not be removed merely because the directive is trailing in the source or output.

For plain NumpyDocString string output, meaningful index metadata is rendered at the end of the document in its parsed form. For example:

.. index:: random
   :refguide: random;distributions, random;gauss

For Sphinx-oriented output, the meaningful index block precedes the main rendered content according to the standard template, and refguide entries are emitted as single index entries. The corresponding example is:

.. index:: random
   single: random;distributions, random;gauss

Other meaningful index categories must likewise remain represented. Only empty or absent index content is suppressed.

5. Compatibility and non-goals

  • Existing behavior when xref conversion is disabled must remain unchanged.
  • Existing parsing, section ordering, class/member handling, summaries, descriptions, examples, references, and other non-xref output must remain compatible.
  • Generated xrefs use standard RST roles, so a custom xref_param_type role is not required for the new output.
  • The task does not require redesigning the general NumPy docstring format or unrelated rendering behavior.
