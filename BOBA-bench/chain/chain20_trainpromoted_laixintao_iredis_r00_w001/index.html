Task: Add parsing support for the CLUSTER KEYSLOT command

Background

This codebase already contains a command-parsing facility that takes a Redis-style command string and turns it into a structured dictionary of named components. Your task is to extend this facility so that the CLUSTER KEYSLOT command gets recognized and parsed correctly.

Parser Behavior (existing infrastructure)

The parser is invoked via a function that receives a command string and returns either:

  • a dictionary mapping component names to their parsed string values (on a successful parse), or
  • None (when the input does not match a valid command form).

The command keyword portion is taken verbatim from the input, with its original letter casing included (e.g. lowercase, uppercase, or mixed).

Required New Behavior: CLUSTER KEYSLOT

Add parsing support for the CLUSTER KEYSLOT <key> command.

Syntax

The command is made up of the two-word command keyword cluster keyslot, followed by exactly one argument: the key.

Result on a successful parse

If the input matches, the parser must return a dictionary holding exactly these two entries:

  • "command_key": the command keyword portion exactly as it appeared in the input (its original casing is kept, as is the original spacing between the two words — a single space).
  • "key": the key argument exactly as it appeared in the input.
Letter casing

For matching, the command keyword is case-insensitive; in the result, however, it is echoed back verbatim as given. Examples:

  • Input cluster keyslot mykey → {"command_key": "cluster keyslot", "key": "mykey"}
  • Input CLUSTER KEYSLOT MYKEY → {"command_key": "CLUSTER KEYSLOT", "key": "MYKEY"}

The key argument itself is likewise preserved verbatim (its casing is never modified).

Key arguments in double quotes

The key argument may be given as a double-quoted string. When the key is wrapped in (or contains) double quotes, the quote characters remain part of the "key" value — the value is captured exactly as it appears in the input, including surrounding quotes, embedded escaped quotes, and any internal whitespace. Examples:

  • Input cluster keyslot "mykey" → {"command_key": "cluster keyslot", "key": "\"mykey\""}
  • Input cluster keyslot "\"mykey" → {"command_key": "cluster keyslot", "key": "\"\\\"mykey\""} (i.e., the raw characters "\"mykey")
  • Input cluster keyslot "mykey " → {"command_key": "cluster keyslot", "key": "\"mykey \""} (a trailing space inside the quotes is preserved)

Scope

Add only the CLUSTER KEYSLOT command handling described above. Do not change the behavior of any other command that the parser already supports.

Task Specification: Grammar for Redis Commands

Overview

You must supply a grammar object that parses Redis CLUSTER subcommands and extracts named tokens from a command string. The grammar must recognize the syntax of several CLUSTER subcommands and expose the parsed components as named variables.

Public API

Supply a module importable as:

iredis.redis_grammar

A module-level object named redis_grammar must be exposed by this module.

The object must support the following:

  • redis_grammar.match(command_string) — returns a match object when the given command string is recognized by the grammar, or None when it is not recognized.
  • The returned match object must support .variables(), which returns a mapping (dict-like) from token name (string) to the matched substring (string). An unmatched token looked up via .get(name) must return a falsy/None value.

Rules for Matching

At the keyword level, commands are matched case-insensitively: the command keyword may appear in any case (e.g. cluster meet, CLUSTER MEET), and the token that captures the command keyword must reflect the case exactly as typed in the input.

The entire command string must be matched. Trailing arguments in excess of what a subcommand accepts must cause the match to fail (return None). Prefixing the keyword with leading text (e.g. Acluster info) must not match.

For each supported subcommand below, a successful match must produce a variables() mapping containing the listed token names with the described values.

cluster addslots and cluster delslots
  • Accepts one or more integer slot values, separated from one another by single spaces.
  • Token command_slots = the command keyword as it was typed (e.g. cluster addslots).
  • Token slots = the whole space-joined string of slot integers (e.g. 1 or 1 2 3 4).
  • Non-integer arguments (e.g. a, abc, or a mix such as 1 a) must not match.
cluster count-failure-reports and cluster forget
  • Exactly one integer node argument is accepted.
  • Token command_node = the command keyword as it was typed.
  • Token node = the string of the single integer.
  • More than one argument, arguments that are non-integer, or a mix must not match.
cluster countkeysinslot
  • Exactly one integer slot argument is accepted.
  • Token command_slot = the command keyword as it was typed.
  • Token slot = the string of the single integer.
  • More than one argument, or non-integer arguments, must not match.
cluster failover
  • Accepts exactly one choice argument; its value (case-insensitive) is force or takeover.
  • Token command_failoverchoice = the command keyword as it was typed.
  • Token failoverchoice = the choice as it was typed (case preserved, e.g. force, FORCE, takeover, TAKEOVER).
cluster getkeysinslot
  • Exactly two integer arguments are accepted: a slot and a count.
  • Token command_slot_count = the command keyword as it was typed.
  • Token slot = the string of the first integer.
  • Token count = the string of the second integer.
  • Fewer or more than two arguments, or arguments that are not integers, must not match.
cluster info
  • No arguments are accepted.
  • Token command = the command keyword as it was typed.
  • Any argument trailing the command must not match.
cluster keyslot
  • Exactly one key argument is accepted.
  • Token command_key = the command keyword as it was typed.
  • Token key = the key as it was typed.
  • The key may be a bare word (e.g. mykey, MYKEY) or a double-quoted string. When the key is double-quoted, the entire quoted literal (surrounding quotes included) is the token value:
    • "mykey" → token value "mykey"
    • A quoted string holding an escaped quote, e.g. "\"mykey" → the token value includes the backslash-escaped quote exactly as typed.
    • A quoted string that contains spaces, e.g. "mykey " → the space inside the quotes is preserved.
cluster meet
  • Exactly two arguments are accepted: an IPv4 address and a port.
  • Token command_ip_port = the command keyword as it was typed (e.g. cluster meet).
  • Token ip = the IPv4 address as a string.
  • Token port = the port as a string.

Validation of the IPv4 address: Each of the four octets, separated by dots, must be a valid integer in the range 0–255. Any value with an octet greater than 255 (e.g. 192.168.0.256, 192.256.0.26, 99.999.100.1, 300.168.0.1) must not match. Valid examples include 192.168.0.1, 255.255.255.255, 0.0.0.0.

Validation of the port: The port must be an integer within the range 1–65535, inclusive. A port of 0 must not match. Any value above 65535 (e.g. 65536, 65545, 65635, 66535, 75535, 99999, 99999999) must not match. An IP-like value sitting in the port position (e.g. 192.168.0.256) must not match. Valid examples include 1, 1024, 6553, 65535.

Notes

  • When a command string fails to match the grammar, match returns None.
  • Token values always reflect the exact text from the input (case and quoting preserved).
