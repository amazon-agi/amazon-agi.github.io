  • Supply the module joommfutil/typesystem.py, which is importable as joommfutil.typesystem.
  • Move or rename the type-system content that the plural package currently exposes so that it resides under the singular package.

The class decorator typesystem

The module must expose typesystem(**kwargs), a factory that produces a class decorator. Every keyword names an attribute to install on the decorated class, and the value paired with it supplies that attribute's descriptor.

@ts.typesystem(
    coefficient=ts.Real,
    axis=ts.RealVector(size=3),
    metadata=ts.TypedAttribute(expected_type=dict),
)
class Example:
    def __init__(self, coefficient, axis, metadata):
        self.coefficient = coefficient
        self.axis = axis
        self.metadata = metadata

For each keyword argument, the decorator must obtain a descriptor instance, bind the descriptor's name to the keyword, and attach that instance to the decorated class under the keyword. The decorator must return the decorated class.

When a descriptor class needs no configuration, it may be passed directly, as with ts.Real, ts.Int, ts.String, ts.Vector, or ts.ObjectName. A descriptor that is already configured is passed as an instance, as with ts.SizedVector(size=2) or ts.TypedAttribute(expected_type=dict).

Mandatory options are validated at the time the descriptor is instantiated. If a descriptor class that requires an option is passed bare, instantiating it while decorating the class must raise the same TypeError. Specifically, bare ts.SizedVector lacks size, and bare ts.TypedAttribute lacks expected_type.

Behavior common to descriptors

Once installed as class attributes, descriptors must have the following behavior:

  • Assigning a valid value stores the original value as given, with no conversion and no copying. Reading the instance attribute returns the assigned value unchanged.
  • Subsequent valid assignments replace the stored value. Each instance stores its values separately.
  • An invalid assignment raises the descriptor-specific exception documented below.
  • Deleting an instance attribute that a descriptor manages is forbidden and raises AttributeError.

The general-purpose descriptor foundations of the module remain public:

  • Descriptor is an unconstrained descriptor: once it has a name, it accepts and stores any value that is assigned.
  • Typed(expected_type=T) accepts a value exactly when isinstance(value, T) is true; in any other case it raises TypeError.
  • MaxSized(size=n) requires the size option and accepts values whose length is exactly n; omitting size raises TypeError, while assigning a value of the wrong length raises ValueError.
  • Unsigned requires a value that is greater than or equal to zero and raises TypeError for a negative value.
  • Positive requires a value that is strictly greater than zero and raises TypeError when the value is zero or negative.

Task Specification: Descriptors for the Type System

Overview

Implement the descriptor-based type system that joommfutil.typesystem exposes. This API makes it possible for a class decorator to install validating descriptors on named class attributes. Whenever a controlled instance attribute is assigned — both during instance initialization and on later reassignment — validation occurs.

A conforming assignment must succeed with the supplied value left uncoerced, and reading the attribute afterward must return that assigned value. An assignment that does not conform must raise the exception specified below.

Public API

The names below must remain available from the public module:

  • Descriptor
  • Typed
  • TypedAttribute
  • MaxSized
  • Unsigned
  • Positive
  • Real
  • Int
  • String
  • UnsignedReal
  • UnsignedInt
  • PositiveReal
  • Vector
  • SizedVector
  • RealVector
  • PositiveRealVector
  • ObjectName
  • typesystem

Imports normally use this form:

import joommfutil.typesystem as ts
typesystem(**attributes)

typesystem functions as a class decorator factory. Each keyword gives an attribute name, and each value is either:

  1. a descriptor class — ts.Real or ts.ObjectName, for example; or
  2. a descriptor instance that has already been configured — ts.SizedVector(size=2) or ts.TypedAttribute(expected_type=dict), for example.

Once applied, the decorator installs a descriptor under every supplied attribute name and returns the decorated class. A descriptor class that needs no extra options can be passed directly. A descriptor that requires configuration must be instantiated with that configuration before it is passed to the decorator.

For example:

@ts.typesystem(
    real=ts.Real,
    integer=ts.Int,
    text=ts.String,
    unsigned=ts.UnsignedReal,
    positive=ts.PositiveReal,
    vector=ts.Vector,
    pair=ts.SizedVector(size=2),
    real3=ts.RealVector(size=3),
    positive3=ts.PositiveRealVector(size=3),
    mapping=ts.TypedAttribute(expected_type=dict),
    name=ts.ObjectName,
)
class Example:
    pass

Contracts for the Descriptors

Typed attributes in general
  • Values are validated by Typed using its configured expected_type.
  • TypedAttribute(expected_type=...) accepts any value for which isinstance(value, expected_type) holds and raises TypeError for all other values. The expected_type option is mandatory.
  • Real accepts real numbers; non-real values, complex numbers among them, are rejected with TypeError.
  • Int accepts integer values. A value that is not an integer, a float for example, raises TypeError; negative integers remain valid.
  • String accepts strings, and non-string values raise TypeError.
Scalars with sign constraints
  • UnsignedReal accepts real values that are greater than or equal to zero. Assigning a real value that is negative raises TypeError.
  • UnsignedInt accepts integer values that are greater than or equal to zero. Assigning a negative integer raises TypeError.
  • PositiveReal accepts only real values that are strictly greater than zero. Assigning zero, or a negative real value, raises TypeError.

The sign violations above belong to this API's type/constraint validation contract. They must not be reported as ValueError just because the assigned object is otherwise numeric.

Vectors and fixed sizes
  • Vector accepts non-scalar vector containers given as a list, tuple, or NumPy array. It places no constraint on the number or type of components. A scalar or a string does not qualify as an accepted vector and raises TypeError.
  • SizedVector(size=n) accepts the same vector container types as Vector but requires a vector of exactly n components. Both shorter vectors and longer vectors raise TypeError.
  • RealVector(size=n) requires an accepted vector container of exactly n components, every one of them a real number. A vector whose length is wrong raises TypeError. A vector of the correct length that contains a non-real component — a complex number, for example — also raises TypeError. For this descriptor, negative real components are valid.
  • PositiveRealVector(size=n) requires an accepted vector container of exactly n real components, all of them strictly greater than zero. A wrong length, a non-real component, or any component that is zero or negative raises TypeError.
  • A fixed-length integer-valued vector constraint requires exactly the number of components declared and requires every component to be an integer. A value with the wrong length, or a component of another type (a float, for instance), raises TypeError.

Even when the supplied object is otherwise an accepted vector container, a vector length mismatch is a validation/type mismatch for this API. It must therefore raise TypeError, not ValueError.

Object names

ObjectName accepts identifier-like strings that are used as object names. A valid name starts with a letter or underscore and contains no spaces; after the initial character, digits may appear. Examples of valid values include "exchange_energy_name" and "_new_name2".

Assigning a non-string, or an invalid name, raises TypeError. Invalid examples include a value that contains a space, such as "new name2", and a value that starts with a digit, such as "2newname2".

Errors Required on Configuration Omissions

Omitting configuration must fail immediately with TypeError:

  • TypedAttribute without expected_type raises TypeError, whether it is being constructed or installed.
  • SizedVector without size raises TypeError, whether it is being constructed or installed. The same required size contract applies to its fixed-size subclasses, such as RealVector and PositiveRealVector.

As a consequence, using a bare configuration-dependent class — @ts.typesystem(a=ts.SizedVector) or @ts.typesystem(a=ts.TypedAttribute), for instance — is invalid and raises TypeError while the decorated class is being created.

Assigning, Retrieving, and Deleting

A successful assignment must preserve the supplied value and make it available through ordinary instance attribute access. This holds both for values assigned inside an __init__ method and for later reassignments.

Controlled attributes cannot be deleted. An attempt to perform del instance.attribute on a descriptor-managed attribute raises AttributeError.

Summary of Exceptions

All of the following require TypeError:

  • assigning an object whose scalar type is wrong;
  • assigning a scalar or string when a vector is required;
  • assigning a vector whose fixed length is wrong;
  • assigning a fixed-length vector that has a component of the wrong type;
  • assigning a negative value to a scalar descriptor that is unsigned;
  • assigning zero, or a negative value, to a scalar descriptor that is strictly positive;
  • assigning a positive-real vector that contains a zero or negative component;
  • assigning an object name that is invalid; and
  • omitting a descriptor configuration option that is mandatory.

In particular, neither fixed-length mismatches nor the sign/range violations these descriptors cover may be changed to ValueError. Assigning conforming values succeeds silently.

ts.typesystem(**kwargs) returns a class decorator. Each keyword argument pairs an attribute name with a type descriptor (one of the descriptor kinds listed above). Usage pattern:

@ts.typesystem(a=ts.ConstantRealVector(size=3),

Parameter(descriptor=Scalar(), const=True) accepts an initial value such as {'r1': 1, 'r2': -3.14}; any subsequent assignment raises AttributeError.

Parameters with otherwise

With Parameter(descriptor=Scalar(), otherwise=tuple):

  • The wrapped descriptor accepts a scalar.
  • (1, 2, 3) is not a scalar; acceptance happens solely because it is a tuple. This does not make arbitrary scalar-valued vectors part of Scalar validation.
  • {'a': 1, 'b': 2} is accepted as a valid parameter dictionary.
  • 'string' raises TypeError.
  • {'a': 1, 'b': [1, 2, 3]} raises TypeError, because the list value fails scalar validation.
  • [1, 2, 3] raises TypeError, since it is neither a scalar, a valid parameter dictionary, nor a tuple.

The typesystem decorator and descriptor behavior shared by descriptors

ts.typesystem(**descriptors) is a decorator that associates each keyword name with its descriptor on the class it decorates. A declaration may be written with either a descriptor instance or a bare descriptor class, including forms such as:

@ts.typesystem(
    scalar=ts.Scalar,
    vector=ts.Vector(size=3),
    name=ts.Name,
)
class Config:
    def __init__(self, **kwargs):
        for key, value in kwargs.items():
            setattr(self, key, value)

Bare declarations such as ts.Scalar, ts.Vector, and ts.Name must behave the same as instances configured with their defaults.

Managed attributes are optional: constructing an object while leaving one of them unassigned must succeed, and that attribute may be assigned later. A value assigned successfully must be readable from the instance. Validation applies in the same way to assignments made in a class constructor and to assignments made later. When an assignment is rejected, it must not replace the value that was stored previously.

It is never allowed to delete a managed attribute. del instance.attribute must raise AttributeError, including when the attribute has never been assigned.

const=True is supported by descriptor classes. The first assignment to a constant attribute that succeeds is allowed, including an assignment made after the object is constructed. An assignment made after that is rejected with AttributeError. For ordinary descriptors, validation can come before constant-write protection: for example, assigning the scalar 0 to an already initialized constant Vector raises TypeError, since it is not a vector, whereas assigning another structurally valid vector raises AttributeError.

ts.Typed

Values are accepted by ts.Typed(expected_type=..., const=...) in accordance with isinstance(value, expected_type).

  • A value that matches is stored unchanged.
  • A value that does not match raises TypeError.
  • When const=True is used, an attribute that has been initialized cannot be reassigned.

Support must be provided for types and abstract base classes such as int, str, list, and numbers.Real.

ts.Scalar

It must be possible to use Scalar as a bare declaration (ts.Scalar), as ts.Scalar(), or with the keyword options expected_type, positive, unsigned, const, and otherwise.

The normal scalar route of Scalar accepts values that satisfy isinstance(value, numbers.Real) and stores them unchanged. That route is refined by the options as follows:

  • expected_type=T additionally requires that isinstance(value, T) hold. A failure raises TypeError.
  • With positive=True, value > 0 is required; values that are zero or negative raise ValueError. positive=False imposes no positivity constraint.
  • With unsigned=True, value >= 0 is required; negative values raise ValueError. unsigned=False imposes no unsigned constraint.
  • otherwise=T adds an alternative route: any value that satisfies isinstance(value, T) is accepted unchanged and does not have to satisfy the normal scalar constraints. As an example, ts.Scalar(otherwise=tuple) accepts both ordinary real scalars and tuples.

Type validation takes place before sign validation. For example, with ts.Scalar(expected_type=float, unsigned=True), assigning the integer -1 raises TypeError rather than the sign-related ValueError. A value that is not real and does not match otherwise also raises TypeError.

ts.Vector

It must be possible to use Vector as a bare declaration (ts.Vector), as ts.Vector(), or with the keyword options size, component_type, positive, unsigned, const, and otherwise.

The normal vector route accepts values of type list, tuple, or numpy.ndarray whose components are real numbers. Accepted values keep their original container type and contents; they are not converted to another vector representation. The externally observable behavior of validation is the following:

  • If the value is not a list, tuple, or NumPy array, TypeError is raised.
  • If any component is not a numbers.Real, TypeError is raised. In particular, assigning ["a", 1, 3] raises TypeError, not ValueError.
  • size=n requires exactly n components. When the length is wrong, ValueError is raised.
  • component_type=T requires every component to satisfy isinstance(component, T). A component that is real but of the wrong configured type raises TypeError.
  • With positive=True, every component is required to be greater than zero; a violation raises ValueError. positive=False disables this constraint.
  • With unsigned=True, every component is required to be greater than or equal to zero; a violation raises ValueError. unsigned=False disables this constraint.
  • otherwise=T adds an alternative accepted type that bypasses the normal vector validation. For example, ts.Vector(size=3, otherwise=float) accepts either a valid three-component vector or a float, storing either one unchanged. A value that is an int or a string and matches neither route raises TypeError.

The checks on container and component kind happen before the checks for configured size, component type, and sign.

ts.Name

Name must be exported, and it must be usable either as ts.Name, as ts.Name(), or with const=True. It accepts strings that:

  • start with a letter or underscore; and
  • have no spaces in them.

The characters coming after the valid initial character are not restricted to Python identifier characters. In particular, names like "a1", "var_name", and "var-name" are valid.

A value that is not a string raises TypeError. A string that begins with a digit or hyphen, or a string that contains a space, raises ValueError. Names that are accepted are stored unchanged.

ts.InSet

A value is accepted by ts.InSet(allowed_values=..., const=...) when it is a member of allowed_values, and it is stored unchanged. When the value is not a member, ValueError is raised. If the descriptor is constant, an attempt to reassign after successful initialization raises AttributeError.

ts.Subset

It is required by ts.Subset(sample_set=..., const=...) that the assigned value be iterable and that every distinct element in it belong to sample_set.

  • An iterable that is empty is valid.
  • Elements that repeat are valid.
  • When the assignment succeeds, the attribute stores a set that contains the distinct elements of the assigned value.
  • A value that is not iterable raises TypeError.
  • An iterable that contains an element outside sample_set raises ValueError.
  • If the descriptor is constant, reassignment after successful initialization raises AttributeError.

For example, with sample_set="xyz", each of [], "x", "yx", and "yxzz" is valid, whereas "a" and [1] raise ValueError.

ts.Parameter

The keyword options descriptor, const, and otherwise are supported by Parameter. The descriptor option may be omitted at construction time, so all of the following declarations must be valid:

ts.Parameter()
ts.Parameter(descriptor=ts.Scalar())
ts.Parameter(descriptor=ts.Vector(size=3))
ts.Parameter(descriptor=ts.Scalar(), otherwise=tuple)

A Parameter(descriptor=d) that has been configured accepts either:

  1. a single value that is accepted by d; or
  2. a non-empty dictionary whose keys satisfy Name and each of whose values is accepted by d.

A scalar, vector, fallback value, or dictionary, once accepted, is stored in its original form. Dictionary keys must therefore be strings that begin with a letter or underscore and contain no spaces. String keys that are malformed raise ValueError, and keys that are not strings raise TypeError. A dictionary that is empty raises ValueError. Errors originating from wrapped value validation retain their descriptor-specific class: type failures raise TypeError, while value or constraint failures raise ValueError. If any key or value is invalid, a parameter value stored previously remains unchanged.

otherwise=T adds an alternative accepted type via isinstance. A fallback value that matches is accepted unchanged, without validation by the wrapped descriptor. For example, ts.Parameter(descriptor=ts.Scalar(), otherwise=tuple) accepts tuples, scalar values, and non-empty dictionaries mapping names to scalars, but does not thereby accept lists or dictionaries with non-scalar values.

A ts.Parameter() created without a descriptor must be accepted by ts.typesystem; the absence of descriptor does not constitute a construction-time error. If (0, 0, 1) is assigned to an attribute backed by that unconfigured parameter, the assignment must raise AttributeError, including when it occurs while a constructor keyword argument is being handled.

After a Parameter(const=True) has been successfully initialized once, any later assignment must raise AttributeError.

ts.Dictionary

The public Dictionary descriptor must be added and exported. At least the following constructor forms must be supported:

ts.Dictionary(
    key_descriptor=ts.Name(),
    value_descriptor=ts.Scalar(),
)

ts.Dictionary(
    value_descriptor=ts.Scalar(),
)

It must be usable as a descriptor that is supplied to ts.typesystem. A value assigned must be a non-empty dictionary; values that are not dictionaries raise TypeError, and an empty dictionary raises ValueError. When both descriptors have been configured, every key is validated by key_descriptor and every value by value_descriptor, and a dictionary that is valid is stored as the attribute value.

For the concrete configuration with Name keys and Scalar values:

  • the assignment of {"a": 1, "b": -3} succeeds;
  • reassigning the attribute to {"a": 15, "b": -51} succeeds, and reading the attribute returns a dictionary equal to that value;
  • the assignment of 5 raises TypeError; and
  • the assignment of {} raises ValueError.

The construction of ts.Dictionary(value_descriptor=ts.Scalar()) without a key descriptor must itself succeed. Assigning {"a": 15, "b": -51} through a descriptor configured so incompletely must raise AttributeError.
