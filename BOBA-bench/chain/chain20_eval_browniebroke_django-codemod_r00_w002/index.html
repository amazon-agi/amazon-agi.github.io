Overview

  2. Refactor the CLI so that command execution is exposed through importable helper functions.

Part 1: Admin Inline has_add_permission Transformer

Existing behavior context

There is a libCST transformer that operates on classes derived from Django admin inline base classes (admin.TabularInline and admin.StackedInline, imported from django.contrib). Within such inline classes, it updates the method:

def has_add_permission(self, request):

by adding a second parameter so the signature becomes:

def has_add_permission(self, request, obj = None):

This applies whether the inline base class is the sole base, one of several bases, or combined with mixins/other bases. It must not apply to classes that do not derive from a recognized admin inline base class (e.g. admin.ModelAdmin or an unrelated class).

The transformer must also correctly manage its per-class state so that entering and leaving one class does not affect the handling of a subsequent, unrelated class in the same module.

New required behavior

In addition to rewriting the method signature, the transformer must rewrite any super().has_add_permission(request) call inside the body of the targeted has_add_permission method so that it forwards the new parameter:

  • super().has_add_permission(request) → super().has_add_permission(request, obj = obj)

This rewrite applies only within inline classes that qualify for the signature change (the same set of classes described above). The rewrite must occur regardless of surrounding statements in the method body (for example, when the super() call appears after conditional logic and other return statements).

For classes that do not qualify (non-inline base classes), neither the signature nor any super().has_add_permission(...) call inside the method body may be modified — the code must be left byte-for-byte unchanged.

The state-clearing requirement above must hold for both recognized inline base classes.

Part 2: CLI Command Execution Helpers

Module: django_codemod.cli

Expose two importable, callable functions at module level:

build_command(codemodders_list)

  • Returns a command instance object suitable for passing to call_command.
  • Must be callable with an empty list and return a usable instance.
call_command(command_instance, path)

Executes the given command over the files found at path.

Behavior:

  1. It gathers the files to process from path. File gathering is performed by a module-level callable named gather_files (accessible as django_codemod.cli.gather_files) that returns a list of file paths.
  2. It runs the transformation by invoking a module-level callable named parallel_exec_transform_with_prettyprint (accessible as django_codemod.cli.parallel_exec_transform_with_prettyprint). This callable returns a result object exposing integer attributes successes, failures, warnings, and skips.
  3. Outcome handling based on the returned result:
    • If failures is 0, the function completes normally and returns None.
    • If failures is greater than 0, the function must terminate the command via a Click exit (raising click.exceptions.Exit).
  4. If invoking parallel_exec_transform_with_prettyprint raises KeyboardInterrupt, call_command must convert it into a Click abort (raising click.Abort).
