Overview

You will be working on a Python codebase (django_codemod) that offers a command-line codemod tool for updating Django code. The task comes in two independent parts:

  1. Extend a transformer based on libCST that fixes calls to a base class method inside admin inline classes.
  2. Refactor the CLI so that command execution is exposed via importable helper functions.

Part 1: has_add_permission Transformer for Admin Inline Classes

Context on the existing behavior

The codebase already contains a libCST transformer that works on classes derived from Django admin inline base classes (admin.TabularInline and admin.StackedInline, imported from django.contrib). Inside those inline classes, it modifies the method:

def has_add_permission(self, request):

by adding a second parameter so that the signature becomes:

def has_add_permission(self, request, obj = None):

The change applies whether the inline base class is the only base, one of multiple bases, or used in combination with mixins/other bases. It must not be applied to classes that do not derive from a recognized admin inline base class (e.g. admin.ModelAdmin or an unrelated class).

The transformer must also manage its per-class state correctly, so that entering and leaving one class does not affect how a subsequent, unrelated class in the same module is handled.

Required new behavior

Besides rewriting the method signature, the transformer must rewrite any super().has_add_permission(request) call within the body of the targeted has_add_permission method so that it forwards the new parameter:

  • super().has_add_permission(request) → super().has_add_permission(request, obj = obj)

Only inline classes that qualify for the signature change (the same set of classes described above) are subject to this rewrite. The rewrite must happen regardless of the statements around it in the method body (for example, when the super() call appears after conditional logic and other return statements).

When a class does not qualify (non-inline base classes), neither the signature nor any super().has_add_permission(...) call inside the method body may be modified — the code must be left byte-for-byte unchanged.

For both recognized inline base classes, the state-clearing requirement above must hold.

Part 2: Helpers for CLI Command Execution

The module to work in is django_codemod.cli.

Two importable, callable functions must be exposed at module level:

build_command(codemodders_list)
  • Accepts a list of codemod/transformer specifications (which may be empty).
  • Returns a command instance object that can be passed to call_command.
  • Must be callable with an empty list and return an instance that is usable.
call_command(command_instance, path)

Runs the given command over the files found at path.

Behavior:

  1. The files to process are gathered from path. The gathering is done by a module-level callable named gather_files (accessible as django_codemod.cli.gather_files) that returns a list of file paths.
  2. The transformation is run by invoking a module-level callable named parallel_exec_transform_with_prettyprint (accessible as django_codemod.cli.parallel_exec_transform_with_prettyprint). This callable returns a result object that exposes the integer attributes successes, failures, warnings, and skips.
  3. How the outcome is handled depends on the returned result:
    • If failures is 0, the function finishes normally and returns None.
    • If failures is greater than 0, the function must terminate the command via a Click exit (raising click.exceptions.Exit).
  4. If invoking parallel_exec_transform_with_prettyprint raises KeyboardInterrupt, call_command must turn it into a Click abort (raising click.Abort).

The existing top-level Click command (djcodemod) must keep working as before, with call_command used internally to perform its execution step.

  • Both gather_files and parallel_exec_transform_with_prettyprint must be referenced via module-level names so that they can be replaced at runtime.

As a result, later transformers observe the output produced by earlier transformers, and all transformers share the context that was supplied, including any context state or deferred import work used by the existing visitors. The command must keep taking part in the normal libcst codemod lifecycle so that it can be executed against Python source files and all supported follow-up transformations are completed.

This takes the place of the former constructor convention, in which the context was the first argument and transformer classes were fixed on a subclass.

django_codemod.cli

The cli module must keep exposing:

  • djcodemod — the Click command serving as the CLI entry point.
  • call_command — the callable used to execute a command instance against a path.
  • DEPRECATED_IN — the mapping used to select transformer classes based on the Django version in which behavior was deprecated.
  • REMOVED_IN — the mapping used to select transformer classes based on the Django version in which behavior was removed.

The values of these mappings remain ordered lists of transformer classes. The supported versions and the transformer membership that exist today must not change.

The build_command helper that existed previously is no longer part of the public API and must not be relied upon. Once a transformer-class list has been selected, the CLI must construct the command directly via BaseCodemodCommand(transformers, context) with a suitable CodemodContext, and pass that command to call_command.

Command-Line Interface and Validation

The command accepts a target path plus exactly one version-selection option:

  • --removed-in <version>
  • --deprecated-in <version>

Invocation pattern:

djcodemod <option> <version> <path>

Sample invocations:

djcodemod --deprecated-in 2.0 .
djcodemod --removed-in 3.0 my_app

The Click interface and validation behavior as they exist must be preserved:

  • PATH is required.
  • Exactly one of --removed-in and --deprecated-in is required; providing neither or both is a usage error.
  • Versions require numeric major and minor components, such as 2.2; a patch component may be supplied and does not alter selection by major/minor version.
  • A well-formed version with no entry in the selected mapping is rejected as unsupported.
  • Malformed versions, and versions that are missing required components, are rejected as usage errors.
  • --help stays available.

Do not alter the supported options, the supported version sets, or their validation behavior.

Processing Files and Reporting Results

When the invocation is valid and its path resolves to Python source files, the CLI must operate on the actual filesystem and must:

  1. Find every .py file that is reachable under the target directory.

  2. Limit discovery to the requested path: . processes the current directory tree, while a named directory such as my_app processes the tree of that directory.

  3. Run the selected transformer classes through the constructed BaseCodemodCommand.

  4. Write the resulting transformations through the normal libcst execution machinery.

  5. Exit with status code 0 once processing has completed without failures.

  6. Print a completion line in exactly the following form:

    Finished codemodding N files!

    In this line, N is the total number of files processed, including successful transformations, skips, and failures reported by the executor. As an example, processing three Python files must produce a line containing Finished codemodding 3 files!.

File discovery and counting must work both for the current directory and for a named subdirectory, including Python files nested within the selected directory tree. The count must reflect the real files discovered on disk rather than a count that is assumed or mocked.

call_command(command_instance, path) must keep its existing execution behavior: it collects the files from the supplied path, executes the command, prints the completion and detailed result summary, and returns None if there are no failures. If one or more files fail, it must terminate with exit status 1 after the result has been reported. An execution that gets interrupted must be surfaced as a Click abort.

Compatibility Constraints and Non-Goals

  • All existing visitor behavior must be preserved; what this task changes is how transformer classes are supplied and run, not what the individual visitors transform.
  • The existing ordering and the contents of DEPRECATED_IN and REMOVED_IN must be preserved.
  • The libcst integration must be preserved, including the processing of real source files and any import updates scheduled by transformers.
  • Do not reintroduce a requirement that BaseCodemodCommand be subclassed merely in order to choose transformers.
  • Do not treat the transformer entries given to the constructor as objects that were instantiated ahead of time.
  • Do not change the CLI option names, version validation, path scope, success/failure handling, or summary wording beyond the requirements above.
