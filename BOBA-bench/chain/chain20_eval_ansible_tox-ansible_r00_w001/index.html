Task Specification: Molecule Scenario Discovery for tox-ansible

Overview

Refactor tox-ansible so that Molecule scenarios are discovered solely from molecule.yml files. Discovery must not depend on whether a directory is an Ansible role, an Ansible collection, or an otherwise unclassified project. A collection marker such as galaxy.yml, a role marker such as tasks/main.yml, and the presence of a roles/ directory have no bearing on eligibility.

The role concept is removed from the plugin's public model. There is no public Role or Collection abstraction, no role argument on scenario cases, and no role-based filtering.

Discovery

Starting at the current working directory, recursively find every file matching:

**/molecule/*/molecule.yml

The parent directory of each matching file is one scenario directory, and every matching file produces exactly one Scenario. Thus both project-root scenarios such as molecule/default/molecule.yml and deeply nested scenarios such as roles/example/molecule/default/molecule.yml are discovered. A project need not otherwise look like an Ansible project.

Only this layout is a discovery match: the configuration file must be directly inside one scenario directory, and that scenario directory must be directly inside a directory named molecule.

Ignored paths

The [ansible] configuration supports an ignore_path list. A candidate under any configured ignored path or matching ignored path segment must be omitted from discovery. For example:

[ansible]
ignore_path =
    ignored

excludes ignored/molecule/not_found/molecule.yml. Ignoring applies before scenarios and generated environments are created.

Path-derived working directories and environment identifiers

For a scenario directory, remove its final molecule/<scenario-directory-basename> portion. The remaining path is that scenario's working directory. For discovered scenarios, generated identifiers use paths relative to the discovery root.

Examples:

Scenario directory Working directory
molecule/s1 ""
something/roles/r1/molecule/s2 something/roles/r1
roles/r2/molecule/s3 roles/r2

The unexpanded tox environment identifier consists of the nonempty working-directory path components followed by the basename of the scenario directory, joined with -. Platform path separators are therefore represented as - in the identifier:

Scenario directory Environment identifier
molecule/one one
roles/complex/molecule/default roles-complex-default
roles/complex/molecule/openstack roles-complex-openstack
roles/simple/molecule/default roles-simple-default

The filesystem basename is deliberately distinct from Scenario.name. If roles/complex/molecule/name_mismatch/molecule.yml declares scenario.name: real_name, then:

  • Scenario.name and str(scenario) are real_name;
  • Molecule commands and scenario filters use real_name;
  • the generated environment identifier remains roles-complex-name_mismatch.

In particular, a YAML name override must never rename the generated tox environment.

Public API

tox_ansible.ansible.scenario.Scenario

Constructor:

Scenario(directory)

directory is the scenario directory, normally the directory directly containing molecule.yml.

Required behavior:

  • directory identifies the supplied scenario path, and the corresponding configuration path is <directory>/molecule.yml.
  • config reads and parses that YAML file. An empty file is valid and is treated as no configuration.
  • A Scenario may also be constructed for a path whose molecule.yml does not exist. A missing file is treated as no configuration for scenario introspection: it must not make name, driver, str(scenario), or command generation fail.
  • name defaults to the basename of directory. If the parsed YAML has a top-level scenario mapping containing name, that value overrides the default.
  • driver is the value of top-level driver.name, or None when it is absent, the file is empty, or the file does not exist.
  • str(scenario) returns the same value as scenario.name.
  • Existing per-scenario requirements behavior remains available: if <directory>/requirements.txt exists, it can be exposed as that scenario's requirements file and included by its scenario case; otherwise there is no scenario requirements file.

Examples:

  • .../default/molecule.yml containing driver:\n name: openstack gives name == "default", str(scenario) == "default", and driver == "openstack".
  • .../surprise/molecule.yml containing driver:\n name: surprise gives name == "surprise", str(scenario) == "surprise", and driver == "surprise".
  • Scenario("molecule/s1") gives name == "s1" and driver is None even when that path and its YAML file do not exist.

[
    "molecule",
    "ansible-lint",
    "yamllint",
    "flake8",
    "pytest",
    "testinfra",
]

The Ansible dependency follows those six entries:

  • an unexpanded case appends "ansible";
  • a case expanded to Ansible version <version> appends "ansible==<version>.*" instead.

Consequently, a basic unexpanded case with no driver-specific or scenario-specific requirements returns exactly:

[
    "molecule",
    "ansible-lint",
    "yamllint",
    "flake8",
    "pytest",
    "testinfra",
    "ansible",
]

  • docker adds docker;
  • openstack includes openstacksdk (and retains its existing Molecule/OpenStack support dependencies);
  • existing ec2 support dependencies remain supported;
  • podman requires no additional dependency.

If the scenario has a requirements.txt, its -r<path> dependency is included after the built-in dependencies. Dependency calculation must not accumulate duplicate entries merely because get_dependencies() is called more than once.

Commands

get_commands(options) returns a list containing exactly one command argv list. That argv list is formed, in order, from:

  1. the literal "molecule";
  2. every entry of options.get_global_opts(), preserving the supplied order, immediately after molecule;
  3. the literals "test", "-s", and the scenario's name (so a YAML scenario.name override is honored here);
  4. any tox positional arguments, appended after the scenario name.

With no global options and no positional arguments, the result is exactly:

[["molecule", "test", "-s", scenario.name]]

With global options ["-c", "derp"] and no positional arguments, the result is exactly:

[["molecule", "-c", "derp", "test", "-s", scenario.name]]
Matrix expansion factors
  • An unexpanded case has get_basepython() returning None.
  • expand_ansible(version) returns a new case, leaves the source case usable, sets the new case's ansible attribute to version, and prepends ansible<version-with-dots-removed>- to its name. For "2.7", the prefix is ansible27-. An Ansible-only expansion has get_basepython() is None.
  • expand_python(version) returns a new case, sets its python attribute to version, and prepends py<version-with-dots-removed>- to its name. Its get_basepython() is "python<version>"; for "4.1", this is "python4.1".
  • Expansions compose, and each new factor is prepended to existing factors. Expanding Python 4.1 and then Ansible 1.0 produces ansible10-py41-my_test.
tox_ansible.tox_lint_case.ToxLintCase

Constructor:

ToxLintCase(cases)

Each usable entry in cases is only guaranteed to expose a scenario attribute. It need not be a ToxTestCase and need not provide get_working_dir(), role, or any other case API.

Required behavior:

  • get_name() returns "lint_all" before expansion.
  • get_working_dir() returns "{toxinidir}".
  • get_dependencies() returns exactly the set {"molecule", "ansible-lint", "flake8", "yamllint"}.
  • expand_python("2.7") returns a lint case named "py27-lint_all".
  • expand_ansible("2.10") returns a lint case named "ansible210-lint_all".

get_commands(options) emits one command for every entry that exposes a scenario, preserving case order. Entries without a scenario, including nested lint cases, are skipped. For each usable entry it must:

  1. derive the target directory directly from entry.scenario.directory using the working-directory rule above;
  2. use entry.scenario.name as the Molecule scenario name; and
  3. join options.get_global_opts() with spaces for the shell command.

It must not delegate working-directory calculation to the entry or require any role-related attribute. The command shape is exactly:

[
    "bash",
    "-c",
    "cd {directory} && molecule {joined_global_options} lint -s {scenario.name}",
]

The placeholders remain in that layout when a value is empty. For example, no global options produce molecule lint with the two spaces resulting from the empty option string. Path-only scenarios with no on-disk molecule.yml must still produce commands successfully.

For no global options, representative results are:

[
    ["bash", "-c", "cd  && molecule  lint -s s1"],
    ["bash", "-c", "cd something/roles/r1 && molecule  lint -s s2"],
    ["bash", "-c", "cd roles/r2 && molecule  lint -s s3"],
]

for scenarios at molecule/s1, something/roles/r1/molecule/s2, and roles/r2/molecule/s3, respectively.

Matrix behavior

The existing Ansible and Python matrix configuration remains supported:

  • with no axes, expansion leaves the case list unchanged;
  • an Ansible axis calls expand_ansible(version) for each configured version and case;
  • a Python axis calls expand_python(version) for each configured version and case;
  • multiple axes form the Cartesian product and apply to both scenario and lint cases.

Configuration installs the Ansible axis before the Python axis. Since each expansion prepends its factor, configuring Ansible 2.8 2.9 and Python 2.7 3.8 yields names such as py27-ansible28-roles-simple-default and py27-ansible28-lint_all, rather than retaining bare generated cases.

Filtering and options

Available filters

tox_ansible.filter.Filter accepts an options object that is guaranteed to expose only the relevant scenario and driver lists. It must not read or require a role option. It applies scenario and driver filtering to an environment dictionary whose values may expose value.tox_case.scenario.

  • An empty filter list does not restrict the input.
  • A nonempty scenario list keeps only entries whose tox_case.scenario.name is in that list.
  • A nonempty driver list keeps only entries whose tox_case.scenario.driver is in that list.
  • If both lists are nonempty, both restrictions apply.
  • An entry lacking tox_case.scenario cannot match an active scenario or driver filter and is removed. Thus an active scenario/driver filter does not retain the aggregate lint environment or unrelated preconfigured environments.

Scenario filtering uses Scenario.name, including a YAML override, rather than the scenario directory basename used in the environment identifier. A filter for default keeps every matching default scenario across all path locations. It must not accidentally filter those scenarios by their former role location.

The standalone ByScenario and ByDriver filters retain the same matching behavior.

tox_ansible.options.Options
  • do_filter() is True when either scenario or driver is nonempty, and False when both are empty.
  • It must not consider a role attribute, even if an external caller happens to attach one.
  • expand_matrix(cases) delegates to the configured matrix and returns its expansion.
  • get_global_opts() returns the configured Molecule global options in order.

The supported selectors remain:

  • --ansible-scenario, with environment equivalent TOX_ANSIBLE_SCENARIO;
  • --ansible-driver, with environment equivalent TOX_ANSIBLE_DRIVER.

Selected values may be supplied through those interfaces using the plugin's existing list/comma-separated option behavior.

There is no role selector or role filtering path.

Configuration and tox integration

The plugin reads the [ansible] section and continues to support:

  • ansible: Ansible versions for matrix expansion;
  • python: Python versions for matrix expansion;
  • molecule_opts: ordered global arguments inserted into Molecule invocations;
  • ignore_path: paths or path segments excluded from scenario discovery.

For every discovered scenario, the plugin creates its path-derived scenario environment. It also creates one logical lint_all case before any matrix expansion. Existing explicitly configured tox environments remain available alongside generated environments. Generated cases participate in configured matrix expansion.

Default environment list ordering

After generated environments are merged with existing configured environments, and after any active scenario/driver selector filtering is applied, the final default tox environment list must be sorted lexicographically by environment name. This sorted order is what a default listing displays, and it determines the placement of lint_all, preconfigured environments, and matrix-expanded environments alike. Merging must also not produce duplicate environment names.

Representative discovery without a matrix:

molecule/one/molecule.yml                                      -> one
molecule/two/molecule.yml                                      -> two
roles/complex/molecule/default/molecule.yml                     -> roles-complex-default
roles/complex/molecule/openstack/molecule.yml                   -> roles-complex-openstack
roles/complex/molecule/name_mismatch/molecule.yml               -> roles-complex-name_mismatch
roles/simple/molecule/default/molecule.yml                      -> roles-simple-default
                                                               + lint_all

The resulting default list for that project, in its required lexicographic order, is:

lint_all
one
roles-complex-default
roles-complex-name_mismatch
roles-complex-openstack
roles-simple-default
two

Likewise, a project with a preconfigured derp environment plus a roles/simple/molecule/default scenario expanded over Ansible 2.8 2.9 and Python 2.7 3.8 lists derp first, followed by the py27-ansible28-... through py38-ansible29-... generated environments in lexicographic order.

The same root-level molecule/one and molecule/two environments must be generated in a plain directory with no galaxy.yml or role structure.

Removed surface and non-goals

The following are no longer importable public APIs:

  • tox_ansible.ansible.role.Role;
  • tox_ansible.ansible.collection.Collection;
  • tox_ansible.filter.by_role.ByRole.

The --ansible-role command behavior and role-based environment-variable selection are removed. Filter, Options.do_filter(), generated case names, descriptions, commands, and constructors must not rely on a role. In particular, ToxTestCase accepts only its scenario.

Do not replace role recognition with collection recognition or any other project-type classification. Filesystem location is used only to find molecule/*/molecule.yml, derive working directories, and create unambiguous path-based tox environment identifiers.
