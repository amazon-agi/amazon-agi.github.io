Task Specification: Streamline the Parser API and Link Contexts to Parser Stacks

Summary

Packet parsing is to be simplified so that one parse call performs the parsing. There is no separately exposed matching step, and a direction argument is not taken by packet-level parsing. Furthermore, a SCHC Context must identify the protocol-stack parser linked to that context and must preserve that identifier through JSON serialization and deserialization.

1. Eliminate the parser match API

The match method must no longer be exposed by parser objects. The classes concerned are:

  • HeaderParser and PacketParser from microschc.parser / microschc.parser.parser;
  • CoAPParser from microschc.parser.protocol.coap;
  • IPv4Parser from microschc.parser.protocol.ipv4;
  • IPv6Parser from microschc.parser.protocol.ipv6; and
  • UDPParser from microschc.parser.protocol.udp.

Through inheritance, a match method must not remain available. Parsing valid input must not require a preliminary validation or matching call, and a replacement matching entry point is not required.

2. API for protocol parsers

Each protocol parser must expose the following public method:

def parse(self, buffer: Buffer) -> HeaderDescriptor

The method must be callable with the single keyword argument buffer, the value of which is a microschc.binary.buffer.Buffer. A HeaderDescriptor for the parsed protocol header must be returned.

For buffers that are valid, the existing parsing results must stay unchanged, including:

  • the identifier of the header and the parsed header length;
  • the number of fields and their order; and
  • for every field, the identifier, the Buffer value and bit length, and the position.

A direction argument may not be required by the public parse method of any protocol parser.

3. API for the packet parser

PacketParser must expose the following method:

def parse(self, buffer: Buffer) -> PacketDescriptor

It must be callable in the following form:

packet_descriptor = packet_parser.parse(buffer=packet_buffer)

The only parse argument after self is buffer; callers must neither supply a direction nor carry out a separate match operation. Only the parser call chain is affected by this change; beyond that, the existing direction-related data types or APIs used elsewhere in the package are not removed.

The existing packet parsing behavior must be preserved by the returned PacketDescriptor:

  • The protocol headers are parsed according to the order configured for the packet parser.
  • fields is the flattened concatenation of the fields of the protocol headers, in protocol and field order.
  • Each flattened field preserves the id, value, and position that its protocol parser produced.
  • Field values continue to be Buffer instances with the same contents and bit lengths as before.
  • payload is whatever remains unconsumed after all configured protocol headers have been parsed.
  • length continues to be the bit length of the original packet buffer.
  • The object that is returned is still a PacketDescriptor.

Complete IPv6/UDP/CoAP packets, including both of these edge cases, must be handled successfully by the parser without raising an exception:

  1. a CoAP message that contains zero options; and
  2. a CoAP message that contains options but no payload, and that therefore ends without a payload marker or payload bytes.

An absent payload is represented in a manner consistent with the existing Buffer-based packet output.

4. Compatibility of the parser factory

The protocol-stack registry API stays available from microschc.parser.protocol.registry. In particular, the existing Stack members and the factory call must keep working, including:

packet_parser = factory(stack_id=Stack.IPV6_UDP_COAP)
packet_descriptor = packet_parser.parse(buffer=packet_buffer)

The factory must continue to return a PacketParser that is configured with the protocol parsers for the requested stack. The stacks that are already registered, including IPv6/UDP/CoAP and IPv4/UDP/CoAP, must retain their identifiers and parser ordering.

5. Context.parser_id

The parser stack associated with the context must be included in the Context data model in microschc.rfc8724. The construction contract is:

Context(
    id: str,
    description: str,
    interface_id: str,
    parser_id: Stack,
    ruleset: List[RuleDescriptor],
)

parser_id must:

  • be accepted when passed as a keyword argument;
  • accept a Stack member from microschc.parser.protocol.registry, such as Stack.IPV6_UDP_COAP; and
  • be exposed, unaltered, as the public context.parser_id attribute.

As an example:

context = Context(
    id="example",
    description="Example context",
    interface_id="eth0",
    parser_id=Stack.IPV6_UDP_COAP,
    ruleset=[],
)

assert context.parser_id == Stack.IPV6_UDP_COAP

All existing Context attributes and the ruleset behavior remain available. The addition of parser_id must not modify the representation or the round-trip behavior of the rules in ruleset.

6. JSON serialization of contexts

The serialized JSON object produced by Context.json(indent=None, separators=None) must include parser_id. Its value must be the string value of the selected Stack member and not its enum member name. By way of example, Stack.IPV6_UDP_COAP is serialized as "IPv6-UDP-CoAP", while Stack.IPV4_UDP_COAP is serialized as "IPv4-UDP-CoAP".

The top-level keys must be ordered as follows:

  1. id
  2. description
  3. interface_id
  4. parser_id
  5. ruleset

Hence, under default JSON formatting, the example context above serializes as:

{"id": "example", "description": "Example context", "interface_id": "eth0", "parser_id": "IPv6-UDP-CoAP", "ruleset": []}

The existing handling of indent and separators must continue to apply, and apart from the addition of parser_id the representations of all pre-existing context and rule fields must remain unchanged.

7. JSON deserialization of contexts

The parser_id string must be read by Context.from_json(json_str=...), and the corresponding Stack enum member must be restored. For instance, when "parser_id": "IPv6-UDP-CoAP" is deserialized, the result must be a context for which:

context.parser_id == Stack.IPV6_UDP_COAP

The other context fields and the nested RuleDescriptor objects must keep deserializing as before. When a context is serialized with Context.json(), a round trip must preserve its parser identifier as a Stack member.

Scope and Compatibility

  • All existing descriptor classes, protocol field identifiers, valid-buffer parsing values, bit lengths, positions, payload behavior, and registered stack values must be preserved, except where the parser signatures are explicitly changed above.
  • match must not be exposed on parser classes.
  • A direction parameter must not be exposed on the public parser parse methods described above.
  • Unrelated JSON formats and SCHC compression, decompression, matching-operator, and rule behavior must not be changed.
  • This task does not expand the behavior for malformed or unsupported protocol input; the required parsing compatibility is applicable to valid supported packets.

Description of the Task

Summary

microSCHC is to be updated so that the selection of a rule for a packet is exposed as an iterator and so that SCHC compression/decompression acts on one contiguous bit stream. Which rules match must not be altered by the return-type change. When the destination is empty, buffer concatenation must in addition keep the destination's bit orientation intact, so that compressed and reconstructed packets place their bits correctly.

Public API in Scope

The interfaces affected are:

  • Ruler(rules_descriptors=[...])
  • Ruler.match_packet_descriptor(self, packet_descriptor)
  • Buffer(content=..., length=..., padding=...) and Buffer.__add__ (which += also uses)
  • compress(packet_descriptor=..., rule_descriptor=...) -> Buffer
  • decompress(schc_packet=..., rule_descriptor=...) -> Buffer

Types already present that are relevant include RuleDescriptor, RuleFieldDescriptor, FieldDescriptor, PacketDescriptor, MatchMapping, Padding, MatchingOperator, and CompressionDecompressionAction.

Bit-Sequence Semantics of Buffer

A Buffer consists of exactly length significant bits. Any bits found in content beyond that logical sequence are padding and form no part of the value:

  • Under Padding.LEFT, the unused bits are placed before the significant bits; a two-bit value 11 can therefore be encoded as content=b'\x03'.
  • Under Padding.RIGHT, the unused bits come after the significant bits; content=b'\xc0' is how the same two-bit value is represented.

Whenever buffers are combined, the combination must work on their logical significant-bit sequences rather than on their raw padded byte strings.

Concatenation of Buffers

Given left + right:

  1. The result's logical bits start with all the significant bits of left, and all the significant bits of right come immediately after them.
  2. As its length, the result gets left.length + right.length.
  3. Between the two sequences, no operand padding and no byte-alignment gap may be inserted.
  4. Should the operands differ in padding orientation, their significant bits must be realigned as needed.
  5. The result adopts the left operand's padding mode.
  6. The concatenation modifies neither operand.

This rule about the left operand's padding mode likewise holds when left.length == 0. With an empty left operand, the right operand must not simply be passed through with the right operand's original padding mode. As an example:

left = Buffer(content=b'', length=0, padding=Padding.RIGHT)
right = Buffer(content=b'\x03', length=2, padding=Padding.LEFT)
combined = left + right

Here combined must come out with length == 2, padding == Padding.RIGHT, content == b'\xc0', and logical bits 11. For accumulators that are initialized as empty right-padded buffers, this behavior is required.

Ruler.match_packet_descriptor

What Gets Returned

An iterator is what match_packet_descriptor(packet_descriptor=...) must return — not a RuleDescriptor directly, and not a materialized collection either. The object that comes back must implement the iterator protocol and support next(...).

As the iterator is advanced, it yields the RuleDescriptor objects that match. The sequence in which matching rules are yielded must follow the order in which they were supplied via rules_descriptors. Code that previously took the first match from the direct return value must therefore now read:

matching_rule = next(ruler.match_packet_descriptor(
    packet_descriptor=packet_descriptor
))

What comes out first in this fashion must be the same rule that the previous API returned directly, the same id included. When multiple rules match, construction order decides the sequence of production. After all matching rules have been consumed, the usual iterator-exhaustion behavior applies.

When no rule matches, the existing RuleDescriptorMatchError behavior on advancing the iterator must be preserved. The higher-level operations already in place that require one rule must consume the first item from the returned iterator, so that their externally visible behavior stays compatible.

How Matching Behaves

Rule eligibility and rule ordering must not be changed by the return-type switch. The matching behavior already in place must be preserved:

  • A rule field applies to the packet only when the field's direction is the packet direction or DirectionIndicator.BIDIRECTIONAL.
  • If the number of applicable rule fields and the number of packet fields differ, the rule is skipped.
  • The pairing of applicable rule fields with packet fields follows the existing list order.
  • Within each pair, the field IDs must match.
  • Matching-operator behavior is unchanged from before: IGNORE accepts the field, EQUAL compares the complete buffer value with the logical length included, MSB compares against the target prefix, and MATCH_MAPPING requires the field value to occur in the mapping.
  • Field ordering and position handling as they currently exist must not be reinterpreted.

Ruler.match_schc_packet stays outside the iterator conversion and must keep returning its matching RuleDescriptor directly.

Compression

A call to compress(packet_descriptor=..., rule_descriptor=...) must return a Buffer in which the SCHC packet is present as one contiguous bit sequence.

Logical Order of the Output

In this exact order, the output is made up of:

  1. Significant rule-ID bits, exactly rule_descriptor.id.length of them.
  2. For every corresponding packet field and rule field, taken in descriptor order: any variable-length prefix that is required, with that field's compression residue immediately after it.
  3. packet_descriptor.payload, placed immediately after the final field residue.

The compression-action semantics that already exist must be kept:

  • NOT_SENT has a residue contribution of zero bits.
  • LSB contributes the least-significant bits its target prefix does not cover.
  • MAPPING_SENT contributes the mapped index.
  • VALUE_SENT contributes the complete logical value of the packet field.

Whenever the rule field behind an LSB or VALUE_SENT residue has length == 0, that residue's bit length is encoded immediately before the residue, per the existing format:

  • lengths below 15: the length expressed in 4 bits;
  • lengths from 15 through 254: 1111 and then the length in 8 bits, 12 bits altogether;
  • lengths from 255 through 65535: 1111, after that 11111111, and then the length in 16 bits, 28 bits altogether.

Every length in this format is a bit length.

Packing and the Resulting Buffer

The buffer that comes back must:

  • use Padding.RIGHT;
  • have a logical length that is equal to the sum of the bit lengths actually emitted for the rule ID, the length prefix, the residue, and the payload;
  • put the first logical bit into the most-significant bit of the output's first byte;
  • position every later component immediately after the one before it, even when either of the two is not byte-aligned;
  • hold only the final right-padding after the last logical bit, with no padding between the components;
  • be stored compactly in ceil(length / 8) bytes, with any low-order bits of the final byte that go unused set to zero.

The input fragments may arrive left-padded or right-padded. That padding orientation must not find its way into the wire format; what gets emitted is only their significant bits. As an illustration: a two-bit rule ID whose logical value is 11 takes up the two most-significant bits of the first SCHC byte. If it were the only component of the output, the outcome would be Buffer(content=b'\xc0', length=2, padding=Padding.RIGHT), not a buffer that starts with the raw byte b'\x03'.

Decompression

decompress(schc_packet=..., rule_descriptor=...) must invert the SCHC bit stream and return the packet after reconstruction as a right-padded Buffer.

Consuming the Input and Rebuilding the Fields
  • Exactly rule_descriptor.id.length bits from the beginning are consumed as the rule ID; those bits do not get copied to the reconstructed packet.
  • The rule fields are rebuilt in descriptor order, and each reconstructed field is appended directly after the field before it, at bit granularity.
  • The decompression-action semantics already in place are to be preserved:
    • With NOT_SENT, the field is reconstructed from its target value.
    • With LSB, the field is reconstructed from the target prefix, with the consumed least-significant residue bits placed after it.
    • With MAPPING_SENT, a mapping index is consumed and the mapped value corresponding to it is reconstructed.
    • With fixed-length VALUE_SENT, the number of residue bits that was declared is consumed.
    • With variable-length residues, the 4-, 12-, or 28-bit length format described above is decoded and consumed before the indicated number of data bits is consumed.
  • Once all the rule fields have been reconstructed, all the SCHC bits that remain are appended as the packet payload.

Between reconstructed fields there must be no byte alignment and no padding. Whatever padding orientation its target value or residue buffer employs, the significant bits of each field occupy exactly the bit positions they held originally.

The Buffer Returned and the Round Trip

The buffer returned must use Padding.RIGHT, must carry the logical length of the reconstructed fields plus the payload, and must be stored compactly, with only trailing right-padding coming after the final logical bit. The first reconstructed bit goes into the most-significant bit of the first byte. If the original packet is byte-aligned, decompress(...).content must exactly equal the original packet bytes; it is not sufficient for the buffer to merely contain equivalent field values in separately aligned bytes.

As an instance: a four-bit IPv6 version value given as Buffer(content=b'\x06', length=4, padding=Padding.LEFT), followed by an eight-bit traffic class of zero, means the reconstructed packet opens with bits 0110 0000, so the first output byte is 0x60, not 0x06.

Given a valid packet descriptor together with a matching rule that the existing compression/decompression actions support, decompressing what compress produced, using that rule, must reproduce the packet field bits in their original sequence, followed by the payload.

Compatibility Constraints

  • As part of the iterator conversion, the set of matching rules, the matching-operator semantics, direction filtering, and the rule order must not be changed.
  • The behavior of the compression/decompression actions and the existing variable-length encoding scheme must be preserved; the change that is required concerns exact bit placement and packing across buffers.
  • Outside the concatenation contract above, the existing Buffer behavior must be preserved, its public padding, slicing, equality, iteration, and serialization behavior included.
  • Per-field or per-residue byte alignment must not be introduced.
  • No new compression actions, matching operators, parser behavior, or rule-selection policy are required here.
  • These requirements are about observable values, lengths, padding modes, ordering, and iterator behavior; a particular internal algorithm is not prescribed.

Equivalently, sum the byte lengths of all fields positioned after the IPv6 header fields (i.e., the transport header fields and the payload) and express the total as a 16-bit value.

UDP Length — UDPComputeFunctions[UDPFields.LENGTH][0]

This function computes the UDP length field: the UDP header's byte count (8 bytes: source port, destination port, length, checksum) plus all of the UDP payload's bytes (everything positioned after the UDP header, any application-layer fields included, together with the trailing payload). The result is expressed as a 16-bit big-endian value.

In the reference stack, whose UDP length is 0x68, the result must be:

  • Buffer(content=b'\x00\x68', length=16).

Again, the Buffer that is returned is always 16 bits long.

UDP Checksum — UDPComputeFunctions[UDPFields.CHECKSUM][0]

The UDP checksum is what this function computes, applying the standard algorithm across the IPv6 pseudo-header plus the UDP header (with the checksum field taken as zero) plus the UDP payload:

  • IPv6 pseudo-header: the source address (16 bytes), the destination address (16 bytes), the UDP length as a 32-bit value, and the next-header value (17 for UDP) as a 32-bit value whose upper 3 bytes are zero.
  • UDP header: the source port, the destination port, the length, and a checksum field of zero.
  • The bytes of the UDP payload.

The checksum comes out as the 16-bit one's-complement of the one's-complement sum of all 16-bit words. Every needed field value (IPv6 source/destination addresses, UDP ports, UDP length, and payload) is obtained from decompressed_fields; the checksum entry itself, however, must be treated as zero, no matter what placeholder value is stored for it.

In the case of the reference packet, the result must be:

  • Buffer(content=b'\x7e\xd5', length=16).

As before, the returned Buffer is invariably 16 bits long.

Task Specification: Compute Functions for Compression Field Descriptors

Overview

You must ensure that a compression rule of the SCHC style can be applied to a parsed packet where certain of the rule field descriptors describe values that are computed out of the packet contents rather than being matched or sent literally. The central point of this task is getting the compressor to handle correctly a rule descriptor that was built for a CoAP packet.

Background

Rule field descriptors are the mechanism by which the codebase models compression rules. The public types that matter here (already present, to be used as given) include:

  • RuleFieldDescriptor(id, length, position, direction, target_value, matching_operator, compression_decompression_action)
  • RuleDescriptor(id, field_descriptors)
  • Buffer(content, length) — a buffer that is bit-oriented: its content is bytes, and its length is a length in bits.
  • Enumerations: CoAPFields, ParserDefinitions, DirectionIndicator, MO (matching operators), CDA (compression/decompression actions).

The compressor consumes a RuleDescriptor (i.e., a list of RuleFieldDescriptors) together with a parsed packet, and the compressed residue is what it produces.

Required Behavior

1. Target-value lengths of field descriptors must be self-consistent

Suppose a RuleFieldDescriptor carries a target_value Buffer that is meant to be matched against a field, or substituted for it, where the field has a declared bit length: the target value's Buffer.length (in bits) must equal the length declared for that field.

To make this concrete: a CoAP OPTION_DELTA field is declared with length=4 and has target content b'\x0c'; the target value Buffer for it must have length=4 (not 0). Whenever the buffer bit-length of the target values matches the declared field length, the compressor must operate correctly.

2. A trailing generic payload descriptor need not appear in rule descriptors

A rule descriptor written for a CoAP packet may terminate after the last field descriptor specific to CoAP (e.g. after the PAYLOAD_MARKER field). A final RuleFieldDescriptor with id=ParserDefinitions.PAYLOAD must not be required. A rule descriptor whose field descriptors end at the last protocol field is something the compressor must process correctly: any packet content that remains is treated as the payload, and the rule does not need an explicit payload field descriptor for that.

3. With the given rule, the compression of a CoAP packet must succeed and produce the correct residue

A rule whose field descriptors include the following must be applied correctly by the compressor:

  • Fields that are matched and elided via MO.EQUAL / CDA.NOT_SENT (the parsed field values must be matched by their target value buffers, with bit-lengths consistent with the declared field lengths).
  • Fields that are sent as residue via MO.IGNORE / CDA.VALUE_SENT.
  • Fields declared with length=0 whose value is variable and is carried in the residue.

The expected compressed output — the rule id, followed by the residue, which is put together from the value-sent fields and from the trailing payload bytes — is what the compressor must produce when such a rule and a parsed CoAP packet that matches are given.

Deliverables

Deliver an implementation/fix of the compression path so that:

  • Target-value buffers are interpreted according to the bit lengths declared for them, and a field descriptor with a declared length of N bits gets matched against exactly N bits taken from the corresponding parsed field.
  • A trailing ParserDefinitions.PAYLOAD field descriptor is not something the compressor depends on; the packet bytes remaining after the described fields are treated as payload.
  • Chunk padding, when residue bytes are being assembled, uses integer division that rounds up to whole bytes (a residue of B bits occupies ceil(B/8) bytes).

Notes

Exactly as given, the public API names and signatures listed above must remain importable and callable; a RuleDescriptor and a parsed packet are what the compressor entry point must accept, and the compressed Buffer is what it must return.

Overview

You must ensure that the COMPUTE compression/decompression action is handled correctly during both compression and decompression, so that a packet that is parsed, compressed, and then decompressed reproduces the original packet bytes exactly. Behavior Requirements

Round-trip correctness for COMPUTE fields

Starting from an IPv6/UDP/CoAP packet:

  1. Parse the raw packet bytes into a PacketDescriptor by means of a parser obtained from factory(stack_id=Stack.IPV6_UDP_COAP).
  2. Compress the PacketDescriptor with a RuleDescriptor by invoking compress(...).
  3. Decompress the resulting SCHC packet with the same RuleDescriptor by invoking decompress(...).

The result of the decompression must be a Buffer whose content and length are byte-for-byte identical to the original packet buffer (that is, a Buffer built from the original raw bytes with length = 8 * len(raw_bytes)).

Semantics of the COMPUTE action

For any rule field whose compression_decompression_action is CDA.COMPUTE:

  • On compression: the field value contributes no bits to the SCHC packet (it is neither stored via VALUE_SENT nor transmitted in any other way); at decompression it is treated as derivable.
  • On decompression: the field value must be recomputed from the reconstructed packet instead of being read from the SCHC residue. The fields listed below must be recomputed correctly so that the reconstructed bytes match the original:
    • IPv6 payload length (IPv6Fields.PAYLOAD_LENGTH, 16 bits): the length, in bytes, of everything following the IPv6 header (i.e., the UDP header together with its payload).
    • UDP length (UDPFields.LENGTH, 16 bits): the length, in bytes, of the UDP header plus the UDP payload.
    • UDP checksum (UDPFields.CHECKSUM, 16 bits): the standard UDP checksum computed over the IPv6 pseudo-header, the UDP header (with the checksum field zeroed during the computation), and the UDP payload.

The recomputed values must be inserted at the correct bit positions so that the fully reconstructed packet equals the original.

Other actions (for context)

The rule under test also exercises the following, and these must continue to work so that the round-trip succeeds:

  • CDA.NOT_SENT with MO.EQUAL: the field is omitted from the residue; it is restored from the rule's target_value.
  • CDA.VALUE_SENT with MO.IGNORE: the field value is carried verbatim in the SCHC residue and restored from it.
  • CDA.MAPPING_SENT with MO.MATCH_MAPPING: the index is carried in the residue and restored via the mapping.

Rules may contain repeated field ids (e.g., multiple CoAP option delta/length/value triplets), each of which is matched positionally in order.

Criterion for Acceptance

When an IPv6/UDP/CoAP packet is parsed via the IPV6_UDP_COAP stack and is then compressed and decompressed with a rule in which the IPv6 payload length, UDP length, and UDP checksum fields use the COMPUTE action, the decompressed Buffer must equal the original packet Buffer exactly (same content bytes, same bit length).

Its JSON object representation contains the keys "id", "value" (a Buffer object), and "position".

PacketDescriptor

It is constructed as:

PacketDescriptor(direction=<DirectionIndicator>, fields=<list[FieldDescriptor]>, payload=<Buffer>)

Note: length is no longer a parameter of the constructor. It must not be required as an input, nor accepted as one.

Attributes available after construction:

  • direction
  • fields (a list of FieldDescriptor)
  • payload (a Buffer)
  • length (an int, computed — see below)

Behavior Requirements

Computation of the raw content

A PacketDescriptor must compute a raw buffer by concatenating the following, in order:

  1. The content bytes of each field's value buffer, in the order in which the fields appear in the fields list.
  2. The content bytes of the payload buffer.

For the raw buffer:

  • content is the concatenation of the byte sequences above.
  • length (in bits) equals the sum of the length values of all field value buffers plus the length of the payload buffer.
  • padding is "right".

Example: given field values with contents 0x0001 (16 bits) and 0x0002 (16 bits), plus a payload of 0x000102 (24 bits), the raw content is the bytes 00 01 00 02 00 01 02, with a length of 56 bits.

The length attribute

The length attribute on a PacketDescriptor is the total bit-length of the raw buffer (the sum of all field value lengths plus the payload length). For the example above, length == 56.

Serializing to JSON: PacketDescriptor.json()

The method returns a JSON string, emitting its keys in exactly this order:

  1. "direction" — the direction value as a string (for example "Up" for DirectionIndicator.UP).
  2. "fields" — a JSON array of field descriptor objects.
  3. "payload" — the payload buffer object.
  4. "raw" — the computed raw buffer object (content, length, padding "right").
  5. "length" — the total bit-length as an integer (equal to the raw buffer's length).

The output must be compact (with a single space after each : and , separator, matching standard JSON formatting).

Example output for the sample given above:

{"direction": "Up", "fields": [{"id": "fd1", "value": {"content": "0001", "length": 16, "padding": "left"}, "position": 0}, {"id": "fd2", "value": {"content": "0002", "length": 16, "padding": "left"}, "position": 0}], "payload": {"content": "000102", "length": 24, "padding": "left"}, "raw": {"content": "00010002000102", "length": 56, "padding": "right"}, "length": 56}

This is a class method that accepts a JSON string in the format produced by json() above (including the "raw" and "length" keys) and returns a PacketDescriptor instance.

  • direction reflects the direction that was serialized (for example "Up" → DirectionIndicator.UP).
  • fields rebuilds the list of FieldDescriptor objects with their id, value buffer (content decoded from hex, length in bits), and position.
