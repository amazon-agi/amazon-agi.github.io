Specification for Updates to the OpenFGA Python SDK (version 0.1.0)

Overview

Bump the OpenFGA Python SDK package version to 0.1.0, support selecting an authorization model in the Check and Expand request bodies, and move to the current wire contracts for the List Objects request and response. Except for the response-field rename and the package-version change that are explicitly described, existing endpoint signatures and behavior must remain compatible.

1. SDK package version

Wherever the current SDK version is publicly surfaced, the SDK package version must be 0.1.0. That covers the distribution metadata, the package-level openfga_sdk.__version__ value, the canonical release-version declaration, debug/version reports, and User-Agent headers generated at runtime. No current-version output may keep reporting 0.0.1.

The version in question is the SDK package version; the OpenFGA API protocol version remains unchanged.

User-Agent values

The default User-Agent strings must be exactly:

  • OAuth client-credentials token requests: openfga-sdk (python) 0.1.0
  • Main OpenFGA API requests: openfga-sdk /0.1.0

The punctuation, casing, and spacing of these strings must be preserved. Header composition as it exists remains intact: for example, API-token authentication must still add its Authorization: Bearer ... header, and default headers supplied by callers must still be sent alongside the updated main-client User-Agent. For OAuth token requests, the existing Accept: application/json and Content-Type: application/json headers must be retained.

2. authorization_model_id support in Check requests

CheckRequest must accept an optional constructor keyword argument named authorization_model_id whose value is a string. The corresponding public attribute must also expose that value.

Once the value is set, serialization for OpenFgaApi.check must include it as the top-level JSON property authorization_model_id, next to the existing tuple_key and any other Check fields that are supplied. It must not be nested inside tuple_key, nor moved to a query or path parameter.

Example of a request body:

{
  "tuple_key": {
    "object": "document:2021-budget",
    "relation": "reader",
    "user": "user:81684243-9356-4421-8fbf-a4f8d36aa31b"
  },
  "authorization_model_id": "1uHxCSuTP0VKPYSnkq1pbb1jeZw"
}

The behavior of the existing tuple_key, contextual_tuples, and trace remains unchanged. If authorization_model_id is not supplied, the existing optional-field behavior is retained.

3. authorization_model_id support in Expand requests

ExpandRequest must accept an optional constructor keyword argument named authorization_model_id whose value is a string, and it must expose that value through the corresponding public attribute.

When it is set, serialization for OpenFgaApi.expand must include it as the top-level JSON property authorization_model_id, next to tuple_key.

Sample request body:

{
  "tuple_key": {
    "object": "document:budget",
    "relation": "reader"
  },
  "authorization_model_id": "1uHxCSuTP0VKPYSnkq1pbb1jeZw"
}

If authorization_model_id is not supplied, the existing optional-field behavior is retained.

4. Contract for the List Objects request

ListObjectsRequest must continue to support these existing top-level request fields:

  • authorization_model_id (str, optional)
  • type (str)
  • relation (str)
  • user (str)
  • contextual_tuples (ContextualTupleKeys, optional)

In particular, authorization_model_id must remain accepted as a constructor keyword and as a public attribute. Once it is set, the request that OpenFgaApi.list_objects sends must serialize it as a top-level authorization_model_id property; it must not be discarded. The other supplied fields likewise stay as top-level properties.

Example request body:

{
  "authorization_model_id": "01G5JAVJ41T49E9TT3SKVS7X1J",
  "type": "document",
  "relation": "reader",
  "user": "user:81684243-9356-4421-8fbf-a4f8d36aa31b"
}

When contextual_tuples is supplied, it must continue to serialize under the top-level contextual_tuples key. When a field is not set, the normal optional-field behavior applies.

ListObjectsRequest does not use tuple_key, page_size, or continuation_token; those fields must not replace or reshape its existing field set. They belong to the separate ReadRequest contract. ReadRequest — including its existing optional authorization_model_id support — is left unchanged by this task.

5. Contract for the List Objects response

The result field represented by ListObjectsResponse is to be renamed from object_ids to objects. The name of the response class stays ListObjectsResponse.

For an API response such as:

{
  "objects": [
    "document:abcd1234"
  ]
}

the result once deserialized must satisfy:

response.objects == ["document:abcd1234"]

For this result field, the constructor, public property, type metadata, JSON-field mapping, and dictionary serialization must all use objects. On the wire, the response key is objects, not object_ids. The values are full OpenFGA object strings, type prefix included (for example, document:abcd1234), rather than bare IDs such as abcd1234.

6. Compatibility and behavior that stays unchanged

Aside from the changes above:

  • OpenFgaApi.check, OpenFgaApi.expand, and OpenFgaApi.list_objects keep their existing signatures and call semantics. They remain async methods that accept their corresponding request body objects and return CheckResponse, ExpandResponse, and ListObjectsResponse, respectively.
  • The endpoints are still POST /stores/{store_id}/check, POST /stores/{store_id}/expand, and POST /stores/{store_id}/list-objects.
  • Request serialization continues to omit fields that were not supplied, while preserving every supplied field defined by the relevant request class.
  • Existing Accept, Content-Type, authentication, custom-header, timeout, routing, validation, response handling, retry, and error behavior remains unchanged, apart from the required User-Agent version update.
  • No endpoint or public request/response contract that is unrelated should be changed.

Task Specification: Change the SDK Version Identifier

Goal

Change the version identifier that the OpenFGA Python SDK uses from 0.1.0 to 0.1.1. The SDK embeds this version string in the User-Agent HTTP header that it sends with outgoing requests.

Behavior Required

Wherever the version is exposed, the SDK must report it as 0.1.1. In particular, the User-Agent header of the HTTP requests that two components make must reflect the version change:

1. Credentials / requests for OAuth tokens

When the SDK retrieves an OAuth access token by sending a POST request to the token endpoint (e.g. https://www.testme.com/oauth/token), the headers of the request must include:

User-Agent: openfga-sdk (python) 0.1.1

together with the headers that are already present:

Accept: application/json
Content-Type: application/json
2. Requests made by the API client

When the SDK issues API calls (e.g. a POST to the check endpoint at http://api.fga.example/stores/{store_id}/check), the headers of the request must include:

User-Agent: openfga-sdk /0.1.1

together with the headers that are already present:

Accept: application/json
Content-Type: application/json

as well as any request-specific headers (such as an Authorization: Bearer <token> header when a bearer token credential is configured, or any custom header supplied by the caller).

Scope of the Change

  • The only change in behavior is the version number appearing in the two User-Agent header formats shown above (openfga-sdk (python) 0.1.1 and openfga-sdk /0.1.1).
  • All other header contents, request methods, URLs, and request payloads stay unchanged.
  • The two User-Agent string formats differ from each other (one contains (python), the other does not), and both must be preserved exactly as shown, with only the version updated to 0.1.1.

Specification of the Task

Overview

The codebase you are working on is the OpenFGA Python SDK. Two changes to the SDK are required by this task: turning schema_version into a required field in authorization model data structures, and fixing the User-Agent header string.

Change 1: The schema_version field in the authorization model models

AuthorizationModel

The AuthorizationModel model class must accept and store a schema_version attribute, which is a string. The constructor must accept schema_version as a keyword argument, in addition to the existing id and type_definitions keyword arguments.

Two AuthorizationModel instances must be considered equal only when all their attributes — schema_version included — are equal.

If an AuthorizationModel is deserialized from a JSON/dict payload that has a schema_version field, that value must be captured into the schema_version attribute.

WriteAuthorizationModelRequest

The WriteAuthorizationModelRequest model class must accept and store a schema_version attribute, which is a string. The constructor must accept schema_version as a keyword argument, in addition to the existing type_definitions keyword argument.

Serializing a WriteAuthorizationModelRequest for transmission must produce a request body that includes a schema_version key holding the provided value, alongside the type_definitions key. For instance, building the request with schema_version="1.1" and a list of type definitions must yield a serialized body of the form:

{
  "schema_version": "1.1",
  "type_definitions": [ ... ]
}

Change 2: The User-Agent header

The default User-Agent HTTP request header for the SDK must be:

openfga-sdk python/0.1.1

(The old value was openfga-sdk /0.1.1; the token python must appear between the space and the slash/version.)

Outgoing API requests must be sent with this header unless a caller-supplied header overrides it.

Notes / Behavior That Stays Unchanged

  • The check, expand, and read_authorization_model API operations keep functioning as before; the added schema_version support and the corrected User-Agent string are the only items in scope.
  • authorization_model_id values are opaque strings that are passed through unchanged (no format validation is being introduced).

Public API Surface (these must be importable and callable)

  • AuthorizationModel(id=..., schema_version=..., type_definitions=...) — a model that has a schema_version attribute and whose equality takes it into account.
  • WriteAuthorizationModelRequest(schema_version=..., type_definitions=...) — a model that, when serialized, writes schema_version into the request body.

These classes live in the SDK's model package and are importable at the same locations as the existing TypeDefinition model.

Holding this configuration and validating it is the responsibility of Credentials. Acquiring OAuth tokens, tracking token-expiry state, and generating authentication headers belong to OAuth2Client; API clients must not depend on Credentials.get_authentication_header.

validate_credentials_config()

For valid configuration, Credentials.validate_credentials_config() returns normally. Invalid configuration raises openfga_sdk.ApiValueError, the same exception type as openfga_sdk.exceptions.ApiValueError.

The rules are:

  1. The method value must be exactly one of "none", "api_token", or "client_credentials". Any other value raises ApiValueError.
  2. The method "none" is valid when no configuration is present. A Credentials created by default construction remains configured with method == "none".
  3. For "api_token":
    • The configuration argument is required.
    • The value of configuration.api_token must be a non-empty string. A missing value, or "", raises ApiValueError.
  4. For "client_credentials":
    • The configuration argument is required.
    • All of client_id, client_secret, api_issuer, and api_audience must be present. A required value that is missing raises ApiValueError.

OAuth2Client API

Import locations and variants

Both classes must be provided at these public import locations:

from openfga_sdk.oauth2 import OAuth2Client          # async
from openfga_sdk.sync.oauth2 import OAuth2Client     # synchronous

The two variants share the same authentication behavior; the only difference is whether I/O is awaitable.

Constructor and token-cache state

Construction takes one positional argument, the credentials:

OAuth2Client(credentials)

The credentials argument is a Credentials instance or None.

Token-cache state is owned by each instance and exposed through:

  • _access_token: the cached token string, initially None/unset.
  • _access_expiry_time: a datetime marking when that token expires, initially None/unset.

The cache belongs to OAuth2Client, not to Credentials.

get_authentication_header(client)

In the async variant, the call is awaitable:

headers = await oauth_client.get_authentication_header(client)

In the synchronous variant, the method is called directly:

headers = oauth_client.get_authentication_header(client)

The return value is always a dictionary of headers. Which authentication path applies is selected as follows.

A valid cached token

A cache entry is valid only if _access_token is set and _access_expiry_time is a datetime in the future. A valid cache returns the following:

{"Authorization": "Bearer <access_token>"}

No token request may be made. On this path the client argument may therefore be None. A valid cache that was pre-populated must be usable even when the OAuth2Client was constructed with credentials=None.

If the token is absent, the expiry is absent, or the expiry is no longer in the future, it is not a valid cache entry.

No authentication

If no valid cached token is available and either:

  • credentials is None, or
  • credentials.method == "none",

the method returns {}. An OAuth2 token request must not be made. As a consequence, API calls made without credentials do not gain an Authorization header.

Static API token

When no valid cached token is taking effect and credentials.method == "api_token", the configured token is returned directly:

{"Authorization": "Bearer <api_token>"}

That value comes from credentials.configuration.api_token. On this path an OAuth2 token request must not be made, and client may be None when the helper is called directly.

OAuth2 client-credentials token

When credentials.method == "client_credentials", a valid cache is used if one is available. Otherwise, a new token is obtained through the provided REST client.

That token request must invoke the REST client's request method exactly once, with these arguments:

request(
    "POST",
    "https://<api_issuer>/oauth/token",
    headers=<token_headers>,
    query_params=None,
    post_params=None,
    _preload_content=True,
    _request_timeout=None,
    body={
        "client_id": <client_id>,
        "client_secret": <client_secret>,
        "audience": <api_audience>,
        "grant_type": "client_credentials",
    },
)

The values of <api_issuer>, <client_id>, <client_secret>, and <api_audience> come from the credential configuration. For example, an issuer of www.testme.com results in https://www.testme.com/oauth/token.

The <token_headers> value must be a urllib3.response.HTTPHeaderDict containing exactly:

{
    "Accept": "application/json",
    "Content-Type": "application/json",
    "User-Agent": "openfga-sdk (python) 0.2.1",
}

The async variant awaits the REST request; the synchronous variant calls it synchronously.

Given a successful HTTP 200 response whose JSON body contains access_token and expires_in, the client:

  1. Stores the access_token value in _access_token.
  2. Sets _access_expiry_time to a datetime that is at least expires_in seconds after the token request was initiated.
  3. Returns {"Authorization": "Bearer <access_token>"}.

A later call that happens before that expiry must reuse the cached token and make no additional token request. Once the cache is absent or has expired, the next client-credentials call must obtain a new token.

If the token endpoint returns a non-success HTTP status, such as 403, the method raises openfga_sdk.exceptions.AuthenticationError instead of returning an authentication header.

Integration into the API clients

Each of the two generic API clients must use the corresponding OAuth2Client for credentials configured on its Configuration:

  • openfga_sdk.api_client.ApiClient uses the async openfga_sdk.oauth2.OAuth2Client, awaiting header generation.
  • openfga_sdk.sync.api_client.ApiClient uses the synchronous openfga_sdk.sync.oauth2.OAuth2Client and calls it directly.

Each API client must obtain the authentication headers through its OAuth2 client before an outgoing OpenFGA request, and merge the returned entries into that request's headers. Across successive requests that one API-client instance makes, an unexpired client-credentials token must be reused without another token request.

In both variants, this integration must produce the following observable results:

  • When there are no credentials or method="none", the OpenFGA request carries no credential-derived Authorization header, and no OAuth2 token request occurs.
  • When credentials with valid method="api_token" are used, the OpenFGA request includes Authorization: Bearer <api_token> and no OAuth2 token request occurs.
  • When method="client_credentials" is set, the OpenFGA request includes the acquired or cached bearer token, and unexpired tokens are reused across requests.
  • Request headers that already exist, including the normal Accept, Content-Type, and User-Agent headers plus user-supplied custom headers, continue to be sent alongside any credential-derived Authorization header.

The higher-level async and synchronous OpenFgaClient classes rely on these generic API clients, so the same authentication behavior must apply when requests are made through either higher-level client.

Expectations for the REST client

The client that get_authentication_header accepts is the matching REST implementation:

  • Async variant: openfga_sdk.rest.RESTClientObject
  • Synchronous variant: openfga_sdk.sync.rest.RESTClientObject

It is possible to construct it with RESTClientObject(Configuration()). The result of its request(...) exposes an HTTP status and JSON-decodable response data. The async request and close operations are awaitable; the synchronous ones are direct calls.

Scope

This task changes only the ownership of the authentication runtime logic. Existing credential construction and validation APIs, OpenFGA request behavior, custom-header behavior, async/sync calling conventions, and exception types must be preserved. Token acquisition and cache state must not be moved back onto Credentials.
