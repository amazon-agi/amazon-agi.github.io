Task Specification: OpenFGA Python SDK 0.1.0 Updates

Overview

Update the OpenFGA Python SDK package version to 0.1.0, support authorization model selection in Check and Expand request bodies, and adopt the current List Objects request and response wire contracts. Existing endpoint signatures and behavior must remain compatible except for the explicitly described response-field rename and package-version change.

1. SDK version

The SDK package version must be 0.1.0 everywhere the current SDK version is publicly surfaced. This includes the distribution metadata, the package-level openfga_sdk.__version__ value, the canonical release-version declaration, debug/version reports, and runtime-generated User-Agent headers. No current-version output may continue to report 0.0.1.

This is the SDK package version; the OpenFGA API protocol version remains unchanged.

User-Agent values

The exact default User-Agent strings must be:

  • OAuth client-credentials token requests: openfga-sdk (python) 0.1.0
  • Main OpenFGA API requests: openfga-sdk /0.1.0

Preserve the punctuation, casing, and spacing in these strings. Existing header composition remains intact: for example, API-token authentication must still add its Authorization: Bearer ... header, and caller-supplied default headers must still be sent alongside the updated main-client User-Agent. OAuth token requests must retain their existing Accept: application/json and Content-Type: application/json headers.

2. authorization_model_id in Check requests

CheckRequest must accept an optional constructor keyword argument named authorization_model_id whose value is a string. It must also expose that value through the corresponding public attribute.

When the value is set, serialization for OpenFgaApi.check must include it as the top-level JSON property authorization_model_id, alongside the existing tuple_key and any other supplied Check fields. It must not be nested inside tuple_key or moved to a query or path parameter.

Example request body:

{
  "tuple_key": {
    "object": "document:2021-budget",
    "relation": "reader",
    "user": "user:81684243-9356-4421-8fbf-a4f8d36aa31b"
  },
  "authorization_model_id": "1uHxCSuTP0VKPYSnkq1pbb1jeZw"
}

The existing tuple_key, contextual_tuples, and trace behavior remains unchanged. If authorization_model_id is not supplied, retain the existing optional-field behavior.

3. authorization_model_id in Expand requests

ExpandRequest must accept an optional constructor keyword argument named authorization_model_id whose value is a string and expose it through the corresponding public attribute.

When set, serialization for OpenFgaApi.expand must include it as the top-level JSON property authorization_model_id, alongside tuple_key.

Example request body:

{
  "tuple_key": {
    "object": "document:budget",
    "relation": "reader"
  },
  "authorization_model_id": "1uHxCSuTP0VKPYSnkq1pbb1jeZw"
}

If authorization_model_id is not supplied, retain the existing optional-field behavior.

4. List Objects request contract

ListObjectsRequest must continue to support its existing top-level request fields:

  • authorization_model_id (str, optional)
  • type (str)
  • relation (str)
  • user (str)
  • contextual_tuples (ContextualTupleKeys, optional)

In particular, authorization_model_id must remain an accepted constructor keyword and public attribute. When it is set, the request sent by OpenFgaApi.list_objects must serialize it as a top-level authorization_model_id property. It must not be discarded. The other supplied fields likewise remain top-level properties.

Example request body:

{
  "authorization_model_id": "01G5JAVJ41T49E9TT3SKVS7X1J",
  "type": "document",
  "relation": "reader",
  "user": "user:81684243-9356-4421-8fbf-a4f8d36aa31b"
}

When supplied, contextual_tuples must continue to serialize under the top-level contextual_tuples key. Normal optional-field behavior applies when a field is not set.

ListObjectsRequest does not use tuple_key, page_size, or continuation_token; those fields must not replace or reshape its existing field set. They belong to the separate ReadRequest contract. ReadRequest, including its existing optional authorization_model_id support, is unchanged by this task.

5. List Objects response contract

Rename the result field represented by ListObjectsResponse from object_ids to objects. The response class name remains ListObjectsResponse.

For an API response such as:

{
  "objects": [
    "document:abcd1234"
  ]
}

the deserialized result must satisfy:

response.objects == ["document:abcd1234"]

The constructor, public property, type metadata, JSON-field mapping, and dictionary serialization for this result field must all use objects. The wire response key is objects, not object_ids. Values are full OpenFGA object strings, including their type prefix (for example, document:abcd1234), rather than bare IDs such as abcd1234.

6. Compatibility and unchanged behavior

Except for the changes above:

  • OpenFgaApi.check, OpenFgaApi.expand, and OpenFgaApi.list_objects retain their existing signatures and call semantics. They remain async methods accepting their corresponding request body objects and returning CheckResponse, ExpandResponse, and ListObjectsResponse, respectively.
  • The endpoints remain POST /stores/{store_id}/check, POST /stores/{store_id}/expand, and POST /stores/{store_id}/list-objects.
  • Existing request serialization continues to omit fields that were not supplied while preserving every supplied field defined by the relevant request class.
  • Existing Accept, Content-Type, authentication, custom-header, timeout, routing, validation, response handling, retry, and error behavior remains unchanged, apart from the required User-Agent version update.
  • No unrelated endpoint or public request/response contract should be changed.

Task Specification: Update SDK Version Identifier

Objective

Update the version identifier used by the OpenFGA Python SDK from 0.1.0 to 0.1.1. This version string is embedded in the User-Agent HTTP header that the SDK sends with outgoing requests.

Required Behavior

The SDK must report its version as 0.1.1 wherever the version is exposed. Specifically, the version change must be reflected in the User-Agent header of HTTP requests made by two components:

1. Credentials / OAuth token requests

When the SDK obtains an OAuth access token via a POST request to the token endpoint (e.g. https://www.testme.com/oauth/token), the request headers must include:

User-Agent: openfga-sdk (python) 0.1.1

along with the existing headers:

Accept: application/json
Content-Type: application/json
2. API client requests

When the SDK makes API calls (e.g. a POST to the check endpoint at http://api.fga.example/stores/{store_id}/check), the request headers must include:

User-Agent: openfga-sdk /0.1.1

along with the existing headers:

Accept: application/json
Content-Type: application/json

and any request-specific headers (such as an Authorization: Bearer <token> header when a bearer token credential is configured, or any custom header the caller supplies).

Scope

  • The only change in behavior is the version number in the two User-Agent header formats shown above (openfga-sdk (python) 0.1.1 and openfga-sdk /0.1.1).
  • All other header contents, request methods, URLs, and request payloads remain unchanged.
  • The two User-Agent string formats differ (one contains (python), the other does not) and both must be preserved exactly as shown, only with the version updated to 0.1.1.
