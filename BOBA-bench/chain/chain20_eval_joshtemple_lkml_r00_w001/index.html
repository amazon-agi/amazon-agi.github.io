Task Specification: Building the Serializer Class in the lkml Package

Overview

A Serializer class must be implemented in the lkml package; it turns Python dictionaries into LookML-formatted string output. It must be possible to import the class as lkml.Serializer.

Public API

  • Module/package: lkml (importable with import lkml)
  • Class: Serializer
    • Must support instantiation with no arguments: lkml.Serializer()
    • Method: serialize_dict(self, data)
      • data: a Python dict.
      • The method returns an iterable/generator of string fragments. Once those fragments are concatenated (joined with the empty string), the result is the complete LookML output described below.

Serialization Behavior

Serialization turns the dictionary into a LookML block. The dict is expected to hold a "name" key together with one or more additional key/value pairs. The rules below dictate how the output is produced.

Structure of the block
  • The value stored under the "name" key becomes the block's key/label; it is not emitted as a normal field line, and instead opens the block.
  • The block opener makes up the first output fragment: the "name" value, then ": {", then a newline. For example, when data["name"] == "dimension", the opening fragment is:
    dimension: {\n
  • Each remaining key/value pair (that is, every key other than "name") is emitted as an indented line, in the order in which the keys appear in the dict.
  • The last output fragment is the closing brace } — a single } character carrying no trailing newline.
Field lines

Each key/value pair whose key is not name is rendered as its own fragment consisting of:

  • Indentation in the form of two leading spaces.
  • The key name, then ": ".
  • The value, formatted per the quoting rules below.
  • A trailing newline \n.
Rules for quoting values

The key determines whether a value is wrapped in double quotes:

  • Unquoted values — the value is emitted verbatim, with no surrounding quotes. This applies to keys including:

    • from_field
    • to_field

  • Quoted values — the value is wrapped in double quotes ("..."). This applies to keys including:

    • label
    • group_label
    • description

Worked Examples

Example 1 — literals without quotes

Input:

{"name": "bind_filters", "from_field": "field_name", "to_field": "field_name"}

Output when concatenated:

bind_filters: {
  from_field: field_name
  to_field: field_name
}

Expressed as ordered fragments:

"bind_filters: {\n"
"  from_field: field_name\n"
"  to_field: field_name\n"
"}"
Example 2 — literals in quotes

Input:

{
    "name": "dimension",
    "label": "Dimension Name",
    "group_label": "Group Name",
    "description": "A dimension description.",
}

Output when concatenated:

dimension: {
  label: "Dimension Name"
  group_label: "Group Name"
  description: "A dimension description."
}

Expressed as ordered fragments:

"dimension: {\n"
'  label: "Dimension Name"\n'
'  group_label: "Group Name"\n'
'  description: "A dimension description."\n'
"}"

Notes

  • The output field lines must preserve the insertion order of the dict keys.
  • The serialize_dict return value must be iterable in such a way that joining its fragments produces the exact strings shown above.

Task Specification: Serializer for Dictionaries

Goal

Implement a serialize_dict method on a serializer object; the method transforms a Python dictionary into a formatted string representation, which is yielded as a sequence of string fragments.

API

The serializer is instantiated through a class provided by your serializer module. The method of interest is:

def serialize_dict(self, data: dict) -> Iterator[str]
  • Input: a dictionary in which the keys are strings and the values are strings.
  • Output: a generator (or any iterator) that yields string fragments. Concatenating all of the yielded fragments (e.g. via "".join(...)) gives the complete serialized output.

How Serialization Behaves

General structure

The output is made up of an optional name prefix, followed by a body enclosed in braces that holds one line per key/value entry.

The name key is optional

The key "name" receives special treatment and is optional:

  • When "name" is present in the dictionary, its value serves as a prefix to the opening brace. The output starts with the value of "name", then a space, then {, then a newline. The name entry itself is NOT emitted as one of the body lines.

    An example of the prefix form:

    dimension_name {

  • When "name" is absent, the output starts directly with { followed by a newline (no prefix, no leading space):

    {
The body lines

Every key/value pair other than "name" is emitted as a line inside the braces. Each of these lines:

  • Starts with two spaces of indentation.
  • Contains the key, then : (colon and single space), then the serialized value.
  • Terminates with a newline.

The order in which the entries appear is the dictionary's iteration order.

How values are formatted (quoted vs. unquoted)

Each value is rendered either as a bare (unquoted) literal or as a double-quoted string; the choice depends on the value's content:

  • Unquoted: values made up solely of characters that are valid for an unquoted identifier-style literal (letters, digits, and underscores) are emitted verbatim, with no quotes surrounding them.

    As an example: the value field_name is emitted as field_name.

  • Quoted: values that contain any other characters (such as spaces or periods) are wrapped in double quotes (").

    Some examples:

    • Dimension Name → "Dimension Name"
    • Group Name → "Group Name"
    • A dimension description. → "A dimension description."
Closing the output

Once all body lines have been emitted, the output finishes with a closing } character. No trailing newline appears after the closing brace.

Full Examples

Without a name, unquoted values:

Input: {"from_field": "field_name", "to_field": "field_name"}

Output:

{
  from_field: field_name
  to_field: field_name
}

Without a name, quoted values:

Input:

{
    "label": "Dimension Name",
    "group_label": "Group Name",
    "description": "A dimension description.",
}

Output:

{
  label: "Dimension Name"
  group_label: "Group Name"
  description: "A dimension description."
}

With a name:

Input: {"name": "dimension_name", "label": "Dimension Name"}

Output:

dimension_name {
  label: "Dimension Name"
}
03 Implement a serializer that turns Python dictionaries into a textual, indented, block-structured representation resembling a LookML-style configuration format. 612 words · rewritten by GPT-5.6-sol, reworded by GLM-5.3-Flash

Overview

Implement a serializer that turns Python dictionaries into a textual, indented, block-structured representation resembling a LookML-style configuration format.

Public API

Expose a serializer object (an instance of a class) that provides the following method:

serialize_dict(data: dict) -> generator/iterable of str

The method's return value is an iterable of string fragments. To obtain the full serialized output, callers join these fragments with "". The fragments must contain their own newline characters and leading whitespace, so that concatenation produces the exact formatted text described below.

Serialization Rules

Given a dictionary, produce block-structured text that uses 2 spaces per indentation level.

How blocks are structured
  • A dictionary at the top level that has no name key is wrapped in a block delimited by { and }.
  • A newline follows the opening brace.
  • The closing } sits on its own line at the indentation level of the block it closes.
  • Each key/value pair inside a block is placed on its own line, indented one level deeper than the braces of its enclosing block.
  • When a nested block closes, the indentation must drop back to the correct parent level.
  • The final closing } at the top level has no trailing newline.
Dictionary values and hoisting of name

A dictionary value is rendered as a nested block. When there is no name key, it takes this form:

key: {
  ...
}

When any dictionary contains a key named name, that key is not rendered as an ordinary line within the block body. Its value is instead hoisted onto the block's opening line. All remaining keys are rendered inside the block in their normal order.

  • For a nested dictionary, use the form key: <name_value> {.
  • For the top-level dictionary, use the form <name_value> {, with no key or colon before the name value. This named opening takes the place of the otherwise bare top-level {.

As an example, serializing:

{
    "name": "dimension_name",
    "label": "Dimension Name",
}

results in:

dimension_name {
  label: "Dimension Name"
}
Scalar values

A scalar value that is not a dictionary is rendered on one line as:

key: value

Rendering uses the value's string form without surrounding quotes, except for the quoted fields and booleans described below.

Quoted string fields

If a key is named exactly label, group_label, or description, its string value must be surrounded by double quotes. Wherever those fields occur — including inside nested dictionaries — this rule applies. For example:

label: "Dimension Name"
group_label: "Group Name"
description: "A dimension description."

Plain string scalar fields other than these remain unquoted.

Boolean values

Boolean scalar values must be serialized as yes when the value is True and as no when it is False.

Ordering

The dictionary's iteration order (insertion order) is the order in which key/value pairs are emitted. A hoisted name key does not appear in the body, and the relative order of the remaining entries is preserved.

Example of Nested Formatting

Serializing the following:

{
    "derived_table": {
        "explore_source": {
            "bind_filters": {
                "from_field": "field_name",
                "to_field": "field_name",
            },
            "name": "explore_name",
        }
    }
}

results in the following, after the returned fragments have been joined:

{
  derived_table: {
    explore_source: explore_name {
      bind_filters: {
        from_field: field_name
        to_field: field_name
      }
    }
  }
}

In this example, the explore_source dictionary has its name value hoisted onto its opening line, its other key remains in the block body, indentation grows by 2 spaces at each nested level, and each closing brace comes back to the indentation of the block it closes.
