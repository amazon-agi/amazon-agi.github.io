01 The croniter class is the subject of this task. 585 words · source specification, reworded by GLM-5.3-Flash

Specification of the Task

Summary

The croniter class is the subject of this task. Its generator-based iteration methods are to behave differently when no matching date can be found within the range of time being searched, and which behavior applies is decided by whether the caller gave an explicit maximum gap between matches.

Public API

The class this task revolves around is croniter, which is imported as follows:

from croniter import croniter
Constructor

A keyword argument max_years_between_matches must be accepted by the constructor, on top of its existing parameters such as the cron expression string, a start datetime, and day_or:

croniter(expr_format, start_time=..., day_or=..., max_years_between_matches=None)
  • max_years_between_matches states the maximum number of years that the search covers, forward or backward, while it looks for the next/previous matching date.
  • Whenever max_years_between_matches is not given (i.e. the argument keeps its default), the search window that takes effect defaults implicitly to 1 year.
  • If, on the other hand, max_years_between_matches is given, the search window is defined by that value (in years).
Generator methods

Two generator methods are required:

croniter_instance.all_next(ret_type=...)
croniter_instance.all_prev(ret_type=...)
  • Starting from the start and moving forward in time, all_next() yields matching dates one after another.
  • Starting from the start and moving backward in time, all_prev() yields matching dates one after another.
  • An optional ret_type argument is accepted by both; it decides the type of the values yielded. Passing datetime makes the yielded values datetime.datetime instances.

Behavior Requirements

CroniterBadDateError is the exception type at issue here; it can be imported from the croniter package.

Consider a generator (all_next() or all_prev()) that sets out to produce its next value while no matching date is located within the search window; the behavior that follows is decided by the manner in which the search window was established:

  1. Implicit window (the default; max_years_between_matches not provided): CroniterBadDateError must be raised by the generator. This informs the caller that the search ran into the implicit limit without a match being found.

  2. Explicit window (max_years_between_matches provided): What the generator must not do here is raise CroniterBadDateError. Rather, iteration comes to an end — a request for the next value raises StopIteration (i.e. the generator is exhausted). Since the caller gave explicit agreement to a maximum gap, using up that range without finding a match is a normal termination rather than an error.

If a matching date is found inside the search window, the generator yields it as usual.

Worked Examples

Take the cron expression "0 13 8 1,4,7,10 wed" in combination with day_or=False:

  • Forward, starting from datetime(2020, 9, 24):

    • max_years_between_matches left out: calling next() on all_next() for the first time raises CroniterBadDateError.
    • max_years_between_matches=5 supplied: the value yielded first (as datetime) is datetime(2025, 1, 8, 13).
    • max_years_between_matches=2 supplied: the first next() raises StopIteration.

  • Reverse, starting from datetime(2025, 1, 8):

    • max_years_between_matches left out: calling next() on all_prev() for the first time raises CroniterBadDateError.
    • max_years_between_matches=5 supplied: the value yielded first (as datetime) is datetime(2020, 7, 8, 13).
    • max_years_between_matches=2 supplied: the first next() raises StopIteration.

Constraints

  • get_next() and get_prev() — the single-step methods — must keep their behavior unchanged; the newly introduced "stop instead of raise" logic comes into play only on the all_next() / all_prev() generator interfaces.
  • For callers that do not pass max_years_between_matches, the behavior that already exists must be preserved (an implicit window with a 1-year default, and CroniterBadDateError raised when no match can be found).

Task Specification: Allowing l as an upper bound in cron range expressions

Background

The croniter Python library is to be modified so that l can serve as the upper endpoint of a cron-field range. The package is importable under the name croniter and supplies the croniter class for parsing cron expressions and computing matching datetimes.

Public API

The existing API listed here must remain importable and callable:

  • croniter(expr, start_time, ret_type=..., day_or=...)
    • The cron expression string is supplied as the first positional argument.
    • A datetime may be passed as the second positional argument.
    • The result type is controlled by the ret_type keyword; for instance, ret_type=datetime returns datetime values.
    • get_next() returns the next matching time after the configured start time; when no return type is passed directly, it uses the ret_type configured on the constructor.
  • croniter_range
  • CroniterBadDateError
  • CroniterBadCronError
  • CroniterNotAlphaError

Outside the change described below, these names together with their existing behavior must remain unchanged.

Required behavior

l as an endpoint of a range

Expressions using the cron range forms <low>-l and <low>-l/<step> must be accepted. The literal l, a lowercase L, denotes the maximum legal value of the field in which it appears. Leaving out /step gives the usual range behavior, which is equivalent to a step of 1.

All cron range rules that already exist continue to apply, including inclusive range endpoints, field-specific value normalization, and optional steps.

Step alignment when the lower endpoint lies below the field minimum

If the field's existing normalization maps or clamps <low> to its minimum, the step sequence remains aligned to the lower endpoint as written. The normalization of that endpoint must not rebase or shift the rest of the stepped sequence.

Take the day-of-month field, whose legal numeric range is 1 through 31: here 0-l/8 consequently has step positions 0, 8, 16, 24 up to the maximum endpoint of 31. When the existing day-of-month normalization is applied to the out-of-range lower position, 0 is mapped to 1, so the effective matching day set is:

1, 8, 16, 24

It must not be interpreted as a progression anchored anew at day 1 (1, 9, 17, 25).

Worked example

Take this expression:

35 * 0-l/8 * *
  • The minute value is 35.
  • The hour field is a wildcard.
  • For day-of-month, the values are 1, 8, 16, and 24.
  • The month and the day-of-week are wildcards.

If the start time is midnight on a day in January 2020, constructing the iterator with ret_type=datetime and calling get_next() must produce the following results:

Start day (January 2020) Next match
1 2020-01-01 00:35:00
2–8 2020-01-08 00:35:00
9–16 2020-01-16 00:35:00
17–24 2020-01-24 00:35:00
25–30 2020-02-01 00:35:00

The table covers every individual start day from January 1 through January 30, inclusive. Specifically:

  • With a midnight start on a matching day, the iterator can return 00:35 on that same day because the occurrence is later than the start instant.
  • Since day 8 is a matching day, starts at midnight from January 2 through January 8 next match on January 8.
  • Day 25 is not a matching day. Once January 24 is past, the schedule rolls over into the next month and next matches on February 1.

Compatibility and scope

The only item to be added or corrected is support for l as the upper endpoint of a range, including its interaction with a step and with existing lower-value normalization. Standalone l behavior must remain unchanged, as must ordinary numeric ranges and steps, iteration semantics, return-type handling, date rollover, timezone behavior, exceptions, and all other existing cron parsing and scheduling behavior.

03 Supporting Sparse Cron Matches That Span Multiple Years 745 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Supporting Sparse Cron Matches That Span Multiple Years

Overview

Extend the croniter library (module croniter, importable via from croniter import croniter, croniter_range, CroniterBadDateError) so that it supports iterating over cron schedules whose consecutive matching dates may be more than one year apart (e.g. quarterly patterns that match only in certain months/day-of-week combinations, leaving some years with no match at all).

Background: Current Behavior

By default, croniter searches for the next/previous matching datetime using a lookahead bounded to one year. If a pattern is sparse enough that the window holds no match, the search fails. This one-year default must be kept intact.

Changes Required

1. New constructor parameter max_years_between_matches

Extend the croniter(...) constructor with a new keyword argument, max_years_between_matches.

  • It gives the maximum number of years to search forward or backward when looking for the next/previous matching datetime.
  • Its default value matches the existing one-year search behavior (i.e., when the argument is not provided, behavior remains unchanged from before this task).
  • When a larger value is provided, the search window widens accordingly, so that matches lying several years away from the starting point can be found.

Example: for the cron expression "0 13 8 1,4,7,10 wed" (day-of-week and day-of-month combined as AND, i.e. day_or=False) and a start of datetime(2020, 9, 24), the next match is datetime(2025, 1, 8, 13), more than four years later. This match can only be reached if the search window is at least 5 years.

2. get_next() / get_prev() behavior

These methods retain their existing behavior: when no matching datetime is found within the configured search window, they raise CroniterBadDateError.

  • Given the default (one-year) window and a sparse pattern that has no match within a year, get_next() raises CroniterBadDateError.
  • If max_years_between_matches is large enough to reach the next match, get_next(datetime) returns the correct matching datetime object.
3. all_next() / all_prev() generator behavior

When no further match is found within the search window, these generator interfaces must distinguish between two cases:

  • Default window (parameter not provided): raise CroniterBadDateError (just as get_next()/get_prev() do). This preserves backward compatibility — the caller is informed that the implicit one-year limit was reached.
  • Explicit window (max_years_between_matches provided): do NOT raise CroniterBadDateError; instead, simply end iteration (raising StopIteration from the generator). Rationale: if the caller explicitly specified the maximum gap, then reaching that limit is an expected termination condition, not an error.

In concrete terms, for the cron "0 13 8 1,4,7,10 wed" with day_or=False:

  • Forward from datetime(2020, 9, 24):

    • Without max_years_between_matches: all_next() → the first next(...) raises CroniterBadDateError.
    • max_years_between_matches=5: all_next(datetime) → the first next(...) yields datetime(2025, 1, 8, 13).
    • max_years_between_matches=2: all_next(datetime) → the first next(...) raises StopIteration (the next match lies beyond 2 years, so iteration ends cleanly).

  • Reverse from datetime(2025, 1, 8):

    • Without max_years_between_matches: all_prev() → the first next(...) raises CroniterBadDateError.
    • max_years_between_matches=5: all_prev(datetime) → the first next(...) yields datetime(2020, 7, 8, 13).
    • max_years_between_matches=2: all_prev() → the first next(...) raises StopIteration.
4. Automatic window sizing for croniter_range()

Adjust croniter_range(start, end, expr_format, ...) so that it automatically determines a suitable max_years_between_matches from the span between start and end. Consequently, croniter_range() must never expose a CroniterBadDateError to its caller — the only possible outcomes are that it yields the matches that fall within the [start, end] range or that it produces no results.

With the cron "0 13 8 1,4,7,10 wed" set to day_or=False, the behavior is as follows:

  • croniter_range(datetime(2020, 1, 1), datetime(2020, 12, 31), cron, day_or=False) yields exactly three datetimes, in this order:
    • datetime(2020, 1, 8, 13)
    • datetime(2020, 4, 8, 13)
    • datetime(2020, 7, 8, 13)
  • croniter_range(datetime(2020, 9, 30), datetime(2020, 10, 30), cron, day_or=False) yields no datetimes (an empty result), even though this span contains no matching date and the underlying pattern is sparse.

Summary of the Public API

  • croniter(expr_format, start_time=..., ..., day_or=..., max_years_between_matches=<default>) — a new keyword parameter has been added; all existing parameters and behavior remain unchanged.
  • croniter.get_next(ret_type=...), croniter.get_prev(ret_type=...) — behavior unchanged (they still raise CroniterBadDateError when there is no match within the window).
  • croniter.all_next(ret_type=...), croniter.all_prev(ret_type=...) — generators whose termination behavior depends on whether max_years_between_matches was supplied explicitly (see section 3).
  • croniter_range(start, end, expr_format, ..., day_or=...) — automatically sizes the search window from start/end; it never raises CroniterBadDateError.
  • CroniterBadDateError — can be imported from the croniter package.

All datetime return values are naive datetime objects that match the calendar values shown above.

Background

The croniter library parses cron expressions and makes the croniter class available in this way:

from croniter import croniter

A croniter instance is built by passing a cron expression as the first argument; a start time and the other constructor options that are already supported may also be supplied. As part of construction, the normalized expansion of the expression is exposed through the public expanded attribute.

The expanded attribute

expanded is a list whose elements line up with the cron fields in expression order:

  • index 0: the minute
  • index 1: the hour
  • index 2: the day of month
  • index 3: the month
  • index 4: the day of week
  • index 5: the second, when a six-field expression is provided

Each element is itself a list that holds the normalized values or special tokens generated by expanding that field. The existing normalization continues to apply; for instance, an uppercase L appearing as a standalone last-day marker is exposed as lowercase "l".

Mandatory canonical ordering

Every inner list that expanded contains must be returned in a deterministic canonical order, regardless of the order in which comma-separated terms, ranges, or other supported syntax appeared in the input. The ordering is determined by what the special tokens mean, not merely by whether a value is a string.

The ordering is:

  1. The wildcard token "*" is placed before integer values.
  2. Integer values are sorted numerically in ascending order.
  3. The last-day token "l" is placed after integer values.

Consequently, when all three categories occur, their relative order is "*", then ascending integers, then "l". A blanket rule that places every string before every integer is not valid, since "*" and "l" carry different ranks. Likewise, values must not be sorted lexicographically according to their string representations.

The sorting is performed on the normalized expanded values. It must continue to work for ordinary numeric fields, expanded ranges, and fields that contain a supported mixture of special tokens and integers.

Examples that are required

The observable results below are required:

croniter("0 8,22,10,23 0 0 0").expanded[1]
# [8, 10, 22, 23]

croniter("0 0 25-L 0 0").expanded[2]
# [25, 26, 27, 28, 29, 30, 31]

croniter("1 1 7,14,21,L * *").expanded[2]
# [7, 14, 21, "l"]

croniter("0 0 * * *,sat#3").expanded[4]
# ["*", 6]

These examples demonstrate that:

  • The order in which numbers appear in the input does not affect the output order.
  • A day-of-month range whose end is L expands to ascending concrete day numbers through 31.
  • A standalone L is normalized to "l" and comes after the numeric day values.
  • In a mixed day-of-week expansion, a wildcard comes before the normalized integer weekday value.

Requirements for compatibility

All existing behavior for cron parsing, validation, normalization, and scheduling must be preserved. Specifically:

  • Handling of five-field and six-field expressions must remain compatible.
  • The supported ranges, steps, comma-separated values, alphabetic month and weekday names, last-day syntax, and nth-weekday syntax must retain their existing meanings.
  • Existing deduplication of values that are repeated or overlap must remain intact.
  • The existing conversion of a complete field domain into the wildcard representation ["*"] must remain intact.
  • The ordering change must not alter the dates that iteration produces, nor the behavior of other public operations.
  • The existing public constructor options and public APIs must remain compatible.

The behavioral change is limited in scope to the consistent canonical ordering of each field list exposed through expanded.

Constraint on dependencies

The ordering described here must not require natsort or any other third-party sorting package. Solely for this sorting behavior, the package must neither import a third-party library nor declare a runtime dependency on one, and it must remain importable and usable when such a package is absent. Sorting facilities from the standard library are sufficient. Existing dependencies that are unrelated to sorting lie outside this change.

  • Constructor: croniter(expr_format, start_time=...), where all other existing optional arguments remain supported
  • Attribute: croniter_instance.expanded, a list ordered by field, made up of normalized expansion lists, each canonically ordered as specified above

Task Description

The croniter library is the focus here: it parses cron expressions and determines the datetimes that match them, relative to a base time.

Public Interface

From the croniter package, the croniter class is available for import:

from croniter import croniter

Construction follows this pattern:

croniter(expr_format, start_time)

Here expr_format is a cron expression string in the standard 5-field format, and start_time is a datetime.datetime instance.

Each instance exposes:

get_prev(ret_type)

It returns the most recent datetime matching the cron expression that lies strictly before the current position, in the form of an instance of the type supplied via ret_type (e.g. datetime.datetime).

Required Behavior — Defect Fix

A defect is present in the backward search (get_prev) for the situation in which the cron expression restricts the schedule to one specific day-of-month within one specific month, while the candidate month that immediately precedes does not contain that day-of-month.

Instead of failing or generating an incorrect result, the search must skip correctly over months/periods that cannot contain the required day and must keep searching backward until it finds a valid matching datetime.

Concrete scenario that must work

Take the cron expression '0 6 30 3 *' (minute 0, hour 6, day-of-month 30, month March, any day-of-week) together with a base time of datetime(2021, 3, 30, 4, 0):

  • Calling get_prev(datetime) must return the datetime for March 30 06:00 in the previous year (2020), that is, year 2020, month 3, day 30, hour 6, minute 0.

Since the base time (March 30, 2021 at 04:00) lies before 06:00 on that same day, the most recent prior match falls not on the base date itself but on March 30 of the preceding year.

Reaching this result is what correct backward traversal must accomplish, without being derailed by intervening months (such as February) that do not have a 30th day.

Summary

Add deterministic hashed (H) and per-expansion random (R) cron-field expressions to croniter. The standard @ schedule aliases are also to be supported, with hash-distributed schedules when a hash_id is supplied. Existing behavior for cron parsing, iteration, date/time, timezone, and ranges must remain compatible.

Public API

The following names remain importable from the top-level package:

from croniter import croniter, CroniterNotAlphaError
Constructor of croniter

An optional hash_id argument is added to the constructor, leaving the behavior of the existing arguments unchanged:

croniter(
    expr_format,
    start_time=None,
    ret_type=float,
    day_or=True,
    max_years_between_matches=None,
    is_prev=False,
    hash_id=None,
)

The hash_id argument accepts:

  • None, which means that no deterministic hash seed is available;
  • a str, which is encoded as UTF-8 before hashing; or
  • a bytes object, which is used unchanged.

A value of any other type must raise TypeError. This contract on types holds whenever the argument is supplied, and not only when some expression ends up using H.

Instances keep exposing get_next(ret_type). When datetime is passed, a datetime is returned; when float is passed, a POSIX timestamp float is returned. Successive calls move forward through the occurrences of the one schedule that was established when the expression was expanded.

croniter.expand

The class method is to be widened so that it accepts arbitrary additional positional and keyword arguments:

@classmethod
def expand(cls, expr_format, *args, **kwargs):
    ...

All of those arguments must be forwarded unchanged to the internal expansion operation to which it delegates. Calls that use the existing form expand(expr_format) must continue to work. This also acts as a subclass compatibility contract: a subclass may override the widened signature, perform its own validation, and delegate with croniter.expand(expr_format, *args, **kwargs). Such a subclass must continue to work both when it is instantiated directly and when it is supplied to the existing range-generation utilities. Expansion driven by the constructor must pass the hash context through this extensible call path.

Layout and bounds of cron fields

Expressions keep the existing five-field order, with an optional sixth field for seconds at the end:

  1. minute: 0..59
  2. hour: 0..23
  3. day of month: 1..31
  4. month: 1..12
  5. day of week: 0..7, where both 0 and 7 denote Sunday
  6. second, when present: 0..59

In special-token range forms, all bounds are inclusive. Ordinary calendar validity still applies: for instance, a selected day 31 simply has no occurrence in a month that lacks that date. Five-field expressions retain the existing seconds behavior; the explicit seconds value that the aliases described below generate comes from their six-field hashed forms.

Hashed expressions (H)

An H value is resolved deterministically from hash_id. A non-None hash seed is required, and it must never fall back to random selection. An H that stays unresolved because no seed is present is invalid under normal alphabetic-token handling and raises CroniterNotAlphaError.

The supported forms are:

  • H: a single deterministic value over the field's full bounds;
  • H(low-high): a single deterministic value inside the inclusive subrange;
  • H/step: a deterministic anchor at the start, followed by values every step through the field's upper bound;
  • H(low-high)/step: the same stepped behavior, restricted to the stated subrange.

For the lifetime of the expanded schedule, the selected value or stepped anchor is fixed.

Exact deterministic resolution procedure

The following reproducible procedure must be used for hash resolution. It is part of the public schedule contract.

  1. A string seed is converted with hash_id.encode("UTF-8"); a bytes seed is used unchanged.

  2. Compute this unsigned CRC-32 value:

    crc = binascii.crc32(hash_id_bytes) & 0xFFFFFFFF

  3. The zero-based field index i is assigned in cron order: minute 0, hour 1, day of month 2, month 3, day of week 4, and second 5.

  4. The hash word for that field is obtained as crc >> i.

  5. For an unstepped field whose inclusive lower and upper bounds are a and b, resolve it as:

    a + ((crc >> i) % (b - a + 1))

    H takes the full field bounds; H(a-b) takes the explicit bounds.

  6. For a stepped form with a step of s, choose the anchor as:

    anchor = a + ((crc >> i) % (s + 1))

    and expand to anchor, anchor + s, anchor + 2s, ... for as long as the values remain at or below b. With H/s, a and b are the full field bounds; with H(a-b)/s, they are the explicit bounds. Thus the anchor offset is picked from 0..s inclusively, rather than from a half-open 0..s-1 interval.

Nothing is concatenated with the seed: no expression text, start time, epoch, field name, or additional salt. Separation of fields comes solely from the right shift by the field index; expression syntax affects the result by way of the applicable field/range bounds. Consequently, expanded hashed values cannot be changed by a change of start time, whereas a change of expression can change its bounds or which fields are hashed. CRC collisions and modulo collisions can happen, so when hash_id is changed, the schedule is expected to change generally, but not invariably.

As a reference point, the UTF-8 bytes for "hello" have unsigned CRC-32 907060870. The formulas above produce minute 10, hour 11, day of month 1, month 9, day of week 0 when the 0..7 range is used, and second 32. The same formulas also give hour anchor 3 for H/3, minute anchor 31 for H(30-59)/10, and hour 2 for H(0-2).

Random expressions (R)

R works by random selection and does not require hash_id. It supports these analogous forms:

  • R;
  • R(low-high);
  • R/step; and
  • R(low-high)/step.

Unstepped forms choose a value within the relevant inclusive bounds. Stepped forms choose a random anchor with the same bounds and anchor-range semantics as their H counterparts, and then repeat by the requested step through the upper bound. Distinct random fields may be selected independently.

The random choices are made as part of expression expansion, not on every occurrence lookup. Therefore the value or anchor selected for each R field stays fixed for the lifetime of that expanded schedule, so repeated get_next calls iterate over one consistent cron schedule. Different constructions need not choose the same values, and no hash_id is needed.

Aliases written as keywords

These aliases are to be supported with their conventional non-hashed meanings when no hash_id is supplied:

Alias Conventional expression
@midnight 0 0 * * *
@hourly 0 * * * *
@daily 0 0 * * *
@weekly 0 0 * * 0
@monthly 0 0 1 * *
@yearly 0 0 1 1 *
@annually 0 0 1 1 *

When hash_id is supplied, these six-field hash-distributed equivalents are used:

Alias Hashed equivalent Meaning
@midnight H H(0-2) * * * H Once daily, with the hour distributed within 0..2
@hourly H * * * * H Once each hour
@daily H H * * * H Once daily
@weekly H H * * H H Once weekly
@monthly H H H * * H Once monthly
@yearly H H H H * H Once yearly
@annually H H H H * H Exactly the same schedule as @yearly

The hashed aliases contain an explicit hashed seconds component. Therefore, under hashing, @midnight is intentionally not exact midnight: it may occur up to roughly three hours after midnight. Across successive occurrences, @annually and @yearly must remain equal for the same seed and start time.

Alphabetic tokens that are invalid

Alphabetic cron syntax that is currently valid remains valid. Any other alphabetic field token, meaning one that is neither valid standard cron syntax nor a supported H/R form, must raise the top-level CroniterNotAlphaError. As an example:

croniter("X X * * *", start_time, hash_id="hello")

must raise CroniterNotAlphaError. Ordinary malformed ranges, steps, and out-of-bounds values continue to use the library's existing cron-validation behavior.

Requirements around determinism and iteration

  • Across processes and runs, the same expression and hash_id must expand to the same hashed schedule.
  • Both seeds given as strings and seeds given as bytes must be stable according to the exact CRC-32 procedure above.
  • Which matching occurrence is next is affected by a start epoch, but a start epoch never feeds into hash resolution.
  • A seed that differs should generally distribute the schedule differently, subject to possible CRC/modulo collisions.
  • During successive calls on one instance, the concrete schedule selected for every H or R field remains unchanged.
  • After special fields have been expanded, the existing datetime and float return modes continue to behave identically.
