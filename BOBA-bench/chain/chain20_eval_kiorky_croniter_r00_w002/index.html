01 Modify the croniter class to change how its generator-based iteration methods behave when a matching date cannot be found within the searched time range,… 484 words · source specification

Overview

Modify the croniter class to change how its generator-based iteration methods behave when a matching date cannot be found within the searched time range, depending on whether the caller explicitly specified a maximum gap between matches.

Public API

The relevant class is croniter, importable as:

from croniter import croniter
Constructor

The constructor must accept a keyword argument max_years_between_matches (in addition to its existing parameters such as the cron expression string, a start datetime, and day_or):

croniter(expr_format, start_time=..., day_or=..., max_years_between_matches=None)
  • max_years_between_matches specifies the maximum number of years to search forward or backward when looking for the next/previous matching date.
  • When max_years_between_matches is not provided (i.e. left at its default), the effective search window is an implicit default of 1 year.
  • When max_years_between_matches is provided, that value (in years) defines the search window.
Generator methods

Two generator methods must exist:

croniter_instance.all_next(ret_type=...)
croniter_instance.all_prev(ret_type=...)
  • all_next() yields successive matching dates moving forward in time from the start.
  • all_prev() yields successive matching dates moving backward in time from the start.
  • Both accept an optional ret_type argument controlling the type of the yielded values. When datetime is passed, yielded values are datetime.datetime instances.

Required Behavior

The exception type involved is CroniterBadDateError, importable from the croniter package.

When a generator (all_next() or all_prev()) attempts to produce the next value and no matching date is found within the search window, the behavior depends on how the search window was determined:

  1. Implicit window (default, max_years_between_matches not provided): The generator must raise CroniterBadDateError. The caller is notified that the search hit the implicit limit without finding a match.

  2. Explicit window (max_years_between_matches provided): The generator must not raise CroniterBadDateError. Instead, iteration simply ends — requesting the next value raises StopIteration (i.e. the generator is exhausted). The caller explicitly agreed to a maximum gap, so exhausting that range without a match is a normal termination, not an error.

When a matching date is found within the search window, the generator yields it normally.

Concrete Examples

Using the cron expression "0 13 8 1,4,7,10 wed" with day_or=False:

  • Forward, start datetime(2020, 9, 24):

    • With no max_years_between_matches: first next() on all_next() raises CroniterBadDateError.
    • With max_years_between_matches=5: first yielded value (as datetime) is datetime(2025, 1, 8, 13).
    • With max_years_between_matches=2: first next() raises StopIteration.

  • Reverse, start datetime(2025, 1, 8):

    • With no max_years_between_matches: first next() on all_prev() raises CroniterBadDateError.
    • With max_years_between_matches=5: first yielded value (as datetime) is datetime(2020, 7, 8, 13).
    • With max_years_between_matches=2: first next() raises StopIteration.

Constraints

  • The single-step methods get_next() and get_prev() must remain unchanged in behavior; the new "stop instead of raise" logic applies only to the all_next() / all_prev() generator interfaces.
  • Existing behavior for callers that do not pass max_years_between_matches must be preserved (default 1-year implicit window, raising CroniterBadDateError on failure to find a match).

Context

Public API

The following existing API must remain importable and callable:

  • croniter(expr, start_time, ret_type=..., day_or=...)
    • The first positional argument is a cron expression string.
    • The second positional argument may be a datetime.
    • The ret_type keyword controls the result type; for example, ret_type=datetime returns datetime values.
    • get_next() returns the next matching time after the configured start time and uses the constructor's configured ret_type when no return type is passed directly.
  • croniter_range
  • CroniterBadDateError
  • CroniterBadCronError
  • CroniterNotAlphaError

These names and their existing behavior outside the change described below must remain unchanged.

Required behavior

l as a range endpoint

Cron range forms <low>-l and <low>-l/<step> must be accepted. The literal l is lowercase L and denotes the maximum legal value of the field in which it appears. Omitting /step has the usual range behavior, equivalent to a step of 1.

All existing cron range rules continue to apply, including inclusive range endpoints, field-specific value normalization, and optional steps.

Step alignment when the lower endpoint is below the field minimum

If <low> is a value that the field's existing normalization maps or clamps to its minimum, the step sequence remains aligned to the lower endpoint as written. Normalizing that endpoint must not rebase or shift the rest of the stepped sequence.

For the day-of-month field, whose legal numeric range is 1 through 31, 0-l/8 therefore has step positions 0, 8, 16, 24 up to the maximum endpoint of 31. Applying the existing day-of-month normalization to the out-of-range lower position maps 0 to 1, so the effective matching day set is:

1, 8, 16, 24

It must not be interpreted as a progression newly anchored at day 1 (1, 9, 17, 25).

Concrete example

For this expression:

35 * 0-l/8 * *
  • The minute is 35.
  • The hour is a wildcard.
  • The day-of-month values are 1, 8, 16, and 24.
  • The month and day-of-week are wildcards.

Given a start time at midnight on a day in January 2020, constructing the iterator with ret_type=datetime and calling get_next() must produce the following results:

Start day (January 2020) Next match
1 2020-01-01 00:35:00
2–8 2020-01-08 00:35:00
9–16 2020-01-16 00:35:00
17–24 2020-01-24 00:35:00
25–30 2020-02-01 00:35:00

This table applies to every individual start day from January 1 through January 30, inclusive. In particular:

  • A midnight start on a matching day can return 00:35 on that same day because the occurrence is later than the start instant.
  • Day 8 is a matching day, so starts at midnight from January 2 through January 8 next match on January 8.
  • Day 25 is not a matching day. Once January 24 has passed, the schedule rolls into the next month and next matches on February 1.

Compatibility and scope

Only support for l as the upper endpoint of a range, including its interaction with a step and existing lower-value normalization, is to be added or corrected. Standalone l behavior, ordinary numeric ranges and steps, iteration semantics, return-type handling, date rollover, timezone behavior, exceptions, and all other existing cron parsing and scheduling behavior must remain unchanged.

03 Support Sparse Cron Matches Across Multiple Years 708 words · source specification

Task Specification: Support Sparse Cron Matches Across Multiple Years

Overview

Modify the croniter library (module croniter, importable via from croniter import croniter, croniter_range, CroniterBadDateError) to support iterating over cron schedules where consecutive matching dates may be separated by more than one year (e.g. quarterly patterns that only match in certain months/day-of-week combinations, so that some years produce no match at all).

Background Behavior

By default, croniter searches for the next/previous matching datetime within a bounded lookahead of one year. When a pattern is sparse enough that no match exists within that window, the search fails. This one-year default must be preserved.

Required Changes

1. New constructor parameter: max_years_between_matches

Add a new keyword argument max_years_between_matches to the croniter(...) constructor.

  • It specifies the maximum number of years to search forward or backward when looking for the next/previous matching datetime.
  • Its default value corresponds to the existing one-year search behavior (i.e., when not provided, behavior is unchanged from before this task).
  • When provided with a larger value, the search window is widened accordingly, allowing matches that are several years away from the starting point to be found.

Example: with the cron expression "0 13 8 1,4,7,10 wed" (day-of-week and day-of-month treated as AND, i.e. day_or=False), starting from datetime(2020, 9, 24), the next match is datetime(2025, 1, 8, 13), which is more than four years later. This match is only reachable if the search window is at least 5 years.

2. Behavior of get_next() / get_prev()

These methods keep their existing behavior of raising CroniterBadDateError when no matching datetime can be found within the configured search window.

  • With the default (one-year) window and a sparse pattern that has no match within a year, get_next() raises CroniterBadDateError.
  • With max_years_between_matches large enough to reach the next match, get_next(datetime) returns the correct matching datetime object.
3. Behavior of all_next() / all_prev() generators

These generator interfaces must distinguish between two cases when no further match is found within the search window:

  • Default window (parameter not provided): raise CroniterBadDateError (as get_next()/get_prev() do). This preserves backward compatibility — the caller is notified that the implicit one-year limit was reached.
  • Explicit window (max_years_between_matches provided): do NOT raise CroniterBadDateError. Instead, simply stop iteration (raise StopIteration from the generator). The rationale: if the caller explicitly specified the maximum gap, then hitting that limit is an expected termination condition, not an error.

Concretely, for the cron "0 13 8 1,4,7,10 wed" with day_or=False:

  • Forward from datetime(2020, 9, 24):

    • No max_years_between_matches: all_next() → first next(...) raises CroniterBadDateError.
    • max_years_between_matches=5: all_next(datetime) → first next(...) yields datetime(2025, 1, 8, 13).
    • max_years_between_matches=2: all_next(datetime) → first next(...) raises StopIteration (the next match is beyond 2 years, so iteration ends cleanly).

  • Reverse from datetime(2025, 1, 8):

    • No max_years_between_matches: all_prev() → first next(...) raises CroniterBadDateError.
    • max_years_between_matches=5: all_prev(datetime) → first next(...) yields datetime(2020, 7, 8, 13).
    • max_years_between_matches=2: all_prev() → first next(...) raises StopIteration.
4. croniter_range() automatic window sizing

Update croniter_range(start, end, expr_format, ...) so that it automatically derives an appropriate max_years_between_matches from the span between start and end. As a result, croniter_range() must never surface a CroniterBadDateError to its caller — it either yields the matches that fall within the [start, end] range or produces no results.

Behavior for the cron "0 13 8 1,4,7,10 wed" with day_or=False:

  • croniter_range(datetime(2020, 1, 1), datetime(2020, 12, 31), cron, day_or=False) yields exactly three datetimes, in order:
    • datetime(2020, 1, 8, 13)
    • datetime(2020, 4, 8, 13)
    • datetime(2020, 7, 8, 13)
  • croniter_range(datetime(2020, 9, 30), datetime(2020, 10, 30), cron, day_or=False) yields no datetimes (empty result), even though this span contains no matching date and the underlying pattern is sparse.

Public API Summary

  • croniter(expr_format, start_time=..., ..., day_or=..., max_years_between_matches=<default>) — new keyword parameter added; all existing parameters and behavior unchanged.
  • croniter.get_next(ret_type=...), croniter.get_prev(ret_type=...) — unchanged behavior (still raise CroniterBadDateError when no match within window).
  • croniter.all_next(ret_type=...), croniter.all_prev(ret_type=...) — generators whose termination behavior depends on whether max_years_between_matches was explicitly given (see section 3).
  • croniter_range(start, end, expr_format, ..., day_or=...) — automatically sizes the search window from start/end; never raises CroniterBadDateError.
  • CroniterBadDateError — importable from the croniter package.

All datetime return values are naive datetime objects matching the calendar values shown above.

Context

The croniter library parses cron expressions and exposes the croniter class as follows:

The expanded attribute

expanded is a list whose elements correspond to the cron fields in expression order:

  • index 0: minute
  • index 1: hour
  • index 2: day of month
  • index 3: month
  • index 4: day of week
  • index 5: second, when a six-field expression is supplied

Each element is itself a list containing the normalized values or special tokens produced by expanding that field. Existing normalization remains in effect; for example, an uppercase L used as a standalone last-day marker is exposed as lowercase "l".

Required canonical ordering

Every inner list in expanded must be returned in a deterministic canonical order, regardless of the order in which comma-separated terms, ranges, or other supported syntax appeared in the input. Ordering is based on the meaning of special tokens, not merely on whether a value is a string.

The order is:

  1. The wildcard token "*" comes before integer values.
  2. Integer values are ordered numerically in ascending order.
  3. The last-day token "l" comes after integer values.

Thus, when all three categories occur, their relative order is "*", then ascending integers, then "l". A generic rule that puts every string before every integer is not valid, because "*" and "l" have different ranks. Likewise, values must not be ordered lexicographically by their string representations.

Sorting occurs on the normalized expanded values. It must continue to work for ordinary numeric fields, expanded ranges, and fields containing a supported mixture of special tokens and integers.

# [25, 26, 27, 28, 29, 30, 31]

croniter("1 1 7,14,21,L * *").expanded[2]

# ["*", 6]

These examples establish that:

  • Numeric input order does not affect output order.
  • A day-of-month range ending in L expands to ascending concrete day numbers through 31.

  • A wildcard in a mixed day-of-week expansion precedes the normalized integer weekday value.

All existing cron parsing, validation, normalization, and scheduling behavior must be preserved. In particular:

  • Five-field and six-field expression handling must remain compatible.

  • Existing deduplication of repeated or overlapping values must remain intact.
  • Existing conversion of a complete field domain to the wildcard representation ["*"] must remain intact.
  • The ordering change must not alter the dates produced by iteration or the behavior of other public operations.
  • Existing public constructor options and public APIs must remain compatible.

The scope of the behavioral change is the consistent canonical ordering of each field list exposed through expanded.

Dependency constraint

This ordering must not require natsort or any other third-party sorting package. The package must neither import nor declare a runtime dependency on a third-party library solely for this sorting behavior, and it must remain importable and usable when such a package is absent. Standard-library sorting facilities are sufficient. Existing dependencies unrelated to sorting are outside this change.

Public API summary

  • Module: croniter

  • Constructor: croniter(expr_format, start_time=...), with all other existing optional arguments remaining supported

It must forward all of those arguments unchanged to the internal expansion operation to which it delegates. Existing expand(expr_format) calls must continue to work. Such a subclass must continue to work when instantiated directly and when supplied to existing range-generation utilities. Constructor-driven expansion must pass the hash context through this extensible call path.

Cron field layout and bounds

Expressions use the existing five-field order, with an optional sixth seconds field at the end:

  1. minute: 0..59
  2. hour: 0..23
  3. day of month: 1..31
  4. month: 1..12
  5. day of week: 0..7, where both 0 and 7 denote Sunday
  6. second, when present: 0..59

All bounds in special-token range forms are inclusive. Ordinary calendar validity still applies: for example, a selected day 31 simply has no occurrence in a month that lacks that date. Five-field expressions retain the existing seconds behavior; the explicit seconds value generated by the aliases described below comes from their six-field hashed forms.

Hashed expressions (H)

H resolves deterministically from hash_id. It requires a non-None hash seed and must never fall back to random selection. An unresolved H without a seed is invalid under normal alphabetic-token handling and raises CroniterNotAlphaError.

Supported forms are:

  • H: one deterministic value over the field's full bounds;
  • H(low-high): one deterministic value in the inclusive subrange;
  • H/step: a deterministic starting anchor followed by values every step through the field's upper bound;
  • H(low-high)/step: the same stepped behavior confined to the stated subrange.

The selected value or stepped anchor is fixed for the expanded schedule's lifetime.

Exact deterministic resolution

Hash resolution must use the following reproducible procedure. It is part of the public schedule contract.

  1. Convert a string seed with hash_id.encode("UTF-8"); use a bytes seed unchanged.

  2. Compute the unsigned CRC-32 value:

    crc = binascii.crc32(hash_id_bytes) & 0xFFFFFFFF

  3. Assign the zero-based field index i in cron order: minute 0, hour 1, day of month 2, month 3, day of week 4, and second 5.

  4. Obtain that field's hash word as crc >> i.

  5. For an unstepped field with inclusive lower and upper bounds a and b, resolve it as:

    a + ((crc >> i) % (b - a + 1))

    H uses the full field bounds; H(a-b) uses the explicit bounds.

  6. For a stepped form with step s, choose its anchor as:

    anchor = a + ((crc >> i) % (s + 1))

    and expand to anchor, anchor + s, anchor + 2s, ... while values remain at or below b. For H/s, a and b are the full field bounds; for H(a-b)/s, they are the explicit bounds. Thus the anchor offset is selected from 0..s inclusively, rather than from a half-open 0..s-1 interval.

No expression text, start time, epoch, field name, or additional salt is concatenated with the seed. Field separation comes solely from the right shift by the field index; expression syntax affects the result through the applicable field/range bounds. Consequently, changing the start time cannot change expanded hashed values, while changing the expression can change its bounds or which fields are hashed. CRC collisions and modulo collisions are possible, so a changed hash_id is expected to generally, but not invariably, change a schedule.

For reference, the UTF-8 bytes for "hello" have unsigned CRC-32 907060870. The formulas above produce minute 10, hour 11, day of month 1, month 9, day of week 0 when using the 0..7 range, and second 32. They also produce hour anchor 3 for H/3, minute anchor 31 for H(30-59)/10, and hour 2 for H(0-2).

Random expressions (R)

R uses random selection and does not require hash_id. It supports the analogous forms:

  • R;
  • R(low-high);
  • R/step; and
  • R(low-high)/step.

Unstepped forms choose a value in the relevant inclusive bounds. Stepped forms choose a random anchor using the same bounds and anchor-range semantics as their H counterparts, then repeat by the requested step through the upper bound. Separate random fields may be selected independently.

Random choices are made as part of expression expansion, not on every occurrence lookup. Each R field's selected value or anchor therefore remains fixed for the lifetime of that expanded schedule, so repeated get_next calls iterate over one consistent cron schedule. Different constructions need not choose the same values, and no hash_id is needed.

Keyword aliases

Support these aliases with their conventional non-hashed meanings when no hash_id is supplied:

Alias Conventional expression
@midnight 0 0 * * *
@hourly 0 * * * *
@daily 0 0 * * *
@weekly 0 0 * * 0
@monthly 0 0 1 * *
@yearly 0 0 1 1 *
@annually 0 0 1 1 *

When hash_id is supplied, use these six-field hash-distributed equivalents:

Alias Hashed equivalent Meaning
@midnight H H(0-2) * * * H Once daily, with the hour distributed within 0..2
@hourly H * * * * H Once each hour
@daily H H * * * H Once daily
@weekly H H * * H H Once weekly
@monthly H H H * * H Once monthly
@yearly H H H H * H Once yearly
@annually H H H H * H Exactly the same schedule as @yearly

The hashed aliases include an explicit hashed seconds component. @midnight is therefore intentionally not exact midnight under hashing: it may occur up to roughly three hours after midnight. @annually and @yearly must remain equal across successive occurrences for the same seed and start time.

Invalid alphabetic tokens

Existing valid alphabetic cron syntax remains valid. Any other alphabetic field token that is neither valid standard cron syntax nor a supported H/R form must raise the top-level CroniterNotAlphaError. For example:

croniter("X X * * *", start_time, hash_id="hello")

must raise CroniterNotAlphaError. Normal malformed ranges, steps, and out-of-bounds values continue to use the library's existing cron-validation behavior.

Determinism and iteration requirements

  • The same expression and hash_id must expand to the same hashed schedule across processes and runs.
  • Both string and bytes seeds must be stable according to the exact CRC-32 procedure above.
  • A start epoch affects which matching occurrence is next, but never feeds into hash resolution.
  • A different seed should generally distribute the schedule differently, subject to possible CRC/modulo collisions.
  • The concrete schedule selected for every H or R field remains unchanged during successive calls on one instance.
  • Existing datetime and float return modes continue to behave identically after special fields have been expanded.

returns 1577877000.0; the following value is exactly 86400 seconds later.

Random-schedule examples

With start time 2020-01-01 00:00 and no hash seed:

  • For R R * * *, the first datetime result lies in the inclusive window from 2020-01-01 00:00 through 2020-01-02 00:00; the second lies from 2020-01-02 00:00 through 2020-01-03 00:00.
  • For R R R(10-20) * *, the first result lies from 2020-01-10 00:00 through 2020-01-21 00:00; the second lies from 2020-02-10 00:00 through 2020-02-21 00:00.

Backward compatibility and non-goals

  • All existing standard cron expressions and their expansion, validation, next/previous occurrence, day-of-month/day-of-week, seconds, timezone, DST, and return-type behavior must remain unchanged.
  • Supplying no hash_id to existing constructor calls must preserve their prior behavior.
  • The feature resolves special syntax into an ordinary fixed cron schedule; it must not re-randomize while iterating.
  • The hash is for deterministic distribution, not cryptographic security.
  • No change is required to existing range-generation semantics beyond preserving widened expand delegation for custom croniter subclasses.
