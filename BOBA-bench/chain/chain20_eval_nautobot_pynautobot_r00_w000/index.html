01 Handling Selection-Type Custom Fields in Record Serialization 711 words · rewritten by GPT-5.6-sol, reworded by GLM-5.3-Flash

Task Specification: Handling Selection-Type Custom Fields in Record Serialization

Background

API records are represented by record objects — for example, the objects returned by getattr(nb, <endpoint_name>).get(<id>). Such objects expose a mutable custom_fields dictionary together with a serialize() method that produces a plain dictionary suitable for sending back to the API.

Custom fields may hold simple scalar values, such as strings or numbers, or selection-type values. When the API returns a selection-type value, it does so as a dictionary containing both the selected value and its human-readable label:

{
    "value": <the selected value>,
    "label": <a human-readable label>
}

The read representation used by the API therefore differs from the write representation expected when a record is serialized.

Behavior Requirements

How custom fields are represented on a record

A record populated from an API response must expose its custom fields via its mutable custom_fields dictionary. Entries may include:

  • Scalar values, among them strings, numbers, and other non-selection values.
  • Selection-type dictionaries that contain "value" and "label".

Callers must remain able to modify individual entries directly, for example:

record.custom_fields["test_custom"] = "Testing"
Serializing records

Invoking record.serialize() with no required arguments must return a dictionary containing a "custom_fields" dictionary. Every custom-field entry must be serialized independently, as follows:

  • A custom-field value that is scalar must be returned unchanged.
  • A selection-type custom-field dictionary that contains "value" and "label" must be flattened to the contents of its "value" key. The serialized custom-field value must not contain the label or the enclosing selection dictionary. This holds even when the selected value is falsy, such as 0, False, an empty string, or None.

Flattening applies only to selection-type values inside custom_fields; it must not change how existing serialization behaves for record attributes unrelated to this change.

Detecting modifications and idempotent saves

The normalization of selection values must be consistent between the record's serialized output and the initial state the library uses to determine whether a record has changed. Even when its API response contains nested selection-type custom-field dictionaries, a record freshly retrieved from the API must be considered unmodified.

As a consequence:

  • Before any user modification, the record's current serialized state must compare equal to the initial state captured for it.
  • The existing change detection must report an untouched record as unchanged; where _compare() is used for this comparison, it must return True.
  • Invoking the existing idempotent save flow on such an untouched record must not issue an update merely because serialization flattened a selection value. Its behavior must stay the same as for any other unchanged record.
  • A real user change — including assigning a different scalar value to a custom field — must still be detected normally. Selection fields present alongside that changed field must still be flattened in the serialization that results.

In short, the nested read representation and the flattened write representation must not, by themselves, create a false modification.

Worked Example

Start from a freshly retrieved record whose custom_fields contains:

{
    "test_custom": "Hello",
    "test_selection": {"value": 2, "label": "second"}
}

the record must initially be treated as unchanged. If the caller then performs:

record.custom_fields["test_custom"] = "Testing"
serialized = record.serialize()

then:

serialized["custom_fields"] == {
    "test_custom": "Testing",
    "test_selection": 2
}

The plain string that was assigned remains unchanged, while the selection-type value is represented by its underlying value.

API Surface and Compatibility

Record objects that endpoint retrieval returns must continue to expose:

  • A mutable custom_fields dictionary attribute that is populated from the API response.
  • A serialize() method taking no required arguments, which returns a dictionary containing the normalized "custom_fields" mapping described above.
  • The existing modification-detection and save behavior, with selection flattening taken into account consistently.

The public access pattern that already exists stays the same: API/app objects expose endpoint attributes, and endpoint objects continue to provide .get(<id>). This task must not alter endpoint lookup, retrieval, record serialization unrelated to this change, or other existing public behavior.

Scope

The change that is required is limited to flattening selection-type custom fields from their value/label read representation to their underlying value in serialized output, while preserving scalar custom fields and ensuring that this representational conversion does not make untouched records appear modified.

Specification of the Task

Overview

The library you are working on is pynetbox, a Python client library for the NetBox API. The task is to fix a bug in how record objects detect changes to their fields; this bug affects idempotent save operations for records containing IP network values.

Background: Semantics of Record Saving

Record objects (obtained through endpoint accessors such as nb.prefixes.get(1)) expose a save() method. Calling save() must:

  • Compare the values currently held by the record's fields against the values the record originally held when it was fetched from the API.
  • If no fields have changed, save() must return a falsy value (specifically False) and must NOT carry out a meaningful update.
  • The comparison used for change detection must correctly recognize that an unmodified record is unchanged — that is, the values produced by re-serializing the object's current state must be the same as the values originally received.

The Bug That Needs Fixing

Some fields of a record represent IP networks and are held internally as netaddr.IPNetwork objects. When the current state of a record is serialized for comparison against its original state, values that are IPNetwork objects were being handled incorrectly: rather than using the object's string representation (which matches the original API value, e.g. "10.1.2.0/24"), some other attribute was being used in its place, so the comparison never matched.

The behavior that is required:

  • When a record's fields are serialized for change comparison, any field whose value is a netaddr.IPNetwork object must be represented by its string form (equivalent to str(IPNetwork_instance)), which matches the string the API originally provided.
  • As a consequence, when a record is fetched from the API and immediately saved with no modifications, it must be detected as unchanged, and save() must return False.

A Concrete Scenario That Must Work

Consider a prefix record fetched from the API whose data includes a prefix field with the value "10.1.2.0/24":

  1. Fetch the record (using the prefixes endpoint get by id).
  2. Call .save() on the record without changing any fields.
  3. The call must return False, which indicates nothing was updated because the current serialized state matches the original state.

Contract for HTTP Response Objects

Request handling in the library consumes HTTP response objects. Response objects that are used for both GET and PUT requests must support:

  • An attribute .status_code (integer, e.g. 200).
  • An attribute .ok (boolean).
  • An attribute .content that holds the raw response body text.
  • A method .json() that parses the response body and returns the corresponding Python object (that is, json.loads of the body content).

Note: consuming responses must rely on .json() (and/or .content) rather than a .text attribute — do not depend on a .text attribute being present on response objects.

Scope

  • The public API surface remains unchanged: endpoint accessors that return record objects with a save() method (as in nb.prefixes.get(1).save()).
  • Do not change behavior beyond fixing the IPNetwork serialization in change detection and ensuring that response objects are consumed via .json()/.content as described.

04 Repair Prefix Idempotence in Record Serialization 527 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Repair Prefix Idempotence in Record Serialization

Background

You are working on pynetbox, a Python client library for the NetBox API. The objects used to represent records fetched from the API track their field values and support a .save() method that performs an HTTP PUT to update the record on the server.

The .save() method of a record must detect whether any of its fields have actually changed since the record was fetched. If nothing has changed, .save() must not send an update and must report that no change occurred. This is the idempotence guarantee.

The bug being fixed is that fields whose values are netaddr.IPNetwork objects are not compared correctly, so the change-detection logic always reports a difference even when the value is unchanged. Because of this, an otherwise-unchanged record reports a change and behaves as if it needs saving.

Required Behavior

Idempotent save() for prefix records

Suppose a record (e.g. a prefix object obtained via nb.prefixes.get(...)) is retrieved from the API and then .save() is called immediately without any of its fields being modified:

  • .save() MUST return a falsy value (specifically False).
  • No difference may be detected between the record's original state and its current serialized state.

For records whose fields include IP network values (such as a prefix field containing a CIDR string like "10.1.2.0/24"), this must hold. Such fields may be represented internally as netaddr.IPNetwork instances, but when the record's current state is compared against its original fetched state, these values must compare as equal to their original (unchanged) representation. For such a field, the correct serialized representation is its string form (e.g. "10.1.2.0/24"), not the numeric .value of the IP network object.

Serializing IP-network-typed fields

During the serialization of a record (in order to build the payload to compare against the original and/or send in a PUT), any field that is represented as a netaddr.IPNetwork must be serialized to its CIDR string representation. That is, for a value v that is an IPNetwork, the serialized value is str(v) (e.g. "10.1.2.0/24"), and this serialized string must itself be a valid input to netaddr.IPNetwork(...).

Removed Behavior

A custom __str__/__repr__ that returns a circuit's cid value must not be defined on the circuit record type. Instead of returning the circuit ID string (e.g. "123456"), a circuit record's string representation should follow the default/generic record string representation behavior. Remove any string-representation override that is circuit-specific.

Public API Surface

It must remain possible to import and call the following exactly as described:

  • pynetbox.prefixes.get(id) → returns a prefix record object.
  • The prefix record object exposes a .save() method that takes no required arguments and returns False when no fields have changed.
  • The serialization of a prefix record must render netaddr.IPNetwork fields as their CIDR string.

(Assume that nb is the top-level API entry point object that has already been used to access .prefixes and .circuits.)

Notes

  • Do not introduce a string representation that is circuit-specific.
  • The comparison used by .save() for change detection must treat an IPNetwork field equal to its unchanged original state, so that unmodified records are recognized as unchanged.

Record._diff() must report, as a set, the names of top-level fields that have changed.

Take a record containing fields such as:

{
    "id": 123,
    "custom_fields": {"foo": "bar"},
    "string_field": "foobar",
    "int_field": 1,
    "nested_dict": {"id": 222, "name": "bar"},
    "tags": ["foo", "bar"],
    "int_list": [123, 321, 231],
}

after:

record.tags.append("baz")
record.nested_dict = 1
record.string_field = "foobaz"

a call to record._diff() must return exactly:

{"tags", "nested_dict", "string_field"}

For tagged_vlans, appending an ID that an existing nested record already represents must not count as a change. As an example, if the original value contains a single VLAN dictionary with "id": 1, then:

record.tagged_vlans.append(1)

must leave record._diff() falsey.

Dictionary conversion

dict(record) must reproduce the structure of the original value, including:

  • scalar fields;
  • nested dictionaries;
  • integer lists;
  • empty lists;
  • tag lists;
  • lists of nested record dictionaries.

As an example, the nested records in a record_list must be converted back into dictionaries carrying their original fields and values, so the resulting dictionary compares equal to the dictionary passed to the constructor.

Specification of the Task

Summary

Introduce a version property on the main API object of the pynetbox package. The property's purpose is to determine the running version of the remote NetBox instance by inspecting the HTTP response headers that a request to the API root returns.

Public API

The pynetbox package must expose its API factory function in a way that makes the following possible:

import pynetbox
api = pynetbox.api(host)

Running this code creates an API object, with host being a base URL string supplied as the positional first argument.

The API object that results must expose a read-only property:

api.version

Behavior Requirements

Whenever api.version is accessed:

  1. The API object must issue an HTTP GET request to the API root URL (using requests.get).
  2. It must read the headers mapping of the response.
  3. If an "API-Version" key is present in the response headers, api.version must return its value (a string), exactly as provided in the header.
  4. If the response headers contain no "API-Version" key, api.version must return an empty string "".
Details and Edge Cases
  • The key used for the header lookup is the literal string "API-Version".
  • The value that is returned is always a string: either the header's value, or "" when the header is absent.
  • Every evaluation of api.version triggers the GET request; the response object is expected to provide a headers attribute (a mapping) and an ok attribute.

Constraints

  • Creating the API object by way of pynetbox.api(host) must not itself require the version request to succeed; the version request only takes place when the version property is accessed.
