01 Handle Selection-Type Custom Fields in Record Serialization 666 words · rewritten by GPT-5.6-sol

Task Specification: Handle Selection-Type Custom Fields in Record Serialization

Background

API records are represented by record objects, such as those returned by getattr(nb, <endpoint_name>).get(<id>). These objects expose a mutable custom_fields dictionary and a serialize() method that produces a plain dictionary suitable for sending back to the API.

Custom fields may contain simple scalar values, such as strings or numbers, or selection-type values. A selection-type value is returned by the API as a dictionary containing both the selected value and its human-readable label:

{
    "value": <the selected value>,
    "label": <a human-readable label>
}

The API's read representation is therefore different from the write representation expected when a record is serialized.

Required Behavior

Custom-field representation on records

A record populated from an API response must expose its custom fields through its mutable custom_fields dictionary. Entries may include:

  • Scalar values, including strings, numbers, and other non-selection values.
  • Selection-type dictionaries containing "value" and "label".

Callers must continue to be able to modify individual entries directly, for example:

record.custom_fields["test_custom"] = "Testing"
Serialization

Calling record.serialize() with no required arguments must return a dictionary containing a "custom_fields" dictionary. Each custom-field entry must be serialized independently as follows:

  • A scalar custom-field value must be returned unchanged.
  • A selection-type custom-field dictionary containing "value" and "label" must be flattened to the contents of its "value" key. The label and the enclosing selection dictionary must not appear in the serialized custom-field value. This applies even when the selected value is falsy, such as 0, False, an empty string, or None.

Flattening is specific to selection-type values inside custom_fields; it must not change existing serialization behavior for unrelated record attributes.

Modification detection and idempotent saves

Selection-value normalization must be consistent between the record's serialized output and the initial state used by the library to determine whether a record has changed. A record freshly retrieved from the API must be considered unmodified even when its API response contains nested selection-type custom-field dictionaries.

Consequently:

  • Before any user modification, the record's current serialized state must compare equal to its captured initial state.
  • Existing change detection must report an untouched record as unchanged; where _compare() is used for this comparison, it must return True.
  • Calling the existing idempotent save flow on such an untouched record must not issue an update merely because serialization flattened a selection value. Its behavior must remain the same as for any other unchanged record.
  • A real user change, including assigning a different scalar value to a custom field, must still be detected normally. Selection fields present alongside that changed field must still be flattened in the resulting serialization.

In short, the nested read representation and flattened write representation must not by themselves create a false modification.

Example

Given a freshly retrieved record whose custom_fields contains:

{
    "test_custom": "Hello",
    "test_selection": {"value": 2, "label": "second"}
}

the record must initially be treated as unchanged. If the caller then performs:

record.custom_fields["test_custom"] = "Testing"
serialized = record.serialize()

then:

serialized["custom_fields"] == {
    "test_custom": "Testing",
    "test_selection": 2
}

The assigned plain string remains unchanged, while the selection-type value is represented by its underlying value.

API Surface and Compatibility

Record objects returned by endpoint retrieval must continue to expose:

  • A mutable custom_fields dictionary attribute populated from the API response.
  • A serialize() method with no required arguments that returns a dictionary containing the normalized "custom_fields" mapping described above.
  • Existing modification-detection and save behavior, with selection flattening accounted for consistently.

The existing public access pattern remains unchanged: API/app objects expose endpoint attributes, and endpoint objects continue to provide .get(<id>). This task must not alter endpoint lookup, retrieval, unrelated record serialization, or other existing public behavior.

Scope

The required change is limited to flattening selection-type custom fields from their value/label read representation to their underlying value in serialized output, while preserving scalar custom fields and ensuring that this representational conversion does not make untouched records appear modified.
