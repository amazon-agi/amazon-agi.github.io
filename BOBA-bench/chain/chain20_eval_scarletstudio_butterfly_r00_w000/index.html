Task Specification: Release Load Module

Overview

Create a new module pipeline/load/release.py providing two Prefect tasks: one uploads match data to a Firebase Realtime Database, and the other deletes match data from it. Both tasks work against a database handle that is passed in as an argument.

Public API

The module must expose two Prefect tasks (that is, objects carrying a .run(...) method that can be invoked directly):

  • upload_matches
  • delete_previous_release

The underlying function of each task is invoked via its .run(...) method using the signatures shown below.

upload_matches

Signature
upload_matches.run(db, matches, community, load_release_tag, force=False)
  • db: a database handle. Database references are obtained via db.reference(path).
  • matches: a pandas DataFrame. Every row is a match record with (at least) these columns:
    • key: a string that identifies the match within its release.
    • release: a string release tag (for example, "2022-04-01").
    • users: a set of user identifiers taking part in the match.
    • community: the community as a string.
    • title: the title of the match (may be None).
    • Additional arbitrary columns may also be present (for example, community); these must NOT be carried into the output records except where explicitly listed below.
  • community: a string serving to namespace the database path.
  • load_release_tag: a string release tag. Match rows are processed only when their release value equals this tag; rows carrying any other release tag are skipped entirely.
  • force: a boolean flag.
Behavior

When force is falsy: the task must carry out no database interaction of any kind. It obtains no references, and no writes occur.

When force is truthy: the task assembles a single updates dictionary and applies it in one call:

db.reference("matches").update(<updates_dict>)

The .update(...) method must be called exactly once and given the complete updates dictionary.

Assembling the updates dictionary

Take into account only rows whose release equals load_release_tag. For every such row, produce one output entry per user in that row's users set.

  • Output key (the key inside the dictionary): "{community}/{release_tag}~{key}~{user}"
    • As an example: "test/2022-04-01~1~A"
  • Output value (a dictionary) with the following contents:
    • "id": "{release_tag}~{key}" (for example, "2022-04-01~1").
    • "for": the user identifier this entry corresponds to.
    • "participants": a dictionary that maps every user in the match's users set to True.
    • "release_tag": the release tag as a string.
    • "release_timestamp": the release tag read as a date at midnight and converted to a Unix timestamp expressed in milliseconds (the seconds-since-epoch timestamp multiplied by 1000). For example, "2022-04-01" → datetime.datetime(2022, 4, 1).timestamp() * 1000.
    • "title": the value of the match's title (may be None).

Except as reflected above, fields from the source row such as key, users, release, and community must NOT appear in the output value.

delete_previous_release

Signature
delete_previous_release.run(db, community, release_tag, now, force=False)
  • db: a database handle. References are obtained via db.reference(path).
  • community: a string serving to namespace database paths.
  • release_tag: a string release tag (for example, "2022-04-01").
  • now: a datetime.datetime that represents the current time.
  • force: a boolean flag.
Condition guarding the delete

The delete operation runs only when either of these holds:

  • force is truthy, or
  • the date represented by release_tag lies in the future relative to now (that is, the release date is later than now).

The release date is obtained by reading release_tag as a date at midnight. For example, with release_tag="2022-04-01":

  • now = datetime.datetime(2022, 3, 31) → the release lies in the future → the operation runs even without force.
  • now = datetime.datetime(2022, 4, 2) → the release lies in the past → the operation runs only if force is truthy.

When the guard condition is not satisfied (the release is not in the future and force is falsy), the task must perform no database interaction: db.reference(...) must not be called at all.

Deletion behavior (when the guard is satisfied)

  1. Query the match records that already exist for the release. Get the matches reference at path "matches/{community}", filter it so that the "release_tag" child equals release_tag, and fetch the results:

    db.reference("matches/{community}") \
  .order_by_child("release_tag") \
  .equal_to(release_tag) \
  .get()

    The .get() call must be invoked exactly once, taking no arguments. The result is a dictionary that maps match-entry keys to their record dictionaries, and each record contains an "id" field of the form "{release_tag}~{key}".

  2. Delete the match entries. Build a dictionary that maps each fetched match-entry key to None, and apply it in a single call:

    db.reference("matches/{community}").update(<deletes_dict>)

    For example, if the fetched keys are "2022-04-01~1~A" and "2022-04-01~1~B", the deletes dictionary is:

    {"2022-04-01~1~A": None, "2022-04-01~1~B": None}

    The .update(...) call on the matches reference must be made exactly once.

  3. Delete the corresponding chat/message entries. Build a dictionary that maps every distinct match "id" (taken from the fetched records) to None, and apply it in a single call:

    db.reference("messages/{community}").update(<chat_deletes_dict>)

    The same "id" may be shared by multiple fetched entries (for instance, one per user for a single match); the chat deletes dictionary must contain each distinct id once. For example:

    {"2022-04-01~1": None}

    The .update(...) call on the messages reference must be made exactly once.

Note that db.reference may be called with different path arguments ("matches/{community}" and "messages/{community}") so that distinct references are obtained for the match and message operations.

Further Notes

  • The modules pipeline/extract/matches.py (which exposes extract_recent_matches) and pipeline/extract/users.py (which exposes extract_users) already exist; they must remain importable and their behavior must stay unchanged, and this task requires no changes to their public behavior.

Task Specification: Matching Engine

Overview

Build a matching engine together with the data schema classes that support it. The engine is given a collection of users and produces a set of matches: it combines the candidate matches coming from a series of generator functions, scores them, ranks them, and fills the users who remain unmatched via a fallback function.

Data Schema

pipeline/schema/user.py

Define a type alias together with a class:

  • UserId — a type alias that stands for str.

  • User — a class whose constructor takes keyword arguments:

    • uid: UserId
    • displayName: str

    When the uid and displayName of two User instances are equal, the instances must compare equal.

pipeline/schema/match.py

Define these classes:

  • Match — a class whose constructor takes one keyword argument:

    • users: set — the set of user ids that take part in the match.

    When the users sets of two Match instances are equal, the instances must compare equal. A match may hold two or more user ids.

  • MatchingInput — a class whose constructor takes keyword arguments:

    • community: str
    • release: str
    • users: list[User]
    • recent_matches: list[Match]

  • MatchingOutput — a class whose constructor takes keyword arguments:

    • community: str
    • release: str
    • users: list[User]
    • matches: list[Match]

    When all four fields of two MatchingOutput instances are equal, the instances must compare equal.

Matching Engine

pipeline/matching/core/engine.py

Define the class MatchingEngine.

Constructor
MatchingEngine(generators, scorer, ranker, fallback)
  • generators — a list of callables. Each generator returns a list of candidate Match objects when it is invoked.
  • scorer — a callable that scores a candidate match.
  • ranker — a callable that is given two arguments (a scoring input and a collection of scored/candidate matches) and returns an ordered list of matches.
  • fallback — a callable that returns a list of Match objects intended to cover any users not yet matched.
Method: run(self, inp: MatchingInput) -> MatchingOutput

When a MatchingInput is passed to it, the method produces a MatchingOutput in which the community, release, and users fields are copied unchanged from the input, and the matches field is computed as follows:

  1. Invoke each generator to gather candidate matches. The combined candidate pool is the union of the matches returned by all generators.
  2. Score and rank the candidates with the scorer and ranker, in order to determine which candidates are selected.
  3. Select candidate matches in ranked order, but accept a candidate only if none of the user ids it contains have already been used by a previously selected match. Any candidate that would reuse an already-matched user is skipped.
  4. After the selection from the candidates is complete, invoke the fallback to produce matches that cover the users who remain unmatched, and append those matches to the result.

The final matches list must contain the accepted candidate matches followed by the fallback matches, in that order.

Selection example

Suppose the users are A, B, C, D, E:

  • The generators produce the candidate matches {A, C} and {A, D}.
  • The ranking leaves the candidate order unchanged.
  • The first candidate, {A, C}, is accepted (A and C were free).
  • The second candidate, {A, D}, is rejected because A has already been matched.
  • The fallback covers the remaining unmatched users B, D, E and produces the match {B, D, E}.
  • The resulting matches are [{A, C}, {B, D, E}].

Notes

  • The engine must not draw on any information beyond what the input and the four provided callables supply; the callables are the only source of candidate generation, scoring, ranking, and fallback behavior.

Summary

Task Specification: Satirical Common-Letter Match Generator

Overview

Build a match generator that pairs users according to how many letters their display names have in common. This generator is for use within a matching engine pipeline.

Required Data Types

The types listed below must be available for import from the module pipeline.types:

User

A record describing a user, constructed with keyword arguments:

  • uid (str): the user's unique identifier.
  • displayName (str): the display name of the user.
MatchingInput

A container holding the input, constructed with keyword arguments:

  • community (str)
  • release (str)
  • users (list of User)
  • recent_matches (list of Match)
Match

A record representing a match, constructed with the keyword argument:

  • users (set of str): the set of uid values of the users that make up the match.

When two Match instances have equal users sets, they must compare equal. (Equality comparison of Match objects is required.)

Required Public API

Within the module pipeline.matching.generators.satirical, provide a function:

def configure_common_letter_generator(min_common: int = 0):
    ...
  • The function accepts an optional keyword argument min_common, an integer whose default value is 0.
  • The function returns a callable (the "generator").

The returned generator is called with one argument, a MatchingInput, and produces an iterable of Match objects (the result must be consumable by list(...)).

Matching Behavior

For a given MatchingInput, the generator considers every unordered pair of distinct users taken from inp.users.

For each pair, compute the number of letters in common between that pair's two display names. A pair qualifies as a match when its count of common letters is greater than or equal to min_common.

Definition of "common letters"

The number of common letters between two display names is the count of distinct characters that appear in both names. The comparison is case-sensitive as given (capitalization on the shared letters is consistent across the display names in scope). Repeated occurrences of a character within a name do not increase the count — only the set of distinct characters shared between the two names is what matters.

Examples of the counting rule (these illustrate the definition only):

  • "Ben" and "Benjamin" have the distinct characters B, e, n in common → 3 common letters.
  • "Ben" and "Boo" have the distinct character B in common → 1 common letter.
Qualifying pairs
  • Under the default min_common=0, every pair qualifies (any count ≥ 0), so all unordered pairs of distinct users are emitted.
  • With a larger min_common, only pairs whose common-letter count meets or exceeds the threshold are emitted.
Output

For each qualifying pair, emit one Match whose users set contains that pair's two uid values.

Ordering

The pairs must be produced in the order that results from iterating over the users in their given list order and forming each pair (user at index i together with each user at a later index j > i), scanning j for each fixed i. Concretely, for users listed as u0, u1, u2, the pair order is (u0,u1), (u0,u2), (u1,u2), and non-qualifying pairs are omitted from the sequence.

Example Behavior

  1. With the default configuration, users with uids "1", "2", "3" and display names "Anna", "Ankur", "Anna" produce matches for the pairs {"1","2"}, {"1","3"}, {"2","3"}, in that order.

  2. For users with uids "1", "2", "3" and display names "Ben", "Benjamin", "Boo", configured with min_common=3, only the match {"1","2"} is produced (the only pair sharing at least 3 distinct letters).

Part 1: Filtering in user extraction by active community membership

  • community: a string that names the target community.
Accessing the data

The method obtains the raw users mapping by way of a call to db.reference("users").get(). The get callable must be invoked exactly once, and with no arguments.

The value that is returned is a dictionary mapping user id strings to user records. Each user record is itself a dictionary and may contain keys such as uid, latestLogin, and communities.

The communities key, when present, maps to a dictionary keyed by community name; each value in it is a membership record dictionary that may contain an active boolean flag.

Rules for filtering

Build the output set of users by including only those user records that satisfy all of the following:

  1. The record's latestLogin value is present and non-null. Records lacking latestLogin (or having a null/absent value) are excluded.

  2. What the record grants is active membership in the target community. To be specific, the record's communities dictionary must contain an entry whose key is exactly the given community string, and the active value of that entry must be exactly True. The following are all excluded:

    • No communities key / an empty communities dictionary.
    • A communities dictionary that holds other community names while not containing the target one.
    • A membership entry for the target community that lacks an active key.
    • A membership entry for the target community whose active value is set to False.

    As long as the target community's entry has active == True, a user with multiple community memberships qualifies.

Output
