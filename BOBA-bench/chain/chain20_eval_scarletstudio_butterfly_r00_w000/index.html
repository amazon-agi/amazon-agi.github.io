Task Specification: Release Load Module

Overview

Create a new module pipeline/load/release.py that provides two Prefect tasks for uploading match data to and deleting match data from a Firebase Realtime Database. Both tasks operate against a database handle passed in as an argument.

Public API

The module must expose two Prefect tasks (i.e., objects with a .run(...) method that can be invoked directly):

  • upload_matches
  • delete_previous_release

Each task's underlying function is invoked via its .run(...) method with the signatures described below.

upload_matches

Signature
upload_matches.run(db, matches, community, load_release_tag, force=False)
  • db: a database handle. Obtain database references via db.reference(path).
  • matches: a pandas DataFrame. Each row is a match record with (at least) the columns:
    • key: a string identifying the match within its release.
    • release: a string release tag (e.g., "2022-04-01").
    • users: a set of user identifiers participating in the match.
    • community: the community string.
    • title: match title (may be None).
    • There may be additional arbitrary columns (e.g., community), which must NOT be carried into the output records except where explicitly listed below.
  • community: a string used to namespace the database path.
  • load_release_tag: a string release tag. Only match rows whose release value equals this tag are processed; rows with any other release tag are skipped entirely.
  • force: a boolean flag.
Behavior

When force is falsy: the task must perform no database interaction at all. No references are obtained and no writes occur.

When force is truthy: the task builds a single dictionary of updates and applies it with one call:

db.reference("matches").update(<updates_dict>)

The .update(...) method must be called exactly once with the complete updates dictionary.

Building the updates dictionary

Consider only rows whose release equals load_release_tag. For each such row, produce one output entry per user in that row's users set.

  • Output key (the dictionary key): "{community}/{release_tag}~{key}~{user}"
    • Example: "test/2022-04-01~1~A"
  • Output value (a dictionary) containing:
    • "id": "{release_tag}~{key}" (e.g., "2022-04-01~1").
    • "for": the user identifier for this entry.
    • "participants": a dictionary mapping every user in the match's users set to True.
    • "release_tag": the release tag string.
    • "release_timestamp": the release tag interpreted as a date at midnight, converted to a Unix timestamp in milliseconds (seconds-since-epoch timestamp multiplied by 1000). For example, "2022-04-01" → datetime.datetime(2022, 4, 1).timestamp() * 1000.
    • "title": the match's title value (may be None).

Fields such as key, users, release, and community from the source row must NOT appear in the output value except as reflected above.

delete_previous_release

Signature
delete_previous_release.run(db, community, release_tag, now, force=False)
  • db: a database handle. Obtain references via db.reference(path).
  • community: a string used to namespace database paths.
  • release_tag: a string release tag (e.g., "2022-04-01").
  • now: a datetime.datetime representing the current time.
  • force: a boolean flag.
Guard condition

The delete operation runs only if either of the following is true:

  • force is truthy, or
  • the release_tag represents a date that is in the future relative to now (i.e., the release date is later than now).

The release date is derived from release_tag interpreted as a date at midnight. For example, with release_tag="2022-04-01":

  • now = datetime.datetime(2022, 3, 31) → release is in the future → operation runs even without force.
  • now = datetime.datetime(2022, 4, 2) → release is in the past → operation runs only if force is truthy.

If the guard condition is not satisfied (release is not in the future and force is falsy), the task must perform no database interaction: db.reference(...) must not be called at all.

Delete behavior (when the guard is satisfied)

  1. Query existing match records for the release. Obtain the matches reference at path "matches/{community}", filter it by the "release_tag" child equal to release_tag, and fetch the results:

    db.reference("matches/{community}") \
  .order_by_child("release_tag") \
  .equal_to(release_tag) \
  .get()

    The .get() call must be invoked exactly once with no arguments. The result is a dictionary mapping match-entry keys to their record dictionaries. Each record contains an "id" field of the form "{release_tag}~{key}".

  2. Delete the match entries. Build a dictionary mapping each fetched match-entry key to None, and apply it with a single call:

    db.reference("matches/{community}").update(<deletes_dict>)

    For example, given fetched keys "2022-04-01~1~A" and "2022-04-01~1~B", the deletes dictionary is:

    {"2022-04-01~1~A": None, "2022-04-01~1~B": None}

    The .update(...) on the matches reference must be called exactly once.

  3. Delete the corresponding chat/message entries. Build a dictionary mapping each distinct match "id" (from the fetched records) to None, and apply it with a single call:

    db.reference("messages/{community}").update(<chat_deletes_dict>)

    Multiple fetched entries may share the same "id" (e.g., one per user for the same match); the chat deletes dictionary must contain each distinct id once. For example:

    {"2022-04-01~1": None}

    The .update(...) on the messages reference must be called exactly once.

Note that db.reference may be called with different path arguments ("matches/{community}" and "messages/{community}") to obtain distinct references for the match and message operations.

Additional Notes

  • The existing modules pipeline/extract/matches.py (exposing extract_recent_matches) and pipeline/extract/users.py (exposing extract_users) already exist and must remain importable and unchanged in behavior; no changes to their public behavior are required by this task.

Matching Engine

pipeline/matching/core/engine.py

Define a class MatchingEngine.

Constructor
MatchingEngine(generators, scorer, ranker, fallback)
  • generators — a list of callables. Each generator, when invoked, returns a list of candidate Match objects.
  • scorer — a callable used to score a candidate match.
  • ranker — a callable that takes two arguments (a scoring input and a collection of scored/candidate matches) and returns an ordered list of matches.
  • fallback — a callable that returns a list of Match objects to cover any users not yet matched.
Method: run(self, inp: MatchingInput) -> MatchingOutput

Given a MatchingInput, produce a MatchingOutput whose community, release, and users fields are copied unchanged from the input, and whose matches field is computed as follows:

  1. Invoke each generator to collect candidate matches. The combined pool of candidates is the union of matches returned by all generators.
  2. Score and rank the candidates using the scorer and ranker to determine which candidates are selected.
  3. Select candidate matches in ranked order, but only accept a candidate if none of the user ids it contains have already been used by a previously selected match. Skip any candidate that would reuse an already-matched user.
  4. After selecting from candidates, invoke the fallback to produce matches covering the users who remain unmatched, and append those to the result.

The final matches list must contain, in order, the accepted candidate matches followed by the fallback matches.

Selection example

Given users A, B, C, D, E:

  • Generators produce candidate matches {A, C} and {A, D}.
  • Ranking preserves the candidate order.
  • The first candidate {A, C} is accepted (A and C were free).
  • The second candidate {A, D} is rejected because A is already matched.
  • The fallback covers the remaining unmatched users B, D, E, producing match {B, D, E}.
  • Resulting matches: [{A, C}, {B, D, E}].

Notes

  • The engine must not use any information beyond what the input and the four provided callables supply; the callables are the sole source of candidate generation, scoring, ranking, and fallback behavior.

Matching Behavior

Given a MatchingInput, the generator considers every unordered pair of distinct users drawn from inp.users.

For each pair, determine the number of letters in common between their two display names. A pair qualifies as a match when the count of common letters is greater than or equal to min_common.

Definition of "common letters"

The number of common letters between two display names is the number of distinct characters that appear in both names. Comparison is case-sensitive as given (the display names in scope use consistent capitalization on the shared letters). Duplicate occurrences of a character within a name do not increase the count — only the set of distinct characters shared between the two names matters.

Examples of the counting rule (for illustration of the definition only):

  • "Ben" and "Benjamin" share the distinct characters B, e, n → 3 common letters.
  • "Ben" and "Boo" share the distinct character B → 1 common letter.

  • With the default min_common=0, every pair qualifies (any count ≥ 0), so all unordered pairs of distinct users are emitted.
  • With a higher min_common, only pairs whose common-letter count meets or exceeds the threshold are emitted.
Output

For each qualifying pair, emit a single Match whose users set contains the two uid values of that pair.

Ordering

Pairs must be produced in the order obtained by iterating over the users in their given list order and forming each pair (user at index i with each user at a later index j > i), scanning j for each fixed i. Concretely, for users listed as u0, u1, u2, the pair order is (u0,u1), (u0,u2), (u1,u2), with non-qualifying pairs omitted from the sequence.

Example Behavior

  1. Users with uids "1", "2", "3" and display names "Anna", "Ankur", "Anna", using the default configuration, produce matches for pairs {"1","2"}, {"1","3"}, {"2","3"} in that order.

  2. Users with uids "1", "2", "3" and display names "Ben", "Benjamin", "Boo", configured with min_common=3, produce only the match {"1","2"} (the only pair sharing at least 3 distinct letters).

Behavior of MultiRanker.rank:

  • The provided rankers list is applied in sequence: the proposed matches are passed through the first ranker, whose output is fed into the second ranker, and so on. The output of the final ranker is the overall result.
  • With an empty rankers list, the proposed matches are returned unchanged, in their original order.
  • Each individual ranker transforms/reorders the stream of matches; MultiRanker composes them left-to-right (first ranker first, last ranker last).

Illustrative composition example (using rankers that perform a stable sort placing matches containing a specific user first):

  • Given proposed matches (in order): {B,E}, {A,B}, {A,C}, {C,D}.
  • Applying a ranker prioritizing user A, then a ranker prioritizing user C, yields: {A,C}, {C,D}, {A,B}, {B,E}.

This demonstrates that the final ranker's ordering effect dominates, applied on top of the ordering produced by earlier rankers.
