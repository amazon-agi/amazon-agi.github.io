Task Specification: Implement xcc.Device Class

Overview

Add a Device class to the xcc package that wraps the device-related endpoints of the remote XC API. It provides read-only access to a device's certificate, specification, expected uptime, status, and availability, and caches remotely fetched data until explicitly refreshed.

Package Integration and Version

The class must be publicly importable as xcc.Device, for example:

import xcc
device = xcc.Device("qpu", connection)

The xcc package version string must be exactly "0.1.0-dev"; concretely, xcc.__version__ == "0.1.0-dev". Any client user-agent composed from the package version must therefore be exactly "XanaduCloudClient/0.1.0-dev".

Public API

Constructor
Device(target: str, connection)
  • target is the string identifying the device, such as "qpu".
  • connection is the connection object used elsewhere in xcc. It can build a full connection URL with connection.url(path) and issue authenticated HTTP requests.
  • The constructor stores these arguments but must not perform any HTTP request. Remote data is fetched only when needed or when an eager refresh is requested.
Read-only properties

All of the following are properties, accessed without parentheses, and are read-only.

Local properties
  • connection returns the same connection object supplied to the constructor.
  • target returns the target string supplied to the constructor.

Reading either local property must not trigger an HTTP request.

Properties derived from device details

These properties use the JSON object returned by the device-details endpoint:

  • status returns the value of its "state" field, such as "online" or "offline".
  • up returns the value of its "up" field as a boolean.
  • expected_uptime returns the value of its "expected_uptime" field without transformation. For example, this may be a mapping from weekday names to lists of time strings.
Properties obtained from secondary endpoints
  • certificate reads the "certificate_url" endpoint reference from the device details, resolves it against the supplied connection as described below, issues a GET request, and returns the parsed JSON response.
  • specification reads the "specifications_url" endpoint reference from the device details, resolves it against the supplied connection as described below, issues a GET request, and returns the parsed JSON response.
Refresh method
refresh(self, lazy: bool = True) -> None

refresh invalidates the instance's cached remote data and returns None.

  • With lazy=True, which is the default, all cached device data is cleared. The call itself performs no HTTP requests. Each subsequently requested value is fetched again as needed.
  • With lazy=False, the cache is immediately repopulated. The method fetches fresh device details first, then fetches both the certificate and the specification using the endpoint references in those fresh details. Thus, a successful eager refresh performs exactly three GET requests: one for details and one for each secondary resource. Subsequent accesses use the newly populated cache.

HTTP Interaction

Device-details endpoint

Device details are fetched with:

GET connection.url("/devices/<target>")

Equivalently, the request path supplied through the connection is /devices/<target>. The JSON response is an object that may contain "state", "up", "expected_uptime", "certificate_url", and "specifications_url". Not every response must contain every field; a property reads the field it requires.

Secondary-endpoint resolution

The values in "certificate_url" and "specifications_url" are endpoint references, not authoritative request origins. For either reference:

  1. Extract only its URL path component.
  2. Resolve that path using the supplied connection. The resulting request destination must be equivalent to connection.url(extracted_path).
  3. Issue an authenticated GET through the supplied connection and parse its JSON response.

This rule applies both to absolute references and to bare paths:

  • If a certificate reference is https://example.com/devices/qpu/certificate, its path is /devices/qpu/certificate; the request is made to connection.url("/devices/qpu/certificate"). The scheme, host, and port from example.com must not be contacted or retained.
  • If a reference is /cert, the request is made to connection.url("/cert").

The same behavior is required for specification references. In particular, an absolute reference whose origin differs from the connection's configured origin must be rebased onto the connection while preserving its path. The reference must not be requested verbatim.

All remote interactions are HTTP GET requests, expect a successful HTTP 200 response, and consume a JSON body. JSON strings must be parsed into Python values before fields are read or property values are returned. Returned values are otherwise left exactly as represented by the parsed JSON.

Caching Semantics

Shared details cache within an instance

Device details are fetched lazily and cached per Device instance. The first access to any property requiring details fetches the details once. Further accesses to status, up, and expected_uptime before a refresh all share that cached object and cause no additional details requests. Secondary properties also reuse cached details when obtaining their endpoint references.

For example, reading up twice and then reading status, without refreshing, results in only one GET to the details endpoint.

Secondary-resource caches

Certificate and specification responses are cached independently for the fetched endpoint references. Repeated access to either property before a refresh must not repeat its secondary GET. Fetching a secondary property may first require a details GET if details are not already cached.

Lazy refresh request behavior

A lazy refresh performs no requests itself. After it, the next access to a details-derived property performs a new details GET and reflects the newly returned data. For example:

  1. The first up access fetches details: one request.
  2. A second up access uses the cache: still one request.
  3. refresh() or refresh(lazy=True) clears the cache: still one request.
  4. The next up access fetches fresh details and returns the new value: two requests in total.

Because all remote caches are invalidated, accessing certificate or specification after a lazy refresh must likewise fetch whatever fresh details and secondary response are then needed.

Eager refresh request behavior

An eager refresh must not reuse stale details or stale secondary data. It immediately fetches details, certificate, and specification in that order of dependency. All three refreshed values are then cached, so reading any of the associated properties immediately afterward performs no additional request.

For example, if one details request has already occurred, refresh(lazy=False) adds three requests—fresh details, certificate, and specification—for four total. A later up access returns the refreshed value without increasing that count.

Cache isolation

All caches are instance-local. Two Device objects created with the same target and connection still fetch and cache their own details independently. Refreshing one instance must neither invalidate nor change data cached by the other instance.

3. Device Properties and Caching

A device has three logical cached resources: its device details, certificate, and specification. Requests use the supplied connection and JSON response values are cached per device instance.

Device details

Device details are obtained with a GET request for /devices/{target}. The following public properties are read from the cached details mapping:

  • device.status returns the "state" field, such as "online" or "offline".
  • device.up returns the boolean "up" field.
  • device.expected_uptime returns the "expected_uptime" mapping.

These properties share the same details cache. Once details have been loaded, repeatedly accessing any details-derived property must not repeat the details request until that device is refreshed.

Certificate and specification
  • device.certificate returns the JSON mapping fetched from the resource referenced by the details field "certificate_url".
  • device.specification returns the JSON mapping fetched from the resource referenced by the details field "specifications_url".

Referenced resources must be requested through the device's connection using the path component of the referenced URL. If details have not yet been loaded, accessing either associated-resource property first loads the details needed to discover its URL. Certificates and specifications are then cached independently, and repeated accesses do not cause further requests until refresh.

4. Initial Lazy and Eager Population

The constructor's lazy value controls initial fetching as well as later refreshes.

Lazy construction (lazy=True)

Construction must perform no device-related network requests and must begin with empty caches. Data is fetched only when a property requiring it is first accessed. In particular, the first access to a details-derived property fetches only the device details in one request; it must not prefetch the certificate or specification. Subsequent details-derived accesses use the cache. Accessing certificate or specification fetches that resource only when needed, after obtaining details if necessary.

Eager construction (lazy=False)

Construction must eagerly populate the complete device cache before returning. It must issue exactly one GET for each of the following resources:

  1. the device details;
  2. the certificate referenced by those details; and
  3. the specification referenced by those details.

Thus a normally completed eager construction performs three resource requests in total. All details-derived, certificate, and specification properties must then be served from this populated cache without additional requests until refresh() is called. Merely reading a property for the first time must not trigger an extra request on an eagerly constructed device.

5. Refresh API and Semantics

The refresh API is:

device.refresh()

refresh() must no longer accept a lazy argument. It clears that device's cached details, certificate, and specification, and then follows the immutable device.lazy strategy.

Lazy refresh

For a device constructed with lazy=True, refresh() only invalidates all three cached resources. The call itself performs no network requests. Each invalidated resource is fetched again only on the next property access that needs it, after which it is cached again.

For example, after device.up has loaded and cached the details, a second device.up access makes no request. Calling refresh() still makes no request. The next device.up access makes exactly one new details request, and later accesses reuse that refreshed value.

Eager refresh

For a device constructed with lazy=False, refresh() invalidates all three resources and immediately repopulates the complete cache. It must fetch the new device details and then fetch the certificate and specification referenced by those new details: one GET for each resource, or three requests for a normal refresh. Property accesses after the call must use the newly populated cache without additional requests.

Consequently, an eager device performs three requests during construction. Calling refresh() performs three more, for six cumulative resource requests, and reading a refreshed property afterward does not increase that count.

6. Per-Instance Cache Isolation

Every Device must own an independent cache for all three resources. Constructing, accessing, invalidating, or repopulating one device's cache must not change another device's cached state, even when the devices have the same target and share the same Connection. Refreshing one such device can expose newly fetched values on that device while the other continues returning its previously cached values.

7. Printable Representation

repr(device) must have the following form:

<Device: target=qpu>

The target portion must use that device's actual target value.

The raw API response provides expected_uptime as a mapping from weekday name (string, e.g. "monday") to a list of two ISO-8601 time strings (e.g. ["16:00:00+00:00", "20:00:00+00:00"]).

The property must transform this into a dictionary mapping each weekday name to a 2-tuple of datetime.time objects, where each time is parsed from its ISO-8601 string via datetime.time.fromisoformat.

Example:

  • Raw response {"expected_uptime": {"monday": ["16:00:00+00:00", "20:00:00+00:00"]}}
  • Result: {"monday": (time.fromisoformat("16:00:00+00:00"), time.fromisoformat("20:00:00+00:00"))}

That is, the string list becomes a tuple of parsed time objects, keyed by the same weekday name.

3. xcc.Connection.request — HTTP error parsing

Connection.request(method, path, ...) issues an HTTP request and returns the response. When the response status code indicates an error (a non-successful HTTP status), the method must raise requests.exceptions.HTTPError. The message of the raised error is derived from the response as follows, in priority order:

  1. Validation error with metadata. If the response body is valid JSON containing a non-empty "meta" field (an object mapping keys to lists of message strings), the error message is composed of all the message strings from every list in "meta", joined by "; ". The messages appear in order of the fields and in list order within each field. For example, a body of

    {"code": "validation-error", "meta": {"_schema": ["Foo", "Bar"], "size": ["Baz"]}}

    produces a message containing Foo; Bar; Baz.

  2. Detailed error. Otherwise, if the response body is valid JSON containing a "detail" field, the error message is the value of that field (e.g. The request body is empty.).

  3. Fallback. Otherwise (the body is invalid JSON, or is valid JSON without usable "meta"/"detail" information), the error message is the default HTTP error text for the status, of the form <code> <reason> (e.g. 400 Client Error: Bad Request, 418 Client Error: I'm a Teapot).

Successful requests behave normally: a 200 response is returned; a 401 response triggers an access-token refresh and retry (an expired access token causes the connection to update its access token and re-issue the request, ultimately returning the successful response).
