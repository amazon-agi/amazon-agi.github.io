Overview

Public API

  • port_name: a string that identifies the serial port used for communication.
  • Based on this port name, the class must open/use a serial connection. (Testing will mock serial communication; the constructor must instantiate a serial object that uses the provided port.)

Method:

get_nodes()
  • Sends the network command across the serial connection.
  • Exactly one write of the command must be made to the serial port. The value that gets written is the command string network once it has been passed through an encoding step. This encoding step must be a transformation that is accessible, such that writing network produces a specific encoded byte/string form (this is the same transformation the test applies via a duco_encoded('network') helper — you must define the command-writing such that the encoded form of 'network' is what gets written). The write must happen in a single call that carries the encoded network command.
  • Reads the response from the device (a single read that returns the full multi-line response text).
  • Parses that response and returns a list of node objects (see below).

Format of the Response

The response arrives as a block of text with the following form:

  Network:
  --- start list ---
  node|addr|type    |ptcl|cerr|prnt|asso|stts|stat|cntdwn|%dbt|trgt|cval|snsr|ovrl|capin |capout|tree|temp|info
  1   |1   |BOX     |9   |0   |0   |0   |0x00|AUTO|0     |58  |30  |30  |0   |255 |235   |3760  |0x01|0   |AUTO:0(0)
  2   |102 |UCBAT   |10  |0   |1   |1   |0x00|-   |0     |-   |-   |-   |0   |-   |-     |-     |-   |100 |-
  34  |132 |UCRH    |255 |0   |1   |1   |0x00|-   |0     |-   |-   |-   |59  |-   |-     |-     |-   |209 |-
  --- end list ---

Main characteristics:

  • On every line, fields are separated by the pipe character |.
  • Fields may have surrounding whitespace that must be stripped.
  • A header line exists (it begins with node|addr|type|...) that labels the columns and must not be treated as a data node.
  • Delimiter/marker lines (Network:, --- start list ---, --- end list ---) appear in the text and must not be treated as data nodes.
  • Every data line describes one node. The node number comes from the first field, and the node address comes from the second field.

Node Objects

A node object must be produced from each parsed data line. The list that get_nodes() returns must contain these node objects in the same order as they appear in the response.

Each node object must expose (at minimum) the following attributes:

  • number: the data line's first field, as a stripped string.
  • address: the data line's second field, as a stripped string.

Both values remain strings (they are not converted to integers).

Expected Parsing Outcome

When the sample response above is used, get_nodes() must return a list of three node objects with:

Index number address
0 '1' '1'
1 '2' '102'
2 '34' '132'

Edge Cases and Notes

  • Only genuine data rows turn into nodes; header and marker lines are excluded.
  • The leading/trailing whitespace in each field must be removed, so that '1 ' becomes '1', '132 ' becomes '132', etc.
  • The order in which the nodes appear in the returned list must match the order in the input text.

Serial protocol

On a valid connection, each call to get_nodes() proceeds as follows:

  1. The write method of the serial object is to be called exactly once with the UTF-8 encoding of the literal command network:

    "network".encode("utf-8")  # b"network"

    This command contains no newline, carriage return, or other bytes.

  2. That write is to be performed before the response is consumed.

  3. The response is obtained through the readline method of that same serial object. What readline returns is the response text, and it may contain the complete multi-line network response; it must therefore be handled as a whole rather than assumed to contain only one physical text line.

Parsing the response

The network response contains a pipe-delimited list, and the lines that delimit that list are lines whose trimmed text is --- start list --- and --- end list ---.

  • The response title, blank lines, the start/end marker lines, and the column-header row (for instance, the row that begins with node|addr) are to be ignored. None of them produces a node.
  • Each node data row in the list is separated by pipes. The node number is the first field, and the node address is the second field.
  • Leading and trailing whitespace is to be stripped from both fields.
  • Both values are to be kept as strings; do not convert numeric-looking values to integers.
  • One node object is to be produced for each node data row. Each returned object must publicly expose:
    • number: the stripped string of the first field.
    • address: the stripped string of the second field.
  • The node objects are to be returned in the same order in which their rows appear in the response.
  • The fields that come after the address do not need to be interpreted for this task.

For instance, rows whose first two fields are 1 | 1, 2 | 102, and 34 | 132 must produce an ordered list with (number, address) pairs:

("1", "1"), ("2", "102"), ("34", "132")

When the serial connection is valid and the network response is well-formed, they must be consumed and parsed without raising an exception.

Requirements for Compatibility

  • Existing public functionality in duco.ducobox is not to be removed or renamed; this includes the existing DucoBox behavior and the ducobox_wrapper(args) entry point.

    • A call to ducobox_wrapper(["--version"]) terminates with exit status 0.
    • When ducobox_wrapper([]) is called without the required port, it terminates with exit status 2.
    • When an invalid logging level is supplied together with a port, ValueError is raised.

Scope and Non-Goals

  • Aside from adding the DucoInterface constructor and the network-discovery behavior specified above, no new serial commands or device features are required.
  • It is not required to parse or to expose the remaining network-response columns.
  • No specific internal class hierarchy or parsing implementation is mandated; conformance is determined by the public API, the serial interactions, the returned values, and the compatibility behavior described here.

  • find_nodes() obtains the device response by way of a single call to the serial object's readline() method.
  • As line separators, the response uses carriage-return characters (\r) rather than newline characters (\n). Discovery must split the response and parse it correctly on \r boundaries.

--- end list ---
