Subplot-grid behavior requirements

Borders and the overall width

The literal lowercase character x must be used for all visible grid borders:

  • the full top and bottom borders are made up of x characters;
  • the left and right edge of each body line is formed by x; and
  • x separates adjacent columns.

When there are C = layout[1] columns, the column widths must be calculated from the requested overall width as follows:

base_width = (width - 3) // C
remainder = (width - 3) % C

Begin with base_width for every column, then add one character to each of the first remainder columns. Extra width is therefore distributed from left to right, and the complete rendered grid must have the requested overall width. As an example, layout=(1, 2) together with width=20 produces column widths of 9 and 8 characters, respectively; the three remaining characters are occupied by the left border, the column separator, and the right border.

Each cell must adhere to all of the following rules:

  1. The top and bottom padding are rendered as blank lines filled with spaces inside the cell, before and after its content lines.
  2. A content line starts with the configured left padding.
  3. Text is truncated to the content width that is available: column_width - left_padding - right_padding.
  4. The portion of the line that remains is filled with spaces, the configured right padding included, until the rendered cell line exactly fills its column width. Short lines are therefore right-padded, whereas overlong lines are truncated.
  5. Multiline text supplied to aprint() takes up successive lines in the same cell.
  6. For each grid row, all cells are rendered up to the height of the tallest cell. If a cell has fewer lines, its missing lines are blank and filled with spaces so that the vertical separators remain aligned.

Given the default padding, layout=(1, 2), and width=20, the available content widths are 5 characters for the first column and 4 for the second. As a consequence, longer strings are visibly cut to those limits.

grid.get_string() must join all of the rendered lines with \n, and there must be no trailing newline after the bottom border. Body lines must be filled to the overall width and must end at the right x border rather than with trailing spaces.

Task Specification: Rendering a Subplot Grid

Overview

Implement subplot-grid rendering in the package imported as apl (for example, import asciiplotlib as apl). A subplot grid takes independent text cells, arranges them in a rectangular grid, and renders the whole grid as a single bordered ASCII string.

Public API

apl.subplot_grid(shape, width, border_style=..., padding=...)

The function creates and returns a subplot-grid object.

  • shape is a 2-tuple (rows, cols) stating how many rows and columns the grid has.
  • width is an integer stating the total character width of the rendered output, counting all outer borders and column separators.
  • border_style is an optional keyword kept for compatibility. It must be accepted, but its value has no effect on rendering: all borders and separators are always drawn using x. For example, border_style="|" still produces borders made of x.
  • padding controls the padding inside every cell. When it is omitted, the default is 1 blank row at the top and bottom and 2 spaces at the left and right. When an integer p is supplied, p units are applied to all four sides in top, right, bottom, left order: p blank rows above and below the content and p spaces to its left and right.

The grid object that is returned must support:

  1. Two-dimensional item access: grid[r, c] returns the cell at zero-based row r and column c. Every position in the grid has an independent cell object.
  2. grid.get_string(): returns the fully rendered grid as a single string; newline characters appear between display rows, and there is no trailing newline.
Cell Objects

Each cell obtained through grid[r, c] must support the following:

  • cell.aprint(text): records text for display within that cell. Newline characters split the text into separate display lines, and those lines are kept in order. Only the behavior of a single aprint call per cell is required.

Rendering Behavior

Every outer border, vertical separator, and horizontal separator is drawn by the renderer using x. Padding and areas that are otherwise empty contain spaces.

Allocation of Width to Columns

Given a total width W and C columns, there are exactly C + 1 one-character vertical borders: the two outer borders and C - 1 separators. The width that remains is allocated to the cell fields. Define:

available = W - (C + 1)
base, remainder = divmod(available, C)

Every column has field width base, and one extra character is given to each of the first remainder columns from the left. Equivalently stated: column j is base + 1 wide when j < remainder, and base wide otherwise. Leftover width is therefore distributed left to right instead of being placed in the last column or thrown away.

For example, with width=20 and two columns, the cell-field widths are [9, 8]: after the three vertical borders, 17 characters remain, so the first field receives the extra character. With width=40 and three columns, the three field widths are all 12.

Every display row that is rendered is exactly width characters wide. A content row has the following structure:

x<column 0 field>x<column 1 field>x...x<last column field>x
Horizontal Border Lines and Grid Rows

A horizontal line made up entirely of width x characters is rendered:

  • at the top of the grid,
  • between every pair of adjacent grid rows, and
  • at the bottom of the grid.

Each grid row is rendered independently between the horizontal lines that surround it. All cells in one grid row use the same displayed height, one that is large enough for the cell with the most text lines in that row together with the required top and bottom padding. Cells having fewer lines are filled with spaces for the remaining display rows.

With the default padding, the text starts after one blank content row and is followed by at least one blank content row. As a consequence, a grid row whose tallest cell has N text lines has N + 2 content rows under the default padding. With an integer padding value p, p blank rows come before the text and p blank rows come after it; a row whose tallest cell has N lines consequently has N + 2p content rows.

Placement, Padding, and Truncation of Text

Inside each cell field:

  • The text lines appear in input order, one line per display row, after the top padding.
  • A line is left-aligned after the left padding of the cell.
  • The usable text width is the field width of the column minus its left and right padding. A line longer than that usable width is truncated to fit.
  • Shorter lines and empty areas are padded with spaces on the right so that the complete field always occupies its assigned width.

With the default padding, a 12-character field contains 2 leading spaces, room for at most 8 text characters, and 2 trailing spaces. Thus, in such a field, Some more text renders as Some mor, Some text as Some tex, and even more as even mor.

grid[0, 1].aprint("Some more text")
result = grid.get_string()

Task Specification: Border Styling of a Subplot Grid

Summary

A function named subplot_grid is to be implemented inside the asciiplotlib package. It arranges a grid made up of subplot cells, each of which can hold text, and produces the complete rendering as one string, with borders placed between the cells and around the grid. Besides a border built from a single custom character, the task requires support for multiple named border styles.

Public Interface

The asciiplotlib package, imported as apl, must expose:

apl.subplot_grid(layout, border_style=..., width=..., padding=...)
Parameters
  • layout: a 2-tuple (rows, cols) stating how many subplot rows and how many columns the grid contains.
  • border_style: decides how the grid's border/separator lines are produced (see "Border Styles" below); by default, the light box-drawing style laid out further down is used.
  • width: the overall display width, in characters, of the grid once rendered; every border character counts toward it.
  • padding: an integer giving the number of blank content lines that are added above and below each cell's text within the cell. It defaults to 0.
Value returned

Calling subplot_grid returns a grid object that behaves as follows:

  • Indexing by (row, col) is supported: grid[r, c] returns the subplot cell located at those coordinates (0-based).
  • Every cell carries an aprint(text) method that sets/adds that cell's text content. The text may contain embedded newlines (\n), which produce several lines inside the cell.
  • The object also exposes get_string(), a method that returns the grid in fully rendered form as a single string (no trailing newline).

How Rendering Works

Sizing and layout
  • The width of the rendered result is exactly width. Counted inside that width are the left border, the vertical separators standing between the columns, and the right border; the interior area is then split among the columns.
  • Every column receives an interior content area of the same width. If the interior does not divide evenly, the columns are sized such that the total (all border/separator columns included) comes out at exactly width. Columns that come earlier may be one character wider than columns that come later.
  • The interior area of a cell is where that cell's text is placed. Every line of text is truncated if that is needed for it to fit the cell's interior content width, and every line is horizontally centered within that area.
  • A cell's content lines are, in order: padding blank lines, then the cell's text lines, then padding blank lines again. All cells in one grid row have the same number of content lines — the maximum that any cell in that row needs — and cells that are shorter get extra blank lines added at the bottom, so that every cell in a row ends up with equal height.
  • Besides any padding lines, a blank content line (one space of vertical margin) sits at the top and at the bottom of every cell's content region.
Drawing the borders

Borders appear in three locations: around the grid as a whole, between rows that are adjacent, and between columns that are adjacent. Depending on the style that was selected, the rendering makes use of the following components:

  • Corners: top-left, top-right, bottom-left, bottom-right.
  • Horizontal line segments — at the top, at the bottom, and as the interior horizontal separators between rows.
  • Vertical line segments — on the left, on the right, and as the interior vertical separators between columns.
  • Junction characters, appearing where interior separators meet the outer border (top edge, bottom edge, left edge, right edge) and where interior separators cross one another.

Each column's interior has its full width covered by the horizontal border segments. At each point where a vertical separator meets a horizontal line, a junction character appears.

Task Specification: Customizable Border Style for Subplot Grid

Overview

Add support for a fully customizable border style to the subplot_grid functionality of the apl module. The public API to use is:

import apl
grid = apl.subplot_grid(shape, width=..., border_style=[...])

Public API

apl.subplot_grid(shape, width=None, border_style=None)
  • shape: a tuple (rows, cols) that gives the grid dimensions.
  • width: an integer that sets the total character width of the rendered grid.
  • border_style: a list of 11 single-character strings defining each border-drawing glyph (described below).

The return value is a grid object that:

  • Supports item access via grid[row, col], which obtains a cell object.
  • Each cell object comes with an aprint(text) method that writes text (possibly multi-line, using \n) into that cell.

Rendering of the table uses Unicode box-drawing characters. Each cell holds the str() representation of its value. For a table with R rows and C columns:

  • The top border line consists of ┌, then for each column a run of ─ characters equal to that column's width, with columns separated by ┬, ending with ┐.

Newline characters join the lines. After the bottom border there is no trailing newline.

Each column's width equals the maximum length of the str() representations of the values in that column. For a column, the horizontal border runs (─) span exactly that column's width.

{left edge:+.2e} - {right edge:+.2e}  [{count:Nd}]  {bar}

  • Heights and lengths undergo quantization to eighths of a character. For each count, the quantized amount is int(round(count / max(counts) * max_size * 8)), with max_size being 40 horizontally and 10 vertically.
  • In a UTF-8 output environment, and unless ASCII is forced, horizontal fractions 0..8 map to " ", "▏", "▎", "▍", "▌", "▋", "▊", "▉", "█", while vertical fractions map to " ", "▁", "▂", "▃", "▄", "▅", "▆", "▇", "█".
  • With force_ascii=True, * is used to render every nonzero fractional or full block. Only ASCII glyphs are contained in the generated histogram. In a non-UTF-8 output environment, these glyphs are also the fallback.
  • From every horizontal bar and from every rendered vertical row, trailing zero cells are removed.

Horizontal output has one row per count. Each row consists of the bin edges formatted as {:+.2e} and separated by -; two spaces; the count in square brackets, right-aligned to the decimal width of the largest count; two more spaces; and the bar. By default, the maximum bar occupies 40 cells. In ASCII mode, fractional nonzero cells become a full *, so a short nonzero bar still remains visible.

Vertical output is emitted from top to bottom in ten rows. Via Figure.hist, the default bar_width=1 provides one character column per bin; larger values duplicate each bin column. grid, which is optional, is a sequence of bin-boundary indices. In Unicode rendering, ▉ is used for the qualifying full cells immediately to the left of those boundaries, so that the divisions become visible. When strip=True is given, quantized-empty bins are removed from both ends before rendering, and boundary positions are adjusted accordingly. In vertical orientation, bin_edges are not printed. A two-character bar_width default applies in the lower-level vertical renderer, whereas calls through Figure.hist use the figure-level default of one character unless bar_width is explicitly supplied. Figure.hist returns None.

Data and size determination

data may be given in any of the following forms:

  • a row with one dimension;
  • rows arranged as a two-dimensional sequence or array; or
  • row groups arranged as a three-dimensional sequence, in the common case a header group followed by a body group.

The same number of columns must be present in every row. Each cell is converted using normal string formatting ("{}".format(value)), which preserves the stable ordinary representations of integers, floats, and strings. For each column, its width is the maximum resulting text width for that column across all groups, before padding.

Alignment and cell padding

alignment is either one of "l", "c", or "r", in which case that alignment applies to every column, or a string that contains exactly one such character per column. Left alignment is the default. When centered text has an odd number of spare cells, the extra space is placed on the right.

The common padding convention also governs cell padding. The default (0, 1) produces one space on both the left and right and no blank rows. Blank rows are inserted inside every logical table row by positive top or bottom padding.

Border styles and row groups

border_style accepts "thin", "rounded", "thick", "double", None, or a pair (regular_style, group_separator_style).

  • The outer border and the separators between rows in the same group are drawn with the regular style.
  • The separators between adjacent row groups are drawn with the second style.
  • The default ("thin", "double") therefore yields ordinary thin borders and a double-line header/body separator.
  • When a single style is passed, that style serves for both kinds of separator.

In a UTF-8 environment, the character sets of the regular style are, in the order horizontal, vertical, four corners, left/right junctions, top/bottom junctions, and cross:

  • thin: ─ │ ┌ ┐ └ ┘ ├ ┤ ┬ ┴ ┼;
  • rounded: ─ │ ╭ ╮ ╰ ╯ ├ ┤ ┬ ┴ ┼;
  • thick: ━ ┃ ┏ ┓ ┗ ┛ ┣ ┫ ┳ ┻ ╋;
  • double: ═ ║ ╔ ╗ ╚ ╝ ╠ ╣ ╦ ╩ ╬.

For mixed Unicode separators, the appropriate connecting glyphs are used. Specifically, thin/double uses ╞, ═, ╪, ╡, while thin/thick uses ┝, ━, ┿, ┥.

With force_ascii=True (or a non-UTF-8 output environment), the output consists of ASCII characters, and the generated borders are ASCII. Thin borders use -, |, and +; the default double group separator uses runs of = with + junctions. For thick and double regular borders, = is used horizontally and I and H are used vertically, respectively. Rounded ASCII borders place / and \ at the outer corners.

When border_style=None, no outer border, column delimiter, row divider, group divider, or extra blank group row is inserted.   • get_string() returns the complete layout, with lines joined by \n. Lines are right-stripped; the finished grid has no trailing whitespace or trailing newline.

Task Specification: Rendering Line Plots with asciiplotlib

Introduction

The package you will work on is asciiplotlib, a Python package (importable as asciiplotlib, conventionally aliased apl) for rendering plots and tables in text form. Your task is to implement the line-plot rendering behavior of the figure object such that its string output matches the exact format laid out below.

Public API

A figure factory and a figure object must be exposed by the package, with this surface:

  • apl.figure() — the return value is a figure object.
  • figure.plot(x, y, label=None, width=<int>, height=<int>, xlim=None, ylim=None, title=None) — records, for rendering, a line plot of the data series x vs y.
    • x, y: sequences of numeric values whose lengths are equal.
    • label: an optional string; if it is given, a legend entry is drawn inside the plot area.
    • width, height: integer inner dimensions of the plot area (in characters/rows) that the caller requests.
    • xlim, ylim: optional 2-tuples (min, max) that constrain the horizontal and vertical data ranges shown.
    • title: an optional string, drawn above the plot as a centered header.
  • figure.get_string() — returns the plot, fully rendered, as a single string (no trailing newline beyond what is described below).

Requirements for Rendering

Rendering produces a bordered chart that carries axis tick labels. The requirements that follow determine the exact character-level layout.

Structural outline
  1. Before the first content row, the returned string starts with exactly one newline character (\n).
  2. Newline characters serve as the row separators. At the very end of the string, no trailing newline is present.
  3. The chart is composed of:
    • A border row at the top.
    • A series of interior rows (the plotting canvas).
    • A border row at the bottom.
    • Below the bottom border, a row of x-axis tick labels.
  4. Plotting data points is done with the * character. To draw the continuous curve, * marks that approximate the data are placed across the canvas.
Y-axis labels and the left margin
  • A left margin for y-axis tick labels comes before each chart row.
  • The y-axis tick labels are right-aligned inside a margin of fixed width.
  • A subset of the interior rows carries labels; the label margins on the remaining interior rows are blank.
  • The label margin width is enough to accommodate the widest label (for negatives, a leading minus sign is included). With the label set 1, 0.8, 0.6, 0.4, 0.2, 0, -0.2, -0.4, -0.6, -0.8, -1, the formatting uses a fixed field, with the effect that, e.g., 1 renders as 1 and -0.2 renders as -0.2 at the row start (the label is separated from the border/canvas by a trailing space).
Gridlines and borders
  • On the top and bottom border rows, the corners and each x-tick position carry +, and - fills the space between them.
  • An interior row lined up with a labeled y-tick starts and ends with +; all the remaining interior rows start and end with |.
  • The x-tick positions on the top and bottom borders (together with the interior gridline columns) are spread evenly over the canvas width. + appears in the tick columns of the top/bottom border.

As a concrete case, take a width=50, height=15 request whose default y-limits are derived from data in [-1, 1]; the top border row is then:

Tick-label row for the x-axis
  • Below the bottom border comes an x-axis label row that lists the tick values; each of them is placed under its corresponding tick column, left-aligned at that column.
  • If the x data spans 0 to 7, this is the tick-label row:

  • If label is provided, the first interior row carries a legend entry, right-aligned toward the right side of the canvas; its form is <label> followed by a run of * characters representing the series marker. The leading newline of the whole string comes before this header. For a width=50 chart with title="header", the header line is the word header centered across the chart width, then an empty line, then the chart.
Axis limits (xlim / ylim)
  • If ylim is supplied, those bounds fix the vertical data range, and the y-tick labels are picked within that range (e.g. ylim=(-1, 1) yields labels 1, 0.5, 0, -0.5, -1).
  • If xlim is supplied, those bounds fix the horizontal data range, and the x-tick labels are picked within that range (e.g. xlim=(-1, 1) yields tick labels -1, -0.5, 0, 0.5, 1).
  • Data points that fall outside the supplied limits are clipped from the canvas; the in-range portion is the only part of the curve that gets drawn.

Task: Add support for horizontal bar charts to asciiplotlib

Summary

Implement a horizontal bar chart method on the figure object that the asciiplotlib package provides. The package can be imported as apl (import asciiplotlib as apl).

Public API

apl.figure()

A factory function that returns a figure object. The figure object must support the following methods, all of which are used in this task:

  • fig.barh(values, labels, force_ascii=False) — adds a horizontal bar chart to the figure.
  • fig.get_string() — returns the rendered figure as a single string, with no trailing newline.

Behavior of barh

fig.barh(values, labels, force_ascii=False) renders a horizontal bar chart, with one row per data point.

Parameters:

  • values: a list of non-negative numeric values, with one entry per bar.
  • labels: a list of strings, with one entry per bar, aligned with values by index.
  • force_ascii: a boolean keyword argument whose default is False. If the value is False, bars are drawn using the full-block character █ (U+2588). If the value is True, bars are drawn using the asterisk character *.
Row structure

Each row is made up of three sections separated by fixed spacing, in this order:

  1. Label section: the label string, which is left-aligned and padded on the right with spaces so that all labels occupy the same width equal to the length of the longest label. Two spaces follow this section.

  2. Value section: the numeric value, formatted as an integer and right-aligned inside brackets. The number is right-justified to the width of the widest value's digit-count, and is wrapped in [ and ]. For instance, with values 3, 10, 5, 2 the widest value has 2 digits, which produces [ 3], [10], [ 5], [ 2]. Two spaces follow this section.

  3. Bar section: a run of the bar character, with a length proportional to the value. The maximum value corresponds to a bar length of 40 characters; for every other bar, the length is round(value / max_value * 40). With values 3, 10, 5, 2 (max = 10), the bar lengths are 12, 40, 20, and 8 respectively.

Format of the output

get_string() returns all rows joined by newline characters; there is no trailing newline after the final row.
