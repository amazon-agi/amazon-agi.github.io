Task: Support for Counterpoise Correction in Gaussian Input Generation

Overview

The generator of Gaussian input files must support counterpoise correction (basis set superposition error, BSSE). Doing so requires accepting a new fragments parameter that assigns each atom in the molecule to a fragment, validating that assignment against the requested counterpoise level, and emitting the fragment assignments in the generated input file.

Public API and Invocation

Calculations are generated through the same entry point that is used elsewhere in the codebase (the mechanism by which a dictionary of parameters is converted into a calculation object exposing an input_file attribute containing the generated Gaussian input text).

A new key is now supported in the parameter dictionary:

  • fragments (string): a comma-separated list of integers with one entry per atom in the molecule, assigning each atom to a fragment number. For instance: "1,1,1,1,2,2,2,2,2".

Counterpoise correction is requested through the specifications string, which contains a counterpoise=N token, where N is the total number of fragments. For instance: "counterpoise=2". Trailing whitespace around the token may be present in the specifications string.

Behavior Requirements

Rendering of the keyword

When a counterpoise=N specification is supplied (together with valid fragments), the Gaussian route/command line must render the counterpoise keyword in the form:

counterpoise(N)

That is to say, counterpoise=N present in the input specifications is emitted as counterpoise(N) on the generated #p command line. The counterpoise/fragments handling should not result in any other keyword being added to the command line.

Fragment assignment inside the geometry block

Each atom line in the geometry block must be annotated with its fragment assignment when counterpoise correction is active. Rather than the plain element symbol, each atom is written as:

Element(Fragment=K) x y z

where K is the fragment number assigned to that atom (taken from the fragments list, in atom order), and x y z are the coordinates.

As an example, with fragments = "1,1,2,2,2,3,4,4,4" and counterpoise=4, the geometry block for an ethanol-derived structure appears as follows:

C(Fragment=1) ...
H(Fragment=1) ...
H(Fragment=2) ...
H(Fragment=2) ...
H(Fragment=2) ...
O(Fragment=3) ...
C(Fragment=4) ...
O(Fragment=4) ...
H(Fragment=4) ...
Validation and Error Conditions

InvalidParameter must be raised for each of the following situations:

  1. Incorrect number of fragment assignments: The number of entries in the fragments list does not equal the number of atoms the molecule contains. (E.g. 10 fragment entries supplied for a 9-atom molecule.)

  2. Fragment count mismatch: The number of distinct fragments that the fragments list implies does not equal the counterpoise level N. To put it concretely, when counterpoise=N is requested, the fragment numbers used must form a set that is exactly the integers 1 through N. (E.g. counterpoise=3 with fragments 1,2,3,3,3,4,5,5,5, which refers to fragment numbers beyond 3.)

  3. Fragment numbering does not start at 1: The fragment numbers must begin at 1. The assignment is invalid if the smallest fragment number used is not 1 (e.g. fragments 2,2,2,2,2,3,3,3,4).

The exception classes InvalidParameter and ImpossibleCalculation are the error types that already exist in the codebase, and they must be raised from the same location they are currently importable from.

Additional Notes

  • The fragment definitions must be consistent with the counterpoise level N: exactly the fragment numbers 1..N must each occur at least once, with total assignments equal to the atom count.
  • Only in combination with a counterpoise=N specification is the fragments parameter meaningful.
02 Handling Counterpoise Calculations in Gaussian Input Generation 764 words · rewritten by GPT-5.6-sol, reworded by GLM-5.3-Flash

Task Specification: Handling Counterpoise Calculations in Gaussian Input Generation

Summary

The pipeline that generates Gaussian input files is to be extended with support for Counterpoise (basis set superposition error correction) calculations. In a Counterpoise calculation, a molecule's atoms are divided into fragments, and a corrected energy calculation is requested. Users select the feature by placing a counterpoise=N entry in the calculation specifications they supply, and every atom is required to have an explicit fragment assignment.

API Surface

Callers reach this functionality via the calculation-generation entry point that already exists. At least the following keyword parameters of that entry point are relevant:

  • nproc (int): processor count.
  • mem (str): the memory specification, e.g. "10000MB".
  • type (str): the calculation type, e.g. "Single-Point Energy".
  • file (str): the geometry file supplied as input, e.g. "ethanol.xyz".
  • software (str): "Gaussian".
  • method (str): the electronic-structure method, e.g. "HF".
  • basis_set (str): the basis set, e.g. "3-21G".
  • charge (str): the molecule's charge, e.g. "0".
  • specifications (str): a free-form string of specifications, in which counterpoise=N may appear.
  • fragments (str): integer fragment indices as a comma-separated list — exactly one entry per atom.
  • solvent (str, optional): the solvent being requested.
  • solvation_model (str, optional): the solvation model being requested.

The existing InvalidParameter exception — importable from the package's exceptions module — must be raised for all invalid-parameter conditions described below.

Behavior Requirements

How the Counterpoise specification is read

When specifications includes counterpoise=N, with N a positive integer, the calculation in question is a Counterpoise calculation, and N is the fragment count that was requested. Whitespace left after the value must be tolerated; counterpoise=4 , for instance, must be parsed as a request for four fragments.

The counterpoise=N form is how callers express the option in the specification; it is the caller-facing syntax. The generated Gaussian route line, by contrast, requires the parenthesized syntax — the two spellings are distinct.

Assigning fragments and checking them

The following applies to a Counterpoise calculation:

  • fragments must contain the fragment indices as integers in a comma-separated list.
  • For every atom in the input geometry, the list must have exactly one entry; the entry order corresponds to the atom order in that geometry.
  • Every fragment index must lie in 1..N.
  • The distinct indices used must, taken together, amount to exactly {1, 2, ..., N}. Fragment numbering must therefore start at 1 and stay contiguous; every requested fragment must be used, and the calculation must not use any additional fragment.

Validation must be complete before an input file is produced. InvalidParameter must be raised when the assignment is missing or malformed, when an entry is not an integer, when the number of assignments does not match, or when the required fragment-index set is violated in any way. Specifically, all of the cases below are invalid:

  • A request carrying counterpoise=2 whose assignments contain fragment 5.
  • With counterpoise=3, a request whose distinct assignments amount to {1, 2, 3, 4, 5}.
  • With counterpoise=3, a request whose distinct assignments amount to {2, 3, 4}.
  • Any assignment list whose entry count is more or fewer than the number of atoms the geometry has.
Mutual exclusivity with solvation

Solvation and Counterpoise cannot be combined. If counterpoise=N is present and the solvation request provides both solvent and solvation_model, generation must raise InvalidParameter, even if the fragment specification is valid in every other respect. To illustrate: a valid four-fragment Counterpoise assignment combined with solvent="dichloromethane" and solvation_model="PCM" must fail, and a Gaussian input file must not be produced in that scenario.

The Gaussian file for a valid request

When the Counterpoise calculation is valid and involves no solvation, the generated Gaussian input file must:

  • Write the route option exactly in the parenthesized form Gaussian uses, counterpoise(N). Caller input given as counterpoise=4, for example, must therefore show up in the route line as counterpoise(4) and not as counterpoise=4.

  • Annotate each atom's element symbol with the assignment matching it, in the form Element(Fragment=K); the K here is the fragment index sitting at that atom's position in the fragments list. For example:

    O(Fragment=2) 0.62360000 0.07990000 1.25870000
H(Fragment=2) 0.94410000 0.53240000 2.04240000

  • Keep, in all other respects, the standard Gaussian input structure that the existing generation pipeline uses, including processor and memory headers, the calculation command containing the method and the basis set, the title, the charge/multiplicity line, and the geometry block. One representative route line:

    #p sp HF/3-21G counterpoise(4)

The fragment annotations must keep the original atom order and coordinates intact.

03 The ccinput package is to be extended with Q-Chem input-file generation. 1385 words · rewritten by GPT-5.6-sol, reworded by GLM-5.3-Flash

Overview

The ccinput package is to be extended with Q-Chem input-file generation. Selecting software="QChem" must make Q-Chem available through the package's existing software-dispatching calculation interface. The result must be a Q-Chem input string put together from $section ... $end blocks.

All existing behavior for other software targets must stay compatible.

Public API

ccinput.wrapper.gen_obj, the existing calculation entry point that returns an object, must accept software="QChem" and return a calculation result in which the .input_file attribute is the generated Q-Chem input as a string. A separate public entry point dedicated to Q-Chem is not required.

ccinput.exceptions.InvalidParameter must remain importable, and it must be used for the conflicting-dispersion error described below.

The calculation keyword arguments that are relevant here are:

  • type: the calculation type.
  • file: the geometry source, given as an .xyz file. The package's existing coordinate parsing and default charge/multiplicity handling apply.
  • software: "QChem" selects this target.
  • method: the computational method, such as "AM1", "HF", "M06-2X", "B3LYP", "PBE0", or "M062X".
  • basis_set: the basis set, such as "3-21G", "Def2-SVP", "6-31+G(d,p)", or "Def2TZVP". For semi-empirical methods, it is omitted from the generated Q-Chem input.
  • charge: the molecular charge. In the molecule section, the existing multiplicity value/default is used alongside it.
  • mem: an optional memory specification, such as "2000MB" or "1200MB". When it is omitted, the Q-Chem total-memory value is 1000.
  • solvent: a solvent name, or an accepted synonym/variant that the existing solvent-name infrastructure resolves.
  • solvation_model: "SMD" or "CPCM", treated case-insensitively.
  • custom_solvation_radii: per-element radius overrides separated by semicolons, such as "Cl=1.00;" or "Cl=1.00;Br=2.00;".
  • specifications: a free-form specification string. The Q-Chem-specific flag that is in scope is "--phirshfeld".
  • d3 and d3bj: booleans that select a dispersion correction.
  • custom_basis_sets: accepted as an input parameter, but it has no effect on Q-Chem output for the calculation types in scope.

Document Layout and Whitespace

The top-level blocks must occur in this order:

  1. $comment
  2. $molecule
  3. $rem
  4. Any blocks for model-specific solvation
  5. $van_der_waals, when required by CPCM custom radii

Where blank lines appear is part of the output contract:

  • Each section opener, each content line of that section, and its $end line must be consecutive. Inside a section there must be no empty line.
  • Between each pair of consecutive top-level section blocks there must be exactly one empty line. This holds between $comment, $molecule, and $rem, and likewise between every later solvation or van-der-Waals block.
  • Empty lines at the very beginning or very end of the document as a whole are immaterial.
  • Aside from this blank-line placement, leading and trailing whitespace on individual lines is immaterial. The section tokens, the contents of the lines, the order of lines within each section, and the order of sections must match this specification.

A calculation without solvation is therefore composed of $comment, one empty separator line, $molecule, one empty separator line, and $rem. SMD appends $smx; CPCM appends $pcm and $solvent, followed by $van_der_waals only when applicable, with exactly one empty separator line at every boundary.

Sections That Must Be Present

$comment

This block is always present, and its content is exactly:

$comment
File created by ccinput
$end
$molecule

This block is always present. The first content line consists of the molecular charge and multiplicity separated by whitespace. After it comes one line per atom, each giving the element symbol and that atom's three Cartesian coordinates, as supplied by the package's existing geometry infrastructure.

As an example:

$molecule
-1 1
Cl 0.0 0.0 0.0
$end
$rem

The $rem block is composed of key = value lines. The lines that follow must be included only when applicable, and in exactly this relative order:

  1. Job type, present in every calculation:

    jobtype = <value>

    Calculation types map as follows:

    Supplied type Value for Q-Chem
    Single-Point Energy sp
    Geometrical Optimisation opt
    Frequency Calculation freq
    TS Optimisation ts
    NMR Prediction sp
    opt opt

  2. NMR property request, present only for NMR Prediction, placed immediately after jobtype:

    moprop = nmr

  3. Method, present in every calculation, lowercased with Q-Chem normalization:

    method = <method>

    Required examples of this normalization include AM1 to am1, HF to hf, M06-2X to m06-2x, B3LYP to b3lyp, and PBE0 to pbe0. The spelling M062X must also normalize to m06-2x.

  4. Semi-empirical marker, present only for semi-empirical methods, as with AM1:

    semi_empirical = true

    A calculation that is semi-empirical must not contain a basis line.

  5. Basis set, present when the method is not semi-empirical:

    basis = <basis_set>

    The value is lowercased and normalized for Q-Chem. Required examples of this normalization include 3-21G to 3-21g, Def2-SVP to def2-svp, 6-31+G(d,p) to 6-31+g(d,p), and Def2TZVP to def2-tzvp.

  6. Total memory, present in every calculation:

    mem_total = <value>

    The memory value must be emitted as the numeric total in MB, following the package's existing memory normalization. The default is 1000; for example, "2000MB" produces 2000 and "1200MB" produces 1200.

  7. Solvation method, present when supported implicit solvation has been requested:

    • SMD:

      solvent_method = smd

    • CPCM:

      solvent_method = pcm

  8. Hirshfeld population analysis, present when specifications requests it by way of --phirshfeld:

    hirshfeld = true

  9. Dispersion correction, present when one is requested:

    • d3=True:

      dft_d = d3_zero

    • d3bj=True:

      dft_d = d3_bj

As an example, the $rem content of a non-solvated D3 optimization is:

$rem
jobtype = opt
method = m06-2x
basis = def2-tzvp
mem_total = 1000
dft_d = d3_zero
$end

Solvation

Solvation-model names are case-insensitive; for instance, "SMD" and "smd" produce identical output. Before they are written, solvent names and accepted synonyms are resolved through the package's solvent infrastructure.

The solvent-resolution behavior that is required includes:

  • Chloroform and CHCL3 are resolved to trichloromethane.
  • Under SMD, octanol resolves to 1-octanol.
  • Under CPCM, octanol and 1-octanol both resolve to octanol.
SMD

With SMD, add solvent_method = smd to $rem, and then append the following block after $rem:

$smx
solvent <resolved_solvent_name>
$end

For chloroform, the block that gets appended, in full, is:

$smx
solvent trichloromethane
$end
CPCM

With CPCM, add solvent_method = pcm to $rem, and then append the following blocks, in order, after $rem:

$pcm
theory cpcm
$end

$solvent
solventname <resolved_solvent_name>
$end

The empty line shown between the blocks is required, and it is the only empty line between them. For chloroform, the solvent line reads:

solventname trichloromethane
Custom Solvation Radii under CPCM

Custom solvation radii have an effect on the Q-Chem output only in the CPCM layout described here. When custom_solvation_radii is supplied together with CPCM:

  1. In $pcm, add radii read immediately after theory cpcm.
  2. Keep the $solvent block positioned after $pcm.
  3. Then append $van_der_waals after $solvent.
  4. Start $van_der_waals with a line that contains 1.
  5. For each override, emit the element's atomic number followed by the radius value that was supplied. The override order from the input string must be preserved.

With custom_solvation_radii="Cl=1.00;", Cl turns into atomic number 17:

$pcm
theory cpcm
radii read
$end

$solvent
solventname trichloromethane
$end

$van_der_waals
1
17 1.00
$end

With custom_solvation_radii="Cl=1.00;Br=2.00;", the content of $van_der_waals is:

$van_der_waals
1
17 1.00
35 2.00
$end

As everywhere else in the document, these blocks contain no empty lines, and there is exactly one empty line between adjacent blocks.

Validation and Behavior on Error

  • A solvation_model that is unsupported, such as "ABC", must cause calculation generation to raise an exception rather than produce Q-Chem text.
  • When both d3=True and d3bj=True are requested in the same calculation, ccinput.exceptions.InvalidParameter must be raised.

Compatibility and Non-Effects

  • Supplying custom_basis_sets must not alter Q-Chem output for the calculation types covered here. With inputs that are otherwise identical, the output produced with this parameter is identical to the output produced without it.
  • The source of the corresponding normalized values used in Q-Chem output remains the existing XYZ parsing, coordinate generation, charge/multiplicity handling, memory normalization, method/basis aliases, and solvent synonym handling.
04 Extend the existing ccinput calculation-generation pipeline with Psi4 input generation. 976 words · rewritten by GPT-5.6-sol, reworded by GLM-5.3-Flash

Specification of the Task

Task: Add Support for Generating Psi4 Input Files

Extend the existing ccinput calculation-generation pipeline with Psi4 input generation. Wherever the package dispatches an already-supported software value, the canonical software value "psi4" must be recognized. The existing behavior of all other software packages must remain unchanged.

Public API and Integration

A new public entry point is not required. Psi4 must operate through the existing public generation APIs in ccinput.wrapper:

  • gen_obj(**parameters) must return a generated calculation object in which the input_file attribute holds the Psi4 input text as a string.
  • gen_input(**parameters) must return the same generated text by way of the package's normal string-producing path.

In other words, choosing software="psi4" must take part in the same software normalization, parameter processing, geometry loading, and dispatch flow as the existing packages.

The public exceptions that matter are imported from ccinput.exceptions:

  • ImpossibleCalculation
  • InvalidParameter

Parameters Used as Input

A Psi4 request is built on the existing parameter dictionary and includes:

  • type: the calculation type that is requested.
  • file: a geometry file that supplies the atomic coordinates, such as an XYZ file.
  • software: "psi4".
  • method: the computational method, such as "hf" or "b3lyp". Matching of the method is case-insensitive.
  • basis_set: the basis set in the package's accepted loose form, such as "sto3g", "def2-tzvp", "ccpVDZ", or "631g". It must be rendered with the Psi4 spelling described below.
  • charge: the molecular charge. A string whose value is an integer, such as "-1", must be accepted and interpreted as an integer.
  • multiplicity (optional): the spin multiplicity. A string whose value is an integer, such as "1", must be accepted and interpreted as an integer. When it is omitted, the default is 1.

The common validation that the existing generation pipeline performs still applies. Where applicable, invalid parameters continue to use InvalidParameter; Psi4 support must not bypass or replace that validation.

Calculation Types Supported

Within this task, Psi4 supports exactly the following calculation categories:

  1. Single-point energy — this covers the existing type aliases that normalize to single-point energy, such as "Energy".
  2. Geometry optimization — this covers the existing type aliases that normalize to optimization, such as "Geometrical Optimisation" and "Opt".

The type determines the final Psi4 function:

Category of calculation Psi4 function
Single-point energy energy
Geometry optimization optimize

Format of the Generated Input

The generated string is made up of one molecule block followed by one Psi4 calculation command. For a geometry that contains one or more atoms, the internal lines must occur in this exact order:

  1. molecule {
  2. <charge> <multiplicity>
  3. For each atom, one contiguous coordinate line, in input order
  4. After the final atom, exactly one empty line
  5. }
  6. After the closing brace, exactly one empty line
  7. <command>('<method>/<basis_set>')

Within this content, no other empty lines may occur. In particular, no empty line is present immediately after molecule {, between the charge/multiplicity line and the first atom, or between atom lines. Even though indentation and leading or trailing horizontal whitespace on nonempty lines are not significant, the two separator lines listed above are required. Whitespace surrounding the complete content is likewise not significant; what is significant is the internal empty-line count and placement. It is optional whether a final newline is present after the command.

The overall shape is therefore:

molecule {
<charge> <multiplicity>
<element>   <x>   <y>   <z>
...

}

<command>('<method>/<basis_set>')
The Molecule Block
  • The charge and multiplicity are emitted as normalized integer values, with whitespace separating them.
  • Each atom is emitted on a line of its own.
  • Element symbols are written with their normalized chemical capitalization.
  • Each X, Y, and Z coordinate is formatted with exactly eight digits after the decimal point.
  • The ordering of atoms from the supplied geometry is preserved.

With charge -1 and multiplicity 1, the complete single-point HF output for a chlorine atom at the origin is:

molecule {
-1 1
Cl   0.00000000   0.00000000   0.00000000

}

energy('scf/sto-3g')
Rendering of the Method

The method and basis set are put together into one single-quoted argument of the form '<method>/<basis_set>'.

  • Hartree–Fock input, written as hf in any letter case, is emitted as scf.
  • DFT methods are emitted with their lowercase names; B3LYP, for instance, is emitted as b3lyp.
Rendering of the Basis Set

The basis set must be normalized to the canonical spelling that this Psi4 output requires. At minimum, the accepted forms listed below must produce exactly these spellings:

Input accepted Value emitted
sto3g sto-3g
def2-tzvp def2-tzvp
ccpVDZ or cc-pvdz cc-pVDZ
631g 6-31G

Consequently, the command forms that are required include:

  • Single-point HF with STO-3G: energy('scf/sto-3g')
  • Single-point B3LYP with def2-TZVP: energy('b3lyp/def2-tzvp')
  • HF optimization using cc-pVDZ: optimize('scf/cc-pVDZ')
  • B3LYP optimization using 6-31G: optimize('b3lyp/6-31G')

Behavior on Error

When a calculation type that is otherwise recognized is not supported for Psi4, generation must raise ImpossibleCalculation. This holds for every category other than single-point energy and geometry optimization; to give an example, a request with type="freq" must fail with ImpossibleCalculation instead of producing an input file.

As appropriate, values that are not valid parameters for the common generation pipeline continue to raise InvalidParameter. A new exception type or public generation function is not required.

Scope and Compatibility

  • Psi4 support must be added in a way that does not change the generated output or the public behavior for existing software selections.
  • For Psi4, only single-point energies and geometry optimizations are required.
  • The Psi4 text that is required is the molecule block and calculation command described above; no separate Psi4-specific public API is introduced.

Goal

Modify the default RMSD threshold value that is used when CREST conformational search commands are generated.

Context

The codebase produces command-line invocations for the CREST tool (which is used with the XTB software backend). When a CREST calculation is configured without an RMSD threshold that has been explicitly specified, a default value is applied to the -rthr command-line flag.

Change Required

crest ethanol.xyz -cinp input -rthr 2.0 -ewin 6

  • All other aspects of CREST command generation (flag names, flag ordering, -ewin handling, -cinp handling, the trailing/leading command structure) stay exactly as they were.
  • No new API surface is added. The change is limited to the default value used when commands are constructed.

Specifications

The specifications string consists of a semicolon-separated list of directives, each of the form name(content). Whitespace around directives is tolerated, and directive names are matched case-insensitively; the option lines that are emitted appear in lowercase form, so SCF(Tight) and scf(tight) are equivalent.

Any token in the string that does not constitute a recognized name(content) directive — including arbitrary non-directive characters such as !# — is silently skipped: it produces no option line, no block, and no error. (The only recognized bare token is string; it is described in the MEP section below.)

A directive whose target block is not applicable to the calculation type is likewise silently ignored: no corresponding block is emitted, and the calculation_block attribute contains no non-whitespace content. For instance, an opt(...) directive on a single-point calculation produces no driver block, and a freq(...) directive on a pure optimisation produces no freq block; in both cases the remainder of the input is generated exactly as if the directive were absent.

The recognized option literals include the following:

  • Tight or tight -> line tight
  • Direct or direct -> line direct
  • grid <args> -> line grid <args> (for example grid coarse)
  • maxiter <N> -> line maxiter <N>
  • odft -> line odft

Task: Supporting an Alternative Specification Syntax in NWChem Input Generation

Background

The codebase produces input files for quantum chemistry, covering a number of different software packages. What this task targets is the generator for NWChem input — more precisely, its parsing of the specifications string supplied by the user, which controls the per-block options in the input that gets generated.

Public API

A factory function is what produces the calculations: it accepts calculation parameters as keyword arguments, and the object it returns carries an input_file attribute — a string holding the generated NWChem input. The keyword arguments that matter include:

  • nproc (int)
  • mem (str, e.g. "10000MB")
  • type (str, e.g. "Single-Point Energy", "Geometrical Optimisation")
  • file (str, filename of the input structure)
  • software (str, "nwchem")
  • method (str, e.g. "M06-2X")
  • basis_set (str, e.g. "Def2-SVP")
  • charge (str/int)
  • specifications (str) — the subject of this task

With the exception of the additional syntax accepted in specifications (described below), the public entry point that already exists behaves as it always has.

Behavior Requirements

Inside the specifications string, options are encoded in groups tied to a "block" keyword, by way of a parenthesized syntax:

BLOCKNAME(option[, option]...)

Several such groups may show up within a single specifications string. All of the syntactic variations listed below must be accepted and correctly handled by the parser; in terms of the options each one defines, the variations are to be treated equivalently:

  1. Options inside one group separated by commas, no spaces present: SCF(Tight,Direct) → yields tight and direct as the options for the SCF block.

  2. Options inside one group separated by commas, spaces present after the commas: SCF(Tight, Direct) → yields tight and direct.

  3. A block group repeated, with whitespace dividing the groups: SCF(Tight) scf(direct) → yields tight and direct. Block-name matching ignores case.

  4. Several blocks that differ from one another, divided by whitespace: SCF(Tight) opt(maxiter 5) → yields tight for SCF, plus maxiter 5 for the optimization/driver block.

  5. A semicolon as the separator between groups (with surrounding blocks after it, or without): SCF(Tight); opt(maxiter 5) scf(direct) → yields, for SCF, tight and direct, and for the driver block, maxiter 5.

In each of these situations:

  • Matching of block names is performed case-insensitively (SCF, scf, opt are all recognized).
  • Tokens for options inside the parentheses are emitted lowercased into the output block that corresponds to them.
  • Where an option is itself a keyword together with an argument (e.g. maxiter 5), that option is kept as a single option line (maxiter 5).
  • Between groups, both semicolons and whitespace function as separators.
Mapping from blocks to output
  • The options coming from SCF(...) are written into the dft block one line apiece, appended after the xc and mult lines.
  • The options coming from opt(...) are written one line apiece into a driver block that is separate.

direct
end

and after that:

tight
end

maxiter 5
end

task dft optimize

When specifications = SCF(Tight); opt(maxiter 5) scf(direct) is used for a geometry optimization, the generated input contains:

dft
xc m06-2x
mult 1
tight
direct
end

driver
maxiter 5
end

task dft optimize

Within a block, options are placed in the sequence in which they occur across the parsed specifications string.

Specification of the Task

Background

Based on a set of calculation parameters, this codebase generates quantum chemistry input files for NWChem. A memory total <N> mb directive, which states the total memory available to the NWChem calculation, appears in every generated input file.

Required Modification

The memory value that the generated NWChem input files emit in the memory total <N> mb line must be corrected.

At present, when the memory specification corresponds to 10000 MB total requested memory, the line written into the generated input is:

memory total 10000 mb

Instead, the following value must be emitted:

memory total 1250 mb
Details of the Behavior
  • When a calculation is configured with the standard/default memory amount used throughout the NWChem input generation (the amount that previously produced memory total 10000 mb), the generated NWChem input must now contain the line memory total 1250 mb in its place.
  • The correction applies uniformly to every NWChem input file that the generator produces, irrespective of the specific calculation type (single point, optimization, frequencies, transition-state search, NEB, constrained/scan calculations, solvation variants, effective-core-potential/basis-set variants, etc.), the molecule involved, or the charge.
  • Everything else in the generated NWChem input files must remain unchanged: the TITLE, start <name>, charge, geometry block, and all method/basis/task directives are unaffected. The numeric value on the memory total ... mb line is the only thing that changes: it goes from 10000 to 1250.
  • The unit stays mb, and the line format surrounding it (memory total <value> mb, with the same indentation and placement as before — immediately after the start <name> line and before the charge line) is preserved exactly.

In brief: the factor that translates the requested memory into the value written on the NWChem memory total line must be adjusted, so that what used to be rendered as 10000 is now rendered as 1250 (that is, for the standard case the written value is one-eighth of the previous value).
