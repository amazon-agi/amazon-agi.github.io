Task: Counterpoise Correction Support for Gaussian Input Generation

Overview

The Gaussian input file generator must support counterpoise (basis set superposition error, BSSE) correction. This requires accepting a new fragments parameter that assigns each atom in the molecule to a fragment, validating that assignment against the requested counterpoise level, and emitting the fragment assignments in the generated input file.

Public API / Invocation

Calculations are generated through the same entry point used elsewhere in the codebase (the mechanism by which a dictionary of parameters is turned into a calculation object exposing an input_file attribute containing the generated Gaussian input text).

The parameter dictionary now supports a new key:

  • fragments (string): a comma-separated list of integers, one per atom in the molecule, assigning each atom to a fragment number. Example: "1,1,1,1,2,2,2,2,2".

Counterpoise correction is requested via the specifications string containing a counterpoise=N token, where N is the total number of fragments. Example: "counterpoise=2". The specifications string may contain trailing whitespace around the token.

Required Behavior

Keyword rendering

When a counterpoise=N specification is provided (with valid fragments), the Gaussian route/command line must render the counterpoise keyword in the form:

counterpoise(N)

That is, counterpoise=N in the input specifications is emitted as counterpoise(N) in the generated #p command line. No other keyword should be added to the command line as a result of the counterpoise/fragments handling.

Fragment assignment in the geometry block

When counterpoise correction is active, each atom line in the geometry block must be annotated with its fragment assignment. Instead of the plain element symbol, each atom is written as:

Element(Fragment=K) x y z

where K is the fragment number assigned to that atom (from the fragments list, in atom order), and x y z are the coordinates.

For example, with fragments = "1,1,2,2,2,3,4,4,4" and counterpoise=4, the geometry block for an ethanol-derived structure appears as:

C(Fragment=1) ...
H(Fragment=1) ...
H(Fragment=2) ...
H(Fragment=2) ...
H(Fragment=2) ...
O(Fragment=3) ...
C(Fragment=4) ...
O(Fragment=4) ...
H(Fragment=4) ...
Validation / Error Conditions

The following situations must raise InvalidParameter:

  1. Wrong number of fragment assignments: The number of entries in the fragments list does not equal the number of atoms in the molecule. (E.g. a 9-atom molecule given 10 fragment entries.)

  2. Fragment count mismatch: The number of distinct fragments implied by the fragments list does not equal the counterpoise level N. Concretely, when counterpoise=N is requested, the set of fragment numbers used must be exactly the integers 1 through N. (E.g. counterpoise=3 with fragments 1,2,3,3,3,4,5,5,5, which references fragment numbers beyond 3.)

  3. Fragment numbering does not start at 1: The fragment numbers must begin at 1. If the smallest fragment number used is not 1 (e.g. fragments 2,2,2,2,2,3,3,3,4), the assignment is invalid.

The exception classes InvalidParameter and ImpossibleCalculation are the existing error types in the codebase and must be raised from the same location they are currently importable from.

Notes

  • The counterpoise level N and the fragment definitions must be consistent: exactly the fragment numbers 1..N must each appear at least once, with total assignments equal to the atom count.
  • The fragments parameter is only meaningful in combination with a counterpoise=N specification.

Task Specification: Counterpoise Calculation Support for Gaussian Input Generation

Overview

Add support for Counterpoise (basis set superposition error correction) calculations in the Gaussian input-file generation pipeline. A Counterpoise calculation partitions the atoms of a molecule into fragments and requests a corrected energy calculation. The feature is selected through a counterpoise=N entry in the user-supplied calculation specifications and requires an explicit fragment assignment for every atom.

Public API

The functionality is available through the existing calculation-generation entry point. Its relevant keyword parameters include at least:

  • nproc (int): number of processors.
  • mem (str): memory specification, for example "10000MB".
  • type (str): calculation type, for example "Single-Point Energy".
  • file (str): input geometry file, for example "ethanol.xyz".
  • software (str): "Gaussian".
  • method (str): electronic-structure method, for example "HF".
  • basis_set (str): basis set, for example "3-21G".
  • charge (str): molecular charge, for example "0".
  • specifications (str): free-form specification string, which may contain counterpoise=N.
  • fragments (str): comma-separated integer fragment indices, with exactly one entry per atom.
  • solvent (str, optional): requested solvent.
  • solvation_model (str, optional): requested solvation model.

All invalid-parameter conditions described below must raise the existing InvalidParameter exception, importable from the package's exceptions module.

Required Behavior

Counterpoise specification parsing

When specifications contains counterpoise=N, where N is a positive integer, the calculation is a Counterpoise calculation and N is the requested number of fragments. Trailing whitespace after the value must be tolerated; for example, counterpoise=4 must be parsed as a four-fragment request.

The counterpoise=N spelling is the caller-facing specification syntax. It is distinct from the parenthesized syntax required in the generated Gaussian route line.

Fragment assignment and validation

For a Counterpoise calculation:

  • fragments must provide a comma-separated list of integer fragment indices.
  • The list must contain exactly one entry for every atom in the input geometry; its order corresponds to the atom order in that geometry.
  • Every fragment index must lie in the range 1..N.
  • The set of distinct indices used must be exactly {1, 2, ..., N}. Thus fragment numbering must begin at 1, remain contiguous, use every requested fragment, and use no additional fragment.

Validation must occur before an input file is produced. A missing or malformed assignment, a non-integer entry, an assignment-count mismatch, or any violation of the required fragment-index set must raise InvalidParameter. In particular, all of the following are invalid:

  • A counterpoise=2 request whose assignments include fragment 5.
  • A counterpoise=3 request whose distinct assignments are {1, 2, 3, 4, 5}.
  • A counterpoise=3 request whose distinct assignments are {2, 3, 4}.
  • Any assignment list with more or fewer entries than the number of atoms in the geometry.
Incompatibility with solvation

Counterpoise and solvation cannot be combined. If counterpoise=N is present and a solvation request supplies both solvent and solvation_model, generation must raise InvalidParameter, even if the fragment specification is otherwise valid. For example, a valid four-fragment Counterpoise assignment combined with solvent="dichloromethane" and solvation_model="PCM" must fail rather than produce a Gaussian input file.

Gaussian output for a valid request

For a valid, non-solvated Counterpoise calculation, the generated Gaussian input file must:

  • Render the route option exactly in Gaussian's parenthesized form counterpoise(N). For example, the caller input counterpoise=4 must appear in the route line as counterpoise(4), not as counterpoise=4.

  • Annotate each atom's element symbol with its corresponding assignment using Element(Fragment=K), where K is the fragment index at the same position in the fragments list. For example:

    O(Fragment=2) 0.62360000 0.07990000 1.25870000
H(Fragment=2) 0.94410000 0.53240000 2.04240000

  • Otherwise retain the standard Gaussian input structure used by the existing generation pipeline, including processor and memory headers, the calculation command with method and basis set, the title, the charge/multiplicity line, and the geometry block. A representative route line is:

    #p sp HF/3-21G counterpoise(4)

The fragment annotations must preserve the original atom order and coordinates.

03 Add Q-Chem input-file generation to the ccinput package. 1261 words · rewritten by GPT-5.6-sol

Overview

Add Q-Chem input-file generation to the ccinput package. Q-Chem must be available through the package's existing software-dispatching calculation interface by selecting software="QChem". The result must be a Q-Chem input string assembled from $section ... $end blocks.

All existing behavior for other software targets must remain compatible.

Public API

The existing object-returning calculation entry point, ccinput.wrapper.gen_obj, must accept software="QChem" and return a calculation result whose .input_file attribute is the generated Q-Chem input as a string. No separate Q-Chem-only public entry point is required.

ccinput.exceptions.InvalidParameter must remain importable and must be used for the conflicting-dispersion error described below.

The relevant calculation keyword arguments are:

  • type: calculation type.
  • file: geometry source, supplied as an .xyz file. Coordinate parsing and the package's existing default charge/multiplicity handling apply.
  • software: "QChem" for this target.
  • method: computational method, such as "AM1", "HF", "M06-2X", "B3LYP", "PBE0", or "M062X".
  • basis_set: basis set, such as "3-21G", "Def2-SVP", "6-31+G(d,p)", or "Def2TZVP". It is omitted from the generated Q-Chem input for semi-empirical methods.
  • charge: molecular charge. The existing multiplicity value/default is used with it in the molecule section.
  • mem: optional memory specification, such as "2000MB" or "1200MB". If omitted, the Q-Chem total-memory value is 1000.
  • solvent: solvent name or an accepted synonym/variant resolved by the existing solvent-name infrastructure.
  • solvation_model: "SMD" or "CPCM", case-insensitively.
  • custom_solvation_radii: semicolon-separated per-element radius overrides, such as "Cl=1.00;" or "Cl=1.00;Br=2.00;".
  • specifications: free-form specification string. The Q-Chem-specific flag in scope is "--phirshfeld".
  • d3 and d3bj: booleans selecting a dispersion correction.
  • custom_basis_sets: accepted as an input parameter but does not affect Q-Chem output for the calculation types in scope.

Document Structure and Whitespace

Top-level blocks must occur in this order:

  1. $comment
  2. $molecule
  3. $rem
  4. Any model-specific solvation blocks
  5. $van_der_waals, when CPCM custom radii require it

Blank-line placement is part of the output contract:

  • Every section opener, every content line in that section, and its $end line must be consecutive. There must be no empty line inside a section.
  • There must be exactly one empty line between each pair of consecutive top-level section blocks. This applies between $comment, $molecule, and $rem, as well as between every later solvation or van-der-Waals block.
  • Leading or trailing empty lines around the entire document are immaterial.
  • Except for this blank-line placement, leading and trailing whitespace on individual lines is immaterial. The section tokens, line contents, line order within each section, and section order must match this specification.

Thus, a calculation without solvation consists of $comment, one empty separator line, $molecule, one empty separator line, and $rem. SMD appends $smx; CPCM appends $pcm and $solvent, followed by $van_der_waals only when applicable, with exactly one empty separator line at every boundary.

Required Sections

$comment

This block is always present and contains exactly:

$comment
File created by ccinput
$end
$molecule

This block is always present. Its first content line is the molecular charge and multiplicity separated by whitespace. It is followed by one line per atom containing the element symbol and its three Cartesian coordinates, as supplied by the package's existing geometry infrastructure.

For example:

$molecule
-1 1
Cl 0.0 0.0 0.0
$end
$rem

The $rem block consists of key = value lines. Include the following lines only when applicable and in exactly this relative order:

  1. Job type, always present:

    jobtype = <value>

    Map calculation types as follows:

    Input type Q-Chem value
    Single-Point Energy sp
    Geometrical Optimisation opt
    Frequency Calculation freq
    TS Optimisation ts
    NMR Prediction sp
    opt opt

  2. NMR property request, present only for NMR Prediction and immediately after jobtype:

    moprop = nmr

  3. Method, always present and lowercased using Q-Chem normalization:

    method = <method>

    Required examples include AM1 to am1, HF to hf, M06-2X to m06-2x, B3LYP to b3lyp, and PBE0 to pbe0. The spelling M062X must also normalize to m06-2x.

  4. Semi-empirical marker, present only for semi-empirical methods such as AM1:

    semi_empirical = true

    A semi-empirical calculation must not contain a basis line.

  5. Basis set, present for non-semi-empirical methods:

    basis = <basis_set>

    The value is lowercased and normalized for Q-Chem. Required examples include 3-21G to 3-21g, Def2-SVP to def2-svp, 6-31+G(d,p) to 6-31+g(d,p), and Def2TZVP to def2-tzvp.

  6. Total memory, always present:

    mem_total = <value>

    Emit the memory value as the numeric total in MB after the package's existing memory normalization. The default is 1000; for example, "2000MB" produces 2000 and "1200MB" produces 1200.

  7. Solvation method, present when supported implicit solvation is requested:

    • SMD:

      solvent_method = smd

    • CPCM:

      solvent_method = pcm

  8. Hirshfeld population analysis, present when specifications requests it with --phirshfeld:

    hirshfeld = true

  9. Dispersion correction, present when requested:

    • d3=True:

      dft_d = d3_zero

    • d3bj=True:

      dft_d = d3_bj

For example, a non-solvated D3 optimization has the following $rem content:

$rem
jobtype = opt
method = m06-2x
basis = def2-tzvp
mem_total = 1000
dft_d = d3_zero
$end

Solvation

Solvation-model names are case-insensitive; for example, "SMD" and "smd" produce identical output. Solvent names and accepted synonyms are resolved through the package's solvent infrastructure before they are written.

Required solvent-resolution behavior includes:

  • Chloroform and CHCL3 resolve to trichloromethane.
  • For SMD, octanol resolves to 1-octanol.
  • For CPCM, both octanol and 1-octanol resolve to octanol.
SMD

For SMD, add solvent_method = smd to $rem, then append this block after $rem:

$smx
solvent <resolved_solvent_name>
$end

For chloroform, the complete appended block is:

$smx
solvent trichloromethane
$end
CPCM

For CPCM, add solvent_method = pcm to $rem, then append these blocks in order after $rem:

$pcm
theory cpcm
$end

$solvent
solventname <resolved_solvent_name>
$end

The empty line shown between the blocks is required and is the only empty line between them. For chloroform, the solvent line is:

solventname trichloromethane
CPCM Custom Solvation Radii

Custom solvation radii affect the Q-Chem output only in the CPCM layout described here. When custom_solvation_radii is supplied with CPCM:

  1. Add radii read immediately after theory cpcm in $pcm.
  2. Keep the $solvent block after $pcm.
  3. Append $van_der_waals after $solvent.
  4. Begin $van_der_waals with a line containing 1.
  5. For each override, emit the element's atomic number followed by the supplied radius value. Preserve the override order from the input string.

For custom_solvation_radii="Cl=1.00;", Cl is converted to atomic number 17:

$pcm
theory cpcm
radii read
$end

$solvent
solventname trichloromethane
$end

$van_der_waals
1
17 1.00
$end

For custom_solvation_radii="Cl=1.00;Br=2.00;", the $van_der_waals content is:

$van_der_waals
1
17 1.00
35 2.00
$end

As everywhere else in the document, there are no empty lines inside these blocks and exactly one empty line between adjacent blocks.

Validation and Error Behavior

  • An unsupported solvation_model, such as "ABC", must cause calculation generation to raise an exception rather than produce Q-Chem text.
  • Requesting both d3=True and d3bj=True in the same calculation must raise ccinput.exceptions.InvalidParameter.

Compatibility and Non-Effects

  • Supplying custom_basis_sets must not alter Q-Chem output for the calculation types covered here. Given otherwise identical inputs, output with this parameter is identical to output without it.
  • Existing XYZ parsing, coordinate generation, charge/multiplicity handling, memory normalization, method/basis aliases, and solvent synonym handling remain the source of the corresponding normalized values used in Q-Chem output.

  1. molecule {

  4. Exactly one empty line after the final atom

  6. Exactly one empty line after the closing brace

<charge> <multiplicity>

  • Psi4 support must be added without changing generated output or public behavior for existing software selections.
  • Only single-point energies and geometry optimizations are required for Psi4.

Specifications

The specifications string is a semicolon-separated list of directives, each of the form name(content). Whitespace around directives is tolerated, and directive names are matched case-insensitively; emitted option lines are in lowercase form, so SCF(Tight) and scf(tight) are equivalent.

Any token in the string that does not form a recognized name(content) directive — including arbitrary non-directive characters such as !# — is silently skipped: it produces no option line, no block, and no error. (The only recognized bare token is string, described in the MEP section below.)

A directive whose target block is not applicable to the calculation type is also silently ignored: no corresponding block is emitted, and the calculation_block attribute contains no non-whitespace content. For example, an opt(...) directive on a single-point calculation produces no driver block, and a freq(...) directive on a pure optimisation produces no freq block; in both cases the rest of the input is generated exactly as if the directive were absent.

scf(<option>) and dft(<option>) append one option line each inside the active electronic-structure method block, placed after the multiplicity line and before end, in the order the directives appear in the string. Either directive name targets the method block regardless of whether the active method is HF (an scf block) or a density functional (a dft block). Recognized option literals include:

  • Tight or tight -> line tight
  • Direct or direct -> line direct
  • grid <args> -> line grid <args> (for example grid coarse)
  • maxiter <N> -> line maxiter <N>
  • odft -> line odft

maxiter 30

Context

Public API

Calculations are produced via a factory function that accepts calculation parameters as keyword arguments and returns an object whose input_file attribute is a string containing the generated NWChem input. The relevant keyword arguments include:

  • nproc (int)
  • mem (str, e.g. "10000MB")
  • type (str, e.g. "Single-Point Energy", "Geometrical Optimisation")
  • file (str, the input structure filename)
  • software (str, "nwchem")
  • method (str, e.g. "M06-2X")

  • charge (str/int)
  • specifications (str) — the focus of this task

The existing public entry point and its behavior remain unchanged, except for the additional accepted syntax in specifications described below.

Required Behavior

The specifications string encodes options grouped by a "block" keyword using a parenthesized syntax:

BLOCKNAME(option[, option]...)

Multiple such groups may appear in a single specifications string. The parser must accept and correctly handle all of the following syntactic variations, treating them equivalently in terms of the options they define:

  1. Comma-separated options within a group, no spaces: SCF(Tight,Direct) → yields the options tight and direct for the SCF block.

  2. Comma-separated options within a group, with spaces after commas: SCF(Tight, Direct) → yields tight and direct.

  3. Repeated block groups separated by whitespace: SCF(Tight) scf(direct) → yields tight and direct. Block names are case-insensitive.

  4. Multiple different blocks separated by whitespace: SCF(Tight) opt(maxiter 5) → yields tight for SCF and maxiter 5 for the optimization/driver block.

  5. Groups separated by a semicolon (with or without surrounding blocks after it): SCF(Tight); opt(maxiter 5) scf(direct) → yields tight and direct for SCF and maxiter 5 for the driver block.

In all cases:

  • Block names are matched case-insensitively (SCF, scf, opt are all recognized).
  • Option tokens inside the parentheses are emitted lowercased into the corresponding block of the output.
  • An option that is itself a keyword with an argument (e.g. maxiter 5) is preserved as a single option line (maxiter 5).
  • Semicolons and whitespace both act as separators between groups.
Block-to-output mapping
  • SCF(...) options are written as individual lines inside the dft block, appended after the xc and mult lines.
  • opt(...) options are written as individual lines inside a separate driver block.
Example outputs

For a single-point DFT energy calculation with specifications equal to any of SCF(Tight,Direct), SCF(Tight, Direct), or SCF(Tight) scf(direct), the generated input contains a dft block of the form:

dft
xc m06-2x
mult 1
tight
direct
end

followed by:

task dft energy

dft

tight
end

driver
maxiter 5
end

For a geometry optimization with specifications = SCF(Tight); opt(maxiter 5) scf(direct), the generated input contains:

dft
xc m06-2x
mult 1
tight
direct
end

driver
maxiter 5
end

task dft optimize

The overall input file structure (title, start line, memory total line, charge line, geometry block, basis block, blocks and task line) is otherwise as normally produced by the NWChem generator. Ordering of options within a block follows the order in which they appear across the parsed specifications string.

Input generation must not create or leave behind any auxiliary files on disk (e.g. no stray *.parameters files) as part of producing the input string. Any radii/parameter data required must be exposed through in-memory attributes of the returned object rather than written to the filesystem.
