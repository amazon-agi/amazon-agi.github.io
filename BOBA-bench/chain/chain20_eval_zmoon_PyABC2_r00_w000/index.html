Overview

Your work takes place in the pyabc2 package. Inside the module pyabc2/keys.py, there is currently a Pitch class. You must add musical-key support by introducing a Key class and two module-level constants, without breaking the existing Pitch functionality.

Additions Required in pyabc2/keys.py

Module-level constants

  1. CHROMATIC_NOTES — a sequence (list) of strings in which each entry is a chromatic note name serving as a valid key tonic (e.g. "C", "C#", "D", etc.). These are the base note names that a mode name may be appended to in order to form a key name.

  2. MODE_VALUES — a sequence (list) of strings giving the names of the musical modes in lowercase (e.g. "major", "minor", "ionian", "dorian", etc.).

The Key class

Introduce a class called Key that can be constructed by supplying the keyword argument name:

Key(name="Cmaj")

The constructor must accept a single string name produced by concatenating a tonic note name followed by a mode name (with no separator). It must successfully parse and construct a Key for every combination consisting of:

  • A tonic taken from CHROMATIC_NOTES, concatenated with
  • A mode string, which may appear in any of the following forms:
    • Sentence case (first letter uppercase, remainder lowercase), e.g. "Major", "Dorian".
    • Entirely lowercase, e.g. "major", "dorian".
    • Entirely uppercase, e.g. "MAJOR", "DORIAN".
    • The first three characters of any of the preceding case variants (a truncated abbreviation), e.g. "Maj", "maj", "MAJ", "Dor".
    • The mode designator made up of the single character "m" (indicating minor).

In other words: for every tonic k in CHROMATIC_NOTES and every mode string m assembled as described above, Key(name=k + m) must construct successfully without raising.

The mode name portion must be parsed case-insensitively, and both the full mode names and their three-character prefixes must be recognized as valid. The bare "m" suffix must be recognized as a valid (minor) mode designator.

Constraints

  • The pre-existing Pitch class, together with its behavior, must remain importable and unchanged.
  • All of Key, Pitch, CHROMATIC_NOTES, and MODE_VALUES must be importable from pyabc2.keys.

Public API Summary

  • pyabc2.keys.MODE_VALUES — a list of lowercase mode-name strings.
  • pyabc2.keys.Key — a class whose constructor accepts the keyword argument name: str.

06 Refactoring Pitch and PitchClass in pyabc2.keys 1277 words · rewritten by GPT-5.6-sol, reworded by GLM-5.3-Flash

Task Specification: Refactoring Pitch and PitchClass in pyabc2.keys

Overview

Rework the pitch-related functionality in pyabc2/keys.py while keeping the behavior of the key-related API intact. The module is required to expose the following public imports:

from pyabc2.keys import Key, Pitch, PitchClass, pitch_value

The two pitch types carry distinct meanings:

  • PitchClass stands for a note that carries no octave information, such as C, D#, or Ebb.
  • Pitch stands for a specific note in a specific octave, such as C4.

pitch_value is a standalone conversion function defined at module level.

The module-level function pitch_value

def pitch_value(name: str, root: str = "C") -> int:
    ...

The function converts an ASCII note name—a letter A through G followed by zero or more # or b accidentals—into its integer chromatic value. With the default root C, the natural notes take the values C=0, D=2, E=4, F=5, G=7, A=9, and B=11. Every # adds one and every b subtracts one; accidentals stack when repeated.

Examples using the default root:

Name Value
C 0
C# 1
Db 1
C### 3
Eb 3
Fbb 3
Dbb 0

The optional root keeps the conversion behavior root-relative; C is the default.

Values outside a single octave

The default-C result must not be silently normalized into 0..11. If accidentals put the raw value less than 0 or at least 12, emit a UserWarning by way of Python's warnings mechanism and return the raw arithmetic result. For instance:

  • pitch_value("B##") returns 13 and emits a warning.
  • pitch_value("Cb") returns -1 and emits a warning.
  • pitch_value("Dbbb") returns -1 and emits a warning.

The PitchClass class

PitchClass stands for a chromatic pitch without an octave.

Construction and attributes
PitchClass(name: str, *, root: str = "C")
PitchClass.from_value(value: int, *, root: str = "C")

Name-based construction accepts spellings such as C, D#, Ebb, and C##. Every instance exposes:

  • .name: the instance's note spelling.
  • .value: the semitone value relative to the instance's root.
  • .root: the note that is regarded as value zero.

The default root is C. from_value accepts values in 0..11 and selects the canonical (“nice”) spelling that corresponds to the absolute chromatic pitch. Under the default root, this is the complete canonical order:

Value Name
0 C
1 C#
2 D
3 Eb
4 E
5 F
6 F#
7 G
8 Ab
9 A
10 Bb
11 B

Notably, sharps are the preferred spelling for values 1 and 6, while flats are the preferred spelling for values 3, 8, and 10.

Equality

Two PitchClass instances are equal if and only if they stand for the same chromatic pitch class, regardless of enharmonic spelling or the root used to express their values. For instance:

PitchClass("C") == PitchClass("Dbb")
Enharmonic spellings

Every PitchClass exposes:

  • .equivalent_flat: an equal PitchClass that uses the letter above and enough flats to preserve the pitch.
  • .equivalent_sharp: an equal PitchClass that uses the letter below and enough sharps to preserve the pitch.

For instance:

p = PitchClass("D")
p.equivalent_flat == PitchClass("Ebb")
p.equivalent_sharp == PitchClass("C##")

These properties return PitchClass objects rather than Pitch objects.

Changing the root
PitchClass.with_root(root: str) -> PitchClass

with_root is a public method returning a new PitchClass; it must not rename the note or mutate the original object. On the new instance, .name is exactly the original note name, .root reflects the root that was supplied, and .value is the modulo-12 semitone distance from that root to the named pitch.

For instance:

p0 = PitchClass("C")
p = p0.with_root("Bb")

assert p.name == "C"
assert p.value == 2
assert p0.name == "C"

So changing a root changes the coordinate system that .value uses, not the note's spelling or its absolute chromatic identity.

The Pitch class

Pitch stands for a specific chromatic pitch that carries octave information.

Construction
Pitch(value: int, octave: int)
Pitch.from_name(name: str) -> Pitch
Pitch.from_etf(freq: float) -> Pitch
  • Direct construction combines an integer chromatic value relative to C with an integer octave.
  • from_name parses a string that combines the note and the octave, such as C4, A4, or C3. The trailing integer gives the octave, and the leading part gives the note letter plus any accidentals.
  • from_etf constructs the nearest equal-tempered pitch for a frequency given in hertz.

Every instance exposes .name, which contains the canonical note name without the octave number.

Equality

Two Pitch instances are equal if and only if their chromatic pitch and their octave are both equal:

Pitch.from_name("C4") == Pitch(0, 4)
Pitch(0, 4) != Pitch(0, 3)
Arithmetic with integers

Pitch supports integer semitone transposition:

  • pitch + integer returns a new Pitch shifted up by that many semitones.
  • pitch - integer returns a new Pitch shifted down by that many semitones.

Positive as well as negative offsets must work, and octave boundaries must be handled correctly. Result names follow the same canonical mapping as PitchClass.from_value. Starting at C4, representative results include:

Expression Result name
C4 + 1 C#
C4 + 2 D
C4 + 5 F
C4 + (-1) B
C4 + 12 C
C4 - 1 B
C4 - (-1) C#
C4 - 12 C

Arithmetic operations return new objects. Apart from producing the correct pitch, canonical name, and octave rollover, no additional contract is imposed here on the exposed numeric .value after arithmetic.

Equal-temperament frequencies

Every Pitch exposes:

  • .equal_temperament_frequency: its frequency in hertz under twelve-tone equal temperament with A4 = 440 Hz.
  • .etf: an alias that returns the same value.

The reference values are:

  • C4: approximately 261.6256 Hz.
  • A4: 440.0 Hz.

Pitch.from_etf carries out the inverse mapping to a Pitch; for example, Pitch.from_etf(440) corresponds to Pitch.from_name("A4").

Compatibility of Key

While the pitch types are separated, Key must remain importable and must retain its existing public surface and externally visible behavior. Specifically:

  • Name-based construction as it exists today continues to accept canonical chromatic roots and the mode names major, minor, Ionian, Aeolian, Mixolydian, Dorian, Phrygian, Lydian, and Locrian. Mode names remain case-insensitive, the three-letter abbreviations of mode names remain accepted, m remains an alias for minor, and when mode information is omitted it continues to mean major.
  • Key-signature and accidental reporting remain available; as an example, A major has F#, C#, and G# in that order.
  • Relative-key properties and aliases remain available: relative_ionian/relative_major and relative_aeolian/relative_minor. So A minor's relative Ionian/major is C, and C major's relative Aeolian/minor is A minor.
  • For key equality, major continues to be regarded as equivalent to Ionian and minor as equivalent to Aeolian.

Internal use of Pitch and PitchClass may be adapted by the refactor, but this public key behavior must not regress.

Required public surface

  • pyabc2.keys.pitch_value(name, ...) -> int, covering stacked accidentals and the UserWarning behavior for raw default-C values outside one octave.
  • pyabc2.keys.PitchClass, covering construction by name, from_value, .name, chromatic equality, .equivalent_flat, .equivalent_sharp, and .with_root.
  • pyabc2.keys.Pitch, covering direct value-and-octave construction, from_name, from_etf, .name, octave-sensitive equality, integer addition/subtraction, .equal_temperament_frequency, and .etf.
  • pyabc2.keys.Key, with its existing public behavior kept intact.

Task Description

Summary

Restructure the pyabc2 package by dividing note-related and key-related functionality between two separate modules: pyabc2/note.py and pyabc2/key.py. The public API described below must be importable from those exact module locations.

Module Organization

pyabc2/note.py

This module must provide the following public names:

  • Pitch — a pitch class paired with an octave.
  • PitchClass — a note name with no octave.
  • pitch_value — translates a note name into an integer chromatic value.
  • CHROMATIC_NOTES — the list of the 12 canonical chromatic note names, starting at C.
pyabc2/key.py

This module must provide the following public names:

  • Key — a musical key given by a tonic and a mode.
  • MODE_VALUES — a collection the members of which are the recognized lowercase mode names: major, minor, ionian, aeolian, mixolydian, dorian, phrygian, lydian, and locrian. Iterating over its members must make these lowercase strings available for deriving accepted user-facing mode spellings.

pyabc2.key may import note functionality from pyabc2.note where needed; nevertheless, Key and its supporting mode data must live in pyabc2/key.py, whereas Pitch, PitchClass, pitch_value, and CHROMATIC_NOTES must live in pyabc2/note.py.

Behavior of Notes and Pitches

CHROMATIC_NOTES

CHROMATIC_NOTES must be a list holding the 12 canonical C-chromatic note names, arranged in ascending semitone order:

["C", "C#", "D", "Eb", "E", "F", "F#", "G", "Ab", "A", "Bb", "B"]

In addition to defining the canonical value-to-name spellings, every member must be usable as the tonic part of the key names described below.

pitch_value

pitch_value(note) returns the integer chromatic value of an ASCII note name, counted from C. For the natural notes, the values are C=0, D=2, E=4, F=5, G=7, A=9, and B=11.

Every # occurring in the name adds one, and every b subtracts one. Accidentals may be repeated, and they are applied arithmetically rather than being discarded or restricted to a single symbol. Specifically:

  • pitch_value("C") == 0
  • pitch_value("C#") == pitch_value("Db") == 1
  • pitch_value("C###") == pitch_value("Eb") == pitch_value("Fbb") == 3

By default, the result is the raw arithmetic value, not one reduced modulo 12. When that result is below 0 or at least 12, the function must nevertheless return it and must emit a UserWarning. Hence:

  • pitch_value("B##") == 13, with a UserWarning.
  • pitch_value("Cb") == -1, with a UserWarning.
  • pitch_value("Dbbb") == -1, with a UserWarning.
PitchClass

The constructor is PitchClass(name, root="C").

  • name is a string with an ASCII note name, such as "C" or "Dbb".
  • .name exposes the note-name spelling that the instance represents.
  • root is an optional reference note name. It alters the coordinate system used for .value but leaves the pitch class's absolute chromatic identity unchanged.
  • .value is the integer chromatic distance from the current root, reduced modulo 12 so that it lies in the range 0 through 11.

PitchClass must additionally provide the following behavior:

  • PitchClass.from_value(value) constructs a pitch class given an integer chromatic value in the range 0 through 11, using the canonical spelling in CHROMATIC_NOTES that corresponds to it. Specifically, the values 0 through 5 produce "C", "C#", "D", "Eb", "E", and "F" respectively.
  • .with_root(root) returns a new PitchClass whose measurement is relative to the root supplied. The original .name and the absolute pitch-class identity are preserved. For example, PitchClass("C").with_root("Bb") still has name "C" and has value 2.
  • .equivalent_flat and .equivalent_sharp return PitchClass objects spelled as the enharmonically equivalent flat and sharp forms. For D, the flat equivalent is E-double-flat and the sharp equivalent is C-double-sharp: PitchClass("D").equivalent_flat == PitchClass("Ebb") and PitchClass("D").equivalent_sharp == PitchClass("C##").
  • .to_pitch(octave) returns a Pitch at the integer octave supplied. The conversion rests on the pitch class's absolute identity and must be independent of its reference root. As a result, both PitchClass("C").to_pitch(4) and PitchClass("C", root="D").to_pitch(4) equal middle C, Pitch(0, 4).
  • Equality is based on chromatic identity rather than on spelling or reference root. Enharmonic spellings therefore compare equal; for example, PitchClass("C") == PitchClass("Dbb").
Pitch

A pitch can be constructed directly as Pitch(value, octave), where value is an integer C-based pitch-class value and octave is an integer octave. The value 0 stands for C. For example, Pitch(0, 4) is C4, while Pitch(0, 3) is C3.

Pitch must provide the behavior that follows:

  • Pitch.from_name(name) builds a pitch from a note-name string that contains an octave, such as "C4" or "A4".
  • .name returns the canonical note name with the octave omitted, drawing its spelling from CHROMATIC_NOTES; the initial values therefore produce "C", "C#", "D", "Eb", "E", and "F".

  • 5 → "P4" (perfect fourth)
  • 6 → tritone (e.g. "A4" / "d5" — not exercised; pick a sensible value)
  • 7 → "P5" (perfect fifth)
  • 8 → "m6" (minor sixth)
  • 9 → "M6" (major sixth)
  • 10 → "m7" (minor seventh)
  • 11 → "M7" (major seventh)
  • 12 → "P8" (perfect octave)

Only the values 0, 2, 10, and 12 are strictly verified; for the remaining entries, the same consistent convention should be followed.

Overview

Implement interval-aware arithmetic for the existing pitch and pitch-class objects, and ensure that semitone values outside one octave are handled consistently by simple intervals. Arithmetic must return the appropriate interval or pitch type, must preserve semantic equality, and must expose normalization through Python's standard warning mechanism.

Public API

The four classes affected here belong to the existing pyabc2.pitch public API and must remain importable in the following way:

from pyabc2.pitch import Pitch, PitchClass, SimpleInterval, SignedInterval

These public classes must not be relocated or replaced. Except for the two object-to-object subtraction operations explicitly redefined below, support for interval operands must coexist with the existing API, including integer-semitone arithmetic.

Conventions for Semitones and Warnings

All constructor values and arithmetic offsets described in this specification are integer numbers of semitones.

Whenever an out-of-range SimpleInterval value gets normalized, a UserWarning must be emitted through Python's standard warnings facility. It must be possible for callers to capture it using normal warning-handling APIs. As a particular case, evaluating an expression such as SimpleInterval(24).name must emit a capturable UserWarning. Values from 0 through 12, inclusive, are already within the range.

SimpleInterval

SimpleInterval(v) represents a musical interval that is directionless and no larger than one octave.

Normalizing the value
  • Values in the inclusive range 0 through 12 keep their value.
  • Every value outside that range is reduced by means of its absolute semitone distance:
    • Set r = abs(v) % 12.
    • If r == 0 and v is a nonzero multiple of 12, the reduced value is 12 (an octave) and not 0 (a unison).
    • In every other case, the reduced value is r.
  • Carrying out this normalization must emit a UserWarning.
  • Accordingly, 24 reduces to 12, whereas a negative value such as -7 reduces to the same directionless interval as 7; a warning is emitted for both out-of-range inputs.
Naming

For the reduced value, the .name property returns the standard short interval name:

Semitones Name
0 P1
1 m2
2 M2
3 m3
4 M3
5 P4
6 A4
7 P5
8 m6
9 M6
10 m7
11 M7
12 P8

For instance:

SimpleInterval(2).name == "M2"
SimpleInterval(10).name == "m7"
SimpleInterval(12).name == "P8"
SimpleInterval(24).name == "P8"  # emits UserWarning
Equality

Equality is based on the reduced semantic value rather than object identity. Whenever inputs reduce to the same simple interval, the intervals compare equal. A SimpleInterval returned by pitch-class arithmetic must compare equal to a directly constructed SimpleInterval that represents the same reduced semitone distance.

SignedInterval

SignedInterval(v) denotes an exact signed semitone displacement. In contrast to a SimpleInterval, it retains direction and may span any number of octaves.

  • Its value stays as the signed semitone count that was supplied.
  • The .name property returns the signed interval notation that already exists. The magnitude is broken down into octave components (P8) plus a simple remainder; for a negative interval, the complete positive-magnitude name is wrapped in -[...].
  • Representative names are:
SignedInterval(0).name == "P1"
SignedInterval(2).name == "M2"
SignedInterval(3).name == "m3"
SignedInterval(15).name == "P8+m3"
SignedInterval(27).name == "2(P8)+m3"
SignedInterval(-27).name == "-[2(P8)+m3]"

For SignedInterval instances, equality is based on the exact signed semitone value. A value returned by pitch arithmetic must compare equal to a directly constructed SignedInterval that has the same signed count.

Pitch

Pitch(n) represents an absolute pitch that is identified by the integer chromatic value n.

Pitch subtraction

Subtracting one Pitch from another must return a SignedInterval and not another pitch. The value is the left pitch value minus the right pitch value, with direction preserved:

Pitch(50) - Pitch(40) == SignedInterval(10)
Pitch(40) - Pitch(50) == SignedInterval(-10)
Addition with a signed interval

When a SignedInterval is added on the right of a Pitch, the operation must return a new Pitch shifted by that exact signed semitone count:

Pitch(40) + SignedInterval(-10) == Pitch(30)

This holds for positive, zero, and negative signed intervals alike. Preexisting arithmetic with integer semitone offsets must continue to work.

Equality

Pitch equality is semantic: instances carrying the same absolute pitch value compare equal, including results produced by interval addition.

PitchClass

PitchClass(n) represents a pitch class that is identified by the integer chromatic value n. Because a simple interval is directionless, pitch-class subtraction applies SimpleInterval normalization instead of retaining the sign of a descending difference.

Pitch-class subtraction

Subtracting one PitchClass from another must return a SimpleInterval. Start from the raw value difference left.value - right.value, then apply the SimpleInterval reduction and warning rules stated above:

PitchClass(7) - PitchClass(0) == SimpleInterval(7)

When the difference is descending, the raw negative value falls outside the simple interval range. It is reduced to its directionless magnitude, and a UserWarning is emitted:

PitchClass(0) - PitchClass(7) == SimpleInterval(7)  # emits UserWarning

As part of producing the normalized result, the warning must be emitted through warnings.

Addition with a simple interval

Adding a SimpleInterval on the right of a PitchClass must return a new PitchClass whose value is shifted by the semitone count of that interval:

PitchClass(0) + SimpleInterval(5) == PitchClass(5)

The root context of the originating pitch class must be preserved. Existing addition and subtraction using integer semitone offsets must continue to retain their current behavior.

Equality

PitchClass equality must remain based on semantic pitch-class value rather than identity. Results produced by interval addition must compare equal to directly constructed pitch classes that represent the same value.

General Compatibility Requirements

  • Every arithmetic result above must be an instance of the stated public type, with == comparing musical values instead of object identities.
  • Support for interval operands must coexist with the integer arithmetic on Pitch and PitchClass that is already established.
  • Behavior that already exists for interval naming, pitch naming, conversion, note, key, and parsing must not regress because of these changes.
