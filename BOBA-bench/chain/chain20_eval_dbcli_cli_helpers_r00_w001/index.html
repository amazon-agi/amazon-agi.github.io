01 A write() method must be added to the existing Config class so that its current in-memory state can be persisted to a file on disk. 491 words · source specification, reworded by GLM-5.3-Flash

Task Description

Summary

A write() method must be added to the existing Config class so that its current in-memory state can be persisted to a file on disk. The Config class must also be structured such that it can be subclassed (inherited from).

Background / Current Behavior

The codebase already has a Config class that:

  • Acts as a nested mapping (access and assignment via config['section']['key'] are supported).
  • Can be associated with a user-specific configuration file path (built from an application name, an application author, and a config file name), as well as with a separate default configuration source file.
  • Offers a write_default_config() method that writes the default configuration to the user config file location.

The tests interact with the class through a helper that builds a Config instance bound to:

  • a user config file at a known path (a filename inside a temporary directory), and
  • a default config source file.

All of the existing behavior described above must be preserved.

Change Required: Config.write()

Add a method with this signature:

def write(self, outfile=None):

Behavior:

  1. Default target (no argument): When the method is called with no arguments (config.write()), it must serialize the current in-memory configuration state and write it to the user configuration file path associated with the instance (the same path that write_default_config() uses).

  2. Explicit output target: When the method is called with outfile set to an open, writable file object (config.write(outfile=f)), it must serialize the current in-memory configuration state and write it to that file object rather than to the user config file path. The file object may have been opened in binary mode.

  3. State reflected in output: The serialized output must reflect any modifications made to the configuration in memory prior to the call. For example, after config['section']['test_boolean_default'] = False is set, a subsequent write() (or write(outfile=f)) must produce output in which that key/value pair appears with its updated value.

Serialization Format

The output that is written is INI-style text. Every key/value pair is rendered on its own line in the form:

key = value

with one space on each side of the =. Booleans are rendered using their Python capitalized string form: True and False. Keys are grouped under their sections.

Concretely, for a section named section that contains a boolean key test_boolean_default:

  • when its value is True, the substring test_boolean_default = True is present in the output;
  • when its value is False, the substring test_boolean_default = False is present in the output.

Inheritance Requirement

The Config class must be implemented so that it is able to serve as a base class for subclasses (i.e., normal subclassing must not be prevented).

Constraints

  • The existing public interface must be preserved: mapping-style access/assignment, the user-config-path association, and write_default_config().
  • Output produced by write() must remain readable in the same format the class already consumes for its default/user config files.

adapter(data, headers, table_format=None, **kwargs)

Module: cli_helpers.tabular_output.delimited_output_adapter

The function is adapter(data, headers, table_format=None, **kwargs).

  • It produces delimited (CSV/TSV style) output.

  • CRLF (\r\n) line endings separate the rows and the header line.

  • At least a tab-delimited format is supported. Example: with headers ['letters', 'number'] and data [['abc', 1], ['d', 456]] producing a tab-delimited table, the output is:

    letters	number
abc	1
d	456

    (each line is terminated by \r\n, and the fields are separated by a tab character).

  • Supplying an unsupported table_format (e.g. 'foobar') must raise ValueError.

Module: cli_helpers.tabular_output.tabulate_adapter

The function is adapter(data, headers, table_format=None, **kwargs).

  • It produces tables that are bordered/aligned, in a variety of sub-formats identified by table_format.

  • For a plain grid-style format, using headers ['letters', 'number'] and data [['abc', 1], ['d', 456]], where the first column is left-aligned and the numeric column is right-aligned, the output is:

    +-----------+----------+
| letters   |   number |
+-----------+----------+
| abc       |        1 |
| d         |      456 |
+-----------+----------+

  • The adapter must not apply numeric-alignment or string-alignment options when the format is a markup-style one (identified by table_format='mediawiki'). With headers ['letters', 'number'] and data [['abc', 1], ['d', 456]], the output is exactly:

    {| class="wikitable" style="text-align: left;"
|+ <!-- caption -->
|-
! letters !! number
|-
| abc || 1
|-
| d || 456
|}

    (Note that the values are not padded/right-aligned the way they would be in grid formats.)

Module: cli_helpers.tabular_output.vertical_table_adapter

The function is adapter(data, headers, sep_title=None, sep_character='*', sep_length=27, **kwargs).

  • Each row is rendered as a vertical block: a separator line, followed by header | value lines in which the header names are left-padded to align the | separator.

  • Default behavior — with headers ('name', 'age') and data [('hello', 'world'), ('hello', 456)] (two records), the output is:

    ***************************[ 1. row ]***************************
name | hello
age  | world
***************************[ 2. row ]***************************
name | world
age  | 456

    (the block finishes with a trailing newline after the last value line).

    By default, the separator line is composed by centering a title of the form [ N. row ] (where N is the 1-based record number) inside a line built from the separator character. With the defaults sep_character='*' and sep_length=27, there are 27 separator characters on each side of the title.

  • Keywords for customization:

    • sep_title: a template string used for the separator title. It may contain {n}, which is replaced by the 1-based record number. Once substituted, the title is always enclosed in [ and ] between the left and right runs of separator characters.
    • sep_character: the character with which the separator line is built on each side of the title.
    • sep_length: either a single integer or a two-element sequence (left, right) that gives the count of separator characters on each side of the title.

    Example — with headers ('name', 'age'), data [('jack', 20), ('jill', 50)], sep_title='PERSON {n}', sep_character='-', sep_length=(1, 5), the output is:

    -[ PERSON 1 ]-----
name | jack
age  | 20
-[ PERSON 2 ]-----
name | jill
age  | 50

    (that is, 1 dash, [ , the title text with {n} substituted, ], then 5 dashes; blocks separated as shown, with a trailing newline after the final value line).

Supported Formats and Their Wiring

  • TabularOutputFormatter must recognize the format names that map to the adapters above. At minimum, the following format names must be supported and route to the correct rendering:
    • 'ascii' — a bordered grid table produced via the tabulate adapter.
    • 'plain' and 'simple' — tabulate sub-formats that are supported (used to verify format_name assignment).
  • Any format name that is not recognized must cause ValueError (both when it is assigned to format_name and when it is passed to format_output).
Example of the 'ascii' format

With data [['1', None], ['2', 'Sam'], ['3', 'Joe']], headers ['id', 'name'], format 'ascii', and missing_value='N/A', the result is:

+----+------+
| id | name |
+----+------+
| 1  | N/A  |
| 2  | Sam  |
| 3  | Joe  |
+----+------+

Note that the None cell is rendered as N/A, the columns are left-aligned, and the returned string has no trailing newline.

Task Specification: Add a style_output Preprocessor Along with a Pygments Compatibility Flag

Summary

A new output preprocessor, style_output, is to be added under this task; it applies ANSI escape codes (terminal styling driven by Pygments) to tabular data and to headers. Also to be exposed is a compatibility flag that reports whether the Pygments library is available.

API Surface Requirements

1. The compatibility flag

A boolean called HAS_PYGMENTS is to be defined at module level in cli_helpers.compat:

  • HAS_PYGMENTS must be True in case the pygments library can be imported, and False when it cannot.
2. The style_output preprocessor

A function is to be added to the module cli_helpers.tabular_output.preprocessors:

def style_output(data, headers, style=None, **kwargs):
    ...

The parameters:

  • data: an iterable whose elements are rows, with every row being an iterable of string cell values.
  • headers: an iterable consisting of string header values.
  • style: optionally, a Pygments Style subclass (so a style class, not an instance). When it is not given, None is used.
  • Keyword arguments beyond these: the function may accept them and ignore them.

Value returned:

  • A 2-tuple (data, headers); data is a list of lists of strings, and headers is a list of strings.

Function Behavior

Case A: No styling requested, or Pygments not available

Whenever style is None or Pygments is not available (HAS_PYGMENTS is False), what the function must return is (data, headers), with the data and headers left unchanged. The original data and headers must compare equal to the returned values.

Case B: Styling by means of a supplied style class (only when Pygments is available)

If Pygments is available and a style class has been provided, each cell value and each header value must be wrapped by the function in ANSI escape sequences derived from the given style (the appropriate ones), with the following Pygments token mapping in use:

  • Header cells — Token.Output.Header is the token used for styling them.
  • Data cells in odd-numbered rows — Token.Output.OddRow is the token used for styling them.
  • Data cells in even-numbered rows — Token.Output.EvenRow is the token used for styling them.

A row's parity comes from its position in the order of data: the first row (index 0) counts as an odd row, the second row (index 1) as an even row, and the pattern keeps alternating after that. Put differently, for parity purposes rows are counted starting from 1, so Token.Output.OddRow is what the first data row uses and Token.Output.EvenRow what the second uses.

Rendering a string value means emitting the ANSI escape codes that match the style definition of the token in question (foreground color, background color, and attributes such as bold), after which comes the original text and then the appropriate reset sequence.

Worked example

Consider a Pygments Style subclass declared like this:

class CliStyle(Style):
    default_style = ""
    styles = {
        Token.Output.Header: 'bold #ansired',
        Token.Output.OddRow: 'bg:#eee #111',
        Token.Output.EvenRow: '#0f0'
    }

along with:

headers = ['h1', 'h2']
data = [['1', '2'], ['a', 'b']]

the call style_output(data, headers, style=CliStyle) must produce:

headers -> ['\x1b[31;01mh1\x1b[39;00m', '\x1b[31;01mh2\x1b[39;00m']
data    -> [['\x1b[38;5;233;48;5;7m1\x1b[39;49m', '\x1b[38;5;233;48;5;7m2\x1b[39;49m'],
            ['\x1b[38;5;10ma\x1b[39m', '\x1b[38;5;10mb\x1b[39m']]

The result that must be returned is (styled_data, styled_headers).

Packaging

Where packaging is concerned, Pygments counts as an optional dependency: the package must declare it as an optional/extra requirement rather than a hard install requirement. This is consistent with the runtime behavior, which degrades gracefully when Pygments is absent.

Preprocessors already present

These functions already existing in cli_helpers.tabular_output.preprocessors — align_decimals, bytes_to_string, convert_to_string, quote_whitespaces, override_missing_value — must remain importable, with no change in their behavior.

For each row, take each cell and format it according to the type declared for its column position in column_types:

      • Decimal('1.0000') → '1.0000'

Summary

Which columns are aligned must be governed by the declared column types, so that text and other non-decimal columns are left unmodified.

Public API

    ...
Arguments
  • data: An iterable of rows, each of which is an iterable of cell values. A cell may already be a string, but callers may also pass in numeric objects such as decimal.Decimal, native numeric values, None, or other values.
  • headers: An iterable holding the column headers.

  • Keyword arguments beyond these must be accepted and ignored.

What the function returns

The return value is a two-element tuple (processed_data, headers).

  • processed_data must come out fully materialized, as a list of row lists.
  • headers must be returned in unchanged form.
  • Alignment-processed values are returned as strings. The original values and types are retained by values in unselected columns and by missing or nonnumeric values that cannot be aligned. Therefore, if all input cells are strings, the data that comes back is a list of lists of strings; mixed input may remain mixed wherever values get passed through.

Behavior Requirements

Which columns are selected

Only columns whose corresponding column_types entry is float fall under decimal alignment. For floating-point and decimal.Decimal data, the surrounding formatter uses this column type.

Any column with a different declared type must be passed through without decimal padding — text columns and integer-declared columns included. Runtime values alone must not lead to an unselected column being aligned. If the caller supplies no column types, no column is selected for alignment.

As an example, differing text lengths — such as "abc", "defg", and "hi" — must not result in leading spaces appearing in a text-declared column.

Values a selected column accepts

Inside a selected column:

  • Alignment of numeric strings must happen directly from their textual representation.
  • Before their width is measured, and before they are returned, numeric objects — decimal.Decimal among them — must be converted to their normal string representation. This conversion is required even in cases where alignment adds no spaces.
  • None and other nonnumeric values must not trigger an exception. They must be passed through unchanged, and the alignment width must not be determined by them.
Aligning on the decimal point

Every alignable value has an integer part: the portion of its string representation that comes before the first decimal point (.). When no decimal point is present, the entire representation serves as the integer part.

For each selected column:

  1. Find, among the alignable values in that column, the greatest integer-part width.
  2. Each alignable value must be prefixed with enough spaces for its integer part to reach that width.
  3. The decimal point and the fractional portion must be left unchanged.

Nothing other than leading alignment spaces may be added. Fractional portions receive no padding, reformatting, rounding, or other changes. The order of the rows and the order of the columns must be preserved.

)

column_types = (str, float)

([], ['num1', 'num2'])

2.5 Config class

The Config class stands for the configuration of an application. It acts like a dictionary/mapping over sections and their key-value pairs (it supports membership tests such as 'section' in config, indexed access such as config['section'], equality comparison between two Config instances, and item assignment such as config['section']['key'] = value). It must be designed so that it can be subclassed.

The constructor
Config(app_name, app_author, filename, default=None, validate=False, write_default=False)

Parameters:

  • app_name — the application name, as a string.
  • app_author — the application author, as a string.
  • filename — the name of the configuration file (it also serves as the base file name when locating the user's config file).
  • default — optional. It may be:
    • None, meaning no defaults;
    • a dict describing the default configuration data; or
    • a str path pointing to a default configuration file.
    • Any other type (e.g., bytes) is invalid.
  • validate — an optional boolean. If it is True, the default is treated as a configspec (a specification defining types/defaults for each field) and configuration data is validated/coerced against it.
  • write_default — an optional boolean indicating the intent to write out the default configuration.

Error conditions in the constructor (raised during instantiation):

  • Raise ValueError if write_default=True while default is not a file path (i.e., there is no default file to write).
  • Raise ValueError if validate=True while default is not a file path (i.e., there is no configspec file to validate against).
  • Raise TypeError if default is supplied but is neither None, a dict, nor a str (for example, bytes is invalid).

Behavior of the constructor:

  • If default is a dict, the config's data is initialized to that dict immediately (before any file reading). After construction, config.data equals the given dict.
  • If default is None, the config's data is initialized to an empty dict. After construction, config.data equals {}.
  • If default is a file path, the default data is not loaded automatically during construction; it is loaded only when read_default_config() is called.

    [section]
