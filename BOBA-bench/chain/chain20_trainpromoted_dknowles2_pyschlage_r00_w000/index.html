Summary

A Lock class representing a Schlage smart lock must be provided by the pyschlage package. A lock can be built from the service's JSON-like payload, can be refreshed from the service, and can be sent lock or unlock commands through the authentication object associated with it.

Public API

pyschlage.Lock

Lock must be defined so that it is importable as pyschlage.models.Lock. The package must also re-export it, so that it is directly accessible as pyschlage.Lock; both import paths must resolve to the same class.

Constructing a Lock and Mapping Its Data

Lock.from_json(auth, json)

As a class method, from_json takes an authentication object together with a JSON-like dictionary describing a lock, and constructs and returns a Lock from them.

  • auth is the object to use for the service requests that follow. On the resulting lock, the exact object supplied must be retained as _auth.
  • json holds the top-level string keys CAT and SAT together with the lock's identity and descriptive data. Its attributes dictionary holds the lock's current state along with other device properties.

The instance that is produced must expose the values below, mapped from the payload exactly as shown:

Lock attribute Where it comes from in the payload Expected type
device_id top-level deviceId str
name top-level name str
model_name top-level modelName str
battery_level attributes.batteryLevel int
firmware_version attributes.mainFirmwareVersion str
is_locked derived from attributes.lockState bool
is_jammed derived from attributes.lockState bool

The flags describing lock state must be interpreted in this way:

  • With lockState == 0: is_locked is False and is_jammed is False.
  • With lockState == 1: is_locked is True and is_jammed is False.
  • With lockState == 2: is_locked is False and is_jammed is True.
  • For any other value, both is_locked and is_jammed are False; each flag is true only for its corresponding value above.

Operations on the Service

The _auth object that was stored provides a request(...) method. Each of the operations below must make exactly one request, using the specified lowercase method, the current device_id, and arguments. The response that comes back provides a .json() method, and its result has the same shape that from_json accepts.

After every operation, the existing Lock object must be refreshed in place from the response's JSON. This refresh applies all properties derived from the payload — including device_id, name, model_name, battery_level, firmware_version, is_locked, and is_jammed — while the associated authentication object is retained. Therefore, callers holding a reference to the lock must observe the new values on that same instance.

Specification of the Task

Overview

The task consists of changing how request paths are built in an authentication client and its associated device model, so that the /devices path segment is no longer hardcoded in the base URL. Instead, callers must supply the path segments explicitly.

Behavior Required

Path handling for auth requests

An authentication object exists that exposes a request(method, path, **kwargs) method. When it is invoked, the object issues an HTTP request whose full URL is formed by joining a fixed base URL with the path supplied by the caller.

The base URL must be:

https://api.allegion.yonomi.cloud/v1

The path argument that the caller passes is appended to this base URL. When the call is made with a path beginning with a leading slash (e.g. "/foo/bar"), the resulting request URL must be:

https://api.allegion.yonomi.cloud/v1/foo/bar

In other words, the base URL contains only the API version segment (/v1) and no additional fixed path segments such as /devices.

The request itself must be issued using:

  • The HTTP method that was given, as the first positional argument.
  • The fully constructed URL, as the second positional argument.
  • timeout=60.
  • auth set to the SRP auth object that this client uses.
  • headers={"X-Api-Key": API_KEY}, with API_KEY being the module-level API key constant.

(Keyword arguments that the caller passes to request are forwarded/incorporated into the outgoing request as before; only the URL construction is affected by this change.)

Path handling in the device model

A device model object is present, constructed from an auth object and a device UUID. It exposes methods that call the auth object's request method. Since the /devices segment is no longer part of the base URL, the device model must now include devices/ at the start of every path that it passes to request.

Concretely, for a device with UUID <uuid>:

  • Update (update()): calls auth.request("get", "devices/<uuid>"). After the call, the JSON that is returned is used to refresh the device's attributes (e.g. the device's name reflects the value from the response JSON).

  • Lock (lock()): calls auth.request("put", "devices/<uuid>", json={"attributes": {"lockState": 1}}). After the call has been made, the device reports as locked (is_locked is truthy).

  • Unlock (unlock()): calls auth.request("put", "devices/<uuid>", json={"attributes": {"lockState": 0}}). After the call has been made, the device reports as not locked (is_locked is falsy).

In all three cases the path argument is exactly "devices/" concatenated with the device UUID (with no leading slash).

Change Summary

  • Strip the /devices segment (or any resource-specific segment) out of the auth client's base URL, leaving only https://api.allegion.yonomi.cloud/v1.
  • Modify the device model so that it prefixes its request paths with devices/.

No other behavior changes are required.

pyschlage.models.AccessCode

AccessCode models a keypad access code that belongs to a lock.

Constructor and its fields

The class must accept the keyword fields below, using the defaults stated:

  • _auth: dispatcher used for requests, default None
  • name: friendly name shown to users (str)
  • code: numeric access-code value, accepted either as an int or as a numeric str and exposed as a str
  • schedule: None, a RecurringSchedule, or a TemporarySchedule; default None
  • device_id: identifier of the owning lock (str or None); default None
  • access_code_id: identifier of the access-code record (str or None); default None
  • disabled: bool; default False
  • notification_enabled: bool; default False

Two AccessCode objects whose field values are equal must compare equal. _auth takes part in equality, in addition to the user-visible fields and the identifier fields.

Normalization of the numeric code

On construction, assignment, and JSON decoding, code must be normalized by way of its numeric value and then exposed as a canonical decimal string. As a result:

  • assigning code = 1122 exposes code == "1122";
  • decoding JSON accessCode: 1122 exposes "1122";
  • decoding JSON accessCode: 123 exposes "123";
  • constructing with code="0123" also exposes "123".

Access-code values are therefore not distinguished by leading zeroes: an otherwise identical object constructed with code="0123" must compare equal to one decoded from the numeric JSON value 123. In serialization, the normalized string is converted back to the numeric JSON value, so either representation serializes as accessCode: 123.

Interpreting the schedule

The schedule is determined from activationSecs, expirationSecs, and schedule1:

  • The pair made up of activationSecs == 0 and expirationSecs == 4294967295 serves as the sentinel for the absence of a temporary interval.

    • A schedule1 equal to the default recurring representation covering all days and the full day denotes that no restriction is effectively in force, and it must be exposed as schedule = None.
  • Epoch-second bounds that are real values, rather than that sentinel pair, decode as a TemporarySchedule that uses activationSecs as its start and expirationSecs as its end. In this state, the recurring placeholder does not replace the temporary schedule.

An access code can have at most one of these public schedule states: None, recurring, or temporary.

DaysOfWeek

What DaysOfWeek represents is a set of seven enabled/disabled flags. These keyword arguments are accepted by its constructor — sun, mon, tue, wed, thu, fri, and sat — with True as the default for every flag. For equality, all seven flags are compared.

An uppercase hexadecimal string with a seven-bit mask inside it serves as the representation on the API side. Running from the most-significant bit to the least-significant, the days go Sunday through Saturday:

Day Bit
sun 6
mon 5
tue 4
wed 3
thu 2
fri 1
sat 0

When all seven days are enabled, the value is "7F"; "5F" is what comes out when only Monday is disabled. to_str() returns the mask, and DaysOfWeek.from_str(value) parses it. Every day flag must be preserved through serialization and through parsing.

RecurringSchedule

These constructor fields, together with their defaults, describe a recurring weekly window:

    start_hour=0,
    start_minute=0,
    end_hour=23,
    end_minute=59,
)

For equality, the day mask is compared along with all four time fields.

{

    "startHour": <start_hour>,
    "startMinute": <start_minute>,
    "endHour": <end_hour>,
    "endMinute": <end_minute>,
}

That shape is what RecurringSchedule.from_json(payload) parses. Round-tripping a non-default recurring value must be lossless; to illustrate, a schedule in which Monday is the only disabled day serializes to daysOfWeek="5F", and parsing it back gives an equal schedule.

    "startMinute": 0,

    "endMinute": 59,
