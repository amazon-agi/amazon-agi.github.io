01 Implementing an Infoblox Connector 1212 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Implementing an Infoblox Connector

Summary

Create a connector that talks to an Infoblox WAPI (Web API) REST service over HTTPS, together with a small set of supporting exception classes and helper functions. The connector must accept its configuration in one of two forms: either an object with attributes or a plain dictionary.

Modules and Public Interface

infoblox_client/exceptions.py

Define these exception classes:

  • InfobloxConfigException — raised when required configuration options are missing.
  • InfobloxTimeoutError — raised when a request times out.
  • InfobloxConnectionError — raised on general connection/request failures.
  • InfobloxBadWAPICredential — raised when credentials are rejected by the WAPI (unauthorized).

Each must be a distinct exception type (a subclass of Exception). They must be instantiable in a way that works with the usages described below (e.g. being usable with only default construction is sufficient, but they may take arguments).

infoblox_client/connector.py
Function defined at module level: reraise_neutron_exception(func)

A decorator that wraps a callable and translates exceptions raised by the requests library during the call into connector exceptions:

  • If the wrapped callable raises requests.exceptions.Timeout, re-raise it as InfobloxTimeoutError.
  • If the wrapped callable raises any of the following, re-raise them as InfobloxConnectionError:
    • requests.exceptions.HTTPError
    • requests.exceptions.ConnectionError
    • requests.exceptions.ProxyError
    • requests.exceptions.SSLError
    • requests.exceptions.TooManyRedirects
    • requests.exceptions.InvalidURL

The decorator returns a new callable. Calling that returned callable (with no arguments) invokes the wrapped callable and the translation described above.

Class: Connector
Class-level attribute
  • DEFAULT_HEADER — a header value (e.g. a dict) that is passed as the headers argument on every HTTP request the connector issues.
Constructor: Connector(options)

options may be either an object that exposes the configuration as attributes or a dict with the corresponding keys. The configuration values below are used:

  • host (string) — the WAPI host name.
  • wapi_version (string) — the WAPI version segment, e.g. 'v1.1'.
  • username (string)
  • password (string)
  • ssl_verify (bool) — passed as the verify argument on requests.
  • http_pool_connections (int)
  • http_pool_maxsize (int)
  • http_request_timeout (int) — passed as the timeout argument on requests.

Construction behavior:

  • If the connector is constructed from a fully-populated object or dict, it must initialize successfully.
  • If it is constructed with a dict (or object) that is missing required options (for example, when only host and wapi_version are provided), the constructor must raise InfobloxConfigException. At minimum, all of the options listed above must be present for construction to succeed.
  • The connector must expose a mutable attribute cloud_api_enabled (see the get_object behavior below, where callers set it to True).
Constructing URLs

Every request URL uses the scheme/host/version prefix:

https://<host>/wapi/<wapi_version>/

With the example config (host='infoblox.example.org', wapi_version='v1.1'), the base is https://infoblox.example.org/wapi/v1.1/.

Method: _construct_url(relative_path, query_params=None, extattrs=None, force_proxy=False)

Constructs and returns the full request URL string.

  • relative_path must be a non-empty string that does not start with /. If relative_path is None, an empty string, or starts with /, raise ValueError.

  • That path is appended to the base prefix: https://<host>/wapi/<wapi_version>/<relative_path>.

  • Query components come from three sources and get combined into a single ?-delimited query string. When at least one query component exists, it is appended after a ?.

  • The parameters making up the query string are:

    • Extensible attributes (extattrs): a dict that maps attribute name to {'value': <value>}. Each becomes a query parameter with key *<attr_name> and value <value>. Example: {'Subnet ID': {'value': 'fake_subnet_id'}} → *Subnet ID=fake_subnet_id.
    • Query parameters (query_params): a dict that maps key to value; each becomes key=value.
    • Proxy search (force_proxy=True): adds _proxy_search=GM as a query parameter.

  • In the final URL, the query parameters must be ordered by key in ascending (alphabetical) order. Specifically:

    • _construct_url('network', query_params={'some_option': 'some_value'}, extattrs={'Subnet ID': {'value': 'fake_subnet_id'}}) → https://infoblox.example.org/wapi/v1.1/network?*Subnet ID=fake_subnet_id&some_option=some_value
    • _construct_url('network', extattrs={'Subnet ID': {'value': 'fake_subnet_id'}}, force_proxy=True) → https://infoblox.example.org/wapi/v1.1/network?*Subnet ID=fake_subnet_id&_proxy_search=GM
    • An example with a single extattr and a single payload param: network?*Subnet ID=fake_subnet_id&ip=0.0.0.0

    (Note: the * characters and spaces appear literally in the resulting URL string — do not percent-encode the produced URLs into a form other than the one shown.)

HTTP calls

The connector issues its HTTP requests through a requests.Session instance (its get, post, put, and delete methods). Every request call must include:

  • headers=DEFAULT_HEADER
  • timeout=<http_request_timeout>
  • verify=<ssl_verify>

Behavior of the methods:

  • create_object(objtype, payload)

    • Sends a POST to the URL built from objtype (no query params) with data=payload.
    • Invocation form: session.post(url, data=payload, headers=DEFAULT_HEADER, timeout=..., verify=...).
    • A successful response carries status code 201.

  • get_object(objtype, payload=None, extattrs=None, force_proxy=False)

    • Sends a GET to the URL built from objtype, with payload used as query params and extattrs used as extensible attributes.
    • Invocation form: session.get(url, headers=DEFAULT_HEADER, timeout=..., verify=...) (no data).
    • A successful response carries status code 200.
    • Proxy handling:
      • When the method is called with force_proxy=True, the object is fetched once, with the URL constructed using force_proxy=True. In terms of URL construction, this corresponds to invoking _construct_url(objtype, <query_params>, <extattrs>, True), where an omitted payload is normalized to {} and an omitted extattrs remains None.
      • When called without force_proxy (default False), and the underlying fetch returns a falsy/empty result while cloud_api_enabled is True, the connector retries the fetch with the proxy forced. In this scenario _construct_url is invoked first as _construct_url(objtype, {}, None, False) and then again as _construct_url(objtype, {}, None, force_proxy=True).
      • If the fetch produces no matching object, get_object returns None.
    • The actual retrieval work is delegated to an internal helper method called _get_object (so that _get_object and _construct_url are separately overridable). _get_object is invoked with the object type and the constructed URL.

  • update_object(ref, payload)

    • Sends a PUT to the URL built from ref with data=payload.
    • Invocation form: session.put(url, data=payload, headers=DEFAULT_HEADER, timeout=..., verify=...).
    • A successful response carries status code 200.

  • delete_object(ref)

    • Sends a DELETE to the URL built from ref.
    • Invocation form: session.delete(url, headers=DEFAULT_HEADER, timeout=..., verify=...).
    • A successful response carries status code 200.
Static method: Connector._validate_authorized(response)

The input is a response-like object that exposes a status_code attribute:

  • When status_code equals requests.codes.UNAUTHORIZED, raise InfobloxBadWAPICredential.
  • For success statuses (requests.codes.OK, requests.codes.CREATED, requests.codes.ACCEPTED), it returns normally without raising.
Static method: Connector.is_cloud_wapi(wapi_version)

Decides whether a WAPI version string indicates a "cloud" API.

  • It returns True when the version denotes major version 2 or greater. Examples that return True: 'v2.1/', '/v2.0/', 'v2.0.1', 'v3.0/', 'v11.0.1/'.
  • Otherwise it returns False. Examples that return False: 'v1.4.1', 'v1.9/', 'v1.99', 'asd', ''.

The classification rule: the string must match a version pattern of the form v<major>.<...> (optionally surrounded by a leading / and/or a trailing /), and the numeric major-version component at the front must be 2 or higher. Strings that do not match a valid v<number>.<...> version pattern return False.

Layout of the Test Support Package

The package/module structure below must exist and be importable:

  • infoblox_client/tests/__init__.py — empty.
  • infoblox_client/tests/base.py — defines TestCase, a subclass of unittest.TestCase that serves as a common base for unit tests.
  • infoblox_client/tests/unit/__init__.py — empty.

Additional Notes

  • The response bodies in these operations are simple JSON strings (e.g. '{}'); no parsing behavior is required beyond succeeding on empty/valid JSON.
  • The connector must never percent-transform the URL forms in a way that differs from the literal examples above (spaces and * appear literally, keys sorted alphabetically).

05 Object Model for Infoblox 1103 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Object Model for Infoblox

Module

All of the code resides in infoblox_client/objects.py. It must be possible to import the public API described below as objects.<Name> (i.e. from infoblox_client import objects).

Context

The module supplies Python model classes that wrap Infoblox WAPI (Web API) objects. Each model class is aware of how to build search/create requests against a connector object, and how to construct instances from the data the WAPI returns.

Contract for the Connector

Model methods work with a connector object that exposes these methods:

  • connector.get_object(infoblox_type, payload, extattrs=None, force_proxy=False, return_fields=None) — returns the object data that was fetched (a dict), or a falsy value if nothing is found.
  • connector.create_object(infoblox_type, payload, return_fields) — returns the data of the created object (a dict).
  • connector.delete_object(ref) — deletes the object identified by the _ref string passed in.

In this contract, infoblox_type denotes the WAPI object type string (e.g. 'record:host', 'fixedaddress', 'ipv6fixedaddress').

Required Public Classes and Their Behavior

objects.HostRecord

Models a WAPI record:host object (its infoblox_type is 'record:host').

Supply two classmethods and one instance method:

HostRecord.search(connector, **kwargs)
  • Accepts keyword arguments that describe the search fields, view and ip among them.
  • The ip argument may be supplied either as a plain string (e.g. '192.168.15.20') or as an IP object (see the IP object requirements below). In both cases, for an IPv4 address, the payload of the search sent to the connector must contain the key ipv4addr with the string value of the address.
  • Calls connector.get_object exactly once with:
    • first positional argument 'record:host'
    • second positional argument the search payload dict, which, for a search by view and IPv4, must equal {'view': <view>, 'ipv4addr': <ip-string>}
    • the keyword arguments extattrs=None, force_proxy=False, return_fields=None
  • Returns a HostRecord instance constructed from the data get_object returned, or a falsy/None result when nothing is found.
HostRecord.create(connector, **kwargs)
  • Accepts keyword arguments, with view and ip among them.
  • The ip value may be passed as a list of IP objects.
  • A search is performed first: connector.get_object is called exactly once with the same signature as above. When the search is by view and by an IP object whose IPv4 address is '22.0.0.2', the search payload must equal {'view': <view>, 'ipv4addr': '22.0.0.2'} (for searching, the IP object is reduced to its plain string address).
  • When the search returns nothing, connector.create_object is called exactly once with:
    • first positional argument 'record:host'
    • second positional argument the create payload, where the IP information appears under the key ipv4addrs as a list of dicts. Each such dict holds the address under ipv4addr and, when supplied, mac (e.g. {'ipv4addr': '22.0.0.2', 'mac': 'fa:16:3e:29:87:70'}), together with view.
    • a third positional argument for return fields.
  • Returns a HostRecord instance built from the created data that was returned.
HostRecord.delete()
  • Calls connector.delete_object exactly once, passing the instance's _ref string (that is, the _ref value from the data the instance was built from).
IP Objects and HostRecord Fields

A HostRecord built from WAPI data whose ipv4addrs list contains one entry must expose an accessor to that entry in the form of a parsed IP object. The IP object must expose these attributes:

  • .ip — the address as a string (e.g. '22.0.0.2')
  • .host — the host value taken from the address entry
  • .configure_for_dhcp — the configure_for_dhcp value taken from the address entry
  • .mac — the mac value, where present

An IP object that has no host information must expose .host as None.

For a host record with a single IPv4 address, the relevant WAPI record shape is:

{
    '_ref': '<ref string>',
    'ipv4addrs': [{
        'configure_for_dhcp': False,
        '_ref': '<ref string>',
        'ipv4addr': '22.0.0.2',
        'mac': 'fa:16:3e:29:87:70',
        'host': '<host string>'}],
    'extattrs': { ... }
}

  • When ip is an IPv6 address, the instance produced must be a objects.FixedAddressV6.

The dispatching must apply both to direct construction and to the create classmethod (below). In other words, objects.FixedAddress(connector, ip=..., ...) and objects.FixedAddress.create(connector, ip=..., ...) both return instances of the appropriate concrete subclass.

objects.FixedAddress(connector, ip=<address>, network_view=<view>, mac=<mac>)

FixedAddress.create(connector, **kwargs)

Accepts ip, network_view, and mac as keyword arguments.

Case: IPv4 (infoblox_type 'fixedaddress'):

  • Performs a search by calling connector.get_object exactly once with:
    • first positional argument 'fixedaddress'
    • second positional argument, the payload {'network_view': <view>, 'ipv4addr': <ip-string>, 'mac': <mac>}

These are the concrete subclasses. FixedAddressV4 deals with IPv4 fixed addresses (infoblox_type 'fixedaddress', address field ipv4addr, uses mac). General Remarks

  • Search and create requests always send the address under the address field name appropriate for the type (ipv4addr for IPv4, ipv6addr for IPv6), reducing any IP-object input to its plain string form.
  • get_object must always be invoked with the keyword arguments extattrs=None, force_proxy=False, return_fields=None.
  • create first performs a search and calls create_object only when the search yields no existing object.

Naming

These names must be publicly importable from infoblox_client.objects: HostRecord, FixedAddress, FixedAddressV4, FixedAddressV6.

06 Handling DUIDs for IPv6 Fixed Addresses 503 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Handling DUIDs for IPv6 Fixed Addresses

Overview

In the infoblox_client library, you must implement or correct DUID (DHCP Unique Identifier) handling for IPv6 fixed address objects, and you must also provide a supporting utility function.

Public API Surface Required

1. The infoblox_client.utils.generate_duid function

The function generate_duid(mac) accepts a MAC address string and returns a DUID string derived from it.

  • The signature is generate_duid(mac).
  • It is called with a single positional argument (the MAC address).
  • It returns a DUID string.

(Other than having to be deterministic for a given MAC, its internal derivation algorithm is not constrained by this task; callers rely on the returned value being used as the object's duid.)

2. Factory behavior of infoblox_client.objects.FixedAddress

FixedAddress serves as a factory/constructor: when it is called with an IPv6 address, it returns an instance of objects.FixedAddressV6.

The constructor is invoked in this form:

objects.FixedAddress(connector, ip=<ip>, network_view=<view>, mac=<mac>)

When an IPv6 address is supplied, the following requirements apply:

  • The object that is returned must be an instance of objects.FixedAddressV6.
  • The mac attribute of the object must equal the mac value passed to the constructor (that value must be preserved, not cleared or overridden).
  • When a mac value is provided, the duid attribute of the object must be set to the result of infoblox_client.utils.generate_duid(mac). In other words, providing a MAC must cause exactly one call to generate_duid with the MAC as its sole argument, and the object's duid must equal the value that function returns.
  • Setting the mac must NOT reset or override the duid back to None; after the object has been constructed with a MAC, duid must hold the generated value.
