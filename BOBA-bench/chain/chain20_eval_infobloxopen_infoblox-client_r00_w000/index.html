Task Specification: Infoblox Connector Implementation

Overview

Implement a connector that communicates with an Infoblox WAPI (Web API) REST service over HTTPS, plus a small set of supporting exception classes and helper functions. The connector must accept its configuration either as an object with attributes or as a plain dictionary.

Modules and Public API

infoblox_client/exceptions.py

Define the following exception classes:

  • InfobloxConfigException — raised when required configuration options are missing.
  • InfobloxTimeoutError — raised when a request times out.
  • InfobloxConnectionError — raised for general connection/request failures.
  • InfobloxBadWAPICredential — raised when the WAPI rejects credentials (unauthorized).

Each must be a distinct exception type (an Exception subclass). They must be instantiable in a way that works with the usages described below (e.g. usable with only default construction is sufficient, but they may take arguments).

infoblox_client/connector.py
Module-level function: reraise_neutron_exception(func)

A decorator that wraps a callable and translates requests library exceptions raised during the call into connector exceptions:

  • If the wrapped callable raises requests.exceptions.Timeout, re-raise as InfobloxTimeoutError.
  • If the wrapped callable raises any of the following, re-raise as InfobloxConnectionError:
    • requests.exceptions.HTTPError
    • requests.exceptions.ConnectionError
    • requests.exceptions.ProxyError
    • requests.exceptions.SSLError
    • requests.exceptions.TooManyRedirects
    • requests.exceptions.InvalidURL

The decorator returns a new callable. Invoking that returned callable (with no arguments) triggers the wrapped callable and the translation described above.

Class: Connector
Class attribute
  • DEFAULT_HEADER — a header value (e.g. a dict) that is passed as the headers argument on every HTTP request the connector makes.
Constructor: Connector(options)

options may be either an object exposing the configuration as attributes or a dict with the corresponding keys. The following configuration values are used:

  • host (string) — WAPI host name.
  • wapi_version (string) — WAPI version segment, e.g. 'v1.1'.
  • username (string)
  • password (string)
  • ssl_verify (bool) — used as the verify argument on requests.
  • http_pool_connections (int)
  • http_pool_maxsize (int)
  • http_request_timeout (int) — used as the timeout argument on requests.

Behavior:

  • When constructed with a fully-populated object or dict, the connector must initialize successfully.
  • When constructed with a dict (or object) that is missing required options (for example, only host and wapi_version provided), the constructor must raise InfobloxConfigException. At minimum, the set of options listed above must all be present for successful construction.
  • The connector must expose a mutable attribute cloud_api_enabled (see the get_object behavior below where it is set to True by callers).
URL construction

All request URLs use the scheme/host/version prefix:

https://<host>/wapi/<wapi_version>/

For the example config (host='infoblox.example.org', wapi_version='v1.1'), the base is https://infoblox.example.org/wapi/v1.1/.

Method: _construct_url(relative_path, query_params=None, extattrs=None, force_proxy=False)

Builds and returns the full request URL string.

  • relative_path must be a non-empty string that does not begin with /. If relative_path is None, an empty string, or begins with /, raise ValueError.

  • The path is appended to the base prefix: https://<host>/wapi/<wapi_version>/<relative_path>.

  • Query components come from three sources and are combined into a single ?-delimited query string. When there is at least one query component, it is appended after a ?.

  • The parameters that make up the query string are:

    • Extensible attributes (extattrs): a dict mapping attribute name to {'value': <value>}. Each becomes a query parameter with key *<attr_name> and value <value>. Example: {'Subnet ID': {'value': 'fake_subnet_id'}} → *Subnet ID=fake_subnet_id.
    • Query parameters (query_params): a dict mapping key to value; each becomes key=value.
    • Proxy search (force_proxy=True): adds the query parameter _proxy_search=GM.

  • The query parameters in the final URL must be ordered by key in ascending (alphabetical) order. Concretely:

    • _construct_url('network', query_params={'some_option': 'some_value'}, extattrs={'Subnet ID': {'value': 'fake_subnet_id'}}) → https://infoblox.example.org/wapi/v1.1/network?*Subnet ID=fake_subnet_id&some_option=some_value
    • _construct_url('network', extattrs={'Subnet ID': {'value': 'fake_subnet_id'}}, force_proxy=True) → https://infoblox.example.org/wapi/v1.1/network?*Subnet ID=fake_subnet_id&_proxy_search=GM
    • A single extattr and a single payload param example: network?*Subnet ID=fake_subnet_id&ip=0.0.0.0

    (Note: the * characters and spaces appear literally in the resulting URL string — do not percent-encode the produced URLs to a form other than shown.)

HTTP operations

The connector performs HTTP requests using a requests.Session instance (its get, post, put, and delete methods). Every request call must include:

  • headers=DEFAULT_HEADER
  • timeout=<http_request_timeout>
  • verify=<ssl_verify>

Method behaviors:

  • create_object(objtype, payload)

    • Issues a POST to the URL built from objtype (no query params) with data=payload.
    • Call form: session.post(url, data=payload, headers=DEFAULT_HEADER, timeout=..., verify=...).
    • A successful response has status code 201.

  • get_object(objtype, payload=None, extattrs=None, force_proxy=False)

    • Issues a GET to the URL built from objtype, using payload as query params and extattrs as extensible attributes.
    • Call form: session.get(url, headers=DEFAULT_HEADER, timeout=..., verify=...) (no data).
    • A successful response has status code 200.
    • Proxy behavior:
      • When called with force_proxy=True, the object is fetched once, constructing the URL with force_proxy=True. In terms of URL construction, this corresponds to invoking _construct_url(objtype, <query_params>, <extattrs>, True) where an omitted payload is normalized to {} and an omitted extattrs remains None.
      • When called without force_proxy (default False) and the underlying fetch returns a falsy/empty result while cloud_api_enabled is True, the connector retries the fetch forcing the proxy. In this scenario _construct_url is invoked first as _construct_url(objtype, {}, None, False) and then again as _construct_url(objtype, {}, None, force_proxy=True).
      • If the fetch yields no matching object, get_object returns None.
    • The actual retrieval work is delegated to an internal helper method named _get_object (so that it and _construct_url are separately overridable). _get_object is invoked with the object type and the constructed URL.

  • update_object(ref, payload)

    • Issues a PUT to the URL built from ref with data=payload.
    • Call form: session.put(url, data=payload, headers=DEFAULT_HEADER, timeout=..., verify=...).
    • A successful response has status code 200.

  • delete_object(ref)

    • Issues a DELETE to the URL built from ref.
    • Call form: session.delete(url, headers=DEFAULT_HEADER, timeout=..., verify=...).
    • A successful response has status code 200.
Static method: Connector._validate_authorized(response)

Given a response-like object exposing a status_code attribute:

  • If status_code equals requests.codes.UNAUTHORIZED, raise InfobloxBadWAPICredential.
  • For success statuses (requests.codes.OK, requests.codes.CREATED, requests.codes.ACCEPTED), return normally without raising.
Static method: Connector.is_cloud_wapi(wapi_version)

Determines whether a WAPI version string indicates a "cloud" API.

  • Returns True when the version denotes major version 2 or greater. Examples that return True: 'v2.1/', '/v2.0/', 'v2.0.1', 'v3.0/', 'v11.0.1/'.
  • Returns False otherwise. Examples that return False: 'v1.4.1', 'v1.9/', 'v1.99', 'asd', ''.

The classifying rule is: the string must match a version pattern of the form v<major>.<...> (optionally surrounded by leading / and/or a trailing /), and the leading numeric major-version component must be 2 or higher. Strings that do not match a valid v<number>.<...> version pattern return False.

Test Support Package Layout

The following package/module structure must exist and be importable:

  • infoblox_client/tests/__init__.py — empty.
  • infoblox_client/tests/base.py — defines TestCase, a subclass of unittest.TestCase used as a common base for unit tests.
  • infoblox_client/tests/unit/__init__.py — empty.

Notes

  • Response bodies in these operations are simple JSON strings (e.g. '{}'); parsing behavior beyond succeeding on empty/valid JSON is not required.
  • The connector must never percent-transform the URL forms differently from the literal examples above (spaces and * appear literally, keys sorted alphabetically).

Task Specification: Infoblox Object Model

Module

All code lives in infoblox_client/objects.py. The public API described below must be importable as objects.<Name> (i.e. from infoblox_client import objects).

Background

This module provides Python model classes wrapping Infoblox WAPI (Web API) objects. Each model class knows how to build search/create requests against a connector object, and how to construct instances from data returned by the WAPI.

Connector Contract

Model methods interact with a connector object that exposes the following methods:

  • connector.get_object(infoblox_type, payload, extattrs=None, force_proxy=False, return_fields=None) — returns the fetched object data (a dict), or a falsy value if nothing is found.
  • connector.create_object(infoblox_type, payload, return_fields) — returns the created object data (a dict).
  • connector.delete_object(ref) — deletes the object identified by its _ref string.

Here infoblox_type is the WAPI object type string (e.g. 'record:host', 'fixedaddress', 'ipv6fixedaddress').

Required Public Classes and Behavior

objects.HostRecord

Represents a WAPI record:host object (its infoblox_type is 'record:host').

Provide two classmethods and one instance method:

HostRecord.search(connector, **kwargs)
  • Accepts keyword arguments describing search fields, including view and ip.
  • The ip argument may be given either as a plain string (e.g. '192.168.15.20') or as an IP object (see IP object requirements below). In both cases, for an IPv4 address, the search payload sent to the connector must contain the key ipv4addr with the string value of the address.
  • Calls connector.get_object exactly once with:
    • first positional argument 'record:host'
    • second positional argument the search payload dict, which for a search by view and IPv4 must equal {'view': <view>, 'ipv4addr': <ip-string>}
    • keyword arguments extattrs=None, force_proxy=False, return_fields=None
  • Returns a HostRecord instance built from the data returned by get_object, or a falsy/None result when nothing is found.
HostRecord.create(connector, **kwargs)
  • Accepts keyword arguments including view and ip.
  • ip may be passed as a list of IP objects.
  • First performs a search: calls connector.get_object exactly once with the same signature as above. When searching by view and by an IP object whose IPv4 address is '22.0.0.2', the search payload must equal {'view': <view>, 'ipv4addr': '22.0.0.2'} (the IP object is reduced to its plain string address for searching).
  • When the search returns nothing, calls connector.create_object exactly once with:
    • first positional argument 'record:host'
    • second positional argument the create payload, in which the IP information appears under the key ipv4addrs as a list of dicts. Each such dict contains the address under ipv4addr and, when supplied, mac (e.g. {'ipv4addr': '22.0.0.2', 'mac': 'fa:16:3e:29:87:70'}), together with view.
    • a third positional argument for return fields.
  • Returns a HostRecord instance built from the returned created data.
HostRecord.delete()
  • Calls connector.delete_object exactly once, passing the instance's _ref string (the _ref value from the data the instance was built from).
IP Objects and HostRecord fields

A HostRecord built from WAPI data whose ipv4addrs list contains one entry must expose an accessor to that entry as a parsed IP object. That IP object must expose attributes:

  • .ip — the address string (e.g. '22.0.0.2')
  • .host — the host value from the address entry
  • .configure_for_dhcp — the configure_for_dhcp value from the address entry
  • .mac — the mac value where present

An IP object with no host information must expose .host as None.

The relevant WAPI record shape for a host record with a single IPv4 address is:

{
    '_ref': '<ref string>',
    'ipv4addrs': [{
        'configure_for_dhcp': False,
        '_ref': '<ref string>',
        'ipv4addr': '22.0.0.2',
        'mac': 'fa:16:3e:29:87:70',
        'host': '<host string>'}],
    'extattrs': { ... }
}

  • create performs a search first and only calls create_object when the search yields no existing object.

Naming

The following names must be publicly importable from infoblox_client.objects: HostRecord, FixedAddress, FixedAddressV4, FixedAddressV6.

Task Specification: DUID Handling for IPv6 Fixed Addresses

Overview

You must implement/correct DUID (DHCP Unique Identifier) handling for IPv6 fixed address objects in the infoblox_client library, and provide a supporting utility function.

Required Public API Surface

1. infoblox_client.utils.generate_duid

A function generate_duid(mac) that accepts a MAC address string and returns a DUID string derived from it.

  • Signature: generate_duid(mac)
  • Called with a single positional argument (the MAC address).
  • Returns a DUID string.

(Its internal derivation algorithm is not constrained by this task beyond being deterministic for a given MAC; callers rely on the returned value being used as the object's duid.)

2. infoblox_client.objects.FixedAddress factory behavior

FixedAddress is a factory/constructor that, when called with an IPv6 address, returns an instance of objects.FixedAddressV6.

Constructor invocation form used:

objects.FixedAddress(connector, ip=<ip>, network_view=<view>, mac=<mac>)

Requirements when an IPv6 address is supplied:

  • The returned object must be an instance of objects.FixedAddressV6.
  • The object's mac attribute must equal the mac value passed to the constructor (it must be preserved, not cleared or overridden).
  • When a mac value is provided, the object's duid attribute must be set to the result of infoblox_client.utils.generate_duid(mac). That is, providing a MAC must cause exactly one call to generate_duid with the MAC as its sole argument, and the object's duid must equal the value that function returns.
  • Setting the mac must NOT reset or override the duid back to None; after construction with a MAC, duid must hold the generated value.
3. DUID preservation when constructing from server data

FixedAddressV6 objects may be constructed/populated from data returned by the backend (NIOS) — a dictionary that includes a duid key. In this case:

  • The object's duid attribute must equal the duid value present in the source data.
  • This duid value must not be lost or overwritten during object population (for example, it must survive any MAC processing that occurs while building the object).

Search / Retrieval Interaction (contextual, unchanged behavior)

When searching for an IPv6 fixed address by IP, network view, and MAC, the underlying connector is queried against the ipv6fixedaddress object type, and the search/return payload includes network_view, ipv6addr, and a duid field. The duid returned from the backend must be reflected on the resulting object (see requirement 3 above).

Summary of the Defect Being Fixed

Two related issues must be resolved:

  1. When an object is built from a backend reply that contains a duid, that duid must be correctly assigned to the object rather than dropped.
  2. When a mac is set on an IPv6 fixed address, the derived duid (from generate_duid(mac)) must be assigned and must not subsequently be overwritten with None.
