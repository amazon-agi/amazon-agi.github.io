01 SCTP INIT_ACK Chunk Parsing 797 words · source specification

Task Specification: SCTP INIT_ACK Chunk Parsing

Objective

Extend the existing SCTP header parser so that it can parse SCTP packets whose payload begins with an INIT_ACK chunk (chunk type 0x02), decomposing the packet into a flat list of field descriptors.

Public API

The parser must be importable and usable via the following surface (already established by existing DATA and INIT chunk support; INIT_ACK must integrate consistently):

  • SCTPParser — a class with a no-argument constructor.
    • Method: parse(self, buffer: Buffer) -> HeaderDescriptor
  • SCTPFields — an enumeration/namespace of field identifier constants (see required members below).
  • HeaderDescriptor — an object with a .fields attribute (a list of FieldDescriptor).
  • FieldDescriptor — an object with attributes .id, .position (int), and .value (a Buffer).
  • Buffer — a byte-content container constructed as Buffer(content: bytes, length: int), where length is expressed in bits. Two Buffer instances are equal when their content and bit-length match.

These types live in the same modules already used by the existing SCTP parser tests; do not change their locations.

Required SCTPFields members

The following identifier constants must exist and be used by the parser:

  • SCTPFields.SOURCE_PORT
  • SCTPFields.DESTINATION_PORT
  • SCTPFields.VERIFICATION_TAG
  • SCTPFields.CHECKSUM
  • SCTPFields.CHUNK_TYPE
  • SCTPFields.CHUNK_FLAGS
  • SCTPFields.CHUNK_LENGTH
  • SCTPFields.CHUNK_INIT_ACK_INITIATE_TAG
  • SCTPFields.CHUNK_INIT_ACK_ADVERTISED_RECEIVER_WINDOW_CREDIT
  • SCTPFields.CHUNK_INIT_ACK_NUMBER_OF_OUTBOUND_STREAMS
  • SCTPFields.CHUNK_INIT_ACK_NUMBER_OF_INBOUND_STREAMS
  • SCTPFields.CHUNK_INIT_ACK_INITIAL_TSN
  • SCTPFields.PARAMETER_TYPE
  • SCTPFields.PARAMETER_LENGTH
  • SCTPFields.PARAMETER_VALUE

(The existing DATA/INIT field members must remain functional; only add what is missing.)

Input

parse receives a single Buffer whose content is the raw SCTP packet bytes and whose length equals len(content) * 8.

Parsing behavior for an INIT_ACK chunk

The packet layout to parse (when the chunk type byte is 0x02) is:

Common SCTP header (12 bytes)

Produce these field descriptors in order:

  1. SOURCE_PORT — 16 bits, bytes 0–1.
  2. DESTINATION_PORT — 16 bits, bytes 2–3.
  3. VERIFICATION_TAG — 32 bits, bytes 4–7.
  4. CHECKSUM — 32 bits, bytes 8–11.
INIT_ACK chunk common header
  1. CHUNK_TYPE — 8 bits (value 0x02 for INIT_ACK).
  2. CHUNK_FLAGS — 8 bits.
  3. CHUNK_LENGTH — 16 bits. This is the total length in bytes of the chunk (chunk type + flags + length + fixed fields + all parameters, before final chunk padding).
INIT_ACK fixed fields
  1. CHUNK_INIT_ACK_INITIATE_TAG — 32 bits.
  2. CHUNK_INIT_ACK_ADVERTISED_RECEIVER_WINDOW_CREDIT — 32 bits.
  3. CHUNK_INIT_ACK_NUMBER_OF_OUTBOUND_STREAMS — 16 bits.
  4. CHUNK_INIT_ACK_NUMBER_OF_INBOUND_STREAMS — 16 bits.
  5. CHUNK_INIT_ACK_INITIAL_TSN — 32 bits.
Variable-length parameters (Type-Length-Value)

After the fixed fields, the remainder of the chunk consists of zero or more parameters. Each parameter begins with:

  • PARAMETER_TYPE — 16 bits.
  • PARAMETER_LENGTH — 16 bits. This value is the number of bytes covering the type, length, and value fields together (i.e. 4 + value_byte_length).

Then, only when the parameter carries a value (i.e. PARAMETER_LENGTH > 4):

  • PARAMETER_VALUE — (PARAMETER_LENGTH - 4) * 8 bits, containing exactly the parameter's value bytes (no padding included).

When PARAMETER_LENGTH == 4 there is no value, so no PARAMETER_VALUE descriptor is emitted for that parameter — only its PARAMETER_TYPE and PARAMETER_LENGTH.

Parameters must be consumed sequentially until the chunk's declared length (CHUNK_LENGTH) is exhausted. Parameter parsing must be driven by the chunk length, and internal padding must be accounted for so consecutive parameters are located at correct offsets. No parameter-padding field descriptor is emitted in this scenario.

Output ordering and count

HeaderDescriptor.fields must be a list of FieldDescriptor objects in the exact order the fields appear in the packet. Every field descriptor's position is 0. Each descriptor's value is a Buffer whose content is the raw bytes of that field and whose bit-length equals the field's bit width as specified above.

Concrete example

For an INIT_ACK packet consisting of the common header, the INIT_ACK fixed fields, one parameter of type 0x0007 with a 800-bit (100-byte) value, and one parameter of type 0xc000 with declared length 0x0004 (no value), the resulting fields list contains exactly 17 descriptors, in order:

  1. SOURCE_PORT = b'\x00\x07' (16)
  2. DESTINATION_PORT = b'\x00\x07' (16)
  3. VERIFICATION_TAG = b'\x43\x23\x25\x44' (32)
  4. CHECKSUM = b'\xc9\x01\x85\x24' (32)
  5. CHUNK_TYPE = b'\x02' (8)
  6. CHUNK_FLAGS = b'\x00' (8)
  7. CHUNK_LENGTH = b'\x00\x80' (16)
  8. CHUNK_INIT_ACK_INITIATE_TAG = b'\x00\x00\x0e\xb0' (32)
  9. CHUNK_INIT_ACK_ADVERTISED_RECEIVER_WINDOW_CREDIT = b'\x00\x00\x10\x00' (32)
  10. CHUNK_INIT_ACK_NUMBER_OF_OUTBOUND_STREAMS = b'\x00\x11' (16)
  11. CHUNK_INIT_ACK_NUMBER_OF_INBOUND_STREAMS = b'\x00\x11' (16)
  12. CHUNK_INIT_ACK_INITIAL_TSN = b'\x00\x00\x36\x14' (32)
  13. PARAMETER_TYPE = b'\x00\x07' (16)
  14. PARAMETER_LENGTH = b'\x00\x68' (16)
  15. PARAMETER_VALUE = the 100 value bytes (800 bits)
  16. PARAMETER_TYPE = b'\xc0\x00' (16)
  17. PARAMETER_LENGTH = b'\x00\x04' (16)

Note in this example that the first parameter's declared length (0x68 = 104) covers 4 header bytes plus 100 value bytes; the second parameter's declared length is 4, so it emits no value descriptor.

Constraints

  • Existing SCTP parsing behavior for DATA and INIT chunks must remain intact and unchanged.
  • The return value is always a HeaderDescriptor instance.

parse receives a Buffer containing a complete SCTP packet: the 12-byte SCTP common header followed by one SACK chunk. SCTP Common Header (bytes 0–11)
Order id Bit length Byte offset
0 SOURCE_PORT 16 0–1
1 DESTINATION_PORT 16 2–3
2 VERIFICATION_TAG 32 4–7
3 CHECKSUM 32 8–11
SACK Chunk (starting at byte 12)
Order id Bit length Byte offset
4 CHUNK_TYPE 8 12

Worked Example

For an input packet whose bytes are:

Only the fixed portion of the SACK chunk (through the "Number of Duplicate TSNs" field) is in scope. Parsing of the variable Gap Ack Block entries and Duplicate TSN entries is not required and is not exercised.

The existing parsing behavior for other chunk types (e.g. INIT, INIT ACK) must continue to work unchanged.

The relevant public API (already present, to be extended) is:

  • SCTPFields — a container of string/identifier constants used as field ids.
  • HeaderDescriptor — has an attribute fields, a list of FieldDescriptor.
  • FieldDescriptor — has attributes id, position (int), and value (a Buffer).
  • Buffer — a byte-content container constructed as Buffer(content=<bytes>, length=<bit_length>), comparable via ==.

These are importable from the same modules used by the existing SCTP parser tests.

Required Behavior

SCTPParser().parse(buffer=...) receives a Buffer wrapping the raw bytes of an SCTP packet (a common header followed by a single chunk). It must return a HeaderDescriptor whose fields list contains one FieldDescriptor per parsed field, in packet byte order.

Field identifiers (on SCTPFields)

The following identifier constants must exist and be used as the id of the corresponding FieldDescriptor:

  • SCTPFields.SOURCE_PORT
  • SCTPFields.DESTINATION_PORT
  • SCTPFields.VERIFICATION_TAG
  • SCTPFields.CHECKSUM
  • SCTPFields.CHUNK_TYPE
  • SCTPFields.CHUNK_FLAGS
  • SCTPFields.CHUNK_LENGTH
  • SCTPFields.PARAMETER_TYPE
  • SCTPFields.PARAMETER_LENGTH
  • SCTPFields.PARAMETER_VALUE
Parsing a HEARTBEAT chunk

When the chunk type byte has value 0x04 (HEARTBEAT), the parser must produce exactly the following fields, in this order:

SCTP common header (first 12 bytes):

  1. SOURCE_PORT — 16 bits, position 0
  2. DESTINATION_PORT — 16 bits, position 0
  3. VERIFICATION_TAG — 32 bits, position 0
  4. CHECKSUM — 32 bits, position 0

Chunk common header (next 4 bytes):

  1. CHUNK_TYPE — 8 bits, position 0 (value 0x04 for HEARTBEAT)
  2. CHUNK_FLAGS — 8 bits, position 0
  3. CHUNK_LENGTH — 16 bits, position 0

HEARTBEAT chunk parameter (a single Heartbeat Info parameter):

  1. PARAMETER_TYPE — 16 bits, position 0
  2. PARAMETER_LENGTH — 16 bits, position 0
  3. PARAMETER_VALUE — a variable-length byte field, position 0. Its length in bits is derived from the PARAMETER_LENGTH value: the parameter length counts the whole parameter including the 2-byte type and 2-byte length fields, so the value field occupies (parameter_length - 4) bytes, i.e. (parameter_length - 4) * 8 bits.

Each FieldDescriptor.value must be a Buffer whose content is the exact bytes read from the packet for that field and whose length is the bit length listed above.

Worked example

Given a packet consisting of these bytes:

0b 59 0b 59 00 00 0e 50 53 c3 05 5f 04 00 00 18
00 01 00 14 40 e4 4b 92 0a 1c 06 2c 1b 66 af 7e
00 00 00 00

wrapped as Buffer(content=<those bytes>, length=len*8), the returned HeaderDescriptor.fields must have length 10 and the following field values:

# id value bytes value bit length
0 SOURCE_PORT 0b 59 16
1 DESTINATION_PORT 0b 59 16
2 VERIFICATION_TAG 00 00 0e 50 32
3 CHECKSUM 53 c3 05 5f 32
4 CHUNK_TYPE 04 8
5 CHUNK_FLAGS 00 8
6 CHUNK_LENGTH 00 18 16
7 PARAMETER_TYPE 00 01 16
8 PARAMETER_LENGTH 00 14 16
9 PARAMETER_VALUE 40 e4 4b 92 0a 1c 06 2c 1b 66 af 7e 00 00 00 00 128

Here PARAMETER_LENGTH is 0x0014 = 20, so the parameter value is 20 - 4 = 16 bytes = 128 bits.

All position values are 0. The return value must be a HeaderDescriptor instance, and every entry in its fields list must be a FieldDescriptor instance.

Constraints

  • Preserve the existing behavior of SCTPParser.parse for chunk types already supported; only add correct handling for the HEARTBEAT chunk (type 0x04).
  • Do not add fields beyond those enumerated above for the HEARTBEAT case.

Overview

Extend the existing SCTP header parser so that it correctly parses SCTP packets carrying a HEARTBEAT ACK chunk. Preserve the established HEARTBEAT request behavior, including extraction of the complete Heartbeat Info parameter value.

The SCTP wire discriminators are significant and must remain distinct:

  • 0x04 identifies a HEARTBEAT request.
  • 0x05 identifies a HEARTBEAT ACK.
  • 0x01 identifies INIT; it must not be interpreted as HEARTBEAT.

Public API Surface

The following must be importable and usable exactly as described:

  • Parser class: SCTPParser, instantiable with no arguments as SCTPParser().
    • Method: parse(self, buffer: Buffer) -> HeaderDescriptor
  • Field identifier enumeration: SCTPFields, providing at least these members:
    • SOURCE_PORT
    • DESTINATION_PORT
    • VERIFICATION_TAG
    • CHECKSUM
    • CHUNK_TYPE
    • CHUNK_FLAGS
    • CHUNK_LENGTH
    • PARAMETER_TYPE
    • PARAMETER_LENGTH
    • PARAMETER_VALUE
  • Supporting types:
    • Buffer(content: bytes, length: int), where length is expressed in bits and equality compares both content and bit length.
    • HeaderDescriptor, with a .fields list of FieldDescriptor objects.
    • FieldDescriptor, with .id, .position, and .value attributes; .value is a Buffer.

Required Behavior

SCTPParser.parse receives a Buffer containing the raw bytes of an SCTP packet and returns a HeaderDescriptor. Its .fields list contains one FieldDescriptor for each parsed field, in packet order. Every returned field has .position == 0.

Chunk-type dispatch and compatibility

The chunk type octet determines the chunk-specific field layout after the common chunk header:

  • For chunk type 0x04, parse the chunk as a HEARTBEAT request and expose its Heartbeat Info parameter fields.
  • For chunk type 0x05, parse the chunk as a HEARTBEAT ACK and expose its Heartbeat Info parameter fields in exactly the same way as for a request.
  • Chunk type 0x01 remains INIT and must continue to use the established INIT layout. It must not produce the HEARTBEAT parameter-only layout described below.
SCTP common header

The fixed 12-byte SCTP common header produces these fields first, in order:

  1. SOURCE_PORT — 16 bits
  2. DESTINATION_PORT — 16 bits
  3. VERIFICATION_TAG — 32 bits
  4. CHECKSUM — 32 bits
Chunk common header

The chunk common header immediately following the SCTP common header produces these fields next, in order:

  1. CHUNK_TYPE — 8 bits
  2. CHUNK_FLAGS — 8 bits
  3. CHUNK_LENGTH — 16 bits
HEARTBEAT and HEARTBEAT ACK parameter

Both HEARTBEAT (0x04) and HEARTBEAT ACK (0x05) carry a Heartbeat Info parameter. A chunk containing the single parameter is decomposed into these fields after the chunk common header:

  1. PARAMETER_TYPE — 16 bits
  2. PARAMETER_LENGTH — 16 bits
  3. PARAMETER_VALUE — all parameter value bytes

The parameter length is the complete parameter length, including the 4-byte parameter type and length header. Therefore, for a valid parameter whose declared length is L bytes, PARAMETER_VALUE contains the following L - 4 bytes and has bit length (L - 4) * 8. The value must be exposed as SCTPFields.PARAMETER_VALUE, rather than as an undifferentiated chunk value, and no bytes belonging to the parameter value may be omitted.

For the 20-byte Heartbeat Info parameter in the examples below, the 4-byte parameter header is followed by a 16-byte, 128-bit value.

A HEARTBEAT request uses chunk type 0x04. For example:

  • HEARTBEAT request and HEARTBEAT ACK chunks with the single parameter shown above must each produce exactly the 10 fields listed, in that order.

  • Every field value must be a Buffer with the exact content and bit length specified.

  • Existing HEARTBEAT request parsing for chunk type 0x04 must remain intact, including complete PARAMETER_VALUE extraction.

Common header (always parsed, in this order)
Field id Bit length
Source Port SOURCE_PORT 16
Destination Port DESTINATION_PORT 16
Verification Tag VERIFICATION_TAG 32
Checksum CHECKSUM 32

Each field's .value is a Buffer whose content is the corresponding raw bytes and whose bit length matches the table.

Chunk common header (always parsed after the common header, in this order)
Field id Bit length
Chunk Type CHUNK_TYPE 8
Chunk Flags CHUNK_FLAGS 8
Chunk Length CHUNK_LENGTH 16

The Chunk Type byte determines which chunk-specific fields (if any) follow. The Chunk Length field is a 16-bit value giving the length of the chunk (chunk common header plus chunk body) in bytes.

Required Chunk Handling

SHUTDOWN — Chunk Type 0x07

Append one field:

Field id Bit length
Cumulative TSN Ack CHUNK_SHUTDOWN_CUMULATIVE_TSN_ACK 32

Total field count: 8.

SHUTDOWN ACK — Chunk Type 0x08

No chunk-specific fields. Total field count: 7.

SHUTDOWN COMPLETE — Chunk Type 0x0e

No chunk-specific fields. Total field count: 7.

Append one field:

Field id Bit length
Cookie CHUNK_COOKIE_ECHO_COOKIE (Chunk Length − 4) × 8

The cookie occupies the remainder of the chunk after the 4-byte chunk common header. Its byte length is Chunk Length − 4 (the 4 bytes being the chunk common header), and its bit length is that byte count times 8. The .value content is exactly those bytes.

Total field count: 8.

COOKIE ACK — Chunk Type 0x0b

No chunk-specific fields. Total field count: 7.

General Requirements

  • parse returns a HeaderDescriptor instance.
  • All entries in .fields are FieldDescriptor instances.
  • Every field's .position is 0.
  • Each field's .value is a Buffer whose content equals the raw bytes read from the packet at that field's location and whose length (in bits) equals the sizes specified above.
  • Field descriptors must appear in the exact order given (common header fields first, then chunk common header fields, then any chunk-specific fields).

Do not add behavior beyond what is specified above for these five chunk types.

Context

There is an existing Buffer class used to represent sequences of bits stored inside byte buffers. The relevant public API includes:

  • A Buffer class (importable from the module used by the rest of the binary buffer code, e.g. Buffer).

  • Padding.LEFT: the meaningful bits are right-aligned; padding bits occupy the high-order (leftmost) positions of the byte sequence.
  • Padding.RIGHT: the meaningful bits are left-aligned; padding bits occupy the low-order (rightmost) positions of the byte sequence.

Required Change

Implement the unary bitwise NOT operator (~) on Buffer, i.e. add an __invert__ method that returns a new Buffer.

Behavior

Applying ~ to a Buffer produces a new Buffer in which every meaningful bit is flipped (0 ↔ 1). The result must have:

  • the same length as the input,
  • the same padding as the input,
  • a content in which only the meaningful bit positions have been inverted; the padding bit positions must remain 0.

In other words, invert only the bits that fall within the length meaningful bits (positioned according to padding), and leave all padding bit positions cleared to 0.

Examples

  1. Full-width buffer (no padding):

    • Input: content=b'\x01\xff\xf0', length=24 (default Padding.LEFT).
    • Result: content=b'\xfe\x00\x0f', length=24, Padding.LEFT.

  2. Left padding (meaningful bits right-aligned):

    • Input: content=b'\x0f\xff\xf0', length=20, Padding.LEFT.
    • The top 4 bits are padding. Only the low 20 bits are inverted; the padding bits stay 0.
    • Result: content=b'\x00\x00\x0f', length=20, Padding.LEFT.

  3. Right padding (meaningful bits left-aligned):

    • Input: content=b'\x0f\xff\x80', length=20, Padding.RIGHT.
    • The bottom 4 bits are padding. Only the high 20 bits are inverted; the padding bits stay 0.
    • Result: content=b'\xf0\x00\x70', length=20, Padding.RIGHT.

The operation does not mutate the original buffer; it returns a new Buffer.

Task Specification: Buffer Class Bit-Level Operations

Overview

Implement and maintain a Buffer data model for logical bit strings stored in byte content. A buffer has a logical bit length and an alignment indicating whether unused bits are on the left or right. The required operation in this task is robust bit-level concatenation through Buffer.__add__, including byte-unaligned operands and operands with different alignments.

Public API Surface

Module and imports

The following names must remain importable from microschc.binary.buffer:

  • Buffer — the bit-buffer class.
  • Padding — the alignment enumeration, with Padding.LEFT and Padding.RIGHT (whose string values are "left" and "right").
Constructor

Buffer(content: bytes, length: int, padding: Padding = Padding.LEFT)

  • content is the byte representation containing the logical bits.
  • length is the number of meaningful bits.
  • padding identifies the side occupied by unused bits.
  • With Padding.RIGHT, meaningful bits are packed toward the most-significant side and unused low-order bits are on the right.
  • With Padding.LEFT, meaningful bits are packed toward the least-significant side and unused high-order bits are on the left.
  • Padding bits are not part of the logical bit sequence. For a non-byte-aligned value, the number of unused bits in its minimal byte representation is (8 - length % 8) % 8.
Equality compatibility

Buffer instances must continue to support ==. Concatenation results must compare equal to the expected Buffer values below. Their public content, length, and padding must also have the specified values; semantic equality alone must not be used to disregard the required result alignment. Existing equality behavior outside this task must not be changed.

Concatenation with Buffer.__add__

left + right -> Buffer

Both operands are Buffer instances. If the right-hand operand is not a Buffer, addition must raise TypeError.

Logical result

Concatenation must:

  1. Read only the left.length meaningful bits from left, according to left.padding.
  2. Read only the right.length meaningful bits from right, according to right.padding.
  3. Append the right operand's meaningful bits immediately after the left operand's meaningful bits, preserving bit order within each operand.
  4. Return a Buffer whose length is left.length + right.length.

Padding bits from either operand must never be included in the concatenated logical sequence. This applies equally to zero-valued meaningful bits: appending a meaningful 0 still increases the result length even when it does not change the visible byte value. Leading zero bits and bytes that belong to the declared logical length must likewise be preserved.

Result alignment

The result must preserve the alignment convention of the left operand:

  • If left.padding is Padding.RIGHT, the result must have padding == Padding.RIGHT. Its concatenated bits are packed toward the most-significant side, and unused low-order bits in the final byte are zero.
  • If left.padding is Padding.LEFT, the result must have padding == Padding.LEFT. Its concatenated bits are packed toward the least-significant side, and unused high-order bits in the first byte are zero.

The right operand's padding affects how its meaningful bits are extracted, but never selects the result's padding. This rule also applies when the left operand is empty. If the total length is byte-aligned, the result must still retain the left operand's Padding value even though no physical padding bits are needed.

The result content must use the byte representation required for the summed logical length, with all unused result bits cleared to zero. Concatenation must work for every pairing of left- and right-padded operands and across arbitrary byte boundaries.

The following results are required exactly:

  1. The unchanged byte value does not permit the appended zero bit to be dropped.

  2. Buffer(content=b"\x00\x8a\xf8", length=23, padding=Padding.RIGHT) concatenated with the low six meaningful bits of Buffer(content=b"\x22", length=6, padding=Padding.LEFT) produces Buffer(content=b"\x00\x8a\xf9\x10", length=29, padding=Padding.RIGHT).

  3. Alignment preservation is independent of the right operand's alignment:

    • Buffer(content=b"\x0f", length=4, padding=Padding.LEFT) + Buffer(content=b"\xf0", length=4, padding=Padding.RIGHT) produces Buffer(content=b"\xff", length=8, padding=Padding.LEFT).
    • Buffer(content=b"\xf0", length=4, padding=Padding.RIGHT) + Buffer(content=b"\x0f", length=4, padding=Padding.LEFT) produces Buffer(content=b"\xff", length=8, padding=Padding.RIGHT).

  4. An empty left operand still determines alignment: Buffer(content=b"", length=0, padding=Padding.LEFT) + Buffer(content=b"\x06", length=4, padding=Padding.LEFT) produces Buffer(content=b"\x06", length=4, padding=Padding.LEFT).

Compatibility and Non-goals

  • No new bitwise-complement (~) behavior is required by this task.
  • Bitwise AND (&), OR (|), value access, and the remaining Buffer operations may already exist; their established contracts must not be changed as part of the concatenation work.
