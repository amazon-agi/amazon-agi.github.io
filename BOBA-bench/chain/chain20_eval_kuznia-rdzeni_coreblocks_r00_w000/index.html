Required behavior

DependentCache is a base class intended to be subclassed. Subclasses call super().__init__() in their own __init__.

It exposes a single public method:

def get(self, cls):
    ...

Behavior of get:

  • When called with a class cls, it must construct an instance of cls, passing the DependentCache instance itself (self) as the single positional argument to cls's constructor (i.e. cls(self)).

        self.x = wc.x

b = wc.get(CachedObject)   # returns the same object; no new construction

02 You are working on a hardware description module (written using the Amaranth HDL framework, exposed in Python). 595 words · source specification

Task: Fix the Round-Robin Transaction Scheduler

Context

You are working on a hardware description module (written using the Amaranth HDL framework, exposed in Python). One of the components is a round-robin priority scheduler, implemented as an Amaranth Elaboratable. This scheduler arbitrates among multiple requesters, granting exactly one at a time in a rotating (round-robin) fashion.

There is a bug in the scheduler's grant logic that must be fixed. Specifically, under certain conditions the scheduler can assert a grant for a requester that did not request in the current cycle.

Scheduler Interface

The scheduler is a synchronous (clocked) module with the following observable ports (bit-vectors of count bits, one bit per requester):

  • requests (input): a bit-mask where each set bit indicates that the corresponding requester is asking to be granted this cycle.
  • grant (output, registered): a bit-mask indicating which requester is currently granted. At most one bit may be set. This value is held in a register and updates on clock edges.
  • valid (output): a single-bit signal that is high (1) when the current grant value points to a validly-granted requester (i.e. when a grant is actually being made this cycle), and low (0) otherwise.

The scheduler chooses the next granted requester by scanning from the position after the most-recently-granted one, wrapping around, and selecting the next requester that is currently asserting requests.

Required Behavior

On each clock cycle, given the requests input, the scheduler must produce grant and valid such that:

  1. A grant is only ever given to an active requester. If grant is nonzero and valid is high, then the granted bit must correspond to a bit that is set in the current cycle's requests. The scheduler must never assert a valid grant for a requester whose request bit is not set.

  2. No requests means no grant. When requests is 0 (no requester is asking), the scheduler must report valid = 0. In this situation there is no valid grant.

  3. Persistent single requester. When exactly one requester continuously asserts its request across consecutive cycles, that same requester must be granted each of those cycles: grant equals that requester's bit-mask and valid = 1 on each such cycle.

The Bug to Fix

The specific defect: after a cycle in which no request was granted (e.g. requests = 0), or in the general round-robin rotation, the scheduler could carry over or compute a grant/valid combination that asserts a grant for a requester that is not currently requesting. The fix must ensure that valid is only asserted when the granted bit genuinely corresponds to a currently-active request bit, in all cases — including immediately following an idle cycle and when a single requester begins (and continues) requesting.

Concrete Scenarios That Must Hold

Consider a 4-bit scheduler (count = 4), observed over successive clock cycles by driving requests and reading back grant after each step:

  • With requests = 0b0000, the resulting grant state must have valid = 0.
  • Following an idle cycle, driving requests = 0b0010 must grant exactly 0b0010 with valid = 1.
  • Continuing to drive requests = 0b0010 on the next cycle must again grant exactly 0b0010 with valid = 1.

At no point may the scheduler produce a valid grant for a bit not present in the current requests input.

Scope

  • Only the scheduler's grant/valid computation needs to change.
  • Do not alter the public interface (port names requests, grant, valid, and the count construction parameter must remain).
  • The single-grant-at-a-time and round-robin rotation semantics must be preserved.

Layout / field naming

For all three adapter roles in this task, both data_in and data_out are Records containing exactly one field named "data".

Transaction Manager and Conflict Resolution
TransactionManager(scheduler)
  • Constructed with a scheduler function (one of the scheduler functions listed below, or any function with the same contract).
  • The manager collects all transactions/methods declared within a transaction context and, each clock cycle, decides which transactions are granted.
  • Core correctness guarantee: two transactions that both use (call) the same method must never both be granted in the same clock cycle. They must be serialized — each call must complete (be granted, produce its result) as a distinct event. No call may be lost, duplicated, or merged with another.

  • Provides a context manager:
    • transactionContext() — within the with tm.transactionContext(): block, transactions and methods declared (including those created by instantiating Adapter / AdapterTrans and adding them as submodules) are registered with the manager.

Scheduler functions

Both scheduler functions share the same calling contract (the interface the TransactionManager uses internally to invoke them). Each implements a conflict-resolution policy that, given the set of ready transactions and their conflict relationships, produces the grant decisions for a cycle:

  • trivial_roundrobin_cc_scheduler — a round-robin policy: among ready, mutually-exclusive-with-already-granted transactions, it rotates which one is granted across cycles.
  • eager_deterministic_cc_scheduler — an eager, deterministic policy: it greedily grants as many non-conflicting ready transactions as possible in a single cycle using a fixed, deterministic ordering.

Reference Circuit (integration scenario the API must support)

The API must support building the following kind of circuit:

  • A single Adapter(i=32, o=32) provides a method. It is wrapped in a testbench adapter for driving/observing.
  • Two separate AdapterTrans instances each wrap a call to that same method's interface (adapter.iface), and each is wrapped in its own testbench adapter.
  • All three are added as submodules inside a with tm.transactionContext(): block of a TransactionModule built from TransactionManager(scheduler), where scheduler is one of the two scheduler functions above.

Because the two AdapterTrans transactions call the same method, they conflict and must be serialized by the manager. The design must be elaboratable and clockable as an ordinary synchronous Amaranth design.

Required end-to-end behavior of this circuit

Consider three concurrent simulation processes, each interacting with one of the three adapters using the enable/wait-for-done/read-output protocol described below:

  • Two "caller" processes, one per AdapterTrans, each feed a stream of distinct integer inputs (one process uses values from one range, the other from a disjoint range). Each call presents its input value and, upon completion, reads back the value returned by the method.
  • One "callee" process interacts with the Adapter that provides the method: on each granted method invocation it observes the argument that was passed by whichever caller was serviced, and it supplies a return value (from its own stream of distinct integers) that is delivered back to that caller.

The system must satisfy:

  1. No lost or spurious calls. Every value sent by a caller is delivered to the callee exactly once; every value supplied by the callee is returned to exactly one caller exactly once. Over a run, the multiset of arguments received by the callee equals the multiset of arguments sent by the two callers combined, and the multiset of return values received by the two callers equals the multiset of return values produced by the callee.
  2. Correct routing of return values. The return value each caller receives corresponds to the callee's response to that caller's invocation (the framework connects a single granted call's argument and result correctly, so a caller's returned value matches the callee value produced during its own serviced call).
  3. Serialization under conflict. Because both callers use the same method, at most one caller's call is serviced per cycle; the two callers' calls are interleaved without ever being merged.
  4. Robustness across offer rates. The above must hold regardless of how frequently each process actually issues/services a call (from every-cycle down to sparse, randomized offering).

This behavior must hold for both scheduler functions.

Simulation Interaction Protocol (testbench adapter helper)

A testbench wrapper exists (in the test support layer) that wraps an adapter and drives it through Amaranth simulation generator processes. Your adapters must expose the en, done, data_in, and data_out attributes so that the following interaction pattern works:

  • Enable / start a call: set en to 1 and drive the desired input fields onto data_in.
  • Poll for a result: in a given cycle, if done is 1, the outputs may be read from data_out (returned as a mapping of field-name → value); otherwise no result is available this cycle.
  • Complete a call: repeatedly advance clock cycles until a result is available (i.e., until done is asserted and outputs are read), then set en back to 0.

Thus a full call: assert en with inputs → wait cycles until done → capture data_out as {field: value} → deassert en → the captured outputs (e.g. {"data": <value>}) are the call's result.

These attribute names and semantics are the contract your AdapterBase/Adapter/AdapterTrans implementations must honor.

Constraints / Notes

  • Adapters take their interface/parameters via the constructor signatures given above: Adapter(i=..., o=...) and AdapterTrans(iface).
  • Do not merge or drop calls; the correctness guarantees above are mandatory and are exercised under both full and sparse request rates.
  • Only the behavior described here is required. Do not add unrelated features.

Task Specification: RISC-V ISA String Parser

Objective

Implement a module coreblocks.isa that parses a RISC-V ISA specification string and exposes the decoded properties. The module must define a public Extension type and a public ISA class.

Public API

Extension

An enumeration of RISC-V extension flags that supports bitwise OR composition (i.e., Extension.I | Extension.M produces a combined value, and multiple flags OR-ed together compare equal regardless of the order in which they were combined). It must be usable as a flag set (an IntFlag-style enumeration is appropriate).

The following members must exist:

  • Extension.I — base integer instruction set (32 registers)
  • Extension.E — reduced base integer instruction set (16 registers)
  • Extension.M — integer multiplication and division
  • Extension.A — atomic instructions
  • Extension.F — single-precision floating point
  • Extension.D — double-precision floating point
  • Extension.C — compressed instructions
  • Extension.ZIFENCE — instruction-fetch fence (fence instruction)
  • Extension.ZICSR — control and status register instructions
ISA
class ISA:
    def __init__(self, isa_str: str) -> None: ...

Constructing an ISA from an ISA string must parse the string and populate the following public instance attributes:

  • xlen (int) — the register/machine width in bits, taken from the rv32 / rv64 prefix (either 32 or 64).
  • reg_cnt (int) — the number of general-purpose registers: 32 for a base that includes the I extension, 16 for a base that includes the E extension.
  • extensions (Extension) — the combined set of extensions present, as an OR of Extension members.
  • ilen (int) — the base instruction length in bits; this is always 32.

ISA String Format

The input string has the form:

rv<xlen><extensions>
  • The literal, lowercase prefix rv.
  • <xlen> is exactly 32 or 64.
  • <extensions> is a description of the enabled extensions.
Extension encoding

Single-letter extensions correspond directly to their Extension member: i, e, m, a, f, d, c.

Multi-letter (z*) extensions are named tokens:

  • zifence → Extension.ZIFENCE
  • zicsr → Extension.ZICSR

Extensions may be written contiguously (e.g. imafdc) or separated by underscores (e.g. i_m_a_f_d_c). Multi-letter (z*) extensions are always underscore-separated tokens. Both notations must be accepted and yield the same result; for example, rv32imafdc_zifence_zicsr and rv32i_m_a_f_d_c_zifence_zicsr decode identically.

The g shorthand

The letter g is shorthand that expands to the combination:

Extension.I | Extension.M | Extension.A | Extension.F | Extension.D | Extension.ZIFENCE | Extension.ZICSR

(For example, rv64g yields exactly that combined set.)

Validity Rules

The following inputs are valid and must parse successfully:

  • rv32i → xlen 32, reg_cnt 32, I
  • rv32ima → xlen 32, reg_cnt 32, I | M | A
  • rv32imafdc → xlen 32, reg_cnt 32, I | M | A | F | D | C
  • rv32imafdc_zifence_zicsr → xlen 32, reg_cnt 32, I | M | A | F | D | C | ZIFENCE | ZICSR
  • rv32i_m_a_f_d_c_zifence_zicsr → same as above
  • rv32ec_zicsr → xlen 32, reg_cnt 16, E | C | ZICSR
  • rv64i → xlen 64, reg_cnt 32, I
  • rv64g → xlen 64, reg_cnt 32, I | M | A | F | D | ZIFENCE | ZICSR

In every valid case ilen is 32.

An invalid ISA string must cause the ISA constructor to raise RuntimeError. The following must be treated as invalid:

  • rv32 — a base integer extension (i or e) is required; neither is present.
  • rv32ie — I and E are mutually exclusive; both present is invalid.
  • rv64e — the E (reduced) base is not permitted with xlen 64.
  • rv32fdc — extensions are present but no base integer extension (i or e) is included.
  • rv64imadc — D requires F; D present without F is invalid.
  • RV32g_c — the rv prefix must be lowercase; uppercase is invalid.
  • rvima — the xlen (32 or 64) is missing.
  • rv42i — the xlen must be exactly 32 or 64; any other numeric value is invalid.

Summary of derived constraints

  • A base integer extension (i or e) must be present.
  • i and e may not both be present.
  • e is only valid with xlen 32.
  • d requires f.
  • The prefix must be exactly the lowercase literal rv, followed by exactly 32 or 64.
  • Any violation raises RuntimeError.

Required Behavior

Ordering semantics

  • On a write (we=1), only those granularity-bit slices of the addressed memory word whose corresponding sel bit is set are updated; slices whose sel bit is clear retain their previous value. Concretely, for each i in range(data_width // granularity), if bit i of sel is set, the memory word's bits [i*granularity : (i+1)*granularity] are overwritten with the corresponding bits of the request data; otherwise those bits are left unchanged.
  • On a read, the slave returns the full stored memory word (as before).

The memory slave exposes its backing memory such that individual words can be inspected (existing mem attribute behavior is preserved).

Existing Wishbone behavior not described here (response signaling, addressing, timing) must remain unchanged.

Task Specification: Reorganize coreblocks Package Structure and Fix Empty Transactions

Overview

This task has two parts:

  1. Reorganize the coreblocks package into a deeper, more structured directory layout by moving existing modules into new sub-packages. The public import paths must match exactly what is described below.

In the transaction framework (coreblocks.transactions), defining a transaction whose body calls no methods must not raise an exception. Such a transaction must be constructed and elaborated successfully, participating in the transaction scheduling machinery like any other transaction — the absence of any method calls within its body is a valid, supported case and must be handled gracefully.
