Expected behavior

DependentCache is a base class designed to be subclassed. Within their own __init__, subclasses invoke super().__init__().

The class exposes a single public method:

    ...

get behaves as follows:

  • When it is called with a class cls, it must construct an instance of cls, passing the DependentCache instance itself (self) as the single positional argument to the constructor of cls (i.e. cls(self)).

Task: Repair the Round-Robin Transaction Scheduler

Background

Your work concerns a hardware description module (written using the Amaranth HDL framework, exposed in Python). One of its components is a round-robin priority scheduler, implemented as an Amaranth Elaboratable. The scheduler arbitrates among multiple requesters, granting exactly one requester at a time in a rotating (round-robin) fashion.

The scheduler's grant logic contains a bug that must be fixed. In particular, under certain conditions the scheduler can assert a grant for a requester that did not request in the current cycle.

The Scheduler's Interface

The scheduler is a synchronous (clocked) module providing the following observable ports (bit-vectors of count bits, one bit per requester):

  • requests (input): a bit-mask in which each set bit signals that the corresponding requester is asking to be granted this cycle.
  • grant (output, registered): a bit-mask that shows which requester is currently granted. At most one bit may be set. The value is held in a register and updates on clock edges.
  • valid (output): a single-bit signal that is high (1) when the current grant value points to a validly-granted requester (that is, when a grant is actually being made this cycle), and low (0) otherwise.

To choose the next granted requester, the scheduler scans from the position after the most-recently-granted one, wraps around, and selects the next requester that is currently asserting requests.

Behavior Requirements

On each clock cycle, given the requests input, the scheduler must produce grant and valid meeting these conditions:

  1. Only active requesters are ever granted. When grant is nonzero and valid is high, the granted bit must correspond to a bit that is set in the current cycle's requests. For a requester whose request bit is not set, the scheduler must never assert a valid grant.

  2. No requests means no grant. If requests is 0 (no requester is asking), the scheduler must report valid = 0. In this situation, there is no valid grant.

  3. A single persistent requester. If exactly one requester asserts its request continuously across consecutive cycles, that same requester must be granted on each of those cycles: grant equals that requester's bit-mask and valid = 1 on each such cycle.

The Defect to Fix

The precise defect is the following: after a cycle in which no request was granted (e.g. requests = 0), or in the general round-robin rotation, the scheduler could carry over or compute a grant/valid combination asserting a grant for a requester that is not currently requesting. The fix must ensure that valid is asserted only when the granted bit genuinely corresponds to a currently-active request bit, in all cases — including immediately following an idle cycle and when a single requester begins (and continues) requesting.

Concrete Scenarios That Must Be True

Take a 4-bit scheduler (count = 4) and observe it across successive clock cycles by driving requests and reading back grant after each step:

  • When requests = 0b0000 is applied, the resulting grant state must have valid = 0.
  • Following an idle cycle, driving requests = 0b0010 must grant exactly 0b0010, with valid = 1.
  • If requests = 0b0010 is driven on the next cycle as well, the scheduler must again grant exactly 0b0010 with valid = 1.

At no point may the scheduler produce a valid grant for a bit that is not present in the current requests input.

Scope of the Change

  • The scheduler's grant/valid computation is the only part that needs to change.
  • The public interface must not be altered (the port names requests, grant, valid, and the count construction parameter must remain).
  • The semantics of single-grant-at-a-time and of round-robin rotation must be preserved.

The framework you are working on is a transaction framework for hardware description, built on top of the Amaranth HDL library (amaranth). It makes it possible to define transactions and methods, and a transaction manager arbitrates the execution of these; consequently, conflicting transactions never run within one and the same clock cycle. Required Behavior

The adapters (AdapterBase, Adapter, AdapterTrans)

An adapter is an Amaranth Elaboratable. The public attributes enumerated below are exposed by each adapter — meaning each AdapterBase subclass — and are usable from within a simulation process:

  • en — a 1-bit control signal. The adapter is requesting/enabling the method/transaction associated with it while this signal is set to 1, and it is not doing so while the signal is 0.
  • done — a 1-bit status signal. The framework sets it to 1 in the cycle where the adapter's method/transaction really executed — that is, the transaction manager granted it — and generated its output.
  • data_in — a Record holding the input payload that goes to the method/transaction.
  • data_out — a Record holding the output payload that the method/transaction produces.
Adapter

You construct it like this:

Adapter(i=<in_width>, o=<out_width>)
  • The bit width of the input layout is what i specifies; o in turn specifies the bit width of the output layout. Under the layout used here, a single field — called "data", with the given width — is carried by both data_in and data_out.
  • A method is defined/provided by an Adapter. An attribute exposes the interface of that method:
    • iface — the method interface object; it is suited to being wrapped by an AdapterTrans (see below).
  • Once the adapter is enabled (en == 1) and granted, the method it defines runs. How its input and output are related, for this task: the value the caller presents on the input is the value seen on the method's output side, and the reverse holds as well (the adapter plays the role of the method's callee endpoint — data travels through the method connection). To make this concrete for the circuit below: the two AdapterTrans instances call a method, and that method's body/target is the Adapter; the data a caller writes turns up at the Adapter's data_out, while the data written at the Adapter's data_in is what gets returned to the caller.
AdapterTrans

You construct it like this:

AdapterTrans(iface)

Here iface stands for a method interface (for instance the iface attribute of an Adapter).

  • A call to the given method is what an AdapterTrans encloses within a transaction of its own.
  • Its transaction requests to run when en == 1; a grant will come only if the scheduler of the transaction manager selects it and, in that same cycle, no conflicting transaction is chosen.
  • In the cycle where the grant happens, done is asserted; the input present on data_in is delivered as the argument to the method, and the method's return value shows up on data_out.
Layout and field names

Throughout this task, for each of the three adapter roles, data_in and data_out are Records having exactly one field apiece, and the name of that field is "data".

Conflict Resolution and the Transaction Manager
TransactionManager(scheduler)
  • Construction takes a scheduler function (one of the scheduler functions listed below, or any function obeying the same contract).
  • All transactions/methods declared within a transaction context are collected by the manager, which then, in each clock cycle, decides which transactions are granted.
  • Core correctness guarantee: where two transactions both use (call) the same method, they must never both be granted in one and the same clock cycle. They must be serialized — as a distinct event, each call must complete (be granted, produce its result). A call may not be lost, duplicated, or merged with another one.
TransactionModule(m, transaction_manager)
  • An Amaranth Module m and a TransactionManager are wrapped together by it.
  • A context manager is provided:
    • transactionContext() — inside a with tm.transactionContext(): block, the transactions and methods declared there — this covers those brought into existence by instantiating Adapter / AdapterTrans and adding them as submodules — get registered with the manager.
  • TransactionModule is elaboratable in its own right (it is the object that elaborate returns, and the one handed to the simulator), and the design it produces contains all of the registered logic together with the arbitration logic the manager generates.
The scheduler functions

One calling contract is shared by both scheduler functions (it is the interface via which the TransactionManager invokes them internally). What each implements is a conflict-resolution policy: taking the set of ready transactions plus their conflict relationships as input, it produces the grant decisions for a cycle:

  • trivial_roundrobin_cc_scheduler — a round-robin policy: from cycle to cycle, it rotates which one of the ready transactions that are mutually exclusive with the already-granted ones is granted.
  • eager_deterministic_cc_scheduler — a policy that is eager and deterministic: in one cycle it greedily grants ready transactions that do not conflict with each other, as many of them as possible, using an ordering that is fixed and deterministic.

The core correctness guarantee must be upheld by both schedulers (two transactions that call the same method are never to be granted in one cycle), and forward progress must be guaranteed by them: eventually, every transaction that keeps requesting will be granted.

Reference Circuit (the integration scenario that the API must support)

A circuit of the following kind must be buildable with the API:

  • A method is provided by one single Adapter(i=32, o=32). For driving/observing, a testbench adapter wraps it.
  • Two AdapterTrans instances, separate from one another, each enclose a call to the interface of that same method (adapter.iface), and a testbench adapter of its own wraps each of them.
  • A TransactionModule is built from TransactionManager(scheduler) — where scheduler is one of the two scheduler functions above — and all three are added as submodules inside a with tm.transactionContext(): block of it.

Since the method that the two AdapterTrans transactions call is the same one, a conflict exists between them, and the manager must serialize them. Like an ordinary synchronous Amaranth design, the result must be elaboratable and clockable.

End-to-end behavior required of this circuit

Imagine three simulation processes running concurrently, each of which talks to one of the three adapters by way of the enable/wait-for-done/read-output protocol laid out below:

  • Two processes play the role of "caller", one for each AdapterTrans; each of them feeds in a stream of distinct integer inputs (the values used by one process come from one range, and the other process draws from a disjoint range). For each call, the process presents its input value and, once the call is complete, it reads back the value the method returned.
  • A single process acts as the "callee" and interacts with the Adapter providing the method: on each granted method invocation, it observes the argument that the serviced caller — whichever of them it was — passed in, and it supplies a return value (drawn from its own stream of distinct integers) that is delivered back to that caller.

The following must be satisfied by the system:

  1. No lost or spurious calls. Every value that a caller sends is delivered to the callee exactly once; every value that the callee supplies is returned to exactly one caller, and exactly once at that. Over the whole of a run, the multiset of arguments the callee receives and the combined multiset of arguments the two callers send are equal; likewise, the multiset of return values the two callers receive and the multiset of return values the callee produces are equal.
  2. Correct routing of return values. The return value arriving at each caller corresponds to the callee's response to the invocation of that caller (when a single call is granted, the framework connects its argument and its result correctly; hence the value a caller gets back matches the callee value that was produced while its own call was serviced).
  3. Serialization under conflict. The same method is used by both callers; consequently, per cycle, at most one caller's call is serviced. The calls of the two callers are interleaved with one another, and at no point do they get merged.
  4. Robustness across offer rates. The above must hold regardless of how often each process in fact issues/services a call, with rates running from every-cycle offering down to sparse, randomized offering.

For both scheduler functions alike, this behavior must hold.

Simulation Interaction Protocol (testbench adapter helper)

There exists a testbench wrapper in the test support layer; it wraps an adapter and drives it by means of Amaranth simulation generator processes. So that the interaction pattern described below works, the attributes en, done, data_in, and data_out must be exposed by your adapters:

  • Enable / start a call: assign the value 1 to en, and drive the input fields that are wanted onto data_in.
  • Poll for a result: in a given cycle, if done is 1, the outputs may be read off data_out (with the outputs returned as a mapping of field-name → value); if it is not 1, no result is available in that cycle.
  • Complete a call: keep stepping the clock forward, cycle after cycle, until a result shows up — that is, until done is asserted and the outputs have been read — and after that set en back to 0.

A full call therefore goes: assert en together with the inputs → wait through cycles until done → capture data_out in the form {field: value} → deassert en → the outputs captured in this way (for example {"data": <value>}) make up the call's result.

The contract your AdapterBase/Adapter/AdapterTrans implementations must honor consists of these attribute names together with their semantics.

Notes / Constraints

  • Adapters get their interface/parameters from the constructor signatures given above: Adapter(i=..., o=...) and AdapterTrans(iface).
  • Calls are not to be merged or dropped; the correctness guarantees stated above are mandatory, and they are exercised under both full and sparse request rates.
  • The behavior described here is the only requirement. No unrelated features are to be added.

Extension

An enumeration of RISC-V extension flags which supports bitwise OR composition (i.e., Extension.I | Extension.M produces a combined value, and several flags OR-ed together compare equal regardless of the order in which they were combined). The members listed below must exist:

  • Extension.A — atomic instructions
  • Extension.F — single-precision floating point
  • Extension.D — double-precision floating point
  • Extension.C — compressed instructions
  • Extension.ZIFENCE — instruction-fetch fence (the fence instruction)
  • Extension.ZICSR — control and status register instructions
ISA
class ISA:
    def __init__(self, isa_str: str) -> None: ...

Constructing an ISA from an ISA string must parse the string and populate the public instance attributes listed below:

Format of the ISA string

The input string takes the form:

rv<xlen><extensions>
  • The prefix rv, which is literal and lowercase.
  • The <xlen> part is exactly 32 or 64.
  • <extensions> describes the enabled extensions.
Encoding of extensions

Each single-letter extension corresponds directly to its Extension member: i, e, m, a, f, d, c.

Multi-letter (z*) extensions are written as named tokens:

  • zifence → Extension.ZIFENCE
  • zicsr → Extension.ZICSR

Extensions may be written contiguously (e.g. imafdc) or with underscores between them (e.g. i_m_a_f_d_c). Multi-letter (z*) extensions are always underscore-separated tokens. Both notations must be accepted and must yield the same result; for example, rv32imafdc_zifence_zicsr and rv32i_m_a_f_d_c_zifence_zicsr decode identically.

Shorthand g

The letter g is a shorthand that expands to the combination:

Extension.I | Extension.M | Extension.A | Extension.F | Extension.D | Extension.ZIFENCE | Extension.ZICSR

(For instance, rv64g yields exactly that combined set.)

Rules for validity

The inputs listed below are valid and must parse successfully:

  • rv32i → xlen 32, reg_cnt 32, I
  • rv32ima → xlen 32, reg_cnt 32, I | M | A

  • rv32imafdc_zifence_zicsr → xlen 32, reg_cnt 32, I | M | A | F | D | C | ZIFENCE | ZICSR
  • rv32i_m_a_f_d_c_zifence_zicsr → same as above
  • rv32ec_zicsr → xlen 32, reg_cnt 16, E | C | ZICSR
  • rv64i → xlen 64, reg_cnt 32, I
  • rv64g → xlen 64, reg_cnt 32, I | M | A | F | D | ZIFENCE | ZICSR

ilen is 32 in every valid case.

  • rv32 — a base integer extension (i or e) is required; neither one is present.
  • rv32ie — I and E are mutually exclusive; having both present is invalid.
  • rv64e — the E (reduced) base is not permitted when xlen is 64.
  • rv32fdc — extensions are present, but no base integer extension (i or e) is included.
  • rv64imadc — D requires F; D without F present is invalid.
  • RV32g_c — the rv prefix must be written in lowercase; uppercase is invalid.
  • rvima — the xlen (32 or 64) is absent.
  • rv42i — the xlen must be exactly 32 or 64; any other numeric value is invalid.

Summary of the derived constraints

  • There must be a base integer extension (i or e) present.
  • i and e may not both be present.
  • e is valid only with xlen 32.
  • d requires f.
  • The prefix must consist of exactly the lowercase literal rv, followed by exactly 32 or 64.
  • Any violation raises RuntimeError.

Summary

  • put — adds a fresh entry to the buffer.

    • Input: a record/struct that has two fields:
      • rl_dst — an index of a logical destination register, log_regs_bits wide.
      • rp_dst — an index of a physical destination register, phys_regs_bits wide.
    • Output: a value that contains a ROB identifier (rob_id) for the entry that was just added, rob_entries_bits wide. When the call made through the adapter returns a single-field result, that returned value is the rob_id itself.
    • The entry begins in a not done state.

  • mark_done — marks an entry that already exists as completed/done.

    • Input: a ROB identifier (rob_id), rob_entries_bits wide, that identifies which entry is to be marked done. When it is called via the adapter with a single argument, that argument is the rob_id.

  • retire — removes the oldest entry and returns it, but only when that oldest entry is marked done.

    • It takes no input arguments.
    • Output: a record/struct with the same two fields that were provided to put for that entry:
      • rl_dst
      • rp_dst
    • The values that are returned must be exactly equal to the rl_dst/rp_dst pair that was passed to put when that entry was created.

Behavior Requirements

Ordering rules
  • Retirement happens in FIFO order: the entry that retire returns is always the oldest entry still in the buffer (the one that was added earliest by put and has not yet been retired).
  • Entries may be marked done through mark_done in any order, regardless of the order in which they were added.
  • An entry is returned by retire only if the oldest (front) entry has been marked done. If the front entry has not been marked done, or if the buffer is empty, retire must not produce a result and its transaction must not be ready to fire.
Readiness and handshake behavior
  • Whenever nothing is available to retire (the buffer is empty, or the front entry has not yet been marked done), the retire method must be not ready: an adapter that wraps it, when enabled and clocked for a cycle, must report its done signal as 0 (the transaction does not fire).
  • When the front entry is present and marked done, retire becomes ready, fires, returns that entry's data, and frees its slot, so that a subsequent entry (once it becomes the front and is done) can be retired.
Buffer capacity
  • The buffer's capacity is 2**rob_entries_bits entries. Being filled completely is a case it must handle correctly: after all slots have been filled, the entries marked done and retired, and once all added entries have been retired, retire must again become not ready (with done reported as 0).
  • Once an entry has been retired, its slot is reusable for future put operations. Across an extended run of interleaved put, mark_done, and retire operations (thousands of operations, with the same physical register indices being reused after retirement), the buffer must never corrupt or reorder data: each retire yields exactly the rl_dst/rp_dst that was originally put for that program-order position.
Concurrent use
  • put, mark_done, and retire must be usable concurrently inside the same clock domain (each one is driven through its own adapter). Their transactional definitions must permit them to operate in the same simulation without conflicting, such that the FIFO ordering and readiness guarantees above hold.

Notes

  • The wrapping of the three methods with AdapterTrans happens externally, and they are driven inside a TransactionModule; design them as standard transaction-framework methods having the input/output layouts described above.
  • Apart from having to be valid, positive bit-widths that produce a working buffer, the exact default values of GenParams are not constrained; the only hard requirement is that all three bit-width attributes exist and that 2**rob_entries_bits, 2**phys_regs_bits, and 2**log_regs_bits give the corresponding element counts.

  • To make it concrete: if the inner output adapter is disabled while the outer method's caller is enabled and drives arg = 0, then the outer method completes (done), and done is not reported by the inner adapter. If instead the inner output adapter is enabled and arg = 1, then the inner adapter and the outer method are both done. If the outer method's caller is disabled, then neither of them is done — even if arg stays at 1.

2. Method carrying an explicit readiness condition (def_method(m, meth, ready=<signal>)). When a method's definition uses a ready argument that is bound to a signal, the method must be grantable/executable — its calling adapter reports done — only when that ready signal is asserted and its caller is enabled. A low ready signal means the method must not be done; a high one means it must be done.

3. Method whose definition sits inside an m.If(<signal>) block. If the whole def_method definition of a method takes place under an m.If(ready) block, the method must be grantable/executable only when the condition signal in question is asserted, its caller being enabled. Condition low → not done; condition high → done.

4. Transaction carrying an explicit request condition (Transaction().body(m, request=<signal>)). If a transaction is created with a request argument that is bound to a signal, it must run only when the signal in question is asserted. Whenever it runs, it calls a method (adapter); done is reported by that adapter only when the request signal is high. Low → not done; high → done.

5. Transaction whose definition sits inside an m.If(<signal>) block. If entry into a transaction's body happens under an m.If(ready) block, the transaction must run only when the condition signal in question is asserted. Low → not done; high → done.

In every one of scenarios 2–5, the relevant TestbenchIO/adapter is enabled the entire time; moving the readiness/request/condition signal back and forth between 0 and 1 must make the adapter's done toggle between false and true in a corresponding way, with the effect observable once the combinational logic has settled, all within the same simulation step.

2.4 General extraction and the precedence rule for LUI

For every legal instruction except the explicit LUI exception:

  • opcode is the standard seven-bit major opcode found in instruction bits [6:0], represented by the matching Opcode member.
  • funct3 is given by bits [14:12].
  • funct7 is given by bits [31:25].
  • funct12 is given by bits [31:20].
  • A valid rd, rs1, or rs2 is, respectively, the bits [11:7], [19:15], or [24:20].

An instruction whose input major opcode is the standard LUI opcode 0b0110111 is deliberately canonicalized into an upper-immediate add operation. This rule takes precedence over both the general opcode extraction and the general funct3 extraction:

  • opcode = Opcode.OP_IMM, not a distinct LUI opcode;
  • funct3 = Funct3.ADD, regardless of input bits [14:12];
  • imm = instr[31:12] << 12;
  • op = OpType.ARITHMETIC;
  • rd is valid and is taken from bits [11:7].

As an example, 0x001230B7 must decode with opcode = Opcode.OP_IMM, funct3 = Funct3.ADD, rd = 1, imm = 0x00123000, and op = OpType.ARITHMETIC. For this encoding, reporting a LUI opcode, or the literal value of bits [14:12], is incorrect.

2.5 Construction of immediates

The instruction format to use is the one selected by the input instruction's actual encoding, including in cases where an output opcode is canonicalized:

  • Ordinary I type (OP_IMM, JALR, and LOAD): sign-extend the 12-bit value held in bits [31:20] to 32 bits.
  • RV32 shift-immediate exception (SLLI, SRLI, and SRAI): zero-extend only the five-bit shift amount located in bits [24:20]. Bits [31:25] choose the shift variant and must not appear in imm. Therefore 0x41F2D793 produces imm = 0x0000001F, and not 0x0000041F.
  • CSR-immediate exception (CSRRWI, CSRRSI, and CSRRCI): zero-extend the five-bit zimm located in bits [19:15]. For these forms, those bits are not a register operand.
  • U type (canonicalized LUI and AUIPC): copy bits [31:12] into immediate bits [31:12] and set the immediate bits [11:0] to zero.
  • S type (STORE): build {instr[31:25], instr[11:7]} and sign-extend the resulting 12-bit value.
  • B type (BRANCH): build {instr[31], instr[7], instr[30:25], instr[11:8], 1'b0} and sign-extend the resulting 13-bit value.
  • J type (JAL): build {instr[31], instr[19:12], instr[20], instr[30:21], 1'b0} and sign-extend the resulting 21-bit value.
  • A valid standard FENCE.I encoding carries a zero immediate and must report imm = 0.

Sign extension is observable in the 32-bit pattern: for example, -1 is 0xFFFFFFFF and -2 is 0xFFFFFFFE.

Function assign

Signature

    ...
  • The parameters lhs and rhs are Record objects from Amaranth.
  • fields can only be supplied as a keyword argument.
  • What the function returns is an iterable of Amaranth assignment statements — the objects that lhs_field.eq(rhs_field) creates, which expose .lhs and .rhs attributes referencing the underlying signals. The function may be written as a generator; callers may materialize the result with list(...).
How fields are selected

Denote by L the set of top-level field names found in lhs, and by R the set of top-level field names found in rhs.

fields decides the set of field names to be assigned:

  • AssignType.RHS: every field found in R gets assigned. Every field in R must additionally be present in L; when that fails, this is an error (see Errors).
  • AssignType.ALL: every field in the union of L and R gets assigned. L and R must be identical sets; when they are not, this is an error.
  • AssignType.COMMON: every field present in both L and R (their intersection) gets assigned. No error is raised over a field present on only one side.
  • A set, or any other iterable, of field names: assignment covers exactly the named fields (an iterable may repeat a name; such duplicates refer to the same field). Every named field must be present in both L and R; when that fails, this is an error.

For each field name that gets selected, one assignment getattr(lhs, name).eq(getattr(rhs, name)) is produced.

Field width checks

Each field chosen for assignment brings a width requirement: the matching lhs and rhs fields must have the same bit width. A difference in widths is an error.

Error behavior

In the situations listed here, the function must raise ValueError:

  • Under AssignType.RHS, when lhs is missing a field that rhs requires.
  • Under AssignType.ALL, when the field-name sets of lhs and rhs fail to be identical (in either direction, or because they merely overlap partially).
  • When fields is a set/iterable of names given explicitly and any named field is missing from lhs or from rhs (this covers being missing from both).
  • When, for a selected field, the bit width on lhs and on rhs is not the same.

Note: raising the errors lazily is allowed — they may come up as the returned iterable is consumed (in other words, raising while the result is being iterated/materialized is acceptable).

7. Fetch unit addressing scheme (within the fetch unit)

The fetch unit issues Wishbone read requests with word addresses: for the instruction at byte-PC pc, the Wishbone request address is pc >> 2 (i.e., the byte address divided by the 4-byte instruction size). Each successive fetch increments the word address by 1. The request address at the start corresponds to gen_params.start_pc >> 2.

The halt_pc mechanism: the fetch unit compares its byte-PC against halt_pc; it ceases to issue fetches once the PC would reach halt_pc, so instructions at byte offsets 0 .. halt_pc - ilen_bytes are fetched while everything at or after halt_pc is not.

Specification of the Task

Two related pieces of functionality must be implemented: a OneHotSwitch context manager utility, and the addition of byte/word-select (sel) support to an existing Wishbone bus implementation.

Part 1: The OneHotSwitch utility

Public interface

A function OneHotSwitch must be provided, importable as:

from coreblocks.utils import OneHotSwitch

Call signature:

OneHotSwitch(m, target)
  • m denotes an Amaranth Module.
  • target is an Amaranth Signal (or value) whose bit-width is N. Each bit position of target is treated as one "one-hot" case.
Behavior

OneHotSwitch acts as a context manager intended for use with the with statement. Entering the context yields a case constructor object, which is itself a context manager factory. It must support exactly the following usage pattern:

with OneHotSwitch(m, target) as OneHotCase:
    with OneHotCase(1 << 0):
        # statements active when target has exactly bit 0 set
        ...
    with OneHotCase(1 << 1):
        # statements active when target has exactly bit 1 set
        ...
    # ... one case per bit position ...

    with OneHotCase():          # optional, no argument
        # statements active when target is zero
        ...

Required semantics:

  • Calling OneHotCase(1 << i) opens a block; the statements in that block take effect precisely when target equals the one-hot value 1 << i (i.e., exactly that single bit set). For each valid bit index i in range(N), when that case is selected, any signals assigned inside the block must be driven according to target matching 1 << i.
  • A call to OneHotCase() with no argument opens a block; the statements in that block take effect precisely when target is 0 (no bits set). This "zero" case is optional — it may be left out of a OneHotSwitch block entirely, and in that case no zero-handling logic is added.
  • The construct must integrate with Amaranth's control-flow such that the assignments made inside each case block are mutually exclusive based on the value of target. Both the combinational assignments inside the case blocks and the normal synchronous logic elsewhere in the module must continue to work correctly.
Concrete requirement for correct behavior

Take a target signal of width 2**W together with an output that, for each bit index i, is assigned the integer i inside the corresponding OneHotCase(1 << i) block:

  • The output must equal i when target == (1 << i).
  • If the optional zero case is present and target == 0, the zero-case block's assignments must be active; for all nonzero one-hot inputs, the zero-case assignments must NOT be active.

Part 2: Support for the Wishbone sel (select) signal

The existing Wishbone bus master and memory slave implementation must be extended so that it supports the Wishbone sel signal (byte/word granularity select).

WishboneParameters

In addition to its existing data_width and addr_width, WishboneParameters must accept a keyword argument granularity:

WishboneParameters(data_width=..., addr_width=..., granularity=...)
  • granularity specifies how wide, in bits, each independently selectable slice of the data word is.
  • The sel signal's width is data_width // granularity. Each bit of sel corresponds to one contiguous granularity-bit slice of the data word, in ascending order (bit i of sel corresponds to the data bits [i*granularity : (i+1)*granularity]).
The Wishbone bus interface

A sel signal of width data_width // granularity must be exposed by the Wishbone master bus interface.

Request interface of the master

The master's request-issuing method must accept requests in the form of a record/dict with the following fields:

  • addr
  • data
  • we
  • sel

The sel value contained in a request must be driven onto the bus's sel line for that transaction. Whenever a transaction is issued, the bus adr, we, sel (and dat_w when writing) must reflect the requested values while stb and cyc are asserted.

The method for retrieving results returns a record/dict containing at least a data field; this is unchanged from the existing behavior. Response handling for ACK/ERR/RTY must be preserved: a retry (RTY) response restarts the cycle (re-issuing the same transaction with the same adr/sel) and does not yield a result until a terminating ACK/ERR response arrives.

sel semantics of the memory slave

On write transactions, the Wishbone memory slave must honor sel with per-slice granularity:

  • On a write (we=1), only those granularity-bit slices of the addressed memory word whose corresponding sel bit is set get updated; slices whose sel bit is clear keep their previous value. Concretely, for each i in range(data_width // granularity), if bit i of sel is set, the bits [i*granularity : (i+1)*granularity] of the memory word are overwritten with the corresponding bits of the request data; otherwise those bits stay unchanged.
  • On a read, the slave returns the full stored memory word, as before.

The memory slave exposes its backing memory so that individual words can be inspected (the existing mem attribute behavior is preserved).

Wishbone behavior that already exists and is not described here (response signaling, addressing, timing) must remain unchanged.
