Goal

The existing Flake8 logging plugin is to be extended so that the L002 check also reports relevant getLogger() calls inside the body of an ordinary function defined with def. This is a scope extension for L002 only: all existing rule semantics, diagnostics, and public interfaces must stay compatible.

L002 behavior that must be preserved

L002 examines recognized calls to the standard-library logging API in which the logger-name argument is an offending value instead of __name__. Its diagnostic message is exactly:

L002 use __name__ with getLogger()

The rule's established recognition of calls and arguments must stay unchanged. Specifically:

  • A qualified call made through the name bound by import logging, such as logging.getLogger(__file__), is recognized. This also covers a module name introduced by import logging as ....
  • The unaliased direct import from logging import getLogger, when followed by getLogger(...), is recognized.
  • The established offending first positional arguments include the bare module-level names __file__ and __cached__.
  • The bare name __name__ is correct and must not trigger L002.
  • A similarly named API that comes from a module other than the standard-library logging module must not trigger L002.

What this task changes is where the established L002 matcher is applied; beyond that, it must not change which imports, calls, or argument forms L002 recognizes. Results at module level and at other previously supported scopes must continue unchanged.

Required behavior for function bodies

L002 detection must examine the body of an ordinary function definition even though the function introduces a new scope. A matching offending call in a statement inside the body must not be skipped merely because it sits within a def. Within that body, the same L002 call and argument rules that are used at previously supported scopes apply.

As an example, given:

import logging
def thing():
    logging.getLogger(__file__)

the plugin must emit exactly one L002 diagnostic for the call inside thing:

(3, 22, "L002 use __name__ with getLogger()")

The extra traversal must not duplicate a diagnostic. Detection at module level and in every other previously supported scope must keep working unchanged.

Diagnostic position

An L002 diagnostic is anchored to the invalid first argument, not to the start of the getLogger() call expression.

  • The reported line is the AST lineno of the invalid argument node, which is 1-based.
  • The reported column is the AST col_offset of the invalid argument node, which is 0-based.

This location rule based on the argument holds in every scope. By way of comparison, module-level logging.getLogger(__file__) reports the zero-based column of __file__ (18), whereas a directly imported getLogger(__file__) reports the zero-based column of __file__ (10). When Flake8 renders a diagnostic, its usual one-based display-column conversion stays in effect; the column that the plugin yields remains the zero-based AST offset.

Task Specification: New Lint Rule L003 for extra Dict Keys That Clash with LogRecord Attributes

Background

The software in question is a flake8 plugin that finds problems with logging usage. A new lint rule, L003, must be added; it flags keys of the extra dictionary supplied to a logging call that clash with reserved LogRecord attribute names.

Behavior of the Rule

For a logging call that receives an extra keyword argument whose value is a dictionary literal, each key in that dictionary must be checked against a set of reserved LogRecord attribute names. An L003 violation must be reported whenever one of these reserved names matches a string-literal key.

Wording of the Reported Message

If the clashing key is named <KEY>, the text of the reported message must be exactly:

L003 extra key '<KEY>' clashes with LogRecord attribute

(Single quotes enclose the key name.)

Attribute Names Reserved by LogRecord

The names below must, at a minimum, be treated as clashing (they are the names exercised):

  • msg
  • args

The full standard set of LogRecord attribute names should be included, so that the rule is triggered only by genuine reserved names. A key like response_msg (it merely has a reserved name as a substring) must not trigger a violation; matching is performed on the exact key name only.

Where Violations Are Reported

The position of the dictionary key (the string literal key node) is where each violation gets reported, under the standard flake8 line/column convention: the internal column is 0-based (flake8 displays it +1).

Below, examples pair source code with the resulting violations (source → reported violations), each violation written in (line, col, message) form where col is 0-based:

  • import logging
logging.info("Hi", extra={"msg": "Ho"})

    → (2, 26, "L003 extra key 'msg' clashes with LogRecord attribute")

  • import logging
logging.debug("Hi", extra={"msg": "Ho"})

    → (2, 27, "L003 extra key 'msg' clashes with LogRecord attribute")

  • import logging
logging.info("Hi", extra={"args": (1,)})

    → (2, 26, "L003 extra key 'args' clashes with LogRecord attribute")

  • A multiline call where the key is on its own line reports at that key's line and column:

    import logging
logging.info(
    "Hi",
    extra={
        "msg": "Ho",
    },
)

    → (5, 8, "L003 extra key 'msg' clashes with LogRecord attribute")

  • Multiple clashing keys in one extra dict each produce a separate violation, reported in order of their position:

    import logging
logging.info(
    "Hi",
    extra={
        "args": (1,),
        "msg": "Ho",
    },
)

    → (5, 8, "L003 extra key 'args' ...") and (6, 8, "L003 extra key 'msg' ...")

  • No violation when no key clashes:

    import logging
logging.info("Hi", extra={"response_msg": "Ho"})

    → no violations

Which Calls Are Checked

The rule applies to logging calls, matching the same call forms handled elsewhere in this plugin:

  • Module-level logging calls via the logging module, e.g. logging.info(...), logging.debug(...), including inside function definitions.
  • Calls on a logger object obtained from logging.getLogger(...), regardless of the variable name it is assigned to, e.g.:
    logger = logging.getLogger(__name__)
logger.info("Hi", extra={"msg": "Ho"})
    and
    log = logging.getLogger(__name__)
log.info("Hi", extra={"msg": "Ho"})
    Both report the clash at the key's position.

Integration Requirements

The rule must be emitted by the existing flake8 plugin so that running flake8 over a file produces output lines in the standard flake8 format, e.g.:

./example.py:2:27: L003 extra key 'msg' clashes with LogRecord attribute

(The column shown is the 1-based counterpart of the internal 0-based column.)

An existing checker mechanism in the plugin — the same one that already yields L001/L002 results as (line, col, message) tuples — is what must produce the violations, so that running the plugin programmatically over source code yields the L003 tuples described above, and a flake8 run from the command line yields the corresponding formatted output lines.

Notes and Edge Cases

  • Inspection is needed only for dictionary literals passed directly as the extra keyword argument; the clash check covers string-literal keys only.
  • Matching against the reserved attribute-name set is done on an exact basis; substrings do not qualify.
  • Exactly one violation is yielded for each clashing key, and it is reported at that key's own source position.

Task Specification: New Lint Rule L004 — logger.exception() Outside except Clauses

Background

Your starting point is an existing Flake8 plugin that targets misuse of Python's standard logging module. The plugin already implements rules such as L003; L004 is a new rule that you must add.

The plugin exposes a checker class; Flake8 discovers it as a plugin by way of the plugin's entry point. Operating on a parsed AST, that checker yields lint results. Each result comes as a tuple of this shape:

(line_number, column_offset, message)

Within each tuple, line_number is 1-based, column_offset is 0-based, and message is a string that starts with the rule code.

The L004 Rule

Objective

Calls to .exception() that target the logging module or a logger object are to be flagged whenever the call does not occur inside an except clause. Since the logging.exception() / logger.exception() API is only meaningful while a currently-active exception is being handled (i.e., within an except block), a call made anywhere else is a mistake.

Diagnostic Message

In Flake8 output, the text coming after the standard <line>:<col>: prefix is exactly this message:

L004 avoid logger.exception() outside of except clauses
Detection Condition

Flagging applies to a call when all of the conditions below are true:

  1. The call takes the shape of a method call, <something>.exception(...), and <something> is:
    • the logging module itself (i.e., logging.exception(...)), or
    • a logger object obtained from logging.getLogger(...) and assigned to a name (e.g. logger = logging.getLogger(__name__) followed by logger.exception(...)).
  2. Lexically, the call does not appear inside the body of an except clause.

The reported position is the flagged call expression's own position (its line and column).

What "Inside an except Clause" Covers

  • A .exception() call sitting directly in the body of an except clause is acceptable and must not be flagged. This holds regardless of whether the try/except is at module level or nested inside a function definition.

  • When a .exception() call sits inside a function definition that is itself nested inside an except clause, the call must still be flagged. The function may be called at any later time — not necessarily while the exception is active — so an intervening def that wraps the call lexically in an except does not make the call safe. Put another way, for the purpose of deciding whether a call is "inside an except clause," the protection is broken by a function-definition boundary lying between the call and the enclosing except.

  • At module level, a .exception() call that has no enclosing except is flagged.

  • A .exception() call inside a function definition is flagged when no enclosing except clause exists between the call and the function scope (nor at module scope).

Example Outcomes

Flagged cases (each of them produces one L004 result at the call site):

import logging
logging.exception("Hi")            # module-level, no except

import logging
def thing():
    logging.exception("Hi")        # inside function, no except

import logging
try:
    acme_api()
except AcmeError:
    def handle():
        logging.exception("Hi")    # inside a def nested in except -> flagged
    handle()

import logging
logger = logging.getLogger(__name__)
logger.exception("Hi")             # logger var, no except

import logging
logger = logging.getLogger(__name__)
def thing():
    logger.exception("Hi")         # logger var inside function, no except

Not flagged (these yield no L004 results):

import logging
try:
    acme_api()
except AcmeError:
    logging.exception("Hi")        # directly inside except

import logging
def thing():
    try:
        acme_api()
    except AcmeError:
        logging.exception("Hi")    # directly inside except within a function

import logging
logger = logging.getLogger(__name__)
try:
    acme_api()
except AcmeError:
    logger.exception("Hi")         # logger var, directly inside except
How the Logging Module and Logger Objects Are Recognized

  • When the module is imported via import logging and referenced as logging.exception(...), the logging module must be recognized.

  • A logger object must be recognized when it is created via logging.getLogger(...) and a simple assignment binds it to a name (e.g., logger = logging.getLogger(__name__)); any subsequent .exception(...) call on that name is treated as a logger call.

Required Integration

The existing Flake8 plugin is what must produce this rule, so that a Flake8 run over a file containing an offending call emits a diagnostic line in the standard format, for example:

./example.py:2:1: L004 avoid logger.exception() outside of except clauses

(Note that the column reported by Flake8 is 1-based: the 0-based AST column offset plus one.)

Constraints

  • The behavior of existing rules must not be altered.
  • For L004, only the behavior described above is required.

Task Specification: the flake8-logging Plugin

Purpose

Create flake8-logging: a Flake8 plugin operating on the AST that examines Python source code for typical misuses of the standard-library logging module. Each diagnostic that this specification defines carries the LOG prefix.

The checks operate at the syntax level and must tell recognized imports of the standard-library logging module apart from unrelated modules or from callables whose names are similar.

Registering the Plugin and Its Checker Interface

The package is required to register a valid Flake8 AST plugin, one with this public behavior:

  • Setting select = LOG in the Flake8 configuration switches on all diagnostics defined by this specification.

  • The plugin announces itself as flake8-logging and exposes the version installed for it. Both the plugin name and a version number must be present in the output of Flake8's --version.

  • The checker class goes by flake8_logging.Plugin. A parsed AST is accepted via the tree keyword argument — Plugin(tree=parsed_tree) is one example.

  • Findings are yielded by the checker's run() method in 4-tuple form:

    (line_number, column_offset, message, type)

    In each 4-tuple, line_number counts from 1 and column_offset from 0, message opens with the full diagnostic code, and type is the checker class itself.

Once Flake8 drives the checker, diagnostics come out in the format Flake8 normally uses. Flake8 takes the checker's column offset, which is 0-based, and shows it as a 1-based displayed column. For example:

./example.py:2:1: LOG001 use logging.getLogger() to instantiate loggers

Diagnostics

LOG001 — use logging.getLogger() to instantiate loggers

Whenever a standard-library logging.Logger gets constructed directly — a situation where logging.getLogger() should be used instead — report it.

Emit this exact message:

LOG001 use logging.getLogger() to instantiate loggers

Calls are recognized in these forms:

  • logging.Logger(...) after import logging.
  • The matching module-attribute call made through an import alias, for instance import logging as log_module and then log_module.Logger(...).
  • Logger(...) after from logging import Logger.

With the module-attribute forms (logging.Logger(...) and its equivalent via a module alias), scope changes the outcome:

  • A call placed in a module body is reported.
  • A call placed in a class body is reported provided the class is not lexically inside a function.
  • Inside the body of a synchronous function (def) or an asynchronous function (async def), a call is not reported; this suppression extends to method bodies and to scopes nested inside such a function.

Wherever it occurs — function bodies included — the direct-name form imported with from logging import Logger stays recognized.

A similarly named constructor is not reported when it is not known to come from the standard-library logging module — for example our_logging.Logger(...) or an unrelated local Logger(...).

The position reported is the point at which the call expression starts.

Examples:

import logging

logging.Logger("module")  # LOG001

class Service:
    logger = logging.Logger("class")  # LOG001

def make_logger():
    return logging.Logger("local")  # no LOG001

async def make_async_logger():
    return logging.Logger("local")  # no LOG001
LOG002 — use name with getLogger()

A recognized getLogger() call is reported when its first positional argument is the name __file__ or __cached__; as logger names, __name__ should be used instead.

The exact message reads:

LOG002 use __name__ with getLogger()

The forms counted as recognized include:

  • logging.getLogger(__file__) and logging.getLogger(__cached__) after import logging.
  • Module-attribute calls made equivalently via an alias for the logging import.
  • getLogger(__file__) or getLogger(__cached__) after from logging import getLogger.
  • Calls inside nested scopes, function bodies among them.

Do not report:

  • logging.getLogger(__name__).
  • logging.getLogger() with no positional arguments supplied.
  • A getLogger attribute that belongs to an unrelated module.

The position to report is that of the offending first argument — not the start of the call.

LOG003 — extra key '<key>' clashes with LogRecord attribute

When a reserved LogRecord attribute name serves as a key in the extra= mapping of a recognized logging call, report that key.

The exact message template is:

LOG003 extra key '<key>' clashes with LogRecord attribute

Within the message, the clashing key shows up as a quoted Python string. For example:

LOG003 extra key 'msg' clashes with LogRecord attribute

The logging methods that are recognized are debug, info, warning, error, critical, log, and exception. The rule is to be applied to:

  • Calls made on the logging module, such as logging.info(...) and logging.debug(...), including calls through an alias for the imported logging module.
  • Calls on recognized logger references that were obtained from logging.getLogger(...). The variable holding the logger may be named anything — logger or log, for instance.

extra= is inspected where it is written directly, either as a dictionary literal or as a dict(...) call with keyword entries. For example:

extra={"msg": value}
extra=dict(msg=value)

The reserved names include:

  • asctime
  • args
  • created
  • exc_info
  • exc_text
  • filename
  • funcName
  • levelname
  • levelno
  • lineno
  • module
  • msecs
  • msg
  • name
  • pathname
  • process
  • processName
  • relativeCreated
  • stack_info
  • taskName
  • thread
  • threadName

Required behavior:

  • One finding is emitted for each clashing key.
  • When several clashing keys occur within a single mapping, their source order is preserved.
  • Calls and mappings that span multiple lines are handled as well.
  • The position to report is that of the clashing key entry — the literal key for a dictionary literal, the keyword key for a dict(...) call.
  • The rule reaches into nested scopes too, function bodies included.
  • When every directly visible key is non-reserved, emit no finding.
  • Keys are not inferred from an expression like extra=extra; mapping expressions that are unsupported or non-literal lead to no LOG003 finding.
  • A logging call lacking an extra= argument likewise leads to no LOG003 finding.

Examples:

import logging

logging.info("response", extra={"msg": response.msg})  # LOG003
logging.debug("response", extra=dict(args=response.args))  # LOG003
logging.info("response", extra={"response_msg": response.msg})  # no LOG003
LOG004 — avoid logger.exception() outside of except clauses

A recognized .exception(...) logging call is reported unless it is lexically contained, within the same function scope, in an except handler.

The exact message reads:

LOG004 avoid logger.exception() outside of except clauses

The check is to be applied to:

  • logging.exception(...), with use via an alias for the imported logging module included.
  • .exception(...) calls made on recognized logger references that came from logging.getLogger(...).
  • Calls located at module level, plus calls sitting inside synchronous or asynchronous functions.

Being lexically within an except handler makes a call allowed. Across a nested function boundary, a surrounding handler does not carry: should a function be defined inside an except handler, an .exception(...) call within it must still produce LOG004, because the function may execute once the handler is no longer active.

Consequently, this is accepted:

import logging

try:
    perform_action()
except ActionError:
    logging.exception("action failed")  # no LOG004

These calls get reported:

import logging

logging.exception("no active exception")  # LOG004

try:
    perform_action()
except ActionError:
    def handle_later():
        logging.exception("may run later")  # LOG004

Place the finding at the start of the call expression.

Task Specification: Adding a LOG005 Diagnostic to the flake8-logging Plugin

Overview

You are extending a flake8 plugin that lints for logging-related issues. You must add a new diagnostic code, LOG005, that flags calls to logging.error(...) located inside an except clause where the call should instead be logging.exception(...).

Public API

The plugin's checker is invoked via the standard flake8 mechanism. There are two ways in which the behavior is exercised, and you must support both:

  1. As a flake8 plugin — running flake8 on a Python source file produces diagnostic output lines of the form:

    ./example.py:LINE:COL: CODE message

    where COL is 1-based.

  2. As a direct in-process check — a helper that runs the plugin on a source string and returns a list of tuples (line, col, "CODE message"), with line 1-based and col 0-based (that is, the 1-based column minus one). This is consistent with the plugin's internal reporting offsets: a diagnostic emitted at 1-based line L and 1-based column C is reported internally as (L, C-1, "CODE message").

The detection logic you are adding goes into the existing checker; these requirements introduce no new module or class names.

Behavior of LOG005

Message Text

The text of the diagnostic message is exactly:

LOG005 use exception() within an except clause
Detection Rule

LOG005 is emitted for a call to logging.error(...) (that is, an attribute call in which the object is the logging module and the attribute is error) when both of the following hold:
