Specification of the Task: Dependency Injection Library fast_depends

What you are implementing here is fast_depends, a Python library for dependency injection. It centers on a decorator that relies on Pydantic (v2) to validate and cast function arguments and return values, together with a Depends mechanism for declaring dependencies between callables.

The public API

Imports and names as listed below must be available in exactly the specified form.

fast_depends
  • inject — a decorator (usable as @inject) that wraps either a sync or an async function.
  • Depends — a callable for declaring a dependency; it is applied as a parameter default or inside Annotated metadata.
  • dependency_provider — an object with an override(original_callable, replacement_callable) method through which dependency callables are substituted.
fast_depends.core
  • build_call_model(func) — returns a "call model" object capturing the function's parameters and dependencies. Whatever object comes back must expose, at minimum, the properties real_params and flat_params described below.
fast_depends.library
  • CustomField — a base class on which user-defined parameter markers are based (see "Custom Fields").
fast_depends.types
  • AnyDict — a type alias that fits the annotation of **kwargs dictionaries.
Signature of Depends

Depends(dependency, *, cast: bool = True)

  • dependency: the callable that is to be resolved.
  • cast: a setting of False means the resolved value of that dependency is not type-cast (details below). True is the default.

How inject behaves

A function f is wrapped by @inject. The sync/async nature is preserved by the wrapper: an async function, once wrapped, gives an awaitable wrapper, while a sync function gives a sync wrapper.

The following takes place on a call of the wrapped function:

  1. Casting/validation of arguments. Every declared parameter is validated and coerced in line with its type annotation, under Pydantic v2 semantics. Examples:

    • Give a parameter annotated float the string "1", and a float comes out.
    • A parameter annotated int ends up an int once coercion has taken place.
    • When the annotation is a Pydantic BaseModel subtype and a dict comes in, a validated model instance is produced (the model's own fields are coerced in the process, e.g. a field annotated int receiving "31" becomes int).

  2. Parameters without annotations are not cast. Take a parameter that has no type annotation (e.g. default = Field(..., alias="b") with no annotation): the value coming in reaches it unchanged (e.g. a str stays a str).

  3. Support for Pydantic Field. Field(...) as a parameter default is honored — this covers alias (the aliased name is what the caller passes) and constraints such as max_length. When an incoming value does not match the constraint or the type, pydantic.ValidationError is raised.

  4. Extra keyword arguments are ignored. It is permitted to call the wrapped function with additional keyword arguments that correspond to no declared parameter, and no error results.

  5. Return-value casting. When the function carries a return annotation, the returned value is coerced to that type. Example: a function annotated -> float that returns an int-valued expression gives a float (so the integer result 6 becomes 6.0).

  6. Incoming types that are invalid — values that cannot be validated against the annotation — raise pydantic.ValidationError.

How Depends works

Resolution of a parameter happens by calling dep whenever the parameter's default is Depends(dep) or its annotation is Annotated[T, Depends(dep)]. The parameters of the dependency itself are resolved/injected recursively in turn (a dependency may have annotated parameters of its own, Fields, and nested Depends).

  • Result casting. The default is that the dependency's return value is cast according to the dependency's return annotation (e.g. a dep annotated -> float returning a yields a float). Should the depending parameter itself be annotated (e.g. c: int = Depends(dep) or Annotated[int, Depends(dep)]), the resolved value is coerced to that annotation.
  • cast=False. With Depends(dep, cast=False), the dependency's resolved value is not coerced.
  • Annotated form. Annotated[int, Depends(dep)] amounts to the same as Depends(dep) used as the default on a parameter typed int. Such a parameter may be supplied without a value provided by the caller.
  • Caching. Over the course of a single top-level call, each distinct dependency callable is resolved at most once; several parameters that depend on the same callable receive the identical resolved object (identity-equal). Nested dependencies shared across the graph are covered by this too.
  • Class dependencies. With Depends(SomeClass), the class is instantiated (its __init__ parameters are injected) and the instance is returned. For Depends(instance) where the instance is callable, resolution happens by calling the instance. Depends(instance.method) is resolved through a call to the bound (possibly async) method.
Rules for mixing sync and async
  • A sync wrapped function may not depend (directly or transitively) on an async dependency. Trying to build an injected function of that kind triggers AssertionError at decoration time (i.e. when @inject is applied).
  • Depending on both sync and async dependencies is something an async wrapped function may do.
Dependencies that yield (generators)

A dependency may also take the shape of a (sync) generator: it yields a value, and cleanup is performed after the yield:

  • The caller is provided with the value that was yielded.
  • Cleanup code positioned after the yield runs after the wrapped function body has completed (while the body executes, it must not have run).
  • Should the dependency raise before yielding, the exception propagates and the wrapped body is not run.
  • If it is the wrapped body that raises, the exception propagates; even in that case the expectation is that cleanup will run, but the exception is re-raised to the caller.

Overriding dependencies

dependency_provider.override(base_dep, override_dep) has the effect that every Depends(base_dep) is resolved with override_dep instead. At call time, the sync/async compatibility rules apply to the overriding callable:

  • When a sync dependency is overridden with an async callable and a sync wrapped function is then called, AssertionError is raised.
  • An async wrapped function may use an override of either a sync or an async callable.

Custom Fields (fast_depends.library.CustomField)

Custom parameter markers can be defined by users on top of the base class CustomField; such a marker is applied as a parameter default (key: int = Header()) or inside Annotated (Annotated[int, Header()]).

The constructor

CustomField(*, cast: bool = True, required: bool = True)

  • required (default True): when True and the field produces no value, validation fails (pydantic.ValidationError). Under False, a missing value resolves to None (and is not required).
  • cast (default True): False means the resolved value is not coerced to the parameter's annotation.
The use method

def use(self, **kwargs) -> dict — is handed the keyword-argument mapping in its current state and returns a (possibly modified) mapping. In subclass implementations, super().use(**kwargs) is called first, and values may then be injected/replaced keyed by the parameter's name.

self.param_name

After being bound to a parameter, each CustomField instance exposes self.param_name — the name of the parameter it decorates. Which key to populate is determined by subclasses from it.

Behavior that is required
  • The incoming call kwargs (e.g. a headers dict) are something a CustomField subclass may inspect, setting kwargs[self.param_name] to the extracted value. After use has run, that value is validated/cast against the parameter's annotation, as happens for any normal parameter.
    • Example: kwargs["headers"][param_name] is read by a Header field and assigned to kwargs[param_name]; with the annotation int, an incoming "1" becomes 1; with float, "1" becomes 1.0.
  • Multiple custom-field parameters within one function each populate their own param_name.
  • required=True (default) together with no produced value: pydantic.ValidationError is raised.
  • required=False together with no produced value: the parameter resolves to None.
  • Coercion for that parameter is disabled by cast=False (e.g. an annotation of float or logging.Logger leaves the incoming raw value untouched).
  • Custom fields work via Annotated[T, Field()] just as they do via defaults.
  • Custom fields also work on dependency functions: when dep uses a custom field, Depends(dep) is resolved correctly (the custom field consumes the same incoming kwargs, e.g. headers).
Async custom fields
  • use may be defined as an async method. An async custom field may only be used on async wrapped functions. When an async custom field is used on a sync wrapped function, AssertionError is raised at decoration time.
  • Both sync and async functions work with a sync custom field.

Properties of the call model (build_call_model)

The object that build_call_model(func) returns exposes:

  • real_params — a set[str] holding the names of parameters that func itself declares directly and that are plain parameters (i.e. not themselves Depends(...) markers). Any name bound to Depends is excluded.
  • flat_params — a set[str] formed from the union of real_params and the plain (non-Depends) parameter names that the entire transitive dependency graph requires. Names duplicated across dependencies collapse into a single entry.

Example: given

def func1(a): ...
def func2(c, b=Depends(func1)): ...
def func3(b): ...
def main(a, b, m=Depends(func2), k=Depends(func3), c=Depends(func1)): ...

the results are build_call_model(main).real_params == {"a", "b"} and .flat_params == {"a", "b", "c"}. (a, b are the plain params of main; the plain params contributed by the dependency graph are a from func1, c from func2, b from func3; {a, b, c} is the union of all plain names.)

Notes and non-requirements

  • The validation backend must be Pydantic v2.
  • Raising on non-existent/forward-reference string annotations is not required; do not add behavior of that kind.

Your task is to implement/modify a Python dependency injection library named fast_depends. What follows is the exact public API surface and behavior that is required.

Public API

These imports must work:

from fast_depends import Depends, inject
from fast_depends.library import CustomField

In addition, a call-model builder must be importable (in the way the tests use it):

from fast_depends import build_call_model   # or an equivalently importable path

(The builder build_call_model must be importable from every location where it is currently exposed; do not change its import location.)

The inject decorator

inject must be usable in two forms:

  1. Bare decorator form: @inject placed directly on a function.
  2. Parameterized form: @inject(...), which returns a decorator.

Both synchronous and asynchronous target functions must be supported.

New keyword argument: extra_dependencies

inject must accept a keyword-only argument extra_dependencies whose default is an empty collection. The value supplied is a sequence (e.g. a tuple) of Depends(...) objects.

Behavior:

  • Regardless of whether its return value is bound to any parameter of the wrapped function, every dependency in extra_dependencies must be invoked (called/resolved) each time the wrapped function is invoked. The return values of these dependencies are not passed into the wrapped function; they are executed purely for their side effects.
  • Resolution of the extra dependencies must happen before (or as part of) the invocation of the wrapped function, so that by the time the wrapped function's own body runs, their side effects have occurred.
  • Per call of the wrapped function, each extra dependency is executed exactly once.

Sync vs. async rules for extra_dependencies:

  • When the wrapped function is async, the extra dependencies may be either synchronous or asynchronous callables; both kinds must be resolved and awaited/called as appropriate.
  • When the wrapped function is synchronous, every extra dependency must be a synchronous callable. If any extra dependency is an asynchronous callable (coroutine function), then applying inject (at decoration time) must raise AssertionError.

Depends

Depends(dependency, *, ...) wraps a callable dependency. For dependency, you may pass:

  • a plain function (sync or async),
  • a callable class instance (an object having __call__), or
  • a bound method of an instance.

Sync vs. async rules for regular Depends parameters:

  • An async target function may depend on dependencies that are sync or async.
  • A synchronous target function must not depend on an asynchronous dependency. If a synchronous function decorated with @inject has a parameter whose default is Depends(async_callable), the decoration must raise AssertionError.

When Depends is passed a callable-class instance, invoking it resolves through the instance's __call__; a bound method may likewise be passed directly.

The call model (build_call_model)

Calling build_call_model(func) returns a model object describing the call signature. The following attributes must be exposed by this model object:

  • params: a mapping (dict-like, supporting .keys()) whose keys are the names of the parameters that the target function itself declares directly (that is, the parameters appearing in the function signature, with parameters contributed only by nested/flattened dependencies excluded).
  • flat_params: a mapping (dict-like, supporting .keys()) whose keys are the complete flattened set of parameter names, including the parameter names required by nested dependencies.

As an example, take a function main(a, b, c=Depends(dep)) in which dep itself requires the parameter c:

  • set(model.params.keys()) yields the function's own parameters, for example {"a", "b"}.
  • set(model.flat_params.keys()) yields the full set, including the names required by dependencies, for example {"a", "b", "c"}.

(Note: the mapping params described above replaces an attribute previously named real_params.)

CustomField (in fast_depends.library)

CustomField acts as a base class for defining custom parameter-injection fields. Subclasses provide their own override of a use method.

Contract for the use method:

  • The signature is def use(self, **kwargs) -> dict for synchronous fields, or async def use(self, **kwargs) -> dict for asynchronous fields.
  • use receives keyword arguments representing the current call context (including any headers mapping passed to the wrapped function) and returns a mapping of keyword arguments that may have been modified.
  • The base super().use(**kwargs) returns the kwargs mapping, which is then to be processed further by the subclass.

Constructing a CustomField must accept the following keyword options:

  • required (default True): when True, a pydantic.ValidationError must be raised at call time if the field's value cannot be resolved from context. When False, a value that cannot be resolved yields None for that parameter.
  • cast (default True): when True, the resolved value is coerced into the annotated type of the parameter (e.g. the string "1" given for an int-annotated parameter becomes 1, and for a float-annotated parameter it becomes 1.0). When False, the resolved value is passed through with no type coercion.

Once bound during injection, each CustomField instance exposes self.param_name, which is the name of the parameter to which it is bound.

Async/sync rules for custom fields:

  • An async-use custom field may be used together with an async wrapped function.
  • If an async-use custom field is used on a synchronous wrapped function, AssertionError must be raised at decoration time.

Example custom field behavior (Header-like): A field that looks up self.param_name within an incoming headers mapping and, if the name is present, sets the parameter's value from headers[param_name], with the required/cast rules above then applying.

Compatibility

All of the code must be compatible with Python 3.7+. Do not depend on type names that are unavailable in the supported versions; the parameter/return annotations for use overrides are standard typing constructs (e.g. Callable[..., Any]) rather than any custom AnyDict alias.

Summary of the behaviors that must hold

  1. Both @inject and @inject(extra_dependencies=(...)) work for sync and async functions.
  2. For their side effects, extra dependencies run once per call; sync functions reject async extra dependencies (AssertionError at decoration).
  3. Async Depends parameters are rejected by sync functions (AssertionError at decoration).
  4. Plain functions, callable class instances, and bound methods are supported by Depends.
  5. Custom fields support required and cast; required fields that go unresolved raise pydantic.ValidationError; async-use fields on sync functions raise AssertionError.
  6. The call model exposes params and flat_params as mappings bearing keys, as specified.

The imports below must succeed:

from fast_depends import Depends

from fast_depends.core import build_call_model
fast_depends.library.CustomField

There must be a class named CustomField importable from fast_depends.library, and it must be constructible with no arguments:

field = CustomField()

If the default value of a callable parameter is an instance of CustomField, that parameter is a custom-field parameter. It is neither an ordinary user-supplied parameter nor a dependency parameter. Instances of CustomField subclasses receive the same treatment.

Depends

Depends(callable) may be placed as a parameter default; doing so marks that parameter as a dependency whose value is resolved by calling callable.

build_call_model(func)

build_call_model(func) analyzes func, and it also recursively analyzes the callables referenced by Depends(...) parameters. The call model it returns exposes at least the two mapping attributes described below.

How Parameters Are Categorized

Parameters of each analyzed callable are classified according to their default values:

  • Plain parameters: parameters that do not have a Depends default and do not have a CustomField default. This includes ordinary required parameters and ordinary parameters with non-special defaults.
  • Dependency parameters: parameters with a Depends(...) marker as their default.
  • Custom-field parameters: parameters carrying a CustomField instance as their default.

These classification rules apply independently both to the top-level callable and to every dependency callable reached recursively.

Required Behavior of the Call Model

model.real_params

real_params must be a mapping. Its keys are exactly the names of the plain parameters that the callable represented by that model declares directly.

For the top-level model, this means:

  • the top-level callable's own plain parameter names are included;
  • all of its dependency parameter names are excluded; and
  • all of its custom-field parameter names are excluded.

Parameters declared by dependency callables are not included in the top-level model's real_params.

model.flat_params

flat_params must be a mapping that holds the plain parameters of the complete Depends dependency graph, flattened recursively. Put equivalently, for any call model:

  1. Start from that model's real_params keys.
  2. For every direct Depends dependency, recursively add the keys of that dependency model's flat_params.

It follows that the top-level flat_params keys are the union of:

  • plain parameter names declared directly by the target callable; and
  • plain parameter names declared by every dependency callable reachable transitively through Depends.

At every depth of the dependency graph, these exclusions apply:

  • A dependency-parameter occurrence does not contribute that dependency parameter's own name.
  • A custom-field parameter's name is not contributed to flat_params, whether the custom field is declared on the top-level callable or on any direct or transitive dependency callable.

What gets excluded depends on each parameter occurrence's category, not on the spelling of its name. Consequently, a name excluded from one callable because it is a dependency slot there may still appear in flat_params if another reachable callable declares a plain parameter with that same name. Since these attributes are mappings, a name contributed more than once appears as a single key.

What is specified here is only the key membership of real_params and flat_params; nothing particular is required about the mapping value type or the key order.

Example Walkthrough

def func1(m):
    ...

def func2(c, b=Depends(func1), d=CustomField()):
    ...

def func3(b):
    ...

def main(a, b, m=Depends(func2), k=Depends(func3)):
    ...

model = build_call_model(main)

main's direct plain parameters are a and b, and therefore:

set(model.real_params.keys()) == {"a", "b"}

Flattening then gives:

  • a and b from main;
  • c from func2;
  • m from func1, which is reached via func2's dependency parameter b; and
  • b from func3, which is already present as a mapping key.

The occurrences of the dependency-slot names main.m, main.k, and func2.b contribute nothing. Even so, the name m appears, because func1.m is a plain parameter. The custom-field parameter func2.d is left out of the flattened mapping. Hence:

set(model.flat_params.keys()) == {"a", "b", "c", "m"}

In particular, d must not be present in flat_params.

Compatibility

The required public API and call-model behavior must work under both Pydantic v1 and Pydantic v2.

Task Specification: Variadic Argument Support in Dependency Injection

Overview

You will be extending a library for dependency injection and type casting that offers an inject decorator. This decorator takes a function (synchronous or asynchronous) and wraps it so that its arguments are validated and cast to the types declared in the function's signature annotations, based on pydantic. Your job is to add correct support for variadic positional (*args) and variadic keyword (**kwargs) parameters, alongside keyword-only parameters.

Public API

The following import paths must exist and behave as described:

  • from fast_depends import inject — a decorator that can be applied to both regular (def) and coroutine (async def) functions. When the target is an async function, the wrapped callable must remain awaitable; when the target is a sync function, the wrapped callable must be called normally.
  • from fast_depends import Depends
  • from fast_depends.library import CustomField
  • from fast_depends.core import build_call_model

(The Depends, CustomField, and build_call_model names must merely be importable from those paths; only their existence is required here.)

Behavior to Be Implemented

The inject decorator must correctly handle function signatures that contain *args and/or **kwargs, plus keyword-only parameters, on top of the ordinary positional/keyword parameters that are already supported.

For all parameters, arguments supplied at call time must be cast to the type declared in the annotation before they are delivered to the underlying function. The return value must be exactly what the underlying function returns (a tuple in the cases below, because the functions return their parameters).

1. Complete variadic support (*args and **kwargs)

Consider a function declared like:

def f(a: int, *args: Tuple[float, ...], b: int, **kwargs: Dict[str, int]):
    return a, args, b, kwargs
  • The value supplied for the regular parameter a is cast to the annotated type: passing 1.0 yields 1 (int).
  • Positional arguments left over after the declared regular parameters are collected into args. Each of these values is cast to the element type declared for the variadic positional parameter (here float). Passing positional values 2.0, 3 gives args == (2.0, 3.0) (all floats). The result of this collection is a tuple, with order preserved.
  • The value supplied for the keyword-only parameter b is cast to the annotated type: passing b=3.0 yields b == 3 (int).
  • Keyword arguments that do not match any declared parameter are collected into kwargs. Each of these values is cast to the value type declared for the variadic keyword parameter (here int). Passing key=1.0 gives kwargs == {"key": 1} (int value). The result of this collection is a dict, with keys preserved.

In concrete terms, calling the wrapped function with positional args 1.0, 2.0, 3 and keyword args b=3.0, key=1.0 must return (1, (2.0, 3.0), 3, {"key": 1}).

2. Variadic positional support only (*args, no **kwargs)

With a function declared like:

def f(a: int, *args: Tuple[float, ...], b: int):
    return a, args, b

When the function is called with positional args 1.0, 2.0, 3 and keyword arg b=3.0, it must return (1, (2.0, 3.0), 3) — a is cast to int, the surplus positional values are cast to float and gathered into a tuple, and b is cast to int.

3. Keyword-only parameter without variadic collection

Take a function declared like:

def f(a: int, *, b: int):
    return a, b

In this case there is no *args collection. The first positional argument fills a; any positional arguments after that are simply discarded (not collected, because no variadic positional parameter exists). The keyword-only parameter b takes its value from the keyword argument.

When the function is called with positional args 1.0, 4 and keyword arg b=3.0, it must return (1, 3) — a is cast to int from 1.0, the additional positional 4 is ignored, and b is cast to int from 3.0.

Notes on Type Casting

  • Casting adheres to pydantic semantics for the annotated types.
  • For variadic positional parameters, each collected value is cast according to the annotation's element type.
  • For variadic keyword parameters, each collected value is cast according to the annotation's value type.
  • All casting behavior for ordinary and annotated parameters that was supported previously must continue working unchanged.

Sync and Async Compatibility

Both the synchronous and the asynchronous forms of inject must display identical casting and collection behavior in all the cases above.
