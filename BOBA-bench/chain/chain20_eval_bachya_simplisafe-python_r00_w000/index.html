Async SimpliSafe Python Library — Task Specification

High-Level Overview

Build simplipy, a Python library that is asyncio-based, for working with the SimpliSafe™ home security REST API (https://api.simplisafe.com). Its job is to authenticate a user, discover the security systems that belong to that user, expose the state of systems and sensors, permit the armed state to be changed, and fetch the event history. Both "v2" and "v3" generations of SimpliSafe hardware must be supported; the two generations use different API endpoints and payload shapes.

All network communication happens through an aiohttp.ClientSession that the caller supplies.

Public API

Package simplipy (simplipy/__init__.py)
async def get_systems(email: str, password: str, websession) -> list
  • The user is authenticated, using the email and password that are given together with the aiohttp client session that is provided.
  • All security systems attached to the account are discovered, and they are returned as a list of System objects (see below).
  • The authentication flow goes through these steps, in order:
    1. POST /v1/api/token — an access token, a refresh token, and an expiration are obtained.
    2. GET /v1/api/authCheck — the userId of the authenticated user is obtained.
    3. GET /v1/users/{userId}/subscriptions — the list of subscriptions/systems is obtained.
  • The full system data (settings/sensors) must then be loaded by the library for each system that is returned; see Discovery and update of systems below.

  • version → the hardware version as an integer (from system['version']; 2 or 3).

Details of the Data Model

Discovery and update of systems

A subscriptions list is found in the response of GET /v1/users/{userId}/subscriptions. Each subscription includes:

  • sid → the system id / subscription id.
  • location.system → the block with the system info, which contains serial, alarmState, isAlarming, version, etc. alarmState may be in uppercase and must be interpreted case-insensitively, as described above.

Which generation applies is decided by the value of location.system.version:

v2 systems (version == 2):

  • The sensor/settings data is obtained by fetching GET /v1/subscriptions/{subscription_id}/settings.
  • settings.sensors appears in the response — a list of sensor objects. Some entries of this list are empty objects ({}), and these must be ignored (they are not counted, and they are not turned into Sensor objects). With the reference v2 data, the resulting sensors mapping contains exactly 34 sensors.
  • The keys found on each v2 sensor object are: type, serial, setting, sensorStatus, sensorData, name, error, and, optionally, battery, entryStatus.
  • Deriving the v2 sensor properties:
    • settings = setting (int).
    • data = sensorData (int).
    • error = error (bool).
    • low_battery, triggered are derived from the sensor's status fields; for the sensor whose serial is '195', all of error, low_battery, triggered are False, with settings == 1 and data == 0.

v3 systems (version == 3):

  • The sensor data is obtained by fetching GET /v1/ss3/subscriptions/{subscription_id}/sensors.
  • A sensors list appears in the response. With the reference v3 data, the resulting sensors mapping contains exactly 21 sensors.
  • The keys found on each v3 sensor object are: type, serial, name, setting (a dict), status (a dict), flags (a dict with swingerShutdown, lowBattery, offline).
  • Deriving the v3 sensor properties:
    • settings = the setting dict.
    • error is derived from status/flags; for the entry sensor with serial '825', the value is False.
    • low_battery = flags.lowBattery.
    • offline = flags.offline.
    • triggered = status.triggered when that key is present. Serial '825' (status.triggered == False) yields False; the siren with serial '236' (its status is empty) likewise yields False.
    • temperature = status.temperature for temperature sensors (e.g. serial '320' → 67). Sensors that are not temperature sensors raise ValueError on access.
Changing the state — endpoints and response handling

v2 (set_away/set_home/set_off):

  • A POST /v1/subscriptions/{subscription_id}/state request is issued (the state that is targeted is conveyed as a request parameter, not as part of the path).
  • The response contains success: true and requestedState: <away|home|off>; the system's state is updated to the SystemStates member that corresponds.

v3 (set_away/set_home/set_off):

  • A POST /v1/ss3/subscriptions/{subscription_id}/state/{state_name} request is issued; here {state_name} is the .name of the SystemStates member being targeted (away, home, or off).
  • The response contains success: true and state: <AWAY|HOME|OFF>; the system's state is updated to the SystemStates member that corresponds.
Events

The response to GET /v1/subscriptions/{system_id}/events contains:

  • numEvents → an integer;
  • lastEventTimestamp → an integer; and
  • events → an array of event objects.

What get_events(timestamp, num_events) returns is the list found under the events key.

Token and expiration behavior

  • After the initial authentication inside get_systems, the access token counts as valid; calls to request(...) succeed.
  • If account._access_token_expire is set to a time in the past, the next request(...) raises TokenExpiredError before any HTTP call is made.

Logging

The standard logging module is what must be used. Log records must be emitted for both unknown alarm states and unknown sensor types, and each such record's message must contain the substring Unknown.

Constants / reference values for the API paths

  • Host of the base API: api.simplisafe.com, with all endpoints under /v1/.
  • Subscriptions of the user: /v1/users/{user_id}/subscriptions.
  • Settings for v2: /v1/subscriptions/{subscription_id}/settings.
  • Events for v2: /v1/subscriptions/{system_id}/events.
  • State for v2: /v1/subscriptions/{subscription_id}/state.
  • Sensors for v3: /v1/ss3/subscriptions/{subscription_id}/sensors.
  • State for v3: /v1/ss3/subscriptions/{subscription_id}/state/{state_name}.
  • Token: /v1/api/token; auth check: /v1/api/authCheck.

In the reference data, the subscription id, the system id, the account id, and the user id all equal 12345; the system serial is 1234ABCD.

Behavior Requirements

The Token Endpoint

Refreshing the token is done by way of a POST to https://api.simplisafe.com/v1/api/token. If the response is a successful one (HTTP 200), its JSON contains the new credentials, a new refresh token among them. Once a refresh has succeeded, an auth-check GET to https://api.simplisafe.com/v1/api/authCheck may then follow, as part of establishing the refreshed session.

401 during the Initial Login

Should the token POST in login_via_credentials — that is, the initial credential login — itself return HTTP 401, InvalidCredentialsError is raised. In this case, no retry attempt is made.

401 during an Authenticated Request — Retry Logic

Take the case of any authenticated request — for example the fetching of subscriptions during get_systems() / system.update() — that receives an HTTP 401 response:

  1. The first 401 does not result in an immediate failure. Instead, an attempt to refresh the access token is made, via a token-refresh POST to /v1/api/token.

  2. The overall operation then completes normally, using the successful response of the retried request. Success, rather than an error, is what the caller observes.

  3. If the refresh itself returns 401 (an unsuccessful refresh): InvalidCredentialsError is raised. The INFO level is where logging must occur (i.e., the record is visible when the logger has been configured for INFO).

refresh_token_dirty is a boolean that signals two things: since it was last read, the refresh token has been updated (rotated), and the new value has yet to be consumed by the consumer:

  • The stored refresh token gets replaced by a successful automatic token refresh; immediately after that, refresh_token_dirty evaluates to True.
  • A read of the refresh_token property is what consumes/acknowledges the new value: refresh_token_dirty evaluates to False after refresh_token has been read.

To make this concrete, here is the sequence that must hold once a 401 has triggered a successful automatic refresh:

  1. The value of refresh_token_dirty is True.
  2. A read of refresh_token returns the refresh token value that was newly issued.
  3. refresh_token_dirty is False immediately after that read.

Summary of the Request Flow for a Successful Recovery

  1. A 401 is returned by an authenticated GET.
  2. The client carries out a token-refresh POST → 200 with new credentials.
  3. The client carries out an auth-check GET → 200.
  4. The original authenticated request is retried by the client → 200.
  5. The operation returns successfully; the refresh token has been rotated, and the dirty flag remains set until read.

Notes

  • Beyond a single refresh attempt per initial 401, do not add retry behavior.
  • The authenticated data requests made in the course of fulfilling get_systems() and system.update() are covered by this behavior uniformly.

  • The reserved label "master" comes from the entry keyed "pin1" — an entry that has no name field.
  • The reserved label "duress" comes from the entry keyed "duress".

/v1/ss3/subscriptions/<SUBSCRIPTION_ID>/settings/pins
