01 You are working on hassil, a Python library for matching natural-language sentences against intent templates. 518 words · source specification

You are working on hassil, a Python library for matching natural-language sentences against intent templates. Implement the changes described below.

Public API Surface

parse_sentence importable from package root

The function parse_sentence must be importable directly from the top-level package:

from hassil import parse_sentence

It must remain importable from hassil.parse as well (existing location). Both import paths must refer to the same callable. It takes a template string and returns a parsed sentence object usable by the matching and sampling functions.

recognize — new ignore_whitespace parameter

The recognize function (importable as it currently is) must accept a new optional keyword argument:

recognize(text, intents, ..., ignore_whitespace=False)
  • ignore_whitespace defaults to False, preserving all existing behavior.
  • When ignore_whitespace=True, all whitespace is treated as insignificant during matching. That is, whitespace present in the input text and whitespace implied between template tokens is ignored when determining whether the input matches a template.

Concretely, with ignore_whitespace=True, a template such as run [the] test (where [the] is an optional word) must successfully match all of the following inputs:

  • "runtest" (no spaces, optional word absent)
  • "runthetest" (no spaces, optional word present)
  • "r u n t h e t e s t" (arbitrary spaces inserted between every character)

In each of these cases, recognize must return a non-None result.

Behavior That Must Continue to Work

Whitespace normalization in alternatives (default matching)

Alternative groups written with irregular internal whitespace must still match correctly under normal (default) matching. For example, the template:

set brightness to ( minimum | lowest)

— note the leading space after ( and around the | — must match the input "set brightness to lowest".

Existing recognition behavior

Entity-text and number-text recognition must continue to work as before. For example:

  • A template capturing a {name} entity mapped to value "A" from text alpha must, for inputs like "run test alpha now", "run test alpha", and "alpha test", produce a result whose name entity has value "A" and whose captured text stripped of surrounding whitespace equals "alpha".
  • A template capturing a {percentage} entity for 50% must, for inputs like "set 50% now", "set 50%", and "50% set", produce a result whose percentage entity has value 50 and stripped captured text "50%".

Sentence Sampling — Nested Optionals

The function sample_expression (importable as it currently is) generates all possible concrete sentences a template can match. It must correctly enumerate templates containing multiple/adjacent optional segments.

For the template:

turn [on] [the] light[s]

sample_expression(parse_sentence(...)) must yield exactly the following set of strings (each optional segment independently present or absent):

  • "turn light"
  • "turn lights"
  • "turn on light"
  • "turn on lights"
  • "turn the light"
  • "turn the lights"
  • "turn on the light"
  • "turn on the lights"

Whitespace in the produced strings must be single-spaced and correctly collapsed where optional words are omitted (no doubled or trailing spaces).

Existing single-optional and alternative sampling behavior must be preserved (e.g., turn [on] the light and this is (the | a) test enumerate as expected).

Task Specification: Add settings Block Support to Intents YAML

Objective

Extend the intents YAML parsing so that a top-level settings block can specify parsing/matching options. Specifically, a settings block may declare ignore_whitespace, and when set, whitespace is ignored during sentence recognition without needing to pass the option explicitly to the recognition call.

Required Behavior

YAML settings block

The intents YAML document may contain an optional top-level settings mapping alongside the existing language and intents keys. Within settings, the key ignore_whitespace (boolean) may be provided.

Example structure:

language: "en"
settings:
  ignore_whitespace: true
intents:
  TestIntent1:
    data:
      - sentences:
          - "run [the] test"

When settings.ignore_whitespace is true, the parsed Intents object must carry this setting so that subsequent recognition ignores whitespace.

Recognition using the setting

When an Intents object was loaded from YAML whose settings block declared ignore_whitespace: true, calling recognize(sentence, intents) — without passing ignore_whitespace — must behave as if whitespace-insensitive matching were requested.

Concretely, given intents defining a sentence pattern such as "run [the] test", the following input sentences must all successfully match (return a non-None result) when the loaded intents carry ignore_whitespace: true in their settings:

  • "runtest"
  • "runthetest"
  • "r u n t h e t e s t"

Public API Surface

  • Intents.from_yaml(file) — classmethod that parses the YAML (file object / path as already supported) and returns an Intents instance. It must now also read the optional top-level settings block, including ignore_whitespace, and store it on the returned object.
  • recognize(sentence, intents) — module-level function. It must honor the ignore_whitespace setting stored on the given intents object when no explicit ignore_whitespace argument is supplied, and return None on no match or a truthy result object on a match.

The ignore_whitespace keyword argument to recognize remains available; the new behavior is that the setting from the YAML settings block takes effect when the argument is not explicitly provided.

03 You are working on a sentence-matching library (Hassil-style intent recognition) that parses template sentences and matches them against input text. 506 words · source specification

Overview

You are working on a sentence-matching library (Hassil-style intent recognition) that parses template sentences and matches them against input text. Two behaviors need to be corrected/implemented related to (1) how grouped/alternative word fragments are treated, and (2) how "skip words" interact with whitespace-ignoring matching.

Public API Surface

The following must be importable and callable as described:

  • parse_sentence(text: str) — parses a template string into a sentence object (as already used in the library).
  • is_match(text: str, sentence, *, expansion_rules=None, slot_lists=None) -> bool — returns whether text matches the parsed sentence. (Existing signature; expansion_rules and slot_lists are keyword arguments as already supported.)
  • recognize(text: str, intents) -> Optional[...] — matches input text against a collection of intents, returning a truthy result on success or None on failure.
  • Intents.from_yaml(file) — constructs an Intents collection from a YAML stream.

Required Behavior

1. Whitespace is significant by default

When ignore_whitespace is not enabled, template matching must require whitespace boundaries to be present in the input where the template has them. Concretely, a template consisting of distinct space-separated words must NOT match an input string that has all whitespace removed.

  • Given a template parsed from "this is a test", the input "thisisatest" must NOT match.
2. Grouped alternatives and optional groups may adjoin surrounding characters without internal whitespace

Template parsing must correctly handle alternative groups ( ... | ... ) and optional groups [ ... ] whose delimiters directly abut adjacent text and whose alternatives are separated by | without surrounding spaces.

  • A template parsed from "give me the penn(y|ies)" must match both "give me the penny" and "give me the pennies". The group attaches directly to the preceding penn with no intervening whitespace, and the alternatives y and ies are separated by | with no surrounding spaces.

  • Optional groups may include a trailing space inside the brackets to represent optional whitespace. A template parsed from "[the ]kitchen" must match both "the kitchen" and "kitchen". When used as an expansion rule (e.g. bound to a rule named area) and referenced from a larger template, matching must succeed accordingly — for example, a rule area = "[the ]kitchen" used within a prefix/suffix template must allow input where the optional the is absent (e.g. matching "abc-kitchen-123").

3. Skip words combined with ignore_whitespace

When an Intents collection is configured with ignore_whitespace: true and declares one or more skip_words, recognition must ignore those skip words even when they appear adjacent to matched content without whitespace separation.

  • Given intents configured with ignore_whitespace: true, a single intent whose sentence is "ad", and a skip word "bc", the input "abcd" must be recognized successfully (the skip word bc is skipped, leaving ad to match). recognize("abcd", intents) must return a non-None result.

Notes

  • Existing matching behavior for other constructs (optional plurals, expansion rules, slot lists, and whitespace-ignoring recognition without skip words) must remain intact.
  • The ignore_whitespace setting continues to allow matching regardless of whitespace differences in input when enabled.

Template Syntax (as exercised)

The parser must support these constructs within a template string:

  • Optional groups: [ ... ] — the enclosed content may be present or absent.
  • Alternatives: ( a | b | c ) — exactly one of the listed alternatives.
  • Expansion rule references: <name> — replaced by the parsed sentence associated with name in the expansion_rules mapping.
  • Slot list references: {name} — matched against the values in the slot_lists mapping under name.
  • Optional whitespace: [ ] — an optional single space. This must match both when a space is present between the surrounding tokens and when no space is present (i.e., the surrounding tokens are directly adjacent / run together).

  • Input where the two parts are separated by a space (e.g. "... de keuken de lampen ...").
  • Input where the two parts are joined with no separating space (e.g. "... de keukenlampen ...").

Matching must be case-insensitive with respect to the literal words and slot-list values (input text in mixed/upper case must match lowercase template words and capitalized slot-list values).

    • area → "[de|het] {area}"
    • doe → "(zet|mag|mogen|doe|verander|maak|schakel)"
    • lamp → "[de|het] (lamp[en]|licht[en]|verlichting)"

both of these input strings must match:

  • "Mogen in de keuken de lampen aan?"
  • "Mogen in de keukenlampen aan?"

Trailing punctuation such as ? in the input must not prevent a match, and unmatched trailing optional groups (e.g. the final [willen | kunnen] and [<doe>]) must be allowed to be absent.

Scope

Do not change the public API names or signatures. The task is to ensure optional-whitespace tokens correctly permit both "space present" and "space absent" matches when situated between references that expand to further tokens, while continuing to support optional groups, alternatives, expansion rules, and literal (non-template) slot lists as described above.

07 Add Permutation Support to Sentence Template Grouping 707 words · source specification

Task Specification: Add Permutation Support to Sentence Template Grouping

Overview

The codebase parses sentence templates into an expression tree, then matches input text against those templates. You must add support for a new grouping construct — a permutation group — that allows the items in a group to match in any order.

Background: Existing Grouping Constructs

The template parser already supports two grouping delimiters inside parentheses:

  • Sequence groups: items separated by nothing/implicitly are matched in order. e.g. (a b).
  • Alternative groups: items separated by | match any one of the alternatives. e.g. (a|b).

You must add a third:

  • Permutation groups: items separated by ; (semicolon) that match in any order.

Required Behavior

1. Parsing a permutation group

When a parenthesized group contains items separated by the ; (semicolon) delimiter, the parser must produce an expression that represents matching those items in every possible order (all permutations).

The parsing entry points are the existing functions used to turn template text into expressions. Specifically:

  • parse_expression(next_chunk("(test; test2)")) (from the expression parsing module — the same module that exposes parse_expression, next_chunk, ListReference, and the expression node types) must produce an alternative expression whose alternatives are the two orderings of the two segments.

Concretely, for the input (test; test2):

  • The group is split on ; into two segments. The text before the ; is "test"; the text after is " test2" (note: leading whitespace after the semicolon is preserved as part of the segment text — do NOT strip it).
  • Each segment becomes a sequence group wrapping its parsed text (a text/word node).
  • The result is an alternative whose items are one sequence group per permutation. Each permutation is itself a sequence group whose items are the per-segment sequence groups arranged in that permutation's order.

For two segments A (= sequence group containing text "test") and B (= sequence group containing text " test2"), the produced structure is exactly:

alternative(
    items=[
        sequence_group(items=[A, B]),
        sequence_group(items=[B, A]),
    ]
)

where:

  • A = sequence_group(items=[text_node(text="test")])
  • B = sequence_group(items=[text_node(text=" test2")])

The ordering of the permutations in the alternative's items list must be: the identity order first ([A, B]), then the swapped order ([B, A]).

Use the existing expression node constructors/types already present in that module: the alternative node (constructed as in the existing alternative-group handling), the sequence-group node (the standard group node), and the text/word node used for literal text. The text fields must contain exactly the substrings described above, including the preserved leading space in the second segment.

2. Matching a permutation group

When a full sentence template containing a permutation group is parsed with parse_sentence(...) (the existing sentence-parsing function in its current module) and matched against input text with is_match(...) (the existing matching helper), the input must be considered a match if it corresponds to any ordering of the permutation group's segments.

For the template "( in the kitchen ; is there smoke )":

  • The input " in the kitchen is there smoke " must match (segments in their written order).
  • The input " is there smoke in the kitchen " must match (segments in the reversed order).

Whitespace inside and around the segments must be handled consistently with existing matching behavior, such that both orderings above match the given inputs.

Constraints

  • Do not alter the behavior of existing sequence groups or alternative groups.
  • The semicolon ; is the delimiter that triggers permutation grouping within a parenthesized group.
  • Segment text is preserved verbatim between delimiters (no trimming of leading/trailing whitespace within a segment).
  • The permutation expansion enumerates all orderings of the group's segments; for N segments this yields N! orderings as the alternatives.

Public API Surface (must remain importable and callable)

All names below already exist except where new behavior is added to them; no new public functions or classes are required — the new behavior is expressed through the existing API:

  • Expression parsing module: parse_expression(chunk), next_chunk(text), ListReference, the alternative node type, the sequence/group node type, and the text/word node type.
  • Sentence module: parse_sentence(text).
  • Matching helper: is_match(text, sentence).

The only functional change is that these functions must now correctly handle the ; permutation delimiter as described above.

Overview

You must extend the hassil intent recognition library to support unmatched entities — a mechanism that allows a sentence to be recognized even when some of its entity slots cannot be resolved against the configured slot lists (either text lists or numeric ranges). This behavior must be opt-in via a new parameter.

Public API Surface

New classes in hassil.recognize

Two new public classes must be importable from the hassil.recognize module:

  1. UnmatchedTextEntity

    • Represents a named entity slot whose captured text could not be matched to any value in the corresponding text slot list.
    • Must be constructible positionally as UnmatchedTextEntity(name, text) where:
      • name (str): the entity/slot name.
      • text (str): the raw captured text for that slot.
    • Two instances must compare equal when their name and text are equal.

  2. UnmatchedRangeEntity

    • Represents a named entity slot whose captured numeric value falls outside the configured numeric range list.
    • Must be constructible as UnmatchedRangeEntity(name, value=...) where:
      • name (str): the entity/slot name.
      • value (int): the captured numeric value.
    • Two instances must compare equal when their name and value are equal.
Modified function: recognize

The existing hassil.recognize (also re-exported from the top-level hassil package) must accept a new keyword parameter:

recognize(sentence, intents, ..., allow_unmatched_entities: bool = False)
  • Default value is False, preserving the current behavior.
  • When False: a sentence that contains entity slots which cannot be resolved must not match (the function returns None).
  • When True: unresolved entity slots do not cause matching to fail; instead each unresolved slot is captured as an unmatched entity, and the sentence is still recognized (the function returns a non-None result).
Result object

The object returned by recognize must expose an attribute:

  • unmatched_entities: a mapping (dict) from entity/slot name (str) to the corresponding unmatched-entity object (UnmatchedTextEntity or UnmatchedRangeEntity).
    • When no entities are unmatched, this mapping is empty.

Required Behavior

Given a sentence template that contains multiple entity slots, where:

  • One or more text slots reference a text slot list, and the corresponding text in the input sentence does not match any value in that list.
  • A range slot references a numeric range list (with a configured minimum and maximum), and the numeric value in the input sentence falls outside that inclusive range.

Then:

  • With allow_unmatched_entities=False, recognition of that sentence returns None.
  • With allow_unmatched_entities=True, recognition returns a result whose unmatched_entities mapping contains exactly one entry per unresolved slot:
    • Each unresolved text slot maps to an UnmatchedTextEntity whose name is the slot name and whose text is the exact substring captured for that slot from the input sentence. This captured text corresponds to the portion of the sentence that filled the slot, including any trailing whitespace that separates it from the following literal text in the template.
    • Each unresolved range slot maps to an UnmatchedRangeEntity whose name is the slot name and whose value is the integer parsed from the input for that slot.
Concrete example

A template like:

set [all] {domain} in {area} to {percent}% now

with slot lists:

  • area = ["living room", "bedroom"]
  • domain = ["lights"]
  • percent = numeric range from 0 to 100

Recognizing the input:

set fans in living room to 101% now
  • With allow_unmatched_entities=False: returns None (fans is not a valid domain, and 101 is out of range).
  • With allow_unmatched_entities=True: returns a result with:
    unmatched_entities == {
    "domain": UnmatchedTextEntity("domain", "fans "),
    "area":   UnmatchedTextEntity("area", "living room "),
    "percent": UnmatchedRangeEntity("percent", value=101),
}

Overview

Add support for a new grammar construct called a permutation to the sentence expression parser. A permutation groups two or more items and matches when those items appear in any order in the input text.

Syntax

A permutation is written using parentheses with items separated by semicolons (;):

(item1; item2)
(A; B; C)

This is distinct from the existing alternative construct, which uses the pipe (|) separator inside parentheses and matches exactly one of its items.

Required Behavior

When the parser encounters a parenthesized group whose top-level items are separated by semicolons, it must produce an expression that matches any ordering of those items.

Expansion Model

A permutation of N items must be represented as an alternative (the same alternative construct produced for |-separated groups) containing one group per possible ordering of the items — i.e., every permutation of the N items, in order. For 2 items there are 2 orderings; for 3 items there are 6 orderings.

Whitespace Insertion

Because permutations are intended for reordering whole words/phrases, each ordering must include a single literal space text chunk (" ") before the first item, between every pair of adjacent items, and after the last item.

Concretely, for an input like (test; test2), each ordering-group must be structured as an ordered sequence of:

  1. a text chunk containing a single space " ",
  2. the first item's parsed group,
  3. a text chunk containing a single space " ",
  4. the second item's parsed group,
  5. a text chunk containing a single space " ".

Each individual permutation item is parsed as its own group. Note that the raw text of items following the separator retains its leading whitespace exactly as written in the source (e.g., in (test; test2) the second item parses to text " test2" while the first is "test").

Resulting Structure Example

For the input (test; test2), the parsed expression must equal an alternative whose items are:

  • Ordering 1 — a group containing, in order: text " ", group[text "test"], text " ", group[text " test2"], text " ".
  • Ordering 2 — a group containing, in order: text " ", group[text " test2"], text " ", group[text "test"], text " ".

A sentence containing a permutation must match input where the permutation's items appear in any order (with the surrounding/interleaving whitespace accounted for by the inserted spaces). For example, a sentence built from (in the kitchen; is there smoke) must match both:

  • in the kitchen is there smoke
  • is there smoke in the kitchen

  • parse_sentence(text) — parses a full sentence string into a matchable sentence expression.
  • The expression constructors already available for building/comparing expression trees:
    • text chunk (TextChunk, referred to as t(text=...) where text is the literal string),

    • alternative (alt(items=[...])).
  • is_match(text, sentence) — returns whether the given input text matches the given parsed sentence.

  • If the sentence's slot text does not match a real slot-list value, then both the slot name (with text equal to the captured fragment) and the missing required-context key (with text == MISSING_ENTITY) appear in unmatched_entities.

Concrete Example

Given these intents:

language: "en"
intents:
  Test:
    data:
      - sentences:
          - "open {name}"
        requires_context:
          domain: cover
lists:
  name:
    values:
      - garage door
  • recognize("open garage door", intents, allow_unmatched_entities=False) → returns None.
  • recognize("open garage door", intents, allow_unmatched_entities=True) → returns a result whose unmatched_entities keys are exactly {"domain"}; the "domain" entry is an UnmatchedTextEntity with text == MISSING_ENTITY.
  • recognize("open back door", intents, allow_unmatched_entities=True) → returns a result whose unmatched_entities keys are exactly {"domain", "name"}. The "domain" entry is an UnmatchedTextEntity with text == MISSING_ENTITY; the "name" entry is an UnmatchedTextEntity with text == "back door".

Constraints

  • Do not alter existing behavior for sentences that fully match, or for existing unmatched-text/unmatched-range handling.
  • The unmatched_entities dictionary must contain entries only for entities that are genuinely unmatched or missing; do not add empty or spurious entries.

Overview

You are modifying an intent recognition library that matches natural-language sentences against a set of intents defined in YAML. Sentences may contain slot references that map to named lists. This task concerns how entity keys are named when slot references use a slot alias and how unmatched entities behave.

Background: Slot Reference Syntax

In sentence templates, a slot reference can take two forms:

  • {list_name} — references a list directly; the entity key is the list name.
  • {list_name:slot_name} — references a list but assigns it an alias (slot name); the entity key must be the slot name, not the list name.

Required Behavior

1. Slot name used for matched wildcard entities

When a sentence template contains a slot reference of the form {list_name:slot_name} and that list is a wildcard list, a successful match must record the resulting entity under the key slot_name (the alias), not under list_name.

The captured entity's value must be the matched span of text from the input sentence.

Example: given a template run {script_name:name} where script_name is a wildcard list, the input run script 1 must match and produce a single entity keyed name whose value is script 1.

2. Slot name used for unmatched entities

When recognition is performed with unmatched entities allowed, and a slot reference of the form {list_name:slot_name} fails to match its list constraints, the resulting unmatched entity must be recorded under the key slot_name (the alias), not under list_name.

This applies regardless of the underlying list type:

  • Value lists (lists defined by an explicit set of values): if the input text at that slot position does not match any of the list's values, the unmatched entity is keyed by the slot name.
    • Example: template run {script_name:name} with script_name a value list; input run missing name produces a single unmatched entity keyed name.
  • Range lists (numeric ranges with from/to bounds):
    • If the input at the slot position is non-numeric, the unmatched entity is keyed by the slot name.
      • Example: template execute script {script_number:number} with script_number a range from 1 to 100; input execute script wrong number produces a single unmatched entity keyed number.
    • If the input at the slot position is numeric but falls outside the range bounds, the unmatched entity is likewise keyed by the slot name.
      • Example: same template; input execute script 0 (0 is outside 1–100) produces a single unmatched entity keyed number.

  • recognize(sentence, intents, allow_unmatched_entities=False) — a module-level function that attempts to match a sentence string against the given Intents. When allow_unmatched_entities=True, sentences may still match even if some slots do not satisfy their list constraints, with those slots recorded as unmatched entities.

    • Returns None if no match is found.
    • On a successful match, returns a result object with:
      • .entities — a mapping (dict-like) from entity key → entity object, where each entity object has a .value attribute (and, for text-based captures, a .text attribute holding the matched input span).
      • .unmatched_entities — a mapping (dict-like) from unmatched-entity key → unmatched-entity object.

Summary of the Change

Wherever an entity (matched or unmatched) is produced from a slot reference that carries an alias ({list_name:slot_name}), the entity must be keyed by the alias (slot_name) rather than by the list name. This must hold for wildcard matches and for all unmatched-entity cases (value lists, non-numeric range inputs, and out-of-range numeric inputs).

Duplicate fixed/unmatched entities for the same slot must not be recorded more than once — each slot yields at most a single entry under its key.
