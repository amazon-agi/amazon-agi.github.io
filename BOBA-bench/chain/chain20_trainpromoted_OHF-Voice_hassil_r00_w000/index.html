01 You are working on hassil, a Python library that matches natural-language sentences against intent templates. 562 words · source specification, reworded by GLM-5.3-Flash

Task Description

You are working on hassil, a Python library that matches natural-language sentences against intent templates. Carry out the changes described below.

Public API Surface

parse_sentence importable from the package root

parse_sentence must be importable directly from the top-level package:

from hassil import parse_sentence

Importing it from hassil.parse (its existing location) must also continue to work. The two import paths must refer to the same callable. The function takes a template string and returns a parsed sentence object that the matching and sampling functions can use.

recognize — the new ignore_whitespace parameter

The recognize function (importable in its current form) must accept a new optional keyword argument:

recognize(text, intents, ..., ignore_whitespace=False)
  • The default of ignore_whitespace is False, which preserves all existing behavior.
  • When ignore_whitespace=True, all whitespace is treated as insignificant during matching. In other words, whitespace present in the input text as well as whitespace implied between template tokens is ignored when determining whether the input matches a template.

To make this concrete: with ignore_whitespace=True, a template such as run [the] test (where [the] is an optional word) must successfully match all of the following inputs:

  • "runtest" (without spaces, optional word absent)
  • "runthetest" (without spaces, optional word present)
  • "r u n t h e t e s t" (with arbitrary spaces inserted between every character)

In each of these cases, the result returned by recognize must be non-None.

Behavior That Must Keep Working

Whitespace normalization inside alternatives (default matching)

Under normal (default) matching, alternative groups written with irregular internal whitespace must still match correctly. As an example, the template:

set brightness to ( minimum | lowest)

— which has a leading space after ( and spaces around the | — must match the input "set brightness to lowest".

Recognition behavior already in place

Recognition of entity text and of number text must continue to work as before. For example:

  • For a template capturing a {name} entity mapped to the value "A" from the text alpha, inputs like "run test alpha now", "run test alpha", and "alpha test" must produce a result in which the name entity has value "A" and the captured text, stripped of surrounding whitespace, equals "alpha".
  • For a template capturing a {percentage} entity for 50%, inputs like "set 50% now", "set 50%", and "50% set" must produce a result in which the percentage entity has value 50 and the stripped captured text is "50%".

Sampling of Sentences — Nested Optionals

The function sample_expression (importable in its current form) generates all possible concrete sentences that a template can match. It must enumerate correctly for templates containing multiple/adjacent optional segments.

For this template:

turn [on] [the] light[s]

sample_expression(parse_sentence(...)) must yield exactly the following set of strings (with each optional segment independently present or absent):

  • "turn light"
  • "turn lights"
  • "turn on light"
  • "turn on lights"
  • "turn the light"
  • "turn the lights"
  • "turn on the light"
  • "turn on the lights"

Whitespace in the produced strings must be single-spaced and correctly collapsed where optional words are omitted, with no doubled or trailing spaces.

The existing sampling behavior for a single optional and for alternatives must be preserved (e.g., turn [on] the light and this is (the | a) test enumerate as expected).

02 Adding settings Block Support to the Intents YAML 359 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Adding settings Block Support to the Intents YAML

Goal

Extend the parsing of the intents YAML so that parsing/matching options can be specified through a top-level settings block. In particular, a settings block may declare ignore_whitespace, and when it is set, whitespace is ignored during sentence recognition without the option having to be passed explicitly to the recognition call.

Behavior Requirements

The settings Block in the YAML

An optional top-level settings mapping may appear in the intents YAML document, alongside the already existing language and intents keys. Inside settings, the key ignore_whitespace (boolean) may be supplied.

Example of the structure:

language: "en"
settings:
  ignore_whitespace: true
intents:
  TestIntent1:
    data:
      - sentences:
          - "run [the] test"

When settings.ignore_whitespace is true, the Intents object produced by parsing must carry this setting so that recognition performed afterwards ignores whitespace.

Recognition That Uses the Setting

When an Intents object has been loaded from YAML whose settings block declared ignore_whitespace: true, a call to recognize(sentence, intents) — without supplying ignore_whitespace — must behave as if whitespace-insensitive matching were requested.

Concretely, given intents that define a sentence pattern such as "run [the] test", all of the following input sentences must match successfully (they return a non-None result) when the loaded intents carry ignore_whitespace: true in their settings:

  • "runtest"
  • "runthetest"
  • "r u n t h e t e s t"

Public API

  • Intents.from_yaml(file) — a classmethod that parses the YAML (a file object / path, as already supported) and returns an Intents instance. It must now also read the optional top-level settings block, ignore_whitespace included, and store it on the object that is returned.
  • recognize(sentence, intents) — a module-level function. It must honor the ignore_whitespace setting stored on the given intents object when no explicit ignore_whitespace argument is supplied, and it must return None in the case of no match or a truthy result object in the case of a match.

The ignore_whitespace keyword argument of recognize continues to be available; the new behavior is that, when the argument is not explicitly provided, the setting from the YAML settings block takes effect.

03 Your work concerns a sentence-matching library (Hassil-style intent recognition) that parses template sentences and matches them against input text. 531 words · source specification, reworded by GLM-5.3-Flash

Task Description

Overview

Your work concerns a sentence-matching library (Hassil-style intent recognition) that parses template sentences and matches them against input text. Two behaviors need correcting/implementing: (1) the treatment of grouped/alternative word fragments, and (2) the way "skip words" interact with whitespace-ignoring matching.

Public API

The items below must be importable and callable as described:

  • parse_sentence(text: str) — takes a template string and produces a sentence object (already in use within the library).
  • is_match(text: str, sentence, *, expansion_rules=None, slot_lists=None) -> bool — indicates whether text matches the parsed sentence. (The signature is the existing one; expansion_rules and slot_lists are keyword arguments, as already supported.)
  • recognize(text: str, intents) -> Optional[...] — compares input text against a collection of intents, returning a truthy result on success or None on failure.
  • Intents.from_yaml(file) — builds an Intents collection from a YAML stream.

Behavior Requirements

1. Whitespace matters by default

If ignore_whitespace is not enabled, template matching must require the input to contain whitespace boundaries wherever the template has them. Concretely, a template made up of distinct space-separated words must NOT match an input string from which all whitespace has been removed.

  • For a template parsed from "this is a test", the input "thisisatest" must NOT match.
2. Grouped alternatives and optional groups may sit flush against surrounding characters without internal whitespace

Template parsing must handle alternative groups ( ... | ... ) and optional groups [ ... ] correctly when their delimiters directly abut adjacent text and their alternatives are separated by | without surrounding spaces.

  • For the template parsed from "give me the penn(y|ies)", matching must succeed for both "give me the penny" and "give me the pennies". The group attaches directly to the preceding penn without any intervening whitespace, and the alternatives y and ies are separated by | with no surrounding spaces.

  • An optional group may include a trailing space inside the brackets to stand for optional whitespace. For the template parsed from "[the ]kitchen", matching must succeed for both "the kitchen" and "kitchen". When such a template is used as an expansion rule (e.g. bound to a rule named area) and referenced from a larger template, matching must succeed accordingly — for instance, a rule area = "[the ]kitchen" used within a prefix/suffix template must allow input in which the optional the is absent (e.g. matching "abc-kitchen-123").

3. Skip words in combination with ignore_whitespace

If an Intents collection is configured with ignore_whitespace: true and declares one or more skip_words, recognition must ignore those skip words even when they occur adjacent to matched content with no whitespace separation.

  • With intents configured with ignore_whitespace: true, a single intent whose sentence is "ad", and a skip word "bc", the input "abcd" must be recognized successfully (the skip word bc gets skipped, leaving ad to match). recognize("abcd", intents) must return a result that is not None.

Notes

  • Matching behavior that already exists for other constructs (optional plurals, expansion rules, slot lists, and whitespace-ignoring recognition without skip words) must stay intact.
  • When enabled, the ignore_whitespace setting continues to allow matching regardless of whitespace differences in the input.

07 Introduce Permutation Support into Sentence Template Grouping 783 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Introduce Permutation Support into Sentence Template Grouping

Overview

Sentence templates are parsed by this codebase into an expression tree; input text is then matched against those templates. You are required to add support for a new grouping construct — a permutation group — under which the items in a group are able to match in any order.

Background: Grouping Constructs Already Supported

Two grouping delimiters inside parentheses are already supported by the template parser:

  • Sequence groups: the items are separated by nothing/implicitly, so they are matched in order. e.g. (a b).
  • Alternative groups: | separates the items, and any one of the alternatives is matched. e.g. (a|b).

A third must be added:

  • Permutation groups: a ; (semicolon) separates the items, which then match in any order.

Behavior Requirements

1. Parsing of a permutation group

Whenever a parenthesized group has its items separated by the ; (semicolon) delimiter, the parser must produce an expression that represents those items being matched in every possible order (all permutations).

Parsing is entered through the existing functions that convert template text into expressions. Specifically:

  • parse_expression(next_chunk("(test; test2)")), which comes from the expression parsing module (this is the same module that exposes parse_expression, next_chunk, ListReference, and the expression node types), must produce an alternative expression; the two orderings of the two segments are its alternatives.

Here is what happens concretely for the input (test; test2):

  • A split on ; turns the group into two segments. The text "test" stands before the ;; the text " test2" stands after it (note: the leading whitespace after the semicolon stays part of the segment text — do NOT strip it).
  • From each segment, a sequence group is formed that wraps its parsed text (a text/word node).
  • What you end up with is an alternative; one sequence group per permutation makes up its items. Each permutation, in turn, is a sequence group, and the items it contains are the per-segment sequence groups laid out in that permutation's order.

Take two segments, A (= sequence group containing text "test") and B (= sequence group containing text " test2"); the structure produced comes out exactly as:

alternative(
    items=[
        sequence_group(items=[A, B]),
        sequence_group(items=[B, A]),
    ]
)

where:

  • A = sequence_group(items=[text_node(text="test")])
  • B = sequence_group(items=[text_node(text=" test2")])

In the alternative's items list, the permutations must be ordered like this: first the identity order ([A, B]), after that the swapped order ([B, A]).

For building the nodes, use the expression node constructors/types that already exist in that module: the alternative node (construct it the way the existing alternative-group handling does), the sequence-group node (the standard group node), and the text/word node that serves for literal text. Exactly the substrings described above — the preserved leading space in the second segment included — are what the text fields must contain.

2. Matching of a permutation group

Parsing of a full sentence template that contains a permutation group happens with parse_sentence(...) (the sentence-parsing function that already exists in its current module); matching against input text then happens with is_match(...) (the matching helper that already exists). The input must count as a match if it corresponds to any ordering of the permutation group's segments.

With the template "( in the kitchen ; is there smoke )":

  • The input " in the kitchen is there smoke " must match (the segments appear in their written order).
  • The input " is there smoke in the kitchen " must match (the segments appear in the reversed order).

Handling of whitespace inside and around the segments must stay consistent with existing matching behavior, so that both orderings above match the given inputs.

Constraints

  • The behavior of existing sequence groups or alternative groups must not be altered.
  • Within a parenthesized group, it is the semicolon ; that acts as the delimiter triggering permutation grouping.
  • Between delimiters, segment text is preserved verbatim (a segment undergoes no trimming of its leading/trailing whitespace).
  • All orderings of the group's segments get enumerated by the permutation expansion; with N segments, N! orderings result, and these are the alternatives.

Public API Surface (must stay importable and callable)

Every name below already exists, apart from the places where new behavior is added to it; no new public functions or classes are required — the existing API is what carries the new behavior:

  • Expression parsing module: parse_expression(chunk), next_chunk(text), ListReference, the alternative node type, the sequence/group node type, and the text/word node type.
  • Sentence module: parse_sentence(text).
  • Matching helper: is_match(text, sentence).

That these functions must now correctly handle the ; permutation delimiter, as described above, is the only functional change.

Summary

A new grammar construct, the permutation, is to be added to the sentence expression parser. A permutation brings together two or more items and matches when those items occur in any order in the input text.

To write a permutation, put the items between parentheses and separate them with semicolons (;):

(item1; item2)
(A; B; C)

This is not the same as the existing alternative construct: there, items inside parentheses are separated by the pipe (|), and exactly one of the items is matched.

If a parenthesized group has its top-level items separated by semicolons, the parser must produce an expression that matches those items in any ordering.

How the Expansion Works

An alternative (the same alternative construct produced for |-separated groups) is the required representation for a permutation of N items: it holds one group for each possible ordering of the items — that is, every permutation of the N items, in order. With 2 items there are 2 orderings; with 3 items there are 6 orderings.

Inserted Whitespace

Permutations are meant for reordering whole words/phrases; consequently, a single literal space text chunk (" ") must be present in every ordering before the first item, between every pair of adjacent items, and after the last item.

To make this concrete with an input such as (test; test2), each ordering-group must take the form of the following ordered sequence:

  1. a text chunk whose content is a single space " ",
  2. the group parsed from the first item,
  3. a text chunk whose content is a single space " ",
  4. the group parsed from the second item,
  5. a text chunk whose content is a single space " ".

Every individual permutation item is parsed into a group of its own. Also worth noting: for items following the separator, the raw text keeps its leading whitespace exactly as it is written in the source (in (test; test2), for example, the second item parses to text " test2", whereas the first is "test").

Example of the Resulting Structure

With (test; test2) as the input, the parsed expression must equal an alternative whose items are:

  • Ordering 1 — a group whose contents, in order, are: text " ", group[text "test"], text " ", group[text " test2"], text " ".
  • Ordering 2 — a group whose contents, in order, are: text " ", group[text " test2"], text " ", group[text "test"], text " ".

Matching Behavior

When a sentence has a permutation in it, that sentence must match input in which the permutation's items occur in any order (the inserted spaces account for the surrounding/interleaving whitespace). As an example, a sentence constructed from (in the kitchen; is there smoke) must match both:

  • in the kitchen is there smoke
  • is there smoke in the kitchen

    • text chunk (TextChunk, referred to as t(text=...), with text being the literal string),

Telling Alternatives and Permutations Apart

What decides the construct is the separator inside a parenthesized group:

  • | → alternative (match exactly one item) — behavior that already exists and remains unchanged.
  • ; → permutation (match items in any order) — the new behavior described above.

Summary

You are working on hassil — a library that recognizes intents in natural language sentences via intent templates, defined in YAML, that come with slot lists. The handling of unmatched entities is what this task extends: entities that an intent's context requires, but that are absent from the input, are now reported as unmatched entities.

Requirement for the Public API

Inside the module hassil.recognize, introduce a new module-level constant:

MISSING_ENTITY

An import written as from hassil.recognize import MISSING_ENTITY must work. The constant is a sentinel string value that serves as the text attribute of an unmatched text entity; that entity is created to represent a required-context entity for which the input sentence had no corresponding value. Beyond this role, nothing constrains its exact value — even so, it must be a distinct marker that distinguishes "this entity was entirely missing from the input" from a real captured text fragment.

UnmatchedRangeEntity and UnmatchedTextEntity — already importable from hassil.recognize — stay available, and nothing about them changes.

Behavior to Be Implemented

Background: how allow_unmatched_entities affects recognition

recognize(sentence, intents, allow_unmatched_entities=...) takes an input sentence and attempts to match it against the defined intents. Under allow_unmatched_entities=False, a sentence is matched only when every entity referenced by the matched template resolves to a real slot-list value. Under allow_unmatched_entities=True, the function may still return a result even when some entities cannot be matched; in that situation, the result's unmatched_entities dictionary (keyed by entity/slot name) gets filled with UnmatchedTextEntity (or UnmatchedRangeEntity) instances.

New requirement: missing required-context entities

The data belonging to an intent may declare requires_context, a mapping that pairs context keys with the values expected for them (for example domain: cover). Matching a slot in the sentence text is what would normally supply the entities to which these context keys correspond.

During recognition of a sentence:

  • If the input does not supply a value for a key named in requires_context, and allow_unmatched_entities=True, the recognition result must include an entry in unmatched_entities under that context key. That entry must be an UnmatchedTextEntity, and its text attribute must be equal to MISSING_ENTITY.

  • With allow_unmatched_entities=False, whenever an unsatisfied required-context key is present, the sentence must fail to match (the function returns None).

Interaction with unmatched text entities

Whenever a sentence template contains a slot reference (for example {name}) and the words actually found in that position do not correspond to any value in the slot list, an UnmatchedTextEntity of its own is produced — keyed by the slot name — and its text attribute holds the literal captured text fragment (with normal handling of the surrounding whitespace). Nothing about this already-existing behavior changes.

Both kinds of unmatched entities occur alongside one another. To spell this out, take an intent whose sentence references a text slot and whose data also declares a required-context key that is absent from the input:

  • When the sentence's slot text does match a real slot-list value, then unmatched_entities contains only the missing required-context key (with text == MISSING_ENTITY).

  • When the sentence's slot text does not match a real slot-list value, then unmatched_entities contains both the slot name (whose text equals the captured fragment) and the missing required-context key (with text == MISSING_ENTITY).

Worked Example

Consider this set of intents:

    values:

Overview

The library you are modifying handles intent recognition: it matches natural-language sentences against a set of intents defined in YAML. Named lists may be referred to from within a sentence by way of slot references. The task at hand covers two questions: which name an entity key receives when a slot reference uses a slot alias, and the way unmatched entities behave.

Background: Slot Reference Forms

A slot reference inside a sentence template can appear in two forms:

  • {list_name} — the list is referenced directly; the list name serves as the entity key.
  • {list_name:slot_name} — the list is referenced while an alias (the slot name) is assigned to it; the entity key must be the slot name rather than the list name.

Behavior Requirements

1. Matched wildcard entities are keyed by the slot name

Take a sentence template containing a slot reference of the form {list_name:slot_name} whose list is a wildcard list. Whenever a match against such a template succeeds, the resulting entity must be recorded with slot_name (the alias) as its key — list_name must not serve as the key.

What the captured entity holds as its value must be the matched span of text from the input sentence.

Example: with the template run {script_name:name}, where script_name is a wildcard list, the input run script 1 must match, and the match must contain a single entity keyed name with script 1 as its value.

2. Unmatched entities are keyed by the slot name

If recognition happens with unmatched entities allowed and a slot reference of the form {list_name:slot_name} fails to satisfy its list's constraints, then the unmatched entity it produces must be recorded with slot_name (the alias) as its key — list_name must not serve as the key.

The type of list underneath makes no difference here:

  • Value lists (such a list is defined by an explicit set of values): if the input text at that slot position does not match any of the values the list contains, the unmatched entity receives the slot name as its key.
    • Example: for the template run {script_name:name} with script_name a value list, the input run missing name produces a single unmatched entity whose key is name.
  • Range lists (numeric ranges bounded by from/to):
    • If the input sitting at the slot position is non-numeric, the slot name becomes the key of the unmatched entity.
      • Example: the template execute script {script_number:number}, with script_number a range from 1 to 100; the input execute script wrong number produces a single unmatched entity whose key is number.
    • If the input at the slot position is numeric yet falls outside the bounds of the range, the unmatched entity is keyed by the slot name all the same.
      • Example: still the same template; the input execute script 0 (0 is outside 1–100) produces a single unmatched entity whose key is number.

Public API Surface

Everything listed below must remain importable and callable exactly as described (this is the existing surface — it must be preserved):

  • Intents.from_yaml(file) — a classmethod that the Intents class provides; it parses a YAML definition supplied by a file-like object (e.g. an io.StringIO) and returns an Intents instance.

  • recognize(sentence, intents, allow_unmatched_entities=False) — a function defined at module level; it takes a sentence string and attempts to match it against the Intents provided. Under allow_unmatched_entities=True, a sentence may still match even when some of its slots do not satisfy their list constraints, with such slots recorded as unmatched entities.

    • None is returned if no match is found.
    • If a match succeeds, the function returns a result object that has:
      • .entities — a mapping (dict-like) from entity key → entity object, in which each entity object has a .value attribute (for text-based captures there is also a .text attribute holding the matched input span).
      • .unmatched_entities — a dict-like mapping from unmatched-entity key → unmatched-entity object.
