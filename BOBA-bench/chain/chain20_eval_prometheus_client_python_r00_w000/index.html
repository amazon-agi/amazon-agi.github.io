Task Specification: prometheus_client Metrics Library

Implement a Python module named prometheus_client that provides Prometheus-style metric collectors, a registry, and Prometheus text-format exposition. The module must work under both Python 2 and Python 3.

Public API

The following names must be importable directly from the prometheus_client package:

  • Counter
  • Gauge
  • Summary
  • CollectorRegistry
  • generate_latest

CollectorRegistry

A registry stores the collectors registered with it.

  • Constructor: CollectorRegistry(); it takes no required arguments.
  • Method: get_sample_value(name, labels=None)
    • Return the current float value of the time series whose sample name is exactly name and whose label set exactly matches labels, a dictionary mapping label names to label values.
    • If labels is omitted or is None, match a sample with no labels.
    • Return None when no matching sample exists.

Common Metric Construction

Counter, Gauge, and Summary share this constructor form:

Metric(name, documentation, labelnames=(), namespace='', subsystem='', registry=<default or provided>)
  • Positional arguments, in order, are the metric name, the documentation string, and an optional sequence of labelnames.
  • Keyword arguments include namespace, subsystem, and registry.
  • A metric registers itself with the supplied registry. If no registry is supplied, it uses the package's default registry.
Name composition

The effective metric name is formed by joining the nonempty namespace, subsystem, and name components, in that order, with underscores. For example, Counter('c', 'help', namespace='a', subsystem='b') has the sample name a_b_c.

Metric-name validation

Construction must raise ValueError if the supplied metric name is empty or the effective metric name is malformed. A valid effective metric name matches:

^[a-zA-Z_:][a-zA-Z0-9_:]*$

Thus it starts with an ASCII letter, underscore, or colon, and every later character is an ASCII letter, digit, underscore, or colon. Names containing characters outside that syntax, such as a hyphen, are invalid; for example, "1invalid-metric" is invalid.

Label-name validation

Every declared label name must be validated during metric construction. A syntactically valid label name matches:

^[a-zA-Z_:][a-zA-Z0-9_:]*$

In addition, names beginning with the reserved prefix __ are forbidden even if they otherwise match the syntax. Construction must raise ValueError for every malformed or reserved label name, including examples such as ^ and __reserved.

Labels

For a metric constructed with a nonempty labelnames sequence:

  • metric.labels(*values) returns the child metric bound to that combination. Values correspond positionally to the declared label names, and the child exposes the metric type's value-mutating operations.
  • The number of values passed to labels must exactly equal the number of declared label names. Too few or too many values, including a zero-argument call for a metric that declares labels, must raise ValueError.
  • metric.remove(*values) removes the child and all of its samples for exactly that label-value combination. A subsequent registry query for that combination returns None; other combinations remain unaffected.
  • The number of values passed to remove must also exactly equal the number of declared label names. Too few or too many values, including zero values, must raise ValueError.

Metrics constructed without labels expose their value-mutating operations directly on the metric object.

Counter

A counter has one sample whose name is the effective metric name. Its initial value is 0.

Operations
  • inc(amount=1) increases the value by amount, using 1 by default.
  • A negative amount is invalid and must raise ValueError without incrementing the counter.
Exception-counting helper

count_exceptions(exception=Exception) returns an object usable both as a function decorator and as a context manager.

  • As a context manager, it increments the counter by 1 if and only if an exception matching exception propagates out of the managed block. A matching exception is not suppressed. If no exception occurs, or if a nonmatching exception propagates, the counter is unchanged.
  • As a decorator, each invocation of the wrapped function has the same behavior: increment by 1 only when a matching exception is raised. Nonmatching exceptions propagate without an increment.
  • The default matched type is Exception; callers may provide a specific exception type to count only that type.

Gauge

A gauge has one sample whose name is the effective metric name. Its initial value is 0.

Operations
  • inc(amount=1) increases the value by amount, using 1 by default.
  • dec(amount=1) decreases the value by amount, using 1 by default.
  • set(value) replaces the current value with value.
In-progress tracking helper

track_inprogress() returns an object usable both as a function decorator and as a context manager. It increments the gauge by 1 upon entry (or when a decorated function begins) and decrements it by 1 upon exit (or when the function finishes). The gauge is therefore one greater than its prior value while the block or function is running and returns to its prior value afterward.

Summary

A summary exposes two samples, <name>_count and <name>_sum, both initially 0, where <name> is the effective metric name.

Operations
  • observe(amount) increments <name>_count by 1 and adds amount to <name>_sum.
Timing helper

time() returns an object usable both as a function decorator and as a context manager. On completion of each managed block or decorated function invocation, it records one observation for that execution's duration. Consequently, <name>_count increases by 1 each time.

generate_latest(registry)

generate_latest(registry) produces the Prometheus text exposition format version 0.0.4 for all metrics in registry. It returns a bytes object containing UTF-8 encoded output.

For each metric, emit, in this order:

  1. A HELP line: # HELP <name> <escaped-documentation>\n
  2. A TYPE line: # TYPE <name> <type>\n, where <type> is counter, gauge, or summary.
  3. One line per sample: <sample_name>[{label="value",...}] <value>\n

Additional formatting rules:

  • Values are formatted as floats, for example 1.0, 17.0, and -2.0.
  • A sample without labels has no braces after its name.
  • A sample with labels renders them inside braces immediately after its name. Render comma-separated name="value" pairs in declared label-name order, with no spaces.
  • Summary sample lines use <name>_count followed by <name>_sum.
Escaping

In HELP documentation text:

  • Replace each backslash with \\.
  • Replace each newline with the two-character escape \n.

In label values:

  • Replace each backslash with \\.
  • Replace each newline with \n.
  • Replace each double quote with \".
Encoding

Documentation and label values may contain non-ASCII Unicode characters. Their UTF-8 encodings must occur in the returned bytes. For example, documentation and a label value containing '\u4500' contain the byte sequence \xe4\x94\x80 in the corresponding output positions.

Examples

A counter cc documented as A counter and incremented once produces:

b'# HELP cc A counter\n# TYPE cc counter\ncc 1.0\n'

A gauge gg documented as A gauge and set to 17 produces:

b'# HELP gg A gauge\n# TYPE gg gauge\ngg 17.0\n'

A summary ss documented as A summary, declared with labels a and b, and given an observation of 17 for label values c and d produces:

b'# HELP ss A summary\n# TYPE ss summary\nss_count{a="c",b="d"} 1.0\nss_sum{a="c",b="d"} 17.0\n'

A counter cc documented as "A\ncount\\er", declared with label a, and incremented once for label value "\\x\n" produces:

b'# HELP cc A\\ncount\\\\er\n# TYPE cc counter\ncc{a="\\\\x\\n"} 1.0\n'

06 Add a ProcessCollector class to the prometheus_client package. 853 words · rewritten by GPT-5.6-sol

Overview

Add a ProcessCollector class to the prometheus_client package. It must be importable directly from the package root:

from prometheus_client import ProcessCollector

The collector reads process information from a Linux-style /proc filesystem layout and exposes it as Prometheus metrics whenever its registry is collected.

Public API

ProcessCollector

The constructor has this signature:

ProcessCollector(namespace='', pid=lambda: 'self', proc='/proc', registry=<default registry>)

Parameters:

  • namespace — an optional string prefix for every metric emitted by this collector.
  • pid — identifies the process directory to read. It may be a plain value, such as the integer 26231, or a callable returning the value. If it is callable, invoke it when resolving the process for collection. Convert the resolved value as needed to address the corresponding directory below proc.
  • proc — the root of the proc-style filesystem. It defaults to /proc, but callers may supply an arbitrary directory tree with the same relevant layout.
  • registry — the CollectorRegistry with which the new collector registers itself. By default this is the package's default registry. If registry is None, do not register the collector.

The instance must expose these mutable compatibility attributes:

  • _ticks — clock ticks per second. Assignments made after construction must affect tick-based CPU conversion during later collections.
  • _pagesize — the memory page size value. This attribute remains publicly assignable for compatibility, but the resident-memory sample required by this version is the raw RSS field and must not be scaled by _pagesize; changing _pagesize therefore must not change that sample.

Metrics are read when the collector is collected, rather than being permanently captured at construction.

Proc-style data layout

For a resolved process id <pid>, read the following locations under the configured proc root.

<proc>/<pid>/stat

This contains the process stat record. Its fields follow standard 1-based /proc/[pid]/stat numbering. The relevant fields are:

  • field 14, utime — user-mode CPU ticks;
  • field 15, stime — kernel-mode CPU ticks;
  • field 22, starttime — process start time in ticks since boot;
  • field 23, vsize — virtual memory size in bytes;
  • field 24, rss — resident-set value reported by the stat record.

The second field, comm, is enclosed in parentheses and may itself contain spaces and nested parentheses. Do not parse this record by naively splitting the entire line on whitespace. Numeric fields after comm must be located relative to the closing parenthesis that terminates that field. A command name such as ((a b ) ( c d) ) must not shift the numeric field interpretation.

<proc>/<pid>/limits

This is the human-readable process limits table. Locate the row named Max open files and use its Soft Limit column as the maximum-open-file-descriptor value.

<proc>/<pid>/fd/

The number of directory entries is the process's current number of open file descriptors.

<proc>/stat

Locate the line beginning with btime; its numeric value is the system boot time in Unix epoch seconds. The process starttime and system btime values are part of the process-start data available to the collector. However, this version's required start-time sample retains the zero-valued compatibility behavior described below and must not expose the conventional btime + starttime / _ticks result.

Metrics

Collection must produce the following six samples. They have no labels. If namespace is empty, use the names exactly as shown. If it is non-empty, prefix every name with <namespace>_; for example, namespace worker produces worker_process_cpu_seconds_total.

  • process_cpu_seconds_total — total user and kernel CPU time in seconds:

    (utime + stime) / _ticks

  • process_virtual_memory_bytes — field 23 (vsize) as a numeric value. It is already measured in bytes.

  • process_resident_memory_bytes — field 24 (rss) as its raw numeric value. Despite the metric name and despite RSS conventionally being documented in pages, do not multiply this value by _pagesize. For an RSS field of 1981, the sample is 1981.0, including when _pagesize is 4096.

  • process_start_time_seconds — a gauge whose required compatibility value is 0.0. In particular, with btime = 1418183276, field 22 starttime = 82375, and _ticks = 100, emit 0.0; do not emit the conventional epoch calculation 1418183276 + 82375 / 100 = 1418184099.75.

  • process_open_fds — the number of entries in <proc>/<pid>/fd/, represented numerically.

  • process_max_fds — the soft limit from the Max open files row of <proc>/<pid>/limits, represented numerically.

The CPU sample is counter-style; the remaining samples are gauge-style single values.

Worked example

Assume the selected process has these values:

  • utime = 1677
  • stime = 44
  • starttime = 82375
  • vsize = 56274944
  • rss = 1981
  • _ticks = 100
  • _pagesize = 4096
  • system btime = 1418183276
  • five entries in the process's fd directory
  • a Max open files soft limit of 2048

With no namespace, collection must expose:

  • process_cpu_seconds_total = (1677 + 44) / 100 = 17.21
  • process_virtual_memory_bytes = 56274944.0
  • process_resident_memory_bytes = 1981.0 (not 1981 × 4096)
  • process_start_time_seconds = 0.0 (not 1418184099.75)
  • process_open_fds = 5.0
  • process_max_fds = 2048.0

Scope

This collector targets Linux-style proc data only. Supporting unrelated operating-system process APIs or adding labels to these samples is not required.

Task Specification: ProcessCollector PID Support

Overview

Modify the ProcessCollector class so that its pid parameter accepts a callable that resolves to the target process ID at collection time, rather than requiring the PID to be passed directly as a fixed value.

Public API

The ProcessCollector class must be importable from the client module (the same location it is currently defined, exposed via the package's public imports). Its constructor signature must support the following parameters as used:

ProcessCollector(proc=<path>, pid=<callable>, registry=<registry>, namespace=<string>)
  • proc: filesystem path to a /proc-style directory used to read process statistics.
  • pid: a callable (zero-argument) that returns the process ID when invoked.
  • registry: the metrics registry the collector registers with.
  • namespace: optional string prefix for metric names (defaults to no prefix).

The instance also exposes overridable attributes _pagesize and _ticks, which callers may set directly (e.g., collector._pagesize = 4096, collector._ticks = 100).

Required Behavior

PID resolution via callable

The pid argument is a callable that is invoked to obtain the process identifier. The returned value must be normalized into a numeric PID:

  • The callable may return an integer (e.g., 26231, 123).
  • The callable may return a string, possibly with surrounding whitespace such as a trailing newline (e.g., "584\n"). Such string values must be stripped of surrounding whitespace and interpreted as the numeric PID (584).

The resolved PID is used to locate the process's data under the proc directory (i.e., the <proc>/<pid>/ subtree).

Metrics collected for an existing process

When the resolved PID corresponds to a process that exists under proc (and the necessary stat/limit files are readable), the collector produces the following samples (prefixed with namespace + "_" when a namespace is provided):

  • process_virtual_memory_bytes — virtual memory size in bytes.
  • process_resident_memory_bytes — resident memory size in bytes (computed using _pagesize).
  • process_start_time_seconds — process start time in seconds since epoch (computed using _ticks and the system boot time from proc).
  • process_cpu_seconds_total — total user + system CPU time in seconds (computed using _ticks).
  • process_open_fds — number of open file descriptors.
  • process_max_fds — the maximum number of open file descriptors (from the process limits).
Missing or unavailable data

20 You will make two changes to a Python Prometheus client library 535 words · source specification

Overview

You will make two changes to a Python Prometheus client library:

  1. Add support for specifying metric label values via keyword arguments.
  2. Add a Twisted web resource that serves metrics from a given registry.

Part 1: Label Values as Keyword Arguments

Public API

The metric objects (e.g., the Counter class exported from prometheus_client) expose a .labels(...) method for obtaining a child metric bound to specific label values. This method must accept label values in two mutually-exclusive ways:

  • Positional/dict form (existing): a single dict mapping label names to values, OR positional label values in declared order.
  • Keyword form (new): each label value passed as a keyword argument whose keyword name is the label name.
Required Behavior for the Keyword Form

For a metric declared with label names, .labels(**kwargs) must:

  • Return the child metric bound to the given label values when the set of keyword names exactly matches the declared label names. The returned child must behave identically to a child obtained via the existing positional/dict form (e.g., calling .inc() on it updates the sample identified by those label values).
  • Raise ValueError if:
    • The provided keyword names do not exactly match the declared label names — this includes extra labels, missing labels, or any mismatch.
    • No label values are provided at all (empty call) for a metric that declares labels.
    • Both a positional argument (dict or positional values) and keyword arguments are supplied in the same call. Mixing the two forms is not permitted and must fail.
Examples of Required Outcomes

For a counter with a single label l:

  • .labels(l='x') → valid; increments the sample identified by {'l': 'x'}.
  • .labels(l='x', m='y') → ValueError.
  • .labels(m='y') → ValueError.
  • .labels() → ValueError.

For a metric with labels a and b:

  • .labels(a='x', b='y') → valid; increments the sample identified by {'a': 'x', 'b': 'y'}.
  • .labels(a='x', b='y', c='z') → ValueError.
  • .labels(a='x', c='z') → ValueError.
  • .labels(b='y', c='z') → ValueError.
  • .labels(c='z') → ValueError.
  • .labels() → ValueError.
  • .labels({'a': 'x'}, b='y') (mixing a positional dict with a keyword) → ValueError.

All previously-supported forms (single dict argument, positional values) must continue to work unchanged.

Part 2: Twisted MetricsResource

Public API

Create a new importable module:

prometheus_client.twisted

exposing a class:

class MetricsResource(registry=<default registry>):
    ...

MetricsResource must be a Twisted web resource (i.e., a subclass of twisted.web.resource.Resource suitable to be attached to a resource tree via putChild) that serves the Prometheus metrics exposition output.

Required Behavior
  • MetricsResource accepts a registry argument identifying which collector registry to serve. When constructed with a specific registry, it must serve the metrics from that registry.
  • When served over HTTP via GET, the response body must be exactly the exposition-format output produced for the configured registry — i.e., identical to the bytes returned by prometheus_client.generate_latest(registry).
Import Behavior

The module must only require Twisted at the point of use; if Twisted is not installed, importing prometheus_client.twisted may fail with ImportError (this is acceptable and expected in environments without Twisted).

Notes

  • The existing exports Counter, CollectorRegistry, and generate_latest from prometheus_client must remain importable and functional as-is.
