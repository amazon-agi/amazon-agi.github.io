Task Specification: the prometheus_client Metrics Library

Build a Python module called prometheus_client that offers Prometheus-style metric collectors, a registry, and exposition in the Prometheus text format. The module must run under both Python 2 and Python 3.

Public API

These names must be importable directly from the prometheus_client package:

  • Counter
  • Gauge
  • Summary
  • CollectorRegistry
  • generate_latest

CollectorRegistry

A registry holds the collectors that have been registered with it.

  • Constructor: CollectorRegistry(); no arguments are required.
  • Method: get_sample_value(name, labels=None)
    • Return the current float value of the time series whose sample name is exactly name and whose label set exactly matches labels, where labels is a dictionary mapping label names to label values.
    • When labels is omitted or is None, match a sample that has no labels.
    • Return None if there is no matching sample.

Shared Metric Construction

Counter, Gauge, and Summary all use this constructor shape:

Metric(name, documentation, labelnames=(), namespace='', subsystem='', registry=<default or provided>)
  • The positional arguments, in order, are the metric name, the documentation string, and an optional labelnames sequence.
  • The keyword arguments include namespace, subsystem, and registry.
  • A metric registers itself with the registry it is given. When no registry is given, it uses the package's default registry.
Composing the name

The effective metric name is built by joining the namespace, subsystem, and name components that are nonempty, in that order, using underscores. For example, the call Counter('c', 'help', namespace='a', subsystem='b') has the sample name a_b_c.

Validating metric names

Construction must raise ValueError when the supplied metric name is empty or when the effective metric name is malformed. A valid effective metric name matches:

^[a-zA-Z_:][a-zA-Z0-9_:]*$

In other words, it begins with an ASCII letter, underscore, or colon, and every character after that is an ASCII letter, digit, underscore, or colon. Any name containing characters outside that syntax, such as a hyphen, is invalid; for example, "1invalid-metric" is invalid.

Validating label names

Each declared label name must be validated while the metric is being constructed. A syntactically valid label name matches:

^[a-zA-Z_:][a-zA-Z0-9_:]*$

Furthermore, names that begin with the reserved prefix __ are forbidden even if they otherwise match the syntax. Construction must raise ValueError for every malformed or reserved label name, including examples such as ^ and __reserved.

Labels

When a metric is constructed with a nonempty labelnames sequence:

  • metric.labels(*values) returns the child metric bound to that combination. The values line up positionally with the declared label names, and the child exposes the value-mutating operations of the metric type.
  • The number of values passed to labels must exactly equal the number of declared label names. Too few or too many values — including a zero-argument call for a metric that declares labels — must raise ValueError.
  • metric.remove(*values) removes the child and all of its samples for exactly that combination of label values. A later registry query for that combination returns None; other combinations remain unaffected.
  • The number of values passed to remove must likewise exactly equal the number of declared label names. Too few or too many values, including zero values, must raise ValueError.

A metric constructed without labels exposes its value-mutating operations directly on the metric object.

Counter

A counter has a single sample whose name is the effective metric name. Its initial value is 0.

Operations
  • inc(amount=1) adds amount to the value, with 1 as the default.
  • A negative amount is invalid; it must raise ValueError without incrementing the counter.
Helper for counting exceptions

count_exceptions(exception=Exception) returns an object that works both as a function decorator and as a context manager.

  • As a context manager, it increments the counter by 1 if and only if an exception matching exception propagates out of the managed block. A matching exception is not suppressed. When no exception occurs, or when a nonmatching exception propagates, the counter is unchanged.
  • As a decorator, every invocation of the wrapped function behaves the same way: increment by 1 only when a matching exception is raised. Nonmatching exceptions propagate without an increment.
  • The default matched type is Exception; callers may supply a specific exception type so that only that type is counted.

Gauge

A gauge has a single sample whose name is the effective metric name. Its initial value is 0.

Operations
  • inc(amount=1) adds amount to the value, with 1 as the default.
  • dec(amount=1) subtracts amount from the value, with 1 as the default.
  • set(value) sets the current value to value.
Helper for tracking in-progress work

track_inprogress() returns an object that serves both as a function decorator and as a context manager. It increments the gauge by 1 on entry (or when a decorated function starts) and decrements it by 1 on exit (or when the function finishes). While the block or function is running, the gauge is therefore one greater than its prior value; afterward it returns to that prior value.

Summary

A summary exposes two samples, <name>_count and <name>_sum, both initially 0, where <name> is the effective metric name.

Operations
  • observe(amount) increments <name>_count by 1 and adds amount to <name>_sum.
Timing helper

time() returns an object that works both as a function decorator and as a context manager. When each managed block or decorated function invocation completes, it records one observation of that execution's duration. So <name>_count increases by 1 each time.

generate_latest(registry)

generate_latest(registry) produces the Prometheus text exposition format version 0.0.4 for all metrics in registry. It returns a bytes object holding UTF-8 encoded output.

For each metric, emit the following, in this order:

  1. A HELP line: # HELP <name> <escaped-documentation>\n
  2. A TYPE line: # TYPE <name> <type>\n, where <type> is counter, gauge, or summary.
  3. One line per sample: <sample_name>[{label="value",...}] <value>\n

Further formatting rules:

  • Values are formatted as floats, for instance 1.0, 17.0, and -2.0.
  • A sample with no labels carries no braces after its name.
  • A sample with labels renders them inside braces immediately after its name. Render the name="value" pairs comma-separated, in declared label-name order, with no spaces.
  • The summary sample lines are <name>_count followed by <name>_sum.
Escaping

Within HELP documentation text:

  • Every backslash is replaced with \\.
  • Each newline is replaced with the two-character escape \n.

Within label values:

  • Every backslash is replaced with \\.
  • Each newline is replaced with \n.
  • Each double quote is replaced with \".
Encoding

Documentation and label values may contain non-ASCII Unicode characters. The returned bytes must contain their UTF-8 encodings. For example, documentation and a label value containing '\u4500' contain the byte sequence \xe4\x94\x80 at the corresponding output positions.

Examples

A counter cc whose documentation is A counter, incremented once, produces:

b'# HELP cc A counter\n# TYPE cc counter\ncc 1.0\n'

A gauge gg whose documentation is A gauge, set to 17, produces:

b'# HELP gg A gauge\n# TYPE gg gauge\ngg 17.0\n'

A summary ss whose documentation is A summary, declared with labels a and b, and given an observation of 17 for label values c and d produces:

b'# HELP ss A summary\n# TYPE ss summary\nss_count{a="c",b="d"} 1.0\nss_sum{a="c",b="d"} 17.0\n'

A counter cc whose documentation is "A\ncount\\er", declared with label a, and incremented once for the label value "\\x\n" produces:

b'# HELP cc A\\ncount\\\\er\n# TYPE cc counter\ncc{a="\\\\x\\n"} 1.0\n'

  • h_count
  • h_sum

  • "2.5"
  • "5.0"

[0.0, 1.0, 2.0, float("inf")]

Summary

The task is to add a ProcessCollector class to the prometheus_client package. It must be possible to import it directly from the package root:

from prometheus_client import ProcessCollector

Whenever its registry is collected, the collector reads process information from a Linux-style /proc filesystem layout and exposes that information as Prometheus metrics.

Public interface

ProcessCollector

The constructor's signature is:

ProcessCollector(namespace='', pid=lambda: 'self', proc='/proc', registry=<default registry>)

Parameters:

  • namespace — an optional string prefix that this collector puts in front of every metric it emits.
  • pid — selects the process directory to read. Its value may be a plain value, such as the integer 26231, or a callable that returns the value. If it is callable, invoke it when the process is resolved for collection. Convert the resolved value as needed so that it addresses the corresponding directory below proc.
  • proc — the root of the proc-style filesystem. The default is /proc, but callers may supply an arbitrary directory tree with the same relevant layout.
  • registry — the CollectorRegistry that the new collector registers itself with. The default here is the package's default registry. When registry is None, do not register the collector.

The following mutable compatibility attributes must be exposed by the instance:

  • _ticks — clock ticks per second. Assignments made after construction must affect the tick-based CPU conversion performed during later collections.
  • _pagesize — the memory page size value. For compatibility, this attribute stays publicly assignable, but the resident-memory sample that this version requires is the raw RSS field and must not be scaled by _pagesize; consequently, changing _pagesize must not change that sample.

Instead of being permanently captured at construction, the metrics are read when the collector is collected.

Layout of the proc-style data

Once the process id <pid> has been resolved, read the following locations under the configured proc root.

<proc>/<pid>/stat

This location holds the process stat record. Field numbering follows the standard 1-based /proc/[pid]/stat scheme. The fields that matter are:

  • field 14, utime — CPU ticks spent in user mode;
  • field 15, stime — CPU ticks spent in kernel mode;
  • field 22, starttime — the process's start time, in ticks since boot;
  • field 23, vsize — the virtual memory size, in bytes;
  • field 24, rss — the resident-set value that the stat record reports.

The second field, comm, is wrapped in parentheses and may itself contain spaces and nested parentheses. This record must not be parsed by naively splitting the entire line on whitespace. The numeric fields after comm must be located relative to the closing parenthesis that terminates that field. A command name such as ((a b ) ( c d) ) must not shift the interpretation of the numeric fields.

<proc>/<pid>/limits

This location provides the human-readable process limits table. Find the row named Max open files and take the value in its Soft Limit column as the maximum-open-file-descriptor value.

<proc>/<pid>/fd/

The process's current number of open file descriptors is given by the number of directory entries.

<proc>/stat

Find the line beginning with btime; the numeric value it carries is the system boot time in Unix epoch seconds. The process-start data available to the collector contains the process starttime value and the system btime value. The required start-time sample of this version, however, keeps the zero-valued compatibility behavior described below and must not expose the conventional btime + starttime / _ticks result.

Metrics

The following six samples must be produced by a collection. No labels are attached to them. If namespace is empty, use the names exactly as shown. If it is non-empty, put the <namespace>_ prefix in front of every name; for instance, the namespace worker gives worker_process_cpu_seconds_total.

  • process_cpu_seconds_total — the total CPU time spent in user and kernel mode, in seconds:

    (utime + stime) / _ticks

  • process_virtual_memory_bytes — the value of field 23 (vsize) as a number. It is already expressed in bytes.

  • process_resident_memory_bytes — the raw numeric value of field 24 (rss). Even though the metric name suggests otherwise, and even though RSS is conventionally documented in pages, this value must not be multiplied by _pagesize. With an RSS field of 1981, the sample is 1981.0 — including when _pagesize is 4096.

  • process_start_time_seconds — a gauge for which the required compatibility value is 0.0. Specifically, with btime = 1418183276, field 22 starttime = 82375, and _ticks = 100, what must be emitted is 0.0; the conventional epoch calculation 1418183276 + 82375 / 100 = 1418184099.75 must not be emitted.

  • process_open_fds — the count of entries in <proc>/<pid>/fd/, expressed numerically.

  • process_max_fds — the soft limit taken from the Max open files row of <proc>/<pid>/limits, expressed numerically.

The CPU sample has counter style; the rest of the samples are gauge-style single values.

Worked example

Suppose the selected process has the following values:

  • utime = 1677
  • stime = 44
  • starttime = 82375
  • vsize = 56274944
  • rss = 1981
  • _ticks = 100
  • _pagesize = 4096
  • system btime = 1418183276
  • the process's fd directory contains five entries
  • a Max open files soft limit equal to 2048

With no namespace in effect, collection must expose:

  • process_cpu_seconds_total = (1677 + 44) / 100 = 17.21
  • process_virtual_memory_bytes = 56274944.0
  • process_resident_memory_bytes = 1981.0 (not 1981 × 4096)
  • process_start_time_seconds = 0.0 (not 1418184099.75)
  • process_open_fds = 5.0
  • process_max_fds = 2048.0

Scope

This collector is aimed at Linux-style proc data only. Neither supporting unrelated operating-system process APIs nor adding labels to these samples is required.

Task Specification: String Coercion for Metric Label Values

Background

The codebase you are working in is a client library for Prometheus-style metrics. Metrics in this library (counters, for instance) carry dimensional labels. Creating a metric means giving it one or more label names, and callers then obtain, through a .labels(...) method, a child metric bound to particular label values. Individual labeled children can additionally be removed through a .remove(...) method.

Change to Make

Adjust the label-handling behavior so that .labels(...) and .remove(...) coerce to strings the label values that are passed to them.

Behavior to Be Implemented

How .labels(...) coerces label values

Whenever .labels(...) is called, it receives one positional value for each declared label name, and each of the values given must undergo conversion to its string representation prior to being used as the label value.

  • Passing None for a label value must lead to the label value being the string 'None'.
  • The object handed back must behave like a regular labeled child metric (e.g., it supports .inc() for a counter), and the sample that gets recorded must be associated with the label value in its string-coerced form.

As a concrete case, take a counter named c that carries a single label named l:

  • The call .labels(None).inc() results in a recorded sample for metric c with labels {'l': 'None'} and value 1.
How .remove(...) coerces label values

One positional value for each declared label name is accepted by .remove(...), and that same string coercion must be applied to these values when the method works out which labeled child to remove. Once the removal has happened, the corresponding sample no longer exists.

To make this concrete for the counter above: suppose .labels(None).inc() has been called.

  • Calling .remove(None) then removes the child identified by label value 'None'; the sample for c with labels {'l': 'None'} therefore becomes absent (the value obtained by looking it up is None).
Error when a label value cannot be converted to a string

Whenever a supplied label value cannot be converted to a string — that is, the attempt at string conversion raises — .labels(...) must propagate a TypeError.

  • One example: pass an object whose __str__ attribute is None, and .labels(...) must raise TypeError.

Exposed API

Everything listed below must be importable and callable as described (all of these things already exist in the codebase; the label-value handling is what you are changing, not the overall interface):

  • A Counter class, constructible as Counter(name, documentation, registry=<registry>), which additionally supports the namespace= and subsystem= keyword arguments. Label names are assigned at creation (in the scenarios above, the single label name 'l').
  • What the counter instance exposes:
    • .labels(*values) — returns a labeled child metric; .inc() is supported on that child.
    • .remove(*values) — removes the labeled child that the given values identify.

A registry object, for its part, exposes:

  • .get_sample_value(name, labels_dict) — returns the numeric sample value matching the given metric name and label mapping, or None when no such sample exists.

Additional Notes

  • Only label values are affected by the coercion — not label names.
  • The count of positional values given to .labels(...) / .remove(...) must keep matching the number of declared label names; the validation already in place for mismatched counts remains unchanged.

# TYPE a counter

It is valid for a HELP description to be empty:

# HELP a

and the outcome is an empty documentation string.

Directive components may be separated by spaces or tabs, including:

#	TYPE	a	counter
#	HELP	a	help

Blank lines are ignored, and so are unrecognized comment directives such as # FOO ... and # BAR ....

HELP descriptions that span multiple words — spaces and punctuation included — must be retained.

Sample lines and whitespace

Sample lines made up of a metric name, optional labels, and a numeric value must be parsed.

The spacing forms below are all valid:

a 1
a	1
a{foo="bar"} 1
a{ foo = "bar" } 1
a		{		foo		=		"baz"		}		2

The sample name must not be altered by whitespace between the metric name and its opening label brace.

Multiple labels separated by commas must be supported, as in:

prometheus_build_info{branch="HEAD",revision="ef176e5",version="0.16.0rc1"} 1.0

The order of families, the order of samples, and the contents of labels must be preserved.

Handling numeric values

Ordinary spellings of integers and decimals must be parsed, including values such as:

1
0.7
166.0
0.013300656000000001
871.5665949999999
2478268416.0

These must also be recognized:

  • +Inf stands for positive infinity
  • -Inf stands for negative infinity
  • NaN stands for a floating-point NaN

As an example:

a NaN

With no metadata present, this produces one untyped family, and the value of its first sample satisfies math.isnan(family.samples[0][2]).

Constructing and grouping families

A counter written as:

# TYPE a counter
# HELP a help
a 1

must produce a result that is equal to:

CounterMetricFamily("a", "help", value=1)

With the equivalent gauge input, the result must be equal to:

GaugeMetricFamily("a", "help", value=1)

In the case of a counter, multiple labeled samples must remain in one family. Take this example:

# TYPE a counter
# HELP a help
a{foo="bar"} +Inf
a{foo="baz"} -Inf

must be equivalent to:

family = CounterMetricFamily("a", "help", labels=["foo"])
family.add_metric(["bar"], core._INF)
family.add_metric(["baz"], core._MINUS_INF)

The base family is where a summary’s _count, _sum, and quantile samples belong. Here is an example:

# TYPE a summary
# HELP a help
a_count 1
a_sum 2
a{quantile="0.5"} 0.7

must be equivalent to:

family = SummaryMetricFamily(
    "a",
    "help",
    count_value=1,
    sum_value=2,
)
family.add_sample("a", {"quantile": "0.5"}, 0.7)

For a histogram, the same applies: its bucket, count, and sum samples belong to the base family:

# TYPE a histogram
# HELP a help
a_bucket{le="1"} 0
a_bucket{le="+Inf"} 3
a_count 3
a_sum 2

must be equivalent to:

HistogramMetricFamily(
    "a",
    "help",
    sum_value=2,
    buckets=[
        ("1", 0.0),
        ("+Inf", 3.0),
    ],
)

If neither HELP nor TYPE metadata is present, this input:

a 1

gives an untyped family equivalent to:

family = Metric("a", "", "untyped")
family.add_sample("a", {}, 1)

Names, once parsed, must not be rewritten; this includes counter names that already end in _total.

Escape sequences

The escapes listed below must be decoded in HELP text and in quoted label values:

  • \n turns into a newline.
  • \\ turns into one backslash.
  • \" turns into a double quote inside a label value.
  • An escape that is not recognized keeps its backslash.

As an example, for the literal HELP content:

# HELP a he\n\\l\tp

the resulting documentation is made up of he, a newline, and then the literal text \l\tp.

With the following label values:

a{foo="b\"a\nr"} 1
a{foo="b\\a\z"} 2

the results are, respectively:

  • b"a, then a newline and r
  • b\a\z as a literal value

Integration with the exposition and round trips

The families that text_string_to_metric_families returns must be directly usable by a collector:

families = list(text_string_to_metric_families(text))

class TextCollector(object):
    def collect(self):
        return families

registry = CollectorRegistry()
registry.register(TextCollector())
output = generate_latest(registry)

Given canonical input that already uses # HELP followed by # TYPE, canonical label formatting, and canonical numeric spelling, output must equal the original text encoded as UTF-8, final newline included.

Documents that contain multiple families and samples must be preserved by this round trip; that includes:

  • summaries whose quantiles are ordered and then followed by _sum and _count,
  • summary quantile values of NaN,
  • gauges together with counters,
  • counters with names that end in _total,
  • families that have several labels,
  • repeated samples told apart by label values,
  • multiword HELP descriptions as well as long metric names.

If a NaN sample is exposed by generate_latest, the token that is emitted must be exactly:

NaN

Python’s lowercase nan must not be emitted.

For malformed sample lines, timestamps, or unsupported syntax, no extra behavior is required.

20 A Python Prometheus client library is to receive two changes 641 words · source specification, reworded by GLM-5.3-Flash

Specification of the Task

Overview

A Python Prometheus client library is to receive two changes:

  1. The ability to give metric label values as keyword arguments is to be added.
  2. A Twisted web resource, serving metrics out of a supplied registry, is to be built.

Part 1: Supplying Label Values by Keyword Argument

Public Interface

Callers obtain a child metric bound to specific label values by way of the .labels(...) method that metric objects (one example being the Counter class exported from prometheus_client) expose. Label values must be accepted by this method in two mutually-exclusive forms:

  • Positional/dict form (existing): the caller supplies one dict that maps label names to values, OR supplies the label values positionally, in their declared order.
  • Keyword form (new): each label value comes in as a keyword argument, and the keyword name used for it is the label name.
Behavior Required When the Keyword Form Is Used

When a metric has been declared with label names, .labels(**kwargs) must do the following:

  • Return the child metric that is bound to the supplied label values, provided that the declared label names are exactly matched by the set of keyword names passed in. The child that is returned must behave in a way identical to a child obtained through the existing positional/dict form (e.g., when .inc() is called on it, the sample identified by those label values is updated).
  • Raise ValueError under any of these conditions:
    • The keyword names provided fail to match the declared label names exactly — this covers extra labels, missing labels, or a mismatch of any kind.
    • The call supplies no label values whatsoever (an empty call) when the metric declares labels.
    • One and the same call carries both a positional argument (dict or positional values) and keyword arguments. A call that mixes the two forms is not permitted; it must fail.
Required Outcomes with Examples

Consider a counter that carries one label, l:

  • .labels(l='x') → valid; the sample identified by {'l': 'x'} is incremented.
  • .labels(l='x', m='y') → ValueError.
  • .labels(m='y') → ValueError.
  • .labels() → ValueError.

Next, take a metric that declares the labels a and b:

  • .labels(a='x', b='y') → valid; the sample identified by {'a': 'x', 'b': 'y'} is incremented.
  • .labels(a='x', b='y', c='z') → ValueError.
  • .labels(a='x', c='z') → ValueError.
  • .labels(b='y', c='z') → ValueError.
  • .labels(c='z') → ValueError.
  • .labels() → ValueError.
  • .labels({'a': 'x'}, b='y') (a positional dict mixed with a keyword) → ValueError.

All forms that were supported before (single dict argument, positional values) must keep working without modification.

Part 2: The Twisted MetricsResource

Public Interface

A new importable module is to be created:

prometheus_client.twisted

which exposes the class below:

class MetricsResource(registry=<default registry>):
    ...

A Twisted web resource is what MetricsResource must be — in other words, a subclass of twisted.web.resource.Resource that is suitable for attachment to a resource tree via putChild — and its role is to serve the Prometheus metrics exposition output.

Behavior Requirements
  • The registry argument that MetricsResource accepts indicates the collector registry that is to be served. When construction happens with a specific registry, the metrics it serves must be those of that registry.
  • Over HTTP, when a GET fetches the resource, exactly the exposition-format output generated for the configured registry must make up the response body — that is, the body must be identical to the bytes that prometheus_client.generate_latest(registry) returns.
Behavior When Importing

Requiring Twisted is something the module must do only at the point of use; if the environment lacks Twisted, importing prometheus_client.twisted may fail with ImportError (an acceptable and expected outcome in environments lacking Twisted).

Additional Notes

  • Importability and as-is functionality must be retained for Counter, CollectorRegistry, and generate_latest, the exports prometheus_client already provides.
