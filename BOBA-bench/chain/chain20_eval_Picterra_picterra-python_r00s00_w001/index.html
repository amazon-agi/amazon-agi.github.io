Task Specification: Fix Parsing of the Vector Layer Upload Response

Background

A client class (in tests it is instantiated through an internal _client() helper) provides functionality for uploading vector layers to a remote service. The upload process works by polling an operations endpoint until the operation completes; an identifier is then extracted from the completed operation's response.

Required Behavior

The upload_vector_layer Method

The client class must expose a method having the following signature:

def upload_vector_layer(self, <target_id>, <file_path>, <name>) -> str

Here:

  • The first positional argument is a numeric identifier for the target to which the vector layer is being uploaded.
  • The second positional argument is a path to a file on disk that is to be uploaded.
  • The third positional argument is a name for the vector layer.
Behavior of the Method

The method carries out the vector layer upload workflow, part of which is polling an operations endpoint until the operation reaches a completed/successful state. When the operation completes successfully, the method must extract and return the vector layer identifier from the operation's response.

Structure of the Response (the fix)

On successful completion of the operation, the operation response contains a results object (a nested dictionary). The vector layer identifier sits inside this results object, under the key vector_layer_id.

In other words, the identifier must be read from:

<operation_response>["results"]["vector_layer_id"]

not directly from a top-level vector_layer_id field on the operation response.

Returned Value

The method must return the string value found at results.vector_layer_id in the response of the completed operation.

As an example: if a successful operation response carries {"results": {"vector_layer_id": "spam"}}, then upload_vector_layer must return "spam".

Scope of the Change

The only change required is to correct where the vector layer identifier is read from in the successful operation response — it now lives nested under the results key instead of at the top level of the response.

    training_steps=<omitted>,
    backbone=<omitted>,
    tile_size=<omitted>,
    background_sample_ratio=<omitted>,
) -> str

<omitted> stands for an optional-argument state; it is neither a detector setting nor a value to serialize. The default for each configuration argument must be an omitted state. Omission must not cause any client-side configuration value to be synthesized or serialized.

Specifically, the client must not insert legacy defaults such as:

  • output_type="polygon"; or
  • training_steps=500.

Task Specification: Switching List Operations to Page-Based Pagination

Summary

The affected client list operations are to be changed so that they return exactly one API page at a time. A sequence-like paginated result object must wrap each response, and the next page can be explicitly requested from it by callers. Under the previous behavior, every available page was requested and flattened automatically into one list; that behavior is replaced by this change.

The methods affected are:

  • list_rasters
  • list_detectors
  • list_raster_markers
  • list_folder_detectors

Compatibility must otherwise be preserved for existing endpoint selection, filtering, item dictionaries, authentication, and HTTP error behavior. In particular, APIError must still be raised — rather than a page result being returned — when a page request is unsuccessful.

Contract of the Paginated Result

What each affected method returns is a paginated result, and only the response page that was explicitly requested is represented by it. The following public behavior must be provided by the object:

  1. Indexing — the item found at index i of the current page's results array is what result[i] returns. The items stay as the raw dictionaries that the API supplies.
  2. Length — what len(result) returns is the number of items that the current page's results array holds, and not the API's total result count.
  3. Iteration — the current page's items are yielded, in order, when the object is iterated over, list(result) included, and the iteration does not proceed to later pages.
  4. Next-page navigation — a new paginated result for the next page is returned by result.next(); when the current page has no successor, None is returned instead.

No requirement exists for any particular public class name; what serves as the contract is the observable sequence and navigation behavior described above.

Shape of a list response

The JSON object that makes up a list response contains at least the following relevant fields:

  • results: the list made up of the current page's raw item dictionaries.
  • next: a URL string that identifies the next page, or null/None when the current page is the final page.

It is from results and next that pagination behavior must be derived. The current page's length and its navigation behavior are not determined by means of the response's count and previous metadata.

Requests and the behavior of .next()
  • Exactly one HTTP request is performed when an affected list method is called, covering its initial or explicitly selected page.
  • Any later page must not be prefetched as part of returning or constructing a paginated result. After a page has already been returned, indexing, measuring, and iterating over it must not issue further requests.
  • If a non-null URL is what next contains, each call to .next() performs exactly one HTTP request to that URL, and a new paginated result wrapping that response is returned by it. It must not fetch any page beyond that next page.
  • If next is None, .next() returns None, and no HTTP request is issued.
  • The URL supplied in the current response is what navigation follows, its query parameters included.

The service relies on the page_number query parameter, which uses 1-based numbering: page 1 is the first page, and successive pages carry page numbers that increase. Requesting a page directly must return the same page items, in the same order, as are obtained by reaching that page through repeated .next() calls.
