01 Transpiling Reduino Led Declarations 634 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Transpiling Reduino Led Declarations

Overview

You will implement one portion of a Python-to-C++ (Arduino) transpiler that lives inside the Reduino package. Python source code that uses Reduino's high-level actuator helpers is parsed by this transpiler, which emits equivalent Arduino C++ code. The scope of this task is the Led actuator: the behavior of its runtime helper, how it is represented in the transpiler AST, the parsing of its declaration, and the emission of the corresponding C++ code.

Available Test Fixtures

The calling code has two fixtures available, and your implementation's behavior must support them (you do not implement the fixtures themselves, but your API must work with them):

  • A src fixture: takes Python source as a string (which may be indented as a multi-line block) and returns a normalized version suitable for parsing. Your parser must accept the source strings that are passed to it.
  • A norm fixture: takes emitted C++ text and returns a normalized version (whitespace-collapsed) for substring checks. After normalization, your emitter output must contain the required substrings.

Required Public API

1. The Reduino.Actuators module

Supply a class Led:

  • Constructor Led(pin=13) — the pin argument is optional; when it is not supplied, it defaults to 13.
  • The Led keeps an internal boolean on/off state, initialized to False (off).
  • get_state() -> bool — returns the state as it currently is (True = on, False = off).
  • toggle() — flips the current state (on turns into off, off turns into on).
  • The Led's pin is accessible and defaults to 13 when it is not specified.

Behavior expected:

  • A Led() fresh out of construction (or a Led built with any pin) starts in state False.
  • When toggle() is called on a Led whose state is False, the state becomes True; a second toggle() call returns it to False.
2. The Reduino.transpile.ast module

Supply a class LedDecl that represents a parsed Led declaration node in the transpiler AST. Instances must expose:

  • A pin attribute that holds the declared Led's integer pin number.
3. The Reduino.transpile.parser module

Supply a function parse(source: str) that accepts Python source code given as a string and returns a program object.

The program object that is returned must expose an attribute setup_body; this attribute is an iterable (e.g., list) of AST nodes for the statements that belong to the Arduino setup() section.

Required parsing behavior:

  • When the Python source imports Led from Reduino.Actuators and constructs a Led with no arguments (e.g., led = Led()), the setup_body of the resulting program must contain exactly one LedDecl node.
  • The pin attribute of that LedDecl node must be 13 (the default pin, because no pin argument was supplied).
4. The Reduino.transpile.emitter module

Supply a function emit(program) -> str that accepts a program object (of the kind returned by parse) and returns Arduino C++ source code as a string.

Required emission behavior for a Led declared with no arguments:

  • The emitted C++ must include a global declaration of the Led's state. When the Led is assigned to the Python variable led, this is a boolean global initialized to false. After whitespace normalization, the output must contain:
    bool __state_led = false;
    (that is, the global variable is named __state_led, where led is the name of the source variable.)
  • The emitted C++ must include a pinMode call that configures the Led's pin as an output. The output must contain this exact substring:
    pinMode(13, OUTPUT);

Notes

  • Only the no-argument Led() declaration path (which defaults to pin 13) is exercised and required.
  • Naming derived from the variable name: the global state variable is named by prefixing __state_ onto the Python variable name to which the Led is assigned.
02 Adding List Support to the Reduino Transpiler 842 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Adding List Support to the Reduino Transpiler

Task Overview

A Python-to-C++ (Arduino) transpiler must be extended so that it supports Python lists. The transpiler has two public stages, both of which must be modified:

  1. The parser stage: parse(source: str) -> Program
  2. The emitter stage: emit(program) -> str

Both parse and emit can be imported from the transpiler package (the same module from which the existing parse, emit, Program, VarAssign, and ExprStmt symbols have already been imported). The behavior of these stages must be extended so that Python list constructs are handled as described below.

Data Structures Involved (already existing, must be produced correctly)

  • Program — the result of parsing. The attributes relevant here are:
    • .helpers — a container that supports the in operator (e.g. a set/dict of feature names).
    • .global_decls — a list of declaration objects, each of which has attributes .name (str), .c_type (str), and .expr (str).
    • .setup_body — a list of statement nodes.
  • VarAssign — a statement node carrying the attributes .name (str) and .expr (str). It represents assignment to a variable that has already been declared.
  • ExprStmt — a statement node with the attribute .expr (str). It represents a standalone expression used as a statement.

Required Functionality

1. List literal declarations

Assigning a list literal to a new variable in Python, e.g.:

values = [1, 2, 3]

must create a global declaration in which:

  • .name is the variable's name (values).
  • .c_type is __redu_list<int> (the element type is inferred from the literal's elements; integer elements yield int).
  • .expr contains __redu_make_list<int>({1, 2, 3}) (this exact substring, with the elements separated by comma-space inside the braces).

Whenever any list feature is used, the string "list" must be present in Program.helpers.

2. Appending to lists

values.append(4) must result in an ExprStmt in setup_body whose .expr contains __redu_list_append(values, 4).

3. Removing from lists

values.remove(2) must result in an ExprStmt in setup_body whose .expr contains __redu_list_remove(values, 2).

4. Indexed access into a list

Reading an element at an index, e.g.:

total = values[0]

must produce a VarAssign whose .name == "total" and whose .expr contains __redu_list_get(values, 0).

5. List comprehensions over range

A list comprehension of the following form:

other = [i * 2 for i in range(3)]

must produce a VarAssign whose .name == "other" and whose .expr contains __redu_list_from_range<int>.

The complete emitted form of this expression must be:

__redu_list_from_range<int>(0, 3, 1, [&](int i) { return (i * 2); })

where:

  • The three numeric arguments correspond to the range's start, stop, and step. For range(3), the start is 0, the stop is 3, and the step is 1.
  • The final argument is a lambda of the form [&](int <var>) { return (<body>); }, where <var> is the comprehension's loop variable and <body> is the transpiled comprehension expression wrapped in parentheses. For i * 2, the body is (i * 2).
  • The element type parameter (int) is inferred from the comprehension expression.
6. Assigning a list variable to another list variable

Reassigning an existing list variable to another list variable, as in:

values = other

must produce an ExprStmt in setup_body whose .expr contains __redu_list_assign(values, other).

7. List length

len(other) appearing in an assignment context, e.g.:

size = len(other)

must produce a VarAssign whose .name == "size" and whose .expr contains __redu_len(other). In the emitted C++, this must appear in the form static_cast<int>(__redu_len(other)).

Error Cases

In the following cases, the parser (parse) must raise ValueError:

A. Size mismatch on list reassignment

Reassigning a list variable to a list literal of a different length, as in:

values = [1, 2]
values = [3]

must raise ValueError.

B. Element-type mismatch on list reassignment

Reassigning a list variable to a list literal whose elements are of a different type, as in:

values = [1, 2]
values = ["a", "b"]

must raise ValueError.

Requirements for the Emitter Output

When emit is called on a Program that makes use of lists, the produced C++ string must include:

  • The line #include <initializer_list>.
  • List declarations are rendered using __redu_make_list<int>({1, 2, 3}).
  • Append operations are rendered as __redu_list_append(values, 4);.
  • Remove operations are rendered as __redu_list_remove(values, 2);.
  • Indexed reads are rendered using __redu_list_get(values, 0).
  • Comprehensions are rendered as __redu_list_from_range<int>(0, 3, 1, [&](int i) { return (i * 2); }).
  • List-to-list reassignment is rendered as __redu_list_assign(values, other);.
  • Length calls are rendered as static_cast<int>(__redu_len(other)).

(The emitter output may undergo whitespace normalization before these substrings are checked; apart from insignificant surrounding whitespace, the exact substrings above must be present.)

Scope and Notes

  • The only list constructs that need to work are the ones described above. Element type inference is required only for lists with integer elements (int), as exercised above.
  • Do not modify unrelated existing behavior (e.g. existing variable, string, f-string, or function support must keep working as before).

Specification of the Task

You are making a modification to a source-to-C++ transpiler. What is being changed is the manner in which list literals are lowered into C++ code. At the moment, list construction is emitted with a C++ std::initializer_list (brace-enclosed) argument; the change you must make is to pass the list elements as direct variadic arguments instead.

Behavior Change Required

When a list literal such as [1, 2, 3] (a list of integers) is processed, the transpiler must lower it to a call to the helper __redu_make_list where:

  • The element type is supplied as a template argument (e.g. __redu_make_list<int>).
  • The list elements are passed as separate, comma-separated positional arguments; they are NOT wrapped in curly braces / an initializer list.

To be specific, the three-element integer list literal [1, 2, 3] must lower to exactly:

__redu_make_list<int>(1, 2, 3)

and the brace-wrapped form __redu_make_list<int>({1, 2, 3}) must not be produced.

Requirements for Emitter Output

The C++ output that is generated must:

  • Contain the direct-argument form __redu_make_list<int>(1, 2, 3) for the list literal that corresponds to it.
  • Not include #include <initializer_list>. The list-construction helper must no longer be dependent on <initializer_list>, and, for this feature, the emitter must not emit that include.

The following list-operation lowerings, which already exist, must remain unchanged and continue to appear in the output:

  • __redu_list_append(values, 4);
  • __redu_list_remove(values, 2);
  • __redu_list_get(values, 0)
Requirements for the Parser / Intermediate Representation

For a global declaration that is bound to a list literal:

  • For a list-of-int, the declaration's inferred C++ type (its c_type attribute) must be __redu_list<int>.
  • The initializer expression of the declaration (its expr attribute) must contain the direct-argument form __redu_make_list<int>(1, 2, 3) (once again, not the brace-wrapped form).

Global declarations remain accessible by name (via their name attribute) from the parsed program's collection of global declarations.

Scope

The only parts affected are the lowering of list literals from the brace/initializer-list form to the direct variadic-argument form, together with the removal of the now-unnecessary <initializer_list> include. All other transpilation behavior, the append/remove/get list operations and the declared list type included, must be preserved.

Task Specification: Connecting SerialMonitor to a Physical Serial Port

Summary

The task is to implement a SerialMonitor class in the module Reduino.Utils for communicating with a physical serial port. It must be possible to import the class as:

from Reduino.Utils import SerialMonitor

Dependency on the Serial Library

Inside the module Reduino.Utils, the serial library must be referenced through a module-level name serial. That name is looked up at runtime (it is not captured at definition time), so that operations use whatever object Reduino.Utils.serial currently refers to. Whenever a serial connection is opened, creating it must be done via a call to serial.Serial(...).

The Constructor

SerialMonitor(baud_rate=..., port=..., timeout=...)

Parameters:

  • baud_rate (first positional argument) — the connection's baud rate. When it is not provided, it must default to a reasonable value (the class must be constructible with no arguments and with only baud_rate given positionally).
  • port — the identifier of the serial port (e.g. a device path string). Optional; it may be omitted or left unset.
  • timeout — the read timeout, in seconds. Optional.

Behavior:

  • The baud_rate that is provided must be exposed as a public attribute monitor.baud_rate.
  • The port that is provided must be exposed as a public attribute monitor.port.
  • If baud_rate is not strictly positive (e.g. 0), the constructor must raise ValueError.
  • Constructing an instance must not open the serial port immediately, and it must succeed even when Reduino.Utils.serial is None.

Opening and Using the Connection

Whenever a serial connection is needed and a port was configured, that connection must be created via:

serial.Serial(port=<port>, baudrate=<baud_rate>, timeout=<timeout>)

passing keyword arguments with exactly these names (port, baudrate, timeout) and the corresponding configured values.

The write(text) Method

monitor.write(text: str) -> ...
  • The given text is sent over the serial port.
  • The text must be transmitted as bytes — encoded to bytes — with a single trailing newline ("\n") appended. For the input "ping", the bytes written to the serial port must be exactly b"ping\n".
  • The write is carried out by calling the serial object's write(payload: bytes) method.

The read() Method

monitor.read() -> str
  • Reads one line from the serial port via a call to the serial object's readline() method, which returns bytes.
  • The returned bytes are decoded to a str, and trailing line-ending/whitespace characters are stripped (both \r and \n must be removed). For raw bytes b"hello world\r\n", the string that is returned must be "hello world".
  • When readline() returns empty bytes (b""), read() must return the empty string "".
  • Each call to read() (including a call that returns the empty string) must print the resulting string, followed by a newline, to standard output. If the read result is "hello world", standard output must receive exactly "hello world\n".
  • Error condition: If no serial connection is available because establishing one is impossible (i.e. no serial port is configured / the serial library is unavailable), read() must raise RuntimeError whose message contains the text No serial port configured.

Notes About the Serial Object Interface

The serial object that comes back from serial.Serial(...) provides:

  • write(payload: bytes) -> int
  • readline() -> bytes
  • close() -> None
  • an is_open attribute

Of that interface, only write and readline are required to be exercised by the write/read methods described above.

Specification for the Task

The object returned by parse(...) exposes at least the attributes below:

08 The Led class in the Reduino.Actuators module is to be extended with brightness control plus several timing-based animation helpers. 762 words · source specification, reworded by GLM-5.3-Flash

Task: Provide Advanced LED Control Helpers

Summary

The Led class in the Reduino.Actuators module is to be extended with brightness control plus several timing-based animation helpers. The behavior Led already provides (construction, on/off, toggle, get_state) must be preserved.

Context and Dependencies

  • The Led class is found at Reduino.Actuators.Led and can be constructed with no arguments: Led().
  • The module Reduino.Actuators refers to a Sleep symbol (i.e. Reduino.Actuators.Sleep) that is used to perform delays. The timing helpers below must obtain the sleep utility through this module-level Sleep name so that it can be substituted.
    • A Sleep is constructed as Sleep(duration, sleep_func=...), where duration is an integer number of milliseconds, and the object produced exposes a wait() method that performs the delay. Each delay in the helpers below must be carried out by constructing a Sleep(duration) and calling its wait().

State Requirements

In addition to its on/off state, the Led must track a numeric brightness:

  • get_state() -> bool — pre-existing behavior; returns whether the LED is currently on.
  • get_brightness() -> int — returns the brightness value currently held (0–255).

How state and brightness relate:

  • A brightness of 0 corresponds to state False (off).
  • Any brightness greater than 0 corresponds to state True (on).

Methods to Implement

set_brightness(value: int) -> None
  • Assigns value as the current brightness.
  • Brings the on/off state in line with it: the state becomes False when value == 0, and True when value > 0.
  • The valid range spans 0 through 255 inclusive. A value outside this range (e.g. 300) must raise ValueError.
blink(duration_ms: int, times: int) -> None
  • Makes the LED blink times times. A single blink turns the LED on, waits, turns it off, and waits — i.e. each blink performs two delays of duration_ms each (on-phase delay and off-phase delay).
  • Every delay takes duration_ms as its duration. With times blinks there must be exactly 2 * times delays, each equal to duration_ms.
  • After the blinking completes, the LED must be off: get_state() is False and get_brightness() is 0.
fade_in(step: int, delay_ms: int) -> None
  • Increases the brightness gradually from its current level up to full brightness (255), adding step each iteration and delaying delay_ms between steps.
  • After the fade completes, the LED is on with brightness exactly 255 (state True).
  • Every delay that is performed uses delay_ms as its duration.
  • step must be a positive integer; a step of 0 or negative must raise ValueError.
fade_out(step: int, delay_ms: int) -> None
  • Decreases the brightness gradually from its current level down to 0, subtracting step each iteration and delaying delay_ms between steps.
  • After the fade completes, the LED is off with brightness exactly 0 (state False).
  • Every delay that is performed uses delay_ms as its duration.
  • step must be a positive integer; a step of 0 or negative must raise ValueError.
flash_pattern(pattern: list[int], delay_ms: int) -> None
  • Steps through each brightness value in pattern in sequence, setting the brightness to each value in turn.
  • A delay of delay_ms is carried out between consecutive values (not after the final value). With a pattern of length n, exactly n - 1 delays are performed, each equal to delay_ms.
  • After the pattern has been applied, the LED reflects the final value in the pattern. (For a pattern that ends in 0, this means state False and brightness 0.)
  • Every value in pattern falls under the same validity range as set_brightness (0–255). If any value is out of range (e.g. 300), a ValueError must be raised.

Signatures

At call sites using keyword arguments, the following parameter names must be supported:

  • set_brightness(value)
  • get_brightness()
  • blink(duration_ms, times)
  • fade_in(step, delay_ms)
  • fade_out(step, delay_ms)
  • flash_pattern(pattern, delay_ms)

The delay_ms of fade_in, fade_out, and flash_pattern, together with step/duration_ms/times, should have sensible defaults or be freely callable both positionally and by keyword as shown above (e.g. set_brightness(128), blink(duration_ms=50, times=2), fade_in(step=50, delay_ms=5), fade_out(step=50, delay_ms=5), flash_pattern([1, 0, 128, 0], delay_ms=25), fade_in(step=0), fade_out(step=-1), flash_pattern([300])).

Timing Notes

All delays must be issued via construction of the module-level Sleep type with the integer millisecond duration, followed by invoking wait() on it, so that replacing Reduino.Actuators.Sleep changes the timing behavior. For each helper, the number of delays and their duration is as specified above and must match exactly.

Constraints

  • The existing Led API surface, as well as the behaviors already provided, must not be changed.
  • Nothing beyond the behavior described here is required.

  • The emit="mcu" mode is MCU-only. At host runtime it must return "" without calling the serial connection's line-reading operation and without printing anything. Serial input that is still pending must remain unconsumed and stay available to a later "host" or "both" read.

Parser Behavior and the Transpiled Expression

parse already recognizes read calls made on a declared SerialMonitor and supports assignments such as:

from Reduino.Utils import SerialMonitor

monitor = SerialMonitor()
payload = monitor.read(...)

Within the parsed program, the assigned expression must depend on emit in the following way:

Mode in the source Expression string emitted
"host" ""
"mcu" Serial.readStringUntil('\n')
"both" Serial.readStringUntil('\n')
Argument not provided Serial.readStringUntil('\n')

These mappings apply regardless of whether the mode is supplied positionally or by keyword. In particular:

  • Both monitor.read("host") and monitor.read(emit="host") emit the empty C++ string literal ""; as a result, no MCU serial read is generated for that value.
  • monitor.read("mcu") together with monitor.read(emit="mcu") emit Serial.readStringUntil('\n').
  • An explicit "both" and the default taken when no argument is passed emit Serial.readStringUntil('\n'), which preserves the existing generated behavior.

The parser's variable-assignment node must keep exposing:

  • name: the name of the assigned variable.
  • expr: the exact emitted expression string selected as described above.

For top-level source like the example above, the assignment remains in the parsed program's setup portion (prog.setup_body). The read expression continues to represent a string value.

Compatibility Expectations

  • Pre-existing calls to read() with no arguments retain "both" behavior.
  • For modes that perform a host read, the existing serial-port configuration errors and the host line-reading behavior remain unchanged.
  • For "mcu", the runtime and transpilation semantics are intentionally asymmetric: direct Python execution performs no host read and returns "", whereas transpilation generates the MCU serial-read expression.

Task: Build an RGBLed Actuator Helper

Goal

A new public class RGBLed is to be added to the Reduino.Actuators module. It must be importable as:

from Reduino.Actuators import RGBLed

The class models an RGB LED driven by three pins (red, green, blue), and it tracks a color state and an on/off state. For timing delays it relies on the existing Sleep helper (Reduino.Actuators.Sleep).

Constructor

RGBLed(red_pin, green_pin, blue_pin)
  • Every pin argument must be an int. When any pin argument is not an int, raise TypeError.
    • Note: bool should not be handled as a valid pin type distinct from this rule; standard int-type checking is expected. (Only genuine ints are valid.)
  • Every pin must be a non-negative integer (>= 0). When any pin is negative, raise ValueError.
  • For the given inputs, pin type validation takes precedence appropriately (a non-int pin raises TypeError).

Initial state once construction has finished:

  • The pins attribute is equal to the tuple (red_pin, green_pin, blue_pin).
  • The color currently set is (0, 0, 0).
  • The on/off state is False.

Accessors for State

  • get_color() → returns the color currently held as a 3-tuple (r, g, b) of ints.
  • get_state() → returns a bool: True when the LED is regarded as on, False when it is off.

Rules for Validating Colors (shared by every color-setting method)

In any method that accepts red/green/blue channel values:

  • Every channel value must be an int. When any channel is not an int (e.g. a float), raise TypeError.
  • Every channel value must sit within the inclusive range 0–255. When any channel is out of range, raise ValueError.

Methods

set_color(r, g, b)
  • Validates r, g, b according to the color validation rules above.
  • The current color is updated to (r, g, b).
  • The on/off state is not changed.
on(r, g, b)
  • Validates r, g, b against the color validation rules.
  • The current color is set to (r, g, b).
  • The on/off state is set to True.
off()
  • The current color is set to (0, 0, 0).
  • The on/off state is set to False.
fade(r, g, b, duration_ms=..., steps=...)

Transitions gradually to the target color (r, g, b) across a number of steps, sleeping between steps.

  • r, g, b are validated against the color validation rules.
  • duration_ms must be >= 0; when negative, raise ValueError.
  • steps must be >= 1; when the value is 0 (or less), raise ValueError.
  • Behavior when the inputs are valid:
    • The fade is performed using Sleep instances for the delays. For each delay, a Sleep object is constructed with the per-step delay duration and its wait() method is then called.
    • The per-step delay given to Sleep is a float equal to duration_ms / steps.
    • The count of sleep delays performed is steps - 1 (delays happen between steps, not after the final step). For example, duration_ms=40, steps=4 produces three delays of 10.0 each.
    • After the fade finishes, the current color equals the target color (r, g, b) and the on/off state is True.
  • Sleep is referenced through the module-level name Sleep in Reduino.Actuators (so it must be constructed as Sleep(duration) with the duration as a positional argument; the wait() method is then invoked on it).
blink(r, g, b, times=..., delay_ms=...)

Blinks the LED to color (r, g, b) a specified number of times, then restores the color that was set before blinking.

  • r, g, b are validated against the color validation rules.
  • times must be >= 1; when the value is 0 (or less), raise ValueError.
  • delay_ms must be >= 0; when negative, raise ValueError.
  • Behavior when the inputs are valid:
    • Before blinking, the current color is recorded.
    • In each blink cycle, the LED is turned to the target color and then off, with a delay after each. The total number of delays is times * 2, each one performed by constructing a Sleep with the delay_ms value (as passed, an int) and calling its wait(). For example, times=2, delay_ms=25 produces four delays of 25 each.
    • After the blinking finishes, the current color is restored to whatever it was immediately before blink was called.

Notes on How Sleep Is Used

Every timed delay in fade and blink must pass through the module-level Sleep symbol in Reduino.Actuators, which is constructed positionally with the delay value and driven by calling .wait(). This symbol must be resolvable/patchable at Reduino.Actuators.Sleep.

Summary of Validation Ordering

  • Type errors (TypeError) apply to non-int pins/channels.
  • Value errors (ValueError) apply to out-of-range pins, out-of-range channels, negative durations/delays, and non-positive steps/times.

Task: Add Support for the RGB LED Actuator to the Reduino Transpiler

Overview

The Reduino transpiler takes a Python-like source language and translates it into Arduino C++ code. Support for an RGBLed actuator must be added at two stages of the pipeline: the parser (which builds an AST) and the emitter (which turns that AST into C++ text).

In the relevant source language, objects imported via from Reduino.Actuators import RGBLed are recognized; they are then constructed and manipulated through method calls.

Part 1: New AST Node Types

Within the module Reduino.transpile.ast, define the new AST node classes listed below, all of them importable by name:

  • RGBLedDecl — models the construction of an RGB LED. It must expose the attributes red_pin, green_pin, and blue_pin.
  • RGBLedSetColor — models a set_color(...) call.
  • RGBLedOn — models an on() call.
  • RGBLedOff — models an off() call.
  • RGBLedFade — models a fade(...) call. It must expose the attributes duration_ms and steps.
  • RGBLedBlink — models a blink(...) call. It must expose the attributes times and delay_ms.

Beyond that, each node should retain whatever additional data (e.g. the variable name it applies to, and color arguments) is needed by the emitter described below.

Part 2: Parser Stage

In Reduino.transpile.parser, the function parse(source) returns a program object having a setup_body attribute (a list of AST nodes). The parser must recognize the statements listed below and produce their corresponding AST nodes within setup_body, in source order.

Construction
rgb = RGBLed(3, 4, 5)

This statement produces an RGBLedDecl. Its positional arguments map to red_pin, green_pin, and blue_pin, respectively.

Keyword arguments are supported as well:

rgb = RGBLed(red_pin=base + 1, green_pin=base + 2, blue_pin=base + 3)
Representing pin values
  • When a pin argument is a literal integer, it is stored as an int (e.g. RGBLed(3, 4, 5) → red_pin == 3, green_pin == 4, blue_pin == 5).
  • When the pin expression is non-literal (symbolic), it is stored as a string holding the expression wrapped in a single pair of parentheses, with a single space around binary operators. For instance, red_pin=base + 1 → red_pin == "(base + 1)", and likewise "(base + 2)", "(base + 3)".
Method calls

For an RGB LED object bound to a variable (e.g. rgb), each of the following method calls produces one AST node:

  • rgb.set_color(r, g, b) → RGBLedSetColor
  • rgb.on() → RGBLedOn
  • rgb.off() → RGBLedOff
  • rgb.fade(r, g, b, duration_ms=..., steps=...) → RGBLedFade, with duration_ms and steps holding the integer values of the corresponding keyword arguments (e.g. duration_ms=750, steps=5 → duration_ms == 750, steps == 5).
  • rgb.blink(r, g, b, times=..., delay_ms=...) → RGBLedBlink, with times and delay_ms holding the integer values of the corresponding keyword arguments (e.g. times=2, delay_ms=150 → times == 2, delay_ms == 150).

Part 3: Emitter Stage

The emitter (invoked as emit(parse(source)), which returns the C++ source text as a string) must generate the C++ shown below from the RGB LED AST nodes.

Notation for what follows: take an RGB LED variable named <var> (e.g. rgb) whose red/green/blue pins are <R>, <G>, <B>.

Global state variables

For each declared RGB LED, emit the global declarations shown below:

bool __rgb_state_<var> = false;
int __rgb_red_<var> = 0;

(Green and blue current-value globals that follow the same __rgb_green_<var> / __rgb_blue_<var> naming are used by the analog writes below.)

Setting up pins

For each declared RGB LED, set up all three pins as outputs:

pinMode(<R>, OUTPUT);
pinMode(<G>, OUTPUT);
pinMode(<B>, OUTPUT);

Where a pin value was stored as a symbolic expression string, it must be emitted literally as that string (without the surrounding quotes) in place of the numeric pin.

Writing a color (set_color)

Applying a color to the LED emits analog writes to each pin that use the current-value globals:

analogWrite(<R>, __rgb_red_<var>);
analogWrite(<G>, __rgb_green_<var>);
analogWrite(<B>, __rgb_blue_<var>);
Fade

A fade emits a stepped loop that ramps toward the target color across the given number of steps, delays between the steps, and updates the pins via the current-value globals. The generated code must contain:

for (int __redu_i = 1; __redu_i <= __redu_steps; ++__redu_i) {

Within that loop, the color is written using analogWrite(<R>, __rgb_red_<var>); … analogWrite(<B>, __rgb_blue_<var>); and a delay(__redu_delay_ms); is issued.

Blink

A blink emits a counted loop that toggles the LED on and off a number of times, with a delay between transitions. The generated code must contain:

for (int __redu_i = 0; __redu_i < __redu_times; ++__redu_i) {

a declaration for tracking the delay:

unsigned long __redu_delay_ms = 0UL;

and delay(__redu_delay_ms); calls, along with analog writes to the pins that use the current-value globals.

Notes

  • The parser and emitter must continue to support existing actuators without change; RGB LED support is additive.
  • Every one of the named AST classes must be importable directly from Reduino.transpile.ast.
  • When some emitter output is compared, whitespace normalization is applied, so the exact spacing between tokens in the generated C++ is not critical except where a specific normalized form is shown; however, statements involving pinMode, analogWrite, and the two for loop headers are matched against raw output and must appear exactly as shown above (with the appropriate pin/variable substitutions).
