Task Specification: Reduino Led Declaration Transpilation

Overview

You are implementing part of a Python-to-C++ (Arduino) transpiler within the Reduino package. The transpiler parses Python source code that uses Reduino's high-level actuator helpers and emits equivalent Arduino C++ code. This task covers the Led actuator: its runtime helper behavior, its representation in the transpiler AST, parsing of its declaration, and emission of the corresponding C++ code.

Test Fixtures Available

Two fixtures are available to the calling code and must be supported by your implementation's behavior (you do not implement the fixtures themselves, but your API must work with them):

  • A src fixture: takes a string of Python source (which may be indented as a multi-line block) and returns a normalized version suitable for parsing. Your parser must accept the source strings passed to it.
  • A norm fixture: takes emitted C++ text and returns a normalized version (whitespace-collapsed) for substring checks. Your emitter output must contain the required substrings after normalization.

Required Public API

1. Reduino.Actuators module

Provide a class Led:

  • Constructor Led(pin=13) — the pin argument is optional and defaults to 13.
  • The Led maintains an internal on/off boolean state, initialized to False (off).
  • get_state() -> bool — returns the current state (True = on, False = off).
  • toggle() — flips the current state (on becomes off, off becomes on).
  • The pin used by the Led is accessible/defaults to 13 when not specified.

Expected behavior:

  • A freshly constructed Led() (or Led with any pin) starts in state False.
  • Calling toggle() on a Led in state False sets it to True; calling toggle() again returns it to False.
2. Reduino.transpile.ast module

Provide a class LedDecl representing a parsed Led declaration node in the transpiler AST. Instances must expose:

  • A pin attribute holding the integer pin number for the declared Led.
3. Reduino.transpile.parser module

Provide a function parse(source: str) that accepts a string of Python source code and returns a program object.

The returned program object must expose an attribute setup_body, which is an iterable (e.g., list) of AST nodes representing statements that belong to the Arduino setup() section.

Parsing behavior required:

  • Given Python source that imports Led from Reduino.Actuators and constructs a Led with no arguments (e.g., led = Led()), the resulting program's setup_body must contain exactly one LedDecl node.
  • That LedDecl node's pin attribute must be 13 (the default pin, since no pin argument was supplied).
4. Reduino.transpile.emitter module

Provide a function emit(program) -> str that accepts a program object (as returned by parse) and returns a string of Arduino C++ source code.

Emission behavior required for a Led declared with no arguments:

  • The emitted C++ must include a global state declaration for the Led. For a Led assigned to the Python variable led, this is a boolean global initialized to false. After whitespace normalization, the output must contain:
    bool __state_led = false;
    (i.e., the global variable name is __state_led where led is the source variable name.)
  • The emitted C++ must include a pinMode call configuring the Led's pin as an output. The output must contain the exact substring:
    pinMode(13, OUTPUT);

Notes

  • Only the no-argument Led() declaration path (defaulting to pin 13) is exercised and required.
  • Variable-name-derived naming: the global state variable is named by prefixing __state_ to the Python variable name the Led is assigned to.
02 Add List Support to the Reduino Transpiler 778 words · source specification

Task Specification: Add List Support to the Reduino Transpiler

Overview

You must extend a Python-to-C++ (Arduino) transpiler to support Python lists. The transpiler has two public stages that must be modified:

  1. A parser stage: parse(source: str) -> Program
  2. An emitter stage: emit(program) -> str

Both parse and emit are importable from the transpiler package (the same module from which the existing parse, emit, Program, VarAssign, and ExprStmt symbols are already imported). You must extend their behavior to handle Python list constructs as described below.

Relevant Data Structures (already existing, must be produced correctly)

  • Program — the parse result. It has the following attributes that are relevant here:
    • .helpers — a container supporting the in operator (e.g. a set/dict of feature names).
    • .global_decls — a list of declaration objects, each with attributes .name (str), .c_type (str), and .expr (str).
    • .setup_body — a list of statement nodes.
  • VarAssign — a statement node with attributes .name (str) and .expr (str). Represents assignment to an already-declared variable.
  • ExprStmt — a statement node with attribute .expr (str). Represents a standalone expression used as a statement.

Required Behavior

1. List literal declaration

A Python assignment of a list literal to a new variable, e.g.:

values = [1, 2, 3]

must create a global declaration where:

  • .name is the variable name (values).
  • .c_type is __redu_list<int> (element type inferred from the literal's elements; integer elements yield int).
  • .expr contains __redu_make_list<int>({1, 2, 3}) (the exact substring, with the elements comma-space separated inside the braces).

When any list feature is used, the string "list" must be present in Program.helpers.

2. Appending to a list

values.append(4) must produce an ExprStmt in setup_body whose .expr contains __redu_list_append(values, 4).

3. Removing from a list

values.remove(2) must produce an ExprStmt in setup_body whose .expr contains __redu_list_remove(values, 2).

4. Indexing a list

Reading an element by index, e.g.:

total = values[0]

must produce a VarAssign with .name == "total" and .expr containing __redu_list_get(values, 0).

5. List comprehension over range

A list comprehension of the form:

other = [i * 2 for i in range(3)]

must produce a VarAssign with .name == "other" whose .expr contains __redu_list_from_range<int>.

The full emitted form of this expression must be:

__redu_list_from_range<int>(0, 3, 1, [&](int i) { return (i * 2); })

where:

  • The three numeric arguments are the range's start, stop, and step. For range(3), start is 0, stop is 3, step is 1.
  • The final argument is a lambda [&](int <var>) { return (<body>); } where <var> is the comprehension loop variable and <body> is the transpiled comprehension expression, parenthesized. For i * 2, the body is (i * 2).
  • The element type parameter (int) is inferred from the comprehension expression.
6. Assigning one list variable to another

Reassigning an existing list variable to another list variable:

values = other

must produce an ExprStmt in setup_body whose .expr contains __redu_list_assign(values, other).

7. Length of a list

len(other) used in an assignment context, e.g.:

size = len(other)

must produce a VarAssign with .name == "size" whose .expr contains __redu_len(other). In the emitted C++, this must appear as static_cast<int>(__redu_len(other)).

Error Conditions

The parser (parse) must raise ValueError in the following cases:

A. List reassignment size mismatch

Reassigning a list variable to a list literal of a different length:

values = [1, 2]
values = [3]

must raise ValueError.

B. List reassignment element-type mismatch

Reassigning a list variable to a list literal whose elements have a different type:

values = [1, 2]
values = ["a", "b"]

must raise ValueError.

Emitter Output Requirements

When emit is called on a Program that uses lists, the produced C++ string must include:

  • The line #include <initializer_list>.
  • List declarations rendered using __redu_make_list<int>({1, 2, 3}).
  • Append operations rendered as __redu_list_append(values, 4);.
  • Remove operations rendered as __redu_list_remove(values, 2);.
  • Indexed reads rendered using __redu_list_get(values, 0).
  • Comprehensions rendered as __redu_list_from_range<int>(0, 3, 1, [&](int i) { return (i * 2); }).
  • List-to-list reassignment rendered as __redu_list_assign(values, other);.
  • Length calls rendered as static_cast<int>(__redu_len(other)).

(The emitter output may be subjected to whitespace normalization before these substrings are checked; the exact substrings above, aside from insignificant surrounding whitespace, must be present.)

Notes / Scope

  • Only the list constructs described above need to work. Element type inference is required only for integer element lists (int) as exercised above.
  • Do not change unrelated existing behavior (e.g. existing variable, string, f-string, or function support must continue to work as before).

Required Behavior Change

When the transpiler processes a list literal such as [1, 2, 3] (a list of integers), it must lower it to a call to the helper __redu_make_list where:

  • The element type is passed as a template argument (e.g. __redu_make_list<int>).
  • The list elements are passed as separate, comma-separated positional arguments — NOT wrapped in curly braces / an initializer list.

Specifically, a three-element integer list literal [1, 2, 3] must lower to exactly:

__redu_make_list<int>(1, 2, 3)

and must not produce the brace-wrapped form __redu_make_list<int>({1, 2, 3}).

Emitter Output Requirements

The generated C++ output must:

  • Contain the direct-argument form __redu_make_list<int>(1, 2, 3) for the corresponding list literal.
  • Not include #include <initializer_list>. The list-construction helper must no longer depend on <initializer_list>, and the emitter must not emit that include for this feature.

The following existing list-operation lowerings must remain unchanged and continue to appear in the output:

  • __redu_list_append(values, 4);
  • __redu_list_remove(values, 2);
  • __redu_list_get(values, 0)

For a global declaration bound to a list literal:

  • The declaration's inferred C++ type (c_type attribute) for a list-of-int must be __redu_list<int>.
  • The declaration's initializer expression (expr attribute) must contain the direct-argument form __redu_make_list<int>(1, 2, 3) (again, not the brace-wrapped form).

Global declarations continue to be accessible by name (via their name attribute) from the parsed program's collection of global declarations.

Scope

Only the lowering of list literals from the brace/initializer-list form to the direct variadic-argument form is affected, along with the removal of the now-unnecessary <initializer_list> include. All other transpilation behavior, including the append/remove/get list operations and the declared list type, must be preserved.

08 Extend the Led class in the Reduino.Actuators module with brightness control and several timing-based animation helpers. 723 words · source specification

Task: Add Advanced LED Control Helpers

Overview

Extend the Led class in the Reduino.Actuators module with brightness control and several timing-based animation helpers. The existing Led behavior (construction, on/off, toggle, get_state) must be preserved.

Context / Dependencies

  • The Led class lives at Reduino.Actuators.Led and can be constructed with no arguments: Led().
  • The module Reduino.Actuators references a Sleep symbol (i.e. Reduino.Actuators.Sleep) which is used to perform delays. Timing helpers below must obtain the sleep utility through this module-level Sleep name so it can be substituted.
    • Sleep is constructed as Sleep(duration, sleep_func=...) where duration is an integer number of milliseconds, and the resulting object exposes a wait() method that performs the delay. Each delay in the helpers below must be realized by constructing a Sleep(duration) and calling its wait().

Required State

The Led must track a numeric brightness in addition to its on/off state:

  • get_state() -> bool — existing behavior; returns whether the LED is currently on.
  • get_brightness() -> int — returns the current brightness value (0–255).

The relationship between state and brightness:

  • Brightness 0 corresponds to state False (off).
  • Any brightness greater than 0 corresponds to state True (on).

Required Methods

set_brightness(value: int) -> None
  • Sets the current brightness to value.
  • Updates the on/off state accordingly: state becomes False when value == 0, and True when value > 0.
  • Valid range is 0 through 255 inclusive. A value outside this range (e.g. 300) must raise ValueError.
blink(duration_ms: int, times: int) -> None
  • Blinks the LED times times. Each blink turns the LED on, waits, turns it off, and waits — i.e. each blink performs two delays of duration_ms each (on-phase delay and off-phase delay).
  • Every delay uses duration_ms as its duration. For times blinks there must be exactly 2 * times delays, each equal to duration_ms.
  • After completion the LED must be off: get_state() is False and get_brightness() is 0.
fade_in(step: int, delay_ms: int) -> None
  • Gradually increases brightness from its current level up to full brightness (255), incrementing by step each iteration, and delaying delay_ms between steps.
  • After completion the LED is on with brightness exactly 255 (state True).
  • Each delay performed uses delay_ms as its duration.
  • step must be a positive integer; a step of 0 or negative must raise ValueError.
fade_out(step: int, delay_ms: int) -> None
  • Gradually decreases brightness from its current level down to 0, decrementing by step each iteration, and delaying delay_ms between steps.
  • After completion the LED is off with brightness exactly 0 (state False).
  • Each delay performed uses delay_ms as its duration.
  • step must be a positive integer; a step of 0 or negative must raise ValueError.
flash_pattern(pattern: list[int], delay_ms: int) -> None
  • Applies each brightness value in pattern in sequence, setting the brightness to each value in turn.
  • A delay of delay_ms is performed between consecutive values (not after the final value). For a pattern of length n, exactly n - 1 delays are performed, each equal to delay_ms.
  • After completion the LED reflects the final value in the pattern. (For a pattern ending in 0, this means state False and brightness 0.)
  • Every value in pattern is subject to the same validity range as set_brightness (0–255). If any value is out of range (e.g. 300), a ValueError must be raised.

Method Signatures

Where keyword arguments are used at call sites, the following parameter names must be supported:

  • set_brightness(value)
  • get_brightness()
  • blink(duration_ms, times)
  • fade_in(step, delay_ms)
  • fade_out(step, delay_ms)
  • flash_pattern(pattern, delay_ms)

delay_ms in fade_in, fade_out, and flash_pattern, and step/duration_ms/times should have sensible defaults or be freely callable both positionally and by keyword as shown above (e.g. set_brightness(128), blink(duration_ms=50, times=2), fade_in(step=50, delay_ms=5), fade_out(step=50, delay_ms=5), flash_pattern([1, 0, 128, 0], delay_ms=25), fade_in(step=0), fade_out(step=-1), flash_pattern([300])).

Notes on Timing

All delays must be issued by constructing the module-level Sleep type with the integer millisecond duration and invoking wait() on it, so that replacing Reduino.Actuators.Sleep changes the timing behavior. The number and duration of delays for each helper is as specified above and must match exactly.

Constraints

  • Do not change the existing Led API surface or the behaviors already provided.
  • No behavior beyond what is described here is required.

on(r, g, b)
  • Validates r, g, b per the color validation rules.
  • Sets the current color to (r, g, b).
  • Sets the on/off state to True.
off()
  • Sets the current color to (0, 0, 0).
  • Sets the on/off state to False.
fade(r, g, b, duration_ms=..., steps=...)

Gradually transitions to the target color (r, g, b) over a number of steps, sleeping between steps.

  • r, g, b are validated per the color validation rules.
  • duration_ms must be >= 0; if negative, raise ValueError.
  • steps must be >= 1; if 0 (or less), raise ValueError.
  • Behavior when valid:
    • Performs the fade using Sleep instances for delays. For each delay, a Sleep object is constructed with the per-step delay duration and then its wait() method is called.
    • The per-step delay passed to Sleep is a float equal to duration_ms / steps.
    • The number of sleep delays performed is steps - 1 (delays occur between steps, not after the final step). For example, duration_ms=40, steps=4 produces three delays of 10.0 each.
    • After completion, the current color equals the target color (r, g, b) and the on/off state is True.
  • Sleep is referenced via the module-level name Sleep in Reduino.Actuators (so it must be constructed as Sleep(duration) with the duration as a positional argument; the wait() method is then invoked on it).
blink(r, g, b, times=..., delay_ms=...)

Blinks the LED to color (r, g, b) a given number of times, then restores the color that was set before blinking.

  • r, g, b are validated per the color validation rules.
  • times must be >= 1; if 0 (or less), raise ValueError.
  • delay_ms must be >= 0; if negative, raise ValueError.
  • Behavior when valid:
    • Records the current color before blinking.
    • For each blink cycle, the LED is turned to the target color and then off, with a delay after each. This results in times * 2 total delays, each performed by constructing a Sleep with the delay_ms value (as passed, an int) and calling its wait(). For example, times=2, delay_ms=25 produces four delays of 25 each.
    • After completion, the current color is restored to whatever it was immediately before blink was called.

Notes on Sleep Usage

All timed delays in fade and blink must go through the module-level Sleep symbol in Reduino.Actuators, constructed positionally with the delay value and driven by calling .wait(). This symbol must be resolvable/patchable at Reduino.Actuators.Sleep.

Validation Ordering Summary

  • Type errors (TypeError) for non-int pins/channels.
  • Value errors (ValueError) for out-of-range pins, out-of-range channels, negative durations/delays, and non-positive steps/times.

Task: Add RGB LED Actuator Support to the Reduino Transpiler

Overview

The Reduino transpiler converts a Python-like source language into Arduino C++ code. You must add support for an RGBLed actuator to two stages of the pipeline: the parser (which builds an AST) and the emitter (which generates C++ text from that AST).

The relevant source language recognizes objects imported via from Reduino.Actuators import RGBLed, constructed and then manipulated through method calls.

Part 1: AST Node Types

In the module Reduino.transpile.ast, define the following new AST node classes, all importable by name:

  • RGBLedDecl — represents construction of an RGB LED. Must expose attributes red_pin, green_pin, and blue_pin.
  • RGBLedSetColor — represents a set_color(...) call.
  • RGBLedOn — represents an on() call.
  • RGBLedOff — represents an off() call.
  • RGBLedFade — represents a fade(...) call. Must expose attributes duration_ms and steps.
  • RGBLedBlink — represents a blink(...) call. Must expose attributes times and delay_ms.

Each node should also retain whatever additional data (e.g. the variable name it applies to, and color arguments) needed by the emitter described below.

Part 2: Parser

The function parse(source) in Reduino.transpile.parser returns a program object with a setup_body attribute (a list of AST nodes). The parser must recognize the following statements and produce the corresponding AST nodes, in source order, within setup_body.

Construction
rgb = RGBLed(3, 4, 5)

Produces an RGBLedDecl. Positional arguments map to red_pin, green_pin, blue_pin respectively.

Keyword arguments are also supported:

rgb = RGBLed(red_pin=base + 1, green_pin=base + 2, blue_pin=base + 3)
Pin value representation
  • A literal integer pin argument is stored as an int (e.g. RGBLed(3, 4, 5) → red_pin == 3, green_pin == 4, blue_pin == 5).
  • A non-literal (symbolic) pin expression is stored as a string containing the expression wrapped in a single pair of parentheses, with a single space around binary operators. For example, red_pin=base + 1 → red_pin == "(base + 1)", and likewise "(base + 2)", "(base + 3)".
Method calls

For an RGB LED object bound to a variable (e.g. rgb), the following method calls each produce one AST node:

  • rgb.set_color(r, g, b) → RGBLedSetColor
  • rgb.on() → RGBLedOn
  • rgb.off() → RGBLedOff
  • rgb.fade(r, g, b, duration_ms=..., steps=...) → RGBLedFade, where duration_ms and steps are the integer values of the corresponding keyword arguments (e.g. duration_ms=750, steps=5 → duration_ms == 750, steps == 5).
  • rgb.blink(r, g, b, times=..., delay_ms=...) → RGBLedBlink, where times and delay_ms are the integer values of the corresponding keyword arguments (e.g. times=2, delay_ms=150 → times == 2, delay_ms == 150).

Part 3: Emitter

The emitter (invoked as emit(parse(source)), returning C++ source text as a string) must generate the following C++ from the RGB LED AST nodes.

Terminology below: given an RGB LED variable named <var> (e.g. rgb) with red/green/blue pins <R>, <G>, <B>.

Global state variables

For each declared RGB LED, emit the following global declarations:

bool __rgb_state_<var> = false;
int __rgb_red_<var> = 0;

(A green and blue current-value global following the same __rgb_green_<var> / __rgb_blue_<var> naming are used by the analog writes below.)

Pin setup

For each declared RGB LED, configure all three pins as outputs:

pinMode(<R>, OUTPUT);
pinMode(<G>, OUTPUT);
pinMode(<B>, OUTPUT);

Pin values that were stored as symbolic expression strings must be emitted literally as that string (without surrounding quotes) in place of the numeric pin.

Applying a color (set_color)

Writing a color to the LED emits analog writes to each pin using the current-value globals:

analogWrite(<R>, __rgb_red_<var>);
analogWrite(<G>, __rgb_green_<var>);
analogWrite(<B>, __rgb_blue_<var>);
Fade

A fade emits a stepped loop that ramps toward the target color over the given number of steps, delaying between steps, and updating the pins via the current-value globals. The generated code must include:

for (int __redu_i = 1; __redu_i <= __redu_steps; ++__redu_i) {

within which the color is written using analogWrite(<R>, __rgb_red_<var>); … analogWrite(<B>, __rgb_blue_<var>); and a delay(__redu_delay_ms); is issued.

Blink

A blink emits a counted loop that toggles the LED on and off a number of times with a delay between transitions. The generated code must include:

for (int __redu_i = 0; __redu_i < __redu_times; ++__redu_i) {

a delay-tracking declaration:

unsigned long __redu_delay_ms = 0UL;

and delay(__redu_delay_ms); calls, along with analog writes to the pins using the current-value globals.

Notes

  • The parser and emitter must continue to support existing actuators unchanged; RGB LED support is additive.
  • All named AST classes must be importable directly from Reduino.transpile.ast.
  • Whitespace normalization is applied when comparing some emitter output, so exact spacing between tokens in generated C++ is not critical except where a specific normalized form is shown; however, statements involving pinMode, analogWrite, and the two for loop headers are matched against raw output and must appear exactly as written above (with the appropriate pin/variable substitutions).
