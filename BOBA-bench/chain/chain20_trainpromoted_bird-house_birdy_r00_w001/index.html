01 Implement the encode Utility Function 450 words · rewritten by GPT-5.6-sol, reworded by GLM-5.3-Flash

Task Specification: Implement the encode Utility Function

Summary

The task is to implement encode in the utils module. The function reads a local file and returns either its unencoded text content or the standard Base64 representation of its raw bytes, depending on the MIME type information that is supplied.

Public API

utils.encode(path, mimetypes)

The utility is accessible through the repository's birdy.utils module, for instance via from birdy import utils.

Parameters
  • path (str): Either a plain path on the local filesystem or a file:// URL identifying a local file.
  • mimetypes (list of str): MIME type declarations that determine whether the local file is text-like or binary. Matching of MIME types must be case-insensitive.
Return Value

The type of the value returned depends on MIME handling:

  • Text-like content is returned as an unencoded str.
  • Binary content is returned as a bytes object that contains the standard Base64 representation of the file's raw bytes.

Required Behavior

1. Handling Local Paths and File URLs

Read the contents of the local file that path identifies. Both of these forms must be accepted:

  • A plain path on the filesystem, such as /tmp/somefile.
  • A file:// URL, such as file:///tmp/somefile.

If both forms identify the same file, the results they produce must be identical.

2. Classification by MIME Type

Comparisons involving MIME types are case-insensitive. Specifically:

  • application/xml is text-like.
  • Any MIME type carrying the text/ prefix is text-like, regardless of letter case. This includes text/plain, TEXT/PLAIN, and other case variants.
  • Binary handling applies to a binary MIME type such as application/x-netcdf.

This decision is controlled by the MIME declarations that are supplied; the function is not required to infer the MIME type from the filename or file contents.

3. Text-Like Content

When the MIME type is text-like, return the file's content as a plain, unencoded str; do not Base64-encode it.

For a file that contains the bytes b'hello', each of the following calls must return exactly 'hello':

utils.encode(path, mimetypes=["application/xml"])
utils.encode(path, mimetypes=["text/plain"])
utils.encode(path, mimetypes=["TEXT/PLAIN"])
4. Binary Content

When the MIME type is binary, apply standard Base64 encoding directly to the raw bytes of the file and return the resulting bytes object; do not decode the Base64 result into a string.

For a file whose content is b'hello':

utils.encode(path, mimetypes=["application/x-netcdf"]) == b'aGVsbG8='

Compatibility Requirements

  • The file contents must be read in a manner that supports raw-byte Base64 encoding.
  • A plain path and an equivalent file:// URL must remain interchangeable.
  • The return types of the text and binary branches are intentionally different: str for text-like content and Base64-encoded bytes for binary content.

Summary

The primary WPS client class must be renamed and a submodule relocated, while the backward-compatible import aliases are preserved. Under the new names/locations, the behavior of the client and of its data converters must remain functional.

Required Public API

  • BirdyClient — an alias kept for backward compatibility; it must remain importable and constructible.

All three (WPSClient, BirdyClient, import_wps) must accept the same construction interface and produce client objects that are equivalent and working. Specifically, each must at minimum be usable with the keyword argument url=<string>.

2. The converters submodule (birdy.client.converters)

A module importable as birdy.client.converters must exist and expose:

  • JSONConverter — a class.
  • default_converters — a dict-like mapping whose key "application/json" maps to the JSONConverter class.

The constructor of the client (WPSClient, and its aliases) must support these keyword arguments:

  • url (string): the endpoint of the WPS service.
  • processes: optionally restricts the client to a subset of processes. The value may be:
    • a list of process identifier strings, or
    • a single process identifier string. When this argument is provided, the resulting client must expose only the matching processes as callable methods.
    • If any requested process name does not exist on the service, the constructor must raise ValueError. The message of the error must contain the offending process name(s); when multiple names are missing, each missing name must appear in the message.
  • convert_objects (bool): determines whether complex outputs are converted into native Python objects (see below).

  • A process that has a single output returns that single value.
  • A process that has multiple outputs returns them as an ordered tuple, in the order of the outputs.

JSONConverter

Remarks

  • For this task, complex-output object handling (other than the JSON→dict and NetCDF→Dataset conversions described above) is not required to be exercised.

Overview

You are modifying birdy, a Python client library for WPS (Web Processing Service). The changes affect the way process execution results are returned to callers, add two new utility functions, and introduce an "interactive" mode on the client.

1. Two New Utility Functions

Add two public functions to the module birdy.utils:

sanitize(name)
  • Input: a string.
  • Output: a string that has been transformed so it is a valid/normalized identifier-style name.
  • Required behavior:
    • sanitize('output') → 'output' (a single word that is already lowercase is left unchanged).
    • sanitize('My Output 1') → 'my_output_1' — that is, the string is lowercased and its spaces are replaced with underscores.
delist(val)
  • Input: a value that is either a list or not a list.
  • Output:
    • If val is a list with more than one element, return the list unchanged.
    • If val is a list with exactly one element, return that single element (unwrapped).
    • If val is not a list, return it unmodified.
  • Examples:
    • delist(['one', 'two']) → ['one', 'two']
    • delist(['one']) → 'one'
    • delist('one') → 'one'

2. Result Format of the WPS Client

The public class for the client is WPSClient, importable via from birdy.client import WPSClient. It is constructed with a keyword argument url (the service endpoint) and, optionally:

  • processes — a list of process identifiers the client is restricted to.
  • convert_objects — a boolean whose default is False.
  • interactive — a boolean whose default is False; see section 3.

Each WPS process is dynamically exposed by the client as a method whose name is that process's identifier. Invoking such a method with the process's inputs executes the process and returns its outputs.

The client instance also carries a mutable attribute _convert_objects (a boolean) that controls whether complex/typed outputs are converted into native Python objects. This attribute can be toggled at runtime after construction.

Return value of calling a process

No matter how many outputs a process has, a call to it returns a collections.namedtuple-style object whose fields correspond to the process's output identifiers.

  • The returned namedtuple's field names are the sanitized (see sanitize above) output identifiers.
  • The returned object supports iteration/unpacking in the order of the outputs, so callers can tuple-unpack it.
  • Each field is also accessible as an attribute, using the sanitized output identifier name.

The following consequences must hold:

  • Single-output process: the return value is a 1-element namedtuple. Unpacking it into a single-element target (value, = client.proc(...)) yields the sole output value.

    • Examples of behavior:
      • A "hello" process that returns a greeting yields a single value equal to e.g. "Hello david".
      • A numeric binary-operator process (inputs inputa, inputb, operator) that returns the result of the operation yields the single computed number (e.g. add of 1 and 2 → 3.0).

  • Multiple-output process: the return value is a namedtuple holding one field per output.

    • It can be unpacked by position (x1, x2 = client.proc(...)).
    • Each output is also accessible via an attribute name equal to the sanitized output identifier (e.g. out.output1, out.output2).
    • Example: a process that produces outputs identified output1 and output2 with values "11" and "19" yields a namedtuple for which positional unpacking gives "11", "19", and .output1 == "11", .output2 == "19".
Conversion of values

The individual output values inside the namedtuple are subject to delist semantics: an output that would otherwise be a single-element list is unwrapped to its scalar value. For example, for a process with many outputs, each output is returned as its scalar value in the corresponding field.

If _convert_objects is True, typed/complex outputs are converted to native Python objects:

  • A NetCDF output is turned into a netCDF4.Dataset object.
  • A JSON output is turned into a dict.
  • Literal outputs are converted to their natural Python types. For a process that echoes back a variety of literal inputs, the leading fields (all but the final two) make up a tuple of native-typed values matching the inputs (string, int, float, and various date/time and enumeration values).
  • A bounding-box output is represented as an object that exposes .crs (an owslib.crs.Crs) and .dimensions (integer).

The conversion utilities used for these conversions reside in the module birdy.client.converters.

3. Interactive Mode

If WPSClient is constructed with interactive=True:

  • Process calls still return the namedtuple result described above.
  • While a process is executing, progress/status information is printed to standard output. The printed output starts with the current date (i.e. it begins with the string form of today's date, str(datetime.date.today())).

4. Backward Compatibility

  • The name BirdyClient must stay importable from the top-level birdy package (from birdy import BirdyClient) as an alias/equivalent of the client class.

Notes and Constraints

  • Only the behaviors described above are required. Handling of complex outputs beyond what is listed here is out of scope.
  • The utils.is_url function must keep behaving as before: it returns truthy for http:// and file:// URLs and falsy for bare filenames.

Overview

A WPSClient class is exposed by the library, along with a command-line interface (CLI) built on click. Right now, WPS capabilities and process descriptions are always fetched by the client and the CLI from a live server over the network.
