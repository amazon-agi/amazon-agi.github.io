Task Specification: Implement encode Utility Function

Overview

Implement encode in the utils module. The function reads a local file and returns either its unencoded text content or the standard Base64 representation of its raw bytes, according to the supplied MIME type information.

Public API

utils.encode(path, mimetypes)

The utility is available through the repository's birdy.utils module, for example via from birdy import utils.

Parameters
  • path (str): Either a plain local filesystem path or a file:// URL that identifies a local file.
  • mimetypes (list of str): MIME type declarations used to determine whether the local file is text-like or binary. MIME matching must be case-insensitive.
Return Value

The return type depends on MIME handling:

  • Text-like content returns an unencoded str.
  • Binary content returns a bytes object containing the standard Base64 representation of the file's raw bytes.

Required Behavior

1. Local Path and File-URL Handling

Read the contents of the local file identified by path. Both of these forms must be accepted:

  • A plain filesystem path, such as /tmp/somefile.
  • A file:// URL, such as file:///tmp/somefile.

When both forms identify the same file, they must produce identical results.

2. MIME-Type Classification

MIME-type comparisons are case-insensitive. In particular:

  • application/xml is text-like.
  • Any MIME type with the text/ prefix is text-like, regardless of letter case. This includes text/plain, TEXT/PLAIN, and other case variants.
  • A binary MIME type such as application/x-netcdf uses binary handling.

The supplied MIME declarations control this decision; the function is not required to infer the MIME type from the filename or file contents.

3. Text-Like Content

For a text-like MIME type, return the file content as a plain, unencoded str. Do not Base64-encode it.

For a file containing the bytes b'hello', each of the following calls must return exactly 'hello':

utils.encode(path, mimetypes=["application/xml"])
utils.encode(path, mimetypes=["text/plain"])
utils.encode(path, mimetypes=["TEXT/PLAIN"])
4. Binary Content

For a binary MIME type, apply standard Base64 encoding directly to the file's raw bytes and return the resulting bytes object. Do not decode the Base64 result into a string.

For a file containing b'hello':

utils.encode(path, mimetypes=["application/x-netcdf"]) == b'aGVsbG8='

Compatibility Requirements

  • File contents must be read in a way that supports raw-byte Base64 encoding.
  • A plain path and an equivalent file:// URL must remain interchangeable.
  • The text and binary branches intentionally have different return types: str for text-like content and Base64-encoded bytes for binary content.

Overview

You are modifying a Python WPS (Web Processing Service) client library named birdy. The changes affect how process execution results are returned to callers, add two new utility functions, and introduce an "interactive" mode on the client.

1. New Utility Functions

In the module birdy.utils, add two public functions:

  • Input: a string.
  • Output: a string, transformed so it is a valid/normalized identifier-style name.
  • Required behavior:

    • sanitize('My Output 1') → 'my_output_1' — i.e., the string is lowercased and spaces are replaced with underscores.
delist(val)
  • Input: either a list or a non-list value.
  • Output:
    • If val is a list containing more than one element, return the list unchanged.
    • If val is a list containing exactly one element, return that single element (unwrapped).
    • If val is not a list, return it unchanged.
  • Examples:
    • delist(['one', 'two']) → ['one', 'two']
    • delist(['one']) → 'one'
    • delist('one') → 'one'

2. WPS Client Result Format

The public client class is WPSClient, importable as from birdy.client import WPSClient. It is constructed with a keyword argument url (the service endpoint), and optionally:

  • processes — a list of process identifiers to restrict the client to.
  • convert_objects — a boolean (default False).
  • interactive — a boolean (default False), see section 3.

The client dynamically exposes each WPS process as a method whose name is the process identifier. Calling such a method with the process's inputs executes the process and returns its outputs.

The client instance also has a mutable attribute _convert_objects (boolean) that controls whether complex/typed outputs are converted into native Python objects. It can be toggled at runtime after construction.

Return value of a process call

Regardless of the number of outputs, a process call returns a collections.namedtuple-style object whose fields correspond to the process's output identifiers.

  • The field names of the returned namedtuple are the sanitized (see sanitize above) output identifiers.
  • The returned object is iterable/unpackable in the order of the outputs, so callers can tuple-unpack it.
  • Each field is also accessible by attribute using the sanitized output identifier name.

Consequences that must hold:

  • Single-output process: the return value is a 1-element namedtuple. Unpacking with a single-element target (value, = client.proc(...)) yields the sole output value.

    • Example behaviors:
      • A "hello" process returning a greeting yields a single value equal to e.g. "Hello david".
      • A numeric binary-operator process (inputs inputa, inputb, operator) returning the result of the operation yields the single computed number (e.g. add of 1 and 2 → 3.0).

  • Multiple-output process: the return value is a namedtuple with one field per output.

    • It can be unpacked positionally (x1, x2 = client.proc(...)).
    • Each output is also accessible by attribute name equal to the sanitized output identifier (e.g. out.output1, out.output2).
    • Example: a process producing outputs identified output1 and output2 with values "11" and "19" yields a namedtuple where positional unpacking gives "11", "19", and .output1 == "11", .output2 == "19".
Value conversion

Individual output values within the namedtuple are subject to delist semantics: an output that would otherwise be a single-element list is unwrapped to its scalar value. For example, a process with many outputs returns each output as its scalar value in the corresponding field.

When _convert_objects is True, typed/complex outputs are converted to native Python objects:

  • A NetCDF output becomes a netCDF4.Dataset object.
  • A JSON output becomes a dict.
  • Literal outputs are converted to their natural Python types. For a process echoing back a variety of literal inputs, the leading fields (all but the final two) form a tuple of native-typed values matching the inputs (string, int, float, and various date/time and enumeration values).
  • A bounding-box output is represented as an object exposing .crs (an owslib.crs.Crs) and .dimensions (integer).

The conversion utilities used for these conversions live in the module birdy.client.converters.

3. Interactive Mode

When WPSClient is constructed with interactive=True:

  • Process calls still return the namedtuple result as described above.
  • While a process is executing, progress/status information is printed to standard output. The printed output begins with the current date (i.e. it starts with the string form of today's date, str(datetime.date.today())).

4. Backward Compatibility

  • The name BirdyClient must remain importable from the top-level birdy package (from birdy import BirdyClient) as an alias/equivalent of the client class.

Notes / Constraints

  • Only the behaviors described above are required. Complex-output handling beyond what is listed here is out of scope.
  • The utils.is_url function must continue to behave as before: it returns truthy for http:// and file:// URLs and falsy for bare filenames.

Within each of these groups, the sort must be stable: inputs that fall into the same group must retain their original relative ordering from the input sequence. (A stable sort using this key over the original sequence satisfies this; the key itself must map all members of a group to an equal value so their relative order is preserved.)

Behavioral detail on "no default value"

An input is treated as having no default value when its defaultValue is empty/absent (e.g. None). Inputs whose defaultValue carries an actual value are treated as having a default.

Concrete ordering consequence

Given a sequence of inputs where the first three consecutive inputs are all required (minOccurs >= 1) with no default value, sorting that sequence with sort_inputs_key must leave those first three inputs in their original positions and original relative order.

Task Specification: Offline WPS Client and CLI Support

Overview

You are working on birdy, a Python library that provides a client for OGC Web Processing Service (WPS) servers. The library exposes a WPSClient class and a command-line interface (CLI) built on click. Currently, the client and CLI always fetch WPS capabilities and process descriptions from a live server over the network. This task adds the ability to construct the client and CLI from pre-fetched XML documents, so they can operate fully offline.

Public API Surface

1. birdy.WPSClient

WPSClient must be importable from the top-level birdy package. Its constructor must accept the following (keyword) parameters relevant to this task:

WPSClient(url, processes=None, converters=None, progress=False, caps_xml=None, desc_xml=None)
  • url (str): The WPS server URL.
  • processes (str or list of str, optional): Restrict the client to a subset of processes. May be a single process identifier (str) or a list of identifiers.
  • converters (list, optional): Output converter classes (unchanged behavior; not central to this task).
  • progress (bool, optional): Enables interactive progress reporting (unchanged behavior).
  • caps_xml (bytes, optional): The raw bytes of a WPS GetCapabilities XML response.
  • desc_xml (bytes, optional): The raw bytes of a WPS DescribeProcess XML response (which may describe multiple processes).

Behavior required:

  • Offline construction: When both caps_xml and desc_xml are provided, the client must be fully constructed without any network access. The capabilities document (caps_xml) supplies the list of available processes and service-level metadata; the process descriptions document (desc_xml) supplies the detailed input/output descriptions for the processes. The client must not contact url in this mode.

  • Capabilities-only offline construction: When caps_xml is provided (with or without desc_xml), the list of processes and the service documentation must be derived from that XML. desc_xml, when present, contains the descriptions for all processes to be exposed.

  • Online construction (unchanged): When caps_xml / desc_xml are not provided, the client fetches them from the server at url as before.

  • Process subsetting with offline data: The processes parameter must work together with offline construction. When only a subset of processes is requested, the client exposes exactly those processes. When processes names one or more identifiers that are not present in the capabilities, a ValueError must be raised whose message contains the offending name(s) (e.g. requesting ["missing"] raises a ValueError mentioning missing; requesting ["wrong", "process", "names"] raises a ValueError whose message contains wrong, process, and names).

  • Process identifiers with special characters: Process identifiers may legally contain characters not valid in Python identifiers (dots, dashes), and processes/inputs/outputs with such identifiers must be handled without error. The client must be able to build from capabilities/description documents whose process identifiers include dots and dashes.

  • Generated attributes / documentation:

    • The client object's docstring (__doc__) must contain the word Processes (it summarizes the available processes/service).
    • Each generated process method must carry a docstring derived from the process description. For example, a process whose title/abstract mentions "Hello" must have a method whose __doc__ contains Hello.
    • Each available process must be accessible as an attribute keyed by its identifier, and the set of process identifiers must be available via a _processes mapping (a dict-like attribute whose keys are the process identifiers).

nb_form(wps, pid)

  • url (str): the WPS server URL.
