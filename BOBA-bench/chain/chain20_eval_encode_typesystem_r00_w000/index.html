01 Introduce three new validator classes — Date, Time, and DateTime — into the module typesystem.validators. 574 words · source specification, reworded by GLM-5.3-Flash

Overview

Introduce three new validator classes — Date, Time, and DateTime — into the module typesystem.validators. They sit alongside the existing String and Integer validators and must be importable from that module.

Interface Common to All Validators

Each validator takes no required arguments at instantiation (e.g. Date(), Time(), DateTime()).

Each validator exposes a method:

def validate(self, value) -> <result>

The result object it returns must provide the following two attributes:

  • .value — the value produced by successful parsing/normalization (when validation succeeds).
  • .errors — a list whose entries are error code strings (when validation fails).

When validation succeeds, .value holds the parsed value. When validation fails, .errors is a list containing exactly one error code string that identifies the failure reason. The specific error codes required are "format" and "invalid" (described below).

Date

validate(value) accepts either of the following:

  • A datetime.date instance — passed through unaltered; .value equals the input.
  • A string in the exact format YYYY-MM-DD (an ISO calendar date, e.g. "2049-01-01") — it is parsed into the corresponding datetime.date. Thus "2049-01-01" yields datetime.date(2049, 1, 1).

Error cases:

  • If the string does not conform to the expected YYYY-MM-DD format (e.g. "20490101"), .errors must equal ["format"].
  • If the string conforms to the format but represents a calendar date that does not exist (e.g. "2049-01-32"), .errors must equal ["invalid"].

Time

validate(value) accepts either of the following:

  • A datetime.time instance — passed through unaltered; .value equals the input.
  • A string in the format HH:MM:SS, with optional fractional seconds. Fractional seconds, when present, appear after a decimal point that follows the seconds. Thus:
    • "12:00:01" yields datetime.time(12, 0, 1).
    • "12:00:01.001" yields datetime.time(12, 0, 1, 1000) (that is, .001 seconds = 1000 microseconds).
    • "12:00:01.000001" yields datetime.time(12, 0, 1, 1) (that is, 1 microsecond).

Error cases:

  • If the string does not conform to the expected time format (e.g. "12.00.01"), .errors must equal ["format"].
  • If the string conforms to the format but represents a time that is out of range (e.g. "12:00:60"), .errors must equal ["invalid"].

DateTime

validate(value) accepts either of the following:

  • A datetime.datetime instance — passed through unaltered; .value equals the input.
  • A string made up of a date and a time separated by a space, plus an optional trailing timezone specifier. Non-zero-padded numeric fields are allowed in the date and time components (e.g. "2049-1-1 12:00:00"). Thus:
    • "2049-1-1 12:00:00" yields datetime.datetime(2049, 1, 1, 12, 0, 0) (no timezone / naive).
    • A trailing Z stands for UTC: "2049-1-1 12:00:00Z" yields datetime.datetime(2049, 1, 1, 12, 0, 0, tzinfo=datetime.timezone.utc).
    • A trailing signed offset expressed in ±HHMM form: "2049-1-1 12:00:00-0230" yields a datetime with tzinfo=datetime.timezone(-datetime.timedelta(hours=2, minutes=30)).

Error cases:

  • If the string does not conform to the expected datetime format (e.g. "2049:01:01 12:00:00", where the date portion uses colons instead of dashes), .errors must equal ["format"].
  • If the string conforms to the format but represents a value that is out of range (e.g. "2049-01-01 12:00:60", with seconds that are out of range), .errors must equal ["invalid"].

Error Semantics Summary

  • "format" — the input string does not adhere to the accepted textual pattern for the validator's type.
  • "invalid" — the input string adheres to the pattern, but the values it contains do not form a real/valid date, time, or datetime.

In both error cases, .errors is a one-element list containing exactly that code.

Task Description

Summary

You will extend the typesystem.validators module by adding two new validator classes, Number and Boolean. These two classes follow the same design pattern as the existing validators (String, Integer, etc.).

Shared Validator Interface

Each validator is a class that is instantiated using keyword configuration options and exposes a validate method:

result = validator.validate(value, strict=False)

The result object that the validate method returns has:

  • a .value attribute holding the validated (and possibly coerced) value on success
  • an .errors attribute holding a list of error code strings on failure

When validation succeeds, .errors is empty/falsy and .value holds the coerced value; when validation fails, .errors contains one or more string error codes as described below.

The strict parameter has a default value of False. With strict=True, type coercion from other types (e.g. strings) is disabled.

Behavior

Valid input is coerced by the validator into a Python float in .value.

Handling of types (non-strict, default):

  • A float input is accepted, and the same value is returned (e.g. 123.1 → 123.1).
  • An int input is accepted and gets coerced to float (e.g. 123 → 123.0).
  • A str input representing a valid number is accepted and coerced to float (e.g. "123.1" → 123.1).
  • A str input that does not represent a number (e.g. "abc") results in the error ["type"].
  • A bool input (e.g. True) produces error ["type"]. Booleans must not be treated as numbers.
  • A float that is not finite (inf or nan) produces error ["finite"].

Handling of types (strict):

  • When strict=True, a str input produces error ["type"], even one representing a valid number (e.g. "123").

Null handling:

  • Using the default configuration, None produces error ["null"].
  • When allow_null=True, None is accepted and .value is None.

Constraint checks (each one produces the listed error code when violated):

  • maximum=M: a value greater than M produces ["maximum"], while a value equal to M is accepted.
  • minimum=M: a value less than M produces ["minimum"], while a value equal to M is accepted.
  • exclusive_maximum=M: a value equal to M produces ["exclusive_maximum"].
  • exclusive_minimum=M: a value equal to M produces ["exclusive_minimum"].
  • enum=[...] (with more than one allowed value): a value not in the list produces ["enum"].
  • enum=[x] (a single allowed value): a value not equal to x produces ["exact"].
  • exact=x: a value not equal to x produces ["exact"].
  • multiple_of=N: a value that is not a multiple of N produces ["multiple_of"].

Handling of types (non-strict, default):

  • A bool input is accepted and returned unchanged: True → True, False → False.
  • A truthy string, such as "True", is coerced to True.
  • The integer 1 is coerced to True.

  • When strict=True, a str input (e.g. "True") produces error ["type"].

Null handling:

  • Using the default configuration, None produces error ["null"].
  • When allow_null=True, None is accepted and .value is None.
  • When allow_null=True, an empty string '' is accepted and .value is None.

Task: Build an Object Validator

Summary

Extend the typesystem.validators module with a new validator class, Object. This validator validates dictionary-like values and provides support for property schemas, constraints, and nested validation.

Public API

The typesystem.validators.Object class

Constructor signature (all parameters are optional keyword arguments):

Object(
    allow_null=False,
    min_properties=None,
    max_properties=None,
    required=None,
    properties=None,
    pattern_properties=None,
    additional_properties=True,
)
  • allow_null (bool): whether None counts as an acceptable input value.
  • min_properties (int or None): the minimum number of properties required.
  • max_properties (int or None): the maximum number of properties allowed.
  • required (list of str or None): keys that must be present.
  • properties (dict mapping str → validator or None): validators applied per key to named properties.
  • pattern_properties (dict mapping regex-string → validator or None): validators applied to keys that match the regex pattern.
  • additional_properties: determines how keys not covered by properties or pattern_properties are handled. Its value may be True, False, None, or a validator instance (see below).
The validate(value, strict=False) method

The method returns a result object exposing:

  • .value — the output value after validation/coercion.
  • .errors — a container holding the errors (see below).
  • .is_valid — truthy when no validation errors exist.

The .errors container:

  • If compared for equality against a list of error codes (e.g. == ["type"]), it matches the list of top-level error codes produced.
  • Provides a .to_dict() method that returns a dict mapping property keys to their error code (a string) or, for nested object errors, to a nested dict.

The error container and ErrorMessage reside in typesystem.base (existing validators already use them; reuse the same result/error mechanism as the other validators in this module).

Behavior Requirements

Validation proceeds as described below and produces the stated value/errors.

Checks for null and type
  • Input of None:
    • If allow_null is False: error code "null".
    • If allow_null is True: valid, with .value equal to None.
  • Input that is neither a dict nor None (e.g. an integer): error code "type".
  • A dict containing a non-string key (e.g. {1: 123}): error code "invalid_key".
  • An empty dict {} when there are no constraints: valid, with .value == {}.
Constraints on property counts
  • min_properties:
    • With min_properties=1 and an empty dict: error code "empty".
    • With min_properties=2 and an empty dict: error code "min_properties".
    • When the dict contains at least min_properties entries: valid.
    • (The special code "empty" is used specifically when min_properties == 1 and the object is empty; otherwise a too-small object yields "min_properties".)
  • max_properties:
    • When the dict contains more than max_properties entries: error code "max_properties".
    • When the dict contains at most max_properties entries: valid.
Required keys
  • required=["example"]:
    • If "example" is present: valid; .value keeps the entry (e.g. {"example": 123}).
    • If "example" is absent: .errors.to_dict() yields {"example": "required"} (keyed by the name of the missing property, error code "required").
Named property validators (properties)

For each key present in the input that has a matching validator in properties, apply that validator to the value:

  • Coerced/validated values take the place of the originals in .value (e.g. Integer() coerces the string "123" to 123).
  • On failure, .errors.to_dict() maps the property key to that validator's error code (e.g. {"example": "type"}).
Default values
  • If a properties validator carries a default (e.g. Integer(default=0)) and its key is absent from the input, the default is inserted into .value (e.g. a missing "example" gives .value == {"example": 0}).
  • If the key is present, it is validated/coerced in the normal way.
Pattern properties (pattern_properties)

For keys that match a regex in pattern_properties, apply the associated validator:

  • Coerced values replace the originals (e.g. key "x-example" matching "^x-.*$" with Integer() coerces "123" → 123).
  • On failure, .errors.to_dict() maps the key to that validator's error code.
Additional properties (additional_properties)

Concerns keys not matched by properties or pattern_properties:

  • True: additional keys are kept unchanged in .value.
  • None: additional keys are dropped from .value (e.g. this results in .value == {}).
  • False: additional keys are rejected; .errors.to_dict() maps each offending key to the error code "invalid_property".
  • A validator instance: each additional key's value is validated/coerced by that validator. When coercion succeeds, the coerced value replaces the value in .value; on failure, the key is mapped to the validator's error code in .errors.to_dict().
Nested validation

When additional_properties (or a property validator) is itself an Object, validation recurses:

  • Nested coerced values are preserved within the output structure (e.g. {"example": {"nested": "123"}} → {"example": {"nested": 123}}).
  • Nested errors are represented as nested dicts in .errors.to_dict() (e.g. {"example": {"nested": "type"}}).

Integration Notes

  • It must be possible to import the Object class via from typesystem.validators import Object.
  • Use the same base result and error-message infrastructure (typesystem.base.ErrorMessage and the result type) as the module's existing validators (Boolean, String, Integer, Number, Date, DateTime, Time).

Overview of the Library

The library supplies:

  1. A collection of validator classes that check/coerce individual values.

  3. A result object that validation returns, exposing the coerced value, errors, and validity.

validator.validate(value, strict=False)

  • With nested object errors, the values are nested dicts, e.g. {"example": {"nested": "Must be a number."}}.

to_dict(style="code") method:

  • Returns a mapping from field key to error code (rather than the text), with the same nesting behavior. E.g. {"example": "type"} or {"example": {"nested": "type"}}.

Task Description

Summary

In this task you work with a Schema base class that supports defining structured data objects with named fields (akin to a lightweight dataclass/schema system). The subject of the task is the behavior of the __repr__ method for schema instances.

Background

A schema is defined by subclassing Schema and declaring fields. To take an example, a Person schema has the fields name and age. Instances can be created by supplying values, as keyword arguments, for some or all of the declared fields:

tom = Person(name="Tom", age=123)   # all fields populated
tom = Person(name="Tom")            # only some fields populated

Behavior Requirements

For a schema instance, __repr__ must render the class name followed by a parenthesized, comma-separated list of the fields that have been populated (i.e., assigned a value); each entry takes the form field_name=value, with the value rendered via its repr. Fields that were not populated do not appear in this listing.

Beyond that, the representation must indicate whether the instance is fully populated or sparsely populated:

  • An instance is fully populated when every declared field has a value. Its representation is exactly:

    ClassName(field1=value1, field2=value2)

    and there is no extra suffix.

  • An instance is sparsely populated when at least one declared field has not been given a value. Its representation must have the literal suffix [sparse] (a single leading space, then the bracketed word sparse) appended after the closing parenthesis:

    ClassName(field1=value1) [sparse]
Concrete expected results

Take a Person schema whose declared fields are name and age:

  • repr(Person(name="Tom", age=123)) must equal:
    Person(name='Tom', age=123)
  • repr(Person(name="Tom")) must equal:
    Person(name='Tom') [sparse]
    (because the age field is unpopulated, the instance is sparse and name is the only field that appears in the field list).

Within the representation, fields are ordered according to the order in which they are declared on the schema.

Constraints

  • Inside the parentheses, only the fields that have actually been populated appear.
  • The suffix [sparse] appears if and only if one or more declared fields are unpopulated.
  • Values are formatted with their repr.

Task: Support Callable Defaults in Schema Fields

Goal

The mechanism that handles default values for fields is to be enhanced, so that a field's default may be passed in as a callable. Whenever a default that was supplied as a callable is applied during validation, that callable must be invoked without any arguments, and the value it returns must be used as the resolved default value.

Public API

The classes involved here are part of the typesystem package and are available under these names:

  • typesystem.Schema — the base class used for defining schemas.
  • typesystem.Date — a field type that both validates and produces datetime.date values.

Declaring field instances as class attributes is how subclasses of a schema are defined; for instance:

class Example(typesystem.Schema):
    created = typesystem.Date(default=datetime.date.today)

A class method is exposed by schemas:

value, error = Example.validate(data)

Here, data stands for a mapping of input values. The call returns a two-tuple: the validated schema instance (or an object that exposes the validated fields as attributes) along with an error value.

Required Behavior

A keyword argument named default is accepted by fields. The default argument's value may take either of the following forms:

  1. A plain value (one that is not callable) — such a value is used directly as the default, just as it was before.
  2. A callable that takes no arguments — the callable is called whenever there is a need to apply the default, and the value it returns is then used as the default.

If, during validation, the input data lacks a field whose default is callable, the resolved value of that field must equal the outcome of calling that callable at validation time.

As a concrete case: take a schema that has a Date field with default set to datetime.date.today. Validating {} — an empty input mapping — must succeed, and on the instance that results, the created attribute must equal datetime.date.today().

Remarks

  • The way a callable default is told apart from a plain default must rest on whether the supplied default is callable.
  • Whatever behavior currently exists for non-callable defaults must remain unchanged.

Summary

This codebase's validation API must be renamed and restructured. Validation is currently triggered by a method called .validate(), which returns a result object. That method must be renamed to .validate_or_error(), with its behavior and signature kept identical. The validate name is being freed up for other use; this task, however, only requires the validate_or_error entry point to exist and to behave as described below.

API Surface Requirements

Field validators (typesystem.fields module)

Each of the following field classes must expose a method:

def validate_or_error(self, value, strict=False)

This requirement covers all field types, including at least:

  • String
  • Integer
  • Float
  • Boolean
  • Choice
  • Object
  • Date
  • Time
  • DateTime

The strict keyword argument must be accepted (it is used by Integer, Float, and Boolean).

Schemas (exposed as typesystem.Schema)

Subclasses of Schema must expose a classmethod:

@classmethod
def validate_or_error(cls, value)

Returned Value: ValidationResult

validate_or_error returns a ValidationResult object with these properties:

  1. A pair of attributes: .value and .error.

    • On success: .value stores the validated/coerced value, and .error is None.
    • On failure: .value is None, and .error stores a ValidationError.

  2. Can be unpacked as a 2-tuple in the order (value, error):

    value, error = validator.validate_or_error(...)

  3. Truthiness: the result is truthy if validation succeeded (no error) and falsy if it failed. Equivalently, bool(result) mirrors success.

  4. repr():

    • On success: ValidationResult(value=<repr of value>)
    • On failure: ValidationResult(error=<repr of error>)

ValidationError

An error object that has:

  1. Equality: two ValidationError instances built with the same text and code compare equal. It must be possible to construct it as:

    ValidationError(text="...", code="...")

  2. .messages() — returns a list of Message instances that describe each error.

  3. Dictionary-like interface — the call dict(error) produces a mapping of field index to message text:

    • With a single top-level error (no field path), the key is the empty string "", e.g. {"": "Must be a number."}.
    • With object property errors, the keys are property names, e.g. {"age": "Must be a number."}.
    • With nested object errors, the values are nested dicts, e.g. {"example": {"nested": "Must be a number."}}.
    • Individual entries can be accessed by subscript, e.g. error["age"] or error[""].

  4. repr():

    • When the error holds a single message with no field index: ValidationError(text='...', code='...')
    • When the error holds messages with indices (one or more): ValidationError([Message(text='...', code='...', index=[...])]) (given as a list of Message reprs)

Message

A message object that can be constructed as Message(text="...", code="...") (an index can optionally be passed), with:

  1. Equality determined by its fields.
  2. repr():
    • When there is no index: Message(text='...', code='...')
    • When there is an index: Message(text='...', code='...', index=[...])

Schema-Level Behavior

Schema.validate_or_error(value) validates a dict against the fields the schema declares and returns a ValidationResult:

  • When validation succeeds, .value holds a schema instance whose attributes are the validated/coerced field values, and two instances built from equal field values compare equal.
  • Field values get coerced according to their field types (e.g. an age field declared as Integer() coerces "123" → 123).
  • Required fields that are missing produce an error mapping keyed by field name, e.g. {"age": "This field is required."}.
  • Field values that are invalid produce an error mapping keyed by field name, e.g. {"age": "Must be a number."}.
  • When the value is absent, a field with a callable default (e.g. Date(default=datetime.date.today)) uses the result of calling that default.

A schema instance's repr() must take the form <ClassName>(<field>=<value>, ...), e.g. Example(a='a', b=1).
