01 Add three new validator classes — Date, Time, and DateTime — to the module typesystem.validators. 526 words · source specification

Overview

Add three new validator classes — Date, Time, and DateTime — to the module typesystem.validators. These join the existing String and Integer validators and must be importable from that module.

Common Validator Interface

Each validator is instantiated with no required arguments (e.g. Date(), Time(), DateTime()).

Each validator exposes a method:

def validate(self, value) -> <result>

The returned result object must provide the following two attributes:

  • .value — the successfully parsed/normalized value (when validation succeeds).
  • .errors — a list of error code strings (when validation fails).

On success, .value holds the parsed value. On failure, .errors is a list containing exactly one error code string identifying the failure reason. The specific error codes required are "format" and "invalid" (described below).

Date

validate(value) accepts either:

  • A datetime.date instance — passed through unchanged; .value equals the input.
  • A string in the exact format YYYY-MM-DD (ISO calendar date, e.g. "2049-01-01") — parsed into the corresponding datetime.date. So "2049-01-01" yields datetime.date(2049, 1, 1).

Error conditions:

  • If the string does not match the expected YYYY-MM-DD format (e.g. "20490101"), .errors must equal ["format"].
  • If the string matches the format but represents a nonexistent calendar date (e.g. "2049-01-32"), .errors must equal ["invalid"].

Time

validate(value) accepts either:

  • A datetime.time instance — passed through unchanged; .value equals the input.
  • A string in the format HH:MM:SS with optional fractional seconds. Fractional seconds, when present, follow a decimal point after the seconds. So:
    • "12:00:01" yields datetime.time(12, 0, 1).
    • "12:00:01.001" yields datetime.time(12, 0, 1, 1000) (i.e. .001 seconds = 1000 microseconds).
    • "12:00:01.000001" yields datetime.time(12, 0, 1, 1) (i.e. 1 microsecond).

Error conditions:

  • If the string does not match the expected time format (e.g. "12.00.01"), .errors must equal ["format"].
  • If the string matches the format but represents an out-of-range time (e.g. "12:00:60"), .errors must equal ["invalid"].

DateTime

validate(value) accepts either:

  • A datetime.datetime instance — passed through unchanged; .value equals the input.
  • A string combining a date and a time, separated by a space, with an optional trailing timezone specifier. The date and time components allow non-zero-padded numeric fields (e.g. "2049-1-1 12:00:00"). So:
    • "2049-1-1 12:00:00" yields datetime.datetime(2049, 1, 1, 12, 0, 0) (no timezone / naive).
    • A trailing Z denotes UTC: "2049-1-1 12:00:00Z" yields datetime.datetime(2049, 1, 1, 12, 0, 0, tzinfo=datetime.timezone.utc).
    • A trailing signed offset in ±HHMM form: "2049-1-1 12:00:00-0230" yields a datetime with tzinfo=datetime.timezone(-datetime.timedelta(hours=2, minutes=30)).

Error conditions:

  • If the string does not match the expected datetime format (e.g. "2049:01:01 12:00:00", which uses colons instead of dashes in the date portion), .errors must equal ["format"].
  • If the string matches the format but represents an out-of-range value (e.g. "2049-01-01 12:00:60", where the seconds are out of range), .errors must equal ["invalid"].

Summary of Error Semantics

  • "format" — the input string does not conform to the accepted textual pattern for the validator's type.
  • "invalid" — the input string conforms to the pattern, but the values it contains do not form a real/valid date, time, or datetime.

In both error cases, .errors is a single-element list containing exactly that code.

Overview

You will extend the typesystem.validators module by adding two new validator classes: Number and Boolean. These follow the same design pattern as the existing validators (String, Integer, etc.).

Common Validator Interface

Each validator is a class that is instantiated with keyword configuration options and exposes a validate method:

result = validator.validate(value, strict=False)

The validate method returns a result object that has:

  • a .value attribute containing the validated (and possibly coerced) value on success
  • an .errors attribute containing a list of error code strings on failure

When validation succeeds, .errors is empty/falsy and .value holds the coerced value. When validation fails, .errors contains one or more string error codes as described below.

The strict parameter defaults to False. When strict=True, type coercion from other types (e.g. strings) is disabled.

Behavior

The validator coerces valid input into a Python float in .value.

Type handling (non-strict, default):

  • A float input is accepted and returned as-is (e.g. 123.1 → 123.1).
  • An int input is accepted and coerced to float (e.g. 123 → 123.0).
  • A str input that represents a valid number is accepted and coerced to float (e.g. "123.1" → 123.1).
  • A str input that does not represent a number (e.g. "abc") produces error ["type"].
  • A bool input (e.g. True) produces error ["type"]. Booleans must not be treated as numbers.
  • A float that is not finite (inf or nan) produces error ["finite"].

Constraint checks (each produces the listed error code when violated):

  • maximum=M: a value greater than M produces ["maximum"]; a value equal to M is accepted.
  • minimum=M: a value less than M produces ["minimum"]; a value equal to M is accepted.
  • exclusive_maximum=M: a value equal to M produces ["exclusive_maximum"].
  • exclusive_minimum=M: a value equal to M produces ["exclusive_minimum"].
  • enum=[...] (with more than one allowed value): a value not in the list produces ["enum"].
  • enum=[x] (a single allowed value): a value not equal to x produces ["exact"].

  • multiple_of=N: a value that is not a multiple of N produces ["multiple_of"].

  • With strict=True, a str input (e.g. "True") produces error ["type"].

Null handling:

  • With default configuration, None produces error ["null"].
  • With allow_null=True, None is accepted and .value is None.
  • With allow_null=True, an empty string '' is accepted and .value is None.

Task: Implement an Object Validator

Overview

Add a new validator class Object to the typesystem.validators module. This validator validates dictionary-like values and supports property schemas, constraints, and nested validation.

API Surface

Class: typesystem.validators.Object

Constructor signature (all parameters optional keyword arguments):

Object(
    allow_null=False,
    min_properties=None,
    max_properties=None,
    required=None,
    properties=None,
    pattern_properties=None,
    additional_properties=True,
)
  • allow_null (bool): whether None is an acceptable input value.
  • min_properties (int or None): minimum number of properties required.
  • max_properties (int or None): maximum number of properties allowed.
  • required (list of str or None): keys that must be present.
  • properties (dict mapping str → validator or None): per-key validators for named properties.
  • pattern_properties (dict mapping regex-string → validator or None): validators applied to keys matching the regex pattern.
  • additional_properties: controls handling of keys not covered by properties or pattern_properties. Can be True, False, None, or a validator instance (see below).
Method: validate(value, strict=False)

Returns a result object exposing:

  • .value — the validated/coerced output value.
  • .errors — an error container (see below).
  • .is_valid — truthy when there are no validation errors.

The .errors container:

  • When compared for equality against a list of error codes (e.g. == ["type"]), it matches the list of top-level error codes produced.
  • Provides a .to_dict() method returning a dict mapping property keys to their error code (a string), or to a nested dict for nested object errors.

The error container and ErrorMessage live in typesystem.base (already used by existing validators; reuse the same result/error mechanism as the other validators in this module).

Required Behavior

Validation proceeds as follows and produces the described value/errors.

Null and type checks
  • None input:
    • If allow_null is False: error code "null".
    • If allow_null is True: valid, with .value equal to None.
  • Non-dict, non-None input (e.g. an integer): error code "type".
  • A dict with a non-string key (e.g. {1: 123}): error code "invalid_key".
  • An empty dict {} with no constraints: valid, with .value == {}.
Property-count constraints
  • min_properties:
    • When min_properties=1 and the dict is empty: error code "empty".
    • When min_properties=2 and the dict is empty: error code "min_properties".
    • When the dict has at least min_properties entries: valid.
    • (The special code "empty" is used specifically when min_properties == 1 and the object is empty; otherwise a too-small object yields "min_properties".)
  • max_properties:
    • When the dict has more than max_properties entries: error code "max_properties".
    • When the dict has at most max_properties entries: valid.
Required keys
  • required=["example"]:
    • If "example" is present: valid; .value retains the entry (e.g. {"example": 123}).
    • If "example" is missing: .errors.to_dict() yields {"example": "required"} (keyed by the missing property name, error code "required").
Named property validators (properties)

For each key present in the input that has a matching validator in properties, run that validator against the value:

  • Coerced/validated values replace the originals in .value (e.g. Integer() coerces the string "123" to 123).
  • On failure, .errors.to_dict() maps the property key to that validator's error code (e.g. {"example": "type"}).
Default values
  • If a properties validator carries a default (e.g. Integer(default=0)) and its key is absent from the input, the default is inserted into .value (e.g. missing "example" produces .value == {"example": 0}).
  • If the key is present, it is validated/coerced normally.
Pattern properties (pattern_properties)

For keys matching a regex in pattern_properties, apply the associated validator:

  • Coerced values replace originals (e.g. key "x-example" matching "^x-.*$" with Integer() coerces "123" → 123).
  • On failure, .errors.to_dict() maps the key to the validator's error code.
Additional properties (additional_properties)

Applies to keys not matched by properties or pattern_properties:

  • True: additional keys are kept as-is in .value.
  • None: additional keys are dropped from .value (e.g. resulting in .value == {}).
  • False: additional keys are rejected; .errors.to_dict() maps each offending key to error code "invalid_property".
  • A validator instance: each additional key's value is validated/coerced by that validator. Successful coercion replaces the value in .value; failure maps the key to the validator's error code in .errors.to_dict().
Nested validation

When additional_properties (or a property validator) is itself an Object, validation recurses:

  • Nested coerced values are preserved in the output structure (e.g. {"example": {"nested": "123"}} → {"example": {"nested": 123}}).
  • Nested errors are represented as nested dicts in .errors.to_dict() (e.g. {"example": {"nested": "type"}}).

Integration Notes

  • The Object class must be importable via from typesystem.validators import Object.
  • Use the same base result and error-message infrastructure (typesystem.base.ErrorMessage and the result type) as the existing validators (Boolean, String, Integer, Number, Date, DateTime, Time) in this module.

  1. A plain (non-callable) value — used directly as the default, as before.
  2. A callable taking no arguments — when the default needs to be applied, the callable is called and its return value is used as the default.

When a field with a callable default is not present in the input data during validation, the field's resolved value must equal the result of calling that callable at validation time.

Concretely, for a schema with a Date field whose default is datetime.date.today, validating an empty input mapping ({}) must succeed, and the resulting instance's created attribute must equal datetime.date.today().

Notes

  • Distinguishing a callable default from a plain default must be based on whether the provided default is callable.
  • Existing behavior for non-callable defaults must be preserved.

Overview

The validation API in this codebase must be renamed and restructured. Currently, validation is triggered by a method named .validate() which returns a result object. This method must be renamed to .validate_or_error(), keeping identical behavior and signature. The name validate is being freed up for other use, but this task only requires the validate_or_error entry point to exist and behave as described below.

Required API Surface

Field validators (module: typesystem.fields)

The following field classes must each expose a method:

def validate_or_error(self, value, strict=False)

This applies to all field types, including at least:

  • String
  • Integer
  • Float
  • Boolean
  • Choice
  • Object
  • Date
  • Time
  • DateTime

The strict keyword argument must be accepted (used by Integer, Float, and Boolean).

Schemas (accessible as typesystem.Schema)

Schema subclasses must expose a classmethod:

@classmethod
def validate_or_error(cls, value)

Return Value: ValidationResult

validate_or_error returns a ValidationResult object with the following properties:

  1. Two attributes: .value and .error.

    • On success: .value holds the validated/coerced value; .error is None.
    • On failure: .value is None; .error holds a ValidationError.

  2. Unpackable as a 2-tuple in the order (value, error):

    value, error = validator.validate_or_error(...)

  3. Truthiness: the result is truthy when validation succeeded (no error) and falsy when it failed. Equivalently, bool(result) reflects success.

  4. repr():

    • Success: ValidationResult(value=<repr of value>)
    • Failure: ValidationResult(error=<repr of error>)

ValidationError

An error object with:

  1. Equality: two ValidationError instances constructed with the same text and code compare equal. It must be constructible as:

    ValidationError(text="...", code="...")

  2. .messages() — returns a list of Message instances describing each error.

  3. Dict-like interface — dict(error) produces a mapping from field index to message text:

    • For a single top-level error (no field path), the key is the empty string "", e.g. {"": "Must be a number."}.
    • For object property errors, keys are property names, e.g. {"age": "Must be a number."}.
    • For nested object errors, values are nested dicts, e.g. {"example": {"nested": "Must be a number."}}.
    • Individual entries are accessible by subscript, e.g. error["age"] or error[""].

  4. repr():

    • When the error carries a single message with no field index: ValidationError(text='...', code='...')
    • When the error carries messages with indices (one or more): ValidationError([Message(text='...', code='...', index=[...])]) (a list of Message reprs)

Message

A message object constructible as Message(text="...", code="...") (optionally with an index), with:

  1. Equality based on its fields.
  2. repr():
    • Without an index: Message(text='...', code='...')
    • With an index: Message(text='...', code='...', index=[...])

Validation Behavior (per field type)

All coercion, defaulting, and error semantics remain exactly as they are today; only the method name changes. The specific behaviors that must hold:

String
  • Valid string → returns the string.
  • "" → error text="Must not be blank.", code="blank".
  • None → error text="May not be null.", code="null".
  • Non-string (e.g. 123) → error text="Must be a string.", code="type".
  • String(max_length=10) on too-long input → text="Must have no more than 10 characters.", code="max_length".
  • String(min_length=3) on too-short input → text="Must have at least 3 characters.", code="min_length".
  • String(allow_blank=False) on "" → text="Must not be blank.", code="blank".
  • String(allow_null=True) on None → value None, no error.
  • String(pattern="^[abc]*$") on matching input → returns the value; on non-matching → text="Must match the pattern /^[abc]*$/.", code="pattern".
Integer
  • 123, "123", 123.0 → value 123.
  • None → text="May not be null.", code="null".
  • "abc", True → text="Must be a number.", code="type".
  • 123.1, float("inf"), float("nan") → text="Must be an integer.", code="integer".
  • "123" with strict=True → text="Must be a number.", code="type".
  • Integer(allow_null=True) on None → value None, no error.
  • Integer(maximum=10): 100 → text="Must be less than or equal to 10.", code="maximum"; 10 → value 10.
  • Integer(minimum=3): 1 → text="Must be greater than or equal to 3.", code="minimum"; 3 → value 3.
  • Integer(exclusive_maximum=10) on 10 → text="Must be less than 10.", code="exclusive_maximum".
  • Integer(exclusive_minimum=3) on 3 → text="Must be greater than 3.", code="exclusive_minimum".
  • Integer(multiple_of=10) on 5 → text="Must be a multiple of 10.", code="multiple_of".
Float
  • 123.1 → 123.1; 123 → 123.0; "123.1" → 123.1.
  • None → text="May not be null.", code="null".
  • "abc", True → text="Must be a number.", code="type".
  • float("inf"), float("nan") → text="Must be finite.", code="finite".
  • "123" with strict=True → text="Must be a number.", code="type".
  • Float(allow_null=True) on None → value None, no error.
  • Float(maximum=10.0): 100.0 → text="Must be less than or equal to 10.0.", code="maximum"; 10.0 → value 10.0.
  • Float(minimum=3.0): 1.0 → text="Must be greater than or equal to 3.0.", code="minimum"; 3.0 → value 3.0.
  • Float(exclusive_maximum=10.0) on 10.0 → text="Must be less than 10.0.", code="exclusive_maximum".
  • Float(exclusive_minimum=3.0) on 3.0 → text="Must be greater than 3.0.", code="exclusive_minimum".
  • Float(precision="0.01") on "123.456" → value 123.46 (rounded to the precision).
Boolean
  • True → True; False → False; "True" → True; 1 → True.
  • None → text="May not be null.", code="null".
  • 2 → text="Must be a boolean.", code="type".
  • Boolean(allow_null=True) on None → value None, no error.
  • Boolean(allow_null=True) on "" → value None, no error.
  • "True" with strict=True → text="Must be a boolean.", code="type".
Choice
  • Constructible with choices= as: a list of values, a dict of {key: label}, or a list of (key, label) tuples.
  • A valid choice value/key → returns that value/key.
  • An invalid value → text="Not a valid choice.", code="choice".
  • None → text="May not be null.", code="null".
  • Choice(..., allow_null=True) on None → value None, no error.
Object

Supported constructor keywords: allow_null, min_properties, max_properties, required, properties, pattern_properties, additional_properties.

  • {} → value {}.
  • None → error mapping {"": "May not be null."}.
  • 123 → {"": "Must be an object."}.
  • Dict with a non-string key (e.g. {1: 123}) → {"": "All object keys must be strings."}.
  • Object(allow_null=True) on None → value None, no error.
  • Object(min_properties=1): {} → {"": "Must not be empty."}; {"a": 1} → value {"a": 1}.
  • Object(min_properties=2): {} → {"": "Must have at least 2 properties."}; {"a": 1, "b": 2} → value unchanged.
  • Object(max_properties=2): {} → {}; {"a": 1, "b": 2, "c": 3} → {"": "Must have no more than 2 properties."}.
  • Object(required=["example"]): {"example": 123} → value unchanged; {} → {"example": "This field is required."}.
  • Object(properties={"example": Integer()}): {"example": "123"} → {"example": 123} (coerced); {"example": "abc"} → {"example": "Must be a number."}.
  • Object(pattern_properties={"^x-.*$": Integer()}): {"x-example": "123"} → {"x-example": 123}; {"x-example": "abc"} → {"x-example": "Must be a number."}.
  • Object(properties={"example": Integer(default=0)}): {"example": "123"} → {"example": 123}; {} → {"example": 0} (default applied).
  • Object(additional_properties=False) on {"example": "123"} → {"example": "Invalid property name."}.
  • Object(additional_properties=True) on {"example": "abc"} → value {"example": "abc"} (kept as-is).
  • Object(additional_properties=None) on {"example": "abc"} → value {} (extra properties dropped).
  • Object(additional_properties=Integer()): {"example": "123"} → {"example": 123}; {"example": "abc"} → {"example": "Must be a number."}.
  • Nested objects, e.g. Object(additional_properties=Object(additional_properties=Integer())): {"example": {"nested": "123"}} → {"example": {"nested": 123}}; {"example": {"nested": "abc"}} → {"example": {"nested": "Must be a number."}}.
Date
  • "2049-01-01" → datetime.date(2049, 1, 1).
  • datetime.date(2049, 1, 1) → same value.
  • "20490101" → text="Must be a valid date format.", code="format".
  • "2049-01-32" → text="Must be a real date.", code="invalid".
Time
  • "12:00:01" → datetime.time(12, 0, 1).
  • "12:00:01.001" → datetime.time(12, 0, 1, 1000).
  • "12:00:01.000001" → datetime.time(12, 0, 1, 1).
  • datetime.time(12, 0, 1) → same value.
  • "12.00.01" → text="Must be a valid time format.", code="format".
  • "12:00:60" → text="Must be a real time.", code="invalid".
DateTime
  • "2049-1-1 12:00:00" → datetime.datetime(2049, 1, 1, 12, 0, 0).
  • "2049-1-1 12:00:00.001" → datetime.datetime(2049, 1, 1, 12, 0, 0, 1000).
  • "2049-1-1 12:00:00Z" → the datetime with UTC tzinfo.
  • "2049-1-1 12:00:00-0230" → the datetime with a fixed offset of −2h30m.
  • datetime.datetime(2049, 1, 1, 12, 0, 0) → same value.
  • "2049:01:01 12:00:00" → text="Must be a valid datetime format.", code="format".
  • "2049-01-01 12:00:60" → text="Must be a real datetime.", code="invalid".

Schema Behavior

Schema.validate_or_error(value) validates a dict against the schema's declared fields, returning a ValidationResult:

  • On success, .value is a schema instance whose attributes are the validated/coerced field values, and two instances constructed from equal field values compare equal.
  • Field values are coerced per their field types (e.g. an age field declared as Integer() coerces "123" → 123).
  • Missing required fields produce an error mapping keyed by field name, e.g. {"age": "This field is required."}.
  • Invalid field values produce an error mapping keyed by field name, e.g. {"age": "Must be a number."}.
  • A field with a callable default (e.g. Date(default=datetime.date.today)) uses the result of calling that default when the value is absent.

Schema instances must have a repr() of the form <ClassName>(<field>=<value>, ...), e.g. Example(a='a', b=1).

Import Requirements

The following must be importable:

  • From typesystem.fields: String, Integer, Float, Boolean, Choice, Object, Date, Time, DateTime.
  • As typesystem.String, typesystem.Schema.
  • ValidationError, ValidationResult, and Message types must be accessible for construction and comparison as described above.
