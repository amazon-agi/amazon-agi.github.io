Objective

Fix the StreamOutput class so that writing non-ASCII (Unicode) strings to its underlying stream works correctly without raising errors.

Public API

The class is located at:

cleo/outputs/stream_output.py

Class name: StreamOutput

It is constructed with a writable byte stream object as its first argument:

output = StreamOutput(stream)

The stream object supports the standard binary I/O interface (write, seek, read, returning/accepting bytes).

Required Behavior

StreamOutput must support writing messages that contain non-ASCII Unicode characters (for example, characters such as é, à, ù, and —).

Specifically:

  • Calling the line-writing method writeln(message) with a Unicode string must write that message followed by a newline (\n) to the underlying stream.
  • The bytes written to the underlying stream must be the UTF-8 encoding of the message text plus the newline character. That is, after writing, seeking the stream back to the beginning and reading its contents and decoding those bytes as UTF-8 must yield exactly the original message with a trailing \n.
  • This must hold both for plain ASCII messages and for messages containing arbitrary non-ASCII Unicode characters. No UnicodeDecodeError (or similar encoding-related error) may be raised when the message contains non-ASCII characters.
Example
output = StreamOutput(stream)
output.writeln('féàù—')
output.get_stream().seek(0)
content = output.get_stream().read().decode('utf-8')
# content == 'féàù—\n'

The accessor get_stream() returns the underlying stream object passed to the constructor.

Notes
  • The core requirement is that the internal write operation (which sends the final text to the underlying byte stream) must correctly handle non-ASCII text by encoding it as UTF-8 before writing.
  • ASCII-only messages must continue to behave identically (still encoded and readable as UTF-8).
02 Update ProgressHelper so repeated progress-bar renders replace the current terminal line without first clearing it using a separate run of spaces. 732 words · source specification

Overview

Update ProgressHelper so repeated progress-bar renders replace the current terminal line without first clearing it using a separate run of spaces. Progress output must also continue to support formatted bar characters when written to decorated output streams.

The change is limited to progress rendering and its interaction with existing output formatting.

Public APIs

The following existing APIs must remain available:

ProgressHelper
  • start(output, max) initializes a progress session at zero for the supplied maximum. Starting alone does not render a progress line.
  • display() renders the current progress state.
  • advance() advances by one step and renders the updated state under the default redraw settings.
  • get_percent() returns progress as a normalized ratio of current / max, not the displayed integer percentage.
  • set_bar_character(character) configures the string used for each completed bar unit. The string may contain Cleo formatting tags.
StreamOutput
  • A stream is accepted as the first constructor argument.
  • The constructor continues to accept decorated as a keyword argument, including StreamOutput(stream, decorated=True).
  • get_stream() returns the underlying stream.
  • Decorated output converts formatting tags to ANSI sequences. Non-decorated output retains its existing behavior of producing plain text without formatting tags.

Progress Rendering

Default line layout

The normal progress format is:

 {current}/{max} [{bar}] {percent}%

Alignment and widths are significant:

  • The current value is right-aligned to the decimal width of the maximum.
  • The format contributes one space before the aligned current value.
  • The default logical bar width is 28 characters.
  • Before completion, the bar contains:
    1. completed bar units,
    2. the current-position marker >,
    3. - filler up to the configured bar width.
  • The displayed percentage is the normalized progress multiplied by 100 and rendered as an integer, right-aligned in a three-character field.
  • There is one separator space between ] and the percentage field.

For a maximum of 50, displaying the initial state and then advancing five times produces these logical lines:

  0/50 [>---------------------------]   0%
  1/50 [>---------------------------]   2%
  2/50 [=>--------------------------]   4%
  3/50 [=>--------------------------]   6%
  4/50 [==>-------------------------]   8%
  5/50 [==>-------------------------]  10%

Thus, advances that do not cross a bar-unit boundary update the counter and percentage without adding a completed bar unit.

Repeated display and line replacement

Every rendered progress message, including the first explicit display(), is emitted as:

  1. exactly one carriage return (\r);
  2. the newly rendered message;
  3. any trailing spaces needed to cover remnants of a longer previously emitted message.

No newline is added.

If the new message is shorter than the prior rendered message, right-pad the new message with spaces to the prior message length. If it is equal in length or longer, do not add padding.

Do not clear the old line by emitting spaces followed by another carriage return. In particular, consecutive equal-width renders must appear in the stream as:

\r<first message>\r<second message>\r<third message>

There must be no interposed blanking run and no second carriage return per render.

Decorated Bar Characters

A custom bar character may contain formatting markup. For example:

progress.set_bar_character("<comment>=</comment>")

When used with a decorated StreamOutput:

  • each completed unit is independently formatted by the output formatter;
  • a comment-styled = is emitted as a yellow ANSI-styled = followed by a reset;
  • multiple completed units concatenate directly, with each unit retaining its own opening and reset sequences;
  • the > marker and - filler remain unstyled;
  • ANSI control sequences do not change the bar's logical width;
  • no extra carriage returns, clearing spaces, raw formatting tags, or stray characters may be introduced.

The carriage-return and overwrite rules are the same for decorated and non-decorated output.

Percentage State

After start(output, max), get_percent() reports zero. Each parameterless advance() increments the current step by one and updates the ratio accordingly. For example, after one advance with a maximum of 50, the ratio is 1 / 50, while the rendered percentage is 2%.

Compatibility and Non-Goals

  • Preserve existing progress customization behavior, including custom formats and bar characters.
  • Preserve existing StreamOutput formatting, stream access, verbosity, encoding, and raw-output behavior.
  • Do not change command handling, other helpers, formatters, input processing, or application behavior.
  • No new terminal-clearing escape sequence is required; replacement continues to use carriage return and optional right-padding.
  • No change is required to the existing semantics of advancing by an explicitly supplied step count.

Overview

The Application class (importable as Application from the project's application module, matching existing imports) must expose three decorator factory methods that can be stacked/combined on a single function to register a command along with its arguments and options.

Required Public API

Add the following methods to the Application class:

application.command(name, description=None)

Returns a decorator. When applied to a function, it registers a command under the given name.

application.argument(name, description=None, required=False, is_list=False)

Returns a decorator that declares an argument to be attached to the command being defined for the decorated function.

application.option(name, shortcut=None, description=None, value_required=False, is_list=False)

Returns a decorator that declares an option to be attached to the command being defined for the decorated function.

Combining Behavior

These decorators must work together when stacked on the same function, e.g.:

@application.command('decorated_foo', description='Foo command')
@application.argument('foo', description='Foo argument', required=True, is_list=True)
@application.option('bar', 'b', description='Bar option', value_required=True, is_list=True)
def decorated_foo_code(i, o):
    """Foo Description"""
    o.writeln('called')

Decorators are applied bottom-up (innermost first). The argument and option decorators contribute definition entries; the command decorator finalizes registration. After all decorators have been applied, the command must be fully registered and accessible from the application.

Resulting State After Registration

Given the example above, the following must hold:

  1. Registration & lookup

    • application.has('decorated_foo') returns True.
    • application.get('decorated_foo') returns the registered command object.

  2. Command code and metadata

    • The command's _code attribute equals the original decorated function object (decorated_foo_code).
    • command.get_description() returns 'Foo command'.
    • command.get_aliases() contains the string 'decorated_foo_code' (the decorated function's name).

  3. Argument definition

    • command.get_definition().get_argument('foo') returns the argument object with:
      • get_description() → 'Foo argument'
      • is_required() → True
      • is_list() → True

  4. Option definition

    • command.get_definition().get_option('bar') returns the option object with:
      • get_shortcut() → 'b'
      • get_description() → 'Bar option'
      • is_value_required() → True
      • is_list() → True

Notes

  • The command's definition (via command.get_definition()) must include every argument and option declared through the stacked argument/option decorators.
  • The registered command must have its aliases include the decorated function's __name__.
  • The registered command's _code must reference the exact function that was decorated.

These four accessor result groups define the complete required behavior for this task.

An exception type raised when validation fails.

A base validator with the following interface:

Float

Field Width Rules

  • %current% and %max% are formatted so that current is right-justified to the string width of max.
    • Examples: max 10 → width 2 (" 0/10", "10/10"); max 50 → width 2; max 200 → width 3 (" 0/200", "200/200").
  • For an indeterminate bar (no max), %current% is right-justified in a field of width 4 (e.g. " 0", " 3", " 5").

Bar Rendering

The bar region consists of, left to right:

  1. A run of completed characters (default =), one per completed unit of the bar width.
  2. A single progress head character (default >), unless the bar is fully complete.
  3. Empty characters (default -) filling the remainder of the bar width.

Rules:

  • Default bar width is 28 characters.
  • With a known maximum: the number of completed characters is floor(percent_complete * bar_width), where percent_complete is current/max clamped so it never reaches 100% until current >= max. When complete (current >= max), the bar is entirely completed characters with no progress head, and percent is 100. Before completion, percent is floor(current/max * 100) (so it can be 99% at 199/200 but shows 100% only at 200/200).
    • Examples (width 28, max 50): 1/50 → > head with zero complete chars → [>--------------------------] at 2%; 2/50 → [=>--------------------------] at 4%; 15/50 → [========>-------------------] at 30%; 25/50 → [==============>-------------] at 50%.
  • With no known maximum (indeterminate): the number of completed characters equals current (capped at the bar width), followed by the progress head, then empty characters. There is no percent shown.
    • Examples (width 28): current 0 → [>---------------------------]; current 1 → [->--------------------------] (note: with a bar character of - and default here the completed run is drawn then head — see below); current 3 → [--->------------------------]; current 5 → [----->----------------------].
    • Note on indeterminate default appearance: the completed characters and empty characters are drawn such that for current N the bar shows N leading marks, then the head >, then dashes filling to width. When set_bar_character('■') is used with current 3 the bar reads [■■■>------------------------].
Bar width when max exceeds width

If max is smaller than or equal to nothing special happens; the bar always uses the configured bar width (default 28) regardless of max, scaling by percentage.

Advancing past max

advance and set_progress may push current beyond the original max. When this happens, the maximum is raised to equal the new current, so the bar shows as complete at 100% with current/current.

  • Example (max 10): at 9 → 9/10 [=========================>--] 90%; advance to 10 → 10/10 [============================] 100%; advance to 11 → 11/11 [============================] 100%.

Redraw / Overwrite Behavior (decorated output)

Each render overwrites the previously displayed line(s):

  • Every rendered line is prefixed with a carriage return control character \x0D.
  • If the format spans multiple lines (N embedded newlines), the render is additionally prefixed with the ANSI sequence \033[<N>A (move cursor up N lines) immediately after the carriage return. For single-line formats there is no cursor-up sequence.
  • The concatenation of all renders (in the order they occur) is what appears on the stream.

So a sequence of single-line renders produces, for each render: \x0D + the formatted line.

Overwriting with a shorter line

When a new render is shorter than the previously rendered line, the new line must be padded with trailing spaces so it fully covers (erases) the longer previous line.

  • Example: previous line 1/50 [>---------------------------] 2% (with percent), new format without percent yields the bar line padded so its visible length matches: 2/50 [=>--------------------------] (trailing spaces filling the space the removed 2% occupied).
clear

clear renders a line consisting solely of spaces, sized to fully overwrite the last rendered line. Following the same overwrite prefix rules, this produces \x0D + a run of spaces the width of the previous line.

  • Example after a 50-wide bar line: a line of spaces the same visible width as 25/50 [==============>-------------] 50%.

Verbosity

If the output's verbosity is VERBOSITY_QUIET, display (and any render) writes nothing to the stream.

Non-Decorated Output

When the output is not decorated:

  • No \x0D and no cursor-movement sequences are emitted.
  • Redraws are throttled/deduplicated by percentage so that only meaningful progress changes are emitted: a new line is written only when the integer percentage changes by a visible increment (for a 200-step bar with a 28-char bar the emitted lines correspond to 0%, 10%, 20%, …, 90%, 100%).
  • Each emitted line is separated from the next by the OS line separator (os.linesep).
  • Example for max=200, advancing one step 200 times then finish(), the emitted lines (joined by os.linesep) are:
       0/200 [>---------------------------]   0%
  20/200 [==>-------------------------]  10%
  40/200 [=====>----------------------]  20%
  60/200 [========>-------------------]  30%
  80/200 [===========>----------------]  40%
 100/200 [==============>-------------]  50%
 120/200 [================>-----------]  60%
 140/200 [===================>--------]  70%
 160/200 [======================>-----]  80%
 180/200 [=========================>--]  90%
 200/200 [============================] 100%

Multibyte Support

Bar characters may be multibyte (e.g. ■). Field widths and padding must be computed by character count, not byte count, so alignment and bar geometry remain correct.

Customization Example (integration)

bar = ProgressBar(output, 10)
bar.set_bar_width(10)
bar.set_bar_character('_')
bar.set_empty_bar_character(' ')
bar.set_progress_character('/')
bar.set_format(' %current%/%max% [%bar%] %percent:3s%%')
bar.start()      # renders "  0/10 [/         ]   0%"
bar.advance()    # renders "  1/10 [_/        ]  10%"

Here, with bar width 10, current 0 of 10 → zero complete chars, head /, 9 empty spaces → [/ ]; current 1 → one _, head /, 8 spaces → [_/ ].

Summary of Required Behaviors

  • Correct default formats chosen by presence of a maximum.
  • Correct field-width alignment of current/max and percent.
  • Correct bar geometry (complete chars, head, empty chars) for both determinate and indeterminate modes.
  • Percentage never shows 100% before completion.
  • Advancing past max raises max and shows 100%.
  • Proper carriage-return / cursor-up overwrite prefixes for decorated output.
  • Padding of shorter lines to erase longer previous lines.
  • clear erases the current line with spaces.
  • finish works even without start.
  • Quiet verbosity suppresses all output.
  • Non-decorated output emits deduplicated lines joined by os.linesep.
  • Multibyte-safe width calculations.
