Task Description

Goal

Repair the StreamOutput class so that writing non-ASCII (Unicode) strings to its underlying stream works correctly without errors being raised.

Public API

The class can be found at:

cleo/outputs/stream_output.py

Name of the class: StreamOutput

Its constructor takes a writable byte stream object as its first argument:

output = StreamOutput(stream)

The stream object offers the standard binary I/O interface (write, seek, read, returning/accepting bytes).

Required Behavior

Writing messages that contain non-ASCII Unicode characters (for example, characters such as é, à, ù, and —) must be supported by StreamOutput.

In particular:

  • When the line-writing method writeln(message) is called with a Unicode string, that message followed by a newline (\n) must be written to the underlying stream.
  • The bytes that get written to the underlying stream must be the UTF-8 encoding of the message text plus the newline character. In other words, after writing, seeking the stream back to the beginning, reading its contents, and decoding those bytes as UTF-8 must yield exactly the original message with a trailing \n.
  • This must hold both for plain ASCII messages and for messages that contain arbitrary non-ASCII Unicode characters. When the message contains non-ASCII characters, no UnicodeDecodeError (or similar encoding-related error) may be raised.
Example
output = StreamOutput(stream)
output.writeln('féàù—')
output.get_stream().seek(0)
content = output.get_stream().read().decode('utf-8')
# content == 'féàù—\n'

The accessor get_stream() returns the underlying stream object that was passed to the constructor.

Remarks
  • At its core, the requirement is that the internal write operation (the one that sends the final text to the underlying byte stream) must handle non-ASCII text correctly by encoding it as UTF-8 before writing.
  • Messages that contain only ASCII must continue to behave identically (still encoded and readable as UTF-8).
02 Modify ProgressHelper so that repeated progress-bar renders replace the current terminal line rather than first clearing it with a separate run of spaces. 793 words · source specification, reworded by GLM-5.3-Flash

Task Description

Summary

Modify ProgressHelper so that repeated progress-bar renders replace the current terminal line rather than first clearing it with a separate run of spaces. Progress output must also keep supporting formatted bar characters when it is written to decorated output streams.

The change is confined to progress rendering and to how it interacts with the existing output formatting.

Public APIs

The existing APIs listed below must remain available:

ProgressHelper
  • A call to start(output, max) initializes a progress session at zero for the supplied maximum. Starting on its own does not render a progress line.
  • display() renders the progress state as it currently stands.
  • advance() moves the progress forward by one step and renders the updated state under the default redraw settings.
  • get_percent() returns the progress as a normalized ratio of current / max, rather than the displayed integer percentage.
  • set_bar_character(character) configures the string that is used for each completed bar unit. That string may contain Cleo formatting tags.
StreamOutput
  • The constructor accepts a stream as its first argument.
  • The constructor still accepts decorated as a keyword argument, including in the form StreamOutput(stream, decorated=True).
  • get_stream() returns the stream that underlies the output.
  • When output is decorated, formatting tags are converted to ANSI sequences. Non-decorated output keeps its existing behavior of producing plain text with no formatting tags.

Rendering Progress

Line layout by default

The standard progress format is:

 {current}/{max} [{bar}] {percent}%

The alignment and widths matter:

  • The current value is right-aligned to the decimal width of the maximum.
  • The format supplies one space before the aligned current value.
  • The logical bar width is 28 characters by default.
  • Before completion is reached, the bar consists of:
    1. completed bar units,
    2. the current-position marker >,
    3. - filler up to the configured bar width.
  • The percentage shown is the normalized progress multiplied by 100, rendered as an integer and right-aligned in a three-character field.
  • One separator space appears between ] and the percentage field.

With a maximum of 50, displaying the initial state and then advancing five times produces the following logical lines:

  0/50 [>---------------------------]   0%
  1/50 [>---------------------------]   2%
  2/50 [=>--------------------------]   4%
  3/50 [=>--------------------------]   6%
  4/50 [==>-------------------------]   8%
  5/50 [==>-------------------------]  10%

In other words, when an advance does not cross a bar-unit boundary, the counter and percentage are updated without a completed bar unit being added.

Repeated rendering and line replacement

Each rendered progress message — including the first explicit display() — is emitted as:

  1. exactly one carriage return (\r);
  2. the message as newly rendered;
  3. any trailing spaces needed to cover remnants of a previously emitted message that was longer.

No newline is appended.

When the new message is shorter than the prior rendered message, right-pad the new message with spaces up to the prior message length. When it is equal in length or longer, add no padding.

The old line must not be cleared by emitting spaces followed by another carriage return. In particular, consecutive renders of equal width must appear in the stream as:

\r<first message>\r<second message>\r<third message>

There must be no blanking run interposed and no second carriage return per render.

Bar Characters in Decorated Output

A custom bar character may contain formatting markup. As an example:

progress.set_bar_character("<comment>=</comment>")

When it is used with a decorated StreamOutput:

  • the output formatter formats each completed unit independently;
  • a = with comment styling is emitted as a yellow ANSI-styled = followed by a reset;
  • multiple completed units concatenate directly, and each unit retains its own opening and reset sequences;
  • the > marker and the - filler remain unstyled;
  • ANSI control sequences leave the bar's logical width unchanged;
  • no extra carriage returns, clearing spaces, raw formatting tags, or stray characters may be introduced.

Decorated and non-decorated output follow the same carriage-return and overwrite rules.

State of the Percentage

After start(output, max) has been called, get_percent() reports zero. Each parameterless advance() increments the current step by one and updates the ratio correspondingly. For instance, after a single advance with a maximum of 50, the ratio is 1 / 50, while the rendered percentage is 2%.

Compatibility and Non-Goals

  • Existing progress customization behavior, including custom formats and bar characters, must be preserved.
  • Existing StreamOutput formatting, stream access, verbosity, encoding, and raw-output behavior must be preserved.
  • Command handling, other helpers, formatters, input processing, and application behavior must not be changed.
  • A new terminal-clearing escape sequence is not required; replacement keeps using carriage return and optional right-padding.
  • The existing semantics of advancing by an explicitly supplied step count require no change.

Overview

Three decorator methods are to be added to the Application class (in cleo.application, imported as from cleo.application import Application) that make it possible for a plain function to be registered as a command by decorating it. While registering a fully-configured command into the application, each decorator returns the original function unchanged (so the decorated name still refers to the function).

The decorated function serves as the command's callable "code": a function that takes two positional parameters (an input object and an output object).

Decorators to Add

All three are methods on Application meant to be applied as decorators, and each one accepts arguments that configure the resulting command. Once decoration has taken place, the command must be retrievable via application.get(<name>), and application.has(<name>) must return True.

For every decorator:

  • The command object that gets registered must expose the decorated function on its _code attribute (that is, command._code is the exact function object that was decorated).
  • The decorator itself must return the original function object, unmodified.
1. Application.command

Usage signature:

@application.command(name, description=...)
def some_function(i, o):
    ...

Behavior:

  • name (the first positional argument) is used as the command's name; application.has(name) returns True and application.get(name) returns the command.
  • The command's description is set by the description keyword argument and is retrievable via command.get_description().
  • The name of the decorated function itself (e.g. "some_function") must be added to the command's aliases; command.get_aliases() must contain that name.
2. Application.argument

Usage signature:

@application.argument(name, description=..., required=..., is_list=...)
def some_function(i, o):
    """Docstring becomes the command description."""
    ...

Behavior:

  • No explicit command name is passed. The command gets registered under the decorated function's own name (e.g. "some_function"); application.has("some_function") returns True.
  • The command's description comes from the decorated function's docstring (its __doc__) and is retrievable via command.get_description().
  • The decorator configures a single command argument, named name (the first positional argument), on the command's definition; this argument is retrievable via command.get_definition().get_argument(name). That argument must reflect:
    • description → argument.get_description()
    • required (truthy) → argument.is_required() returns True
    • is_list (truthy) → argument.is_list() returns True
3. Application.option

Usage signature:

@application.option(name, shortcut, description=..., value_required=..., is_list=...)
def some_function(i, o):
    """Docstring becomes the command description."""
    ...

Behavior:

  • No explicit command name is passed. The command gets registered under the decorated function's own name; application.has("some_function") returns True.
  • The command's description comes from the decorated function's docstring (__doc__), retrievable via command.get_description().
  • The decorator configures a single command option named name (the first positional argument) together with shortcut shortcut (the second positional argument) on the command's definition; this option is retrievable via command.get_definition().get_option(name). That option must reflect:
    • shortcut → option.get_shortcut()
    • description → option.get_description()
    • value_required (truthy) → option.is_value_required() returns True
    • is_list (truthy) → option.is_list() returns True

Notes About the Command Object

The command that each decorator produces is a normal application command consistent with the existing framework:

  • Its _code is set to the decorated function.
  • It supports get_description(), get_aliases(), and get_definition().
  • Its definition supports get_argument(name) and get_option(name), and the argument/option objects returned by them support get_description(), is_required(), is_list() (argument) and get_shortcut(), get_description(), is_value_required(), is_list() (option).

The signature of the decorated callable is (input, output) — the two parameters may be given arbitrary names; only positional invocation matters.

Task Specification: Composable Command Decorators

Overview

Three decorator factory methods must be exposed by the Application class (importable as Application from the project's application module, consistent with the existing imports). These methods can be stacked/combined on a single function in order to register a command together with its arguments and options.

Required Public API

The Application class is to be extended with the following methods:

application.command(name, description=None)

The method returns a decorator. Applying that decorator to a function registers a command under the specified name.

application.argument(name, description=None, required=False, is_list=False)

The method returns a decorator that declares an argument, which is to be attached to the command being defined for the decorated function.

application.option(name, shortcut=None, description=None, value_required=False, is_list=False)

The method returns a decorator that declares an option, which is to be attached to the command being defined for the decorated function.

Behavior When Combined

When they are stacked on the same function, these decorators must work together, e.g.:

@application.command('decorated_foo', description='Foo command')
@application.argument('foo', description='Foo argument', required=True, is_list=True)
@application.option('bar', 'b', description='Bar option', value_required=True, is_list=True)
def decorated_foo_code(i, o):
    """Foo Description"""
    o.writeln('called')

The decorators are applied bottom-up (innermost first). Definition entries are contributed by the argument and option decorators, while the command decorator finalizes registration. Once all decorators have been applied, the command must be fully registered and accessible from the application.

State After Registration

For the example above, the following must hold:

  1. Registration and lookup

    • The call application.has('decorated_foo') returns True.
    • The call application.get('decorated_foo') returns the registered command object.

  2. Code and metadata of the command

    • The _code attribute of the command is equal to the original decorated function object (decorated_foo_code).
    • A call to command.get_description() returns 'Foo command'.
    • The result of command.get_aliases() contains the string 'decorated_foo_code' (the decorated function's name).

  3. The argument's definition

    • The call command.get_definition().get_argument('foo') returns the argument object, which has:
      • get_description() → 'Foo argument'
      • is_required() → True
      • is_list() → True

  4. The option's definition

    • The call command.get_definition().get_option('bar') returns the option object, which has:
      • get_shortcut() → 'b'
      • get_description() → 'Bar option'
      • is_value_required() → True
      • is_list() → True

Notes

  • Every argument and option declared through the stacked argument/option decorators must be included in the command's definition (obtained via command.get_definition()).
  • The aliases of the registered command must include the decorated function's __name__.
  • The _code of the registered command must reference the exact function that was decorated.

These four groups of accessor results define the complete required behavior for this task.

Summary

The constructor:

Overview

Build a Parser class that can take a command "signature" string and turn it into structured definitions of the command name, its arguments, and its options.

Public API

Parser.parse(expression: str) -> dict

The method receives a single signature string and returns a dictionary holding exactly these keys:

  • 'name' — a string giving the command name.
  • 'arguments' — a list of argument definition objects (in the order they appear).
  • 'options' — a list of option definition objects (in the order they appear).

Format of the Signature String

A signature string starts with the command name, which may be followed by any number of whitespace-separated tokens, each enclosed in curly braces {...}.

  • Arguments are tokens that are not prefixed with --.
  • Options are tokens that are prefixed with --.

The command name is the portion of the string that comes before the first {. Arbitrary runs of whitespace may separate tokens (including when the expression is put together from multiple concatenated substrings). Whitespace around the name and inside the tokens must be handled gracefully.

Syntax of an Argument Token

Inside the braces, an argument token takes the form:

name[modifiers][ : description]
  • name — the argument name.
  • Modifiers that may appear after the name:
    • ? — the argument is optional (not required).
    • * — the argument accepts a list of values.
    • ?* — optional and a list.
    • (no modifier present) — the argument is required and not a list.
    • * on its own — a list and required.
  • An optional : description suffix (a colon surrounded by spaces) supplies the argument's description. Whitespace surrounding the description must be stripped.
Syntax of an Option Token

Inside the braces, an option token starts with the -- prefix and takes the form:

--[shortcut|]name[modifiers][ : description]
  • An optional shortcut may come before the name, separated from it by | (e.g. --o|option). When a shortcut is present, the text before | (after the --) is the shortcut.
  • name — the option name.
  • Modifiers that may appear after the name:
    • = — the option accepts a single value.
    • =* — the option accepts a list of values (and accepts a value).
    • (when there is no =) — the option is a flag that does not accept a value.
  • An optional : description suffix supplies the option's description, with surrounding whitespace stripped.

Argument objects must expose the following:
  • get_name() -> str — the argument name.
  • get_description() -> str — the description (as parsed; empty if none was given).
  • is_list() -> bool — True when the argument was marked with *.
  • is_required() -> bool — True unless the argument was marked with ?.
Option objects must expose the following:
  • get_name() -> str — the option name.
  • get_shortcut() — the shortcut string when one was given (e.g. 'o').
  • get_description() -> str — the description (as parsed; empty if none was given).
  • accept_value() -> bool — True when the option was marked with = or =*, False otherwise.
  • is_list() -> bool — True when the option was marked with =*.

For 'command:name {argument*} {--option=}':

  • option 'option': accept_value() = True

For 'command:name {argument?*} {--option=*}':

  • argument 'argument': is_list() = True, is_required() = False
  • option 'option': accept_value() = True, is_list() = True

  • argument 'argument': description 'The argument description.', is_list() = True, is_required() = False
  • option 'option': description 'The option description.', accept_value() = True, is_list() = True

  • option 'option': get_shortcut() = 'o', accept_value() = False

For 'command:name {--o|option=}':

  • option 'option': get_shortcut() = 'o', accept_value() = True

For 'command:name {--o|option=*}':

  • option 'option': get_shortcut() = 'o', accept_value() = True, is_list() = True

For 'command:name {--o|option=* : The option description.}':

  • option 'option': get_shortcut() = 'o', description 'The option description.', accept_value() = True, is_list() = True

A TableStyle that has just been constructed comes with these defaults: horizontal -, vertical |, crossing +, one space per side of cell content, and right-side padding with left alignment.
  • The number of physical columns is the greatest occupied column index to be found among headers and body rows, once colspan has been applied and the positions held by active row spans have been skipped. Even where a span is the only thing covering a column, that column still exists as an independent, physical one.
  • Column widths must be computed according to the exact rules that follow:
    • L is to denote the length of a cell's longest visible line once formatting tags have been removed, and S that cell's colspan.
    • The unpadded width of the physical column where a cell begins receives floor(L / S) from that cell.
    • The span's other covered columns do not have this contribution copied over to them. Only cells that start in those columns in other rows supply width contributions to them.
    • For each physical column, it is the maximum contribution among all header and body cells that start in it which applies; where no such contribution exists, the column's unpadded width is zero.
    • Under the default and borderless styles, each physical column's rendered width comes to its unpadded width with two spaces of cell padding added.
    • Accordingly, when a lone three-character cell spans two columns, the horizontal segments in the default style measure three characters and two characters wide, in that order. Zero unpadded width is contributed by one-character cells whose colspans exceed one, which is why covered columns that are otherwise empty end up with default border segments two characters long.
  • For a spanning content line, the vertical borders within its span are suppressed, with those positions pressed into service as part of the field the cell renders. That is not what top, bottom, header, or full-row separator lines do — they leave those physical column divisions unsuppressed, with a crossing kept at every boundary between physical columns.
  • Placement of a row span advances left-to-right, to the next unoccupied physical position. When both rowspan and colspan belong to one cell, that cell's rectangular range is reserved in its entirety, and every reserved position is skipped by the values in the logical rows that come after.
  • Should a row span reach past the rows that were supplied, enough implicit empty logical rows are created for the requested span to be completed.
  • Where multiline row spans are involved, row heights must comply with this contract:
    • To start with, every logical row possesses at least one visual line, and it is tall enough for every non-row-spanning cell that starts in it.
    • If the visible lines of a row-spanning cell outnumber the heights of the rows it covers taken together, all of the additional height goes to the last logical row among those covered.
    • Next, the lines of the spanning cell are emitted in an unbroken run through the visual lines of the covered rows; positions that go unused are blank.
    • Hence, with a four-line value spanning two rows that are otherwise single-line, the first of the covered rows ends up with one visual line and the second with three. Beside the spanning cell's first and second lines stand the ordinary neighboring values belonging to the first and second logical rows, whereas the third and fourth lines have neighbors that are blank, unless multiline content of some other kind occupies those positions.
  • Every header row has a horizontal separator emitted after it — not only the complete header block does. Consequently, multiple header rows end up with full-width separators in between. The separator that trails the last header row is also the divider between header and body or, where no body exists, the closing border; no duplicate closing line gets added.
  • Where a TableSeparator finds itself inside a row, the same active-rowspan skipping rules that apply to an ordinary cell decide its placement. The segment assigned to it is filled with the horizontal border character over the entire rendered width of that physical column, and the normal spaces at cell sides are left out. At the segment's left and right boundaries it is vertical border characters that remain — crossing characters do not.
  • Exactly one line separator brings every nonempty render to a close. When render() is called again and again, complete tables are appended directly after the final newline that came just before, with no additional blank line and with no span/layout state retained from the preceding call.

Task Specification: Implementing a ProgressBar Helper

Overview

Implement a ProgressBar class that draws a text-based progress bar onto an output stream, replacing the current line on every redraw. It must be possible to import it as:

from cleo.helpers import ProgressBar

The bar writes to a StreamOutput instance (from cleo.outputs.stream_output). You may assume this class already exists and exposes the behavior described below.

Supporting Output Contract (must be satisfied for the bar to function)

StreamOutput is constructed with:

StreamOutput(stream, decorated=True, verbosity=StreamOutput.VERBOSITY_NORMAL)
  • stream is a binary stream open for writing (e.g. io.BytesIO).
  • Class constants exposed on it include VERBOSITY_QUIET and VERBOSITY_NORMAL.
  • It exposes get_stream(), which returns the underlying stream.
  • Text sent to the output is encoded to bytes on the stream.
  • With decorated=True, ANSI control sequences for cursor movement are emitted (see the rendering rules below). With decorated=False, no cursor-movement sequences are emitted, and every render is written on its own line, separated by the OS line separator (os.linesep).
  • At verbosity VERBOSITY_QUIET, nothing at all is written.

Public API

Constructor
ProgressBar(output, max=0)
  • output: a StreamOutput.
  • max: the maximum number of steps (an integer). A value of 0 (or leaving it unset) means the bar has no known maximum (indeterminate total).
Methods
  • start(max=None) — Start or reset the progress. Sets the current step to 0. If max is provided, it becomes the new maximum. Renders the bar immediately.
  • advance(step=1) — Add step to the current step and render again.
  • set_progress(step) — Assign an absolute value to the current step and render again.
  • display() — Render the bar in its current state, without changing progress.
  • finish() — Render the bar as completed. Even if the bar has never been started, it must still render as complete.
  • clear() — Write blanks over the current line (spaces sized to the last rendered line), effectively erasing the visible bar.
  • set_format(format) — Set the output format. Accepts a named built-in format (e.g. 'normal') or a raw format string containing placeholders (see the Format section).
  • set_bar_width(width) — Set how wide (in characters) the bar region is.
  • set_bar_character(char) — Set the character used for the bar's completed portion.
  • set_empty_bar_character(char) — Set the character used for the bar's empty portion.
  • set_progress_character(char) — Set the character used for the progress head that moves along the bar.

Format and Placeholders

A format string may contain the following placeholders:

  • %current% — the current step, right-justified in a field whose width equals the number of characters needed to display the maximum (see the width rules below).
  • %max% — the value of the maximum.
  • %bar% — the bar region as rendered (see Bar Rendering).
  • %percent:3s% — the completion percentage as an integer, right-justified in a field of width 3, with a % sign literally following when the format includes one.
Named Formats

Two built-in named formats are needed; they are selected automatically based on whether a maximum is known, and each is also selectable by name:

  • normal (applied when a maximum IS known):

     %current%/%max% [%bar%] %percent:3s%%

    Example rendered with max 10 and current 0: 0/10 [>---------------------------] 0%

  • The indeterminate format (applied when max is 0/unknown):

     %current% [%bar%]

    Example rendered with current 0: 0 [>---------------------------]

When no format has been set explicitly, the correct default is picked automatically from whether a maximum is known at the time rendering first occurs (i.e. after a max has been supplied by start/construction). Explicitly setting the 'normal' format must produce identical output to the automatic normal selection.

Rules for Field Widths

  • %current% and %max% are formatted such that current is right-justified to the string width of max.
    • Examples: with max 10 → width 2 (" 0/10", "10/10"); with max 50 → width 2; with max 200 → width 3 (" 0/200", "200/200").
  • For an indeterminate bar (no max), %current% is right-justified within a field of width 4 (e.g. " 0", " 3", " 5").

Bar Rendering

The bar region is made up of, from left to right:

  1. A run of completed characters (default =), one for each completed unit of the bar width.
  2. One single progress head character (default >), unless the bar is fully complete.
  3. Empty characters (default -) filling the rest of the bar width.

Rules:

  • The bar width defaults to 28 characters.
  • With a known maximum: the number of completed characters is floor(percent_complete * bar_width), where percent_complete is current/max clamped so that it never reaches 100% until current >= max. Once complete (current >= max), the bar consists entirely of completed characters with no progress head, and percent is 100. Before completion, percent is floor(current/max * 100) (so 99% can occur at 199/200, but 100% shows only at 200/200).
    • Examples (width 28, max 50): 1/50 → a > head with zero complete chars → [>--------------------------] at 2%; 2/50 → [=>--------------------------] at 4%; 15/50 → [========>-------------------] at 30%; 25/50 → [==============>-------------] at 50%.
  • With no known maximum (indeterminate): the number of completed characters equals current (capped at the bar width); after it come the progress head and then the empty characters. No percent is shown.
    • Examples (width 28): current 0 → [>---------------------------]; current 1 → [->--------------------------] (note: with a bar character of - and the default here, the completed run is drawn then head — see below); current 3 → [--->------------------------]; current 5 → [----->----------------------].
    • Note on the indeterminate default look: the completed characters and the empty characters are drawn so that, for current N, the bar shows N leading marks, then the head >, then dashes filling out to the width. When set_bar_character('■') is used with current 3, the bar reads [■■■>------------------------].
Bar width when max exceeds the width

If max is smaller than or equal to, nothing special happens; the bar always uses the configured bar width (default 28), regardless of max, scaling by percentage.

Advancing past max

advance and set_progress may push current beyond the original max. When that happens, the maximum is raised so that it equals the new current, and the bar therefore shows as complete at 100% with current/current.

  • Example (max 10): at 9 → 9/10 [=========================>--] 90%; advancing to 10 → 10/10 [============================] 100%; advancing to 11 → 11/11 [============================] 100%.

Redraw / Overwrite Behavior (decorated output)

Every render replaces the line(s) shown previously:

  • Every rendered line is prefixed by a carriage return control character \x0D.
  • If the format spans multiple lines (N embedded newlines), the render is additionally prefixed with the ANSI sequence \033[<N>A (move cursor up N lines), placed immediately after the carriage return. Single-line formats have no cursor-up sequence.
  • What appears on the stream is the concatenation of all renders, in the order they occur.

So a run of single-line renders produces, for each render: \x0D + the formatted line.

Overwriting with a shorter line

If the newly rendered line is shorter than the line rendered before it, the new line must be padded with trailing spaces so that it fully covers (erases) the longer previous line.

  • Example: previous line 1/50 [>---------------------------] 2% (with percent); a new format without percent yields the bar line padded so that its visible length matches: 2/50 [=>--------------------------] (trailing spaces filling the space the removed 2% occupied).
clear

clear renders a line made up solely of spaces, sized so that it fully overwrites the last rendered line. Following the same overwrite prefix rules, this produces \x0D + a run of spaces as wide as the previous line.

  • Example: after a 50-wide bar line, a line of spaces with the same visible width as 25/50 [==============>-------------] 50%.

Verbosity

If the output's verbosity is VERBOSITY_QUIET, nothing is written to the stream by display (or by any render).

Non-Decorated Output

When the output is not decorated:

  • Neither \x0D nor cursor-movement sequences are emitted.
  • Redraws are throttled/deduplicated by percentage so that only meaningful progress changes are emitted: a new line is written only when the integer percentage changes by a visible increment (for a 200-step bar with a 28-char bar, the emitted lines correspond to 0%, 10%, 20%, …, 90%, 100%).
  • The OS line separator (os.linesep) separates each emitted line from the next.
  • Example: for max=200, advancing one step 200 times and then calling finish(), the emitted lines (joined by os.linesep) are:
       0/200 [>---------------------------]   0%
  20/200 [==>-------------------------]  10%
  40/200 [=====>----------------------]  20%
  60/200 [========>-------------------]  30%
  80/200 [===========>----------------]  40%
 100/200 [==============>-------------]  50%
 120/200 [================>-----------]  60%
 140/200 [===================>--------]  70%
 160/200 [======================>-----]  80%
 180/200 [=========================>--]  90%
 200/200 [============================] 100%

Multibyte Support

The bar characters may be multibyte (e.g. ■). Field widths and padding must be computed by counting characters, not bytes, so that alignment and bar geometry remain correct.

Customization Example (integration)

bar = ProgressBar(output, 10)
bar.set_bar_width(10)
bar.set_bar_character('_')
bar.set_empty_bar_character(' ')
bar.set_progress_character('/')
bar.set_format(' %current%/%max% [%bar%] %percent:3s%%')
bar.start()      # renders "  0/10 [/         ]   0%"
bar.advance()    # renders "  1/10 [_/        ]  10%"

Here, with bar width 10: at current 0 of 10 → zero complete chars, the head /, and 9 empty spaces → [/ ]; at current 1 → one _, the head /, and 8 spaces → [_/ ].

Summary of the Required Behaviors

  • Default formats chosen correctly according to whether a maximum is present.
  • Field-width alignment of current/max and percent is correct.
  • Bar geometry (complete chars, head, empty chars) is correct for both determinate and indeterminate modes.
  • The percentage never shows 100% before completion.
  • Advancing past max raises max and shows 100%.
  • Proper carriage-return / cursor-up overwrite prefixes for decorated output.
  • Shorter lines are padded to erase longer previous lines.
  • clear erases the current line with spaces.
  • finish works even when start has not been called.
  • Quiet verbosity suppresses all output.
  • Non-decorated output emits deduplicated lines joined by os.linesep.
  • Width calculations are multibyte-safe.
