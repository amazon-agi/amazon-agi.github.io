01 Two methods are to be added to the TerraModel class 483 words · source specification, reworded by GLM-5.3-Flash

Task Description

Summary

Two methods are to be added to the TerraModel class: one that lets a user find out whether lookup tables are associated with the model, and one that retrieves those lookup tables. In addition, the string representation of the model is to be updated so that it reports whether or not lookup tables are present.

Module Location

The class TerraModel is defined in the terratools.terra_model module and can be imported as follows:

from terratools.terra_model import TerraModel

Background / Existing Behavior (assumed to be present)

A set of lookup tables may be attached to a TerraModel by means of a pre-existing add_lookup_tables(...) method. That method accepts a MultiTables object (one that comes from the package's lookup-table machinery). Until a call is made to add_lookup_tables, no lookup tables are attached to a newly constructed model.

The work involved is to supply the query methods and to extend the model's repr.

New Methods That Are Required

TerraModel.has_lookup_tables(self) -> bool

The return value is a boolean that tells whether lookup tables are currently attached to the model.

  • Before any lookup tables have been added (in other words, on a newly created TerraModel), the method returns False.
  • After add_lookup_tables(...) has been used to add lookup tables, the method returns True.
TerraModel.get_lookup_tables(self)

Returns the lookup tables object that the model currently has attached.

  • Once add_lookup_tables(some_multitables) has been used to attach lookup tables, this method returns exactly the object that was passed in (it must compare equal to the object supplied to add_lookup_tables).

Required Modification to the String Representation

One extra line must be included at the end of a TerraModel's string representation (repr), and this line states whether the model has lookup tables. Its label is has lookup tables:, right-aligned/padded in the same way as the lines already present, and the value it shows is the boolean returned by has_lookup_tables().

For concreteness, the repr as it currently stands finishes with lines of this form:

  number of lateral points: 3
                    fields: ['t', 'c_hist']
         composition names: ['a', 'b']
        composition values: None

Once this change has been made, one additional line must appear at the end, so that (for a model with no lookup tables) the repr ends as follows:

  number of lateral points: 3
                    fields: ['t', 'c_hist']
         composition names: ['a', 'b']
        composition values: None
         has lookup tables: False

The label on the new line is aligned such that its colon is level with the colons of the labels already present (the text of the label, has lookup tables, is right-justified to the same width as the other labels). This value is the boolean converted to string form (False in the case where no lookup tables are attached).

Restrictions

  • No other existing behavior of TerraModel is to be modified.
  • The only argument these two new methods take is self.

1. Adiabat computation (terratools.terra_model)

1.1 The module-level function _calculate_adiabat(depth)

Add a module-level function named _calculate_adiabat to terratools.terra_model.

  • Input: depth, which is a numeric depth value.
  • Output: a numeric relative adiabat temperature, computed as follows.

The weighting factor is defined as:

w = 1 / (1 + np.exp((-1 * depth - 660) / 60))

Evaluate the two contributions:

lower_mantle = ((-0.00002 * depth**2) + (0.4 * depth) + 1700) * w
upper_mantle = ((depth * 0.5) + 1600) * (1 - w)

Return this expression:

lower_mantle + upper_mantle - 1600

Compute the exponential using numpy.exp. For scalar depth, the returned value must be exactly equal to the expression above rather than merely approximately equal to an algebraically rearranged form.

1.2 The TerraModel.add_adiabat() method

Add the method add_adiabat(self) to TerraModel. It accepts no arguments besides self.

For each model radius, compute:

depth = max(radii) - radius

Evaluate the adiabat at that depth with the formula from section 1.1, and add it in place to the existing "t" temperature field. The contribution of a layer applies to every lateral point in that layer. Calling the method therefore increases the existing temperatures rather than replacing them.

The depth used for this operation is always relative to the maximum radius in get_radii(). In particular, since the radii are stored in increasing order, the first/minimum-radius layer uses:

depth = radii.max() - radii[0]

After the call, the modified values must be exposed through get_field("t"), and get_radii() must continue to expose the model radii.

Specification of the Flow Vector Conversion Task

Summary

Create a new module terratools/flow_conversion.py that provides a function for rotating flow vectors from a global Cartesian coordinate system into a local geographical (radial, south, east) coordinate frame that is defined at a given latitude and longitude on a sphere.

Public Interface

The following function must be exposed by the module:

def rotate_vector(vector, lat, lon):
    ...
Function Parameters
  • vector: Either a single 3-component vector [x, y, z], or else a sequence of such 3-component vectors (e.g. [[x1, y1, z1], [x2, y2, z2], ...]). The components are numeric.
  • lat: Latitude expressed in degrees (numeric).
  • lon: Longitude expressed in degrees (numeric).
Returned Value
  • If a single 3-component vector is provided, the rotated vector must be returned as a length-3 sequence (indexable by [0], [1], [2]), e.g. a NumPy array of shape (3,).
  • If multiple vectors are provided, the rotated vectors must be returned in the same order, such that indexing the result by [i] yields the rotated form of the i-th input vector as a length-3 sequence.

Definition of the Coordinate Transformation

The transformation takes an input Cartesian vector [x, y, z] (in the global frame) and maps it into the local geographical frame at the point specified by (lat, lon). The output components correspond to the [radial, south, east] directions in the global frame at that point.

The following mappings fully specify the required behavior.

The equator case (lat = 0, lon = 0)

For the point on the sphere located at latitude 0, longitude 0:

Global input vector Output vector
[0, 0, 1] (the global +z direction, i.e. north) [1, 0, 0]
[0, 0, -1] (the global −z direction, i.e. south) [-1, 0, 0]
[1, 0, 0] (the global +x direction) [0, 0, 1]
[-1, 0, 0] (the global −x direction) [0, 0, -1]
[0, 1, 0] (the global +y direction) [0, -1, 0]
[0, -1, 0] (the global −y direction) [0, 1, 0]
The north pole case (lat = 90, lon = 0)

For the point on the sphere located at latitude 90, longitude 0:

Global input vector Output vector
[0, 0, 1] (the global +z direction) [0, 0, 1]
[1, 0, 0] (the global +x direction) [-1, 0, 0]
[0, 0, -1] (the global −z direction) [0, 0, -1]

Inputs made up of multiple vectors at the north pole must follow the same per-vector mapping. For example, an input of [[0, 0, -1], [1, 0, 0]] at (lat=90, lon=0) must produce results equivalent to [[0, 0, -1], [-1, 0, 0]], with the input order preserved.

Every output is correct to floating-point precision (a small numerical error is acceptable).

Validation of Inputs

The function must validate its arguments and raise AssertionError when the input is invalid:

  • lat must be numeric; if the value is non-numeric (e.g. a string), AssertionError must be raised.
  • lon must be numeric; if the value is non-numeric (e.g. a string), AssertionError must be raised.
  • The numeric components of the vector argument must be valid; if a vector contains non-numeric elements (e.g. ['vec1', 'vec2', 'vec3']), AssertionError must be raised.

Additional Notes

  • The module must be importable as terratools.flow_conversion, and rotate_vector must be importable from it.
  • No functions or behaviors other than these are required.

Summary

Background

A TerraModel is constructed from lateral coordinate arrays and a radial coordinate array, together with named fields. The constructor call has the form:

TerraModel(lon=<sequence>, lat=<sequence>, r=<sequence>, fields={<name>: <array>})

The number of lateral grid nodes is given by the length of lon (equivalently, by the length of lat), and the number of radii is given by the length of r.

Methods to Add

get_1d_profile(self, lat, lon, field)

For the named scalar field, return the radial profile at the lateral location nearest to the given lat/lon position.

  • Parameters:
    • lat: the latitude, in degrees.
