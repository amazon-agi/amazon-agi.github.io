Overview

You must make changes to the sqlitecollections.base module. Two related changes are involved: (1) reworking how a default in-memory/temporary database connection is established when a collection object is created with no arguments, and (2) adding a sanitize_table_name function with prefix support.

Module to be changed

The module in question is sqlitecollections/base — that is, the base module inside the sqlitecollections package.

Part 1: The sanitize_table_name function

A function with the following signature must be implemented in the base module:

def sanitize_table_name(table_name: str, prefix: str = ...) -> str
Behavior

From an arbitrary input string, the function is to produce a "sanitized" table name by removing all characters that are not valid in a table name identifier. The set of valid characters consists of the following:

  • ASCII letters (a–z, A–Z)
  • ASCII digits (0–9)
  • the underscore character (_)

Every other character — including but not limited to ~ ! @ # $ % ^ & * ( ) + - = { } | [ ] \ ; : ' " < > ? , . / and whitespace — must be stripped out entirely, preserving the order of the remaining valid characters.

Transformation examples:

  • Input "~!@#$%^&*()_+-=qwerty{}|[]\\;:'\"<>?,./01234abc" → output "_qwerty01234abc"
  • Input "abc" → output "abc"
The prefix parameter

An optional second parameter, prefix, is accepted by the function. It is intended to be used only in cases where the sanitized result would otherwise be invalid as a table name. When the input already yields a valid (non-empty) table name after sanitization, the prefix argument must be ignored and must have no effect on the returned value.

  • sanitize_table_name("abc", prefix="list") must return "abc" (the prefix is ignored here because "abc" is already a valid table name).

How prefix behaves exactly when sanitization produces an invalid/empty result is not otherwise constrained by this task; however, the parameter must exist and be accepted without error.

Part 2: Default connection setup when a collection is constructed with no arguments

Within the base module there is a base class, SqliteCollectionBase. If an instance of a concrete subclass is created with no constructor arguments (no connection provided), the object must establish its own database connection using a temporary file.

Behavior that is required

When an object of this kind is constructed with no arguments:

  1. A temporary file must be created through a call to NamedTemporaryFile (which within the base module is referenced as sqlitecollections.base.NamedTemporaryFile). The keyword arguments suffix=".db" and prefix="sc_" must be passed to this call.
  2. The filesystem path of the temporary file is provided by the .name attribute of the object that NamedTemporaryFile returns.
  3. A SQLite connection must be established by invoking sqlite3.connect (which is referenced within the base module as sqlitecollections.base.sqlite3.connect) exactly once, with that temporary file name passed as its single positional argument.
  4. The connection object that results must become the object's connection attribute (accessible via the instance's connection property).

In other words, creating the temporary file and making the sqlite3.connect call must happen directly (via NamedTemporaryFile and sqlite3.connect at module scope) rather than being delegated to any intermediate helper functions.

Removal of the previous helpers

The helper functions create_temporary_db_file and create_tempfile_connection, which previously existed in the base module, must no longer be present there and must no longer be used. The logic of these two helpers is folded directly into the connection-setup path described above.

Other constructor behavior (unchanged; must continue to hold)

When it is constructed with no arguments, the resulting instance must also expose:

  • a serializer attribute equal to the module/class default serializer,
  • a deserializer attribute equal to the module/class default deserializer.

(These are the defaults that already exist; do not alter them.)

Public API surface summary

  • sqlitecollections.base.sanitize_table_name(table_name: str, prefix: str = ...) -> str
  • sqlitecollections.base.NamedTemporaryFile — this must be a module-level reference, and it must be invoked during no-argument construction.
  • sqlitecollections.base.sqlite3.connect — it must be invoked during no-argument construction.
  • SqliteCollectionBase, which has a connection property plus serializer and deserializer attributes.

    1. the raw table name string given to the constructor, and
    2. the instance's container_type_name attribute (which serves as the prefix).
  • The value that sanitize_table_name returns must be:
    • assigned to the instance's table_name attribute,
    • used as the name of the SQLite table that gets created for this instance, and
    • recorded in the collection's metadata (the metadata entry links this sanitized table name to the instance's id and the container type name).

Put differently: if the constructor receives the raw table name "tablename" and sanitize_table_name returns "sanitized_tablename", then:

  • instance.table_name equals "sanitized_tablename",
  • a table called sanitized_tablename exists in the database and is selectable,
  • the metadata holds a row that maps "sanitized_tablename" to the instance id and container type name,
  • and sanitize_table_name was invoked once, as sanitize_table_name("tablename", instance.container_type_name).

  • It is not permitted to change any other observable behavior of the constructor (serializer, deserializer, persist, and other attributes keep their existing semantics).

  • sc.Dict[KeyType, ValueType](connection=..., table_name=...) — an existing collection that behaves like a dict. It is constructed with an SQLite connection and a table name. Calling .keys() on the instance returns the keys-view object.
  • The keys-view object must implement a __ror__ method such that other | keys_view is evaluated as keys_view.__ror__(other) when other is a plain iterable (e.g. the result of iter(...)).
  • sc.Set — the type of the result of the operation described below (an existing collection type that is set-like). The returned object exposes a .table_name attribute that names its backing SQLite table.

Behavior required of __ror__

Assume a keys-view sut over a dict whose keys are, in some order, "a", "c", "b", and an iterable other. The expression:

other | sut

must:

  1. Return a new instance of sc.Set.
  2. The set that is returned must contain the union of:
    • all keys that are currently present in the underlying dict (the keys viewed by sut), and
    • all elements yielded by iterating other.
  3. Duplicate elements (an element that appears both in other and among the keys) must appear only once in the result.
  4. The values that are stored in the resulting set are serialized with the project's default serialization (the same serialization that is used for elements elsewhere in the library). To be concrete, for each distinct element e in the union, the backing table of the returned set contains one row whose serialized value is equal to sc.base.SqliteCollectionBase._default_serializer(e).
Examples showing the union semantics

If sut views the keys "a", "b", "c":

  • The expression iter((1, 2, 3)) | sut yields a sc.Set whose elements are {"a", "b", "c", 1, 2, 3}.
  • The expression iter(("a", "b")) | sut yields a sc.Set whose elements are {"a", "b", "c"} (overlapping elements do not get duplicated).

Constraints

  • Once the resulting set object is discarded (deleted), the operation must not leave behind any auxiliary/persistent tables in the database beyond the original items table. While the result object is alive, creating the result set may allocate its own backing table, but after the result is deleted, only the original dict's table must remain.
  • It is sufficient to iterate other a single time in order to gather its elements; other may be a one-shot iterator.

Element types

The keys may be arbitrary hashable values, and other may likewise yield arbitrary hashable values (integers, strings, etc.); the union combines them with no type restriction beyond hashability/serializability.

Add subtraction support to the keys view that a SQLite-backed dictionary returns.

Public interface

The package is imported as follows:

import sqlitecollections as sc

The relevant APIs are the following:

sc.Dict(connection: sqlite3.Connection, table_name: str)
sc.Dict.keys()

keys_view.__sub__(other: Iterable[Any]) -> sc.Set

An equivalent form that callers must be able to use is:

result = keys_view - other

The object that is returned must expose its existing table_name attribute.

Behavior that is required

Starting from a dictionary whose keys are "a", "b", and "c":

  • Subtracting an iterator that contains no equal keys, such as iter((1, 2, 3)), returns an sc.Set that contains "a", "b", and "c".
  • Subtracting iter(("a", "b")) returns an sc.Set that contains only "c".

Accordingly, the right-hand operand must accept a one-pass iterator, not only a set or other reusable collection.

The result must:

  • Be an sc.Set instance.
  • Be backed by the same SQLite connection that the dictionary uses.
  • Store each of the resulting keys as a set value, using the collection’s normal/default serialization. Its backing table, which is identified by result.table_name, must expose these values through the serialized_value column.
  • Use a temporary backing table of its own. Deleting the returned set must remove that table while leaving the original dictionary table intact. Such a cleanup must not invalidate the dictionary or its keys view, which must remain usable for subsequent subtraction operations.

Change that is required

Add support for reflected subtraction to dictionary key views.

Public API

The relevant APIs of the package are:

  • sqlitecollections.Dict

    • Constructor usage:
      Dict(connection: sqlite3.Connection, table_name: str)
    • Method:
      Dict.keys()
      which returns the dictionary’s keys-view object.

  • The keys-view object must support:

    KeysView.__rsub__(self, other: Iterable[Any]) -> sqlitecollections.Set

  • sqlitecollections.Set

    • The object that is returned must expose the name of its backing SQLite table via:
      result.table_name

  • sqlitecollections.base.SqliteCollectionBase._default_serializer(value) remains the serializer that is used for values stored in the result set.

Behavior

When an expression has the form:

left_iterator - dictionary.keys()

the keys view’s reflected subtraction must return a sqlitecollections.Set containing the elements of the left iterator that are not keys in the dictionary.

Suppose a dictionary is backed by an existing SQLite table that contains the keys "a", "b", and "c":

result = iter((1, 2, 3)) - dictionary.keys()

must:

  • return a sqlitecollections.Set instance;
  • contain 1, 2, and 3;
  • store those values in the result’s backing table as serialized_value values that SqliteCollectionBase._default_serializer produces;
  • create the result’s backing table within the same SQLite connection as the dictionary.

Likewise:

result = iter(("a", "b")) - dictionary.keys()

must return an empty sqlitecollections.Set, since both of the left-side values are dictionary keys. The empty result must still have a queryable backing table that result.table_name identifies.

The creation of either result must not modify the original dictionary table.

Lifecycle of the result

The backing table of the returned set is temporary to that result object. Once the result object is deleted, its backing table must be removed from the shared SQLite connection, with the original dictionary table left intact and no result table left behind.
