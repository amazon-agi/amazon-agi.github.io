Task Specification: int128 and int256 Serialization

Summary

Build serialization (dump) and deserialization (load) functions for fixed-width 128-bit and 256-bit unsigned integer values. Their purpose is to convert between Python integers and the little-endian byte representations of those values.

Public API

Two modules are to be created:

Module: mtpylon.serialization.int128

This module must expose two callables:

  • dump(number: int) -> bytes
  • load(input_bytes: bytes) -> <LoadedValue>
Module: mtpylon.serialization.int256

This module must expose two callables:

  • dump(number: int) -> bytes
  • load(input_bytes: bytes) -> <LoadedValue>

Required Behavior

dump
  • int128.dump: Given an integer, it returns exactly 16 bytes representing that value in little-endian byte order.
  • int256.dump: Given an integer, it returns exactly 32 bytes representing that value in little-endian byte order.

Example (int128): dumping the integer 0x3E0549828CCA27E966B301A48FECE2FC produces this 16-byte sequence:

\xfc\xe2\xec\x8f\xa4\x01\xb3\x66\xe9\x27\xca\x8c\x82\x49\x05\x3e

Example (int256): dumping the integer 0x3E0549828CCA27E966B301A48FECE2FC3E0549828CCA27E966B301A48FECE2FC produces the 32-byte sequence obtained by repeating the above 16-byte block twice:

\xfc\xe2\xec\x8f\xa4\x01\xb3\x66\xe9\x27\xca\x8c\x82\x49\x05\x3e\xfc\xe2\xec\x8f\xa4\x01\xb3\x66\xe9\x27\xca\x8c\x82\x49\x05\x3e
load

The function takes a bytes input and reads a fixed-width value from the beginning of that input, treating the bytes as a little-endian unsigned integer. It returns an object with the following attributes:

  • value: the integer that was decoded.
  • offset: how many bytes were consumed — 16 for int128, 32 for int256.

The load function reads only as many leading bytes as needed; the offset attribute always equals the type's fixed width (16 or 32).

Example (int128): loading the 16-byte sequence shown above gives an object whose value equals 0x3E0549828CCA27E966B301A48FECE2FC and whose offset equals 16.

Example (int256): loading the 32-byte sequence shown above gives an object whose value equals 0x3E0549828CCA27E966B301A48FECE2FC3E0549828CCA27E966B301A48FECE2FC and whose offset equals 32.

For their respective width, dump and load are inverse operations.

Error Cases
  • int128.load: If the input has fewer than 16 bytes, raise ValueError.
  • int256.load: If the input has fewer than 32 bytes, raise ValueError.

Notes

The object that load returns must support attribute access through .value and .offset.

02 This task calls for a module that serializes (dump) and deserializes (load) byte strings per the MTProto encoding scheme for the bytes/string type. 637 words · source specification, reworded by GLM-5.3-Flash

Task: Byte-String Serialization for MTProto

Overview

This task calls for a module that serializes (dump) and deserializes (load) byte strings per the MTProto encoding scheme for the bytes/string type.

Module and Public API

Create a module with the path mtpylon/serialization/bytes.py and expose two functions from it:

def dump(value: bytes) -> bytes: ...
def load(input_bytes: bytes) -> LoadedValue: ...

The object returned by load must carry two attributes:

  • value — the bytes after decoding
  • offset — an int recording the total number of bytes consumed from the input

(Any object type supporting .value and .offset attribute access is acceptable; for instance a named tuple or a small dataclass.)

Encoding Scheme

The byte string's length L is what decides which encoding is used.

Short form (applies when L <= 253)
  • One byte comes first and holds L (the length, as a single byte).
  • The L bytes of payload are written after it.
  • Zero or more padding bytes (\x00) are then appended so that the total length (length prefix byte + payload + padding) is a multiple of 4.

Examples:

  • For a 4-byte payload: 1 length byte + 4 payload bytes = 5 bytes, and padding brings the total to 8 bytes (3 padding bytes).
  • For a 13-byte payload: 1 length byte + 13 payload bytes = 14 bytes, and padding brings the total to 16 bytes (2 padding bytes).
Long form (applies when L >= 254)
  • The sequence opens with the marker byte \xfe (254).
  • Then L is encoded as a 3-byte little-endian integer.
  • After those length bytes come the L payload bytes.
  • The encoding closes with zero or more padding bytes (\x00) so that the total length (1 marker byte + 3 length bytes + payload + padding) is a multiple of 4. Because the 4-byte header is itself always aligned to 4, the padding is decided by aligning the payload length to a multiple of 4.

Examples:

  • With a 256-byte payload, the result is \xfe\x00\x01\x00 (marker + length 256 little-endian), then the 256 payload bytes; the total is 260 bytes, already a multiple of 4 (no padding).
  • With a 257-byte payload, the result is \xfe\x01\x01\x00, then the 257 payload bytes, then 3 padding bytes; the total is 264 bytes.

Behavior of dump

dump takes a bytes value as input and, following the scheme above, returns the encoded bytes (length <= 253 selects the short form; in every other case the long form applies).

Behavior of load

The input is a bytes buffer that starts with an encoded byte string:

  • Start by reading the first byte. If it is less than 254, the buffer is short form: that byte is the payload length L, and immediately after it comes the payload.
  • If the first byte is 254 (\xfe), the buffer is long form: L in little-endian occupies the next 3 bytes, with the payload following.
  • Return an object in which value holds the decoded payload (bytes of length L) and offset holds the total number of bytes consumed — counting the length prefix, the payload, and any padding required to align the consumed total to a multiple of 4.

Examples of consumed offsets:

  • A 4-byte payload in short form: the offset is 8.
  • A 13-byte payload in short form: the offset is 16.
  • A 256-byte payload in long form: the offset is 260.
  • A 257-byte payload in long form: the offset is 264.

Past the encoded byte string there may be further data in the input buffer; what is consumed is only the leading encoded value, and the offset that gets reported accounts for that.

Error Conditions

Whenever the input buffer is empty, load must raise ValueError.

03 Serialization of Strings 623 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Serialization of Strings

Summary

Serialization (dump) and deserialization (load) of str values must be implemented in a new module, mtpylon/serialization/string.py. The byte format used for the encoding is length-prefixed and aligned to 4 bytes.

Pre-existing Dependency

A constant must be exposed by the module mtpylon/serialization/bytes.py:

  • LONG_STRING_CHAR: a single byte b'\xfe', serving as a marker for long strings.

(Should this constant not already exist in that module, it must be created there so that it can be imported.)

Public API

The following must be provided in mtpylon/serialization/string.py:

dump(value: str) -> bytes

Turns a string into its representation in the padded, length-prefixed byte format detailed below.

load(data: bytes) -> LoadedValue

Bytes (in the same format) are deserialized into a result object; this object exposes two attributes:

  • .value — the str that results from decoding.
  • .offset — an int carrying the total count of bytes this string consumes (its length prefix and any padding included).

Whatever name you prefer may be given to the returned object's type, but it must be reachable via attribute access (loaded.value, loaded.offset).

Format Used for Encoding

The UTF-8 byte representation of a string is where encoding begins. Let n denote the string's count of UTF-8 encoded bytes.

Short strings (n <= 253)
  • Prefix: one byte holding the value n.
  • Body: the string's UTF-8 encoded bytes.
  • Padding: zero bytes (b'\x00') placed at the end so that (prefix + body + padding) together total a multiple of 4.

Padding calculation: before any padding is added, the total length comes to 1 + n. The minimum number of \x00 bytes that reaches the next multiple of 4 is appended. When 1 + n is a multiple of 4 already, no padding is added.

These examples demonstrate the padding behavior:

  • With a 15-byte string, the result is prefix \x0f + 15 bytes = 16 bytes total (a multiple of 4 already, so no padding).
  • With a 12-byte string, the result is prefix \x0c + 12 bytes + 3 padding bytes = 16 bytes total.
Long strings (n >= 254)
  • Prefix: n, encoded as a 3-byte little-endian integer, placed after the LONG_STRING_CHAR byte (b'\xfe') (4 prefix bytes in total).
  • Body: the string's UTF-8 encoded bytes.
  • Padding: zero bytes, appended so that (4-byte prefix + body + padding) adds up to a multiple of 4.

Padding calculation: \x00 bytes bring the body length n up to the next multiple of 4. When n is a multiple of 4 already, no padding is added.

Example:

  • For a 505-byte string: prefix \xfe + 3-byte little-endian size + 505 body bytes + 3 padding bytes = 512 bytes total.

Behavior of load

From the start of the input bytes, load parses the format described above:

  • When the first byte is not \xfe (short string): n is given by that byte's value. The UTF-8 body consists of the next n bytes. .offset covers the entire length consumed, prefix and padding included (i.e., 1 + n rounded up to the next multiple of 4).
  • When the first byte is \xfe (long string): the little-endian length n is carried by the following 3 bytes. The UTF-8 body consists of the next n bytes. .offset covers the entire length consumed, the 4-byte prefix and padding included (i.e., 4 + n rounded up to the next multiple of 4).

.value always holds the decoded string once padding has been stripped.

Requirement for Round Trips

There must be mutual consistency between dump and load: applying load to the bytes that dump produced brings back the original string value, and .offset equals the total byte length of the dumped output.

05 Implement serialization (dump) and deserialization (load) of a "vector" type — a homogeneous list of elements — in line with the MTProto-style binary encoding. 487 words · source specification, reworded by GLM-5.3-Flash

Task: Vector Serialization Implementation

Implement serialization (dump) and deserialization (load) of a "vector" type — a homogeneous list of elements — in line with the MTProto-style binary encoding.

Module and Public Interface

Create the module mtpylon.serialization.vector that exposes two functions:

def dump(dump_object, value) -> bytes
def load(load_object, input_bytes)

You may rely on the following existing element serializers (already available for import):

  • mtpylon.serialization.int.load, mtpylon.serialization.int.dump
  • mtpylon.serialization.string.load, mtpylon.serialization.string.dump

Their behavior (for reference on how elements are encoded):

  • For an integer, int.dump(value) returns 4 little-endian bytes.
  • int.load(bytes) reads out a 4-byte little-endian integer.
  • string.dump(value) returns the MTProto string encoding (a length prefix, then the bytes, then padding to a 4-byte boundary).
  • string.load(bytes) reads a string of that form.
  • Every load function returns an object with the attributes .value (the decoded value) and .offset (the number of bytes consumed).

Binary Layout

A serialized vector is made up of the following, in this order:

  1. A 4-byte vector identifier that is fixed: b'\x15\xc4\xb5\x1c'.
  2. A 4-byte unsigned integer in little-endian order giving the number of elements.
  3. Every element serialized with the provided element dumper, concatenated together.

dump(dump_object, value)

  • dump_object is a callable that serializes a single element to bytes (e.g. int.dump or string.dump).
  • value is a list made up of elements.
  • Returns bytes: the vector id comes first, followed by the element count as a 4-byte little-endian integer, followed by each element in value serialized in order via dump_object.

Example: dumping [2, 3, 4] with the int dumper yields:

b'\x15\xc4\xb5\x1c' + b'\x03\x00\x00\x00' + b'\x02\x00\x00\x00' + b'\x03\x00\x00\x00' + b'\x04\x00\x00\x00'

load(load_object, input_bytes)

  • load_object is a callable that decodes a single element out of bytes, returning an object with .value and .offset (the bytes consumed).
  • input_bytes is the buffer of bytes to decode from.
  • Returns an object with:
    • .value: the list containing the decoded elements.
    • .offset: how many bytes were consumed in total for the whole vector (the 4-byte id, plus the 4-byte count, plus the sum of the bytes that all elements consumed).

Steps for decoding:

  1. Read the first 4 bytes and verify that they equal the vector id b'\x15\xc4\xb5\x1c'.
  2. Read the 4 bytes after that as the little-endian element count.
  3. Decode that number of elements sequentially, advancing through the buffer by the length each element consumed.

Example: loading the buffer that int-dumping [2, 3, 4] produced yields .value == [2, 3, 4] and .offset == 20. Loading a string vector ['hello', 'world', 'telegram'], where each string is encoded with a length prefix and 4-byte padding, yields .value == ['hello', 'world', 'telegram'] and .offset == 36.

Error Cases

Raise ValueError in these situations:

  • The first 4 bytes of input_bytes fail to match the vector id.
  • The buffer is too short to hold the 4-byte length field (e.g. when only the vector id is present).

07 Subscript Lookup on Schema 606 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Subscript Lookup on Schema

Goal

Implement subscript (__getitem__) support on the Schema class so that combinator data and function data can be retrieved by key.

Public API

The items below must be importable:

  • from mtpylon import Schema
  • from mtpylon.schema import CombinatorData, FunctionData
The Data Classes

Lookups on a Schema return data objects of two kinds, CombinatorData and FunctionData. Both expose the following read-only attributes:

CombinatorData

  • id — an integer that identifies the combinator.
  • params — the combinator's parameters as a sequence (supports len()).
  • predicate — a string holding the combinator's predicate name.
  • type — a string giving the name of the type the combinator belongs to.

FunctionData

  • id — an integer that identifies the function.
  • params — the function's parameters as a sequence (supports len()).
  • method — a string holding the function's method name.
  • type — a string giving the name of the function's return type.

Required Behavior of Schema.__getitem__(key)

A Schema instance is assembled from types (each having one or more combinators) together with functions. The subscript expression schema[key] must resolve the key and return the combinator or function data associated with it.

The key may take one of the following forms:

  1. A combinator class — a class that stands for a single, specific combinator of a type. Return the matching CombinatorData.

  2. A type "construct" — the abstract type/base object that pulls multiple combinators together (e.g. a boolean type that groups its true/false combinators). Supplying such a construct is not a valid lookup: raise ValueError.

  3. A function — a callable/object that the schema registers as a function. Return the matching FunctionData.

  4. An integer — a numeric identifier. Check it against the id of any registered combinator or function:

    • If the integer matches a combinator's id, return that combinator's CombinatorData.
    • If the integer matches a function's id, return that function's FunctionData.
Error Cases
  • When the key is a type construct (an aggregate type instead of a specific combinator), raise ValueError.
  • When the key is a combinator class, function, or integer that the schema does not contain, raise KeyError.
Details of Returned Values
  • If a combinator is located (via its class or via an integer id), the returned CombinatorData mirrors that combinator: its id, params, predicate, and type.
  • If a function is located (via the function object or via an integer id), the returned FunctionData mirrors that function: its id, params, method, and type.
  • Combinators that have no parameters yield params of length 0.

Expected Resolution Examples

Suppose a schema contains:

  • a Bool type that has boolTrue among its combinators (id 2574415285, no params, type Bool).
  • a Task type carrying a task combinator (id 6457282, 3 params, type Task).
  • a login function (id 475889219, 2 params, return type User).

In that case:

  • schema[BoolTrue] → CombinatorData(id=2574415285, params len 0, predicate='boolTrue', type='Bool')
  • schema[Task] → CombinatorData(id=6457282, params len 3, predicate='task', type='Task')
  • schema[2574415285] → the boolTrue CombinatorData
  • schema[6457282] → the task CombinatorData
  • schema[login] → FunctionData(id=475889219, params len 2, method='login', type='User')
  • schema[475889219] → the login FunctionData
  • schema[Bool] (the aggregate boolean type) → raises ValueError
  • schema[<unknown combinator class>] → raises KeyError
  • schema[<unregistered function>] → raises KeyError
  • schema[12312] (unknown id) → raises KeyError

Note: in the example above, Task acts both as a type construct name and as the single combinator; when a type has exactly one combinator, the lookup resolves to that combinator's CombinatorData rather than raising ValueError. Only aggregate types with multiple combinators (such as Bool) raise ValueError.

09 Schema-Driven Serialization (dump) 875 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Schema-Driven Serialization (dump)

Summary

The task is to implement a function dump that writes values into the MTProto-style binary (TL) wire format; resolution of type/combinator/function metadata happens via a Schema object. Basic types, schema-registered objects (combinators), and schema-registered functions (together with their arguments) must be handled by the serialization.

Public API

mtpylon.serialization.dump
def dump(schema, value, **kwargs) -> bytes
  • schema: a Schema instance; it describes the objects and functions that are known.
  • value: either a schema-registered function (a callable) or an instance of a schema-registered object/type.
  • **kwargs: keyword arguments through which the parameters of a function are passed, in the case where value is a function.
  • The return value is the serialized bytes.

It must be possible to import this function as from mtpylon.serialization import dump.

mtpylon.exceptions.DumpError

An exception class, available as the import from mtpylon.exceptions import DumpError, which is raised whenever any serialization failure described below occurs.

Format of the Serialized Data

Every integer below is little-endian; the only exceptions are cases where the examples imply otherwise.

Number prefix (combinator or function)

The serialization of every object or function opens with a 4-byte combinator (or function) identifier; the schema metadata for that object/function is where this identifier comes from. First in the output is this 4-byte prefix; after it come the serialized values of the object's/function's parameters, in the order in which they were declared.

The int basic type

An int is written out as a 4-byte little-endian value. Example: 12 → b'\x0c\x00\x00\x00'.

The str basic type

A str goes onto the wire as a byte-aligned string with a length prefix:

  • If a string's byte length is small (it fits in a single length byte), one length byte holding the number of content bytes is emitted, then the UTF-8 content bytes, and after those the zero-padding bytes; the padding is sized so that the total length (length byte + content + padding) is a multiple of 4.

Examples:

  • 'root' (4 bytes) → b'\x04root\x00\x00\x00' (8 bytes in total: 1 length byte + 4 content + 3 padding).
  • 'dump by schema' (14 bytes) → b'\x0edump by schema\x00' (16 bytes in total: 1 length byte + 14 content + 1 padding).
The boolean objects

Two boolean singleton object types, BoolTrue and BoolFalse, are part of the schema. Each of them serializes to nothing more than its 4-byte identifier:

  • BoolTrue() → b'\xb5\x75\x72\x99'
  • BoolFalse() → b'\x37\x97\x79\xbc'
Objects from the schema (combinators)

In the case where value is an instance of a schema-registered object, the object's 4-byte combinator number is emitted, and after that each declared parameter value is serialized (in order) in accordance with its declared type. A parameter type may itself be a basic type or another schema type (nested objects such as Bool included).

Functions from the schema

In the case where value is a schema-registered function, the function's 4-byte identifier is emitted. Task Specification: Combinators with Optional-Field Support

Overview

The mtpylon schema/combinator system must be extended so that combinators support optional fields. A dataclass field is called optional when a bit inside a "flags" integer field that precedes it controls whether the field is present in the serialized output.

Defining a Combinator with Meta

Writing a combinator means creating a dataclass that contains a nested Meta class. A new optional attribute may also be declared on Meta, alongside the existing name and order:

class Meta:
    name = 'authorizedUser'
    order = ('id', 'username', 'password', 'avatar_url')
    flags = {
        'avatar_url': 0
    }
  • The flags attribute is a dict that assigns to field names a non-negative integer bit position inside a flags integer.
  • An optional field is any field whose name shows up among the keys of flags; the Python type declared for such a field is Optional[T] (e.g. Optional[str]).
  • Whenever flags is present, a synthetic flags field named flags whose TL type is # is logically added as the combinator's first parameter, placed ahead of all the fields listed in order.

TL Type Strings and Schema Representation

How field types are written
  • Take an optional field whose underlying type is T and whose bit position is n: its TL type is then flags.n?<t>, with <t> standing for the TL type name of T. As an illustration, an Optional[str] sitting at bit 0 carries the type flags.0?string.
  • For the synthetic flags field, the name is flags and the type is #.
JSON schema of a combinator (the params list)

For a combinator that has optional fields, the params array must be laid out in the following order:

  1. The first entry is {"name": "flags", "type": "#"}.
  2. After that come the fields from order, each with its name and type: optional fields are written with the flags.n?<t> notation, and non-optional fields are given their plain TL type name.

The params of the authorizedUser combinator, as an example:

[
  {"name": "flags", "type": "#"},
  {"name": "id", "type": "int"},
  {"name": "username", "type": "string"},
  {"name": "password", "type": "string"},
  {"name": "avatar_url", "type": "flags.0?string"}
]
Single-line TL form of a combinator

A combinator's single-line TL representation must contain the flags field along with the optional-field notation. Applied to the example above:

authorizedUser#5d8fe2e9 flags:# id:int username:string password:string avatar_url:flags.0?string = User;

Behind the #, in hex, sits the combinator id / number (see below).

The Combinator's Number (id)

Computing the combinator id works as before: the TL textual description of the combinator is the input. Because that description now contains the flags:# field plus the flags.n?<t> optional-field notation, the id changes as a result. For the authorizedUser combinator described above, the id that must come out is:

  • Integer / hex: 0x5d8fe2e9 (i.e. 1569662185).

This id must be discoverable via the schema (the membership check is by number), and it must be present in both the JSON schema ("id") and the TL textual form (#5d8fe2e9).

Serialization via dump

When the combinator instance being serialized has optional fields — that is, Meta.flags is present — the following must be produced, in this order:

  1. Combinator id: the combinator number, written as 4 bytes in little-endian order.
  2. Flags integer: 4 bytes in little-endian order. To compute the value, take the bitwise OR of (1 << bit_position) over every optional field whose current value is not None. When all optional fields are None, the resulting flags value is 0.
  3. Fields in order, written out in that same order, subject to this rule:
    • For a non-optional field, the value is serialized the normal way.
    • For an optional field, a value of None means the field is omitted entirely (nothing gets emitted); a value that is not None is serialized the normal way (as its underlying type).
Examples of the serialized bytes

b'\x05zapix\x00\x00'         # username

(As for the int and string serialization formats — 4-byte little-endian ints, and length-prefixed padded strings — these stay as the codebase already implements them.)

Overview

A CallableFunc instance represents a function invocation that has been deserialized and exposes:

  • params (dict): a mapping from parameter names (str) to their deserialized argument values. When the function takes no parameters, this dict is empty.

How Deserialization Works

The schema describes combinators (data constructors) as well as functions, each of which is identified by a 4-byte little-endian combinator/function id at the start of its encoding. load reads the leading id, resolves it against the schema, and decodes the rest of the bytes according to the resolved definition.

Encodings of basic types inside objects
  • int: 4 bytes in little-endian order.
  • str: an encoding that is length-prefixed and aligned to 4 bytes. A single length byte (for short strings) comes before the raw bytes, and zero bytes are appended so that the total encoded length (length byte + content) reaches the next multiple of 4.
  • Bool: encoded as a 4-byte combinator id (BoolTrue or BoolFalse), which is decoded to the corresponding boolean combinator instance.
  • Vector: encoded as a 4-byte vector id (0x1cb5c415), then a 4-byte little-endian element count, then the encoded elements in order.
Combinators (data objects)

If the leading id matches a combinator:

  • Construct the corresponding object type, decoding every field in declaration order according to its type.
  • A field may itself be a basic type, a Bool combinator, another combinator, or a vector of combinators.
  • value is the object that was constructed; offset is the total number of bytes consumed.

Examples of the required behavior:

  • A boolean combinator (BoolTrue/BoolFalse) is decoded from its 4-byte id into the corresponding instance, and 4 bytes are consumed.
  • A combinator that has int, str, and Bool fields decodes each of them in order and consumes the sum of their encoded sizes plus the leading 4-byte combinator id.
  • A combinator that holds a vector of other combinators decodes the vector id, the element count, and each element, consuming all the corresponding bytes.
Optional (flagged) fields

Certain combinators encode a 4-byte little-endian flags field. An optional field is present only when its corresponding flag bit is set:

  • If the flags value indicates that an optional field is present, decode that field and consume its bytes.
  • If the flags value indicates that the optional field is absent, do not decode it; the resulting object then has no value for that field, and no bytes are consumed for it.

The offset reflects the bytes that were actually consumed, and it differs depending on which optional fields are present.

Functions

If the leading id matches a function in the schema:

  • value is an instance of CallableFunc.
  • CallableFunc.func is the callable that belongs to that function id.
  • CallableFunc.params is a dict mapping each parameter name to its decoded argument value; the arguments are decoded in declaration order, after the leading 4-byte function id.
  • A function that takes no parameters yields params == {} and consumes 4 bytes.

Error Behavior

  • If no combinator or function in the schema corresponds to the leading 4-byte id, load raises ValueError.

Notes

  • input may hold more bytes than are needed; load consumes only the bytes belonging to a single top-level object and reports the number of consumed bytes through offset.
  • Decoded boolean combinator instances must be equal to the corresponding BoolTrue()/BoolFalse() instances.
