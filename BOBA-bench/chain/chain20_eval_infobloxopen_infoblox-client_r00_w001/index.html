01 Within the infoblox_client.objects module, IP address objects (represented by the IP class and its concrete subclasses such as IPv4 for IPv4 addresses) have… 438 words · source specification, reworded by GLM-5.3-Flash

Overview

Within the infoblox_client.objects module, IP address objects (represented by the IP class and its concrete subclasses such as IPv4 for IPv4 addresses) have a host field. This host field must be handled as a shadow field: it may be kept on the object in memory (e.g., populated when the object is built from data returned by NIOS), but it must not be part of the payload sent to the backend when a parent object is updated via the API.

Required Behavior

The host field on IP objects
  • The IP object type must still accept and store a host value (settable and gettable on the in-memory instance).
  • The host field must not show up in the dictionary representation of the IP object that gets serialized and sent on update operations to the connector/backend.
How HostRecord updates are affected

When update() is called on a HostRecord object that holds one or more IP addresses (in its ip / ipv4addrs collection), the update payload sent to the connector's update_object method must include the serialized IP entries without the host key — no matter whether a given IP object has a host value set internally.

Each IP entry that gets serialized into the update payload must still include its other writable fields, such as:

  • ipv4addr — the string holding the IP address
  • mac — the string holding the MAC address (when set)
  • configure_for_dhcp — the boolean for DHCP configuration (when set, including False)

Other fields that are set on the HostRecord (e.g., extattrs) must continue to be included in the update payload as before.

Interaction points the tests require
  • objects.IP.create(ip=..., mac=..., configure_for_dhcp=...) — creates a new IP object. This classmethod must accept at least the keyword arguments ip, mac, and configure_for_dhcp, and must produce an object whose serialized form leaves out host.
  • A HostRecord instance must expose an ip attribute (a list) that new IP objects can be appended to, and an extattrs attribute that can be assigned.
  • When host_record.update() is called, it must invoke the connector's update_object with:
    1. the ref of the record,
    2. a payload dictionary that contains ipv4addrs (a list of the serialized IP entries, each excluding host) along with any other set fields such as extattrs,
    3. a third positional argument (the return-fields / additional argument as passed previously).

Constraints

  • Do not make any other change to the set of fields that get serialized for IP objects; the only thing to ensure is that host is excluded from update payloads while still being retained on the in-memory object.

Background

This task deals with a Python client library for Infoblox, infoblox_client. Infoblox network objects are modeled by the library through classes that automatically choose the correct object type variant depending on whether the address that is supplied is IPv4 or IPv6.

Some object classes have two underlying WAPI type names — one for IPv4 and one for IPv6 (for example, network vs ipv6network). When a search or lookup takes place, the library examines the address-bearing fields in the arguments that were provided in order to detect whether the address is IPv4 or IPv6, and then chooses the appropriate WAPI type name accordingly.

Change That Is Required

1. IP version detection must take the network field into account

The set of field names used to detect the required IP version (IPv4 vs IPv6) must contain the field named network, in addition to whatever address-carrying fields are already in use (such as cidr).

The behavior that is required:

  • When a search/lookup is invoked and the address value is provided under the key network, the library must detect the IP version from that value correctly and choose the WAPI type name that matches.
  • Specifically, for the search operation of the Network object:
    • Invoking infoblox_client.objects.Network.search(connector, network_view=<view>, network=<ipv6-cidr>), where <ipv6-cidr> is an IPv6 CIDR string (e.g. 'fffe:2312::/64'), must lead to a single lookup against the connector in which the WAPI type name 'ipv6network' is used.
    • The lookup must pass the search fields dictionary, which contains exactly network_view and network with the provided values (e.g. {'network_view': 'some-view', 'network': 'fffe:2312::/64'}), together with extattrs=None, force_proxy=False, and a set of return fields.

    • Class: Network
      • Classmethod: search(connector, **search_fields) — accepts a connector object plus keyword search fields, including network_view and network (or cidr). Returns the result of the lookup against the connector. It selects the WAPI type name according to the IP version detected for the address supplied in an address-bearing field (network, cidr, etc.).

  • Object manager (the existing class that exposes create_ip_range):

    • Method: create_ip_range(net_view, start_ip, end_ip, network, disable, ext_attrs) — creates an IP range object; its flow must include an invocation of the connector's get-object lookup.

Summary

Add a shared reply-field processing mechanism to infoblox_client.objects.InfobloxObject. For every InfobloxObject subclass, values returned by NIOS that represent structured data must be converted consistently. The initial global rule converts the WAPI extattrs field into an objects.EA value, while existing subclass-specific converters and object lifecycle behavior are preserved.

Behavior Requirements

Global processing of reply fields

objects.InfobloxObject must provide a class-level mapping for global field processing, _global_field_processing. The mapping links WAPI field names to converter callables. Each converter accepts the raw value of one reply field and returns the structured value, such as a sub-object or a list of sub-objects, to assign to the resulting object.

When an object is constructed or populated from a NIOS reply:

  1. Begin with the global processing rules.
  2. Combine these with the concrete class's _custom_field_processing rules.
  3. Apply the effective converter to every mapped field that is present in the reply.
  4. If the same field appears in both mappings, the class-specific converter must take precedence.

Combining the mappings must not cause unrelated rules to be suppressed. For example, a host record must continue to convert its returned address list with its custom rule while also converting returned extensible attributes with the global rule.

12 Extended Attribute (EA) Serialization with Filtering of Empty Values 466 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Extended Attribute (EA) Serialization with Filtering of Empty Values

Overview

You must implement or modify the EA class in the module infoblox_client.objects such that its to_dict() method serializes extended attributes to a dictionary correctly, excluding attributes whose values are considered "empty".

Public API Surface

  • Module: infoblox_client.objects
  • Class: EA
  • Constructor: EA(ea) — ea is a dict that maps attribute names (strings) to their values.
  • Method: to_dict(self) — this returns a dict.

to_dict() Behavior

When an EA has been constructed from a dictionary of attribute name → value pairs, to_dict() must return a dict with the following structure:

  • The value returned is a dict.
  • Each retained attribute is represented as a key in the returned dict, and the name of that key matches the original attribute name. The associated value is itself a dict that contains at least the key 'value'.
  • The 'value' entry must equal str(original_value), i.e. the string form of the original attribute value.
Filtering of Empty Values

An attribute must be excluded from the returned dict if its value is one of the following "empty" values:

  • The empty string ('')
  • None (Python's None object)
  • The empty list ([])

All values other than these must be retained, including values that are falsy but not part of the excluded set above. In particular, the following must be retained:

  • Strings that are not empty (e.g. 'some-id', 'tenant-name')
  • The string 'True' as well as the string 'False'
  • The string 'None' (the literal string of four characters, which is distinct from the None object)
  • The string '0'
  • The boolean False
  • The integer 0
  • Lists that are not empty (e.g. ['record_a', 'record_ptr'])

For each retained attribute, the 'value' entry equals str(original_value). As examples:

  • the integer 0 → '0'
  • the boolean False → 'False'
  • the string 'None' → 'None'
  • the list ['record_a', 'record_ptr'] → str(['record_a', 'record_ptr'])

Summary of the Retain/Exclude Rules

Value Retained?
'' (the empty string) Excluded
None Excluded
[] (the empty list) Excluded
False Retained
0 Retained
'0' Retained
'False' Retained
'None' Retained

non-empty list Retained

Note: the distinction depends on the specific empty values '', None, and [], rather than on truthiness in general — False and 0 are retained.

Existing Additional Behavior (must remain intact)

The EA class exposes a class method named from_dict(value), which returns None when value is None, an empty string, or 0.

Any other existing serialization behavior of EA must be preserved, as must its get() accessor.
