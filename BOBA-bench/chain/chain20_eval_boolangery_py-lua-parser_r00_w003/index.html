Task Specification: Attaching Source Tokens to AST Nodes

Overview

You are working on a parser for Lua source code that resides in the luaparser package. The parser exposes an ast module (luaparser.ast), which parses Lua source into an Abstract Syntax Tree (AST), and an astnodes module (luaparser.astnodes), which defines the AST node classes.

Your task is to ensure that every AST node produced by the parser carries the sequence of source tokens spanning the region of source text that the node represents.

Public API (already provided; must stay importable/callable)

  • luaparser.ast.parse(source: str) → returns the root node of the AST (a Chunk).
  • luaparser.ast.walk(tree) → yields the AST nodes reachable from tree (for iterating over the tree).
  • The AST node classes importable from luaparser.astnodes, including at least: Chunk, Block, LocalAssign, Assign, Number, Name, AddOp, ULengthOP, Table, Call, Invoke, AnonymousFunction.

Required Behavior

Each AST node must expose a tokens attribute, an ordered sequence of token objects. Each token object must expose a .text attribute (a string) holding the exact source text of that token, including whitespace tokens (a space is an individual token with .text == ' ').

The tokens attribute of a node must contain, in source order, every token lying within the span of source text that node covers — including whitespace tokens that fall between the node's other tokens.

Ordering of nodes yielded by walk

The nodes come out of walk(tree) in the following order (this ordering is what the token checks rely on): the Chunk comes first, then its Block, then the statements/expressions in a top-down manner. If a construct contains multiple sibling expressions, those siblings appear after their containing node.

Token-span rules for each node type

A node's tokens sequence covers exactly the source text running from that node's first token to its last token, inclusive of all intervening tokens (whitespace included). Specifically:

  • Chunk and Block: cover the full span of the program body they contain. With a single top-level statement, both carry the same token list, which spans that whole statement.

  • LocalAssign (e.g. local a = 42): the tokens are local, , a, , =, , 42.

  • Assign (e.g. a = 1 + 0.2): the tokens are a, , =, , 1, , +, , 0.2.

  • Number: consists of a single token whose text is the numeric literal (e.g. 42, 0.2, 1).

  • Name: consists of a single token whose text is the identifier (e.g. a).

  • AddOp (e.g. 1 + 0.2): the tokens are 1, , +, , 0.2.

  • ULengthOP (e.g. #t): the tokens are #, t.

  • Table (e.g. {foo = "bar", bar = "foo"}): the tokens span from the opening brace through the closing brace, inclusive: {, foo, , =, , "bar", ,, , bar, , =, , "foo", }. In .text, string literal tokens keep their surrounding quotes.

  • Call (e.g. print("hello")): the tokens are print, (, "hello", ).

  • Invoke (method call using :):

    • foo:print("hello") → the tokens are foo, :, print, (, "hello", ).
    • With a chained invoke foo:bar():print("hello"), the outer Invoke covers the whole chain: foo, :, bar, (, ), :, print, (, "hello", ); the inner Invoke (foo:bar()) covers: foo, :, bar, (, ).

  • AnonymousFunction (e.g. function() local a end): the tokens span from the function keyword through the closing end: function, (, ), , local, , a, , end.

Notes

  • Whitespace between tokens must be represented as distinct token objects (with .text == ' ') and included in the tokens list of the node they fall within.
  • A token's .text is the verbatim slice of source for that token (operators, punctuation, keywords, identifiers, numeric literals, and quoted string literals as written in the source).
  • The existing structural equality of parsed trees (node types and their fields) must continue to hold; adding tokens must not change the way nodes compare structurally.

Task Specification: Preserving Tokens on AST Nodes

Overview

You are working in a Lua parser library that resides in the luaparser package. That library exposes an ast module (luaparser.ast) which parses Lua source code into an Abstract Syntax Tree (AST).

Your assignment is to ensure that AST nodes carry a tokens attribute holding the sequence of lexical tokens (whitespace and punctuation included) that make up that node, exactly as they appear in the original source.

Public API

Parsing

  • luaparser.ast.parse(source: str) — parses a Lua source string and returns the root AST node (a Chunk). The function already exists; it must now populate nodes with token information as described below.

  • luaparser.ast.walk(node) — returns an iterable that yields every node in the tree in a deterministic order (a top-down traversal starting from the root). Node enumeration makes use of this function.

Node classes

The node classes that follow must be importable (they already exist in the codebase and must remain constructible with the shown keyword/positional arguments): Chunk, Block, Forin, Call, Table, If, ElseIf, Return, Number, TrueExpr, Label, Goto.

The tokens attribute

There is an attribute that every AST node must expose:

  • node.tokens — an ordered sequence of token objects. Each token object must expose a .text attribute (a string) holding the exact textual content of that token, whitespace tokens (spaces, newlines) and punctuation included.

A node's tokens sequence must contain all tokens that span the node — from the first token that belongs to the node through the last token that belongs to the node — in source order, whitespace and intervening tokens included. Whitespace between tokens (spaces, indentation runs, and newlines) is represented as its own token entry in each case.

Token Behavior Requirements

What follows specifies the exact token sequences that must be produced for particular constructs. Whitespace matters: a single space is ' ', a two-space indentation run is ' ', and a newline is '\n'. Every contiguous run of identical whitespace between two meaningful tokens is represented as a single token.

The Forin node

For a for-in loop shaped like this (the loop body indented by two spaces):

for k, v in pairs({}) do
  print(k, v)
end

the Forin node's tokens sequence must have .text values in this order:

'for', ' ', 'k', ',', ' ', 'v', ' ', 'in', ' ', 'pairs', '(', '{', '}', ')', ' ', 'do', '\n', ' ', 'print', '(', 'k', ',', ' ', 'v', ')', '\n', 'end'

The Call node

For the function call pairs({}), the tokens values of the Call node are, in order:

'pairs', '(', '{', '}', ')'

For the function call print(k, v), the tokens values of the Call node are, in order:

'print', '(', 'k', ',', ' ', 'v', ')'

The Table node

For an empty table constructor {}, the tokens values of the Table node are, in order:

'{', '}'

If / ElseIf nodes

For an if/elseif/elseif/else statement shaped like this:

if true then
elseif false then
elseif 42 then
else
  return true
end

the If node's tokens sequence must span the entire statement; the values, in order, are:

'if', ' ', 'true', ' ', 'then', '\n', 'elseif', ' ', 'false', ' ', 'then', '\n', 'elseif', ' ', '42', ' ', 'then', '\n', 'else', '\n', ' ', 'return', ' ', 'true', '\n', 'end'

The first ElseIf node (the one for elseif false then) has tokens values, in order:

'elseif', ' ', 'false', ' ', 'then'

The second ElseIf node (the one for elseif 42 then) has tokens values, in order:

'elseif', ' ', '42', ' ', 'then'

(Note: the token span of each ElseIf node covers only its elseif ... then header, not the branches that follow.)

The Label node

For the label statement ::foo::, the tokens values of the Label node are, in order:

'::', 'foo', '::'

The Goto node

For the goto statement goto foo, the tokens values of the Goto node are, in order:

'goto', ' ', 'foo'

Note on Traversal Ordering

When all nodes of a parsed tree are enumerated via walk, the first node yielded is the root Chunk, then comes its Block, then the top-level statement, and then that statement's sub-expressions/sub-statements in a consistent top-down order. The token behavior described above must hold for each such node, no matter where it falls in the walk order.

Constraints

  • The existing structural parsing behavior (the shape of the AST and node equality) must be preserved.

  • Whitespace and punctuation must be captured as individual tokens; a node's token span may not have any whitespace runs dropped from it.

  • The source is parsed after leading/trailing blank-line normalization consistent with the current parser behavior (the inputs above are dedented multi-line strings that begin with a newline).

Task Specification: Attaching Tokens to AST Nodes and Adding Line Editing Support

Overview

The task targets the Lua parser library (luaparser) and involves two of its public modules:

  • luaparser.ast — responsible for parsing Lua source into an AST.
  • luaparser.asttokens — a token-level view and editor for Lua source.

The following two changes must be made:

  1. Change the element type held in each AST node's tokens attribute.
  2. Give the asttokens module line-editing capabilities.

Part 1: The tokens Attribute of AST Nodes

Background

luaparser.ast exposes the following:

  • ast.parse(src) — takes a Lua source string, parses it, and returns an AST tree.
  • ast.walk(tree) — returns an iterable over AST nodes in a deterministic traversal order.

Every AST node carries a tokens attribute: an ordered, index-accessible sequence (supporting node.tokens[i]) holding the source tokens that make up that node, including whitespace, comments, keywords, identifiers, operators, punctuation, string/number literals, and newlines — in source order.

Required Change

At present, each element of node.tokens exposes its raw source text directly through a .text attribute (i.e. node.tokens[i].text). This must change so that each element of node.tokens instead wraps the token in a .value attribute, and the raw source text is read via node.tokens[i].value.text.

Put differently, for any AST node and any valid index i, node.tokens[i].value.text must yield the exact source substring corresponding to that token.

Behavior That Must Hold

For a parsed tree, walking over the nodes and inspecting node.tokens[i].value.text must return the exact literal source fragments, preserving:

  • Comments as individual tokens (e.g. the line comment -- exemple is a single token whose .value.text is '-- exemple').
  • Newlines as individual tokens for which .value.text is '\n'.
  • Whitespace runs as individual tokens carrying the exact whitespace string in .value.text (e.g. ' ', ' ').
  • Keywords, identifiers, operators, punctuation, and literals each as their own token whose text matches exactly (e.g. 'local', 'a', '=', '42', '#', '{', '}', '::', 'goto', 'for', 'in', 'do', 'end', 'if', 'elseif', 'else', 'then', 'return', ':', '(', ')', ',', 'function', '"bar"', '0.2', etc.).

Examples of the required ordering and content (each entry is one token; the .value.text shown):

  • For the source -- exemple\nlocal a = 42, the tokens of the top-level chunk node are: '-- exemple', '\n', 'local', ' ', 'a', ' ', '=', ' ', '42'. Its inner block and the local-assignment node begin at the 'local' token (the leading comment/newline is not included in them): 'local', ' ', 'a', ' ', '=', ' ', '42'. The number literal node has a single token, '42'; the name node has a single token, 'a'.
  • For the addition expression a = 1 + 0.2, the assignment node's tokens are 'a', ' ', '=', ' ', '1', ' ', '+', ' ', '0.2'; the binary add-op node's tokens are '1', ' ', '+', ' ', '0.2'.

The traversal order, the token boundaries, and the inclusion of whitespace/comment/newline tokens all remain as in current behavior — only the access path changes, from .text to .value.text.

Part 2: Line Editing with asttokens

Current Public Surface

luaparser.asttokens exposes the following:

  • asttokens.parse(src) — takes a Lua source string, parses it, and returns a token-container object.
  • The token container exposes allToSource(), which returns the full source string reconstructed from all tokens.
  • A Tokens enumeration whose members include Tokens.SPACE and Tokens.LOCAL, plus a mechanism to build a token sequence and render it via .toSource().
New Requirements
The lines() Method on the Token Container

The token container that asttokens.parse returns must provide a lines() method; that method returns an iterable of line-editor objects, one per source line. Calling list(container.lines()) must be supported, and indexing the resulting list (lines[0], etc.) must yield individual line-editor objects.

Each line-editor object represents the tokens belonging to a single line of the source.

Methods on the Line-Editor Object

Each line-editor object must provide the following:

toSource() — returns the exact source text of that line (its trailing newline is included if present, and any leading/trailing whitespace is included as it currently appears in the tokens).

rstrip() — removes the trailing whitespace tokens on the line that precede the line's terminating newline (i.e. it strips whitespace at the end of the line's content but keeps the newline). It returns a line-editor object (one that supports a subsequent .toSource() call).

  • Example: for the source local foo = "s"; \n followed by an indented next line, the first line's rstrip().toSource() must be 'local foo = "s";\n' (the trailing spaces before the newline get removed, while the newline is retained).

indent(n) — ensures the line begins with exactly n spaces of leading indentation, mutating the line in place. After indent(n) has been called:

  • The new indentation is reflected in the line-editor's toSource().

  • The parent container's allToSource() reflects the change as well (the mutation is applied to the shared token data).

  • Details of the behavior:

    • When the line currently has no leading indentation, indent(2) prepends 2 spaces. Example: local foo = "s"; becomes local foo = "s";.
    • When the line already has exactly the requested indentation, indent(2) leaves it unchanged. Example: local foo = "s"; stays local foo = "s";.

    In both cases, the resulting leading whitespace is exactly n spaces, followed by the rest of the line's content unchanged.

Constraints
  • indent must modify the underlying tokens in a way that leaves both the line-editor's toSource() and the container's allToSource() consistent afterward.
  • rstrip affects only trailing whitespace before the newline; other tokens and the newline are preserved.

Summary of the Public API to Provide

  • luaparser.ast.parse(src) and luaparser.ast.walk(tree) — signatures unchanged; the tokens elements of an AST node now expose .value.text (each element wraps a token in a .value attribute, and the .text of that attribute gives the source fragment).
  • luaparser.asttokens.parse(src) — returns a container that has allToSource() together with the new lines() method.
  • Line-editor objects (yielded by lines()), providing the methods toSource(), rstrip(), and indent(n) as described above.
  • The luaparser.asttokens.Tokens enum with its existing members (SPACE, LOCAL, etc.) — unchanged.

Overview

The project you are working on is luaparser, a parser for Lua source code that builds an Abstract Syntax Tree (AST). Each AST node exposes a tokens attribute: a sequence of token objects, each of which carries a .value.text string holding the exact source text of that token (including keywords, identifiers, literals, punctuation, whitespace, and comments).

Your task is to alter the way the token range of each AST node is computed so that every node includes all hidden tokens (whitespace and comments) that immediately precede its first non-hidden token, in addition to the tokens it already spans.

Public API (already exists — do not rename)

  • the luaparser.ast module, which provides:
    • ast.parse(source: str) — parses a Lua source string and returns the AST tree.
    • ast.walk(tree) — returns an iterable which yields every node in the tree.
  • AST nodes expose the following:
    • node.tokens — a sequence of token objects that supports indexing.
    • token.value.text — a token's raw source text.
  • Node classes referenced (they already exist): Block, LocalAssign, Number, Name, AddOp, ULengthOP, Table, AnonymousFunction, Forin, Call, If, ElseIf, Label, Goto.

Required Change of Behavior

At present, the tokens sequence of a node starts at its first meaningful (non-hidden) token. It must instead start earlier, with the range extended backward to include the run of hidden tokens (whitespace such as spaces ' ', newlines '\n', indentation like ' ', and comments such as '-- exemple') that sit immediately before that first meaningful token.

Stated another way: for each node, take the contiguous block of leading hidden tokens that precede its first significant token and prepend it to its tokens sequence. The trailing end of a node's token range stays unchanged. Token order must be preserved (leading hidden tokens come first, in source order, followed by the previously-included tokens).

Concrete outcomes

For a node whose meaningful content previously started with, for example, a keyword or literal, that node's tokens[0] (and possibly tokens[1], etc.) now become the preceding hidden token(s). The following are examples of the resulting leading tokens:

  • When a single space precedes a node, that node now has tokens[0].value.text == ' ', and its former first token is shifted to tokens[1].
  • When a newline precedes a node, that node now has tokens[0].value.text == '\n'.
  • When a comment line and newline precede a node (e.g. source -- exemple\nlocal a = 42), the assignment node begins with tokens[0] == '-- exemple', tokens[1] == '\n', then 'local', ' ', 'a', ...
  • When newline + indentation precede a node (e.g. a call inside a do ... end body), that node begins with tokens[0] == '\n', tokens[1] == ' ', then the call's own tokens.
Behavior that must NOT be altered
  • A node whose first meaningful token is not preceded by any hidden token retains its existing token range unchanged. As an example, a Table node written directly as {} immediately after an opening ( begins at tokens[0] == '{', with no whitespace prepended.
  • The complete sequence of a node's own tokens (keywords, operators, identifiers, literals, interior whitespace, and body tokens) stays as before; the only additions are leading hidden tokens at the front.
  • Parsing itself (which constructs are recognized, which node types are produced, the tree structure, and the traversal order of ast.walk) is unchanged.

Summary

The token span of each AST node is to be extended so that it also covers the immediately-preceding hidden (whitespace/comment) tokens; as a result, node.tokens starts at the first hidden token of the leading whitespace/comment run that precedes the node's first significant token. Everything else concerning node tokens and parsing is unchanged.

    • .last() — this returns the stream's last token.
  • Each token object has:

    • .next(ignore=<default>) — the next token is returned; skipping tokens of certain types is optional (see below).
    • .prev(ignore=<default>) — the previous token is returned; skipping tokens of certain types is optional (see below).
  • luaparser.asttokens.Tokens — token type identifiers gathered in an enumeration/namespace. At least the following must be defined in it:
    • Tokens.SPACE — the token type corresponding to whitespace/spaces.
    • Tokens.NAME — the token type corresponding to identifiers/names.

How Tokenization Behaves

For the source local a = 1, tokenization must produce a stream built from the tokens below, arranged in this order and each carrying the .text shown:

'local'  ' '  'a'  ' '  '='  ' '  '1'  '<EOF>'

Concretely:

  • The local keyword.
  • A single space, ' '.
  • The name, a.
  • Once again a single space, ' '.
  • The operator, =.
  • One more single space, ' '.
  • The number, 1.
  • The final token marks end of file; its .text is '<EOF>'.

The stream's first token, obtained through .first(), is 'local'; its last token, obtained through .last(), is '<EOF>'.

Semantics of next / prev Navigation

next and prev both accept one optional parameter, ignore. The value of this parameter is a list of token types (values from Tokens).

Passing an empty ignore list (ignore=[])

An empty list, when passed, means no tokens are skipped: navigation moves exactly one token along, in the direction that was given.

  • From a starting token of 'local', calling .next([]) again and again produces, in order: ' ', 'a', ' ', '=', ' ', '1'.
  • Beginning instead at '<EOF>', repeated calls to .prev([]) produce, in order: '1', ' ', '=', ' ', 'a', ' ', 'local'.
Behavior when no argument is given (the default)

A call to next or prev made with no argument triggers the default: whitespace/space tokens (Tokens.SPACE) are skipped. The navigation travels in the direction given, stepping past every token whose type belongs to the ignore set; the token it returns is the first one that is not ignored.

  • With 'local' as the starting point, successive calls to .next() give, in order: 'a', '=', '1' (each of the space tokens is skipped).
  • With '<EOF>' as the starting point, successive calls to .prev() give, in order: '1', '=', 'a', 'local', and after that None (no non-ignored token exists before 'local', which is why prev returns None).
Supplying a custom ignore list

Handing the navigation a non-empty list makes it skip every token whose type is found in that list; the token returned is the first one whose type the list does not contain.

  • Taking 'local' as the start, a call to .next([Tokens.SPACE, Tokens.NAME]) yields '=' (the space that follows and the name a both get skipped).

Boundary Cases

  • If the navigation moves beyond the token stream's end in one direction (i.e., there is no further non-ignored token), the method returns None.
  • The default value of the ignore parameter must be equivalent to ignoring space tokens; as a result, a call made with no argument gives the "skip spaces" behavior described above, whereas passing [] explicitly turns off all skipping.

Restrictions

  • Do not change the observable behavior of any of .text, .first(), or .last() — the observable behavior of all three must stay as it is.
  • The ignore argument, meanwhile, is a list made up of token type values drawn from Tokens.

Context

Behavior Requirements

For all AST nodes that contain a body of statements, the body attribute (and any analogous statement-list attribute such as orelse when it holds a list of statements) MUST be a Block node that wraps the list of statements, rather than a bare Python list.

Concretely, when the parser constructs these nodes, the value passed as the body must be a Block instance built from the list of contained statements. An empty body must be represented as Block([]) (that is, a Block wrapping an empty list), not as [].

Constructing Block

It must be possible to construct the Block node both positionally and by keyword:

  • Block(body=[...]) — the same thing via the body keyword.

  • Function — the body is a Block.
  • LocalFunction — the body is a Block.

The parser exposes a means of walking all AST nodes in order. Background

The luaparser.ast module parses Lua source into an abstract syntax tree (AST) and exposes ast.walk for iterating over that tree. AST nodes are Python objects, and their children may be stored directly in fields or inside node lists. Parsed nodes also expose source-token information through tokens (whose elements provide .value.text), as well as source ranges.

The order that ast.walk returns must be corrected. It must mirror the semantic and source-code order of child nodes instead of Python attribute declaration, assignment, insertion, or dictionary iteration order.

Public Interface

The APIs listed below must remain importable and callable:

  • luaparser.ast.parse(source: str) parses Lua source and returns the root AST node. This task does not change its parsing behavior.
  • luaparser.ast.walk(tree) returns an iterable over the AST nodes. Callers must be able to consume it incrementally or to materialize it with list(ast.walk(tree)).

Contract for Traversal

Pre-order, depth-first ordering

ast.walk must carry out a deterministic pre-order depth-first traversal:

  1. Yield the given root node first.
  2. Visit the direct children of a node in their semantic source order.
  3. Yield each child node before that child's own descendants.
  4. Finish a child's entire subtree before moving on to the next sibling child.

Every AST node that is reachable from the root must still be yielded, and no AST node may be omitted simply because it is stored in a list. List containers and scalar metadata are not AST nodes themselves and are not yielded. Ordinary node lists keep their source/list order.

The source-order rule governs the relationship between siblings; it does not turn the result into a global sort. A parent is always yielded before its children, including cases where a parent and child begin at the same source position.

What child order means

“Field order” refers to the order in which the represented child constructs occur in the Lua program or, for synthetic children, their semantic structural position. It does not refer to the order in which a Python node class happens to declare or assign its fields. The result must not depend on __dict__ order or on comparable object-layout details.

As a consequence, common structures are traversed in the following way:

  • For assignments, all target subtrees are visited from left to right, followed by all value subtrees from left to right.
  • For binary operations, the left operand subtree is visited before the right operand subtree.
  • For unary operations, the operand is visited after the unary-operation node.
  • For calls and invocations, the callee/source and method/function portions are visited before the arguments, all in source order. A chained call or invocation visits the enclosing node first and then fully visits its earlier source expression before later method names and arguments.
  • For indexed expressions, the source value is visited before the index expression when that is their source order, regardless of the order in which the attributes are stored.
  • Conditions, bodies, alternate clauses, function parameters, function bodies, loop variables, iterator expressions, and loop bodies follow the structural order in which those constructs occur in the Lua statement.
Generic for ... in loop ordering

For a generic for-in loop, the direct-child order must be:

  1. the loop's target names, from left to right;
  2. the iterator expression subtrees, from left to right;
  3. the subtree of the loop body block.

This ordering is required even when a Forin object's fields are stored or declared in a different order. For instance, walking:

for k, v in pairs({}) do
  print(k, v)
end

must start with the following node-type sequence (including identifying names where useful):

Chunk, Block, Forin, Name(k), Name(v),
Call, Name(pairs), Table,
Block, Call, Name(print), Name(k), Name(v)

So the iterator Call is reached before its empty Table argument, and that iterator subtree in its entirety is reached before the body Block.

Table constructor nodes

A Table represents entries by way of parallel keys and values collections, but traversal must preserve the structure of table entries rather than walking all keys and then all values. The entries are visited in source order. For each entry, the key subtree is visited and then that same entry's value subtree, before moving on to the next entry. When a key has descendants, its entire subtree is completed before the value subtree.

The rule also covers array-style entries whose numeric keys are synthesized in the AST and therefore have no literal key syntax in the source. A synthetic key of this kind remains part of the yielded node set and is visited immediately before its corresponding value subtree.

As an example, once the assignment target and the Table node have been visited, the children of:

must be visited in the following order:

Name(foo), String(bar), Name(bar), String(foo)

For a mixed, nested constructor such as:

  options = { radio = true },
  "enabled",
  157,
  [true] = false,
  ['true'] = true,
}

the complete pre-order sequence begins as follows:

Chunk, Block, Assign, Name(foo), Table,
Name(options), Table, Name(radio), TrueExpr,
Number(1), String(enabled),
Number(2), Number(157),
TrueExpr, FalseExpr,
String(true), TrueExpr

In this example, the Number(1) and Number(2) nodes are the synthetic array keys. The bracketed [true] key is consequently the node at zero-based position 13 in the complete walk, and it is immediately followed by its false value. Its existing token coverage, which includes the whitespace and the brackets, must remain unchanged.

All of the following results must be produced by the general rules above:

  1. Simple assignment — for local a = 42, the sequence of interest is LocalAssign, Name(a), Number(42). The target comes before the assigned value.

  2. Binary expression assignment — for a = 1 + 0.2, the sequence is:

  3. Unary length expression — for len = #t, Name(len) comes before ULengthOP, which in turn comes before its Name(t) operand.

  4. Table assignment — for a = {...}, Name(a) comes before the Table node. The table's entries are then subject to the key/value interleaving rule above.

  5. Bracketed table keys — a key expression such as [true] sits at the source position of its own table entry and is visited before that entry's value; it is not grouped together with all other table keys.

  6. Nested method invocation — for foo:bar():print("hello"), the sequence is:

elseif false then

    Chunk, Block, If, TrueExpr, Block,
ElseIf, FalseExpr, Block,

    So each elseif clause, together with its own contents, forms a contiguous group before the next clause begins.

  • SemiColon() — a statement made up of nothing but a semicolon.
  • Do(body) — stands for a do ... end block; the body is a Block.
  • Name(id) — an identifier; the argument may be passed as id (first positional).
  • Index(idx, value) — an indexing expression; idx and value are passed by keyword.
  • Number(n) — a numeric literal; the argument may be passed as n (first positional). Integer and float literals must both be supported.
  • String(s) — a string literal; the argument may be passed as s (first positional). Strings written with double quotes, with single quotes, or in long-bracket form ([[ ... ]]) must be supported, including long-bracket contents that themselves contain bracket sequences.
  • TrueExpr() — represents the true literal.
  • FalseExpr() — represents the false literal.

Definitions of functions and methods:

  • Function(name, args, body) — the definition of a global function. name may be a Name or an Index chain; args holds a list of Name; body holds a Block.
  • LocalFunction(name, args, body) — the definition of a local function.
  • Method(source, name, args, body) — the definition of a method (function Obj:name(...)); source is the object, name is the method's name, args is a list, and body is a Block.

Calls:

  • Call(func, args) — a call to a function; func is the callable expression, while args is a list of argument expressions. Three forms of call syntax must be supported: with parentheses; with a single string argument and no parentheses (f "str"); and with a single table argument and no parentheses.

Tables:

  • Table(fields) — a table constructor; fields holds a list of Field.
  • Field(key, value, comments=None, between_brackets=False) — one field of a table.
    • key holds a Name (for the name = value form) or an expression serving as an explicit key.
    • value carries the expression that is the field's value.
    • comments is an optional list of Comment nodes belonging to the field.
    • between_brackets is a boolean telling whether the key was written in [ ... ] bracket form.
    • Fields written array-style (bare values) are assigned implicit integer keys Number(1), Number(2), ... in order.

Operators (each takes the operand expressions left and right, positionally):

  • Arithmetic: AddOp, together with the corresponding operator nodes for subtraction, multiplication, division, floor division, modulo, and exponentiation.
  • Bitwise: BAndOp (bitwise and), along with the corresponding nodes for bitwise or, bitwise xor, left shift, and right shift.
  • Relational: the nodes covering less-than, greater-than, less-or-equal, greater-or-equal, equality, and inequality.
  • Logical: AndLoOp and OrLoOp (the binary logical and / or).
  • Concatenation: the node Concat(left, right).

Unary operator:

  • The length operator #: a unary operator node having a single operand.

Comments:

  • Comment(s) — a node representing a comment, which stores the raw comment text (the leading -- included). Comments that appear before a statement must be attached to that statement (statements carry a comments list), and comments located inside a table constructor must be attached to the corresponding Field.
Requirements on Parsing Behavior
  • Parentheses that enclose an expression (e.g. res = (1 < 2)) must be preserved/represented in the tree that results.
  • Assignments with multiple targets and values are supported.
  • Indexing chained via . (e.g. t.a.b.c) results in Index nodes nested inside one another, whose idx values are String nodes.
  • The order of statements and blocks is preserved.

The luaparser.utils.tests Module

Provide a base class that helps with testing:

Class: TestCase(unittest.TestCase)
  • The method assert_ast_equal(self, ast, other):
    • If ast and other are both instances of Node: assert that the childs collections of the two have equal length, assert that ast is an instance of the class of other, and then compare, recursively, each pair of corresponding children with assert_ast_equal.
    • Otherwise: ast == other must be asserted.

Compatibility Remarks

  • The function that does the pretty-printing goes by the name to_pretty_str (the name is not any camelCase variant).
  • The helper method that checks equality goes by the name assert_ast_equal (the name is not any camelCase variant).

Further Requirements

  • An optional third comments argument must be accepted by Assign and LocalAssign: Assign(targets, values, comments=None) and LocalAssign(targets, values, comments=None). It must work both when passed positionally and when passed as a keyword.
  • Method must accept an optional comments argument that comes after body: Method(source, name, args, body, comments=None). It must work both when passed positionally and when passed as a keyword.
  • The comments supplied to these nodes must be exposed by them as an ordered collection; in structural equality, comments must take part in the same way as their other fields. When comments are parsed and attached to these statements, they must appear in source order.
