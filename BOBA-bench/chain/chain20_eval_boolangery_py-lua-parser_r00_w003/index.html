Task Specification: Attach Source Tokens to AST Nodes

Overview

You are working on a Lua source-code parser located in the luaparser package. The parser exposes an ast module (luaparser.ast) that parses Lua source into an Abstract Syntax Tree (AST), and an astnodes module (luaparser.astnodes) that defines the AST node classes.

Your task is to ensure that every AST node produced by the parser carries the sequence of source tokens that span the region of source text the node represents.

Public API (already available; must remain importable/callable)

  • luaparser.ast.parse(source: str) → returns the root AST node (a Chunk).
  • luaparser.ast.walk(tree) → yields the AST nodes reachable from tree (used to iterate over the tree).
  • AST node classes importable from luaparser.astnodes, including at least: Chunk, Block, LocalAssign, Assign, Number, Name, AddOp, ULengthOP, Table, Call, Invoke, AnonymousFunction.

Required Behavior

Each AST node must expose a tokens attribute: an ordered sequence of token objects. Each token object must expose a .text attribute (a string) giving the exact source text of that token, including whitespace tokens (spaces are individual tokens with .text == ' ').

The tokens attribute of a node must contain, in source order, every token that lies within the span of source text covered by that node — including whitespace tokens that fall between the node's other tokens.

Ordering of nodes from walk

walk(tree) yields nodes in the following order (this is the ordering the token checks rely on): the Chunk first, then its Block, then the statements/expressions in a top-down manner. Where multiple sibling expressions exist within a construct, they appear after their containing node.

Token-span rules per node type

The tokens sequence for a node covers exactly the source text from the first token of the node to the last token of the node, inclusive of all intervening tokens (including whitespace). Concretely:

  • Chunk and Block: cover the entire span of the program body they contain. For a single top-level statement, both carry the same token list, spanning that whole statement.

  • LocalAssign (e.g. local a = 42): tokens are local, , a, , =, , 42.

  • Assign (e.g. a = 1 + 0.2): tokens are a, , =, , 1, , +, , 0.2.

  • Number: a single token whose text is the numeric literal (e.g. 42, 0.2, 1).

  • Name: a single token whose text is the identifier (e.g. a).

  • AddOp (e.g. 1 + 0.2): tokens are 1, , +, , 0.2.

  • ULengthOP (e.g. #t): tokens are #, t.

  • Table (e.g. {foo = "bar", bar = "foo"}): tokens span from the opening brace through the closing brace inclusive: {, foo, , =, , "bar", ,, , bar, , =, , "foo", }. String literal tokens keep their surrounding quotes in .text.

  • Call (e.g. print("hello")): tokens are print, (, "hello", ).

  • Invoke (method call via :):

    • foo:print("hello") → tokens: foo, :, print, (, "hello", ).
    • For a chained invoke foo:bar():print("hello"), the outer Invoke covers the whole chain: foo, :, bar, (, ), :, print, (, "hello", ); the inner Invoke (foo:bar()) covers: foo, :, bar, (, ).

  • AnonymousFunction (e.g. function() local a end): tokens span from the function keyword through the closing end: function, (, ), , local, , a, , end.

Notes

  • Whitespace between tokens must be represented as distinct token objects (with .text == ' ') and included in the covered node's tokens list.
  • The .text of a token is the verbatim source slice for that token (operators, punctuation, keywords, identifiers, numeric literals, and quoted string literals as written in the source).
  • Existing structural equality of parsed trees (node types and their fields) must continue to hold; adding tokens must not change how nodes compare structurally.

Task Specification: Token Preservation on AST Nodes

Overview

You are working on a Lua parser library located in the luaparser package. The library exposes an ast module (luaparser.ast) that parses Lua source code into an Abstract Syntax Tree (AST).

Your task is to ensure that AST nodes carry a tokens attribute containing the sequence of lexical tokens (including whitespace and punctuation) that make up that node, exactly as they appear in the original source.

Public API

Parsing

  • luaparser.ast.parse(source: str) — parses a Lua source string and returns the root AST node (a Chunk). This function already exists; it must now populate token information on nodes as described below.

  • luaparser.ast.walk(node) — returns an iterable that yields every node in the tree, in a deterministic order (a top-down traversal starting from the root). This function is used to enumerate nodes.

Node types

The following node classes must be importable (they already exist in the codebase and must continue to be constructible with the shown keyword/positional arguments): Chunk, Block, Forin, Call, Table, If, ElseIf, Return, Number, TrueExpr, Label, Goto.

Token attribute

Every AST node must expose an attribute:

  • node.tokens — an ordered sequence of token objects. Each token object must expose a .text attribute (a string) that holds the exact textual content of that token, including whitespace tokens (spaces, newlines) and punctuation.

The tokens sequence of a node must contain all tokens that span the node — from the first token belonging to the node through the last token belonging to the node — in source order, including whitespace and intervening tokens. Whitespace between tokens (spaces, indentation runs, and newlines) each appear as their own token entry.

Required Token Behavior

The following describes the exact token sequences that must be produced for specific constructs. Whitespace is significant: a single space is ' ', a two-space indentation run is ' ', and a newline is '\n'. Each contiguous run of identical whitespace between two meaningful tokens is represented as a single token.

Forin node

For a for-in loop of the form (the loop body indented by two spaces):

for k, v in pairs({}) do
  print(k, v)
end

The Forin node's tokens sequence, in order, must have .text values:

'for', ' ', 'k', ',', ' ', 'v', ' ', 'in', ' ', 'pairs', '(', '{', '}', ')', ' ', 'do', '\n', ' ', 'print', '(', 'k', ',', ' ', 'v', ')', '\n', 'end'

Call node

For the function call pairs({}), the Call node's tokens values in order are:

'pairs', '(', '{', '}', ')'

For the function call print(k, v), the Call node's tokens values in order are:

'print', '(', 'k', ',', ' ', 'v', ')'

Table node

For an empty table constructor {}, the Table node's tokens values in order are:

'{', '}'

If / ElseIf nodes

For an if/elseif/elseif/else statement of the form:

if true then
elseif false then
elseif 42 then
else
  return true
end

The If node's tokens sequence must span the entire statement, values in order:

'if', ' ', 'true', ' ', 'then', '\n', 'elseif', ' ', 'false', ' ', 'then', '\n', 'elseif', ' ', '42', ' ', 'then', '\n', 'else', '\n', ' ', 'return', ' ', 'true', '\n', 'end'

The first ElseIf node (for elseif false then) has tokens values in order:

'elseif', ' ', 'false', ' ', 'then'

The second ElseIf node (for elseif 42 then) has tokens values in order:

'elseif', ' ', '42', ' ', 'then'

(Note: each ElseIf node's token span covers its elseif ... then header only, not the following branches.)

Label node

For the label statement ::foo::, the Label node's tokens values in order are:

'::', 'foo', '::'

Goto node

For the goto statement goto foo, the Goto node's tokens values in order are:

'goto', ' ', 'foo'

Traversal ordering note

When enumerating all nodes of a parsed tree via walk, the first node yielded is the root Chunk, followed by its Block, then the top-level statement, and then that statement's sub-expressions/sub-statements in a consistent top-down order. The token behavior above must hold for each such node regardless of its position in the walk order.

Constraints

  • Existing structural parsing behavior (the shape of the AST and node equality) must be preserved.
  • Whitespace and punctuation must be captured as individual tokens; no whitespace runs may be dropped from a node's token span.
  • Source is parsed after leading/trailing blank-line normalization consistent with the current parser behavior (the inputs above are dedented multi-line strings beginning with a newline).

Task Specification: Attach Tokens to AST Nodes and Add Line Editing Support

Overview

This task concerns a Lua parser library (luaparser) with two relevant public modules:

  • luaparser.ast — parses Lua source into an AST.
  • luaparser.asttokens — a token-level view/editor of Lua source.

Two changes are required:

  1. Change the element type stored in each AST node's tokens attribute.
  2. Add line-editing capabilities to the asttokens module.

Part 1: AST Node tokens Attribute

Context

luaparser.ast exposes:

  • ast.parse(src) — parses a Lua source string and returns an AST tree.
  • ast.walk(tree) — returns an iterable of AST nodes in a deterministic traversal order.

Every AST node has a tokens attribute: an ordered, index-accessible sequence (supporting node.tokens[i]) of the source tokens that make up that node, including whitespace, comments, keywords, identifiers, operators, punctuation, string/number literals, and newlines — in source order.

Required Change

Currently each element of node.tokens exposes its raw source text directly via a .text attribute (i.e. node.tokens[i].text). This must change so that each element of node.tokens instead wraps the token in a .value attribute, and the raw source text is read via node.tokens[i].value.text.

In other words, for any AST node and any valid index i, node.tokens[i].value.text must yield the exact source substring corresponding to that token.

Behavior That Must Hold

For a parsed tree, walking the nodes and inspecting node.tokens[i].value.text must return the exact literal source fragments, preserving:

  • Comments as individual tokens (e.g. a line comment -- exemple is a single token whose .value.text is '-- exemple').
  • Newlines as individual tokens whose .value.text is '\n'.
  • Whitespace runs as individual tokens whose .value.text is the exact whitespace string (e.g. ' ', ' ').
  • Keywords, identifiers, operators, punctuation, and literals each as their own token with the exact matching text (e.g. 'local', 'a', '=', '42', '#', '{', '}', '::', 'goto', 'for', 'in', 'do', 'end', 'if', 'elseif', 'else', 'then', 'return', ':', '(', ')', ',', 'function', '"bar"', '0.2', etc.).

Examples of the ordering and content required (each entry is one token; the .value.text shown):

  • For source -- exemple\nlocal a = 42, the top-level chunk node's tokens are: '-- exemple', '\n', 'local', ' ', 'a', ' ', '=', ' ', '42'. Its inner block and the local-assignment node begin at the 'local' token (they do not include the leading comment/newline): 'local', ' ', 'a', ' ', '=', ' ', '42'. The number literal node has one token '42'; the name node has one token 'a'.
  • For an addition expression a = 1 + 0.2, the assignment node tokens are 'a', ' ', '=', ' ', '1', ' ', '+', ' ', '0.2'; the binary add-op node tokens are '1', ' ', '+', ' ', '0.2'.

The traversal order, token boundaries, and inclusion of whitespace/comment/newline tokens are unchanged from current behavior — only the access path changes from .text to .value.text.

Part 2: asttokens Line Editing

Existing Public Surface

luaparser.asttokens exposes:

  • asttokens.parse(src) — parses a Lua source string and returns a token-container object.
  • The token container exposes allToSource() — returns the full source string reconstructed from all tokens.
  • A Tokens enumeration with members including Tokens.SPACE and Tokens.LOCAL, and a mechanism to build a token sequence and render it via .toSource().
New Requirements
lines() method on the token container

The token container returned by asttokens.parse must provide a method lines() that returns an iterable of line-editor objects, one per source line. list(container.lines()) must be supported, and indexing the resulting list (lines[0], etc.) must yield individual line-editor objects.

Each line-editor object represents the tokens belonging to one line of the source.

Line-editor object methods

Each line-editor object must provide:

toSource() — returns the exact source text for that line (including its trailing newline if present, and including any leading/trailing whitespace as currently in the tokens).

rstrip() — removes trailing whitespace tokens on the line that precede the line's terminating newline (i.e. strips whitespace at the end of the line's content but keeps the newline). Returns a line-editor object (supporting a subsequent .toSource() call).

  • Example: for source local foo = "s"; \n followed by an indented next line, the first line's rstrip().toSource() must be 'local foo = "s";\n' (the trailing spaces before the newline are removed, the newline is retained).

indent(n) — ensures the line begins with exactly n spaces of leading indentation, mutating the line in place. After calling indent(n):

  • The line-editor's toSource() reflects the new indentation.

  • The parent container's allToSource() also reflects the change (the mutation is applied to the shared token data).

  • Behavior details:

    • If the line currently has no leading indentation, indent(2) prepends 2 spaces. Example: local foo = "s"; becomes local foo = "s";.
    • If the line already has exactly the requested indentation, indent(2) leaves it unchanged. Example: local foo = "s"; stays local foo = "s";.

    In both cases the resulting leading whitespace is exactly n spaces followed by the rest of the line's content unchanged.

Constraints
  • indent must modify the underlying tokens such that both the line-editor's toSource() and the container's allToSource() are consistent afterward.
  • Only trailing whitespace before the newline is affected by rstrip; other tokens and the newline are preserved.

Summary of Public API to Provide

  • luaparser.ast.parse(src) and luaparser.ast.walk(tree) — unchanged signatures; AST node tokens elements now expose .value.text (each element wraps a token in a .value attribute, whose .text gives the source fragment).
  • luaparser.asttokens.parse(src) — returns a container with allToSource() and a new lines() method.
  • Line-editor objects (yielded by lines()) with methods: toSource(), rstrip(), and indent(n) as described above.
  • luaparser.asttokens.Tokens enum with existing members (SPACE, LOCAL, etc.) — unchanged.

    • ast.walk(tree) — returns an iterable that yields every node in the tree.

    • node.tokens — an indexable sequence of token objects.

Currently, a node's tokens sequence begins at its first meaningful (non-hidden) token. It must instead begin earlier, extended backward to include the run of hidden tokens (whitespace such as spaces ' ', newlines '\n', indentation like ' ', and comments such as '-- exemple') that sit immediately before that first meaningful token.

In other words, for each node, prepend to its tokens sequence the contiguous block of leading hidden tokens that precede its first significant token. The trailing end of a node's token range is unchanged. The order of tokens must be preserved (leading hidden tokens first, in source order, followed by the previously-included tokens).

  • The full sequence of a node's own tokens (keywords, operators, identifiers, literals, interior whitespace, and body tokens) remains as before; only leading hidden tokens are added at the front.
  • Parsing itself (which constructs are recognized, node types produced, tree structure, and ast.walk traversal order) is unchanged.

Summary

Extend each AST node's token span to also cover the immediately-preceding hidden (whitespace/comment) tokens, so that node.tokens starts at the first hidden token of the leading whitespace/comment run that precedes the node's first significant token. Everything else about node tokens and parsing is unchanged.

Constraints

  • The ignore argument is a list of token type values drawn from Tokens.
