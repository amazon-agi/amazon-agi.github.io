Overview

You are working on pynetbox, a Python client library for the NetBox API. API responses are represented as record objects, and nested API values may themselves be represented as records. This task concerns correct construction, endpoint identity, comparison, hashing, serialization compatibility, and write behavior for these records, especially when a related object is embedded in a parent response.

Required Behavior

1. Nested records must behave like directly fetched records

When a record is built from an API response, a nested dictionary representing a related API object—at minimum, one containing an id and a url—must be wrapped as a full record object. The same applies to such dictionaries contained in lists. Other structured values that are already modeled as nested records, such as value/label/id choice objects, must continue to be exposed through attribute access.

For endpoint identity, equality, hashing, scalar field access, and collection membership, a related record built from nested response data must behave like the same resource fetched directly from its own endpoint. All fields supplied in the nested response, including id, vid, name, and display_name, must remain accessible on the nested record.

2. Derive resource endpoint context from canonical object URLs

When record data contains a canonical NetBox object URL of the form:

<base_url>/api/<app>/<endpoint>/<id>/

the record's resource endpoint context must be derived from the app and endpoint represented by that URL. This applies independently to every nested record; a nested object must not retain the parent's resource type merely because it was embedded in the parent's response.

For example, a VLAN embedded in a DCIM interface response with an URL under /api/ipam/vlans/ must acquire VLAN endpoint identity, while the enclosing object retains interface endpoint identity. A directly fetched VLAN and that nested VLAN can therefore have the same record identity.

Endpoint reconstruction must not alter the existing behavior of records that were fetched directly or records whose endpoint was already supplied by the endpoint loader.

3. Endpoint derivation must be safe without a usable API client

Record construction is also supported directly through pynetbox.core.response.Record(values, api, endpoint). Constructing a record must continue to work when api is None or otherwise lacks usable client configuration, even when the record itself or any nested record contains a full canonical object URL. Construction must not fail merely because endpoint derivation cannot read client properties such as base_url, token, session_key, or ssl_verify.

Such locally constructed records must remain usable for local record operations, including:

  • parsing and accessing nested values;
  • serialize(); and
  • _diff().

In particular, serialization must retain its established behavior of converting nested records in a list to their IDs. Existing set-like serialization and diff semantics for fields such as tagged_vlans and tags must remain intact; duplicate values must not create a spurious change. If endpoint context cannot be materialized because no usable client exists, the endpoint supplied to the constructor, including None, is a valid fallback for these local operations.

This no-client guarantee applies to construction and local operations. Network operations may still require a usable API client and HTTP session.

4. Noncanonical or incomplete URLs must degrade gracefully

A url value is not guaranteed to have the canonical /api/<app>/<endpoint>/<id>/ shape. If its path does not contain enough information to identify an app and endpoint, record construction must not raise an error. The endpoint supplied to the record constructor must be retained instead.

For example, a nested record with the URL:

http://localhost:8080/test

must still be constructed successfully even though no NetBox app and endpoint can be derived from the path.

The record's own URL remains authoritative for writes. After a field on such an existing nested record is changed, save() must PATCH the nested record's own normalized URL—not its parent's endpoint URL. A URL without a trailing slash must be normalized for the request, so the example above is written as:

http://localhost:8080/test/

Failure to derive endpoint identity must not prevent that write when the record otherwise has the API/session context needed to perform it.

5. Equality, hashing, and membership

Record equality must represent resource identity rather than construction origin. Records with the same resource endpoint identity and the same id must compare equal whether they came from a direct fetch, a nested dictionary, or a list within another response. Resource IDs continue to distinguish different records within an endpoint.

Hashing must be consistent with equality: whenever two records compare equal, their hash values must also be equal. This preserves correct behavior in hashed collections as well as ordinary list membership. Comparing a directly fetched record against a list of nested records with the in operator must therefore succeed when the list contains the same resource.

Scalar fields do not replace identity comparison, but fields present in both representations must expose their corresponding response values. In particular, directly fetched and nested representations of the same VLAN must expose matching id and vid values.

6. Interface records expose VLAN-related fields

An interface record returned from the DCIM interfaces endpoint must expose the following attributes from its API data:

  • mode: a nested object exposing its value, label, and id values when present;
  • untagged_vlan: a nested VLAN record object; and
  • tagged_vlans: a list of nested VLAN record objects.

Every entry in tagged_vlans must be a fully formed record exposing its id, vid, and all other VLAN fields included in the response. The VLAN records in both untagged_vlan and tagged_vlans must receive VLAN endpoint identity from their object URLs when those URLs are canonical.

Public API Surface

The following imports and call patterns must remain available:

  • pynetbox.api(...) creates the top-level API client.
  • The client exposes applications and endpoints through attribute access.
  • client.dcim.interfaces.get(<id>) returns one interface record.
  • client.ipam.vlans.get(<id>) returns one VLAN record. Equivalently, when the IPAM app is held in a variable, ipam.vlans.get(<id>) performs the same operation.
  • Endpoint objects expose get(<id>), and records returned by it are built from JSON API responses.
  • pynetbox.core.response.Record(values, api, endpoint) remains usable for direct record construction, including the no-client local-operation cases described above.
Interface record attributes

An interface record from dcim/interfaces must support:

  • interface.tagged_vlans → a list of VLAN records;
  • interface.untagged_vlan → a VLAN record; and
  • interface.mode → a nested value/label/id object.
VLAN record attributes

  • .id;
  • .vid; and
  • all other fields present in its response data, such as name, display_name, site, and role.

HTTP Request Behavior

Fetching one record by ID must issue an HTTP GET to the detail URL:

<base_url>/api/<app>/<endpoint>/<id>/

For example, fetching interface ID 1 uses:

http://localhost:8000/api/dcim/interfaces/1/

With no query parameters, the underlying GET call must receive:

  • params={};
  • json=None;
  • the standard request headers, including authentication when configured; and
  • verify=True under the default SSL-verification configuration.

The request layer must continue accepting URL query parameters and passing them through via the underlying GET call's params keyword argument. A plain single-record ID fetch with no parameters must use an empty dictionary rather than omitting params. Endpoint reconstruction for nested records must not change this request signature.

Concrete Consistency Requirement

Given a VLAN fetched directly and an interface whose tagged_vlans data contains that VLAN:

interface = client.dcim.interfaces.get(1)

where the direct and nested VLAN representations both have ID 3 and VID 1210, all of the following must hold:

vlan.vid == interface.tagged_vlans[0].vid
vlan.id == interface.tagged_vlans[0].id

hash(vlan) == hash(interface.tagged_vlans[0])

Compatibility Constraints

  • Existing record construction and endpoint behavior for directly fetched records must remain intact.
  • Existing conversion of nested dictionaries and lists into record objects must remain intact.
  • Serialization, comparison, diffing, saving, deleting, and lazy detail behavior outside the endpoint-identity correction must not regress.
  • Canonical URL endpoint derivation is best-effort when client context is unavailable and must be non-fatal for unrecognized URL shapes.
  • A noncanonical URL does not need to become a navigable NetBox endpoint; it must remain usable as the record's own write URL.
  • Equality/hash and endpoint reconstruction changes must not change the standard single-record fetch request or query-parameter behavior described above.

Modify the pynetbox NetBox client so that SSL verification is no longer configured by a library-level ssl_verify option or by a verify keyword on individual HTTP calls. TLS behavior must instead be left to the HTTP machinery being used. Also make acquisition of the authentication session key lazy and specific to secrets access rather than an initialization side effect.

The API object continues to own a shared requests.Session for normal API traffic. API-version discovery is the deliberate exception: it must retain its existing module-level requests.get dispatch rather than using the API object's shared session.

1. Remove the ssl_verify option and state

The ssl_verify option must be removed completely.

  • The public constructor remains callable as pynetbox.api(url, token=None, private_key=None, private_key_file=None, threading=False) with the existing arguments and semantics, but it must not accept an ssl_verify keyword argument. Supplying that removed keyword must be rejected rather than silently accepted or ignored.
  • The resulting API object must not expose an ssl_verify attribute.
  • Application accessors and endpoint objects must not expose or propagate an ssl_verify attribute.
  • The request/query layer must not accept, retain, or use ssl_verify configuration either.
  • Do not introduce a renamed replacement option or a compatibility alias for this setting.

Existing constructor behavior unrelated to SSL verification remains unchanged, including URL normalization, token and private-key handling, the mutual-exclusion rule for private_key and private_key_file, and the threading option.

No outgoing HTTP operation may supply a verify keyword argument. This applies to GET, POST, PUT, PATCH, DELETE, OPTIONS, session-key authentication, OpenAPI retrieval, count queries, pagination requests, detail routes, custom RPC-style routes, and any other HTTP operation issued by the library.

For calls made through the API object's shared requests.Session, preserve the existing session object, HTTP method, URL, and every request argument other than verify. In particular:

  • A normal endpoint GET continues to receive its URL and the existing params, json, and headers keyword arguments.
  • A normal endpoint POST continues to receive its URL and the existing params, headers, and json keyword arguments.
  • A normal endpoint DELETE continues to receive its URL and the existing params, json, and headers keyword arguments.
  • Specialized calls that intentionally use a narrower argument set, such as OpenAPI retrieval, must retain that argument set and merely omit verify.

For example, the effective shapes are equivalent to:

http_session.get(url, params=params, json=data, headers=headers)
http_session.post(url, params=params, headers=headers, json=data)
http_session.delete(url, params=params, json=data, headers=headers)

The exact existing values of URLs, parameters, JSON bodies, form data, and headers—including token and session-key headers—must not otherwise change. The library must neither set a per-call verification flag nor use the removed constructor option to alter the shared session. A caller that needs custom certificate verification behavior can configure or replace the API object's http_session; the session's own behavior governs calls dispatched through it.

3. Acquire a secrets session key only when needed

Session-key acquisition must no longer occur while constructing the API object or while constructing a low-level request/query object.

  • Creating pynetbox.api(...), including with both a token and a private key, must not itself send a session-key POST.
  • Merely obtaining application or endpoint objects must not send that POST.
  • Using non-secrets applications must not acquire a session key. Ordinary operations such as all, filter, get, create, record updates or deletion, detail-endpoint calls, custom RPC-style calls, choices, and count queries must continue to work without an initialization-time session-key request.
  • When authenticated secrets access actually requires a session key and the necessary token and private key are available, acquisition is initiated at the secrets application level rather than by general request construction.
  • Preserve the existing secrets authentication protocol: acquire the key through the shared HTTP session, use the existing session-key endpoint, credentials, form body, response handling, and subsequent X-Session-Key authentication behavior. That authentication POST must also omit verify.

This is a relocation and timing change, not a redesign of token authentication, private-key loading, secrets decryption, response handling, or error behavior.

4. Preserve the API-version discovery dispatch boundary

The version property and the corresponding version lookup must remain an exception to shared-session dispatch.

  • Version discovery must issue its GET through the module-level requests.get function.
  • It must not issue that GET through api.http_session, even if the caller has configured or replaced that session.
  • The call must preserve the existing normalized API base URL and Content-Type: application/json; header, but it must not include a verify keyword.
  • Existing result behavior remains unchanged: return the API-Version response header when present, return an empty string when the header is absent on a successful response, and preserve the existing request-error behavior for an unsuccessful response.

Thus, configuring the API object's session affects ordinary API and OpenAPI calls but does not reroute version discovery through that session.

5. Preserve the existing public client surface

The following interfaces must remain importable and callable:

  • pynetbox.api(url, ...), subject only to removal of ssl_verify.
  • The standard application accessors, including dcim, ipam, circuits, secrets, tenancy, extras, and virtualization.
  • Dynamically exposed endpoint objects such as devices, interfaces, racks, prefixes, VLANs, cables, and the other existing endpoints.
  • Existing endpoint and record operations, including all, filter, get, create, count, choices operations, record save/update/delete operations, detail endpoints, and custom calls.
  • OpenAPI-document retrieval and low-level count retrieval.

All of these operations must preserve their existing URL construction, authentication headers, filtering, pagination, serialization, return values, and error behavior except for the explicitly required session-key timing change and omission of verify.

Constraints and non-goals

  • Do not alter request URLs, methods, query parameters, bodies, headers, response conversion, or error handling merely to accomplish this change.
  • Do not move API-version discovery onto the API object's stored session.
  • Do not add new required behavior beyond removing ssl_verify and per-call verify, making secrets session-key acquisition lazy, and preserving the version-discovery dispatch behavior described above.

Package Structure and Public API Surface

The following import paths and names must be available:

  • pynetbox.api(url, token=None, private_key_file=None) — factory returning an API client object.
  • pynetbox.core.response.Record — record class.
  • pynetbox.core.query.Request — request class.
  • pynetbox.core.query.url_param_builder — function.
  • pynetbox.core.query.Request.get and Request.options — public instance methods that can be dynamically replaced through normal Python attribute replacement.
  • pynetbox.core.endpoint.Endpoint — endpoint class, importable as Endpoint.
  • pynetbox.models.dcim.Devices — DCIM device record subclass.
  • pynetbox.models.ipam.IpAddresses — IPAM IP-address record subclass.
  • pynetbox.models.ipam.Prefixes — IPAM prefix record subclass.

HTTP operations use requests.sessions.Session, referenced at pynetbox.core.query.requests.sessions.Session, for session-based methods including get, post, put, patch, and delete. API version detection uses requests.get directly. Calls use the keyword arguments params=, json=, and headers= in the shapes described below, except where an operation's explicit call shape omits them.

API Client — pynetbox.api

pynetbox.api(url, token=None, private_key_file=None) returns a truthy client object with:

  • base_url: the supplied URL with trailing slashes removed and /api appended. Both "http://localhost:8000" and "http://localhost:8000/" therefore produce "http://localhost:8000/api".
  • Application accessors dcim, ipam, circuits, tenancy, virtualization, and extras.
  • A version property that performs requests.get against the base API URL and returns the response's API-Version header. If that header is absent, it returns "".

When token and private_key_file are both supplied, initialization obtains a session key by issuing a session POST. The response has a JSON body containing the session key.

Application Objects

An application accessor such as api.dcim returns an application object with these behaviors:

  • Endpoint attributes are created by attribute access, for example api.dcim.devices, api.ipam.prefixes, and api.circuits.circuits.
  • custom_choices() returns the JSON dictionary returned by Request.get without changing its keys or values. For example, a result keyed by Testfield1 and Testfield2 is returned with those same entries.
  • choices() on the DCIM application sends a session GET to {base_url}/dcim/_choices/ with params={}, json=None, and the standard GET headers, then returns the parsed truthy dictionary.

Endpoints — pynetbox.core.endpoint.Endpoint

The constructor is Endpoint(api, app, name).

Endpoint attribute names may contain underscores. The endpoint object's name and its URL use hyphens in place of underscores. The list URL is:

{base_url}/{app}/{name-with-hyphens}/
all()

Sends a session GET to the list URL with params={}, json=None, and the standard GET headers. It returns a list of instances of the endpoint's record class.

Pagination must be followed and all result pages combined. On the first pagination follow-up, the request still targets the plain list URL and uses the server-derived pagination window as parameters; for example, params={"limit": 221, "offset": 50}.

filter(**kwargs)

Sends a session GET to the list URL with the supplied filters as params, json=None, and the standard GET headers. It returns a list of record objects.

  • List-valued filters are passed through unchanged. For example, filter(role=["test", "test1"], site="TEST#1") sends params={"role": ["test", "test1"], "site": "TEST#1"}.
  • At least one filter is required; filter() with no filters raises ValueError rather than behaving like all().
  • Endpoint-control names such as id are reserved for this method. In particular, filter(id=1) raises ValueError; IDs must be retrieved with get. The reserved names are id, pk, limit, and offset.
get(id)

Sends a session GET to {list_url}{id}/ with params={}, json=None, and the standard GET headers. It returns one instance of the endpoint's record class. The returned value supports both str(record) and dict(record).

create(...)

Two calling forms are required:

  • create(**fields) creates one object, sends a session POST, and returns a truthy record object.
  • create(list_of_dicts) performs bulk creation, sends a session POST, and returns a list of record objects.
choices()

Uses Request.options() and returns the endpoint's parsed choices. Given an OPTIONS document whose actions.POST fields contain choices lists, the returned dictionary maps each such field directly to its choices list.

Records — pynetbox.core.response.Record

The constructor is Record(values, api, endpoint), where values is a dictionary.

Attribute, string, and dictionary behavior
  • Top-level dictionary keys become attributes.
  • Nested dictionaries are recursively converted to Record objects or the appropriate specialized subclass, except for fields explicitly required to remain plain dictionaries.
  • Lists of nested dictionaries become lists of record objects.
  • str(record) returns a string. Where the record class has an appropriate display or name field, that field defines the representation; for example, a circuit with display value "123456" has str(record) == "123456".
  • dict(record) reconstructs a plain dictionary: nested records become dictionaries and lists of records become lists of dictionaries.
  • custom_fields remains a directly accessible, mutable dictionary, so callers can use record.custom_fields[...].
Lazy loading of partial nested records

A nested object may initially contain only a partial representation such as its id, display fields, and url. If a missing attribute is requested from such a record and the record has a url, attribute access must retrieve the full object from that URL, populate the record from the response, and return the requested attribute. Thus accessing device.rack.role must work even when the device's embedded rack data omitted role, provided the rack's detail URL supplies it; the resulting nested role is itself a Record.

The full-detail lookup is triggered by normal missing-attribute access and is not repeatedly performed after details have been loaded. If no URL exists, or the requested attribute is still absent after hydration, normal AttributeError behavior applies. Probing the special keys attribute while converting a record to a dictionary must not trigger network hydration.

Equality and hashing

Records are hashable and compare by API identity:

  • A record's identity key is its endpoint name together with its id when an ID is present. A record without an ID is keyed by its endpoint name.
  • hash(record) returns an integer.
  • Two Record instances with the same endpoint name and ID compare equal and have equal hashes, even if they are distinct Python objects or came from different responses.
  • Records with different IDs compare unequal and produce different hashes; records from different endpoint names are likewise distinct.

This equality behavior must make ordinary membership operations work across separately loaded representations. For example, a VLAN loaded from the VLAN endpoint must compare equal to the corresponding VLAN object in an interface's tagged_vlans list when their endpoint names and IDs match.

serialize()

Returns a dictionary suitable for writing to the API. Serialization follows these rules:

  • Scalar fields are emitted as-is. Aftertee is imposed by this deduplication.
  • custom_fields is included as a nested dictionary. Mutating record.custom_fields["test_custom"] = "Testing" produces serialize()["custom_fields"]["test_custom"] == "Testing"; custom choice dictionaries serialize to their underlying value.
  • Assigning a scalar equal to the underlying value of an originally nested choice is serialization-equivalent to leaving that choice unchanged.
_diff() and _compare()

_diff() returns a set containing exactly the names of fields whose effective serialized values differ from their initial serialized values. For example, changing tags, replacing a nested object, and changing a string field returns those three field names, while untouched fields are omitted.

Diffing uses the same record-to-ID, choice-value, and set-like normalization as serialize(). Therefore, adding a duplicate scalar ID to a tagged_vlans list that already contains a record with that ID yields an empty/falsy _diff() result.

_compare() returns True when the current serialized state equals the loaded state and False after an effective field change. Normalization-equivalent assignments are unchanged for this purpose. Choice fields must round-trip idempotently for all of these initial shapes:

  • {"value": 1, "label": "test"} followed by assignment of 1.
  • {"value": "test", "label": "test", "id": 1} followed by assignment of "test".
  • {"value": "test", "label": "test"} followed by assignment of "test".
save() and updates

When effective changes exist, save() sends an HTTP PATCH containing the changed serialized fields and returns a truthy success result. A record with no effective changes is idempotent: saving it performs no update and returns a falsy value.

A nested child record that has its own url saves against that URL, not its parent's endpoint. For example, changing a child loaded from http://localhost:8080/api/test-app/test-endpoint/ and calling child.save() uses that URL as the first argument to the session's patch method.

delete()

Sends a session DELETE to the record's detail URL with params={}, json=None, and the standard GET/DELETE headers. It returns a truthy value on success.

_endpoint_from_url(url)

Derives the record endpoint from a detail URL. Given http://localhost:8080/api/test-app/test-endpoint/1/, it returns an endpoint whose name is "test-endpoint": the endpoint is the segment after the application segment and before any trailing numeric ID.

Related-Object and Detail Endpoints

Certain record classes expose detail endpoints relative to the parent record's detail URL:

  • device.napalm.list(method="get_facts") sends a session GET to {base_url}/dcim/devices/1/napalm/ with params={"method": "get_facts"}, json=None, and the standard GET headers. It returns the parsed body, including a truthy ret["get_facts"] when supplied by the API.
  • rack.units.list() sends a session GET to {base_url}/dcim/racks/1/units/ with params={}, json=None, and the standard GET headers. It returns a list whose entries expose .device as pynetbox.models.dcim.Devices.
  • rack.elevation.list() behaves the same way at {base_url}/dcim/racks/1/elevation/, including the typed .device attribute.
  • prefix.available_ips.list() sends a session GET to {base_url}/ipam/prefixes/1/available-ips/ with the same empty-parameter GET shape and returns a list, such as a three-entry available-address result.
  • prefix.available_ips.create(params) sends a session POST to {base_url}/ipam/prefixes/1/available-ips/ with params={}, the standard JSON POST headers, and json=params. A single-object response is returned as a truthy pynetbox.models.ipam.IpAddresses instance, not as a raw dictionary.

  • Without a token: {"accept": "application/json;"}.
  • With token abc123: {"accept": "application/json;", "authorization": "Token abc123"}.

{"Content-Type": "application/json;", "authorization": "Token abc123"}
