Task Description

Behavior Overview

You will be working on pynetbox, a Python client library for the NetBox API. Record objects stand in for API responses, and nested API values may themselves take the shape of records. This task is about getting construction, endpoint identity, comparison, hashing, serialization compatibility, and write behavior right for these records, with particular attention to the case where a related object is embedded in a parent response.

Behavior Requirements

1. A nested record must behave like one that was fetched directly

Whenever a record gets built from an API response, a nested dictionary that stands for a related API object must be wrapped to form a full record object; at minimum, this covers a dictionary that contains an id and a url. Dictionaries of this kind that sit inside lists fall under the same rule. Other structured values that already get modeled as nested records—value/label/id choice objects, for instance—must continue to be exposed through attribute access.

With respect to endpoint identity, equality, hashing, scalar field access, and collection membership, the behavior of a related record assembled from nested response data must match that of the same resource when it is fetched directly from its own endpoint. Every field the nested response supplies—id, vid, name, and display_name among them—must stay accessible on the nested record.

2. Resource endpoint context must be derived from canonical object URLs

If the record data includes a canonical NetBox object URL of the form:

<base_url>/api/<app>/<endpoint>/<id>/

then the app and endpoint shown by that URL must be what the record's resource endpoint context is derived from. Every nested record is covered by this in its own right; a nested object must not hold on to the parent's resource type just because it was embedded in the parent's response.

To illustrate: a VLAN embedded in a DCIM interface response whose URL sits under /api/ipam/vlans/ must take on VLAN endpoint identity, while the object that encloses it keeps interface endpoint identity. For that reason, a directly fetched VLAN and that nested VLAN can share the same record identity.

The existing behavior of records that were fetched directly, and of records whose endpoint was already supplied by the endpoint loader, must not be altered by endpoint reconstruction.

3. Endpoint derivation must stay safe without a usable API client

Direct construction of records is also supported, via pynetbox.core.response.Record(values, api, endpoint). Even in cases where the record itself, or any nested record it contains, holds a full canonical object URL, construction must keep working when api is None or otherwise lacks usable client configuration. Endpoint derivation being unable to read client properties such as base_url, token, session_key, or ssl_verify must not, on its own, make construction fail.

Records built locally like this must stay usable for local record operations, including:

  • parsing of nested values and access to them;
  • serialize(); and
  • _diff().

In particular, when nested records sit in a list, serialization must keep up its established practice of converting them to their IDs. The set-like serialization and diff semantics that fields such as tagged_vlans and tags already exhibit must stay intact; duplicate values must not bring about a spurious change. Should endpoint context be impossible to materialize because no usable client exists, the endpoint given to the constructor—None included—is a valid fallback for these local operations.

Construction and local operations are what this no-client guarantee covers. A usable API client and an HTTP session may still be required by network operations.

4. URLs that are noncanonical or incomplete must degrade gracefully

Nothing guarantees that a url value has the canonical /api/<app>/<endpoint>/<id>/ shape. When its path holds too little information for an app and endpoint to be identified from it, an error must not be raised by record construction; instead, the endpoint given to the record constructor must be kept.

To take an example, consider a nested record whose URL is:

http://localhost:8080/test

Even though the path allows no NetBox app and endpoint to be derived from it, construction of this record must still succeed.

Where writes are concerned, the URL belonging to the record itself stays authoritative. After a field on an existing nested record of this kind has been changed, save() must issue its PATCH against the nested record's own normalized URL—not its parent's endpoint URL. When a URL has no trailing slash, it must be normalized for the request, so the example above ends up written as:

http://localhost:8080/test/

Provided the record otherwise has the API/session context that performing the write calls for, a failure to derive endpoint identity must not stand in the way of that write.

5. Record equality, hashing, and membership

What record equality must represent is resource identity, not the origin a record was constructed from. When two records have the same resource endpoint identity and the same id, they must compare equal, no matter whether they came from a direct fetch, from a nested dictionary, or from a list inside another response. Within an endpoint, different records keep being distinguished from one another by their resource IDs.

Hashing must line up with equality: whenever two records compare equal, their hash values must be equal too. Correct behavior in hashed collections, as well as in ordinary list membership, is preserved by this. It follows that using the in operator to compare a directly fetched record against a list of nested records must succeed when that list holds the same resource.

Identity comparison is not replaced by scalar fields; nevertheless, any field that both representations contain must expose the response value corresponding to it. One case in point: the directly fetched and the nested representation of the same VLAN must expose id and vid values that match.

6. VLAN-related fields must be exposed by interface records

From the API data of an interface record returned by the DCIM interfaces endpoint, the following attributes must be exposed:

  • mode: a nested object that, when the values are present, exposes its value, label, and id;
  • untagged_vlan: an object that is a nested VLAN record; and
  • tagged_vlans: a list made up of nested VLAN record objects.

Every entry that tagged_vlans contains must be a fully formed record, one that exposes its id, vid, and all the other VLAN fields included in the response. Both the VLAN records under untagged_vlan and those under tagged_vlans must be given VLAN endpoint identity from their object URLs when those URLs are canonical.

Public API

Availability must be preserved for the following imports and call patterns:

  • The top-level API client comes from pynetbox.api(...).
  • Through attribute access, the client exposes applications and endpoints.
  • One interface record is returned by client.dcim.interfaces.get(<id>).
  • One VLAN record is returned by client.ipam.vlans.get(<id>). When the IPAM app is held in a variable, ipam.vlans.get(<id>) performs the same operation; the two forms are equivalent.
  • Endpoint objects expose get(<id>), and the records that this call returns are built from JSON API responses.
  • pynetbox.core.response.Record(values, api, endpoint) remains usable for direct record construction, the no-client local-operation cases described above included.
Attributes of interface records

These attributes must be supported by an interface record from dcim/interfaces:

  • interface.tagged_vlans → a list of VLAN records;
  • interface.untagged_vlan → a VLAN record; and
  • interface.mode → a nested value/label/id object.
Attributes of VLAN records

Whether it was fetched directly or came nested, a VLAN record out of ipam/vlans must support:

  • .id;
  • .vid; and
  • all the other fields its response data contains, such as name, display_name, site, and role.

Behavior of HTTP Requests

An HTTP GET must be issued to the detail URL when a single record is fetched by ID:

<base_url>/api/<app>/<endpoint>/<id>/

By way of example, interface ID 1 is fetched using:

http://localhost:8000/api/dcim/interfaces/1/

If no query parameters are present, the following is what the underlying GET call must receive:

  • params={};
  • json=None;
  • the standard request headers, authentication included when it is configured; and
  • verify=True with the SSL-verification configuration left at its default.

URL query parameters must continue to be accepted by the request layer, which passes them through via the params keyword argument of the underlying GET call. For a plain ID fetch of a single record without parameters, an empty dictionary must be used; leaving params out is not allowed. The request signature must not be changed by the endpoint reconstruction carried out for nested records.

Concrete Requirement for Consistency

Suppose a VLAN is fetched directly, and an interface's tagged_vlans data contains that VLAN:

vlan = client.ipam.vlans.get(3)
interface = client.dcim.interfaces.get(1)

with the direct and the nested VLAN representation both carrying ID 3 and VID 1210; under these conditions, the following must all hold:

vlan.vid == interface.tagged_vlans[0].vid
vlan.id == interface.tagged_vlans[0].id
vlan in interface.tagged_vlans
hash(vlan) == hash(interface.tagged_vlans[0])

Constraints on Compatibility

  • For records obtained by a direct fetch, the record construction and endpoint behavior that already exist must stay intact.
  • The conversion that already turns nested dictionaries and lists into record objects must stay intact.
  • Outside the endpoint-identity correction, serialization, comparison, diffing, saving, deleting, and lazy detail behavior must not regress.
  • Deriving an endpoint from canonical URLs is best-effort whenever client context is unavailable, and for URL shapes that are not recognized the derivation must be non-fatal.
  • There is no requirement for a noncanonical URL to become a navigable NetBox endpoint; it must stay usable as the write URL belonging to the record itself.
  • The equality/hash changes and the endpoint reconstruction changes must leave the standard single-record fetch request and the query-parameter behavior described above unchanged.

Summary

Within the pynetbox NetBox client, configuration of SSL verification by a library-level ssl_verify option and by a verify keyword on individual HTTP calls must stop happening; TLS behavior must instead be left to whatever HTTP machinery is in use. Acquisition of the authentication session key, in addition, is to become lazy and specific to secrets access rather than a side effect of initialization.

For ordinary API traffic, a shared requests.Session remains owned by the API object. The deliberate exception is API-version discovery: dispatch by way of the module-level requests.get, exactly as it works today, must be retained there rather than sending that traffic through the API object's shared session.

1. Removing the ssl_verify option and the state attached to it

The ssl_verify option must be eliminated in full.

  • Calling the public constructor as pynetbox.api(url, token=None, private_key=None, private_key_file=None, threading=False) keeps working with the same arguments and semantics as before; an ssl_verify keyword argument, though, must not be accepted by it. When that removed keyword is supplied, it must be rejected — quietly taking it or overlooking it is not allowed.
  • Exposing an ssl_verify attribute on the API object that gets built must not happen.
  • An ssl_verify attribute must not be exposed or propagated by application accessors or by endpoint objects.
  • Accepting, retaining, or using ssl_verify configuration must not happen in the request/query layer either.
  • A renamed replacement option, and equally a compatibility alias for this setting, must not be introduced.

Constructor behavior that has nothing to do with SSL verification keeps working as before — URL normalization, token and private-key handling, the mutual-exclusion rule for private_key and private_key_file, and the threading option all belong to this category.

2. Never pass verify on a per-call basis

There is no outgoing HTTP operation that may supply a verify keyword argument. In scope are GET, POST, PUT, PATCH, DELETE, OPTIONS, session-key authentication, OpenAPI retrieval, count queries, pagination requests, detail routes, custom RPC-style routes, and any other HTTP operation the library issues.

For calls that travel through the API object's shared requests.Session, what must be preserved is the existing session object, the HTTP method, the URL, and every request argument other than verify. Concretely:

  • For a normal endpoint GET, the URL keeps being handed over along with the existing params, json, and headers keyword arguments.
  • For a normal endpoint POST, the URL keeps being handed over along with the existing params, headers, and json keyword arguments.
  • For a normal endpoint DELETE, the URL keeps being handed over along with the existing params, json, and headers keyword arguments.
  • Specialized calls that by design operate with a narrower argument set — OpenAPI retrieval, for one — must hold on to that argument set and omit nothing besides verify.

To give an example, the calls effectively take these shapes:

http_session.get(url, params=params, json=data, headers=headers)
http_session.post(url, params=params, headers=headers, json=data)
http_session.delete(url, params=params, json=data, headers=headers)

In every other respect, URLs, parameters, JSON bodies, form data, and headers — token and session-key headers included — must hang on to their exact current values. Setting a per-call verification flag is something the library must not do, and the removed constructor option must not serve it as a means of altering the shared session either. If custom certificate verification behavior is what a caller needs, that caller can configure or replace the API object's http_session; calls dispatched through the session are then governed by the session's own behavior.

3. A secrets session key is acquired only when it is needed

Session-key acquisition must no longer be set off by construction of the API object, nor by construction of a low-level request/query object.

  • Creating pynetbox.api(...) must not, on its own, send a session-key POST — including when a token and a private key are both supplied.
  • That POST must not go out merely because application or endpoint objects were obtained.
  • Working with non-secrets applications must not lead to a session key being acquired. Ordinary operations — all, filter, get, create, record updates or deletion, detail-endpoint calls, custom RPC-style calls, choices, and count queries among them — must keep working with no session-key request made at initialization time.
  • When authenticated secrets access actually requires a session key, and the necessary token and private key are available, initiation of the acquisition happens at the secrets application level — general request construction is not what triggers it.
  • The secrets authentication protocol already in place must be preserved: the key is acquired through the shared HTTP session, and use is made of the existing session-key endpoint, credentials, form body, response handling, plus the X-Session-Key authentication behavior that follows. verify must likewise be left out of that authentication POST.

In sum, this is about moving where and when the acquisition happens; token authentication, private-key loading, secrets decryption, response handling, and error behavior are not being redesigned.

4. Keeping the dispatch boundary for API-version discovery

An exception to shared-session dispatch must continue to exist, taking the form of the version property and the version lookup that corresponds to it.

  • The GET that version discovery performs must be issued through the module-level requests.get function.
  • Issuing that GET through api.http_session must not happen, even if the caller has configured or replaced that session.
  • What the call must preserve is the existing normalized API base URL along with the Content-Type: application/json; header, while a verify keyword must not be included.
  • How results behave is untouched: when the API-Version response header is present, return it; when that header is absent on a successful response, return an empty string; and for an unsuccessful response, the existing request-error behavior must be preserved.

Configuring the API object's session therefore does make a difference for ordinary API and OpenAPI calls, yet version discovery is not rerouted through that session.

5. Keeping the public client surface as it exists

The interfaces enumerated next must remain importable and callable:

  • pynetbox.api(url, ...), the removal of ssl_verify being its only exception.
  • The standard application accessors, which include dcim, ipam, circuits, secrets, tenancy, extras, and virtualization.
  • Endpoint objects that get exposed dynamically, with devices, interfaces, racks, prefixes, VLANs, cables, and the other existing endpoints as examples.
  • The operations that endpoints and records already offer, which include all, filter, get, create, count, choices operations, record save/update/delete operations, detail endpoints, and custom calls.
  • Retrieval of the OpenAPI document plus low-level count retrieval.

For every one of these operations, the existing URL construction, authentication headers, filtering, pagination, serialization, return values, and error behavior must be kept; the explicitly required session-key timing change and the omission of verify are the exceptions.

Constraints and non-goals

  • Request URLs, methods, query parameters, bodies, headers, response conversion, and error handling must not be altered merely in order to accomplish this change.
  • API-version discovery must not be relocated onto the session that the API object stores.
  • Removing ssl_verify and per-call verify, making secrets session-key acquisition lazy, and preserving the version-discovery dispatch behavior described above — beyond these items, new required behavior must not be added.

Task Specification: Building the pynetbox Client Library

Build pynetbox, a Python client library that interacts with a NetBox REST API. An API client, application accessors, endpoint objects, record objects, specialized record subclasses, and low-level query utilities are the pieces the library provides. The behavior laid out below is required.

Package Layout and Public Interface

These import paths and names must be available:

  • pynetbox.api(url, token=None, private_key_file=None) — a factory that returns an API client object.
  • pynetbox.core.response.Record — the record class.
  • pynetbox.core.query.Request — the request class.
  • pynetbox.core.query.url_param_builder — a function.
  • pynetbox.core.query.Request.get and Request.options — public instance methods that normal Python attribute replacement can dynamically swap out.
  • pynetbox.core.endpoint.Endpoint — the endpoint class, which can be imported as Endpoint.
  • pynetbox.models.dcim.Devices — the record subclass for DCIM devices.
  • pynetbox.models.ipam.IpAddresses — the record subclass for IPAM IP addresses.
  • pynetbox.models.ipam.Prefixes — the record subclass for IPAM prefixes.

Session-based methods — get, post, put, patch, and delete among them — carry out their HTTP work through requests.sessions.Session, referenced at pynetbox.core.query.requests.sessions.Session. Version detection for the API relies on requests.get, used directly. The keyword arguments params=, json=, and headers= appear in calls with the shapes described below; an operation whose explicit call shape leaves them out is the exception.

The API Client — pynetbox.api

The call pynetbox.api(url, token=None, private_key_file=None) returns a truthy client object equipped with:

  • base_url: whatever URL was passed in, minus its trailing slashes, with /api added at the end. Both "http://localhost:8000" and "http://localhost:8000/" therefore end up as "http://localhost:8000/api".
  • Accessors for the applications dcim, ipam, circuits, tenancy, virtualization, and extras.
  • A version property that runs requests.get against the base API URL and returns the response's API-Version header — or, when that header is absent, "".

Suppose both a token and a private_key_file are given: initialization then obtains a session key by way of a session POST, and the session key sits in the JSON body of the response.

Application Accessor Objects

An application accessor — api.dcim, say — returns an application object, and that object behaves as follows:

  • Endpoint attributes come into existence through attribute access; examples are api.dcim.devices, api.ipam.prefixes, and api.circuits.circuits.
  • custom_choices() returns whatever JSON dictionary Request.get returned, keys and values left as they were. To illustrate: a result keyed by Testfield1 and Testfield2 is returned carrying those same entries.
  • On the DCIM application, choices() performs a session GET against {base_url}/dcim/_choices/, passing params={}, json=None, and the standard GET headers, and it then returns the parsed dictionary, which is truthy.

Endpoint Objects — pynetbox.core.endpoint.Endpoint

Endpoint(api, app, name) is the constructor.

Underscores may appear in endpoint attribute names. Hyphens stand in for underscores in the endpoint object's name and in its URL. The list URL then reads:

{base_url}/{app}/{name-with-hyphens}/
all()

A session GET goes out to the list URL, carrying params={}, json=None, and the standard GET headers; the method returns a list of instances of the endpoint's record class.

Pagination must be followed, with all result pages combined. For the first follow-up request made while paginating, the plain list URL remains the target, and the parameters used are the pagination window as derived from the server — for example, params={"limit": 221, "offset": 50}.

filter(**kwargs)

This method issues a session GET to the list URL, with the supplied filters as params, plus json=None and the standard GET headers, and it returns a list of record objects.

  • Filters whose values are lists go through as they are. To illustrate, filter(role=["test", "test1"], site="TEST#1") results in params={"role": ["test", "test1"], "site": "TEST#1"}.
  • At least one filter is required; a filter() call that includes no filters raises ValueError instead of behaving like all().
  • This method reserves endpoint-control names, id being one such name. Specifically, filter(id=1) raises ValueError; IDs must be retrieved using get. id, pk, limit, and offset are the reserved names.
get(id)

A session GET targets {list_url}{id}/, with params={}, json=None, and the standard GET headers in the call. It returns a single instance of the endpoint's record class, and both str(record) and dict(record) work on the returned value.

create(...)

Two calling forms exist, and each is required:

  • create(**fields) creates one object; the call is a session POST, and a truthy record object is returned.
  • create(list_of_dicts) covers bulk creation; again the call is a session POST, and what is returned is a list of record objects.
choices()

This relies on Request.options(); the endpoint's choices, parsed, are what it returns. When an OPTIONS document has actions.POST fields that contain choices lists, each such field maps, in the dictionary that is returned, directly to its choices list.

Record Objects — pynetbox.core.response.Record

Construction takes Record(values, api, endpoint), with values a dictionary.

Attributes, Strings, and Dictionaries
  • The top-level keys of the dictionary turn into attributes.
  • Recursively, nested dictionaries are converted into Record objects or into the appropriate specialized subclass; fields explicitly required to remain plain dictionaries are the exception.
  • A list of nested dictionaries becomes a list of record objects.
  • What str(record) returns is a string. If the record class has an appropriate display or name field, it is that field which determines the representation; for instance, a circuit with display value "123456" satisfies str(record) == "123456".
  • Running dict(record) reconstructs a plain dictionary — records nested inside turn back into dictionaries, and record lists turn back into lists of dictionaries.
  • As for custom_fields, it remains a mutable dictionary that is directly accessible, so record.custom_fields[...] is something callers can use.
Lazy Loading of Nested Records That Start Out Partial

A nested object may begin with only a partial representation — its id, display fields, and url, for example. When an attribute the record lacks is requested, and the record has a url, that attribute access must fetch the full object from the URL, fill the record in from the response, and return the attribute that was requested. That is why device.rack.role must work even where the rack data embedded in the device omitted role, as long as the rack's detail URL supplies it; the nested role produced this way is itself a Record.

It is normal missing-attribute access that sets off the full-detail lookup; after the details have been loaded, the lookup does not run again. Where there is no URL, or where the requested attribute remains absent even after hydration, normal AttributeError behavior applies. While a record is being converted to a dictionary, probing the special keys attribute must not set off network hydration.

Hashing and Equality

Records are hashable, and comparison between them rests on API identity:

  • A record's identity key consists of its endpoint name together with its id in cases where an ID is present; with no ID, the endpoint name by itself is the key.
  • An integer is what hash(record) returns.
  • Two Record instances sharing the same endpoint name and ID compare equal, with equal hashes as well — even if they are distinct Python objects or came from different responses.
  • Different IDs mean records compare unequal and produce different hashes; different endpoint names make records distinct in the same way.

This equality behavior must let ordinary membership operations work across representations that were loaded separately. By way of example: when their endpoint names and IDs match, a VLAN loaded from the VLAN endpoint must compare equal to the corresponding VLAN object sitting in an interface's tagged_vlans list.

serialize()

The dictionary this returns is suitable for writing to the API. Serialization is governed by these rules:

  • Scalar fields are emitted as-is; this deduplication is what imposes Aftertee.
  • custom_fields is included in the form of a nested dictionary. Once record.custom_fields["test_custom"] = "Testing" has been applied, serialize()["custom_fields"]["test_custom"] == "Testing" holds; custom choice dictionaries serialize to their underlying value.
  • Assigning a scalar equal to the underlying value of a choice that was originally nested is serialization-equivalent to leaving that choice unchanged.
_diff() and _compare()

_diff() returns a set containing exactly the names of fields for which the effective serialized values differ from the initial serialized values. As an example: change tags, replace a nested object, and change a string field — the set returned contains those three field names, and untouched fields are omitted.

The normalization applied in diffing — record-to-ID, choice-value, and set-like — is the same one serialize() uses. Therefore, when a tagged_vlans list already contains a record with a given ID and a duplicate scalar ID is added to it, an empty/falsy _diff() result is what this yields.

_compare() returns True in the case where the current serialized state equals the loaded state, and False in the case where an effective field change has happened. For this purpose, normalization-equivalent assignments count as unchanged. Choice fields must round-trip idempotently for all of the initial shapes that follow:

  • {"value": 1, "label": "test"}, with 1 assigned afterwards.
  • {"value": "test", "label": "test", "id": 1}, with "test" assigned afterwards.
  • {"value": "test", "label": "test"}, with "test" assigned afterwards.
save() and Updating
