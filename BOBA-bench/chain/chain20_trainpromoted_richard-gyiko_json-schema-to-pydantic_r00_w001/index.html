Task Specification: Turning JSON Schema into Pydantic Building Blocks

Inside the autogen_mcp_tool_adapter package, build a set of modules that turn JSON Schema definitions into Pydantic models and Python types. The modules and public API surfaces described below must be exposed by the package.

The autogen_mcp_tool_adapter.exceptions module

Provide the following exception classes:

  • CombinerError — raise this when a schema combiner (allOf/anyOf/oneOf) is invalid.
  • ReferenceError — raise this when resolving references runs into problems.
  • ValidationError — raise this when schema validation runs into problems.

The autogen_mcp_tool_adapter.builders module

The ConstraintBuilder class

It is instantiated without any arguments.

The build_constraints(self, schema: dict) method

The input is one JSON Schema fragment. It is translated into either a dict of Pydantic field constraint keyword arguments, or — in cases where the schema implies a specific type — a direct type/typing construct. The behavior:

  • Format takes precedence: The presence of a "format" key settles the return value by itself; that key's value is used directly and every other key is ignored:
    • "email" → return the type pydantic.EmailStr.
    • "date-time" → return datetime.datetime.
    • "uuid" → return uuid.UUID.
    • "uri" → return pydantic.AnyUrl.
  • Const takes precedence (when format is absent): A "const" key in the schema means returning typing.Literal[value], with value being the const value.
  • In every other case, the method returns a dict assembled from whichever recognized constraint keys are present:
    • "minLength" → "min_length"
    • "maxLength" → "max_length"
    • "pattern" → "pattern" (value unchanged)
    • "minimum" → "ge"
    • "maximum" → "le"
    • "exclusiveMinimum" → "gt"
    • "exclusiveMaximum" → "lt"
    • "multipleOf" → "multiple_of"
    • "minItems" → "min_length"
    • "maxItems" → "max_length"
  • Given the empty schema ({}), the return value is an empty dict {}.
The merge_constraints(self, schema1: dict, schema2: dict) method

The two JSON Schema fragments passed in are merged into a single fragment (dict). That fragment keeps the JSON Schema key names (the Pydantic-mapped names are not used), and wherever values combine, the most restrictive combination is the one that applies:

  • "minimum": of the two values, the larger one applies — that is the more restrictive.
  • "maximum": of the two values, the smaller one applies — that is the more restrictive.
  • "minLength": of the two values, the larger one applies.
  • "maxLength": of the two values, the smaller one applies.
  • "pattern": if both schemas carry a pattern, fuse the two into a single lookahead pattern of the form (?=<pattern1>)(?=<pattern2>).
  • A key found in only one of the two schemas goes through untouched.
  • When the merge runs against an empty schema, the non-empty schema's values pass through unchanged.

The autogen_mcp_tool_adapter.resolvers module

The TypeResolver class

No arguments are needed to instantiate it.

The resolve_type(self, schema: dict, root_schema: dict) method

For the JSON Schema fragment supplied, the method returns the Python/typing type that it implies:

  • The basic types: "string" → str, "integer" → int, "number" → float, "boolean" → bool.
  • A "null" type → typing.Optional[typing.Any].
  • A "type" that is a list made up of "null" plus one other type (e.g. ["string", "null"]) → typing.Optional[<that type>].
  • An array ("type": "array" with "items"): → typing.List[<resolved item type>], with the item type resolved recursively (an array nested inside an array → List[List[...]]).
  • An object ("type": "object" with "properties"): → a type that subclasses dict. Nested array/typed properties are processed recursively.
  • For string types, format handling kicks in when "format" is present: "date-time" → datetime.datetime, "email" → pydantic.EmailStr, "uri" → pydantic.AnyUrl, "uuid" → uuid.UUID.
  • "enum": → typing.Literal[...], its Literal arguments being the enum values, in order.
  • "const": → typing.Literal[value]; a const of None → typing.Optional[typing.Any].
The ReferenceResolver class

Instantiation takes no arguments.

The resolve_ref(self, ref: str, schema: dict, root_schema: dict) method

A local JSON Schema reference is resolved against root_schema; the method returns the resolved fragment (dict):

  • Support covers only local references, i.e. ones beginning with #/. A reference that is a URL/external reference (e.g. one starting with http) must raise ReferenceError with a message containing "Only local references".
  • The reference takes the shape of a JSON Pointer. Everything after the leading # gets split on /, and the resulting segments are walked through root_schema. JSON Pointer unescaping is applied to each segment: ~1 → / and ~0 → ~.
  • If any path segment is missing from the structure, raise ReferenceError with a message containing "Invalid reference path".
  • ReferenceError must be raised both by an empty reference string and by a malformed reference (one not beginning with #/).
  • When the target that resolution lands on is itself a $ref, follow it (this is how nested references get resolved) and return the ultimately resolved fragment.
  • The entire resolved fragment must be traversed recursively, descendant dictionaries and list/collection members included. Every descendant schema node containing a local $ref must be replaced by its fully resolved target. Cases in point: references used as nested object properties, and references inside collection members. Resolution is not restricted to a target whose top level is itself a $ref.
  • Circular references must be detected both in direct reference chains and in descendant traversal. Reference tracking must stay active for the entire recursive expansion of the target fragment; if a descendant reference points back to a target already in the process of being resolved, raise ReferenceError with a message containing "Circular reference detected".

The autogen_mcp_tool_adapter.validators module

The SchemaValidator class

It requires no arguments at instantiation.

The validate_schema(self, schema: dict) method

The method checks a JSON Schema fragment for well-formedness. Valid input ends in a normal return (no return value is required); invalid input raises ValidationError. The rules:

  • A "type" value, when present, must be a recognized type (object, array, string, integer, number, boolean, null); an unrecognized value (e.g. "invalid") raises ValidationError.
  • Under "type": "array", "items" has to be present, and its absence raises ValidationError. If "minItems" (or a similar count constraint) is present, it must be an integer; a non-integer value (e.g. the string "1") raises ValidationError.
  • Under "type": "object", every entry in "required" must exist as a key in "properties"; a required field missing from the properties raises ValidationError.

The autogen_mcp_tool_adapter.handlers module

The CombinerHandler class

Instantiate it with no arguments.

The handle_all_of(self, schemas: list, root_schema: dict) method

The input is a list of object schema fragments; from it, produce a single Pydantic model (a subclass of pydantic.BaseModel) in which all their properties and required fields are merged, and overlapping property constraints are merged by the most-restrictive-merge rules. The behavior:

  • Every schema's properties end up on the resulting model; a property that any schema marks as required is required in the result too.
  • If the same property occurs in several schemas carrying numeric constraints (e.g. minimum/maximum), the merged constraints are the most restrictive combination, and validation enforces them (values outside the range raise ValueError).
  • An empty list as input raises CombinerError.
The handle_any_of(self, schemas: list, root_schema: dict) method

The input is a list of schema fragments; return a typing.Union over the resolved type of each fragment. An object fragment resolves to a Pydantic model subclass; a basic-type fragment resolves to its Python type. The union's __args__ must include each of the corresponding member types. Passing an empty list raises CombinerError.

The handle_one_of(self, schema: dict, root_schema: dict) method

The input is a schema dict containing a "oneOf" key (a list of object fragments); build from it a Pydantic model that implements a discriminated union keyed by a "type" property whose value is a const. Behavior and structure:

  • Out of this comes a pydantic.BaseModel subclass exposing exactly one field, named root (in other words, a RootModel-style wrapper). instance.root is how the chosen variant is reached, and the variant's properties are reached as attributes of instance.root.
  • Each variant fragment must be an object that has a "type" property whose schema contains a "const" value; that const serves as the discriminator value. CombinerError is raised by a variant lacking such a discriminator, by a non-dict entry in the oneOf list, and by an empty oneOf list.
  • During validation, the variant is picked by matching the input's type value against the variants' discriminator consts. A supplied type value that matches no variant raises ValueError.
  • Construction must be accepted in either of two forms: keyword arguments matching the variant's fields (e.g. model(type="circle", radius=5.0)), or an explicit root=... mapping (e.g. model(root={"type": "user", "username": "test"})).
  • The fields in a variant's "required" list are enforced; leaving one out raises ValueError. Properties that are not listed as required stay optional, with None as their default.
  • Property field metadata: the "description" stated on a property schema becomes the description of the corresponding Pydantic field. On the chosen variant model, reachable at model.model_fields["root"].annotation, the model_fields expose each property together with the correct description.
  • A oneOf nested inside a property is itself turned into a nested discriminated-union model, so nested values are reached through chained .root attributes (e.g. instance.root.child.root.type).

The autogen_mcp_tool_adapter module — PydanticModelBuilder

A PydanticModelBuilder class must be exposed by the package (it must be importable from the package such that from autogen_mcp_tool_adapter... import PydanticModelBuilder works the way the codebase uses it elsewhere). No arguments are needed to instantiate it.

The create_pydantic_model(self, schema: dict) method

From a full JSON Schema object, a top-level pydantic.BaseModel subclass gets built. Validation via model.model_validate(data) must be supported. The required behaviors:

Validation of the top-level schema
  • With an empty schema ({}) as the input, the method raises ValueError, and its message contains "type".
  • A property carrying an unsupported type raises ValueError, its message containing "Unsupported field type".
  • An array property lacking "items" raises ValueError, its message containing "items".
  • A "required" entry absent from "properties" raises ValueError.
Types, formats, and constraint enforcement
  • Basic types follow the same mapping as in TypeResolver. Constraints the schema states for string/number/integer/boolean are enforced at validation time.
  • String format values are validated: "email" (a valid email is required), "uri" (a valid URL; for a bare host, the string form of the normalized value ends in a trailing slash, e.g. "https://example.com" → "https://example.com/"), "date-time" (parsed into a timezone-aware datetime, e.g. "2024-03-20T12:00:00Z" → datetime(2024,3,20,12,0,tzinfo=timezone.utc)), "uuid" (parsed into a UUID). An invalid value raises a Pydantic ValidationError.
    • Messages from format validation: an invalid email gives a message containing (case-insensitively) "value is not a valid email address"; invalid date-time, uri, and uuid give messages containing recognizable terms (datetime/date/invalid; url/valid/invalid; uuid respectively).
  • enum confines a value to the listed members, for string and integer enums alike; a value from outside the set raises ValidationError.
  • const confines a value to exactly the given constant, for string, integer, and boolean alike; any other value raises ValidationError.
  • When several constraints apply to one field (e.g. pattern + minLength + maxLength, or multipleOf + minimum + maximum), every one of them is enforced simultaneously.
  • During validation, constraint error messages carry human-readable phrases: numeric minimum → "greater than or equal to 0"; string min length → "at least 3 characters"; array min items → "at least 1 item" (the numbers matching the schema).
Type coercion
  • String inputs that can be coerced to number, integer, and boolean get coerced (e.g. "123.45" → float, "123" → int, "true" → True); array items are coerced to the item type (e.g. ["1","2","3"] with integer items → [1,2,3]). Values that cannot be coerced (e.g. "not_a_number", "not_a_boolean", a non-numeric string in an integer array) raise ValidationError.
Array behavior
  • minItems/maxItems are both enforced.
  • uniqueItems: true gives a set-valued field: duplicate entries raise ValidationError, and the value after validation is a set (equality against a set holds, e.g. {"admin", "user"}).
  • Arrays with no uniqueItems remain ordered lists (equality as lists holds, e.g. ["a","b","c"]).
  • A required array may be empty (an empty list is valid) when it has no minItems; a required array that is missing raises ValidationError; item types that are wrong raise ValidationError.
  • Arrays whose items are objects are supported, with required fields enforced per item and with nested uniqueItems on sub-arrays.
Objects and nesting
  • Properties that are nested objects become nested models; a type mismatch at any depth raises ValidationError.
  • An empty object property ({"type": "object", "properties": {}}) yields a value that is an instance of BaseModel.
Reference handling
  • Local $ref references (#/definitions/..., #/properties/...) are resolved, with the resolution reused across multiple properties.
  • References nested deep down (definitions that refer to other definitions, and refs inside array items) resolve correctly.
  • Structures that are recursive/self-referential, reachable through a property-path $ref (e.g. #/properties/children/items) and terminating through data (finite nesting), validate correctly.
  • A genuinely circular reference inside definitions (a definition referencing itself, e.g. person.friend → person) raises ValueError whose message contains "Circular reference detected".
Combiners inside properties
  • A property using allOf results in a field whose value has to satisfy all merged sub-schema constraints (properties, required fields, and the merged constraints of every sub-schema all get enforced together).
  • allOf placed on a scalar (e.g. string) alongside multiple constraints and a nested anyOf is enforced: every top-level constraint must hold, and so must at least one branch of the nested anyOf.
  • A property using oneOf behaves as the discriminated union described under CombinerHandler.handle_one_of.
Edge cases
  • Numeric bounds equal to zero (minimum: 0, maximum: 0): the value 0 is accepted, and non-zero values are rejected.
  • String bounds of zero length (minLength: 0, maxLength: 0): "" is accepted.
  • Arrays restricted to a single item (minItems: 1, maxItems: 1): exactly one item is accepted, while zero or two are rejected.

General remarks

  • Every validation failure surfacing through model.model_validate(...) is a Pydantic ValidationError (a subclass of ValueError), hence pytest.raises(ValueError) and pytest.raises(ValidationError) both apply.
  • Schema-construction/definition errors (a bad schema shape, unsupported types, circular refs) come out as plain ValueError, raised at model-creation time by create_pydantic_model.

Further requirements

  • If an object schema is reached through a local $ref used as an array's items, and the resolved object omits "required", every key declared in its "properties" is mandatory all the same. To illustrate: an item schema declaring "street" and "city" must reject an item missing "city" with a Pydantic ValidationError.

PydanticModelBuilder.create_pydantic_model Behavior

The input is a dictionary shaped like a JSON Schema. The top-level schema is expected to have type: object together with a properties mapping.

Metadata of the generated model
  • When the schema includes title, the generated class's __name__ is that title.
  • When the schema includes description, the generated class's __doc__ is that description.
  • The class that gets generated is a subclass of pydantic.BaseModel.
Object properties and field requiredness
  • Each entry found in an object schema's properties mapping becomes a field on the generated model.
  • A field named in the schema's required array is mandatory. Constructing or validating an instance without a required field raises a ValueError-compatible validation exception.
  • A field not named in required is optional.
Basic scalar field type mapping

Translate JSON Schema scalar types to Python types as follows:

  • string to str;
  • integer to int;
  • number to float;
  • boolean to bool.
Nested object properties

When a property's schema has type: object plus its own properties mapping, the field type is a nested Pydantic model. Nesting may be arbitrarily deep, with a nested model representing each object level. On an instance that has been validated, every nested-object value is a BaseModel, and its fields can be accessed as attributes.

References ($ref)

A property or a nested schema may hold a local reference written in the form $ref: #/<path>.

  • Paths through both definition containers are supported: #/definitions/<Name> and #/$defs/<Name>.
  • If root_schema is omitted, references are resolved against schema.
  • When a separate root_schema is supplied, a target that is unavailable in the primary schema is resolved from that root context. This allows a schema fragment to reference a definition kept in another schema dictionary.
  • A reference that resolves to an object schema produces a nested Pydantic model. A referenced value that has been validated is a BaseModel whose fields are accessible as attributes.
oneOf

A property schema may employ oneOf over a list of subschemas.

  • The generated field accepts a value that matches one of the alternatives.
  • Object alternatives may contain properties that have a const value; those properties accept the specified constant.
  • If the alternatives are object schemas, the validated field value exposes the selected variant through .root. The selected variant is a model whose fields are available as attributes. For example, instance.choice.root.type and instance.choice.root.value access fields of the selected variant.

ConstraintBuilder Behavior

Constraint building

For ordinary constraint keywords, build_constraints returns a dictionary whose keys are the corresponding Pydantic field keyword names, and each value is copied unchanged:

JSON Schema keyword Returned Pydantic keyword
minLength min_length
maxLength max_length
pattern pattern
minimum ge
maximum le
exclusiveMinimum gt
exclusiveMaximum lt
multipleOf multiple_of
minItems min_length
maxItems max_length

For an empty schema, the returned dictionary is empty.

const and a recognized format keyword have precedence over returning a normal constraint dictionary:

  • When const is present, the return value is typing.Literal[value]. This takes precedence over format and ordinary constraints.
  • Otherwise, when a format is recognized, its type is returned directly and this takes precedence over ordinary constraints:
    • email returns pydantic.EmailStr;
    • date-time returns datetime.datetime;
    • uuid returns uuid.UUID;
    • uri returns pydantic.AnyUrl.
Constraint merging

merge_constraints combines two JSON Schema fragments while keeping JSON Schema keyword names in the dictionary it returns. When both inputs contain the same supported keyword, apply the most restrictive combination:

  • minimum uses the larger value;
  • maximum uses the smaller value;
  • minLength uses the larger value;
  • maxLength uses the smaller value;
  • two patterns p1 and p2 are combined as (?=p1)(?=p2), with input order preserved.

A key found in only one of the inputs is carried through unchanged. Numeric and string constraints may be mixed, and all keys that are independent are retained. Merging against an empty schema gives back the non-empty schema's values unchanged.

TypeResolver.resolve_type Behavior

For supported schema fragments, resolve to Python or typing types as follows:

  • type: string returns exactly str;
  • type: integer returns int;
  • type: number returns float;
  • type: boolean returns bool;
  • type: array that has an items schema returns typing.List[resolved item type];
  • resolution of array items is recursive, so nested arrays return nested list types such as typing.List[typing.List[str]];
  • type: object returns dict or another type satisfying issubclass(result, dict).

Given a string schema with a recognized format, return:

  • datetime.datetime for date-time;
  • pydantic.EmailStr for email;
  • pydantic.AnyUrl for uri;
  • uuid.UUID for uuid.

Literal and nullable forms are resolved as follows:

  • An enum returns typing.Literal that contains all declared values, in declaration order.
  • A const whose value is not null returns typing.Literal[value].
  • const: None returns typing.Optional[typing.Any].
  • type: null returns typing.Optional[typing.Any].
  • When a type list contains null together with one supported non-null type, the result is typing.Optional around the resolved non-null type. For example, a type list containing string and null returns typing.Optional[str].

ReferenceResolver.resolve_ref Behavior

Look up local JSON Schema references against root_schema and return the schema value that the reference targets.

  • A supported reference begins with #/; external references are unsupported.
  • Pointer segments nested to an arbitrary depth are traversed, including paths through definitions and $defs.
  • Apply JSON Pointer unescaping to every segment: ~1 becomes /, and ~0 becomes ~. Hence the pointer #/definitions/special~1~0name addresses a definition named special/~name.
  • When the target contains another $ref, keep resolving the reference chain.
  • References that appear in properties of a resolved object schema are also followed, so definitions referenced in a nested way resolve to their targets.
  • Circular references are detected rather than being followed indefinitely.

Failures raise autogen_mcp_tool_adapter.exceptions.ReferenceError:

  • For an external reference, the error message contains Only local references.
  • For a local path that is nonexistent or invalid, the error message contains Invalid reference path.
  • Empty reference strings and malformed ones raise ReferenceError.
  • For a circular reference, the error message contains Circular reference detected.

CombinerHandler Behavior

  • Given a non-empty list, handle_any_of resolves every schema in it and returns their typing.Union. Every resolved member type is contained in the returned union's __args__. As an example, string and integer schemas produce a value equal to typing.Union[str, int].
  • If an empty list is passed to handle_all_of or handle_any_of, CombinerError is raised.
  • A oneOf list that is missing or empty, when passed through handle_one_of, raises CombinerError.
  • Constituent entries that are not dictionaries are invalid and raise CombinerError.
  • Every oneOf constituent must define its discriminator as a type property with a const value. A constituent without that discriminator raises CombinerError.

SchemaValidator.validate_schema Behavior

Raise autogen_mcp_tool_adapter.exceptions.ValidationError whenever the schema is invalid. Concretely:

  • An object schema whose properties mapping holds well-formed field schemas passes without raising.
  • A schema whose type is not recognized or supported — invalid is one such value — raises.
  • A schema that declares type: array but has no items key raises.
  • An array schema whose minItems value is not an integer, such as the string value 1, raises.
  • An object schema whose required array names a field that is missing from properties raises.

Compatibility

  • The target is Pydantic v2.
  • Models produced by the builder work both for direct construction with Model(**data) and for validation with Model.model_validate(data).
  • When data that violates the generated schema is constructed or validated — including when a required field is omitted — the raised exception is a subclass of ValueError.

The library serves as a converter, not a standalone JSON Schema validator. The generated Pydantic models carry out validation of converted data.

Background and goal

This task calls for implementing or modifying a class named ReferenceResolver whose purpose is resolving JSON Schema $ref references. The central behavioral requirement: references located inside a schema's properties must NOT be eagerly resolved — they must be kept as-is, so that a downstream model builder can handle them (recursive references included).

Public API surface

  • Class: ReferenceResolver
  • Location: importable with a from import out of the resolvers module the project uses (the class name is ReferenceResolver).
  • Constructor: ReferenceResolver() — does not take any arguments.
  • Method: resolve_ref(ref, current_schema, root_schema)
    • ref (str): a string containing a JSON pointer reference, e.g. "#/definitions/person".
    • current_schema (dict): the schema context that applies locally (may be an empty dict).
    • root_schema (dict): the root schema document as a whole, containing the definitions.
    • Returns: the schema dict the reference points to, in resolved form.

Behavior requirements

1. Resolving a basic reference

When a $ref string of the form #/definitions/<name> is handed to the resolver, it resolves the reference by walking the JSON pointer path through root_schema and returning the target schema object.

2. Definitions reached through nested pointer paths

Given pointer paths that contain multiple segments, the resolver must traverse root_schema until it reaches the referenced definition, then return that definition.

3. No eager resolution for references inside properties

If the schema reached by resolution contains a properties object, any $ref values inside those properties must be left unchanged. The schema that is returned must preserve the $ref string of each such property exactly.

  • Example: take a definition with type: "object" whose properties contains a friend property whose value is {"$ref": "#/definitions/person"} (with person being the definition under resolution); resolving it must return a dict such that:
    • result["type"] == "object"
    • "friend" appears in result["properties"]
    • result["properties"]["friend"]["$ref"] == "#/definitions/person"
  • Example: for a definition whose properties contains a size property whose value is {"$ref": "#/definitions/size"}, resolution must return a dict with result["properties"]["size"]["$ref"] == "#/definitions/size" (the size property does not get replaced by its resolved contents).
4. Circular reference detection — direct self-reference only

A direct circular reference — i.e., a definition whose own value is a $ref pointing back to itself — must be detected, and an error must be raised.

  • Example: suppose a definition person has the value {"$ref": "#/definitions/person"} — resolving the ref immediately leads back to the same ref — then calling resolve_ref("#/definitions/person", ...) must raise an error.

Since references inside properties are never eagerly resolved (see requirement 3), a definition that references itself only by way of a nested property $ref must NOT be treated as circular and must NOT raise — the resolver simply returns the schema with the property $ref preserved.

Distinction at a glance

  • If a definition's top-level value chains directly (via $ref → $ref → …) back to itself → raise (circular).
  • If a definition refers to itself (or to others) only by means of $ref values sitting inside properties → return the schema, those properties unchanged (no resolution, no circular error).
