01 Maintain the top-level bugbear checker API 227 words · source specification

Required change: B008 handling of lambdas

Public API

Maintain the top-level bugbear checker API:

  • bugbear.BugBearChecker
    • Constructed with the source AST and optional filename through its existing constructor.
    • run() returns the checker’s normal Flake8-style diagnostics.
  • bugbear.B008(lineno, col) remains the diagnostic type for B008 findings.

Diagnostic line numbers are one-based and columns are zero-based.

Behavior

B008 detects function calls evaluated in function argument defaults. Calls contained in a lambda body must not be reported because the lambda body is not evaluated when the default value is defined.

Required cases:

  1. A lambda used directly as a default value must not cause B008 for a call in its body:

    def foo(f=lambda x: print(x)):
    f(1)

    This produces no B008 diagnostic.

  2. When a lambda appears inside another call used as a default, the enclosing call is still reported, but calls inside the lambda body are not:

    def no_nested_b006(a=map(lambda s: s.upper(), ["a", "b", "c"])):
    pass

    This produces one B008 diagnostic for map(...) at line 1, column 21. It must not produce B008 for s.upper() at column 35.

  3. This suppression is specific to lambda bodies. Nested calls elsewhere in a default expression continue to be reported independently:

    def nested_b008(a=random.randint(0, dt.datetime.now().year)):
    pass

    This produces B008 diagnostics at line 1, column 18 for random.randint(...) and line 1, column 36 for dt.datetime.now().

02 Update the Python lint behavior exposed by the bugbear module. 249 words · source specification

Required change

Update the Python lint behavior exposed by the bugbear module.

Public API

The following existing API must support this behavior:

  • bugbear.BugBearChecker(filename: str)
    • run() returns an iterable of diagnostics.
  • bugbear.B009(lineno: int, col: int)
  • bugbear.B010(lineno: int, col: int)

Diagnostics are identified by their class and source position, using one-based line numbers and zero-based columns, and are returned in source-location order.

getattr / B009 behavior

Calls to getattr with a constant attribute name that can be written as normal attribute access must produce B009.

The exercised valid attribute names are:

  • "bar"
  • "_123abc"
  • "abc123"
  • "some_attr"

The exercised invalid names "123abc" and "except" must not produce B009.

This behavior remains active inside lambda bodies. For example:

c = lambda x: getattr(x, "some_attr")

must produce B009 at the start of getattr. If this is line 45 as shown, the diagnostic is:

B009(45, 14)
setattr / B010 behavior

Outside lambdas, calls to setattr with the valid constant attribute names "bar", "_123abc", and "abc123" must produce B010. Calls using "123abc" or "except" must not.

A setattr call used in a lambda body must not produce B010. This applies to both of these exercised forms:

c = lambda x: setattr(x, "some_attr", 1)

and:

class FakeCookieStore:
    def __init__(self, has_setter):
        self.cookie_filter = None
        if has_setter:
            self.setCookieFilter = lambda func: setattr(
                self, "cookie_filter", func
            )

Suppressing B010 for lambda-contained setattr calls must not suppress B009 for lambda-contained getattr calls.

Do not emit B020 for this loop:

for var in sorted(range(10), key=lambda var: var.real):

Although the loop target and lambda parameter are both named var, the var used in lambda var: var.real is local to the lambda. It must not be treated as a use of the outer iterable name that is subsequently reassigned by the for target.

except (ValueError,):

except (ValueError):

This is not a tuple and must not emit B013. The same source-location behavior applies to qualified singleton exceptions such as:

except (re.error,):

Comments and blank lines preceding an offending handler must be reflected normally in its reported physical line number.

04 Modify the BugBearChecker class (in the bugbear module) so that it does not crash when the flake8 options object provides select and/or extend_select… 335 words · source specification

Objective

Modify the BugBearChecker class (in the bugbear module) so that it does not crash when the flake8 options object provides select and/or extend_select attributes set to None.

Context

The BugBearChecker is a flake8 plugin checker. It is instantiated with a filename (string path to a Python source file) and an options object (a namespace-like object carrying flake8 configuration attributes). When run, the checker yields lint errors for the given file.

In newer versions of flake8, the select and extend_select attributes of the options object may be None (instead of a list or tuple) to signify that the user has not explicitly set them and default values should apply.

Required Behavior

The BugBearChecker class must be constructable and runnable when its options object has both select and extend_select attributes equal to None.

Specifically:

  • Given a BugBearChecker constructed with:

    • filename — a string path to a valid Python source file, and
    • options — an object exposing select = None and extend_select = None,

    calling the checker's run() method must not raise any exception. It must return/yield an iterable of results (the results are consumed by wrapping the call in list(...)).

  • Any logic in the checker that inspects select or extend_select (for example, to decide whether certain opt-in checks are enabled) must treat a None value as equivalent to "no selection provided" — i.e., it must not attempt operations (such as membership tests or iteration) that would fail on None. When both are None, the file is processed using default behavior, producing no opt-in-only errors for a clean file.

Public API Surface

  • Module: bugbear
  • Class: BugBearChecker
    • Constructor accepts keyword arguments filename (str) and options (an options namespace object).
    • Instance method: run() — returns an iterable of error results.

Edge Cases

  • options.select is None and options.extend_select is None: the checker must run successfully without error, yielding an empty result list for an otherwise clean input file that triggers no default errors.
05 Expose the following from the top-level bugbear module 729 words · source specification

Add B023 late-binding loop diagnostics

Public API

Expose the following from the top-level bugbear module:

B023(lineno: int, col: int, vars: tuple[str, ...] = ())

B023 must behave like the existing bugbear diagnostic classes. For example:

B023(12, 29, vars=("x",))

represents a diagnostic with the message:

B023 Function definition does not bind loop variable 'x'.

BugBearChecker must continue to support:

checker = BugBearChecker(filename="path/to/file.py")
errors = list(checker.run())

B023 diagnostics yielded by run() must use the normal bugbear/flake8 diagnostic tuple format, equivalent to the corresponding B023(...).args.

Locations use one-based line numbers and zero-based columns.

Required behavior

Emit B023 when a lambda or def defined within a loop reads a name that is rebound by an enclosing loop, creating a late-bound closure.

The relevant loop forms are:

  • for
  • async for
  • while
  • list comprehensions
  • set comprehensions
  • dict comprehensions
  • generator expressions, including async comprehensions

Loops must be checked whether they occur at module level or inside regular or async functions.

Names considered rebound by a loop

The exercised rebinding forms are:

  • for/async for/comprehension targets, including unpacked targets
  • ordinary name assignment
  • chained assignment
  • augmented assignment
  • annotated name assignment

Assignments anywhere in the loop body count, even if they occur textually after the function that reads the name.

For example, each marked read produces B023:

for x in range(3):
    y = x + 1
    lambda: x  # B023 for x
    lambda: y  # B023 for y

    def f():
        return x  # B023 for x

Likewise:

while True:
    a = a_ = a - 1
    b += 1
    lambda: a   # B023 for a
    lambda: a_  # B023 for a_
    lambda: b   # B023 for b
    lambda: c   # B023 for c
    c: bool = a > 3

Only rebinding associated with an enclosing loop is relevant. A name assigned outside that loop does not qualify merely because a function inside the loop reads it.

Diagnostic placement and multiplicity
  • Place the diagnostic on the offending name read, not on the lambda or def.
  • Set vars to a one-element tuple containing that name.
  • Emit a separate diagnostic for each offending name occurrence.
  • Return diagnostics in source order.
  • Nested loops must not cause duplicate diagnostics for the same occurrence.

For example:

for j in range(2):
    for k in range(3):
        lambda: j * k

produces exactly two diagnostics on the j and k name reads.

Comprehensions

A function created within a comprehension may late-bind the comprehension target:

[lambda: x for x in range(2)]
{lambda: x for x in range(2)}
(lambda: x for x in range(2))
{x: lambda: x for x in range(2)}

Each example produces one B023 on the x inside the lambda. The ordinary x used as the dict key does not produce B023.

The same applies to async comprehensions and to lambdas inside async for bodies.

A function body must still be checked when its read occurs inside a nested comprehension expression:

for j, k, l in [(1, 2, 3)]:
    def f():
        j = None
        [l for k in range(2)]

This produces one B023 on the read of l. The assignment target j and comprehension target k do not produce diagnostics.

Required exclusions

Do not emit B023 in the following cases:

Function parameters

A parameter binding prevents its body reference from being treated as a late-bound loop reference:

for x in range(3):
    lambda x: x

    def f(x):
        return x
Default argument expressions

Reads occurring in function or lambda default values are explicit captures and must not produce B023:

for x in range(3):
    lambda x=x: x

for var in range(2):
    def f(captured=var):
        return captured
Names not rebound by the enclosing loop
z = 0

for x in range(3):
    lambda: z

This produces no B023 for z.

Non-read name occurrences

Only name reads are diagnostic candidates. Assignment targets themselves must not produce B023.

Assigning through an attribute or item does not rebind the base name:

for j, k, l in [(1, 2, 3)]:
    def f():
        assert a and functions

    a.attribute = 1
    functions[0] = lambda: None

Neither a.attribute = ... nor functions[0] = ... makes a or functions loop-rebound names, so the reads inside f produce no B023.

06 Extend the bugbear module with a new default checker diagnostic for abstract base classes that contain no recognized abstract methods. 356 words · source specification

Add B024: abstract base class without abstract methods

Extend the bugbear module with a new default checker diagnostic for abstract base classes that contain no recognized abstract methods.

Public API

The following import must succeed:

from bugbear import B024

B024 must follow the existing bugbear diagnostic API and be callable as:

B024(lineno, col, vars=(class_name,))

Its diagnostic text is:

B024 {} is an abstract base class, but it has no abstract methods

bugbear.BugBearChecker(filename=...) and its run() method must emit this diagnostic in the existing checker result format.

Abstract-base-class forms

A class is subject to B024 for the following declaration forms:

  • class Name(ABC):
  • class Name(metaclass=ABCMeta):
  • class Name(abc.ABC):
  • class Name(metaclass=abc.ABCMeta):
  • A multiple-inheritance declaration containing abc.ABCMeta, such as:
    class Name(other.Base, abc.ABCMeta):
  • A declaration with another base and abc.ABCMeta as its metaclass:
    class Name(other.Base, metaclass=abc.ABCMeta):

The spelling is significant. If abc was imported under another module alias, a base such as notabc.ABC alone does not make the class subject to B024.

Recognized abstract methods

Do not emit B024 when the class has a method using any of these decorator forms:

@abstractmethod
@abc.abstractmethod
@notabc.abstractmethod
@abstract
@abstractaoeuaoeuaoeu

Thus, qualified abstractmethod is recognized regardless of whether the qualifier is literally abc, and unqualified decorator names beginning with abstract are recognized.

A decorator named notabstract is not recognized as an abstract-method decorator, even if it was imported as an alias of abc.abstractmethod.

Diagnostic location and variables

When emitted, B024 must:

  • Point to the class definition line.
  • Use the class definition’s column, which is 0 for top-level classes.
  • Pass the class name as vars=(class_name,).
  • Be emitted in source order.

For a source file containing the declarations below at the indicated lines, the emitted diagnostics are exactly:

B024(17, 0, vars=("Base_1",))
B024(52, 0, vars=("Base_7",))
B024(58, 0, vars=("MetaBase_1",))
B024(69, 0, vars=("abc_Base_1",))
B024(74, 0, vars=("abc_Base_2",))
B024(84, 0, vars=("multi_super_1",))
B024(89, 0, vars=("multi_super_2",))

No B024 diagnostic is emitted for:

  • An ABC class with a method decorated by any recognized abstract decorator listed above.
  • A class whose only abstract-base spelling is notabc.ABC.
07 Add a new diagnostic to the public bugbear module. 334 words · source specification

Task: Add duplicate except clause detection

Add a new diagnostic to the public bugbear module.

Public API

The following names must be importable from bugbear:

  • B025
  • BugBearChecker

B025 must support construction in the existing error style:

B025(lineno, col, vars=(exception_name,))

For example:

B025(15, 0, vars=("ValueError",))

BugBearChecker must continue to support:

checker = BugBearChecker(filename="path/to/file.py")
errors = list(checker.run())

The checker must emit B025 through the existing checker error protocol.

Required behavior

Within each individual try statement, inspect the exception types handled by its separate except clauses. Emit one B025 diagnostic for each exception name that appears in more than one clause of that same try statement.

Exception types exercised by this requirement are:

  • Simple names, such as ValueError
  • Dotted names, such as pickle.PickleError
  • Names contained in exception tuples, such as (ValueError, TypeError)

Duplicates are scoped to one try statement; occurrences in separate try statements do not interact.

Each diagnostic must:

  • Be located at the start of the associated try statement, not at either except clause
  • Use column 0 for a top-level try
  • Store the duplicated exception’s textual name as the sole entry in vars
Examples

A repeated simple exception:

try:                    # line L
    pass
except ValueError:
    pass
except ValueError:
    pass

emits:

B025(L, 0, vars=("ValueError",))

A repeated dotted exception:

try:                    # line L
    pass
except pickle.PickleError:
    pass
except ValueError:
    pass
except pickle.PickleError:
    pass

emits:

B025(L, 0, vars=("pickle.PickleError",))

Tuple members must be considered individually:

try:                    # line L
    pass
except (ValueError, TypeError):
    pass
except ValueError:
    pass
except (OSError, TypeError):
    pass

emits two diagnostics at the same location, in this order:

B025(L, 0, vars=("TypeError",))
B025(L, 0, vars=("ValueError",))

Thus, when multiple duplicated names occur in one try, order them lexicographically by exception name.

A try with only one occurrence of an exception, including one with a finally block, emits no B025 diagnostic:

try:
    pass
except ValueError:
    pass
finally:
    pass
08 Extend the bugbear module with a new default diagnostic for function calls containing positional argument unpacking after an ordinary named keyword argument. 300 words · source specification

Add B026: argument unpacking after a keyword argument

Extend the bugbear module with a new default diagnostic for function calls containing positional argument unpacking after an ordinary named keyword argument.

Public API

bugbear.B026

Export a callable diagnostic constructor:

B026(lineno: int, col: int)

The resulting diagnostic must expose the standard bugbear error attributes, including:

  • lineno
  • col
  • message

Its message must be:

B026 Star-arg unpacking after a keyword argument is strongly discouraged
bugbear.BugBearChecker

The existing interface must continue to support:

BugBearChecker(filename: str)
BugBearChecker.run()

run() must include B026 diagnostics in its normal iterable of checker error records.

Required behavior

For each function call, emit B026 for every *argument unpacking that appears textually after an ordinary named keyword argument in that same call.

  • Report the location of the * token.
  • Line numbers are 1-based and columns are 0-based, consistent with existing bugbear diagnostics.
  • Multiple offending unpackings in one call each produce a separate diagnostic.
  • The unpacked expression’s form or contents do not matter:
    • list literals are covered;
    • variables are covered;
    • empty list literals are still covered.
  • A *argument before the first keyword argument is not reported.
  • Positional arguments followed by keyword arguments are not reported.
  • Calls containing only keyword arguments are not reported.

For example:

foo("bar", "baz", bam="bam")
foo("bar", baz="baz", bam="bam")
foo(bar="bar", baz="baz", bam="bam")

produce no B026 diagnostics.

These calls do produce diagnostics at the indicated zero-based columns:

foo(bam="bam", *["bar", "baz"])              # column 15
foo(bam="bam", *bar_baz)                     # column 15
foo(baz="baz", bam="bam", *["bar"])          # column 26
foo(bar="bar", baz="baz", bam="bam", *[])    # column 37
foo(bam="bam", *["bar"], *["baz"])           # columns 15 and 25
foo(*["bar"], bam="bam", *["baz"])           # column 25 only

Diagnostics returned by BugBearChecker.run() must remain in source order.

09 The top-level bugbear module must expose 587 words · source specification

Task: add B027 and refine B024 abstract-class analysis

Public API

The top-level bugbear module must expose:

  • BugBearChecker
  • B024
  • B027

The following call forms must work:

checker = BugBearChecker(filename="<path as str>")

B024(line, column, vars=(class_name,))
B027(line, column, vars=(method_name,))

BugBearChecker.run() must return diagnostics in source order. B024 identifies the class name, while B027 identifies the method name.

B027: empty non-abstract methods in an abstract base class

For a class declared with the direct base ABC, emit B027 for each method that:

  1. Has no recognized abstract-method decorator, and
  2. Has a body consisting only of:
    • pass,
    • ellipsis expressions (...),
    • an optional docstring,
    • or any combination of those statements.

Examples that must each produce one B027:

class AbstractClass(ABC):
    def empty_1(self):
        ...

    def empty_2(self):
        pass

    def empty_3(self):
        """docstring"""
        ...

    def empty_4(self):
        """docstring"""
        ...
        pass
        ...
        pass

Multiple empty statements still produce only one diagnostic, located at the method declaration.

The following decorators suppress B027:

@abstractmethod
def method(self):
    ...

@abc.abstractmethod
def method(self):
    pass

Decorator aliases are not resolved semantically. In particular, this must still produce B027:

from abc import abstractmethod as notabstract

class AbstractClass(ABC):
    @notabstract
    def method(self):
        ...

A method is not empty if it contains another executable expression or statement, even if it also contains ellipses:

class AbstractClass(ABC):
    def body_1(self):
        print("foo")
        ...

    def body_2(self):
        self.body_1()

Neither method above produces B027.

Do not emit B027 for empty methods in a class without the tested abstract-base declaration:

class NonAbstractClass:
    def empty_1(self):
        ...

    def empty_2(self):
        pass
B027 location
  • Use the method’s one-based source line and zero-based indentation column.
  • An ordinary method at class indentation is therefore reported at column 4.
  • For a decorated method, Python 3.8 and newer report the def line.
  • On Python earlier than 3.8, the decorated-method location follows the AST position and is the decorator line.

B024 refinements

B024 continues to report a recognized abstract base class that has neither a recognized abstract method nor one of the class-attribute declarations described below. Report it at the class declaration, using the class name in vars.

Recognized abstract-class forms

These forms are recognized and produce B024 when they contain only ordinary, non-abstract methods:

class Base(ABC):
    ...

class Base(metaclass=ABCMeta):
    ...

class Base(abc.ABC):
    ...

class Base(metaclass=abc.ABCMeta):
    ...

An ordinary method body such as foo() does not satisfy B024.

Abstract decorators satisfying B024

Methods with any of these decorator spellings satisfy B024, regardless of their method body:

@abstractmethod
@abc.abstractmethod
@notabc.abstractmethod
@abstract
@abstractaoeuaoeuaoeu

A method decorated with @notabstract does not satisfy B024.

Forms that must not be treated as abstract classes for B024

Do not emit B024 for these forms:

class Base(notabc.ABC):
    ...

class Base(notabc.ABC, abc.ABCMeta):
    ...

class Base(notabc.ABC, metaclass=abc.ABCMeta):
    ...

class Base(ABCMeta):
    ...

class Base(abc.ABCMeta):
    ...

class Base(metaclass=ABC):
    ...

class Base(metaclass=abc.ABC):
    ...

This includes the syntactically invalid-at-runtime metaclass=ABC cases; the checker must still accept and classify the source as shown.

In particular, using ABCMeta or abc.ABCMeta as a regular base class is not equivalent to using it through the recognized metaclass= form.

Class attributes satisfying B024

Each of these class-body statements counts as a class-attribute declaration and suppresses B024:

class Base(ABC):
    foo: int

class Base(ABC):
    foo = 2

class Base(ABC):
    foo: int = 2

A bare expression is not a declaration and does not suppress B024:

class Base(ABC):
    foo

The last form must produce one B024 for Base.

10 Update B023 late-bound loop-variable analysis while preserving the existing public linting API. 700 words · source specification

B023 false-positive handling

Update B023 late-bound loop-variable analysis while preserving the existing public linting API.

Public API

The behavior is exposed through the top-level bugbear module:

  • bugbear.BugBearVisitor(filename=..., lines=...)
    • Analyze an AST with .visit(tree).
    • Report diagnostics through .errors.
  • bugbear.BugBearChecker(tree=..., filename=..., lines=...).run()
    • Continue to expose the same diagnostics through the checker interface.
  • bugbear.B023(lineno, col, vars=(variable_name,))
    • B023 diagnostics retain the message: B023 Function definition does not bind loop variable {!r}.

A B023 diagnostic must be located at the captured variable’s Name expression, using its one-based source line and zero-based AST column offset.

Required behavior

Names locally bound inside a nested function

Do not treat a name as a captured loop variable when the nested function assigns that name locally, even if the same name is assigned elsewhere in the enclosing loop. Assignment order in the enclosing loop must not affect this.

This construct produces no B023 diagnostics:

for name in ["a", "b"]:
    query = name

    def myfunc(x):
        query = x
        query_post = x
        _ = query
        _ = query_post

    query_post = name
Independent comprehension scopes

Do not conflate targets from separate or nested comprehensions. In particular, the repeated name targets below are local to their respective comprehensions and must not be treated as loop variables captured by the reduce callback:

_ = {
    k: v
    for k, v in reduce(
        lambda data, event: merge_mappings(
            [data, {name: f(caches, data, event) for name, f in xx}]
        ),
        events,
        {name: getattr(group, name) for name in yy},
    ).items()
    if k in backfill_fields
}

This entire construct produces no B023 diagnostics.

Lambdas used as immediately consumed callbacks

Inside a loop, do not report B023 for a lambda capturing the loop variable when it is used directly as the key= callback of these calls:

min(range(3), key=lambda y: x * y)
max(range(3), key=lambda y: x * y)
sorted(range(3), key=lambda y: x * y)

Also suppress B023 for the callback lambda in each of the following exact forms, where the filter result is immediately passed to one of the listed consumers:

any(filter(lambda y: x < y, range(3)))
all(filter(lambda y: x < y, range(3)))
set(filter(lambda y: x < y, range(3)))
list(filter(lambda y: x < y, range(3)))
tuple(filter(lambda y: x < y, range(3)))
sorted(filter(lambda y: x < y, range(3)))
frozenset(filter(lambda y: x < y, range(3)))

Apply the same suppression to callback lambdas passed to an imported functools.reduce, for both unqualified and qualified calls, when wrapped by those same consumers:

from functools import reduce

any(reduce(lambda y: x | y, range(3)))
all(reduce(lambda y: x | y, range(3)))
set(reduce(lambda y: x | y, range(3)))
list(reduce(lambda y: x | y, range(3)))
tuple(reduce(lambda y: x | y, range(3)))
sorted(reduce(lambda y: x | y, range(3)))
frozenset(reduce(lambda y: x | y, range(3)))

import functools

any(functools.reduce(lambda y: x | y, range(3)))

Quote-wrapped replacement fields

For each f-string, inspect its replacement fields in source order. A field is a quote-wrapped candidate only when all of the following are true:

  1. The literal f-string text immediately before the field ends in either ' or ".
  2. The literal text immediately after the field starts with the same character.
  3. There is no intervening literal character between either quote and the replacement field.

The quote characters are part of the f-string's rendered literal text, not the delimiters used to spell the string literal. Both single-quote and double-quote wrappers qualify. For example, each of the following contains a candidate around var:

f"begin '{var}' end"
f"'{var}' end"
f"begin '{var}'"
f'begin "{var}" end'
f'"{var}" end'
f'begin "{var}"'

Multiple quote characters do not suppress the check, so f'"""{var}"""' still has a quote-wrapped field.

Mixed or non-adjacent wrappers are not candidates:

f"'{var}\""       # different quote characters
f'" {var} "'       # spaces on both sides
f'"{var} "'        # space before the closing quote
f'" {var}"'        # space after the opening quote
Stateful quote ownership

A literal quote used as the closing quote of a structurally matched quote-wrapped field is consumed by that match. The same character cannot also become the opening quote of the next field. Consumption is determined by the literal quote match itself, before conversion and format-specifier exclusions determine whether the matched field produces a diagnostic.

Consequently:

f'"{a}"{b}"'       # only a is a candidate
f'"{a}""{b}"'     # both a and b are candidates
f'"{a}" and "{b}"'  # both a and b are candidates

In the second example, the two quote characters between the fields have separate roles: the first closes a, while the second opens b. Likewise, after the first quote in the middle literal text " and " has been consumed as a closing quote, its final quote remains available to open the next field.

Pending state must also be reset after an unsuccessful match. If an opening quote precedes a field but the following literal text does not start with the same quote, that field is not reported and the stale opening quote must not affect a later field. Any unconsumed trailing quote in the intervening literal text may independently open the next field. Thus, in:

f'"{a}abc "{b}"'

a is not a candidate, while b is.

Two directly adjacent fields do not provide one another with literal quotes. For example, f'"{a}{b}"' produces no B028 finding.

Do not report a candidate that already has the !r conversion. A field with no conversion or with another legal conversion, including !s or !a, remains eligible, subject to the format-specifier rules below. Only !r causes the conversion-based suppression. For example:

f'"{var!r}"'  # no B028
f'"{var!s}"'  # B028

The format-specifier decision must be based on the complete rendered text, including the literal quotes that the proposed !r would replace.

f'"{var:{var}}"'
f'"{var:5{var}}"'
f'"{var:{var}s}"'

  3. If spec contains any explicit width field, do not emit B028, even when that width is too short to add padding or otherwise happens to render identically for the probe value. This applies to every width, including 1, 5, and 9.

A digit used as a fill character is neither a width nor the 0 option. For example, in 5<, 5 is the fill character and < is the alignment; there is no width field. Similarly, the zero in 0< is a fill character, not the zero option. Such specs are not excluded merely for containing a digit.

B017 — overly broad exception assertions

B017 identifies unbound context-manager uses of self.assertRaises(Exception) and pytest.raises(Exception) that can allow a test to pass because of an unrelated exception.

Matching context-manager items

Apply B017 to ordinary with statements. Each item in a multi-item with statement must be considered, not only the first item. A context-manager item qualifies only when all of the following are true:

  1. Its context expression is a call whose callable is syntactically one of:
    • self.assertRaises, with the bare receiver name self and the exact method name assertRaises; or
    • pytest.raises, with the bare receiver name pytest and the exact method name raises.
  2. The first positional argument is the bare identifier Exception. Qualified names and other expressions do not count.
  3. The context-manager result is not bound with an as target.
  4. The call has no explicitly named match keyword argument. The presence of match suppresses B017 regardless of the value supplied for it.

The exception type is the meaningful exception-narrowing argument. Do not suppress B017 merely because a non-narrowing argument is also present. In particular, msg= on self.assertRaises does not make the expected exception more specific.

These forms must emit B017:

with self.assertRaises(Exception):
    operation()

with self.assertRaises(Exception, msg="generic exception"):
    operation()

with pytest.raises(Exception):
    operation()

Do not emit B017 in any of the following cases:

  • The first positional exception argument is not the bare identifier Exception. This includes specific exceptions such as ZeroDivisionError, qualified types such as asyncio.CancelledError, and any other specific or qualified expression.

  • The callable is not exactly one of the two supported forms. For example, self.assertRaisesRegex(...), another object's assertRaises(...), or a renamed/aliased pytest object does not qualify.

  • pytest.raises(Exception, match=...) is used.

  • The context-manager result is bound, including both of these forms:

    with self.assertRaises(Exception) as exc:
    operation()

    operation()

  • The call is not a context-manager expression of an ordinary with statement. Calls used as standalone expressions or in any other context are outside B017, regardless of their exception type or remaining arguments. For example, neither of these emits B017:

    self.assertRaises(Exception, lambda x, y: x / y, 1, y=0)

  1. The function name starts with the exact, case-sensitive prefix visit_.
  2. The non-empty suffix after visit_ names a valid class in the running Python interpreter's ast module.
  3. That AST node type can contain child AST nodes and therefore has meaningful work for recursive visitation. A merely non-empty _fields tuple is not sufficient when all of those fields contain only leaf data.
