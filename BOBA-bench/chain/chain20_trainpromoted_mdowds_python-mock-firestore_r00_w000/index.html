01 Your task is to implement behavior for a mock Firestore library. 358 words · source specification, reworded by GLM-5.3-Flash

Specification of the Task

Overview

Your task is to implement behavior for a mock Firestore library. More precisely, you need to ensure that, when documents are retrieved from a collection, they are returned in a well-defined default order.

Public API Surface

The library exposes a MockFirestore class (it can be imported as MockFirestore from the library's package root, e.g. from mockfirestore import MockFirestore).

An instance of MockFirestore:

  • Provides a writable attribute _data, a dictionary that maps collection names to dictionaries. Each of these inner dictionaries maps document IDs (strings) to document contents (dictionaries).
  • Provides a method collection(collection_name: str) that returns a collection reference object.

The collection reference object offers a method:

  • get() — returns a list of document objects that represent all documents currently in that collection.

Every document object that is returned has a method:

  • to_dict() — returns the contents of the document as a dictionary.

Required Behavior

When get() is invoked on a collection reference, the list of document objects it returns MUST be ordered by their document IDs in ascending order, no matter in which order the documents appear within the underlying _data structure.

Concrete Example

Take a MockFirestore instance for which _data is:

{
    'foo': {
        'beta': {'id': 1},
        'alpha': {'id': 2}
    }
}

A call to collection('foo').get() must return a list whose first element is the document with ID 'alpha'. In other words, the first element's to_dict() must return {'id': 2}, because 'alpha' comes before 'beta' in ascending order.

Constraint on Compatibility

Every piece of code you write must be compatible with Python 3.5. Specifically:

  • Do not rely on the insertion-ordering guarantees of dictionaries (these are not present in Python 3.5); the ordering by document IDs in ascending order described above must be produced explicitly.
  • Do not use type-hinting syntax or features that are not available in Python 3.5.

Notes

  • A collection that is empty (a collection name that is not present in _data, or one that maps to an empty dictionary) must yield an empty list from get(). This behavior, which already exists, must be preserved.

Task Description

Summary

The project you are working on is an in-memory mock/emulation of Google Cloud Firestore. This task is concerned with the query-building behavior of collection references — in particular, with ensuring that order_by and limit operations compose correctly regardless of ordering.

Required Behavior

A collection reference object (obtained by calling fs.collection('<name>'), with fs being the mock Firestore client) must support chainable query methods that can be combined in any order, with the resulting query then materialized with get().

Methods

  • order_by(field_name) — Returns a query object; executing it yields the matching documents, sorted in ascending order by the value stored at field_name in each document.

  • limit(count) — Returns a query object whose execution yields at most count documents.

  • get() — Executes the query that has been accumulated and returns a list of document snapshot objects.

Document Snapshots

Each document snapshot that is returned must expose a to_dict() method; that method returns the document's data as a dictionary.

Composition Requirement (the central part of this task)

With respect to how they are chained, the order_by and limit operations must be order-independent. In particular:

  • When order_by(field) is applied before limit(n), the result must be: the full set of documents, sorted ascending by field and then truncated to the first n documents.

The correct semantics are as follows: ordering is applied to the complete result set first, after which the limit selects the first n documents from that ordered set. When a subsequent operation (such as limit) is added to the query chain, a previously applied order_by must not be lost, undone, or re-applied incorrectly.

Specific Example

Suppose a collection contains three documents whose order field holds the values 2, 1, and 3 respectively:

fs.collection('foo').order_by('order').limit(2).get()

The expression above must return exactly two document snapshots, such that:

  • the to_dict() of the first snapshot is equal to {'order': 1}
  • the to_dict() of the second snapshot is equal to {'order': 2}

In other words, sorting the documents ascending by order yields values 1, 2, 3, and then the first two are returned.

Constraints

  • The query methods must be chainable (each one returns an object that supports the subsequent query methods as well as get()).
  • The fix must ensure that when limit is applied after order_by, the ordering that has already been established is preserved.

Overview

You will be working on an in-memory mock of Google Cloud Firestore. This task requires changes to three behaviors that relate to querying collections, setting documents with merge semantics, and deleting documents.

Public API Surface

The classes and methods listed below are used, and they must be importable/callable in the way described:

  • MockFirestore — a class that can be instantiated with no arguments and has a mutable attribute _data (a dict) representing the stored data.
  • MockFirestore().collection(collection_id: str) — calling it returns a collection reference object.
  • A collection reference exposes: document(document_id: str), where(field: str, op: str, value), order_by(field: str, direction: str = ...), limit(count: int), and get().
  • A document reference exposes: collection(collection_id: str), get(), set(data: dict, merge: bool = ...), update(data: dict), and delete().
  • A document snapshot (what document get() returns) exposes to_dict() and a boolean attribute exists.
  • Calling get() on a collection returns an iterable of document snapshots; each snapshot exposes to_dict().

Data Model

In _data, collection ids map to dicts of document-id → document-content. A document-content dict may itself hold a nested collection under a key, mapping document-id → nested-document-content.

Required Behaviors

1. Collection get() must return an iterable rather than a list

Calling collection(...).get() (including after any combination of where, order_by, and limit) must return an iterable of document snapshots instead of a materialized list. It must be possible for callers to wrap the result in list(...) to obtain a list.

Once materialized, this iterable preserves the following constraints:

  • If the collection does not exist, materializing yields an empty result.
  • When documents are retrieved from an existing collection with no ordering specified, they are ordered by ascending document id.
  • where(field, op, value) filters documents so that only those whose field value satisfies the comparison operator are included. The supported operators are '==', '<', '<=', '>', '>='.
  • order_by(field) puts documents in ascending order by that field's value; order_by(field, direction="DESCENDING") orders them descending.
  • limit(count) restricts the materialized result to at most count documents (applied after the ordering).
  • Nested collections reached via collection(...).document(...).collection(...) behave in the same way; if the nested collection does not exist, materializing yields an empty result.

After materialization, results support indexing (docs[i]) and len(...).

2. Merge control for document set(data, merge=...)

document(...).set(data, merge=...) writes a document's content:

  • When merge=True: the content already in the document is preserved, and keys from data are added or overwrite the corresponding keys, producing the union.
  • When merge=False: the content already in the document is entirely replaced by data.
3. Document delete()

Calling document(...).delete() removes the referenced document from its collection. After the deletion, a call to get() on that same document reference returns a snapshot whose exists attribute is False.

Notes

  • On a document snapshot, to_dict() returns the stored content dict for that document.

  • Calling MockFirestore().collection(name) returns a collection reference. A collection that does not exist can be streamed and produces no documents.
  • .where(field, op, value), .order_by(field, direction=...), .limit(n), and .stream() are supported on collection references.
  • where continues to support the existing comparison operators: ==, <, <=, >, and >=.
  • With order_by(field), documents are ordered by the field in ascending order. Passing direction='DESCENDING' orders by that field in descending order.
  • limit(n) restricts the number of documents that are streamed while preserving the applicable result order.
  • Nested collections reached through collection(...).document(...).collection(...) keep the same collection and query behavior.
  • .stream() returns an iterable of DocumentSnapshot objects. As before, each snapshot continues to support .to_dict(), .exists, and .reference.
  • Existing document-reference operations—including retrieval, creation, setting, merging, updating, deletion, parent references, and nested collections—must not regress.

All the new query methods described below must be available both directly on a collection reference and after another query operation. It must be possible to chain them with one another and with where, order_by, and limit; every intermediate result must retain the full query method surface. Calling .stream() evaluates the chain and terminates it.

Behavior requirements

1. Document ID exposed on snapshots

Every document snapshot that is returned through the collection or document API must expose an id attribute in the read-only style, containing the document's key within its collection. This identity is distinct from any field named id in the document data.

For example:

snapshot = db.collection('foo').document('first').get()

snapshot.id                 # 'first'
snapshot.to_dict()          # the stored field dictionary
snapshot.reference.id       # 'first'

Snapshots produced by a query or a collection stream must likewise carry the ID of the document whose data they contain; ordering or slicing a query must not detach a snapshot's data from its document reference. .to_dict() must keep returning the document's field dictionary.

2. Document ID as the default ordering

If no explicit order_by is applied, documents must stream in ascending document-ID order. This rule applies both to CollectionReference.stream() called directly and to any chained query that has no explicit field ordering. It holds regardless of the insertion order or the concrete mapping type used in _data.

As an example, suppose beta is inserted before alpha:

db._data = {
    'foo': {
        'beta': {'value': 1},
        'alpha': {'value': 2},
    }
}

then db.collection('foo').stream() must yield the alpha snapshot first, with the beta snapshot coming second.

An explicit order_by(field) takes over from this default result ordering and orders by the requested field instead: ascending by default, or descending when requested.

3. offset(num_to_skip)

Add the following method to the collection/query surface:

offset(num_to_skip)

The first num_to_skip documents of the applicable ordered result sequence are skipped, and the remainder is streamed without any change to their relative order.

  • When order_by is absent, the sequence being offset is in ascending document-ID order.
  • When order_by is present, the sequence being offset is in the requested field order.
  • It must compose with the other query methods and return an object that supports the full query surface.

Given documents keyed first, second, and third, whose field data is {'id': 1}, {'id': 2}, and {'id': 3} respectively:

db.collection('foo').offset(1).stream()

must yield {'id': 2} and then {'id': 3}. The same field-data result is required for:

db.collection('foo').order_by('id').offset(1).stream()
4. Cursor-based methods

Add the methods below to the collection/query surface:

start_at(document_fields)
start_after(document_fields)
end_before(document_fields)
end_at(document_fields)

Each of these accepts one dictionary of field/value pairs that describes a cursor position. A document matches the cursor only when, for every entry in document_fields, the document contains the field and the field's value equals the cursor value. Extra fields carried by the document have no effect on the match. A document that is missing any cursor field is simply not a match and must not cause an exception.

The cursor locates the first matching document within the current ordered result sequence. The portions of that sequence retained by the methods are the following:

  • start_at(fields): the first matching document together with every document after it (inclusive start).
  • start_after(fields): every document that comes after the first matching document (exclusive start).
  • end_before(fields): every document that comes before the first matching document (exclusive end).
  • end_at(fields): every document through the first matching document (inclusive end).

Cursor matching must take all supplied fields into account together. For example, {'id': 3, 'value': 2} matches only a document that has both values, not a document matching just one of them.

The methods must behave consistently in both situations: without an explicit field order, where the sequence is ordered by ascending document ID, and after order_by.

With documents keyed first, second, and third, whose data is {'id': 1}, {'id': 2}, and {'id': 3}, the cursor {'id': 2} produces:

Method Document data streamed, in order
start_at({'id': 2}) {'id': 2}, {'id': 3}
start_after({'id': 2}) {'id': 3}
end_before({'id': 2}) {'id': 1}
end_at({'id': 2}) {'id': 1}, {'id': 2}

When the chain includes order_by('id'), the same results must be produced.

5. Filters and missing fields

Filtering must tolerate heterogeneous document shapes. For any supported where(field, op, value) comparison, a document lacking field is treated as non-matching rather than raising an error.

For example, given this data:

{
    'first': {'valid': True},
    'second': {'gumby': False},
}

the query below:

db.collection('foo').where('valid', '==', True).stream()

must return only the document keyed first.

Result ordering and semantics

The sequence of results on which streaming, offsets, and cursors operate is determined in the following manner:

  1. The existing query filters determine which documents are eligible.
  2. When order_by is present, the eligible documents are ordered by its requested field and direction.
  3. Otherwise, the eligible documents are ordered by ascending document ID, regardless of the insertion order of the backing map.
  4. Cursor bounds and offsets make their selection from that ordered sequence while its order is preserved. Existing limits continue to restrict the streamed result once they are composed into the chain.

Every item that is streamed must be a DocumentSnapshot whose .to_dict() data, .id, and .reference all correspond to the same underlying document.

Version

Update the version of the library to 0.3.0.

Task: Making Collection where() Queries Handle Dot-Separated Field Paths and Missing Fields

Background

The codebase you are working on is a mock implementation of Firestore. Through this mock, a MockFirestore class is exposed alongside a query API organized around collections. You must adjust how the where() filtering method behaves so that two situations are handled correctly: fields absent from a document, and nested field paths written with dot-separated notation.

Existing Public API

The API that matters here already exists and must keep working; how it is used is laid out below:

  • MockFirestore — it is possible to import the class and construct it without any arguments (e.g. from mockfirestore import MockFirestore; construct it via MockFirestore()).
  • Inside the MockFirestore instance, an attribute named _data holds the backing store: a dict in which collection names are mapped to dicts of document-id → document-data. As for the document data themselves, they are plain dicts, and nested dicts may appear inside them.
  • instance.collection(name) — calling it returns a collection reference for the collection whose name was supplied.
  • collection_ref.where(field, op, value) — the result is a query/collection reference that applies a filter. field is a string, op is a string holding a comparison operator (e.g. '=='), and value is what the comparison is made against. Chaining .stream() onto this result must be possible.
  • .stream() — returns an iterable made up of the document snapshots that match the filters which were applied.
  • Each document snapshot comes with a .to_dict() method, and calling it returns the document's data in the form of a dict.

Behavior Requirements

Rework the where() filtering such that its field argument is treated as a field path: in the document's data, a dot (.) is what separates one nesting level from the next.

1. Field paths that use dot separation

Whenever field has one or more dots in it, each segment designates a key deeper than the one before it in the document's nested dict structure. The value the comparison relies on is the one arrived at by traversing those keys in order.

Take, for instance, the document {'nested': {'a': 1}}: a filter built on the field path 'nested.a' with operator '==' performs its comparison against the value 1. A document is included in the results when its traversed value equals the query value; when that value does not equal the query value, the document is left out.

A field name containing no dot still refers to a top-level key, just as it did before.

2. Fields that are missing

If the referenced field path is missing from a document — that is, the top-level key is absent, or any segment along a nested path is absent — the document must simply not match the filter, and it must be excluded from the results. An error must not be raised in this situation.

Edge Cases

  • If the top-level field name used in a filter is one that no document possesses, the filter yields zero results.
  • When an equality operator is combined with a nested field path (e.g. 'nested.a'), the filter returns exactly the documents whose value at that nested path is equal to the query value; documents whose value differs are excluded.
  • The results are returned in the form of document snapshots; each snapshot's .to_dict() returns the original document data in full (nested structure included).

Task Specification: MockFirestore Data Isolation

Overview

This task deals with a mock implementation of a document database modeled on Firestore. You must ensure that the data held inside the mock is fully isolated from the objects callers supply or that are returned to them, so that mutating an object outside the mock never changes the data stored internally (and the reverse holds as well).

Public API Surface

The following must be importable and usable:

from mockfirestore import MockFirestore

  • MockFirestore() — a constructor that takes no arguments. Each instance exposes a mutable attribute _data (a dict) representing the backing store. Callers may assign to _data directly in order to seed the store. The structure is nested: keys at the top level are collection names mapping to dicts, whose keys are document ids mapping to dicts holding that document's field data.

  • MockFirestore.collection(collection_name: str) — returns a collection reference object.

  • The collection reference exposes .document(document_id: str) — which returns a document reference object.

  • The document reference exposes:

    • .set(data: dict) — stores data as the contents of the document under the given id.
    • .update(data: dict) — merges data into the document's existing contents at the top level (keys at the top level of data replace the matching stored keys).
    • .get() — returns a document snapshot object.

  • The document snapshot exposes:

    • .to_dict() — returns the field data of the document as a dict.

Required Behavior

1. Isolation on set()

When set(data) is invoked, the mock must store a copy of data instead of keeping a reference to the caller's object. Once set() has been called, any later mutation the caller performs on the original data object (for example, changing one of its top-level values) must have no effect on what is subsequently retrieved via get().to_dict().

Example of the required outcome: seed _data with an empty collection foo, call set({'id': 'bar'}) on document bar, then change the passed dict's id to 'new value'. When the document is retrieved, the result is {'id': 'bar'}.

2. Isolation on update()

When update(data) is called, the mock must store a copy of the incoming data — deep enough that nested structures are isolated too — instead of keeping references into the caller's object. After update() has been called, mutating a nested value inside the original data object must have no effect on what is later retrieved via get().to_dict().

Example of the required outcome: seed document first with {'nested': {'id': 1}}, call update({'nested': {'id': 2}}), then modify the passed dict so that its nested id becomes 3. When the document is retrieved, the result is {'nested': {'id': 2}}.

3. Isolation on to_dict()

to_dict() must return a copy of the stored document data rather than a reference into the backing store. After a dict has been obtained from to_dict(), later mutations to the underlying _data store must not change the dict that was already returned.

Example of the required outcome: seed document first with {'id': 1}, call get().to_dict() to obtain a dict, then mutate _data so the stored id becomes 2. The dict obtained earlier still equals {'id': 1}.

Notes

  • The existing behavior of set(), update(), get(), and to_dict() (storing, merging, retrieving, and reporting document contents correctly) must keep working as it did before; the only change is the guarantee of the isolation described above.
