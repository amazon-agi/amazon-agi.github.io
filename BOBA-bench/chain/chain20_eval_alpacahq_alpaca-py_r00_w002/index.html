02 Implement a method on the BrokerClient class that retrieves account activities from the broker API, with configurable pagination behavior. 610 words · source specification

Task: Implement BrokerClient.get_account_activities with pagination support

Overview

Implement a method on the BrokerClient class that retrieves account activities from the broker API, with configurable pagination behavior. The API returns activity records in pages, and the method must correctly aggregate or stream these pages based on a pagination strategy.

Public API Surface

Method
class BrokerClient:
    def get_account_activities(
        self,
        activity_filter: GetAccountActivitiesRequest,
        handle_pagination: PaginationType,
    ):
        ...

The method accepts:

  • activity_filter: a GetAccountActivitiesRequest instance describing filter parameters for the query (must be constructible with no arguments).
  • handle_pagination: a PaginationType enum value controlling how paging is handled.
Supporting Types

The following must be importable and usable by callers:

  • GetAccountActivitiesRequest — a request/filter model that can be instantiated with no arguments (all fields optional).
  • PaginationType — an enumeration providing at least the members PaginationType.FULL, PaginationType.NONE, and PaginationType.ITERATOR.
  • BaseActivity — the base model type that each returned activity record is parsed into.

Data Model

The API returns JSON arrays of activity objects. There are two shapes of activity, distinguished by their activity_type:

  1. Non-trade activities (e.g. activity_type = "CSD"), with fields such as:

    • id, account_id, activity_type, date, net_amount, description, status.

  2. Trade activities (e.g. activity_type = "FILL"), with fields such as:

    • id, account_id, activity_type, transaction_time, type, price, qty, side, symbol, leaves_qty, order_id, cum_qty, order_status.

Both shapes must be parseable, and each parsed record must be an instance of BaseActivity.

Pagination Behavior

The broker API endpoint for account activities is paginated. A single request returns up to a page-size worth of records. When a full page is returned, the caller must continue fetching subsequent pages (using the last returned item to advance to the next page); when a page returns fewer records than the page size, that page is the last one.

For the purposes of this task, the page size behavior is such that a page containing 4 records indicates there may be more pages, and the paging continues until a request returns fewer than a full page.

The method's return value and request-issuing behavior depend on handle_pagination:

PaginationType.FULL
  • Fetch all pages, following pagination until exhausted.
  • Return a single List containing every activity record from all pages, in order.
  • Given a data set spanning multiple pages that requires 3 HTTP requests to fully retrieve, exactly 3 requests must be made, and the combined result must contain all 8 records.
  • Each element of the returned list must be a BaseActivity instance.
PaginationType.NONE
  • Fetch only the first page.
  • Make exactly 1 HTTP request.
  • Return a single List containing only the records from that first page (4 records for the reference data set).
  • Each element of the returned list must be a BaseActivity instance.
PaginationType.ITERATOR
  • Return a generator/iterator that yields one page at a time.
  • Each item produced by the generator is a List of BaseActivity instances (one page's worth of records).
  • Pages are fetched lazily as the generator is advanced.
  • After all pages have been consumed, advancing the generator again yields nothing further (i.e. next(generator, None) returns None).
  • Over the reference data set requiring 3 requests, driving the generator to exhaustion results in exactly 3 HTTP requests being made in total.

Reference Data Set

For a data set that, when fully paginated, spans 3 HTTP requests:

  • The first page returns 4 records.
  • Subsequent pages continue until a page returns fewer than 4 records.
  • The total number of records across all pages is 8.
  • The records include both non-trade ("CSD") and trade ("FILL") activity shapes, and all must parse successfully into BaseActivity instances.

Pagination behavior

The method supports three pagination modes via handle_pagination:

  • PaginationType.NONE: Perform a single request and return the results as a list. Only one HTTP request is made.

Add a new optional keyword parameter to this existing method:

def get_account_activities(
    self,
    activity_filter: GetAccountActivitiesRequest,

    handle_pagination: Optional[PaginationType] = None,
) -> Union[List[BaseActivity], Iterator[List[BaseActivity]]]:

  • The parameter must be callable as a keyword argument (max_items_limit=...).

This method performs GET requests to the endpoint path /v1/accounts/activities.

Required Behavior

When handle_pagination=PaginationType.FULL and max_items_limit is specified, the method returns a List of activity model instances whose length is exactly max_items_limit, provided the server has at least that many items available.

The implementation must enforce max_items_limit regardless of how many items the server actually returns in any single response. Even if the server returns more items than were requested in a page, the final result must be truncated so that its total length never exceeds max_items_limit.

Page-size request behavior

The client controls how many items it requests per page via the page_size query parameter. When a max_items_limit is in effect, the client must request only as many items as it still needs:

  • On each request, the page_size sent to the server must equal the number of remaining items needed to reach max_items_limit (i.e., max_items_limit minus the number of items already collected), unless normal pagination page-size logic would request fewer.

Concretely:

  • Case: date filter present, single request. When the GetAccountActivitiesRequest includes a date value, the operation completes in a single HTTP request (call count = 1). In this case the page_size query parameter sent must equal max_items_limit. Regardless of the number of items the server returns in that single response, the returned list must be truncated to max_items_limit. The date query parameter must also be present, serialized as the datetime rendered in "YYYY-MM-DD HH:MM:SS" form (e.g. a date of 2022-03-04 becomes "2022-03-04 00:00:00").

  • Case: standard multi-page pagination. When paginating across multiple requests, after the first page has been collected the next request's page_size must reflect only the number of items still needed to reach max_items_limit. For example, if the first response supplies 4 items and max_items_limit is 5, the second request must send page_size=1. Once max_items_limit items have been collected, pagination stops and the combined result is truncated to max_items_limit items.

Supporting Types (already present in the codebase)

  • GetAccountActivitiesRequest: a request model accepting an optional date field (a datetime).
  • PaginationType: an enum with at least a FULL member.
  • Activity model classes (e.g. TradeActivity) into which the JSON response objects are parsed.

Notes

  • The default behavior (when max_items_limit is not supplied) must remain unchanged.
  • Truncation must be applied to the aggregated result, not left to the server.

Task Specification: Account Activity List Pagination

Overview

Implement automatic pagination for the account activities retrieval method on the BrokerClient. When the API returns paginated results, the client must transparently follow all pages and return the complete, combined list of activity objects.

Public API Surface

You must ensure the following are importable and callable:

  • BrokerClient.get_account_activities(self, activity_filter: GetAccountActivitiesRequest) -> List[Union[NonTradeActivity, TradeActivity]]

    • Accepts a GetAccountActivitiesRequest request object (which must be constructible with no arguments, i.e. GetAccountActivitiesRequest()).
    • Returns a Python list.

  • GetAccountActivitiesRequest — a request/parameters model constructible with no arguments.

  • NonTradeActivity — model class representing a non-trade activity entry.

  • TradeActivity — model class representing a trade activity entry.

These must be importable from the package's public surface used by BrokerClient (the same module paths from which the client and its models are normally imported).

Required Behavior

Default full-pagination retrieval

When get_account_activities is called with a default (empty) GetAccountActivitiesRequest, and the underlying account activities API endpoint returns its results across multiple pages, the client must:

  1. Issue the initial request to the account activities endpoint.
  2. Continue requesting subsequent pages until the API signals there are no more results (i.e., until a returned page is empty / does not indicate a further page).
  3. Combine all activity records from every page into a single flat list, preserving the order in which they are returned across the pages.
  4. Return that combined list.
Pagination token handling

For each page beyond the first, the client must request the next page by supplying a page_token query parameter. The value of page_token for the next request must be derived from the last activity item of the most recently received page — specifically, that item's identifier is used as the page_token.

Concretely, for a response set that spans three pages:

  • The first request carries no page_token.
  • The second request must carry a page_token query parameter equal to the id of the last activity item from the first page's response.
  • The third request must carry a page_token query parameter equal to the id of the last activity item from the second page's response.
Termination

Pagination stops when the endpoint returns a page that contains no further activities. That terminal (empty) page does not contribute items to the result and represents the end of the sequence.

Result composition and types
  • The returned value is a list.
  • Each element is deserialized into the appropriate activity model based on its kind: trade-type entries become TradeActivity instances, and non-trade-type entries become NonTradeActivity instances.
  • A given result list may contain a mixture of NonTradeActivity and TradeActivity objects, interleaved according to the order returned by the API.

Concrete Reference Scenario

Given a paginated endpoint whose full result set totals 8 activity records spread across pages (with a final empty page terminating the sequence):

  • get_account_activities(GetAccountActivitiesRequest()) performs exactly 3 HTTP requests to the endpoint.
  • The returned list has length 8.
  • The elements' types reflect the underlying activity kinds (e.g., a non-trade entry yields a NonTradeActivity, a trade entry yields a TradeActivity), interleaved as returned.
  • The second HTTP request includes exactly one query parameter, page_token, whose value is the id of the last item from the first page.
  • The third HTTP request includes exactly one query parameter, page_token, whose value is the id of the last item from the second page.

Notes

  • The page_token used for each subsequent page must be sourced from the identifier of the last item of the immediately preceding page's response — not from any pre-existing token field on the request object.

Task Specification: Broker Document Type Consolidation and API Refinements

Overview

You are making refinements to an Alpaca Broker SDK. The primary change is consolidating two document-type enums into a single enum, along with adjusting a method parameter name and changing validation behavior for a request model.

Required Changes

1. Consolidate UploadDocumentType into DocumentType

There must be a single enum named DocumentType that serves the role previously split between an upload-specific document type enum and any general document type enum. The separate UploadDocumentType enum must no longer exist.

DocumentType must be importable from:

  • alpaca.broker.enums
  • The top-level alpaca.broker package

DocumentType must include at least the following members (used by callers):

  • DocumentType.ACCOUNT_APPROVAL_LETTER
  • DocumentType.W8BEN

The following enums must continue to exist and be importable from both alpaca.broker.enums and alpaca.broker:

  • TradeDocumentType
  • UploadDocumentMimeType (must include at least UploadDocumentMimeType.PDF and UploadDocumentMimeType.JSON)
  • UploadDocumentSubType (must include at least UploadDocumentSubType.FORM_W8_BEN and UploadDocumentSubType.ACCOUNT_APPLICATION)
2. UploadDocumentRequest model

A model named UploadDocumentRequest must be importable from alpaca.broker (and usable by the broker client). It must accept the following fields:

  • document_type — a DocumentType
  • document_sub_type — an optional UploadDocumentSubType
  • content — a string
  • mime_type — an UploadDocumentMimeType

Validation rules on construction:

  • If document_type is DocumentType.W8BEN, construction must raise ValueError.
  • If document_sub_type is UploadDocumentSubType.FORM_W8_BEN, construction must raise ValueError.

(In other words, this request type explicitly rejects W-8 BEN documents; those are handled by a dedicated request type below.)

3. UploadW8BenDocumentRequest model

A model named UploadW8BenDocumentRequest must be importable from alpaca.broker. It must be constructible with only:

  • content — a string
  • mime_type — an UploadDocumentMimeType

When constructed this way, it must default appropriately such that its document_type corresponds to a W-8 BEN document type and its document_sub_type corresponds to the W-8 BEN sub type (i.e., default values that represent W-8 BEN). Construction with only content and mime_type must succeed without error.

This model must enforce its W-8 BEN identity via assignment-time validation (validation must run when fields are reassigned on an existing instance, not only at construction):

  • Assigning document_type to anything other than the W-8 BEN document type must raise ValueError whose message contains the text: document_type must be W8BEN.
  • Assigning document_sub_type to anything other than the W-8 BEN sub type must raise ValueError whose message contains the text: document_sub_type must be FORM_W8_BEN.
4. W8BenDocument model

A model named W8BenDocument must be importable from alpaca.broker.

5. BrokerClient.download_trade_document_for_account_by_id parameter rename

The method download_trade_document_for_account_by_id on alpaca.broker.client.BrokerClient must accept its destination path via a keyword parameter named file_path (previously file_name). Its signature must accept the keyword arguments:

  • account_id
  • document_id
  • file_path

Behavior:

  • account_id and document_id must be validated as UUIDs. If either is passed a value that is not a valid UUID (e.g., the string "not a uuid"), the method must raise ValueError. This validation must occur regardless of the file_path value. Both a UUID object and a valid UUID string are acceptable for the valid parameter.
  • On a successful call, the method downloads the trade document and writes it to the given file_path. The download flow involves making the requests necessary to retrieve and store the document content (the successful path results in more than one underlying HTTP request being made).
