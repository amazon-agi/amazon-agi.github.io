Task: Implement BrokerClient.get_account_activities with support for pagination

Summary

Add a method to the BrokerClient class that retrieves account activities from the broker API, with pagination behavior that can be configured. The API returns activity records in pages, and the method must aggregate or stream these pages correctly according to a pagination strategy.

Public API

Method
class BrokerClient:
    def get_account_activities(
        self,
        activity_filter: GetAccountActivitiesRequest,
        handle_pagination: PaginationType,
    ):
        ...

The method accepts the following:

  • activity_filter: a GetAccountActivitiesRequest instance that describes the filter parameters for the query (it must be constructible with no arguments).
  • handle_pagination: a PaginationType enum value that controls how paging is handled.
Supporting Types

The following must be importable by callers and usable by them:

  • GetAccountActivitiesRequest — a request/filter model that can be instantiated with no arguments (all of the fields are optional).
  • PaginationType — an enumeration that provides at least the members PaginationType.FULL, PaginationType.NONE, and PaginationType.ITERATOR.
  • BaseActivity — the base model type into which each returned activity record is parsed.

Data Model

The API returns JSON arrays of activity objects. Activities come in two shapes, distinguished by their activity_type:

  1. Non-trade activities (e.g. activity_type = "CSD"), having fields such as:

    • id, account_id, activity_type, date, net_amount, description, status.

  2. Trade activities (e.g. activity_type = "FILL"), having fields such as:

    • id, account_id, activity_type, transaction_time, type, price, qty, side, symbol, leaves_qty, order_id, cum_qty, order_status.

Parsing must succeed for both shapes, and each parsed record must be an instance of BaseActivity.

Pagination Behavior

The broker API endpoint for account activities is paginated. One request returns up to a page-size worth of records. When a full page is returned, the caller must keep fetching subsequent pages (advancing to the next page with the last returned item); when a page returns fewer records than the page size, that page is the last one.

For this task, the page size behavior is such that a page containing 4 records signals that there may be more pages, and paging continues until a request returns fewer than a full page.

The method's return value and its request-issuing behavior depend on handle_pagination:

PaginationType.FULL
  • Fetch all pages, advancing through the pagination until it is exhausted.
  • Return a single List that contains every activity record from all pages, in order.
  • For a data set that spans multiple pages and requires 3 HTTP requests to retrieve fully, exactly 3 requests must be made, and the combined result must contain all 8 records.
  • Each element in the returned list must be a BaseActivity instance.
PaginationType.NONE
  • Fetch only the first page.
  • Make exactly 1 HTTP request.
  • Return a single List that contains only the records from that first page (4 records for the reference data set).
  • Each element in the returned list must be a BaseActivity instance.
PaginationType.ITERATOR
  • Return a generator/iterator that yields one page at a time.
  • Each item the generator produces is a List of BaseActivity instances (one page's worth of records).
  • The generator fetches pages lazily as it is advanced.
  • After all pages have been consumed, advancing the generator again yields nothing further (i.e. next(generator, None) returns None).
  • With the reference data set that requires 3 requests, driving the generator to exhaustion results in exactly 3 HTTP requests being made in total.

Reference Data Set

For a data set that spans 3 HTTP requests when fully paginated:

  • The first page returns 4 records.
  • Subsequent pages keep coming until a page returns fewer than 4 records.
  • Across all pages, the total number of records is 8.
  • The records include activity shapes of both the non-trade ("CSD") and the trade ("FILL") kind, and all of them must parse successfully into BaseActivity instances.

The number of items the client asks for per page is controlled through the page_size query parameter. Whenever a max_items_limit is in effect, the client must request only as many items as it still needs:

  • With each request, the page_size sent to the server must equal the number of items still needed to reach max_items_limit (that is, max_items_limit minus the number of items already collected), unless the normal pagination page-size logic would request fewer.

Summary

Public API

    • A Python list is the return value.

  • GetAccountActivitiesRequest — a request/parameters model that can be constructed with no arguments.

  • TradeActivity — the model class for a trade activity entry.

All of these must be importable from the public surface of the package that BrokerClient uses (the same module paths from which the client and its models are normally imported).

Behavior Requirements

Full-pagination retrieval by default

Take the case where get_account_activities is called with a default (empty) GetAccountActivitiesRequest and the underlying account activities API endpoint returns its results across multiple pages. The following actions are then required of the client:

  1. An initial request is sent to the account activities endpoint.
  2. Requests for subsequent pages continue until the API signals that there are no more results (i.e., until a page that is returned is empty / does not indicate a further page).
  3. All of the activity records from every page are combined into one flat list, and the order in which they are returned across the pages is kept intact.
  4. The combined list is what the client returns.
Handling of the pagination token

The client must request every page beyond the first by supplying a page_token query parameter. For the next request, the page_token value must be derived from the last activity item of the page received most recently — that is, the identifier belonging to that item serves as the page_token.

To make this concrete, take a response set spanning three pages:

  • No page_token is carried by the first request.
  • On the second request, a page_token query parameter must be carried, and it must equal the id of the last activity item from the first page's response.
  • On the third request, a page_token query parameter must be carried, and it must equal the id of the last activity item from the second page's response.
Stopping condition

What stops pagination is the endpoint returning a page that holds no further activities. No items are contributed to the result by that terminal (empty) page — it stands for the end of the sequence.

Composition and types of the result
  • What is returned is a list.
  • Deserialization of every element uses the activity model appropriate for its kind: an entry of trade type becomes a TradeActivity instance, and an entry of non-trade type becomes a NonTradeActivity instance.
  • Within a single result list, a mixture of NonTradeActivity and TradeActivity objects may be present, interleaved in line with the order the API returns.

Concrete Reference Example

Picture a paginated endpoint whose complete result set amounts to 8 activity records distributed across pages, with a final empty page bringing the sequence to an end:

  • Exactly 3 HTTP requests to the endpoint are made by get_account_activities(GetAccountActivitiesRequest()).
  • The returned list's length is 8.
  • The type of each element mirrors the underlying activity kind (e.g., NonTradeActivity is what a non-trade entry yields, while a trade entry yields a TradeActivity), interleaved in the order in which they were returned.
  • On the second HTTP request, exactly one query parameter is present — page_token — and its value is the id of the last item from the first page.
  • On the third HTTP request, exactly one query parameter is present — page_token — and its value is the id of the last item from the second page.

Additional Notes

  • For every subsequent page, the source of the page_token must be the identifier of the last item of the immediately preceding page's response — not any pre-existing token field on the request object.

PaginationType is an enum, importable from alpaca.broker.client, whose members are FULL, NONE, and ITERATOR.

The pagination behavior is driven by handle_pagination:

  • Default (when handle_pagination is None): behaves like FULL.
  • PaginationType.FULL: Requests pages repeatedly until an empty page comes back, accumulating the results and returning a single flat List of all deserialized activities. Each subsequent request must set the page_token query parameter to the id of the last item on the previous page. (E.g. with three responses of 4, 4, and 0 items, the result is a list of 8 items; the second request carries page_token = id of the 4th item from page one, the third request carries page_token = id of the last item from page two.)
  • PaginationType.NONE: Makes exactly one request and returns a single List of the deserialized activities from that page (no pagination).
  • PaginationType.ITERATOR: Returns a generator (an Iterator). Until the generator is first advanced, no HTTP request is made. Each next() yields a List containing the deserialized activities of one page. When the underlying API returns an empty page, the generator is exhausted (a subsequent next() with a default returns that default / raises StopIteration). For responses of 4, 4, 0 items, advancing the generator yields two lists of 4 items each and then stops, having made 3 requests total.

max_items_limit (an integer cap on the total number of items returned):

  • Valid only together with PaginationType.FULL. If it is supplied with any other pagination type (e.g. ITERATOR), raise ValueError with a message containing: max_items_limit can only be specified for PaginationType.FULL
  • When it is set with FULL, the total number of items returned must not exceed max_items_limit, even if the API returns more items than were requested on a page. If the remaining allowance for a page is smaller than the default page size, the request's page_size query parameter must be set to exactly that remaining allowance. (E.g. with a max of 5 and pages that each return 4: after the first page of 4 comes back, the second request sets page_size=1, and the final result contains exactly 5 items across 2 requests. With a max of 2 and a single page returning 5, the result contains exactly 2 items.)
