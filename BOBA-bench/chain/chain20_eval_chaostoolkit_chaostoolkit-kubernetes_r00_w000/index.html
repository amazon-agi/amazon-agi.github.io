Overview

The package you are working on is chaosk8s, a Python package delivering chaos-engineering probes and actions for Kubernetes. You must build a Kubernetes API client factory in the package's top-level module, connect the existing probes/actions to that factory, and introduce a new probe that determines whether a service endpoint has been initialized.

Public API Requirements

Package chaosk8s (top-level __init__)

The chaosk8s module is where the following belongs:

has_local_config_file() -> bool

A function whose result indicates whether a local Kubernetes configuration file is available. It accepts no arguments, and its return value is a boolean. (Various flows will patch/mock it, so it must be importable and callable at chaosk8s.has_local_config_file.)

create_k8s_api_client(secrets: Mapping = None) -> client.ApiClient

This function assembles and returns a kubernetes.client.ApiClient that is set up for communication with a Kubernetes cluster.

Expected behavior:

  • One optional argument, secrets — a mapping — is accepted by the function. It must be callable in both styles: with no arguments (create_k8s_api_client()) and with a mapping (create_k8s_api_client(secrets)).
  • Whenever has_local_config_file() returns False, the client configuration must come from a set of configuration keys. Lookup of these keys happens in the provided secrets mapping when one is supplied, and otherwise in the process environment variables (os.environ). The keys that matter are:
    • KUBERNETES_HOST → sets configuration.host
    • KUBERNETES_API_KEY → sets the API key value
    • KUBERNETES_API_KEY_PREFIX → sets the API key prefix
  • What the function returns must be a kubernetes.client.ApiClient with a .configuration that reflects those values:
    • api.configuration.host equals the value of KUBERNETES_HOST.
    • api.configuration.api_key maps the authorization entry to the value of KUBERNETES_API_KEY.
    • api.configuration.api_key_prefix maps the authorization entry to the value of KUBERNETES_API_KEY_PREFIX.

An equivalently configured client must be produced by both the environment-driven path (no secrets argument) and the secrets-driven path (mapping passed explicitly).

The types from the kubernetes library (kubernetes.client, kubernetes.config) can be used.

Probes module: chaosk8s.probes

The probes module must source its Kubernetes API client from the top-level factory described above (i.e. chaosk8s.create_k8s_api_client, which consults chaosk8s.has_local_config_file in turn). When they construct API objects such as client.CoreV1Api(...), the probes use the kubernetes client that is reachable as chaosk8s.probes.client.

These probes, which already exist, must stay importable and functional:

  • all_microservices_healthy
  • microservice_available_and_healthy
  • microservice_is_not_available
New probe to add: service_endpoint_is_initialized

At a minimum, the signature is:

service_endpoint_is_initialized(name, ns="default")

Expected behavior:

  • A CoreV1Api instance (from client.CoreV1Api(...)) is employed, and its list_namespaced_service method gets called to look up services matching the supplied name.

  • When at least one item is present in the lookup result, the service endpoint counts as initialized; the function then returns None (i.e., succeeds silently).

  • When the lookup result contains no items, the probe fails by raising FailedProbe (from the project's existing exceptions); the message of that exception contains the text:

    service '<name>' is not initialized

    with <name> standing for the service name that was supplied (e.g. service 'mysvc' is not initialized).

Actions module: chaosk8s.actions

These must stay importable:

  • start_microservice
  • kill_microservice

The API client used by start_microservice(spec_path=...) must come through the same top-level factory mechanism (with chaosk8s.has_local_config_file being consulted). A spec_path pointing at a specification file is accepted by it. In the case of a file that is neither a YAML (.yaml/.yml) nor a JSON (.json) file, FailedProbe must be raised, with a message that contains:

cannot process <path>

with <path> standing for the supplied spec_path.

Notes on acquiring a Kubernetes client

Whatever code path acquires a Kubernetes client must check chaosk8s.has_local_config_file(), in the probes as well as the actions. If that check returns False, the client must be built from environment variables / secrets, in the way described under create_k8s_api_client. In other words, when configuration is supplied via environment/secrets, the probes and actions must not require a local kube config file to be present in order to function.

  • all_microservices_healthy(...) fails with a FailedProbe that contains the system is unhealthy whenever any pod's status phase indicates failure (e.g. Failed).
  • When a matching deployment/item still exists, microservice_is_not_available(name, ...) fails with a FailedProbe that contains microservice '<name>' looks healthy.

Every error condition raises FailedProbe; that exception is importable from the project's existing exceptions module.

03 Your work takes place in the chaosk8s package, which provides probes for verifying the state of Kubernetes microservices. 519 words · source specification, reworded by GLM-5.3-Flash

Task Description

Summary

Your work takes place in the chaosk8s package, which provides probes for verifying the state of Kubernetes microservices. The task consists of changing one existing probe and adding one new probe in the module chaosk8s.probes.

Background

The functions listed below already exist and can be imported from chaosk8s.probes:

  • all_microservices_healthy
  • microservice_available_and_healthy
  • microservice_is_not_available
  • service_endpoint_is_initialized

The module has access to the Kubernetes client by way of chaosk8s.probes.client, as well as to a chaosk8s.probes.watch module (the Kubernetes watch API). The loading of configuration depends on chaosk8s.has_local_config_file.

Required Modifications

1. Change microservice_is_not_available(name)

The job of this function is to verify that a microservice is not running. It must be changed so that it inspects pods rather than deployments.

Behavior:

  • Fetch the list of namespaced pods using the Kubernetes Core V1 API (client.CoreV1Api, method list_namespaced_pod).
  • Look at the pods that come back (the items collection of the result).
  • A pod counts as running if its status.phase equals the string "Running".
  • If any pod is discovered in the "Running" phase, the microservice counts as available when it should not be. In that situation, raise chaoslib.exceptions.FailedActivity with a message that contains:
    microservice '<name>' is actually running
    where <name> denotes the value of the name argument.
2. Introduce the new function deployment_is_not_fully_available(name)

Create a new public function that can be imported as:

from chaosk8s.probes import deployment_is_not_fully_available

Signature: deployment_is_not_fully_available(name, ...) — it must be callable with a single positional argument, namely the microservice/deployment name.

Purpose: Verify that a deployment is not fully available, that is, that it never reaches the state in which all desired replicas are ready before an observation timeout occurs.

Behavior:

  • Stream events for the deployment identified by name with the help of the Kubernetes watch API (watch.Watch()).
  • For each streamed event, take the deployment object from that event (each event is a mapping with an "object" key holding the deployment).
  • A deployment counts as "fully available" when deployment.spec.replicas equals deployment.status.ready_replicas.
    • When a deployment that has been observed is fully available, this is the undesired condition and the watch should stop being consumed / considered complete.
  • The function must keep observing the stream until the watch stops producing events. Given that the desired state (deployment never becoming fully available) is confirmed by the observation window ending without full availability, the underlying stream is expected to eventually raise urllib3.exceptions.ReadTimeoutError when the deployment stays fully available for the whole window.

Return / error conditions:

  • If, having observed the deployment in a not fully available state (i.e. spec.replicas != status.ready_replicas), the stream ends (is exhausted), the probe succeeds and the function returns True.
  • If the deployment stayed fully available throughout the observation window, with the result that the stream raises urllib3.exceptions.ReadTimeoutError, raise chaoslib.exceptions.FailedActivity with a message containing:
    microservice '<name>' failed to stop running within
    where <name> denotes the value of the name argument.

Notes

  • All error conditions must result in chaoslib.exceptions.FailedActivity being raised.
  • The functions must respect the existing configuration-loading mechanism, which is gated by chaosk8s.has_local_config_file.

07 Implement a Pod Termination Action 358 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Implement a Pod Termination Action

Goal

Introduce a new action that terminates Kubernetes pods whose names match a name pattern within a namespace.

Public API Surface

Create a module at chaosk8s/pod/actions.py which exposes the following function:

def terminate_pods(name_pattern=None, ns="default", ...):
    ...

It must be possible to import the function as:

from chaosk8s.pod.actions import terminate_pods
Package Layout

Ensure that chaosk8s/pod/ forms a proper Python package (that is, it is importable). The module must import the Kubernetes Python client so that a reference with the name client is accessible at module scope (chaosk8s.pod.actions.client), providing access to client.CoreV1Api.

Required Behavior

The terminate_pods function accepts:

  • name_pattern: a string containing a regular expression that is used to match pod names.
  • ns: the Kubernetes namespace, with "default" as its default.

Once the function is invoked, it must:

  1. Acquire a CoreV1Api instance using client.CoreV1Api().
  2. Call list_namespaced_pod on that API instance to list the pods in the given namespace.
  3. Filter the pods that are returned so that only pods whose metadata.name matches the supplied name_pattern (as a regular expression, with search semantics — a match anywhere in the name that satisfies the pattern) are selected.
  4. Delete each matching pod by calling delete_namespaced_pod on the API instance, passing:
    • the pod's metadata.name as the first positional argument,
    • the namespace (ns) as the second positional argument,
    • a delete-options / body object as the third argument.

Pods whose names do not match the pattern must NOT be deleted.

Example

Assume two pods exist, named "my-app-1" and "some-db". Calling:

terminate_pods(name_pattern="my-app-[0-9]$")

must produce exactly one deletion call, deleting the pod named "my-app-1" in the "default" namespace. The pod named "some-db" must not be deleted.

Configuration Loading Context

The module sits inside a package (chaosk8s) which exposes a has_local_config_file helper together with a client reference at the top level (chaosk8s.client). These back the setup of Kubernetes configuration/authentication. terminate_pods should work correctly when local configuration is not present.

Dependencies

The implementation depends on the kubernetes Python client library and integrates with the chaoslib framework (which defines FailedActivity in chaoslib.exceptions).

Public API of the Probe

Once relocated, the function must keep this interface, with the argument order and defaults included:

def read_microservices_logs(
    name: str,
    last: Union[str, None] = None,
    ns: str = "default",
    from_previous: bool = False,
    label_selector: str = "name in ({name})",
    secrets: Secrets = None
) -> Dict[str, str]
Parameters
  • name: The name of the microservice, used when the pod label selector is formatted.
  • last: An optional human-readable date or relative duration, such as "10 minutes", that limits the logs to the number of seconds elapsed between the parsed time and now.
  • ns: The Kubernetes namespace in which pods are to be found. The default is "default".

Return Value

The probe must return a dictionary whose keys are the selected pod names and whose values are those pods' logs decoded as UTF-8 strings:

{
    "myapp-1235": "hello"
}

If no pods match, an empty dictionary must be returned. If multiple pods match, the logs of each pod must be fetched and one entry per pod name must be included.

Selecting Pods and Kubernetes Configuration

On each invocation, the probe must do the following:

  1. Format label_selector using the supplied name. With the defaults in effect, name="myapp" results in "name in (myapp)".
  2. Acquire the API client by way of the existing top-level chaosk8s.create_k8s_api_client(secrets) mechanism. This keeps the package's existing local-configuration detection and its environment/secrets fallback behavior intact.
  3. Build a Core V1 API from that API client via the current chaosk8s.pod.probes.client binding.
  4. List the pods in ns with the formatted selector, which is equivalent to calling list_namespaced_pod(ns, label_selector=formatted_selector).

The relocation must not introduce a separate Kubernetes configuration path, and it must not bypass the package-level configuration helper.

Time Window for the Logs

If last is truthy, it must be parsed with the existing fluent date parsing behavior, and the integer number of seconds elapsed from the parsed date/time to the current date/time must be calculated. That non-zero value must be passed to Kubernetes as since_seconds.

If last is absent or false, since_seconds must not be sent. If the conversion produces zero, since_seconds must be omitted, preserving the existing behavior. With no time window, the probe requests the available logs and does not impose an additional tail limit.

How Logs Are Retrieved

For every pod the list operation returns, call the Core V1 pod-log operation with that pod's metadata name along with the following options:

  • namespace=ns
  • follow=False
  • previous=from_previous
  • timestamps=True
  • _preload_content=False
  • since_seconds=<calculated seconds> only when a non-zero time window was calculated

Read the response stream that is returned, decode its bytes as UTF-8, and store the resulting string under the pod's name. This probe does not convert configuration, date parsing, Kubernetes API, stream-reading, or UTF-8 decoding errors into a different result; they continue to propagate.

Kubernetes Client Binding and Its Replaceability

The module-level chaosk8s.pod.probes.client value must be the root of all Kubernetes Core V1 access performed by read_microservices_logs. In particular, the Core V1 API through which pods are listed and logs are read must be constructed from the current value of that attribute.

If chaosk8s.pod.probes.client is replaced before an invocation, that invocation must use the replacement object, regardless of whether the function was imported from the new module or through the compatibility entry point. The moved probe must not keep resolving its Core V1 API through chaosk8s.probes.client. Other probes that remain in chaosk8s.probes may, as before, keep using that module's client binding.

Preserving Backward Compatibility

Callers that exist today must still be able to import and invoke the probe from its original location:

from chaosk8s.probes import read_microservices_logs

The original location must serve as a compatibility alias or re-export of the relocated probe, remain part of the legacy module's public export surface, and produce the same behavior as:

from chaosk8s.pod.probes import read_microservices_logs

Execution via the compatibility entry point must be routed through the relocated behavior, so that replacing chaosk8s.pod.probes.client is honored. Keeping an independent legacy implementation that still uses chaosk8s.probes.client does not satisfy this requirement.

Scope and Non-Goals

  • The probe's inputs, defaults, output shape, label-selection semantics, relative-time semantics, log-request options, or decoding behavior must not be changed.
  • Unrelated probes and actions must not be relocated or altered.
  • The package's existing Kubernetes configuration and local-config detection mechanism must not be replaced or modified.
  • The original chaosk8s.probes.read_microservices_logs import path must not be removed; it remains a supported compatibility API even though the probe now lives in the pod-specific module.

Task Specification: Implement Pod Phase Probes

Goal

Two probe functions are to be implemented in a new module chaosk8s/pod/probes.py; they inspect the phase of Kubernetes pods that match a label selector.

The New Module and Its Public API

Create the module chaosk8s.pod.probes, which exposes the following two functions:

def pods_in_phase(label_selector: str, phase: str = "Running", ns: str = "default") -> bool
def pods_not_in_phase(label_selector: str, phase: str = "Running", ns: str = "default") -> bool

Accessing the Kubernetes Client

  • The Kubernetes client must be imported by the module under the name client (i.e. from kubernetes import client or an equivalent form, so that chaosk8s.pod.probes.client is the client module).
  • Pods are obtained by calling client.CoreV1Api() and then invoking list_namespaced_pod on the returned object.

  • rand (bool): when it is set to True, candidate pods are picked at random.
  • mode (str): the mode used for selection; 'percentage' is a value it supports.
  • qty (int): a quantity whose interpretation is governed by mode (a count of pods, or else a percentage when mode='percentage').
  • grace_period / handling of the grace period (see further below).

Behavior That Is Required

One or more pods are selected by the function out of the "default" namespace — depending on the parameters above — and each selected pod is terminated through a call to the Kubernetes core V1 API method delete_namespaced_pod.

Each delete_namespaced_pod call MUST be formed as follows:

  1. The name of the pod (pod.metadata.name), which goes in the first positional argument.
  2. The namespace string "default", which goes in the second positional argument.
  3. A deletion options object, which goes in the keyword argument body.

The change that is required above all: the deletion options object must be supplied under the keyword body=..., and it must NOT be passed positionally.

The deletion options object
  • When no grace period has been specified, what is passed to body is a delete-options object (an acceptable value is any V1DeleteOptions instance).
  • When a grace period has been specified (for example, 5 seconds), the value passed to body must be a V1DeleteOptions instance whose construction sets grace_period_seconds to that value — that is, the equivalent of client.V1DeleteOptions(grace_period_seconds=5).
Selection and call-count behavior
  • If name_pattern is the only parameter and a single pod matches, that pod is the target of exactly one termination call.
  • If name_pattern is combined with all=True, every matching pod is terminated (one termination call for each pod).
  • If all=True is set without any pattern, every pod in the namespace is terminated (one termination call for each pod).
  • If no parameters are given, exactly one pod is terminated.
  • If qty=N is given and N is greater than the number of selected pods, all selected pods are terminated.
  • If mode='percentage' and qty=P are set, a percentage P of the selected pods is terminated (with rounding applied, so that 40% of 5 pods, for example, produces 2 termination calls).
  • The rand=True flag makes the choice of candidate pods random, yet the number terminated and the call convention are not affected.

Across all cases, the argument convention for delete_namespaced_pod set out above (name positional, "default" positional, body as a keyword) must hold.

Goal

Alter the logic that creates the Kubernetes API client inside the chaosk8s module so that, when configuration is loaded from a local kube config file with a context specified, config.load_kube_config is used rather than config.new_client_from_config.

Public API

The chaosk8s module must expose a function:

def create_k8s_api_client()

This function constructs and returns a Kubernetes API client that is based on the current environment.

Behavior Requirements

When a local kubernetes configuration file is present (i.e., the client is being created from a kube config rather than from in-cluster secrets) and a particular context is requested through the KUBERNETES_CONTEXT environment variable:

  • The function must call config.load_kube_config (where config denotes the imported kubernetes config module, accessible as chaosk8s.config), supplying the context as the keyword argument context.
  • Concretely, if KUBERNETES_CONTEXT is set to a value such as "minikube", the call that is made must be config.load_kube_config(context="minikube").

The context value that is passed to load_kube_config must come from the KUBERNETES_CONTEXT environment variable.

Remarks

  • The config object that is used to load the configuration must be importable/patchable as the config attribute of the chaosk8s module (i.e., chaosk8s.config).
  • Whether a local config file is available is decided by a mechanism that already exists in the module (a check that signals a kube config file exists); when that check reports that a config file is present, the context-based loading path described above is followed.
