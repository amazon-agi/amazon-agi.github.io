Your job is to modify the nexmo Python module (the package that can be imported as nexmo, containing the nexmo.Client class). Implement the features described below.

1. Version Attribute of the Module

A __version__ attribute (a string) that represents the library's current version must be exposed by the nexmo module.

2. Application Name/Version Options for the Client Constructor

In addition to its existing parameters, the nexmo.Client constructor must accept two new optional keyword arguments:

  • app_name (string)
  • app_version (string)

Constructor keyword arguments that already exist, and that must continue to work, include at least:

  • key
  • secret
  • signature_secret

When app_name and app_version are both provided, the client must build a User-Agent identifier string made up of the following components, joined by a single / (forward slash) character, in exactly this order:

  1. The string literal nexmo-python
  2. The module's __version__
  3. The Python version currently running (as returned by platform.python_version())
  4. app_name
  5. app_version

Example: given a __version__ of 1.3.0, Python 3.8.1, app_name='ExampleApp', and app_version='X.Y.Z', the identifier is:

nexmo-python/1.3.0/3.8.1/ExampleApp/X.Y.Z

This User-Agent identifier must be sent as the User-Agent HTTP header on outbound API requests (for example, the request carried out by get_balance(), which is an HTTP GET to https://rest.nexmo.com/account/get-balance). When app_name/app_version are not provided, what is used is the base identifier (without the app name/version components).

3. The Client.signature(params) Method

Add to nexmo.Client an instance method signature(self, params).

  • Input: params is a dict of string keys to string values (there is no sig entry in it).
  • Output: returns a string — the signature computed for the given parameters, using the client's signature_secret.

The signature computation must produce exactly this result: given

params = {'a': '1', 'b': '2', 'timestamp': '1461605396'}

and a client instantiated with signature_secret='secret', signature(params) must return:

6af838ef94998832dbfc29020b564830

The algorithm: sort the params by key; concatenate each key/value as &key=value (in sorted key order); append the signature_secret; and compute the MD5 hex digest of the string that results. The result is a lowercase hexadecimal string that is 32 characters long.

4. The Client.check_signature(params) Method

Add to nexmo.Client an instance method check_signature(self, params).

  • Input: params is a dict of string keys to string values that contains a sig entry holding a signature that was provided.
  • Behavior: compute the signature over params with the sig entry excluded (using the same algorithm as signature), and compare it against the value of the sig entry.
  • Output: returns True if the computed signature and the provided sig value match; otherwise returns False.

For example, with a client that has signature_secret='secret' and

params = {'a': '1', 'b': '2', 'timestamp': '1461605396', 'sig': '6af838ef94998832dbfc29020b564830'}

check_signature(params) must return True.

07 The public nexmo module must allow Client to be constructed with a callback-signing secret passed in addition to its existing credentials 348 words · rewritten by GPT-5.6-sol, reworded by GLM-5.3-Flash

Task Description

Public API requirements

The public nexmo module must allow Client to be constructed with a callback-signing secret passed in addition to its existing credentials:

client = nexmo.Client(
    key=<api_key>,
    secret=<api_secret>,
    signature_secret='secret'
)

signature_secret is the secret employed for callback signature generation and validation. Existing ways of constructing Client, and its behavior, must remain compatible.

Expose the following public instance methods:

Client.signature(params)
Client.check_signature(params)

Generating signatures

Client.signature(params)

The params parameter is a dictionary of callback parameters. Using the client's signature_secret, the method must return the callback signature as a lowercase hexadecimal string.

Build the signature deterministically through these steps:

  1. Sort the parameter keys into ascending key order.
  2. Starting from an empty string, append each sorted key/value pair in the exact form &key=value; as a consequence, the first pair also has a leading &.
  3. Append the client's signature_secret directly onto the end of that string, without inserting any further delimiter.
  4. Compute the MD5 digest of the string that results.
  5. Return the digest in its lowercase hexadecimal representation.

Consequently, dictionary insertion order must not affect the result.

As an example, given:

params = {
    'a': '1',
    'b': '2',
    'timestamp': '1461605396'
}

together with signature_secret='secret', the exact string to be hashed is:

&a=1&b=2&timestamp=1461605396secret

and the value produced must be:

'6af838ef94998832dbfc29020b564830'

Validating signatures

Client.check_signature(params)

The params parameter is a dictionary that contains the callback parameters plus a sig entry. The sig value holds the signature supplied with the callback; it is not among the callback parameters included in the signature input.

The method must compute the expected signature from all entries other than sig, applying the same sorted-parameter MD5 algorithm and the client's signature_secret, and compare it against the supplied sig. The method must return a Python boolean — True if the supplied signature is valid, and False if it is not.

For instance, given:

params = {
    'a': '1',
    'b': '2',
    'timestamp': '1461605396',
    'sig': '6af838ef94998832dbfc29020b564830'
}

together with signature_secret='secret', the value the method must return is:

True

Task Specification: JWT Authentication for the Voice API in the Nexmo Python Client

Purpose

The Client class of the nexmo Python module must be extended to support application/JWT authentication — using an application ID and an RSA private key — alongside the existing API-key/secret authentication. The Voice API operations under /v1/calls must be added, and all existing client methods, request formats, endpoints, response handling, compatibility aliases, and signature helpers must be preserved. API key and secret credentials must be optional, so that a client intended only for JWT-authenticated APIs can be constructed and used.

Public API Surface

The nexmo module must expose the following:

  • nexmo.__version__, a string that contains the module version.
  • nexmo.Client, the client class that is described below.
  • The exception hierarchy that already exists: nexmo.Error, nexmo.ClientError, nexmo.ServerError, and nexmo.AuthenticationError. AuthenticationError is a kind of ClientError, and both client- and server-side errors are kinds of Error.

Client Construction and Credential Handling

Client.__init__

Keyword arguments must continue to be accepted by the constructor, which must support the following optional arguments:

  • key — the API key.
  • secret — the API secret.
  • application_id — the Nexmo application ID used in JWT claims.
  • private_key — an RSA private key in the form of a PEM-formatted string, used to sign JWTs.
  • signature_secret — the secret that signature and check_signature use.
  • app_name — an optional application name for the User-Agent.
  • app_version — an optional application version for the User-Agent.

API key and secret values that are not supplied directly may continue to come from NEXMO_API_KEY and NEXMO_API_SECRET. Independently of that, the signature secret may continue to come from NEXMO_SIGNATURE_SECRET. Those environment values being absent must not make API key or secret mandatory.

Construction must succeed when key and secret are omitted — the following case included:

client = nexmo.Client(application_id='myid', private_key='abcde')

In particular, construction itself must not require the private key to be parsed or used. With any combination of the optional arguments, construction must also succeed. A client that has a valid application_id and private_key but no API key or secret must be able to make JWT-authenticated Voice API calls.

The User-Agent Header

A User-Agent header must be included in every HTTP request made by the client, whether the request is API-key-authenticated or JWT-authenticated.

  • Unless both application metadata values are supplied, the value is the following:

    nexmo-python/{__version__}/{python_version}

  • When both app_name and app_version are supplied, both components are appended:

    nexmo-python/{__version__}/{python_version}/{app_name}/{app_version}

In the above, {python_version} is the value returned by platform.python_version(). The components are joined with /.

Specification of the Task

Configurable methods for signature hashing

The nexmo module at the top level must continue to expose Client. This change extends the existing request-signing behavior without altering the rest of the client's public API.

The public API

Beyond the options it already has, nexmo.Client must accept these keyword arguments:

client = nexmo.Client(
    key=...,
    secret=...,
    signature_secret=...,
    signature_method=...,
)

The following must be exposed by the client:

Client.signature(params)

Here, params is a dictionary of parameters. The generated signature is returned as a lowercase hexadecimal string.

The method below already exists and must remain compatible with the signing mode that has been selected:

Client.check_signature(params)

It reads the sig parameter that was supplied, excludes sig from the signed parameters, and returns whether it matches the signature generated with that client. Removing sig for validation purposes must not remove it from the caller's dictionary. A sig that is missing or does not match must not validate.

Canonicalization of parameters

The canonicalization behavior the client already has must be retained by all signing modes:

  1. When params has no truthy timestamp value, insert timestamp into that same dictionary using the current Unix time as an integer. A truthy timestamp that already exists is retained.
  2. Handle the parameters in ascending key order.
  3. In each parameter key, replace every & or = with _. Convert each value to its string representation, then perform the same replacements in the value.
  4. Build each component in the form &<safe_key>=<safe_value>, then concatenate the components without separators beyond their leading &. The resulting text is encoded as UTF-8.

As an example, the fixed parameters used below result in this canonical payload:

&a=1&b=2&timestamp=1461605396

The API key and secret do not themselves form part of this payload. Signing makes use of signature_secret; the client's existing support for the signature_secret constructor argument and its NEXMO_SIGNATURE_SECRET environment fallback is retained.

Explicitly specified signing modes

When signature_method is explicitly provided, it must support these values in their exact lowercase form:

  • "md5"
  • "sha1"
  • "sha256"
  • "sha512"

For each explicit mode, generate an HMAC with the UTF-8-encoded signature_secret as its key, the canonical UTF-8 payload as its message, and the configured method as its digest algorithm. Return the lowercase hexadecimal digest of that HMAC. Aliases that are case-insensitive are not required.

With:

key = "nexmo-api-key"
secret = "nexmo-api-secret"
signature_secret = "secret"
params = {"a": "1", "b": "2", "timestamp": "1461605396"}

the required results are as follows:

signature_method Client.signature(params)
"md5" "c15c21ced558c93a226c305f58f902f2"
"sha1" "3e19a4e6880fdc2c1426bfd0587c98b9532f0210"
"sha256" "a321e824b9b816be7c3f28859a31749a098713d39f613c80d455bbaffae1cd24"
"sha512" "812a18f76680fa0fe1b8bd9ee1625466ceb1bd96242e4d050d2cfd9a7b40166c63ed26ec9702168781b6edcf1633db8ff95af9341701004eec3fcf9550572ee8"
Compatibility when the method is omitted

When signature_method is omitted, the legacy signing algorithm must be preserved; the omission must not be treated as explicit signature_method="md5". Legacy signing computes an MD5 digest over the canonical payload with the UTF-8-encoded signature_secret directly following it, instead of using HMAC.

Consequently, with signature_secret="secret" and the fixed parameters above:

client = nexmo.Client(
    key="nexmo-api-key",
    secret="nexmo-api-secret",
    signature_secret="secret",
)

assert client.signature(params) == "6af838ef94998832dbfc29020b564830"

This distinction is deliberate: with "md5" given explicitly, c15c21ced558c93a226c305f58f902f2 is returned, whereas an omitted method returns the legacy value 6af838ef94998832dbfc29020b564830.

When signature_method was omitted, Client.check_signature must likewise continue to validate legacy webhook signatures. As an example, the client above with the omitted method must return True for:

client.check_signature({
    "a": "1",
    "b": "2",
    "timestamp": "1461605396",
    "sig": "6af838ef94998832dbfc29020b564830",
})
Constraints for compatibility

The option being introduced is additive. Existing client construction—including clients that use application credentials without an API key or API secret—and all request, authentication, response, and error behavior that is unrelated must remain unchanged.

Change required

Add the following two methods to the public nexmo.Client API. The existing behavior of the client must remain compatible.

nexmo.Client.get_recording

Method signature:

Client.get_recording(url)
Behavior of the request
  • Make an HTTP GET request to the exact URL that is supplied as url.
  • Include in the request the User-Agent header configured for the client.
Returned value

The return value is the response body, unchanged, as raw binary data:

  • On Python 3, bytes.
  • On Python 2, str.

The response must not be parsed as JSON, nor decoded as text. For instance, if the response body is b'THISISANMP3', the method must return that raw content.

nexmo.Client.submit_sms_conversion

Method signature:

Client.submit_sms_conversion(message_id)
Behavior of the request

  • Issue an HTTP POST request to exactly:

    https://api.nexmo.com/conversions/sms

  • Both of the following fields must be included in the serialized request body:

    • message-id, with a value that preserves the supplied message_id.
    • timestamp.

  • No particular value or format for the timestamp is required; the timestamp field needs only to be present.

As an example, when the method is called with message_id='a-message-id', the serialized body must contain the literal text:

message-id=a-message-id
Handling of a successful response

It is not required for a successful response to contain JSON. Specifically, an HTTP 200 response that has a plain-text body such as OK must allow the method call to complete normally. For such a response, the method must not require JSON decoding or raise a JSON-decoding error.
