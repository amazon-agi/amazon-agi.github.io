01 Extend B018 Check to Module-Level Statements 551 words · source specification

Task Specification: Extend B018 Check to Module-Level Statements

Background

This codebase is a flake8 plugin (a bug-detection linter) that exposes a checker class named BugBearChecker. The checker is constructed with a filename keyword argument pointing to a Python source file, and its run() method yields lint errors discovered in that file.

One of the checks emitted by this plugin is B018. Currently, B018 detects "useless expression" statements — bare value expressions used as statements that have no effect — but only within certain scopes (e.g., class or function bodies). This task requires extending B018 detection so it also applies to statements written directly at module level (the top level of a file).

Public API Surface

No new public API needs to be created. The relevant surface, which already exists and must continue to work as described, is:

  • BugBearChecker — a class constructible as BugBearChecker(filename=<path string>).
  • BugBearChecker.run() — a method that returns an iterable of error tuples. Each error tuple has the form (line, col, message, type), where line is the 1-based line number, col is the 0-based column offset, and message is a string that begins with the error code (e.g. "B018 ...").

Required Behavior

When the checker analyzes a source file, it must emit a B018 error for each module-level statement that consists solely of a bare "useless" value expression. These are top-level statements (column offset 0) whose entire content is a value literal or collection literal that is evaluated and immediately discarded.

Expressions that MUST trigger B018 at module level

A module-level bare-expression statement must be flagged when the expression is one of the following:

  • A numeric literal (integer, float, or complex/imaginary number).
  • A byte-string literal (e.g. b"foo").
  • The named constants True, False, and None.
  • A list literal (e.g. [1, 2]).
  • A set literal (e.g. {1, 2}).
  • A dict literal (e.g. {"foo": "bar"}).
Expressions that MUST NOT trigger B018

The following module-level bare-expression statements must not be flagged:

  • A plain string literal used as a statement (this is treated as a docstring / documentation and is excluded).
  • A formatted string literal (f-string) used as a statement.
Statements that MUST NOT trigger B018
  • Assignment statements and other non-bare-expression statements at module level produce no B018 error.
Error Location
  • Each emitted B018 error must report the line number of the offending statement and a column offset of 0.

Notes

  • This behavior mirrors the existing B018 detection performed in narrower scopes; the change is to apply the same detection to statements at the top level of the module as well.
  • The set of expression kinds that trigger versus suppress B018 (numbers, bytes, named constants, list/set/dict literals trigger; plain and formatted string literals do not) must be exactly as enumerated above.

Concrete Example

Given a source file whose module-level statements are, in order:

a = 2
"str"
f"{int}"
1j
1
1.0
b"foo"
True
False
None
[1, 2]
{1, 2}
{"foo": "bar"}

The checker must emit B018 errors (at column 0) for exactly the statements 1j, 1, 1.0, b"foo", True, False, None, [1, 2], {1, 2}, and {"foo": "bar"}. It must not emit B018 for the assignment a = 2, the plain string "str", or the f-string f"{int}".

02 Extend B017 Check to Detect pytest.raises with a Single Bare Exception 971 words · source specification

Task Specification: Extend B017 Check to Detect pytest.raises with a Single Bare Exception

Background

This project is a flake8 plugin (bugbear) that emits lint warnings identified by codes like B017. The B017 check flags "blind" / overly-broad exception assertions in test code: constructs that assert a block raises Exception (or an equally broad, non-specific exception) without narrowing the expected exception.

Currently, B017 only recognizes the unittest-style self.assertRaises(...) context manager. This task extends B017 so it also recognizes the pytest.raises(...) context manager under the same conditions.

What B017 Flags

B017 targets with statements (context managers) whose context expression is a call that "asserts a raise" using a single, broad exception argument.

A B017 violation is produced when all of the following hold for a context manager item in a with statement:

  1. The context expression is a call to one of the following:
    • self.assertRaises(...) (existing behavior — an attribute call whose method name is assertRaises)
    • pytest.raises(...) (new behavior)
  2. The call is passed exactly one positional argument (the exception type), and that single argument is the broad exception being asserted.
  3. No keyword arguments are passed to the call.

The following must not be flagged:

  • self.assertRaisesRegex(Exception, "...") — a different method name, and it carries a second (regex) argument.
  • pytest.raises(Exception, "Regex is good") — a pytest.raises call carrying more than one argument. (More than one positional argument means the exception is being narrowed / matched, so it is not a blind assertion.)
  • A pytest.raises(...) / self.assertRaises(...) call that has any keyword arguments.

Binding the context manager to a name via as (e.g. with pytest.raises(Exception) as ex:) does not affect whether B017 fires — a single-argument, no-keyword call is still flagged regardless of an as target.

The specific exception type named in the single argument does not matter for flagging purposes — any single positional exception argument (whether a bare name like Exception or a dotted reference like asyncio.CancelledError) triggers the violation, as long as the call has exactly one argument and no keywords.

Error Location and Message

Each violation is reported at the location of the offending with statement (its line and column offset). The error code is B017.

The message text for B017 remains the existing message used for blind-exception assertions (unchanged from current behavior):

B017 assertRaises(Exception): should be considered evil. It raises a broad exception which is difficult to reason about. Please use a more specific exception type or pytest.raises() with `match`, or `except .. as e: assert str(e) == "message"`.

(The exact wording of this message should match whatever the check currently emits; only the set of constructs that trigger it changes.)

Expected Behavior Summary

Given a test-style module containing, within methods of a class, these context managers:

  • with self.assertRaises(Exception): → flagged (existing)
  • with pytest.raises(Exception): → flagged (new)
  • with self.assertRaises(Exception) as ex: → flagged (existing)
  • with pytest.raises(Exception) as pyt_ex: → flagged (new)
  • with self.assertRaisesRegex(Exception, "..."): → not flagged
  • with pytest.raises(Exception, "..."): → not flagged (more than one argument)
  • with self.assertRaises(asyncio.CancelledError): → flagged (existing)
  • with pytest.raises(asyncio.CancelledError): → flagged (new)

Public API

The plugin's public entry point is unchanged. It is invoked as:

  • Class BugBearChecker, constructed with a filename keyword argument (BugBearChecker(filename="path/to/file.py")), importable from the plugin's top-level module (bugbear).
  • Calling .run() on the instance yields the detected violations. Each yielded item is a tuple whose first two elements are the 1-based line number and 0-based column offset of the violation, and whose third element is a message string beginning with the error code (e.g. "B017 ...").

No new public API surface is required; only the internal B017 detection logic must be broadened as described above.

Additional Requirements

  • The requirements below supersede any conflicting statements in the earlier sections of this specification regarding as bindings and the exception type named in the argument.

  • B017 must fire only when the context-manager item has no as binding. A with self.assertRaises(Exception) as ex: or with pytest.raises(Exception) as pyt_ex: statement must not be flagged, even though the call itself has exactly one positional argument and no keywords. Binding the context manager to a name is treated as evidence that the caught exception will be inspected, so it is not a blind assertion.

  • B017 must fire only when the single positional argument is the bare name Exception (an unqualified identifier). Any other argument — including dotted/attribute references such as asyncio.CancelledError, and any other bare exception name — must not trigger B017. In particular, with self.assertRaises(asyncio.CancelledError): and with pytest.raises(asyncio.CancelledError): are both compliant and produce no violation.

  • Consequently, the full set of B017-triggering constructs is exactly: a with statement item whose context expression is a call to self.assertRaises (or any attribute call named assertRaises) or to pytest.raises, with exactly one positional argument that is the bare name Exception, no keyword arguments, and no as binding on that item.

  • For a module containing, in order, the following context managers inside class methods:

    1. with self.assertRaises(Exception): — flagged
    2. with pytest.raises(Exception): — flagged
    3. with self.assertRaises(Exception) as ex: — not flagged
    4. with pytest.raises(Exception) as pyt_ex: — not flagged
    5. with self.assertRaisesRegex(Exception, "..."): — not flagged
    6. with pytest.raises(Exception, "..."): — not flagged
    7. with self.assertRaises(asyncio.CancelledError): — not flagged
    8. with pytest.raises(asyncio.CancelledError): — not flagged

    the checker must emit exactly two B017 violations — one for each of the first two items — and nothing else.

  • Violations yielded by BugBearChecker.run() must appear in source order (ascending line number). Each violation's reported position is the with statement's own 1-based line number and 0-based column offset (e.g., a with statement indented inside a method body at 8 spaces reports column offset 8).

  • The message string for each B017 violation must begin with B017 followed by the existing blind-exception message text, unchanged.

03 Add a new lint check, B028, to the bugbear module. 1591 words · rewritten by GPT-5.6-sol

Objective

Add a new lint check, B028, to the bugbear module. B028 identifies f-string replacement fields that are immediately surrounded by matching literal quote characters and whose format behavior satisfies the equivalence rules below. The diagnostic recommends using !r instead of manually placing quotes around the interpolated value.

Public API and integration

The following names must remain directly importable from bugbear:

  • B028: an error factory/namedtuple-style object consistent with the module's other Bxxx errors. It must support construction as B028(lineno, col, vars=(value_source,)), where value_source is the representation described below. Its associated diagnostic message must begin with B028.
  • BugBearVisitor: the AST visitor used by the checker. It must accept construction with BugBearVisitor(filename="", lines=""), expose a mutable errors list that callers can replace with [], and support the standard visit(tree) entry point. Visiting a tree must append B028 errors to that list.
  • BugBearChecker: its run() method must include B028 findings in the same adapted output and ordering conventions as the existing AST-based checks.

B028 is a normal Bxxx check, not an optional B9xx check. It must coexist with all existing diagnostics; no behavior of any other check is to change.

Supported Python versions

B028 detection is required only on Python 3.8 and newer. All B028-specific detection and compatibility logic must be guarded so that the module continues to operate on earlier supported Python versions. On Python versions earlier than 3.8, no B028 diagnostic is required.

Quote-wrapped replacement fields

For each f-string, inspect its replacement fields in source order. A field is a quote-wrapped candidate only when all of the following are true:

  1. The literal f-string text immediately before the field ends in either ' or ".
  2. The literal text immediately after the field starts with the same character.
  3. There is no intervening literal character between either quote and the replacement field.

The quote characters are part of the f-string's rendered literal text, not the delimiters used to spell the string literal. Both single-quote and double-quote wrappers qualify. For example, each of the following contains a candidate around var:

f"begin '{var}' end"
f"'{var}' end"
f"begin '{var}'"
f'begin "{var}" end'
f'"{var}" end'
f'begin "{var}"'

Multiple quote characters do not suppress the check, so f'"""{var}"""' still has a quote-wrapped field.

Mixed or non-adjacent wrappers are not candidates:

f"'{var}\""       # different quote characters
f'" {var} "'       # spaces on both sides
f'"{var} "'        # space before the closing quote
f'" {var}"'        # space after the opening quote
Stateful quote ownership

A literal quote used as the closing quote of a structurally matched quote-wrapped field is consumed by that match. The same character cannot also become the opening quote of the next field. Consumption is determined by the literal quote match itself, before conversion and format-specifier exclusions determine whether the matched field produces a diagnostic.

Consequently:

f'"{a}"{b}"'       # only a is a candidate
f'"{a}""{b}"'     # both a and b are candidates
f'"{a}" and "{b}"'  # both a and b are candidates

In the second example, the two quote characters between the fields have separate roles: the first closes a, while the second opens b. Likewise, after the first quote in the middle literal text " and " has been consumed as a closing quote, its final quote remains available to open the next field.

Pending state must also be reset after an unsuccessful match. If an opening quote precedes a field but the following literal text does not start with the same quote, that field is not reported and the stale opening quote must not affect a later field. Any unconsumed trailing quote in the intervening literal text may independently open the next field. Thus, in:

f'"{a}abc "{b}"'

a is not a candidate, while b is.

Two directly adjacent fields do not provide one another with literal quotes. For example, f'"{a}{b}"' produces no B028 finding.

Conversion requirement

Do not report a candidate that already has the !r conversion. A field with no conversion or with another legal conversion, including !s or !a, remains eligible, subject to the format-specifier rules below. Only !r causes the conversion-based suppression. For example:

f'"{var!r}"'  # no B028
f'"{var!s}"'  # B028

Format-specifier eligibility

The format-specifier decision must be based on the complete rendered text, including the literal quotes that the proposed !r would replace.

Nested replacement fields

If the format specifier itself contains any nested replacement field, do not emit B028. Such specs are not to be parsed or evaluated for this check. This includes:

f'"{var:{var}}"'
f'"{var:5{var}}"'
f'"{var:{var}s}"'
Static format specs

For a format specifier containing only literal text, let spec be that text. A colon with no text after it uses spec == ""; absence of a colon has the same format-eligibility result.

Apply these exclusions:

  1. If spec is invalid for formatting a string, do not emit B028.
  2. If the standard format-specification mini-language's 0 option is present before the optional width field, do not emit B028. Its presence signals a likely intended numeric value even on Python versions where it is accepted for strings and has no visible effect.
  3. If spec contains any explicit width field, do not emit B028, even when that width is too short to add padding or otherwise happens to render identically for the probe value. This applies to every width, including 1, 5, and 9.

A digit used as a fill character is neither a width nor the 0 option. For example, in 5<, 5 is the fill character and < is the alignment; there is no width field. Similarly, the zero in 0< is a fill character, not the zero option. Such specs are not excluded merely for containing a digit.

For every remaining valid spec, use this exact observable equivalence rule with the representative string "hello":

plain = ("'{:" + spec + "}'").format("hello")
with_repr = ("{!r:" + spec + "}").format("hello")

Emit B028 exactly when plain == with_repr. Otherwise, do not emit it. The single quotes in the plain format string are essential: they represent the existing literal wrappers and make the comparison cover the complete output. This canonical single-quote probe is used for format eligibility even when the source field is wrapped in double quotes; the source quote style affects quote matching, but not this equivalence calculation.

This decision procedure governs all static combinations of fill, alignment, sign, z, alternate form, zero option, width, grouping, precision, and presentation type.

Required format-spec outcomes

Subject to quote matching and conversion rules, B028 is emitted for:

  • no format specifier;
  • an explicitly empty spec, as in f'"{var:}"';
  • alignment-only specs <, >, and ^;
  • fill/alignment with no width, such as 5<;
  • the explicit string presentation type s;
  • other valid, width-free specs for which the two complete renderings above are equal, such as .8 for the representative value;
  • !s combined with an otherwise eligible spec.

B028 is not emitted for:

  • any explicit width, including 1, 5, or 9, whether or not it visibly pads the representative value;
  • the 0 option before the optional width;
  • a valid width-free spec for which the complete renderings differ, such as a precision that truncates the plain and repr-converted strings differently;
  • sign options +, -, or space when they are invalid for strings;
  • integer presentation types such as b or x;
  • floating-point or percentage presentation types such as e or %;
  • = alignment, the z option, or any other spec invalid for strings;
  • any spec containing a nested replacement field.

Diagnostics

Number and order

Emit one B028 error for each eligible replacement field. If one f-string has several eligible fields, emit a separate error for each field in source order. Quote consumption applies before deciding whether a later field is independently eligible.

Location

Every B028 generated for an f-string must use the lineno and col_offset assigned by the AST to that f-string's JoinedStr node as a whole. It must not use the location of the individual replacement expression. Therefore, all B028 errors from one f-string share a location. This also applies to an f-string formed by implicit concatenation across physical lines: the location is the AST location of the resulting combined JoinedStr.

vars value representation

The vars tuple contains exactly one string representing the flagged field's expression. Use the following representation rules:

  • simple name: var;
  • attribute chain: var.__str__ or var.__str__.__repr__;
  • call: foo();
  • string constant: 'hello', using Python's repr-style quoting;
  • singleton/boolean constants: None, True;
  • on Python 3.9 and newer, use AST unparsing for other expressions, so a binary addition is 3 + 5 and an ellipsis is ...;
  • on Python 3.8, when faithful unparsing is unavailable, use the AST node type name as the fallback, so those same examples are BinOp and Ellipsis respectively.

For example, eligible fields in the following f-strings have vars values ("'hello'",), ("foo()",), and ("var.__str__.__repr__",):

f'a "{"hello"}" b'
f'a "{foo()}" b'
f'"{var.__str__.__repr__}"'

Additional non-diagnostic and robustness requirements

  • A replacement field lacking either adjacent matching quote is not reported.
  • Literal constants adjacent to a field trigger matching only when their relevant character is ' or ". Inputs such as f'5{var}"' and a field between unlike quote constants must not crash the checker.
  • A failed candidate must not leave state that causes a later field to be reported spuriously.
  • Existing checks, checker loading, filtering, and error adaptation behavior must remain unchanged apart from the addition of B028 findings.

Overview

flake8-bugbear is a Flake8 plugin that emits lint diagnostics. This task changes only the behavior of checks B017 and B906. All other checks and existing configuration behavior must remain unchanged.

The public checker API must remain compatible:

  • Construct the checker as bugbear.BugBearChecker(filename=...).
  • Iterating BugBearChecker.run() yields Flake8-compatible tuples of the form (line, column, message, type).
  • Diagnostic lines are one-based and columns are zero-based.
  • The existing diagnostic messages and codes must remain unchanged; in particular, the message for each diagnostic begins with B017 or B906 as appropriate.

B017 — overly broad exception assertions

B017 identifies unbound context-manager uses of self.assertRaises(Exception) and pytest.raises(Exception) that can allow a test to pass because of an unrelated exception.

Matching context-manager items

Apply B017 to ordinary with statements. Each item in a multi-item with statement must be considered, not only the first item. A context-manager item qualifies only when all of the following are true:

  1. Its context expression is a call whose callable is syntactically one of:
    • self.assertRaises, with the bare receiver name self and the exact method name assertRaises; or
    • pytest.raises, with the bare receiver name pytest and the exact method name raises.
  2. The first positional argument is the bare identifier Exception. Qualified names and other expressions do not count.
  3. The context-manager result is not bound with an as target.
  4. The call has no explicitly named match keyword argument. The presence of match suppresses B017 regardless of the value supplied for it.

The exception type is the meaningful exception-narrowing argument. Do not suppress B017 merely because a non-narrowing argument is also present. In particular, msg= on self.assertRaises does not make the expected exception more specific.

These forms must emit B017:

with self.assertRaises(Exception):
    operation()

with self.assertRaises(Exception, msg="generic exception"):
    operation()

with pytest.raises(Exception):
    operation()
Exclusions

Do not emit B017 in any of the following cases:

  • The first positional exception argument is not the bare identifier Exception. This includes specific exceptions such as ZeroDivisionError, qualified types such as asyncio.CancelledError, and any other specific or qualified expression.

  • The callable is not exactly one of the two supported forms. For example, self.assertRaisesRegex(...), another object's assertRaises(...), or a renamed/aliased pytest object does not qualify.

  • pytest.raises(Exception, match=...) is used.

  • The context-manager result is bound, including both of these forms:

    with self.assertRaises(Exception) as exc:
    operation()

with pytest.raises(Exception) as exc:
    operation()

  • The call is not a context-manager expression of an ordinary with statement. Calls used as standalone expressions or in any other context are outside B017, regardless of their exception type or remaining arguments. For example, neither of these emits B017:

    self.assertRaises(Exception, lambda x, y: x / y, 1, y=0)
pytest.raises(Exception, lambda x, y: x / y, 1, y=0)
