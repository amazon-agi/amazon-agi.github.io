01 Making the B018 Check Also Cover Module-Level Statements 622 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Making the B018 Check Also Cover Module-Level Statements

Background

The codebase at hand is a bug-detection linter shipped as a flake8 plugin, and it exposes a checker class that goes by the name BugBearChecker. The checker gets constructed with a filename keyword argument that points to a Python source file, and the lint errors discovered in that file are yielded by its run() method.

Among the checks this plugin emits is B018. At present, B018 catches "useless expression" statements, meaning bare value expressions that serve as statements and have no effect, but it does so only within certain scopes (e.g., class or function bodies). This task requires an extension of B018 detection so that it also applies to statements written directly at module level (the top level of a file).

Public API Surface

There is no need to create any new public API. The surface that matters already exists and must keep working as described; it consists of:

  • BugBearChecker — a class that can be constructed as BugBearChecker(filename=<path string>).
  • BugBearChecker.run() — a method that returns an iterable of error tuples when invoked. Each error tuple takes the shape (line, col, message, type): line is the 1-based line number, col is the 0-based column offset, and message is a string starting with the error code (e.g. "B018 ...").

Required Behavior

Whenever a source file is analyzed, the checker must emit a B018 error for each module-level statement whose content is solely a bare "useless" value expression. In other words, these are statements at the top level (column offset 0) made up entirely of a value literal or a collection literal, evaluated and immediately discarded.

Expressions at module level that MUST trigger B018

A bare-expression statement appearing at module level must be flagged when its expression is one of the following:

  • A numeric literal (an integer, a float, or a complex/imaginary number).
  • A byte-string literal (for instance b"foo").
  • The named constants True, False, and None.
  • A list literal (for instance [1, 2]).
  • A set literal (for instance {1, 2}).
  • A dict literal (for instance {"foo": "bar"}).
Expressions that MUST NOT trigger B018

At module level, a bare-expression statement must not be flagged when it takes one of the following forms:

  • A plain string literal serving as a statement (it counts as a docstring / documentation and is therefore excluded).
  • A statement that is a formatted string literal (an f-string).
Statements that MUST NOT trigger B018
  • At module level, assignment statements — as well as any other statements that are not bare expressions — produce no B018 error.
Location of the Error
  • Each B018 error that gets emitted must report the offending statement's line number together with a column offset of 0.

Notes

  • The B018 detection that already exists for narrower scopes is what this behavior mirrors; what changes is that the same detection is to be applied to statements at the top level of the module as well.
  • How expression kinds divide between triggering B018 and suppressing it (numbers, bytes, named constants, list/set/dict literals trigger; plain and formatted string literals do not) must match the enumeration above exactly.

Concrete Example

Take a source file with these module-level statements, in this order:

a = 2
"str"
f"{int}"
1j
1
1.0
b"foo"
True
False
None
[1, 2]
{1, 2}
{"foo": "bar"}

For exactly the following statements, the checker must emit B018 errors at column 0: 1j, 1, 1.0, b"foo", True, False, None, [1, 2], {1, 2}, and {"foo": "bar"}. B018 must not be emitted for the assignment a = 2, the plain string "str", or the f-string f"{int}".

02 Teach B017 to Detect pytest.raises Carrying a Single Bare Exception 1070 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Teach B017 to Detect pytest.raises Carrying a Single Bare Exception

Context

What we have here is a flake8 plugin named bugbear; the lint warnings it emits carry codes such as B017. Through the B017 check, "blind" / overly-broad exception assertions get flagged in test code — constructs asserting that a block raises Exception (or an exception equally broad and non-specific) without the expected exception being narrowed.

For now, B017's recognition covers only the unittest-style self.assertRaises(...) context manager. This task extends B017 so that it also picks up the pytest.raises(...) context manager when the same conditions apply.

What Triggers B017

The focus of B017 is with statements (context managers) whose context expression consists of a call that "asserts a raise" and that takes a single, broad exception argument.

A B017 violation is produced when, for a context manager item in a with statement, all of the following are true:

  1. The call making up the context expression targets one of the following:
    • self.assertRaises(...) (already-supported behavior — an attribute call that goes by the method name assertRaises)
    • pytest.raises(...) (behavior this task adds)
  2. Exactly one positional argument (the exception type) is supplied to the call, and that lone argument is the broad exception being asserted.
  3. The call is handed no keyword arguments.

These must not be flagged:

  • self.assertRaisesRegex(Exception, "...") — the method name differs here, and a second (regex) argument is present as well.
  • pytest.raises(Exception, "Regex is good") — a pytest.raises call to which more than one argument is given. (Once there is more than one positional argument, the exception is being narrowed / matched, hence no blind assertion.)
  • Any pytest.raises(...) / self.assertRaises(...) call to which keyword arguments are supplied.

Whether B017 fires is not affected when the context manager gets bound to a name via as (e.g. with pytest.raises(Exception) as ex:) — a call with a single argument and no keywords is still flagged, no matter whether an as target is present.

For flagging purposes it makes no difference which specific exception type the single argument names — any single positional exception argument (be it a bare name like Exception or a dotted reference like asyncio.CancelledError) triggers the violation, provided the call has exactly one argument and no keywords.

Error Position and Message

The reporting position for every violation is the offending with statement itself (its line and column offset). The code used for the error is B017.

B017's message text continues to be the existing one used for blind-exception assertions (current behavior left untouched):

B017 assertRaises(Exception): should be considered evil. It raises a broad exception which is difficult to reason about. Please use a more specific exception type or pytest.raises() with `match`, or `except .. as e: assert str(e) == "message"`.

(As far as this message's wording goes, it should match whatever the check currently emits; what changes is only the set of constructs that trigger it.)

Expected Outcomes at a Glance

Take a test-style module where these context managers appear inside methods of a class:

  • with self.assertRaises(Exception): → flagged (existing)
  • with pytest.raises(Exception): → flagged (new)
  • with self.assertRaises(Exception) as ex: → flagged (existing)
  • with pytest.raises(Exception) as pyt_ex: → flagged (new)
  • with self.assertRaisesRegex(Exception, "..."): → not flagged
  • with pytest.raises(Exception, "..."): → not flagged (more than one argument)
  • with self.assertRaises(asyncio.CancelledError): → flagged (existing)
  • with pytest.raises(asyncio.CancelledError): → flagged (new)

Public-Facing API

Nothing about the plugin's public entry point changes. Invocation works like this:

  • The class BugBearChecker, which is constructed with a filename keyword argument (BugBearChecker(filename="path/to/file.py")) and which is importable from the plugin's top-level module (bugbear).
  • When .run() is called on the instance, the detected violations are what it yields. Every item yielded is a tuple: its first two elements hold the violation's 1-based line number and 0-based column offset, and its third element is a message string that starts with the error code (e.g. "B017 ...").

Adding to the public API surface is not required; the internal B017 detection logic is the only thing that must be broadened, as described above.

Supplementary Requirements

  • Should any earlier section of this specification conflict with what follows on the subjects of as bindings and the exception type named in the argument, the requirements below take precedence.

  • An as binding on the context-manager item must be absent for B017 to fire — B017 fires only without one. A with self.assertRaises(Exception) as ex: or with pytest.raises(Exception) as pyt_ex: statement must not be flagged, even though the call itself carries exactly one positional argument and no keywords. The reasoning: giving the context manager a name is treated as evidence that the caught exception will be inspected, hence no blind assertion.

  • For B017 to fire, the single positional argument must be the bare name Exception (an unqualified identifier) — nothing else qualifies. Any other argument must not trigger B017; that covers dotted/attribute references such as asyncio.CancelledError and equally any other bare exception name. In particular, with self.assertRaises(asyncio.CancelledError): and with pytest.raises(asyncio.CancelledError): are both compliant — neither produces a violation.

  • The full set of constructs that trigger B017 is therefore exactly: a with statement item whose context expression is a call to self.assertRaises (or to any attribute call named assertRaises) or else to pytest.raises, which receives exactly one positional argument — the bare name Exception — receives no keyword arguments, and whose item has no as binding.

  • Consider a module whose class methods contain the context managers below, in this order:

    1. with self.assertRaises(Exception): — flagged
    2. with pytest.raises(Exception): — flagged
    3. with self.assertRaises(Exception) as ex: — not flagged
    4. with pytest.raises(Exception) as pyt_ex: — not flagged
    5. with self.assertRaisesRegex(Exception, "..."): — not flagged
    6. with pytest.raises(Exception, "..."): — not flagged
    7. with self.assertRaises(asyncio.CancelledError): — not flagged
    8. with pytest.raises(asyncio.CancelledError): — not flagged

    the checker must emit exactly two B017 violations — one for each of the first two items — and nothing else.

  • The violations that BugBearChecker.run() yields must show up in source order (with line numbers ascending). For every violation, the position reported is the with statement's own 1-based line number and 0-based column offset (to illustrate: a with statement indented 8 spaces inside a method body reports column offset 8).

  • Each B017 violation comes with a message string that must begin with B017 and then continue with the existing blind-exception message text, kept unchanged.

03 A new lint check named B028 is to be introduced into the bugbear module. 1837 words · rewritten by GPT-5.6-sol, reworded by GLM-5.3-Flash

Task Description

Goal

A new lint check named B028 is to be introduced into the bugbear module. B028 flags f-string replacement fields that matching literal quote characters immediately surround, provided their format behavior satisfies the equivalence rules below. The diagnostic recommends using !r in place of quotes placed by hand around the interpolated value.

Public API and integration

Direct importability from bugbear must be preserved for these names:

  • B028: an error factory/namedtuple-style object built in the same style as the module's other Bxxx errors. Constructing it as B028(lineno, col, vars=(value_source,)) must be supported, value_source being the representation described below. Its associated diagnostic message must start with B028.
  • BugBearVisitor: the AST visitor on which the checker depends. Construction with BugBearVisitor(filename="", lines="") must be accepted by it; it must expose a mutable errors list that callers can replace with []; and the standard visit(tree) entry point must be supported. Whenever a tree is visited, B028 errors must be appended to that list.
  • BugBearChecker: its run() method must include B028 findings, keeping to the same adapted output and ordering conventions as the existing AST-based checks.

B028 counts as a normal Bxxx check rather than an optional B9xx check. It must coexist with all existing diagnostics; no behavior belonging to any other check is to change.

Python versions supported

Only from Python 3.8 onwards is B028 detection required. All B028-specific detection and compatibility logic must sit behind guards, so that the module keeps operating on earlier supported Python versions. For Python versions older than 3.8, no B028 diagnostic is required.

Quote-wrapped replacement fields

For every f-string, its replacement fields are to be inspected in source order. Only when the conditions below all hold does a field count as a quote-wrapped candidate:

  1. The literal f-string text immediately preceding the field ends in either ' or ".
  2. The literal text coming immediately after the field begins with that same character.
  3. Between either quote and the replacement field, no literal character intervenes.

These quote characters belong to the f-string's rendered literal text; they are not the delimiters with which the string literal is spelled. Wrappers of both the single-quote and the double-quote kind qualify. To illustrate, a candidate surrounds var in every one of the following:

f"begin '{var}' end"
f"'{var}' end"
f"begin '{var}'"
f'begin "{var}" end'
f'"{var}" end'
f'begin "{var}"'

The check is not suppressed by multiple quote characters, so f'"""{var}"""' still contains a quote-wrapped field.

Wrappers that are mixed or non-adjacent do not count as candidates:

f"'{var}\""       # different quote characters
f'" {var} "'       # spaces on both sides
f'"{var} "'        # space before the closing quote
f'" {var}"'        # space after the opening quote
Stateful ownership of quotes

When a structurally matched quote-wrapped field takes a literal quote as its closing quote, the match consumes that quote. The same character cannot also double as the opening quote of the next field. What determines consumption is the literal quote match itself; only afterwards do the conversion and format-specifier exclusions come into play, determining whether the matched field produces a diagnostic.

As a consequence:

f'"{a}"{b}"'       # only a is a candidate
f'"{a}""{b}"'     # both a and b are candidates
f'"{a}" and "{b}"'  # both a and b are candidates

Consider the second example: the two quote characters located between the fields play distinct roles — the first closes a, and the second opens b. Along the same lines, once the first quote inside the middle literal text " and " has been consumed as a closing quote, its final quote stays available for opening the next field.

After an unsuccessful match, the pending state must also be reset. If a field is preceded by an opening quote but the literal text following it does not start with the same quote, that field goes unreported, and the stale opening quote must not affect a later field. Any trailing quote left unconsumed within the intervening literal text may open the next field in its own right. Hence, in:

f'"{a}abc "{b}"'

a does not qualify as a candidate, but b does.

Literal quotes are not provided to one another by two fields that sit directly adjacent. For instance, f'"{a}{b}"' gives rise to no B028 finding.

Conversion requirement

A candidate that already carries the !r conversion must not be reported. Fields that have no conversion, or that have another legal conversion — !s and !a are two examples — stay eligible, with the format-specifier rules below still applying. !r is the only conversion that triggers the conversion-based suppression. For example:

f'"{var!r}"'  # no B028
f'"{var!s}"'  # B028

Format-specifier eligibility

The decision about the format specifier must rest on the complete rendered text, and that text includes the literal quotes the proposed !r would replace.

Nested replacement fields

B028 must not be emitted when the format specifier itself contains any nested replacement field. For this check, such specs are neither to be parsed nor to be evaluated. Examples falling under this:

f'"{var:{var}}"'
f'"{var:5{var}}"'
f'"{var:{var}s}"'
Static format specs

Take a format specifier made up of nothing but literal text, and name its text spec. A colon followed by no text means spec == "" applies; when no colon appears at all, the format-eligibility outcome comes out the same.

These exclusions apply:

  1. When spec turns out to be invalid for formatting a string, B028 must not be emitted.
  2. When the 0 option defined by the standard format-specification mini-language appears before the optional width field, B028 must not be emitted. Its presence signals that a numeric value was probably intended, even on Python versions where strings accept it and it has no visible effect.
  3. When any explicit width field appears in spec, B028 must not be emitted — even if that width is too short to add padding or otherwise happens to render identically for the probe value. Every width falls under this, 1, 5, and 9 included.

When a digit plays the role of fill character, it is neither a width nor the 0 option. In 5<, for example, 5 acts as the fill character and < as the alignment; no width field exists there. The zero in 0< behaves the same way: it is a fill character, not the zero option. The mere presence of a digit is not, on its own, a reason to exclude such specs.

Every remaining valid spec is to be put through this exact observable equivalence rule, with "hello" as the representative string:

plain = ("'{:" + spec + "}'").format("hello")
with_repr = ("{!r:" + spec + "}").format("hello")

B028 is emitted exactly when plain == with_repr; every other outcome means B028 is not emitted. Within the plain format string, the single quotes play an essential part: they stand in for the existing literal wrappers, so the comparison spans the complete output. Even for a source field wrapped in double quotes, this canonical single-quote probe is what format eligibility uses; quote matching is affected by the source quote style, but this equivalence calculation is not.

All static combinations of fill, alignment, sign, z, alternate form, zero option, width, grouping, precision, and presentation type are governed by this decision procedure.

Required format-spec outcomes

Provided the quote matching and conversion rules are satisfied, B028 is emitted for:

  • the absence of a format specifier;
  • a spec that is explicitly empty, as in f'"{var:}"';
  • specs holding alignment and nothing else: <, >, and ^;
  • fill/alignment where no width appears, 5< being one case;
  • the explicit presentation type for strings, s;
  • other valid specs free of width for which the two complete renderings above are equal, .8 applied to the representative value being one such case;
  • an otherwise eligible spec put together with !s.

B028 is not emitted in the following cases:

  • any explicit width (with 1, 5, or 9 among them), whether or not the representative value is visibly padded by it;
  • the 0 option when it comes before the optional width;
  • a valid spec free of width for which the complete renderings differ — for example, a precision that truncates the plain and repr-converted strings in different ways;
  • the sign options +, -, or space, in the cases where they are invalid for strings;
  • integer presentation types, b or x for instance;
  • presentation types of the floating-point or percentage kind, e or % for instance;
  • the = alignment, the z option, or any other spec that is invalid for strings;
  • any spec with a nested replacement field inside it.

Diagnostics

Count and order

One B028 error is to be emitted for every eligible replacement field. Should a single f-string contain several eligible fields, a separate error is emitted for each of them, in source order. The question of whether a later field is independently eligible is decided after quote consumption has applied.

Location

For every B028 emitted for an f-string, the lineno and col_offset must be the ones the AST assigns to that f-string's JoinedStr node as a whole. The location of the individual replacement expression must not be used instead. All B028 errors produced by one f-string therefore have a single shared location. The same requirement covers an f-string that implicit concatenation across physical lines has formed: its location is the AST location of the combined JoinedStr that results.

Representation of the vars value

Exactly one string, representing the flagged field's expression, is what the vars tuple holds. These representation rules are to be used:

  • a simple name maps to var;
  • an attribute chain maps to var.__str__ or var.__str__.__repr__;
  • a call maps to foo();
  • a string constant maps to 'hello', with Python's repr-style quoting applied;
  • the singleton/boolean constants map to None and True;
  • on Python 3.9 and newer, AST unparsing handles other expressions, so a binary addition comes out as 3 + 5 and an ellipsis as ...;
  • on Python 3.8, when faithful unparsing is unavailable, the AST node type name is what serves as the fallback, so those same examples come out as BinOp and Ellipsis respectively.

As an illustration, the eligible fields inside the following f-strings carry the vars values ("'hello'",), ("foo()",), and ("var.__str__.__repr__",):

f'a "{"hello"}" b'
f'a "{foo()}" b'
f'"{var.__str__.__repr__}"'

Further non-diagnostic and robustness requirements

  • No report is made for a replacement field missing either of the adjacent matching quotes.
  • Matching is triggered by literal constants next to a field only in the case that their relevant character is ' or ". The checker must not crash on inputs like f'5{var}"' or on a field placed between unlike quote constants.
  • State left behind by a candidate that failed must not result in a later field being reported spuriously.
  • Apart from the addition of B028 findings, the behavior of existing checks, checker loading, filtering, and error adaptation must stay unchanged.

Specification of the Task

Summary

As a Flake8 plugin, flake8-bugbear emits lint diagnostics. This task modifies only the behavior of the checks B017 and B906. Every other check, along with the existing configuration behavior, must remain unchanged.

The public API of the checker must remain compatible:

  • The checker is constructed as bugbear.BugBearChecker(filename=...).
  • Iterating over BugBearChecker.run() yields Flake8-compatible tuples with the shape (line, column, message, type).
  • Diagnostic lines are one-based, and columns are zero-based.
  • The existing diagnostic messages and codes must remain unchanged; in particular, each diagnostic's message begins with B017 or B906, as appropriate.

B017 — exception assertions that are overly broad

For a file that contains correct and incorrect method definitions, the diagnostics required are exactly:

  • B902(22, 17, vars=("'i_am_special'", "instance", "self"))
  • B902(24, 30, vars=("'cls'", "instance", "self"))
  • B902(26, 4, vars=("(none)", "instance", "self"))
  • B902(29, 12, vars=("'self'", "class", "cls"))
  • B902(31, 22, vars=("*args", "instance", "self"))
  • B902(36, 30, vars=("**kwargs", "instance", "self"))
  • B902(38, 32, vars=("*, self", "instance", "self"))
  • B902(40, 44, vars=("*, self", "instance", "self"))
  • B902(52, 17, vars=("'self'", "metaclass instance", "cls"))
  • B902(55, 20, vars=("'cls'", "metaclass class", "metacls"))

These same diagnostics (identical positions and vars) must also hold when the signatures in an equivalent file use positional-only parameter syntax (/) — adding a trailing positional-only marker must not change which methods are flagged, the reported positions, or the contextual values.

B903 — Class that could be a data class / namedtuple

A class whose body only assigns to instance attributes in __init__, with nothing else meaningful done, must be flagged — the suggestion being that it could be a namedtuple or dataclass. When a class also defines additional methods, it must NOT be flagged. Report on the class definition line, at column 0.

In the relevant file, the diagnostics required are exactly:

  • B903(31, 0)
  • B903(37, 0)

Criteria for acceptance

For each of the input files described above, list(BugBearChecker(filename=...).run()) — after being filtered to the relevant error code(s) — must equal exactly the set of diagnostics listed for that check: same line, same column, same code, and (for B902) same contextual vars. All supported Python versions must satisfy this — Python 3.12 specifically included, and there the previous node-stack name/attribute collision must no longer occur.

Beyond the diagnostics listed, no new ones may be produced for these inputs; likewise, none of the listed diagnostics may be missing.
