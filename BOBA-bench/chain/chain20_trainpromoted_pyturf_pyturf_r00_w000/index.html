Task: Implement Helper Functions for GeoJSON Features

Summary

Create a module at turf/helpers/_features.py that provides factory functions for building GeoJSON Feature and FeatureCollection objects. The objects built by these functions give both attribute-based and dictionary-based access to their data, and the functions perform input validation.

Public API

These are the functions that the module turf.helpers._features must expose:

point(coordinates, properties=None, ...)
line_string(coordinates, properties=None, ...)
polygon(coordinates, properties=None, ...)
multi_point(coordinates, properties=None, ...)
multi_line_string(coordinates, properties=None, ...)
multi_polygon(coordinates, properties=None, ...)
points(list_of_coordinates, properties=None, options=None, ...)
line_strings(list_of_coordinates, properties=None, options=None, ...)
polygons(list_of_coordinates, properties=None, options=None, ...)

Structure of the Objects

Feature Objects

A Feature is what point, line_string, polygon, multi_point, multi_line_string, and multi_polygon return. It must support attribute access:

  • .type — holds the string "Feature".
  • .properties — a dictionary. When no properties argument is supplied, this must be an empty dict {}. In all other cases it holds the supplied dictionary (accessible both as a whole and by key, e.g. feature.properties["name"]).
  • .geometry — a geometry object that supports attribute access:
    • .type — a string naming the geometry type (see below).
    • .coordinates — the coordinate data, stored as given (nesting preserved). It must compare equal (==) to the input coordinate list.
FeatureCollection Objects

A FeatureCollection is what points, line_strings, and polygons return. It must support attribute access:

  • .features — a list of Feature objects, one for each input coordinate entry. len(...) returns the count.
  • .id — the value supplied through the options argument's "id" key (see below).
  • Each Feature in .features carries the shared properties dict that was passed to the collection function, accessible by key (e.g. .features[0].properties["foo"]).

Geometry Type per Function

Function geometry .type
point "Point"
line_string "LineString"

Details for Each Function

point(coordinates, properties=None)
  • coordinates is a position: a list of exactly two numbers, [lng, lat].
  • The .coordinates of the resulting geometry preserves this list, so coordinates[0] and coordinates[1] are the two numbers.
line_string(coordinates, properties=None)
  • coordinates is a list of two or more positions, each one a [lng, lat] pair.
polygon(coordinates, properties=None)
  • coordinates is a list of LinearRings, and each LinearRing is a list of positions.
  • Each ring must contain four or more positions, and its first and last position must be equal (a closed ring).
multi_point(coordinates, properties=None)
  • coordinates is a list made up of positions.
multi_line_string(coordinates, properties=None)
  • coordinates is a list of LineStrings, each one a list of two or more positions.
multi_polygon(coordinates, properties=None)
  • coordinates is a list of Polygons, each one a list of LinearRings (with every ring following the polygon ring rules given above: four or more positions, closed).
points(list_of_coordinates, properties=None, options=None)
line_strings(list_of_coordinates, properties=None, options=None)
polygons(list_of_coordinates, properties=None, options=None)
  • list_of_coordinates is a list in which each entry is a valid coordinate structure for the corresponding singular type.
  • One Feature is built per entry (using the singular helper's rules), and the Features are collected into a FeatureCollection.
  • The properties dict is shared by all generated features.
  • The options argument is a dict, and its "id" key becomes the collection's .id.

Validation and Error Behaviour

Calling a function with invalid input must raise an exception. Each exception message must contain the substring specified for its case.

  • Required coordinates argument missing (calling point(), line_string(), polygon() with no arguments): an exception must be raised.

  • point:

    • The coordinates are not a valid 2-element position (e.g. [1]): the message contains "[lng, lat]".
    • The coordinate values are not numeric (e.g. [1, "xyz"]): the message contains "invalid".

  • line_string:

    • Fewer than two positions are supplied (e.g. [[5, 10]]): the message contains "two or more".
    • Coordinate values that are not numeric (e.g. [["xyz", 10], [1, 4]]): the message contains "invalid".

  • polygon:

    • The coordinates are not a list of LinearRings (e.g. the string "xyz"): the message contains "list of LinearRing".
    • A ring is not a list of positions (e.g. ["xyz"]): the message contains "list of Positions".
    • A ring has fewer than four positions (e.g. [[[5, 10], [20, 40], [40, 0]]]): the message contains "4 or more Positions".
    • A ring's first and last positions are not equal (e.g. [[[5, 10], [20, 40], [40, 0], [2, 3]]]): the message contains "not equivalent".

  • multi_line_string:

    • Any contained LineString has fewer than two positions (e.g. [[[0, 0]], [[5, 0], [15, 8]]]): the message contains "two or more".

  • multi_polygon:

    • Any ring contained in the input whose first and last positions are not equal: the message contains "not equivalent".
    • Any ring contained in the input that has fewer than four positions: the message contains "4 or more Positions".

Notes About Numeric Validation

Coordinate values must be numbers. When a position contains a non-numeric value (such as a string), this triggers the "invalid" error described for point and line_string. Numeric integers such as the ones shown in the examples are valid.

Goal

Create a module turf.length that exposes a public function length computing the overall linear (geodesic) distance along the line segments of a GeoJSON geometry, feature, or collection.

Public interface

from turf.length import length
Function signature
def length(geojson, options=None):
    ...
  • geojson: the input whose length is measured (see the accepted input types below).
  • options: an optional dict. "units" is the only key exercised; its value is a string that names the output distance unit (e.g. "feet"). When it is omitted, options may be None.
Value returned

A number: the total distance, expressed in the requested units, obtained by summing the great-circle distances between each pair of consecutive coordinates along every line contained in the input.

Inputs that are accepted and how they are measured

The function must traverse the input's coordinate structure and sum the distances between consecutive coordinate pairs. The distance between two [longitude, latitude] positions must be computed as a geodesic (great-circle) distance on the Earth and then converted to the requested unit.

The input forms that follow must be supported:

  1. A raw list of coordinate line strings — a list in which each element is a list of [lon, lat] positions (that is, the structure of a MultiLineString's coordinates). Each inner list is handled as an independent line; distances are summed within each inner list and across all of them.

  2. A Feature whose geometry is one of the following:

    • LineString — add up distances along its single coordinate sequence.
    • MultiLineString — add up distances along each of its coordinate sequences.
    • Polygon — add up distances along each ring (each ring is treated as a line that follows its coordinate order, including the closing segment back to the first point as given by the ring's coordinates).
    • MultiPolygon — add up distances along every ring of every polygon.

  3. A FeatureCollection — add up the measured length of every feature it contains.

Feature/geometry objects may be supplied either as plain GeoJSON-style dicts or as objects created by the helper constructors in turf.helpers (for example multi_line_string(...)). Both must be handled equivalently.

Within each individual line/ring, distance is accumulated by stepping through consecutive coordinate pairs in order. No distance is contributed from a line's last point to the first point unless that point appears explicitly in the line's coordinate list (as is the case for polygon rings).

Error cases

The function must reject inputs that contain no measurable line geometry. Specifically:

  • A bare coordinate position such as [0, 0] (a single point given as a raw list).
  • A Point feature (for example, the result of turf.helpers.point([0, 0])).

For such cases the function must raise an exception whose message contains the substring Input must be.

Expected numeric results

Validation happens after the results are rounded to the nearest integer. With units="feet", the representative results that follow must hold (rounded):

  • A MultiLineString feature consisting of two lines (points of the first line [-77.031669, 38.878605] … [-77.019824, 38.892368], second line [-77.041669, 38.885821] … [-77.035661, 38.878605]) → 15433.
  • When the same coordinate structure is passed as a raw list of point lists → 15433.
  • A Polygon with a single ring [-77.031669, 38.878605] … [-77.04, 38.88] → [-77.031669, 38.878605] → 18364.
  • A MultiPolygon made up of two polygons (ring coordinate counts of 8 and 5 respectively) → 27335.
  • A FeatureCollection that contains the MultiLineString above plus the Polygon above → 33796 (that is, the sum of its members).
  • One long real-world LineString route → 1068692.
  • A second long real-world LineString route → 2432897.

These values pin down the choice of Earth radius / distance model and the unit conversion factor; your implementation must reproduce them (to the rounded integer) for the given coordinates.

Additional notes

  • Coordinates use [longitude, latitude] order (degrees).
  • The distance-summing logic should rely on a geodesic point-to-point distance computation that is consistent across all input types, so that the same coordinates always yield the same total no matter how they are wrapped (raw list, Feature, or FeatureCollection).

Public API

Parameters

A GeoJSON Point Feature takes this form:

    {
    "type": "Feature",
    "properties": {...},
    "geometry": {
        "type": "Point",
        "coordinates": [lng, lat]
    }
}

  • bearing: a numeric compass bearing in degrees, measured clockwise starting from north. Consequently, 0 is north, 90 is east, and 180 is south. Negative values and values greater than 360 adhere to the same angular convention.

  • units: the name of the distance unit. Its default value is the string "kilometers". Default unit semantics

Origin properties are also not copied to the result.

Required Calculation

Apply the package's shared spherical conversion semantics, which are based on an earth radius of 6,371,008.8 metres. Equivalently, once [longitude1, latitude1] has been extracted, convert the origin and the bearing to radians and convert distance in units into the angular distance delta. For a bearing of theta, the destination is given by:

latitude2 = asin(

    + cos(latitude1) * sin(delta) * cos(theta)
)

longitude2 = longitude1 + atan2(
    sin(theta) * sin(delta) * cos(latitude1),
    cos(delta) - sin(latitude1) * sin(latitude2)
)

    "properties": {},
    "geometry": {
        "type": "Point",
        "coordinates": [<rounded lng>, <rounded lat>]

}

Task Specification: Implementing the square Module

Goal

The task is to create a new module that, given an input bounding box, computes the smallest bounding box that encloses it and that is a perfect square.

Public API

Create a module at turf/square/ exposing a callable named square, which can be imported as:

from turf.square import square

Function Signature

def square(bbox):
    ...

Behavior

The square function takes a single argument, bbox: a list of four numeric values representing a bounding box of the form:

[west, south, east, north]

in which:

  • the horizontal extent is defined by west (bbox[0]) and east (bbox[2]),
  • the vertical extent is defined by south (bbox[1]) and north (bbox[3]).

The function must return a new bounding box (a list of four numeric values, in the same format) which is the smallest square that fully contains the input bounding box. Along the dimension that needs to be expanded, the returned box is centered on the input box.

Rules for the computation

Define:

  • horizontal_distance = east - west
  • vertical_distance = north - south

Then:

  • If horizontal_distance >= vertical_distance (the box's width is greater than or equal to its height):

    • The horizontal extent is left unchanged.
    • The vertical extent is expanded symmetrically about its center, such that its height equals horizontal_distance.
    • Concretely, taking mid = (south + north) / 2 and half = horizontal_distance / 2, the result is:
      [west, mid - half, east, mid + half]

  • Otherwise (the box's height is greater than its width):

    • The vertical extent is left unchanged.
    • The horizontal extent is expanded symmetrically about its center, such that its width equals vertical_distance.
    • Concretely, taking mid = (west + east) / 2 and half = vertical_distance / 2, the result is:
      [mid - half, south, mid + half, north]

  • When the input box is already square (horizontal_distance == vertical_distance), the box that gets returned is equal to the input box.

Examples
Input bbox Returned value
[0, 0, 5, 10] [-2.5, 0, 7.5, 10]
[0, 0, 10, 5] [0, -2.5, 10, 7.5]
[0, 0, 10, 10] [0, 0, 10, 10]

The returned value must be a list the elements of which compare equal to the values shown above.
