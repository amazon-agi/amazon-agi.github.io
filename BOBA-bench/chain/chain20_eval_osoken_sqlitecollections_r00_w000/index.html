Specification of the Task

Summary

The sqlitecollections package is to be implemented, providing collection types that are backed by SQLite. Exposure of the generic base class SqliteCollectionBase and the concrete mutable mapping Dict is required from the module sqlitecollections.core. A container persists its state in an SQLite table and registers that table in metadata that is shared.

Public API of sqlitecollections.core

All of the names below must be importable from sqlitecollections.core:

  • SqliteCollectionBase
  • Dict
  • uuid4, with uuid.uuid4 as the initial binding
  • dumps and loads, with pickle.dumps and pickle.loads as the initial bindings
  • NamedTemporaryFile, with tempfile.NamedTemporaryFile as the initial binding

Public dependency hooks are what the module-level bindings of uuid4, dumps, loads, and NamedTemporaryFile serve as: construction must perform the lookup of these bindings at runtime, so that callers can replace them. In particular, the default codecs are the current module-level dumps and loads, and not function objects that were permanently captured in constructor defaults.

SqliteCollectionBase

SqliteCollectionBase[T] is an abstract base class that is generic; generic subscription at runtime, for instance SqliteCollectionBase[Any], must be supported by it. A concrete subclass must provide a schema_version property whose value is a string, along with _do_create_table(self, commit: bool = False) -> None.

Instantiation

These are the parameters the constructor accepts:

SqliteCollectionBase(
    connection=None,
    table_name=None,
    serializer=None,
    deserializer=None,
    destruct_table_on_delete=False,
)
  • connection may be None, a string giving a database name/path, or an existing sqlite3.Connection.
    • When None is given, a connection backed by a temporary file gets created: NamedTemporaryFile().name is obtained, and that name is handed to sqlite3.connect.
    • When a string is given, sqlite3.connect receives that string.
    • When an existing sqlite3.Connection is given, that exact object gets reused.
    • TypeError is raised for any other type.
  • serializer is a callable whose input is a value and whose output is bytes. Should it be omitted or None, the module-level dumps is used.
  • deserializer is a callable whose input is bytes and whose output is a value. Should it be omitted or None, the module-level loads is used.
  • The default for destruct_table_on_delete is False.

Through the following properties/attributes, the resolved values must be exposed:

  • connection: sqlite3.Connection
  • table_name: str
  • serializer
  • deserializer
  • destruct_table_on_delete: bool
  • container_type_name: str, which equals self.__class__.__name__
  • schema_version: str, which the concrete subclass supplies

Calling the configured serializer is what serialize(value) must do, and calling the configured deserializer is what deserialize(blob) must do.

Resolving the table name

  • A table_name that is supplied gets used directly.

  • Should table_name be omitted, the format is exactly the following:

    <container_type_name>_<str(uuid4()) with every hyphen removed>

    To illustrate: the class name ConcreteSqliteCollectionClass together with the UUID 4da95358-64e7-40e7-b888-31e14e1c1d09 yields ConcreteSqliteCollectionClass_4da9535864e740e7b88831e14e1c1d09.

The metadata table and initialization

A metadata table with at least these columns is required on each connection that a container uses:

  • table_name
  • schema_version
  • container_type

Construction ensures that the metadata table and the concrete backing table both exist. What the container's metadata row stores is, verbatim:

(table_name, schema_version, container_type_name)

Its metadata record is required to be uniquely identified by the table name. The behavior observable during initialization is the following:

  • When the same concrete container is built twice against one connection and table_name, the already-initialized backing table is reused, and exactly one metadata row results. The rows already present in that backing table are not cleared.
  • One metadata row per name is produced on a single connection by distinct table names.
  • What SELECT table_name, schema_version, container_type FROM metadata returns mirrors the insertion order of the distinct table names.
  • Reuse of an initialized table is possible when its metadata identifies the same container type and schema version and the physical table exists.

Creation of the concrete table happens via the subclass hook _do_create_table(self, commit: bool = False) -> None.

Destructive lifecycle switch

With destruct_table_on_delete set to False, both the backing table and the metadata row survive finalization/deletion of the container. When True is set instead, finalization is required to:

  1. delete the metadata row whose table name and container type match the container's,
  2. drop the backing table, and
  3. have the connection finalize those database changes.

Dict

A subclass of SqliteCollectionBase is Dict[KT, VT], implementing a mutable mapping whose storage is SQLite. Generic subscription, for instance Dict[Hashable, Any], must return a class that is usable. For Dict itself, the following holds:

  • schema_version == "0"
  • container_type_name == "Dict"
Instantiation and codecs

These are the parameters the constructor accepts:

Dict(
    connection=None,
    table_name=None,
    serializer=None,
    deserializer=None,
    key_serializer=None,
    key_deserializer=None,
    destruct_table_on_delete=False,
    data=None,
    **kwargs,
)

Values get encoded and decoded by serializer and deserializer. Keys get encoded and decoded independently by key_serializer and key_deserializer, which are exposed via properties carrying those same names. Whenever a key codec is omitted, its default is the corresponding configured value codec. In the absence of custom codecs, the module-level pickle dumps/loads bindings are what both keys and values use. The configured key codecs are what serialize_key(key) and deserialize_key(blob) must use; the hashability validation described below is additionally performed by key serialization.

When it is provided, data serves as an initial mapping. Population takes place in this order:

  1. the entries of data, in that mapping's iteration order;
  2. the entries of kwargs, in keyword order.

Precedence over duplicate keys coming from data goes to keyword entries; still, when a duplicate gets replaced, that key's original insertion position must be retained. An already initialized table gets updated, not cleared first, by the initial data.

Backing-table schema and how data is persisted

Exactly three columns, named as follows and appearing in this order, make up a Dict backing table:

  1. serialized_key — a unique BLOB that is non-null
  2. serialized_value — a BLOB that is non-null
  3. item_order — an ordering key of integer type

A compatible schema is equivalent to the following:

CREATE TABLE <table_name> (
    serialized_key BLOB NOT NULL UNIQUE,
    serialized_value BLOB NOT NULL,
    item_order INTEGER PRIMARY KEY
)

item_order 0 is received by the first inserted key. For a newly inserted key, the value is one greater than the current maximum item_order; when an existing key is replaced, its order is preserved. Renumbering of the remaining rows is not done by deletions, so gaps are permitted. On every supported Python version, ascending item_order is what always determines ordering.

In storage, which bytes identify a key is decided by the serialized key. Deserialization happens for the values handed back to callers. As a result, a mutation applied to a deserialized mutable value does not persist on its own; assignment of the changed value back into the mapping is required.

If an existing compatible table holds data whose encoding is non-canonical for the currently active codecs, opening it requires decoding and re-encoding its keys and values with the active key and value codecs, with every item_order preserved. Among other things, this covers reading rows that an older pickle protocol wrote and bringing them to the current default pickle.dumps representation. Apart from that, all entries are preserved when an existing dictionary is opened.

Unhashable keys and keys that are missing

For each operation that takes a key—lookup, assignment, deletion, membership, get, pop, and setdefault included—an unhashable key must be rejected by way of TypeError in the standard form containing:

unhashable type: '<type-name>'

During indexed lookup, deletion, or pop without a default, a missing key raises KeyError(key); the exception argument is therefore the original key.

Fundamental mapping behavior
  • The row count of the backing table is what len(d) returns, even when gaps exist in item_order.
  • d[key] returns the deserialized value that corresponds to the serialized key which matches.
  • d[key] = value performs an upsert. For a key that already exists, only the value gets replaced and the key is not moved; appending at the next order index happens for a new key.
  • The row that matches is removed by del d[key], while the order indices of other rows stay unchanged.
  • Membership is reported by serialized key for key in d and key not in d.
  • iter(d) returns a collections.abc.Iterator whose elements are deserialized keys in ascending insertion order. A fresh iterator is produced by each call; a single iterator behaves with the normal one-shot exhaustion.
  • All entries are removed by clear(), which leaves the backing table empty. It also works when the mapping is already empty.
Methods and views on the dictionary
  • get(key, default=None) returns either the value already present or default, and nothing gets inserted.
  • A collections.abc.KeysView enumerating the keys in insertion order is what keys() returns.
  • items() returns a collections.abc.ItemsView whose enumeration covers deserialized (key, value) pairs in insertion order.
  • A collections.abc.ValuesView enumerating the values in insertion order is what values() returns.
  • pop(key[, default]) removes an existing value and returns it. Should the key be absent, a default that was supplied is returned and the mapping stays unchanged; with no default supplied, KeyError(key) is raised.
  • setdefault(key, default=None) returns a value that already exists, leaving it unchanged. When the key is missing, key is appended together with default, that default is returned, and None gets used if no default was supplied.
  • Normal mutable-dictionary semantics apply to update([other], **kwargs). It accepts first a mapping or an iterable of key/value pairs, then keyword entries. In-place replacement happens for existing values, and new keys get appended in source order.
popitem()

The (key, value) pair inserted most recently is what popitem() removes and returns, taking the greatest item_order (LIFO). Deserialization applies to the returned key and value, and the row corresponding to them is removed. An empty mapping causes it to raise:

KeyError("popitem(): dictionary is empty")

Exactly 'popitem(): dictionary is empty' is the message carried by that exception.

Iteration in reverse order
  • For Python 3.8 and later, a collections.abc.Iterator over deserialized keys in descending insertion order is what reversed(d) returns.
  • On versions earlier than Python 3.8, reversibility is absent from Dict; TypeError carrying the standard message 'Dict' object is not reversible is what reversed(d) raises.
Union operators for mappings

From Python 3.9 onward:

  • When other is a mapping, d | other returns a fresh SQLite-backed Dict sitting on the same SQLite connection. Its table is fresh and automatically generated, and d is not mutated by it. Their relative order is retained by left-hand entries; duplicate left-hand values are replaced by right-hand values while those keys stay in place; right-hand iteration order governs the appending of keys unique to the right operand. The result being a fresh table means its item_order values run consecutively beginning at 0.
  • The identical right-precedence merge is carried out in place by d |= other. The original object and its backing table are kept, positions of existing keys are preserved, and new keys from the right-hand side get appended at the end.

Neither operator has support on versions before Python 3.9. The normal TypeError forms, which identify Dict and the type of the right operand, get raised:

unsupported operand type(s) for |: 'Dict' and '<right-type>'
unsupported operand type(s) for |=: 'Dict' and '<right-type>'

Requirements around compatibility

  • Across supported Python versions, both those before and those after 3.8 and 3.9, runtime behavior must work.
  • Import-time or runtime failures must not be caused by the typing and collections.abc import differences between those versions.
  • Even in cases where the built-in dict did not yet guarantee it, insertion ordering is guaranteed across all supported Python versions.

Scope of the work

What is required covers only SqliteCollectionBase, Dict, and the behaviors that are explicitly listed. Additional standard mapping methods may be provided, but no collection type besides these is required.

(Place it at the same import location used by the existing project for List; it must be importable directly.)

Class definition
  • List must be a generic class that supports subscripted type parameters, e.g. List[str].
  • The List class must be a subclass of collections.abc.MutableSequence.
Constructor
List(connection, table_name)
  • connection: an open sqlite3.Connection object (keyword argument: connection).
  • table_name: the name of the database table that holds the elements (keyword argument: table_name).

Calls pass both arguments by keyword.

Data Model

The table backing the list (its name is given by table_name) contains one row per list element. The columns that matter are:

  • serialized_value: a BLOB that holds the pickle-serialized Python value of the element.
  • item_index: an integer that gives the zero-based position of the element within the list.

To fetch an element's value, read the serialized_value BLOB of the row whose item_index matches the requested position and deserialize it with pickle.

Required Behavior

Access by integer index — __getitem__

Support fetching an element by a non-negative integer index via subscript syntax:

value = sut[i]
  • For a valid index i (an item_index that exists in the table), return the deserialized Python object stored in the serialized_value of that row.
  • If the index i does not match any existing row (i.e. no element exists at that position), raise IndexError with the message list index out of range.

Indices are zero-based. For this task, only non-negative integer indices need to be supported.

Example

Consider a table items populated with three rows whose deserialized values are "a", "b", "c" at item_index 0, 1, 2 respectively:

sut = List[str](connection=conn, table_name="items")
sut[0]   # -> "a"
sut[1]   # -> "b"
sut[2]   # -> "c"
sut[3]   # raises IndexError("list index out of range")

Task Description

Overview

Add support for negative indices to the indexed element access (__getitem__) of an existing list-like class.

Background

An existing list-like container class supports item access through the subscript operator (sut[i]). It already supports the following:

  • Retrieval via a non-negative integer index (0, 1, 2, ...), which returns the element located at that position.
  • Whenever a non-negative index is beyond the last element, IndexError is raised with the message "list index out of range".

Required Modification

Extend the subscript access (__getitem__) so that negative indices are also supported, following standard Python list indexing semantics:

  • The index -1 returns the last element.
  • The index -2 returns the second-to-last element.
  • More generally, an index of -n returns the element at position length - n, where 1 <= n <= length.

Edge Cases and Error Conditions

  • When a negative index is out of range — that is, when its absolute value is greater than the number of elements — raise IndexError with the message "list index out of range".

Summary of Behavior (by example)

Given a container holding the elements "a", "b", "c" in that order:

Index Result
-1 "c"
-2 "b"
-3 "a"
-4 raises IndexError with message "list index out of range"

The existing behavior for non-negative indices must stay unchanged.

Task: Add Slice Indexing and Membership Testing to List

Background

You are working with List, a collection class with sequence-like behavior in the sqlitecollections package that stores its elements in a SQLite database. Storage takes place in a table, where every element sits in its own row as a pickled (serialized) value, and an item_index column records each element's position (0-based).

The class is imported as:

from sqlitecollections import List

To construct a List, you pass keyword arguments, including connection (a sqlite3.Connection) and table_name (a str); the class is generic over its element type (e.g. List[str], List[Any]).

Each instance exposes a table_name attribute (a str) that identifies the SQLite table holding its elements.

A metadata registry exists that associates each collection's table name with a container type name; a List backed by the table "items" appears in this metadata as ("items", "0", "List").

On List, you must implement two behaviors: __getitem__ when it is given a slice, and __contains__ (membership testing).

Behavior Requirements

1. __getitem__ when given a slice argument

Implement List.__getitem__(self, key) such that, when key is a slice object, it returns a new List instance that contains exactly the elements obtained by applying that slice to the sequence of elements, in order.

  • Whatever is returned must itself be a List and must expose its own table_name attribute referring to a separate backing table (distinct from the source list's table). The source list's own table and its contents must be left unchanged.
  • Elements in the new list must be stored contiguously with item_index values 0, 1, 2, … in the order the slice produces, and each element's serialized value must equal the pickled form of the corresponding source element.
  • Slice semantics must exactly match standard Python sequence slicing, including:
    • start, stop, and step, each of which can be None or any integer (positive, negative, or zero-magnitude out-of-range values such as ±100 relative to a 26-element sequence).
    • Negative indices count from the end.
    • Negative step (reverse ordering); note that step may be None or nonzero integers such as ±10, ±20, ±100.
    • Out-of-range start/stop values being clamped the way Python does it, producing empty results where appropriate.
    • The result equals whatever list(elements)[slice] would yield for the same slice.
  • When a returned sliced List object is garbage-collected / deleted, the temporary backing table created for it must be cleaned up, so that after all such temporary lists have been disposed of, only the original List (table "items", type "List") remains registered in the metadata and present in the database.
2. __contains__ (membership testing)

Implement List.__contains__(self, value) such that value in list_instance returns True if and only if some element stored in the list is equal to value, and returns False otherwise. As a consequence, value not in list_instance returns the logical negation.

Equality is determined by value across arbitrary picklable Python objects, including:

  • strings (e.g. "a"),
  • bytes (e.g. b"a"),
  • None,
  • integers (e.g. 0),
  • nested tuple structures (e.g. ((0, 1), "a")),
  • lists (e.g. [0, 1]).

A bytes value and a str value are distinct and do not match one another. For a value that is not present in the list, in yields False (and not in yields True).

Constraints

  • As a side effect of either operation, the source list's contents and its backing table must not be modified.
  • Once the returned sliced lists are disposed of, the slice operation must not leave orphaned tables or metadata entries behind.
