from prometheus_flask_exporter import PrometheusMetrics

The goal is to make the prefix used for the library's built-in ("default") metrics configurable and to allow those metrics to be registered explicitly at a later point rather than only during construction. Existing controls for where the metrics exposition route is registered must continue to work with both direct Flask application binding and the application-factory pattern.

Public API

The class must support both direct binding and application-factory-style deferred binding:

# Direct binding
metrics = PrometheusMetrics(app, registry=registry)

# Deferred binding
metrics = PrometheusMetrics(app=None, registry=registry)
metrics.init_app(app)

The constructor and init_app must accept and support the following keyword options relevant to this task:

  • app: a Flask application instance, or None. If it is None, no application is bound during construction; init_app(app) binds one later.
  • path: the path at which to register the Prometheus exposition route. It defaults to "/metrics". A custom string registers the route at that path. None suppresses automatic registration of an exposition route.
  • registry: the Prometheus CollectorRegistry against which metrics are registered and from which the endpoint serves metrics.
  • export_defaults (bool, default True): controls whether the built-in default metrics are registered automatically. If False, no default metrics are registered until explicitly requested through export_defaults.
  • defaults_prefix (str, default "flask"): the prefix applied to the names of automatically registered default metrics.

Binding an application, whether in the constructor or through init_app, must retain that application for later operations that omit an app argument. These operations must not depend on an active Flask application context.

metrics.version

A bound instance must expose a string version attribute identifying the exporter. Its value is used as the version label on the exporter information metric.

metrics.export_defaults(...)

This public method registers the built-in default metrics on demand. In addition to retaining its existing default-metric options, it must accept the keyword argument:

  • prefix (str): the prefix for the default metric names registered by this call. If omitted, the default prefix is "flask".

For example:

metrics.export_defaults(prefix='late')

The method must operate on the already-bound application when no application is supplied, without requiring an active application context. Metrics registered this way begin collecting immediately for subsequent requests.

metrics.register_endpoint(path, app=None)

This public method registers a Prometheus exposition route.

  • path is the route path to register.
  • If app is supplied, the route is registered on that Flask application.
  • If app is omitted, the method must use the application previously bound either directly in the constructor or through init_app. It must work without an active Flask application context.

Using path=None during construction or initialization only disables automatic route registration; it does not disable default metric collection. A route may be registered later with register_endpoint(path). Registering it later must not reset the registry or discard observations made before the route existed: metrics collected before manual route registration must be available immediately from the newly registered endpoint.

For example:

# Requests can already be observed here.
metrics.register_endpoint('/manual/metrics')

In this case the library must not automatically provide /metrics; absent an independently registered application route, that URL has Flask's normal not-found behavior. The manually registered /manual/metrics route serves the existing registry.

    • P_http_request_duration_seconds_bucket, with le and the request labels;
    • P_http_request_duration_seconds_count;
    • P_http_request_duration_seconds_sum.

  • the corresponding flask-prefixed default metrics must not be registered.

The configured default prefix applies only to the library's built-in metrics; names explicitly supplied for custom metrics retain their normal behavior.

  • none of the built-in information, request counter, or request duration metrics are registered automatically;

  • exposition-route registration remains controlled independently by path.

Normal use must not require callers to push an application context manually. All of the following must work after either direct binding or init_app(app), without an active application context:

  • issuing requests through the Flask client and collecting metrics;
  • explicitly exporting defaults on the bound application; and
  • registering an exposition route later through register_endpoint(path) without passing app again.

Route registration timing and metric registration timing are independent. Delaying one must preserve the behavior and observations of the other as described above.

Task Specification: Robust Request Timing in Prometheus Flask Exporter

Context

You are working on a Flask extension that exports Prometheus metrics for HTTP requests. The extension registers a before_request hook that records a request start timestamp, and an after_request hook that uses that timestamp to observe request latency and to count requests by method and status.

The relevant class is PrometheusMetrics in the prometheus_flask_exporter package. Its export_defaults() method installs the default request-tracking hooks and exposes a counter of total HTTP requests.

Problem

Flask allows multiple before_request hooks. If another before_request hook registered by the application aborts or raises an exception before the exporter's own before_request hook runs, then the request start timestamp is never recorded on the request object. However, Flask still triggers the after_request processing in this case.

Currently, the after_request logic unconditionally reads the previously stored start timestamp from the request object. When that timestamp was never set, this raises an AttributeError, breaking metrics collection for aborted requests.

Required Behavior

The after_request handling installed by export_defaults() must not fail when the request start timestamp was never recorded on the current request.

Specifically:

  • When a request is aborted or fails inside another before_request hook (so the exporter's start-timestamp was never set), the after_request processing must complete without raising.
  • In that situation, the latency/duration observation (the histogram/summary section that depends on the start timestamp) must be skipped.
  • The total HTTP request counter must still be incremented for such requests, labeled with the request method and the resulting HTTP status code.

For requests that proceed normally (where the start timestamp was recorded), all existing behavior is unchanged, including latency observation and request counting.

Concrete Scenario the Behavior Must Satisfy

Given an application that registers a before_request hook which aborts every request with HTTP status 400 (except requests to the metrics-exposition endpoint), and given export_defaults() has been called:

  • Issuing requests to an arbitrary path (which are aborted with 400) must not cause any error in the metrics machinery.
  • The total HTTP request counter, exposed under the metric name flask_http_request_total, must reflect one increment per such request. For two GET requests aborted with status 400, the counter labeled with method="GET" and status="400" must equal 2.0.

API Surface

  • Package/module: prometheus_flask_exporter
  • Class: PrometheusMetrics
  • Method: export_defaults(self, ...) — registers the before_request and after_request hooks; the total-request counter it exposes must use the metric name flask_http_request_total with labels method and status.

No new public API is required; the change is entirely in the resilience of the existing after_request hook behavior described above.

  • The label value is the return value of calling the function with the current request.

Callables without a valid label name (anonymous functions)

No spurious warnings

The deprecation warning is only emitted at the point where default metrics are actually configured with the group_by_endpoint flag set (i.e. when export_defaults(...) runs with a truthy group_by_endpoint).

  • Metric name: flask_http_request_duration_seconds (with the usual histogram _bucket and _count series).
  • Each recorded request contributes to the +Inf bucket and increments the count for its label combination.
  • Labels present: the grouping label (name and value as described above), method, status, plus histogram-standard labels (le on buckets).

  • Omitting all grouping parameters keeps the previous default behavior: group by request.path under a path label.
  • group_by_endpoint=True continues to group by endpoint but now additionally emits a one-time DeprecationWarning mentioning group_by_endpoint.
  • The new group_by parameter is the preferred, general mechanism.

Problem

A tracking decorator must not replace Flask's exception handling with a response constructed directly by the decorator. Doing so bypasses registered error handlers and causes response-based labels to observe the wrong status, headers, or other response properties. At the same time, an unhandled Werkzeug HTTP exception must retain its normal HTTP response semantics rather than being treated like an unhandled ordinary Python exception.

Required Behavior

1. Delegate raised exceptions to Flask

If a decorated Flask view raises an exception, the decorator must pass it through the current application's normal user-exception handling mechanism, with the behavior of Flask.handle_user_exception.

This requirement applies to both:

  • ordinary Python exceptions, such as NotImplementedError; and
  • werkzeug.exceptions.HTTPException subclasses, including exceptions raised by flask.abort(...).

Flask, rather than the decorator, must select and invoke any applicable error handler.

2. Respect registered error handlers and their complete responses

When Flask finds a matching error handler, the handler's return value determines the request response. Before evaluating response-based labels, that return value must be finalized as a Flask response in the same way as a normal view return value. Consequently, label callables must be able to observe all final response properties, including:

  • the status code chosen by the handler;
  • headers added by the handler; and
  • any other properties of the finalized response object.

This applies whether the handler returns a response object directly or another Flask-supported response value, such as a body/status tuple or a body/status/headers tuple.

For example, if a handler for NotImplementedError returns a response with status 400, a label defined as lambda response: response.status_code must produce 400. The finalized handler-produced response must continue through the request as the decorated view's result; the exception must not propagate when Flask successfully handles it.

If Flask's user-exception handling raises because an ordinary, non-HTTP exception has no applicable handler, the decorator must not swallow or replace that exception. Before propagating it, the decorator must perform its metric update exactly once. Response-based labels for that update must be evaluated against a response representing HTTP status 500. Thus, for an unhandled ordinary exception:

  • a status label based on response.status_code is recorded as 500;
  • a summary's count and sum are updated once; and
  • the synthetic 500 response is used only for metric evaluation and must not be returned in place of the exception.

The same principle applies if Flask's user-exception processing itself raises an unhandled non-HTTP exception: metric evaluation uses a 500 response, then normal exception propagation is preserved.

4. Preserve unhandled HTTP-exception semantics

An HTTP exception for which no custom error handler exists is not subject to the ordinary-exception re-raise-with-500 rule. It must follow Flask's normal HTTP-exception behavior and become a response carrying the HTTP exception's own status code.

For example, an unhandled abort(503) must:

  • complete as the normal 503 HTTP response;
  • be recorded with status=503 by response-based metric labels; and
  • not be converted into a synthetic 500 metric response or re-raised by the decorator as an unhandled ordinary exception.

A matching HTTP-exception handler still takes precedence as described above; in that case, labels use the handler's finalized response instead of the exception's original status.

5. Record each decorated metric exactly once

For every invocation of a decorated view, the decorator's normal metric update must occur exactly once, regardless of whether the view:

  • returns successfully;
  • raises an exception handled by a registered error handler;
  • raises an unhandled ordinary exception; or
  • raises an HTTP exception with or without a matching custom handler.

Each metric uses the response corresponding to its outcome when evaluating response-based labels. In particular, summaries and histograms must make one observation per invocation, and counters must make their normal single increment. Existing behavior of the different metric types remains otherwise unchanged. If multiple metric decorators are stacked, each decorator updates its own metric once.

6. Finalize and return successful view responses

For a successful decorated Flask view, the view's Flask-supported return value must be finalized into the response used for label evaluation. That same finalized response object must be returned by the wrapper, rather than returning the original unfinalized value and requiring Flask to construct the response a second time.

This response behavior must continue to work for ordinarily named routes, routes with an explicitly assigned endpoint name, and decorated views registered through blueprints. It must not change the existing return-value behavior of metric-decorated helper functions that are not themselves the active Flask view.

Expected Outcomes

  • Handled HTTP exception: A view raises 409 Conflict; its registered handler returns status 400 and a header containing the original code. The metric is recorded once using status 400 and can read the header value 409.
  • Unhandled ordinary exception: A view raises an ordinary exception without a matching handler. The metric is recorded once with status=500, then the exception propagates from the wrapper.
  • Unhandled HTTP exception: A view calls abort(503) without a matching custom handler. The request retains the normal 503 response, and the metric is recorded once with status=503.
  • Successful view: The metric is recorded once against the finalized successful response, and that response is returned by the wrapper.

No new public API is introduced.
