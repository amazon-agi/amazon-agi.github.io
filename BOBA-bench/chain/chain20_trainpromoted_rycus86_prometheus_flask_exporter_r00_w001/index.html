Task Specification: Configurable Metrics Prefix in the Flask Prometheus Exporter

Overview

Your task is to implement behavior inside a Python library that exposes Prometheus metrics for Flask applications. The public class is PrometheusMetrics, which can be imported as:

from prometheus_flask_exporter import PrometheusMetrics

The aim is to make the prefix used for the library's built-in ("default") metrics configurable, and to allow those metrics to be registered explicitly at a later point rather than only during construction. The existing controls for where the metrics exposition route is registered must continue to work both with direct Flask application binding and with the application-factory pattern.

Public API

Constructing PrometheusMetrics and binding the application

The class must support both direct binding and deferred binding in the application-factory style:

# Direct binding
metrics = PrometheusMetrics(app, registry=registry)

# Deferred binding
metrics = PrometheusMetrics(app=None, registry=registry)
metrics.init_app(app)

The constructor and init_app must accept and support the following keyword options, which are relevant to this task:

  • app: a Flask application instance, or None. If it is None, construction binds no application; init_app(app) binds one later.
  • path: the path where the Prometheus exposition route is registered. Its default is "/metrics". A custom string causes the route to be registered at that path. None suppresses automatic registration of an exposition route.
  • registry: the Prometheus CollectorRegistry that metrics are registered against and from which the endpoint serves metrics.
  • export_defaults (bool, default True): determines whether the built-in default metrics are registered automatically. If it is False, no default metrics are registered until they are explicitly requested through export_defaults.
  • defaults_prefix (str, default "flask"): the prefix applied to the names of the default metrics that are registered automatically.
  • group_by_endpoint (bool): this existing grouping option must continue to be accepted. By default the duration metric groups by request path; when it is enabled, the grouping is by Flask endpoint instead.

When an application is bound — whether in the constructor or through init_app — that application must be retained for later operations that omit an app argument. These operations must work without depending on an active Flask application context.

The metrics.version attribute

A bound instance must expose a string version attribute that identifies the exporter. Its value is used as the version label on the exporter information metric.

The metrics.export_defaults(...) method

This public method registers the built-in default metrics whenever they are requested. Alongside retaining its existing default-metric options, it must accept the keyword argument:

  • prefix (str): the prefix for the default metric names that this call registers. If it is omitted, the default prefix is "flask".

For example:

metrics.export_defaults(prefix='late')

When no application is supplied, the method must operate on the already-bound application, and it must do so without requiring an active application context. Metrics registered in this way begin collecting immediately for subsequent requests.

The metrics.register_endpoint(path, app=None) method

Through this public method, a Prometheus exposition route is registered.

  • path is the path of the route to register.
  • When app is supplied, the route gets registered on that Flask application.
  • When app is omitted, the method must use the application that was bound previously, either directly in the constructor or through init_app. It must work even when no Flask application context is active.

Setting path=None at construction or initialization time only disables the automatic route registration; it does not disable default metric collection. A route may be registered later with register_endpoint(path). Registering the route later must not reset the registry or discard observations made before the route existed: metrics collected before manual route registration must be available immediately from the newly registered endpoint.

For example:

metrics = PrometheusMetrics(app, path=None, registry=registry)
# Requests can already be observed here.
metrics.register_endpoint('/manual/metrics')

In this scenario the library must not automatically provide /metrics; if no application route has been registered independently, that URL has Flask's normal not-found behavior. The /manual/metrics route, registered manually, serves the existing registry.

Decorator for custom counters

The instance must provide a decorator for counters, with the signature:

metrics.counter(name, description, labels=None)

labels is an optional mapping from a label name to a callable or static value that produces the label value on each invocation. The decorator may wrap a Flask view or another function used by a view, and each time the decorated function is invoked, its Prometheus counter is incremented.

Required Behavior

Names and prefixes of default metrics

When the default metrics are exported with a prefix P, the following metric families must be registered:

  • P_exporter_info: a metric whose value is 1.0 and which carries a version label equal to metrics.version.
  • P_http_request_total: a counter of HTTP requests, with method and status labels.
  • P_http_request_duration_seconds: a histogram of request duration, which carries method, path, and status labels under the default path grouping. It exposes the standard histogram child series, including:
    • P_http_request_duration_seconds_bucket, with le together with the request labels;
    • P_http_request_duration_seconds_count;
    • P_http_request_duration_seconds_sum.

If endpoint grouping is enabled, endpoint takes the place of path on the duration histogram, while the existing grouping behavior otherwise remains unchanged.

If defaults_prefix is omitted, the automatic prefix is flask, so names such as flask_exporter_info, flask_http_request_total, and flask_http_request_duration_seconds_count are produced.

When a custom defaults_prefix is supplied, for example "www":

  • the metrics must be exposed as www_exporter_info, www_http_request_total, www_http_request_duration_seconds, together with its child series; and
  • the corresponding default metrics with the flask prefix must not be registered.

The default prefix that has been configured applies only to the library's built-in metrics; names explicitly supplied for custom metrics keep their normal behavior.

Deferring the default export

If an instance is bound with export_defaults=False:

  • none of the built-in information, request counter, or request duration metrics are registered automatically;
  • requests that happen before an explicit export do not create built-in *_exporter_info, *_http_request_total, or duration series under flask or any other prefix; and
  • registration of the exposition route remains independently controlled by path.

After this call:

metrics.export_defaults(prefix='late')
  • late_exporter_info must exist immediately with value 1.0 and version=metrics.version;
  • subsequent requests must increment late_http_request_total with method and status labels; and
  • subsequent requests must be observed by late_http_request_duration_seconds, including its count series, which carries method, path, and status labels.

Backfilling must not take place: requests that were completed before export_defaults was called are not included. For instance, if two requests happen before registration and three happen afterward, the late-prefixed request counter and the histogram count report 3.0, not 5.0.

Endpoint registration happens independently of collection

Suppressing the exposition route, or delaying it, must not suppress the registration or collection of metrics. If default metrics are active while path=None, requests that were made before register_endpoint(...) are retained in the configured registry and are exposed after the route has been registered manually. Conversely, turning off default export does not prevent the configured endpoint from serving any other metrics present in that registry. Requests that reach an exporter-provided exposition route must remain excluded from default request tracking, so that scraping does not alter the default request metrics.

Suffix of counter sample names

Counters created through metrics.counter(...) follow the naming convention of the Prometheus client: the counter sample name that is reported carries a _total suffix. A counter created with the name cnt_1 is therefore exposed as cnt_1_total. This holds both without custom labels and with custom labels, for example cnt_2_total{uri=...,code=...}.

Built-in counters follow the same convention, including flask_http_request_total and the corresponding request counters with a custom prefix; no additional _total is appended to a name that already uses the counter suffix.

Metrics exposition and restricted registry queries

Every exposition endpoint, whether registered automatically or manually, must serve the configured registry in Prometheus text exposition format with HTTP status 200. The default route is /metrics, while a custom path or a route added with register_endpoint provides the same behavior at its configured location.

The endpoint must support restricted-registry queries that use one or more name[] query parameters. A restricted request returns status 200 and includes the metric families that were selected while unrelated families are omitted. For example, callers may select the exporter information metric alone, or they may select the bucket, count, and sum series of the request duration histogram.

For a bound application where GET /test returns 200, a restricted response that selects the default flask duration histogram series must include lines such as:

flask_http_request_duration_seconds_bucket{le="0.1",method="GET",path="/test",status="200"} 1.0
flask_http_request_duration_seconds_count{method="GET",path="/test",status="200"} 1.0

The label ordering must match this exposition: le, method, path, status for the bucket samples and method, path, status for the count samples.

Requirements for the application context and timing

In normal use, callers must not be required to push an application context manually. After either direct binding or init_app(app), all of the following must work without an active application context:

  • sending requests through the Flask client and collecting metrics;
  • explicitly exporting defaults on the bound application; and
  • registering an exposition route at a later point through register_endpoint(path) without passing app again.

The timing of route registration and the timing of metric registration are independent of each other. Delaying one of them must preserve the behavior and observations of the other, as described above.

02 Making Request Timing Resilient in the Prometheus Flask Exporter 513 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Making Request Timing Resilient in the Prometheus Flask Exporter

Background

The work here concerns a Flask extension that exports Prometheus metrics for HTTP requests. Two hooks get registered by this extension: a before_request hook, which records the start timestamp of a request, and an after_request hook, which takes that timestamp and uses it to observe request latency and to count requests by method and status.

Within the prometheus_flask_exporter package sits the class that matters, PrometheusMetrics. Installation of the default request-tracking hooks is done by its export_defaults() method, which also exposes a counter of total HTTP requests.

Problem Description

Flask allows an application to have more than one before_request hook. Whenever a different before_request hook, one registered by the application, aborts or raises an exception before the exporter's own before_request hook gets to run, the request start timestamp is then never recorded on the request object. Even so, in this situation Flask still triggers the after_request processing.

As things stand, the after_request logic reads from the request object the start timestamp that was stored there earlier, and it does so unconditionally. If that timestamp was never set, an AttributeError is raised, with the consequence that metrics collection for aborted requests breaks.

Behavior Requirements

The after_request handling put in place by export_defaults() must not fail in a case where the request start timestamp was never recorded on the current request.

More concretely:

  • A request that is aborted or fails inside another before_request hook — a situation in which the exporter's start-timestamp was never set — is one where the after_request processing must complete without raising.
  • Under those circumstances, the latency/duration observation, i.e. the histogram/summary section that depends on the start timestamp, must be skipped.
  • The total HTTP request counter, for its part, must still be incremented for such requests, with the request method and the resulting HTTP status code serving as its labels.

Where requests proceed normally (i.e. the start timestamp was recorded), all existing behavior carries over unchanged — latency observation and request counting included.

A Concrete Scenario the Behavior Must Satisfy

Take an application whose registered before_request hook aborts every request with HTTP status 400 (the exception being requests to the metrics-exposition endpoint), and take export_defaults() to have been called:

  • Issuing requests to an arbitrary path (such requests being aborted with 400) must not produce any error in the metrics machinery.
  • One increment per such request is what the total HTTP request counter, which is exposed under the metric name flask_http_request_total, must reflect. Once two GET requests have been aborted with status 400, the counter carrying the labels method="GET" and status="400" must equal 2.0.

API Surface

  • Package/module: prometheus_flask_exporter
  • Class: PrometheusMetrics
  • Method: export_defaults(self, ...) — the hooks before_request and after_request are registered by this method; the metric name flask_http_request_total is what the total-request counter exposed by it must use, together with the labels method and status.

No new public API is required; the change is confined entirely to the resilience of the existing after_request hook behavior described above.

Task Specification: Configurable Grouping (group_by) for HTTP Request Duration Metrics

Overview

Flask applications receive Prometheus metrics from this library. Whenever default metrics are exported, each request is recorded into a histogram of HTTP request durations named flask_http_request_duration_seconds. As things stand, the duration metric has labels such as method, status, together with one more label — the one that identifies the request "group."

The default metrics configuration must be extended so that a new group_by parameter makes the label used for grouping request durations configurable, while the deprecated group_by_endpoint flag is preserved.

Public API

Configuration gets applied on the metrics object the codebase uses (that is the object returned by instantiating the library's main metrics class, and it is also the object that exposes export_defaults(...)). The grouping configuration is accepted at two entry points:

  1. the metrics object's constructor / initialization call (the call that is invoked to set up default metrics).
  2. the metrics object's export_defaults(...) method.

Both of these must accept the keyword arguments below, which are the ones relevant to this task:

  • group_by — determines the label name and the label value by which the request duration metric is grouped. It accepts:
    • a string that names an attribute of the Flask request object (e.g. 'path', 'full_path', 'endpoint', 'url_rule'), or
    • a callable that takes the Flask request object and returns the group value.
    • If not supplied, the default is 'path'.
  • group_by_endpoint — a boolean flag that is deprecated; its default value is falsy.
  • export_defaults — a boolean that already exists; it decides whether default metrics get set up at construction time. When falsy, the construction step registers no defaults.

Behavior Requirements

Grouping via a request attribute (group_by given as a string)

If group_by is a string, then for every request the request duration metric must include a label whose name equals the string value and whose value equals the corresponding attribute of the Flask request object.

  • With group_by='path' (this doubles as the default when group_by is omitted): the label name is path and the value comes from request.path (e.g. /default1).
  • With group_by='full_path': the label name is full_path and the value is request.full_path; the query string is part of this value (e.g. /test?x=1).
  • With group_by='endpoint': the label name is endpoint and the value is request.endpoint, i.e. the Flask view function name (e.g. a_test_endpoint). When the grouping is by endpoint, no path label appears on the metric.
  • With group_by='url_rule': the label name is url_rule and the value is the string form of request.url_rule (the route pattern, e.g. /test/<item>). Requests that fall under the same rule but have different concrete paths must share the same label value, which means they aggregate into the same series.

In all cases the metric keeps its other labels (method, status) as well, and requests whose group values coincide accumulate together (e.g. two requests to the same url_rule produce a count of 2.0; each distinct group value produces an independent series).

Grouping with a callable (group_by given as a function)

If group_by is a callable, it gets invoked with the Flask request object and must return the group value string.

  • The label name placed on the metric is taken from the callable's name (its __name__). For instance, a function named composite gives rise to a label named composite.
  • The label value is what the function returns when it is called with the current request.

As an example, a function composite(r) that returns "%s::%s >> %s" % (r.method, r.path, r.args.get('type', 'none')) creates a label composite with values such as GET::/sample >> A, GET::/sample >> Beta, POST::/plain >> none, each of these forming its own series.

Callables lacking a valid label name (anonymous functions)

Whenever a callable does not yield a name usable as a Prometheus label — one such case is a lambda, whose __name__ is not a valid label — configuring group_by with it must raise an exception. The message the exception carries must contain the text invalid label; a case-insensitive search should find this substring.

The deprecated group_by_endpoint flag

The group_by_endpoint keyword must keep functioning as it always has: with a truthy value, request durations are grouped by the Flask endpoint — the label is named endpoint and its value is the view function name — and the metric carries no path label.

In addition, whenever a truthy group_by_endpoint is supplied — at construction time, or via a later call to export_defaults(...) — a DeprecationWarning must be issued exactly once per such call. The message of that warning must contain the substring group_by_endpoint.

No spurious warnings

Configuring the metrics object with defaults disabled (export_defaults=False) while not passing group_by_endpoint must not emit any deprecation warning. The deprecation warning is emitted only when default metrics are actually being configured and the group_by_endpoint flag is set — that is, when export_defaults(...) runs with a truthy group_by_endpoint.

Details of the Metric

  • Name of the metric: flask_http_request_duration_seconds (together with the usual histogram _bucket and _count series).
  • Every recorded request contributes to the +Inf bucket and also increments the count tied to its label combination.
  • As for the labels present: there is the grouping label (with its name and value as described above), method, status, and the histogram-standard labels (le on buckets).

Summary of Backwards Compatibility

  • If all grouping parameters are left out, the earlier default behavior stays: grouping happens by request.path under a path label.
  • group_by_endpoint=True still groups by endpoint, but it now also emits a one-time DeprecationWarning that mentions group_by_endpoint.
  • Going forward, the new group_by parameter is the preferred, general mechanism.

Overview

Your work targets prometheus_flask_exporter, a Flask extension that registers Prometheus metrics. The task at hand concerns the handling of the prefix applied to default metric names, and it adds a way to switch prefixing off entirely.

Requirements for the Public API

Module-Level Constant

The package prometheus_flask_exporter must export a constant named NO_PREFIX, which can be imported directly:

from prometheus_flask_exporter import NO_PREFIX

This constant serves as a sentinel value that is passed in place of a prefix string to signal that no prefix should be applied to default metric names.

The Metrics Object

The metrics object (that is, the extension instance, which tests construct through a helper equivalent to instantiating the exporter with the Flask app) must support:

  • A constructor keyword argument defaults_prefix that controls the prefix applied to the names of the default metrics.
  • A method export_defaults(prefix=...) that registers the default metrics, accepting a prefix keyword argument that controls the prefix applied to those metric names.
  • A version attribute (which is used as the value of a version label on the info metric).

Behavior

Semantics of the Prefix

The default metrics are these base metric names:

  • exporter_info — a gauge/info metric whose value is 1.0 and that carries a version label equal to the metrics object's version attribute.
  • http_request_total — a counter of HTTP requests, labeled by method and status.
  • http_request_duration_seconds (together with an associated ..._count series) — the request duration, labeled by method, path, and status.

Whenever a prefix is supplied, it is joined to each base metric name using a single underscore separator. The provided prefix value must not include a trailing underscore; the underscore separator is inserted automatically.

Examples of the fully-qualified metric names that result:

  • Given defaults_prefix='www' → the metrics are named www_exporter_info, www_http_request_total, www_http_request_duration_seconds, etc.
  • When prefix='late' is passed to export_defaults → the metrics are named late_exporter_info, etc.

Note how this differs from any prior behavior: the prefix argument is now a bare token (e.g. 'www', 'late'), and the separating underscore is added by the code — not supplied by the caller.

Mode With No Prefix

Once defaults_prefix is set to the NO_PREFIX constant, the default metrics are registered with no prefix and no leading underscore. Under this mode the metric names are exactly the base names:

  • exporter_info
  • http_request_total
  • http_request_duration_seconds (and http_request_duration_seconds_count)

To be specific, with NO_PREFIX:

  • The metric exporter_info is present with value 1.0 and a version label equal to the metrics object's version.
  • There is no metric named flask_exporter_info.
  • The metric http_request_total reflects the correct request count (labeled method, status), and there is no metric named flask_http_request_total.
  • As for http_request_duration_seconds_count, the metric reflects the correct request count (labeled method, path, status).

Put differently, NO_PREFIX must NOT produce names with the historical default flask_ prefix, nor produce a stray leading underscore.

Constraint Summary

  • The top-level prometheus_flask_exporter package must export NO_PREFIX.
  • NO_PREFIX is to be treated as a request to emit default metric names with no prefix at all.
  • Any string prefix is joined to the base names with exactly one underscore, and the caller is not required to include the underscore.

Initialization that is deferred

Task Specification: Robust Exception Handling for Metric Tracking Decorators

Background

Through the public PrometheusMetrics class, prometheus_flask_exporter delivers Prometheus instrumentation for Flask applications. Its metric-tracking decorators, for instance summary(...), can wrap Flask view functions and evaluate metric labels based on the response a request produces.

For instance:

@app.route('/some-path')
@metrics.summary(
    'metric_name',
    'description',
    labels={'status': lambda response: response.status_code}
)
def view_function():
    ...

A label callable that accepts a response must be given the final Flask response belonging to the decorated view. That covers a response produced by a registered Flask error handler. Static labels and label callables that take no arguments keep their existing behavior.

Problem Statement

A tracking decorator must not replace Flask's exception handling with a response that the decorator constructs directly. If it did, registered error handlers would be bypassed and response-based labels would observe the wrong status, headers, or other response properties. At the same time, an unhandled Werkzeug HTTP exception must keep its normal HTTP response semantics instead of being handled as an unhandled ordinary Python exception.

Required Behavior

1. Pass raised exceptions through to Flask

When a decorated Flask view raises an exception, the decorator must route it through the current application's normal user-exception handling mechanism, matching the behavior of Flask.handle_user_exception.

This requirement covers both of the following:

  • ordinary Python exceptions, such as NotImplementedError; and
  • werkzeug.exceptions.HTTPException subclasses, including exceptions raised by flask.abort(...).

It is Flask, not the decorator, that must select and invoke any applicable error handler.

2. Honor registered error handlers and their complete responses

If Flask locates a matching error handler, the handler's return value determines the request response. Before response-based labels are evaluated, that return value must be finalized as a Flask response in the same way as a normal view return value. As a consequence, label callables must be able to observe all final response properties, including:

  • the status code the handler chose;
  • headers the handler added; and
  • any other properties of the finalized response object.

This holds whether the handler returns a response object directly or another Flask-supported response value, such as a body/status tuple or a body/status/headers tuple.

As an example, if a handler for NotImplementedError returns a response with status 400, a label defined as lambda response: response.status_code must be 400. If a handler for an HTTP 409 Conflict returns status 400 and exposes the original code in an X-Original header, response-based labels must observe status 400 as well as the value 409 for that header. A matching handler's chosen status must not be overridden by the HTTP exception's original status.

The finalized response produced by the handler must continue through the request as the decorated view's result; when Flask handles the exception successfully, the exception must not propagate.

3. Let unhandled ordinary exceptions propagate, but still record the metric

When Flask's user-exception handling raises because an ordinary, non-HTTP exception has no applicable handler, the decorator must not swallow or replace that exception. It must propagate from the decorated view with its normal type and value, so the surrounding Flask configuration or caller can handle it in the usual way.

Before propagating the exception, the decorator must perform its metric update exactly once. For that update, response-based labels must be evaluated against a response representing HTTP status 500. Consequently, for an unhandled ordinary exception:

  • a status label based on response.status_code is recorded as 500;
  • the count and sum of a summary are updated once; and
  • the synthetic 500 response serves only for metric evaluation and must not be returned in place of the exception.

The same principle holds if Flask's user-exception processing itself raises an unhandled non-HTTP exception: metric evaluation is done against a 500 response, and normal exception propagation is then preserved.

4. Keep unhandled HTTP-exception semantics intact

When an HTTP exception has no custom error handler, it does not fall under the ordinary-exception re-raise-with-500 rule. It must follow Flask's normal HTTP-exception behavior and become a response that carries the HTTP exception's own status code.

As an example, an unhandled abort(503) must:

  • finish as the normal 503 HTTP response;
  • be recorded with status=503 by response-based metric labels; and
  • not be turned into a synthetic 500 metric response or re-raised by the decorator as an unhandled ordinary exception.

A matching HTTP-exception handler still takes precedence as described above; labels then use the handler's finalized response instead of the exception's original status.

5. Record each decorated metric exactly once

On every invocation of a decorated view, the decorator's normal metric update must occur exactly once, regardless of whether the view:

  • returns successfully;
  • raises an exception that a registered error handler handles;
  • raises an unhandled ordinary exception; or
  • raises an HTTP exception with or without a matching custom handler.

When response-based labels are evaluated, each metric uses the response that corresponds to its outcome. Specifically, summaries and histograms must make one observation per invocation, and counters must make their normal single increment. Apart from that, the existing behavior of the different metric types stays unchanged. When multiple metric decorators are stacked, each decorator updates its own metric once.

6. Finalize successful view responses and return them

When a decorated Flask view is successful, its Flask-supported return value must be finalized into the response that label evaluation uses. That same finalized response object is what the wrapper must return, rather than returning the original unfinalized value and requiring Flask to construct the response a second time.

This response behavior must keep working for ordinarily named routes, for routes whose endpoint name is explicitly assigned, and for decorated views registered through blueprints. The existing return-value behavior of metric-decorated helper functions that are not themselves the active Flask view must not be changed.

Expected Results

  • Handled ordinary exception: A view raises NotImplementedError; its registered handler returns status 400. The request finishes with the handler's response, and the metric is recorded once with status=400.
  • Handled HTTP exception: A view raises 409 Conflict; its registered handler returns status 400 plus a header containing the original code. The metric is recorded once with status 400 and can read the header value 409.
  • Unhandled ordinary exception: A view raises an ordinary exception with no matching handler. The metric is recorded once with status=500, and the exception then propagates from the wrapper.
  • Unhandled HTTP exception: A view calls abort(503) with no matching custom handler. The request keeps the normal 503 response, and the metric is recorded once with status=503.
  • Successful view: The metric is recorded once against the finalized successful response, and the wrapper returns that response.

Public API and Compatibility

No new public API is added. It must remain possible to import PrometheusMetrics from prometheus_flask_exporter, and the existing metric decorators—including summary(name, description, labels=...), histogram(...), counter(...), and gauge(...)—must keep their existing signatures and their ordinary metric semantics. The existing response-label, no-argument-label, static-label, registry, endpoint, blueprint, application-factory, default-metric, and metrics-export behavior must stay compatible. The only behavior that changes is the response finalization and exception-handling behavior described above.
