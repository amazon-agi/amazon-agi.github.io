Task: Add Quoting of Expanded CIDR Wildcard Strings in TextQueryBackend

Background

The TextQueryBackend class (the base backend used to convert Sigma rules into text-based query languages) supports the conversion of network values written in CIDR notation. When a backend does not support CIDR queries natively, it can expand a CIDR into a set of wildcard string patterns (for instance, 192.168.0.0/14 turns into 192.168.*, 192.169.*, 192.170.*, 192.171.*).

At the moment, these expanded wildcard values are emitted without quotes. You must add support for optionally enclosing each expanded CIDR wildcard string in a configurable quote character.

Required Modification

Introduce a new class variable in TextQueryBackend:

cidrv4_str_quote : ClassVar[Optional[str]] = None
Expected Behavior

Whenever a CIDR value is expanded into wildcard string patterns (that is, when cidrv4_wildcard is set to a non-None value such as "*"), each resulting wildcard string must be wrapped using the value of cidrv4_str_quote:

  • If cidrv4_str_quote is None, the expanded wildcard strings are emitted without any quote characters around them (this is the existing behavior).
  • If cidrv4_str_quote is set to a string (for example, '"'), each expanded wildcard string must have that string on both sides of it.

The quoting is applied to the wildcard values themselves, before they are inserted into the field/value or list expressions.

Example Scenarios

For a backend configured with:

  • cidrv4_in_list_expression = "{field} in ({list})"
  • cidrv4_expression = "{field}={value}"
  • cidrv4_wildcard = "*"
  • cidrv4_str_quote = '"'

a single CIDR field mapped to fieldA|cidrv4: 192.168.0.0/14 (where fieldA maps to mappedA) must produce:

mappedA in ("192.168.*", "192.169.*", "192.170.*", "192.171.*")

and a list combining the CIDR values 192.168.0.0/14 and 10.10.10.0/24 must produce:

mappedA in ("192.168.*", "192.169.*", "192.170.*", "192.171.*") or mappedA="10.10.10.*"

(Note that a single expanded wildcard makes use of the single-value expression, and multiple expanded wildcards make use of the in-list expression.)

Using the same setup except with cidrv4_str_quote = None, the identical inputs must produce the corresponding unquoted forms:

mappedA in (192.168.*, 192.169.*, 192.170.*, 192.171.*)
mappedA in (192.168.*, 192.169.*, 192.170.*, 192.171.*) or mappedA=10.10.10.*

Task Specification: Converting CIDR Values Without a Bound Field

Introduction

You are working within a query-conversion backend framework (the TextQueryBackend base class and its conversion machinery). The task consists of adding support for converting CIDRv4 network values that occur without a bound field name (the so-called "unbound" or field-less matches), and of making the quoting of CIDR string values simpler.

Background and Concepts

  • A CIDRv4 value is an IPv4 network written in CIDR notation, e.g. 192.168.0.0/14.
  • A detection can reference a CIDR value attached to a field (bound) or without any field (unbound / field-less). If a CIDR value is unbound, rendering it must use dedicated "unbound" expression templates.
  • The backend has support for an optional CIDR wildcard mode. If cidrv4_wildcard is None, a CIDR value is emitted verbatim in its network/prefix form. If cidrv4_wildcard is set to a string (e.g. "*"), the CIDR is expanded into one or more wildcarded network prefixes, each of which ends with the wildcard character.

Behavior Requirements

1. Unbound CIDRv4 conversion without a wildcard

If a CIDRv4 value is matched without a bound field and the backend's cidrv4_wildcard is None:

  • The value must be rendered with the single-value unbound CIDR expression template unbound_value_cidrv4_expression, in which the {value} placeholder is replaced by the CIDR in its plain network/prefixlen form (no quoting).
  • Example: for the input CIDR 192.168.0.0/14 with the template _={value}, the output must be:
    _=192.168.0.0/14
2. Unbound CIDRv4 conversion with wildcard expansion

If a CIDRv4 value is matched without a bound field and the backend's cidrv4_wildcard is set to a string (e.g. "*"):

  • The CIDR must be expanded into its constituent wildcarded network prefixes, with each prefix followed by the wildcard character.
  • Each expanded value must be rendered as a quoted string, and the collection of expanded values must then be joined and inserted into the {list} placeholder of the unbound list CIDR expression template, unbound_list_cidrv4_expression.
  • Example: for the input CIDR 192.168.0.0/14, the wildcard "*", and the template _ in ({list}), the output must be:
    _ in ("192.168.*", "192.169.*", "192.170.*", "192.171.*")
    (that is, the /14 network expands into the four /16 prefixes 192.168.*, 192.169.*, 192.170.*, 192.171.*, each of them double-quoted and comma-space separated.)
3. How wildcard-expanded CIDR values are quoted

When CIDR values are expanded into wildcarded prefixes (covering both bound and unbound cases), each expanded prefix must be rendered as a double-quoted string ("..."). This quoting must take place without relying on any separate CIDR-specific quote-configuration attribute.

  • Any dependency on a distinct cidrv4_str_quote class attribute for wildcard-expanded CIDR string quoting must be removed. Expanded CIDR prefixes are quoted by means of the backend's general string-quoting behavior.
  • For 192.168.0.0/14 with wildcard "*" and a list expression template of the form {field} in ({list}) (with field mapped to mappedA), the existing bound-field wildcard behavior must continue to produce:
    mappedA in ("192.168.*", "192.169.*", "192.170.*", "192.171.*")
    without any CIDR-specific quote attribute being set.

Public API

The conversion machinery must recognize and use the following backend class attributes (ClassVar[str]):

  • unbound_value_cidrv4_expression — a template string that contains a {value} placeholder, used to render a single unbound CIDR value when no wildcard expansion applies.
  • unbound_list_cidrv4_expression — a template string that contains a {list} placeholder, used to render the joined, quoted, wildcard-expanded CIDR prefixes for an unbound match.

CIDR string quoting must no longer require the following existing attribute:

  • cidrv4_str_quote — this attribute must not be needed for producing quoted wildcard-expanded CIDR values; quoting of expanded CIDR prefixes must work when this attribute is absent/unset.

Constraint Summary

  • Bound CIDR conversion (both the None-wildcard and the wildcard mode) must retain its existing output behavior, but wildcard-expanded values must be double-quoted by means of general string quoting rather than via a CIDR-specific quote attribute.
  • Unbound CIDR conversion must be newly supported in both the None-wildcard case (single verbatim value via unbound_value_cidrv4_expression) and the wildcard case (quoted expanded prefixes joined into unbound_list_cidrv4_expression).

Task: Add Support for Partial Regular Expressions (re_contains modifier)

Summary

Add support for a new "partial regular expression" value type together with its corresponding detection-item modifier. The type acts like a regular expression that is wrapped automatically so that it matches anywhere within a value (i.e., a "contains" semantic achieved by prefixing and suffixing with .*).

Required Modifications

1. New type SigmaPartialRegularExpression

Add a class SigmaPartialRegularExpression to the module sigma.types.

  • It must be possible to import it from sigma.types.
  • Its constructor accepts a single regular expression pattern string, e.g. SigmaPartialRegularExpression("test.*").
  • Automatic wrapping behavior: the pattern that is stored, and that takes effect, must be the input pattern with .* prepended and appended, unless the pattern already begins with .* (in which case nothing is prepended) or already ends with .* (in which case nothing is appended). Specifically:
    • SigmaPartialRegularExpression("test.*") must be equal to SigmaPartialRegularExpression(".*test.*"). Put differently, constructing from the raw pattern "test.*" gives, by equality, the same object as constructing from the fully-wrapped pattern ".*test.*". The effective pattern that results is .*test.*.
    • When two SigmaPartialRegularExpression instances are compared for equality, the comparison must reflect their effective (wrapped) patterns.
  • Validation: the pattern must be validated as a legal regular expression. Constructing the object must raise sigma.exceptions.SigmaRegularExpressionError if the pattern is not a valid regular expression. For example, SigmaPartialRegularExpression("(test.*") must raise SigmaRegularExpressionError.
  • A pattern that is valid, such as "test.*", must construct successfully (truthy).

This type should behave in the same way as the existing SigmaRegularExpression type (the same escaping/serialization behavior that is expected of a regular expression value), with the only difference being the automatic .*-wrapping of its pattern.

2. New modifier SigmaPartialRegularExpressionModifier

Add a class SigmaPartialRegularExpressionModifier to the module sigma.modifiers.

  • It must be possible to import it from sigma.modifiers.
  • It is constructed just like the existing modifiers (e.g. SigmaPartialRegularExpressionModifier(detection_item, applied_modifiers_list)), taking a detection item together with a list of previously-applied modifiers.
  • A call to .modify(SigmaString("foo?bar.*")) must return SigmaPartialRegularExpression(".*foo?bar.*") — i.e. the incoming plain string is converted into a SigmaPartialRegularExpression constructed from that string (which is then automatically wrapped with leading/trailing .*).
  • Restriction: this modifier is applicable only to unmodified values. If any other modifier has already been applied (i.e. the list of applied modifiers is non-empty), a call to .modify(...) must raise sigma.exceptions.SigmaValueError with a message that contains the text only applicable to unmodified values.

This modifier should behave in the same way as the existing SigmaRegularExpressionModifier, with the only difference being that it produces a SigmaPartialRegularExpression.

3. Registration of the re_contains modifier identifier

The new modifier must be usable in the field specifications of Sigma rule detection items via the modifier keyword re_contains, i.e. fieldA|re_contains: <pattern>.

End-to-end behavior that is expected

When a rule that contains a detection item such as:

detection:
    sel:
        fieldA|re_contains: pat.*tern/foobar
    condition: sel

is processed and converted by a backend that serializes regular expressions in the form /PATTERN/ (with / and \ escaped by a backslash in the regex output, in line with how ordinary regular expression values are already serialized), the output that results must be a regular-expression match in which the pattern has been wrapped with leading and trailing .*. Concretely, for the field mapping fieldA → mappedA, the query that is produced is:

mappedA=/.*pat.*tern\/foo\bar.*/

This is the same serialization that the existing regular-expression modifier would produce, except that the effective pattern is prefixed and suffixed with .*.

Constraints

  • The existing SigmaRegularExpression type, as well as the behavior of SigmaRegularExpressionModifier, must remain unchanged.
  • All new public symbols (SigmaPartialRegularExpression, SigmaPartialRegularExpressionModifier) must be importable from the module paths stated above.

  • add_applied_processing_item(self, processing_item) — Records that this detection item has had the given processing item applied to it. The value passed as processing_item is an instance of ProcessingItem (see sigma.processing.pipeline).

  • was_processed_by(self, identifier: str) -> bool — Returns True when a processing item whose identifier attribute equals the given identifier string has been recorded on this detection item through add_applied_processing_item; otherwise it returns False.

For any identifier, a newly constructed SigmaDetectionItem that has had no processing items applied must return False from was_processed_by.

  • add_applied_processing_item(self, processing_item) — Records the given processing item as applied to this detection. The method must recurse into the detection's contents: the processing item is received by every element in detection_items. If an element is itself a SigmaDetection, the processing item must be propagated recursively so that all SigmaDetectionItem instances nested inside it (at any depth) have the processing item recorded on them.

    After this method has been called, was_processed_by("<identifier>") must return True on every SigmaDetectionItem contained anywhere within the detection tree.

It must be possible to construct the ProcessingItem class as:

ProcessingItem(transformation, identifier="test")

That is, it accepts a transformation object as its first positional argument and an identifier keyword argument (a string). The identifier must be exposed in such a way that was_processed_by can match it.

1.4 Transformation (in sigma.processing.transformations)

It must be possible to import the base Transformation class from sigma.processing.transformations, and the class must provide:

  • set_processing_item(self, processing_item) — Attaches a ProcessingItem to this transformation. The processing item that gets stored is the one that transformations record onto the detection items they modify.
1.5 Tracking behavior of the transformations

A transformation that has been assigned a processing item via set_processing_item(...) and is then applied to a rule via apply(pipeline, rule) must record that processing item only on the detection items it actually modifies. The processing item must not be recorded on detection items that the transformation leaves unchanged.

In particular:

  • FieldMappingTransformation: A detection item counts as modified (and must be tracked) when its field name is changed by the mapping. If a mapping maps one source field to a list of target field names, every one of the resulting detection items counts as modified and must be tracked. Detection items whose field does not appear in the mapping are not tracked.

    Example: with the mapping {"field1": "fieldA", "field3": ["fieldC", "fieldD"]} applied to detection items whose fields are field1, field2, field3, the resulting items fieldA, fieldC, fieldD are marked as processed by the transformation's identifier, whereas field2 is not.

  • AddFieldnameSuffixTransformation: Only detection items whose field is affected (i.e. matched by the configured fields selector) and that therefore receive the suffix are tracked. Detection items that are unaffected are not tracked. If fields is configured with a list containing one field name (e.g. ["field1"]) and the transformation type is "plain", only the detection item whose field matches gets the suffix and is marked as processed.

  • WildcardPlaceholderTransformation: The only detection items tracked are those whose values are actually transformed (placeholders replaced). When a detection item's placeholder value is replaced (e.g. a value's placeholder converted into a wildcard), that detection item is marked as processed. Detection items whose values remain unchanged (because their placeholders were not eligible for replacement under the current include/exclude configuration) are not marked as processed.

    This tracking must take place when the transformation has been given a processing item; when no processing item has been assigned, application still proceeds and modifies values as before.

1.6 Flexibility of configuration input

The fields entry must be accepted by AddFieldnameSuffixTransformation.from_dict(...) as a list of field names, e.g.:

AddFieldnameSuffixTransformation.from_dict({
    "type": "plain",
    "suffix": ".test",
    "fields": ["field1"],
})

2. Normalization of Partial Regular Expressions

SigmaPartialRegularExpression (in sigma.types)

A SigmaPartialRegularExpression is a regular expression that must match a substring anywhere in the value. At construction time, the regular expression string that is supplied must be normalized so that it ends up anchored with .* on both ends:

  • If the input does not begin with .*, .* is prepended.
  • If the input does not end with .*, .* is appended.

As a consequence, all of the following must be equal to SigmaPartialRegularExpression(".*test.*"):

  • SigmaPartialRegularExpression("test")
  • SigmaPartialRegularExpression(".*test")
  • SigmaPartialRegularExpression("test.*")

When their normalized regular expression strings are equal, two SigmaPartialRegularExpression instances compare equal.

On construction, invalid regular expressions (that cannot be compiled) must raise SigmaRegularExpressionError (from sigma.exceptions). As an example, SigmaPartialRegularExpression("(test.*") must raise SigmaRegularExpressionError.

Summary of the Public API

The items below must be importable and callable as described:

  • sigma.processing.transformations.Transformation — exposing set_processing_item(processing_item).
  • sigma.processing.transformations.FieldMappingTransformation, AddFieldnameSuffixTransformation, WildcardPlaceholderTransformation — each of which supports set_processing_item(...) and applies tracking during apply(pipeline, rule).
  • sigma.processing.pipeline.ProcessingItem — can be constructed as ProcessingItem(transformation, identifier="test").
  • sigma.rule.SigmaDetectionItem — providing add_applied_processing_item(processing_item) and was_processed_by(identifier) -> bool.
  • sigma.rule.SigmaDetection — providing add_applied_processing_item(processing_item), which recurses into nested detections/items.
  • sigma.types.SigmaPartialRegularExpression — applying two-sided .* normalization on construction.

Task: Add Regular Expression Matching of Field Names to the Field Conditions

Summary

The module sigma.processing.conditions contains two processing condition classes, IncludeFieldCondition and ExcludeFieldCondition. Both must support matching a detection item's field name, either by exact string comparison or by regular expression matching.

Public Interface

It must be possible to construct both classes with the following signature:

IncludeFieldCondition(fields, type="plain")
ExcludeFieldCondition(fields, type="plain")
  • fields: a list of strings. What these strings represent depends on the matching type: they are either literal field names or regular expression patterns.
  • type: a string that selects the matching mode. This parameter is optional and defaults to plain (exact) string matching. The two supported values are:
    • "plain" — matching against the field name by exact string equality (the default behavior).
    • "re" — matching against the field name with regular expressions.

Each class must provide the following method:

match(pipeline, detection_item) -> bool

Here, pipeline is a processing pipeline instance, and detection_item is a detection item that carries a field name.

How Matching Behaves

In what follows, F denotes the detection item's field name.

IncludeFieldCondition
  • For type="plain" (the default): match returns True when F is exactly equal to any string in fields, and False otherwise.
  • For type="re": match returns True when F matches any of the regular expression patterns in fields, and False otherwise. A pattern matches when it matches the field name (searching/matching the field name against the pattern, so that patterns like f.* match a field name beginning with f).
ExcludeFieldCondition

Given the same inputs and matching type, ExcludeFieldCondition is the logical negation of IncludeFieldCondition:

  • For type="plain" (the default): match returns False when F is exactly equal to any string in fields, and True otherwise.
  • For type="re": match returns False when F matches any of the regular expression patterns in fields, and True otherwise.

Error Behavior

When a class is constructed with a type value that is not one of the supported values ("plain", "re"), a sigma.exceptions.SigmaConfigurationError must be raised at construction time. The message of that exception must contain the words "Invalid" and "type" (more precisely, the substring "Invalid" followed later by "type", so that it satisfies a match against the pattern Invalid.*type).

Notes and Examples

Consider a detection item whose field name is "otherfield":

  • IncludeFieldCondition(["o[0-9]+", "f.*"], "re").match(...) returns True (a match occurs because the pattern f.* — or a matching pattern — matches "otherfield" ... note: "otherfield" matches because f.* occurs; treat re matching as testing each pattern against the field name).
  • IncludeFieldCondition(["o[0-9]+", "x.*"], "re").match(...) returns False (there is no pattern that matches "otherfield").
  • ExcludeFieldCondition(["o[0-9]+", "f.*"], "re").match(...) returns False.
  • ExcludeFieldCondition(["o[0-9]+", "x.*"], "re").match(...) returns True.

With plain matching against the field name "otherfield":
