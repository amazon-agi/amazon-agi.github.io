Task Specification: WARC Record Creation for Payloads Without HTTP Headers

Objective

Modify the WARCWriter.create_warc_record() method in warcio.warcwriter so that it correctly builds WARC records for record types whose payload does not contain embedded HTTP headers (for example, DNS records of type response and resource), automatically computing the correct Content-Length from the supplied payload.

Public API

The relevant class is WARCWriter located at module path warcio.warcwriter, constructed as:

WARCWriter(filebuf, gzip=False)

The method under change:

create_warc_record(uri, record_type, payload=<stream>, warc_content_type=..., length=..., ...)

where:

  • uri — the WARC target URI (a string), e.g. 'dns:google.com'.
  • record_type — a string, e.g. 'response' or 'resource'.
  • payload — a readable binary stream (e.g. a BytesIO) holding the record block.
  • length — optional; when omitted it must be auto-computed from the payload.

Required Behavior

1. Determining whether HTTP headers are present in the payload

When create_warc_record() is given a payload stream, it must decide whether that payload begins with HTTP headers that should be parsed out into the record's HTTP headers.

  • For a record of type response, if the payload does not begin with a valid HTTP status/response line, then the payload must be treated as an opaque block with no HTTP headers. The full payload content is used as the record block.
  • For a record of type resource, the payload is always treated as an opaque block with no HTTP headers.

Existing behavior for payloads that do begin with valid HTTP headers must continue to work as before.

2. Automatic length computation

When length is not supplied, create_warc_record() must compute the block length by reading the payload stream, so the resulting Content-Length header exactly equals the number of bytes in the payload block. Supplying a payload without an explicit length must produce the correct positive Content-Length (not 0 and never a negative value).

3. Default Content-Type per record type

When warc_content_type is not explicitly provided:

  • A response record must emit Content-Type: application/http; msgtype=response.
  • A resource record must emit Content-Type: application/warc-record.
4. Digests

Both WARC-Payload-Digest and WARC-Block-Digest must be computed over the payload block. When the payload contains no HTTP headers (the block is exactly the payload), these two digests are identical.

Concrete Expected Output

Given a writer created with WARCWriter(stream, gzip=False) and this payload:

20170509000739
google.com.     185 IN  A   209.148.113.239
google.com.     185 IN  A   209.148.113.238
google.com.     185 IN  A   209.148.113.250

(147 bytes, LF line endings, trailing newline included)

Response DNS record — created via create_warc_record('dns:google.com', 'response', payload=BytesIO(payload)) — the serialized record must be:

WARC/1.0\r\n
WARC-Type: response\r\n
WARC-Record-ID: <urn:uuid:...>\r\n
WARC-Target-URI: dns:google.com\r\n
WARC-Date: ...\r\n
WARC-Payload-Digest: sha1:2AAVJYKKIWK5CF6EWE7PH63EMNLO44TH\r\n
WARC-Block-Digest: sha1:2AAVJYKKIWK5CF6EWE7PH63EMNLO44TH\r\n
Content-Type: application/http; msgtype=response\r\n
Content-Length: 147\r\n
\r\n
<147-byte payload>
\r\n\r\n

Resource DNS record — created via create_warc_record('dns:google.com', 'resource', payload=BytesIO(payload)) — the serialized record must be identical to the above except:

  • WARC-Type: resource
  • Content-Type: application/warc-record

In both cases:

  • Content-Length is 147, matching the payload byte count exactly.
  • WARC-Payload-Digest and WARC-Block-Digest are both sha1:2AAVJYKKIWK5CF6EWE7PH63EMNLO44TH.
  • The record block is the payload verbatim, followed by the standard \r\n\r\n record separator.

(The WARC-Record-ID and WARC-Date values are generated as usual; only the constraints above on header names, ordering, and computed values are required.)

Constraints

  • All previously supported record types and payload formats (payloads that begin with HTTP headers) must continue to behave unchanged.

05 Two areas of the WARC library must be adjusted while preserving existing behavior 819 words · rewritten by GPT-5.6-sol

Overview

Two areas of the WARC library must be adjusted while preserving existing behavior: the WARC writer must serialize records whose effective content type has been removed, and the chunked-data reader must safely and exactly pass through payloads that are not valid HTTP chunked-transfer data.

1. WARC Writer — Records Without a Content Type

Record creation API

Writer objects expose the record factory method:

create_warc_record(uri, record_type, payload=..., length=..., warc_content_type=...)

The returned record exposes a mutable content_type attribute.

Content-type selection and compatibility

When no effective warc_content_type override is supplied, the writer must preserve the established content-type selection behavior rather than applying one universal value to every record type. The effective value is selected in this order:

  1. A non-empty warc_content_type supplied by the caller.
  2. A Content-Type already present in supplied WARC headers.
  3. The record type's established default, when one exists.
  4. The generic fallback 'application/warc-record' for a record type with no type-specific default.

The established type-specific defaults include:

Record type Default content_type
warcinfo 'application/warc-fields'
metadata 'application/warc-fields'
response 'application/http; msgtype=response'
revisit 'application/http; msgtype=response'
request 'application/http; msgtype=request'

Thus, for example, a resource record created without an explicit content type receives the generic fallback 'application/warc-record', while response, request, revisit, warcinfo, and metadata records retain their type-specific defaults. The selected value is available through the record's mutable content_type attribute.

Serializing content_type = None

After creation or parsing, a record's content_type may be explicitly set to None. Writing such a record must succeed. In the serialized WARC record-header block, the writer must omit Content-Type entirely. In particular, it must not emit any of the following:

  • Content-Type: None
  • Content-Type: with an empty value
  • A stale Content-Type value left over in the record headers

All other normal writer behavior remains intact, including the WARC version line, ordinary WARC headers, digest calculation, content-length calculation, payload bytes, header/payload separator, and trailing record separator. Header ordering, generated identifiers, dates, and digests continue to follow the writer's normal behavior.

For a resource record targeting ftp://example.com/ with the 9-byte payload b"some\ntext", setting record.content_type = None produces the following logical uncompressed record shape:

WARC/1.0\r\n
WARC-Type: resource\r\n
WARC-Record-ID: <...>\r\n
WARC-Target-URI: ftp://example.com/\r\n
WARC-Date: ...\r\n
WARC-Payload-Digest: sha1:...\r\n
WARC-Block-Digest: sha1:...\r\n
Content-Length: 9\r\n
\r\n
some\ntext\r\n
\r\n

There is no WARC Content-Type header between the block digest and content length.

This omission requirement applies consistently:

  • when the record already has a known content length;
  • when the writer must buffer a record with an unknown or missing content length and recompute its length and digests; and
  • for both plain and gzip writer output. For gzip output, the decompressed WARC record must have the same header omission and logical contents as plain output.

A parsed WARC record that did not contain a Content-Type header has an effective content_type of None; rewriting it must likewise preserve the absence of that header while adding or recomputing other required fields normally.

2. Chunked Data Reader — Exact Non-Chunked Passthrough

Public API

ChunkedDataReader remains importable from warcio.bufferedreaders and is constructed with a byte stream as its first positional argument, with optional decompression selection:

ChunkedDataReader(stream, decomp_type=None)

The stream may be any compatible file-like byte reader, such as io.BytesIO. Its read() method returns bytes. Existing handling of correctly framed chunked data and optional decompression remains unchanged.

Fallback for non-chunked input

If the input cannot be validated as HTTP chunked-transfer encoding, the reader must fall back to non-chunked operation and return the raw input bytes verbatim when no decompression is requested. It must not add, remove, reorder, or alter bytes. Any bytes already inspected while attempting to interpret a chunk-size line, chunk body, or delimiter remain part of the passthrough data.

This requirement includes input whose beginning consists entirely of hexadecimal-looking ASCII characters. A large candidate value is not sufficient to establish chunked framing; if the required framing is absent, the reader must treat the stream as ordinary data rather than failing because the candidate chunk size is numerically too large.

Trailing line endings are data in passthrough mode. In particular, a final \r\n must not be consumed as if it were chunk framing.

Required examples:

ChunkedDataReader(BytesIO(b"ABCDE" * 10)).read()
# b"ABCDE" * 10

ChunkedDataReader(BytesIO(b"ABCDE" * 10 + b"\r\n")).read()
# b"ABCDE" * 10 + b"\r\n"

Both calls must complete without a chunk-size parsing or numeric-overflow failure. The second result retains the final CRLF exactly.

API Surface Summary

  • ChunkedDataReader(stream, decomp_type=None) from warcio.bufferedreaders, with read() returning bytes and exact raw passthrough for invalid/non-chunked framing.
  • Writer objects exposing create_warc_record(uri, record_type, payload=..., length=..., warc_content_type=...). Returned records have a mutable content_type; established record-type defaults are preserved, 'application/warc-record' is the fallback only when no type-specific default applies, and setting content_type to None causes the WARC Content-Type header to be omitted during serialization.
