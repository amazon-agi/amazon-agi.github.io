Overview

Change the simplipy library so that its API client no longer requires callers to provide an aiohttp.ClientSession. Supplying a session must become optional across all client entry points, and the client must function correctly whether or not a session is supplied.

Public API Surface

All of the symbols below are importable from the top-level simplipy package (e.g., from simplipy import API).

API class

The API class must support the following usage patterns:

  • Direct construction without a session:

    API()

    Instantiating API with no arguments must succeed and produce a fully usable client.

  • API.login_via_credentials(email, password) — async classmethod/coroutine.

    • Signature: login_via_credentials(email, password) — it must be callable with exactly the email and password (positional). A session argument is not required.
    • Authenticates with the given credentials and returns a ready-to-use API instance.
    • If the backend rejects the credentials (authentication returns an HTTP 403 with an invalid-credentials payload), it must raise InvalidCredentialsError.

  • API.login_via_token(refresh_token) — async classmethod/coroutine.

    • Signature: login_via_token(refresh_token) — it must be callable with just the refresh token (positional). A session argument is not required.
    • Authenticates with the given refresh token and returns a ready-to-use API instance.

An API instance must expose:

  • request(method, endpoint) — async coroutine that performs an HTTP request against the SimpliSafe API.

    • On a response that is not successful (e.g., HTTP 404), it must raise RequestError.
    • When the current access token is expired (see below), a call to request must transparently obtain a fresh access token by way of the stored refresh token and then complete the request successfully.

  • _access_token — attribute that holds the current access token string.

  • _access_token_expire — attribute that holds a datetime marking the point at which the current access token is considered expired. Callers may set this attribute directly; if it is set to a time in the past, the next request must trigger a token refresh.

  • refresh_token — property that returns the current refresh token string.

  • refresh_token_dirty — boolean property that tells whether the refresh token has changed (become "dirty") since it was last read.

    • Once a token refresh has taken place, this property must read True.
    • Reading the refresh_token property clears the dirty flag, so a read of refresh_token_dirty that immediately follows must be False.

  • get_systems() — async coroutine that returns a list of the System objects associated with the account.

System class
  • It must be possible to construct it as System(api, data), where api is an API instance and data is a dict describing the system.
  • When a System is constructed from data whose data['system']['alarmState'] is an unrecognized value, this must not raise; instead it must emit a log record (via the standard logging module) whose message contains the substring Unknown. The state of the resulting system must resolve to the unknown/fallback state.
  • A System must expose an api attribute that references its owning API instance (so that system.api.request(...), system.api._access_token, system.api._access_token_expire, system.api.refresh_token, and system.api.refresh_token_dirty are all accessible).

Taking away the mandatory session parameter must not change any existing behavior. In particular, the items below must continue to work exactly as they did before, but now with no session supplied by the caller:

  • System.get_events(from_timestamp, count) returns the events belonging to the account.

  • Access to sensor and system properties behaves unchanged.

  • If the system data includes an unrecognized sensor type, the library must emit a log record whose message contains the substring Unknown.

Task Specification: The SimpliSafe API Client Requires an Explicit aiohttp.ClientSession

Summary

The simplipy package offers an asynchronous client for the SimpliSafe service. Every API client must use an aiohttp.ClientSession that its caller creates and supplies. Providing the session is mandatory: an omitted-session form does not exist, and the package must never create an automatic fallback session.

The session lifecycle is owned by the caller, who must keep it open for as long as the API instance, the systems it returns, or their sensors may perform requests. Authentication, token refresh, subscription retrieval, system updates, event retrieval, and state changes must all make use of that same supplied session.

All existing V2 and V3 system, sensor, event, and state-control behavior must keep working with this explicit-session API.

Public Import Locations

The public import locations that already exist must stay available. Specifically:

  • API can be imported via from simplipy import API.
  • System, SystemV2, SystemV3, and SystemStates stay available from simplipy.system.
  • The sensor classes and SensorTypes stay available from simplipy.sensor.
  • SimplipyError, InvalidCredentialsError, and RequestError stay available from simplipy.errors.

simplipy.API

The API class represents a connection to the SimpliSafe service that is either authenticated or unauthenticated.

Constructor
API(websession)
  • websession is a required aiohttp.ClientSession; a default value does not exist for it.
  • A call to API() without a session is not supported.
  • All HTTP traffic must run through the supplied object; API must not create another ClientSession.
  • Building API(websession) directly, with no login, must succeed. The resulting object can be given directly to System.
Authentication Factory Methods
@classmethod
async def login_via_credentials(cls, email, password, websession) -> API
  • email and password hold the account credentials.
  • websession is the required third argument and is the aiohttp.ClientSession that the caller created.
  • On success, the coroutine returns an authenticated API that uses that session.
  • Credentials rejected with an HTTP 403 invalid-credentials response must raise InvalidCredentialsError, not RequestError.
@classmethod
async def login_via_token(cls, refresh_token, websession) -> API
  • refresh_token is a refresh token that was issued previously.
  • websession is the second argument and is required.
  • On success, the coroutine returns an authenticated API whose capabilities are the same as those of one created through credentials.

The public call shapes that are required are exactly (email, password, websession) and (refresh_token, websession), respectively. Neither factory may support authentication by silently manufacturing a session of its own.

Authentication State

An authenticated API — the object exposed through system.api included — provides the following:

  • _access_token: the string for the current access token.
  • _access_token_expire: a datetime that represents when the current access token expires. It stays assignable.
  • refresh_token: the string for the current refresh token. When this property is read, the value is acknowledged and its dirty flag is cleared.
  • refresh_token_dirty: a boolean saying whether the refresh token has changed since it was last read through refresh_token. Reading refresh_token_dirty by itself does not acknowledge the token.
  • user_id: the user identifier of the authenticated account once authentication completes.

When a changed refresh token is installed, it is marked dirty. Reading refresh_token returns the token and flips refresh_token_dirty to False. If the token changes again later, it is marked dirty once more.

Requests and Automatic Refresh
async def request(
    self, method, endpoint, *,
    headers=None, params=None, data=None, json=None, **kwargs
) -> dict
  • method is the HTTP method — "get" or "post", for example.
  • endpoint denotes a service path such as "api/authCheck"; it is resolved beneath the SimpliSafe API base path.
  • The optional request arguments continue to be supported and are sent over the caller's session.
  • Successful JSON responses are returned as decoded Python data even when no JSON content type is advertised by the response.
  • The current access token is carried by authenticated requests.
  • A failing response that is not special, HTTP 404 for instance, or another aiohttp client failure must raise RequestError.

Before an ordinary request goes out, the client must compare _access_token_expire against the current time. If the token has expired — including when a caller assigns a time in the past — the client must first refresh by way of the current refresh token and then carry out the original request. The access token obtained from that refresh must be used, and a changed refresh token must leave refresh_token_dirty as True until refresh_token is read. A refresh must not recursively trigger another refresh.

After authentication has established user_id, an HTTP 403 that indicates an endpoint is unavailable under the account's plan is not treated as invalid credentials. In that case it must:

  1. emit an INFO-level message that contains the phrase "not available";
  2. return an empty mapping from request; and
  3. allow the higher-level update and state methods to return without raising or applying a nonexistent response.

04 Automatic Token Refresh upon a 401 Response 823 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Automatic Token Refresh upon a 401 Response

Background

At the center of this task sits a Python library — one built on asyncio and aiohttp — that functions as a client of the SimpliSafe HTTP API (api.simplisafe.com). The public class API, which the task revolves around, is importable from the library's top-level package. What you must implement is behavior that refreshes the access token automatically whenever the API returns an HTTP 401 response.

The Public API

Everything below must be importable and callable in exactly the manner described.

The API class

  • API.login_via_credentials(email, password, websession) — a coroutine implemented as an async classmethod; authentication happens by means of an email/password pair together with an aiohttp.ClientSession. What it performs is a POST to https://api.simplisafe.com/v1/api/token. When it succeeds, an API instance is returned. Further down, the way it handles a 401 is described.

  • api.get_systems() — an async method (coroutine) whose return value is a list of the system objects belonging to the account. Fetching those systems entails a GET request to https://api.simplisafe.com/v1/users/{user_id}/subscriptions.

  • api.refresh_token — a property through which the current refresh token string is returned.

  • api.refresh_token_dirty — a property (boolean). Its meaning is set out under "Dirty Flag Semantics" below.

Every system object that get_systems() returns exposes the following:

  • system.update() — an async method (coroutine) whose job is refreshing the state of the system. It issues one or more GET requests (e.g. to /v1/users/{user_id}/subscriptions and /v1/subscriptions/{subscription_id}/settings).

  • system.api — a reference to the API instance that owns the system (with the result that system.api.refresh_token, system.api.refresh_token_dirty, etc. are accessible).

Exception Class
  • InvalidCredentialsError — an exception class, importable from the library's errors/exceptions module (and re-exported too, so that existing import paths continue to work). It is raised in the manner described below.

Behavior Requirements

The Token Endpoint

Refreshing the token is done by way of a POST to https://api.simplisafe.com/v1/api/token. If the response is a successful one (HTTP 200), its JSON contains the new credentials, a new refresh token among them. Once a refresh has succeeded, an auth-check GET to https://api.simplisafe.com/v1/api/authCheck may then follow, as part of establishing the refreshed session.

401 during the Initial Login

Should the token POST in login_via_credentials — that is, the initial credential login — itself return HTTP 401, InvalidCredentialsError is raised. In this case, no retry attempt is made.

401 during an Authenticated Request — Retry Logic

Take the case of any authenticated request — for example the fetching of subscriptions during get_systems() / system.update() — that receives an HTTP 401 response:

  1. The first 401 does not result in an immediate failure. Instead, an attempt to refresh the access token is made, via a token-refresh POST to /v1/api/token.

  2. If the refresh succeeds (the token endpoint returns 200): the stored credentials — the refresh token included — are updated, and the original request, the one that failed with the 401, undergoes a transparent retry. The overall operation then completes normally, using the successful response of the retried request. Success, rather than an error, is what the caller observes.

  3. If the refresh itself returns 401 (an unsuccessful refresh): InvalidCredentialsError is raised. Whenever a refresh attempt is unsuccessful, an informational log record must be emitted — one whose message contains the word "unsuccessful". Exactly one log record of this kind is emitted for each unsuccessful refresh attempt. The INFO level is where logging must occur (i.e., the record is visible when the logger has been configured for INFO).

Dirty Flag Semantics — refresh_token_dirty

refresh_token_dirty is a boolean that signals two things: since it was last read, the refresh token has been updated (rotated), and the new value has yet to be consumed by the consumer:

  • The stored refresh token gets replaced by a successful automatic token refresh; immediately after that, refresh_token_dirty evaluates to True.
  • A read of the refresh_token property is what consumes/acknowledges the new value: refresh_token_dirty evaluates to False after refresh_token has been read.

To make this concrete, here is the sequence that must hold once a 401 has triggered a successful automatic refresh:

  1. The value of refresh_token_dirty is True.
  2. A read of refresh_token returns the refresh token value that was newly issued.
  3. refresh_token_dirty is False immediately after that read.

Summary of the Request Flow for a Successful Recovery

  1. A 401 is returned by an authenticated GET.
  2. The client carries out a token-refresh POST → 200 with new credentials.
  3. The client carries out an auth-check GET → 200.
  4. The original authenticated request is retried by the client → 200.
  5. The operation returns successfully; the refresh token has been rotated, and the dirty flag remains set until read.

Notes

  • Beyond a single refresh attempt per initial 401, do not add retry behavior.
  • The authenticated data requests made in the course of fulfilling get_systems() and system.update() are covered by this behavior uniformly.
