01 Modify the simplipy library so that its API client no longer requires callers to supply an aiohttp.ClientSession. 796 words · source specification

Overview

Modify the simplipy library so that its API client no longer requires callers to supply an aiohttp.ClientSession. Providing a session must become optional across all client entry points, and the client must function correctly whether or not one is provided.

Public API Surface

All symbols below are importable from the top-level simplipy package (e.g., from simplipy import API).

API class

The API class must support the following usage patterns:

  • Direct construction with no session:

    API()

    Constructing API with no arguments must succeed and produce a fully usable client.

  • API.login_via_credentials(email, password) — async classmethod/coroutine.

    • Signature: login_via_credentials(email, password) — must be callable with exactly the email and password (positional). No session argument is required.
    • Authenticates using the given credentials and returns a ready-to-use API instance.
    • If the credentials are rejected by the backend (authentication returns an HTTP 403 with an invalid-credentials payload), it must raise InvalidCredentialsError.

  • API.login_via_token(refresh_token) — async classmethod/coroutine.

    • Signature: login_via_token(refresh_token) — must be callable with just the refresh token (positional). No session argument is required.
    • Authenticates using the given refresh token and returns a ready-to-use API instance.

An API instance must expose:

  • request(method, endpoint) — async coroutine to perform an HTTP request against the SimpliSafe API.

    • On a non-successful response (e.g., HTTP 404), it must raise RequestError.
    • When the current access token is expired (see below), calling request must transparently obtain a fresh access token using the stored refresh token and then complete the request successfully.

  • _access_token — attribute holding the current access token string.

  • _access_token_expire — attribute holding a datetime marking when the current access token is considered expired. Callers may set this attribute directly; if it is set to a past time, the next request must trigger a token refresh.

  • refresh_token — property returning the current refresh token string.

  • refresh_token_dirty — boolean property indicating whether the refresh token has changed (become "dirty") since it was last read.

    • After a token refresh occurs, this property must read True.
    • Reading the refresh_token property clears the dirty flag, so an immediately following read of refresh_token_dirty must be False.

  • get_systems() — async coroutine returning a list of System objects associated with the account.

System class
  • Must be constructible as System(api, data) where api is an API instance and data is a dict describing the system.
  • Constructing a System from data whose data['system']['alarmState'] is an unrecognized value must not raise; instead it must emit a log record (via the standard logging module) whose message contains the substring Unknown. The resulting system's state must resolve to the unknown/fallback state.
  • A System must expose an api attribute referencing its owning API instance (so system.api.request(...), system.api._access_token, system.api._access_token_expire, system.api.refresh_token, and system.api.refresh_token_dirty are all accessible).

Behavior That Must Be Preserved

Removing the mandatory session parameter must not change any existing behavior. In particular, the following must continue to work exactly as before, but now without any caller-supplied session:

  • get_systems() returns the correct systems for both v2 and v3 accounts, including correct serial, system_id, api._access_token, and sensor counts.
  • System.update() refreshes system data correctly for both v2 and v3.
  • System.get_events(from_timestamp, count) returns the account's events.
  • State-changing methods set_away(), set_home(), and set_off() correctly update system.state; calling set_off() when already off remains valid.
  • Sensor and system property access behaves unchanged.
  • When the backend reports a feature as unavailable (HTTP 403 with an unavailable-feature payload) during operations such as update() and set_away(), the library must log informational records whose messages contain the substring not available (one such record per affected operation).
  • When system data contains an unrecognized sensor type, the library must emit a log record whose message contains the substring Unknown.

Constraints

  • All existing API methods and System methods that previously required a session must remain functionally identical aside from the session becoming optional.
  • When no session is provided by the caller, the client must create and manage its own session internally so that all network operations succeed.
  • Each API client instance must operate independently (constructing a new client with no session must yield a self-contained, working client).

Error / Exception Types

The following exception types must be importable from the simplipy package (or its errors module, consistent with existing import paths):

  • RequestError — raised on failed HTTP requests.
  • InvalidCredentialsError — raised on rejected credentials.
  • SimplipyError — base library error (e.g., raised when accessing the triggered attribute of a non-entry sensor in a v2 system).

Enums

  • SystemStates enum must include at least the members off, away, and home, plus an unknown/fallback member used when an unrecognized alarmState is encountered.
  • SensorTypes enum must include at least the keypad member.

Task Specification: Require an Explicit aiohttp.ClientSession for the SimpliSafe API Client

Overview

The simplipy package provides an asynchronous client for the SimpliSafe service. Every API client must use an aiohttp.ClientSession created and supplied by its caller. Supplying the session is mandatory: there is no omitted-session form and the package must never create an automatic fallback session.

The caller owns the session lifecycle and must keep it open for as long as the API instance, its returned systems, or their sensors may perform requests. Authentication, token refresh, subscription retrieval, system updates, event retrieval, and state changes must all use that same supplied session.

All existing V2 and V3 system, sensor, event, and state-control behavior must continue to work with this explicit-session API.

Public Imports

Existing public import locations must remain available. In particular:

  • API is importable with from simplipy import API.
  • System, SystemV2, SystemV3, and SystemStates remain available from simplipy.system.
  • Sensor classes and SensorTypes remain available from simplipy.sensor.
  • SimplipyError, InvalidCredentialsError, and RequestError remain available from simplipy.errors.

simplipy.API

API represents an authenticated or unauthenticated connection to the SimpliSafe service.

Constructor
API(websession)
  • websession is a required aiohttp.ClientSession. It has no default value.
  • API() without a session is not a supported call.
  • The supplied object must be used for all HTTP traffic; API must not create another ClientSession.
  • Constructing API(websession) directly, without logging in, must succeed. The resulting object can be passed directly to System.
Authentication factories
@classmethod
async def login_via_credentials(cls, email, password, websession) -> API
  • email and password are the account credentials.
  • websession is the required third argument and is the caller-created aiohttp.ClientSession.
  • On success, the coroutine returns an authenticated API using that session.
  • Rejected credentials represented by an HTTP 403 invalid-credentials response must raise InvalidCredentialsError, not RequestError.
@classmethod
async def login_via_token(cls, refresh_token, websession) -> API
  • refresh_token is a previously issued refresh token.
  • websession is the required second argument.
  • On success, the coroutine returns an authenticated API with the same capabilities as one created through credentials.

The required public call shapes are exactly (email, password, websession) and (refresh_token, websession) respectively. Neither factory may support authentication by silently manufacturing its own session.

Authentication state

An authenticated API, including the object exposed through system.api, provides:

  • _access_token: the current access-token string.
  • _access_token_expire: a datetime representing when the current access token expires. It remains assignable.
  • refresh_token: the current refresh-token string. Reading this property acknowledges the value and clears its dirty flag.
  • refresh_token_dirty: a boolean indicating whether the refresh token has changed since it was last read through refresh_token. Reading refresh_token_dirty alone does not acknowledge the token.
  • user_id: the authenticated account's user identifier once authentication completes.

Installing a changed refresh token marks it dirty. Reading refresh_token returns the token and changes refresh_token_dirty to False. A later token change marks it dirty again.

Requests and automatic refresh
async def request(
    self, method, endpoint, *,
    headers=None, params=None, data=None, json=None, **kwargs
) -> dict
  • method is the HTTP method, such as "get" or "post".
  • endpoint is a service path such as "api/authCheck"; it is resolved beneath the SimpliSafe API base path.
  • The optional request arguments continue to be supported and are sent through the caller's session.
  • Successful JSON responses are returned as decoded Python data even when the response does not advertise a JSON content type.
  • Authenticated requests carry the current access token.
  • A non-special failing response, such as HTTP 404, or another aiohttp client failure must raise RequestError.

Before an ordinary request is issued, the client must compare _access_token_expire with the current time. If the token has expired, including when a caller assigns a time in the past, the client must first refresh via the current refresh token and then proceed with the original request. The newly obtained access token must be used, and a changed refresh token must leave refresh_token_dirty as True until refresh_token is read. Refreshing must not recursively trigger another refresh.

After authentication has established user_id, an HTTP 403 indicating that an endpoint is unavailable under the account's plan is not treated as invalid credentials. It must:

  1. emit an INFO-level message containing the phrase "not available";
  2. return an empty mapping from request; and
  3. allow higher-level update and state methods to return without raising or applying a nonexistent response.
Subscription and system discovery
async def get_subscription_data(self) -> dict
async def get_systems(self) -> list
  • get_subscription_data() returns the active subscription/location response for the authenticated user.
  • get_systems() returns one version-appropriate system object for each active subscription. Version 2 locations produce SystemV2; version 3 locations produce SystemV3.
  • Each system's api attribute refers to the same API object that created it, including its session and authentication state.
  • Before a system is returned, its sensor collection is populated using the appropriate V2 or V3 service behavior.
  • Credential and refresh-token authentication must produce equivalent system objects and populated sensor collections.

Systems

  • api is an API instance, including one created directly as API(websession).
  • data is location data containing at least {'system': {'alarmState': <str>, ...}} for state initialization.
  • Construction initializes sensors as a mapping keyed by sensor serial number.

Version-specific systems returned by get_systems() retain these public attributes and properties:

  • api: the originating API instance.
  • address: the location's street address.
  • alarm_going_off: whether the system is currently alarming.
  • serial: the system serial number.
  • state: the current SystemStates value.
  • system_id: the service identifier for the system/subscription.
  • temperature: the system's reported overall temperature.
  • version: 2 or 3.
  • sensors: a dictionary from serial strings to SensorV2 or SensorV3 objects.

SystemStates retains these members and values:

  • alarm_count = 1
  • away = 2
  • away_count = 3
  • entry_delay = 4
  • error = 5
  • exit_delay = 6
  • home = 7
  • home_count = 8

Events

This returns the response's event list. When supplied, from_timestamp and num_events are sent as the corresponding event-query parameters. Omitting them retrieves the service's default event range.

State control
async def set_away(self) -> None
async def set_home(self) -> None
async def set_off(self) -> None

These methods use the correct V2 or V3 operation, and a successful response updates state to SystemStates.away, SystemStates.home, or SystemStates.off. Requesting the already-current state is a successful no-op and leaves the state unchanged. If remote management is unavailable for the account plan, the unavailable-feature behavior described above applies and the state is not falsely changed.

Updating
async def update(self, refresh_location=True, cached=True) -> None
  • With refresh_location=True, location-level data and the system state are refreshed before sensor data.
  • cached retains its existing meaning: V2 uses it as the cached settings choice, while V3 requests a forced refresh when cached is false.
  • Existing sensor objects with matching serial numbers receive updated data, and newly discovered serial numbers are added to sensors.
  • Empty responses caused by an unavailable plan return cleanly without corrupting the existing collection.

Sensors

Sensors remain version-specific and are stored under their serial-number keys. Individual sensors are not updated independently; callers refresh them through their parent system's update() method.

SensorTypes retains these members and values:

  • keychain = 2
  • panic_button = 3
  • motion = 4
  • entry = 5
  • glass_break = 6
  • carbon_monoxide = 7

V2 sensor behavior

SensorV2 exposes:

  • data: the raw integer sensor data.
  • error: the sensor error flag.
  • low_battery: true when the reported battery value is not "ok"; a missing battery value is treated as okay.
  • settings: the raw V2 setting value.
  • trigger_instantly: the V2 instant-trigger flag.
  • triggered: for entry sensors, true only when entry status is "open"; missing status is treated as closed. Accessing triggered on any non-entry V2 sensor raises SimplipyError.
V3 sensor behavior

  • low_battery: the low-battery flag.
  • offline: the offline flag.
  • settings: the V3 settings dictionary.
  • trigger_instantly: the instantTrigger setting where that setting applies.
  • triggered: the reported triggered status for motion, entry, glass-break, carbon-monoxide, smoke, leak, and temperature sensors, defaulting to false when absent. Other V3 sensor types, including sirens, return false.
  • temperature: the reported temperature for a temperature sensor. Accessing this property on a non-temperature sensor raises AttributeError.

Errors

The exception hierarchy remains public through simplipy.errors:

  • SimplipyError is the package's base exception.
  • InvalidCredentialsError derives from SimplipyError and represents rejected login credentials.
  • RequestError derives from SimplipyError and represents ordinary request failures.

Unsupported sensor-property access retains the version-specific behavior described above rather than being converted to RequestError.

04 Automatic Token Refresh on 401 Response 660 words · source specification

Task Specification: Automatic Token Refresh on 401 Response

Context

This task concerns a Python library (using asyncio and aiohttp) that acts as a client for the SimpliSafe HTTP API (api.simplisafe.com). The relevant public class is API, importable from the library's top-level package. You must implement automatic access-token refresh behavior when the API returns an HTTP 401 response.

Public API Surface

The following must be importable and callable exactly as described.

API class

  • API.login_via_credentials(email, password, websession) — an async classmethod (coroutine) that authenticates using an email/password pair and an aiohttp.ClientSession. It performs a POST to https://api.simplisafe.com/v1/api/token. On success it returns an API instance. Its 401 handling behavior is described below.

  • api.get_systems() — an async method (coroutine) returning a list of system objects associated with the account. Retrieving systems involves a GET request to https://api.simplisafe.com/v1/users/{user_id}/subscriptions.

  • api.refresh_token — property returning the current refresh token string.

  • api.refresh_token_dirty — property (boolean). See "Dirty Flag Semantics" below.

Each system object returned by get_systems() exposes:

  • system.update() — an async method (coroutine) that refreshes the system's state. This performs one or more GET requests (e.g. to /v1/users/{user_id}/subscriptions and /v1/subscriptions/{subscription_id}/settings).

  • system.api — a reference to the owning API instance (so that system.api.refresh_token, system.api.refresh_token_dirty, etc. are accessible).

Exception
  • InvalidCredentialsError — an exception class importable from the library's errors/exceptions module (and re-exported such that existing import paths continue to work). Raised as described below.

Required Behavior

Token endpoint

The token refresh operation is a POST to https://api.simplisafe.com/v1/api/token. A successful response (HTTP 200) returns JSON containing new credentials including a new refresh token. After a successful refresh, an auth-check GET to https://api.simplisafe.com/v1/api/authCheck may follow as part of establishing the refreshed session.

401 during initial login

If the initial credential login (the token POST in login_via_credentials) itself returns HTTP 401, raise InvalidCredentialsError. No retry is attempted for this case.

401 during an authenticated request — retry logic

When any authenticated request (such as fetching subscriptions during get_systems() / system.update()) receives an HTTP 401 response:

  1. On the first 401, do not immediately fail. Instead, attempt to refresh the access token by issuing a token-refresh POST to /v1/api/token.

  2. If the refresh succeeds (token endpoint returns 200): update the stored credentials (including the refresh token) and transparently retry the original request that failed with the 401. The overall operation then completes normally using the retried request's successful response. The caller observes success, not an error.

  3. If the refresh itself returns 401 (refresh unsuccessful): raise InvalidCredentialsError. When a refresh attempt is unsuccessful, an informational log record must be emitted whose message contains the word "unsuccessful". Exactly one such log record is emitted per unsuccessful refresh attempt. Logging must occur at the INFO level (i.e., visible when the logger is configured for INFO).

Dirty Flag Semantics — refresh_token_dirty

refresh_token_dirty is a boolean indicating that the refresh token has been updated (rotated) since it was last read, and that the consumer has not yet consumed the new value:

  • Immediately after a successful automatic token refresh has replaced the stored refresh token, refresh_token_dirty evaluates to True.
  • Reading the refresh_token property consumes/acknowledges the new value: after refresh_token has been read, refresh_token_dirty evaluates to False.

Concretely, the following sequence must hold after a successful automatic refresh triggered by a 401:

  1. refresh_token_dirty is True.
  2. Reading refresh_token returns the newly issued refresh token value.
  3. Immediately after that read, refresh_token_dirty is False.

Summary of Request Flow for a Successful Recovery

  1. Authenticated GET returns 401.
  2. Client performs token-refresh POST → 200 with new credentials.
  3. Client performs auth-check GET → 200.
  4. Client retries the original authenticated request → 200.
  5. Operation returns successfully; refresh token has been rotated and the dirty flag is set until read.

Notes

  • Do not add retry behavior beyond a single refresh attempt per initial 401.
  • The behavior applies uniformly to authenticated data requests made while fulfilling get_systems() and system.update().

Overview

This includes a new Lock entity type with state management (lock/unlock operations), lock-specific properties, and integration into the existing System object. Data Model

Systems are populated from a sensors/devices payload. Each device entry contains at least:

  • serial: string identifier
  • type: integer device type
  • name: string
  • status: object (structure varies by device type)
  • flags: object with swingerShutdown, lowBattery, offline booleans
  • setting: object

A lock device (type == 16) has a status object with these fields:

  • pinPadState: int
  • lockState: int (1 means locked)
  • pinPadOffline: bool
  • pinPadLowBattery: bool
  • lockDisabled: bool
  • lockLowBattery: bool
  • calibrationErrDelta: int
  • calibrationErrZero: int
  • lockJamState: int

Devices whose type does not correspond to a known/handled entity (e.g. type == 253 with an empty status object) must not break parsing; they are simply added to the general device/sensor collection and ignored by lock handling.

When a V3 system is populated from the standard test fixture, system.sensors must contain 22 entries. All devices from the payload — including lock devices and unknown-type devices — count toward this collection. (Previously this count was 21; the new fixture adds a lock device and an unknown-type device, bringing it to 22.)

Lock Behavior

Properties (read-only)

A Lock object exposes the following boolean properties, derived from the device status fields:

  • disabled → status["lockDisabled"]
  • error → true when there is a calibration error, i.e. when calibrationErrDelta or calibrationErrZero indicates an error (both are 0 = no error in the standard fixture, so this is False)
  • jammed → derived from lockJamState (0 = not jammed → False)
  • lock_low_battery → status["lockLowBattery"]
  • low_battery → from the device flags.lowBattery
  • offline → from the device flags.offline
  • pin_pad_low_battery → status["pinPadLowBattery"]
  • pin_pad_offline → status["pinPadOffline"]

For the standard fixture (all the above status/flag fields are False/0), every one of these properties must evaluate falsy.

  • state → a LockStates value. When lockState is 1, state is LockStates.locked. This property reflects the lock's current known state and updates when lock/unlock operations succeed.
Operations

Provide two async methods on Lock:

  • async def lock(self) — sends a request to lock the door lock.
  • async def unlock(self) — sends a request to unlock the door lock.

Both methods issue an HTTP POST to:

/v1/doorlock/{SUBSCRIPTION_ID}/{LOCK_ID}/state

where SUBSCRIPTION_ID is the system's subscription id and LOCK_ID is the lock's serial number.

The response body is a JSON object of the form {"state": "lock"} (for a successful lock) or {"state": "unlock"} (for a successful unlock).

On a successful unlock(), the lock's state becomes LockStates.unlocked. On a successful lock(), the lock's state becomes LockStates.locked. These state transitions must be observable immediately after the awaited call returns.

If an operation's remote request fails (server responds with HTTP 401, and the subsequent token-refresh attempt also fails with 401), the operation must raise simplipy.errors.InvalidCredentialsError, and the local state must remain unchanged.

Concretely:

  • If a lock is currently LockStates.locked and unlock() fails as described, the call raises InvalidCredentialsError and the lock's state remains LockStates.locked.

This same guarantee applies to the existing System arming operations:

  • If system.state is SystemStates.off and system.set_away() fails (POST to /v1/ss3/subscriptions/{SUBSCRIPTION_ID}/state/away returns 401 and token refresh returns 401), the call raises InvalidCredentialsError and system.state remains SystemStates.off.

In other words, local state must only be updated after a successful remote response; a failure must leave prior state intact.

Existing Imports That Must Remain Valid

  • from simplipy import API
  • from simplipy.errors import InvalidCredentialsError, PinError
  • from simplipy.system import System, SystemStates
  • from simplipy.entity import EntityTypes
  • from simplipy.lock import LockStates

SystemStates must expose SystemStates.off.

InvalidCredentialsError and PinError must be raisable exception types in simplipy.errors.

Constraints on Scope

Do not change existing behavior beyond what is described here (PIN handling, sensor parsing for non-lock devices, system arming state transitions on success, etc. remain as-is). The only new observable behaviors are: the Lock entity and its API, the locks mapping on System, the increased device count due to the two new devices in the fixture, and the "no state change on failure" guarantee for both lock operations and system arming.
