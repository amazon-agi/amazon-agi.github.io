Task Description

Summary

Build the public table2ascii renderer. It takes optional header, body, and footer rows and turns them into a single Unicode box-drawing table string. The first column is a key column, divided from the remaining value columns by a double vertical rule; value columns are separated from each other by whitespace rather than vertical rules.

Public Interface

The table2ascii package/module must export the callable directly:

from table2ascii import table2ascii


def table2ascii(header_row=None, body=None, footer_row=None) -> str:
    ...

All three arguments may be given positionally or by keyword; each one defaults to None.

  • header_row: an optional list of strings, one entry per column.
  • body: an optional list of rows, each of which is a list of strings.
  • footer_row: an optional list of strings, one entry per column.

Sections that are missing or empty are omitted. Every non-empty header, body row, and footer is part of the same table and must have the same number of columns. The function returns the complete table in string form.

Table and Column Layout

For a table that has n columns:

  • Column 0 serves as the key column.
  • Columns 1 through n - 1 are the value columns.
  • In content lines, ║ separates the key and value regions; border/separator lines use the corresponding junction character for this separation.
  • Adjacent value columns are separated by whitespace; vertical box-drawing separators are not placed between them.

Automatic Width Calculation and Footer Compatibility

For each column i, define m_i as the largest len(cell) in that column over all supplied content rows:

  • the header, if present;
  • every body row, if present; and
  • the footer, if present.

Footer content therefore takes part in the width calculation exactly as header and body content do. No content is truncated.

For tables with no footer, the content width is w_i = m_i. When a non-empty footer is supplied, the established footer-bearing layout is preserved by applying a minimum content width of three characters: w_i = max(3, m_i). The complete visible field for column i is f_i = w_i + 2, which accounts for one outer space on each side of the centered content area. Consequently, footer-bearing cells that contain at most three characters use the established fixed five-character fields; longer content expands its column instead of being truncated.

Alignment and Spacing of Cells

Every cell — header, body, and footer cells in both key and value columns included — is centered inside its column's w_i-character content area. When an odd number of spare spaces is required for centering, the extra space goes on the left.

For cell text s in column i, with d = w_i - len(s), the complete field is:

<one space><ceil(d / 2) spaces><s><floor(d / 2) spaces><one space>

Equivalently, let field_i(s) denote that complete field. A content line takes the form:

║field_0(s0)║field_1(s1) field_2(s2) ... field_(n-1)(sN)║

The one literal space between complete value fields combines with the trailing space of one field and the leading space of the next; as a result, adjacent value content areas are separated by exactly three spaces, before any centering space inside those areas is taken into account. The value region also contains one outer space immediately after the key divider and one immediately before the right border. For a one-column table, the line is just ║field_0(s0)║ and contains no key/value divider.

Value cells are consequently centered, not left-aligned. Notably, a one-character value in a two-character content area is given the spare space before the value.

Borders and Separator Lines

Use these Unicode box-drawing characters:

  • Top border: ╔, ═, ╦, ╗
  • Header and footer separators: ╟, ─, ╫, ╢
  • Bottom border: ╚, ═, ╩, ╝
  • Content borders and key divider: ║

For two or more columns, define the visible value-region width as:

R = f_1 + f_2 + ... + f_(n-1) + (n - 2)

The last term accounts for the single literal separator between each pair of value fields. The border lines are then:

╔ + (═ repeated f_0 times) + ╦ + (═ repeated R times) + ╗
╟ + (─ repeated f_0 times) + ╫ + (─ repeated R times) + ╢
╚ + (═ repeated f_0 times) + ╩ + (═ repeated R times) + ╝

These expressions denote concatenation, not literal + characters. In each region, the number of horizontal fill characters must exactly equal that region's visible width in a content line. For a one-column table, leave out the middle junction and value region, using only the left corner/connector, f_0 fill characters, and the right corner/connector.

Ordering of Sections

Assemble the output in this order:

  1. Top border.
  2. If a header is present: the header content line, immediately followed by a header separator.
  3. Every body content line, in input order.
  4. If a footer is present: a footer separator, immediately followed by the footer content line.
  5. Bottom border.

Whenever a header is present, a header separator is emitted, even when no body follows it. Whenever a footer is present, a footer separator is emitted, even when there is no header or body. Thus, when a header and footer are supplied without a body, the header separator and the footer separator form consecutive lines.

Each rendered line, the bottom border included, ends with \n.

When all three sections are missing or empty, keep the empty-frame result:

╔═════╗
╚═════╝

A newline also follows each line in this result. For an empty section, no header or footer separator is emitted.

Contract for rendering

Column widths and alignment

For every column, take the widest string that appears in that column across all supplied sections. The width of the rendered slot for that column is then that widest content width plus two spaces.

Each cell is centered within its slot, and it always has at least one space on each side. When the centering space that remains is odd, the extra space is put before the value. Equivalently, for a value whose length is n in a column whose widest value has length m, use:

  • the value is preceded by 1 + ceil((m - n) / 2) spaces; and
  • the value is followed by 1 + floor((m - n) / 2) spaces.

Width calculation takes into account all supplied sections, including a footer in cases where no body is present.

Borders, separation of columns, and separators between sections

  • For the top border, the characters ╔, ═, ╦, and ╗ are used.

Validation of Presence and Column Count

A section counts as absent when it is None or an empty section list ([]). Specifically, an empty body contributes no rows, and an empty header or footer emits neither a content row nor a separator for that section.

The number of cells must be the same for every present row. Once this consistency requirement is satisfied, the column count is taken from any present header, footer, or body row. Whenever present rows disagree, raise ValueError; this includes any of the following cases:

  • a non-empty header and a non-empty footer differ in length;
  • any body row differs in length from a non-empty header;
  • any body row differs in length from a non-empty footer; or
  • body rows differ in length from one another, even when no header or footer is supplied.

No column-count constraint of its own is imposed by an absent or empty section.

Column Widths and Alignment of Cells

Treat each column independently and inspect that column in every present header, body, and footer row. If M_i is the greatest content display width in column i, the rendered field width of that column is:

w_i = M_i + 2

The two added positions guarantee at least one space on each side of every value.

Every cell in every section is centered within its computed field width; this holds equally for the first column and for header, body, and footer cells. For content whose width is n in a field whose width is w, let P = w - n and render:

floor(P / 2) spaces + content + ceil(P / 2) spaces

So when the total padding is odd, the smaller share goes before the value and the one extra space goes after it. This is centered alignment whose tie-breaking is right-biased, not left alignment. For example:

  • "G" in a field of width 5 is rendered as " G ";
  • "30" in a field of width 5 is rendered as " 30 ";
  • "G" in a field of width 4 is rendered as " G ".

Geometry of the Table

Unicode box-drawing characters are used by the renderer.

Grouping of Columns

A double vertical divider (║) visually separates the first column from all remaining columns. The columns after the first make up one visual region, separated from one another by a single space rather than by vertical rules.

For fields f0, f1, ..., the shape taken by a content row with multiple columns is:

║f0║f1 f2 ...║

The inter-column spaces in the remaining-column region exist in addition to the padding already contained in each field. With only a single column, no remaining-column region or internal divider exists, and the row takes the shape ║f0║.

Lines for Borders and Separators
  • The top border is drawn with ╔, ╦, and ╗, filled with ═.
  • The bottom border is drawn with ╚, ╩, and ╝, filled with ═.
  • A section separator is drawn with ╟, ╫, and ╢, filled with ─.
  • In content rows, ║ is used at both outer edges and between the first column and the remaining-column region.

The internal junction (╦, ╩, or ╫) is present whenever there is a remaining-column region. Borders and section separators retain the same widths as content rows. No tees or crosses are used to mark the boundaries between columns after the first; their complete shared region is filled continuously with the applicable horizontal character.

Output Ordering and Section Behavior

Lines are emitted in this exact order:

  1. The top border.
  2. If the header is present and non-empty, emit the header row, followed by a section separator.
  3. All body rows in their input order, with no separator between body rows.
  4. If the footer is present and non-empty, emit a section separator, followed by the footer row.
  5. The bottom border.

The consequences of this ordering include the following:

  • When there is no header, body rows begin immediately below the top border.
  • Even with no body, a header is still followed by its separator and then by whatever comes next.
  • There is always a separator immediately before a footer, even if no body rows and no header are present.
  • If a header and footer are present but the body is absent or empty, both the post-header separator and the pre-footer separator are emitted, so two identical separator lines are adjacent.
  • A separator is emitted only for its corresponding non-empty header or footer section.

Every emitted line, the bottom border included, is followed by \n.

How the Table Is Rendered

The output is a grid surrounded by borders. A non-empty header supplies one row; the body rows appear in the order they were supplied; a non-empty footer likewise supplies one row. To work out the column widths, the values found in every non-empty section that is present are used.

When the list given for header or body is empty, it counts as absent: it supplies no rows and no section of its own. More generally, an empty section does not result in its header/footer boundary divider being emitted.

Widths of columns, padding, and alignment

The field width belonging to a column is found by taking the length of the widest cell that occurs in that column across the header, all body rows, and the footer, and then adding two characters for the mandatory minimum padding of one space on each side.

Centering within that field width is applied to every cell. Calculate:

extra = field_width - len(cell_text) - 2

The field is then filled as follows:

  • 1 + floor(extra / 2) spaces before the cell text; and
  • 1 + ceil(extra / 2) spaces after the cell text.

If the surplus cannot be split evenly, the additional space therefore ends up after the cell content. No matter whether a cell's column lies in a single-column heading region or in a multi-column region, this centering rule applies to it.

Where two adjacent columns meet at an ordinary boundary, the two padded fields have one space between them instead of a vertical border. Where a heading boundary is enabled, ║ is what separates them. Hence, adjacent columns that no heading divider splits make up one contiguous region, yet each of them keeps its own field width and alignment.

Heading separators for the first and last columns

Which internal double-line heading boundaries appear is chosen by the two boolean options:

  • first_col_heading=True produces a heading separator drawn immediately after the first column.
  • last_col_heading=True produces a heading separator drawn immediately before the last column.
  • Both options may be enabled at once; both heading separators are then drawn.
  • If both options are False, the table has no internal vertical heading separators, and all columns make up one contiguous region bounded only by the table's outer edges.

For a table with five columns, the regions come out as follows:

  • first_col_heading=True, last_col_heading=False: column 0, followed by columns 1–4.
  • first_col_heading=False, last_col_heading=True: columns 0–3, followed by column 4.
  • first_col_heading=True, last_col_heading=True: column 0, then columns 1–3, and finally column 4.
  • first_col_heading=False, last_col_heading=False: columns 0–4 forming one region.

Throughout the table, each enabled heading boundary appears as:

  • ╦ in the top border;
  • ║ in content rows;
  • ╫ in horizontal section dividers; and
  • ╩ in the bottom border.

In content rows, an ordinary column boundary shows up as a space, while the horizontal stroke simply continues through that position in border and divider rows.

Characters used for the box drawing

These are the characters the output is made of:

  • top border: ╔, ═, ╦, ╗;
  • content edges and enabled heading separators: ║;
  • section dividers: ╟, ─, ╫, ╢;
  • bottom border: ╚, ═, ╩, ╝.
Dividers between sections

The header and footer divider rules hold no matter whether body rows are present:

  • Immediately after every non-empty header row comes one horizontal divider.
  • Immediately before every non-empty footer row comes one horizontal divider.
  • Beyond these cases, body rows introduce no horizontal dividers.

As a consequence:

  • a table containing only a header gets a divider after that header;
  • a table containing only a footer gets a divider before that footer;

Rules for Rendering

Sections of the table

Every rendered table has a top border and a bottom border. In between, the sections that are present are emitted in exactly this order:

  1. When a non-empty header is present, emit the header row and then a horizontal section separator.
  2. Emit each body row in its given order. Between body rows there are no horizontal separators.
  3. When a non-empty footer is present, emit a horizontal section separator and then the footer row.

A section separator is tied to the header or the footer, not to whether a body is present. As a result:

  • a table with only a header has a separator immediately after that header;
  • a table with only a footer has a separator immediately before that footer;
  • a table with only a body has no section separator;
  • a header and a footer, with no body, produce two consecutive separator lines;
  • an empty header, body, or footer acts as though that section were None.

Every line of output, including the bottom border, ends with \n.

Column sizing

Each column has a field width of its own. With automatic sizing (column_widths=None), a column's width is:

maximum character length of any value in that column + 2

That maximum is taken over every value present in the header, body, and footer. The two extra characters give at least one immediate padding space on each side of a value.

A column_widths list that is supplied overrides automatic sizing. Each entry denotes the full requested width of the rendered field for that column, value and padding included.

Between each pair of adjacent column fields there is also one character position. On content rows, this position is either a heading-divider character or a space. On horizontal border/separator rows, it is either the matching heading junction or the row's horizontal fill character. Adjacent columns with no heading divider therefore form one visually continuous region instead of gaining ordinary vertical grid lines.

When alignments is omitted, every column uses Alignment.CENTER. The alignment selected for a column applies consistently to its header value, to all its body values, and to its footer value.

Inside a field of width w, a value whose character length is n keeps one immediate space before it and one after it. The w - n - 2 surplus spaces that remain are placed as follows:

  • Alignment.LEFT: every surplus space is placed after the value and its required trailing space.
  • Alignment.RIGHT: every surplus space is placed before the value and its required leading space.

Specification of the Task

Summary

This task changes the way the "simple" table style renders: the vertical separator between the first (index/label) column and the remaining columns switches from a single-line character to a double-line character.

Required Change in Behavior

When a table in the "simple" theme/style gets rendered as text, drawing the vertical divider that sits between the first column and the rest of the columns must be done with the double vertical bar character ║ (U+2551, "BOX DRAWINGS DOUBLE VERTICAL").

This divider used to be rendered with the single vertical bar character │ (U+2502, "BOX DRAWINGS LIGHT VERTICAL"). In every occurrence of this first-column divider — in the header row, in each data row, and in any summary/footer row — the character must now be ║ in place of │.

Specific Rendered Output

When a simple-style table having a first column and four data columns is rendered, its text output must match exactly the layout that follows (note that on every content row the ║ separator appears immediately after the first column):

 ═════ ═════ ═════ ═════ ═════ 
   #  ║  G     H     R     S   
 ═════ ═════ ═════ ═════ ═════ 
   1  ║ 30    40    35    30   
   2  ║ 30    40    35    30   
 ═════ ═════ ═════ ═════ ═════ 
  SUM ║ 130   140   135   130  
 ═════ ═════ ═════ ═════ ═════

Points to note:

  • The horizontal separator rows (the ═════ lines) are left untouched.
  • Across the header row, each data row, and the summary row, the only modification concerns the character sitting between the first column and the subsequent columns: it is ║ rather than │.
  • All of the spacing, the column widths, the alignment, and all other characters stay exactly as they were.

Scope of the Change

  • Only the "simple" style is touched by this change; do not modify the behavior of the other styles.
  • Change nothing beyond the first-column vertical separator character for the simple style.

Nothing in the public API for constructing and rendering tables changes; what is affected is only the character emitted for the simple style's first-column vertical separator.

Sections, dimensions, and the produced output

Order and presence of sections

Each of header, body, and footer is optional in its own right, and rendering happens in that order.

  • A header that is present is immediately followed by the heading-row separator of the selected style.
  • A footer that is present is immediately preceded by a heading-row separator of that same kind.
  • As a consequence, two adjacent separator lines are produced when a header and a footer have no body between them.
  • Even a footer on its own still has its separator before the footer row.
  • A section list that is empty is treated as absent; in particular, header=[] adds neither a header nor a separator, and body=[] adds no body rows.

The number of columns must be the same for all present rows — the header, the footer, and every body row included. Any mismatch raises ValueError.

General rules for rendering
  • The separator between output lines is "\n".
  • No trailing newline is present in the returned string.
  • Leading and trailing spaces supplied by a style are kept when they are significant; the omission applies only to structural lines that are made entirely of spaces.
  • For a given column, header, body, and footer values all use the same width and alignment.
  • Neighboring non-heading columns are separated by nothing but their cell padding unless the style supplies an ordinary column divider.

Automatic width calculation

When column_widths is None, sizing happens independently for each column. Its rendered field width is:

max(length of every displayed string in that column across header, body, and footer) + 2

Those two additional positions supply one space of normal cell padding on each side of the longest value. Sections that are absent take no part in this calculation.

Explicitly supplied widths

  1. There must be exactly one width per table column in it; otherwise raise ValueError.
  2. Each width must be an integer of at least 2; a width that is negative, zero, or one character long raises ValueError.

In every section, that column is aligned consistently. Take the available padding to be the field width minus the string length of the value. Whenever at least two padding positions are available, one normal margin space is kept on each side, and any spaces that remain are allocated as follows:

  • LEFT: the additional spaces are placed after the value.
  • RIGHT: the additional spaces are placed before the value.
  • CENTER: the additional spaces are split around the value; when that split is odd, the extra space goes after the value.

When fewer than two padding positions are available, no field expansion happens: with left alignment the available space goes after the value, with right alignment it goes before the value, and center alignment applies the same split rule. Therefore, with an odd total padding amount, centered content always gets the smaller half before the value and the larger half after it.

  • With first_col_heading=True, the heading-column divider of the selected style is used immediately after the first column.

  • One may enable either flag, both flags, or neither flag, including for body-only tables.

Denote each column's rendered field width by W1 through Wn. Validation of the alignments option

When alignments is passed in, the list must carry exactly one entry per column, and each of those entries must be a valid Alignment member. A list of the wrong length, or an entry that is not valid, raises ValueError.

Validation of explicit column widths

When column_widths is passed in:

  1. The list must carry exactly one width per column.
  2. A width denotes the exact size of that column's rendered content field; the mandatory padding around cell text counts toward it, while border and separator characters stay outside it.
  3. Every width must be at least the display width of that column's longest individual rendered sub-line plus two characters — those two characters buy one space of padding on each side.

A ValueError is raised when the list has the wrong length, when a width is negative or otherwise undersized, or when any width is too small for its column. Widths given explicitly are not expanded silently.

Handling of Multiline Cells

Breaking a cell into sub-lines

Whenever a string cell holds one or more \n characters, the cell is broken apart at every \n. The pieces then appear, in their original order, on consecutive physical lines. Because of this, a newline at the start, at the end, or in a run of several produces empty sub-lines — and even these empty sub-lines count toward row height. A string that has no \n, as well as any non-string cell value, takes up one sub-line. The feature brings in no automatic wrapping and no truncation.

Height of a logical row and vertical placement

To work out the physical height of a logical row, take the largest sub-line count that any cell in that row has. Inside the logical row, top alignment holds for all cells:

  • Sub-line one of a cell lands on the first physical line, sub-line two on the second, and so on.
  • When a cell runs out of sub-lines before the row's height is reached, each physical line that is left holds a full-width whitespace field belonging to that cell.
  • These continuation fields do not show the original value a second time.

Take a row whose tallest cell carries three sub-lines: that logical row then yields three content lines. A neighboring cell whose content fits one line shows up only on the first of them and stays blank over the remaining two.

Widths computed automatically

Sizing that happens automatically works from individual sub-lines rather than from the unsplit string. For a given column, the widest single sub-line is located across all header, body, and footer cells of that column, after which two characters are added to cover cell padding. The newline character itself takes up no column width; likewise, summing the lengths of all lines inside a multiline cell has no bearing on the width.

So a cell holding "short\nlonger" needs enough text space for longer, not for the whole unsplit value. Whatever width comes out is applied to every physical line and every section of that column.

Applying alignment and padding

Every nonblank sub-line in a column — headers and footers included — is aligned on its own, per the alignment chosen for that column. Write W for the rendered field width and L for the display width of the sub-line. Two spaces always serve as the base padding, one before the text and one after it; the leftover W - L - 2 spaces are handed out like this:

  • Alignment.LEFT: all extra spaces are appended after the text.
  • Alignment.RIGHT: all extra spaces come ahead of the text.
  • Alignment.CENTER: the extra spaces are shared between the two sides of the text; when their number is odd, the extra one lands after the text.

If the alignments option is absent, centering applies to all sub-lines. Whenever a continuation sub-line is missing, the entire field is rendered as W spaces — the column's alignment makes no difference.

Assembling the Table and Rendering Its Structure

The one thing a multiline logical row changes is how many content lines it occupies. The logical section structure of the table stays untouched, and no horizontal separators appear between the row's sub-lines.

Assembly proceeds in the long-standing order:

  1. The top edge taken from the style.
  2. The header, when non-empty, with one heading-row separator after it.
  3. The body rows, when non-empty; the style's ordinary row separator is placed only between distinct logical body rows.
  4. The footer, when non-empty, with one heading-row separator before it.
  5. The bottom edge taken from the style.

Even with no body following, a header that is present still gets the header separator emitted after it. Even with no body or header around it, a footer that is present still gets the footer separator emitted before it. So a table with a header and a footer but an empty body keeps the two adjacent heading separators that the existing API produces. A table consisting solely of a body has no heading-row separator, unless a present header or footer requires one anyway. When a style's corresponding separator is made up only of spaces, the style omits that whitespace-only structural line.

Spreading a row across several lines never inserts separators within a header block, within a body row, or within a footer block. On every physical content line, the left/right edges and the inter-column dividers are the same ones a single-line row would use.

Task: Introduce a configurable cell_padding option in table2ascii

Summary

The table2ascii package offers a function that renders an ASCII/Unicode box-drawing table out of header, body, and footer data. A new keyword-only option, cell_padding, must be added; it controls how much horizontal padding (spaces) is added on each side of every cell's content.

Public Interface

The function must be importable in this way:

from table2ascii import table2ascii, Alignment

The table2ascii function must accept (at least) the keyword arguments below, which are the ones used here:

  • header: a list of cell values making up the top row.
  • body: a list of rows, where each row is itself a list of cell values.
  • footer: a list of cell values making up the bottom row.
  • first_col_heading (bool): when True, a heavier column separator is drawn between the first column and the remaining columns.
  • column_widths (list of int, optional): an explicit total width, in characters, for each column.
  • alignments (list of Alignment): horizontal alignment on a per-column basis. Alignment is an enum that exposes LEFT, CENTER, and RIGHT.
  • cell_padding (int): the new option, described below.

The function returns the rendered table as a single string, with rows separated by \n and with no trailing newline.

Semantics of cell_padding

cell_padding determines how many space characters are added to both the left and right sides of each cell's content within its column. The option is applied uniformly to header, body, and footer cells.

  • A value of 1 matches the default behavior (one space of padding on each side).
  • With a value of 0, no padding is added around cell content.
  • A value of N (N ≥ 0) results in N spaces being added on each side.
Interaction with automatic column sizing

When column_widths is not provided, each column's width is sized so that it fits its widest cell content plus 2 * cell_padding extra characters (padding on each side). Within the column, cell content is separated from the column borders by exactly cell_padding spaces.

Example — when cell_padding=0, single-character contents produce columns exactly one character wide:

╔═╦═══════╗
║#║G H R S║
╟─╫───────╢
║1║2 3 4 5║
╟─╫───────╢
║A║B 1 2 3║
╚═╩═══════╝

In this output, the first column (heading column) is one char wide, and the remaining four single-char columns are joined by single-space column separators with no surrounding padding.

Example — when cell_padding=2, each cell's content has two spaces added on each side:

╔═════╦═══════════════════════╗
║  #  ║  G     H     R     S  ║
╟─────╫───────────────────────╢
║  1  ║  2     3     4     5  ║
╟─────╫───────────────────────╢
║  A  ║  B     1     2     3  ║
╚═════╩═══════════════════════╝
Interaction between explicit column_widths and alignments

When column_widths is provided, each column takes up exactly the total width that was specified. Under cell_padding=0, cell content is placed within the full column width in line with the column's alignment, and no additional padding is reserved:

  • Alignment.LEFT: content is left-justified inside the column width.
  • Alignment.RIGHT: content is right-justified inside the column width.
  • Alignment.CENTER: content is centered inside the column width.

Example — for column_widths=[4, 8, 5, 4, 5], alignments [LEFT, CENTER, RIGHT, LEFT, RIGHT], first_col_heading=True, and cell_padding=0:

╔════╦═════════════════════════╗
║#   ║   G         H R        S║
╟────╫─────────────────────────╢
║1   ║   2         3 4        5║
╟────╫─────────────────────────╢
║A   ║   B         1 2        3║
╚════╩═════════════════════════╝

Validation / Error Handling

The function must raise ValueError if cell_padding is negative (less than 0).

Formatting Details (derived from the expected output)

  • The outer border and its corners use the Unicode box-drawing characters ╔ ╦ ╗ ╚ ╩ ╝ ═ ║.
  • For interior horizontal separator rows, ╟ ╫ ╢ ─ are used.
  • Vertical borders/separators use ║; the separator next to the first column (when first_col_heading=True) is the heavier ║, whereas separators between non-heading columns are a single space within each content/separator row (see examples).
  • Rows are joined using \n; no trailing newline appears in the returned string.

For the inputs shown above, the rendered output must exactly match the example strings.

Task Specification: Custom Exception Classes and Support for Numeric Alignments

Overview

table2ascii turns tabular Python data into ASCII/Unicode tables. Enhance its input-validation API by supplying dedicated exception types for the validation failures that already exist, and allow column alignments to be given as the integers 0, 1, and 2. Apart from these changes, valid table rendering and the existing public API must remain compatible.

Compatibility of the Existing Public API

The main callable and the alignment enum must remain available as follows:

from table2ascii import Alignment, table2ascii
from table2ascii import table2ascii as t2a

The top-level exports TableStyle and PresetStyle must also remain available. The existing table2ascii call interface must not be removed or changed incompatibly; its parameters are:

table2ascii(
    header=None,
    body=None,
    footer=None,
    *,
    first_col_heading=False,
    last_col_heading=False,
    column_widths=None,
    alignments=None,
    cell_padding=1,
    style=PresetStyle.double_thin_compact,
)

What this task changes are the validation exception types and the accepted alignment values, not the generated output for calls that are already valid.

New Public Exceptions Module

A public module named table2ascii.exceptions must be provided. Every one of the classes below must be directly importable from that module:

from table2ascii.exceptions import (
    AlignmentCountMismatchError,
    InvalidAlignmentError,
    InvalidCellPaddingError,
    ColumnWidthsCountMismatchError,
    ColumnWidthTooSmallError,
    BodyColumnCountMismatchError,
    FooterColumnCountMismatchError,
)

Each listed exception must inherit from Python's built-in ValueError, either directly or through another exception class. As a result, existing callers that catch ValueError must continue to catch all of these failures. No particular wording for the new exception messages is required; the specific exception class is the required public distinction.

Requirements for Validation

table2ascii must apply the following exception classifications.

Alignments
  • AlignmentCountMismatchError must be raised when an alignments sequence is supplied but its number of entries does not equal the table's number of columns.
  • InvalidAlignmentError must be raised when any supplied alignment entry is not one of the supported named or numeric alignment values. Integers other than 0, 1, and 2, negative integers included, are invalid.
Cell Padding
  • cell_padding=0 stays valid, as do positive padding values.
  • InvalidCellPaddingError must be raised when cell_padding is negative.
Column Widths
  • column_widths=None still requests automatic sizing. Likewise, an individual None entry in a supplied width sequence continues to request automatic sizing for that column.
  • ColumnWidthsCountMismatchError must be raised when a supplied column_widths sequence does not contain exactly one entry for each table column.
  • ColumnWidthTooSmallError must be raised when a supplied numeric column width is negative or falls below the minimum width needed for that column's rendered content. The minimum must continue to account for the longest line of string-converted content in the column as well as the configured cell padding on both sides.
Body and Footer Column Counts
  • BodyColumnCountMismatchError must be raised when body rows do not have the required common column count. This includes a body row whose length differs from a present header, and body rows whose lengths differ from one another when no header establishes the column count.
  • FooterColumnCountMismatchError must be raised when a footer has a column count that differs from the rest of the established table, subject to the body/footer-only classification rule below. Specifically, a header/footer disagreement when no body is present is a footer mismatch.
  • Body/footer-only classification: when no header is present, all body rows have one common column count, and the footer has a different column count, BodyColumnCountMismatchError must be raised, not FooterColumnCountMismatchError. For this rule, an empty header is treated as absent.

Header and body sections that are empty must retain their existing behavior and must not on their own be treated as malformed rows.

Support for Numeric Alignment

The three named alignment members remain:

  • Alignment.LEFT
  • Alignment.CENTER
  • Alignment.RIGHT

Entries in the alignments argument may be either these members or the corresponding plain integer values:

Integer Equivalent named alignment
0 Alignment.LEFT
1 Alignment.CENTER
2 Alignment.RIGHT

As an example, alignments=[0, 1, 2] must format its columns exactly the way alignments=[Alignment.LEFT, Alignment.CENTER, Alignment.RIGHT] does. The equivalence holds for all rendered content, including every line of multiline cells. Integer values other than these are not alignments and must result in InvalidAlignmentError when supplied to table2ascii.

Compatibility and Non-Goals

  • Output must be preserved for valid existing inputs, including automatic widths, explicit widths, zero or positive cell padding, named alignments, multiline cells, string-convertible values, heading-column options, preset styles, and custom styles.
  • The default behavior of center-aligning all columns must be preserved for the cases where alignments is omitted or None.
  • The new exceptions are a refinement of the generic ValueError validation failures; successful rendering behavior must not be altered by them.
  • The table2ascii function signature and unrelated style behavior require no change.
