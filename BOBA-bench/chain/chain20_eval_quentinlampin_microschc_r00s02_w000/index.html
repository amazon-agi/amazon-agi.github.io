Task: Implementing an SCTP Header Parser

Overview

The goal is to implement a parser for the SCTP (Stream Control Transmission Protocol) header that takes a raw byte buffer and breaks it down into a structured list of field descriptors. The parser must handle the SCTP common header, a chunk common header, and a DATA chunk (payload and trailing padding included).

Module and Public API

Create the module microschc/protocol/sctp.py and expose the following public names from it:

SCTPFields

A holder of string constants that serve as field identifiers. It must define the attributes listed below (at minimum), each of which has a descriptive string identifier as its value:

  • SOURCE_PORT
  • DESTINATION_PORT
  • VERIFICATION_TAG
  • CHECKSUM
  • CHUNK_TYPE
  • CHUNK_FLAGS
  • CHUNK_LENGTH
  • CHUNK_DATA_TSN
  • CHUNK_DATA_STREAM_IDENTIFIER
  • CHUNK_DATA_STREAM_SEQUENCE_NUMBER
  • CHUNK_DATA_PAYLOAD_PROTOCOL_IDENTIFIER
  • CHUNK_DATA_PAYLOAD
  • CHUNK_PADDING

Apart from having to be distinct identifiers per field, no constraint is placed on the concrete string values; their only use is as the id of the produced field descriptors.

SCTPParser

A class supporting instantiation with no arguments: SCTPParser().

It must provide the following method:

def parse(self, buffer: Buffer) -> HeaderDescriptor

where Buffer stands for microschc.binary.buffer.Buffer and HeaderDescriptor for microschc.parser.parser.HeaderDescriptor.

Supporting Types (already present in the codebase)

  • microschc.binary.buffer.Buffer — instantiated as Buffer(content=<bytes>, length=<bit_length>). Equality between two Buffer instances holds when their content and bit-length are equal.
  • microschc.parser.parser.HeaderDescriptor — has a fields attribute that is a list of FieldDescriptor objects.
  • microschc.rfc8724.FieldDescriptor — each one has at least the attributes id, position, and value. The value attribute is a Buffer.

Required Parsing Behavior

When parse is given a Buffer whose content is an SCTP packet, it returns a HeaderDescriptor whose fields is an ordered list of FieldDescriptor objects. Each FieldDescriptor must have position equal to 0, with id set to the corresponding SCTPFields constant and value set to a Buffer that contains exactly the bits of that field.

In order, the layout of the packet to parse is as follows:

SCTP common header (12 bytes):

  1. Source Port Number — 16 bits, id SCTPFields.SOURCE_PORT
  2. Destination Port Number — 16 bits, id SCTPFields.DESTINATION_PORT
  3. Verification Tag — 32 bits, id SCTPFields.VERIFICATION_TAG
  4. Checksum — 32 bits, id SCTPFields.CHECKSUM

Chunk common header: 5. Chunk Type — 8 bits, id SCTPFields.CHUNK_TYPE 6. Chunk Flags — 8 bits, id SCTPFields.CHUNK_FLAGS 7. Chunk Length — 16 bits, id SCTPFields.CHUNK_LENGTH

The 16-bit Chunk Length value states the number of bytes in the chunk, counted from the start of the chunk common header (i.e. from the Chunk Type field) up to and including the chunk's data/value, but excluding any trailing padding needed to align the chunk to a 4-byte boundary.

DATA chunk body (this chunk's Chunk Type is 0, i.e. a DATA chunk): 8. TSN — 32 bits, id SCTPFields.CHUNK_DATA_TSN 9. Stream Identifier — 16 bits, id SCTPFields.CHUNK_DATA_STREAM_IDENTIFIER 10. Stream Sequence Number — 16 bits, id SCTPFields.CHUNK_DATA_STREAM_SEQUENCE_NUMBER 11. Payload Protocol Identifier — 32 bits, id SCTPFields.CHUNK_DATA_PAYLOAD_PROTOCOL_IDENTIFIER 12. Payload — id SCTPFields.CHUNK_DATA_PAYLOAD. The Chunk Length determines its length in bits: the payload takes up the bytes remaining in the chunk after the chunk common header (4 bytes) and the DATA chunk fixed fields (TSN 4 bytes, Stream Identifier 2 bytes, Stream Sequence Number 2 bytes, Payload Protocol Identifier 4 bytes = 12 bytes). So payload byte length = Chunk Length - 4 - 12.

Chunk padding: 13. Padding — id SCTPFields.CHUNK_PADDING. There may be padding bytes after the chunk so that the total chunk length (chunk common header + chunk body + padding) is a multiple of 4 bytes. The value of the padding field must contain exactly those padding bytes. When the chunk is already 4-byte aligned, no padding field is produced.

Concrete Example

Consider an input packet in which:

  • Source Port = 0x250f
  • Destination Port = 0x960c
  • Verification Tag = 0xc9596db9
  • Checksum = 0x00000000
  • Chunk Type = 0x00, Chunk Flags = 0x03, Chunk Length = 0x0049 (73 bytes)
  • TSN = 0xbc5bc068
  • Stream Identifier = 0x0000
  • Stream Sequence Number = 0x0000
  • Payload Protocol Identifier = 0x0000003c
  • Payload = 57 bytes (73 − 4 − 12 = 57 bytes → 456 bits)
  • Padding = 3 bytes (73 rounded up to 76 → 3 padding bytes → 24 bits)

The returned HeaderDescriptor.fields is a list of 13 FieldDescriptor objects following exactly the order listed above, each with position == 0 and the described id and value.

Notes

  • The order of the fields in the returned list is significant and must match the order given above.
  • Every field value is a Buffer object whose bit length matches the field's bit width as described.
  • For the described behavior, only DATA chunks (Chunk Type 0) with a single chunk followed by optional padding need to be handled.

Task Specification: Support for Parsing SCTP INIT Chunks

Overview

The existing SCTP protocol parser is to be extended so that it can parse SCTP packets containing a chunk of type INIT (Chunk Type = 1), covering both the chunk's fixed fields and its optional parameters. The parser must continue to parse DATA chunks correctly, just as it already does.

Public API

Everything listed below must be importable and usable exactly as described.

Parser
  • SCTPParser — a class that can be instantiated without any arguments.
  • SCTPParser.parse(self, buffer: Buffer) -> HeaderDescriptor — reads an SCTP header (the common header plus a single chunk) out of the supplied buffer and returns a HeaderDescriptor.
Supporting types (already present in the codebase; used as-is)
  • Buffer(content: bytes, length: int) — length here is the size in bits. Two Buffer instances compare as equal when their content and bit-length both match.
  • HeaderDescriptor — has a fields attribute, which is an ordered list of FieldDescriptor objects.
  • FieldDescriptor — has the attributes id, position (int), and value (Buffer).
Field identifiers

In addition to any constants already used for the common header and the DATA chunk, SCTPFields must expose the following identifier constants:

  • SCTPFields.SOURCE_PORT
  • SCTPFields.DESTINATION_PORT
  • SCTPFields.VERIFICATION_TAG
  • SCTPFields.CHECKSUM
  • SCTPFields.CHUNK_TYPE
  • SCTPFields.CHUNK_FLAGS
  • SCTPFields.CHUNK_LENGTH
  • SCTPFields.CHUNK_INIT_INITIATE_TAG
  • SCTPFields.CHUNK_INIT_ADVERTISED_RECEIVER_WINDOW_CREDIT
  • SCTPFields.CHUNK_INIT_NUMBER_OF_OUTBOUND_STREAMS
  • SCTPFields.CHUNK_INIT_NUMBER_OF_INBOUND_STREAMS
  • SCTPFields.CHUNK_INIT_INITIAL_TSN
  • SCTPFields.PARAMETER_TYPE
  • SCTPFields.PARAMETER_LENGTH
  • SCTPFields.PARAMETER_VALUE
  • SCTPFields.PARAMETER_PADDING

(DATA-chunk parsing as it exists today, together with its associated field identifiers — SCTPFields.CHUNK_PADDING included — must stay functional and unchanged.)

Required Behavior

SCTPParser.parse is handed a Buffer that wraps the complete SCTP header bytes, and it returns a HeaderDescriptor whose fields list holds one FieldDescriptor for each parsed field, in order. For every FieldDescriptor:

  • the position is 0;
  • the value is a Buffer whose content holds the field's raw bytes and whose length is that field's length in bits.
Common SCTP header (always parsed first, in order)
Order id Length in bits
Source Port Number SOURCE_PORT 16
Destination Port Number DESTINATION_PORT 16
Verification Tag VERIFICATION_TAG 32
Checksum CHECKSUM 32
Chunk common header (parsed next, in order)
Order id Length in bits
Chunk Type CHUNK_TYPE 8
Chunk Flags CHUNK_FLAGS 8
Chunk Length CHUNK_LENGTH 16
INIT chunk body (when Chunk Type = 1)

If the chunk type byte is equal to 0x01, the fixed fields listed below are parsed after the chunk common header, in order:

Order id Length in bits
Initiate Tag CHUNK_INIT_INITIATE_TAG 32
Advertised Receiver Window Credit CHUNK_INIT_ADVERTISED_RECEIVER_WINDOW_CREDIT 32
Number of Outbound Streams CHUNK_INIT_NUMBER_OF_OUTBOUND_STREAMS 16
Number of Inbound Streams CHUNK_INIT_NUMBER_OF_INBOUND_STREAMS 16
Initial TSN CHUNK_INIT_INITIAL_TSN 32
INIT chunk parameters (following the fixed INIT fields)

After the fixed INIT fields, the rest of the chunk is made up of zero or more parameters. Every parameter uses a Type-Length-Value encoding and is parsed into FieldDescriptors in order:

  • Parameter Type — PARAMETER_TYPE, 16 bits.
  • Parameter Length — PARAMETER_LENGTH, 16 bits. This value states the parameter's total length in bytes, covering the 2-byte type field, the 2-byte length field, and the value bytes, but not any trailing padding.
  • Parameter Value — PARAMETER_VALUE, which is present only when the parameter length signals that value bytes exist (that is, length > 4). Its bit length is (parameter_length - 4) * 8.
  • Parameter Padding — PARAMETER_PADDING, which is present only when the parameter's value length is not a multiple of 4 bytes. The padding raises the parameter's total occupied length to the next multiple of 4 bytes; its bit length is the number of padding bytes × 8.

Parameter parsing proceeds sequentially until the input has been consumed. A parameter whose length is exactly 4 (type + length only, no value) yields only the PARAMETER_TYPE and PARAMETER_LENGTH descriptors — no value descriptor and no padding descriptor.

Worked example of how parameters are handled

Take an INIT chunk with these trailing bytes:

\xc0\x00 \x00\x04            (parameter 1: type=0xc000, length=4, no value, no padding)
\x00\x0c \x00\x06 \x00\x05 \x00\x00   (parameter 2: type=0x000c, length=6, value=2 bytes, padding=2 bytes)

the parameter field descriptors that get produced are, in order:

  • PARAMETER_TYPE = \xc0\x00 (16 bits)
  • PARAMETER_LENGTH = \x00\x04 (16 bits)
  • PARAMETER_TYPE = \x00\x0c (16 bits)
  • PARAMETER_LENGTH = \x00\x06 (16 bits)
  • PARAMETER_VALUE = \x00\x05 (16 bits)
  • PARAMETER_PADDING = \x00\x00 (16 bits)

Concrete end-to-end expectation

For the following 44-byte input:

00 07 00 07 00 00 00 00 37 61 a7 46 01 00 00 20
43 23 25 44 00 00 ff ff 00 11 00 11 5c fe 37 9f
c0 00 00 04 00 0c 00 06 00 05 00 00

calling parse returns a HeaderDescriptor containing exactly 18 FieldDescriptors, in this order:

  1. SOURCE_PORT = \x00\x07 (16)
  2. DESTINATION_PORT = \x00\x07 (16)
  3. VERIFICATION_TAG = \x00\x00\x00\x00 (32)
  4. CHECKSUM = \x37\x61\xa7\x46 (32)
  5. CHUNK_TYPE = \x01 (8)
  6. CHUNK_FLAGS = \x00 (8)
  7. CHUNK_LENGTH = \x00\x20 (16)
  8. CHUNK_INIT_INITIATE_TAG = \x43\x23\x25\x44 (32)
  9. CHUNK_INIT_ADVERTISED_RECEIVER_WINDOW_CREDIT = \x00\x00\xff\xff (32)
  10. CHUNK_INIT_NUMBER_OF_OUTBOUND_STREAMS = \x00\x11 (16)
  11. CHUNK_INIT_NUMBER_OF_INBOUND_STREAMS = \x00\x11 (16)
  12. CHUNK_INIT_INITIAL_TSN = \x5c\xfe\x37\x9f (32)
  13. PARAMETER_TYPE = \xc0\x00 (16)
  14. PARAMETER_LENGTH = \x00\x04 (16)
  15. PARAMETER_TYPE = \x00\x0c (16)
  16. PARAMETER_LENGTH = \x00\x06 (16)
  17. PARAMETER_VALUE = \x00\x05 (16)
  18. PARAMETER_PADDING = \x00\x00 (16)

Every position value is 0.

Constraints

  • DATA-chunk parsing behavior, as it exists, must be preserved unchanged.
  • Do not introduce fields, identifiers, or behaviors beyond the ones specified above.

Task Specification: Parsing the SCTP INIT_ACK Chunk

Goal

The existing SCTP header parser is to be extended so that it can parse SCTP packets whose payload starts with an INIT_ACK chunk (chunk type 0x02), breaking the packet down into a flat list of field descriptors.

Public API Surface

The parser must be importable and usable by way of the following surface (a surface already provided by the existing DATA and INIT chunk support; INIT_ACK must integrate consistently):

  • SCTPParser — a class whose constructor takes no arguments.
    • Method: parse(self, buffer: Buffer) -> HeaderDescriptor
  • SCTPFields — an enumeration/namespace holding field identifier constants (see the required members below).
  • HeaderDescriptor — an object carrying a .fields attribute (a list of FieldDescriptor).
  • FieldDescriptor — an object providing the attributes .id, .position (int), and .value (a Buffer).
  • Buffer — a container of byte content, constructed as Buffer(content: bytes, length: int), with length expressed in bits. Two Buffer instances count as equal when their content and bit-length match.

These types reside in the same modules that the existing SCTP parser tests already use; their locations must not be changed.

SCTPFields members that are required

The following identifier constants are required to exist and to be used by the parser:

  • SCTPFields.SOURCE_PORT
  • SCTPFields.DESTINATION_PORT
  • SCTPFields.VERIFICATION_TAG
  • SCTPFields.CHECKSUM
  • SCTPFields.CHUNK_TYPE
  • SCTPFields.CHUNK_FLAGS
  • SCTPFields.CHUNK_LENGTH
  • SCTPFields.CHUNK_INIT_ACK_INITIATE_TAG
  • SCTPFields.CHUNK_INIT_ACK_ADVERTISED_RECEIVER_WINDOW_CREDIT
  • SCTPFields.CHUNK_INIT_ACK_NUMBER_OF_OUTBOUND_STREAMS
  • SCTPFields.CHUNK_INIT_ACK_NUMBER_OF_INBOUND_STREAMS
  • SCTPFields.CHUNK_INIT_ACK_INITIAL_TSN
  • SCTPFields.PARAMETER_TYPE
  • SCTPFields.PARAMETER_LENGTH
  • SCTPFields.PARAMETER_VALUE

(The pre-existing DATA/INIT field members must remain functional; add only the ones that are missing.)

Parser Input

parse takes a single Buffer; its content is the raw SCTP packet bytes and its length equals len(content) * 8.

Behavior when parsing an INIT_ACK chunk

When the chunk type byte is 0x02, the packet layout to parse is the following:

The common SCTP header (12 bytes)

Emit the following field descriptors in this order:

  1. SOURCE_PORT — 16 bits, spanning bytes 0–1.
  2. DESTINATION_PORT — 16 bits, spanning bytes 2–3.
  3. VERIFICATION_TAG — 32 bits, spanning bytes 4–7.
  4. CHECKSUM — 32 bits, spanning bytes 8–11.
The common header of the INIT_ACK chunk
  1. CHUNK_TYPE — 8 bits (its value is 0x02 for INIT_ACK).
  2. CHUNK_FLAGS — 8 bits.
  3. CHUNK_LENGTH — 16 bits. It carries the chunk's total length in bytes (chunk type + flags + length + fixed fields + all parameters, before final chunk padding).
The fixed INIT_ACK fields
  1. CHUNK_INIT_ACK_INITIATE_TAG — 32 bits.
  2. CHUNK_INIT_ACK_ADVERTISED_RECEIVER_WINDOW_CREDIT — 32 bits.
  3. CHUNK_INIT_ACK_NUMBER_OF_OUTBOUND_STREAMS — 16 bits.
  4. CHUNK_INIT_ACK_NUMBER_OF_INBOUND_STREAMS — 16 bits.
  5. CHUNK_INIT_ACK_INITIAL_TSN — 32 bits.
Parameters of variable length (Type-Length-Value)

After the fixed fields, the rest of the chunk is made up of zero or more parameters. Each parameter starts with:

  • PARAMETER_TYPE — 16 bits.
  • PARAMETER_LENGTH — 16 bits. Its value is the number of bytes covering the type, length, and value fields together (i.e. 4 + value_byte_length).

After that, only when the parameter carries a value (i.e. PARAMETER_LENGTH > 4):

  • PARAMETER_VALUE — (PARAMETER_LENGTH - 4) * 8 bits, holding exactly the parameter's value bytes (padding is not included).

When PARAMETER_LENGTH == 4 the parameter has no value, so no PARAMETER_VALUE descriptor is emitted for it — only its PARAMETER_TYPE and PARAMETER_LENGTH.

Parameters must be consumed in sequence until the chunk's declared length (CHUNK_LENGTH) is exhausted. The chunk length must drive parameter parsing, and internal padding must be taken into account so that consecutive parameters are located at the correct offsets. In this scenario, no field descriptor for parameter padding is emitted.

Ordering and count of the output

HeaderDescriptor.fields must be a list of FieldDescriptor objects following the exact order in which the fields appear in the packet. The position of every field descriptor is 0. Each descriptor's value is a Buffer whose content holds the raw bytes of that field and whose bit-length equals the field's bit width as specified above.

Worked example

Take an INIT_ACK packet made up of the common header, the INIT_ACK fixed fields, one parameter of type 0x0007 with an 800-bit (100-byte) value, and one parameter of type 0xc000 with declared length 0x0004 (no value); the resulting fields list contains exactly 17 descriptors, in this order:

  1. SOURCE_PORT = b'\x00\x07' (16)
  2. DESTINATION_PORT = b'\x00\x07' (16)
  3. VERIFICATION_TAG = b'\x43\x23\x25\x44' (32)
  4. CHECKSUM = b'\xc9\x01\x85\x24' (32)
  5. CHUNK_TYPE = b'\x02' (8)
  6. CHUNK_FLAGS = b'\x00' (8)
  7. CHUNK_LENGTH = b'\x00\x80' (16)
  8. CHUNK_INIT_ACK_INITIATE_TAG = b'\x00\x00\x0e\xb0' (32)
  9. CHUNK_INIT_ACK_ADVERTISED_RECEIVER_WINDOW_CREDIT = b'\x00\x00\x10\x00' (32)
  10. CHUNK_INIT_ACK_NUMBER_OF_OUTBOUND_STREAMS = b'\x00\x11' (16)
  11. CHUNK_INIT_ACK_NUMBER_OF_INBOUND_STREAMS = b'\x00\x11' (16)
  12. CHUNK_INIT_ACK_INITIAL_TSN = b'\x00\x00\x36\x14' (32)
  13. PARAMETER_TYPE = b'\x00\x07' (16)
  14. PARAMETER_LENGTH = b'\x00\x68' (16)
  15. PARAMETER_VALUE = the 100 value bytes (800 bits)
  16. PARAMETER_TYPE = b'\xc0\x00' (16)
  17. PARAMETER_LENGTH = b'\x00\x04' (16)

Note that in this example the first parameter's declared length (0x68 = 104) covers 4 header bytes plus 100 value bytes; the second parameter's declared length is 4, so it emits no value descriptor.

Constraints

  • The behavior of the existing SCTP parsing for DATA and INIT chunks must remain intact and unchanged.
  • The value returned is always a HeaderDescriptor instance.

Task: Add Support for HEARTBEAT Chunks to the SCTP Parser

Background

The codebase already contains a header parser for SCTP (Stream Control Transmission Protocol). This parser currently handles an SCTP common header followed by a chunk. The task is to extend it so that packets whose chunk is a HEARTBEAT chunk get parsed correctly.

The relevant public API (already present, to be extended) consists of:

  • SCTPParser — the parser class; it takes no arguments when instantiated: SCTPParser().
    • Method: parse(self, buffer: Buffer) -> HeaderDescriptor
  • SCTPFields — a container of string/identifier constants that serve as field ids.
  • HeaderDescriptor — has an attribute fields, which is a list of FieldDescriptor.
  • FieldDescriptor — has the attributes id, position (int), and value (a Buffer).
  • Buffer — a container of byte content, built as Buffer(content=<bytes>, length=<bit_length>) and comparable via ==.

These can be imported from the same modules that the existing SCTP parser tests use.

Behavior That Is Required

SCTPParser().parse(buffer=...) is passed a Buffer wrapping the raw bytes of an SCTP packet (a common header followed by a single chunk). It must return a HeaderDescriptor whose fields list holds one FieldDescriptor for each parsed field, in the byte order of the packet.

Field identifiers (on SCTPFields)

The identifier constants listed below must exist and be used as the id of the corresponding FieldDescriptor:

  • SCTPFields.SOURCE_PORT

A Buffer class already exists; it is used to represent sequences of bits stored inside byte buffers. The public API that is relevant here includes:

  • A Buffer class (importable from the module the rest of the binary buffer code uses, e.g. Buffer).
  • A constructor that accepts keyword arguments:
    • content: a bytes object that holds the raw bytes.
    • length: an int that gives the number of meaningful bits in the buffer.
    • padding: an optional value taken from a Padding enum, with Padding.LEFT as the default. The enum exposes Padding.LEFT and Padding.RIGHT.
  • Equality comparison (==) of two Buffer instances.

Since length may be smaller than 8 * len(content), some bits in content are padding bits that are not meaningful. The padding value indicates where those padding bits are located:

  • Padding.LEFT: the meaningful bits are right-aligned, with the padding bits occupying the high-order (leftmost) positions of the byte sequence.
  • Padding.RIGHT: the meaningful bits are left-aligned, with the padding bits occupying the low-order (rightmost) positions of the byte sequence.

Change to Implement

Add the unary bitwise NOT operator (~) to Buffer; that is, implement an __invert__ method that returns a new Buffer.

Behavior

Applying ~ to a Buffer results in a new Buffer in which every meaningful bit is flipped (0 ↔ 1). The result must have:

  • the same length as the input,
  • the same padding as the input,
  • a content where only the meaningful bit positions have been inverted; the padding bit positions must remain 0.

Put another way, the only bits inverted are those that fall within the length meaningful bits (positioned according to padding), and all padding bit positions are cleared to 0.

Examples

  1. Buffer using the full width (no padding):

    • Input: content=b'\x01\xff\xf0', length=24 (default Padding.LEFT).
    • Result: content=b'\xfe\x00\x0f', length=24, Padding.LEFT.

  2. Padding on the left (meaningful bits right-aligned):

    • Input: content=b'\x0f\xff\xf0', length=20, Padding.LEFT.
    • The 4 bits at the top are padding. Only the low 20 bits are inverted; the padding bits stay 0.
    • Result: content=b'\x00\x00\x0f', length=20, Padding.LEFT.

  3. Padding on the right (meaningful bits left-aligned):

    • Input: content=b'\x0f\xff\x80', length=20, Padding.RIGHT.
    • The 4 bits at the bottom are padding. Only the high 20 bits are inverted; the padding bits stay 0.
    • Result: content=b'\xf0\x00\x70', length=20, Padding.RIGHT.

The operation does not mutate the original buffer; a new Buffer is returned.

Task Specification: Adding Checksum Computation to SCTP

Aim

Extend the SCTP protocol module that resides at microschc/protocol/sctp.py with a checksum computation capability.

Public API That Must Be Provided

Besides the already existing symbols SCTPParser and SCTPFields, the module microschc.protocol.sctp must also export a new symbol named SCTPComputeFunctions.

SCTPComputeFunctions

The keys of SCTPComputeFunctions are SCTP field identifiers; put differently, it is a dictionary (mapping). Under the key SCTPFields.CHECKSUM, the value associated with it must be a container that supports indexing (e.g. a tuple), and the first element of that container (index 0) is a callable that carries out the checksum computation described below.

To put it another way, the access pattern that follows must be valid:

compute_fn = SCTPComputeFunctions[SCTPFields.CHECKSUM][0]

Function That Computes the Checksum

Function Signature

Accessing SCTPComputeFunctions[SCTPFields.CHECKSUM][0] returns a callable; that callable must accept two positional arguments:

compute_fn(decompressed_fields: List[Tuple[str, Buffer]], field_position: int) -> Buffer
  • decompressed_fields: an ordered list made up of (field_id, value) pairs; each field_id is a string identifying an SCTP field, and each value is a microschc.binary.buffer.Buffer. What the list holds is the field sequence of an SCTP packet that has been fully parsed, in header/packet order — the outcome of parsing a complete SCTP packet.
  • field_position: an integer index. It says which occurrence/position in the field sequence matches the checksum field being computed (that is, the position of the checksum field in the packet layout).
What the Function Does

What must be computed by the function is the SCTP CRC-32c checksum of the entire SCTP packet as rebuilt from the decompressed_fields supplied to it, while the checksum field itself is treated as zero (that is, the four checksum bytes take the value 0x00000000 before the CRC is computed).

Reconstructing the packet amounts to concatenating all the field values, in the order that decompressed_fields gives, and the result of that concatenation is the byte sequence of the full SCTP packet. Calculation of the checksum then happens as the SCTP standard (CRC-32c / Castagnoli) prescribes, and the resulting 32-bit checksum, in the byte order required by SCTP, is placed into the packet.

Returned Value

As its output, the function must return a microschc.binary.buffer.Buffer whose length is 32 bits and which contains the computed 4-byte checksum.

Worked-Out Example

Suppose an SCTP packet has the following full byte content:

00 07 00 07 00 00 00 00 00 00 00 00 01 00 00 20
43 23 25 44 00 00 ff ff 00 11 00 11 5c fe 37 9f
c0 00 00 04 00 0c 00 06 00 05 00 00

(the bytes at offset 8..11 make up the checksum field; in this example they are already zeroed). Parsing this packet via SCTPParser().parse(...) and then passing the field list it produces, along with field_position = 3, to the compute function must yield:

Buffer(content=b'\x37\x61\xa7\x46', length=32)

Restrictions

  • The behavior that SCTPParser and SCTPFields already have must stay unchanged; the outcome of parsing a complete SCTP packet is still a HeaderDescriptor whose fields are FieldDescriptor objects that expose .id and .value attributes.
  • No other new public behavior is required.
