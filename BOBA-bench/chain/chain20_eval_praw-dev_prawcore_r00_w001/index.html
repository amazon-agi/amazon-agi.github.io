session.request('GET', '/some/path')

Task: Handle HTTP 201 Created Responses in Session.request

Background

The codebase you are working in is prawcore, a Python library offering authenticated HTTP session handling for the Reddit API. The class of interest is prawcore.Session, which exposes a request method for making authenticated API calls.

Change Required

The Session.request method must handle HTTP responses that carry a 201 Created status code correctly, treating them as successful responses in the same manner it already treats 200 OK responses.

At present, 200 OK responses are the only ones recognized as successful, and their JSON body is parsed and returned. You must extend this behavior so that a 201 Created response is recognized as successful too: its JSON body must be parsed and returned to the caller.

Specification of Behavior

prawcore.Session.request

Signature (this already exists; its interface must not be changed):

def request(self, method, path, params=None, data=None):
  • method: the HTTP method, given as a string (e.g., 'GET', 'POST', 'PUT').
  • path: the path of the API endpoint (e.g., '/api/v1/me/friends/spez').
  • params: query parameters (optional).
  • data: the request body (optional). It may be supplied as a raw string (e.g., the string '{}').

Behavior to be implemented/verified:

  • If the server returns a response whose status code is 201 Created, the method must parse the response body as JSON and return the resulting deserialized object (e.g., a dict).
  • This handling must be identical to how a 200 OK response is handled — the caller receives the parsed JSON content of the response body.

Concrete example of the required behavior:

A PUT request to /api/v1/me/friends/spez with a body consisting of the string '{}' that yields a 201 Created response whose body is a JSON object (for example, an object that includes a name key) must return that parsed JSON object, so that the returned value contains the key name.

Constraints

  • The public signature of Session.request must not be altered.
  • Existing handling of 200 OK responses must not be removed or changed.
  • The only functional requirement is that 201 Created responses be handled as successful responses whose JSON body is parsed and returned.

Further Requirements

  • When form bodies are supplied as mappings, they must be serialized deterministically, with the fields ordered by their names in ascending lexicographic order. This applies consistently to the request paths of Session, Authenticator, Authorizer, and ScriptAuthorizer.
  • Form serialization must use the standard application/x-www-form-urlencoded encoding: spaces are turned into +, reserved characters are percent-encoded, and fields are joined with &. Canonical examples include:
    • token=dummy+token&token_type_hint=access_token
    • code=invalid+code&grant_type=authorization_code&redirect_uri=http%3A%2F%2Flocalhost%3A8080
    • grant_type=refresh_token&refresh_token=<REFRESH_TOKEN>
    • grant_type=password&password=<PASSWORD>&username=<USERNAME>
    • api_type=json&kind=self&sr=reddit_api_test&text=Test%21&title=A+Test+from+PRAWCORE.
  • When a body is already supplied as a raw string, it must be transmitted unchanged rather than form-serialized or reordered; for example, data='{}' must produce the exact request body {}.

Overview

You must make changes to the authorization classes in the prawcore package. At the top level, the package exposes Authenticator, Authorizer, and DeviceIDAuthorizer (as prawcore.Authenticator, prawcore.Authorizer, and prawcore.DeviceIDAuthorizer), together with the exception types prawcore.InvalidInvocation and prawcore.OAuthException.

The changes deal with how these two authorizer classes are constructed and validated, together with how DeviceIDAuthorizer supplies a default device ID.

Existing Context That Is Relevant

An Authenticator is built with prawcore.Authenticator(requestor, client_id) and may optionally have a client_secret attribute. In the scenarios below, the client_secret attribute of an Authenticator instance can be set directly after construction (e.g. to None or to a string), and the authorizer classes must take that current value into account.

Authorizer instances expose the following attributes/methods:

  • access_token
  • scopes
  • refresh_token
  • is_valid() — returns a boolean

Behavior That Is Required

prawcore.Authorizer

Constructor: Authorizer(authenticator, refresh_token=None)

  1. Authenticator of an invalid type. If construction is given an object that is not a valid authenticator (specifically, any object that does not supply the attributes the constructor accesses on an authenticator — e.g. None, an integer, a boolean, or a bare object() instance), construction must fail by raising AttributeError. That is to say, the constructor is expected to access authenticator attributes directly at construction time, and carrying out that access against these unsuitable values naturally raises AttributeError.

  2. Client secret is missing. If construction is given a valid authenticator whose client_secret is None, construction must raise prawcore.InvalidInvocation. Put another way, Authorizer requires the authenticator to have a (non-None) client secret.

  3. When a refresh token is supplied. Construction succeeds when the constructor is given a valid authenticator (one that has a client secret) together with a refresh token string. Immediately after construction:

    • access_token is None
    • scopes is None
    • refresh_token equals the supplied refresh token
    • is_valid() returns False
prawcore.DeviceIDAuthorizer

Constructor: DeviceIDAuthorizer(authenticator, device_id='DO_NOT_TRACK_THIS_DEVICE')

device_id is an optional parameter whose default is the string 'DO_NOT_TRACK_THIS_DEVICE'.

  1. The client secret must be absent. If construction is given an authenticator whose client_secret is set to a (non-None) value, construction must raise prawcore.InvalidInvocation. DeviceIDAuthorizer is meant for authenticators that have no client secret.

  2. Initialization that succeeds. Construction succeeds when the authenticator handed over has no client secret (i.e. it was built as prawcore.Authenticator(requestor, client_id) with no secret set). Immediately after construction:

    • access_token is None
    • scopes is None
    • refresh_token is None
    • is_valid() returns False

  3. refresh() with the default device ID. When refresh() is called on a DeviceIDAuthorizer built with the default device_id, the call must perform an OAuth "installed client" token request. The request must be an HTTP POST to https://www.reddit.com/api/v1/access_token whose form-encoded body contains:

    • grant_type = https://oauth.reddit.com/grants/installed_client
    • device_id = the value of the device ID (DO_NOT_TRACK_THIS_DEVICE for the default)

    If the response is successful, the authorizer becomes valid: after refresh(), access_token is a non-empty string, scopes is populated, and is_valid() returns True.

  4. refresh() with a device ID that is too short. If a device_id that is too short (for example a 19-character string) is used at construction, calling refresh() leads to the server rejecting the request, and refresh() must raise prawcore.OAuthException.

Distinguishing Rules, Summarized

  • Authorizer requires the authenticator to have a client secret, so constructing it without one raises InvalidInvocation; giving it an object that isn't authenticator-like raises AttributeError.
  • DeviceIDAuthorizer forbids the authenticator from having a client secret, so constructing it with one raises InvalidInvocation. Its device_id argument is optional, with 'DO_NOT_TRACK_THIS_DEVICE' as its default, and its token exchange uses the installed-client grant type.

prawcore.TrustedAuthenticator

Construction stays as:

The existing three-argument API must be kept:

Task Specification: Retrying on ChunkedEncodingError

Summary

HTTP requests are issued by the prawcore library through a Session object. If a request fails at the transport level with a requests.exceptions.ChunkedEncodingError, the request must be retried automatically. This specification spells out the retry behavior together with the exception handling contract that must be implemented.

Required Behavior

Retrying on transport-level failures

If the call that prawcore.Session.request(...) makes to perform an underlying HTTP request (via the requests library's Session.request method) raises a requests.exceptions.ChunkedEncodingError, the operation must be retried.

  • For a single call to prawcore.Session.request, the total number of times the underlying requests session's request method is invoked must be exactly 3 when every attempt raises ChunkedEncodingError. In other words: an initial attempt plus two retries.
  • After all the attempts are exhausted (all of them raising ChunkedEncodingError), a prawcore.exceptions.RequestException must be raised.

Note: Any delay/backoff between retries must be carried out via time.sleep. (Because the test environment neutralizes time.sleep, its presence must not otherwise affect the behavior or the timing correctness of the retry count.)

Contract for RequestException

The class prawcore.exceptions.RequestException must:

  • Be importable as prawcore.exceptions.RequestException.
  • Be a subclass of the library's base exception hierarchy, making it a valid exception type to raise and catch.
  • The underlying exception must be wrapped. The class must expose an attribute named original_exception that holds the exact exception instance that caused the failure (i.e., the same ChunkedEncodingError object instance that was raised by the underlying request call). When the retries are exhausted, the original_exception attribute of the raised RequestException must be the identical object (identity, not just equality) of the transport exception that triggered the failure.

Public API Surface

The items that follow must exist and be importable/callable as described:

  • prawcore.Requestor(user_agent) — builds a requestor; it is already used to configure sessions.
  • prawcore.TrustedAuthenticator(requestor, client_id, client_secret)
  • prawcore.ReadOnlyAuthorizer(authenticator) — provides a refresh() method that performs an access-token request.
  • prawcore.Session(authorizer) — provides the method request(method, path, ...) that performs the (possibly retried) HTTP request.
  • prawcore.exceptions.RequestException — with an original_exception attribute as described earlier.

Notes on scope

  • Only ChunkedEncodingError from requests.exceptions is exercised as the condition that triggers retries.
  • The successful authorization/token-refresh path (a normal HTTP 200 response that returns a JSON body containing access_token, expires_in, and scope) must continue to work normally and must not be subject to spurious retries when no transport error occurs.

Constraints

  • For the exhausted-retry scenario, the total attempt count must not be changed from 3.
  • Ensure that the wrapped original exception instance is preserved unchanged.
