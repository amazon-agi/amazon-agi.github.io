Task: Support HTTP 201 Created Responses in Session.request

Context

You are working on prawcore, a Python library that provides authenticated HTTP session handling for the Reddit API. The relevant class is prawcore.Session, which exposes a request method used to make authenticated API calls.

Required Change

The Session.request method must correctly handle HTTP responses with a 201 Created status code, treating them as successful responses in the same way it already treats 200 OK responses.

Currently, only 200 OK responses are recognized as successful and have their JSON body parsed and returned. You must extend this so that a 201 Created response is also recognized as successful: its JSON body must be parsed and returned to the caller.

Behavioral Specification

prawcore.Session.request

Signature (already exists; do not change its interface):

def request(self, method, path, params=None, data=None):
  • method: the HTTP method as a string (e.g., 'GET', 'POST', 'PUT').
  • path: the API endpoint path (e.g., '/api/v1/me/friends/spez').
  • params: optional query parameters.
  • data: optional request body. May be passed as a raw string (e.g., the string '{}').

Behavior to implement/verify:

  • When the server returns a response with status code 201 Created, the method must parse the response body as JSON and return the resulting deserialized object (e.g., a dict).
  • This must work identically to how a 200 OK response is handled — the caller receives the parsed JSON content of the response body.

Concrete example of the required behavior:

A PUT request to /api/v1/me/friends/spez with a string body of '{}' that yields a 201 Created response containing a JSON object body (for example, an object that includes a name key) must return that parsed JSON object, such that the returned value contains the key name.

Constraints

  • Do not alter the public signature of Session.request.
  • Do not remove or change existing handling of 200 OK responses.
  • The only functional requirement is that 201 Created responses are handled as successful responses whose JSON body is parsed and returned.

  • Form bodies supplied as mappings must be serialized deterministically, with fields ordered by their names in ascending lexicographic order. This applies consistently to Session, Authenticator, Authorizer, and ScriptAuthorizer request paths.
  • Form serialization must use standard application/x-www-form-urlencoded encoding: spaces become +, reserved characters are percent-encoded, and fields are joined with &. Canonical examples include:

    • code=invalid+code&grant_type=authorization_code&redirect_uri=http%3A%2F%2Flocalhost%3A8080

    • api_type=json&kind=self&sr=reddit_api_test&text=Test%21&title=A+Test+from+PRAWCORE.
  • A body already supplied as a raw string must be transmitted unchanged rather than form-serialized or reordered; for example, data='{}' must produce the exact request body {}.

Overview

You must modify the authorization classes in the prawcore package. The package exposes Authenticator, Authorizer, and DeviceIDAuthorizer at the top level (prawcore.Authenticator, prawcore.Authorizer, prawcore.DeviceIDAuthorizer), along with the exception types prawcore.InvalidInvocation and prawcore.OAuthException.

The changes concern how these two authorizer classes are constructed and validated, and how DeviceIDAuthorizer supplies a default device ID.

Relevant Existing Context

An Authenticator is constructed as prawcore.Authenticator(requestor, client_id) and may optionally carry a client_secret attribute. In the scenarios below, the client_secret attribute of an Authenticator instance can be set directly (e.g. to None or to a string) after construction, and the authorizer classes must observe that current value.

Authorizer instances expose the attributes/methods:

  • access_token
  • scopes
  • refresh_token
  • is_valid() — returns a boolean

Required Behavior

prawcore.Authorizer

Constructor: Authorizer(authenticator, refresh_token=None)

  1. Invalid authenticator type. When constructed with an object that is not a valid authenticator (specifically, any object that does not provide the attributes the constructor accesses on an authenticator — e.g. None, an integer, a boolean, or a bare object() instance), construction must fail by raising AttributeError. In other words, the constructor is expected to access authenticator attributes directly at construction time, and doing so against these unsuitable values naturally raises AttributeError.

  2. Missing client secret. When constructed with a valid authenticator whose client_secret is None, construction must raise prawcore.InvalidInvocation. That is, Authorizer requires the authenticator to have a (non-None) client secret.

  3. With a refresh token. When constructed with a valid authenticator (having a client secret) and a refresh token string, construction succeeds. Immediately after construction:

    • access_token is None
    • scopes is None
    • refresh_token equals the supplied refresh token
    • is_valid() returns False
prawcore.DeviceIDAuthorizer

Constructor: DeviceIDAuthorizer(authenticator, device_id='DO_NOT_TRACK_THIS_DEVICE')

The device_id parameter is optional and defaults to the string 'DO_NOT_TRACK_THIS_DEVICE'.

  1. Client secret must be absent. When constructed with an authenticator whose client_secret is set to a (non-None) value, construction must raise prawcore.InvalidInvocation. DeviceIDAuthorizer is intended for authenticators that have no client secret.

  2. Successful initialization. When constructed with an authenticator that has no client secret (i.e. built as prawcore.Authenticator(requestor, client_id) with no secret set), construction succeeds. Immediately after construction:

    • access_token is None
    • scopes is None
    • refresh_token is None
    • is_valid() returns False

  3. refresh() with default device ID. Calling refresh() on a DeviceIDAuthorizer built with the default device_id must perform an OAuth "installed client" token request. The request must be an HTTP POST to https://www.reddit.com/api/v1/access_token with a form-encoded body containing:

    • grant_type = https://oauth.reddit.com/grants/installed_client
    • device_id = the device ID value (DO_NOT_TRACK_THIS_DEVICE for the default)

    On a successful response, the authorizer becomes valid: after refresh(), access_token is a non-empty string, scopes is populated, and is_valid() returns True.

  4. refresh() with a short device ID. When constructed with a device_id that is too short (for example a 19-character string), calling refresh() results in the server rejecting the request, and refresh() must raise prawcore.OAuthException.

Summary of the Distinguishing Rules

  • Authorizer requires the authenticator to have a client secret; constructing it without one raises InvalidInvocation. Constructing it with an object that isn't authenticator-like raises AttributeError.
  • DeviceIDAuthorizer forbids the authenticator from having a client secret; constructing it with one raises InvalidInvocation. Its device_id argument is optional with a default of 'DO_NOT_TRACK_THIS_DEVICE', and its token exchange uses the installed-client grant type.

Task Specification: Retry on ChunkedEncodingError

Overview

The prawcore library issues HTTP requests through a Session object. When a request fails at the transport level with a requests.exceptions.ChunkedEncodingError, the request must be automatically retried. This specification defines the retry behavior and the exception handling contract that must be implemented.

Required Behavior

Retry on transport-level failures

When prawcore.Session.request(...) performs an underlying HTTP request (via the requests library's Session.request method) and that call raises a requests.exceptions.ChunkedEncodingError, the operation must be retried.

  • The total number of times the underlying requests session's request method is invoked for a single call to prawcore.Session.request must be exactly 3 when every attempt raises ChunkedEncodingError. That is: an initial attempt plus two retries.
  • After all attempts are exhausted (all raising ChunkedEncodingError), a prawcore.exceptions.RequestException must be raised.

Note: Any delay/backoff between retries must be performed via time.sleep. (The test environment neutralizes time.sleep, so its presence must not otherwise affect behavior or timing correctness of the retry count.)

RequestException contract

The prawcore.exceptions.RequestException class must:

  • Be importable as prawcore.exceptions.RequestException.
  • Be a subclass of the library's base exception hierarchy such that it is a valid exception type to raise and catch.
  • Wrap the underlying exception. It must expose an attribute named original_exception that holds the exact exception instance that caused the failure (i.e., the same ChunkedEncodingError object instance that was raised by the underlying request call). When the retries are exhausted, the original_exception attribute of the raised RequestException must be the identical object (identity, not just equality) of the transport exception that triggered the failure.

Public API Surface

The following must exist and be importable/callable as described:

  • prawcore.Requestor(user_agent) — constructs a requestor; already used to configure sessions.
  • prawcore.TrustedAuthenticator(requestor, client_id, client_secret)
  • prawcore.ReadOnlyAuthorizer(authenticator) — supports a refresh() method that performs an access-token request.
  • prawcore.Session(authorizer) — with method request(method, path, ...) that performs the (possibly retried) HTTP request.
  • prawcore.exceptions.RequestException — with an original_exception attribute as described above.

Notes on scope

  • Only ChunkedEncodingError from requests.exceptions is exercised as the retry-triggering condition.
  • The successful authorization/token-refresh path (a normal HTTP 200 response returning a JSON body with access_token, expires_in, and scope) must continue to function normally and must not be subject to spurious retries when no transport error occurs.

Constraints

  • Do not change the total attempt count from 3 for the exhausted-retry scenario.
  • Ensure the wrapped original exception instance is preserved unchanged.
