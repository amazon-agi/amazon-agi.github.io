Task Specification: Keep nc2zarr Public Behavior and Add DatasetWriter Post-Processing

Overview

This task adds optional custom post-processing to nc2zarr.writer.DatasetWriter while the existing conversion pipeline and its public extension points are preserved. A configured post-processor is handed the complete output xarray.Dataset immediately before serialization, and the dataset it returns is written.

One public resolution format is shared by the callable references used by preprocessing, processing, and post-processing. The existing behavior — configuration, input opening, preprocessing, rechunking, conversion, logging, command-line, local-storage, and object-storage — must remain compatible.

References to custom callables

nc2zarr.custom.load_custom_func
load_custom_func(func_ref: str) -> Callable

A callable reference takes the form "<module>:<attribute.path>":

  • <module> is a Python module that can be imported.
  • <attribute.path> is made up of one or more valid Python identifiers separated by dots.
  • Resolution begins at the imported module and follows every attribute in order. Both module-level callables and dotted attributes such as class methods must be supported.
  • The resolved object is returned only when it is callable.

Every failure is a ValueError with one of the following exact messages:

  • If the module or attribute part is missing, the colon is missing, or an attribute-path identifier is invalid:
    func_ref "<ref>" is invalid, format must be <module>:<function>
  • If the module cannot be imported:
    module for function "<ref>" not found
  • If an attribute is missing while the path is traversed:
    function "<ref>" not found, unknown attribute "<attribute>"
  • If a successfully resolved object is not callable:
    "<ref>" is not callable

All of the custom dataset hooks described below accept one xarray.Dataset and return the dataset that the next pipeline stage must use.

Loading configuration

nc2zarr.config.load_config
load_config(config_paths=None, return_kwargs=False, **kwargs) -> dict
  • If there are no configuration paths and no keyword values, it returns {}.
  • As config_paths, one path or a sequence of YAML paths may be supplied.
  • Keyword names that are flat and begin with input_, process_, or output_ are converted into the corresponding nested input, process, or output mapping. Names other than these, dry_run and verbosity among them, remain at the top level.
  • Explicit false values such as False and zero are retained; only keyword values that are absent or None are omitted from nested configuration construction.
  • When return_kwargs=True, the input, process, and output mappings are flattened back to input_*, process_*, and output_* names, so the result can be passed as constructor keyword arguments.
  • When multiple YAML mappings are given, they are recursively merged from left to right. A later scalar value replaces an earlier value, nested mappings are recursively combined, and list values are concatenated. Input-path lists in particular accumulate in file order.
  • Keyword configuration supplied explicitly is merged after all YAML configurations. For replaceable values it therefore has later precedence, while keyword lists append to earlier lists under the list-concatenation rule.

A path that is missing raises nc2zarr.error.ConverterError with exactly:

Configuration not found: <path>

Opening datasets
open_datasets(preprocess=None) -> Iterator[xarray.Dataset]
  • When path resolution finds no inputs, iteration raises ConverterError with exactly No inputs found.
  • In the default case, one dataset is yielded for each resolved input path.
  • With input_multi_file=True, exactly one dataset is yielded, combining the resolved files along the concatenation dimension. Inputs carrying one time slice therefore produce one time-concatenated dataset.
  • If preprocess is provided, the dataset it returns is the one used. In multi-file mode, it is applied to the individual inputs before they are combined.
  • NetCDF and local Zarr inputs remain supported; when no engine was explicitly selected, a local .zarr directory is opened with the Zarr engine.
  • With input_prefetch_chunks=True, encoded source chunk sizes are discovered and used when the data is opened. In the single-file case, the result preserves the source chunk topology. In the multi-file case, the result preserves the source spatial chunks and has one source chunk per input file along the concatenation dimension.

Preprocessing datasets

nc2zarr.preprocessor.DatasetPreProcessor
DatasetPreProcessor(
    input_variables=None,
    input_custom_preprocessor=None,
    input_concat_dim=None,
    input_datetime_format=None,
)

The preprocess_dataset(ds) method performs the following stages in order:

  1. If a non-empty input_variables list is given, retain the requested variables and coordinates and remove the unrequested ones. With input_variables=None (or an empty list), all variables are preserved.
  2. If input_custom_preprocessor is given, resolve it via load_custom_func, call it with the selected dataset, and use its return value.
  3. If input_concat_dim is given, ensure that the dimension and its coordinate are usable for concatenation.

This order makes it possible for a custom preprocessor to perform structural changes, for example replacing a sounder_dim dimension with an existing time coordinate; the returned dimensions must be reflected in the final preprocessing result.

A time coordinate that already exists and satisfies the concatenation requirement is preserved unchanged. If the requested concatenation coordinate is absent:

  • For input_concat_dim="time", the dataset attributes time_coverage_start and time_coverage_end are read. Space-separated ISO timestamps, T/Z ISO timestamps, and compact YYYYMMDDhhmmss timestamps must be accepted. When it is supplied, input_datetime_format controls parsing.
  • At least one coverage endpoint must be present. When only one is present, it is used for both bounds.
  • Create a one-element time coordinate positioned at the midpoint of the two endpoints.
  • Create time_bnds, containing the start and end values, on the dimensions ("time", "bnds").
  • Set time.attrs["bounds"] to "time_bnds", and expand data variables along time where needed.

The following failures raise ConverterError with these exact messages:

Cannot parse timestamp from "<value>".
Missing time_coverage_start and/or time_coverage_end in dataset attributes.
Missing (coordinate) variable "<name>" for dimension "<name>".

The final message is the one that applies when a non-time concatenation coordinate cannot be found.

Processing datasets and output encodings

nc2zarr.processor.DatasetProcessor
DatasetProcessor(
    process_rename=None,
    process_rechunk=None,
    process_custom_processor=None,
    output_encoding=None,
)

The process_dataset(ds) method returns a two-item tuple, (dataset, encoding), and applies the operations in this order:

  1. Rename variables as dictated by process_rename.
  2. If process_custom_processor is configured, resolve and invoke it and use the returned dataset.
  3. Apply process_rechunk and construct the Zarr chunk encodings.
  4. Merge the generated chunk encodings with output_encoding.

As a result, a custom processor sees the renamed arrays, and the rechunk rules may refer to the renamed names. When rename, custom processing, rechunking, and output encoding all require no work, the exact input dataset object is returned with {}.

Rules for rechunking

process_rechunk is a mapping in which the "*" entry supplies the default dimension rules, and the variable-name entries override those defaults for that variable. A rule for a variable may be a dimension-to-size mapping, or a single value applied to all of that variable's dimensions.

The supported sizes are:

  • An integer: that chunk size is requested.
  • None: the dimension's full extent is used as a single chunk.
  • "input": the input chunk size is preserved; for an unchunked input, its full dimension extent is used.

Rules given per variable take precedence over the wildcard rules. The requested rechunking must affect the Dask chunk topology of the selected arrays. A coordinate such as time that is unaffected remains unchunked when it is not selected, independently of any storage-chunk tuple generated for it.

When rechunking is active, the returned encoding contains a chunks tuple, in dimension order, for each non-scalar data variable and coordinate. Arrays that are unspecified and unchunked receive full-extent chunk sizes, while chunked inputs retain their input size unless overridden. For scalar variables, a chunks tuple is not required. output_encoding is merged per variable: generated chunks are preserved and configured fields are added, and on key conflicts explicitly configured fields take precedence.

Any chunk-size value that is unsupported raises ValueError with exactly:

invalid chunk size: <repr>

with <repr> being the representation of the invalid value.

Configuring both output_append=True and an output_custom_postprocessor that is not None raises ValueError with exactly:

output_append and output_custom_postprocessor cannot be given both
How the post-processor behaves
  • output_custom_postprocessor applies the same "<module>:<attribute.path>" resolution and failure behavior as load_custom_func.
  • One xarray.Dataset is passed to the resolved callable, and it must return an xarray.Dataset.
  • It is applied to the complete final dataset immediately before that dataset is written; what is serialized is the value it returns, not the pre-processed argument.
  • The writer must isolate the caller's dataset from the changes made in post-processing. Variables, coordinates, attributes, or other changes introduced by the hook must appear in the stored dataset, without the original dataset object supplied by the caller being mutated.
  • If there is no configured post-processor, the dataset is written unchanged.
  • Post-processing is deliberately incompatible with constructor append mode, because it operates on a complete output dataset rather than individual appended slices.

For example:

def my_postprocessor(ds: xr.Dataset) -> xr.Dataset:
    return ds.assign(crs=xr.DataArray(42))

When it is referenced as "my.module:my_postprocessor", the reopened Zarr dataset contains crs, while the caller's original in-memory dataset does not.

Behavior for local and object storage
  • A normal write to a fresh local path creates a Zarr store directory that xarray.open_zarr can read.
  • When output_overwrite=True, an existing store is successfully replaced. When output_overwrite=False, a fresh path succeeds, but an existing store is not silently replaced, and the backend's conflict error propagates.
  • With output_append=True, data is appended to an existing store along output_append_dim, and a store is created when one does not yet exist. The default append dimension is time.
  • With dry_run=True, no creation, deletion, replacement, or append operation is performed. In particular, it creates no new local store and leaves any existing store in place, even when overwrite was requested.
  • When output_s3_kwargs is supplied, object storage is selected, and credentials plus custom client endpoint options are accepted. Merely constructing the writer must not contact or require the configured endpoint. An s3:// output path also selects object storage.
  • When a write to an inaccessible object-storage destination fails, the storage/backend exception must propagate rather than success being reported.

def preprocess_dataset(self, ds: xr.Dataset) -> xr.Dataset

The processing order is: variable selection, custom preprocessing, and then ensuring the concatenation dimension.

Selecting variables and custom preprocessing
  • With input_variables=None, all variables are preserved.
  • An input_variables collection that is supplied selects exactly the requested variables and coordinates.
  • input_custom_preprocessor is a <module>:<dotted.attribute> callable reference that load_custom_func resolves. For example, a hook may swap dimensions so that a sounder_dim dimension is replaced by a time coordinate dimension.
Concatenation coordinates and the synthesized time coordinate

  • When the requested concatenation coordinate already exists, it is preserved. A scalar coordinate may be expanded into its named dimension where needed. If the coordinate is already a proper dimension coordinate, its values must be left untouched.

  • When the requested coordinate is absent and named time, time_coverage_start and time_coverage_end are read from the dataset's global attributes, and the coordinate is synthesized:

    • Each attribute value is parsed as a timestamp. If input_datetime_format is supplied, it gives an explicit parse format; otherwise common textual forms must be accepted automatically, including at least YYYY-MM-DD HH:MM:SS (e.g. 2020-09-08 10:30:00), ISO YYYY-MM-DDTHH:MM:SSZ (e.g. 2020-09-08T10:30:00Z), and compact YYYYMMDDHHMMSS (e.g. 20200908103000).
    • If one of the two attributes is the only one present, its value serves as both start and end of the coverage interval.
    • Add a time coordinate with one element, whose single value is the midpoint of the coverage interval. For example, a coverage interval from 2020-09-08 10:30:00 to 2020-09-08 12:30:00 yields the time value 2020-09-08 11:30:00.
    • The attributes of the synthesized time coordinate must be exactly {'bounds': 'time_bnds'}.
    • Add a time_bnds variable with dimensions ('time', 'bnds'); its single row contains the parsed start and end timestamps, in that order.

  • When a coverage timestamp cannot be parsed, ConverterError must be raised with exactly:

    Cannot parse timestamp from "<value>".

  • When neither time_coverage_start nor time_coverage_end supplies a coverage timestamp, ConverterError must be raised with exactly:

    Missing time_coverage_start and/or time_coverage_end in dataset attributes.

    Attributes named only start_time and end_time are not a substitute for the required attribute names; a dataset that carries only those must still fail with the message above.

  • When the requested concatenation coordinate is absent and its name is not time, no coordinate can be synthesized. ConverterError must be raised with exactly:

    Missing (coordinate) variable "<name>" for dimension "<name>".

    For example, requesting input_concat_dim='t' on a dataset that has no t variable produces Missing (coordinate) variable "t" for dimension "t".

  • After the concatenation coordinate is available, data variables that do not yet use the concatenation dimension must be expanded along it, so that every data variable in the returned dataset carries the concatenation dimension. Any associated bounds variable (the one named by the coordinate's bounds attribute, or <dim>_bnds by default) must remain present in the result.

def process_dataset(self, ds: xr.Dataset) -> Tuple[xr.Dataset, Dict[str, Dict[str, Any]]]

nc2zarr.processor.DatasetProcessor.process_dataset returns a (dataset, encoding) pair. The processing order is:

  1. Renaming: process_rename is a mapping from existing names to new names that is applied to the dataset, so a renamed variable shows up only under its new name in the result.
  2. Custom processing: process_custom_processor is a <module>:<dotted.attribute> callable reference that load_custom_func resolves. It is invoked with the current dataset, and processing continues with the dataset it returns.
  3. Rechunking, as detailed below.

If there is no effective renaming, custom processing, or rechunking, and no output encoding, process_dataset must return the original dataset object itself (identity preserved) along with an empty encoding mapping {}. Empty mappings for process_rechunk and output_encoding count as "no effective processing".

Rechunking

process_rechunk configures chunk sizes per dimension:

  • The special key '*' provides a default mapping from dimension names to chunk-size rules that applies to every variable.
  • Any other key names a variable and overrides that variable's defaults. A per-variable override may be either:
    • a mapping from dimension names to chunk-size rules, applied across all of that variable's dimensions (dimensions that the mapping does not name are treated as None), or
    • a single scalar rule (an integer, None, or 'input') that applies to every dimension of that variable.
  • Dimensions that no applicable rule covers default to 'input'.

The meanings of the chunk-size rules are:

  • An integer gives the requested chunk size for that dimension; it may exceed the dimension length.
  • None stands for the full dimension length (that dimension is left unchunked).
  • 'input' stands for the source chunk size of that dimension, or for the full dimension length when the input is unchunked.

Whenever a resolved rule value is not an integer, None, or 'input', a ValueError must be raised with exactly:

invalid chunk size: <value>

For instance, a list rule like [1, 2, 3] produces invalid chunk size: [1, 2, 3].

With rechunking enabled:

  • The dataset that is returned is a rechunked copy (not the same object), and the data chunking of each variable must reflect the resolved sizes. For example, a variable with 100 elements along time, rechunked to 20, exposes chunks (20, 20, 20, 20, 20) along that dimension.
  • The encoding mapping that is returned holds one entry per dataset variable, of the form {'chunks': (<resolved sizes in the variable's dimension order>)}. For instance, with defaults {'*': {'lon': 8, 'lat': 4, 'time': 1}}, a variable with dimensions (time, lat, lon) yields {'chunks': (1, 4, 8)}, and the coordinate lon yields {'chunks': (8,)}.

Appending must succeed in this case: these non-time variables must be written once and then left unchanged (not duplicated or concatenated) across subsequent appends, while the variables that are dimensioned by time are concatenated along time as usual. After all appends have been carried out, the concatenation of the time-dimensioned data across all appended slices must match the original per-slice inputs in order.

This behavior must work correctly when reading and writing take place with CF decoding disabled (input_decode_cf=False, datasets opened with decode_cf=False).

finalize() — adjusting the metadata

finalize() modifies the global attributes (.attrs) of the written Zarr store. Before finalize() is called, none of the attributes described below are present on the store (they are added only by finalize()). Which behavior applies depends on the constructor settings:

When output_adjust_metadata is truthy:

finalize() must compute the following global attributes and add them to the store, with the values derived from the actual contents of the written dataset:

  • history — must be present (added). No further constraint is placed on its exact textual content.
  • source — must be present. Its value is a list of the input source files joined with comma-and-space (", "), including only paths that are NetCDF inputs (paths ending in .nc) and excluding any Zarr paths (e.g. paths ending in .zarr), with their original order preserved. For example, given input paths ['a.nc', 'z.zarr', 'b.nc'], the resulting source value is "a.nc, b.nc".
  • time_coverage_start — the dataset's earliest time coverage, formatted as "YYYY-MM-DD HH:MM:SS".
  • time_coverage_end — the dataset's latest time coverage, formatted as "YYYY-MM-DD HH:MM:SS".

Rules used to compute time_coverage_start / time_coverage_end:

  • If the dataset's time coordinate variable declares a bounds variable through its bounds attribute (e.g. time.attrs['bounds'] == 'time_bnds', with time_bnds present and having dimensions ("time", "bnds")), then the coverage start is the minimum value of the bounds variable, and the coverage end is the maximum value of the bounds variable.
  • Otherwise, the coverage start is the earliest time value, and the coverage end is the latest time value.

For a concrete example: writing three daily slices whose time values correspond to 2020-12-01 10:00:00, 2020-12-02 10:00:00, and 2020-12-03 10:00:00 (no bounds) yields time_coverage_start == "2020-12-01 10:00:00" and time_coverage_end == "2020-12-03 10:00:00".

When time_bnds is present and covers 09:30:00–10:30:00 on each of the same three days, the outcome is time_coverage_start == "2020-12-01 09:30:00" and time_coverage_end == "2020-12-03 10:30:00".

When output_metadata is provided (i.e. a mapping):

finalize() must add each key/value pair from output_metadata to the store as a global attribute (e.g. {'comment': 'This dataset is crap.'} results in the store having attribute comment with that value). Attributes that are not listed in output_metadata are unaffected.

These two behaviors are independent of one another, and each of them may be triggered by its respective setting.

Component 2: Converter

The constructor of the Converter class must carry out argument validation. Errors are raised as ConverterError (an exception that can be imported from the same location as Converter). The args tuple of the exception must contain exactly the single message string described.

  • If both output_overwrite=True and output_append=True are given, a ConverterError must be raised with the message: Output overwrite and append flags cannot be given both.

  • An output_metadata parameter must be accepted by the constructor. It must be a mapping from attribute names (strings) to values. If output_metadata is not a mapping (e.g. a list), or if any of its keys is not a string (e.g. an integer key), a ConverterError must be raised with the message: Output metadata must be a mapping from attribute names to values.

  • When at least one input path is provided and output_metadata is a valid mapping (including one keyed by string names), the constructor must not raise on account of these parameters.

(For context: when no input is given, the constructor already raises ConverterError with message At least one input must be given. — this existing behavior is unchanged.)

Import requirements

  • Converter and ConverterError from their existing module.
  • DatasetWriter from its existing module, with the constructor parameters and the write_dataset / finalize methods described above.
