Task Specification: Preserve nc2zarr Public Behavior and Add DatasetWriter Post-Processing

Overview

Add optional custom post-processing to nc2zarr.writer.DatasetWriter while preserving the existing conversion pipeline and its public extension points. A configured post-processor receives the complete output xarray.Dataset immediately before serialization, and its returned dataset is written.

Callable references used by preprocessing, processing, and post-processing share one public resolution format. Existing configuration, input opening, preprocessing, rechunking, conversion, logging, command-line, local-storage, and object-storage behavior must remain compatible.

Custom callable references

nc2zarr.custom.load_custom_func
load_custom_func(func_ref: str) -> Callable

A callable reference has the form "<module>:<attribute.path>":

  • <module> is an importable Python module.
  • <attribute.path> is one or more valid Python identifiers separated by dots.
  • Resolution starts at the imported module and follows every attribute in order. This must support both module-level callables and dotted attributes such as class methods.
  • The resolved object is returned only if it is callable.

Failures are ValueErrors with the following exact messages:

  • A missing module or attribute part, a missing colon, or an invalid attribute-path identifier:
    func_ref "<ref>" is invalid, format must be <module>:<function>
  • A module that cannot be imported:
    module for function "<ref>" not found
  • A missing attribute while traversing the path:
    function "<ref>" not found, unknown attribute "<attribute>"
  • A successfully resolved object that is not callable:
    "<ref>" is not callable

All custom dataset hooks described below accept one xarray.Dataset and return the dataset that the next pipeline stage must use.

Configuration loading

nc2zarr.config.load_config
load_config(config_paths=None, return_kwargs=False, **kwargs) -> dict
  • With no configuration paths and no keyword values, it returns {}.
  • config_paths may be one path or a sequence of YAML paths.
  • Flat keyword names beginning with input_, process_, or output_ are converted to the corresponding nested input, process, or output mapping. Other names, including dry_run and verbosity, remain at the top level.
  • Explicit false values such as False and zero are retained; only absent or None keyword values are omitted from nested configuration construction.
  • With return_kwargs=True, the input, process, and output mappings are flattened back to input_*, process_*, and output_* names so the result can be passed as constructor keyword arguments.
  • Multiple YAML mappings are recursively merged from left to right. Later scalar values replace earlier values, nested mappings are recursively combined, and list values are concatenated. In particular, input-path lists accumulate in file order.
  • Explicit keyword configuration is merged after all YAML configurations. It therefore has later precedence for replaceable values, while keyword lists append to earlier lists under the list-concatenation rule.

A missing path raises nc2zarr.error.ConverterError with exactly:

Configuration not found: <path>

Dataset preprocessing

preprocess_dataset(ds) performs these stages in order:

  1. If a non-empty input_variables list is given, retain the requested variables and coordinates and remove unrequested ones. With input_variables=None (or an empty list), preserve all variables.
  2. If input_custom_preprocessor is given, resolve it using load_custom_func, call it with the selected dataset, and use its return value.
  3. If input_concat_dim is given, ensure that dimension and its coordinate are usable for concatenation.

This order allows a custom preprocessor to perform structural changes, for example replacing a sounder_dim dimension with an existing time coordinate; the returned dimensions must be reflected in the final preprocessing result.

An existing time coordinate that already satisfies the concatenation requirement is preserved unchanged. If the requested concatenation coordinate is absent:

  • For input_concat_dim="time", read time_coverage_start and time_coverage_end from dataset attributes. Space-separated ISO timestamps, T/Z ISO timestamps, and compact YYYYMMDDhhmmss timestamps must be accepted. input_datetime_format, when supplied, controls parsing.
  • At least one coverage endpoint must be present. If only one is present, use it for both bounds.
  • Create a one-element time coordinate at the midpoint of the two endpoints.
  • Create time_bnds containing the start and end values on dimensions ("time", "bnds").
  • Set time.attrs["bounds"] to "time_bnds" and expand data variables along time where needed.

The following failures raise ConverterError with exact messages:

Cannot parse timestamp from "<value>".
Missing time_coverage_start and/or time_coverage_end in dataset attributes.
Missing (coordinate) variable "<name>" for dimension "<name>".

The final message applies when a non-time concatenation coordinate cannot be found.

Dataset processing and output encodings

nc2zarr.processor.DatasetProcessor
DatasetProcessor(
    process_rename=None,
    process_rechunk=None,
    process_custom_processor=None,
    output_encoding=None,
)

process_dataset(ds) returns a two-item tuple (dataset, encoding) and applies operations in this order:

  1. Rename variables according to process_rename.
  2. Resolve and invoke process_custom_processor, if configured, and u returned dataset.
  3. Apply process_rechunk and construct Zarr chunk encodings.
  4. Merge generated chunk encodings with output_encoding.

Thus a custom processor sees renamed arrays, while rechunk rules may refer to the renamed names. If rename, custom processing, rechunking, and output encoding all require no work, the exact input dataset object is returned with {}.

Rechunk rules

process_rechunk is a mapping whose "*" entry supplies default dimension rules and whose variable-name entries override those defaults for that variable. A variable rule may be a dimension-to-size mapping or a single value applied to all of that variable's dimensions.

Supported sizes are:

  • An integer: request that chunk size.
  • None: use the dimension's full extent as a single chunk.
  • "input": preserve the input chunk size; for an unchunked input, use its full dimension extent.

Per-variable rules take precedence over wildcard rules. Requested rechunking must affect the selected arrays' Dask chunk topology. An unaffected coordinate such as time remains unchunked when it is not selected, independently of any storage-chunk tuple generated for it.

When rechunking is active, the returned encoding contains a chunks tuple in dimension order for each non-scalar data variable and coordinate. Unspecified unchunked arrays receive full-extent chunk sizes, while chunked inputs retain their input size unless overridden. Scalar variables do not require a chunks tuple. output_encoding is merged per variable, preserving generated chunks and adding configured fields; explicitly configured fields take precedence on key conflicts.

Any unsupported chunk-size value raises ValueError with exactly:

invalid chunk size: <repr>

where <repr> is the representation of the invalid value.

Post-processor behavior
  • output_custom_postprocessor uses the same "<module>:<attribute.path>" resolution and failure behavior as load_custom_func.
  • The resolved callable receives one xarray.Dataset and must return an xarray.Dataset.
  • It is applied to the complete final dataset immediately before that dataset is written. Its return value, not the pre-processed argument, is serialized.
  • The writer must isolate the caller's dataset from post-processing changes. Variables, coordinates, attributes, or other changes introduced by the hook must appear in the stored dataset without mutating the original dataset object supplied by the caller.
  • With no configured post-processor, the dataset is written unchanged.
  • Post-processing is intentionally incompatible with constructor append mode because it operates on a complete output dataset rather than individual appended slices.

For example:

def my_postprocessor(ds: xr.Dataset) -> xr.Dataset:
    return ds.assign(crs=xr.DataArray(42))

If referenced as "my.module:my_postprocessor", the reopened Zarr dataset contains crs, while the caller's original in-memory dataset does not.

Local and object-storage behavior
  • A normal write to a fresh local path creates a Zarr store directory readable by xarray.open_zarr.
  • With output_overwrite=True, an existing store is replaced successfully. With output_overwrite=False, a fresh path succeeds, but an existing store is not silently replaced and the backend's conflict error propagates.
  • output_append=True appends to an existing store along output_append_dim and creates a store when one does not yet exist. The default append dimension is time.
  • dry_run=True performs no creation, deletion, replacement, or append operation. In particular, it creates no new local store and leaves any existing store in place even when overwrite was requested.
  • Supplying output_s3_kwargs selects object storage and accepts credentials plus custom client endpoint options. Merely constructing the writer must not contact or require the configured endpoint. An s3:// output path also selects object storage.
  • A failed write to an inaccessible object-storage destination must propagate the storage/backend exception rather than report success.

def process_dataset(self, ds: xr.Dataset) -> Tuple[xr.Dataset, Dict[str, Dict[str, Any]]]

nc2zarr.processor.DatasetProcessor.process_dataset returns a (dataset, encoding) pair. Processing order is:

  1. Renaming: process_rename is a mapping of existing names to new names applied to the dataset, so a renamed variable appears only under its new name in the result.
  2. Custom processing: process_custom_processor is a <module>:<dotted.attribute> callable reference resolved by load_custom_func. Invoke it with the current dataset and continue with its returned dataset.

Rechunking

process_rechunk configures per-dimension chunk sizes:

  • The special key '*' supplies a default mapping from dimension names to chunk-size rules that applies to every variable.
  • Any other key names a variable and overrides the defaults for that variable. A per-variable override may be either:
    • a mapping from dimension names to chunk-size rules, which is applied across all of that variable's dimensions (dimensions the mapping does not name are treated as None), or
    • a single scalar rule (an integer, None, or 'input'), which applies to every dimension of that variable.
  • Dimensions not covered by any applicable rule default to 'input'.

Chunk-size rules have these meanings:

  • An integer is the requested chunk size for that dimension. It may exceed the dimension length.
  • None means the full dimension length (the dimension is left unchunked).
  • 'input' means the source chunk size of that dimension, or the full dimension length when the input is unchunked.

Any resolved rule value that is not an integer, None, or 'input' must raise ValueError with exactly:

invalid chunk size: <value>

For example, a list rule such as [1, 2, 3] produces invalid chunk size: [1, 2, 3].

When rechunking is enabled:

  • The returned dataset is a rechunked copy (not the same object), and each variable's data chunking must reflect the resolved sizes. For example, a variable with 100 elements along time rechunked to 20 exposes chunks (20, 20, 20, 20, 20) along that dimension.
  • The returned encoding mapping contains one entry per dataset variable of the form {'chunks': (<resolved sizes in the variable's dimension order>)}. For instance, with defaults {'*': {'lon': 8, 'lat': 4, 'time': 1}}, a variable with dimensions (time, lat, lon) yields {'chunks': (1, 4, 8)} and the coordinate lon yields {'chunks': (8,)}.
Encoding merge

Entries from output_encoding that name dataset variables must be merged into the returned encoding: a variable's generated chunk encoding is updated key-by-key with its output_encoding entry. For example, rechunking r_i32 together with output_encoding={'r_i32': {'compressor': None, 'fill_value': None}} yields {'chunks': (...), 'compressor': None, 'fill_value': None} for that variable.

Extend nc2zarr.batch with a job-status value object and live state tracking for batch jobs. DryRunJob, LocalJob, and SlurmJob must all expose readable status and state attributes or properties. Status observation must be asynchronous: submitting a local or Slurm job must not wait for that job to finish.

The former is_running boolean API is removed. Callers must determine lifecycle state through status, comparing it with the JobStatus constants.

JobStatus

Add a public JobStatus value-object class in nc2zarr.batch.

Defined statuses

The class must expose at least these class-level constants, each of which is a JobStatus instance:

  • JobStatus.RUNNING, whose status ID is 'Running'
  • JobStatus.COMPLETED, whose status ID is 'Completed'
  • JobStatus.UNKNOWN, whose status ID is 'Unknown'

Additional statuses may be defined, but these three and their exact IDs are required.

Construction and identity

JobStatus(status_id) accepts a defined status ID string and returns the canonical singleton for that ID. In particular:

JobStatus('Running') is JobStatus.RUNNING
JobStatus('Running') is JobStatus('Running')
JobStatus('Completed') is JobStatus.COMPLETED
JobStatus('Unknown') is JobStatus.UNKNOWN

Invalid construction has type-specific errors whose messages use repr() for the offending value:

  • An unknown string raises ValueError. For example, JobStatus('Pippo') must raise with exactly invalid status_id: 'Pippo'.
  • A non-string raises TypeError. For example, JobStatus(137) must raise with exactly invalid status_id: 137.
Equality and hashing
  • Status objects with the same status ID compare equal.
  • A status object compares equal to its plain status-ID string in either operand order. For example, both JobStatus.RUNNING == 'Running' and 'Running' == JobStatus.RUNNING are true.
  • Its hash is the hash of its status-ID string. Thus hash(JobStatus('Running')), hash(JobStatus.RUNNING), and hash('Running') are equal.
String forms
  • str(JobStatus.RUNNING) is exactly 'Running'.
  • repr(JobStatus.RUNNING) is exactly "JobStatus('Running')".

Common job contract

BatchJob remains the common public abstraction for batch jobs. Each concrete job returned by submit_job(...) must expose:

  • status: the current canonical JobStatus instance.
  • state: the current low-level state for that job type.

State and status may change asynchronously as an observer refreshes them. Job completion means that the launched process or scheduled job is no longer running; it does not imply that its exit code was zero.

DryRunJob

DryRunJob.submit_job(command, out_path, err_path, **job_params)

A dry-run job logs/describes the requested submission but performs no work, launches no process, and does not create a scheduled job. It returns a DryRunJob immediately with:

job.status is JobStatus.COMPLETED

It must expose state as required by the common contract, although no particular low-level state structure is required for a job that was not launched. Extra job parameters supplied by batch orchestration, including working-directory and environment parameters, must be accepted without causing real work.

LocalJob

LocalJob.submit_job(
    command,
    out_path,
    err_path,
    *,
    env_vars=None,
    cwd_path=None,
    poll_period=None,
)
  • command is a list of strings containing the executable and its arguments.
  • Standard output is redirected to out_path, and standard error is redirected to err_path.
  • If env_vars is provided, its entries augment or override the corresponding entries in the inherited process environment; unrelated inherited variables remain available.
  • If cwd_path is provided, it is the subprocess working directory.
  • poll_period is an optional interval in seconds for refreshing local process state. If omitted, a default polling interval may be used.
  • The method returns a LocalJob after spawning the subprocess and observes it in the background.

While the process is alive:

job.status is JobStatus.RUNNING

Once the process terminates, regardless of exit code:

job.status is JobStatus.COMPLETED

job.state must always be a dictionary containing at least:

  • 'pid': the subprocess process ID.
  • 'exit_code': None while no exit code has been observed, then the subprocess exit code after termination.

The existing exit_code property remains available and reflects the observed process exit code. Output streams must be closed once observation detects termination. If process creation itself fails, any output files opened by submission must be closed and the spawning exception must propagate.

SlurmJob

SlurmJob.submit_job(
    command,
    out_path,
    err_path,
    *,
    env_vars=None,
    cwd_path=None,
    partition=None,
    duration=None,
    poll_period=None,
    sbatch_program='sbatch',
    squeue_program='squeue',
)
  • command is a list of strings containing the executable and its arguments.
  • env_vars supplies variables to export to the scheduled job. Values are converted to their string command-line forms.
  • cwd_path, partition, and duration are optional Slurm working-directory, partition, and time-limit values.
  • poll_period is the queue refresh interval in seconds; an implementation default may be used when it is omitted.
  • sbatch_program and squeue_program select the submission and queue-query executables respectively.
Submission command

Construct the submission command in this exact argument order:

<sbatch_program> -o <out_path> -e <err_path> [--partition=<partition>] [--time=<duration>] [--chdir=<cwd_path>] [--export=ALL,<K1>=<V1>,<K2>=<V2>,...] <command...>

The bracketed arguments are included only when their corresponding values are supplied. Environment entries retain the order in which they are provided. The output and error options must use the two-argument short forms -o <out_path> and -e <err_path>. Do not add --job-name, --output, or --error arguments.

For example, with all optional values present, the argument order is:

sbatch -o job.out -e job.err --partition=short-serial --time=02:00:00 --chdir=. --export=ALL,TEST1=123,TEST2=ABC nc2zarr --help

The command is invoked while capturing the submission program's standard output and standard error.

Submission failure

If the submission program exits with a nonzero status:

  1. Write its captured standard output to out_path and its captured standard error to err_path.
  2. Raise EnvironmentError.
  3. The exception message must be exactly the following prefix followed by the rendered command line that was invoked:
Slurm job submission failed for command line: <rendered command line>

For the example above, the complete message is:

Slurm job submission failed for command line: sbatch -o job.out -e job.err --partition=short-serial --time=02:00:00 --chdir=. --export=ALL,TEST1=123,TEST2=ABC nc2zarr --help
Successful submission and job ID

A successful submission is identified from a standard-output line of this form:

Submitted batch job <ID>

Leading and trailing whitespace around the line may be ignored. The returned SlurmJob exposes the numeric ID as a string through job_id; for example, the line Submitted batch job 43862490 produces job.job_id == '43862490'.

A zero exit status without a parseable submission line is not a successful job submission and must raise EnvironmentError indicating that the Slurm job ID could not be obtained.

After obtaining the ID, begin observing the job in the background with squeue_program. A successfully submitted active job has JobStatus.RUNNING until polling determines another status.

Queue state

Queue output has a whitespace-separated header row followed by a whitespace-separated data row for the requested job. For example:

JOBID PARTITION NAME USER ST TIME NODES NODELIST(REASON)
43862490 short-ser ghg/ch4/ forman R 0:03 1 host495

On a successful query that returns the row, state is a dictionary pairing each header with the corresponding value, preserving values as strings:

{
    'JOBID': '43862490',
    'PARTITION': 'short-ser',
    'NAME': 'ghg/ch4/',
    'USER': 'forman',
    'ST': 'R',
    'TIME': '0:03',
    'NODES': '1',
    'NODELIST(REASON)': 'host495',
}

An active row such as the example above keeps the public status at JobStatus.RUNNING. If a successful query establishes that the job is no longer active, the public status becomes JobStatus.COMPLETED.

If a queue query exits with a nonzero status, that refresh must set:

job.state is None
job.status is JobStatus.UNKNOWN

A failed refresh replaces any previously known state in this way.

Observation lifecycle

A SlurmJob exposes:

  • is_observing: True while background queue polling is active and False when it is not.
  • end_observation(): stops background polling. Once this call returns, is_observing must be False.

After successful submission, observation starts automatically and remains active through successful queue refreshes unless explicitly ended or the observed lifecycle completes.

Persistent queue-query failure must not leave observation running indefinitely, but neither may a single transient failure stop it immediately. Observation must self-terminate after a small fixed number of consecutive failed polls, approximately three to five polling periods. Successful polling resets a consecutive-failure streak.

The required timing is externally observable: with poll_period=0.1 seconds and every queue query failing, the job must still report is_observing == True about 0.2 seconds after submission, and must report is_observing == False by about 0.6 seconds after submission. During this failure interval and after automatic shutdown, the latest failed-poll state remains None and status remains JobStatus.UNKNOWN unless another successful refresh has superseded it.

TemplateBatch compatibility

The existing template-based orchestration must continue to work with the new status API.

TemplateBatch(
    config_template_variables,
    config_template_path,
    config_path_template,
    create_parents=True,
    dry_run=False,
    verbosity=0,
)

For each mapping in config_template_variables, write_config_files() must:

  1. Replace each literal ${name} placeholder represented by the mapping in both the configuration contents and config_path_template, using the string form of the value.
  2. Create a missing parent directory when create_parents is true, except that a dry run performs no filesystem creation.
  3. Write the interpolated configuration unless this is a dry run.
  4. Return one tuple (config_path, out_path, err_path) in input order. out_path and err_path are formed by replacing the configuration path's extension with .out and .err respectively.

execute(nc2zarr_args=None, job_type=None, job_cwd_path=None, job_env_vars=None, **job_params) must return a list with one non-blocking job submission per generated configuration. Each command has this form:

nc2zarr <nc2zarr_args...> -c <config_path>

The default job type is local; supported names are local, slurm, and dry_run. Any other value must raise ValueError with the exact message illegal job_type "<value>". Validation still applies when the batch itself is a dry run. For a valid requested type, dry_run=True forces DryRunJob, creates no configuration files or processes, and every returned job has status is JobStatus.COMPLETED.

Working-directory and environment values, together with remaining job_params, must be forwarded to each selected job class.

Scope and compatibility

This change replaces only the old is_running lifecycle check with status/state; existing submission, output redirection, environment, template expansion, and job-ID behavior must remain compatible as described above. No changes to conversion, configuration loading, dataset processing, or command-line conversion behavior are required.

Required change

In the public nc2zarr.batch module, add a public instance property to BatchJob:

class BatchJob:
    @property
    def done(self) -> Optional[bool]:
        ...

done is part of the BatchJob API and must also be available as an inherited property on the existing nc2zarr.batch.DryRunJob, nc2zarr.batch.LocalJob, and nc2zarr.batch.SlurmJob classes.

Required behavior

The property reports completion using three states based on the job's current status:

  • Return True when the job has completed and status is JobStatus.COMPLETED.
  • Return False while the job has a known, non-completed active status. In particular:
    • a newly submitted LocalJob that is still running returns False;
    • a successfully observed but unfinished SlurmJob returns False.
  • Return None when completion cannot be determined because the status is JobStatus.UNKNOWN. In particular:
    • a newly submitted SlurmJob returns None before its first observation result is available;
    • if polling a SlurmJob fails and its status remains JobStatus.UNKNOWN, done continues to return None, including after observation has stopped.

Required lifecycle transitions

  • A DryRunJob returned by DryRunJob.submit_job(...) has status is JobStatus.COMPLETED and done is True.
  • A running LocalJob changes from done is False to done is True when its status changes to JobStatus.COMPLETED.
  • SlurmJob.end_observation() only stops observation. It must not mark an unfinished job as completed: a successfully observed unfinished job remains done is False after observation ends.

All existing batch-job status and observation behavior must remain compatible; done is an additive completion-reporting API.
