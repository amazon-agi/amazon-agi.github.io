01 Change the way infoblox_client.connector.Connector makes its HTTP requests. 181 words · source specification, reworded by GLM-5.3-Flash

Change to implement

Change the way infoblox_client.connector.Connector makes its HTTP requests.

Public API involved

The API that gets exercised is:

  • infoblox_client.connector.Connector(options)
  • Connector.create_object(object_type, payload)
  • Connector.get_object(object_type, query_parameters)
  • Connector.update_object(object_reference, payload)
  • Connector.delete_object(object_reference)

Existing optional arguments and return/error behavior stay outside the scope of this change.

Behavior of requests

For all requests that these methods send through the HTTP session of the connector:

  • create_object uses POST
  • get_object uses GET
  • update_object uses PUT
  • delete_object uses DELETE

Each of the post, get, put, and delete calls, taken individually, must not include a verify keyword argument at all. This holds both for ordinary payloads/queries and for ones that contain extensible attributes.

The request calls must keep providing their existing arguments:

  • POST and PUT: URL, serialized JSON data, Connector.DEFAULT_HEADER, and the timeout configured for the request
  • GET and DELETE: URL, Connector.DEFAULT_HEADER, and the timeout configured for the request

At request level, do not pass verify=True, verify=False, or verify=None. TLS verification must consequently not be overridden per request; the verification setting of the HTTP session remains authoritative.

02 Modify infoblox_client.objects.EA so that extensible-attribute values retain their collection shape when they are converted between the plain Python… 808 words · rewritten by GPT-5.6-sol, reworded by GLM-5.3-Flash

Goal

Modify infoblox_client.objects.EA so that extensible-attribute values retain their collection shape when they are converted between the plain Python representation and the WAPI wire representation. Specifically, values that are lists or tuples must be processed element by element instead of being stringified as a whole.

Public behavior requirements

This behavior must be available via the existing EA interfaces:

  • EA._process_value(rule, value)
  • EA.from_dict(eas_from_nios) for parsing extensible attributes in WAPI format
  • EA(...).to_dict() for producing the WAPI mapping from an EA instance
EA._process_value(rule, value)

_process_value must be callable on EA in the form EA._process_value(rule, value) and must behave as follows:

  • When value is a list, apply rule once to each element and return the results in a list, with element order preserved.
  • When value is a tuple, apply rule once to each element and return the results in a list, with element order preserved. The result is a list, not a tuple.
  • In every other case, apply rule directly to the value and return that result. For this purpose, strings are scalar values.

With str as the rule, the required results include:

EA._process_value(str, [1, 2, 3]) == ['1', '2', '3']
EA._process_value(str, (1, 2)) == ['1', '2']
EA._process_value(str, 1) == '1'
EA._process_value(str, 'string') == 'string'

Parsing extensible attributes in WAPI form

EA.from_dict(eas_from_nios) must still accept the WAPI representation:

{
    'EA Name': {
        'value': value
    }
}

Parsing must process the inner value of each entry according to the shape of that value:

  • A list stays a list, with the parsing conversion applied independently to each element.
  • A tuple is exposed as a list, with the parsing conversion applied independently to each element.
  • A scalar is processed directly.
  • The existing strict Boolean conversion stays in effect: the exact strings 'True' and 'False' become the Boolean values True and False; other values remain unchanged. This conversion applies independently to scalars as well as to collection elements. As an example, the string '0' remains '0'.
  • A falsy top-level eas_from_nios input still produces None.

As a result, parsing the mapping below must preserve the list-valued EA instead of turning it into a string:

wire_eas = {
    'DNS Record Types': {
        'value': ['record_a', 'record_ptr']
    }
}

ea = EA.from_dict(wire_eas)
assert ea.get('DNS Record Types') == ['record_a', 'record_ptr']

Generating extensible attributes in WAPI form

Calling to_dict() on an EA instance must return a mapping that represents each retained plain EA entry as:

'EA Name': {'value': processed_value}

The following rules govern the conversion of processed_value:

  • Retained scalar values are converted using str.
  • Retained list values are converted element by element with str, and the inner value remains a Python list. The list itself must not be converted into its string representation.
  • Retained tuple values are likewise converted element by element with str, with the inner value being a Python list.
  • Filtering is applied to the complete EA value, not separately to the elements of a retained collection.

Before conversion, omit an EA entry if its complete value is exactly one of the following empty values:

  • None
  • the empty string ''
  • the empty list []

These constitute the omission cases. Falsy values other than these must not be discarded. Specifically:

  • Boolean False is retained and turns into the string 'False'.
  • Integer 0 is retained and turns into the string '0'.
  • String values such as 'False', '0', and 'None' are kept unchanged by the string conversion.

As an example:

plain_eas = {
    'Subnet ID': 'some-id',
    'Tenant Name': 'tenant-name',
    'Cloud API Owned': 'True',
    'DNS Record Types': ['record_a', 'record_ptr'],
    'False String EA': 'False',
    'False EA': False,
    'Zero EA': 0,
    'None String EA': 'None',
    'Zero String EA': '0',
    'None EA': None,
    'Empty String EA': '',
    'Empty List EA': [],
}

wire_eas = EA(plain_eas).to_dict()

The output must be:

{
    'Subnet ID': {'value': 'some-id'},
    'Tenant Name': {'value': 'tenant-name'},
    'Cloud API Owned': {'value': 'True'},
    'DNS Record Types': {'value': ['record_a', 'record_ptr']},
    'False String EA': {'value': 'False'},
    'False EA': {'value': 'False'},
    'Zero EA': {'value': '0'},
    'None String EA': {'value': 'None'},
    'Zero String EA': {'value': '0'},
}

None EA, Empty String EA, and Empty List EA must not appear in that result.

Compatibility

Existing EA behavior must stay available alongside the collection handling above:

  • EA() produces an object with an empty plain EA mapping, and EA(ea_dict) accepts the plain {name: value} representation.
  • An EA value is stored with set(name, value).
  • get(name, default=None) returns either the stored value or the supplied default.
  • The ea_dict property returns a top-level copy of the plain {name: value} representation, so changing a key in the returned mapping does not change the corresponding stored key.
  • Scalar WAPI values still round-trip through from_dict() and to_dict(), including the strict Boolean conversions described above.

{

    "username": "admin",
    "password": "password",
    "ssl_verify": False,

Cloud WAPI: True
  • "2.1/"
  • "/2.0/"
  • "2.0.1"
  • "3.0/"
  • "11.0.1/"
  • "v2.1"
  • "v2.0"
Not cloud WAPI: False
  • "1.4.1"
  • "1.9/"
  • "1.99"
  • "asd"
  • "v1.4"

max_results must not be injected into object lookups

When no result limit was requested, higher-level object and object-manager operations must call the connector's get_object method without a max_results keyword. Specifically, they must not pass max_results=None.

get_object(

    payload=None,
    return_fields=None,
    extattrs=None,
    force_proxy=False,
)

  • IPv4 network lookup with object type "network"
  • IPv6 network lookup with object type "ipv6network"
  • Host-record lookup with object type "record:host"
  • IPv4-address lookup with object type "ipv4address"

It also covers InfobloxObjectManager workflows that look up:

  • host records,
  • networks,
  • IP ranges,
  • network views,
  • DNS records during name binding or unbinding,
  • fixed addresses during allocation/deallocation checks,
  • and extensible-attribute definitions.

How the concrete low-level connector handles an explicitly supplied max_results argument is outside the scope of this change.

07 Add Support for the max_results Option 462 words · source specification, reworded by GLM-5.3-Flash

Task Specification: Add Support for the max_results Option

Overview

Add support for an option, max_results, that limits the maximum number of objects the appliance returns. This option must be threaded through the connector's object-retrieval method as well as the search methods of API objects.

Requirements

1. Connector: the get_object method

Objects are retrieved through a get_object method that the connector class (in the connector module) exposes. In its current form, the signature accepts, at minimum, an object type, a payload, and keyword arguments such as return_fields, extattrs, and force_proxy.

Add a new keyword argument max_results, which defaults to None:

def get_object(self, obj_type, payload=None, return_fields=None,
               extattrs=None, force_proxy=False, max_results=None):

Behavior:

  • When a value other than None is provided for max_results, the request URL sent to the appliance must include the _max_results query parameter, set to that value.
    • As an example, a call to get_object('network', {}, max_results=20) made against a WAPI base of https://infoblox.example.org/wapi/v1.1/ must issue an HTTP GET to:
      https://infoblox.example.org/wapi/v1.1/network?_max_results=20
      (the request uses the connector's default headers and the configured HTTP request timeout).
  • When max_results is None (its default), no _max_results parameter is added to the URL, so the existing URL-building behavior is preserved.
2. API Objects: the search and search_all methods

The class methods search and search_all, which internally invoke the connector's get_object, are exposed by objects derived from the base InfobloxObject class.

  • A max_results keyword argument must be accepted by these methods.
  • The max_results value (defaulting to None when it is not supplied) must be passed through to the connector's get_object call as the max_results keyword argument.
  • If max_results is not explicitly provided, the value passed to get_object must be None.

Every existing get_object invocation performed by these search methods must now include max_results as a keyword argument (with value None when unspecified), alongside the existing extattrs, force_proxy, and return_fields keyword arguments.

3. Object Manager

All calls that the object-manager layer makes to the connector's get_object (to locate existing objects during create/delete/bind and related operations) must pass max_results as a keyword argument. If these callers do not specify a limit, the value passed must be None.

Notes

  • The max_results keyword argument is forwarded unchanged; apart from placing it into the _max_results URL parameter when it is not None, no validation or transformation of its value is required.
  • The Tenant object is removed, together with its search support; no requirement exists for a Tenant class or a grid:cloudapi:tenant search path.

Summary of the Public API Surface

  • Connector get_object(self, obj_type, payload=None, return_fields=None, extattrs=None, force_proxy=False, max_results=None) — _max_results=<value> is added to the request URL when max_results is not None.
  • InfobloxObject.search(...) and InfobloxObject.search_all(...) — accept max_results (defaulting to None) and forward it to get_object.

09 Update the public API in infoblox_client.connector so that a default maximum result count can be configured on a Connector and is used by all GET operations. 680 words · rewritten by GPT-5.6-sol, reworded by GLM-5.3-Flash

Specification of the Task

Add support for connector-wide max_results

Update the public API in infoblox_client.connector so that a default maximum result count can be configured on a Connector and is used by all GET operations. Except for the addition of this option and its fallback behavior, existing connector behavior and call compatibility must remain unchanged.

Constructing a Connector

The following must continue to be supported by the constructor:

Connector(options)

options may be either an attribute-style options object or a mapping that is passed directly to the constructor. The existing required options, defaults, validation, session configuration, and handling of all other options must be preserved.

A public max_results attribute must be exposed on every constructed connector:

  • When an attribute-style options object exposes max_results, that value is to be copied unchanged to connector.max_results.
  • When a mapping contains a max_results entry, that value is to be copied unchanged to connector.max_results.
  • When max_results is not present, connector.max_results is to be set to None. This applies in particular when a mapping that does not contain that entry is passed directly to Connector(options).
  • The supported values are integers, with zero and negative integers among them, and None. Values must not be made positive, clamped, or transformed in any other way.

As an example:

options = {
    "host": "infoblox.example.org",
    "username": "admin",
    "password": "password",
    "max_results": 50,
}
connector = Connector(options)
assert connector.max_results == 50

With the same required connection options, but where no max_results entry is present:

connector = Connector(options_without_max_results)
assert connector.max_results is None

A default of None means that the connector itself does not add a result limit; that default must not be replaced with the appliance's WAPI default value.

Connector.from_dict

The following must be supported by the public class/static factory:

Connector.from_dict(options)

with options being a mapping. The connector that is returned must use the same option semantics as direct construction from a mapping:

  • The value of a max_results entry is exposed unchanged as connector.max_results.
  • When the entry is not supplied, connector.max_results is None.
  • By way of example, max_results=50 results in connector.max_results == 50.

Connector.get_object

The existing GET API, including its current optional arguments and their ordering, must be preserved, with a full call shape equivalent to:

get_object(
    obj_type,
    payload=None,
    return_fields=None,
    extattrs=None,
    force_proxy=False,

Apart from that, the other keys (ipv4addrs, view) together with the return-fields list (['ipv4addrs', 'extattrs']) must remain just as displayed, with the addition of ttl leaving them unaffected.

Public API Surface (must remain importable/callable)

  • objects.IP.create(ip, mac) → returns objects.IPv4 when the address is IPv4.
  • objects.IPv4 — the concrete class for IPv4.
  • objects.HostRecord.create(connector, **kwargs) → returns objects.HostRecordV4 if the addresses supplied are IPv4.
  • objects.HostRecordV4 — the concrete host record class for IPv4.

HostRecord.create(...) must accept the ttl keyword, and that keyword must flow into the create_object payload as described.

Task Specification: Query-Parameter URL Encoding in the Infoblox Connector

Summary

Within the infoblox_client.connector module sits the Connector class, which puts WAPI request URLs together; the inputs are a base URL, an object type, and a set of query parameters, and that set may include ordinary query options and "extensible attribute" search parameters. As things stand, the URL construction emits the names and the values of query parameters without applying proper URL encoding. You must ensure that the query parameters end up properly URL encoded when the request URL is put together.

Behavior Requirements

Whenever a request URL gets built, the query string portion (everything after the ?) must be generated by applying standard application/x-www-form-urlencoded encoding to the parameter names and their values. Specifically:

  • If parameter names contain special characters, those characters must be percent-encoded. Namely:
    • A leading * (the prefix attached to extensible-attribute search keys) must be encoded as %2A.
    • A space character must be encoded as +.
  • & joins multiple parameters, while = joins each name/value pair.
Worked example

Suppose the base WAPI URL is https://infoblox.example.org/wapi/v1.1 and the object type is network. Combine these with:

  • an extensible-attribute search parameter, with *Subnet ID as its key and fake_subnet_id as its value, and
  • an additional query parameter, ip, carrying the value 0.0.0.0

The URL that must be produced is:

https://infoblox.example.org/wapi/v1.1/network?%2ASubnet+ID=fake_subnet_id&ip=0.0.0.0

In the same way, when the *Subnet ID=fake_subnet_id extensible attribute is combined with:

  • a some_option=some_value query parameter must yield:
    https://infoblox.example.org/wapi/v1.1/network?%2ASubnet+ID=fake_subnet_id&some_option=some_value
  • the force-proxy flag (it adds _proxy_search=GM) must yield:
    https://infoblox.example.org/wapi/v1.1/network?%2ASubnet+ID=fake_subnet_id&_proxy_search=GM

Public API

The items listed below must stay importable and callable with these signatures/behaviors, so that existing callers keep working:

  • Connector.get_object(self, objtype, payload=None, return_fields=None, extattrs=None, force_proxy=False, ...) — fetches objects of the type supplied to it. On invocation with an object type, a payload/query mapping, and an extattrs mapping, an HTTP GET must be issued by the method against the encoded URL laid out above, passing the connector's default headers and the configured HTTP request timeout.

  • Connector._construct_url(self, relative_path, query_params=None, extattrs=None, force_proxy=False) — returns the request URL in fully constructed form, as a string, with the query string encoded in the manner described above.

Parameter Semantics for URL Construction
  • query_params: maps ordinary query option names to their values.
  • extattrs: maps extensible-attribute names to objects that each carry a value; out of each entry comes a query parameter — its name is the attribute name with * prepended, and its value is that attribute's value.
  • force_proxy: when true, this causes a _proxy_search=GM query parameter to be added.

Remarks

  • The query parameters produced must be ordered such that extensible-attribute parameters appear before ordinary query parameters / proxy flags, in line with the examples above.
  • The change touches only the encoding behavior of the query string; the base URL, the path segment (/network), and the overall structure remain as they were.
