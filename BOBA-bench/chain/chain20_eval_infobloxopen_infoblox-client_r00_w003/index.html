The exercised API is:

  • Connector.update_object(object_reference, payload)

Existing optional arguments and return/error behavior are outside the scope of this change.

Request behavior

For all requests issued by these methods through the connector’s HTTP session:

  • create_object uses POST
  • get_object uses GET
  • update_object uses PUT

The individual post, get, put, and delete calls must not include a verify keyword argument at all. This applies both to ordinary payloads/queries and those containing extensible attributes.

The request calls must continue to provide their existing arguments:

  • GET and DELETE: URL, Connector.DEFAULT_HEADER, and the configured request timeout

Do not pass verify=True, verify=False, or verify=None at request level. TLS verification must therefore not be overridden per request; the HTTP session’s verification setting remains authoritative.

Objective

Update infoblox_client.objects.EA so extensible-attribute values retain their collection shape when converted between the plain Python representation and the WAPI wire representation. In particular, list and tuple values must be processed element by element rather than being stringified as a whole.

Required public behavior

The behavior must be available through the existing EA interfaces:

  • EA._process_value(rule, value)
  • EA.from_dict(eas_from_nios) for parsing WAPI-formatted extensible attributes
  • EA(...).to_dict() for generating the WAPI mapping from an EA instance
EA._process_value(rule, value)

_process_value must be callable on EA as EA._process_value(rule, value) and must behave as follows:

  • If value is a list, apply rule once to each element and return the results in a list, preserving element order.
  • If value is a tuple, apply rule once to each element and return the results in a list, preserving element order. The result is a list, not a tuple.
  • For every other value, apply rule directly to the value and return that result. Strings are scalar values for this purpose.

Using str as the rule, the required results include:

EA._process_value(str, [1, 2, 3]) == ['1', '2', '3']
EA._process_value(str, (1, 2)) == ['1', '2']
EA._process_value(str, 1) == '1'
EA._process_value(str, 'string') == 'string'

Parsing WAPI extensible attributes

EA.from_dict(eas_from_nios) must continue to accept the WAPI representation:

{
    'EA Name': {
        'value': value
    }
}

For each entry, parsing must process the inner value according to its shape:

  • A list remains a list, with the parsing conversion applied independently to each element.
  • A tuple is exposed as a list, with the parsing conversion applied independently to each element.
  • A scalar is processed directly.
  • The existing strict Boolean conversion remains in effect: the exact strings 'True' and 'False' become the Boolean values True and False; other values remain unchanged. This conversion applies independently to collection elements as well as to scalars. For example, the string '0' remains '0'.
  • A falsy top-level eas_from_nios input continues to produce None.

Consequently, parsing this mapping must preserve the list-valued EA rather than turn it into a string:

wire_eas = {
    'DNS Record Types': {
        'value': ['record_a', 'record_ptr']
    }
}

ea = EA.from_dict(wire_eas)
assert ea.get('DNS Record Types') == ['record_a', 'record_ptr']

Generating WAPI extensible attributes

Calling to_dict() on an EA instance must return a mapping in which each retained plain EA entry is represented as:

'EA Name': {'value': processed_value}

The following conversion rules apply to processed_value:

  • Retained scalar values are converted with str.
  • Retained list values are converted element by element with str; the inner value remains a Python list. The list itself must not be converted to its string representation.
  • Retained tuple values are likewise converted element by element with str, and the inner value is a Python list.
  • Filtering applies to the complete EA value, not separately to elements of a retained collection.

Before conversion, omit an EA entry when its complete value is exactly one of the following empty values:

  • None
  • the empty string ''
  • the empty list []

These are the omission cases. Other falsy values must not be discarded. In particular:

  • Boolean False is retained and becomes the string 'False'.
  • Integer 0 is retained and becomes the string '0'.
  • String values such as 'False', '0', and 'None' are retained unchanged by string conversion.

For example:

plain_eas = {
    'Subnet ID': 'some-id',
    'Tenant Name': 'tenant-name',
    'Cloud API Owned': 'True',
    'DNS Record Types': ['record_a', 'record_ptr'],
    'False String EA': 'False',
    'False EA': False,
    'Zero EA': 0,
    'None String EA': 'None',
    'Zero String EA': '0',
    'None EA': None,
    'Empty String EA': '',
    'Empty List EA': [],
}

wire_eas = EA(plain_eas).to_dict()

The result must be:

{
    'Subnet ID': {'value': 'some-id'},
    'Tenant Name': {'value': 'tenant-name'},
    'Cloud API Owned': {'value': 'True'},
    'DNS Record Types': {'value': ['record_a', 'record_ptr']},
    'False String EA': {'value': 'False'},
    'False EA': {'value': 'False'},
    'Zero EA': {'value': '0'},
    'None String EA': {'value': 'None'},
    'Zero String EA': {'value': '0'},
}

None EA, Empty String EA, and Empty List EA must not be present in that result.

Compatibility

Existing EA behavior must remain available alongside the collection handling above:

  • EA() creates an object with an empty plain EA mapping, and EA(ea_dict) accepts the plain {name: value} representation.
  • set(name, value) stores an EA value.
  • get(name, default=None) returns the stored value or the supplied default.
  • The ea_dict property returns the plain {name: value} representation as a top-level copy, so changing a key in the returned mapping does not change the corresponding stored key.
  • Scalar WAPI values continue to round-trip through from_dict() and to_dict(), including the strict Boolean conversions described above.

07 Add max_results Option Support 430 words · source specification

Task Specification: Add max_results Option Support

Overview

Add support for a max_results option that limits the maximum number of objects returned from the appliance. This option must be threaded through the connector's object-retrieval method and the search methods of API objects.

Requirements

1. Connector: get_object method

The connector class (in the connector module) exposes a get_object method used to retrieve objects. Its current signature accepts, at minimum, an object type, a payload, and keyword arguments such as return_fields, extattrs, and force_proxy.

Add a new keyword argument max_results, defaulting to None:

def get_object(self, obj_type, payload=None, return_fields=None,
               extattrs=None, force_proxy=False, max_results=None):

Behavior:

  • When max_results is provided as a non-None value, the request URL sent to the appliance must include the query parameter _max_results set to that value.
    • For example, calling get_object('network', {}, max_results=20) against a WAPI base of https://infoblox.example.org/wapi/v1.1/ must issue an HTTP GET to:
      https://infoblox.example.org/wapi/v1.1/network?_max_results=20
      (using the connector's default headers and configured HTTP request timeout).
  • When max_results is None (the default), no _max_results parameter is added to the URL, preserving existing URL-building behavior.
2. API Objects: search and search_all

Objects derived from the base InfobloxObject class expose search and search_all class methods that internally invoke the connector's get_object.

  • These methods must accept a max_results keyword argument.
  • The value of max_results (defaulting to None when not supplied) must be passed through to the connector's get_object call as the max_results keyword argument.
  • When not explicitly provided, the max_results value passed to get_object must be None.

Every existing invocation of get_object performed by these search methods must now include max_results as a keyword argument (with value None when unspecified), alongside the existing extattrs, force_proxy, and return_fields keyword arguments.

3. Object Manager

All calls made by the object-manager layer to the connector's get_object (for locating existing objects during create/delete/bind and related operations) must pass max_results as a keyword argument. When these callers do not specify a limit, the value passed must be None.

Notes

  • The max_results keyword argument is passed through unchanged; no validation or transformation of its value is required beyond placing it into the _max_results URL parameter when it is not None.
  • The Tenant object and its search support are removed; there is no requirement for a Tenant class or a grid:cloudapi:tenant search path.

Summary of Public API Surface

  • Connector get_object(self, obj_type, payload=None, return_fields=None, extattrs=None, force_proxy=False, max_results=None) — adds _max_results=<value> to the request URL when max_results is not None.
  • InfobloxObject.search(...) and InfobloxObject.search_all(...) — accept max_results (default None) and forward it to get_object.

09 Update the public API in infoblox_client.connector so a default maximum result count can be configured on a Connector and used by all GET operations. 610 words · rewritten by GPT-5.6-sol

Add connector-wide max_results support

Update the public API in infoblox_client.connector so a default maximum result count can be configured on a Connector and used by all GET operations. Existing connector behavior and call compatibility must remain unchanged except for the addition of this option and its fallback behavior.

Connector construction

The constructor must continue to support:

Connector(options)

options may be either an attribute-style options object or a mapping supplied directly to the constructor. Existing required options, defaults, validation, session configuration, and handling of all other options must be preserved.

Every constructed connector must expose a public max_results attribute:

  • If an attribute-style options object exposes max_results, copy that value unchanged to connector.max_results.
  • If a mapping contains a max_results entry, copy that value unchanged to connector.max_results.
  • If max_results is omitted, set connector.max_results to None. This applies in particular when a mapping without that entry is passed directly to Connector(options).
  • Supported values are integers, including zero and negative integers, and None. Values must not be made positive, clamped, or otherwise transformed.

For example:

options = {
    "host": "infoblox.example.org",
    "username": "admin",
    "password": "password",
    "max_results": 50,
}
connector = Connector(options)
assert connector.max_results == 50

With the same required connection options but no max_results entry:

connector = Connector(options_without_max_results)
assert connector.max_results is None

A None default means that the connector does not add a result limit of its own; it must not be replaced with the appliance's WAPI default value.

Connector.from_dict

The public class/static factory must support:

Connector.from_dict(options)

where options is a mapping. The returned connector must use the same option semantics as direct mapping construction:

  • A max_results entry is exposed unchanged as connector.max_results.
  • If the entry is omitted, connector.max_results is None.
  • For example, max_results=50 results in connector.max_results == 50.

Connector.get_object

Preserve the existing GET API, including its current optional arguments and their ordering, with a full call shape equivalent to:

get_object(
    obj_type,
    payload=None,
    return_fields=None,
    extattrs=None,
    force_proxy=False,
    max_results=None,
)

In particular, existing calls involving payload, return_fields, extattrs, or force_proxy must remain compatible, and max_results must remain available as a keyword argument.

Result-limit resolution

Resolve the value used for the WAPI _max_results query parameter as follows:

  1. If the call supplies an integer max_results, that call-specific value takes priority over connector.max_results.
  2. If the call omits max_results, or passes max_results=None, use connector.max_results as the fallback. Thus, a caller that forwards the default value None does not suppress a configured connector-wide limit.
  3. If the resolved value is an integer, include it in the GET URL as _max_results=<value>. Zero and negative integers are real values and must not be treated as though the option were absent.
  4. If the resolved value is None, do not add a connector-derived _max_results query parameter.

The selected integer must be represented unchanged in the query string. In particular, a negative value must retain its minus sign. The connector-wide fallback applies to every URL generated for that GET operation, including any existing proxy-search attempt.

All established GET behavior must continue to work alongside _max_results, including payload query fields, requested return fields, extensible-attribute filters, proxy-search handling, response parsing, and error behavior.

Request examples

For a connector configured with host infoblox.example.org, WAPI version 1.1, and max_results=10:

connector.get_object("network", {})

When invoked with an object type, a payload/query mapping, and an extattrs mapping, it must issue an HTTP GET against the encoded URL described above, passing the connector's default headers and configured HTTP request timeout.

  • Connector._construct_url(self, relative_path, query_params=None, extattrs=None, force_proxy=False) — returns the fully constructed request URL string with the query string encoded as described above.

Parameter semantics used by URL construction
  • query_params: a mapping of ordinary query option names to values.
  • extattrs: a mapping of extensible-attribute names to objects each carrying a value; each entry contributes a query parameter whose name is the attribute name prefixed with * and whose value is that attribute's value.
  • force_proxy: when true, adds a _proxy_search=GM query parameter.

Notes

  • The ordering of the produced query parameters must place extensible-attribute parameters before ordinary query parameters / proxy flags, matching the examples above.
  • Only the encoding behavior of the query string is changing; the base URL, path segment (/network), and overall structure remain the same.
