About BOBA-Bench

280 chains · 140 repositories · 5,600 requests · Updated October 2026

An agent completes 20 requests in sequence on a real repository, each in a fresh conversation, with no feedback; at the end the tests of all 20 must pass. What it measures, how it compares, and the questions we are asked most.

What BOBA-Bench measures

Coding agents are autonomous developers. Given a request, they change the code and report back when done. As such, they can handle not only independent requests but whole chains of them, each request built on the last. Agents are known to report wrong work as done, yet benchmarks still test them one request at a time, on human-written code, checked once.

BOBA-Bench asks what happens when an agent is left alone: 280 chains of 20 consecutive requests from 140 real repositories, 5,600 requests in all. The agent receives the requests one at a time, each in a fresh conversation, on the code it just wrote; after every submission a hidden verifier checks the new request and every protected test, and the agent never hears from it. A chain passes when the repository after request 20 passes every test of all 20 requests (pass@1); the leaderboard also reports how often something protected broke on the way (regression rate) and how many chains delivered every request on its own step without ever breaking anything (strict pass@1).

Each chain is cut from a stretch of a repository's real history wherever the developers added tests. The tests they added are the hidden contract of the request, the specification is written from them, and the change the developers made is the gold reference. Twenty consecutive cuts form a chain in which later requests build on, extend or revise what earlier ones introduced.

The 10 agents on the leaderboard complete 39–66% of chains (51% on average), 28–56% strictly. Taken one at a time they complete 95% of requests on average; chained, 51% of chains. Worse code is not the cause: once checked, agent code is nearly as good a base for later requests as human code (Finding 2). The cause is the mistakes agents miss. They declare a request done once their own tests pass, even when those tests miss a mistake; the next request then builds on broken code and fails about twice as often, and the mistake is rarely found later. Asked whether an implementation is correct, agents are right 53% of the time, barely better than a coin flip (Finding 3). A single external “that's wrong” after a failed request and one repair round lift chain completion from 51% to 59% (Finding 4).

In simpler terms, what limits coding agents left alone is not the code they write but the mistakes they cannot see: without verification, every request that follows is built on broken assumptions. Each request is evaluated by hidden tests; every number on this site is derived from the released records.

Frequently asked questions

How are chains constructed?

Each chain is a stretch of a real repository's history. We walk the commits of 140 Python repositories, cut the walk wherever the developers added or changed tests, and keep a cut only if its new tests fail before the developers' change and pass after it. Twenty consecutive cuts form a chain; each cut becomes a request.

A language model writes the specification of every request from the test diff, the commit messages and the linked issues, never from the developers' patch. Three model families then audit each specification against its hidden tests until all three find it sufficient, and two models must solve the released specifications blind. Specifications and tests are never edited to keep a chain: windows that fail a check are dropped. Finally, the base state of every chain is sealed in an offline container pinned by digest. See what a request looks like.

What does an agent receive?

One specification at a time, each in a fresh conversation, on one repository that persists across the 20 requests: at request k the agent sees the specification of request k and the repository exactly as it left it after request k−1, with no memory of the earlier conversations. It never sees the hidden tests, the specifications of later requests, a budget or a verdict, and works with a single bash tool through mini-swe-agent 2.4.6. All 20 requests always run.

You can find the full prompt here.

How is BOBA-Bench evaluated?

After every submission, a grader running in a fresh container that receives only the agent's git history checks the new state: the tests the developers added at request k (its F2P tests) must pass, and every protected test, the repository's original suite plus the hidden tests of requests 1 to k−1 (the P2P list), must keep passing. Tests written by the agent are discarded. The agent is never told the verdict and the chain continues to request 20 whatever happens.

pass@1 (the headline) is estimated from eight independent attempts per chain: the mean over the attempts of the final repository passing every test of F2P20 ∪ P2P20, with a repository-clustered 95% interval; the first attempt alone is in the Details view. Regression rate and strict pass@1 are means over the same attempts. pass@8 counts a chain whose eight attempts include at least one pass. reached@k is the share of first attempts whose original run graded request k or later. Every number on this site is computed from the released records.

Why report strict pass@1 and the regression rate next to pass@1?

pass@1 only looks at the repository after request 20. A model that ignored every request and repaired everything at request 20 would score the same pass@1 as a model that delivered each request when it was asked; a model that broke the build at request 3 and fixed it at request 19 would too. Strict pass@1 exposes both: it counts only chains in which every request's own tests passed on its own step and no protected test ever broke. The difference pass@1 − strict pass@1 is reported as healing, the share of chains that pass at 20 only because something broken or missing earlier was repaired later. The regression rate adds how often a protected test broke at some point, healed or not, which is what a user of the agent would have experienced along the way. A handful of chains per model are strict but still fail pass@1: a pre-existing test of the original suite is failing before and after request 20 without ever having been protected; the hint under the leaderboard footnotes them.

What is a silent miss?

A submission the agent reported complete whose hidden tests fail. Nobody tells the agent, so the next request is built on the broken state. Silent misses are rare per request: on the leaderboard runs a request fails 3–6% of the time while everything before it is intact, and the rate does not fall as a chain progresses; but failures compound over a chain (twenty requests at 95% each give 36%), which is why models that complete 66–84% of their requests finish far fewer chains. On the leaderboard a silent miss does not end the chain: the agent keeps receiving requests, and the three headline numbers say whether the final repository passes everything (pass@1), whether something protected broke on the way (regression rate) and whether every request was delivered on its own step (strict pass@1).

What requests are in the benchmark? How do you guarantee a chain is feasible?

439 exact-20 windows were cut from two oracle-verified corpora; fifteen rounds of checks left the 280 chains released here. A chain is kept only if:

  1. every request's test patch applies to its base state, at least one of its tests fails before the developers' change and all pass after it (fail-to-pass), and the tests that passed before keep passing (pass-to-pass);
  2. the developers' own patches, replayed one after another in the sealed container, pass every state's contract (the gold walk), twice, in two independent grader runs;
  3. three model reviewers unanimously judge every specification sufficient to pass its hidden tests, after up to two rewrites;
  4. the specification is solvable blind by at least one of two models, or certified as a fair but hard request;
  5. the environment is reproducible, offline and free of test-aware logic, and the grader's verdicts are deterministic;
  6. its contract follows from the specification: 14 chains were dropped because at one request the hidden test could only be satisfied from the developers' own implementation of the earlier requests.

Nothing is repaired to pass a check: windows are dropped, never edited. The construction funnel lists every round and its reason.

What makes a specification adequate?

Because the agent is never shown the hidden tests, every request must be recoverable from its specification alone. Three independent reviewers (GLM-5.2, Claude Fable 5 and GPT-5.6-sol) each read the specification, the hidden test patch and the base repository in a sandbox and return sufficient or insufficient; a specification is accepted only when all three return sufficient on the same text. Dissent sends it to an author model that rewrites it from the reviewers' findings, and the new text is reviewed afresh. 74.6% of specifications were unanimous on the first pass; 1,325 of the 5,600 released request occurrences carry a GPT-5.6-sol rewrite and 49 a Fable 5 rewrite. Examples are on the requests page.

What about the agent's own tests and other changes?

The agent may write and run any tests it likes while working; the grader discards them and applies the frozen test patch of the request in a fresh container. Only the agent's source changes are graded. Editing existing tests, grader files or git metadata is a protocol violation, and the sandbox has no network. A forensic audit of every trajectory in the release (28,212 runs, 14 detector families and a 1,504-item judge sample) found agents trying often but no defeat of the grader in the benchmark.

Does more inference-time compute help?

Retrying a chain from scratch does: under the leaderboard protocol, pass@8 (at least one of eight independent attempts passes) is 11–26 points above pass@1, 60–84% against 39–66%. But 19 of the 280 chains were passed by no model in any of its eight attempts (44 by no model in its first attempt), and more attempts do not make a model notice its own mistakes: the new-failure rate is as high at the end of a chain as at its start (the census). Attempts are a lottery over the same blind spot, not a fix for it.

Does telling the agent that it is wrong help?

Yes. In the Verified setting the agent is told once, in a fresh conversation, that the previous request left tests failing, and gets one repair round before the next request. Every one of the 10 leaderboard models finishes more projects: pass@1 rises by +1 to +22 points (38–67% → 45–74%), and the share of misses repaired by the next request goes from 6–8% to 10–24%. The signal has a cost: repairs break protected tests of their own, so the regression rate rises by +3.2 to +8.9 points. The paper's experiments on the shape of the signal (repeating it, naming the failing tests, a watcher who is sometimes wrong) were run under the paper's protocol and are kept folded under the verification panel.

Is agent-written code a worse base than human code?

Not once it is verified. In the Matched Foundations comparison, the next request is attempted from the agent's own certified code and from the developers' code at the same point of the same chain: the leaderboard's 10 models pass it within −3.6 to +0.8 points of the human base (−0.9 on average). What degrades a chain is building on unverified code: after one unnoticed miss, the next request's own tests fail 14–24 points more often than from a clean state, and the odds roughly double with every additional open mistake.

Can one agent review another?

Barely. In the 10 × 10 review matrix of the leaderboard models (every model reviews every model's wrong implementations and the same requests passed from a correct state, 109 pairs per author, 21,800 reviews) a reviewer in a fresh context with the specification, the repository and the diff judges a submission by writing and running tests. No reviewer tells a wrong implementation from its correct twin in more than 18.8% of pairs: 7 reviewers accept 77–95% of the wrong code, the 3 others reject 42–58% of the correct code; a model reviewing its own code is more lenient still. See the review matrices.

Why mini-swe-agent? Could other scaffolds achieve higher performance?

mini-swe-agent is minimal, open and competitive across benchmarks, which makes the comparison about the models. On a 58-chain subset (52 repositories) we also ran Codex CLI, the OpenHands SDK and pi: first-attempt completion stays between 41.4 and 50.0% across the four scaffolds, with every paired difference inside its confidence interval. A different harness does not help models complete chains unattended.

Have the models seen these repositories before?

Probably, since nearly every change predates their training cutoffs. A near-verbatim recall probe on sampled change blocks (all 10 leaderboard models, same items and controls as the paper) finds that Opus 5.5 reproduces 19.2% of the benchmark blocks but also 13.8% of same-repository code outside the benchmark window (an excess of +4.0 points, interval [−1.7, +10.2]), and the other models at most 15.1%. No model shows a benchmark-specific excess whose interval excludes zero. Memorizing a repository makes it easier for every model, but it does not explain the results: from a certified agent base, where memorized code is of least use, agents do as well as from the human base (matched foundations).

What about other models?

The leaderboard has 10 models. The paper's experiments (the findings on the front page) were run with five models — four of the leaderboard (Claude Fable 5, GPT-6 Astra, Kimi K3, GPT-5.6 Sol) and GLM-5.2, which has no run under the current protocol and therefore does not appear on the leaderboard. The benchmark, grader and harness are in the repository.
